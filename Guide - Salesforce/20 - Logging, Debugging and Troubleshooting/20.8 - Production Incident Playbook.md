# Production Incident Playbook

## The first five minutes

Under pressure, people investigate before they establish what is happening. The order matters.

**1. Establish scope.** How many users, which operation, since when. "Three agents cannot approve claims since about 09:00" is actionable; "the system is broken" is not.

**2. Check whether it is Salesforce.** [status.salesforce.com](https://status.salesforce.com) for the instance. A platform incident changes the entire response — you communicate rather than investigate.

**3. Check what changed.**

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail
WHERE CreatedDate = LAST_N_DAYS:2
ORDER BY CreatedDate DESC
```

**This is the highest-yield query in incident response.** A deployment, a deactivated flow, a changed permission set, a modified validation rule — six months of retention and it names the person.

Alongside it, the deployment history:

```bash
sf project deploy report --target-org production
```

**4. Decide: stop the bleeding, or diagnose?** If data is being corrupted, stop first. If users are blocked but nothing is being damaged, diagnose — a hasty fix frequently makes it worse.

**5. Communicate.** Who is affected, what is known, when the next update comes. A silent team is assumed to be doing nothing.

## Stopping the bleeding

The mechanisms, in order of preference — least invasive first.

**Disable the automation for the affected users.**

```
Setup → Custom Settings → Automation Settings → Manage
    New at the Profile level: Disable_All_Automation__c = true
```

A hierarchy Custom Setting is the fastest lever available, and the reason the bypass mechanism exists. **No deployment, effective immediately, scoped to one profile or one user.**

An untested bypass is the one you discover does not work during the incident, which is why [[11.5 - Trigger Handler Pattern]] insists on testing it.

**Deactivate a flow.** One click in Setup, immediate, and reversible.

**Abort a runaway job.**

```java
System.abortJob('7075g00000ABCDeAAB');
```

Or from Setup, under Apex Jobs.

**Deactivate a validation rule.** Immediate, and it removes a guard — so note it for reinstatement.

**Deactivate a trigger.** Requires a deployment, which is why it is far down this list. The metadata `status` field set to `Inactive` and deployed.

**Whatever you disable, write it down.** Incidents are resolved and the temporary bypass stays on for three months.

## Diagnosing

The sequence from [[16.10 - Performance Profiling Workflow]], adapted for pressure.

**Reproduce it.** As the affected user, in a sandbox if possible. An incident that cannot be reproduced is diagnosed from logs — which only exist if logging was already on.

**Set a narrow trace flag** on the affected user, short expiration, categories not under investigation at NONE. See [[20.2 - Trace Flags and Log Management]].

**Read the limit block first**, then `CODE_UNIT_STARTED` for the shape, then the specific area.

**Check the custom log.** If one exists, it may already hold the answer — with a correlation Id tying the failing transaction together:

```sql
SELECT Context__c, Severity__c, Message__c, Correlation_Id__c, Logged_At__c
FROM Application_Log__c
WHERE Severity__c IN ('Error', 'Fatal') AND Logged_At__c = TODAY
ORDER BY Logged_At__c DESC
```

**This is why the framework exists.** Without it, an unreproducible incident has no evidence at all. See [[20.5 - Custom Logging Frameworks]].

**Check async job outcomes:**

```sql
SELECT ApexClass.Name, Status, NumberOfErrors, ExtendedStatus, CompletedDate
FROM AsyncApexJob
WHERE CreatedDate = LAST_N_DAYS:1 AND Status IN ('Failed', 'Aborted')
```

**Check org limits**, since exhaustion is org-wide and produces confusing symptoms:

```java
for (System.OrgLimit orgLimit : OrgLimits.getAll()) {
    if (orgLimit.getValue() > orgLimit.getLimit() * 0.8) {
        System.debug(orgLimit.getName() + ': ' + orgLimit.getValue()
            + ' of ' + orgLimit.getLimit());
    }
}
```

An exhausted API allocation or async allocation makes unrelated things fail with unhelpful errors.

## Incident patterns

The shapes that recur, with their usual causes.

**"It worked yesterday."** A deployment, a configuration change, or a Salesforce release. `SetupAuditTrail` first.

**"It works for me but not for them."** Permissions, sharing, record type, or profile. Reproduce with `System.runAs` in a sandbox, or with Login As.

**"It fails intermittently."** Contention, concurrency, or a limit near its ceiling. Ask what the failing records share — it is nearly always a common parent or owner. See [[10.8 - Record Locking and Deadlocks]].

**"It fails only at volume."** A query in a loop, or a limit reached at 200 records and not at 20.

**"It fails at the same time each day."** A scheduled job, an integration window, or several batch jobs queueing behind the five-concurrent limit.

**"Data is wrong but nothing errored."** A silent failure — a swallowed exception, an event that exhausted its retries, or an integration that stopped running. The last is the worst, because nothing anywhere reports it.

**"The sync stopped."** Check the last-run timestamp, not the error log. A job that stopped running produces no failure record.

```sql
SELECT Context__c, MAX(Logged_At__c) lastSeen
FROM Application_Log__c
WHERE Logged_At__c = LAST_N_DAYS:7
GROUP BY Context__c
```

## Data damage

The category needing the most care, and where haste causes the most harm.

**Stop the process first.** Disable the automation before assessing scope, or the damage grows while you investigate.

**Assess the scope precisely:**

```sql
SELECT COUNT(Id), Status__c
FROM Warranty_Claim__c
WHERE LastModifiedDate = TODAY AND LastModifiedById = '0055g00000ABCDeAAN'
GROUP BY Status__c
```

**Check field history** for the previous values:

```sql
SELECT ParentId, Field, OldValue, NewValue, CreatedDate
FROM Warranty_Claim__History
WHERE CreatedDate = TODAY AND Field = 'Status__c'
```

**Field history is frequently the only record of the prior state**, and it is why tracking the fields that matter is worth the cost before an incident. See [[22.3 - Field Audit Trail and Data Retention]].

**For deleted records**, the Recycle Bin retains for 15 days:

```sql
SELECT Id, Claim_Number__c, IsDeleted, LastModifiedDate
FROM Warranty_Claim__c WHERE IsDeleted = true AND LastModifiedDate = TODAY ALL ROWS
```

```java
undelete restorableClaims;
```

**Restore from a backup** if history is insufficient. This is where the org's backup strategy is tested, and where its absence becomes expensive.

**Correct in batches with partial success**, not one large DML:

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    // bypass on, so the correction does not re-trigger the automation that caused the damage
    AutomationBypass.bypass('WarrantyClaim');

    for (Warranty_Claim__c claim : scope) {
        claim.Status__c = priorStatusFromHistory.get(claim.Id);
    }

    Database.update(scope, false);
}
```

**Bypassing during the correction** is essential — the automation that caused the problem will run again otherwise.

## Communicating

Three audiences, three messages.

**Users:** what is affected, what to do instead, when the next update comes. Not the cause.

**The business:** scope, impact, and expected resolution time. An honest estimate beats an optimistic one.

**The team:** everything — findings, what has been tried, what is ruled out. A shared channel prevents two people investigating the same thing.

**Update on a cadence**, even when there is nothing new. "Still investigating, next update in 30 minutes" is better than silence.

## After the incident

The part that gets skipped, and the part that prevents recurrence.

**Reinstate what was disabled.** The bypass, the validation rule, the flow. Track them, or they stay off.

**Write it up**, without blame:

```
What happened
Impact — users affected, records affected, duration
Timeline — detection, diagnosis, mitigation, resolution
Root cause
What made it hard to diagnose
Actions
```

**"What made it hard to diagnose" is the most valuable section**, and it is usually the same answers: no logging on that path, no monitoring for that failure mode, no test for that case.

**Add the missing test.** A defect that reached production is a case nobody tested. A test reproducing it means it cannot recur silently.

**Add the missing monitoring.** If the failure was discovered by a user rather than by an alert, that is the gap.

**Add the missing log.** If the diagnosis needed a reproduction, the code path needs logging.

## Preparing before the incident

What separates a thirty-minute incident from a six-hour one, and all of it is built beforehand.

```
[ ] A bypass mechanism, tested
[ ] A custom logging framework, always on
[ ] Correlation Ids across transactions
[ ] Daily alerts on failed jobs and org limits
[ ] Alerts on absence — jobs that stopped running
[ ] Field history on fields that matter
[ ] A tested backup and restore path
[ ] Access to production logs without a change request
[ ] A runbook naming who does what
[ ] A sandbox with production-shaped data for reproduction
```

**The bypass and the logging framework are the two that matter most.** One stops the damage; the other explains it.

## A triage card

```
1. Scope        who, what, since when
2. Platform     status.salesforce.com
3. Changes      SetupAuditTrail, deployment history
4. Stop         bypass setting → deactivate flow → abort job
5. Evidence     custom log → AsyncApexJob → OrgLimits → trace flag
6. Diagnose     limit block → CODE_UNIT_STARTED → the specific area
7. Assess       how many records, what were the prior values
8. Fix          batched, with partial success, automation bypassed
9. Restore      re-enable what was disabled
10. Learn       test, log, monitor
```

## Section 20 in one paragraph

Debug logs answer questions about a transaction you can reproduce, and most production incidents are not reproducible — which is why the limit block is the right place to start reading, why the Developer Console's execution overview is the only tool that attributes time per operation, and why neither is sufficient on its own. A custom logging framework, publishing through platform events so entries survive rollback and carrying a correlation Id across transactions, is the difference between an incident with evidence and one with speculation; Event Monitoring adds what actually happened across the org, if the org has Shield, and `SetupAuditTrail`, `LoginHistory`, and `OrgLimits` cover a useful fraction of it if it does not. Errors mislead in consistent ways — a governor limit names your code when a flow spent the budget, `CONCURRENT_REQUESTS_LIMIT_EXCEEDED` names the victim rather than the cause, and `invalid_grant` says nothing at all. And the response to an incident is decided before it happens: a tested bypass to stop the damage, always-on logging to explain it, field history to reverse it, and alerting on absence, because the integration that stopped running produces no error and is the failure nobody notices.
