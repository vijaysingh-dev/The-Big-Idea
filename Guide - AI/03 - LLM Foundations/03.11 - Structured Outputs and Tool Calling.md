# Structured Outputs and Tool Calling

## Why Structured Output Matters

LLMs generate natural language. Production systems need data. Bridging this gap — making LLMs produce reliably parseable output — is a core AI engineering challenge.

Failure modes without structured output:

- Model responds with explanation instead of JSON
- JSON is syntactically valid but missing required fields
- Model adds markdown code fences (`\```json`) around JSON, breaking` json.loads()`
- Response is structurally correct but field values are unexpected types

---

## Approaches to Structured Output

### Approach 1: Prompt Engineering (Fragile)

```
"Respond ONLY with a JSON object in this format:
{\"sentiment\": \"positive\" | \"negative\", \"confidence\": float}
Output ONLY the JSON. No explanation. No markdown."
```

Works sometimes. Fails when:

- Model is smaller / less instruction-following
- Output is complex with many nested fields
- Temperature is high

### Approach 2: Regex / Parser Post-processing (Brittle)

Extract JSON from model output with regex. Handles the code fence problem but fails on malformed JSON.

```python
import re, json

def extract_json(text):
    match = re.search(r'\{.*\}', text, re.DOTALL)
    if match:
        return json.loads(match.group())
    raise ValueError("No JSON found")
```

### Approach 3: Native Structured Output (Recommended)

Modern APIs support **constrained decoding** — the model's token sampling is constrained to only produce valid tokens for the specified schema. Guarantees syntactic validity.

**OpenAI (response_format)**:

```python
from pydantic import BaseModel

class SentimentResult(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    confidence: float
    key_phrases: list[str]

response = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[{"role": "user", "content": f"Analyze: {text}"}],
    response_format=SentimentResult,
)
result = response.choices[0].message.parsed  # type: SentimentResult
```

**Anthropic (tool use for structured output)**: Anthropic doesn't have a `response_format` parameter — use tool calling with a single tool instead:

```python
response = client.messages.create(
    model="claude-opus-4-5",
    tools=[{
        "name": "return_analysis",
        "description": "Return structured analysis",
        "input_schema": SentimentResult.model_json_schema()
    }],
    tool_choice={"type": "tool", "name": "return_analysis"},
    messages=[{"role": "user", "content": text}]
)
```

**Outlines / Instructor library**: For open-source models, libraries like Outlines enable constrained decoding at the sampling level.

## Tool Calling / Function Calling

Tool calling allows the model to request the execution of an external function. The model doesn't execute the tool — it outputs a structured description of what tool to call with what arguments; your code executes it.

### Flow

```
1. You send:    [user message] + [list of available tools]
2. Model decides it needs a tool → outputs ToolUse block
3. You execute: call the actual function with provided arguments
4. You send:    tool result back to model
5. Model uses:  tool result to compose final response
```

### OpenAI Tool Calling

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_stock_price",
        "description": "Get current stock price for a ticker symbol",
        "parameters": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker, e.g. AAPL"},
            },
            "required": ["ticker"]
        }
    }
}]

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What's Apple's stock price?"}],
    tools=tools,
)

# Check if model wants to call a tool
if response.choices[0].message.tool_calls:
    tool_call = response.choices[0].message.tool_calls[0]
    args = json.loads(tool_call.function.arguments)
    # {"ticker": "AAPL"}
    
    # Execute the actual function
    result = get_stock_price(args["ticker"])
    
    # Send result back
    messages.append(response.choices[0].message)
    messages.append({"role": "tool", "tool_call_id": tool_call.id, "content": str(result)})
    
    # Get final response
    final = client.chat.completions.create(model="gpt-4o", messages=messages)
```

### Tool Design Principles

**Good tool design**:

```python
{
    "name": "search_documents",
    "description": "Search the internal knowledge base for relevant documents. Use when the user asks about company policies, procedures, or historical data.",
    "parameters": {
        "query": {"type": "string", "description": "Search query in natural language"},
        "date_filter": {"type": "string", "description": "Optional: filter to documents after this date (YYYY-MM-DD)"},
    }
}
```

**Bad tool design**:

```python
{
    "name": "search",
    "description": "Search",  # ← too vague, model won't know when to use it
    "parameters": {"q": {"type": "string"}}  # ← field names should be descriptive
}
```

Rules:

- **Description is critical**: The model uses the description to decide whether and when to call the tool
- **Parameter names should be self-documenting**
- **Include when-to-use guidance** in the description
- **Fewer tools is better**: With 50 tools, the model struggles to pick the right one

## Parallel Tool Calls

Modern models support calling multiple tools in one response:

```python
# Model might respond with:
tool_calls = [
    {"name": "get_stock_price", "args": {"ticker": "AAPL"}},
    {"name": "get_stock_price", "args": {"ticker": "MSFT"}},
    {"name": "get_market_news", "args": {"topic": "tech stocks"}},
]
```

Execute these in parallel (asyncio), then send all results back together. This reduces latency for multi-tool workflows.

## Constrained Decoding Internals

When you specify a JSON schema, the inference engine constructs a **logit mask** at each token step — setting to -∞ any token that would make the output syntactically invalid given the schema and current state.

For example, if you're in a string value of a boolean field, only "true" and "false" tokens are allowed.

This is guaranteed syntactic validity, but NOT semantic validity. The model still might put "negative" in a field that should be "positive" — it just can't put an integer there.
