# CAP Theorem and PACELC

> **Revision tags:** #fundamentals #distributed-systems #cap  
> **Related:** [[01.6 - Consistency Models]] | [[01.11 - Distributed Concepts]]

---

## CAP Theorem

### The Statement

In a distributed system, during a **network partition**, you can have only **one** of:
- **Consistency (C):** Every read returns the most recent write
- **Availability (A):** Every request gets a non-error response (may not be the latest data)

> Partition Tolerance (P) is not optional — partitions happen in any distributed system. The choice is always **C vs A** during a partition.

### What Each Means Precisely

**Consistency (C) in CAP:**  
This is *linearizability* — after a write completes, every subsequent read anywhere in the cluster reflects that write. Not "eventual" — immediate.

**Availability (A) in CAP:**  
Every non-failing node that receives a request must respond. Not "sometimes" — always.

**Partition Tolerance (P):**  
The system continues operating even when network messages between nodes are dropped or delayed.

### The Real Choice

```
Normal operation (no partition): you can have C AND A.
During a partition: you MUST choose.
```

**Choose C over A (CP systems):**  
- If the partition means we can't guarantee the latest data, return an error rather than stale data.
- Examples: HBase, ZooKeeper, etcd, MongoDB (with strong consistency)
- Use when: financial systems, inventory counts, anything where stale data causes real harm

**Choose A over C (AP systems):**  
- During a partition, respond with possibly stale data rather than fail.
- Nodes diverge; data syncs when partition heals (eventual consistency).
- Examples: Cassandra, CouchDB, DynamoDB (default), DNS
- Use when: social feeds, product catalogs, recommendation systems

### The Most Common Misunderstanding

CAP is about *partition scenarios only*. It says nothing about performance or normal operation. Engineers often misuse it as "Cassandra trades consistency for performance" — that's not CAP, that's a different tradeoff.

## PACELC — Extending CAP

CAP doesn't say anything about performance during *normal operation* (no partition). PACELC fills this gap.

### The Framework

```
IF Partition THEN Availability vs Consistency
ELSE          Latency vs Consistency
```

**P → A vs C** (same as CAP)  
**E → L vs C** (during normal operation: low latency OR strong consistency)

### Why the E-L-C Tradeoff Matters

Strong consistency during normal operation requires:
- Quorum reads/writes (wait for majority of nodes to agree)
- Synchronous replication

Both add latency. Systems that prioritize low latency relax consistency.

### PACELC Classification of Real Systems

| System | Partition Choice | Normal Choice | Classification |
|---|---|---|---|
| DynamoDB (default) | Availability | Latency | PA/EL |
| Cassandra | Availability | Latency | PA/EL |
| PostgreSQL (single node) | N/A | Consistency | PC/EC |
| MySQL with sync replication | Consistency | Consistency | PC/EC |
| HBase | Consistency | Consistency | PC/EC |
| MongoDB (tunable) | Configurable | Configurable | Tunable |

## Practical Implications for System Design

### When to choose CP

- Payment processing — a double-charge is worse than an error
- Inventory management — overselling is worse than a failed purchase
- Leader election — only one leader can exist
- Distributed locking — correctness requires agreement

### When to choose AP

- User profiles — serving a slightly stale bio is fine
- Product catalog — showing yesterday's price for a second is acceptable
- Social feeds — eventual consistency matches user expectations
- DNS — stale resolution is better than no resolution

### The Spectrum, Not Binary

Real systems implement tunable consistency:
- DynamoDB: Read consistency level (eventual vs strong)
- Cassandra: Quorum levels (ONE, QUORUM, ALL)
- CockroachDB: Serializable isolation

You don't always pick one extreme. You pick the right level per operation.

---

## How to Talk About CAP in Interviews

**Don't say:** "I'll use Cassandra because it's CP."  
(Cassandra is AP by default.)

**Do say:** "For the transaction ledger I need CP — I'd use PostgreSQL with synchronous replication. For the user activity feed, AP is fine — Cassandra or DynamoDB with eventual consistency gives me the write throughput I need and stale reads are acceptable."

The signal interviewers want: you understand that consistency is a per-operation decision, not a database-level flip switch.
