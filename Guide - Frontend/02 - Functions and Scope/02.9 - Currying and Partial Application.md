# Currying and Partial Application

Two related techniques for producing specialized functions from general ones. They are frequently conflated; the distinction is small but worth getting right, because interviewers ask about it.

**Currying** transforms a function of N arguments into N chained functions of one argument each: `f(a, b, c)` becomes `f(a)(b)(c)`.

**Partial application** fixes *some* arguments and returns a function taking the rest: `f(a, b, c)` with `a` fixed becomes `g(b, c)`. The result is called with the remaining arguments in one go.

```js
const add = (a, b, c) => a + b + c;

// Curried
const curried = a => b => c => a + b + c;
curried(1)(2)(3); // 6

// Partially applied
const partial = add.bind(null, 1);
partial(2, 3);    // 6
```

Both are just closures ([[02.3 - Closures]]) capturing the arguments supplied so far.

## A generic curry

The standard implementation collects arguments until it has enough, using `fn.length` — the declared parameter count — as the threshold.

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...rest) => curried.apply(this, [...args, ...rest]);
  };
}

const volume = curry((l, w, h) => l * w * h);

volume(2)(3)(4);   // 24
volume(2, 3)(4);   // 24
volume(2)(3, 4);   // 24
volume(2, 3, 4);   // 24
```

This is "loose" currying — it accepts arguments in any grouping, which is what Lodash's `_.curry` does and what interviewers usually want.

Two real limitations of the `fn.length` approach: it breaks on default parameters and rest parameters, since both stop the count. `(a, b = 1) => {}` has `length === 1`, so the curried version fires after one argument. Any curried function must therefore have a fixed, explicit arity.

## Why the argument order matters

Currying is only useful if the argument you want to fix comes *first*. This drives an API design convention: **configuration before data**.

```js
// Data-last — composes well
const filter = predicate => array => array.filter(predicate);
const map = fn => array => array.map(fn);

const activeNames = pipe(
  filter(u => u.active),
  map(u => u.name)
);

activeNames(users);
```

Native array methods are data-first (`array.filter(fn)`), which is why functional libraries like Ramda ship data-last versions of everything. If you find yourself writing wrapper after wrapper to reorder arguments, that is the signal you want a data-last API.

## Practical uses

**Pre-configured loggers and clients:**

```js
const createLogger = level => module => message =>
  console.log(`[${level}] ${module}: ${message}`);

const errorLog = createLogger("ERROR");
const authError = errorLog("auth");

authError("token expired");
```

**Event handler factories in React:**

```js
function TodoList({ todos, onToggle }) {
  const handleToggle = id => () => onToggle(id);

  return todos.map(t => (
    <li key={t.id} onClick={handleToggle(t.id)}>{t.text}</li>
  ));
}
```

Readable, but note it creates a new function per item per render. For a memoized list item this defeats `React.memo`. The alternative is to read the id from a `data-id` attribute in a single stable handler, or delegate to the parent ([[12.4 - Event Delegation]]). For a list of ten it does not matter; for a virtualized list of thousands it does.

**Validation and middleware composition:**

```js
const minLength = n => value =>
  value.length >= n ? null : `Must be at least ${n} characters`;

const validators = [minLength(8), hasDigit, hasSymbol];
const errors = validators.map(v => v(password)).filter(Boolean);
```

Each validator is a plain single-argument function, so they compose, are individually testable, and can be assembled from configuration.

**Redux middleware** is a triple-curried function by design: `store => next => action => {}`. Understanding currying is a prerequisite for reading it ([[20.5 - Middleware and Thunks]]).

## How senior engineers actually use this

**They use partial application constantly and full currying rarely.** Fixing a config argument to produce a specialized function is everyday work. Chained single-argument calls are mostly confined to functional-programming codebases and library internals.

**They design for data-last where composition matters.** Validation pipelines, data transforms and middleware benefit. Ordinary business functions do not, and forcing currying on them hurts readability.

**They prefer explicit closures over a generic `curry` helper.** `const errorLog = msg => log("ERROR", msg)` is clearer to a reader, keeps types intact in TypeScript, and produces better stack traces than a generic curry wrapper. Generic curry has a real cost: TypeScript inference on variadic curried functions is fragile, and debugging steps through anonymous frames.

**They watch for identity churn in React.** Any curried factory called during render allocates a new function. Fine by default; a problem at memoization boundaries.

## Common pitfalls

- Currying a function with default or rest parameters and getting the arity wrong.
- Losing `this` — a curried method detaches from its object. Bind first, or avoid `this` entirely.
- Over-currying application logic until stack traces are unreadable and breakpoints have nowhere useful to land.
- Assuming currying improves performance. It adds closure allocations; the benefit is expressiveness only.
- Forgetting that a curried function holds its captured arguments alive as long as the partial exists.

## Interview angle

Two things get asked: "difference between currying and partial application", and "implement curry". For the first, state it crisply — currying converts to a chain of unary functions, partial application fixes some arguments and returns a function of the rest. For the second, write the `fn.length` accumulator version and volunteer its limitations with defaults and rest parameters, plus the `bind` alternative for simple partial application.
