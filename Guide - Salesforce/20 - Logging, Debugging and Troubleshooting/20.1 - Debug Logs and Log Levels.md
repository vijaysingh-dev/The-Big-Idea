# Debug Logs and Log Levels

## The problem with debug logs

A single save on a busy object produces a log of 40,000 lines, most of it noise. Reading it top to bottom is the wrong approach and the reason people find logs unhelpful.

**Read a log in this order:**

1. The limit block at the end
2. The `CODE_UNIT_STARTED` entries, for the shape of what ran
3. The specific area the first two point at

## Log levels

Set per category, and the categories matter more than the levels.

```
NONE
ERROR
WARN
INFO
DEBUG
FINE
FINER
FINEST
```

**The categories:**

```
Apex Code           method entry and exit, System.debug, exceptions
Apex Profiling      cumulative limit usage, per-namespace
Callout             HTTP request and response detail
Database            SOQL, DML, and their row counts
System              System method calls
Validation          validation rule evaluation
Visualforce
Workflow            flows, workflow rules, process builder
NBA                 Einstein Next Best Action
Wave                CRM Analytics
```

## Level presets worth using

**Diagnosing a limit failure:**

```
Apex Code:      DEBUG
Apex Profiling: FINE
Database:       INFO
Workflow:       INFO
Everything else: NONE
```

`Apex Profiling` at FINE gives the per-namespace limit block, which is what shows a managed package consuming 60 queries.

**Diagnosing an integration:**

```
Callout:        FINEST
Apex Code:      DEBUG
Database:       INFO
Everything else: NONE
```

`Callout` at FINEST logs the full request and response, including headers — which is where a malformed payload or a wrong content type becomes visible.

**Diagnosing declarative automation:**

```
Workflow:       FINER
Validation:     INFO
Database:       INFO
Apex Code:      INFO
```

`Workflow` at FINER shows each flow element evaluating, with its inputs and outputs.

**Avoid FINEST on Apex Code** unless you specifically need method-level entry and exit. It multiplies log size several times over and pushes past the size cap, truncating the part you actually needed.

## The 20 MB truncation

**A log over 20 MB is truncated**, and the truncation removes the **middle** — keeping the beginning and the end.

That is deliberate and it is why the limit block at the end survives. It also means a long transaction's interesting middle section can be gone entirely.

When a log truncates:

**Lower the levels.** Set everything not under investigation to NONE.

**Narrow the operation.** Reproduce with one record rather than 200.

**Use checkpoints** instead, which capture state at a point without logging everything. See [[20.4 - Heap Dumps and Checkpoints]].

## Reading the limit block

The first thing to look at, every time.

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 94 out of 100
  Number of query rows: 41203 out of 50000
  Number of SOSL queries: 0 out of 20
  Number of DML statements: 118 out of 150
  Number of DML rows: 8420 out of 10000
  Maximum CPU time: 8214 out of 10000
  Maximum heap size: 3145728 out of 6000000
  Number of callouts: 0 out of 100

LIMIT_USAGE_FOR_NS|northwind_pkg|
  Number of SOQL queries: 12 out of 100
```

**The namespace headers matter.** A managed package has its own budget, and its consumption appearing separately is one of the few genuine advantages of managed packages. See [[16.1 - Why Governor Limits Exist]].

**Anything above 70% on a routine operation is a warning**, not a pass. Data grows and automation accumulates.

## Reading the execution shape

`CODE_UNIT_STARTED` and `CODE_UNIT_FINISHED` bracket each unit of execution, and the nesting shows the cascade.

```
CODE_UNIT_STARTED [EXTERNAL] DML BEGIN Op:Insert Type:Claim_Part__c
  CODE_UNIT_STARTED [EXTERNAL] Trigger:ClaimPartTrigger after insert
    DML_BEGIN [2] Op:Update Type:Warranty_Claim__c Rows:48
      CODE_UNIT_STARTED [EXTERNAL] Trigger:WarrantyClaimTrigger before update
      CODE_UNIT_STARTED [EXTERNAL] Flow:Claim_Approval_Routing
      CODE_UNIT_STARTED [EXTERNAL] Trigger:WarrantyClaimTrigger after update
        DML_BEGIN [3] Op:Update Type:Asset Rows:12
          CODE_UNIT_STARTED [EXTERNAL] Trigger:AssetTrigger after update
```

**Each nesting level is a cascade level.** Four deep on one user action is an org where automation accumulated without an owner, and it is the usual explanation for a CPU limit failure on an operation that looks trivial. See [[11.9 - Triggers and Order of Execution]].

**Scanning for `CODE_UNIT_STARTED` alone** gives the shape of the transaction in twenty lines rather than forty thousand:

```bash
grep "CODE_UNIT_STARTED" debug.log
```

## Finding a query in a loop

```bash
grep "SOQL_EXECUTE_BEGIN" debug.log | sort | uniq -c | sort -rn | head -20
```

```
    200 SOQL_EXECUTE_BEGIN|[47]|Aggregations:0|SELECT Id, SerialNumber FROM Asset WHERE Id = :tmpVar1
      3 SOQL_EXECUTE_BEGIN|[12]|Aggregations:0|SELECT Id FROM Machine_Coverage__c WHERE ...
      1 SOQL_EXECUTE_BEGIN|[8]|Aggregations:1|SELECT COUNT() FROM Warranty_Claim__c WHERE ...
```

**A query appearing 200 times is in a loop**, and the bracketed number is the line. That single command resolves most query-limit investigations in an unfamiliar codebase.

## Reading rows retrieved

```
SOQL_EXECUTE_BEGIN|[31]|Aggregations:0|SELECT Id, Name FROM Account WHERE ...
SOQL_EXECUTE_END|[31]|Rows:18420
```

**`Rows` is where a heap problem becomes visible.** A query returning 18,000 wide records will exhaust the 6 MB synchronous heap on its own, and the failure appears later in an unrelated line.

Watch for a query with a high row count and a wide field list — that combination is the usual cause of `Apex heap size too large`. See [[16.3 - CPU Time and Heap Size]].

## System.debug

```java
System.debug('Processing ' + claims.size() + ' claims');
System.debug(LoggingLevel.ERROR, 'Coverage lookup failed for asset ' + assetId);
System.debug(LoggingLevel.WARN, JSON.serializePretty(payload));
```

**Specifying a level lets the statement survive a low Apex Code setting.** A `System.debug` at ERROR appears even when the category is set to ERROR, which is how a permanently useful diagnostic can be left in place without producing noise.

Three cautions:

**`System.debug` costs CPU even when the log level would suppress it**, because the string is constructed before the call. In a loop over 10,000 records that is measurable.

```java
// The concatenation happens regardless of the log level
for (Warranty_Claim__c claim : claims) {
    System.debug('Processing ' + claim.Claim_Number__c + ' at ' + claim.Claim_Amount__c);
}
```

**Never log personal or payment data.** Debug logs are readable by anyone with the permission and are retained.

**Remove diagnostic debugging before merging.** A codebase littered with `System.debug('here 3')` is a codebase where logs are useless.

## Structured debug output

For anything worth keeping, structure beats prose.

```java
System.debug(LoggingLevel.INFO, JSON.serializePretty(new Map<String, Object>{
    'context' => 'ClaimApproval',
    'claimCount' => claims.size(),
    'queriesUsed' => Limits.getQueries(),
    'cpuMs' => Limits.getCpuTime()
}));
```

Searchable, parseable, and it survives being read six months later.

## Log retention and volume

```
Retained for 7 days
Capped at 1,000 MB per org, oldest deleted first
A trace flag expires after a set window, maximum 24 hours
```

**The 1,000 MB cap is reached quickly** when a trace flag is left on a busy integration user — and when it fills, older logs are deleted, including ones you needed.

Leaving a trace flag on the Automated Process user in a busy org will consume the allocation in hours.

## What logs do not capture

Worth knowing so time is not spent looking.

**Anything with no trace flag.** Logs are not retroactive; if the trace flag was not set when the error occurred, there is no log.

**Some platform-internal operations**, including parts of sharing recalculation.

**The full picture across async boundaries.** A Queueable produces its own log under a different user, and correlating them means matching request Ids.

**Formula field evaluation** in most cases.

That first point is the important one operationally: **a production incident cannot be diagnosed from logs unless logging was already on.** That is the argument for a persistent custom logging framework rather than relying on debug logs. See [[20.5 - Custom Logging Frameworks]].

## A reading workflow

```
1. Limit block          → which resource is the constraint
2. grep CODE_UNIT_STARTED → what ran, and how deeply nested
3. grep SOQL_EXECUTE_BEGIN | uniq -c → is anything in a loop
4. Check Rows on the largest queries → heap risk
5. Read the section the above points at
6. Add targeted System.debug and reproduce, if still unclear
```

**Do not start at step 5.** Reading a 40,000-line log linearly is how people conclude that debug logs are unhelpful.

## Downloading and searching

```bash
sf apex list log --target-org production
sf apex get log --log-id 07L5g00000ABCDeAAN --target-org production > debug.log
sf apex tail log --target-org my-sandbox --color
```

`apex tail log` streams logs as they are generated, which is the fastest loop when reproducing something interactively.

For anything large, downloading and using command-line tools beats the Developer Console:

```bash
grep -n "FATAL_ERROR" debug.log
grep -c "SOQL_EXECUTE_BEGIN" debug.log
awk '/CODE_UNIT_STARTED/,/CODE_UNIT_FINISHED/' debug.log | head -100
```

## Practical guidance

**Start at the limit block**, not the top.

**Set categories to NONE** except the ones under investigation.

**Avoid FINEST on Apex Code** unless you need method-level tracing.

**Use `grep` on `CODE_UNIT_STARTED`** to see the transaction's shape in twenty lines.

**Use `uniq -c` on `SOQL_EXECUTE_BEGIN`** to find a query in a loop.

**Check `Rows`** on large queries when diagnosing heap.

**Specify a logging level** on debug statements worth keeping.

**Never log personal or payment data.**

**Remember logs are not retroactive** — that is what a custom logging framework is for.
