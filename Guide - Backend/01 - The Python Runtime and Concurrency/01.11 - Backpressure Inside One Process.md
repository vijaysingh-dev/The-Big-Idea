# Backpressure Inside One Process

#backend #python #asyncio #reliability

> **In one line:** If work arrives faster than you can finish it, something must slow down the sender or start refusing work — and if you do not choose which, the answer defaults to "grow memory until the process dies".

---

## The Idea

**Backpressure** is the signal that travels *backwards* from a slow consumer to a fast producer, telling it to ease off.

Without it, the picture is simple and bad:

```
Producer: 1000/sec ──►  [ queue ]  ──► Consumer: 500/sec
                            │
                            └── grows by 500 items every second, forever
```

Memory climbs. Latency climbs, because each item waits behind a longer queue. Eventually the process is OOM-killed and every queued item is lost.

⚠️ **Async makes this worse, not better.** With threads, the thread pool size was an accidental limit. With coroutines you can create a million tasks for almost nothing, so there is no accidental limit at all. Every limit must be deliberate.

💡 **The key realisation: an unbounded queue does not solve overload, it hides it.** It converts a fast, visible failure (rejection) into a slow, invisible one (rising latency and memory), and the slow one is much harder to diagnose and much more damaging.

---

## The Three Responses to Overload

When you cannot keep up, you have exactly three options. There is no fourth.

| Response | Mechanism | Use when |
|---|---|---|
| **Slow the producer** | Block or `await` until there is room | The producer can wait — internal pipelines, file processing |
| **Reject the work** | Return 503 immediately | The producer cannot wait — HTTP requests |
| **Drop something** | Discard old or low-value items | Fresh data beats complete data — metrics, presence, live prices |

Buffering is not a fourth option. Buffering is a delay before you have to pick one of the three anyway, with more memory used and more latency added.

## Mechanism 1 — Bounded Queues

```python
queue = asyncio.Queue(maxsize=1000)

async def producer():
    async for item in source:
        await queue.put(item)         # blocks when full — this IS the backpressure

async def consumer():
    while True:
        item = await queue.get()
        try:
            await process(item)
        finally:
            queue.task_done()
```

`maxsize` is the whole mechanism. `await queue.put()` on a full queue suspends the producer until there is room. The pressure propagates backwards automatically.

⚠️ **`asyncio.Queue()` with no `maxsize` is unbounded**, and it is the default. Every unbounded queue in your codebase is a memory leak waiting for a traffic spike.

Choosing the size:

```
maxsize = consumer throughput × how long you are willing to wait
```

Consumer does 500/sec, you accept 2 seconds of buffering → `maxsize = 1000`.

A larger queue does not increase throughput. It only adds latency. The queue's job is to absorb short bursts, not sustained overload — nothing absorbs sustained overload.

### Non-blocking variants for the drop strategy

```python
try:
    queue.put_nowait(item)
except asyncio.QueueFull:
    dropped_total.inc()
```

Or drop the oldest, which is usually right for live data:

```python
if queue.full():
    queue.get_nowait()               # discard the stalest item
queue.put_nowait(item)
```

For a live price feed or a presence update, the newest item is the only one that matters. Delivering a stale one late is worse than not delivering it.

## Mechanism 2 — Semaphores

For limiting concurrency rather than buffering.

```python
sem = asyncio.Semaphore(50)

async def fetch(url):
    async with sem:
        return await client.get(url)
```

⚠️ **A semaphore bounds concurrency but not admission.**

```python
async with asyncio.TaskGroup() as tg:
    for url in million_urls:
        tg.create_task(fetch(url))       # 1,000,000 Task objects created immediately
```

Only 50 run at once, but a million Tasks exist, each a few KB. That is gigabytes of memory before any useful work happens.

The fix is a worker pool over a bounded queue:

```python
async def run_bounded(items, worker_count=50, queue_size=200):
    queue = asyncio.Queue(maxsize=queue_size)

    async def worker():
        while True:
            item = await queue.get()
            try:
                await process(item)
            finally:
                queue.task_done()

    async with asyncio.TaskGroup() as tg:
        workers = [tg.create_task(worker()) for _ in range(worker_count)]
        for item in items:
            await queue.put(item)        # backpressure on the feed
        await queue.join()
        for w in workers:
            w.cancel()
```

Constant memory regardless of input size. **This function is worth keeping in your standard toolkit.**

## Mechanism 3 — TCP Backpressure

The most elegant one, because it reaches all the way to the client.

```python
async def stream_data(writer: asyncio.StreamWriter):
    async for chunk in produce():
        writer.write(chunk)
        await writer.drain()          # suspends if the client is not keeping up
```

`write()` buffers. `drain()` waits until that buffer is below the low-water mark. If the client reads slowly, its TCP receive window shrinks, your send buffer fills, and `drain()` suspends your producer.

```
Slow client ──► TCP window shrinks ──► your send buffer fills
             ──► drain() suspends ──► producer stops
```

⚠️ **`write()` without `drain()` is an unbounded memory buffer.** This is the standard bug in streaming code, and it does not appear in testing because your test client reads instantly.

Same idea at the transport level:

```python
transport.set_write_buffer_limits(high=256 * 1024, low=64 * 1024)
transport.pause_reading()      # stop consuming from the socket
transport.resume_reading()
```

uvicorn does exactly this on incoming request bodies — see [[01.9 - ASGI and How Uvicorn Serves a Request]].

The TCP mechanism itself is covered in [[02.4 - Flow Control and Congestion Control]].

## Mechanism 4 — Admission Control

For HTTP, the producer is a user who cannot be asked to wait indefinitely. So reject.

```bash
uvicorn app:app --limit-concurrency 1000
```

Above 1000 in-flight requests, uvicorn returns 503 immediately. The load balancer can retry elsewhere.

Better, shed selectively based on your actual health signal:

```python
class LoadShedder:
    def __init__(self, max_lag_ms=100, max_queue=500):
        self.max_lag_ms = max_lag_ms
        self.max_queue = max_queue

    def should_shed(self, path: str) -> bool:
        if path in ("/health", "/ready"):
            return False
        if current_loop_lag_ms() > self.max_lag_ms:
            return True
        return work_queue.qsize() > self.max_queue
```

💡 **Shed the cheapest-to-reject and least valuable work first.** Health checks never. A paid customer's write before an anonymous read. Latency-sensitive before batch. A 503 in 1ms is a far better outcome than a 200 in 30 seconds, because the client can retry the first and has already given up on the second.

Full treatment in [[11.4 - Backpressure and Load Shedding]].

## Choosing Per Data Type

| Data | Strategy | Why |
|---|---|---|
| HTTP requests | Reject (503) | User is waiting; queueing helps nobody |
| Database writes from a pipeline | Slow the producer | Correctness matters, the producer can wait |
| Log lines | Drop, with a counter | Losing logs beats losing the service |
| Metrics | Drop oldest | Newest sample is the useful one |
| WebSocket broadcast to a slow client | Drop or disconnect that client | One slow client must not slow everyone |
| Financial transactions | Slow the producer, never drop | Losing one is unacceptable |
| Presence / typing indicators | Drop freely | Stale presence is worthless anyway |
| Kafka consumption | Slow the producer (stop polling) | The log is durable — it will wait |

⚠️ **The WebSocket row causes real outages.** A broadcast loop that awaits `drain()` on every client means the slowest client sets the pace for everyone. Give each client a bounded outbound queue and disconnect one that stays full. See [[04.7 - Presence Fanout and Backpressure]].

## In Production

### The symptom shape

Backpressure failures look distinctive:

```
Memory:   ───────╱╱╱╱╱╱╱╱  climbs steadily, never recovers
Latency:  ───────╱╱╱╱╱╱╱╱  climbs with it
CPU:      ────────────────  flat, and not high
Errors:   ────────────────  zero, until the OOM kill
```

Zero errors with rising memory and latency is the giveaway. The system is *accepting* everything and *completing* nothing. A system with backpressure would be showing you errors, which is the healthier failure.

### Every queue needs three things

1. **A size limit.** Always. No exceptions.
2. **A depth metric.** Queue depth is your earliest overload signal — it moves before latency does.
3. **A documented full policy.** Written down: block, reject, or drop. If nobody chose, the answer is "grow until OOM".

```python
class BoundedQueue:
    def __init__(self, maxsize: int, name: str, on_full: str = "block"):
        self._q = asyncio.Queue(maxsize=maxsize)
        self.name = name
        self.on_full = on_full

    async def put(self, item):
        queue_depth.labels(self.name).set(self._q.qsize())
        if self.on_full == "block":
            await self._q.put(item)
        elif self.on_full == "drop_new":
            try:
                self._q.put_nowait(item)
            except asyncio.QueueFull:
                queue_dropped.labels(self.name).inc()
        elif self.on_full == "drop_old":
            if self._q.full():
                self._q.get_nowait()
                queue_dropped.labels(self.name).inc()
            self._q.put_nowait(item)
```

Forcing `on_full` to be an explicit argument means nobody can create a queue without having made the decision. That is a small API design choice with a large effect.

### The audit worth doing today

Grep your services for:

```bash
rg "asyncio.Queue\(\)"          # unbounded
rg "Queue\(maxsize=0\)"         # unbounded, spelled differently
rg "\.write\(" --type py        # is there a drain() after it?
rg "create_task" --type py      # is anything bounding these?
rg "gather\(\*"                 # how large can that list get?
```

Every hit is a potential memory incident. Most take five minutes to fix.

### It has to reach the source

Backpressure only works if it propagates all the way back:

```
Database slow
  → writer queue fills
    → parser slows
      → downloader slows
        → HTTP client stops fetching
          → OK. The pressure reached the source
```

Break the chain anywhere — one unbounded queue in the middle — and everything upstream of it keeps running at full speed. Memory accumulates at that one break point.

💡 **When diagnosing, find the unbounded buffer.** It is always the component whose memory is growing, and it is always immediately upstream of the actual slow thing.

**Part 1 — Watch it die.** Three-stage pipeline (fetch → parse → write), no bounds, consumer artificially 3x slower than the producer. Run for five minutes logging RSS, queue depth and latency every second.

Chart it. Note the exact moment memory becomes the problem and the moment the OOM killer arrives. **Save this chart** — it is the picture of an entire category of production incident.

**Part 2 — Bound it.** Same pipeline with bounded queues. Same load. Memory should be flat and throughput should be identical, because throughput was always limited by the slowest stage. This is the point people find counterintuitive: bounding costs you nothing in throughput and saves you everything in memory.

**Part 3 — All three policies.** Run the bounded pipeline with `block`, `drop_new` and `drop_old`. Chart memory, latency, and items lost for each. Then write down which you would pick for: log shipping, order processing, a live price feed, and user analytics — with reasoning.

Then use `ss -tmi` to observe the send queue and window on the server side. You are watching TCP flow control do the work for you.

**Part 5 — The slow client incident.** Broadcast server, 100 clients, 5 reading at 1KB/sec. Naive version: measure message latency for the 95 fast clients and watch it track the slow ones. Fixed version: per-client bounded queue with a disconnect policy. Same measurement.

**Chart both.** This is Conduit phase 3's core design problem, solved before you meet it.

**Part 6 — Load shedding.** FastAPI app with a shedder driven by loop lag. Overload it. Chart p99 and error rate with the shedder off and on.

Off: p99 climbs to tens of seconds, zero errors, then a health-check failure and a restart. On: p99 stays flat and some requests get a fast 503. Write down which failure you would rather explain to a customer.
