# Secrets and Key Management

#backend #security #operations

> **In one line:** The best secret is one that does not exist, the second best is one that expires in an hour, and the worst is a static string that has been in your environment variables since 2023.

---

## The Idea

[[10.8 - Configuration and Secrets]] covered delivery — where secrets live and how they reach your process. **This note is about the cryptographic side: keys, encryption at rest, and what happens when something leaks.**

```
No secret         workload identity           ← best
Short-lived       dynamic credentials, 1h TTL
Rotatable         static, with dual-value support
Static forever    ← the one you actually have
```

💡 **The hierarchy is about blast radius over time.** A leaked workload identity token is useless in five minutes; a leaked API key from 2023 works until someone notices.

## Eliminating Secrets

```python
# ❌ a static database password
DATABASE_URL = "postgresql://app:hunter2@db:5432/conduit"

# ✅ workload identity — the platform proves who you are
credentials = await google.auth.default()
```

💡 **Workload identity is strictly better than any secret manager where it is available.** The platform issues a short-lived token based on the pod's service account — **there is nothing to rotate, nothing to leak, and nothing to store.**

| Platform | |
|---|---|
| GCP | Workload Identity |
| AWS | IRSA (IAM Roles for Service Accounts) |
| Azure | Managed Identity |
| Kubernetes → anything | **OIDC federation** |

⚠️ **It does not cover third-party credentials.** A Stripe key or an OpenAI key still has to come from somewhere — **and those are the ones worth putting in a proper secret manager.**

### Dynamic secrets

```python
creds = await vault.read("database/creds/app")
# username: v-app-x7k2..., password: ..., lease_duration: 3600
```

💡 **A credential valid for one hour has a bounded blast radius with no human action required.** Rotation stops being a project and becomes the default state.

⚠️ **Your connection pool must handle expiry** — reconnect before the lease ends, and handle a pooled connection whose credentials were revoked ([[06.9 - Connection Pooling and PgBouncer]]).

```python
pool = await asyncpg.create_pool(dsn, max_inactive_connection_lifetime=1800)
```

## Encryption at Rest

### Envelope encryption

```
KMS master key (never leaves the HSM)
  └── encrypts data encryption keys (DEKs)
        └── DEKs encrypt your data
```

```python
# Generate a DEK, encrypted by KMS
response = kms.generate_data_key(KeyId=MASTER_KEY_ID, KeySpec="AES_256")
plaintext_dek, encrypted_dek = response["Plaintext"], response["CiphertextBlob"]

aesgcm = AESGCM(plaintext_dek)
nonce = os.urandom(12)
ciphertext = aesgcm.encrypt(nonce, plaintext, associated_data)

store(encrypted_dek=encrypted_dek, nonce=nonce, ciphertext=ciphertext)
del plaintext_dek
```

💡 **Envelope encryption exists because KMS calls are slow and rate-limited.** Encrypting a million rows directly with KMS is impossible; encrypting a million rows with a DEK and one KMS call is trivial.

⚠️ **Store the encrypted DEK alongside the ciphertext.** Decryption is: KMS-decrypt the DEK, then AES-decrypt the data. **Rotating the master key means re-encrypting only the DEKs, not the data.**

### AEAD, and the associated data

```python
aad = f"org:{org_id}:doc:{doc_id}".encode()
ciphertext = aesgcm.encrypt(nonce, plaintext, aad)
```

💡 **Associated data is authenticated but not encrypted, and it binds the ciphertext to its context.** Moving an encrypted blob from one document row to another makes decryption fail — **which prevents a whole class of ciphertext-swapping attacks.**

⚠️ **Never reuse a nonce with the same key in AES-GCM.** Nonce reuse in GCM is catastrophic — it leaks the authentication key, not just one plaintext. **Use a random 96-bit nonce per encryption, or a strict counter.**

**Use AEAD — AES-GCM or ChaCha20-Poly1305 — never a raw block cipher mode.** Unauthenticated encryption lets an attacker modify ciphertext undetected.

### What to encrypt

| Layer | Protects against |
|---|---|
| **Disk encryption** | Physical theft. **Free, always on** |
| **Database TDE** | Filesystem access, backup theft |
| **Application-level** | **A compromised database, and a curious DBA** |

⚠️ **Application-level encryption is the only layer that protects against someone with database access**, and it is the only one that costs you queryability.

```sql
SELECT * FROM users WHERE ssn = ?           -- ❌ impossible on encrypted data
```

💡 **Encrypt the small number of fields that genuinely need it** — payment details, government identifiers, health data, connector credentials — **and accept that you cannot query, index or sort them.**

**For equality lookups on encrypted fields, store a keyed hash alongside:**

```python
lookup_hash = hmac.new(SEARCH_KEY, value.encode(), hashlib.sha256).hexdigest()
```

⚠️ **This leaks equality** — identical values produce identical hashes — **which is a real disclosure for low-cardinality fields.** Acceptable for an email; not for a diagnosis code.

## Key Rotation

```
Master key       annually, or on compromise. KMS handles it
DEK              on re-encryption
Signing key      quarterly, with `kid` and JWKS ([[14.2 - Sessions Tokens and Rotation]])
Webhook secret   quarterly, dual-value ([[05.12 - Webhooks and Callbacks]])
API keys         user-initiated, or on a schedule
Database creds   dynamic, hourly
```

💡 **Design every secret to support two live values from the start.** Retrofitting dual-value support during an incident is much harder than building it in.

```python
def verify(payload: bytes, signature: str) -> bool:
    return any(
        hmac.compare_digest(sign(payload, secret), signature)
        for secret in (settings.secret_current, settings.secret_previous)
    )
```

**Three deploys, zero downtime** — add, swap, remove. **Expand/contract applied to secrets** ([[06.11 - Zero Downtime Migrations]]).

### Key versioning for encrypted data

```python
@dataclass
class Ciphertext:
    key_version: int
    nonce: bytes
    data: bytes
```

⚠️ **Without a version marker you can never rotate an encryption key**, because you cannot tell which key decrypted which row. **One integer, decided at design time, and it is the difference between rotatable and permanent.**

**Rotate lazily:** decrypt with the recorded version, re-encrypt with the current one on next write, and run a background job for the remainder.

## When a Secret Leaks

⚠️ **Assume every secret in git history is compromised, permanently.** Deleting the commit does not help — the history exists in every clone, every fork, and every CI cache.

```
1. ROTATE first. Not "investigate first"
2. Revoke the old value
3. Check access logs for use of the leaked credential
4. Then investigate how it leaked
5. Then prevent the class
```

💡 **Rotation is the mitigation and it comes before understanding** — the same principle as incident response ([[11.10 - Incidents and Postmortems]]).

### Prevention

```yaml
# pre-commit
- repo: https://github.com/gitleaks/gitleaks
  hooks: [{id: gitleaks}]
```

```yaml
# CI, on every push
- run: gitleaks detect --source . --redact --log-opts="--all"
```

💡 **A recognisable prefix on your own credentials — `ck_live_` — lets GitHub's secret scanning notify you when one is committed to a public repository**, which has prevented a great many breaches ([[14.2 - Sessions Tokens and Rotation]]).

**Register your prefix with the secret scanning partner programme if you issue keys to customers.**

## In Production

### Do not write your own cryptography

⚠️ **This is not conservatism — the failure modes are silent.** Encryption that "works" in tests can be trivially breakable.

| Need | Use |
|---|---|
| Symmetric encryption | `cryptography` AESGCM, or **Tink** |
| Password hashing | Argon2id, bcrypt |
| Signing | Ed25519, RS256 |
| Random | `secrets`, never `random` |
| Comparison | `secrets.compare_digest` |
| **A full solution** | **Tink** — it makes misuse hard by design |

💡 **Google's Tink is worth knowing about.** It removes the dangerous choices — you cannot select a mode without authentication, you cannot reuse a nonce, and key rotation is built into the keyset format.

⚠️ **`random` is not cryptographically secure.** `random.choice` for a token, a password reset code or a session ID is predictable. **`secrets` everywhere it matters.**

### Access control on secrets

```hcl
path "database/creds/documents-service" {
  capabilities = ["read"]
}
```

⚠️ **A service that can read every secret is a single compromise away from total loss.** Scope per service, per environment.

💡 **Audit logging on secret access is one of the highest-value controls available** — an unusual read pattern is a strong compromise signal, and it is the one thing environment variables cannot give you.

```python
secret_access_total.labels(secret=..., service=..., result=...).inc()
```

### Encryption key hierarchy

```
KMS master key (per environment)
  ├── DEK: document content
  ├── DEK: connector credentials
  ├── DEK: PII fields
  └── HMAC key: lookup hashes
```

💡 **Separate keys per data class.** A compromise of the search-index key must not decrypt customer connector credentials.

⚠️ **Never share keys across environments.** A staging key that decrypts production data means staging is production from a security perspective.

### The checklist

```
□  Workload identity wherever the platform supports it
□  Dynamic credentials for databases, where available
□  Third-party secrets in a manager, not environment variables
□  Every secret supports two live values
□  Encrypted data carries a key version
□  AEAD only; never a raw block cipher mode
□  Nonces never reused
□  Associated data binds ciphertext to its context
□  Separate keys per data class and per environment
□  Least-privilege access policies per service
□  Audit logging on secret access
□  Secret scanning in pre-commit and CI
□  A written rotation procedure per secret, practised
□  A leak runbook that starts with "rotate"
```

⚠️ **The second-to-last item is the one that fails.** A rotation procedure that has never been executed does not work, **and you will discover that during the incident that requires it.**

**Practise rotation on a schedule, in production.**

### Conduit's key management

| Secret | Storage | Rotation |
|---|---|---|
| Database credentials | **Workload identity** | None needed |
| Object storage | **Workload identity** | None needed |
| Embedding API key | Secret manager, mounted file | Quarterly, dual-value |
| **Connector OAuth tokens** | **Encrypted with a dedicated DEK** | Refreshed by the provider |
| Webhook signing secret | Secret manager, **dual-value** | Quarterly |
| JWT signing key | KMS, with `kid` | Quarterly, JWKS |
| Session encryption key | Secret manager | Annually |

💡 **The connector tokens are the highest-value secret Conduit holds** — they are live credentials to a customer's Google Drive. **A dedicated key, encrypted at the application layer, with the organisation ID as associated data** ([[14.3 - OAuth2 and OIDC]]).

⚠️ **Two secrets eliminated entirely by workload identity.** That is the first thing to reach for, and it is the reason the remaining list is short enough to manage properly.

## Codebase

**Repo:** `google/tink`, `hashicorp/vault`, `pyca/cryptography`

**Question to answer:** How does Tink prevent nonce reuse and mode misuse, and what does its keyset format buy you? Then: how does Vault issue and revoke a dynamic database credential?

**Read, in order:**

1. `google/tink/docs/PRIMITIVES.md` and the keyset design — **how Tink makes misuse structurally hard**: no mode selection, no nonce management, and rotation built into the key format. **The answer to the first question**
2. `tink/cc/aead/aes_gcm_key_manager.cc` or the Python equivalent — nonce generation, and the key size constraints it enforces
3. `vault/builtin/logical/database/` — **credential creation and lease revocation.** The answer to the second question, and the lease mechanism is the interesting part
4. `pyca/cryptography` — `hazmat/primitives/ciphers/aead.py`. **Note that the whole module is named `hazmat`** — the library is telling you these are sharp tools
5. **AWS KMS envelope encryption documentation** — the pattern, with the operational reasoning for why direct KMS encryption does not scale

💡 Tink's design philosophy is the transferable lesson: **the API does not let you make the dangerous choice.** You cannot select ECB, you cannot manage a nonce, and you cannot use a key for the wrong purpose. **That is what a well-designed security API looks like, and it is worth applying to your own internal interfaces.**

**Size:** 1–2 sessions.

## Exercise

**Drill 14.5 — Encrypt, rotate, and survive a leak**

⚠️ Everything runs against your own local stack, with test keys.

```
drills/14-secrets/
├── identity/{workload_identity.py, dynamic_creds.py, RESULTS.md}
├── envelope/{encrypt.py, decrypt.py, kms_local.py, bench.py}
├── mistakes/{nonce_reuse.py, no_aad.py, ecb.py, weak_random.py, FINDINGS.md}
├── rotation/{key_versions.py, lazy_reencrypt.py, dual_value.py, RESULTS.md}
├── lookup/{blind_index.py, leakage.md}
├── leak/{scan.py, runbook.md, drill.md}
└── README.md
```

**Part 1 — Eliminate two secrets.** Replace a static database password and object storage credentials with workload identity (or a local OIDC-federation equivalent).

**Confirm no credential exists in your configuration.** Then implement dynamic database credentials with a one-hour lease.

**Test expiry:** hold a pooled connection past the lease and **confirm what happens.** Then set `max_inactive_connection_lifetime` correctly and confirm it recovers.

**Part 2 — Envelope encryption.** Implement it against a local KMS stand-in, with key versioning and associated data.

**Benchmark: direct KMS encryption per row versus envelope encryption**, for 10,000 rows.

**Report the ratio and the KMS API call count.** That difference is why envelope encryption exists.

**Part 3 — Four cryptographic mistakes.** For each, implement it and demonstrate the consequence:

| Mistake | Demonstrate |
|---|---|
| **Nonce reuse in AES-GCM** | Two ciphertexts with the same key and nonce — **XOR them and recover plaintext relationships** |
| **No associated data** | Move a ciphertext to another row; decryption succeeds when it should not |
| **ECB mode** | Encrypt a bitmap and **look at it** — the classic penguin |
| **`random` instead of `secrets`** | Seed it, predict the next "random" token |

💡 **The ECB one is worth doing visually.** Seeing the pattern survive encryption makes the concept permanent.

**Part 4 — Key rotation, lazily.** Encrypt 100,000 rows with key v1.

Rotate to v2. **Confirm reads still work for v1 rows**, that writes use v2, and that a background job migrates the remainder.

**Measure the migration duration and the impact on live queries.**

Then **remove key v1 before migration completes** and confirm the failure — establishing why you must verify completion before retiring a key.

**Part 5 — Dual-value rotation.** A webhook signing secret with active senders.

**Single-value:** rotate and measure how long signatures fail.
**Dual-value:** rotate through three deploys and confirm zero failures.

**Part 6 — Blind index.** Encrypted email fields with an HMAC lookup hash.

**Confirm equality lookup works.** Then demonstrate the leakage: **with 1,000 rows where 200 share a value, show that the hash reveals the grouping.**

**Write down which fields you would and would not use this for.**

**Part 7 — The leak drill.** Commit a fake API key to a test repository.

**Confirm your pre-commit hook blocks it.** Then bypass the hook and confirm CI catches it.

Then run the full leak procedure against a real (test) credential: **rotate, revoke, check access logs, and verify the old value no longer works.**

**Time the whole procedure.** Then write `runbook.md` and have someone else follow it.

**Part 8 — Access control and audit.** Scope secret access per service with least-privilege policies.

**Confirm a service cannot read another service's secrets.**

Then implement access audit logging and **detect an anomalous read pattern** — one service suddenly reading every secret.

**Done when:**
- Two secrets are eliminated entirely by workload identity
- Dynamic credential expiry is handled correctly by your pool
- Your envelope encryption benchmark shows the KMS call reduction
- All four cryptographic mistakes are demonstrated, including the ECB image
- Lazy key rotation completes, and removing the old key early fails as expected
- Dual-value rotation achieves zero signature failures
- Blind index equality leakage is demonstrated on real data
- Someone else can execute your leak runbook, timed
