# Reading Session: Saleor's GraphQL Layer

#backend #reading #graphql

> **In one line:** Saleor is a large commercial GraphQL API that has survived years of real pressure, and reading it shows you what every solution from section 05 looks like when it has been maintained rather than demonstrated.

## The Path

### 1. The entry point — `saleor/graphql/api.py`

```python
schema = build_federated_schema(
    Query,
    mutation=Mutation,
    types=[...],
    subscription=Subscription,
)
```

**Then `saleor/graphql/views.py`:**

```python
class GraphQLView(View):
    def handle_query(self, request: HttpRequest) -> JsonResponse:
        ...
        response = self.execute_graphql_request(request, data)
        ...
```

💡 **Look at what happens *around* execution:** the app/user resolution, the query cost check, the error masking, and the plugin hooks. **That wrapper is where a production GraphQL layer differs from a tutorial one.**

⚠️ **Find their query complexity or depth handling.** Every public GraphQL API needs it, and seeing where a real one puts the check — **before execution, in validation** — confirms the design from [[05.8 - GraphQL Security and Limits]].

### 2. The type definitions — `saleor/graphql/product/types/products.py`

```python
class Product(ChannelContextTypeWithMetadata[models.Product]):
    id = graphene.GlobalID(required=True)
    name = graphene.String(required=True)
    ...
    variants = NonNullList(
        ProductVariant,
        description="List of variants for the product.",
    )
```

⚠️ **`ChannelContext` is Saleor's most pervasive design decision.** A product's price, availability and visibility differ per sales channel, so **almost every type carries a channel alongside the model instance.**

💡 **This is worth understanding because it is the shape of "context that must flow through every resolver".** Multi-tenancy has the same requirement ([[14.6 - Multi Tenant Isolation]]) — **and Saleor solved it by making the context part of the type rather than relying on every resolver to remember.**

**That is a structural fix, and it is the pattern to steal.**

### 3. The resolvers, and the loaders

```python
@staticmethod
def resolve_variants(root: ChannelContext[models.Product], info):
    ...
    return (
        ProductVariantsByProductIdAndChannel(info.context)
        .load((root.node.id, root.channel_slug))
        .then(lambda variants: [ChannelContext(v, root.channel_slug) for v in variants])
    )
```

💡 **Every relationship goes through a loader. Every one.** There is no direct ORM access in a resolver.

⚠️ **Note the composite key `(product_id, channel_slug)`.** The loader batches across both dimensions, **which is what makes channel-aware batching possible.**

**`saleor/graphql/product/dataloaders/products.py`:**

```python
class ProductByIdLoader(DataLoader):
    context_key = "product_by_id"

    def batch_load(self, keys):
        products = models.Product.objects.using(self.database_connection_name).in_bulk(keys)
        return [products.get(product_id) for product_id in keys]
```

💡 **The naming convention is `<Thing>By<Key>Loader`.** With forty loaders in a schema, **a systematic name is the difference between finding the right one and writing a duplicate** ([[05.6 - The N+1 Problem and DataLoader]]).

⚠️ **`[products.get(k) for k in keys]` is the alignment rule made explicit** — same length, same order, `None` for missing. **A real codebase writes this the same way every time, precisely because getting it wrong is silent.**

### Loaders that call loaders

```python
class VariantChannelListingByVariantIdAndChannelSlugLoader(DataLoader):
    def batch_load(self, keys):
        variant_ids, channel_slugs = zip(*keys)
        ...
        channels = ChannelBySlugLoader(self.context).load_many(set(channel_slugs))
        return channels.then(with_channels)
```

💡 **Loaders composing with other loaders is how a deep schema stays at a constant number of queries.** Reading two or three of these makes the pattern obvious, **and it is the part tutorials never reach.**

### 4. Permissions — `saleor/graphql/core/fields.py` and the decorators

```python
class ProductVariant(...):
    ...
    @staticmethod
    @one_of_permissions_required([ProductPermissions.MANAGE_PRODUCTS])
    def resolve_private_metadata(root, info):
        ...
```

⚠️ **Permissions are on the *field*, not only on the query.** A `Product` reachable through an order, a collection or a search result carries the same field-level checks.

💡 **This is the field-traversal problem from [[05.8 - GraphQL Security and Limits]]**, solved by attaching the check to the type that owns the data rather than to the entry point.

**Look for how they handle a permission denial on a non-nullable field** — the null-propagation interaction from [[05.5 - How GraphQL Execution Works]] is a real design constraint here.

### 5. Mutations — `saleor/graphql/product/mutations/`

```python
class ProductCreate(ModelMutation):
    class Arguments:
        input = ProductCreateInput(required=True, description="Fields required to create a product.")

    class Meta:
        description = "Creates a new product."
        model = models.Product
        object_type = Product
        permissions = (ProductPermissions.MANAGE_PRODUCTS,)
        error_type_class = ProductError
        error_type_field = "product_errors"

    @classmethod
    def clean_input(cls, info, instance, data, **kwargs):
        ...
        raise ValidationError({"slug": ValidationError(message, code=ProductErrorCode.REQUIRED)})
```

💡 **Errors are validated, collected and returned in the payload — not raised as GraphQL errors.**

```graphql
mutation {
  productCreate(input: {...}) {
    product { id }
    errors { field message code }
  }
}
```

⚠️ **`code` is the stable machine-readable identifier; `message` is presentation** ([[05.3 - Error Design]]). **Saleor generates an enum per domain — `ProductErrorCode`, `OrderErrorCode` — which is more structure than most APIs bother with and it is why their clients can branch reliably.**

**Read `ModelMutation` in `saleor/graphql/core/mutations.py`.** The template method pattern — `clean_input`, `construct_instance`, `clean_instance`, `save`, `post_save_action` — **is how they avoid rewriting validation for two hundred mutations.**

### 6. Pagination — `saleor/graphql/core/connection.py`

```python
def connection_from_queryset_slice(qs, args=None, connection_type=..., ...):
    ...
    sorting_fields = get_sorting_fields(sort_by, ...)
    ...
    filter_kwargs = _get_filter_kwargs(after, sorting_fields, ...)
```

⚠️ **This is keyset pagination over a Django queryset**, with the cursor encoding the sort fields ([[05.2 - Versioning Pagination and Filtering]]).

💡 **Note the tiebreaker handling.** Real keyset pagination over user-selectable sort fields is genuinely fiddly, **and this file is one of the better open-source implementations to learn from.**

**Look for how they cap `first`/`last`** — an uncapped connection is a denial-of-service vector.

## What to Take Away

### The organising conventions

| Convention | Why it scales |
|---|---|
| `<Thing>By<Key>Loader` | Forty loaders remain findable |
| One loader file per domain | `product/dataloaders/products.py` |
| `ModelMutation` base class | Validation written once |
| Error code enums per domain | Clients can branch reliably |
| `ChannelContext` on types | Context cannot be forgotten by a resolver |
| Permissions on fields | Every path is covered |

💡 **A large GraphQL schema survives on conventions, not on cleverness.** Every one of these is boring and every one of them is load-bearing.

### What they chose not to solve

⚠️ **Look for the compromises. They are instructive.**

```
- Some resolvers do hit the ORM directly. Find them and ask why
- Deeply nested paginated connections have limits — some are documented as unsupported
- Not everything is batched; some fields accept a query per parent
- The schema is very large, and deprecation is slow
```

💡 **"We do not support arbitrarily deep nested pagination" is a legitimate product decision**, and seeing a real API state it explicitly is permission to make the same call ([[05.6 - The N+1 Problem and DataLoader]]).

### The scale of the thing

```bash
rg "class.*DataLoader" saleor/graphql --count
rg "class.*Mutation" saleor/graphql --count
```

⚠️ **Count them.** The numbers are the argument for conventions — **at that scale, ad-hoc decisions are not survivable.**

## In Production

### What to apply to Conduit

| Saleor pattern | Conduit application |
|---|---|
| `<Thing>By<Key>Loader` naming | Adopt directly |
| Loader-only data access in resolvers | **Enforce with a lint rule** |
| Error code enums per domain | ([[05.3 - Error Design]]) |
| `ModelMutation` template | For repetitive CRUD mutations |
| **Tenant context on types** | **`ChannelContext` → `OrgContext`** |
| Field-level permissions | ([[14.1 - AuthN vs AuthZ]]) |
| Capped connection page sizes | |

💡 **The `ChannelContext` → `OrgContext` translation is the highest-value idea in this session.** Making the tenant part of the type means a resolver *cannot* forget it — **which is structurally stronger than a check every resolver must remember** ([[14.6 - Multi Tenant Isolation]]).

### Measuring what you learned

```python
graphql_db_queries_per_request.observe(count)
```

⚠️ **Run one of Saleor's own complex queries with query logging on and count.** Then run a deliberately naive equivalent.

**The ratio is the value of the loader discipline**, measured on a real schema rather than a toy one.

## Codebase

**Repo:** `saleor/saleor`

**Question to answer:** For a product list query with variants, channel listings and permissions, how many database queries execute, and which code prevents it from being N+1?

**Read, in order:**

1. `saleor/graphql/api.py` and `views.py` — schema construction and the request wrapper
2. `saleor/graphql/product/types/products.py` — **`Product` and `ProductVariant`.** Note every resolver returning a loader
3. **`saleor/graphql/product/dataloaders/products.py` — read several loaders in full.** The naming, the alignment, and the composition
4. `saleor/graphql/core/mutations.py` — **`ModelMutation`** and the template method sequence
5. `saleor/graphql/product/mutations/products.py` — a concrete mutation, and its `clean_input`
6. `saleor/graphql/core/connection.py` — keyset pagination with user-selectable sorts
7. `saleor/graphql/core/fields.py` and the permission decorators — field-level authorisation

💡 The dataloader files are the highest-value read. **Three or four of them, in full, teaches the composition pattern better than any documentation** — and the fact that they all look the same is precisely the point.

**Size:** 3 sessions.

## Exercise

**Drill 15.5 — Count the queries, then adopt the conventions**

```
drills/15-saleor/
├── trace/{TRACE.md, query_counts.md}
├── experiments/{naive_vs_loaders.py, permission_traversal.py,
│                deep_pagination.py, RESULTS.md}
├── conventions/{audit.md, lint_rule.py}
├── conduit/{org_context.py, loaders.py, error_codes.py, mutations.py}
└── README.md
```

**Part 1 — Run Saleor and count.** Start it with the sample data and query logging enabled.

**Run a complex product query** — products with variants, channel listings, categories and images.

**Count the database queries.** Then chart query count against `first: 10, 50, 100`.

💡 **It should be flat.** That flatness is what the loader discipline buys.

**Part 2 — Break it.** Fork one type and replace a loader-based resolver with direct ORM access.

**Re-run and count.** Chart both against result size — one flat, one linear.

**Report the query count at `first: 100`.**

**Part 3 — Permission traversal.** Find a type with field-level permissions.

**Reach it through three different query paths** — directly, through an order, and through a search result.

**Confirm the permission check applies on all three.**

Then remove the field-level check and add it only at the top-level query. **Confirm you can now read the field through the other two paths.**

**Part 4 — Deep pagination limits.** Find a nested connection — variants within products.

**Request `products(first: 100) { variants(first: 100) }`.** Measure query count, rows fetched, response size and latency.

**Then find where Saleor caps or refuses this.** If they do not, note that as a finding and measure how far you can push it.

**Part 5 — Count the conventions.** Run the counting commands.

**Report: number of loaders, mutations, types and error code enums.**

Then check consistency: **how many loaders follow the `<Thing>By<Key>Loader` name?** Any that do not are either an exception worth understanding or a lapse.

**Part 6 — Find the compromises.** Search for resolvers that access the ORM directly rather than through a loader.

**For each, work out why.** Some will be genuinely single-instance; some will be technical debt.

**Write `audit.md`** with three examples and your assessment of each.

**Part 7 — A lint rule for Conduit.** Write a `semgrep` or AST rule enforcing "no ORM access inside a resolver — use a loader".

**Run it against your own GraphQL code and fix the violations.** Then wire it into CI ([[14.4 - Common Vulnerabilities]]).

**Part 8 — Adopt four conventions.** In Conduit:

```
1. OrgContext on every type, following ChannelContext
2. <Thing>By<Key>Loader naming, applied consistently
3. Error code enums per domain
4. A ModelMutation-style base for repetitive CRUD
```

**Then run your own complex query and count the database queries before and after.**

**Confirm `OrgContext` makes a tenant-forgetting resolver impossible** — write one deliberately and confirm it does not type-check or does not compile.

**Done when:**
- Saleor's query count is flat against result size, measured
- Your broken version is linear, with the count at `first: 100` recorded
- A field-level permission holds across three query paths, and fails when moved to the top level
- You know where deep nested pagination stops being supported
- You have counted loaders, mutations, types and error enums
- `audit.md` assesses three direct-ORM resolvers
- A lint rule enforces loader-only access in Conduit's resolvers
- `OrgContext` makes forgetting the tenant structurally impossible
