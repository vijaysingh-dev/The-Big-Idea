# AuthN vs AuthZ

#backend #security #architecture

> **In one line:** Authentication establishes who you are and happens once at the edge; authorisation decides what you may do and must happen at every place data is reached.

---

## The Idea

```
Authentication:  "Who are you?"        → an identity
Authorisation:   "May you do this?"    → a decision
```

⚠️ **Conflating them is the root of most access-control bugs.** A system that authenticates at the gateway and assumes that is sufficient has no authorisation at all.

💡 **Authenticate once at the edge; authorise in the service that owns the data** ([[10.6 - API Gateway and BFF]]). The gateway cannot make authorisation decisions because it does not know the domain — **it does not know that this document belongs to that organisation.**

---

## Authorisation Models

### RBAC — role-based

```python
ROLE_PERMISSIONS = {
    "viewer": {"document:read"},
    "editor": {"document:read", "document:write"},
    "admin":  {"document:read", "document:write", "document:delete", "member:manage"},
}
```

💡 **Simple, auditable, and it covers most products.** "What can an editor do" has a fixed answer you can write down.

⚠️ **RBAC cannot express instance-level rules.** "Editors can edit documents *they created*" is not a role — it is a condition on a specific object, and bolting conditions onto roles produces `editor_of_own_documents_in_shared_folders` and forty other roles.

**Role explosion is the signal that you have outgrown RBAC.**

### ABAC — attribute-based

```python
def can(user, action, resource) -> bool:
    return (
        user.org_id == resource.org_id
        and action in ROLE_PERMISSIONS[user.role]
        and (resource.owner_id == user.id or resource.is_shared)
        and not resource.is_locked
    )
```

**Expressive.** ⚠️ **And hard to audit** — "who can access this document" requires evaluating the policy against every user.

### ReBAC — relationship-based

```
document:doc_42#viewer@user:alice
document:doc_42#parent@folder:f_7
folder:f_7#viewer@group:engineering#member
```

**The question becomes a graph traversal: is there a path from this user to this permission on this object?**

💡 **This is Google's Zanzibar model, and it is what you need for hierarchical sharing** — folders inheriting to documents, groups containing groups, "anyone with the link".

⚠️ **It requires a dedicated system** — SpiceDB, OpenFGA, Ory Keto — or a substantial amount of your own graph code. **Do not build it unless your product genuinely needs it.**

### Choosing

```
Do permissions depend on the specific object?
├── NO  → RBAC. Stop here
└── YES → Are there hierarchies, or groups within groups, or sharing?
    ├── NO  → RBAC + ownership checks (this covers most SaaS)
    └── YES → ReBAC (SpiceDB / OpenFGA)
```

💡 **"RBAC plus an ownership check plus a tenant check" is the right answer for the large majority of products**, and reaching for a policy engine before you need one adds a dependency on the critical path of every request.

## Where Authorisation Must Live

⚠️ **The most common architectural failure: authorising only at the endpoint.**

```python
@app.get("/documents/{doc_id}")
async def get_document(doc_id: str, user: User):
    if not await can_read(user, doc_id):        # checked here
        raise HTTPException(404)
    doc = await repo.get(doc_id)
    doc.annotations = await annotations.list(doc_id)     # ⚠️ not checked
    return doc
```

**Every path to an object must be authorised, not just the obvious one.** This is acute in GraphQL, where clients reach objects through paths you did not anticipate ([[05.8 - GraphQL Security and Limits]]).

### Enforce at the data layer

```python
async def batch_load_documents(ids: list[str], viewer: User):
    return await conn.fetch(
        "SELECT * FROM documents WHERE id = ANY($1) AND org_id = $2",
        ids, viewer.org_id,
    )
```

💡 **A repository that cannot return another tenant's data is stronger than a check every caller must remember.** Every code path goes through it, including ones written next year by someone who has not read this note.

### And in the database

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
    USING (org_id = current_setting('app.current_org_id')::uuid);
```

⚠️ **RLS enforces the tenant boundary against every code path, every migration script, and every person with a `psql` prompt** ([[06.16 - Multi Tenant Data Models]]).

**Three layers: the database enforces tenancy, the repository enforces tenancy and ownership, the handler enforces the action.** Each catches what the others miss.

## Fail Closed

```python
# ❌
try:
    allowed = await authz.check(user, action, resource)
except Exception:
    allowed = True                # "do not break the product"

# ✅
try:
    allowed = await authz.check(user, action, resource)
except Exception:
    authz_errors_total.inc()
    raise HTTPException(503)      # refuse, loudly
```

⚠️ **Authorisation is the one dependency that must never degrade** ([[11.6 - Graceful Degradation]]). Everything else can serve stale or partial data; **an authorisation failure that fails open is a breach.**

💡 **This is also why permissions must never be cached with a long TTL** ([[07.1 - Cache Layers Across One Request]]). A revoked permission cached for 60 seconds is 60 seconds of unauthorised access.

**Short-TTL caching with immediate invalidation on change is acceptable. A five-minute TTL is not.**

## 403 versus 404

```
403 Forbidden  → "you may not access document 42"   ⚠️ confirms it exists
404 Not Found  → "no such document"                  reveals nothing
```

💡 **Return 404 for objects the user cannot see.** Otherwise an attacker enumerates your ID space and learns which documents exist, how many customers you have, and how fast you are growing ([[05.3 - Error Design]]).

⚠️ **Timing gives it away too.** If a permission-denied path is measurably faster than a not-found path, the 404 is decorative.

**Use 403 only when the user can see the object but not perform the action** — they can read a document but not delete it.

## In Production

### The permission model, written down

```markdown
| Resource  | Action | Who |
|-----------|--------|-----|
| document  | read   | org member with role viewer+, or explicit share |
| document  | write  | org member with role editor+, and (owner or shared-edit) |
| document  | delete | org member with role admin, or the owner |
| member    | invite | org member with role admin |
| billing   | manage | org member with role owner |
```

💡 **This table is the specification your tests assert against.** Without it, "is this correct" has no answer, and every reviewer applies their own model.

### Testing authorisation

```python
@pytest.mark.parametrize("role,action,expected", PERMISSION_MATRIX)
async def test_permission_matrix(role, action, expected, client):
    user = await make_user(role=role)
    response = await client.request(*ACTIONS[action], user=user)
    assert (response.status_code < 400) == expected
```

⚠️ **Test the negative cases.** A test suite confirming admins can delete tells you nothing; **one confirming viewers cannot is the test that matters.**

```python
async def test_cross_tenant_isolation(client):
    doc = await make_document(org=org_a)
    user_b = await make_user(org=org_b)
    assert (await client.get(f"/documents/{doc.id}", user=user_b)).status_code == 404
```

💡 **A cross-tenant probe on every resource type is the highest-value security test you can write**, and it should be parameterised over every endpoint.

### Audit logging

```python
audit.log(
    actor=user.id, action="document.delete", resource=doc.id,
    org_id=user.org_id, result="allowed", reason="role:admin",
    request_id=request_id, ip=request.client.host,
)
```

⚠️ **Log denials as well as grants.** A spike in denials is either a broken client or someone probing you.

💡 **Log the *reason*, not just the outcome.** "Allowed because role:admin" versus "allowed because owner" is the difference between an audit log you can investigate and one you can only count.

**Audit logs are append-only and retained far longer than application logs** — often years, for compliance.

### Service-to-service authorisation

⚠️ **Internal services need authorisation too.** "It is behind the gateway" is not an authorisation model — it is a network assumption that one misconfiguration invalidates ([[10.6 - API Gateway and BFF]]).

| Mechanism | |
|---|---|
| **Forward the user's token** | The service authorises the *user*. Preferred |
| Service identity (mTLS) | The service authorises the *caller* |
| Both | The caller is allowed, and the user is allowed |

💡 **Forwarding the user token means the document service applies the same permission model regardless of who called it.** Header-trust is faster and one network policy away from a breach.

### The audit checklist

```
□  Authentication at the edge; authorisation in the service
□  Every path to an object is authorised, not just the obvious endpoint
□  Tenant boundary enforced in the repository AND in the database (RLS)
□  Authorisation fails closed
□  Permissions never cached with a long TTL
□  404 not 403 for invisible objects, with no timing difference
□  A written permission matrix
□  Negative tests for every role and action
□  A cross-tenant probe test per resource type
□  Audit log with actor, action, resource, result and reason
□  Service-to-service calls carry and check identity
```

### Conduit's model

| Layer | Enforces |
|---|---|
| Gateway | **Authentication** — validates the JWT, forwards the token |
| Service handler | The action against the role |
| Repository | **Tenant and ownership** — every query scoped by `org_id` |
| DataLoader | Tenant boundary, so GraphQL traversal cannot escape it |
| Postgres RLS | **Tenant boundary, unconditionally** |

💡 **Four layers, and each catches a different mistake.** A forgotten handler check is caught by the repository; a raw query bypassing the repository is caught by RLS; a GraphQL path nobody anticipated is caught by the loader.

⚠️ **The permission check is never cached and never backgrounded** ([[08.1 - Why Background Work Exists]]). It is a synchronous, required dependency, and that cost is accepted deliberately.

**RBAC with an ownership check, not ReBAC** — Conduit has organisations, roles and per-document sharing, but no nested groups or folder hierarchies. **Write down the trigger for reconsidering: folder-level inheritance, or sharing across organisations.**

## Codebase

**Repo:** `authzed/spicedb`, `openfga/openfga`, `saleor/saleor`

**Question to answer:** How does a Zanzibar-style system answer "can user X view document Y" — what does the traversal look like, and how is it made fast? Then: how does a large real application structure its permission checks?

**Read, in order:**

1. **The Google Zanzibar paper** — **read this before any code.** The relationship-tuple model and the consistency mechanism (zookies). **It is the reference design for every ReBAC system**
2. `spicedb/internal/graph/check.go` — **the check traversal.** How a permission query walks the relationship graph, and where it prunes
3. `spicedb/internal/dispatch/` — caching and request deduplication. **How a graph traversal is made fast enough for the request path**
4. `openfga/pkg/typesystem/` — the authorisation model DSL. A more approachable entry point than SpiceDB's schema language
5. `saleor/saleor/permission/` and the `@permission_required` decorators — **RBAC in a large real application.** Note where the checks live relative to the data access

💡 The Zanzibar paper's most transferable idea is not the graph — it is the **consistency token**. A permission check returns a token, and a subsequent read can require the check to be at least as fresh. **That solves the "I revoked access and it is still cached" problem properly**, and it is the part most homegrown systems get wrong.

**Size:** 2 sessions.

## Exercise

**Drill 14.1 — Break your own access control**

⚠️ Everything runs against your own local stack.

```
drills/14-authz/
├── matrix/{permissions.md, test_matrix.py}
├── layers/{handler.py, repository.py, loader.py, rls.sql, tests/}
├── attacks/{idor.py, traversal.py, enumeration.py, cross_tenant.py, FINDINGS.md}
├── failures/{fail_open.py, cached_permission.py, RESULTS.md}
├── models/{rbac.py, abac.py, rebac.py, COMPARISON.md}
├── audit/{logging.py, queries.sql}
└── README.md
```

**Part 1 — Write the permission matrix.** Every resource, every action, every role, every condition. **Then implement it.**

**Part 2 — Test every cell, especially the negatives.** Parameterise over the full matrix.

**Count your tests: positive cases versus negative cases.** If negatives are fewer, you have not tested authorisation.

**Part 3 — Five attacks.** Against a version with checks only at the endpoint:

| Attack | |
|---|---|
| **IDOR** — request another user's document by ID | |
| **Traversal** — reach a User through `document → annotations → author` | |
| **Enumeration** — distinguish 403 from 404, including by timing | |
| **Cross-tenant** — as org A, read org B's data | |
| **Mass assignment** — set `org_id` in a create request | |

**Demonstrate each succeeding.** Then add the repository and loader layers and confirm each is blocked.

**Part 4 — Defence in depth, proven.** With all four layers implemented, **deliberately remove one at a time and confirm the attack is still blocked by the others.**

| Removed | Should still be blocked by |
|---|---|
| Handler check | Repository |
| Repository scoping | RLS |
| Loader check | RLS |
| **RLS** | Repository — but a raw query now escapes |

**The last row is the interesting one.** Write a query bypassing the repository and confirm RLS is the only thing stopping it.

**Part 5 — Fail open, and cached permissions.** Make the authorisation check fail open on error, then make the check error.

**Demonstrate unauthorised access.** Then fail closed and confirm a 503.

Then cache a permission for 60 seconds, revoke access, and **measure the exposure window.** Then implement immediate invalidation and measure again.

**Part 6 — Timing side channel.** Measure response time for: a document that exists and is accessible, one that exists and is not, and one that does not exist.

**If the three differ measurably, your 404 is decorative.** Fix it and re-measure.

**Part 7 — Three models.** Implement the same requirements with RBAC, ABAC, and ReBAC (OpenFGA or SpiceDB).

Then add a requirement: **"documents in a shared folder inherit the folder's permissions, and groups can contain groups."**

**Measure for each: lines of code, check latency, and how easy it is to answer "who can access document X".**

**RBAC should become painful; ReBAC should handle it naturally.** That transition point is what tells you when to adopt one.

**Part 8 — Audit logging.** Log every authorisation decision with actor, action, resource, result and reason.

**Then answer three questions from the log alone:** who accessed document X in the last month, what did user Y do yesterday, and were there any denial spikes?

**Time each.** Then simulate an attacker probing IDs and **confirm your denial-rate alert fires.**

**Done when:**
- Your test suite has more negative than positive authorisation cases
- All five attacks succeed against the endpoint-only version and fail against the layered one
- Removing each layer individually still leaves the attack blocked, except where you can name why
- Fail-open demonstrably grants unauthorised access
- Your 403/404 timing difference is unmeasurable
- The three-model comparison shows where RBAC breaks down
- Three audit questions are answerable from the log, timed
- A probing attacker triggers your denial-rate alert
