# SOLID Principles

**SOLID** is not a checklist — it's a compass. Each principle addresses a specific type of pain that grows as systems scale. Learn _why_ each exists before _what_ it is.

---

## Quick Reference

|Principle|One-liner|Violation Smell|
|---|---|---|
|**S**RP|One reason to change|"God class", 500-line service|
|**O**CP|Open to extend, closed to modify|`if type == "X"` chains|
|**L**SP|Subtypes must honor parent contracts|Override throws exception|
|**I**SP|Don't force unused dependencies|Empty interface implementations|
|**D**IP|Depend on abstractions, not concretions|`new ConcreteService()` in class|

---

## S — Single Responsibility Principle

### The Real Definition

> A class should have **one reason to change**.

"One reason to change" means one _actor_ or _stakeholder_ cares about that class. Not "one method" or "one function."

### Why It Exists

When a class serves multiple purposes, changes to one purpose can break another. A change for the billing team breaks the reporting team's code — even though they share a class.

### Deep Example

```python
# ❌ VIOLATION — OrderService has 3 reasons to change:
# 1. Order processing logic changes
# 2. Email format changes
# 3. DB schema changes
class OrderService:
    def place_order(self, order):
        # Validates, calculates, persists, sends email — all in one place
        if not order.items:
            raise ValueError("Empty order")
        
        total = sum(item.price * item.qty for item in order.items)
        order.total = total
        
        # DB logic baked in — if DB changes, this class changes
        db.execute("INSERT INTO orders ...", order)
        
        # Email logic baked in — if email template changes, this class changes
        smtp.send(order.user.email, f"Order {order.id} placed. Total: {total}")


# ✅ CORRECT — Each class has one reason to change
class OrderValidator:
    """Changes only when validation rules change."""
    def validate(self, order):
        if not order.items:
            raise ValueError("Order must have items")
        if order.total < 0:
            raise ValueError("Order total cannot be negative")


class OrderPricingEngine:
    """Changes only when pricing logic changes."""
    def calculate_total(self, order) -> float:
        subtotal = sum(item.price * item.qty for item in order.items)
        return self._apply_discounts(subtotal, order)
    
    def _apply_discounts(self, subtotal, order):
        # discount logic isolated here
        return subtotal


class OrderRepository:
    """Changes only when persistence strategy changes."""
    def save(self, order):
        db.execute("INSERT INTO orders ...", order)


class OrderNotifier:
    """Changes only when notification content/channel changes."""
    def notify_placed(self, order):
        smtp.send(order.user.email, self._build_email(order))
    
    def _build_email(self, order):
        return f"Order {order.id} confirmed. Total: {order.total}"


class OrderService:
    """Orchestrates — changes only when workflow steps change."""
    def __init__(self, validator, pricing, repo, notifier):
        self.validator = validator
        self.pricing = pricing
        self.repo = repo
        self.notifier = notifier
    
    def place_order(self, order):
        self.validator.validate(order)
        order.total = self.pricing.calculate_total(order)
        self.repo.save(order)
        self.notifier.notify_placed(order)
```

### Anti-patterns to Recognize

- Class name ends in `Manager`, `Handler`, `Helper`, `Utils` — red flag
- Class imports from 5+ different modules/domains
- Class has both `send_email` and `calculate_price` methods

### Interview Perspective

When asked "how would you refactor this god class?", decompose by _actor_: who cares about each piece? Draw the split there.

## O — Open/Closed Principle

### The Real Definition

> Software entities should be **open for extension** but **closed for modification**.

Add new behavior by _adding_ code, not changing existing code. Existing code = tested, deployed, proven.

### Why It Exists

Every time you modify existing code, you risk breaking what already works. New requirements should not require editing battle-tested logic.

### Deep Example

```python
# ❌ VIOLATION — Adding a new payment method requires editing this class
class PaymentProcessor:
    def process(self, payment):
        if payment.method == "credit_card":
            stripe_client.charge(payment.amount, payment.card_token)
        elif payment.method == "paypal":
            paypal_client.create_payment(payment.amount, payment.paypal_id)
        elif payment.method == "crypto":          # new requirement → editing existing code!
            crypto_client.transfer(payment.amount, payment.wallet)
        # Every new method = modify this class = risk breaking existing methods


# ✅ CORRECT — Add new payment type by adding a new class, not modifying existing
from abc import ABC, abstractmethod

class PaymentStrategy(ABC):
    @abstractmethod
    def process(self, payment) -> PaymentResult:
        pass
    
    @abstractmethod
    def supports(self, method: str) -> bool:
        pass


class CreditCardPayment(PaymentStrategy):
    def supports(self, method): return method == "credit_card"
    
    def process(self, payment):
        result = stripe_client.charge(payment.amount, payment.card_token)
        return PaymentResult(success=result.ok, transaction_id=result.id)


class PayPalPayment(PaymentStrategy):
    def supports(self, method): return method == "paypal"
    
    def process(self, payment):
        result = paypal_client.create_payment(payment.amount, payment.paypal_id)
        return PaymentResult(success=result.status == "COMPLETED", transaction_id=result.id)


# Adding crypto: ZERO changes to existing code
class CryptoPayment(PaymentStrategy):
    def supports(self, method): return method == "crypto"
    
    def process(self, payment):
        result = crypto_client.transfer(payment.amount, payment.wallet)
        return PaymentResult(success=result.confirmed, transaction_id=result.hash)


class PaymentProcessor:
    def __init__(self, strategies: list[PaymentStrategy]):
        self.strategies = strategies
    
    def process(self, payment) -> PaymentResult:
        strategy = next((s for s in self.strategies if s.supports(payment.method)), None)
        if not strategy:
            raise ValueError(f"Unsupported payment method: {payment.method}")
        return strategy.process(payment)
```

### The Key Insight

OCP is enabled by **abstraction**. You can't close a class against modification if there's no abstraction to extend. Design the abstraction first.

### Common Mistake

**Over-applying OCP prematurely.** Don't abstract until you see the second variation. "Rule of Three": refactor to OCP when you see the third case, not the first.

## L — Liskov Substitution Principle

### The Real Definition

> If S is a subtype of T, then objects of type T may be replaced with objects of type S **without breaking the program**.

In plain terms: a subclass must honor the **behavioral contract** of its parent — not just the method signatures.

### Why It Exists

Inheritance breaks down when subclasses _weaken_ the contract. Users of the parent class assume certain behaviors — subtypes must not surprise them.

### The Contract Rules (Barbara Liskov)

1. **Preconditions** cannot be strengthened in a subtype
2. **Postconditions** cannot be weakened in a subtype
3. **Invariants** of the supertype must be preserved
4. **Exceptions** — subtype should not throw new unexpected exceptions

### Deep Example

```python
# ❌ VIOLATION — ReadOnlyFile violates File's contract
class File:
    def read(self) -> bytes:
        pass
    
    def write(self, data: bytes):
        pass  # contract: after write(), file contains data


class ReadOnlyFile(File):
    def read(self) -> bytes:
        return open(self.path, 'rb').read()
    
    def write(self, data: bytes):
        raise PermissionError("This file is read-only")  # VIOLATION: surprises callers of File


def process_file(file: File):
    file.write(b"log entry")  # works for File, explodes for ReadOnlyFile


# ✅ CORRECT — Proper hierarchy that respects contracts
class ReadableFile(ABC):
    @abstractmethod
    def read(self) -> bytes: pass


class WritableFile(ReadableFile, ABC):
    @abstractmethod
    def write(self, data: bytes): pass


class DiskFile(WritableFile):
    def read(self): ...
    def write(self, data): ...


class ReadOnlyDiskFile(ReadableFile):
    def read(self): ...
    # write() doesn't exist — no violated promise


# ❌ Classic Rectangle/Square violation
class Rectangle:
    def set_width(self, w): self.width = w
    def set_height(self, h): self.height = h
    def area(self): return self.width * self.height


class Square(Rectangle):
    def set_width(self, w):
        self.width = w
        self.height = w  # "helpfully" keeping square invariant
    
    def set_height(self, h):
        self.width = h   # VIOLATION: caller sets height, width changes unexpectedly
        self.height = h


def resize(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(3)
    assert rect.area() == 15  # passes for Rectangle, FAILS for Square (area = 9)
```

### Interview Perspective

LSP violations often appear in inheritance hierarchies with "special case" subclasses. Ask: "does every subtype fulfill the promise of the base type?" If a subtype _can't_ do something the base promises, it shouldn't inherit.

## I — Interface Segregation Principle

### The Real Definition

> Clients should not be forced to depend on interfaces they do not use.

Fat interfaces create coupling. A class implementing a fat interface is coupled to all the methods — even ones it doesn't need.

### Deep Example

```python
# ❌ VIOLATION — All exporters forced to implement all methods
class DataExporter(ABC):
    @abstractmethod
    def export_to_csv(self, data): pass
    
    @abstractmethod
    def export_to_pdf(self, data): pass
    
    @abstractmethod
    def export_to_excel(self, data): pass
    
    @abstractmethod
    def send_via_email(self, data, email): pass
    
    @abstractmethod
    def upload_to_s3(self, data, bucket): pass


class SimpleCSVExporter(DataExporter):
    def export_to_csv(self, data): ...       # only this is relevant
    def export_to_pdf(self, data): raise NotImplementedError   # forced stub
    def export_to_excel(self, data): raise NotImplementedError # forced stub
    def send_via_email(self, data, email): raise NotImplementedError
    def upload_to_s3(self, data, bucket): raise NotImplementedError


# ✅ CORRECT — Focused, composable interfaces
class CsvExporter(ABC):
    @abstractmethod
    def export_to_csv(self, data) -> str: pass

class PdfExporter(ABC):
    @abstractmethod
    def export_to_pdf(self, data) -> bytes: pass

class EmailDelivery(ABC):
    @abstractmethod
    def send_via_email(self, content, recipient: str): pass

class CloudStorage(ABC):
    @abstractmethod
    def upload(self, content, path: str) -> str: pass


# Implement only what you need
class OrderReportExporter(CsvExporter, PdfExporter):
    def export_to_csv(self, data): ...
    def export_to_pdf(self, data): ...


class SalesEmailer(CsvExporter, EmailDelivery):
    def export_to_csv(self, data): ...
    def send_via_email(self, content, recipient): ...
```

### Key Insight

ISP is also about the **caller's perspective**: each consumer should only know about the methods it uses. This reduces coupling and makes mocking in tests trivial.

## D — Dependency Inversion Principle

### The Real Definition

> 1. High-level modules should not depend on low-level modules. Both should depend on **abstractions**.
> 2. Abstractions should not depend on details. Details should depend on abstractions.

### Why It Exists

When high-level business logic depends on low-level infrastructure (DB, email, HTTP), swapping infrastructure requires changing business logic. That's backwards.

### Deep Example

```python
# ❌ VIOLATION — OrderService (high-level) depends on MySQLOrderRepo (low-level detail)
class OrderService:
    def __init__(self):
        self.repo = MySQLOrderRepository()      # hard dependency on concrete impl
        self.notifier = SMTPEmailNotifier()     # hard dependency on SMTP
    
    def place_order(self, order):
        self.repo.save(order)
        self.notifier.send(order.user.email, "Order placed")


# ✅ CORRECT — Both high-level and low-level depend on abstractions
class OrderRepository(ABC):
    @abstractmethod
    def save(self, order): pass
    
    @abstractmethod
    def find_by_id(self, order_id) -> Order: pass


class Notifier(ABC):
    @abstractmethod
    def notify(self, recipient: str, message: str): pass


# High-level module
class OrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier):
        self.repo = repo          # depends on abstraction
        self.notifier = notifier  # depends on abstraction
    
    def place_order(self, order):
        self.repo.save(order)
        self.notifier.notify(order.user.email, "Order placed")


# Low-level modules implement the abstractions
class MySQLOrderRepository(OrderRepository):
    def save(self, order): ...
    def find_by_id(self, order_id): ...


class PostgresOrderRepository(OrderRepository):  # swap without touching OrderService
    def save(self, order): ...
    def find_by_id(self, order_id): ...


class SMTPNotifier(Notifier):
    def notify(self, recipient, message): ...


class SlackNotifier(Notifier):  # swap without touching OrderService
    def notify(self, recipient, message): ...


# Wiring happens at composition root (main.py / DI container)
service = OrderService(
    repo=MySQLOrderRepository(),
    notifier=SMTPNotifier()
)
```

### DIP + Dependency Injection

DIP is the _principle_. Dependency Injection is the _technique_ to implement it. DI frameworks (Spring, FastAPI's `Depends`, Python's `dependency_injector`) automate the wiring.

### Interview Perspective

DIP is the foundation of testability. Ask: "can I swap the DB for a mock in tests without changing business logic?" If yes, you've applied DIP.

## SOLID Together — A Mental Model

```
         ┌─────────────────────────────────────────────┐
         │           Your Business Logic               │
         │    (high-level, stable, hard to change)     │
         └────────────────┬────────────────────────────┘
                          │ depends on abstractions (DIP)
         ┌────────────────▼────────────────────────────┐
         │              Interfaces                     │
         │   (focused per consumer - ISP)              │
         │   (open to new implementations - OCP)       │
         └────────────────┬────────────────────────────┘
                          │ implemented by
         ┌────────────────▼────────────────────────────┐
         │         Concrete Implementations            │
         │  (one responsibility each - SRP)            │
         │  (substitutable by subclasses - LSP)        │
         └─────────────────────────────────────────────┘
```

## Common Interview Questions

| Question                                   | Key Answer Point                                                                            |
| ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| "Which SOLID principle is most important?" | DIP — it enables all others                                                                 |
| "How does SOLID relate to testing?"        | DIP makes mocking possible; SRP makes unit scope obvious                                    |
| "When would you NOT follow SOLID?"         | Small scripts, prototypes, when cost of abstraction > benefit                               |
| "SOLID vs YAGNI — when do they conflict?"  | SOLID can lead to premature abstraction; apply SOLID when you see the variation, not before |
