# TanStack Query Fundamentals

Server state is not client state. It lives on a server you do not control, it goes stale without your knowledge, it can be requested by several components at once, and it needs revalidation, retries and cancellation ([[20.1 - Where State Should Live]]).

TanStack Query is a **cache** for that data, not a state manager.

## What it replaces

```jsx
// Roughly 40 lines, and still missing caching, deduplication and background refetch
const [data, setData] = useState(null);
const [error, setError] = useState(null);
const [status, setStatus] = useState("idle");

useEffect(() => {
  const controller = new AbortController();
  setStatus("loading");

  (async () => {
    try {
      const res = await fetch(url, { signal: controller.signal });
      if (!res.ok) throw new HttpError(res.status);
      setData(await res.json());
      setStatus("success");
    } catch (err) {
      if (err.name === "AbortError") return;
      setError(err);
      setStatus("error");
    }
  })();

  return () => controller.abort();
}, [url]);
```

```jsx
const { data, error, status } = useQuery({
  queryKey: ["products", categoryId],
  queryFn: ({ signal }) => api.getProducts(categoryId, { signal }),
});
```

The second version additionally gives caching across components, request deduplication, background refetching, retries with backoff, and cancellation on unmount or key change.

## Setup

```jsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,
      retry: (count, error) => error.status < 500 ? false : count < 3,
    },
  },
});

<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>
```

Two defaults worth changing immediately: `staleTime` (the library default of 0 means every mount refetches) and the retry predicate (the default retries 4xx errors, which will fail identically) ([[24.3 - Retries Timeouts and Cancellation]]).

## Query keys

```jsx
["products"]                                    // all products
["products", { category: "shoes", page: 2 }]    // a filtered list
["products", productId]                         // one product
```

The key is the **cache identity**. Two components using the same key share one cache entry and one in-flight request — deduplication is automatic and requires no coordination.

The key is also the **dependency array**: when it changes, the query refetches. Every value the query function reads must appear in the key, exactly like a hook dependency ([[17.3 - useEffect and the Dependency Array]]).

Keys are hashed deterministically, so object property order does not matter.

**Centralize keys in a factory.** Scattered inline keys are the main source of invalidation bugs:

```js
export const productKeys = {
  all: ["products"],
  lists: () => [...productKeys.all, "list"],
  list: (filters) => [...productKeys.lists(), filters],
  details: () => [...productKeys.all, "detail"],
  detail: (id) => [...productKeys.details(), id],
};
```

The hierarchy enables prefix invalidation: `invalidateQueries({ queryKey: productKeys.lists() })` invalidates every list regardless of filters, without touching detail queries ([[24.7 - Caching Stale Time and Invalidation]]).

## Query options factories

```js
export const productQuery = (id) => ({
  queryKey: productKeys.detail(id),
  queryFn: ({ signal }) => api.getProduct(id, { signal }),
  staleTime: 5 * 60_000,
});

// Component
const { data } = useQuery(productQuery(id));

// Router loader
await queryClient.ensureQueryData(productQuery(params.id));

// Prefetch on hover
queryClient.prefetchQuery(productQuery(id));
```

Defining the query once and reusing it across components, loaders and prefetches keeps the key and the fetcher from drifting apart. This is the single most valuable structural habit with the library ([[23.6 - Data Loading with Loaders and Actions]]).

## Reading the result

```jsx
const {
  data, error,
  status,          // "pending" | "error" | "success"
  fetchStatus,     // "fetching" | "paused" | "idle"
  isFetching,      // any fetch in flight, including background
  isRefetching,    // background fetch with data already present
  refetch,
} = useQuery(productQuery(id));
```

`status` and `fetchStatus` are deliberately separate. `status === "success"` with `isFetching === true` means data is on screen and being refreshed — showing a full skeleton there is a regression ([[24.2 - Loading Error and Empty States]]).

The convention is dim on background refetch, skeleton only on first load.

## Dependent queries

```jsx
const { data: user } = useQuery(userQuery(userId));

const { data: projects } = useQuery({
  ...projectsQuery(user?.teamId),
  enabled: Boolean(user?.teamId),
});
```

`enabled` defers a query until its input exists. Without it, the query runs with `undefined` and either fails or caches garbage.

Note that a disabled query has `status: "pending"` but `fetchStatus: "idle"` — checking `isLoading` (which combines both) rather than `isPending` avoids showing a spinner for a query that has not started.

## Mutations

```jsx
const queryClient = useQueryClient();

const { mutate, isPending } = useMutation({
  mutationFn: (input) => api.createProduct(input),
  onSuccess: (created) => {
    queryClient.invalidateQueries({ queryKey: productKeys.lists() });
    queryClient.setQueryData(productKeys.detail(created.id), created);
  },
});

mutate({ name: "New product" });
```

`invalidateQueries` marks matching queries stale and refetches the mounted ones. `setQueryData` writes directly, avoiding a refetch when the mutation response already contains the new state.

Doing both is common: seed the detail cache from the response, invalidate the lists that may now be ordered or filtered differently.

Mutations do **not** retry by default, which is correct — a POST is not idempotent ([[24.3 - Retries Timeouts and Cancellation]]).

## Transforming data

```jsx
useQuery({
  ...productsQuery(filters),
  select: (data) => data.items.map(toViewModel),
});
```

`select` runs after fetching and is memoized on the raw data. Two components can select different shapes from the same cache entry without duplicating the request.

Use it for derived shapes; keep the cache holding the server's response so invalidation and updates stay simple.

## Cancellation

```jsx
queryFn: ({ signal }) => fetch(url, { signal })
```

The library supplies an `AbortSignal` and aborts on unmount or key change. Forwarding it is what fixes the search race condition — a slow earlier response resolving after a fast later one ([[04.6 - AbortController and Cancellation]]).

Failing to forward `signal` silently disables this, which is a common oversight in the API layer ([[24.1 - Building an API Layer]]).

## Suspense mode

```jsx
const { data } = useSuspenseQuery(productQuery(id));   // data is never undefined

<ErrorBoundary fallback={<Error />}>
  <Suspense fallback={<Skeleton />}>
    <ProductDetail />
  </Suspense>
</ErrorBoundary>
```

Loading and error branches move to boundaries, and `data` is typed as always present — which removes a great deal of optional chaining ([[19.4 - Suspense]]).

The tradeoff: sibling `useSuspenseQuery` calls in one component serialize into a waterfall. Use `useSuspenseQueries` for parallel fetches.

## DevTools

```jsx
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";

<ReactQueryDevtools initialIsOpen={false} />
```

Shows every cache entry, its state, its data, and when it was last fetched. For debugging "why did this refetch" or "why is this stale", it is the fastest available tool and worth installing on day one.

## Alternatives

**SWR** — smaller, simpler, similar model. Fewer features around mutations and infinite queries.

**RTK Query** — the natural choice if the project already uses Redux Toolkit, with the same caching model integrated into the store ([[20.4 - Redux Toolkit]]).

**Framework loaders** — Next.js and React Router handle fetching at the route level, which removes waterfalls but does not provide client-side caching. Combining a loader with a query cache gets both ([[23.6 - Data Loading with Loaders and Actions]]).

All of them are better than `useEffect` fetching.

## How senior engineers actually use this

**They set `staleTime` deliberately.** The default of 0 refetches on every mount, which surprises people who expect a cache.

**They centralize query keys and query options** so keys and fetchers cannot drift.

**They forward `signal` through the API layer**, since cancellation is otherwise silently absent.

**They distinguish first load from background refetch** in the UI.

**They keep client state out of the query cache** — it is a server-state cache, not a general store.

## Common pitfalls

- Leaving `staleTime: 0`, causing a refetch on every mount.
- Missing a dependency in the query key, so data goes stale silently.
- Not forwarding `signal`, disabling cancellation.
- Showing a skeleton during background refetch.
- Retrying 4xx errors with the default retry setting.
- Inline query keys, making invalidation unreliable.
- Storing client-only state in the query cache.
- Sequential `useSuspenseQuery` calls creating waterfalls.

## Interview angle

"Why use a data-fetching library instead of useEffect" is the question. Frame it as server state versus client state: server data is a cache of something you do not own, so it needs staleness, revalidation, deduplication, retries and cancellation — all of which effect-based fetching reimplements badly. Then the specifics: query keys as cache identity and dependency array, the status/fetchStatus split for background refetch, and automatic cancellation via `AbortSignal`.
