## Goal

Build a working rate limiter to understand it from the inside — not just use it as a black box.

We'll implement two algorithms:
1. **Token Bucket** — allows bursting, smooth sustained rate
2. **Sliding Window Counter** — approximate, memory-efficient, distributed-friendly

Then show how production systems extend these.

---

## 1. Token Bucket (In-Memory, Single Process)

### Core Design

```
State per client:
  tokens: float        (current token count)
  last_refill: float   (timestamp of last refill)

On each request:
  1. Refill tokens based on elapsed time
  2. If tokens >= 1: consume 1 token, allow request
  3. Else: reject request
```

### Implementation

```python
import time
import threading
from dataclasses import dataclass, field
from typing import Dict

@dataclass
class TokenBucket:
    capacity: float         # max tokens
    refill_rate: float      # tokens per second
    tokens: float = field(init=False)
    last_refill: float = field(init=False)
    lock: threading.Lock = field(default_factory=threading.Lock, init=False)

    def __post_init__(self):
        self.tokens = self.capacity
        self.last_refill = time.monotonic()

    def _refill(self):
        now = time.monotonic()
        elapsed = now - self.last_refill
        added = elapsed * self.refill_rate
        self.tokens = min(self.capacity, self.tokens + added)
        self.last_refill = now

    def consume(self, tokens: float = 1.0) -> bool:
        with self.lock:
            self._refill()
            if self.tokens >= tokens:
                self.tokens -= tokens
                return True   # allowed
            return False      # rate limited


# Per-client rate limiter store
class RateLimiter:
    def __init__(self, capacity: int, refill_rate: float):
        self.capacity = capacity
        self.refill_rate = refill_rate
        self._buckets: Dict[str, TokenBucket] = {}
        self._lock = threading.Lock()

    def is_allowed(self, client_id: str) -> bool:
        with self._lock:
            if client_id not in self._buckets:
                self._buckets[client_id] = TokenBucket(
                    capacity=self.capacity,
                    refill_rate=self.refill_rate
                )
        return self._buckets[client_id].consume()


# Usage
limiter = RateLimiter(capacity=10, refill_rate=2)  # 10 burst, 2/s sustained

for i in range(15):
    allowed = limiter.is_allowed("user:42")
    print(f"Request {i+1}: {'✅ allowed' if allowed else '❌ limited'}")
```

### Output

```
Request 1–10:  ✅ allowed  (burst capacity used up)
Request 11–15: ❌ limited  (refill rate 2/s, not enough tokens yet)
```

## 2. Sliding Window Counter (Redis-based, Distributed)

### Core Design

Use two fixed-window counters to approximate a sliding window:

```
current_window_count  = count in the current fixed window
previous_window_count = count in the previous fixed window
weight = how far we are into the current window (0.0 to 1.0)

estimated_count = previous_window_count * (1 - weight) + current_window_count
```

### Implementation

```python
import time
import redis

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def is_rate_limited(client_id: str, limit: int, window_seconds: int) -> bool:
    """
    Sliding window counter using two Redis keys.
    Returns True if the request should be rate-limited.
    """
    now = time.time()
    current_window = int(now // window_seconds)
    previous_window = current_window - 1

    current_key  = f"rl:{client_id}:{current_window}"
    previous_key = f"rl:{client_id}:{previous_window}"

    # Atomic increment of current window counter
    pipe = r.pipeline()
    pipe.incr(current_key)
    pipe.expire(current_key, window_seconds * 2)  # keep for 2 windows
    pipe.get(previous_key)
    results = pipe.execute()

    current_count  = int(results[0])
    previous_count = int(results[2] or 0)

    # How far into current window are we? (0.0 = start, 1.0 = end)
    weight = (now % window_seconds) / window_seconds

    # Weighted estimate
    estimated = previous_count * (1 - weight) + current_count

    return estimated > limit


# Usage
for i in range(12):
    limited = is_rate_limited("user:42", limit=10, window_seconds=60)
    print(f"Request {i+1}: {'❌ limited' if limited else '✅ allowed'}")
```

### Why This Works

At time 10:00:45 (45s into current window):
- Previous window (10:00:00–10:01:00) had 8 requests
- Current window (10:01:00–10:02:00) has 4 requests so far
- Weight = 45/60 = 0.75

Estimated = 8 × (1 - 0.75) + 4 = 8 × 0.25 + 4 = **6** — under limit of 10, allow.

## 3. Token Bucket in Redis (Distributed)

The cleanest production-grade version: store token state in Redis, use Lua for atomic operations.

```python
import redis
import time

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

# Lua script — atomic: runs as a single Redis command
TOKEN_BUCKET_SCRIPT = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])    -- tokens per second
local now = tonumber(ARGV[3])            -- current timestamp (float)
local requested = tonumber(ARGV[4])      -- tokens to consume

-- Load current state
local data = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(data[1]) or capacity
local last_refill = tonumber(data[2]) or now

-- Refill based on elapsed time
local elapsed = now - last_refill
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

-- Try to consume
if new_tokens >= requested then
    new_tokens = new_tokens - requested
    redis.call('HMSET', key, 'tokens', new_tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 1)
    return 1  -- allowed
else
    redis.call('HMSET', key, 'tokens', new_tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 1)
    return 0  -- rate limited
end
"""

def is_allowed(client_id: str, capacity: int, refill_rate: float) -> bool:
    key = f"token_bucket:{client_id}"
    now = time.time()
    result = r.eval(TOKEN_BUCKET_SCRIPT, 1, key, capacity, refill_rate, now, 1)
    return bool(result)
```

## What Production Systems Add

Our implementation covers the core algorithm. Production systems add:

| Feature | What It Solves |
|---|---|
| Multi-tier limits | Per-second AND per-day limits on the same client |
| Dynamic limits | Different limits per API key tier (free vs paid) |
| Graceful headers | `X-RateLimit-Remaining`, `Retry-After` in response |
| Metrics & alerting | Track rate-limit hit rate per client/endpoint |
| Bypass lists | Internal services exempt from limits |
| Distributed consensus | Redlock-style for multi-region rate limiting |
| Warm-up / cold start | New client starts with full bucket, not empty |

---

## Key Takeaways

- Token bucket = two numbers (tokens + last_refill) + atomic update
- The Lua script is critical — without atomicity, concurrent requests race on the same bucket
- Redis handles distribution; in-memory handles single-process
- The algorithm is simple; the complexity is in edge cases (TTL management, clock drift, Redis failure behavior)
