# SOQL and DML Limits

## The numbers

```
                              Synchronous   Asynchronous
SOQL queries                          100            200
Records retrieved by SOQL          50,000         50,000
SOSL queries                           20             20
Records retrieved by SOSL           2,000          2,000
DML statements                        150            150
Records processed by DML           10,000         10,000
```

Note that the **row** limits do not double in async — only the statement counts do. A transaction retrieving 50,000 rows is at the ceiling whether it is synchronous or not.

## Query count: the collect-query-act rule

The 100-query limit is almost always hit the same way.

```java
// One query per record; dies at 101
for (Warranty_Claim__c claim : claims) {
    Asset asset = [SELECT Id, SerialNumber FROM Asset WHERE Id = :claim.Asset__c];
    claim.Asset_Serial__c = asset.SerialNumber;
}
```

```java
// One query for all of them
Set<Id> assetIds = new Set<Id>();
for (Warranty_Claim__c claim : claims) {
    if (claim.Asset__c != null) {
        assetIds.add(claim.Asset__c);
    }
}

Map<Id, Asset> assets = new Map<Id, Asset>([
    SELECT Id, SerialNumber FROM Asset WHERE Id IN :assetIds
]);

for (Warranty_Claim__c claim : claims) {
    Asset asset = assets.get(claim.Asset__c);
    if (asset != null) {
        claim.Asset_Serial__c = asset.SerialNumber;
    }
}
```

Covered fully in [[10.6 - Bulkification Patterns]]; restated here because it accounts for the large majority of query-limit failures.

## The queries you did not write

The shared-budget point from [[16.1 - Why Governor Limits Exist]], made concrete.

**Flows query per record.** A record-triggered flow with one Get Records element, firing on a save of 200 records, issues up to 200 queries — against the same 100-query limit as your trigger. This is the single most common source of "my perfectly bulkified trigger fails". See [[07.10 - Flow Limits and Performance]].

**Managed packages** consume from the same budget in their own namespace, and you cannot see or change what they do.

**Roll-up recalculation** sends parent records through their own save pipeline, and their triggers query too.

**Validation rules** with cross-object formulas cost query work.

The practical consequence: an object with a trigger, three flows, and a managed package has a query budget shared four ways, and yours is whatever is left.

## Query rows

Separate from the query count and easier to miss.

```java
// 4 queries, 50,000 rows — hits the row limit, not the query limit
List<Warranty_Claim__c> a = [SELECT Id FROM Warranty_Claim__c LIMIT 20000];
List<Warranty_Claim__c> b = [SELECT Id FROM Warranty_Claim__c LIMIT 20000];
List<Warranty_Claim__c> c = [SELECT Id FROM Warranty_Claim__c LIMIT 20000];
```

**Rows accumulate across every query in the transaction**, including subqueries and rows retrieved by managed packages.

A relationship subquery counts parents **and** children:

```sql
SELECT Id, (SELECT Id FROM Warranty_Claims__r)
FROM Asset
```

1,000 assets with 60 claims each is 61,000 rows and fails. See [[08.2 - Relationship Queries]].

Two mitigations:

**`SELECT COUNT()` does not consume the row limit** for the rows counted:

```java
Integer total = [SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Submitted'];
```

**The list form of the SOQL for loop** retrieves 200 at a time, keeping heap bounded — though the total still counts toward 50,000:

```java
for (List<Warranty_Claim__c> chunk : [SELECT Id, Status__c FROM Warranty_Claim__c WHERE ...]) {
    // heap holds 200 at a time
    update chunk;
}
```

Beyond 50,000 rows, Batch Apex. Its `QueryLocator` handles up to 50 million and is not subject to this limit. See [[12.4 - Batch Apex]].

## DML statements

```java
// One statement per record
for (Warranty_Claim__c claim : claims) {
    update claim;
}

// One statement for all of them
update claims;
```

**DML on an empty list still counts as a statement**, which is why the guard matters in code with several conditional paths:

```java
if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

In a handler with six conditional updates, six unguarded statements are consumed even when nothing matched.

## DML rows

```
10,000 records processed by DML, per transaction
```

**Cascading operations count.** Updating 200 opportunities that each cascade a roll-up to an account processes 200 plus up to 200 more. If the account trigger updates contacts, more still.

This is why a bulk operation that looks like 200 records can exhaust a 10,000-row budget — the cascade at step 15 of the order of execution multiplies it. See [[07.13 - Order of Execution]].

**A cascade delete counts every deleted child.** Deleting 100 claims with 50 parts each is 5,100 rows.

## Combining DML statements

Where records are genuinely independent, a mixed list is one statement:

```java
List<SObject> toInsert = new List<SObject>();
toInsert.addAll((List<SObject>) newTasks);
toInsert.addAll((List<SObject>) newLogs);
insert toInsert;
```

**Only for independent records.** Anything with a dependency — children referencing parents that do not yet exist — must be sequenced.

The saving is rarely worth the risk, and it matters when a large handler is approaching the statement limit.

## SOSL

```
20 SOSL queries, 2,000 rows
```

Much tighter than SOQL, and the reason a single multi-object SOSL beats several single-object ones:

```sql
FIND :searchTerm IN ALL FIELDS
RETURNING
    Asset (Id, Name LIMIT 10),
    Warranty_Claim__c (Id, Claim_Number__c LIMIT 10),
    Case (Id, CaseNumber LIMIT 10)
```

One SOSL query across three objects, rather than three SOQL queries — and it uses the text index rather than scanning. See [[08.8 - SOSL and Full Text Search]].

## Async limits

```
SOQL queries          200
Query rows         50,000
DML statements        150
DML rows           10,000
CPU time      60 seconds
Heap               12 MB
```

The important point is not the doubling. It is that **each async execution is a new transaction with a fresh budget**.

```java
// One transaction, one budget
processAllClaims(tenThousandClaimIds);

// Fifty transactions, fifty budgets
for (List<Id> chunk : chunked(tenThousandClaimIds, 200)) {
    System.enqueueJob(new ClaimProcessorQueueable(chunk));
}
```

Batch Apex does the chunking automatically, with monitoring, which is why it is the right tool above a few thousand records rather than a hand-rolled Queueable chain. See [[12.10 - Choosing the Right Async Tool]].

## Diagnosing

The limit block at the end of every debug log:

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 94 out of 100
  Number of query rows: 41203 out of 50000
  Number of DML statements: 118 out of 150
  Number of DML rows: 8420 out of 10000
```

**Anything above 70 percent on a routine operation is a warning.** Data grows and automation accumulates; a transaction at 94 queries today fails next quarter.

To find *which* query, the log shows each `SOQL_EXECUTE_BEGIN` with its line number. A query appearing 200 times is in a loop, and the line number names it.

The Developer Console's execution tree groups by operation and is faster to read than the raw log for this. See [[20.3 - Developer Console and Log Inspector]].

## Testing against the limits

```java
@IsTest
static void handlerStaysWithinQueryLimitsInBulk() {
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(assets, 200);

    Test.startTest();
    insert claims;

    // asserting on consumption catches a regression that a functional test would miss
    System.debug('Queries: ' + Limits.getQueries() + ' of ' + Limits.getLimitQueries());
    Assert.isTrue(Limits.getQueries() < 30,
        'The handler should use well under the query limit for 200 records');
    Test.stopTest();
}
```

`Test.startTest()` resets the limit counters, so the assertion measures only the code under test.

Asserting on consumption rather than only on behaviour is worth doing for anything on a hot object. A query added inside a loop passes every functional test and fails in production.

## Practical guidance

**Collect, query once, act once.** It solves most of the query limit.

**Guard DML with `isEmpty()`.**

**Count with `SELECT COUNT()`** rather than retrieving rows.

**Use the list form of the SOQL for loop** for large result sets.

**Watch subqueries** — parents and children share the row limit.

**Remember the cascade** counts toward DML rows.

**Use one multi-object SOSL** rather than several SOQL queries for search.

**Move to Batch Apex** above a few thousand records.

**Audit the object's total automation**, not just your code.

**Assert on limit consumption** in bulk tests for hot objects.
