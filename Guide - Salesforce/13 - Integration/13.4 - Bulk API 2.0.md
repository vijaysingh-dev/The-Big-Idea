# Bulk API 2.0

## When to use it

Above roughly **a few thousand records**, the REST API stops being the right tool. Each request consumes the daily API allocation, and 500,000 records at 200 per call is 2,500 requests.

Bulk API 2.0 takes the whole dataset as one job, processes it asynchronously in parallel, and consumes a separate allocation.

The rough boundary:

| Volume | Tool |
| --- | --- |
| Under 200 | REST, single record or sObject Collections |
| 200 to a few thousand | sObject Collections, batched |
| Above that | Bulk API 2.0 |

## The job lifecycle

Four steps.

**1. Create the job**

```
POST /services/data/v62.0/jobs/ingest
```

```json
{
  "object": "Warranty_Claim__c",
  "externalIdFieldName": "ERP_Claim_Id__c",
  "operation": "upsert",
  "lineEnding": "LF"
}
```

The response includes a job Id and a `contentUrl`.

**2. Upload the data**

```
PUT /services/data/v62.0/jobs/ingest/{jobId}/batches
Content-Type: text/csv
```

```csv
ERP_Claim_Id__c,Claim_Amount__c,Status__c,Asset__r.ERP_Asset_Id__c
CLM-99201,150000,Under Review,MCH-88213
CLM-99202,90000,Submitted,MCH-88214
```

Note the `Asset__r.ERP_Asset_Id__c` column — setting a lookup by the parent's external key, which removes the ID-mapping step from a migration entirely. See [[10.3 - Upsert, Merge and External IDs]].

**3. Close the job**, which starts processing

```
PATCH /services/data/v62.0/jobs/ingest/{jobId}
{ "state": "UploadComplete" }
```

**4. Poll for completion**

```
GET /services/data/v62.0/jobs/ingest/{jobId}
```

```json
{
  "state": "JobComplete",
  "numberRecordsProcessed": 487213,
  "numberRecordsFailed": 42,
  "totalProcessingTime": 284000
}
```

States: `Open`, `UploadComplete`, `InProgress`, `JobComplete`, `Failed`, `Aborted`.

**5. Retrieve results**

```
GET /services/data/v62.0/jobs/ingest/{jobId}/successfulResults/
GET /services/data/v62.0/jobs/ingest/{jobId}/failedResults/
GET /services/data/v62.0/jobs/ingest/{jobId}/unprocessedRecords/
```

The failed results file contains **the original row plus the error message**, which makes the standard recovery loop straightforward: fix the file, resubmit just those rows.

Keeping every failed-results file from a migration is worth doing. Reconciliation at the end is counting what went in against what was in the source, and these files are half the arithmetic.

## Operations

```
insert
update
upsert          requires externalIdFieldName
delete          Id column only
hardDelete      bypasses the recycle bin, requires a specific permission
```

`hardDelete` is substantially faster for large deletions because the recycle bin is skipped entirely. It is also irreversible. See [[10.4 - Delete, Undelete and the Recycle Bin]].

## Bulk query

The extraction counterpart, and the right way to pull large volumes out:

```
POST /services/data/v62.0/jobs/query
```

```json
{
  "operation": "query",
  "query": "SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c FROM Warranty_Claim__c WHERE Claim_Date__c = LAST_N_YEARS:2"
}
```

```
GET /services/data/v62.0/jobs/query/{jobId}/results
```

Results come back as CSV, paginated with a `Sforce-Locator` header:

```
Sforce-Locator: MjAwMDAwMA
Sforce-NumberOfRecords: 50000
```

Passing the locator as a `locator` parameter retrieves the next chunk.

`queryAll` as the operation includes deleted and archived records.

Bulk query is not subject to the 50,000-row limit that constrains synchronous SOQL, which is what makes it viable for full extracts.

## Serial versus parallel

The setting that resolves most bulk-load failures.

**Parallel** is the default. Chunks process concurrently, which is fast and is where lock contention appears — several chunks touching children of the same parent collide with `UNABLE_TO_LOCK_ROW`.

**Serial** processes one chunk at a time. Slower, and it eliminates contention.

```json
{
  "object": "Warranty_Claim__c",
  "operation": "insert",
  "concurrencyMode": "Serial"
}
```

The better first fix is usually not serial mode but **sorting the file by parent Id**, so children of the same parent land in the same chunk. That keeps parallelism and removes most of the contention. Serial is the fallback when sorting is not enough. See [[10.8 - Record Locking and Deadlocks]].

## Preparing for a large load

The steps that make the difference between a three-hour load and a three-day one.

**Sort by parent Id.** The single most effective change.

**Disable non-essential automation.** Validation rules, flows, and triggers all run on every loaded record. Deactivating what is not needed for the load can halve the runtime. This must be deliberate and reversible, and anything skipped has to be reconciled afterwards — which is what the bypass mechanism in [[11.5 - Trigger Handler Pattern]] is for.

**Defer sharing calculation.** Setup offers an option to suspend sharing recalculation during a load and run it once at the end. On a large load into a private object this is often the largest single speedup. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

**Turn off field history tracking** temporarily where it is not needed for the migrated data. History rows are written for every tracked field on every record.

**Load in dependency order.** Parents before children, and always use external IDs so no ID-mapping pass is needed.

**Time it in a Full sandbox first.** A load taking three hours there will not take twenty minutes in production.

See [[23.5 - Bulk Data Loading at Scale]].

## Limits

- **150 million records per rolling 24 hours** across all bulk jobs
- **100 MB per uploaded file**, base64-encoded content counted
- **15,000 batches per 24 hours** in the older Bulk API 1.0 model
- Jobs and results are **retained for 7 days**
- Bulk API consumes a **separate allocation** from the daily REST API request limit

That last point is the commercial argument for it beyond speed: a 500,000-record load through REST would consume a meaningful fraction of the daily API allocation, and through Bulk it consumes almost none of it.

## Bulk API 1.0

Still supported, and you will meet it in older tooling. The differences:

**You manage batching.** 1.0 requires the client to split data into batches of up to 10,000 records; 2.0 does it for you.

**More granular monitoring**, at batch level rather than job level.

**Different endpoints** — `/services/async/62.0/job` rather than `/services/data/v62.0/jobs/ingest`.

Data Loader uses 1.0 by default in some configurations. For new work, 2.0 is simpler and there is no reason to choose 1.0.

## Bulk API from Apex

Salesforce calling its own Bulk API is unusual — Batch Apex is the in-org equivalent and does not consume API calls.

The case where it makes sense: pushing data **to another org**.

```java
public with sharing class CrossOrgBulkLoader implements Queueable, Database.AllowsCallouts {

    private final List<Warranty_Claim__c> claims;

    public CrossOrgBulkLoader(List<Warranty_Claim__c> claims) {
        this.claims = claims;
    }

    public void execute(QueueableContext context) {
        String jobId = createJob();
        uploadCsv(jobId, buildCsv(claims));
        closeJob(jobId);

        // polling belongs in a separate scheduled job, not in this transaction
        insert new Bulk_Job_Tracker__c(External_Job_Id__c = jobId, Status__c = 'UploadComplete');
    }

    private String createJob() {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:Partner_Org/services/data/v62.0/jobs/ingest');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(new Map<String, String>{
            'object' => 'Warranty_Claim__c',
            'operation' => 'upsert',
            'externalIdFieldName' => 'Source_Claim_Id__c'
        }));

        HttpResponse res = new Http().send(req);
        Map<String, Object> parsed = (Map<String, Object>) JSON.deserializeUntyped(res.getBody());
        return (String) parsed.get('id');
    }
}
```

Polling for completion belongs in a separate scheduled job. A Queueable waiting for a bulk job to finish would exceed its callout time budget and hold the transaction open for nothing.

## Data Loader and the CLI

For one-off and scripted loads, the tooling is usually better than hand-built API calls.

```bash
sf data upsert bulk \
  --sobject Warranty_Claim__c \
  --file claims.csv \
  --external-id ERP_Claim_Id__c \
  --wait 30 \
  --target-org production

sf data query bulk \
  --query "SELECT Id, Claim_Number__c FROM Warranty_Claim__c WHERE Status__c = 'Closed'" \
  --output-file closed-claims.csv \
  --wait 30 \
  --target-org production
```

`--wait` polls until completion. Omitting it returns the job Id immediately, which is what you want in a pipeline that checks later.

Data Loader in command-line mode remains the standard for recurring scheduled loads on a server. See [[02.13 - Data Import and Export Tools]].

## Errors

The failed results file is where diagnosis starts. The errors that recur:

```
REQUIRED_FIELD_MISSING              a field-level required field
INVALID_CROSS_REFERENCE_KEY         a lookup pointing at a missing record — usually load order
DUPLICATE_VALUE                     unique field or external Id collision
FIELD_CUSTOM_VALIDATION_EXCEPTION   a validation rule rejected the row
UNABLE_TO_LOCK_ROW                  contention — sort by parent, or go serial
CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY  a trigger threw; the message usually names the class
STORAGE_LIMIT_EXCEEDED              the org is out of data storage
```

**`INVALID_CROSS_REFERENCE_KEY` in bulk almost always means load order** — children loaded before parents, or an external key that does not resolve.

**`UNABLE_TO_LOCK_ROW` clustering around certain parents** is the signature of skew or unsorted data.

## Practical guidance

**Use Bulk 2.0**, not 1.0, for new work.

**Always upsert on an external ID**, so a resubmission is safe.

**Set lookups by the parent's external key** rather than mapping Ids.

**Sort by parent Id** before loading.

**Disable non-essential automation** for large loads, deliberately and reversibly.

**Defer sharing calculation** on large loads into private objects.

**Keep every failed-results file** for reconciliation.

**Time the load in a Full sandbox** before scheduling it in production.
