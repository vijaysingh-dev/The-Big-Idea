# Caching Strategy Across Layers

A request can be answered from five places, each faster and less fresh than the one below it.

```
1. In-memory query cache        instant, per tab, lost on reload
2. Persisted client cache       instant, survives reload  (localStorage / IndexedDB)
3. Service Worker cache         instant, works offline
4. HTTP cache                   no request at all, browser-managed
5. CDN edge cache               one short network hop
   ↓
   Origin
```

Designing a caching strategy means deciding, per kind of data, **which layer answers and how it becomes stale**.

## The layers, and what each is for

**Query cache** (TanStack Query, RTK Query, Apollo). Holds server data in memory, keyed by query key, with explicit staleness and invalidation ([[24.7 - Caching Stale Time and Invalidation]]). This is where most frontend caching decisions actually live.

**Persisted cache.** The query cache written to storage so a returning user sees content immediately while it revalidates. Needs a version buster and care about what is stored ([[14.2 - LocalStorage and SessionStorage]]).

**Service Worker cache.** The only programmable layer, and the only one that works offline ([[14.4 - Cache API and Service Workers]]). Also the only one capable of permanently breaking your site if the logic is wrong.

**HTTP cache.** Browser-managed, driven by response headers. Zero JavaScript involved, and it applies to assets as well as API responses ([[15.7 - HTTP Caching and CDNs]]).

**CDN.** Shared across users, so it only helps for data that is not user-specific.

## Match the layer to the data

| Data | Layer | Policy |
| --- | --- | --- |
| Hashed JS/CSS | HTTP + CDN | `max-age=31536000, immutable` |
| HTML | HTTP | `no-cache` — always revalidate |
| Images | HTTP + CDN | long max-age with hashed or versioned URLs |
| Reference data (countries, categories) | query + CDN | `staleTime: Infinity` |
| Product catalogue | query + CDN | `staleTime` 1–5 min, `s-maxage` at the edge |
| User profile | query | `staleTime` 5 min, `private` |
| Cart, inventory | query | `staleTime: 0`, never cached publicly |
| Anything with a `Set-Cookie` | none shared | `private` at minimum |

The critical safety rule: **anything user-specific must be `private`**. A CDN storing a response containing another user's data is a serious incident, and CDN misconfiguration here has caused real breaches at large companies.

## The two-tier asset strategy

```
/assets/main.a3f9c2.js   Cache-Control: public, max-age=31536000, immutable
/index.html              Cache-Control: no-cache
```

Content-hashed filenames mean the URL changes when the content does, so assets can be cached forever with no invalidation problem. The uncached HTML is the pointer to the current filenames.

This is why bundlers hash output, and it is the highest-leverage caching decision in a frontend deployment ([[27.2 - Module Bundling Concepts]]).

The associated failure: after a deploy, an open tab holds HTML referencing chunks that were deleted. Keep old assets for a day or two and ship client-side reload-on-chunk-error ([[27.9 - CI CD and Frontend Deployment]]).

## stale-while-revalidate everywhere

The same pattern appears at three layers, and recognizing it as one idea simplifies the design:

```
Cache-Control: max-age=60, stale-while-revalidate=600      # HTTP
staleTime: 60_000                                          # query cache
caches.match(req) then fetch and update                    # Service Worker
```

Serve what you have immediately, refresh in the background, swap when ready. The user waits for nothing; the data converges to fresh.

The consequence to design for is that the UI must handle **data that is present but updating** — dimming rather than replacing with a skeleton ([[24.2 - Loading Error and Empty States]]).

## Invalidation

The hard part, and the one that produces most caching bugs.

**Time-based.** `staleTime` and `max-age`. Simple, and always either too eager or too stale for something.

**Event-based.** A mutation invalidates related queries:

```ts
onSuccess: () => queryClient.invalidateQueries({ queryKey: productKeys.lists() })
```

Correct by construction — the server is the source of truth and you refetch it. Hierarchical query keys make prefix invalidation possible, which is why key factories matter ([[24.6 - TanStack Query Fundamentals]]).

**Tag-based.** RTK Query and Next.js use tags rather than keys:

```ts
providesTags: ["Product"],
invalidatesTags: ["Product"],
```

**Version-based.** For persisted and Service Worker caches, a version in the key so a schema change discards the old data rather than deserializing an incompatible shape.

**Cross-tab.** A mutation in one tab leaves other tabs stale. `BroadcastChannel` propagates the signal:

```ts
const channel = new BroadcastChannel("cache");
channel.onmessage = (e) => queryClient.invalidateQueries({ queryKey: e.data.key });
```

Frequently forgotten, and visible to any user who works with two tabs open.

## Direct writes versus invalidation

```ts
// Write — no round trip, but can drift from server-computed fields
queryClient.setQueryData(productKeys.detail(id), updated);

// Invalidate — always consistent, costs a request
queryClient.invalidateQueries({ queryKey: productKeys.detail(id) });
```

Write when the mutation response contains the complete new state. Invalidate when the server computes anything the client cannot predict — a derived total, a modified timestamp, a re-sorted position.

The common combination: `setQueryData` for the entity that was returned, `invalidateQueries` for lists whose ordering or membership may have changed ([[24.8 - Optimistic Updates with TanStack Query]]).

## Bounding cache growth

Every distinct key is an entry. A query keyed by a search string accumulates one entry per search — a slow memory leak in a long-lived SPA ([[07.1 - How Garbage Collection Works]]).

```ts
useQuery({ queryKey: ["search", q], gcTime: 2 * 60_000 });   // short for high cardinality
```

`localStorage` has a hard ~5MB quota and throws when exceeded, so persisted caches need a size cap and an eviction policy. IndexedDB has far more room but needs explicit management ([[14.3 - IndexedDB]]).

## Privacy and correctness

Two rules that are easy to violate and expensive to get wrong:

**Clear the cache on logout.**

```ts
async function signOut() {
  await api.post("/auth/logout");
  queryClient.clear();
  await caches.delete("api-cache");
  window.location.href = "/login";
}
```

Without this, the next user on a shared device sees the previous user's data flash before it refetches ([[23.4 - Protected Routes and Auth Flows]]).

**Never persist sensitive data.** Tokens, personal information and payment details should not be written to `localStorage` or a Service Worker cache. Use `partialize` to select what is persisted rather than persisting everything by default.

## Debugging

```
DevTools → Network → Size column
  (memory cache)   in-process, cleared on tab close
  (disk cache)     HTTP cache hit
  (ServiceWorker)  served by the worker
  304              revalidated, body not re-sent
  a byte count     full download
```

Add the `Cache-Control` column to the Network panel to see the directive per response without opening headers.

The query library's DevTools shows every cache entry with its freshness state, which answers "why did this refetch" in seconds ([[24.6 - TanStack Query Fundamentals]]).

Note that a hard reload bypasses everything, so cache behavior must be tested with normal navigation.

## How senior engineers actually use this

**They decide the layer per data type**, rather than applying one policy everywhere.

**They set `staleTime` from how long stale data is acceptable**, not from a default.

**They invalidate rather than write** by default, and write only when the response is complete.

**They mark anything user-specific `private`**, and treat CDN cache keys as a security surface.

**They clear all caches on logout** and never persist sensitive data.

**They bound high-cardinality caches** with a short `gcTime`.

## Common pitfalls

- User-specific responses cached publicly at a CDN.
- Unhashed assets with long `max-age`, serving stale JavaScript.
- HTML cached, so deploys do not take effect.
- `no-cache` used where `no-store` was meant, writing sensitive data to disk.
- Cache not cleared on logout.
- Unbounded growth from search-keyed queries.
- Direct cache writes drifting from server-computed fields.
- No cross-tab invalidation.
- A Service Worker pinning users to an old build with no kill switch.

## Interview angle

"How would you design caching for this application" wants the layer stack and a per-data-type decision rather than one global policy. The specific points that land: the two-tier asset strategy (immutable hashed assets, uncached HTML) and why hashing enables it; stale-while-revalidate as the same idea appearing at three layers; event-based invalidation after mutations as more reliable than time-based; and `private` on anything user-specific because a shared cache storing personal data is a security incident, not a performance bug.
