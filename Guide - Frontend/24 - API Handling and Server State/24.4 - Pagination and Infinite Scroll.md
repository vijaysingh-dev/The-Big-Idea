# Pagination and Infinite Scroll

## Offset versus cursor

**Offset pagination** uses a page number or a row offset:

```
GET /products?page=2&limit=20
GET /products?offset=20&limit=20
```

Simple, supports jumping to an arbitrary page, and shows a total count. Two real problems:

**Drift.** If an item is inserted at the top between page 1 and page 2, the last item of page 1 shifts down and appears again on page 2. Deletions cause items to be skipped entirely. On a fast-moving feed this is constant.

**Cost at depth.** `OFFSET 100000` requires the database to scan and discard 100,000 rows. Deep pages get progressively slower.

**Cursor pagination** uses an opaque pointer to the last item seen:

```
GET /products?after=eyJpZCI6MTIzfQ&limit=20
```

```json
{
  "items": [...],
  "pageInfo": { "endCursor": "eyJpZCI6MTQzfQ", "hasNextPage": true }
}
```

The cursor encodes the sort key of the last row, so the next query is `WHERE (created_at, id) < (cursor)` — an index seek regardless of depth. No drift, constant performance.

The tradeoffs: no jumping to page 50, and usually no total count (counting is the expensive part).

```
Need page numbers or a total?      → offset
Feed, chat, activity, real-time?   → cursor
Large dataset, deep paging?        → cursor
Admin table with sort and jump?    → offset
```

Cursor is the better default for anything append-heavy. Offset remains right for tables users navigate deliberately.

## Paginated queries

```jsx
function ProductTable() {
  const [page, setPage] = useState(1);

  const { data, isPlaceholderData } = useQuery({
    queryKey: ["products", page],
    queryFn: () => api.getProducts({ page }),
    placeholderData: keepPreviousData,
  });

  return (
    <div style={{ opacity: isPlaceholderData ? 0.6 : 1 }}>
      <Table rows={data.items} />
      <button onClick={() => setPage(p => p - 1)} disabled={page === 1}>Prev</button>
      <button onClick={() => setPage(p => p + 1)} disabled={!data.hasMore}>Next</button>
    </div>
  );
}
```

`keepPreviousData` is what makes pagination feel smooth: the previous page stays on screen while the next loads, rather than the table collapsing to a skeleton and jumping the scroll position ([[24.2 - Loading Error and Empty States]]).

Prefetching the next page removes the wait almost entirely:

```jsx
useEffect(() => {
  if (data?.hasMore) {
    queryClient.prefetchQuery({
      queryKey: ["products", page + 1],
      queryFn: () => api.getProducts({ page: page + 1 }),
    });
  }
}, [page, data?.hasMore, queryClient]);
```

**Put the page in the URL**, not in state — refresh, back-button and shareable links all depend on it ([[23.3 - Dynamic Routes and Params]]):

```jsx
const [params, setParams] = useSearchParams();
const page = Number(params.get("page") ?? 1);
```

And reset to page 1 whenever a filter changes, or the user lands on page 7 of a 2-page result.

## Infinite queries

```jsx
const {
  data,
  fetchNextPage,
  hasNextPage,
  isFetchingNextPage,
} = useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam, signal }) => api.getFeed({ cursor: pageParam, signal }),
  initialPageParam: null,
  getNextPageParam: (lastPage) => lastPage.pageInfo.endCursor ?? undefined,
});

const items = data?.pages.flatMap(p => p.items) ?? [];
```

Returning `undefined` from `getNextPageParam` is how the library knows there are no more pages — returning `null` does not work.

`data.pages` is an array of page objects, flattened for rendering. Keeping the page structure matters for cache updates and for `maxPages` trimming.

## The load trigger

```jsx
const sentinelRef = useRef(null);

useEffect(() => {
  const el = sentinelRef.current;
  if (!el || !hasNextPage) return;

  const observer = new IntersectionObserver(
    ([entry]) => { if (entry.isIntersecting) fetchNextPage(); },
    { rootMargin: "400px" }
  );

  observer.observe(el);
  return () => observer.disconnect();
}, [hasNextPage, fetchNextPage]);

<div ref={sentinelRef} aria-hidden="true" />
```

`IntersectionObserver` is strictly better than a scroll handler — it runs off the main thread and needs no throttling ([[12.5 - Custom Events and Observer APIs]]).

`rootMargin: "400px"` triggers the fetch before the sentinel is visible, so the next page usually arrives before the user reaches the bottom.

Guard on `hasNextPage`, or the observer fires repeatedly at the end of the list.

## Always provide a manual trigger

```jsx
{hasNextPage && (
  <button onClick={() => fetchNextPage()} disabled={isFetchingNextPage}>
    {isFetchingNextPage ? "Loading..." : "Load more"}
  </button>
)}
```

A button, in addition to the observer, is not optional. Keyboard users cannot trigger a scroll sentinel meaningfully, and automatic loading is unpredictable for screen reader users. The observer handles the common case; the button makes it accessible ([[09.5 - Accessibility Fundamentals]]).

Announce new content:

```jsx
<div aria-live="polite" className="sr-only">
  {isFetchingNextPage ? "Loading more" : `${items.length} items loaded`}
</div>
```

## What infinite scroll costs

**No footer.** Anything below the list becomes unreachable. This is why e-commerce sites generally avoid pure infinite scroll — the footer holds navigation and legal links people actually need.

**No sense of position.** "Page 3 of 12" tells the user how much is left; an endless list does not.

**Unbounded memory.** Ten pages of 50 items is 500 DOM subtrees and growing. Pair with virtualization for long feeds ([[19.5 - Virtualization and Windowing]]), or trim:

```jsx
useInfiniteQuery({ maxPages: 5, ... });
```

**Broken back navigation.** Clicking an item and returning loses scroll position and all loaded pages unless the cache preserves them.

**Not linkable.** A user cannot share "the part of the feed I was looking at".

A "load more" button avoids most of these and is often the better choice. Reserve automatic infinite scroll for genuinely feed-shaped content.

## Scroll restoration

```jsx
useQuery({ gcTime: 10 * 60 * 1000 });   // keep pages cached across navigation
```

Returning to a feed should restore both the loaded pages and the scroll position. The cache handles the data; the router handles the scroll ([[23.2 - React Router Setup and Nested Routes]]).

Without this, tapping an item and pressing back drops the user at the top of a one-page feed — a frequent complaint in mobile web apps.

## Bidirectional and reverse lists

Chat and comment threads load **upward**:

```jsx
const { fetchPreviousPage, hasPreviousPage } = useInfiniteQuery({
  getPreviousPageParam: (firstPage) => firstPage.pageInfo.startCursor,
});
```

Prepending content shifts everything below it, so the scroll position must be preserved manually:

```jsx
const prevHeight = useRef(0);

useLayoutEffect(() => {
  const el = containerRef.current;
  if (prevHeight.current) {
    el.scrollTop = el.scrollHeight - prevHeight.current;
  }
  prevHeight.current = el.scrollHeight;
}, [items.length]);
```

`useLayoutEffect` is required — doing this after paint produces a visible jump ([[17.5 - useLayoutEffect vs useEffect]]).

CSS `overflow-anchor` handles some of this natively, and `flex-direction: column-reverse` is a common trick for chat, though it inverts keyboard scrolling.

## Duplicates and gaps

Even with cursors, items can appear twice if the sort key is not unique. Deduplicate on render:

```jsx
const items = useMemo(() => {
  const seen = new Set();
  return data.pages.flatMap(p => p.items).filter(i => {
    if (seen.has(i.id)) return false;
    seen.add(i.id);
    return true;
  });
}, [data]);
```

A `Set` makes this O(n) rather than O(n²) ([[06.5 - Map and Set]]). Duplicate React keys otherwise cause warnings and unpredictable reconciliation ([[16.6 - Lists and Keys]]).

## How senior engineers actually use this

**They default to cursor pagination** for feeds and offset for tables, and push back when an API offers only offset for a real-time list.

**They keep the page in the URL** and reset it on filter change.

**They use `keepPreviousData` and prefetch the next page**, which together make pagination feel instant.

**They always ship a "load more" button** alongside any scroll sentinel.

**They pair infinite scroll with virtualization and `maxPages`** for anything users scroll a long way through.

## Common pitfalls

- Offset pagination on a fast-moving feed, causing duplicates and skips.
- `getNextPageParam` returning `null` instead of `undefined`.
- No `hasNextPage` guard, so the observer fires in a loop.
- Infinite scroll with no keyboard-accessible trigger.
- A footer made unreachable by infinite scroll.
- Scroll position lost on back navigation.
- Unbounded page accumulation without virtualization or trimming.
- Duplicate keys from overlapping pages.

## Interview angle

"Offset versus cursor pagination" is the core question, and the answer is drift and depth cost: offset duplicates and skips items when the underlying data changes, and `OFFSET n` degrades linearly, while a cursor is an index seek with stable results. Then the UX layer — `keepPreviousData` for smooth transitions, `IntersectionObserver` with `rootMargin` for early loading, and a manual button for accessibility. Mentioning that infinite scroll makes the footer unreachable and breaks back-navigation shows product judgement, not just implementation knowledge.
