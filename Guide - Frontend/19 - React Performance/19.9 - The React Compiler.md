# The React Compiler

The React Compiler is a build-time tool that automatically memoizes components and values, removing most of the need for `useMemo`, `useCallback` and `React.memo`.

## The problem it solves

Manual memoization is a cascade ([[19.2 - React.memo and Memoization Strategy]]):

```jsx
const Child = React.memo(ChildComponent);

function Parent({ items, filter }) {
  const filtered = useMemo(() => items.filter(filter), [items, filter]);
  const handleSelect = useCallback((id) => select(id), []);
  const config = useMemo(() => ({ theme, locale }), [theme, locale]);

  return <Child items={filtered} onSelect={handleSelect} config={config} />;
}
```

Every link must be stable or the whole chain is wasted — silently, with no warning. Maintaining this across a codebase is genuinely hard, and half-applied memoization is worse than none: you pay the comparison cost and re-render anyway.

The compiler does it automatically and completely.

## What it produces

```jsx
// Source
function Parent({ items, filter }) {
  const filtered = items.filter(filter);
  const handleSelect = (id) => select(id);
  return <Child items={filtered} onSelect={handleSelect} />;
}
```

```jsx
// Roughly what the compiler emits
function Parent({ items, filter }) {
  const $ = useMemoCache(4);

  let filtered;
  if ($[0] !== items || $[1] !== filter) {
    filtered = items.filter(filter);
    $[0] = items; $[1] = filter; $[2] = filtered;
  } else {
    filtered = $[2];
  }

  // ... same pattern for handleSelect and the returned JSX
}
```

A per-component cache slot array, with granular checks around every value and every JSX expression. It memoizes at a finer granularity than a human would — including individual JSX subtrees, not just props.

## Setup

```bash
npm i -D babel-plugin-react-compiler
```

```js
// vite.config.js
export default {
  plugins: [
    react({
      babel: { plugins: [["babel-plugin-react-compiler", {}]] },
    }),
  ],
};
```

Next.js has a config flag. The compiler works with React 17+ through a runtime shim, and natively from React 19.

Also install the ESLint rule, which is the more immediately useful half:

```js
// eslint.config.js
"react-hooks/react-compiler": "error"
```

It flags code the compiler cannot safely optimize, which is a direct list of rules-of-React violations in your codebase.

## It only optimizes safe code

The compiler performs static analysis to prove a component follows the rules of React ([[16.5 - Rendering and Purity]]). Where it cannot prove safety, it **skips that component silently** and leaves it unoptimized.

Reasons it bails out:

- Mutation of props, state, or values received from outside
- Reading or writing refs during render
- Conditional hook calls ([[17.1 - Rules of Hooks and How They Work]])
- Side effects during render
- Dynamic patterns it cannot analyze

This is the significant shift: **purity now has a direct performance payoff**. Code that violates the rules of React does not just risk subtle bugs under concurrent rendering — it loses automatic optimization.

Check what was compiled with the React DevTools "Memo ✨" badge on optimized components, or the compiler's build output.

## What it does not do

**It does not reduce the number of components that render.** It makes each render cheaper by reusing computed values and skipping unchanged JSX subtrees. Structural fixes still matter more:

- Moving state down
- Passing elements as `children`
- Splitting contexts
- Virtualizing long lists

These reduce the work; the compiler optimizes the work that remains ([[19.1 - What Causes Re-renders]]).

**It does not fix expensive effects, network waterfalls, or bundle size.**

**It does not remove the need to understand memoization** — reading existing code, debugging why something re-renders, and reasoning about reference identity are all still required.

## Migration

Existing `useMemo`, `useCallback` and `React.memo` are left in place and continue to work. The compiler adds its own memoization around them.

Practical approach:

1. Enable the ESLint rule first and fix the violations. This is worthwhile regardless of whether you adopt the compiler.
2. Enable the compiler on a subset of directories.
3. Verify with the Profiler that behavior is unchanged and performance did not regress ([[19.8 - Profiling with React DevTools]]).
4. Remove manual memoization gradually, where it is clearly redundant.

Do not do a mass deletion of memo calls. Some exist for reasons beyond render performance — for example, keeping a reference stable for a third-party library — and the compiler's analysis is not identical to human intent.

There is an escape hatch:

```jsx
function Component() {
  "use no memo";     // opt this component out
}
```

Useful when a component genuinely depends on being re-created, or when debugging a suspected compiler issue.

## What it means for new code

On a compiled codebase, the default guidance inverts:

**Before:** memoize proactively at boundaries, maintain the cascade.
**After:** write straightforward code, follow the rules of React, and let the compiler handle memoization. Reach for manual memoization only when the Profiler shows a specific need the compiler did not cover.

This makes React code substantially simpler to write — no dependency arrays for pure computation, no `useCallback` on every handler, no memo wrapper on every list row.

## Status

The compiler reached a stable release and is used in production at Meta across large surfaces. Adoption in the wider ecosystem is ongoing, and it is enabled by default in some framework templates.

Given that it is newer than most training material, it is worth verifying current status and configuration in the official documentation rather than relying on any single source.

## How senior engineers actually use this

**They enable the ESLint rule immediately**, even without the compiler, because it surfaces real correctness problems.

**They treat compiler bailouts as a code-quality signal** — a component the compiler cannot optimize is a component that also has a latent concurrency risk.

**They still prioritize structural optimization.** Fewer components rendering beats cheaper renders.

**They do not delete manual memoization en masse** during migration.

**They verify with the Profiler** rather than assuming the compiler improved things.

## Common pitfalls

- Expecting the compiler to fix architectural performance problems.
- Assuming every component is optimized — bailouts are silent.
- Deleting all manual memoization at once during migration.
- Ignoring the ESLint rule's warnings, which are the compiler's bailout reasons.
- Believing purity is now optional because the compiler exists — it is the precondition.

## Interview angle

Mentioning the React Compiler unprompted in a performance discussion signals you follow the ecosystem. Explain what it does — automatic, fine-grained memoization inserted at build time — and, more importantly, the condition: it only optimizes code that provably follows the rules of React, so purity and correct hook usage now have a direct performance consequence. Adding that it makes renders cheaper but does not reduce how many components render, so composition still matters more, shows you understand its scope rather than treating it as a magic fix.
