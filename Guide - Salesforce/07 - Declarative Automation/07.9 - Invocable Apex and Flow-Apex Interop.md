# Invocable Apex and Flow-Apex Interop

## The extension point

`@InvocableMethod` exposes an Apex method to Flow Builder, Agentforce, and the REST API as a callable action. It is the seam between declarative and programmatic automation, and the place where most well-designed orgs put their shared business logic.

## The contract

```java
public with sharing class CoverageActions {

    public class Request {
        @InvocableVariable(required=true label='Asset Id' description='The machine to check')
        public Id assetId;

        @InvocableVariable(required=true label='Check Date')
        public Date checkDate;
    }

    public class Result {
        @InvocableVariable(label='Is Covered') public Boolean isCovered;
        @InvocableVariable(label='Coverage Level') public String coverageLevel;
        @InvocableVariable(label='Contract Id') public Id contractId;
    }

    @InvocableMethod(
        label='Check Asset Coverage'
        description='Returns active service contract coverage for an asset on a given date'
        category='Warranty'
    )
    public static List<Result> check(List<Request> requests) {
        Set<Id> assetIds = new Set<Id>();
        for (Request req : requests) {
            assetIds.add(req.assetId);
        }

        Map<Id, Machine_Coverage__c> coverageByAsset = new Map<Id, Machine_Coverage__c>();
        for (Machine_Coverage__c coverage : [
            SELECT Asset__c, Coverage_Level__c, Service_Contract__c,
                   Coverage_Start_Date__c, Coverage_End_Date__c
            FROM Machine_Coverage__c
            WHERE Asset__c IN :assetIds AND Service_Contract__r.Status__c = 'Active'
            ORDER BY Coverage_End_Date__c DESC
        ]) {
            if (!coverageByAsset.containsKey(coverage.Asset__c)) {
                coverageByAsset.put(coverage.Asset__c, coverage);
            }
        }

        List<Result> results = new List<Result>();
        for (Request req : requests) {
            Result result = new Result();
            Machine_Coverage__c coverage = coverageByAsset.get(req.assetId);
            result.isCovered = coverage != null
                && coverage.Coverage_Start_Date__c <= req.checkDate
                && coverage.Coverage_End_Date__c >= req.checkDate;
            if (result.isCovered) {
                result.coverageLevel = coverage.Coverage_Level__c;
                result.contractId = coverage.Service_Contract__c;
            }
            results.add(result);
        }
        return results;
    }
}
```

The rules, all of which are enforced and none of which are optional:

**One `@InvocableMethod` per class.** A second one is a compile error.

**Static, public or global.**

**Takes exactly one parameter, and it must be a `List`.**

**Returns a `List` or `void`.**

**The returned list must match the input list in length and order.** This is the rule that produces the worst bugs when broken — a mismatched list gives the flow another record's answer, silently.

## Why the list signature exists

Flow invokes the action **once with all the records** when called in a bulk context. A record-triggered flow on 200 records calls the action once with 200 requests, not 200 times with one.

That is the entire performance argument for invocable Apex over a subflow. A subflow runs per record and queries per record. The invocable method queries once for all of them.

Writing the method as if it receives one record — looping and querying inside the loop — throws away the advantage and reintroduces the limit problem the action was meant to solve.

## Supported types

`@InvocableVariable` supports primitives, `Id`, sObjects, and `List` of any of those. Custom Apex classes are supported as the request and result wrapper types.

Not supported: `Map`, `Set`, `Object`, and nested collections. Where a map is needed, pass parallel lists or serialize to JSON.

An sObject parameter is genuinely useful — a flow can pass `$Record` directly:

```java
public class Request {
    @InvocableVariable(required=true) public Warranty_Claim__c claim;
    @InvocableVariable public List<Machine_Coverage__c> coverageRecords;
}
```

Generic sObject typing is possible with `sObject` rather than a concrete type, which makes an action reusable across objects at the cost of losing compile-time field checking.

## Writing for the caller

The `label` and `description` on the method and on each variable are the interface. They appear in Flow Builder's action picker, and for Agentforce they are how the model decides when to use the action.

Vague descriptions produce administrators choosing the wrong action and agents calling the wrong tool. Write them as if for someone who will never read the code, because that is exactly the audience.

`category` groups related actions in the picker, which matters once an org has thirty of them.

## Errors

An exception thrown from an invocable method surfaces to the flow as a fault, taking the fault path if one exists. Without a fault path, the flow fails and the transaction rolls back.

Two approaches:

**Throw for genuine failures.** A callout failing, data being invalid in a way the flow cannot handle. The flow's fault path handles it. See [[07.8 - Flow Error Handling and Fault Paths]].

**Return a status in the result for expected outcomes.** "No coverage found" is not an error; it is an answer. Returning `isCovered = false` lets the flow branch on it rather than diverting to a fault path.

Confusing these produces flows full of fault paths handling normal business conditions.

```java
public class Result {
    @InvocableVariable public Boolean success;
    @InvocableVariable public String errorMessage;
    @InvocableVariable public Id createdRecordId;
}
```

For actions that write data, returning a success flag and a message lets the flow show the user something useful rather than a platform error string.

## Callouts from flow

An invocable method making an HTTP callout needs care about context.

From a **screen flow**, the callout runs synchronously and works normally.

From a **record-triggered flow**, the callout happens inside the save transaction, which is not allowed after DML. The method must be marked `@future(callout=true)` or enqueue a Queueable — and both are asynchronous, so the flow cannot use the response.

```java
@InvocableMethod(label='Notify ERP of Claim Approval')
public static void notifyErp(List<Id> claimIds) {
    // enqueued rather than called directly, so the callout leaves the save transaction
    System.enqueueJob(new ErpNotificationQueueable(new Set<Id>(claimIds)));
}
```

Returning `void` is correct here — there is nothing meaningful to return, because the work has not happened yet. See [[12.3 - Queueable Apex]] and [[13.14 - Apex Callouts]].

## Security

An invocable method is callable from any flow, and flows can be launched by users through quick actions and Experience Cloud pages. Treat it as a reachable endpoint.

- Declare a sharing keyword explicitly
- Use `WITH USER_MODE` on queries and `as user` on DML where the action runs in user context
- Validate that the requester is entitled to the records they passed, particularly for Agentforce actions where the input comes from a conversation

See [[03.13 - Enforcing Security in Apex and SOQL]].

## Testing

An invocable method is ordinary Apex and should be unit tested directly, with a bulk case.

```java
@IsTest
static void coverageCheckHandlesMixedAssetsInBulk() {
    List<Asset> assets = TestDataFactory.createAssetsWithCoverage(100);
    List<Asset> uncovered = TestDataFactory.createAssets(100);

    List<CoverageActions.Request> requests = new List<CoverageActions.Request>();
    for (Asset a : assets) {
        requests.add(buildRequest(a.Id, Date.today()));
    }
    for (Asset a : uncovered) {
        requests.add(buildRequest(a.Id, Date.today()));
    }

    Test.startTest();
    List<CoverageActions.Result> results = CoverageActions.check(requests);
    Test.stopTest();

    Assert.areEqual(200, results.size(), 'One result per request, in order');
    Assert.isTrue(results[0].isCovered, 'First 100 assets have coverage');
    Assert.isFalse(results[199].isCovered, 'Last 100 assets have none');
}
```

Asserting on result count and on specific indexes is what verifies the order contract, which is the thing most likely to be broken by a later change.

## When to reach for it

**Use invocable Apex when:** the logic needs to bulk-process, query efficiently, loop, call out, or be reused across flows and agents.

**Use a subflow when:** the logic is simple, declarative, and should be admin-maintainable.

**Use neither when:** the logic belongs entirely in a trigger and the flow is not the right home for it at all. An invocable action called from a record-triggered flow, doing what a trigger would do, is an indirection with no benefit.
