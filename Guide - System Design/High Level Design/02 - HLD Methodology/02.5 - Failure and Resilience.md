## The Failure-First Mindset

Senior engineers design from failure scenarios outward, not from happy paths inward.

The question is never "will this fail?" — it's "when this fails, what happens?"

Every component in a distributed system will eventually:
- Crash
- Be unreachable (network partition)
- Respond slowly (timeout)
- Return wrong results (Byzantine failure)
- Become overloaded

Design for all of these before they happen in production.

---

## Failure Classification

### Types of Failures

| Type | Description | Example |
|---|---|---|
| **Crash failure** | Node stops responding | Server OOM kill, process crash |
| **Omission failure** | Messages are dropped | Network packet loss |
| **Timing failure** | Response arrives too late | Slow DB query under load |
| **Byzantine failure** | Node sends wrong/inconsistent data | Corrupted data, buggy service |
| **Cascading failure** | One failure triggers others | Slow DB → thread pool exhaustion → all requests fail |

### Failure Scope

```
Process failure        → 1 instance affected
Machine failure        → 1 server affected
Rack/switch failure    → 10-100 servers affected
AZ failure             → datacenter affected
Region failure         → millions of users affected
```

Design redundancy at the scope that matches your availability SLA.

## Timeouts

**Every network call must have a timeout.** Without one, a slow downstream service will exhaust your thread pool.

```python
# Bad: no timeout
response = requests.get("http://payment-service/charge")

# Good: explicit timeout
response = requests.get("http://payment-service/charge", timeout=2.0)
```

**Timeout strategy:**
- Set timeouts based on your latency budget (if your SLA is 500ms total, don't set a 10s downstream timeout)
- Use connection timeout + read timeout separately
- Log every timeout as a warning — they signal upstream problems

## Retries

Retrying failed requests recovers from transient failures (brief network hiccup, momentary overload).

### Retry Conditions

**Retry these:**
- Connection refused (service temporarily down)
- Timeout (service slow but running)
- HTTP 503 Service Unavailable
- HTTP 429 Too Many Requests (after waiting)

**Never retry these:**
- HTTP 400 Bad Request (the request is wrong — retrying won't fix it)
- HTTP 401/403 (auth failure — retrying won't fix it)
- Non-idempotent operations without an idempotency key (e.g., POST /charge without a payment ID)

### Exponential Backoff with Jitter

Simple retries with fixed intervals cause "thundering herd" — all clients retry at the same time after a failure, re-overloading the recovering service.

```python
# Base formula
delay = min(cap, base * 2^attempt)

# Add jitter: randomize to spread retries
delay = random(0, min(cap, base * 2^attempt))
```

```
Attempt 1: wait 0.1–0.2s
Attempt 2: wait 0.2–0.4s
Attempt 3: wait 0.4–0.8s
Attempt 4: wait 0.8–1.6s
Attempt 5: wait cap (e.g., 30s)
```

## Circuit Breakers

A circuit breaker prevents a service from repeatedly calling a downstream service that's known to be failing.

### States

```
CLOSED (normal):
  → Calls pass through
  → Track failure rate

  If failure rate > threshold:
    → Trip to OPEN

OPEN (failing):
  → Reject calls immediately (fail fast)
  → No calls to downstream
  → Start timer

  Timer expires:
    → Move to HALF-OPEN

HALF-OPEN (testing):
  → Allow a small number of test calls
  → If they succeed: → CLOSED
  → If they fail:    → OPEN again
```

### Why Circuit Breakers Matter

Without a circuit breaker:
1. Payment service is down
2. Order service calls payment, waits for timeout (5s each)
3. Order service threads all blocked waiting
4. Order service becomes unresponsive
5. API gateway can't reach order service
6. Users see total failure even for operations that don't need payment

With a circuit breaker: when payment fails threshold, circuit opens → order service fails fast → can still serve orders (with "payment pending" status).

**Libraries:** Resilience4j (Java), Polly (.NET), Hystrix (deprecated), custom implementations.

## Graceful Degradation

When a component fails, serve a reduced-quality response rather than a hard failure.

| Component Failure | Degraded Response |
|---|---|
| Recommendation service down | Show popular items instead of personalized |
| Search service down | Return empty results with message |
| Image service down | Show placeholder image |
| Analytics service down | Skip logging — don't fail the main request |
| Payment service down | Queue the payment for retry later; show "processing" |

**Hard dependency vs soft dependency:**
- **Hard:** Request cannot succeed without this component → caller must fail
- **Soft:** Request can succeed in a degraded form → caller should degrade

Identify and mark these explicitly in your design. Most dependencies should be soft.

## Bulkheads

Prevent failures in one area from exhausting shared resources.

**Thread pool bulkheads:**
Give each downstream dependency its own thread pool.

```
Order Service
├── Thread pool for Payment Service calls (max 20 threads)
├── Thread pool for Inventory Service calls (max 20 threads)
└── Thread pool for Notification Service calls (max 10 threads)
```

If Payment Service is slow and exhausts its pool, Inventory and Notification calls are unaffected.

**Connection pool bulkheads:**
Separate database connection pools per use case.

```
Order writes: pool A (max 10 connections)
Analytics reads: pool B (max 5 connections)
```

Heavy analytics queries can't starve order processing connections.

## Idempotency in Failure Recovery

When a request fails partway through, retrying must not cause double-processing.

**Pattern: Idempotency key**
```
Client assigns unique ID per logical operation.
Server stores result by ID.
On retry: return stored result without re-executing.
```

Critical for: payment charging, email sending, order creation.

## Disaster Recovery

### Key Metrics

**RTO (Recovery Time Objective):** Maximum acceptable downtime after a failure.  
**RPO (Recovery Point Objective):** Maximum acceptable data loss (measured in time).

```
RTO = 1 hour means: we must be back online within 1 hour of a failure
RPO = 15 min means: we can lose at most 15 minutes of data
```

### DR Strategies

| Strategy | RTO | RPO | Cost |
|---|---|---|---|
| **Backup and restore** | Hours–days | Hours | Low |
| **Pilot light** | Minutes–hours | Minutes | Medium |
| **Warm standby** | Minutes | Seconds–minutes | High |
| **Multi-site active-active** | Seconds | Near-zero | Very high |

**Backup and restore:** Take periodic snapshots, restore from them if needed. Cheapest. Worst RTO/RPO.

**Pilot light:** Replicate data continuously to another region. Infrastructure is minimal (just the DB). Scale up on failure.

**Warm standby:** Full copy of the system running at reduced capacity in a second region. Traffic switches on failure.

**Multi-site active-active:** Both regions serve live traffic. Failure of one region has zero user impact.

### What to Put in Your HLD

State RTO/RPO targets, then match the DR strategy to them:
- "We target 99.9% availability (8.7h downtime/year). Backup and restore is sufficient."
- "We target 99.99% (52 min/year). We need warm standby at minimum."
- "We target 99.999% (5 min/year). We need multi-site active-active."

## The Failure Checklist (Use in Every Design)

```
For each component:
[ ] What happens when it crashes? (redundancy, auto-restart)
[ ] What happens when it's slow? (timeout, circuit breaker)
[ ] What happens when its downstream fails? (graceful degradation)
[ ] What happens during a deployment? (rolling deploy, no downtime)
[ ] What happens when the AZ goes down? (multi-AZ, failover)
[ ] What happens when the region goes down? (DR strategy)
[ ] Is every write durable? (fsync, synchronous replica, WAL)
[ ] Are retries idempotent? (idempotency keys)
[ ] Is there a dead-letter queue for failed async operations?
```
