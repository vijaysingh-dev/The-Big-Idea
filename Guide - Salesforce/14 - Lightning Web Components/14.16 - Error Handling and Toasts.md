# Error Handling and Toasts

## The error shapes

An error reaching a component can arrive in half a dozen structures depending on where it came from. This is the first practical problem.

```javascript
// Apex AuraHandledException
{ body: { message: 'This claim exceeds the coverage limit.' } }

// DML failure through LDS
{ body: { output: { errors: [{ message: '...' }],
                    fieldErrors: { Claim_Amount__c: [{ message: '...' }] } } } }

// A page-level error
{ body: { pageErrors: [{ message: '...' }] } }

// An array of errors
{ body: [{ message: '...' }, { message: '...' }] }

// A JavaScript error
{ message: 'Cannot read properties of undefined' }
```

A shared reducer belongs in a utility module rather than being rewritten per component:

```javascript
// c/errorUtils/errorUtils.js
export function reduceErrors(errors) {
    if (!Array.isArray(errors)) {
        errors = [errors];
    }

    return errors
        .filter((error) => !!error)
        .map((error) => {
            if (Array.isArray(error.body)) {
                return error.body.map((e) => e.message);
            }
            if (error.body?.output) {
                const output = error.body.output;
                const fieldMessages = Object.values(output.fieldErrors ?? {})
                    .flat()
                    .map((e) => e.message);
                const pageMessages = (output.errors ?? []).map((e) => e.message);
                return [...pageMessages, ...fieldMessages];
            }
            if (error.body?.pageErrors?.length) {
                return error.body.pageErrors.map((e) => e.message);
            }
            if (typeof error.body?.message === 'string') {
                return error.body.message;
            }
            if (typeof error.message === 'string') {
                return error.message;
            }
            return 'An unexpected error occurred.';
        })
        .flat()
        .filter((message) => !!message);
}
```

```javascript
import { reduceErrors } from 'c/errorUtils';

catch (error) {
    this.errorMessages = reduceErrors(error);
}
```

## Throwing usable errors from Apex

```java
@AuraEnabled
public static void approveClaim(Id claimId, Decimal amount) {
    try {
        ClaimApprovalService.approve(new Set<Id>{ claimId }, amount);
    } catch (ClaimValidationException e) {
        // AuraHandledException surfaces the message; anything else becomes a generic error
        throw new AuraHandledException(e.getMessage());
    } catch (Exception e) {
        AutomationLogger.logError('ClaimController.approveClaim', claimId, e.getMessage());
        throw new AuraHandledException('The claim could not be approved. Reference: ' + logId);
    }
}
```

**An uncaught Apex exception surfaces as "An internal server error has occurred"**, which tells the user nothing and tells the developer nothing either.

`AuraHandledException` is what carries a message across. Two rules for what goes in it:

**Write for the user.** Not the field API name, not the status code.

**Do not leak internals.** A message containing `FIELD_CUSTOM_VALIDATION_EXCEPTION: Claim_Amount__c` exposes the schema and confuses the reader.

Including a log reference — so support can find the full stack trace — turns an opaque failure into a traceable one. See [[09.10 - Exception Handling and Custom Exceptions]].

## Toasts

```javascript
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

showToast(title, message, variant) {
    this.dispatchEvent(new ShowToastEvent({
        title,
        message,
        variant,                    // success, error, warning, info
        mode: 'dismissable'         // dismissable, pester, sticky
    }));
}
```

**Modes matter.** `dismissable` auto-dismisses after a few seconds. `sticky` stays until closed — right for errors the user must read. `pester` stays for a set period regardless.

**Errors should be sticky.** A three-second toast announcing that a save failed is a toast the user misses.

Message data allows placeholders and links:

```javascript
this.dispatchEvent(new ShowToastEvent({
    title: 'Claim approved',
    message: 'Claim {0} has been approved. {1}',
    messageData: [
        this.claimNumber,
        { url: `/lightning/r/Warranty_Claim__c/${this.claimId}/view`, label: 'View claim' }
    ],
    variant: 'success'
}));
```

## Where toasts do not work

The limitation that catches people.

**Toasts are unavailable in Experience Cloud** in several configurations, and **in flow screens**. The event dispatches and nothing appears.

A component intended for both internal and external use needs a fallback:

```javascript
showMessage(title, message, variant) {
    // toasts are unreliable outside internal Lightning pages, so fall back to inline
    if (this.supportsToasts) {
        this.dispatchEvent(new ShowToastEvent({ title, message, variant, mode: 'sticky' }));
        return;
    }
    this.inlineMessage = { title, message, variant };
}

get supportsToasts() {
    return !this.isExperienceCloud && !this.isFlowScreen;
}
```

Detecting the context is awkward, and the simpler answer is often **inline messages everywhere** — they work in every context and keep the error next to the thing that failed.

## Inline errors

Usually better than a toast, for the same reason a validation rule's field-level error beats a page-level one: the message appears where the problem is.

```html
<template lwc:if={hasError}>
    <div class="slds-notify slds-notify_alert slds-theme_error slds-m-bottom_small"
         role="alert">
        <span class="slds-assistive-text">Error</span>
        <lightning-icon icon-name="utility:error" variant="inverse" size="x-small"
                        class="slds-m-right_x-small">
        </lightning-icon>
        <template for:each={errorMessages} for:item="message">
            <p key={message}>{message}</p>
        </template>
    </div>
</template>
```

`role="alert"` and the assistive text matter — a visual error with no announcement is invisible to a screen reader user.

For forms, `<lightning-messages>` inside a record edit form renders errors in the standard place with no code:

```html
<lightning-record-edit-form record-id={recordId} object-api-name="Warranty_Claim__c">
    <lightning-messages></lightning-messages>
    <lightning-input-field field-name="Claim_Amount__c"></lightning-input-field>
</lightning-record-edit-form>
```

Omitting it means validation errors are returned to `onerror` and nothing appears — a form that silently refuses to save. See [[14.12 - Lightning Data Service and Record Forms]].

## Field-level errors

```javascript
showFieldError(fieldName, message) {
    const input = this.template.querySelector(`[data-field="${fieldName}"]`);
    input?.setCustomValidity(message);
    input?.reportValidity();
}

clearFieldError(fieldName) {
    const input = this.template.querySelector(`[data-field="${fieldName}"]`);
    // clearing requires setting an empty string and re-reporting
    input?.setCustomValidity('');
    input?.reportValidity();
}
```

`setCustomValidity` without `reportValidity` sets the state and displays nothing. Both are needed.

Validating a whole form:

```javascript
validateForm() {
    return [...this.template.querySelectorAll('lightning-input, lightning-combobox')]
        .reduce((validSoFar, input) => {
            input.reportValidity();
            return validSoFar && input.checkValidity();
        }, true);
}
```

The `reduce` rather than `every` is deliberate — `every` short-circuits on the first failure, so later fields never get their message displayed.

## errorCallback

The component-level error boundary, catching errors thrown by **descendants**.

```javascript
errorCallback(error, stack) {
    this.hasFatalError = true;
    this.fatalMessage = error.message;

    LoggingService.report({
        component: 'claimDashboard',
        message: error.message,
        stack
    });
}
```

```html
<template lwc:if={hasFatalError}>
    <div class="slds-notify slds-notify_alert slds-theme_error">
        <p>This section could not be displayed. The team has been notified.</p>
    </div>
</template>
<template lwc:else>
    <c-claim-list claims={claims}></c-claim-list>
</template>
```

**It does not catch the component's own errors** — only those from children.

Its value is containment: a dashboard with six child components, where one throwing blanks the whole page, is worse than one showing five components and an error panel. Wrapping each region in a boundary is cheap and underused. See [[14.5 - Component Lifecycle Hooks]].

## Logging client errors

Client-side errors are invisible unless reported.

```javascript
import logClientError from '@salesforce/apex/ClientLogController.log';

async reportError(context, error, stack) {
    try {
        await logClientError({
            component: context,
            message: error?.message ?? String(error),
            stack: stack ?? error?.stack,
            pageUrl: window.location.href
        });
    } catch (loggingError) {
        // logging must never throw — a failed log is not worth breaking the page
        console.error('Failed to log client error', loggingError);
    }
}
```

The nested try/catch matters. A logging call that throws, inside an error handler, produces a second error and often an infinite loop.

On the Apex side, writing through a platform event keeps the log durable even if the surrounding transaction rolls back. See [[20.5 - Custom Logging Frameworks]].

## The loading and error states

Every component fetching data has three states, and skipping one produces a visible defect.

```javascript
get isLoading() {
    return !this.claimResult?.data && !this.claimResult?.error;
}

get hasError() {
    return !!this.claimResult?.error;
}

get hasData() {
    return this.claimResult?.data?.length > 0;
}

get isEmpty() {
    return this.claimResult?.data?.length === 0;
}
```

```html
<template lwc:if={isLoading}>
    <lightning-spinner alternative-text="Loading claims"></lightning-spinner>
</template>
<template lwc:elseif={hasError}>
    <c-error-panel errors={claimResult.error}></c-error-panel>
</template>
<template lwc:elseif={isEmpty}>
    <p class="slds-p-around_medium slds-text-color_weak">No claims found.</p>
</template>
<template lwc:else>
    <c-claim-list claims={claims}></c-claim-list>
</template>
```

**Empty is distinct from loading.** A component showing "No claims found" for a second while data loads is a small but persistent annoyance, and the four-state pattern above avoids it.

## The finally block

```javascript
async handleApprove() {
    this.isProcessing = true;
    this.error = undefined;

    try {
        await approveClaim({ claimId: this.recordId });
        await refreshApex(this.claimResult);
        this.showToast('Approved', 'The claim has been approved.', 'success');
    } catch (error) {
        this.error = reduceErrors(error);
    } finally {
        // clearing the spinner here means a failure does not leave the UI hung
        this.isProcessing = false;
    }
}
```

A spinner cleared only on the success path leaves a failed action looking like a hang, which is one of the most common small defects in Lightning components.

## Practical guidance

**Share one error reducer** across the org.

**Throw `AuraHandledException`** with a message written for the user, and a log reference.

**Make error toasts sticky.**

**Prefer inline errors to toasts**, particularly in Experience Cloud and flow screens where toasts may not appear.

**Include `<lightning-messages>`** in every record edit form.

**Use `reduce`, not `every`**, when validating a form, so all messages display.

**Add `errorCallback`** to container components.

**Log client errors to Apex**, with a nested try/catch so logging never throws.

**Handle four states**: loading, error, empty, and data.

**Clear spinners in `finally`.**
