# Big Objects

## What they are

A big object stores hundreds of millions or billions of records inside Salesforce, on a different storage layer from standard and custom objects.

The tradeoff is stated plainly by the design: you get enormous scale, and you give up nearly every convenience the platform normally provides. No triggers, no roll-ups, no standard reports, no user interface to speak of, no flexible querying.

They exist for one shape of problem: **write a lot, read rarely, and only by a known key.**

## When they are the right answer

- **Audit and history archives.** Field history older than the standard retention window, moved out of the history object.
- **Event and telemetry data.** Machine sensor readings, login events, application logs.
- **Transaction history.** Years of orders or payments kept for compliance but rarely queried.
- **Archived operational records.** Closed cases from six years ago that must be retrievable but do not belong in day-to-day reporting.

The common thread: high volume, written once, read occasionally, and always looked up by a specific identifier rather than searched freely.

## The index is the design

This is the part that determines whether a big object works or is useless.

When you create a big object, you define an **index** consisting of up to five fields, in a specific order. That index is permanent — it cannot be changed after creation, and there is no adding a second one later.

Every query must filter on those fields, **in order, from the left**, with no gaps.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<CustomObject xmlns="http://soap.sforce.com/2006/04/metadata">
    <label>Machine Reading</label>
    <pluralLabel>Machine Readings</pluralLabel>
    <deploymentStatus>Deployed</deploymentStatus>
    <fields>
        <fullName>Machine_Id__c</fullName>
        <label>Machine Id</label>
        <type>Text</type>
        <length>18</length>
        <required>true</required>
    </fields>
    <fields>
        <fullName>Reading_Timestamp__c</fullName>
        <label>Reading Timestamp</label>
        <type>DateTime</type>
        <required>true</required>
    </fields>
    <fields>
        <fullName>Temperature__c</fullName>
        <label>Temperature</label>
        <type>Number</type>
        <precision>8</precision>
        <scale>2</scale>
    </fields>
    <indexes>
        <fullName>MachineReadingIndex</fullName>
        <label>Machine Reading Index</label>
        <fields>
            <name>Machine_Id__c</name>
            <sortDirection>ASC</sortDirection>
        </fields>
        <fields>
            <name>Reading_Timestamp__c</name>
            <sortDirection>DESC</sortDirection>
        </fields>
    </indexes>
</CustomObject>
```

With that index, these work:

```sql
-- filters on the first index field
SELECT Machine_Id__c, Reading_Timestamp__c, Temperature__c
FROM Machine_Reading__b
WHERE Machine_Id__c = 'a0X5g000001AbCdEAK'

-- filters on first, then second, in order
SELECT Machine_Id__c, Temperature__c
FROM Machine_Reading__b
WHERE Machine_Id__c = 'a0X5g000001AbCdEAK'
  AND Reading_Timestamp__c > 2026-01-01T00:00:00Z
```

This does not:

```sql
-- skips the first index field
SELECT Machine_Id__c FROM Machine_Reading__b
WHERE Reading_Timestamp__c > 2026-01-01T00:00:00Z
```

Because the index cannot be changed later, getting the field order right is the single most important decision. The rule: put the field you will *always* filter on first, and order the rest by how frequently they appear in your access patterns.

Index fields are also required and cannot be null, and their combination acts as the record's identity — writing a record with the same index values overwrites the existing one rather than creating a duplicate.

## Writing to them

Writes are asynchronous and use `Database.insertImmediate()` rather than normal DML.

```java
public with sharing class ReadingArchiveService {

    public static void archive(List<Machine_Reading_Staging__c> staged) {
        List<Machine_Reading__b> readings = new List<Machine_Reading__b>();

        for (Machine_Reading_Staging__c s : staged) {
            readings.add(new Machine_Reading__b(
                Machine_Id__c = s.Machine__c,
                Reading_Timestamp__c = s.Recorded_At__c,
                Temperature__c = s.Temperature__c
            ));
        }

        // big object writes bypass the normal DML pipeline and do not count against DML limits
        Database.SaveResult[] results = Database.insertImmediate(readings);

        for (Database.SaveResult r : results) {
            if (!r.isSuccess()) {
                System.debug('Archive write failed: ' + r.getErrors()[0].getMessage());
            }
        }
    }
}
```

Writes do not participate in the normal transaction. They are not rolled back if the surrounding transaction fails, and they do not fire triggers because big objects do not have any. There is also no update operation in the usual sense — writing the same index values replaces the record.

For large volumes, the Bulk API is the correct path rather than Apex.

## Reading them

Two mechanisms, and the difference is significant.

**Standard SOQL** works if your filter matches the index prefix and you only need a modest number of rows. Results come back synchronously, and the row limit is much lower than for normal objects.

**Async SOQL** is for anything larger. You submit a query, Salesforce processes it in the background, and the results are written into a *different* object — a standard or custom object you specify. You then read that object normally.

This is the mental adjustment: for large reads, a big object query does not return data to your code. It populates another table, and your code reads that.

```
POST /services/data/v62.0/async-queries/
{
  "query": "SELECT Machine_Id__c, Temperature__c FROM Machine_Reading__b WHERE Machine_Id__c = 'a0X...'",
  "operation": "insert",
  "targetObject": "Reading_Summary__c",
  "targetFieldMap": {
    "Machine_Id__c": "Machine__c",
    "Temperature__c": "Temperature__c"
  }
}
```

Async SOQL is what makes analytical use of big objects possible at all, and it is also why big objects are unsuitable for anything interactive.

## What you give up

Worth stating as a list, because the absence is the defining feature:

- No triggers, no flows on the object
- No roll-up summaries, in or out
- No standard reports or dashboards; reporting requires Async SOQL into a reportable object first
- No page layouts or record pages worth using; the record detail experience is minimal
- No validation rules
- No field history
- No search
- No `LIMIT` beyond a low ceiling on synchronous queries, and no `ORDER BY` outside the index order
- No `COUNT()` or aggregate functions in synchronous SOQL
- No standard sharing; access is controlled by object permissions only, which is a genuine security consideration for sensitive archives

## Where they fit in an archiving strategy

The realistic pattern:

1. Operational data lives in a normal custom object where it can be reported on, automated, and edited.
2. A scheduled Batch Apex job moves records older than a retention threshold into a big object.
3. The originals are deleted, freeing storage and keeping the operational object fast.
4. A Lightning Web Component on the parent record queries the big object by index key, so users can still see historical detail on demand.
5. Periodic analytical needs use Async SOQL into a reporting object.

Step 4 is what makes this acceptable to users. Without a way to see the archived data in context, an archive feels like data loss. See [[23.4 - Archiving with Big Objects and External Storage]].

## Big objects, external objects, or a warehouse

Three answers to overlapping questions, and choosing between them is a real architecture decision:

**Big object** — you own the data, it must stay in Salesforce for compliance or access reasons, volume is very high, access is by known key.

**External object** — the data lives elsewhere and should stay there, and you need to display it in context. See [[02.14 - External Objects and Salesforce Connect]].

**Data warehouse or Data Cloud** — the data needs genuine analytical querying, joins across sources, or machine learning. Big objects are not an analytics platform, and trying to use one as one is a common and frustrating mistake. See [[24.2 - Data Cloud Fundamentals]].

## Section 02 in one paragraph

Objects are tables, but the choice between standard, custom, external, and big determines where data lives and what the platform will do for you. Field types decide what can be filtered, indexed, and integrated. Relationship type decides ownership, sharing, deletion, and roll-ups, and is the highest-consequence modelling decision you make. Formulas are free and always current but not filterable at scale; roll-ups are stored and filterable but require master-detail and cost you locking. Record types let one object serve several processes, and are routinely overused. Everything in section 03 sits on top of these choices, because who can see a record is determined largely by how you modelled it here.
