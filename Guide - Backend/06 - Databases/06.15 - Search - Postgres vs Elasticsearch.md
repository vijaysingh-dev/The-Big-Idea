# Search: Postgres vs Elasticsearch

#backend #databases #search

> **In one line:** Both build an inverted index from words to documents; the difference is that Elasticsearch is built entirely around relevance ranking and Postgres treats search as one feature among many.

---

## The Idea

An inverted index maps terms to the documents containing them. **Both do exactly this.** The differences are in how text becomes terms, how results are scored, and what you can do with them.

💡 **Postgres full-text search is genuinely good and it is free. Elasticsearch is better at relevance, at scale, and at the features around search — and it is a second datastore with all the costs from [[06.14 - Beyond Postgres]].**

**Start with Postgres. Move when you can name the specific thing it cannot do.**

---

## Postgres Full-Text Search

```sql
SELECT to_tsvector('english', 'The quarterly reports were running late');
-- 'late':7 'quarter':2 'report':3 'run':5
```

Parse into tokens, drop stop words, stem to root forms, record positions. **The query goes through the same pipeline, so `quarterly` matches `quarter`.**

### Making it fast

```sql
ALTER TABLE documents
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(content, '')), 'B')
) STORED;

CREATE INDEX ON documents USING gin (search_vector);
```

💡 **Generated columns (Postgres 12+) mean the vector updates automatically** — no trigger to write, no chance of it going stale. **This replaces a lot of older trigger-based advice.**

**`setweight` gives you four tiers (A–D)**, so a match in the title outranks one in the body.

### Query parsers

| Function | Behaviour |
|---|---|
| `to_tsquery` | Strict syntax. **Errors on user input** |
| `plainto_tsquery` | All terms ANDed |
| `phraseto_tsquery` | Adjacent terms only |
| **`websearch_to_tsquery`** | **Google-like. Use this for user input** |

⚠️ **Never pass user input to `to_tsquery`** — a stray `&` or unbalanced quote raises a syntax error. **`websearch_to_tsquery` handles quotes, `OR` and `-` exclusion, and never errors.**

### Ranking

⚠️ **`ts_rank` does not implement BM25.** It has no inverse document frequency, so a match on a very common word counts as much as a match on a rare one. **This is the biggest relevance gap versus Elasticsearch**, and it is why Postgres results often feel "less right" even when they contain the correct documents.

```sql
ORDER BY
    ts_rank_cd(search_vector, query) * 0.6
  + (1.0 / (1 + extract(epoch from now() - created_at) / 86400)) * 0.3
  + (view_count::float / (view_count + 100)) * 0.1
DESC
```

💡 **Blending text relevance with business signals — recency, popularity, the user's own documents — often matters more than the text scoring itself.** A mediocre text score with good business signals frequently beats BM25 alone.

### Fuzzy matching

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX ON documents USING gin (title gin_trgm_ops);

SELECT title, similarity(title, $1) FROM documents WHERE title % $1;
WHERE title ILIKE '%quarterl%'        -- now indexable
```

💡 **`pg_trgm` is the most useful search extension after FTS itself.** Typo tolerance, autocomplete, and — importantly — **it makes unanchored `LIKE` patterns use an index, which is otherwise impossible** ([[06.3 - Indexes Deep Dive]]).

### Where Postgres FTS falls short

| Limitation | |
|---|---|
| **No BM25** | Relevance is measurably worse |
| **Ranking requires fetching rows** | Cannot rank in the index |
| No built-in fuzzy in FTS | `pg_trgm` is separate and does not combine cleanly |
| Limited language analysis | Basic stemming; no proper CJK segmentation |
| No aggregations on results | Faceted counts need separate queries |

⚠️ **The "ranking requires fetching rows" limitation is the one that bites at scale.** A query matching 500,000 documents must read all 500,000 to rank them, even to return 20. **Elasticsearch ranks within the index and only fetches the winners.**

**This is why Postgres FTS degrades on broad queries specifically** — narrow queries stay fast.

## Elasticsearch

```json
GET /documents/_search
{
  "query": {"multi_match": {"query": "quarterly report",
                            "fields": ["title^3", "content"], "fuzziness": "AUTO"}},
  "aggs": {"by_source": {"terms": {"field": "source_id"}}},
  "highlight": {"fields": {"content": {}}}
}
```

| Capability | Why it matters |
|---|---|
| **BM25 by default** | Rare terms weighted higher. Substantially better relevance |
| **Ranks in the index** | Only fetches the top N documents |
| Aggregations | Faceted counts in the same request |
| Highlighting | Snippets showing matched terms in context |
| Rich analysis | Synonyms, language-specific analysers, custom pipelines |
| Horizontal scaling | Sharded and replicated by design |

### BM25, briefly

| Component | Effect |
|---|---|
| **IDF** | A term in 1% of documents scores far higher than one in 60% |
| **Term frequency saturation** | The 10th occurrence adds much less than the 2nd |
| **Length normalisation** | A match in a short document counts more |

💡 **IDF is the piece Postgres lacks entirely**, and it is the largest single contributor to the relevance gap.

### Analysis: where results actually come from

⚠️ **Analysis is applied at index time, so changing it requires reindexing everything.** With aliases, that is not disruptive:

```json
POST /_aliases
{"actions": [{"remove": {"index": "documents_v1", "alias": "documents"}},
             {"add": {"index": "documents_v2", "alias": "documents"}}]}
```

💡 **Always query through an alias, never a concrete index name.** It makes reindexing a zero-downtime alias swap, **and retrofitting it later means changing every query in your application.**

## The Sync Problem

⚠️ **Dual writes are broken:**

```python
await postgres.insert(doc)
await es.index(doc)          # fails → the index is missing a document, permanently
```

**Correct approaches:** outbox ([[09.3 - The Outbox Pattern]]), CDC ([[09.4 - Change Data Capture]]), or periodic reconciliation.

💡 **Run reconciliation regardless of which sync method you choose.** Every mechanism drifts eventually — a bug, an outage, a manual database edit — **and a nightly job comparing per-organisation counts and checksums catches it before users do.**

**Elasticsearch must be rebuildable from Postgres. Test the rebuild.**

### Handling the index being down

```python
try:
    return await es_search(q, org_id)
except (ConnectionError, TimeoutError):
    search_fallback_total.inc()
    return await postgres_search(q, org_id)      # degraded, but working
```

💡 **Keeping the Postgres FTS index alongside Elasticsearch gives you a fallback path** ([[11.6 - Graceful Degradation]]). **Relevance is worse and the service stays up.**

## In Production

### The decision

```
Is search a core product feature, or a convenience?
├── Convenience (find a document by title)
│   └── Postgres FTS. Done
│
└── Core feature
    ├── < 1M documents, simple relevance needs
    │   └── Postgres FTS + pg_trgm. Measure before moving
    └── Any of:
        - relevance quality is a competitive concern
        - faceted navigation, aggregations on results
        - highlighting, synonyms, per-language analysis
        - > 10M documents with broad queries
        └── Elasticsearch / OpenSearch
```

⚠️ **The honest threshold is lower than people claim in either direction.** Postgres FTS handles millions of documents fine for narrow queries. **It struggles specifically on broad queries and on relevance quality — and those are the two things a search-centric product cares about most.**

### Measuring relevance, not just latency

💡 **Search quality is measurable and almost nobody measures it.**

```python
GOLDEN = [("quarterly report", ["doc_42", "doc_17", "doc_3"]), ...]

def precision_at_k(results, expected, k=10):
    return len(set(results[:k]) & set(expected)) / min(k, len(results))
```

**Track precision@10, MRR and NDCG against a golden set in CI.** A ranking change that improves latency and destroys relevance is a regression, **and without these metrics you will ship it.**

⚠️ This is exactly the discipline the AI vault applies to RAG evaluation. **Search quality evaluation transfers directly to retrieval quality evaluation** — building the habit here pays off in phase 9.

### Permission-aware search

```sql
-- Postgres: a WHERE clause against real columns
SELECT * FROM documents
WHERE org_id = $1
  AND (is_public OR id IN (SELECT document_id FROM acl WHERE user_id = $2))
  AND search_vector @@ websearch_to_tsquery($3)
ORDER BY ts_rank_cd(...) DESC LIMIT 20;
```

⚠️ **Elasticsearch has no joins, so permissions must be denormalised into each document** — and re-indexed whenever they change. **A permission change on a folder containing 10,000 documents means re-indexing 10,000 documents.**

💡 **This is a genuinely strong argument for Postgres in a permission-heavy product**, and it is the same reasoning as the pgvector choice in [[06.14 - Beyond Postgres]].

**The alternative — post-filtering by permission — breaks pagination:** you asked for 20, got 20, and after filtering have 3.

### Operating Elasticsearch

| Concern | |
|---|---|
| **Memory** | JVM heap ≤ 32GB (compressed pointers), leave half of RAM for the OS cache |
| **Shard sizing** | 10–50GB per shard. Too many small shards is a common mistake |
| Refresh interval | Default 1s. Raise it for bulk indexing |
| Bulk indexing | Always. Individual document indexing is very slow |
| **Mapping explosion** | Dynamic mapping on user data can create thousands of fields |

⚠️ **Dynamic mapping plus user-controlled JSON is a real outage.** Each new field key becomes a mapping entry, cluster state grows, and the cluster degrades. **Set `"dynamic": "strict"` on anything derived from user input.**

## Codebase

**Repo:** `postgres/postgres`, `apache/lucene`, `elastic/elasticsearch`

**Question to answer:** How does Postgres store a `tsvector` in a GIN index, and why does ranking require fetching the heap row? Then: in Lucene, where is BM25 scored, and how does it avoid fetching documents that will not make the top N?

**Read, in order:**

1. `postgres/src/backend/utils/adt/tsvector.c` and `tsrank.c` — **`calc_rank_cd` is `ts_rank_cd`.** Note that it operates on the `tsvector` value, **which must be read from the heap**
2. `postgres/src/backend/access/gin/README` — how GIN stores multiple keys per row, and the pending list
3. `postgres/src/backend/tsearch/` — the parser, dictionaries and stemming pipeline
4. `lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java` — **BM25 in about 200 readable lines.** IDF, saturation and length normalisation are right there
5. `lucene/core/src/java/org/apache/lucene/search/TopScoreDocCollector.java` — **Lucene tracks the minimum competitive score and skips documents that cannot beat it** (block-max WAND)
6. `elasticsearch/server/src/main/java/org/elasticsearch/index/query/` — how the query DSL becomes Lucene queries

💡 The `TopScoreDocCollector` reading explains the architectural gap precisely: **Lucene can skip documents because it scores from the index; Postgres must materialise every matching row to rank it.** That is not a tuning difference, it is a design difference, **and it is why Postgres FTS degrades on broad queries.**

**Size:** 2 sessions.

## Exercise

**Drill 6.15 — Measure relevance, not just speed**

```
drills/06-search/
├── corpus/{generate.py, golden.json}
├── postgres/{schema.sql, search.py, trigram.sql, ranking.py}
├── elasticsearch/{mapping.json, analysis.json, search.py, reindex.sh}
├── evaluation/{metrics.py, compare.py, RESULTS.md}
├── scale/{broad_queries.py, latency.py, PLOT.md}
├── sync/{outbox.py, reconcile.py, FINDINGS.md}
├── permissions/{postgres_acl.sql, es_denormalised.py, COMPARISON.md}
└── README.md
```

**Part 1 — A corpus and a golden set.** 5 million documents with realistic text — varied lengths, a Zipfian word distribution, titles that sometimes match content.

Then **50 judged queries**: for each, list the documents that should be in the top 10, ranked.

⚠️ **Building the golden set is the hard part and it is the point of the drill.** Without it you can only compare speed, which is the less important axis.

**Part 2 — Postgres search, done well.** Weighted `tsvector`, GIN index, `websearch_to_tsquery`, `ts_rank_cd`, plus `pg_trgm`. Then blended ranking, tuned against your golden set.

**Part 3 — Elasticsearch, done well.** Proper mapping, custom analyser with synonyms, field boosting, fuzziness, highlighting.

**Part 4 — Compare on relevance.** Run all 50 golden queries against both. **Compute precision@10, MRR and NDCG@10 for each.**

Then find the queries where they differ most and work out why. **The IDF cases should stand out** — queries containing one rare and one common term.

Then try to close the gap in Postgres by manually weighting rare terms, and report how far you get.

**Part 5 — The broad query cliff.** Queries matching 10, 1,000, 100,000 and 1,000,000 documents.

**Chart p50 and p99 latency against match count for both systems.**

**Postgres should degrade sharply; Elasticsearch should stay roughly flat.** Then confirm the cause with `EXPLAIN ANALYZE` — heap fetches dominating.

**Part 6 — Sync and repair.** Outbox-based indexing. Inject failures: Elasticsearch down, a partial bulk failure, a crash between commit and relay.

**Count divergences.** Then write a reconciliation job comparing per-organisation counts and content hashes, and confirm it repairs every case.

Then do a full rebuild from Postgres and verify the result matches.

**Part 7 — Permission-aware search, both ways.**

Postgres: a `WHERE` clause joining the ACL table. Elasticsearch: denormalised `allowed_users`.

**Change a permission affecting 10,000 documents and measure how long each takes to reflect it.**

Then measure search latency for a user with access to 1% of documents in both, and **check whether pagination returns full pages.**

**Write your recommendation for Conduit with the numbers.**

**Done when:**
- Your golden set has 50 judged queries
- The relevance table has precision@10, MRR and NDCG for both systems
- You can name the query types where the IDF gap matters most
- Your latency-versus-match-count chart shows the Postgres cliff
- Outbox sync survives three failure types with reconciliation catching drift
- You have measured permission-change propagation time in both systems
- Your Conduit recommendation cites your own relevance and latency numbers
