# Reading Real Traffic

#backend #networking #debugging #tools

> **In one line:** When logs disagree with reality, packet capture is the only source of truth left — and knowing four commands turns a day of guessing into ten minutes of looking.

---

## The Idea

Your logs say the request was sent. Their logs say it never arrived. Somebody is wrong, and neither of you can prove it.

Packet capture ends that argument. It shows what actually crossed the wire, with timestamps, in order, from whichever side you can get access to.

💡 **This is a skill with a strange payoff curve.** You will use it maybe five times a year. Each of those five times it will save hours and settle a question nothing else could. It is worth a weekend to learn once.

---

## The Four Tools

| Tool | Use |
|---|---|
| **`ss`** | Current socket state. First thing to run, always |
| **`tcpdump`** | Capture packets on a server, no GUI needed |
| **Wireshark** | Read those captures properly, with protocol decoding |
| **`mitmproxy`** | Read HTTPS content — the one thing tcpdump cannot do |

## `ss` — Start Here

Always the first command. It answers "what does this machine think its connections are doing?" in one line.

```bash
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
```

```
   1247 ESTAB
    843 TIME-WAIT
     12 CLOSE-WAIT
      3 SYN-SENT
      1 LISTEN
```

That distribution names the problem class immediately — see the table in [[02.3 - TCP Connection Lifecycle]].

```bash
ss -tlnp                          # what's listening, and which process
ss -tan state established dst 10.0.0.5    # connections to one peer
ss -ti                            # per-connection: rtt, cwnd, retransmits
ss -tm                            # memory used per socket
ss -tan sport = :8000             # the accept queue on your listener
```

`ss -ti` is the underrated one. It gives you `rtt`, `cwnd` and `retrans` per connection, which is how you distinguish "the network is bad" from "the server is slow" ([[02.4 - Flow Control and Congestion Control]]).

## `tcpdump`

### The commands worth memorising

```bash
# Everything to or from one host, don't resolve names, show payload
sudo tcpdump -i any -nn -A host 10.0.0.5

# Write to a file for Wireshark. -s 0 = full packets, not truncated
sudo tcpdump -i any -w capture.pcap -s 0 'host 10.0.0.5 and port 443'

# Only SYNs — who is trying to connect?
sudo tcpdump -i any 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'

# Only RSTs — who is killing connections?
sudo tcpdump -i any -nn 'tcp[tcpflags] & tcp-rst != 0'

# Only retransmissions are not directly filterable — capture and analyse in Wireshark

# DNS traffic
sudo tcpdump -i any -nn port 53

# Ring buffer: 10 files of 100MB, overwrite oldest. For catching a rare event
sudo tcpdump -i any -w cap.pcap -C 100 -W 10
```

⚠️ **Always use `-s 0`** (or a modern tcpdump, where it is the default). An older default truncated packets to 68 bytes, which captures headers and throws away the payload you needed.

⚠️ **Never run an unfiltered capture on a busy production host.** You will fill the disk in minutes and add real CPU load. Always filter by host and port.

### The filter syntax

```bash
host 10.0.0.5                    # to or from
src host 10.0.0.5                # from only
dst port 443
net 10.0.0.0/8
port 80 or port 443
tcp and not port 22              # exclude your own SSH session
'tcp[tcpflags] & tcp-rst != 0'   # flag matching — quote it
greater 1000                     # packets larger than 1000 bytes
```

💡 **`and not port 22` is worth building into muscle memory.** Without it, your capture is full of your own SSH traffic, and it also feeds back on itself.

### The ring buffer trick

For a problem that happens once every few hours:

```bash
sudo tcpdump -i any -w /tmp/cap.pcap -C 100 -W 10 -s 0 'host 10.0.0.5'
```

Ten files, 100MB each, oldest overwritten. Leave it running. When the incident happens, stop it and you have the last ~1GB of traffic including the event.

This is how you catch intermittent problems that you can never reproduce on demand.

## Wireshark

`tcpdump` captures. Wireshark analyses. Capture on the server, analyse on your laptop.

### Display filters — different syntax from capture filters

```
ip.addr == 10.0.0.5
tcp.port == 443
http.request.method == "POST"
tcp.flags.reset == 1
tcp.analysis.retransmission
tcp.analysis.zero_window
tcp.analysis.duplicate_ack
dns.qry.name contains "example"
frame.time_delta > 0.1
```

⚠️ Capture filters (`tcpdump` syntax) and display filters (Wireshark syntax) are **different languages**. `host 10.0.0.5` for capture, `ip.addr == 10.0.0.5` for display. This trips up everyone at least once.

### The features that matter

| Feature | What it gives you |
|---|---|
| **Follow → TCP Stream** | The whole conversation as readable text. Use this constantly |
| **Statistics → Conversations** | Who talked to whom, how much, how long |
| **Statistics → TCP Stream Graphs** | Time/sequence graph — see stalls and retransmits visually |
| **Analyze → Expert Information** | Wireshark lists every problem it found. **Start here** |
| **Time column → seconds since previous** | Instantly reveals where the delay is |

💡 **Two habits that pay for themselves immediately:** open Expert Information first, because Wireshark has already found the retransmissions and zero-window events for you; and change the time column to "seconds since previous displayed packet", because a 3-second gap in that column is your entire answer.

### Decrypting TLS

Wireshark cannot read TLS by default. Two ways in:

```bash
# 1. Have your client log session keys
export SSLKEYLOGFILE=/tmp/keys.log
curl https://example.com
# Wireshark → Preferences → Protocols → TLS → (Pre)-Master-Secret log filename
```

Python and most browsers honour `SSLKEYLOGFILE`. This works even with forward secrecy, which is why it exists.

```bash
# 2. For HTTP specifically, use mitmproxy instead — usually easier
```

## `mitmproxy` — for HTTPS content

When you need to see request and response **bodies**, not packets.

```bash
mitmproxy                     # interactive terminal UI
mitmweb                       # browser UI
mitmdump -w flows.mitm        # non-interactive capture
```

Point your client at it:

```bash
export HTTPS_PROXY=http://localhost:8080
export SSL_CERT_FILE=~/.mitmproxy/mitmproxy-ca-cert.pem
python my_script.py
```

⚠️ Your client must trust mitmproxy's CA, because it is performing a deliberate man-in-the-middle. This is exactly the attack that `verify=False` enables accidentally ([[02.9 - TLS]]) — doing it on purpose here is a good way to internalise why that setting is dangerous.

Scripting it is where it becomes powerful:

```python
# addon.py — modify traffic in flight
def response(flow):
    if "/api/users" in flow.request.pretty_url:
        flow.response.status_code = 500
```

```bash
mitmdump -s addon.py
```

Now you can inject failures into a third-party API you do not control, which is enormously useful for testing error handling.

## In Production

### Where to capture

| Situation | Capture at |
|---|---|
| "Did the request arrive?" | Both sides. The comparison is the answer |
| Slow response | The server, to separate network time from processing time |
| Connection resets | Both sides. Check the TTL of the RST to find who sent it |
| In Kubernetes | An ephemeral debug container sharing the pod's network namespace |

```bash
kubectl debug -it mypod --image=nicolaka/netshoot --target=api
# now you are in the pod's network namespace with tcpdump, ss, dig, curl
```

💡 **`nicolaka/netshoot` is worth knowing by name.** It is a container image with every network tool preinstalled, and `kubectl debug` puts it inside your pod's network namespace without changing the pod. This is the standard way to debug Kubernetes networking.

### The RST fingerprint

When a connection resets, the question is who sent it.

```bash
sudo tcpdump -i any -nn -v 'tcp[tcpflags] & tcp-rst != 0'
```

Look at the **TTL** of the RST packet:

```
Your packets:      TTL 64  (fresh from your kernel)
Peer's packets:    TTL 52  (64 minus 12 hops)
The RST:           TTL 61  (64 minus 3 hops)  ← a middlebox 3 hops away sent it
```

A TTL matching neither endpoint means something in the middle killed your connection. That is a firewall, load balancer or NAT gateway, not the peer — and knowing that redirects the entire investigation.

### Reading a slow request

```
0.000  →  SYN
0.024  ←  SYN-ACK              24ms   network RTT
0.024  →  ACK
0.025  →  ClientHello
0.049  ←  ServerHello...       24ms   TLS RTT
0.051  →  Finished
0.052  →  GET /users
2.891  ←  200 OK               2839ms ← the server, not the network
```

The gap between the request and the first response byte is server processing time. Everything before it is network and handshake.

**One capture answers "is it the network or the server?" definitively**, and that question is the source of a great deal of unproductive argument between teams.

### When you cannot capture

Sometimes you have no access. Fall back to:

```bash
# The layer timing breakdown from [[02.1 - The Stack in One Picture]]
curl -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s https://api.example.com

# Per-hop loss and latency
mtr -T -P 443 api.example.com

# Socket state on your side
ss -ti dst api.example.com
```

The `curl` command gets you 80% of the diagnostic value for 5% of the effort, and it needs no privileges.

## Codebase

**Repo:** `the-tcpdump-group/tcpdump` + `libpcap`, and `mitmproxy/mitmproxy`

**Question to answer:** How does tcpdump capture packets without being in the network path, and how does the filter expression get compiled so that filtering happens efficiently rather than by inspecting every packet in userspace?

**Read, in order:**

1. `libpcap/pcap-linux.c` — how it opens a raw socket and receives copies of packets. Look for `PACKET_MMAP`, which is why capture is cheap
2. `libpcap/gencode.c` — **this is the interesting part.** Your filter expression is compiled into **BPF bytecode** and run inside the kernel, so non-matching packets are discarded before ever reaching userspace
3. `libpcap/bpf_filter.c` — the BPF virtual machine. It is small, and it is the ancestor of eBPF, which now runs a large part of modern Linux observability
4. `mitmproxy/proxy/layers/tls.py` — how mitmproxy generates a certificate per hostname on the fly. This is the mechanics of the attack that certificate verification prevents

💡 The libpcap reading has a bonus payoff: **BPF is the foundation of eBPF**, which underlies Cilium, modern profilers, and most new Linux observability tooling. Understanding the original filter VM makes all of that much easier to pick up later.

**Size:** 1 session.

**Drill 2.10 — Read the wire**

This drill is pure tool fluency. The deliverable is speed, not artifacts.

```
drills/02-capture/

│   ├── mystery_2/        # connection resets — who sent them?
│   ├── mystery_3/        # works small, fails large

│   ├── mystery_5/        # request "sent" but never "received"
│   └── SOLUTIONS.md

```

**Part 1 — Filter fluency.** Write 20 filter expressions, capture-side and display-side, covering: one host, one port, SYNs only, RSTs only, large packets, DNS, HTTP POSTs, retransmissions, zero windows, and excluding your SSH session.

Test each. This is rote and it is the foundation for everything else.

**Part 2 — Annotate one request.** Capture a single HTTPS request end to end. Annotate every packet: what it is, which layer, what it means, and the time delta from the previous one.

Identify precisely where each of DNS, TCP handshake, TLS handshake, request, server processing and response begins and ends.

**Part 3 — Five mysteries.** Build five scenarios, each with a single cause, using toxiproxy, `tc netem` and firewall rules. **Then wait a week and diagnose them from capture alone**, without reading your own setup scripts.

For each: what did you look at first, what confirmed it, and how long did it take?

Mystery 4 is the important one — the failure that only happens at low traffic, which is the idle-timeout inversion from [[02.10 - NAT Firewalls and Middleboxes]]. Its counterintuitive shape is exactly what makes real incidents hard.

**Part 4 — Decrypt your own traffic.** Use `SSLKEYLOGFILE` to decrypt a Python HTTPS request in Wireshark. Read the plaintext HTTP inside the TLS.

Then do the same with mitmproxy and compare which is more convenient for which question.

**Part 5 — Inject failures.** Write mitmproxy addons that: return 500 for 10% of requests, add 3 seconds of latency, truncate a response body, and return malformed JSON.

Point your service at it through the proxy. **Find out which of these your error handling actually survives.** Most services handle the 500 and fail badly on the truncated body and the malformed JSON — and those are the realistic failures.

**Part 6 — Capture in Kubernetes.** Deploy a service to a local cluster. Use `kubectl debug` with netshoot to capture traffic inside the pod. Write the exact command sequence in `netshoot.md` so that future-you can copy it during an incident without thinking.

**Done when:**
- All 20 filters work and you know which syntax goes where
- `ANNOTATED.md` accounts for every packet and every time gap in one request
- You solved all five mysteries from capture alone, with times recorded
- You have read your own decrypted HTTPS traffic
- You know which injected failures your error handling survives
- The netshoot command sequence is written down and tested
