# Signals and Process Lifecycle

#backend #os #signals #docker #shutdown

> **In one line:** Signals are the kernel's way of tapping a process on the shoulder. `SIGTERM` asks it to leave, `SIGKILL` removes it, and getting the first one delivered and handled inside a container is the difference between graceful shutdown and dropped requests on every deploy.

---

## The Idea

A signal is a small asynchronous notification: just a number. It interrupts whatever the process is doing and runs a handler, or does a default action.

| Signal | Number | Default | Sent by | Meaning |
|---|---|---|---|---|
| `SIGINT` | 2 | Terminate | Ctrl-C | "User wants you to stop" |
| `SIGTERM` | 15 | Terminate | `kill`, Docker, Kubernetes, systemd | "Please shut down cleanly" |
| `SIGKILL` | 9 | Terminate | `kill -9`, OOM killer, Kubernetes after the grace period | **Cannot be caught, blocked or ignored** |
| `SIGQUIT` | 3 | Core dump | Ctrl-\\ | Gunicorn: fast shutdown. Java: thread dump. |
| `SIGHUP` | 1 | Terminate | Terminal closed; by convention `kill -HUP` | "Reload config" (nginx, gunicorn), "reopen log files" |
| `SIGCHLD` | 17 | Ignore | Kernel, when a child exits | "Time to `wait()` for your child" |
| `SIGPIPE` | 13 | Terminate | Kernel, on write to a closed pipe or socket | Python ignores it and raises `BrokenPipeError` instead |
| `SIGSEGV` | 11 | Core dump | Kernel, on invalid memory access | A crash in C code: an extension, or the interpreter |
| `SIGUSR1/2` | 10/12 | Terminate | You | App-defined: gunicorn uses `USR1` to reopen logs, `USR2` to upgrade the binary |
| `SIGSTOP` / `SIGCONT` | 19/18 | Stop / continue | Debuggers, Ctrl-Z (`SIGTSTP`) | Cannot catch `SIGSTOP` |

```bash
kill -l                 # list all
kill -TERM $PID         # polite
kill -KILL $PID         # not polite
grep Sig /proc/$PID/status   # SigBlk, SigIgn, SigCgt bitmasks: blocked, ignored, caught
```

## How Python Handles Signals

```python
import signal, sys

def on_term(signum, frame):
    print("SIGTERM received, shutting down")
    sys.exit(0)            # raises SystemExit in the main thread

signal.signal(signal.SIGTERM, on_term)
```

Three rules that surprise people:

1. **Handlers run only in the main thread.** CPython's C-level handler just sets a flag. The interpreter checks the flag between bytecodes **in the main thread** and runs your Python handler there.
2. **A main thread blocked in C code delays the handler.** If it is stuck in a long C call (a big regex, a numpy operation, a `lock.acquire()` without a timeout on older versions), the handler waits until that call returns.
3. **By default Python turns `SIGINT` into `KeyboardInterrupt`** and leaves `SIGTERM` at its default action, which kills the process **without** running `finally` blocks or `atexit` handlers. A plain Python script killed by `docker stop` gets no cleanup unless you install a `SIGTERM` handler.

### In asyncio

```python
import asyncio, signal

async def main():
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, stop.set)

    server = await start_server()
    await stop.wait()
    await server.drain_and_close()     # stop accepting, finish in-flight work

asyncio.run(main())
```

`loop.add_signal_handler` uses the **self-pipe trick**: the C handler writes a byte to a pipe the event loop is watching, so the signal becomes an ordinary readable event in the loop. No code runs at an unsafe moment. Uvicorn installs its own handlers this way. That is how it drains on `SIGTERM`.

## The Container Shutdown Sequence

When Kubernetes deletes a pod (deploy, scale-down, node drain):

```
t=0     Pod marked Terminating
        ├── removed from Service endpoints (asynchronously! may lag a few seconds)
        └── preStop hook runs (if any)
        then SIGTERM → PID 1 of each container
t=0..N  your app drains: stops accepting, finishes in-flight requests, closes pools
t=N     terminationGracePeriodSeconds (default 30) expires
        SIGKILL → everything left in the container
```

Docker's `docker stop` is the same with a 10-second default.

### The PID 1 problem

In a container, your entrypoint process is **PID 1**. The kernel treats PID 1 specially: **a signal with no handler installed is ignored**, rather than applying its default action. So:

```dockerfile
CMD ["python", "app.py"]          # app.py is PID 1
```

If `app.py` never installs a `SIGTERM` handler, `SIGTERM` does nothing. Kubernetes waits the full 30 seconds, then `SIGKILL`s. Every deploy takes 30 s per pod and drops every in-flight request.

And the shell form is worse:

```dockerfile
CMD python app.py                 # actually runs: /bin/sh -c "python app.py"
```

Now `sh` is PID 1. It receives `SIGTERM` and **does not forward it** to Python. Same result.

**Fixes:**

| Fix | How |
|---|---|
| Exec form | `CMD ["python", "app.py"]`, never the shell form |
| `exec` in entrypoint scripts | `exec uvicorn app:app ...` as the last line, so the server **replaces** the shell and becomes PID 1 |
| A tiny init | `tini` (`ENTRYPOINT ["tini", "--"]`) or `docker run --init`. It forwards signals and reaps zombies. |
| Handle `SIGTERM` | uvicorn and gunicorn already do. Your custom workers and scripts must. |

### The endpoint-removal race

Even with perfect `SIGTERM` handling there is a race. The pod is removed from load balancers **at the same time** the signal is sent, and removal takes a few seconds to propagate to every kube-proxy and ingress. If your app stops accepting connections instantly, requests still routed to it fail.

The standard fix is to keep serving briefly before draining:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

Full shutdown design, including draining long-lived connections, is in [[12.7 - Graceful Shutdown and Draining]].

## Exit Codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | General error (an uncaught Python exception exits with 1) |
| 2 | Misuse: bad CLI arguments (argparse uses 2) |
| 126 / 127 | Not executable / command not found |
| **128 + N** | Killed by signal N |
| **130** | 128 + 2: `SIGINT` (Ctrl-C) |
| **137** | 128 + 9: `SIGKILL`. OOM killer, or the grace period ran out |
| **143** | 128 + 15: `SIGTERM` with the default action. The process did not handle it, and did not need to. |
| 139 | 128 + 11: `SIGSEGV`. A native crash. |

💡 **137 has two causes.** Check `OOMKilled` in `kubectl describe pod`. If it is not an OOM, your app ignored `SIGTERM` and was killed after the grace period. That is the PID 1 problem above.

## Signal Safety, Briefly

A signal can arrive between any two machine instructions. In C, a handler may only call **async-signal-safe** functions; `malloc` and `printf` are not among them. Python sidesteps this by deferring your handler to a safe point, which is why Python handlers can do anything, but run late.

For the same reason, avoid heavy work inside a handler. Set a flag or an event and let the main code act on it.

**Question to answer:** Trace a `SIGTERM` from `docker stop` to uvicorn closing its listening socket. Where does the signal turn into a Python-level event?

1. CPython `Modules/signalmodule.c` — `signal_handler()` (the C handler: sets a flag, writes to the wakeup fd) and `PyErr_CheckSignals()` (runs your Python handler later)
