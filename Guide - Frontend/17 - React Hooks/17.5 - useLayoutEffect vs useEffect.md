# useLayoutEffect vs useEffect

Identical APIs, different timing relative to paint.

```
render → DOM mutated → useLayoutEffect → browser paints → useEffect
                       ^ blocks paint              ^ after paint
```

**`useLayoutEffect`** runs synchronously after DOM mutation and **before** the browser paints. React waits for it to finish before allowing a frame.

**`useEffect`** runs asynchronously after paint, so it never delays the frame.

## Why the difference matters

If an effect changes something visual, `useEffect` produces a visible flash of the intermediate state:

```jsx
function Tooltip({ targetRef, children }) {
  const [pos, setPos] = useState({ top: 0, left: 0 });
  const ref = useRef(null);

  useLayoutEffect(() => {
    const target = targetRef.current.getBoundingClientRect();
    const tip = ref.current.getBoundingClientRect();
    setPos({ top: target.top - tip.height, left: target.left });
  }, []);

  return <div ref={ref} style={{ position: "absolute", ...pos }}>{children}</div>;
}
```

With `useEffect`, the tooltip paints at `{0, 0}` in the top-left corner, then jumps to its correct position on the next frame. With `useLayoutEffect`, React measures, updates state, re-renders and commits — all before a single pixel is shown.

That "re-render before paint" is the key capability: a `setState` inside a layout effect is processed synchronously in the same frame.

## When to use useLayoutEffect

Only when you **measure the DOM and immediately change something visual based on the measurement**:

- Positioning tooltips, popovers, dropdowns
- Measuring text to decide whether to truncate
- Scroll restoration on mount
- Synchronizing scroll position between two panes
- Focus management where a flash of the wrong focus ring would be visible
- Measuring for virtualized list item heights

Everything else uses `useEffect`.

## The performance cost

`useLayoutEffect` blocks paint. Whatever it does is added directly to the frame's critical path, and if it triggers a re-render, that render happens synchronously too.

```jsx
useLayoutEffect(() => {
  expensiveComputation();     // delays the frame by its full duration
}, []);
```

Layout effects also run for every component in a commit before any paint, so several across a tree add up. This is why the default should be `useEffect` and the layout variant should require justification.

## The SSR warning

```
Warning: useLayoutEffect does nothing on the server
```

There is no DOM and no paint during server rendering, so layout effects cannot run. If the component depends on one to look correct, the server HTML will differ from the client's first paint.

Three responses, in order of preference:

**Do not need it on the server.** If the layout effect only adjusts an interactive element (a tooltip that appears on hover), it never matters — the server output is correct without it.

**Render nothing until mounted**, for genuinely measurement-dependent UI:

```jsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
if (!mounted) return null;
```

This costs a client-only render, so use it narrowly.

**Use the isomorphic wrapper** to silence the warning where the effect is genuinely client-only:

```jsx
const useIsomorphicLayoutEffect =
  typeof window !== "undefined" ? useLayoutEffect : useEffect;
```

Every major component library ships this. It suppresses the warning without changing behavior, since on the server neither hook runs anyway.

## Ordering within a commit

Both hooks run **child-first**:

```
Child layout effect → Parent layout effect → paint → Child effect → Parent effect
```

And cleanup of the previous run happens before the next setup, for both.

All layout effects across the whole tree run before any passive effect. So a parent's `useLayoutEffect` still runs before a child's `useEffect`.

This matters when a parent needs to measure something a child sets up — the child's layout effect has run by then, but its passive effect has not.

## flushSync as the escape hatch

Occasionally you need a state update applied to the DOM *within an event handler*, before reading layout:

```jsx
import { flushSync } from "react-dom";

const handleAdd = () => {
  flushSync(() => {
    setItems([...items, newItem]);
  });
  listRef.current.lastChild.scrollIntoView();
};
```

Without `flushSync`, the new item is not in the DOM yet when `scrollIntoView` runs. This bypasses batching and forces a synchronous render and commit ([[18.6 - Batching and the Update Queue]]).

It is expensive and disables concurrent optimizations for that update, so it is a last resort — but it is the right tool when the alternative is a layout effect that only exists to react to one specific interaction.

## Interaction with concurrent rendering

Layout effects are part of the commit phase, which is synchronous and uninterruptible ([[18.4 - Render Phase vs Commit Phase]]). So they always see a consistent, fully-committed DOM.

The render phase can be interrupted and restarted; the commit phase — including layout effects — cannot. This is precisely why measurement belongs in a layout effect rather than during render, where the work might be discarded.

## Refs and measurement

```jsx
const [height, setHeight] = useState(0);
const ref = useRef(null);

useLayoutEffect(() => {
  setHeight(ref.current.offsetHeight);
}, [children]);
```

For anything that changes size over time, `ResizeObserver` is better than a layout effect with a dependency guess ([[12.5 - Custom Events and Observer APIs]]) — it fires exactly when the size changes rather than when you predicted it might.

A callback ref is another option, and it runs at the same time as a layout effect:

```jsx
const measureRef = useCallback(node => {
  if (node) setHeight(node.getBoundingClientRect().height);
}, []);
```

This handles the case where the element mounts conditionally, which a layout effect with `[]` misses.

## How senior engineers actually use this

**They default to `useEffect`** and switch only after seeing an actual visual flash.

**They keep layout effects minimal** — measure, compute, set state, nothing more — because everything in them delays the frame.

**They use `ResizeObserver` for ongoing measurement** rather than layout effects with fragile dependencies.

**They ship the isomorphic wrapper** in any library or SSR application.

**They know `flushSync` exists** but treat reaching for it as a signal to reconsider the design.

## Common pitfalls

- Using `useLayoutEffect` everywhere "to be safe", adding frame-blocking work throughout the tree.
- Using `useEffect` for measurement and shipping a visible position flash.
- The SSR warning ignored, leading to hydration mismatches.
- Expensive work inside a layout effect.
- Measuring in a layout effect with `[]` when the element mounts later.
- Assuming parent layout effects run before child ones.

## Interview angle

"Difference between useEffect and useLayoutEffect" is a common mid-to-senior question. Answer with the timing — synchronous before paint versus asynchronous after — and give the concrete consequence: a tooltip positioned in `useEffect` visibly jumps, while `useLayoutEffect` lets React re-render before the frame is shown. Then note the cost (it blocks paint) and the SSR caveat. Mentioning `flushSync` for the event-handler case rounds it out.
