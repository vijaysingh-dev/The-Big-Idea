# Enforcing Security in Apex and SOQL

## The default is unsafe

Apex runs in **system mode** by default. That means:

- SOQL returns every record regardless of the running user's record access
- Field-level security is not applied to query results
- Object permissions are not checked before DML
- A Lightning component calling that Apex will happily display everything

This is deliberate — some code legitimately needs elevated access — but it means **security enforcement in code is the developer's job**. This is the most common finding in Salesforce security reviews and the most common cause of real data exposure in custom code.

Three separate things need enforcing, and they use different mechanisms:

1. **Record access** — sharing keywords, or `USER_MODE`
2. **Object permissions** — describe checks, or `USER_MODE`
3. **Field-level security** — `stripInaccessible`, describe checks, or `USER_MODE`

## Sharing keywords

These control record access only. They do nothing for object or field permissions.

```java
public with sharing class ClaimService { }
public without sharing class ClaimAdminService { }
public inherited sharing class ClaimUtils { }
```

**`with sharing`** applies the running user's record access to queries in this class.

**`without sharing`** ignores record access entirely. Legitimate uses exist: a service that must aggregate across all records, a sharing recalculation job, an approval process that needs to read a record the approver cannot yet see. Each use should be deliberate and commented.

**`inherited sharing`** takes on the mode of whatever called it. This is the correct default for reusable utility classes, because it neither silently opens access nor silently restricts a caller that needed system mode.

Two behaviours worth knowing precisely:

**The keyword does not propagate through the call stack the way people assume.** A `with sharing` class calling a `without sharing` class means the inner class runs without sharing. The inner declaration wins for code inside it.

**A class with no keyword is not neutral.** When entered directly — from a Lightning controller, a REST endpoint, or an anonymous block — it runs *without* sharing. Omitting the keyword is therefore a security decision made by accident, which is why every class should declare one explicitly.

Inner classes inherit the outer class's sharing declaration and cannot override it.

## USER_MODE

The current recommendation, and the shortest path to correct behaviour. It enforces record sharing, object permissions, and field-level security together.

```java
// Query: sharing, CRUD, and FLS all applied
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c, Approved_Amount__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
    WITH USER_MODE
];

// DML: object and field permissions applied
insert as user newClaims;
update as user claims;
delete as user obsoleteClaims;
```

`WITH SYSTEM_MODE` exists as the explicit opposite, which is useful for making intent obvious in a class that is otherwise in user mode.

`USER_MODE` replaces the older `WITH SECURITY_ENFORCED`, which only covered object and field access on queries, did not apply sharing, and had gaps around polymorphic relationship fields. New code should use `USER_MODE`.

The behaviour on violation is to throw an exception. That is usually correct — if the user should not see the data, the operation should fail rather than silently returning less.

## stripInaccessible

When you want to return whatever the user is permitted to see rather than failing, `Security.stripInaccessible` removes inaccessible fields from a collection.

```java
public with sharing class ClaimController {

    @AuraEnabled(cacheable=true)
    public static List<Warranty_Claim__c> getClaimsForAccount(Id accountId) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Status__c, Approved_Amount__c, Internal_Notes__c
            FROM Warranty_Claim__c
            WHERE Account__c = :accountId
            WITH USER_MODE
        ];

        SObjectAccessDecision decision = Security.stripInaccessible(AccessType.READABLE, claims);
        return decision.getRecords();
    }
}
```

It is equally important on the way in. Data arriving from a component should be sanitized before DML, so a user cannot set a field they are not permitted to edit by crafting the request:

```java
@AuraEnabled
public static Id saveClaim(Warranty_Claim__c claim) {
    SObjectAccessDecision decision = Security.stripInaccessible(
        AccessType.UPSERTABLE, new List<Warranty_Claim__c>{ claim }
    );
    Warranty_Claim__c safe = (Warranty_Claim__c) decision.getRecords()[0];
    upsert as user safe;
    return safe.Id;
}
```

Without that, a component that renders only three fields can still be used to write to any field on the object, because the Apex method accepts a whole sObject. This is a real and frequently exploited pattern.

`decision.getRemovedFields()` returns what was stripped, which is worth logging.

## Describe checks

Still necessary when you need to branch on permission rather than fail or strip.

```java
if (!Schema.sObjectType.Warranty_Claim__c.isAccessible()) {
    throw new SecurityException('No access to warranty claims.');
}

if (Schema.sObjectType.Warranty_Claim__c.fields.Approved_Amount__c.isUpdateable()) {
    claim.Approved_Amount__c = amount;
}

if (Schema.sObjectType.Warranty_Claim__c.isDeletable()) {
    delete as user claims;
}
```

Describe calls consume CPU, so hoist them out of loops and cache results in static variables.

## SOQL injection

The other half of secure Apex. Static SOQL with bind variables is safe. Dynamic SOQL built by string concatenation is not.

```java
// Vulnerable: user input concatenated into the query
String status = ApexPages.currentPage().getParameters().get('status');
String query = 'SELECT Id FROM Warranty_Claim__c WHERE Status__c = \'' + status + '\'';
List<Warranty_Claim__c> claims = Database.query(query);
```

An input of `Closed' OR Name != '` turns that filter into something that matches everything.

Three defences, in order of preference:

```java
// 1. Bind variables work in dynamic SOQL too
String status = userInput;
String query = 'SELECT Id FROM Warranty_Claim__c WHERE Status__c = :status WITH USER_MODE';
List<Warranty_Claim__c> claims = Database.query(query);

// 2. Escape when a bind is genuinely impossible
String safe = String.escapeSingleQuotes(userInput);

// 3. Allowlist anything that cannot be bound, such as field or object names
private static final Set<String> SORTABLE = new Set<String>{ 'Claim_Date__c', 'Status__c', 'Amount__c' };
if (!SORTABLE.contains(sortField)) {
    throw new IllegalArgumentException('Invalid sort field');
}
```

Field and object names cannot be bind variables, which is why an allowlist is the only safe approach for a dynamic sort or a dynamic object query. See [[08.7 - Dynamic SOQL]].

## Where enforcement matters most

**`@AuraEnabled` methods.** These are directly callable by any authenticated user, including through the API, regardless of what the component actually renders. Assume every `@AuraEnabled` method is a public endpoint, because it effectively is.

**`@RestResource` and `webservice` methods.** Same reasoning, more obviously.

**`@InvocableMethod`.** Callable from flows, which may run in a different context than expected.

**Anything a Guest User can reach.** Experience Cloud guest access is the highest-risk surface on the platform, because it is unauthenticated. Guest user sharing has its own restricted model, and the standard guidance is that guest users should never have write access to objects and should reach data only through explicitly designed, tightly scoped Apex.

## A practical checklist

For any Apex class that a user can reach:

- Declare a sharing keyword explicitly
- Use `WITH USER_MODE` on queries, or justify why not
- Use `as user` on DML, or justify why not
- Run `stripInaccessible` on sObjects arriving from the client before writing them
- Use bind variables, never concatenation, in dynamic SOQL
- Allowlist any dynamic field or object name
- Return only the fields the UI needs, not the whole record
- Test with `System.runAs()` as a non-administrator

That list is close to what an AppExchange security review checks for, and it is a reasonable internal standard regardless. See [[22.5 - Secure Apex Coding and OWASP on Platform]] and [[22.7 - AppExchange Security Review]].

## Testing enforcement

```java
@IsTest
static void restrictedUserCannotSeeApprovedAmount() {
    User restricted = TestDataFactory.createUser('Service_Coordinator');
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    System.runAs(restricted) {
        List<Warranty_Claim__c> results = ClaimController.getClaimsForAccount(claim.Account__c);
        Assert.isFalse(
            results[0].getPopulatedFieldsAsMap().containsKey('Approved_Amount__c'),
            'Approved amount should be stripped for this user'
        );
    }
}
```

`getPopulatedFieldsAsMap()` is the way to assert that a field was actually removed rather than merely null.
