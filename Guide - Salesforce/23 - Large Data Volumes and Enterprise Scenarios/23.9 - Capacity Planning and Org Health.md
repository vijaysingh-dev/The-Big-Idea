# Capacity Planning and Org Health

## The premise

Most Salesforce scale failures are predictable. The data grew, the automation accumulated, the allocation filled — all of it visible months before it became an incident, and nobody was looking.

**Capacity planning is watching a small number of numbers and acting on their trend**, not on their current value.

## The numbers worth watching

```
Data storage                      by object, trended
File storage
Record counts per object          trended
Ownership concentration           per object
Parent concentration              per object
Daily API consumption
Daily async execution consumption
Platform event publish and delivery
Batch job duration                per job, trended
Scheduled job last-run timestamps
Trigger and flow count per object
Custom field count per object
Apex code size
```

**Trend matters more than level.** An object at 40% of a threshold that doubled in six months is a problem; one at 70% that has been flat for two years is not.

## Storage

```
Setup → Storage Usage
```

Data storage and file storage are allocated separately, and hitting either produces `STORAGE_LIMIT_EXCEEDED` on operations that worked yesterday.

**Roughly 2 KB per record** for most objects, more for wide ones.

**The page shows record counts by object**, which is the fastest inventory available and worth capturing monthly:

```java
public with sharing class StorageSnapshotBatch implements Schedulable {

    public void execute(SchedulableContext ctx) {
        // capturing the count per object monthly is what makes growth visible
        List<Org_Metric__c> metrics = new List<Org_Metric__c>();

        metrics.add(buildMetric('Warranty_Claim__c',
            [SELECT COUNT() FROM Warranty_Claim__c]));
        metrics.add(buildMetric('Claim_Part__c',
            [SELECT COUNT() FROM Claim_Part__c]));
        metrics.add(buildMetric('Case', [SELECT COUNT() FROM Case]));

        insert metrics;
    }
}
```

**A count snapshot per object per month** turns "the org is growing" into "claims will pass eight million in March", which is actionable.

## Allocations

```java
public with sharing class OrgLimitMonitor implements Schedulable {

    public void execute(SchedulableContext ctx) {
        List<Org_Metric__c> metrics = new List<Org_Metric__c>();

        for (System.OrgLimit orgLimit : OrgLimits.getAll()) {
            metrics.add(new Org_Metric__c(
                Metric__c = orgLimit.getName(),
                Value__c = orgLimit.getValue(),
                Limit__c = orgLimit.getLimit(),
                Percent_Used__c = orgLimit.getLimit() == 0
                    ? 0
                    : (orgLimit.getValue() * 100.0) / orgLimit.getLimit(),
                Captured_At__c = Datetime.now()
            ));
        }

        insert metrics;
        alertOnThresholds(metrics);
    }
}
```

**The allocations worth alerting on:**

```
DailyApiRequests                    exhaustion stops every integration
DailyAsyncApexExecutions            exhaustion stops every job
DailyBulkApiBatches
DailyStandardVolumePlatformEvents
DailyDeliveredPlatformEvents
DataStorageMB
FileStorageMB
```

**Alert at 70%**, not at 95%. The point is to act before it matters.

**Daily capture is necessary** because these reset daily — a snapshot at midnight shows nothing.

## Distribution

The check that catches skew before it becomes a project.

```sql
SELECT AccountId, Account.Name, COUNT(Id) FROM Contact
GROUP BY AccountId, Account.Name ORDER BY COUNT(Id) DESC LIMIT 10

SELECT OwnerId, Owner.Name, COUNT(Id) FROM Warranty_Claim__c
GROUP BY OwnerId, Owner.Name ORDER BY COUNT(Id) DESC LIMIT 10

SELECT Region__c, COUNT(Id) FROM Warranty_Claim__c
GROUP BY Region__c ORDER BY COUNT(Id) DESC LIMIT 10
```

**Run these monthly on every high-volume object.** Skew develops gradually and is far easier to correct at 20,000 children than at 400,000.

**The threshold to watch:** 10,000 records under one parent, or owned by one user. See [[10.9 - Data Skew]].

## Job health

```sql
SELECT ApexClass.Name, JobType, Status, NumberOfErrors, ExtendedStatus,
       JobItemsProcessed, CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE CreatedDate = LAST_N_DAYS:7 AND Status IN ('Failed', 'Aborted')
```

**Duration trended** is the earliest performance warning available:

```sql
SELECT ApexClass.Name, CreatedDate, CompletedDate, JobItemsProcessed
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND CreatedDate = LAST_N_DAYS:90
ORDER BY ApexClass.Name, CreatedDate
```

**A job whose duration has doubled over six months will overrun its window**, and the trend is visible long before it does.

**Alert on absence:**

```sql
SELECT Job_Name__c, MAX(Started_At__c) lastRun
FROM Batch_Run_Log__c GROUP BY Job_Name__c
```

**A job that stopped running produces no failure record.** This query is the only thing that detects it, and it is the failure mode most orgs have no coverage for. See [[23.8 - Real Failure Scenarios and Root Causes]].

## Technical debt

The org-level metrics that predict future pain.

**Automation count per object:**

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status, LengthWithoutComments FROM ApexTrigger ORDER BY TableEnumOrId"
```

```sql
SELECT ApiName, Label, TriggerType, TriggerObjectOrEventLabel, Status
FROM FlowDefinitionView WHERE Status = 'Active'
ORDER BY TriggerObjectOrEventLabel
```

**More than one trigger on an object** is a signal. **Four flows on one object** is a CPU limit waiting to happen. See [[11.4 - One Trigger Per Object]].

**Field count per object:**

```sql
SELECT EntityDefinition.QualifiedApiName, COUNT(Id)
FROM FieldDefinition
GROUP BY EntityDefinition.QualifiedApiName
ORDER BY COUNT(Id) DESC
```

An object with 400 fields is expensive to query and usually contains many nobody uses.

**Unused fields**, which is harder and worth doing periodically:

```sql
SELECT MetadataComponentName, RefMetadataComponentName
FROM MetadataComponentDependency
WHERE RefMetadataComponentType = 'CustomField'
```

A field with no dependencies and no data is a deletion candidate. See [[13.6 - Metadata API and Tooling API]].

**API version distribution:**

```sql
SELECT ApiVersion, COUNT(Id) FROM ApexClass GROUP BY ApiVersion ORDER BY ApiVersion
```

```sql
SELECT Application, ApiVersion, COUNT(Id) FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:30 AND ApiType != null
GROUP BY Application, ApiVersion
```

**The second query matters more** — it shows which integrations are on old versions, which is what breaks on a retirement. See [[01.11 - Release Cycle, Trust and Status]].

**Coverage and static analysis findings**, trended:

```sql
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate ORDER BY NumLinesUncovered DESC
```

## Projecting

The arithmetic that makes it actionable.

```
Warranty_Claim__c
    Jan 2026    5,200,000
    Apr 2026    6,100,000
    Jul 2026    7,000,000

    Growth: ~300,000 per month
    At 10,000,000 by:  October 2027
```

**Then the questions:**

**When does the nightly job overrun its window?** Extrapolate its duration.

**When does a query stop being selective?** The threshold is a proportion, so it depends on the filter's distribution as well as the total.

**When does storage fill?**

**When does the archive job need to start?** Before, not after.

**Extrapolation is crude and sufficient.** The point is to know roughly when, not exactly.

## Acting on it

The interventions, mapped to what the trend shows.

```
Storage growing toward the limit      → archiving, file cleanup
An object approaching a query
  selectivity threshold               → archiving, indexes, denormalization
Ownership concentration rising        → redistribute before it becomes a project
Parent concentration rising           → split the catch-all record
Batch duration rising                 → scope tuning, then archiving
API allocation rising                 → batch the integration, push rather than poll
Async allocation rising               → larger scope, fewer jobs
Automation count rising per object    → consolidate
```

**Archiving appears three times**, which reflects reality — it is the most broadly effective intervention available and the one that requires an organizational decision rather than a technical one. See [[23.4 - Archiving with Big Objects and External Storage]].

## A health check

The review worth running quarterly, which takes a morning.

```
Volume
  [ ] Record counts per object, against last quarter
  [ ] Storage consumption and projection
  [ ] Top parents and owners per high-volume object

Performance
  [ ] Batch job durations, trended
  [ ] Query plans for the ten most-used queries
  [ ] Page load times, if Event Monitoring is available

Allocations
  [ ] API, async, event, and storage consumption at peak
  [ ] Anything above 70%

Reliability
  [ ] Failed jobs, last quarter
  [ ] Jobs that stopped running
  [ ] Integration reconciliation results

Debt
  [ ] Triggers and flows per object
  [ ] Fields per object, and unused field candidates
  [ ] API version distribution, including integrations
  [ ] Test coverage and suite duration
  [ ] Static analysis findings, trended

Security
  [ ] Users with Modify All Data
  [ ] Integration user permissions
  [ ] Guest user access
  [ ] Sandbox masking
```

**The output is a short list of things to do**, prioritized, with an owner. A health check producing a fifty-item list produces nothing.

## Section 23 in one paragraph

At scale, the platform's behaviour is dominated by two things: whether a query can use an index, and how much work a change causes the sharing engine to do — and nearly every large-volume problem reduces to one of those. Distribution matters more than count, which is why 400,000 records under one account is worse than eight million spread evenly, and why the first diagnostic on any contention problem is asking what the failing records share. The interventions have a clear order of effectiveness: reduce the data, fix the distribution, make queries selective, simplify sharing, then index — and archiving appears first because it improves everything else at once while being the one that requires a retention decision rather than a technical change. Most failures at scale are predictable and silent: a query that stopped being selective, a job that stopped running, a recursion guard that skipped half a data load, a duplicate payment created eighteen months ago by a missing `oldMap` comparison. And six of the eight scenarios in this section would have been caught by monitoring rather than by review, which is the substantive point — at volume, problems are found by watching numbers trend, not by reading code.
