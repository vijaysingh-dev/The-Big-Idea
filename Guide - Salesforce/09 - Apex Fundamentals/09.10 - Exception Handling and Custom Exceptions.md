# Exception Handling and Custom Exceptions

## The basics

```java
try {
    processClaims(claims);
} catch (DmlException e) {
    handleDmlFailure(e);
} catch (Exception e) {
    logUnexpected(e);
    throw e;
} finally {
    cleanUp();
}
```

**All Apex exceptions are unchecked.** There are no checked exceptions and no `throws` declarations. Nothing forces a caller to handle anything, which puts the burden of knowing what can fail entirely on the developer.

`finally` runs whether or not an exception occurred, including after a `return`.

## The exception hierarchy

The ones you will actually meet:

```
Exception
├── DmlException              insert, update, delete failures
├── QueryException            zero or multiple rows for a single assignment
├── SObjectException          accessing a field that was not queried
├── NullPointerException      dereferencing null
├── ListException             index out of bounds
├── TypeException             failed cast
├── CalloutException          HTTP callout failure
├── LimitException            governor limit exceeded — NOT CATCHABLE
├── JSONException             malformed JSON
├── MathException             division by zero
├── StringException           invalid string operation, including bad Id
├── NoAccessException         insufficient permissions
├── NoDataFoundException
└── SecurityException
```

## LimitException cannot be caught

This is the most important exception behaviour on the platform.

```java
try {
    for (Integer i = 0; i < 200; i++) {
        Account a = [SELECT Id FROM Account LIMIT 1];  // exceeds 100 queries
    }
} catch (Exception e) {
    // never reached
}
```

`System.LimitException` bypasses `catch` blocks entirely. The transaction ends and everything rolls back.

The reason is deliberate: if limit exceptions were catchable, code could swallow them and continue consuming resources, defeating the fairness mechanism the limits exist to enforce ([[01.5 - Multi-Tenant Architecture]]).

The consequence for design: **you cannot recover from a limit failure, so you must not approach limits.** Checking remaining capacity proactively is the only defence:

```java
if (Limits.getQueries() > Limits.getLimitQueries() - 10) {
    System.enqueueJob(new ContinueProcessingQueueable(remainingIds));
    return;
}
```

See [[16.7 - Designing Around Limits]].

## DmlException

The one you handle most often, and it carries per-record detail.

```java
try {
    update claims;
} catch (DmlException e) {
    for (Integer i = 0; i < e.getNumDml(); i++) {
        Id failedId = e.getDmlId(i);
        String message = e.getDmlMessage(i);
        StatusCode code = e.getDmlType(i);
        List<String> fields = e.getDmlFieldNames(i);

        AutomationLogger.logError('ClaimUpdate', failedId, code + ': ' + message);
    }
}
```

`getDmlType()` returning a `StatusCode` is what lets you distinguish transient failures from permanent ones:

```java
if (e.getDmlType(i) == StatusCode.UNABLE_TO_LOCK_ROW) {
    // transient — worth retrying
} else if (e.getDmlType(i) == StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION) {
    // permanent — retrying achieves nothing
}
```

For bulk operations, **partial-success DML is usually better than a try-catch**, because it reports per record without aborting the batch:

```java
List<Database.SaveResult> results = Database.update(claims, false);

for (Integer i = 0; i < results.size(); i++) {
    if (!results[i].isSuccess()) {
        for (Database.Error err : results[i].getErrors()) {
            AutomationLogger.logError('ClaimUpdate', claims[i].Id,
                err.getStatusCode() + ': ' + err.getMessage());
        }
    }
}
```

See [[10.2 - Database Class Methods and Partial Success]].

## Custom exceptions

Any class ending in `Exception` and extending `Exception` becomes one. The name suffix is mandatory.

```java
public class ClaimValidationException extends Exception { }
public class IntegrationException extends Exception { }
public class ConfigurationException extends Exception { }
```

Apex generates the standard constructors automatically — no-argument, message, message with cause, and cause alone. You cannot declare your own constructors on an exception class, which is an unusual restriction.

Adding context through fields works:

```java
public class ClaimValidationException extends Exception {
    public Id claimId;
    public String failedRule;
}
```

```java
ClaimValidationException e = new ClaimValidationException('Claim exceeds coverage limit');
e.claimId = claim.Id;
e.failedRule = 'CoverageLimit';
throw e;
```

Custom exception types let callers handle different failures differently, which is the entire point:

```java
try {
    claimService.submit(claims);
} catch (ClaimValidationException e) {
    return Response.validationFailure(e.getMessage());
} catch (IntegrationException e) {
    scheduleRetry(claims);
    return Response.deferred();
} catch (Exception e) {
    AutomationLogger.logError('ClaimSubmit', null, e.getMessage());
    return Response.systemError();
}
```

Catch order matters — more specific types first, since `catch (Exception e)` matches everything.

## Exception methods

```java
e.getMessage()           // the message
e.getTypeName()          // 'System.DmlException'
e.getStackTraceString()  // full stack trace
e.getCause()             // the wrapped exception, if any
e.getLineNumber()
e.initCause(other)       // wrap another exception
```

**`getStackTraceString()` is what makes a log entry useful.** A logged message without it tells you what failed and not where.

Wrapping preserves the original while adding context:

```java
try {
    HttpResponse response = new Http().send(request);
} catch (CalloutException e) {
    IntegrationException wrapped = new IntegrationException(
        'ERP sync failed for batch ' + batchId, e
    );
    throw wrapped;
}
```

`getCause()` on the wrapper returns the original `CalloutException`.

## addError in triggers

Inside a trigger, `addError()` is the mechanism rather than throwing.

```java
for (Warranty_Claim__c claim : claims) {
    if (claim.Claim_Amount__c > coverageLimit) {
        claim.addError('Claim_Amount__c', 'This claim exceeds the coverage limit.');
    }
}
```

The difference from throwing:

**`addError()` on a record blocks that record**, and with partial-success DML the others still save. **Throwing aborts the whole transaction.**

**`addError(fieldName, message)` places the message next to the field** in the UI, which is a meaningfully better experience than a page-level error.

**The message reaches the user directly**, so it must be written for them. See [[06.5 - Validation Rules]].

```java
// Bad: internal detail leaked to the user
claim.addError('CoverageValidator: limit check failed for policy ' + policyId);

// Good
claim.addError('Claim_Amount__c',
    'This claim exceeds the coverage limit on the service contract. '
    + 'Contact the account manager to review coverage.');
```

`addError` also takes an exception object, and `setDmlOptions` controls whether the message is escaped as HTML.

## What not to do

**Swallowing exceptions.**

```java
try {
    update claims;
} catch (Exception e) {
    // nothing
}
```

The single worst pattern in Apex. The update failed, nobody knows, and the data is wrong. If an exception is genuinely acceptable, log it and say why in a comment.

**Catching Exception when you mean something specific.** Catching everything hides bugs — a null pointer exception in your own code gets treated as a business failure.

**Using exceptions for control flow.** An expected condition is a return value, not an exception. "No coverage found" is an answer; "the coverage service is unreachable" is an exception.

**Catching and rethrowing with no added value.**

```java
catch (Exception e) {
    throw e;   // pointless
}
```

**Logging the message without the stack trace.**

## Logging that survives rollback

The problem: when an exception propagates, the transaction rolls back, **including any log record you inserted in the catch block.**

```java
try {
    processClaims(claims);
} catch (Exception e) {
    insert new Automation_Log__c(Message__c = e.getMessage());  // rolled back with everything else
    throw e;
}
```

Three ways around it:

**Publish a platform event.** Events published with immediate behaviour survive rollback by design, which is precisely why they are the recommended logging mechanism.

```java
catch (Exception e) {
    EventBus.publish(new Automation_Error__e(
        Context__c = 'ClaimService.processClaims',
        Message__c = e.getMessage(),
        Stack_Trace__c = e.getStackTraceString()
    ));
    throw e;
}
```

**Catch without rethrowing**, so the transaction commits and the log survives. Only correct when the failure is genuinely recoverable.

**Use a savepoint**, rolling back the work and then logging in the surviving transaction. See [[10.5 - Savepoints, Rollback and Transaction Control]].

The platform event approach is the one that scales, and it is what mature orgs standardize on. See [[20.5 - Custom Logging Frameworks]].

## Testing exceptions

```java
@IsTest
static void submitThrowsWhenCoverageExceeded() {
    Warranty_Claim__c claim = TestDataFactory.createClaim(2000000);

    Test.startTest();
    try {
        ClaimService.submit(new List<Warranty_Claim__c>{ claim });
        Assert.fail('Expected ClaimValidationException');
    } catch (ClaimValidationException e) {
        Assert.isTrue(e.getMessage().contains('coverage limit'),
            'Message should name the failing rule');
    }
    Test.stopTest();
}
```

`Assert.fail()` after the call is essential — without it, a test where the exception is never thrown passes silently, which is exactly the bug the test exists to catch.

Asserting on the message content, not just the type, verifies the user-facing behaviour.

## Practical guidance

**Never swallow an exception.** Log it, with the stack trace.

**Catch specific types**, ordered most specific first.

**Use `LimitException`'s uncatchability as a design constraint.** Check limits proactively.

**Prefer partial-success DML to try-catch** for bulk operations.

**Use `addError` in triggers**, on the specific field, with a message written for the user.

**Log through a platform event** so the record survives rollback.

**Wrap exceptions to add context**, preserving the cause.

**Always `Assert.fail()`** after the call in an exception test.
