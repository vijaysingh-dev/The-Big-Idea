# Salesforce Shield Overview

## What Shield is

A paid add-on bundling three capabilities that the platform does not include:

```
Platform Encryption      encryption at rest, with the key under your control
Event Monitoring         who did what, across the whole org
Field Audit Trail        field history retained for up to 10 years
```

**Transaction Security Policies** come alongside it, and **Data Mask** is a separate free product frequently discussed with it.

The question worth asking before anything else: **what problem is Shield being bought to solve?**

## What Shield does not do

More important than what it does, because Shield is frequently proposed as a general answer to "we need security".

**It is not access control.** Sharing, profiles, and permission sets are the platform's access model, and they are free. A field encrypted with Shield is still readable by anyone with field-level access to it.

**It is not a substitute for secure code.** An `@AuraEnabled` method with no sharing declaration leaks data whether or not the fields are encrypted. See [[22.5 - Secure Apex Coding and OWASP on Platform]].

**It does not protect against a compromised user account.** An attacker with valid credentials sees decrypted data, because the platform decrypts for authorized users.

**It is not compliance.** GDPR and HIPAA require processes, contracts, and data governance. Shield supports some of that and satisfies none of it on its own. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

**The honest framing:** Shield addresses a specific set of requirements — encryption at rest with customer-managed keys, forensic visibility, and long-horizon audit history. It does not make an insecure org secure.

## Platform Encryption

**Encrypts data at rest**, with keys you can control and rotate.

Salesforce already encrypts data at rest at the infrastructure level. Shield's addition is **key management** — a tenant secret you generate, control, and can destroy.

**Why that matters:** for some regulatory and contractual requirements, "the vendor encrypts it" is insufficient and "we control the key" is the requirement.

**The cost is functional.** Encrypted fields lose capabilities:

```
Cannot be used in a WHERE clause with probabilistic encryption
Cannot be sorted
Cannot be used in formula fields
Cannot be an external ID
Cannot be used in some roll-up summaries
Reduced in report and list view filtering
```

Deterministic encryption restores exact-match filtering at the cost of weaker cryptographic properties. Covered fully in [[22.2 - Platform Encryption]].

**Encrypting the wrong field breaks features nobody anticipated**, which is why field selection is a design exercise rather than a checkbox.

## Event Monitoring

**Who did what, across the org**, delivered as daily log files or as real-time platform events.

Around fifty event types. The ones that justify the purchase:

```
ApexExecution      duration, CPU, and whether a request was long-running
API / RestApi      which integration, how many rows, which API version
ReportExport       data leaving the org
ContentTransfer    file downloads
Login / LoginAs
LightningPageView  real-user page performance
```

**The two use cases that recur:**

**Security forensics.** "Who exported the customer list before they resigned" has an answer, and nothing else provides it.

**Performance diagnosis.** `IS_LONG_RUNNING_REQUEST` identifies what is consuming concurrency slots for real users, which no other tool shows. See [[16.6 - Concurrency and Long Running Requests]] and [[20.6 - Event Monitoring and Operational Visibility]].

**Real-Time Event Monitoring** delivers a subset as platform events, subscribable immediately rather than daily — which is what makes alerting possible rather than only reporting.

## Field Audit Trail

**Standard field history:** 20 fields per object, retained 18 months to 24 months.

**Field Audit Trail:** 60 fields per object, retained **up to 10 years**.

```
Setup → Field Audit Trail → set the retention policy per object
```

History beyond 18 months moves to a big object, queryable but not reportable in the usual way:

```sql
SELECT FieldHistoryType, ParentId, Field, OldValue, NewValue, CreatedDate
FROM FieldHistoryArchive
WHERE ParentId = 'a0X5g000001AbCdEAK'
```

**Where it earns its place:** regulatory retention requirements, financial services audit, and any org where "what was this value three years ago" is a real question.

Covered in [[22.3 - Field Audit Trail and Data Retention]].

## Transaction Security Policies

The preventive half, and the part that stops an incident rather than documenting it.

```
Setup → Transaction Security Policies → New

Event Type:  ReportEvent
Condition:   row count > 10,000 on a report containing contact details
Action:      Block, and notify the security team
```

Actions: **Block**, **Two-Factor**, **End Session**, **Notify**.

Custom conditions in Apex:

```java
global with sharing class LargeExportPolicy implements TxnSecurity.EventCondition {

    global Boolean evaluate(SObject event) {
        ReportEvent reportEvent = (ReportEvent) event;

        // evaluated in flight, so this blocks the export rather than recording it
        return reportEvent.RowsProcessed > 10000
            && reportEvent.ReportName.contains('Customer Contact');
    }
}
```

**This is the capability most worth having**, and the one most often left unconfigured after Shield is purchased.

## Data Mask

**Free**, and separate from Shield despite being discussed alongside it.

Installed as a managed package, it masks personal data in sandboxes:

```
Anonymization      random values
Pseudonymization   realistic fake values, preserving format
Deletion           the field is emptied
Pattern-based      format preserved, content changed
```

**A sandbox with real customer data is production data with weaker controls.** Data Mask addresses that, and it costs nothing beyond the configuration effort.

Running it from `SandboxPostCopy` means masking happens before anyone can access the data. See [[21.11 - Sandbox Strategy and Data Seeding]] and [[22.4 - Data Mask and Sandbox Data Privacy]].

## What to do without Shield

Most orgs do not have it, and a meaningful amount is available free.

**Classic Encryption** — an encrypted text field type, without Shield:

```
Field type: Text (Encrypted)
Masking:    full, last four visible, credit card format
```

Weaker than Platform Encryption, unavailable for standard fields, and it cannot be used in most functionality. Adequate for a single sensitive field, not for a data-protection strategy.

**`LoginHistory`** for authentication forensics:

```sql
SELECT UserId, LoginTime, SourceIp, Application, ApiType, ApiVersion, Status
FROM LoginHistory WHERE LoginTime = LAST_N_DAYS:30
```

**`SetupAuditTrail`** for configuration changes, retained six months:

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail WHERE CreatedDate = LAST_N_DAYS:30
```

**Standard field history** on the fields that matter.

**A custom logging framework** for application-level visibility, which covers the largest gap Event Monitoring would otherwise fill. See [[20.5 - Custom Logging Frameworks]].

**Login IP ranges, session settings, and MFA**, all free and all more impactful than encryption for most threat models. See [[03.14 - Login Policies, MFA and Session Security]].

**The honest position:** an org without Shield that has enforced MFA, scoped its integration users, and enforces sharing correctly in Apex is more secure than one with Shield that has not.

## Deciding whether to buy it

**Buy Shield when:**

- A regulation or contract requires customer-managed encryption keys
- Field history must be retained beyond 18 months
- Forensic visibility into data access is a stated requirement
- The org handles data where a breach carries regulatory penalty
- Security review or audit has named a gap Shield closes

**Do not buy it when:**

- It is being purchased as a general answer to "we need security"
- The basics are not in place — MFA, scoped integration users, sharing enforcement
- Nobody will configure Transaction Security or read the event logs
- The requirement is access control, which sharing already provides

**The failure mode worth naming:** Shield purchased, encryption enabled on a dozen fields, Event Monitoring never read, Transaction Security never configured, and a false sense that security is handled. That is expensive and it is common.

## Sequencing

If Shield is being adopted, the order that produces value fastest:

**1. Event Monitoring first.** It requires no functional change, produces immediate visibility, and informs everything else. Enabling the Event Monitoring Analytics App gives dashboards on day one.

**2. Transaction Security next.** A small number of high-value policies — large exports, suspicious logins.

**3. Field Audit Trail** where retention is required, since it is additive and low-risk.

**4. Platform Encryption last**, because it is the one with functional consequences and needs the most analysis.

Most implementations do this in reverse, starting with encryption because it sounds like the security feature — and then spend weeks discovering which reports broke.

## What this section covers

Platform Encryption and its functional tradeoffs, Field Audit Trail, Data Mask, secure Apex coding against the OWASP categories, compliance patterns for GDPR and HIPAA, the AppExchange security review, and a threat-modelling approach for an org.

**The theme:** most Salesforce security failures are not encryption failures. They are a missing sharing keyword, a guest user profile with too much access, an integration user with System Administrator, or an `@AuraEnabled` method trusting a record Id from the client.
