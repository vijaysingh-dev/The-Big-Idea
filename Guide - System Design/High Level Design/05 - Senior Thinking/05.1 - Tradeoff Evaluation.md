# Tradeoff Evaluation

> **Revision tags:** #senior-thinking #tradeoffs  
> **Related:** [[05.2 - Failure First Thinking]] | [[02.4 - Architecture Decisions]]

---

## Why Tradeoffs Are the Job

Every architecture decision is a tradeoff. There is no globally optimal choice — only the best fit for your context: scale, team size, operational maturity, latency requirements, and budget.

A senior engineer is not someone who knows the right answers. They're someone who knows which questions to ask, what the real constraints are, and how to reason transparently about the choices being made.

Interviewers aren't looking for the "correct" architecture. They're looking for your reasoning process.

---

## The Tradeoff Evaluation Framework

When facing an architectural decision, work through five lenses:

```
1. What problem does each option solve?
2. What does each option cost? (performance, ops burden, money, complexity)
3. What does each option break or make harder?
4. What's the reversibility? (easy to change vs locked in)
5. What's the right choice given the actual constraints?
```

Never evaluate Option A in isolation. Always compare.

## The Most Common Tradeoff Pairs

### Consistency vs Availability

The fundamental distributed systems tension (CAP theorem).

```
Strong consistency:
  + Correct data always, no stale reads
  - Higher latency (coordination required)
  - Less available during network partition
  Use for: payments, inventory counts, leader election

Eventual consistency:
  + Lower latency, higher availability
  - Stale reads possible
  - Conflict resolution complexity
  Use for: social feeds, product ratings, DNS
```

**The nuance:** It's not binary. Use strong consistency for operations where staleness causes harm. Use eventual consistency everywhere else.

---

### Latency vs Throughput

They're related but not the same.

```
Optimizing for latency (single-request speed):
  - Synchronous processing
  - In-memory caching
  - Read replicas nearby
  - Pre-computation
  Cost: more infrastructure, higher memory usage

Optimizing for throughput (requests/second):
  - Batching
  - Async processing
  - Write buffering
  - Connection pooling
  Cost: higher individual request latency
```

A payment processing UI needs **latency** (user waits for result).  
A metrics ingestion pipeline needs **throughput** (1M events/sec, each can wait 5s).

---

### Simplicity vs Resilience

```
Simple system (monolith, synchronous, single DB):
  + Easy to understand, debug, deploy
  + Fewer moving parts = fewer failure modes
  - Single point of failure
  - All-or-nothing failure blast radius

Resilient system (microservices, async, replicated):
  + Fault isolation, graceful degradation
  + Independent scaling per component
  - Distributed systems complexity
  - Harder to debug end-to-end failures
```

**Senior engineer instinct:** Don't add resilience complexity before you need it. A monolith with good backups is more reliable than a poorly implemented microservices architecture.

---

### Cost vs Performance

```
Higher performance:
  - More replicas → higher availability, more cost
  - Larger instances → lower latency, more cost
  - More cache → fewer DB hits, more memory cost
  - Multi-region → lower global latency, 2-3× infra cost

Lower cost:
  - Fewer replicas → lower availability
  - Smaller instances → possible performance bottleneck
  - Less cache → more DB load
  - Single region → higher latency for distant users
```

**The senior move:** Quantify the cost difference before deciding. "A second Redis replica is $X/month. The P-0 incident we'd avoid from Redis downtime costs $Y in SLA violations. Y >> X → add the replica."

---

### Flexibility vs Efficiency

```
Flexible design (generic, extensible):
  + Easy to change requirements
  + New use cases supported without redesign
  - Over-engineered if requirements are stable
  - Abstractions add indirection and complexity

Efficient design (purpose-built, specific):
  + Maximum performance for the known use case
  + Simpler code, fewer abstractions
  - Hard to adapt when requirements change
  - May need full rewrite for new use cases
```

Start with flexibility when the domain is new or unstable. Optimize for efficiency when the access pattern is known and stable.

## How to Frame Tradeoffs in Conversations

**In an interview:**

Don't say: "I'll use Kafka."  
Say: "I'm choosing Kafka over SQS here because we need replay capability for the analytics consumer. The tradeoff is operational complexity — we'd need to manage a Kafka cluster. If replay weren't required, I'd use SQS for simplicity."

**Template:**
```
I'm choosing [Option A] over [Option B] because [primary benefit for our context].
The tradeoff is [what we give up].
This is acceptable because [why the tradeoff is worth it].
If [constraint changed], I'd reconsider [option B].
```

## The Three Questions Before Any Decision

1. **What's the scale?** — Solutions that work at 1K RPS are wrong at 1M RPS, and vice versa.
2. **What's the failure mode?** — Is it better to be slow or wrong? Available or consistent?
3. **Who operates this?** — A 5-person team can't maintain a 30-service microservices architecture.

---

## Tradeoff Anti-Patterns

**Resume-driven architecture:** Choosing Kafka/Kubernetes/microservices because they look impressive, not because the problem requires them.

**Premature optimization:** Adding sharding, caching layers, and CDNs before measuring whether the simpler solution is too slow.

**False precision:** "Our p99 will be exactly 47ms with this design." Real systems have too many variables for that level of certainty. Say: "We expect sub-100ms p99 based on similar systems."

**Ignoring operational cost:** "We'll use Kafka." Who manages it? Who debugs it at 2 AM? A managed service (Confluent Cloud, AWS MSK) costs more but shifts operational burden.

**Local optimization:** Optimizing one component in isolation while ignoring the system bottleneck. Add read replicas while the bottleneck is actually the application CPU.

## The Reversibility Principle

Not all decisions are equal. Prioritize getting reversible decisions right over agonizing over irreversible ones — and vice versa for truly locked-in choices.

```
Easily reversible (optimize later, decide quickly):
  - Which internal API contract to use
  - Deployment configuration
  - Cache TTL values
  - Feature flag state

Hard to reverse (decide carefully, involve the team):
  - Primary database engine (PostgreSQL vs Cassandra)
  - Communication protocol between services (REST vs events)
  - Multi-tenancy model (shared DB vs per-tenant DB)
  - Data model (schema changes at 1B rows are painful)
```

Jeff Bezos calls these Type 1 (one-way door) vs Type 2 (two-way door) decisions. Move fast on Type 2. Slow down for Type 1.
