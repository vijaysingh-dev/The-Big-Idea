# Permission Sets and Permission Set Groups

## What they are

A permission set is a bundle of permissions that can be assigned to any number of users, on top of their profile. A user has one profile and any number of permission sets.

They grant the same kinds of things a profile does — object permissions, field-level security, system permissions, Apex class access, record type availability — and they combine **additively**. If the profile grants Read and a permission set grants Edit, the user has Edit.

There is no subtraction. A permission set cannot take away what a profile granted. That asymmetry is why the recommended model is a minimal profile plus additive permission sets.

## The design pattern that works

Build permission sets around **capabilities**, not around people or teams.

Bad, because it does not compose:

```
Sales Rep Europe Permission Set
Sales Rep Asia Permission Set
Senior Sales Rep Permission Set
```

Good, because any user can be assembled from the pieces:

```
Opportunity Management          create, read, edit opportunities and line items
Opportunity Deletion            delete opportunities
Discount Approval               access to approval-related fields and the approval action
Warranty Claim Processing       full access to the claim objects
Warranty Claim Approval         edit the approved amount field
Reporting Access                create and edit reports and dashboards
Data Export                     export reports, weekly export
```

A European sales rep gets Opportunity Management and Reporting Access. A senior rep adds Discount Approval and Opportunity Deletion. A service coordinator gets Warranty Claim Processing. Nobody needs a new profile, and granting one person one extra capability is a single assignment.

The test for a well-designed permission set: its name describes something a person *does*, and it contains only what is needed to do that.

## Permission set groups

Once you have granular permission sets, assigning eight of them to every new hire becomes tedious. **Permission set groups** bundle permission sets into a role-shaped package.

```
Permission Set Group: Sales Representative
    Opportunity Management
    Account and Contact Management
    Reporting Access
    Campaign Participation

Permission Set Group: Service Coordinator
    Warranty Claim Processing
    Case Management
    Knowledge Reader
    Reporting Access
```

Assign one group per role. The underlying permission sets stay reusable across groups — Reporting Access appears in both, defined once.

This is the structure that scales: granular permission sets as the building blocks, groups as the job-shaped assemblies, minimal profiles underneath.

## Muting

Permission set groups introduce the one genuinely subtractive mechanism in the model.

Because permission sets combine additively, a group can grant more than intended. A group might include a permission set that grants Delete on Opportunity, when this particular role should not have it — but that permission set is used elsewhere and cannot be changed.

A **muting permission set** attached to the group removes specific permissions from the group's combined result.

```
Permission Set Group: Junior Sales Representative
    Opportunity Management
    Account and Contact Management
    Reporting Access
    Muting: Junior Restrictions
        mutes Delete on Opportunity
        mutes Export Reports
```

The muting applies only within that group. The same permission sets used in another group are unaffected.

Two cautions. Muting only affects permissions granted *by that group* — a permission granted by the user's profile or by a separately assigned permission set is not muted. And heavy use of muting is usually a signal that the underlying permission sets are too coarse; the cleaner fix is often to split them.

## Assignment, including time-limited access

Assignment is a record on `PermissionSetAssignment`, which means it is queryable and can be automated.

```sql
SELECT Assignee.Name, PermissionSet.Label, PermissionSet.IsOwnedByProfile, ExpirationDate
FROM PermissionSetAssignment
WHERE PermissionSet.Name = 'Warranty_Claim_Approval'
  AND Assignee.IsActive = true
```

Note `PermissionSet.IsOwnedByProfile` — every profile has a hidden permission set behind it, which is why this object returns more rows than expected. Filter it out when auditing real assignments.

**Expiring assignments** are a genuinely useful feature: a permission set can be assigned with an end date, after which it is removed automatically. This is the correct mechanism for temporary elevated access — a contractor, a quarter-end close, a migration window — instead of granting access and hoping someone remembers to revoke it.

Assigning in Apex, which is how automated provisioning works:

```java
public with sharing class PermissionProvisioningService {

    public static void grantTemporaryApproval(Set<Id> userIds, Date expiresOn) {
        PermissionSet approvalSet = [
            SELECT Id FROM PermissionSet WHERE Name = 'Warranty_Claim_Approval' LIMIT 1
        ];

        Set<Id> alreadyAssigned = new Set<Id>();
        for (PermissionSetAssignment existing : [
            SELECT AssigneeId FROM PermissionSetAssignment
            WHERE PermissionSetId = :approvalSet.Id AND AssigneeId IN :userIds
        ]) {
            alreadyAssigned.add(existing.AssigneeId);
        }

        List<PermissionSetAssignment> toCreate = new List<PermissionSetAssignment>();
        for (Id userId : userIds) {
            if (!alreadyAssigned.contains(userId)) {
                toCreate.add(new PermissionSetAssignment(
                    AssigneeId = userId,
                    PermissionSetId = approvalSet.Id,
                    ExpirationDate = expiresOn
                ));
            }
        }

        if (!toCreate.isEmpty()) {
            insert toCreate;
        }
    }
}
```

`PermissionSetAssignment` is a setup object, so this cannot share a transaction with DML on normal objects. See [[10.7 - Mixed DML and Setup Objects]].

## Permission set licenses

Some permission sets require a **permission set license** — a separately purchased entitlement for a specific feature, such as CRM Analytics, Sales Console, or Identity Connect.

The failure mode: the permission set exists, it is assigned, and the feature still does not work, because the license was not assigned to the user. Check `PermissionSetLicenseAssign` when this happens.

## Auditing with permission sets

One of the strongest practical arguments for this model is that it makes auditing possible. Object permissions across both profiles and permission sets live in one queryable object:

```sql
SELECT Parent.Label, Parent.Profile.Name, SobjectType,
       PermissionsRead, PermissionsEdit, PermissionsDelete,
       PermissionsModifyAllRecords
FROM ObjectPermissions
WHERE SobjectType = 'Warranty_Claim__c'
  AND (PermissionsDelete = true OR PermissionsModifyAllRecords = true)
```

Field-level security similarly:

```sql
SELECT Parent.Label, Field, PermissionsRead, PermissionsEdit
FROM FieldPermissions
WHERE SobjectType = 'Warranty_Claim__c' AND Field = 'Warranty_Claim__c.Approved_Amount__c'
```

Answering "who can edit the approved amount" with a query, rather than by opening forty profiles, is the difference between an org that can pass an audit and one that cannot.

## Migrating an existing org

Orgs built on profiles can be moved gradually, and the sequence that works:

1. Create a minimal profile for each license type
2. For each existing profile, identify the distinct capabilities it grants
3. Build permission sets for those capabilities, reusing across profiles where they overlap
4. Build permission set groups matching the current profiles
5. Move users to the minimal profile plus the appropriate group, in waves
6. Retire the old profiles once no users remain on them

Step 3 is where the value appears, because the overlap between profiles is usually large and most capabilities are shared.

## Practical guidance

**Name permission sets by capability, in a consistent format.** `Opportunity_Management`, `Warranty_Claim_Approval`. A name that describes a job title is a group, not a permission set.

**Keep them small.** A permission set granting access to fifteen objects is doing too much and cannot be reused.

**Use expiring assignments for anything temporary.** Elevated access that has to be manually revoked usually is not.

**Do not create a permission set per field.** The granularity should match how permissions are actually granted, and that is usually at the level of a task, not a field.

**Prefer permission sets in source control over profiles.** They retrieve completely and deploy predictably, which profiles do not.
