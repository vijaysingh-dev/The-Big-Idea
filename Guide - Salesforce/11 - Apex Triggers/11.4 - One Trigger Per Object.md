# One Trigger Per Object

## The rule

**One trigger per object.** It routes to a handler class and contains nothing else.

This is close to universal in the Salesforce ecosystem, and the reason is specific rather than aesthetic.

## Why: order is not controllable

When two triggers exist on the same object, **the order in which they execute is not defined**. Salesforce does not guarantee it, does not expose a setting for it, and can change it.

```java
trigger ClaimValidationTrigger on Warranty_Claim__c (before update) {
    // sets Approval_Tier__c
}

trigger ClaimRoutingTrigger on Warranty_Claim__c (before update) {
    // reads Approval_Tier__c to choose an approver
}
```

If routing runs first, it reads a stale tier. Nothing errors. The claim is routed to the wrong approver, and the defect appears intermittently in production while working consistently in the sandbox.

Worse, the order can change after a deployment, a release, or a metadata reorganization. Code that worked for two years starts failing with no change to it.

Flows at least have an explicit `Flow Trigger Order` setting ([[07.3 - Record-Triggered Flows]]). Triggers have nothing equivalent.

**With one trigger, order is the order of statements in the handler.** Explicit, visible, and under your control.

## The other reasons

**Debuggability.** "What runs when a claim is saved" has one answer, in one file.

**Recursion control.** A single entry point makes a guard reliable. Several triggers each guarding independently interact in ways nobody can reason about.

**Bypass.** Disabling automation during a migration means one switch, not several.

**Limits.** Each trigger queries independently. Consolidating lets one query serve every concern.

**Reviewability.** A pull request touching the one handler shows the full picture of what changed about the object's behaviour.

## The shape

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    WarrantyClaimTriggerHandler.run();
}
```

Three lines. Every production trigger in the org looks like this, differing only in the object name and the event list.

The handler does the dispatching, covered in [[11.5 - Trigger Handler Pattern]].

## Ordering inside the handler

Once consolidated, ordering becomes a deliberate decision rather than an accident.

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (AutomationBypass.isBypassed('WarrantyClaim')) {
            return;
        }

        switch on Trigger.operationType {
            when BEFORE_UPDATE {
                // order matters: derived fields first, then routing that reads them,
                // then validation that checks the result
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
                ClaimRoutingService.assignApprover(Trigger.new, Trigger.oldMap);
                ClaimValidationService.validate(Trigger.new, Trigger.oldMap);
            }
            when AFTER_UPDATE {
                ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
                ClaimRollupService.recalculate(
                    ClaimService.affectedAssetIds(Trigger.new, Trigger.oldMap)
                );
            }
        }
    }
}
```

The comment naming the dependency is worth its space here, because the ordering constraint is real and a future edit could reorder these without realizing.

## Migrating an org with several triggers

Common in an inherited org, and the sequence that works:

**1. Inventory.**

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status, LengthWithoutComments FROM ApexTrigger ORDER BY TableEnumOrId, Name" \
  --target-org production
```

Any object with more than one active trigger is a candidate, and `LengthWithoutComments` shows which contain business logic rather than routing.

**2. Write characterization tests first.** Before changing anything, write tests asserting the *current* behaviour — the fields that get set, the records that get created. These become the regression suite, and they should pass identically before and after.

This step is the one that gets cut and the one that makes the migration safe. Without it, consolidation is a rewrite with no way to verify equivalence.

**3. Move logic out of each trigger into service classes**, one at a time, leaving the triggers in place calling the new services. Tests should still pass.

**4. Create the single trigger and handler**, calling the services in a deliberate order.

**5. Deactivate the old triggers** by setting `status` to `Inactive` in their metadata and deploying. Do not delete yet.

**6. Verify** in production for a full business cycle.

**7. Delete** the old triggers.

Deactivating before deleting means a rollback is a one-line metadata change rather than a redeployment of code that no longer exists.

## When a second trigger is unavoidable

Rare, and there is one legitimate case: **a managed package installs its own trigger on an object you also trigger on.**

You cannot consolidate with it, and its order relative to yours is not controllable. What you can do:

**Find out what it does.** The package documentation, or observation in a sandbox.

**Do not depend on its output** within the same save. If your logic needs a field the package sets, the dependency is unreliable — move your work to an after-update handler that reacts to the field changing, or to an async job.

**Watch the limit budget.** The package's queries and DML come out of the same allowance as yours. A package consuming 80 queries leaves you 20.

This is one of the practical costs of managed packages, and it is worth knowing before installing one on a heavily automated object. See [[01.7 - Salesforce Clouds Overview]].

## Objects that need no trigger at all

Worth stating, because the one-trigger rule is sometimes read as an instruction to create one everywhere.

If the object's automation is entirely declarative — a before-save flow for field defaults, a validation rule, a native roll-up — it needs no trigger. Creating an empty trigger "for consistency" adds a file, a test coverage requirement, and a thing to maintain.

Create the trigger when there is logic that genuinely needs Apex.

## Testing the consolidated handler

The handler is the single entry point, so its test should exercise every event.

```java
@IsTest
private class WarrantyClaimTriggerHandlerTest {

    @IsTest
    static void insertSetsDerivedFieldsInBulk() {
        List<Asset> assets = TestDataFactory.createAssets(50);

        List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
        for (Integer i = 0; i < 200; i++) {
            claims.add(new Warranty_Claim__c(
                Asset__c = assets[Math.mod(i, 50)].Id,
                Claim_Amount__c = 600000,
                Claim_Date__c = Date.today(),
                Status__c = 'Submitted'
            ));
        }

        Test.startTest();
        insert claims;
        Test.stopTest();

        List<Warranty_Claim__c> saved = [
            SELECT Approval_Tier__c, Region__c FROM Warranty_Claim__c WHERE Id IN :claims
        ];
        Assert.areEqual(200, saved.size(), 'All claims should save');
        Assert.areEqual('Executive', saved[0].Approval_Tier__c, 'Tier should be derived on insert');
        Assert.isNotNull(saved[0].Region__c, 'Region should be stamped from the asset account');
    }

    @IsTest
    static void bypassPreventsAllHandlerWork() {
        AutomationBypass.bypass('WarrantyClaim');

        Warranty_Claim__c claim = TestDataFactory.buildClaim(600000);

        Test.startTest();
        insert claim;
        Test.stopTest();

        Warranty_Claim__c saved = [
            SELECT Approval_Tier__c FROM Warranty_Claim__c WHERE Id = :claim.Id
        ];
        Assert.isNull(saved.Approval_Tier__c, 'Bypass should prevent derived field assignment');
    }
}
```

Two hundred records across fifty assets is deliberate — several claims per asset, which is exactly the case a naive roll-up gets wrong.

Testing the bypass explicitly matters because it is the mechanism you will rely on during an incident, and an untested bypass that does not work is worse than none.

## Practical guidance

**One trigger per object**, three lines, routing to a handler.

**Declare the events explicitly** and keep the convention consistent across the org.

**Order services deliberately in the handler**, and comment the dependency where one exists.

**Write characterization tests before consolidating** an org with several triggers.

**Deactivate before deleting** during a migration.

**Do not depend on a managed package trigger's output** within the same save.

**Do not create a trigger where declarative automation suffices.**
