# Async Concurrency Patterns

The combinators in [[04.5 - Promise Combinators]] handle fixed, small sets of promises. Production code needs more: bounded parallelism, retries, deduplication, sequencing, and queues. These are the patterns worth having memorized.

## Concurrency limiting

Firing a thousand requests at once produces rate-limit errors, memory pressure and unpredictable latency. Bound it:

```js
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  const executing = new Set();

  for (const [index, item] of items.entries()) {
    const task = Promise.resolve()
      .then(() => fn(item, index))
      .then(value => { results[index] = value; });

    executing.add(task);
    task.finally(() => executing.delete(task));

    if (executing.size >= limit) await Promise.race(executing);
  }

  await Promise.all(executing);
  return results;
}

const users = await mapLimit(ids, 5, id => fetchUser(id));
```

`Promise.race` over the in-flight set is the idiom for "wait until any one slot frees". Writing results by index preserves input order regardless of completion order.

Note that a rejection here propagates out of the `await Promise.race(...)` and abandons the remaining items. If partial success is acceptable, wrap `fn` so it returns a settled-style result rather than rejecting.

The production equivalent is `p-limit`, which does the same thing with proper error and queue semantics.

## Retry with exponential backoff and jitter

```js
async function retry(fn, { attempts = 3, baseDelay = 300, signal } = {}) {
  for (let attempt = 0; attempt < attempts; attempt++) {
    try {
      return await fn({ signal });
    } catch (err) {
      const isLast = attempt === attempts - 1;
      if (isLast || !isRetryable(err) || signal?.aborted) throw err;

      const backoff = baseDelay * 2 ** attempt;
      const jitter = Math.random() * backoff * 0.3;
      await delay(backoff + jitter, { signal });
    }
  }
}

function isRetryable(err) {
  if (err.name === "AbortError") return false;
  if (err instanceof TypeError) return true;              // network failure
  return err.status >= 500 || err.status === 429;
}
```

Three details that separate a real implementation from a naive one:

**Only retry retryable failures.** A 400 or 404 will fail identically every time; retrying wastes time and hides the bug. 5xx, 429 and network errors are worth retrying.

**Exponential backoff.** Retrying immediately on a struggling server makes the outage worse — the classic retry storm.

**Jitter.** Without random spread, every client that failed at the same moment retries at the same moment. Randomizing the delay by ±30% desynchronizes them. This is the part people forget and it is the reason AWS documents it prominently.

Also respect `Retry-After` when the server sends it on a 429 or 503 — an explicit instruction beats your backoff calculation.

## Request deduplication

Multiple components asking for the same data should produce one request:

```js
function createDeduper(fn) {
  const inFlight = new Map();

  return (key, ...args) => {
    if (!inFlight.has(key)) {
      inFlight.set(key, Promise.resolve(fn(key, ...args)).finally(() => inFlight.delete(key)));
    }
    return inFlight.get(key);
  };
}

const getUser = createDeduper(id => fetch(`/api/users/${id}`).then(r => r.json()));
```

This works because a promise can have any number of consumers and settles once ([[04.2 - Promises from First Principles]]). Deleting on `finally` means only *in-flight* requests are shared, not results — caching results is a separate concern ([[24.7 - Caching Stale Time and Invalidation]]).

One caution: if any consumer aborts the shared request, all of them lose it. Deduplication and cancellation interact badly unless you reference-count.

## Sequential queue

When operations must not overlap — saving a document, applying edits, writing to IndexedDB:

```js
function createQueue() {
  let tail = Promise.resolve();

  return task => {
    const result = tail.then(task);
    tail = result.catch(() => {});  // a failure must not break the chain
    return result;
  };
}

const enqueue = createQueue();
enqueue(() => save(doc1));
enqueue(() => save(doc2)); // runs after doc1 finishes
```

The `catch(() => {})` on `tail` is essential. Without it, one failed task rejects the tail and every subsequent task is skipped. The caller still sees the rejection through `result`.

## Latest-wins (switch)

For search-as-you-type, only the newest request's result should be applied:

```js
function createLatest(fn) {
  let currentId = 0;
  let controller;

  return async (...args) => {
    const id = ++currentId;
    controller?.abort();
    controller = new AbortController();

    const result = await fn(...args, { signal: controller.signal });
    if (id !== currentId) return;  // superseded
    return result;
  };
}
```

Both guards are needed: the abort stops the network work, and the id check protects against a response that had already resolved before the abort landed ([[04.6 - AbortController and Cancellation]]).

## Async iteration for streams

When results arrive over time rather than all at once — paginated APIs, server-sent events, streamed responses:

```js
async function* paginate(url) {
  let next = url;
  while (next) {
    const page = await fetch(next).then(r => r.json());
    yield* page.items;
    next = page.nextUrl;
  }
}

for await (const item of paginate("/api/items")) {
  process(item);
  if (shouldStop) break;  // breaking stops fetching further pages
}
```

The consumer controls the pace, and `break` genuinely halts the producer — the generator is suspended and never resumes ([[06.6 - Iterators and Generators]]). That backpressure is impossible with `Promise.all` over a page count.

## How senior engineers actually use this

**They never write an unbounded `Promise.all` over user-sized data.** Any collection whose length is not known at author time gets a concurrency limit.

**They put retry in the API layer, not at call sites.** One retry policy, one place to tune it, one place to add metrics. Scattered retries multiply — a retry inside a retry gives you nine attempts instead of three.

**They make idempotency a precondition for retry.** Retrying a POST that creates an order can create two orders. Either the endpoint accepts an idempotency key or the operation is not retryable ([[15.1 - HTTP Fundamentals]]).

**They reach for a library once the requirements are real.** `p-limit`, `p-retry`, `p-queue` handle edge cases you will otherwise rediscover. Writing them once is a good exercise; shipping your own is usually not worth the maintenance.

## Common pitfalls

- Retrying non-idempotent operations, or retrying 4xx errors.
- Backoff without jitter, producing synchronized retry storms.
- A queue whose chain breaks permanently after the first rejection.
- Deduplication that caches forever, so stale data is served indefinitely.
- Latest-wins implemented with only an abort and no id check, leaving a narrow race window.
- Nested retry layers multiplying attempt counts.

## Interview angle

These are staple machine-coding problems: "implement a function that runs N promises with at most K concurrent", "implement retry with exponential backoff", "implement a task queue that runs sequentially". Write the core loop, then volunteer the production concerns — jitter, retryable-error classification, idempotency, and what happens when one task rejects. The unprompted edge cases are what the question is actually measuring.
