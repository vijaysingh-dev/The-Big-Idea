# Task Design Rules

#backend #queues #celery #design

> **In one line:** A task will run twice, run late, run against changed data, and run on a worker deployed from a different commit — design it so that all four are fine.

---

## The Idea

A function becomes a task and its execution context changes completely.

| In a request | As a task |
|---|---|
| Runs immediately | Runs in seconds, or hours |
| Runs once | May run twice |
| Same deployed code | Producer and worker may differ |
| Data is fresh | Data may have changed |
| A user is waiting | Nobody is watching |
| Failure returns a 500 | Failure is a log line |

💡 **Every rule below follows from one of those six differences.** They are not stylistic preferences; each one is a bug that happens without it.

---

## Rule 1: Pass IDs, Not Objects

```python
# ⚠️ Wrong
process_document.delay(document=doc)

# Right
process_document.delay(document_id=doc.id)
```

Four reasons, and any one is sufficient:

| Reason | |
|---|---|
| **Serialisation** | An ORM object does not serialise to JSON cleanly |
| **Staleness** | The object may have changed between enqueue and execution |
| **Message size** | A large object is copied on every retry ([[08.2 - Queue Semantics]]) |
| **Freshness** | The worker reads current state, which is almost always what you want |

⚠️ **The staleness case is the subtle one.** A task carrying a document object with `status='pending'` will still see `pending` when it runs an hour later, even if the document was archived in between.

```python
@app.task
def process_document(document_id: str):
    doc = repo.get(document_id)
    if doc is None or doc.deleted_at:
        return                              # gone since enqueue. Fine
    if doc.status != "pending":
        return                              # already handled
    ...
```

💡 **A task should re-read and re-validate its preconditions.** The world moved while it was queued, and the task must tolerate that.

## Rule 2: Make It Idempotent

```python
@app.task(acks_late=True)
def process_document(document_id: str):
    with db.transaction():
        claimed = db.execute(
            "INSERT INTO processed (key) VALUES ($1) ON CONFLICT DO NOTHING RETURNING key",
            f"process_document:{document_id}",
        )
        if claimed is None:
            return                          # already done
        do_the_work(document_id)
```

⚠️ **`acks_late=True` means at-least-once, which means duplicates.** A task that is not idempotent under `acks_late` will eventually double-charge, double-send or double-count.

Covered fully in [[07.5 - Idempotency Keys and Deduplication]]. The task-specific points:

**Prefer natural idempotency:**

```python
# Idempotent — absolute
repo.set_status(doc_id, "indexed")

# Not idempotent — relative
repo.increment_processed_count(org_id)
```

**Prefer a unique constraint over a dedup table:**

```sql
UNIQUE (document_id, chunk_index)      -- re-running the chunker inserts nothing new
```

💡 **The task-level question: if this task runs twice, what does a user see?** If the answer is "nothing different", you are done. If it is "two emails" or "a doubled counter", you need a mechanism.

## Rule 3: Keep It Short

```python
# ⚠️ One 45-minute task
@app.task
def ingest_source(source_id: str):
    for doc in fetch_all_documents(source_id):     # 10,000 documents
        process(doc)
```

| Problem | |
|---|---|
| A failure at 90% redoes everything | ([[08.1 - Why Background Work Exists]]) |
| Exceeds the visibility timeout | Duplicate execution ([[08.4 - Brokers and Result Backends]]) |
| Blocks a worker slot for 45 minutes | Throughput collapses |
| Killed on every deploy | Grace periods are not 45 minutes |
| No progress visibility | "Running" for 45 minutes |

```python
@app.task
def ingest_source(source_id: str):
    for doc_id in fetch_document_ids(source_id):
        process_document.delay(doc_id)      # fan out
```

💡 **The coordinator task's only job is to enqueue.** It runs in seconds, is trivially retryable, and — if the enqueue is idempotent — retrying it is harmless.

**Target: tasks under 60 seconds.** Above that, look for a way to split. Above five minutes, it is almost certainly wrong.

⚠️ **Do not over-split.** Twenty 2-second tasks pay twenty times the queueing, serialisation and state-transition overhead. **Find the granularity where the overhead is under a few percent** — usually 10–60 seconds.

## Rule 4: Handle Missing and Changed State

```python
@app.task(bind=True, max_retries=3)
def send_notification(self, user_id: str, document_id: str):
    user = repo.get_user(user_id)
    if user is None:
        return                              # deleted. Not an error

    doc = repo.get_document(document_id)
    if doc is None:
        return

    if not can_access(user, doc):
        return                              # permission revoked since enqueue

    send(user, doc)
```

⚠️ **A task that raises on missing state will retry three times and land in the DLQ**, generating an alert for something that is not a problem.

💡 **Distinguish "gone" from "broken".** A deleted entity is a normal outcome and should return quietly. A database connection failure is an error and should retry.

**The permission re-check is the one people forget**, and it is a security issue: a notification enqueued when a user had access, delivered after it was revoked.

## Rule 5: Distinguish Permanent from Transient Failures

```python
@app.task(bind=True, max_retries=5)
def sync_source(self, source_id: str):
    try:
        return do_sync(source_id)

    except (ConnectionError, TimeoutError, RateLimitError) as e:
        raise self.retry(exc=e, countdown=backoff(self.request.retries))

    except (InvalidCredentials, SourceDeleted, MalformedConfig) as e:
        mark_failed(source_id, reason=str(e))
        return                              # ⚠️ do NOT retry

    except Exception:
        raise                               # unknown — retry, then DLQ
```

💡 **Retrying a permanent failure is pure waste** — five attempts with exponential backoff over ten minutes, arriving at exactly the same result, and delaying the alert that would have told someone.

⚠️ **The `except Exception` branch matters.** An unknown exception should retry — it might be transient — and then reach the DLQ where a human sees it. Swallowing unknowns is how bugs stay hidden.

**Catalogue your exceptions.** Every task should have an explicit list of what is retryable, and everything else is either terminal or unknown.

## Rule 6: Version Your Tasks

⚠️ **During a rolling deploy, the producer and the worker are on different commits.**

```
Old workers running          New code deployed
Old worker receives a message for a task it does not know    → error
New worker receives a message with old-format arguments      → error
```

**The rules, which are [[05.13 - Contract Testing and Schema Evolution]] applied to tasks:**

```python
# ✅ Adding an optional parameter with a default
@app.task
def process_document(document_id: str, force: bool = False): ...

# ⚠️ Adding a required parameter
@app.task
def process_document(document_id: str, mode: str): ...     # old messages break

# ⚠️ Renaming a task
@app.task(name="app.tasks.process_document")               # pin the name explicitly
def process_doc(document_id: str): ...
```

💡 **Always pin the task name.** By default Celery derives it from the module and function path, so moving the function to another module silently changes its name — and every queued message for the old name becomes unroutable.

**The safe procedure for a breaking change:**

```
1. Deploy workers that understand BOTH old and new formats
2. Deploy producers emitting the new format
3. Wait for the old-format queue to drain
4. Remove old-format handling
```

⚠️ **Deleting a task while messages for it are still queued** produces `Received unregistered task of type` and the messages are rejected. **Drain first, delete after.**

## Rule 7: Set Explicit Limits

```python
@app.task(
    bind=True,
    acks_late=True,
    reject_on_worker_lost=True,
    max_retries=5,
    soft_time_limit=300,
    time_limit=360,
    autoretry_for=(ConnectionError, TimeoutError),
    retry_backoff=True,
    retry_backoff_max=600,
    retry_jitter=True,
)
def process_document(self, document_id: str): ...
```

⚠️ **Every one of these has a bad default:**

| Setting | Default | Why the default is wrong |
|---|---|---|
| `acks_late` | `False` | At-most-once. Tasks lost on worker kill |
| `max_retries` | 3 | Often fine, and should be deliberate |
| `time_limit` | None | **A hung task occupies a slot forever** |
| `retry_jitter` | `True` in recent versions | Without it, retries synchronise ([[03.4 - Idempotency and Safe Retries]]) |

💡 **Define a base task class so the defaults are yours, not Celery's:**

```python
class BaseTask(Task):
    acks_late = True
    reject_on_worker_lost = True
    max_retries = 5
    soft_time_limit = 300
    time_limit = 360
    retry_backoff = True
    retry_jitter = True

app.Task = BaseTask
```

**This is the highest-leverage ten lines in a Celery codebase.**

## Rule 8: Make Tasks Thin

```python
# ⚠️ Business logic inside the task
@app.task
def process_document(document_id: str):
    doc = repo.get(document_id)
    text = extract(doc.content)
    chunks = [text[i:i+500] for i in range(0, len(text), 500)]
    for i, c in enumerate(chunks):
        repo.save_chunk(document_id, i, c)
    repo.set_status(document_id, "indexed")
```

```python
# Thin task, testable logic
@app.task
def process_document(document_id: str):
    return DocumentProcessor(repo).process(document_id)
```

💡 **A task should be an adapter: deserialise arguments, call a domain service, translate exceptions.** The logic belongs in a plain class you can unit test without a broker, a worker or a Celery app.

**This is the same layering discipline as an HTTP handler** ([[05.1 - REST Done Properly]]) — the transport should be replaceable without touching the logic.

⚠️ **Logic inside tasks is why most Celery codebases are hard to test.** Testing requires `task_always_eager` or a real worker, both of which are slower and less precise than calling a function.

## In Production

### The task checklist

```
□  Arguments are IDs and primitives, JSON-serialisable
□  Idempotent, or has a dedup record
□  Under 60 seconds, or split
□  Re-reads and re-validates state
□  Re-checks permissions if it acts on behalf of a user
□  Returns quietly on missing entities
□  Explicit retryable vs terminal exception handling
□  Task name pinned explicitly
□  Time limits set
□  acks_late with idempotency
□  Logic in a domain service, not the task
□  Emits structured logs with the task ID and entity ID
```

### Logging and context

```python
@task_prerun.connect
def bind_context(task_id, task, args, kwargs, **_):
    structlog.contextvars.bind_contextvars(
        task_id=task_id,
        task_name=task.name,
        **{k: v for k, v in kwargs.items() if k.endswith("_id")},
    )
```

💡 **Binding the entity IDs into logging context means every log line from that task is searchable by document ID** — which is what you actually need when a customer asks why their document failed.

**Propagate the trace context too**, or your traces break at the queue boundary ([[12.3 - Instrumenting Conduit End to End]]):

```python
def enqueue_with_trace(task, **kwargs):
    carrier = {}
    TraceContextTextMapPropagator().inject(carrier)
    return task.apply_async(kwargs=kwargs, headers={"traceparent": carrier.get("traceparent")})
```

### Testing tasks

```python
# ⚠️ eager mode hides real behaviour
app.conf.task_always_eager = True
```

**`task_always_eager` executes tasks synchronously in-process.** It does not test serialisation, retries, time limits, or idempotency under concurrency.

```python
# Test the logic directly — fast, precise
def test_processor_handles_missing_document(repo):
    assert DocumentProcessor(repo).process("nonexistent") is None

# Test the task adapter — serialisation and error translation
def test_task_serialises(celery_app):
    sig = process_document.s(document_id="doc_42")
    assert json.dumps(sig.kwargs)          # must serialise

# Test with a real worker — integration only, few of these
def test_retry_on_transient(celery_worker):
    ...
```

💡 **Three layers, most tests at the first.** The domain service is where the logic is, and it needs no Celery at all.

**Test idempotency concurrently**, not sequentially ([[07.5 - Idempotency Keys and Deduplication]]).

### The task that kills workers

```python
@app.task(acks_late=True, reject_on_worker_lost=True)
def process_huge_document(document_id: str):
    content = repo.get_content(document_id)     # 2 GB → OOM
```

⚠️ **`reject_on_worker_lost` requeues it, the next worker OOMs, and you have a crash loop consuming your entire fleet.**

```python
@app.task(bind=True, max_retries=2)
def process_huge_document(self, document_id: str):
    size = repo.get_size(document_id)
    if size > MAX_PROCESSABLE:
        mark_failed(document_id, "too large")
        return                                   # terminal, no retry
    ...
```

💡 **Guard against the input that caused the crash, not just the crash.** `max_retries` bounds the damage; a precondition check prevents it.

**This is the "poison message" case and it is the strongest argument for a DLQ** ([[08.6 - Retries Backoff and Dead Letters]]).

### Conduit's task inventory

| Task | Duration | Idempotency | Retryable failures |
|---|---|---|---|
| `sync_source` | ~5s (fans out) | Unique on `(source_id, run_id)` | Network, rate limit |
| `fetch_document` | ~10s | Unique on `(source_id, external_id)` | Network, 5xx |
| `extract_text` | ~15s | Absolute status write | OOM (bounded), parser errors |
| `chunk_document` | ~5s | Unique on `(doc_id, chunk_index)` | None — pure function |
| `embed_chunks` | ~30s | Unique on `(chunk_id, model_version)` | Rate limit, network |
| `index_chunks` | ~5s | Idempotent upsert | Search backend errors |
| `notify_collaborators` | ~2s | Dedup on `(user_id, doc_id, event)` | Provider errors |

💡 **Note that every one has a natural uniqueness constraint**, which means none of them needs a dedup table. **That is what good task design looks like** — idempotency falling out of the data model rather than being bolted on.

## Codebase

**Repo:** `onyx-dot-app/onyx`, `getsentry/sentry`, `celery/celery`

**Question to answer:** In Onyx's indexing pipeline, how does a task establish that its work has not already been done, and how does it handle a document that changed between enqueue and execution? Then: how does Sentry structure tasks so the logic is testable without a worker?

**Read, in order:**

1. `onyx/backend/onyx/background/celery/tasks/` — **the task definitions.** Note the granularity, the fan-out pattern, and the state re-reads at the start of each task
2. `onyx/backend/onyx/db/index_attempt.py` — **the state model.** This is how they track what has been done, and it is the idempotency mechanism
3. `sentry/src/sentry/tasks/` — **look at how thin the tasks are.** Most are a few lines calling into a service
4. `sentry/src/sentry/tasks/base.py` — **their base task decorator**, encoding the defaults this note argues for. Worth copying the idea
5. `celery/celery/app/task.py` — the `Task` class and every option, so you know what the base class can set

💡 Sentry's `instrumented_task` decorator is the pattern to steal: **one decorator applied to every task, setting retry policy, time limits, metrics and error reporting consistently.** Nobody has to remember the options, because the decorator has them.

**Size:** 1–2 sessions.
