# The Event Loop

The event loop is the mechanism that lets a single-threaded language handle thousands of concurrent operations without blocking. It is not part of JavaScript — it lives in the host runtime (the browser or Node), and it is specified in the HTML standard, not the ECMAScript standard.

Its job is embarrassingly simple. In pseudocode:

```
while (true) {
  if (callStack is empty) {
    task = oldest item in the task queue
    if (task) run task
    drain the entire microtask queue
    if (a frame is due) run rendering steps
  }
}
```

Everything else is detail on top of that loop.

## The pieces

**Call stack** — where synchronous code executes. One at a time. Covered in [[01.3 - The Call Stack]].

**Web APIs / host APIs** — timers, network, DOM events, file I/O. These run outside the JS thread, often on other threads the browser owns.

**Task queue (macrotask queue)** — callbacks waiting to be run: timer callbacks, event handlers, network completions.

**Microtask queue** — a separate, higher-priority queue: promise reactions, `queueMicrotask`, `MutationObserver`.

**Event loop** — the coordinator that moves work from the queues onto the stack, but only when the stack is empty.

```
    call stack
        |
        | empty?
        v
  +-------------+        +---------------------+
  | event loop  |<-------| microtask queue     |  drained fully
  +-------------+        +---------------------+
        ^                +---------------------+
        |----------------| task queue          |  one per turn
                         +---------------------+
                                  ^
                                  |
                         Web APIs (timers, fetch, DOM events)
```

## The critical rule

**A task runs to completion.** The event loop cannot interrupt running JavaScript. It only regains control when the stack empties.

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");

// 1, 4, 3, 2
```

Walk it through: `1` and `4` are synchronous and run immediately. `setTimeout` hands its callback to the timer API, which queues it as a task. `Promise.resolve().then` queues a microtask. When the synchronous script finishes and the stack empties, the loop drains microtasks first — `3` — then takes one task — `2`.

This ordering is the source of most "why did this log out of order" confusion, and is expanded in [[01.6 - Microtasks vs Macrotasks]].

## setTimeout(fn, 0) does not mean "now"

`setTimeout` specifies a *minimum* delay, not a guaranteed one. The callback is queued after the delay elapses and runs when the loop next picks up a task.

```js
setTimeout(() => console.log("timer"), 0);

const start = Date.now();
while (Date.now() - start < 2000) {}

console.log("blocking done");
// "blocking done" then "timer", roughly 2 seconds later
```

The timer fired on schedule. The callback simply could not run, because the stack was busy. Browsers also clamp nested timers to a 4 ms minimum after five levels of nesting, and throttle timers in background tabs to once per second or less.

## Blocking the loop is the main performance failure mode

Because rendering happens inside the same loop, any long-running JavaScript prevents painting and input handling. A 200 ms task means a 200 ms window where a click does nothing.

The browser aims for a frame every ~16.7 ms at 60 Hz. Work exceeding 50 ms is classified as a **long task** and is what degrades **INP** (Interaction to Next Paint, the responsiveness metric in Core Web Vitals — see [[13.5 - Core Web Vitals]]).

The standard fixes, in order of preference:

```js
// Yield between chunks so the loop can render and handle input
async function processInChunks(items, handler) {
  for (let i = 0; i < items.length; i++) {
    handler(items[i]);
    if (i % 100 === 0) await new Promise(r => setTimeout(r, 0));
  }
}
```

Better still on modern browsers, `scheduler.yield()` yields while keeping priority. Best of all, move genuinely heavy computation off the main thread entirely with a Web Worker ([[08.4 - Web Workers]]).

Note that `await` alone does **not** yield to rendering — it yields to the microtask queue, which is drained before the browser paints. Only a task boundary (a timer, a message, `scheduler.yield`) actually lets a frame through.

## Node's event loop differs

Node uses libuv and organizes its loop into named phases: timers, pending callbacks, poll, check, close. `setImmediate` runs in the check phase, `process.nextTick` runs before all promise microtasks. Browser code and Node code that both "use the event loop" therefore have different ordering guarantees. Do not port assumptions between them.

## How senior engineers actually use this

**They think in terms of "who owns the main thread right now".** Debugging jank starts with the Performance panel: record, find the long yellow scripting block, expand it, and identify what monopolized the thread.

**They budget interactions, not functions.** The target is that any user input produces a visible response within ~200 ms. That budget is spent across event handler, state update, re-render and paint, all on the same thread.

**They break work at task boundaries deliberately.** Large list transforms, JSON parsing of big payloads, and syntax highlighting are chunked or deferred, often via `useTransition` in React ([[22.4 - useTransition and startTransition]]), which is a scheduler built on exactly these primitives.

**They never poll with tight loops.** Waiting for a condition uses events or promises, never a `while` loop, because a `while` loop can never let the awaited work run.

## Common pitfalls

- Assuming `setTimeout(fn, 0)` runs immediately, or that timer delays are accurate.
- Adding an `await` and expecting the UI to repaint mid-function. Microtasks do not yield to rendering.
- Recursive `setTimeout` chains or promise loops that never let the queue drain, starving other work.
- Testing performance on a fast desktop. The loop's frame budget is the same everywhere, but the work per frame is four to six times slower on a mid-range phone. Use CPU throttling in DevTools.

## Interview angle

"Explain the event loop" is close to universal. A complete answer covers: one call stack, host APIs handle async work off-thread, completed work is queued, the loop moves queued work onto the stack only when it is empty, microtasks drain fully before the next task, and rendering happens between tasks. Following it with a concrete ordering example, then noting that long tasks block rendering, demonstrates you understand the consequence and not just the diagram.
