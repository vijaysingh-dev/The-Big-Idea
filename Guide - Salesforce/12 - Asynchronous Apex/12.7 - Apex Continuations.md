# Apex Continuations

## The narrow problem they solve

A user clicks a button. The component needs data from an external system that takes fifteen seconds to respond. The user must see the result.

A normal callout holds the Apex thread for those fifteen seconds, counting against the 120-second total callout limit and, more importantly, occupying a server thread. Salesforce also enforces a concurrency limit on long-running synchronous requests — more than ten requests running over five seconds each, per org, and new requests are rejected.

A **Continuation** releases the thread while waiting. The request is parked, the callout runs, and when the response arrives a callback method resumes with it.

This is the one async mechanism where the user is still waiting, which is what makes it different from everything else in this section.

## The shape

```java
public with sharing class ErpInventoryController {

    private static final String CALLOUT_LABEL = 'inventoryLookup';

    @AuraEnabled(continuation=true cacheable=true)
    public static Object getInventory(String serialNumber) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/inventory?serial='
            + EncodingUtil.urlEncode(serialNumber, 'UTF-8'));
        req.setMethod('GET');
        req.setTimeout(60000);

        Continuation con = new Continuation(60);
        con.continuationMethod = 'processResponse';
        con.state = serialNumber;
        con.addHttpRequest(req);

        // returning the Continuation parks the request; the thread is released
        return con;
    }

    @AuraEnabled
    public static InventoryResult processResponse(List<String> labels, Object state) {
        HttpResponse res = Continuation.getResponse(labels[0]);

        if (res.getStatusCode() != 200) {
            throw new AuraHandledException(
                'Inventory lookup failed: ' + res.getStatusCode()
            );
        }

        return InventoryResult.parse(res.getBody(), (String) state);
    }
}
```

Two methods. The first sets up the callout and returns the `Continuation`. The second receives the response.

`con.state` carries data between them, since they are separate invocations with no shared context.

The constructor argument is the timeout in seconds, up to 120.

## Calling it from a component

```javascript
import { LightningElement, api } from 'lwc';
import getInventory from '@salesforce/apex/ErpInventoryController.getInventory';

export default class InventoryLookup extends LightningElement {
    @api serialNumber;
    inventory;
    error;
    isLoading = false;

    async handleLookup() {
        this.isLoading = true;
        this.error = undefined;

        try {
            // the continuation is transparent to the client — this is an ordinary call
            this.inventory = await getInventory({ serialNumber: this.serialNumber });
        } catch (e) {
            this.error = e.body?.message ?? 'Lookup failed';
        } finally {
            this.isLoading = false;
        }
    }
}
```

The continuation is invisible to the client. It calls one method and gets one result, with the parking and resumption handled by the platform.

## Parallel callouts

Up to three requests can be added to one continuation, and they run in parallel.

```java
@AuraEnabled(continuation=true cacheable=true)
public static Object getAssetContext(String serialNumber) {
    Continuation con = new Continuation(60);
    con.continuationMethod = 'processAll';
    con.state = serialNumber;

    // three parallel calls, so total latency is the slowest rather than the sum
    con.addHttpRequest(buildRequest('/api/inventory?serial=' + serialNumber));
    con.addHttpRequest(buildRequest('/api/warranty?serial=' + serialNumber));
    con.addHttpRequest(buildRequest('/api/service-history?serial=' + serialNumber));

    return con;
}

@AuraEnabled
public static AssetContext processAll(List<String> labels, Object state) {
    AssetContext context = new AssetContext();
    context.serialNumber = (String) state;

    // labels come back in the order the requests were added
    context.inventory = parseInventory(Continuation.getResponse(labels[0]));
    context.warranty = parseWarranty(Continuation.getResponse(labels[1]));
    context.history = parseHistory(Continuation.getResponse(labels[2]));

    return context;
}
```

Three sequential five-second calls take fifteen seconds. Three parallel ones take five. This is the strongest practical argument for continuations beyond the thread-release benefit.

`addHttpRequest` returns a label you can capture explicitly, which is clearer than relying on list order when the requests are built conditionally.

## Chaining continuations

The callback can return another `Continuation`, which is how a dependent sequence works — call A, use its result to call B.

```java
@AuraEnabled
public static Object processFirst(List<String> labels, Object state) {
    HttpResponse res = Continuation.getResponse(labels[0]);
    String contractId = parseContractId(res.getBody());

    Continuation next = new Continuation(60);
    next.continuationMethod = 'processSecond';
    next.state = contractId;
    next.addHttpRequest(buildRequest('/api/contracts/' + contractId + '/coverage'));

    return next;
}
```

Up to three chained continuations. Beyond that, the design needs rethinking — a UI making four dependent calls is slow regardless of the mechanism, and the answer is usually a single composite endpoint on the external side.

## Limits

- **Up to 3 parallel callouts** per continuation
- **Up to 3 chained continuations**
- **120 seconds maximum timeout** per continuation
- **1 MB maximum response size**
- **No DML before the continuation** in the same request — the same rule as any callout after DML

That last one is the constraint that catches people. A controller method cannot save a record and then start a continuation. If the flow is "save, then fetch", it needs two client calls.

## Where continuations are not the answer

**Anything the user does not wait for.** A Queueable is simpler and has no client-side involvement. This is the overwhelming majority of integration work.

**Fast callouts.** A call returning in under a second gains nothing from a continuation and costs two methods and a state object. Use a normal callout.

**Triggers, batch jobs, or scheduled jobs.** Continuations are for user-initiated requests only.

**Work needing DML first.**

The honest summary: **continuations are a narrow tool.** Most orgs never need one. The situations where they earn their place are real-time lookups against a slow external system during a user interaction — an inventory check, a credit decision, an address validation against a slow service.

Before reaching for one, ask whether the data could be cached, synced in advance, or fetched asynchronously with the UI updating when it arrives. Those are usually better answers.

## Visualforce continuations

Continuations originated in Visualforce and the pattern differs:

```java
public with sharing class InventoryVfController {

    public String result { get; set; }
    private String requestLabel;

    public Object startRequest() {
        Continuation con = new Continuation(60);
        con.continuationMethod = 'processResponse';

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/inventory');
        req.setMethod('GET');
        requestLabel = con.addHttpRequest(req);

        return con;
    }

    public Object processResponse() {
        HttpResponse res = Continuation.getResponse(requestLabel);
        result = res.getBody();
        return null;   // null returns control to the page
    }
}
```

```html
<apex:page controller="InventoryVfController">
    <apex:form>
        <apex:commandButton action="{!startRequest}" value="Check Inventory" reRender="output"/>
        <apex:outputPanel id="output">{!result}</apex:outputPanel>
    </apex:form>
</apex:page>
```

Here the label is stored as an instance variable rather than passed to the callback, because the Visualforce controller instance persists across the continuation.

Worth recognizing in legacy code. New work uses the Lightning form.

## Testing

```java
@IsTest
static void continuationReturnsInventoryData() {
    Test.setMock(HttpCalloutMock.class, new InventorySuccessMock());

    Test.startTest();
    Continuation con = (Continuation) ErpInventoryController.getInventory('SN-88213');

    // the mock response is bound to the continuation's request label
    Map<String, HttpRequest> requests = con.getRequests();
    String label = new List<String>(requests.keySet())[0];

    HttpResponse mockResponse = new HttpResponse();
    mockResponse.setStatusCode(200);
    mockResponse.setBody('{"available":12,"warehouse":"Pune"}');
    Test.setContinuationResponse(label, mockResponse);

    Object result = Test.invokeContinuationMethod(
        new ErpInventoryController(), con
    );
    Test.stopTest();

    Assert.isNotNull(result, 'The callback should return a parsed result');
}
```

`Test.setContinuationResponse` and `Test.invokeContinuationMethod` are the specific test helpers. Testing continuations is more ceremony than testing an ordinary callout, which is another small argument against using them where a normal callout would do.

## Practical guidance

**Use a continuation only when the user is waiting for a slow external call.**

**Batch parallel requests** — three calls in one continuation rather than three sequential.

**Carry context in `con.state`**, since the two methods share nothing else.

**No DML before the continuation.**

**Prefer Queueable** for anything the user does not wait for, which is nearly everything.

**Consider caching or pre-syncing** before building a real-time lookup at all.
