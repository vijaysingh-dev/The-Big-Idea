# Iterators and Generators

The iteration protocol is the contract behind `for...of`, spread, destructuring, `Promise.all` and every other place the language accepts "a sequence of things". Generators are syntax for producing iterators without writing the protocol by hand.

## The iterable protocol

An object is **iterable** if it has a `[Symbol.iterator]` method returning an **iterator** — an object with a `next()` method returning `{ value, done }`.

```js
const range = {
  from: 1,
  to: 3,

  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;

    return {
      next() {
        return current <= last
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      },
    };
  },
};

[...range];                      // [1, 2, 3]
for (const n of range) {}
const [a, b] = range;            // destructuring works too
```

Everything that works with `for...of` implements this: arrays, strings, `Map`, `Set`, `NodeList`, `arguments`, `FormData`, `URLSearchParams`. Plain objects do not, which is why `for...of` over an object throws and you need `Object.entries` ([[06.3 - flat flatMap and Reshaping Data]]).

An iterator that is also iterable (returns `this` from `[Symbol.iterator]`) can be paused and resumed across multiple `for...of` loops — generators do this automatically.

## Generators

```js
function* range(from, to) {
  for (let i = from; i <= to; i++) {
    yield i;
  }
}

[...range(1, 3)];   // [1, 2, 3]
```

Calling a generator function runs **no code**. It returns a generator object — both an iterator and an iterable. Each `next()` runs until the next `yield` and suspends there, preserving the entire local state.

```js
const gen = range(1, 3);
gen.next();   // { value: 1, done: false }
gen.next();   // { value: 2, done: false }
gen.next();   // { value: 3, done: false }
gen.next();   // { value: undefined, done: true }
```

`yield*` delegates to another iterable:

```js
function* combined() {
  yield 0;
  yield* range(1, 3);
  yield* [10, 20];
}
```

A `return` value in a generator appears as the `value` of the final `{ done: true }` result, and is skipped by `for...of` and spread.

## Laziness

This is the property that matters. Values are produced on demand, so infinite sequences are expressible:

```js
function* naturals() {
  let n = 0;
  while (true) yield n++;
}

function* take(iterable, count) {
  let i = 0;
  for (const v of iterable) {
    if (i++ >= count) return;
    yield v;
  }
}

[...take(naturals(), 5)];  // [0, 1, 2, 3, 4]
```

And pipelines process one element at a time rather than materializing intermediate arrays:

```js
function* map(iterable, fn) {
  for (const v of iterable) yield fn(v);
}

function* filter(iterable, pred) {
  for (const v of iterable) if (pred(v)) yield v;
}

const result = take(filter(map(naturals(), n => n * n), n => n % 2 === 1), 3);
[...result];  // [1, 9, 25]
```

The array-method equivalent would never terminate. For finite but large data, the memory difference is the point: `.map().filter()` over a million rows allocates two million-element arrays; the generator version allocates none.

Note the ergonomic cost — these read worse than method chains. The Iterator Helpers proposal adds `.map`, `.filter`, `.take`, `.drop` directly to iterators, which removes this objection where supported.

## Two-way communication

`next(value)` sends a value *into* the generator, which becomes the result of the suspended `yield`:

```js
function* conversation() {
  const name = yield "What is your name?";
  const age = yield `Hello ${name}, how old are you?`;
  return `${name} is ${age}`;
}

const g = conversation();
g.next();          // { value: "What is your name?" }
g.next("Vijay");   // { value: "Hello Vijay, how old are you?" }
g.next(30);        // { value: "Vijay is 30", done: true }
```

The first `next()` cannot send a value, since there is no suspended `yield` yet.

This bidirectional behavior is exactly how `async/await` is implemented: `await` is `yield`, and a driver function resumes the generator when the yielded promise settles ([[04.4 - async await]]). Before native `async` existed, `co` and Babel's regenerator did precisely this.

`throw()` and `return()` inject an error or force early completion:

```js
g.throw(new Error("x"));  // thrown at the suspension point
g.return(42);             // runs finally blocks, completes the generator
```

`for...of` calls `return()` automatically when you `break`, which is why cleanup in a `finally` block inside a generator actually runs.

## Async generators

```js
async function* paginate(url) {
  let next = url;
  while (next) {
    const page = await fetch(next).then(r => r.json());
    yield* page.items;
    next = page.nextUrl;
  }
}

for await (const item of paginate("/api/items")) {
  process(item);
  if (enough) break;   // stops fetching further pages
}
```

`Symbol.asyncIterator`, `for await...of`, and natural **backpressure** — the producer only fetches the next page when the consumer asks. This is the cleanest way to consume paginated APIs, SSE streams and `ReadableStream` bodies, and it is genuinely hard to express with promises alone ([[04.7 - Async Concurrency Patterns]]).

Streams are async iterable natively:

```js
for await (const chunk of response.body) {
  processChunk(chunk);
}
```

## Where you meet these in practice

**Redux-Saga** uses generators for side-effect orchestration — yielding effect descriptions that a middleware interprets, which makes the logic synchronously testable ([[20.5 - Middleware and Thunks]]).

**Tree traversal** is where generators shine in application code:

```js
function* walk(node) {
  yield node;
  for (const child of node.children ?? []) {
    yield* walk(child);
  }
}

for (const node of walk(root)) {
  if (node.id === target) return node;  // stops traversal immediately
}
```

Recursive traversal with early exit, no accumulator array, no callback inversion.

**Unique id generation**, **cursor-based pagination**, and **state machines** are the other recurring cases.

## How senior engineers actually use this

**They implement `Symbol.iterator` on custom collections**, usually with a generator method, so domain objects work with spread and `for...of` like built-ins ([[03.6 - Symbols and Well Known Symbols]]).

**They use async generators for streaming and pagination**, where the alternative is manual loop-and-accumulate code that cannot be cancelled cleanly.

**They use generators sparingly in application logic.** They are slower than plain loops, harder to debug (stepping through suspensions is awkward), and unfamiliar to many reviewers. The bar is: does laziness, early termination, or backpressure actually matter here?

**They recognize regenerator output in bundles.** Transpiling generators for old targets pulls in a sizeable runtime; if a bundle grew unexpectedly, a generator in a hot dependency is a candidate ([[27.5 - Babel and Transpilation]]).

## Common pitfalls

- Expecting a generator to run on call. It runs on the first `next()`.
- Passing a value to the first `next()`, where it is discarded.
- Re-using an exhausted generator. Once done, it stays done; call the function again for a fresh one.
- Assuming spread on an infinite generator terminates — it does not.
- Forgetting `yield*` and yielding the inner iterable itself as a single value.
- Using async generators where `Promise.all` is simpler and parallel; async generators are inherently sequential.

## Interview angle

"What is a generator" and "how does `async/await` work internally" connect here — the honest answer to the second is that it is a generator driven by a promise-resolving trampoline. Being able to implement `Symbol.iterator` by hand and then show the two-line generator equivalent demonstrates you understand the protocol rather than just the syntax. Lazy infinite sequences and tree traversal with early exit are the two examples worth having ready.
