# Live Chat and Digital Engagement

## The channel landscape

Beyond email and phone, customers reach support through web chat, WhatsApp, SMS, Facebook Messenger, Apple Messages, and in-app messaging. Salesforce groups these under **Digital Engagement**, licensed separately.

The distinction that shapes everything: **chat is synchronous, messaging is asynchronous.**

A web chat session exists while the customer has the window open. Close it and the conversation ends. An agent is engaged for its duration.

A WhatsApp conversation persists. The customer sends a message, gets a reply four hours later, responds the next morning. The same conversation continues across days.

That difference changes routing, capacity, staffing, and the data model, and treating the two the same is the most common design mistake in this area.

## Web chat

**Embedded Service Chat** deploys a chat widget onto a website with a generated snippet. Configuration covers pre-chat forms, queueing behaviour, offline handling, and branding.

The objects:

**LiveChatTranscript** — the record of a session, with `Body` holding the full transcript, plus wait time, duration, and outcome.
**LiveChatVisitor** — the visitor, carrying the session identity.
**LiveChatButton** — the entry point, mapping to a queue or skill set.
**LiveChatDeployment** — the site configuration.

```sql
SELECT Id, CaseId, ContactId, ChatDuration, WaitTime, Status, StartTime, EndTime,
       OwnerId, Owner.Name
FROM LiveChatTranscript
WHERE StartTime = LAST_N_DAYS:7
ORDER BY StartTime DESC
```

A transcript can create or attach to a Case, which is usually what you want — a chat that resolves nothing still becomes a case someone follows up.

**Pre-chat forms** capture identity before the session starts, which is what lets the agent open with context rather than "who am I speaking to". Matching the entered email to a Contact and surfacing their open cases before the first message is a meaningful quality difference and costs one Apex call.

**Capacity for chat is different from cases.** An agent can hold six open cases and two concurrent chats. Chat consumes more Omni-Channel capacity per item because it demands continuous attention. See [[05.7 - Omni-Channel Routing]].

## Messaging

**Messaging for In-App and Web** and the channel-specific connectors handle asynchronous conversations.

The objects:

**MessagingSession** — a conversation, which can span days.
**MessagingEndUser** — the person, identified by phone number, WhatsApp ID, or app user ID.
**MessagingChannel** — the configured channel.
**ConversationEntry** — individual messages within a session.

The behaviours that differ from chat:

**Sessions do not end when the customer stops responding.** They time out after a configured period, and the conversation can be resumed.

**An agent does not stay engaged.** They reply and move on. Capacity is consumed differently — an agent might hold fifteen open messaging conversations because each demands attention only intermittently.

**Identity persists.** The same phone number returning next month is the same `MessagingEndUser`, with history. This is genuinely valuable and is what makes messaging feel personal in a way email does not.

**Consent matters legally.** WhatsApp and SMS have opt-in requirements, and message templates for business-initiated conversations require approval by the platform provider. This is a compliance question that belongs in design, not in testing.

## Bots

**Einstein Bots** handle the opening of a conversation: identifying the customer, collecting information, answering common questions from knowledge, and escalating to a human when needed.

The structure is dialogs, intents, entities, and variables, with the ability to call Apex through invocable methods.

```java
public with sharing class BotOrderStatusService {

    public class StatusRequest {
        @InvocableVariable(required=true) public String orderNumber;
        @InvocableVariable(required=true) public String contactEmail;
    }

    public class StatusResponse {
        @InvocableVariable public String status;
        @InvocableVariable public String expectedDate;
        @InvocableVariable public Boolean found;
    }

    @InvocableMethod(label='Get Order Status' description='Looks up order status for a bot dialog')
    public static List<StatusResponse> getStatus(List<StatusRequest> requests) {
        List<StatusResponse> responses = new List<StatusResponse>();

        Set<String> orderNumbers = new Set<String>();
        for (StatusRequest req : requests) {
            orderNumbers.add(req.orderNumber);
        }

        Map<String, Order> ordersByNumber = new Map<String, Order>();
        for (Order o : [
            SELECT OrderNumber, Status, EffectiveDate, Account.Id
            FROM Order WHERE OrderNumber IN :orderNumbers
        ]) {
            ordersByNumber.put(o.OrderNumber, o);
        }

        for (StatusRequest req : requests) {
            StatusResponse response = new StatusResponse();
            Order o = ordersByNumber.get(req.orderNumber);
            response.found = o != null;
            if (o != null) {
                response.status = o.Status;
                response.expectedDate = String.valueOf(o.EffectiveDate);
            }
            responses.add(response);
        }
        return responses;
    }
}
```

Bot invocable methods must accept and return **lists**, and the returned list must be the same length and order as the input. Getting this wrong produces a bot that returns the wrong customer's data, which is a serious defect rather than a cosmetic one.

**Agentforce** is the newer, more capable successor — agents that reason about a request and choose actions rather than following a scripted dialog tree. See [[24.4 - Agentforce Fundamentals]].

The design principle for either: **the handoff to a human must be clean.** The agent receiving an escalated conversation should see everything the bot collected. A customer who explained their problem to a bot and is then asked to repeat it is worse off than if the bot had never existed.

## Routing and staffing implications

Digital channels change the operating model, and this is where implementations underestimate the work.

**Chat requires agents online and idle.** An agent fully occupied with cases cannot take chat. Chat coverage requires staffing dedicated to it, at least partly.

**Messaging can be handled between other work**, which is why capacity settings for messaging are much higher than for chat.

**Channel switching is common.** A chat becomes a phone call becomes an email thread. If each creates a separate record with no link, the customer explains three times. The design answer is that every channel attaches to the same Case, with the conversation records as children.

**Business hours per channel differ.** Chat may be 9 to 6 while email is 24-hour. Configuring an offline experience for chat — a form rather than a dead widget — is a small thing that prevents a bad impression.

## Transcript retention

Chat and messaging transcripts accumulate quickly. A support desk handling 200 chats a day produces 73,000 transcripts a year, each with a full text body.

The body field is a long text area, which means it consumes real storage and cannot be filtered on efficiently. Retention policy — archive to a big object, or delete after a defined period — should be designed before the volume becomes a problem rather than after. See [[23.4 - Archiving with Big Objects and External Storage]].

## Reporting

The metrics specific to these channels:

```sql
SELECT Status, COUNT(Id) sessions, AVG(WaitTime) avgWait, AVG(ChatDuration) avgDuration
FROM LiveChatTranscript
WHERE StartTime = LAST_N_DAYS:30
GROUP BY Status
```

**Wait time** is the customer-visible number and the one that drives abandonment. **Abandonment rate** — visitors who left before an agent connected — is the clearest signal of understaffing. **Concurrency** shows whether capacity settings are realistic.

For bots, **containment rate** — conversations resolved without a human — is the metric, and it should be read alongside satisfaction. A bot with high containment and low satisfaction is deflecting customers rather than helping them, which costs more in the long run than the agent time it saved.

## Practical guidance

**Do not treat chat and messaging as the same channel.** Capacity, staffing, and session behaviour all differ.

**Use pre-chat forms and match to Contact.** Opening with context changes the interaction quality.

**Set chat capacity lower than case capacity.** Chat demands continuous attention.

**Make bot handoff clean.** Everything the bot collected must reach the human.

**Handle consent for WhatsApp and SMS properly.** It is a legal requirement, not a preference.

**Configure an offline experience for chat.** A widget that does nothing outside business hours is worse than no widget.

**Plan transcript retention early.** The volume grows faster than anyone estimates.
