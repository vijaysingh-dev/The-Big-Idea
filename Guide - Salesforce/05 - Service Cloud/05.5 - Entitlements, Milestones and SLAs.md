# Entitlements, Milestones and SLAs

## What this feature answers

Two questions, both contractual:

**Is this customer entitled to support at all?** They may have no contract, an expired one, or one that covers only certain products.

**What service level are they owed?** A premium contract might promise a one-hour response and eight-hour resolution; a standard one, next business day.

An **SLA** — Service Level Agreement — is the contractual promise. Entitlements and milestones are how Salesforce tracks compliance with it.

## The object model

**Entitlement.** What a customer is entitled to. Linked to an Account, optionally to a specific Asset or Contact, with a start and end date, a business hours record, and a type.

**ServiceContract.** The commercial agreement, with a term. An entitlement can belong to one.

**ContractLineItem.** A product line on a service contract, which can carry its own entitlement — so a customer with three machines under one contract can have different coverage per machine.

**Entitlement Process.** The definition of the milestones that apply. Attached to an entitlement.

**Milestone.** A time-based target within the process: First Response, Resolution, Escalation Warning.

**CaseMilestone.** The instance of a milestone on a specific case, with a target date, a completion date, and a violation flag.

**MilestoneType.** The reusable definition of a milestone, referenced by entitlement processes.

```sql
SELECT Id, Name, AccountId, StartDate, EndDate, Type, BusinessHoursId,
       SlaProcess.Name, ServiceContract.ContractNumber
FROM Entitlement
WHERE AccountId = :accountId AND EndDate >= TODAY
```

## How milestones work

When a case is created with an entitlement, the entitlement process starts and its milestones are instantiated as `CaseMilestone` records with target dates calculated from the case creation time, the milestone's time trigger, and the entitlement's **business hours**.

The business hours part is what makes it correct. A two-hour first response target on a case raised at 5pm, for a team working 9 to 6, is due at 10am the next working day — not 7pm. Holidays are excluded too. Building this calculation by hand is a well-known source of subtle bugs, and the platform doing it is the main reason to use the feature rather than custom fields.

A milestone is **completed** when its completion criteria are met, and each milestone type defines what counts:

- First Response completes when an outbound email is sent, or a custom action fires
- Resolution completes when the case status becomes a closed status

Completion can be triggered declaratively or from Apex:

```java
public with sharing class MilestoneService {

    public static void completeFirstResponse(Set<Id> caseIds) {
        List<CaseMilestone> milestones = [
            SELECT Id, CaseId, CompletionDate
            FROM CaseMilestone
            WHERE CaseId IN :caseIds
              AND MilestoneType.Name = 'First Response'
              AND CompletionDate = null
        ];

        for (CaseMilestone milestone : milestones) {
            milestone.CompletionDate = Datetime.now();
        }

        update milestones;
    }
}
```

The common trigger for this is an outbound `EmailMessage` on the case — the first agent reply completes the first response milestone.

## Milestone actions

Each milestone can have three sets of actions:

**Success actions** — run when completed on time.
**Warning actions** — run at a configured point before the target, typically at 75 or 80 percent of the allowed time. This is the useful one: it prompts the agent while there is still time to act.
**Violation actions** — run when the target passes without completion.

Each set can update fields, send email, create tasks, or send outbound messages. For anything more, the action can be a flow.

The warning action is where most of the practical value sits. A violation notification tells you that you already failed; a warning at 80 percent lets someone prevent it.

## Stopped milestones

A milestone can be **paused** when the case enters a status flagged as stopping the clock — typically Awaiting Customer.

This is the feature that makes SLA measurement honest. Without it, a case waiting three days for the customer to send a serial number counts those three days against the resolution target, and the metric measures the customer rather than the support team.

Configuration is on the entitlement process: which statuses stop the milestone clock. `StopStartDate` on the case records when it was stopped, and `SlaExitDate` marks when the process ended.

This connects directly to the status model in [[05.2 - Cases and the Case Lifecycle]] — Awaiting Customer earns its place partly because milestones can pause on it.

## Entitlement lookup and assignment

When a case is created, something must find the right entitlement. The standard options search by Account, Contact, or Asset, and Lightning provides an entitlement lookup component on the case page.

For automated case creation — Email-to-Case, integrations, portal — the assignment has to be code or flow:

```java
public with sharing class EntitlementAssignmentService {

    public static void assignEntitlements(List<Case> cases) {
        Set<Id> accountIds = new Set<Id>();
        Set<Id> assetIds = new Set<Id>();

        for (Case c : cases) {
            if (c.AccountId != null) {
                accountIds.add(c.AccountId);
            }
            if (c.AssetId != null) {
                assetIds.add(c.AssetId);
            }
        }
        if (accountIds.isEmpty() && assetIds.isEmpty()) {
            return;
        }

        // asset-level entitlements are more specific and take precedence over account-level ones
        Map<Id, Id> entitlementByAsset = new Map<Id, Id>();
        Map<Id, Id> entitlementByAccount = new Map<Id, Id>();

        for (Entitlement e : [
            SELECT Id, AccountId, AssetId, EndDate
            FROM Entitlement
            WHERE (AccountId IN :accountIds OR AssetId IN :assetIds)
              AND StartDate <= TODAY AND EndDate >= TODAY
            ORDER BY EndDate DESC
        ]) {
            if (e.AssetId != null && !entitlementByAsset.containsKey(e.AssetId)) {
                entitlementByAsset.put(e.AssetId, e.Id);
            }
            if (e.AccountId != null && !entitlementByAccount.containsKey(e.AccountId)) {
                entitlementByAccount.put(e.AccountId, e.Id);
            }
        }

        for (Case c : cases) {
            if (c.EntitlementId != null) {
                continue;
            }
            Id entitlementId = entitlementByAsset.get(c.AssetId);
            if (entitlementId == null) {
                entitlementId = entitlementByAccount.get(c.AccountId);
            }
            c.EntitlementId = entitlementId;
        }
    }
}
```

Two details. The `ORDER BY EndDate DESC` with a `containsKey` guard picks the longest-running entitlement when several apply, which is a business decision worth confirming rather than assuming. And asset-level precedence over account-level reflects the general principle that the more specific entitlement wins.

**Set the entitlement in a before-insert trigger**, because the entitlement process starts when the case is saved. Setting it afterwards means the milestones are created from the later timestamp, and the first response target is wrong.

## Adapting to the manufacturing model

For Northwind, entitlements map onto the existing objects from section 02:

```
Service_Contract__c (custom)  ←  the commercial agreement
    Machine_Coverage__c        ←  which machines are covered
        Machine__c             ←  maps to standard Asset, or stays custom

Entitlement                    ←  created per covered machine, per contract
    linked to Account and to the Asset representing the machine
    Entitlement Process        ←  chosen by coverage level (Premium / Standard)
```

The design choice worth making explicitly: whether `Machine__c` should be the standard **Asset** object instead. Asset integrates natively with Entitlement, Case, and Field Service, and choosing it means entitlement assignment works with no custom lookup logic. Keeping a custom object means more control and more code. For a business where installed equipment is central, Asset is usually the better answer, and this is exactly the "use the standard object even if the fit is imperfect" principle from [[02.1 - Objects Overview]].

## Reporting on compliance

The output that justifies the whole feature:

```sql
SELECT MilestoneType.Name milestone,
       COUNT(Id) total,
       SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) violations
FROM CaseMilestone
WHERE Case.CreatedDate = LAST_N_DAYS:90
GROUP BY MilestoneType.Name
```

Compliance by customer, which is what account managers get asked about:

```sql
SELECT Case.Account.Name customer,
       COUNT(Id) milestones,
       SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) breaches
FROM CaseMilestone
WHERE Case.CreatedDate = THIS_QUARTER
GROUP BY Case.Account.Name
HAVING SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) > 0
ORDER BY SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) DESC
```

Where contracts carry financial penalties for breach, this query is the one finance cares about, and its accuracy depends entirely on milestones being paused correctly.

## When not to use entitlements

The feature carries real configuration overhead. It is not worth it when:

- Support is uniform for all customers with no contractual differences
- There are no time commitments anyone measures against
- The support desk is small enough that visibility solves the problem

For those cases, an escalation rule and a couple of custom date fields do the job at a fraction of the complexity.

The signal that entitlements *are* needed: contracts specify response times, and someone is asked to prove compliance.

## Practical guidance

**Assign the entitlement in a before-insert trigger.** Timing matters.

**Configure stopped statuses.** SLA measurement is dishonest without them.

**Use warning actions, not just violation actions.** Preventing a breach beats recording one.

**Tie entitlements to business hours per region.** A global support operation needs several business hours records.

**Consider using the standard Asset object** for equipment rather than a custom one, precisely because entitlements integrate with it.

**Do not adopt entitlements without a contractual driver.** The complexity is only justified by a real obligation.
