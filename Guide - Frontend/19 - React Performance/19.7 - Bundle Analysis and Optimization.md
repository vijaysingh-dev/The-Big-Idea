# Bundle Analysis and Optimization

JavaScript is the most expensive resource on a page byte-for-byte — it must be downloaded, parsed, compiled and executed, and all of that happens on the main thread ([[01.1 - How JavaScript Runs]]). A 200KB image and 200KB of JavaScript are not comparable costs.

## Measure first

```bash
npm i -D rollup-plugin-visualizer    # Vite
npm i -D webpack-bundle-analyzer     # webpack
npx source-map-explorer dist/assets/*.js
```

```js
// vite.config.js
import { visualizer } from "rollup-plugin-visualizer";
export default { plugins: [visualizer({ gzipSize: true, brotliSize: true })] };
```

The treemap answers the only question that matters: **what is actually large?** Assumptions are usually wrong — the biggest chunk is frequently a transitive dependency nobody chose directly.

Read **gzipped or brotli** sizes, not raw. Raw size overstates text-heavy code by 3–4×.

Chrome DevTools' **Coverage** panel shows how much of each file executed before first interaction. High unused percentages point at code that should be split rather than deleted.

## The usual offenders

| Dependency | Cost | Alternative |
| --- | --- | --- |
| `moment` | ~70KB + locales | `date-fns`, `dayjs`, `Intl.DateTimeFormat` |
| `lodash` (full) | ~70KB | native methods, or per-method imports |
| Full icon libraries | 100–500KB | named imports, or an SVG sprite |
| `axios` | ~15KB | `fetch` with a small wrapper |
| Chart libraries | 200–400KB | lazy load, or a lighter library |
| Rich text editors | 300–800KB | lazy load |
| `polyfills` for old browsers | varies | tighten `browserslist` |

Two import patterns that quietly cost the most:

```js
import _ from "lodash";                 // entire library
import { debounce } from "lodash";      // still the whole library in CJS builds
import debounce from "lodash/debounce"; // just this function
import { debounce } from "lodash-es";   // tree-shakeable
```

```js
import * as Icons from "react-icons";   // everything
import { FiSearch } from "react-icons/fi";  // just this icon
```

`moment` deserves specific mention because it is still extremely common and bundles every locale by default. `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat` are built in and cover most formatting needs with zero bytes.

## Tree shaking requirements

Tree shaking removes unused exports, but only when the bundler can prove removal is safe ([[27.6 - Tree Shaking]]):

- **ES modules only.** CommonJS is dynamic and cannot be statically analyzed ([[08.1 - ES Modules vs CommonJS]]).
- **No side effects at module scope.** Code that runs on import cannot be dropped.
- **`"sideEffects": false`** in the package's `package.json`, or a list of files that do have side effects.

```json
{ "sideEffects": ["*.css", "./src/polyfills.js"] }
```

Getting this wrong in your own package means consumers ship all of it.

Note that a namespace re-export barrel file can defeat tree shaking:

```js
// index.js — importing one thing pulls the analysis through everything
export * from "./a";
export * from "./b";
```

Some bundlers handle this; many do not, especially with side effects present. Deep imports are safer for large internal libraries.

## Chunk strategy

```js
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          react: ["react", "react-dom"],
          vendor: ["@tanstack/react-query", "date-fns"],
        },
      },
    },
  },
};
```

The reasoning is caching, not size. Framework code changes rarely; application code changes on every deploy. Splitting them means a deploy invalidates only the app chunk, and returning users re-download a few KB rather than a few hundred.

Do not over-split. Each chunk is a request, and HTTP/2 multiplexing reduces but does not eliminate the overhead.

## Duplicate dependencies

```bash
npm ls react
npx depcheck
```

Two versions of the same library both end up in the bundle. Worse, two copies of React cause "Invalid hook call" ([[17.1 - Rules of Hooks and How They Work]]), and two copies of a state library mean two independent stores.

```json
{ "overrides": { "react": "18.3.1" } }
```

The analyzer visualizes this clearly — the same package appearing twice in the treemap.

## Polyfills and browser targets

```json
// package.json
{ "browserslist": ["> 0.5%", "last 2 versions", "not dead"] }
```

An overly broad target adds transpilation overhead and polyfills for browsers nobody uses. Check the actual analytics for your product; supporting a browser with 0.1% share can cost 30KB and slower output for everyone else ([[27.5 - Babel and Transpilation]]).

## Compression

```
gzip:   baseline
brotli: ~15-20% smaller than gzip on JS
```

Brotli at maximum quality for static assets is nearly free — it is done once at build time and cached. Verify it is actually enabled:

```bash
curl -H "Accept-Encoding: br" -I https://example.com/assets/main.js
# content-encoding: br
```

Many performance problems turn out to be a CDN serving uncompressed assets.

## Budgets

```js
// vite.config.js
build: { chunkSizeWarningLimit: 500 }
```

Better, enforce in CI with `size-limit`:

```json
{
  "size-limit": [
    { "path": "dist/assets/index-*.js", "limit": "150 kB" }
  ]
}
```

Bundle size regresses gradually — a dependency here, a helper there. A CI check turns it into a visible decision at PR time rather than a discovery six months later.

## Rough targets

For the initial load, gzipped:

```
< 100 KB   good
100-200 KB acceptable for an application
200-350 KB heavy — split more
> 350 KB   likely a problem on mobile networks
```

Context matters — an internal admin tool on desktop has different constraints from a consumer site in a market with slow connections. The number that matters is time-to-interactive on a mid-range phone on 4G, not the byte count itself.

## What actually moves the number

In rough order of impact:

1. **Route-level code splitting** — usually 40–70% off the initial bundle ([[19.3 - Code Splitting and React.lazy]])
2. **Replacing or lazy-loading one heavy dependency** — often 100–300KB
3. **Fixing import patterns** — lodash, icons, date libraries
4. **Tightening browser targets**
5. **Vendor chunk separation** for caching

Micro-optimizing application code is almost never where the bytes are. Dependencies typically account for 70–90% of a frontend bundle.

## How senior engineers actually use this

**They run the analyzer before optimizing**, every time, because the intuition is usually wrong.

**They treat adding a dependency as a size decision.** Checking bundlephobia before installing takes ten seconds.

**They enforce a budget in CI**, so regressions are caught at the PR that causes them.

**They check for duplicate versions** whenever the bundle grows unexpectedly.

**They optimize the initial bundle specifically**, not total bytes — code that loads after interaction is far cheaper.

## Common pitfalls

- Reading raw sizes instead of gzipped.
- `import _ from "lodash"` or namespace imports from icon libraries.
- Barrel files defeating tree shaking.
- Duplicate React or duplicate state libraries.
- Over-splitting into dozens of tiny chunks.
- An overly broad `browserslist` inflating output for everyone.
- Brotli not actually enabled on the CDN.
- Optimizing application code while dependencies dominate the bundle.

## Interview angle

"How would you reduce bundle size" should start with measurement — run the analyzer, read gzipped sizes, check Coverage — and then the ordered levers: route splitting, replacing or lazy-loading heavy dependencies, fixing import patterns, tightening targets. Mentioning that dependencies are usually 70–90% of the bundle, and that a CI size budget prevents gradual regression, moves the answer from tactics to process.
