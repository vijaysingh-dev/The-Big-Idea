# Aura to LWC Migration

## The rule that shapes everything

**An LWC can be nested inside an Aura component. An Aura component cannot be nested inside an LWC.**

```xml
<!-- Works -->
<aura:component>
    <c:claimList recordId="{!v.recordId}" onclaimselected="{!c.handleSelected}"/>
</aura:component>
```

```html
<!-- Not possible -->
<template>
    <c-legacy-aura-panel></c-legacy-aura-panel>
</template>
```

Migration therefore works **inward**: the Aura shell stays, and its internals are replaced one piece at a time. Attempting to start at the outermost component stalls, because it still contains Aura children.

## The interoperability surface

**Aura parent to LWC child** — properties down as attributes:

```xml
<c:claimList record-id="{!v.recordId}" max-rows="10"/>
```

Attribute names use kebab-case, matching the LWC convention.

**LWC child to Aura parent** — a standard `CustomEvent`:

```javascript
// in the LWC
this.dispatchEvent(new CustomEvent('claimselected', {
    detail: { claimId: this.claim.Id }
}));
```

```xml
<c:claimList onclaimselected="{!c.handleClaimSelected}"/>
```

```javascript
({
    handleClaimSelected: function(component, event, helper) {
        const claimId = event.getParam("claimId");
    }
})
```

**Aura calling an LWC's public method:**

```javascript
const listComponent = component.find("claimList");
listComponent.refresh();
```

```xml
<c:claimList aura:id="claimList"/>
```

`aura:id` is how Aura finds a child, and `component.find()` returns it. Public methods marked `@api` on the LWC are callable directly.

**Shared Apex.** An `@AuraEnabled` method works unchanged from both frameworks, which is what makes incremental migration possible without touching the server layer.

**Lightning Message Service** works across both, which is the answer for replacing an application event during a partial migration. See [[14.8 - Lightning Message Service]].

## The migration sequence

**1. Inventory.**

```bash
sf data query --use-tooling-api \
  --query "SELECT DeveloperName, ApiVersion, Description FROM AuraDefinitionBundle ORDER BY DeveloperName" \
  --target-org production
```

Then, for each, note where it is used — a FlexiPage, a quick action, a parent component, an Experience Cloud page. A component nobody uses is a deletion rather than a migration, and there are usually several.

**2. Prioritize.**

Migrate the leaves first — components with no Aura children — because they can be replaced without touching anything else.

Prioritize by value: performance-critical pages, components changing frequently, components blocking other work. **Not by age**, and not alphabetically.

**3. Write characterization tests first.**

Before changing anything, write Jest tests against the intended behaviour and Apex tests against the controller. The Apex controller usually does not change, so its tests carry over directly.

This is the step that gets cut and the one that makes the migration verifiable. Without it, "does the new one behave the same" has no answer.

**4. Build the LWC alongside.**

```
force-app/main/default/aura/claimList/       existing
force-app/main/default/lwc/claimList/        new
```

Same name is fine — they are different metadata types and do not collide.

**5. Swap the reference.**

In the parent Aura component:

```xml
<!-- <c:claimList aura:id="list" recordId="{!v.recordId}"/> -->
<c:claimList record-id="{!v.recordId}" onclaimselected="{!c.handleSelected}"/>
```

The markup is nearly identical, which is convenient and makes it easy to miss that the child changed.

For a component placed directly on a page, the FlexiPage must be updated — and deployed. See [[14.19 - Deploying and Exposing Components]].

**6. Verify, then delete the Aura component.**

Delete only after a full usage cycle. A component still referenced somewhere you did not find fails at runtime, and finding it after deletion is worse.

## The translation table

| Aura | LWC |
| --- | --- |
| `aura:attribute` | A field, or `@api` for public |
| `{!v.x}` | `{x}` |
| `{!v.a > v.b}` | A getter |
| `{!c.method}` | `onclick={method}` |
| `aura:if` / `aura:set attribute="else"` | `lwc:if` / `lwc:else` |
| `aura:iteration` | `for:each` with a `key` |
| `component.get("v.x")` | `this.x` |
| `component.set("v.x", value)` | `this.x = value` |
| `component.find("id")` | `this.template.querySelector()` |
| `init` handler | `connectedCallback` |
| `afterRender` | `renderedCallback` |
| Controller and helper | One class |
| `$A.enqueueAction` | `await apexMethod()` or `@wire` |
| Component event | `CustomEvent` |
| Application event | Lightning Message Service |
| `force:showToast` | `ShowToastEvent` |
| `force:navigateToSObject` | `NavigationMixin` |
| `force:refreshView` | `refreshApex` and `notifyRecordUpdateAvailable` |
| `.design` file | `targetConfigs` in the metadata |
| `implements="..."` | `targets` in the metadata |

## A worked conversion

**Before:**

```xml
<aura:component controller="ClaimController"
                implements="flexipage:availableForRecordHome,force:hasRecordId">
    <aura:attribute name="recordId" type="Id"/>
    <aura:attribute name="claims" type="List" default="[]"/>
    <aura:attribute name="isLoading" type="Boolean" default="true"/>

    <aura:handler name="init" value="{!this}" action="{!c.doInit}"/>

    <lightning:card title="Warranty Claims">
        <aura:if isTrue="{!v.isLoading}">
            <lightning:spinner alternativeText="Loading"/>
            <aura:set attribute="else">
                <aura:iteration items="{!v.claims}" var="claim">
                    <div onclick="{!c.handleSelect}" data-claim-id="{!claim.Id}">
                        {!claim.Claim_Number__c}
                    </div>
                </aura:iteration>
            </aura:set>
        </aura:if>
    </lightning:card>
</aura:component>
```

```javascript
({ doInit: function(c, e, h) { h.loadClaims(c); } })
```

```javascript
({
    loadClaims: function(component) {
        const action = component.get("c.getClaims");
        action.setParams({ accountId: component.get("v.recordId") });
        action.setCallback(this, function(response) {
            if (response.getState() === "SUCCESS") {
                component.set("v.claims", response.getReturnValue());
            }
            component.set("v.isLoading", false);
        });
        $A.enqueueAction(action);
    }
})
```

**After:**

```javascript
import { LightningElement, api, wire } from 'lwc';
import getClaims from '@salesforce/apex/ClaimController.getClaims';

export default class ClaimList extends LightningElement {
    @api recordId;

    claimResult;

    @wire(getClaims, { accountId: '$recordId' })
    wiredClaims(result) {
        // keeping the whole result enables refreshApex later
        this.claimResult = result;
    }

    get claims() {
        return this.claimResult?.data ?? [];
    }

    get isLoading() {
        return !this.claimResult?.data && !this.claimResult?.error;
    }

    handleSelect(event) {
        this.dispatchEvent(new CustomEvent('claimselected', {
            detail: { claimId: event.currentTarget.dataset.claimId }
        }));
    }
}
```

```html
<template>
    <lightning-card title="Warranty Claims">
        <template lwc:if={isLoading}>
            <lightning-spinner alternative-text="Loading"></lightning-spinner>
        </template>
        <template lwc:else>
            <template for:each={claims} for:item="claim">
                <div key={claim.Id} data-claim-id={claim.Id} onclick={handleSelect}>
                    {claim.Claim_Number__c}
                </div>
            </template>
        </template>
    </lightning-card>
</template>
```

Three files become two, and the imperative load becomes a wire that refreshes automatically when `recordId` changes.

**The Apex controller is unchanged.**

## Where migration gets hard

**Application events.** No equivalent, and consumers are not discoverable from the firing code. Every one must be found and converted to LMS.

```bash
grep -rl "ClaimApproved" force-app/main/default/aura/
```

**`force:refreshView`.** It refreshes the whole page. The LWC replacement is per-consumer: `refreshApex` for each wire and `notifyRecordUpdateAvailable` for LDS. A component relying on it to update three unrelated things needs all three handled. See [[14.11 - refreshApex and Cache Invalidation]].

**Two-way binding.** An Aura child mutating a parent attribute has no LWC equivalent by design. Each instance becomes a property down and an event up, and finding them means reading for `{!v.x}` on passed attributes.

**Logic in expressions.** Every expression containing a comparison or a concatenation becomes a getter. Mechanical, and easy to miss one.

**Dynamic component creation.** `$A.createComponent` has a partial LWC equivalent in `lwc:is`, and complex dynamic construction may need redesign.

**Third-party libraries.** Aura's looser DOM boundary means some libraries work there and not inside a shadow root. The options are light DOM, a different library, or keeping that one component in Aura. See [[14.15 - Styling, SLDS and Design Tokens]].

## What cannot be migrated

**Lightning Out dependency applications.** `ltng:outApp` has no LWC equivalent — an Aura application is required to bootstrap an LWC into an external page. It is a three-line wrapper with no logic, and it stays.

```xml
<aura:application access="GLOBAL" extends="ltng:outApp">
    <aura:dependency resource="c:claimList"/>
</aura:application>
```

**Some quick action configurations** and a small number of console and Experience Cloud contexts, though the list shrinks each release.

## The policy that works

**No new Aura.** Every new component is an LWC, including one nested inside an Aura parent.

**Migrate opportunistically.** When substantially changing a component, migrate it. When adding a feature to one, add the feature as a nested LWC.

**Never as a project.** "Migrate all Aura to LWC" is a plan with cost, risk, and no business outcome. A working Aura component is not a defect.

**Prioritize by value.** Performance-critical pages, components changing often, components blocking other work.

The realistic end state is a mostly-LWC org with a handful of Aura components that work and nobody touches, plus one Lightning Out wrapper. That is a good place to be, and "zero Aura" is not a goal worth spending money on.

## Section 15 in one paragraph

Aura is the superseded framework, kept in this course because you will inherit it rather than write it. Its distinguishing features are the ones LWC deliberately removed: logic in markup expressions, two-way attribute binding that lets a child silently mutate parent state, and application events that broadcast to unknown consumers. The one-way nesting rule — LWC inside Aura, never the reverse — means migration works inward from the leaves, with the Apex controller unchanged and Lightning Message Service replacing application events. The hardest parts are the ones with no equivalent: `force:refreshView`, which refreshed everything, and two-way binding, which made data flow invisible. And the right policy is no new Aura, opportunistic migration, and leaving working components alone — because a stable Aura component that nobody touches costs nothing, and rewriting it costs a sprint.
