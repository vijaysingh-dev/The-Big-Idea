# Rate Limiters

> **Revision tags:** #building-blocks #rate-limiting #reliability  
> **Related:** [[04.1 - Rate Limiter]] | [[03.2 - Reverse Proxies and API Gateways]]

---

## What It Is

A rate limiter controls the rate at which a client can make requests to a service, rejecting requests that exceed a defined threshold.

```
Client A: 10 req/s allowed → 10 requests pass → 11th rejected (HTTP 429)
Client B: same limit, only sends 3 req/s → all pass
```

---

## Why It Exists

- **Protect services from overload:** A single misbehaving client can't exhaust server resources
- **Prevent abuse:** Bots, scrapers, credential stuffers can't hammer endpoints
- **Ensure fair usage:** One power user can't starve others
- **Cost control:** Metered APIs limit usage per pricing tier
- **Security:** Slow down brute-force attacks (login, OTP endpoints)

---

## Rate Limiting Algorithms

### Token Bucket

A bucket holds up to `capacity` tokens. Tokens are added at a fixed `refill_rate`. Each request consumes one token. Requests are rejected when the bucket is empty.

```
capacity = 10 tokens
refill_rate = 2 tokens/second

t=0:    bucket=10
t=0:    5 requests arrive → bucket=5
t=1:    2 tokens added → bucket=7
t=1:    8 requests arrive → 7 pass, 1 rejected → bucket=0
t=2:    2 tokens added → bucket=2
```

**Properties:**
- Allows short bursts up to `capacity`
- Smoothly limits sustained rate to `refill_rate`
- Simple to implement

**Best for:** APIs that want to allow bursting but limit sustained rate.

### Leaky Bucket

Requests enter a queue (the "bucket"). A background process drains the queue at a fixed rate. If the bucket overflows, requests are rejected.

```
incoming: variable rate
outgoing: fixed rate (e.g., 10 req/s)
overflow: rejected
```

**Properties:**
- Smooths out bursty traffic — output is always at a constant rate
- No bursting allowed
- Can add latency (requests wait in queue)

**Best for:** Protecting downstream services that can only handle a fixed rate (e.g., a payment processor with strict SLA).

### Fixed Window Counter

Divide time into fixed windows (e.g., 1-minute buckets). Count requests per window. Reject if count exceeds limit.

```
Window: 10:00:00 – 10:01:00 → limit: 100
  10:00:30: 100 requests → all pass, counter=100
  10:00:45: 1 more request → rejected

Window: 10:01:00 – 10:02:00 → counter resets to 0
  10:01:01: 100 requests → all pass again
```

**Problem: Boundary burst.** A client can send 100 requests at 10:00:59 and 100 more at 10:01:01 — 200 requests in 2 seconds, despite a "100/minute" limit.

**Best for:** Rough limiting where the boundary burst problem is acceptable.

### Sliding Window Log

Store the timestamp of every request in a sorted list (log). On each request, remove timestamps older than the window, count remaining, reject if over limit.

```
Limit: 5 requests per 60 seconds
Current time: 10:01:30

Log: [10:00:35, 10:00:55, 10:01:10, 10:01:25]
Remove entries < 10:00:30 → none to remove
Count = 4 → under limit → allow, add 10:01:30 to log
```

**Properties:**
- Precise — no boundary burst problem
- Memory-intensive — stores every request timestamp
- Expensive for high-volume clients

**Best for:** Low-volume, precision-critical limiting (e.g., SMS/email sending per user).

### Sliding Window Counter (Hybrid)

Approximates sliding window using two fixed window counters with a weighted average.

```
Limit: 100/minute
Current time: 10:01:45 (45 seconds into current window)

Previous window (10:00–10:01): count = 80
Current window  (10:01–10:02): count = 30

Estimated count = 80 × (15/60) + 30 = 80 × 0.25 + 30 = 50

50 < 100 → allow
```

**Properties:**
- Low memory (only 2 counters per window)
- Approximate — up to 0.003% error under normal distributions
- Used by: Redis cell module, Cloudflare's rate limiter

**Best for:** High-volume distributed rate limiting where precision ≈ accuracy is acceptable.

## Where to Implement

**API Gateway layer:**  
Central enforcement, no per-service implementation needed. Limits applied before traffic reaches services.

```
Client → API Gateway (rate limit check) → Service
```

**Service layer:**  
More granular, per-endpoint limits. Useful for internal services where the gateway doesn't apply.

**Client library / SDK:**  
Client-side throttling to avoid hitting server limits. Doesn't protect the server but improves client reliability.

---

## Distributed Rate Limiting

When multiple instances of a service run, each has its own in-memory counter. A 100 req/s limit with 5 instances means each enforces 100 req/s locally → effective limit is 500 req/s.

**Solution: centralized counter in Redis**

```python
def is_rate_limited(user_id, limit, window_seconds):
    key = f"rate_limit:{user_id}:{current_window(window_seconds)}"
    count = redis.incr(key)
    if count == 1:
        redis.expire(key, window_seconds)
    return count > limit
```

All instances share the same Redis key → consistent global limit.

**Tradeoff:** Every request requires a Redis round trip (~1ms). For high-throughput APIs, this is acceptable. For ultra-low-latency paths, consider approximate local counting with periodic sync.

---

## Rate Limit Response

Return enough information for clients to handle gracefully:

```
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1705000060
Retry-After: 30

{ "error": "rate_limit_exceeded", "retry_after_seconds": 30 }
```

`Retry-After` tells clients when to retry. Well-behaved clients back off automatically.

## Rate Limiting Strategies by Use Case

| Use Case | Strategy | Key |
|---|---|---|
| Public API per user | Token bucket | user_id |
| Login endpoint | Sliding window | ip_address + username |
| SMS/email sending | Sliding window log | user_id |
| Per-plan API quota | Fixed window (daily) | api_key + date |
| Service-to-service | Token bucket | caller_service_id |
| Expensive endpoints | Lower limit than others | endpoint + user_id |

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Redis down | Can't check rate limits | Fail open (allow all) vs fail closed (reject all) — document your choice |
| Redis slow | Rate limit check adds latency | Circuit breaker, local fallback counter |
| Counter overflow (very high volume) | Always limited or never limited | Use appropriate data type (64-bit int) |
| IP spoofing | Clients bypass IP-based limits | Use authenticated user_id as key where possible |
| Clock skew in window calculation | Inconsistent windows across nodes | Use Redis server time (TIME command), not local time |
