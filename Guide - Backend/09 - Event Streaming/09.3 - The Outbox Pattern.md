# The Outbox Pattern

#backend #streaming #reliability

> **In one line:** You cannot write to a database and publish a message atomically, so write the message *into* the database in the same transaction and let a separate process publish it.

---

## The Problem

```python
async with conn.transaction():
    await repo.create_document(doc)

await kafka.send("documents", document_created_event(doc))   # ← and if this fails?
```

Three failure points, all real:

```
Commit succeeds, publish fails       → the document exists, nobody knows
Commit succeeds, process dies        → same
Publish succeeds, commit rolls back  → an event for something that never happened
```

⚠️ **This is the dual-write problem and there is no configuration that fixes it.** Two systems, no distributed transaction, and any ordering leaves a window.

The naive attempts, and why each fails:

```python
# "Publish first"
await kafka.send(...)                    # ← if the commit fails, a phantom event
async with conn.transaction():
    await repo.create_document(doc)
```

```python
# "Retry the publish"
for _ in range(3):
    try:
        await kafka.send(...)
        break
    except Exception:
        await asyncio.sleep(1)
# ← the process dies during the retry loop. Event lost.
```

```python
# "Publish in an after-commit hook"
@event.listens_for(session, "after_commit")
def publish(session): ...
# ← the process can die between commit and hook. Same window.
```

💡 **Every attempt leaves a window because the window is inherent.** The only way to close it is to make the message part of the transaction.

---

## The Outbox

```sql
CREATE TABLE outbox (
    id            bigserial PRIMARY KEY,
    aggregate_type text NOT NULL,
    aggregate_id  text NOT NULL,
    event_type    text NOT NULL,
    payload       jsonb NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    published_at  timestamptz
);

CREATE INDEX ON outbox (id) WHERE published_at IS NULL;
```

```python
async with conn.transaction():
    doc = await repo.create_document(data)
    await conn.execute(
        """INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload)
           VALUES ('document', $1, 'document.created', $2)""",
        doc.id, json.dumps(event_payload(doc)),
    )
# ← both committed, or neither
```

```python
# A separate relay publishes
async def relay():
    while True:
        rows = await conn.fetch(
            "SELECT * FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100"
        )
        for row in rows:
            await kafka.send(topic_for(row["event_type"]), row["payload"])
            await conn.execute(
                "UPDATE outbox SET published_at = now() WHERE id = $1", row["id"]
            )
        await asyncio.sleep(0.1 if rows else 1.0)
```

💡 **The event now exists as durably as the data**, because it is the same transaction. **The publish becomes a retryable background operation rather than a correctness-critical one.**

⚠️ **The relay gives you at-least-once, not exactly-once.** A crash between `kafka.send` and the `UPDATE` republishes on restart. **That is fine and expected** — consumers deduplicate on event ID ([[07.5 - Idempotency Keys and Deduplication]]).

## Getting the Relay Right

### Ordering

⚠️ **`ORDER BY id` is necessary and not sufficient**, because `bigserial` values are assigned at insert time and committed out of order:

```
T1 gets id 100, runs slowly
T2 gets id 101, commits
Relay reads: sees 101, publishes, marks published_at
T1 commits: 100 is now visible, but the relay has moved past it
```

⚠️ **The relay must not track a high-water mark on `id`** for exactly this reason. **Selecting `WHERE published_at IS NULL` avoids it** — row 100 becomes visible and is picked up on the next poll, out of order but not lost.

💡 **If strict ordering per aggregate matters, order by `id` within an aggregate and process aggregates independently**, or use CDC ([[09.4 - Change Data Capture]]) which reads the WAL in commit order and does not have this problem at all.

### Concurrency

```sql
UPDATE outbox SET published_at = now()
WHERE id IN (
    SELECT id FROM outbox WHERE published_at IS NULL
    ORDER BY id LIMIT 100
    FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

💡 **`FOR UPDATE SKIP LOCKED` lets several relay instances run without coordination** ([[06.6 - Transactions and Isolation Levels]]). No leader election, no singleton.

⚠️ **But marking published *before* publishing means a crash loses the event.** For at-least-once you must publish first, then mark:

```python
rows = await claim_batch()              # SELECT ... FOR UPDATE SKIP LOCKED, no update
for row in rows:
    await kafka.send(...)
    await mark_published(row["id"])
```

**Claim with a lock, publish, then mark — inside the same transaction as the claim**, so a crash releases the lock and another relay retries.

### Deletion versus soft marking

```sql
-- Option A: delete after publishing
DELETE FROM outbox WHERE id = $1;

-- Option B: mark, clean up later
UPDATE outbox SET published_at = now() WHERE id = $1;
DELETE FROM outbox WHERE published_at < now() - interval '7 days';
```

⚠️ **Option A creates a lot of dead tuples on a hot table** ([[06.7 - MVCC Vacuum and Bloat]]). A high-throughput outbox with immediate deletes bloats badly and vacuum struggles to keep up.

💡 **Option B with partitioning by day is the best of both** — mark published, and drop yesterday's partition:

```sql
CREATE TABLE outbox (...) PARTITION BY RANGE (created_at);
DROP TABLE outbox_2026_08_16;      -- instant, zero bloat
```

**Keeping published events for a few days is also operationally useful** — "did we publish that event?" becomes a query.

## Latency

```
Poll interval 1s → up to 1s of publish latency
```

For most events that is fine. When it is not:

### `LISTEN`/`NOTIFY` to wake the relay

```sql
CREATE FUNCTION notify_outbox() RETURNS trigger AS $$
BEGIN
    PERFORM pg_notify('outbox', '');
    RETURN NEW;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER outbox_notify AFTER INSERT ON outbox
FOR EACH STATEMENT EXECUTE FUNCTION notify_outbox();
```

```python
await listener.add_listener("outbox", lambda *_: wake.set())

while True:
    await asyncio.wait_for(wake.wait(), timeout=1.0)   # wake, or poll fallback
    wake.clear()
    await drain_outbox()
```

💡 **`NOTIFY` fires only on commit**, so it cannot wake the relay for an uncommitted row. That transactional property is exactly what you want here.

⚠️ **`LISTEN` needs a dedicated connection and does not work through PgBouncer in transaction mode** ([[06.9 - Connection Pooling and PgBouncer]]). Use a direct connection for the listener.

**Keep the poll as a fallback** — `NOTIFY` is fire-and-forget, and a listener that was briefly disconnected misses the wake-up.

### Or use CDC

Reading the WAL directly gives you sub-second latency, commit ordering, and no polling at all — at the cost of running Debezium or equivalent ([[09.4 - Change Data Capture]]).

💡 **Debezium's outbox event router reads the outbox table via CDC and publishes to Kafka**, which combines the transactional guarantee of the outbox with the latency and ordering of CDC. **It is the strongest version of this pattern.**

## In Production

### Monitoring

```python
outbox_pending_count.set(count)
outbox_oldest_pending_age_seconds.set(age)          # ← the key metric
outbox_published_total.inc()
outbox_publish_failures_total.labels(reason=...).inc()
outbox_relay_lag_seconds.observe(published_at - created_at)
```

⚠️ **`outbox_oldest_pending_age_seconds` climbing means the relay is down or stuck**, and every second it climbs is a second of events not reaching consumers. **Alert on it**, not on pending count ([[08.1 - Why Background Work Exists]]).

💡 **The relay is a single point of failure for your entire event stream.** If it stops, the database is fine, the API is fine, and no downstream system learns anything. **That failure is silent unless you monitor for it.**

### The relay is not optional infrastructure

| Concern | |
|---|---|
| **Must always be running** | Multiple instances with `SKIP LOCKED` |
| Deploys must not create gaps | Rolling, with overlap |
| Its own alerting | Separate from the application |
| Bounded batch size | So one huge batch does not stall it |
| **Publish failures must not block the batch** | Skip and retry individually |

```python
for row in rows:
    try:
        await kafka.send(...)
        await mark_published(row["id"])
    except Exception:
        outbox_publish_failures_total.inc()
        continue          # ← do not block the rest of the batch
```

⚠️ **One unpublishable event blocking the relay stalls every event behind it** ([[02.5 - Head of Line Blocking]]). Skip it, count it, and alert if a row's `created_at` exceeds a threshold.

### Table growth

```
1,000 events/second × 86,400 = 86 million rows/day
```

⚠️ **A high-throughput outbox is a high-throughput table**, with the write amplification of every index on it and the bloat of every update.

| Mitigation | |
|---|---|
| **Partition by day**, drop old partitions | Instant cleanup, zero bloat |
| Minimal indexes | One partial index on unpublished |
| `fillfactor` below 100 | HOT updates for the `published_at` write ([[06.1 - Storage Engines]]) |
| Consider CDC instead | No outbox table at all |

💡 **At very high volume, the outbox table becomes a meaningful fraction of your database write load.** That is the point at which CDC directly from your domain tables becomes the better answer.

### Ordering guarantees, stated honestly

```
Within one transaction:     ordered (single insert, or ordered ids)
Across transactions:        NOT guaranteed by the relay
Per aggregate:              achievable, with care
Globally:                   no
```

⚠️ **Be explicit in your event catalogue about what ordering the outbox provides** ([[09.2 - Event Modeling]]). Consumers that assume global ordering will be wrong.

💡 **Make consumers order-independent where you can** — version checks and absolute values rather than deltas — and the question stops mattering ([[08.2 - Queue Semantics]]).

### Testing it

```python
async def test_no_event_lost_on_crash():
    for kill_point in ["after_commit", "after_send", "before_mark"]:
        doc_id = await create_document_with_crash(kill_point)
        await run_relay_until_drained()
        events = await consume_all()
        assert len([e for e in events if e["document_id"] == doc_id]) >= 1
```

**Assert at-least-once, not exactly-once.** The relay's contract is that nothing is lost; duplicates are the consumer's problem.

Then separately assert that consumers deduplicate correctly.

### When you do not need it

⚠️ **The outbox is not free** — a table, a relay process, monitoring, and latency.

```
Does a lost event cause a real problem?
├── NO  → publish directly, accept the rare loss
│         (analytics samples, cache invalidation with a TTL backstop)
└── YES → outbox, or CDC
```

💡 **For Conduit: yes for `document.*` and `organisation.deleted`**, because the search index and offboarding depend on them. **No for analytics events**, where losing one in a thousand is invisible.

**Being explicit about which events need the guarantee keeps the outbox small and the relay fast.**

## Codebase

**Repo:** `debezium/debezium`, `eventuate-tram` (docs), `dotnet/aspnetcore` (or any outbox implementation)

**Question to answer:** How does Debezium's outbox event router work — what does it read, and how does it map an outbox row to a Kafka topic and key? Then: how does it guarantee ordering, and what does it do that a polling relay cannot?

**Read, in order:**

1. `debezium/debezium-core/src/main/java/io/debezium/transforms/outbox/EventRouter.java` — **the outbox event router.** How columns map to topic, key, headers and payload
2. `debezium/debezium-core/.../outbox/EventRouterConfigDefinition.java` — the expected table shape. **It is a convention worth adopting even if you poll**
3. `debezium/debezium-connector-postgres/` — how it reads the WAL, and why that gives commit ordering. **The answer to the second question**
4. **Eventuate Tram documentation** — a polling-based outbox with a well-documented ordering discussion
5. **microservices.io — Transactional outbox** — Chris Richardson's canonical write-up, including the polling versus log-tailing comparison

💡 The ordering answer is the valuable one: **CDC reads the WAL in commit order, so it does not have the `bigserial` visibility problem at all.** A polling relay sees rows in visibility order, which is not commit order. **That difference is the strongest technical argument for CDC over polling**, and it is subtle enough that most people implement polling and never notice.

**Part 1 — Lose events with dual writes.** A document creation that commits then publishes.

Kill the process at three points: after commit before send, mid-send, and after send before the response.

**Count lost events and phantom events over 1,000 attempts with random kills.**

Then try each naive fix — publish first, retry loop, after-commit hook — and **show that each still loses events**, with the count for each.

**Part 2 — Build the outbox.** Transactional insert, a relay with `SKIP LOCKED`, publish-then-mark, partitioned table.

**Re-run the crash matrix.** Assert zero lost events across all kill points, and record the duplicate rate.

Then assert consumers deduplicate correctly, so duplicates are harmless.

**Part 3 — The ordering problem, reproduced.** Two concurrent transactions where the one with the lower `bigserial` commits later.

Instrument the relay to log the order it publishes in. **Confirm it publishes 101 before 100.**

Then implement a relay that tracks a high-water mark on `id` instead of `published_at IS NULL`, and **show it losing row 100 entirely.**

**This is the subtle bug the note warns about, and reproducing it is the point.**

Then implement per-aggregate ordering and verify it.

**Part 4 — Failure modes.**

- **Relay down:** stop it for 10 minutes under load. Chart pending count and oldest age. **Confirm zero loss on recovery.**
- **Poison event:** one row that always fails to publish. **Confirm it blocks the batch**, then fix with skip-and-continue and confirm the rest flows.
- **Concurrent relays:** run three instances. Confirm no event is published twice by two relays, and measure throughput scaling.

**Part 5 — Latency, three ways.** Measure time from commit to consumer receipt for: 1-second polling, 100ms polling, `LISTEN`/`NOTIFY`, and CDC via Debezium.

**Chart p50 and p99 for each.** Then measure the database load each imposes — polling at 100ms is a query ten times a second, forever.

**Part 6 — Table growth and bloat.** 1,000 events/second for an hour.

Compare three cleanup strategies: delete on publish, mark and periodic delete, and mark with daily partitions.

Measure: table size, bloat percentage, vacuum time, and relay throughput as the table grows.

**The delete strategy should bloat badly.** Quantify it ([[06.7 - MVCC Vacuum and Bloat]]).

**Part 7 — The decision.** For every event in Conduit's catalogue, decide: outbox, direct publish, or neither.

**Justify each.** For every "direct publish", state what a lost event would cost and why that is acceptable.

Then measure the outbox's overhead — added write latency, database load — and confirm it is proportionate for the events that need it.

**Done when:**
- Naive dual writes lose events, and all three naive fixes still do
- The outbox loses zero events across every crash point
- You reproduced out-of-order publishing and the high-water-mark data loss
- A poison event blocked a batch, and skip-and-continue fixed it
- Your latency chart covers four relay strategies with their database cost
- The delete-on-publish strategy demonstrably bloats
- Every Conduit event has a justified outbox decision
