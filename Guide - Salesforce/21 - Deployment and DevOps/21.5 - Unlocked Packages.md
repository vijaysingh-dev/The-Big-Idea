# Unlocked Packages

## What problem they solve

Org development puts everything in one bucket. As it grows:

**Deployments are all-or-nothing.** A change to the claims module deploys alongside everything else, and a failing test anywhere blocks it.

**Dependencies are invisible.** The claims code depends on the core services, and nothing in the metadata says so.

**Ownership is unclear.** Two teams working in one directory conflict constantly.

**Nothing is versioned.** "Which version of the claims module is in UAT" has no answer.

**Unlocked packages make modules explicit** — versioned, installable, with declared dependencies.

## Unlocked versus managed

```
Unlocked    for your own org's modularity
            metadata remains editable in the target org
            no namespace required
            no security review

Managed     for distributing to other organizations
            source is hidden, global members are permanent
            namespace required
            security review for AppExchange
```

**"Unlocked" means the subscriber can still edit the metadata.** A change made in the target org is possible, and the next upgrade may overwrite it. That is deliberate: modularity without lock-in.

For distribution to other companies, see [[21.6 - Managed Packages and ISV Basics]].

## Structuring the packages

```
force-app/
    core/          objects, shared services, logging, utilities
    claims/        warranty claims: objects, automation, components
    contracts/     service contracts and coverage
    integration/   ERP sync, depending on all three
```

```json
{
  "packageDirectories": [
    {
      "path": "force-app/core",
      "default": true,
      "package": "Northwind Core",
      "versionNumber": "2.4.0.NEXT"
    },
    {
      "path": "force-app/claims",
      "package": "Northwind Claims",
      "versionNumber": "1.7.0.NEXT",
      "dependencies": [
        { "package": "Northwind Core", "versionNumber": "2.4.0.LATEST" }
      ]
    },
    {
      "path": "force-app/integration",
      "package": "Northwind Integration",
      "versionNumber": "1.2.0.NEXT",
      "dependencies": [
        { "package": "Northwind Core", "versionNumber": "2.4.0.LATEST" },
        { "package": "Northwind Claims", "versionNumber": "1.7.0.LATEST" }
      ]
    }
  ],
  "namespace": "",
  "sourceApiVersion": "62.0"
}
```

**Dependencies point one way.** Core knows nothing about Claims. The platform enforces this — a circular dependency fails at version creation.

**`LATEST` in a dependency** tracks the newest promoted version; a pinned version number holds it fixed. `LATEST` is simpler and couples the packages more tightly.

## Deciding the boundaries

The design work, and where most of the difficulty sits.

**By ownership, primarily.** A package maintained by two teams is a source of friction, and the whole point is independent release.

**By dependency direction.** If A and B each reference the other, they are one package or the shared part becomes a third.

**Shared metadata goes in the lowest common package.** A field on Account used by both Claims and Contracts belongs in Core.

**The hard case is standard objects.** Account and Case belong to Salesforce, so fields added to them go wherever needs them — and two packages both adding fields to Account creates a coupling that is easy to miss and awkward to unwind.

**A practical rule:** custom fields on a standard object go in the package that owns the *behaviour* using them, and if two packages need it, it goes in Core.

## Creating and versioning

```bash
sf package create \
  --name "Northwind Core" \
  --package-type Unlocked \
  --path force-app/core \
  --target-dev-hub my-devhub

sf package version create \
  --package "Northwind Core" \
  --installation-key-bypass \
  --code-coverage \
  --wait 30 \
  --target-dev-hub my-devhub

sf package version promote \
  --package "Northwind Core@2.4.0-7" \
  --target-dev-hub my-devhub
```

**Version creation builds the package in a temporary scratch org**, deploys the metadata, and runs the tests. It takes several minutes and fails on anything the metadata is missing — which is a useful completeness check in itself.

**`--code-coverage` computes coverage**, and **75% is required to promote**.

**Promotion is the release gate.** An unpromoted version can only be installed in a scratch org or sandbox; production requires a promoted version.

```
2.4.0-7
│ │ │ └── build number, assigned automatically
│ │ └──── patch
│ └────── minor
└──────── major
```

`NEXT` in `sfdx-project.json` increments the build automatically.

## Installing

```bash
sf package install \
  --package "Northwind Core@2.4.0-7" \
  --target-org uat \
  --wait 20 \
  --publish-wait 10

sf package installed list --target-org uat
```

**Dependencies must be installed first**, in order. A script for a full environment build:

```bash
#!/bin/bash
set -e

TARGET=$1

for PKG in "Northwind Core@2.4.0-7" "Northwind Claims@1.7.0-12" "Northwind Integration@1.2.0-4"; do
    echo "Installing $PKG"
    # --upgrade-type Mixed keeps subscriber changes where the package did not change them
    sf package install --package "$PKG" --target-org "$TARGET" \
      --wait 20 --upgrade-type Mixed --no-prompt
done

sf apex run --file scripts/apex/post-install.apex --target-org "$TARGET"
```

**`--upgrade-type`** controls how subscriber-side changes are handled:

```
Mixed          the default — package changes applied, other changes kept
DeprecateOnly  removed components are deprecated rather than deleted
Delete         removed components are deleted
```

## What deletion means

**Removing a component from the package deletes it from every org on upgrade**, along with its data.

```
Remove Claim_Legacy_Status__c from the package
    → upgrade
        → the field and every value in it are gone
```

**This is the sharpest edge of unlocked packages.** In org development, a field removed from the repository simply stays in the org. In a package, it is deleted.

The mitigations:

**Deprecate before removing.** Mark the field as unused, wait a release, then remove it.

**Use `--upgrade-type DeprecateOnly`** for a cautious upgrade.

**Check the version diff** before promoting:

```bash
sf package version report --package "Northwind Core@2.4.0-7" --target-dev-hub my-devhub
```

## Ancestry

For a package with real subscribers, ancestry establishes the upgrade path.

```json
{
  "path": "force-app/core",
  "package": "Northwind Core",
  "versionNumber": "2.5.0.NEXT",
  "ancestorVersion": "2.4.0.7"
}
```

**Without ancestry, a new version is not an upgrade** — it cannot be installed over the previous one, and the subscriber must uninstall first, losing data.

For an internal package deployed only by your own pipeline, ancestry can be skipped. For anything installed in orgs you do not control, it is required.

## Migrating an org into packages

The realistic sequence, because this is a project.

**1. Get everything into source control first.** Packages need a complete, working repository. An org-development org with partial retrieval cannot be packaged.

**2. Map the dependencies.** Which classes reference which objects, which flows call which Apex. The dependency query is the starting point:

```sql
SELECT MetadataComponentName, MetadataComponentType,
       RefMetadataComponentName, RefMetadataComponentType
FROM MetadataComponentDependency
```

**3. Extract Core first.** The shared utilities, logging, and base objects that everything depends on. This is the hardest package to get right and the one everything else waits on.

**4. Extract one feature package.** Prove the model end to end — create, version, install, upgrade — before extracting the rest.

**5. Extract the remainder incrementally**, keeping the unpackaged directory as the residue.

**6. Accept a permanent unpackaged remainder.** Some metadata — profiles, org settings, standard object layouts — is awkward to package and reasonable to leave in a plain directory.

**The most common failure:** attempting to package everything at once, discovering a circular dependency between two large areas, and abandoning the effort. Extracting Core and one feature first surfaces that problem while it is still small.

## Testing a package

```bash
sf org create scratch --definition-file config/project-scratch-def.json --alias pkg-test --duration-days 1

sf package install --package "Northwind Core@2.4.0-7" --target-org pkg-test --wait 20
sf package install --package "Northwind Claims@1.7.0-12" --target-org pkg-test --wait 20

sf apex run test --test-level RunLocalTests --target-org pkg-test --wait 30
sf org delete scratch --target-org pkg-test --no-prompt
```

**Testing the upgrade path** matters more than testing a fresh install:

```bash
sf package install --package "Northwind Core@2.3.0-4" --target-org upgrade-test --wait 20
sf data import tree --plan data/seed-plan.json --target-org upgrade-test
sf package install --package "Northwind Core@2.4.0-7" --target-org upgrade-test --wait 20
# verify the seeded data survived
```

A fresh install always works; an upgrade over existing data is where deletions and field changes cause damage.

## The costs, honestly

**Dependency management is real work.** A change to a Core object can break three dependent packages, and finding out means building and installing them.

**Version creation is slow.** Several minutes per package, which lengthens the pipeline.

**Circular dependencies force restructuring**, sometimes substantially.

**Deletion is destructive.** The org-development safety net is gone.

**Cross-package references are constrained.** A flow in one package referencing an Apex class in another works and creates a dependency that must be declared.

**Not everything packages cleanly.** Profiles, some org settings, and certain Experience Cloud metadata are awkward.

## When to adopt

**Adopt when:**

- Several teams conflict in one repository
- Deployments fail on unrelated tests
- You cannot release one feature without releasing everything
- Shared utilities are copied between orgs
- The repository is complete and source control is working

**Do not adopt when:**

- One or two developers maintain the org
- The repository is incomplete
- Deployments are not currently painful
- Nobody will own the dependency graph

**The prerequisite is a complete repository.** Packaging an org where half the configuration was never retrieved produces a package that does not work, and the effort is wasted.

## Practical guidance

**Extract Core first**, then one feature, then the rest.

**Keep dependencies one-directional**, and expect to restructure where they are not.

**Deprecate before removing** — deletion takes the data with it.

**Test the upgrade path**, not just a fresh install.

**Script the install sequence**, since order matters.

**Set ancestry** for anything installed in orgs you do not control.

**Accept an unpackaged remainder** rather than forcing everything.

**Get source control complete first.** Nothing else works without it.
