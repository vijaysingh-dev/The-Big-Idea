# Metadata Filtering and Hybrid Search

## Why Metadata Filtering Matters

Pure vector search finds semantically similar content, but production RAG systems need to constrain results to:

- Documents from a specific source ("only Confluence")
- Documents from a specific time ("after 2024-01-01")
- Documents accessible to the current user (ACL)
- Documents of a specific type ("only code files")

Metadata filtering applies these constraints during vector search.

---

## The Filtering Challenge in ANN

ANN indexes are built assuming you'll search the full vector space. Adding a filter changes the effective search space, breaking the index structure's assumptions.

```
Without filter: search all 10M vectors → HNSW finds top-K efficiently
With filter:    search only 10K vectors matching filter → HNSW was built for 10M
```

If the filtered subset is small (< ~1% of index), HNSW performs poorly — it navigates toward dense regions that may be filtered out, then has to backtrack.

---

## Pre-filtering vs Post-filtering vs In-filtering

### Post-filtering (Naive, Often Wrong)

Run ANN search first, then discard non-matching results:

```python
results = vector_store.search(query, top_k=10)
filtered = [r for r in results if r.metadata["source"] == "confluence"]
```

**Problem**: If only 2 of the top-10 pass the filter, you return 2 results even though 10 exist in the database matching both the query and filter. Low recall when filter is selective.

**Fix**: Retrieve `top_k * (1/filter_selectivity)` to compensate:

```python
estimated_k = int(10 / filter_selectivity)  # e.g., 10 / 0.1 = 100
results = vector_store.search(query, top_k=estimated_k)
filtered = [r for r in results if passes_filter(r)][:10]
```

Works but is wasteful and breaks down with very selective filters.

### Pre-filtering (Better for Selective Filters)

Apply the filter first, then run exact search on the matching subset:

```python
# Get all document IDs matching the filter
matching_ids = metadata_store.query({"source": "confluence", "date": {"$gte": "2024-01-01"}})

# Exact search within the matching subset
results = vector_store.search_subset(query, subset_ids=matching_ids, top_k=10)
```

**Problem**: If the matching subset is large (millions of documents), exact search is slow. **When to use**: Highly selective filters + small index, or when you have a good metadata index to quickly identify matching IDs.

### In-filtering (Best General Approach)

The filter is applied _during_ ANN graph traversal. The ANN algorithm explores graph neighbors but skips nodes that don't match the filter.

Qdrant, Weaviate, and Vespa implement this. The index is augmented with a payload index for efficient in-traversal filtering.

```python
# Qdrant example — filter applied during HNSW traversal
results = qdrant_client.search(
    collection_name="documents",
    query_vector=query_embedding,
    query_filter=Filter(
        must=[
            FieldCondition(key="source", match=MatchValue(value="confluence")),
            FieldCondition(key="date", range=DatetimeRange(gte="2024-01-01")),
        ]
    ),
    limit=10
)
```

**How Qdrant implements this**: Builds a separate inverted index for filterable fields. During HNSW traversal, only nodes passing the filter are considered as candidates. Automatically switches to brute-force when the filtered set is very small (< configured threshold).

## Metadata Index Design

For efficient filtering, decide which fields to index:

```python
# Qdrant collection schema with payload indexes
qdrant_client.create_payload_index(
    collection_name="documents",
    field_name="source",       # string → for equality filters
    field_schema=PayloadSchemaType.KEYWORD,
)

qdrant_client.create_payload_index(
    collection_name="documents",
    field_name="created_at",   # datetime → for range filters
    field_schema=PayloadSchemaType.DATETIME,
)

qdrant_client.create_payload_index(
    collection_name="documents",
    field_name="tenant_id",    # multi-tenancy isolation
    field_schema=PayloadSchemaType.KEYWORD,
)
```

**Rule**: Index fields that appear in `WHERE`-like conditions. Don't index fields only used for display (title, URL).

## Hybrid Search in Vector DBs

Most production vector DBs now support hybrid search natively — combining BM25 keyword scoring with ANN vector scoring in a single query.

### Qdrant Hybrid Search

```python
results = qdrant_client.query_points(
    collection_name="documents",
    prefetch=[
        Prefetch(query=sparse_vector, using="sparse", limit=100),   # BM25
        Prefetch(query=dense_vector, using="dense", limit=100),      # ANN
    ],
    query=FusionQuery(fusion=Fusion.RRF),   # Merge with RRF
    limit=10,
)
```

### Vespa Hybrid Search

```
select * from documents where
    ({targetHits: 100}nearestNeighbor(embedding, q))   /* ANN */
    or
    userQuery()                                          /* BM25 */
| rank using: hybrid_rank_profile                       /* Combined scoring */
```

Vespa's advantage: BM25 and ANN are computed in the same distributed query with no network hop between systems.

### Elasticsearch / OpenSearch Hybrid

```json
{
  "knn": {"field": "embedding", "query_vector": [...], "k": 100, "num_candidates": 200},
  "query": {"match": {"content": "query terms"}},
  "_source": ["title", "content"],
  "rank": {"rrf": {}}
}
```

Elasticsearch 8.x+ supports native hybrid search with RRF via the `rank` parameter.

## Choosing Between Pre/Post/In-Filtering

```
Filter selectivity:
├── > 50% of index passes filter (broad filter)
│   → Post-filtering: search full index, filter results
│
├── 1–50% of index passes filter (moderate)
│   → In-filtering: modern vector DBs handle this well
│
└── < 1% of index passes filter (very selective)
    ├── Tenant isolation → use separate collections per tenant
    └── Otherwise → Pre-filtering then exact search
```

**Practical rule**: Start with in-filtering (Qdrant, Weaviate, Vespa all support it). Only optimize further if latency is unacceptable.

## Multi-tenancy Patterns

### Pattern 1: Shared Index with Tenant Filter (Simple)

All tenants in one index, filtered at query time:

```python
filter = {"tenant_id": current_tenant_id}
```

**Pros**: Simple, single index to manage. **Cons**: Noisy neighbors, hard to delete all data for one tenant, privacy risk from filter bypass bugs.

### Pattern 2: Separate Collections Per Tenant (Safer)

```python
collection_name = f"tenant_{tenant_id}"
qdrant_client.search(collection_name=collection_name, ...)
```

**Pros**: Hard isolation, easy tenant deletion, independent scaling. **Cons**: Many collections to manage (but Qdrant handles this well; Pinecone charges per index).

### Pattern 3: Namespace (Pinecone model)

Some vector DBs support namespaces — logical partitions within a single index:

```python
pinecone_index.upsert(vectors=..., namespace=tenant_id)
pinecone_index.query(vector=..., namespace=tenant_id)
```
