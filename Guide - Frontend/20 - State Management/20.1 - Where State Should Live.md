# Where State Should Live

Most state management problems are placement problems. Before choosing a library, classify the state — the right home is usually obvious once you do.

## The five kinds of state

**1. Server state** — data owned by the backend. Users, products, orders.

It is not really "state" in the React sense; it is a **cache** of something owned elsewhere. It goes stale, needs revalidation, deduplication, retries and cancellation. Putting it in `useState` or Redux means reimplementing all of that badly ([[24.6 - TanStack Query Fundamentals]]).

This is the single most consequential distinction, and it typically accounts for 60–80% of what people think they need a state library for.

**2. URL state** — the current route, filters, search query, pagination, selected tab, open modal.

Belongs in the URL, not in memory. Putting it there gives you shareable links, browser back/forward, refresh survival and bookmarkability for free:

```jsx
const [params, setParams] = useSearchParams();
const page = Number(params.get("page") ?? 1);
```

The test: **should refreshing the page preserve this?** If yes, it belongs in the URL.

**3. Local UI state** — an input value, an open/closed flag, hover state, a form draft.

`useState` in the component that owns it. Most state in a well-structured application is this.

**4. Shared client state** — the theme, an authenticated user object, a shopping cart before checkout, feature flags.

Genuinely global, genuinely client-owned. This is what state libraries are actually for — and there is usually far less of it than expected.

**5. Form state** — technically local, but with enough specific requirements (validation, dirty tracking, per-keystroke render cost) that it deserves its own tool ([[21.3 - React Hook Form]]).

## The decision sequence

```
Does it come from the server?          → a data library
Should it survive a refresh / be shareable? → the URL
Is it used by one component?           → useState
Is it used by a few nearby components? → lift to the closest common parent
Is it used across distant parts of the tree? → context (rarely changing) or a store
```

Work top to bottom. Reaching for a store first is the common mistake, and it usually means server state ends up in a global store where it becomes stale and hand-managed.

## Lifting state up

```jsx
// Sibling components both need the filter
function Page() {
  const [filter, setFilter] = useState("");
  return (
    <>
      <FilterBar value={filter} onChange={setFilter} />
      <Results filter={filter} />
    </>
  );
}
```

Lift to the **closest** common ancestor, not to the top. Every level you lift past enlarges the subtree that re-renders ([[19.1 - What Causes Re-renders]]).

The reverse operation matters equally — **push state down** when only a small part of a tree uses it:

```jsx
// Before — the whole page re-renders per keystroke
function Page() {
  const [query, setQuery] = useState("");
  return <><input value={query} onChange={...} /><Dashboard /></>;
}

// After
function Page() {
  return <><SearchBox /><Dashboard /></>;
}
```

## When prop drilling is fine

Two or three levels of passing a prop is not a problem. It is explicit, traceable and typed.

Prop drilling becomes a problem at five-plus levels, or when intermediate components take props they do not use purely to forward them.

Before reaching for context, try composition ([[16.3 - Components and Props]]):

```jsx
// Drilling
<Page user={user}><Sidebar user={user}><Profile user={user} /></Sidebar></Page>

// Composition — no drilling, no context
<Page sidebar={<Sidebar><Profile user={user} /></Sidebar>} />
```

## Derived state does not belong anywhere

```jsx
// Redundant — two sources of truth
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

// Correct
const [items, setItems] = useState([]);
const total = items.reduce((s, i) => s + i.price, 0);
```

Every stored derived value is a synchronization path that can break. Compute during render; memoize only if measured ([[17.6 - useMemo]]).

The same applies at the store level — a store holding both `items` and `itemCount` is a store with a bug waiting to happen. Selectors derive; state stores.

## A worked example

An e-commerce product listing page:

| State | Home | Why |
| --- | --- | --- |
| Product list | data library | server-owned, cacheable |
| Category filter | URL | shareable, back-button |
| Sort order | URL | shareable |
| Page number | URL | shareable |
| Search query | URL (debounced) | shareable |
| Cart contents | store + persistence | crosses routes, survives navigation |
| "Add to cart" pending | data library mutation | server operation |
| Quick-view modal open | `useState` local | ephemeral |
| Hovered card | `useState` local | ephemeral |
| Theme | context | rarely changes, read widely |

Very little of this needs a global store. That is typical — most applications need a store for two or three things.

## Signals that placement is wrong

**A global store full of server data.** It will go stale, and you will hand-write refetching.

**Filters in `useState`.** Sharing a filtered view by URL becomes impossible, and refresh loses the state.

**An effect syncing two pieces of state.** One of them is derived ([[17.4 - useEffect Pitfalls]]).

**Context re-rendering the whole app.** Either the value is unmemoized, or the context mixes fast- and slow-changing data ([[17.9 - useContext]]).

**Props threaded through five layers.** Composition or context.

**Reaching for Redux on day one.** Add it when a concrete problem appears.

## Persistence

Separate from placement, but related:

```jsx
// Survives refresh, per-tab
sessionStorage

// Survives close, shared across tabs
localStorage

// Server-owned, survives everywhere
the backend
```

Cart contents and drafts are common `localStorage` candidates ([[14.2 - LocalStorage and SessionStorage]]). Auth tokens deserve careful thought ([[15.5 - JWT Sessions and Token Storage]]).

## How senior engineers actually use this

**They classify before choosing.** Server, URL, local, shared — the answer follows from the classification.

**They put far more in the URL than most people do.** Filters, tabs, sort, pagination and even open panels. It costs nothing and removes a whole class of state management.

**They keep state as local as possible** and lift only when a second consumer appears.

**They keep server data out of client stores**, which eliminates the majority of stale-data bugs.

**They add a global store late**, when there is a specific thing that genuinely needs it.

## Common pitfalls

- Server data in Redux or `useState`, with hand-rolled caching.
- Filters and tabs in component state, breaking links and refresh.
- Lifting state higher than necessary, enlarging re-render scope.
- Storing derived values.
- Reaching for context to avoid two levels of prop passing.
- Adding a state library before there is a problem it solves.

## Interview angle

"Where should state live" and "how do you decide between Context and Redux" both benefit from the classification framing rather than a feature comparison. Lead with the four categories — server, URL, local, shared — and note that server state is the largest slice and belongs in a data library, and that URL state is the most under-used option. Then the decision sequence: local first, lift to the closest common parent, composition before context, store last. That framing is more convincing than any library comparison.
