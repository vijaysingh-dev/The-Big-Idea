# Timeouts and Deadlines Across Hops

#backend #http #reliability #distributed-systems

> **In one line:** A timeout is a local guess about how long to wait; a deadline is an absolute instant shared across every hop — and switching from one to the other is what stops a slow dependency from consuming your entire system.

---

## The Idea

Every service in a chain sets its own timeout. Each one is reasonable in isolation.

```
Client        30s
  → Gateway   30s
    → API     30s
      → Search 30s
        → DB   30s
```

The client gives up at 30 seconds. But the gateway, API, search service and database all keep working for their full 30 seconds on a request nobody is waiting for.

That is wasted work at every layer, held connections at every layer, and occupied workers at every layer — precisely during the overload that caused the slowness in the first place.

💡 **The fix is to propagate a deadline rather than a duration.** "This request must be finished by 14:32:07.500" travels with the request. Every hop knows the real remaining budget and can stop immediately when it is gone.

---

## Timeout vs Deadline

| | Timeout | Deadline |
|---|---|---|
| Expressed as | Duration ("30 seconds") | Instant ("14:32:07.500Z") |
| Set by | Each hop, independently | The caller, once |
| Travels | No | Yes, in a header or metadata |
| Budget | Resets at every hop | Shared across all hops |

```python
# Timeout thinking — each hop starts its clock from zero
async with asyncio.timeout(5):
    await downstream.call()

# Deadline thinking — the budget is already partly spent
remaining = deadline - time.monotonic()
if remaining <= 0:
    raise DeadlineExceeded()
async with asyncio.timeout(remaining):
    await downstream.call(deadline=deadline)
```

gRPC has this built in — deadlines are part of the protocol and propagate automatically. HTTP does not, so you implement it yourself.

## Implementing Deadline Propagation

### The header

There is no standard, but two conventions are common:

```http
X-Request-Deadline: 2026-08-17T14:32:07.500Z     # absolute
grpc-timeout: 4500m                               # remaining, gRPC style
```

⚠️ **Absolute deadlines require synchronised clocks.** Servers within a datacentre running NTP are typically within a few milliseconds, which is fine. Across organisational boundaries or to a mobile client, clock skew makes absolute deadlines unusable — use a remaining-duration header instead, recomputed at each hop.

For internal services, absolute is simpler and self-correcting. For anything crossing a trust boundary, use remaining duration.

### The middleware

```python
from contextvars import ContextVar

_deadline: ContextVar[float | None] = ContextVar("deadline", default=None)

def remaining() -> float | None:
    d = _deadline.get()
    return None if d is None else d - time.monotonic()


class DeadlineMiddleware:
    def __init__(self, app, default_budget: float = 10.0, max_budget: float = 60.0):
        self.app = app
        self.default_budget = default_budget
        self.max_budget = max_budget

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)

        headers = dict(scope["headers"])
        raw = headers.get(b"x-request-timeout-ms")

        budget = self.default_budget
        if raw:
            try:
                budget = min(int(raw) / 1000, self.max_budget)
            except ValueError:
                pass

        if budget <= 0:
            return await self._deadline_exceeded(send)

        token = _deadline.set(time.monotonic() + budget)
        try:
            async with asyncio.timeout(budget):
                await self.app(scope, receive, send)
        except TimeoutError:
            await self._deadline_exceeded(send)
        finally:
            _deadline.reset(token)
```

⚠️ **`max_budget` matters.** Without a cap, a client can send `X-Request-Timeout-Ms: 3600000` and occupy a worker for an hour. Any client-supplied budget must be clamped to something you are willing to honour.

### Passing it downstream

```python
async def call_downstream(client: httpx.AsyncClient, url: str):
    rem = remaining()
    if rem is not None and rem <= 0:
        raise DeadlineExceeded("no budget left")

    headers = {}
    if rem is not None:
        headers["X-Request-Timeout-Ms"] = str(int(rem * 1000))

    return await client.get(url, headers=headers, timeout=rem)
```

💡 **Using `contextvars` means the deadline follows the request through your whole call stack without threading it through every function signature.** It also propagates into `asyncio.to_thread` calls, which is exactly what you want. This is the cleanest use of `contextvars` in a backend service.

⚠️ It does **not** propagate through `BaseHTTPMiddleware` reliably ([[01.9 - ASGI and How Uvicorn Serves a Request]]), which is one more reason to write pure ASGI middleware for anything involving context.

## Budget Allocation

Given 10 seconds, how do you spend it?

```
Total budget                      10.0s
├── Auth check                     0.3s
├── Fetch document (DB)            1.0s
├── Search service                 4.0s
│   ├── its own DB                 2.0s
│   └── embedding service          1.5s
├── Enrich (parallel)              2.0s
└── Serialise + send               0.5s
                                  ─────
Allocated                          7.8s
Headroom                           2.2s
```

Three rules:

**1. Children must sum to less than the parent.** Otherwise the parent's deadline never usefully fires.

**2. Leave headroom.** Network hops, serialisation, and scheduling delay all cost time that does not appear in your call list. 20–30% headroom is reasonable.

**3. Parallel calls share the wall clock, not the budget.** Three calls in a `TaskGroup` with 2 seconds each consume 2 seconds total, not 6.

### Deriving the numbers

Do not invent them. Measure.

```
Downstream p99 = 800ms
Timeout        = p99 × 1.5 = 1200ms
```

⚠️ **Setting a timeout at p50 means you fail half of your slow-but-valid requests.** Setting it at p99.9 means you wait far too long on genuine failures. **p99 × 1.5** is a reasonable starting point, adjusted by how much you care about the tail.

💡 A timeout is a statement about what you consider a failure. If a call normally takes 100ms and you set a 30-second timeout, you have decided that a 200× slowdown is acceptable — which it almost never is. **Most production timeouts are far too generous**, usually because they were set once, defensively, and never revisited.

## Retries Within a Budget

Retries and deadlines interact, and getting this wrong is expensive.

```python
async def call_with_retry(fn, attempts=3):
    for i in range(attempts):
        rem = remaining()
        if rem is None or rem <= 0:
            raise DeadlineExceeded()

        # Do not start an attempt that cannot finish
        if rem < MIN_ATTEMPT_TIME:
            raise DeadlineExceeded("insufficient budget for another attempt")

        try:
            async with asyncio.timeout(min(rem, PER_ATTEMPT_TIMEOUT)):
                return await fn()
        except (TimeoutError, RetryableError):
            if i == attempts - 1:
                raise
            backoff = min(rem / 4, 0.2 * 2 ** i)
            await asyncio.sleep(random.uniform(0, backoff))
```

Two ideas worth extracting:

**Do not start an attempt you cannot finish.** With 200ms remaining and a dependency whose p50 is 400ms, starting another attempt guarantees a timeout while consuming a connection and a worker on both sides. Fail immediately instead.

**Backoff must fit inside the budget.** A 2-second backoff with 500ms remaining means you never retry at all — you just wait and then fail. Scale the backoff to the remaining budget.

## In Production

### Every network call needs a timeout

⚠️ **A missing timeout is not "no limit" — it is "whatever TCP does", which can be 15 minutes.** One unresponsive dependency with no timeout will exhaust every pool you have.

```python
# Audit rule: every one of these must have an explicit number
httpx.AsyncClient(timeout=...)
asyncpg.create_pool(command_timeout=..., timeout=...)
redis.Redis(socket_timeout=..., socket_connect_timeout=...)
aiokafka.AIOKafkaProducer(request_timeout_ms=...)
boto3.client(config=Config(connect_timeout=..., read_timeout=...))
```

`redis-py`'s `socket_timeout` defaults to `None`. That single default has caused a lot of outages.

### The four HTTP timeouts

```python
httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=1.0)
```

| Timeout | Catches |
|---|---|
| `connect` | Host unreachable, firewall dropping |
| `read` | Server accepted but is not responding |
| `write` | Cannot push the request body |
| `pool` | **Your own** pool is exhausted |

💡 **Setting one combined number means you cannot distinguish these in your metrics**, and they need entirely different responses. `connect` failures mean the dependency is down. `pool` failures mean *you* are the problem. Label your timeout metrics by type.

### Client disconnect should cancel work

```python
@app.get("/search")
async def search(q: str, request: Request):
    if await request.is_disconnected():
        raise HTTPException(499)
    return await do_search(q)
```

Better: uvicorn cancels the task on disconnect, so structured concurrency handles it automatically ([[01.7 - Cancellation and Structured Concurrency]]). What matters is that your downstream calls are inside the cancellable scope, so the cancellation propagates rather than being shielded.

⚠️ **But a multi-step state change must not depend on the client staying connected.** Write a durable record and enqueue the rest ([[03.4 - Idempotency and Safe Retries]]).

### Metastable failure

The failure mode that deadlines are really protecting you against.

```
1. A dependency slows down
2. Requests take longer, so more are in flight simultaneously
3. Connection pools and workers fill
4. Queueing adds latency, so requests take even longer
5. Clients time out and retry, adding load
6. The dependency recovers — but the system does not
```

⚠️ **Step 6 is the important one.** The system is now sustaining its own overload through queued work and retries. Removing the original cause does not fix it. You need to shed load or restart to break the cycle.

Deadlines break the loop at step 3: work with an expired deadline is dropped immediately rather than queued, so the queue cannot grow without bound. This is why deadline propagation is a resilience feature, not a tidiness feature.

Pairs with load shedding ([[11.4 - Backpressure and Load Shedding]]) and circuit breakers ([[11.3 - Circuit Breakers and Bulkheads]]).

### Observability

```python
timeout_total.labels(dependency="search", kind="read").inc()
deadline_remaining_at_start.labels(endpoint="/search").observe(remaining())
deadline_exceeded_total.labels(hop="search").inc()
```

**Track the remaining budget when each hop starts.** If a downstream service consistently receives requests with 200ms left, your allocation upstream is wrong, and you will see a wave of deadline-exceeded errors that look like the downstream's fault and are not.

💡 This one metric — budget-remaining-on-arrival — turns "the search service is timing out" into "the API service is allocating it too little time", which are completely different investigations.

## Codebase

**Repo:** `grpc/grpc`, `envoyproxy/envoy`, `encode/httpx`

**Question to answer:** gRPC has deadline propagation built in. Find where the deadline is serialised into the wire format, how it is converted between absolute and relative across hops, and what a server does when it arrives already expired. Then: how does Envoy compute the timeout it passes to an upstream, and what does `x-envoy-expected-rq-timeout-ms` do?

**Read, in order:**

1. `grpc/src/python/grpcio/grpc/_channel.py` — how a Python client deadline becomes wire metadata
2. `grpc/src/core/lib/transport/timeout_encoding.cc` — **the encoding itself.** gRPC sends *remaining time*, not an absolute instant, precisely to avoid clock-skew problems. Note the compact format
3. `grpc/src/core/lib/surface/call.cc` — server-side deadline handling, including the already-expired case
4. `envoy/source/common/router/router.cc` — search for `timeout` and `x-envoy-expected-rq-timeout-ms`. **Envoy subtracts the time already spent** before passing the budget on. This is deadline propagation done properly at the infrastructure layer
5. `httpx/_config.py` and `httpcore/_async/connection_pool.py` — the four timeouts and where each is enforced

💡 The gRPC design decision in step two is the key insight: **relative time, recomputed at each hop, rather than an absolute timestamp.** It sacrifices a little precision to eliminate an entire class of clock-skew bugs. When you build this yourself over HTTP, copy that choice unless you fully control clock synchronisation.

**Size:** 1 session.

```
└── README.md
```

**Part 1 — Build the chain.** Four services. The deepest one has controllable latency via toxiproxy. Each hop naively sets a 30-second timeout.

Instrument every hop to record: work started, work completed, and whether the caller was still waiting when it finished.

**Part 2 — Measure the waste.** Client timeout at 2 seconds. Make the deepest service take 20 seconds.

Count: how many hops kept working after the client gave up, for how long, and how many connections and workers were held.

Then run this at 100 requests per second and watch the pools fill. **Chart in-flight work versus useful work.** The gap is what deadline propagation recovers.

**Part 3 — Implement propagation.** Deadline middleware with contextvars, a client wrapper that passes the remaining budget, and a `max_budget` clamp.

Re-run part 2. Every hop should stop within milliseconds of the client giving up. **Chart the same in-flight-versus-useful graph and put it beside the first one.** This pair of charts is the argument.

**Part 4 — Allocate a budget.** Give the top-level 5 seconds. Allocate it across the chain with headroom. Add parallel calls in one hop and confirm they share wall-clock time rather than budget.

Then deliberately over-allocate — children summing to more than the parent — and show that the parent's deadline becomes the only one that ever fires, making the child timeouts decorative.

**Part 5 — Retries inside a budget.** Implement retry logic that respects the remaining budget.

Test three cases: plenty of budget (retries happen), tight budget (retry refused because it cannot finish), and backoff longer than the remaining budget (backoff scaled down).

Then implement it *without* budget awareness and show it burning the entire budget on backoff, never actually retrying.

**Part 6 — Induce metastable failure.** This is the important experiment.

Sustained load at 80% of capacity. Then a 30-second latency spike in the deepest service. Then remove the spike.

Without deadlines: the system should **not** recover. Chart latency and queue depth continuing to climb after the cause is gone. Record how long it stays broken and what finally fixes it.

With deadlines plus load shedding: it should recover within seconds of the cause being removed.

**This is the single most valuable experiment in section 03.** Metastable failure is the thing that turns a blip into a multi-hour incident, and having caused one yourself makes the whole category legible.

**Part 7 — Budget metrics.** Export budget-remaining-on-arrival per hop. Deliberately misallocate the budget upstream and show the metric identifying the true cause while the error messages point at the wrong service.

**Done when:**
- Your before/after in-flight-work charts are side by side
- Every hop stops within 100ms of the client disconnecting
- Over-allocation is demonstrated to make child timeouts meaningless
- Budget-aware retries refuse attempts they cannot finish
- You induced a metastable failure that did not self-recover, and then prevented it
- Your budget metric correctly blames the upstream misallocation
