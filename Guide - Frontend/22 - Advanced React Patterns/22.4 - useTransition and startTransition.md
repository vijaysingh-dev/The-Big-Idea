# useTransition and startTransition

Marks a state update as **non-urgent**, so React can interrupt it to handle more urgent work first.

```jsx
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  setQuery(e.target.value);                       // urgent — input must respond
  startTransition(() => {
    setResults(filterLargeList(e.target.value));  // non-urgent — interruptible
  });
}
```

## The problem it solves

```jsx
function Search() {
  const [query, setQuery] = useState("");
  const results = filterHugeList(query);   // 300ms

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <Results items={results} />
    </>
  );
}
```

Every keystroke blocks the main thread for 300ms. Characters appear late, the cursor stutters, and the app feels broken ([[18.5 - Concurrent Rendering and the Scheduler]]).

Both updates were treated as equally urgent. They are not: the input must respond within a frame; the results can lag.

## What a transition actually does

Inside `startTransition`, updates are assigned a lower-priority lane. React then:

- **Renders in the background** while the browser stays responsive
- **Interrupts and restarts** if a higher-priority update arrives
- **Keeps the previous UI on screen** until the new one is ready — no blanking

```
keystroke "rea" → urgent: input updates, commits immediately
                → transition: begin rendering results
keystroke "reac" → urgent: input updates, commits
                → previous transition render DISCARDED, restarted with "reac"
```

The discarded render is why purity matters — any side effect in it happened with no corresponding commit ([[16.5 - Rendering and Purity]]).

## isPending

```jsx
<div style={{ opacity: isPending ? 0.6 : 1 }}>
  <Results items={results} />
</div>
```

`isPending` is true while the transition renders. The convention is to **dim stale content** rather than replace it with a spinner — the user keeps seeing usable data while the update lands.

Note that reading `isPending` re-renders the component, so `useTransition` belongs in the component that needs the indicator, not at the root.

## useTransition vs startTransition

```jsx
import { useTransition, startTransition } from "react";

const [isPending, startTransition] = useTransition();   // hook — provides isPending
startTransition(() => setState(x));                      // standalone — no isPending
```

The standalone import is for code outside components — a store action, a router, an event listener. Use the hook when you need the pending state.

## Requirements and limits

**The update must be synchronous inside the callback:**

```jsx
// Broken — the setState happens after the transition scope ends
startTransition(async () => {
  const data = await fetch(url).then(r => r.json());
  setResults(data);
});

// Correct — await outside, transition around the update
const data = await fetch(url).then(r => r.json());
startTransition(() => setResults(data));
```

React 19 added async transition support for Actions, but the general rule for plain state updates still holds: the setter must run synchronously within the callback.

**It does not make anything faster.** A 2-second render wrapped in a transition is still 2 seconds; it just stops blocking input. If the work is genuinely too slow, the fix is doing less work — memoization, virtualization, or moving it off the main thread ([[19.5 - Virtualization and Windowing]], [[08.4 - Web Workers]]).

**Yielding is per component, not per millisecond.** A single component doing 200ms of synchronous work cannot be interrupted mid-function. Transitions help when the cost is spread across many components.

**Do not wrap urgent updates.** Input values, toggles, checkbox state and anything the user expects to respond instantly should stay urgent. Wrapping them makes the UI feel laggy.

## With Suspense

The most valuable interaction. Without a transition, an update that suspends replaces visible content with the fallback:

```jsx
// Content vanishes, skeleton appears, new content appears
setTab("photos");

// Old content stays visible while the new tab loads
startTransition(() => setTab("photos"));
```

Inside a transition, React keeps the current UI and renders the new one in the background, swapping only when ready ([[19.4 - Suspense]]).

This is why routers wrap navigations in transitions — React Router and Next.js do it internally, which is why navigation does not blank the page.

## Actions (React 19)

Async functions passed to `action` or `formAction` are automatically transitions:

```jsx
const [state, formAction, isPending] = useActionState(
  async (prev, formData) => {
    await save(formData);
    return { success: true };
  },
  {}
);
```

React manages pending state, error handling and ordering. This is the idiomatic form-submission path in React 19 ([[21.2 - Validation Strategies]]).

`useOptimistic` composes with it to show expected results immediately ([[24.5 - Optimistic UI]]).

## Where transitions genuinely help

- **Search and filter over large datasets** — the canonical case
- **Tab switching** where the new panel is expensive
- **Route navigation** — usually handled by the router
- **Charts and visualizations** re-rendering on a control change
- **Rich text editors** with expensive derived views

The common shape: a cheap input driving an expensive output.

## Transition vs debounce vs deferred value

| | Mechanism | Best for |
| --- | --- | --- |
| Debounce | delays the work by time | network requests, rate-limited APIs |
| `useTransition` | deprioritizes an update you own | expensive rendering from a setter you control |
| `useDeferredValue` | lags a value you receive | expensive rendering from a prop or external value |

They are not interchangeable. Debouncing a network request avoids sending it; a transition does not reduce work, it reschedules it. For an expensive *render*, a transition beats a debounce because the update still starts immediately and simply yields ([[29.1 - Debounce and Throttle]]).

Choose `useDeferredValue` when you do not own the setter ([[22.5 - useDeferredValue]]).

## How senior engineers actually use this

**They separate urgent from non-urgent explicitly** — the input value urgent, everything derived from it in a transition.

**They dim rather than blank** using `isPending`, which reads as faster than a spinner.

**They wrap navigations and tab switches** so Suspense boundaries do not flash fallbacks.

**They do not use transitions to paper over slow code.** If the profiler shows one component costing 200ms, that is the thing to fix.

**They keep `useTransition` local** to the component showing the pending indicator.

## Common pitfalls

- Wrapping urgent updates, making the UI feel unresponsive.
- `async` inside `startTransition` with the setter after an `await`.
- Expecting a transition to make rendering faster.
- Using it instead of memoization or virtualization for genuinely heavy work.
- `useTransition` at the app root, re-rendering everything when `isPending` flips.
- Debouncing where a transition is more appropriate, adding artificial delay.

## Interview angle

"What is useTransition" should get: marks an update as non-urgent so React can interrupt it, keeping urgent updates like typing responsive, with `isPending` for a stale indicator. The strong follow-ups are the Suspense interaction — without a transition, a suspending update blanks visible content — and the honest limitation that it reschedules work rather than reducing it, so it is not a substitute for fixing genuinely slow renders.
