# Choosing the Right Async Tool

## The decision tree

Work through in order and stop at the first match.

**1. Does the user need the result on screen, from a slow external call?**
→ **Continuation**. The only mechanism where the user is still waiting.

**2. Is it more than a few thousand records?**
→ **Batch Apex**. Automatic chunking, fresh limits per chunk, real monitoring.

**3. Does it run on a clock?**
→ **Scheduled Apex** starting a batch, or a **scheduled flow** at low volume.

**4. Should several independent consumers react, or an external system?**
→ **Platform Events**.

**5. Does an external system need every record change?**
→ **Change Data Capture**.

**6. Does it need failure handling and retry?**
→ **Queueable with a Finalizer**.

**7. Anything else?**
→ **Queueable**. The general-purpose default.

`@future` appears nowhere in that list. It is legacy, and Queueable does everything it does with more capability. The one place it survives is the mixed-DML workaround, where it is marginally less code. See [[12.2 - Future Methods]].

## The comparison

| | Future | Queueable | Batch | Scheduled | Platform Event | CDC | Continuation |

| Volume | Small | Medium | 50M | Any | Per event | Automatic | One request |
| Parameters | Primitives | Any | Constructor | None | Event fields | Automatic | Request state |
| Callouts | Yes | Yes | Per chunk | Via a job | In subscriber | In subscriber | The point |
| Job Id | No | Yes | Yes | Yes | No | No | No |
| Chaining | No | Yes | Via finish | Reschedule | Via subscriber | No | Up to 3 |

| User waits | No | No | No | No | No | No | Yes |

## Worked decisions

**"Notify the ERP when a claim is approved."**
→ Queueable enqueued from the trigger. A callout cannot run after DML, and there is one consumer.

If the ERP, Slack, and an audit system all need to know, → platform event with three subscribers, so adding a fourth requires no change to the publisher.

**"Archive claims closed over three years ago."**
→ Batch Apex. Volume, chunking, and per-chunk limits.

**"Run the archive weekly."**
→ Scheduled Apex whose only job is `Database.executeBatch(new ClaimArchiveBatch(), 200)`.

**"Check inventory in the ERP when the agent opens the case."**
→ Continuation. The agent is waiting, and the call is slow.

**"Keep the data warehouse current."**
→ CDC with a Pub/Sub subscriber, if latency matters. `SystemModstamp` polling with the Bulk API if a nightly load is acceptable — simpler, and often the right answer.

**"Assign a permission set when a record is created."**
→ Queueable. `PermissionSetAssignment` is a setup object and cannot share a transaction with normal DML. See [[10.7 - Mixed DML and Setup Objects]].

**"Retry a failed integration up to three times with backoff."**
→ Queueable with a Finalizer. It is the only mechanism with a guaranteed post-failure hook.

**"Record why an async job failed."**
→ A Finalizer, which runs in its own transaction so the log survives. For synchronous code, a platform event with immediate publish.

**"Recalculate a roll-up across two million claims."**
→ Batch Apex, scope tuned down if the parent object has heavy automation.

**"Send a satisfaction survey seven days after case closure."**
→ A scheduled path on a record-triggered flow. Per-record timing, no sweep required, and no code. See [[07.3 - Record-Triggered Flows]].

## The mistakes that recur

**Enqueuing per record.**

```java
// 200 jobs, fails at 50
for (Warranty_Claim__c claim : Trigger.new) {
    System.enqueueJob(new SyncQueueable(new Set<Id>{ claim.Id }));
}
```

One job for the batch. Every async mechanism has an enqueue cap and shares a daily allocation.

**Passing records instead of Ids.** The record is a snapshot from enqueue time. Pass Ids and query fresh, unless you specifically need the old values.

**Assuming statics survive.** Every async execution is a new transaction. Recursion guards reset, caches reset, flags reset.

**Forgetting `Database.AllowsCallouts`.** The failure appears at runtime on the first callout, in a job that may only sometimes call out.

**No termination condition on a chain.** A Queueable chain with no exit runs until the org's daily async allocation is exhausted, affecting every other job.

**Non-idempotent event subscribers.** At-least-once delivery is a certainty. A subscriber that creates a record without an idempotency key will create duplicates.

**Asserting before `Test.stopTest()`.** The job has not run yet.

**Forgetting `Test.getEventBus().deliver()`.** Subscribers never run, and the test passes proving nothing.

**Scheduling everything at 02:00.** Five batch jobs run, the sixth waits, and it starts during business hours.

**No monitoring.** An async failure has no user to report to. A job failing nightly for a month is entirely normal in an org without alerting.

## Async under load

The behaviours that only appear at scale.

**Jobs queue.** Under load a Queueable may run minutes after enqueue. Anything with a real deadline must acknowledge that.

**The flex queue holds batch jobs** beyond the 5 concurrent limit, up to 100. Reordering is possible in Setup.

**The daily allocation is org-wide.** 250,000 executions, or 200 times the licence count. An integration enqueuing per record can starve every other job in the org.

**Event delivery counts per subscriber.** Five external systems on one event is five deliveries.

**Locking is worse in parallel.** Batch chunks processing children of the same parent contend. Sorting the query locator by parent Id fixes most of it. See [[10.8 - Record Locking and Deadlocks]].

## Monitoring, which is not optional

Three things worth having in any org relying on async work.

**A failure query, checked daily:**

```sql
SELECT Id, ApexClass.Name, JobType, Status, ExtendedStatus, NumberOfErrors,
       CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE Status IN ('Failed', 'Aborted') AND CreatedDate = LAST_N_DAYS:7
ORDER BY CreatedDate DESC
```

**A run log object**, written from `finish` or a Finalizer, recording what ran, how many records, and the outcome. This is what turns "the sync failed" into something diagnosable.

**Alerting on absence, not just failure.** A job that stopped running is as serious as one that failed, and only a run log detects it.

```sql
SELECT Job_Name__c, MAX(Started_At__c) lastRun
FROM Batch_Run_Log__c
GROUP BY Job_Name__c
```

Any job whose last run is older than its schedule interval is broken, and nothing else surfaces that.

## Section 12 in one paragraph

Async exists for four reasons: callouts cannot follow DML, each async execution gets a fresh limit budget, batch chunking is the only way to touch millions of records, and users should not wait for work they do not need. Queueable is the default — rich parameters, a job Id, chaining, and Finalizers for retry and logging — and future methods are legacy with no remaining advantage. Batch Apex is for volume, with `Database.Stateful` for cross-chunk accumulation and the important constraint that tests run only one chunk. Platform events decouple a publisher from its consumers and are the only reliable way to log something that rolls back; CDC does the same automatically for every record change, aimed at external replication. Everything async shares two properties that produce most of the bugs: statics reset because it is a new transaction, and delivery is at-least-once so handlers must be idempotent. And none of it reports failure to a user, which makes monitoring — including alerting on jobs that stopped running — part of the design rather than an afterthought.
