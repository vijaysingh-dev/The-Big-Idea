# What Causes Re-renders

A component re-renders for exactly four reasons. Everything else is a consequence of one of them.

1. **Its own state changed**
2. **Its parent re-rendered**
3. **A context it consumes changed**
4. **Its props changed** — but only if it is wrapped in `React.memo`

Reason 2 is the one people misunderstand.

## Parent renders re-render all children

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveChild />       {/* re-renders, even with no props */}
    </div>
  );
}
```

By default, React re-renders the entire subtree below the component whose state changed. Props are irrelevant — an unmemoized child re-renders because its parent did, not because anything it receives changed.

This surprises people who expect "props didn't change, so it should skip". React does not compare props unless you ask it to with `React.memo` ([[19.2 - React.memo and Memoization Strategy]]).

## Re-render is not DOM update

```jsx
function Static() {
  return <div className="box">Fixed</div>;
}
```

Re-rendering this a thousand times means a thousand function calls and a thousand element comparisons, and **zero DOM mutations**. The reconciler sees identical output and does nothing ([[18.2 - Reconciliation and the Diffing Algorithm]]).

So a re-render costs only the render itself, and the render is usually cheap. Chasing every re-render is a common waste of effort.

Re-renders become expensive when:

- The component tree below is large (hundreds or thousands of nodes)
- The render function does real work — filtering, sorting, formatting a big list
- It happens very frequently — on every keystroke, scroll or mouse move

Outside those cases, a re-render is a few microseconds.

## Composition beats memoization

The most effective fix is usually structural rather than a memo call.

**Move state down.** If only a small part of the tree uses the state, isolate it:

```jsx
// Before — the whole page re-renders on every keystroke
function Page() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ExpensiveDashboard />
    </>
  );
}

// After — only SearchBox re-renders
function Page() {
  return (
    <>
      <SearchBox />
      <ExpensiveDashboard />
    </>
  );
}
```

**Pass children as props.** This is the technique most worth internalizing:

```jsx
function Counter({ children }) {
  const [count, setCount] = useState(0);
  return (
    <div onClick={() => setCount(c => c + 1)}>
      {count}
      {children}     {/* NOT re-rendered */}
    </div>
  );
}

<Counter>
  <ExpensiveChild />
</Counter>
```

`children` is an element created in the *outer* component's render. When `Counter`'s state changes, `Counter` re-renders but `children` is the same element reference, so React skips that subtree entirely ([[18.1 - Virtual DOM and React Elements]]).

No `React.memo`, no `useMemo`, no dependency arrays — and it cannot go stale.

## Reference identity

When a child *is* memoized, these break the memo:

```jsx
<Child
  style={{ margin: 8 }}          // new object every render
  items={[]}                     // new array every render
  onClick={() => handle()}       // new function every render
  config={{ ...defaults }}       // new object every render
/>
```

`React.memo` compares with `Object.is`, and every literal has a fresh identity. The fixes are `useMemo`, `useCallback`, or hoisting constants to module scope:

```jsx
const STYLE = { margin: 8 };
const EMPTY = [];
```

The same applies to context values and hook dependency arrays ([[17.6 - useMemo]]).

## Context re-renders everything

```jsx
<AppContext.Provider value={{ user, theme, cursor }}>
```

Every consumer re-renders when the provider's value changes by `Object.is`, regardless of which field they read. `React.memo` does **not** stop it — memo compares props, and context is not a prop.

Mitigations: memoize the value, split contexts by change frequency, and separate state from dispatch ([[17.9 - useContext]]).

## State updates that change nothing

```jsx
setCount(0);                 // already 0 — usually bails out
setItems([...items]);        // new array reference — always re-renders
setUser({ ...user });        // new object reference — always re-renders
```

Spreading an unchanged object or array produces a new reference and a guaranteed re-render. This happens accidentally in reducers and normalization code more often than people expect.

## Diagnosing

React DevTools Profiler is the tool:

1. Enable "Highlight updates when components render" in settings — a visual outline flashes around re-rendering components.
2. Record an interaction in the Profiler tab.
3. Read the flamegraph: width is duration, and clicking a component shows **why it rendered** — "Props changed: onSelect", "Hook 1 changed", "Parent rendered", "Context changed".

That "why did this render" attribution is the whole answer to most performance questions, and it removes the guesswork ([[19.8 - Profiling with React DevTools]]).

## The order of interventions

1. **Move state down** so fewer components are in the affected subtree
2. **Pass elements as children** so expensive subtrees keep their identity
3. **Split contexts** by change frequency
4. **`React.memo` + `useCallback`/`useMemo`** at the boundary that matters
5. **Virtualize** if the problem is sheer node count ([[19.5 - Virtualization and Windowing]])

Steps 1–3 are free and cannot go stale. Step 4 adds dependency arrays that can be wrong. Reaching for step 4 first is the common mistake.

## The React Compiler changes step 4

The compiler inserts memoization automatically based on what actually flows into memoized boundaries, which removes most manual `useMemo`/`useCallback`/`memo` work ([[19.9 - The React Compiler]]).

It does not remove the value of steps 1–3 — a smaller affected subtree is still better than a memoized large one.

## How senior engineers actually use this

**They profile before optimizing.** The component they assume is the problem usually is not.

**They reach for composition first.** Moving state down and passing children solves more real cases than memoization, with no maintenance cost.

**They accept most re-renders.** A re-render producing identical output costs nothing meaningful.

**They watch the specific hot paths** — keystroke handlers, scroll handlers, drag interactions, and anything rendering hundreds of rows.

## Common pitfalls

- Believing props determine whether a child re-renders (they do not, without memo).
- Equating re-render with DOM update.
- Wrapping everything in `React.memo` and `useCallback` preemptively.
- Unmemoized context values re-rendering entire subtrees.
- Inline objects, arrays and functions defeating memoized children.
- Optimizing based on intuition rather than the Profiler.

## Interview angle

"What causes unnecessary re-renders" and "how do you optimize React performance" both land here. Lead with the four causes and stress that a parent re-rendering re-renders all children regardless of props — that is the fact most candidates get wrong. Then note that re-render ≠ DOM update, so most re-renders are harmless, and give the intervention order with composition ahead of memoization. The `{children}` trick is a compact, memorable demonstration of real understanding.
