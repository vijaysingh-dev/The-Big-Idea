# Unit of Work

## The problem

A service creating several kinds of record ends up with DML scattered through it, in dependency order, with the Id-mapping done by hand.

```java
public static void processIntake(List<ErpClaimDto> payload) {
    List<Account> accounts = buildAccounts(payload);
    insert accounts;                                    // DML 1

    Map<String, Id> accountIdByCode = mapByCode(accounts);

    List<Asset> assets = buildAssets(payload, accountIdByCode);
    insert assets;                                      // DML 2

    Map<String, Id> assetIdBySerial = mapBySerial(assets);

    List<Warranty_Claim__c> claims = buildClaims(payload, assetIdBySerial);
    insert claims;                                      // DML 3

    List<Claim_Part__c> parts = buildParts(payload, claims);
    insert parts;                                       // DML 4

    insert buildLogs(payload);                          // DML 5
}
```

Five DML statements, three manual Id maps, and the ordering encoded in the method's structure. Add a sixth object and every map has to be threaded through.

## What a Unit of Work does

It **collects** the records to be written, resolves the relationships, and performs the DML in one place at the end, in dependency order.

```java
public static void processIntake(List<ErpClaimDto> payload) {
    UnitOfWork uow = UnitOfWork.newInstance(new List<SObjectType>{
        Account.SObjectType,
        Asset.SObjectType,
        Warranty_Claim__c.SObjectType,
        Claim_Part__c.SObjectType,
        Integration_Log__c.SObjectType
    });

    for (ErpClaimDto dto : payload) {
        Account account = buildAccount(dto);
        uow.registerNew(account);

        Asset asset = buildAsset(dto);
        // the parent has no Id yet; the unit of work resolves it after the insert
        uow.registerNew(asset, Asset.AccountId, account);

        Warranty_Claim__c claim = buildClaim(dto);
        uow.registerNew(claim, Warranty_Claim__c.Asset__c, asset);

        for (ErpPartDto partDto : dto.parts) {
            uow.registerNew(buildPart(partDto), Claim_Part__c.Warranty_Claim__c, claim);
        }
    }

    uow.commitWork();
}
```

**The order of `SObjectType` in the constructor is the insert order.** That is the whole mechanism: you declare the dependency graph once, and the unit of work resolves parent Ids into child lookups after each insert.

## What it buys

**Fewer DML statements.** One insert per object rather than one per batch per object, which matters against the 150-statement limit in a service with many object types. See [[16.2 - SOQL and DML Limits]].

**No manual Id mapping.** The `registerNew(child, field, parent)` form handles it.

**Explicit ordering**, declared once rather than encoded in method structure.

**A single transaction boundary.** `commitWork` wraps everything in a savepoint and rolls back on failure, so a partial write is not possible.

**Testability.** A mocked unit of work lets a service be tested without any DML at all — which is the largest practical benefit in a mature codebase.

## The operations

```java
uow.registerNew(record);                          // insert
uow.registerNew(child, field, parent);            // insert, resolving the parent Id
uow.registerDirty(record);                        // update
uow.registerDirty(record, fieldsToUpdate);        // update specific fields
uow.registerUpsert(record);
uow.registerDeleted(record);
uow.registerRelationship(child, field, parent);   // relationship only
uow.registerEmail(emailMessage);
uow.registerPublishBeforeTransaction(event);      // platform event, published before commit
uow.registerPublishAfterSuccessTransaction(event);
uow.registerPublishAfterFailureTransaction(event);

uow.commitWork();
```

**The event registration methods are underrated.** `registerPublishAfterSuccessTransaction` publishes only if the commit succeeded, and `registerPublishAfterFailureTransaction` only if it failed — which is exactly the failure-logging shape that is otherwise fiddly to get right. See [[12.8 - Platform Events]].

## A minimal implementation

fflib's `fflib_SObjectUnitOfWork` is the reference. A stripped-down version shows the mechanism:

```java
public with sharing class UnitOfWork {

    private final List<SObjectType> insertOrder;
    private final Map<SObjectType, List<SObject>> newRecords =
        new Map<SObjectType, List<SObject>>();
    private final Map<SObjectType, List<SObject>> dirtyRecords =
        new Map<SObjectType, List<SObject>>();
    private final List<Relationship> relationships = new List<Relationship>();

    private class Relationship {
        SObject child;
        SObjectField field;
        SObject parent;
    }

    public UnitOfWork(List<SObjectType> insertOrder) {
        this.insertOrder = insertOrder;
        for (SObjectType type : insertOrder) {
            newRecords.put(type, new List<SObject>());
            dirtyRecords.put(type, new List<SObject>());
        }
    }

    public void registerNew(SObject record) {
        newRecords.get(record.getSObjectType()).add(record);
    }

    public void registerNew(SObject child, SObjectField field, SObject parent) {
        registerNew(child);

        Relationship relationship = new Relationship();
        relationship.child = child;
        relationship.field = field;
        relationship.parent = parent;
        relationships.add(relationship);
    }

    public void registerDirty(SObject record) {
        dirtyRecords.get(record.getSObjectType()).add(record);
    }

    public void commitWork() {
        Savepoint sp = Database.setSavepoint();

        try {
            for (SObjectType type : insertOrder) {
                List<SObject> toInsert = newRecords.get(type);
                if (!toInsert.isEmpty()) {
                    insert as user toInsert;
                }

                // parents of this type now have Ids, so their children can be resolved
                resolveRelationshipsFor(type);
            }

            for (SObjectType type : insertOrder) {
                List<SObject> toUpdate = dirtyRecords.get(type);
                if (!toUpdate.isEmpty()) {
                    update as user toUpdate;
                }
            }

        } catch (Exception e) {
            Database.rollback(sp);
            throw e;
        }
    }

    private void resolveRelationshipsFor(SObjectType parentType) {
        for (Relationship relationship : relationships) {
            if (relationship.parent.getSObjectType() == parentType) {
                relationship.child.put(relationship.field, relationship.parent.Id);
            }
        }
    }
}
```

The interesting part is `resolveRelationshipsFor` running **after each type's insert** — that is what lets a child registered before its parent existed get the right Id.

## Where it does not fit

**Simple services.** A method inserting one list of records does not need a unit of work; `insert claims` is clearer.

**Anything needing partial success.** `commitWork` is all-or-none. A batch job wanting `Database.insert(records, false)` with per-record error handling has to do its own DML. This is a real limitation and it rules out the pattern for most bulk integration work. See [[10.2 - Database Class Methods and Partial Success]].

**Trigger contexts modifying `Trigger.new`.** A before trigger assigns in memory with no DML; there is nothing to batch.

**When the ordering is trivially simple.** Two objects with a clear parent-child relationship do not need a declared graph.

## The partial-success gap

Worth dwelling on, because it decides whether the pattern is usable in a given service.

```java
// Unit of work: all or nothing
uow.commitWork();

// What a bulk integration actually needs
List<Database.SaveResult> results = Database.insert(claims, false);
handleFailures(results, claims);
```

An intake service processing 500 records from an ERP wants 497 to succeed and 3 to be reported. The unit of work gives 0 or 500.

Options: perform the DML directly for that service, extend the unit of work to support partial success, or split into a unit of work for the atomic part and direct DML for the tolerant part.

The pragmatic answer in most codebases is **the unit of work for user-initiated, atomic operations, and direct partial-success DML for bulk integration.**

## Testing with a mocked unit of work

The strongest argument for the pattern, and it requires the interface form.

```java
public interface IUnitOfWork {
    void registerNew(SObject record);
    void registerNew(SObject child, SObjectField field, SObject parent);
    void registerDirty(SObject record);
    void commitWork();
}
```

```java
public with sharing class ClaimIntakeService {

    public static void processIntake(List<ErpClaimDto> payload, IUnitOfWork uow) {
        for (ErpClaimDto dto : payload) {
            Warranty_Claim__c claim = buildClaim(dto);
            uow.registerNew(claim);
        }
        uow.commitWork();
    }

    public static void processIntake(List<ErpClaimDto> payload) {
        processIntake(payload, UnitOfWork.newInstance(INSERT_ORDER));
    }
}
```

```java
@IsTest
static void intakeRegistersOneClaimPerPayloadRow() {
    MockUnitOfWork mockUow = new MockUnitOfWork();
    List<ErpClaimDto> payload = TestDataFactory.buildIntakePayload(50);

    Test.startTest();
    // no DML at all — the service's logic is verified in milliseconds
    ClaimIntakeService.processIntake(payload, mockUow);
    Test.stopTest();

    Assert.areEqual(50, mockUow.registeredNew.size(), 'One claim per payload row');
    Assert.isTrue(mockUow.commitCalled, 'The work should be committed');
}
```

The overloaded method — one taking the dependency, one supplying the real implementation — is the standard injection shape. See [[18.8 - Dependency Injection and Testability]].

**This is the payoff:** a service test with no DML, no queries, and no trigger execution, running in milliseconds. On a large suite that is the difference between a test run people wait for and one they skip.

## The Stub API alternative

Rather than hand-writing a mock, `System.StubProvider` generates one:

```java
fflib_ApexMocks mocks = new fflib_ApexMocks();
fflib_SObjectUnitOfWork uowMock = (fflib_SObjectUnitOfWork)
    mocks.mock(fflib_SObjectUnitOfWork.class);

Test.startTest();
ClaimIntakeService.processIntake(payload, uowMock);
Test.stopTest();

((fflib_SObjectUnitOfWork) mocks.verify(uowMock, 50)).registerNew(
    (SObject) fflib_Match.sObjectOfType(Warranty_Claim__c.SObjectType)
);
```

More expressive verification, at the cost of a dependency and a mocking API to learn. Covered in [[18.8 - Dependency Injection and Testability]].

## When to adopt

**Skip it when** services write one or two object types, or when partial success is needed.

**Adopt it when** a service writes four or more object types with dependencies, when Id-mapping code is repeated, or when service tests are slow because everything requires DML.

**The clearest signal:** a service method with five `insert` statements and three manual Id maps between them.

**The honest caveat:** the pattern is genuinely useful and it is also the fflib layer teams most often adopt without needing. In an org where services write one object each, it adds indirection for no benefit.

## Practical guidance

**Declare the insert order once**, in the constructor.

**Use `registerNew(child, field, parent)`** rather than mapping Ids by hand.

**Use the event registration methods** for publish-on-success and publish-on-failure.

**Accept the interface as a parameter** so services can be tested without DML.

**Do not use it where partial success is required.**

**Do not adopt it** until a service is writing several dependent object types.
