# Long Polling

#backend #realtime #http

> **In one line:** Hold the request open until there is something to say — the oldest realtime technique, still the most compatible, and still the fallback every realtime library ships with.

---

## The Idea

Ordinary polling wastes requests when nothing has changed:

```
GET /events → nothing
GET /events → nothing
GET /events → nothing
GET /events → one event    ← 3 wasted requests, up to 30s of latency
```

Long polling inverts it. The server holds the request open until it has something:

```
GET /events?since=42
   (server waits...)
   (event happens)
→ 200 OK {"events": [...], "cursor": 43}

GET /events?since=43        ← client immediately asks again
```

Latency approaches zero. Wasted requests approach zero. And it is **plain HTTP** — no upgrade, no special framing, no protocol negotiation.

💡 **Long polling is the most compatible realtime technique that exists.** It works through every proxy, every corporate firewall, every ancient load balancer, and every HTTP client. That is why Socket.IO, SignalR and every other realtime library falls back to it when WebSockets fail.

---

## The Mechanics

### The server

```python
@app.get("/events")
async def poll(since: int, request: Request, timeout: int = 30):
    queue = await broker.subscribe(request.state.user_id)
    try:
        # Anything already waiting? Return immediately
        missed = await log.since(since)
        if missed:
            return {"events": missed, "cursor": missed[-1].id}

        # Otherwise wait, bounded
        try:
            event = await asyncio.wait_for(queue.get(), timeout=timeout)
            batch = [event]
            # Drain anything else that arrived while we were waking up
            while not queue.empty() and len(batch) < 100:
                batch.append(queue.get_nowait())
            return {"events": batch, "cursor": batch[-1].id}
        except TimeoutError:
            return {"events": [], "cursor": since}      # empty, client re-polls

    finally:
        await broker.unsubscribe(request.state.user_id, queue)
```

Four details that matter:

**Check the log before waiting.** If events happened between the client's last poll and this request, return them immediately. Skipping this creates a gap.

**Bounded wait.** 25–30 seconds, comfortably under every proxy timeout. Return an empty response rather than holding forever.

**Drain the queue.** If three events arrive together, send all three in one response rather than one per round trip.

**`finally` unsubscribes.** Same leak as SSE ([[04.3 - SSE in Production]]).

### The client

```javascript
async function poll(cursor) {
    while (running) {
        try {
            const res = await fetch(`/events?since=${cursor}`);
            if (!res.ok) throw new Error(res.status);
            const data = await res.json();
            cursor = data.cursor;
            data.events.forEach(handle);
        } catch (e) {
            await sleep(backoff());     // only back off on error
        }
    }
}
```

⚠️ **Do not sleep between successful polls.** The whole point is that the server does the waiting. A client that sleeps 1 second after each response has reintroduced polling latency for no benefit.

**Do back off on errors**, with jitter — otherwise a server restart produces a synchronised hammer from every client ([[03.4 - Idempotency and Safe Retries]]).

## The Gap Problem

The defining correctness issue.

```
t=0   Client polls, gets events 1-5, cursor=5
t=1   Server responds
t=2   Event 6 happens          ← client is not connected right now
t=3   Client polls with since=5
```

If the server only listens for *new* events from t=3 onwards, event 6 is lost forever.

**The fix is the cursor.** The client always says where it got to, and the server always checks durable history before waiting.

```python
missed = await log.since(since)      # ← this line is the whole solution
if missed:
    return {"events": missed, "cursor": missed[-1].id}
```

💡 **This is the same replay-log requirement as SSE**, and it is why the two techniques are architecturally identical underneath. The transport differs; the correctness requirements do not. Build the event log once and both work.

⚠️ Same buffer-overflow case too: if the client's cursor is older than your oldest retained event, you must tell it to resync rather than silently continuing from the newest.

## Long Polling vs SSE

They solve the same problem. The differences are operational.

| | Long polling | SSE |
|---|---|---|
| Protocol | Plain HTTP requests | One long HTTP response |
| Proxy compatibility | **Universal** | Good, but buffering breaks it |
| Requests per event | One | Zero |
| Server connection held | Yes, per waiting client | Yes, per client |
| Reconnect logic | Yours | Browser's |
| Replay | Yours (cursor) | Browser's (`Last-Event-ID`) |
| Headers/auth | **Normal, every request** | `EventSource` cannot set headers |
| Browser connection limit | Applies, but connections cycle | Applies, and they never free |
| Overhead per event | Full HTTP request + response | ~20 bytes |

💡 **Long polling's underrated advantage is that every poll is a normal request.** It carries headers, so auth is trivial. It re-evaluates authorisation on every poll, so a revoked user stops receiving data within one poll cycle — whereas an SSE connection established an hour ago may still be streaming to a user whose access was removed.

⚠️ **The overhead is real though.** At 10 events per second per client, long polling means 10 full HTTP requests per second per client. SSE means 10 small writes on one connection. For high event rates, SSE wins decisively.

**The rule: long polling for low-frequency events where compatibility matters. SSE for anything frequent.**

## In Production

### Connection cost is the same

A common misconception is that long polling is "lighter" because it does not hold a persistent connection.

It does hold a connection — for up to 30 seconds at a time, and the client reconnects immediately. **The server-side connection count is effectively the same as SSE.** You are holding a socket, a task, and a subscription per waiting client either way.

What differs is that connections cycle, which means:

- Load balancers redistribute clients across pods naturally
- A deploy does not produce a reconnect storm — clients just poll the new pod
- Each cycle costs a request/response round trip

💡 **The deploy behaviour is a genuine advantage.** With SSE, a rolling deploy drops 1,000 connections at once ([[04.3 - SSE in Production]]). With long polling, clients are already reconnecting every 30 seconds, so a deploy is invisible. For a service that deploys frequently, that matters.

### Timeout coordination

```
Client fetch timeout       35s
Server hold timeout        30s      ← must be shortest
Proxy read timeout         60s
Load balancer idle         60s
```

⚠️ **The server's hold must be shorter than every proxy timeout in the path.** If nginx times out at 60s and you hold for 90s, the client gets a 504 instead of an empty response. Since 504s look like errors, your monitoring lights up during completely normal operation.

**25–30 seconds is the standard hold**, chosen to sit safely below the common 60-second defaults.

### Worker occupancy

Each waiting client occupies a task. That is fine for asyncio, and fatal for a synchronous worker model.

⚠️ **Long polling with a thread-per-request or process-per-request server is unworkable.** 1,000 clients means 1,000 blocked workers. This is why long polling has a historical reputation for being expensive — it was, on the servers of the time. With asyncio it costs a few KB per waiting client.

Same warning as SSE about `--limit-concurrency`: waiting long-poll requests count toward it.

### Batching and coalescing

```python
# Wait a little after the first event to collect more
event = await queue.get()
batch = [event]
deadline = time.monotonic() + 0.05          # 50ms coalescing window
while time.monotonic() < deadline and len(batch) < 100:
    try:
        batch.append(await asyncio.wait_for(queue.get(), timeout=0.01))
    except TimeoutError:
        break
```

A 50ms delay to batch multiple events into one response can dramatically reduce request count when events are bursty. The cost is 50ms of latency, which is imperceptible.

💡 **This coalescing window is the single most effective long-polling optimisation** and it is three lines. Without it, a burst of 20 events produces 20 request/response cycles.

### Observability

Long polling has a specific monitoring hazard: **every request takes 30 seconds by design.**

```
p50 request duration: 30s      ← this is healthy
```

Your latency dashboards, your slow-request alerts, and your load balancer's timeout warnings will all fire. Exclude long-poll endpoints from standard latency monitoring and track instead:

```python
longpoll_waiting_clients.set(count)
longpoll_events_per_response.observe(len(batch))
longpoll_empty_responses_total.inc()        # timed out with nothing
longpoll_gap_recovered_total.observe(count) # events returned from the log
```

**`events_per_response` is the efficiency metric.** If it is consistently 1, your coalescing window is not helping and every event costs a round trip.

## Codebase

**Repo:** `zulip/zulip`, `socketio/socket.io`, `signalr` (docs)

**Question to answer:** Zulip has run long polling at scale for over a decade. How does a client that was offline for ten minutes catch up without missing or duplicating events, and what happens when its queue has been garbage collected? Then: how does Socket.IO decide to fall back from WebSocket to long polling, and how does it avoid losing messages during the transition?

**Read, in order:**

1. `zulip/zerver/tornado/event_queue.py` — **the reference implementation.** Per-client queues, event IDs, the `last_event_id` handling, and the queue garbage collector for clients that never return
2. `zulip/zerver/tornado/handlers.py` — the actual long-poll handler, including every edge case around client disconnect and server restart
3. `zulip/zerver/lib/events.py` — how a client fetches full initial state and then transitions to incremental events. **This is the resync path done properly**
4. `socket.io/packages/engine.io/lib/transports/polling.js` — long polling as a transport, including the write buffer and the transition to WebSocket
5. `socket.io/packages/engine.io-client/lib/transport.js` — the upgrade handshake. How it tests WebSocket while keeping long polling alive, so nothing is lost if the upgrade fails

💡 The Socket.IO upgrade mechanism is clever and worth understanding: it starts with long polling (which always works), then *probes* WebSocket in parallel, and only switches once the probe succeeds. If the probe fails, long polling continues seamlessly. That is a good pattern for any capability upgrade — **verify the better path works before abandoning the working one.**

**Size:** 1–2 sessions.

**Part 1 — Build it correctly.** Long-poll endpoint with cursor-based catch-up, a bounded hold, event coalescing, queue cleanup, and abandoned-queue garbage collection.

The GC is the part people omit: a client that disappears without a final poll leaves a queue that grows forever. Expire queues after a few minutes of no polling.

**Part 2 — Prove there are no gaps.** The critical correctness test.

```
1. Client polls, receives events 1-5
2. While the client is between polls, generate events 6-8
3. Client polls with since=5
4. Assert it receives exactly 6, 7, 8
```

Then run this continuously for 10 minutes with events generated at random intervals, and assert the client received every event exactly once with no duplicates and no gaps.

**Then deliberately break it** — remove the log check and only listen for new events — and show the test failing. That contrast is what makes the cursor mechanism stick.

**Part 3 — Overflow and resync.** Client disconnected long enough for its cursor to fall out of a 1,000-event buffer.

Confirm the server returns an explicit resync signal rather than silently continuing. Then implement the client resync path — refetch full state, resume from the new cursor — and verify final state correctness.

**Part 4 — Coalescing, measured.** Generate events in bursts: 20 events in 100ms, then 10 seconds of quiet.

Measure requests per event with coalescing windows of 0ms, 20ms, 50ms and 200ms. Chart requests-per-event and added latency against window size.

**Find the point of diminishing returns.** For bursty events this should be dramatic — one request instead of twenty.

**Part 5 — Three transports, one workload.** Fixed-interval polling (5s), long polling, and SSE. Same event source, 500 clients.

Measure at three event rates: 1 event/minute, 1 event/second, 10 events/second per client.

| Metric | |
|---|---|
| Requests per second at the server | |
| Bytes transferred | |
| Event latency p50 and p99 | |
| Server memory | |
| CPU | |

**Nine cells. Chart it.** You should find long polling competitive at low rates and clearly losing at high rates — and you will have your own numbers for where the crossover is.

**Part 6 — The timeout mismatch.** Server holds for 90 seconds behind an nginx with `proxy_read_timeout 60s`.

Watch clients receive 504s during completely normal operation. Watch your error rate dashboard light up. Then fix the hold duration and confirm it disappears.

**Record how misleading the symptom was** — this is a configuration bug that presents as a service failure.

**Part 7 — The deploy advantage.** 500 clients on long polling, 500 on SSE. Rolling restart.

Chart requests per second and error rate during the rollout for both.

**Long polling should be nearly invisible; SSE should spike.** This is the concrete argument for long polling in a frequently-deployed service, and having the chart makes it a design consideration rather than a preference.

**Done when:**
- Your 10-minute continuous test shows zero gaps and zero duplicates
- The broken version demonstrably fails the same test
- Resync works end to end after a buffer overflow
- Your coalescing chart identifies the right window for bursty events
- The nine-cell comparison shows where each transport wins
- The timeout mismatch is reproduced, and you noted how misleading it was
- The deploy comparison chart shows long polling's advantage
