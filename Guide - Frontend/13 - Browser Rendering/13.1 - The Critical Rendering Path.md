# The Critical Rendering Path

The sequence of steps between receiving HTML bytes and painting pixels. Everything you do to improve first-load performance is an intervention somewhere in this pipeline.

## The steps

```
HTML bytes -> tokens -> nodes -> DOM
CSS bytes  -> tokens -> nodes -> CSSOM
DOM + CSSOM -> Render Tree -> Layout -> Paint -> Composite
```

**Parsing HTML** builds the DOM incrementally, so the browser can start rendering before the document finishes downloading.

**Parsing CSS** builds the CSSOM. Unlike the DOM, this cannot be used incrementally — a later rule can override an earlier one, so the browser waits for the whole stylesheet.

**The render tree** combines them, containing only visible elements. `display: none` elements are excluded entirely; `visibility: hidden` elements are included, since they still occupy space.

**Layout** (also called reflow) computes the geometry of every box.

**Paint** fills in pixels — text, colours, shadows, borders — into layers.

**Composite** assembles the layers on the GPU into the final image.

## Render-blocking resources

**CSS is render-blocking.** The browser will not paint until the CSSOM is complete, because painting with incomplete styles would produce a flash of unstyled content.

**Synchronous scripts are parser-blocking.** A `<script>` without `defer` or `async` stops HTML parsing entirely: the browser must fetch, parse and execute it before continuing, because the script might call `document.write`.

Worse, a script also waits for any pending CSS above it, since it might read computed styles. So a stylesheet in `<head>` blocks a script, which blocks the parser.

```html
<script src="app.js"></script>          <!-- blocks parsing -->
<script src="app.js" defer></script>    <!-- downloads in parallel, runs after parse, in order -->
<script src="app.js" async></script>    <!-- downloads in parallel, runs whenever ready -->
<script type="module" src="app.js"></script>  <!-- deferred by default -->
```

**`defer` is the default choice** for application code: parallel download, execution in document order, after the DOM is ready. **`async`** suits independent third-party scripts (analytics) where order does not matter — but note `async` scripts execute the instant they arrive, which can interrupt parsing at an unpredictable point.

## The preload scanner

While the main parser is blocked, a secondary scanner reads ahead in the raw HTML looking for resources to start fetching — scripts, stylesheets, images. This is a significant optimization and it has one important limitation: **it only sees markup in the HTML source.**

Resources it cannot discover:

- Images set as CSS `background-image`
- Anything injected by JavaScript
- Fonts referenced from CSS (discovered only after CSSOM construction)
- Images inside a client-rendered component tree

This is why a hero image applied as a CSS background scores badly on LCP, and why fonts often need an explicit preload ([[09.4 - Head Metadata and SEO Basics]]):

```html
<link rel="preload" as="font" type="font/woff2" href="/inter.woff2" crossorigin>
```

The `crossorigin` attribute is mandatory for fonts even same-origin, because fonts are always fetched in CORS mode. Omitting it causes a double fetch — a very common mistake.

## Optimizing the path

**Reduce critical bytes.** Minify and compress CSS and JS. Brotli typically beats gzip by 15–20% on text.

**Inline critical CSS** — the styles needed for above-the-fold content — in a `<style>` tag, and load the rest asynchronously:

```html
<style>/* critical rules */</style>
<link rel="stylesheet" href="rest.css" media="print" onload="this.media='all'">
```

The `media="print"` trick makes the stylesheet non-blocking, then swaps it in on load. Worth doing for landing pages; usually over-engineering for authenticated applications where users arrive with a warm cache.

**Split CSS by media** — genuinely media-conditional stylesheets do not block:

```html
<link rel="stylesheet" href="print.css" media="print">
```

**Defer all non-critical JavaScript** and code-split by route ([[08.2 - Dynamic Imports]]).

**Preconnect to critical third-party origins** — DNS, TCP and TLS for a new origin can cost 100–300 ms on mobile:

```html
<link rel="preconnect" href="https://api.example.com" crossorigin>
```

Limit this to two or three origins; each open connection has a cost.

## Fonts

Web fonts are a frequent and under-diagnosed source of slow rendering.

```css
@font-face {
  font-family: "Inter";
  src: url("/inter.woff2") format("woff2");
  font-display: swap;
  font-weight: 100 900;    /* variable font range */
  unicode-range: U+0000-00FF;
}
```

`font-display` controls the behavior while the font loads:

- **`swap`** — show fallback immediately, swap when ready. No invisible text, but a visible reflow (FOUT).
- **`optional`** — use the font only if it arrives almost immediately; otherwise keep the fallback for this page load. Best for CLS, and the font is cached for the next visit.
- **`block`** — invisible text for up to 3s (FOIT). Almost never what you want.

The swap causes layout shift unless the fallback metrics match. `size-adjust`, `ascent-override` and `descent-override` let you tune a fallback to match:

```css
@font-face {
  font-family: "Inter-fallback";
  src: local("Arial");
  size-adjust: 107%;
  ascent-override: 90%;
}
```

A **variable font** replaces several weight files with one, which is usually a net win despite the larger single file.

Subsetting with `unicode-range` matters for products serving Indic scripts — a full Devanagari font can be several hundred kilobytes.

## Measuring

```js
const nav = performance.getEntriesByType("navigation")[0];
nav.domContentLoadedEventEnd;
nav.loadEventEnd;
nav.responseStart - nav.requestStart;   // TTFB
```

In DevTools, the Network panel's waterfall shows which resources blocked which. The Performance panel's timeline shows parse, style, layout and paint phases. Lighthouse's "Eliminate render-blocking resources" audit names the specific files.

The metrics that matter in order: **TTFB** (server response), **FCP** (first pixel of content), **LCP** (the main content element) ([[13.5 - Core Web Vitals]]).

## In frameworks

A client-rendered SPA has a structurally worse critical path: the HTML is nearly empty, so nothing paints until the JS bundle downloads, parses, executes and renders.

```
CSR:  HTML -> JS download -> JS parse -> JS execute -> fetch data -> paint
SSR:  HTML (with content) -> paint -> JS download -> hydrate -> interactive
```

SSR moves first paint much earlier at the cost of server work and a hydration step. Streaming SSR sends HTML in chunks so the browser can start painting before the server finishes. Server Components go further by never shipping some component code at all ([[28.11 - Rendering Strategies]]).

## How senior engineers actually use this

**They audit what blocks first.** The Network waterfall answers "why is the page blank for two seconds" faster than any amount of code reading.

**They ensure the LCP element is discoverable in the initial HTML** — a real `<img>` with `fetchpriority="high"`, not a CSS background or a JS-injected element.

**They use `font-display: optional` or carefully matched fallback metrics** to eliminate font-driven layout shift.

**They preload sparingly.** Fonts and the LCP image. Preloading ten things prioritizes nothing.

**They test on throttled mobile.** The path is identical everywhere; the constants are four to six times worse on a mid-range phone.

## Common pitfalls

- Synchronous scripts in `<head>` blocking the parser.
- Missing `crossorigin` on font preloads, causing a double fetch.
- The LCP image as a CSS background, invisible to the preload scanner.
- `font-display: block`, giving invisible text.
- Preloading everything.
- Importing an entire icon or component library in the critical bundle.
- Measuring on a fast desktop connection only.

## Interview angle

"What happens when you type a URL and press enter" almost always reaches this pipeline, and "how would you improve page load time" lands squarely on it. Walk the steps — DOM and CSSOM, render tree, layout, paint, composite — then name the interventions: defer scripts, inline critical CSS, preconnect, make the LCP element discoverable, and control font loading. The preload scanner limitation is a strong detail because it explains *why* CSS background heroes score badly.
