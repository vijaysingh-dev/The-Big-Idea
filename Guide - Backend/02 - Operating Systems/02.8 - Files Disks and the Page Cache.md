# Files Disks and the Page Cache

#backend #os #storage #durability #linux

> **In one line:** `write()` returning means your data reached kernel memory, not the disk. Durability needs `fsync`, the page cache makes reads fast and writes dangerous, and every database's design is a response to these two facts.

---

## The Idea

There are four places your bytes can be after you "save" them:

```
your buffer (Python BufferedWriter, ~8 KB)
   │  flush()                         ← lost if the PROCESS crashes before this
   ▼
kernel page cache (RAM)
   │  fsync() / background writeback  ← lost if the MACHINE crashes before this
   ▼
disk's volatile write cache
   │  FLUSH / FUA command (fsync sends it)
   ▼
stable storage (NAND flash / platter)  ← survives power loss
```

`write()` returns after step 2. The kernel writes dirty pages to disk later, typically within about 30 seconds. If the machine loses power in between, the write is gone, even though your code saw success.

**This one fact is why write-ahead logs, `fsync`, `synchronous_commit`, Kafka's `acks` and Redis's `appendfsync` all exist.**

---

## The Page Cache

Linux uses free RAM to cache file contents. Every `read` and `write` on a regular file goes through it (unless you use `O_DIRECT`).

```bash
free -h
#               total   used   free   shared  buff/cache  available
# Mem:           31Gi   8.2Gi  1.1Gi   412Mi       22Gi       22Gi
```

- `buff/cache` is the page cache. It is **not wasted**. It is RAM doing useful work, and the kernel drops clean pages instantly when processes need memory.
- `available` is the number to look at: free memory plus cache that can be reclaimed.
- "Linux ate my RAM" is the page cache, and it is fine.

| Operation | With a warm page cache | Cold (from disk) |
|---|---|---|
| Read 4 KB | ~1 µs | ~100 µs (NVMe), ~10 ms (HDD) |
| Write 4 KB | ~1 µs (just memory) | Same, until writeback or `fsync` |
| `fsync` | — | ~0.1–2 ms (NVMe with power-loss protection), ~10 ms (consumer SSD or HDD), worse on cloud network disks |

💡 **Postgres leans on the page cache on purpose.** It has its own `shared_buffers`, typically 25% of RAM, and lets the OS cache the rest. That is double caching, and it is deliberate. See [[07.2 - Postgres Architecture]].

## fsync and Friends

| Call | Guarantees |
|---|---|
| `fsync(fd)` | File data **and** metadata (size, mtime) are on stable storage |
| `fdatasync(fd)` | Data, plus only the metadata needed to read it back (size). Skips mtime. Cheaper. |
| `sync()` | Everything, system-wide. Do not call it from applications. |
| `O_SYNC` / `O_DSYNC` on open | Every `write` behaves as if followed by `fsync` / `fdatasync` |
| `O_DIRECT` | Bypass the page cache. Your buffers must be aligned. Used by databases that manage their own cache. |

### The rename dance: replacing a file safely

```python
import os

def atomic_write(path: str, data: bytes) -> None:
    tmp = f"{path}.tmp"
    with open(tmp, "wb") as f:
        f.write(data)
        f.flush()                # Python buffer → kernel
        os.fsync(f.fileno())     # kernel → disk
    os.replace(tmp, path)        # atomic rename
    dir_fd = os.open(os.path.dirname(path) or ".", os.O_RDONLY)
    try:
        os.fsync(dir_fd)         # make the rename itself durable
    finally:
        os.close(dir_fd)
```

Every step is there for a reason:

1. Write to a temp file, so a crash never leaves a half-written `path`.
2. `flush` then `fsync`, so the contents are on disk **before** the rename.
3. `os.replace` is atomic on POSIX. Readers see the old file or the new one, never a mix.
4. `fsync` the **directory**. The rename is a change to the directory, and it is not durable until the directory is synced.

⚠️ Skip step 2 and after a crash you can get a zero-length file under the new name. ext4 users hit exactly this in 2009, when applications relied on ordering the filesystem never promised.

### fsyncgate

In 2018 Postgres developers discovered that when `fsync` fails on Linux, the kernel may **mark the dirty pages clean and drop the error**. A retried `fsync` then "succeeds", and the data is gone. Postgres's fix was to **crash on any fsync failure** and recover from the WAL. The lesson: an I/O error on the durability path is not retryable. Treat it as data loss.

## Inodes and Directories

A filesystem stores:

- **Inodes:** metadata (size, owner, permissions, timestamps) and pointers to data blocks. **The file's name is not in the inode.**
- **Directories:** files that map names to inode numbers.

Consequences you will meet:

| Behaviour | Why |
|---|---|
| `rm` on an open file frees no space | The name is gone, but an open fd still references the inode. Space is freed at the last `close`. `lsof +L1` lists these. |
| "No space left on device" with `df` showing free space | Out of **inodes**, usually millions of tiny files. Check with `df -i`. |
| Hard links | Two names, one inode. |
| `mv` within a filesystem is instant | It only edits directory entries. Across filesystems it is a copy plus a delete. |

⚠️ **Deleted-but-open log files are a classic full-disk incident.** Logrotate deletes `app.log`, but the app keeps the fd and keeps writing into a file nobody can see. The disk fills and `du` cannot find where. The fix is `copytruncate`, reopening logs on `SIGHUP`, or (in containers) logging to stdout.

## Journaling Filesystems

ext4 and XFS keep a **journal**: a small log of pending metadata changes written before the real change. After a crash, the filesystem replays the journal instead of scanning the whole disk.

| ext4 mode | Journals | Trade-off |
|---|---|---|
| `data=ordered` (default) | Metadata only, but data blocks are written before the metadata that points at them | Good default |
| `data=writeback` | Metadata only, no ordering | Faster; a crash can leave old garbage in files |
| `data=journal` | Data and metadata | Safest, slowest |

💡 **A journal is a write-ahead log.** So are Postgres's WAL, Kafka's log segments, Redis's AOF and etcd's Raft log. Same idea: append the intent sequentially, `fsync` it, then apply. Sequential appends are fast on every storage device, and the log makes recovery a replay. You meet this pattern in [[07.1 - Storage Engines]] and [[10.1 - Queue vs Log]].

## Storage Devices: Numbers to Know

| Device | Random 4 KB read | Sequential | Notes |
|---|---|---|---|
| HDD | ~100–200 IOPS | ~150–250 MB/s | Seeks dominate. Sequential I/O is everything. |
| SATA SSD | ~50–100k IOPS | ~500 MB/s | |
| NVMe SSD | ~500k–1M+ IOPS | 3–7+ GB/s | Needs deep queues (many parallel requests) to reach peak |
| Cloud block storage (EBS gp3) | 3,000 IOPS baseline, provisioned up to 16k | 125 MB/s baseline, up to 1,000 | **Network-attached.** Latency ~0.5–1 ms, and IOPS is a billed limit |
| Local instance NVMe | Like NVMe | Like NVMe | Fast but **ephemeral**: gone when the instance stops |

⚠️ **On cloud disks, IOPS is a quota, not a capability.** A database that hits the provisioned IOPS limit sees latency jump from 1 ms to 50 ms, while the disk itself is fine. `iostat -x 1` showing a high `aqu-sz` and `r_await` with steady IOPS at a round number is the tell.

```bash
iostat -x 1
# r/s w/s   r_await w_await   aqu-sz  %util
# reads/writes per s, average latency (ms), queue depth, busy %
```

`%util` near 100% means saturated on an HDD, but on NVMe (which serves many requests in parallel) it only means "always at least one request in flight". Use latency (`r_await`, `w_await`) and queue size instead.

## In Production

| System | Durability knob | Trade-off |
|---|---|---|
| Postgres | `synchronous_commit`, `fsync`, `wal_sync_method` | `synchronous_commit=off` risks losing the last few hundred ms of commits on a crash, never corruption |
| Redis AOF | `appendfsync always \| everysec \| no` | `everysec` (the default) can lose about one second of writes |
| Kafka | Relies on replication (`acks=all`, `min.insync.replicas`), not per-message fsync | Durability comes from copies on several machines, not from the local disk |
| SQLite | `PRAGMA synchronous`, WAL mode | WAL mode plus `synchronous=NORMAL` is the common fast-and-safe setting |

💡 Notice Kafka's choice. Replicating to three machines' page caches is often both faster and safer than `fsync` on one. Durability is a system property, not a disk property.

**Repos:** `mit-pdos/xv6-riscv`, `redis/redis`

**Question to answer:** How does a filesystem make a multi-block update crash-safe, and how does Redis decide when to call `fsync` on its append-only file?

**Read, in order:**

1. xv6 `kernel/log.c` — a complete write-ahead journal in about 200 lines: `begin_op`, `log_write`, `end_op`, `commit`, `recover_from_log`. Read all of it.
2. xv6 `kernel/bio.c` — the buffer cache: xv6's page cache, with LRU
3. xv6 `kernel/fs.c` — `ialloc`, `bmap`, `dirlookup`. Inodes and directories in code.
4. Redis `src/aof.c` — `flushAppendOnlyFile()`. Find the three `appendfsync` branches and the background fsync thread (`bioCreateFsyncJob`).

**Size:** 2 sessions. The xv6 log is the best 200 lines on durability you will ever read.
