# Deployment Strategies, Rollback and Hotfixes

## The uncomfortable truth about rollback

**There is no rollback on Salesforce.**

A deployment cannot be undone with a command. There is no "revert to the previous version" button, no blue-green swap, no traffic shift.

What exists instead:

**Deploy the previous version forward.** Which requires having it, and works only if the change was purely additive in a reversible way.

**Destructive changes** to remove what was added — which deletes data along with the field.

**Feature toggles** to disable the code path without deploying at all.

**The bypass mechanism** to disable automation immediately.

**Data restoration** from backup or field history.

**Design for forward recovery, not for rollback.** That framing changes how deployments are planned.

## What cannot be undone

The specifics worth knowing before deploying.

**A deleted field takes its data.** Restoring the field does not restore the values.

**A changed field type may be irreversible.** Text to Number converts and discards what does not parse.

**A picklist value removed** is gone from every record referencing it.

**A master-detail converted to lookup**, or the reverse, changes the sharing model and may not convert back.

**Data written by new automation** is not removed by removing the automation.

**A `global` member in a managed package** can never be removed.

**Anything with an irreversible step needs a plan before deployment**, not after.

## Additive deployment

The strategy that makes recovery possible.

```
Release 1   add Claim_Amount_V2__c, populate it alongside the old field
            new code reads V2 with a fallback to the old
Release 2   switch every reader to V2
Release 3   stop populating the old field
Release 4   remove the old field
```

Four releases where one would do, and **each one is individually reversible.**

**Never rename a field in a single release.** A rename is a delete and a create, and the data does not follow.

**Never change a field's type in a single release.** Add the new field, migrate, switch readers, then remove.

**Never remove a field in the release that stops using it.** Leave a gap so the previous version still works if you deploy it forward.

That last point is the one that makes forward recovery viable: if release N removed a field that release N-1 used, deploying N-1 forward fails.

## Feature toggles

The closest thing to a rollback that exists.

```java
public with sharing class ClaimApprovalService {

    public static void approve(Set<Id> claimIds, Decimal amount) {
        // the new path is deployed but inactive until the toggle is flipped
        if (FeatureToggles.isEnabled('Tiered_Approval_Routing')) {
            new TieredApprovalService().approve(claimIds, amount);
            return;
        }
        new LegacyApprovalService().approve(claimIds, amount);
    }
}
```

**Deploy dark, enable later.** The code is in production and inactive; enabling it is a metadata record change rather than a deployment.

**Disabling is immediate** and requires no release window.

**Custom Metadata for org-wide toggles** — they deploy, so the state travels with the code.

**Custom Settings for per-user pilots** — they do not deploy, so a pilot group can differ per environment. See [[17.2 - Custom Settings]] and [[18.10 - Custom Metadata Driven Architecture]].

**What toggles cannot hide:** a new required field, an active validation rule, a changed page layout, an active flow. Schema changes are visible the moment they deploy, which is the limit of the technique.

**Remove toggles once the feature is stable.** A codebase with forty toggles has forty untested combinations.

## The bypass mechanism

The fastest lever available during an incident.

```
Setup → Custom Settings → Automation Settings → Manage
    New at the Profile level: Disable_All_Automation__c = true
```

**No deployment, effective immediately, scoped to a profile or a user.**

This is the reason the bypass exists and the reason it must be tested. An untested bypass is the one you discover does not work while production is broken. See [[11.5 - Trigger Handler Pattern]] and [[20.8 - Production Incident Playbook]].

## Sequencing a release

The order that avoids breaking things mid-deployment.

```
1. Schema      new objects and fields, additive only
2. Code        Apex, LWC — reading new fields defensively
3. Automation  flows, triggers, validation rules
4. Security    permission sets granting access to the new fields
5. Post-deploy Custom Setting records, scheduled job rescheduling
6. Enable      flip the feature toggle
```

**Schema before code**, because code referencing a field that does not exist fails to compile.

**Security after automation**, because granting access to a field before the automation populating it exists produces a visible empty field.

**The toggle last**, so everything is in place before anything changes behaviour.

For a large release, deploying stages separately rather than as one transaction makes a partial failure recoverable.

## Post-deployment steps

The things that do not deploy, versioned so they cannot be forgotten.

```java
// scripts/apex/post-deploy.apex

if ([SELECT COUNT() FROM Automation_Settings__c] == 0) {
    insert new Automation_Settings__c(
        SetupOwnerId = UserInfo.getOrganizationId(),
        Disable_All_Automation__c = false
    );
}

// a scheduled class cannot be modified while scheduled, so it is rescheduled after deploying
for (CronTrigger ct : [
    SELECT Id FROM CronTrigger
    WHERE CronJobDetail.Name LIKE 'Claim Reconciliation%' AND State != 'DELETED'
]) {
    System.abortJob(ct.Id);
}
System.schedule('Claim Reconciliation Daily', '0 0 2 * * ?', new ClaimReconciliationBatch());

// backfilling a new field, guarded so a rerun is safe
if ([SELECT COUNT() FROM Warranty_Claim__c WHERE Approval_Tier__c = null] > 0) {
    Database.executeBatch(new ClaimTierBackfillBatch(), 200);
}
```

```bash
sf apex run --file scripts/apex/post-deploy.apex --target-org production
```

**The guards make it idempotent**, so running it twice is safe — which matters because it will be run twice eventually.

**The full list of what does not deploy**, and therefore belongs here or in a documented manual step:

```
Custom Setting records
Named Credential secrets
Connected app consumer keys
Certificate private keys
Deliverability settings
Scheduled job schedules
Skinny tables and custom indexes
Territory model activation
Some Experience Cloud settings
```

See [[21.1 - Metadata, Source of Truth and Deployment Concepts]].

## Forward recovery

When something is wrong after a release.

**1. Assess.** Is data being damaged, or are users blocked? Damage means stop first; blocked means diagnose first.

**2. Disable, not deploy.** In order of speed:

```
Feature toggle          seconds, no deployment
Bypass setting          seconds, no deployment
Deactivate a flow       one click
Abort a job             one command
Deactivate a validation rule
Deploy the previous version   minutes to an hour
```

**The first four require no deployment**, which is why they are worth building before they are needed.

**3. Deploy forward if necessary.**

```bash
git checkout v2026.07.1
sf project deploy validate --manifest manifest/package.xml \
  --test-level RunLocalTests --target-org production
sf project deploy quick --job-id 0Af... --target-org production
```

**This works only if the previous version is deployable** — no removed fields, no irreversible schema change. That is the constraint additive deployment exists to preserve.

**4. Assess data damage.**

```sql
SELECT COUNT(Id), Status__c FROM Warranty_Claim__c
WHERE LastModifiedDate = TODAY AND LastModifiedById = :integrationUserId
GROUP BY Status__c
```

```sql
SELECT ParentId, Field, OldValue, NewValue, CreatedDate
FROM Warranty_Claim__History WHERE CreatedDate = TODAY
```

**Field history is frequently the only record of the prior state**, which is why tracking the fields that matter is worth its cost before an incident. See [[22.3 - Field Audit Trail and Data Retention]].

**5. Correct in batches, with the automation bypassed:**

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    // bypass on, so the correction does not re-trigger what caused the damage
    AutomationBypass.bypass('WarrantyClaim');

    for (Warranty_Claim__c claim : scope) {
        claim.Status__c = priorStatus.get(claim.Id);
    }
    Database.update(scope, false);
}
```

## Hotfixes

```bash
git checkout main
git checkout -b hotfix/claim-approval-null-pointer

# fix, add a test reproducing the defect, commit

sf project deploy validate --manifest manifest/package.xml \
  --test-level RunLocalTests --target-org production --wait 60
sf project deploy quick --job-id 0Af... --target-org production

# merge back into main AND every long-lived branch
git checkout main && git merge hotfix/claim-approval-null-pointer && git push
git checkout uat && git merge main && git push
git checkout integration && git merge main && git push
```

**Merging back into every long-lived branch is the step that gets forgotten**, and the result is the bug reappearing in the next release because uat still holds the old code. See [[21.7 - Git Branching Strategies for Salesforce]].

**Add the test in the hotfix**, not afterwards. A defect that reached production is a case nobody tested, and the test is what stops it recurring silently.

**Keep the hotfix minimal.** The temptation to include the other small fix is how a hotfix becomes an incident.

## Release windows

**Deploy when someone can watch it.** Friday evening is convenient for users and terrible for whoever gets the call on Saturday.

**Deploy when users are not working**, which for a global org means picking the least-bad window rather than a good one.

**Validate in advance, quick-deploy in the window.** A thirty-minute test run on Thursday afternoon becomes a two-minute deployment on Saturday morning. See [[21.8 - CI-CD Pipelines]].

**Have a rehearsal.** Deploying to a full sandbox with production-shaped data, timed, tells you how long the real one takes and what breaks.

**Smoke test immediately after:**

```java
// scripts/apex/smoke-test.apex
Warranty_Claim__c claim = new Warranty_Claim__c(
    Asset__c = testAssetId, Claim_Amount__c = 150000, Claim_Date__c = Date.today()
);
insert claim;

Warranty_Claim__c saved = [
    SELECT Approval_Tier__c, Region__c FROM Warranty_Claim__c WHERE Id = :claim.Id
];

if (saved.Approval_Tier__c == null) {
    throw new SmokeTestException('Approval tier was not derived — the trigger may not be active');
}

delete claim;
```

A scripted smoke test running immediately after deployment catches the catastrophic case in seconds rather than waiting for a user to report it.

## A release checklist

```
Before
  [ ] Validated against production, tests passing
  [ ] Deployed and tested in a full sandbox with production-shaped data
  [ ] Timed, so the window is realistic
  [ ] Post-deployment script written and idempotent
  [ ] Manual steps documented, with an owner
  [ ] Feature toggle in place for anything risky
  [ ] Previous version tagged and deployable
  [ ] Data changes reversible, or backed up
  [ ] Someone available afterwards

During
  [ ] Deploy in sequence — schema, code, automation, security
  [ ] Run the post-deployment script
  [ ] Run the smoke test
  [ ] Complete the manual steps
  [ ] Enable the feature toggle

After
  [ ] Verify the smoke test passed
  [ ] Check for errors in the log and in AsyncApexJob
  [ ] Confirm scheduled jobs are scheduled
  [ ] Tag the release
  [ ] Communicate completion
```

## Practical guidance

**Design for forward recovery.** There is no rollback.

**Deploy additively**, and leave a release gap before removing anything.

**Never rename or retype a field in one release.**

**Use feature toggles** for anything risky, and remove them once stable.

**Build and test a bypass mechanism** before you need it.

**Sequence the deployment** — schema, code, automation, security, then enable.

**Make the post-deployment script idempotent**, including scheduled job rescheduling.

**Validate in advance, quick-deploy in the window.**

**Smoke test immediately after.**

**Merge hotfixes into every long-lived branch**, with the test included.
