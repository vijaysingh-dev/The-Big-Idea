# Hierarchical and Self Relationships

## Two related ideas

A **self relationship** is a lookup from an object to itself, used to build a tree. Account has one built in: `ParentId`, which creates account hierarchies.

A **hierarchical relationship** is a special lookup type available only on the User object, used for the manager chain. It is a distinct field type because the platform uses it for approval routing and for hierarchical custom settings.

Both model the same shape — a tree — and both share the same set of problems.

## Building a self relationship

Create a lookup on the object, pointing at the same object.

```
Object: Machine__c
Field: Parent_Machine__c
Type: Lookup(Machine__c)
Child relationship name: Sub_Machines
```

Now a production line can be a machine containing component machines, each of which can contain others.

The platform will not let you create a master-detail self relationship directly, though you can achieve something similar with a junction object. In practice a lookup is what you want, because cascade-deleting an entire hierarchy is rarely the desired behaviour.

## Standard hierarchies to know

- **Account.ParentId** — corporate structures, subsidiaries, divisions
- **User.ManagerId** — the hierarchical relationship, used by approval processes
- **Case.ParentId** — parent and child cases, for splitting or grouping issues
- **UserRole.ParentRoleId** — the role hierarchy, which drives record visibility
- **Product2 and Campaign** both support parent references

The role hierarchy is the one with the most consequence, because record access flows up it. See [[03.8 - Role Hierarchy]].

## The hard part: querying a tree

SOQL has no recursive query. There is no `CONNECT BY`, no recursive common table expression. You cannot ask for "this record and all its descendants" in one query.

You can traverse a fixed number of levels upward:

```sql
SELECT Id, Name,
       Parent_Machine__r.Name,
       Parent_Machine__r.Parent_Machine__r.Name,
       Parent_Machine__r.Parent_Machine__r.Parent_Machine__r.Name
FROM Machine__c
WHERE Id = :machineId
```

This works to 5 levels and is genuinely ugly. It also silently returns nulls beyond the actual depth, so code reading it must handle that.

For an unknown depth, you query level by level in a loop:

```java
public with sharing class MachineHierarchyService {

    public static Set<Id> getAllDescendants(Id rootMachineId) {
        Set<Id> allDescendants = new Set<Id>();
        Set<Id> currentLevel = new Set<Id>{ rootMachineId };
        Integer depth = 0;

        // each pass fetches one level down; the depth cap prevents a cycle from looping forever
        while (!currentLevel.isEmpty() && depth < 10) {
            Set<Id> nextLevel = new Set<Id>();
            for (Machine__c child : [
                SELECT Id FROM Machine__c WHERE Parent_Machine__c IN :currentLevel
            ]) {
                if (allDescendants.add(child.Id)) {
                    nextLevel.add(child.Id);
                }
            }
            currentLevel = nextLevel;
            depth++;
        }
        return allDescendants;
    }
}
```

Two things make that safe. `Set.add()` returns false if the value was already present, so a record already seen is not queued again — which stops a cycle from producing an infinite loop. And the depth cap bounds the number of queries, because each level costs one SOQL query against a 100-query limit.

That query cost is the real constraint. A ten-level hierarchy costs ten queries before you have done anything else. Deep or unbounded hierarchies are a poor fit for synchronous Apex and usually belong in Batch Apex.

## The materialized path pattern

When hierarchy traversal is frequent and performance matters, the standard workaround is to store the path on each record.

Add a text field holding the ancestry:

```
Machine A (root)         Hierarchy_Path__c = "/a1B000001/"
  Machine B              Hierarchy_Path__c = "/a1B000001/a1B000002/"
    Machine C            Hierarchy_Path__c = "/a1B000001/a1B000002/a1B000003/"
```

Now "everything under Machine A" is a single indexed query:

```sql
SELECT Id, Name FROM Machine__c WHERE Hierarchy_Path__c LIKE '/a1B000001/%'
```

One query instead of ten. Also a `Hierarchy_Level__c` number field makes depth filtering trivial.

The cost is maintenance: the path must be recomputed whenever a record's parent changes, and moving a node high in the tree means updating every descendant. That is usually a Queueable or Batch job rather than a synchronous trigger, because the descendant count is unbounded.

This tradeoff — cheap reads, expensive writes — is the right one whenever the tree is read far more often than it is restructured, which is almost always.

## Preventing cycles

Nothing in the platform stops a record from becoming its own ancestor. A user sets Machine A's parent to Machine C, which is already a descendant of A, and now traversal loops forever.

This must be prevented explicitly. A validation rule can catch the trivial case of a record pointing at itself:

```
Id = Parent_Machine__c
```

The general case needs Apex, walking upward from the proposed parent to check the record does not appear:

```java
public with sharing class MachineHierarchyValidator {

    public static void preventCycles(List<Machine__c> machines, Map<Id, Machine__c> oldMap) {
        Map<Id, Id> parentByChild = new Map<Id, Id>();
        for (Machine__c m : [SELECT Id, Parent_Machine__c FROM Machine__c WHERE Parent_Machine__c != null]) {
            parentByChild.put(m.Id, m.Parent_Machine__c);
        }

        for (Machine__c m : machines) {
            if (m.Parent_Machine__c == null) {
                continue;
            }
            if (oldMap != null && oldMap.get(m.Id).Parent_Machine__c == m.Parent_Machine__c) {
                continue;
            }

            Id ancestor = m.Parent_Machine__c;
            Integer guard = 0;
            while (ancestor != null && guard < 50) {
                if (ancestor == m.Id) {
                    m.addError('This would create a circular hierarchy.');
                    break;
                }
                ancestor = parentByChild.get(ancestor);
                guard++;
            }
        }
    }
}
```

Note the single query outside the loop, and the guard counter as a second line of defence in case a cycle already exists in the data. Both are necessary.

## Account hierarchies in practice

Account's `ParentId` is used in almost every enterprise org, and it has real limitations worth knowing before someone promises otherwise.

**Roll-ups do not aggregate up a hierarchy.** There is no native way to sum opportunity amounts across an account and all its subsidiaries. This is one of the most frequently requested things in Sales Cloud and it requires custom Apex, a scheduled job, or a package.

**Sharing does not follow the hierarchy.** Access to a parent account does not grant access to its children. People assume it does, constantly.

**Depth is not enforced.** Nothing prevents a fifteen-level corporate structure, and reporting on it becomes impractical.

Because of this, enterprise orgs frequently add a `Ultimate_Parent_Account__c` lookup maintained by automation, pointing every account in a tree at the top of it. Reporting then groups on that single field instead of traversing. It is the materialized path idea in its simplest form, and it solves most real reporting requirements.

## User hierarchy and approvals

The hierarchical relationship on User exists mainly so approval processes can route to "the submitter's manager" without hardcoding anyone. Approval steps can walk this chain, which means the manager field must be accurate for approvals to work at all.

Hierarchical custom settings also use it, resolving a value at org level, then profile, then user, with the most specific winning. See [[17.2 - Custom Settings]].

## Design guidance

**Cap the depth deliberately.** An unbounded hierarchy is an unbounded query count. Most businesses genuinely need three or four levels, and a validation rule enforcing that is cheaper than the code to handle fifteen.

**Store the path if you traverse often.** The maintenance cost is real but bounded; the traversal cost is not.

**Never traverse a hierarchy inside a trigger without limits.** A synchronous trigger that walks a tree will eventually meet a tree deep enough to exhaust the query limit. Push it to async. See [[12.3 - Queueable Apex]].

**Always guard against cycles.** Not sometimes. A single cyclical record can take down every batch job that touches the object.
