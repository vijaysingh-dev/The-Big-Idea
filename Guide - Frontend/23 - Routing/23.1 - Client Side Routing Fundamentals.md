# Client Side Routing Fundamentals

A traditional navigation is a full page load: request, parse HTML, download assets, execute scripts, discard everything from the previous page. **Client-side routing** intercepts that, updates the URL, and swaps the rendered view without a server round trip.

## The History API

The whole mechanism rests on three browser APIs:

```js
history.pushState(state, "", "/products/42");    // adds an entry, no navigation
history.replaceState(state, "", "/products/42"); // replaces the current entry

window.addEventListener("popstate", (e) => {
  // fires on back/forward — NOT on pushState
  render(location.pathname, e.state);
});
```

`pushState` changes the URL and adds a history entry without loading anything. `popstate` fires when the user navigates with the back or forward button.

The asymmetry matters: `pushState` does **not** fire `popstate`, so a router must handle its own navigations directly and only use `popstate` for browser-driven ones.

A minimal router:

```js
function navigate(path) {
  history.pushState(null, "", path);
  render(path);
}

window.addEventListener("popstate", () => render(location.pathname));

document.addEventListener("click", (e) => {
  const link = e.target.closest("a");
  if (!link || link.origin !== location.origin) return;
  if (e.metaKey || e.ctrlKey || e.shiftKey || link.target === "_blank") return;
  e.preventDefault();
  navigate(link.pathname + link.search);
});
```

The modifier-key and `target` checks are essential — without them, Cmd+click stops opening a new tab, which users notice immediately. Every real router does this ([[12.4 - Event Delegation]]).

## The location object

```js
location.pathname   // "/products/42"
location.search     // "?sort=price&page=2"
location.hash       // "#reviews"
location.origin     // "https://example.com"

new URLSearchParams(location.search).get("sort");   // "price"
```

`URLSearchParams` handles encoding, repeated keys and iteration properly. Parsing query strings by hand is a recurring source of bugs with array values and special characters.

## The server must cooperate

Client routing means a URL like `/products/42` exists only in JavaScript. If the user refreshes or shares that link, the server receives a request for a path that has no file.

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

Every static host needs an equivalent rewrite — Netlify's `_redirects`, Vercel's rewrites, S3's error-document trick, Apache's `.htaccess`. Missing it produces "works when I click, 404 on refresh", which is one of the most common deployment surprises.

Hash routing (`/#/products/42`) avoids the requirement entirely, since the hash never reaches the server. That is its only advantage; the URLs are ugly, they hurt SEO, and the hash is unavailable for anchors. Use it only when server configuration is genuinely impossible.

## What routers add

Beyond `pushState`, a router provides:

- **Route matching** with params — `/products/:id`
- **Nested routes** and shared layouts ([[23.2 - React Router Setup and Nested Routes]])
- **Scroll restoration** — browsers do it for real navigations, not for `pushState`
- **Focus management** on navigation
- **Code splitting** per route ([[23.5 - Lazy Routes]])
- **Data loading** coordinated with navigation ([[23.6 - Data Loading with Loaders and Actions]])
- **Navigation blocking** for unsaved changes
- **Transitions** so Suspense boundaries do not flash ([[22.4 - useTransition and startTransition]])

The last three are why hand-rolled routers stop being viable past a certain size.

## Accessibility on navigation

The single most-missed part of client routing.

A real page load resets focus to the document and announces the new page. `pushState` does neither — a screen reader user stays exactly where they were while the content changes entirely, with no indication anything happened.

```jsx
function Route({ children, title }) {
  const ref = useRef(null);
  const { pathname } = useLocation();

  useEffect(() => {
    document.title = title;
    ref.current?.focus();
  }, [pathname, title]);

  return <main ref={ref} tabIndex={-1}>{children}</main>;
}
```

Three things needed on every navigation: move focus (to `<main>` or the page heading), update `document.title`, and optionally announce via a live region ([[09.5 - Accessibility Fundamentals]]).

`tabIndex={-1}` makes the element programmatically focusable without adding it to the tab order ([[17.8 - useRef]]).

## Scroll restoration

Browsers restore scroll position on real back/forward navigation. With `pushState` they do not, so a router must handle it:

```js
history.scrollRestoration = "manual";
```

The pattern is to save `window.scrollY` keyed by history entry before navigating away, and restore it on `popstate`. React Router provides `<ScrollRestoration />` for this.

Getting it right requires waiting for content to render before scrolling, which is why naive implementations restore to the wrong position on data-loaded pages.

## Links must be real anchors

```jsx
<a href="/products/42">Product</a>          {/* correct */}
<div onClick={() => navigate("/products/42")}>Product</div>   {/* wrong */}
```

A `<div>` with an onClick loses: Cmd+click, middle-click, right-click "open in new tab", keyboard activation, the status-bar URL preview, and — importantly — crawlability. Search engines follow `href` attributes, not click handlers ([[09.4 - Head Metadata and SEO Basics]]).

`<Link>` components render real anchors and call `preventDefault` only for plain left-clicks.

## SPA versus MPA

Client routing is not automatically better:

**Client routing wins** for app-like experiences with shared state across views, frequent navigation between related screens, and expensive-to-recreate UI (an editor, a dashboard, a map).

**Server routing wins** for content sites, when SEO matters most, when the initial load budget is tight, and when there is little shared state between pages.

Modern frameworks blur this — Next.js and React Router v7 do server rendering with client navigation, getting the initial-load characteristics of MPAs and the transition smoothness of SPAs ([[28.11 - Rendering Strategies]]).

The View Transitions API now gives cross-document animated transitions to plain server-rendered sites, removing one of the historical reasons to adopt an SPA ([[11.4 - Transitions and Animations]]).

## How senior engineers actually use this

**They configure the server rewrite first**, because it is the failure everyone hits and it only appears in deployment.

**They handle focus and title on every navigation**, since it is invisible in testing and essential for real users.

**They always render real anchors** for anything navigable.

**They choose routing strategy from the content**, not by default — a marketing site does not need an SPA.

**They let the router handle scroll restoration** rather than hand-rolling it.

## Common pitfalls

- Missing server rewrite, so refresh 404s.
- Intercepting Cmd/Ctrl-click and breaking new-tab behavior.
- `<div onClick>` instead of `<a href>`.
- No focus management, leaving screen reader users lost on navigation.
- `document.title` never updated, so history and tabs are unlabelled.
- Expecting `pushState` to fire `popstate`.
- Parsing query strings manually instead of using `URLSearchParams`.

## Interview angle

"How does client-side routing work" wants the History API — `pushState` changes the URL without a request, `popstate` handles back/forward, and a click handler intercepts anchors. The details that distinguish a strong answer: the server needs a catch-all rewrite or refresh 404s, `pushState` does not fire `popstate`, and modifier-key clicks must be left alone. Raising focus management and `document.title` on navigation is the accessibility point most candidates miss entirely.
