# Fiber Architecture

Fiber is the rewrite of React's core that shipped in React 16. Its purpose was to make rendering **interruptible**, which the previous implementation could not be.

## The problem it solved

The old reconciler ("stack reconciler") walked the tree with recursion:

```
render(A) → render(B) → render(C) → ...
```

Recursion means the call stack owns the traversal. There is no way to pause halfway, hand control to the browser, and resume — you would have to unwind the stack and lose your place.

So a large tree update ran to completion, blocking the main thread. A 200ms render meant 200ms of frozen UI: no paint, no input handling ([[01.4 - The Event Loop]]).

Fiber replaces recursion with a **linked list the reconciler walks manually**, so the traversal state lives in data rather than on the call stack. That single change is what makes pausing possible.

## What a fiber is

A fiber is a JavaScript object representing one unit of work — roughly, one element in the tree, with persistent identity across renders.

```js
{
  tag: FunctionComponent,      // what kind of node
  type: MyComponent,            // the function, or "div"
  key: null,
  stateNode: null,              // the DOM node, for host components
  memoizedState: hooksLinkedList,   // the hooks chain
  memoizedProps: {...},
  pendingProps: {...},

  return: parentFiber,          // "parent"
  child: firstChildFiber,
  sibling: nextSiblingFiber,

  alternate: otherTreeFiber,    // the counterpart in the other tree
  flags: Placement | Update,    // what to do at commit
  lanes: 0b0010,                // priority of pending work
}
```

Three pointers instead of a children array: `child`, `sibling`, `return`. That is what makes it a traversable linked structure.

Note `memoizedState` on a function component fiber holds the **hooks linked list** — which is why hooks are positional and why call order must be stable ([[17.1 - Rules of Hooks and How They Work]]).

## The traversal

React walks the tree iteratively:

```
begin(fiber)
  if fiber has a child   → move to child
  else                   → complete(fiber), then move to sibling
  if no sibling          → complete(parent), move to parent's sibling
```

Depth-first, but driven by an explicit loop:

```js
function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork) requestIdleCallbackLike(workLoop);   // resume later
  else commitRoot();
}
```

`nextUnitOfWork` is a variable, not a stack frame. React can stop after any unit, yield to the browser, and pick up exactly where it left off ([[18.5 - Concurrent Rendering and the Scheduler]]).

## Double buffering

React maintains **two trees**:

- **current** — what is on screen
- **workInProgress** — what is being built

Each fiber has an `alternate` pointer to its counterpart in the other tree. React builds the workInProgress tree, and at commit swaps `root.current` to point at it. The old tree then becomes the scratch space for the next render, so fibers are recycled rather than reallocated.

```
current  ⇄  alternate  ⇄  workInProgress
```

Two consequences:

**Abandoning work is free.** If a render is interrupted by something higher priority, React discards the incomplete workInProgress tree. The current tree is untouched, so the user never sees a partial update. This is why rendering must be pure — a discarded render's side effects cannot be undone ([[16.5 - Rendering and Purity]]).

**Commit is atomic.** The swap is a single pointer assignment, so the DOM is never in a half-updated state.

## Lanes

Fiber tracks priority using **lanes** — a bitmask where each bit is a priority level.

```
SyncLane           discrete input (click, keypress)
InputContinuous    dragging, scrolling
DefaultLane        normal updates
TransitionLane     startTransition
IdleLane           offscreen work
```

A bitmask lets React express "work at these several priorities" and check membership with a single bitwise operation, which is why lanes replaced the earlier expiration-time model.

An update is assigned a lane based on how it was triggered. React renders the highest-priority lanes first; a low-priority render in progress is interrupted when a higher-priority update arrives ([[22.4 - useTransition and startTransition]]).

## Flags

During the render phase React records what each fiber needs at commit time in a `flags` bitmask:

```
Placement   insert into the DOM
Update      change attributes or run effects
Deletion    remove
Ref         attach or detach a ref
Passive     has a useEffect to run
```

Fibers with flags are collected into an **effect list** so the commit phase can walk only the changed nodes rather than the entire tree.

This split — figure out *what* to do in the interruptible render phase, *do* it in the atomic commit phase — is the central structural idea ([[18.4 - Render Phase vs Commit Phase]]).

## What this buys you

The concrete features Fiber made possible:

- **Concurrent rendering** — interruptible, prioritized updates
- **Suspense** — pausing a subtree while data loads and showing a fallback
- **Error boundaries** — a fiber can catch an error and re-render a fallback subtree
- **Portals** — a fiber's DOM output can be placed anywhere
- **Returning arrays and fragments** — a fiber can produce several children without a wrapper
- **Server Components and streaming** — partial trees committed as they arrive

None of these were expressible with a recursive reconciler.

## What you actually need from this

You will not interact with fibers directly. What matters practically:

**Rendering must be pure**, because a render may be discarded or repeated. This is not a style rule; the architecture depends on it.

**Hooks are positional** because they live in a linked list on the fiber.

**State survives when the fiber survives.** A fiber persists as long as its type and position are stable — which is exactly the reconciliation rule ([[18.2 - Reconciliation and the Diffing Algorithm]]).

**Interruption is real.** Under transitions or Suspense, a component may render several times before anything commits.

## How senior engineers actually use this

**They treat purity as load-bearing**, because they know why it is required rather than just that it is.

**They read `__reactFiber$` in DevTools occasionally** when debugging a library integration, though this is rare.

**They explain state loss correctly** — "the fiber was replaced because the type or position changed" — rather than guessing.

**They do not optimize around fiber.** It is background knowledge that informs judgment, not a performance lever.

## Common pitfalls

- Assuming a component function runs exactly once per commit. Under concurrent rendering it may run several times.
- Side effects during render, which a discarded render leaves stranded.
- Reading or writing refs during render, which is unsafe for the same reason.
- Treating "fiber" as something to tune. It is architecture, not configuration.

## Interview angle

"What is Fiber" is a senior-level question. The answer: a rewrite of the reconciler replacing recursive traversal with a linked list of work units, so rendering can be paused, resumed, prioritized and abandoned. Mention double buffering (current and workInProgress with alternate pointers, giving atomic commits and free abandonment) and lanes for priority. Close by connecting it to what it enabled — concurrent rendering, Suspense, error boundaries — and to why purity is architecturally required.
