# Dynamic SOQL

## When the query is not known at compile time

Inline SOQL is validated at deployment — a bad field name fails to compile. That safety is real and it is why inline SOQL is the default.

Dynamic SOQL gives that up in exchange for building the query at runtime. Legitimate reasons:

- The object or fields are configuration-driven
- A user chooses which columns to display or which field to sort by
- A generic utility works across several objects
- Filters are assembled from a variable set of criteria
- A managed package must adapt to the subscriber org's schema

If none of those apply, use inline SOQL.

## The mechanics

```java
String query = 'SELECT Id, Claim_Number__c, Status__c FROM Warranty_Claim__c WHERE Status__c = :status';
String status = 'Submitted';
List<Warranty_Claim__c> claims = Database.query(query);
```

**Bind variables work in dynamic SOQL**, and they resolve against variables in the enclosing scope. This is the primary defence against injection and should be used wherever a value is involved.

`Database.query` returns `List<SObject>`, cast to the concrete type when known.

`Database.queryWithBinds` takes an explicit bind map, which is clearer and does not depend on variable scoping:

```java
Map<String, Object> binds = new Map<String, Object>{
    'status' => 'Submitted',
    'threshold' => 100000
};

List<Warranty_Claim__c> claims = Database.queryWithBinds(
    'SELECT Id, Claim_Number__c FROM Warranty_Claim__c '
    + 'WHERE Status__c = :status AND Claim_Amount__c > :threshold',
    binds,
    AccessLevel.USER_MODE
);
```

This is the form to prefer in new code. The explicit bind map removes the scoping dependency, and the `AccessLevel` parameter enforces sharing, object, and field permissions in one place. See [[03.13 - Enforcing Security in Apex and SOQL]].

## SOQL injection

The vulnerability that makes this note necessary.

```java
// Vulnerable
String status = ApexPages.currentPage().getParameters().get('status');
String query = 'SELECT Id FROM Warranty_Claim__c WHERE Status__c = \'' + status + '\'';
List<SObject> results = Database.query(query);
```

An input of `Closed' OR Name != '` turns the filter into something matching every row. On an object with field-level restrictions or in a portal context, this is a real data exposure.

Three defences, in order of preference:

**1. Bind variables.** Always, for values.

**2. `String.escapeSingleQuotes()`** where a bind genuinely cannot be used. This escapes quotes and nothing else — it does not sanitize field names or operators.

**3. An allowlist** for anything that cannot be bound.

Field names, object names, and the `ORDER BY` field **cannot** be bind variables. An allowlist is the only safe approach:

```java
public with sharing class ClaimQueryService {

    private static final Set<String> SORTABLE_FIELDS = new Set<String>{
        'Claim_Date__c', 'Claim_Amount__c', 'Status__c', 'Claim_Number__c'
    };

    private static final Set<String> SORT_DIRECTIONS = new Set<String>{ 'ASC', 'DESC' };

    public static List<Warranty_Claim__c> search(String sortField, String direction, String status) {
        if (!SORTABLE_FIELDS.contains(sortField)) {
            throw new IllegalArgumentException('Invalid sort field: ' + sortField);
        }
        if (!SORT_DIRECTIONS.contains(direction.toUpperCase())) {
            throw new IllegalArgumentException('Invalid sort direction');
        }

        // sortField and direction are validated against allowlists; status is bound
        String query =
            'SELECT Id, Claim_Number__c, Claim_Date__c, Claim_Amount__c, Status__c '
            + 'FROM Warranty_Claim__c '
            + 'WHERE Status__c = :status '
            + 'ORDER BY ' + sortField + ' ' + direction.toUpperCase() + ' NULLS LAST '
            + 'LIMIT 200';

        return Database.query(query);
    }
}
```

Throwing on an invalid value rather than silently defaulting is deliberate — a caller passing an unexpected field name is either a bug or an attack, and both should be loud.

## Building queries safely

A query builder that validates field names against the schema is the robust general solution:

```java
public with sharing class SafeQueryBuilder {

    private final Schema.SObjectType objectType;
    private final Set<String> validFields;
    private final List<String> selectFields = new List<String>();
    private final List<String> conditions = new List<String>();

    public SafeQueryBuilder(String objectName) {
        this.objectType = Schema.getGlobalDescribe().get(objectName);
        if (objectType == null) {
            throw new IllegalArgumentException('Unknown object: ' + objectName);
        }
        this.validFields = objectType.getDescribe().fields.getMap().keySet();
    }

    public SafeQueryBuilder selectField(String fieldName) {
        // validating against the describe means an unknown or misspelled field fails immediately
        if (!validFields.contains(fieldName.toLowerCase())) {
            throw new IllegalArgumentException('Unknown field: ' + fieldName);
        }
        selectFields.add(fieldName);
        return this;
    }

    public SafeQueryBuilder whereEquals(String fieldName, String bindName) {
        if (!validFields.contains(fieldName.toLowerCase())) {
            throw new IllegalArgumentException('Unknown field: ' + fieldName);
        }
        conditions.add(fieldName + ' = :' + bindName);
        return this;
    }

    public String build() {
        if (selectFields.isEmpty()) {
            selectFields.add('Id');
        }
        String query = 'SELECT ' + String.join(selectFields, ', ')
            + ' FROM ' + objectType.getDescribe().getName();
        if (!conditions.isEmpty()) {
            query += ' WHERE ' + String.join(conditions, ' AND ');
        }
        return query;
    }
}
```

`Schema.getGlobalDescribe()` is expensive — it walks every object in the org. Call it once and cache the result in a static, never inside a loop. This is a common cause of `Apex CPU time limit exceeded` in code that looks harmless. See [[16.3 - CPU Time and Heap Size]].

## Field-level security with dynamic queries

Dynamic SOQL makes it easier to accidentally select fields the user cannot see, because the field list is assembled rather than reviewed.

`AccessLevel.USER_MODE` on `queryWithBinds` handles it. Where that is not available, `stripInaccessible` on the results does:

```java
List<SObject> results = Database.query(query);
SObjectAccessDecision decision = Security.stripInaccessible(AccessType.READABLE, results);
return decision.getRecords();
```

See [[03.6 - Field Level Security]].

## A configuration-driven query

The pattern that justifies dynamic SOQL in most orgs — a component whose columns are configurable:

```java
public with sharing class ConfigurableListController {

    @AuraEnabled(cacheable=true)
    public static List<SObject> getRecords(String configName, Id parentId) {
        List<List_Configuration__mdt> configs = [
            SELECT Object_API_Name__c, Field_List__c, Parent_Field__c,
                   Filter_Clause__c, Sort_Field__c, Row_Limit__c
            FROM List_Configuration__mdt
            WHERE DeveloperName = :configName
            LIMIT 1
        ];
        if (configs.isEmpty()) {
            throw new IllegalArgumentException('Unknown list configuration');
        }
        List_Configuration__mdt config = configs[0];

        SafeQueryBuilder builder = new SafeQueryBuilder(config.Object_API_Name__c);
        for (String field : config.Field_List__c.split(',')) {
            builder.selectField(field.trim());
        }
        builder.whereEquals(config.Parent_Field__c, 'parentId');

        String query = builder.build();
        if (String.isNotBlank(config.Filter_Clause__c)) {
            query += ' AND ' + config.Filter_Clause__c;
        }
        query += ' ORDER BY ' + config.Sort_Field__c
              + ' LIMIT ' + Integer.valueOf(config.Row_Limit__c);

        return Database.queryWithBinds(
            query,
            new Map<String, Object>{ 'parentId' => parentId },
            AccessLevel.USER_MODE
        );
    }
}
```

The metadata holds the configuration, so adding a new list is a deployment of a record rather than a code change. See [[18.10 - Custom Metadata Driven Architecture]].

Note the residual risk: `Filter_Clause__c` is raw SOQL from metadata, concatenated in. That is acceptable only because Custom Metadata records are deployable metadata, editable only by someone with Customize Application — not user input. Documenting that assumption matters, because the next person may not realize it.

## Other dynamic operations

Dynamic SOQL usually appears alongside dynamic sObject handling:

```java
// Create an sObject by name
SObject record = Schema.getGlobalDescribe().get('Warranty_Claim__c').newSObject();
record.put('Status__c', 'Submitted');
record.put('Claim_Amount__c', 150000);
insert record;

// Read a field by name
Object value = record.get('Claim_Amount__c');

// Read what was actually populated
Map<String, Object> populated = record.getPopulatedFieldsAsMap();
```

`getPopulatedFieldsAsMap()` returns only fields that were queried or set, which is the correct way to check whether a field was in the result set rather than merely null.

## Practical guidance

**Use inline SOQL unless you genuinely cannot.** The compile-time validation is worth a lot.

**Prefer `queryWithBinds` with `AccessLevel.USER_MODE`** for new dynamic queries.

**Never concatenate a value.** Bind it.

**Allowlist field names, object names, and sort directions.** They cannot be bound.

**Validate against the describe** rather than a hardcoded list where the field set is open-ended.

**Cache `getGlobalDescribe()`** in a static. It is expensive.

**Document any place raw SOQL fragments come from metadata**, so the trust assumption is explicit.
