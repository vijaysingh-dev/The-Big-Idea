# Salesforce Editions and Licensing

## Why a developer needs this

Licensing sounds like a procurement problem. It is actually one of the most common causes of a design that has to be thrown away.

You can build a beautiful solution and then discover that the users it is for cannot see the Opportunity object, or that the org cannot create another custom tab, or that the integration you designed exceeds the daily API allowance. None of these are code problems and none of them can be fixed in code.

## Editions

An **edition** is the tier of Salesforce the customer bought. It sets what features exist and what the limits are.

| Edition | Position | Developer-relevant notes |
| --- | --- | --- |
| Essentials / Starter | Small business entry tier | Very restricted; no Apex, minimal customization |
| Professional | Mid-market | No Apex by default, limited API access; a frequent constraint |
| Enterprise | The common enterprise default | Full Apex, API, workflow, custom objects. Most orgs you work in |
| Unlimited / Performance | Enterprise plus higher limits | More API calls, more sandboxes, more storage, premier support |
| Developer Edition | Free personal org | Full feature set, tiny limits and storage. Your practice environment |

The one to remember: **Professional Edition is where developers get surprised.** Apex is not available in Professional Edition in the normal way. Custom Apex can only run there if it arrives inside a managed package that passed Salesforce's security review. If a client is on Professional and asks for a trigger, the honest answers are "upgrade to Enterprise", "solve it with flow", or "package it", not "sure".

Edition also controls hard ceilings: number of custom objects, custom fields per object, number of sandboxes, daily API call allowance, and data storage. These are not soft limits and they cannot be raised without paying.

## User licenses

Edition is what the *company* bought. A **user license** is what an *individual user* is allowed to do. This is where the real architectural constraints live.

**Salesforce (full CRM) license.** Access to everything, including the standard CRM objects: Lead, Opportunity, Case, Campaign, Quote, Contract. The most expensive license.

**Salesforce Platform license.** Access to custom objects, plus a limited set of standard objects — Account, Contact, Activity, Report, Dashboard, Document — but **not** Lead, Opportunity, Case, Campaign, or Forecast. Much cheaper. Used for employees who need a custom internal app but not the CRM itself.

**Experience Cloud licenses.** For external users — customers, partners, distributors, patients. Several types, priced per login or per member. These users have significantly restricted access, cannot be given a role in the normal way, and rely on Sharing Sets and Sharing Rules for record access. See [[17.9 - Experience Cloud Basics]].

**Chatter and Identity licenses.** Collaboration or single-sign-on only.

The Platform license limitation is the classic trap. A design that stores work on a custom object and displays related Cases will fail for Platform-licensed users, because Case is simply invisible to them. Discovering this after building is expensive.

You can check what a user actually has:

```sql
SELECT Id, Name, Profile.Name, Profile.UserLicense.Name, UserType
FROM User
WHERE IsActive = true
```

And what the org owns:

```sql
SELECT Name, TotalLicenses, UsedLicenses, Status
FROM UserLicense
```

Both are useful during discovery on an unfamiliar org, and both are worth checking before you promise anything.

## Add-on products

Several capabilities people assume are "in Salesforce" are separately purchased, and their absence changes the design.

- **Salesforce Shield** — platform encryption, field audit trail, event monitoring. See section 22.
- **CPQ and Revenue Cloud** — advanced quoting, pricing rules, subscription billing.
- **Field Service** — work orders, scheduling, mobile technicians.
- **CRM Analytics** — advanced analytics beyond standard reports.
- **Data Cloud** and **Agentforce** — see section 24.
- **Additional API calls, storage, and sandboxes** — all purchasable, all metered.

"Can we just use Field Service for that?" is a licensing question with a price attached, not a configuration question.

## Limits that actually bite

**API call allowance.** Every org has a daily cap on inbound API requests, calculated from edition and user count. A poorly designed integration that polls every minute per record can exhaust an entire day's allowance before lunch. When the allowance is gone, integrations fail until the rolling window resets. This single fact shapes integration design more than anything else — it is why bulk and composite APIs exist. See [[13.4 - Bulk API 2.0]] and [[13.5 - Composite and Composite Graph API]].

**Data storage.** Most standard records are counted at 2 KB each regardless of actual size, so ten million records is roughly 20 GB, and orgs are usually allocated far less than they expect. Storage overruns are why archiving strategies exist. See [[23.4 - Archiving with Big Objects and External Storage]].

**File storage** is counted separately from data storage, and attachments consume it fast.

**Custom object and field counts.** Enterprise Edition allows a few hundred custom objects and a few hundred fields per object. Large orgs genuinely hit this and then have to consolidate, which is painful. It is one reason experienced engineers resist adding a field for every request.

You can see current consumption in Setup under Company Information, or query it:

```java
Map<String, System.OrgLimit> limits = OrgLimits.getMap();
System.OrgLimit apiRequests = limits.get('DailyApiRequests');
System.debug('API calls used: ' + apiRequests.getValue() + ' of ' + apiRequests.getLimit());
```

Production integrations often log this figure to catch exhaustion before users do.

## How this shapes real designs

**Licensing decides the external user architecture.** A retailer wanting a million customers to see their orders will not buy a million CRM licenses. The options are Experience Cloud with a login-based license model, or keeping that data outside Salesforce and integrating. The cost difference between those choices is enormous, and it is an architecture decision made on commercial grounds.

**Licensing decides build versus buy.** If a requirement needs CPQ and CPQ is not licensed, the choice is buy the product or build a simplified version on custom objects. Building looks cheaper until you own quoting logic for the next decade.

**Licensing decides integration patterns.** A tight API allowance pushes you toward batching, event-driven pushes, and change data capture, and away from chatty synchronous calls. See [[13.1 - Integration Fundamentals and Patterns]].

**Always ask three questions during discovery:** what edition is this org on, what licenses do the intended users hold, and what is the current API and storage consumption. Asking on day one prevents the most expensive category of rework there is.
