# Avoiding Architectural Mistakes

> **Revision tags:** #senior-thinking #architecture #antipatterns  
> **Related:** [[05.1 - Tradeoff Evaluation]] | [[05.2 - Failure First Thinking]] | [[05.3 - Design For Change]]

---

## Why Mistakes Happen

Architectural mistakes are rarely made by people who don't know the technology. They're made by people who:
- Apply the right tool to the wrong problem
- Optimize for the wrong dimension (future scale that never comes)
- Under-invest in the dimensions that matter (observability, failure handling)
- Make assumptions that later prove false

Most architectural mistakes are expensive to fix not because the fix is technically hard, but because production data has accumulated, teams have built on top of the bad decision, and changing the foundation disrupts everything.

---

## Mistake 1: Premature Microservices

**What happens:** A team of 5 engineers splits their system into 15 microservices because they've heard that's how "serious" companies do it.

**The actual cost:**
- Every feature now requires coordinating changes across 3–4 services
- Debugging requires tracing across service boundaries
- Deployment is 15 pipelines, not 1
- The team spends 60% of time on infrastructure, 40% on product
- Distributed transactions where a monolith would have had ACID

**The rule:** You need microservices when team ownership boundaries and scaling requirements diverge enough that a monolith becomes the bottleneck — not before.

**What to do instead:** Build a modular monolith. Extract a service only when you can point to a specific pain it solves (scaling need, team ownership conflict, different tech requirement).

---

## Mistake 2: Shared Mutable Database

**What happens:** Multiple services read and write the same database tables directly.

```
Order Service  ──→ DB.orders
Payment Service ──→ DB.orders  (reads order status)
Inventory Service ──→ DB.orders (updates fulfillment)
Analytics ──→ DB.orders (heavy read queries)
```

**The actual cost:**
- Schema migration in `orders` table requires coordinating and deploying all 4 services simultaneously
- Analytics heavy reads slow down transactional writes
- No clear ownership — any service can corrupt any other service's data
- "Microservices" in name only — tightly coupled in practice

**The rule:** Each service owns its data. Other services get data via API or events, not direct DB access.

---

## Mistake 3: Synchronous Chains of Doom

**What happens:** Every operation is a synchronous call chain.

```
User clicks "Checkout"
→ Order Service (sync) → Payment Service (sync) → Fraud Service (sync) → Risk API (sync)
→ Inventory Service (sync) → Warehouse API (sync)
→ Notification Service (sync) → Email API (sync) → SMS API (sync)
Total latency: sum of all hops
```

**The actual cost:**
- User waits for the slowest service in the chain
- One slow downstream affects all users
- One down downstream fails all checkouts
- Every new step added to the chain degrades latency for everyone

**The rule:** Identify which steps are truly synchronous (user needs the result immediately) and which can be async. For checkout: payment result is synchronous. Email notification is asynchronous.

```
User clicks "Checkout"
→ Order Service (sync) → Payment Service (sync)  ← user sees result here
→ Queue: [send email, update inventory, log analytics]  ← async, user doesn't wait
```

## Mistake 4: No Idempotency on Mutations

**What happens:** POST /charge creates a new charge every time it's called — no idempotency key.

```
Client calls POST /charge → network timeout (request may have succeeded)
Client retries POST /charge → user charged twice
```

**The actual cost:**
- Duplicate payments, duplicate orders, duplicate emails
- Angry users, customer support tickets, refunds
- Hard to detect (no error — two successful charges)

**The rule:** All non-idempotent operations must support an idempotency key. Clients must include it. The server must deduplicate.

---

## Mistake 5: Treating the Cache as the Source of Truth

**What happens:** Code reads from cache and assumes it always has the latest data. Writes update the cache but inconsistently update the DB (or the cache update fails silently).

```
# Dangerous pattern
cache.set("user:42:balance", new_balance)
# If this fails silently, cache has wrong data
# But code never checks DB — trusts cache
```

**The actual cost:**
- Cache diverges from DB; users see wrong balances, wrong inventory, wrong state
- Hard to reproduce (depends on timing of cache population)
- Recovery requires manual cache invalidation + restart

**The rule:** The database is the source of truth. The cache is a performance optimization. Cache misses should always fall through to the database. Critical data (balances, inventory) should not be cached without strong invalidation guarantees.

---

## Mistake 6: Missing Observability Until Production Breaks

**What happens:** The team builds a system, deploys to production, and only adds logging/metrics after the first major incident — when they realize they can't tell what's happening.

**The actual cost:**
- Incidents take 10× longer to diagnose without data
- Correlating symptoms to causes is guesswork
- "We think it was X, but we can't be sure"
- Pattern repeats because root cause was never confirmed

**The rule:** Observability is a first-class requirement, not an afterthought. Before launch: structured logging, RED metrics, distributed tracing, and SLO-based alerts must be in place.

---

## Mistake 7: Ignoring the N+1 Query Problem

**What happens:** Code fetches a list of items, then for each item makes an additional DB query.

```python
# N+1 problem
orders = db.query("SELECT * FROM orders WHERE user_id = ?", user_id)
for order in orders:
    # This is N additional queries for N orders
    order.items = db.query("SELECT * FROM order_items WHERE order_id = ?", order.id)
```

**The actual cost:**
- 100 orders → 101 DB queries instead of 2
- Latency grows linearly with list size
- DB connection pool exhausted under load
- No indication in code that this is a performance problem

**The rule:** Any list endpoint must batch-load related data. Use SQL JOINs, ORM eager loading (`prefetch_related`), or a single query with a `WHERE id IN (...)` clause.

---

## Mistake 8: Not Designing for Operational Day 2

**What happens:** The system works on launch day. Six months later, nobody knows how to:
- Debug a slow request in production
- Roll back a bad deploy safely
- Scale a specific bottleneck without downtime
- Rotate credentials
- Migrate the database schema

**The actual cost:**
- Incidents become outages because the team can't respond effectively
- Deployments require scheduled maintenance windows
- Engineers are afraid to change the system

**The rule:** For every component: write a runbook. Document: how to deploy, how to rollback, how to debug latency, how to scale, what the failure modes are, how to recover.

---

## The Checklist Before Committing to a Design

```
Architecture sanity check:
[ ] Does each service own its data? No shared mutable DB?
[ ] Are the async vs sync boundaries correct? No chains of doom?
[ ] Is every mutation idempotent or protected by idempotency keys?
[ ] Are there timeouts on every outbound call?
[ ] Is there a circuit breaker for every hard dependency?
[ ] Is the cache invalidation strategy correct and tested?
[ ] Are there metrics and alerts for every component?
[ ] Is the failure mode of each component designed (not assumed)?
[ ] Is the schema designed for forward-compatible evolution?
[ ] Is there a runbook for day-2 operations?
```
