# Redux Toolkit

Redux Toolkit (RTK) is the official, recommended way to write Redux. It is not a separate library so much as the standard configuration — hand-written action types, action creators and switch reducers are legacy.

## What it replaces

```js
// Before RTK — three files, ~50 lines for one feature
const ADD_TODO = "todos/ADD_TODO";
const addTodo = (text) => ({ type: ADD_TODO, payload: { id: nanoid(), text } });

function todosReducer(state = initialState, action) {
  switch (action.type) {
    case ADD_TODO:
      return { ...state, items: [...state.items, action.payload] };
    default:
      return state;
  }
}
```

```js
// With RTK
const todosSlice = createSlice({
  name: "todos",
  initialState: { items: [], filter: "all" },
  reducers: {
    todoAdded: {
      reducer(state, action) {
        state.items.push(action.payload);      // "mutation" — safe, see below
      },
      prepare(text) {
        return { payload: { id: nanoid(), text, done: false } };
      },
    },
    todoToggled(state, action) {
      const todo = state.items.find(t => t.id === action.payload);
      if (todo) todo.done = !todo.done;
    },
    filterChanged(state, action) {
      state.filter = action.payload;
    },
  },
});

export const { todoAdded, todoToggled, filterChanged } = todosSlice.actions;
export default todosSlice.reducer;
```

`createSlice` generates the action types (`"todos/todoAdded"`), the action creators, and the reducer from one definition.

## The mutation is not mutation

Reducer bodies look mutating but are not. RTK wraps them in Immer, which hands the reducer a **draft** — a `Proxy` that records writes and produces a correctly structurally-shared immutable result ([[20.6 - Immer and Immutable Updates]], [[08.3 - Proxy and Reflect]]).

Two rules that follow:

**Either mutate the draft or return a new state — never both:**

```js
// Wrong
todoCleared(state) {
  state.items = [];
  return { ...state, items: [] };   // throws
}

// Fine
todoCleared(state) { state.items = []; }
todoCleared() { return { items: [], filter: "all" }; }
```

**The draft only works inside the reducer.** Storing a draft or using it asynchronously throws, because Immer revokes the proxy when `produce` returns.

## The store

```js
import { configureStore } from "@reduxjs/toolkit";

export const store = configureStore({
  reducer: {
    todos: todosReducer,
    auth: authReducer,
  },
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

`configureStore` sets up, by default: the thunk middleware, Redux DevTools, and development-only checks for accidental mutation and non-serializable values in state or actions.

Those development checks are genuinely valuable — the serializability check catches `Date` objects, `Map`s and class instances landing in the store, which break time-travel debugging and persistence.

If you legitimately need non-serializable values (a `File` in an action, for instance):

```js
middleware: (getDefault) => getDefault({
  serializableCheck: { ignoredActions: ["upload/started"] },
}),
```

## Typed hooks

```ts
import { useDispatch, useSelector } from "react-redux";

export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
export const useAppSelector = useSelector.withTypes<RootState>();
```

Define these once and import them everywhere instead of the raw hooks. Without them, every `useSelector` call needs a manual `RootState` annotation and `dispatch` will not accept thunks.

## Async with createAsyncThunk

```js
export const fetchTodos = createAsyncThunk(
  "todos/fetch",
  async (userId, { rejectWithValue, signal }) => {
    try {
      const res = await fetch(`/api/todos?user=${userId}`, { signal });
      if (!res.ok) throw new Error(res.statusText);
      return res.json();
    } catch (err) {
      return rejectWithValue(err.message);
    }
  }
);

const todosSlice = createSlice({
  name: "todos",
  initialState: { items: [], status: "idle", error: null },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchTodos.pending, (state) => { state.status = "loading"; })
      .addCase(fetchTodos.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(fetchTodos.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.payload;
      });
  },
});
```

`createAsyncThunk` generates three action types and dispatches them around the promise. The `signal` it provides supports cancellation ([[04.6 - AbortController and Cancellation]]).

`extraReducers` is for responding to actions defined elsewhere — other slices' actions, or thunk lifecycle actions. This is how one action updates several slices.

## RTK Query

For server data, RTK Query removes the thunk boilerplate above entirely:

```js
export const api = createApi({
  reducerPath: "api",
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  tagTypes: ["Todo"],
  endpoints: (builder) => ({
    getTodos: builder.query({
      query: (userId) => `todos?user=${userId}`,
      providesTags: ["Todo"],
    }),
    addTodo: builder.mutation({
      query: (body) => ({ url: "todos", method: "POST", body }),
      invalidatesTags: ["Todo"],
    }),
  }),
});

export const { useGetTodosQuery, useAddTodoMutation } = api;
```

```jsx
function TodoList({ userId }) {
  const { data, isLoading, error } = useGetTodosQuery(userId);
  const [addTodo, { isLoading: isAdding }] = useAddTodoMutation();
}
```

Caching, deduplication, automatic refetching, tag-based invalidation, polling and optimistic updates — all handled. The `invalidatesTags`/`providesTags` mechanism is the invalidation model: adding a todo invalidates the `Todo` tag, which refetches every query providing it.

If you are already using Redux, RTK Query is the natural choice for server state. If you are not, TanStack Query is the more common standalone option ([[24.6 - TanStack Query Fundamentals]]). Both solve the same problem; neither should coexist with hand-written fetch thunks.

## createEntityAdapter

For normalized collections ([[20.7 - State Normalization]]):

```js
const todosAdapter = createEntityAdapter({
  sortComparer: (a, b) => b.createdAt - a.createdAt,
});

const todosSlice = createSlice({
  name: "todos",
  initialState: todosAdapter.getInitialState({ status: "idle" }),
  reducers: {
    todoAdded: todosAdapter.addOne,
    todosReceived: todosAdapter.setAll,
    todoUpdated: todosAdapter.updateOne,
    todoRemoved: todosAdapter.removeOne,
  },
});

export const { selectAll, selectById } = todosAdapter.getSelectors(
  (state) => state.todos
);
```

It maintains `{ ids: [], entities: {} }` and generates CRUD reducers and selectors. O(1) lookups, no duplicated entity copies, and sorted order maintained automatically.

## Listener middleware

The modern replacement for sagas in most cases:

```js
const listener = createListenerMiddleware();

listener.startListening({
  actionCreator: todoAdded,
  effect: async (action, api) => {
    api.cancelActiveListeners();          // debounce
    await api.delay(500);
    await api.dispatch(syncToServer(action.payload));
  },
});
```

Reactive side effects with cancellation, debouncing and access to state — without the generator learning curve of redux-saga ([[20.5 - Middleware and Thunks]]).

## How senior engineers actually use this

**They use `createSlice` for everything** and never hand-write action types.

**They use RTK Query for server data** rather than `createAsyncThunk` per endpoint. Async thunks are for client-side async logic that is not a request.

**They define typed hooks once** and ban the untyped ones via lint.

**They use `createEntityAdapter`** for any collection keyed by id.

**They keep the serializability check on**, since disabling it usually means something belongs outside the store.

## Common pitfalls

- Mutating the draft *and* returning a value from the same reducer.
- Using a draft outside the reducer, hitting a revoked proxy.
- Non-serializable values in state, silently breaking DevTools and persistence.
- `createAsyncThunk` per endpoint when RTK Query would remove all of it.
- Selectors defined inline, returning new references on every call ([[20.3 - Redux Core Concepts]]).
- Untyped `useSelector` calls scattered through the codebase.

## Interview angle

"How does Redux Toolkit simplify Redux" expects: `createSlice` generating action types, creators and reducers from one definition; Immer allowing mutation-style writes that produce immutable updates; `configureStore` setting up DevTools, thunks and development checks by default. The stronger additions are RTK Query for server state — showing you know Redux's own answer to the "don't put server data in Redux" problem — and `createEntityAdapter` for normalization.
