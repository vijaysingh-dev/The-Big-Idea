# API Gateway and BFF

#backend #microservices #architecture

> **In one line:** A gateway handles the cross-cutting concerns every service would otherwise implement, a BFF shapes responses for one specific client — and confusing the two produces a gateway full of business logic that everyone is afraid to change.

---

## The Idea

```
Clients → [ edge ] → services
```

Two distinct things get put at that edge:

| | API Gateway | BFF |
|---|---|---|
| Purpose | **Cross-cutting concerns** | **Client-specific shaping** |
| Instances | One, shared | **One per client type** |
| Owned by | Platform team | **The client team** |
| Contains | Auth, rate limiting, routing, TLS | Aggregation, response shaping |
| Business logic | **None** | Some — presentation logic |
| Changes when | Policy changes | **The client changes** |

💡 **The distinction matters because they have different change rates and different owners.** A gateway changes when security policy changes; a BFF changes every time the mobile app adds a screen.

⚠️ **Putting client-specific aggregation in a shared gateway means every client team needs changes to a component owned by the platform team**, which is a coordination bottleneck and the exact thing microservices were meant to remove.

---

## The API Gateway

```
Client → Gateway → ┬── documents-service
                   ├── search-service
                   └── billing-service
```

**What belongs here:**

| Concern | Why at the edge |
|---|---|
| **TLS termination** | One place to manage certificates ([[02.9 - TLS]]) |
| **Authentication** | Validate the token once, not in every service |
| **Rate limiting** | Global view of a client's usage ([[11.5 - Rate Limiting and Quotas]]) |
| **Routing** | Path or host to service |
| **Request/response logging** | One consistent access log |
| **CORS** | One policy ([[03.7 - Cookies Sessions and CORS]]) |
| **Request ID generation** | The root of every trace |
| **Protocol translation** | HTTP in, gRPC out ([[05.11 - REST vs GraphQL vs gRPC]]) |

⚠️ **What does not belong here:**

| Anti-pattern | Why |
|---|---|
| Business logic | Untestable, owned by nobody, feared by everyone |
| **Response aggregation** | That is a BFF concern |
| Data transformation beyond protocol | Same |
| Per-client special cases | Same |
| Anything requiring a database | The gateway should be stateless |

💡 **The test: could you replace the gateway with a different product without changing behaviour?** If the answer is no because it contains logic, you have built a monolith at the edge.

### Authentication at the edge

```python
# Gateway validates once
claims = verify_jwt(request.headers["authorization"])
request.headers["x-user-id"] = claims["sub"]
request.headers["x-org-id"] = claims["org"]
```

```python
# Services trust the headers — ⚠️ only if they cannot be reached directly
user_id = request.headers["x-user-id"]
```

⚠️ **This only works if services are unreachable from outside the gateway.** A service that trusts `x-user-id` and is reachable on the network is an authentication bypass.

| Defence | |
|---|---|
| Network policy — services only accept traffic from the gateway | |
| **mTLS** — services verify the caller is the gateway ([[02.9 - TLS]]) |
| **Forward the original token** — services validate it themselves | Defence in depth |

💡 **Forwarding the token and having services validate it is the safer pattern**, and the validation cost is small if you cache the JWKS. **Header-trust is faster and it is one misconfigured network policy away from a breach.**

⚠️ **Authorisation is different from authentication.** The gateway can establish *who* you are; it should not decide *what you may do*, because that requires domain knowledge the gateway does not have.

**Authenticate at the edge, authorise in the service.**

## The BFF

```
Web app     → web-bff     → services
Mobile app  → mobile-bff  → services
Partner API → partner-bff → services
```

💡 **Each client has genuinely different needs**, and a single API serving all of them either over-fetches for mobile or under-serves the web.

```python
# mobile-bff: minimal payload, aggressive aggregation
@app.get("/home")
async def home(user: User):
    async with asyncio.TaskGroup() as tg:
        docs = tg.create_task(documents.recent(user.org_id, limit=10))
        counts = tg.create_task(analytics.summary(user.org_id))
        notifs = tg.create_task(notifications.unread(user.id))

    return {
        "documents": [{"id": d.id, "title": d.title[:60]} for d in docs.result()],
        "unread": len(notifs.result()),
        "total": counts.result()["total"],
    }
```

**One request, one round trip, exactly the fields the home screen renders.**

| Benefit | |
|---|---|
| **One network round trip** | Matters enormously on mobile |
| **Payload sized for the client** | No over-fetching |
| **Owned by the client team** | They change it when their screen changes |
| **Client-specific versioning** | The mobile app can lag without holding back web |

⚠️ **The cost is duplication between BFFs.** Three BFFs calling the same three services means three copies of the aggregation logic.

💡 **That duplication is usually acceptable and occasionally not.** When three BFFs share substantial logic, extract it into a library — **not into a shared BFF**, which recreates the coordination problem.

### GraphQL as a BFF

```graphql
query MobileHome {
  recentDocuments(first: 10) { id title }
  unreadCount
  usageSummary { total }
}
```

💡 **GraphQL is a BFF that the client configures itself**, which removes the need for a BFF per client — each client asks for what it needs ([[05.4 - GraphQL - The Core Model]]).

⚠️ **The tradeoffs come with it**: no HTTP caching, unbounded query cost, and harder observability ([[05.7 - GraphQL Caching]], [[05.8 - GraphQL Security and Limits]]).

**GraphQL replaces the BFF pattern when client diversity is the driver.** If you have one web client, a plain BFF is simpler.

## The Gateway as a Single Point of Failure

⚠️ **Every request passes through it.** If it is down, everything is down.

| Mitigation | |
|---|---|
| Multiple replicas behind a load balancer | Table stakes |
| **Stateless** | So any replica can serve any request |
| Health checks that reflect real capability | ([[03.10 - Proxies and Load Balancers]]) |
| **No shared mutable state** | Rate limit counters in Redis, not memory |
| Aggressive resource limits | So one bad request cannot exhaust it |

💡 **The gateway must be the most boring, most stable component in your system.** Every feature added to it increases the blast radius of a bug.

⚠️ **A gateway that requires a deploy every time a service changes has become coupled to those services**, and it is now a deployment bottleneck. **Routing should be configuration, not code.**

### The latency tax

```
Client → Gateway → BFF → Service
         +2ms      +2ms   +work
```

⚠️ **Each hop adds latency and a failure point.** A gateway plus a BFF plus a service is three network hops before any work happens.

💡 **Collapse them where you can.** For many systems, **the BFF *is* the gateway** — one component doing auth, rate limiting and aggregation — and that is fine when one team owns both concerns.

**Separate them when the ownership genuinely differs.**

## What the Gateway Must Do Right

### Timeout budget propagation

```python
budget = min(client_timeout, MAX_BUDGET)
headers["x-request-timeout-ms"] = str(int(budget * 1000))
```

💡 **The gateway is where the request budget originates** ([[03.11 - Timeouts and Deadlines Across Hops]]). Every downstream hop should receive a shrinking remaining budget.

### Request ID and trace context

```python
request_id = request.headers.get("x-request-id") or f"req_{ulid()}"
with tracer.start_as_current_span("gateway", attributes={"request_id": request_id}):
    ...
```

⚠️ **If the gateway does not start the trace, nothing downstream can be correlated** ([[12.3 - Instrumenting Conduit End to End]]).

**Return the request ID to the client** so a support ticket contains it.

### Load shedding

```python
if in_flight > MAX_CONCURRENT:
    return Response(503, headers={"Retry-After": "1"})
```

💡 **The gateway is the right place to shed load**, because it is the only component with a global view of incoming traffic ([[11.4 - Backpressure and Load Shedding]]).

⚠️ **Shed selectively.** Health checks never, authenticated traffic before anonymous, and cheap rejections before expensive ones.

### Not becoming a bottleneck

```python
# ❌ A database call per request in the gateway
user = await db.fetch("SELECT * FROM users WHERE token = $1", token)

# ✅ Stateless validation
claims = jwt.decode(token, key=cached_jwks, algorithms=["RS256"])
```

⚠️ **A gateway that queries a database on every request has made that database the bottleneck for your entire system**, and the failure mode is total.

**Everything the gateway needs should be in the request, in memory, or in a cache it can degrade without.**

## In Production

### The layering

```
Load balancer      L4/L7, TLS, health checks    ([[03.10 - Proxies and Load Balancers]])
  Gateway          auth, rate limit, routing, tracing
    BFF            aggregation, client shaping
      Services     business logic
```

⚠️ **Four layers is a lot.** Each is justified only if it does something the others cannot.

💡 **A common and correct simplification for a smaller system:**

```
Load balancer → BFF/Gateway (one component) → Services
```

**Two hops instead of four.** Split them later when ownership diverges.

### Choosing an implementation

| Option | |
|---|---|
| **Envoy** | Dynamic config via API. What service meshes use |
| **Kong / Traefik** | Plugin ecosystems, easier configuration |
| **nginx** | Ubiquitous, fast, configuration is idiosyncratic |
| **Cloud gateways** | Managed, integrated, less flexible |
| **Your own** | FastAPI as a BFF. **Right when it is a BFF, not a gateway** |

💡 **Do not write your own API gateway.** Auth, rate limiting, TLS and routing are solved, and a hand-written gateway becomes a maintenance burden that is on the critical path for every request.

**Do write your own BFF.** Aggregation logic is your business logic, and it belongs in code you own.

### Monitoring

```python
gateway_requests_total.labels(route=r, status=s, upstream=u).inc()
gateway_duration_seconds.labels(route=r).observe(elapsed)
gateway_upstream_duration_seconds.labels(upstream=u).observe(elapsed)
gateway_auth_failures_total.labels(reason=...).inc()
gateway_rate_limited_total.labels(client=c).inc()
gateway_shed_total.inc()
```

💡 **The gap between `gateway_duration` and `gateway_upstream_duration` is the gateway's own overhead.** If it grows, the gateway is doing too much.

⚠️ **Label by route, not by path**, or a path with an ID in it produces unbounded cardinality — `/documents/doc_42` becomes a distinct label value per document.

### The gateway failure modes

| Symptom | Cause |
|---|---|
| Everything is slow | Gateway CPU or connection pool saturated |
| Some routes 502 | An upstream is down and the gateway is not degrading |
| Auth failures spike | JWKS cache stale, or a key rotated |
| Latency added but upstreams are fast | The gateway is doing too much work |
| One client degrades everyone | Rate limiting missing or misconfigured |

💡 **"Latency added but upstreams are fast" is the signal that the gateway has accumulated logic**, and it is the point at which you move that logic into a BFF or a service.

### Conduit's edge

```
Browser ──HTTPS──► Load balancer ──► Gateway/BFF ──gRPC──► Services
                                     (one component)
```

| Concern | Where |
|---|---|
| TLS | Load balancer |
| Authentication | Gateway — validates the JWT, forwards it |
| **Authorisation** | **Services** — they own the domain rules |
| Rate limiting | Gateway, per organisation, backed by Redis |
| Routing | Gateway, configuration-driven |
| **GraphQL aggregation** | Gateway — it is the BFF |
| Request ID and tracing | Gateway |
| Load shedding | Gateway |

💡 **One component doing both jobs, because one team owns both.** The ADR should say that, and name the trigger for splitting: **a second client type with genuinely different aggregation needs, or a platform team taking ownership of the cross-cutting concerns.**

⚠️ **The token is forwarded, not just the claims**, so services validate independently. **The extra validation cost is worth not depending on network policy for security.**


**Part 1 — No gateway.** Three clients calling four services directly.

**Implement auth, rate limiting, CORS, request IDs and tracing in every service.** Count the duplication.

Then change the auth mechanism. **Count the services you had to touch.**

**Part 2 — Add a gateway.** Move all five concerns to the edge. Routing as configuration, not code.

**Re-run the auth change.** It should touch one component.

Then add a fifth service. **Confirm it requires only a configuration change**, not a gateway deploy.

**Part 3 — The header-trust bypass.** Gateway sets `x-user-id`; services trust it.

**Call a service directly, bypassing the gateway, with a forged header.** Confirm you can act as any user.

Then implement three defences — network policy, mTLS, and token forwarding with in-service validation — and confirm each blocks it.

**Measure the latency cost of token validation in every service**, and decide whether it is worth it. **Cache the JWKS and measure again.**

**Part 4 — Three BFFs.** The same home screen for web, mobile and a partner API.

Measure for each: payload size, round trips, and fields fetched but unused.

**Then implement it once in GraphQL** and compare. **Measure how much BFF code GraphQL eliminated**, and what it cost in caching and cost-limiting work.

**Part 5 — The latency tax.** The same operation through 1, 2, 3 and 4 layers.

Chart p50 and p99 for each. **Compute the overhead per layer.**

Then measure the same under load, where connection pool contention at each layer compounds.

**Part 6 — Failure modes.**

- **Gateway down:** confirm everything fails, and measure recovery time with multiple replicas
- **One upstream down:** confirm the gateway degrades that route rather than failing all of them
- **A slow upstream:** confirm it does not exhaust the gateway's connection pool ([[11.3 - Circuit Breakers and Bulkheads]])
- **JWKS unreachable:** confirm cached keys keep auth working, and measure how long

**Part 7 — The anti-pattern.** Put business logic in the gateway: a discount calculation, a permission rule, and a data transformation.

**Then try to unit test it.** Measure the setup required.

**Then change a service's response shape** and count what broke in the gateway.

Then move the logic out and re-measure both.

**Part 8 — The ADR.** Conduit's edge: one component or two, and why.

**Cite your latency-per-layer number and your BFF duplication count.** Name the trigger for splitting the gateway from the BFF.

**Done when:**
- You quantified the duplication of running without a gateway
- Adding a service required only a configuration change
- You bypassed header-trust auth and blocked it three ways
- Your BFF comparison includes what GraphQL eliminated and what it cost
- Your latency-per-layer chart shows the overhead of each hop
- A slow upstream does not degrade unrelated routes
- Logic in the gateway is demonstrably harder to test and more brittle
- The ADR cites your own numbers and names its split trigger
