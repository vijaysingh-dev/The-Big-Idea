# CI/CD Pipelines

#backend #operations #delivery

> **In one line:** A pipeline's job is to give a fast, trustworthy verdict on a change and then deliver it safely — and the two properties that matter most are speed and the absence of flakiness.

---

## The Idea

```
commit → lint → test → build → scan → deploy staging → verify → deploy prod
```

⚠️ **Two failure modes kill a pipeline's value, and both are cultural before they are technical:**

**Too slow.** A 40-minute pipeline means developers batch changes, which makes each deploy riskier and harder to diagnose ([[10.10 - Deployment Strategies]]).

**Flaky.** A suite that fails randomly trains the team to re-run rather than investigate — **and then the first genuine failure gets re-run too** ([[10.9 - Testing Microservices]]).

💡 **The target: under 10 minutes from push to a verdict, with a flakiness rate of zero.** Everything else is secondary.

---

## Stage Design

```yaml
# Fast feedback first
- lint + type check          30s    (parallel)
- unit tests                 60s    (parallel)
- integration tests         180s
- contract tests             40s
- build image               120s
- security scan              60s
- deploy staging + smoke    180s
```

💡 **Order by speed × probability of failure.** A lint error should fail in 30 seconds, not after eight minutes of tests.

⚠️ **Nothing in the per-commit path should require another service to be running.** That is what contract tests buy you ([[05.13 - Contract Testing and Schema Evolution]]) — **and it is what keeps the pipeline fast and non-flaky.**

### Parallelism

```yaml
jobs:
  lint: {runs-on: ubuntu-latest, steps: [...]}
  types: {runs-on: ubuntu-latest, steps: [...]}
  unit: {runs-on: ubuntu-latest, steps: [...]}
  integration:
    strategy:
      matrix: {shard: [1, 2, 3, 4]}
    steps:
      - run: pytest --shard-id=${{ matrix.shard }} --num-shards=4
```

💡 **Sharding a slow integration suite across four runners cuts wall-clock time by roughly four**, and it costs only runner minutes — usually a good trade against developer waiting time.

⚠️ **Shard by measured duration, not by file count.** Splitting alphabetically means one shard gets all the slow tests.

## Caching

⚠️ **CI runners start empty every time.** Without caching, every build is a cold build.

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.cache/uv
    key: uv-${{ hashFiles('requirements.txt') }}
    restore-keys: uv-
```

```yaml
- uses: docker/build-push-action@v6
  with:
    cache-from: type=registry,ref=ghcr.io/org/app:buildcache
    cache-to: type=registry,ref=ghcr.io/org/app:buildcache,mode=max
```

💡 **Registry-backed Docker layer caching is often the single largest pipeline speedup available** ([[13.2 - Production Dockerfiles]]).

⚠️ **`restore-keys` matters.** Without a prefix fallback, a one-line dependency change means a complete cache miss.

### Test containers

```python
@pytest.fixture(scope="session")
def postgres():
    with PostgresContainer("postgres:17") as pg:
        yield pg.get_connection_url()
```

⚠️ **Session-scoped, not function-scoped.** Starting a Postgres container per test turns a 3-minute suite into 30 minutes.

💡 **Reuse the container and reset state between tests instead** — truncate tables, or use a transaction rolled back per test.

## Flakiness

⚠️ **A flaky test is worse than no test.** It provides no signal and it destroys trust in the ones that work.

| Cause | Fix |
|---|---|
| **Shared state between tests** | **A per-test tenant** ([[06.16 - Multi Tenant Data Models]]) |
| `sleep`-based assertions | Poll for the condition with a timeout |
| Wall-clock dependence | Inject time |
| **Test order dependence** | Randomise order in CI to expose it |
| Real network calls | Stub them |
| Port collisions | Ephemeral ports |
| Unseeded randomness | Seed it, and log the seed |

```bash
pytest -p no:randomly --randomly-seed=last     # reproduce a failure
pytest --randomly-seed=12345                    # in CI, log the seed
```

💡 **Randomising test order in CI is the cheapest way to expose order dependence**, and it finds real bugs.

### Quarantine, do not retry

```yaml
- run: pytest --reruns 3        # ⚠️ hides the problem
```

⚠️ **Automatic retries make flaky tests invisible and permanent.**

💡 **Better: track per-test flake rate, quarantine anything above a threshold into a separate non-blocking job, and fix or delete it within a sprint.**

```python
test_result_total.labels(test=..., result=..., attempt=...).inc()
```

**Measure it.** A team that cannot state its flakiness rate has one.

## Deployment

### Environments

```
PR preview     ephemeral, per pull request
staging        production-shaped, production-scale data
production     progressive rollout
```

💡 **Ephemeral preview environments are the practical alternative to a shared staging environment**, which is always broken by someone else's deploy ([[10.9 - Testing Microservices]]).

⚠️ **Staging with 10,000 rows tells you nothing about production with 10 million** ([[06.4 - Reading EXPLAIN ANALYZE]]). **Seed it realistically or do not trust its performance results.**

### Migrations run separately

```yaml
- name: Run migrations
  run: kubectl apply -f migration-job.yaml && kubectl wait --for=condition=complete job/migrate

- name: Deploy
  run: kubectl set image deployment/documents app=$IMAGE
```

⚠️ **Never run migrations on application startup.** N pods race to run the same migration, most block on an advisory lock, readiness probes may trip, and a migration failure becomes a deploy failure ([[06.11 - Zero Downtime Migrations]]).

💡 **Separating them also lets you run a long backfill without deploying** — which you will need.

### The deploy verdict

```yaml
- name: Verify
  run: |
    kubectl rollout status deployment/documents --timeout=300s
    ./scripts/smoke-test.sh
    ./scripts/check-error-rate.sh --threshold 0.01 --window 300
```

⚠️ **`kubectl rollout status` only confirms the pods are Ready.** It says nothing about whether they are working correctly.

💡 **A deploy is not successful until the error rate is normal.** Automated verification against the SLO metrics, with automatic rollback, is what turns a deploy from a hope into a checked operation ([[12.2 - SLI SLO and Error Budgets]]).

## GitOps

```
Git repo (manifests) ──watched by──> Argo CD / Flux ──applies──> cluster
```

| Advantage | |
|---|---|
| **Git is the source of truth** | The cluster state is auditable and reviewable |
| **Drift detection** | Manual `kubectl edit` is reverted or flagged |
| Rollback is a revert | |
| **CI does not need cluster credentials** | A meaningful security improvement |

⚠️ **The last point is the strongest argument.** In a push-based pipeline, your CI system holds credentials that can deploy anything to production — **and CI is a frequent target because it runs untrusted code from pull requests.**

💡 **With GitOps, CI writes to a git repository and the cluster pulls.** The blast radius of a compromised CI runner shrinks considerably.

⚠️ **The cost is indirection.** "Why is this version running" now requires checking the manifest repo, the sync status and the controller logs. **Worth it above a handful of services; overhead below that.**

## In Production

### Supply chain

⚠️ **Your pipeline runs code from your dependencies, on a machine with credentials.**

```yaml
permissions:
  contents: read
  id-token: write          # OIDC, no long-lived secrets
```

| Practice | |
|---|---|
| **Pin actions by SHA** | `uses: actions/checkout@8f4b7f8...` — a tag can be moved |
| **Minimal `permissions`** | Default to read-only, grant per job |
| **OIDC instead of stored credentials** | No long-lived cloud keys in CI |
| **Never run untrusted PR code with secrets** | `pull_request_target` is dangerous |
| Sign images | Cosign, and verify at admission |
| Generate an SBOM | ([[13.2 - Production Dockerfiles]]) |

⚠️ **`pull_request_target` runs with repository secrets and checks out the PR's code by default.** A fork can exfiltrate every secret you have. **If you use it, do not check out the PR head.**

### Secrets in the pipeline

```yaml
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123:role/deploy
    aws-region: eu-west-1
```

💡 **OIDC federation removes long-lived credentials from CI entirely** — the runner exchanges a short-lived identity token for temporary cloud credentials ([[10.8 - Configuration and Secrets]]).

**Add secret scanning on every commit and in pre-commit:**

```yaml
- run: gitleaks detect --source . --redact
```

### Measuring the pipeline

```python
pipeline_duration_seconds.labels(stage=...).observe(elapsed)
pipeline_result_total.labels(result=...).inc()
test_flake_rate.labels(test=...).set(rate)
deployment_frequency.inc()
lead_time_seconds.observe(merge_to_production)
change_failure_rate.set(ratio)
time_to_restore_seconds.observe(elapsed)
```

💡 **The last four are the DORA metrics**, and they are the best available summary of delivery health.

| Metric | Elite |
|---|---|
| Deployment frequency | On demand, multiple per day |
| Lead time (commit → production) | < 1 hour |
| Change failure rate | 0–15% |
| Time to restore | < 1 hour |

⚠️ **Deployment frequency and change failure rate correlate positively, not negatively.** Teams deploying more often have *fewer* failures per deploy, because each change is smaller.

**The instinct to deploy less often after an incident makes the next incident harder to diagnose.**

### The pipeline audit

```
□  Under 10 minutes to a verdict
□  Flakiness rate zero, and measured
□  Fastest checks first
□  Dependency and Docker layer caching
□  Test order randomised
□  No stage requires another service running
□  Migrations run as a separate job before deploy
□  Deploy verified against error rate, with automatic rollback
□  Actions pinned by SHA
□  Minimal permissions; OIDC not stored credentials
□  Secret scanning
□  SBOM and image signing
□  DORA metrics tracked
```

### Conduit's pipeline

```
On PR:
  lint + types              parallel   30s
  unit                      parallel   45s
  integration (4 shards)    parallel  120s
  contract                             40s
  migration lint                       10s
  schema compatibility                 15s
  build + scan                        150s
  preview environment + smoke         180s
                                     ─────
                            wall clock ~6 min

On merge to main:
  the above, then:
  migration job → wait
  deploy staging → smoke → error rate check
  deploy production (rolling) → rollout status → error rate check
  auto-rollback if error rate > 1% for 5 minutes
```

💡 **The migration lint and schema compatibility checks are Conduit-specific and they earn their 25 seconds** — they catch the two classes of change most likely to cause an outage ([[06.11 - Zero Downtime Migrations]], [[05.13 - Contract Testing and Schema Evolution]]).

⚠️ **The auto-rollback on error rate is what makes frequent deploys safe.** Without it, a bad deploy at 6pm on a Friday is discovered by users.

## Codebase

**Repo:** `argoproj/argo-cd`, `sigstore/cosign`, well-run open-source pipelines

**Question to answer:** How does Argo CD detect drift between the desired state in git and the live cluster, and what does it do about it? Then: how does image signing and verification at admission actually work?

**Read, in order:**

1. `argo-cd/controller/appcontroller.go` — **the reconciliation loop.** How it compares desired and live state and computes a diff
2. `argo-cd/util/argo/diff/` — **the normalisation logic.** Why comparing Kubernetes objects is harder than it sounds: defaulted fields, mutating webhooks, and managed fields
3. `sigstore/cosign` — the sign and verify flow, and **keyless signing via OIDC.** Read the README on keyless first; it removes key management entirely
4. `sigstore/policy-controller` — **admission-time verification.** How a cluster refuses to run an unsigned image
5. **A well-run project's workflows** — Sentry's, Home Assistant's, or Kubernetes' own `.github/workflows`. **Note the caching, sharding and permission scoping**

💡 The Argo CD diff normalisation is the unglamorous, genuinely hard part. **A Kubernetes object you applied is not the object stored** — defaults are filled in, webhooks mutate it, controllers add fields. **Deciding "has this drifted" requires knowing which differences to ignore**, and that code is where GitOps tools earn their keep.

**Size:** 1 session.

## Exercise

**Drill 13.5 — From 40 minutes to 6**

```
drills/13-cicd/
├── baseline/{workflow.yml, MEASURE.md}
├── speed/{parallel.yml, sharding.py, caching.yml, RESULTS.md}
├── flakiness/{detect.py, quarantine.py, order_random.py, RESULTS.md}
├── deploy/{migration_job.yaml, verify.sh, rollback.sh, RESULTS.md}
├── security/{permissions.yml, oidc.yml, pr_target_attack.md, cosign.sh}
├── gitops/{argocd/, drift_test.sh}
├── metrics/{dora.py, dashboard.json}
└── audit.md
```

**Part 1 — Build a slow pipeline, then measure it.** Sequential stages, no caching, no sharding, function-scoped test containers.

**Measure: total wall-clock time, time per stage, and time from push to first failure signal for a lint error.**

**Part 2 — Optimise, one change at a time.** Measure after each:

| Change | Expected |
|---|---|
| Parallelise independent jobs | Large |
| Session-scoped containers | Large |
| Dependency caching | Moderate |
| Docker registry layer caching | **Large** |
| Shard integration tests ×4 | Large |
| Reorder fastest-first | Time to first failure signal drops sharply |

**Build the table. Target: under 10 minutes total, under 60 seconds to a lint failure.**

**Part 3 — Find and fix flakiness.** Write three flaky tests: shared state with order dependence, `sleep`-based timing, and wall-clock dependence.

**Run the suite 100 times and count failures per test.**

Then enable random test ordering and **confirm it exposes the order dependence deterministically.**

Then fix all three and re-run 100 times. **Report the rate before and after.**

Then implement flake tracking and quarantine, **and confirm a newly-introduced flaky test is quarantined automatically rather than blocking.**

**Part 4 — Migrations and verification.** A migration job that runs before the deploy and blocks it on failure.

**Test three cases:** a successful migration, a failing migration (deploy must not proceed), and a migration that succeeds but whose deploy is bad.

**For the third, confirm your error-rate check catches it and automatic rollback fires.** Measure time from deploy to rollback complete.

**Part 5 — The `pull_request_target` attack.** In a throwaway repository, configure a workflow using `pull_request_target` that checks out the PR head and has access to a dummy secret.

**From a fork, demonstrate exfiltrating the secret.**

⚠️ **Throwaway repository, dummy secret, delete afterwards.**

**Then fix it** and confirm the attack fails. **Then audit your real workflows for the same pattern.**

**Part 6 — Supply chain hardening.** Pin every action by SHA, scope `permissions` per job, replace stored cloud credentials with OIDC, add secret scanning, and sign images with cosign.

**Then configure admission-time verification and confirm an unsigned image is refused.**

**Part 7 — GitOps.** Deploy Conduit with Argo CD.

**Then manually `kubectl edit` a Deployment and confirm drift is detected and reverted.**

Compare push-based and pull-based on: what credentials CI holds, time from merge to running, rollback procedure, and how you answer "what version is running".

**Part 8 — DORA metrics.** Instrument all four over 20 simulated changes including two failures.

**Then deliberately batch changes** — deploy weekly instead of per-merge — for another 20 changes.

**Compare change failure rate and time to restore between the two modes.** The batched version should be worse on both, and having your own numbers makes that argument concrete.

**Done when:**
- Your pipeline went from the baseline to under 10 minutes, with per-change measurements
- Time to a lint failure is under 60 seconds
- Flakiness rate is zero across 100 runs, with quarantine automated
- A failing migration blocks the deploy and a bad deploy auto-rolls back
- You exfiltrated a secret via `pull_request_target` and then prevented it
- An unsigned image is refused at admission
- Argo CD reverts a manual cluster edit
- Your DORA numbers show batched deploys performing worse
