# Stampede, Hot Keys and Negative Caching

#backend #caching #reliability

> **In one line:** Three failure modes that only appear at scale — everyone missing the same key at once, everyone hitting the same key at once, and everyone asking for a key that does not exist.

---

## Cache Stampede

Also called dogpiling, or thundering herd.

```
t=0.000   Cache key expires
t=0.001   1,000 concurrent requests all miss
t=0.002   1,000 identical database queries
```

⚠️ **This is worse than having no cache at all**, because with no cache the load would have been steady. **With a cache, load is near zero and then briefly 1,000× — and your database is sized for the steady state.**

💡 **The characteristic signature is periodic latency spikes at exactly your TTL interval.** If your p99 spikes every 300 seconds and your TTL is 300 seconds, you have found it.

### Fix 1: Single-flight lock

```python
async def get_with_lock(key: str, loader, ttl: int = 300):
    if cached := await redis.get(key):
        return deserialise(cached)

    if await redis.set(f"lock:{key}", "1", nx=True, ex=10):
        try:
            value = await loader()
            await redis.setex(key, ttl, serialise(value))
            return value
        finally:
            await redis.delete(f"lock:{key}")

    for _ in range(50):                        # wait briefly for the other loader
        await asyncio.sleep(0.02)
        if cached := await redis.get(key):
            return deserialise(cached)

    return await loader()                      # give up waiting, load it ourselves
```

⚠️ **The `ex=10` on the lock is not optional.** Without it, a crash while holding the lock means every subsequent request waits forever ([[07.4 - Distributed Locks Done Right]]).

**The fallback after the wait loop matters too** — waiting indefinitely converts a load spike into a latency spike, which is not obviously better.

### Fix 2: Probabilistic early expiry

The most elegant fix, and it needs no coordination at all.

```python
entry = deserialise(raw)
now = time.time()

# XFetch: probability of early refresh rises as expiry approaches
if now - entry.delta * beta * math.log(random.random()) >= entry.expiry:
    return await load_and_cache(key, loader, ttl)

return entry.value
```

Where `delta` is how long the last regeneration took. **An expensive value gets refreshed earlier and more eagerly than a cheap one.**

💡 **This is the XFetch algorithm, and it is genuinely clever: each reader independently decides whether to refresh, with probability rising as expiry approaches.** Statistically, exactly one refreshes early — **no lock, no coordination, no waiting.**

⚠️ It only helps for keys with steady traffic. A key read once every ten minutes gets no benefit.

### Fix 3: Serve stale while revalidating

```python
entry = deserialise(raw)
if entry.is_fresh():
    return entry.value

if await redis.set(f"refresh:{key}", "1", nx=True, ex=30):
    spawn(load_and_cache(key, loader, ttl + stale))

return entry.value          # stale, and immediate
```

**Nobody ever waits.** The value stays in Redis past its logical freshness, and one background task refreshes it.

💡 **This is the same mechanism as HTTP's `stale-while-revalidate`** ([[03.5 - HTTP Caching]]) and **the best general answer when serving slightly stale data is acceptable.**

**Store two timestamps** — logical expiry and hard expiry — so you can distinguish "stale but usable" from "gone".

### Fix 4: Never expire, refresh externally

```python
async def refresh_loop():
    while True:
        for key in hot_keys():
            await redis.set(key, serialise(await load(key)))   # no TTL
        await asyncio.sleep(60)
```

⚠️ **If the refresher dies, the cache silently serves ever-staler data forever.** Add a heartbeat and alert on refresher staleness, **or use a long TTL as a backstop so failure is visible.**

**Right for a small set of very hot, expensive keys** — a homepage feed, a global configuration blob.

## Hot Keys

A different problem: not everyone missing, but everyone hitting.

```
Key: "config:global"    →  50,000 requests/second, all to one Redis key
```

⚠️ **Redis is single-threaded per shard.** A single hot key means a single CPU core serves all of that traffic, regardless of how many nodes you have. **In Redis Cluster it is worse — the whole slot lives on one node, and you cannot rebalance a single key.**

### The signature

```bash
redis-cli --hotkeys                    # requires an LFU eviction policy
redis-cli monitor | head -10000 | awk '{print $4}' | sort | uniq -c | sort -rn
```

**Uneven CPU across cluster nodes with even key counts is the giveaway.**

### Fix 1: Local caching in front of Redis

```python
_local = TTLCache(maxsize=1000, ttl=5)

async def get_hot(key: str):
    if key in _local:
        return _local[key]
    value = await redis.get(key)
    _local[key] = value
    return value
```

💡 **A 5-second local TTL turns 50,000 Redis requests per second into 40 pods × 0.2 requests per second.** For a value that changes rarely, **this is the single most effective fix and it costs almost nothing.**

The trade is per-pod staleness ([[07.1 - Cache Layers Across One Request]]) — pair it with pub/sub invalidation if 5 seconds is too long.

### Fix 2: Key splitting

```python
async def get_split(base_key: str, replicas: int = 16):
    return await redis.get(f"{base_key}:{random.randint(0, replicas - 1)}")
```

Sixteen copies spread across sixteen slots, so sixteen cluster nodes share the load.

⚠️ **Writes now cost 16×, and the copies can diverge briefly during an update.** Only worth it for read-dominated keys where the local-cache fix is insufficient.

### Fix 3: Read replicas

Spreads read load. **Adds replication lag**, so a value written and immediately read may be missing.

## Negative Caching

```python
doc = await repo.get(doc_id)
if doc is None:
    return None          # ← nothing cached, so the next identical request queries again
```

⚠️ **A key that does not exist is queried every single time.** An attacker requesting random IDs bypasses your cache entirely and hits the database at full rate. **This is a cache-penetration attack and it is trivially executable.**

```python
NULL_SENTINEL = b"\x00__none__"

raw = await redis.get(f"doc:{doc_id}")
if raw == NULL_SENTINEL:
    return None                        # cached absence
if raw:
    return Document.model_validate_json(raw)

doc = await repo.get(doc_id)
if doc is None:
    await redis.setex(f"doc:{doc_id}", 30, NULL_SENTINEL)
    return None
await redis.setex(f"doc:{doc_id}", 300, doc.model_dump_json())
return doc
```

💡 **Use a shorter TTL for negatives than positives** — typically 30 seconds against 300. A newly-created entity becomes visible quickly, while a scan of random IDs is still absorbed.

⚠️ **The sentinel must be distinguishable from a legitimate cached value.** An empty string or `"null"` can collide with real data; a byte sequence that cannot appear in your serialisation format cannot.

### Bloom filters for large key spaces

```python
if not await bloom.might_contain(doc_id):
    return None                            # definitely does not exist, zero queries
```

A bloom filter answers "definitely not present" or "possibly present". **False positives fall through to the normal path; false negatives cannot happen.**

```
10 million IDs at 1% false positive rate ≈ 12 MB
```

💡 **`BF.EXISTS` in RedisBloom makes this a one-line check**, and it is the right answer when your key space is too large to cache every negative.

⚠️ **Deletions are the weakness** — a standard bloom filter cannot remove items. **Rebuild it periodically**, or use a cuckoo filter if deletions matter.

## In Production

### The three together

They compound. **A hot key that expires produces a stampede; a stampede on a key that does not exist produces penetration.**

```python
class ResilientCache:
    async def get(self, key: str, loader, ttl: int = 300, negative_ttl: int = 30):
        if key in self.local:                                   # hot key defence
            return self.local[key]

        raw = await self.redis.get(key)
        if raw == NULL_SENTINEL:
            return None
        if raw is not None:
            entry = deserialise(raw)
            if entry.is_fresh() or not await self._claim_refresh(key):
                self.local[key] = entry.value                   # stale-while-revalidate
                return entry.value
            spawn(self._reload(key, loader, ttl))
            return entry.value

        return await self._load_with_lock(key, loader, ttl, negative_ttl)
```

💡 **Build this once as a shared utility.** Every one of these defences is easy to forget in an ad-hoc cache call, **and a single well-tested wrapper means every caller gets all of them.**

### Cold start after a deploy

⚠️ **A rolling deploy empties every in-process cache and can empty Redis if it restarts too.**

```
Steady state:   95% hit ratio, 120 database queries/second
After deploy:   0% hit ratio, 2,400 database queries/second
```

**Every stampede defence fires simultaneously, and if your database cannot take the cold-start load, the deploy itself is an outage.**

| Mitigation | |
|---|---|
| **Warm in the readiness probe** | A pod does not take traffic until its cache is populated |
| Stagger the rollout | Longer deploys, smaller spikes |
| Persist Redis across restarts | RDB or AOF, so only local caches go cold |
| Load shed on database pressure | Fail fast rather than pile up ([[11.4 - Backpressure and Load Shedding]]) |

**Test the cold start.** Flush Redis under production-level load and see whether you survive.

### Detecting each one

| Problem | Signal |
|---|---|
| **Stampede** | Periodic latency spikes at TTL intervals; database QPS spikes with flat request rate |
| **Hot key** | Uneven Redis node CPU; one key dominating in `--hotkeys` |
| **Penetration** | High miss ratio with low hit ratio and high database load; many distinct keys queried once |

```python
cache_stampede_prevented_total.inc()        # lock acquired
cache_stale_served_total.inc()
cache_negative_hits_total.inc()
cache_penetration_suspected_total.inc()     # miss on a never-seen key
```

💡 **`cache_stale_served_total` rising sharply means your loader is failing or slow**, since values are staying past freshness. **An early warning that precedes user-visible errors.**

### The rate limiting connection

```python
if miss_rate_for_client(client_id) > 0.9 and requests > 100:
    raise HTTPException(429)
```

⚠️ **A client with a 100% cache miss rate over many requests is either broken or hostile.** Legitimate traffic has locality; enumeration does not. **A useful signal that is cheap to compute** ([[11.5 - Rate Limiting and Quotas]]).

## Codebase

**Repo:** `redis/redis`, `golang/groupcache`, `sqlalchemy/dogpile.cache`

**Question to answer:** How does groupcache guarantee that only one process in a cluster loads a given key, and what does it do about hot keys? Then: in Redis, why does a single hot key limit throughput even in a cluster?

**Read, in order:**

1. `golang/groupcache/singleflight/singleflight.go` — **the whole file is about 60 lines** and it is the canonical single-flight implementation. Read it first
2. `golang/groupcache/groupcache.go` — **`load` and the peer selection.** Note the `hotCache`: **groupcache automatically caches frequently-requested keys locally even when another peer owns them.** A genuinely good design
3. `dogpile.cache/dogpile/lock.py` — the stale-while-revalidate lock in Python
4. `redis/src/cluster.c` — slot assignment. **A key hashes to exactly one slot, and a slot lives on exactly one node** — there is no mechanism to split a single key
5. `RedisBloom/src/rebloom.c` — bloom filter implementation, for the penetration defence

💡 groupcache's `hotCache` is the idea worth stealing: **it measures which keys are requested most and automatically promotes them to a local cache, without the application asking.** Most cache libraries make you decide statically which keys are hot; **groupcache learns it, and that is a better design and not hard to implement.**

**Size:** 1 session.
