## What a Message Queue Is

A message queue is a component that accepts messages from producers, stores them durably, and delivers them to consumers — decoupling the two sides in time and rate.

```
[Producer] ──message──→ [Queue] ──message──→ [Consumer]
(sends and forgets)     (stores)             (processes at its own pace)
```

The producer doesn't wait for the consumer. The queue absorbs the difference in speed.

---

## Why It Exists

- **Decoupling:** Producer and consumer don't need to be running simultaneously
- **Load leveling:** Queue absorbs traffic spikes — consumers process at a steady rate even when producers burst
- **Reliability:** Messages are stored durably; if consumer crashes, the message is not lost
- **Retry:** Failed messages can be retried without the producer knowing
- **Fan-out:** One message can be consumed by multiple consumers (topic-based)

## Traditional Message Queue (RabbitMQ / SQS style)

### How It Works

```
Producer → Queue → Consumer A
                 → Consumer B  (competing consumers — only one gets each message)
```

- Each message is delivered to **one consumer** (work queue / competing consumers model)
- Consumer **acknowledges** the message after processing
- If consumer crashes without ACK, message is requeued and redelivered
- Message is deleted after ACK

### Delivery Semantics

- **At-most-once:** Message delivered once; may be lost if consumer crashes before processing. Fast but unreliable.
- **At-least-once:** Message redelivered until ACK. Consumer may process it more than once. Requires idempotent consumers.
- **Exactly-once:** Each message processed exactly once. Expensive to guarantee; requires distributed transactions or idempotency + deduplication at consumer.

Most production queues offer **at-least-once**. Build idempotent consumers.

### RabbitMQ

- AMQP protocol
- Exchange types: direct (routing key), topic (pattern matching), fanout (broadcast)
- Message TTL, dead letter queues, priority queues
- Not designed for replay — messages are consumed and deleted
- Good for: task queues, RPC patterns, complex routing

### AWS SQS

- Managed, no servers to maintain
- Standard queues: at-least-once, best-effort ordering
- FIFO queues: exactly-once, strict ordering (lower throughput)
- Visibility timeout: message hidden during processing; requeued if not deleted in time
- Dead Letter Queue (DLQ): messages that fail N times are moved here for inspection

## Kafka: The Log-Based Message Broker

Kafka is fundamentally different from traditional queues. It's an **append-only distributed log**.

### Core Concepts

**Topic:** A named log of messages. Think of it as a category (e.g., `order-events`, `payment-events`).

**Partition:** Each topic is split into N partitions. Each partition is an ordered, immutable log stored on disk.

```
Topic: "order-events"
  Partition 0: [msg0, msg1, msg4, msg7, ...]
  Partition 1: [msg2, msg5, msg8, ...]
  Partition 2: [msg3, msg6, msg9, ...]
```

**Offset:** Each message in a partition has a sequential integer offset. Consumers track their own position (offset) in the log.

**Broker:** A Kafka server. A Kafka cluster is multiple brokers.

**Producer:** Writes messages to a topic. Chooses partition (by key hash or round-robin).

**Consumer Group:** A group of consumers that jointly consume a topic. Each partition is assigned to exactly one consumer in a group.

```
Topic: 3 partitions
Consumer Group: 3 consumers

Consumer 1 → Partition 0
Consumer 2 → Partition 1
Consumer 3 → Partition 2
```

Add a 4th consumer → one consumer sits idle (can't have more consumers than partitions per group).

### The Key Insight: Log Retention

Unlike traditional queues, **Kafka does not delete messages after consumption.** Messages are retained for a configurable period (e.g., 7 days) or until a size limit.

This enables:
- **Replay:** Consumers can rewind and reprocess old messages
- **Multiple independent consumers:** Each consumer group tracks its own offset — one group consuming doesn't affect another
- **Fault recovery:** If a consumer crashes and recovers, it resumes from its last committed offset

### Ordering Guarantees

Kafka guarantees ordering **within a partition**, not across partitions.

```
Producer sends: order_id=42, order_id=43, order_id=42 (update)
If all go to same partition (by key "42"): guaranteed order
If spread across partitions: no global order guarantee
```

**Pattern:** Use the entity ID as the partition key to ensure all events for the same entity are ordered.

```python
producer.send("order-events", key=str(order_id), value=event_payload)
```

### Replication in Kafka

Each partition has a **leader** and N-1 **followers** (replicas on other brokers).

```
Partition 0 Leader: Broker 1
Partition 0 Replica: Broker 2, Broker 3
```

**ISR (In-Sync Replicas):** The set of replicas that are caught up with the leader. A write is committed only when all ISR members have received it (configurable: `acks=all`).

**Durability settings:**
```
acks=0    → fire and forget (fastest, possible data loss)
acks=1    → leader acknowledged (moderate, leader crash may lose data)
acks=all  → all ISR acknowledged (slowest, durable)
```

### Consumer Offset Management

Consumers commit their offset to Kafka (stored in `__consumer_offsets` internal topic) after processing.

```python
for message in consumer:
    process(message)
    consumer.commit()  # mark offset as processed
```

**At-least-once processing:** Commit after processing. If crash before commit → message reprocessed on recovery.  
**At-most-once processing:** Commit before processing. If crash during processing → message lost.

## Kafka vs Traditional Queue — When to Use Each

| Dimension | Traditional Queue (SQS/RabbitMQ) | Kafka |
|---|---|---|
| **Message retention** | Deleted after ACK | Retained (days/weeks), replayable |
| **Ordering** | Best-effort (FIFO queues for strict) | Per-partition guarantee |
| **Throughput** | Moderate | Very high (millions/sec) |
| **Multiple consumers** | Competing consumers (one gets message) | Each consumer group gets all messages |
| **Replay** | ❌ | ✅ |
| **Routing** | Complex (exchange/routing keys) | Simple (topic/partition) |
| **Operational complexity** | Low (SQS is managed) | Higher (Kafka cluster management) |
| **Use for** | Task queues, simple async | Event streaming, audit logs, data pipelines |

**Choose Kafka when:**
- You need replay (new consumer wants historical events)
- Multiple independent consumer groups need the same data
- Very high throughput (> 100K messages/sec)
- Event sourcing or audit log
- Data pipeline (stream to multiple systems)

**Choose SQS/RabbitMQ when:**
- Simple task queue (send email, process image)
- Don't need replay
- Lower throughput
- Want managed simplicity (SQS)

## Dead Letter Queues (DLQ)

When a message fails processing repeatedly, it's moved to a DLQ rather than blocking the queue.

```
Normal queue → consumer processes
             → if fails 3 times → DLQ
DLQ → engineer investigates → fix bug → replay to main queue
```

Always configure DLQs. Without one, a poison pill message (malformed, causes consumer crash) can block the queue forever.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Consumer crashes mid-processing | Message requeued (at-least-once) | Idempotent consumers |
| Broker goes down (Kafka) | Partition leader election, brief unavailability | Replication factor ≥ 3, min.insync.replicas=2 |
| Consumer lag grows | Messages pile up, processing falls behind | Scale up consumers, add partitions |
| Poison pill message | Consumer crash loop | DLQ after N retries, alert on DLQ |
| Disk full on broker | Writes fail | Monitor disk, set retention policies |
