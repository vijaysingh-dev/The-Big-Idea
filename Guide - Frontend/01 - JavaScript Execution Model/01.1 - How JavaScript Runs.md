# How JavaScript Runs

Before touching closures, the event loop or React, it helps to know what is actually executing your code. Almost every "why is this slow / why did this happen in that order" question later in this course traces back to something in this note.

## The two things people confuse: engine vs runtime

**JavaScript engine** — the program that reads your JS source and executes it. Examples: V8 (Chrome, Edge, Node.js, Deno), SpiderMonkey (Firefox), JavaScriptCore (Safari, Bun).

**JavaScript runtime** — the engine *plus* everything the host environment adds around it. The browser runtime adds the DOM, `fetch`, `setTimeout`, `localStorage`. The Node runtime adds `fs`, `http`, `process`.

This distinction matters more than it looks:

```js
setTimeout(() => console.log("hi"), 0);
```

`setTimeout` is not JavaScript. It is not in the ECMAScript specification at all. It is a function the browser hands to the engine. That is why the same code behaves differently in Node, and why `document` does not exist in a Web Worker — different runtime, same engine.

**ECMAScript** is the language specification (syntax, types, `Promise`, `Array.prototype.map`). Everything else — DOM, timers, network — comes from the host.

```
+------------------------------------------------+
|              Runtime (browser)                 |
|                                                |
|   +--------------------+   +----------------+  |
|   |   Engine (V8)      |   |   Web APIs     |  |
|   |  - parser          |   |  - DOM         |  |
|   |  - interpreter     |   |  - fetch       |  |
|   |  - JIT compiler    |   |  - timers      |  |
|   |  - heap + stack    |   |  - storage     |  |
|   +--------------------+   +----------------+  |
|                                                |
|   +----------------+   +--------------------+  |
|   |  Event Loop    |   |  Task Queues       |  |
|   +----------------+   +--------------------+  |
+------------------------------------------------+
```

The event loop and task queues also live outside the engine, in the host. We cover those in [[01.4 - The Event Loop]].

## The pipeline: source text to running code

JavaScript is often called "interpreted". That was true in 2008. Modern engines are **JIT-compiled** — *just-in-time*, meaning code is compiled to machine code while the program is running, rather than ahead of time like C++.

Here is the V8 pipeline, which is representative of all modern engines:

**1. Parsing → AST**

The parser reads your source and builds an **AST** (Abstract Syntax Tree — a tree representation of your code's structure, where `a + b` becomes a node "addition" with two children).

V8 does this in two passes. The **pre-parser** does a fast scan that skips function bodies, recording only enough to know where each function starts and ends. The **full parser** builds a real AST only for code that is about to run. This is why a 2 MB bundle costs you before a single line executes: the engine must at minimum scan all of it.

**2. AST → bytecode (Ignition)**

V8's interpreter, **Ignition**, compiles the AST into bytecode — a compact, platform-independent instruction set — and starts executing it immediately. Bytecode is much smaller than machine code, which matters for memory on mobile devices.

**3. Profiling → optimized machine code (TurboFan)**

While Ignition runs, it records **type feedback**: what types actually flow through each operation. Functions that run often become "hot". V8's optimizing compiler, **TurboFan**, then compiles those hot functions to highly optimized machine code, using the observed types as assumptions.

**4. Deoptimization**

Those assumptions can be wrong. If a function optimized for numbers suddenly receives a string, the engine must **deoptimize** — throw away the optimized code and fall back to bytecode.

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 100000; i++) add(i, i + 1);

add("hello", "world");
```

The loop makes `add` hot; TurboFan compiles a version assuming two numbers. The final call violates that and triggers a deopt. One call is harmless. The same pattern inside a hot render path is not.

## Hidden classes and inline caches

This is the part that actually changes how you write code.

JavaScript objects are dynamic — you can add properties any time. Looking up a property by name in a hash map on every access would be slow. So V8 secretly assigns each object a **hidden class** (also called a *shape* or *map*): a description of the object's layout, saying "property `x` is at offset 0, property `y` is at offset 1".

Objects created the same way share a hidden class. When they do, V8 can install an **inline cache** at a property access site — a small cache that remembers "last time I saw shape S here, and `y` was at offset 1", turning a lookup into a single memory read.

```js
function makePointFast(x, y) {
  return { x, y };
}

function makePointSlow(x, y) {
  const p = {};
  p.x = x;
  p.y = y;
  return p;
}
```

Both produce identical objects, but the second walks through an extra intermediate shape (`{}` → `{x}` → `{x, y}`), creating more hidden class transitions. More importantly:

```js
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };
```

`a` and `b` have **different hidden classes** because property insertion order differs. Code that reads `.x` from both sees two shapes and becomes **polymorphic** — the inline cache holds several shapes and lookups get slower. Past roughly four shapes it goes **megamorphic** and falls back to a full hash lookup.

Practical rules that fall out of this:

- Initialize all object properties in a constructor or literal, in a consistent order.
- Do not add properties to objects after creation in hot paths.
- Avoid `delete` on objects in hot paths — it can force the object into slow dictionary mode.
- Keep arrays homogeneous. `[1, 2, 3]` uses a packed integer representation; `[1, "two", {}]` does not.

## Single-threaded, but not single-tasked

The engine executes your JavaScript on **one thread**. There is one call stack, one heap. Two lines of your JS never run simultaneously.

But the runtime is multi-threaded. When you call `fetch`, the browser performs the network request on its own threads and only hands the result back to your single JS thread later via the event loop. That is why JavaScript is single-threaded *and* non-blocking at the same time.

The consequence you will hit constantly in React work: **any long synchronous JS blocks everything** — no rendering, no click handling, no scroll response.

```js
const start = Date.now();
while (Date.now() - start < 3000) {}
```

For three seconds the page is frozen. Nothing paints, no input is processed. This is the single most common cause of "the UI feels laggy" bugs, and it is why we care about [[13.3 - Layout Thrashing]] and [[08.4 - Web Workers]] later.

## Memory: stack and heap

The engine keeps two memory regions:

**Stack** — fixed-size, fast, LIFO. Holds execution contexts (function call frames) and primitive values. Blowing past its limit gives you `RangeError: Maximum call stack size exceeded`. Covered in [[01.3 - The Call Stack]].

**Heap** — large, unstructured. Holds objects, arrays, functions. Managed by the garbage collector, covered in [[07.1 - How Garbage Collection Works]].

```js
let a = 10;
let b = a;
b = 20;
console.log(a); // 10 — primitives copy by value

let o1 = { n: 10 };
let o2 = o1;
o2.n = 20;
console.log(o1.n); // 20 — o1 and o2 hold the same heap reference
```

The variables `o1` and `o2` sit on the stack; the object itself sits on the heap. Both variables hold the same address. This single fact explains most React "why didn't my component re-render" bugs, since React compares references, not contents.

## How senior engineers actually use this

**They optimize load time before runtime.** Parse and compile cost is proportional to bytes shipped. On a mid-range Android phone, a large bundle can spend hundreds of milliseconds just being parsed before anything renders. This is why [[27.6 - Tree Shaking]], code splitting and lazy loading matter more than micro-optimizing loops. The fastest JavaScript is the JavaScript you never ship.

**They rarely hand-tune for the JIT.** Hidden class discipline is worth following as a habit — consistent object shapes, homogeneous arrays — but nobody restructures business logic for TurboFan. The exceptions are genuinely hot paths: canvas and animation loops, large data transforms, virtualized list rendering. Everywhere else, profile first.

**They reach for the profiler, not intuition.** Chrome DevTools' Performance panel shows scripting, rendering and painting time separately. The usual finding is not "my algorithm is slow" but "we are doing 400 ms of synchronous work on the main thread in a click handler". `console.time` and the User Timing API (`performance.mark` / `performance.measure`) are the everyday tools.

**They know which runtime they are in.** Code shared between browser and Node must not assume `window` or `document` exist. This is the root of most server-side rendering bugs — see [[28.11 - Rendering Strategies]].

## Common pitfalls

- Assuming JavaScript is interpreted line by line, and therefore expecting the source order to match execution order. Hoisting, the event loop and JIT compilation all break that assumption.
- Treating "single-threaded" as "can only do one thing at a time". The runtime does plenty in parallel; only your JS is serialized.
- Micro-benchmarking in the console. Engines optimize tight synthetic loops in ways real code never sees, so numbers from a `for` loop with a constant body are usually meaningless.
- Assuming Node and the browser behave identically. Different runtimes, different globals, different timer semantics.

## Interview angle

The question is usually phrased as "what happens when you run a JavaScript file?" or "is JavaScript compiled or interpreted?". A strong answer covers: source is parsed into an AST, an interpreter produces bytecode and starts running immediately, hot functions get optimized to machine code using observed types, and wrong assumptions cause deoptimization — so it is neither purely interpreted nor purely compiled. Mentioning that the engine is separate from the runtime, and that timers and the DOM come from the host, tends to land well.
