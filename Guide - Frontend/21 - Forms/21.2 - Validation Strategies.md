# Validation Strategies

Validation has three separate decisions: **where** it runs, **when** it fires, and **how** errors are expressed.

## Client validation is UX, server validation is security

Client-side validation exists to give fast feedback. It can always be bypassed — disabling JavaScript, using `curl`, or editing the request in DevTools.

**The server must validate everything, independently.** Client validation is a convenience layer, never a control.

The ideal is one schema shared by both, so the rules cannot drift:

```ts
// schema.ts — shared
export const signupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8).regex(/[0-9]/, "Must contain a number"),
  age: z.number().int().min(13),
});
```

## Schema validation with Zod

```ts
import { z } from "zod";

const schema = z.object({
  email: z.string().email("Enter a valid email"),
  password: z.string().min(8, "At least 8 characters"),
  confirm: z.string(),
}).refine(data => data.password === data.confirm, {
  message: "Passwords must match",
  path: ["confirm"],          // attach the error to a specific field
});

type FormValues = z.infer<typeof schema>;   // types derived from the schema
```

Two things this buys beyond validation:

**Types come from the schema**, so the validated shape and the TypeScript type cannot disagree ([[25.7 - Typing API Responses and Zod]]).

**`refine` handles cross-field rules** — password confirmation, date ranges, conditional requirements — which per-field validators cannot express.

Parsing the result:

```ts
const result = schema.safeParse(values);
if (!result.success) {
  const errors = result.error.flatten().fieldErrors;
  // { email: ["Enter a valid email"], password: [...] }
}
```

`safeParse` returns a result object rather than throwing, which is what you want in a form handler.

Valibot and Yup are alternatives; Valibot is notably smaller if bundle size matters, since it is fully tree-shakeable.

## When to validate

Timing matters more for UX than the rules themselves.

| Trigger | Feel |
| --- | --- |
| `onChange` from the start | hostile — errors while typing the first character |
| `onBlur` first, then `onChange` | the standard good default |
| `onSubmit` only | acceptable for short forms, frustrating for long ones |

The rule most libraries implement: **validate on blur, then re-validate on change once the field has an error.** The user is not told they are wrong until they finish, and then gets immediate confirmation when they fix it.

```jsx
const { register } = useForm({
  mode: "onTouched",           // validate on first blur
  reValidateMode: "onChange",  // then on every change
});
```

The CSS equivalent for native validation is `:user-invalid`, which only matches after interaction ([[10.3 - Selectors and Pseudo Classes]]):

```css
input:user-invalid { border-color: var(--error); }
```

## Async validation

```jsx
const checkUsername = async (value) => {
  const res = await fetch(`/api/username-available?u=${value}`);
  const { available } = await res.json();
  return available || "That username is taken";
};

<input {...register("username", { validate: checkUsername })} />
```

Three requirements: debounce it, handle the in-flight state visibly, and cancel superseded requests ([[04.6 - AbortController and Cancellation]]).

Async validation must also be repeated on submit — the username could be taken between the check and the submission. Treat it as a hint, not a guarantee.

## Server errors

```jsx
async function onSubmit(values) {
  try {
    await api.signup(values);
  } catch (err) {
    if (err.status === 422) {
      Object.entries(err.fieldErrors).forEach(([field, message]) => {
        setError(field, { type: "server", message });
      });
    } else {
      setError("root", { message: "Something went wrong. Try again." });
    }
  }
}
```

Two categories with different handling:

**Field errors** (422) map onto specific inputs and should be displayed there.
**Form errors** (network failure, 500, rate limit) go in a form-level region.

The API should return a predictable shape:

```json
{ "fieldErrors": { "email": "Already registered" }, "formError": null }
```

Agreeing this shape with the backend early saves a lot of ad-hoc parsing later ([[28.5 - Global Error Handling]]).

## Error message quality

```
"Invalid input"                          → useless
"Password does not meet requirements"    → which requirement?
"Password must contain a number"         → actionable
```

Say what is wrong and what to do. For multi-rule fields, show progress rather than a single error:

```jsx
<ul>
  <li data-met={value.length >= 8}>At least 8 characters</li>
  <li data-met={/[0-9]/.test(value)}>Contains a number</li>
</ul>
```

Live requirement checklists test better than error messages for password fields, because they are visible before the user fails.

## Accessible errors

```jsx
<input
  id="email"
  aria-invalid={Boolean(error)}
  aria-describedby={error ? "email-error" : undefined}
/>
{error && <p id="email-error" role="alert">{error.message}</p>}
```

And a summary for long forms, focused on submit:

```jsx
{Object.keys(errors).length > 0 && (
  <div ref={summaryRef} tabIndex={-1} role="alert">
    <h2>There are {Object.keys(errors).length} problems</h2>
    <ul>
      {Object.entries(errors).map(([field, err]) => (
        <li key={field}><a href={`#${field}`}>{err.message}</a></li>
      ))}
    </ul>
  </div>
)}
```

Moving focus to the summary after a failed submit is what makes a long form usable with a screen reader — otherwise the user has no idea anything happened ([[09.5 - Accessibility Fundamentals]]).

## React 19 form actions

```jsx
const [state, formAction, isPending] = useActionState(
  async (prevState, formData) => {
    const parsed = schema.safeParse(Object.fromEntries(formData));
    if (!parsed.success) {
      return { errors: parsed.error.flatten().fieldErrors };
    }
    await save(parsed.data);
    return { success: true };
  },
  { errors: {} }
);

<form action={formAction}>
  <input name="email" aria-invalid={Boolean(state.errors.email)} />
  {state.errors.email && <p role="alert">{state.errors.email}</p>}
  <button disabled={isPending}>Submit</button>
</form>
```

React manages the pending state, and the form works without JavaScript when paired with a server action — genuine progressive enhancement ([[17.12 - Lesser Known Hooks]]).

## Validation is not sanitization

Validation checks shape; it does not make data safe to render or store.

- Escaping for display is React's job by default ([[16.2 - JSX]])
- HTML that must be rendered needs sanitizing with DOMPurify ([[15.6 - Frontend Security]])
- SQL safety is the server's job, via parameterized queries

A validated string can still contain a `javascript:` URL or a script payload.

## How senior engineers actually use this

**They define one schema and share it** between client and server, deriving types from it.

**They validate on blur and re-validate on change**, which is the timing users actually like.

**They agree an error response shape with the backend** before building the form.

**They focus an error summary on failed submit** for anything longer than a few fields.

**They treat client validation as UX only** and never as a security boundary.

## Common pitfalls

- Validating on every keystroke from the first character.
- Client validation without matching server validation.
- Duplicated rules that drift between client and server.
- Async validation without debounce or cancellation.
- Errors conveyed only by colour, with no `aria-describedby`.
- Vague messages that do not say what to fix.
- No handling for form-level errors, only field errors.
- Assuming validated means sanitized.

## Interview angle

"How do you handle form validation" should cover all three axes: where (client for UX, server for security, one shared schema), when (blur then change), and how (field errors versus form errors, with accessible announcement). The details that stand out are the shared-schema-with-inferred-types point and the error summary with focus management — both show you have shipped forms people actually use rather than demos.
