# Multi-Tenant Isolation

#backend #security #multi-tenancy

> **In one line:** Every layer of your system holds tenant data, and isolation is only as strong as the weakest one — so the question is not "did we filter by org_id" but "what happens to every layer when one check is missed".

---

## The Idea

[[06.16 - Multi Tenant Data Models]] covered the data model — pool, bridge, silo, and RLS. **This note is the security view: every place tenant data can cross a boundary, and how to prove it does not.**

```
Database         → RLS, repository scoping
Cache            → key namespacing
Search index     → filter, or index-per-tenant
Object storage   → prefix, or bucket-per-tenant
Message queues   → payload scoping
Logs and traces  → tenant labelling
Background jobs  → tenant context propagation
Exports and reports → the most commonly missed
```

⚠️ **Most isolation reviews check the database and stop.** The cache, the search index and the background job path are where the real leaks are.

---

## The Layers, and How Each Leaks

### Cache

```python
key = f"doc:{doc_id}"                       # ❌ no tenant in the key
key = f"org:{org_id}:doc:{doc_id}"          # ✅
```

⚠️ **If document IDs are globally unique, an unscoped key "works" — until an ID collision, or until a cached *query result* is served to the wrong tenant.**

```python
key = f"search:{query_hash}"                          # ❌ catastrophic
key = f"org:{org_id}:search:{query_hash}"             # ✅
```

💡 **Query result caches are the dangerous case**, because the same query text from two tenants must produce different results ([[07.2 - Cache Strategies and Invalidation]]).

**Make the tenant a mandatory argument of your cache helper**, so an unscoped key is a type error rather than a review comment.

### Search index

```python
# Shared index — the filter is the only thing between tenants
await es.search(index="documents", query={
    "bool": {
        "filter": [{"term": {"org_id": org_id}}],      # ⚠️ MUST be a filter, not a should
        "must": [{"match": {"content": q}}],
    }
})
```

⚠️ **A tenant filter in the wrong clause silently becomes optional.** In Elasticsearch, `should` without `minimum_should_match` means "boost if present", not "require".

💡 **Wrap it so the filter cannot be omitted:**

```python
async def tenant_search(org_id: str, query: dict) -> dict:
    return await es.search(index="documents", query={
        "bool": {"filter": [{"term": {"org_id": org_id}}], "must": [query]}
    })
```

**Index-per-tenant is stronger** — a query against the wrong index returns nothing rather than everything — **and it does not scale past a few hundred tenants** ([[06.15 - Search - Postgres vs Elasticsearch]]).

### Object storage

```
s3://conduit-documents/org_7/doc_42/original.pdf
```

⚠️ **A signed URL is a bearer credential.** If it leaks — a referrer header, a shared link, a log line — anyone with it can read the object until expiry.

| Control | |
|---|---|
| Tenant prefix in the key | |
| **Short expiry on signed URLs** | Minutes, not days |
| **Verify authorisation before signing** | The signature is not the check |
| IAM policies scoped by prefix | For service-level isolation |
| Never make a bucket public | |

💡 **The authorisation check happens when you *sign*, not when the object is fetched.** A code path that signs a URL without checking permission has handed out access.

### Background jobs

```python
await enqueue(reindex_document, doc_id)                    # ❌ no tenant context
await enqueue(reindex_document, org_id=org_id, doc_id=doc_id)   # ✅
```

⚠️ **The worker has no request context.** Whatever authorisation the request path enforced is gone — **the job runs with whatever it was given.**

```python
async def reindex_document(org_id: str, doc_id: str):
    doc = await repo.get(doc_id, org_id=org_id)      # scoped, always
    if doc is None:
        return
```

💡 **Pass the tenant explicitly and scope every query in the worker.** A job that takes only a resource ID trusts its caller completely ([[08.5 - Task Design Rules]]).

**The same applies to event consumers** — an event carrying `document_id` without `org_id` forces the consumer to look it up unscoped.

### Exports and reports

⚠️ **The most commonly missed path, and the highest impact.**

An export job assembling data from several sources — documents, annotations, users, usage statistics — **must scope every one of them.** One unscoped query produces a file containing another tenant's data, delivered to a customer.

💡 **Exports deserve their own isolation test**, because they touch more tables than any request handler and they produce a durable artefact.

### Logs and traces

```python
log.info("document indexed", org_id=org_id, document_id=doc_id)
```

⚠️ **A shared logging platform means one tenant's data in a system many people can query.** Do not log document content, user emails or connector credentials.

💡 **Log identifiers, not content.** `document_id=doc_42` is useful for debugging; the document's text is a disclosure.

## Proving Isolation

### The cross-tenant probe

```python
@pytest.mark.parametrize("resource_type", ALL_RESOURCE_TYPES)
async def test_cross_tenant_denied(resource_type, client):
    resource = await make_resource(resource_type, org=org_a)
    user_b = await make_user(org=org_b)

    for method, path in ENDPOINTS[resource_type]:
        response = await client.request(method, path.format(id=resource.id), user=user_b)
        assert response.status_code == 404, f"{method} {path} leaked"
```

💡 **Parameterised over every resource type and every endpoint, this is the single highest-value security test in a multi-tenant product** ([[14.1 - AuthN vs AuthZ]]).

**Adding a new endpoint without adding it to `ENDPOINTS` should fail a coverage check.**

### Layer-by-layer probes

```python
async def test_cache_isolation():
    await cache_document(org_a, doc_id, content_a)
    assert await get_cached_document(org_b, doc_id) is None

async def test_search_isolation():
    await index_document(org_a, doc_id, "unique-phrase-xyz")
    assert await search(org_b, "unique-phrase-xyz") == []

async def test_storage_isolation():
    url = await signed_url(org_a, doc_id)
    with pytest.raises(Unauthorized):
        await signed_url(org_b, doc_id)

async def test_worker_isolation():
    await reindex_document(org_id=org_b.id, doc_id=doc_a.id)
    assert await search(org_b, "content-of-doc-a") == []
```

⚠️ **Write one of these per layer.** The database test alone gives false confidence.

### Removing a layer

💡 **The strongest proof of defence in depth: disable one layer and confirm the others still hold.**

```python
async def test_rls_catches_missing_repository_scope():
    # A deliberately unscoped raw query
    with pytest.raises(NoResultsForTenant):
        await raw_conn.fetch("SELECT * FROM documents WHERE id = $1", doc_a.id)
```

**Run this as a test.** If removing the repository scoping still returns nothing, RLS is genuinely enforcing.

## In Production

### The isolation matrix

```markdown
| Layer          | Mechanism                     | Tested |
|----------------|-------------------------------|--------|
| Postgres       | RLS (FORCE) + repository      | ✅     |
| Redis          | org-prefixed keys             | ✅     |
| Search index   | mandatory filter wrapper      | ✅     |
| Object storage | prefix + authorised signing   | ✅     |
| Kafka          | org_id in every event payload | ✅     |
| Background jobs| org_id argument, scoped reads | ✅     |
| Exports        | every source query scoped     | ✅     |
| Logs/traces    | identifiers only, no content  | ✅     |
```

⚠️ **The "Tested" column is the point.** An untested isolation mechanism is a hypothesis.

### Noisy neighbours are an isolation concern

⚠️ **Availability isolation matters as much as data isolation to a customer.**

| Problem | Control |
|---|---|
| One tenant's expensive queries | Per-tenant concurrency limits, `statement_timeout` |
| One tenant's bulk import | Per-tenant queue throttling ([[08.7 - Routing Queues Priorities and Prefetch]]) |
| One tenant's API traffic | Per-tenant rate limits ([[11.5 - Rate Limiting and Quotas]]) |
| One tenant's data volume | Quotas, and `org_id` leading every index |

💡 **Query tagging makes attribution possible** ([[06.16 - Multi Tenant Data Models]]):

```python
sql = f"/* org:{org_id} */ SELECT ..."
```

**Without it, "one customer is slow" and "the system is slow" look identical.**

### Deletion must be complete and provable

⚠️ **GDPR erasure applies to every layer, and "we deleted them from the database" is not compliance.**

```
□  Primary database         CASCADE delete, verified by query
□  Read replicas            follows automatically
□  Search index             explicit deletion, verified
□  Cache                    invalidate by namespace
□  Object storage           delete by prefix, verified
□  Message queues           in-flight messages for that tenant
□  Backups                  documented retention, then expiry
□  Logs and analytics       often forgotten. Include it
□  Derived stores           analytics, vector index
```

💡 **Each store needs a verification query, and the deletion process must produce a record that all of them completed** ([[10.4 - Data Ownership]]).

**Run the verification as an automated test against a throwaway tenant.**

### Per-tenant encryption

```
KMS master key
  └── DEK per tenant
        └── encrypts that tenant's sensitive data
```

💡 **Per-tenant DEKs give you cryptographic deletion** — destroy the key and the data is unrecoverable, including from backups. **That is a genuinely strong compliance story** ([[14.5 - Secrets and Key Management]]).

⚠️ **The cost is key management at tenant scale**, and it complicates cross-tenant analytics. **Worth it for regulated data; disproportionate otherwise.**

### Monitoring

```python
tenant_isolation_violation_total.inc()        # ← page immediately
cross_tenant_probe_denied_total.inc()
unscoped_query_detected_total.inc()
```

```python
def assert_tenant(rows, org_id):
    if any(r["org_id"] != org_id for r in rows):
        tenant_isolation_violation_total.inc()
        log.critical("cross-tenant data in response")
        raise TenantIsolationError()
```

💡 **The outgoing assertion turns a silent breach into a loud 500**, and it is cheap enough to run in production. **A leak that raises an error is enormously better than one that renders in a customer's browser.**

⚠️ **`tenant_isolation_violation_total` must page.** It should never fire, and if it does, something is seriously wrong right now.

### The enterprise question

⚠️ **"Where is our data, and who can access it?" is a question you will be asked in every enterprise sales cycle.**

The credible answer names the layers:

> "Your data is in a shared Postgres cluster with row-level security enforced by the database, in an object storage prefix scoped to your organisation with IAM policies, and in a search index with a mandatory tenant filter. We test cross-tenant access on every resource type in CI. For customers requiring physical isolation, we offer a dedicated database and storage bucket."

💡 **Having the isolation matrix and the test suite means that answer is verifiable rather than reassuring**, and the difference is obvious to a technical buyer.

### Conduit's isolation

| Layer | Mechanism |
|---|---|
| Postgres | **RLS with `FORCE`**, plus repository scoping |
| DataLoaders | Tenant boundary enforced in every batch function |
| Redis | `org:{id}:` prefix, enforced by the cache helper's signature |
| Search | Mandatory filter wrapper; no raw index access |
| Object storage | `org_{id}/` prefix; authorisation checked before signing |
| Kafka | `org_id` in every event; consumers scope every query |
| Workers | `org_id` as an explicit argument |
| Response | Outgoing assertion in every environment |
| **Enterprise tier** | **Dedicated database and bucket** ([[06.16 - Multi Tenant Data Models]]) |

💡 **Nine layers, and the design goal is that any single one being wrong is caught by another.** The DataLoader and RLS layers in particular cover the two paths most likely to be forgotten: a GraphQL traversal nobody anticipated, and a raw query written in a hurry.

## Codebase

**Repo:** `supabase/supabase`, `citusdata/citus`, `postgres/postgres`

**Question to answer:** How does Supabase use RLS as the primary authorisation mechanism, and what patterns do they recommend for correctness and performance? Then: how does a sharded system enforce the tenant boundary at the shard level?

**Read, in order:**

1. **Supabase RLS documentation and their security guides** — **a product whose entire authorisation model is RLS.** Their patterns and pitfalls are directly applicable
2. `postgres/src/backend/rewrite/rowsecurity.c` — how a policy becomes a query predicate ([[06.16 - Multi Tenant Data Models]])
3. `citus/src/backend/distributed/planner/multi_router_planner.c` — **how a distribution column proves a query touches one shard.** Tenancy and sharding are the same problem when the shard key is the tenant key
4. **AWS SaaS Lens — tenant isolation** — the architectural patterns per layer, including storage and compute
5. **Any multi-tenant open-source product** — search for how the tenant filter is applied in the cache and search paths specifically

💡 The Supabase material is unusually valuable because **their business depends on RLS being correct**, so their documentation covers the failure modes honestly — including the performance traps and the `FORCE` requirement that most tutorials omit.

**Size:** 1 session.

## Exercise

**Drill 14.6 — Leak data from every layer, then close each one**

⚠️ Everything runs against your own local stack.

```
drills/14-tenancy/
├── layers/{database.py, cache.py, search.py, storage.py, queue.py, worker.py, export.py}
├── leaks/{probe_all.py, unscoped_cache.py, wrong_es_clause.py, signed_url.py,
│           job_no_tenant.py, export_leak.py, FINDINGS.md}
├── defence/{assertions.py, wrappers.py, tests/}
├── removal/{disable_layer.py, RESULTS.md}
├── deletion/{delete_tenant.py, verify.py, RESULTS.md}
├── noisy/{limits.py, attribution.py, PLOT.md}
└── matrix.md
```

**Part 1 — Build all eight layers.** A multi-tenant Conduit slice touching database, cache, search, object storage, queue, workers, exports, and logs.

**Part 2 — Leak from six layers.** For each, write the plausible mistake and demonstrate the actual cross-tenant access:

| Layer | Mistake |
|---|---|
| Cache | Unscoped key on a query result |
| **Search** | Tenant filter in `should` instead of `filter` |
| Storage | Signing a URL without checking authorisation |
| Queue | Event carrying only `document_id` |
| **Worker** | Job takes a resource ID with no tenant |
| **Export** | One of five source queries unscoped |

**For each, demonstrate reading another tenant's data**, and estimate how long it would go unnoticed.

💡 **The export one is worth doing carefully** — it is the highest-impact and the least likely to be caught by a handler-level test.

**Part 3 — Close each structurally.** Not with a check to remember:

```
Cache helper requires org_id as a positional argument
Search wrapper is the only way to query the index
Signing function performs the authorisation check itself
Job signature requires org_id
Repository is the only path to data, and it is always scoped
```

**For each, confirm the vulnerable pattern is now impossible rather than merely discouraged.**

**Part 4 — The universal probe.** A parameterised test over every resource type and every endpoint, as org B against org A's resources.

**Then add a coverage check that fails when an endpoint exists without a corresponding probe.**

**Confirm it fails when you add a new endpoint.**

**Part 5 — Remove a layer, prove the others hold.** For each of RLS, repository scoping, the DataLoader check, and the response assertion:

**Disable it and confirm the attack is still blocked by the remaining layers.**

⚠️ **Find the case where removing one layer *does* leak.** There will be one — usually a raw query with RLS disabled. **That tells you which layer is load-bearing.**

**Part 6 — Complete deletion.** Delete a tenant with 10,000 documents across all eight layers.

**Write a verification query per store** and confirm each is clean.

Then simulate a partial failure — the search index deletion fails — and **confirm your process detects the incompleteness** rather than reporting success.

**Then answer definitively: "is this tenant fully deleted?"**

**Part 7 — Noisy neighbours.** One tenant running expensive queries and a bulk import simultaneously.

**Chart p99 latency for other tenants.**

Then add per-tenant concurrency limits, query timeouts, and queue throttling. **Chart again.**

Then add query tagging and **attribute the cost to the right tenant from your slow log alone.**

**Part 8 — The matrix and the sales answer.** Complete the isolation matrix with a tested mark against every layer.

**Then write the paragraph you would give an enterprise buyer**, and confirm every claim in it maps to a test in your suite.

**Done when:**
- Six layer-specific leaks are demonstrated with real cross-tenant access
- Each is closed structurally, and the vulnerable pattern is impossible
- Your universal probe covers every endpoint, with a coverage check
- Removing each layer individually still blocks the attack, except the one you can name
- Tenant deletion is verified per store, and a partial failure is detected
- Per-tenant limits protect other tenants, with attribution from logs
- Every claim in your enterprise answer maps to a passing test
