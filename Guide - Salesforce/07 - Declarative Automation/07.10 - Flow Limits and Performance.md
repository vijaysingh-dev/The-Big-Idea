# Flow Limits and Performance

## Flows consume the same budget as everything else

There is no separate allowance for flows. A flow's queries, DML statements, CPU time, and heap all draw from the **same per-transaction limits** as Apex, validation rules, roll-up recalculation, and installed packages.

The canvas hides this, which is why flow-heavy orgs accumulate limit failures nobody can attribute to a specific change.

The limits that matter, per synchronous transaction:

- 100 SOQL queries
- 50,000 records retrieved
- 150 DML statements
- 10,000 records processed by DML
- 10 seconds CPU time
- 6 MB heap

Plus flow-specific ones:

- 2,000 elements executed per flow interview
- 50 versions per flow
- Limits on scheduled path executions per hour

The 2,000-element limit is reached by a loop over a large collection — 500 records with four elements inside the loop is 2,000 executions.

## The three failure modes

**Query or DML inside a loop.** The flow equivalent of SOQL-in-a-loop, and the most common. Nothing on the canvas warns you.

**Per-record execution in a bulk save.** A record-triggered flow runs once per record. A Get Records element in it issues one query per record. Two hundred records in a data load is 200 queries against a limit of 100.

**Cascading automation.** Flow A updates Record B, whose flow updates Record C, whose flow updates Record A. Every save re-enters the pipeline, and the limit consumed belongs to the original transaction.

The second is the one people miss, because the flow looks correct. There is no flow construct for "collect IDs across the whole batch and query once" — that requires Apex.

## The pattern that fixes loops

```
Wrong                          Right
─────                          ─────
Loop over records              Get Records (all at once, before the loop)
    Get Records                Loop over records
    Assignment                     Assignment
    Update Records                 Add to output collection
End Loop                       End Loop
                               Update Records (once, on the collection)
```

Build the output collection inside the loop; perform the DML after it. This is the same collect-query-act structure as bulkified Apex ([[10.6 - Bulkification Patterns]]).

For lookups inside a loop, fetch the parent records once before the loop and use a **Collection Filter** element or a decision to match, rather than querying per iteration.

## Reducing per-record cost

Ordered by impact:

**Set entry conditions.** A flow with none runs on every save of the object, evaluating everything. On a high-volume object this is pure waste.

**Use "only when a record is updated to meet the condition requirements."** Without it, a flow with condition `Status = 'Approved'` fires on every edit of every approved record forever, rather than once on the transition.

**Prefer before-save.** No DML, no second pass through the save pipeline, roughly ten times cheaper for same-record field assignment. See [[07.4 - Before-Save vs After-Save Flows]].

**Minimize `$Record` relationship traversal.** `{!$Record.Account__r.Owner.Manager.Email}` is work per record. Where the same parent data is needed repeatedly, one Get Records is cheaper.

**Move bulk-sensitive logic to invocable Apex**, which receives all records in one call and can query once. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

**Consolidate flows.** Five flows on one object each with a Get Records is five queries per record. One flow with one Get Records and internal decisions is one.

## Measuring it

Flow Debug shows the path taken but not the cost. Debug logs do.

Set the **Workflow** log level to FINER and the **Apex Code** level to DEBUG, then perform the operation. The log shows each flow element, each query issued, and the cumulative limit consumption.

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 87 out of 100
  Number of query rows: 3421 out of 50000
  Number of DML statements: 12 out of 150
  Maximum CPU time: 8214 out of 10000
```

That block at the end of every debug log is the diagnostic. Reading it after a bulk operation in a sandbox with realistic volume is how limit problems are found before production finds them.

For a specific investigation, the **Developer Console** execution tree shows time spent per element, which identifies the expensive step rather than just the expensive transaction. See [[20.3 - Developer Console and Log Inspector]].

## Testing at volume

The central weakness of flow: **Flow Debug runs one record.** A flow debugged successfully proves nothing about its behaviour with 200.

The only reliable test is a bulk operation in a sandbox with realistic data:

```java
// Anonymous Apex: exercise the flow with a realistic batch
List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
for (Integer i = 0; i < 200; i++) {
    claims.add(new Warranty_Claim__c(
        Asset__c = assetIds[Math.mod(i, assetIds.size())],
        Claim_Date__c = Date.today(),
        Status__c = 'Submitted'
    ));
}
insert claims;
```

Running that in a sandbox and reading the limit block at the end of the log is the closest thing flow has to a load test. It takes five minutes and it is the step almost nobody performs.

Where flows and Apex coexist on an object, this also reveals the **combined** cost, which is what production actually experiences.

## Async flows

Some flow work can be moved out of the user's transaction:

**Scheduled paths** on record-triggered flows run later, in a separate transaction with fresh limits. A path scheduled for zero minutes after the trigger is the flow equivalent of an async job, and it is a legitimate technique for moving expensive work out of the save.

**Platform event-triggered flows** run asynchronously in their own transaction.

**"Run Asynchronously" paths** on record-triggered flows exist specifically for work that needs callouts or that should not block the save.

The tradeoff: async work cannot report failure to the user, and it needs its own monitoring. See [[07.8 - Flow Error Handling and Fault Paths]].

## When flow is the wrong tool

The honest signals that a requirement has outgrown flow:

- It needs a query per record in a bulk context
- The canvas no longer fits on a screen and has more than three nesting levels
- It requires recursion control
- It processes tens of thousands of records
- Correctness depends on precise bulk behaviour
- It needs real unit tests with assertions
- It needs a callout whose response the process must act on

None of these are absolute, and all of them are worth noticing. A flow that has grown to sixty elements with four subflows is code, written in a medium that has no tests, no code review worth the name, and no debugger.

## The org-level audit

Worth running periodically:

```sql
SELECT ApiName, Label, ProcessType, TriggerType, TriggerObjectOrEventLabel,
       VersionNumber, LastModifiedBy.Name, LastModifiedDate
FROM FlowDefinitionView
WHERE Status = 'Active'
ORDER BY TriggerObjectOrEventLabel, TriggerType
```

Grouped by object, that shows how many flows fire on each save. Any object with more than two active record-triggered flows is worth examining, and any object with more than four is a consolidation candidate.

## Practical guidance

**Never query or perform DML inside a loop.**

**Always set entry conditions**, and use the update-to-meet-conditions option.

**Prefer before-save**, and never update `$Record` from an after-save flow.

**Test with 200 records in a sandbox** and read the limit block in the log.

**Move bulk-sensitive logic to invocable Apex.**

**Audit flows per object.** More than two per object per timing is a design smell.

**Recognize when a flow has become code**, and move it before it fails in production.
