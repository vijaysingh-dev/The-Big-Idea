# Promise Chaining and Error Handling

Chaining works because every `.then` returns a new promise, and returning a promise from a handler makes the chain wait for it ([[04.2 - Promises from First Principles]]). That single rule flattens what would have been nested callbacks.

## Flattening

```js
getUser(id)
  .then(user => getOrders(user.id))
  .then(orders => getDetails(orders[0].id))
  .then(details => render(details))
  .catch(handleError);
```

Compare with the four-level pyramid in [[04.1 - Callbacks and Callback Hell]]. One error handler covers every step, and each step is a flat expression rather than a nested scope.

The critical word is **return**:

```js
// Broken — the chain does not wait
getUser(id)
  .then(user => { getOrders(user.id); })
  .then(orders => console.log(orders)); // undefined

// Correct
getUser(id)
  .then(user => getOrders(user.id))
  .then(orders => console.log(orders));
```

An arrow with a block body returns `undefined` unless you write `return`. This is the single most common promise bug, and it is invisible — the code runs, it just produces `undefined` and swallows any error from the un-returned promise.

## The nesting trap

```js
// Nested — user is available, but the chain is a pyramid again
getUser(id).then(user =>
  getOrders(user.id).then(orders =>
    getDetails(orders[0].id).then(details =>
      render({ user, orders, details })
    )
  )
);
```

People nest because a later step needs an earlier value. Three ways out:

```js
// Pass a composite object down
getUser(id)
  .then(user => getOrders(user.id).then(orders => ({ user, orders })))
  .then(({ user, orders }) => getDetails(orders[0].id).then(details => ({ user, orders, details })))
  .then(render);

// Close over via an outer variable
let user;
getUser(id)
  .then(u => { user = u; return getOrders(u.id); })
  .then(orders => render({ user, orders }));

// async/await — almost always the right answer
async function load(id) {
  const user = await getUser(id);
  const orders = await getOrders(user.id);
  const details = await getDetails(orders[0].id);
  return render({ user, orders, details });
}
```

The third is why `async/await` exists ([[04.4 - async await]]). Chaining remains the better choice for pipelines where no step needs a value from two steps back.

## Error propagation

A rejection skips every subsequent `.then` until it finds a rejection handler.

```js
step1()
  .then(step2)   // skipped on rejection
  .then(step3)   // skipped
  .catch(handle) // runs
  .then(step4);  // runs — the chain has recovered
```

This is the part people miss: **`.catch` recovers**. Whatever it returns fulfills the next promise, so the chain continues normally. To keep the chain rejected, re-throw:

```js
.catch(err => {
  log(err);
  throw err;
})
```

Placement matters:

```js
// catch first — later errors are unhandled
fetchData().catch(handle).then(process);

// catch last — covers everything above it
fetchData().then(process).catch(handle);
```

Almost always put `.catch` at the end. Use an early `.catch` only when you deliberately want to recover and continue, for example supplying a default on a failed optional request.

## then's second argument vs catch

```js
p.then(onSuccess, onError);   // onError does NOT catch onSuccess throwing
p.then(onSuccess).catch(onError); // onError catches both
```

`.then(f, g)` attaches both handlers to the *same* promise, so `g` cannot see errors from `f`. The chained form attaches `onError` to the promise `then` returned, which includes `onSuccess`'s outcome.

The one legitimate use of the two-argument form is when you specifically want to distinguish "the original operation failed" from "my handler failed".

## finally

```js
setLoading(true);
fetchData()
  .then(render)
  .catch(showError)
  .finally(() => setLoading(false));
```

Runs on both paths, receives no arguments, and is transparent — it passes the value or rejection through untouched. Returning a value from it is ignored; returning a promise delays the chain.

Note `.finally` does not handle the rejection. Placing it after `.catch` means the chain is already recovered; placing it before means a rejection still propagates past it.

## fetch does not reject on HTTP errors

The most consequential gotcha in the browser:

```js
fetch("/api/missing")
  .then(res => res.json())   // runs even on 404 or 500
  .catch(err => {});         // only fires on network failure
```

`fetch` rejects only on network-level failure — DNS, connection refused, CORS block, abort. A 404 or 500 is a *successful* HTTP exchange as far as `fetch` is concerned. You must check `res.ok` yourself:

```js
async function request(url, options) {
  const res = await fetch(url, options);
  if (!res.ok) {
    throw new HttpError(res.status, await res.text().catch(() => ""));
  }
  return res.json();
}
```

Every API-layer wrapper you write should do this once, centrally ([[24.1 - Building an API Layer]]).

## Unhandled rejections

A rejected promise with no handler anywhere in its chain triggers an `unhandledrejection` event in browsers and, since Node 15, crashes the process.

```js
window.addEventListener("unhandledrejection", event => {
  reportToSentry(event.reason);
  event.preventDefault(); // suppress the console error if you have handled it
});
```

Two subtleties. Attaching a handler *later* in the same tick avoids the warning, but attaching it after a macrotask does not — the rejection has already been reported. And a promise stored without a handler (`const p = fetch(...)`) will report as unhandled even if you `await` it later in a different task.

## Sequential vs parallel

```js
// Sequential — total time is the sum
const a = await getA();
const b = await getB();

// Parallel — total time is the max
const [a, b] = await Promise.all([getA(), getB()]);
```

Chaining independent operations is a silent performance bug. Whenever two awaits do not depend on each other, they should start together ([[04.5 - Promise Combinators]]).

Note that `Promise.all` starts *nothing* — the promises are already running the moment they were created. `Promise.all` only coordinates waiting.

## How senior engineers actually use this

**They centralize error normalization.** One place converts network failures, non-2xx responses and parse errors into a consistent error type with a status, a code and a user-facing message. Everything downstream handles one shape.

**They distinguish expected from unexpected failures.** A 401 triggers a token refresh; a 404 renders an empty state; a 500 reports to monitoring and shows a generic message. Treating all errors identically produces either noisy dashboards or silent data loss.

**They always attach a terminal `.catch` or wrap in `try/catch`.** A dangling promise chain in a click handler is how errors disappear in production.

**They wire `unhandledrejection` to their error reporter.** It is the safety net that catches everything the code forgot.

## Common pitfalls

- Omitting `return` inside a block-bodied `.then`.
- Assuming `fetch` rejects on 404 or 500.
- Putting `.catch` in the middle and accidentally recovering, so downstream code runs with bad data.
- Using `.then(f, g)` and expecting `g` to catch `f`'s errors.
- Awaiting independent operations sequentially.
- Creating a promise, not handling it, and getting an unhandled rejection even though you meant to await it later.

## Interview angle

Expect "how does error handling work in promise chains" and often a snippet asking what a chain outputs when a middle step throws. Cover: rejections skip forward to the nearest rejection handler; `.catch` recovers unless it re-throws; `.then(f, g)` differs from `.then(f).catch(g)`; and `fetch` does not reject on HTTP error status. That last point is the one interviewers use to separate people who have written frontend code from people who have read about it.
