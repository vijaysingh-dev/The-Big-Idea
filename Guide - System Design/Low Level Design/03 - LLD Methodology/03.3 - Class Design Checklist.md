# Class Design Checklist

Use this as a final review before presenting your design. Each section catches a common class of bugs or design gaps.

---

## 1. Entity Design Checklist

For every entity/aggregate:

- [ ] **Identity** — does it have a unique ID? What type? (UUID recommended over auto-increment for distributed systems)
- [ ] **Immutable fields** — what can never change after creation? (e.g., `created_at`, `order_id`)
- [ ] **Mutable fields** — what changes over time? Are setters protected?
- [ ] **Invariants** — what must always be true? Are they enforced in the entity, not the service?
- [ ] **State machine** — does the entity have a lifecycle? Are invalid transitions blocked?
- [ ] **Value Objects** — could Money, Address, PhoneNumber be VOs instead of primitives?
- [ ] **Equals/hash** — based on identity (ID), not attributes
- [ ] **Domain events** — does this entity emit events when something meaningful happens?

```python
# Checklist applied to Order:
class Order:
    id: UUID           # ✅ UUID identity
    created_at: datetime  # ✅ immutable after creation
    _status: OrderStatus  # ✅ private — only changed via confirm/cancel/ship methods
    _total: Money         # ✅ Value Object, not Decimal
    
    def confirm(self):  # ✅ invariant enforced — checks DRAFT status before transitioning
        self._assert_status(OrderStatus.DRAFT)
        self._status = OrderStatus.CONFIRMED
        self._events.append(OrderConfirmed(self.id))
    
    def __eq__(self, other): return self.id == other.id  # ✅ identity-based
```

## 2. Validation Checklist

- [ ] **Input validation** at API boundary — invalid format → 400 before entering domain
- [ ] **Domain validation** in entities/services — business rule violation → domain exception
- [ ] **Cross-entity validation** in domain services — when one entity validates against another
- [ ] **Error messages** are user-friendly and specific (not "validation error")
- [ ] **Fail fast** — validate before expensive operations (don't charge payment then discover invalid address)

```python
# Validation layers
class OrderRequest(BaseModel):  # Pydantic — input validation
    items: List[OrderItemRequest] = Field(..., min_items=1)
    payment_method_id: str = Field(..., min_length=1)

class Order:
    def add_item(self, item):
        if item.quantity <= 0:               # domain validation
            raise DomainError("Quantity must be positive")
        if len(self._items) >= 50:           # domain invariant
            raise DomainError("Max 50 items per order")

class InventoryValidator:
    def validate_availability(self, order, inventory):  # cross-entity
        for item in order.items:
            stock = inventory.available_stock(item.product_id)
            if stock < item.quantity:
                raise InsufficientStockError(item.product_id, stock, item.quantity)
```

## 3. Error Handling Checklist

- [ ] **Domain exceptions** defined — `OrderNotFoundError`, `PaymentDeclinedError`, not generic `Exception`
- [ ] **Exception hierarchy** — base `DomainError`, `InfrastructureError` for separation
- [ ] **No silent failures** — every catch either handles or re-raises
- [ ] **Infrastructure errors wrapped** — DB exceptions don't leak into domain layer
- [ ] **API boundary catches** — controller maps domain exceptions to HTTP status codes
- [ ] **Logging** — errors logged with context (order_id, user_id, operation)
- [ ] **No returning None for not-found** — raise `NotFoundError` or return `Optional` explicitly

```python
# Exception hierarchy
class DomainError(Exception): pass
class OrderNotFoundError(DomainError): pass
class InvalidStateTransition(DomainError): pass
class InsufficientStockError(DomainError):
    def __init__(self, product_id, available, requested):
        super().__init__(f"Product {product_id}: available={available}, requested={requested}")
        self.product_id = product_id
        self.available = available
        self.requested = requested

# API boundary mapping
@app.exception_handler(OrderNotFoundError)
def handle_order_not_found(request, exc):
    return JSONResponse(status_code=404, content={"error": str(exc)})

@app.exception_handler(InsufficientStockError)
def handle_insufficient_stock(request, exc):
    return JSONResponse(status_code=409, 
                       content={"error": "Insufficient stock", 
                                "product_id": str(exc.product_id)})
```

## 4. Idempotency Checklist

For every state-changing operation:

- [ ] **Is it safe to call twice?** If yes, already idempotent. If no:
- [ ] **Idempotency key** accepted from client (for critical operations like payments, order creation)
- [ ] **Deduplication check** — look up by idempotency key before processing
- [ ] **Same response on duplicate** — return same result as first call, don't error
- [ ] **Key stored with result** — in same transaction as the operation

```python
class OrderService:
    def place_order(self, cmd: PlaceOrderCommand) -> Order:
        # Idempotency: check before creating
        existing = self._repo.find_by_idempotency_key(cmd.idempotency_key)
        if existing:
            return existing   # same result, no duplicate processing
        
        order = Order.create(cmd)
        order.idempotency_key = cmd.idempotency_key
        return self._repo.save(order)  # key saved with order atomically
```

## 5. State Management Checklist

- [ ] **State defined explicitly** — enum or state objects, not strings
- [ ] **Transitions explicit** — all allowed transitions documented/enforced
- [ ] **Terminal states identified** — `DELIVERED`, `CANCELLED` — no transitions out
- [ ] **State change emits event** — observable state transitions
- [ ] **Concurrent state changes** — optimistic locking or version check

```python
# State transition table — document all allowed transitions
VALID_TRANSITIONS = {
    OrderStatus.DRAFT:     {OrderStatus.CONFIRMED, OrderStatus.CANCELLED},
    OrderStatus.CONFIRMED: {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID:      {OrderStatus.SHIPPED},
    OrderStatus.SHIPPED:   {OrderStatus.DELIVERED},
    OrderStatus.DELIVERED: set(),   # terminal
    OrderStatus.CANCELLED: set(),   # terminal
}

# Optimistic locking for concurrent modification
class Order:
    version: int = 0  # incremented on each save
    
    # Repository checks version matches before saving
    # If another process updated between load and save → conflict error
```

## 6. Transaction Boundary Checklist

- [ ] **One business operation = one transaction**
- [ ] **Multiple aggregates in one transaction?** → Reconsider boundaries, or use UoW carefully
- [ ] **Events dispatched AFTER commit** — never inside transaction
- [ ] **Non-critical side effects** (email, analytics) — outside transaction, catch exceptions
- [ ] **Long-running operations** — not inside transaction (holds DB locks)

```python
class OrderApplicationService:
    def place_order(self, cmd):
        # Transaction scope: only DB operations
        with self._uow:
            order = Order.create(cmd)
            self._uow.orders.save(order)
            # commit on exit
        
        # After commit: side effects (not in transaction)
        try:
            self._event_bus.publish(order.get_events())
        except Exception as e:
            logger.error(f"Event dispatch failed: {e}")  # don't fail the order
```

## 7. Concurrency Checklist

- [ ] **Shared mutable state** — identified and protected (locks, atomic ops)
- [ ] **Database-level concurrency** — optimistic locking (version) or pessimistic (SELECT FOR UPDATE)
- [ ] **Race conditions** — "check-then-act" patterns reviewed (read-modify-write)
- [ ] **Thread-safety** — Singleton, cache, rate limiter reviewed for thread safety
- [ ] **Deadlock avoidance** — consistent lock ordering when multiple resources locked

```python
# Race condition: two requests check stock simultaneously, both see "1 left", both reserve
# Solution: database-level atomic decrement
inventory_repo.decrement_and_check(
    product_id=item.product_id,
    quantity=item.quantity
)
# SQL: UPDATE inventory SET reserved = reserved + %s 
#       WHERE product_id = %s AND (quantity - reserved) >= %s
# Returns rows_affected — if 0, insufficient stock
```

## 8. Testability Checklist

- [ ] **Core business logic testable without DB** — service uses Repository interface, InMemory impl for tests
- [ ] **Dependencies injected** — no `new ConcreteService()` inside domain classes
- [ ] **Pure functions** identified — deterministic functions extracted for property testing
- [ ] **Domain events** testable — `order.get_events()` returns events for assertion
- [ ] **Clock injectable** — `datetime.now()` abstracted for time-dependent logic

```python
# Injectable clock for testability
class Clock(ABC):
    @abstractmethod
    def now(self) -> datetime: pass

class SystemClock(Clock):
    def now(self): return datetime.now()

class FixedClock(Clock):
    def __init__(self, fixed_time: datetime):
        self._time = fixed_time
    def now(self): return self._time

# Test with fixed time
def test_order_created_at():
    fixed = datetime(2024, 1, 15, 10, 0, 0)
    service = OrderService(repo=InMemoryOrderRepository(), clock=FixedClock(fixed))
    order = service.create_order(cmd)
    assert order.created_at == fixed
```

## 9. Observability Checklist

- [ ] **Log entry and exit** of significant operations with context IDs
- [ ] **Log level appropriate** — DEBUG for detailed trace, INFO for milestones, ERROR for failures
- [ ] **Structured logging** — JSON logs with consistent fields (`order_id`, `user_id`, `operation`)
- [ ] **Metrics emitted** — counters (orders placed), gauges (queue depth), histograms (latency)
- [ ] **Correlation ID** propagated — trace a request across services
- [ ] **Alerting hooks** — threshold for business metrics (payment failure rate > 5% → alert)

```python
# Structured logging example
logger.info("Order placed", extra={
    "order_id": str(order.id),
    "user_id": str(order.user_id),
    "total": str(order.total),
    "item_count": order.item_count,
    "operation": "place_order",
    "correlation_id": get_correlation_id()
})
```

## 10. API Design Checklist

- [ ] **REST resource naming** — nouns, plural: `/orders`, `/users/{id}/orders`
- [ ] **Idempotent HTTP methods** respected — GET/PUT/DELETE are idempotent, POST is not
- [ ] **Response codes** correct — 201 Created, 404 Not Found, 409 Conflict, 422 Unprocessable
- [ ] **Pagination** on list endpoints — cursor or page-based
- [ ] **Versioning** strategy — `/v1/orders` or header-based
- [ ] **Request validation** — 400 for malformed, 422 for semantically invalid
- [ ] **Consistent error format** — `{"error": "...", "code": "ORDER_NOT_FOUND"}`

## Quick Pre-Submission Review (2 min)

Before finishing a design, run through:

```
1. Can I trace a "place order" flow end-to-end through the classes?
2. What happens if the payment service is down?
3. What happens if the same request is sent twice?
4. Can I add a new payment method without touching existing code?
5. Can I write a unit test for core logic without a real DB?
6. Are all state transitions valid and enforced?
7. Does anything need a distributed lock?
```

If you can answer all 7 with confidence, the design is solid.
