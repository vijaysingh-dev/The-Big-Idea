# Profiles

## What a profile is

Every user has exactly one profile. It is mandatory, it is assigned on the user record, and it defines the baseline of what that user can do.

A profile bundles together several unrelated things:

- **Object permissions** — create, read, edit, delete, view all, modify all, per object
- **Field-level security** — visible and read-only, per field
- **System permissions** — org-wide capabilities like Manage Users, Run Reports, API Enabled, View All Data
- **App and tab visibility** — which apps and tabs appear
- **Page layout assignment** — which layout is shown, per object and record type
- **Record type availability** — which record types the user can select
- **Apex class and Visualforce page access**
- **Login hours and login IP ranges**
- **Password policies** (in some cases)

That is a lot of unrelated concerns in one object, and it is the root of the profile problem described below.

## The profile problem

Because a user has exactly one profile, and a profile bundles everything, any variation in requirements forces a new profile.

Sales in Europe needs the same permissions as sales in Asia but a different page layout. That is a second profile. A senior sales user needs one extra system permission. Third profile. A team needs access to one custom object the others do not. Fourth.

Orgs that manage permissions primarily through profiles end up with dozens of them, differing in tiny ways, all needing updating whenever anything changes. Adding a new custom object means editing every profile. Auditing "who can delete Opportunities" means reading every profile. Nobody can safely delete any of them because nobody knows what each is for.

This is why the ecosystem has moved decisively toward permission sets.

## The modern approach

**Assign a minimal profile. Grant everything else through permission sets.**

The profile becomes almost empty: license type, login hours if needed, default layouts, and nothing more. Every actual capability is granted by a permission set or permission set group, assigned per user.

The advantages compound:

- One profile can serve hundreds of users with different capabilities
- A new capability is one permission set, assigned to whoever needs it, rather than an edit to twenty profiles
- Removing a capability from one person is unassigning a permission set, not creating a new profile
- Auditing is possible: "who has Delete on Opportunity" is a query against permission set assignments
- Permission sets can be time-limited, which profiles cannot

Salesforce has stated an intent to move permissions out of profiles entirely over time. Building on permission sets now is aligned with where the platform is going.

## What still lives only on the profile

Not everything has moved yet, which is why profiles cannot be ignored:

- **Page layout assignment** by record type
- **Record type availability and defaults**
- **Login hours and login IP ranges**
- **Default app**
- Some organization-level settings

So the realistic model is: profile handles presentation and login constraints, permission sets handle capability.

## The standard profiles

Every org has a set that cannot be deleted:

**System Administrator** — everything, including View All Data and Modify All Data. Should be held by very few people.

**Standard User** — read, create, edit, delete on standard CRM objects.

**Read Only** — read access only.

**Solution Manager**, **Marketing User**, **Contract Manager** — standard profiles with specific extra permissions.

**Minimum Access - Salesforce** — a deliberately near-empty profile, introduced specifically to support the permission-set-driven model. This is the one to clone as a starting point in a new org.

Standard profiles cannot be edited in most respects. The normal practice is to clone one and modify the clone.

## The permissions that matter most

Two system permissions deserve specific attention because they bypass the entire sharing model.

**View All Data** — read every record of every object, ignoring sharing entirely.
**Modify All Data** — read, edit, and delete every record of every object, ignoring sharing entirely.

These are not "more access". They are an override of the record-level security model. A user with Modify All Data is unaffected by organization-wide defaults, role hierarchy, or sharing rules.

There are also per-object equivalents — **View All** and **Modify All** on a specific object — which are the correct tool when someone genuinely needs full access to one object without org-wide power. A data migration user, or a service that must update every case, should have View All and Modify All on the specific objects, not the org-wide permission.

Other permissions worth watching in an audit: **API Enabled**, **Manage Users**, **Customize Application**, **Author Apex**, **Export Reports**, **Manage Sharing**, **View Encrypted Data**, **Password Never Expires**.

## Profiles as metadata

Profiles deploy as XML, and their behaviour during deployment is a well-known source of pain.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Profile xmlns="http://soap.sforce.com/2006/04/metadata">
    <custom>true</custom>
    <objectPermissions>
        <object>Warranty_Claim__c</object>
        <allowCreate>true</allowCreate>
        <allowRead>true</allowRead>
        <allowEdit>true</allowEdit>
        <allowDelete>false</allowDelete>
        <viewAllRecords>false</viewAllRecords>
        <modifyAllRecords>false</modifyAllRecords>
    </objectPermissions>
    <fieldPermissions>
        <field>Warranty_Claim__c.Approved_Amount__c</field>
        <readable>true</readable>
        <editable>false</editable>
    </fieldPermissions>
    <userPermissions>
        <name>ApiEnabled</name>
        <enabled>true</enabled>
    </userPermissions>
</Profile>
```

The pain point: when you retrieve a profile, the platform only includes permissions for metadata that is *also* in the retrieval. Retrieve a profile alone and you get a nearly empty file. Deploy that file and, depending on the deployment mode, you may wipe permissions that were not included.

This is a real cause of production incidents. The practical rules most teams adopt:

- Retrieve profiles alongside the objects and fields they reference, or use a package manifest that includes both
- Prefer permission sets in source control, since they retrieve completely and deploy predictably
- Review profile diffs in pull requests carefully; a profile diff that removes a hundred lines is usually a retrieval artefact, not an intentional change

See [[21.1 - Metadata, Source of Truth and Deployment Concepts]].

## Querying profiles and permissions

```sql
SELECT Id, Name, UserLicense.Name, PermissionsModifyAllData, PermissionsViewAllData
FROM Profile
ORDER BY Name
```

Object permissions are queryable through `ObjectPermissions`, which covers both profiles and permission sets — the `Parent` relationship distinguishes them:

```sql
SELECT Parent.Profile.Name, Parent.Label, SobjectType,
       PermissionsRead, PermissionsCreate, PermissionsEdit, PermissionsDelete,
       PermissionsViewAllRecords, PermissionsModifyAllRecords
FROM ObjectPermissions
WHERE SobjectType = 'Warranty_Claim__c'
```

That query is the fastest way to answer "who can delete these records", and it is worth keeping.

In Apex, checking the running user's permissions:

```java
if (Schema.sObjectType.Warranty_Claim__c.isDeletable()) {
    delete claims;
}

// System permissions are checked through FeatureManagement or a describe on PermissionSet
Boolean canManageUsers = FeatureManagement.checkPermission('ManageUsers');
```

## Practical guidance

**Clone Minimum Access, not System Administrator.** Starting from a permissive profile and removing permissions means you will miss some.

**One profile per license type and layout requirement, not per team.** If two teams need the same layouts and differ only in capability, they share a profile and differ in permission sets.

**Audit View All Data and Modify All Data quarterly.** These are the permissions that make a data breach possible, and they accumulate.

**Document what each profile is for.** In its description. Orgs routinely contain profiles nobody can explain and nobody dares delete.

**Do not use profiles to control record access.** That is what the sharing model is for. Using View All Data because sharing rules seemed hard is the most common serious security mistake in the ecosystem.
