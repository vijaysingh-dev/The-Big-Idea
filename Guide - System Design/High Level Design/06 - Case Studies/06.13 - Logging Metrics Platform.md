# Case Study: Logging and Metrics Platform

> **Revision tags:** #case-study #observability #logging #metrics  
> **Related:** [[03.19 - Observability Stack]] | [[02.6 - Observability Security Cost]]

---

## Requirements Clarification

**Functional:**
- Ingest logs from thousands of services (structured JSON)
- Ingest metrics (counters, gauges, histograms) from services and infrastructure
- Store logs queryable for 30 days hot, 1 year cold
- Store metrics at full resolution for 15 days, downsampled for 1 year
- Query: full-text log search, metric time-series queries, aggregations
- Alerting: fire when metrics breach thresholds or log patterns match

**Non-functional:**
- Log ingestion: 10M log lines/s, p99 < 1s from emit to searchable
- Metrics ingestion: 1M data points/s
- Query latency: log search < 5s; metric query < 2s
- No data loss: logs and metrics must survive ingestion pipeline failures
- Cost-efficient at scale: 10 TB/day of logs is expensive

**Out of scope:** Distributed tracing (separate system), ML-based anomaly detection

---

## Estimation

```
Logs:
  1000 services × 10K log lines/s each = 10M lines/s
  Average log line: 500 bytes (JSON)
  Ingestion rate: 10M × 500 bytes = 5 GB/s = 18 TB/hour = 432 TB/day

Metrics:
  1M data points/s
  Each data point: ~100 bytes (metric name, labels, value, timestamp)
  Ingestion rate: 100 MB/s = 8.6 TB/day

Storage (30 days hot logs):
  432 TB/day × 30 days = 12.96 PB raw
  After compression (10:1 for structured JSON): ~1.3 PB
  → Requires a distributed columnar store (Elasticsearch cluster or ClickHouse)

Metrics (15 days full resolution):
  8.6 TB/day × 15 days = 129 TB
  → Prometheus + long-term storage (Thanos / VictoriaMetrics)
```

**Key challenges:** 5 GB/s ingestion without backpressure, cost-efficient storage for PB-scale data, sub-5s query over 30 days of logs.

## Architecture

```
[Services / Infra]
    │ emit logs + metrics
    ▼
[Collectors]               (Fluentd / Prometheus agents / OTel Collector)
    │
    ▼
[Kafka]                    (ingestion buffer — absorbs spikes, decouples)
    │
    ├──→ [Log Pipeline]
    │          │
    │     [Log Processor]  (parse, enrich, filter PII, route)
    │          │
    │     [Indexer]        → Elasticsearch / ClickHouse (hot, 30d)
    │          │
    │     [Archiver]       → S3 (cold, 1y, compressed Parquet)
    │
    └──→ [Metrics Pipeline]
               │
          [Prometheus]     (scrape + short-term storage, 15d)
               │
          [Thanos / VM]    (long-term storage, aggregation, 1y)
               │
          [Grafana]        (dashboards, alerting)
```

## Log Ingestion Pipeline

### Why Kafka in the Middle?

Without Kafka:
```
10M lines/s → Elasticsearch directly → ES can't keep up during spikes → data loss
```

With Kafka:
```
10M lines/s → Kafka (durably stored) → Elasticsearch at its own pace
             (absorbs spike)          (backpressure handled by Kafka retention)
```

Kafka provides:
- Durable buffer (configurable retention: 24h of logs if ES is slow)
- Replay (re-index if Elasticsearch needs rebuilding)
- Fan-out (same log stream to multiple consumers: hot storage, cold archive, alerting)

### Log Processor

Before indexing, logs pass through a processing stage:

```python
def process_log_batch(logs: List[dict]) -> List[dict]:
    result = []
    for log in logs:
        # 1. Parse if not already JSON
        if isinstance(log, str):
            log = json.loads(log)

        # 2. Normalize timestamp to UTC
        log['@timestamp'] = parse_timestamp(log.get('timestamp'))

        # 3. Enrich with metadata
        log['host'] = resolve_hostname(log.get('host'))
        log['environment'] = get_env(log.get('service'))

        # 4. Filter PII (GDPR compliance)
        log = redact_pii(log)   # mask emails, phone numbers, card numbers

        # 5. Route: error logs get indexed immediately (high priority)
        if log.get('level') == 'ERROR':
            log['_index'] = 'logs-errors-hot'
        else:
            log['_index'] = 'logs-general-hot'

        result.append(log)
    return result
```

### Elasticsearch Index Design

```
Daily indices (partition by date for efficient deletion):
  logs-2024-01-15
  logs-2024-01-16
  ...

After 30 days: delete (or move to cold tier → S3)
ILM (Index Lifecycle Management): automates this
```

```json
{
  "mappings": {
    "properties": {
      "@timestamp":  { "type": "date" },
      "level":       { "type": "keyword" },
      "service":     { "type": "keyword" },
      "message":     { "type": "text" },
      "trace_id":    { "type": "keyword" },
      "host":        { "type": "keyword" },
      "duration_ms": { "type": "integer" }
    }
  }
}
```

**Dynamic mapping disabled:** Enforce schema so arbitrary fields don't bloat the mapping. Unknown fields go to a generic `extra` object field.

## Cold Storage: S3 + Parquet

Logs older than 30 days are too expensive to keep in Elasticsearch. Archive to S3 in columnar format.

```
Log Archiver (Kafka consumer):
  Accumulate 1 hour of logs in memory
  Convert to Apache Parquet format (columnar, 10-20× compression over JSON)
  Write to S3: s3://logs-archive/year=2024/month=01/day=15/hour=10/service=payment/*.parquet
  Delete from in-memory buffer

Queries against archived logs:
  Use AWS Athena (serverless SQL over S3)
  SELECT * FROM logs WHERE service = 'payment' AND level = 'ERROR'
    AND timestamp > '2024-01-01' AND timestamp < '2024-01-31'
  → Athena reads only relevant Parquet files (partition pruning)
  → ~$5 per TB scanned vs thousands of dollars for Elasticsearch at that scale
```

**Cost comparison:**
- Elasticsearch: ~$0.25/GB/month → 1.3 PB × $0.25 = $325K/month
- S3 + Athena: ~$0.023/GB/month storage + query costs → ~$30K/month

Cold storage for old logs saves ~10×.

## Metrics Pipeline

### Prometheus Architecture

Prometheus pulls (scrapes) metrics from services:

```
Every 15 seconds:
  Prometheus → GET http://payment-service:8080/metrics
  Parses Prometheus format:
    # HELP http_requests_total Total HTTP requests
    http_requests_total{method="POST", status="200"} 48291
    http_requests_total{method="POST", status="500"} 23
```

Prometheus stores metrics in a local TSDB (time-series database) with 15-day retention.

### Long-Term Storage: Thanos / VictoriaMetrics

For metrics beyond 15 days, and for multi-Prometheus federation:

```
Thanos Sidecar: runs alongside each Prometheus
  - Uploads Prometheus data blocks to S3 every 2 hours
  - Allows querying Prometheus data via Thanos Query

Thanos Query: federated query layer
  - Aggregates results from multiple Prometheus + S3 archives
  - Deduplicates (multiple Prometheus instances scraping same targets)

Thanos Compactor:
  - Downsamples old data (5-min resolution after 30 days, 1-hour after 1 year)
  - Reduces storage cost for historical metrics
```

### Metric Downsampling

Storing every 15-second sample for 1 year is expensive and usually unnecessary:

```
0–30 days:   15-second resolution (full fidelity, for recent debugging)
30–90 days:  5-minute resolution  (4× compression)
90+ days:    1-hour resolution    (20× compression, for trend analysis)
```

ClickHouse as alternative: some companies (Cloudflare, Uber) use ClickHouse for metrics because its columnar storage achieves better compression and query performance for time-series aggregations.

## Alerting Pipeline

```
[Prometheus Alertmanager]
  Rules: alert when metric breaches threshold
  
  Example rule:
    - alert: HighErrorRate
      expr: rate(http_requests_total{status=~"5.."}[5m]) /
            rate(http_requests_total[5m]) > 0.01
      for: 2m
      labels: { severity: critical }
      annotations:
        summary: "Error rate > 1% for {{ $labels.service }}"

  When alert fires:
    → Send to PagerDuty (P1), Slack (P2), Email (P3)
    → Deduplicate: same alert firing multiple times → one notification
    → Silence: suppress during known maintenance windows

[Log-based alerting] (Elasticsearch → ElastAlert or Grafana)
  Rule: "more than 10 ERROR logs from payment-service in 1 minute"
  → Same routing as metric alerts
```

## Query Experience

### Log Search (Kibana / Grafana Loki)

```
Query: "payment-service errors in last 1 hour"
  service:payment AND level:ERROR AND @timestamp:[now-1h TO now]

Result: paginated log lines with highlighting
  2024-01-15 10:23:45 ERROR payment-service "payment_charge_failed"
    order_id=ord_4421, error=timeout, duration_ms=2001
```

### Metric Query (Grafana + PromQL)

```
Query: "p99 latency of payment service over last 24 hours"
PromQL: histogram_quantile(0.99,
          rate(http_request_duration_seconds_bucket{
            service="payment-service"
          }[5m])
        )
```

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Elasticsearch indexer slow | Kafka lag grows | Auto-scale indexers; alert on lag > 5 min |
| Kafka broker down | Producers see write errors | Kafka replication (RF=3); producers retry |
| Prometheus down | Metrics gap | Multiple Prometheus instances (one per AZ); Thanos merges |
| S3 upload fails (archiver) | Logs not archived | Retry with exponential backoff; alert if lag > 2 hours |
| ES disk full | Indexing stops | ILM auto-deletes old indices; alert at 70% disk |
| Alert storm | On-call buried in noise | Alertmanager deduplication + grouping; route by severity |

---

## What This Design Demonstrates

- Kafka as an ingestion buffer that decouples producers from slow consumers
- Daily ES index rotation for efficient TTL management
- S3 + Parquet + Athena for cost-efficient cold log storage (10× savings)
- Prometheus pull model vs push: no service discovery needed at ES
- Downsampling as a cost optimization for long-term metrics
- Alertmanager deduplication to prevent alert storms
