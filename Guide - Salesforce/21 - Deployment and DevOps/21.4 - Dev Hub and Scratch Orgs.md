# Dev Hub and Scratch Orgs

## What a scratch org is

A **disposable, source-driven org** created from a definition file, used for days, and deleted.

The contrast with a sandbox is the point:

| | Sandbox | Scratch Org |
| --- | --- | --- |
| Created from | A copy of production | A definition file |
| Lifetime | Until refreshed | 1 to 30 days |
| Refresh interval | 1 to 29 days by type | Not applicable — recreate |
| Data | Copied, or none | Seeded by script |
| Configuration | Whatever production has | Exactly what you declared |
| Source tracking | Developer Pro and below | Yes |
| Cost | Licensed allocation | Dev Hub allocation |

**A scratch org is built from your repository.** If the repository is incomplete, the scratch org is broken — which is uncomfortable and is exactly the feedback that keeps a repository honest.

## Enabling the Dev Hub

```
Setup → Dev Hub → Enable Dev Hub
```

Enabled in **production** normally, or in a Developer Edition org for a team without production access. It is irreversible, and it does not affect anything else in the org.

```bash
sf org login web --alias my-devhub --set-default-dev-hub
sf config set target-dev-hub=my-devhub
```

**Allocations depend on edition:**

```
Enterprise      typically 40 active, 80 per day
Unlimited       typically 100 active, 200 per day
Performance     similar to Unlimited
```

"Active" is the constraint that bites — a team that never deletes scratch orgs hits it in a fortnight.

## The definition file

```json
{
  "orgName": "Northwind Development",
  "edition": "Enterprise",
  "features": [
    "EnableSetPasswordInApi",
    "PersonAccounts",
    "ServiceCloud",
    "AuthorApex",
    "DebugApex",
    "Communities",
    "PlatformCache:5",
    "MultiCurrency"
  ],
  "settings": {
    "lightningExperienceSettings": {
      "enableS1DesktopEnabled": true
    },
    "securitySettings": {
      "passwordPolicies": {
        "enableSetPasswordInApi": true
      }
    },
    "caseSettings": {
      "systemUserEmail": "support@northwind.com"
    },
    "experienceBundleSettings": {
      "enableExperienceBundleMetadata": true
    }
  }
}
```

**The definition file is the org's configuration as code**, which is the substantive advantage over sandboxes — the org's shape is versioned, reviewable, and reproducible.

**`features`** enable capabilities: `PersonAccounts`, `Communities`, `MultiCurrency`, `StateAndCountryPicklist`, `ContactsToMultipleAccounts`, and many more. Some take a quantity — `PlatformCache:5` allocates 5 MB.

**`settings`** configure org preferences that would otherwise be manual clicks.

Getting the file right takes iteration, and it is worth the effort: a missing feature produces a deployment failure whose message rarely names the feature.

## Creating and using

```bash
sf org create scratch \
  --definition-file config/project-scratch-def.json \
  --alias feature-claims \
  --duration-days 7 \
  --set-default

sf project deploy start --source-dir force-app --target-org feature-claims
sf data import tree --plan data/seed-plan.json --target-org feature-claims
sf apex run --file scripts/apex/scratch-setup.apex --target-org feature-claims

sf org open --target-org feature-claims

sf org delete scratch --target-org feature-claims --no-prompt
```

**`--duration-days` defaults to 7 and maxes at 30.** An expired scratch org is deleted automatically, which is a feature — it forces the work to be committed.

**Wrap the whole sequence in a script**, because it will be run several times a week:

```bash
#!/bin/bash
set -e

ALIAS=${1:-scratch}

sf org create scratch --definition-file config/project-scratch-def.json \
  --alias "$ALIAS" --duration-days 7 --set-default
sf project deploy start --source-dir force-app --target-org "$ALIAS"
sf apex run --file scripts/apex/scratch-setup.apex --target-org "$ALIAS"
sf data import tree --plan data/seed-plan.json --target-org "$ALIAS"
sf org assign permset --name Claim_Access --target-org "$ALIAS"
sf org open --target-org "$ALIAS"
```

**A scratch org that takes fifteen manual minutes to set up is a scratch org nobody creates.** The script is what makes the model work.

## Source tracking

The capability that changes the workflow.

```bash
# What differs between the org and local source
sf project retrieve preview --target-org feature-claims
sf project deploy preview --target-org feature-claims

# Pull org changes into local source
sf project retrieve start --target-org feature-claims

# Push local changes to the org
sf project deploy start --target-org feature-claims

# Reset when tracking gets confused
sf project reset tracking --target-org feature-claims
```

**No manifest needed.** Change a field in the org's UI, run retrieve, and the file appears locally. Change a class locally, run deploy, and it lands.

That loop — configure in the UI, retrieve, commit — is what makes declarative work reviewable, and it does not exist in production or full sandboxes.

## Seeding data

A scratch org has no data.

**`data import tree`** for reference and small related sets:

```bash
sf data export tree \
  --query "SELECT Id, Name, BillingCountry, (SELECT Id, Name, SerialNumber FROM Assets) FROM Account LIMIT 20" \
  --prefix seed --output-dir data --target-org production

sf data import tree --plan data/seed-Account-plan.json --target-org feature-claims
```

**200 records per file**, and relationships are resolved at import. Right for reference data, wrong for volume.

**Anonymous Apex** for anything requiring logic:

```java
// scripts/apex/scratch-setup.apex
insert new Automation_Settings__c(
    SetupOwnerId = UserInfo.getOrganizationId(),
    Disable_All_Automation__c = false
);

List<Account> accounts = new List<Account>();
for (Integer i = 0; i < 20; i++) {
    accounts.add(new Account(Name = 'Northwind Customer ' + i, BillingCountry = 'India'));
}
insert accounts;

// generating volume in code beats maintaining a large data file
List<Asset> assets = new List<Asset>();
for (Account account : accounts) {
    for (Integer i = 0; i < 5; i++) {
        assets.add(new Asset(
            AccountId = account.Id,
            Name = 'Press P400',
            SerialNumber = 'SN-' + account.Id + '-' + i,
            Status = 'Installed'
        ));
    }
}
insert assets;
```

**This is where Custom Setting records get created**, since they do not deploy and every scratch org starts without them. See [[17.2 - Custom Settings]].

**SFDMU** for complex hierarchical data:

```bash
sf sfdmu run --sourceusername production --targetusername feature-claims --path data/
```

It resolves relationships by external ID across several objects, which `import tree` cannot do at scale. See [[21.11 - Sandbox Strategy and Data Seeding]].

## Where scratch orgs do not fit

Being direct, because the model has real gaps.

**No production data.** A performance problem that only appears at eight million rows is invisible. Query selectivity, skew, and lock contention need a full sandbox. See [[16.9 - Skinny Tables and Custom Indexes]].

**Managed packages must be installed each time**, which adds minutes to creation and occasionally fails:

```bash
sf package install --package 04t5g000000ABCDeAA --target-org feature-claims --wait 20
```

**An incomplete repository produces a broken org.** In a mature org where much configuration was never retrieved, the scratch org will not work — and fixing that is the real cost of adoption.

**Some features are unavailable** in scratch orgs, or behave differently — certain Experience Cloud configurations, some licensing-dependent features, and Shield capabilities.

**Not suitable for UAT.** Business users testing against synthetic data in a 7-day org is not user acceptance testing.

## Scratch orgs versus sandboxes

The practical division most teams settle on:

```
Scratch org        feature development, unit testing, CI validation, demos
Developer sandbox  work needing production metadata that is not in the repository
Partial sandbox    integration testing with representative data
Full sandbox       UAT, performance testing, and release rehearsal
```

**Scratch orgs for building; sandboxes for validating against reality.** Neither replaces the other, and an org using only sandboxes has no forcing function keeping the repository complete.

## In CI

```yaml
- name: Create scratch org
  run: |
    sf org login jwt --client-id ${{ secrets.DEVHUB_CLIENT_ID }} \
      --jwt-key-file server.key --username ${{ secrets.DEVHUB_USERNAME }} \
      --alias devhub --set-default-dev-hub

    sf org create scratch --definition-file config/project-scratch-def.json \
      --alias ci --duration-days 1 --wait 10

- name: Deploy and test
  run: |
    sf project deploy start --source-dir force-app --target-org ci
    sf apex run test --test-level RunLocalTests --code-coverage --wait 30 --target-org ci

- name: Clean up
  if: always()
  run: sf org delete scratch --target-org ci --no-prompt
```

**A scratch org per pull request** validates against a clean org — no residue from previous work, no configuration drift.

**`if: always()` on the cleanup** matters. A failed pipeline that leaves the org behind exhausts the active allocation within days, and then every subsequent build fails for an unrelated reason.

Creation takes two to five minutes, which is the main cost of this approach and usually acceptable.

## Managing the allocation

```bash
sf org list --all
sf org list --clean --no-prompt   # removes expired org entries locally
```

```sql
SELECT SignupUsername, Status, ExpirationDate, CreatedBy.Name, Description
FROM ActiveScratchOrg ORDER BY ExpirationDate
```

Run against the Dev Hub, that query shows who is holding orgs.

**Practices that keep the allocation available:**

**Short durations.** One day for CI, seven for feature work.

**Delete when finished**, rather than waiting for expiry.

**`if: always()` cleanup** in every pipeline.

**A scheduled sweep** for orphaned orgs in a large team.

## Scratch org snapshots

For an org where creation is slow — several managed packages, substantial seeding — a **snapshot** captures a configured scratch org as a template.

```bash
sf org create snapshot --source-org configured-org --name northwind-base \
  --description "Base org with packages and seed data" --target-dev-hub my-devhub

sf org create scratch --snapshot northwind-base --alias feature-x --duration-days 7
```

Creation from a snapshot takes seconds rather than minutes.

**The snapshot must be recreated when the base changes**, which is the maintenance cost. Worth it when creation exceeds five minutes; unnecessary below that.

## Practical guidance

**Script the entire creation sequence**, or nobody will use scratch orgs.

**Version the definition file** — it is the org's configuration as code.

**Seed with anonymous Apex** for anything needing logic, including Custom Settings.

**Use short durations** and delete explicitly.

**Always clean up in CI**, including on failure.

**Use full sandboxes for performance and UAT** — scratch orgs cannot represent production volume.

**Expect an incomplete repository to break the scratch org**, and treat that as the useful signal it is.

**Consider snapshots** when creation exceeds five minutes.
