# Forms and Native Input Behavior

Forms carry more built-in behavior than any other part of HTML — labeling, validation, submission, autofill, keyboard handling, mobile keyboards. Most of it is discarded by frameworks that rebuild forms from scratch, usually worse.

## Labels

Every input needs an accessible name. There are four ways, in descending order of preference:

```html
<label for="email">Email</label>
<input id="email" type="email">

<label>Email <input type="email"></label>   <!-- implicit, no id needed -->

<input aria-labelledby="emailHeading">
<input aria-label="Email">                  <!-- last resort, invisible label -->
```

A correctly associated `<label>` does something `aria-label` cannot: clicking it focuses the input, and for checkboxes and radios it expands the hit target substantially — a real usability win on mobile.

Placeholder text is not a label. It disappears on focus, fails contrast requirements in most implementations, and is not reliably announced.

## Input types

The `type` attribute controls validation, the mobile keyboard, and the UI affordance:

```html
<input type="email">     <!-- @ keyboard, format validation -->
<input type="tel">       <!-- numeric keypad, no validation -->
<input type="url">
<input type="number">    <!-- spinner, numeric only -->
<input type="search">    <!-- clear button, "search" key -->
<input type="date">      <!-- native date picker -->
<input type="password">  <!-- masked, triggers password manager -->
<input type="file" accept="image/*" multiple>
```

`type="number"` is a common mistake for things that are digit strings rather than quantities — phone numbers, OTP codes, credit cards, postal codes. It strips leading zeros, allows `e` and `-`, and scroll-wheel changes the value accidentally. Use `type="text"` with `inputmode`:

```html
<input type="text" inputmode="numeric" pattern="[0-9]*" autocomplete="one-time-code">
```

`inputmode` controls the mobile keyboard without changing validation semantics: `numeric`, `decimal`, `tel`, `email`, `url`, `search`.

## Autocomplete

```html
<input autocomplete="email">
<input autocomplete="new-password">
<input autocomplete="current-password">
<input autocomplete="one-time-code">
<input autocomplete="street-address">
<input autocomplete="cc-number">
```

The spec defines dozens of tokens. Getting these right is one of the cheapest UX improvements available — correct tokens let browsers and password managers fill an address form in one tap. `autocomplete="off"` on a login form is user-hostile and is ignored by most browsers anyway.

`autocomplete="one-time-code"` enables OTP autofill from SMS on iOS and Android, which matters for any Indian product using phone-based auth.

## Native validation

```html
<form novalidate>
  <input
    type="email"
    required
    minlength="5"
    maxlength="100"
    pattern="[^@]+@[^@]+\.[a-z]{2,}"
    title="Enter a valid email address"
  >
</form>
```

The Constraint Validation API exposes this to JavaScript:

```js
input.validity.valueMissing;
input.validity.typeMismatch;
input.validity.patternMismatch;
input.validity.tooShort;
input.checkValidity();          // returns boolean, fires invalid event
input.reportValidity();         // also shows the browser's message
input.setCustomValidity("This email is already registered");
```

Native validation messages cannot be styled and are not localized to your app's language settings, which is why most production apps use `novalidate` on the form and render their own messages — while still using the `validity` API to drive them. The CSS pseudo-classes remain useful either way:

```css
input:invalid { border-color: red; }
input:user-invalid { border-color: red; }   /* only after interaction */
```

`:user-invalid` is the one you want — `:invalid` marks empty required fields as invalid before the user has typed anything.

## Submission

```html
<form action="/search" method="get">
  <input name="q">
  <button type="submit">Search</button>
</form>
```

Native submission gives you: Enter-to-submit from any input, the implicit submit button, disabled-state handling, and the `submit` event.

```js
form.addEventListener("submit", (e) => {
  e.preventDefault();
  const data = Object.fromEntries(new FormData(form));
  send(data);
});
```

`FormData` collects all named controls automatically, handles files, and supports multiple values for the same name (`formData.getAll("tags")`). It is significantly less code than reading each input by ref.

Two attributes worth knowing:

- **`<button>` defaults to `type="submit"`** inside a form. A button meant for something else needs `type="button"` — forgetting this causes accidental submissions and is a very common bug.
- **`formaction` and `formmethod`** on a button override the form's, letting one form have "Save" and "Save and publish" buttons.

## Grouping

```html
<fieldset>
  <legend>Shipping address</legend>
  <input name="line1">
  <input name="city">
</fieldset>
```

`<fieldset>` and `<legend>` group related controls, and screen readers announce the legend as context for each control inside. This is the correct wrapper for radio groups — without it, the group has no accessible name.

## Controlled inputs in React

```jsx
<input value={value} onChange={e => setValue(e.target.value)} />
```

Two things this breaks that native inputs handle:

**IME composition.** For languages using an input method editor — Chinese, Japanese, Korean, and Indic scripts using phonetic input — intermediate composition states fire `change` events. Controlled inputs that transform the value mid-composition corrupt the input. Guard with composition events:

```jsx
const [composing, setComposing] = useState(false);

<input
  value={value}
  onChange={e => setValue(e.target.value)}
  onCompositionStart={() => setComposing(true)}
  onCompositionEnd={e => { setComposing(false); commit(e.target.value); }}
/>
```

**Cursor position.** Reformatting the value in `onChange` — inserting thousand separators, uppercasing — moves the caret to the end. Preserving it requires manual `setSelectionRange` in a layout effect.

Both are arguments for uncontrolled inputs where you do not need per-keystroke state ([[16.8 - Controlled vs Uncontrolled Components]]), which is exactly React Hook Form's design ([[21.3 - React Hook Form]]).

## Accessible error messaging

```html
<label for="email">Email</label>
<input
  id="email"
  aria-invalid="true"
  aria-describedby="email-error"
>
<p id="email-error" role="alert">Enter a valid email address</p>
```

`aria-describedby` links the message to the input so it is announced on focus; `role="alert"` announces it immediately when it appears. Errors shown only as red borders are invisible to screen reader users and to many users with colour vision deficiency.

## How senior engineers actually use this

**They start from native form behavior and add only what is missing.** Enter-to-submit, autofill and validation state come free; reimplementing them is work that produces a worse result.

**They get `autocomplete` and `inputmode` right on every field.** It is a few attributes and it measurably improves completion rates on mobile.

**They use `FormData` for submission** rather than tracking every field in state, unless per-keystroke reactivity is genuinely needed.

**They test with a keyboard only.** Tab through the form, submit with Enter, trigger an error. Most form bugs surface within thirty seconds of doing this.

## Common pitfalls

- Placeholder used as a label.
- `type="number"` for phone numbers, OTPs and card numbers.
- `<button>` inside a form without `type="button"`, submitting unexpectedly.
- `:invalid` styling firing before the user has typed.
- Missing `<fieldset>`/`<legend>` around radio groups.
- Errors conveyed by colour alone, with no `aria-describedby`.
- Controlled inputs breaking IME composition for non-Latin scripts.

## Interview angle

Form questions tend to be practical — "how would you build an accessible form", "controlled vs uncontrolled". Lead with what the platform provides: label association, input types driving mobile keyboards, autocomplete tokens, the Constraint Validation API, and `FormData`. Then explain when you override it and why. The IME and cursor-position issues with controlled inputs are strong details, especially for products with a non-English user base.
