# Before-Save vs After-Save Flows

## The performance difference is not marginal

A before-save flow that sets a field on the triggering record is roughly **ten times faster** than an after-save flow doing the same thing.

The reason is structural. A before-save flow modifies the record while it is in memory, before it is written. No DML, no second save, no re-entry into the order of execution.

An after-save flow updating its own triggering record must issue an Update, which saves the record **again** — running validation rules again, before-triggers again, after-triggers again, and every other flow again.

That is not a small inefficiency. It is doubling the work of the entire save pipeline for something that could have been an in-memory assignment.

## What each can do

| | Before-save | After-save |
| --- | --- | --- |
| Set fields on the triggering record | Yes, no DML | Yes, requires an Update |
| Create related records | No | Yes |
| Update related records | No | Yes |
| Delete records | No | Yes |
| Send email | No | Yes |
| Call an action or Apex | Limited | Yes |
| Access the record's Id on insert | No | Yes |
| Scheduled paths | No | Yes |
| Query records | Yes | Yes |

The dividing line: **before-save modifies the record itself; after-save does everything else.**

## The Id problem

On insert, a before-save flow runs before the record has an Id. Anything needing the Id — creating a child record, setting a self-reference, logging the record key — must be after-save.

On update the Id exists, so this only constrains insert scenarios.

## When to use before-save

Any assignment of a value onto the triggering record:

- Defaulting a field from another field on the same record
- Stamping a value from a parent record
- Normalizing data — trimming whitespace, uppercasing a code, formatting a phone number
- Setting a status or category derived from other fields
- Copying a value that must be filterable and therefore cannot be a formula

That last one is the pattern worth naming. A formula field is not indexed and does not perform when filtered at volume ([[06.4 - Cross-Object Formulas and Limits]]). A before-save flow writing the same derived value into a real field gives you an indexable, filterable, reportable field at almost no cost.

```
Start: Record-Triggered on Warranty_Claim__c
       Before Save, Created and Updated

Assignment:
    {!$Record.Search_Key__c} = UPPER(TRIM({!$Record.Serial_Number__c}))
    {!$Record.Region__c} = {!$Record.Account__r.BillingCountry}
    {!$Record.Is_High_Value__c} = {!$Record.Claim_Amount__c} > 500000
```

No DML, no second save, and `Search_Key__c` can be marked as an external ID and indexed.

## When to use after-save

Anything touching another record or the outside world:

- Creating a task, a child record, or a log entry
- Updating a parent or related record
- Sending an email or a custom notification
- Publishing a platform event
- Calling invocable Apex that does DML or a callout
- Scheduling a future path

## The self-update anti-pattern

The most common flow performance problem in the wild:

```
After-Save flow on Case
    Get Records: the Case that triggered it
    Assignment: set a field
    Update Records: the same Case
```

This saves the case a second time, re-running every validation rule, every trigger, and every other flow. On a high-volume object with several automations, the cost compounds badly, and it can produce recursion if another flow reacts to the update.

Every instance of this should be a before-save flow. Auditing an org for after-save flows that update `$Record` is one of the highest-return performance exercises available, and it usually finds several.

## Where they sit in the pipeline

From [[07.13 - Order of Execution]]:

```
3.  System validation
4.  Before-save record-triggered flows      ← in-memory, no DML
5.  Before triggers
6.  Custom validation rules
7.  Record saved, not committed
8.  After triggers
9.  Assignment rules
10. After-save record-triggered flows       ← DML re-enters the pipeline
11. Escalation rules
12. Roll-up summaries recalculate
13. Sharing recalculation
14. Commit, then post-commit logic
```

Two things follow.

**Before-save flows run before validation rules.** A before-save flow can populate a field that a validation rule requires, and the validation will pass. This is genuinely useful — defaults that satisfy invariants.

**After-save flows run after triggers.** A field set by an Apex after-trigger is visible to the after-save flow. A field set by an after-save flow is *not* visible to that trigger, because it already ran. Ordering assumptions between flows and triggers are the source of a specific and confusing class of bug.

## Interaction with Apex triggers

Both a before-save flow and a before trigger can modify the same record. The flow runs first.

If both set the same field, the trigger wins, because it runs later. Nobody intends this, and it surfaces as "the flow is not working" when the flow is working perfectly and being overwritten.

This is why the guidance in [[07.1 - Automation Landscape and Tool Selection]] matters: **one mechanism per concern per object.** Flows and triggers may coexist on an object; they should not both write the same field.

## A migration worth doing

Many orgs carry after-save flows that were converted from Process Builder, which had no before-save equivalent. Every one of those doing nothing but same-record field updates should become a before-save flow.

The conversion is usually straightforward: change the timing, remove the Get Records and Update Records elements, and assign directly to `$Record`.

Finding candidates:

```sql
SELECT Id, ApiName, Label, TriggerType, ProcessType, LastModifiedDate
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerType = 'RecordAfterSave'
ORDER BY ApiName
```

Then inspect each for whether it does anything beyond updating its own record. The ones that do not are pure win to convert.

## Practical guidance

**Default to before-save.** Move to after-save only when the work genuinely requires it.

**Never update `$Record` from an after-save flow.** It is always a before-save flow in disguise.

**Use before-save to write filterable copies of formula values.**

**Remember before-save runs before validation rules** — useful for defaults, and a reason validation rules cannot assume a field was empty.

**Do not have a flow and a trigger writing the same field.** The trigger wins, silently.

**Audit existing after-save flows** for self-updates. It is a common and cheap performance improvement.
