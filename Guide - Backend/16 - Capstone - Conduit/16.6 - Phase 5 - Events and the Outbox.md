# Phase 5: Events and the Outbox

#backend #project #capstone

> **In one line:** The moment you have two services and a search index, dual writes start losing data — and the outbox is the only fix that survives a crash between the commit and the publish.

---

## The Problem Phase 4 Created

```python
async with conn.transaction():
    doc = await repo.create(data)
await kafka.send("document.created", event)     # ← crash here: the event is lost
```

⚠️ **There is no transaction spanning Postgres and Kafka.** A crash between them leaves a document that exists with an event that never fired — **and the search index never learns about it.**

💡 **You also now have four consumers wanting the same events**, and a task queue cannot serve them — a queue consumes destructively ([[09.1 - Queue vs Log]]).

---

## What You Build

### The outbox

```sql
CREATE TABLE outbox (
    id             bigserial PRIMARY KEY,
    aggregate_type text NOT NULL,
    aggregate_id   uuid NOT NULL,
    org_id         uuid NOT NULL,
    event_type     text NOT NULL,
    payload        jsonb NOT NULL,
    trace_context  jsonb,
    created_at     timestamptz NOT NULL DEFAULT now()
);
```

```python
async with conn.transaction():
    doc = await repo.create(data)
    await conn.execute(
        "INSERT INTO outbox (aggregate_type, aggregate_id, org_id, event_type, payload, trace_context) "
        "VALUES ('document', $1, $2, 'document.created', $3, $4)",
        doc.id, org_id, payload, trace_carrier(),
    )
```

💡 **The event and the data commit together or not at all.** If the document exists, the event exists ([[09.3 - The Outbox Pattern]]).

⚠️ **Store the trace context in the row.** The relay runs later, in another process, with no ambient context — **the row must carry it or your trace splits** ([[12.3 - Instrumenting Conduit End to End]]).

### The relay, via CDC

```json
{
  "name": "conduit-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "table.include.list": "public.outbox",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregate_type",
    "transforms.outbox.table.field.event.key": "aggregate_id"
  }
}
```

💡 **Debezium reads the WAL, so there is no polling, no lag under load, and no extra query traffic** ([[09.4 - Change Data Capture]]).

⚠️ **The replication slot is the danger.** If Debezium stops, WAL accumulates until the primary's disk fills.

```sql
ALTER SYSTEM SET max_slot_wal_keep_size = '100GB';
```

**This converts "the primary dies" into "the connector needs resyncing", which is enormously preferable** ([[06.7 - MVCC Vacuum and Bloat]]).

**Alert on any inactive slot, immediately.**

### The topics

```
documents          key = document_id   90-day retention
document-events    key = document_id   30 days
annotations        key = document_id   30 days
org-config         key = org_id        compacted, infinite
```

💡 **The partition key determines ordering.** Keying by `document_id` means all events for one document are ordered; events across documents are not ([[09.1 - Queue vs Log]]).

⚠️ **90-day retention on `documents` is the decision that makes index rebuilds possible** — and it is the reason Kafka is here rather than Redis Streams ([[09.8 - Kafka Recap and Where It Fits]]).

### The consumers

```python
async def handle(msg):
    ctx = extract_trace(msg.headers)
    with tracer.start_as_current_span("index.upsert", context=ctx):
        async with conn.transaction():
            claimed = await conn.fetchval(
                "INSERT INTO processed_messages (message_id, consumer) VALUES ($1, $2) "
                "ON CONFLICT DO NOTHING RETURNING message_id",
                msg.key_and_offset(), "search-indexer",
            )
            if claimed is None:
                duplicate_messages_total.inc()
                return
            await apply(msg)
    await consumer.commit()
```

⚠️ **Ack after the transaction commits, never before.** Committing the offset first means a crash loses the message ([[07.5 - Idempotency Keys and Deduplication]]).

💡 **The dedup marker and the effect are in one transaction.** A crash anywhere leaves a consistent state.

| Consumer | Purpose | Replayable? |
|---|---|---|
| search-indexer | Maintains the index | **Yes — the whole point** |
| analytics | Aggregates usage | Yes |
| **notifier** | Sends emails | **No — separate consumer, never replayed** |
| audit | Append-only log | Yes |

⚠️ **The notifier is a separate consumer specifically so it can never be replayed.** A replay flag can be forgotten; a consumer that does not participate in replays cannot send a month of emails ([[09.7 - Replay Backfill and Reprocessing]]).

### Schema discipline, without a registry

```json
{"type": "document.created", "version": 2, "occurred_at": "...", "data": {...}}
```

```python
def to_current(record: dict, version: int) -> DocumentCreated:
    if version < 2:
        record["index_version"] = "v1"
    return DocumentCreated(**record)
```

💡 **A version envelope plus upcasting plus a CI schema diff gives most of a registry's benefit** at a fraction of the operational cost ([[09.6 - Schema Registry and Compatibility]]).

⚠️ **Write down the trigger for adding a registry: a second team consuming these events.**

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Outbox** | Dual write | Dual writes lose events. Measured |
| **CDC relay (Debezium)** | Polling relay | No lag under load, no query traffic |
| **Kafka** | Redis Streams | 90-day retention for index rebuilds ([[09.8 - Kafka Recap and Where It Fits]]) |
| **Key by `document_id`** | By `org_id` | Per-document ordering is what matters |
| **Version envelope** | Schema Registry | One team, four event types |
| **Separate notifier consumer** | A replay flag | Cannot be forgotten |
| Offsets committed after the transaction | Auto-commit | At-least-once, no loss |

⚠️ **The Kafka decision must cite a number.** Compute the memory Redis Streams would need for 90 days of your event volume — **that figure is usually what decides it.**

## What Will Go Wrong

### Dual writes lose events, measurably

**Before building the outbox, measure the naive version:**

```
Kill the process between commit and publish, 1,000 times
→ count events lost
```

💡 **That number is the entire justification for the outbox**, and having it makes the ADR concrete.

### The replication slot fills the disk

⚠️ **Stop Debezium under write load and watch `pg_wal` grow.**

```sql
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;
```

**This is the highest-severity failure in the whole phase.** Reproduce it, then bound it.

### The trace splits at the broker

⚠️ **Without the trace context in the outbox row and in the Kafka headers, one upload becomes two disconnected traces.**

**Break it deliberately and measure how long it takes to answer "why did this document take 40 seconds to index".**

### Consumers are not actually idempotent

⚠️ **A consumer that increments a counter double-counts on replay** ([[09.7 - Replay Backfill and Reprocessing]]).

```python
async def test_consumer_is_replayable():
    await consume_all(events)
    baseline = await snapshot()
    await reset_and_consume_all(events)
    assert await snapshot() == baseline
    await consume_all(events)                # replay on top
    assert await snapshot() == baseline
```

**Write this test for every consumer.**

### The rebalance stall

⚠️ **Default `partition.assignment.strategy` is eager**, so a rolling deploy stops all consumption while the group rebalances.

```python
partition_assignment_strategy="cooperative-sticky"
```

💡 **The single highest-value non-default Kafka setting** — it turns minutes of stalled consumption into seconds ([[09.8 - Kafka Recap and Where It Fits]]).

### `acks=all` without `min.insync.replicas`

⚠️ **With one in-sync replica, "all" means one.** The two settings only work together.

## Acceptance Criteria

```
□  Dual-write loss measured, then eliminated by the outbox
□  1,000 crash injections between commit and publish: zero events lost
□  Debezium stopped: max_slot_wal_keep_size bounds the damage, verified
□  Alert on inactive replication slot, tested
□  All four consumers idempotent, proven by the replay test
□  Offsets committed after the transaction, verified by a crash test
□  One trace spans upload → outbox → Kafka → indexer → index
□  cooperative-sticky: rolling deploy stall measured, before and after
□  acks=all with min.insync.replicas=2, verified by killing a leader
□  Search index rebuildable from offset 0, byte-identical to the source
□  A schema change is caught by CI before it breaks a consumer
□  The notifier cannot be replayed, structurally
```

⚠️ **The rebuild criterion is the payoff for the whole phase.** If the index cannot be rebuilt from the log, the retention decision bought you nothing.

---

## What You Should Be Able To Explain

```
"Why the outbox rather than just publishing after the commit?"
  → We measured it: 1,000 crash injections lost 43 events. The outbox
     lost zero. There is no transaction spanning Postgres and Kafka

"Why CDC rather than polling the outbox?"
  → Polling adds query load and lags under exactly the conditions where
     you need it. CDC reads the WAL. The cost is a replication slot,
     which we bound with max_slot_wal_keep_size

"Why Kafka rather than Redis Streams?"
  → 90-day retention. At our event rate that is 340GB, which does not
     fit in memory. We need it because the index must be rebuildable —
     and in phase 9 we re-embed everything

"How do you know your consumers are safe to replay?"
  → Every consumer has a test that consumes, snapshots, resets,
     re-consumes and asserts identical state. The notifier is a separate
     consumer that never participates in replays

"What is wrong with this system now?"
  → It has no defences. A slow dependency exhausts our workers, there
     are no circuit breakers, and we have never tested a failure.
     Phase 6
```

**Question to answer:** How does Debezium's outbox event router transform a table row into a topic message, and how does it handle a restart?

💡 The `EventRouter` transform is worth reading because **it is the outbox pattern productised** — and seeing which fields it expects tells you exactly how to shape your outbox table.

## Exercise

**Drill 16.6 — Lose events, then make it impossible**

```
conduit/phases/05/
├── outbox/{schema.sql, writer.py, debezium.json}
├── consumers/{indexer.py, analytics.py, notifier.py, audit.py}
├── measure/{dual_write_loss.py, slot_growth.py, rebalance.py, RESULTS.md}
├── replay/{rebuild_index.py, verify.py, RESULTS.md}
├── schema/{envelope.py, upcast.py, ci_diff.py}
├── adr/{026-outbox.md ... 030-schema.md}
└── PHASE5.md
```

**Part 1 — Measure dual-write loss.** The naive version: commit, then publish.

**Kill the process between them, 1,000 times.** Count lost events.

Then take Kafka down for 30 seconds under load and count again. **Two numbers, and they justify everything that follows.**

**Part 2 — Build the outbox and re-measure.** Same 1,000 crash injections. **Zero loss.**

Then kill the process at every point in the relay: before reading, after reading before publishing, after publishing before marking, and after marking.

**Confirm at-least-once with no loss at every point.**

**Part 3 — The replication slot.** Stop Debezium under sustained write load.

**Chart `pg_wal` directory size over 30 minutes.** Confirm it grows without bound.

Then set `max_slot_wal_keep_size` and confirm the slot is invalidated instead of the disk filling.

**Write the alert rule and test that it fires.**

**Part 4 — Consumer idempotency.** For each of the four consumers, write and run the replay test.

⚠️ **Deliberately make the analytics consumer accumulate rather than upsert.** Confirm the test catches it, then fix it.

Then crash each consumer between the effect and the offset commit, **and confirm redelivery produces exactly-once effect.**

**Part 5 — The full rebuild.** Drop the search index entirely.

**Reset the consumer group to offset 0 and rebuild.**

**Verify byte-identical to the source database**, per organisation.

**Measure the rebuild duration and the load it placed on the database.** Then rate-limit it and re-measure — this is the phase-9 rehearsal.

**Part 6 — Rebalance cost.** Six consumers on 24 partitions, processing continuously.

**Measure total consumption stall during a rolling restart with the default strategy and with `cooperative-sticky`.**

**Chart both.**

**Part 7 — Durability settings.** Three brokers. Test `acks` in (1, all) × `min.insync.replicas` in (1, 2).

**For each: produce 10,000 records, kill the leader mid-produce, count records lost.**

**Confirm `acks=all` with `min.insync.replicas=1` loses data** — the combination people assume is safe.

**Part 8 — Schema evolution.** Add a required field to an event and deploy the producer first.

**Confirm consumers break.** Then implement the version envelope and upcasting, and confirm a v1 consumer handles a v2 event.

**Then write the CI schema diff** and confirm it catches the breaking change before merge.

**Part 9 — The trace.** Instrument the full path with trace context in the outbox row and Kafka headers.

**Confirm one connected trace.** Then remove the context from the outbox row and **confirm it splits — screenshot both.**

**Measure how long it takes to diagnose a slow ingestion with the broken trace versus the connected one.**

**Done when:**
- Dual-write loss is measured, and the outbox eliminates it across 1,000 injections
- An unbounded replication slot filled your disk, and the setting bounded it
- All four consumers pass the replay test, including one you deliberately broke
- The search index rebuilds byte-identically from offset 0
- Your rebalance chart shows the cooperative-sticky improvement
- `acks=all` with `min.insync.replicas=1` demonstrably loses data
- A breaking schema change is caught by CI, not by a consumer
- The trace connects across the outbox and the broker, verified by breaking it
