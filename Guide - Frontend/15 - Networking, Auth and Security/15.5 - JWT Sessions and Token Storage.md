# JWT, Sessions and Token Storage

## What a JWT is

Three base64url-encoded parts joined by dots:

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE3MDB9.signature
   header                  payload                      signature
```

```json
// header
{ "alg": "RS256", "typ": "JWT", "kid": "key-1" }

// payload
{ "sub": "user-123", "exp": 1700000000, "iat": 1699996400, "iss": "auth.example.com", "aud": "api.example.com", "role": "editor" }
```

**The payload is encoded, not encrypted.** Anyone holding the token can read it — paste it into jwt.io and every claim is visible. Never put anything sensitive in a JWT.

The signature guarantees integrity: the token has not been modified. It guarantees nothing about confidentiality.

Standard claims worth knowing: `sub` (subject), `exp` (expiry), `iat` (issued at), `nbf` (not before), `iss` (issuer), `aud` (audience), `jti` (unique id, used for revocation lists).

## Decoding in the client

```js
function decodeJwt(token) {
  const payload = token.split(".")[1];
  return JSON.parse(atob(payload.replace(/-/g, "+").replace(/_/g, "/")));
}
```

Base64url uses `-` and `_` where base64 uses `+` and `/`, which is why the replacement is needed.

**Decoding is not verification.** A client can read `exp` to decide when to refresh, and read `role` to render UI — but must never treat any claim as trustworthy for a security decision. Verification requires the signing key and happens on the server ([[15.4 - Authentication vs Authorization]]).

## Sessions vs JWTs

| | Server sessions | JWTs |
| --- | --- | --- |
| State | server-side store | stateless |
| Revocation | immediate | hard — valid until expiry |
| Scale | needs shared store | none |
| Size | small opaque id | 200–800+ bytes per request |
| Contents | opaque | readable claims |

The revocation problem is the decisive one. A session is deleted and immediately dead. A JWT remains valid until `exp` no matter what — a compromised token, a fired employee, a password change. Mitigations all reintroduce state:

- **Short expiry** (5–15 minutes) plus refresh tokens — reduces the window, does not close it.
- **A denylist** of revoked `jti` values — now you have a lookup on every request, which is a session store with extra steps.
- **A `tokenVersion` claim** compared against the user record — same tradeoff.

The honest summary: for a single application with a single backend, sessions are simpler and safer. JWTs earn their place in distributed systems where services must verify identity without calling a central auth service, and in cross-domain or mobile contexts where cookies are awkward.

## Access and refresh tokens

```
Access token:  short-lived (5-15 min), sent with every request
Refresh token: long-lived (days-weeks), used only to obtain a new access token
```

The refresh token should be an `HttpOnly`, `Secure`, `SameSite` cookie scoped to the refresh endpoint's path — it is never needed by JavaScript.

**Refresh token rotation** issues a new refresh token on each use and invalidates the old one. If an old token is reused, that indicates theft, and the entire token family should be revoked. This is the standard defense and is worth insisting on.

## Where to store the access token

There is no option without tradeoffs. Understanding them is what the question is really about.

**`localStorage`** — trivially readable by any script on the page. An XSS vulnerability means the token is exfiltrated to the attacker's server and usable from anywhere until expiry. Not recommended ([[14.2 - LocalStorage and SessionStorage]]).

**`HttpOnly` cookie** — unreadable by JavaScript, so XSS cannot steal it. But it is sent automatically on every request, which reintroduces CSRF exposure, mitigated by `SameSite=Lax` plus a CSRF token for state-changing requests ([[15.6 - Frontend Security]]).

**In-memory (a JavaScript variable)** — not persisted anywhere, so nothing survives a page reload. Combined with an `HttpOnly` refresh cookie, a reload silently re-acquires an access token. This is the strongest browser-only option: XSS can use the token while the page is open, but cannot exfiltrate anything that outlives the session.

```js
let accessToken = null;   // module scope, never persisted

export const setToken = (t) => { accessToken = t; };
export const getToken = () => accessToken;
```

**BFF (Backend-For-Frontend)** — the browser holds only an `HttpOnly` session cookie; the server holds the tokens and attaches them to upstream calls. No token in the browser at all. This is the current IETF recommendation for browser applications, and it is what most mature products converge on.

The frequently-heard argument "if you have XSS you've lost anyway" is imprecise. With `HttpOnly` or in-memory storage the attacker acts within the victim's live session; with `localStorage` they take the credential away and use it independently, potentially for weeks. The difference is real.

## Silent refresh, done correctly

```js
let refreshPromise = null;

async function withAuth(request) {
  let res = await request(getToken());

  if (res.status === 401) {
    refreshPromise ??= fetch("/auth/refresh", { method: "POST", credentials: "include" })
      .then(r => {
        if (!r.ok) throw new Error("refresh failed");
        return r.json();
      })
      .then(({ accessToken }) => { setToken(accessToken); })
      .finally(() => { refreshPromise = null; });

    try {
      await refreshPromise;
    } catch {
      logout();
      throw new AuthError();
    }

    res = await request(getToken());   // retry once
  }

  return res;
}
```

Three requirements: **deduplicate** concurrent refreshes (with rotation, parallel refreshes invalidate each other), **retry once only** (a second 401 after refresh means the session is genuinely dead, and retrying forever produces an infinite loop), and **log out cleanly** on refresh failure.

Proactive refresh — renewing shortly before `exp` rather than waiting for a 401 — avoids the failed request entirely and is worth adding once the reactive path works.

## Cross-tab consistency

```js
const channel = new BroadcastChannel("auth");

channel.onmessage = (e) => {
  if (e.data.type === "logout") clearClientState();
  if (e.data.type === "token") setToken(e.data.token);
};
```

Without this, logging out in one tab leaves others in a stale authenticated state until their next failed request. Sharing refreshed tokens also avoids every tab refreshing independently.

## Common mistakes

**Sensitive data in the payload.** Email addresses, phone numbers, internal ids — all readable.

**Trusting client-decoded claims.** Rendering an admin panel because `role === "admin"` in a decoded token is fine; *authorizing* on it is not.

**`alg: none`.** A historical vulnerability class where a server accepted an unsigned token. Verification must pin the expected algorithm rather than reading it from the header.

**Long-lived access tokens.** A 24-hour access token combines the worst of both models — no revocation and a wide theft window.

**No expiry validation.** Both server and client should check `exp`, with a small clock-skew tolerance.

## How senior engineers actually use this

**They default to server sessions with `HttpOnly` cookies** unless there is a concrete distributed-systems reason for JWTs.

**They use a BFF where the deployment allows it**, keeping tokens out of the browser entirely.

**They keep access tokens in memory** when tokens must live in the browser, with a refresh cookie for reload survival.

**They deduplicate refresh and retry exactly once.**

**They keep access token lifetimes short** and insist on refresh token rotation.

## Common pitfalls

- Tokens in `localStorage` with XSS treated as hypothetical.
- Concurrent refresh calls invalidating each other under rotation.
- Infinite retry loops after a failed refresh.
- Believing JWTs are encrypted.
- Client-side authorization decisions based on decoded claims.
- Access tokens valid for hours or days.
- No cross-tab logout propagation.
- Refresh tokens accessible to JavaScript.

## Interview angle

"Where would you store a JWT" is a filter question, and the answer that lands is a comparison rather than a verdict: `localStorage` is exfiltratable via XSS, `HttpOnly` cookies resist that but need CSRF protection, in-memory plus a refresh cookie is the strongest browser-only option, and a BFF avoids the problem entirely. Follow with the revocation problem as the real difference between JWTs and sessions, and describe refresh deduplication — most candidates have not thought about concurrent 401s.
