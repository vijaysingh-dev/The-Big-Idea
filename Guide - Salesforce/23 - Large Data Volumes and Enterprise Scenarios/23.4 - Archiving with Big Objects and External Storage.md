# Archiving with Big Objects and External Storage

## The most effective LDV intervention

Fewer rows makes every query faster, every index more selective, every report quicker, every load cheaper, every batch job shorter, and every sharing recalculation less expensive.

**No index, no skinny table, and no query tuning matches the effect of removing rows that nobody reads.**

It is reached for last because it requires a retention decision, and retention decisions require someone to own them.

## The decision

```
What can leave?         status plus age, usually
What must be kept?      the fields needed for audit and lookup, not all of them
Where does it go?       a big object, an external system, or a warehouse
How is it seen?         a component, a report, or an external tool
Who decided?            the retention policy, with a stated reason
```

**The fifth line is the one that blocks projects.** Without a written retention policy, nobody will authorize deletion, and the archive never happens. See [[22.3 - Field Audit Trail and Data Retention]].

## Big objects

The platform's own archive store.

```
Claim_Archive__b
    Index (defined at creation, immutable):
        Asset_Id__c          Text(18)
        Claim_Date__c        Date
        Claim_Number__c      Text(30)

    Fields:
        Claim_Amount__c      Number(16,2)
        Status__c            Text(40)
        Account_Id__c        Text(18)
        Approved_Amount__c   Number(16,2)
```

**What they give:**

```
Effectively unlimited volume — billions of rows
Minimal storage cost compared to standard objects
No sharing rows
No triggers, no automation, no recalculation
Queryable with SOQL, within constraints
```

**What they cost:**

```
The index is defined at creation and cannot be changed
Queries must filter on index fields, in order, from the left
No updates — insert and delete only
Not reportable in the usual way
No relationships to standard objects
Async SOQL required for large result sets
```

**The index definition is the entire design.** Getting it wrong means the data is written and unqueryable, and fixing it means recreating the object and reloading.

## Designing the index

```
Index: Asset_Id__c, Claim_Date__c, Claim_Number__c
```

**Filtering must proceed left to right, without gaps:**

```sql
-- Works
WHERE Asset_Id__c = :assetId
WHERE Asset_Id__c = :assetId AND Claim_Date__c > :cutoff
WHERE Asset_Id__c = :assetId AND Claim_Date__c > :cutoff AND Claim_Number__c = :number

-- Does not work
WHERE Claim_Date__c > :cutoff
WHERE Claim_Number__c = :number
WHERE Asset_Id__c = :assetId AND Claim_Number__c = :number
```

**The question that determines the index:** how will this be queried?

```
"Show a machine's claim history"        → Asset_Id__c first
"Show a customer's claim history"       → Account_Id__c first
"Find a specific claim by number"       → Claim_Number__c first
```

**If both the asset and the account views are needed**, either two big objects with different indexes, or accepting that one view is unavailable.

**The index is also the uniqueness constraint.** Two records with the same index values are one record — the second overwrites the first. Including something distinguishing is necessary.

## Writing to a big object

```java
public with sharing class ClaimArchiveBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Number__c, Claim_Amount__c, Approved_Amount__c,
                   Status__c, Claim_Date__c, Asset__c, Account__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Closed'
              AND Claim_Date__c < LAST_N_YEARS:3
              AND Legal_Hold__c = false
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        List<Claim_Archive__b> archives = new List<Claim_Archive__b>();

        for (Warranty_Claim__c claim : scope) {
            archives.add(new Claim_Archive__b(
                Asset_Id__c = claim.Asset__c,
                Claim_Date__c = claim.Claim_Date__c,
                Claim_Number__c = claim.Claim_Number__c,
                Claim_Amount__c = claim.Claim_Amount__c,
                Approved_Amount__c = claim.Approved_Amount__c,
                Status__c = claim.Status__c,
                Account_Id__c = claim.Account__c
            ));
        }

        // insertImmediate is the big object write path; ordinary DML does not apply
        List<Database.SaveResult> results = Database.insertImmediate(archives);

        // only delete what was successfully archived
        List<Warranty_Claim__c> archived = new List<Warranty_Claim__c>();
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                archived.add(scope[i]);
            }
        }

        Database.delete(archived, false);
        Database.emptyRecycleBin(archived);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Three things this gets right:**

**`insertImmediate`** is the big object write mechanism. It is not transactional with the surrounding DML, which is why the results must be checked.

**Only deleting what was archived** prevents data loss when an archive write fails.

**`emptyRecycleBin`** reclaims the storage immediately; without it the records sit in the bin for 15 days and the storage benefit is delayed. See [[10.4 - Delete, Undelete and the Recycle Bin]].

**`Legal_Hold__c` in the query** is what stops the archive job deleting a record under litigation hold. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

## Reading a big object

```java
public with sharing class ClaimArchiveSelector {

    public static List<Claim_Archive__b> byAsset(Id assetId, Integer maxRows) {
        // the filter follows the index definition, leftmost first
        return [
            SELECT Claim_Number__c, Claim_Date__c, Claim_Amount__c, Status__c
            FROM Claim_Archive__b
            WHERE Asset_Id__c = :assetId
            ORDER BY Claim_Date__c DESC
            LIMIT :maxRows
        ];
    }
}
```

**Standard SOQL works for small result sets.** For large ones, **Async SOQL** writes results to a standard object:

```
POST /services/data/v62.0/async-queries
{
  "query": "SELECT Asset_Id__c, Claim_Amount__c FROM Claim_Archive__b WHERE Claim_Date__c > 2020-01-01T00:00:00Z",
  "operation": "insert",
  "targetObject": "Claim_Analysis__c",
  "targetFieldMap": { "Asset_Id__c": "Asset__c", "Claim_Amount__c": "Amount__c" }
}
```

Async SOQL runs in the background and populates a standard object that can then be reported on — which is how archived data becomes analysable.

## Surfacing the archive

**Archived data nobody can see is data that was effectively deleted**, and that is the objection that blocks archiving projects.

```javascript
import { LightningElement, api, wire } from 'lwc';
import getArchivedClaims from '@salesforce/apex/ClaimArchiveController.getArchivedClaims';

export default class ArchivedClaimHistory extends LightningElement {
    @api recordId;

    @wire(getArchivedClaims, { assetId: '$recordId' })
    archivedClaims;

    get hasArchived() {
        return this.archivedClaims?.data?.length > 0;
    }
}
```

A component on the Asset page showing archived claims beside current ones means the user experience is unchanged. **That is what makes archiving politically acceptable**, and it should be built before the first record is archived rather than after users complain.

## External archiving

The alternative to big objects.

```
Salesforce  →  a data warehouse, a data lake, or the source ERP
```

**Where it is better:**

**The data is needed for analysis** across systems, where a warehouse is the right tool.

**The volume is enormous** — hundreds of millions of rows.

**It already exists elsewhere.** Invoice history in the ERP does not need archiving from Salesforce; it needs not being copied there in the first place.

**Reporting on the archive is a requirement**, which big objects serve poorly.

**Surfacing it back** through Salesforce Connect as an external object gives the same in-context view without storing anything:

```
ErpInvoice__x        OData connection to the warehouse
    indirect lookup on Account.ERP_Account_Id__c
        → a related list on the Account page
```

See [[02.14 - External Objects and Salesforce Connect]].

**The tradeoff:** an external dependency. The related list errors when the external system is down, and there is no automation or reporting on external objects.

## Choosing where the archive lives

| Requirement | Store |
| --- | --- |
| In-context history, low access frequency | Big object |
| Analysis and reporting across systems | Warehouse |
| Data already exists in the source system | Leave it there, surface externally |
| Regulatory retention with occasional retrieval | Big object |
| Hundreds of millions of rows | Warehouse |
| Must be automatable | Neither — it stays in a standard object |

**"Must be automatable" is the constraint that stops archiving.** If a closed claim from four years ago still needs to trigger something, it cannot be archived — which is usually a sign the requirement should be questioned rather than accommodated.

## Deletion at scale

The other half, and it is slower than insertion.

**The platform maintains sharing rows, indexes, and the recycle bin on delete**, which makes deleting a million rows a substantial operation.

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    Database.delete(scope, false);
    // purging inside execute prevents the bin overflowing partway through a long job
    Database.emptyRecycleBin(scope);
}
```

**Purging inside `execute`** matters on a job deleting millions of rows. Otherwise the bin fills, starts purging arbitrarily, and the storage never comes back during the run.

**The Bulk API hard delete** bypasses the bin entirely and is substantially faster, requiring a specific permission:

```bash
sf data delete bulk --sobject Warranty_Claim__c --file claims-to-delete.csv \
  --hard-delete --wait 60 --target-org production
```

**Delete children before parents** to avoid cascade overhead.

**Reduce the scope size** where the object has heavy automation, and **bypass the automation** during the archive:

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    // archiving should not fire triggers; the records are leaving, not changing
    AutomationBypass.bypass('WarrantyClaim');
    // ...
}
```

Without that, archiving a million claims runs a million trigger executions.

## Field history and archiving

**Deleting a record deletes its field history**, which is frequently the audit evidence the retention policy requires.

**Capture what is needed before deleting:**

```java
List<Claim_History_Archive__b> historyArchives = new List<Claim_History_Archive__b>();

for (Warranty_Claim__History history : [
    SELECT ParentId, Field, OldValue, NewValue, CreatedById, CreatedDate
    FROM Warranty_Claim__History WHERE ParentId IN :claimIds
]) {
    historyArchives.add(new Claim_History_Archive__b(
        Claim_Id__c = history.ParentId,
        Changed_Date__c = history.CreatedDate,
        Field__c = history.Field,
        Old_Value__c = String.valueOf(history.OldValue),
        New_Value__c = String.valueOf(history.NewValue),
        Changed_By__c = history.CreatedById
    ));
}

Database.insertImmediate(historyArchives);
```

**This step is routinely missed**, and it is discovered when an audit asks for a change history that no longer exists.

## Running it

**Archiving is a scheduled job**, not a one-time project.

```java
public with sharing class ArchiveScheduler implements Schedulable {
    public void execute(SchedulableContext ctx) {
        Database.executeBatch(new ClaimArchiveBatch(), 200);
    }
}
```

```java
System.schedule('Claim Archive Monthly', '0 0 2 1 * ?', new ArchiveScheduler());
```

**Monthly is usually right** — frequent enough that each run is small, infrequent enough not to compete with other jobs.

**The first run is the large one.** Archiving six years of accumulated history at once means a job running for days, and it should be split — one year at a time, verified between runs.

**Monitor it:**

```sql
SELECT ApexClass.Name, Status, JobItemsProcessed, NumberOfErrors, ExtendedStatus,
       CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE ApexClass.Name = 'ClaimArchiveBatch' ORDER BY CreatedDate DESC LIMIT 12
```

**An archive job that stopped running** produces no error and the object grows again. Alerting on absence is what catches it. See [[20.6 - Event Monitoring and Operational Visibility]].

## A staged approach

For an org with no archiving and a large object.

**1. Establish the retention policy**, in writing, with a reason. This is the blocker, and it is organizational rather than technical.

**2. Build the archive object and the surfacing component**, and deploy both before archiving anything.

**3. Archive one year**, verify the counts, and verify the component shows the data.

**4. Archive the remainder**, a year at a time.

**5. Schedule the ongoing job.**

**6. Monitor.**

**Building the surfacing component first** is what makes step 3 acceptable to the business — they see the data has moved rather than gone.

## Practical guidance

**Archive before optimizing.** It is the most effective intervention available.

**Design the big object index around the query**, and know it cannot be changed.

**Use `insertImmediate`**, and check the results before deleting.

**Only delete what was successfully archived.**

**Capture field history before deleting the record.**

**Honour a legal hold flag.**

**Purge the recycle bin inside `execute`** on large deletions.

**Bypass automation during archiving.**

**Build the surfacing component before archiving anything.**

**Schedule it, and alert on absence.**
