# Component Design and API Design

A component's props are a public API. The same considerations apply as to any interface: small surface, hard to misuse, easy to extend without breaking existing callers.

## The pressure that shapes everything

Requirements arrive incrementally. Each one adds a prop:

```jsx
<Modal
  title="Confirm"
  showCloseButton
  headerIcon={<Warning />}
  footerButtons={[{ label: "OK", primary: true }]}
  size="lg"
  closeOnOverlayClick={false}
  renderHeader={custom}          // the escape hatch that admits defeat
/>
```

Twelve props, most combinations meaningless, and a render prop because the configuration eventually could not express what someone needed.

Composition inverts this:

```jsx
<Modal onClose={close}>
  <Modal.Header icon={<Warning />}>Confirm</Modal.Header>
  <Modal.Body>Are you sure?</Modal.Body>
  <Modal.Footer>
    <Button variant="primary" onClick={confirm}>OK</Button>
  </Modal.Footer>
</Modal>
```

Fewer props, unlimited arrangements, and the caller decides layout because the caller already knows what they want ([[22.6 - Compound Components]]).

**The signal to refactor:** more than about three boolean props, a growing `variant === ...` chain, or the appearance of a `render*` prop.

## Make invalid states unrepresentable

```tsx
// Every combination is possible, most are meaningless
type AlertProps = {
  isError?: boolean;
  isSuccess?: boolean;
  error?: Error;
  message?: string;
  onRetry?: () => void;
};

// Only valid combinations compile
type AlertProps =
  | { variant: "error"; error: Error; onRetry: () => void }
  | { variant: "success"; message: string };
```

A discriminated union means `error` cannot be passed with `variant="success"`, and the compiler narrows inside the component ([[25.6 - Discriminated Unions and Narrowing]]).

This converts a class of runtime bugs into compile errors, and it documents the valid combinations without a comment.

## Controlled and uncontrolled

Any component with internal state should support both:

```jsx
function Accordion({ expanded: controlled, defaultExpanded = false, onToggle }) {
  const [internal, setInternal] = useState(defaultExpanded);
  const isControlled = controlled !== undefined;
  const expanded = isControlled ? controlled : internal;

  const toggle = () => {
    if (!isControlled) setInternal(v => !v);
    onToggle?.(!expanded);
  };
}
```

Two rules: decide by whether the prop is `undefined`, and **always call the callback** so controlled consumers stay informed ([[16.8 - Controlled vs Uncontrolled Components]]).

Every serious component library uses exactly this pattern.

## Forward everything you do not consume

```jsx
function Input({ label, id, ref, ...rest }) {
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} ref={ref} {...rest} />
    </>
  );
}
```

A component that swallows unknown props forces consumers to wrap it the first time they need `aria-describedby` or `data-testid`.

```tsx
type InputProps = { label: string } & ComponentPropsWithoutRef<"input">;
```

This inherits every native prop and keeps them correct as React's types evolve. Overriding one requires `Omit` first, or the intersection produces `never` ([[25.4 - Typing Props and Children]]).

Forwarding the ref matters equally — without it, nobody can focus, measure or scroll to the element ([[22.3 - forwardRef and useImperativeHandle]]).

## Styling extension

Consumers will need to adjust appearance. Three levels, in increasing power:

```jsx
<Card className="mt-4" />                              // merge, do not replace
<Card style={{ "--card-padding": "2rem" }} />          // custom properties
<Card classNames={{ root: "...", header: "..." }} />   // slot-level targeting
```

`className` must **merge**, not overwrite:

```jsx
function Card({ className, ...rest }) {
  return <div className={cn("card", className)} {...rest} />;
}
```

Order matters: caller classes last so they can win. With Tailwind, `tailwind-merge` resolves conflicting utilities correctly, which naive concatenation does not.

CSS custom properties are the cleanest extension point for design tokens — they cascade, they can be set per instance, and they need no prop plumbing ([[10.4 - Units Custom Properties and Theming]]).

## Accessibility is part of the API

```jsx
function Toggle({ pressed, onPressedChange, label }) {
  return (
    <button
      type="button"
      aria-pressed={pressed}
      aria-label={label}
      onClick={() => onPressedChange(!pressed)}
    >
      {pressed ? <CheckIcon /> : null}
    </button>
  );
}
```

A component that cannot be made accessible by its consumer is broken. That means: it accepts an accessible name, it manages its own ARIA state, it handles expected keyboard interaction, and it forwards `aria-*` props.

Fixing accessibility once in `Button`, `Modal`, `Input` and `Menu` fixes it across the whole application. That leverage is the strongest argument for a design system ([[09.5 - Accessibility Fundamentals]]).

For complex widgets — combobox, menu, date picker — the keyboard and ARIA requirements are long enough that a headless library is usually the right call rather than reimplementing the APG patterns.

## Escape hatches

Every abstraction fails eventually. Provide a way out that does not require forking:

```jsx
<Select asChild>
  <CustomTrigger />
</Select>
```

Radix's `asChild` merges behavior onto a caller-supplied element rather than rendering its own. It solves "I need your behavior but my markup" without an `as` prop and its typing complexity.

Other escape hatches: exposing an imperative handle for genuinely imperative actions, a `render` prop for one specific slot, and `classNames` for internal element targeting.

A library with no escape hatch gets forked. A library with too many has no coherent API. Two or three, deliberately chosen.

## Sizing components

**Split** when a part has its own state the rest does not need, when it is reused elsewhere, or when it re-renders far more often than its siblings ([[19.1 - What Causes Re-renders]]).

**Do not split** because a file feels long. Two components that always change together, share six props and are used in one place are harder to follow than one.

A useful check: if extracting requires passing more than three or four props back down, the boundary is wrong.

## Documenting

```tsx
/**
 * A dismissible notification.
 *
 * @example
 * <Alert variant="error" error={err} onRetry={refetch} />
 */
```

Types document the shape; examples document the intent. A Storybook story per meaningful state — default, loading, error, empty, long content, RTL — doubles as visual regression coverage and as the place designers and engineers agree on behavior.

The states worth having stories for are exactly the ones people forget to build ([[24.2 - Loading Error and Empty States]]).

## Versioning a shared library

Breaking changes are expensive across an organization. Prefer additive change:

```jsx
// Deprecate rather than remove
function Button({ variant, type, ...rest }) {
  if (type !== undefined && process.env.NODE_ENV !== "production") {
    console.warn("Button: `type` is deprecated, use `variant`");
  }
  return <button data-variant={variant ?? type} {...rest} />;
}
```

Support both for a release, warn in development, then remove. A codemod for the migration turns an organization-wide change from weeks into a PR ([[28.10 - Design Systems and Component Libraries]]).

## How senior engineers actually use this

**They treat a growing prop list as a design signal**, and reach for composition before adding the fourth boolean.

**They use discriminated unions for variants**, making invalid props uncompilable.

**They support controlled and uncontrolled modes** in every stateful component.

**They forward refs and unknown props** as a non-negotiable rule.

**They build accessibility into the primitives**, since that is where the leverage is.

**They provide a deliberate escape hatch** so consumers do not fork.

## Common pitfalls

- Boolean prop explosion where a variant enum belongs.
- `className` replacing rather than merging.
- Swallowed props and refs, forcing consumer wrappers.
- Accessibility left to consumers who will not add it.
- No escape hatch, leading to forks.
- Overriding a native prop without `Omit`, producing `never`.
- Splitting so aggressively that prop drilling appears.
- Breaking changes without a deprecation period or codemod.

## Interview angle

"How would you design a reusable component API" is a design question, and the strongest answer contrasts configuration with composition using a concrete example — a Modal that accumulates props versus one that accepts arranged children. Then the specifics: discriminated unions so invalid prop combinations do not compile, dual controlled/uncontrolled support via the `undefined` check, forwarding refs and unknown props, merging `className`, and building accessibility into the primitive because that is where it scales.
