# Query Performance at Scale

## The one thing that matters

**Can the query use an index?**

At small volume the answer is irrelevant — scanning 5,000 rows is fast either way. At ten million it is the entire difference between 200 milliseconds and a timeout.

Everything in this note is about making the answer yes.

## The optimizer's decision

Salesforce's query optimizer estimates how many rows a filter will return and decides whether an index is worth using.

```
Standard index    selective below ~30% of the first million rows,
                  then ~15% beyond, capped around 1,000,000 rows
Custom index      selective below ~10%, capped around 333,000 rows
```

**A filter returning too many rows gets a table scan regardless of indexing**, because scanning is cheaper than an index lookup plus a fetch for that many rows.

**That is why `Status__c != 'Closed'` on an object where 70% of records are open cannot be optimized.** No index helps; the filter is not selective.

## Reading the query plan

```
Developer Console → Query Editor → paste the query → Plan
```

```
Cardinality  Fields        Leading Operation Type  Cost   sObject Cardinality
     18420   Status__c     TableScan               2.84    8412000
      1240   Account__c    Index                   0.11    8412000
```

**Cost above 1 means a table scan.** Below 1 means the optimizer will use an index.

**`Leading Operation Type`:**

```
Index        an index will be used
TableScan    the whole table is read
Other        a sharing-based plan — expensive at volume
Sharing      similar
```

**`Other` is the one worth noticing.** It means the optimizer used the sharing table rather than a field index, which on a private object with millions of records is slow. Making the filter selective on an indexed field is the fix. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

Also available through the REST explain endpoint:

```bash
sf api request rest \
  '/services/data/v62.0/query/?explain=SELECT+Id+FROM+Warranty_Claim__c+WHERE+Status__c=%27Submitted%27' \
  --target-org production
```

## What is indexed

```
Id
Name
OwnerId
CreatedDate, CreatedById
LastModifiedDate, LastModifiedById
SystemModstamp
RecordTypeId
Division
Lookup and master-detail fields
External ID fields
Unique fields
```

**External ID and Unique fields are indexed**, which is why marking an integration key as an external ID improves query performance as well as enabling upsert. See [[10.3 - Upsert, Merge and External IDs]].

**Custom indexes are requested from Salesforce Support**, with evidence — the query, the volume, the frequency, and the current performance. See [[16.9 - Skinny Tables and Custom Indexes]].

## The anti-patterns

Each one prevents index use, and each has a rewrite.

**Negative operators:**

```sql
-- Cannot use an index
WHERE Status__c != 'Closed'
WHERE Status__c NOT IN ('Closed', 'Cancelled')

-- Can
WHERE Status__c IN ('Submitted', 'Under Review', 'Approved', 'Rejected')
```

**Enumerating the positive values** is the single most common query fix, and it requires knowing the picklist — which is why a new value added later silently excludes records. A comment naming the intent helps.

**Leading wildcards:**

```sql
-- Cannot use an index
WHERE Claim_Number__c LIKE '%00042'

-- Can
WHERE Claim_Number__c LIKE 'WC-00042%'
```

**For genuine text search, SOSL uses the search index** and is the right tool:

```sql
FIND {00042} IN NAME FIELDS RETURNING Warranty_Claim__c (Id, Claim_Number__c)
```

See [[08.8 - SOSL and Full Text Search]].

**Null comparisons:**

```sql
-- Standard indexes exclude nulls
WHERE Approved_Date__c = null
```

**A custom index can be built to include nulls**, requested explicitly. Worth asking for when a null check is a common access pattern — an integration finding unprocessed records is exactly that shape:

```sql
SELECT Id FROM Warranty_Claim__c WHERE ERP_Confirmation__c = null LIMIT 200
```

**Formula fields in filters:**

```sql
-- Only indexable if the formula is deterministic and same-record
WHERE Days_Open_Formula__c > 30
```

A formula referencing another object, or using `TODAY()` or `NOW()`, cannot be indexed. A stored field maintained by automation can. See [[06.4 - Cross-Object Formulas and Limits]].

**`OR` across different fields:**

```sql
-- The optimizer frequently cannot use an index for either side
WHERE Account__c = :accountId OR Asset__c = :assetId
```

Two queries and a merged result is sometimes faster, which is unintuitive and worth measuring.

## Making a filter selective

**Add a date bound.** The most common fix, and the one that usually works.

```sql
-- Non-selective across eight million rows
WHERE Status__c = 'Submitted'

-- Selective, and usually what the user actually wants
WHERE Status__c = 'Submitted' AND Claim_Date__c = LAST_N_DAYS:90
```

**`CreatedDate` and `SystemModstamp` are indexed by default**, so a bound on either is free selectivity.

**Filter on the most selective field first** in a compound filter. The optimizer chooses, and giving it a genuinely selective option is what matters.

**Use a two-column index** where two fields are always filtered together. Support can create these, and the column order matters — the more selective field first.

## Query design at scale

**Select fewer fields.**

```sql
-- Wide rows, heap risk, and slower
SELECT FIELDS(ALL) FROM Warranty_Claim__c WHERE ...

-- What is actually used
SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c FROM Warranty_Claim__c WHERE ...
```

**Formula fields are computed per row on read.** Eight cross-object formulas across 500,000 rows is 4,000,000 traversals.

**Always LIMIT.** A query with no limit works until the data grows.

**Aggregate in the database:**

```sql
-- 50,000 rows retrieved to compute a sum
SELECT Claim_Amount__c FROM Warranty_Claim__c WHERE Asset__c IN :assetIds

-- One row per asset
SELECT Asset__c, SUM(Claim_Amount__c) FROM Warranty_Claim__c
WHERE Asset__c IN :assetIds GROUP BY Asset__c
```

**`SELECT COUNT()` does not consume the row limit** for the rows counted, which makes it the right tool for a count.

See [[08.4 - Aggregate Queries, GROUP BY and HAVING]].

## Subqueries

```sql
SELECT Id, SerialNumber, (SELECT Id, Claim_Amount__c FROM Warranty_Claims__r)
FROM Asset WHERE AccountId = :accountId
```

**Parent and child rows both count** toward the 50,000-row limit. A thousand assets with sixty claims each is 61,000 rows and fails.

**Two queries with a map** is frequently better at volume than one with a subquery — the row accounting is clearer and each can be bounded independently.

## Pagination

`OFFSET` has a hard ceiling of 2,000 and degrades before reaching it — the database still reads every skipped row.

**Keyset pagination** is the alternative:

```java
public static List<Warranty_Claim__c> nextPage(Datetime lastDate, Id lastId, Integer pageSize) {
    // ordering on an indexed field and using the last row as the cursor
    // means each page is an index seek rather than a scan-and-skip
    return [
        SELECT Id, Claim_Number__c, Claim_Date__c
        FROM Warranty_Claim__c
        WHERE (Claim_Date__c < :lastDate)
           OR (Claim_Date__c = :lastDate AND Id > :lastId)
        WITH USER_MODE
        ORDER BY Claim_Date__c DESC, Id ASC
        LIMIT :pageSize
    ];
}
```

**The tiebreaker on Id** handles duplicate dates, which is what makes the cursor stable.

**For an external consumer, the REST API's `nextRecordsUrl`** is a proper server-side cursor with none of these problems and should be used in preference. See [[08.5 - LIMIT, OFFSET, ORDER BY and Pagination]].

## Batch query locators

```java
public Database.QueryLocator start(Database.BatchableContext ctx) {
    return Database.getQueryLocator([
        SELECT Id, Status__c, Asset__c
        FROM Warranty_Claim__c
        WHERE Status__c = 'Under Review'
        ORDER BY Asset__c
    ]);
}
```

**`QueryLocator` handles up to 50 million rows** and is not subject to the 50,000-row limit.

**`ORDER BY Asset__c` groups children of the same parent into the same chunk**, which is the in-code equivalent of sorting a data file and reduces lock contention on the parent. See [[23.5 - Bulk Data Loading at Scale]].

**A non-selective query locator still works** — batch jobs are permitted to scan — but it is slower to start, and the `start` method has its own timeout.

## Skinny tables

For a wide object where reports and list views are slow.

```
Warranty_Claim__c    60 fields, 8 million rows
Skinny table         6 fields, 8 million rows
```

**The optimizer uses it transparently** — no code change, no different object name.

**What it fixes:** the cost of reading a wide row, and the join between standard and custom field storage.

**What it does not:** a non-selective filter. A table scan against a skinny table is still a table scan.

**Constraints:** up to 100 columns, no cross-object fields, not copied to sandboxes automatically, and requested from Support.

**They are a last resort**, after the query itself has been made selective. See [[16.9 - Skinny Tables and Custom Indexes]].

## Reports and list views

The same rules, and the place users notice first.

**A report on a large object with a non-selective filter times out**, and the user reports it before any developer notices.

**The fixes users can apply themselves:**

```
A relative date filter — THIS FISCAL QUARTER, LAST 90 DAYS
A row limit
Filtering on an indexed field
```

**The fixes that require a developer:**

```
A denormalized indexed field replacing a cross-object filter
A custom index
A skinny table
Archiving
```

**Report filters using `not equal to`** have the same problem as SOQL, and a report builder will not warn about it.

## Archiving as a query fix

Frequently the right answer, and the one reached for last.

```
8,000,000 claims, filtered non-selectively    → timeout
2,000,000 claims after archiving              → the same filter is now selective
```

**Reducing the row count changes what counts as selective.** A filter returning 400,000 rows is above the threshold at eight million records and below it at two million.

**Archiving improves every query on the object at once**, without a single index request. See [[23.4 - Archiving with Big Objects and External Storage]].

## A diagnostic sequence

```
1. Read the query plan.  Cost above 1 means a scan.

2. Check whether the filter is selective at all:
     SELECT COUNT() FROM Object__c WHERE <the filter>
     SELECT COUNT() FROM Object__c
   If it returns most of the table, no index will help.

3. Remove the anti-patterns:
     != and NOT IN     → a positive IN list
     leading wildcard  → SOSL, or a prefix match
     null comparison   → a null-inclusive custom index
     formula filter    → a stored field

4. Add a date bound.

5. Select fewer fields, and add a LIMIT.

6. Then consider a custom index or a skinny table.

7. Consider archiving, which fixes everything at once.
```

**Steps 1 to 4 resolve most cases** and cost nothing. Step 6 requires a support request and evidence; step 7 requires a retention decision.

## Monitoring

```sql
SELECT ApexClass.Name, MethodName, RunTime
FROM ApexTestResult WHERE AsyncApexJobId = :jobId
ORDER BY RunTime DESC LIMIT 20
```

Test runtime is a proxy — a test that has doubled in duration usually means a query has.

**With Event Monitoring**, `ApexExecution` gives `DB_TOTAL_TIME` per transaction for real users, which is the only view of production query performance:

```
Filter ApexExecution where DB_TOTAL_TIME is high
Group by ENTRY_POINT
```

See [[20.6 - Event Monitoring and Operational Visibility]].

**Batch job duration trended** is the earliest warning available:

```sql
SELECT ApexClass.Name, CreatedDate, CompletedDate, JobItemsProcessed
FROM AsyncApexJob WHERE JobType = 'BatchApex' AND CreatedDate = LAST_N_DAYS:90
ORDER BY CreatedDate DESC
```

A job whose duration has doubled over six months is telling you the data grew past a threshold.

## Practical guidance

**Read the query plan before assuming anything.** Cost above 1 is a scan.

**Check whether the filter is selective at all** — if not, indexing cannot help.

**Rewrite `!=` and `NOT IN` as positive `IN` lists.**

**Add a date bound.** It is the most common fix.

**Use SOSL for text search**, not `LIKE '%...'`.

**Select fewer fields, and always LIMIT.**

**Aggregate in the database** rather than retrieving rows to sum.

**Use keyset pagination**, not `OFFSET`.

**Order batch query locators by parent** to reduce contention.

**Watch for `Leading Operation Type: Other`** — a sharing-based plan.

**Consider archiving**, which makes every query on the object more selective at once.
