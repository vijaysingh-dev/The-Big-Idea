# Formula Fields

## The one thing to understand

A formula field is **not stored**. It is calculated every time the record is read.

That single fact explains everything else about formula fields: why they are always current, why they cost nothing to maintain, why they cannot be written to, why they can slow down queries, and why they have limits that stored fields do not.

## What they are for

A formula field derives a value from other fields on the same record, or on a parent record up to a limited depth.

```
// Days a warranty claim has been open
IF( ISBLANK(Closed_Date__c),
    TODAY() - DATEVALUE(CreatedDate),
    Closed_Date__c - DATEVALUE(CreatedDate) )
```

```
// Colour-coded risk indicator, referencing the parent account
IF( Account__r.Credit_Rating__c = "High Risk" && Amount__c > 100000,
    "At Risk",
    IF( Amount__c > 100000, "Large", "Standard" ) )
```

Both of these are always correct, with no automation, no trigger, and no recalculation job. If the underlying field changes, the formula reflects it on the next read.

## Where the value is genuinely large

**No maintenance.** A trigger that stamps a calculated value has to handle every path that could change the inputs — user edits, integrations, batch jobs, flows. A formula handles all of them by construction.

**Zero storage.** Formula fields do not consume data storage.

**Reportable and filterable.** Unlike a value calculated in a component, a formula field can be reported on, filtered on, and used in list views.

**Available to automation.** Flows, validation rules, and Apex can all read them.

This is why the standard guidance is real: **if a formula field can do it, do not write a trigger.** The trigger is more code, more tests, more deployment risk, and it can drift out of sync with reality.

## Cross-object formulas

A formula can traverse *upward* through lookup and master-detail relationships using the `__r` syntax.

```
Account__r.Owner.Name
Account__r.Parent.Industry
Machine__r.Product__r.Family
```

The limit is **10 levels of relationship traversal** per formula, and a total of 15 unique relationships referenced across all formulas, validation rules, and roll-ups on a single object.

Crucially, formulas traverse upward only. A formula on Account cannot look at its Opportunities. Aggregating from children is what roll-up summaries and Apex are for. See [[02.6 - Roll-Up Summary Fields]].

## The limits that actually bite

**Compiled size: 5,000 bytes.** Not the characters you typed — the compiled form, which expands considerably when the formula references other formula fields. This is the limit people hit first, and the error is unhelpful.

**Formula characters: 3,900.** What you typed.

**Spanning relationships: 10 per formula.**

**Total spanning relationships per object: 15**, shared across all formulas, validation rules, roll-ups, and workflow rules on that object. In a mature org this is a genuinely scarce resource, and someone eventually cannot add a needed validation rule because the budget is spent.

When you hit the compiled size limit, the practical options are: simplify the logic, break it into a helper formula field that the main formula references, replace repeated sub-expressions with a single intermediate field, or accept that it should be a trigger. There is no way to raise the limit.

## Where formula fields hurt

This is the part that separates people who use formulas well from people who use them everywhere.

**They are computed at query time, so they cost CPU on every read.** A single formula is negligible. Forty complex cross-object formulas on Opportunity, queried in a batch job over 200,000 records, is not — this genuinely causes `Apex CPU time limit exceeded` in code that contains no obvious loop. If you are querying at volume, select only the formula fields you actually need.

**They cannot be indexed in the general case.** Formula fields are not indexed unless they meet narrow conditions, so filtering a large object on a formula field produces a non-selective query. On an object with several million rows, this is the difference between a fast query and a timeout. When a value must be filtered at scale, storing it in a real field via a trigger or flow is the correct choice, even though it is more work. See [[08.9 - Indexes and Selective Queries]].

**Cross-object formulas add joins.** Every `__r` traversal is work the query engine does on every row.

**They cannot be written to.** A formula field cannot be set by a user, an integration, or Apex. If a value ever needs manual override, it cannot be a formula.

**They do not fire automation.** A formula field changing does not trigger a record-triggered flow or an Apex trigger, because the record was never updated. Automation that needs to react to a derived value cannot watch a formula field. This surprises people regularly.

## Formula fields in Apex

They are queried like any other field and are read-only:

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c, Days_Open__c, Risk_Level__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
];

for (Warranty_Claim__c c : claims) {
    if (c.Days_Open__c > 30) {
        c.Priority__c = 'High';
    }
}
update claims;
```

Two behaviours to know. Formula values are recalculated after DML, but the in-memory object you hold is **not** refreshed — you must re-query to see the updated formula value. And in a `before` trigger, formula fields reflect the *old* field values, because the record has not been saved yet. Both of these produce confusing bugs the first time you meet them.

## Choosing between formula, roll-up, flow, and trigger

The decision most orgs would benefit from applying consistently:

| Need | Use |
| --- | --- |
| Value derived from same record or a parent, always current | Formula field |
| Aggregate of child records, master-detail relationship | Roll-Up Summary |
| Aggregate of child records, lookup relationship | Flow or Apex |
| Value must be filterable on a large object | Stored field, set by flow or trigger |
| Value must be overridable by a user | Stored field |
| Value must trigger downstream automation | Stored field |
| Logic needs queries, callouts, or loops | Apex |

## Things worth knowing that are not obvious

**`ISCHANGED`, `PRIORVALUE`, and `ISNEW` are not available in formula fields.** They work in validation rules and workflow, not in formula fields, because a formula field has no concept of a previous state.

**Text formulas returning HTML.** Formula fields of type Text can return HTML using `IMAGE()` and `HYPERLINK()`, which is how status indicators and traffic lights are built without code.

```
IMAGE( IF(Days_Open__c > 30, "/img/samples/flag_red.gif", "/img/samples/flag_green.gif"), "status" )
```

**Blank handling.** A formula referencing a null number treats it as zero or as blank depending on a setting on the field, and getting this wrong silently produces wrong arithmetic. Be explicit with `BLANKVALUE()` or `NULLVALUE()` rather than relying on the default.

**Checkbox formulas are extremely useful.** A formula checkbox is often the cleanest way to express a condition once and reuse it in reports, list views, validation rules, and flow entry criteria, instead of restating the same logic in five places.
