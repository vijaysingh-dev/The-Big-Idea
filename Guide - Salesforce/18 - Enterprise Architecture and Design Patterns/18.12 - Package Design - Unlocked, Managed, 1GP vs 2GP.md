# Package Design - Unlocked, Managed, 1GP vs 2GP

## The three ways to organize metadata

**Org development.** Everything in one bucket, deployed with a manifest or change sets. What most orgs do.

**Unlocked packages.** Metadata grouped into versioned, installable units. For your own org's modularity.

**Managed packages.** The same, plus intellectual property protection and namespace isolation. For distributing to other orgs — AppExchange and ISVs.

## Org development, and its limits

```
force-app/
    main/default/
        classes/          400 files
        lwc/              120 components
        objects/
        flows/
```

**It works, and it works less well as it grows.** The problems are cumulative rather than sudden:

Deployments become all-or-nothing. Everything is coupled to everything, so a change anywhere risks anything. Ownership is unclear when several teams share one directory. And there is no way to say "the claims module depends on the core module" — the dependency exists in the code and nowhere in the metadata.

The signal to move: **a deployment fails because of a test in an unrelated feature**, or two teams keep conflicting in the same directory.

## Unlocked packages

Versioned, installable metadata modules within your own org.

```bash
sf package create \
  --name "Northwind Core" \
  --package-type Unlocked \
  --path force-app/core \
  --target-dev-hub my-devhub

sf package version create \
  --package "Northwind Core" \
  --installation-key-bypass \
  --wait 20 \
  --code-coverage

sf package install \
  --package "Northwind Core@1.2.0-3" \
  --target-org production \
  --wait 20
```

**Unlocked means the metadata can still be edited in the target org** — a subscriber-side change is possible, and the next package upgrade may overwrite it. That is a deliberate design: modularity without lock-in.

**What they buy:**

**Modularity.** A change to the claims module affects the claims module.

**Explicit dependencies.** A package declares what it depends on, and the platform enforces the install order.

**Independent versioning.** Core can be at 2.4 while Claims is at 1.7.

**Smaller, faster deployments.** Only the changed package is installed, and only its tests run.

**Clear ownership.** A package has a team.

**What they cost:**

**Dependency management is real work.** A change to a core object's field can break three dependent packages, and finding out means installing them.

**No circular dependencies.** If Claims and Contracts each reference the other, they are one package or the shared part is extracted into a third.

**Ordering.** Installations must respect the dependency graph.

**A structure to maintain**, including deciding where a new field belongs.

## Structuring the packages

```
northwind-core           objects, shared services, utilities, logging framework
    ↑
northwind-claims         warranty claims: objects, automation, components
    ↑
northwind-contracts      service contracts and coverage
    ↑
northwind-erp-sync       integration layer, depending on all three
```

**The rules that make this hold together:**

**Dependencies point one way.** Core knows nothing about Claims.

**Shared metadata lives in the lowest common package.** A field on Account used by both Claims and Contracts belongs in Core.

**No circular dependencies.** The compiler enforces this, and discovering it late means restructuring.

**Package boundaries follow ownership**, not just technical layering. A package maintained by two teams will be a source of friction.

The hardest part in practice: **standard objects.** Account and Case belong to Salesforce, so fields added to them go in whichever package needs them — and two packages both adding fields to Account creates a coupling that is easy to miss.

## Managed packages

For distributing to other organizations. Two things distinguish them.

**A namespace.** Every component gets a prefix:

```
northwind__Warranty_Claim__c
northwind__ClaimApprovalService
northwind__claimList
```

The namespace is registered once to a Dev Hub, is permanent, and cannot be changed.

**Intellectual property protection.** Subscribers cannot see the Apex source. Only `global` members are visible and callable.

## The global commitment

The most consequential rule in managed package development.

**A `global` member can never be removed or have its signature changed.** Doing so breaks every subscriber org that references it.

```java
global with sharing class ClaimApprovalService {

    // permanent: this signature can never change
    global static void approve(Set<Id> claimIds, Decimal amount) {
        new ClaimApprovalServiceImpl().approve(claimIds, amount);
    }
}
```

```java
// public: free to change, invisible to subscribers
public with sharing class ClaimApprovalServiceImpl {

    public void approve(Set<Id> claimIds, Decimal amount) { }
}
```

**Design the global surface deliberately and keep it small.** A thin global facade delegating to public implementation is the standard shape — the contract holds while the implementation evolves.

The same applies to `global` interfaces, `global` custom objects, and `global` fields. A field marked global in version 1.0 is there forever.

Extending a global method means adding an overload, not changing the existing one:

```java
global static void approve(Set<Id> claimIds, Decimal amount) {
    approve(claimIds, amount, null);
}

global static void approve(Set<Id> claimIds, Decimal amount, String reason) { }
```

## 1GP versus 2GP

**First-Generation Packaging (1GP)** builds from a **packaging org** — a dedicated org where the metadata lives and the package is assembled by adding components in the UI.

**Second-Generation Packaging (2GP)** builds from **source control**, through the CLI, with the Dev Hub as the registry.

| | 1GP | 2GP |
| --- | --- | --- |
| Source of truth | The packaging org | Source control |
| Build | Manual, in the UI | CLI, scriptable |
| Namespace | One package per namespace | Several packages per namespace |
| CI/CD | Difficult | Designed for it |
| Versioning | Sequential | Branch and version aware |
| Patch versions | Supported | Supported |
| Modularity | One monolith | Several packages |
| Status | Legacy | Current |

**2GP is the current approach**, and new ISV development should use it. The ability to have several packages under one namespace is the structural difference — an ISV can ship a core package and optional modules rather than one monolith.

**1GP survives** in established ISVs with years of subscriber history. Migrating a 1GP package to 2GP is possible and is a project, so it happens when there is another reason to restructure.

## Package versions and upgrades

```
1.2.0-3
│ │ │ └── build number
│ │ └──── patch
│ └────── minor
└──────── major
```

```bash
sf package version create --package "Northwind Claims" --code-coverage --wait 30
sf package version promote --package "Northwind Claims@1.3.0-5"
```

**A version must be promoted before it can be installed in production**, which is the release gate.

**Upgrades preserve subscriber data.** Fields are added, not replaced. Removing a field from a managed package **deletes subscriber data**, which is why it is heavily restricted and generally impossible for global components.

**Deprecation, not deletion.** The `@deprecated` annotation marks a global member as unsupported while leaving it callable:

```java
@deprecated
global static void approveClaim(Id claimId) {
    approve(new Set<Id>{ claimId }, null);
}
```

## Protected components

For a managed package shipping configuration that subscribers should not change:

```
Protected Custom Metadata Type    invisible and uneditable in the subscriber org
Protected Custom Setting          same
Protected Custom Permission
```

This is how a package ships its own internal configuration — feature registries, rule tables, internal toggles — without exposing them. See [[17.1 - Custom Metadata Types]].

**Public custom metadata**, by contrast, is how a package lets subscribers configure it. Choosing which is which is a design decision made per type.

## Limits inside a package

Two things behave differently for managed package code, both to the package's advantage.

**Governor limits are tracked per namespace.** A package's queries and DML count against its own allocation, separate from the subscriber's:

```
LIMIT_USAGE_FOR_NS|(default)|Number of SOQL queries: 47 out of 100
LIMIT_USAGE_FOR_NS|northwind|Number of SOQL queries: 12 out of 100
```

**Code coverage is tracked per namespace**, so a package's tests do not need to cover subscriber code and vice versa.

**Test execution**, though, is a real cost: a package's tests run during installation, which makes a slow test suite a slow install. See [[16.1 - Why Governor Limits Exist]].

## The security review

An AppExchange listing requires passing Salesforce's security review, which is thorough and takes weeks.

What it checks, in effect:

```
[ ] Sharing keyword declared on every class
[ ] WITH USER_MODE or explicit CRUD and FLS checks
[ ] No SOQL or SOSL injection — bind variables throughout
[ ] No hardcoded credentials or endpoints
[ ] No cross-site scripting in components or Visualforce
[ ] CSRF protection on state-changing operations
[ ] Named Credentials for callouts
[ ] No storing of secrets in custom settings or metadata
[ ] Escaped output everywhere
```

**Running Salesforce Code Analyzer before submitting** catches most of it, and the graph engine specifically traces data flow for injection paths across method calls, which PMD alone does not. See [[09.13 - Apex Coding Standards and Best Practices]].

A rejected review costs weeks, so treating this as a development standard rather than a pre-submission task is the right approach.

## Choosing

| Situation | Approach |
| --- | --- |
| Small org, one team | Org development |
| Large org, several teams, coupling problems | Unlocked packages |
| Shared utilities across several orgs | Unlocked packages |
| Distributing to other companies | Managed, 2GP |
| Existing 1GP product with subscriber history | Stay 1GP unless restructuring anyway |
| Consulting deliverable installed at clients | Unlocked, or managed if IP matters |

**Do not adopt packaging because it is the recommended architecture.** The migration from org development to packages is substantial — untangling dependencies, deciding boundaries, and rebuilding the pipeline — and it is worth it when the coupling is causing real pain, not before.

**The signals that it is time:** deployments failing on unrelated tests, teams conflicting in the same directory, or an inability to release one feature without releasing everything.

## Section 18 in one paragraph

Layered architecture on Salesforce is one constraint and a set of consequences: nothing below the trigger handler references `Trigger`, which makes every service callable from a button, a batch job, a flow action, and a test with constructed records. Selectors centralize queries so `WITH USER_MODE` cannot be forgotten and consumption can be counted; domain classes hold per-object behaviour that is true regardless of the process; the unit of work batches DML and resolves parent Ids, at the cost of ruling out partial success. fflib is the reference implementation and its real value is the mocking infrastructure rather than the layering, which is achievable without it — and adopting it in a small org is the most common expensive mistake in this area. Custom Metadata turns thresholds, mappings, and handler registration into deployable configuration, trading compile-time safety for the ability to change behaviour without a release. Events decouple a publisher from consumers it does not know about, which is right when there are several and indirection when there is one. And every pattern in this section is over-engineering somewhere and necessary somewhere else — the architectural work is deciding which, for this org, this team, and this rate of change.
