# Indexes and Selective Queries

## The concept everything else in this section depends on

A query is **selective** when its filter uses an index and matches a small enough fraction of the object's rows that the engine can use that index.

A non-selective query on a large object is scanned rather than looked up, and beyond a threshold the platform refuses it entirely:

```
System.QueryException: Non-selective query against large object type
```

That error is the platform protecting other tenants ([[01.5 - Multi-Tenant Architecture]]), and it appears suddenly as data grows. A query written when the object had 50,000 rows fails at two million, with no code change.

## The selectivity thresholds

The optimizer uses approximate thresholds:

**Standard index** — selective if the filter matches under **30%** of the first million rows, and under **15%** of rows beyond that, capped at roughly 1 million rows returned.

**Custom index** — selective if the filter matches under **10%** of the first million rows, and under **5%** beyond that, capped at roughly 333,000 rows.

The exact numbers matter less than the shape: **as an object grows, the fraction a filter must match gets smaller.** A filter matching 20% of rows is selective at 100,000 records and non-selective at 5 million.

When a query has several filters, the optimizer needs **at least one** to be selective. Adding a selective filter to a non-selective query is usually the fix.

## What is indexed automatically

Standard indexes, present without asking:

- `Id`
- `Name`
- `OwnerId`
- `CreatedDate`, `LastModifiedDate`, `SystemModstamp`
- `RecordTypeId`
- All lookup and master-detail relationship fields
- Fields marked **Unique**
- Fields marked **External ID**
- `Email` on Contact and Lead
- Division, where used

That list drives a lot of design. **Marking a field as an external ID gives you an index**, which is why it appears in this course as advice for integration fields, phone-number normalization, and lookup keys — the idempotency benefit and the index come together.

## Custom indexes

Anything else needs a custom index, and **you cannot create one yourself.** It is a request to Salesforce Support, who evaluate the field's data distribution and create it if warranted.

They generally will not index:

- Fields with poor selectivity — a checkbox that is true for 90% of rows
- Formula fields that are non-deterministic (referencing `TODAY()`, `$User`, or another object's fields in some cases)
- Long text areas, rich text, multi-select picklists
- Fields on objects small enough not to need it

Deterministic formula fields **can** be indexed, which is the exception worth knowing. A formula referencing only fields on the same record, with no date or user functions, is a candidate.

## What defeats an index

Even on an indexed field, these prevent the optimizer using it:

**Leading wildcards.** `Name LIKE '%press%'` cannot use the index. `Name LIKE 'press%'` can. This is why the phone lookup in [[05.12 - CTI and Voice]] and the search box in [[08.8 - SOSL and Full Text Search]] both need different approaches.

**`!=` and `NOT IN`.** Negation typically matches most rows, so the optimizer skips the index.

**`OR` across fields where any branch is non-selective.** The whole query becomes non-selective. Two selective queries unioned in Apex often outperform one `OR` query.

**Null comparisons on nullable fields.** `WHERE Approved_Amount__c != null` matches most rows on most objects.

**Functions applied to the field.** Comparing a converted or calculated value cannot use the index on the raw field.

**Filtering on a formula field** in the general case, since formula fields are not indexed unless specifically arranged.

**Filtering only on a parent's field.** `WHERE Asset__r.Account.Tier__c = 'Enterprise'` traverses per row; the index that helps is on the child's own lookup field.

## The patterns that fix a non-selective query

**Add an indexed filter.** The single most effective fix. A date range on `CreatedDate`, an owner, a record type, or a lookup — anything that narrows the set using an index.

```sql
-- Non-selective on a large object
SELECT Id FROM Warranty_Claim__c WHERE Status__c != 'Closed'

-- Selective: the date filter uses the standard index on Claim_Date__c if indexed,
-- or CreatedDate which always is
SELECT Id FROM Warranty_Claim__c
WHERE CreatedDate = LAST_N_MONTHS:6 AND Status__c != 'Closed'
```

**Replace negation with enumeration.** `Status__c IN ('Submitted', 'Under Review')` can use an index; `Status__c != 'Closed'` cannot.

**Split `OR` into separate queries.** Two selective queries and a merged result beats one non-selective query.

```java
Map<Id, Warranty_Claim__c> combined = new Map<Id, Warranty_Claim__c>([
    SELECT Id, Claim_Number__c FROM Warranty_Claim__c WHERE Asset__c IN :assetIds
]);
combined.putAll([
    SELECT Id, Claim_Number__c FROM Warranty_Claim__c WHERE Account__c IN :accountIds
]);
```

Using a `Map` keyed on Id deduplicates the union automatically.

**Store what you filter.** A derived value computed by a before-save flow or a trigger, in a real indexed field, rather than a formula. This is the recurring recommendation from [[06.4 - Cross-Object Formulas and Limits]] and it exists because of this note.

**Mark integration keys as external IDs.** Free index, plus idempotent upserts.

## Skinny tables

For very large objects, Salesforce Support can create a **skinny table** — a flattened copy containing a subset of frequently used fields, maintained automatically in sync.

It avoids the join between the standard and custom field structures that multi-tenant storage otherwise requires, which is where the gain comes from.

Constraints: you cannot create or see them, they support a limited number of fields, they do not include soft-deleted records, and they are not automatically copied to sandboxes on refresh — which produces the confusing situation where production is fast and the sandbox is not.

Skinny tables are a support-managed optimization of last resort, requested after indexing and query restructuring have been exhausted. See [[16.9 - Skinny Tables and Custom Indexes]].

## Divisions

An older partitioning mechanism that segments an org's data into divisions, with queries scoped to one.

Rarely enabled in new orgs, and worth recognizing when inherited. Where it exists, it acts as a powerful implicit filter and is part of why some queries perform better than expected.

## Designing for selectivity

The decisions made early that determine whether queries perform later:

**Give every high-volume object an indexed field the common queries filter on.** Usually a date, a status stored as an indexed field, or a lookup.

**Mark external IDs from day one.** Retrofitting one onto a populated object requires backfilling every row.

**Prefer lookups to text keys.** Lookup fields are indexed; a text field holding a related record's name is not.

**Design queries around the indexed fields**, not around what is convenient to express.

**Estimate five-year volume during data modelling.** A query that is fine at 100,000 rows and fails at 5 million is a design problem, not a tuning problem. See [[02.12 - Schema Builder and Data Modelling Practice]].

## Verifying selectivity

Do not guess. The Query Plan tool in the Developer Console shows which index the optimizer would use and its estimated cost, and it is the subject of the next note: [[08.10 - Query Plan Tool and Query Optimization]].

## Practical guidance

**Always include at least one selective, indexed filter** on a query against a large object.

**Prefer `IN` to `!=`.**

**Avoid leading wildcards.** Use SOSL.

**Split `OR` conditions** into separate queries and merge with a Map.

**Store and index anything filtered at volume.** Formula fields are not the answer for filtering.

**Request an index rather than working around a slow query indefinitely.** Support will create one for a legitimately selective field.

**Test with production-scale data** in a Full sandbox. Selectivity problems are invisible in a small org, which is exactly why they reach production.
