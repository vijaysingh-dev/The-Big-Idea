# Memory Leaks from Closures and Timers

A closure keeps its defining environment alive ([[02.3 - Closures]]). That is the feature. It becomes a leak when the closure itself lives longer than the data deserves — and timers are the most common way to give a closure an unnecessarily long life.

## Timers are roots

A pending `setTimeout` or a running `setInterval` is a GC root. Everything the callback closes over stays reachable until the timer fires or is cleared.

```js
function startPolling(dataset) {   // dataset is 50 MB
  setInterval(() => {
    checkStatus(dataset.id);
  }, 1000);
}
```

The interval never stops, so `dataset` is never collected — even though only `dataset.id` is used. The fix is to capture the minimum:

```js
function startPolling(dataset) {
  const id = dataset.id;
  const handle = setInterval(() => checkStatus(id), 1000);
  return () => clearInterval(handle);
}
```

Returning the cleanup function is the pattern that makes this hard to get wrong ([[02.4 - Closure Patterns in Production]]).

`setTimeout` leaks too, just briefly — a 10-minute timeout retains its closure for 10 minutes. A "session expiry" timeout holding a large user object is a real, if bounded, cost.

## Shared closure contexts

The subtle one. V8 allocates **one context object per scope**, shared by every closure created in it. If any of those closures references a large variable, that variable stays alive for all of them.

```js
function setup() {
  const bigData = loadHugeDataset();
  const smallId = 1;

  const unused = () => bigData.length;      // never called, but exists
  const handler = () => console.log(smallId);

  window.addEventListener("click", handler);
}
```

`handler` only uses `smallId`, but because `unused` exists in the same scope and references `bigData`, the shared context retains `bigData` for as long as `handler` is registered. V8 does optimize away variables that *no* closure in the scope references, but one reference from any closure is enough to keep it.

The fix is scope isolation:

```js
function setup() {
  const smallId = createIdFrom(loadHugeDataset());  // bigData scoped inside
  window.addEventListener("click", () => console.log(smallId));
}
```

Extract the heavy work into its own function so the large value never shares a scope with the long-lived closure.

## Accumulating closures

```js
const handlers = [];

function onRouteChange(route) {
  handlers.push(() => render(route));   // grows forever
}
```

Any array or map of callbacks that is appended to but never pruned is a leak. Subscription systems must return an unsubscribe function, and callers must call it.

```js
function subscribe(fn) {
  listeners.add(fn);
  return () => listeners.delete(fn);
}
```

## Recursive setTimeout

```js
function poll() {
  fetchStatus().then(() => setTimeout(poll, 1000));
}
poll();  // no way to stop it
```

Each iteration schedules the next, and there is no handle to cancel. Keep the handle, or use an `AbortSignal` ([[04.6 - AbortController and Cancellation]]):

```js
function poll({ signal }) {
  if (signal.aborted) return;
  fetchStatus().then(() => {
    if (!signal.aborted) {
      const id = setTimeout(() => poll({ signal }), 1000);
      signal.addEventListener("abort", () => clearTimeout(id), { once: true });
    }
  });
}
```

## In React

```jsx
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000);
  return () => clearInterval(id);   // required
}, []);
```

Without the cleanup, unmounting the component leaves the interval running forever, holding the closure — including `setTick`, which holds the fiber, which holds the component's entire subtree. One forgotten `clearInterval` in a route-level component leaks the whole page's state every time the user navigates.

The same applies to `setTimeout` in effects, `requestAnimationFrame` loops (`cancelAnimationFrame`), and any subscription.

A related trap is state updates after unmount. Older React warned about this; current versions do not, but the underlying problem — a pending callback holding a reference to an unmounted tree — is still real.

## Closures over DOM nodes

```js
function attach(node) {
  const bigTable = node.querySelector("table");   // large subtree

  setInterval(() => {
    console.log("tick");   // does not use bigTable
  }, 1000);
}
```

If `bigTable` shares a context with the interval closure, the entire table subtree is retained even after it is removed from the document — a detached DOM leak ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

## How senior engineers actually use this

**They pair every `set` with a `clear` in the same block.** The `useEffect` cleanup return is the enforcement mechanism in React; in vanilla code it is a returned disposer.

**They capture the minimum.** If a callback needs an id, close over the id, not the object it came from. This costs one line and removes an entire retention path.

**They prefer `AbortController` for cancellation** because one signal can tear down timers, listeners and fetches together ([[04.6 - AbortController and Cancellation]]).

**They audit long-lived subscriptions.** Anything registered at app startup — a global interval, a WebSocket handler, a store subscription — holds whatever it closes over for the session's lifetime. These deserve explicit review.

## Common pitfalls

- `useEffect` with a timer and no cleanup.
- Recursive `setTimeout` with no cancellation handle.
- Closing over a large object to use one small field of it.
- An unused closure in the same scope retaining data for a used one.
- Subscription arrays that grow without a corresponding removal.
- `setInterval` continuing to fire in a background tab (throttled, but not stopped) and accumulating work.

## Interview angle

"What causes memory leaks in JavaScript" should get closures and timers first, with a concrete example. The shared-context point — that an unused closure can retain data for a used one in the same scope — is a genuinely advanced detail that few candidates mention. Pairing it with "and in React, a missing `useEffect` cleanup leaks the whole subtree" connects the theory to daily work.
