# Queue vs Log

#backend #streaming #kafka #architecture

> **In one line:** A queue deletes a message once someone has handled it; a log keeps it and lets every reader track its own position — and that single difference is why Kafka is not a faster RabbitMQ.

---

## The Idea

```
QUEUE
  Producer → [ msg3 msg2 msg1 ] → Consumer
                                    consumed messages are GONE

LOG
  Producer → [ msg1 msg2 msg3 msg4 msg5 ]
                      ▲         ▲
                 consumer A   consumer B      each tracks its own offset
                                              nothing is deleted
```

| | Queue | Log |
|---|---|---|
| After consumption | **Deleted** | **Retained** |
| Position tracked by | The broker | **The consumer** |
| Multiple consumers | Compete for messages | **Each reads everything independently** |
| Replay | Impossible | **Trivial — reset the offset** |
| Ordering | Best-effort | **Strict within a partition** |
| Adding a consumer later | Sees only new messages | **Can read from the beginning** |

💡 **The mental shift: a log is a durable, ordered, replayable record of what happened. A queue is a work distribution mechanism.** They solve different problems and the confusion between them causes real architectural mistakes.

---

## Commands versus Events

The distinction that determines which one you need.

```
COMMAND   "process document 42"        → an instruction. One handler. A queue
EVENT     "document 42 was indexed"    → a fact. Many interested parties. A log
```

| | Command | Event |
|---|---|---|
| Tense | Imperative | **Past tense** |
| Consumers | Exactly one | Zero or many |
| Producer knows the consumer | Yes | **No** |
| Can be rejected | Yes | **No — it already happened** |
| Naming | `SendEmail` | `EmailSent` |

💡 **The test: if you added a second consumer, would the producer need to change?** For a command, yes — you would need to decide which handler gets it. For an event, no — the new consumer simply subscribes.

⚠️ **The most common architectural mistake in this area is using a queue for events**, because a queue consumes destructively. A second team wanting the same events needs a second queue, which means the producer must know about them — and the decoupling you wanted has evaporated.

## Kafka's Model

```
Topic: documents
  Partition 0: [ 0 ][ 1 ][ 2 ][ 3 ][ 4 ]
  Partition 1: [ 0 ][ 1 ][ 2 ]
  Partition 2: [ 0 ][ 1 ][ 2 ][ 3 ]
```

| Concept | |
|---|---|
| **Topic** | A named stream of records |
| **Partition** | An ordered, append-only sequence. The unit of parallelism |
| **Offset** | A record's position within a partition. Monotonic, never reused |
| **Consumer group** | A set of consumers sharing the work of a topic |

### Partitions determine everything

```python
partition = hash(key) % num_partitions
```

⚠️ **Ordering is guaranteed within a partition and nowhere else.** Two records in different partitions have no defined relative order.

💡 **Choosing the partition key is choosing what must stay ordered.** Keying by `document_id` means all events for one document are ordered relative to each other, with no ordering guarantee between documents — which is almost always exactly what you want ([[08.2 - Queue Semantics]]).

```python
await producer.send("documents", key=document_id.encode(), value=payload)
```

⚠️ **A null key means round-robin distribution and no ordering at all.** If you find yourself needing ordering later, you cannot retrofit it without repartitioning.

**Choose the key deliberately at design time**, and write down what it guarantees.

### Partition count

```
Max parallelism per consumer group = number of partitions
```

⚠️ **A consumer group cannot have more useful consumers than partitions.** With 3 partitions and 10 consumers, 7 sit idle.

💡 **Over-provision partitions, within reason.** Increasing partition count later **breaks key-to-partition affinity** — `hash(key) % 6` sends a key to a different partition than `hash(key) % 3` did, so ordering across the change is lost.

| Consideration | |
|---|---|
| Too few | Limits parallelism; hard to increase later |
| Too many | More open files, more memory, longer rebalances, higher latency |
| Reasonable start | 2–4× your expected peak consumer count |

**Decreasing partition count is impossible.** Start higher than you think you need.

## Consumer Groups

```
Topic with 4 partitions

Group "indexer":     consumer-1 → P0, P1     consumer-2 → P2, P3
Group "analytics":   consumer-1 → P0,P1,P2,P3
```

💡 **Each group gets its own copy of the stream and its own offsets.** Adding the analytics group does not affect the indexer at all, and the producer knows nothing about either.

**This is the property that makes a log the right substrate for events.**

### Rebalancing

When a consumer joins or leaves, partitions are reassigned.

```
consumer-2 dies → its partitions are reassigned to consumer-1
```

⚠️ **During a rebalance, consumption stops.** With the older eager protocol, *every* consumer stops and reassigns — a "stop-the-world" pause that can last seconds.

```python
# Incremental cooperative rebalancing — only affected partitions move
partition_assignment_strategy = "cooperative-sticky"
```

💡 **Use cooperative-sticky.** It reassigns only what must move, so a consumer joining does not pause the whole group. On a deploy with a rolling restart, the difference between eager and cooperative is minutes of stalled consumption versus seconds.

⚠️ **Frequent rebalances are a real production problem**, and the usual cause is a consumer exceeding `max.poll.interval.ms` — the group coordinator assumes it is dead and rebalances.

```
max.poll.interval.ms = 300000      # 5 min: how long between poll() calls
session.timeout.ms = 45000         # how long without a heartbeat before eviction
```

**If processing a batch takes longer than `max.poll.interval.ms`, you are evicted mid-work**, the partitions move, and the work is redone. **Either reduce `max.poll.records` or increase the interval.**

## Offsets

```python
await consumer.commit()                    # commit current position
```

| Strategy | Semantics |
|---|---|
| **Auto-commit** | Periodic, in the background. **At-most-once or duplicates, unpredictably** |
| **Commit after processing** | At-least-once |
| **Commit before processing** | At-most-once |
| **Store offset with your data** | Exactly-once effects |

⚠️ **`enable.auto.commit=true` is the default and it is the wrong default.** Offsets are committed on a timer regardless of whether the records were processed, so a crash can lose messages *and* duplicate them depending on timing.

```python
consumer = AIOKafkaConsumer(..., enable_auto_commit=False)

async for msg in consumer:
    await process(msg)
    await consumer.commit()          # at-least-once
```

💡 **The strongest pattern: store the offset in the same transaction as the effect.**

```python
async with conn.transaction():
    await apply_effect(msg)
    await conn.execute(
        "INSERT INTO consumer_offsets (topic, partition, offset) VALUES ($1,$2,$3) "
        "ON CONFLICT (topic, partition) DO UPDATE SET offset = $3",
        msg.topic, msg.partition, msg.offset,
    )
```

**Now the offset and the effect commit atomically**, and on restart you seek to your stored offset rather than Kafka's ([[07.5 - Idempotency Keys and Deduplication]]). This is exactly-once effects, done properly.

## Retention and Compaction

```
log.retention.hours = 168          # 7 days
log.retention.bytes = -1           # unlimited
cleanup.policy = delete            # or compact
```

### Time or size retention

Records older than the retention period are deleted, whole segments at a time.

💡 **Retention determines how far back you can replay.** Seven days means you can rebuild a derived store from the last week. If you need to rebuild from the beginning of time, you need either infinite retention or a snapshot plus recent events.

### Compaction

```
cleanup.policy = compact
```

Keeps only the **latest record per key**, forever.

```
Before: [a:1] [b:1] [a:2] [c:1] [a:3] [b:2]
After:  [c:1] [a:3] [b:2]
```

💡 **A compacted topic is a durable key-value store with a change history.** It is how you distribute configuration, permissions or reference data — a new consumer reads from offset 0 and gets the current state of every key.

⚠️ **A null value is a tombstone**, deleting the key after `delete.retention.ms`. Forgetting this means deleted entities reappear when a consumer rebuilds.

**`cleanup.policy = compact,delete`** does both — compact old keys and delete records older than the retention period.

## When a Log Is Right

| Signal | Log |
|---|---|
| **Multiple consumers of the same data** | Yes |
| **You might need to replay** | Yes |
| Rebuilding a derived store | Yes |
| An audit trail is required | Yes |
| Consumers added later need history | Yes |
| Ordering per entity matters | Yes |
| High throughput, sequential writes | Yes |

| Signal | Queue |
|---|---|
| One handler, one instruction | Queue |
| Work distribution across workers | Queue |
| Per-message retry with backoff | **Queue** |
| Dead letter handling | **Queue** |
| Delayed execution | Queue |
| Priorities | Queue |

⚠️ **Kafka is bad at per-message retry.** A log has no concept of "retry this one message later" — the offset is a position, not a set of individual messages. Retrying means either blocking the partition or sending to a retry topic ([[09.7 - Replay Backfill and Reprocessing]]).

💡 **The strongest signal for a queue: you need per-message retry with backoff and a DLQ.** That is what task queues are built for and what logs are not ([[08.6 - Retries Backoff and Dead Letters]]).

**Most systems need both**, and the split follows the command/event distinction.

## In Production

### The head-of-line problem

```
Partition 0: [ msg1 ][ msg2 ][ msg3 ]
                ▲ fails repeatedly
```

⚠️ **A consumer that cannot process a record and will not advance blocks the entire partition** ([[02.5 - Head of Line Blocking]]). Every subsequent record for every key in that partition waits.

Three responses:

| Response | |
|---|---|
| **Skip and send to a DLQ topic** | Advance the offset, handle it separately. **Usually right** |
| **Retry topics with delays** | `retry-5s`, `retry-1m`, `retry-10m`, then DLQ |
| **Block** | Correct only when ordering is genuinely inviolable |

💡 **The retry-topic pattern is the standard Kafka answer:** a failing record is produced to a retry topic with a delay, and a separate consumer handles it. **The main partition advances immediately**, which preserves liveness at the cost of ordering for that record.

⚠️ **Write down which topics can tolerate skipping.** For an audit log or a ledger, skipping is wrong and blocking is correct — and that means a poison record is a page, not a background task.

### Consumer lag

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
    --describe --group indexer
```

```
TOPIC       PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
documents   0          145823          145901          78
documents   1          98234           102891          4657     ← this one
```

💡 **Lag is the single most important Kafka metric**, and it should be measured per partition, not just per group. A group with total lag of 5,000 spread evenly is healthy; the same 5,000 concentrated on one partition means one consumer is stuck or one key is hot.

```python
consumer_lag.labels(topic=t, partition=p, group=g).set(lag)
consumer_lag_seconds.labels(...).set(time_lag)      # ← better
```

⚠️ **Lag in records is less useful than lag in time.** 10,000 records might be a second or an hour. Compute the timestamp difference between the last committed record and the log end.

### Producer configuration

```python
producer = AIOKafkaProducer(
    acks="all",                        # all in-sync replicas
    enable_idempotence=True,           # dedup on the broker
    max_in_flight_requests_per_connection=5,
    compression_type="lz4",
    linger_ms=10,                      # batch briefly
)
```

⚠️ **`acks=1` (leader only) can lose data** if the leader fails before replicas catch up. `acks=all` with `min.insync.replicas=2` is the durable configuration.

💡 **`enable_idempotence=True` prevents duplicate records from producer retries** — the broker deduplicates on producer ID and sequence number. **It also allows `max_in_flight > 1` without reordering**, which without idempotence would let a retry overtake a later record ([[07.5 - Idempotency Keys and Deduplication]]).

### Kafka is not the default

⚠️ **Kafka is significant operational weight**: a cluster (or KRaft quorum), partition planning, consumer group management, and a whole vocabulary your team must learn.

```
Do you need replay, multiple consumers, or an audit trail?
├── NO  → a task queue. Do not add Kafka
└── YES → is Redis Streams sufficient?
    ├── Moderate volume, short retention, one datacentre → Redis Streams
    └── High volume, long retention, many consumers      → Kafka
```

💡 **Redis Streams gives you the log model — consumer groups, offsets, replay — without a Kafka cluster** ([[04.6 - Scaling Long Lived Connections]]). For a system Conduit's size it is often sufficient, and the migration path to Kafka exists if volume grows.

**Conduit adds Kafka in phase 5 deliberately**, because the search index must be rebuildable by replay and multiple consumers need the same document events. **That is a real requirement, and it is the justification.**

## Codebase

**Repo:** `apache/kafka`, `aio-libs/aiokafka`, `redis/redis`

**Question to answer:** How does Kafka store a partition on disk, and what makes reads and writes sequential? Then: in a consumer group, what exactly happens during a rebalance, and how does cooperative-sticky differ from eager?

**Read, in order:**

1. `kafka/core/src/main/scala/kafka/log/LogSegment.scala` and `UnifiedLog.scala` — **the segment layout: an append-only data file plus a sparse offset index.** This is why writes are sequential and reads are a binary search plus a scan
2. `kafka/clients/src/main/java/.../consumer/internals/ConsumerCoordinator.java` — **`onJoinPrepare` and `onJoinComplete`.** The rebalance protocol. **The answer to the second question**
3. `kafka/clients/src/main/java/.../consumer/CooperativeStickyAssignor.java` — **how it computes a minimal reassignment** rather than revoking everything
4. `kafka/clients/src/main/java/.../producer/internals/RecordAccumulator.java` — batching by partition, and what `linger_ms` controls
5. `aiokafka/aiokafka/consumer/consumer.py` — the Python client's offset handling and commit modes
6. `redis/src/t_stream.c` — **Redis Streams**, for comparison. Consumer groups and pending-entry lists implement the same model with different tradeoffs

💡 The `LogSegment` reading is the one that explains Kafka's performance. **A partition is a sequence of files appended to sequentially, with a sparse index; reads are sequential too, and the OS page cache does most of the work.** There is no B-tree, no random write, and no in-place update — which is why a single broker handles very high throughput on ordinary disks ([[06.1 - Storage Engines]]).

**Size:** 2–3 sessions.

**Part 1 — Build a log.** Append-only segments with a sparse index, keyed partitioning, consumer groups with offset tracking, retention by time and size, and compaction.

**Test:** two consumers in a group split partitions; one dies and the other takes over from the correct offset; a replay from offset 0 produces identical results.

**This is the flagship drill of section 09.** After it, Kafka's behaviour is recognisable rather than mysterious.

**Part 2 — The same requirement, both ways.** "Notify the search indexer and the analytics pipeline when a document changes."

Implement with a task queue and with your log.

Then add a third consumer. **Measure what had to change in each** — the producer should be untouched in the log version and modified in the queue version.

Then replay the last hour into a new consumer. **The queue version cannot do it at all.**

**Part 3 — Partition key consequences.** A real Kafka cluster, 6 partitions.

Produce document events keyed three ways: by `document_id`, by `org_id`, and with a null key.

For each measure: ordering guarantees observed, partition balance, and whether one large organisation creates a hot partition.

Then **increase the partition count from 6 to 12** and confirm that key-to-partition affinity breaks — the same key now lands elsewhere, and ordering across the change is lost.

**Part 4 — Rebalancing.** A consumer group of 4 on 12 partitions, processing continuously.

Add a fifth consumer. Measure **total consumption stall time** with `range` and with `cooperative-sticky` assignors.

Then a rolling restart of all consumers, and measure the same.

**Then cause an eviction:** make processing exceed `max.poll.interval.ms`. **Confirm the consumer is evicted mid-work, partitions move, and work is redone.** Then fix it by reducing `max.poll.records`.

**Part 5 — The offset crash matrix.** Kill a consumer at six points: before poll, after poll before processing, mid-processing, after processing before commit, after commit, and during a rebalance.

Run against auto-commit, manual commit after processing, and offset-stored-with-the-effect.

**Eighteen cells.** Record lost, duplicated, or exactly-once.

**Only the third should be exactly-once at every point.**

**Part 6 — Compaction and tombstones.** A compacted topic holding organisation configuration.

Write 10,000 updates across 100 keys. Force compaction. **Confirm only 100 records remain and a new consumer reading from 0 gets current state.**

Then delete a key with a tombstone. Confirm it disappears — then wait past `delete.retention.ms`, have a new consumer read from 0, and **confirm the key is simply absent rather than resurrected.**

Then deliberately get it wrong: delete by writing an empty value instead of null, and show the key persisting.

**Part 7 — Poison record.** A record that always fails processing, in a partition with 10,000 others.

**Confirm the partition is completely blocked** and measure lag growth.

Then implement the retry-topic pattern with three delay tiers plus a DLQ. **Confirm the main partition advances immediately.**

Then measure what was lost: the ordering guarantee for that key.

**Write in `FINDINGS.md` which Conduit topics can tolerate skipping and which cannot.**

**Done when:**
- Your log handles group rebalancing and replay-from-zero correctly
- Adding a third consumer required no producer change in the log version
- You have shown partition count changes breaking key affinity
- Cooperative-sticky measurably reduced rebalance stall time
- Your eighteen-cell offset matrix shows only transactional offsets achieving exactly-once
- Tombstones work, and the wrong deletion method demonstrably does not
- The retry-topic pattern unblocked a partition, and you know what it cost
