# Future Methods

## The oldest async mechanism

```java
public with sharing class ErpNotificationService {

    @future(callout=true)
    public static void notifyApproval(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Claim_Amount__c, Asset__r.SerialNumber
            FROM Warranty_Claim__c WHERE Id IN :claimIds
        ];

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/claims/approved');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(ClaimPayload.from(claims)));

        HttpResponse res = new Http().send(req);
        if (res.getStatusCode() >= 300) {
            throw new IntegrationException('ERP notification failed: ' + res.getStatusCode());
        }
    }
}
```

`@future` marks a static method to run later, in its own transaction. `callout=true` is required for any method making an HTTP call.

## The rules

**Static and void.** No return value, ever.

**Parameters must be primitives or collections of primitives.** No sObjects, no custom classes, no `Map<Id, Account>`.

This is the constraint that shapes every use. Passing a record means serializing it:

```java
@future
public static void processClaim(String serializedClaim) {
    Warranty_Claim__c claim = (Warranty_Claim__c) JSON.deserialize(
        serializedClaim, Warranty_Claim__c.class
    );
}
```

Passing Ids and re-querying is better anyway — the record may have changed since the caller ran.

**Cannot be called from another future method**, or from a batch job, or from another async context in most cases.

**Cannot be chained.** A future method cannot enqueue another.

**No way to monitor it.** It appears in `AsyncApexJob`, and there is no job Id returned to the caller.

## Why this is legacy

Queueable does everything future does, better:

| | `@future` | Queueable |
| --- | --- | --- |
| Parameters | Primitives only | Any type, including sObjects |
| Returns a job Id | No | Yes |
| Chainable | No | Yes |
| Callable from async | No | Yes, with limits |
| Monitorable | Barely | Fully, via the job Id |
| Failure handling | None | Transaction Finalizers |

**New code should use Queueable.** There is no capability future has that Queueable lacks, and several it has that future does not. See [[12.3 - Queueable Apex]].

## Where you still meet it

**The mixed DML workaround.** The most common surviving legitimate use, because it is the smallest amount of code that solves the problem.

```java
public with sharing class UserProvisioningService {

    public static void provision(Account account, User newUser) {
        insert account;
        createUserAsync(JSON.serialize(newUser));
    }

    @future
    private static void createUserAsync(String serializedUser) {
        // a separate transaction, so setup and non-setup DML no longer conflict
        insert (User) JSON.deserialize(serializedUser, User.class);
    }
}
```

See [[10.7 - Mixed DML and Setup Objects]].

**Legacy code.** Any org more than a few years old has future methods, and rewriting working ones is rarely the highest-value work. Migrate them when you touch them for another reason.

**Simple fire-and-forget callouts** where nothing needs monitoring. Defensible, and Queueable costs one extra class.

## The bulkification trap

Future methods are called per invocation, and the 50-async-calls limit applies.

```java
// Wrong: 200 future calls, fails at 50
for (Warranty_Claim__c claim : Trigger.new) {
    ErpNotificationService.notifyApproval(new Set<Id>{ claim.Id });
}

// Correct: one call with all the ids
Set<Id> claimIds = new Set<Id>();
for (Warranty_Claim__c claim : Trigger.new) {
    claimIds.add(claim.Id);
}
if (!claimIds.isEmpty()) {
    ErpNotificationService.notifyApproval(claimIds);
}
```

The method taking a `Set<Id>` rather than a single `Id` is what makes the correct form possible. A future method taking one Id invites the wrong call site.

## The ordering problem

**Future methods have no guaranteed execution order.** Two calls made in sequence may run in either order, or concurrently.

```java
ErpNotificationService.sendHeader(orderId);
ErpNotificationService.sendLines(orderId);   // may arrive first
```

This is a real source of integration bugs — the external system receives lines before the header and rejects them.

Queueable chaining guarantees order, which is one of the stronger practical arguments for it.

## No failure handling

A future method that throws does two things: rolls back its own transaction, and logs an entry in `AsyncApexJob` that nobody looks at.

There is no callback, no retry, and no way for the caller to know. The only defence is handling it inside the method:

```java
@future(callout=true)
public static void notifyApproval(Set<Id> claimIds) {
    try {
        // ... the callout
    } catch (Exception e) {
        // logging inside the method is the only failure signal available
        insert new Integration_Log__c(
            Context__c = 'ErpNotification',
            Message__c = e.getMessage(),
            Stack_Trace__c = e.getStackTraceString(),
            Record_Ids__c = String.join(new List<Id>(claimIds), ',')
        );
    }
}
```

Note the log insert works here — the exception was caught, so the transaction commits. If it propagated, the log would roll back with it.

Queueable with a Transaction Finalizer handles this properly, with retry logic and a guaranteed post-execution hook. See [[12.6 - Transaction Finalizers]].

## Limits

Future methods run with async limits: 200 SOQL queries, 12 MB heap, 60 seconds CPU, 200 records per DML.

The enqueue caps:

- **50 future calls per synchronous transaction**
- **250,000 async executions per day** org-wide, shared with every other async mechanism
- **A limit on concurrent future methods** at the org level

The daily allocation is the one that catches high-volume integrations. Per-record future calls exhaust it in hours.

## Testing

```java
@IsTest
static void approvalTriggersErpNotification() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock());
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    claim.Status__c = 'Approved';
    update claim;
    Test.stopTest();   // the future method runs here

    Warranty_Claim__c refreshed = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c);
}
```

Assertions go **after** `Test.stopTest()`. The method has not run before it.

A future method cannot be called from a test method that has already called one, which occasionally forces test restructuring.

## Migrating to Queueable

Mechanical, and worth doing when you are in the file anyway.

```java
// Before
@future(callout=true)
public static void notifyApproval(Set<Id> claimIds) {
    // work
}
ErpNotificationService.notifyApproval(claimIds);
```

```java
// After
public with sharing class ErpNotificationQueueable
    implements Queueable, Database.AllowsCallouts {

    private final Set<Id> claimIds;

    public ErpNotificationQueueable(Set<Id> claimIds) {
        this.claimIds = claimIds;
    }

    public void execute(QueueableContext context) {
        // the same work
    }
}
System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

What you gain: a job Id for monitoring, the ability to attach a Finalizer for retry, chaining, richer parameters, and callability from other async contexts.

## Practical guidance

**Use Queueable in new code.** There is no reason to write a future method today except brevity in the mixed-DML case.

**Take a collection parameter**, never a single Id.

**Call it once, not per record.**

**Do not rely on execution order** between future methods.

**Handle exceptions inside the method**, since there is no external failure signal.

**Migrate future methods opportunistically** rather than as a project.
