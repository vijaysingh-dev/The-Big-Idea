# REST API

## The default choice

The REST API is what most integrations use. JSON, standard HTTP verbs, and a resource model that maps directly onto objects and records.

```
https://myorg.my.salesforce.com/services/data/v62.0/sobjects/Warranty_Claim__c/a0X5g000001AbCdEAK
```

The version in the path pins behaviour. Old versions eventually retire, which is why auditing what your integrations actually use matters. See [[01.11 - Release Cycle, Trust and Status]].

## The core resources

```
GET    /services/data/                              available versions
GET    /services/data/v62.0/                        available resources
GET    /services/data/v62.0/sobjects/               all objects
GET    /services/data/v62.0/sobjects/Account/describe   full metadata for one object

POST   /services/data/v62.0/sobjects/Account         create
GET    /services/data/v62.0/sobjects/Account/{id}    retrieve
PATCH  /services/data/v62.0/sobjects/Account/{id}    update
DELETE /services/data/v62.0/sobjects/Account/{id}    delete

GET    /services/data/v62.0/query/?q=SELECT+Id+FROM+Account    SOQL
GET    /services/data/v62.0/queryAll/?q=...                    including deleted
GET    /services/data/v62.0/search/?q=FIND+{press}             SOSL
```

**PATCH, not PUT.** Salesforce updates only the fields present in the body. Sending a partial record updates those fields and leaves the rest alone, which is the behaviour you want and differs from a strict REST PUT.

## Retrieving specific fields

```
GET /services/data/v62.0/sobjects/Warranty_Claim__c/a0X5g000001AbCdEAK?fields=Claim_Number__c,Status__c,Claim_Amount__c
```

Without `fields`, the response contains every field on the object — expensive on a wide object with formula fields, and rarely what the caller needs.

## Upsert by external ID

The single most useful REST operation for integrations.

```
PATCH /services/data/v62.0/sobjects/Warranty_Claim__c/ERP_Claim_Id__c/CLM-99201
```

```json
{
  "Claim_Amount__c": 150000,
  "Status__c": "Under Review"
}
```

The external system uses **its own key** in the URL. No Salesforce Id, no lookup, and the operation is idempotent — a retry updates rather than duplicates.

The response distinguishes the outcomes:

```json
{ "id": "a0X5g000001AbCdEAK", "success": true, "created": true }
```

**201 Created** for an insert, **204 No Content** for an update. This is the mechanism that makes retry-safe integration straightforward, and it is the reason external IDs appear throughout this course. See [[10.3 - Upsert, Merge and External IDs]].

## Setting relationships by external ID

A lookup can be set using the parent's external key, which removes the ID-mapping step from a migration entirely.

```json
{
  "Claim_Amount__c": 150000,
  "Asset__r": { "ERP_Asset_Id__c": "MCH-88213" }
}
```

The nested object under the **relationship name** — `Asset__r`, not `Asset__c` — tells the platform to resolve the parent by that field.

## Querying

```
GET /services/data/v62.0/query/?q=SELECT+Id,Name,Status__c+FROM+Warranty_Claim__c+WHERE+Status__c='Submitted'
```

The query must be URL-encoded. Large or complex queries are better sent as a POST to `/query/` with the query in the body, avoiding URL length limits.

Pagination is server-side and automatic:

```json
{
  "totalSize": 4213,
  "done": false,
  "records": [ "... 2000 records ..." ],
  "nextRecordsUrl": "/services/data/v62.0/query/01g5g00000ABCDeAAN-2000"
}
```

The client follows `nextRecordsUrl` until `done` is true. This is a proper server-side cursor with none of `OFFSET`'s problems, and it is the correct way for an external system to read a large table. See [[08.5 - LIMIT, OFFSET, ORDER BY and Pagination]].

Batch size can be requested up to 2,000:

```
Sforce-Query-Options: batchSize=200
```

## sObject Collections

Up to 200 records in one call, which is the difference between one API request and 200.

```
POST /services/data/v62.0/composite/sobjects
```

```json
{
  "allOrNone": false,
  "records": [
    { "attributes": {"type": "Warranty_Claim__c"}, "Claim_Amount__c": 150000, "Status__c": "Submitted" },
    { "attributes": {"type": "Warranty_Claim__c"}, "Claim_Amount__c": 90000,  "Status__c": "Submitted" }
  ]
}
```

`allOrNone: false` gives partial success, with a per-record result — the REST equivalent of `Database.insert(records, false)`.

The `attributes.type` on each record is required and is easy to omit.

Upsert by external ID works too:

```
PATCH /services/data/v62.0/composite/sobjects/Warranty_Claim__c/ERP_Claim_Id__c
```

**Any integration writing more than a handful of records should use this**, not individual calls. It is the simplest and largest reduction in API consumption available.

## Response codes

```
200  OK
201  Created
204  No Content — successful update or delete
300  Multiple Choices — an external Id matched several records
400  Bad Request — malformed, or a validation error
401  Unauthorized — expired or invalid token
403  Forbidden — permissions, or an exceeded limit
404  Not Found
405  Method Not Allowed
409  Conflict
415  Unsupported Media Type
500  Server Error
```

Errors carry a structured body:

```json
[{
  "message": "This claim exceeds the coverage limit on the service contract.",
  "errorCode": "FIELD_CUSTOM_VALIDATION_EXCEPTION",
  "fields": ["Claim_Amount__c"]
}]
```

`errorCode` is what a client should branch on. `REQUEST_LIMIT_EXCEEDED` means the daily API allocation is gone; `UNABLE_TO_LOCK_ROW` is transient and worth retrying; `FIELD_CUSTOM_VALIDATION_EXCEPTION` is permanent.

**300 Multiple Choices** deserves attention — it means the external ID is not unique, which is a data problem rather than a request problem. Marking external ID fields Unique prevents it.

## Headers worth knowing

```
Authorization: Bearer {access_token}
Content-Type: application/json
Accept: application/json

Sforce-Auto-Assign: false          skip assignment rules
Sforce-Query-Options: batchSize=200
If-Modified-Since: {http-date}     conditional retrieval
Sforce-Call-Options: client=MyIntegration
```

`Sforce-Auto-Assign` is the REST counterpart of the assignment rule DML option. By default the API does **not** run assignment rules, which is why leads and cases created through it stay with the integration user unless the header is set or the operation explicitly requests it. This is the same silent failure described in [[05.3 - Case Assignment and Auto-Response Rules]].

## Calling out from Apex

The reverse direction — Salesforce as the client:

```java
public with sharing class ErpClient {

    public static ErpResponse fetchInventory(String serialNumber) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/inventory?serial='
            + EncodingUtil.urlEncode(serialNumber, 'UTF-8'));
        req.setMethod('GET');
        req.setHeader('Accept', 'application/json');
        req.setTimeout(30000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() == 200) {
            return (ErpResponse) JSON.deserialize(res.getBody(), ErpResponse.class);
        }
        if (res.getStatusCode() == 404) {
            return ErpResponse.notFound();
        }
        throw new IntegrationException(
            'Inventory lookup failed: ' + res.getStatusCode() + ' ' + res.getBody()
        );
    }
}
```

`callout:ERP_System` resolves through a Named Credential, so no URL or credential appears in code. `urlEncode` on any value going into a query string is not optional.

The default timeout is 10 seconds; the maximum is 120. Setting it explicitly makes the behaviour visible.

See [[13.14 - Apex Callouts]] and [[13.13 - Named Credentials and External Credentials]].

## Rate and concurrency limits

**The daily API request allocation** is the binding constraint. Every REST call counts, including describe calls and query pagination requests.

```
GET /services/data/v62.0/limits/
```

```json
{
  "DailyApiRequests": { "Max": 1000000, "Remaining": 743210 },
  "DailyBulkApiBatches": { "Max": 15000, "Remaining": 14980 }
}
```

An integration checking this and backing off when the remaining allocation is low is more robust than one that discovers exhaustion through `REQUEST_LIMIT_EXCEEDED`.

**25 concurrent long-running requests** — over 20 seconds — per org. Exceeding it produces rejections that look like an outage.

## Reducing API consumption

The techniques, in order of impact:

**sObject Collections** for writes. 200 records per call.

**Composite API** to bundle unrelated operations into one round trip. See [[13.5 - Composite and Composite Graph API]].

**Bulk API** for anything above a few thousand records. See [[13.4 - Bulk API 2.0]].

**Push rather than poll.** CDC or platform events, so the external system is notified rather than asking. See [[12.9 - Change Data Capture]].

**Query incrementally** using `SystemModstamp`, not full extracts:

```
GET /services/data/v62.0/query/?q=SELECT+Id,Status__c,SystemModstamp+FROM+Warranty_Claim__c+WHERE+SystemModstamp>2026-08-01T00:00:00Z+ORDER+BY+SystemModstamp+ASC
```

`SystemModstamp` rather than `LastModifiedDate`, because some platform updates do not touch the latter. See [[02.2 - Standard Objects and the Core CRM Data Model]].

## Tooling

```bash
# The CLI issues authenticated REST calls without managing tokens
sf api request rest '/services/data/v62.0/sobjects/Account/describe' --target-org my-sandbox

sf api request rest '/services/data/v62.0/composite/sobjects' \
  --method POST --body @records.json --target-org my-sandbox
```

**Workbench** for exploratory work in a browser. **Postman**, with the official Salesforce collection, for building and testing requests.

## Practical guidance

**Use PATCH upsert on an external ID** as the default write operation.

**Use sObject Collections** for anything above a few records.

**Set `Sforce-Auto-Assign`** where assignment rules should run.

**Branch on `errorCode`**, not the message text.

**Check `/limits/`** and back off before exhaustion.

**Query incrementally on `SystemModstamp`.**

**Follow `nextRecordsUrl`** rather than paginating manually.

**Encode everything** going into a URL.
