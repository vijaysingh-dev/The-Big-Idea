# Concurrency and Long Running Requests

## The ten-second rule

**No more than 10 synchronous Apex requests running longer than 5 seconds each, per org, at once.**

Beyond that, new requests are **rejected** with `CONCURRENT_REQUESTS_LIMIT_EXCEEDED` — not queued, not slowed. Rejected.

This limit is different in character from the others in this section. It is not about what one transaction consumes; it is about how many slow transactions the org has in flight simultaneously.

## Why it exists

Each synchronous request occupies an application server thread. A thread held for six seconds is a thread unavailable to every other user on that server.

Ten concurrent slow requests is the point at which one org's slow code starts affecting the shared infrastructure meaningfully. The cap protects other tenants, and it protects the org from itself — without it, a slow endpoint under load would consume every available thread.

## What counts

**Synchronous Apex running over 5 seconds.**

```
Counts:      Apex triggers and their downstream automation
             @AuraEnabled controller methods
             Apex REST and SOAP endpoints
             Visualforce controllers
             Synchronous API calls executing Apex

Does not:    Batch Apex, Queueable, future methods, scheduled Apex
             Platform event subscribers
             Callout wait time within a Continuation
             Reports and standard page loads
```

**Async is exempt**, which is one of the strongest architectural arguments for it beyond limit budgets.

**Continuations are exempt for the waiting portion** — that is precisely what they exist for. A component making a fifteen-second external call through a Continuation releases the thread while waiting. See [[12.7 - Apex Continuations]].

## The failure mode

The symptom is confusing, because the rejected requests are usually not the slow ones.

```
Integration user runs 10 slow API requests, each taking 8 seconds
    → all 10 slots occupied
    → an agent clicks a button on a case
    → CONCURRENT_REQUESTS_LIMIT_EXCEEDED
```

The agent's fast, well-written component fails because of an unrelated integration. The error names their transaction, and their transaction is fine.

That indirection is why the limit is often diagnosed late — the failing code is not the cause.

## Where slow requests come from

**Integrations calling Apex REST endpoints** that do substantial work synchronously.

**Bulk API and REST operations** triggering heavy automation on save. A data load of 200 records where the trigger cascade takes seven seconds occupies a slot per batch.

**Components calling Apex** that queries non-selectively against a large object.

**Visualforce pages** doing heavy processing in a controller.

**Cascading automation** on a hot object, where a single save runs four objects' triggers and flows. See [[07.13 - Order of Execution]].

## Diagnosing

**Event Monitoring**, with Shield, logs long-running requests with the actual Apex and the duration. It is the only way to see which requests are slow **for real users** across the org.

```sql
SELECT Id, ApexClassId, DurationMilliseconds, IsLongRunningRequest, RequestId
FROM ApexExecution
WHERE IsLongRunningRequest = true
```

Without Shield, the diagnostic is coarser:

**Debug logs** on the affected user, checking the total transaction time rather than only the limit block.

**The pattern of failures.** `CONCURRENT_REQUESTS_LIMIT_EXCEEDED` clustering at a particular time of day usually points at a scheduled integration.

**`AsyncApexJob` and `LoginHistory`** to correlate with integration activity.

The question that resolves most cases: **what else was running when the failures happened?**

## Reducing request duration

The direct fix, and everything here appears elsewhere in this section — concurrency is what makes it urgent rather than merely untidy.

**Make queries selective.** A non-selective query against a multi-million-row object is the most common cause of a seven-second transaction. See [[08.10 - Query Plan Tool and Query Optimization]].

**Reduce automation on hot objects.** A save running four objects' triggers, three flows, and roll-up recalculation is slow by construction.

**Move work out of the save.** A trigger doing enrichment that could happen in a Queueable holds the user's thread for the duration.

**Cache expensive lookups** in Platform Cache rather than recomputing per request. See [[16.8 - Platform Cache]].

**Fix CPU-heavy code.** Nested loops and describe calls in loops. See [[16.3 - CPU Time and Heap Size]].

## Moving work off the synchronous path

The architectural answer.

```java
public with sharing class ClaimSubmissionService {

    public static SubmissionResult submit(Warranty_Claim__c claim) {
        // synchronous: only what the user needs to see the result
        ClaimValidationService.validate(claim);
        insert claim;

        // asynchronous: everything else
        System.enqueueJob(new ClaimEnrichmentQueueable(new Set<Id>{ claim.Id }));

        return SubmissionResult.success(claim.Id);
    }
}
```

The test to apply: **does the user need this to have happened before the page returns?**

Validation, the save itself, and anything the response depends on: synchronous.

Enrichment, notification, integration, aggregate recalculation, logging: asynchronous.

Most transactions have far more in the first category than they need. See [[12.1 - Why Async and the Async Landscape]].

## Integration design

Integrations are the most common source of concurrency pressure, and the mitigations are the ones from section 13.

**Batch the payload.** One request with 200 records rather than 200 requests.

**Use Bulk API above a few thousand records.** It is asynchronous and exempt.

**Use sObject Collections and Composite** for moderate volumes — fewer requests, each doing more.

**Do not poll aggressively.** An integration polling every minute per record is both an API allocation problem and a concurrency problem.

**Push rather than poll.** Platform events and CDC notify rather than requiring the external system to ask. See [[13.1 - Integration Fundamentals and Patterns]].

**Throttle on the client side.** A middleware layer buffering requests protects the org from bursts, which is one of the genuine arguments for a broker. See [[13.18 - MuleSoft and Middleware Basics]].

## Continuations

For a component where the user waits on a slow external system, a Continuation releases the thread during the wait.

```java
@AuraEnabled(continuation=true cacheable=true)
public static Object getInventory(String serialNumber) {
    Continuation con = new Continuation(60);
    con.continuationMethod = 'processResponse';
    con.addHttpRequest(buildRequest(serialNumber));
    return con;
}
```

Without it, a fifteen-second external call occupies a concurrency slot for fifteen seconds. With it, the slot is released and reclaimed when the response arrives.

This is the one place where a Continuation is unambiguously the right tool, and it is narrow — most integration work does not have a user waiting. See [[12.7 - Apex Continuations]].

## Other concurrency limits

```
Concurrent long-running API requests        25 per org
Concurrent CometD streaming clients   1,000 to 2,000 by edition
Batch jobs queued or active                  5 org-wide
Concurrent Bulk API batches                 by edition
```

**The 25-request API cap** is separate from the Apex one and applies to API requests running over 20 seconds. An integration issuing many slow queries hits it independently.

**The 5-concurrent-batch limit** produces the queueing behaviour described in [[16.4 - Callout and Async Limits]] — jobs sit in the flex queue rather than failing, which is more forgiving than rejection.

## Load testing

Concurrency problems do not appear in a sandbox with one user, which is why they reach production.

**Test in a Full sandbox with production-scale data**, since query duration is the main driver and it scales with volume.

**Simulate concurrent load** where the org will have it — a data load running while users work, or an integration firing during business hours.

**Measure the duration of the hot paths**, not just their correctness:

```java
Long start = System.currentTimeMillis();
ClaimService.processApprovals(claims, oldMap);
System.debug('Duration: ' + (System.currentTimeMillis() - start) + 'ms');
```

**Anything over 3,000ms on a user-facing path deserves attention**, well before it reaches the five-second threshold — because the threshold is where it starts consuming a concurrency slot, not where it becomes a problem.

## Practical guidance

**Keep synchronous transactions under a few seconds.** Five is the threshold that consumes a slot.

**Move everything the user does not need to async.**

**Make queries selective** — non-selective queries against large objects are the main cause.

**Batch integration payloads**, and use Bulk API above a few thousand records.

**Use Continuations** where a user genuinely waits on a slow external call.

**Correlate failures with what else was running.** The failing request is usually not the cause.

**Enable Event Monitoring** if the org has Shield — it is the only view of real-user request duration.

**Test under concurrent load** with production-scale data.
