# Images, Media and Loading Attributes

Images are usually the largest bytes on a page and the most common cause of a poor LCP score ([[13.5 - Core Web Vitals]]). Most of the fix is HTML attributes, not JavaScript.

## The baseline image

```html
<img
  src="hero-800.jpg"
  alt="Team reviewing dashboards"
  width="800"
  height="450"
  loading="lazy"
  decoding="async"
>
```

**`width` and `height`** are not optional. The browser uses the ratio to reserve space before the image loads, preventing layout shift. Without them, content jumps when each image arrives — the primary cause of a bad CLS score. CSS can still override the rendered size:

```css
img { max-width: 100%; height: auto; }
```

**`loading="lazy"`** defers offscreen images natively — no `IntersectionObserver` needed. Never apply it to above-the-fold images, particularly the LCP element, because it delays the very thing being measured.

**`decoding="async"`** lets the browser decode off the main thread, avoiding a decode-induced frame drop.

**`fetchpriority="high"`** on the LCP image raises its priority above the default, which is one of the highest-leverage single-attribute changes available:

```html
<img src="hero.jpg" fetchpriority="high" loading="eager" width="1200" height="600" alt="...">
```

## alt text

```html
<img src="chart.png" alt="Revenue grew 40% from Q1 to Q3">   <!-- describes meaning -->
<img src="decoration.svg" alt="">                            <!-- decorative: empty alt -->
<img src="logo.svg" alt="Acme">                              <!-- functional: the text it replaces -->
```

Three rules: describe what the image *conveys*, not what it depicts; use `alt=""` (not a missing attribute) for purely decorative images so screen readers skip them; and for an image inside a link, the alt text describes the link destination.

A missing `alt` attribute causes screen readers to read the filename, which is worse than either option.

## Responsive images

Two distinct problems, two syntaxes.

**Resolution switching** — same image, different sizes. Use `srcset` with `w` descriptors and `sizes`:

```html
<img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 600px"
  alt="..."
  width="800" height="450"
>
```

`sizes` tells the browser how wide the image will *render* at each breakpoint. The browser combines that with device pixel ratio and picks from `srcset`. Getting `sizes` wrong is the usual reason `srcset` appears not to work — the browser downloads a 1600w image for a 300px slot because you told it the image was full-width.

**Art direction** — different crops or images per breakpoint. Use `<picture>`:

```html
<picture>
  <source media="(max-width: 600px)" srcset="portrait-crop.jpg">
  <source media="(min-width: 601px)" srcset="landscape-crop.jpg">
  <img src="landscape-crop.jpg" alt="..." width="1200" height="600">
</picture>
```

**Format negotiation** also uses `<picture>`:

```html
<picture>
  <source type="image/avif" srcset="photo.avif">
  <source type="image/webp" srcset="photo.webp">
  <img src="photo.jpg" alt="..." width="800" height="450">
</picture>
```

Browsers pick the first `<source>` they support. The `<img>` is the mandatory fallback and carries the `alt`, `width` and `height`.

## Format choice

| Format | Use for | Notes |
| --- | --- | --- |
| AVIF | photos | smallest, slower to encode, universal support now |
| WebP | photos, transparency | ~30% smaller than JPEG, safe everywhere |
| JPEG | photo fallback | universal |
| PNG | screenshots, sharp edges, transparency | large for photos |
| SVG | icons, logos, illustrations | scales infinitely, tiny, styleable with CSS |

SVG is the right answer for anything vector. Inlined SVG can be styled and animated with CSS; referenced SVG cannot, but caches better.

Note that an SVG from an untrusted source can contain scripts — sanitize before inlining ([[15.6 - Frontend Security]]).

## Preventing layout shift with CSS

```css
img, video {
  max-width: 100%;
  height: auto;
}

.thumbnail {
  aspect-ratio: 16 / 9;
  object-fit: cover;
}
```

`aspect-ratio` reserves space when the intrinsic dimensions are unknown; `object-fit: cover` crops rather than distorts. Together they eliminate most image-related CLS.

## Video

```html
<video
  controls
  muted
  playsinline
  preload="metadata"
  poster="thumb.jpg"
  width="800" height="450"
>
  <source src="clip.webm" type="video/webm">
  <source src="clip.mp4" type="video/mp4">
  <track kind="captions" src="captions.vtt" srclang="en" label="English" default>
</video>
```

- **`preload="metadata"`** fetches only duration and dimensions. `preload="auto"` on several videos will download tens of megabytes nobody watches.
- **`muted` + `playsinline`** are both required for autoplay to work on iOS; `playsinline` also prevents forced fullscreen.
- **`poster`** gives something to show immediately and prevents a blank box.
- **`<track kind="captions">`** is a legal requirement in many contexts and a usability win in all of them.

For anything longer than a short clip, use adaptive streaming (HLS or DASH) rather than a single file, so the client can switch quality with bandwidth.

## Preloading the LCP image

```html
<link rel="preload" as="image" href="hero.avif" type="image/avif" fetchpriority="high">
```

The preload scanner finds `<img>` tags in the initial HTML quickly, so an explicit preload is mainly valuable when the LCP image is set by CSS (a background image) or injected by JavaScript — both of which the scanner cannot see. That is a common failure mode: a hero image applied as a CSS `background-image` is discovered late and scores badly.

Where possible, make the LCP element a real `<img>` in the initial HTML.

## In React

```jsx
<img
  src={src}
  alt={alt}
  width={800}
  height={450}
  loading={isPriority ? "eager" : "lazy"}
  fetchPriority={isPriority ? "high" : undefined}
  onError={e => { e.currentTarget.src = FALLBACK; }}
/>
```

Note JSX uses `fetchPriority` (camelCase) while HTML uses `fetchpriority`. Frameworks with an image component — Next.js `<Image>` — generate `srcset`, set dimensions and handle formats automatically, which is most of this note done for you ([[19.6 - Image and Asset Optimization]]).

## How senior engineers actually use this

**They always set dimensions or `aspect-ratio`.** This single habit removes most CLS.

**They identify the LCP element and treat it specially** — eager loading, high fetch priority, preloaded if not discoverable, and never lazy.

**They serve images through a CDN with automatic format and size negotiation.** Hand-maintaining five variants of every image does not scale; an image CDN generates them on demand from one source.

**They lazy-load everything below the fold** and audit that nothing above it is lazy.

## Common pitfalls

- Missing `width`/`height`, causing layout shift.
- `loading="lazy"` on the LCP image, delaying the metric it defines.
- `srcset` without a correct `sizes`, so the browser downloads oversized files.
- Missing `alt`, or decorative images with descriptive alt text.
- Hero image as a CSS background, invisible to the preload scanner.
- `preload="auto"` on multiple videos.
- Serving a 4000px source scaled down by CSS.

## Interview angle

Image questions come up inside performance discussions — "how would you improve LCP" or "how do you handle responsive images". Cover dimensions to prevent CLS, `srcset`/`sizes` versus `<picture>` for the two different problems, modern formats with fallbacks, native lazy loading with the above-the-fold exception, and `fetchpriority` on the LCP element. Mentioning that a CSS background image is discovered late by the preload scanner is a detail that signals real performance work.
