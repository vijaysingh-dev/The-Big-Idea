# Layered Architecture on the Platform

## The layers

```
Entry points          Trigger, LWC controller, REST resource, invocable action,
                      batch job, platform event subscriber
        ↓
Service layer         business logic, transaction boundaries, orchestration
        ↓
Domain layer          per-object behaviour and validation
        ↓
Selector layer        all queries for an object
        ↓
Unit of Work          batched DML across the transaction
```

Each layer knows only the one below it. An entry point never queries; a selector never contains business logic.

## Why layers at all

Not aesthetics. Four concrete consequences.

**One implementation, many callers.** The same approval logic runs from a trigger, a Lightning button, a batch job, a flow action, and a REST endpoint — written once.

**Testability.** A service taking collections is testable with constructed records and no DML. A service reading `Trigger.new` can only be tested by inserting records and firing a trigger, which is an order of magnitude slower.

**Query control.** Selectors make every query visible in one place, which is what lets you count them and keep them selective.

**Change isolation.** A field rename touches the selector. A rule change touches the service. A new entry point touches neither.

## The rule that makes it work

**A service never reads `Trigger` context.**

```java
// Only callable from a trigger, forever
public static void handleApprovals() {
    for (Warranty_Claim__c claim : Trigger.new) { }
}

// Callable from anywhere
public static void handleApprovals(
    List<Warranty_Claim__c> claims,
    Map<Id, Warranty_Claim__c> priorClaims
) { }
```

That single constraint is the difference between a layered architecture and a trigger with extra files. The handler reads `Trigger` and passes plain collections onward; nothing below it knows where the data came from. See [[11.5 - Trigger Handler Pattern]].

## A worked slice

**Entry point — the trigger:**

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, after insert, after update
) {
    WarrantyClaimTriggerHandler.run();
}
```

**Entry point — the handler, the only place `Trigger` appears:**

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (AutomationBypass.isBypassed('WarrantyClaim')) {
            return;
        }

        switch on Trigger.operationType {
            when BEFORE_INSERT {
                ClaimService.applyDerivedFields(Trigger.new, null);
            }
            when BEFORE_UPDATE {
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
            }
            when AFTER_UPDATE {
                ClaimService.handleStatusTransitions(Trigger.new, Trigger.oldMap);
            }
        }
    }
}
```

**Service — orchestration and business rules:**

```java
public with sharing class ClaimService {

    public static void handleStatusTransitions(
        List<Warranty_Claim__c> claims,
        Map<Id, Warranty_Claim__c> priorClaims
    ) {
        List<Warranty_Claim__c> newlyApproved = new List<Warranty_Claim__c>();

        for (Warranty_Claim__c claim : claims) {
            Warranty_Claim__c prior = priorClaims?.get(claim.Id);
            if (claim.Status__c == 'Approved'
                && (prior == null || prior.Status__c != 'Approved')) {
                newlyApproved.add(claim);
            }
        }

        if (newlyApproved.isEmpty()) {
            return;
        }

        // the service orchestrates; it does not query or write directly
        Map<Id, Machine_Coverage__c> coverage =
            CoverageSelector.activeByAsset(assetIds(newlyApproved));

        ClaimPaymentService.createPayments(newlyApproved, coverage);
        ClaimRollupService.recalculate(assetIds(newlyApproved));
        ErpNotificationService.enqueue(recordIds(newlyApproved));
    }
}
```

**Selector — queries only:**

```java
public with sharing class CoverageSelector {

    public static Map<Id, Machine_Coverage__c> activeByAsset(Set<Id> assetIds) {
        Map<Id, Machine_Coverage__c> byAsset = new Map<Id, Machine_Coverage__c>();

        if (assetIds.isEmpty()) {
            return byAsset;
        }

        for (Machine_Coverage__c coverage : [
            SELECT Id, Asset__c, Coverage_Limit__c, Coverage_End_Date__c
            FROM Machine_Coverage__c
            WHERE Asset__c IN :assetIds AND Service_Contract__r.Status__c = 'Active'
            WITH USER_MODE
            ORDER BY Coverage_End_Date__c DESC
        ]) {
            // first wins, so the ORDER BY gives the longest-running coverage
            if (!byAsset.containsKey(coverage.Asset__c)) {
                byAsset.put(coverage.Asset__c, coverage);
            }
        }
        return byAsset;
    }
}
```

Four small classes. Each has one reason to change.

## What goes where

| Concern | Layer |
| --- | --- |
| Which trigger events exist | Trigger |
| Which service runs for which event | Handler |
| Bypass and recursion control | Handler |
| Change detection against the prior value | Service |
| Business rules and thresholds | Service |
| Orchestration across objects | Service |
| Transaction boundaries and savepoints | Service |
| Validation with `addError` | Domain, or service |
| Per-object derived fields | Domain, or service |
| Every SOQL query | Selector |
| Batched DML | Unit of Work |

**Change detection belongs in the service, not the handler.** The handler passes both collections and the service decides what changed, which keeps the handler a readable list of what runs when.

## Naming

```
ClaimService                  business logic
ClaimSelector                 queries
Claims                        domain, plural of the object
WarrantyClaimTriggerHandler   trigger dispatch
ClaimController               Lightning controller
ClaimResource                 Apex REST endpoint
ClaimSyncBatch                batch job
ClaimApprovalQueueable        async job
ClaimServiceTest              tests
```

Class names are globally unique in the org — there is no package system within a namespace — so the role suffix carries more weight here than in most languages. See [[09.13 - Apex Coding Standards and Best Practices]].

## Where the layers get bent

Honest observations from real codebases.

**Selectors that grow business logic.** A selector method named `getClaimsNeedingApproval` has encoded a business rule in its WHERE clause. Sometimes right — the rule is genuinely a query — and sometimes the rule belongs in the service, with the selector returning candidates.

**Services calling services.** Fine, and it creates a dependency graph worth keeping shallow. `ClaimService` calling `PaymentService` is reasonable; a cycle between them is not.

**Domain versus service.** The line is blurry, and the working distinction is: **domain is behaviour of one object; service is behaviour spanning objects or expressing a process.** Setting a claim's derived tier is domain; approving a claim, creating a payment, and notifying the ERP is service. See [[18.4 - Domain Layer]].

**Controllers with logic.** A Lightning controller should be as thin as a trigger — accept parameters, call a service, shape the response. Logic in a controller is logic only callable from that component.

## How much structure is enough

The most important question in this section, and the one most treatments skip.

**A small org — a handful of objects, one or two developers:**

```
Trigger → Handler → Service
```

Three layers. Queries inline in the service. No domain classes, no unit of work. This is entirely appropriate and adding more is over-engineering.

**A medium org — a dozen triggered objects, a small team:**

```
Trigger → Handler → Service → Selector
```

Selectors earn their place once queries are duplicated across services and query count becomes a concern.

**A large org — many objects, several teams, packages:**

```
Trigger → Handler → Service → Domain → Selector → Unit of Work
```

The full structure, with dependency injection at the seams for testability.

**The signals to add a layer:**

- The same query appears in three services → selectors
- Per-object validation is duplicated across services → domain
- Transactions perform many separate DML statements → unit of work
- Tests are slow because everything requires DML → injection and mocking

**The signal you have too much:** a new developer cannot trace a save through the code in ten minutes, or a one-field change touches five files.

Adopting fflib's full architecture in an org with six objects is a common and expensive mistake. See [[18.7 - fflib Apex Commons in Practice]].

## Testing by layer

The payoff, and the reason the structure is worth it at scale.

**Service tests** — the bulk of the suite, and they can avoid DML entirely:

```java
@IsTest
static void alreadyApprovedClaimsAreNotTreatedAsNewlyApproved() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };
    Map<Id, Warranty_Claim__c> prior = new Map<Id, Warranty_Claim__c>{
        claimId => new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };

    Test.startTest();
    List<Warranty_Claim__c> result = ClaimService.findNewlyApproved(claims, prior);
    Test.stopTest();

    Assert.isTrue(result.isEmpty(), 'An already-approved claim is not a new approval');
}
```

Milliseconds, no DML, no queries. On a suite of a thousand tests that is the difference between three minutes and forty.

**Selector tests** — real data, verifying the query returns what it should.

**Handler tests** — real DML, verifying the wiring and bulk behaviour. Fewer, and slower.

That shape — many fast service tests, few slow integration tests — is what a healthy Apex suite looks like, and it is only achievable when services take collections. See [[19.1 - Apex Testing Fundamentals]].

## Practical guidance

**Nothing below the handler reads `Trigger`.**

**Every service method takes collections** and tolerates a null prior map.

**Controllers and REST resources are as thin as triggers.**

**Add layers when the pain arrives**, not preemptively.

**Keep the service dependency graph shallow and acyclic.**

**Name by role**, since class names are globally unique.

**Write most tests against services**, with constructed records and no DML.
