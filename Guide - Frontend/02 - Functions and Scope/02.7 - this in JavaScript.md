# this in JavaScript

`this` is the one part of JavaScript that is **dynamically scoped** — its value is determined by *how a function is called*, not where it was written. Everything confusing about `this` follows from that single fact.

## The binding rules, in priority order

Evaluate top to bottom; the first match wins.

**1. `new` binding** — the function was called with `new`. `this` is the newly created object.

```js
function User(name) {
  this.name = name;
}
const u = new User("Vijay"); // this === u
```

**2. Explicit binding** — `call`, `apply` or `bind` set it directly ([[02.8 - call apply and bind]]).

```js
greet.call(person);
greet.apply(person, [arg]);
const bound = greet.bind(person);
```

**3. Implicit binding** — the function was called as a method. `this` is the object *left of the dot* at the call site.

```js
const obj = {
  name: "obj",
  show() { return this.name; },
};
obj.show(); // "obj"
```

**4. Default binding** — a plain call. `this` is `undefined` in strict mode and modules, or the global object in sloppy mode.

```js
function show() { return this; }
show(); // undefined in a module, window in a sloppy script
```

**Arrow functions sit outside this list entirely.** They have no own `this` and inherit it lexically ([[02.6 - Arrow Functions]]). No call-site rule can override that — even `.call()` on an arrow is ignored.

## The losing-`this` bug

Implicit binding depends only on the call site, so extracting a method breaks it:

```js
const user = {
  name: "Vijay",
  greet() { return `Hi ${this.name}`; },
};

user.greet();                    // "Hi Vijay"

const g = user.greet;
g();                             // TypeError — this is undefined

setTimeout(user.greet, 100);     // same problem
[1].map(user.greet);             // same problem
```

Passing `user.greet` passes the function value alone. The object association existed only in the expression `user.greet()`, not in the function itself.

Three fixes:

```js
setTimeout(user.greet.bind(user), 100);
setTimeout(() => user.greet(), 100);
// or define greet as a class field arrow so it is bound at construction
```

## `this` in classes

```js
class Counter {
  count = 0;

  increment() { this.count++; }        // prototype method — dynamic this
  reset = () => { this.count = 0; };   // class field — lexically bound
}

const c = new Counter();
const inc = c.increment;
inc(); // TypeError: Cannot read properties of undefined

const reset = c.reset;
reset(); // works
```

Class bodies are always strict mode, so a lost `this` is `undefined` rather than the global object — which surfaces as a `TypeError` immediately instead of silently writing globals. That is a feature.

## `this` in DOM handlers

```js
button.addEventListener("click", function () {
  console.log(this); // the button — the browser calls the handler with it
});

button.addEventListener("click", () => {
  console.log(this); // whatever this was in the enclosing scope
});
```

`event.currentTarget` gives you the element regardless of function form, and is the portable choice.

## `this` at module and global level

| Context | Value of `this` |
| --- | --- |
| ES module top level | `undefined` |
| Classic script top level | `globalThis` (`window`) |
| Function, sloppy mode | `globalThis` |
| Function, strict mode / module | `undefined` |
| Class body | always strict — `undefined` when unbound |
| Arrow at module top level | `undefined` |

Use `globalThis` when you genuinely need the global object; it works in browsers, Node and workers.

## How senior engineers actually use this

**They avoid `this` in application code.** Hooks-based React, factory functions and plain modules mean most modern frontend code never writes `this` at all. The pattern from [[02.4 - Closure Patterns in Production]] — a factory returning closures over private state — sidesteps the entire problem.

**They still need it for interop.** Class-based libraries, older SDKs, DOM APIs, Web Components and some animation libraries all use `this`. Knowing the rules is about reading and debugging other people's code more than writing your own.

**They read the call site, not the definition.** When debugging a `this` problem the question is always "how was this function invoked", and the answer is usually "it was passed somewhere and called bare".

**They use `bind` at construction, not at call time.** `onClick={this.handle.bind(this)}` in a render creates a new function every render and breaks memoization. Binding once in the constructor, or using a class-field arrow, avoids that.

## Common pitfalls

- Extracting a method and calling it standalone.
- Using an arrow as an object method, so `this` is module scope rather than the object.
- Nested regular functions inside methods, where the inner function gets default binding:

```js
const obj = {
  items: [1, 2, 3],
  logAll() {
    this.items.forEach(function (i) {
      console.log(this.items); // undefined — default binding
    });
  },
};
```

The fix is an arrow callback, or `forEach`'s optional second `thisArg` parameter.

- Assuming `bind` can be reapplied. A bound function's `this` is permanent; `f.bind(a).bind(b)` still uses `a`.
- Expecting `this` in a module to be `window`. It is `undefined`.

## Interview angle

Expect "what does `this` refer to" with three or four snippets covering method call, extracted method, arrow in a method, and `new`. Answer by naming the rule that applies at each call site rather than describing the value, in the order: `new`, explicit bind, implicit (object before the dot), default — and note that arrows opt out entirely and inherit lexically. Mentioning that class bodies are strict, so lost `this` throws instead of silently hitting `window`, is a good detail.
