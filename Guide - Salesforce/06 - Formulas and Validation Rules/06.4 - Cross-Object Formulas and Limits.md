# Cross-Object Formulas and Limits

## Traversing upward

A formula can read fields on parent records through lookup and master-detail relationships, using `__r` for custom relationships and the relationship name for standard ones.

```
Account__r.Name
Account__r.Owner.Email
Asset__r.Account.BillingCountry
Service_Contract__r.Account__r.Ultimate_Parent_Account__r.Name
```

Each dot is a **spanning relationship**, and they are a metered resource.

**Formulas traverse upward only.** A formula on Account cannot read its Opportunities. Aggregating from children is what roll-up summaries and Apex are for. See [[02.6 - Roll-Up Summary Fields]].

## The two limits

**10 spanning relationships per formula.** The depth of a single expression.

**15 unique spanning relationships per object**, counted across *all* formula fields, validation rules, workflow rules, and roll-up summary filters on that object combined.

The second is the one that bites. It is a shared budget, it is invisible until you exhaust it, and the failure mode is that someone cannot add a needed validation rule because eleven formula fields already consumed the allowance.

Uniqueness is per relationship path, not per reference. Ten formulas all reading `Account__r.Name` consume one. One formula reading `Account__r.Name`, `Asset__r.Name`, and `Service_Contract__r.Name` consumes three.

That asymmetry suggests the mitigation: **concentrate traversals through few relationships** rather than spreading them across many.

## Compiled size, which is the real constraint

The 5,000-byte compiled limit is reached far earlier than the 3,900-character typing limit, because **compilation expands references**.

A formula referencing another formula field compiles that field's entire definition inline. Reference three formula fields, each fifty lines, and your ten-line formula compiles to something much larger. Nested formula chains hit the limit in ways that are genuinely surprising.

The error message names the limit and not the cause, which makes it a frustrating debugging session the first time.

The options when you hit it:

**Simplify the logic.** Often a nested `IF` chain can become a `CASE`.

**Extract a repeated sub-expression into a helper formula field.** This reduces the source formula and increases the compiled size, so it helps only when the sub-expression appears several times.

**Push a value into a stored field** populated by a trigger or flow, and reference that instead. The formula reads one field rather than computing.

**Accept that it should be Apex.** A formula approaching the compiled limit is usually one that should not be a formula.

## The performance cost

Formula fields are computed at **read time**, on every read, for every row returned.

A single formula is negligible. Forty cross-object formulas on Opportunity, queried in a batch job over 200,000 records, is not — this genuinely produces `Apex CPU time limit exceeded` in code containing no visible loop, which makes it hard to diagnose.

The practical consequences:

**Select only the formula fields you need.** A query pulling every field on a formula-heavy object is expensive in a way `SELECT Id, Name` is not.

**Cross-object formulas cost more**, because each traversal is a join the query engine performs per row.

**Formula fields are not indexed** in the general case, so filtering on one against a large object produces a non-selective query. On a multi-million-row object this is the difference between a fast query and a timeout. See [[08.9 - Indexes and Selective Queries]].

The rule that follows: **display and low-volume filtering, yes; high-volume filtering, no.** When a derived value must be filtered at scale, store it.

## What cannot be referenced

Several things are unavailable in cross-object formulas, and the restrictions are not obvious:

- Long text areas and rich text areas
- Multi-select picklists on a parent, except through `INCLUDES` on the same record
- Encrypted fields
- Some system fields on parent records
- A field on a parent that is itself a cross-object formula spanning further, beyond the depth limit
- Roll-up summary fields on a parent, in some contexts

Polymorphic lookups — `WhatId`, `WhoId`, `OwnerId` on Case — cannot be traversed in formulas at all, because the target type is not known at compile time. This is a real limitation: a formula on Task cannot read the related Opportunity's amount, because `WhatId` might point at an Account.

The workaround is a stored field populated by automation that knows the type at runtime:

```java
public with sharing class TaskContextService {

    public static void stampOpportunityAmount(List<Task> tasks) {
        Set<Id> opportunityIds = new Set<Id>();
        for (Task t : tasks) {
            // filter by key prefix, since WhatId can point at several object types
            if (t.WhatId != null && String.valueOf(t.WhatId).startsWith('006')) {
                opportunityIds.add(t.WhatId);
            }
        }
        if (opportunityIds.isEmpty()) {
            return;
        }

        Map<Id, Opportunity> opps = new Map<Id, Opportunity>([
            SELECT Id, Amount, StageName FROM Opportunity WHERE Id IN :opportunityIds
        ]);

        for (Task t : tasks) {
            Opportunity opp = opps.get(t.WhatId);
            if (opp != null) {
                t.Related_Deal_Amount__c = opp.Amount;
            }
        }
    }
}
```

Key prefixes are the reliable way to determine an ID's object type — `006` is Opportunity, `001` Account, `003` Contact, `500` Case. `Id.getSObjectType()` also works and is more readable.

## Relationship depth versus formula count

A design tension worth naming.

Deep traversal in one formula — `Asset__r.Account.Parent.Owner.Manager.Email` — consumes five of the ten per-formula spanning slots and is fragile: any relationship in the chain being null makes the whole thing null.

Several shallow formulas spread the risk but consume more of the fifteen-per-object budget.

The pattern that scales best: **denormalize the value you need onto the record that needs it**, using automation, and reference it directly.

For the Northwind model, rather than every claim traversing to the ultimate parent account through three hops, a trigger stamps `Ultimate_Parent_Account__c` on Account, and formulas on claim traverse one level to read it. One spanning relationship instead of three, no null-chain fragility, and it can be indexed. See [[04.7 - Account Hierarchies and Account Teams]].

## When to stop using formulas

The signals that a formula has outgrown itself:

- It approaches the compiled size limit
- It references three or more other formula fields
- It needs data from child records
- It needs to be filtered on a large object
- It needs a value that changes on a schedule rather than on read
- It cannot be understood in one reading by someone who did not write it

The last one is not a technical limit and it is the most important. A forty-line nested formula that works is a liability, because the next person to change it will get it wrong.

## Practical guidance

**Watch the 15-per-object budget.** It is invisible until exhausted, and exhausting it blocks work that matters more than the formula that consumed it.

**Concentrate traversals through few relationships.**

**Denormalize rather than traversing deeply.** A stamped field is cheaper, more robust, and indexable.

**Select only the formula fields you need** in queries against formula-heavy objects.

**Store what you filter at volume.**

**Use key prefixes or `getSObjectType()`** for polymorphic relationships, since formulas cannot traverse them.
