# Slack, Heroku and Mobile SDK Touchpoints

## Why this note exists

Three adjacent surfaces that come up in architecture conversations and in interviews. The useful knowledge is **when each is the right answer**, not how to build on them — each is a platform in its own right.

## Slack

Salesforce owns Slack, and the integration surface is deeper than a webhook.

**Slack Sales Elevate and Service Elevate** are packaged applications bringing pipeline and case management into Slack. Configuration rather than development.

**Salesforce Channels** link a Slack channel to a record — a deal room tied to an opportunity, a swarm channel tied to a case. Messages and record updates flow both ways.

**Slack apps built with the Slack SDK**, authenticating against Salesforce and calling its APIs like any external system.

**Flow actions for Slack** — the declarative path, and usually the right starting point:

```
Record-Triggered Flow on Warranty Claim
    Condition: Claim_Amount__c > 500000 AND Status changed to Submitted
    Action: Send Slack Message
        Channel: #warranty-escalations
        Message: New high-value claim {!$Record.Claim_Number__c} for
                 {!$Record.Account__r.Name} — {!$Record.Claim_Amount__c}
```

No code, no connected app to build, and an administrator maintains it.

**When to build a custom Slack app instead:** interactive workflows where a user acts from within Slack — approving a claim from a message button, or a slash command that queries Salesforce. Notification-only requirements do not need one.

**Swarming** for support is the pattern worth knowing: a case escalates, a channel opens with the right experts, the conversation is captured back onto the case. It is a Service Cloud feature rather than a development project. See [[05.8 - Service Console and Agent Productivity]].

## Heroku

A managed application platform, owned by Salesforce, for running code that does not fit Apex.

**What it is for:**

**Long-running or compute-heavy work.** Apex has a 10-second CPU limit; Heroku does not. Machine learning, image processing, complex optimization.

**Languages Salesforce does not run.** Python, Node, Ruby, Go, Java.

**Customer-facing applications at scale** where Experience Cloud licensing would be prohibitive — a consumer web app with a million users.

**Data processing pipelines** feeding Salesforce.

**Libraries that cannot run in Apex.** A PDF generation library, a specific statistical package.

**Heroku Connect** is the distinctive piece: bidirectional synchronization between Salesforce objects and a Heroku Postgres database, configured rather than coded.

```
Salesforce Account  ←→  Postgres table "salesforce.account"
```

The application reads and writes Postgres; Heroku Connect keeps both sides aligned. That lets a high-traffic application query a real database rather than consuming Salesforce API calls per request — which is often the deciding factor.

**The tradeoffs:**

Sync lag between the two systems. A separate platform to operate, deploy, and monitor. Additional cost. Data residing outside Salesforce, with its own compliance implications.

**When not to use it:** anything Apex can do comfortably. Heroku is for the cases where the platform's limits are the constraint, not for preferring a different language.

## Mobile SDK

For building a **custom native or hybrid mobile app** against Salesforce, when the standard Salesforce mobile app is not sufficient.

```
iOS (Swift), Android (Kotlin), React Native, Hybrid
Handles: OAuth, secure token storage, offline sync, encrypted local store
```

**SmartStore** is the encrypted local database; **Mobile Sync** handles offline record sync with conflict resolution.

**When it is justified:**

- A field engineer working without connectivity, needing full offline capability
- Device hardware integration — barcode scanning, specialized sensors, Bluetooth equipment
- A branded consumer app where the Salesforce app would be inappropriate
- A workflow so specific that the standard app cannot express it

**When it is not:**

The Salesforce mobile app with well-designed Lightning pages covers most internal use. Building a custom app means owning app store releases, device testing, and a codebase that must track platform changes.

**Salesforce Field Service has its own mobile app** with offline capability built in, which is nearly always the right answer for field service rather than a custom build. See [[05.13 - Field Service Basics]].

The honest guidance: **a custom mobile app is a large ongoing commitment.** The question to answer first is what specifically the standard app cannot do.

## Choosing between them

| Requirement | Surface |
| --- | --- |
| Notify a channel when a record changes | Flow Slack action |
| Approve a record from within Slack | Custom Slack app |
| Compute exceeding Apex limits | Heroku |
| A language Apex does not support | Heroku |
| A consumer-scale web application | Heroku, with Heroku Connect |
| A high-traffic app needing database access | Heroku Connect |
| Internal mobile access | Salesforce mobile app |
| Field service with offline work | Field Service mobile app |
| Device hardware integration | Mobile SDK |
| Full offline for a bespoke workflow | Mobile SDK |

## The pattern behind all three

Each is a **boundary decision**: the point at which the requirement leaves the Salesforce platform.

The check worth applying before crossing that boundary:

**Can the platform do it?** Flow, Apex, LWC, Experience Cloud, and the standard mobile app cover more than teams assume.

**What does leaving cost?** A separate deployment pipeline, separate monitoring, separate security review, separate people who understand it, and an integration to maintain.

**What does staying cost?** Fighting a limit, an unnatural implementation, or a poor user experience.

Crossing the boundary is right when the second cost genuinely exceeds the third. It is frequently chosen for the wrong reason — familiarity with another language, or a preference for a different toolchain.

## Section 17 in one paragraph

The platform features in this section share a theme: each removes a reason to write code. Custom Metadata holds configuration that deploys, is queryable for free, and can be referenced from formulas, flows, and Apex alike — making it the default for anything a hardcoded constant would otherwise express, with Custom Settings surviving only for the hierarchy that bypass switches and per-user flags need. Custom Labels take user-facing text out of code and make it translatable, which matters in any org spanning more than one language. Files, email, reports, list views, and search are each the packaged answer to a requirement teams routinely build components for — a report with a scheduled conditional subscription is an alerting system, a list view with a mass quick action is a bulk approval tool, and a lookup filter is a validation rule that runs at the right moment. Experience Cloud inverts the emphasis: the configuration is straightforward and the security is not, because the guest user is the internet and every reachable Apex class is a public endpoint. And Slack, Heroku, and the Mobile SDK are boundary decisions rather than features — worth taking when a platform limit genuinely blocks the requirement, and expensive when taken for familiarity.
