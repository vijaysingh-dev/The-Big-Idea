# Rerankers: Cross-Encoders vs Bi-Encoders

## The Two-Stage Retrieval Pattern

Retrieval systems face a fundamental tension:

- **Speed requirement**: Must scan millions of documents in <100ms
- **Quality requirement**: Must accurately rank by actual relevance

No single model optimally satisfies both. The solution is a two-stage pipeline:

```
Stage 1 — Recall (fast, approximate)
  Query → Bi-encoder + BM25 → top-100 candidates

Stage 2 — Precision (slow, accurate)
  top-100 candidates → Cross-encoder reranker → top-10 final
```

Stage 1 casts a wide net cheaply. Stage 2 precisely scores the small candidate set.

---

## Bi-Encoders (Stage 1)

### How They Work

Encodes query and document **independently** into vectors:

```
Encoder(query)    → query_vector
Encoder(document) → doc_vector
score = cosine_similarity(query_vector, doc_vector)
```

Because encoding is independent, you can **pre-compute and store all document vectors**. At query time, you only encode the query (fast) and run ANN search.

### Speed Profile

- Index build time: O(N) — embed every document once
- Query time: O(1) for embedding + O(log N) for ANN search
- Latency: ~5–50ms per query at scale

### Quality Ceiling

Because query and document never "see" each other during encoding, the model can't capture fine-grained relevance signals. The query "What caused the 2008 financial crisis?" and the document "The housing bubble collapse triggered..." are embedded independently — the model can't directly compare them during encoding.

---

## Cross-Encoders (Stage 2 / Reranking)

### How They Work

Encodes the query and document **together** as a single input:

```
Input:  [CLS] query text [SEP] document text [SEP]
Output: relevance_score  (single scalar, 0–1)
```

The attention mechanism can compare every token in the query against every token in the document — capturing nuanced relevance signals.

```python
from sentence_transformers import CrossEncoder

model = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

pairs = [
    ("What caused the 2008 crisis?", "The housing bubble..."),
    ("What caused the 2008 crisis?", "Mortgage-backed securities..."),
    ("What caused the 2008 crisis?", "The cat sat on a mat..."),
]
scores = model.predict(pairs)
# [0.92, 0.87, 0.01]  ← clear separation between relevant and irrelevant
```

### Speed Profile

- Cannot pre-compute: scores are query-dependent
- Query time: O(K) where K = number of candidates to rerank
- Latency: ~100–500ms for K=100 (heavy model), ~20–50ms for K=20 (small model)
- **Must limit K**: You cannot rerank 10,000 documents — only the top-K from Stage 1

### Quality Advantage

Cross-encoders are significantly more accurate than bi-encoders for ranking because the joint attention allows direct token-level comparison. On standard benchmarks (MS MARCO), cross-encoders score ~10–15 MRR points higher than bi-encoders.

## Reranking in RAG Systems

Reranking's impact on RAG quality is significant because the LLM's answer quality depends on what's in its context. A reranker that promotes the best chunk from position 7 to position 1 directly improves the final answer.

### Typical Pipeline

```python
# Stage 1: Retrieve top-100 with hybrid search
candidates = hybrid_search(query, top_k=100)

# Stage 2: Rerank top-100 → top-10
pairs = [(query, doc.text) for doc in candidates]
scores = reranker.predict(pairs)

# Sort by reranker scores
reranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
final_context = [doc for doc, score in reranked[:10]]

# Stage 3: Assemble context for LLM
prompt = build_prompt(query, final_context)
answer = llm.call(prompt)
```

### Context Position Matters: Lost in the Middle

Research shows LLMs perform best on information at the **beginning and end** of context, worst in the middle. After reranking, order the most relevant chunks first and last, putting lower-quality chunks in the middle.

---

## Latency Optimization for Rerankers

The reranker is often the latency bottleneck in a RAG pipeline. Options:

1. **Reduce candidate count**: Retrieve top-25 instead of top-100 if recall allows
2. **Smaller reranker model**: `MiniLM-L-6` vs `electra-base` — 5× faster, small quality drop
3. **Batch processing**: Send all pairs in a single model call (GPU batching)
4. **Async**: Run reranker while beginning to assemble other prompt components
5. **Cache**: Cache reranker scores for (query, doc) pairs that appear frequently

---

## When to Skip Reranking

Not every system needs a reranker. Skip it when:

- Latency budget is very tight (<200ms total)
- Corpus is small (<10K documents) — bi-encoder quality is sufficient
- Queries are highly specific (BM25 exact match is already precise)
- You've verified retrieval quality is good without it (always evaluate first)

Add it when:

- Answer quality is inconsistent
- Retrieved documents are often topically correct but not quite the right passage
- You have heterogeneous document types with varying lengths
