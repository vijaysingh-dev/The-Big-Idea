# Testing Security and Sharing

## The problem with every other test in your org

**Tests run as a System Administrator by default.**

That user sees every record, every field, and bypasses sharing entirely. A test that passes as an administrator says nothing about whether a support agent can use the feature — and the security defects that matter are exactly the ones an administrator cannot see.

```java
@IsTest
static void agentsSeeOnlyTheirOwnAccountsClaims() {
    // as an administrator this returns everything, and proves nothing
    List<Warranty_Claim__c> claims = ClaimSelector.byAccount(accountId);
}
```

## System.runAs

```java
@IsTest
static void anAgentCannotSeeAnotherAccountsClaims() {
    User agent = TestUserFactory.create('Support Agent', 'Claim_Access');
    Warranty_Claim__c ownClaim = TestDataFactory.createClaimOwnedBy(agent.Id);
    Warranty_Claim__c otherClaim = TestDataFactory.createClaimForAnotherAccount();

    Test.startTest();
    System.runAs(agent) {
        // sharing is enforced inside this block
        List<Warranty_Claim__c> visible = [SELECT Id FROM Warranty_Claim__c];

        Assert.areEqual(1, visible.size(), 'The agent should see only their own claim');
        Assert.areEqual(ownClaim.Id, visible[0].Id);
    }
    Test.stopTest();
}
```

**What `runAs` enforces:**

```
Record-level sharing
Object permissions (CRUD)
Field-level security
Profile and permission set settings
User-specific settings and locale
```

**What it does not:**

```
Governor limits — they remain the administrator's context
The mixed DML restriction, which it actually relaxes
```

## The mixed DML exception

`runAs` is the sanctioned workaround for creating users alongside records.

```java
@IsTest
static void claimVisibilityFollowsSharing() {
    User engineer;

    // wrapping user creation isolates the setup DML from the record DML that follows
    System.runAs(new User(Id = UserInfo.getUserId())) {
        engineer = TestUserFactory.create('Service Engineer', 'Claim_Access');
    }

    Warranty_Claim__c claim = TestDataFactory.createClaim();

    System.runAs(engineer) {
        Assert.areEqual(0, [SELECT COUNT() FROM Warranty_Claim__c],
            'A private object should be invisible to a non-owner');
    }
}
```

Wrapping in `runAs` with the **current** user is what creates the transaction separation. See [[10.7 - Mixed DML and Setup Objects]].

## Creating test users

```java
@IsTest
public class TestUserFactory {

    public static User create(String profileName, String permissionSetName) {
        User user;

        System.runAs(new User(Id = UserInfo.getUserId())) {
            Profile p = [SELECT Id FROM Profile WHERE Name = :profileName LIMIT 1];

            String unique = String.valueOf(System.currentTimeMillis())
                + String.valueOf(Math.round(Math.random() * 1000));

            user = new User(
                FirstName = 'Test',
                LastName = 'User' + unique,
                Email = 'test' + unique + '@example.com',
                // globally unique across every Salesforce org, not just this one
                Username = 'test' + unique + '@northwind.test',
                Alias = unique.right(8),
                ProfileId = p.Id,
                TimeZoneSidKey = 'Asia/Kolkata',
                LocaleSidKey = 'en_IN',
                EmailEncodingKey = 'UTF-8',
                LanguageLocaleKey = 'en_US'
            );
            insert user;

            if (String.isNotBlank(permissionSetName)) {
                PermissionSet ps = [
                    SELECT Id FROM PermissionSet WHERE Name = :permissionSetName LIMIT 1
                ];
                insert new PermissionSetAssignment(AssigneeId = user.Id, PermissionSetId = ps.Id);
            }
        }
        return user;
    }
}
```

**Profiles and permission sets are visible in tests**, so querying them works without `SeeAllData`.

**A user with a role** is needed to test the role hierarchy:

```java
public static User createWithRole(String profileName, String roleName) {
    UserRole role = [SELECT Id FROM UserRole WHERE DeveloperName = :roleName LIMIT 1];
    User user = create(profileName, null);

    System.runAs(new User(Id = UserInfo.getUserId())) {
        update new User(Id = user.Id, UserRoleId = role.Id);
    }
    return user;
}
```

**Roles are org metadata**, so a test depending on a specific role couples to the org's configuration. Creating roles in tests is not possible, which is a real constraint on hierarchy testing.

## Testing field-level security

```java
@IsTest
static void restrictedFieldsAreStrippedForAnAgent() {
    User agent = TestUserFactory.create('Support Agent', null);
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    System.runAs(agent) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Amount__c, Internal_Margin__c
            FROM Warranty_Claim__c WITH USER_MODE
        ];

        // USER_MODE nulls fields the user cannot read rather than throwing
        Assert.isNotNull(claims[0].Claim_Amount__c);
        Assert.isNull(claims[0].Internal_Margin__c,
            'An agent should not see the internal margin');
    }
    Test.stopTest();
}
```

**`WITH USER_MODE` nulls inaccessible fields.** Without it, the query returns everything and the test proves nothing about field-level security. See [[03.13 - Enforcing Security in Apex and SOQL]].

Testing `stripInaccessible` on the write path:

```java
@IsTest
static void anAgentCannotWriteToARestrictedField() {
    User agent = TestUserFactory.create('Support Agent', null);
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    System.runAs(agent) {
        // a crafted request attempting to set a field the UI never exposes
        Warranty_Claim__c incoming = new Warranty_Claim__c(
            Id = claim.Id,
            Fault_Description__c = 'Updated',
            Internal_Margin__c = 999999
        );

        ClaimController.save(incoming);
    }
    Test.stopTest();

    Warranty_Claim__c refreshed = [
        SELECT Fault_Description__c, Internal_Margin__c
        FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Updated', refreshed.Fault_Description__c);
    Assert.areNotEqual(999999, refreshed.Internal_Margin__c,
        'stripInaccessible should have removed the restricted field');
}
```

**This is the test that catches a missing `stripInaccessible`**, and it is the specific exposure that makes an `@AuraEnabled` method dangerous — a component rendering three fields can otherwise write to any field on the object.

## Testing object permissions

```java
@IsTest
static void aReadOnlyUserCannotCreateAClaim() {
    User readOnly = TestUserFactory.create('Read Only', null);

    Test.startTest();
    System.runAs(readOnly) {
        try {
            insert TestDataFactory.buildClaim(150000);
            Assert.fail('A read-only user should not be able to create a claim');
        } catch (DmlException e) {
            Assert.isTrue(e.getMessage().contains('INSUFFICIENT_ACCESS')
                || e.getMessage().contains('insufficient access'),
                'Expected an access error, got: ' + e.getMessage());
        }
    }
    Test.stopTest();
}
```

## Testing sharing rules and Apex sharing

```java
@IsTest
static void apexSharingGrantsAccessToTheAssignedEngineer() {
    User engineer;
    System.runAs(new User(Id = UserInfo.getUserId())) {
        engineer = TestUserFactory.create('Service Engineer', 'Claim_Access');
    }

    Warranty_Claim__c claim = TestDataFactory.createClaim();

    System.runAs(engineer) {
        Assert.areEqual(0, [SELECT COUNT() FROM Warranty_Claim__c WHERE Id = :claim.Id],
            'Before sharing, the engineer sees nothing');
    }

    Test.startTest();
    ClaimSharingService.shareWithEngineer(claim.Id, engineer.Id);
    Test.stopTest();

    System.runAs(engineer) {
        Assert.areEqual(1, [SELECT COUNT() FROM Warranty_Claim__c WHERE Id = :claim.Id],
            'After the Apex share, the engineer can see the claim');
    }
}
```

**Asserting both before and after** is what proves the sharing did the work rather than the record having been visible anyway. See [[03.11 - Apex Sharing and Programmatic Sharing]].

## Testing an @AuraEnabled method as a real user

The most valuable security test in most orgs.

```java
@IsTest
static void theControllerDoesNotLeakAnotherAccountsClaim() {
    User agent = TestUserFactory.create('Support Agent', 'Claim_Access');
    Warranty_Claim__c otherClaim = TestDataFactory.createClaimForAnotherAccount();

    Test.startTest();
    System.runAs(agent) {
        try {
            // a caller can pass any Id, regardless of what the component renders
            ClaimController.getClaim(otherClaim.Id);
            Assert.fail('The controller should not return an inaccessible claim');
        } catch (AuraHandledException e) {
            // the expected outcome
        }
    }
    Test.stopTest();
}
```

**An `@AuraEnabled` method is callable by any authenticated user with any parameter.** Testing it as an administrator, with an Id the administrator can see, verifies nothing about that.

## Testing guest user access

The highest-risk surface, and the hardest to test.

```java
@IsTest
static void theGuestUserCannotReachInternalClaims() {
    User guest = [
        SELECT Id FROM User
        WHERE Profile.Name LIKE '%Site Guest User%' AND IsActive = true
        LIMIT 1
    ];

    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    System.runAs(guest) {
        Assert.areEqual(0, [SELECT COUNT() FROM Warranty_Claim__c],
            'The guest user must not see internal claims');
    }
    Test.stopTest();
}
```

**The guest user must already exist**, so this test depends on a site being configured — which makes it fragile across environments. Guarding on the query returning nothing is worth adding:

```java
List<User> guests = [SELECT Id FROM User WHERE Profile.Name LIKE '%Site Guest User%' LIMIT 1];
if (guests.isEmpty()) {
    return;   // no site configured in this org
}
```

Skipping rather than failing is the pragmatic choice, and it means the test provides no protection in an org where the site is missing. Reviewing guest permissions manually remains necessary. See [[17.9 - Experience Cloud Basics]].

## Testing custom permissions

```java
@IsTest
static void onlyUsersWithThePermissionCanApproveLargeClaims() {
    User withPermission = TestUserFactory.create('Support Agent', 'Large_Claim_Approver');
    User withoutPermission = TestUserFactory.create('Support Agent', null);

    Warranty_Claim__c claim = TestDataFactory.createClaim(900000);

    Test.startTest();
    System.runAs(withoutPermission) {
        Database.SaveResult result = Database.update(
            new Warranty_Claim__c(Id = claim.Id, Status__c = 'Approved'), false
        );
        Assert.isFalse(result.isSuccess(), 'Without the permission, approval is blocked');
    }

    System.runAs(withPermission) {
        Database.SaveResult result = Database.update(
            new Warranty_Claim__c(Id = claim.Id, Status__c = 'Approved'), false
        );
        Assert.isTrue(result.isSuccess(), 'With the permission, approval succeeds');
    }
    Test.stopTest();
}
```

**Testing both sides** is what makes this meaningful. A test only verifying the permitted case does not prove the restriction exists.

This also covers the validation rule using `$Permission`, which has no other test coverage. See [[06.5 - Validation Rules]].

## What runAs cannot test

Worth knowing so time is not wasted.

**Governor limits** remain in the outer context.

**Some declarative behaviour**, including certain sharing recalculations that happen asynchronously.

**The full role hierarchy** where the org has no suitable roles, since roles cannot be created in tests.

**Territory-based sharing**, which behaves inconsistently in test context.

**Guest user behaviour fully** — the site context differs from a `runAs` block, and only testing on the published site reveals some differences.

For each of these, the compensation is manual verification with a documented checklist rather than a test.

## A security test checklist

```
[ ] Every @AuraEnabled method tested as a non-administrator
[ ] An inaccessible record Id passed to each controller method
[ ] Field-level security verified with WITH USER_MODE
[ ] stripInaccessible verified on write paths
[ ] Object permissions verified for a read-only profile
[ ] Custom permission checks tested from both sides
[ ] Apex sharing tested before and after
[ ] Guest user access tested where a site exists
[ ] REST endpoints tested as an integration user, not an administrator
```

## Practical guidance

**Never test security as an administrator.**

**Wrap user creation in `runAs`** with the current user, for the mixed-DML rule.

**Use a globally unique username.**

**Test `@AuraEnabled` methods with an Id the user should not see.**

**Use `WITH USER_MODE` in the test query** to verify field-level security.

**Test both sides of a permission check.**

**Assert before and after** when testing Apex sharing.

**Accept that some things cannot be tested**, and cover them with a review checklist.
