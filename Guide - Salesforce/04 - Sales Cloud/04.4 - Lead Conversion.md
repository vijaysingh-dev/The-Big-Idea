# Lead Conversion

## What conversion actually does

Converting a Lead is a single platform operation that does several things at once:

1. Creates or matches an **Account**, using the Lead's `Company` text
2. Creates or matches a **Contact**, using the Lead's name
3. Optionally creates an **Opportunity**
4. Copies mapped fields from the Lead onto each of the three
5. Moves **Activities** (Tasks and Events) to the new Contact and Opportunity
6. Repoints **CampaignMember** records from the Lead to the new Contact
7. Sets `IsConverted = true` and populates the three `Converted*Id` fields
8. Sets `Status` to the status flagged as Converted in the Lead Process

The Lead record remains in the database forever. It is not deleted, and it is not editable afterwards.

**Conversion is irreversible.** There is no unconvert. The only recovery is to delete the created records and manually recreate the lead, which loses the activity history.

## Field mapping

Standard fields map automatically — name, phone, email, address, and so on. Custom fields must be mapped explicitly in Setup, under the Lead object's Fields section.

The rules that catch people:

**A custom Lead field can map to one field on each of Account, Contact, and Opportunity.** So `Machine_Interest__c` on Lead can map to a field on Opportunity and a different field on Contact.

**Data types must be compatible.** A picklist maps to a picklist with the same values, or to a text field. Mismatches cause conversion failures, and the error message is not always clear about which field is at fault.

**Unmapped data is lost.** Not hidden — lost, in the sense that it stays on the converted Lead where nobody looks at it and no report includes it.

That last point drives a design principle: **be reluctant to add custom fields to Lead.** Every field added is a field that needs mapping, a mapping that needs maintaining, and a target field that needs to exist on the other side. Leads should hold what is needed to qualify, and no more.

## Converting in Apex

```java
public with sharing class LeadConversionService {

    public static List<Database.LeadConvertResult> convert(List<Lead> leads, Boolean createOpportunity) {
        LeadStatus convertedStatus = [
            SELECT MasterLabel FROM LeadStatus WHERE IsConverted = true LIMIT 1
        ];

        List<Database.LeadConvert> requests = new List<Database.LeadConvert>();
        for (Lead lead : leads) {
            Database.LeadConvert lc = new Database.LeadConvert();
            lc.setLeadId(lead.Id);
            lc.setConvertedStatus(convertedStatus.MasterLabel);
            lc.setDoNotCreateOpportunity(!createOpportunity);
            lc.setOpportunityName(lead.Company + ' - Initial Opportunity');
            requests.add(lc);
        }

        // allOrNone false so one bad lead does not abort the batch
        return Database.convertLead(requests, false);
    }
}
```

The options on `Database.LeadConvert` worth knowing:

- `setAccountId()` — convert into an **existing** Account instead of creating one
- `setContactId()` — convert into an existing Contact
- `setOpportunityId()` — attach to an existing Opportunity
- `setDoNotCreateOpportunity(true)` — skip opportunity creation
- `setOwnerId()` — set the owner of the created records
- `setSendNotificationEmail(true)` — notify the new owner
- `setOpportunityName()` — otherwise defaults to the company name

Reading the results:

```java
for (Database.LeadConvertResult result : results) {
    if (result.isSuccess()) {
        System.debug('Account: ' + result.getAccountId()
                   + ' Contact: ' + result.getContactId()
                   + ' Opportunity: ' + result.getOpportunityId());
    } else {
        for (Database.Error err : result.getErrors()) {
            System.debug('Conversion failed: ' + err.getMessage());
        }
    }
}
```

**Conversion counts as multiple DML operations** — one for each record created plus the lead update. Converting 200 leads in one transaction will exceed limits. The practical batch size is well under 100, and bulk conversion belongs in Batch Apex.

## Matching to existing records

By default, conversion creates a new Account named after the Lead's `Company` text. Since that text is free-form, "Northwind Manufacturing", "Northwind Mfg", and "northwind manufacturing ltd" produce three separate accounts.

This is the largest data quality problem in the whole lead process.

Salesforce offers some matching in the conversion UI, showing possible existing accounts and contacts. It is limited, and in practice most orgs build their own matching, either before conversion or as part of it.

```java
public with sharing class LeadMatchingService {

    public static Map<Id, Id> findMatchingAccounts(List<Lead> leads) {
        Set<String> domains = new Set<String>();
        Map<Id, String> domainByLead = new Map<Id, String>();

        for (Lead lead : leads) {
            if (String.isNotBlank(lead.Email) && lead.Email.contains('@')) {
                String domain = lead.Email.substringAfter('@').toLowerCase();
                domainByLead.put(lead.Id, domain);
                domains.add(domain);
            }
        }

        Map<String, Id> accountByDomain = new Map<String, Id>();
        for (Account acc : [
            SELECT Id, Email_Domain__c FROM Account
            WHERE Email_Domain__c IN :domains
        ]) {
            accountByDomain.put(acc.Email_Domain__c.toLowerCase(), acc.Id);
        }

        Map<Id, Id> result = new Map<Id, Id>();
        for (Id leadId : domainByLead.keySet()) {
            Id accountId = accountByDomain.get(domainByLead.get(leadId));
            if (accountId != null) {
                result.put(leadId, accountId);
            }
        }
        return result;
    }
}
```

Email domain matching is crude but effective for business-to-business, and it catches the majority of cases that name matching misses. Free email domains need excluding, obviously.

The matched account ID then goes into `setAccountId()`, and conversion attaches rather than creates.

## Triggers during conversion

Conversion fires triggers on all four objects: Lead update, Account insert, Contact insert, Opportunity insert. Understanding which context you are in matters, because logic appropriate for a normal Account insert may not be appropriate during conversion.

Apex can detect it:

```java
public with sharing class AccountTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isInsert) {
            // records created by conversion have their lead source populated from the lead
            AccountService.applyDefaults(Trigger.new);
        }
    }
}
```

For Lead specifically, `Trigger.new` records will have `IsConverted = true` during the conversion update, which is the reliable way to identify conversion in a Lead trigger:

```java
for (Lead lead : Trigger.new) {
    Lead prior = Trigger.oldMap.get(lead.Id);
    if (lead.IsConverted && !prior.IsConverted) {
        // this update is the conversion itself
    }
}
```

A caution worth knowing: **validation rules on Account, Contact, and Opportunity all apply during conversion.** A required field on Opportunity that the lead has no source for will block conversion entirely, with an error users find baffling because they were converting a lead, not creating an opportunity. Reviewing validation rules with conversion in mind is a step most implementations skip and then debug later.

## Person Accounts

If Person Accounts are enabled, conversion behaves differently: a Lead with no `Company` value converts into a Person Account rather than a separate Account and Contact. Whether that is desirable depends on the business model. See [[04.5 - Accounts - Business vs Person Accounts]].

## Reporting after conversion

The `Converted*Id` fields are what make lead-to-revenue reporting possible.

```sql
SELECT LeadSource, COUNT(Id) converted, SUM(ConvertedOpportunity.Amount) pipeline
FROM Lead
WHERE IsConverted = true AND ConvertedDate = LAST_N_MONTHS:12
GROUP BY LeadSource
```

Conversion rate by source, cycle time from creation to conversion, and pipeline generated per source are the three metrics that justify the whole lead process. All three depend on statuses being maintained honestly and on conversion actually being used rather than reps creating opportunities directly.

## Practical guidance

**Map every custom Lead field or do not create it.** Unmapped fields are data loss with extra steps.

**Build account matching.** Relying on the default behaviour guarantees duplicate accounts.

**Review validation rules on the three target objects** for conversion compatibility before go-live.

**Batch conversions in Apex.** The DML cost per lead is high.

**Do not let reps bypass conversion.** An opportunity created directly, with a lead left sitting in Working, breaks attribution permanently.

**Decide the opportunity question deliberately.** Not every qualified lead should produce an opportunity immediately. Converting without an opportunity, and creating one when a real deal exists, keeps the pipeline honest.
