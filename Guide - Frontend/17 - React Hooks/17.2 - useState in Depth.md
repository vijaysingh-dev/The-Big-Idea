# useState in Depth

The snapshot model and batching are covered in [[16.4 - State and useState Mental Model]]. This note covers the parts that come up once you are past the basics.

## Lazy initialization

```jsx
useState(readFromStorage());       // runs on EVERY render, result discarded after the first
useState(() => readFromStorage()); // runs once
```

The argument is an expression evaluated before `useState` is called, so React cannot avoid running it. Passing a function defers it to the initial render only.

Worth doing whenever initialization touches `localStorage`, parses JSON, computes over a list, or calls `crypto.randomUUID()`.

The syntax overlap means storing a function as state needs double wrapping:

```jsx
const [fn, setFn] = useState(() => myFunction);       // stores the function
setFn(() => newFunction);                              // updater returning the function
```

## Updater functions

```jsx
setCount(c => c + 1);
```

Use the updater form whenever the next value depends on the previous one. Two reasons beyond correctness within a single handler:

**It removes the value from the dependency array:**

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);   // correct — no dependency on count
```

Without the updater form, `count` must be a dependency, so the interval is torn down and recreated every second.

**It survives stale closures.** A callback captured in an event listener, a timer, or a promise continuation reads the value from *its* render. The updater form reads the current value at apply time instead ([[02.3 - Closures]]).

Note that updater functions must be pure — React may call them twice in Strict Mode.

## The bailout

React compares with `Object.is`. Identical values may skip the re-render:

```jsx
setCount(0);      // already 0 — bail out
setUser(user);    // same reference — bail out
setItems([...items]);  // new array, same contents — RE-RENDERS
```

The last line is a common accidental re-render: spreading an unchanged array creates a new reference, and React has no way to know the contents match.

React may still render once more before settling — the bailout skips the commit, not always the render — so do not rely on it as a guarantee.

## Objects and arrays in state

Always replace, never mutate ([[06.7 - Immutable Data Patterns]]):

```jsx
setUser(u => ({ ...u, name }));
setItems(items => [...items, newItem]);
setItems(items => items.filter(i => i.id !== id));
setItems(items => items.map(i => i.id === id ? { ...i, done: true } : i));
setItems(items => items.toSorted(cmp));
```

For anything past two levels of nesting, either flatten the shape ([[20.7 - State Normalization]]) or use Immer ([[20.6 - Immer and Immutable Updates]]).

## Splitting versus grouping

```jsx
// Separate — good when they change independently
const [name, setName] = useState("");
const [email, setEmail] = useState("");

// Grouped — good when they always change together
const [position, setPosition] = useState({ x: 0, y: 0 });
```

The cost of grouping is that every update must spread; the cost of splitting is more update calls in handlers that change several. Neither costs re-renders — updates within one handler are batched regardless.

Past roughly five or six related fields with interdependent transitions, `useReducer` is usually clearer ([[17.10 - useReducer]]).

## Derived state does not belong in useState

```jsx
// Redundant
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce(sum, 0)), [items]);

// Correct
const [items, setItems] = useState([]);
const total = items.reduce(sum, 0);
```

Every stored derived value is a synchronization path that can break, and the effect version renders twice per change. Compute during render; wrap in `useMemo` only if measurement shows it matters ([[17.6 - useMemo]]).

## Adjusting state during render

There is one legitimate case for updating state during render — when a component needs to reset something because a prop changed, and `key` is not appropriate:

```jsx
function List({ items }) {
  const [selection, setSelection] = useState(null);
  const [prevItems, setPrevItems] = useState(items);

  if (items !== prevItems) {
    setPrevItems(items);
    setSelection(null);
  }
}
```

React detects a `setState` call during the render of the *same* component and immediately re-renders with the new state, before committing anything or rendering children. No extra paint, no flash.

This is documented and supported, but it should be rare. `key` handles most resets more clearly, and the pattern must never call `setState` on a *different* component during render — that is an error.

## Async state and race conditions

```jsx
const [data, setData] = useState(null);

useEffect(() => {
  const controller = new AbortController();

  fetch(url, { signal: controller.signal })
    .then(r => r.json())
    .then(setData)
    .catch(e => { if (e.name !== "AbortError") setError(e); });

  return () => controller.abort();
}, [url]);
```

Without cancellation, a slow earlier request can resolve after a fast later one and overwrite it ([[04.6 - AbortController and Cancellation]]). This is the main reason to use a data library rather than `useState` plus `useEffect` for server data ([[24.6 - TanStack Query Fundamentals]]).

Note that setting state after unmount is no longer warned about in React 18+, but the underlying race is still a bug.

## Typing

```tsx
const [count, setCount] = useState(0);                 // number
const [user, setUser] = useState<User | null>(null);   // explicit when null-initialized
const [items, setItems] = useState<Item[]>([]);        // explicit for empty arrays

type Setter = React.Dispatch<React.SetStateAction<User>>;
```

`useState(null)` infers `null`, so the generic is required whenever the initial value is narrower than the eventual type.

## How senior engineers actually use this

**They default to the updater form** for any dependent update, which makes handlers and effects immune to staleness.

**They use lazy initialization** for anything more expensive than a literal.

**They derive instead of storing**, and treat a `useEffect` that calls `setState` from other state as a code smell.

**They keep server data out of `useState`** entirely, since caching, deduplication, cancellation and refetching all have to be rebuilt otherwise.

**They reach for `useReducer`** once a component has several interdependent state values.

## Common pitfalls

- `useState(expensive())` running every render.
- `setCount(count + 1)` called several times in one handler.
- Mutating state objects, producing no re-render.
- Storing derived values and letting them desync.
- Spreading unchanged arrays or objects and causing needless re-renders.
- Stale closures in timers and event listeners.
- Race conditions from uncancelled fetches.
- `useState(null)` without a type parameter in TypeScript.

## Interview angle

Beyond the snapshot question, the useful depth here is lazy initialization (and why the function form matters), the updater form's role in removing effect dependencies and defeating stale closures, and the `Object.is` bailout explaining why mutation fails. Mentioning the legitimate "adjust state during render" pattern is unusual and shows you have read the documentation carefully rather than only used the API.
