# Chunking Strategies

## Why Chunking Matters

Chunking is the most impactful architectural decision in a RAG system. The right chunk size and strategy determines:

- Whether the retrieved chunk contains enough context to answer the question
- Whether the retrieved chunk is precise enough to be useful (not swamped by irrelevant content)
- How many tokens you consume in the LLM call
- Whether the LLM can locate the answer within the chunk

**The fundamental tension**:

- Small chunks → precise retrieval, but may miss surrounding context
- Large chunks → more context, but retrieval is noisier and uses more tokens

---

## The Goldilocks Problem

```
Too small (50 tokens):
  "Revenue grew 12% year-over-year"
  ← No context: year? which company? compared to what?

Too large (5000 tokens):
  [Full 10-page earnings report]
  ← Noisy: model has to find the relevant sentence in a wall of text

Just right (300-500 tokens):
  [Earnings summary paragraph with company, date, key metrics]
  ← Enough context, specific enough to be useful
```

---

## Strategy 1: Fixed-Size Chunking

Split every N tokens, with overlap of M tokens:

```python
def fixed_size_chunk(text, chunk_size=512, overlap=64):
    tokens = tokenizer.encode(text)
    chunks = []
    
    start = 0
    while start < len(tokens):
        end = min(start + chunk_size, len(tokens))
        chunk_tokens = tokens[start:end]
        chunks.append(tokenizer.decode(chunk_tokens))
        start += chunk_size - overlap   # slide forward with overlap
    
    return chunks
```

**Overlap** preserves context across chunk boundaries — sentences split by a chunk boundary appear in both adjacent chunks, so neither loses context.

**When to use**: Simple, fast. Good baseline. Use when documents are homogeneous (all similar length and structure).

**Failure mode**: Splits mid-sentence or mid-paragraph, destroying the semantic unit.

## Strategy 2: Recursive Character Splitting

Split by semantic separators in order of priority, falling back to smaller separators:

```python
# LangChain's RecursiveCharacterTextSplitter logic
SEPARATORS = ["\n\n", "\n", ". ", " ", ""]

def recursive_split(text, chunk_size, separators=SEPARATORS):
    # Try to split by the highest-priority separator
    for sep in separators:
        if sep in text:
            parts = text.split(sep)
            # Combine parts that are too small, split parts that are too large
            return merge_and_split(parts, chunk_size, sep)
    
    # Fallback: split by characters
    return [text[i:i+chunk_size] for i in range(0, len(text), chunk_size)]
```

**When to use**: Default choice for most documents. Respects paragraph and sentence boundaries. Better than fixed-size for prose.

## Strategy 3: Semantic Chunking

Split where the semantic content changes significantly:

```python
def semantic_chunk(text, threshold=0.3):
    sentences = split_into_sentences(text)
    embeddings = embedding_model.encode(sentences)
    
    chunks = []
    current_chunk = [sentences[0]]
    
    for i in range(1, len(sentences)):
        # Compare current sentence to previous
        similarity = cosine_similarity(embeddings[i], embeddings[i-1])
        
        if similarity < threshold:
            # Semantic break — start new chunk
            chunks.append(" ".join(current_chunk))
            current_chunk = [sentences[i]]
        else:
            current_chunk.append(sentences[i])
    
    chunks.append(" ".join(current_chunk))
    return chunks
```

**Advantage**: Each chunk is semantically coherent — all sentences about the same topic.

**Disadvantage**: More expensive (requires embedding every sentence). Inconsistent chunk sizes. Threshold requires tuning per domain.

**When to use**: Long documents with distinct topic shifts (legal docs, technical manuals, research papers).

## Strategy 4: Document-Structure-Aware Chunking

Use the document's own structure (headings, sections) as chunk boundaries:

```python
def structure_aware_chunk(markdown_text, max_chunk_tokens=512):
    # Split on markdown headings
    sections = re.split(r'\n#{1,3} ', markdown_text)
    chunks = []
    
    for section in sections:
        if count_tokens(section) <= max_chunk_tokens:
            chunks.append(section)
        else:
            # Further split large sections recursively
            chunks.extend(recursive_split(section, max_chunk_tokens))
    
    return chunks
```

**When to use**: Markdown documents (wikis, GitHub READMEs), HTML with clear heading hierarchy, technical documentation.

**Preserve heading context**: A chunk from "## Revenue Analysis" should carry that heading in its metadata or text — otherwise retrieval loses the section context.

## Strategy 5: Hierarchical / Parent-Child Chunking

Index small chunks for retrieval precision, but return the parent chunk for full context:

```python
# Index structure
parent_chunks = split_document(text, chunk_size=2000)   # large
child_chunks = split_document(text, chunk_size=300)     # small

# Each child chunk knows its parent
for child in child_chunks:
    child.parent_id = find_parent(child, parent_chunks)

# Index child chunks for retrieval (precise matching)
vector_store.index(child_chunks)

# At query time: retrieve child chunks, then fetch parent for context
def retrieve_with_parent(query, top_k=5):
    child_results = vector_store.search(query, top_k=top_k)
    parent_ids = {chunk.parent_id for chunk in child_results}
    return [document_store.get(pid) for pid in parent_ids]
```

**Why this works**: Small chunks embed more precisely — query "What was Q3 revenue?" matches a small chunk containing exactly that sentence. But when passed to the LLM, you send the larger parent chunk with full surrounding context.

**When to use**: Technical documentation, earnings reports, legal contracts — any document where precise retrieval AND full context both matter.

## Strategy 6: Metadata-Aware Chunking

Tag each chunk with structured metadata extracted from the document:

```python
def metadata_aware_chunk(document):
    chunks = base_chunker(document.text)
    
    for chunk in chunks:
        # Extract structured metadata
        chunk.metadata.update({
            "date": extract_date(chunk.text),
            "entities": extract_entities(chunk.text),  # NER
            "section": find_section_heading(chunk.text, document),
            "document_type": classify_document(document),
        })
    
    return chunks
```

Metadata enables **filtered retrieval**:

```python
# Only retrieve from recent documents
results = vector_store.search(
    query=query,
    filter={"date": {"$gte": "2024-01-01"}, "document_type": "earnings_report"}
)
```

## Chunking for Specific Content Types

|Content Type|Recommended Strategy|Notes|
|---|---|---|
|Prose / articles|Recursive with ~512 tokens|Natural paragraph boundaries|
|Technical docs|Structure-aware (heading-based)|Preserve section context|
|Legal/contracts|Semantic chunking|Section-coherent chunks important|
|Code|By function/class|Never split within a function|
|Q&A documents|One Q&A pair per chunk|Self-contained retrieval unit|
|Tables|One table per chunk|Preserve tabular structure|
|Slack/chat|By conversation thread|Context requires thread|

---

## Practical Chunk Size Guidelines

|Use Case|Chunk Size (tokens)|Overlap|
|---|---|---|
|Dense technical docs|256–512|50–100|
|General knowledge base|512–1024|100–200|
|Long-form documents|1024–2048|200–400|
|Q&A pairs|Variable (full Q+A)|None|
|Code snippets|Variable (full function)|None|

**Rule of thumb**: Chunk size should be tuned against your evaluation set, not chosen arbitrarily. Try 3 sizes and measure retrieval recall@10. The best performing one wins.
