# Containers From First Principles

#backend #containers #linux

> **In one line:** A container is an ordinary Linux process with a restricted view of the system — namespaces limit what it can see, cgroups limit what it can use, and nothing else about it is special.

---

## The Idea

⚠️ **There is no "container" object in the Linux kernel.** There is a process, with some flags set at creation, and a filesystem it was told to treat as root.

```
Namespaces  → what the process can SEE
cgroups     → what the process can USE
Capabilities, seccomp → what the process can DO
Union filesystem → what the process's root looks like
```

💡 **Once you internalise "it is just a process", most container behaviour stops being surprising** — why `ps` inside a container shows PID 1, why memory limits kill your process, why a container with no `init` handles signals badly ([[11.7 - Graceful Shutdown and Draining]]).

---

## Namespaces

```c
clone(child_fn, stack, CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | ..., arg);
```

| Namespace | Isolates |
|---|---|
| **PID** | Process IDs. Your process becomes PID 1 |
| **NET** | Network interfaces, routes, ports, iptables |
| **MNT** | Mount points and the filesystem view |
| **UTS** | Hostname |
| **IPC** | Shared memory, semaphores |
| **USER** | User and group IDs. **Root inside can be unprivileged outside** |
| **CGROUP** | The cgroup hierarchy view |
| TIME | Boot time and monotonic clock offsets |

```bash
sudo unshare --pid --fork --mount-proc /bin/bash
ps aux                # only your processes. You are PID 1
```

**Two commands, and you have made a container.**

### The PID 1 problem

⚠️ **PID 1 has special kernel semantics: default signal handlers are not installed.** A process that does not explicitly handle `SIGTERM` **ignores it entirely** and gets `SIGKILL` after the grace period ([[11.7 - Graceful Shutdown and Draining]]).

```dockerfile
CMD python -m app                     # ❌ shell form: sh is PID 1, does not forward signals
CMD ["python", "-m", "app"]           # ✅ exec form: python is PID 1
ENTRYPOINT ["tini", "--"]             # ✅ a proper init that forwards and reaps
```

💡 **PID 1 is also responsible for reaping orphaned children.** A process that does not reap accumulates zombies. **`tini` exists solely to do these two things correctly**, and it is about 200 lines.

**Test it:** `docker stop` your container and time it. **Under a second means signals work; ten seconds means you got `SIGKILL`.**

### User namespaces

💡 **UID 0 inside the namespace can map to an unprivileged UID outside.** A process that believes it is root has no privileges on the host.

⚠️ **Rootless containers are the meaningful security improvement here**, and they are still not the default in many setups. **Check whether yours are.**

## cgroups

**Namespaces limit visibility; cgroups limit consumption.**

```bash
# cgroup v2
echo "500000 1000000" > /sys/fs/cgroup/mygroup/cpu.max     # 0.5 CPU
echo "536870912" > /sys/fs/cgroup/mygroup/memory.max        # 512 MB
echo $$ > /sys/fs/cgroup/mygroup/cgroup.procs
```

### Memory limits kill, they do not throttle

⚠️ **Exceeding `memory.max` triggers the OOM killer.** Your process is killed with `SIGKILL` — **no cleanup, no graceful shutdown, no in-flight request completion.**

```
State: Terminated
Reason: OOMKilled
Exit Code: 137          # 128 + 9 (SIGKILL)
```

💡 **Exit code 137 means OOM-killed. Memorise it** — it is the single most common confusing container failure, and it looks like a crash with no logs because the process never got a chance to log anything.

**The container is then restarted, often into the same condition**, producing a crash loop.

### CPU limits throttle, they do not kill

```
cpu.max = 50000 100000     # 50ms of CPU per 100ms period
```

⚠️ **When the quota is exhausted, the process is stopped until the next period** — up to 100ms of dead time.

```bash
cat /sys/fs/cgroup/cpu.stat
# nr_throttled 4821
# throttled_usec 38472913
```

💡 **`nr_throttled` climbing is the explanation for "the service is slow and CPU usage is only 40%".** The average is low because the process spent half of each period frozen. **This is one of the most misdiagnosed performance problems in Kubernetes** ([[13.4 - Probes Resources and Autoscaling]]).

### The runtime must see the limit

⚠️ **Older runtimes read `/proc/cpuinfo` and `/proc/meminfo`, which show the *host's* values.** A container limited to 0.5 CPU on a 64-core machine sees 64 cores and sizes its thread pools accordingly.

```python
os.cpu_count()          # ⚠️ may return the host's core count
len(os.sched_getaffinity(0))    # better, and still not cgroup-aware
```

💡 **Read the cgroup limit directly:**

```python
def cpu_limit() -> float:
    quota, period = Path("/sys/fs/cgroup/cpu.max").read_text().split()
    return float(period) if quota == "max" else float(quota) / float(period)
```

**Size your worker count from this, not from `os.cpu_count()`** ([[01.10 - Connection Pools and Limits]]).

## The Filesystem

```
Layer 4 (writable)   your container's changes
Layer 3 (read-only)  COPY . /app
Layer 2 (read-only)  RUN pip install -r requirements.txt
Layer 1 (read-only)  FROM python:3.13-slim
```

**OverlayFS presents the stack as one filesystem.** Reads fall through to the first layer containing the file; **writes copy the file up to the writable layer first.**

⚠️ **Copy-up means the first write to a large file copies the entire file.** Writing one byte to a 2GB file in a lower layer copies 2GB.

💡 **This is why databases in containers need a volume.** A write-heavy workload against the overlay filesystem is dramatically slower than against a mounted volume.

### Layers are why cache ordering matters

```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt     # cached unless requirements change
COPY . .                                # invalidated on every code change
```

⚠️ **Reverse those two and every code change reinstalls every dependency.** The most common Dockerfile mistake, and it costs minutes on every build ([[13.2 - Production Dockerfiles]]).

**A layer's cache is invalidated by its own change or any change above it**, so put the least-frequently-changing instructions first.

## Images and Registries

```
Manifest → config (env, cmd, entrypoint) + layer digests
Each layer → a content-addressed tarball
```

💡 **Layers are shared across images by digest.** Ten images from the same base share one copy of that base on disk and pull it once.

⚠️ **A tag is mutable. A digest is not.**

```dockerfile
FROM python:3.13-slim                    # ⚠️ moves
FROM python:3.13-slim@sha256:abc123...   # ✅ immutable
```

**Pin by digest for reproducibility**, and update deliberately.

## In Production

### Container is not a security boundary

⚠️ **A shared kernel means a kernel exploit escapes the container.** Namespaces are isolation, not virtualisation.

| Defence | |
|---|---|
| **Run as non-root** | The single highest-value hardening |
| Read-only root filesystem | Plus `tmpfs` for writable paths |
| **Drop all capabilities** | Add back only what is needed |
| seccomp profile | Restrict syscalls |
| No privileged containers | |
| **Do not mount the Docker socket** | It is root on the host |

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  capabilities: {drop: ["ALL"]}
```

💡 **For genuinely untrusted workloads, use gVisor or Firecracker** — a real kernel boundary. **Ordinary application isolation does not need it; multi-tenant code execution does.**

### Debugging a container

```bash
kubectl exec -it pod -- /bin/sh                 # if a shell exists
kubectl debug -it pod --image=nicolaka/netshoot --target=app    # ephemeral container
```

💡 **`kubectl debug` with an ephemeral container is the answer for distroless images.** It attaches a debugging container to the same namespaces — **you get tooling without shipping tooling in your production image** ([[13.2 - Production Dockerfiles]]).

**This is the technique that makes distroless practical**, and many people avoid distroless because they do not know it exists.

### The failure modes

| Symptom | Cause |
|---|---|
| **Exit 137** | **OOMKilled** |
| Exit 143 | `SIGTERM`, handled. Normal shutdown |
| Exit 1 with no logs | The application failed to start; check `stderr` |
| **`docker stop` takes 10s** | **Signals not reaching PID 1** |
| Slow, low CPU usage | **cgroup throttling** |
| Slow file writes | Overlay copy-up; needs a volume |
| Too many threads | The runtime sees host CPUs |
| Zombie processes | PID 1 not reaping |

### Conduit's container decisions

| Decision | |
|---|---|
| Base image | `python:3.13-slim`, pinned by digest |
| Init | Exec-form `CMD`, with `tini` for workers that spawn children |
| User | Non-root, UID 10001 |
| Root filesystem | Read-only, `tmpfs` for `/tmp` |
| Capabilities | All dropped |
| **Worker count** | **Derived from `cpu.max`, not `os.cpu_count()`** |
| Memory limit | Set from measured usage plus 30% headroom |
| **Debugging** | **`kubectl debug`, no shell in the image** |

⚠️ **The worker-count decision is the one with the largest practical impact.** Getting it from the host's core count on a 64-core node means 64 workers × a pool of 20 = 1,280 database connections from one pod ([[06.9 - Connection Pooling and PgBouncer]]).

## Codebase

**Repo:** `opencontainers/runc`, `krallin/tini`, `moby/moby`

**Question to answer:** In runc, what exactly happens between `runc create` and the container process running — which namespaces are created, in what order, and when are cgroups applied? Then: what does tini do that a plain application entrypoint does not?

**Read, in order:**

1. `krallin/tini/src/tini.c` — **read this first. About 200 lines**, and it does exactly two things: forward signals to the child, and reap zombies. **The answer to the second question, and it makes PID 1's responsibilities concrete**
2. `runc/libcontainer/nsenter/nsexec.c` — **the namespace setup, in C.** `clone` with the namespace flags, and the ordering constraints. **The answer to the first question**
3. `runc/libcontainer/container_linux.go` — `start` and `newInitProcess`. The Go side orchestrating the above
4. `runc/libcontainer/cgroups/fs2/` — **cgroup v2 controllers.** How `memory.max` and `cpu.max` are written
5. `opencontainers/runtime-spec/config.md` — **the specification.** Short, and it tells you precisely what a container is defined to be

💡 Reading `tini.c` in full takes fifteen minutes and permanently fixes your understanding of container signal handling. **Every "why does my container take ten seconds to stop" question is answered by that file.**

**Size:** 1–2 sessions.

## Exercise

**Drill 13.1 — Build a container without Docker**

```
drills/13-containers/
├── manual/{namespaces.sh, cgroups.sh, chroot.sh, mini_container.py}
├── pid1/{no_handler.py, with_handler.py, tini.dockerfile, RESULTS.md}
├── limits/{memory_oom.py, cpu_throttle.py, detect_limits.py, RESULTS.md}
├── filesystem/{layers.sh, copy_up.py, RESULTS.md}
├── security/{escape_attempts.sh, hardened.yaml, FINDINGS.md}
├── debug/{distroless.dockerfile, ephemeral.sh}
└── README.md
```

**Part 1 — Build one by hand.** Using `unshare`, `chroot` and cgroup files directly, create an isolated process with its own PID, network, mount and UTS namespaces, plus a memory and CPU limit.

**No Docker.** Confirm: `ps` shows only your processes, the hostname differs, memory is limited, and CPU is throttled.

**Then write `mini_container.py`** doing the same with `os.unshare` and direct cgroup writes. **A hundred lines, and it demystifies the whole topic.**

**Part 2 — PID 1 signal handling.** Three containers: shell-form `CMD`, exec-form `CMD` with no `SIGTERM` handler, and exec-form with a handler.

**`docker stop` each and time it.**

| Version | Expected |
|---|---|
| Shell form | ~10s (SIGKILL) |
| Exec form, no handler | ~10s (PID 1 ignores default SIGTERM) |
| Exec form, with handler | < 1s |

**The second one surprises people** — exec form alone is not sufficient if the process does not handle the signal.

Then a process spawning children that become orphans. **Count zombies with and without `tini`.**

**Part 3 — Memory limits.** A process gradually allocating memory, with `memory.max` at 256MB.

**Confirm it is `SIGKILL`ed with exit 137**, and confirm no shutdown handler ran and nothing was logged.

Then add a `SIGTERM` handler and confirm it still does not run — **OOM kill is not catchable.**

**Then measure the real memory limit you need** by tracking RSS under load, and set it with 30% headroom.

**Part 4 — CPU throttling.** A CPU-bound workload with `cpu.max` at 0.5.

**Measure request latency and `nr_throttled` from `cpu.stat`.**

**Chart p99 latency against CPU limit** for 0.25, 0.5, 1, 2, 4. **Confirm that reported CPU usage stays well below the limit while latency degrades badly** — that is the misdiagnosis this drill exists to prevent.

Then remove the limit and set only a request, and compare.

**Part 5 — Detecting your own limits.** Implement `cpu_limit()` and `memory_limit()` reading cgroup files.

**Compare against `os.cpu_count()` on a machine with more cores than your limit.**

Then size your worker count and pool from the real limit, and **compute how many database connections the naive version would have opened.**

**Part 6 — Copy-up.** A 500MB file in a lower image layer.

**Measure the time to write one byte to it**, then to the same file on a mounted volume.

**Report the ratio.** Then run a write-heavy workload against both.

**Part 7 — Security.** Attempt from inside a container: read host processes, access the host network, write to a host path, and escalate to root.

**Confirm each is blocked or not**, with default settings and with the hardened `securityContext`.

Then mount the Docker socket and **demonstrate that it is equivalent to root on the host.** Delete that experiment afterwards.

**Part 8 — Debugging without a shell.** Build a distroless image with no shell.

**Confirm `kubectl exec` fails.** Then use `kubectl debug` with an ephemeral container and **confirm you can inspect the process, its network and its filesystem.**

**Write the runbook entry**, because during an incident nobody remembers the flag order.

**Done when:**
- You built a working container with `unshare`, `chroot` and cgroup files
- All three PID 1 variants are timed, including the surprising second one
- An OOM kill demonstrably bypasses your shutdown handler
- Your latency-versus-CPU-limit chart shows throttling with low reported usage
- Your application derives its worker count from cgroups, not host cores
- You have the copy-up versus volume write ratio
- The hardened `securityContext` blocks attempts the default allows
- You can debug a distroless container, with a written runbook entry
