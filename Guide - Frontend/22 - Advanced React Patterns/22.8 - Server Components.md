# Server Components

React Server Components (RSC) run **only on the server**. Their code never ships to the browser, and their output is a serialized description of UI that the client renders.

```jsx
// app/page.jsx — a Server Component by default in Next.js App Router
import { db } from "@/lib/db";

export default async function ProductPage({ params }) {
  const product = await db.product.findUnique({ where: { id: params.id } });

  return (
    <article>
      <h1>{product.name}</h1>
      <AddToCartButton productId={product.id} />
    </article>
  );
}
```

```jsx
// AddToCartButton.jsx
"use client";

export function AddToCartButton({ productId }) {
  const [added, setAdded] = useState(false);
  return <button onClick={() => setAdded(true)}>Add to cart</button>;
}
```

The database client, the query, and the page component itself contribute **zero bytes** to the client bundle.

## Not the same as SSR

| | SSR | Server Components |
| --- | --- | --- |
| Runs on server | yes | yes |
| Code shipped to client | yes — for hydration | no |
| Re-renders on client | yes | never |
| Can hold state | yes | no |
| Output | HTML | a serialized component tree |

Traditional SSR renders to HTML and then ships the same component code to the client so it can hydrate and take over. RSC ships **only the result**. There is nothing to hydrate for a Server Component because it will never re-render.

The output format is not HTML — it is the RSC payload, a streaming serialized tree that can interleave with client components and be re-fetched on navigation without a full page load.

## The boundary

`"use client"` marks a boundary, not a single file. Everything imported by a client component becomes client code too.

```
Server Component (default)
  ├── Server Component
  ├── "use client" Client Component
  │     └── everything imported here is also client code
  └── Server Component
```

This has a practical consequence people hit immediately: putting `"use client"` at the top of a layout makes the entire subtree client-side, defeating the point.

Push the boundary **down**, as close to the interactivity as possible.

## Passing server content into client components

A Client Component cannot import a Server Component, but it **can render one passed as `children`**:

```jsx
// Server Component
export default function Page() {
  return (
    <ClientAccordion>
      <ServerRenderedContent />   {/* stays server-rendered */}
    </ClientAccordion>
  );
}
```

The element is created in the server's render, so it arrives as data rather than as code. This is the key composition technique — it lets an interactive wrapper contain server-only content, and it is the same element-as-prop idea from [[16.3 - Components and Props]].

## Props must be serializable

```jsx
// Fine
<ClientComponent data={{ id: 1, items: [] }} date={new Date()} />

// Error
<ClientComponent onSelect={() => {}} icon={<Icon />} instance={new Map()} />
```

Props crossing the boundary are serialized. Functions, class instances and symbols cannot cross. React elements can.

The exception is **Server Actions**, which are functions the server explicitly marks as callable:

```jsx
async function addToCart(formData) {
  "use server";
  await db.cart.add({ productId: formData.get("id") });
  revalidatePath("/cart");
}

<form action={addToCart}>
```

The client receives a reference, not the function body. Calling it makes an RPC to the server.

## What Server Components cannot do

- `useState`, `useReducer`, `useEffect` — no state, no lifecycle
- Event handlers — `onClick`, `onChange`
- Browser APIs — `window`, `localStorage`, `document`
- Context providers or `useContext`
- Refs
- Custom hooks that use any of the above

They can: be `async`, `await` directly, read from a database or filesystem, use secrets, and render other Server or Client Components.

## What you gain

**Zero bundle cost for data-fetching code.** A markdown renderer, a date library, an ORM client, a syntax highlighter — all stay on the server. This is often the largest practical win: bundles shrink substantially without any code splitting work ([[19.7 - Bundle Analysis and Optimization]]).

**Data fetching without waterfalls.** A Server Component `await`s directly, next to the component that needs the data, without a client round trip per level ([[19.4 - Suspense]]).

**Direct backend access.** No API layer needed for server-rendered data — the component queries directly, with secrets safely on the server.

**Automatic code splitting at the boundary.** Every `"use client"` import is a split point.

## What you give up

**A server.** RSC requires a Node or edge runtime. A static SPA on a CDN cannot use it.

**Framework coupling.** RSC needs bundler and router integration. In practice this means Next.js App Router, or React Router v7 / Waku.

**A more complex mental model.** Two kinds of components with different capabilities, a serialization boundary, and the need to reason about where code runs.

**Different debugging.** Server component errors appear in server logs, not the browser console.

## Data fetching patterns

```jsx
// Parallel — both start immediately
export default async function Page() {
  const userPromise = getUser();
  const postsPromise = getPosts();
  const [user, posts] = await Promise.all([userPromise, postsPromise]);
}

// Streaming — the shell renders while slow parts load
export default function Page() {
  return (
    <>
      <Header />
      <Suspense fallback={<Skeleton />}>
        <SlowSection />
      </Suspense>
    </>
  );
}
```

Sequential `await`s in nested Server Components serialize into a waterfall, exactly as they do on the client ([[04.4 - async await]]). Start requests in parallel and let Suspense stream the results.

React's `cache()` deduplicates identical calls within a single render pass, so two components requesting the same user do not produce two queries.

## Where client state still lives

RSC does not replace client state management. Interactive components still need `useState`, and shared client state still needs context or a store ([[20.1 - Where State Should Live]]).

The shift is that **server data no longer needs client caching** for the initial render — it arrives already rendered. Client-side data libraries remain necessary for data that changes in response to user interaction after load.

Providers must be Client Components, wrapping server children:

```jsx
// providers.jsx
"use client";
export function Providers({ children }) {
  return <ThemeContext value={theme}>{children}</ThemeContext>;
}
```

Children passed through stay server-rendered — only the provider itself is client code.

## Current state

RSC is stable in React 19 and is the default in the Next.js App Router. Adoption outside Next.js is growing but still limited by the bundler and router integration required.

Given how recently this landed, verify specifics against current documentation rather than any single source.

## How senior engineers actually use this

**They push `"use client"` as far down the tree as possible**, treating a boundary near the root as a design failure.

**They pass server content as `children`** into client wrappers rather than making the wrapper's whole subtree client-side.

**They keep heavy, non-interactive dependencies on the server** — that is where most of the bundle win comes from.

**They start requests in parallel** and use Suspense boundaries for streaming.

**They still use a client data library** for post-load interactions, and do not treat RSC as a replacement.

## Common pitfalls

- `"use client"` at the top of a layout, making everything client-side.
- Passing functions or class instances across the boundary.
- Sequential `await`s producing server-side waterfalls.
- Trying to use `useState` or browser APIs in a Server Component.
- Expecting a Client Component to import a Server Component — it must receive it as `children`.
- Confusing RSC with SSR in discussion.
- Assuming RSC removes the need for client state management.

## Interview angle

"What are Server Components" needs the distinction from SSR stated clearly: SSR renders on the server and ships the component code for hydration; RSC ships only the rendered output and never re-renders, so the code contributes nothing to the bundle. Then the boundary model — `"use client"` marks a subtree, so push it down — and the composition technique of passing Server Components as `children` into Client Components. Naming the tradeoff (requires a server and framework integration, adds a mental model) makes the answer balanced rather than promotional.
