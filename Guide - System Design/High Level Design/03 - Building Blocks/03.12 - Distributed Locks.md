# Distributed Locks

> **Revision tags:** #building-blocks #distributed-systems #concurrency  
> **Related:** [[03.5 - Redis Patterns]] | [[04.7 - Distributed Lock]]

---

## What It Is

A distributed lock ensures that across multiple processes or machines, only one holder can perform a critical section at a time.

```
Without distributed lock:
  Server A: reads inventory=5, decrements to 4, writes
  Server B: reads inventory=5, decrements to 4, writes  ← same 5! lost update
  Result: inventory=4 instead of 3

With distributed lock:
  Server A acquires lock → reads 5, writes 4, releases lock
  Server B acquires lock → reads 4, writes 3, releases lock
  Result: inventory=3 ✅
```

---

## Why It Exists

In distributed systems, a single process mutex (like a threading lock) doesn't work — it only covers one machine. When multiple instances of a service run concurrently, coordinating access to shared resources requires a lock that lives outside any single process.

**Common use cases:**
- Prevent double-charging a payment
- Ensure only one instance runs a scheduled job at a time
- Coordinate leader election
- Prevent race conditions on shared external resources

---

## Properties a Distributed Lock Must Have

1. **Mutual exclusion:** Only one client holds the lock at any time
2. **Deadlock-free:** Even if a lock holder crashes, the lock is eventually released (via TTL)
3. **Fault-tolerant:** Lock remains available even if some nodes fail

## Redis-Based Lock (Single Node)

The simplest production-grade approach for non-critical use cases.

```python
import uuid, redis

r = redis.Redis()
LOCK_KEY = "lock:order:42"
TTL_SECONDS = 30

def acquire_lock(key, ttl):
    token = str(uuid.uuid4())
    # SET key token NX EX ttl — atomic: set only if key doesn't exist
    acquired = r.set(key, token, nx=True, ex=ttl)
    return token if acquired else None

def release_lock(key, token):
    # Lua script: check token matches before deleting (atomic)
    script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """
    r.eval(script, 1, key, token)

# Usage
token = acquire_lock(LOCK_KEY, TTL_SECONDS)
if token:
    try:
        process_order(42)
    finally:
        release_lock(LOCK_KEY, token)
else:
    raise LockNotAvailableError()
```

**Why the token?** Without it, a process could release another process's lock:
```
Process A acquires lock (token=abc), starts work
A's TTL expires → lock released automatically
Process B acquires lock (token=xyz), starts work
A finishes (took too long) → deletes lock key → deletes B's lock!
```
The Lua script ensures you only release the lock if you still own it.

## Fencing Tokens

TTL-based locks have an inherent race: the lock holder can be paused (GC, OS scheduling) past its TTL, then resume and act while someone else holds the lock.

```
Process A:  acquire lock (TTL=30s)
             ... GC pause for 35 seconds ...
Process B:  lock expired → acquires lock
Process A:  resumes, believes it holds lock → writes to storage ← PROBLEM
```

**Fencing tokens** solve this. The lock service issues a monotonically increasing token with each grant. Storage layer rejects writes with an older token.

```
A acquires lock: token=33
B acquires lock: token=34 (A's expired)
A tries to write with token=33 → storage rejects (34 > 33 is current)
B writes with token=34 → accepted ✅
```

ZooKeeper and etcd provide fencing tokens natively via their versioning mechanisms (`zxid`, revision).

## Redlock (Multi-Node Redis)

For higher fault tolerance, Redis creator Salvatore Sanfilippo proposed Redlock: acquire the lock on a majority (N/2+1) of independent Redis instances.

```
5 Redis instances:
Acquire on instance 1 ✅
Acquire on instance 2 ✅
Acquire on instance 3 ✅  ← majority (3/5) acquired
Acquire on instance 4 ✅
Acquire on instance 5 ❌ (network timeout)

Lock acquired: majority succeeded within time window
```

**Total elapsed time must be < TTL** for the lock to be considered valid.

**Controversy:** Martin Kleppmann published a detailed critique arguing Redlock is unsafe under certain timing assumptions (clock drift, process pauses). The consensus in the industry: Redlock is acceptable for efficiency locks (preventing duplicate work) but not for correctness locks (where the fencing token approach is required).

## ZooKeeper / etcd Locks

For stronger guarantees, use a consensus-based coordination service.

**ZooKeeper ephemeral sequential nodes:**
```
All candidates create: /locks/order-42/lock-0000000001
                                       lock-0000000002
                                       lock-0000000003

Smallest node = lock holder
Others watch the node immediately before theirs
When that node is deleted → try to acquire (watch-based, no polling)
```

If the lock holder crashes, ZooKeeper automatically deletes the ephemeral node (session expires) → next candidate is notified.

**Guarantees:** Linearizable, provides fencing via `zxid`. No clock dependency.

**etcd** provides similar primitives with lease-based locking and revision-based fencing.

**Tradeoff:** ZooKeeper/etcd add operational complexity (separate cluster to maintain). Use Redis-based locks for most cases; use ZooKeeper/etcd when the correctness guarantee is critical.

---

## Lock Granularity

Course-grained locking → simple but high contention  
Fine-grained locking → complex but more parallelism

```
Coarse: lock:global_inventory      ← entire inventory locked per write
Fine:   lock:product:sku:XJ900     ← only this product locked
```

Always lock at the finest granularity that correctly protects the resource.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Lock holder crashes without releasing | Lock held until TTL expires | Short TTL + background heartbeat to extend |
| TTL too short | Lock expires while holder is working | Extend TTL via heartbeat if work continues |
| TTL too long | Crash causes long unavailability | Balance with expected work duration |
| Clock skew (Redlock) | Lock validity window miscalculated | Use fencing tokens; avoid Redlock for correctness-critical locks |
| Redis node failure (single-node) | Lock service unavailable | Sentinel/Cluster for HA, or accept brief unavailability |

## Interview Expectations

- Know the Redis SET NX EX pattern
- Know why you need a token to release (not just a plain delete)
- Know fencing tokens and when they matter
- Know Redlock exists but is controversial
- Know ZooKeeper/etcd for stronger guarantees
