# TCP Settings That Matter

#backend #networking #tcp #production

> **In one line:** Most kernel tuning advice on the internet is cargo cult; there are about eight settings that genuinely matter for a backend service, and five of them belong in your application code, not in `sysctl`.

---

## The Idea

Search for "Linux TCP tuning" and you get a list of forty `sysctl` lines copied between blog posts since 2009. Half are obsolete, several are harmful, and most address problems you do not have.

Modern Linux auto-tunes well. The defaults are good for most workloads. **The settings that matter are the ones the defaults cannot know about** — how many connections you expect, how long your connections idle, and whether your traffic is interactive or bulk.

This note is the short list, with why each one exists and how to tell whether it applies to you.

⚠️ **Rule before touching anything: measure, change one thing, measure again.** Tuning without measurement is how people end up with forty lines of `sysctl` and no idea which ones do anything.

---

## Set These in Your Application

Per-socket settings are better than kernel-wide ones. They are explicit, they travel with your code, and they work in containers where you may not control the node.

### TCP_NODELAY — for anything interactive

```python
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

**The problem it solves.** Nagle's algorithm holds small writes until either the buffer fills or the previous data is acknowledged, to avoid sending 41-byte packets carrying 1 byte of data. Delayed ACK, on the other side, holds acknowledgements for up to 40ms hoping to piggyback them on outgoing data.

Together they deadlock briefly:

```
Sender:   has a small write, waits for the previous ACK  (Nagle)
Receiver: has an ACK, waits for outgoing data to attach it to  (delayed ACK)
          ...40ms pass...
Receiver: gives up and sends the ACK alone
Sender:   finally sends
```

A consistent, unexplained 40ms on small request/response exchanges.

💡 **Set `TCP_NODELAY` on every request/response protocol.** Redis, gRPC, Postgres drivers and most HTTP servers already do. If you write your own protocol and see suspiciously round 40ms latencies, this is it — and the roundness of the number is the giveaway.

Leave Nagle on only for genuinely bulk streaming where you write in small pieces and do not care about per-write latency.

### SO_KEEPALIVE — for anything long-lived

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 60)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)
```

The default `TCP_KEEPIDLE` is **7200 seconds**. Two hours of holding a file descriptor and a pool slot for a peer that no longer exists. Set it to 60.

Covered in [[02.3 - TCP Connection Lifecycle]]. Application-level heartbeats are still better where the protocol allows them, because they also catch a peer that is alive but wedged.

### SO_REUSEADDR — on every server socket

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
```

Lets you rebind immediately after restart instead of waiting out `TIME_WAIT`. No downside. Always set it.

### SO_REUSEPORT — for multi-process servers

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
```

Several processes bind the same port; the kernel distributes connections between them.

⚠️ Distribution is by hash of the connection tuple, not by load. One worker can receive a run of expensive connections while another idles. With long-lived connections (WebSocket, gRPC) this imbalance persists for the connection's lifetime and can be severe.

For short HTTP requests it is fine. For long-lived connections, prefer a shared accept queue or an L7 proxy that balances per-request.

### Buffer sizes — usually leave alone

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 4 * 1024 * 1024)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF, 4 * 1024 * 1024)
```

⚠️ **Setting these explicitly disables Linux's auto-tuning for that socket.** Usually a downgrade. The one real case for setting them is a high bandwidth-delay product link where you need a window larger than auto-tuning will grow to — cross-continent bulk transfer, essentially.

Calculate the requirement rather than guessing:

```
buffer needed = bandwidth × RTT
1 Gbps × 200ms = 25 MB
```

Then verify with `ss -ti` that the window actually grows to match. See [[02.4 - Flow Control and Congestion Control]].

## Set These at the Kernel

Fewer, and each has a specific trigger.

### somaxconn — if you have connection bursts

```bash
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=8192
```

Your `listen(backlog)` is **silently clamped** to `somaxconn`. The default was 128 for years (now 4096 on newer kernels). Asking for 2048 and getting 128 with no warning is a real and common surprise.

**How to tell you need it:**

```bash
ss -tln sport = :8000        # Recv-Q approaching Send-Q
netstat -s | grep -i "listen queue"    # non-zero and climbing
```

⚠️ **A full accept queue usually means your application is too slow to accept, not that the queue is too small.** Raising the backlog buys you a bigger buffer in front of the same problem. Check for a blocked event loop first ([[01.6 - The Blocking Call Problem]]). Raise the backlog to absorb genuine bursts, not to hide a stall.

### Ephemeral port range — if you make many outbound connections

```bash
sysctl -w net.ipv4.ip_local_port_range="10000 65535"
```

Widens the range from ~28,000 to ~55,000 source ports.

⚠️ **This is a symptom fix.** If you are exhausting ports, you are not reusing connections. Fix that first ([[01.10 - Connection Pools and Limits]]). Widen the range only when you have genuine need for that many simultaneous outbound connections.

### tcp_tw_reuse — if TIME_WAIT is genuinely your limit

```bash
sysctl -w net.ipv4.tcp_tw_reuse=1
```

Allows reusing a `TIME_WAIT` socket for a new **outbound** connection when timestamps make it safe. Safe on modern kernels, and it only helps the outbound direction.

⚠️ **`net.ipv4.tcp_tw_recycle` was removed from Linux in 4.12 and must never be used.** It broke connections from clients behind NAT in ways that were extremely hard to diagnose. If you find it in a blog post or an old runbook, that document is stale — treat everything else in it with suspicion.

### Congestion control — if your clients are on lossy networks

```bash
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq
```

BBR substantially outperforms CUBIC when loss is caused by wireless interference rather than congestion. Worth testing if you serve mobile clients directly. Not worth changing for internal service-to-service traffic on a clean network.

### File descriptor limits — always

```bash
ulimit -n 65536
```

Not TCP exactly, but every socket is a file descriptor, and running out produces incoherent errors ([[02.2 - Sockets From First Principles]]).

```yaml
# Kubernetes
spec:
  containers:
    - name: api
      securityContext:
        capabilities:
          add: ["SYS_RESOURCE"]
```

Or set it in the container entrypoint. Export current fd usage as a metric.

## Things People Tune That Do Not Help

| Setting | Why not |
|---|---|
| `tcp_tw_recycle` | **Removed. Never use it.** Breaks NAT |
| `tcp_fin_timeout` | Only affects `FIN_WAIT_2`, not `TIME_WAIT`. Almost always the wrong knob |
| Huge `tcp_max_tw_buckets` | Hides the reuse problem rather than fixing it |
| Manually setting `tcp_rmem`/`tcp_wmem` | Auto-tuning is better unless you have a specific BDP requirement |
| `tcp_slow_start_after_idle=0` | Genuinely helps for long-lived bursty connections, but check `ss -ti` first to confirm the window is actually collapsing |
| Disabling `tcp_timestamps` | Breaks window scaling safety and `tw_reuse`. Do not |
| Increasing `netdev_max_backlog` | Only relevant at very high packet rates on the NIC |

💡 **A useful heuristic: if a suggested setting does not come with a metric that tells you whether it applied, it is cargo cult.** Every legitimate change in this note has an observable before-and-after.

## TCP Fast Open

```bash
sysctl -w net.ipv4.tcp_fastopen=3
```

Allows data in the SYN packet, saving one round trip on repeat connections to the same server.

Reality: middlebox support is patchy, benefits are modest, and HTTP/3's 0-RTT handshake solves the same problem better. Know it exists; do not spend time on it.

## In Production

### The audit worth doing

For any service, answer these seven questions:

1. Is `TCP_NODELAY` set on request/response sockets?
2. Is keepalive enabled with a sane idle time, or do you have application heartbeats?
3. What is your fd limit, and what is your current usage?
4. What is `somaxconn`, and what backlog did you actually request?
5. Are you reusing outbound connections, or opening one per request?
6. What is your `TIME_WAIT` count under peak load?
7. Do you have per-socket timeouts on every network call?

Most services fail three or four of these. Fixing them is worth more than any `sysctl` change.

### Container reality

In Kubernetes, `sysctl` settings are node-level. Options:

```yaml
# Allowed "safe" sysctls, per pod
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "4096"
```

Only a small allow-list is permitted without a privileged init container. **Which is another argument for doing it per-socket in your application** — no node access needed, and the setting is versioned with your code.

### The realistic priority order

If you have limited time, spend it here:

```
1. Connection reuse in your HTTP/DB clients        ← biggest win by far
2. Timeouts on every call                           ← prevents the worst failures
3. TCP_NODELAY on request/response protocols        ← removes a 40ms floor
4. Keepalive or heartbeats on long-lived connections
5. fd limits raised and monitored
6. somaxconn, if you see accept queue overflow
7. Everything else                                  ← measure first
```

Items 1 and 2 are application code and they matter far more than the entire rest of the list combined.

## Codebase

**Repo:** `redis/redis`, `haproxy/haproxy`, `envoyproxy/envoy` (docs)

**Question to answer:** Which socket options does each of these set, and where do they differ? Redis, HAProxy and Envoy have different workloads — find one option each sets differently and work out why.

**Read, in order:**

1. `redis/src/anet.c` — the complete set of options Redis uses, each with a helper function. This is the cleanest catalogue of socket options in any codebase
2. `redis/src/config.c` — search for `tcp-backlog` and `tcp-keepalive`. Note the warning Redis prints if `somaxconn` is lower than the configured backlog. **That warning is a nice piece of engineering empathy** and worth copying in your own servers
3. `haproxy/src/proto_tcp.c` — HAProxy's socket setup. It is a proxy, so it configures both directions
4. Envoy docs: the `socket_options` and `per_connection_buffer_limit_bytes` configuration reference

**Then, practically:** grep your own service's dependencies for `setsockopt` and find out what your HTTP client, database driver and Redis client actually set. Most engineers have never checked, and the answers are frequently surprising.

**Size:** 1 session.

## Exercise

**Drill 2.5 — Measure every knob**

The rule for this drill: **no setting goes in your final config unless you measured its effect.**

```
drills/02-tuning/
├── harness/
│   ├── server.py         # configurable socket options
│   ├── client.py         # configurable load pattern
│   └── measure.sh        # ss -ti sampling + latency histogram
├── nodelay/
│   ├── experiment.py     # request/response with and without
│   └── FINDINGS.md
├── backlog/
│   ├── burst.py          # 2000 connections in 100ms
│   ├── sweep.sh          # somaxconn 128 / 1024 / 4096
│   └── FINDINGS.md
├── keepalive/
│   └── detection_time.md # table of detection times per config
├── buffers/
│   ├── bdp.py            # high-RTT transfer, auto vs manual buffers
│   └── FINDINGS.md
├── congestion/
│   └── cubic_vs_bbr.md   # reuse the 02.4 harness, lossy conditions
├── audit/
│   ├── my_deps.md        # what your actual dependencies set
│   └── CHECKLIST.md      # the seven questions, answered for Conduit
└── README.md
```

**Part 1 — The 40ms floor.** Small request/response protocol, 1000 exchanges, with and without `TCP_NODELAY`. Plot the latency histogram for both.

Without it you should see a bimodal distribution with a cluster near 40ms. **Seeing that shape yourself is the point** — you will recognise it instantly in a production histogram afterwards.

Then find the specific condition that triggers it: it needs a write, then a second small write before the ACK arrives. Write down the exact pattern in your own words.

**Part 2 — Backlog under burst.** Server that accepts slowly. Fire 2000 connections in 100ms. Sweep `somaxconn` across 128, 1024, 4096 with a matching `listen()`.

Measure: connections refused, connections timed out, and the p99 time-to-accept. Confirm that raising the backlog converts *failures* into *latency* — which is sometimes what you want and sometimes not.

Then reproduce the same overflow with a large backlog but a blocked event loop. **Two causes, one symptom.** Write down how you would distinguish them from metrics alone.

**Part 3 — Keepalive detection time.** Establish a connection, drop the peer with a firewall rule, and measure time-to-detection for: defaults, `KEEPIDLE=60`, `KEEPIDLE=10` with `INTVL=5` and `CNT=2`, and 15-second application heartbeats.

Build the table. Include the cost column — packets per idle connection per minute — because that matters at 50,000 connections.

**Part 4 — Buffers and BDP.** Using `tc netem` for a 200ms RTT and 1 Gbps, transfer 100MB with auto-tuned buffers, then with `SO_RCVBUF` set small, then set large.

Sample `ss -ti` throughout and plot the window size. Confirm that auto-tuning reaches the BDP and that setting the buffer manually can make things worse.

**Part 5 — Audit your dependencies.** For httpx, asyncpg, redis-py and uvicorn, find out what socket options each actually sets. Read the source. Write it up in `my_deps.md` with file references.

**Part 6 — The Conduit checklist.** Answer the seven questions for Conduit phase 1. For each "no", either fix it or write down why it does not apply. This becomes part of [[Assets.4 - Production Readiness Checklist]].

**Done when:**
- Your part 1 histogram shows the bimodal 40ms cluster disappearing
- You can produce accept-queue overflow two ways and distinguish them
- The keepalive table has four rows with detection times and packet costs
- `my_deps.md` cites real source lines
- The Conduit checklist has seven answered questions
