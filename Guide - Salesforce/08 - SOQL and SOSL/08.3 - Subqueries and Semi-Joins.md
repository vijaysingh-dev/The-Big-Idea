# Subqueries and Semi-Joins

## Filtering by the existence of related records

A **semi-join** filters records based on whether related records exist. An **anti-join** filters on their absence.

```sql
-- Semi-join: assets that have at least one open claim
SELECT Id, Name, SerialNumber
FROM Asset
WHERE Id IN (
    SELECT Asset__c FROM Warranty_Claim__c WHERE Status__c != 'Closed'
)
```

```sql
-- Anti-join: assets with no claims at all
SELECT Id, Name, SerialNumber
FROM Asset
WHERE Id NOT IN (
    SELECT Asset__c FROM Warranty_Claim__c
)
```

The inner query selects exactly one field, which must be an ID or a reference field. Selecting more than one is a syntax error.

## The most useful applications

**Records missing an expected relationship.** The gap report pattern:

```sql
-- Closed cases with no knowledge article attached
SELECT Id, CaseNumber, Reason, Type
FROM Case
WHERE IsClosed = true
  AND ClosedDate = LAST_N_DAYS:90
  AND Id NOT IN (SELECT CaseId FROM CaseArticle)
```

```sql
-- Accounts with no open opportunity
SELECT Id, Name, Industry
FROM Account
WHERE Type = 'Customer'
  AND Id NOT IN (SELECT AccountId FROM Opportunity WHERE IsClosed = false)
```

```sql
-- Contracts approaching renewal with no renewal opportunity created
SELECT Id, ContractNumber, EndDate, AccountId
FROM Contract
WHERE Status = 'Activated'
  AND EndDate = NEXT_N_DAYS:120
  AND Id NOT IN (SELECT Source_Contract__c FROM Opportunity WHERE Source_Contract__c != null)
```

That last one is the idempotency guard from the renewal batch job in [[04.11 - Quotes, Orders and Contracts]], written as a query rather than a stored field.

**Filtering by a related record's attributes** without returning them:

```sql
-- Claims on assets belonging to enterprise-tier accounts
SELECT Id, Claim_Number__c, Claim_Amount__c
FROM Warranty_Claim__c
WHERE Asset__c IN (
    SELECT Id FROM Asset WHERE Account.Tier__c = 'Enterprise'
)
```

This is often cleaner than traversing `Asset__r.Account.Tier__c` in the `WHERE`, and sometimes performs differently — worth checking the query plan for both forms on a large object.

## The limits

**One level of nesting.** A subquery cannot contain another subquery.

**Two semi-joins or anti-joins per query**, and they cannot be combined with `OR` in some configurations.

**The inner query selects one field only.**

**The inner query has its own row limit**, and a subquery matching a very large number of rows is a common cause of poor performance.

## The `NOT IN` performance trap

This is the important part of this note.

**`NOT IN` with a subquery is frequently non-selective.** The engine must evaluate every row of the outer object against the inner result set, and there is no index that helps.

On a small object this is invisible. On an object with several million rows it produces a query that times out, and the failure appears suddenly as data grows.

The symptoms and the alternatives:

**Alternative 1: a maintained flag field.** A checkbox or lookup on the parent, populated by automation, so the query filters on an indexed field instead of an absence.

```sql
-- Instead of NOT IN, filter on a field a trigger maintains
SELECT Id, ContractNumber, EndDate
FROM Contract
WHERE Status = 'Activated'
  AND EndDate = NEXT_N_DAYS:120
  AND Renewal_Opportunity__c = null
```

`Renewal_Opportunity__c = null` on an indexed lookup field is far more efficient than an anti-join, and it is the reason the renewal batch in section 04 uses a lookup rather than a subquery.

**Alternative 2: query both sides and diff in Apex.** Viable when both sets are bounded.

```java
public with sharing class CoverageGapService {

    public static List<Asset> findUncoveredAssets(Id accountId) {
        Map<Id, Asset> assets = new Map<Id, Asset>([
            SELECT Id, Name, SerialNumber
            FROM Asset WHERE AccountId = :accountId
        ]);

        // collect the covered ids, then remove them from the full set
        Set<Id> covered = new Set<Id>();
        for (Machine_Coverage__c coverage : [
            SELECT Asset__c FROM Machine_Coverage__c
            WHERE Asset__c IN :assets.keySet()
              AND Service_Contract__r.Status__c = 'Active'
        ]) {
            covered.add(coverage.Asset__c);
        }

        assets.keySet().removeAll(covered);
        return assets.values();
    }
}
```

Two selective queries and a set operation, instead of one non-selective one. `Set.removeAll()` doing the diff is the piece worth remembering.

**Alternative 3: restrict the outer set first.** An anti-join over a narrowly filtered outer query is much less dangerous than one over the whole object. Adding a date filter or an owner filter before the `NOT IN` often makes an unusable query usable.

## Semi-joins versus relationship subqueries

Two different things that look similar:

```sql
-- Relationship subquery: returns the children alongside the parents
SELECT Id, Name, (SELECT Id, Status__c FROM Warranty_Claims__r)
FROM Asset

-- Semi-join: filters parents by child existence, returns no child data
SELECT Id, Name
FROM Asset
WHERE Id IN (SELECT Asset__c FROM Warranty_Claim__c)
```

Use a relationship subquery when you need the child data. Use a semi-join when you only need to filter and the child data is irrelevant — it returns fewer rows and consumes less heap.

## `IN` with an Apex collection

Distinct from a semi-join, and usually preferable when the set is known:

```java
Set<Id> assetIds = new Set<Id>{ id1, id2, id3 };

List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c
    FROM Warranty_Claim__c
    WHERE Asset__c IN :assetIds
];
```

This binds a collection rather than running a nested query. It is selective if the field is indexed, and it is the standard bulkification pattern — collect IDs across a batch, query once.

The practical limit is the size of the bound collection. Very large `IN` lists degrade, and beyond a few thousand values the query becomes slow. At that point, the semi-join or a chunked approach is better.

## Combining with other filters

Semi-joins compose with normal filters, and putting the selective filter first helps the engine:

```sql
SELECT Id, CaseNumber, Subject
FROM Case
WHERE AccountId = :accountId
  AND IsClosed = false
  AND ContactId IN (
      SELECT Id FROM Contact WHERE Title LIKE '%Manager%'
  )
```

The `AccountId` filter is selective and narrows the set before the semi-join is evaluated, which is exactly what you want. A semi-join as the only filter on a large object is the shape to avoid.

## Practical guidance

**Use anti-joins for gap analysis** — records missing an expected relationship. They are the clearest way to express it.

**Watch `NOT IN` on large objects.** It is frequently non-selective and fails as data grows.

**Prefer a maintained field to an anti-join** in anything that runs regularly, particularly scheduled jobs.

**Always add a selective filter alongside a semi-join** on a large object.

**Bind an Apex collection when the set is known and bounded.** It is clearer and usually faster.

**Check the query plan** for any semi-join running against a large object. See [[08.10 - Query Plan Tool and Query Optimization]].
