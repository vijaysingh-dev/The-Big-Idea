# Monolith, Modular Monolith, Microservices

#backend #microservices #architecture

> **In one line:** Microservices buy independent deployability at the cost of turning every function call into a network call — and most teams pay that cost before they have the organisational problem it solves.

---

## The Idea

```
Monolith            one deployable, one database, one codebase
Modular monolith    one deployable, enforced internal boundaries
Microservices       many deployables, separate databases, network between them
```

| | Monolith | Modular monolith | Microservices |
|---|---|---|---|
| Deploy unit | One | One | **Many** |
| Refactoring across boundaries | Trivial | Easy | **Very hard** |
| Transactions across boundaries | **ACID** | ACID | **Sagas** ([[08.11 - Durable Workflows and Sagas]]) |
| Team independence | Low | Medium | **High** |
| Operational complexity | Low | Low | **High** |
| Debugging | One stack trace | One stack trace | **Distributed tracing** |
| Failure modes | Process-level | Process-level | **Partial failure everywhere** |
| Scaling | Whole app | Whole app | **Per service** |

💡 **The organising insight: microservices are an organisational solution, not a technical one.** They exist so that five teams can deploy independently without coordinating. If you are one team, you are paying for coordination you do not need.

⚠️ **The technical arguments — independent scaling, technology diversity, fault isolation — are all achievable other ways and all weaker than people claim.**

---

## What You Actually Give Up

The costs are concrete and they are consistently understated.

### Transactions

```python
# Monolith
async with conn.transaction():
    await documents.create(doc)
    await quotas.increment(org_id, doc.size)
    await audit.log(user_id, "document.created")
# ← all or nothing
```

```python
# Microservices
doc = await document_service.create(doc)
await quota_service.increment(org_id, doc.size)      # ← fails? doc already exists
await audit_service.log(user_id, "document.created")  # ← fails? no audit record
```

⚠️ **You have replaced a database transaction with a distributed one, which does not exist.** The replacement is a saga with compensating actions, and it is dramatically more code and more failure modes.

💡 **This is the single largest cost and it is rarely counted.** Every operation spanning two services needs idempotency, retries, compensation and reconciliation ([[07.5 - Idempotency Keys and Deduplication]]).

### Queries

```sql
-- Monolith
SELECT d.title, u.name, o.plan
FROM documents d JOIN users u ON u.id = d.author_id JOIN orgs o ON o.id = d.org_id;
```

```python
# Microservices
docs = await document_service.list(org_id)
users = await user_service.get_many([d.author_id for d in docs])     # ← batch, or N+1
org = await billing_service.get_org(org_id)
# then join in application code
```

⚠️ **A join becomes a network call plus application-side assembly**, and if you forget to batch it becomes N+1 across the network ([[05.6 - The N+1 Problem and DataLoader]]).

**Reporting queries spanning services are the worst case** — "documents per plan tier per month" has no home.

### Latency

```
Monolith:      function call        ~0.001 ms
Microservices: gRPC call            ~1–5 ms
               with a retry         ~10 ms
               chained 4 deep       ~20 ms of pure coordination
```

💡 **Every service boundary adds a round trip, and depth serialises them** ([[05.10 - Federation and Schema Composition]]). A request touching four services in a chain has four times the latency floor of one touching them in parallel.

### Debugging

```
Monolith:      one stack trace shows the whole path
Microservices: four services, four log streams, and a trace ID if you set it up
```

⚠️ **Distributed tracing is not optional in a microservice system** ([[12.3 - Instrumenting Conduit End to End]]). Without it, "why was this request slow" is unanswerable.

**Budget for the observability work as part of the split**, not as a follow-up.

## The Modular Monolith

The option people skip, and usually the right answer.

```
src/
├── documents/           ← a module
│   ├── api.py           public interface — the ONLY entry point
│   ├── service.py
│   ├── models.py
│   └── repository.py
├── billing/
│   ├── api.py
│   └── ...
└── search/
```

```python
# billing/service.py
from documents.api import get_document           # ✅ the public interface

from documents.repository import DocumentRepo    # ❌ reaching inside
from documents.models import Document            # ❌ depending on internals
```

💡 **The discipline: modules talk through explicit interfaces, never by importing each other's internals or querying each other's tables.** That is exactly the microservice constraint, enforced by convention and tooling rather than by the network.

### Enforcing it

```python
# import-linter contract
[importlinter:contract:module-boundaries]
name = Modules only use public APIs
type = forbidden
source_modules = billing, search
forbidden_modules = documents.repository, documents.models
```

```sql
-- Separate schemas, separate database roles
CREATE SCHEMA documents;
CREATE SCHEMA billing;

GRANT USAGE ON SCHEMA documents TO billing_role;    -- ⚠️ or don't
REVOKE ALL ON SCHEMA documents FROM billing_role;
```

💡 **Schema separation with role-based permissions makes cross-module table access a database error**, which is stronger enforcement than any code review. **It is also exactly the boundary you would need if you later split**, so the work is not wasted.

⚠️ **Without enforcement, a modular monolith degrades into a monolith within one sprint.** Someone reaches across a boundary because it is faster, the review passes, and the boundary is gone.

**Automated enforcement is what makes it real.**

### What you get

| | |
|---|---|
| **ACID transactions** | Across modules, still |
| **Refactoring** | Move a boundary in an afternoon |
| **One deploy** | No version skew, no coordination |
| **One trace** | Debugging is a stack trace |
| **Boundaries you can validate** | Before committing to a network between them |
| **A clear extraction path** | If a module genuinely needs to be a service |

💡 **The strongest argument: a modular monolith lets you get the boundaries wrong cheaply.** Moving a boundary in a monolith is a refactor; moving it between services is a migration with data movement, API changes and a deployment plan.

⚠️ **Boundaries are almost always wrong the first time**, because you do not yet know how the domain will evolve. **Splitting early means committing to boundaries at the moment you understand them least.**

## When to Actually Split

```
Do you have multiple teams that need to deploy independently?
├── NO → modular monolith. Stop here
│
└── YES → is a shared deploy actually blocking them?
    ├── NO → improve the deploy pipeline first
    └── YES → split, along team boundaries
```

### The genuine signals

| Signal | |
|---|---|
| **Deploy coordination is a real bottleneck** | Teams waiting on each other's releases |
| **A component has genuinely different scaling needs** | GPU work, or 100× the traffic |
| **Different availability requirements** | Payments must survive what search does not |
| **Regulatory or data residency isolation** | Some data cannot share infrastructure |
| **Different technology is genuinely required** | A Rust or Go component for a specific reason |
| **The codebase is too large for one team to reason about** | And modules did not solve it |

⚠️ **Notice how many are organisational.** The technical ones — scaling, technology — are usually satisfiable within a monolith by running the same deployable with different configuration.

```yaml
# One image, different roles
deployment: api        command: ["uvicorn", "app:app"]
deployment: worker     command: ["arq", "app.worker"]
deployment: embedder   command: ["arq", "app.embed_worker"]   # GPU nodes
```

💡 **"We need to scale the embedder separately" does not require a separate service.** One codebase, one image, three deployments with different resources. **You get independent scaling without independent deployment**, and that is often exactly the split you wanted.

### The false signals

| Claim | Reality |
|---|---|
| "Microservices scale better" | The same deployable with more replicas scales fine |
| "Fault isolation" | A network call fails *more* ways than a function call |
| "Technology diversity" | Usually a liability. Fewer languages is better |
| "It is the modern architecture" | Not an argument |
| "Our codebase is too big" | **Modules solve this. Try them first** |
| "Independent scaling" | Separate deployments of one image |

⚠️ **The fault isolation claim deserves particular scepticism.** In a monolith, a bug in the billing module is an exception in one request. In a microservice system, a slow billing service exhausts your connection pool, saturates your workers, and can take down every service calling it — unless you built circuit breakers, timeouts and bulkheads ([[11.3 - Circuit Breakers and Bulkheads]]).

💡 **Microservices give you *more* failure modes, not fewer.** They give you the *ability* to isolate failures, which you then have to implement.

## In Production

### The cost, quantified

Before splitting, count what you will build.

| Per service | |
|---|---|
| CI/CD pipeline | |
| Deployment manifests, resource limits, probes | |
| Monitoring, dashboards, alerts | |
| On-call runbook | |
| Client library, or generated stubs | |
| Contract tests | ([[05.13 - Contract Testing and Schema Evolution]]) |
| Circuit breakers and timeouts on every caller | |
| Trace propagation | |
| Auth between services | mTLS or tokens |

| Per split boundary | |
|---|---|
| The API contract, and its evolution | |
| Data ownership decisions and duplication | ([[10.4 - Data Ownership]]) |
| Saga for any operation spanning it | |
| Reconciliation for the data you duplicated | |

⚠️ **A four-service split is roughly four times the operational surface plus six boundaries to maintain.** That is a real ongoing cost, and it does not go away.

### The extraction procedure

When you do split, do it in this order:

```
1. Establish the module boundary in the monolith first
2. Enforce it — no cross-boundary imports, no cross-schema queries
3. Route all access through the module's public API
4. Change that API to be network-shaped (async, serialisable, no shared objects)
5. Extract the data — separate schema, then separate database
6. Move the code out, keep the same API
7. Point the caller at the network
```

💡 **Steps 1–4 are all reversible and all deliverable in a monolith.** By the time you reach step 5, you know the boundary is right because you have been living with it.

⚠️ **Extracting the data is the hard step, not extracting the code.** Foreign keys must go, joins must be replaced, and transactions must become sagas ([[10.4 - Data Ownership]]).

**If a boundary has fifteen foreign keys crossing it, that is the boundary telling you it is wrong.**

### The strangler pattern

```
Client → Gateway → ┬── monolith  (existing routes)
                   └── new service (extracted routes)
```

Route by path at the gateway, moving routes one at a time. **The monolith and the service coexist**, and rollback is a routing change.

💡 **This is expand/contract at the architecture level** ([[06.11 - Zero Downtime Migrations]]), and it is the only safe way to extract from a running system.

### Conduit's position

**Modular monolith through phase 3. One split in phase 4, and it is arguable.**

| Module | Extract? |
|---|---|
| `documents` | No — the core domain, everything touches it |
| `sources` | No — tightly coupled to documents |
| `search` | No — a query path over the same data |
| **`ingestion`** | **Maybe** — different scaling, long-running, and in phase 9 it needs GPUs |
| `billing` | No — low traffic, and transactional with organisations |

💡 **The honest phase-4 answer for one developer is: do not split, run the ingestion worker as a separate deployment of the same image.** You get independent scaling and GPU placement without a network boundary, a saga, or duplicated data.

⚠️ **Conduit's phase 4 splits anyway, deliberately, because the point is to feel the cost** ([[00.3 - The Conduit Project]]). **The ADR should say so honestly**: "we split to learn what it costs, and here is what it cost."

**That is a more valuable outcome than a clean architecture, and it is a genuinely defensible thing to say in an interview.**

## Codebase

**Repo:** `saleor/saleor`, `GoogleCloudPlatform/microservices-demo`, `gitlabhq/gitlabhq`

**Question to answer:** Saleor is a large modular monolith and Online Boutique is a small microservice system. For the same kind of operation — placing an order — compare what each has to do. Then: how does GitLab, one of the largest open monoliths, enforce internal boundaries?

**Read, in order:**

1. `saleor/saleor/order/actions.py` — **order placement in a monolith.** Note the single transaction spanning inventory, payment records and order creation
2. `microservices-demo/src/checkoutservice/main.go` — **the same operation across five services.** Count the network calls, the error handling, and what happens when one fails partway
3. `microservices-demo/protos/demo.proto` — the full system contract. **The boundaries, made explicit**
4. `gitlab/doc/development/software_design.md` and their modular monolith documentation — **how GitLab enforces boundaries without splitting.** Domain boundaries, and the tooling that checks them
5. `saleor/saleor/plugins/` — Saleor's extension mechanism, which gives some of the independence of services without the network

💡 The checkout service comparison is the most instructive read in this note. **The monolith version is one transaction; the microservice version is five calls with partial-failure handling at each step, and it still does not compensate properly.** Reading them side by side makes the cost concrete rather than theoretical.

**Size:** 2 sessions.

## Exercise

**Drill 10.1 — Split, then measure what it cost**

```
drills/10-architecture/
├── monolith/
│   ├── modules/          # documents, billing, search
│   ├── boundaries.py     # import-linter contracts
│   ├── schemas.sql       # separate schemas, separate roles
│   └── tests/
├── split/
│   ├── document_service/
│   ├── billing_service/
│   ├── gateway/
│   └── protos/
├── measure/
│   ├── latency.py        # same operations, both architectures
│   ├── failure.py        # what breaks when one part is down
│   ├── transaction.py    # ACID vs saga
│   ├── operations.py     # count the operational surface
│   └── RESULTS.md
├── enforcement/
│   ├── break_boundary.py # violate it, see if CI catches it
│   └── FINDINGS.md
├── extraction/
│   ├── strangler.py      # route by path
│   ├── data_split.sql    # remove foreign keys, replace joins
│   └── RESULTS.md
└── ADR.md
```

**Part 1 — Build the modular monolith.** Three modules with enforced boundaries: public API modules, `import-linter` contracts, separate database schemas with separate roles.

Implement an operation spanning all three: create a document, increment the org's quota, index it.

**Part 2 — Break the boundary deliberately.** Import a repository from another module. **Confirm `import-linter` fails the build.**

Then query another module's table directly. **Confirm the database rejects it** because of role permissions.

Then measure how long each violation would have survived without enforcement, by reviewing your own diff and seeing whether you would have caught it.

**Part 3 — Split it.** Extract `documents` and `billing` into separate services with gRPC between them and a gateway in front.

**Implement the same operation.** Count: network calls, error paths, lines of code, and failure modes you had to handle explicitly.

**Part 4 — Measure the latency cost.** The same five operations in both architectures, under identical load.

Measure p50 and p99 for each. **Then chart the difference against the number of service hops per operation.**

**Part 5 — Measure the failure cost.** Take `billing` down.

**Monolith:** which operations fail? **Microservices:** which fail, and does the failure spread?

Then make billing *slow* rather than down. **In the microservice version without circuit breakers, confirm it exhausts the document service's connection pool and degrades operations that do not need billing at all** ([[11.3 - Circuit Breakers and Bulkheads]]).

**This is the fault isolation claim, tested.** Then add circuit breakers and measure the improvement.

**Part 6 — ACID versus saga.** The document-plus-quota operation.

**Monolith:** kill the process mid-transaction. Confirm the state is consistent.

**Microservices:** kill it after the document is created and before the quota increments. **Confirm the state is inconsistent.**

Then implement a saga with compensation. **Count the lines and the failure cases**, and kill the process at each point during compensation too ([[08.11 - Durable Workflows and Sagas]]).

**Part 7 — Count the operational surface.** For both architectures, enumerate: pipelines, dashboards, alerts, runbooks, contracts, and configuration files.

**Report the ratio.**

**Part 8 — The strangler extraction.** Starting from the monolith, extract `documents` using the seven-step procedure while serving traffic.

**Measure downtime — it must be zero.** Then measure what step 5 (data extraction) actually required: foreign keys removed, joins replaced, queries rewritten.

**Then write the ADR for Conduit phase 4**, honestly. If the answer is "we split to learn, and here is what it cost", say that.

**Done when:**
- Boundary violations are caught by both tooling and the database
- Your latency chart shows the cost per service hop
- A slow dependency degraded unrelated operations, and circuit breakers fixed it
- The saga required substantially more code than the transaction, quantified
- You have the operational surface ratio between the two architectures
- The strangler extraction completed with zero downtime
- The ADR is honest about the reason for splitting
