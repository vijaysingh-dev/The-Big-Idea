# Text, Logical and Picklist Functions

## Logical functions

**`IF(condition, valueIfTrue, valueIfFalse)`** — the workhorse. Both branches must return the same type.

**`AND(a, b, ...)`**, **`OR(a, b, ...)`**, **`NOT(a)`** — the function forms are easier to read and indent than `&&` and `||` when there are more than two conditions.

**`CASE(expression, value1, result1, value2, result2, ..., elseResult)`** — a lookup table. Far more readable than nested `IF` when you are mapping one value to another.

```
CASE(Priority__c,
  "Critical", 1,
  "High",     2,
  "Medium",   3,
  "Low",      4,
  99
)
```

The final argument is the default and is mandatory. `CASE` compares for exact equality only — there is no range matching, which is why tier calculations still need nested `IF`.

**`ISBLANK(field)`** — true for null and for empty text. The modern choice over `ISNULL`.

**`BLANKVALUE(field, substitute)`** and **`NULLVALUE(field, substitute)`** — substitute a default. Use these explicitly rather than relying on the "treat blanks as zeroes" checkbox, which is invisible to anyone reading the formula.

**`ISNUMBER(text)`** — whether a text value can be parsed as a number. Useful when validating data that arrived from an integration.

**`ISCHANGED(field)`**, **`PRIORVALUE(field)`**, **`ISNEW()`** — available in validation rules, workflow, and flow formulas, **not** in formula fields. A formula field has no previous state to compare against.

```
// Validation rule: the approved amount can only be set by an approver, and only once set, never reduced
AND(
  ISCHANGED(Approved_Amount__c),
  NOT(ISNEW()),
  Approved_Amount__c < PRIORVALUE(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims)
)
```

## Picklist functions

**`ISPICKVAL(picklistField, "value")`** — the correct way to test a single picklist value. More efficient than converting to text.

**`TEXT(picklistField)`** — converts to the **API name** of the value, not the label. This distinction matters: if someone renames a picklist label from "Closed Won" to "Won", `TEXT()` still returns the API name, and translated orgs return the same API name regardless of the user's language. Comparing against labels breaks in translated orgs; comparing against API names does not.

**`INCLUDES(multiSelectField, "value")`** — the only way to test a multi-select picklist. Returns true if the value is among those selected.

```
INCLUDES(Certifications__c, "Press Line")
```

Multi-select picklists are awkward in every context, and this function is the reason most experienced engineers avoid them. Testing for combinations means several `INCLUDES` calls, counting selections is not directly possible, and reporting on them is painful. A junction object or a set of checkboxes is nearly always better. See [[02.4 - Fields - Types and Behaviour]].

**`PRIORVALUE(TEXT(picklistField))`** — checking what a picklist changed from, in a validation rule.

## Text functions

The commonly used set:

```
LEN(text)                          length
LEFT(text, n) / RIGHT(text, n)     take from either end
MID(text, start, length)           substring, 1-indexed
FIND(search, text)                 position, 0 if not found
CONTAINS(text, search)             true or false, case-sensitive
BEGINS(text, prefix)               true or false
SUBSTITUTE(text, old, new)         replace all occurrences
TRIM(text)                         strip leading and trailing whitespace
UPPER(text) / LOWER(text)          case conversion
LPAD(text, length, pad)            pad from the left
RPAD(text, length, pad)            pad from the right
TEXT(value)                        convert number, date, or picklist to text
VALUE(text)                        convert text to number
BR()                               line break, in text formulas
```

`MID` is 1-indexed, not 0-indexed. `FIND` returns 0 when not found, not -1.

`CONTAINS` is case-sensitive, which surprises people. For a case-insensitive check, lower both sides:

```
CONTAINS(LOWER(Description__c), "urgent")
```

## Regular expressions

**`REGEX(text, pattern)`** is available **in validation rules only**, not in formula fields. It returns true when the text matches the pattern in full — it is a full match, not a search, so patterns usually need `.*` at both ends to find something within a string.

```
// Validation: serial number must match the format XX-9999-XX
NOT(REGEX(Serial_Number__c, "[A-Z]{2}-[0-9]{4}-[A-Z]{2}"))
```

```
// Validation: Indian mobile number, allowing optional country code
AND(
  NOT(ISBLANK(Mobile__c)),
  NOT(REGEX(Mobile__c, "(\\+91[\\-\\s]?)?[6-9][0-9]{9}"))
)
```

Backslashes must be escaped, so `\d` becomes `\\d`. This is the most common source of regex validation rules that never match anything.

The regex flavour is Java's, which supports most of what you would expect but not everything — lookbehind support in particular varies, and complex patterns are worth testing on a real record before trusting.

For anything beyond format validation, Apex is the better tool. A regex in a validation rule that takes ten minutes to read is a maintenance problem.

## Building display text

A frequent use of text formulas is producing a readable summary for a list view or a report.

```
// Claim summary for a list view column
TEXT(Status__c) &
IF(
  ISPICKVAL(Status__c, "Approved"),
  " — " & TEXT(ROUND(Approved_Amount__c / Claim_Amount__c * 100, 0)) & "% of claim",
  IF(
    ISPICKVAL(Status__c, "Rejected"),
    " — " & BLANKVALUE(TEXT(Rejection_Reason__c), "reason not recorded"),
    ""
  )
)
```

`BLANKVALUE` on the rejection reason prevents the whole expression collapsing to null when the reason is empty, which is exactly the null-propagation trap from [[06.1 - Formula Engine and Syntax]].

## IMAGE and HYPERLINK

Text formulas can return HTML, which is how status indicators are built without code.

```
// Traffic light based on days open against the SLA target
IMAGE(
  CASE(
    SIGN(Days_Open__c - SLA_Days__c),
    -1, "/img/samples/light_green.gif",
     0, "/img/samples/light_yellow.gif",
        "/img/samples/light_red.gif"
  ),
  "SLA status"
)
```

```
// Link to the related machine in Lightning
HYPERLINK(
  "/lightning/r/Asset/" & Asset__c & "/view",
  Asset__r.Name,
  "_self"
)
```

Two cautions. `IMAGE` and `HYPERLINK` output does not render everywhere — it works on record pages, list views, and reports, and not in email templates or exported data. And a formula field returning HTML cannot be used for filtering or grouping meaningfully.

For images, referencing a **Static Resource** is more robust than the built-in sample images, which are undocumented and could change:

```
IMAGE("/resource/StatusIcons/green.png", "On track")
```

## Custom permissions in formulas

`$Permission.Custom_Permission_Name` checks whether the running user has a custom permission, granted through a permission set.

This is meaningfully better than checking `$Profile.Name`, because profile names change, orgs have many profiles, and hardcoding one means the formula breaks the moment someone creates a new profile that should also qualify.

```
// Field is editable only by approvers, enforced by validation rather than layout
AND(
  ISCHANGED(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims)
)
```

The pattern: create a custom permission, grant it through a permission set, reference it in formulas and validation rules. Now the question "who can approve claims" has one answer, queryable through permission set assignments. See [[03.4 - Permission Sets and Permission Set Groups]].

## Practical guidance

**Use `ISPICKVAL` for single-value picklist tests**, `TEXT()` when you need the value as a string.

**Compare against API names, not labels.** Labels are translated and renameable.

**Use `CASE` for value mapping**, nested `IF` for ranges.

**Be explicit about nulls** with `BLANKVALUE` rather than relying on a checkbox.

**Escape backslashes in `REGEX`.** It is the most common reason a pattern never matches.

**Avoid multi-select picklists** rather than writing elaborate `INCLUDES` logic around them.

**Use custom permissions, not profile names**, for permission checks in formulas.
