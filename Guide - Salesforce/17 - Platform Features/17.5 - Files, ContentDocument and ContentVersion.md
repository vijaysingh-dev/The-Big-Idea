# Files, ContentDocument and ContentVersion

## The three objects

The file data model confuses people because a single uploaded file creates records in three objects, and the one you query depends on what you want.

```
ContentVersion          the actual file content, one row per version
ContentDocument         the logical file, pointing at the latest version
ContentDocumentLink     the join between a document and a record or user
```

```
Upload "inspection-report.pdf" to a claim
  → ContentVersion    (v1, holds the bytes)
  → ContentDocument   (created automatically, LatestPublishedVersionId → v1)
  → ContentDocumentLink (ContentDocumentId → the document, LinkedEntityId → the claim)

Upload v2 of the same file
  → ContentVersion    (v2)
  → ContentDocument   (LatestPublishedVersionId → v2)
  → no new link
```

**You insert a ContentVersion. The platform creates the ContentDocument.** That asymmetry is the first thing to internalize.

## Uploading from Apex

```java
public with sharing class FileService {

    public static Id attachFile(Id recordId, String fileName, Blob content) {
        ContentVersion version = new ContentVersion(
            Title = fileName,
            PathOnClient = fileName,          // the extension here determines the file type
            VersionData = content,
            IsMajorVersion = true
        );
        insert version;

        // the ContentDocumentId is only populated after insert, so a re-query is required
        Id documentId = [
            SELECT ContentDocumentId FROM ContentVersion WHERE Id = :version.Id
        ].ContentDocumentId;

        insert new ContentDocumentLink(
            ContentDocumentId = documentId,
            LinkedEntityId = recordId,
            ShareType = 'V',
            Visibility = 'AllUsers'
        );

        return documentId;
    }
}
```

Three details that catch people:

**`PathOnClient` determines the file type.** Salesforce reads the extension from it, not from `Title`. Omitting the extension produces a file the browser cannot open.

**`ContentDocumentId` is null before insert** and populated after, which forces the re-query.

**The link is a separate insert.** A ContentVersion with no ContentDocumentLink is an orphan — it exists, consumes storage, and appears on no record.

## Adding a version

To add a version rather than a new file, supply the existing `ContentDocumentId`:

```java
ContentVersion newVersion = new ContentVersion(
    ContentDocumentId = existingDocumentId,   // makes this a version, not a new file
    Title = fileName,
    PathOnClient = fileName,
    VersionData = updatedContent,
    IsMajorVersion = true,
    ReasonForChange = 'Updated after re-inspection'
);
insert newVersion;
```

No new link is needed — the document is already linked, and every consumer sees the new version automatically.

**Version history is retained**, which is one of the genuine advantages of Files over the legacy Attachment object.

## ShareType and Visibility

The two fields on `ContentDocumentLink` that determine access, and the source of most file permission problems.

```
ShareType
  V   Viewer     — read only
  C   Collaborator — read and edit
  I   Inferred   — access follows the linked record's sharing

Visibility
  AllUsers      — internal and external users who can see the record
  InternalUsers — internal only
  SharedUsers   — explicitly shared users only
```

**`ShareType = 'I'`** is usually what you want for a file attached to a record: access follows the record's sharing, so a user who can see the claim can see its files, and a user who cannot, cannot.

**`Visibility = 'InternalUsers'`** hides the file from Experience Cloud users even when they can see the record. Getting this wrong is how internal-only documents become visible to customers on a portal, and it is worth an explicit decision rather than a default.

## Querying files

**Files on a record:**

```sql
SELECT ContentDocumentId,
       ContentDocument.Title,
       ContentDocument.FileExtension,
       ContentDocument.ContentSize,
       ContentDocument.LatestPublishedVersionId,
       ContentDocument.CreatedDate
FROM ContentDocumentLink
WHERE LinkedEntityId = :claimId
```

**A `ContentDocumentLink` query must filter on `LinkedEntityId` or `ContentDocumentId`.** Querying it without one of those filters throws — the object cannot be scanned.

```sql
-- Throws: an implementation restriction
SELECT Id FROM ContentDocumentLink LIMIT 10
```

That restriction means **finding all files across many records requires querying per parent Id in an `IN` clause**, which is fine, and there is no way to list every file in the org through this object.

**The file content:**

```sql
SELECT Id, Title, VersionData, FileType, ContentSize
FROM ContentVersion
WHERE ContentDocumentId = :documentId AND IsLatest = true
```

`IsLatest = true` gets the current version; omitting it returns every version.

**`VersionData` is a Blob and counts toward heap.** Querying it across many rows will exhaust the 6 MB synchronous limit quickly, so select it only when you need the bytes. See [[16.3 - CPU Time and Heap Size]].

## Uploading from LWC

```html
<lightning-file-upload
    label="Attach inspection report"
    name="claimEvidence"
    accept=".pdf,.jpg,.png"
    record-id={recordId}
    onuploadfinished={handleUploadFinished}
    multiple>
</lightning-file-upload>
```

```javascript
handleUploadFinished(event) {
    const files = event.detail.files;
    // documentId is what links to the record; contentVersionId is the specific version
    const documentIds = files.map((file) => file.documentId);
    this.recordUploads(documentIds);
}
```

**`lightning-file-upload` handles the link automatically** when `record-id` is set, which removes the three-step Apex dance entirely.

It also handles chunking for large files and enforces the accepted types. **This is the right way to upload from a component** — building a custom uploader that base64-encodes into Apex hits the 6 MB heap limit and the callout size cap.

Note that `record-id` is required for guest users, and guest upload has additional restrictions.

## Downloading

```javascript
import { NavigationMixin } from 'lightning/navigation';

downloadFile(contentDocumentId) {
    this[NavigationMixin.Navigate]({
        type: 'standard__webPage',
        attributes: {
            url: `/sfc/servlet.shepherd/document/download/${contentDocumentId}`
        }
    });
}
```

For a specific version:

```
/sfc/servlet.shepherd/version/download/{contentVersionId}
```

**Never build a download by querying `VersionData` and constructing a data URI** — it consumes heap, breaks on large files, and the servlet path handles permissions correctly.

## Content Distribution: public links

Sharing a file with someone who has no Salesforce login:

```java
public with sharing class FileSharingService {

    public static String createPublicLink(Id contentVersionId, Integer daysValid) {
        ContentDistribution distribution = new ContentDistribution(
            Name = 'Claim evidence',
            ContentVersionId = contentVersionId,
            PreferencesAllowViewInBrowser = true,
            PreferencesAllowOriginalDownload = true,
            PreferencesNotifyOnVisit = false,
            // an expiry is not set automatically; without it the link is permanent
            ExpiryDate = Datetime.now().addDays(daysValid),
            PreferencesExpires = true
        );
        insert distribution;

        return [
            SELECT DistributionPublicUrl FROM ContentDistribution WHERE Id = :distribution.Id
        ].DistributionPublicUrl;
    }
}
```

**A public link is genuinely public** — anyone with the URL can access the file, with no authentication. Setting `PreferencesExpires` and an `ExpiryDate` is not optional for anything sensitive, and `PreferencesPasswordRequired` adds a password gate.

This is the mechanism behind "share a document with a customer by email", and it is also a data-leak vector when used carelessly.

## Attachments, and why not to use them

The legacy file model:

```
Attachment    ParentId → the record, Body → the bytes
Document      stored in folders, largely obsolete
Note          the legacy note object
```

**Attachments are superseded by Files** and should not be used in new work. Files give versioning, sharing to multiple records, Experience Cloud support, preview generation, and a better UI.

You will still meet Attachments in older orgs, and the migration path is a batch job creating ContentVersions from `Attachment.Body` and then deleting the originals. Worth doing when touching that area, not as a project on its own.

**One thing Attachments still do:** they can be private (`IsPrivate`), and their permission model is simpler. Rarely a reason to choose them.

## Storage

```
File storage   separate allocation from data storage
               counted per org, by edition and user count
Maximum file size  2 GB via the UI and API in most contexts
                   38 MB via a base64-encoded API insert
```

**File storage is separate from data storage**, which surprises people watching one and not the other.

**Versions consume storage.** A file with ten versions consumes ten times the space, which makes version retention a real cost on high-volume attachment processes.

**Deleting a ContentDocument deletes every version**, and it goes to the recycle bin first. `Database.emptyRecycleBin` frees the storage immediately. See [[10.4 - Delete, Undelete and the Recycle Bin]].

## Finding orphaned files

A recurring cleanup task, since files without links accumulate:

```sql
SELECT Id, Title, ContentSize, CreatedDate, CreatedBy.Name
FROM ContentDocument
WHERE Id NOT IN (SELECT ContentDocumentId FROM ContentDocumentLink WHERE LinkedEntityId != null)
```

In practice every file has at least one link — to its owner — so the useful query filters for documents linked only to a user and to no record:

```java
// Files whose only link is the owner's, meaning they are attached to no record
Map<Id, Integer> linkCountByDocument = new Map<Id, Integer>();
for (AggregateResult ar : [
    SELECT ContentDocumentId docId, COUNT(Id) linkCount
    FROM ContentDocumentLink
    WHERE ContentDocumentId IN :documentIds
    GROUP BY ContentDocumentId
]) {
    linkCountByDocument.put((Id) ar.get('docId'), (Integer) ar.get('linkCount'));
}
```

## Triggers on files

`ContentVersion` and `ContentDocumentLink` support triggers, which is how file-related automation is built.

```java
trigger ContentVersionTrigger on ContentVersion (after insert) {
    ContentVersionTriggerHandler.run();
}
```

```java
public with sharing class ContentVersionTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isInsert) {
            // the link does not exist yet at this point, so parent context must be
            // derived from FirstPublishLocationId
            ClaimEvidenceService.classifyUploads(Trigger.new);
        }
    }
}
```

**`FirstPublishLocationId`** on ContentVersion holds the record it was uploaded to, and it is the only parent reference available in the insert trigger — the `ContentDocumentLink` is created afterwards.

Useful uses: virus-scan callouts, classifying documents by name, enforcing a file-type policy, and updating a checkbox on the parent when evidence is attached.

## Practical guidance

**Insert a ContentVersion, then re-query for the ContentDocumentId**, then create the link.

**Set `PathOnClient` with the extension** — it determines the file type.

**Use `ShareType = 'I'`** so access follows the record.

**Set `Visibility` deliberately**, particularly where Experience Cloud users are involved.

**Filter `ContentDocumentLink` queries** on `LinkedEntityId` or `ContentDocumentId`; they cannot be scanned.

**Do not select `VersionData`** unless you need the bytes — it is heap.

**Use `lightning-file-upload`** rather than building a custom uploader.

**Download through the shepherd servlet path**, not by constructing a data URI.

**Set an expiry on every ContentDistribution.**

**Use Files, not Attachments**, in new work.
