# The Cascade, Specificity and Inheritance

Three separate mechanisms decide the final value of every CSS property. Most "why isn't my CSS applying" confusion comes from conflating them.

## The order of resolution

For a given element and property, the browser resolves in this order:

1. **Origin and importance** — where the rule came from and whether it is `!important`
2. **Layer** — `@layer` ordering
3. **Specificity** — how precisely the selector targets the element
4. **Source order** — later wins among equals

If no rule matches, the value comes from **inheritance** or the property's **initial value**.

## Origin and importance

From lowest to highest priority:

```
user-agent styles
user-agent !important                    <- (reversed at the top)
author styles (your CSS)
user styles
author !important
user !important
transitions and animations
```

Note the inversion: `!important` reverses the normal order, which is why a user's `!important` stylesheet can override yours. That is deliberate — it exists so users can force high-contrast or larger text.

Inline `style` attributes sit above normal author rules but below author `!important`.

## Specificity

Counted as three numbers `(A, B, C)`, compared left to right:

| Component | Counts |
| --- | --- |
| A | IDs |
| B | classes, attributes, pseudo-classes |
| C | elements, pseudo-elements |

```css
#header                          /* 1,0,0 */
.nav .item                       /* 0,2,0 */
.nav a:hover                     /* 0,2,1 */
a                                /* 0,0,1 */
[data-state="open"]              /* 0,1,0 */
#header .nav a                   /* 1,1,1 */
```

Crucially, **it does not carry**. Eleven classes `(0,11,0)` still lose to one ID `(1,0,0)`. Specificity is compared component-wise, not as a base-10 number.

Zero-specificity items: the universal selector `*`, combinators (`>`, `+`, `~`, space), and `:where()`.

Special cases worth knowing:

```css
:where(.a, .b)      /* 0,0,0 — always zero, whatever is inside */
:is(.a, #b)         /* takes the HIGHEST specificity of its arguments: 1,0,0 */
:not(.a)            /* same rule as :is — takes the argument's specificity */
:has(.child)        /* same rule as :is */
```

`:where()` is genuinely useful for library and reset styles: it lets you write a selector that is trivially overridable by consumers.

```css
:where(button, input) { font: inherit; }   /* any author rule beats this */
```

## Layers

`@layer` inserts a priority tier *below* specificity, which is the cleanest solution to specificity wars:

```css
@layer reset, base, components, utilities;

@layer components {
  #specific-thing { color: blue; }   /* high specificity */
}

@layer utilities {
  .text-red { color: red; }          /* low specificity, but LATER layer wins */
}
```

The layer order declared first is authoritative. Any rule in a later layer beats any rule in an earlier one regardless of specificity. Unlayered styles have the highest priority of all.

This is how a design system can ship components that utility classes can override without `!important` — the pattern Tailwind and modern CSS frameworks now use ([[11.5 - CSS Architecture]]).

## Inheritance

Some properties inherit from parent to child by default; most do not.

**Inherited:** `color`, `font-*`, `line-height`, `letter-spacing`, `text-align`, `text-transform`, `visibility`, `cursor`, `list-style`, `white-space`, `direction`.

**Not inherited:** everything box-related — `margin`, `padding`, `border`, `background`, `width`, `height`, `display`, `position`, `overflow`.

The rough rule: typography inherits, layout does not.

Explicit control:

```css
.child {
  color: inherit;   /* take the parent's computed value */
  color: initial;   /* the property's spec-defined default */
  color: unset;     /* inherit if inheritable, else initial */
  color: revert;    /* back to the user-agent / previous origin value */
  all: unset;       /* apply unset to every property */
}
```

`revert` is the useful one for undoing a reset without knowing the original value.

Note that form controls do **not** inherit fonts by default — the browser applies its own. Hence the near-universal reset:

```css
button, input, select, textarea { font: inherit; }
```

## Custom properties are inherited

```css
:root { --brand: #0b5; }
.card { --brand: #b50; }     /* overrides for this subtree */
.card .button { color: var(--brand); }   /* #b50 */
```

Custom properties inherit like `color`, which is what makes component-scoped theming work without any preprocessing ([[10.4 - Units Custom Properties and Theming]]).

They resolve at computed-value time, so a custom property set on an ancestor cascades down and can be changed at any depth — including from JavaScript.

## Why !important is a trap

```css
.button { color: red !important; }
```

It works, and then the next person needs to override it and must also use `!important`, at which point specificity decides between two `!important` rules and you have recreated the original problem one level up.

Legitimate uses: overriding third-party styles you cannot edit, and utility classes in a framework that must always win. Everything else is a specificity problem with a better solution — usually `@layer` or a lower-specificity architecture.

## Debugging

In DevTools' Styles pane, rules are listed in cascade order with losing declarations struck through. Hovering a struck-through property shows why it lost. The Computed pane shows the winning value and, expanded, the full chain of rules that were considered.

Two frequent non-cascade explanations for "my CSS isn't working":

- The property does not apply to that element's display type (`width` on an inline element, `gap` outside flex/grid).
- The value is invalid, so the whole declaration is discarded silently. DevTools shows a warning icon.

## How senior engineers actually use this

**They keep specificity flat and low.** A codebase where nearly every rule is `(0,1,0)` — a single class — is trivially predictable. This is the core insight behind BEM, CSS Modules and utility CSS alike.

**They use `@layer` to separate reset, base, components and utilities** rather than fighting with selector weight.

**They use `:where()` for defaults** that consumers should be able to override without thought.

**They avoid IDs in selectors entirely.** An ID's specificity is high enough to make later overrides painful, and IDs are better reserved for anchors and `for`/`aria-describedby` references.

## Common pitfalls

- Assuming specificity carries, so many classes beat an ID.
- `:is()` and `:not()` silently raising specificity to their highest argument.
- `!important` chains.
- Expecting `padding` or `background` to inherit.
- Form controls not inheriting fonts.
- An invalid value discarding the declaration with no visible error.
- Unlayered styles unexpectedly beating layered ones.

## Interview angle

"How does CSS specificity work" is standard. Give the three-component model, stress that it does not carry across components, and list the zero-specificity selectors. Then extend beyond the memorized answer: origin and importance sit above specificity, `@layer` sits between them, and `:where()`/`:is()` change the calculation. Mentioning that flat specificity is the actual design goal — not winning specificity battles — is what separates a practitioner's answer.
