# Schema Registry and Compatibility

#backend #streaming #contracts

> **In one line:** Events outlive the code that wrote them, so a producer and a consumer are almost never on the same schema version — and a registry is what turns that from a hope into a checked contract.

---

## The Idea

```
Producer v2 writes:  {"id": "doc_42", "title": "Q3", "index_version": "v3"}
Consumer v1 reads:   expects {"id", "title"}                    → fine
Consumer v3 reads:   expects {"id", "title", "chunk_count"}     → missing field
```

⚠️ **In a log with 30-day retention, a consumer replaying from 30 days ago reads records written by four deployments ago** ([[09.2 - Event Modeling]]). Every schema version that ever produced a retained record is live.

💡 **A schema registry gives you three things:** a canonical definition of each event's shape, a compatibility rule checked at publish time, and a way for a consumer to decode a record written by a version it has never seen.

**Without one, schema evolution is a convention, and conventions are broken by whoever joins next.**

---

## Compatibility Modes

The vocabulary that makes this precise.

| Mode | Means | Allows |
|---|---|---|
| **BACKWARD** | A **new consumer** can read **old data** | Delete a field, add an optional field |
| **FORWARD** | An **old consumer** can read **new data** | Add a field, delete an optional field |
| **FULL** | Both | Add or delete optional fields only |
| **NONE** | No checking | Anything |
| `*_TRANSITIVE` | Checked against **all** previous versions, not just the last | |

⚠️ **The direction is confusing and the confusion causes real mistakes.** The mnemonic: **the mode names what the *new schema* can do relative to existing data.**

```
BACKWARD:  I can read backwards in time    → upgrade CONSUMERS first
FORWARD:   old readers can read forward    → upgrade PRODUCERS first
```

💡 **`BACKWARD` is the right default for event streams**, because it means you can deploy the new consumer, let it read the backlog written by the old producer, and then upgrade the producer. **That ordering matches how you actually deploy.**

⚠️ **Use the `_TRANSITIVE` variants.** Plain `BACKWARD` only checks against the immediately previous version, so a chain of individually-compatible changes can produce a schema that cannot read a record from five versions ago — which is exactly the record you meet during a replay.

---

## What Each Change Costs

With Avro, and the same logic applies to Protobuf and JSON Schema.

```json
{
  "type": "record",
  "name": "DocumentIndexed",
  "fields": [
    {"name": "document_id", "type": "string"},
    {"name": "org_id", "type": "string"},
    {"name": "chunk_count", "type": "int"},
    {"name": "index_version", "type": ["null", "string"], "default": null}
  ]
}
```

| Change | BACKWARD | FORWARD |
|---|---|---|
| **Add a field with a default** | ✅ | ✅ |
| Add a field without a default | ❌ | ✅ |
| **Remove a field with a default** | ✅ | ✅ |
| Remove a field without a default | ✅ | ❌ |
| Rename a field | ❌ | ❌ |
| Change a type | ❌ | ❌ |
| Widen a type (`int` → `long`) | ✅ | ❌ |
| **Add an enum value** | ❌ | ✅ |
| Add an enum value **with a default** | ✅ | ✅ |

💡 **The rule that covers almost everything: always give new fields a default.** A field with a default can be added and removed freely under both modes, which means your schema can evolve in either direction without coordination.

⚠️ **`"type": ["null", "string"], "default": null` is the Avro idiom for an optional field**, and the `default` is what makes it compatible — a nullable union without a default is not.

### Enums are the trap

```json
{"type": "enum", "name": "Status", "symbols": ["PENDING", "INDEXED", "FAILED"]}
```

⚠️ **Adding `ARCHIVED` breaks BACKWARD compatibility** — an old consumer reading a record with the new symbol cannot decode it.

```json
{
  "type": "enum", "name": "Status",
  "symbols": ["PENDING", "INDEXED", "FAILED", "ARCHIVED"],
  "default": "UNKNOWN"
}
```

**With a default, an unrecognised symbol decodes as `UNKNOWN`** rather than failing.

💡 **This is the same problem as adding an enum value to a REST API** ([[05.13 - Contract Testing and Schema Evolution]]), and the fix is the same in spirit: consumers must handle values they do not recognise. **The registry makes it enforceable.**

## Avro, Protobuf or JSON Schema

| | Avro | Protobuf | JSON Schema |
|---|---|---|---|
| Encoding | **Binary, compact** | Binary, compact | Text |
| Schema needed to decode | **Yes** — writer's schema | No — field numbers | No |
| Compatibility rules | Mature, well-defined | Mature | Weaker |
| Human-readable on the wire | No | No | **Yes** |
| Field identity | **By name** | **By number** | By name |
| Ecosystem | Kafka-native | Broad | Broad |

💡 **Avro's distinguishing feature is that the writer's schema is needed to decode**, which is why the registry is not optional — every record carries a schema ID and the consumer fetches the definition. **That is what makes reading a record from five versions ago possible.**

⚠️ **Protobuf identifies fields by number, so renaming is free on the wire and breaks every generated client** ([[05.13 - Contract Testing and Schema Evolution]]). Avro identifies by name, so renaming breaks the wire format too — which is arguably safer, because it fails loudly.

**JSON Schema is the pragmatic choice when human-readability matters more than size.** For debugging an event stream by eye, being able to read the topic with `kafka-console-consumer` is genuinely valuable.

### The wire format

```
[magic byte: 0][schema id: 4 bytes][avro payload]
```

💡 **The schema ID is five bytes of overhead per record**, and it is what lets a consumer fetch the exact schema the producer used. Without it, a consumer would have to guess.

⚠️ **This means the registry is on the critical path for deserialisation.** Consumers cache schemas by ID, so a registry outage does not stop existing consumers — but a new schema ID they have not seen will fail until the registry returns.

## Using It

```python
from confluent_kafka.schema_registry import SchemaRegistryClient
from confluent_kafka.schema_registry.avro import AvroSerializer

registry = SchemaRegistryClient({"url": "http://schema-registry:8081"})

serializer = AvroSerializer(registry, DOCUMENT_INDEXED_SCHEMA,
                           to_dict=lambda obj, ctx: obj.model_dump())
```

```python
deserializer = AvroDeserializer(registry, DOCUMENT_INDEXED_SCHEMA)
# ← the consumer's schema. The writer's is fetched by ID and reconciled
```

💡 **Avro resolves the writer's schema against the reader's schema at decode time** — filling in defaults for fields the reader expects and the writer did not have, and dropping fields the writer had and the reader does not want. **That reconciliation is the whole point**, and it is what makes a consumer able to read four years of history.

### Subject naming

```
documents-value        ← TopicNameStrategy (default)
DocumentIndexed        ← RecordNameStrategy
documents-DocumentIndexed  ← TopicRecordNameStrategy
```

⚠️ **`TopicNameStrategy` means one schema per topic**, so a topic carrying multiple event types cannot be registered.

💡 **Use `TopicRecordNameStrategy` if a topic carries several event types** — a `documents` topic with `DocumentCreated`, `DocumentIndexed` and `DocumentArchived`. **Decide this before you have data**, because changing it means re-registering everything.

## In Production

### CI enforcement

```bash
# Check compatibility before merging
curl -X POST http://schema-registry:8081/compatibility/subjects/documents-value/versions/latest \
     -H "Content-Type: application/vnd.schemaregistry.v1+json" \
     -d @schema.json
```

```yaml
# In CI
- name: Check schema compatibility
  run: schema-registry-check --subject documents-value --schema schemas/document_indexed.avsc
```

💡 **The point of a registry is that it fails the build, not the deploy.** A compatibility check in CI turns "we hope nobody breaks this" into a compiler error.

⚠️ **Check against the *deployed* schema version**, not the one in `main`. Otherwise you validate against a state that does not exist in production ([[05.13 - Contract Testing and Schema Evolution]]).

### Setting the mode per subject

```bash
curl -X PUT http://schema-registry:8081/config/documents-value \
     -d '{"compatibility": "BACKWARD_TRANSITIVE"}'
```

| Subject type | Mode |
|---|---|
| Public event, many consumers | **`FULL_TRANSITIVE`** |
| Internal event, one team | `BACKWARD_TRANSITIVE` |
| CDC topic | `BACKWARD_TRANSITIVE` |
| Compacted topic (state) | **`FULL_TRANSITIVE`** — records live forever |
| Short-retention telemetry | `BACKWARD` |

💡 **A compacted topic needs `FULL_TRANSITIVE`** because records are retained indefinitely — a consumer reading from offset 0 encounters the oldest schema version that ever existed ([[09.1 - Queue vs Log]]).

### When you must break compatibility

```
1. Create a NEW topic with the new schema
2. Producer writes to both
3. Migrate consumers one at a time
4. Stop writing to the old topic
5. Delete after retention expires
```

⚠️ **You cannot force a breaking change on a topic with retained data**, because the old records still exist and consumers will read them.

💡 **A new topic is the migration path**, and it is expand/contract applied to streams ([[06.11 - Zero Downtime Migrations]]). The dual-write period is the expand phase.

**Version in the topic name** if breaking changes are expected: `documents.v1`, `documents.v2`.

### Upcasting in consumers

Even with a registry, a consumer often wants one internal shape.

```python
def to_current(record: dict, schema_version: int) -> DocumentIndexed:
    if schema_version < 2:
        record["index_version"] = "v1"          # default for old records
    if schema_version < 3:
        record["chunk_count"] = record.pop("chunks", 0)
    return DocumentIndexed(**record)
```

💡 **Upcast at the boundary so the rest of the handler knows one shape.** The upcast functions are permanent, small, and they are what makes replay across years of history possible ([[09.2 - Event Modeling]]).

### Monitoring

```python
schema_registry_requests_total.labels(result=...).inc()
schema_cache_misses_total.inc()
deserialisation_failures_total.labels(topic=t, reason=...).inc()
unknown_enum_values_total.labels(field=f, value=v).inc()
```

⚠️ **`deserialisation_failures_total` rising means a producer shipped an incompatible schema**, and it should page someone — those records are not being processed and the lag is growing silently.

💡 **`unknown_enum_values_total` is the early warning for the enum problem.** A consumer decoding `UNKNOWN` is working, and it is also telling you it does not understand something new.

### Without a registry

⚠️ **If you are not running one, you still need the discipline** — just unenforced.

```python
# Minimum viable: version in the envelope, upcast on read
{"type": "document.indexed", "version": 2, "data": {...}}
```

| Compensating control | |
|---|---|
| Version field in every event | So consumers can branch |
| Schema definitions in a shared repository | Even if not enforced |
| **CI check diffing schema files** | Catch breaking changes at review |
| Consumers tolerant of unknown fields | Never fail on an extra field |
| Consumers with defaults for missing fields | Never fail on an absent one |

💡 **For Conduit at phase 5, a registry may be disproportionate** — one team, a handful of event types, JSON payloads. **The version field plus a CI schema diff gives most of the benefit** ([[05.13 - Contract Testing and Schema Evolution]]).

**Write down the trigger: a second team consuming your events is when the registry earns its operational cost.**

## Codebase

**Repo:** `confluentinc/schema-registry`, `apache/avro`

**Question to answer:** How does Avro resolve a writer's schema against a reader's schema — what happens field by field? Then: how does the registry decide whether a new schema is compatible, and what does `_TRANSITIVE` change?

**Read, in order:**

1. `avro/lang/java/avro/src/main/java/org/apache/avro/io/parsing/ResolvingGrammarGenerator.java` — **schema resolution.** How reader and writer schemas are reconciled field by field. **The answer to the first question**, and it explains exactly why defaults matter
2. `avro/lang/java/avro/src/main/java/org/apache/avro/SchemaCompatibility.java` — **the compatibility algorithm itself.** Readable, and it is the source of truth for the table in this note
3. `schema-registry/core/src/main/java/io/confluent/kafka/schemaregistry/CompatibilityLevel.java` and `AvroCompatibilityChecker` — **how modes map onto the checker.** `_TRANSITIVE` checks against every previous version rather than just the latest
4. `schema-registry/client/src/main/java/io/confluent/kafka/schemaregistry/client/CachedSchemaRegistryClient.java` — **the client-side cache.** Why a registry outage does not stop existing consumers
5. `confluentinc/confluent-kafka-python` — `schema_registry/avro.py`, the Python serialiser and the wire format

💡 `SchemaCompatibility.java` is worth reading directly, because **it is the authoritative answer to "is this change safe" and it is more precise than any table.** When a compatibility check fails for a reason you did not expect, this file explains why.

**Size:** 1 session.

**Part 1 — The compatibility matrix, verified.** Register a base schema, then attempt each of the nine changes from the table under each of the four modes.

**Thirty-six cells.** Record accepted or rejected, and compare against the table.

**Any disagreement means your understanding is wrong**, and finding out here rather than in production is the point.

**Part 2 — Transitive matters.** Under plain `BACKWARD`, make a chain of three individually-compatible changes.

Then attempt to read a record written with version 1 using version 4's schema. **Confirm it fails.**

Then repeat under `BACKWARD_TRANSITIVE` and confirm the third change is rejected at registration.

**This is the argument for `_TRANSITIVE` and it is not obvious until you produce it.**

**Part 3 — Schema resolution, observed.** Write 1,000 records with schema v1. Deploy a consumer with schema v3, which adds two fields with defaults and removes one.

**Confirm the consumer reads all 1,000**, with defaults filled in for the new fields.

Then remove a `default` from one of the new fields and **confirm decoding now fails.** Record the exact error.

**Part 4 — The enum trap.** A `Status` enum consumed by a running consumer.

Add a symbol without a default. **Confirm the producer is rejected under `BACKWARD`.**

Then set the mode to `FORWARD`, produce records with the new symbol, and **confirm the old consumer fails to decode.**

Then add a default and confirm both directions work, with the unknown value decoding as the default.

**Instrument `unknown_enum_values_total`** and confirm it fires.

**Part 5 — A genuinely breaking change.** Change `chunk_count` from `int` to a nested `ChunkStats` record.

**Confirm the registry rejects it in every mode.**

Then execute the new-topic migration: dual-write, migrate one consumer, then the other, stop the old write, and verify no records were lost during the transition.

**Measure the dual-write period cost** — duplicated storage and producer overhead.

**Part 6 — Three formats.** The same event in Avro, Protobuf and JSON Schema.

Compare: encoded size, serialisation and deserialisation time, compatibility checking quality, and **readability with `kafka-console-consumer`.**

Then make the same breaking change in each and compare what happens — Protobuf renames pass on the wire and break clients, Avro renames fail outright.

**Part 7 — Without a registry.** Implement the version-envelope approach with upcasting.

Then a CI check that diffs schema files and blocks breaking changes, using the same rules as the registry.

Test it against ten changes, five safe and five breaking. **Confirm it matches the registry's verdict in all ten.**

Then write the ADR for Conduit: registry or not, with the trigger for reconsidering.

**Done when:**
- Your 36-cell matrix matches the table, or you understand why not
- You produced a transitively-incompatible chain and `_TRANSITIVE` caught it
- A missing default demonstrably breaks resolution, with the exact error recorded
- The enum trap is reproduced in both directions and fixed with a default
- The new-topic migration completed with zero lost records
- You know which format lets you read the topic by eye
- Your CI diff matches the registry's verdict on ten changes
