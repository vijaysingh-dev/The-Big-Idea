# Tree Shaking

Tree shaking is dead-code elimination across module boundaries: the bundler determines which exports are actually reachable from the entry point and drops the rest.

```js
// utils.js
export function used() {}
export function unused() {}

// main.js
import { used } from "./utils";
// unused() is not in the output
```

The name comes from shaking a dependency tree and letting the dead leaves fall.

## Why it needs ES modules

```js
// ESM — static, analyzable at build time
import { debounce } from "lodash-es";

// CommonJS — dynamic, resolved at runtime
const _ = require("lodash");
const fn = condition ? _.debounce : _.throttle;
```

ES module imports and exports are **statically determinable** — the bundler knows the full graph without executing anything. `require()` is a function call whose argument could be computed, so the bundler must assume the whole module is needed ([[08.1 - ES Modules vs CommonJS]]).

This is the single most important practical consequence: **a CommonJS-only dependency cannot be tree shaken**. Check whether a package ships an ESM build before assuming your import is doing what you think.

## Side effects are the hard part

```js
// analytics.js
console.log("loaded");                    // runs on import
window.analytics = createTracker();        // runs on import

export function track() {}
```

Removing this module changes behavior, so the bundler cannot safely drop it even if `track` is unused. Since the bundler cannot prove a module is pure, it assumes it is not — unless told otherwise.

```json
// package.json
{ "sideEffects": false }
```

This declares "no module in this package has import-time side effects, so unused exports may be removed freely."

If some files do:

```json
{ "sideEffects": ["*.css", "./src/polyfills.js"] }
```

CSS imports are the near-universal exception — `import "./styles.css"` has no exports and exists purely for its effect. A `"sideEffects": false` that forgets CSS causes styles to silently vanish from production builds, which is a memorable bug.

**For library authors this field is not optional.** Omitting it means every consumer bundles your entire package regardless of what they import ([[27.1 - npm and package.json]]).

## Import patterns that break it

```js
import _ from "lodash";                    // ~70KB — the whole library
import { debounce } from "lodash";         // still ~70KB — lodash is CJS
import debounce from "lodash/debounce";    // ~2KB
import { debounce } from "lodash-es";      // ~2KB — ESM build, tree shakes
```

The second line is the trap: it *looks* like a named import that should tree shake, but `lodash` ships CommonJS, so the bundler includes everything.

```js
import * as Icons from "react-icons";      // hundreds of KB
import { FiSearch } from "react-icons/fi"; // one icon
```

Namespace imports (`import * as`) generally defeat tree shaking, because the bundler must assume any property could be accessed dynamically.

These two patterns account for most unexpectedly large frontend bundles ([[19.7 - Bundle Analysis and Optimization]]).

## Barrel files

```js
// components/index.ts
export * from "./Button";
export * from "./Modal";
export * from "./DataGrid";       // heavy — pulls in a charting library
```

```js
import { Button } from "@/components";     // may pull in DataGrid too
```

Whether this tree shakes depends on whether the bundler can prove every re-exported module is side-effect-free. With `"sideEffects": false` and pure modules it usually works; with any impure module in the barrel it often does not.

Barrels also hurt build performance — importing one name forces the bundler to resolve and analyze every module in the barrel, which on a large component library measurably slows both builds and IDE responsiveness.

For internal libraries, deep imports are safer and faster:

```js
import { Button } from "@/components/Button";
```

## Things that block elimination

```js
// Class methods — bundlers cannot prove a method is unused
class Utils {
  static used() {}
  static unused() {}      // retained
}

// Prototype assignment
MyClass.prototype.method = function () {};    // retained

// Dynamic property access
const method = obj[computedName];              // forces retention

// Anything reassigning module scope
export let counter = 0;
export function increment() { counter++; }     // mutable binding, retained
```

Standalone exported functions shake reliably. Classes, prototypes and dynamic access do not — which is a real argument for preferring plain functions in shared utility modules.

## PURE annotations

```js
export const instance = /*#__PURE__*/ createExpensiveThing();
```

The comment tells the bundler this call has no side effects, so if `instance` is unused the whole call can be removed. Without it, a top-level function call is assumed impure and retained.

Build tools insert these automatically in many cases, and library authors add them manually around factory calls. Worth recognizing in compiled output.

## Verifying it worked

Assumptions here are frequently wrong. Measure:

```bash
npx vite build && npx vite-bundle-visualizer
npx source-map-explorer dist/assets/*.js
```

The treemap shows what actually landed in the bundle. A dependency you believed was tree shaken appearing at full size is the common discovery.

Chrome DevTools' **Coverage** panel shows how much of each file executed. High unused percentages point at code that should be split or removed — though a component library will always show high unused figures on any single route ([[19.7 - Bundle Analysis and Optimization]]).

## Production only

Tree shaking runs during production builds, not in development. `vite build` shakes; `vite dev` does not.

This means bundle-size problems are invisible during development and only appear in a production build. Checking bundle output before shipping, or enforcing a size budget in CI, is what catches regressions early:

```json
{
  "size-limit": [{ "path": "dist/assets/index-*.js", "limit": "150 kB" }]
}
```

## What it does not do

Tree shaking removes **unused exports**. It does not:

- Remove code inside a function that is called
- Split code by route — that is code splitting ([[19.3 - Code Splitting and React.lazy]])
- Help with CommonJS dependencies
- Remove unused CSS — that needs PurgeCSS or a utility framework's own scanning

Tree shaking and code splitting are complementary: shaking removes what is never used, splitting defers what is not needed yet.

## How senior engineers actually use this

**They check whether a dependency ships ESM** before adding it, using bundlephobia or the package's `exports` field.

**They use deep or per-module imports** for lodash, date libraries and icon sets.

**They avoid namespace imports** in application code.

**They set `sideEffects` correctly** in every package they publish, including the CSS exception.

**They verify with a bundle analyzer** rather than trusting that tree shaking happened.

## Common pitfalls

- `import { x } from "lodash"` believing it tree shakes — it does not.
- Namespace imports from icon and utility libraries.
- `"sideEffects": false` without listing CSS, silently dropping styles.
- Barrel files pulling in heavy unrelated modules.
- Expecting class methods or prototype assignments to be eliminated.
- Testing bundle size in development, where shaking does not run.
- Assuming tree shaking replaces code splitting.

## Interview angle

"What is tree shaking and what does it require" wants: dead-code elimination of unused exports, requiring statically analyzable ES module syntax and accurate `sideEffects` metadata, because a module with import-time side effects cannot be safely removed. The practical follow-up worth volunteering is the lodash example — a named import from a CommonJS package looks tree-shakeable and is not — and that library authors who omit `sideEffects` force every consumer to bundle the whole package.
