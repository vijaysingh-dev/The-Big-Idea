# Collections - Lists, Sets and Maps

## Why this note matters more than its position suggests

Collections are the core of every bulkified pattern on the platform. The difference between code that works at 200 records and code that fails is almost always a collection used correctly or incorrectly.

Three types, each solving a different problem:

**List** — ordered, allows duplicates, indexed access.
**Set** — unordered, no duplicates, fast membership testing.
**Map** — key-value pairs, fast lookup by key.

## List

```java
List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
claims.add(claim);
claims.addAll(otherClaims);

claims.get(0);
claims[0];                    // equivalent
claims.set(0, newClaim);
claims.remove(0);             // by index, returns the removed element
claims.size();
claims.isEmpty();
claims.clear();
claims.contains(claim);       // O(n) — use a Set if you do this often
claims.indexOf(claim);
claims.sort();                // natural order, or Comparable
```

`List` is what DML operates on and what SOQL returns. Every DML statement takes a list.

**`remove(index)` takes an index, not an element.** Removing by value requires finding the index first, and removing inside a loop shifts subsequent indexes — a classic off-by-one source. Build a new list instead.

```java
// Wrong: indexes shift as elements are removed
for (Integer i = 0; i < claims.size(); i++) {
    if (claims[i].Status__c == 'Closed') {
        claims.remove(i);
    }
}

// Correct: build the list you want
List<Warranty_Claim__c> open = new List<Warranty_Claim__c>();
for (Warranty_Claim__c claim : claims) {
    if (claim.Status__c != 'Closed') {
        open.add(claim);
    }
}
```

## Set

```java
Set<Id> assetIds = new Set<Id>();
assetIds.add(assetId);              // returns true if it was not already present
assetIds.addAll(otherIds);
assetIds.contains(assetId);         // O(1)
assetIds.remove(assetId);
assetIds.removeAll(otherIds);
assetIds.retainAll(otherIds);       // intersection
assetIds.size();
```

Three properties make `Set` the collection of choice for collecting IDs:

**Automatic deduplication.** Fifty claims on one asset produce one entry, so you query that asset once.

**`add()` returns a boolean** indicating whether the value was new. This is the standard way to detect a duplicate without a separate check, and it is what makes cycle detection work in hierarchy traversal ([[02.9 - Hierarchical and Self Relationships]]).

**Constant-time membership testing.** `contains()` on a Set is O(1); on a List it is O(n). Checking membership inside a loop against a List is a quiet O(n²) that appears as a CPU limit failure.

`removeAll` and `retainAll` do set difference and intersection, which is how the gap-analysis pattern in [[08.3 - Subqueries and Semi-Joins]] avoids a non-selective anti-join.

## Map

```java
Map<Id, Account> accountsById = new Map<Id, Account>();
accountsById.put(accountId, account);
accountsById.get(accountId);          // null if absent
accountsById.containsKey(accountId);
accountsById.remove(accountId);
accountsById.keySet();                // Set of keys
accountsById.values();                // List of values
accountsById.putAll(otherMap);
```

**Constructing a Map directly from a query** is the single most useful idiom in Apex:

```java
Map<Id, Account> accountsById = new Map<Id, Account>([
    SELECT Id, Name, Total_Revenue__c FROM Account WHERE Id IN :accountIds
]);
```

The map is keyed on `Id` automatically. This one construct removes most nested loops from Apex, and recognizing where it applies is a large part of writing performant code.

## The grouping pattern

Building a map from a key to a list of records appears constantly:

```java
Map<Id, List<Warranty_Claim__c>> claimsByAsset = new Map<Id, List<Warranty_Claim__c>>();

for (Warranty_Claim__c claim : claims) {
    if (!claimsByAsset.containsKey(claim.Asset__c)) {
        claimsByAsset.put(claim.Asset__c, new List<Warranty_Claim__c>());
    }
    claimsByAsset.get(claim.Asset__c).add(claim);
}
```

Worth extracting into a utility, since it appears in every codebase:

```java
public with sharing class CollectionUtils {

    public static Map<Id, List<SObject>> groupBy(List<SObject> records, String fieldName) {
        Map<Id, List<SObject>> grouped = new Map<Id, List<SObject>>();

        for (SObject record : records) {
            Id key = (Id) record.get(fieldName);
            if (key == null) {
                continue;
            }
            if (!grouped.containsKey(key)) {
                grouped.put(key, new List<SObject>());
            }
            grouped.get(key).add(record);
        }
        return grouped;
    }
}
```

## The nested loop trap

The most common CPU limit failure, and it contains no query at all — which is why it survives code review.

```java
// O(accounts × contacts)
for (Account acc : accounts) {
    for (Contact con : contacts) {
        if (con.AccountId == acc.Id) {
            acc.Primary_Contact_Email__c = con.Email;
        }
    }
}
```

Two hundred accounts and ten thousand contacts is two million iterations, and `Apex CPU time limit exceeded` with an error pointing nowhere useful.

The fix is always the same: build a map first, then loop once.

```java
Map<Id, Contact> contactByAccount = new Map<Id, Contact>();
for (Contact con : contacts) {
    if (!contactByAccount.containsKey(con.AccountId)) {
        contactByAccount.put(con.AccountId, con);
    }
}

for (Account acc : accounts) {
    Contact primary = contactByAccount.get(acc.Id);
    if (primary != null) {
        acc.Primary_Contact_Email__c = primary.Email;
    }
}
```

10,200 iterations instead of two million. **Any time two loops are nested over collections of records, a map is the answer.**

## Composite keys

Grouping by more than one field needs a composite key, since Apex has no tuple type:

```java
Map<String, List<Warranty_Claim__c>> claimsByAssetAndStatus =
    new Map<String, List<Warranty_Claim__c>>();

for (Warranty_Claim__c claim : claims) {
    // a delimiter unlikely to appear in the values keeps the key unambiguous
    String key = claim.Asset__c + '|' + claim.Status__c;
    if (!claimsByAssetAndStatus.containsKey(key)) {
        claimsByAssetAndStatus.put(key, new List<Warranty_Claim__c>());
    }
    claimsByAssetAndStatus.get(key).add(claim);
}
```

Choosing a delimiter that cannot appear in the values matters. Concatenating a status containing a pipe character produces silently wrong grouping.

## Sorting

```java
List<Decimal> amounts = new List<Decimal>{ 300, 100, 200 };
amounts.sort();  // natural order
```

sObject lists sort by the object's display field by default. Custom ordering requires a wrapper implementing `Comparable`:

```java
public class ClaimByAmount implements Comparable {
    public Warranty_Claim__c claim;

    public ClaimByAmount(Warranty_Claim__c claim) {
        this.claim = claim;
    }

    public Integer compareTo(Object other) {
        Decimal mine = claim.Claim_Amount__c ?? 0;
        Decimal theirs = ((ClaimByAmount) other).claim.Claim_Amount__c ?? 0;
        return mine > theirs ? -1 : (mine < theirs ? 1 : 0);
    }
}
```

Null handling in the comparator is not optional — comparing a null Decimal throws, and the failure appears as an obscure exception inside `sort()`.

Sorting in Apex costs CPU; sorting in SOQL costs nothing extra if the field is indexed. Prefer `ORDER BY` where the data is being queried anyway. See [[08.5 - LIMIT, OFFSET, ORDER BY and Pagination]].

## Collections of collections

```java
Map<Id, Map<String, List<Warranty_Claim__c>>> nested =
    new Map<Id, Map<String, List<Warranty_Claim__c>>>();
```

Legal and usually a signal that a small wrapper class would be clearer:

```java
public class AssetClaimSummary {
    public Id assetId;
    public Integer openCount;
    public Decimal totalValue;
    public List<Warranty_Claim__c> recentClaims;
}

Map<Id, AssetClaimSummary> summaryByAsset = new Map<Id, AssetClaimSummary>();
```

Named fields are easier to read and easier to change than three levels of generic nesting.

## Heap

Collections consume heap, capped at 6 MB synchronously and 12 MB asynchronously.

A list of 50,000 sObjects with many fields, including long text areas, will exhaust it before the row limit. The mitigations:

**Select fewer fields.** The largest single lever.

**Process in chunks** with a `for` loop over the query, which retrieves 200 at a time.

**Clear collections you have finished with**, though Apex garbage collection means this helps less than it would elsewhere.

**Move to Batch Apex**, where each chunk gets a fresh heap.

See [[16.3 - CPU Time and Heap Size]].

## Practical guidance

**Use `Set<Id>` to collect IDs.** Deduplication and O(1) membership come free.

**Construct maps directly from queries.**

**Never nest loops over record collections.** Build a map.

**Never call `List.contains()` inside a loop.** Use a Set.

**Null-guard comparators.**

**Choose delimiters carefully** in composite keys.

**Prefer a small wrapper class** to deeply nested generic collections.
