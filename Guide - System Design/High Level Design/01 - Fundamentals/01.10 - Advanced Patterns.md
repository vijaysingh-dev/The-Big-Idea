## Event-Driven Architecture (EDA)

### What It Is

Services communicate by **producing and consuming events** rather than direct calls. An event is a record of something that happened: `OrderPlaced`, `PaymentProcessed`, `InventoryReserved`.

```
[Order Service] ──event: OrderPlaced──→ [Event Bus]
                                              ├──→ [Payment Service]
                                              ├──→ [Inventory Service]
                                              └──→ [Notification Service]
```

### Why It Exists

In a synchronous call chain, a slow or failing downstream service blocks the upstream. EDA decouples producers from consumers entirely — the Order Service doesn't know or care who's listening.

### Properties

- **Temporal decoupling:** Producer and consumer don't need to be running at the same time
- **Loose coupling:** Services don't need to know each other's APIs
- **Fan-out is natural:** One event, many consumers
- **Audit trail:** Events are a natural log of what happened and when

### Tradeoffs

- Hard to reason about end-to-end flows (no single stack trace)
- Eventual consistency — consumers process at their own pace
- Event schema evolution is a versioning challenge
- Debugging requires distributed tracing

### Event Sourcing

A related pattern: instead of storing current state, store the *sequence of events* that produced it.

```
State = reduce(events, initial_state)

Events: [AccountOpened, MoneyDeposited(100), MoneyWithdrawn(30)]
State:  { balance: 70 }
```

Benefits: Full audit history, ability to replay, ability to derive new projections.  
Cost: Complex queries (must replay), storage grows indefinitely, schema migration is hard.

## CQRS (Command Query Responsibility Segregation)

### What It Is

**Separate the write model (Commands) from the read model (Queries).**  
Writes go to a normalized write store. Reads come from a denormalized read store optimized for queries.

```
Client ──Command──→ [Write Model (SQL, normalized)]
                          │
                      (events/sync)
                          ↓
                   [Read Model (denormalized, per query)]
Client ──Query──→ [Read Model]
```

### Why It Exists

Write and read access patterns often conflict:
- Writes need normalization, transactions, referential integrity
- Reads need denormalized, fast, pre-joined data

Putting both through the same model forces compromises.

### Example

E-commerce product page:
- **Write:** Product table (normalized: name, price, stock — each in its own table)
- **Read:** Pre-joined view with product name, category, images, reviews, seller info — all in one document in Elasticsearch or Redis

### Tradeoffs

- Eventual consistency between write and read models (read model lags write model)
- Operational complexity — two models to maintain and keep in sync
- Much faster reads (read model is purpose-built)
- Much simpler reads (no joins)

### When to Use

- Read:write ratio is heavily skewed toward reads
- Read query patterns are very different from the write data shape
- High performance reads are critical (product pages, dashboards)
- Often combined with event sourcing

## SAGA Pattern

### What It Is

A pattern for managing **long-running distributed transactions** across multiple services, where you can't use a single ACID transaction.

Instead of one atomic transaction, a SAGA is a sequence of local transactions, each publishing an event or calling the next service. If a step fails, **compensating transactions** undo the previous steps.

### Two Approaches

**Choreography (event-based):**
Each service listens for events and decides what to do next.

```
Order Service: emit OrderCreated
  → Payment Service: hears OrderCreated → process payment → emit PaymentProcessed
    → Inventory Service: hears PaymentProcessed → reserve stock → emit StockReserved
      → Order Service: hears StockReserved → confirm order
```

If Payment fails:
```
Payment Service: emit PaymentFailed
  → Order Service: hears PaymentFailed → cancel order (compensating tx)
```

**Orchestration (central coordinator):**
One orchestrator service drives the flow, calling each participant and handling failures.

```
[Saga Orchestrator]
   → Call Payment Service → success
   → Call Inventory Service → failure → call Payment Service rollback
   → Emit OrderFailed
```

### Tradeoffs

| | Choreography | Orchestration |
|---|---|---|
| Coupling | Low (no central coordinator) | Higher (orchestrator knows all steps) |
| Visibility | Hard to see the whole flow | Easy to see the whole flow |
| Fault handling | Distributed, hard to debug | Centralized, easier to debug |
| New step added | Add new listener | Modify orchestrator |
| Best for | Simple flows | Complex flows |

### Compensating Transactions

Compensating transactions are not rollbacks — they are **new forward-moving operations** that undo the effect of a previous step.

Examples:
- Payment charged → Compensating: Refund
- Email sent → Compensating: Send cancellation email (you can't unsend)
- Record created → Compensating: Mark as cancelled (soft delete)

Not everything can be perfectly compensated. That's acceptable — design around it.

## Idempotency

### What It Is

An operation is idempotent if **calling it multiple times has the same effect as calling it once.**

```
Idempotent:     DELETE /user/42  (after first delete, more deletes do nothing)
Not idempotent: POST /charge     (each POST creates a new charge)
```

### Why It Matters

Networks are unreliable. Retries are necessary. Without idempotency, retries cause duplicate processing:
- Payment charged twice
- Email sent twice
- Order created twice

### How to Implement

**Idempotency keys:**  
Client generates a unique key per logical operation and sends it with every retry.

```
POST /charge
Headers: Idempotency-Key: a3f8b7c2-...

Server:
1. Check if key exists in idempotency store
2. If yes: return stored result (don't re-execute)
3. If no: execute, store result with key, return result
```

**Natural idempotency:**  
Some operations are naturally idempotent:
- `SET balance = 100` (idempotent — same result each time)
- `balance += 10` (NOT idempotent — cumulative each time)

**In message queues:**  
Consumers must be idempotent because message queues guarantee *at-least-once* delivery. A message may be delivered more than once.

### Idempotency in HTTP Methods (RFC)

| Method | Idempotent? | Safe? |
|---|---|---|
| GET | ✅ | ✅ |
| PUT | ✅ | ❌ |
| DELETE | ✅ | ❌ |
| POST | ❌ | ❌ |
| PATCH | ❌ | ❌ |

## Backpressure

### What It Is

A mechanism to prevent a fast producer from overwhelming a slow consumer.

```
Producer (1000 msg/s) → Consumer (100 msg/s)
Without backpressure: queue grows until OOM crash
With backpressure:    producer slows down or drops, or consumer signals "slow down"
```

### Why It Exists

In distributed systems, different components process at different speeds. Without backpressure, the system accumulates unbounded work until it collapses.

### Backpressure Strategies

1. **Blocking (sync):** Producer blocks when consumer buffer is full. Simple but causes head-of-line blocking.

2. **Buffering:** Accept messages into a buffer; when buffer is full, apply one of:
   - **Block producer** (bounded queue with blocking put)
   - **Drop oldest** (circular buffer)
   - **Drop newest** (reject new arrivals when full)
   - **Error to producer** (HTTP 429 Too Many Requests)

3. **Load shedding:** Deliberately drop requests when overloaded. Preferable to crashing.

4. **Rate limiting:** Upstream rate limiter prevents producers from exceeding consumer capacity.

5. **Reactive Streams (programmatic):** Consumer explicitly signals how many messages it can handle (`request(n)` protocol). Implemented in RxJava, Project Reactor.

### Backpressure in Kafka

Kafka doesn't push to consumers — consumers pull at their own rate. This is built-in backpressure: the consumer decides its processing rate, and the log accumulates messages it hasn't processed yet (up to retention period).

### Backpressure in HTTP

HTTP 429 (Too Many Requests) with `Retry-After` header is the web's backpressure mechanism.

## How These Patterns Combine in Practice

A payment flow in an e-commerce system uses all of these:

```
POST /checkout (sync to user)
  → Order Service creates order (idempotency key from frontend)
  → Emits OrderCreated event (event-driven)
  → SAGA Orchestrator picks up:
      1. PaymentService.charge() (idempotent with payment ID)
      2. InventoryService.reserve() (idempotent with order ID)
      3. If either fails → compensating transactions
  → Read model updated for order status page (CQRS)
  → Backpressure: if payment processor is slow, queue absorbs; workers slow down gracefully
```
