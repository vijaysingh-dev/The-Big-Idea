# Connection Reuse and Keep-Alive

#backend #http #performance

> **In one line:** Reusing a warm connection skips DNS, the TCP handshake, the TLS handshake and slow start — which is usually the single largest performance win available to a backend service, and it is a configuration change rather than a rewrite.

---

## The Idea

Every new HTTPS connection costs:

```
DNS lookup            0–20ms   (cached usually)
TCP handshake         1 RTT
TLS 1.3 handshake     1 RTT
TCP slow start        2–3 RTT to reach full speed
```

On a 50ms link that is roughly 100ms before your first byte, plus a throughput ramp. On a cross-region link at 150ms RTT it is 300ms+.

A reused connection costs **zero** of that. The request goes out immediately, at full window size.

💡 **Quantified: for a small API call over a 100ms link, a cold connection is roughly 220ms and a warm one is roughly 100ms.** You just made every call twice as fast by changing one line of client configuration. Nothing else in normal backend work has that ratio.

---

## How Keep-Alive Works

### HTTP/1.1: on by default

```
GET /a HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Length: 5

hello
                        ← connection stays open
GET /b HTTP/1.1         ← next request on the same connection
Host: api.example.com
```

To close:

```
Connection: close
```

⚠️ **Keep-alive requires exact framing.** The receiver must know precisely where one message ends so it can start parsing the next. If `Content-Length` is wrong by one byte, the next request is parsed from the wrong offset and everything breaks. This is the connection between [[03.1 - HTTP1.1 Message Format]] and this note — framing exists so that reuse is possible.

### Serialized, not concurrent

On one HTTP/1.1 connection, requests happen **one at a time**.

```
[req1 ──► resp1][req2 ──► resp2][req3 ──► resp3]
```

Concurrency needs multiple connections. This is application-level head-of-line blocking ([[02.5 - Head of Line Blocking]]), and it is why browsers open six connections per host and why HTTP client pools have both a total limit and a per-host limit.

### HTTP/2: concurrent on one connection

```
One connection, many interleaved streams
```

One warm HTTP/2 connection replaces six warm HTTP/1.1 ones. Much better — until a packet is lost, at which point every stream stalls together.

## The Client Side

This is where the win is, and where people lose it.

### The mistake

```python
# Creates a new pool, new connection, new TLS handshake — every single call
async def get_user(uid):
    async with httpx.AsyncClient() as client:
        return await client.get(f"https://users/{uid}")
```

Every call pays the full cold-start cost. It also leaks ephemeral ports into `TIME_WAIT` ([[02.3 - TCP Connection Lifecycle]]).

### The fix

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(
        limits=httpx.Limits(
            max_connections=100,
            max_keepalive_connections=20,
            keepalive_expiry=30.0,
        ),
        timeout=httpx.Timeout(connect=2, read=10, write=5, pool=3),
        http2=True,
    )
    yield
    await app.state.http.aclose()
```

One client, app lifetime. This is the whole change.

### The three limits

| Setting | Meaning |
|---|---|
| `max_connections` | Total concurrent connections across all hosts |
| `max_keepalive_connections` | How many stay open when idle |
| `keepalive_expiry` | How long an idle connection is kept |

⚠️ **`keepalive_expiry` must be shorter than every idle timeout in the path.** Your load balancer, your NAT gateway, and the server all have one. Whoever is shortest closes first, and if that is not you, your pool hands out a dead socket.

```
Server keep-alive timeout:   65s
NAT mapping timeout:         120s
ALB idle timeout:            60s      ← shortest
Your keepalive_expiry:       30s      ← must be under 60
```

💡 **This is the single most common cause of intermittent `Connection reset by peer` in production**, and it is worse at low traffic because that is when connections sit idle. See [[02.10 - NAT Firewalls and Middleboxes]].

## The Server Side

```bash
uvicorn app:app --timeout-keep-alive 5
```

```nginx
keepalive_timeout 65s;
keepalive_requests 1000;

upstream backend {
    server app:8000;
    keepalive 32;                 # connections nginx keeps open to your app
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

location / {
    proxy_pass http://backend;
    proxy_http_version 1.1;       # required — default is 1.0, which disables keep-alive
    proxy_set_header Connection "";  # required — clears the hop-by-hop header
}
```

⚠️ **Those last two lines are missed constantly.** nginx defaults to HTTP/1.0 toward upstreams, which means no keep-alive at all, which means a new connection to your app for every single request. You get all the connection churn you thought you had eliminated, and it is invisible unless you look.

Check it:

```bash
ss -tan state time-wait dst <app-ip> | wc -l    # high = churn
```

### The tradeoff on server-side timeout

| Timeout | Effect |
|---|---|
| Too short (1–2s) | Clients reconnect constantly, losing the benefit |
| Too long (300s) | Idle connections hold file descriptors and memory |
| 5–65s | The usual range |

An idle connection costs a file descriptor and a few KB of kernel buffers. At 100,000 idle connections that is real, but at typical scales the cost of *not* keeping them is higher.

## Where Connections Silently Die

A pooled connection can be dead without you knowing. There is no notification.

| Killer | Typical timeout |
|---|---|
| Server keep-alive | 5–65s |
| Load balancer idle | 60s (AWS ALB default) |
| NAT mapping | 30–900s |
| Stateful firewall | 60–3600s |
| Cloud NAT gateway | 350s (GCP) |
| The server restarting | Immediate |

The fix is always one of two things: **expire your connections before the shortest killer**, or **validate before use**.

```python
# SQLAlchemy: both approaches
engine = create_async_engine(
    dsn,
    pool_recycle=1800,      # expire proactively
    pool_pre_ping=True,     # validate before handing out
)
```

`pool_pre_ping` costs one round trip per checkout and eliminates an entire class of intermittent error. For most services that is an excellent trade.

## In Production

### The measurement that convinces people

```python
async def measure(reuse: bool, n: int = 100):
    if reuse:
        async with httpx.AsyncClient() as client:
            start = time.perf_counter()
            for _ in range(n):
                await client.get(url)
    else:
        start = time.perf_counter()
        for _ in range(n):
            async with httpx.AsyncClient() as client:
                await client.get(url)
    return (time.perf_counter() - start) / n
```

Run it against a service in another region. The ratio is typically 2–4×, sometimes more. **Take that number to whoever needs convincing** — it is far more persuasive than an explanation.

### Symptoms of no reuse

| Signal | Where to look |
|---|---|
| High `TIME_WAIT` count | `ss -tan state time-wait \| wc -l` |
| CPU spent in TLS handshakes | `py-spy record`, look for `ssl` frames |
| Latency much higher than server-reported processing time | Compare your client timing against the server's |
| Ephemeral port exhaustion | `Cannot assign requested address` |
| Every request shows a TLS handshake | `tcpdump` for ClientHello frequency |

The last one is the definitive test. **One ClientHello per request means zero reuse**, no matter what your configuration claims.

### The checklist

For every outbound dependency:

1. Is the client created once, at app startup?
2. Are `max_keepalive_connections` and `keepalive_expiry` set explicitly?
3. Is `keepalive_expiry` shorter than every idle timeout in the path?
4. Is HTTP/2 enabled where the server supports it?
5. Is there a proxy in between with `proxy_http_version 1.1`?
6. Do you have `pool_pre_ping` or equivalent for database connections?
7. Have you verified reuse with `tcpdump` rather than assumed it?

Item 7 is the one people skip, and it is the one that catches misconfiguration.

### When not to reuse

Reuse is not universally correct:

- **Behind a load balancer with sticky connections.** A long-lived connection pins you to one backend. When that backend is replaced, you keep hitting the replacement or a dead one. Periodic recycling spreads load and picks up new backends
- **gRPC through an L4 load balancer.** All streams pin to one backend, defeating load balancing entirely ([[02.5 - Head of Line Blocking]])
- **When the destination scales up.** Existing connections do not migrate to new instances. `keepalive_requests` and `pool_recycle` force periodic redistribution

💡 **The general principle: connection reuse trades load distribution for latency.** Long-lived connections are fast but sticky. That is fine for a database and a problem for a horizontally scaled service behind an L4 balancer. Recycling periodically is the compromise, and it is why `keepalive_requests 1000` exists.

💡 The interesting question to hold while reading httpcore: **what happens to a request that picks a dead connection?** Does it retry on a fresh one, or does it surface the error? The answer determines whether your service sees intermittent failures or transparently recovers, and it differs between libraries. Find out what yours does.

**Part 1 — The core number.** 100 requests, client created per request versus once. Measure at RTT 1ms, 20ms, 50ms, 150ms, 300ms using netem.

Chart the ratio against RTT. **The ratio should grow with latency**, because handshake cost is latency-bound while processing cost is not. That shape is the argument.

Then verify with `tcpdump`: count ClientHello packets in each run. 100 versus 1.

**Part 2 — Verify, do not assume.** Configure a client that *looks* correct but is not — for example, a client created once but with `max_keepalive_connections=0`. Show that the configuration reads fine and the traffic shows zero reuse.

Write down the three ways to verify reuse: `tcpdump` ClientHello count, `ss -tan state time-wait` on the client, and timing. **Never trust configuration alone** is the lesson.

**Part 3 — The connection death incident.** Toxiproxy between your client and server with a 10-second idle timeout. Client pool with 60-second `keepalive_expiry`.

Send one request every 30 seconds. Watch the intermittent failures. **Then send 100 requests per second and watch the problem vanish**, because connections never idle long enough. Document this inversion — it is what makes the bug hard to find.

Fix three ways and compare: shorten `keepalive_expiry`, add validation before use, and add retry-on-idempotent-failure. Note which fixes cost a round trip and which do not.

**Part 4 — The nginx trap.** App behind nginx. Configure the upstream block **without** `proxy_http_version 1.1` and `proxy_set_header Connection ""`.

Measure `TIME_WAIT` count between nginx and your app under load. It should be enormous. Then add the two lines and measure again.

**This is a two-line fix that people ship without for years.** Quantify what it was costing.

**Part 5 — Reuse versus load distribution.** Three backend instances behind a simple L4 load balancer. A client with long-lived pooled connections. Send 10,000 requests and count per backend.

Then add `keepalive_requests`-style recycling — close and reopen every N requests — and count again. Chart the distribution in both cases.

Then kill one backend mid-test and measure how long until the client stops sending to it in each configuration.

**Part 6 — HTTP/2 comparison.** Same workload over an HTTP/1.1 pool of 6 and one HTTP/2 connection. Measure at 0% and 1% packet loss.

HTTP/2 should win clearly on the clean link and lose on the lossy one. Connect the result back to [[02.5 - Head of Line Blocking]].

**Done when:**
- Your reuse-ratio-vs-RTT chart shows the ratio growing with latency
- You have `tcpdump` proof of reuse, not just configuration
- You reproduced the idle-timeout incident including the low-traffic inversion
- You have quantified the cost of the missing nginx directives
- Part 5 shows the reuse/distribution tradeoff with real distributions
- The HTTP/2 comparison shows the crossover under loss
