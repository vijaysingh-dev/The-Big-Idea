# Rapid Fire - React

## Fundamentals

**Why React instead of direct DOM manipulation?**
Imperative code needs a separate update path per state-view pair, so complexity grows with their product. Declarative rendering gives one path: `UI = f(state)`. Updates also stop being destructive of focus, scroll and input state. → [[16.1 - Why React]]

**Is the virtual DOM fast?**
No — hand-written optimal DOM updates are faster. The virtual DOM makes a *maintainable* approach fast enough by avoiding a full DOM rebuild. The value is the cheap constraint, not raw speed. → [[18.1 - Virtual DOM and React Elements]]

**What is JSX?**
A syntax extension compiled to function calls producing plain objects. Not HTML, not a template language, and not part of React itself. → [[16.2 - JSX]]

**Why does `{items.length && <List />}` render "0"?**
`&&` returns the falsy left operand, and React renders `0` while skipping `false`, `null` and `undefined`. Use `items.length > 0 &&`. → [[16.7 - Conditional Rendering and Composition]]

**Why must components be pure?**
The render phase is interruptible and may be discarded or repeated, so a side effect during render can happen zero, one or several times per commit — and cannot be undone. Purity is what makes concurrent rendering, Strict Mode checks and compiler memoization sound. → [[16.5 - Rendering and Purity]]

**Why does state not update immediately?**
State is a snapshot. The variable is a `const` from this render; `setState` schedules a new render with a new binding. Three `setCount(count + 1)` calls yield one increment — use the updater form `setCount(c => c + 1)`. → [[16.4 - State and useState Mental Model]]

**Why does mutating state not re-render?**
React compares with `Object.is`. An in-place mutation leaves the reference identical, so nothing changed as far as React can tell. → [[16.4 - State and useState Mental Model]]

**Controlled vs uncontrolled?**
Controlled means React state owns the value; uncontrolled means the DOM does and React reads it when needed. Controlled costs a re-render per keystroke, which is why large forms use uncontrolled libraries. → [[16.8 - Controlled vs Uncontrolled Components]]

## Keys and reconciliation

**Why are keys important?**
They give React element identity across renders, so it can match, move and preserve state instead of matching by position. → [[16.6 - Lists and Keys]]

**Why not use array indexes as keys?**
Index keys are equivalent to no keys — position is identity again. Delete an item from the middle and React reuses the component instance for that index, so local state, input values and checkbox state attach to the wrong items. → [[16.6 - Lists and Keys]]

**How does reconciliation work?**
Two heuristics make an O(n³) problem O(n): different element types replace the whole subtree, and keys identify children within a list. Outside keyed lists, position determines identity. → [[18.2 - Reconciliation and the Diffing Algorithm]]

**Why does defining a component inside another break things?**
It is a new function identity every render, so a new `type`, so React unmounts and remounts the entire subtree — losing state and DOM. It is the usual cause of "my input loses focus while typing". → [[16.3 - Components and Props]]

**How do you reset a component's state?**
Change its `key`. React treats it as a different component and mounts a fresh instance — cleaner than an effect that resets each field. → [[16.6 - Lists and Keys]]

## Hooks

**Why can't hooks be called conditionally?**
Hooks are stored positionally in a linked list on the fiber, matched by call order rather than by name. A changed order makes state attach to the wrong hook. → [[17.1 - Rules of Hooks and How They Work]]

**When does `useEffect` run?**
After the commit and after paint, asynchronously. Cleanup runs **before** the next effect, not after. Effects run child-first. → [[17.3 - useEffect and the Dependency Array]]

**`useEffect` vs `useLayoutEffect`?**
`useLayoutEffect` runs synchronously after DOM mutation and **before** paint, so a measure-then-adjust is invisible. `useEffect` runs after paint, so the same code produces a visible flash. Layout effects block the frame, so they need justification. → [[17.5 - useLayoutEffect vs useEffect]]

**When should you *not* use `useEffect`?**
Deriving state (compute during render), resetting state on prop change (use `key`), responding to user actions (use the handler), and chaining state transitions (do it in one handler or a reducer). If it is not synchronizing with something outside React, it probably should not exist. → [[17.4 - useEffect Pitfalls]]

**What is a stale closure?**
A callback that captured values from an earlier render — typically an effect with an empty dependency array containing a timer. Fix with the updater form or correct dependencies. → [[02.3 - Closures]]

**When should you use `useMemo`?**
Two reasons: skipping genuinely expensive computation (roughly 1ms+, measured), and preserving referential identity for dependency arrays, memoized children and context values. The second is the more common and more important. It is a hint, not a guarantee — never rely on it for stable ids. → [[17.6 - useMemo]]

**When should you use `useCallback`?**
Only where there is a comparison boundary: a prop to a `React.memo` child, a hook dependency, or a value returned from a custom hook. Elsewhere it costs more than it saves. → [[17.7 - useCallback]]

**`useRef` vs `useState`?**
Both persist across renders; only state triggers re-renders, and refs are mutable in place. Refs are for DOM handles and instance-like values, and must not be read or written during render. → [[17.8 - useRef]]

**When would you use `useReducer` over `useState`?**
Several interdependent values, complex transitions, the same transition dispatched from several places, or a state machine. `dispatch` is also guaranteed stable, which enables the state/dispatch context split. → [[17.10 - useReducer]]

**Do two components using the same custom hook share state?**
No. Each call allocates its own hook slots in its own component. Custom hooks share logic, not state — sharing state needs context or a store. → [[17.11 - Custom Hooks]]

**What is `useSyncExternalStore` for?**
Subscribing to a mutable external source safely under concurrent rendering, preventing tearing. Every store library uses it internally. `getSnapshot` must return a cached value or you get an infinite loop. → [[17.12 - Lesser Known Hooks]]

## Internals

**What is Fiber?**
A rewrite of the reconciler replacing recursion with a linked list of work units, so rendering can be paused, resumed, prioritized and abandoned. It enabled concurrent rendering, Suspense and error boundaries. → [[18.3 - Fiber Architecture]]

**Render phase vs commit phase?**
Render is interruptible, discardable and may repeat — no DOM is touched. Commit is synchronous and atomic — DOM changes, refs attached, layout effects run, then paint, then passive effects. → [[18.4 - Render Phase vs Commit Phase]]

**What is concurrent rendering?**
Interruptible rendering with priorities, so urgent updates (typing) are not blocked by non-urgent ones (filtering a large list). It is not multithreading and does not make rendering faster. → [[18.5 - Concurrent Rendering and the Scheduler]]

**Why does Strict Mode run effects twice in development?**
To verify effects are re-runnable and components are pure — both of which the architecture relies on. The fix for a double-invocation bug is proper cleanup, never a ref guard. → [[18.7 - Strict Mode and Double Invocation]]

**What changed with automatic batching in React 18?**
Batching extended from React event handlers to everywhere — timers, promises, native handlers. `flushSync` opts out when the DOM must be updated within the same handler. → [[18.6 - Batching and the Update Queue]]

## Performance

**What causes a component to re-render?**
Its own state changed, its parent re-rendered, a context it consumes changed, or its props changed **and** it is wrapped in `React.memo`. A parent re-rendering re-renders all children regardless of props. → [[19.1 - What Causes Re-renders]]

**Does a re-render mean DOM work?**
No. Re-rendering calls the function and diffs the output; identical output produces zero DOM mutations. Most re-renders are harmless. → [[19.1 - What Causes Re-renders]]

**What is `React.memo` and why does it often not work?**
It shallowly compares props and skips re-rendering when unchanged. Inline object, array or function props have a new identity every render, so the comparison always fails. → [[19.2 - React.memo and Memoization Strategy]]

**How do you avoid re-renders without memoization?**
Move state down so fewer components are affected, and pass expensive subtrees as `children` — the element is created in the outer render, so its reference is stable and React skips it. → [[19.1 - What Causes Re-renders]]

**How do you render 100,000 rows?**
Virtualize — render only the visible window plus overscan, with a spacer preserving scroll height. Consider pagination or `content-visibility: auto` first; both are far cheaper to implement. → [[19.5 - Virtualization and Windowing]]

**What is code splitting?**
Breaking the bundle into chunks loaded on demand via `import()`, with `React.lazy` plus `Suspense` for components. Split by route first, then by heavy dependency, and prefetch on hover to recover the navigation delay. → [[19.3 - Code Splitting and React.lazy]]

**What is the React Compiler?**
A build-time tool that inserts memoization automatically, removing most manual `useMemo`/`useCallback`/`memo`. It only optimizes code that provably follows the rules of React, so purity now has a direct performance payoff. → [[19.9 - The React Compiler]]

## Advanced

**What do error boundaries catch?**
Render-phase errors in their subtree. **Not** event handlers, async code, SSR, or errors in the boundary itself — which is why global `error` and `unhandledrejection` handlers are still required. → [[22.1 - Error Boundaries]]

**What is a portal?**
Rendering into a different DOM node while staying in the React tree, to escape `overflow: hidden` and stacking contexts. Events still bubble through the **React** tree, which surprises outside-click handlers. → [[22.2 - Portals]]

**What is Suspense?**
A boundary rendering a fallback while a descendant is not ready. Paired with `startTransition`, it keeps existing content visible instead of flashing a skeleton on every navigation. → [[19.4 - Suspense]]

**Server Components vs SSR?**
SSR renders on the server and ships the component code for hydration. RSC ships only the rendered output and never re-renders, so the code contributes zero bundle bytes. → [[22.8 - Server Components]]

**Context vs Redux?**
Context is dependency injection with no subscription granularity — every consumer re-renders on any value change, and `React.memo` does not stop it. A store provides selector-based subscriptions so only components reading changed data re-render. → [[20.2 - Context API and Its Limits]]

**Why must reducers be pure?**
Determinism is what makes replay, time-travel debugging and safe middleware possible — and React may call an updater twice in Strict Mode. → [[20.3 - Redux Core Concepts]]
