# File Descriptors and the IO Model

#backend #os #io #linux #file-descriptors

> **In one line:** A file descriptor is a small integer that names an open kernel object: a file, a socket, a pipe or an epoll set. Blocking versus non-blocking I/O on those integers is the whole reason event loops exist.

---

## The Idea

"Everything is a file" really means **everything is a file descriptor**. When you open a file, accept a connection, create a pipe or set up an epoll instance, the kernel hands you a small integer. Every later operation passes that integer back.

```
Process fd table           Open file table (kernel)        Object
┌────┬───────────┐        ┌──────────────────────┐
│ 0  │ ──────────┼──────► │ tty, offset, flags    │ ──► terminal
│ 1  │ ──────────┼──────► │ tty                   │
│ 2  │ ──────────┼──────► │ tty                   │
│ 3  │ ──────────┼──────► │ offset=4096, O_RDONLY │ ──► inode: /var/log/app.log
│ 4  │ ──────────┼──────► │ TCP socket state      │ ──► 10.0.0.5:5432 (Postgres)
│ 5  │ ──────────┼──────► │ listening socket      │ ──► 0.0.0.0:8000
│ 6  │ ──────────┼──────► │ epoll instance        │ ──► watches 4, 5, ...
└────┴───────────┘        └──────────────────────┘
```

Three levels, and the middle one matters:

- The **fd** is per process, just an index.
- The **open file description** holds the offset and flags. After `fork` or `dup`, two fds can share one description, and therefore one offset. That is why a parent and child writing to the same log file do not overwrite each other's lines, and why shell redirection works.
- The **object** is the inode, socket or pipe itself.

```bash
ls -l /proc/$PID/fd           # what each fd points at
lsof -p $PID                  # same, more readable
ls /proc/$PID/fd | wc -l      # how many are open
```

## The Limit That Takes Services Down

Every process has a maximum number of open fds.

```bash
ulimit -n                         # soft limit for this shell (often 1024!)
cat /proc/$PID/limits | grep "open files"
cat /proc/sys/fs/file-max         # system-wide ceiling
```

```
OSError: [Errno 24] Too many open files
```

Every connection is an fd. A service holding 800 client connections, 100 upstream HTTP keep-alive connections, a 50-connection DB pool and some log files is past 1,000 already. With the classic default soft limit of 1024, the next `accept()` fails.

**Fixes:**

| Where | How |
|---|---|
| systemd | `LimitNOFILE=65535` in the unit file |
| Docker | `--ulimit nofile=65535:65535` or `ulimits:` in compose |
| Kubernetes | Inherits the container runtime's default (usually high, often 1,048,576). Check rather than assume. |
| In Python | `resource.setrlimit(resource.RLIMIT_NOFILE, (hard, hard))` raises the soft limit up to the hard one |

⚠️ **Running out of fds is often a leak, not a limit problem.** A client created per request and never closed (`httpx.AsyncClient()` inside a handler), responses not closed, files opened without `with`. Graph the fd count over time. A sawtooth is healthy; a ramp is a leak. Raising the limit only delays the outage.

## Five I/O Models

All network I/O in every language is built on one of these. Python's asyncio uses the third.

### 1. Blocking

```
read(fd) ──── thread sleeps until data arrives ────► returns data
```

Simple. One thread per connection. Breaks at thousands of connections (memory and scheduler cost). This is thread-per-request servers and plain `socket.recv`.

### 2. Non-blocking (polling)

```python
sock.setblocking(False)
sock.recv(4096)    # no data? raises BlockingIOError (EAGAIN) immediately
```

The thread never sleeps, but if you just loop on `recv` you burn 100% CPU asking "anything yet?". Useless on its own. Essential combined with model 3.

### 3. I/O multiplexing (readiness): select, poll, epoll, kqueue

```
epoll_wait([fd4, fd5, fd9, ...]) ── sleep until ANY of them is ready ──► [fd9 readable]
then: recv(fd9) on a non-blocking socket — guaranteed not to block
```

One thread watches thousands of fds. The kernel tells you **which are ready**, and you do the read yourself. This is nginx, Redis, Node.js, Go's netpoller and Python's asyncio (`selectors.EpollSelector`). The full C10k story is in [[03.12 - Event Driven Servers]].

### 4. Signal-driven I/O

The kernel sends `SIGIO` when an fd is ready. Rarely used. Signals are awkward ([[02.9 - Signals and Process Lifecycle]]).

### 5. Asynchronous I/O (completion): io_uring, Windows IOCP

```
submit: "read 4 KB from fd9 into this buffer"  ──► returns immediately
later:  completion queue says "done, 4096 bytes are in your buffer"
```

The kernel does the read for you and reports **completion**, not readiness. `io_uring` (Linux 5.1+) uses shared ring buffers so you can submit and reap many operations with few or no syscalls. It is also the first good answer to async **file** I/O on Linux.

| Model | Tells you | Syscalls per operation | Used by |
|---|---|---|---|
| Blocking | Nothing. You wait. | 1 | Simple scripts, thread pools |
| epoll | "fd is ready" | ~2 (`epoll_wait` + `read`), batched | asyncio, nginx, Redis, Node |
| io_uring | "operation is done" | Batched, can reach ~0 | Newer databases and proxies, some Rust runtimes |

## Disk Files Are the Odd One Out

⚠️ **epoll does not work on regular files.** A file on disk is always reported "ready", so a `read()` that has to go to disk still blocks the thread. That is why:

- asyncio has no truly async file API; `aiofiles` runs file I/O in a thread pool.
- Node.js runs file I/O on libuv's thread pool.
- `await asyncio.to_thread(path.read_bytes)` is the honest way to read a file from async code.

If your event loop stalls when a request reads a large file or writes a big log synchronously, this is the reason. See [[01.6 - The Blocking Call Problem]].

## Pipes and Redirection

A pipe is a pair of fds: one write end, one read end, with a kernel buffer (64 KB by default on Linux) between them.

```python
r, w = os.pipe()
```

- Writing to a full pipe **blocks** the writer. This is backpressure built into Unix.
- Reading from an empty pipe blocks until data arrives, or returns 0 (EOF) once every write end is closed.
- Writing to a pipe whose read end is closed raises `SIGPIPE` / `EPIPE` ([[02.9 - Signals and Process Lifecycle]]).

⚠️ **The classic subprocess deadlock:** you start a child with `stdout=PIPE` and `stderr=PIPE`, then call `proc.wait()` before reading. The child fills the 64 KB stdout pipe and blocks writing. You block waiting for it to exit. Forever. Always use `proc.communicate()` or `subprocess.run(..., capture_output=True)`, which read both pipes while waiting.

## Zero-Copy: sendfile and splice

Serving a file the naive way copies it four times:

```
disk → page cache → (read) user buffer → (write) socket buffer → NIC
```

`sendfile(out_fd, in_fd, ...)` tells the kernel to move bytes from the page cache to the socket directly, never through user space. nginx's `sendfile on;`, Kafka's consumer reads, and Starlette's `FileResponse` (via `loop.sendfile` where available) all use this. It is a big part of why Kafka can serve consumers at disk speed ([[10.1 - Queue vs Log]]).

## Codebase

**Repos:** `python/cpython`, `mit-pdos/xv6-riscv`

**Question to answer:** What happens inside asyncio between `await reader.read(100)` and the kernel telling it that fd 9 has data?

**Read, in order:**

1. xv6 `kernel/file.c` and `kernel/file.h` — `struct file` is the open file description: a ref count, an offset, a type. `filedup()` shows why `fork` shares offsets.
2. xv6 `kernel/pipe.c` — a complete pipe in about 100 lines: a ring buffer, sleep on full, sleep on empty
3. CPython `Lib/selectors.py` — `EpollSelector.register()` and `select()`
4. CPython `Lib/asyncio/selector_events.py` — `_SelectorSocketTransport._read_ready()`. This runs when epoll says the socket is readable.
5. CPython `Lib/subprocess.py` — `Popen.communicate()` on POSIX (`_communicate`), which uses a selector to drain both pipes without deadlocking

**Size:** 2 sessions.
