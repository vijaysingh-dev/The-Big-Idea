# Aura Components, Attributes and Expressions

## Reading an existing component

This note is aimed at working in code you inherited rather than writing new Aura.

```xml
<aura:component controller="ClaimController"
                implements="flexipage:availableForRecordHome,force:hasRecordId"
                access="global">

    <aura:attribute name="recordId" type="Id"/>
    <aura:attribute name="claims" type="List" default="[]"/>
    <aura:attribute name="selectedClaim" type="Object"/>
    <aura:attribute name="isLoading" type="Boolean" default="true" access="private"/>

    <aura:handler name="init" value="{!this}" action="{!c.doInit}"/>
    <aura:handler name="change" value="{!v.recordId}" action="{!c.handleRecordChange}"/>

    <lightning:card title="Warranty Claims">
        <aura:if isTrue="{!v.isLoading}">
            <lightning:spinner alternativeText="Loading"/>

            <aura:set attribute="else">
                <aura:iteration items="{!v.claims}" var="claim">
                    <div class="claim-row" onclick="{!c.handleSelect}"
                         data-claim-id="{!claim.Id}">
                        <span>{!claim.Claim_Number__c}</span>
                        <lightning:formattedNumber value="{!claim.Claim_Amount__c}"
                                                   style="currency" currencyCode="INR"/>
                    </div>
                </aura:iteration>
            </aura:set>
        </aura:if>
    </lightning:card>
</aura:component>
```

`controller="ClaimController"` binds the component to an Apex class — a declaration LWC replaces with a per-method import.

## Attributes

```xml
<aura:attribute name="claims" type="List" default="[]"/>
<aura:attribute name="amount" type="Decimal" default="0"/>
<aura:attribute name="claim" type="Warranty_Claim__c"/>
<aura:attribute name="statusOptions" type="String[]"/>
<aura:attribute name="isEditable" type="Boolean" default="false" access="private"/>
<aura:attribute name="callback" type="Aura.Action"/>
```

Types include the primitives, `Object`, `List`, `Map`, `Set`, sObject types, and `Aura.Action` for a passed function.

`access` of `private`, `public`, or `global` is the Aura equivalent of `@api` — public and global attributes are settable by a parent.

Reading and writing from JavaScript:

```javascript
const claims = component.get("v.claims");
component.set("v.isLoading", false);
```

**`component.set` is what triggers a rerender.** Mutating the value returned by `get` does not — the same reassignment rule as LWC, expressed differently.

```javascript
// Does not rerender
component.get("v.claims").push(newClaim);

// Rerenders
const claims = component.get("v.claims");
component.set("v.claims", [...claims, newClaim]);
```

## Expressions

```xml
{!v.claimNumber}                     an attribute
{!c.handleClick}                     a controller method
{!v.amount > 500000}                 logic in markup
{!v.firstName + ' ' + v.lastName}    concatenation
{!v.isOpen ? 'Open' : 'Closed'}      a ternary
{!$Label.c.Claim_Approved}           a custom label
{!$Resource.chartjs}                 a static resource
{!$User.Id}                          a global value provider
```

**Aura allows logic in expressions.** It is convenient, and it puts business rules in markup where they cannot be unit tested and are easy to miss when reading the code.

When migrating, every expression containing logic becomes a getter in the LWC class — which is usually an improvement rather than a chore.

## Two-way versus one-way binding

The distinction with no LWC equivalent, and the source of Aura's most confusing behaviour.

```xml
<!-- Two-way: the child mutating this changes the parent's attribute -->
<c:claimEditor claim="{!v.selectedClaim}"/>

<!-- One-way: the child gets a copy -->
<c:claimEditor claim="{#v.selectedClaim}"/>
```

With `{!}`, a child setting the attribute silently changes the parent's value with no event and no visible data flow. Tracing where a value changed means reading every component that receives it.

LWC removed this deliberately: data flows down through properties and back up through events, and the path is always visible.

When reading Aura code, **`{!}` on a passed attribute is a place where the child may be mutating parent state.**

## Conditionals and iteration

```xml
<aura:if isTrue="{!v.hasClaims}">
    <c:claimList claims="{!v.claims}"/>

    <aura:set attribute="else">
        <p>No claims found.</p>
    </aura:set>
</aura:if>
```

`<aura:set attribute="else">` is the else branch, and it is nested inside the `aura:if` rather than being a sibling — which reads awkwardly and is easy to misplace.

```xml
<aura:iteration items="{!v.claims}" var="claim" indexVar="index">
    <div>{!index}: {!claim.Claim_Number__c}</div>
</aura:iteration>
```

**No `key` attribute.** Aura handles reuse internally, which means it does not have LWC's index-key bug and also gives less control.

## The controller and helper

```javascript
// claimListController.js
({
    doInit: function(component, event, helper) {
        helper.loadClaims(component);
    },

    handleSelect: function(component, event, helper) {
        const claimId = event.currentTarget.dataset.claimId;
        helper.selectClaim(component, claimId);
    }
})
```

```javascript
// claimListHelper.js
({
    loadClaims: function(component) {
        const action = component.get("c.getClaims");
        action.setParams({ accountId: component.get("v.recordId") });

        action.setCallback(this, function(response) {
            const state = response.getState();

            if (state === "SUCCESS") {
                component.set("v.claims", response.getReturnValue());
            } else if (state === "ERROR") {
                // errors arrive as an array, and getError() is easy to forget
                const errors = response.getError();
                this.showError(component, errors[0]?.message ?? 'Unknown error');
            }
            component.set("v.isLoading", false);
        });

        $A.enqueueAction(action);
    },

    showError: function(component, message) {
        const toast = $A.get("e.force:showToast");
        toast.setParams({ title: "Error", message: message, type: "error" });
        toast.fire();
    }
})
```

**Controller functions cannot call each other.** Shared logic must go in the helper, which is the reason the two files exist.

**`$A.enqueueAction` is required.** An action that is configured but never enqueued does nothing, with no error — a classic Aura debugging session.

**Every callback checks `getState()`.** The states are `SUCCESS`, `ERROR`, `INCOMPLETE`, and `ABORTED`. Code checking only for `SUCCESS` silently ignores failures.

## Calling Apex

```java
public with sharing class ClaimController {

    @AuraEnabled(cacheable=true)
    public static List<Warranty_Claim__c> getClaims(Id accountId) {
        return [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c
            FROM Warranty_Claim__c
            WHERE Account__c = :accountId
            WITH USER_MODE
        ];
    }
}
```

The same `@AuraEnabled` annotation serves both frameworks — an Apex controller written for Aura works unchanged from LWC, which is what makes migration incremental. See [[14.10 - Calling Apex - Wire vs Imperative]].

`cacheable=true` in Aura requires `setStorable()` on the action to actually cache:

```javascript
action.setStorable();
$A.enqueueAction(action);
```

LWC's wire service does this automatically, which is one of several places where LWC removed a manual step.

## The renderer

```javascript
// claimListRenderer.js
({
    afterRender: function(component, helper) {
        this.superAfterRender();
        helper.initializeChart(component);
    }
})
```

`render`, `rerender`, `afterRender`, and `unrender`, each calling its `super` method.

Rarely needed and heavily misused in older code — DOM manipulation in `rerender` is a common cause of Aura components that behave unpredictably. LWC's `renderedCallback` covers the legitimate cases.

## The design file

```xml
<!-- claimList.design -->
<design:component label="Claim List">
    <design:attribute name="cardTitle" label="Card title" default="Warranty Claims"/>
    <design:attribute name="maxRows" label="Maximum rows" default="10"/>
    <design:attribute name="showClosed" label="Include closed claims"/>
</design:component>
```

The App Builder configuration surface, equivalent to `targetConfigs` in an LWC's metadata file. Only attributes listed here are configurable, and they must also be declared as `aura:attribute` in the component.

## Interfaces

```xml
implements="flexipage:availableForRecordHome,
            flexipage:availableForAllPageTypes,
            force:hasRecordId,
            force:hasSObjectName,
            force:lightningQuickAction,
            forceCommunity:availableForAllPageTypes,
            lightning:isUrlAddressable,
            lightning:actionOverride"
```

`force:hasRecordId` is what injects the record Id on a record page — the equivalent of naming the LWC property `recordId`.

`force:lightningQuickAction` versus `force:lightningQuickActionWithoutHeader` determines whether the quick action modal supplies its own header and buttons.

## Debugging

```javascript
console.log(JSON.stringify(component.get("v.claims")));
$A.log("message", value);
```

**Enable Debug Mode** in Setup for the user, which serves unminified framework code and makes stack traces readable. Without it, an Aura error points into minified framework internals and tells you nothing.

The errors that recur:

**"Cannot read property of undefined"** — usually an attribute read before initialization, or a callback firing after the component was destroyed.

**Nothing happens** — an action that was never enqueued.

**"Access Check Failed"** — an attribute or component accessed without sufficient `access`, which is Aura's namespace protection and is confusing until you know what it means.

## Modifying inherited Aura

Practical guidance for the common task.

**Do not extend it.** Adding features to an Aura component that could be an LWC compounds the problem. Add the new functionality as an LWC nested inside it.

```xml
<aura:component>
    <!-- existing Aura markup -->
    <c:newFeaturePanel recordId="{!v.recordId}"/>
</aura:component>
```

**Check for two-way binding** before changing anything that passes attributes to children.

**Check `getState()` handling** — older code frequently ignores the error path.

**Look for logic in expressions**, which is where behaviour hides.

**Enable Debug Mode** before investigating anything.

## Practical guidance

**Use `component.set` to change state**, never mutate what `get` returned.

**Enqueue every action.**

**Handle `ERROR` and `INCOMPLETE`**, not just `SUCCESS`.

**Put shared logic in the helper**, since controller functions cannot call each other.

**Treat `{!}` on passed attributes as a mutation risk.**

**Add new functionality as a nested LWC** rather than extending the Aura component.

**Enable Debug Mode** when investigating.
