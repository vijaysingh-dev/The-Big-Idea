# Reports and Dashboards

## Why a developer needs this

Two reasons.

**Report types are metadata you design.** A user cannot report on what the report type does not expose, and getting them wrong is the most common reason "we can't report on that" becomes a development request.

**Reports are the cheapest answer to many requirements.** A request for a custom component showing claims by status, with a chart, is usually a report — no code, no test coverage, no maintenance.

## Report types

A report type defines which objects and fields are available, and how they join.

```
Setup → Report Types → New Custom Report Type

Primary Object:  Warranty Claim
Report Type Label: Claims with Coverage and Parts
Deployment Status: Deployed
```

Then the relationships:

```
Warranty Claim
  └── (A) Claim Parts             each Claim may or may not have Parts
        └── (B) Products          each Part must have a Product
```

**The A/B choice is the entire design decision.**

**(A) "may or may not have"** — an outer join. Claims with no parts still appear.

**(B) "must have"** — an inner join. Claims with no parts are excluded.

Choosing B when A was meant silently hides records, and the user reports the numbers as wrong without knowing why. This is the single most common report type defect.

## Standard versus custom report types

**Standard report types** are generated automatically for every object and its relationships. They cover most needs and cannot be modified.

**Custom report types** are needed when:

- You need four levels of relationship — standard types stop at two
- You want to expose fields from a lookup that standard types omit
- You need an outer join the standard type does not provide
- You want to restrict which fields users see in reports

**Custom report types can add fields via lookup**, which is how a report on Claims shows the Account's industry without a formula field:

```
Report Type: Claims with Coverage
  Add fields related via lookup → Asset → Account → Industry
```

That capability removes a whole category of formula fields created solely for reporting — worth knowing, because those formulas cost compile size and query time on every read. See [[06.4 - Cross-Object Formulas and Limits]].

## Report formats

```
Tabular     a flat list; no grouping, no charts
Summary     grouped by rows, with subtotals
Matrix      grouped by rows and columns
Joined      several report blocks side by side
```

**Summary is the default choice** for anything analytical. Tabular is for a list to export.

**A tabular report cannot be used as a dashboard source** unless it has a row limit set, which is a small trap.

**Joined reports** show, for example, open claims, closed claims, and rejected claims as three blocks with a shared grouping. Useful, and they cannot be used for some dashboard component types.

## Bucket fields, formulas, and filters

Three things that reduce the need for custom fields.

**Bucket fields** group values without a formula field:

```
Bucket: Claim Size
  Small     Claim_Amount__c < 50000
  Medium    50000 ≤ Claim_Amount__c < 500000
  Large     Claim_Amount__c ≥ 500000
```

**Row-level formulas** compute per row inside the report:

```
Days_Open = TODAY() - Claim_Date__c
```

**Summary formulas** compute on grouped values:

```
Approval rate:  RowCount:SUM / PARENTGROUPVAL(RowCount:SUM, GRAND_SUMMARY)
```

`PARENTGROUPVAL` and `PREVGROUPVAL` are what make percentage-of-total and period-over-period comparisons possible without a custom field.

**Reaching for a formula field when a report formula would do** adds a permanent schema field, consumes compile size, and is computed on every query rather than only in the report. Ask which is needed.

## Filters

```
Field filters       Status equals Submitted
Filter logic        (1 AND 2) OR 3
Cross filters       Accounts WITH Claims, or WITHOUT Claims
Row limits          top 10 by amount
Relative dates      LAST 90 DAYS, THIS FISCAL QUARTER
```

**Cross filters** are underused and genuinely powerful — "Assets without an active service contract" is a cross filter, and building it any other way needs a formula field or a batch job.

**Relative date filters** are what make a report reusable. A report filtered to a fixed date range is a snapshot; one filtered to `THIS FISCAL QUARTER` is a dashboard.

## Sharing and folders

```
Report folder
  Access:  Viewer, Editor, Manager
  Shared with: roles, role and subordinates, public groups, territories
```

**Folder access controls who sees the report definition. Record-level security controls what data appears in it.**

Two users running the same report see different rows, because reports respect sharing. That is the correct behaviour and it surprises people who expect a report to show everything.

The exception is a report run in a dashboard with a **running user** — covered below.

## Dashboards

A dashboard component is a report, rendered as a chart, gauge, metric, or table.

```
Component types
  Chart        bar, line, donut, funnel, scatter
  Gauge        a value against thresholds
  Metric       a single number
  Table        rows with conditional highlighting
  Lightning table  richer formatting, more columns
```

**Every dashboard component needs a source report**, and the report's grouping determines what the chart can show. A chart with no grouping is not possible, which is why tabular reports are limited as sources.

## The running user

The most consequential dashboard setting.

**Fixed running user** — everyone sees the same data, as that user sees it. Right for an executive dashboard where the numbers should be identical for everyone.

**Dynamic dashboard** — each viewer sees data as themselves. Right for a manager dashboard where each manager should see their own team.

```
Dashboard properties → View Dashboard As
  Me                            fixed, as the creator
  Another person                fixed, as a named user
  The dashboard viewer          dynamic
```

**Dynamic dashboards are limited in number by edition** — typically 5 in Enterprise, 10 in Unlimited — which is the constraint that forces a fixed running user more often than the design would prefer.

**A fixed running user is a data exposure decision.** Setting it to an administrator means every viewer sees every record's contribution to the numbers, regardless of their own access. That is frequently intended and should be deliberate. See [[03.7 - Organization-Wide Defaults]].

## Subscriptions and refresh

```
Report subscription     scheduled email of the report, with conditions
Dashboard subscription  scheduled email of the dashboard image
```

**Report subscriptions support conditions**, which turns a report into an alert:

```
Send when:  Record Count is greater than 10
Schedule:   Weekdays at 08:00
```

That is the declarative equivalent of a scheduled Apex job checking a threshold and emailing — and it needs no code, no test coverage, and no deployment.

**Subscription limits** apply per user and per org, and a scheduled report that fails silently is a real operational gap. Reports scheduled by a departed user stop running.

## Reporting snapshots

The mechanism for trend reporting, and one of the more useful under-known features.

```
Setup → Reporting Snapshots → New

Source Report:      Open Claims by Region
Target Object:      Claim_Snapshot__c
Field Mappings:     Region → Region__c, Record Count → Claim_Count__c
Schedule:           Daily at 23:00
```

Each run writes the report's summary rows into a custom object. Over time that object holds a history the source data cannot provide.

**This is how you report on "how many open claims did we have last Tuesday"** when the claims themselves have since closed. Without a snapshot, that history does not exist. See [[04.13 - Forecasting and Revenue Management]].

The constraint: the target object needs a field per mapped column, and the snapshot writes rows on every run, so volume needs managing.

## Reports in Apex

```java
// Run a report and read the results
Reports.ReportResults results = Reports.ReportManager.runReport(reportId, true);

Reports.ReportFactWithDetails fact = (Reports.ReportFactWithDetails)
    results.getFactMap().get('T!T');

for (Reports.ReportDetailRow row : fact.getRows()) {
    for (Reports.ReportDataCell cell : row.getDataCells()) {
        System.debug(cell.getLabel() + ' = ' + cell.getValue());
    }
}
```

The Reports API lets Apex read a report's results, which is occasionally the right way to reuse a complex report definition rather than rewriting its logic in SOQL.

**Limits:** 500 synchronous report runs per hour, 2,000 rows returned, and the report must be accessible to the running user.

In practice, **querying directly is usually better** — the Reports API is awkward, the fact map keys are cryptic, and a SOQL aggregate is faster and clearer. The exception is when the report definition is genuinely complex and maintained by an administrator, and duplicating it in Apex would create two sources of truth.

## When a report is the right answer

The check worth running before building anything:

**Can a report do it?** Grouping, filtering, charts, conditional formatting, scheduled delivery with conditions, and export — all with no code.

**Can a report plus a dashboard do it?** Add visualization and a running user.

**Can a reporting snapshot do it?** Trend data over time.

**Does it need a component?** Custom interaction, a data shape reports cannot express, or embedding in a specific place.

A custom LWC that displays claims grouped by status, with a chart, is a report someone decided to build. The report is better: it is maintainable by an administrator, it exports, it schedules, it respects sharing without any code, and it does not need a test.

## Reports and performance

Reports are queries, and the same rules apply.

**A report on a large object with a non-selective filter times out.** The fix is the same: a date bound, a more selective filter, or an index. See [[16.9 - Skinny Tables and Custom Indexes]].

**Skinny tables help reports specifically**, because a report reading six columns from a sixty-field object benefits directly from the narrower row.

**Formula fields are computed per row on read.** A report over 500,000 rows with eight cross-object formulas is doing eight traversals per row.

**Row limits and date filters** are the practical mitigations users can apply themselves.

## Practical guidance

**Get the A/B relationship right** in custom report types — B silently hides records.

**Add lookup fields to report types** rather than creating formula fields for reporting.

**Use bucket fields and report formulas** before adding schema fields.

**Use relative date filters** so reports stay useful.

**Set the dashboard running user deliberately** — it is a data exposure decision.

**Use report subscriptions with conditions** as a no-code alerting mechanism.

**Use reporting snapshots** for anything needing history.

**Query directly rather than through the Reports API** unless the report definition is the source of truth.

**Ask whether a report would do** before building a component.
