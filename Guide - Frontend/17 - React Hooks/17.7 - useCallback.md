# useCallback

`useCallback` returns the same function reference between renders as long as its dependencies are unchanged.

```jsx
const handleClick = useCallback(() => {
  onSelect(id);
}, [onSelect, id]);
```

It is exactly `useMemo(() => fn, deps)` — same mechanism, specialized syntax ([[17.6 - useMemo]]).

## What problem it solves

Functions defined in a component body are recreated every render. The *allocation* is negligible — engines create millions of closures per second. What costs something is the **new identity**:

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  const handleSelect = () => doSomething();   // new function every render

  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveList onSelect={handleSelect} />   {/* new prop → re-renders */}
    </>
  );
}

const ExpensiveList = React.memo(function ExpensiveList({ onSelect }) { ... });
```

`React.memo` compares props with `Object.is`. A new function reference fails that comparison, so the memo does nothing and the expensive child re-renders on every count change.

```jsx
const handleSelect = useCallback(() => doSomething(), []);
```

Now the reference is stable and the memo works.

## The three legitimate uses

**1. A prop to a memoized child.** As above. Without `React.memo` on the child, `useCallback` accomplishes nothing — the child re-renders either way.

**2. A dependency of another hook.**

```jsx
const fetchData = useCallback(async () => {
  const res = await fetch(`/api/items?q=${query}`);
  setItems(await res.json());
}, [query]);

useEffect(() => { fetchData(); }, [fetchData]);
```

Without the memo, `fetchData` changes every render and the effect fires in a loop.

Note that in this specific case, moving the function *inside* the effect is usually better and removes the need for `useCallback` entirely ([[17.3 - useEffect and the Dependency Array]]).

**3. A value returned from a custom hook.**

```jsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle];
}
```

A custom hook cannot know whether its consumer will use the function in a dependency array or pass it to a memoized child. Returning stable references is part of a good hook API ([[17.11 - Custom Hooks]]).

## When it does nothing

```jsx
// Child is not memoized — it re-renders regardless
const handle = useCallback(() => {}, []);
<PlainChild onClick={handle} />

// DOM elements do not care about prop identity
<button onClick={useCallback(() => {}, [])} />

// Not used in any dependency array or memoized boundary
const format = useCallback(v => v.toFixed(2), []);
```

The last one is worth stressing: a memoized function that is only *called* gains nothing. `useCallback` preserves identity, and identity only matters at a comparison boundary.

Inline arrows on DOM elements — `onClick={() => setOpen(true)}` — are fine and idiomatic. React attaches one delegated listener per event type at the root, so the handler identity does not cause any DOM work ([[12.3 - The Event Model]]).

## The stability chain

`useCallback` only helps if its own dependencies are stable:

```jsx
function Parent({ items }) {
  const config = { sortBy: "name" };                     // new every render
  const handle = useCallback(() => sort(items, config), [items, config]);
  // handle is new every render — the memo is wasted
}
```

One unstable link makes the whole chain useless, and there is no warning. This "memoization cascade" — needing `useMemo` for objects, `useCallback` for functions, and `React.memo` for components, all of which must agree — is the strongest argument for the React Compiler ([[19.9 - The React Compiler]]).

## Alternatives that avoid it

**The updater form** removes state from dependencies:

```jsx
const increment = useCallback(() => setCount(c => c + 1), []);   // no count dependency
```

**A ref for the latest value** when a callback must read something without reacting to it:

```jsx
const onChangeRef = useRef(onChange);
useEffect(() => { onChangeRef.current = onChange; });

const stable = useCallback((v) => onChangeRef.current(v), []);
```

This is what libraries use internally, and it is what `useEffectEvent` will replace ([[17.3 - useEffect and the Dependency Array]]).

**Event delegation** avoids per-item callbacks in large lists entirely:

```jsx
<ul onClick={handleListClick}>
  {items.map(item => <li key={item.id} data-id={item.id}>{item.name}</li>)}
</ul>
```

One handler instead of N, and no memoization needed ([[12.4 - Event Delegation]]).

**Composition** often removes the memoized boundary altogether:

```jsx
// Passing an element instead of a callback
<Layout sidebar={<Filters onChange={setFilters} />}>{content}</Layout>
```

The element is created in the parent's render and does not change when `Layout` re-renders ([[16.3 - Components and Props]]).

## Cost

Every `useCallback` allocates a hook slot, stores the dependency array, and runs a comparison per dependency on each render. It also creates the inline function anyway — the memo decides which reference to *return*, not whether to allocate.

So an unnecessary `useCallback` is strictly slower than no `useCallback`, plus it adds a dependency array that can go stale.

This is why blanket "wrap everything in useCallback" advice is wrong: it costs performance and correctness for no benefit in the majority of cases.

## The React Compiler

The compiler inserts memoization automatically for functions and values, based on what actually flows into memoized boundaries. On a compiled codebase, manual `useCallback` becomes largely unnecessary and the memoization cascade disappears.

It only optimizes components that follow the rules of React, so purity and correct hook usage now translate directly into performance ([[16.5 - Rendering and Purity]]).

## How senior engineers actually use this

**They add `useCallback` only where there is a comparison boundary** — a memoized child, a hook dependency, or a custom hook's return value.

**They check the whole chain.** A `useCallback` whose dependencies are unstable is worse than none.

**They prefer restructuring to memoizing.** The updater form, moving functions into effects, delegation and composition each remove the need rather than papering over it.

**They use the Profiler to confirm** a memoized child was actually re-rendering before adding the memo.

## Common pitfalls

- `useCallback` on a prop to a non-memoized child.
- An unstable dependency silently defeating the memo.
- Missing dependencies producing a stale closure inside the callback.
- Wrapping every handler by default, adding overhead and dependency arrays everywhere.
- Memoizing a function that is only ever called, never compared.
- Assuming inline arrows on DOM elements are a performance problem.

## Interview angle

"When should you use useCallback" is a filter question. The right answer is that it preserves function identity, which only matters at a comparison boundary — a `React.memo` child, a hook dependency array, or a custom hook's public API — and that using it elsewhere costs more than it saves. Mentioning the memoization cascade (every dependency must also be stable) and that the React Compiler exists to eliminate this class of manual work shows current, practical understanding.
