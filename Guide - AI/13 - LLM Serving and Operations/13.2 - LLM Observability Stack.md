# LLM Observability Stack

## What It Is

LLM observability is the practice of capturing, storing, and analyzing the full execution trace of every LLM-powered request — inputs, outputs, intermediate steps, latency, cost, and quality signals — so you can debug failures, detect regressions, measure quality, and improve the system over time.

Standard APM gives you HTTP status codes and latency percentiles — that tells you whether your system is *up*. LLM observability tells you whether it's *working*. Those are entirely different questions.

The three dominant tools: **Langfuse** (open-source, self-hostable, full LLMOps), **Helicone** (proxy-based, zero code change), **Arize Phoenix** (evaluation-heavy, OpenTelemetry-native). Each has a distinct philosophy. Understanding all three makes you a stronger system designer — and for your target companies (Helicone, Langfuse, Arize, Vellum are all on your list), knowing competitor internals is expected in interviews.

---

## Why It Matters

- LLM failures are **silent**: a 200 OK with a hallucinated answer looks identical to a correct one at the HTTP layer
- Without traces you can't answer: "Why did this user get a bad answer?" — the most important debugging question
- Quality regressions happen gradually: retrieval degrades, prompts drift, model updates change behavior — you won't notice without continuous measurement
- Cost regressions are invisible without token-level tracking: a prompt change that adds 200 tokens is $70K/year at scale
- For LLMOps companies (Helicone, Langfuse, Arize, Vellum) in your target list — understanding the internals of competing tools is expected

---

## The Observability Data Model

Before looking at tools, define what data you need:

```
Trace (one user request end-to-end)
├── trace_id, user_id, session_id
├── input (user's message)
├── output (final response)
├── latency_ms, cost_usd
├── metadata (app version, feature flag, A/B variant)
│
└── Spans (each pipeline step)
    ├── Span: query_embedding
    │   ├── model: "text-embedding-3-small"
    │   ├── input_tokens: 12, latency_ms: 45
    │
    ├── Span: retrieval
    │   ├── query, top_k, results: [{chunk_id, score, title}]
    │   ├── latency_ms: 80
    │
    ├── Span: reranking
    │   ├── input_count: 10, output_count: 5, latency_ms: 120
    │
    └── Span: llm_generation
        ├── model, system_prompt, messages, response
        ├── input_tokens: 3550, output_tokens: 400, cached_tokens: 500
        ├── latency_ms: 1200, cost_usd: 0.013
```

This hierarchical structure (trace → spans) is the OpenTelemetry data model. All three tools are built on it.

## Langfuse — Architecture and Internals

### Philosophy

Open-source LLM engineering platform. Thesis: traces, evaluations, and prompt management belong in the same tool — you need all three to close the feedback loop (observe → evaluate → improve → redeploy).

### Architecture

```
Application Code
    │  SDK (Python/JS) — async batch HTTP POST
    ▼
Langfuse API Server (Go)
    │
    ├── Write path → ClickHouse (columnar, analytics)
    │              + PostgreSQL (prompts, users, datasets)
    │
    └── Read path  → ClickHouse queries → UI / REST API
```

**ClickHouse** is the key choice: columnar storage enables fast aggregations (avg latency by model, cost per user per day) without scan overhead. Append-only writes mean high ingestion throughput and no update contention.

Self-hosting is Docker Compose or Kubernetes — relevant for enterprise customers with data residency requirements.

### SDK Integration Patterns

**Pattern 1: Decorator (cleanest)**

```python
from langfuse.decorators import observe, langfuse_context
from langfuse.openai import openai  # drop-in replacement

@observe()   # creates a trace automatically
def rag_pipeline(question: str, user_id: str) -> str:
    langfuse_context.update_current_trace(
        user_id=user_id,
        metadata={"feature": "enterprise_search"},
    )

    chunks = retrieve(question)

    # openai calls auto-traced: model, tokens, cost, latency
    response = openai.chat.completions.create(
        model="gpt-4o",
        messages=build_messages(question, chunks),
    )
    return response.choices[0].message.content
```

**Pattern 2: Manual spans (full control)**

```python
from langfuse import Langfuse
lf = Langfuse()

def rag_pipeline(question: str, user_id: str) -> str:
    trace = lf.trace(name="rag_query", user_id=user_id, input={"question": question})

    # Retrieval span
    ret_span = trace.span(name="retrieval", input={"query": question})
    chunks = retrieve(question)
    ret_span.end(output={"chunk_ids": [c.id for c in chunks]})

    # LLM generation span
    gen = trace.generation(
        name="llm_generation",
        model="gpt-4o",
        input=build_messages(question, chunks),
    )
    response = llm_call(question, chunks)
    gen.end(
        output=response.content,
        usage={"input": response.usage.prompt_tokens,
               "output": response.usage.completion_tokens},
    )

    trace.update(output=response.content)
    return response.content
```

**Pattern 3: OpenAI drop-in (zero business logic change)**

```python
# Replace:  from openai import OpenAI
# With:
from langfuse.openai import OpenAI
client = OpenAI()
# All calls auto-traced. Nothing else changes.
```

### Scoring and Evaluation

```python
# Attach automated LLM-as-judge score
lf.score(
    trace_id=trace.id,
    name="faithfulness",
    value=0.92,
    comment="All claims supported by context",
    source="automated",
)

# Attach user feedback
lf.score(
    trace_id=trace.id,
    name="user_rating",
    value=1,        # thumbs up=1, thumbs down=0
    source="human",
)
```

Scores attached to traces enable: filtering traces by quality, building regression suites from low-quality examples, A/B testing prompt versions by average score.

### Prompt Management

```python
# Pull versioned prompt from Langfuse (not hardcoded)
prompt = lf.get_prompt("rag_system_prompt", version=2)
compiled = prompt.compile(company_name="Acme Corp")

# Prompt is linked to traces — see which version produced which outputs
```

## Helicone — Architecture and Internals

### Philosophy

Helicone is a **proxy**. Route your OpenAI/Anthropic calls through Helicone servers. Zero code changes required — just change `base_url`.

Thesis: observability should require the least possible engineering work to adopt.

### Architecture

```
Your Application
    │  HTTP → Helicone proxy
    ▼
Helicone Proxy (Cloudflare Workers — edge, globally distributed)
    │
    ├── Log request + response → ClickHouse (async, non-blocking)
    │
    └── Forward to LLM API (OpenAI/Anthropic) transparently
```

**Cloudflare Workers** runs at the edge globally, adds <5ms latency, handles massive volume without dedicated servers. This is the architectural reason Helicone can offer "zero latency overhead" — the proxy is closer to the LLM API than your servers are.

### Integration

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-...",
    base_url="https://oai.hconeai.com/v1",       # ← only change
    default_headers={
        "Helicone-Auth": f"Bearer {HELICONE_API_KEY}",
        "Helicone-User-Id": user_id,
        "Helicone-Session-Id": session_id,
        "Helicone-Property-Feature": "enterprise_search",  # custom dimensions
    },
)

# Everything else unchanged
response = client.chat.completions.create(model="gpt-4o", messages=[...])
```

Because Helicone is a full proxy, it captures everything: complete request/response bodies, latency, token counts, streaming responses (assembled for logging). No SDK needed, no code changes in business logic.

### Helicone Gateway Features

```python
# Rate limiting via header (no code changes)
headers = {"Helicone-RateLimit-Policy": "100;w=60;u=user"}

# Proxy-level caching
headers = {"Helicone-Cache-Enabled": "true",
           "Helicone-Cache-Bucket-Max-Size": "10"}

# Model fallback routing
headers = {"Helicone-Fallbacks": json.dumps([
    {"modelName": "gpt-4o-mini"},  # fallback if primary fails
])}
```

### Helicone vs Langfuse Decision

| Dimension | Helicone | Langfuse |
|-----------|----------|----------|
| Integration effort | Near-zero (change base_url) | SDK integration |
| RAG step tracing | LLM calls only | Full pipeline spans |
| Evaluation/scoring | Basic | Deep (datasets, A/B) |
| Prompt management | No | Yes |
| Self-hostable | Yes (OSS core) | Yes (full stack) |
| Latency overhead | <5ms (edge) | <10ms (SDK async) |
| Best for | Quick LLM API observability | Full LLMOps platform |

**Practical rule**: Start with Helicone for instant visibility. Migrate to Langfuse when you need full pipeline tracing, prompt management, and evaluation datasets.

## Arize Phoenix — Architecture and Internals

### Philosophy

Phoenix (Arize AI) is **evaluation-first observability**. While Langfuse and Helicone emphasize tracing, Phoenix emphasizes: "Given your traces, what is the quality of your system?" It integrates LLM-as-judge evaluation and dataset management more deeply than the others, and uses OpenTelemetry as its native protocol.

### Architecture

```
Application Code
    │  OpenTelemetry SDK (standard protocol)
    ▼
Phoenix Collector
    │
    ├── Storage: SQLite (local dev) / PostgreSQL (prod)
    │           + Parquet export for large-scale analysis
    │
    └── Eval pipeline: LLM-as-judge runs async against captured traces
```

### OpenTelemetry Integration

```python
from opentelemetry import trace as otel_trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from openinference.instrumentation.openai import OpenAIInstrumentor
import phoenix as px

# Start local Phoenix UI
px.launch_app()

# Wire OTel → Phoenix
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(px.get_default_span_exporter()))
otel_trace.set_tracer_provider(provider)

# Auto-instrument — all OpenAI calls now traced with zero business logic change
OpenAIInstrumentor().instrument()

# Supports: OpenAI, Anthropic, LangChain, LlamaIndex, DSPy, Guardrails, Bedrock
```

### Phoenix Evals — The Key Differentiator

```python
import phoenix.evals as evals
from phoenix.evals import (
    HallucinationEvaluator, QAEvaluator, RelevanceEvaluator, run_evals,
)
from phoenix.session.evaluation import get_qa_with_reference

# Pull production traces as a DataFrame
queries_df = get_qa_with_reference(px.active_session())
# Columns: input, output, reference (retrieved context), latency, cost, ...

# Run evaluators (each is an LLM-as-judge prompt template)
results = run_evals(
    dataframe=queries_df,
    evaluators=[
        HallucinationEvaluator(model=OpenAIModel("gpt-4o")),
        QAEvaluator(model=OpenAIModel("gpt-4o")),
        RelevanceEvaluator(model=OpenAIModel("gpt-4o")),
    ],
    provide_explanation=True,
)

# Scores attached back to traces in Phoenix UI
px.log_evaluations(results)
```

**How Phoenix's hallucination evaluator works internally** (from source):

```
Template:
  "In this task, you will be presented with a query, a reference text and an answer.
   The answer is generated to the question based on the reference text.
   Is there any information in the answer that is NOT supported by the reference text?

   [BEGIN DATA]
   Query: {input}
   Reference: {reference}
   Answer: {output}
   [END DATA]

   Your response must be a single word, either 'factual' or 'hallucinated', and
   should not contain any text or characters aside from that word."
```

The evaluator runs this for every trace row in the DataFrame. Results feed back as scores visible in the Phoenix UI.

## Minimal Custom Observability

When you need observability without a platform dependency:

```python
import time, uuid, json
from dataclasses import dataclass, field, asdict
from typing import Optional

@dataclass
class LLMSpan:
    span_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    name: str = ""
    model: str = ""
    input_tokens: int = 0
    output_tokens: int = 0
    cached_tokens: int = 0
    latency_ms: float = 0.0
    cost_usd: float = 0.0
    metadata: dict = field(default_factory=dict)

@dataclass
class Trace:
    trace_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    user_id: str = ""
    input: str = ""
    output: str = ""
    latency_ms: float = 0.0
    spans: list = field(default_factory=list)
    metadata: dict = field(default_factory=dict)

# Simple in-process context
_current_trace: Optional[Trace] = None

def traced_llm_call(prompt_messages, model="gpt-4o", trace=None):
    start = time.perf_counter()
    response = openai_client.chat.completions.create(
        model=model, messages=prompt_messages
    )
    latency = (time.perf_counter() - start) * 1000

    usage = response.usage
    cost = (usage.prompt_tokens * 2.50 + usage.completion_tokens * 10.0) / 1_000_000

    span = LLMSpan(
        name="llm_generation",
        model=model,
        input_tokens=usage.prompt_tokens,
        output_tokens=usage.completion_tokens,
        cached_tokens=getattr(getattr(usage, "prompt_tokens_details", None),
                               "cached_tokens", 0),
        latency_ms=latency,
        cost_usd=cost,
    )
    if trace:
        trace.spans.append(span)

    return response, span

# Flush to your store (Postgres, ClickHouse, S3)
def flush_trace(trace: Trace):
    db.insert("llm_traces", {
        "trace_id": trace.trace_id,
        "user_id": trace.user_id,
        "input": trace.input[:2000],
        "output": trace.output[:2000],
        "latency_ms": trace.latency_ms,
        "total_cost_usd": sum(s.cost_usd for s in trace.spans),
        "total_input_tokens": sum(s.input_tokens for s in trace.spans),
        "spans": json.dumps([asdict(s) for s in trace.spans]),
    })
```

This is the skeleton every observability tool is built on. Knowing it helps you understand what any SDK is doing under the hood.

## Revision Anchors

- **Data model hierarchy**: Trace (one user request) → Spans (pipeline steps). Trace has user_id/session_id. Each span has latency, tokens, cost. All tools build on this OpenTelemetry model.
- **Langfuse**: SDK-based, ClickHouse + Postgres backend, full LLMOps (traces + eval + prompt management). Self-hostable. Decorator pattern is the cleanest integration.
- **Helicone**: Proxy-based (Cloudflare Workers), zero code change (just change base_url), <5ms latency overhead. Limited to LLM API calls only — can't trace retrieval or custom logic.
- **Phoenix**: OTel-native, evaluation-first. `run_evals()` runs LLM-as-judge on DataFrames of traces. Best for systematic quality measurement.
- **Practical path**: Helicone first (instant visibility) → Langfuse when you need full pipeline tracing + prompt management → Phoenix when you need systematic evaluation.
- **Minimum alert set**: P95 latency, hourly cost, single query cost spike, error rate, empty response rate.
