# Admin and Configuration Questions

## How to use this

Each answer is written as it should be delivered — the reasoning, not the definition. The one-line version is what a junior candidate says; the rest is what distinguishes the rest.

---

## Data model

**Master-detail versus lookup — when do you choose each?**

Master-detail when the child cannot exist without the parent and should inherit its access. It gives roll-up summaries, cascade delete, and — the part people miss — **the child has no sharing rows of its own**, because access derives from the parent. At eight million child records that is a substantial difference in sharing table size.

Lookup when the lifecycle is independent, when reparenting is common, or when the child needs its own sharing.

The tension worth naming: master-detail reduces sharing volume and increases lock contention, because every child save locks the parent for roll-up recalculation. If the parent distribution is even, master-detail. If one parent has 300,000 children, the contention makes lookup the safer choice even with the sharing cost.

**What is a junction object, and what would you watch for at scale?**

A custom object with two master-detail relationships, modelling many-to-many. Machine Coverage joining Assets to Service Contracts, in our case.

At scale the junction is frequently the highest-volume object in the model — 100,000 assets and 20,000 contracts can produce two million junction records — and it is often designed without that in mind.

Two things I would do: master-detail on both sides so it generates no sharing rows, and a unique composite key field, because a trigger-based duplicate check misses duplicates arriving together in the same insert. The database enforces uniqueness regardless of how the record arrives.

**When would you use a big object?**

Append-only, high-volume data that needs to be retained and rarely read — telemetry, archived transactions, audit history beyond the standard retention.

The design decision is the index, defined at creation and immutable. Queries must filter on the index fields left to right without gaps, so getting it wrong means the data is written and unqueryable. That is the question to settle before creating it: how will this be read?

No updates, no triggers, no reporting in the usual way. It is a store, not an object.

## Security and sharing

**Walk me through the security model.**

Four layers, and they combine.

Object level — CRUD, from profiles and permission sets. Field level — which fields the user can see or edit. Record level — sharing: OWD, role hierarchy, sharing rules, manual, team, Apex. And then Apex, which enforces none of it by default.

The order matters: object access first, then field, then record. A user with no read on the object never reaches the sharing question.

The point I would make is that Apex is the gap. A class with no sharing keyword runs without sharing when it is the entry point, and a query with no `WITH USER_MODE` ignores field-level security entirely. So an `@AuraEnabled` method is effectively a public endpoint, and every control has to be explicit.

**Profiles versus permission sets — what is your position?**

Permission sets for everything, and profiles kept minimal.

The practical reasons: permission sets are additive and combinable, so a user gets exactly what their role needs without a profile per combination. They deploy completely, whereas a profile retrieval only includes permissions for metadata also in the retrieval — which is how a deployment silently removes permissions.

Salesforce is moving this way too; profiles are being reduced to the settings that genuinely need one.

Permission set groups are worth mentioning — bundling several sets by job function, with a muting set for the exceptions.

**How does the role hierarchy actually work, and what would you watch at scale?**

Grants a manager access to what their subordinates own, upward through the hierarchy.

At scale the thing to know is that it is **materialized** — sharing is stored as rows, not computed at query time. Every level above a record's owner is a row. So hierarchy depth multiplies sharing table size, and moving a user in the hierarchy recalculates sharing for every record they own.

I have seen a role change lock an org for three hours because the user owned 340,000 opportunities. The fix is redistributing ownership, and preventively, keeping integration users out of the hierarchy entirely — a user with no role generates no hierarchy shares.

**How would you give a user access to one specific record?**

Manual sharing for a one-off, if the OWD is private. Apex sharing where it is driven by logic, with a custom row cause so it survives an ownership change — a share with the default `Manual` cause is removed when the owner changes.

If it is a recurring pattern, a criteria-based sharing rule granting to a public group is better than either, because the platform maintains it.

## Automation

**Flow or Apex — how do you decide?**

The honest answer is that it depends on four things: complexity, volume, who maintains it, and whether it needs to be testable.

Flow for straightforward record automation an administrator will own — field updates, record creation, screen-based processes, approval routing. Before-save flows for same-record field updates specifically, because they avoid a second save.

Apex for complex logic, for anything needing real bulk safety, for callouts, and for anything where the correctness matters enough to want a test suite. Flow testing is genuinely weaker — native tests run one record, screen flows cannot be tested at all — and that asymmetry is a real input to the decision.

The pattern I like is a flow orchestrating and invocable Apex doing the work. The administrator owns the process, the developer owns the logic, and the logic has tests.

The thing I would avoid is both on the same object writing the same field. Before-save flows run before before-triggers, after-save flows run after after-triggers, and neither order is configurable. Debugging that is unpleasant.

**Order of execution — walk me through it.**

Broadly: system validation, before-save flows, before triggers, custom validation, the record saved but not committed, after triggers, assignment rules, auto-response, workflow field updates, escalation, after-save flows, entitlements, roll-up recalculation, criteria-based sharing, commit, then post-commit — email, async jobs, platform events.

The implications matter more than the list. Before triggers run before validation rules, so a before trigger can populate a field a validation rule requires. After-save flows run after after-triggers, so a trigger cannot see what a flow set. And roll-up recalculation sends the parent through its own save pipeline, which is where a cascade starts — that is usually the explanation for a CPU limit failure on an operation that looks trivial.

**A validation rule needs to check a field on a related object. Options?**

Cross-object formula in the rule, if it is a straightforward parent traversal — up to the formula size limit.

Where it needs more, a before trigger with `addError` on the field, which also gives a better error message and can be bulk-aware.

A third option people forget: a roll-up summary or a denormalized field maintained by automation, then a simple validation rule on it. That is frequently the cleanest, because the value is then also filterable and reportable.

## Reporting

**When would you use a custom report type?**

When a standard one does not give what is needed — more than two levels of relationship, fields from a lookup that standard types omit, or an outer join the standard type does not provide.

The design decision is the A/B relationship: "may or may not have" is an outer join, "must have" is inner. Choosing B when A was meant silently excludes records, and the user reports the numbers as wrong without knowing why. That is the most common report type defect.

The capability worth mentioning is adding fields via lookup — it removes a whole category of formula fields created solely for reporting, which cost compile size and query time on every read.

**What is a reporting snapshot, and when would you use one?**

A scheduled job writing a report's summary rows into a custom object, building a history the source data cannot provide.

The case is trend reporting on something that changes — "how many open claims did we have last Tuesday" when the claims have since closed. Without a snapshot that history does not exist.

**A report on a large object times out. What do you do?**

Same as any query: check whether the filter is selective at all. If it returns most of the table, no index helps.

Then the anti-patterns — `not equal to` cannot use an index, so rewriting as a positive list of values. A date bound, which is the most common fix. Fewer fields, because formula fields are computed per row on read.

Then a custom index or a skinny table, with evidence for the support request.

But the answer that fixes everything at once is archiving. Reducing the object from eight million to two million changes what counts as selective, and improves every other query on the object at the same time.

## Deployment

**How do you move changes between orgs?**

Source control and the CLI, with change sets only where there is no alternative.

The practical setup: metadata in Git, branches mapped to orgs, `sfdx-git-delta` generating a manifest from the diff so only what changed deploys, and CI validating on every pull request with `deploy validate` — which runs the deployment and its tests without committing.

For a production release, validate in advance and quick-deploy in the window. A thirty-minute test run happens on Thursday; the release takes two minutes on Saturday.

The thing to be careful about is profiles. Retrieving one only includes permissions for metadata also in the retrieval, so a profile diff removing a hundred lines is usually a retrieval artefact rather than an intended change. Permission sets in source control, profiles managed carefully or manually.

**What does not deploy?**

Custom Setting records — the definition does, the data does not, which produces a null pointer immediately after a release if nothing null-checks. Named Credential secrets. Connected app consumer keys. Certificate private keys. Scheduled job schedules. Deliverability settings. Skinny tables and custom indexes, which are per org.

All of those are manual post-deployment steps, and the ones nobody documents are the ones that break production. I would put them in a versioned anonymous Apex script so they are repeatable rather than remembered.

## Data management

**How would you load two million records?**

Bulk API 2.0, upserting on an external ID so a resubmission is safe.

The preparation matters more than the tool. Sort the file by parent Id — that alone resolves most lock contention, because children of the same parent land in the same batch. Disable non-essential automation for the load user with a hierarchy Custom Setting, and reconcile afterwards with a batch job, which is far faster than the trigger doing it per record. Suspend sharing calculation if the object is private. Disable field history where the history has no meaning.

Load in dependency order, verify counts between objects before proceeding, and use `Parent__r.External_Id__c` for lookups so there is no ID-mapping pass.

Afterwards, reconcile on totals as well as counts — a matching count with a wrong total means a column shifted.

And rehearse it in a Full sandbox first, because the rehearsal produces the duration that determines the window.

**How would you find and fix duplicates?**

Duplicate rules and matching rules prevent them going forward — that is the first move, because cleaning up while they are still being created is futile.

For the existing ones, a report grouped by the matching field, or an aggregate query, to quantify. Then merge, which is supported on Account, Contact, Case, and Lead only.

Two things to watch on merge: the master's field values win, so preserving a better value from the duplicate means updating the master before merging. And external systems hold the dead Ids — which is what an external ID field solves, by letting reconciliation happen on the source key rather than the Salesforce Id.

At volume, merge does not bulkify — it is one DML per call — so a large deduplication is a batch job with a small scope size.

## The questions behind the questions

Most of these are testing one of four things:

**Do you know the mechanism exists?** The junior bar.

**Do you know why it works that way?** Sharing is materialized; limits are a fairness mechanism; before triggers run before validation.

**Do you reason about tradeoffs?** Master-detail versus lookup, flow versus Apex, index versus archive.

**Have you been burned?** The specific detail — the profile retrieval artefact, the null Custom Setting after deployment, the role change that locked the org.

**The fourth is what marks experience**, and it cannot be memorized convincingly. It comes from having built things.
