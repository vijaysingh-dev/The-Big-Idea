# CSS Architecture

Every CSS methodology exists to solve the same two problems: **global scope** (any selector can affect any element) and **specificity escalation** (overriding requires ever-more-specific selectors). The approaches differ in how they solve them and what they cost.

## BEM

A naming convention that simulates scoping through discipline.

```css
.card { }
.card__title { }
.card__body { }
.card--featured { }
.card__title--truncated { }
```

Block, element, modifier. Every selector is a single class, so specificity is flat `(0,1,0)` everywhere and the cascade never fights itself ([[10.1 - The Cascade Specificity and Inheritance]]).

**Pros:** no tooling, works anywhere, class names document structure, trivially debuggable.

**Cons:** long class names, nothing *enforces* the convention, no dead-code detection, and it does not prevent collisions — it just makes them unlikely.

Still the right choice for projects without a build step, and the underlying naming discipline remains useful inside other approaches.

## CSS Modules

Build-time scoping. Class names are rewritten to be unique.

```css
/* Card.module.css */
.card { padding: 1rem; }
.title { font-weight: 600; }
```

```jsx
import styles from "./Card.module.css";
<div className={styles.card}><h2 className={styles.title} /></div>
```

The output is `Card_card__a1b2c`. Collisions are impossible by construction, and unused classes are detectable.

```css
:global(.third-party) { }
.title { composes: heading from "./typography.module.css"; }
```

**Pros:** real scoping, plain CSS, zero runtime, works with any framework, good editor tooling.

**Cons:** dynamic values still need inline styles or custom properties, and sharing tokens requires a separate mechanism.

The usual pattern for dynamic values keeps CSS in the stylesheet and passes data through custom properties:

```jsx
<div className={styles.bar} style={{ "--progress": `${pct}%` }} />
```

```css
.bar::after { width: var(--progress); }
```

## Utility CSS (Tailwind)

Composition from single-purpose classes.

```jsx
<div className="flex items-center gap-4 rounded-lg bg-white p-4 shadow-sm">
```

**Pros:** no naming decisions, no unused CSS (the build only emits used utilities), stylesheet size plateaus as the app grows, constraints come from the design token scale rather than discipline, and colocation means deleting a component deletes its styles.

**Cons:** markup is verbose, dynamic class names must be complete strings for the scanner to find them, and reviewing a diff of class strings is harder than reviewing a stylesheet.

The dynamic class trap:

```jsx
// Broken — the scanner cannot see this
<div className={`text-${color}-500`} />

// Correct — full class names present in source
const colors = { red: "text-red-500", blue: "text-blue-500" };
<div className={colors[color]} />
```

Repetition is handled by extracting **components**, not by extracting CSS classes. A `<Button>` component is the reuse unit; `@apply` recreates the problems utilities were meant to solve and the Tailwind maintainers advise against it.

## CSS-in-JS

Styles authored in JavaScript, scoped automatically.

```jsx
const Button = styled.button`
  padding: ${p => (p.size === "lg" ? "12px 24px" : "8px 16px")};
  background: ${p => p.theme.primary};
`;
```

**Runtime CSS-in-JS** (styled-components, Emotion) generates and injects styles during render. It gives full access to props and JavaScript logic, but costs bundle size, render-time work, and it interacts badly with React Server Components — which is why its popularity has declined sharply.

**Zero-runtime CSS-in-JS** (vanilla-extract, Panda, Linaria) extracts styles to static CSS at build time:

```ts
// styles.css.ts
export const button = style({
  padding: "8px 16px",
  ":hover": { background: vars.color.brandDark },
});
```

Type-safe, no runtime cost, but requires a build integration and variants must be enumerated rather than computed freely.

## Choosing

| Situation | Reasonable choice |
| --- | --- |
| No build step | BEM |
| Component-scoped, plain CSS preferred | CSS Modules |
| Fast iteration, design-system constraints | Tailwind |
| Type safety, complex variants | vanilla-extract or Panda |
| Server Components | anything zero-runtime |

The most common production combination is Tailwind or CSS Modules for components, custom properties for tokens, and cascade layers for ordering.

## Structure that survives

Independent of methodology, some things consistently help.

**Tokens in one place**, as custom properties on `:root`, with a primitive layer and a semantic layer ([[10.4 - Units Custom Properties and Theming]]).

**Cascade layers** to make ordering explicit rather than dependent on import sequence:

```css
@layer reset, tokens, base, components, utilities;
```

Utilities declared last always win, without `!important` and without specificity tricks.

**Component colocation.** `Card.tsx` next to `Card.module.css`, so deleting the component deletes its styles. Directory-based organization (`styles/components/card.css`) reliably accumulates dead CSS.

**A modern reset** — normalize.css is largely obsolete; the useful pieces now are `box-sizing`, margin removal, `font: inherit` on form controls, `max-width: 100%` on media, and `line-height` defaults. Josh Comeau's reset and Andy Bell's are both short and well-reasoned.

## Performance considerations

**CSS is render-blocking.** The browser will not paint until all stylesheets in `<head>` have loaded and the CSSOM is built ([[13.1 - The Critical Rendering Path]]).

Practical mitigations:

- **Critical CSS inlined** in `<head>`, the rest loaded asynchronously — worthwhile for landing pages, over-engineering for most apps.
- **Route-level CSS splitting**, which bundlers do automatically for CSS Modules and CSS-in-JS.
- **Media-conditional loading**: `<link rel="stylesheet" href="print.css" media="print">` does not block rendering.
- **`content-visibility: auto`** on offscreen sections skips their layout and paint entirely until they scroll into view — one of the highest-impact single properties for long pages.

Unused CSS is measurable in DevTools' Coverage panel. Note that "unused" there means "not used on this page right now", so a component library will always show high unused percentages on any single view.

## How senior engineers actually use this

**They pick one approach and enforce it.** Mixing BEM, modules and inline styles in one codebase produces the worst of each. Consistency matters more than which is objectively best.

**They keep specificity flat.** Whatever the methodology, nearly every selector should be a single class.

**They put tokens in custom properties regardless of methodology**, since that is what makes theming and design-system alignment possible at runtime.

**They use cascade layers** to end ordering arguments structurally.

**They colocate styles with components** so dead code is deleted along with the code that used it.

## Common pitfalls

- Mixing methodologies within one codebase.
- Nesting three or four levels deep, producing high-specificity selectors that need `!important` to override.
- `@apply` in Tailwind, recreating the maintenance problem utilities avoid.
- Dynamic class name construction that build-time scanners cannot see.
- Runtime CSS-in-JS in a Server Component tree.
- Global stylesheets that grow indefinitely because nobody can prove a rule is unused.
- Reading the Coverage panel's unused percentage as waste without accounting for other routes.

## Interview angle

"How would you structure CSS for a large application" is a design question. Cover the two underlying problems — global scope and specificity — then compare approaches by how they solve them and what they cost, rather than advocating one. Mentioning cascade layers, token architecture and colocation shows you think about maintenance rather than syntax. Being able to explain why runtime CSS-in-JS has fallen out of favour, specifically around Server Components and render cost, signals current awareness.
