# The Rendering Cycle

Rendering is a step *inside* the event loop, not a separate process. Understanding where it sits explains why some code causes visible jank and other code does not.

## Where rendering happens in the loop

Per turn of the loop, in order:

```
1. Run one task
2. Drain all microtasks
3. If it is time for a frame:
     a. run requestAnimationFrame callbacks
     b. style calculation
     c. layout (reflow)
     d. paint
     e. composite
4. If time remains before the next frame, run requestIdleCallback
```

Steps 3b–3e are the browser's pixel pipeline, covered in depth in [[13.1 - The Critical Rendering Path]] and [[13.2 - Reflow Repaint and Composite]].

## The frame budget

At 60 Hz the browser wants a new frame every **16.7 ms**. On a 120 Hz phone that drops to 8.3 ms. The browser itself needs a few milliseconds for style, layout, paint and composite, so the realistic budget for your JavaScript is closer to **10 ms** per frame.

Exceed it and a frame is dropped: the previous frame stays on screen for two intervals, which the eye reads as stutter. Drop several in a row during a scroll or animation and it reads as the app being broken.

Note that the browser only produces a frame when something changed and only when the display is ready for one. An idle page runs no rendering steps at all.

## requestAnimationFrame

`requestAnimationFrame` (rAF) schedules a callback to run immediately before the next frame's style and layout. It is the correct primitive for anything visual.

```js
function animate(timestamp) {
  const progress = Math.min((timestamp - start) / duration, 1);
  el.style.transform = `translateX(${progress * 300}px)`;
  if (progress < 1) requestAnimationFrame(animate);
}

const start = performance.now();
requestAnimationFrame(animate);
```

Why rAF beats `setTimeout(fn, 16)`:

- It is synchronized to the display refresh, so writes land exactly once per frame rather than drifting.
- It automatically pauses in background tabs and on hidden elements, saving battery.
- It adapts to 90 Hz and 120 Hz displays without code changes.
- The timestamp argument is the frame's start time, so animations can be driven by elapsed time rather than frame count, which keeps them correct even when frames are dropped.

That last point matters: never advance an animation by a fixed increment per callback. If frames drop, a time-based animation stays on schedule while a frame-based one runs in slow motion.

## requestIdleCallback

`requestIdleCallback` runs low-priority work in the leftover time after a frame is committed.

```js
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && queue.length) {
    process(queue.shift());
  }
  if (queue.length) requestIdleCallback(handleIdle);
}, { timeout: 2000 });
```

Good uses: sending analytics, prefetching data for a likely next route, warming caches, cleaning up. Bad uses: anything that must happen by a deadline, anything visual, anything on the critical path. It is unsupported in Safari, so treat it as an enhancement with a `setTimeout` fallback.

## Reads and writes in the same frame

A layout-triggering read forces the browser to compute layout *right now*, even though it planned to do it later in the frame. Interleaving reads and writes therefore causes repeated synchronous layouts:

```js
// Forces layout on every iteration
elements.forEach(el => {
  el.style.height = el.offsetHeight * 2 + "px";
});

// Read everything, then write everything
const heights = elements.map(el => el.offsetHeight);
elements.forEach((el, i) => {
  el.style.height = heights[i] * 2 + "px";
});
```

This is **layout thrashing**, treated fully in [[13.3 - Layout Thrashing]]. The rule is: batch all reads, then all writes.

## What this means for React

React's concurrent renderer exists precisely to fit inside this cycle. It breaks rendering into small units of work and yields between them so the browser can produce frames, using the scheduler described in [[18.5 - Concurrent Rendering and the Scheduler]]. `useTransition` and `useDeferredValue` are the user-facing controls over that behavior.

A practical consequence: `useEffect` runs *after* paint, while `useLayoutEffect` runs *before* paint, inside the same frame. That is why measuring DOM and adjusting position belongs in `useLayoutEffect` — doing it in `useEffect` causes a visible flash of the pre-adjustment layout ([[17.5 - useLayoutEffect vs useEffect]]).

## How senior engineers actually use this

**They animate only `transform` and `opacity`.** Those two properties can be handled by the compositor thread, skipping layout and paint entirely, which means animations keep running smoothly even when the main thread is busy. Animating `width`, `top` or `margin` forces layout every frame.

**They prefer CSS animations and the Web Animations API over rAF loops.** Declarative animations can be run off the main thread. A rAF loop cannot. Reach for JS animation only when the values genuinely depend on runtime state.

**They measure frames, not functions.** The Performance panel shows dropped frames directly, and the Rendering tab's "Frame rendering stats" overlay gives a live FPS meter. Reasoning about which code "feels slow" without recording a profile wastes time.

**They defer non-urgent work explicitly.** Analytics beacons, prefetches and logging go into idle callbacks or `sendBeacon`, never into a click handler.

## Common pitfalls

- Driving animations with `setInterval`, which drifts against the refresh rate and keeps running in background tabs.
- Advancing animation state by a fixed delta per rAF callback instead of by elapsed time.
- Doing heavy work inside a rAF callback. Whatever runs there is directly in the frame's critical path.
- Assuming `requestIdleCallback` will run soon. Under sustained load it may not run at all without a `timeout` option.
- Reading `offsetHeight`, `getBoundingClientRect` or `scrollTop` inside a loop that also writes styles.

## Interview angle

Expect "what is requestAnimationFrame and why not setTimeout", and "why does my animation stutter". Strong answers place rendering inside the event loop, cite the ~16.7 ms budget, explain that rAF is refresh-synchronized and pauses when hidden, and mention that `transform`/`opacity` avoid layout and paint by running on the compositor. Connecting it to dropped frames and INP shows you have debugged this in production rather than read about it.
