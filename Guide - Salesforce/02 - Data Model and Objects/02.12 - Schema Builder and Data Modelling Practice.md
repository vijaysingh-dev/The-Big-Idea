# Schema Builder and Data Modelling Practice

## Schema Builder

A visual tool in Setup showing objects as boxes and relationships as lines. You can drag objects onto a canvas, create fields and relationships directly, and see the shape of a model.

What it is good for: understanding an unfamiliar org, and explaining a model to non-technical people. Opening Schema Builder on a legacy org and dragging in the six objects a project touches is one of the fastest ways to orient yourself.

What it is not good for: designing. It has no layout memory worth relying on, it becomes unreadable past about fifteen objects, and it cannot show you the things that matter most — sharing implications, volume, or which relationships are actually used.

Design on paper or in a diagramming tool, then build. Use Schema Builder to read, not to think.

## A working method for data modelling

The sequence below is what experienced engineers actually do, and the ordering matters more than any individual step.

**1. List the nouns the business uses.** Literally write down the words that appear in requirements. Machine, warranty claim, service contract, technician, part, shipment. Each is a candidate object.

**2. Map each noun onto a standard object if one fits.** This is the step that saves the most work. A "deal", "sale", or "project pipeline" is Opportunity. A "customer", "supplier", or "partner" is Account. A "ticket", "complaint", or "incident" is Case. Accept imperfect fits. See [[02.2 - Standard Objects and the Core CRM Data Model]].

**3. For each remaining noun, ask whether it needs its own object at all.** Many do not. A list of five statuses is a picklist. A set of three flags is three checkboxes. A single extra piece of information is a field on an existing object. The bar for a new object is that it has its own lifecycle, its own fields, and its own records users create.

**4. Draw the relationships and name their cardinality.** One machine to many claims. Many machines to many contracts. Write it out in words before choosing field types, because the words determine the type.

**5. Choose lookup or master-detail for each.** Apply the decision sequence from [[02.7 - Relationships - Lookup vs Master-Detail]]. Ask specifically: whose sharing should govern this child, and should deleting the parent remove it.

**6. Decide the sharing model for every object now, not later.** Private, Public Read Only, or Public Read/Write. Tightening it later forces a full sharing recalculation across all existing records, which on a large object is a scheduled maintenance event.

**7. Estimate volume per object over five years.** Not today's count. An object receiving 50,000 rows a month is at three million in five years, which changes indexing, archiving, and query design. See section 23.

**8. Identify the external identifiers.** For every object that will be integrated, decide the field that holds the source system's key and mark it as an external ID before any data arrives.

**9. Walk through the actual business processes against the model.** Take a real scenario end to end and check every step is representable. This is where missing objects and missing fields surface, and it is much cheaper than discovering them after build.

## A worked example

Requirement, as stated by a manufacturing business:

> We sell industrial machines. Customers buy service contracts covering some or all of their machines. When a machine breaks under warranty, the customer raises a claim. Technicians visit, use spare parts, and we track the cost. Contracts renew annually and we want to forecast renewal revenue.

Working through the method:

**Nouns:** customer, machine, service contract, claim, technician, spare part, visit, renewal.

**Standard object mapping:**
- Customer → Account
- Technician → User, or Contact if they are external contractors
- Spare part → Product2, with pricing through PricebookEntry
- Renewal → Opportunity, since it is forecastable revenue and Opportunity brings forecasting for free
- Claim → Case is a candidate, and worth serious consideration since Case brings entitlements, milestones, escalation, and Omni-Channel routing

That last one deserves a pause. Modelling the claim as a Case rather than a custom object gets you the entire Service Cloud toolkit at no build cost. The counter-argument is that a warranty claim has a financial approval dimension a Case does not naturally model. A common resolution is Case for the service interaction and a custom object for the financial claim, linked — but the decision should be explicit, not accidental.

**Remaining custom objects:**
- `Machine__c` — has its own lifecycle, serial numbers, install dates, warranty terms
- `Service_Contract__c` — has its own dates, coverage levels, pricing
- `Machine_Coverage__c` — junction between machine and contract
- `Claim_Part__c` — parts used on a claim, with quantity and cost

**Visit** is probably not an object. It is an Event, or a field on the claim. Resist the extra object until someone demonstrates it needs its own records.

**Relationships:**

```
Account --lookup--> Machine__c            (machines survive account deletion; service owns them)
Account --lookup--> Service_Contract__c
Machine__c --master-detail--> Machine_Coverage__c <--master-detail-- Service_Contract__c
Machine__c --lookup--> Case               (claims relate to a machine but are Cases)
Case --master-detail--> Claim_Part__c     (parts are part of the claim)
Product2 --lookup--> Claim_Part__c        (parts reference the catalogue)
Service_Contract__c --lookup--> Opportunity  (renewal opportunity references the contract)
```

Each choice has a reason. Machines are lookups from Account because service owns them and they must survive if an account record is merged. Coverage is master-detail on both sides so both parents get roll-ups and orphans are impossible. Claim parts are master-detail on Case because a part line is meaningless without its claim, and this gives a free roll-up of total part cost.

**Volume estimate:** 40,000 machines, growing 8,000 a year. Contracts roughly 5,000, renewed annually, so 5,000 new opportunities a year. Claims perhaps 15,000 a year, which is 75,000 Cases in five years. Claim parts maybe three per claim, so 225,000. All comfortable, none needing big objects or archiving in the near term — but the claim parts number is the one to watch.

**External IDs:** `ERP_Machine_Id__c` on Machine, `ERP_Contract_Number__c` on Service Contract, `ERP_Part_Code__c` on Product2. The ERP is the source of truth for all three.

**Sharing:** Machine private, because not every sales user should see every customer's equipment. Service Contract private. Coverage inherits from Machine as its primary master.

## Documenting the model

An entity relationship diagram that lives somewhere findable, showing objects, relationship types, and cardinality. Keep it updated, or it becomes actively misleading, which is worse than not having one.

Alongside it, a short document per object stating what it represents, who owns records, what the sharing model is, and what the expected volume is. This is the thing that helps the person who inherits the org in three years, and it takes an hour.

## Common modelling mistakes

**Building custom objects that duplicate standard ones.** The single most expensive mistake. `Deal__c` next to Opportunity, `Company__c` next to Account.

**Modelling the current user interface rather than the domain.** "They have a spreadsheet with these twelve columns" is not a data model. Ask what each column means and where it belongs.

**One giant object.** Two hundred fields on a single object, half of them relevant only to a subset of records, is a sign that two or three objects were merged. It hits field limits, makes layouts unusable, and inflates query heap.

**Too many objects.** The opposite failure. Every relationship is a join, every join is query cost, and every object is another sharing model to maintain.

**Ignoring volume.** A model that is elegant at 100,000 records and unusable at 20 million. Volume estimates belong in the design, not in a later performance review.

**Deferring the sharing model.** Almost always the most expensive thing to change later, because it means recalculating access on every existing record. Decide it while the object is empty.
