# Coroutines Tasks and Futures

#backend #python #asyncio

> **In one line:** A coroutine is a pausable function, a Future is a box that will hold a result later, and a Task is the thing that drives a coroutine and puts its result in the box. Most async bugs come from confusing the three.

---

## The Idea

Three objects. People use the words interchangeably and then get confused by error messages.

| Object | What it is | Runs on its own? |
|---|---|---|
| **Coroutine** | A function that can pause. Created by calling an `async def` | No. Something must drive it |
| **Future** | A placeholder for a result that will exist later | No. It just holds a value |
| **Task** | A Future that also drives a coroutine | Yes. The loop steps it |

`Task` is a subclass of `Future`. That single fact explains a lot of asyncio's API: anywhere you can pass a Future, you can pass a Task.

```python
async def work():
    return 42

coro = work()                       # coroutine object. Nothing has run
task = asyncio.create_task(coro)    # now the loop will drive it
result = await task                 # 42
```

⚠️ **Calling an async function runs none of its body.** If you have ever written `fetch_data()` without `await` and wondered why nothing happened, this is why. Python warns — `RuntimeWarning: coroutine was never awaited` — and that warning is worth turning into an error in tests.

---

## How It Really Works

### A coroutine is a generator with a flag

```python
async def work():
    await asyncio.sleep(1)
    return 42

c = work()
type(c)                        # <class 'coroutine'>
c.__code__.co_flags & 0x80     # CO_COROUTINE flag is set
c.send(None)                   # drives it forward, same as a generator
```

You drive it the same way you drive a generator: `send()` to advance, `throw()` to inject an exception, `close()` to shut it down. `await` compiles down to essentially the same bytecode as `yield from`.

### What `await` actually does

Two very different things, depending on what you await.

**Awaiting a coroutine does not touch the loop at all:**

```python
async def a():
    return 1

async def b():
    x = await a()        # direct call. The loop never sees this
    return x + 1
```

This is a plain function call that happens to be able to pause. No suspension, no scheduling.

**Awaiting a Future is what suspends:**

```python
async def c():
    await some_future    # yields the Future all the way up to the Task
```

The Future travels up through every enclosing coroutine to the Task driving them. The Task attaches a callback and stops. Later, someone calls `future.set_result(...)`, the callback fires, the Task resumes the coroutine, and the value appears where the `await` was.

💡 **This is the key insight of the whole note.** Awaiting is not itself a yield point. A chain of a hundred `await`s on coroutines suspends zero times. Only a Future suspends. And at the bottom of every real suspension is a Future that the event loop will complete when a socket becomes readable or a timer expires.

That means this function never yields control, no matter how many awaits it has:

```python
async def looks_async_isnt():
    total = 0
    for i in range(10_000_000):
        total += await add_one(i)     # add_one is `async def` but never awaits a Future
    return total
```

It blocks the entire loop for its full duration. See [[01.6 - The Blocking Call Problem]].

### The Task step cycle

This is the loop that runs your code. Understanding it once removes most async confusion.

```
Task.__step(value):
    result = coro.send(value)          # run until the next Future

    if coro returned:                  # StopIteration
        self.set_result(value)         # Task is done

    elif result is a Future:
        result.add_done_callback(self.__wakeup)
        # Task now sits idle. The loop moves on

Task.__wakeup(future):
    self.__step(future.result())       # resume, passing the value in
```

Concretely, for `await asyncio.sleep(1)`:

```
1. sleep() creates a Future
2. sleep() calls loop.call_later(1, future.set_result, None)
3. sleep() awaits the Future → yields it up to the Task
4. Task attaches __wakeup, then stops. The loop runs other things
5. One second later, the timer fires, set_result runs
6. set_result schedules the done-callback via call_soon
7. Next loop iteration, __wakeup runs, Task steps the coroutine
8. Your code resumes on the line after the await
```

⚠️ Note steps 6 and 7. Completing a Future does **not** immediately resume the coroutine. It schedules the resumption for the next loop iteration. So `await asyncio.sleep(0)` is a real yield point that gives other tasks a turn without waiting — it is the standard way to be polite in a long loop.

### Creating a Task starts it, but not immediately

```python
async def main():
    task = asyncio.create_task(work())   # scheduled via call_soon, has NOT run yet
    print("A")                            # this prints first
    await asyncio.sleep(0)                # now the loop gets a turn — work() starts
    print("B")
```

`create_task` puts the first step on the ready queue. Nothing runs until the current coroutine yields.

## The Bugs

### Bug 1 — Sequential when you meant parallel

```python
# 3 seconds
a = await fetch(url1)
b = await fetch(url2)
c = await fetch(url3)

# 1 second
a, b, c = await asyncio.gather(fetch(url1), fetch(url2), fetch(url3))
```

The most common async performance bug there is, and it is invisible in code review because both versions look reasonable.

⚠️ Watch for it hiding inside a loop:

```python
# Sequential — one at a time
results = [await fetch(u) for u in urls]

# Parallel
results = await asyncio.gather(*[fetch(u) for u in urls])
```

### Bug 2 — Fire and forget, garbage collected

```python
async def handler():
    asyncio.create_task(send_analytics())   # nobody holds a reference
    return {"ok": True}
```

The loop holds only a **weak reference** to tasks. If nothing else references your task, it can be garbage collected mid-execution. It vanishes, sometimes, under load, non-deterministically. This is a genuinely nasty bug because it is rare enough to look like a network problem.

```python
_background: set[asyncio.Task] = set()

def spawn(coro):
    task = asyncio.create_task(coro)
    _background.add(task)
    task.add_done_callback(_background.discard)
    return task
```

Better still, use a `TaskGroup` so the task's lifetime is scoped — [[01.7 - Cancellation and Structured Concurrency]].

### Bug 3 — Swallowed exceptions

```python
task = asyncio.create_task(might_fail())
# never awaited
```

If the task raises and nobody ever calls `task.result()`, the exception sits in the Future. You get a "Task exception was never retrieved" message when it is garbage collected — possibly minutes later, possibly never, possibly not at all if the process exits first.

```python
loop.set_exception_handler(lambda loop, ctx: log.error("async error", extra=ctx))
```

Set this in every service. It is your last line of defence against silent failure.

### Bug 4 — `gather` and partial failure

```python
results = await asyncio.gather(a(), b(), c())
```

By default, if `b()` raises, `gather` re-raises immediately — but `a()` and `c()` **keep running**. You have lost your handle on them and they may complete, or fail, unobserved.

```python
results = await asyncio.gather(a(), b(), c(), return_exceptions=True)
for r in results:
    if isinstance(r, Exception):
        log.warning("one failed", exc_info=r)
```

`return_exceptions=True` gives you all results, with exceptions as values. Almost always what you actually want when the operations are independent.

If you want the opposite — cancel siblings on the first failure — use a `TaskGroup`.

### Bug 5 — Sharing a client across event loops

```python
client = httpx.AsyncClient()      # created at import time, no loop running
```

Connection pools bind to the loop that created them. Created at import, or in a different loop (common in tests), you get `Event loop is closed` or `Future attached to a different loop`. Create clients in a lifespan handler, not at module level.

## The API You Actually Need

| Call | Use it for |
|---|---|
| `await coro` | Sequential, you need the result now |
| `asyncio.create_task(coro)` | Start it now, await later |
| `asyncio.gather(*coros)` | Run several, get all results. Add `return_exceptions=True` |
| `asyncio.TaskGroup()` | The modern default. Scoped lifetime, cancels siblings on failure |
| `asyncio.wait_for(coro, timeout)` | One operation with a deadline |
| `asyncio.timeout(seconds)` | A deadline around a block of code. Cleaner than `wait_for` |
| `asyncio.as_completed(coros)` | Process results in finish order, not submit order |
| `asyncio.shield(coro)` | Protect from cancellation. Rarely correct — think twice |
| `asyncio.Queue` | Producer/consumer with backpressure via `maxsize` |
| `asyncio.Semaphore` | Limit concurrency |
| `asyncio.Event` | One-shot signal between tasks |
| `loop.run_in_executor` | Run blocking code in a thread. See [[01.8 - Offloading Work]] |
| `asyncio.run_coroutine_threadsafe` | Submit work to a loop from a non-async thread |

💡 **Default to `TaskGroup` over `gather`** on Python 3.11+. It cannot leak tasks, it cancels siblings on failure, and it guarantees everything is finished when the block exits.

```python
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(fetch(url1))
    t2 = tg.create_task(fetch(url2))
# both are guaranteed complete here; failures surface as an ExceptionGroup
```

## In Production

### Where these show up in real incidents

| Symptom | Likely cause |
|---|---|
| Endpoint slower than the sum of its calls suggests | Sequential awaits that should be a gather |
| Analytics/audit events randomly missing | Fire-and-forget tasks garbage collected |
| "Task exception was never retrieved" in logs | An unawaited task failing silently. Something is broken and you have not noticed |
| Latency fine at low load, terrible at high load | Unbounded task creation — no semaphore |
| `Event loop is closed` in tests only | A client created outside the test's loop |
| Work continues after a request is cancelled | No structured concurrency; the client disconnected but the tasks did not |

### Bounding concurrency is not optional

```python
async def fetch_all(urls):
    return await asyncio.gather(*[fetch(u) for u in urls])
```

With 10,000 urls this opens 10,000 connections at once. You will exhaust file descriptors, exhaust the target service, or both. Async makes it *easy* to overwhelm things, which is a real hazard — with threads, the thread pool size limited you by accident.

```python
async def fetch_all(urls, limit=50):
    sem = asyncio.Semaphore(limit)

    async def one(url):
        async with sem:
            return await fetch(url)

    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(one(u)) for u in urls]
    return [t.result() for t in tasks]
```

⚠️ Note this still creates 10,000 Task objects even though only 50 run at once. For very large inputs, use a bounded `asyncio.Queue` with a fixed worker count instead. Covered in [[01.11 - Backpressure Inside One Process]].

### Naming tasks

```python
asyncio.create_task(sync_source(source_id), name=f"sync-source-{source_id}")
```

Costs nothing. When you dump all tasks during an incident, the difference between 400 tasks named `Task-1..400` and 400 named `sync-source-<id>` is the difference between a five-minute diagnosis and an hour.

```python
for t in asyncio.all_tasks():
    print(t.get_name(), t.get_coro().__qualname__)
```

Expose that on a debug endpoint. You will thank yourself.

**Question to answer:** Trace `await asyncio.sleep(1)` from your code all the way to the loop and back. Identify every object created and every callback registered. Then explain why the coroutine resumes on the *next* loop iteration rather than immediately when the timer fires.

**Read, in order:**

1. `Lib/asyncio/futures.py` — `Future`, especially `__await__`, `set_result`, `add_done_callback`. Short and it is the core abstraction
2. `Lib/asyncio/tasks.py` — `Task.__step` and `Task.__wakeup`. **This is the most important function in asyncio.** Read the branching on what the coroutine yielded
3. `Lib/asyncio/tasks.py` — then `sleep`, `gather`, `wait_for`. `gather` is more subtle than it looks; read how it handles `return_exceptions`
4. `Lib/asyncio/taskgroups.py` — `TaskGroup`. Compare its error handling with `gather`'s
5. `Lib/asyncio/runners.py` — `asyncio.run`, and what it does on shutdown with pending tasks

**Then, a comparison session.** Open `python-trio/trio` and read `trio/_core/_run.py`. Trio made deliberately different choices — no bare task spawning, nurseries only, different cancellation. Write half a page on which design you prefer and why. This comparison is what makes you able to *argue* about async design rather than just use it.

**Size:** 2 sessions.
