# useDeferredValue

Returns a version of a value that **lags behind** during expensive renders, letting the urgent parts of the UI update immediately.

```jsx
function Search() {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);

  const results = useMemo(
    () => filterHugeList(deferredQuery),
    [deferredQuery]
  );

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <Results items={results} />
    </>
  );
}
```

The input uses `query` and updates instantly. The results use `deferredQuery` and update when React has time.

## How it works

On a state change, React first renders with the **old** deferred value — fast, because nothing expensive re-computes — and commits that immediately so the input reflects the keystroke. Then it schedules a background re-render with the new value at transition priority.

If another keystroke arrives before that finishes, the background render is discarded and restarted with the newest value ([[18.5 - Concurrent Rendering and the Scheduler]]).

The net effect: the input never blocks, and the results catch up when typing pauses — without any timer.

## The difference from useTransition

They do the same thing from opposite ends:

| | `useTransition` | `useDeferredValue` |
| --- | --- | --- |
| Wraps | the state **update** | the **value** |
| Requires | access to the setter | nothing |
| Use when | you own the state | the value comes from a prop, context or a library |

```jsx
// You own the setter
startTransition(() => setResults(filter(query)));

// You do not — the value arrives as a prop
function Results({ query }) {
  const deferredQuery = useDeferredValue(query);
}
```

This is the practical decision rule: **do I control the setter?** If not, `useDeferredValue` is the only option.

## Showing staleness

```jsx
const isStale = query !== deferredQuery;

<div style={{ opacity: isStale ? 0.6 : 1, transition: "opacity 200ms" }}>
  <Results items={results} />
</div>
```

Comparing the current and deferred values gives the same signal as `isPending` from `useTransition`. Dimming stale content reads better than a spinner — the user keeps seeing usable data.

Add a transition delay so brief updates do not flicker:

```css
.results { transition: opacity 200ms 100ms; }   /* 100ms delay */
```

## Memoization is required

```jsx
// Broken — filter runs on every render regardless
const results = filterHugeList(deferredQuery);

// Correct
const results = useMemo(() => filterHugeList(deferredQuery), [deferredQuery]);
```

Without `useMemo`, the expensive work runs during both the fast render (with the old value) and the background render — so nothing is saved ([[17.6 - useMemo]]).

The same applies to child components: they must be memoized to skip re-rendering when the deferred value is unchanged.

```jsx
const Results = React.memo(function Results({ items }) { ... });
```

Missing either of these is why `useDeferredValue` frequently appears not to work.

## With Suspense

`useDeferredValue` keeps stale content visible while new data loads, instead of showing a fallback:

```jsx
function SearchPage({ query }) {
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <div style={{ opacity: isStale ? 0.5 : 1 }}>
      <Suspense fallback={<Skeleton />}>
        <SearchResults query={deferredQuery} />
      </Suspense>
    </div>
  );
}
```

On the first render the fallback shows. On subsequent query changes, the previous results stay visible while the new ones load — a substantially better experience than a skeleton flashing on every keystroke ([[19.4 - Suspense]]).

## The initialValue option

React 19 added a second argument for the initial render:

```jsx
const deferredQuery = useDeferredValue(query, "");
```

On the very first render the hook returns the initial value, then immediately schedules a background render with the real one. Useful when the first render is also expensive and you want the shell up first.

## Not a debounce

```jsx
// Debounce — always waits 300ms, regardless of machine speed
const debounced = useDebounce(query, 300);

// Deferred — updates as soon as React can, which on a fast machine is immediately
const deferred = useDeferredValue(query);
```

Three differences:

**Adaptive.** On a fast machine with a small list, the deferred value updates in the same frame — no artificial delay. A debounce always waits.

**Interruptible.** A debounce, once it fires, runs to completion and blocks. A deferred render yields.

**Wrong tool for network calls.** `useDeferredValue` does not prevent a request from being sent; it only deprioritizes rendering. Debouncing is still correct for rate-limited APIs and expensive server queries ([[29.1 - Debounce and Throttle]]).

The rule: **debounce network requests, defer expensive renders.** They are often used together — debounce the fetch, defer the render of the result.

## When it helps

- Filtering or searching a large in-memory list
- A chart or visualization re-computing from an input
- A live preview (markdown, code, template) updating as the user types
- Any cheap input driving an expensive derived render

The shape is always the same: one value updates frequently, and something expensive depends on it.

## When it does not

**When the work is not actually expensive.** Deferring a cheap render adds a scheduling round trip for nothing.

**When the value must be exact immediately.** A controlled input's own `value` must never be deferred, or typing breaks.

**When the cost is a network request.** Deferring does not reduce requests.

**When one component is doing 200ms of synchronous work.** Yielding happens between components, not inside one ([[18.5 - Concurrent Rendering and the Scheduler]]).

## How senior engineers actually use this

**They pick between the two hooks by setter ownership**, not by preference.

**They always pair it with `useMemo` and `React.memo`**, since it does nothing without them.

**They show staleness by dimming**, with a short transition delay to avoid flicker.

**They combine debounce and defer** for search: debounce the request, defer the rendering of results.

**They measure first.** If the profiler does not show an expensive render, neither hook helps.

## Common pitfalls

- No `useMemo` around the expensive computation, so nothing is deferred in practice.
- Unmemoized child components re-rendering anyway.
- Deferring a controlled input's own value, breaking typing.
- Using it to reduce network requests, which it does not do.
- Expecting it to help when one component is synchronously slow.
- Using it where the work is trivially cheap.

## Interview angle

"Difference between `useDeferredValue` and `useTransition`" is the question, and the answer is the axis: one defers a value, the other deprioritizes an update — so the choice is whether you own the setter. The distinguishing details are that it must be paired with memoization to have any effect, and that it is adaptive rather than time-based like a debounce, so it introduces no artificial delay on fast machines. Adding "debounce network calls, defer renders" shows you know they solve different problems.
