# Responsive Design

Responsive design used to mean media queries. It now means using intrinsically flexible layout first, and reaching for queries only where content genuinely needs a different arrangement.

## The prerequisite

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

Without this, mobile browsers render at a ~980px virtual viewport and scale the result down, making every media query irrelevant ([[09.4 - Head Metadata and SEO Basics]]).

## Media queries

```css
/* Mobile first — base styles are the small screen, queries add complexity */
.card { padding: 1rem; }

@media (width >= 48rem) {
  .card { padding: 2rem; }
}

@media (width >= 48rem) and (width < 64rem) { }
@media (48rem <= width <= 64rem) { }        /* range syntax */
```

The range syntax (`width >= 48rem`) is now widely supported and clearer than `min-width`/`max-width`, which invert confusingly.

**Mobile-first** is the default approach for a practical reason: the small-screen layout is usually the simpler one, so building up adds complexity rather than removing it, and the base styles work on any device that fails to match a query.

Use `rem` (or `em`) in breakpoints rather than `px`. Breakpoints in `em` respond to the user's font-size setting, so a user with large text gets the simpler layout at a proportionally larger viewport — which is usually what they want.

**Choose breakpoints from content, not devices.** Resize the browser until the layout looks wrong; that width is the breakpoint. Device-based breakpoints (`768px` for "iPad") are obsolete the moment a new device ships.

## Container queries

The genuinely important shift. Media queries ask about the viewport; container queries ask about the component's available space.

```css
.card-wrapper {
  container-type: inline-size;
  container-name: card;
}

@container card (width >= 30rem) {
  .card {
    display: grid;
    grid-template-columns: auto 1fr;
  }
}
```

A card in a narrow sidebar stays stacked; the same card in a wide main column goes horizontal. The component is now genuinely reusable, which media queries can never achieve because they know nothing about where the component sits.

Container units are relative to the container:

```css
.card__title { font-size: clamp(1rem, 5cqi, 2rem); }
```

`cqi` is 1% of the container's inline size; `cqw`, `cqh`, `cqb` cover the other dimensions.

Two constraints: `container-type: inline-size` applies size containment on the inline axis, meaning the container's width no longer depends on its contents — so a container cannot be sized by its children in that axis. And a component cannot query itself; it must query an ancestor, which is why the wrapper element exists in the example above.

## Intrinsically responsive layout

Most responsiveness should not require any query at all.

```css
/* Cards that reflow with no breakpoints */
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(250px, 100%), 1fr));
  gap: 1rem;
}

/* Fluid type with sensible bounds */
h1 { font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem); }

/* Readable line length */
.prose { max-width: 65ch; }

/* Sidebar that wraps when there is no room */
.layout {
  display: flex;
  flex-wrap: wrap;
  gap: 2rem;
}
.sidebar { flex: 1 1 250px; }
.content { flex: 999 1 60%; min-width: 0; }
```

The last pattern — a very large `flex-grow` on the content — makes the sidebar and content sit side by side when there is room and stack when there is not, with no query. These techniques come from the "Every Layout" approach and are worth studying as a category.

The `min(250px, 100%)` inside `minmax` prevents overflow on viewports narrower than 250px, which the plain version does not handle.

## Preference queries

```css
@media (prefers-reduced-motion: reduce) { }
@media (prefers-color-scheme: dark) { }
@media (prefers-contrast: more) { }
@media (prefers-reduced-transparency: reduce) { }
@media (forced-colors: active) { }        /* Windows High Contrast */
```

`prefers-reduced-motion` is a genuine accessibility requirement, not a nicety — vestibular disorders make large motion physically unpleasant:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

`forced-colors: active` means the OS is overriding your colours entirely. Do not fight it; use `forced-color-adjust` sparingly and ensure the layout survives without your colour scheme.

## Interaction queries

```css
@media (hover: hover) and (pointer: fine) {
  .card:hover { transform: translateY(-2px); }
}

@media (pointer: coarse) {
  .button { min-height: 44px; }
}
```

`hover: hover` prevents hover styles from sticking on touch devices, where a tap triggers hover and it never clears. `pointer: coarse` identifies touch input, where a minimum 44×44px target is the accepted accessibility standard.

These are more useful than width queries for interaction decisions — a large tablet is wide but touch-driven.

## Responsive images and typography

Covered in detail in [[09.3 - Images Media and Loading Attributes]], but the essentials:

```html
<img srcset="s.jpg 400w, m.jpg 800w, l.jpg 1600w"
     sizes="(width >= 48rem) 50vw, 100vw"
     src="m.jpg" width="800" height="450" alt="...">
```

For type, `clamp()` with a `rem` component keeps text zoomable while still scaling with the viewport.

## Testing

**Device emulation** in DevTools covers layout but not real conditions.

**Network and CPU throttling** matter more. A mid-range Android phone is roughly four to six times slower than a development laptop, and that is where the layout thrashing and long tasks show up ([[13.3 - Layout Thrashing]]).

**Test at 200% and 400% browser zoom.** WCAG requires content to remain usable at 400% zoom in a 1280px viewport, which is equivalent to a 320px layout — this catches horizontal-scroll bugs that device emulation misses.

**Test with a real device** on a real network at least once per project. Emulation consistently understates how bad slow connections feel.

## How senior engineers actually use this

**They write layouts that need as few breakpoints as possible.** `auto-fit` grids, `clamp()` and flex-wrap handle most of it; every breakpoint added is a state that must be maintained and tested.

**They use container queries for components and media queries for page structure.** That division matches what each mechanism actually knows about.

**They set breakpoints in `rem` from content, not device names.**

**They treat `prefers-reduced-motion` as required.** It is three lines and it matters to real users.

**They check `hover: hover` before adding hover effects** to anything that also needs to work on touch.

## Common pitfalls

- Missing or restrictive viewport meta tag.
- Device-name breakpoints in `px`.
- Hover styles sticking on touch devices.
- Viewport-only `clamp()` values preventing text from scaling with zoom.
- Container queries applied to the component itself rather than a wrapper.
- Forgetting `min-width: 0` / `minmax(0, 1fr)`, causing horizontal overflow on narrow screens.
- Testing only with device emulation and never with throttling or a real device.
- `100vh` on mobile, where browser chrome makes it too tall — use `100dvh`.

## Interview angle

"How do you approach responsive design" should get more than "media queries". Lead with mobile-first and content-driven breakpoints, then the intrinsic techniques — fluid grids, `clamp()`, flex-wrap — that avoid queries entirely, then container queries as the current answer for component-level responsiveness and why media queries cannot solve that problem. Mentioning `prefers-reduced-motion` and `hover: hover` shows you think about users rather than viewports.
