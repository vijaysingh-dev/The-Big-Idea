# Leads and Lead Management

## What a Lead is, and why it is separate

A Lead is a single flat record holding a person, their company as **free text**, and how they arrived. It is deliberately not connected to Account or Contact.

That disconnection is the entire design. Leads come from web forms, trade show badge scans, purchased lists, and marketing imports. Most of that data is wrong, duplicated, or worthless. If it went straight into Account and Contact, the clean customer database would be polluted within a month.

So Leads are a staging area. Only records that survive qualification get promoted, through **conversion**, into the real model.

## The fields that matter

`FirstName`, `LastName`, `Company` (text, not a lookup), `Email`, `Phone`, `Title`, `Status`, `LeadSource`, `Rating`, `Industry`, `AnnualRevenue`, `NumberOfEmployees`, `OwnerId`.

And the conversion fields: `IsConverted`, `ConvertedDate`, `ConvertedAccountId`, `ConvertedContactId`, `ConvertedOpportunityId`.

**`IsConverted` is the field that causes the most bugs.** Converted Leads remain in the database permanently. They are hidden from most standard list views, so they are invisible in the user interface, but SOQL returns them unless you filter.

```java
// Almost always wrong: silently includes converted leads
List<Lead> leads = [SELECT Id, Email FROM Lead WHERE Email = :inboundEmail];

// Correct
List<Lead> leads = [
    SELECT Id, Email, Status
    FROM Lead
    WHERE Email = :inboundEmail AND IsConverted = false
];
```

Every trigger, batch job, duplicate check, and integration that touches Lead needs this filter. It is the single most common Lead-related defect.

## Lead status and the Lead Process

`Status` drives qualification. A **Lead Process** is metadata defining which statuses are available, tied to a Record Type, exactly as Sales Process works for Opportunity.

A workable status model:

```
New              → nobody has touched it
Working          → someone is attempting contact
Nurturing        → real interest, not ready to buy
Qualified        → meets criteria, ready to convert
Disqualified     → not a fit, with a reason
```

One status must be flagged as **Converted** in the Lead Process. That status is what the conversion process sets.

The design principle: statuses should describe the state of the *relationship*, not the activity count. "Called Three Times" is not a status. "Nurturing" is.

**Disqualified needs a reason field.** Without it, the lead database becomes a graveyard nobody can analyse. With it, marketing can see that forty percent of leads from a particular source are out of territory, which is actionable.

## Lead source and attribution

`LeadSource` is a standard picklist and is the foundation of marketing attribution. It carries forward to the Contact and Opportunity on conversion, which is what makes source-to-revenue reporting possible at all.

Two things go wrong routinely:

**The picklist grows uncontrolled.** Web, Website, web form, Web Form, and Inbound Web as five separate values. Making the picklist **restricted** prevents integrations inserting arbitrary values, and this is worth doing from day one.

**Source is treated as a single value when the reality is multi-touch.** A prospect attends a webinar, downloads a paper, and then fills in a contact form. `LeadSource` captures one of those. Real attribution needs Campaign Members and Campaign Influence. See [[04.12 - Campaigns and Campaign Influence]].

## Web-to-Lead

A generated HTML form that posts directly to Salesforce and creates a Lead. Configured in Setup, no authentication required.

Useful and genuinely limited:

- No authentication means it is spammable; a captcha and server-side filtering are effectively mandatory
- A daily limit on submissions, beyond which leads are queued or dropped
- No validation beyond field types
- The generated markup is dated and usually needs replacing

Most serious implementations post to an API endpoint from their own form handler instead, giving control over validation, deduplication, and error handling. The pattern:

```java
@RestResource(urlMapping='/inbound-lead/*')
global with sharing class InboundLeadService {

    @HttpPost
    global static ResponseDto createLead(String firstName, String lastName,
                                         String company, String email, String source) {
        if (String.isBlank(email) || String.isBlank(lastName)) {
            return ResponseDto.failure('Email and last name are required.');
        }

        // match on email against unconverted leads so repeat submissions update rather than duplicate
        List<Lead> existing = [
            SELECT Id, Status FROM Lead
            WHERE Email = :email AND IsConverted = false
            LIMIT 1
        ];

        Lead lead = existing.isEmpty()
            ? new Lead(LastName = lastName, FirstName = firstName, Company = company,
                       Email = email, LeadSource = source, Status = 'New')
            : new Lead(Id = existing[0].Id, Latest_Submission__c = Datetime.now());

        upsert as user lead;
        return ResponseDto.success(lead.Id);
    }
}
```

See [[13.15 - Building Apex REST and SOAP Services]].

## Duplicate management

Leads duplicate more than any other object. The platform provides two pieces:

**Matching Rules** define what counts as a duplicate — fuzzy name matching, exact email, standardized company name.

**Duplicate Rules** define what happens when a match is found: block, or allow with a warning, and whether to report it. They can act across objects, so a new Lead can be matched against existing Contacts.

Duplicate rules apply to the UI and, if configured, to the API. They are worth enabling on Lead in every org.

For high-volume inbound, deduplicating at the integration layer is usually better than relying on duplicate rules, because you control the merge logic and the failure behaviour.

**Lead merge** allows up to three leads to be combined. Unlike Account and Contact merging, lead merging is comparatively simple because leads have few related records.

## Lead scoring

Two approaches.

**Einstein Lead Scoring** analyses the org's history of which leads converted and produces a score, with the factors that drove it. It needs a reasonable volume of historical conversions to work — a few thousand leads with a mix of outcomes — and it needs the data to be honest, which means leads must actually be marked Disqualified rather than left in Working forever. See [[04.15 - Einstein for Sales]].

**Custom scoring** is a formula field or Apex assigning points for firmographic fit and behavioural signals. Cruder, fully controllable, and often the right starting point before there is enough history for Einstein.

```
// Simple fit score as a formula field
IF(ISPICKVAL(Industry, "Manufacturing"), 20, 0) +
IF(NumberOfEmployees > 500, 20, IF(NumberOfEmployees > 100, 10, 0)) +
IF(AnnualRevenue > 50000000, 20, 0) +
IF(ISPICKVAL(LeadSource, "Trade Show"), 15, 0)
```

## Lead hygiene, which is the real problem

Every org accumulates dead leads. Leads in Working with no activity for eighteen months. Leads with no email. Leads from a bought list nobody ever called.

They are not harmless: they distort conversion metrics, they slow queries, they consume storage, and they make Einstein scoring worse by feeding it noise.

A maintenance job worth having:

```java
public with sharing class LeadHygieneBatch implements Database.Batchable<SObject>, Schedulable {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Status, Disqualification_Reason__c
            FROM Lead
            WHERE IsConverted = false
              AND Status IN ('New', 'Working')
              AND LastActivityDate < LAST_N_DAYS:540
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Lead> scope) {
        for (Lead lead : scope) {
            lead.Status = 'Disqualified';
            lead.Disqualification_Reason__c = 'No activity in 18 months';
        }
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 200);
    }
}
```

Note `Database.update(scope, false)` for partial success — one lead failing a validation rule should not abandon the whole batch.

## Practical guidance

**Filter `IsConverted = false` everywhere.** Triggers, batch jobs, integrations, duplicate checks, reports.

**Make LeadSource a restricted picklist** and control it centrally.

**Require a disqualification reason.** The data is worthless without it.

**Do not add many custom fields to Lead.** Every field you want to survive conversion needs a mapping to a field on Account, Contact, or Opportunity, and unmapped data is lost at conversion. See [[04.4 - Lead Conversion]].

**Watch the conversion rate by source.** It is the single most useful metric the object produces, and it only works if statuses are maintained honestly.
