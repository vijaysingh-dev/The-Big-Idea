# Zustand, Jotai and Modern Alternatives

Redux solved global state when there was no alternative. The current generation of libraries makes different tradeoffs, and the choice mostly comes down to **top-down store** versus **bottom-up atoms**.

All of them are built on `useSyncExternalStore`, which is what makes them concurrent-safe ([[17.12 - Lesser Known Hooks]]).

## Zustand — a single store, selector reads

```js
import { create } from "zustand";

const useCartStore = create((set, get) => ({
  items: [],

  addItem: (item) => set(state => ({ items: [...state.items, item] })),

  removeItem: (id) => set(state => ({
    items: state.items.filter(i => i.id !== id),
  })),

  clear: () => set({ items: [] }),

  get total() {
    return get().items.reduce((sum, i) => sum + i.price, 0);
  },
}));
```

```jsx
function CartBadge() {
  const count = useCartStore(state => state.items.length);   // re-renders only when count changes
  return <span>{count}</span>;
}

function AddButton({ item }) {
  const addItem = useCartStore(state => state.addItem);      // stable — never re-renders
  return <button onClick={() => addItem(item)}>Add</button>;
}
```

The selector is the whole idea: subscribe to a slice, re-render only when that slice changes. `set` merges shallowly by default, like class `setState`.

Underneath, it is the closure-based store pattern from [[02.4 - Closure Patterns in Production]] — roughly a `Set` of listeners and a state variable.

**Reading outside React:**

```js
useCartStore.getState().addItem(item);
useCartStore.subscribe(state => console.log(state.items));
```

This is genuinely useful: event handlers, WebSocket callbacks and route loaders can read and write the store without hooks.

**Selector stability.** A selector returning a new object re-renders on every change:

```js
// Broken — new object each call
const { items, total } = useCartStore(s => ({ items: s.items, total: s.total }));

// Use useShallow
import { useShallow } from "zustand/react/shallow";
const { items, total } = useCartStore(useShallow(s => ({ items: s.items, total: s.total })));
```

The same reference-identity problem as Redux selectors ([[20.3 - Redux Core Concepts]]).

**Middleware:**

```js
const useStore = create(
  devtools(
    persist(
      immer((set) => ({ ... })),
      { name: "cart", partialize: (s) => ({ items: s.items }) }
    )
  )
);
```

Redux DevTools, `localStorage` persistence with selective serialization, and Immer for nested updates ([[20.6 - Immer and Immutable Updates]]).

Zustand is ~1KB, has no provider requirement, and the API is small enough to learn in an afternoon.

## Jotai — atoms, bottom-up

```js
import { atom, useAtom, useAtomValue } from "jotai";

const itemsAtom = atom([]);
const filterAtom = atom("all");

const visibleItemsAtom = atom((get) => {
  const items = get(itemsAtom);
  const filter = get(filterAtom);
  return filter === "all" ? items : items.filter(i => i.status === filter);
});

const addItemAtom = atom(null, (get, set, item) => {
  set(itemsAtom, [...get(itemsAtom), item]);
});
```

```jsx
const [items, setItems] = useAtom(itemsAtom);
const visible = useAtomValue(visibleItemsAtom);   // recomputes only when dependencies change
```

State is composed from small independent atoms rather than carved out of one object. Derived atoms form a dependency graph, and Jotai recomputes only what actually depends on a change — memoization is structural rather than manual.

Async atoms integrate with Suspense ([[19.4 - Suspense]]):

```js
const userAtom = atom(async (get) => {
  const id = get(userIdAtom);
  return fetch(`/api/users/${id}`).then(r => r.json());
});
```

Jotai fits well when state is naturally fine-grained and highly derived — editors, canvases, form builders, dashboards with many independent controls. It fits less well when you want one obvious place to look for "the state".

**Valtio** is the same team's proxy-based alternative: mutate a proxy object directly and components re-render based on what they actually read during render. Less explicit, very ergonomic.

## Comparison

| | Redux Toolkit | Zustand | Jotai |
| --- | --- | --- | --- |
| Model | one store, reducers | one store, actions | many atoms |
| Size (gzip) | ~13KB | ~1KB | ~3KB |
| Provider required | yes | no | optional |
| Boilerplate | moderate | minimal | minimal |
| DevTools | excellent, time travel | via middleware | basic |
| Middleware | rich ecosystem | built-in set | limited |
| Outside React | yes | yes | with a store handle |
| Best for | large apps, audit trails, teams | most applications | fine-grained derived state |

## Choosing

```
Do you have server state?           → a query library first, and most of the "need" disappears
Small amount of shared client state? → Zustand
Fine-grained, highly derived state?  → Jotai
Need middleware, time travel, strict conventions? → Redux Toolkit
Large team needing enforced structure? → Redux Toolkit
```

The first line matters most. Once server data lives in TanStack Query or RTK Query, what remains is typically a theme, an auth user, a cart, and some UI preferences — which Zustand handles in twenty lines ([[20.1 - Where State Should Live]]).

Redux's constraints are a genuine feature on a large team: one way to change state, an inspectable log of every change, and a middleware layer for cross-cutting concerns. On a team of three, those constraints are mostly overhead.

## Signals

A different model gaining ground — Solid, Preact, Angular and Vue all use variants:

```js
const count = signal(0);
const doubled = computed(() => count.value * 2);

count.value++;   // only what reads count updates
```

Fine-grained reactivity: reading a signal during render registers a dependency, and writing it updates exactly those subscribers — with no virtual DOM diff and no component re-render at all.

React has deliberately not adopted signals. The React team's position is that the model conflicts with concurrent rendering's ability to discard and restart renders, and that the React Compiler achieves comparable performance while keeping the simpler "re-render the component" mental model ([[19.9 - The React Compiler]]).

Worth understanding as context for why React's approach differs, and because signal-based libraries are increasingly common.

## Migration reality

Mixing libraries is normal and fine:

```
TanStack Query   → server data
Zustand          → shared client state
useState         → local state
URL              → shareable state
```

This combination is probably the most common modern setup. Each tool does one job.

Migrating from Redux is usually incremental — new features use the new store, existing slices stay until touched. A big-bang rewrite of state management is rarely justified.

## How senior engineers actually use this

**They move server state out first.** This alone removes most of the pressure that makes people shop for state libraries.

**They default to Zustand** for the remaining shared client state in new projects, and keep Redux where it exists and works.

**They use selectors carefully** in any library, since unstable return references defeat the subscription granularity that is the entire point.

**They do not migrate working Redux code** without a concrete reason.

**They keep the store small** — a store that grows to mirror the whole application usually means server data crept back in.

## Common pitfalls

- Reaching for a state library when the problem is server data.
- Selectors returning new objects, re-rendering on every change.
- Putting everything in the global store, including local UI state.
- Choosing by popularity rather than by the shape of the state.
- Mixing two client state libraries in one codebase without a clear boundary.
- Expecting Zustand's or Jotai's DevTools to match Redux's time travel.

## Interview angle

"Context vs Redux vs Zustand" is a common opener. The strongest response reframes it: classify the state first, move server data to a query library, and note that what remains is usually small. Then compare on the axis that matters — subscription granularity and middleware needs — rather than listing features. Mentioning that all of these build on `useSyncExternalStore` for concurrency safety, and that React has deliberately not adopted signals, demonstrates depth beyond library familiarity.
