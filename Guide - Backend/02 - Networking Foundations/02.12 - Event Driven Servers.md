# Event Driven Servers

#backend #networking #concurrency

> **In one line:** Asking the kernel "which of these 10,000 sockets is ready?" is a different question from checking each one, and the difference between `select` and `epoll` is the difference between O(n) and O(1) per event.

---

## The Idea

You have 10,000 open connections. At any instant, maybe 50 have data waiting. How do you find those 50?

**Option 1: ask about all of them, every time.** Hand the kernel a list of 10,000 file descriptors and get back the ready ones. The kernel scans all 10,000. So does your code, checking which came back ready. Every iteration, forever.

**Option 2: register once, get notified.** Tell the kernel about each socket once. It keeps a list. When something becomes ready, it moves that socket to a ready list. You ask for the ready list and get exactly the 50.

Option 1 is `select` and `poll`. Option 2 is `epoll` (Linux) and `kqueue` (BSD/macOS). The difference is the entire reason the modern internet can serve millions of concurrent connections.

---

## The History: C10k

In 1999 Dan Kegel asked: can one server handle 10,000 concurrent connections?

At the time the standard model was one thread or process per connection. At 10,000 connections that meant 10,000 threads — gigabytes of stack space, and a kernel scheduler spending more time switching between threads than doing work.

The answer turned out to be: yes, with one thread and the right system call. That answer produced nginx, Node.js, and everything in [[01.4 - Building an Event Loop From Scratch]].

Today the question is C10M, and the answers involve `io_uring` and kernel bypass. Same idea, further along.

## The Mechanisms

### select — 1983, and still everywhere

```c
fd_set readfds;
FD_ZERO(&readfds);
for (each socket) FD_SET(sock, &readfds);
select(maxfd + 1, &readfds, NULL, NULL, &timeout);
for (each socket) if (FD_ISSET(sock, &readfds)) handle(sock);
```

| Problem | Effect |
|---|---|
| **`FD_SETSIZE` is 1024** | Hard limit, compiled in. Cannot be raised portably |
| Rebuild the set every call | The kernel modifies it in place |
| Kernel scans all descriptors | O(n) per call |
| You scan all descriptors | O(n) again, in userspace |

Portable everywhere, including Windows. That is its only remaining advantage.

### poll — same idea, no 1024 limit

```c
struct pollfd fds[10000];
poll(fds, nfds, timeout);
for (i = 0; i < nfds; i++) if (fds[i].revents) handle(fds[i].fd);
```

Removes the fixed limit and does not destroy your array. Still O(n) in both kernel and userspace, still copies the whole array in and out on every call.

### epoll — Linux, 2002

```c
int ep = epoll_create1(0);

struct epoll_event ev = {.events = EPOLLIN, .data.fd = sock};
epoll_ctl(ep, EPOLL_CTL_ADD, sock, &ev);          // register once

struct epoll_event events[64];
int n = epoll_wait(ep, events, 64, timeout);       // returns ONLY ready ones
for (i = 0; i < n; i++) handle(events[i].data.fd);
```

The kernel keeps a registered set and a ready list. When a socket becomes readable, the kernel's networking code moves it to the ready list. `epoll_wait` returns that list.

**O(1) per ready event**, independent of how many sockets are registered. 10 sockets or 10 million, the cost is proportional to how many are actually ready.

### kqueue — BSD and macOS, 1999

Same performance characteristics, better design in some ways: one API handles sockets, files, timers, signals and process events, and you can register and wait in a single call.

Python's `selectors` module picks the best available backend for you, which is why the code in [[01.4 - Building an Event Loop From Scratch]] works everywhere.

### The comparison

| | select | poll | epoll / kqueue |
|---|---|---|---|
| Max descriptors | 1024 | Unlimited | Unlimited |
| Register cost | Every call | Every call | Once |
| Kernel scan | O(n) | O(n) | O(ready) |
| Userspace scan | O(n) | O(n) | O(ready) |
| Data copied per call | Whole set | Whole array | Only ready events |
| Portable | Everywhere | POSIX | Linux / BSD only |

## Level-Triggered vs Edge-Triggered

epoll offers two modes and misunderstanding them causes real bugs.

**Level-triggered (default).** "There is data" — reported every time you ask, until you have consumed it all.

```python
epoll_wait()         # socket 5 is readable
read(5, 100)         # 500 bytes were available, you read 100
epoll_wait()         # socket 5 is STILL reported readable. 400 bytes remain
```

Forgiving. You cannot lose an event by under-reading.

**Edge-triggered (`EPOLLET`).** "Something changed" — reported only when the state transitions.

```python
epoll_wait()         # socket 5 became readable
read(5, 100)         # you read 100 of 500 bytes
epoll_wait()         # NOTHING. No new data arrived, so no new edge
                     # your 400 bytes sit there forever
```

⚠️ **With edge-triggered mode you must read until `EAGAIN`**, draining the socket completely, or you will hang holding data you were told about once and never again.

```python
while True:
    try:
        data = sock.recv(4096)
        if not data:
            break
        handle(data)
    except BlockingIOError:
        break          # drained. Now it is safe to wait again
```

Edge-triggered means fewer syscalls (you are not repeatedly told about the same readiness) at the cost of much stricter correctness requirements. **Most frameworks use level-triggered because the bugs are not worth the savings.** nginx uses edge-triggered, carefully.

💡 This is a good general lesson: the higher-performance option is often the one with a sharper failure mode. Choose it only when you have measured that you need it.

## The Thundering Herd

Multiple processes waiting on the same listening socket. A connection arrives. **All of them wake up.** One gets it, the rest go back to sleep having done nothing.

At high connection rates this wastes substantial CPU.

Solutions:

| Approach | How |
|---|---|
| `EPOLLEXCLUSIVE` | Kernel wakes only one waiter. Linux 4.5+ |
| `SO_REUSEPORT` | Each process has its own socket and its own queue |
| Accept mutex | One process accepts at a time (nginx's older approach) |

⚠️ `SO_REUSEPORT` distributes by hash, not by load, so it can produce imbalance with long-lived connections — see [[02.6 - TCP Settings That Matter]].

## io_uring — The Current Frontier

epoll tells you when you *can* do I/O. You then make a syscall to actually do it. At high rates, those syscalls dominate — and they got more expensive after Spectre and Meltdown mitigations.

`io_uring` removes them. You and the kernel share two ring buffers in memory:

```
Submission queue   → you write "read 4KB from fd 7 into this buffer"
                     kernel picks it up
Completion queue   ← kernel writes "done, 4096 bytes"
```

**Zero syscalls in the steady state.** You write to shared memory; the kernel reads it. It also works for file I/O, which epoll never did properly — regular files are always "ready", so epoll cannot make file reads asynchronous.

Status in 2026: mature in the kernel and widely used in databases and high-performance proxies. Python support exists but is not mainstream; there is no `io_uring` asyncio backend in the standard library. Know it exists, understand why it matters, and expect it to become the default eventually.

⚠️ It has had a rough security history — enough that Google disabled it in ChromeOS and Android for a period. Its very power (letting userspace queue arbitrary kernel operations) is also its attack surface.

## In Production

### What this means for your Python service

You are not writing `epoll_ctl` calls. But the model explains behaviour you will see:

| Observation | Explanation |
|---|---|
| 50,000 idle connections cost almost nothing | The loop is blocked in `epoll_wait`. Idle sockets cost only memory |
| One slow handler stalls everything | Between `epoll_wait` calls, nothing else can happen ([[01.6 - The Blocking Call Problem]]) |
| CPU is 0% but latency is bad | Waiting in `epoll_wait` is not CPU. Look at what you are waiting *for* |
| uvloop is 2–4× faster | libuv makes fewer syscalls and manages buffers better |
| File reads block despite async | epoll does not work for regular files. This is why `aiofiles` uses threads |

That last row is a real gotcha. `aiofiles` is not truly async — it runs blocking file I/O in a thread pool, because epoll cannot help with regular files. Only `io_uring` fixes that properly.

### The event-driven ceiling

An event loop scales connections beautifully and does **not** scale CPU work at all.

```
100,000 idle WebSocket connections    → fine, one process
1,000 requests/sec of trivial work    → fine
100 requests/sec of 50ms CPU work     → completely saturated
```

The model's assumption is that you spend most of your time waiting. When you do not, you need processes ([[01.3 - Threads Processes and Coroutines]]).

### Descriptor limits are the real wall

```bash
ulimit -n                       # per-process
sysctl fs.file-max              # system-wide
ls /proc/<pid>/fd | wc -l       # current usage
```

You will hit the file descriptor limit long before you hit epoll's limits. Set it to 65536+ and export usage as a metric.

### Choosing a server model

| Workload | Model |
|---|---|
| Many connections, little work each | Event loop. Your default |
| Few connections, heavy CPU each | Process per core |
| Mixed | Event loop + offload pool ([[01.8 - Offloading Work]]) |
| Extremely high packet rate | io_uring, or kernel bypass (DPDK) |
| Blocking libraries you cannot replace | Threads, sized deliberately |

## Codebase

**Repo:** `redis/redis`, `nginx/nginx`, `libuv/libuv`

**Question to answer:** Redis, nginx and libuv all solve the same problem with different tradeoffs. For each: which epoll mode do they use (level or edge), how do they handle the thundering herd, and how do they abstract over epoll/kqueue portability?

**Read, in order:**

1. `redis/src/ae.c` — **the best starting point anywhere.** A complete event loop in under 500 lines. Read `aeMain`, `aeProcessEvents`, `aeCreateFileEvent`
2. `redis/src/ae_epoll.c` and `ae_kqueue.c` — the same interface, two backends. This is the cleanest portability abstraction you will find, and it is 150 lines
3. `nginx/src/event/modules/ngx_epoll_module.c` — production-grade, edge-triggered. Note how carefully it drains sockets, and find `NGX_USE_EPOLL_EVENT`
4. `nginx/src/event/ngx_event_accept.c` — the accept mutex and thundering herd handling
5. `libuv/src/unix/linux.c` — libuv's epoll integration. This is what uvloop, and therefore your production Python, actually runs on

💡 **Read Redis first and give it real time.** `ae.c` is short enough to understand completely, which almost no other production event loop is. Once you hold that whole file in your head, nginx and libuv become variations on something you already know rather than new material.

**Size:** 2 sessions. High value.

**Part 1 — Five servers, one protocol.** Same echo protocol, five concurrency models. Then benchmark at 100, 1,000, 5,000, 10,000 and 50,000 connections.

Measure: memory, connection setup time, throughput, p99 latency, CPU.

**Predict the shape of each curve before you run it.** You should find thread-per-connection failing on memory somewhere in the low thousands, select refusing to go past 1024 at all, and epoll flat throughout.

**This chart is the C10k problem, reproduced with your own numbers.** It is one of the most quotable artifacts you can produce from this vault.

**Part 2 — The cost of idle.** 50,000 connections that send nothing. Measure memory per connection and CPU usage for each model that can even reach that number.

Then have 1% of them send a message every second and measure again. **The gap between "idle cost" and "active cost" is the entire economic argument for event-driven servers.**

**Part 3 — Break edge triggering.** Implement `edge_broken.py`: register with `EPOLLET`, read a fixed 100 bytes per event.

Send 1000 bytes. Watch the server process 100 and then hang forever holding 900 bytes it will never be told about again.

Then implement `edge_correct.py` draining to `EAGAIN`. Confirm it works.

Then measure the syscall difference between level and edge triggered using `strace -c`. Report whether the saving was worth the risk. **Be honest — for most workloads it is not.**

**Part 4 — Thundering herd.** Eight processes sharing one listening socket. Instrument each to count how many times it woke up versus how many connections it actually accepted.

The wasted-wakeup ratio should be roughly 7:1. Then apply `EPOLLEXCLUSIVE`, then `SO_REUSEPORT`, and measure again.

For `SO_REUSEPORT`, also measure **fairness**: how evenly were connections distributed across the eight? Then repeat with long-lived connections of varying duration and show the imbalance persisting. That imbalance is the real-world caveat that the documentation does not emphasise.

**Part 5 — Compare with the real thing.** Run the same benchmark against your own loop from [[01.4 - Building an Event Loop From Scratch]], against asyncio, and against asyncio with uvloop.

Explain every gap. Where you are slower than asyncio, find the specific reason. **This is the most instructive part of the drill** — you have already read `base_events.py`, so the answers are findable.

**Done when:**
- Your five-model chart covers all five connection counts
- Thread-per-connection has visibly hit a wall and you know which resource caused it
- `edge_broken.py` hangs and you can explain exactly why in two sentences
- You have measured the thundering herd ratio and both fixes
- You can account for the performance gap between your loop and uvloop
