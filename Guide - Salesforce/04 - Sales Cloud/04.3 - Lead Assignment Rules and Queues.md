# Lead Assignment Rules and Queues

## The problem

A lead arrives at three in the morning from a web form. Somebody has to own it, quickly, and it has to be the right somebody — the rep who covers that territory, that industry, or that product.

Speed matters here more than almost anywhere else in the sales process. Response time to inbound leads correlates strongly with conversion, and a lead sitting unassigned for a day is usually a lost lead.

## Assignment rules

An **assignment rule** is an ordered list of rule entries. Each entry has criteria and a target — a user or a queue. The first entry whose criteria match wins, and evaluation stops there.

```
Rule: Standard Lead Assignment

1. Country = "India" AND Industry = "Manufacturing"     → Queue: India Manufacturing
2. Country = "India"                                     → Queue: India General
3. AnnualRevenue > 50000000                              → User: Enterprise Team Lead
4. (no criteria — catch-all)                             → Queue: Unassigned Leads
```

Only **one assignment rule can be active at a time** per object. Everything lives in that one rule's entries, which is why the ordering is the whole design.

Entry four is the pattern worth always including: **a catch-all at the bottom**. Without it, leads matching nothing keep the owner they were created with, which for a web-to-lead submission is the default lead owner and for an integration is the integration user. Leads silently owned by an integration user are invisible to everyone and are a recurring source of lost pipeline.

## Queues

A queue is a group that can own records ([[03.12 - Public Groups, Queues and Territory Management]]). Assigning leads to a queue rather than a person means the team sees the pool and claims work by taking ownership.

The choice between assigning to a user and to a queue:

**Assign to a user** when there is a clear single owner — a named territory rep, an account manager.

**Assign to a queue** when the team should self-serve, when load balancing matters, or when nobody specific is right yet.

Queue-owned leads sit in a list view. A member takes ownership, which removes it from the queue. The main weakness is that queues do not distribute — everyone sees everything, and popular leads get taken while the rest sit. Round-robin distribution needs building.

## When assignment rules run, and when they do not

This trips people up constantly.

Assignment rules run at step 9 of the order of execution, **after** before and after triggers ([[07.13 - Order of Execution]]). So a trigger cannot see the assigned owner, because assignment has not happened yet.

More importantly, **assignment rules do not run automatically for records created through the API or Apex** unless explicitly requested. Through the user interface there is an "Assign using active assignment rule" checkbox. Through code, you set a DML option:

```java
public with sharing class LeadIntakeService {

    public static void createWithAssignment(List<Lead> leads) {
        Database.DMLOptions options = new Database.DMLOptions();
        options.assignmentRuleHeader.useDefaultRule = true;
        options.emailHeader.triggerUserEmail = true;

        for (Lead lead : leads) {
            lead.setOptions(options);
        }

        Database.insert(leads, false);
    }
}
```

Without `useDefaultRule = true`, every lead created by an integration keeps the integration user as owner. This is one of the most common integration defects in Sales Cloud, and it is silent — no error, the leads just vanish from everyone's view.

A specific rule can also be targeted by ID rather than using the active default:

```java
options.assignmentRuleHeader.assignmentRuleId = specificRuleId;
```

## Round-robin distribution

Assignment rules cannot round-robin. They evaluate criteria, and criteria do not know whose turn it is.

The standard approach uses a counter, and the important detail is handling concurrency correctly.

```java
public with sharing class RoundRobinAssignmentService {

    public static void assign(List<Lead> leads, String poolName) {
        List<Assignment_Pool_Member__c> members = [
            SELECT Id, User__c FROM Assignment_Pool_Member__c
            WHERE Pool_Name__c = :poolName AND Active__c = true
            ORDER BY Sort_Order__c
        ];

        if (members.isEmpty()) {
            return;
        }

        // FOR UPDATE locks the counter row so parallel transactions cannot read the same value
        Assignment_Counter__c counter = [
            SELECT Id, Next_Index__c FROM Assignment_Counter__c
            WHERE Pool_Name__c = :poolName LIMIT 1
            FOR UPDATE
        ];

        Integer index = Integer.valueOf(counter.Next_Index__c);
        for (Lead lead : leads) {
            lead.OwnerId = members[Math.mod(index, members.size())].User__c;
            index++;
        }

        counter.Next_Index__c = Math.mod(index, members.size());
        update counter;
    }
}
```

`FOR UPDATE` is what makes this correct under concurrent load. Without it, two simultaneous transactions read the same counter value and assign to the same person. With it, the second waits. The tradeoff is lock contention if leads arrive very rapidly, which is why high-volume implementations often use Platform Events to serialize assignment through a single subscriber instead. See [[08.6 - FOR UPDATE and Record Locking]].

Availability should factor in too — skipping members who are out of office, or weighting by current open lead count, are common extensions.

## Routing on more than criteria

Assignment rules evaluate fields on the Lead. When routing needs something more — a lookup to a territory table, a call to an external system, a capacity check — you need code or flow.

The usual pattern is a before-insert handler that sets `OwnerId` directly, and a simple catch-all assignment rule behind it:

```java
public with sharing class LeadRoutingService {

    public static void route(List<Lead> leads) {
        Set<String> postcodes = new Set<String>();
        for (Lead lead : leads) {
            if (String.isNotBlank(lead.PostalCode)) {
                postcodes.add(lead.PostalCode.substring(0, 3));
            }
        }

        Map<String, Id> ownerByPostcode = new Map<String, Id>();
        for (Territory_Assignment__mdt mapping : Territory_Assignment__mdt.getAll().values()) {
            ownerByPostcode.put(mapping.Postcode_Prefix__c, mapping.Owner_User_Id__c);
        }

        for (Lead lead : leads) {
            if (String.isBlank(lead.PostalCode)) {
                continue;
            }
            Id owner = ownerByPostcode.get(lead.PostalCode.substring(0, 3));
            if (owner != null) {
                lead.OwnerId = owner;
            }
        }
    }
}
```

Using Custom Metadata for the mapping means territory changes are a deployment of records rather than a code change, and `getAll()` consumes no SOQL query. See [[17.1 - Custom Metadata Types]].

Setting `OwnerId` in a before trigger takes precedence, because assignment rules only apply when the record is submitted with the assignment header set. If both run, understand which wins in your configuration and pick one.

## Notification

Assignment rules can send an email to the new owner using a template. Useful and limited — email is slow and easily ignored.

More effective in practice: a custom notification through the mobile app, a Slack message, or a Lightning task created for the owner. All of these can be triggered from a flow or from Apex after assignment.

```java
Messaging.CustomNotification notification = new Messaging.CustomNotification();
notification.setTitle('New lead assigned');
notification.setBody(lead.Company + ' — ' + lead.Name);
notification.setNotificationTypeId(notificationTypeId);
notification.setTargetId(lead.Id);
notification.send(new Set<String>{ lead.OwnerId });
```

## Practical guidance

**Always end with a catch-all entry.** Unassigned leads are lost leads.

**Set `useDefaultRule` on every integration that creates leads.** Test it explicitly, because the failure is silent.

**Prefer queues to individuals for anything with volume.** People go on holiday; queues do not.

**Measure time-to-first-touch**, not just conversion rate. It is the metric that shows whether routing is actually working.

**Keep the rule entry list short and ordered by specificity.** A rule with forty entries is unmaintainable, and it is usually a sign that routing logic belongs in Custom Metadata driving Apex instead.
