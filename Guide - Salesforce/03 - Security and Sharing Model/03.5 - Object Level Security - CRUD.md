# Object Level Security - CRUD

## The four permissions, and the two overrides

Object-level security answers: can this user work with this *kind* of record at all?

**Create** — insert new records
**Read** — see records they have record-level access to
**Edit** — modify records they have record-level access to
**Delete** — delete records they have record-level access to

Plus two that behave differently:

**View All** — read every record of this object, ignoring the sharing model entirely
**Modify All** — read, edit, and delete every record of this object, ignoring the sharing model, and delete regardless of ownership

CRUD is often written as an acronym for the first four. The two overrides are the ones that matter most from a security perspective, because they are not degrees of access — they switch the record-level model off for that object.

## How the permissions interact with sharing

This is the point people get wrong most often.

Object permission and record access are **both** required. They are ANDed, not ORed.

- Edit on the object + no record access = cannot edit anything
- No Edit on the object + full record access through sharing = still cannot edit
- Edit on the object + Read-only record access from a sharing rule = cannot edit that record

The exception is View All and Modify All, which grant record access directly. A user with Modify All on Warranty Claim can edit every claim in the org regardless of ownership, OWD, or sharing rules.

## When View All and Modify All are appropriate

They have legitimate uses, and the distinction between the per-object versions and the org-wide ones matters.

**Per-object View All / Modify All** is the right tool for:
- An integration user that must read or update every record of specific objects
- A data migration user, scoped to the objects being migrated
- A support role that must see all cases but not all opportunities

**Org-wide View All Data / Modify All Data** (system permissions on the profile) should be limited to System Administrators, and even then, kept to as few people as possible.

The practical rule: if someone needs full access to one object, grant it on that object. Reaching for the org-wide permission because it is quicker is the most common way orgs end up with far more full-access users than they intended.

## Ownership and delete

Delete has a subtlety. A record owner, and anyone above them in the role hierarchy, can delete a record if they have the Delete object permission. But a user who gained *edit* access through a sharing rule cannot delete, because sharing rules grant at most Read/Write, never Delete.

Delete access comes from ownership, the role hierarchy above the owner, or Modify All. There is no sharing rule that grants delete.

This surprises people designing collaborative processes: "the team can edit each other's claims but nobody can delete them" is the default behaviour of a sharing rule, not something you have to configure.

## Checking permissions in Apex

This is the developer's responsibility, and the platform does not do it for you. A SOQL query in Apex returns records regardless of whether the running user has Read on the object.

```java
// Explicit describe-based checks
if (!Schema.sObjectType.Warranty_Claim__c.isAccessible()) {
    throw new SecurityException('You do not have access to warranty claims.');
}

if (Schema.sObjectType.Warranty_Claim__c.isCreateable()) {
    insert claims;
}

if (Schema.sObjectType.Warranty_Claim__c.isUpdateable()) {
    update claims;
}

if (Schema.sObjectType.Warranty_Claim__c.isDeletable()) {
    delete claims;
}
```

These describe methods reflect the running user's combined profile and permission set permissions.

The modern and much cleaner approach is `USER_MODE`, which applies object permissions, field-level security, and sharing in one step:

```java
// Object permissions, field-level security, and sharing all enforced
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c, Approved_Amount__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
    WITH USER_MODE
];

insert as user claims;
update as user claims;
```

`WITH USER_MODE` on queries and `as user` on DML throw an exception if the user lacks the required permission, rather than silently returning or writing partial data. This is generally what you want, and it replaces the older `WITH SECURITY_ENFORCED`, which only covered field and object access on queries and had gaps around polymorphic fields.

Full treatment, including `stripInaccessible` and the cases where you deliberately want system mode, is in [[03.13 - Enforcing Security in Apex and SOQL]].

## Auditing object permissions

`ObjectPermissions` covers both profiles and permission sets, which makes it the single place to answer access questions.

```sql
SELECT Parent.Profile.Name, Parent.Label, SobjectType,
       PermissionsCreate, PermissionsRead, PermissionsEdit, PermissionsDelete,
       PermissionsViewAllRecords, PermissionsModifyAllRecords
FROM ObjectPermissions
WHERE SobjectType = 'Warranty_Claim__c'
ORDER BY Parent.Profile.Name NULLS LAST
```

Rows where `Parent.Profile.Name` is populated come from a profile's implicit permission set; rows where it is null come from a real permission set.

Finding everyone with an override on a sensitive object:

```sql
SELECT Parent.Label, Parent.Profile.Name, SobjectType
FROM ObjectPermissions
WHERE PermissionsModifyAllRecords = true
  AND SobjectType IN ('Warranty_Claim__c', 'Claim_Payment__c')
```

## Common failure patterns

**Granting Modify All to fix a sharing problem.** Someone cannot see records they should see, sharing rules seem complicated, and Modify All makes it work. It also gives them every other record, permanently, and nobody revisits it.

**Forgetting Create on a related object.** A flow or Apex that creates a child record fails for users without Create on the child, even though the parent works fine. The error surfaces at an unexpected point in the process.

**Assuming the UI reflects the API.** A field marked read-only on a page layout is still writable through Apex and the API. Only field-level security is enforced everywhere. See [[03.6 - Field Level Security]].

**Integration users with far more than they need.** An integration that reads accounts and writes cases frequently ends up with Modify All Data because it was the fastest way to get it working. Scope it to the specific objects and operations instead — it is the highest-value security improvement available in most orgs.

**Testing only as an administrator.** An administrator has Modify All Data and therefore experiences none of this. Any feature involving permissions must be tested as a real user, and in Apex tests that means `System.runAs()`. See [[19.8 - Testing Security and Sharing]].

## Design guidance

**Grant Create, Read, Edit generously; grant Delete deliberately.** Deletion is where irreversible damage happens, and most users have no business need for it. Cancelled and Archived statuses serve the actual requirement in most cases.

**Prefer per-object View All / Modify All to the org-wide equivalents.** Same capability, dramatically smaller blast radius.

**Review object permissions when adding an object.** A new object is invisible to everyone until granted, which is the correct default and a frequent cause of "the new feature does not work for anyone but you".
