# Generics

A generic is a **type parameter** — a placeholder filled in at the call site, so a function or type can work with many types while preserving the relationship between input and output.

```ts
function identity<T>(value: T): T {
  return value;
}

identity("hello");   // T inferred as "hello" → returns string
identity(42);        // T inferred as 42 → returns number
```

The alternative loses information:

```ts
function identity(value: any): any {}      // returns any — all type safety gone
function identity(value: unknown): unknown {} // safe, but caller must narrow
```

`T` preserves the connection: what goes in determines what comes out.

## Constraints

```ts
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: "1", age: 30 };
getProperty(user, "age");      // number
getProperty(user, "missing");  // Error: not assignable to "id" | "age"
```

`K extends keyof T` restricts the key to properties that actually exist, and `T[K]` gives the precise value type for that key. This is the pattern behind every typed property accessor, form field path, and table column definition.

```ts
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest("abc", "de");        // string
longest([1, 2], [3]);        // number[]
```

Constraining to a shape rather than a concrete type keeps the return type precise — returning `{ length: number }` would discard everything else.

## Defaults

```ts
type ApiResponse<T = unknown> = {
  data: T;
  status: number;
};

type Paginated<T, Meta = { total: number }> = {
  items: T[];
  meta: Meta;
};
```

Defaults make a generic usable without explicit arguments. Note the default should be `unknown`, not `any` — `any` silently disables checking for anyone who omits the parameter.

## Inference, and when to override it

TypeScript infers type arguments from the values passed. Explicit arguments are needed when there is nothing to infer from:

```ts
const items = await fetchJson<Product[]>("/api/products");
const [user, setUser] = useState<User | null>(null);
```

`useState(null)` infers `null`, so the generic is required whenever the initial value is narrower than the eventual type ([[17.2 - useState in Depth]]).

A common trap is over-constraining inference:

```ts
// T is inferred as string, losing the literal
function pick<T>(options: T[]): T {}
pick(["a", "b"]);                         // string

// Preserves the literal union
function pick<const T extends string>(options: T[]): T {}
pick(["a", "b"]);                         // "a" | "b"
```

The `const` type parameter modifier tells the checker to infer literal types, which is what you want for option lists, route names and event maps.

## Generic components

```tsx
type SelectProps<T> = {
  options: T[];
  value: T | null;
  onChange: (value: T) => void;
  getLabel: (option: T) => string;
};

function Select<T>({ options, value, onChange, getLabel }: SelectProps<T>) {
  return (
    <ul>
      {options.map((option, i) => (
        <li key={i} onClick={() => onChange(option)}>{getLabel(option)}</li>
      ))}
    </ul>
  );
}

<Select
  options={products}
  value={selected}
  onChange={setSelected}        // (value: Product) => void — fully typed
  getLabel={(p) => p.name}      // p inferred as Product
/>
```

The type flows from `options` through to `onChange` and `getLabel` with no annotations at the call site. This is the main practical payoff of generics in React — a reusable component that stays precisely typed for every consumer ([[25.4 - Typing Props and Children]]).

Note that `React.FC` cannot express this, which is one reason it fell out of favour.

In a `.tsx` file, `<T>` in an arrow function is ambiguous with JSX. Use a function declaration, or `<T,>`:

```tsx
const Select = <T,>({ options }: SelectProps<T>) => { ... };
```

## Generic hooks

```ts
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = localStorage.getItem(key);
      return raw ? (JSON.parse(raw) as T) : initial;
    } catch {
      return initial;
    }
  });

  return [value, setValue] as const;   // tuple, not (T | Dispatch)[]
}
```

`as const` on the return is essential — without it TypeScript widens the tuple to an array union and destructuring gives the wrong types.

## Conditional types

```ts
type Unwrap<T> = T extends Promise<infer U> ? U : T;

type A = Unwrap<Promise<string>>;   // string
type B = Unwrap<number>;             // number
```

`infer` extracts a type from a position within another type. It is the mechanism behind `ReturnType`, `Parameters` and `Awaited`.

Practical use in an API layer:

```ts
type ApiData<T extends (...args: any[]) => Promise<any>> = Awaited<ReturnType<T>>;

type Product = ApiData<typeof productsApi.byId>;
```

The component type is derived from the API function, so changing the fetcher's return type propagates automatically.

Conditional types distribute over unions by default:

```ts
type ToArray<T> = T extends any ? T[] : never;
type R = ToArray<string | number>;      // string[] | number[]
```

Wrapping in a tuple prevents distribution when you do not want it: `[T] extends [any]`.

## Mapped types

```ts
type Nullable<T> = { [K in keyof T]: T[K] | null };
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };

type UserGetters = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }
```

Key remapping with `as` plus template literal types generates derived shapes. Useful for event maps, form field paths, and API client generation — and easy to overuse.

## Knowing when to stop

Generics are a cost as well as a capability. A deeply generic utility with four type parameters and conditional returns is often harder to read, harder to debug when inference fails, and slower to compile than three concrete functions.

Signals it has gone too far:

- Errors that span twenty lines and mention types you did not write
- Needing explicit type arguments at every call site because inference broke
- More time spent on the types than on the logic

The rule: **add a generic when a real second use case appears**, not in anticipation of one.

## Compile performance

Complex conditional and recursive types are re-evaluated frequently. In large codebases they are a common cause of slow editor responsiveness.

```bash
tsc --diagnostics
tsc --generateTrace ./trace
```

If check time is high, deeply generic utility types are usually the culprit. Interfaces and simpler shapes compile substantially faster ([[25.1 - Types vs Interfaces]]).

## How senior engineers actually use this

**They constrain generics rather than leaving them open**, because `T extends { id: string }` produces far better errors and inference than a bare `T`.

**They rely on inference and avoid explicit type arguments**, treating the need for them as a signal the signature is wrong.

**They use `as const` on returned tuples** from hooks.

**They stop at two type parameters** in application code, and reserve heavy type-level programming for library boundaries.

**They check compile time** when the editor gets slow, since generic utilities are the usual cause.

## Common pitfalls

- `any` instead of a type parameter, discarding the input/output relationship.
- Unconstrained generics producing unhelpful errors deep in the call.
- `<T>` in a `.tsx` arrow function parsed as JSX.
- Returning a tuple without `as const`, so destructured values are unions.
- Over-generic utilities nobody can debug.
- Losing literal types where a `const` type parameter was needed.
- Recursive conditional types slowing the whole project.

## Interview angle

"What are generics and why use them" wants the core idea: a type parameter preserves the relationship between input and output, where `any` discards it and `unknown` forces the caller to narrow. Then a concrete constraint example — `K extends keyof T` returning `T[K]` — which shows generics doing real work rather than acting as a placeholder. In a React context, a generic `Select` component whose `onChange` is typed from `options` is the most convincing demonstration.
