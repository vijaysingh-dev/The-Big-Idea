# Conditional Rendering and Composition

## The forms

```jsx
{condition && <Panel />}
{condition ? <A /> : <B />}
{condition ? <A /> : null}

if (!data) return <Spinner />;      // early return
return <Content data={data} />;
```

Early returns are usually the most readable option when a whole branch differs. Inline expressions are better for small pieces inside a larger tree.

## The && trap

```jsx
{items.length && <List items={items} />}    // renders "0" when the list is empty
{count && <Badge count={count} />}          // renders "0" when count is 0
```

`&&` returns the **left operand** when it is falsy, and React renders `0` while skipping `false`, `null` and `undefined` ([[16.2 - JSX]]).

Fixes:

```jsx
{items.length > 0 && <List items={items} />}
{Boolean(count) && <Badge count={count} />}
{count ? <Badge count={count} /> : null}
```

The comparison form is preferable — it states the intent rather than relying on coercion.

An adjacent trap with strings:

```jsx
{name && <p>{name}</p>}    // renders nothing for "" — correct, but only by luck
```

## Nested ternaries

```jsx
{isLoading ? <Spinner /> : error ? <Error error={error} /> : data ? <List data={data} /> : <Empty />}
```

This is technically fine and practically unreadable. Two better shapes:

**Early returns:**

```jsx
function Results({ status, data, error }) {
  if (status === "loading") return <Spinner />;
  if (status === "error") return <Error error={error} />;
  if (!data.length) return <Empty />;
  return <List data={data} />;
}
```

**A lookup map**, when the branches are uniform:

```jsx
const views = {
  loading: <Spinner />,
  error: <Error error={error} />,
  success: <List data={data} />,
};

return views[status] ?? null;
```

Note the map form evaluates every branch eagerly. Use functions if any branch is expensive:

```jsx
const views = {
  loading: () => <Spinner />,
  success: () => <List data={data} />,
};
return (views[status] ?? (() => null))();
```

## Status unions beat boolean flags

```jsx
// Representable but meaningless combinations
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
const [isEmpty, setIsEmpty] = useState(false);

// One value, one truth
const [status, setStatus] = useState("idle");
```

Three booleans give eight states, of which perhaps four are valid. A union type makes invalid states unrepresentable, and in TypeScript a discriminated union lets the compiler narrow the data type per branch ([[25.6 - Discriminated Unions and Narrowing]]):

```tsx
type State =
  | { status: "loading" }
  | { status: "error"; error: Error }
  | { status: "success"; data: Item[] };
```

Now `state.data` is only accessible in the success branch, and `state.error` only in the error branch. The compiler enforces what the ternary chain merely hoped for.

## Conditional rendering vs hiding

```jsx
{isOpen && <Panel />}                        // unmounts — state is lost
<Panel style={{ display: isOpen ? "block" : "none" }} />   // stays mounted
<Panel hidden={!isOpen} />
```

Unmounting destroys the component's state, effects, scroll position and any uncontrolled input values. Hiding preserves everything but keeps the component rendering and its effects running.

Choose by intent:

- **Unmount** when the content should reset each time it opens, or when it is expensive and rarely shown.
- **Hide** when reopening should restore the previous state — a filter panel mid-edit, a tab with scroll position, a video that should keep playing.

Note that `display: none` content is still in the DOM and still read by search engines, but is removed from the accessibility tree — so hiding is not a way to keep content available to screen readers.

## Composition instead of conditionals

A component accumulating conditional branches driven by props is usually a composition problem:

```jsx
// Configuration — every variation adds a prop and a branch
function Card({ hasImage, hasFooter, isCompact, showBadge }) {
  return (
    <div className={isCompact ? "card card--compact" : "card"}>
      {hasImage && <img />}
      {showBadge && <Badge />}
      {hasFooter && <footer />}
    </div>
  );
}

// Composition — no branches, unlimited variations
function Card({ children, className = "" }) {
  return <div className={`card ${className}`}>{children}</div>;
}

<Card className="card--compact">
  <CardImage src={src} />
  <CardBody>...</CardBody>
</Card>
```

The second version has one prop and no conditionals, yet covers strictly more cases ([[16.3 - Components and Props]]).

The signal to refactor: a component with more than about three boolean props, or a `if (variant === ...)` chain that keeps growing.

## Slot props

For layouts where the caller supplies specific regions:

```jsx
function Page({ header, sidebar, children }) {
  return (
    <div className="layout">
      {header}
      {sidebar && <aside>{sidebar}</aside>}
      <main>{children}</main>
    </div>
  );
}
```

The `sidebar &&` here is legitimate — it is checking for an optional slot, and elements are never `0`.

## Render props for behavior

When the variation is behavioral rather than structural:

```jsx
<Query url="/api/items">
  {({ status, data }) =>
    status === "loading" ? <Spinner /> : <List data={data} />
  }
</Query>
```

Hooks made most render props unnecessary — `useQuery` is simpler than a render-prop component. They remain useful for headless components that need to control mounting or provide values that depend on internal DOM state ([[22.7 - Render Props and HOCs]]).

## Guarding on data shape

```jsx
{user?.profile && <Profile profile={user.profile} />}
{items?.length > 0 && <List items={items} />}
```

Optional chaining prevents crashes on missing data, but a component full of `?.` usually means the data should have been normalized at the boundary ([[05.7 - Optional Chaining and Nullish Coalescing]]). Defaulting to `[]` and `{}` in the API layer removes most of these checks.

## How senior engineers actually use this

**They model state as a union and render one branch per state**, rather than accumulating booleans.

**They use early returns for whole-branch differences** and reserve inline conditionals for small pieces.

**They prefer composition over conditional props.** A growing set of boolean props is the trigger to restructure.

**They decide unmount-versus-hide deliberately**, because it determines whether state survives.

**They never write `{count && ...}`.**

## Common pitfalls

- `{0 && ...}` rendering a stray zero.
- Deeply nested ternaries.
- Parallel booleans permitting impossible states.
- Unmounting a component that should have preserved its state, or vice versa.
- A component with six boolean props and a conditional for each.
- Assuming `display: none` keeps content available to assistive technology.
- Optional chaining scattered through components instead of normalizing data once.

## Interview angle

The `{0 && ...}` bug is asked directly and often, so explain it precisely: `&&` returns the falsy left operand, and React renders `0` but skips `false`/`null`/`undefined`. Beyond that, the strong material is the state-modeling point — replacing boolean flags with a status union so invalid states cannot be represented — and the unmount-versus-hide distinction, since both show design thinking rather than syntax recall.
