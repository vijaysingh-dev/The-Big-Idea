# Common Errors and How to Read Them

## A reference for the errors you will actually see

Each entry: what it means, what causes it, and what to do. Ordered roughly by how often they appear.

---

## Governor limits

**`System.LimitException: Too many SOQL queries: 101`**

A query in a loop, or accumulated automation across triggers, flows, and packages sharing the 100-query budget.

Find it with:

```bash
grep "SOQL_EXECUTE_BEGIN" debug.log | sort | uniq -c | sort -rn | head
```

A query appearing 200 times is in a loop, and the bracketed number is the line. If nothing is in a loop, the budget is being spent by other automation — check the per-namespace limit block. See [[16.2 - SOQL and DML Limits]].

**`System.LimitException: Apex CPU time limit exceeded`**

The hardest to diagnose, because the cause is frequently not your code. Nested loops, `getGlobalDescribe()` in a loop, string concatenation with `+=`, or accumulated flows and validation rules.

Bracket the sections with `Limits.getCpuTime()` to find where it goes. If the cost is in the DML rather than in your code, the problem is downstream automation. See [[16.3 - CPU Time and Heap Size]].

**`System.LimitException: Apex heap size too large: 6291456`**

A query returning too many wide rows, a static collection accumulating, or string building in a loop.

A checkpoint's Extents panel names what is holding the memory. See [[20.4 - Heap Dumps and Checkpoints]].

**`System.LimitException: Too many DML rows: 10001`**

Cascading operations count. Updating 200 records that each cascade a roll-up processes 400 or more.

**`System.LimitException: Too many callouts: 101`**

One callout per record instead of one per batch.

## DML and save errors

**`UNABLE_TO_LOCK_ROW`**

Two transactions competing for the same record — nearly always a shared parent. Ask **what the failing records have in common**; it is a shared account, asset, or owner.

Fixes: sort by parent Id before loading, use serial mode in the Bulk API, reduce roll-ups on the hot parent, or address ownership skew. See [[10.8 - Record Locking and Deadlocks]] and [[10.9 - Data Skew]].

Transient — worth retrying.

**`MIXED_DML_OPERATION`**

```
DML operation on setup object is not permitted after you have updated
a non-setup object (or vice versa)
```

`User`, `PermissionSetAssignment`, `GroupMember`, and similar cannot share a transaction with normal objects. Move one side to a Queueable, or wrap in `System.runAs` in a test. See [[10.7 - Mixed DML and Setup Objects]].

**`FIELD_CUSTOM_VALIDATION_EXCEPTION`**

A validation rule rejected the record. The message is the rule's own error text.

Permanent — retrying achieves nothing. If the rule is firing unexpectedly, something before step 6 of the order of execution changed the field: a before-save flow or a before trigger. See [[07.13 - Order of Execution]].

**`INVALID_CROSS_REFERENCE_KEY`**

A lookup pointing at a record that does not exist, or one the user cannot access.

In a bulk load, **this almost always means load order** — children before parents, or an external key that does not resolve.

**`REQUIRED_FIELD_MISSING`**

A field required at the layout level does not block the API; a field required at the field level does. The message names the field.

**`ENTITY_IS_LOCKED`**

The record is in an approval process. Automation attempting to update a locked record fails until it is approved or recalled. See [[04.16 - Approval Processes in the Sales Cycle]].

**`CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY`**

A trigger threw. The message usually names the class and line, and the real error follows it.

**`STORAGE_LIMIT_EXCEEDED`**

The org is out of data storage. Not a code problem.

**`DUPLICATE_VALUE`**

A unique field or external ID collision. In an upsert, this often means the external ID is not actually unique — which also produces `300 Multiple Choices` through the REST API.

## Callouts

**`You have uncommitted work pending. Please commit or rollback before calling out.`**

A callout after DML in the same transaction. Move it to a Queueable or a platform event subscriber. See [[13.14 - Apex Callouts]].

**`System.CalloutException: Read timed out`**

The external system did not respond within the timeout. Transient, and worth retrying with backoff.

If it is persistent, the timeout may be too short — the default is 10 seconds.

**`System.CalloutException: Unauthorized endpoint`**

No Remote Site Setting and no Named Credential for that URL. Use a Named Credential. See [[13.13 - Named Credentials and External Credentials]].

**`Methods defined as TestMethod do not support Web service callouts`**

A callout in a test with no mock registered. See [[19.5 - Mocking Callouts]].

**HTTP 401 that persists**

The credential is wrong or revoked. The platform refreshes tokens automatically, so a single 401 may be transient and a repeated one is configuration.

## Authentication

**`invalid_grant`**

The least informative and most common OAuth error. It covers, in order of likelihood:

```
Wrong login endpoint — login.salesforce.com for a sandbox
The user has not been pre-authorized for the connected app
Permitted Users is not set to admin-approved (JWT flow)
An expired or already-used authorization code
Clock drift beyond the assertion's expiry window
An IP restriction
```

Working through them in that order is faster than guessing. Verify with the CLI first, which isolates configuration from client code:

```bash
sf org login jwt --client-id {key} --jwt-key-file server.key \
  --username integration@northwind.com --instance-url https://myorg.my.salesforce.com
```

See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**`INVALID_SESSION_ID`**

The token expired, or `UserInfo.getSessionId()` was used in an async context where it is unavailable. Use a Named Credential pointing at the org itself.

**`REQUEST_LIMIT_EXCEEDED`**

The daily API allocation is exhausted — org-wide, affecting every integration until the window resets. Check `OrgLimits` and find the consuming client.

## Lightning components

**"An internal server error has occurred"**

An uncaught Apex exception in an `@AuraEnabled` method. Throw `AuraHandledException` with a usable message and a log reference instead. See [[14.16 - Error Handling and Toasts]].

**The component does not appear in App Builder**

In order: `isExposed` is false, the target is missing, the object is not in `targetConfig`, or the FlexiPage was not deployed. See [[14.19 - Deploying and Exposing Components]].

**The component appears blank for some users**

The user lacks access to the Apex class it calls. Apex class access is granted through a permission set, and the developer's admin profile hides the problem.

**A field is undefined in JavaScript**

The wrapper property has no `@AuraEnabled` annotation. Every property crossing to the client needs it.

**The UI does not update after a change**

A field was mutated rather than reassigned. `this.claims.push(x)` does not rerender; `this.claims = [...this.claims, x]` does. See [[14.4 - Reactivity and Decorators]].

**Stale data after a save**

The Apex wire cache was not invalidated. `refreshApex` for Apex wires, `notifyRecordUpdateAvailable` for LDS — they are different caches. See [[14.11 - refreshApex and Cache Invalidation]].

## Deployment

**`Deploy failed: Test coverage of selected Apex Class is 0%`**

A class with no coverage in a deployment that requires it. Either include its test or check whether the class is dead code.

**`Cannot modify a scheduled Apex class`**

A scheduled job exists for the class. Abort the job, deploy, reschedule — which is why scheduler classes should be trivial and rarely changed. See [[12.5 - Scheduled Apex]].

**`Cannot delete field: referenced by...`**

A formula, validation rule, flow, layout, report type, or Apex class references it. The dependency query finds them:

```sql
SELECT MetadataComponentName, MetadataComponentType
FROM MetadataComponentDependency
WHERE RefMetadataComponentName = 'Claim_Amount__c'
```

**A profile deployment removed permissions**

Profiles retrieve only permissions for metadata also in the retrieval. Retrieve profiles alongside their objects and fields, and prefer permission sets in source control. See [[13.6 - Metadata API and Tooling API]].

## Async

**A job silently did not run**

Check `AsyncApexJob` for `Failed` or `Aborted`, and check the daily async allocation — exhaustion is org-wide and produces no per-job error.

**`Database.AllowsCallouts` missing**

A runtime failure on the first callout, in a job that may only sometimes call out.

**A platform event subscriber did nothing**

In a test, `Test.getEventBus().deliver()` was omitted. In production, check `EventBusSubscriber` for lag, and set a trace flag on the **Automated Process user** — a flag on the publisher captures nothing.

**A batch job failed on some chunks**

Usually scope size. Halve it. If the failures cluster around certain records, it is contention.

## Reading an unfamiliar error

The general approach.

**1. Read the whole message.** Salesforce errors frequently contain the real cause after the status code.

```
CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY: ClaimTrigger: execution of AfterUpdate
caused by: System.NullPointerException: Attempt to de-reference a null object
Class.ClaimRollupService.recalculate: line 47, column 1
```

The status code is the outer failure; the null pointer at line 47 is the actual bug.

**2. Identify the layer.** Governor limit, DML, callout, authentication, or component.

**3. Ask whether it is transient or permanent.** Locks and timeouts are transient; validation and permissions are not. See [[13.17 - Error Handling, Retries and Idempotency]].

**4. Ask what changed.** `SetupAuditTrail` covers six months and answers "who deactivated the flow".

**5. Ask what the failing records have in common.** For contention and skew, this is the whole diagnosis.

## Errors that mislead

Worth knowing, because they send people in the wrong direction.

**A governor limit error names your code, and your code may be fine.** The budget is shared with flows, validation rules, roll-ups, and managed packages.

**`CONCURRENT_REQUESTS_LIMIT_EXCEEDED` names the rejected request**, which is usually a fast, well-written one. The cause is ten *other* slow requests.

**`invalid_grant` says nothing useful.** Work the list.

**A null pointer in a roll-up service** is frequently a missing parent, not a bug in the arithmetic.

**"An internal server error has occurred"** means an uncaught exception, not a platform fault.

---

## Practical guidance

**Read past the status code** — the real cause usually follows.

**Classify as transient or permanent** before deciding to retry.

**Check `SetupAuditTrail`** when something worked yesterday.

**Ask what the failing records share** for contention errors.

**Do not trust that a limit error names the culprit.**

**Verify authentication with the CLI** before debugging client code.

**Trace the Automated Process user** for event and CDC subscribers.
