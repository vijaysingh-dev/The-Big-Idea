# Evaluation Pipelines and Monitoring

## Why Offline Evals Aren't Enough

Offline evaluation (golden sets, RAGAS, benchmark suites — see [[../04 - Fine-Tuning and Model Adaptation/04.5 - Evaluation - Offline vs Online|04.5]] and [[../05 - RAG Systems/05.8 - RAG Evaluation Frameworks|05.8]]) tells you whether a system is good *before* shipping. It says nothing about what's happening in production right now:

- Real queries drift away from the eval set's distribution over time
- Upstream data changes (new document types, schema changes) silently degrade retrieval
- A model provider updates weights behind a pinned name and quality shifts
- Users find failure modes no eval set anticipated

Production evaluation pipelines and monitoring exist to catch what offline evals structurally cannot: continuous, real-traffic signal.

---

## LLM-as-Judge in Production

Running a full eval suite against every production response is expensive. The common pattern is **sampled, asynchronous judging**:

```python
async def judge_response(query: str, context: list[str], response: str) -> dict:
    judge_prompt = f"""Rate this AI response on a 1-5 scale for each dimension.

Query: {query}
Retrieved context: {context}
Response: {response}

Dimensions:
- faithfulness: is every claim supported by the context? (1=hallucinated, 5=fully grounded)
- relevance: does the response answer the query? (1=off-topic, 5=directly answers)
- completeness: does it use the available context fully? (1=missed key info, 5=complete)

Output JSON: {{"faithfulness": int, "relevance": int, "completeness": int, "reasoning": str}}"""

    result = await judge_llm.call(judge_prompt, response_format="json")
    return json.loads(result)

async def sampled_production_eval(query, context, response, sample_rate=0.05):
    if random.random() < sample_rate:
        scores = await judge_response(query, context, response)
        log_eval_scores(query, scores)
```

**Judge model selection**: use a different, typically stronger model than the one being judged (avoids self-preference bias), and pin its version — an unpinned judge makes score trends meaningless when the judge silently changes.

**Known judge biases to correct for** (see [[../13 - LLM Serving and Operations/13.3 - Evaluation Deep Dive|13.3]] for the underlying research):

|Bias|Effect|Mitigation|
|---|---|---|
|Position bias|Prefers first-listed option in pairwise comparisons|Randomize order, average both directions|
|Verbosity bias|Longer responses score higher regardless of quality|Explicit length-normalization instruction in judge prompt|
|Self-enhancement|Judge favors outputs from its own model family|Use a judge from a different provider than the production model|

## Drift Detection

Drift is any shift in the distribution of inputs, outputs, or quality scores relative to a known-good baseline.

### Types of Drift to Track

|Type|What changed|Detection signal|
|---|---|---|
|**Query drift**|Users ask different kinds of questions than the eval set covers|Embedding-space distance between live queries and eval set centroid|
|**Retrieval drift**|Same query now returns different/worse chunks|Overlap (Jaccard) between retrieved doc IDs week-over-week|
|**Model drift**|Provider updates a pinned model's underlying weights|Automated eval score deltas on a fixed regression set, run daily|
|**Quality drift**|Judge/user scores trend downward over time|Rolling 7-day average of judge scores vs a control band|

### Query Drift Detection

```python
def compute_query_drift(live_queries: list[str], eval_set_queries: list[str]) -> float:
    live_embeddings = embed_batch(live_queries)
    eval_embeddings = embed_batch(eval_set_queries)

    live_centroid = np.mean(live_embeddings, axis=0)
    eval_centroid = np.mean(eval_embeddings, axis=0)

    # Cosine distance between centroids — rising trend means the eval set
    # no longer represents what users are actually asking
    return 1 - cosine_similarity(live_centroid, eval_centroid)
```

### Automated Regression Detection

Run the full golden-set eval on a schedule, not just at deploy time — this catches silent upstream model updates:

```python
async def daily_regression_check(golden_set, baseline_scores, threshold=0.05):
    current_scores = await run_eval(current_config, golden_set)

    for metric, baseline in baseline_scores.items():
        delta = baseline - current_scores[metric]
        if delta > threshold:
            alert(
                f"Regression on {metric}: {baseline:.2f} → {current_scores[metric]:.2f}",
                severity="high",
            )
```

This is what catches a model provider changing behavior under a pinned version string, or a reranker service silently degrading.

## Monitoring Dashboards

Production AI monitoring needs three layers, each answering a different question:

|Layer|Question it answers|Example metrics|
|---|---|---|
|**System health**|Is the infrastructure working?|P50/P95/P99 latency, error rate, throughput, token usage|
|**Quality**|Are responses good?|Judge scores, faithfulness rate, citation accuracy, user thumbs-down rate|
|**Business**|Is this delivering value?|Task completion rate, escalation-to-human rate, session length|

```python
@dataclass
class QueryMetrics:
    query_id: str
    timestamp: datetime
    latency_ms: int
    prompt_version: str
    model_id: str
    retrieval_score: float | None      # top-chunk similarity
    judge_scores: dict | None          # sampled — not every query
    user_feedback: str | None          # thumbs up/down, if given
    error: str | None

def emit_metrics(m: QueryMetrics):
    metrics.histogram("query.latency_ms", m.latency_ms, tags={"model": m.model_id})
    if m.judge_scores:
        for dim, score in m.judge_scores.items():
            metrics.gauge(f"quality.{dim}", score, tags={"prompt_version": m.prompt_version})
    if m.user_feedback:
        metrics.increment(f"feedback.{m.user_feedback}")
```

**Dashboard design principle**: quality metrics should always be sliced by `prompt_version` and `model_id`. An aggregate quality number that blends two prompt versions hides the exact regression a version rollout would otherwise reveal (see [[10.6 - Prompt and Model Versioning]]).

## Alerting Thresholds

Alert fatigue is the main failure mode of AI monitoring — too many low-signal alerts trains engineers to ignore them. Alert on trend breaks, not point-in-time noise:

```python
ALERT_RULES = {
    "latency_p95_ms": {"threshold": 5000, "window": "5m"},
    "error_rate": {"threshold": 0.02, "window": "5m"},
    "judge_faithfulness_avg": {"threshold": -0.10, "window": "1h", "type": "relative_drop"},
    "user_thumbs_down_rate": {"threshold": 0.15, "window": "1h"},
}
```

Route infrastructure alerts (latency, errors) to on-call immediately. Route quality alerts (judge score drops, drift) to a daily digest unless the drop is severe — quality regressions rarely need a 2am page, but they do need someone to look within a day.
