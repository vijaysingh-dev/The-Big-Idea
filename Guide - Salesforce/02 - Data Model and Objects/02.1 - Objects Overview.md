# Objects Overview

## What an object is

An **object** is Salesforce's word for a table. A record is a row. A field is a column. If you have used any relational database, the mental model transfers directly.

What does not transfer is that an object is not a physical table ([[01.5 - Multi-Tenant Architecture]]). Creating one inserts metadata rather than running `CREATE TABLE`. That is why it takes two seconds and why you get a user interface, an API, reports, search, sharing, and an audit trail for free the moment it exists.

There are four kinds, and they differ in where the data physically lives and what the platform will do for you.

## The four kinds

| Type | Where data lives | Suffix | Counts against storage | Typical use |
| --- | --- | --- | --- | --- |
| Standard | Salesforce | none | Yes | Account, Contact, Case — the CRM itself |
| Custom | Salesforce | `__c` | Yes | Anything specific to your business |
| External | Another system | `__x` | No | Data you read but do not own |
| Big | Salesforce, separate store | `__b` | No (separate allocation) | Billions of rows of history or events |

The `__c` suffix on custom objects and fields is not decoration. It is how the platform distinguishes your metadata from its own, and it appears everywhere: API names, SOQL, Apex, integration payloads.

## Standard objects

Built by Salesforce, present in every org, and heavily wired into product features. Account, Contact, Lead, Opportunity, Case, Campaign, Product2, Pricebook2, Quote, Contract, Order, Task, Event, User.

They come with things you would otherwise build yourself: forecasting on Opportunity, escalation on Case, conversion on Lead, the mobile experience, Einstein scoring, and dozens of report types.

Their constraints are the price. You cannot delete a standard object or its standard fields. You cannot rename the API name. You can rename labels, add custom fields, and hide fields with permissions, but the underlying structure is fixed.

**The rule that saves the most pain: use the standard object if the concept matches, even imperfectly.** Rebuilding Opportunity as `Deal__c` because the standard one has fields you dislike is one of the most expensive mistakes in this ecosystem. You lose forecasting, quoting, the sales path, Einstein, and every standard report, and you spend the next five years reimplementing them badly.

## Custom objects

Everything the CRM does not model. In a manufacturing business that might be `Machine__c`, `Warranty_Claim__c`, `Service_Contract__c`, `Shipment__c`.

You get the same platform features standard objects get — tabs, layouts, reports, sharing, API access, triggers, history tracking. You also get full control: rename it, delete it, restructure it.

Edition limits apply. Enterprise Edition allows a few hundred custom objects and a few hundred custom fields per object. Large orgs genuinely reach these ceilings, which is one reason experienced engineers resist creating a field for every request. See [[01.4 - Salesforce Editions and Licensing]].

```sql
SELECT Id, Name, Serial_Number__c, Warranty_Expiry__c, Account__c
FROM Machine__c
WHERE Warranty_Expiry__c = NEXT_N_DAYS:90
```

## External objects

An external object looks like a normal object but stores nothing. Queries against it are translated into live calls to an outside system through **Salesforce Connect** — an OData service, a custom Apex adapter, or a cross-org connection.

The record you see was fetched a moment ago from an ERP, a data warehouse, or a legacy database. Nothing is copied into Salesforce.

Use it when data is large, changes constantly, is legally required to stay elsewhere, or is simply not worth the storage. Do not use it when you need the data offline, need to report on it heavily, or need automation to fire on it — external objects support only limited triggers, no roll-ups, and no standard reporting joins. Full treatment in [[02.14 - External Objects and Salesforce Connect]].

## Big objects

Storage for volumes that would destroy a normal object: hundreds of millions or billions of rows. Audit history, device telemetry, transaction logs, long-term archives.

The tradeoff is severe and deliberate. A big object has no user interface to speak of, no triggers, no roll-ups, no standard reports. Queries must filter on the index fields you defined when creating it, in order, and anything else requires **Async SOQL**, which returns results into another object rather than to your code. See [[02.15 - Big Objects]].

## Choosing between them

The decision sequence experienced engineers actually run:

1. **Does a standard object model this concept?** If yes, use it. Accept imperfect fit.
2. **Do we own this data and need it in Salesforce?** If no, external object.
3. **Will this exceed roughly ten million rows and mostly be written and rarely read?** If yes, big object.
4. **Otherwise, custom object.**

Step 1 is where most bad architectures start. A requirement described as "we need to track deals but ours are different" is almost always Opportunity with custom fields and a record type.

## Naming, and why it matters permanently

API names are effectively forever. Renaming one breaks every Apex reference, formula, flow, integration payload, and report that uses it, and some of those break silently.

Conventions worth holding to:

- Singular object names: `Warranty_Claim__c`, not `Warranty_Claims__c`
- Descriptive field names that survive a business reorganization: `Annual_Contract_Value__c`, not `ACV_2024__c`
- Never encode a system, team, or year into a name
- Avoid abbreviations that only the current team understands

## Inspecting objects at runtime

Reading an org's schema programmatically is a core skill, used by dynamic components, validation utilities, and org-analysis tooling.

```java
// Everything the org knows about a given object
Schema.DescribeSObjectResult describe = Machine__c.SObjectType.getDescribe();
System.debug(describe.getLabel() + ' / queryable: ' + describe.isQueryable()
             + ' / createable: ' + describe.isCreateable());

// All objects in the org, useful for scanners and admin tooling
for (Schema.SObjectType objType : Schema.getGlobalDescribe().values()) {
    Schema.DescribeSObjectResult d = objType.getDescribe();
    if (d.isCustom() && d.isCreateable()) {
        System.debug(d.getName());
    }
}
```

`getGlobalDescribe()` is expensive — it walks every object in the org and consumes real CPU time. Call it once and cache the result in a static variable rather than inside a loop. This is a common cause of `Apex CPU time limit exceeded` in code that looks harmless. See [[16.3 - CPU Time and Heap Size]].
