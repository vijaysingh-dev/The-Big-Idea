# Cookies Sessions and CORS

#backend #http #security #browser

> **In one line:** Cookies are sent automatically by the browser, which is both their entire usefulness and the reason CSRF exists — and CORS is the browser's rule about which sites may read your API's responses, not about who may call it.

---

## Cookies

### The mechanics

```http
Set-Cookie: session=abc123; Path=/; Domain=api.example.com; Max-Age=3600;
            Secure; HttpOnly; SameSite=Lax
```

The browser stores it and sends it on every matching request, automatically, without your code doing anything.

```http
Cookie: session=abc123; theme=dark
```

⚠️ **"Automatically" is the important word.** A request triggered by another website also carries your cookies. That is the root of CSRF.

### The attributes

| Attribute | Effect |
|---|---|
| `Secure` | HTTPS only. **Always set this** |
| `HttpOnly` | JavaScript cannot read it. Blocks theft via XSS |
| `SameSite=Strict` | Never sent on cross-site requests, including normal link clicks |
| `SameSite=Lax` | Sent on top-level navigations (clicking a link), not on cross-site POSTs or subresources. **The modern default** |
| `SameSite=None` | Sent on all cross-site requests. **Requires `Secure`** |
| `Path=/app` | Only sent for matching paths |
| `Domain=example.com` | Sent to that domain **and all subdomains** |
| `Max-Age` / `Expires` | Lifetime. Without either, it dies with the browser session |
| `__Host-` prefix | Browser enforces `Secure`, `Path=/`, and no `Domain` |

💡 **`SameSite=Lax` is now the browser default** when the attribute is absent, and it eliminates most classic CSRF on its own. It does not eliminate all of it — a cross-site GET that mutates state still works, which is one more reason GET must be safe ([[03.3 - Methods Status Codes and Semantics]]).

⚠️ **`Domain=example.com` is broader than people expect.** It sends the cookie to `evil.example.com` too. In an organisation where subdomains are handed out to teams or customers, this is a real risk. Omit `Domain` entirely to scope the cookie to the exact host, and use the `__Host-` prefix to have the browser enforce it.

```http
Set-Cookie: __Host-session=abc; Path=/; Secure; HttpOnly; SameSite=Lax
```

The `__Host-` prefix is free security. Use it.

### Size and count

- ~4KB per cookie
- ~50 cookies per domain
- All cookies are sent on **every** request to that domain

⚠️ **A 3KB JWT in a cookie is 3KB added to every request, including every image and asset request to that domain.** On a page with 50 assets that is 150KB of pure overhead per page load. This is a real argument against putting large tokens in cookies, and against serving assets from the same domain as your API.

## Sessions

Two models, and the choice has real consequences.

### Server-side sessions

```
Cookie: session=abc123     →   Redis: session:abc123 → {user_id: 7, org: 3}
```

| | |
|---|---|
| **Good** | Instant revocation. Tiny cookie. Data never leaves your infrastructure |
| **Bad** | A lookup per request. A store to run and scale |

### Token-based (JWT in a cookie)

```
Cookie: session=eyJhbGc...   →   verify signature, read claims
```

| | |
|---|---|
| **Good** | No lookup. Stateless. Easy horizontal scaling |
| **Bad** | **Cannot revoke.** Large cookie. Claims go stale |

💡 **The revocation problem is the real one.** "Log out everywhere", "this user was fired", "this token leaked" — none of them work with pure JWTs. The standard workaround is short-lived access tokens plus a refresh token that *is* checked against a store, which means you have a session store anyway, just consulted less often.

⚠️ **Be honest about this in interviews.** "JWTs are stateless so they scale better" is only true if you never need revocation, and almost every real system does. The considered answer is: short access token lifetime (5–15 minutes), refresh tokens in a revocable store, and a denylist for emergency revocation within the access-token window.

Covered fully in [[14.2 - Sessions Tokens and Rotation]].

## CSRF

### The attack

You are logged into `bank.com`. You visit `evil.com`, which contains:

```html
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

The browser sends the request **with your bank.com cookies**, because that is what cookies do. The bank sees an authenticated request and honours it.

### Defences

| Defence | How |
|---|---|
| **`SameSite=Lax` or `Strict`** | Browser will not send the cookie cross-site. **Primary defence now** |
| **CSRF token** | A random value in a form field or header that the attacker cannot read |
| **Double-submit cookie** | Same value in a cookie and a header; the attacker cannot set the header |
| **Origin / Referer check** | Reject requests from unexpected origins |
| **Do not use cookies** | Bearer token in an `Authorization` header is not sent automatically |

💡 **The cleanest answer for a modern API: do not authenticate with cookies.** An `Authorization: Bearer` header is never sent automatically by the browser, so CSRF simply does not apply. Cookies remain necessary when the browser must send credentials without JavaScript — server-rendered apps, and downloads or `<img>` tags that need auth.

### The layered position

For a cookie-authenticated API, use all of:

1. `SameSite=Lax` (or `Strict` where usable)
2. A CSRF token on all state-changing requests
3. An `Origin` header check

Any one can be bypassed in some browser or configuration. Together they are solid.

## CORS

### What it actually is

CORS is a **browser** restriction, and this is the part everyone gets wrong.

```
JavaScript on evil.com  →  fetch("https://api.bank.com/me")
```

The request **is sent**. The server **does receive and process it**. The browser then refuses to give the response to the JavaScript unless the server said it was allowed.

⚠️ **CORS is not access control.** It does not stop a request. `curl`, Python, a mobile app and a server-side proxy all ignore CORS entirely. It protects *users* from *malicious sites reading responses*, not your API from unauthorised callers.

**Never treat CORS as a security boundary.** Your authorization checks must stand on their own.

### Simple requests

Some requests are sent without a preflight:

- Method is `GET`, `HEAD` or `POST`
- `Content-Type` is `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`
- No unusual headers

```http
GET /me HTTP/1.1
Origin: https://app.example.com

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
```

⚠️ **`Content-Type: application/json` is not on the simple list**, which is why almost every JSON API triggers a preflight.

### Preflight

```http
OPTIONS /documents HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
Vary: Origin
```

💡 **`Access-Control-Max-Age` is the one people forget.** Without it, the browser preflights **every single request** — doubling your request count and adding a full round trip to each call. Setting it to 86400 caches the preflight for a day.

⚠️ Chrome caps it at 2 hours regardless of what you send. Still worth setting.

### The credentials rule

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true      # ← ILLEGAL COMBINATION
```

The browser rejects this. With credentials (cookies), you must echo a specific origin:

```python
allowed = {"https://app.example.com", "https://admin.example.com"}

origin = request.headers.get("origin")
if origin in allowed:
    response.headers["Access-Control-Allow-Origin"] = origin
    response.headers["Access-Control-Allow-Credentials"] = "true"
    response.headers["Vary"] = "Origin"
```

⚠️ **`Vary: Origin` is mandatory here.** Without it, a cache stores the response with one origin's `Access-Control-Allow-Origin` header and serves it to a different origin, which then fails — or worse, succeeds when it should not. This bug is intermittent and depends on cache state, which makes it miserable to diagnose.

### The dangerous shortcut

```python
# Reflecting any origin — effectively allow-all, with credentials
response.headers["Access-Control-Allow-Origin"] = request.headers["origin"]
response.headers["Access-Control-Allow-Credentials"] = "true"
```

This lets **any** website read authenticated responses from your API on behalf of a logged-in user. It is a full account-takeover primitive and it appears in real codebases because it makes the error message go away.

Always use an explicit allow-list.

### In FastAPI

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["content-type", "authorization"],
    expose_headers=["x-request-id", "etag"],
    max_age=86400,
)
```

⚠️ **`expose_headers` is needed for JavaScript to read any non-standard response header.** By default only a handful are visible. If your frontend cannot read `ETag` or `X-Request-Id`, this is why — and the symptom (header present in devtools, absent in JavaScript) is confusing until you know.

## In Production

### The CORS debugging sequence

```bash
# 1. Simulate the preflight
curl -X OPTIONS https://api.example.com/documents \
  -H 'Origin: https://app.example.com' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type' -i

# 2. Simulate the actual request
curl https://api.example.com/documents -H 'Origin: https://app.example.com' -i
```

| Symptom | Cause |
|---|---|
| Works in Postman, fails in browser | It is CORS. Postman ignores it |
| Preflight returns 404 | Your router does not handle `OPTIONS` |
| Preflight returns 401 | **Auth middleware is running before CORS.** Preflights carry no credentials |
| Works, then intermittently fails | Missing `Vary: Origin`, cache poisoning |
| Header present in devtools, missing in JS | Missing `expose_headers` |
| Cookie not sent | Missing `credentials: 'include'` on the client, or `SameSite` |
| Every request is slow | Missing `max-age`, preflighting everything |

⚠️ **"Preflight returns 401" is the most common one and the most confusing.** A preflight `OPTIONS` request carries no cookies and no `Authorization` header — by design. If your authentication middleware runs before your CORS middleware, it rejects the preflight, and the browser reports a CORS error rather than an auth error. **Order your middleware so CORS runs first.**

### Cookies in a multi-service setup

```
app.example.com     → frontend
api.example.com     → backend
```

These are different *hosts* but the same *site* (same registrable domain), so `SameSite=Lax` cookies are still sent. Good.

```
app.example.com     → frontend
api.example-cdn.io  → backend
```

Different sites. You need `SameSite=None; Secure`, which reopens CSRF and is increasingly restricted by browsers blocking third-party cookies.

💡 **Design your domains so the frontend and API are the same site.** Use a subdomain, or route the API through the frontend's origin at `/api`. This avoids third-party cookie restrictions entirely and is one of those architectural choices that is trivial at the start and painful later.

### The tenant-subdomain risk

If Conduit gives each organisation a subdomain (`acme.conduit.app`), then a cookie with `Domain=conduit.app` is sent to every tenant's subdomain. A tenant who can inject content into their own subdomain can read it.

Scope cookies to the exact host, and treat every tenant subdomain as untrusted. This is [[14.6 - Multi Tenant Isolation]] territory and it is worth deciding before you ship subdomains.

## Codebase

**Repo:** `encode/starlette`, `django/django`, `chromium` (docs)

**Question to answer:** In Starlette's CORS middleware, trace what happens to a preflight request versus a real one. Where would placing an auth middleware break it? Then: how does Django's CSRF protection actually work, and why does it use both a cookie and a form field?

**Read, in order:**

1. `starlette/middleware/cors.py` — **the whole file, it is short.** Find `preflight_response` and note that it short-circuits before reaching your app. That is why middleware order matters
2. `starlette/middleware/sessions.py` — cookie-based signed sessions. Note the size limit and the signing
3. `django/django/middleware/csrf.py` — the double-submit implementation, including token masking. **The masking is a BREACH mitigation** ([[03.6 - Compression and Streaming Responses]]) and the comments say so
4. `django/django/http/response.py` — `set_cookie` and the attribute handling, including `SameSite` defaults
5. Chromium's SameSite explainer and the third-party cookie deprecation documentation — for where browser behaviour is heading

💡 The Django CSRF source is unusually well commented and it explains *why* each defence exists, including attacks you may not have heard of. It is a better security education than most dedicated material.

**Size:** 1 session.

## Exercise

**Drill 3.7 — Attack your own app**

Build the attacks first. They are what make the defences memorable.

```
drills/03-browser/
├── app/
│   ├── api.py            # cookie-authenticated API
│   ├── frontend/         # a real page on a different origin
│   └── config.py         # toggle every defence
├── attacks/
│   ├── csrf_form.html    # classic form CSRF
│   ├── csrf_get.html     # GET that mutates
│   ├── cors_read.html    # read responses cross-origin
│   └── subdomain.html    # cookie leakage across subdomains
├── defences/
│   ├── samesite.py
│   ├── csrf_token.py     # double-submit with masking
│   ├── origin_check.py
│   └── bearer.py         # the no-cookie approach
├── cors/
│   ├── preflight.sh      # every preflight scenario
│   ├── middleware_order.py    # auth-before-CORS, the 401 bug
│   ├── vary_poisoning.py
│   └── FINDINGS.md
├── cost/
│   └── preflight_cost.py # measure with and without max-age
└── README.md
```

⚠️ Everything here runs against your own local stack only.

**Part 1 — Build a vulnerable app.** Cookie session auth, no `SameSite`, no CSRF token, a `POST /transfer` endpoint. Serve a frontend on a genuinely different origin (different port counts, but use different hostnames via `/etc/hosts` for realism).

**Part 2 — CSRF, for real.** Write `csrf_form.html` on the attacker origin. Log into your app in the browser, then visit the attacker page. **Watch the transfer succeed.**

Then enable `SameSite=Lax` and watch it fail. Then write `csrf_get.html` — a GET endpoint that mutates — and show that `Lax` **does not** stop it, because top-level navigations still carry the cookie.

That second demonstration is the important one. It is why "safe methods must be safe" is a security requirement and not style guidance.

**Part 3 — Layer the defences.** Implement a double-submit CSRF token with per-request masking. Then an `Origin` header check. Confirm each blocks the attack independently.

Then implement bearer-token auth and show the attack becoming structurally impossible — the attacker's page cannot set an `Authorization` header.

**Part 4 — CORS is not access control.** With CORS configured to allow only your frontend, call the API from the attacker page and observe the browser blocking the response.

Then call the **same endpoint** with `curl` and with a Python script and get the data successfully.

**Write this in `FINDINGS.md` in one sentence.** It is the fact that most people have wrong, and stating it clearly is worth interview points.

**Part 5 — The 401 preflight.** Put your auth middleware before CORS middleware. Watch every browser request fail with a CORS error while `curl` with credentials works fine.

Capture the browser console message and the actual `OPTIONS` response side by side. This mismatch — a CORS error message caused by an auth problem — is why the bug takes so long to find.

**Part 6 — Vary poisoning.** Two allowed origins. Omit `Vary: Origin`. Put nginx with `proxy_cache` in front.

Request from origin A, then from origin B. Show origin B receiving A's `Access-Control-Allow-Origin` header and failing. Then add `Vary: Origin` and confirm the fix.

**Part 7 — The cost of preflights.** Measure total requests and total latency for 100 API calls with `max-age=0` and with `max-age=86400`. Chart both.

Also measure the effect of a 3KB cookie on a page loading 50 assets from the same domain — total bytes uploaded, with and without.

**Done when:**
- You successfully performed CSRF against your own app and then blocked it three ways
- You showed `SameSite=Lax` failing to stop a mutating GET
- You read your own API from `curl` while the browser was blocked, and can state why in one sentence
- You reproduced the auth-before-CORS 401 and captured both views of it
- Vary poisoning is demonstrated and fixed
- You have numbers for preflight cost and cookie overhead
