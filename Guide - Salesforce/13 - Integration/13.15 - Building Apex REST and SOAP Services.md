# Building Apex REST and SOAP Services

## When to build a custom endpoint

The standard REST API already exposes every object. A custom endpoint is worth building when:

**The operation is business logic, not data access.** "Submit a warranty claim" involves validation, coverage checking, and approval routing — not a record insert.

**Several records must change atomically**, with logic between them.

**The external system should not know your schema.** A stable endpoint contract insulates callers from field renames and model changes.

**Standard APIs cannot express it.** Lead conversion, merge, or anything requiring computation.

**You want a simpler contract** than the external team can build against the generic API.

Where the requirement genuinely is "create a record", the standard REST API is better — it needs no code, no tests, and no maintenance.

## Apex REST

```java
@RestResource(urlMapping='/claims/*')
global with sharing class ClaimResource {

    @HttpPost
    global static ClaimResponse submit(
        String assetSerialNumber,
        Decimal claimAmount,
        String faultDescription,
        String externalReference
    ) {
        try {
            ClaimSubmission submission = new ClaimSubmission(
                assetSerialNumber, claimAmount, faultDescription, externalReference
            );
            return ClaimSubmissionService.submit(submission);

        } catch (ClaimValidationException e) {
            RestContext.response.statusCode = 400;
            return ClaimResponse.failure(e.getMessage(), 'VALIDATION_FAILED');

        } catch (Exception e) {
            RestContext.response.statusCode = 500;
            AutomationLogger.logError('ClaimResource.submit', null, e.getMessage());
            return ClaimResponse.failure('An unexpected error occurred', 'INTERNAL_ERROR');
        }
    }

    @HttpGet
    global static ClaimResponse getStatus() {
        String claimNumber = RestContext.request.params.get('claimNumber');

        if (String.isBlank(claimNumber)) {
            RestContext.response.statusCode = 400;
            return ClaimResponse.failure('claimNumber is required', 'MISSING_PARAMETER');
        }

        return ClaimSubmissionService.getStatus(claimNumber);
    }
}
```

The endpoint is `/services/apexrest/claims/`.

**The annotations:** `@HttpGet`, `@HttpPost`, `@HttpPut`, `@HttpPatch`, `@HttpDelete`. One method per verb per class.

**`global` is required** on the class and its methods.

**Parameters are deserialized from the JSON body automatically** for POST, PUT, and PATCH — the parameter names must match the JSON keys. For GET and DELETE, read them from `RestContext.request.params`.

## RestContext


Reading a path parameter — the part matched by the wildcard:

```java
@HttpGet
global static ClaimResponse getByNumber() {
    String uri = RestContext.request.requestURI;
    // '/claims/CLM-99201' → 'CLM-99201'
    String claimNumber = uri.substring(uri.lastIndexOf('/') + 1);
    return ClaimSubmissionService.getStatus(claimNumber);
}
```

## URL mapping

```java
@RestResource(urlMapping='/claims/*')        // /services/apexrest/claims/anything
@RestResource(urlMapping='/claims/v2/*')     // versioned
@RestResource(urlMapping='/warranty/*')
```

**Versioning the path** is worth doing from the start. Once an external system depends on your contract, changing it breaks them, and a `/v2/` path lets both run during a migration.

Mappings must be unique across the org, which is another reason to namespace them by domain.

## Designing the contract

The part that matters more than the syntax.

**Return a consistent envelope**, so callers handle success and failure the same way:

```java
global class ClaimResponse {
    global Boolean success;
    global String errorCode;
    global String message;
    global String claimNumber;
    global String claimId;
    global Decimal approvedAmount;

    global static ClaimResponse failure(String message, String errorCode) {
        ClaimResponse response = new ClaimResponse();
        response.success = false;
        response.message = message;
        response.errorCode = errorCode;
        return response;
    }
}
```

**A machine-readable `errorCode`** matters more than the message. A caller branching on message text breaks the moment someone improves the wording.

**Set the HTTP status code**, and do not rely on the body alone. A caller checking only the status must not see 200 for a failure.

**Do not expose Salesforce internals.** Field API names, record Ids, and governor limit exceptions in an error message leak your schema and confuse the caller. Translate them.

```java
// Leaks internals
return ClaimResponse.failure(e.getMessage(), 'ERROR');
// 'FIELD_CUSTOM_VALIDATION_EXCEPTION: Claim_Amount__c exceeds Coverage_Limit__c'

// A contract the caller can act on
return ClaimResponse.failure(
    'The claim amount exceeds the coverage limit for this machine.',
    'COVERAGE_LIMIT_EXCEEDED'
);
```

## Bulk endpoints

An external system submitting 500 claims should not make 500 calls.

```java
@RestResource(urlMapping='/claims/batch/*')
global with sharing class ClaimBatchResource {

    global class BatchRequest {
        global List<ClaimSubmission> claims;
    }

    global class BatchResponse {
        global Integer submitted;
        global Integer failed;
        global List<ClaimResult> results;
    }

    @HttpPost
    global static BatchResponse submitBatch() {
        BatchRequest request = (BatchRequest) JSON.deserialize(
            RestContext.request.requestBody.toString(), BatchRequest.class
        );

        if (request.claims == null || request.claims.isEmpty()) {
            RestContext.response.statusCode = 400;
            return BatchResponse.empty();
        }
        if (request.claims.size() > 200) {
            RestContext.response.statusCode = 413;
            return BatchResponse.tooLarge();
        }

        // partial success, with a per-item result, so one bad claim does not reject the batch
        return ClaimSubmissionService.submitBatch(request.claims);
    }
}
```

**Deserializing the raw body** rather than using named parameters is how a list is accepted — Apex REST cannot bind a top-level array to a parameter.

**Cap the batch size** and return 413 above it, rather than letting a caller send 5,000 and hit governor limits.

**Return a per-item result** with partial success, matching the behaviour of `Database.insert(records, false)`.

## Security

An Apex REST endpoint is a **public endpoint** to anyone with a valid token. Every rule from [[03.13 - Enforcing Security in Apex and SOQL]] applies with more force.

```java
@RestResource(urlMapping='/claims/*')
global with sharing class ClaimResource {   // explicit sharing declaration

    @HttpGet
    global static ClaimResponse getStatus() {
        String claimNumber = RestContext.request.params.get('claimNumber');

        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Status__c, Approved_Amount__c, Account__c
            FROM Warranty_Claim__c
            WHERE Claim_Number__c = :claimNumber
            WITH USER_MODE
            LIMIT 1
        ];

        if (claims.isEmpty()) {
            // 404 rather than 403, so the response does not reveal whether the record exists
            RestContext.response.statusCode = 404;
            return ClaimResponse.failure('Not found', 'NOT_FOUND');
        }

        return ClaimResponse.from(claims[0]);
    }
}
```

The checklist:

- **Declare a sharing keyword.** A class with none runs without sharing when entered directly.
- **`WITH USER_MODE`** on queries, `as user` on DML.
- **`stripInaccessible`** on sObjects arriving in the body.
- **Verify ownership.** A caller supplying a claim number must not receive another customer's claim — check that the record belongs to the account the integration user is entitled to see.
- **Return 404, not 403**, for records the caller may not see, so the response does not confirm existence.
- **Validate and cap everything.** Batch size, string lengths, numeric ranges.

The ownership check is the one most often missing, and it is the same failure as the Agentforce action in [[05.15 - Einstein for Service and Agentforce]].

## Apex SOAP

Older, and occasionally required by a caller whose tooling expects a WSDL.

```java
global with sharing class ClaimWebService {

    webservice static String submitClaim(String serialNumber, Decimal amount) {
        ClaimSubmission submission = new ClaimSubmission(serialNumber, amount);
        return ClaimSubmissionService.submit(submission).claimNumber;
    }
}
```

The `webservice` keyword generates a WSDL, downloadable from the class detail page.

Constraints: `webservice` methods must be `static` and `global`, cannot be in a class with an inner class exposing certain types, and the WSDL is regenerated whenever the class changes — meaning callers may need to update.

**Do not build new SOAP services.** REST is simpler for both sides. This exists for callers who genuinely cannot do otherwise. See [[13.3 - SOAP API]].

## Testing

```java
@IsTest
static void submitReturnsClaimNumberForValidRequest() {
    Asset asset = TestDataFactory.createAssetWithCoverage('SN-88213');

    RestRequest req = new RestRequest();
    req.requestURI = '/services/apexrest/claims/';
    req.httpMethod = 'POST';
    RestContext.request = req;
    RestContext.response = new RestResponse();

    Test.startTest();
    ClaimResponse response = ClaimResource.submit('SN-88213', 150000, 'Bearing failure', 'EXT-1');
    Test.stopTest();

    Assert.isTrue(response.success, 'A valid submission should succeed');
    Assert.isNotNull(response.claimNumber, 'A claim number should be returned');
}

@IsTest
static void submitRejectsUncoveredAsset() {
    TestDataFactory.createAsset('SN-99999');   // no coverage

    RestContext.request = new RestRequest();
    RestContext.response = new RestResponse();

    Test.startTest();
    ClaimResponse response = ClaimResource.submit('SN-99999', 150000, 'Fault', 'EXT-2');
    Test.stopTest();

    Assert.isFalse(response.success);
    Assert.areEqual('NO_ACTIVE_COVERAGE', response.errorCode,
        'The error code is the contract, not the message');
    Assert.areEqual(400, RestContext.response.statusCode);
}
```

`RestContext.request` and `RestContext.response` must be constructed manually — they are null in a test otherwise, and code reading `RestContext.request.params` throws.

Asserting on the **error code and status code**, not the message, tests the contract the caller actually depends on.

## Documenting the contract

An endpoint nobody can integrate against is not useful. What the consuming team needs:

- The URL, verb, and authentication method
- Request and response schemas with example payloads
- Every error code and what causes it
- Rate limits and batch size caps
- Idempotency behaviour — is a retry safe?

Publishing an **OpenAPI specification** is the cleanest form, and it also enables External Services to consume the endpoint from a flow. See [[13.16 - External Services and Declarative Integration]].

## Limits

An Apex REST call runs as a **synchronous transaction** with standard limits: 100 SOQL queries, 150 DML statements, 10 seconds CPU, 6 MB heap.

It also counts against the **daily API request allocation**, one request per call.

**A callout cannot follow DML** inside the endpoint, which means an endpoint that saves a record and then notifies another system must enqueue the notification. See [[13.14 - Apex Callouts]].

For anything long-running, return a job Id immediately and let the caller poll:

```java
@HttpPost
global static AsyncResponse startBulkImport() {
    List<ClaimSubmission> claims = parseBody();
    Id jobId = System.enqueueJob(new BulkClaimImportQueueable(claims));

    RestContext.response.statusCode = 202;   // Accepted
    return new AsyncResponse(jobId, '/services/apexrest/jobs/' + jobId);
}
```

202 with a status URL is the standard shape for an operation that will complete later.

## Practical guidance

**Build a custom endpoint for business operations**, not for record access.

**Version the URL path** from the start.

**Return a consistent envelope** with a machine-readable error code.

**Set HTTP status codes**, and do not signal failure only in the body.

**Never leak Salesforce internals** in error messages.

**Cap batch sizes** and return partial results.

**Treat the endpoint as public**: sharing keyword, `USER_MODE`, ownership verification, 404 over 403.

**Construct `RestContext` in tests.**

**Publish an OpenAPI spec.**

**Return 202 with a job reference** for anything long-running.
