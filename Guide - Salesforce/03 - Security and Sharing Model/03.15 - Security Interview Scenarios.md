# Security Interview Scenarios

## How to use this note

Security is a topic where reasoning through cases is the only way to know you have understood it. These are the scenarios that come up in interviews and, more usefully, the ones that come up as real support tickets.

Work through each before reading the answer.

## The diagnostic method

Before the scenarios, the method they all use. When someone reports an access problem, three questions in order:

**1. Can they see any records of this object?** No means object permissions. Yes means the object is fine.

**2. Can they see some records but not this one?** That is record-level sharing.

**3. Can they see the record but a field is missing?** That is field-level security.

Then confirm rather than reason, using the two queries worth memorizing:

```sql
SELECT RecordId, HasReadAccess, HasEditAccess, HasDeleteAccess, MaxAccessLevel
FROM UserRecordAccess
WHERE UserId = :userId AND RecordId = :recordId
```

```sql
SELECT ParentId, UserOrGroupId, AccessLevel, RowCause
FROM Warranty_Claim__Share
WHERE ParentId = :recordId
```

The first says what access exists. The second says why.

## Scenario 1

> A sales rep can see all Accounts but cannot see any Opportunities, including ones on accounts they own. What is wrong?

**Answer.** Almost certainly the object permission. If they could see *some* opportunities it would be sharing, but seeing none at all — including on their own accounts — points at Read being missing on the Opportunity object in their profile and permission sets.

The tell is "including ones they own". Ownership always grants record access, so if ownership is not enough, the problem is above the record level.

Worth also checking: their user license. A Salesforce Platform license has no access to Opportunity at all, and no permission configuration will change that.

---

## Scenario 2

> Opportunity OWD is Private. A manager reports they cannot see their team's opportunities.

**Answer.** Check in order:

1. Does the manager have a **role**, and is it above the reps' roles in the role hierarchy? A manager with no role gets nothing from the hierarchy.
2. Is **Grant Access Using Hierarchies** enabled on Opportunity? It cannot be disabled for standard objects, so this rules itself out here, but on a custom object it would be the answer.
3. Are the reps' records actually **owned** by the reps? If a data load set the owner to an integration user, the hierarchy path does not exist.

The third is the most common real cause, and it is invisible unless you look at the owner.

Note that the User `Manager` field is irrelevant here. It drives approvals, not visibility. Confusing the two is the single most common misunderstanding in this area.

---

## Scenario 3

> Warranty Claim OWD is Private. The escalation team must see every claim marked Critical, regardless of owner or region. Design it.

**Answer.** A **criteria-based sharing rule** on Warranty Claim:

```
Criteria: Priority__c equals "Critical"
Share with: Public Group "Escalation Team"
Access: Read/Write
```

Share to a public group rather than a role, so team membership changes do not require touching the rule.

Access is granted and removed automatically as the priority field changes, which is the desired behaviour.

Follow-up worth anticipating: *what if they also need to delete claims?* Sharing rules cannot grant delete. Delete comes from ownership, the role hierarchy above the owner, or Modify All on the object. If the escalation team genuinely needs delete, that is Modify All on Warranty Claim in their permission set — with the understanding that this also bypasses the sharing model entirely for that object.

## Scenario 4

> A claim must be visible to whichever engineer is assigned to the active service contract covering that claim's machine. The engineer changes over time. Design it.

**Answer.** No declarative option works, because the condition lives two objects away — claim to machine to coverage to contract — and criteria-based rules can only evaluate fields on the record itself.

This is **Apex managed sharing**:

- A custom sharing reason on `Warranty_Claim__c`, so the shares survive ownership changes and can be identified for recalculation
- A service that computes the correct set of users and writes `Warranty_Claim__Share` rows
- Called from triggers on claim, coverage, and contract
- Recalculation done asynchronously, because a contract change can affect thousands of claims
- A scheduled full-rebuild job as a safety net

Full implementation in [[03.11 - Apex Sharing and Programmatic Sharing]].

A good follow-up answer: if the engineers form a stable team, sharing to a **public group** instead of individual users reduces the share row count by orders of magnitude and removes recalculation entirely on membership changes.

## Scenario 5

> A user can see a Warranty Claim record but the Approved Amount field is blank, even though it has a value.

**Answer.** Field-level security. The field is not visible to their profile or permission sets.

Distinguish this from the field being removed from the page layout: layout removal hides it from that layout only, and the field remains readable through reports, list views, the API, and Apex. FLS hides it everywhere.

The diagnostic query:

```sql
SELECT Parent.Label, Parent.Profile.Name, PermissionsRead, PermissionsEdit
FROM FieldPermissions
WHERE Field = 'Warranty_Claim__c.Approved_Amount__c'
```

---

## Scenario 6

> Approved Amount is hidden from service coordinators by FLS. A coordinator reports they can see the value anyway, in a field called Claim Summary.

**Answer.** Claim Summary is a **formula field** that references Approved Amount.

Formula fields are not subject to the field-level security of the fields they reference. This is documented behaviour, not a bug, and it is the most common way FLS is defeated accidentally.

The same applies to roll-up summaries: a sum of hidden child values is visible to anyone who can see the roll-up.

The fix is to restrict the formula field as well, or to remove the reference. The lesson is to check, whenever restricting a field, what else exposes it.

## Scenario 7

> Account OWD is Private. A user with no sharing rules, no role above the owner, and no team membership can still read an Account. How?

**Answer.** **Implicit sharing.** They have access to a child record — an Opportunity or a Case on that Account — and access to a child grants Read on the parent Account automatically.

Without this the standard UI could not function; an opportunity page cannot render without its account.

Confirm it in the share table:

```sql
SELECT AccountId, UserOrGroupId, AccountAccessLevel, RowCause
FROM AccountShare
WHERE AccountId = :accountId
```

`RowCause = 'ImplicitChild'` is the answer.

The design lesson: an Account cannot be hidden from someone who can see its opportunities or cases. Any design that assumes otherwise is wrong.

## Scenario 8

> A Lightning component shows three fields. A user discovers they can update any field on the object through that component. How?

**Answer.** The `@AuraEnabled` method accepts a whole sObject and writes it without sanitizing.

```java
// Vulnerable
@AuraEnabled
public static void save(Warranty_Claim__c claim) {
    update claim;
}
```

The component renders three fields, but the method is a callable endpoint. Anyone can invoke it with a fully populated sObject.

The fix is `stripInaccessible` on the way in, plus user-mode DML:

```java
@AuraEnabled
public static void save(Warranty_Claim__c claim) {
    SObjectAccessDecision decision = Security.stripInaccessible(
        AccessType.UPDATABLE, new List<Warranty_Claim__c>{ claim }
    );
    update as user decision.getRecords();
}
```

The general principle: **every `@AuraEnabled` method is a public endpoint**, regardless of what the component displays. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Scenario 9

> Explain the difference between the role hierarchy and the User Manager field.

**Answer.** They are unrelated fields serving unrelated purposes.

The **role hierarchy** (`UserRoleId` and `UserRole.ParentRoleId`) controls record visibility. Users above a record owner in the hierarchy can see and edit that record.

The **Manager field** (`User.ManagerId`) drives approval routing and hierarchical custom settings. It grants no record access at all.

They are frequently out of sync, and each produces its own confusing symptom: a manager who cannot see their team's records has a role problem; an approval going to the wrong person has a Manager field problem.

## Scenario 10

> Design the sharing model for this org: sales reps own opportunities in their territory; regional directors see their region; the service team sees all accounts but no opportunities; an integration user must update every case nightly; and finance must see closed-won opportunity amounts only.

**Answer.**

**OWD:** Account Public Read Only, Opportunity Private, Case Private.

**Sales reps** own their opportunities. Ownership grants full access.

**Regional directors** sit above reps in the role hierarchy. No sharing rule needed.

**Service team** sees accounts through Public Read Only OWD. They need no Opportunity object permission at all, which is cleaner than granting the object and restricting records — a user with no Read on Opportunity sees nothing regardless of sharing.

**Integration user** gets a dedicated profile or permission set with **View All and Modify All on Case specifically** — not View All Data at org level. Authenticated through the JWT bearer flow, no IP restriction on the profile, with the connected app scoped to what it needs.

**Finance** gets Read on Opportunity plus a criteria-based sharing rule for `StageName = 'Closed Won'` shared with the "Finance" public group at Read Only. Field-level security restricts them to the fields they need. If they must see amounts but not customer detail, FLS handles that — and check that no formula field exposes what FLS hides.

The two things an interviewer is listening for: scoping the integration user to specific objects rather than org-wide, and recognizing that withholding the object permission is simpler than restricting records for the service team.

---

## Section 03 in one paragraph

Access is decided by two independent questions: what kinds of things can this user work with, answered by profiles and permission sets, and which specific records, answered by the sharing model. Object and field permissions combine additively and never subtract, except through permission set group muting. Record access starts at the organization-wide default and is only ever opened upward — by the role hierarchy, sharing rules, teams, manual shares, implicit sharing, and Apex. View All and Modify All bypass the record model entirely and should be scoped per object. Apex enforces none of this by default, so `USER_MODE`, sharing keywords, and `stripInaccessible` are the developer's responsibility. When something does not behave as expected, ask the platform with `UserRecordAccess` and the share table's `RowCause` rather than reasoning through the layers.
