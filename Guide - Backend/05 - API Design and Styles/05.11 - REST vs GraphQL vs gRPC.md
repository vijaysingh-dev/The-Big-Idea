# REST vs GraphQL vs gRPC

#backend #api-design #architecture

> **In one line:** REST is for the public internet, gRPC is for service-to-service, GraphQL is for clients with diverse data needs — and most real systems use all three, at different layers.

---

## The Idea

These are not competitors. They optimise for different things.

| | REST | GraphQL | gRPC |
|---|---|---|---|
| Contract | OpenAPI (optional) | Schema (mandatory) | Protobuf (mandatory) |
| Transport | HTTP/1.1 or 2 | HTTP POST | HTTP/2 |
| Payload | JSON | JSON | Binary Protobuf |
| **Who decides the response shape** | Server | **Client** | Server |
| **HTTP caching** | **Excellent** | Poor | None |
| Browser support | Native | Native | Needs a proxy |
| Streaming | SSE | Subscriptions | **Native, bidirectional** |
| Code generation | Optional | Good | **Excellent** |
| Payload size | Baseline | Baseline | **30–60% smaller** |

💡 **The sentence that captures it: REST optimises for the network's caching infrastructure, GraphQL for client flexibility, gRPC for machine-to-machine efficiency.** Each sacrifices what the others prioritise.

---

## What Each Is Genuinely Good At

### REST

**Its superpower is that the entire internet already understands it.** A CDN caches it, a browser caches it, a proxy caches it — nothing had to be taught anything ([[03.5 - HTTP Caching]]).

| Strong when | |
|---|---|
| Public API for third parties | Every language has an HTTP client |
| Read-heavy, cacheable data | The caching chain does your scaling |
| Simple CRUD domains | The mapping is natural |
| Debuggability matters | `curl` and devtools just work |

⚠️ Weak when a client needs data from five resources and pays five round trips, or when different clients need different subsets and you end up building `?fields=` — an ad-hoc query language.

### GraphQL

**Its superpower is client-specified responses.** One round trip, exactly the fields needed, different for every client, without server changes.

| Strong when | |
|---|---|
| Many clients with different needs | The reason it exists |
| Mobile on poor networks | Round trips are expensive |
| Rapid frontend iteration | No backend change for a new field |

⚠️ Weak on caching ([[05.7 - GraphQL Caching]]), on cost control ([[05.8 - GraphQL Security and Limits]]), and on observability — every request is `POST /graphql`.

### gRPC

**Its superpower is that the contract generates the code.** Change the proto, regenerate, and the compiler finds every call site.

| Strong when | |
|---|---|
| Service-to-service | Efficiency and typing matter, browsers do not |
| Polyglot systems | One contract, ten languages |
| High message rates | Binary encoding and HTTP/2 multiplexing |
| Bidirectional streaming | Native, first-class |
| **Deadlines across hops** | **Built into the protocol** ([[03.11 - Timeouts and Deadlines Across Hops]]) |

⚠️ Weak in browsers (needs gRPC-Web plus a proxy), in debuggability (binary on the wire), and with L4 load balancers ([[03.8 - HTTP2]]).

## Payload and Latency, Measured

```
REST JSON, uncompressed        1,240 bytes
REST JSON, gzipped               420 bytes
GraphQL (same fields)          1,180 bytes
gRPC Protobuf                    380 bytes
gRPC Protobuf, gzipped           290 bytes
```

⚠️ **Gzipped JSON is close to raw Protobuf.** The 3× raw difference shrinks considerably once compression is on ([[03.6 - Compression and Streaming Responses]]).

**Where gRPC's real advantage lies is CPU, not size:**

```
Serialise + deserialise, 10,000 objects:
  json (stdlib)      840 ms
  orjson             180 ms
  protobuf            95 ms
```

💡 **For a service handling a few hundred requests per second, none of this matters and you should optimise for developer experience.** At tens of thousands, serialisation CPU becomes a real line item. **Measure before choosing on performance grounds.**

## The Layered Architecture

```
Browser / mobile
    │  GraphQL (client-shaped) or REST (cacheable resources)
    ▼
BFF / API gateway
    │  gRPC (typed, fast, streaming)
    ▼
Internal services
    │  gRPC / events
    ▼
Data stores
```

💡 **The boundary rule: the protocol changes where the trust and capability boundary changes.** External clients get HTTP-based protocols because that is what browsers and third parties can use; internal services get gRPC because you control both ends.

### Conduit's shape

| Boundary | Protocol | Why |
|---|---|---|
| Browser → gateway | GraphQL | Three clients wanting different document fields |
| Public integrations | REST | Third parties, cacheable, `curl`-able |
| Gateway → ingestion | gRPC | Internal, typed, streaming progress |
| Gateway → search | gRPC | High message rate |
| Ingestion progress → browser | SSE | One-way push ([[04.2 - Server Sent Events]]) |
| Services → services (async) | Kafka | Decoupled, replayable ([[09.1 - Queue vs Log]]) |

⚠️ **Five protocols sounds like over-engineering and it is not, because each boundary has genuinely different requirements.** What *would* be over-engineering is using all five where one boundary exists.

## Choosing

```
Is this between your own services, inside your network?
├── YES → gRPC
│         (unless you need HTTP caching, or a team cannot adopt codegen)
│
└── NO → Is the consumer a browser or mobile app you control?
    ├── YES → Do multiple clients need different subsets of the same data?
    │         ├── YES → GraphQL
    │         └── NO  → REST
    └── NO (third party) → REST
```

### The questions that actually decide it

1. **How many client types, and how different are their needs?** One → REST. Five divergent → GraphQL.
2. **Is the data cacheable and read-heavy?** Strongly favours REST.
3. **Do you control both ends?** If yes, gRPC becomes viable.
4. **What is the message rate?** Below ~1,000/s, choose on developer experience.
5. **Who is integrating?** Third parties always find REST easiest.
6. **Do you need bidirectional streaming?** gRPC, or WebSocket.

💡 **Question 1 is decisive for GraphQL.** If the answer is "one web app", you are paying real costs — caching, cost limits, observability complexity — for a benefit you are not receiving.

## The Arguments to Be Sceptical Of

| Claim | Reality |
|---|---|
| "GraphQL eliminates over-fetching" | True, and it introduces unbounded query cost |
| "gRPC is faster" | For serialisation CPU, yes. For a request waiting 40ms on a database, irrelevant |
| "REST is outdated" | It is the only one the whole internet can consume without help |
| "GraphQL replaces REST" | It replaces the read layer. Uploads, webhooks and cacheable public data stay REST |
| "One protocol everywhere is simpler" | Simpler to describe, worse at every boundary |

⚠️ **The most expensive mistake here is adopting GraphQL for a single-client application** because it is modern. You inherit N+1, cost limiting, caching loss and observability complexity, and the flexibility goes unused.

## Migration Realities

### REST → GraphQL

The usual path is GraphQL as a layer *over* existing REST services.

⚠️ **This is where federated N+1 appears in disguise** — every GraphQL field becomes an HTTP call to your own REST API. DataLoader over REST works ([[05.6 - The N+1 Problem and DataLoader]]), **but only if the REST API has batch endpoints.** If it does not, you have built a slower API with more moving parts.

**Add `GET /documents?ids=1,2,3` before you add GraphQL.**

### The honest cost of adding a protocol

| New protocol | You now also need |
|---|---|
| GraphQL | Cost limits, DataLoader, a caching strategy, per-query observability |
| gRPC | L7 load balancing, proto build pipeline, gRPC-Web if browsers |
| Both | Two sets of auth middleware, two error models, two observability integrations |

💡 **Every protocol you add is a permanent tax on every cross-cutting concern.** Auth, tracing, rate limiting, error handling and metrics must all be implemented again. **That cost is invisible at adoption and obvious two years later.**

## Codebase

**Repo:** `GoogleCloudPlatform/microservices-demo`, `saleor/saleor`, `stripe` (docs)

**Question to answer:** Online Boutique uses gRPC between 11 services and HTTP to the browser. Find the boundary — which service translates, and what does it have to do? Then: Saleor chose GraphQL for a largely CRUD domain. What did it buy, and what did it cost?

**Read, in order:**

1. `microservices-demo/protos/demo.proto` — **the entire system contract in one file.** Read it first; it tells you the architecture faster than any diagram
2. `microservices-demo/src/frontend/handlers.go` — **the boundary.** HTTP in, gRPC out to five services. Note the error translation and deadline handling
3. `microservices-demo/src/checkoutservice/main.go` — a service calling five others with deadlines and partial failure handling
4. `saleor/saleor/graphql/` — a large GraphQL API over a CRUD domain. **Look at the dataloaders and permission code and ask whether REST would have needed any of it**
5. **Stripe API docs** — REST at its best. Note what they optimise for: `curl`-ability, idempotency, versioning, clear errors

💡 The frontend service in Online Boutique is worth studying closely. **It is a BFF, and reading it shows exactly what translating between protocols costs**: error mapping, deadline conversion, type conversion, and partial-failure decisions. **That code is the price of a protocol boundary, made concrete.**

**Size:** 2 sessions.

## Exercise

**Drill 5.11 — One domain, three protocols, real numbers**

```
drills/05-three-protocols/
├── domain/{models.py, repository.py, service.py}     # NO protocol code
├── rest/{app.py, openapi.yaml}
├── graphql/{schema.py, loaders.py}
├── grpc/{conduit.proto, server.py, client.py}
├── bench/{scenarios.py, payload.py, cpu.py, caching.py, RESULTS.md}
├── crosscutting/{auth.py, tracing.py, errors.py, COST.md}
└── decision/ADR.md
```

**Part 1 — One domain, three interfaces.** The Conduit document domain implemented once in `domain/`, exposed three ways.

⚠️ **The rule: no protocol-specific code in `domain/`.** If your business logic imports `strawberry` or `grpc`, you have coupled them — **and this constraint is the most valuable part of the exercise.**

**Part 2 — Five realistic scenarios.** Implement each against all three:

| Scenario | Shape |
|---|---|
| Fetch one document with author and source | Nested read |
| List 50 documents, title only | Wide, shallow |
| List 50 documents with authors | The N+1 shape |
| Create a document | Write |
| Stream ingestion progress | Streaming |

Measure per scenario per protocol: round trips, bytes (compressed and not), server CPU, client CPU, p50 and p99.

**Fifteen cells × six metrics. This table is the deliverable** and it is the thing you will refer back to for years.

**Part 3 — Serialisation cost, isolated.** Benchmark encode+decode of 10,000 objects: `json`, `orjson`, GraphQL response construction, Protobuf.

**Then compute at what request rate serialisation becomes 10% of your CPU budget for each.** That number is when the choice starts mattering on performance grounds.

**Part 4 — Caching, measured.** nginx `proxy_cache` in front of all three, under read-heavy traffic.

REST should cache well. GraphQL should not. gRPC cannot. **Then add persisted queries plus GET to GraphQL and measure again** ([[05.7 - GraphQL Caching]]).

**Part 5 — The cross-cutting tax.** Implement authentication, request-ID propagation, distributed tracing and structured errors for each protocol. **Twelve implementations of four concerns.**

Count lines and note conceptual differences. Then add a fifth concern — per-organisation rate limiting — and measure how long each took.

**Write `COST.md` honestly.** This is the number that never appears in protocol comparisons and it is often the deciding one.

**Part 6 — The GraphQL-over-REST trap.** Resolvers calling your own REST API rather than the domain layer.

Run scenario 3 and count HTTP calls. **It should be 51.**

Then add a batch endpoint and a DataLoader over it. Count again. **Seeing the intermediate state is what stops you shipping it.**

**Part 7 — The ADR.** Choose a protocol for each of the six boundaries. **Each choice must cite a number from your own results**, and include one boundary where you chose the less fashionable option and explain why.

**Done when:**
- `domain/` has zero protocol imports and all three interfaces use it
- Your 15×6 results table is complete
- You know the request rate at which serialisation cost matters for each
- Your caching comparison includes GraphQL with and without persisted queries
- `COST.md` quantifies the cross-cutting tax per protocol
- The GraphQL-over-REST trap is reproduced at 51 calls and fixed
- The ADR cites your own numbers for all six boundaries
