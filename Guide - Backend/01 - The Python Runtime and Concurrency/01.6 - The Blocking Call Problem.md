# The Blocking Call Problem

#backend #python #asyncio #production

> **In one line:** One synchronous call inside a coroutine freezes every request the process is serving, and it will not show up as an error — only as latency you cannot explain.

---

## The Idea

An event loop runs one thing at a time and switches only at `await` ([[01.4 - Building an Event Loop From Scratch]]). So a coroutine that does not yield holds the loop for as long as it runs.

```python
@app.get("/user/{id}")
async def get_user(id: int):
    return requests.get(f"http://users/{id}").json()   # blocks the whole loop
```

If that call takes 200ms, then for 200ms:

- No other request is processed
- No response is written
- No new connection is accepted
- Health checks do not get answered
- Every WebSocket and SSE stream in the process is frozen

One user's slow request became everyone's slow request.

⚠️ **There is no error.** No exception, no warning, no log line. Your dashboards show low CPU, a healthy database and rising p99. This is why it is the most expensive async bug in practice — not because it is hard to fix, but because it is hard to *find*.

---

## What Counts as Blocking

Anything that takes real time without an `await`.

### Network I/O with a sync library

```python
requests.get(...)              # blocking. Use httpx.AsyncClient
psycopg2 / pymysql             # blocking. Use asyncpg / psycopg 3 async
redis.Redis()                  # blocking. Use redis.asyncio
boto3                          # blocking. Use aioboto3, or a thread
any vendor SDK                 # assume blocking until proven otherwise
```

💡 **The tell:** if you did not write `await` in front of it, it did not yield. That is the entire test, and it catches almost everything.

### File I/O

```python
open("f").read()               # blocking
Path("f").write_text(x)        # blocking
os.listdir("/big/dir")         # blocking
```

Local file reads are usually microseconds and fine in practice. Network filesystems, large files and container-mounted volumes are not. Use `aiofiles` or a thread for anything above a few hundred KB.

### CPU work

```python
json.loads(huge_payload)       # blocking, and holds the GIL
bcrypt.hashpw(pw, salt)        # deliberately ~100ms
re.match(pattern, big_string)  # can be unbounded with a bad pattern
sorted(million_items)
pandas / numpy on big data
image.resize(...)
```

⚠️ **`json.loads` on a large body is the one people never suspect.** A 50MB JSON payload can take a full second of pure CPU. Use `orjson` (2–5x faster), limit request body size, and reject oversized payloads at the proxy.

### Sneaky ones

```python
time.sleep(1)                  # asyncio.sleep, always
subprocess.run(...)            # asyncio.create_subprocess_exec
socket.gethostbyname(host)     # DNS is blocking — a slow resolver stalls the loop
logging to a slow handler      # a network log handler blocks. Use a queue handler
import heavy_module            # inside a request handler — first import is slow
```

DNS deserves a mention. `socket.getaddrinfo` is synchronous, and asyncio runs it in a thread pool by default. If your resolver is slow or the thread pool is full, connection setup blocks. Symptom: connections that intermittently take 5 seconds to establish for no visible reason.

## Detecting It

Four methods, in order of when you would use them.

### 1. Loop lag monitor — leave this running always

```python
import asyncio, time, logging

log = logging.getLogger(__name__)

async def loop_lag_monitor(interval: float = 0.1, threshold: float = 0.05):
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        lag = time.perf_counter() - start - interval
        loop_lag_seconds.observe(lag)
        if lag > threshold:
            log.warning("event loop blocked", extra={"lag_ms": round(lag * 1000)})
```

You asked to be woken in 100ms. You were woken in 340ms. The extra 240ms is time the loop was busy with something that did not yield.

💡 **Export this as a metric in every async service you run.** Loop lag correlates with user-visible p99 far better than CPU utilisation does, and it points directly at the cause rather than at a symptom.

### 2. asyncio debug mode — use in development

```bash
PYTHONASYNCIODEBUG=1 python app.py
```

```python
asyncio.run(main(), debug=True)
```

It logs any callback taking longer than 100ms, with the source location:

```
WARNING: Executing <Task get_user ... at app.py:42> took 0.312 seconds
```

That log line names the file and line. It finds most blocking calls in minutes.

```python
loop.slow_callback_duration = 0.05     # tighten it to find smaller offenders
```

⚠️ Debug mode adds real overhead. Development and staging only.

### 3. py-spy — use in production, during an incident

```bash
# What is the process doing right now?
py-spy dump --pid 1234

# Live view, sampled
py-spy top --pid 1234

# Record 30 seconds into a flamegraph
py-spy record --pid 1234 --duration 30 --output profile.svg
```

`py-spy dump` on a stuck process shows you the exact stack that is blocking. No code change, no restart, works on a running production container.

Look for a thread whose top frame is in `requests`, `ssl`, `json`, or your own CPU-heavy function — rather than in `epoll_wait`, which is the healthy state.

### 4. BlockBuster — use in tests

```bash
pip install blockbuster
```

```python
from blockbuster import BlockBuster

@pytest.fixture(autouse=True)
def no_blocking():
    with BlockBuster():
        yield
```

It patches known blocking functions to raise when called from the event loop. Your test suite now fails on blocking calls instead of shipping them.

💡 **This is the highest-leverage item in this note.** Detection at runtime is good; prevention at CI time is better. Adding this fixture to Conduit in phase 1 will save you real hours later.

## Fixing It

### Fix 1 — Use the async library (best)

| Blocking | Async |
|---|---|
| `requests` | `httpx.AsyncClient`, `aiohttp` |
| `psycopg2` | `asyncpg`, `psycopg` 3 async |
| `redis` | `redis.asyncio` |
| `pymongo` | `motor`, or PyMongo's async API |
| `boto3` | `aioboto3` |
| `elasticsearch` | `AsyncElasticsearch` |
| `open()` | `aiofiles` |
| `subprocess` | `asyncio.create_subprocess_exec` |
| `time.sleep` | `asyncio.sleep` |
| `smtplib` | `aiosmtplib` |
| `paramiko` | `asyncssh` |

### Fix 2 — Push it to a thread

When no async version exists, or the work is C code that releases the GIL.

```python
import asyncio

result = await asyncio.to_thread(legacy_sdk.fetch, arg)
```

```python
# For CPU work that holds the GIL, use a process instead
loop = asyncio.get_running_loop()
result = await loop.run_in_executor(process_pool, cpu_heavy, data)
```

⚠️ **This trades one bottleneck for another.** The default thread pool in a FastAPI app is 40 wide (anyio's limiter). Forty concurrent slow calls exhaust it, and then every other threaded call in the process queues behind them — including `def` endpoints that have nothing to do with the slow one. See the incident in [[01.3 - Threads Processes and Coroutines]].

Bound each dependency separately so one cannot starve the others:

```python
sdk_limiter = anyio.CapacityLimiter(10)

async def call_sdk(arg):
    return await anyio.to_thread.run_sync(legacy_sdk.fetch, arg,
                                          limiter=sdk_limiter)
```

This is the bulkhead pattern applied inside one process — [[11.3 - Circuit Breakers and Bulkheads]].

### Fix 3 — Get it out of the request path

If the work is genuinely heavy — image processing, document parsing, report generation — it does not belong in a request at all, blocking or not. Queue it.

```python
@app.post("/documents")
async def upload(file: UploadFile):
    doc_id = await store_raw(file)
    await enqueue(process_document, doc_id)
    return {"id": doc_id, "status": "processing"}
```

Section 08 is about this.

### Fix 4 — Yield inside a long loop

For pure-Python work you cannot move, at least be polite:

```python
async def process_many(items):
    for i, item in enumerate(items):
        transform(item)
        if i % 100 == 0:
            await asyncio.sleep(0)     # let other tasks run
```

⚠️ This is a mitigation, not a fix. Total time is unchanged and you have added switching overhead. Use it when you must keep the work in-process, not as a first choice.

### Fix 5 — Use `def`, deliberately

FastAPI runs `def` endpoints in the thread pool automatically.

```python
@app.get("/report")
def generate_report():          # not async — runs in a thread
    return heavy_sync_work()
```

This is a legitimate choice for an endpoint that is entirely synchronous. The danger is *mixing*: an `async def` endpoint that calls one blocking function is the bad case, because it gets no thread and blocks the loop.

💡 **The rule: all-async or all-sync per endpoint. Never half.**

## In Production

### The incident shape

You will see this exact pattern, probably more than once:

```
14:02  p99 latency starts climbing on ALL endpoints
14:05  CPU is at 30%. Database is idle. Nothing looks wrong
14:08  Health checks start timing out
14:09  Kubernetes restarts the pod
14:10  Recovers, then repeats 20 minutes later
```

Cause: one endpoint calls a third-party API with `requests`. That API got slow. Every request in the process now waits behind it.

The tell that distinguishes this from a genuine capacity problem: **all endpoints degrade together, including ones that share no dependency**, while CPU stays low. A capacity problem degrades under CPU pressure. A blocked loop degrades with the CPU idle.

### Pre-production checklist

| Check | How |
|---|---|
| No blocking calls in async code | BlockBuster in the test suite |
| Loop lag is monitored | Metric + alert at 50ms |
| py-spy available in the image | `pip install py-spy`, and the container allows `ptrace` |
| Thread pool bounded per dependency | Separate `CapacityLimiter` for each blocking integration |
| Exception handler set | `loop.set_exception_handler` |
| Debug mode in staging | `PYTHONASYNCIODEBUG=1` |
| Body size limited | At the proxy, before JSON parsing happens |

⚠️ **The py-spy one is easy to miss.** In Kubernetes, attaching to a process needs `SYS_PTRACE` capability or a shared process namespace. Sort this out before an incident, not during one. A tool you cannot run when you need it is not a tool.

### Numbers to hold

| Blocking duration | Effect at 100 req/s |
|---|---|
| 1ms | Negligible |
| 10ms | p99 rises noticeably |
| 100ms | Roughly 10 requests queued behind each one. Serious |
| 1s | About 100 requests queued. Health checks fail. Pod restarts |
| 10s | Total outage of that process |

The relationship is not linear. A queue that receives work faster than it drains grows without limit — this is queueing theory, and the practical version is in [[11.8 - Capacity Planning and Load Testing]].
