# Subscriptions

#backend #api-design #graphql #realtime

> **In one line:** Subscriptions are GraphQL's realtime story, they need every piece of machinery from section 04, and for most systems a plain SSE endpoint would have been simpler.

---

## The Idea

```graphql
subscription DocumentIndexed($sourceId: ID!) {
  documentIndexed(sourceId: $sourceId) {
    id
    title
    source { name }
  }
}
```

The client subscribes once; the server pushes a result every time a matching event occurs, shaped exactly like a query result.

💡 **The genuine advantage over raw SSE is that the payload is typed and field-selected.** The client asks for the fields it wants, gets schema validation, and reuses its normalised cache ([[05.7 - GraphQL Caching]]) — events update the same cached entities as query results, so every view refreshes automatically.

**That is a real benefit, and it is the only one.** Everything else about subscriptions is harder than the alternatives.

---

## The Transport

GraphQL does not specify a transport. In practice there are two protocols.

### graphql-ws

```
Client → WebSocket connect, subprotocol "graphql-transport-ws"
Client → {"type": "connection_init", "payload": {"token": "..."}}
Server → {"type": "connection_ack"}
Client → {"type": "subscribe", "id": "1", "payload": {"query": "subscription {...}"}}
Server → {"type": "next", "id": "1", "payload": {"data": {...}}}
Client → {"type": "complete", "id": "1"}
```

Multiple subscriptions multiplex over one WebSocket, each with an `id`. **Auth happens in `connection_init`**, which neatly solves the header problem from [[04.8 - WebSocket and WebRTC Recap]].

⚠️ The older `subscriptions-transport-ws` protocol is unmaintained, still widely deployed, and not compatible.

### SSE transport

```
POST /graphql/stream
Accept: text/event-stream
```

The `graphql-sse` protocol runs subscriptions over Server-Sent Events — simpler, and it inherits automatic reconnection, no upgrade handshake, and easy proxying ([[04.2 - Server Sent Events]]).

💡 **If your subscriptions are server-push only — which they are, by definition — the SSE transport is the better choice and it is under-used.** WebSocket's full duplex buys nothing here, because a subscription never sends client→server data after the initial request.

**WebSocket dominates because Apollo Client defaulted to it, not because it is better suited.**

## Implementation

```python
@strawberry.subscription
async def document_indexed(self, info: Info, source_id: strawberry.ID
                           ) -> AsyncGenerator[Document, None]:
    if not await can_read_source(info.context.user, source_id):
        raise PermissionError("not authorised")

    queue = await info.context.broker.subscribe(f"source:{source_id}")
    try:
        async for event in queue:
            if event.type != "document_indexed":
                continue
            doc = await info.context.loaders.document.load(event.document_id)
            if doc is not None:
                yield doc
    finally:
        await info.context.broker.unsubscribe(queue)
```

**Authorisation happens once, at subscribe time.** ⚠️ **That is a problem** — a subscription can live for hours and permission can be revoked in that time.

**The `finally` block is mandatory** — the same leak as SSE ([[04.3 - SSE in Production]]).

**The resolver yields a domain object**, and GraphQL then executes the client's selection set against it — which means nested resolvers run **per event**.

### The per-event execution cost

```graphql
subscription {
  documentIndexed {
    title
    source { name }          # a resolver call, per event
    annotations(first: 5) { author { name } }   # more, per event
  }
}
```

⚠️ **Every event runs the full selection set.** At 100 events/second with a nested selection, that is hundreds of resolver invocations per second per subscriber.

💡 **DataLoader does not help across events**, because loaders are per-request and each event is effectively its own execution.

**The practical guidance: keep subscription selection sets shallow.** Push an ID and a few scalars, and let the client fetch details via a normal query — its normalised cache will often already have them.

## Filtering: Where?

| Location | Cost |
|---|---|
| **At the publisher** | Most efficient, but the publisher must know subscriber criteria |
| **At the backplane topic** | Topic per source. Good if cardinality is bounded |
| **In the resolver** | Simple, but every pod receives every event |
| **At the client** | ⚠️ **Never** — the data has already left the server |

⚠️ **Filtering at the client is an authorisation failure**, not merely inefficiency. If a user should not see an event, it must not be sent ([[04.6 - Scaling Long Lived Connections]]).

**Topic-per-entity is usually right**, but watch cardinality — topic-per-document with a million documents means a million potential topics; topic-per-organisation with local filtering is often the better trade.

## Everything From Section 04 Applies

| Requirement | Note |
|---|---|
| Heartbeats | graphql-ws has `ping`/`pong`. Configure them |
| Backplane for multi-pod | [[04.6 - Scaling Long Lived Connections]] |
| Per-client bounded queues | [[04.7 - Presence Fanout and Backpressure]] |
| **Replay after disconnect** | **Not in the protocol. You build it** |
| Subscription cleanup | `finally`, always |
| Deploy reconnect storms | Jitter, staggered shutdown |

⚠️ **The replay gap is the significant one.** SSE gives you `Last-Event-ID` for free; graphql-ws has no equivalent — a client that reconnects starts from the current moment and **silently misses everything in between.**

```graphql
subscription DocumentIndexed($sourceId: ID!, $since: String) { ... }
```

```python
if since:
    missed = await log.since(since)
    if missed is None:
        yield ResyncRequired()
    else:
        for event in missed:
            yield await hydrate(event)
# then go live
```

💡 **Most GraphQL subscription implementations in the wild do not do this**, which means they silently lose events on every reconnect — including on every deploy. **If correctness matters, this is not optional.**

## In Production

### Subscriptions versus a query plus SSE

| | GraphQL subscription | SSE + normal queries |
|---|---|---|
| Typed payload | Yes | You define it |
| Field selection | Yes | Fixed |
| Client cache integration | Automatic | Manual |
| **Replay on reconnect** | **Build it** | **Built in** |
| Transport complexity | WebSocket + protocol | Plain HTTP |
| Observability | One `/graphql` endpoint | Per-endpoint |
| Per-event execution cost | Full selection set | Whatever you serialise |

💡 **A common and defensible architecture: SSE pushes a lightweight notification, the client then runs a normal GraphQL query.**

```
SSE:    {"type": "document_indexed", "id": "doc_42"}
Client: query { document(id: "doc_42") { ...whatever it needs } }
```

**You get replay for free, the payload is tiny, and the client fetches exactly what it wants — often nothing, because the cache already has it.** The cost is one extra round trip per event, usually irrelevant for a notification.

**Recommend this shape unless the client genuinely needs field-selected push payloads at high frequency.**

### Scaling numbers

⚠️ **Budget for execution cost, not just connection count.** A subscription with a five-field selection at 10 events/second costs roughly 50 resolver invocations per second, per subscriber. **10,000 subscribers is a genuinely large amount of work you would not be doing with a plain push payload.**

### Observability

```python
subscription_active.labels(field=...).set(count)
subscription_events_sent.labels(field=...).inc()
subscription_execution_duration.observe(elapsed)
subscription_dropped_events.labels(reason=...).inc()
```

**Label by subscription field**, because one expensive subscription type will dominate your cost.

### Authorisation over time

```python
async for event in queue:
    if time.monotonic() - last_check > 60:
        if not await can_read_source(info.context.user, source_id):
            raise PermissionError("access revoked")
        last_check = time.monotonic()
    yield ...
```

⚠️ **Without this, a user removed from an organisation keeps receiving its data until they disconnect** — which could be days. Same problem and same discipline as long-lived WebSocket auth ([[04.8 - WebSocket and WebRTC Recap]]).

### Federation makes it harder

In a federated graph the gateway must hold a connection to whichever subgraph owns the subscription, and entity resolution per event is expensive. **Most federated deployments keep subscriptions in one subgraph or avoid them entirely** ([[05.10 - Federation and Schema Composition]]).

## Codebase

**Repo:** `enisdenjo/graphql-ws`, `strawberry-graphql/strawberry`, `hasura/graphql-engine`

**Question to answer:** In the graphql-ws protocol, how are multiple subscriptions multiplexed over one connection, and what happens to in-flight subscriptions when the connection drops? Then: how does Hasura handle 10,000 subscribers without running 10,000 database queries per event?

**Read, in order:**

1. **graphql-ws protocol specification** (`PROTOCOL.md`) — **short and complete.** Every message type, the connection lifecycle, and the error cases. Read before any code
2. `graphql-ws/src/server.ts` — subscription registry, `id` multiplexing, cleanup on disconnect
3. `strawberry/subscriptions/protocols/graphql_transport_ws/handlers.py` — the Python server side. **Note the cleanup path and ping/pong handling**
4. `strawberry/schema/execute.py` — `subscribe`, and how each yielded value is executed against the selection set. **This is where the per-event cost lives**
5. **Hasura's multiplexing blog post** — the answer to the second question, and it is genuinely clever

💡 Hasura's approach is worth understanding even though you will not implement it: **they group subscribers with identical query shapes and different variables into one poller**, execute a single query returning results for all of them, and fan out. **That turns 10,000 subscribers into one database query per interval** — a fundamentally different scaling model.

**Size:** 1–2 sessions.

**Part 1 — Build subscriptions properly.** `documentIndexed`, `annotationCreated`, `ingestionProgress` over graphql-ws, using the backplane from drill 4.5. Authorisation at subscribe time, `finally` cleanup, heartbeats, per-connection limits.

**The leak test:** open 500 subscriptions, kill the clients abruptly, assert broker subscriptions return to zero.

**Part 2 — Measure per-event cost.** The same subscription with selection sets of increasing depth: one scalar; plus a nested object; plus a nested list; plus a nested list with its own nested object.

At 100 events/second, measure CPU and resolver invocations for each.

**Chart cost against selection depth.** That chart is the argument for shallow payloads, and it is a number most people have never measured.

**Part 3 — The reconnect gap.** Client subscribed and receiving. Kill the connection. Generate 50 events. Reconnect.

**Confirm all 50 are lost silently.**

Then implement replay with a `since` argument and an event log. Confirm zero loss. Then overflow the log and confirm an explicit resync signal rather than a silent gap.

**Part 4 — Revoked access.** Subscribe with permission, remove it in the database, confirm events keep arriving. **Measure how long.**

Then implement periodic re-authorisation and a maximum subscription lifetime, and measure again. **Write down the exposure window for each configuration** — a security review will ask for it.

**Part 5 — Two transports.** The same subscriptions over graphql-ws and graphql-sse.

At 500 subscribers compare: server memory, CPU, reconnect behaviour after a proxy timeout, deploy storm shape, and proxy configuration required. **Write your recommendation with the numbers.**

**Part 6 — The alternative architecture.** SSE pushing `{"type": "document_indexed", "id": "doc_42"}`, with the client running a normal GraphQL query in response.

Compare against subscriptions at 500 clients and 50 events/second on: server CPU, bytes on the wire, end-to-end latency, requests per second, **client cache hit rate on the follow-up query**, and implementation complexity.

**The cache hit rate is the interesting column** — many follow-up queries will be served entirely from the client's normalised cache, costing nothing.

Then state which you would choose for each of Conduit's three realtime features.

**Part 7 — Multiplexing.** 1,000 subscribers to `ingestionProgress` with different `runId` values.

Naive: measure database queries per event batch. Then group by query shape, execute one query for all run IDs, fan out locally. **Report the ratio.**

**Done when:**
- 500 abrupt disconnects leave zero leaked broker subscriptions
- Your cost-versus-depth chart quantifies the per-event penalty
- Replay eliminates the reconnect gap, with explicit resync on overflow
- You know the access-revocation exposure window for each configuration
- Your transport comparison has real numbers and a stated recommendation
- The SSE-notify alternative is measured on six metrics
- Multiplexing reduces database queries by a measured ratio
