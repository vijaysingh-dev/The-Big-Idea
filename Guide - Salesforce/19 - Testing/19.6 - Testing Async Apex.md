# Testing Async Apex

## The constraints, up front

Each async mechanism behaves differently in a test, and knowing the constraint before writing the test saves an hour.

```
Queueable       runs at Test.stopTest(); only ONE chain level executes
@future         runs at Test.stopTest()
Batch           runs at Test.stopTest(); exactly ONE execute() chunk runs
Scheduled       runs at Test.stopTest() if scheduled during the test
Platform events do NOT flush automatically — Test.getEventBus().deliver() required
CDC             also requires Test.enableChangeDataCapture()
Finalizers      run, but only one retry level
```

## Queueable

```java
@IsTest
static void theSyncJobUpdatesTheClaimStatus() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock(200, '{"confirmationNumber":"ERP-1"}'));
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    System.enqueueJob(new ErpSyncQueueable(new Set<Id>{ claim.Id }));
    Test.stopTest();   // the job runs here

    Warranty_Claim__c refreshed = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c);
}
```

**Assertions after `stopTest`.** Before it, the job has not run.

**Enqueued from a trigger** works the same way — perform the DML inside the block and assert afterwards:

```java
Test.startTest();
claim.Status__c = 'Approved';
update claim;          // the trigger enqueues
Test.stopTest();       // the job runs

Assert.areEqual('Synced', refresh(claim).ERP_Sync_Status__c);
```

## The chaining limit

**Only one chained level executes**, and attempting a second throws.

```java
public void execute(QueueableContext context) {
    processChunk();

    // without this guard, the test fails on the second enqueue
    if (!remaining.isEmpty() && !Test.isRunningTest()) {
        System.enqueueJob(new ClaimSyncQueueable(remaining));
    }
}
```

That guard means the chaining logic is untested by the integration test. Test the **decision** separately:

```java
@IsTest
static void chunkingCarriesTheRemainderForward() {
    List<Id> ids = TestIdFactory.generateMany(Warranty_Claim__c.SObjectType, 350);
    ClaimSyncQueueable job = new ClaimSyncQueueable(ids);

    Assert.areEqual(150, job.currentChunk().size(), 'The first chunk takes 150');
    Assert.areEqual(200, job.remainder().size(), 'The rest is carried forward');
}
```

Exposing `currentChunk()` and `remainder()` as `@TestVisible` is what makes this possible, and it is worth the small widening.

## Batch: one chunk

```java
@IsTest
static void archiveBatchProcessesClosedClaims() {
    TestDataFactory.createClosedClaims(250);

    Test.startTest();
    Database.executeBatch(new ClaimArchiveBatch(), 200);
    Test.stopTest();

    // 200 processed, 50 left — one chunk only, regardless of record count
    Assert.areEqual(50, [SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Closed']);
}
```

**Multi-chunk behaviour is invisible through `executeBatch`.** `Database.Stateful` accumulation in particular cannot be verified this way.

Call `execute` directly for cross-chunk logic:

```java
@IsTest
static void statefulCountersAccumulateAcrossChunks() {
    ClaimReconciliationBatch batch = new ClaimReconciliationBatch();
    List<Warranty_Claim__c> chunkOne = TestDataFactory.createClaims(5);
    List<Warranty_Claim__c> chunkTwo = TestDataFactory.createClaims(5);

    Test.startTest();
    batch.execute(null, chunkOne);
    batch.execute(null, chunkTwo);
    batch.finish(null);
    Test.stopTest();

    Batch_Run_Log__c log = [SELECT Records_Processed__c FROM Batch_Run_Log__c LIMIT 1];
    Assert.areEqual(10, log.Records_Processed__c, 'The counter accumulates across chunks');
}
```

**Passing `null` for the `BatchableContext`** works when the method does not use it. Where `finish` reads `ctx.getJobId()`, it needs a null guard:

```java
public void finish(Database.BatchableContext ctx) {
    AsyncApexJob job = ctx == null ? null : [
        SELECT Status, NumberOfErrors FROM AsyncApexJob WHERE Id = :ctx.getJobId()
    ];
    logRun(job);
}
```

That guard exists purely for testability, which is a reasonable trade.

**Testing `start` separately** verifies the query without running the whole job:

```java
@IsTest
static void theQueryLocatorSelectsOnlyOldClosedClaims() {
    TestDataFactory.createClosedClaim(Date.today().addYears(-5));
    TestDataFactory.createClosedClaim(Date.today().addMonths(-2));
    TestDataFactory.createOpenClaim(Date.today().addYears(-5));

    Test.startTest();
    Database.QueryLocator locator = new ClaimArchiveBatch().start(null);
    Database.QueryLocatorIterator iterator = locator.iterator();
    Test.stopTest();

    Integer count = 0;
    while (iterator.hasNext()) {
        iterator.next();
        count++;
    }
    Assert.areEqual(1, count, 'Only the old closed claim should be selected');
}
```

## Scheduled Apex

```java
@IsTest
static void theSchedulerStartsTheReconciliationBatch() {
    Test.startTest();
    String cron = '0 0 2 * * ?';
    Id jobId = System.schedule('Test Reconciliation', cron, new ClaimReconciliationBatch());
    Test.stopTest();   // the scheduled job runs here

    CronTrigger trigger = [
        SELECT CronExpression, TimesTriggered FROM CronTrigger WHERE Id = :jobId
    ];
    Assert.areEqual(cron, trigger.CronExpression);
    Assert.areEqual(0, trigger.TimesTriggered, 'It has not fired on its schedule yet');
}
```

**`System.schedule` inside `startTest` causes the job to run at `stopTest`**, regardless of the cron expression — which is how the scheduled work gets tested at all.

`TimesTriggered` is 0 because the scheduled execution has not occurred on its actual schedule; the test-context run is separate.

**A self-rescheduling job** needs the same `Test.isRunningTest()` guard as a chained Queueable, or the reschedule inside the run causes a failure. See [[12.5 - Scheduled Apex]].

## Platform events

**The one that does not flush automatically.**

```java
@IsTest
static void approvalPublishesAnEventAndTheSubscriberActs() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 120000);

    // without this, the subscriber never runs and the test passes proving nothing
    Test.getEventBus().deliver();
    Test.stopTest();

    Assert.areEqual(1, [SELECT COUNT() FROM Payment_Instruction__c],
        'The subscriber should have created a payment instruction');
}
```

**Omitting `deliver()` is the most consequential mistake here**, because the test passes. Coverage is produced, the publisher is exercised, and the subscriber — which is where the logic lives — never runs.

**Chained events** need `deliver()` called repeatedly:

```java
Test.getEventBus().deliver();   // the first subscriber runs and publishes another event
Test.getEventBus().deliver();   // the second subscriber runs
```

**Test idempotency explicitly**, since at-least-once delivery makes it the property most likely to be wrong:

```java
@IsTest
static void aRedeliveredEventDoesNotDuplicate() {
    Test.startTest();
    EventBus.publish(buildApprovalEvent('a0X123', 120000));
    Test.getEventBus().deliver();

    // the same event again, simulating redelivery
    EventBus.publish(buildApprovalEvent('a0X123', 120000));
    Test.getEventBus().deliver();
    Test.stopTest();

    Assert.areEqual(1, [SELECT COUNT() FROM Payment_Instruction__c],
        'A redelivered event must not create a second instruction');
}
```

See [[12.8 - Platform Events]].

## Change Data Capture

Two required calls rather than one.

```java
@IsTest
static void aClaimUpdatePublishesAChangeEvent() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    Test.enableChangeDataCapture();

    claim.Status__c = 'Approved';
    update claim;

    Test.getEventBus().deliver();
    Test.stopTest();

    List<Claim_Audit__c> audit = [SELECT Change_Type__c, Changed_Fields__c FROM Claim_Audit__c];
    Assert.areEqual(1, audit.size());
    Assert.isTrue(audit[0].Changed_Fields__c.contains('Status__c'));
}
```

**`Test.enableChangeDataCapture()` before the DML**, and `deliver()` after.

**Gap events cannot be simulated**, so the gap-handling branch is untestable and needs code review rather than coverage. See [[12.9 - Change Data Capture]].

## Transaction Finalizers

```java
@IsTest
static void aFailedCalloutIsLoggedByTheFinalizer() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock(503, '{"error":"unavailable"}'));

    Test.startTest();
    System.enqueueJob(new ErpSyncQueueable(claimIds, 1));
    Test.stopTest();   // the job fails and the finalizer runs

    List<Integration_Log__c> logs = [
        SELECT Attempt__c, Severity__c FROM Integration_Log__c WHERE Context__c = 'ErpSync'
    ];
    Assert.areEqual(1, logs.size(), 'The finalizer should have logged the failure');
    Assert.areEqual('Warning', logs[0].Severity__c,
        'A retryable failure below the cap logs as a warning');
}
```

**The finalizer runs**, and the retry it enqueues is subject to the one-level chaining limit — so the attempt-three-gives-up path cannot be reached through the integration test.

Test the decision directly:

```java
@IsTest
static void permanentFailuresAreNotRetried() {
    RetryableFinalizer finalizer =
        new RetryableFinalizer('ErpSync', ErpSyncQueueable.class, claimIds, 1);

    Assert.isFalse(finalizer.isTransientForTest(
        new DmlException('FIELD_CUSTOM_VALIDATION_EXCEPTION')),
        'A validation failure should not be retried');
    Assert.isTrue(finalizer.isTransientForTest(new CalloutException('Read timed out')),
        'A timeout should be retried');
}
```

`@TestVisible` on the private classifier is what makes this possible, and it is the right trade — the classification logic is the part that matters. See [[12.6 - Transaction Finalizers]].

## Verifying the job ran

```java
@IsTest
static void theBatchJobCompletesWithoutErrors() {
    TestDataFactory.createClaims(50);

    Test.startTest();
    Id jobId = Database.executeBatch(new ClaimEnrichmentBatch(), 200);
    Test.stopTest();

    AsyncApexJob job = [
        SELECT Status, NumberOfErrors, JobItemsProcessed, TotalJobItems, ExtendedStatus
        FROM AsyncApexJob WHERE Id = :jobId
    ];

    Assert.areEqual('Completed', job.Status, job.ExtendedStatus);
    Assert.areEqual(0, job.NumberOfErrors, 'No chunk should have failed');
}
```

Querying `AsyncApexJob` after `stopTest` verifies the job's own status rather than only its side effects — useful when a chunk swallows an exception and the data looks fine.

## The async testing checklist

```
[ ] Assertions after Test.stopTest()
[ ] Callout mocks set before Test.startTest()
[ ] Test.getEventBus().deliver() for platform events
[ ] Test.enableChangeDataCapture() before the DML for CDC
[ ] Chained jobs guarded with Test.isRunningTest()
[ ] Cross-chunk batch logic tested by calling execute() directly
[ ] BatchableContext null-guarded where it is used in finish()
[ ] Idempotency tested by delivering the same event twice
[ ] AsyncApexJob status asserted for batch jobs
[ ] Failure paths tested, not just the happy path
```

## What cannot be tested

Worth knowing so time is not spent trying.

**Multi-chunk batch execution** through `executeBatch`.

**More than one chain level**, for Queueables or scheduled jobs.

**Genuine timing and concurrency.** Two async jobs racing cannot be reproduced.

**Gap events** in CDC.

**Real retry exhaustion** across several async transactions.

**Actual scheduled execution** on its cron schedule.

For each of these, the compensation is the same: **extract the decision into a testable method** and test that, then accept that the orchestration around it is verified by review and by monitoring rather than by the suite.

## Practical guidance

**Assertions after `stopTest`.**

**Mocks before `startTest`.**

**`Test.getEventBus().deliver()`** for platform events — omitting it produces a passing test that proves nothing.

**`Test.enableChangeDataCapture()`** before the DML for CDC.

**Guard chained enqueues** with `Test.isRunningTest()`.

**Call `execute` directly** for multi-chunk logic.

**Test idempotency** by delivering the same event twice.

**Extract async decision logic** into methods that can be tested directly.
