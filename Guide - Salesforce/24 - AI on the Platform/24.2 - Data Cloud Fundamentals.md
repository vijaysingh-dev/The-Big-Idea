# Data Cloud Fundamentals

## What problem it solves

A customer exists in six systems, differently.

```
Salesforce CRM      Contact: priya.sharma@northwind-customer.com
ERP                 Customer 4471, P. Sharma
Support portal      user_88213
Marketing platform  psharma@gmail.com
Web analytics       an anonymous visitor ID that later logged in
Service telemetry   machine serial numbers, no person at all
```

**No single system knows they are one person**, and every AI feature, every segmentation, and every "complete view" requires that they do.

**Data Cloud ingests, harmonizes, and resolves identity across systems**, producing a unified profile that other things — including AI — can ground on.

## It is not a CRM object

The distinction that matters most for a developer.

```
Salesforce CRM      transactional, record-level, governed by sharing,
                    limited to storage allocations, queried with SOQL

Data Cloud          analytical, very high volume, its own access model,
                    queried with SQL, stored separately
```

**Data Cloud data is not in your org's objects.** It is a separate store with a separate query language, surfaced back into the org through specific mechanisms.

**Thinking of it as "a very large custom object" leads to wrong designs.** It is closer to a warehouse with identity resolution and real-time activation.

## The data model layers

```
Data Streams        the ingestion — connectors and files
    ↓
Data Lake Objects   raw ingested data, per source, untransformed
    ↓
Data Model Objects  harmonized into a canonical model
    ↓
Unified Profiles    identity-resolved individuals
    ↓
Calculated Insights aggregations computed across the model
    ↓
Segments and Activations  what is done with it
```

**The transformation is the work.** Each source's fields are mapped into the standard data model, which is what makes cross-source queries possible.

## Data streams

```
Salesforce CRM connector      standard and custom objects, near real time
Marketing Cloud
Amazon S3
Google Cloud Storage
Snowflake, Databricks, BigQuery    zero-copy in some configurations
Ingestion API                      streaming or bulk, for anything else
MuleSoft
Web and mobile SDK                 behavioural data
```

**Zero-copy federation** is the significant recent capability — querying data in Snowflake or BigQuery without copying it into Data Cloud. It removes the storage cost and the sync lag, at the cost of query performance depending on the external warehouse.

**Refresh modes:**

```
Full refresh        replaces everything each run
Incremental         only changed records
Streaming           near real time
```

**Incremental requires a reliable change indicator** — a modified timestamp or a change stream. Where the source has none, full refresh is the only option, and at volume that is expensive.

## The canonical data model

Data Cloud ships a standard model, and mapping into it is the harmonization step.

```
Individual              a person
Contact Point Email     an email address belonging to an individual
Contact Point Phone
Party Identification    an external identifier
Account
Case
Sales Order
Product
Engagement              an interaction — email opened, page viewed
```

```
Northwind mapping:

Salesforce Contact        → Individual + Contact Point Email + Contact Point Phone
ERP Customer              → Individual + Party Identification (ERP customer number)
Portal user               → Individual + Party Identification (portal user ID)
Warranty_Claim__c         → a custom Data Model Object
Machine telemetry         → Engagement, or a custom DMO
```

**Custom Data Model Objects** exist for anything the standard model does not cover, and warranty claims are exactly that case.

**Mapping is where the project time goes**, and it is a data modelling exercise rather than a technical one — deciding what "an individual" means when six systems disagree.

## Identity resolution

The core capability, and the part with real subtlety.

```
Ruleset: Northwind Customer Identity

Rule 1 (exact)      Email matches exactly
Rule 2 (exact)      Party Identification matches on ERP customer number
Rule 3 (fuzzy)      Last name exact + normalized email domain + fuzzy first name
Rule 4 (exact)      Phone number, normalized
```

**Rules run in order**, and a match at any rule unifies the records into one profile.

**The tension:**

**Too loose** — two different people are merged. A shared family email address unifies a parent and child; a generic `info@company.com` unifies an entire company's contacts into one person.

**Too tight** — one person appears as four profiles, and the unified view is not unified.

**Fuzzy matching on name alone is nearly always too loose.** Two people named Priya Sharma in an Indian customer base is not unusual, and merging them is worse than leaving them separate.

**The practical approach:** start tight with exact matches on strong identifiers, examine the results, and loosen deliberately with evidence.

```sql
-- Profiles with an implausible number of source records, which suggests over-merging
SELECT UnifiedIndividualId, COUNT(*) FROM IndividualIdentityLink
GROUP BY UnifiedIndividualId ORDER BY COUNT(*) DESC LIMIT 20
```

**Reviewing the top of that list** is how over-merging is caught, and it should be done before anything depends on the profiles.

## Calculated Insights

Aggregations computed across the model, available for segmentation, activation, and grounding.

```sql
-- Calculated Insight: customer service exposure
SELECT
    ssot__Individual__dlm.ssot__Id__c AS IndividualId,
    COUNT(Warranty_Claim__dlm.Id__c) AS TotalClaims,
    SUM(Warranty_Claim__dlm.Claim_Amount__c) AS TotalClaimValue,
    MAX(Warranty_Claim__dlm.Claim_Date__c) AS LastClaimDate
FROM ssot__Individual__dlm
JOIN Warranty_Claim__dlm
  ON ssot__Individual__dlm.ssot__Id__c = Warranty_Claim__dlm.Individual_Id__c
GROUP BY ssot__Individual__dlm.ssot__Id__c
```

**These run on a schedule** — batch, or streaming for some types — and the results are attributes on the profile.

**Why they matter for AI:** a prompt grounded on "this customer has had 14 claims totalling ₹2.3 crore, most recently last month" produces a materially different reply from one grounded on the current claim alone.

**Computing that in Apex would mean a query across eight million rows per invocation.** As a Calculated Insight it is precomputed.

## Bringing it back into the org

Four mechanisms, and choosing between them is the design decision.

**Data Cloud Related Lists** — profile data displayed on a CRM record, with no copying.

**Data Actions** — a Data Cloud event triggering a platform event, a flow, or a webhook:

```
Trigger:  a Calculated Insight crosses a threshold
Action:   publish a platform event
    → an Apex subscriber creates a proactive service case
```

**Data Cloud in Flow** — Get Records against Data Model Objects, usable in automation.

**Query API** — for Apex:

```java
ConnectApi.CdpQueryInput input = new ConnectApi.CdpQueryInput();
input.sql = 'SELECT TotalClaims__c, TotalClaimValue__c '
    + 'FROM Customer_Exposure__cio WHERE IndividualId__c = \'' + individualId + '\'';

ConnectApi.CdpQueryOutputV2 result = ConnectApi.CdpQuery.queryANSISqlV2(input);
```

**SQL, not SOQL**, and the injection concern is the same as dynamic SOQL — the value must be validated or bound.

**Data Cloud queries do not consume SOQL governor limits**, and they have their own consumption cost.

## Data Cloud and AI grounding

The connection that makes Data Cloud relevant to this section.

```
Prompt template
    ↓
Grounding: CRM record fields
         + Data Cloud unified profile attributes
         + Calculated Insight aggregations
         + retrieved knowledge articles
    ↓
The model
```

**Retrieval-augmented generation** on Data Cloud content is the pattern for grounding on unstructured data — knowledge articles, past case resolutions, documentation — where the relevant passage is found by similarity rather than by a filter.

**Vector search** over ingested unstructured content is what makes "find the three most relevant knowledge articles for this case description" work without the case being categorized first.

**The engineering:** deciding what to retrieve, how much, and in what order. Too little context produces a generic answer; too much dilutes it and costs more. See [[24.3 - Prompt Builder and Prompt Templates]].

## When Data Cloud is not the answer

Being direct, because it is proposed more often than it fits.

**A single-source problem.** If all the data is already in Salesforce, Data Cloud adds a layer for no benefit.

**A reporting problem.** Reports, dashboards, and CRM Analytics handle CRM data. Data Cloud is for cross-source unification.

**A storage problem.** Archiving to a big object is cheaper and simpler than ingesting into Data Cloud to reduce CRM storage.

**A small-scale problem.** Data Cloud is priced for volume, and a few hundred thousand records across two systems is frequently better served by an integration and a matching key.

**The test:** are there several systems whose records need resolving to one person, at volume? If not, an external ID and an upsert is a simpler answer. See [[10.3 - Upsert, Merge and External IDs]].

## Costs

Consumption-based, and the units are worth understanding before designing.

```
Data ingested          per GB
Rows processed         for Calculated Insights and identity resolution
Data stored
Segments published
Activations
Queries
```

**Design decisions that affect cost:**

**Ingest only what is needed.** Streaming every field of every object is expensive and usually unnecessary.

**Incremental refresh rather than full.**

**Zero-copy federation** where the source is a supported warehouse — no ingestion cost.

**Calculated Insight frequency.** Hourly is far more expensive than daily, and daily is frequently sufficient.

## Practical guidance

**Treat it as a warehouse with identity resolution**, not as a large custom object.

**The mapping is the work.** Budget for it as a data modelling exercise.

**Start identity resolution tight**, and loosen with evidence.

**Review over-merged profiles** before anything depends on them.

**Use Calculated Insights for aggregations** that would otherwise be an expensive query.

**Use zero-copy federation** where the source supports it.

**Ingest incrementally**, and only what is needed.

**Ask whether a single system and an external ID would do** before proposing it.
