# Beyond Postgres

#backend #databases #architecture

> **In one line:** Every non-relational database is relational-minus-something plus one specialised capability, and the honest question is whether that capability is worth what you gave up.

---

## The Idea

Postgres does relational, JSONB, full-text search, geospatial, time-series (TimescaleDB), vectors (pgvector), queues (`SKIP LOCKED`) and pub/sub — adequately to well.

💡 **The right framing: what does this specialised store do that Postgres cannot do adequately, and is that gap larger than the cost of running a second database?**

| Cost of a second datastore | |
|---|---|
| Operations | Backups, upgrades, monitoring, on-call knowledge |
| **Consistency** | Two stores means no transaction across them |
| Development | A second data model, query language and set of failure modes |
| Hiring | Fewer people know it |
| Failure surface | One more thing that can be down |

⚠️ **The consistency cost is the one that bites.** The moment your data lives in two stores, keeping them in sync becomes your problem — **and it produces the hardest bugs** ([[09.3 - The Outbox Pattern]]).

---

## Document Stores

**MongoDB, DocumentDB, Firestore**

| Genuinely good at | |
|---|---|
| Deeply nested data read as a unit | One document, one read |
| Schema that varies per record | No migration to add a field |
| Horizontal write scaling | Sharding is built in |

⚠️ **What you give up:** joins, transactions across documents (available since 4.0, slower and more limited), schema enforcement, and ad-hoc query flexibility.

💡 **Postgres's JSONB covers most document-store use cases** ([[06.10 - Schema Design]]). You get flexible documents *and* joins, transactions and constraints on the structured parts.

**The remaining case for MongoDB is horizontal write scaling with an inherently document-shaped model** — and even then Citus is worth evaluating first.

⚠️ **The common failure: using a document store for relational data.** Orders, customers and products are relational, and modelling them as documents means either duplicating data everywhere or doing joins in application code. **Both are worse than a relational database.**

## Wide-Column Stores

**Cassandra, ScyllaDB, HBase, DynamoDB**

```cql
CREATE TABLE events_by_org (
    org_id uuid, bucket text, created_at timestamp, event_id uuid, payload text,
    PRIMARY KEY ((org_id, bucket), created_at, event_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

**The partition key determines which node holds the data; the clustering columns determine the sort order within it.**

| Genuinely good at | |
|---|---|
| Very high write throughput | LSM engine, no read-before-write ([[06.1 - Storage Engines]]) |
| Linear horizontal scaling | Add nodes, capacity grows |
| Multi-region active-active | Built for it |

⚠️ **The fundamental constraint: you must design the table around the query.**

```cql
SELECT * FROM events_by_org WHERE org_id = ? AND bucket = ?;    -- fast
SELECT * FROM events_by_org WHERE event_id = ?;                 -- ❌ full scan
```

**A different query means a different table**, populated by writing the same data twice. **That is normal in Cassandra, and it is a completely different design discipline.**

💡 **The question to ask before adopting: can you enumerate every query your application will ever make?** If yes, and they are all partition-key lookups, it works beautifully. **If your queries evolve, you will be creating new tables and backfilling them constantly.**

### The anti-patterns

⚠️ **Do not build a queue on Cassandra.** Insert-then-delete creates tombstones that accumulate, and range scans must read past every one ([[06.1 - Storage Engines]]). **Scans get slower over time on a table that appears empty.**

⚠️ **Unbounded partitions.** A partition key of `org_id` alone means one organisation's data grows forever on one node. **Always bucket.**

⚠️ **`ALLOW FILTERING` is a trap** — fine on a development dataset, fatal in production.

### DynamoDB specifically

💡 **DynamoDB's single-table design is genuinely clever and genuinely hard.** All entity types share one table, with composite keys encoding relationships. It gives one-request access to related data at any scale — **and it requires knowing your access patterns completely up front, and it is very difficult to explain to a new team member.**

**The pricing model matters more than expected:** on-demand is expensive at scale, provisioned requires capacity planning, and **a hot partition throttles regardless of total provisioned capacity.**

## Time-Series Databases

**TimescaleDB, InfluxDB, ClickHouse, Prometheus**

| Genuinely good at | |
|---|---|
| Compression | 10–20× is normal — values in a column are similar |
| Time-range aggregation | Columnar layout, vectorised execution |
| Automatic retention | Drop old chunks |
| Continuous aggregates | Pre-computed rollups, updated incrementally |

### TimescaleDB

```sql
SELECT create_hypertable('metrics', 'time');
ALTER TABLE metrics SET (timescaledb.compress, timescaledb.compress_segmentby = 'device_id');
SELECT add_compression_policy('metrics', INTERVAL '7 days');
```

💡 **TimescaleDB is a Postgres extension, so you keep everything** — joins to relational tables, transactions, your existing tooling and operational knowledge. **This is the strongest argument for it over a separate time-series database**, and it makes the adoption cost dramatically lower.

### ClickHouse

Columnar, extraordinarily fast for analytical scans — billions of rows in under a second.

⚠️ **ClickHouse is not an OLTP database.** Updates and deletes are asynchronous mutations that rewrite parts. There are no real transactions. Point lookups are slow relative to a B-tree.

💡 **The right shape is Postgres for transactions, ClickHouse for analytics, connected by CDC** ([[09.4 - Change Data Capture]]). **Trying to serve both workloads from one store means compromising both.**

## Graph Databases

**Neo4j, Neptune, ArangoDB**

⚠️ **Recursive CTEs in Postgres handle a great deal of this:**

```sql
WITH RECURSIVE reachable AS (
    SELECT id, 0 AS depth FROM users WHERE id = $1
    UNION ALL
    SELECT e.to_id, r.depth + 1 FROM reachable r
    JOIN edges e ON e.from_id = r.id WHERE r.depth < 4
)
SELECT DISTINCT id FROM reachable;
```

💡 **The threshold is roughly: fixed-depth traversal up to 3–4 hops is fine in Postgres; variable-depth over millions of edges with graph algorithms is where a graph database earns its place.** Fraud detection, recommendation engines and network topology are the genuine cases.

**For a typical application's "user follows user" relationships, a join table in Postgres is correct.**

## Vector Databases

**pgvector, Qdrant, Pinecone, Weaviate, Vespa**

```sql
CREATE EXTENSION vector;
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

SELECT content FROM chunks
WHERE document_id = ANY($1)                  -- ← metadata filter
ORDER BY embedding <=> $2 LIMIT 10;
```

💡 **pgvector is the right starting point for most RAG systems**, and this is a case where "just use Postgres" is unusually strong — you get vectors *plus* transactional metadata, joins to your permission model, and one backup story.

⚠️ **The filtering problem is what pushes people to dedicated vector stores.** Approximate nearest-neighbour indexes and metadata filters interact badly:

| Approach | Problem |
|---|---|
| **Pre-filter** then search | The ANN index is built over all vectors; filtering first may leave too few reachable candidates |
| Search then **post-filter** | You asked for 10, got 10, and 9 were filtered out — now you have 1 |

**pgvector handles this reasonably with iterative scan (0.8+), and a dedicated store with native filtered-ANN does it better at scale.**

| When to move off pgvector | |
|---|---|
| Hundreds of millions of vectors | Index build time and memory |
| Heavy metadata filtering with high selectivity | Filtered ANN quality |
| Hybrid sparse + dense retrieval | Vespa, Qdrant |
| Sub-10ms p99 at very high QPS | Purpose-built engines |

**The backend point is that this is a storage engine decision like any other, and the same "what does it do that Postgres cannot" question applies.**

## Making the Decision

```
Is this the primary system of record?
├── YES → Postgres, unless you have a specific, measured reason
│
└── NO (derived, cached, or analytical)
    ├── Analytical scans over billions of rows  → ClickHouse
    ├── Time-series with heavy aggregation      → TimescaleDB (stay in Postgres)
    ├── Vector similarity, moderate scale       → pgvector (stay in Postgres)
    ├── Vector similarity, very large scale     → Qdrant / Vespa
    ├── Full-text search, complex relevance     → Elasticsearch ([[06.15 - Search - Postgres vs Elasticsearch]])
    ├── Variable-depth graph traversal          → Neo4j
    └── Extreme write throughput, known queries → Cassandra / ScyllaDB
```

💡 **Notice how many branches end in "stay in Postgres".** That is not laziness — **the operational and consistency costs of a second store are high enough that the specialised store must be substantially better, not marginally.**

### The questions to answer before adopting

1. **What specific query or workload is Postgres failing at?** With measurements
2. **Have you exhausted Postgres?** Indexes, partitioning, extensions, replicas
3. **What is the consistency model between the two stores?**
4. **What happens when it is down?** Degrade, or fail
5. **Who operates it?** Backups, upgrades, on-call
6. **What is the migration path back?**

⚠️ **Question 3 is the one that gets waved away, and it becomes the hardest engineering problem you have.** "We'll sync it with a background job" is not an answer — it is a description of the problem.

## In Production

### The polyglot pattern that works

```
Postgres          system of record. All writes. Source of truth
    │  CDC / outbox
    ├──► Elasticsearch    search index      (rebuildable)
    ├──► ClickHouse       analytics         (rebuildable)
    ├──► Redis            cache             (rebuildable)
    └──► Qdrant           vectors           (rebuildable)
```

💡 **The invariant that makes this manageable: every derived store must be rebuildable from Postgres.** If you can drop and rebuild it, a sync bug is an inconvenience rather than data loss. **If a derived store holds data existing nowhere else, you have two systems of record and no coherent backup story.**

**Test the rebuild.** A rebuild path that has never been executed does not work.

### Keeping them in sync

| Method | Consistency |
|---|---|
| **Dual write from the application** | **Broken — no atomicity** |
| Outbox pattern | Eventual, no loss ([[09.3 - The Outbox Pattern]]) |
| CDC from the WAL | Eventual, no loss ([[09.4 - Change Data Capture]]) |
| Periodic full rebuild | Eventually correct, slow |

⚠️ **Dual writes are broken and extremely common:**

```python
await postgres.insert(doc)
await elasticsearch.index(doc)      # if this fails, the two now disagree
```

**There is no transaction spanning them.** A crash between the two leaves permanent divergence. **The outbox pattern exists precisely to solve this.**

### The Conduit decision

| Need | Store | Why |
|---|---|---|
| Documents, users, orgs, annotations | **Postgres** | Relational, transactional, system of record |
| Ingestion events | **Postgres, partitioned** | Retention via `DROP`, joins to documents |
| Cache | **Redis** | Rebuildable, standard |
| Search | **Postgres FTS first, Elasticsearch if needed** | Measure before adding a store |
| Vectors (phase 9) | **pgvector** | Metadata filtering against the permission model matters more than raw scale |

💡 **The pgvector choice is worth defending explicitly**: permission-aware retrieval means every vector search is filtered by organisation and document ACLs. **Doing that in Postgres is a `WHERE` clause against real columns; doing it in a separate vector store means syncing the permission model into it.** The filtering requirement outweighs the scale advantage until well past a million chunks.

## Codebase

**Repo:** `pgvector/pgvector`, `timescale/timescaledb`, `apache/cassandra`

**Question to answer:** How does pgvector's HNSW index interact with a `WHERE` clause? Then: how does Cassandra decide which node holds a partition, and what happens when one partition grows unboundedly?

**Read, in order:**

1. `pgvector/src/hnswscan.c` and `hnswutils.c` — **the HNSW index scan.** How it interacts with the executor's filter, and the iterative scan logic. **This is the crux of the filtered-ANN problem**
2. `pgvector/README.md` — the filtering section. Short and honest about the tradeoffs
3. `timescaledb/src/chunk.c` — how a hypertable becomes chunks. **Note that it is built on Postgres partitioning** ([[06.13 - Partitioning and Sharding]])
4. `timescaledb/tsl/src/compression/` — columnar compression inside a row store. The mechanism behind the 10–20× ratios
5. `cassandra/src/java/org/apache/cassandra/dht/` — the partitioner and token ring. **How a partition key becomes a node**
6. `cassandra/src/java/org/apache/cassandra/db/compaction/` — the tombstone handling that makes the queue anti-pattern fatal

💡 The pgvector filtered-scan code is directly relevant to your AI work. **Understanding why "filter then search" and "search then filter" both have failure modes** — and what iterative scan does about it — **is the difference between a RAG system that returns good results under filtering and one that quietly returns too few.**

**Size:** 2 sessions.

## Exercise

**Drill 6.14 — Prove you need the second database**

```
drills/06-beyond-postgres/
├── workloads/{analytical.py, timeseries.py, vector.py, graph.py, highwrite.py}
├── postgres/{baseline.sql, optimised.sql, RESULTS.md}
├── specialised/{clickhouse/, timescale/, pgvector/, qdrant/, RESULTS.md}
├── sync/{dual_write.py, outbox.py, rebuild.py, FINDINGS.md}
└── decision/ADR.md
```

**Part 1 — Five workloads, Postgres first.** Implement each naively and measure. **Then optimise properly** — indexes, partitioning, extensions, materialised views, tuned configuration — and measure again.

💡 **The gap between naive and optimised Postgres is usually larger than the gap between optimised Postgres and a specialised store. Quantify it before comparing anything.**

**Part 2 — The specialised stores.** The same five workloads against ClickHouse, TimescaleDB, pgvector, a recursive CTE, and Cassandra.

**Build the table: naive Postgres, optimised Postgres, specialised store.** Three columns per workload.

**Part 3 — The filtered vector problem.** 1 million embeddings with organisation and document metadata.

Query: top-10 by cosine similarity, filtered to one organisation holding 1% of the data.

**Measure recall** (how many of the true top-10 you got) and latency for: pre-filtering, post-filtering, pgvector's iterative scan, and Qdrant's native filtered search.

**Then vary the filter selectivity — 50%, 10%, 1%, 0.1% — and chart recall against selectivity for each approach.**

⚠️ **The recall column is the one that matters and the one people forget to measure.** A fast search returning the wrong results is not a fast search. **This chart is directly reusable in your AI vault work.**

**Part 4 — Cassandra's constraints.** Model Conduit's documents in Cassandra with three access patterns: by organisation, by ID, and by status. **Note that this means three tables and triple writes.**

Then create an unbounded partition and grow it. **Measure query latency as it grows and find the point where it becomes a problem.**

Then build a queue on it — insert, read, delete — and **measure scan latency over ten cycles. Confirm the tombstone degradation.**

**Part 5 — Dual writes diverge.** Postgres plus Elasticsearch with naive dual writes.

Inject failures: Elasticsearch down for 30 seconds, a network timeout after Postgres commits, and a process kill between the two writes.

**Count the divergences.** Then implement the outbox pattern and repeat — divergence should be zero.

**Part 6 — Rebuild from source.** Drop your derived store entirely and rebuild it from Postgres.

Measure rebuild duration, and **whether the result is byte-identical to what was there before.**

**If it is not identical, you have found a bug in your sync — and that is the most valuable outcome of this drill.**

**Part 7 — The ADR.** For Conduit, decide which stores to run. Answer the six questions with your own measurements, and **state explicitly, for each rejected store, what measurement would change your mind.**

**Done when:**
- Your three-column table shows naive versus optimised Postgres versus specialised
- You can state, per workload, how much of the gap tuning closed
- Your recall-versus-selectivity chart covers four filtering approaches
- You reproduced Cassandra's unbounded-partition and tombstone problems
- Dual writes demonstrably diverged, and the outbox eliminated it
- Your derived store rebuilds identically from Postgres
- The ADR names a specific threshold for each rejected store
