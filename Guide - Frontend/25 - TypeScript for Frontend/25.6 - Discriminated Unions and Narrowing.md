# Discriminated Unions and Narrowing

A discriminated union is a union of object types sharing a **literal** property that identifies which member you have. Checking that property narrows the type.

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; error: Error }
  | { status: "success"; data: Product[] };

function render(state: State) {
  switch (state.status) {
    case "loading":
      return <Skeleton />;
    case "error":
      return <ErrorView error={state.error} />;      // error exists here
    case "success":
      return <List items={state.data} />;            // data exists here
    case "idle":
      return null;
  }
}
```

Outside the `success` branch, `state.data` is a compile error. The type system enforces what a comment or a convention only suggests.

## Making invalid states unrepresentable

This is the point, and it is worth stating plainly:

```ts
// 8 combinations, ~4 of them meaningless
type BadState = {
  isLoading: boolean;
  error: Error | null;
  data: Product[] | null;
};

// 4 states, all valid
type GoodState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; error: Error }
  | { status: "success"; data: Product[] };
```

With the boolean version, `isLoading: true` alongside `error` and `data` is representable, so every consumer must decide what that means — and different consumers decide differently. With the union, it cannot occur ([[24.2 - Loading Error and Empty States]]).

The same reasoning applies to component props ([[25.4 - Typing Props and Children]]):

```tsx
type AlertProps =
  | { variant: "error"; error: Error; onRetry: () => void }
  | { variant: "success"; message: string };
```

## Requirements for narrowing to work

**The discriminant must be a literal type**, not `string`:

```ts
type A = { kind: string; value: number };      // does NOT narrow
type B = { kind: "a"; value: number };         // narrows
```

**It must be present on every member.** A member missing the discriminant breaks narrowing for the whole union.

**Objects must be typed as the union**, not inferred separately. An object literal assigned without annotation widens `kind` to `string`, losing the discriminant:

```ts
const action = { type: "increment", by: 1 };            // type: string
dispatch(action);                                        // Error

const action = { type: "increment", by: 1 } as const;    // type: "increment"
```

This trips people up in reducers and test fixtures constantly.

## Narrowing mechanisms

Beyond the discriminant check, TypeScript narrows through several operations:

```ts
if (typeof x === "string") { }              // typeof, for primitives
if (x instanceof Error) { }                  // instanceof, for classes
if ("data" in obj) { }                       // in, for optional properties
if (Array.isArray(x)) { }                    // built-in type guards
if (x !== null) { }                          // equality narrowing
if (x) { }                                   // truthiness — careful with 0 and ""
```

Truthiness narrowing is the one that misleads:

```ts
function f(count?: number) {
  if (count) { }          // excludes 0 as well as undefined
  if (count != null) { }  // excludes only null and undefined
}
```

`0` and `""` are falsy but valid, so a truthiness check silently drops them ([[05.3 - Types Coercion and Equality]]).

## Exhaustiveness checking

The pattern that makes unions maintainable:

```ts
function render(state: State) {
  switch (state.status) {
    case "idle": return null;
    case "loading": return <Skeleton />;
    case "error": return <ErrorView error={state.error} />;
    case "success": return <List items={state.data} />;
    default: {
      const _exhaustive: never = state;
      throw new Error(`Unhandled state: ${JSON.stringify(state)}`);
    }
  }
}
```

If all cases are handled, `state` in the default branch is `never` and the assignment compiles. Add a new union member and the assignment fails — pointing at every switch that needs updating.

This turns "add a state and find all the places that handle states" from a search into a compile error. It is the highest-value pattern in this note.

Enabling `noImplicitReturns` and `switch` exhaustiveness lint rules gives similar coverage without the boilerplate.

## Custom type guards

```ts
function isHttpError(err: unknown): err is HttpError {
  return err instanceof HttpError;
}

function isNonEmpty<T>(arr: T[]): arr is [T, ...T[]] {
  return arr.length > 0;
}

try {
  await save();
} catch (err) {
  if (isHttpError(err) && err.status === 422) { }
}
```

The `x is T` return type tells the checker that a `true` result means narrowing. Note the guard's body is **not verified** — an incorrect predicate silently lies to the type system, which is why guards should be small and obviously correct.

TypeScript 5.5 infers predicates for simple cases automatically:

```ts
const isDefined = (x: string | undefined) => x !== undefined;
values.filter(isDefined);      // now narrows to string[]
```

Previously this required an explicit `x is string`.

## Assertion functions

```ts
function assertDefined<T>(value: T | null | undefined, message: string): asserts value is T {
  if (value == null) throw new Error(message);
}

const user = users.find(u => u.id === id);
assertDefined(user, "User not found");
user.name;      // narrowed — no optional chaining needed
```

`asserts value is T` narrows for the remainder of the scope rather than inside a block. Useful at boundaries where absence is genuinely a bug rather than a case to handle.

Assertion functions require an explicit type annotation on the variable holding them — TypeScript will not infer them through a `const` alias.

## Narrowing pitfalls

**Narrowing is lost across closures:**

```ts
function f(value: string | null) {
  if (value === null) return;
  setTimeout(() => value.toUpperCase(), 0);   // Error — value may have changed
}
```

The checker cannot prove the variable was not reassigned before the callback runs. Assign to a `const` first:

```ts
const safe = value;
if (safe === null) return;
setTimeout(() => safe.toUpperCase(), 0);      // fine
```

**Narrowing is lost after a function call** on a mutable object property:

```ts
if (obj.value !== null) {
  doSomething();
  obj.value.trim();        // Error — doSomething() might have changed it
}
```

Destructuring to a local first avoids this.

**Optional chaining does not narrow the parent:**

```ts
if (user?.profile) {
  user.profile.name;       // this does narrow
  user.name;               // user is still User | undefined
}
```

## Unknown over any

```ts
function handle(err: unknown) {
  if (err instanceof Error) return err.message;
  if (typeof err === "string") return err;
  return "Unknown error";
}
```

Caught errors are `unknown` by default under `useUnknownInCatchVariables` (included in `strict`). That is correct — anything can be thrown ([[05.9 - Error Handling and Custom Errors]]) — and it forces the narrowing that `any` would skip.

The general rule: `unknown` at every boundary where the shape is not guaranteed, then narrow. `any` disables checking silently and propagates.

## Modelling API responses

```ts
type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string } };

const result = await api.getProduct(id);
if (!result.ok) return <Error message={result.error.message} />;
return <Product data={result.data} />;
```

Making failure part of the type rather than an exception forces every caller to handle it. This suits expected failures — validation, not-found, forbidden — while genuine faults still throw ([[24.1 - Building an API Layer]]).

## How senior engineers actually use this

**They model every async view as a status union**, not parallel booleans.

**They add an exhaustive `never` check** to any switch over a union that will grow.

**They use `as const` on action and fixture objects**, or narrowing silently fails.

**They keep type guards small**, since the body is unverified.

**They accept `unknown` at boundaries** and narrow, rather than reaching for `any`.

## Common pitfalls

- A discriminant typed `string` instead of a literal.
- Object literals losing their literal type without `as const`.
- Truthiness narrowing excluding valid `0` and `""`.
- Narrowing lost inside a closure or after a function call.
- Type guards whose body does not match the predicate.
- `any` in a catch block, skipping the narrowing that `unknown` forces.
- No exhaustiveness check, so adding a union member silently misses call sites.

## Interview angle

"How would you model loading and error state in TypeScript" is where this lands, and the answer is the discriminated union with the argument that it makes invalid states unrepresentable — three booleans give eight combinations, half of them meaningless. Then the exhaustiveness check with `never`, which converts "add a state and find every consumer" into a compile error. Mentioning that narrowing is lost across closures, and why, shows you have hit the real edges.
