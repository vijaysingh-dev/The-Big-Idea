# Fine-Tuning Fundamentals

## When to Fine-Tune

Fine-tuning is overused. Before fine-tuning, exhaust these in order:

```
1. Prompt engineering  → Zero cost, try first
2. Few-shot examples   → Still just prompt cost
3. RAG               → Dynamic knowledge injection
4. Fine-tuning        → Only if above fail
```

**Legitimate reasons to fine-tune**:

- Consistent output format that prompt engineering can't reliably achieve
- Specialized domain vocabulary/style not in base training
- Reducing latency via smaller model (fine-tune small model to match large model behavior)
- Reducing cost (smaller fine-tuned model outperforms larger base model on specific task)
- Behavior that must hold across thousands of diverse inputs consistently
- Strong latency constraint requiring a smaller model

**Wrong reasons to fine-tune**:

- ❌ To inject new knowledge (use RAG)
- ❌ To get it to "know about" recent events (use RAG)
- ❌ Because prompting "kind of works but isn't perfect" (try harder on prompting)
- ❌ Because a tutorial suggests it

## Types of Fine-Tuning

### Full Fine-Tuning

Update **all** model weights on your dataset.

```
Pretrained weights  ──training──→  Task-specific weights
(all parameters updated)
```

- Highest quality ceiling
- Requires significant compute (full model in GPU memory + gradients + optimizer states ≈ 16× model size in bytes)
- Risk of **catastrophic forgetting** — fine-tuning on narrow data can degrade general capabilities
- Rarely done outside of well-resourced teams

### Supervised Fine-Tuning (SFT)

Train on `(instruction, response)` pairs to teach instruction following:

```json
{"messages": [
    {"role": "system",    "content": "You are a financial data analyst."},
    {"role": "user",      "content": "Summarize this earnings report: ..."},
    {"role": "assistant", "content": "Q3 2024 results show..."}
]}
```

This is what converts a base model to an instruction-following model (e.g., Llama-base → Llama-Instruct).

**Data requirements**: Typically 1K–100K high-quality examples. Quality > quantity. 500 excellent examples often beat 10K mediocre ones.

### Instruction Tuning

A form of SFT but with diverse task types:

- Summarize this article
- Translate to French
- Answer this question
- Write code to do X

The diversity prevents overfitting to a narrow task. It's how models become generally useful rather than task-specific.

## The SFT Training Loop

```python
# Simplified SFT training loop
for batch in dataloader:
    input_ids = batch["input_ids"]     # tokenized instruction + response
    labels = batch["labels"]           # same as input_ids, but -100 on instruction tokens
    
    # Forward pass
    logits = model(input_ids)
    
    # Only compute loss on response tokens (not instruction tokens)
    loss = cross_entropy(logits, labels, ignore_index=-100)
    
    # Backward pass
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
```

**Key detail**: Labels mask out the instruction tokens (set to -100 = ignore). You only compute loss on the assistant's response tokens — you're teaching the model what the right response is given the instruction, not teaching it to reconstruct the instruction.

## Data Requirements

|Scenario|Min examples|Quality bar|
|---|---|---|
|Formatting behavior|500–1K|High: consistent format in every example|
|Domain adaptation|5K–50K|Medium: must cover domain breadth|
|Instruction following|10K–100K|High: diverse, well-written responses|
|Replacing a large model|50K–500K|Very high: comprehensive coverage|

**Data quality checklist**:

- [ ] Consistent format across all examples
- [ ] No instruction-response contradictions
- [ ] Representative of real input distribution
- [ ] Correct responses (errors in training data = baked-in errors)
- [ ] Adequate diversity (don't over-represent any single pattern)

See [[04.4 - Dataset Preparation and Quality]] for full data pipeline.

## Catastrophic Forgetting

When you fine-tune on a narrow dataset, the model can "forget" its general capabilities:

```
Before fine-tuning: Excellent at translation, code, math, QA...
After fine-tuning on medical QA only:
  - Medical QA: excellent ✅
  - Translation: degraded ❌
  - General reasoning: degraded ❌
```

**Mitigations**:

1. **PEFT (LoRA)**: Only update a small fraction of weights → much less forgetting
2. **Replay**: Mix general instruction-following data with your task data
3. **Lower learning rate**: Smaller steps → less overwriting of pretrained knowledge
4. **Fewer epochs**: Stop before the model overfits to your narrow task

## Full Fine-Tuning vs PEFT Tradeoffs

|Dimension|Full Fine-Tuning|PEFT (LoRA)|
|---|---|---|
|GPU memory|Very high|Low–medium|
|Training time|Long|Short|
|Quality ceiling|Highest|Nearly as good (90–95%)|
|Catastrophic forgetting|High risk|Low risk|
|Inference cost|Same as base model|Same as base model|
|Deployment|Single merged model|Base model + adapter|

For most production use cases: **PEFT/LoRA is the right default**. See [[04.3 - PEFT - LoRA QLoRA Adapters]].
