# Context API and Its Limits

Context is **dependency injection**. It makes a value available to a subtree without passing it through every intermediate component. The API mechanics are in [[17.9 - useContext]]; this note is about when it is and is not the right tool.

## The fundamental limitation

**There is no subscription granularity.** Every consumer re-renders when the provider's value changes, regardless of which part of the value they read.

```jsx
const AppContext = createContext();

<AppContext.Provider value={{ user, theme, notifications, cart }}>
```

A component reading only `theme` re-renders when `notifications` changes. There is no `useContext(AppContext, ctx => ctx.theme)` — selectors do not exist in the context API.

`React.memo` does not help. Memo compares props; context is not a prop, so a memoized consumer still re-renders on every context change.

This one property determines everything about when context is appropriate.

## The two mitigations

**1. Memoize the value.**

```jsx
// Every consumer re-renders on every provider render
<Ctx.Provider value={{ user, setUser }}>

// Stable
const value = useMemo(() => ({ user, setUser }), [user]);
<Ctx.Provider value={value}>
```

Forgetting this is the most common context bug, and it is invisible without profiling ([[17.6 - useMemo]]).

**2. Split by change frequency.**

```jsx
<ThemeContext value={theme}>         {/* changes almost never */}
  <UserContext value={user}>          {/* changes on login/logout */}
    <CartContext value={cart}>        {/* changes often */}
```

A component reading only theme is now unaffected by cart changes. Splitting is the primary technique, and it works well when the data genuinely separates.

**3. Separate state from dispatch.**

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <StateContext value={state}>
      <DispatchContext value={dispatch}>{children}</DispatchContext>
    </StateContext>
  );
}
```

`dispatch` from `useReducer` is guaranteed stable, so components that only dispatch never re-render on state changes ([[17.10 - useReducer]]). In a form or toolbar, that is most of the components.

## Where context fits well

The pattern: **read widely, change rarely.**

- Theme and design tokens
- Locale and translations
- The authenticated user
- Feature flags
- A router instance
- A query client or store instance
- Component-scoped state in compound components ([[22.6 - Compound Components]])

The last one is worth noting: context inside a single component's subtree — `<Tabs>` sharing the active tab with `<TabPanel>` — is an excellent use. The subtree is small, so the re-render scope is bounded.

## Where context does not fit

**Frequently-changing global state.** A cart updated on every quantity change, a live data feed, cursor position, or anything updating per keystroke will re-render every consumer.

**Large state objects read partially.** If most consumers need one field of a twenty-field object, you are paying for nineteen irrelevant re-renders each time.

**Server data.** Caching, revalidation, deduplication and cancellation are not context's job ([[24.6 - TanStack Query Fundamentals]]).

## Context versus a store

| | Context | Store (Zustand/Redux/Jotai) |
| --- | --- | --- |
| Purpose | dependency injection | state management |
| Subscription | whole value | selector-based slice |
| Re-renders | all consumers | only components reading changed data |
| Middleware | none | logging, persistence, devtools |
| Outside React | no | yes — read/write from anywhere |
| Setup | built in | a dependency |

The decisive difference is selector granularity:

```jsx
// Context — re-renders on any change to the context value
const { count } = useContext(AppContext);

// Store — re-renders only when count changes
const count = useStore(s => s.count);
```

Stores implement this with `useSyncExternalStore` ([[17.12 - Lesser Known Hooks]]) — they subscribe outside React and only trigger a re-render when the selected slice actually changed.

The common production shape is **both**: context provides the store *instance* (so it can be scoped, tested and server-rendered per request), and the store's own subscription mechanism handles reads.

```jsx
const StoreContext = createContext(null);

function useAppStore(selector) {
  const store = useContext(StoreContext);
  return useStore(store, selector);
}
```

## Try composition first

Context is frequently reached for to solve prop drilling that composition solves better ([[16.3 - Components and Props]]):

```jsx
// Drilling
<Layout user={user}><Sidebar user={user}><Profile user={user} /></Sidebar></Layout>

// Composition — no drilling, no context
<Layout sidebar={<Sidebar><Profile user={user} /></Sidebar>} />
```

The official guidance is explicit: pass props, then try composition, then use context. Two or three levels of drilling is not a problem worth abstracting.

## Provider nesting

```jsx
<QueryClientProvider client={client}>
  <ThemeProvider>
    <AuthProvider>
      <RouterProvider>
        <App />
```

Deep provider nesting is normal and has no meaningful runtime cost — each provider adds one fiber. Extract it into a single `<Providers>` component for readability.

## Server Components

Context requires interactivity, so it works only in Client Components. A Server Component cannot call `useContext` or render a provider ([[22.8 - Server Components]]).

The pattern is a client provider wrapping server-rendered children:

```jsx
// providers.tsx
"use client";
export function Providers({ children }) {
  return <ThemeContext value={theme}>{children}</ThemeContext>;
}
```

Children passed through remain server components — only the provider itself is client-side. This is worth understanding because it is a common source of "why is my whole app a client component" problems.

## How senior engineers actually use this

**They memoize every provider value**, as a reflex.

**They split contexts by change frequency** rather than creating one app-wide context.

**They use context for injection and a store for state.** Context providing a store instance is the standard production shape.

**They export a custom hook with a guard**, not the raw context object:

```jsx
function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}
```

**They try composition first** for prop drilling.

## Common pitfalls

- Unmemoized provider values.
- One large context mixing fast- and slow-changing data.
- Expecting `React.memo` to block context re-renders.
- Using context as a general state manager for frequently-changing values.
- Server data in context.
- Reaching for context to avoid two levels of prop passing.
- Rendering a provider in a Server Component.

## Interview angle

"Context API vs Redux" is the standard question, and comparing features misses the point. The strong answer distinguishes purpose: context is dependency injection with no subscription granularity, so every consumer re-renders on any value change; a store provides selector-based subscriptions so only affected components re-render. Then give the mitigations — memoize the value, split by frequency, separate state from dispatch — and note that the common production setup uses both together.
