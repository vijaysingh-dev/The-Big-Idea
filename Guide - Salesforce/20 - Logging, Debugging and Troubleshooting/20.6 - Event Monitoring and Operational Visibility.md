# Event Monitoring and Operational Visibility

## What it adds

Debug logs show one transaction. Custom logs show what your code recorded. **Event Monitoring shows what actually happened across the org** — every login, every API call, every report run, every slow request, for every user.

It answers questions nothing else can:

- Which Apex is slow **for real users**, not in a test
- Who exported the customer list last month
- Which integration is consuming the API allocation
- Which pages are slow, for which users, in which regions
- Whether a permission change is actually being used

**It requires Salesforce Shield** or the Event Monitoring add-on. That licensing gate is why many orgs do not have it, and why this note also covers what to do without it.

## Event log files

Events are delivered as `EventLogFile` records, one per event type per day.

```sql
SELECT Id, EventType, LogDate, LogFileLength, LogFileFieldNames
FROM EventLogFile
WHERE LogDate = LAST_N_DAYS:7 AND EventType = 'ApexExecution'
ORDER BY LogDate DESC
```

The file itself is CSV, fetched from `LogFile`:

```bash
sf data query \
  --query "SELECT Id, EventType, LogDate FROM EventLogFile WHERE EventType='ApexExecution' AND LogDate=LAST_N_DAYS:1" \
  --target-org production

sf api request rest '/services/data/v62.0/sobjects/EventLogFile/0AT5g00000ABCDeAAB/LogFile' \
  --target-org production > apex-execution.csv
```

**Delivery is daily by default**, with hourly available on some editions. That lag matters — Event Monitoring is not a real-time alerting tool.

## The event types that matter

Around fifty exist; these are the ones worth knowing.

**`ApexExecution`** — every Apex transaction with its duration, CPU time, callout time, and whether it was long-running.

```
TIMESTAMP, USER_ID, REQUEST_ID, ENTRY_POINT, QUIDDITY,
RUN_TIME, CPU_TIME, DB_TOTAL_TIME, CALLOUT_TIME,
IS_LONG_RUNNING_REQUEST, NUMBER_SOQL_QUERIES, NUMBER_DML_ROWS
```

**`IS_LONG_RUNNING_REQUEST`** is the field that identifies what is consuming concurrency slots — the limit from [[16.6 - Concurrency and Long Running Requests]] that causes rejections for unrelated users.

**`QUIDDITY`** names the execution context: `VF` for Visualforce, `AURA` for Lightning, `BATCH_APEX`, `QUEUEABLE`, `SYNCHRONOUS`, `REST`, and so on. Filtering by it separates user-facing slowness from batch slowness.

**`ApexCallout`** — outbound HTTP calls with URL, method, status, and duration. This is where an external system's degradation becomes visible before it starts failing.

**`API` and `RestApi`** — inbound calls with the user, the client, the URI, the rows returned, and the API version. **The API version field is what tells you what breaks when Salesforce retires old versions.**

**`Login` and `LoginAs`** — every authentication with source IP, browser, platform, and status.

**`ReportExport` and `ContentTransfer`** — data leaving the org. The primary security use.

**`LightningPageView` and `LightningPerformance`** — page load times by page, browser, and region, from real sessions.

**`Search`** — what users search for and whether they find anything, which drives search configuration.

**`FlowExecution`** — flow runs with duration and status.

## The questions it answers

**"Which Apex is slow for real users?"**

```
Filter ApexExecution where IS_LONG_RUNNING_REQUEST = true
Group by ENTRY_POINT
Sort by count and by average RUN_TIME
```

That is the list of what to fix, ordered by impact — and it cannot be derived from anything else.

**"Who is consuming the API allocation?"**

```
Filter API and RestApi
Group by USER_ID and CLIENT_NAME
Sum the row count
```

A single integration accounting for 80% of the daily allocation is a common finding, and it is invisible without this. See [[13.1 - Integration Fundamentals and Patterns]].

**"What data left the org?"**

```
Filter ReportExport and ContentTransfer
Group by USER_ID
```

The compliance and offboarding use, and the one auditors ask about.

**"Which pages are slow, and for whom?"**

```
Filter LightningPageView
Group by PAGE_APP_NAME and BROWSER_NAME
Compare EE_PAGE_TIME across regions
```

Frequently reveals that a page is fine in the office and slow for a region on a worse network — which changes the fix from "optimize the query" to "reduce the payload".

**"Is this external system degrading?"**

```
Filter ApexCallout
Group by URL
Trend the average RUN_TIME weekly
```

A median response time that doubled last month is a warning before the timeouts start.

## Transaction Security Policies

The real-time half of Shield. Where event log files are daily, **Transaction Security** evaluates in-flight and can block.

```
Setup → Transaction Security Policies → New

Event Type:  ReportEvent
Condition:   row count > 10,000 AND report contains sensitive fields
Action:      Block, and notify the security team
```

Policies can **Block**, require **Two-Factor**, **End Session**, or **Notify**.

Custom conditions are written in Apex:

```java
global with sharing class LargeExportPolicy implements TxnSecurity.EventCondition {

    global Boolean evaluate(SObject event) {
        ReportEvent reportEvent = (ReportEvent) event;

        // blocking a large export of a sensitive report, in flight
        return reportEvent.RowsProcessed > 10000
            && reportEvent.ReportName.contains('Customer Contact');
    }
}
```

This is genuinely preventive rather than forensic, and it is the part of Shield that stops an incident rather than documenting it. See [[22.1 - Salesforce Shield Overview]].

## Real-Time Event Monitoring

A newer capability delivering events as **platform events**, subscribable immediately rather than daily.

```java
trigger ApiEventTrigger on ApiEvent (after insert) {
    for (ApiEvent event : Trigger.new) {
        if (event.RowsProcessed > 50000) {
            SecurityAlertService.notify('Large API extract', event);
        }
    }
}
```

Available event types include `ApiEvent`, `LoginEvent`, `ReportEvent`, `ListViewEvent`, and `SessionHostileEvent`.

**Some can be stored** in big objects for retention beyond the standard window, which is how long-term audit history is kept without consuming data storage. See [[02.15 - Big Objects]].

## Without Shield

Most orgs do not have it, and there is still meaningful visibility available.

**`LoginHistory`** is standard:

```sql
SELECT UserId, LoginTime, SourceIp, Application, ApiType, ApiVersion, Status, Browser
FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:7 AND Application != 'Browser'
ORDER BY LoginTime DESC
```

**`Application` and `ApiVersion`** answer which integrations are connecting and on which API version — the retirement question, without Shield.

**`AsyncApexJob`** for job outcomes:

```sql
SELECT ApexClass.Name, JobType, Status, NumberOfErrors, ExtendedStatus,
       CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE CreatedDate = LAST_N_DAYS:7 AND Status IN ('Failed', 'Aborted')
```

**`SetupAuditTrail`** for configuration changes:

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail
WHERE CreatedDate = LAST_N_DAYS:30
ORDER BY CreatedDate DESC
```

**Six months of retention**, and it is the first thing to check when something worked yesterday and does not today. "Who deactivated the flow" has an answer here.

**`OrgLimits`** for allocation consumption:

```java
for (System.OrgLimit orgLimit : OrgLimits.getAll()) {
    if (orgLimit.getValue() > orgLimit.getLimit() * 0.7) {
        Logger.warn('OrgLimits',
            orgLimit.getName() + ': ' + orgLimit.getValue() + ' of ' + orgLimit.getLimit());
    }
}
```

Logged daily by a scheduled job, this catches API and async exhaustion before users report it.

**A custom logging framework** covers application-level visibility, which is the largest gap Shield would otherwise fill. See [[20.5 - Custom Logging Frameworks]].

## Building a monitoring baseline

What is worth having in any production org, Shield or not.

**Daily, automated:**

```
Failed async jobs                     AsyncApexJob
Org limit consumption above 70%       OrgLimits
Integration errors                    the custom log
Jobs that stopped running             the custom log's last-run timestamps
```

**Weekly, reviewed:**

```
Setup changes                         SetupAuditTrail
Login anomalies                       LoginHistory
Error trend by context                the custom log
Slow operations                       ApexExecution, if Shield
```

**Alert on absence, not only on failure.** An integration that has logged nothing for six hours, on a schedule that runs hourly, is broken — and no error was raised. That query is the single most valuable monitoring check most orgs lack.

## Exporting for analysis

Salesforce reports are a poor log-analysis tool. For anything at operational scale, events belong in a platform built for it.

```
Event Log File Browser        a free AppExchange app, for ad hoc inspection
Splunk / Datadog / Elastic    with a Salesforce connector
CRM Analytics                 with the Event Monitoring app
A data warehouse              via daily extract
```

**The Event Monitoring Analytics App** ships prebuilt dashboards, which is the fastest route to value for an org that has just enabled Shield.

## Practical guidance

**Filter `ApexExecution` on `IS_LONG_RUNNING_REQUEST`** to find what is consuming concurrency.

**Group API events by user and client** to find the integration eating the allocation.

**Check `ApiVersion` in `LoginHistory`** before a version retirement.

**Use Transaction Security** to block rather than merely record.

**Check `SetupAuditTrail` first** when something worked yesterday.

**Log org limit consumption daily**, Shield or not.

**Alert on absence** as well as on failure.

**Export to a real log platform** for anything at scale.
