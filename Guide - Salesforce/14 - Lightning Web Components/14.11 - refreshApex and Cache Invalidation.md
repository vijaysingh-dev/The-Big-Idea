# refreshApex and Cache Invalidation

## The problem

A wire fetches data. An imperative call changes it. The wire has no idea and keeps showing the old values.

```javascript
@wire(getClaims, { accountId: '$recordId' })
claimResult;

async handleApprove() {
    await approveClaim({ claimId: this.selectedId });
    // the list still shows the claim as Submitted
}
```

This is the most common complaint about wires, and the fix depends on **which cache** is stale.

## Two caches

**The Apex client cache** holds results of `cacheable=true` methods, keyed on method and parameters. Invalidated with `refreshApex`.

**The Lightning Data Service record cache** holds records fetched through `getRecord`, `getRecords`, and the record forms. Invalidated with `notifyRecordUpdateAvailable`, or automatically when LDS itself performs the update.

Using the wrong tool on the wrong cache does nothing, which produces the confusing situation where `refreshApex` is called and nothing changes.

## refreshApex

```javascript
import { refreshApex } from '@salesforce/apex';

@wire(getClaims, { accountId: '$recordId' })
claimResult;   // the whole result object, not destructured

get claims() {
    return this.claimResult?.data ?? [];
}

async handleApprove() {
    await approveClaim({ claimId: this.selectedId });
    await refreshApex(this.claimResult);
}
```

**The stored value must be the whole wire result**, not just its data. `refreshApex` needs the internal handle attached to it.

```javascript
// Works
@wire(getClaims, { accountId: '$recordId' })
claimResult;

// Does not work — the handle is lost
@wire(getClaims, { accountId: '$recordId' })
wiredClaims({ data }) {
    this.claims = data;
}
```

With the function form, keep the result as well:

```javascript
@wire(getClaims, { accountId: '$recordId' })
wiredClaims(result) {
    // keeping the raw result is what makes refreshApex possible later
    this.claimResult = result;

    if (result.data) {
        this.claims = result.data.map((claim) => ({
            ...claim,
            statusClass: claim.Status__c === 'Rejected' ? 'slds-theme_error' : ''
        }));
    } else if (result.error) {
        this.error = result.error;
    }
}
```

**`refreshApex` returns a Promise**, so awaiting it means the data has arrived before the next line runs. Not awaiting it is a common cause of a spinner that stops too early.

## What refreshApex actually does

It invalidates the cache entry and re-executes the wire. Every component wired to the same method with the same parameters gets fresh data, not just the one that called it.

That is usually helpful and occasionally surprising — refreshing in one component updates a sibling that shares the wire.

**It does not refresh other methods.** A component with three wires needs three refreshes, or a single composed method that covers all three:

```javascript
async refreshAll() {
    await Promise.all([
        refreshApex(this.claimResult),
        refreshApex(this.coverageResult),
        refreshApex(this.assetResult)
    ]);
}
```

`Promise.all` runs them in parallel rather than sequentially, which matters when each is a round trip.

## notifyRecordUpdateAvailable

For the LDS record cache, when a record was changed outside LDS — by an Apex call, or by another system.

```javascript
import { notifyRecordUpdateAvailable } from 'lightning/uiRecordApi';

async handleApprove() {
    await approveClaim({ claimId: this.recordId });

    // tells LDS the record changed server-side, so every component using it refetches
    await notifyRecordUpdateAvailable([{ recordId: this.recordId }]);
}
```

This refreshes **every component on the page** using that record through LDS, including the standard record detail panel and the highlights panel. That is its main value — a custom action updating a record can make the whole page reflect the change.

It replaces the deprecated `getRecordNotifyChange`.

**When it is not needed:** if the update went through LDS itself — `updateRecord`, or a `lightning-record-edit-form` — the cache updates automatically.

## Which to use

| The change was made by | Refresh with |
| --- | --- |
| Imperative Apex | `refreshApex` on the Apex wire, and `notifyRecordUpdateAvailable` if LDS also shows the record |
| `updateRecord` from LDS | Nothing — automatic |
| `lightning-record-edit-form` | Nothing — automatic |
| A platform event, from another user | `refreshApex` and/or `notifyRecordUpdateAvailable` |
| A flow launched from the component | Both, since the flow's changes are invisible to both caches |

The last row catches people: a screen flow in a modal updating records leaves both caches stale, and the component that launched it must refresh explicitly on the flow's `statuschange` event.

## The typical pattern

```javascript
import { LightningElement, api, wire } from 'lwc';
import { refreshApex } from '@salesforce/apex';
import { notifyRecordUpdateAvailable } from 'lightning/uiRecordApi';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';
import getClaims from '@salesforce/apex/ClaimController.getClaims';
import approveClaim from '@salesforce/apex/ClaimController.approveClaim';

export default class ClaimApprovalPanel extends LightningElement {
    @api recordId;

    claimResult;
    isProcessing = false;

    @wire(getClaims, { accountId: '$recordId' })
    wiredClaims(result) {
        this.claimResult = result;
    }

    get claims() {
        return this.claimResult?.data ?? [];
    }

    async handleApprove(event) {
        const claimId = event.target.dataset.claimId;
        this.isProcessing = true;

        try {
            await approveClaim({ claimId, approvedAmount: this.approvedAmount });

            // both caches, because the list comes from Apex and the record panel from LDS
            await Promise.all([
                refreshApex(this.claimResult),
                notifyRecordUpdateAvailable([{ recordId: claimId }])
            ]);

            this.showToast('Approved', 'The claim has been approved.', 'success');
        } catch (error) {
            this.showToast('Approval failed', reduceErrors(error), 'error');
        } finally {
            this.isProcessing = false;
        }
    }
}
```

The `finally` block clearing the spinner regardless of outcome is the detail most often missed — a failed action that leaves the spinner running looks like a hang.

## Refreshing from a platform event

When another user's action should update this component:

```javascript
import { subscribe, unsubscribe } from 'lightning/empApi';

connectedCallback() {
    if (this.subscription) {
        return;
    }
    subscribe('/event/Claim_Approved__e', -1, (message) => {
        // only refresh if the event concerns records this component is showing
        if (this.isRelevant(message.data.payload)) {
            refreshApex(this.claimResult);
        }
    }).then((response) => {
        this.subscription = response;
    });
}

disconnectedCallback() {
    unsubscribe(this.subscription);
}
```

The relevance check matters. Refreshing on every event, in a console with several open tabs, produces a burst of Apex calls each time anything happens anywhere.

Throttling is worth adding where events are frequent:

```javascript
scheduleRefresh() {
    // collapses a burst of events into one refresh
    clearTimeout(this.refreshTimer);
    this.refreshTimer = setTimeout(() => refreshApex(this.claimResult), 500);
}
```

Clearing the timer in `disconnectedCallback` prevents a refresh firing against an unmounted component.

## The refresh loop trap

```javascript
@wire(getClaims, { accountId: '$recordId' })
wiredClaims(result) {
    this.claimResult = result;
    if (result.data) {
        this.updateSomething();   // if this triggers a refresh, it loops forever
    }
}
```

A wire handler that causes its own wire to re-execute is an infinite loop. It is easy to create indirectly — the handler updates a record, a trigger fires, an event publishes, a subscriber refreshes, the wire runs again.

The defences: never refresh from within a wire handler, and make event subscribers check relevance before refreshing.

## The manual refresh option

Sometimes the right answer is not to refresh automatically.

A dashboard summarizing thousands of records, refreshing on every change anywhere, is expensive and distracting. A refresh button, plus a "last updated" timestamp, is often the better experience:

```html
<lightning-button-icon icon-name="utility:refresh"
                       alternative-text="Refresh"
                       onclick={handleRefresh}>
</lightning-button-icon>
<span class="slds-text-body_small">Updated {lastRefreshedLabel}</span>
```

Deciding between automatic and manual is a design question, not a technical one, and the automatic answer is not always right.

## Testing

```javascript
import { refreshApex } from '@salesforce/apex';

jest.mock('@salesforce/apex', () => ({ refreshApex: jest.fn() }), { virtual: true });

it('refreshes the list after an approval', async () => {
    approveClaim.mockResolvedValue('a0X123');

    const element = createElement('c-claim-panel', { is: ClaimPanel });
    document.body.appendChild(element);

    getClaims.emit(mockClaims);
    await flushPromises();

    element.shadowRoot.querySelector('lightning-button').click();
    await flushPromises();

    expect(refreshApex).toHaveBeenCalled();
});
```

Asserting that the refresh happened is worth doing — the stale-data bug is easy to reintroduce and invisible in a unit test that only checks the Apex call. See [[14.18 - Jest Testing for LWC]].

## Practical guidance

**Store the whole wire result**, not just its data.

**Await `refreshApex`** so the spinner clears at the right time.

**Use `notifyRecordUpdateAvailable`** for the LDS cache and `refreshApex` for the Apex cache — they are different caches.

**Refresh both** when a change affects an Apex list and an LDS record panel.

**Refresh after a flow**, since neither cache knows what it did.

**Check relevance before refreshing on an event**, and throttle bursts.

**Never refresh from inside a wire handler.**

**Clear the spinner in `finally`.**

**Consider a manual refresh** for expensive dashboards.
