# Execution Context and Scope Chain

An **execution context** is the environment the engine creates every time it is about to run some code. It holds the answers to three questions: what variables exist here, what does `this` refer to, and where do I look if I cannot find a variable locally.

Hoisting, the temporal dead zone, closures and `this` are all consequences of how execution contexts are built. Understanding this one mechanism removes the need to memorize those rules separately.

## The three kinds of context

**Global execution context** — created once when your script loads. Its variable environment is the global object (`window` in browsers, `globalThis` everywhere), and `this` points at it (in non-module, non-strict code).

**Function execution context** — created fresh on every function *call*, not on every function definition. Calling a function ten times creates ten contexts.

**Eval context** — created by `eval()`. Ignore it; it is effectively deprecated in practice.

## Two phases: creation, then execution

Every context is built in two passes.

**Creation phase.** The engine scans the code and sets up:

1. A **variable environment** — `var` declarations and function declarations get registered. `var` bindings are initialized to `undefined`; function declarations are fully assigned.
2. A **lexical environment** — `let` and `const` declarations get registered but left *uninitialized*. This uninitialized state is the temporal dead zone (see [[05.2 - Hoisting and the Temporal Dead Zone]]).
3. A reference to the **outer environment** — this is what forms the scope chain.
4. The value of `this`.

**Execution phase.** The engine runs the code line by line, assigning values.

```js
console.log(a);     // undefined  — var registered, initialized to undefined
console.log(fn());  // "works"    — function declaration fully hoisted
console.log(b);     // ReferenceError — let is in the TDZ

var a = 1;
let b = 2;
function fn() { return "works"; }
```

Nothing is "moved to the top" of the file, despite how hoisting is usually taught. The bindings simply already exist by the time execution starts, because the creation phase registered them.

## The scope chain

Each context stores a pointer to the environment it was **defined in** — not the one that called it. When the engine cannot resolve an identifier locally, it follows that pointer outward, one environment at a time, until it finds the binding or hits the global environment and throws a `ReferenceError`.

```js
const level = "global";

function outer() {
  const level = "outer";

  function inner() {
    console.log(level);
  }

  return inner;
}

function caller() {
  const level = "caller";
  outer()();
}

caller(); // "outer"
```

`inner` logs `"outer"` even though it was *called* from inside `caller`. The chain is fixed by where the function sits in the source, which is why it is called **lexical** scoping. This is covered further in [[02.2 - Lexical Scope]].

A useful mental picture of the chain during the `inner` call:

```
inner env      { }                -> outer env
outer env      { level: "outer" } -> global env
global env     { level: "global", outer, caller } -> null
```

## Blocks create environments too

`let` and `const` are block-scoped, so `{ }`, `if`, `for` and `while` bodies each create their own lexical environment.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3

for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0);
}
// 0, 1, 2
```

The `var` loop has one binding shared by all three callbacks. The `let` loop creates a fresh binding per iteration, and the engine copies the current value into each one. This is the single most common interview question derived from scope mechanics.

## How senior engineers actually use this

**They read stack-trace scope, not guess it.** In Chrome DevTools, pausing on a breakpoint shows a Scope panel listing Local, Closure and Global sections. That panel *is* the scope chain, materialized. When a variable holds an unexpected value, opening that panel is faster than reasoning about it.

**They keep the chain shallow.** Deeply nested functions mean longer lookup chains and, more importantly, more places a name can be shadowed. Extracting inner functions to module scope with explicit parameters usually makes code both faster to read and easier to test.

**They rely on this for module design.** The module pattern, dependency injection via closures, and React custom hooks all work because a function carries its defining environment with it. See [[02.4 - Closure Patterns in Production]].

**They treat global scope as a leak.** Anything on `globalThis` lives for the page's lifetime and can never be garbage collected, and it collides across scripts. ES modules (see [[08.1 - ES Modules vs CommonJS]]) have their own top-level scope specifically to avoid this.

## Common pitfalls

- Believing hoisting physically moves code. It does not; declarations are registered before execution, which produces the same observable behavior for `var` but not for `let`.
- Assuming scope follows the call stack. It follows source structure. A function called from anywhere still sees the variables it was written next to.
- Shadowing a variable accidentally in a nested block and wondering why the outer one never updates.
- Assigning to an undeclared variable in non-strict mode, which silently creates a global. Always use strict mode or modules, where this throws.

## Interview angle

"Explain execution context" expects: a context is created per script and per function call, built in a creation phase (bindings registered, `this` set, outer reference stored) followed by an execution phase, and unresolved identifiers are looked up along the scope chain formed by those outer references. Tying hoisting and TDZ back to the creation phase, rather than reciting them as separate rules, is what distinguishes a strong answer.
