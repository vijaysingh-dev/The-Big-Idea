# Lightning Data Service and Record Forms

## The best Apex controller is no Apex controller

**Lightning Data Service** reads and writes records without Apex. It enforces field-level security and sharing automatically, shares a cache across every component on the page, and keeps them in sync when a record changes.

What that removes: an Apex class, its test class, the `WITH USER_MODE` you might forget, the `stripInaccessible` you might not know about, and the cache invalidation you would have to build.

For single-record operations, **LDS should be the default and Apex the exception.**

## Reading a record

```javascript
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue, getFieldDisplayValue } from 'lightning/uiRecordApi';
import CLAIM_NUMBER from '@salesforce/schema/Warranty_Claim__c.Claim_Number__c';
import CLAIM_AMOUNT from '@salesforce/schema/Warranty_Claim__c.Claim_Amount__c';
import CLAIM_STATUS from '@salesforce/schema/Warranty_Claim__c.Status__c';
import ASSET_SERIAL from '@salesforce/schema/Warranty_Claim__c.Asset__r.SerialNumber';

const FIELDS = [CLAIM_NUMBER, CLAIM_AMOUNT, CLAIM_STATUS, ASSET_SERIAL];

export default class ClaimSummary extends LightningElement {
    @api recordId;

    @wire(getRecord, { recordId: '$recordId', fields: FIELDS })
    claim;

    get claimNumber() {
        return getFieldValue(this.claim.data, CLAIM_NUMBER);
    }

    get formattedAmount() {
        // displayValue is locale and currency formatted by the platform
        return getFieldDisplayValue(this.claim.data, CLAIM_AMOUNT);
    }

    get serialNumber() {
        return getFieldValue(this.claim.data, ASSET_SERIAL);
    }
}
```

**Schema imports are compile-time checked.** A field that does not exist fails at deployment, and — usefully — a field referenced this way **cannot be deleted** without first removing the reference. That dependency tracking is a real advantage over string field names.

**Relationship traversal works**, up to a limited depth, using the `Asset__r.SerialNumber` form.

**`getFieldValue` returns the raw value; `getFieldDisplayValue` returns the formatted one.** For currency, dates, and picklists, the display value is what should be rendered — it respects the user's locale with no client-side formatting.

## fields versus optionalFields

```javascript
@wire(getRecord, { recordId: '$recordId', fields: REQUIRED_FIELDS, optionalFields: EXTRA_FIELDS })
claim;
```

**`fields`** — if the user cannot access one, the whole wire returns an error.

**`optionalFields`** — inaccessible fields are simply absent, and the rest still returns.

Use `optionalFields` for anything not every user can see. A component using `fields` for a restricted field breaks entirely for users without access, which is rarely the intended behaviour.

## Creating and updating

```javascript
import { createRecord, updateRecord, deleteRecord } from 'lightning/uiRecordApi';
import CLAIM_OBJECT from '@salesforce/schema/Warranty_Claim__c';
import ASSET_FIELD from '@salesforce/schema/Warranty_Claim__c.Asset__c';
import AMOUNT_FIELD from '@salesforce/schema/Warranty_Claim__c.Claim_Amount__c';

async createClaim() {
    const fields = {};
    fields[ASSET_FIELD.fieldApiName] = this.assetId;
    fields[AMOUNT_FIELD.fieldApiName] = this.amount;

    try {
        const record = await createRecord({
            apiName: CLAIM_OBJECT.objectApiName,
            fields
        });
        this.claimId = record.id;
    } catch (error) {
        this.handleError(error);
    }
}

async updateClaim() {
    const fields = {};
    fields.Id = this.recordId;
    fields[AMOUNT_FIELD.fieldApiName] = this.newAmount;

    // updateRecord refreshes the LDS cache automatically, so no notify call is needed
    await updateRecord({ fields });
}
```

**`updateRecord` requires `Id` in the fields object**, not as a separate parameter.

**The cache updates automatically.** Every component on the page showing that record — including the standard highlights panel and detail section — reflects the change with no `notifyRecordUpdateAvailable` call. This is a substantial advantage over an Apex update. See [[14.11 - refreshApex and Cache Invalidation]].

## The record forms

Three base components, in increasing order of control.

**`lightning-record-form`** — the simplest, and the least controllable:

```html
<lightning-record-form
    record-id={recordId}
    object-api-name="Warranty_Claim__c"
    layout-type="Compact"
    columns="2"
    mode="view"
    onsuccess={handleSuccess}>
</lightning-record-form>
```

`layout-type` of `Compact` or `Full` uses the org's page layout, which means an administrator adding a field to the layout changes the component with no deployment. That is either exactly what you want or a loss of control.

**`lightning-record-view-form`** — read-only, with control over which fields and where:

```html
<lightning-record-view-form record-id={recordId} object-api-name="Warranty_Claim__c">
    <div class="slds-grid slds-gutters">
        <div class="slds-col slds-size_1-of-2">
            <lightning-output-field field-name="Claim_Number__c"></lightning-output-field>
            <lightning-output-field field-name="Status__c"></lightning-output-field>
        </div>
        <div class="slds-col slds-size_1-of-2">
            <lightning-output-field field-name="Claim_Amount__c"></lightning-output-field>
            <lightning-output-field field-name="Claim_Date__c"></lightning-output-field>
        </div>
    </div>
</lightning-record-view-form>
```

**`lightning-record-edit-form`** — editable, with full layout control:

```html
<lightning-record-edit-form
    record-id={recordId}
    object-api-name="Warranty_Claim__c"
    onsubmit={handleSubmit}
    onsuccess={handleSuccess}
    onerror={handleError}>

    <lightning-messages></lightning-messages>

    <lightning-input-field field-name="Claim_Amount__c" required></lightning-input-field>
    <lightning-input-field field-name="Status__c"></lightning-input-field>
    <lightning-input-field field-name="Description__c"></lightning-input-field>

    <div class="slds-m-top_medium">
        <lightning-button variant="brand" type="submit" label="Save"></lightning-button>
        <lightning-button label="Cancel" onclick={handleCancel}></lightning-button>
    </div>
</lightning-record-edit-form>
```

`<lightning-messages>` renders validation and DML errors in the standard place. Omitting it means errors are returned to `onerror` and nothing appears on screen — a form that silently refuses to save.

## Intercepting the submit

```javascript
handleSubmit(event) {
    // preventing the default lets you modify or validate before the save
    event.preventDefault();

    const fields = event.detail.fields;
    fields.Approved_By__c = USER_ID;
    fields.Approved_Date__c = new Date().toISOString();

    if (fields.Claim_Amount__c > this.coverageLimit) {
        this.showError('The claim exceeds the coverage limit for this machine.');
        return;
    }

    this.template.querySelector('lightning-record-edit-form').submit(fields);
}
```

This is the pattern for adding derived values or performing client-side validation before the record saves — without giving up LDS's security enforcement and cache behaviour.

## What LDS gives you free

**Field-level security.** A field the user cannot see does not render, and does not appear in the data. No Apex, no `stripInaccessible`. See [[03.6 - Field Level Security]].

**Sharing enforcement.** A record the user cannot access returns an error rather than data.

**A shared cache.** Two components showing the same record fetch it once.

**Automatic synchronization.** An update through LDS updates every component showing that record.

**Validation rule messages** surfaced in the standard format, in the user's language.

**Locale formatting** for currency, dates, and numbers.

**Accessibility** on every input.

Rebuilding any of this in an Apex controller is work, and getting the security parts wrong is a real exposure.

## The other wire adapters

```javascript
import { getRecords } from 'lightning/uiRecordApi';          // several records at once
import { getObjectInfo } from 'lightning/uiObjectInfoApi';    // metadata, record types
import { getPicklistValues } from 'lightning/uiObjectInfoApi';
import { getListUi } from 'lightning/uiListApi';              // list view data
import { getRelatedListRecords } from 'lightning/uiRelatedListApi';
```

**`getPicklistValues`** is worth knowing — it populates a picklist with the org's actual values, respecting record type, with no Apex:

```javascript
@wire(getObjectInfo, { objectApiName: CLAIM_OBJECT })
objectInfo;

@wire(getPicklistValues, {
    recordTypeId: '$objectInfo.data.defaultRecordTypeId',
    fieldApiName: STATUS_FIELD
})
statusValues;

get statusOptions() {
    return this.statusValues.data?.values ?? [];
}
```

The chained wire — `getObjectInfo` supplying the record type Id to `getPicklistValues` — is the standard shape, and it demonstrates that a wire parameter can reference another wire's result.

## Where LDS does not fit

Being honest about the boundaries.

**Multiple records with complex filtering.** LDS reads by Id. Anything needing a WHERE clause is Apex or GraphQL.

**Aggregations.** Sums, counts, grouping.

**Bulk operations.** Updating fifty records means fifty calls.

**Cross-object logic.** Reading a claim, checking its coverage, and computing eligibility is one Apex method or three LDS wires plus client-side logic.

**Objects LDS does not support.** External objects, big objects, and some standard objects are unsupported. Discovering this partway through a build is a real risk, so checking early is worth the minutes.

**Anything requiring a transaction.** LDS operations are individual; there is no atomicity across several.

## The decision

| Requirement | Use |
| --- | --- |
| Display one record's fields | `getRecord` or a record view form |
| Edit one record | `lightning-record-edit-form` |
| Create one record | `createRecord` or an edit form with no record Id |
| A filtered list | Apex, or the GraphQL wire adapter |
| Aggregations | Apex |
| Several records by Id | `getRecords` |
| Picklist values | `getPicklistValues` |
| Related list | `getRelatedListRecords` |
| Business logic on save | Apex, or an edit form with an intercepted submit |
| Bulk update | Apex |

The GraphQL wire adapter covers a useful middle ground — filtered, related queries with field-level security enforced and no Apex. See [[13.7 - GraphQL API]].

## A worked example

A panel using LDS for the record and Apex only for what LDS cannot do:

```javascript
export default class ClaimPanel extends LightningElement {
    @api recordId;

    // LDS for the record itself: FLS enforced, cached, auto-synced
    @wire(getRecord, { recordId: '$recordId', fields: FIELDS, optionalFields: OPTIONAL_FIELDS })
    claim;

    // Apex only for the aggregation LDS cannot do
    @wire(getCoverageSummary, { assetId: '$assetId' })
    coverageResult;

    get assetId() {
        return getFieldValue(this.claim.data, ASSET_FIELD);
    }

    async handleApprove() {
        const fields = { Id: this.recordId };
        fields[STATUS_FIELD.fieldApiName] = 'Approved';

        // updateRecord keeps every component on the page in sync automatically
        await updateRecord({ fields });
        await refreshApex(this.coverageResult);
    }
}
```

The record update goes through LDS and needs no cache notification. The Apex aggregation does need `refreshApex`. Knowing which is which is the practical skill.

## Practical guidance

**Default to LDS for single-record read and write.**

**Use schema imports**, not string field names — compile-time checking and deletion protection.

**Use `optionalFields`** for anything not every user can see.

**Use `getFieldDisplayValue`** for currency and dates.

**Include `<lightning-messages>`** in every edit form.

**Intercept `onsubmit`** to add derived values or validate.

**Use `getPicklistValues`** rather than an Apex describe call.

**Reach for Apex only for filtering, aggregation, bulk, and cross-object logic.**

**Confirm LDS supports the object** before designing around it.
