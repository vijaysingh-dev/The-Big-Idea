# Async Processing at Scale

## The constraints that bind

At volume, the limits that matter are not the per-transaction ones — those are solved by chunking. They are the org-wide ones.

```
5 batch jobs queued or active, org-wide
100 scheduled Apex jobs
250,000 async executions per day, or 200 × user licences
50 async calls enqueued per synchronous transaction
1 Queueable enqueued from within a Queueable
```

**The five-concurrent-batch limit is the throughput ceiling**, and it is the one most orgs hit first.

## The five-job ceiling

```
Six nightly jobs, all scheduled for 02:00
    → five start
        → the sixth sits in the flex queue
            → if the first five are slow, it runs at 06:00
                → during the business day
```

**Jobs beyond five sit in the flex queue in Holding status**, up to 100. They are not lost; they are delayed.

```sql
SELECT Id, ApexClass.Name, Status, JobItemsProcessed, TotalJobItems, CreatedDate
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND Status IN ('Holding', 'Queued', 'Preparing', 'Processing')
ORDER BY CreatedDate
```

**The mitigations:**

**Stagger the schedules.** 02:00, 02:30, 03:00, rather than all at once.

**Chain rather than schedule independently**, where the jobs are related:

```java
public void finish(Database.BatchableContext ctx) {
    logResults(ctx);

    // chaining runs them in sequence, using one slot rather than three
    if (!Test.isRunningTest()) {
        Database.executeBatch(new ClaimRollupBatch(), 200);
    }
}
```

**Reorder the flex queue** in Setup when a critical job is behind slow ones.

**Consolidate.** Three jobs each iterating the same object can frequently be one job doing three things per chunk.

## Scope size

The primary tuning lever, and it is per job rather than global.

```java
Database.executeBatch(new ClaimEnrichmentBatch(), 50);      // heavy per-record work
Database.executeBatch(new SimpleFieldUpdateBatch(), 2000);  // trivial per-record work
```

**Smaller scope:** more transactions, more overhead, less work per transaction, shorter locks, more resilient to limits.

**Larger scope:** fewer transactions, less overhead, more work per transaction, longer locks.

**A job failing intermittently on some chunks is usually a scope problem**, and halving it is the first thing to try.

**Each chunk counts as an async execution** against the daily allocation, so a scope of 1 on ten million records is ten million executions — far beyond the daily limit. That is the constraint on going small.

## The daily allocation

```
250,000 async executions per day, or 200 × user licences, whichever is higher
```

**Org-wide, and shared across every async mechanism** — batch chunks, Queueables, future methods, and scheduled jobs.

```java
System.OrgLimit async = OrgLimits.getMap().get('DailyAsyncApexExecutions');
System.debug(async.getValue() + ' of ' + async.getLimit());
```

**Exhausting it stops every async job in the org**, and the symptom is jobs that simply do not run — with no error.

**The arithmetic that matters:**

```
10,000,000 records ÷ scope 200 = 50,000 executions
10,000,000 records ÷ scope 50  = 200,000 executions
```

**Scope size determines allocation consumption**, and a large job with a small scope can consume the whole day's budget.

**Checking before starting a large job:**

```java
public static Boolean hasCapacityFor(Integer recordCount, Integer scopeSize) {
    System.OrgLimit async = OrgLimits.getMap().get('DailyAsyncApexExecutions');
    Integer required = (recordCount / scopeSize) + 1;

    // headroom, so other jobs in the org are not starved
    return (async.getLimit() - async.getValue()) > (required + 5000);
}
```

## Batch chaining for very large volumes

A single batch job handles 50 million records. Beyond that, or where the work must be staged, chaining.

```java
public with sharing class ClaimProcessingBatch
    implements Database.Batchable<SObject>, Database.Stateful {

    private final Date processFrom;
    private final Date processTo;
    private Integer processed = 0;

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        // bounding by date keeps each job's locator manageable and its progress trackable
        return Database.getQueryLocator([
            SELECT Id, Status__c, Asset__c
            FROM Warranty_Claim__c
            WHERE Claim_Date__c >= :processFrom AND Claim_Date__c < :processTo
            ORDER BY Asset__c
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        ClaimProcessingService.process(scope);
        processed += scope.size();
    }

    public void finish(Database.BatchableContext ctx) {
        logRun(ctx, processed);

        Date nextTo = processFrom;
        Date nextFrom = nextTo.addMonths(-1);

        // walking backwards a month at a time, one job at a time
        if (nextFrom >= EARLIEST_DATE && !Test.isRunningTest()) {
            Database.executeBatch(new ClaimProcessingBatch(nextFrom, nextTo), 200);
        }
    }
}
```

**Bounding each job by date** gives three things: a manageable query locator, visible progress, and a restart point if the chain breaks.

**A chain that breaks mid-way** is recoverable because the boundary is known — restart from the month that failed rather than from the beginning.

## Queueable chaining

```java
public with sharing class ClaimSyncQueueable implements Queueable, Database.AllowsCallouts {

    private final List<Id> remaining;
    private static final Integer CHUNK = 150;

    public void execute(QueueableContext context) {
        List<Id> batch = new List<Id>();
        List<Id> rest = new List<Id>();

        for (Integer i = 0; i < remaining.size(); i++) {
            if (i < CHUNK) {
                batch.add(remaining[i]);
            } else {
                rest.add(remaining[i]);
            }
        }

        ClaimSyncService.sync(new Set<Id>(batch));

        // the termination condition is not optional; a chain without one runs
        // until the daily allocation is exhausted, affecting every job in the org
        if (!rest.isEmpty() && !Test.isRunningTest()) {
            System.enqueueJob(new ClaimSyncQueueable(rest));
        }
    }
}
```

**One Queueable at a time** — the chain is sequential by construction.

**Above a few thousand records, Batch Apex is better.** It chunks automatically, has proper monitoring, and does not depend on your chunking logic being correct. See [[12.10 - Choosing the Right Async Tool]].

## Contention in parallel batches

Batch chunks run in parallel, which is where lock contention appears.

```java
public Database.QueryLocator start(Database.BatchableContext ctx) {
    return Database.getQueryLocator([
        SELECT Id, Asset__c FROM Warranty_Claim__c
        WHERE Status__c = 'Under Review'
        ORDER BY Asset__c
    ]);
}
```

**`ORDER BY` on the parent** groups children of the same parent into the same chunk, so one chunk holds the lock rather than four competing for it.

**This is the same principle as sorting a data file**, applied to a query locator, and it resolves most batch lock contention. See [[10.8 - Record Locking and Deadlocks]].

**Handling the lock failures that remain:**

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    List<Database.SaveResult> results = Database.update(scope, false);

    Set<Id> retryable = new Set<Id>();
    for (Integer i = 0; i < results.size(); i++) {
        if (results[i].isSuccess()) {
            continue;
        }
        for (Database.Error err : results[i].getErrors()) {
            if (err.getStatusCode() == StatusCode.UNABLE_TO_LOCK_ROW) {
                retryable.add(scope[i].Id);
            } else {
                logPermanentFailure(scope[i].Id, err);
            }
        }
    }

    if (!retryable.isEmpty()) {
        System.enqueueJob(new ClaimRetryQueueable(retryable));
    }
}
```

**Retrying only lock failures** avoids reprocessing records that failed validation — which would fail identically every time.

## Stateful accumulation

`Database.Stateful` preserves instance variables across chunks, and at volume it is a heap risk.

```java
public with sharing class ClaimReconciliationBatch
    implements Database.Batchable<SObject>, Database.Stateful {

    private Integer processed = 0;
    private Integer failed = 0;
    private final List<String> errors = new List<String>();

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                processed++;
            } else {
                failed++;
                // capped, because this list persists across every chunk
                if (errors.size() < 100) {
                    errors.add(scope[i].Id + ': ' + results[i].getErrors()[0].getMessage());
                }
            }
        }
    }
}
```

**An uncapped collection accumulated over 50,000 chunks exhausts the heap**, and the job fails near the end after hours of work.

**Counters are safe; collections need a cap.**

## Platform events at scale

**Delivery allocation counts per subscriber**, which is the constraint that surprises orgs adding consumers over time.

```
1 event published
  → 4 external subscribers
      = 4 deliveries
```

**Filtering at the source** with a custom channel is far cheaper than filtering in the subscriber, because unfiltered events still consume the allocation:

```
Channel:  High_Value_Claims__chn
Members:  Claim_Approved__e
Filter:   Approved_Amount__c > 100000
```

**Subscriber batch size** matters — a trigger processing 2,000 events in one transaction must be bulkified, and reducing the batch size is the mitigation when per-event work is heavy.

**Watch subscriber lag:**

```sql
SELECT Topic, Type, Position, Tip, Status FROM EventBusSubscriber
```

`Position` well behind `Tip` means events are queueing, and with 72-hour retention a subscriber falling further behind loses events permanently. See [[16.5 - Platform Event and Streaming Limits]].

## Throughput planning

The arithmetic worth doing before building.

```
10,000,000 records to process
Scope size 200                      → 50,000 chunks
Each chunk ~3 seconds               → 150,000 seconds sequential
5 concurrent jobs                   → ~8.3 hours wall clock
Daily allocation consumed           → 50,000 of 250,000
```

**Then the questions:**

**Does it fit in the window?** 8.3 hours does not fit a four-hour overnight window.

**Does it starve other jobs?** Five concurrent slots means nothing else runs.

**Is the daily allocation sufficient** for this plus everything else?

**The levers:** larger scope where the per-record work permits, fewer records through archiving, or splitting across nights.

## Monitoring

```sql
SELECT ApexClass.Name, JobType, Status, ExtendedStatus, NumberOfErrors,
       JobItemsProcessed, TotalJobItems, CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE CreatedDate = LAST_N_DAYS:7 AND Status IN ('Failed', 'Aborted')
ORDER BY CreatedDate DESC
```

**Duration trended** is the earliest warning:

```sql
SELECT ApexClass.Name, CreatedDate, CompletedDate, JobItemsProcessed
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND CreatedDate = LAST_N_DAYS:90
ORDER BY CreatedDate DESC
```

**A job whose duration has doubled over six months** is telling you the data grew past a threshold, and it will overrun its window before long.

**Alert on absence**, not only on failure:

```sql
SELECT Job_Name__c, MAX(Started_At__c) lastRun
FROM Batch_Run_Log__c GROUP BY Job_Name__c
```

**A job that stopped running produces no failure record.** Only a last-run timestamp per job detects it, and it is the failure mode most often missed. See [[20.5 - Custom Logging Frameworks]].

## Practical guidance

**Stagger scheduled jobs**, given the five-concurrent limit.

**Chain related jobs** rather than scheduling them independently.

**Tune scope size per job** — smaller for heavy work, larger for trivial.

**Watch the daily async allocation.** Scope size determines consumption.

**Order batch query locators by parent** to group contention into one chunk.

**Retry lock failures only**, and log permanent ones.

**Cap stateful collections.**

**Bound each job in a chain by date**, so a break is recoverable.

**Filter platform events at the source**, since delivery counts per subscriber.

**Trend job duration**, and alert on jobs that stopped running.
