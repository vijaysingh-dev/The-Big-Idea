# Styling, SLDS and Design Tokens

## Scoped by default

Each component's styles are scoped to its shadow root. A `.header` class in one component does not affect another, and a parent's stylesheet does not reach into a child.

```css
/* claimSummary.css — applies only inside this component */
.claim-header {
    font-weight: 700;
}
```

That encapsulation is enforced, not conventional, and it removes the whole category of CSS collision that plagues large applications.

The cost: **you cannot style a child component's internals from the parent.** Restyling `lightning-datatable`'s cells from the outside is not possible in the intended way, which is a genuine constraint and the source of most styling frustration in LWC.

## Use SLDS classes

The **Salesforce Lightning Design System** is available globally, and its utility classes cover most layout and spacing needs.

```html
<div class="slds-p-around_medium slds-m-bottom_small">
    <p class="slds-text-heading_small slds-text-color_default">Claim Summary</p>
    <p class="slds-text-body_regular slds-text-color_weak">No coverage found</p>
</div>

<div class="slds-grid slds-gutters slds-wrap">
    <div class="slds-col slds-size_1-of-1 slds-medium-size_1-of-2">Left</div>
    <div class="slds-col slds-size_1-of-1 slds-medium-size_1-of-2">Right</div>
</div>
```

The patterns worth memorizing:

```
slds-p-around_medium     padding all sides
slds-p-horizontal_small  padding left and right
slds-m-top_large         margin top
slds-grid  slds-col      flexbox layout
slds-size_1-of-3         column width
slds-medium-size_1-of-2  responsive width from medium up
slds-text-heading_small
slds-text-color_error / _weak / _success
slds-theme_error / _success / _warning / _shade
slds-truncate            single-line ellipsis
slds-hide / slds-show
slds-assistive-text      visible only to screen readers
```

Sizes are `xxx-small`, `xx-small`, `x-small`, `small`, `medium`, `large`, `x-large`, `xx-large`.

**Using SLDS classes means the component follows the org's theme automatically**, including branded Experience Cloud sites and dark mode where enabled. Hand-written spacing does not.

## Design tokens

For custom CSS, tokens as CSS custom properties keep values consistent with the theme:

```css
.claim-row {
    padding: var(--lwc-spacingSmall, 0.75rem);
    border-bottom: 1px solid var(--lwc-colorBorder, #dddbda);
    color: var(--lwc-colorTextDefault, #080707);
    font-size: var(--lwc-fontSize3, 0.875rem);
}

.claim-row.is-overdue {
    background-color: var(--lwc-colorBackgroundRowNew, #fef8f8);
    border-left: 3px solid var(--lwc-colorBorderError, #c23934);
}
```

**Always supply a fallback**, the second argument to `var()`. A token that is unavailable in a given context — an older Experience Cloud template, a context where the theme is not applied — leaves the property unset without one.

The token families worth knowing: `--lwc-spacing*`, `--lwc-color*`, `--lwc-fontSize*`, `--lwc-fontWeight*`, `--lwc-borderRadius*`, `--lwc-shadow*`, `--lwc-lineHeight*`.

## :host

Styles the component's own element.

```css
:host {
    display: block;
}

:host(.compact) {
    padding: var(--lwc-spacingXSmall, 0.5rem);
}
```

**`:host { display: block; }` is worth adding to most components.** Custom elements default to `display: inline`, which makes width, height, and margin behave unexpectedly and is a common source of layout confusion.

## Styling child components

The hard part.

Base components encapsulate their internals, so a parent cannot restyle them directly. Three approaches, in order of preference.

**1. Use the component's documented attributes.**

```html
<lightning-button variant="destructive" label="Reject"></lightning-button>
<lightning-icon variant="warning" size="small"></lightning-icon>
<lightning-badge class="slds-theme_error" label="Overdue"></lightning-badge>
```

Many base components accept a `class` and apply it to their outer element, which is enough for spacing and colour.

**2. CSS custom properties the component exposes.**

Some base components document styling hooks:

```css
lightning-button {
    --slds-c-button-brand-color-background: var(--lwc-colorBackgroundButtonBrand);
    --slds-c-button-text-color: white;
}
```

The set of supported hooks is per component and documented in the component reference. This is the sanctioned mechanism and it is expanding release by release.

**3. `::part()`**, where a component exposes parts.

Increasingly available on base components, and the standards-based way to reach specific internal elements.

**What not to do:** `::shadow`, `/deep/`, or JavaScript that reaches into a child's shadow root. These either do not work or break without warning when Salesforce changes the component's internals.

If a base component genuinely cannot be styled to requirement, building a custom component is more honest than fighting the encapsulation — and it will still be working after the next release.

## Static stylesheets

A shared stylesheet can be imported into several components:

```css
/* sharedStyles/sharedStyles.css */
.claim-card {
    border-radius: var(--lwc-borderRadiusMedium, 0.25rem);
    box-shadow: var(--lwc-shadowDrag);
}
```

```javascript
import { LightningElement } from 'lwc';
import sharedStyles from '@salesforce/resourceUrl/sharedStyles';
import { loadStyle } from 'lightning/platformResourceLoader';

export default class ClaimCard extends LightningElement {
    stylesLoaded = false;

    renderedCallback() {
        if (this.stylesLoaded) {
            return;
        }
        this.stylesLoaded = true;
        loadStyle(this, sharedStyles + '/shared.css');
    }
}
```

The guard is essential — `renderedCallback` fires on every rerender, and without it the stylesheet loads repeatedly.

**`loadStyle` injects into the component's shadow root**, so it stays scoped. It does not leak to siblings.

The newer approach is a **CSS module**, imported directly:

```javascript
import { LightningElement } from 'lwc';
import sharedCss from './shared.css';

export default class ClaimCard extends LightningElement {
    static stylesheets = [sharedCss];
}
```

Cleaner where available, since it needs no static resource and no lifecycle hook.

## Light DOM

A component can opt out of shadow DOM entirely:

```javascript
export default class ClaimTable extends LightningElement {
    static renderMode = 'light';
}
```

```html
<template lwc:render-mode="light">
    <div class="claim-table">...</div>
</template>
```

**Styles then leak in and out**, and third-party libraries expecting global DOM access work.

The legitimate uses: integrating a charting or grid library that traverses the DOM, and Experience Cloud components that must inherit site branding fully.

The cost is the encapsulation that makes components safe to compose. **Use light DOM only when a specific requirement forces it**, and document why — a future developer will wonder.

Note that in light DOM, `this.template.querySelector` becomes `this.querySelector`.

## Responsive layout

```html
<lightning-layout multiple-rows>
    <lightning-layout-item size="12" small-device-size="6" medium-device-size="4"
                           padding="around-small">
        <c-claim-card claim={claim}></c-claim-card>
    </lightning-layout-item>
</lightning-layout>
```

Sizes are out of twelve, and the device-size attributes apply from that breakpoint upward.

For CSS-based responsiveness, **container queries are not reliably available**, so media queries against the viewport are the practical option — which is imperfect in a console where a component may sit in a narrow region of a wide viewport.

Where layout must respond to the component's own width, measuring in `renderedCallback` is the fallback, with the usual caution about triggering rerenders:

```javascript
renderedCallback() {
    const width = this.template.querySelector('.container')?.offsetWidth;
    const isNarrow = width < 480;

    // comparing before assigning prevents an infinite rerender loop
    if (isNarrow !== this.isNarrow) {
        this.isNarrow = isNarrow;
    }
}
```

## Experience Cloud

Components on an Experience Cloud site inherit the site's branding, which may differ substantially from the internal theme.

Two consequences:

**Hardcoded colours look wrong.** A component styled with the internal palette on a branded partner site is jarring. Design tokens adapt; hex values do not.

**SLDS may not be fully available** depending on the template. Testing in the actual site rather than the builder preview is worth the extra step.

## Accessibility

Styling and accessibility overlap more than they appear to.

```html
<button class="slds-button slds-button_icon" title="Approve claim">
    <lightning-icon icon-name="utility:check" size="x-small"></lightning-icon>
    <span class="slds-assistive-text">Approve claim</span>
</button>
```

**An icon-only control needs assistive text.** Without it, a screen reader announces nothing useful.

**Do not convey meaning by colour alone.** A red row means nothing to a colour-blind user; a red row with an icon and a label does.

**Maintain contrast.** Custom colours that look subtle can fall below the accessibility threshold.

Base components handle most of this. Custom markup does not, which is another argument for using them.

## Practical guidance

**Use SLDS utility classes** rather than writing spacing and layout CSS.

**Use design tokens with fallbacks** for custom values.

**Add `:host { display: block; }`** to most components.

**Style child components through their documented attributes and styling hooks**, never by reaching into shadow DOM.

**Guard `loadStyle` in `renderedCallback`**, or prefer a CSS module.

**Use light DOM only when forced**, and document the reason.

**Test on Experience Cloud in the site**, not the builder.

**Add assistive text to icon-only controls**, and never convey meaning by colour alone.
