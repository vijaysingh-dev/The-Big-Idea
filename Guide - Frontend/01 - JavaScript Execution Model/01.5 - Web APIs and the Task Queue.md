# Web APIs and the Task Queue

The event loop only moves work around. The actual asynchronous work is done by **host APIs** — capabilities the browser or Node exposes to JavaScript, implemented in C++ and frequently running on threads your JS code never sees.

## What counts as a Web API

None of these are JavaScript. Remove the browser and they vanish.

| Category | Examples |
| --- | --- |
| Timers | `setTimeout`, `setInterval`, `requestAnimationFrame`, `requestIdleCallback` |
| Network | `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` |
| DOM | `document`, `addEventListener`, `MutationObserver` |
| Storage | `localStorage`, `IndexedDB`, Cache API |
| Media and devices | `getUserMedia`, geolocation, notifications |
| Concurrency | `Worker`, `postMessage`, `BroadcastChannel` |

The pattern is always the same: JavaScript calls in, the browser starts work elsewhere, and when it completes the browser queues a callback for the event loop to run.

```js
fetch("/api/user")   // returns immediately, browser does DNS + TCP + TLS + HTTP off-thread
  .then(res => res.json())
  .then(data => render(data));

console.log("this logs first");
```

The network request occupies zero main-thread time while in flight. This is why an app can have fifty requests open and still feel responsive — none of them are blocking the single JS thread.

## The task queue

Completed host work is placed in a **task queue** as a *task* (the spec's term; "macrotask" is the common informal name). The event loop takes **one** task per iteration, runs it to completion, then drains microtasks, then possibly renders.

Sources of tasks:

- Timer callbacks (`setTimeout`, `setInterval`)
- DOM event callbacks (click, scroll, input)
- Network completion callbacks for XHR
- `postMessage` and `MessageChannel` messages
- Parsing and script-loading steps

Crucially, the spec allows **multiple task queues** with different priorities. Browsers keep user-interaction tasks in a higher-priority queue than timers, which is why a click generally beats a pending `setTimeout` even if the timer was queued first. Do not rely on precise ordering between different task sources.

## Timers in detail

```js
const id = setInterval(() => poll(), 1000);
clearInterval(id);
```

`setInterval` schedules the *next* run without waiting for the previous callback to finish. If `poll()` takes 1500 ms, callbacks stack up and the queue fills with work that can never keep pace. The safer pattern is a self-rescheduling timeout:

```js
function pollLoop() {
  poll().finally(() => setTimeout(pollLoop, 1000));
}
```

This guarantees a full gap between runs regardless of how long each one takes, and it degrades gracefully when the network is slow.

Other timer behaviors worth knowing:

- After five levels of nesting, browsers clamp the minimum delay to 4 ms.
- Background tabs throttle timers heavily — often to once per minute after a few minutes hidden. Anything time-critical should recompute from `Date.now()` on wake rather than counting ticks.
- Timers are not precise. For animation use `requestAnimationFrame` ([[01.7 - The Rendering Cycle]]); for audio use the Web Audio clock.

## Events are tasks too

```js
button.addEventListener("click", handler);
```

The browser listens for input on its own threads. On a click it queues a task that dispatches the event through the DOM tree ([[12.3 - The Event Model]]) and runs your handler. Your handler therefore occupies the main thread, and a slow handler directly delays the next frame.

Scroll, `resize`, `mousemove` and `pointermove` fire far more often than you can usefully respond to. Throttling them is standard practice ([[29.1 - Debounce and Throttle]]), as is marking listeners passive so the browser need not wait for you before scrolling:

```js
window.addEventListener("scroll", onScroll, { passive: true });
```

## Where fetch actually resolves

A subtlety worth internalizing: `fetch` resolves its promise via the **microtask** queue, not the task queue, even though the underlying network completion arrives as a task. The browser queues a task when the response headers arrive; that task resolves the promise, which schedules the `.then` reaction as a microtask. So promise callbacks always run before the next timer, regardless of how the underlying work was completed.

## How senior engineers actually use this

**They offload rather than optimize.** If a task is expensive and does not touch the DOM — parsing a large CSV, image processing, diffing large objects — it goes to a Worker. No amount of main-thread cleverness beats not being on the main thread.

**They treat handlers as latency budgets.** A click handler that synchronously does 100 ms of work has already spent half the responsiveness budget before React even renders. The usual fix is to do the minimum synchronously (update the input value, show a spinner) and defer the rest.

**They use `MessageChannel` for zero-delay tasks.** When you need a real task boundary without the 4 ms timer clamp, a `MessageChannel` `postMessage` to yourself is the classic trick. React's scheduler used exactly this technique for years.

**They clean up every timer and listener.** Every `setInterval` and `addEventListener` is a retained reference. In React that means a cleanup function from `useEffect`; forgetting it is the most common memory leak in frontend code ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

## Common pitfalls

- Using `setInterval` for anything whose duration is variable, especially network polling.
- Assuming timer delays are honored in background tabs, then finding a session timer that never fired.
- Adding non-passive `scroll` or `touchmove` listeners, which forces the browser to wait for your handler before scrolling.
- Believing `fetch` runs on a background thread of *yours*. The request does; the callback runs on the main thread like everything else.

## Interview angle

Questions here usually take the form "where does `setTimeout` live?" or "how does `fetch` work without blocking?". The expected answer is that these are host-provided APIs, not language features; they perform work outside the JS thread and enqueue a callback on completion; the event loop runs one task per turn once the stack is clear. Mentioning timer clamping and background throttling signals real browser experience.
