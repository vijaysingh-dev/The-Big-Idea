# Architecture Decisions: Style, API Design, Data Flow, Database Selection

## The Decision Hierarchy

Architecture decisions have a natural order. Each decision constrains the next:

```
1. Architecture style      (monolith vs microservices vs event-driven)
2. Service decomposition   (what are the service boundaries?)
3. Communication style     (sync vs async, REST vs gRPC vs events)
4. API design              (what does each service expose?)
5. Data flow               (how does a request move through the system?)
6. Database selection      (which storage type per service/use case?)
```

Making step 6 before step 1 is a common mistake — database choices depend on all prior decisions.

---

## Choosing Architecture Style

Apply this decision tree based on your estimation results:

```
Team < 20 engineers AND scale < 10K RPS?
  → Monolith or Modular Monolith

Different services have vastly different scaling needs?
  → Microservices for those services

Need async fan-out (notifications, audit, triggers)?
  → Event-driven components

Processing pipelines, not request-response?
  → Stream processing (Kafka + consumers)
```

**In interviews:** Justify in one sentence. "Given the small team and moderate scale, I'll use a modular monolith initially, with the feed service extracted as a standalone service because its scaling profile is completely different."

## Service Decomposition

When to split a service:

| Trigger | Example |
|---|---|
| Independent scaling needs | Payment service needs more instances than user profile service |
| Different reliability SLAs | Core transaction vs analytics |
| Different team ownership | 3 teams, 3 services |
| Different tech requirements | ML model serving needs GPU, rest doesn't |
| Blast radius reduction | Recommendation failure shouldn't take down checkout |

**When NOT to split:**
- You're guessing at boundaries (wait until the pain is real)
- The two parts always deploy together and share data
- The split would require distributed transactions

## Communication Style Selection

### When to use synchronous (REST / gRPC)

- Caller needs the result to continue (auth check, pricing lookup)
- User is waiting for a response
- Operation is short-lived (< 1 second)
- Simple request-response semantics

**REST:** Standard HTTP, wide tooling, easy to debug. Use for external APIs and general service calls.  
**gRPC:** Binary protocol (Protocol Buffers), lower latency, strong typing, streaming support. Use for internal high-throughput service-to-service calls.

### When to use asynchronous (events / queues)

- Caller doesn't need an immediate result
- Fan-out to multiple consumers
- Operation is long-running (report generation, video transcoding)
- Consumer may be temporarily unavailable
- Audit trail or event log is needed

## API Design Thinking

### REST API Design Principles

**Resource-oriented naming:**
```
✅  GET  /users/{id}/orders        (get orders for a user)
❌  GET  /getUserOrders?user_id=42 (verb-based, not REST)

✅  POST /orders                   (create an order)
❌  POST /createOrder              (action in URL)
```

**HTTP method semantics:**
```
GET    → Read, idempotent, safe (no side effects)
POST   → Create (not idempotent)
PUT    → Full update, idempotent
PATCH  → Partial update
DELETE → Delete, idempotent
```

**Versioning strategy:**
```
URL versioning:    /v1/users, /v2/users        (visible, cache-friendly)
Header versioning: Accept: application/vnd.api+json;version=2
```

URL versioning is most common and easiest to reason about.

**Pagination for list endpoints:**
```
Cursor-based (preferred for large datasets):
  GET /posts?after_id=12345&limit=20
  Response: { data: [...], next_cursor: "67890" }

Offset-based (simple but has deep-page problems):
  GET /posts?page=5&limit=20
```

### Key API Design Questions

Before finalizing APIs, ask:
- Is this idempotent? Should it be? (critical for payments, retries)
- What's the error response contract? (don't return 200 with error in body)
- Is pagination needed? (any list that can grow unboundedly)
- What's the authentication mechanism? (bearer token, API key, mTLS)
- What are the rate limits?

## Data Flow Design

Draw the full request path before deciding where to add components.

### How to Draw Data Flow

1. Start with the client action ("user clicks Buy")
2. Follow the request through each component
3. Annotate: sync or async? cached or not? read or write?
4. Mark failure points

**Example — E-commerce checkout:**

```
User clicks "Place Order"
  │
  ▼ (sync)
API Gateway ──[auth token validation]──→ Auth Service
  │
  ▼ (sync)
Order Service
  ├──→ [sync] Payment Service.charge()
  │           └── if success: continue
  │           └── if fail: return error to user
  │
  ├──→ [sync] Inventory Service.reserve()
  │
  ├── write Order to Orders DB (PostgreSQL)
  │
  └──→ [async, event: OrderPlaced]──→ Queue
                                        ├──→ Notification Worker (send email)
                                        ├──→ Analytics Worker (update metrics)
                                        └──→ Fulfillment Worker (trigger shipping)
  │
  ▼ (sync response to user)
"Order confirmed, ID: 8472"
```

This map reveals:
- What must be sync (payment — user needs to know if it failed)
- What can be async (email notification — user doesn't need to wait for it)
- Where failures cascade (payment failure blocks everything)
- Where async decoupling helps (analytics failure won't break checkout)

## Database Selection

### The Decision Matrix

| Use Case | Recommended DB | Why |
|---|---|---|
| Relational data, transactions, ACID | PostgreSQL, MySQL | Strong consistency, joins, FK constraints |
| High write throughput, wide columns | Cassandra, HBase | LSM tree, partition tolerance, linear write scale |
| Key-value with low latency | Redis, DynamoDB | O(1) lookup, in-memory or SSD-optimized |
| Document store (flexible schema) | MongoDB, DynamoDB | Schema flexibility, nested data |
| Full-text search | Elasticsearch, OpenSearch | Inverted index, relevance ranking |
| Time-series (metrics, logs) | InfluxDB, TimescaleDB, ClickHouse | Columnar storage, time-based compression |
| Graph relationships | Neo4j, Amazon Neptune | Efficient graph traversals |
| Object/blob storage | S3, GCS, Azure Blob | Cheap, durable, unlimited scale |
| Analytics / OLAP | BigQuery, Redshift, ClickHouse | Columnar, scan-optimized |

### The Five Questions for DB Selection

1. **What's the query pattern?** Point lookup? Range scan? Full-text? Graph traversal?
2. **What's the read:write ratio?** Read-heavy → optimize for read (replicas, caching). Write-heavy → optimize for write (LSM trees, batching).
3. **What consistency level is needed?** ACID transactions → relational. Eventual OK → NoSQL.
4. **What's the scale?** Single machine handles more than people think. Don't shard prematurely.
5. **What are the access patterns?** How many different ways do you query this data? More access patterns → normalized SQL. Single access pattern → NoSQL is fine.

### Polyglot Persistence

Production systems commonly use multiple databases:

```
User Service:      PostgreSQL (relational, ACID, user profile + auth)
Session Store:     Redis (key-value, low latency, TTL support)
Product Catalog:   MongoDB (document, flexible schema, nested attributes)
Search:            Elasticsearch (full-text, faceted search)
Analytics:         ClickHouse (columnar, aggregation queries)
Media:             S3 (object storage, infinite scale)
```

Each database is optimized for its specific access pattern.
