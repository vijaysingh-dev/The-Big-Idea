# npm and package.json

## The manifest

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "private": true,
  "engines": { "node": ">=20" },
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "test": "vitest",
    "lint": "eslint ."
  },
  "dependencies": { "react": "^19.0.0" },
  "devDependencies": { "vite": "^6.0.0" }
}
```

Three fields worth setting deliberately:

**`"type": "module"`** makes `.js` files ES modules. Without it they are CommonJS, and config files using `import` fail ([[08.1 - ES Modules vs CommonJS]]).

**`"private": true"`** prevents accidental publication to the registry. Every application should have it.

**`"engines"`** documents the required Node version. Combined with `.nvmrc`, it prevents the "works on my machine" class of build failure.

## dependencies vs devDependencies

The distinction is about **what ends up in the shipped artifact**, not what is needed to build.

```
dependencies      → imported by application code
devDependencies   → build tools, test runners, linters, type packages
```

For a bundled frontend application the practical impact is small — the bundler includes what is imported regardless of which section it sits in. It matters for:

- **Published packages**, where `dependencies` are installed transitively by consumers
- **Docker builds** using `npm ci --omit=dev` to produce smaller images
- **Audit noise**, since a vulnerability in a dev-only tool is not shipped

Misplacing a runtime dependency in `devDependencies` breaks a production install of a published package while working fine locally.

`peerDependencies` declares "the consumer must provide this" — a React component library lists `react` as a peer so it does not bundle a second copy ([[19.7 - Bundle Analysis and Optimization]]).

## Semver ranges

```
"^1.2.3"   → >=1.2.3 <2.0.0    minor and patch updates
"~1.2.3"   → >=1.2.3 <1.3.0    patch only
"1.2.3"    → exact
"*"        → anything (never do this)
```

`^` is the default and is right for most dependencies. The assumption behind it — that minor versions are backwards compatible — holds most of the time and fails often enough to make lockfiles essential.

For `0.x` versions, `^0.2.3` allows only `0.2.x`, because pre-1.0 packages are treated as unstable.

Pin exact versions for anything where an unexpected update would be expensive — build tools that gate CI, and packages with a history of breaking changes in minor releases.

## The lockfile

`package-lock.json` records the exact resolved version of every package in the tree, including transitive ones.

**Commit it. Always.** Without it, two developers installing the same `package.json` a week apart get different trees, and CI can build something nobody tested.

```bash
npm ci        # installs exactly the lockfile, fails if it disagrees with package.json
npm install   # resolves ranges, may update the lockfile
```

Use `npm ci` in CI and Docker — it is faster, deterministic, and refuses to silently drift ([[27.9 - CI CD and Frontend Deployment]]).

A lockfile conflict in a merge is resolved by regenerating, not by hand-editing:

```bash
git checkout --theirs package-lock.json
npm install
```

## Scripts

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "test": "vitest",
    "test:ci": "vitest run --coverage",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "prepare": "husky"
  }
}
```

`npm run <name>` puts `node_modules/.bin` on the PATH, so local binaries are callable without a path prefix.

Lifecycle scripts run automatically:

- `prepare` — after `npm install`, used to set up git hooks
- `pre<script>` / `post<script>` — `prebuild` runs before `build`

`preinstall` and `postinstall` scripts from **dependencies** also run automatically, which is a real supply-chain risk. `npm ci --ignore-scripts` disables them, at the cost of breaking packages that legitimately need a build step.

Passing arguments through:

```bash
npm run test -- --watch
```

## npm, pnpm, yarn, bun

| | Notes |
| --- | --- |
| **npm** | bundled with Node, no setup, slowest |
| **pnpm** | content-addressed store with symlinks — much faster, far less disk |
| **yarn** | Berry adds PnP and zero-installs; classic yarn is legacy |
| **bun** | fastest installs, also a runtime and test runner; younger ecosystem |

**pnpm** is the strongest default for new projects. Its structural advantage is that it creates a **strict** `node_modules` — a package can only import what it declared. npm's flat hoisting lets code import a transitive dependency that happens to be present, which then breaks when that dependency's version changes upstream. pnpm makes that a hard error at install time.

It is also the standard choice for monorepos, where the disk and install-time savings compound across packages.

Switching is low-risk: delete `node_modules` and the lockfile, run `pnpm install`, commit `pnpm-lock.yaml`.

## Overrides

```json
{
  "overrides": {
    "semver": "^7.5.4",
    "react": "19.0.0"
  }
}
```

Forces a version across the whole tree, including transitive dependencies. Two main uses: patching a vulnerable transitive package before its parent updates, and **deduplicating a package that must be a singleton**.

The second is the more common frontend need. Two copies of React cause "Invalid hook call" ([[17.1 - Rules of Hooks and How They Work]]); two copies of a state library mean two independent stores. Check with:

```bash
npm ls react
```

pnpm uses `pnpm.overrides`, yarn uses `resolutions`.

## Auditing

```bash
npm audit
npm audit fix
npm audit --omit=dev          # only what ships
npm outdated
```

`npm audit` reports every vulnerability in the tree including dev-only tooling, which produces a lot of noise. `--omit=dev` narrows it to what actually reaches users.

Not every advisory is exploitable in a frontend context — a ReDoS in a build-time markdown parser is not a production risk. Triage rather than chasing zero.

Automated dependency updates (Dependabot, Renovate) grouped weekly are more sustainable than periodic large upgrades.

## Exports and entry points

For a published package:

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  },
  "sideEffects": false
}
```

`exports` replaces `main` and defines what consumers may import — anything not listed is inaccessible, which lets you refactor internals freely.

`"sideEffects": false` tells bundlers that unused exports can be dropped, which is what enables tree shaking for consumers ([[27.6 - Tree Shaking]]). If some files do have side effects (CSS imports, polyfills), list them:

```json
"sideEffects": ["*.css", "./src/polyfills.js"]
```

Getting this wrong means consumers ship your entire package regardless of what they import.

## Workspaces

```json
{
  "workspaces": ["apps/*", "packages/*"]
}
```

Monorepo support: one install, shared `node_modules`, and internal packages linked rather than published. Combined with pnpm and a task runner like Turborepo, this is the standard shape for a frontend monorepo with shared types, schemas and UI components ([[25.7 - Typing API Responses and Zod]]).

## How senior engineers actually use this

**They commit the lockfile and use `npm ci` in CI**, without exception.

**They set `"private": true`** on applications and `"engines"` alongside an `.nvmrc`.

**They check `npm ls <pkg>` when something behaves oddly**, since duplicate copies of React or a state library cause confusing errors.

**They prefer pnpm** for new projects and monorepos, mainly for the strict `node_modules`.

**They automate dependency updates weekly** rather than doing large periodic upgrades.

## Common pitfalls

- Lockfile not committed, producing non-reproducible builds.
- `npm install` in CI instead of `npm ci`.
- Runtime dependencies placed in `devDependencies` in a published package.
- Duplicate React from a linked or mismatched dependency.
- `"sideEffects"` unset in a library, disabling consumer tree shaking.
- Chasing `npm audit` to zero including dev-only advisories.
- Hand-editing a lockfile to resolve a merge conflict.
- Missing `"type": "module"` while using ESM syntax in config files.

## Interview angle

Package management rarely gets a dedicated question but appears constantly in tooling discussions. The points worth having ready: the lockfile is what makes builds reproducible and `npm ci` is what enforces it; `^` assumes minor versions are compatible, which is why the lockfile matters; `dependencies` versus `devDependencies` matters for published packages and Docker rather than for bundled apps; and duplicate copies of React are the usual explanation for "Invalid hook call".
