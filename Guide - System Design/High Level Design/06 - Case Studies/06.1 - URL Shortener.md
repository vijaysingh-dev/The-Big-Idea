# Case Study: URL Shortener

> **Revision tags:** #case-study #starter  
> **Related:** [[03.4 - Caching Systems]] | [[03.6 - Databases SQL and NoSQL]]

---

## Requirements Clarification

**Functional:**
- Create a short URL from a long URL → returns a short code (e.g., `sho.rt/abc1234`)
- Redirect: visiting the short URL redirects to the original
- Optional: custom aliases, link expiry, analytics (click count)

**Non-functional:**
- High read:write ratio — reads (redirects) >> writes (URL creation)
- Redirects must be fast (< 10ms p99 — user is waiting for page load)
- URLs must be unique — no collisions
- Availability: 99.9% for redirects (writes can be slightly degraded)

**Out of scope (for this design):** User accounts, link editing, detailed analytics dashboard, custom domains

---

## Estimation

```
DAU: 100M users
Writes: 100M × 0.1 URL/day = 10M URLs/day = 115 writes/s
Reads:  100M × 1 redirect/day = 100M/day = 1,160 reads/s → peak ~3,500 reads/s
Read:write ratio = 10:1

Storage per URL:
  short_code:  7 bytes
  long_url:    150 bytes (avg)
  created_at:  8 bytes
  expires_at:  8 bytes
  ≈ 175 bytes/URL

Storage: 10M URLs/day × 175 bytes = 1.75 GB/day
5-year total: ~3.2 TB → fits on a single large DB node with replicas

Bandwidth (redirect response):
  3,500 reads/s × 300 bytes ≈ 1 MB/s → negligible
```

**Key insight:** This is read-heavy, storage is manageable. The main challenge is redirect latency, not write throughput.

## Architecture

```
Client
  │
  ▼
[Load Balancer]
  │
  ├──→ [URL Shortening Service]  ← writes
  │          │
  │          ▼
  │     [PostgreSQL Primary]
  │
  └──→ [Redirect Service]        ← reads (high traffic)
             │
             ├── Redis cache (hot URLs)
             │      └── hit: return 301/302 immediately
             │
             └── PostgreSQL Read Replica (cache miss)
```

## Core Design Decisions

### Short Code Generation

**Option A: Hash-based**
```python
import hashlib, base64

def generate_short_code(long_url: str) -> str:
    digest = hashlib.md5(long_url.encode()).digest()
    encoded = base64.urlsafe_b64encode(digest).decode()
    return encoded[:7]   # 7 chars from base64 alphabet (a-z, A-Z, 0-9, -, _)
```

Problem: hash collisions. Two different URLs may produce the same code. Requires collision checking and retry.

**Option B: Auto-increment ID + Base62 encode (preferred)**
```python
BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode_base62(n: int) -> str:
    result = []
    while n:
        result.append(BASE62[n % 62])
        n //= 62
    return ''.join(reversed(result)) or '0'

# DB: INSERT INTO urls (...) RETURNING id
# short_code = encode_base62(id)
# 62^7 = 3.5 trillion unique codes → enough for billions of URLs
```

**Why base62 over hash:** No collision risk, predictable code space, compact representation. The auto-increment ID is the unique source of truth.

**Problem with single DB sequence:** Can become write bottleneck at very high scale.  
**Solution:** Pre-generate ranges in a separate ID generator service, or use a distributed ID generator (Twitter Snowflake pattern).

---

### Redirect: 301 vs 302

```
301 Permanent Redirect:
  + Browser caches the redirect — subsequent visits don't hit your server
  - Can't update/expire the redirect (cached in browser)
  - Analytics lose click count (browser bypasses your server)

302 Temporary Redirect:
  + Every click hits your server — accurate analytics, can expire links
  - More load on your redirect service
```

**Decision:** Use 302 for all links. If you need browser caching for performance (very high traffic links), use 301 only for permanent links where analytics aren't needed.

---

### Caching Strategy

```
Cache key:   short_code
Cache value: long_url
TTL:         24 hours (or match link expiry)

Cache-aside flow:
1. Redirect request arrives: GET /{short_code}
2. Check Redis: cache hit → return 302 immediately
3. Cache miss → query PostgreSQL read replica
4. Populate cache → return 302
```

**What to cache:** Top 20% of URLs (by traffic) will serve 80% of redirects. A 10GB Redis instance can cache ~57M URL entries (175 bytes each). More than enough for hot URLs.

**Cache invalidation:** On URL expiry or deletion, `DEL short_code` from Redis.

---

### Database Schema

```sql
CREATE TABLE urls (
    id          BIGSERIAL PRIMARY KEY,
    short_code  VARCHAR(10)  NOT NULL UNIQUE,
    long_url    TEXT         NOT NULL,
    user_id     BIGINT       REFERENCES users(id),
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    expires_at  TIMESTAMPTZ,
    click_count BIGINT       NOT NULL DEFAULT 0
);

CREATE INDEX idx_urls_short_code ON urls(short_code);
CREATE INDEX idx_urls_expires_at ON urls(expires_at) WHERE expires_at IS NOT NULL;
```

**Click count increment:** Don't update on every redirect (hot row contention).  
Better: increment in Redis (`INCR click_count:{short_code}`) and batch-flush to DB every minute.

---

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Redis cache down | All redirects hit DB | Cache-aside: fall through to DB; monitor DB load spike |
| DB primary down | Can't create new URLs | Read replicas still serve redirects; Patroni failover for writes |
| DB replica down | Cache misses hit primary | Route reads to primary temporarily; add replica |
| Hash collision (if using hash) | Wrong URL served | Check-and-retry on collision; prefer sequence-based generation |
| Link expired but cached | Redirect to expired URL | Set Redis TTL = link expiry time; check expiry at DB layer |

---

## Scaling Strategy

**Current design handles ~3,500 reads/s easily** with Redis in front of 2–3 DB replicas.

**If scale increases 100×:**
- Read replicas scaled to 10+ (or switch to DynamoDB for O(1) key-value reads)
- Redis cluster for distributed caching
- CDN in front of redirect service (cache 301 redirects at edge for high-traffic links)
- Shard URLs table by `short_code` prefix

**Write scaling:** At 11,500 writes/s, a single PostgreSQL primary can handle this. Beyond that: shard by consistent hash of short_code.

## What This Design Demonstrates

- Separating read and write services (optimized independently)
- Cache-aside pattern as the primary read optimization
- Choosing sequence + base62 over hashing (no collisions)
- 302 vs 301 tradeoff (analytics vs performance)
- Lazy click count aggregation (avoiding hot row contention)
