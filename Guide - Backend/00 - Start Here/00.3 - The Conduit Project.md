# The Conduit Project

#backend #capstone #conduit

> **In one line:** One system, built over a year, that ends up needing every topic in this vault — and then becomes your AI project.

---

## Why a Single Long Project

Drills teach you mechanisms. A long project teaches you the thing drills cannot: **what happens when decisions made in month one hurt you in month six.**

That experience is most of what "senior" actually means. You cannot get it from tutorials because tutorials end before the pain starts.

A single project also solves the portfolio problem. Ten weekend projects prove nothing. One system with real load tests, real failure handling, real architecture decision records and a real git history is worth more than any certificate.

---

## What Conduit Is

**Conduit is a document ingestion and search platform.**

A user connects a source — a folder, a Google Drive, a website, a Slack export. Conduit pulls documents from it, processes them, stores them, and makes them searchable. Users see ingestion progress live, and can annotate documents together in real time.

That is it. It sounds small. It is not.

---

## Why This Shape

Three reasons, and all three matter:

**1. It genuinely needs every topic.** Nothing is bolted on for the sake of practice:

| Need | Topic it forces you to learn |
|---|---|
| Pulling from slow external APIs | Async I/O, connection pools, timeouts, backpressure |
| Documents arriving in bulk | Task queues, retries, idempotency |
| Live progress in the browser | SSE, and why SSE not WebSocket |
| Collaborative annotation | WebSocket, presence, fanout |
| Search over millions of chunks | Postgres indexes, then full text search, then a real index |
| Multiple teams using one instance | Multi-tenancy, isolation, RLS |
| Anything at all going wrong | Circuit breakers, dead letters, replay |
| Knowing what is happening | Traces, metrics, SLOs |

**2. It is a real product shape.** Notion, Glean, Onyx, Elastic and Confluence all have this shape. Design conversations about it are real conversations, not toy ones.

**3. It becomes your AI project.** In phase 9, chunks get embeddings, search becomes hybrid retrieval, and answers stream over the SSE layer you already built. Your backend capstone turns into your AI capstone with no rewrite. This is exactly the architecture in [[00 - Index (AI)]], and its companion codebase Onyx is the same shape.

## The Domain Model

Start here. Everything grows out of these six entities.

```
Organisation ──┬── User
               │
               └── Source ──── Document ──── Chunk
                     │             │
                     │             └──── Annotation
                     │
                     └──── IngestionRun ──── DocumentTask
```

| Entity | What it is |
|---|---|
| **Organisation** | A tenant. Everything is scoped to one |
| **User** | A person, belongs to one or more orgs, has a role |
| **Source** | A connected place documents come from. Has credentials and a sync schedule |
| **Document** | One file or page, with content, metadata and a version |
| **Chunk** | A slice of a document. Meaningless now, essential in phase 9 |
| **IngestionRun** | One sync attempt on a source. Has status and progress |
| **DocumentTask** | One document's processing within a run. Has retries and a failure reason |

⚠️ **Design this schema carefully in phase 1.** You will live with it for a year. In particular, decide now: is `Document` versioned, or overwritten? That single choice changes phases 2, 5 and 9.

## The Nine Phases

Each phase is a note in section 16. Each depends on the vault sections listed.

### Phase 1 — The Core Service
*Needs: 01, 06, LLD vault*

One FastAPI service. Postgres. Users, orgs, sources, documents. Clean layering — routes, services, repositories, domain. Alembic migrations. Real tests.

**No queue, no cache, no second service.** Resist. The whole point of phase 4 is feeling why you needed to split, and you cannot feel that if you split on day one.

**Exit criteria:** documents can be created and searched via the API, 90% of business logic is testable without a database, and you have load-tested it and know its numbers.

### Phase 2 — Ingestion Pipeline
*Needs: 07, 08*

Celery workers pull from sources, parse documents, store chunks. Retries with backoff. Dead letter queue. Idempotency so re-running a sync does not duplicate documents. The outbox pattern so an event is never lost between the database commit and the publish.

**Exit criteria:** `kill -9` on a worker mid-document loses nothing and duplicates nothing visible to the user.

### Phase 3 — Realtime Layer
*Needs: 04*

SSE stream for ingestion progress. WebSocket for collaborative annotation with presence. A Redis backplane so it works across multiple app instances.

**Exit criteria:** three app nodes behind a load balancer, a user on node 1 sees the annotation of a user on node 3, and killing node 2 does not affect anyone else.

### Phase 4 — Split Into Services
*Needs: 05, 10*

Extract the ingestion service. gRPC between internal services. A GraphQL gateway for clients. Now you have distributed failure, and you find out what it costs.

**Exit criteria:** you have written an ADR that honestly evaluates whether this split was worth it. "No" is an acceptable and impressive answer if you defend it.

### Phase 5 — Event Backbone
*Needs: 09*

Kafka. CDC from Postgres for document changes. A search index built by consuming the log, so it can be rebuilt from scratch by replaying.

**Exit criteria:** delete the search index entirely, replay from offset 0, and end up with a byte-identical index.

### Phase 6 — Hardening
*Needs: 11*

Rate limits per org. Circuit breakers on every external call. Load shedding when the queue is deep. Deadline propagation across services. Graceful shutdown that drains in-flight work.

**Exit criteria:** one dependency at 100% failure does not take down the caller, and p99 latency stays flat instead of climbing.

### Phase 7 — Visibility
*Needs: 12*

OpenTelemetry traces across every service, including through Celery and Kafka. RED metrics. SLOs with burn-rate alerts. A dashboard you would actually use at 3am.

**Exit criteria:** one trace shows a request from the browser, through the gateway, through gRPC, into a Celery task, out to Kafka, and back.

### Phase 8 — Prove It
*Needs: 11*

k6 load tests to the breaking point. Chaos experiments: kill the database, fill the disk, add 500ms latency to Redis. Write a real postmortem for one of them.

**Exit criteria:** you know your throughput ceiling and your bottleneck, with numbers.

### Phase 9 — Handover to AI
*Needs: AI vault*

Chunks get embeddings. Search becomes hybrid — BM25 plus vector, with reranking. Answers stream over the SSE layer from phase 3. Access control from phase 1 becomes permission-aware retrieval.

**Exit criteria:** the AI vault's section 05 (RAG Systems) is now a set of changes to a system you already own, not a new project.

## Rules

These are not optional. They are what turns a project into evidence of seniority.

**One commit per meaningful change, with a real message.** Your git history is part of the deliverable. An interviewer who scrolls it should see a mind working.

**An ADR for every significant decision.** One page, four sections:

```markdown
# ADR-007: Use SSE for ingestion progress, not WebSocket

## Status
Accepted — 2026-03-14

## Context
Ingestion progress is one-way, server to client. Updates are frequent
but small. Clients are browsers behind corporate proxies.

## Decision
Use Server-Sent Events over HTTP/1.1 with heartbeats every 15s.

## Alternatives considered
- WebSocket: full duplex we do not need, more proxy problems,
  needs its own auth handshake
- Polling every 2s: simplest, but 30x more requests at our client count

## Consequences
- Browser connection limit of 6 per host applies. Must use HTTP/2
  or a dedicated subdomain if a user opens many tabs
- Reconnect and replay logic needed via Last-Event-ID
- Cannot send client→server on this channel. Fine, we have REST for that
```

This habit — writing down what you rejected and why — is the clearest single signal of a senior engineer. Almost nobody does it.

**Every phase ends with a load test.** You must know your numbers at every stage. Knowing them only at the end tells you nothing about what changed them.

**Never move to the next phase without tests and a README.**

**Keep `docs/` with diagrams you actually update.** A stale diagram is worse than none.

## The Six Questions

You are done with any phase when you can answer all six without hedging:

1. What is the throughput ceiling, and what is the bottleneck?
2. What happens when each dependency fails — every one, individually?
3. Where is data duplicated, and how does it become consistent again?
4. What is the p99, and why is it different from the p50?
5. If traffic went up 100x tomorrow, what breaks first and what is the fix?
6. What did you choose *not* to build, and why was that correct?

Write the answers down at the end of each phase. By phase 9 you will have a document that is, effectively, a system design interview you have already passed.

**Repo:** `onyx-dot-app/onyx`

## Exercise

**Conduit Phase 0 — Design before code**

No implementation yet. Just decisions, written down.

```
conduit/
├── README.md            # what the product does, in 200 words
└── docs/
    ├── architecture.md  # the phase-1 diagram only
    ├── domain.md        # the six entities, with fields and constraints
    └── adr/
        ├── ADR-001-monolith-first.md
        ├── ADR-002-postgres-as-primary-store.md
        └── ADR-003-document-versioning-strategy.md
```

ADR-003 is the hard one and the important one. Decide whether documents are versioned or overwritten, and write down the consequences for phases 2, 5 and 9. You will find that a decision that looks trivial now determines a lot later. That realisation is the exercise.

**Done when:** all three ADRs are written, the domain model has every field and constraint listed, and the repo has one commit.
