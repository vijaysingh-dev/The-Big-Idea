# Metadata, Source of Truth and Deployment Concepts

## What makes Salesforce deployment different

In most stacks, the repository is the truth and a deployment overwrites the target completely.

On Salesforce, **the org is a live, editable system.** An administrator can change a flow, a field, or a permission set directly in production. A deployment is not a replacement — it is a **merge** into a system that has its own state.

That single difference explains nearly every deployment problem in this section.

## Metadata versus data

**Metadata** — the configuration and code. Objects, fields, classes, flows, layouts, permission sets, validation rules.

**Data** — the records. Accounts, claims, users, and Custom Setting rows.

**Deployments move metadata, not data.**

The consequences that surprise people:

**Custom Setting rows do not deploy.** The definition does; the records do not. A fresh deployment leaves every read returning null. See [[17.2 - Custom Settings]].

**Custom Metadata records do deploy.** They are metadata by design, which is the main reason to prefer them.

**Named Credential secrets do not deploy.** The structure does; the client secret and private key must be populated per org.

**Connected app consumer keys do not deploy.** Deploying a connected app creates a new one with new credentials.

Every one of these is a manual post-deployment step, and the ones nobody documents are the ones that break production.

## Org development versus source development

**Org development.** The org is the source of truth. Changes are made in a sandbox and moved with change sets. The repository, if one exists, is a copy.

*Where it survives:* small orgs, admin-heavy teams, organizations without a developer.

*What it costs:* no history, no branching, no code review, no CI, and no way to know what changed between two releases.

**Source development.** The repository is the source of truth. Metadata is retrieved into files, versioned in Git, and deployed from there.

*What it requires:* the CLI, Git, and a team willing to work that way.

*What it gives:* history, review, automated testing, reproducible environments, and a real answer to "what is in this release".

**Source development is the destination**, and getting there from a mature org-development org is a project rather than a switch.

## The repository structure

```
force-app/
    main/default/
        classes/
            ClaimApprovalService.cls
            ClaimApprovalService.cls-meta.xml
        triggers/
        lwc/claimList/
        objects/Warranty_Claim__c/
            Warranty_Claim__c.object-meta.xml
            fields/Claim_Amount__c.field-meta.xml
            validationRules/
            recordTypes/
        flows/
        permissionsets/
        customMetadata/
manifest/
    package.xml
    destructiveChangesPost.xml
config/
    project-scratch-def.json
scripts/
    apex/post-deploy.apex
sfdx-project.json
```

**Every metadata component has a `-meta.xml` companion**, holding the API version and status. An Apex class without one does not deploy.

**Objects are decomposed** into a folder per object, with fields, validation rules, and record types as separate files. That decomposition is what makes Git diffs meaningful — a field change touches one file rather than a 4,000-line object definition.

## sfdx-project.json

```json
{
  "packageDirectories": [
    { "path": "force-app/core", "default": true, "package": "Northwind Core", "versionNumber": "2.4.0.NEXT" },
    { "path": "force-app/claims", "package": "Northwind Claims", "versionNumber": "1.7.0.NEXT",
      "dependencies": [{ "package": "Northwind Core", "versionNumber": "2.4.0.LATEST" }] }
  ],
  "namespace": "",
  "sfdcLoginUrl": "https://login.salesforce.com",
  "sourceApiVersion": "62.0"
}
```

**`packageDirectories`** define the modules. A single-directory project is the starting point; several directories with declared dependencies is the packaged structure. See [[21.5 - Unlocked Packages]].

**`sourceApiVersion`** applies to metadata with no explicit version of its own.

## The manifest

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>Warranty_Claim__c</members>
        <members>Machine_Coverage__c</members>
        <name>CustomObject</name>
    </types>
    <types>
        <members>ClaimApprovalService</members>
        <members>ClaimApprovalServiceTest</members>
        <name>ApexClass</name>
    </types>
    <types>
        <members>*</members>
        <name>PermissionSet</name>
    </types>
    <version>62.0</version>
</Package>
```

**`*` retrieves everything of that type.** Convenient for retrieval, risky for deployment — it picks up whatever exists at the time, which may include someone's in-progress work.

Naming members explicitly is safer for anything being deployed.

## What deployment actually does

**It is a merge, not a replacement.**

```
Deploy:  ClaimApprovalService, Claim_Amount__c

Result:  those two components are replaced in the target
         everything else in the org is untouched
```

**Components not in the deployment are not removed.** A field deleted from the repository still exists in production until a destructive change removes it explicitly.

That asymmetry means **the org accumulates**. Fields nobody uses, classes nobody calls, flows nobody remembers — all still there because deleting them requires deliberate action and untangling references.

## Destructive changes

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>Legacy_Claim_Status__c</members>
        <name>CustomField</name>
    </types>
    <version>62.0</version>
</Package>
```

```bash
sf project deploy start \
  --manifest manifest/package.xml \
  --post-destructive-changes manifest/destructiveChangesPost.xml \
  --target-org production
```

**Post is usually correct** — deploy the replacement, then remove the old component.

Deletions fail when anything still references the component: a formula, a validation rule, a flow, a report type, an Apex class, a layout. Finding them:

```sql
SELECT MetadataComponentName, MetadataComponentType
FROM MetadataComponentDependency
WHERE RefMetadataComponentName = 'Legacy_Claim_Status__c'
```

**Untangling references is usually more work than the deletion**, which is why unused metadata survives for years.

## The profile problem

The single most consequential deployment trap.

**When you retrieve a profile, the platform includes only permissions for metadata also in the retrieval.**

```
Retrieve: Profile only
Result:   a near-empty profile file

Deploy that file → permissions not included may be removed
```

The defences:

**Retrieve profiles alongside the objects, fields, and classes they reference.**

**Prefer permission sets in source control.** They retrieve completely, and they are better practice in any case. See [[03.4 - Permission Sets and Permission Set Groups]].

**Review profile diffs with suspicion.** One removing a hundred lines is a retrieval artefact, not an intended change.

Many teams deliberately exclude profiles from source control entirely and manage them manually, which is a defensible response to how badly they behave.

## API versions

```xml
<apiVersion>62.0</apiVersion>
```

Every Apex class, trigger, and LWC pins its own version, and the platform preserves that behaviour across releases.

**Raising it is a deliberate change requiring testing**, not housekeeping. A class on version 45 behaves as version 45 did, which is why old code keeps working.

**Salesforce retires old versions periodically**, which is the forcing function. Auditing what the org actually uses:

```sql
SELECT ApiVersion, COUNT(Id) classCount FROM ApexClass GROUP BY ApiVersion ORDER BY ApiVersion
```

```sql
SELECT Application, ApiVersion, COUNT(Id) FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:30 AND ApiType != null
GROUP BY Application, ApiVersion
```

The second query is the important one — it shows which **integrations** are on old versions, which is what actually breaks on a retirement. See [[01.11 - Release Cycle, Trust and Status]].

## Validation deployments

```bash
sf project deploy validate \
  --manifest manifest/package.xml \
  --test-level RunLocalTests \
  --target-org production
```

**Runs the deployment and its tests without committing.** The result is a validation Id that can be deployed quickly later:

```bash
sf project deploy quick --job-id 0Af5g00000ABCDeAAB --target-org production
```

**Quick deploy is the mechanism for a short release window.** Validate in advance — which runs every test and takes as long as it takes — then commit in seconds during the window.

The validation expires after 10 days, and the target org must not have changed materially in between.

## Test levels

```
NoTestRun               sandbox only
RunSpecifiedTests       named classes — fast, and coverage must still clear
RunLocalTests           everything except managed packages — the production default
RunAllTestsInOrg        including managed package tests
```

**Production requires at least `RunLocalTests`** for most deployments, which means every test in the org runs on every release. A slow suite is a slow release, and that is the practical pressure toward fast tests. See [[19.10 - Code Coverage, Quality and CI Gates]].

`RunSpecifiedTests` is allowed for some deployments and still requires 75% coverage on the deployed classes.

## Deployment limits

```
10,000 files or 400 MB per deployment
25 concurrent deploy or retrieve operations
75% org-wide Apex coverage
Every trigger covered
All tests passing
```

The file cap is reached by an initial deployment into a fresh org, which is one reason a large org's first move to source control is split into several deployments.

## What does not deploy

The list worth keeping, because each item is a manual step someone will forget.

```
Custom Setting records
Named Credential secrets
Connected app consumer keys and secrets
Certificate private keys
Data of any kind
Some Setup toggles — deliverability, org preferences
Territory model activation
Some Experience Cloud site settings
Skinny tables and custom indexes — requested per org
```

**Document these per environment.** The failure mode is an integration that authenticates in the sandbox and returns 401 in production, discovered during the release window.
