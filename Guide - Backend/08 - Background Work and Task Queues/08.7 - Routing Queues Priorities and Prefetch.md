# Routing, Queues, Priorities and Prefetch

#backend #queues #celery #operations

> **In one line:** One queue for everything means your 10-millisecond tasks wait behind your 10-minute ones — and the fix is almost always separate queues rather than priorities.

---

## The Idea

```
[ celery ] ← send_email, process_document, generate_report, refresh_cache
```

One queue, one worker pool, mixed durations. Three problems appear immediately:

| Problem | |
|---|---|
| **Head-of-line blocking** | A fast task waits behind slow ones ([[02.5 - Head of Line Blocking]]) |
| **No isolation** | A flood of one task type starves everything else |
| **No differentiated scaling** | You cannot add capacity for just the slow work |

💡 **The single most effective structural fix in a task queue system is separating queues by workload shape**, not by domain. `fast` and `slow` is a better split than `documents` and `notifications`.

---

## Routing

```python
app.conf.task_routes = {
    "app.tasks.send_*":          {"queue": "fast"},
    "app.tasks.process_document": {"queue": "ingestion"},
    "app.tasks.embed_*":          {"queue": "gpu"},
    "app.tasks.generate_report":  {"queue": "slow"},
    "app.tasks.*":                {"queue": "default"},
}
```

Or per-task:

```python
@app.task(queue="ingestion")
def process_document(document_id: str): ...
```

Or per-call, when the routing depends on the data:

```python
queue = "priority" if org.tier == "enterprise" else "default"
process_document.apply_async(kwargs={"document_id": doc_id}, queue=queue)
```

⚠️ **A task sent to a queue no worker consumes disappears into a growing backlog with no error.** It is one of the quieter production failures.

```bash
# Assert every configured queue has a consumer
celery -A app inspect active_queues
```

💡 **Add a startup check that every queue in `task_routes` is consumed by at least one worker pool.** It is ten lines and it prevents a whole class of silent failure.

### Dynamic routing

```python
class TenantRouter:
    def route_for_task(self, name, args=None, kwargs=None, **opts):
        if name.startswith("app.tasks.embed"):
            return {"queue": "gpu"}
        org_id = (kwargs or {}).get("org_id")
        if org_id and is_enterprise(org_id):
            return {"queue": "priority"}
        return {"queue": "default"}

app.conf.task_routes = (TenantRouter(),)
```

⚠️ **A router runs on the producer, in the request path.** Keep it fast and free of I/O — `is_enterprise` hitting the database on every enqueue is a real latency cost.

## How to Split Queues

### By duration — the primary split

```
fast        < 1 second     notifications, cache invalidation, webhooks
default     1–30 seconds   most work
slow        > 30 seconds   reports, exports, bulk operations
```

💡 **This is the split that solves head-of-line blocking**, and it is the one to do first. Everything else is refinement.

### By resource

```
cpu         parsing, image processing        → prefork pool, concurrency = cores
io          API calls, database work         → gevent pool, high concurrency
gpu         embedding                         → dedicated nodes, concurrency 1–2
```

⚠️ **Different resource profiles need different pool types** ([[08.3 - Celery Architecture]]). A worker with `--pool=gevent --concurrency=500` is right for I/O and catastrophic for CPU-bound work.

**This is a strong reason to split**: one queue cannot have two pool configurations.

### By blast radius

```
critical    payments, auth        ← never starved
default     everything else
bulk        backfills, migrations ← can be paused entirely
```

💡 **Being able to pause the `bulk` queue during an incident is genuinely valuable.** Stopping a backfill to free capacity for user-facing work is a one-command mitigation, and it only exists if the backfill has its own queue.

### By tenant, sometimes

```
priority    enterprise customers
default     everyone else
```

⚠️ **Per-tenant queues do not scale** — a queue per tenant means thousands of queues and workers idling on empty ones. **Tier-based queues do**, and they cap the number at two or three.

**For genuine per-tenant fairness, use rate limiting rather than queues** ([[11.5 - Rate Limiting and Quotas]]).

## Prefetch

The setting that causes the most confusing behaviour in Celery.

```
prefetch_count = concurrency × worker_prefetch_multiplier
```

```bash
--concurrency=4 --prefetch-multiplier=4      # 16 messages reserved
```

⚠️ **A worker reserves 16 messages while it can run 4. The other 12 are invisible to every other worker.**

```
Worker A: reserves 16 tasks × 10 minutes each = 160 minutes of work held
Worker B: idle, queue empty
```

💡 **This is the classic Celery starvation pattern**, and the default multiplier of 4 makes it the default behaviour for long tasks.

| Task duration | Multiplier |
|---|---|
| Milliseconds | 4–16 — prefetch amortises broker round trips |
| Seconds | 1–2 |
| **Minutes** | **1** |
| **Mixed** | **Separate queues.** No single value is right |

```python
app.conf.worker_prefetch_multiplier = 1
```

⚠️ **`prefetch_multiplier=1` still reserves `concurrency` messages**, so a worker with `--concurrency=8` holds 8. For very long tasks with `acks_late`, that is 8 messages unavailable to others.

```bash
# Long-task workers: low concurrency, low prefetch, more workers
celery worker -Q slow --concurrency=2 --prefetch-multiplier=1
```

💡 **The general rule: `prefetch × concurrency × task_duration` should be small relative to how long you are willing for another worker to sit idle.**

### The `acks_late` interaction

⚠️ **With `acks_late=True`, prefetched-but-unstarted messages are held unacknowledged.** A worker crash requeues all of them — including the ones it never began — which is correct but means a long redelivery delay on Redis ([[08.4 - Brokers and Result Backends]]).

## Priorities

```python
app.conf.task_queue_max_priority = 10
app.conf.task_default_priority = 5

task.apply_async(kwargs={...}, priority=9)
```

| Broker | Priority support |
|---|---|
| RabbitMQ | **Native**, within a queue |
| Redis | Emulated with separate keys per priority level |
| SQS | **None** |

⚠️ **Priorities have three limitations that make them less useful than they sound:**

**1. They do not preempt.** A running low-priority task continues; the high-priority task waits for a free slot.

**2. Prefetch defeats them.** Messages already reserved by a worker are processed in reservation order regardless of priority. **With prefetch 16, a priority-9 task arriving now waits behind 16 already-reserved messages.**

**3. Starvation.** If high-priority work arrives continuously, low-priority work never runs.

💡 **Separate queues with dedicated workers beat priorities in almost every case**, because they give you guaranteed capacity rather than a preference. A `priority` queue with two dedicated workers means priority work always has two slots; priority 9 on a shared queue means "sooner, probably".

```bash
# Guaranteed capacity, not a preference
celery worker -Q priority --concurrency=4
celery worker -Q priority,default --concurrency=8      # helps priority first, then default
```

⚠️ **The `-Q priority,default` ordering does not mean "drain priority first"** — Celery consumes from all listed queues. **For strict ordering you need separate worker pools.**

## Fairness

### Global rate limits

```python
@app.task(rate_limit="100/m")
def call_external_api(...): ...
```

⚠️ **Celery's `rate_limit` is per-worker, not global.** Ten workers with `100/m` means 1,000 per minute in total, which is almost never what you meant.

```python
# Global rate limiting needs shared state
async def acquire_global_slot(key: str, limit: int, window: int) -> bool:
    count = await redis.incr(f"rl:{key}:{int(time.time()) // window}")
    if count == 1:
        await redis.expire(f"rl:{key}:{int(time.time()) // window}", window * 2)
    return count <= limit
```

💡 **For an external API with a global quota, the limit must live in shared state.** Per-worker limits multiply by your worker count, which changes when you scale.

### Per-tenant fairness

```python
@app.task(bind=True)
def process_document(self, document_id: str, org_id: str):
    if not await acquire_global_slot(f"org:{org_id}", limit=50, window=60):
        raise self.retry(countdown=random.uniform(5, 30))
    ...
```

⚠️ **This burns worker slots on retries.** A better pattern is to check before dequeuing, which Celery does not support — which is an argument for a queue-per-tier plus concurrency limits per pool.

💡 **The cleanest fairness mechanism in Celery is capacity allocation via separate worker pools**, not runtime limiting. Give the `bulk` queue two workers and it cannot consume more than two workers' worth of capacity, no matter how much is queued.

## In Production

### The queue topology

```
Queue        Workers  Concurrency  Pool     Prefetch  Purpose
fast         3        16           gevent   4         < 1s tasks
default      4        8            prefork  2         normal work
ingestion    6        4            prefork  1         document pipeline
gpu          2        1            solo     1         embedding
slow         2        2            prefork  1         reports, exports
bulk         1        2            prefork  1         backfills, pausable
```

💡 **Write this table down.** It is the single most useful piece of documentation for a task-queue system, and it makes the capacity allocation explicit rather than emergent.

### Autoscaling per queue

```yaml
# KEDA scaling on queue depth
triggers:
  - type: redis
    metadata:
      listName: ingestion
      listLength: "20"          # one replica per 20 queued messages
```

⚠️ **Scale on queue *age*, not depth, where you can** ([[08.1 - Why Background Work Exists]]). Depth of 10,000 fast tasks is fine; depth of 20 with the oldest at 30 minutes is not.

💡 **Scale-down is the harder direction.** A worker terminated mid-task requeues its work; with `acks_late` nothing is lost, and you have wasted the work done so far. **Set `terminationGracePeriodSeconds` above your task time limit** ([[11.7 - Graceful Shutdown and Draining]]).

### Detecting starvation

```bash
celery -A app inspect reserved     # ← the diagnostic
```

```python
worker_reserved_tasks.labels(worker=name).set(count)
worker_active_tasks.labels(worker=name).set(count)
queue_depth.labels(queue=name).set(depth)
queue_oldest_age_seconds.labels(queue=name).set(age)
```

⚠️ **One worker with 40 reserved tasks while others have zero is prefetch hoarding**, and it is invisible from queue depth alone.

💡 **The three-signal diagnosis:**

| Depth | Oldest age | Reserved | Diagnosis |
|---|---|---|---|
| High | Low | Even | Healthy burst |
| High | **High** | Even | Not enough capacity |
| Low | **High** | Uneven | **Prefetch hoarding, or a stuck task** |
| Low | High | Zero | **No consumer on this queue** |

### The pause switch

```bash
celery -A app control cancel_consumer bulk        # stop consuming
celery -A app control add_consumer bulk           # resume
```

💡 **Being able to pause a queue without a deploy is a valuable incident tool.** Stop the backfill, free the capacity, resolve the incident, resume.

⚠️ **This requires broker fanout support** — it does not work on SQS ([[08.4 - Brokers and Result Backends]]). With SQS you need a feature flag the tasks check, or separate worker deployments you can scale to zero.

### Conduit's topology

| Queue | Why separate |
|---|---|
| `fast` | Notifications and cache invalidation must not wait behind ingestion |
| `ingestion` | The document pipeline. Its own scaling and its own failure domain |
| `embedding` | GPU-bound in phase 9. Different node type, concurrency 1–2 |
| `slow` | Exports and reports. Minutes-long, must not block anything |
| `bulk` | Backfills and reindexing. **Pausable during an incident** |

💡 **Five queues for a system this size is proportionate**, and each one exists for a reason that can be stated in a sentence. **A topology where you cannot explain why each queue exists is over-engineered.**

**Repo:** `celery/celery`, `onyx-dot-app/onyx`, `kedacore/keda`

**Question to answer:** In Celery, where is the prefetch count applied, and what happens to reserved messages when a worker shuts down gracefully? Then: how does Onyx structure its queues, and what determined the split?

**Read, in order:**

1. `celery/celery/worker/consumer/tasks.py` — **where `qos.increment_eventually` sets the prefetch count.** This is the mechanism
2. `celery/celery/worker/state.py` — `reserved_requests` and `active_requests`. **What `inspect reserved` actually reports**
3. `celery/celery/worker/consumer/consumer.py` — graceful shutdown. **Find where reserved-but-unstarted messages are handled** — the answer to the first question
4. `celery/celery/app/routes.py` — how `task_routes` patterns are matched, and how a custom router class is invoked
5. `onyx/backend/onyx/background/celery/` — **their queue definitions and routing.** Note how many queues and what the split is based on
6. `keda/pkg/scalers/redis_scaler.go` — how autoscaling reads queue depth, and what it cannot see

💡 The Onyx topology is worth studying because **it is a real system in Conduit's exact domain**, and comparing their split to the one you would design is a good calibration exercise. Note in particular whether they split by duration, by resource, or by domain.

**Part 1 — Measure the blocking.** One queue, four workers. Enqueue 1,000 tasks of 50ms and 20 tasks of 5 minutes, interleaved.

**Chart completion time for the fast tasks.** Some should wait many minutes.

Measure p50 and p99 for the fast tasks, and how long until all 1,000 complete.

**Part 2 — Split and re-measure.** Two queues, `fast` and `slow`, with dedicated workers and the same total capacity.

**Same load.** Fast-task p99 should drop by orders of magnitude.

**Put the two charts side by side.** This is the argument for queue separation, and it takes twenty minutes to produce.

Then try a third configuration — one queue with priorities — and show it does **not** solve the problem, because a running slow task still occupies its slot.

**Part 3 — Prefetch hoarding.** Two workers, `concurrency=2`, `prefetch_multiplier=4`. Twenty tasks of 30 seconds.

**Use `inspect reserved` to show one worker holding 16 and the other 4.**

Chart total completion time against multiplier (1, 2, 4, 8, 16) for 30-second tasks and for 50ms tasks.

**The two curves should point in opposite directions.** That is the whole prefetch lesson in one image.

Then find the crossover duration where the optimal multiplier changes from high to 1.

**Part 4 — Priorities and their limits.** RabbitMQ with `task_queue_max_priority=10`.

Enqueue 100 priority-1 tasks, then 10 priority-9 tasks. **Measure whether the high-priority ones actually run first.**

Then set `prefetch_multiplier=8` and repeat. **Confirm priorities are largely defeated by prefetch.**

Then the same on Redis and observe the emulation's behaviour.

Then implement the separate-queue alternative and confirm it gives guaranteed capacity rather than a preference.

**Part 5 — Rate limits multiply.** A task with `rate_limit="60/m"` running on 1, 3 and 10 workers.

**Measure the actual rate against an external endpoint.** It should be 60, 180 and 600 per minute.

Then implement a Redis-backed global limit and confirm it holds at 60 regardless of worker count.

Then measure the cost: how many worker slots are burned on retries when the limit is hit, and implement a variant that reduces it.

**Part 6 — Per-tenant fairness.** One tenant enqueues 100,000 tasks; nine others enqueue 100 each.

**Measure completion time for the small tenants.** They should be starved.

Then three fixes: a tier queue, a per-tenant concurrency limit, and per-tenant rate limiting. **Compare fairness achieved against worker capacity wasted.**

**Part 7 — Operations.** Route a task to a queue nobody consumes. **Confirm no error appears anywhere** and measure how long until you would notice from metrics alone.

Then implement the startup consumer check.

Then pause and resume the `bulk` queue under load, and measure the capacity freed.

**Part 8 — The three-signal diagnosis.** Build the diagnostic that reads depth, oldest age and reserved counts, and reports which of the four situations you are in.

Then have a script induce one of the four at random, and **diagnose it correctly within 60 seconds.**

**Done when:**
- Your single-queue versus split-queue charts show the fast-task improvement
- Priorities demonstrably fail to solve what separate queues solve
- Your prefetch curves point in opposite directions for long and short tasks
- You have measured priorities being defeated by prefetch
- Per-worker rate limits multiplied by worker count, and a global limit did not
- A starved small tenant is fixed by one of three mechanisms, with the cost stated
- A queue with no consumer was silently backlogged, and your startup check prevents it
- Your diagnostic identifies all four situations correctly
