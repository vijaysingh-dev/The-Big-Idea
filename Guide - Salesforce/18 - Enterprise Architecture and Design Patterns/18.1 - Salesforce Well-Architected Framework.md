# Salesforce Well-Architected Framework

## What it is

Salesforce's own published architecture guidance, organized around three qualities a solution should have. It is unusually practical for a vendor framework, and it is worth knowing because it gives shared vocabulary for architecture conversations — including in interviews and design reviews.

```
Trusted      Secure, Compliant, Reliable
Easy         Intentional, Automated, Resilient
Adaptable    Composable, Evolvable, Extensible
```

Nine qualities across three pillars. The value is not the taxonomy; it is that each one names a failure mode you will otherwise rediscover.

## Trusted

**Secure.** The system protects data appropriately.

In practice: object and field permissions granted through permission sets, sharing designed rather than defaulted, `WITH USER_MODE` on every reachable query, and guest-facing surfaces treated as public endpoints. See [[03.13 - Enforcing Security in Apex and SOQL]] and [[17.9 - Experience Cloud Basics]].

**Compliant.** The system meets its regulatory obligations.

Data residency, retention, right-to-erasure, audit trail, and consent. These are design constraints rather than features — a right-to-erasure requirement discovered after launch means field history, feed items, backups, and every downstream system need addressing. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

**Reliable.** The system works consistently under real conditions.

Bulk-safe automation, idempotent integrations, monitored async jobs, and headroom against governor limits. The recurring failure is code that works at one record and fails at 200. See [[16.7 - Designing Around Limits]].

## Easy

**Intentional.** Every part of the system exists for a stated reason.

The counter-example is the org where nobody can say what a flow does or why a field exists. The practical discipline is documenting the decision, not just the implementation — and consolidating: one trigger per object, one automation mechanism per concern. See [[07.1 - Automation Landscape and Tool Selection]].

**Automated.** Deployment, testing, and operations are repeatable.

Source control, CI, automated tests, and scripted post-deployment steps. A release process that depends on someone remembering to populate a Custom Setting is not automated. See [[21.8 - CI-CD Pipelines]].

**Resilient.** Failures are visible and recoverable.

Fault paths on flows, Finalizers on Queueables, durable logging, reconciliation jobs, and alerting on absence as well as on error. The failure mode this addresses: an integration that stopped running three weeks ago and nobody noticed. See [[13.17 - Error Handling, Retries and Idempotency]].

## Adaptable

**Composable.** Parts can be recombined without rework.

Services taking collections rather than reading `Trigger.new`, presentational components separated from containers, and integrations behind a defined contract rather than coupled to a schema. See [[18.3 - Service Layer]].

**Evolvable.** The system can change without breaking.

Configuration in Custom Metadata rather than hardcoded, external IDs so data can be reconciled, versioned API contracts, and interfaces at the seams. See [[18.10 - Custom Metadata Driven Architecture]].

**Extensible.** Others can build on it.

Documented events, invocable actions administrators can use in flows, and public methods with stable signatures. An org where every change requires a developer is not extensible. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Using it in practice

The framework earns its place in three activities.

**As a review checklist.** Before a design is approved, walk the nine qualities and ask which are weak. Most designs are strong on two or three and silent on the rest.

**As shared vocabulary.** "This is reliable but not evolvable" is a more productive sentence than "I don't like it", and it moves the conversation to the specific tradeoff.

**As a way to surface implicit decisions.** A design with no answer for "what happens when this fails" has made a resilience decision by omission.

## The decision guides

Alongside the framework, Salesforce publishes **decision guides** for specific recurring questions — automation tool selection, integration patterns, record-level access, data modelling.

These are more immediately useful than the framework itself, because they take a real question and lay out the options with their consequences. The automation and integration guides in particular are worth reading in full; several notes in this course summarize them.

## Where a framework helps and where it does not

**It helps** as a checklist against forgetting a dimension, as vocabulary in a review, and as a way of making implicit choices explicit.

**It does not help** as a substitute for judgment. Nine qualities do not tell you whether to use a flow or a trigger on this object, with this data volume, maintained by this team. The specifics decide, and the framework only tells you which questions to ask.

The honest use: **read it once, keep the nine qualities in mind during design reviews, and rely on the decision guides for actual decisions.**

## The tension the framework does not resolve

Worth stating, because it is the substance of most real architecture arguments.

**Composability costs simplicity.** A layered architecture with services, selectors, and domains is more composable and harder to read for a new developer.

**Extensibility costs control.** Exposing invocable actions means administrators can use them in ways you did not anticipate, including badly.

**Evolvability costs immediacy.** Configuration in Custom Metadata is more flexible and less obvious than a constant in code.

**Automation costs setup time.** A CI pipeline pays for itself over a year and costs a sprint up front.

There is no universally right answer to any of these. An org with three developers and forty users needs less structure than one with thirty developers and forty thousand users, and applying the same architecture to both is a mistake in one direction or the other.

**The framework describes the destination for a large, long-lived org.** Judging how much of it to adopt is the actual architectural work, and section 18 covers the patterns with that calibration attached.

## What this section covers

The layered architecture the framework implies — service, domain, selector, and unit of work — followed by the reference implementation, dependency injection and testability, classical patterns adapted to Apex, metadata-driven design, event-driven architecture, and package structure.

Throughout, the question is not only "what is the pattern" but **"when is it worth it"**, because every one of these patterns is over-engineering in a small org and necessary in a large one.
