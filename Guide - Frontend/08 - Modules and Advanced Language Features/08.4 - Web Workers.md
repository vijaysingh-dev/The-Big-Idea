# Web Workers

A Web Worker runs JavaScript on a **separate thread** with its own event loop, heap and global scope. It is the only way to do genuinely parallel computation in the browser, and the only real fix for main-thread blocking ([[01.4 - The Event Loop]]).

## The basics

```js
// main.js
const worker = new Worker(new URL("./worker.js", import.meta.url), { type: "module" });

worker.postMessage({ type: "parse", payload: largeCsv });

worker.onmessage = (e) => {
  console.log(e.data);
};

worker.onerror = (e) => console.error(e.message);

worker.terminate();   // stop it immediately
```

```js
// worker.js
self.onmessage = (e) => {
  const { type, payload } = e.data;
  if (type === "parse") {
    self.postMessage({ type: "result", payload: parse(payload) });
  }
};
```

The `new URL(..., import.meta.url)` form is what Vite and webpack recognize for bundling a worker as a separate entry. A bare string path works in plain HTML but not through a bundler.

## What a worker can and cannot do

**Available:** `fetch`, `XMLHttpRequest`, `WebSocket`, `IndexedDB`, Cache API, `setTimeout`, `crypto`, `OffscreenCanvas`, `WebAssembly`, `importScripts` (classic workers) or `import` (module workers).

**Not available:** `window`, `document`, the DOM, `localStorage`, `alert`, direct access to anything on the main thread.

The DOM restriction is the fundamental constraint. A worker can compute, fetch and transform; it cannot render. Anything that touches the UI must be posted back.

## Message passing and its cost

Messages are copied using the **structured clone algorithm** ([[08.5 - Serialization and Structured Clone]]), not shared. That copy is synchronous on the sending thread and proportional to the data size.

```js
worker.postMessage(tenMegabyteArray);   // blocks the main thread while copying
```

For large binary data, use **transferables** — ownership moves instead of copying, and the transfer is O(1):

```js
const buffer = new ArrayBuffer(50 * 1024 * 1024);

worker.postMessage(buffer, [buffer]);   // second argument: transfer list

buffer.byteLength;   // 0 — the main thread no longer owns it
```

Transferable types include `ArrayBuffer`, `MessagePort`, `ImageBitmap`, `OffscreenCanvas` and streams. Plain objects and arrays are not transferable.

`SharedArrayBuffer` allows genuine shared memory with `Atomics` for synchronization, but requires cross-origin isolation headers (`COOP` and `COEP`) — a real deployment constraint, since enabling them breaks most third-party embeds.

## When a worker is worth it

The overhead is real: worker startup is roughly 10–40 ms, each message costs a clone, and the code duplication (a worker cannot share module instances with the main thread) adds bundle weight.

Worth it:

- **Parsing large payloads** — CSV, big JSON, XML. `JSON.parse` on a 10 MB response blocks for hundreds of milliseconds.
- **Image and video processing** — filters, resizing, encoding, especially with `OffscreenCanvas`.
- **Cryptography and hashing** — file checksums, encryption before upload.
- **Search and indexing** — building a client-side full-text index.
- **Data transforms on large datasets** — grouping, sorting, aggregating tens of thousands of rows.
- **Syntax highlighting and diffing** in editors.

Not worth it:

- Anything under ~50 ms of work.
- Anything DOM-bound.
- Network requests alone — `fetch` is already off-thread; only the response *processing* benefits.

## Worker types

**Dedicated Worker** — one owner, the default and the one you want 95% of the time.

**Shared Worker** — shared across tabs of the same origin, communicating via `port`. Useful for a single WebSocket connection serving several tabs, or cross-tab state sync. Support is inconsistent (Chrome for Android does not support it), and `BroadcastChannel` covers many of the same needs more simply.

**Service Worker** — a network proxy with a lifecycle independent of any page, used for offline support and caching. Structurally a worker, but a different concern entirely ([[14.4 - Cache API and Service Workers]]).

## Making it usable: request/response over messages

Raw `postMessage` is fire-and-forget, which is awkward for request/response. The standard wrapper:

```js
function createWorkerClient(worker) {
  const pending = new Map();
  let nextId = 0;

  worker.onmessage = (e) => {
    const { id, result, error } = e.data;
    const entry = pending.get(id);
    if (!entry) return;
    pending.delete(id);
    error ? entry.reject(new Error(error)) : entry.resolve(result);
  };

  return (type, payload, transfer = []) =>
    new Promise((resolve, reject) => {
      const id = nextId++;
      pending.set(id, { resolve, reject });
      worker.postMessage({ id, type, payload }, transfer);
    });
}

const call = createWorkerClient(worker);
const parsed = await call("parse", csvText);
```

Correlating by id is the whole trick. **Comlink** does this and more — it proxies the worker's exported functions so calls look like ordinary async method calls, using `Proxy` under the hood ([[08.3 - Proxy and Reflect]]):

```js
import * as Comlink from "comlink";

const api = Comlink.wrap(new Worker(...));
const result = await api.parse(csvText);
```

For most projects, Comlink is the right level of abstraction.

## Worker pools

Spinning up a worker per task wastes the startup cost. For repeated work, keep a pool sized to `navigator.hardwareConcurrency`:

```js
const size = Math.max(1, (navigator.hardwareConcurrency ?? 4) - 1);
```

Leaving one core for the main thread is the usual heuristic. Libraries like `workerpool` and `threads.js` handle the queueing.

## In React

```jsx
useEffect(() => {
  const worker = new Worker(new URL("./parse.worker.js", import.meta.url), { type: "module" });
  const call = createWorkerClient(worker);

  call("parse", file).then(setRows).catch(setError);

  return () => worker.terminate();
}, [file]);
```

Terminating on cleanup is mandatory — a worker outlives its component otherwise, holding memory and possibly continuing to compute ([[07.2 - Memory Leaks from Closures and Timers]]).

## How senior engineers actually use this

**They profile before reaching for a worker.** The Performance panel's long-task markers identify what actually blocks. Moving the wrong thing to a worker adds complexity for no gain.

**They move the whole pipeline, not one step.** Fetching on the main thread and parsing in a worker means the large response still crosses a thread boundary as a clone. Fetching *inside* the worker and posting back only the processed result avoids that entirely — often the single biggest design improvement.

**They use transferables for anything binary**, and shape their protocol so results are small even when inputs are large.

**They use Comlink rather than hand-rolling message protocols**, unless the protocol is trivially simple.

## Common pitfalls

- Trying to access the DOM or `localStorage` inside a worker.
- Posting huge objects and blocking the main thread on the clone — the very problem you were solving.
- Forgetting `terminate()`, leaking threads across route changes.
- Using a bare string path for the worker file, which bundlers do not resolve.
- Assuming closures or module state are shared. Workers have entirely separate heaps; anything needed must be posted.
- Adding a worker for work that takes 5 ms.

## Interview angle

"How would you keep the UI responsive during heavy computation" is the question this answers. Explain that JavaScript is single-threaded, so the only real options are chunking with yields or moving work off-thread, and that a worker gives true parallelism at the cost of structured-clone message passing. Mentioning transferables for zero-copy binary handoff, and fetching inside the worker to avoid the clone entirely, is what distinguishes a designed answer from a memorized one.
