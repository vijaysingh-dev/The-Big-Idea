# Semantic HTML and Document Structure

Semantic HTML means using elements for what they mean, not how they look. A `<button>` is a button because it does something when activated, not because it is styled like one.

The payoff is concrete: assistive technology navigation, keyboard behavior, focus management, browser defaults and search engine understanding all come free from the correct element and must be rebuilt by hand from the wrong one.

## The cost of a div

```html
<div class="btn" onclick="submit()">Submit</div>
```

What this loses compared to `<button>`:

- Not focusable — no `Tab` access
- No `Enter` or `Space` activation
- Not announced as a button by screen readers
- No `:disabled` state, no form submission behavior
- No default focus ring

Making it equivalent requires `tabindex="0"`, `role="button"`, keydown handlers for both `Enter` and `Space`, `aria-disabled`, and manual focus styling — roughly twenty lines to recreate what the browser gives for free. This is why the first rule of ARIA is that no ARIA is better than bad ARIA: use the native element.

## Document landmarks

```html
<body>
  <header>
    <nav aria-label="Main">...</nav>
  </header>

  <main>
    <article>
      <h1>Title</h1>
      <section>
        <h2>Section heading</h2>
      </section>
    </article>

    <aside>Related links</aside>
  </main>

  <footer>...</footer>
</body>
```

These map to ARIA landmark roles, and screen reader users navigate between them directly — pressing a key to jump to `main` skips the entire header and navigation.

Rules worth knowing:

- **`<main>`** — exactly one per page, containing the primary content. Not nested inside `article`, `aside`, `header`, `footer` or `nav`.
- **`<header>` / `<footer>`** — become landmarks only at the top level; inside `article` or `section` they are just grouping elements.
- **`<nav>`** — for major navigation blocks, not every group of links. Multiple `<nav>`s need distinguishing `aria-label`s.
- **`<aside>`** — tangentially related content, not "the sidebar" as a layout concept.

## article vs section vs div

**`<article>`** — independently distributable. A blog post, a comment, a product card, a news item. The test: would this make sense syndicated on its own?

**`<section>`** — a thematic grouping that is part of something larger. **It should have a heading.** A `<section>` without one is almost always a `<div>`.

**`<div>`** — no semantic meaning. The correct choice for pure layout wrappers, and there is nothing wrong with using it for that.

Overusing `<section>` is a common overcorrection: wrapping every flex container in `<section>` adds noise to the accessibility tree without adding meaning.

## Headings

Headings form the document outline, and screen reader users navigate by them more than by any other mechanism.

```html
<h1>Page title</h1>
  <h2>Major section</h2>
    <h3>Subsection</h3>
  <h2>Another major section</h2>
```

Rules:

- One `<h1>` per page in practice, describing the page's purpose.
- **Do not skip levels** going down. `h2` → `h4` breaks navigation.
- Choose the level by hierarchy, never by size. Size is CSS.

The HTML5 "document outline algorithm" — where heading levels would be scoped by sectioning elements — was **never implemented by any browser or screen reader** and has been removed from the spec. So `<h1>` inside a nested `<section>` is not automatically an `h2`. Use explicit levels.

## Lists

```html
<ul>            <!-- unordered -->
<ol>            <!-- ordered, sequence matters -->
<dl>            <!-- name-value pairs -->
  <dt>Term</dt>
  <dd>Definition</dd>
</dl>
```

Screen readers announce "list, 5 items", which is genuinely useful orientation. Navigation menus, card grids and tag lists are all lists.

`<dl>` is underused and is the right element for metadata tables, key-value summaries and glossaries.

## Tables

```html
<table>
  <caption>Q3 revenue by region</caption>
  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">Revenue</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">North</th>
      <td>₹1.2Cr</td>
    </tr>
  </tbody>
</table>
```

`<caption>`, `<th>` and `scope` are what make a table navigable — a screen reader announces the relevant row and column headers as the user moves between cells. Without them a data table is an unreadable stream of numbers.

Use tables for tabular data only. Layout tables are a solved problem — Grid and Flexbox handle that ([[11.2 - CSS Grid]]).

## Text-level semantics

```html
<strong>important</strong>      <!-- not <b> -->
<em>emphasis</em>               <!-- not <i> -->
<time datetime="2026-08-05">5 August</time>
<abbr title="Single Point of Failure">SPOF</abbr>
<code>const x = 1</code>
<mark>highlighted</mark>
<blockquote cite="...">...</blockquote>
```

`<b>` and `<i>` still exist for stylistic offsets with no added emphasis (a ship name, a keyword in a technical sense), but `<strong>` and `<em>` are the defaults.

`<time datetime>` gives machines an unambiguous timestamp while the visible text can say "3 days ago".

## Interactive elements you should not rebuild

```html
<details>
  <summary>Show more</summary>
  Hidden content
</details>

<dialog id="modal">
  <form method="dialog"><button>Close</button></form>
</dialog>
```

`<details>` gives you an accessible accordion with zero JavaScript. `<dialog>` with `showModal()` gives focus trapping, `Escape` to close, inert background content and a `::backdrop` pseudo-element — all the things custom modal implementations get wrong.

The Popover API (`popover` attribute) covers tooltips and menus similarly. Reaching for these before a library is increasingly the right call.

## In React

JSX renders HTML, so all of this applies unchanged. The specific React additions:

```jsx
// Fragments avoid wrapper divs that break table and list semantics
<>
  <td>A</td>
  <td>B</td>
</>

// Correct: a list of articles
<ul>
  {posts.map(p => (
    <li key={p.id}>
      <article>
        <h2>{p.title}</h2>
      </article>
    </li>
  ))}
</ul>
```

Component boundaries do not imply element boundaries. A `<Card>` component rendering a `<div>` inside a `<ul>` is invalid HTML even though the JSX looks tidy.

Heading levels are the recurring problem: a reusable component cannot know its depth. Either accept a level prop (`<Heading level={2}>`) or use a context that tracks nesting depth.

## How senior engineers actually use this

**They choose the element before the styling.** Deciding "this is a button" and then styling it is faster and more correct than styling a div and adding accessibility later.

**They audit with the accessibility tree, not the DOM tree.** Chrome DevTools' Accessibility pane shows what assistive technology actually sees, which reveals missing landmarks and mislabeled controls immediately.

**They keep a skip link.** `<a href="#main" class="skip-link">Skip to content</a>` as the first focusable element saves keyboard users from tabbing through a full navigation on every page.

**They validate the HTML.** Invalid nesting — a `<div>` inside a `<p>`, a `<li>` outside a list — causes browsers to silently restructure the DOM, which produces React hydration mismatches that are very hard to diagnose otherwise.

## Common pitfalls

- Clickable `<div>`s and `<span>`s.
- `<section>` without a heading.
- Heading levels chosen by font size.
- Multiple `<h1>`s or skipped levels.
- Data tables without `<th scope>` or `<caption>`.
- Nesting a block element inside `<p>`, silently breaking the DOM.
- Assuming the HTML5 outline algorithm scopes heading levels. It does not exist.

## Interview angle

Semantic HTML questions are usually "why not just use divs" or "what makes a page accessible". The strongest answer is concrete: name what a native `<button>` provides that a `<div>` does not, and point out that recreating it correctly takes twenty lines and is usually done wrong. Mentioning landmarks and heading navigation shows you understand how assistive technology actually moves through a page rather than treating accessibility as a checklist.
