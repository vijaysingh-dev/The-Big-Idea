# Conduit: Overview and Architecture

#backend #project #capstone

> **In one line:** Nine phases that turn a single-file FastAPI application into a distributed, observable, multi-tenant document platform — built in the order the problems actually appear, not in the order the topics were taught.

---

## What Conduit Is

**A document ingestion and realtime search platform.**

```
Sources (upload, Google Drive, Slack)
    → ingest → extract text → chunk → index
        → search (full-text, later semantic)
            → annotate, share, export
```

💡 **The domain was chosen because it naturally requires everything in this vault**: long-running work, realtime progress, multi-tenancy, external APIs, search, and eventually vectors. **Nothing is bolted on to justify a topic.**

⚠️ **It is not a product.** It is a vehicle for encountering real problems in a realistic sequence, **and the value is in the decisions you record, not the code you ship.**

## The Target Architecture

```
                    Browser / API clients
                            │
                    ┌───────▼────────┐
                    │  Gateway / BFF │  auth, rate limit, GraphQL, SSE
                    └───────┬────────┘
                            │ gRPC
        ┌───────────────────┼───────────────────┐
        │                   │                   │
   ┌────▼─────┐      ┌──────▼──────┐     ┌──────▼─────┐
   │ Documents│      │   Search    │     │ Ingestion  │
   └────┬─────┘      └──────┬──────┘     └──────┬─────┘
        │                   │                   │
   ┌────▼──────────────┐    │            ┌──────▼──────┐
   │ Postgres (RLS)    │    │            │ Embedding   │
   │ partitioned       │    │            │ API         │
   └────┬──────────────┘    │            └─────────────┘
        │ outbox → CDC      │
   ┌────▼─────┐        ┌────▼────────┐
   │  Kafka   │───────►│ Search index│
   └────┬─────┘        └─────────────┘
        ├──► analytics
        ├──► notifier
        └──► audit
              │
        ┌─────▼─────┐
        │   Redis   │  cache, SSE backplane, rate limits
        └───────────┘
```

**Managed externally:** Postgres, Redis, Kafka, object storage.

💡 **Three services, not eleven.** The split is `documents`, `search` and `ingestion`, **and even that is arguably one more than necessary** ([[10.11 - The Real Cost of Microservices]]).

## The Decisions, Up Front

**These are made once and referenced throughout. Each links to the note that justifies it.**

### Data

| Decision | Why |
|---|---|
| **Postgres as the system of record** | Relational, transactional, and it does most things adequately ([[06.14 - Beyond Postgres]]) |
| **UUIDv7 primary keys** | Sequential index behaviour, non-guessable ([[06.10 - Schema Design]]) |
| **`org_id` on every table** | Every index leads with it; RLS is one column ([[06.16 - Multi Tenant Data Models]]) |
| **Pool model with RLS** | Many small tenants; silo for enterprise ([[14.6 - Multi Tenant Isolation]]) |
| **Time-partitioned events** | Retention by `DROP`, not `DELETE` ([[06.13 - Partitioning and Sharding]]) |
| **Postgres FTS first** | Measure before adding Elasticsearch ([[06.15 - Search - Postgres vs Elasticsearch]]) |
| **pgvector, not a vector store** | Permission-filtered retrieval matters more than scale |

### Communication

| Boundary | Protocol |
|---|---|
| Browser → gateway | **GraphQL** — three clients, different needs ([[05.11 - REST vs GraphQL vs gRPC]]) |
| Public integrations | **REST** — third parties, cacheable |
| Gateway → services | **gRPC** — internal, typed |
| Progress push | **SSE** — one-way ([[04.1 - Choosing a Realtime Transport]]) |
| Services → services | **Kafka events** ([[09.1 - Queue vs Log]]) |

⚠️ **Only two synchronous required dependencies:** documents and auth. **Everything else degrades** ([[10.3 - Communication Patterns]]).

### Coordination

| Need | Mechanism |
|---|---|
| Work distribution | **`FOR UPDATE SKIP LOCKED`** — no leader ([[07.6 - Leader Election and Coordination]]) |
| Duplicate prevention | **A unique constraint**, not a lock |
| Source sync exclusion | `pg_try_advisory_xact_lock` |
| Scheduler singleton | Kubernetes `Lease` |

💡 **One lock in the whole system, and it is for efficiency rather than correctness** ([[07.4 - Distributed Locks Done Right]]).

### Security

| Layer | Enforces |
|---|---|
| Gateway | Authentication, forwards the token |
| Handler | Action against role |
| Repository | Tenant and ownership |
| DataLoader | Tenant boundary |
| **Postgres RLS** | **Tenant boundary, unconditionally** |
| Response | Outgoing assertion |

**Six layers, so any one being wrong is caught by another** ([[14.1 - AuthN vs AuthZ]]).

## The SLOs

| Journey | SLI | SLO |
|---|---|---|
| Document read | 2xx/3xx/4xx in < 500ms | 99.5% |
| Search | Results in < 1s | 99.0% |
| **Upload to searchable** | **Indexed within 5 minutes** | **95.0%** |
| Ingestion correctness | Indexed without error | 99.5% |

💡 **The freshness SLO is the one users care about** ([[12.2 - SLI SLO and Error Budgets]]), and it spans the whole asynchronous pipeline.

⚠️ **Search is 99.0%, not 99.5%, because it is an optional dependency that degrades.** Setting equal targets for optional and required paths lets the optional one dominate your budget.

## How to Use This Section

### Each phase note contains

```
- The problem the previous phase created
- What you build
- The decisions, with alternatives considered
- The things that will go wrong
- Acceptance criteria — measurable, not "it works"
- What you should be able to explain afterwards
```

### The rules

⚠️ **Measure everything.** Every decision in the ADR must cite a number you produced.

⚠️ **Write the ADR before you build**, then revise it after. **The gap between what you predicted and what happened is the learning.**

⚠️ **Do not skip the failure testing.** Building the happy path teaches you a fraction of what breaking it does.

💡 **Prefer the boring option and record why.** "We used Postgres FTS because our golden-set relevance was acceptable and Elasticsearch would have cost $450/month plus operational burden" is a stronger answer than any architecture diagram.

### The artefacts

By the end you should have:

```
□  A running system, deployable in one command
□  ~20 ADRs, each citing your own measurements
□  A load test suite with a known capacity number
□  A chaos catalogue with hypotheses and results
□  A dashboard someone else can use to diagnose an incident
□  A runbook covering ten failure scenarios
□  A cost model with cost-per-document
□  A written answer to "would you build it this way again"
```

💡 **The ADRs are the deliverable, not the code.** In an interview, "here is the decision I made and the number that justified it" is what distinguishes you.

## What This Is Not

⚠️ **Not a portfolio piece to impress with feature count.** Nobody will run it.

⚠️ **Not an excuse to use every technology.** The ADRs where you *rejected* something are the strong ones.

⚠️ **Not a substitute for the drills.** The section drills produce the measurements the phase ADRs cite — **build the drill, then apply it.**

💡 **It is a way to encounter the problems in sequence, with enough context that the solutions make sense.** Most engineers meet these problems one at a time, years apart, under pressure. **Meeting them deliberately, in order, is the point.**

## Codebase

**Repo:** `onyx-dot-app/onyx`

**Question to answer:** Onyx is a production system in Conduit's exact domain. How did they solve the problems each phase introduces, and where did they make a different choice?

**Read, in order:**

1. `onyx/backend/onyx/db/models.py` — **the schema.** Compare to your phase-1 design. **Note what they denormalise and why**
2. `onyx/backend/onyx/server/` — the API surface. **Where does the request end and background work begin?**
3. `onyx/backend/onyx/background/` — **the ingestion pipeline, staged.** Directly Conduit's phase 2
4. `onyx/backend/onyx/document_index/` — the search abstraction. **They chose Vespa; note what that bought them**
5. `onyx/backend/onyx/connectors/` — **source connectors.** Conduit's phase 3, with the OAuth and rate-limiting problems solved

💡 **Read Onyx once now, at the start, and again after phase 5.** The second reading is much richer, **because you will recognise the problems their code is solving rather than just the code.**

**Size:** 2 sessions now, 2 later.

## Exercise

**Drill 16.1 — Design it before you build it**

```
conduit/
├── docs/
│   ├── ARCHITECTURE.md
│   ├── DECISIONS.md          # the ADR index
│   ├── SLOS.md
│   └── adr/
├── phases/
└── README.md
```

**Part 1 — Write the domain model.** Before any code: organisations, users, sources, documents, chunks, annotations, ingestion runs.

**For each: fields, relationships, and the tenant key.**

⚠️ **Apply [[06.10 - Schema Design]]'s rules** — UUIDv7, `timestamptz`, `org_id` everywhere, constraints in the database.

**Part 2 — Write the SLOs first.** Four SLIs, four targets, with precise "good" definitions.

💡 **Writing these before building forces you to decide what the product promises**, and every later decision is measured against them.

**Part 3 — The boundary map.** For every operation, decide inline or background ([[08.1 - Why Background Work Exists]]).

**For every background decision:** the shape, the user-facing status, and the failure behaviour.

**Part 4 — The communication map.** For every interaction: sync or async, required or optional, degradation path, timeout budget.

**Then compute the effective availability** from the required synchronous dependencies and **compare it to your SLO** ([[10.3 - Communication Patterns]]).

⚠️ **If the arithmetic does not meet the SLO, change the architecture now**, before writing code.

**Part 5 — Write the rejection ADRs.** Before building, write the ADRs for what you are *not* doing:

```
ADR-001: We will not use microservices in phase 1
ADR-002: We will not use Kafka in phase 1
ADR-003: We will not use Elasticsearch until Postgres FTS is measured insufficient
ADR-004: We will not use a service mesh
ADR-005: We will not shard
```

💡 **Each must name the specific signal that would change the decision.** "We will reconsider Elasticsearch when relevance falls below 0.7 precision@10 on our golden set" is an engineering commitment; "when we need it" is not.

**Part 6 — The phase plan.** For each of the nine phases: what you build, what problem it solves from the previous phase, and the acceptance criteria.

**Part 7 — Set up the repository.** One repository, the phase structure, the ADR template, and a `README.md` that explains what this is.

**Then write `ARCHITECTURE.md`** as it will look at phase 9 — **the target, so every phase has a direction.**

**Done when:**
- The domain model exists on paper with tenant keys and constraints
- Four SLOs are written with precise "good" definitions
- Every operation has a justified inline-or-background decision
- Your effective availability calculation meets your SLO, or the architecture changed
- Five rejection ADRs each name a reconsideration trigger
- Nine phases have acceptance criteria
- `ARCHITECTURE.md` describes the phase-9 target
