# GraphQL Security and Limits

#backend #api-design #graphql #security

> **In one line:** GraphQL lets the client write the query, so a 200-byte request can ask for a billion rows — which means every production GraphQL server needs cost limits, and rate limiting by request count is meaningless.

---

## The Idea

In REST, the server decides how much work each endpoint does. **In GraphQL, the client does.**

```graphql
query {
  documents(first: 100) {
    annotations(first: 100) {
      author { organisation { documents(first: 100) { annotations(first: 100) { text } } } }
    }
  }
}
```

A few hundred bytes. Potentially 100 million rows.

⚠️ **Even with perfect DataLoader batching this is fatal** ([[05.6 - The N+1 Problem and DataLoader]]). Batching reduces round trips, not work. Three queries fetching 100 million rows is still 100 million rows.

💡 **The core defence is to compute the cost of a query before executing it, and reject anything too expensive.**

---

## Depth Limiting

The simplest control, and the weakest.

```python
class MaxDepthRule(ValidationRule):
    def enter_field(self, node, *_):
        self.depth += 1
        if self.depth > self.max_depth:
            self.report_error(GraphQLError(f"Query depth {self.depth} exceeds {self.max_depth}"))

    def leave_field(self, node, *_):
        self.depth -= 1
```

⚠️ **Depth alone does not stop this:**

```graphql
query { documents(first: 10000) { title } }     # depth 2, ten thousand rows
```

**Set a depth limit anyway** — 10 to 15 is generous — because it stops fragment-based recursion cheaply. **Just do not mistake it for cost control.**

`NoFragmentCycles` is mandatory ([[05.5 - How GraphQL Execution Works]]).

## Complexity Analysis

The real defence: assign a cost to each field and sum before executing.

```python
COMPLEXITY = {
    ("Query", "documents"):      lambda args: args.get("first", 20),
    ("Document", "annotations"): lambda args: args.get("first", 20),
    ("Document", "author"):      lambda args: 1,
    ("Document", "title"):       lambda args: 0,       # free, already loaded
    ("Query", "search"):         lambda args: args.get("first", 20) * 10,
}
```

Cost multiplies through nesting:

```
documents(first: 100)          = 100
  annotations(first: 50)       = 100 × 50   = 5,000
    author                     = 5,000 × 1  = 5,000
                               total ≈ 10,100
```

```python
if complexity > MAX_COMPLEXITY:
    raise GraphQLError(
        f"Query complexity {complexity} exceeds maximum {MAX_COMPLEXITY}",
        extensions={"code": "QUERY_TOO_COMPLEX", "complexity": complexity, "max": MAX_COMPLEXITY},
    )
```

💡 **Tell the client the numbers.** "Too complex" is unactionable; "complexity 47,000, max 5,000" tells them to reduce `first` and by roughly how much. **That is the difference between a limit developers work with and one they fight.**

### Deriving the costs

**Do not invent them. Measure.**

```python
field_cost_observed.labels(parent=..., field=...).observe(rows_fetched)
```

⚠️ **Set the limit from measured client behaviour, not a guess.** A limit that rejects real queries generates support load and teaches developers to work around you.

**Run in log-only mode first** — compute complexity, log it, reject nothing — for a week. Then set the limit above the p99 of legitimate traffic.

### Where it runs

```
parse → validate (including complexity) → execute
                  ▲ reject here — near-zero cost
```

⚠️ **Computing cost during execution is too late.** By the time you notice, you have fetched the rows.

## Rate Limiting by Cost

Request-count limiting is meaningless when one request can be a million times more expensive than another.

```python
async def check_rate_limit(org_id: str, complexity: int):
    used = await redis.incrby(f"gql:budget:{org_id}", complexity)
    if used == complexity:
        await redis.expire(f"gql:budget:{org_id}", 60)
    if used > HOURLY_BUDGET:
        raise GraphQLError("Rate limit exceeded",
                           extensions={"code": "RATE_LIMITED", "used": used})
```

Better: a token bucket denominated in complexity points ([[11.5 - Rate Limiting and Quotas]]).

💡 **This is how GitHub's GraphQL API works, and it is the right model.** It also gives clients a clear incentive to request less data, aligning their behaviour with your capacity.

Expose the budget so clients can self-regulate:

```json
{"extensions": {"cost": {"actual": 342, "remaining": 4213, "resetAt": "..."}}}
```

⚠️ **Charge the *actual* cost after execution, not just the estimate.** A query estimated at 5,000 that returned 3 rows should not consume 5,000 points — otherwise clients pay for pessimism and stop using pagination arguments honestly.

## Introspection

```graphql
query { __schema { types { name fields { name args { name } } } } }
```

This returns your entire data model, including things your UI never exposes.

| Environment | Introspection |
|---|---|
| Development, staging | On |
| **Production, internal API** | **Off** |
| Production, public API | On — it is the documentation |

⚠️ **Disabling introspection is obscurity, not security.** Tools like `clairvoyance` reconstruct a schema from error messages using field-name suggestions. **Also disable "did you mean" suggestions.**

💡 **The real defence is that every field is authorised**, so knowing a field exists gains an attacker nothing. **Treat introspection blocking as reducing attack surface, never as the boundary.**

---

## Field-Level Authorisation

```python
@strawberry.field
async def email(self, info: Info) -> str | None:
    if not can_view_email(info.context.user, self):
        return None
    return self._email
```

⚠️ **Authorisation must be at the field, not the query.** GraphQL lets clients reach objects through paths you did not anticipate:

```graphql
query {
  document(id: "public_doc") {
    annotations { author { email, organisation { billingDetails } } }
  }
}
```

Checking authorisation only on `Query.user` misses every other path to a `User`.

**The rule: authorise on the type that owns the data, wherever it is reached from.**

### Making it systematic

```python
# Enforce the tenant boundary inside the loader
async def batch_load_users(ids, viewer):
    rows = await db.fetch(
        "SELECT * FROM users WHERE id = ANY($1) AND org_id = $2", ids, viewer.org_id
    )
```

💡 **Enforcing the tenant boundary inside the DataLoader is the strongest pattern**, because every code path reaching a user goes through it. A resolver that forgets its check still cannot cross tenants.

⚠️ **Note the interaction with null propagation** ([[05.5 - How GraphQL Execution Works]]): returning `None` for an unauthorised non-null field nulls the parent. **Make authorisation-sensitive fields nullable**, or return a typed error in the payload.

## The Attacks

| Attack | Defence |
|---|---|
| Deeply nested query | Depth limit + complexity |
| Wide query, huge `first` | Complexity, and cap `first` per field |
| **Alias duplication** | **Count aliases in complexity** |
| Fragment cycle | `NoFragmentCycles` (standard) |
| Batched query array | Limit array size, sum complexity |
| Introspection reconnaissance | Disable in production + disable suggestions |
| Field-level data exposure | Per-field authorisation |
| Expensive mutation flood | Limit top-level mutations per request |
| Huge query string | Size limit before parsing |

### The alias attack

```graphql
query { a: expensiveSearch(q:"x"){id}, b: expensiveSearch(q:"x"){id}, ...×1000 }
```

⚠️ **Aliases are not merged.** A naive complexity calculator counting distinct field names sees cost 1 and lets through 1,000 executions.

**Complexity must walk the AST and count every selection.** Test this specifically.

## In Production

### The layered configuration

```python
schema = strawberry.Schema(
    query=Query, mutation=Mutation,
    extensions=[
        QueryDepthLimiter(max_depth=12),
        ComplexityLimiter(max_complexity=5000),
        MaxAliasesLimiter(max_aliases=15),
        MaxTokensLimiter(max_tokens=10000),
        CostRateLimiter(),
        MaskErrors(),
    ],
)
```

```python
MAX_QUERY_BYTES = 50_000            # before parsing
MAX_BATCH_SIZE = 10
MAX_TOP_LEVEL_MUTATIONS = 5
ALLOW_INTROSPECTION = False
```

💡 **Persisted queries with build-time registration make most of this unnecessary** ([[05.7 - GraphQL Caching]]). If only queries from your build manifest can execute, arbitrary malicious queries are structurally impossible. **For a first-party API, an allow-list is stronger and simpler than any runtime cost analysis.**

**Keep the limits anyway as defence in depth, and for development.**

### Rolling out without breaking clients

```
Week 1:  Compute complexity, log it, reject nothing
Week 2:  Analyse the distribution. Set the limit above p99.9 of legitimate traffic
Week 3:  Warn in extensions when exceeded, still allow
Week 4:  Contact the clients still exceeding it
Week 5:  Enforce
```

⚠️ **Enforcing a limit you have not measured will break a legitimate client in production.** The log-only phase usually reveals one internal dashboard doing something outrageous nobody knew about.

### Error masking

```python
result.errors = [
    e if isinstance(e.original_error, UserError)
    else GraphQLError("Internal server error", extensions={"requestId": request_id})
    for e in result.errors
]
```

⚠️ **GraphQL error messages leak more than REST's by default**, because unhandled resolver exceptions become error messages in the response. **Masking is mandatory in production.**

### What to monitor

```python
graphql_query_complexity.observe(complexity)
graphql_rejected_total.labels(reason="complexity"|"depth"|"rate_limit").inc()
graphql_introspection_attempts_total.inc()
```

💡 **`graphql_introspection_attempts_total` in production is a security signal.** With introspection disabled and a first-party client, legitimate traffic should never attempt it. **A non-zero rate means someone is probing you.**

## Codebase

**Repo:** `github` (docs), `slicknode/graphql-query-complexity`, `strawberry-graphql/strawberry`

**Question to answer:** How does GitHub calculate the cost of a GraphQL query, and how does it charge for connections versus scalar fields? Then: in a complexity library, how are aliases and fragments handled, and where does it hook into execution?

**Read, in order:**

1. **GitHub GraphQL resource limits documentation** — **the best public specification of query cost limiting.** Their node-count formula and rate-limit model are the reference design
2. `slicknode/graphql-query-complexity/src/QueryComplexity.ts` — the AST walk. **Look at fragment handling and multiplication through nesting** — this is the algorithm to port
3. `strawberry/extensions/query_depth_limiter.py` and `max_aliases_limiter.py` — small, readable, showing the extension hook point
4. `graphql-core/src/graphql/validation/rules/custom/no_schema_introspection.py` — introspection blocking as a validation rule
5. `saleor/saleor/graphql/api.py` — search for their limits and permission handling. **A real large schema's actual configuration**, more informative than any tutorial

💡 GitHub's cost model is worth studying closely because it is **a public API with untrusted clients** — the hardest case. If you ever expose GraphQL externally, copy their approach rather than inventing one.

**Size:** 1–2 sessions.

## Exercise

**Drill 5.8 — Attack your own schema, then defend it**

⚠️ Everything here runs against your own local stack only.

```
drills/05-graphql-security/
├── attacks/{deep_nesting.py, wide_query.py, alias_bomb.py, fragment_cycle.py, batch_flood.py, introspect.py, field_traversal.py}
├── defences/{depth.py, complexity.py, cost_ratelimit.py, authorisation.py, masking.py, config.py}
├── calibration/{log_only.py, distribution.py, RESULTS.md}
├── reconnaissance/reconstruct.py
└── README.md
```

**Part 1 — Break your own server.** Against the engine from drills 5.4–5.6, **with DataLoader working and no limits.**

For each attack measure: request size, response time, database rows, peak memory.

| Attack | Target |
|---|---|
| 15-level nesting | Time out or exhaust memory |
| `first: 100000` at three levels | Fetch millions of rows |
| 1,000 aliases of one expensive field | 1,000 executions |
| Fragment cycle | Hang |
| 500 operations in one batch | Serial execution for minutes |

**Build the table. Note that DataLoader was working perfectly throughout — that is the point.**

**Part 2 — Complexity analysis.** An AST walker with fragment expansion and **alias counting**.

Test against every attack. **Verify it runs as a validation rule — assert zero resolver calls and zero database queries for a rejected query.**

Then test against your five legitimate Conduit queries and confirm they pass comfortably.

**Part 3 — Calibrate honestly.** Log-only mode against realistic traffic.

Chart the distribution. Identify p50, p99, p99.9. **Set your limit from the data**, then verify no legitimate query is rejected and every attack is.

**Then set the limit at p50 instead and observe how many legitimate queries break.** That contrast is why the calibration phase exists.

**Part 4 — Cost-based rate limiting.** A token bucket in complexity points, with the budget in `extensions`.

Compare two clients: one sending 1,000 cheap queries, one sending 10 expensive ones with identical total cost.

**Under request-count limiting one is blocked and one is not. Under cost limiting they are treated equally.** Measure and chart both.

Then implement charge-by-actual-cost and show a query estimated at 5,000 returning 3 rows consuming 3 points.

**Part 5 — Field traversal.** Authorise only on `Query.user`. Then reach a `User` via `document → annotations → author` and read a field you should not see.

**Confirm the breach.** Then implement authorisation at the field, and separately at the loader. **Confirm the loader version blocks it even when you deliberately remove the field check.**

**Part 6 — Reconstruct the schema with introspection off.** Use error messages and field-name suggestions to rediscover types and fields.

**Measure how much you can recover.** Then disable suggestions and measure again.

**Write down how much protection introspection blocking actually provided** — the honest answer is "some, and not enough to rely on".

**Part 7 — The production configuration.** Assemble everything, re-run every attack. **All must be rejected before any resolver runs.** All five legitimate queries must pass.

Then add persisted queries with an allow-list and **note which of the other defences that makes redundant.**

**Done when:**
- Your attack table shows five successful attacks against a batched, DataLoader-correct server
- Complexity analysis rejects all of them at validation, with zero database queries
- Your limit is set from a measured distribution, not a guess
- Cost limiting treats cheap-and-many equally with expensive-and-few
- Field traversal is blocked at the loader even with the field check removed
- You know how much of your schema is recoverable with introspection disabled
