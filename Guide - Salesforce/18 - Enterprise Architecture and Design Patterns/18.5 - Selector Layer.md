# Selector Layer

## The idea

**Every query for an object lives in one class.**

```java
public with sharing class ClaimSelector {

    private static final List<String> BASE_FIELDS = new List<String>{
        'Id', 'Claim_Number__c', 'Status__c', 'Claim_Amount__c',
        'Claim_Date__c', 'Asset__c', 'Account__c'
    };

    public static Map<Id, Warranty_Claim__c> byIds(Set<Id> claimIds) {
        if (claimIds == null || claimIds.isEmpty()) {
            return new Map<Id, Warranty_Claim__c>();
        }

        return new Map<Id, Warranty_Claim__c>([
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c,
                   Claim_Date__c, Asset__c, Account__c
            FROM Warranty_Claim__c
            WHERE Id IN :claimIds
            WITH USER_MODE
        ]);
    }

    public static Map<Id, List<Warranty_Claim__c>> openByAsset(Set<Id> assetIds) {
        Map<Id, List<Warranty_Claim__c>> byAsset = new Map<Id, List<Warranty_Claim__c>>();

        if (assetIds == null || assetIds.isEmpty()) {
            return byAsset;
        }

        for (Warranty_Claim__c claim : [
            SELECT Id, Asset__c, Status__c, Claim_Amount__c, Claim_Date__c
            FROM Warranty_Claim__c
            WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
            WITH USER_MODE
            ORDER BY Claim_Date__c DESC
        ]) {
            if (!byAsset.containsKey(claim.Asset__c)) {
                byAsset.put(claim.Asset__c, new List<Warranty_Claim__c>());
            }
            byAsset.get(claim.Asset__c).add(claim);
        }
        return byAsset;
    }
}
```

## Why centralize queries

**Visibility.** Every query for an object is in one file. "How many queries does this transaction make, and are they selective" has an answer you can read.

**Consistency.** Field lists, `WITH USER_MODE`, `ORDER BY`, and `LIMIT` are applied the same way everywhere rather than depending on who wrote the caller.

**Reuse.** The same query serves a trigger, a controller, and a batch job.

**Change isolation.** A field rename touches one class. A performance fix — adding a date bound, narrowing a filter — is applied once and benefits every caller.

**Security by construction.** `WITH USER_MODE` in the selector means a caller cannot forget it. That is the strongest single argument for the layer. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Return shapes

The design decision that determines whether the selector actually helps.

```java
// A flat list — the caller usually has to reshape it
public static List<Warranty_Claim__c> openByAsset(Set<Id> assetIds)

// Keyed by Id — ready to look up
public static Map<Id, Warranty_Claim__c> byIds(Set<Id> claimIds)

// Grouped by parent — ready to iterate per parent
public static Map<Id, List<Warranty_Claim__c>> openByAsset(Set<Id> assetIds)
```

**Return the shape the caller needs.** A selector returning a flat list, where every caller then builds the same map, has moved the query and left the duplication.

The grouped-map return is the one that most reliably prevents a per-record query at the call site, because the caller has the lookup already.

## Empty input guards

```java
if (assetIds == null || assetIds.isEmpty()) {
    return new Map<Id, List<Warranty_Claim__c>>();
}
```

**Every selector method needs this.** A query with an empty `IN` clause still consumes one of the 100 queries, and in a handler with several conditional paths the waste adds up. See [[16.2 - SOQL and DML Limits]].

Returning an empty collection rather than null is also what lets callers skip a null check.

## Field lists

Two approaches, with a real tradeoff.

**Explicit per method** — clear, and duplicated:

```java
SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c FROM Warranty_Claim__c
```

**A shared field list with dynamic SOQL** — DRY, and less readable:

```java
private static final Set<String> BASE_FIELDS = new Set<String>{
    'Id', 'Claim_Number__c', 'Status__c', 'Claim_Amount__c'
};

private static String buildQuery(Set<String> extraFields, String whereClause) {
    Set<String> fields = new Set<String>(BASE_FIELDS);
    fields.addAll(extraFields ?? new Set<String>());

    return 'SELECT ' + String.join(new List<String>(fields), ', ')
        + ' FROM Warranty_Claim__c WHERE ' + whereClause;
}
```

Dynamic SOQL costs compile-time field validation and introduces injection risk if any part is user-supplied. Bind variables and an allowlist for field names are mandatory. See [[08.7 - Dynamic SOQL]].

**The pragmatic position:** explicit static queries in most selectors, dynamic only where the field set genuinely varies — a configurable component, or a packaged framework.

## Selective by construction

The selector is the right place to enforce query hygiene.

```java
public static List<Warranty_Claim__c> recentByAccount(Id accountId, Integer dayWindow) {
    Integer window = dayWindow == null ? 90 : dayWindow;
    Date cutoff = Date.today().addDays(-window);

    return [
        SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c
        FROM Warranty_Claim__c
        WHERE Account__c = :accountId
          AND Claim_Date__c >= :cutoff
          AND Status__c IN ('Submitted', 'Under Review', 'Approved')
        WITH USER_MODE
        ORDER BY Claim_Date__c DESC
        LIMIT 1000
    ];
}
```

Three things this enforces that a caller might not:

**A date bound**, which is the most common fix for a non-selective query.

**A positive `IN` list** rather than `!= 'Closed'`, since negative operators cannot use an index.

**A `LIMIT`**, so a data growth surprise degrades rather than fails.

See [[08.9 - Indexes and Selective Queries]].

## Instance versus static

fflib uses instance-based selectors with a base class supplying field-set handling and security enforcement:

```java
public with sharing class ClaimsSelector extends fflib_SObjectSelector {

    public List<Schema.SObjectField> getSObjectFieldList() {
        return new List<Schema.SObjectField>{
            Warranty_Claim__c.Id,
            Warranty_Claim__c.Claim_Number__c,
            Warranty_Claim__c.Status__c,
            Warranty_Claim__c.Claim_Amount__c
        };
    }

    public Schema.SObjectType getSObjectType() {
        return Warranty_Claim__c.SObjectType;
    }

    public List<Warranty_Claim__c> selectById(Set<Id> ids) {
        return (List<Warranty_Claim__c>) selectSObjectsById(ids);
    }
}
```

**What the base class buys:** consistent field handling, automatic security enforcement, and a mockable instance for tests.

**What it costs:** a dependency, more ceremony, and a field list expressed as `SObjectField` tokens rather than in the query.

**Static selectors are simpler** and adequate for most orgs. Instance-based earns its place when tests need to mock the selector — which is the subject of [[18.8 - Dependency Injection and Testability]].

## Cross-object queries

Which selector owns a query joining two objects?

**The one whose object is the primary in the FROM clause.**

```java
// FROM Warranty_Claim__c → belongs in ClaimSelector
public static List<Warranty_Claim__c> withAssetAndAccount(Set<Id> claimIds) {
    return [
        SELECT Id, Claim_Number__c,
               Asset__r.SerialNumber, Asset__r.Account.Name, Asset__r.Account.BillingCountry
        FROM Warranty_Claim__c
        WHERE Id IN :claimIds
        WITH USER_MODE
    ];
}
```

```java
// FROM Asset with a subquery → belongs in AssetSelector
public static List<Asset> withOpenClaims(Set<Id> assetIds) {
    return [
        SELECT Id, SerialNumber,
               (SELECT Id, Claim_Amount__c FROM Warranty_Claims__r WHERE Status__c != 'Closed')
        FROM Asset
        WHERE Id IN :assetIds
        WITH USER_MODE
    ];
}
```

The subquery form is worth watching: **parent and child rows both count** toward the 50,000-row limit, so a wide subquery across many parents adds up faster than it looks. See [[08.2 - Relationship Queries]].

## Aggregates

```java
public static Map<Id, Decimal> totalOpenAmountByAsset(Set<Id> assetIds) {
    Map<Id, Decimal> totals = new Map<Id, Decimal>();

    if (assetIds.isEmpty()) {
        return totals;
    }

    // aggregating in the database rather than summing in Apex saves heap and CPU
    for (AggregateResult result : [
        SELECT Asset__c assetId, SUM(Claim_Amount__c) total
        FROM Warranty_Claim__c
        WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
        WITH USER_MODE
        GROUP BY Asset__c
    ]) {
        totals.put((Id) result.get('assetId'), (Decimal) result.get('total'));
    }
    return totals;
}
```

Selectors returning aggregates rather than raw records is a substantial win at volume — retrieving 50,000 claims to sum them in Apex costs heap and CPU that the database does for free. See [[08.4 - Aggregate Queries, GROUP BY and HAVING]].

## Testing

**Selector tests need real data**, since they exist to verify the query.

```java
@IsTest
static void openByAssetExcludesClosedClaims() {
    Asset asset = TestDataFactory.createAsset();
    TestDataFactory.createClaim(asset.Id, 'Submitted');
    TestDataFactory.createClaim(asset.Id, 'Approved');
    TestDataFactory.createClaim(asset.Id, 'Closed');

    Test.startTest();
    Map<Id, List<Warranty_Claim__c>> result =
        ClaimSelector.openByAsset(new Set<Id>{ asset.Id });
    Test.stopTest();

    Assert.areEqual(2, result.get(asset.Id).size(), 'Closed claims should be excluded');
}
```

```java
@IsTest
static void emptyInputDoesNotConsumeAQuery() {
    Test.startTest();
    Integer before = Limits.getQueries();
    ClaimSelector.openByAsset(new Set<Id>());
    // proving the guard works, since an unguarded query still costs one
    Assert.areEqual(before, Limits.getQueries(), 'An empty input should not query');
    Test.stopTest();
}
```

Testing that a selector respects sharing is worth doing for anything reachable by external users:

```java
@IsTest
static void selectorRespectsSharing() {
    User portalUser = TestUserFactory.createPortalUser();
    Warranty_Claim__c otherClaim = TestDataFactory.createClaimForAnotherAccount();

    System.runAs(portalUser) {
        Map<Id, Warranty_Claim__c> result =
            ClaimSelector.byIds(new Set<Id>{ otherClaim.Id });
        Assert.isTrue(result.isEmpty(), 'A portal user should not see another account\'s claim');
    }
}
```

## When to adopt

**Skip selectors when** the org is small and queries appear once each. A query inline in a service is readable and fine.

**Adopt them when** the same query appears in three places, when query count is a live concern, or when `WITH USER_MODE` keeps getting forgotten.

**The signal:** you cannot answer "what does this transaction query" without reading five classes.

## Practical guidance

**One selector per object**, named `ObjectSelector`.

**Guard empty inputs** — an empty `IN` still costs a query.

**Return the shape the caller needs**, usually a map.

**Put `WITH USER_MODE` in the selector**, so callers cannot forget it.

**Enforce a `LIMIT` and a date bound** where the object is large.

**Prefer aggregates to retrieving rows** for totals and counts.

**Own a cross-object query in the selector of the FROM object.**

**Test with real data**, including the sharing case.
