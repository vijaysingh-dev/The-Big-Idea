# Reading Session: The Celery Worker Loop

#backend #reading #queues

> **In one line:** Celery's behaviour under failure is entirely determined by the order of four operations in the worker loop, and reading that order settles every argument about `acks_late`, prefetch and lost tasks.

---

## Why This Codebase

💡 **Celery is where most Python backend teams' hardest production bugs live** — duplicated tasks, lost tasks, workers that stop consuming, memory that only grows.

**Almost all of them are explained by code you can read in an afternoon.**

## The Path

### 1. The client side — `celery/app/task.py`

```python
def apply_async(self, args=None, kwargs=None, task_id=None, ..., **options):
    ...
    return app.send_task(self.name, args, kwargs, task_id=task_id, ...)
```

`celery/app/base.py:send_task`:

```python
def send_task(self, name, args=None, kwargs=None, ..., **options):
    ...
    options = router.route(options, route_name or name, args, kwargs, task_type)
    message = amqp.create_task_message(task_id, name, args, kwargs, ...)
    ...
    amqp.send_task_message(P, name, message, **options)
```

💡 **Routing happens entirely on the client.** The message is built with its destination queue already decided — **the worker does no routing at all** ([[08.7 - Routing Queues Priorities and Prefetch]]).

⚠️ **That means a routing change requires redeploying the *producer*, not the worker.** A common source of confusion.

```python
# Protocol 2 message format
headers = {"lang": "py", "task": name, "id": task_id, "eta": eta,
           "expires": expires, "retries": retries, "argsrepr": ..., "origin": ...}
body = (args, kwargs, {"callbacks": ..., "errbacks": ..., "chain": ..., "chord": ...})
```

**Read `celery/app/amqp.py:as_task_v2`.** The message format is the contract between producer and worker, **and version skew here is what breaks rolling deploys** ([[08.5 - Task Design Rules]]).

### 2. The worker starts — `celery/worker/worker.py`

```python
class WorkController:
    class Blueprint(bootsteps.Blueprint):
        default_steps = {
            'celery.worker.components:Hub',
            'celery.worker.components:Pool',
            'celery.worker.components:Timer',
            'celery.worker.components:StateDB',
            'celery.worker.components:Consumer',
        }
```

⚠️ **Bootsteps are Celery's dependency-ordered startup system.** Each step declares what it requires, and the blueprint resolves the order.

💡 **Do not try to understand the bootstep machinery.** Note that `Consumer` is the one that matters and move on — **this is exactly the "know when to stop" discipline from [[15.1 - How to Read a Large Codebase]]**.

### 3. The consumer loop — `celery/worker/consumer/consumer.py`

```python
def start(self):
    blueprint = self.blueprint
    while blueprint.state not in STOP_CONDITIONS:
        ...
        try:
            blueprint.start(self)
        except self.connection_errors as exc:
            ...
            self.on_connection_error_after_connected(exc)
```

**The outer loop is reconnection.** If the broker connection drops, it rebuilds and continues.

⚠️ **Note `self.restart_count` and the backoff.** A broker outage produces reconnection attempts with increasing delay — **and without jitter, every worker reconnects simultaneously** ([[11.2 - Timeouts Retries and Jitter]]).

```python
def on_task_received(self, message):
    ...
    strategy = strategies[type_]
    strategy(message, None, message.ack_log_error, message.reject_log_error, callbacks)
```

💡 **`ack_log_error` and `reject_log_error` are passed *into* the strategy.** The consumer does not decide when to ack — **it hands the ack callable to the code that will decide.** That indirection is where `acks_late` lives.

### 4. The strategy — `celery/worker/strategy.py`

**The most important file in this session. Read it in full — it is about 200 lines.**

```python
def default(task, app, consumer, info=logger.info, error=logger.error, ...):
    ...
    def task_message_handler(message, body, ack, reject, callbacks, ...):
        ...
        req = Req(message, on_ack=ack, on_reject=reject, app=app, hostname=hostname,
                  eventer=eventer, task=task, connection_errors=connection_errors,
                  body=body, headers=headers, decoded=decoded, utc=utc)

        if _does_info:
            info(_app_trace.LOG_RECEIVED, ...)

        if (req.expires or req.id in revoked_tasks) and req.revoked():
            return

        signals.task_received.send(sender=consumer, request=req)

        if task_sends_events:
            send_event('task-received', ...)

        if req.eta:
            ...
            consumer.timer.call_at(eta, apply_eta_task, (req,), priority=6)
        else:
            if rate_limits_enabled:
                ...
            else:
                consumer.apply_eta_task(req) if req.utc else task_reserved(req)
                handle(req)
```

💡 **The strategy is *compiled once per task type*, not per message.** Celery builds a closure with all the configuration resolved — rate limits, event sending, ack behaviour — **so the per-message path is as short as possible.**

⚠️ **Note that `revoked` is checked here, before execution.** Revocation only works if the worker has seen the revoke broadcast — **a worker that started after the revoke does not know about it** unless persistent revokes are enabled.

**Also note `req.eta`:** a countdown task is held in an in-memory timer on the worker that received it. **If that worker dies, the task is redelivered only if it was not acked** — which for `acks_early` it was.

💡 **That is why `countdown` with early acks loses tasks on worker restart**, and it is a real production surprise.

### 5. The request — `celery/worker/request.py`

**Where the ack decision actually lives.**

```python
def execute_using_pool(self, pool, **kwargs):
    task_id = self.task_id
    ...
    if self.revoked():
        raise TaskRevokedError(task_id)

    time_limit, soft_time_limit = self.time_limits
    result = pool.apply_async(
        trace_task_ret,
        args=(self._type, task_id, self._request_dict, self._body, self._content_type,
              self._content_encoding),
        accept_callback=self.on_accepted,
        timeout_callback=self.on_timeout,
        callback=self.on_success,
        error_callback=self.on_failure,
        soft_timeout=soft_time_limit,
        timeout=time_limit,
        correlation_id=task_id,
    )
    return result
```

```python
def on_accepted(self, pid, time_accepted):
    self.worker_pid = pid
    self.time_start = time_accepted
    ...
    if not self.task.acks_late:
        self.acknowledge()          # ⚠️ ACK BEFORE EXECUTION
```

```python
def on_success(self, failed__retval__runtime, **kwargs):
    ...
    if self.task.acks_late:
        self.acknowledge()          # ✅ ACK AFTER EXECUTION
```

⚠️ **This is the entire `acks_late` question, in six lines.**

```
acks_late = False (default):  ack on accept  → worker dies → TASK LOST
acks_late = True:             ack on success → worker dies → TASK REDELIVERED
```

💡 **The default is at-most-once.** Most people believe Celery is at-least-once by default, and it is not ([[08.2 - Queue Semantics]]).

```python
def on_failure(self, exc_info, send_failed_event=True, return_ok=False):
    ...
    if isinstance(exc, Retry):
        return self.on_retry(exc_info)
    ...
    if self.task.acks_late:
        requeue = self.task.reject_on_worker_lost and isinstance(exc, WorkerLostError)
        ...
        self.acknowledge() if not requeue else self.reject(requeue=requeue)
```

⚠️ **`reject_on_worker_lost` is the setting for "the worker was killed, requeue the task".** Without it, a task whose worker was OOM-killed is acknowledged as failed rather than retried ([[13.1 - Containers From First Principles]]).

### 6. Execution — `celery/app/trace.py`

```python
def build_tracer(name, task, loader=None, hostname=None, store_errors=True, ...):
    ...
    def trace_task(uuid, args, kwargs, request=None):
        ...
        try:
            R = retval = fun(*args, **kwargs)
            state = SUCCESS
        except Reject as exc:
            ...
        except Retry as exc:
            I, R, state, retval = on_error(task_request, exc, RETRY, call_errbacks=False)
        except Exception as exc:
            I, R, state, retval = on_error(task_request, exc)
        ...
```

💡 **`build_tracer` compiles a closure per task, resolving the result backend, the signal handlers and the error handling once.** The same optimisation as the strategy.

**Read `on_error` and note that `Retry` is an exception, not a return value** — `self.retry()` raises, and the tracer catches it.

### 7. Prefetch — `celery/worker/consumer/tasks.py`

```python
def start(self, c):
    ...
    c.task_consumer = c.app.amqp.TaskConsumer(
        c.connection, on_decode_error=c.on_decode_error,
    )
    ...
```

`celery/worker/consumer/consumer.py`:

```python
def _update_prefetch_count(self, index=0):
    ...
    return self._update_qos_eventually(index)
```

⚠️ **The effective prefetch is `worker_prefetch_multiplier × concurrency`.** With the default multiplier of 4 and concurrency 8, **each worker reserves 32 messages.**

💡 **Two workers, 40 short tasks and one long task: the worker that grabs the long task has also reserved 31 short ones, which sit idle behind it** ([[08.7 - Routing Queues Priorities and Prefetch]]).

**`worker_prefetch_multiplier = 1` for long or variable-duration tasks.** This is the single most impactful Celery setting for task-distribution fairness.

## What to Take Away

### The four operations, and their order

```
1. Receive the message
2. ACK          ← here if acks_late=False
3. Execute
4. ACK          ← here if acks_late=True
```

⚠️ **Everything about Celery's failure behaviour follows from which of 2 or 4 is used.**

| Configuration | Worker dies during execution |
|---|---|
| `acks_late=False` (default) | **Task lost silently** |
| `acks_late=True` | Task redelivered — **so it must be idempotent** ([[07.5 - Idempotency Keys and Deduplication]]) |
| `acks_late=True` + `reject_on_worker_lost=True` | Redelivered even on `WorkerLostError` |

💡 **`acks_late=True` plus an idempotent task is the correct configuration for almost everything**, and it is not the default.

### The settings that matter, now justified

```python
task_acks_late = True
task_reject_on_worker_lost = True
worker_prefetch_multiplier = 1
task_time_limit = 300
task_soft_time_limit = 240
broker_transport_options = {"visibility_timeout": 3600}   # Redis only
worker_max_tasks_per_child = 1000
```

⚠️ **`visibility_timeout` on Redis is the one people miss.** Redis has no real ack; Celery emulates it by re-delivering a message not acked within the visibility timeout. **A task running longer than that is delivered to a second worker while the first is still running** ([[08.4 - Brokers and Result Backends]]).

💡 **`visibility_timeout` must exceed your longest task duration.** The default is one hour, and a task that takes ninety minutes runs twice, forever.

### Where memory goes

⚠️ **`worker_max_tasks_per_child` exists because worker processes leak.** Not necessarily your code — a C extension, a connection pool, or fragmentation.

💡 **Recycling after N tasks is a workaround that works**, and the alternative is finding the leak. **Set it, and separately investigate.**

## In Production

### The failure modes, explained

| Symptom | Cause in the code |
|---|---|
| **Tasks disappear on deploy** | `acks_late=False` + `SIGKILL` |
| **Tasks run twice** | `visibility_timeout` < task duration, or a non-idempotent retry |
| **One worker idle, one overloaded** | Prefetch reserving messages |
| **`countdown` tasks lost on restart** | Held in an in-memory timer, already acked |
| Worker stops consuming | Connection lost, reconnection backoff |
| **Memory grows steadily** | No `max_tasks_per_child` |
| Revoke does not work | Worker started after the broadcast |
| Retries do not back off | No `retry_backoff` configured |

💡 **Every one of these is a line of code you have now read**, which is the point of the session.

### The audit

```
□  acks_late=True, and every task is idempotent
□  reject_on_worker_lost=True
□  prefetch_multiplier=1 for variable-duration tasks
□  visibility_timeout > longest task (Redis)
□  Hard and soft time limits set
□  max_tasks_per_child set
□  terminationGracePeriodSeconds > longest task ([[11.7 - Graceful Shutdown and Draining]])
□  Retries have backoff and jitter
□  A dead letter path exists ([[08.6 - Retries Backoff and Dead Letters]])
□  Queue oldest-age monitored, not just depth
```

**Part 1 — Trace the ack points.** Set breakpoints in `on_accepted` and `on_success`.

**Run a task with `acks_late=False`, then `True`.** Record which fires and when relative to execution.

**Write `ack_points.md`** with the exact line numbers.

**Part 2 — Lose tasks deliberately.** 1,000 tasks each taking 2 seconds, with `acks_late=False`.

**`kill -9` the worker halfway. Count completed tasks.**

**Report how many were lost.** Then repeat with `acks_late=True` and confirm zero loss.

Then with `acks_late=True` and `reject_on_worker_lost=False`, **kill the worker with an OOM-style kill and confirm the difference.**

**Part 3 — Duplicate tasks via visibility timeout.** Redis broker, `visibility_timeout=60`, a task taking 90 seconds.

**Instrument the task to log its worker ID.** Run it and **confirm two workers execute the same task.**

**Measure the overlap.** Then set `visibility_timeout=3600` and confirm it stops.

💡 **This is the most common Celery-on-Redis production bug**, and reproducing it once makes it unforgettable.

**Part 4 — Prefetch unfairness.** Two workers, concurrency 4. Enqueue one 60-second task followed by 40 one-second tasks.

**With `prefetch_multiplier=4`: chart per-worker utilisation and total completion time.**

**Then sweep the multiplier: 1, 2, 4, 8.** Chart total completion time and worker idle time.

**Confirm that 1 is best for this workload and worst for throughput on uniformly short tasks** — establishing the trade.

**Part 5 — `countdown` loss.** Enqueue 100 tasks with `countdown=60` and `acks_late=False`.

**Restart the workers after 30 seconds. Count how many execute.**

**Confirm they are lost**, then explain why from the strategy code. Then find a configuration where they are not.

**Part 6 — Shutdown.** A worker with 60-second tasks.

**Warm shutdown (`SIGTERM`):** measure how long it takes and whether tasks complete.
**Cold shutdown (`SIGQUIT`):** measure tasks abandoned.
**Grace period too short:** measure tasks redone per deploy.

**Then add `cancel_consumer` in `preStop`** and measure how much less work is in flight when the grace period starts ([[11.7 - Graceful Shutdown and Draining]]).

**Part 7 — Make a task safely retryable.** A task with a database write and an external API call.

**Run it with `acks_late=True` and kill the worker at three points**: before the write, between the write and the API call, and after both.

**For each, confirm exactly-once effect after redelivery.** Where it is not, add idempotency ([[07.5 - Idempotency Keys and Deduplication]]).

**Part 8 — Audit Conduit's Celery configuration.** Run the ten-item checklist.

**For every setting, cite the line of Celery source that justifies it.** A configuration you can justify from the source is one you will not second-guess during an incident.

**Done when:**
- You have the exact line numbers for both ack points
- You lost a measured number of tasks with `acks_late=False`
- Two workers executed the same task via visibility timeout, with the overlap measured
- Your prefetch sweep shows the fairness/throughput trade
- `countdown` tasks are lost on restart, and you can explain why from the code
- Warm, cold and short-grace shutdowns are all measured
- A task survives kills at three points with exactly-once effect
- Every Conduit Celery setting is justified by a source reference
