# Custom Metadata Types

## What they solve

Configuration that needs to be **deployable**, **queryable**, and **free to read**.

```java
// Hardcoded: changing it needs a deployment and a code review
if (claim.Claim_Amount__c > 500000) {
    claim.Approval_Tier__c = 'Executive';
}
```

```java
// Configuration: changing it needs a metadata record
for (Approval_Tier__mdt tier : ApprovalTierService.tiers()) {
    if (claim.Claim_Amount__c >= tier.Minimum_Amount__c) {
        claim.Approval_Tier__c = tier.Tier_Name__c;
        break;
    }
}
```

The threshold moves without touching code, and the change moves through environments as metadata rather than as data.

## The defining property

**Custom metadata records do not consume SOQL queries.**

```java
// Does not count toward the 100-query limit
List<Approval_Tier__mdt> tiers = [
    SELECT Tier_Name__c, Minimum_Amount__c, Requires_Executive__c
    FROM Approval_Tier__mdt
    WHERE Active__c = true
    ORDER BY Minimum_Amount__c DESC
];
```

The platform caches them. That single property is why they are the default choice for configuration, and why Platform Cache is usually unnecessary for it. See [[16.8 - Platform Cache]].

## Type versus record

```
Approval_Tier__mdt              the TYPE, deployed as metadata
  ├── Standard                  a RECORD, also metadata
  ├── Manager
  └── Executive
```

Both the definition and the rows deploy through the Metadata API and move between environments in a package. That is the fundamental difference from Custom Settings, where the definition deploys and the data does not. See [[17.2 - Custom Settings]].

## Defining one

```
Setup → Custom Metadata Types → New

Label:               Approval Tier
Object Name:         Approval_Tier
Visibility:          Public
```

Fields are created as on any object:

```
Tier_Name__c          Text(50)
Minimum_Amount__c     Number(16,2)
Requires_Executive__c Checkbox
Approver_Role__c      Text(80)
Active__c             Checkbox
Description__c        Text Area
```

Every record has `DeveloperName`, `MasterLabel`, `Label`, and `NamespacePrefix` automatically.

**Field types not available:** currency, roll-up summary, formula referencing other objects, and geolocation. Text, number, checkbox, picklist, date, and metadata relationships cover nearly every real case.

## Metadata relationships

A field type unique to custom metadata, letting a record point at another metadata component.

```
Field: Object__c
Type:  Metadata Relationship → Entity Definition

Field: Field__c
Type:  Metadata Relationship → Field Definition (filtered by Object__c)
```

```java
for (Field_Mapping__mdt mapping : [
    SELECT Object__r.QualifiedApiName, Field__r.QualifiedApiName, Target_Field__c
    FROM Field_Mapping__mdt WHERE Active__c = true
]) {
    String objectName = mapping.Object__r.QualifiedApiName;
    String fieldName = mapping.Field__r.QualifiedApiName;
}
```

**This gives deploy-time validation**: a mapping referencing a deleted field fails deployment rather than failing at runtime. That is a real advantage over storing field API names as text, where a rename silently breaks the configuration.

## Reading them

```java
public with sharing class ApprovalTierService {

    private static List<Approval_Tier__mdt> cachedTiers;

    public static List<Approval_Tier__mdt> tiers() {
        if (cachedTiers == null) {
            cachedTiers = [
                SELECT Tier_Name__c, Minimum_Amount__c, Requires_Executive__c, Approver_Role__c
                FROM Approval_Tier__mdt
                WHERE Active__c = true
                ORDER BY Minimum_Amount__c DESC
            ];
        }
        return cachedTiers;
    }

    public static String tierFor(Decimal amount) {
        for (Approval_Tier__mdt tier : tiers()) {
            if (amount >= tier.Minimum_Amount__c) {
                return tier.Tier_Name__c;
            }
        }
        return 'Standard';
    }
}
```

The static cache is not about the query limit — there is none — but about avoiding repeated retrieval within a transaction.

Two convenience methods avoid SOQL entirely:

```java
Approval_Tier__mdt tier = Approval_Tier__mdt.getInstance('Executive');
Map<String, Approval_Tier__mdt> all = Approval_Tier__mdt.getAll();
```

`getInstance` takes the `DeveloperName`. `getAll` returns everything keyed by developer name. Both read from the cache and **return only fields marked as visible**, which occasionally surprises — for full field access, use SOQL.

## Where they fit

**Business thresholds.** Approval tiers, discount limits, SLA targets.

**Feature toggles** that should deploy with the code that reads them.

**Handler registration**, driving which classes run for which object and event. See [[18.10 - Custom Metadata Driven Architecture]].

**Integration endpoints and mappings** — field mappings, external system identifiers, retry policies.

**Validation and routing rules** where an administrator should be able to add a case without a deployment.

**Country, region, and unit reference data** that rarely changes.

## Where they do not

**User-specific or profile-specific values.** Custom metadata has no hierarchy. A hierarchy Custom Setting does. See [[17.2 - Custom Settings]].

**Anything users edit routinely.** They are metadata, which means editing them in production is a metadata change — governed, audited, and often restricted.

**High-volume data.** They are configuration, not a data store.

**Anything written by Apex frequently.** Writes are asynchronous deployments, covered below.

**Secrets.** They are readable and deployable. Named Credentials hold credentials. See [[13.13 - Named Credentials and External Credentials]].

That last point deserves emphasis: a custom metadata record holding an API key is visible to anyone who can query it and travels in every package.

## Writing from Apex

Possible, and asynchronous — a metadata deployment rather than DML.

```java
public with sharing class MetadataWriteService {

    public static void updateThreshold(String tierName, Decimal newMinimum) {
        Metadata.CustomMetadata record = new Metadata.CustomMetadata();
        record.fullName = 'Approval_Tier.' + tierName;
        record.label = tierName;

        Metadata.CustomMetadataValue value = new Metadata.CustomMetadataValue();
        value.field = 'Minimum_Amount__c';
        value.value = newMinimum;
        record.values.add(value);

        Metadata.DeployContainer container = new Metadata.DeployContainer();
        container.addMetadata(record);

        // asynchronous: the callback reports success or failure, not this method
        Metadata.Operations.enqueueDeployment(container, new MetadataDeployCallback());
    }
}
```

**No DML.** No `insert`, no `update`. The deployment is queued and the callback reports the outcome.

**Not available in tests** in the usual way — the deployment does not execute, so the callback path needs separate unit testing.

Writing from Apex is right for admin tooling and for a managed package configuring itself on install. It is wrong as a general write path, because a deployment per change is slow and rate-limited.

## Testing

**Custom metadata records deployed in the org are visible in tests**, unlike Custom Setting data.

```java
@IsTest
static void executiveTierAppliesAboveThreshold() {
    // the real deployed configuration is available, no setup needed
    String tier = ApprovalTierService.tierFor(750000);
    Assert.areEqual('Executive', tier);
}
```

Convenient, and it couples the test to the org's configuration — a changed threshold breaks the test.

For isolation, inject the configuration:

```java
public with sharing class ApprovalTierService {

    @TestVisible
    private static List<Approval_Tier__mdt> overrideTiers;

    public static List<Approval_Tier__mdt> tiers() {
        if (overrideTiers != null) {
            return overrideTiers;
        }
        return loadFromMetadata();
    }
}
```

```java
@IsTest
static void tierBoundariesAreInclusive() {
    // constructed in memory; no deployment, no dependency on org configuration
    ApprovalTierService.overrideTiers = new List<Approval_Tier__mdt>{
        new Approval_Tier__mdt(Tier_Name__c = 'Executive', Minimum_Amount__c = 500000),
        new Approval_Tier__mdt(Tier_Name__c = 'Manager', Minimum_Amount__c = 100000)
    };

    Assert.areEqual('Executive', ApprovalTierService.tierFor(500000),
        'The boundary value should fall in the higher tier');
}
```

Custom metadata records can be constructed in memory with `new`, which is what makes this work. See [[18.8 - Dependency Injection and Testability]].

## In formulas and flows

Custom metadata is reachable declaratively, which multiplies its value.

**In a formula**, through `$CustomMetadata`:

```
$CustomMetadata.Approval_Tier__mdt.Executive.Minimum_Amount__c
```

The record is referenced by developer name, so it is a fixed record rather than a lookup — useful for a single threshold, not for iterating.

**In a flow**, a Get Records element on the metadata type works normally, and consumes no query.

**In a validation rule**, referencing a threshold rather than hardcoding it:

```
AND(
    ISCHANGED(Status__c),
    ISPICKVAL(Status__c, "Approved"),
    Claim_Amount__c > $CustomMetadata.Approval_Tier__mdt.Manager.Minimum_Amount__c,
    NOT($Permission.Can_Approve_Large_Claims)
)
```

Now the threshold is in one place, used by the validation rule, the flow, and the Apex.

## Limits

```
No SOQL query consumption
Long text areas count toward a per-transaction retrieval limit
Records are cached; changes may take a short time to propagate
Deployment through the Metadata API, not DML
Protected types are hidden from subscriber orgs in a managed package
```

**Protected custom metadata** is worth knowing for packaging: a protected type is invisible and uneditable in a subscriber org, which is how a managed package ships configuration that customers should not change. See [[18.12 - Package Design - Unlocked, Managed, 1GP vs 2GP]].

## Custom metadata versus the alternatives

| Need | Use |
| --- | --- |
| Configuration deployed with code | **Custom Metadata** |
| Per-user or per-profile value | Hierarchy Custom Setting |
| Values users edit routinely in production | A custom object |
| Secrets and credentials | Named Credentials |
| Cross-transaction cache of computed data | Platform Cache |
| High-volume records | A custom object |

The default is Custom Metadata, and the exceptions are narrow. Most configuration that lives in a Custom Setting in an older org would be better as Custom Metadata today.

## Practical guidance

**Default to Custom Metadata for configuration.** No query cost, deployable, testable.

**Use metadata relationships** for object and field references, so a rename breaks the deployment rather than production.

**Cache in a static** within a transaction.

**Inject an override for tests** rather than depending on deployed records.

**Reference thresholds from formulas and validation rules** so one value serves every layer.

**Never store secrets** in custom metadata.

**Use protected types** for packaged configuration subscribers should not edit.

**Do not write from Apex** as a routine path — deployments are slow and rate-limited.
