## Reverse Proxy

### What It Is

A reverse proxy sits in front of backend servers and forwards client requests to them. Clients talk to the proxy; they don't know which backend server actually handles the request.

```
Client ──request──→ [Reverse Proxy] ──forward──→ [Backend Server]
Client ←─response── [Reverse Proxy] ←─response── [Backend Server]
```

"Reverse" distinguishes it from a forward proxy (which sits in front of clients and proxies their outbound requests — e.g., a corporate web filter).

### Why It Exists

A reverse proxy centralizes cross-cutting concerns so backends don't have to implement them:

- **SSL termination** — decrypt HTTPS once, forward HTTP internally
- **Caching** — serve cached responses without hitting the backend
- **Compression** — gzip responses at the proxy layer
- **Request buffering** — absorb slow clients so backends aren't tied up
- **Access logging** — centralized log of all incoming requests
- **Static file serving** — serve static assets directly, skip backend entirely

### Common Reverse Proxies

**Nginx:** The most widely deployed. Excels at static file serving, SSL termination, and L7 proxying. Configuration is declarative and powerful.

**HAProxy:** Best-in-class for high-throughput TCP/HTTP load balancing. More focused than Nginx, extremely performant.

**Envoy:** Modern, built for microservices. Dynamic configuration, rich observability, the backbone of Istio service mesh.

**Caddy:** Modern, automatic HTTPS, simple config. Good for smaller deployments.

## API Gateway

### What It Is

An API gateway is a specialized reverse proxy for APIs. It's the single entry point for all client-to-service communication and handles API-specific concerns.

```
Mobile App  ──→
Web Browser ──→  [API Gateway]  ──→  [User Service]
3rd Party   ──→                 ──→  [Order Service]
                                ──→  [Product Service]
```

### What an API Gateway Does

**Request routing:** Route `/api/users/*` to User Service, `/api/orders/*` to Order Service. One client endpoint, many backend services.

**Authentication:** Validate JWT tokens or API keys before requests reach services. Services don't need to implement auth themselves.

**Rate limiting:** Enforce per-client or per-endpoint request limits. Protects backends from abuse.

**Request transformation:** Modify request headers, translate between REST and gRPC, aggregate multiple backend calls into one client response.

**Response transformation:** Strip internal fields from responses, add standard headers (CORS, caching), aggregate partial responses.

**SSL termination:** Handle TLS at the gateway; backends use plain HTTP internally.

**Logging and tracing:** Inject trace IDs, log all requests at the entry point.

**API versioning:** Route `/v1/*` to old service, `/v2/*` to new service.

### API Gateway vs Load Balancer

| Feature | Load Balancer | API Gateway |
|---|---|---|
| Primary purpose | Distribute traffic | API management |
| Routing logic | IP/port/path-based | Path, header, auth-aware |
| Auth enforcement | ❌ | ✅ |
| Rate limiting | Basic (if any) | Per-client, per-endpoint |
| Request transformation | ❌ | ✅ |
| Protocols | TCP, HTTP | HTTP, gRPC, WebSocket |
| Typical position | In front of a service tier | In front of all services |

In practice, you often have both: an L4/L7 load balancer in front of your API gateway cluster, and the API gateway in front of your services.

```
Client → [Load Balancer] → [API Gateway cluster] → [Services]
```

## The Backend for Frontend (BFF) Pattern

As client types diversify (mobile, web, TV, IoT), different clients need different API shapes.

**Problem:** A generic API optimized for one client is inefficient for others.
- Mobile needs small payloads, fewer fields
- Web needs aggregated data (fewer round trips)
- Third-party needs versioned stable APIs

**Solution:** A separate API gateway (BFF) per client type, each tailored to that client's needs.

```
[Mobile App]      → [Mobile BFF]     → [Backend Services]
[Web Browser]     → [Web BFF]        → [Backend Services]
[Third-Party API] → [Public API GW]  → [Backend Services]
```

Each BFF handles its client's aggregation, transformation, and protocol needs. Backends remain generic.

**Tradeoff:** More gateways to maintain, but each is simple and focused.

## Common API Gateway Patterns

### Authentication Enforcement

```
Request arrives at gateway
→ Extract JWT from Authorization header
→ Validate signature and expiry
→ Extract user_id and roles from claims
→ Inject as headers (X-User-Id, X-User-Roles) to backend
Backend trusts these headers (internal network only)
```

Services don't implement auth — they just read the injected headers.

### Request Aggregation (Gateway Aggregation)

One client request triggers multiple backend calls; the gateway aggregates them.

```
GET /dashboard
→ Gateway calls User Service   → { name, email }
→ Gateway calls Order Service  → { recent_orders }
→ Gateway calls Stats Service  → { summary_metrics }
→ Gateway merges and returns single response
```

Reduces client-side round trips. Adds gateway complexity.

### Circuit Breaker at the Gateway

Gateway applies circuit breaker pattern per backend service. If Order Service is failing, gateway fails fast for order-related requests without waiting for timeout, and can return a cached or degraded response.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Gateway crashes | All traffic lost | Multiple gateway instances behind LB |
| Gateway becomes bottleneck | All services affected | Horizontal scaling of gateway |
| Backend service down | Gateway returns 502/504 | Circuit breaker, fallback response |
| Auth service down | All requests blocked if gateway depends on it | Cache auth results, fail open vs fail closed decision |
| Config error in gateway | Wrong routing, broken auth | Canary deployments of gateway config |

**The gateway as a chokepoint:** The gateway handles all traffic. Performance issues or bugs in the gateway affect every service. Keep the gateway thin — put business logic in services, not the gateway.

## Real Production Examples

- **AWS API Gateway:** Managed, serverless-friendly, integrates with Lambda, Cognito auth. Expensive at high volume.
- **Kong:** Open-source, plugin-based (auth, rate limiting, tracing). Can be self-hosted or managed.
- **Apigee (Google):** Enterprise-focused, strong analytics and developer portal.
- **Nginx + Lua / OpenResty:** Custom gateway logic in Lua scripts on top of Nginx. Very high performance.
- **Envoy + Istio:** Service mesh approach — gateway and per-service sidecar proxies, centrally controlled.
