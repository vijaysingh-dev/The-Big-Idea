# Prompt Builder and Prompt Templates

## What it is

A prompt template is a **reusable, grounded instruction** to a language model, stored as metadata, with merge fields resolving against CRM data at invocation.

```
Setup → Prompt Builder → New Prompt Template

Type:              Field Generation
Name:              Claim_Resolution_Summary
Object:            Warranty_Claim__c
Target Field:      Resolution_Summary__c
Model:             the org's configured model
```

**It deploys like any metadata**, versions in source control, and is invoked from a flow, from Apex, from a Lightning component, or by a field's generation action.

## The template types

```
Sales Email          drafts an email, grounded on a record
Field Generation     produces a value for a specific field
Record Summary       summarizes a record and its related data
Flex                 general purpose, invoked from anywhere
```

**Flex is the one a developer uses most**, because it takes arbitrary inputs and is callable from Apex.

## Writing the prompt

```
You are a service coordinator at Northwind Industrial, a manufacturer of
industrial presses. Write a brief, factual summary of this warranty claim
for the customer's account manager.

Claim: {!$Input:Warranty_Claim__c.Claim_Number__c}
Machine: {!$Input:Warranty_Claim__c.Asset__r.Name} (serial {!$Input:Warranty_Claim__c.Asset__r.SerialNumber})
Reported fault: {!$Input:Warranty_Claim__c.Fault_Description__c}
Status: {!$Input:Warranty_Claim__c.Status__c}
Claimed: {!$Input:Warranty_Claim__c.Claim_Amount__c}
Approved: {!$Input:Warranty_Claim__c.Approved_Amount__c}

Coverage context:
{!$Flow:Claim_Coverage_Context}

Write no more than four sentences. State only what the data above supports.
If the approved amount differs from the claimed amount, say so and give the
reason from the coverage context. Do not speculate about cause.
```

**Four things this does deliberately:**

**Establishes a role and a context.** "Service coordinator at a press manufacturer" constrains vocabulary and tone.

**Grounds on specific fields**, named rather than dumped.

**Grounds on computed context** through a flow, which is where anything requiring logic goes.

**Constrains the output** — length, scope, and an explicit instruction not to speculate.

**That last line matters more than it looks.** Without it, a model given a claim with a null approved amount will produce a plausible explanation for a number that does not exist.

## Grounding sources

```
Merge fields               record fields, including cross-object traversal
Related lists              child records
Flow                       anything a flow can compute or retrieve
Apex                       anything Apex can compute
Data Cloud                 unified profile attributes and Calculated Insights
Knowledge retrieval        semantically relevant articles
```

**Grounding through a flow** is the common pattern for anything needing logic:

```
Flow: Claim_Coverage_Context
    Input:  claimId
    Get Records: Machine_Coverage__c for the claim's asset, active contracts
    Get Records: the last three claims on the same asset
    Assign:  a formatted text summary
    Output:  coverageContext (Text)
```

**The flow returns text**, which the prompt embeds. Structuring that text well is part of the prompt engineering — a well-labelled block reads better to the model than a raw dump.

**Grounding through Apex** where the retrieval is complex:

```java
public with sharing class ClaimGroundingService {

    @InvocableMethod(label='Get Claim Coverage Context')
    public static List<String> getContext(List<Id> claimIds) {
        List<String> contexts = new List<String>();

        for (Id claimId : claimIds) {
            Machine_Coverage__c coverage = CoverageSelector.activeForClaim(claimId);
            List<Warranty_Claim__c> history = ClaimSelector.recentForSameAsset(claimId, 3);

            // formatting for a model, not for a screen: labelled, compact, unambiguous
            contexts.add(String.format(
                'Coverage level: {0}\n'
                + 'Coverage limit: {1}\n'
                + 'Coverage ends: {2}\n'
                + 'Prior claims on this machine (last 3): {3}',
                new List<Object>{
                    coverage?.Coverage_Level__c ?? 'None',
                    coverage?.Coverage_Limit__c ?? 0,
                    coverage?.Coverage_End_Date__c ?? 'n/a',
                    summarizeHistory(history)
                }
            ));
        }
        return contexts;
    }
}
```

**Formatting for a model is not the same as formatting for a screen.** Labelled, compact, and explicit about missing values — `'Coverage level: None'` is better than an empty string, because it tells the model the absence is known rather than unavailable.

## Invoking from Apex

```java
public with sharing class ClaimSummaryService {

    public static String generateSummary(Id claimId) {
        ConnectApi.EinsteinPromptTemplateGenerationsInput input =
            new ConnectApi.EinsteinPromptTemplateGenerationsInput();

        ConnectApi.WrappedValue claimValue = new ConnectApi.WrappedValue();
        claimValue.value = claimId;

        input.inputParams = new Map<String, ConnectApi.WrappedValue>{
            'Input:Warranty_Claim__c' => claimValue
        };

        ConnectApi.EinsteinLlmAdditionalConfigInput config =
            new ConnectApi.EinsteinLlmAdditionalConfigInput();
        config.applicationName = 'ClaimSummary';
        input.additionalConfig = config;

        ConnectApi.EinsteinPromptTemplateGenerationsRepresentation response =
            ConnectApi.EinsteinLLM.generateMessagesForPromptTemplate(
                'Claim_Resolution_Summary', input
            );

        return response.generations[0].text;
    }
}
```

**`applicationName`** appears in the audit trail, which is what makes usage traceable per feature. See [[24.5 - Einstein Trust Layer]].

**This is a callout in effect**, so the usual rules apply — it cannot follow DML in the same transaction, and it belongs in a Queueable when triggered by a save. See [[13.14 - Apex Callouts]].

## Prompt design that works

The practices that produce reliable output, rather than occasionally impressive output.

**Be specific about the role and the audience.**

```
Weak:    "Summarize this claim."
Better:  "Write a summary for the customer's account manager, who needs to
          know whether to expect a complaint."
```

**Constrain length explicitly.** "Brief" means nothing; "no more than four sentences" means something.

**Say what not to do.**

```
Do not speculate about the cause of the fault.
Do not mention internal margin or cost figures.
Do not promise a resolution date.
```

**Negative instructions work**, and they are how a model is kept out of territory it should not enter.

**Handle missing data explicitly.**

```
If the approved amount is blank, state that the claim is still under review
rather than reporting an amount.
```

**Without this, a null field produces an invention.** It is the single most common source of a confidently wrong generated output.

**Give an example** where the format matters:

```
Format the response as:

Status: <one line>
Outcome: <one line>
Next step: <one line>
```

**Ask for structure when the output will be parsed:**

```
Respond with only a JSON object, no preamble and no markdown fences:
{"summary": "...", "sentiment": "positive|neutral|negative", "escalate": true|false}
```

Then parse defensively:

```java
private static ClaimAssessment parse(String response) {
    try {
        String cleaned = response.replaceAll('```json|```', '').trim();
        return (ClaimAssessment) JSON.deserialize(cleaned, ClaimAssessment.class);
    } catch (Exception e) {
        // a model can return something unparseable regardless of the instruction
        AutomationLogger.logWarning('ClaimAssessment', 'Unparseable response: ' + response);
        return ClaimAssessment.unavailable();
    }
}
```

**Always assume the response may not match the requested format.** The instruction reduces the probability; it does not eliminate it.

## Testing a prompt

Prompt Builder has a preview, which runs the template against a real record and shows both the resolved prompt and the response.

**Preview against the awkward cases**, not the clean one:

```
A claim with a null approved amount
A claim with no coverage at all
A claim with a very long fault description
A claim with a fault description in another language
A claim whose asset was deleted
A claim with characters that might affect the prompt structure
```

**The resolved prompt is the more useful half of the preview.** Seeing what the model actually received explains most unexpected output — a merge field that resolved to blank, a flow that returned nothing, a related list that was empty.

**There is no automated evaluation**, which is the substantive gap. Building one means a set of representative records, a documented expectation per record, and a periodic manual review. See [[24.7 - Designing AI Features Responsibly on CRM Data]].

## Where the output goes

The design decision that determines the risk.

**Displayed for review** — a draft the user edits before sending. Low risk, and the right default.

**Written to a field** — a summary stored on the record. Medium risk, because it becomes data others rely on.

**Driving an action** — a generated assessment that routes or escalates. High risk, and it needs a confidence gate and a fallback.

```java
ClaimAssessment assessment = ClaimAssessmentService.assess(claimId);

// a generated assessment routes only where it is unambiguous; anything else
// goes to a human queue rather than being acted on
if (assessment.isAvailable && assessment.confidence == 'high') {
    ClaimRoutingService.route(claimId, assessment.suggestedQueue);
} else {
    ClaimRoutingService.routeToManualReview(claimId);
}
```

**The fallback is not optional.** A prompt that fails, times out, or returns something unparseable must leave the record in a defined state.

## Versioning and deployment

Prompt templates are metadata:

```
force-app/main/default/genAiPromptTemplates/Claim_Resolution_Summary.genAiPromptTemplate-meta.xml
```

**They deploy, version, and diff** like anything else, which means a prompt change goes through review rather than being edited in production.

**Reviewing a prompt diff is a genuine review activity** — a changed instruction alters behaviour as much as a code change does, and it has no test coverage.

## Cost

Generative features are consumption-priced, and the units are prompt and response length.

**Design consequences:**

**Do not invoke on every save.** A prompt triggered by a record-triggered flow on a high-volume object is expensive and usually unnecessary.

**Invoke on demand**, from a button, where the user decides they want it.

**Ground with what is needed**, not everything available. A prompt embedding fifty fields costs more and produces worse output than one embedding eight relevant ones.

**Cache where the input has not changed.** A summary regenerated on every page load is waste.

## Practical guidance

**Ground specifically.** Named fields and computed context, not a dump.

**Constrain the output** — length, scope, and explicit prohibitions.

**Handle missing data in the prompt**, or the model invents.

**Format grounding for a model** — labelled, compact, explicit about absences.

**Request JSON for parseable output**, and parse defensively anyway.

**Preview against the awkward records**, and read the resolved prompt.

**Default to displaying for review** rather than acting automatically.

**Always have a fallback** for failure and low confidence.

**Review prompt diffs like code.**

**Invoke on demand, not on every save.**
