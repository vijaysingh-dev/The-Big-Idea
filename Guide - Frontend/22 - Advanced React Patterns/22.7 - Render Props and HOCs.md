# Render Props and HOCs

Two pre-hooks patterns for sharing stateful logic between components. Hooks replaced both for most purposes, but they remain everywhere in existing code and each still has a narrow legitimate use.

## Higher-order components

A function taking a component and returning a wrapped component ([[02.5 - Higher Order Functions and Callbacks]]):

```jsx
function withAuth(Component) {
  function WithAuth(props) {
    const { user, loading } = useAuth();
    if (loading) return <Spinner />;
    if (!user) return <Redirect to="/login" />;
    return <Component {...props} user={user} />;
  }

  WithAuth.displayName = `withAuth(${Component.displayName ?? Component.name})`;
  return WithAuth;
}

const Dashboard = withAuth(BaseDashboard);
```

You will recognize the shape from `connect()` in older Redux, `withRouter`, `withStyles` and `React.memo` itself.

### The problems

**Prop origin is invisible.** A component receiving `user`, `dispatch`, `classes` and `history` gives no indication which wrapper supplied each. Tracing a prop means reading every HOC in the chain.

**Naming collisions.** Two HOCs both injecting `data` silently conflict, and the outer one wins.

**Wrapper hell.** `withAuth(withRouter(withTheme(connect(...)(Component))))` produces a DevTools tree several levels deep for one component.

**Static methods and refs are lost** unless explicitly hoisted (`hoist-non-react-statics`) and forwarded.

**Typing is painful.** Expressing "removes these props, adds those" in TypeScript is genuinely awkward.

Hooks solve all of these — the source of a value is the hook call, visible on the line where it is used ([[17.11 - Custom Hooks]]).

### Where HOCs still make sense

**Wrapping every instance with behavior**, where the wrapper must sit outside the component:

```jsx
const SafeWidget = withErrorBoundary(Widget);
const Instrumented = withProfiler(Chart);
```

A hook cannot wrap its own component in an error boundary or a Suspense boundary — those must be ancestors ([[22.1 - Error Boundaries]]).

**Library integration where you do not control the component**, such as Sentry's `withProfiler` or an analytics wrapper applied at the route level.

`React.memo`, `forwardRef` and `lazy` are all HOCs, which is a reminder the pattern is not obsolete — just narrow.

## Render props

A prop whose value is a function returning JSX:

```jsx
function MousePosition({ children }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  useEffect(() => {
    const handler = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener("pointermove", handler);
    return () => window.removeEventListener("pointermove", handler);
  }, []);

  return children(pos);
}

<MousePosition>
  {({ x, y }) => <div>Cursor at {x}, {y}</div>}
</MousePosition>
```

The prop is conventionally `children`, though any name works (`render={...}`).

### The problems

**Nesting.** Three render props produce a pyramid:

```jsx
<Auth>
  {user => (
    <Theme>
      {theme => (
        <Data userId={user.id}>
          {data => <View data={data} theme={theme} />}
        </Data>
      )}
    </Theme>
  )}
</Auth>
```

The hooks version is four flat lines.

**A new function every render**, which breaks memoization on the child unless wrapped in `useCallback` ([[19.2 - React.memo and Memoization Strategy]]).

**Extra component instances** in the tree for what is essentially a value.

### Where render props still make sense

**When the parent must control rendering** — measuring, virtualizing, or deciding what to render based on internal state:

```jsx
<VirtualList items={items} height={400}>
  {(item, index) => <Row item={item} index={index} />}
</VirtualList>
```

The list decides *which* items render; the caller decides *how*. A hook cannot express that — the rendering decision belongs to the parent.

This is why virtualization, drag-and-drop, autosizing and chart libraries still expose render props ([[19.5 - Virtualization and Windowing]]).

**When the value depends on DOM measurement** the parent performs.

**Headless components generally** — though most modern headless libraries expose hooks and compound components instead ([[22.6 - Compound Components]]).

## The hooks equivalent

```jsx
function useMousePosition() {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  useEffect(() => {
    const handler = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener("pointermove", handler);
    return () => window.removeEventListener("pointermove", handler);
  }, []);

  return pos;
}

function Component() {
  const { x, y } = useMousePosition();
  const user = useAuth();
  const theme = useTheme();
  const data = useData(user.id);
}
```

Flat, explicit about where each value comes from, no wrapper components, composes without nesting, and types inferred naturally.

## Reading legacy code

Recognizing these matters because large parts of the ecosystem predate hooks:

```jsx
connect(mapStateToProps, mapDispatchToProps)(Component)   // Redux HOC
withRouter(Component)                                      // React Router v5
<Query>{({ data }) => ...}</Query>                          // Apollo render prop
<Formik>{({ values }) => ...}</Formik>                      // Formik render prop
<Downshift>{...}</Downshift>                                // combobox render prop
```

Migration is usually straightforward: the HOC or render-prop component almost always has a hook equivalent (`useSelector`, `useNavigate`, `useQuery`, `useFormikContext`).

## Choosing

```
Need a value or behavior?               → custom hook
Parent must control what renders?       → render prop
Must wrap the component from outside?   → HOC
Multiple coordinated parts?             → compound components
```

Default to hooks. The other three are for the cases hooks structurally cannot cover.

## How senior engineers actually use this

**They write custom hooks** for new shared logic, without exception.

**They keep HOCs for boundary-wrapping** — error boundaries, Suspense, profiling — where an ancestor is required.

**They accept render props from libraries** where the library controls rendering, and do not fight the API.

**They migrate incrementally**, converting a HOC to a hook when they are already touching the file.

**They set `displayName`** on any HOC they do write, so DevTools remains readable.

## Common pitfalls

- Writing new HOCs for logic a hook would cover.
- Prop collisions between stacked HOCs.
- Losing refs and statics through a HOC without forwarding and hoisting.
- Inline render-prop functions defeating memoization.
- Deep render-prop nesting where hooks would be flat.
- Missing `displayName`, producing anonymous components in DevTools.

## Interview angle

"What are render props and HOCs, and why did hooks replace them" is a good history question. Cover both shapes, then the specific problems — HOCs hide prop origin, collide, and nest; render props nest and create new function identities — and how hooks solve each by making the source of every value visible at the call site. The part that separates a strong answer is naming what hooks *cannot* do: wrap a component in a boundary from outside (HOC) and let a parent control what renders (render prop). Both patterns survive for exactly those reasons.
