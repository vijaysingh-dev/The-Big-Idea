# What Agents Actually Are

## The Hype vs Reality

The word "agent" is overloaded. Marketing says: "autonomous AI that handles complex tasks end-to-end." Reality is more nuanced.

A useful working definition:

> **An agent is a system where an LLM controls the flow of execution** — deciding what to do next, calling tools, observing results, and repeating until a goal is achieved or a stopping condition is met.

The key distinction from a simple RAG system: the LLM is making **control flow decisions**, not just generating text.

---

## The Spectrum from Pipeline to Agent

This isn't binary — it's a spectrum:

```
More Deterministic                          More Agentic
─────────────────────────────────────────────────────────
Single LLM call     →    RAG pipeline    →    ReAct agent    →    Autonomous agent
(no routing)             (fixed steps)        (tool loops)         (open-ended planning)

"Summarize this"    →    "Answer this"    →    "Research X"   →    "Complete this task"
                         from documents        using tools          however needed
```

Most production "agents" sit in the middle — they have some fixed structure with bounded LLM-controlled loops.

---

## What Makes Something an Agent

Three properties separate agents from pipelines:

### 1. Tool Use

The agent can call external functions — search, code execution, database queries, API calls — and incorporate results into its reasoning.

```python
tools = [
    {"name": "web_search", "description": "Search the web for current information"},
    {"name": "run_python", "description": "Execute Python code and return output"},
    {"name": "read_file",  "description": "Read contents of a file"},
]
```

### 2. Observation-Action Loop

The agent acts, observes the result, and uses that result to decide the next action — repeating until done.

```
Thought: I need to find Apple's revenue
Action: web_search("Apple Q3 2024 revenue")
Observation: "Apple reported $85.8B revenue in Q3 2024"
Thought: Now I have the number. I can answer.
Action: [return answer]
```

### 3. Dynamic Control Flow

The agent decides whether to continue, which tool to call next, or when to stop — not a fixed program.

---

## The ReAct Pattern

The foundational agent architecture. Interleaves Reasoning and Acting:

```
Loop:
  1. Thought: Reason about the current state
  2. Action:  Choose a tool to call
  3. Observation: Receive tool result
  4. Repeat until: Thought concludes answer is ready
```

Implementation via tool calling:

```python
def run_react_agent(user_query, tools, llm, max_steps=10):
    messages = [{"role": "user", "content": user_query}]
    
    for step in range(max_steps):
        # LLM decides: answer now, or call a tool?
        response = llm.call(messages=messages, tools=tools)
        messages.append(response)
        
        if not response.tool_calls:
            # No tool call → agent is done
            return response.content
        
        # Execute tool calls
        for call in response.tool_calls:
            result = execute_tool(call.name, call.arguments)
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(result)
            })
    
    # Hit step limit
    return "Could not complete task within step limit"
```

## Where Agents Are Actually Useful

The honest answer: agents are valuable for a narrower set of tasks than the hype suggests.

### Genuinely Good Use Cases

**1. Research and information synthesis** Multi-step search + synthesis from multiple sources. Requires dynamic tool selection — no fixed query pipeline covers all cases.

- "Research the competitive landscape for X and write a summary"

**2. Code generation and debugging** Generate code → execute → observe error → fix → repeat. The loop is natural.

- "Write a Python script that scrapes X, then test it and fix any errors"

**3. Data analysis tasks** Generate analysis code → run on data → interpret results → generate follow-up analysis.

- "Analyze this CSV and identify the top 3 insights"

**4. Task automation with unpredictable steps** Fill out form A, then depending on the result, either do B or C.

- Workflow steps that depend on intermediate results

### Where Agents Fail / Are Overkill

**❌ Simple Q&A**: Use RAG. Agents add latency and cost for no benefit.

**❌ Well-defined workflows**: If the steps are always the same, use a pipeline. Agents add unnecessary non-determinism.

**❌ High-stakes single-shot decisions**: Agents make mistakes in loops; errors compound. Don't use agents where one wrong step causes irreversible harm.

**❌ When latency matters**: An agent with 5 tool calls at 2s each = 10s minimum. Simple RAG can answer in 0.5s.

---

## The Cost Calculus

Agents are expensive. Each tool call = one LLM round trip:

```
Simple RAG:
  1 embedding call (fast, cheap)
  1 LLM call (e.g., $0.002)
  Total: ~$0.003, ~1.5s

5-step ReAct agent:
  5+ LLM calls (each with growing context)
  Multiple tool calls (search, code execution)
  Total: ~$0.05–0.20, ~10–30s
```

**Rule**: Only use agents when the task genuinely requires it and the user is willing to wait and pay for it.

---

## The Reliability Problem

Agents compound errors. If each step has 90% reliability:

```
1-step pipeline: 90% success
5-step agent:    0.9^5 = 59% success
10-step agent:   0.9^10 = 35% success
```

Production agents must account for this through:

- Retry logic at each step
- Verification steps after important actions
- Human-in-the-loop for critical decisions
- Fallback to simpler behavior when confidence is low

---

## Agents vs Workflows: The Decision

```
Does the task have a predictable, fixed structure?
├── Yes → Use a pipeline / workflow (faster, cheaper, more reliable)
└── No

Does the task require dynamic tool selection?
├── No → Use RAG or simple chain
└── Yes

Is the user willing to wait 10–30 seconds?
├── No → Reconsider; pre-compute or simplify
└── Yes

Is the task recoverable if the agent makes a mistake?
├── No → Add human-in-the-loop interrupt
└── Yes → Agent is appropriate
```
