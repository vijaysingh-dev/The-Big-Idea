# Building an Event Loop From Scratch

#backend #python #asyncio #concurrency

> **In one line:** An event loop is a `while True` that asks the OS "which sockets are ready?", runs the callbacks waiting on those sockets, runs anything whose timer expired, and goes around again. That is the entire idea.

---

## The Idea

You have 10,000 connections. Almost all of them are idle at any moment. You want one thread to serve all of them.

The naive approach is to check each socket in turn — 10,000 checks, mostly finding nothing. Wasteful.

Instead you hand the whole list to the OS and say: *"here are 10,000 sockets, wake me when any of them has data."* The OS knows, because it is the thing receiving the packets. It wakes you with just the ready ones.

That call is `epoll` on Linux, `kqueue` on macOS/BSD, IOCP on Windows. Python wraps all of them in the `selectors` module.

The loop then is:

```
while running:
    timeout = time until the next scheduled timer
    events = selector.select(timeout)      # sleeps here — this is where waiting happens
    for each ready socket: queue its callback
    move expired timers into the ready queue
    run everything in the ready queue
```

Every async framework you have used — asyncio, Node.js, nginx, Redis, Go's runtime — is this loop plus quality-of-life features.

---

## Building It

We will build a working loop in four steps. By the end it runs a real TCP echo server with 1000 concurrent connections and no `asyncio` import.

### Step 1 — Selectors

Start with the OS-level part alone, no coroutines.

```python
import selectors, socket

sel = selectors.DefaultSelector()

def accept(sock):
    conn, addr = sock.accept()
    conn.setblocking(False)
    sel.register(conn, selectors.EVENT_READ, read)

def read(conn):
    data = conn.recv(1024)
    if data:
        conn.sendall(data)
    else:
        sel.unregister(conn)
        conn.close()

server = socket.socket()
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("localhost", 8080))
server.listen(128)
server.setblocking(False)
sel.register(server, selectors.EVENT_READ, accept)

while True:
    for key, _ in sel.select():
        key.data(key.fileobj)
```

That is a complete, working, single-threaded server handling thousands of connections. Twenty-five lines.

⚠️ **`setblocking(False)` is the load-bearing line.** Without it, `recv` waits until data arrives and the whole loop freezes. Non-blocking sockets return immediately, possibly with nothing, and the selector tells you when to try again.

The problem with this version is obvious as soon as logic gets real: every step is a separate function, and passing state between them means globals or dictionaries keyed by socket. This is callback hell. Coroutines exist to fix exactly this.

### Step 2 — Awaitables

An `await` expression needs an object that can suspend. The protocol is: an object with `__await__` returning a generator. Whatever that generator yields comes back to whoever is driving it.

```python
class Awaitable:
    def __init__(self, request):
        self.request = request

    def __await__(self):
        result = yield self.request     # hand the request out to the loop
        return result                   # the loop sends the answer back in
```

So `await something` means: "give this request to my driver, and pause until it sends me an answer."

Our loop understands four request types:

```python
def sleep(seconds):
    return Awaitable(("sleep", seconds))

def sock_accept(sock):
    return Awaitable(("read", sock))

def sock_recv(sock, n):
    return Awaitable(("read", sock, n))

def sock_send(sock, data):
    return Awaitable(("write", sock, data))
```

### Step 3 — The Task

A **Task** wraps a coroutine and steps it forward. This is the piece that connects coroutines to the loop.

```python
class Task:
    def __init__(self, coro, loop):
        self.coro = coro
        self.loop = loop
        self.result = None
        self.done = False

    def step(self, value=None, exc=None):
        try:
            if exc is not None:
                request = self.coro.throw(exc)
            else:
                request = self.coro.send(value)     # run until the next yield
        except StopIteration as e:
            self.result = e.value
            self.done = True
            return

        self.loop.handle(request, self)
```

`coro.send(value)` runs the coroutine until it yields, and returns what it yielded. When the coroutine finally returns, `send` raises `StopIteration` with the return value attached. That is the whole mechanism behind `await`.

### Step 4 — The loop

```python
import selectors, time, heapq
from collections import deque


class EventLoop:
    def __init__(self):
        self.selector = selectors.DefaultSelector()
        self.ready = deque()
        self.timers = []
        self.tasks = 0

    def create_task(self, coro):
        task = Task(coro, self)
        self.tasks += 1
        self.ready.append(lambda: task.step())
        return task

    def handle(self, request, task):
        kind = request[0]

        if kind == "sleep":
            when = time.monotonic() + request[1]
            heapq.heappush(self.timers, (when, next(self._ids), task))

        elif kind == "read":
            sock = request[1]
            self.selector.register(sock, selectors.EVENT_READ,
                                   ("read", task, request))

        elif kind == "write":
            sock = request[1]
            self.selector.register(sock, selectors.EVENT_WRITE,
                                   ("write", task, request))

    def run_until_complete(self, coro):
        main = self.create_task(coro)

        while not main.done:
            timeout = self._next_timeout()
            events = self.selector.select(timeout)

            for key, _ in events:
                kind, task, request = key.data
                self.selector.unregister(key.fileobj)
                self.ready.append(lambda t=task, k=kind, r=request:
                                  t.step(self._do_io(k, r)))

            now = time.monotonic()
            while self.timers and self.timers[0][0] <= now:
                _, _, task = heapq.heappop(self.timers)
                self.ready.append(lambda t=task: t.step())

            for _ in range(len(self.ready)):
                self.ready.popleft()()

        return main.result

    def _next_timeout(self):
        if self.ready:
            return 0                      # work waiting — do not sleep at all
        if self.timers:
            return max(0, self.timers[0][0] - time.monotonic())
        return None                       # nothing to do — sleep until I/O

    def _do_io(self, kind, request):
        if kind == "read":
            sock = request[1]
            return sock.accept() if len(request) == 2 else sock.recv(request[2])
        sock, data = request[1], request[2]
        return sock.send(data)
```

Three details in there are worth pausing on, because they are the same three details in real asyncio:

**The timeout calculation.** If work is already queued, timeout is 0 — do not sleep, there is work to do. If only timers are pending, sleep exactly until the earliest one. If nothing at all, sleep indefinitely until I/O arrives. This is why an idle async server uses 0% CPU.

**`for _ in range(len(self.ready))`.** It processes a snapshot of the queue. If a callback adds more work, that work runs on the *next* iteration, not this one. Without this, one callback that keeps rescheduling itself starves all I/O forever. CPython's `_run_once` does exactly this, for exactly this reason.

**Timers in a heap.** You need the earliest one in O(1) and insertion in O(log n). A sorted list would be O(n) to insert. With 100,000 pending timeouts that difference is the whole ballgame.

### Using it

```python
async def handle_client(conn, loop):
    while True:
        data = await sock_recv(conn, 1024)
        if not data:
            break
        await sock_send(conn, data)
    conn.close()


async def server(loop):
    sock = socket.socket()
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    sock.bind(("localhost", 8080))
    sock.listen(128)
    sock.setblocking(False)

    while True:
        conn, addr = await sock_accept(sock)
        conn.setblocking(False)
        loop.create_task(handle_client(conn, loop))


loop = EventLoop()
loop.run_until_complete(server(loop))
```

Sequential-looking code. One thread. Thousands of connections.

## How Real asyncio Differs

Your loop is the correct shape. Real asyncio adds the parts that make it survive production.

| Your loop | asyncio | Why |
|---|---|---|
| Awaitable yields a request tuple | Coroutines yield **Futures** | A Future is a shared placeholder — many things can wait on one result |
| Register/unregister the socket every read | Register once, keep a **transport** and **protocol** | Syscalls are not free at high rates |
| No cancellation | `task.cancel()` throws `CancelledError` into the coroutine | You need to stop things. See [[01.7 - Cancellation and Structured Concurrency]] |
| Exceptions lost if nobody looks | Warns loudly about never-retrieved exceptions | Silent failure is worse than a crash |
| No thread integration | `call_soon_threadsafe`, `run_in_executor` | Blocking code has to go somewhere. See [[01.8 - Offloading Work]] |
| Callbacks run immediately | `call_soon` queue with a fairness snapshot | Same idea as ours, more careful |
| One selector backend | Pluggable, plus `uvloop` on libuv | Performance |

The structure of CPython's `_run_once` in `Lib/asyncio/base_events.py` is:

```
1. Compute timeout from the timer heap and the ready queue
2. selector.select(timeout)
3. Turn ready file descriptors into callbacks on _ready
4. Move expired timers to _ready
5. Run exactly len(_ready) callbacks — a snapshot
```

Five steps. The same five you just wrote.

## In Production

### Why the shape matters for your services

Everything about how async services behave follows from this loop.

**One slow callback delays everything.** There is no preemption. A callback that takes 200ms means every other connection waits 200ms. This is the whole content of [[01.6 - The Blocking Call Problem]].

**Idle is free.** 50,000 idle WebSocket connections cost you memory for 50,000 small objects and nothing else. The loop is asleep inside `select()`. This is the entire reason async won for connection-heavy workloads.

**Loop lag is your best health signal.** Schedule a task that sleeps 100ms in a loop and measures how late it actually woke up. That number is how blocked your loop is, and it correlates with p99 better than CPU usage does.

```python
async def lag_monitor():
    while True:
        start = time.perf_counter()
        await asyncio.sleep(0.1)
        lag = time.perf_counter() - start - 0.1
        if lag > 0.05:
            log.warning("event loop lag", extra={"lag_ms": lag * 1000})
```

💡 Put this in every async service you run. It costs nothing and it is the first thing you will want during an incident.

**File descriptors are the real ceiling.** Every connection is a file descriptor. Default limits are often 1024.

```bash
ulimit -n                    # your limit
cat /proc/<pid>/limits       # what the process actually got
ls /proc/<pid>/fd | wc -l    # how many are in use right now
```

⚠️ Running out of file descriptors produces confusing errors — `OSError: [Errno 24] Too many open files` from a totally unrelated part of the code, or an accept loop that silently stops accepting. Set the limit high in your container spec and monitor usage.

### uvloop

`uvloop` replaces the loop implementation with one built on libuv, the C library behind Node.js. Same API, roughly 2–4x faster on raw throughput.

```python
import uvloop
uvloop.install()
```

Or just use `uvicorn[standard]`, which uses it automatically.

Whether that 2–4x reaches your users depends on where your time goes. If you are waiting 35ms on a database, making the loop faster changes very little. If you are proxying huge volumes of small messages, it matters a lot.
