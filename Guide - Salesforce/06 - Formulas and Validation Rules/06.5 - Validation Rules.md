# Validation Rules

## The inverted logic

A validation rule is a formula returning a boolean. **True means block the save.**

This inversion catches everyone at least once. You are not writing "the record is valid"; you are writing "the record is broken".

```
// Blocks saving when the approved amount exceeds the claim amount
Approved_Amount__c > Claim_Amount__c
```

## Where they run

Validation rules fire at **step 6 of the order of execution** — after before-triggers, before the record is saved. See [[07.13 - Order of Execution]].

Two consequences follow:

**A before-trigger can populate a field that satisfies a validation rule.** The trigger runs first.

**Validation rules apply to everything**: the user interface, the API, Data Loader, Apex, flows, and integrations. This is the point — a rule enforced at field level cannot be bypassed by an integration, unlike a page layout's required flag.

That universality is also the risk. A rule written for the UI blocks a data migration, a nightly integration, and a batch job, and the failure is often discovered at the worst moment.

## Error placement

A rule can display its message at the top of the page or **next to a specific field**. Field placement is meaningfully better — the user sees which field to fix rather than reading a message and hunting.

Always set it where the rule concerns one field.

## Common patterns

**Required conditionally on stage or status:**

```
AND(
  ISPICKVAL(Status__c, "Approved"),
  ISBLANK(Approved_Amount__c)
)
```

**Preventing backward movement:**

```
AND(
  ISCHANGED(Status__c),
  ISPICKVAL(PRIORVALUE(Status__c), "Closed"),
  NOT($Permission.Can_Reopen_Claims)
)
```

**Restricting who can change a field:**

```
AND(
  ISCHANGED(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims)
)
```

Using a custom permission rather than a profile name is what makes this maintainable. Profile names change, orgs accumulate profiles, and hardcoding one means the rule breaks the moment a new profile should also qualify. See [[03.4 - Permission Sets and Permission Set Groups]].

**Date consistency:**

```
AND(
  NOT(ISBLANK(Claim_Closed_Date__c)),
  Claim_Closed_Date__c < Claim_Date__c
)
```

**Format validation with regex:**

```
AND(
  NOT(ISBLANK(Serial_Number__c)),
  NOT(REGEX(Serial_Number__c, "[A-Z]{2}-[0-9]{4}-[A-Z]{2}"))
)
```

**Cross-object condition:**

```
AND(
  ISPICKVAL(Status__c, "Approved"),
  Asset__r.Warranty_End_Date__c < Claim_Date__c
)
```

Note the null guards. `NOT(ISBLANK(field))` before testing the field is not optional — without it, a null value produces a null comparison, and the behaviour is not what you expect.

## Bypass mechanisms

This is the design detail that separates rules that survive from rules that get deactivated in a crisis.

Every validation rule of consequence should have a deliberate bypass. Without one, a data migration, an emergency correction, or an integration that legitimately needs to write historical data forces someone to deactivate the rule for the whole org — and the redeployment is often forgotten.

**Custom permission bypass**, the cleanest option:

```
AND(
  ISCHANGED(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims),
  NOT($Permission.Bypass_Claim_Validation)
)
```

**Hierarchy custom setting bypass**, which can be toggled per user or per profile at runtime without a deployment:

```
AND(
  NOT($Setup.Validation_Bypass__c.Skip_Claim_Rules__c),
  ISPICKVAL(Status__c, "Approved"),
  ISBLANK(Approved_Amount__c)
)
```

The custom setting version is what makes a data migration survivable: enable the bypass for the migration user, load, disable it. No deactivation, no deployment, no forgetting.

The convention worth adopting org-wide: **one bypass setting, referenced by every validation rule**, so the mechanism is uniform and discoverable. See [[17.2 - Custom Settings]].

## Validation rules versus Apex validation

Both enforce invariants. The tradeoffs are real in both directions.

**Validation rules** are visible to administrators in Setup, deploy as metadata, need no test coverage, and apply automatically to every entry path. Their limits: no queries, no loops, no access to child records, and complex logic becomes unreadable.

**Apex validation** using `addError()` can query, aggregate, and express arbitrary logic. Its cost: it is invisible to administrators, needs tests, and someone debugging a blocked save will search Setup, find no validation rule, and be confused.

```java
public with sharing class ClaimValidationService {

    public static void validateAgainstCoverage(List<Warranty_Claim__c> claims) {
        Set<Id> assetIds = new Set<Id>();
        for (Warranty_Claim__c claim : claims) {
            if (claim.Asset__c != null) {
                assetIds.add(claim.Asset__c);
            }
        }
        if (assetIds.isEmpty()) {
            return;
        }

        Set<Id> coveredAssets = new Set<Id>();
        for (Machine_Coverage__c coverage : [
            SELECT Asset__c FROM Machine_Coverage__c
            WHERE Asset__c IN :assetIds
              AND Service_Contract__r.Status__c = 'Active'
              AND Coverage_End_Date__c >= TODAY
        ]) {
            coveredAssets.add(coverage.Asset__c);
        }

        for (Warranty_Claim__c claim : claims) {
            if (claim.Asset__c != null && !coveredAssets.contains(claim.Asset__c)) {
                claim.addError('Asset__c', 'This machine has no active service contract coverage.');
            }
        }
    }
}
```

That check is impossible declaratively — it needs a query across two objects with a date filter. The single query outside the loop is what makes it bulk-safe.

`addError(fieldName, message)` places the error on a specific field. `addError(message)` puts it at the record level.

The guidance most teams settle on: **declarative for anything expressible declaratively; Apex only where a query is genuinely needed.** And when Apex validation exists, document it prominently, because its invisibility is a real cost.

## Where validation rules cause trouble

**Lead conversion.** Rules on Account, Contact, and Opportunity all apply during conversion. A required field on Opportunity that the lead has no source for blocks conversion entirely, with an error users find baffling. Reviewing validation rules for conversion compatibility is a step most implementations skip. See [[04.4 - Lead Conversion]].

**Data migration.** Historical data rarely satisfies today's rules. This is what the bypass mechanism exists for.

**Integrations.** A rule requiring a field the source system does not have causes silent integration failures — records rejected, error logs nobody reads.

**Kanban and inline edit.** Dragging a card runs the full save pipeline. A validation rule requiring fields not on the card makes the Kanban view unusable. See [[04.14 - Path, Kanban and Sales Productivity]].

**Flows and automation.** A record-triggered flow updating a record hits validation rules. A rule that assumes a human is present will block automation.

**Bulk operations.** A rule failing on one record in an all-or-none DML aborts the entire batch. `Database.update(records, false)` handles it; a plain `update` statement does not. See [[10.2 - Database Class Methods and Partial Success]].

## Writing messages people can act on

The error message is user interface, and most are written as if nobody will read them.

```
Bad:  "Invalid data"
Bad:  "Validation failed for rule VR_Claim_007"
Bad:  "Approved amount error"

Good: "The approved amount cannot exceed the claimed amount."
Good: "Add a resolution before closing this case."
Good: "This machine has no active service contract. Check coverage before approving."
```

The test: does the message tell the user **what to do next**? Naming the rule, the field API name, or the technical condition does not.

## Limits and maintenance

- 500 active validation rules per object in most editions
- Each counts toward the object's 15 spanning relationship budget if it traverses
- Rules are evaluated on every save, so a hundred rules on a high-volume object is measurable CPU cost

Maintenance realities worth planning for:

**Rules accumulate and are never removed.** Nobody deletes a validation rule, because nobody is sure what depends on it. Naming rules by intent and using the description field is the only defence.

**Deactivated rules stay deactivated.** Someone turns one off for a migration and it is never turned back on. This is the strongest argument for the bypass pattern.

**Order is not controllable.** All rules evaluate, and all failures are shown together. There is no short-circuiting and no priority.

## Practical guidance

**Remember true means block.**

**Place errors on the field.**

**Guard against nulls explicitly.**

**Build a bypass into every rule of consequence**, using one org-wide mechanism.

**Use custom permissions, not profile names.**

**Write messages that say what to do.**

**Test rules against lead conversion, data loading, and Kanban** before go-live, not after.

**Prefer declarative unless a query is genuinely needed.**
