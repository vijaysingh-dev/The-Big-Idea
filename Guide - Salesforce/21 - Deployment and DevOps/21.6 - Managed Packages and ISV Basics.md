# Managed Packages and ISV Basics

## What changes when you distribute

An unlocked package is your own metadata, organized. A **managed package** is software installed in organizations you do not control, by people you cannot call, running on data you cannot see.

Three things follow from that, and they shape every decision:

**The namespace is permanent.**
**The `global` surface can never be removed.**
**A mistake is in every subscriber org until they upgrade.**

## The namespace

Registered once, to a Dev Hub, and it cannot be changed.

```
northwind__Warranty_Claim__c
northwind__ClaimApprovalService
northwind__claimList
```

Every component carries the prefix in a subscriber org, which is what prevents collisions with the subscriber's own metadata and with other packages.

**Choose carefully.** It appears in every API integration a subscriber builds, in every formula, and in every SOQL query they write against your objects.

```bash
sf org create scratch --definition-file config/project-scratch-def.json \
  --alias namespace-org --duration-days 30
# then register the namespace in that org and link it to the Dev Hub
```

## The global commitment

The rule that governs managed package development.

**A `global` member can never be removed or have its signature changed.** Doing so breaks every subscriber org referencing it, and Salesforce prevents the change at version creation.

```java
global with sharing class ClaimApprovalService {

    // permanent: this signature exists forever
    global static ApprovalResult approve(Set<Id> claimIds, Decimal amount) {
        return new ClaimApprovalServiceImpl().approve(claimIds, amount);
    }
}
```

```java
// public: invisible to subscribers, free to change
public with sharing class ClaimApprovalServiceImpl {
    public ApprovalResult approve(Set<Id> claimIds, Decimal amount) { }
}
```

**A thin global facade over a public implementation** is the standard shape. The contract holds; the implementation evolves.

Extending means adding an overload:

```java
global static ApprovalResult approve(Set<Id> claimIds, Decimal amount) {
    return approve(claimIds, amount, null);
}

global static ApprovalResult approve(Set<Id> claimIds, Decimal amount, String reason) { }
```

The same permanence applies to `global` interfaces, custom objects, and fields. **A field marked global in 1.0 is there forever.**

## Deprecation

```java
@deprecated
global static void approveClaim(Id claimId) {
    approve(new Set<Id>{ claimId }, null);
}
```

Marks a member as unsupported while leaving it callable. Subscribers see a warning; existing code keeps working.

**This is the only mechanism available** — there is no removal path for global members.

## What subscribers can and cannot see

```
Apex source            hidden
Apex debug logs        hidden by default
global members         visible and callable
public members         invisible
Custom objects         visible, prefixed
Protected metadata     invisible
Validation rules       visible, not editable
Layouts                editable by the subscriber
```

**A subscriber cannot debug your code**, which is why a package needs its own logging and its own diagnostics — you cannot ask them to send you a debug log of your internals.

**Subscriber Support Access** lets you log into their org, with permission, to troubleshoot:

```
The subscriber grants access → you log in from the License Management App
```

That is the primary support mechanism, and it depends on the subscriber granting it.

## Protected components

For configuration a subscriber should not change.

```
Protected Custom Metadata Type    invisible and uneditable in subscriber orgs
Protected Custom Setting          same
Protected Custom Permission
```

**Public custom metadata is how subscribers configure your package.** Protected is how you ship internal configuration — feature registries, rule tables, internal toggles.

Deciding which is which per type is a design decision, and getting it wrong is awkward: a protected type cannot later be made public without a workaround. See [[17.1 - Custom Metadata Types]].

## Namespace and limits

Two behaviours that favour managed packages.

**Governor limits are tracked per namespace:**

```
LIMIT_USAGE_FOR_NS|(default)|Number of SOQL queries: 47 out of 100
LIMIT_USAGE_FOR_NS|northwind|Number of SOQL queries: 12 out of 100
```

Your package's consumption is separate from the subscriber's — which is a genuine advantage and one of the few real benefits of the namespace beyond collision avoidance.

**Code coverage is tracked per namespace**, so your tests cover your code and theirs cover theirs.

**Your tests run during installation**, which makes a slow suite a slow install for every customer. That is a commercial reason to keep tests fast, beyond developer experience. See [[19.10 - Code Coverage, Quality and CI Gates]].

## The security review

Required for an AppExchange listing. It is thorough, takes weeks, and a rejection costs a release cycle.

What it checks:

```
[ ] Sharing keyword declared on every class
[ ] WITH USER_MODE, or explicit CRUD and FLS enforcement
[ ] No SOQL or SOSL injection — bind variables throughout
[ ] No hardcoded credentials, endpoints, or Ids
[ ] No cross-site scripting in components or Visualforce
[ ] CSRF protection on state-changing operations
[ ] Named Credentials for all callouts
[ ] No secrets in custom settings or metadata
[ ] Escaped output everywhere
[ ] No use of prohibited or deprecated APIs
```

**Run Salesforce Code Analyzer before submitting:**

```bash
sf scanner run --target force-app --severity-threshold 3
sf scanner run dfa --target force-app --projectdir force-app
```

The graph engine traces user-supplied data through several method calls into a dynamic query, which is the specific finding that most often causes a rejection and which PMD alone does not catch. See [[21.9 - Static Analysis, PMD and Code Review]].

**Treat these as development standards**, not as a pre-submission checklist. Retrofitting security enforcement across a codebase is a project.

## 1GP versus 2GP

**First-Generation Packaging** builds from a **packaging org** — components added through the UI, versions built there.

**Second-Generation Packaging** builds from **source control**, through the CLI.

| | 1GP | 2GP |
| --- | --- | --- |
| Source of truth | The packaging org | Source control |
| Build | Manual, in the UI | CLI, scriptable |
| Packages per namespace | One | Several |
| CI/CD | Difficult | Designed for it |
| Branch-based versioning | No | Yes |
| Status | Legacy | Current |

**2GP for new development.** The several-packages-per-namespace capability is the structural difference — an ISV can ship a core package plus optional modules rather than one monolith.

**1GP survives** in established products with years of subscriber history. Migration is possible and is a project, undertaken when there is another reason to restructure.

## Building and releasing

```bash
sf package create \
  --name "Northwind Warranty" \
  --package-type Managed \
  --path force-app/main \
  --target-dev-hub my-devhub

sf package version create \
  --package "Northwind Warranty" \
  --installation-key "install-key" \
  --code-coverage \
  --wait 60 \
  --target-dev-hub my-devhub

sf package version promote --package "Northwind Warranty@1.3.0-5"
```

**`--installation-key`** protects the package from being installed by anyone with the version Id. `--installation-key-bypass` removes that protection, which is fine for internal packages and not for distributed ones.

**Ancestry is mandatory** for a managed package with subscribers:

```json
{
  "path": "force-app/main",
  "package": "Northwind Warranty",
  "versionNumber": "1.4.0.NEXT",
  "ancestorVersion": "1.3.0.5"
}
```

Without it, a new version is not an upgrade — subscribers must uninstall first, losing their data.

## Upgrades and subscriber data

**Upgrades preserve data.** Fields are added, not replaced.

**Removing a field deletes subscriber data**, which is why it is heavily restricted and effectively impossible for global components.

**Removing a global Apex member is blocked** at version creation.

**Layout changes** may not apply if the subscriber customized the layout.

**Push upgrades** let you upgrade subscriber orgs without their action:

```bash
sf package version promote --package "Northwind Warranty@1.3.0-5"
# then schedule a push upgrade from the License Management App
```

Used for security patches and for retiring an old version. Pushing a breaking change to orgs that did not ask for it is a fast way to lose customers, so it is reserved for patches.

## Patch versions

For fixing a released version without shipping the next feature release.

```
1.3.0    the released version
1.3.1    a patch — bug fixes only, no new components
```

Patch versions cannot add components or change the schema. They exist so a critical bug can be fixed for subscribers on 1.3 while 1.4 is still in development.

## Licensing and the LMA

The **License Management App**, installed in your business org, tracks subscribers, licences, and versions.

```
Package subscribers          who has it installed
License records              seat counts and expiry
Version distribution         who is on which version
Subscriber support access    granted, for troubleshooting
```

**Licence enforcement** can be per seat or site-wide, and is defined per package. The platform enforces it — an unlicensed user cannot access your components.

**Version distribution is the operationally useful view.** Knowing that 40% of subscribers are on a version you want to retire shapes the deprecation plan.

## Testing across editions

A subscriber's org may be Professional, Enterprise, or Unlimited, and features differ.

```bash
sf org create scratch --edition Professional --alias pro-test --duration-days 1
sf package install --package "Northwind Warranty@1.3.0-5" --target-org pro-test --wait 20
sf apex run test --test-level RunLocalTests --target-org pro-test
```

**Professional Edition is the one that catches problems** — no record types in some configurations, limited API access, fewer custom objects, and features your package may assume.

Testing against the lowest edition you support is not optional, and it is frequently skipped.

## When a managed package is the right choice

**Yes when:** distributing to other companies, listing on AppExchange, protecting intellectual property, or needing per-subscriber licensing.

**No when:** the target is your own orgs — unlocked packages are simpler with none of the permanence constraints.

**A consulting deliverable** is the ambiguous case: unlocked if the client should be able to modify it, managed if the IP matters and you will maintain it.

## Practical guidance

**Choose the namespace carefully** — it is permanent and public.

**Keep the global surface small**, behind a facade.

**Use `@deprecated`**, since removal is impossible.

**Set ancestry**, or upgrades are not upgrades.

**Use protected metadata** for internal configuration, public for subscriber configuration.

**Run Code Analyzer including the graph engine** before submitting for review.

**Keep tests fast** — they run during every installation.

**Test on Professional Edition.**

**Reserve push upgrades for patches.**
