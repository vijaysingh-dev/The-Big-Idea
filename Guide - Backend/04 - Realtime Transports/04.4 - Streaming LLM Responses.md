# Streaming LLM Responses

#backend #realtime #sse #ai

> **In one line:** LLM streaming is SSE with three complications — cancellation is expensive to get wrong, tokens are not the unit users care about, and the whole response is only valid once it is complete.

---

## The Idea

An LLM generates one token at a time. Waiting for a 500-token answer takes 10–30 seconds. Streaming shows the first word in 300ms.

The perceived improvement is enormous and the mechanism is exactly [[04.2 - Server Sent Events]]:

```
data: {"choices":[{"delta":{"content":"The"}}]}

data: {"choices":[{"delta":{"content":" answer"}}]}

data: {"choices":[{"delta":{"content":" is"}}]}

data: [DONE]
```

💡 **This note exists because you are moving into AI engineering, and this is where your backend knowledge becomes directly valuable.** Everything in sections 01–04 applies: backpressure, cancellation, connection pools, timeouts, buffering. The people who build LLM serving infrastructure well are backend engineers who understand streaming, not ML researchers.

---

## What Makes It Different

### 1. Cancellation costs real money

A disconnected SSE client wastes a little CPU. A disconnected LLM stream wastes **GPU time**, which is the most expensive resource in the system.

```python
async def stream_completion(request: Request, prompt: str):
    generator = llm.stream(prompt)
    try:
        async for chunk in generator:
            if await request.is_disconnected():
                break
            yield format_sse(chunk)
    finally:
        await generator.aclose()          # tells the engine to abort
```

⚠️ **The `aclose()` matters enormously.** Without it, the inference engine keeps generating tokens for a request nobody will read. At scale, abandoned generations can consume a substantial fraction of your GPU capacity — and it is invisible, because those requests complete successfully from the engine's point of view.

vLLM handles this explicitly with an abort path. If you are proxying an LLM API, make sure your cancellation propagates all the way to the upstream request.

### 2. Time to first token is the metric

```
TTFT  (time to first token)     ← what users perceive as "fast"
TPOT  (time per output token)   ← what users perceive as "smooth"
Total latency                    ← what your dashboard probably measures
```

⚠️ **Total latency is nearly useless for streaming.** A response that starts in 200ms and takes 20 seconds feels fast. One that starts in 8 seconds and takes 9 feels broken. They have similar totals.

```python
ttft_seconds.observe(first_token_at - request_start)
tpot_seconds.observe((last_token_at - first_token_at) / token_count)
tokens_generated.observe(token_count)
```

The reason TTFT and TPOT are separate is architectural: inference has two phases with different characteristics.

```
Prefill:  process the whole prompt at once   → compute-bound, determines TTFT
Decode:   generate one token at a time       → memory-bandwidth-bound, determines TPOT
```

A long prompt hurts TTFT. A long output hurts total time. They are tuned differently, which is why the two metrics must be separate.

### 3. The response is only valid when complete

```
User asked for JSON.
Stream delivers: {"name": "Alice", "sco
Connection drops.
```

You have a partial response that is not valid JSON and cannot be used.

Approaches:

| Approach | Notes |
|---|---|
| Accumulate server-side, validate, then commit | You still stream for display, but persist only the complete result |
| Partial JSON parser | Renders progressively. Libraries exist. Complexity |
| Stream text, structure separately | Stream the prose, send structured data in a final event |

💡 **The last one is usually right for tool-calling and structured output.** Stream the human-readable part for perceived speed, then send the structured payload as a final `data:` event once it is complete and validated. The user sees immediate progress; your system never acts on partial structure.

### 4. Tokens are not the display unit

```
Tokens:  "The" " ans" "wer" " is" " 42"
Display: word by word, or character by character
```

A raw token stream renders unevenly — some tokens are whole words, some are fragments. Many products buffer slightly and emit at a smoother rate.

There is a real tradeoff: buffering to 20ms boundaries looks better and adds 20ms of latency. Worth measuring what your users actually prefer rather than assuming.

## The Server

```python
@app.post("/v1/chat/completions")
async def chat(request: Request, body: ChatRequest):
    if not body.stream:
        return await complete_sync(body)

    async def generate():
        request_id = f"chatcmpl-{uuid4().hex}"
        first_token_at = None
        token_count = 0

        generator = engine.generate(body.messages, request_id=request_id)
        try:
            async for chunk in generator:
                if first_token_at is None:
                    first_token_at = time.perf_counter()
                    ttft_seconds.observe(first_token_at - start)
                token_count += 1

                yield sse(
                    {
                        "id": request_id,
                        "object": "chat.completion.chunk",
                        "choices": [{"index": 0, "delta": {"content": chunk.text}}],
                    }
                )

            yield sse(
                {
                    "id": request_id,
                    "choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}],
                }
            )
            yield b"data: [DONE]\n\n"

        except asyncio.CancelledError:
            await engine.abort(request_id)
            raise
        finally:
            if token_count:
                tpot_seconds.observe(
                    (time.perf_counter() - first_token_at) / token_count
                )
            await generator.aclose()

    return StreamingResponse(
        generate(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

⚠️ **`except asyncio.CancelledError: await engine.abort(...); raise`** is the pattern that saves GPU time. Catch it, clean up, re-raise ([[01.7 - Cancellation and Structured Concurrency]]).

## Errors Mid-Stream

You have already sent `200 OK`. Something fails at token 300.

```python
try:
    async for chunk in generator:
        yield sse({"choices": [{"delta": {"content": chunk.text}}]})
except ModelError as e:
    yield sse({"error": {"message": str(e), "type": "server_error"}})
    yield b"data: [DONE]\n\n"
```

⚠️ **The client must handle an `error` field appearing in the stream**, because the HTTP status already said everything was fine. Every LLM API does this and clients that ignore it silently truncate.

Failure modes to handle:

| Failure | Response |
|---|---|
| Model out of memory | Error event, then `[DONE]` |
| Context length exceeded mid-generation | Error event with the specific type |
| Upstream provider error (if proxying) | Error event, consider fallback |
| Content filter triggered | Error event with `finish_reason: content_filter` |
| Timeout | Error event, abort upstream |

💡 **`finish_reason` is the field that tells the client why generation stopped**: `stop` (natural), `length` (hit max tokens), `content_filter`, `tool_calls`. A client that ignores it cannot distinguish "the model finished" from "we ran out of budget", which produces silently truncated answers.

## Proxying Another Provider

The common case: your service calls OpenAI or Anthropic and streams to your user.

```python
async def proxy_stream(messages: list[dict]):
    async with httpx.AsyncClient(timeout=httpx.Timeout(connect=5, read=120)) as client:
        async with client.stream(
            "POST",
            "https://api.provider.com/v1/messages",
            json={"messages": messages, "stream": True},
            headers={"Authorization": f"Bearer {key}"},
        ) as upstream:
            if upstream.status_code != 200:
                await upstream.aread()
                raise UpstreamError(upstream.status_code)

            async for line in upstream.aiter_lines():
                if line.startswith("data: "):
                    yield transform(line)
```

Three things that go wrong:

**The read timeout applies between chunks, not to the whole stream.** `read=120` means "no more than 120 seconds between tokens", which is what you want. A total timeout would kill long generations.

**Errors arrive after a 200.** Providers stream error events too. You must parse them and translate rather than passing them through blindly.

⚠️ **Cancellation must propagate upstream.** If your client disconnects and you do not close the upstream stream, you keep paying the provider for tokens nobody reads. `async with client.stream(...)` handles this when the generator is closed properly — but only if your `finally` actually runs.

## In Production

### The queue is where latency lives

At capacity, requests wait for GPU time.

```
TTFT = queue wait + prefill time
```

Under load, queue wait dominates completely. This is a backpressure problem, not an ML problem ([[01.11 - Backpressure Inside One Process]]).

```python
if inference_queue.qsize() > MAX_QUEUE:
    raise HTTPException(503, headers={"Retry-After": "5"})
```

⚠️ **Without admission control, an overloaded inference service accepts unlimited requests and every TTFT climbs into the tens of seconds.** Users abandon, retry, and add more load. That is a metastable failure ([[03.11 - Timeouts and Deadlines Across Hops]]) with an expensive resource at the bottom of it.

**Fast rejection is much better than slow acceptance here** — a user who gets a 503 in 50ms retries or waits; a user who waits 40 seconds for a first token has already left the tab open and moved on, while your GPU keeps working.

### Continuous batching changes the shape

Modern inference servers (vLLM, TGI) use **continuous batching**: requests join and leave the batch at token boundaries rather than waiting for a whole batch to finish.

Consequences for you:

- Throughput scales well with concurrency, up to a memory limit
- TPOT degrades gracefully as batch size grows — everyone gets slightly slower rather than some waiting
- **The real limit is KV cache memory**, not compute. Long contexts consume it fast
- Admission control should consider total context length, not request count

💡 **"How many concurrent requests can we handle" has no fixed answer** — it depends on prompt lengths, because KV cache is per-token. Ten requests with 100k-token contexts may exhaust memory that a hundred requests with 1k contexts would not. Your capacity metric should be tokens in flight, not requests in flight.

### Cost tracking

Every stream costs money, and you cannot know the total until it ends.

```python
finally:
    await record_usage(
        org_id=org_id,
        prompt_tokens=prompt_tokens,
        completion_tokens=token_count,
        model=model,
    )
```

⚠️ **Record usage in `finally`**, so a cancelled generation is still billed for the tokens actually produced. Otherwise users can cancel just before completion and consume resources for free — which becomes an abuse vector once anyone notices.

### Buffering breaks everything, again

All of [[04.3 - SSE in Production]] applies with more force. A buffered LLM stream is indistinguishable from a slow model, and the diagnosis usually starts by blaming the model.

**Test with `curl -N` through your full production path before blaming inference.**

## Codebase

**Repo:** `vllm-project/vllm`, `huggingface/text-generation-inference`, `openai/openai-python`

**Question to answer:** In vLLM, trace one streaming request from the HTTP endpoint to the GPU and back. Specifically: where does a client disconnect get detected, and what exactly happens to the in-flight generation? Then: how does continuous batching decide when a new request joins the running batch?

**Read, in order:**

1. `vllm/entrypoints/openai/api_server.py` — the FastAPI routes and the `StreamingResponse` construction
2. `vllm/entrypoints/openai/serving_chat.py` — **`chat_completion_stream_generator` is the core of this note.** Follow the token loop, the `finish_reason` logic, and the abort path
3. `vllm/engine/async_llm_engine.py` — `AsyncLLMEngine.generate` and `abort`. **This is where a disconnect becomes freed GPU memory**
4. `vllm/core/scheduler.py` — continuous batching. `_schedule_running` and `_schedule_prefills`. How requests join and leave, and how KV cache memory constrains admission
5. `openai/openai-python/src/openai/_streaming.py` — the client-side SSE parser. Small, and it shows exactly what a well-behaved client does with `[DONE]` and error events

💡 The vLLM scheduler is the most valuable reading here for someone with your background. **It is a queueing and admission control problem**, and it is solved with techniques you already know from sections 01 and 11 — bounded queues, preemption, and memory-based admission. Reading it makes the backend-to-AI bridge concrete: this is a systems problem, not an ML one.

**Part 1 — A realistic mock engine.** Configurable TTFT, TPOT, and a simulated KV cache budget where longer contexts consume more. It must support abort, and abort must actually free the budget.

Add failure injection: OOM, context length exceeded, mid-generation error.

**This mock is the reusable asset** — it lets you test everything without a GPU.

**Part 2 — The gateway.** OpenAI-compatible `/v1/chat/completions` with `stream: true`. Correct chunk format, `finish_reason`, `[DONE]`, and error events.

Then a resilient client that handles: normal completion, mid-stream error, truncation, and `finish_reason: length`.

**Part 3 — Measure cancellation waste.** 100 concurrent streams, 50 clients disconnecting halfway.

Version A: no cancellation propagation. Version B: proper abort.

Measure total engine-seconds consumed in both. **The difference is your wasted GPU spend**, and expressing it as a percentage is what makes the case for the ten lines of code.

Then extend it to the proxy case: disconnect your client and verify with `tcpdump` that the upstream connection actually closes.

**Part 4 — TTFT under load.** Sweep concurrency from 1 to 200 against the batched mock engine.

Chart TTFT p50 and p99, TPOT, and throughput in tokens per second against concurrency.

**Find the knee.** Then add admission control and chart again — you should see TTFT staying flat with a rising rejection rate instead of climbing without bound. **Put the two charts side by side.** This is the fast-failure-versus-slow-failure argument in its most expensive setting.

**Part 5 — Context length as the real limit.** Fixed concurrency of 20. Sweep average prompt length: 500, 2k, 8k, 32k, 128k tokens.

Show that the number of concurrent requests you can serve depends on context length, not request count. Then implement token-budget-based admission instead of request-count-based and show it handling the mix correctly.

**Part 6 — Structured output.** An endpoint that must return valid JSON.

Version A: stream raw tokens, client parses at the end. Kill the connection at 80% and show the client holding unusable partial JSON.

Version B: stream prose for display, accumulate and validate the structure server-side, emit it as a final event. Kill at 80% and show the client correctly reporting an incomplete result rather than acting on garbage.

**Part 7 — Wire it into Conduit.** Conduit phase 9 preview: a search endpoint that streams an answer over the SSE layer from [[04.3 - SSE in Production]]. Same connection infrastructure, new payload.

Add TTFT and TPOT metrics, token accounting per organisation, and admission control.

**Done when:**
- Your cancellation experiment quantifies wasted engine time as a percentage
- Upstream connections verifiably close on client disconnect
- Your TTFT-versus-load charts show the knee and the effect of admission control
- You have shown context length rather than request count being the binding limit
- The structured-output client never acts on incomplete data
- Conduit streams an answer over its existing SSE infrastructure
