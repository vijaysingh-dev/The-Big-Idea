# Immutable Data Patterns

React, Redux and every memoization mechanism in the ecosystem detect change by comparing references. Mutating an object in place leaves the reference identical, so nothing notices. Immutable updates — producing a new object for anything that changed — are therefore not a style preference but a correctness requirement.

## Mutating vs non-mutating array methods

| Mutates | Non-mutating equivalent |
| --- | --- |
| `push`, `unshift` | `[...arr, x]`, `[x, ...arr]` |
| `pop`, `shift` | `arr.slice(0, -1)`, `arr.slice(1)` |
| `splice` | `toSpliced`, or slice + spread |
| `sort` | `toSorted` |
| `reverse` | `toReversed` |
| `arr[i] = x` | `with(i, x)` |
| `fill`, `copyWithin` | `map` |

The ES2023 additions — `toSorted`, `toReversed`, `toSpliced`, `with` — are the modern answers and read far better than slice gymnastics.

```js
const updated = items.with(2, newItem);
const sorted = items.toSorted((a, b) => a.age - b.age);
const removed = items.toSpliced(index, 1);
```

Everything else — `map`, `filter`, `slice`, `concat`, `flat`, `flatMap` — was already non-mutating.

## The standard update recipes

```js
// Add
[...items, newItem];

// Remove by id
items.filter(i => i.id !== id);

// Update one item
items.map(i => i.id === id ? { ...i, done: true } : i);

// Update or insert
items.some(i => i.id === item.id)
  ? items.map(i => i.id === item.id ? item : i)
  : [...items, item];

// Move an item
const moved = [...items];
moved.splice(to, 0, ...moved.splice(from, 1));  // on a copy, so acceptable
```

The `map`-with-conditional pattern is the one to internalize. It replaces `findIndex` + `splice` and never mutates.

## Nested objects

Every level on the path to the change needs a new reference. Levels not on the path should keep their old reference — that is **structural sharing**, and it is what keeps memoization working.

```js
setState(s => ({
  ...s,
  user: {
    ...s.user,
    address: { ...s.user.address, city: "Delhi" },
  },
}));
```

`s.settings` is untouched here, so anything memoized on `s.settings` does not re-render. A deep clone would have broken that.

Three levels is about where this stops being pleasant, which is a signal about the state shape rather than the syntax.

## Nested arrays of objects

The awkward case:

```js
setBoard(board =>
  board.map((row, r) =>
    r !== rowIndex
      ? row
      : row.map((cell, c) => (c !== colIndex ? cell : { ...cell, value }))
  )
);
```

Note the early `row` returns — unchanged rows keep their identity, so a memoized `Row` component only re-renders the one that changed ([[19.2 - React.memo and Memoization Strategy]]). Writing `board.map(row => row.map(...))` without the guard would create new arrays for every row and defeat that.

## Immer

Immer lets you write mutating syntax and produces the correctly-shared immutable result. It works via a `Proxy` that records writes to a draft ([[08.3 - Proxy and Reflect]]).

```js
import { produce } from "immer";

const next = produce(state, draft => {
  draft.user.address.city = "Delhi";
  draft.items.push(newItem);
  draft.items[0].done = true;
});
```

Only the touched paths get new references; everything else is shared. Redux Toolkit builds this in, so reducers look mutating but are not ([[20.6 - Immer and Immutable Updates]]).

The tradeoffs: a small runtime cost, `Proxy` semantics that can surprise (drafts are not the original objects, so `instanceof` and reference equality inside the recipe behave differently), and the fact that returning a value *and* mutating the draft in the same recipe throws.

## Flatten instead of nesting

The best fix for deep updates is usually not better update syntax but a flatter state shape:

```js
// Deeply nested — painful to update
{ users: [{ id, posts: [{ id, comments: [...] }] }] }

// Normalized — every update is one level deep
{
  users: { byId: {}, allIds: [] },
  posts: { byId: {}, allIds: [] },
  comments: { byId: {}, allIds: [] },
}
```

Updating a comment now touches one entry in one map. This is normalization ([[20.7 - State Normalization]]) and it removes most of the need for deep-update helpers.

## Object.freeze in development

```js
const state = process.env.NODE_ENV === "development"
  ? deepFreeze(initialState)
  : initialState;
```

Freezing turns accidental mutation into a thrown error in strict mode instead of a silently missing re-render. Redux Toolkit does this automatically in development and disables it in production, where the cost would be real.

Remember `Object.freeze` is shallow ([[03.1 - Objects and Property Descriptors]]).

## Structural sharing and why deep clone is wrong

```js
// Wrong — every child gets a new reference, all memoized children re-render
const next = structuredClone(state);
next.user.city = "Delhi";

// Right — only the changed path gets new references
const next = { ...state, user: { ...state.user, city: "Delhi" } };
```

Deep cloning is both slower and worse for performance downstream. This is the most common misunderstanding about immutability: the goal is *new references where something changed*, not *new references everywhere*.

## Persistent data structures

Libraries like Immutable.js implement tries where an update to a large collection allocates O(log n) new nodes and shares the rest. Worth knowing about; rarely worth adopting now — Immer covers the ergonomics without forcing a non-native API through your entire codebase, and plain objects interoperate with everything.

## How senior engineers actually use this

**They treat all state as immutable, including inside reducers and stores.** The rule is uniform so there is never a question of which objects are safe to mutate.

**They use Immer for anything past two levels of nesting**, and consider deeper nesting a signal to normalize.

**They freeze state in development builds.** It converts a whole class of silent bugs into loud ones.

**They mutate freely on local, unshared data.** Building an array inside a function before returning it, accumulating in a loop, sorting a fresh copy — none of that needs immutable discipline, and applying it there just makes code slower and noisier.

## Common pitfalls

- `sort`, `reverse`, `splice` or `push` on props or state.
- Deep cloning state and destroying structural sharing.
- Spreading only the top level and mutating a nested object.
- Spreading state that did not change, creating a new reference and an unnecessary re-render.
- Mutating a `Map` or `Set` in state ([[06.5 - Map and Set]]).
- Returning the same array from a reducer after mutating it, so nothing re-renders.

## Interview angle

"Why does React need immutable state" is the core question. The answer is reference comparison: React and `React.memo` compare with `Object.is`, so an in-place mutation is invisible. Follow with structural sharing — new references only along the changed path — and explain why a deep clone is the wrong fix. Being able to write a nested update by hand and then show the Immer equivalent covers the practical follow-up.
