# Why Governor Limits Exist

## The mechanism, not the annoyance

Your code runs on servers shared with thousands of other customers. One badly written loop could degrade service for all of them.

There are two ways to prevent that: give each tenant dedicated hardware, which destroys the economics of multi-tenancy, or **cap what any single transaction may consume**. Salesforce chose the cap.

Governor limits are a **fairness mechanism**, not performance guidance. That framing explains everything else about how they behave.

## Why they fail hard

A limit exception is thrown mid-execution and the transaction rolls back entirely. There is no warning, no throttling, no degraded mode.

That is deliberate. A soft limit could be ignored; a hard one cannot. Code that would consume more than its share is stopped rather than slowed, because slowing it would still consume the resources.

**`LimitException` cannot be caught.**

```java
try {
    for (Integer i = 0; i < 200; i++) {
        Account a = [SELECT Id FROM Account LIMIT 1];
    }
} catch (Exception e) {
    // never reached
}
```

If it were catchable, code could swallow the exception and continue consuming, defeating the mechanism. The consequence for design is direct: **you cannot recover from a limit failure, so you must design not to approach one.** See [[16.7 - Designing Around Limits]].

## Per transaction, not per day

The single most useful thing to understand about the shape of the limits.

```
100 SOQL queries          per transaction
150 DML statements        per transaction
10 seconds CPU            per transaction
6 MB heap                 per transaction
100 callouts              per transaction
```

Salesforce does not care how much work you do in total. It cares that no single request monopolizes a server.

**That is why async exists.** A Queueable, each Batch chunk, and each platform event subscriber is a **new transaction with a fresh budget**. Splitting work into more, smaller transactions is the fundamental scaling strategy on the platform, and section 12 is largely about the mechanics of doing so.

## The limits that matter

**Synchronous, per transaction:**

```
SOQL queries                          100
Records retrieved by SOQL          50,000
SOSL queries                           20
Records retrieved by SOSL           2,000
DML statements                        150
Records processed by DML           10,000
CPU time                       10 seconds
Heap size                            6 MB
Callouts                              100
Cumulative callout time        120 seconds
Async calls enqueued                   50
Email invocations                      10
Describe calls                        100
Future methods                         50
```

**Asynchronous** roughly doubles most of them: 200 queries, 12 MB heap, 60 seconds CPU.

The two worth memorizing are **100 queries** and **10 seconds CPU**, because they are the ones you hit first and the ones that constrain design.

## The budget is shared

This is the part that surprises people.

**Every limit is shared by everything running in the transaction** — your trigger, other triggers, flows, validation rules, roll-up recalculation, and any installed managed package.

```
DML on Warranty_Claim__c
  → your before trigger:        4 queries
  → a validation rule:          0
  → your after trigger:         6 queries, 2 DML
  → a record-triggered flow:    3 queries per record × 200 = 600  ← fails here
  → a managed package trigger:  12 queries
  → roll-up recalculation on the parent:
      → the parent's trigger:   8 queries
```

Perfectly bulkified Apex can fail because a flow consumed 90 queries before it ran. The error names your code, and your code is not the problem.

Two consequences:

**Auditing total automation on hot objects** is a real activity, not a nicety. See [[07.13 - Order of Execution]].

**Consolidating automation** — one trigger per object, one flow per object per timing — is partly about limits, not just about ordering.

## Where the limits come from

Understanding the mechanism makes the specific numbers less arbitrary.

**Query limits** exist because the query engine runs against shared tables. A query is expensive for everyone, not just for you. This is also why **selectivity** matters — a non-selective query scans data belonging to every tenant on that instance. See [[08.9 - Indexes and Selective Queries]].

**CPU limits** exist because application servers are shared. Ten seconds is roughly the point beyond which one request meaningfully affects others on the same server.

**Heap limits** exist for the same reason at the memory level.

**Callout limits** exist because a callout holds a thread while waiting for an external system you do not control. The 120-second cumulative cap is what stops one transaction occupying a thread for minutes.

**The no-callout-after-DML rule** is the same reasoning applied to database transactions: an open transaction plus a slow external system means database locks held for the duration of someone else's outage.

## Checking limits at runtime

```java
Limits.getQueries();              // used so far
Limits.getLimitQueries();         // the cap
Limits.getDmlStatements();
Limits.getLimitDmlStatements();
Limits.getCpuTime();
Limits.getLimitCpuTime();
Limits.getHeapSize();
Limits.getLimitHeapSize();
Limits.getCallouts();
Limits.getQueryRows();
Limits.getDmlRows();
```

The defensive pattern:

```java
public with sharing class ClaimEnrichmentService {

    public static void enrich(List<Id> claimIds) {
        List<Id> remaining = new List<Id>();

        for (Integer i = 0; i < claimIds.size(); i++) {
            // leaving headroom means the deferral itself has budget to run
            if (Limits.getQueries() > Limits.getLimitQueries() - 10
                || Limits.getCpuTime() > Limits.getLimitCpuTime() - 2000) {

                for (Integer j = i; j < claimIds.size(); j++) {
                    remaining.add(claimIds[j]);
                }
                break;
            }

            processClaim(claimIds[i]);
        }

        if (!remaining.isEmpty()) {
            System.enqueueJob(new ClaimEnrichmentQueueable(remaining));
        }
    }
}
```

Leaving headroom rather than checking against the exact limit matters — the enqueue and the remaining logic themselves consume budget.

This pattern is for genuinely variable work. **It is not a substitute for bulkification**, and code that needs it for ordinary processing is code that should be restructured.

## Reading the limit block

Every debug log ends with the consumption summary, and it is the primary diagnostic:

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 87 out of 100
  Number of query rows: 34211 out of 50000
  Number of SOSL queries: 0 out of 20
  Number of DML statements: 43 out of 150
  Number of DML rows: 2841 out of 10000
  Maximum CPU time: 8214 out of 10000
  Maximum heap size: 3145728 out of 6000000
  Number of callouts: 0 out of 100
```

**Numbers above roughly 70 percent on a normal operation are a warning.** Data grows, automation accumulates, and a transaction at 87 queries today fails next quarter.

Note the `(default)` namespace header — a managed package's consumption appears under its own namespace, and the totals are separate. A package with its own limit budget is one of the few genuine advantages of managed packages. See [[18.12 - Package Design - Unlocked, Managed, 1GP vs 2GP]].

## The limits that are not per transaction

A separate category, org-wide and daily:

```
API requests                    by edition and user count
Async executions                250,000/day, or 200 × user licences
Email to external addresses     by edition
Platform event publishes        by edition
Event deliveries                per subscriber
Data storage                    by edition and user count
File storage                    separately allocated
```

These behave differently: exhausting them affects the whole org until the window resets, not just one transaction. An integration polling per record can exhaust the daily API allocation before lunch, and every other integration then fails. See [[13.1 - Integration Fundamentals and Patterns]].

```java
Map<String, System.OrgLimit> orgLimits = OrgLimits.getMap();
System.OrgLimit api = orgLimits.get('DailyApiRequests');
System.debug(api.getValue() + ' of ' + api.getLimit());
```

Logging that figure daily catches exhaustion before users report it.

## The mental model that helps

Three framings that make the limits feel less arbitrary.

**Limits are a budget, and the budget is shared.** Your code is one line item among several in the same transaction.

**Async is the way to get more budget**, not a way to avoid limits. Each async execution is a fresh transaction, which is why "move it to a Queueable" is the answer to so many limit problems.

**Hitting a limit is a design signal.** Code approaching 100 queries is not slightly inefficient; it is structured wrong. The fix is nearly always collect-query-act, not a limit check.
