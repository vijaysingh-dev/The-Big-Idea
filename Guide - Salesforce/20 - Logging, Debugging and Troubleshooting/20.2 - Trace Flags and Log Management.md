# Trace Flags and Log Management

## The mechanism

**No trace flag, no log.** Logs are not retroactive — an error that occurred before the flag was set produced nothing.

A trace flag has three parts:

```
Traced entity    which user, class, or trigger
Debug level      which categories at which levels
Expiration       when it stops, maximum 24 hours ahead
```

```
Setup → Debug Logs → New

Traced Entity Type:  User
Traced Entity:       integration.erp@northwind.com
Debug Level:         Integration_Diagnostics
Expiration Date:     [now + 2 hours]
```

## Choosing the traced entity

**User** — every transaction that user initiates. The default and usually correct.

**Apex Class** and **Apex Trigger** — a class-level trace flag overrides the user's level **for that class only**, which lets one class be traced at FINEST while the rest of the transaction stays at INFO.

That override is the most useful and least known feature here:

```
User trace flag:   Apex Code = INFO         (keeps the log small)
Class trace flag:  Apex Code = FINEST       (on ClaimApprovalService only)
```

The result is a readable log with full detail exactly where it is needed, which is how a large transaction gets diagnosed without hitting the 20 MB truncation.

## Which user to trace

The question people get wrong, and it costs an afternoon.

**The user who experienced the problem.** Not you. A log from your session running the same operation may behave differently — different sharing, different permissions, different record type.

**The Automated Process user** for platform event subscribers, CDC handlers, and some scheduled work. A subscriber trigger produces nothing under the publishing user's flag.

**The integration user** for API-initiated transactions.

**The scheduling user** for scheduled Apex, since a scheduled job runs as whoever scheduled it.

**The Guest User** for Experience Cloud public pages.

Tracing the wrong user and finding no logs is the most common wasted step in a debugging session.

## Debug levels as reusable presets

A **Debug Level** is a named set of category levels, reusable across trace flags.

```
Setup → Debug Levels → New

Name: Integration_Diagnostics
    Apex Code:      DEBUG
    Apex Profiling: FINE
    Callout:        FINEST
    Database:       INFO
    Workflow:       NONE
    Validation:     NONE
    System:         NONE
    Visualforce:    NONE
```

Worth defining three or four once, rather than setting levels by hand each time:

```
Limit_Diagnostics       Apex Profiling FINE, Database INFO, Workflow INFO
Integration_Diagnostics Callout FINEST, Apex Code DEBUG
Automation_Diagnostics  Workflow FINER, Validation INFO, Database INFO
Minimal                 Apex Code ERROR, everything else NONE
```

`SFDC_DevConsole` is the built-in default, and it is broad enough to truncate on a busy transaction.

## Setting flags programmatically

For scripted diagnosis and for automation.

```bash
sf apex tail log --target-org my-sandbox --color
```

That single command creates a trace flag on the running user, streams logs live, and cleans up on exit — the fastest loop when reproducing something interactively.

Creating one explicitly through the Tooling API:

```bash
sf data create record --use-tooling-api --sobject TraceFlag \
  --values "TracedEntityId=0055g00000ABCDeAAN \
            DebugLevelId=7dl5g00000XYZabAAB \
            LogType=USER_DEBUG \
            StartDate=2026-08-12T09:00:00.000Z \
            ExpirationDate=2026-08-12T11:00:00.000Z" \
  --target-org production
```

Querying what is active:

```bash
sf data query --use-tooling-api \
  --query "SELECT Id, TracedEntity.Name, DebugLevel.DeveloperName, ExpirationDate, LogType
           FROM TraceFlag ORDER BY ExpirationDate DESC" \
  --target-org production
```

**Worth running periodically.** Forgotten trace flags on busy users are the usual cause of the log storage cap filling.

## LogType values

```
USER_DEBUG          a user-initiated transaction
CLASS_TRACING       a class-level override
DEVELOPER_LOG       the Developer Console's own flag
```

The Developer Console creates and removes its own `DEVELOPER_LOG` flag when opened and closed, which occasionally conflicts with a manually set one.

## The storage cap

```
1,000 MB of logs per org
Oldest deleted first when full
Individual logs retained 7 days
```

**A trace flag on a busy integration user fills the allocation in hours**, and when it fills, older logs are deleted — including the one capturing the problem.

The practical discipline:

**Set a short expiration.** Two hours, not twenty-four.

**Set narrow levels.** Everything not under investigation at NONE.

**Remove the flag when finished**, rather than waiting for expiry.

**Never leave a flag on the Automated Process user** in a busy org.

Deleting logs to reclaim space:

```bash
sf data query --use-tooling-api \
  --query "SELECT Id FROM ApexLog WHERE LogUserId = '0055g00000ABCDeAAN'" \
  --result-format csv > logs.csv

sf data delete bulk --sobject ApexLog --file logs.csv --use-tooling-api --target-org production
```

## Finding the right log

```bash
sf apex list log --target-org production
```

```sql
SELECT Id, LogUser.Name, Operation, Status, LogLength, StartTime, DurationMilliseconds
FROM ApexLog
WHERE StartTime = TODAY AND Status != 'Success'
ORDER BY StartTime DESC
```

**`Operation`** names what triggered it — a class name, a trigger, `/services/data/v62.0/sobjects/...` for an API call.

**`Status`** is the outcome. Anything other than `Success` is worth reading first.

**`DurationMilliseconds`** identifies the slow ones without opening any of them, which is the fastest way to find a performance problem in a session with fifty logs.

**`LogLength`** near 20 MB means truncation — the log is incomplete.

## Tracing a production incident

The sequence under pressure.

**1. Identify the affected user and the operation.** "It failed for Priya when approving a claim at about 09:30."

**2. Check whether a log already exists.** Occasionally a flag is already active:

```sql
SELECT Id, LogUser.Name, Operation, Status, StartTime
FROM ApexLog WHERE StartTime = TODAY ORDER BY StartTime DESC
```

**3. Set a narrow flag on that user**, with a short expiration.

**4. Have them reproduce**, or reproduce as them in a sandbox.

**5. Read the limit block first**, then the shape.

**6. Remove the flag.**

**If it cannot be reproduced**, debug logs are the wrong tool. A persistent custom log, written at the time of the failure, is the only record — which is the argument for having one before the incident. See [[20.5 - Custom Logging Frameworks]].

## Async and the Automated Process user

The specific case worth knowing, because it wastes time otherwise.

```
Platform event subscriber trigger  → Automated Process user
Change Data Capture handler        → Automated Process user
Scheduled Apex                     → the scheduling user
Queueable from a trigger           → the user who initiated the trigger
Batch Apex                         → the user who started the batch
@future                            → the calling user
Flow scheduled path                → the Automated Process user
```

**Platform event and CDC subscribers are the ones that surprise people.** A trace flag on the publishing user captures the publish and nothing after it, because the subscriber runs as a different user in a different transaction.

Setting a flag on the Automated Process user is how a subscriber gets diagnosed — with a short expiration, since that user is busy in any event-driven org.

## Trace flags in a scratch org

Scratch orgs and sandboxes have the same mechanism, and two conveniences:

```bash
# Streams live, creating and removing the flag automatically
sf apex tail log --target-org scratch-org --color

# Runs anonymous Apex and returns the log directly
sf apex run --file scripts/diagnose.apex --target-org scratch-org
```

`sf apex run` returning the log inline is the fastest possible diagnostic loop — write a snippet, run it, read the output, without touching Setup at all.

## Automating flag cleanup

For an org where flags accumulate:

```java
public with sharing class TraceFlagCleanup implements Schedulable {

    public void execute(SchedulableContext ctx) {
        // trace flags live in the Tooling API, so this is a callout rather than DML
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:Self/services/data/v62.0/tooling/query/?q='
            + EncodingUtil.urlEncode(
                'SELECT Id FROM TraceFlag WHERE ExpirationDate < ' + nowIso(), 'UTF-8'));
        req.setMethod('GET');

        deleteEach(new Http().send(req));
    }
}
```

`callout:Self` is a Named Credential pointing at the org itself, which is necessary because `UserInfo.getSessionId()` is unavailable in async contexts. See [[13.13 - Named Credentials and External Credentials]].

Worth building only in an org where this is a recurring problem; in most, a periodic manual check suffices.

## Practical guidance

**Trace the affected user**, not yourself.

**Trace the Automated Process user** for event and CDC subscribers.

**Use a class-level flag** to get FINEST on one class without truncating the log.

**Define reusable debug levels** rather than setting categories each time.

**Set short expirations**, and remove the flag when finished.

**Audit active trace flags periodically.**

**Query `ApexLog` by duration and status** to find the interesting log quickly.

**Use `sf apex tail log`** for an interactive loop.

**Remember logs are not retroactive** — if it could not be reproduced, only a persistent log has the answer.
