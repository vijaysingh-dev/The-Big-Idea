# End to End Testing with Playwright

E2E tests drive a real browser against a running application, exercising the frontend, the backend and the database together. They give the highest confidence and cost the most, so the suite should be small and focused on journeys that must not break.

## Setup

```ts
// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  reporter: [["html"], ["list"]],

  use: {
    baseURL: "http://localhost:5173",
    trace: "on-first-retry",
    screenshot: "only-on-failure",
    video: "retain-on-failure",
  },

  projects: [
    { name: "chromium", use: devices["Desktop Chrome"] },
    { name: "mobile", use: devices["Pixel 7"] },
  ],

  webServer: {
    command: "npm run dev",
    url: "http://localhost:5173",
    reuseExistingServer: !process.env.CI,
  },
});
```

`trace: "on-first-retry"` is the most valuable setting here. A trace captures the DOM at every step, network activity, console output and a screenshot timeline — so a CI failure can be replayed locally in the trace viewer rather than reproduced by guesswork.

`webServer` starts the app automatically, so `npx playwright test` works from a clean checkout.

## A representative test

```ts
import { test, expect } from "@playwright/test";

test("user can complete checkout", async ({ page }) => {
  await page.goto("/products");

  await page.getByRole("link", { name: /wireless headphones/i }).click();
  await page.getByRole("button", { name: /add to cart/i }).click();

  await expect(page.getByRole("status")).toHaveText(/added to cart/i);

  await page.getByRole("link", { name: /cart/i }).click();
  await page.getByRole("button", { name: /checkout/i }).click();

  await page.getByLabel(/card number/i).fill("4242424242424242");
  await page.getByRole("button", { name: /pay/i }).click();

  await expect(page.getByRole("heading", { name: /order confirmed/i })).toBeVisible();
});
```

The same role-and-name query priority as React Testing Library, for the same reason — it matches how users and assistive technology find things ([[26.3 - React Testing Library]]).

## Auto-waiting eliminates most flakiness

```ts
await page.getByRole("button").click();
```

Before clicking, Playwright waits for the element to be attached, visible, stable (not animating), enabled, and able to receive events. There is no need for explicit waits.

```ts
await expect(page.getByRole("alert")).toBeVisible();   // retries until timeout
```

Web-first assertions retry automatically. This is the fundamental difference from older tools where `sleep` calls were normal.

Never write:

```ts
await page.waitForTimeout(2000);   // arbitrary — slow when it passes, flaky when it fails
```

If a wait seems necessary, wait for a **condition** instead:

```ts
await page.waitForResponse(r => r.url().includes("/api/orders") && r.ok());
await page.waitForURL("/orders/*");
await expect(page.getByTestId("spinner")).toBeHidden();
```

## Locators over selectors

```ts
page.getByRole("button", { name: /submit/i });
page.getByLabel(/email/i);
page.getByText(/welcome/i);
page.getByPlaceholder(/search/i);
page.getByTestId("chart-container");

page.getByRole("listitem").filter({ hasText: "Shoes" });
page.getByRole("row", { name: /order 123/i }).getByRole("button", { name: /cancel/i });
```

Locators are **lazy** — they resolve at the moment of use, so they do not go stale when the DOM re-renders. That property alone removes a large class of flakiness from React applications, where elements are frequently replaced.

Chaining and filtering handles lists and tables without brittle CSS paths.

For elements with no accessible identity, `data-testid` is the escape hatch — but a page where most locators are test ids usually has an accessibility problem ([[09.5 - Accessibility Fundamentals]]).

## Authentication once

```ts
// e2e/auth.setup.ts
import { test as setup } from "@playwright/test";

setup("authenticate", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel(/email/i).fill(process.env.TEST_EMAIL!);
  await page.getByLabel(/password/i).fill(process.env.TEST_PASSWORD!);
  await page.getByRole("button", { name: /sign in/i }).click();
  await page.waitForURL("/dashboard");

  await page.context().storageState({ path: "e2e/.auth/user.json" });
});
```

```ts
projects: [
  { name: "setup", testMatch: /auth\.setup\.ts/ },
  {
    name: "chromium",
    use: { ...devices["Desktop Chrome"], storageState: "e2e/.auth/user.json" },
    dependencies: ["setup"],
  },
],
```

Logging in once and reusing the storage state — cookies and `localStorage` — saves several seconds per test. On a suite of forty tests that is the difference between a two-minute and a six-minute CI run ([[14.2 - LocalStorage and SessionStorage]]).

Keep one test that exercises the login flow itself; everything else starts authenticated.

## Test isolation

Each test gets a fresh browser context — separate cookies, storage and cache. That handles browser state, but **not** application data.

Two workable strategies:

**Unique data per test.** Every test creates its own records with generated identifiers, so parallel runs cannot collide:

```ts
const email = `test-${crypto.randomUUID()}@example.com`;
```

**Reset between runs.** A seeded database restored before the suite. Simpler to reason about, but forces serial execution unless each worker gets its own database.

The first scales better and is what most teams settle on. Tests that depend on a specific pre-existing record are the main source of order-dependent failures.

## Network control

```ts
// Fail a third-party dependency deterministically
await page.route("**/api/recommendations", route =>
  route.fulfill({ status: 500 })
);

// Simulate offline
await context.setOffline(true);

// Assert a request was made correctly
const request = page.waitForRequest(r => r.url().includes("/api/analytics"));
await page.getByRole("button", { name: /save/i }).click();
expect((await request).postDataJSON()).toMatchObject({ event: "save" });
```

E2E tests should generally hit the **real backend** — that is the point. Route interception is for isolating genuinely external dependencies: payment providers, third-party analytics, flaky vendor APIs, and for forcing error states that are hard to trigger otherwise ([[24.2 - Loading Error and Empty States]]).

## What to cover

Keep it small. A good E2E suite is 10–30 tests covering journeys where a failure would be serious:

- Sign up and log in
- The core workflow — checkout, publish, submit
- Payment
- Critical permission boundaries
- One test per major route confirming it renders

**Not** covered here: form validation permutations, edge cases, error message wording, component variants. Those belong in integration tests, which run in seconds rather than minutes ([[26.1 - Testing Philosophy]]).

A useful heuristic: if a bug in this path would prompt a phone call, it deserves an E2E test.

## Debugging

```bash
npx playwright test --ui          # interactive mode with time travel
npx playwright test --debug       # step through with the inspector
npx playwright codegen localhost:5173   # record interactions into a test
npx playwright show-trace trace.zip
```

The UI mode is the standout — it shows a timeline of every action with a DOM snapshot at each step, so you can scrub back to the exact moment before a failure. It removes most of the guesswork that made older E2E tooling painful.

`codegen` is useful for discovering locators, though generated tests usually need rewriting to use roles rather than CSS.

## Visual and accessibility checks

```ts
await expect(page).toHaveScreenshot("dashboard.png", { maxDiffPixels: 100 });
```

Visual regression catches CSS breakage that DOM assertions miss. It also produces false positives from font rendering and animation differences across environments — run it on a consistent platform, usually a Docker image matching CI.

```ts
import AxeBuilder from "@axe-core/playwright";

const results = await new AxeBuilder({ page }).analyze();
expect(results.violations).toEqual([]);
```

Automated accessibility scanning in E2E catches roughly a third of issues and is cheap to add to existing tests.

## CI

```yaml
- run: npx playwright install --with-deps chromium
- run: npx playwright test
- uses: actions/upload-artifact@v4
  if: failure()
  with:
    name: playwright-report
    path: playwright-report/
```

Uploading the report and traces on failure is what makes CI failures actionable — without it, "it failed in CI" is a dead end ([[27.9 - CI CD and Frontend Deployment]]).

Sharding splits the suite across parallel jobs:

```bash
npx playwright test --shard=1/4
```

## Handling flakiness

Retries hide flakiness; they do not fix it. `retries: 2` in CI is pragmatic, but a test that only passes on retry should be investigated.

The usual causes, in order:

1. A hard-coded `waitForTimeout`
2. Test data collisions between parallel runs
3. Animations not settled — usually fixed by disabling animations in test mode
4. Race conditions in the application itself, which the test correctly caught

The last case is worth stressing: an intermittently failing E2E test sometimes indicates a real bug, not a bad test.

## How senior engineers actually use this

**They keep the E2E suite small** and push everything else down to integration tests.

**They enable traces on retry**, which turns CI failures into replayable sessions.

**They reuse authentication state** rather than logging in per test.

**They generate unique test data** so tests can run in parallel.

**They never use fixed waits**, and treat one appearing in review as a defect.

**They investigate retry-only passes** rather than accepting them.

## Common pitfalls

- `waitForTimeout` instead of waiting for a condition.
- Tests sharing data, failing when run in parallel or reordered.
- Logging in through the UI in every test.
- Trying to cover every case in E2E instead of integration tests.
- CSS selectors instead of role-based locators.
- No trace or report artifacts, making CI failures undebuggable.
- Retries masking a genuine application race condition.
- Visual snapshots taken in an inconsistent environment.

## Interview angle

"When would you write an E2E test versus an integration test" is the question. Frame it as confidence per unit of cost: E2E exercises the real stack and catches integration failures nothing else can, but it is slow, more fragile and expensive to maintain — so reserve it for journeys where a break would be serious, and cover everything else lower down. Mentioning auto-waiting locators and trace-on-retry shows you know why modern E2E is far less painful than its reputation.
