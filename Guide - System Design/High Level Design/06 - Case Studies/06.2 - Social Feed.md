# Case Study: Social Feed (Instagram-style)

> **Revision tags:** #case-study #feed #fan-out  
> **Related:** [[03.8 - Message Queues and Kafka]] | [[03.4 - Caching Systems]]

---

## Requirements Clarification

**Functional:**
- Users can post photos/videos with captions
- Users follow other users
- Users see a feed of posts from people they follow (reverse-chronological or ranked)
- Like and comment on posts
- User profile page with their posts

**Non-functional:**
- 99.9% availability for feed reads
- Feed load time < 200ms p99
- Eventually consistent — seeing a post 1–2 seconds after it's created is acceptable
- Write-heavy for big accounts (celebrity with 50M followers posts → 50M fan-out)
- Read:write ratio ≈ 100:1 for most users

**Out of scope:** Stories, Reels, ads, DMs, notifications (separate system)

---

## Estimation

```
DAU: 500M users
Posts per day: 500M × 0.05 posts/user = 25M posts/day = 290 writes/s
Feed reads:    500M × 10 reads/day   = 5B reads/day  = 58,000 reads/s
Read:write ratio ≈ 200:1

Post storage:
  post_id, user_id, caption, media_url, created_at ≈ 500 bytes/post
  25M × 500 bytes = 12.5 GB/day text data
  Media (photos/videos): separate object storage (S3) — not counted here

Feed cache:
  Each user's feed = 20 posts × 8 bytes (post_id) = 160 bytes
  500M users × 160 bytes = 80 GB for all feed caches → fits in Redis cluster
```

**Key insight:** Feed reads dominate. The core challenge is serving 58K feed reads/s with < 200ms latency.

---

## The Fan-Out Problem

When a user posts, their followers need to see it in their feed. With 50M followers, naively writing to 50M feeds is expensive.

Two approaches:

### Fan-Out on Write (Push Model)

When user posts → immediately write post_id to all followers' feed lists.

```
Post created
    │
    ▼
[Fan-out Workers] (Kafka consumers)
    ├── Read follower list (50M for a celebrity)
    └── For each follower:
          LPUSH feed:{follower_id} {post_id}
          LTRIM feed:{follower_id} 0 999  # keep latest 1000
```

**Pros:** Feed reads are O(1) — just read the pre-built list from Redis  
**Cons:** Celebrity post = 50M Redis writes. Write amplification is severe.  
**Good for:** Users with few followers (< 1M)

### Fan-Out on Read (Pull Model)

No pre-building. When user opens feed → fetch posts from all followed accounts.

```
User opens feed
    │
    ▼
[Feed Service]
  1. Get list of followed user IDs (from graph DB / Redis)
  2. For each followed user: get their N most recent posts
  3. Merge, sort by time, return top 20
```

**Pros:** No write amplification. Celebrities' posts are fetched on demand.  
**Cons:** Feed read requires N queries (one per followed account) — slow for users following thousands of accounts.  
**Good for:** Accounts with massive followings (celebrities)

### Hybrid Model (Production Standard)

Use fan-out on write for normal users, fan-out on read for celebrities.

```
Define: celebrity threshold = accounts with > 1M followers

Post by normal user (<1M followers):
  → Fan-out on write → push post_id to all follower feed caches

Post by celebrity (>1M followers):
  → No fan-out → mark post in celebrity_posts:{user_id} only

When user opens feed:
  1. Read pre-built feed cache (fan-out-on-write posts)
  2. Check if any followed accounts are celebrities
  3. Fetch recent posts from celebrity accounts in real-time
  4. Merge the two lists by timestamp
  5. Return top 20
```

This bounds write amplification (no celebrity posts fanned out) while keeping read latency low (most posts are pre-built in cache).

## Architecture

```
[Client]
    │
    ▼
[API Gateway]  ──auth──→  [Auth Service]
    │
    ├──→ [Post Service]      → writes posts
    │         │
    │         ▼
    │    [Kafka: post-events]
    │         │
    │         └──→ [Fan-out Workers] → Redis feed caches
    │
    ├──→ [Feed Service]      → reads feeds
    │         │
    │         ├── Redis (pre-built feed lists)
    │         └── Post Service (celebrity posts, cache miss)
    │
    ├──→ [Media Service]     → upload/serve photos/videos
    │         │
    │         └── S3 + CDN
    │
    └──→ [Graph Service]     → follow/unfollow, follower counts
              │
              └── Graph DB or denormalized follower tables
```

## Data Model

### Posts Table (PostgreSQL or Cassandra)

```sql
CREATE TABLE posts (
    post_id    UUID         PRIMARY KEY,
    user_id    BIGINT       NOT NULL,
    caption    TEXT,
    media_url  TEXT,
    created_at TIMESTAMPTZ  NOT NULL,
    like_count BIGINT       DEFAULT 0,
    is_deleted BOOLEAN      DEFAULT false
);

CREATE INDEX idx_posts_user_created ON posts(user_id, created_at DESC);
```

At scale: partition by `user_id` → Cassandra or sharded PostgreSQL. Query pattern is always "get posts by user_id ordered by created_at" — fits a wide-column store well.

### Feed Cache (Redis)

```
Key:   feed:{user_id}
Type:  Redis Sorted Set (score = timestamp, member = post_id)
Size:  Keep latest 200–1000 post_ids per user

ZADD feed:42 1705000001 "post:8821"
ZADD feed:42 1705000002 "post:8822"
ZREVRANGE feed:42 0 19  → 20 most recent post_ids
```

Sorted Set by timestamp supports efficient range queries and TTL-less expiry by trimming old entries.

### Follow Graph

```sql
CREATE TABLE follows (
    follower_id  BIGINT NOT NULL,
    followee_id  BIGINT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (follower_id, followee_id)
);

CREATE INDEX idx_follows_followee ON follows(followee_id);
-- "who follows user X?" = secondary index on followee_id
```

For very large graphs: use a dedicated graph store (Neo4j) or a denormalized adjacency list in Redis/Cassandra.

## Feed Read Flow

```
1. Client: GET /feed?user_id=42&cursor=...

2. Feed Service:
   a. Read feed cache: ZREVRANGE feed:42 0 19
   b. If < 20 results (cold cache): rebuild from follows + posts DB
   c. For each followed celebrity: fetch recent posts (real-time)
   d. Merge all post_ids by timestamp
   e. Batch-fetch post details: SELECT * FROM posts WHERE id IN (...)
   f. Return hydrated posts

3. Pagination via cursor (post_id of last item):
   ZREVRANGEBYSCORE feed:42 {cursor_score} -inf LIMIT 0 20
```

**Post hydration:** Don't store full post data in the feed list. Store only post_ids. Hydrate in batch. This keeps the feed list lean and post data up-to-date (edited captions, updated like counts).

---

## Media Upload Flow

```
1. Client requests upload URL: POST /media/upload
2. Media Service: generate presigned S3 PUT URL → return to client
3. Client uploads directly to S3
4. Client notifies Media Service: POST /media/confirm { s3_key }
5. Media Service: trigger transcoding job (for videos)
6. On transcoding complete: update media record with CDN URL
7. Client creates post with media_url pointing to CDN
```

Never proxy media through your servers. S3 + CDN handles bytes. Your servers handle metadata only.

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Fan-out worker crashes mid-fan-out | Some followers miss the post | At-least-once Kafka delivery; idempotent fan-out (ZADD is idempotent) |
| Feed cache miss | Slower feed load (DB query) | Rebuild from DB; pre-warm on user login |
| Post DB shard overloaded | Writes fail | Circuit breaker; fan-out workers back off |
| Celebrity fan-out on read is slow | Feed reads slow for users following celebrities | Cache celebrity's recent post_ids separately (invalidate on new post) |
| Redis OOM | Feed caches evicted | Keep only top 1000 posts per user; accept re-building from DB |

---

## What This Design Demonstrates

- Fan-out on write vs read and the hybrid solution for celebrity accounts
- Separating post storage (DB) from feed lists (Redis sorted set)
- Cursor-based pagination for infinite scroll
- Presigned URL pattern for media upload
- Post hydration pattern (store IDs, not full objects, in feed cache)
