# Metadata API and Tooling API

## Two APIs for configuration, not data

Everything else in this section moves **records**. These two move **metadata** — objects, fields, classes, flows, permission sets, layouts.

**Metadata API** is for deployment. Retrieve a package of metadata from one org, deploy it to another. Asynchronous, package-oriented, and what the CLI uses underneath.

**Tooling API** is for development tooling. Query and modify individual metadata components at runtime, synchronously. It is what the Developer Console and the VS Code extensions use.

The distinction: **Metadata API for deployments, Tooling API for inspection and single-component edits.**

## Metadata API

The mental model is packages. Describe what you want with a manifest, retrieve it as a zip, deploy that zip elsewhere.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>Warranty_Claim__c</members>
        <members>Machine_Coverage__c</members>
        <name>CustomObject</name>
    </types>
    <types>
        <members>ClaimService</members>
        <members>ClaimServiceTest</members>
        <name>ApexClass</name>
    </types>
    <types>
        <members>*</members>
        <name>PermissionSet</name>
    </types>
    <version>62.0</version>
</Package>
```

`*` retrieves every component of that type. Naming members explicitly is safer for anything you intend to deploy, because `*` picks up whatever exists at retrieval time.

In practice you rarely call it directly — the CLI wraps it:

```bash
sf project retrieve start --manifest manifest/package.xml --target-org production
sf project deploy start --manifest manifest/package.xml --target-org staging
sf project deploy validate --manifest manifest/package.xml --target-org production
```

`deploy validate` runs the deployment and its tests without committing, which is how a release is checked against production before the window. See [[21.3 - Salesforce CLI and SFDX]].

## The profile retrieval trap

Worth stating early, because it causes real incidents.

**When you retrieve a profile, the platform only includes permissions for metadata also present in the retrieval.** Retrieve a profile alone and you get a near-empty file. Deploy that file and, depending on the deployment mode, you may wipe permissions that were not included.

The defences:

- Retrieve profiles alongside the objects and fields they reference
- Prefer **permission sets** in source control, since they retrieve completely
- Review profile diffs carefully — one removing a hundred lines is usually a retrieval artefact, not an intended change

See [[03.3 - Profiles]].

## Destructive changes

Deletion is a separate manifest:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>Legacy_Claim_Status__c</members>
        <name>CustomField</name>
    </types>
    <version>62.0</version>
</Package>
```

```bash
sf project deploy start \
  --manifest manifest/package.xml \
  --post-destructive-changes manifest/destructiveChangesPost.xml \
  --target-org production
```

`pre` runs before the main deployment, `post` after. Post is usually correct — deploy the replacement, then remove the old component.

Deletions fail when anything still references the component: a formula, a validation rule, a flow, an Apex class, a report type. Untangling those references is generally more work than the deletion, which is why unused metadata survives in orgs for years.

## Tooling API

Synchronous, record-oriented, and queryable with SOQL. It exposes metadata as objects you can query and modify individually.

```bash
sf data query --use-tooling-api \
  --query "SELECT Id, Name, TableEnumOrId, Status, LengthWithoutComments FROM ApexTrigger" \
  --target-org production
```

The objects that matter most:

```
ApexClass, ApexTrigger, ApexPage, ApexComponent
ApexCodeCoverage, ApexCodeCoverageAggregate
ApexTestResult, ApexTestRunResult
ApexLog, TraceFlag, DebugLevel
CustomField, CustomObject, EntityDefinition, FieldDefinition
Flow, FlowDefinition, FlowVersionView
ValidationRule, WorkflowRule
MetadataComponentDependency
SandboxProcess
```

## What Tooling API makes possible

**Code coverage reporting**, per class, which is what CI pipelines gate on:

```sql
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate
ORDER BY NumLinesUncovered DESC
```

That query, run after a test execution, produces the coverage table a pull request should show. See [[19.10 - Code Coverage, Quality and CI Gates]].

**Dependency analysis**, which is otherwise impossible:

```sql
SELECT MetadataComponentName, MetadataComponentType,
       RefMetadataComponentName, RefMetadataComponentType
FROM MetadataComponentDependency
WHERE RefMetadataComponentName = 'Claim_Amount__c'
```

"What breaks if I delete this field" has an answer, and it is this query. It is one of the genuinely useful things the Tooling API provides that nothing else does.

**Org inventory**, the first thing to run in an inherited org:

```sql
SELECT Name, TableEnumOrId, Status FROM ApexTrigger ORDER BY TableEnumOrId
SELECT Id, ValidationName, EntityDefinition.QualifiedApiName, Active FROM ValidationRule
SELECT DeveloperName, TableEnumOrId FROM WorkflowRule
```

**Debug log management** programmatically, by creating `TraceFlag` records through the Tooling endpoint rather than through DML.

## Executing anonymous Apex through the API

Useful for deployment scripts and automated data fixes:

```bash
sf apex run --file scripts/post-deploy-setup.apex --target-org production
```

Underneath this is the Tooling API's `executeAnonymous` endpoint. Making post-deployment steps a versioned script rather than a manual checklist is what stops them being forgotten. See [[21.10 - Deployment Strategies, Rollback and Hotfixes]].

## Metadata operations from Apex

Apex can call the Metadata API through the `Metadata` namespace, which is how a managed package or an admin tool creates configuration at runtime.

```java
public with sharing class PicklistValueService {

    public static void addValue(String objectName, String fieldName, String newValue) {
        String fullName = objectName + '.' + fieldName;

        List<Metadata.Metadata> components = Metadata.Operations.retrieve(
            Metadata.MetadataType.CustomField, new List<String>{ fullName }
        );

        Metadata.CustomField field = (Metadata.CustomField) components.get(0);

        Metadata.CustomValue value = new Metadata.CustomValue();
        value.fullName = newValue;
        value.label = newValue;
        field.valueSet.valueSetDefinition.value.add(value);

        Metadata.DeployContainer container = new Metadata.DeployContainer();
        container.addMetadata(field);

        // deployment is asynchronous; the callback reports the outcome
        Metadata.Operations.enqueueDeployment(container, new DeploymentCallback());
    }
}
```

**Deployment is asynchronous**, and the callback is where success or failure is reported.

The `Metadata` namespace supports a **limited subset** of types — custom fields, page layouts, record types, custom metadata records, and some others. It does not support Apex classes, flows, or objects.

## Which to use

| Task | API |
| --- | --- |
| Deploy a release | Metadata API, via the CLI |
| Retrieve metadata for source control | Metadata API |
| Query what exists in the org | Tooling API |
| Find dependencies before deleting | Tooling API |
| Read code coverage | Tooling API |
| Manage debug logs | Tooling API |
| Run anonymous Apex | Tooling API |
| Create a picklist value at runtime | `Metadata` namespace in Apex |
| Create an object or class at runtime | Not possible from Apex; deployment only |

## Limits

**Metadata API:** 10,000 files or 400 MB per deployment, 25 concurrent operations, and production deployments require 75% coverage with all tests passing.

**Tooling API:** counts against the daily API request allocation, with its own lower SOQL row limits.

## Where this fits

The Metadata API underpins everything in section 21 — the CLI, packaging, CI pipelines, and deployment strategy all sit on it. This note is the API-level view; the practice is there.

The Tooling API is the org-inspection tool used throughout this course: the trigger inventory in [[11.4 - One Trigger Per Object]], the flow inventory in [[07.13 - Order of Execution]], and the coverage query in section 19.

## Practical guidance

**Use the CLI rather than calling the Metadata API directly.**

**Retrieve profiles with their referenced metadata**, and prefer permission sets in source control.

**Use `deploy validate`** against production before a release window.

**Run the dependency query before deleting anything.**

**Keep post-deployment steps as versioned anonymous Apex**, not a manual checklist.

**Build an org inventory from Tooling API queries** when inheriting an org.
