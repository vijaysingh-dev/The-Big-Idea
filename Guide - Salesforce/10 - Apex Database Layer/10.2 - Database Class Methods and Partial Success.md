# Database Class Methods and Partial Success

## The choice

```java
update claims;                       // all-or-none: one failure aborts everything
Database.update(claims, false);      // partial success: failures reported per record
```

`Database.update(records, allOrNone)` with `allOrNone = false` saves what it can and reports the rest.

This is not a minor stylistic choice. In a batch job, an integration, or any bulk operation, **all-or-none means one bad record discards 199 good ones**, and the whole batch has to be reprocessed.

## Reading the results

```java
List<Database.SaveResult> results = Database.update(claims, false);

for (Integer i = 0; i < results.size(); i++) {
    Database.SaveResult result = results[i];

    if (result.isSuccess()) {
        continue;
    }

    // results are index-aligned with the input list, which is how you know which record failed
    for (Database.Error err : result.getErrors()) {
        AutomationLogger.logError(
            'ClaimUpdate',
            claims[i].Id,
            err.getStatusCode() + ': ' + err.getMessage()
            + ' [' + String.join(err.getFields(), ', ') + ']'
        );
    }
}
```

**The results list is index-aligned with the input list.** `results[3]` corresponds to `claims[3]`. This is the only way to know which record failed, and it means you must not reorder or filter the input between the call and reading the results.

`Database.Error` gives:

```java
err.getStatusCode()      // StatusCode enum
err.getMessage()         // human-readable message
err.getFields()          // List<String> of fields that caused it
```

## Result types

Each operation has its own result class, all with the same shape:

```java
Database.SaveResult      insert, update
Database.UpsertResult    upsert — adds isCreated()
Database.DeleteResult    delete
Database.UndeleteResult  undelete
Database.MergeResult     merge — adds getMergedRecordIds()
```

`Database.UpsertResult.isCreated()` distinguishes an insert from an update, which matters for reporting on an integration run:

```java
List<Database.UpsertResult> results = Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);

Integer created = 0;
Integer updated = 0;
for (Database.UpsertResult result : results) {
    if (result.isSuccess()) {
        if (result.isCreated()) {
            created++;
        } else {
            updated++;
        }
    }
}
```

## Status codes worth handling differently

`getStatusCode()` returns an enum, and branching on it is what separates a useful error handler from one that logs everything identically.

The ones that matter:

```java
StatusCode.UNABLE_TO_LOCK_ROW                   transient — retry
StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION    a validation rule — permanent
StatusCode.REQUIRED_FIELD_MISSING               permanent
StatusCode.INVALID_CROSS_REFERENCE_KEY          a lookup to a missing record
StatusCode.DUPLICATE_VALUE                      unique field or external Id collision
StatusCode.INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY   permission
StatusCode.STRING_TOO_LONG                      permanent
StatusCode.ENTITY_IS_LOCKED                     in an approval process
StatusCode.CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY a trigger threw
```

```java
public with sharing class DmlResultHandler {

    public class Outcome {
        public List<Id> succeeded = new List<Id>();
        public List<Id> retryable = new List<Id>();
        public List<String> permanentFailures = new List<String>();
    }

    private static final Set<StatusCode> TRANSIENT = new Set<StatusCode>{
        StatusCode.UNABLE_TO_LOCK_ROW,
        StatusCode.ENTITY_IS_LOCKED,
        StatusCode.UNABLE_TO_LOCK_ROW
    };

    public static Outcome classify(List<Database.SaveResult> results, List<SObject> records) {
        Outcome outcome = new Outcome();

        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                outcome.succeeded.add(results[i].getId());
                continue;
            }

            Boolean isTransient = false;
            for (Database.Error err : results[i].getErrors()) {
                if (TRANSIENT.contains(err.getStatusCode())) {
                    isTransient = true;
                } else {
                    outcome.permanentFailures.add(
                        records[i].Id + ': ' + err.getStatusCode() + ' ' + err.getMessage()
                    );
                }
            }

            if (isTransient) {
                outcome.retryable.add(records[i].Id);
            }
        }
        return outcome;
    }
}
```

Retrying a validation rule failure a hundred times achieves nothing and burns limits. Retrying a lock failure usually succeeds. Distinguishing them is the point of the exercise. See [[13.17 - Error Handling, Retries and Idempotency]].

## AllOrNone and transaction semantics

An important subtlety: **partial success does not create separate transactions.**

`Database.update(claims, false)` still runs inside one transaction. If a later statement in the same transaction throws, the successful updates from the partial-success call **are rolled back with everything else**.

```java
Database.update(claims, false);   // 195 succeed, 5 fail

processPayments(claims);          // throws

// all 195 updates are rolled back
```

Partial success controls whether **that DML statement** aborts on a bad record. It does not isolate the statement from the transaction.

Where genuine isolation is needed, the options are savepoints ([[10.5 - Savepoints, Rollback and Transaction Control]]) or moving work into separate async transactions.

## Logging failures that survive rollback

The corollary: a log record inserted in the same transaction as a failure is rolled back with it.

```java
// Rolled back if anything later throws
insert new Automation_Log__c(Message__c = 'Update failed');
```

Platform events published with immediate behaviour survive rollback by design, which is why they are the recommended mechanism:

```java
List<Automation_Error__e> events = new List<Automation_Error__e>();
for (Integer i = 0; i < results.size(); i++) {
    if (!results[i].isSuccess()) {
        events.add(new Automation_Error__e(
            Context__c = 'ClaimUpdate',
            Record_Id__c = claims[i].Id,
            Message__c = results[i].getErrors()[0].getMessage()
        ));
    }
}
if (!events.isEmpty()) {
    EventBus.publish(events);
}
```

See [[12.8 - Platform Events]] and [[20.5 - Custom Logging Frameworks]].

## Choosing between the forms

**Use the statement form (`insert records`) when:**

- The operation must be atomic — all records or none
- A failure is genuinely exceptional and should abort
- You are in a trigger where `addError` is the better mechanism anyway
- The code is simple and a failure means the request is invalid

**Use `Database.method(records, false)` when:**

- Processing in bulk — batch jobs, integrations, data loads
- Individual records can legitimately fail without invalidating the rest
- You need per-record error reporting
- A retry mechanism exists for transient failures

The default for anything batch-shaped is partial success. The default for a user-initiated single operation is the statement form.

## Other Database methods

```java
// Query with a locator, for batch contexts
Database.QueryLocator locator = Database.getQueryLocator([SELECT Id FROM Warranty_Claim__c]);

// Count without retrieving
Integer count = Database.countQuery('SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = :status');

// Dynamic query with binds and access level
List<SObject> records = Database.queryWithBinds(query, binds, AccessLevel.USER_MODE);

// Convert leads
List<Database.LeadConvertResult> conversions = Database.convertLead(requests, false);

// Empty the recycle bin permanently
Database.emptyRecycleBin(recordsToPurge);

// Rollback to a savepoint
Savepoint sp = Database.setSavepoint();
Database.rollback(sp);
```

`Database.countQuery` is worth knowing — it returns a count from a dynamic query string without retrieving rows, which the inline `SELECT COUNT()` form cannot do dynamically.

## Testing partial success

```java
@IsTest
static void validationFailureDoesNotAbortTheBatch() {
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(200);
    // one record deliberately violates a validation rule
    claims[50].Claim_Amount__c = -1;

    Test.startTest();
    List<Database.SaveResult> results = Database.insert(claims, false);
    Test.stopTest();

    Integer succeeded = 0;
    for (Database.SaveResult r : results) {
        if (r.isSuccess()) {
            succeeded++;
        }
    }

    Assert.areEqual(199, succeeded, 'One bad record should not block the other 199');
    Assert.isFalse(results[50].isSuccess(), 'The invalid record should fail');
    Assert.areEqual(
        StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION,
        results[50].getErrors()[0].getStatusCode(),
        'Failure should be the validation rule'
    );
}
```

Asserting on the specific index and the status code is what proves the alignment and the classification logic actually work.

## Practical guidance

**Use partial success for anything bulk.**

**Results are index-aligned** — do not reorder the input between the call and reading results.

**Branch on `getStatusCode()`** to separate transient failures from permanent ones.

**Log through a platform event**, so the record survives rollback.

**Remember partial success is not transaction isolation.** A later exception still rolls everything back.

**Use `isCreated()` on upsert results** to report inserts versus updates.

**Test the partial-success path explicitly**, with a deliberately bad record in a bulk set.
