# Fixing a Slow Database at Scale

#backend #databases #postgres #performance #interview

> **In one line:** "We're doing N requests a second and the database takes 5 seconds, so how do you fix it?" is really four questions in order. Is the number real? Where are the 5 seconds actually spent? What's the cheapest fix for that cause? How do you keep most of the traffic away from the database for good? This note is the playbook. The deep dives on each step are linked, not repeated.

---

## The Scenario

> *"Our API serves 10 million requests per second and responses currently take 5 seconds. The database is the bottleneck. How would you optimize it?"*

There's a trap in the question. Interviewers ask it to see whether you **jump to a solution** ("add Redis", "shard it") or **diagnose first**. The playbook:

```
0. Sanity-check the numbers        → what scale are we really at?
1. Find where the 5 s goes         → measure; don't guess
2. Fix the queries                 → biggest win, lowest cost
3. Fix connection handling         → pools, PgBouncer, Little's law
4. Take load off the database      → caching, replicas, precomputation
5. Fix the write path              → batching, async, partitioning
6. Scale out or change the store   → sharding, purpose-built databases
7. Protect it                      → timeouts, shedding, circuit breakers
```

Steps 1–3 fix most real incidents. Steps 4–6 are what "10M req/s" requires. Step 7 is what keeps the next slowdown from taking everything down with it.

---

## Step 0: Sanity-Check the Numbers

**10 million requests per second is enormous.** It's in the range of the largest internet services' *total* traffic. Do the arithmetic out loud:

| If "10M" means… | Average rate | Peak (×3–5) | What it implies |
|---|---|---|---|
| 10M requests **per day** | ~116 req/s | ~500 req/s | A single, well-indexed Postgres handles this easily. The 5 s is a query or pool bug, not a scale problem |
| 10M **per hour** | ~2,800 req/s | ~10k req/s | Still a single primary plus maybe replicas and a cache |
| 10M **per minute** | ~170k req/s | ~500k+ req/s | Caching is mandatory. Replicas, probably sharding for writes |
| 10M **per second** | 10M req/s | — | The database **cannot** see most of this traffic. It's a caching and CDN architecture question |

Reference capacity ([[Assets.3 - Numbers To Know]]): one Postgres primary does roughly **10k–50k writes/s**, and very roughly **tens to low hundreds of thousands of simple indexed reads/s** on large hardware. So 10M req/s hitting the DB directly would need hundreds of database nodes even with perfect queries.

Then ask the clarifying questions that change the answer:

| Question | Why it matters |
|---|---|
| **Read/write ratio?** | 99% reads → caching and replicas. Write-heavy → batching, queues, sharding |
| **Is it one endpoint or all of them?** | Usually one or two queries cause most of the load |
| **p50 or p99 is 5 s?** | p50 = 5 s means everything is broken (pools, locks, a missing index on the hot path). p99 = 5 s means a tail: one slow query, lock contention, GC, cold cache |
| **Was it always slow, or did it get slow?** | "Got slow" → data growth, a deploy, a plan change, bloat, a new access pattern |
| **How stale can the data be?** | Decides whether caching is allowed and with what TTL |
| **Consistency requirements?** | Decides whether read replicas are safe ([[06.12 - Replication and Failover#The Read Replica Correctness Problem]]) |

> 💡 Saying *"10M per second is the scale of the biggest internet services. Let me make sure I understand the real number, because the answer at 500 req/s is a missing index and the answer at 10M req/s is a CDN"* is a strong opening. It shows you think in orders of magnitude.

## Step 1: Find Where the 5 Seconds Go

"The database is slow" is a hypothesis, not a measurement. Request latency is a sum:

```
total = queue wait at LB/app             (overloaded workers, full threadpool)
      + connection pool wait              ← very often the biggest term
      + network to DB
      + query execution (planning + I/O + CPU + lock waits)
      + network back
      + serialization in the app          (big result sets through Pydantic/ORM)
```

### Measure each term

**From the application (tracing):** a span around **pool acquire** and a separate span around **query execute**. If acquire is 4.9 s and execute is 100 ms, your problem is concurrency, not the query.

```python
# asyncpg: time the two phases separately
async def fetch_user_orders(pool, user_id):
    t0 = time.perf_counter()
    async with pool.acquire() as conn:                       # ← pool wait
        t1 = time.perf_counter()
        rows = await conn.fetch(QUERY, user_id)              # ← execution
        t2 = time.perf_counter()
    metrics.histogram("db.pool_wait_ms").observe((t1 - t0) * 1000)
    metrics.histogram("db.query_ms").observe((t2 - t1) * 1000)
    return rows
```

**From Postgres, the top offenders by total time:**

```sql
-- Requires the pg_stat_statements extension (enable it on every production DB)
SELECT
    calls,
    round(total_exec_time::numeric / 1000, 1)        AS total_s,
    round(mean_exec_time::numeric, 1)                AS mean_ms,
    round(stddev_exec_time::numeric, 1)              AS stddev_ms,
    rows / NULLIF(calls, 0)                          AS rows_per_call,
    round(100.0 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0), 1) AS cache_hit_pct,
    left(query, 120)                                 AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 15;
```

Sort by **total** time, not mean. A 2 ms query called 50,000 times a second costs more than a 3 s report run once an hour.

**What's running and waiting right now:**

```sql
SELECT pid, state, wait_event_type, wait_event,
       now() - query_start AS running_for, left(query, 100) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY running_for DESC;
```

| `wait_event_type` | Means | Go to |
|---|---|---|
| `Lock` | Waiting on a row or table lock held by someone else | [[06.8 - Locking and Deadlocks]] |
| `IO` (`DataFileRead`) | Reading from disk: working set doesn't fit in memory, or a missing index | Step 2, more RAM |
| `LWLock` | Internal contention (buffer mapping, WAL) | High concurrency; fewer active connections |
| `Client` (`ClientRead`) | DB is waiting for the **app**. Often an idle-in-transaction connection | App holds transactions open across network calls ([[06.17 - Database Anti Patterns#4. Network Calls Inside Transactions]]) |
| *(null)*, state `active` | On CPU | Query is doing too much work: Step 2 |

**Then read the plan for the top query:**

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT id, total, status, created_at
FROM orders
WHERE customer_id = 42 AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

What to look for, in order ([[06.4 - Reading EXPLAIN ANALYZE]]):
1. **`Seq Scan`** on a big table with a selective filter → missing index.
2. **`Rows Removed by Filter: 2,400,000`** → the index doesn't cover the filter.
3. **Estimated rows vs actual rows off by 100×** → stale statistics or correlated columns → `ANALYZE`, extended statistics ([[06.5 - The Query Planner]]).
4. **`Sort` with `external merge Disk:`** → sorting on disk. You need an index that matches `ORDER BY`, or more `work_mem`.
5. **`Buffers: shared read=…`** large → coming from disk, not cache.

## Step 2: Fix the Queries (Biggest Win, Lowest Cost)

Almost every real "5 second" incident ends here. In rough order of how often each one is the culprit:

### 2.1 Missing or wrong index

```sql
-- Query filters by customer_id + status and sorts by created_at.
-- One composite index serves the filter AND the sort AND the LIMIT.
CREATE INDEX CONCURRENTLY idx_orders_customer_status_created
    ON orders (customer_id, status, created_at DESC);

-- Covering: add the selected columns so Postgres never touches the table (index-only scan)
CREATE INDEX CONCURRENTLY idx_orders_cust_cover
    ON orders (customer_id, created_at DESC) INCLUDE (total, status);

-- Partial: only index the rows you actually query
CREATE INDEX CONCURRENTLY idx_orders_pending
    ON orders (created_at) WHERE status = 'pending';
```

Typical result: **Seq Scan 4,800 ms → Index Scan 0.4 ms.** Rules:
- **Equality columns first, then range/sort columns.** `(customer_id, status, created_at)`, not `(created_at, customer_id)`.
- Always `CONCURRENTLY` in production, or the build locks writes ([[06.11 - Zero Downtime Migrations]]).
- Every index slows writes and uses memory. Remove unused ones (`pg_stat_user_indexes.idx_scan = 0`).

Full detail: [[06.3 - Indexes Deep Dive]].

### 2.2 The query can't use the index you have

```sql
-- ❌ function on the column: can't use an index on email
WHERE lower(email) = 'a@b.com'
-- ✅ expression index, or store normalized
CREATE INDEX CONCURRENTLY idx_users_email_lower ON users (lower(email));

-- ❌ implicit cast: comparing a text column to an integer parameter
WHERE phone = 9876543210
-- ✅ match types
WHERE phone = '9876543210'

-- ❌ leading wildcard
WHERE name LIKE '%singh'
-- ✅ trigram index (pg_trgm) or real search (06.15)

-- ❌ OR across different columns often defeats indexes
WHERE customer_id = 42 OR referrer_id = 42
-- ✅ UNION ALL of two indexed queries
```

### 2.3 N+1 queries from the ORM

One request → 1 query for the list + 1 query **per row**. 200 rows = 201 round trips at 1 ms each = 200 ms of pure latency, multiplied by every concurrent user.

```python
# ❌ N+1: lazy loading inside a loop
orders = (await session.scalars(select(Order).limit(200))).all()
for o in orders:
    print(o.customer.name)          # one query per order

# ✅ eager load: 2 queries total
orders = (await session.scalars(
    select(Order).options(selectinload(Order.customer)).limit(200)
)).all()
```

Detect it by **queries per request** in tracing. Anything over ~10 on a read endpoint deserves a look ([[06.17 - Database Anti Patterns#2. N+1 Queries]]).

### 2.4 Fetching too much

- `SELECT *` pulls large columns (JSONB, text) through the network and the ORM. Select only what the response needs.
- **Unbounded results:** a list endpoint without `LIMIT` is fine at 1,000 rows and an outage at 10M.
- **Offset pagination:** `OFFSET 100000` reads and discards 100,000 rows. Use keyset pagination:

```sql
-- ❌ gets slower with every page
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000;

-- ✅ constant time on any page (needs index on (created_at DESC, id DESC))
SELECT id, total, created_at FROM orders
WHERE (created_at, id) < ($1, $2)          -- the last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Full treatment: [[05.2 - Versioning Pagination and Filtering]].

### 2.5 Database health problems that look like slow queries

| Problem | Symptom | Fix |
|---|---|---|
| **Stale statistics** | Plan suddenly flipped to a seq scan after a bulk load | `ANALYZE table`. Tune autovacuum analyze thresholds |
| **Bloat** | Table or index far bigger than its live rows. Scans slow down over months | Tune autovacuum. `pg_repack` ([[06.7 - MVCC Vacuum and Bloat]]) |
| **Lock contention** | Queries wait on `Lock`. One hot row updated by everyone (counters!) | Shorter transactions. Move counters to Redis. `SKIP LOCKED` for queues |
| **Long-running transactions** | Vacuum can't clean up. Replicas lag. Locks held | `idle_in_transaction_session_timeout`, and never make network calls inside a transaction |
| **Working set > RAM** | `cache_hit_pct` < 99%. `IO` waits | More memory, fewer and smaller indexes, archive old data, partition |
| **Wrong planner costs on SSD** | Planner avoids indexes it should use | `random_page_cost = 1.1` on NVMe ([[06.5 - The Query Planner]]) |

## Step 3: Fix Connection Handling

### Little's law tells you why slow queries become outages

```
connections busy  =  throughput  ×  time each query holds a connection
```

| Throughput | Query time | Connections needed |
|---|---|---|
| 5,000 queries/s | 2 ms | **10** |
| 5,000 queries/s | 50 ms | **250** |
| 5,000 queries/s | 5 s | **25,000** |

Postgres is happiest with roughly **cores × 2** *active* connections, around 20 on an 8-core box ([[06.9 - Connection Pooling and PgBouncer]]). So when a query slows from 2 ms to 50 ms, the pool runs out. Requests then **queue for a connection**, and that queue wait is often most of the "5 seconds". The DB looks only moderately busy while users time out.

> 💡 **This is why fixing one slow query can fix "everything is slow".** It frees connections, which removes the pool queue that every other endpoint was stuck in.

### What to do

- **Size pools from math, not hope:** `per-process pool × processes × pods` must stay under what the DB (or PgBouncer) allows. 20 pods × 4 workers × 20 = 1,600 connections will overwhelm Postgres ([[01.10 - Connection Pools and Limits]]).
- **Put PgBouncer in transaction mode** in front of Postgres. Thousands of client connections multiplex onto ~20–50 server connections.
- **Set pool acquire timeouts.** Fail fast after 1–2 s with a 503 instead of waiting forever.
- **Hold connections briefly.** No HTTP calls, LLM calls or `sleep` while a transaction is open.

```python
pool = await asyncpg.create_pool(
    DSN,
    min_size=5,
    max_size=20,                       # per process. Multiply by processes × pods!
    command_timeout=2.0,               # client-side guard
    server_settings={
        "statement_timeout": "2000",                     # ms. DB kills runaway queries
        "idle_in_transaction_session_timeout": "5000",
    },
)
```

## Step 4: Take Load Off the Database

Once each query is efficient, the remaining lever is **making fewer of them**. This is the step that makes 10M req/s possible.

### The layered cache: arithmetic for 10M req/s

Each layer absorbs most of the traffic that reaches it:

```
10,000,000 req/s
   │  CDN / edge cache, 95% hit (public, cacheable GETs)
   ▼
   500,000 req/s reach your app
   │  in-process cache (LRU, 1–5 s TTL), 80% hit
   ▼
   100,000 req/s
   │  Redis cluster, 95% hit
   ▼
     5,000 req/s
   │  read replicas (× 3)
   ▼
     ~1,700 req/s per replica   ← an easy load for Postgres
```

The exact hit ratios are illustrative. The point is that **no database serves 10M req/s. A stack of caches does, and the database serves the leftovers.**

| Layer | Latency | Good for | Watch out for |
|---|---|---|---|
| **CDN / HTTP cache** | 1–20 ms at the edge | Public or semi-public GETs: product pages, configs, images | Personalized data. Invalidation via purge or short TTL + `stale-while-revalidate` ([[03.5 - HTTP Caching]], [[03.3 - CDN]]) |
| **In-process cache** | ~µs | Very hot, small, tolerant of a few seconds of staleness: feature flags, config, top-N lists | Each pod has its own copy, so they're inconsistent. Memory per pod |
| **Redis** | 0.2–1 ms | Shared cache, sessions, counters, rate limits, leaderboards | Stampedes, hot keys, invalidation ([[07.2 - Cache Strategies and Invalidation]], [[07.3 - Stampede Hot Keys and Negative Caching]]) |
| **Read replicas** | Same as primary | Read-heavy queries that can tolerate replication lag | Read-your-writes. Lag under load ([[06.12 - Replication and Failover]]) |

### Cache-aside with stampede protection

The basic pattern plus the two production details that matter: TTL **jitter** (so keys don't all expire at once) and **single-flight** (only one request recomputes a missing key).

```python
import json
import random

import redis.asyncio as redis

r = redis.from_url("redis://cache:6379", decode_responses=True)


async def get_product(product_id: int) -> dict:
    key = f"product:v2:{product_id}"                      # version in key = easy mass invalidation
    if (cached := await r.get(key)) is not None:
        return json.loads(cached)

    # Single-flight: only one caller rebuilds. Others wait briefly and re-read.
    lock = r.lock(f"lock:{key}", timeout=5, blocking_timeout=2)
    if await lock.acquire():
        try:
            if (cached := await r.get(key)) is not None:  # someone filled it while we waited
                return json.loads(cached)
            product = await db_fetch_product(product_id)
            ttl = 300 + random.randint(0, 60)             # jitter: avoid synchronized expiry
            await r.set(key, json.dumps(product), ex=ttl)
            return product
        finally:
            await lock.release()

    # Couldn't get the lock in time: fall back to the DB rather than fail
    return await db_fetch_product(product_id)


async def update_product(product_id: int, data: dict) -> None:
    await db_update_product(product_id, data)
    await r.delete(f"product:v2:{product_id}")             # invalidate AFTER the commit
```

More Redis patterns with code (hashes, sorted sets, rate limiting, locks, streams): [[Redis]] and [[03.5 - Redis Patterns]].

### Precompute instead of computing per request

| Technique | When |
|---|---|
| **Materialized view** refreshed every N minutes (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) | Dashboards, aggregates, leaderboards that can lag |
| **Denormalized read table** updated by events or CDC | Hot read path that joins 5 tables ([[09.4 - Change Data Capture]], [[02.22 - CQRS]]) |
| **Counters in Redis** (`INCR`), flushed to the DB periodically | Like and view counts. Removes the hot-row lock |
| **Request coalescing** at the app or edge | Thousands of identical concurrent requests for the same key → one DB query |

## Step 5: Fix the Write Path

If the slowness is on writes:

| Technique | Effect |
|---|---|
| **Batch inserts** (`executemany`, multi-row `INSERT`, `COPY`) | 10–100× fewer round trips and commits |
| **Async writes via a queue** | API returns 202 and a worker writes. Absorbs spikes. The user sees eventual consistency ([[08.1 - Why Background Work Exists]]) |
| **Fewer indexes on write-heavy tables** | Every index is extra work on every insert |
| **Shorter transactions** | Less lock time, less contention |
| **Avoid hot rows** | Shard the counter (`counter_shard_0..15`) or move it to Redis |
| **Time-based partitioning** | Inserts go to a small current partition, and old data is dropped with `DROP PARTITION` instead of `DELETE` ([[06.13 - Partitioning and Sharding]]) |
| **Primary key choice** | Random UUIDv4 keys scatter inserts across the B-tree. Use bigint or UUIDv7 ([[06.17 - Database Anti Patterns#5. UUIDv4 Primary Keys]]) |

## Step 6: Scale Out, or Change the Store

Only after Steps 1–5. Each of these adds permanent operational complexity.

### Vertical first

A bigger instance (more RAM so the working set fits, faster disks, more cores) is the cheapest scale-out you'll ever do. Modern cloud Postgres goes to hundreds of cores and terabytes of RAM. Take it as far as it goes first.

### Partitioning (one database, split tables)

Range or list partitioning by time or tenant keeps indexes small and makes data retention cheap. Note that this is **data** partitioning, not the network partition in CAP ([[01.11 - Distributed Concepts]]).

### Sharding (many databases)

When **writes** or **data size** outgrow one primary:

| Decision | Guidance |
|---|---|
| **Shard key** | The column on almost every query's `WHERE`: `tenant_id`, `user_id`. A bad key means cross-shard queries everywhere |
| **Scheme** | Hash (even spread, no range scans) vs range (range scans, risk of hot shards) vs directory/lookup (flexible, extra hop) |
| **Cross-shard operations** | Joins, transactions and unique constraints across shards become application problems |
| **Tooling** | Citus (Postgres), Vitess (MySQL), or managed distributed SQL (CockroachDB, Spanner, YugabyteDB) |

Full detail: [[06.13 - Partitioning and Sharding]], [[Assets.2 - DB Selection and Checklists]].

### Move the workload to a store built for it

| Workload | Better home |
|---|---|
| Key-value lookups at huge scale | DynamoDB, Cassandra/ScyllaDB, Redis |
| Analytics and aggregations over billions of rows | ClickHouse, BigQuery, a warehouse. Not OLTP Postgres |
| Full-text search | Elasticsearch/OpenSearch ([[06.15 - Search - Postgres vs Elasticsearch]]) |
| Time series / metrics | TimescaleDB, Prometheus, ClickHouse |
| Append-only event history | Kafka as the log, with materialized views downstream ([[09.1 - Queue vs Log]]) |

## Step 7: Protect the Database

Even after it's fast, make sure the next problem can't cascade:

- **`statement_timeout`** on every connection. A runaway query is killed instead of holding a connection forever.
- **Pool acquire timeout** plus **load shedding**: return 503 early instead of queuing ([[11.4 - Backpressure and Load Shedding]]).
- **Circuit breaker** around the DB in callers that have a fallback (serve stale cache) ([[11.3 - Circuit Breakers and Bulkheads]]).
- **Rate limits** per client or tenant so one noisy customer can't take the whole DB ([[11.5 - Rate Limiting and Quotas]]).
- **Bulkheads:** separate pools, or a separate replica, for batch jobs and reports, so analytics can't starve the API.
- **Graceful degradation:** serve cached or partial data when the DB is struggling ([[11.6 - Graceful Degradation]]).

## Effort vs Impact Cheat Sheet

| Fix | Effort | Typical impact | Do it when |
|---|---|---|---|
| Add or fix an index | Minutes | 10–10,000× on that query | `Seq Scan` / `Rows Removed by Filter` on a hot query |
| Fix N+1 | Hours | 10–100× fewer queries | Queries-per-request > 10 |
| Keyset pagination | Hours | Constant time on deep pages | `OFFSET` on large tables |
| Pool sizing + PgBouncer | Hours | Removes the queue wait (often seconds) | Pool wait ≫ query time |
| `statement_timeout`, acquire timeout | Minutes | Turns outages into errors | Always |
| Redis cache-aside | Days | 90%+ fewer reads | Read-heavy, staleness acceptable |
| Read replicas | Days | ×N read capacity | Read-heavy, lag acceptable |
| Materialized views / denormalization | Days–weeks | Removes expensive joins from the hot path | Same expensive aggregate on every request |
| Vertical scaling | Hours (plus cost) | ×2–4 | Working set doesn't fit in RAM |
| Partitioning | Weeks | Smaller indexes, cheap retention | Tables > 50–100M rows, time-ordered |
| Sharding | Months | Unbounded write scale | Writes or size exceed one primary. Last resort |
| CDN in front | Days | Removes most traffic entirely | Public, cacheable GETs at very high RPS |

## The Two-Minute Interview Answer

"First I'd check the number. 10M requests a second is the scale of the biggest services on the internet, and no database serves that directly. If it's 10M a day, that's around 120 a second, and the 5 seconds is almost certainly a query or pool bug, not a scale problem.

Then I'd measure before changing anything. I'd split the latency into pool wait and query execution with tracing, look at pg_stat_statements sorted by total time to find the few queries that matter, check pg_stat_activity for lock or IO waits, and run EXPLAIN ANALYZE with BUFFERS on the top offenders.

The usual fixes, cheapest first: the right composite or covering index, removing N+1s, selecting only the needed columns, keyset instead of offset pagination, and fixing stale statistics or bloat. Then connections. By Little's law, slow queries multiply the connections you need, so the pool runs out and requests queue. That queue is often most of the 5 seconds. So: PgBouncer in transaction mode, pools sized from the math, and statement and acquire timeouts so the system fails fast.

For real scale, the goal is that the database sees only a small fraction of requests: a CDN for cacheable responses, a short-TTL in-process cache, Redis cache-aside with jittered TTLs and single-flight against stampedes, read replicas where some lag is acceptable, and precomputed views for expensive aggregates. On the write side: batching, queues, and partitioning. Sharding by a key like tenant ID only once writes outgrow a single primary, because it's the most expensive change to live with. Finally, timeouts, load shedding and circuit breakers so one slow query can't cascade into an outage."

**Likely follow-ups:**
- *How do you know an index will help before adding it?* `EXPLAIN` shows the scan type and the rows removed by the filter. Test on a production-sized copy. `hypopg` lets you try hypothetical indexes without building them.
- *Cache invalidation: how do you keep it correct?* Delete the key after the DB commit (not before), keep TTLs short as a safety net, version keys for bulk invalidation, and use CDC-driven invalidation when correctness matters ([[07.2 - Cache Strategies and Invalidation]]).
- *Read replica returns stale data right after a user writes. Fix?* Read-your-writes: route that user's reads to the primary for a few seconds after a write, or wait for the replica to reach the write's LSN ([[06.12 - Replication and Failover#The Read Replica Correctness Problem]]).
- *When would you choose sharding over replicas?* Replicas scale **reads** only. Every write still goes to one primary. Sharding is for when **writes** or **total data size** exceed a single primary.
- *Why not just switch to NoSQL?* It trades query flexibility, joins and transactions for scale-out. That's right for a known key-value access pattern at huge scale, and wrong as a fix for missing indexes.
