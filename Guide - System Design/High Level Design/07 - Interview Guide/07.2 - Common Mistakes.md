# Common Interview Mistakes

> **Revision tags:** #interview #mistakes  
> **Related:** [[07.1 - How HLD Interviews Work]] | [[07.3 - Communicating Tradeoffs]]

---

## Mistakes Before You Start Drawing

### Mistake 1: Starting Without Clarifying Requirements

```
Interviewer: "Design a rate limiter."

Bad response:
  [immediately starts drawing]
  "So we'll have a Redis cluster with token bucket algorithm..."

Good response:
  "Before I design, can I ask a few questions?
   Is this a standalone service, or embedded in API Gateway?
   What's the expected throughput — requests per second?
   Are we rate limiting per user, per IP, per API key, or all three?
   Do we need distributed rate limiting across multiple servers?"
```

Skipping clarification is the single most common way to waste your own time and signal lack of experience.

---

### Mistake 2: Treating Scale as Constant

Every design decision is scale-dependent. A system for 100 users looks nothing like one for 100M.

```
Bad: "I'll use microservices and Kafka for this."
     (for a system serving 500 users)

Good: "At 500 users, a modular monolith with PostgreSQL is entirely sufficient.
      If we expect to grow to 50K users in 2 years, I'd add a Redis cache
      and read replica. Kafka would be premature optimization at this stage."
```

Always derive architecture from the estimation, not from habit.

---

### Mistake 3: Not Writing Down Assumptions

Every assumption you make silently is a risk. Write them down:

```
Assumptions I'm working with:
  - 100M DAU
  - Read:write ratio = 100:1
  - 99.9% availability required
  - Eventual consistency acceptable for feed
  - No multi-region requirement (single region, US)
```

This protects you: if the interviewer meant something different, they'll correct you early — not 20 minutes in when you've built on a wrong assumption.

## Mistakes During Design

### Mistake 4: Memorized Architectures Without Justification

Some candidates memorize "Instagram architecture" and draw it regardless of the actual problem.

```
Bad: "For the feed, we'll use fan-out on write with Redis sorted sets,
      a Kafka topic for post events, and Cassandra for post storage."
     (stated without any reference to the actual requirements)

Good: "Given the read:write ratio is 100:1 and we need sub-100ms feed loads,
      fan-out on write makes sense for most users — we pre-build the feed in Redis.
      For accounts with >1M followers, fan-out on read is cheaper — we fetch
      their posts at read time instead. This hybrid approach is what Instagram uses."
```

The architecture is the same. The difference is justification from requirements.

---

### Mistake 5: Perfect Happy Path, No Failure Thinking

A very common gap for mid-level engineers.

```
Bad: [Designs the entire checkout flow perfectly]
     "...and that's the checkout system."

Good: "Let me also cover what happens when things go wrong.
      If the payment service is unavailable: the checkout fails fast via circuit breaker —
      we don't want Order Service threads blocked. The inventory reservation is released.
      If the DB write succeeds but Kafka emit fails: we use the outbox pattern —
      the DB and outbox row are written atomically, so the event will be picked up
      by the outbox processor on its next run."
```

---

### Mistake 6: Wrong Level of Detail

Two failure modes:
- Going too deep on one unimportant component (spending 15 minutes on auth for a URL shortener)
- Staying too shallow on the core problem (mentioning "we'll add a cache" without specifying what's cached, how it's invalidated, TTL)

**Rule:** Go deep on the component that is the interesting/hard part of the specific problem. For a URL shortener: redirect latency and code generation. For a chat system: WebSocket connection management and message routing.

---

### Mistake 7: Technology Namedropping Without Substance

```
Bad: "We'll use Kafka, Redis, Elasticsearch, Cassandra, and gRPC."

Good: "For the event stream, I'm thinking Kafka because we need replay capability —
      the analytics consumer wants to re-process historical events. If we didn't
      need replay, SQS would be simpler operationally."
```

Every technology choice needs a "because." Naming technologies without reasoning is a red flag.

---

### Mistake 8: Inconsistent Scale

When your design components don't match the stated scale.

```
Bad:
  "We're designing for 10M users."
  [later in the design]
  "We'll use a single PostgreSQL instance."
  
  At 10M users with 100K read QPS, a single PostgreSQL instance will be crushed.
  You need read replicas or a caching layer at minimum.
```

After estimating QPS, check that every component you propose can handle that QPS.

---

### Mistake 9: Choosing the "Cool" Technology Over the Right One

```
Bad: "For the session store, I'll use Cassandra because it's horizontally scalable."
     (When Redis would perfectly serve this use case with far less complexity)

Good: "Sessions are key-value with TTL — Redis is the obvious choice.
      It's in-memory, has native TTL support, and handles millions of
      session reads per second easily. Cassandra would be over-engineering here."
```

Prefer simple and correct over complex and impressive.

## Mistakes During Discussion / Deep-Dive

### Mistake 10: Defending Suboptimal Choices Inflexibly

Interviewers often push back on your choices to see how you react.

```
Interviewer: "Why not use Cassandra here instead of PostgreSQL?"

Bad response: "No, PostgreSQL is definitely the right choice."
             (defensive, closed)

Good response: "Good question — Cassandra would give us better write throughput
               at scale. I chose PostgreSQL because we need ACID transactions
               across multiple tables in the checkout flow, which Cassandra
               doesn't support. If we're willing to handle consistency in the
               application layer, Cassandra becomes a viable option.
               What constraint matters most to you here?"
```

Interviewers respect candidates who can engage with challenges thoughtfully.

---

### Mistake 11: Vague Answers to "How Would You Scale This?"

This question will come. Have a concrete answer.

```
Bad: "We'd scale horizontally."

Good: "Let's think through the bottlenecks.
      The API tier is stateless — we scale horizontally behind the load balancer,
      adding instances as QPS grows. That's straightforward.
      The database is the constraint. For reads, we add read replicas and a Redis cache
      — that gets us 10× read capacity. For writes, at 10K write QPS a well-configured
      PostgreSQL can handle it. If we go to 100K write QPS, we'd need to shard by
      user_id, which adds complexity. I'd cross that bridge when the metrics demand it."
```

---

### Mistake 12: Not Handling "What If 100× Scale?"

Prepare for this explicitly. When asked:

```
Structure:
  1. Identify which component becomes the bottleneck first
  2. Address that specific bottleneck
  3. Proceed to the next bottleneck

Example (URL Shortener at 100× scale):
  "At 100× scale, we go from 3,500 to 350,000 redirect reads/s.
  Redis can handle 500K operations/s on a single node — the cache itself is fine.
  The bottleneck becomes the Redis→DB fallback on cache miss.
  Solution: increase cache TTL, pre-warm the cache for trending URLs,
  add read replicas, or switch to a key-value store like DynamoDB
  that scales horizontally by default. At 350K QPS, I'd move to
  a Redis Cluster with consistent hashing across 5 nodes."
```

## The Pre-Interview Checklist

Before any HLD interview:

```
Mental preparation:
  [ ] Know the framework: clarify → estimate → design → fail → scale
  [ ] Have estimation numbers memorized (see Assets/estimation-cheatsheet)
  [ ] Know your go-to components cold: LB, cache, DB choices, queue, CDN
  [ ] Practice drawing clean architecture diagrams (even on paper)

For the specific company:
  [ ] Research their tech stack (don't propose tech they famously avoid)
  [ ] Know their product — your example design will use their domain

During:
  [ ] Ask before you design
  [ ] Write down assumptions
  [ ] Draw left to right
  [ ] Label everything
  [ ] Think out loud
  [ ] Address failures unprompted
```
