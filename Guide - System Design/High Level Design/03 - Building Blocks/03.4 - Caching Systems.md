# Caching Systems

> **Revision tags:** #building-blocks #caching  
> **Related:** [[03.3 - CDN]] | [[03.5 - Redis Patterns]] | [[02.4 - Architecture Decisions]]

## What It Is

A cache is a fast, temporary storage layer that holds copies of data so future requests for that data can be served faster than fetching from the original (slower) source.

```
Without cache:
Request → Service → Database (100ms)

With cache:
Request → Service → Cache (1ms) → done
                 → Cache miss → Database (100ms) → populate cache → done
```

---

## Why It Exists

- **Latency:** Memory access (~100ns) is orders of magnitude faster than disk (100µs) or network (1ms+)
- **Throughput:** A single cache can serve thousands of reads per second; a DB under load degrades
- **Cost:** Fewer DB queries = smaller DB instance needed
- **Availability:** Cache can serve stale data when DB is down

---

## Where Caches Live (Caching Layers)

```
Browser Cache          → client-side, HTTP cache headers
CDN Cache              → edge, geographically distributed
Application Cache      → in-process memory (e.g., Python dict, Guava LoadingCache)
Distributed Cache      → Redis, Memcached — shared across service instances
Database Cache         → query cache, buffer pool (internal to the DB)
Read Replicas          → separate DB nodes for read-only queries
```

Each layer has different latency, size, and consistency characteristics. Systems often use multiple layers.

## Caching Strategies

### Cache-Aside (Lazy Loading)

The application manages the cache explicitly. Cache is populated on demand.

```
def get_user(user_id):
    # Check cache first
    user = cache.get(f"user:{user_id}")
    if user:
        return user  # cache hit

    # Cache miss: fetch from DB
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)

    # Populate cache for next time
    cache.set(f"user:{user_id}", user, ttl=3600)
    return user
```

**Pros:** Only caches what's actually requested. Cache failure doesn't break reads (fall back to DB).  
**Cons:** First request always misses (cold start). Data can be stale until TTL expires.

**Most common pattern in production.**

### Write-Through

Every write goes to both the cache and the DB synchronously.

```
def update_user(user_id, data):
    db.update("UPDATE users SET ... WHERE id = ?", user_id, data)
    cache.set(f"user:{user_id}", data, ttl=3600)
```

**Pros:** Cache is always up-to-date. No stale reads.  
**Cons:** Every write is slower (double write). Cache fills with data that may never be read.

### Write-Behind (Write-Back)

Write to cache immediately; asynchronously flush to DB later.

```
Write → Cache (immediate, returns to client)
             ↓ (async, after delay)
           Database
```

**Pros:** Very fast writes. Batching DB writes reduces DB load.  
**Cons:** Data loss if cache crashes before flush. Complexity in ordering and consistency.

**Used for:** High write throughput scenarios where some data loss is acceptable (metrics, counters, non-critical state).

### Refresh-Ahead

Proactively refresh cache before it expires, predicting which entries will be needed.

```
When item in cache has 10% TTL remaining:
  → Asynchronously fetch fresh data from DB
  → Update cache
  → Client always gets cached data (no cold miss)
```

**Pros:** Eliminates cache miss latency for frequently accessed data.  
**Cons:** Wastes resources refreshing data that may not be requested again.

## Cache Eviction Policies

When the cache is full, old entries must be removed to make room. Policy determines which ones.

| Policy | Rule | Best For |
|---|---|---|
| **LRU** (Least Recently Used) | Evict the entry that was accessed least recently | General purpose — the most common |
| **LFU** (Least Frequently Used) | Evict the entry accessed least often | When frequency matters more than recency |
| **FIFO** | Evict the oldest entry (by insertion time) | Simple, less effective |
| **Random** | Evict a random entry | Surprisingly effective, zero overhead |
| **TTL** | Entries expire after a fixed time, regardless of access | When freshness is the primary concern |

**Redis default:** LRU with optional TTL per key.

## Cache Invalidation Strategies

The hardest problem in caching ("there are only two hard things in computer science...").

### TTL (Time-to-Live)

Entries expire after a fixed duration. Simple. May serve stale data up to TTL duration.

```
cache.set("product:123", product_data, ttl=300)  # expires in 5 minutes
```

### Event-based invalidation

When the underlying data changes, explicitly invalidate the cache entry.

```
def update_product(product_id, data):
    db.update(...)
    cache.delete(f"product:{product_id}")  # immediate invalidation
```

**Problem:** If the DB write succeeds but cache delete fails → stale data persists.  
**Solution:** Accept occasional staleness, or use a cache-aside pattern where the next read will repopulate from DB.

### Cache-busting by versioning

Include a version in the cache key. Updating the version effectively invalidates all old entries.

```
cache_key = f"product:{product_id}:v{schema_version}"
```

## The Cache Stampede (Thundering Herd)

When a popular cache entry expires, many concurrent requests all miss simultaneously and all attempt to fetch from the DB at once.

```
10,000 req/s for product:123
TTL expires at T=0
T=0 → 10,000 requests miss cache → 10,000 DB queries → DB overloaded
```

**Solutions:**

1. **Mutex/Lock:** Only one request fetches from DB; others wait for it to populate the cache.
```python
if not cache.exists(key):
    if lock.acquire(key, timeout=5):
        # fetch and populate
        data = db.fetch(...)
        cache.set(key, data, ttl=300)
        lock.release(key)
    else:
        # wait and retry
        time.sleep(0.1)
        return get_from_cache_or_db(key)
```

2. **Probabilistic early expiration:** Randomly start refreshing a cache entry before it expires, based on a probability that increases as TTL decreases. No locking needed.

3. **Stale-while-revalidate:** Return stale data immediately while refreshing in the background. No thundering herd because users always get a response.

## Cache Sizing

```
Cache size = hot_data_fraction × total_working_set

Rule of thumb: 20% of data handles 80% of requests (Pareto)

Example:
  Total product catalog = 500 GB
  Hot 20% = 100 GB
  Cache 100 GB in Redis → covers 80% of requests
```

Start small and measure hit rate. A hit rate below 80% suggests undersized cache or poor key design.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Cache server down | All requests fall through to DB | Circuit breaker, graceful DB fallback |
| Cache stampede | DB overloaded on cache expiry | Mutex, stale-while-revalidate |
| Memory exhaustion | Evictions remove hot data, hit rate drops | Set eviction policy, right-size cache |
| Stale data | Users see outdated information | Short TTLs or event-based invalidation |
| Cold start | New cache instance serves no traffic, DB overloaded | Pre-warm cache on startup, traffic ramping |

- Know cache-aside as the default pattern
- Know LRU eviction by default
- Know the thundering herd problem and at least one mitigation
