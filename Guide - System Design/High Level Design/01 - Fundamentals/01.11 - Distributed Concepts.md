## Partitioning and Sharding

### What It Is

**Partitioning** = splitting data into pieces so each piece lives on a different node.  
**Sharding** = horizontal partitioning of a database (most common usage in interviews).

A single machine has finite storage and write throughput. When you exceed it, you partition data across multiple machines.

### Partitioning Strategies

**Range partitioning:**  
Assign contiguous ranges of a key to a shard.

```
Shard 1: user_id  1 – 1,000,000
Shard 2: user_id  1,000,001 – 2,000,000
Shard 3: user_id  2,000,001 – 3,000,000
```

Pros: Simple range queries.  
Cons: Hot spots if data or writes concentrate in one range (e.g., sequential IDs all hit Shard 3 when it's the latest).

**Hash partitioning:**  
Apply a hash function to the partition key; use the hash modulo N to pick a shard.

```
shard = hash(user_id) % num_shards
```

Pros: Even distribution, no hot spots.  
Cons: Range queries are impossible (data is scattered); resharding is expensive.

**Consistent hashing:**  
Arrange shards on a virtual ring. Data maps to the nearest shard clockwise. Adding/removing nodes only moves a fraction of keys.

```
Ring:  [Shard A at 0°] ... [Shard B at 120°] ... [Shard C at 240°]
Key k: hash(k) maps to position → assigned to the next shard clockwise
```

Used by: Cassandra, Amazon DynamoDB, Redis Cluster.  
Advantage: Minimal data movement when scaling.

### Shard Key Selection — Critical

The shard key determines the partition. A bad shard key causes hot spots.

**Bad:** Shard by timestamp (all writes go to the "current" shard).  
**Bad:** Shard by geography if 90% of users are in one region.  
**Good:** Shard by user_id (hash) — even distribution.  
**Good:** Shard by tenant_id for multi-tenant SaaS — tenant data stays together.

### Cross-Shard Queries

Queries that need data from multiple shards are expensive — they require a scatter-gather across all shards and an aggregation step. Design data models to minimize cross-shard queries.

## Replication

### What It Is

Copying data to multiple nodes so that:
- The system survives node failures (fault tolerance)
- Reads can be served from multiple nodes (read scalability)

### Replication Topologies

**Single-leader (Primary/Replica):**
One node accepts all writes (leader). Changes replicate to followers.

```
[Leader] ──writes──→ [Replica 1]
         ──writes──→ [Replica 2]
```

Reads can go to replicas.  
Writes are limited to leader's capacity.  
Leader failure requires failover (electing a new leader).

**Multi-leader:**  
Multiple nodes accept writes. Used for multi-datacenter or offline-capable systems.

```
[DC1 Leader] ←──sync──→ [DC2 Leader]
```

Writes can conflict → need conflict resolution strategy.  
Used by: CouchDB, MySQL Group Replication, Google Docs (OT).

**Leaderless (Dynamo-style):**  
Any node accepts reads or writes. Uses quorum reads/writes for consistency.

```
Write quorum W: write must succeed on W nodes
Read quorum  R: read must succeed on R nodes
If W + R > N: guaranteed to see the latest write
```

Used by: Cassandra, DynamoDB, Riak.

### Sync vs Async Replication

**Synchronous:** Leader waits for replica to acknowledge before confirming write.
- Durable: replica is always up-to-date
- Slow: write latency includes replica round-trip
- Unavailable if replica is slow/down (or use semi-sync: wait for at least one replica)

**Asynchronous:** Leader confirms write immediately; replica catches up later.
- Fast: write latency is just local disk write
- Risk: if leader crashes before replica catches up, data loss

Most production databases use **asynchronous replication by default** with options for synchronous.

### Replication Lag

In async replication, replicas trail the leader by some amount (milliseconds to seconds under normal conditions, more under load).

Implications:
- Reads from replicas may be stale
- If a user writes then reads from a replica, they may not see their own write (violates read-your-writes consistency)
- Solutions: Read-after-write consistency (route reads to leader for the same user session), or sticky routing

## Consensus

### The Problem

In a distributed system with multiple nodes, how do you get all nodes to agree on a single value or decision — even if some nodes fail or messages are delayed?

Examples of consensus problems:
- Which node is the leader?
- Did this transaction commit?
- Is this configuration value X or Y?

### Why It's Hard

The **FLP Impossibility Result** proves that no deterministic consensus algorithm can guarantee termination in an asynchronous network if even one node can crash. Real systems work around this with timeouts and probabilistic guarantees.

### Consensus Algorithms

**Paxos:** The foundational algorithm. Correct but notoriously hard to understand and implement. Used as the basis for many systems.

**Raft:** Designed to be understandable. Same guarantees as Paxos, clearer leader-based model.

```
Leader elected → Leader accepts writes → Replicates to followers → 
Majority acknowledge → Leader commits → Notifies followers
```

Used by: etcd (Kubernetes), CockroachDB, TiKV, Consul.

**Viewstamped Replication, Zab (ZooKeeper):** Variants with similar properties.

### Quorum

Quorum = minimum number of nodes that must agree for an operation to proceed.

```
For N nodes: quorum = N/2 + 1 (majority)
3 nodes: quorum = 2
5 nodes: quorum = 3
```

Any two majorities must overlap by at least one node → the overlapping node ensures the latest write is always visible.

### Practical Uses in System Design

- **Leader election:** ZooKeeper, etcd (used by Kubernetes master, Kafka controller)
- **Distributed locks:** Require consensus to ensure only one holder
- **Configuration management:** etcd stores Kubernetes cluster config with consensus
- **Replicated state machines:** Any system where all replicas must apply operations in the same order

## Failure Domains

### What It Is

A **failure domain** is a set of components that share a common failure mode — if one fails, all of them can fail.

Understanding failure domains helps you place redundancy at the right boundaries.

### Failure Domain Hierarchy (Cloud)

```
Hardware failure (single disk, NIC)
    ↓
Server failure (single VM/physical machine)
    ↓
Rack failure (power strip, top-of-rack switch)
    ↓
Availability Zone failure (AZ) — datacenter building, power grid
    ↓
Region failure (rare: natural disaster, major infrastructure failure)
```

### Designing Across Failure Domains

**3-AZ deployment (common cloud pattern):**

```
Region us-east-1
├── AZ us-east-1a: [App servers] [DB primary]
├── AZ us-east-1b: [App servers] [DB replica]
└── AZ us-east-1c: [App servers] [DB replica]

Load balancer distributes across all AZs.
If 1a goes down: 1b and 1c continue serving (quorum maintained).
```

**Multi-region:** For disaster recovery or global low-latency. Higher cost and complexity, needed for 99.99%+ availability SLAs.

## Blast Radius Thinking

### What It Is

**Blast radius** = the scope of impact when a component fails.

A good architecture minimizes blast radius: a failure in one part of the system should affect the smallest possible set of users and functionality.

### Blast Radius Reduction Techniques

**Cell-based architecture:** Divide the system into independent "cells" (e.g., by user shard or geography). A failure in Cell 1 doesn't affect Cell 2.

```
[ Cell 1: Users A-F ]    [ Cell 2: Users G-M ]    [ Cell 3: Users N-Z ]
Each cell has its own full stack (API + DB + Cache)
```

**Bulkheads:** Separate thread pools, connection pools, or circuit breakers per downstream service. Slow downstream A doesn't exhaust resources for downstream B.

**Feature flags:** Roll out changes to 1% of traffic first. Blast radius = 1%.

**Deployment rings:** Deploy to internal users → 1% → 10% → 100%. Catch failures before full rollout.

**Hard dependencies vs soft dependencies:** Classify which services are critical-path (hard) vs nice-to-have (soft). Soft dependencies should fail gracefully, not bring down the whole request.

### Blast Radius in Interviews

When designing failure handling, explicitly state:
- "If the Recommendation Service is down, we'll return an empty list rather than fail the entire product page."
- "We shard by user_id so a shard failure affects at most X% of users."
- "We deploy per-region so a regional failure doesn't affect other regions."

This is the kind of thinking that distinguishes senior-level design.
