# Complex Forms

Field arrays, multi-step wizards, autosave and conditional fields — the patterns that appear once a form stops being a flat list of inputs.

## Field arrays

```jsx
import { useFieldArray } from "react-hook-form";

function LineItems() {
  const { control, register } = useFormContext();
  const { fields, append, remove, move } = useFieldArray({
    control,
    name: "items",
  });

  return (
    <>
      {fields.map((field, index) => (
        <div key={field.id}>          {/* field.id — NOT index */}
          <input {...register(`items.${index}.name`)} />
          <input {...register(`items.${index}.qty`, { valueAsNumber: true })} />
          <button type="button" onClick={() => remove(index)}>Remove</button>
        </div>
      ))}
      <button type="button" onClick={() => append({ name: "", qty: 1 })}>
        Add item
      </button>
    </>
  );
}
```

The critical detail: **`key={field.id}`, never `key={index}`**. RHF generates a stable id per row precisely because index keys cause state to attach to the wrong row after a removal or reorder ([[16.6 - Lists and Keys]]).

The field name is a path string — `items.0.name` — which is how RHF addresses nested values without nesting components.

`valueAsNumber` matters: form inputs produce strings, and a numeric field validated against `z.number()` fails without it.

## Nested and dynamic schemas

```ts
const schema = z.object({
  items: z.array(
    z.object({
      name: z.string().min(1, "Required"),
      qty: z.number().int().positive(),
    })
  ).min(1, "Add at least one item"),
});
```

Errors arrive at matching paths:

```jsx
errors.items?.[index]?.name?.message   // per-row
errors.items?.root?.message            // array-level ("add at least one")
```

Array-level errors landing under `root` rather than on the array itself is a common confusion.

## Conditional fields

```jsx
function PaymentFields() {
  const { control, register } = useFormContext();
  const method = useWatch({ control, name: "method" });

  return (
    <>
      <select {...register("method")}>
        <option value="card">Card</option>
        <option value="upi">UPI</option>
      </select>

      {method === "card" && <input {...register("cardNumber")} />}
      {method === "upi" && <input {...register("upiId")} />}
    </>
  );
}
```

`useWatch` in a small child component isolates the re-render to just this section ([[21.3 - React Hook Form]]).

Conditional validation needs a discriminated union rather than optional fields, so the compiler and the validator both understand which shape applies ([[25.6 - Discriminated Unions and Narrowing]]):

```ts
const schema = z.discriminatedUnion("method", [
  z.object({ method: z.literal("card"), cardNumber: z.string().length(16) }),
  z.object({ method: z.literal("upi"), upiId: z.string().email() }),
]);
```

Note that unmounting a field leaves its value in the form state by default. `shouldUnregister: true` clears it — usually what you want for conditional fields, so a hidden card number is not submitted.

## Multi-step wizards

Two viable architectures.

**One form, steps as views** — a single `useForm` instance, steps render subsets of fields:

```jsx
function Wizard() {
  const [step, setStep] = useState(0);
  const methods = useForm({ resolver: zodResolver(fullSchema), mode: "onTouched" });

  const next = async () => {
    const valid = await methods.trigger(stepFields[step]);   // validate only this step
    if (valid) setStep(s => s + 1);
  };

  return (
    <FormProvider {...methods}>
      {step === 0 && <StepOne />}
      {step === 1 && <StepTwo />}
      <button type="button" onClick={next}>Next</button>
    </FormProvider>
  );
}
```

`trigger(fieldNames)` validates a subset. All values persist across steps automatically because they live in one form instance.

**Separate forms, shared external state** — each step has its own `useForm`, and completed steps write to a store or the URL. Better when steps are far apart in the routing tree, or when the wizard spans page navigations.

The first is simpler and covers most cases. Choose the second when steps are separate routes.

Putting the step in the URL is worth doing either way — it gives back-button support and shareable progress ([[20.1 - Where State Should Live]]):

```jsx
const [params, setParams] = useSearchParams();
const step = Number(params.get("step") ?? 0);
```

## Autosave

```jsx
function AutosaveForm({ documentId }) {
  const { control, getValues } = useFormContext();
  const values = useWatch({ control });
  const debounced = useDebounce(values, 1000);
  const isFirst = useRef(true);

  useEffect(() => {
    if (isFirst.current) { isFirst.current = false; return; }
    saveDraft(documentId, debounced);
  }, [debounced, documentId]);
}
```

Four things a real implementation needs:

**Skip the first run**, or it saves immediately on mount with unchanged values.

**Debounce**, typically 500–2000ms ([[29.1 - Debounce and Throttle]]).

**Sequence the requests.** Two saves in flight can land out of order, so the older one wins. Either queue them ([[04.7 - Async Concurrency Patterns]]) or include a version and let the server reject stale writes.

**Show status.** "Saving…", "Saved", "Failed — retry" is the minimum. Silent autosave that fails silently is worse than no autosave.

For editors, also save on `visibilitychange` and use `navigator.sendBeacon` for the unload path, since a normal fetch may be cancelled:

```js
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") {
    navigator.sendBeacon("/api/draft", JSON.stringify(getValues()));
  }
});
```

## Unsaved changes warning

```jsx
const { formState: { isDirty } } = useFormContext();

useEffect(() => {
  if (!isDirty) return;

  const handler = (e) => { e.preventDefault(); };
  window.addEventListener("beforeunload", handler);
  return () => window.removeEventListener("beforeunload", handler);
}, [isDirty]);
```

`beforeunload` covers tab close and external navigation. In-app navigation needs the router's own blocker:

```jsx
const blocker = useBlocker(({ currentLocation, nextLocation }) =>
  isDirty && currentLocation.pathname !== nextLocation.pathname
);
```

Reset the form after a successful submit, or `isDirty` stays true and the prompt fires on a form the user already saved ([[21.3 - React Hook Form]]).

## File uploads

```jsx
<input type="file" {...register("attachment")} accept="image/*" />

const onSubmit = async (data) => {
  const formData = new FormData();
  formData.append("file", data.attachment[0]);
  formData.append("title", data.title);
  await fetch("/api/upload", { method: "POST", body: formData });
};
```

File inputs are always uncontrolled — their value cannot be set programmatically for security reasons. Validate size and type client-side for feedback, and again on the server for enforcement.

For progress, `fetch` cannot report upload progress; `XMLHttpRequest` still can, which is why upload libraries persist.

## Performance at scale

For forms with a hundred-plus fields — insurance applications, configuration screens, tax forms:

- Uncontrolled by default, `Controller` only where necessary
- `useWatch` scoped to the smallest possible component
- Virtualize very long repeating sections ([[19.5 - Virtualization and Windowing]])
- Split into steps, which also improves completion rates

Measure with the Profiler under CPU throttling; form lag is one of the clearest cases where development machines mislead ([[19.8 - Profiling with React DevTools]]).

## How senior engineers actually use this

**They use `field.id` as the key** in every field array, without exception.

**They put wizard step and filter state in the URL**, so back and refresh behave.

**They make autosave visible and sequenced**, never silent and never parallel.

**They reset after submit** so the unsaved-changes prompt stays accurate.

**They model conditional fields as discriminated unions** rather than a pile of optional fields.

## Common pitfalls

- `key={index}` in a field array, corrupting row state after removal.
- Numeric inputs submitting strings without `valueAsNumber`.
- Conditional fields retaining values after unmount without `shouldUnregister`.
- Autosave firing on mount, or racing itself.
- `isDirty` left true after a successful save.
- `useWatch` at the form root, re-rendering everything.
- Trying to control a file input.

## Interview angle

Complex forms come up as "how would you build a multi-step form" or "how would you handle a dynamic list of fields". For the wizard: one form instance with per-step validation via `trigger`, step in the URL, and a discriminated-union schema for conditional branches. For arrays: stable generated ids as keys, path-based field names, and array-level versus row-level error placement. Mentioning autosave sequencing and the unsaved-changes blocker shows breadth beyond the happy path.
