# Recursion Control and Static Guards

## How recursion happens

A trigger updates a record, which fires a trigger, which updates a record.

The paths, from [[07.13 - Order of Execution]]:

**Direct.** An after trigger on Claim updates a Claim. Its own trigger fires again.

**Via a parent.** A Claim trigger updates its Asset. The Asset trigger updates its Claims. Back to the Claim trigger.

**Via a roll-up.** A child insert recalculates the parent's roll-up at step 15, which sends the parent through its own save pipeline — its triggers, its flows, its validation rules.

**Via a flow.** A record-triggered flow updates a record whose trigger updates the record the flow was triggered by.

**Via a workflow field update.** Legacy, and still present in older orgs — a field update at step 11 re-runs steps 5 through 8.

The platform caps save recursion and throws `maximum trigger depth exceeded` at the limit. Relying on that is relying on a crash.

## The symptom before the crash

Recursion often does not crash. It runs twice, or four times, and the symptoms are subtler:

- A payment record created twice
- A counter incremented by two instead of one
- A notification sent three times
- `Apex CPU time limit exceeded` on an operation that looks trivial
- A batch job that works at 50 records and fails at 200

Those are worse than a crash, because nobody attributes them to recursion.

## The wrong guard

```java
public with sharing class TriggerControl {
    public static Boolean hasRun = false;
}
```

```java
if (TriggerControl.hasRun) {
    return;
}
TriggerControl.hasRun = true;
```

This works for the simple case and fails in a way that is hard to see.

A static persists for the **whole transaction**, not for one trigger invocation. So:

**A data load of 400 records** arrives as two chunks of 200. The first sets the flag. The second is skipped entirely — 200 records silently unprocessed, with no error.

**A trigger updating other records of the same object** — reparenting, cascading a status — skips them.

**A batch job** processing several chunks in one transaction skips all but the first.

The failure mode is records that did not get processed, discovered weeks later by someone reconciling data.

## The right guard

Track **which record Ids** have been processed, not whether the handler ran.

```java
public with sharing class TriggerControl {

    private static Map<String, Set<Id>> processedByContext = new Map<String, Set<Id>>();

    public static List<SObject> filterUnprocessed(String context, List<SObject> records) {
        Set<Id> processed = processedByContext.get(context);
        if (processed == null) {
            return records;
        }

        List<SObject> unprocessed = new List<SObject>();
        for (SObject record : records) {
            if (!processed.contains(record.Id)) {
                unprocessed.add(record);
            }
        }
        return unprocessed;
    }

    public static void markProcessed(String context, List<SObject> records) {
        if (!processedByContext.containsKey(context)) {
            processedByContext.put(context, new Set<Id>());
        }
        Set<Id> processed = processedByContext.get(context);
        for (SObject record : records) {
            processed.add(record.Id);
        }
    }

    @TestVisible
    private static void reset() {
        processedByContext.clear();
    }
}
```

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isUpdate) {
            List<Warranty_Claim__c> unprocessed =
                (List<Warranty_Claim__c>) TriggerControl.filterUnprocessed(
                    'WarrantyClaim_AfterUpdate', Trigger.new
                );

            if (unprocessed.isEmpty()) {
                return;
            }

            TriggerControl.markProcessed('WarrantyClaim_AfterUpdate', unprocessed);
            ClaimService.handleStatusChanges(unprocessed, Trigger.oldMap);
        }
    }
}
```

Now a second chunk of 200 different records processes normally, and the same record re-entering the trigger is skipped.

The **context key** matters. `WarrantyClaim_AfterUpdate` and `WarrantyClaim_BeforeUpdate` are separate concerns and need separate tracking, or guarding one suppresses the other.

## The better answer: do not recurse

A guard is a defence. Not causing the recursion is better, and often available.

**Change detection.** Most recursion produces a second pass where nothing actually changed. Comparing against `oldMap` means the second pass does nothing anyway.

```java
for (Warranty_Claim__c claim : newClaims) {
    Warranty_Claim__c prior = oldClaims.get(claim.Id);
    // on the recursive pass the status is unchanged, so nothing fires
    if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') {
        newlyApproved.add(claim);
    }
}
```

This is the single most effective technique, and in many handlers it removes the need for a guard entirely. See [[11.2 - Trigger Context Variables]].

**Use before triggers for same-record updates.** A before trigger assigns in memory with no DML, so there is nothing to recurse. Most self-update recursion is an after trigger that should have been a before trigger. See [[11.3 - Before vs After - Choosing the Right Event]].

**Only update records that changed.**

```java
List<Asset> toUpdate = new List<Asset>();
for (Asset asset : assets.values()) {
    // skipping unchanged records stops the parent trigger firing for no reason
    if (asset.Open_Claim_Count__c != originalCounts.get(asset.Id)) {
        toUpdate.add(asset);
    }
}
if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

A roll-up that updates every parent whether or not the value changed fires the parent's trigger unnecessarily on every child save. Comparing first is cheap and removes a whole cascade.

## Statics reset at async boundaries

A guard set in the synchronous transaction is **gone** in a Queueable, a future method, a batch chunk, or a platform event subscriber. Each of those is a new transaction.

That is usually what you want — the async work should process the records. It is worth knowing so that a guard is not mistaken for protection it does not provide.

If deduplication must survive an async boundary, it has to be persisted — a field on the record, a custom object row, or state passed to the Queueable constructor. See [[09.8 - Static Members and Class Level State]].

## Guards and partial rollback

A subtle interaction worth knowing.

**Static variables are not rolled back.** If a savepoint rollback discards DML, the guard still shows those records as processed. A retry after the rollback silently skips them.

```java
Savepoint sp = Database.setSavepoint();
try {
    update claims;              // the guard marks them processed
} catch (Exception e) {
    Database.rollback(sp);      // the data is discarded, the guard is not
    TriggerControl.reset();     // required before any retry
    update claims;
}
```

Resetting the guard after a rollback is necessary and easy to forget. See [[10.5 - Savepoints, Rollback and Transaction Control]].

## Testing recursion control

```java
@IsTest
static void secondPassIsSkippedButOtherRecordsAreNot() {
    TriggerControl.reset();

    List<Warranty_Claim__c> firstBatch = TestDataFactory.createClaims(200);
    List<Warranty_Claim__c> secondBatch = TestDataFactory.buildClaims(200);

    Test.startTest();
    for (Warranty_Claim__c claim : firstBatch) {
        claim.Status__c = 'Approved';
    }
    update firstBatch;

    // a second, distinct set in the same transaction must still be processed
    insert secondBatch;
    Test.stopTest();

    Integer payments = [SELECT COUNT() FROM Claim_Payment__c];
    Assert.areEqual(200, payments, 'One payment per approved claim, no duplicates');

    Integer secondBatchProcessed = [
        SELECT COUNT() FROM Warranty_Claim__c
        WHERE Id IN :secondBatch AND Approval_Tier__c != null
    ];
    Assert.areEqual(200, secondBatchProcessed,
        'A boolean guard would have skipped this entire batch');
}
```

That second assertion is the point of the test. A boolean guard passes the first assertion and fails the second, which is exactly the bug that goes unnoticed in production.

## Diagnosing recursion

**Debug logs** show nested `CODE_UNIT_STARTED` blocks. Each nesting level is a re-entry:

```
CODE_UNIT_STARTED [EXTERNAL] Trigger:WarrantyClaimTrigger after update
  DML_BEGIN [2] Op:Update Type:Asset Rows:47
    CODE_UNIT_STARTED [EXTERNAL] Trigger:AssetTrigger after update
      DML_BEGIN [3] Op:Update Type:Warranty_Claim__c Rows:312
        CODE_UNIT_STARTED [EXTERNAL] Trigger:WarrantyClaimTrigger after update  ← recursion
```

Four levels of nesting on one user action is the picture of an org where automation has accumulated without an owner.

**The limit block** at the end of the log shows the cumulative cost:

```
Number of SOQL queries: 94 out of 100
Number of DML statements: 118 out of 150
Maximum CPU time: 9204 out of 10000
```

Numbers close to the limit on a small operation mean something is running more times than intended.

See [[20.1 - Debug Logs and Log Levels]].

## Practical guidance

**Never use a boolean guard.** Track record Ids.

**Use a per-context key**, so guarding one event does not suppress another.

**Prefer change detection to a guard.** Most recursion becomes harmless when the second pass finds nothing changed.

**Use before triggers for same-record updates**, so there is nothing to recurse.

**Only update records whose values actually changed.**

**Reset the guard after a rollback.**

**Provide a `@TestVisible reset()`** and call it at the start of tests that depend on guard state.

**Test that a second distinct batch is still processed.** That is the assertion a boolean guard fails.
