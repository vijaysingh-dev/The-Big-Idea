# How GraphQL Execution Works

#backend #api-design #graphql

> **In one line:** Execution starts every sibling field before awaiting any of them, and that one scheduling detail is what makes DataLoader possible and what makes GraphQL performance predictable.

---

## The Idea

```
query string
   ▼  PARSE       → AST. Syntax only. Cacheable by query hash
   ▼  VALIDATE    → does this make sense against the schema? Cacheable
   ▼  EXECUTE     → call resolvers, build the result tree
   ▼  SERIALISE   → JSON, with errors and paths
```

💡 **Parse and validate are pure functions of the query string and schema.** Both are cacheable, both cost real CPU on large queries, and caching them is the foundation of persisted queries ([[05.7 - GraphQL Caching]]).

---

## Phase 1: Parse

```graphql
query DocDetail($id: ID!) {
  document(id: $id) { title, source { name } }
}
```

```
OperationDefinition(query, name="DocDetail", variables=[id: ID!])
  Field(name="document", args=[id: Variable(id)])
    Field(name="title")
    Field(name="source")
      Field(name="name")
```

Pure syntax, no schema knowledge. A query for a nonexistent field parses fine.

⚠️ **Parsing is a denial-of-service surface.** A deeply nested query string is cheap to send and expensive to parse. **Limit query string length before parsing, not after.**

---

## Phase 2: Validate

Independent visitors, each checking one rule.

| Rule | Catches |
|---|---|
| `FieldsOnCorrectType` | A field that does not exist |
| `ValuesOfCorrectType` | `id: 42` where `ID!` expects a string |
| **`NoFragmentCycles`** | Mutually recursive fragments |
| `OverlappingFieldsCanBeMerged` | Two aliases of one field with conflicting arguments |
| `ScalarLeafs` | Subfields on a scalar, or none on an object |

💡 **This is where you add your own rules.** Depth limits, complexity analysis, field-level authorisation and introspection blocking are all validation rules, and they run **before any resolver executes** — so a rejected query costs almost nothing ([[05.8 - GraphQL Security and Limits]]).

```python
class MaxDepthRule(ValidationRule):
    def enter_field(self, node, *args):
        self.depth += 1
        if self.depth > MAX_DEPTH:
            self.report_error(GraphQLError(f"Query exceeds max depth {MAX_DEPTH}"))
```

⚠️ **`NoFragmentCycles` is a security rule, not a nicety.** Without it, mutually recursive fragments expand infinitely during execution and hang the process.

## Phase 3: Execute — The Part That Matters

```python
async def execute_selection_set(parent, selection_set, path):
    fields = collect_fields(selection_set)        # merge aliases, resolve fragments

    results = {}
    for response_key, field_nodes in fields.items():
        results[response_key] = execute_field(parent, field_nodes, path + [response_key])

    # ALL sibling resolvers have been STARTED before any is awaited
    return {k: await v for k, v in results.items()}
```

**Read that twice.** Every field at one level is *started* before any is *awaited*.

```
Level 2:  start title()  start source()  start annotations()
          await all three                     ← all started first
```

💡 **This is the single fact that makes DataLoader work.** Twenty `author()` resolvers all call `loader.load(id)` before the event loop yields, so the loader accumulates twenty IDs and issues one batched query. **Without this scheduling property, batching would be impossible.**

**Breadth-first within a level, depth-first between levels.** Understanding that sentence is most of what you need to reason about GraphQL performance.

### Field collection

```graphql
{ document(id: "1") { title, ...DocFields, title } }
fragment DocFields on Document { status, source { name } }
```

`collect_fields` flattens fragments, merges duplicate response keys, and applies `@skip`/`@include` — all before any resolver runs.

⚠️ **Duplicate fields are merged; *aliased* fields are not.**

```graphql
{ a: expensiveField, b: expensiveField, c: expensiveField }   # three resolutions
```

**This is a real attack vector**, and it is why complexity analysis must count aliases rather than distinct field names.

### complete_value — where types are enforced

```python
async def complete_value(field_type, result, path, info):
    if is_non_null(field_type):
        completed = await complete_value(field_type.of_type, result, path, info)
        if completed is None:
            raise NonNullError(path)              # propagates upward
        return completed

    if result is None:
        return None

    if is_list(field_type):
        return await gather(*[complete_value(field_type.of_type, item, path + [i], info)
                              for i, item in enumerate(result)])

    if is_leaf(field_type):
        return field_type.serialize(result)

    return await execute_selection_set(result, sub_selection, path)
```

**The list case is where N+1 is born** — each item independently resolves its own children.

### Null propagation

```graphql
type Query { documents: [Document!]! }
type Document { source: Source! }
```

If one document's `source` resolver returns null:

```
1. Source! is non-null, got null → error
2. Document.source is required   → Document becomes null
3. The list is [Document!]        → the LIST becomes null
4. Query.documents is [Document!]! → data becomes null
```

**One bad row nulls the entire response.**

```json
{"data": null, "errors": [{"message": "...", "path": ["documents", 7, "source"]}]}
```

⚠️ **This is why over-using `!` is dangerous.** The `path` in the error tells you where it started, which is the only reason this is debuggable.

💡 **`!` for fields from your own database that structurally always exist; nullable for anything crossing a service boundary.**

## Phase 4: Serialise

```json
{
  "data": { ... },
  "errors": [{
    "message": "Source unavailable",
    "path": ["documents", 3, "source"],
    "extensions": {"code": "DEPENDENCY_UNAVAILABLE", "requestId": "req_..."}
  }]
}
```

`data` and `errors` coexist — **partial success is normal in GraphQL**, unlike REST.

`extensions` on errors is where your error codes live ([[05.3 - Error Design]]). The spec says nothing about the shape, so pick one and document it.

## In Production

### Caching parse and validate

```python
_cache: dict[str, tuple[DocumentNode, list[GraphQLError]]] = {}

def get_document(query: str, schema) -> DocumentNode:
    key = hashlib.sha256(query.encode()).hexdigest()
    if key not in _cache:
        ast = parse(query)
        _cache[key] = (ast, validate(schema, ast))
    ...
```

Real applications send a small number of distinct queries repeatedly, so hit rates are very high. **Parsing and validating a large query can be 5–15ms**, and at high request rates that is real avoidable CPU.

⚠️ **Bound the cache.** An unbounded dict keyed by arbitrary client input is a memory exhaustion vector.

### Where time goes

```
Parse            2ms   (0ms cached)
Validate         3ms   (0ms cached)
Execute        180ms   ← almost always here
Serialise        4ms
```

💡 **Execution time is resolver time, and resolver time is usually database time.** GraphQL is rarely slow because of GraphQL; it is slow because the query shape produced 200 database round trips.

### Per-field tracing

```python
class TracingExtension(Extension):
    async def resolve(self, next_, root, info, **kwargs):
        start = time.perf_counter()
        try:
            return await next_(root, info, **kwargs)
        finally:
            field_duration.labels(parent=str(info.parent_type),
                                  field=info.field_name).observe(time.perf_counter() - start)
```

⚠️ **Wrapping every resolver has real overhead** — a query touching 5,000 fields pays 5,000 timer calls. **Sample it:** trace 1% fully, and always trace requests over a latency threshold.

### Parallelism is not free

All sibling resolvers start concurrently. Twenty each acquiring a database connection means twenty concurrent connections from one request.

⚠️ **One GraphQL query can exhaust your connection pool by itself** ([[01.10 - Connection Pools and Limits]]). This surprises people because the request count is one.

**Bound resolver concurrency per request, and prefer batching over parallelism** — one query for twenty authors beats twenty parallel queries.

### Mutations serialise, and it matters

```graphql
mutation { a: deleteDocument(id:"1"){ok}, ..., z: deleteDocument(id:"26"){ok} }
```

Twenty-six sequential mutations, each in its own transaction. **Any timeout kills the request midway, leaving partial work.**

💡 **Limit top-level mutation fields per request** — three to five is reasonable. Clients needing bulk operations should get a purpose-built bulk mutation.

💡 The thing to hold in mind reading `execute_fields`: **if it awaited each field before starting the next, GraphQL would be unusably slow and DataLoader would be impossible.** The performance of every GraphQL server rests on those few lines.

## Exercise

**Drill 5.5 — Instrument execution**

Builds on the engine from drill 5.4.

```
drills/05-graphql-execution/
├── engine/{execute.py, trace.py, cache.py}
├── experiments/{scheduling.py, nullability.py, alias_attack.py, mutation_serial.py, pool_exhaust.py, RESULTS.md}
├── cache/{bench.py, unbounded.py}
├── visualise/flamegraph.py
└── README.md
```

**Part 1 — Prove the scheduling.** Log the exact moment each resolver *starts* and *completes*.

Run a query with twenty sibling fields, each sleeping 100ms.

**Assert all twenty start timestamps are within 1ms of each other, and the total is ~100ms, not 2 seconds.**

Then deliberately break it — await each before starting the next — and show the total becoming 2 seconds. **This contrast is the whole note.**

**Part 2 — Nullability propagation, exhaustively.** Five nesting levels with varied nullability.

| Failing field | Expected |
|---|---|
| `String` in a nullable object | Field null, everything else intact |
| `String!` in `Document` (nullable) | `Document` becomes null |
| `String!` in `Document!` in `[Document!]!` | **`data` becomes null entirely** |

**Confirm the `path` points at the originating field, not where propagation stopped.**

**Part 3 — The alias attack.** One expensive field, 1,000 aliases.

**Measure execution time and database calls — it should be 1,000× a single call.**

Then write a validation rule counting aliased duplicates and confirm it runs before any resolver.

**Part 4 — Mutation serialisation.** Fifty top-level mutations, each 100ms. Total should be ~5 seconds.

**Kill the connection at 2.5 seconds and inspect the database — half committed.** Write down what that means for client retry logic, then implement a mutation count limit.

**Part 5 — Pool exhaustion from one query.** 50 items, each resolving a field that acquires a connection. Pool size 10.

Watch it deadlock. Then fix it two ways — a per-request semaphore, and batching via a loader — and compare.

**Part 6 — Parse/validate caching.** Benchmark queries of 100, 1,000 and 10,000 tokens. Add an LRU and measure the hit-path cost and the saving at a realistic request rate.

Then the attack: 100,000 unique queries with an unbounded cache. **Watch memory grow.** Bound it and confirm the ceiling.

**Part 7 — A field timing flamegraph.** Render the timing tree with width proportional to time and call counts annotated.

Run your five Conduit queries through it. **The N+1 pattern should be visually obvious** — a wide bar with a count of 20 next to it.

**Done when:**
- Twenty sibling resolvers demonstrably start within 1ms of each other
- Your nullability table covers five levels with correct error paths
- The alias attack works, and your rule stops it before execution
- Fifty serial mutations leave partial state when interrupted, and you have a limit
- One query no longer exhausts a pool of 10
- Your flamegraph makes N+1 visible at a glance
