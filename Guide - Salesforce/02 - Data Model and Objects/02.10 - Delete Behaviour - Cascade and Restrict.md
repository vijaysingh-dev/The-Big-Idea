# Delete Behaviour - Cascade and Restrict

## Why this deserves its own note

Deleting is where data models reveal what they actually mean. A relationship you chose casually determines whether removing one account removes ten years of service history.

It is also where the platform behaves in ways that surprise people: deletes are soft, cascades ignore some automation, and some deletes are silently blocked.

## Deletes are soft, for fifteen days

Deleted records go to the **Recycle Bin** rather than disappearing. `IsDeleted` is set to true, and the record is recoverable for 15 days, after which it is purged permanently.

This has real implications:

**Deleted records are still in the database and still count toward storage** until purged. Deleting a million records does not free storage immediately.

**They can be queried** with `ALL ROWS`:

```sql
SELECT Id, Name, IsDeleted, LastModifiedDate
FROM Machine__c
WHERE IsDeleted = true
ORDER BY LastModifiedDate DESC
ALL ROWS
```

**They can be restored** with `undelete`, which also restores most of their relationships.

**The bin has a capacity limit**, calculated from your storage allocation. When it overflows, the oldest records are purged early — so the 15 days is a maximum, not a guarantee. Relying on the Recycle Bin as a backup is a mistake for exactly this reason.

## The three behaviours

**Cascade delete.** Deleting the parent deletes the children. This is master-detail's behaviour, and it is not optional.

**Clear the reference.** Deleting the parent leaves the child, with the lookup field emptied. This is the default for lookups.

**Restrict delete.** Deleting the parent is blocked while children exist. This is an option on lookup fields, chosen when the field is created or edited.

For a lookup, the choice between clearing and restricting is a checkbox labelled "Don't allow deletion of the lookup record that's part of a lookup relationship". It is worth setting deliberately rather than accepting the default, because the default silently orphans data.

## Cascade delete, and what it skips

This is the behaviour that causes the most damage, because it is both powerful and quiet.

Deleting one record can remove an entire subtree. Master-detail supports three levels, so deleting a top-level record can cascade down two more.

The critical detail: **cascade deletes bypass some automation.** Deleting a master record deletes its details without necessarily firing the detail object's delete triggers in the way you would expect, and validation rules on the children do not stop it. Logic you wrote to prevent deletion of a child in certain states will not save you.

This means a validation rule on `Warranty_Claim_Line__c` saying "cannot delete an approved line" is defeated entirely by deleting the parent claim.

If deletion must be genuinely prevented, prevent it on the parent, in a `before delete` trigger on the parent object:

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void preventDeletionOfProcessedClaims(List<Warranty_Claim__c> claims) {
        Set<Id> claimIds = new Set<Id>();
        for (Warranty_Claim__c c : claims) {
            claimIds.add(c.Id);
        }

        Set<Id> claimsWithPayments = new Set<Id>();
        for (Claim_Payment__c payment : [
            SELECT Warranty_Claim__c FROM Claim_Payment__c WHERE Warranty_Claim__c IN :claimIds
        ]) {
            claimsWithPayments.add(payment.Warranty_Claim__c);
        }

        for (Warranty_Claim__c c : claims) {
            if (claimsWithPayments.contains(c.Id)) {
                c.addError('This claim has payments recorded and cannot be deleted. Cancel it instead.');
            }
        }
    }
}
```

`addError()` on a record in a `before delete` trigger blocks that record's deletion and rolls back the transaction, with the message shown to the user.

## What else blocks a delete

Even without restrict-delete configured, the platform refuses some deletions:

- A record referenced by another record through a lookup marked as restricted
- An Account with cases, or with certain related records, depending on configuration
- A record locked by an in-progress approval process
- A parent whose child deletion would itself fail
- Records in use by an active flow or process definition

The error messages are frequently unhelpful, naming an internal relationship rather than the actual blocker. When a delete fails mysteriously, the practical approach is to check related lists first, then approval status, then restricted lookups.

## Delete in Apex

```java
List<Machine__c> obsolete = [
    SELECT Id FROM Machine__c
    WHERE Status__c = 'Decommissioned' AND Decommission_Date__c < LAST_N_YEARS:7
];

// partial success mode, so one failure does not abandon the whole batch
List<Database.DeleteResult> results = Database.delete(obsolete, false);

for (Integer i = 0; i < results.size(); i++) {
    if (!results[i].isSuccess()) {
        for (Database.Error err : results[i].getErrors()) {
            System.debug('Failed to delete ' + obsolete[i].Id + ': ' + err.getMessage());
        }
    }
}
```

`Database.delete(records, false)` allows partial success — records that can be deleted are, and failures are reported individually. `delete records` as a statement is all-or-nothing: one failure rolls back everything. For bulk cleanup jobs, partial success is nearly always what you want. See [[10.2 - Database Class Methods and Partial Success]].

Undelete restores from the bin:

```java
List<Machine__c> restorable = [SELECT Id FROM Machine__c WHERE IsDeleted = true ALL ROWS];
undelete restorable;
```

Undelete also restores cascade-deleted children, which is genuinely useful after an accidental parent delete — provided you act within 15 days.

`emptyRecycleBin()` purges permanently and cannot be reversed. It is occasionally necessary during large data migrations to free storage, and it should be treated with corresponding care.

## Limits on deletion at scale

Deleting large volumes is slower than inserting them, because the platform must handle sharing rows, indexes, and the recycle bin.

For very large deletions:

- **Batch Apex** with a `Database.emptyRecycleBin()` call in the finish method
- **Bulk API hard delete**, which bypasses the recycle bin entirely and is substantially faster; it requires a specific user permission
- Delete in **descending order of dependency**, children before parents, to avoid cascade overhead

Deleting fifty million rows is a project, not a task. See [[23.5 - Bulk Data Loading at Scale]].

## Design guidance

**Set restrict-delete on lookups where orphaning would be a data quality problem.** The default of silently clearing the reference produces records that look fine but reference nothing, and nobody notices for months.

**Do not rely on child validation rules to prevent deletion.** Cascade defeats them. Guard on the parent.

**Prefer soft deletion for anything with history.** A status of Cancelled or Archived preserves audit trail, reporting continuity, and the ability to answer questions later. Actual deletion should be reserved for genuine mistakes and for data that must legally be removed.

**Know that deletion is a compliance requirement too.** Right-to-erasure requests under privacy regulation require real deletion, including from field history and from backups. That is a design problem, not a delete statement. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

**Test cascade behaviour before production.** In a sandbox, delete one parent and count what disappeared. The result is often larger than anyone predicted.
