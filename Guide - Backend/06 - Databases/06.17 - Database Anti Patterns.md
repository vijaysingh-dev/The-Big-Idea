# Database Anti-Patterns

#backend #databases #postgres #review

> **In one line:** Fifteen mistakes that appear in almost every codebase, each of which works fine at small scale and fails at large scale — which is exactly why they survive code review.

---

## The Idea

💡 **The common thread: these all work at 10,000 rows and fail at 10 million.** They pass tests, they pass review, and they surface as "the application got slow and nobody knows why" eighteen months later.

**Use this as a code review checklist and as a self-audit for Conduit.**

---

## 1. `SELECT *`

| Cost | |
|---|---|
| **TOAST decompression** | A large `content` column is fetched even if unused ([[06.2 - Postgres Architecture]]) |
| Prevents index-only scans | The index cannot cover every column |
| Breaks on schema change | A new column silently appears in your response |

⚠️ **On a table with a large text or JSONB column, `SELECT *` can be 40× slower.** The most common and most easily fixed performance mistake.

---

## 2. N+1 Queries

```python
docs = await conn.fetch("SELECT * FROM documents WHERE org_id = $1", org_id)
for doc in docs:
    doc.author = await conn.fetchrow("SELECT * FROM users WHERE id = $1", doc.author_id)
```

101 queries ([[05.6 - The N+1 Problem and DataLoader]]). **Not a GraphQL-specific problem** — any ORM produces it the moment you touch a relationship inside a loop.

💡 **Add a query-count assertion to your tests.** It is the only defence that survives a new developer adding a field to a serialiser.

---

## 3. Offset Pagination

`O(offset)`, and it **silently skips and duplicates rows** when data changes underneath it ([[05.2 - Versioning Pagination and Filtering]]). Use keyset pagination with a unique tiebreaker.

---

## 4. Network Calls Inside Transactions

```python
async with conn.transaction():
    doc = await repo.get(doc_id)
    result = await external_api.call(doc)      # 2 seconds
    await repo.update(doc_id, result)
```

⚠️ **You are holding a connection, row locks, and the vacuum horizon for the duration of a call you do not control** ([[06.7 - MVCC Vacuum and Bloat]]).

**Rule: no network calls inside a transaction, ever.**

---

## 5. UUIDv4 Primary Keys

Random values scatter inserts across the entire index, causing page splits, rapid bloat, and a working set that will not stay in memory ([[06.1 - Storage Engines]]).

💡 **There is no remaining reason to choose v4 over v7 for a primary key.** Same size, same non-guessability, same client-side generation, dramatically better index behaviour.

---

## 6. No Timeouts

⚠️ **A missing timeout is not "no limit" — it is "whatever TCP does", which can be fifteen minutes.**

```python
pool = await asyncpg.create_pool(dsn, command_timeout=10, timeout=5)
```

```sql
ALTER ROLE app_user SET statement_timeout = '30s';
ALTER ROLE app_user SET lock_timeout = '5s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '60s';
```

**Set all three, per role** ([[06.8 - Locking and Deadlocks]]).

---

## 7. Enum as Integer

```sql
status integer NOT NULL     -- 1 = pending, 2 = indexed, 3 = failed
```

The mapping lives in application code, or a comment, or someone's memory. **Every ad-hoc query needs a lookup table you carry in your head, and a second service reading the database gets it wrong.**

💡 **Storage is not the constraint here — comprehensibility is.** `WHERE status = 'failed'` is self-documenting in a way `WHERE status = 3` never will be.

---

## 8. Timestamps Without a Time Zone

⚠️ **`timestamp` stores a reading with no anchor.** Two servers in different zones write different instants for the same moment, and you cannot tell afterwards. **Use `timestamptz`. Same 8 bytes. Always.**

---

## 9. Floats for Money

```sql
price_cents bigint NOT NULL CHECK (price_cents >= 0),
currency char(3) NOT NULL
```

Or `numeric(12,2)`. **Integer minor units are preferable** because they cannot be accidentally divided into a fraction of a cent.

---

## 10. Application-Enforced Constraints

```python
if await repo.email_exists(email):
    raise DuplicateEmail()
await repo.create_user(email)      # race: two requests both pass the check
```

⚠️ **Check-then-act is a race condition at every isolation level below Serializable** ([[06.6 - Transactions and Isolation Levels]]).

💡 **A database constraint is enforced against every code path, every service, and every person with a `psql` prompt.** Application checks are enforced against the code paths you remembered.

---

## 11. Unbounded Result Sets

Fine with 100 documents. At 5 million, it is an out-of-memory kill.

⚠️ **Every query returning multiple rows needs a limit, even internal ones. Especially internal ones** — nobody paginates a background job until it kills a worker.

---

## 12. Indexing Everything, or Nothing

```sql
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

💡 **Run that on any production database and you will find unused indexes.** Each costs write throughput, disk, buffer pool space, and vacuum time, for nothing ([[06.3 - Indexes Deep Dive]]).

**Check `idx_scan` across a full business cycle** — an index used only by a monthly report shows zero in a week.

---

## 13. `ORDER BY` Without a Tiebreaker

⚠️ **Rows with equal timestamps have no defined order**, and Postgres may return them differently on different executions. **Users see rows appear twice across pages, with no cause visible in the code.**

**Every `ORDER BY` needs a unique tiebreaker, not just paginated ones.**

---

## 14. Migrations That Lock

```sql
ALTER TABLE documents ALTER COLUMN size TYPE bigint;      -- rewrites
CREATE INDEX ix_documents_org ON documents (org_id);      -- no CONCURRENTLY
UPDATE documents SET author_id = owner_id;                -- one enormous transaction
```

All three take the table offline, and all three have safe alternatives ([[06.11 - Zero Downtime Migrations]]).

⚠️ **And every migration needs `lock_timeout`**, because even a "safe" `ADD COLUMN` queues the entire application behind it if a long query is running.

---

## 15. Building a Queue Naively

```sql
SELECT * FROM jobs WHERE status = 'pending' LIMIT 10;
UPDATE jobs SET status = 'running' WHERE id = ANY($1);
```

⚠️ **Two workers claim the same jobs.** The gap between select and update is a race.

```sql
UPDATE jobs SET status = 'running', worker_id = $1
WHERE id IN (
    SELECT id FROM jobs WHERE status = 'pending'
    ORDER BY created_at LIMIT 10 FOR UPDATE SKIP LOCKED
) RETURNING *;
```

💡 **`FOR UPDATE SKIP LOCKED` is the correct primitive and it should be reflexive** ([[06.6 - Transactions and Isolation Levels]]). **And partition the table by time**, so completed jobs are dropped rather than deleted ([[06.13 - Partitioning and Sharding]]).

## The Ones People Argue About

### Soft deletes

⚠️ **Every query must now remember `WHERE deleted_at IS NULL`.**

**Defensible when** you genuinely need undelete or audit history. **Use partial indexes and a view** to make the common path safe by default. **Consider an archive table instead** — moving rows out is cleaner than filtering them forever.

### Storing files in the database

⚠️ **Bloats your database, your backups and your replication stream.** A 500GB database that is 480GB of PDFs makes every operation slower.

**Almost always: object storage plus a URL.** The exception is small files where transactional consistency with the row genuinely matters.

### ORMs

💡 **The reasonable position: use an ORM for CRUD, write SQL for anything with performance requirements, and always be able to see the generated query.**

**Log every query in development.** If you cannot see what your ORM emits, you cannot review it.

### Triggers

⚠️ **A trigger is code that executes without appearing in any call stack.** Debugging "why did this row change" becomes archaeology.

**Defensible for:** `updated_at`, audit logging, maintaining denormalised counters. **Not for:** business rules, notifications, or anything a developer would reasonably expect to find in application code.

## The Review Checklist

```
□  No SELECT * outside ad-hoc queries
□  No queries inside loops
□  Keyset pagination, with a unique tiebreaker
□  No network calls inside transactions
□  Every ORDER BY has a tiebreaker
□  Every multi-row query has a limit
□  Timeouts set: statement, lock, idle-in-transaction
□  Constraints in the database, not just the application
□  timestamptz, not timestamp
□  Money as integer minor units or numeric
□  Enums as text with a CHECK
□  UUIDv7 or bigint keys, not UUIDv4
□  Every index is used; no redundant left-prefixes
□  Migrations: CONCURRENTLY, lock_timeout, batched backfills
□  Queues use FOR UPDATE SKIP LOCKED
□  Tenant filter present, and enforced by RLS
□  No unbounded queues or result sets
```

💡 **Turn as much of this as possible into automation** rather than a human checklist:

| Check | Automation |
|---|---|
| N+1 | Query count assertions in tests |
| Dangerous migrations | A CI linter ([[06.11 - Zero Downtime Migrations]]) |
| Missing timeouts | A startup assertion on pool configuration |
| Unused indexes | A weekly report from `pg_stat_user_indexes` |
| Missing tenant filter | RLS ([[06.16 - Multi Tenant Data Models]]) |
| Slow queries | `pg_stat_statements` alerting |

**A checklist a human runs is a checklist a human forgets.**

## In Production

### The audit that finds most of them

```sql
-- Unused indexes
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE idx_scan < 50
ORDER BY pg_relation_size(indexrelid) DESC LIMIT 20;

-- Heavy sequential scans
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / nullif(seq_scan, 0) AS avg_rows
FROM pg_stat_user_tables WHERE seq_scan > 100 ORDER BY seq_tup_read DESC LIMIT 20;

-- Expensive queries, by TOTAL time
SELECT calls, total_exec_time, mean_exec_time, rows, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;

-- Bloat
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- Long transactions
SELECT pid, now() - xact_start AS age, state, left(query, 80)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;

-- Transaction ID age  ← the one that can take you offline
SELECT max(age(datfrozenxid)) FROM pg_database;
```

💡 **Order `pg_stat_statements` by `total_exec_time`, not `mean_exec_time`.** A 2ms query called ten million times costs far more than a 5-second query called twice, **and the expensive queries in aggregate are almost never the ones people suspect.**

**Run this audit quarterly. It takes fifteen minutes and it consistently finds something.**

### The three that cause the most incidents

1. **No timeouts** — turns a slow dependency into a total outage
2. **Migrations without `lock_timeout`** — turns a routine deploy into an outage
3. **Long transactions** — bloat, lock queues, and wraparound risk, from one bug

⚠️ **All three are configuration, not code. They can be fixed this afternoon and they prevent the worst class of incident.**

### Conduit's self-audit

Run the checklist against Conduit phase 1. **Every "no" either gets fixed or gets a written justification.** This becomes part of [[Assets.4 - Production Readiness Checklist]].

## Exercise

**Drill 6.17 — Audit, then automate**

```
drills/06-antipatterns/
├── examples/{bad.py, good.py}
├── measure/{select_star.py, n_plus_one.py, offset.py, uuid_keys.py, no_timeout.py, RESULTS.md}
├── automation/{query_counter.py, migration_lint.py, config_assert.py, query_analyzer.py, ci.yaml}
├── audit/{queries.sql, report.py, conduit_audit.md}
└── README.md
```

**Part 1 — Write all fifteen, plausibly.** A small application containing every anti-pattern, written the way a competent engineer under time pressure would.

**Do not caricature them. The point is that they look reasonable.**

**Part 2 — Measure the five easiest to quantify.** On a 10-million-row dataset:

| Anti-pattern | Measure |
|---|---|
| `SELECT *` versus named columns | Latency, buffers, TOAST reads |
| N+1 versus batched | Query count, total time |
| Offset versus keyset at depth | Latency, and rows skipped under concurrent inserts |
| UUIDv4 versus v7 keys | Insert throughput over time, index size |
| No timeout versus timeout | Behaviour when a dependency hangs |

**Build the table with real numbers.** These are what you quote in a code review — **"it is 43× slower and here is the measurement" is much stronger than "it is slower".**

**Part 3 — Automate N+1 detection.** Query-counting instrumentation plus assertions in every database test.

**Introduce an N+1 by adding a field to a serialiser. Confirm CI fails with a message naming the offending code.**

**Part 4 — The migration linter.** A CI check rejecting non-concurrent index creation, type changes, `SET NOT NULL` on a large table, unbatched `UPDATE`, and DDL without `lock_timeout` — with an override mechanism.

Test against ten migrations, five safe and five dangerous.

**Part 5 — Startup assertions.** Code that fails to start if pool timeouts, `statement_timeout`, or `idle_in_transaction_session_timeout` are unset.

💡 **Assertions at startup are better than documentation**, because a misconfigured deploy fails immediately rather than at 3am under load.

**Part 6 — A development query analyzer.** Following GitLab's approach: raise in development and test when a query has no `LIMIT` and no `WHERE` on an indexed column, or uses `SELECT *` on a table with a TOASTed column.

**Run it against your own `bad.py` and confirm it catches them.**

**Part 7 — Audit Conduit.** Run the six audit queries and the seventeen-item checklist against Conduit phase 1.

**For each finding, either fix it or write a one-line justification.** Then set up the audit to run monthly and report into your observability stack.

**Done when:**
- All fifteen anti-patterns exist in plausible code with a correct counterpart
- Your measurement table has real numbers for five of them
- CI fails on a deliberately introduced N+1, naming the code
- Your migration linter catches five dangerous operations
- The application refuses to start without timeouts configured
- Your query analyzer catches unbounded and `SELECT *` queries in development
- `conduit_audit.md` has a finding or justification for all seventeen items
