# Render Phase vs Commit Phase

Every React update has two phases with fundamentally different properties.

| | Render phase | Commit phase |
| --- | --- | --- |
| What happens | call components, diff, build workInProgress tree | apply DOM changes, run effects |
| Interruptible | yes | no |
| Can be discarded | yes | no |
| May run several times | yes | no |
| Touches the DOM | no | yes |
| Side effects allowed | no | yes |

## Render phase

React calls component functions, produces elements, reconciles them against the previous tree, and marks fibers with flags describing what the commit will need to do ([[18.3 - Fiber Architecture]]).

Nothing is applied. The DOM is untouched throughout.

Because this phase is interruptible, React may:

- **pause** it to let the browser paint or handle input
- **restart** it if a higher-priority update arrives
- **discard** it entirely if the result is no longer needed

This is why the render phase must be pure ([[16.5 - Rendering and Purity]]). A side effect during render — a network request, a mutation of external state, a log to an analytics service — happens even when the render is thrown away, and cannot be undone.

What runs here:

- Component function bodies
- `useState` and `useReducer` initializers and updater functions
- `useMemo` factories
- `useCallback` (returning, not calling)
- The `key` and `type` comparisons of reconciliation

## Commit phase

Once React has a complete workInProgress tree, it commits — synchronously and uninterruptibly. Three sub-steps:

**1. Before mutation.** `getSnapshotBeforeUpdate` for class components. React reads the DOM before changing it.

**2. Mutation.** DOM nodes are inserted, updated and removed. Refs from the previous tree are detached. The `root.current` pointer is swapped to the new tree.

**3. Layout.** Refs are attached with new values, `useLayoutEffect` cleanup and setup run, `componentDidMount`/`componentDidUpdate` fire.

Then the browser paints. After paint, `useEffect` cleanup and setup run asynchronously.

```
render (interruptible)
   ↓
commit: before mutation
   ↓
commit: mutation (DOM changes, refs detached)
   ↓
commit: layout (refs attached, useLayoutEffect)
   ↓
paint
   ↓
useEffect (passive, async)
```

The commit is atomic because the tree swap is a single pointer assignment — the user never sees a half-updated DOM.

## Why the split matters

**Effects placement.** `useLayoutEffect` runs in the commit's layout step, before paint, so measurements and adjustments are invisible to the user. `useEffect` runs after paint, so it never blocks a frame ([[17.5 - useLayoutEffect vs useEffect]]).

**Refs are null during render.** They are attached in the layout step, so reading `ref.current` in a component body gives `null` on the first render and a stale value afterwards ([[17.8 - useRef]]).

**Components may render more than once per commit.** With transitions, Suspense or Strict Mode, several render passes can precede a single commit. Code that assumes one execution per visible update is wrong.

**State updates during render are handled differently.** A `setState` called during the render of the *same* component causes React to immediately re-render before committing — this is the supported "adjust state during render" pattern ([[17.2 - useState in Depth]]). A `setState` targeting a *different* component during render is an error.

## Interruption in practice

```jsx
const [isPending, startTransition] = useTransition();

startTransition(() => {
  setSearchResults(computeExpensiveResults(query));
});
```

React begins rendering the results at transition priority. If the user types again, a higher-priority update arrives:

```
render results (query="rea") → interrupted
  → render input with "reac" (urgent, commits)
  → restart results render for "reac"
```

The first render's work is discarded. Any side effect it performed would have already happened, with no corresponding commit — which is the concrete failure mode purity prevents ([[18.5 - Concurrent Rendering and the Scheduler]]).

## Tearing

A related hazard: if a component reads a **mutable external value** during render, and the render is interrupted, two components in the same tree can observe different values.

```jsx
// Component A renders, reads store.count === 5
//   → interrupted; store.count becomes 6
// Component B renders, reads store.count === 6
//   → both commit together, UI is internally inconsistent
```

That inconsistency is called tearing, and it is why `useSyncExternalStore` exists — it forces a consistent snapshot across the whole render ([[17.12 - Lesser Known Hooks]]).

## Profiling by phase

React DevTools' Profiler separates the two:

- **Render duration** — time in component functions and reconciliation
- **Commit duration** — time applying DOM changes and running layout effects

The distinction drives the fix. High render time means expensive component logic or too many components rendering — address with memoization or by narrowing what re-renders. High commit time means large DOM changes — address with virtualization or by reducing how much of the tree actually changes ([[19.8 - Profiling with React DevTools]]).

Many "slow React" complaints are actually high commit time from rendering thousands of DOM nodes, where memoization does nothing.

## What is safe where

| Operation | Render | Commit / effects |
| --- | --- | --- |
| Read props, state, context | yes | yes |
| Compute derived values | yes | yes |
| Read `ref.current` | no | yes |
| Write `ref.current` | no (except lazy init) | yes |
| Read the DOM | no | yes (layout effect) |
| Network requests | no | yes |
| Subscribe to events | no | yes |
| Mutate external state | no | yes |
| `setState` | same component only | yes |

## How senior engineers actually use this

**They place effects by phase**, using layout effects only when the visual result depends on a measurement.

**They read the Profiler by phase**, since render-heavy and commit-heavy problems have opposite solutions.

**They keep render pure** with the interruption model in mind, rather than as an abstract rule.

**They use `useSyncExternalStore` for external state**, knowing tearing is a genuine possibility under concurrent rendering.

## Common pitfalls

- Side effects in the render phase.
- Reading refs or the DOM during render.
- Assuming one render per commit.
- Optimizing render time when the profiler shows commit time is the cost.
- Subscribing to external state with `useState` + `useEffect`, risking tearing.
- Expecting `useEffect` to run before paint.

## Interview angle

"Explain the render and commit phases" is a strong senior question. Give the two-phase split with the key property of each — render is interruptible, discardable and may repeat; commit is synchronous and atomic — then derive the practical rules from it: purity is required because renders can be discarded, refs are null during render because they attach in commit, and layout effects run before paint while passive effects run after. Mentioning tearing and `useSyncExternalStore` demonstrates you understand the consequences rather than the vocabulary.
