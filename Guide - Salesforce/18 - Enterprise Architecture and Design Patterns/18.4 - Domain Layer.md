# Domain Layer

## The idea

An sObject is a data structure with no behaviour. A **domain class** wraps a collection of one object's records and holds the logic that belongs to that object regardless of who is calling.

```java
public with sharing class Claims {

    private final List<Warranty_Claim__c> records;
    private final Map<Id, Warranty_Claim__c> priorRecords;

    public Claims(List<Warranty_Claim__c> records) {
        this(records, null);
    }

    public Claims(List<Warranty_Claim__c> records, Map<Id, Warranty_Claim__c> priorRecords) {
        this.records = records;
        this.priorRecords = priorRecords;
    }

    public void applyDefaults() {
        for (Warranty_Claim__c claim : records) {
            if (String.isBlank(claim.Status__c)) {
                claim.Status__c = 'Submitted';
            }
            if (claim.Claim_Date__c == null) {
                claim.Claim_Date__c = Date.today();
            }
        }
    }

    public void validate() {
        for (Warranty_Claim__c claim : records) {
            if (claim.Claim_Amount__c != null && claim.Claim_Amount__c <= 0) {
                claim.addError('Claim_Amount__c', Label.Claim_Error_Amount_Must_Be_Positive);
            }
        }
    }

    public List<Warranty_Claim__c> newlyApproved() {
        List<Warranty_Claim__c> result = new List<Warranty_Claim__c>();

        for (Warranty_Claim__c claim : records) {
            Warranty_Claim__c prior = priorRecords?.get(claim.Id);
            if (claim.Status__c == 'Approved'
                && (prior == null || prior.Status__c != 'Approved')) {
                result.add(claim);
            }
        }
        return result;
    }
}
```

```java
// From the handler
new Claims(Trigger.new, Trigger.oldMap).validate();

// From a service
List<Warranty_Claim__c> approved = new Claims(claims, priorClaims).newlyApproved();
```

**Instance-based, not static** — the collection is the state, which is what distinguishes domain from service.

## Domain versus service

The distinction people get stuck on, and a workable rule:

**Domain is behaviour of one object, true regardless of the process.**
"A claim amount must be positive." "A claim's region comes from its asset's account." "A claim is newly approved when its status changed to Approved."

**Service is a process, usually spanning objects.**
"Approving a claim means validating coverage, creating a payment, recalculating the asset total, and notifying the ERP."

The test: **could this logic be wrong in one process and right in another?** If yes, it is service. If it is always true of the object, it is domain.

```java
// Domain — always true of a claim
public Boolean isHighValue(Warranty_Claim__c claim) {
    return claim.Claim_Amount__c > 500000;
}

// Service — a decision about a process
public static void routeForApproval(Set<Id> claimIds) { }
```

## Where domain earns its place

**Deduplicating per-object logic.** The same validation needed by a trigger, a REST endpoint, and a batch job, written once and callable from all three.

**Making trigger handlers thin.** A handler that constructs a domain object and calls three methods is readable in a way that an inline loop is not.

**Encapsulating derived-field logic** so that anything creating a claim gets the same defaults, whether it came from the UI, an integration, or a data load.

## Where it does not

**A small org.** Two objects with straightforward validation do not need a domain layer; validation rules and a service method suffice.

**Objects with no behaviour.** A junction object with no rules gets no domain class.

**As a place to put everything.** A domain class that queries other objects and orchestrates a process has become a service with the wrong name.

## Domain with an interface

For polymorphism across objects — a common need in generic tooling:

```java
public interface IValidatable {
    void validate();
    void applyDefaults();
}

public with sharing class Claims implements IValidatable { }
public with sharing class ServiceContracts implements IValidatable { }
```

```java
public with sharing class DomainDispatcher {

    public static void validate(List<SObject> records) {
        IValidatable domain = DomainFactory.newInstance(records);
        // the caller does not know or care which object this is
        domain?.validate();
    }
}
```

The factory resolves the concrete class:

```java
public with sharing class DomainFactory {

    private static final Map<SObjectType, Type> DOMAIN_BY_TYPE = new Map<SObjectType, Type>{
        Warranty_Claim__c.SObjectType => Claims.class,
        Service_Contract__c.SObjectType => ServiceContracts.class
    };

    public static IValidatable newInstance(List<SObject> records) {
        if (records == null || records.isEmpty()) {
            return null;
        }

        Type domainType = DOMAIN_BY_TYPE.get(records.getSObjectType());
        if (domainType == null) {
            return null;
        }

        IValidatable domain = (IValidatable) domainType.newInstance();
        ((IDomainConstructable) domain).setRecords(records);
        return domain;
    }
}
```

This is the shape fflib formalizes with its `Constructor` inner class. See [[18.7 - fflib Apex Commons in Practice]] and [[09.12 - Generics, Type Casting and Reflection]].

## Guarding the collection

A domain class receiving a list holds a reference the caller can still mutate. For before-trigger contexts that is exactly right — modifying `Trigger.new` is how field assignment works.

For other contexts, deciding whether the domain owns or borrows the collection matters:

```java
public Claims(List<Warranty_Claim__c> records) {
    // a defensive copy where the domain should not affect the caller's list
    this.records = new List<Warranty_Claim__c>(records);
}
```

The copy is shallow — the records themselves are shared — so it prevents adding and removing, not field mutation. In practice, sharing the list is usually correct and worth being deliberate about.

## Selection methods

A useful domain idiom: methods returning filtered subsets, keeping the filtering logic with the object.

```java
public List<Warranty_Claim__c> highValue() {
    List<Warranty_Claim__c> result = new List<Warranty_Claim__c>();
    for (Warranty_Claim__c claim : records) {
        if (claim.Claim_Amount__c > 500000) {
            result.add(claim);
        }
    }
    return result;
}

public Set<Id> assetIds() {
    Set<Id> ids = new Set<Id>();
    for (Warranty_Claim__c claim : records) {
        if (claim.Asset__c != null) {
            ids.add(claim.Asset__c);
        }
    }
    return ids;
}

public Set<Id> affectedAssetIds() {
    Set<Id> ids = assetIds();

    // a reparented claim leaves the old asset's aggregate stale unless it is included
    if (priorRecords != null) {
        for (Warranty_Claim__c claim : records) {
            Warranty_Claim__c prior = priorRecords.get(claim.Id);
            if (prior?.Asset__c != null && prior.Asset__c != claim.Asset__c) {
                ids.add(prior.Asset__c);
            }
        }
    }
    return ids;
}
```

That `affectedAssetIds` method is a good example of why domain is worth it: the old-parent subtlety is easy to forget, and having it in one place means every caller gets it right. See [[11.7 - Bulkified Trigger Patterns]].

## Testing

Domain classes are the easiest thing in the architecture to test, because they are pure functions over constructed records.

```java
@IsTest
static void reparentedClaimsIncludeBothAssets() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);
    Id oldAssetId = TestIdFactory.generate(Asset.SObjectType);
    Id newAssetId = TestIdFactory.generate(Asset.SObjectType);

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Asset__c = newAssetId)
    };
    Map<Id, Warranty_Claim__c> prior = new Map<Id, Warranty_Claim__c>{
        claimId => new Warranty_Claim__c(Id = claimId, Asset__c = oldAssetId)
    };

    Test.startTest();
    Set<Id> affected = new Claims(claims, prior).affectedAssetIds();
    Test.stopTest();

    Assert.areEqual(2, affected.size(), 'Both the old and new asset need recalculating');
    Assert.isTrue(affected.contains(oldAssetId), 'The old asset must be included');
}
```

No DML, no queries, and it tests the exact subtlety that causes wrong roll-up totals in production.

## Should you adopt it?

The honest calibration.

**Skip the domain layer when** the org is small, per-object logic is thin, or the team is one or two developers. Service classes with well-named private methods cover the same ground with less indirection.

**Adopt it when** the same object logic is needed from several entry points, when validation and derived fields are duplicated across services, or when the team is large enough that a consistent shape per object is worth more than brevity.

**The middle path most teams settle on:** service classes for processes, plus a small set of domain classes for the two or three objects with genuinely rich behaviour. Not every object needs one, and forcing a domain class per object produces a lot of near-empty files.

## Practical guidance

**Domain is per-object behaviour; service is a process.**

**Instance-based, constructed with the collection.**

**Keep queries out** — a domain class querying other objects has become a service.

**Put subtle collection logic in domain methods**, so every caller gets it right.

**Handle the null prior map**, since the same class serves insert and update.

**Test with constructed records** — no DML needed.

**Do not create a domain class per object reflexively.** Two or three rich ones beat twenty empty ones.
