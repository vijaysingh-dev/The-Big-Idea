# Finding Service Boundaries

#backend #microservices #design

> **In one line:** A good boundary is one where the data does not want to cross — and the reliable way to find it is to look at where transactions end, not where the org chart says.

---

## The Idea

```
❌ By technical layer      api-service, business-service, data-service
❌ By entity               user-service, document-service, tag-service
✅ By business capability  ingestion, search, billing, identity
```

⚠️ **Layer-based splitting is the worst possible boundary.** Every feature touches all three services, so nothing can be deployed independently — you have all the cost of microservices and none of the benefit.

⚠️ **Entity-based splitting is nearly as bad**, because entities are related. A `tag-service` separate from a `document-service` means every document listing needs a network call, and a transaction spanning them is impossible.

💡 **The right unit is a business capability: a coherent set of operations that a team owns end to end, with its own data, that changes for its own reasons.**

---

## Bounded Contexts

The idea from domain-driven design that actually helps.

**A bounded context is a boundary within which a term has one consistent meaning.**

```
In `identity`:  a User is credentials, email, MFA settings
In `billing`:   a User is a payer with a plan and payment methods
In `documents`: a User is an author with a display name
```

💡 **These are three different models of the same person, and that is correct.** Forcing them into one shared `User` object means every service depends on every field, and a change to MFA settings redeploys billing.

⚠️ **A shared model across contexts is the most common cause of coupling that microservices were supposed to eliminate.** A "common" or "shared-models" library is the anti-pattern — the moment two services import it, they cannot deploy independently.

```python
# In documents-service — its own model, only what it needs
@dataclass
class Author:
    id: str
    display_name: str
```

**Each context defines what it needs, referenced by a shared ID.** That ID is the only thing they agree on.

## Finding Them

### 1. Follow the transactions

💡 **The strongest signal: where does an ACID transaction need to span?**

```python
async with conn.transaction():
    doc = await documents.create(data)
    await chunks.create_many(doc.id, chunks)
    await index_entries.upsert(chunks)
```

**Those three must be atomic.** Splitting between them means a saga, compensation and reconciliation ([[08.11 - Durable Workflows and Sagas]]).

```python
await documents.create(data)
# ... later, eventually ...
await notifications.send(doc.collaborators)
```

**These do not need to be atomic.** A notification that arrives a second later, or fails and retries, is fine.

⚠️ **Draw the boundary where atomicity is not required.** If you find yourself writing a saga for something that was one transaction, the boundary is wrong.

### 2. Follow the change rate

```
documents/   changed in 340 of the last 500 commits
billing/     changed in 12
search/      changed in 180
```

💡 **Things that change together belong together.** If two modules always appear in the same commit, the boundary between them is imaginary.

```bash
# Find co-change clusters
git log --format="%H" --name-only | analyse_cochange.py
```

⚠️ **Conversely, a module that almost never changes is a candidate for extraction** — a stable API and a stable implementation means the deploy coordination cost is near zero.

### 3. Follow the data gravity

```sql
-- Count foreign keys crossing a proposed boundary
SELECT count(*) FROM information_schema.table_constraints tc
JOIN ... WHERE source_schema = 'documents' AND target_schema = 'billing';
```

⚠️ **Fifteen foreign keys crossing a boundary is the boundary telling you it is wrong.** Every one becomes either a network call, duplicated data, or a dropped constraint ([[10.4 - Data Ownership]]).

💡 **A good boundary has one or two references crossing it, and they are IDs.**

### 4. Follow the query patterns

```sql
-- Which tables appear together in queries?
SELECT query FROM pg_stat_statements ORDER BY calls DESC LIMIT 100;
```

**Tables consistently joined together belong in the same service.** A boundary that turns a join into a network call plus application-side assembly is expensive ([[10.1 - Monolith Modular Monolith Microservices]]).

### 5. Follow the teams

💡 **Conway's law: your architecture will mirror your communication structure whether you want it to or not.**

⚠️ **The inverse — designing the architecture to match the team structure you want — is the "inverse Conway manoeuvre"**, and it works. But it only makes sense if you have multiple teams. **With one team, the boundary should follow the domain, not an imaginary org chart.**

## Testing a Boundary

Before committing, ask these five questions.

| Question | Bad answer |
|---|---|
| **What transactions span it?** | "Several" |
| **How many foreign keys cross it?** | "More than two" |
| **How often do both sides change in one commit?** | "Usually" |
| **Can each side be understood alone?** | "You need to know both" |
| **What happens when one side is down?** | "The other cannot function" |

⚠️ **If the last answer is "nothing works", the boundary is not a boundary — it is a network call inside what should be one process.**

💡 **The strongest test: can you describe what each service does in one sentence, without mentioning the other?**

```
✅  "Ingestion pulls documents from external sources and prepares them for search."
✅  "Billing tracks usage and manages subscriptions."

❌  "The document service stores documents that the chunk service chunks."
```

## Common Wrong Boundaries

### The chatty pair

```
Order service → Inventory service: 12 calls per checkout
```

⚠️ **High call volume between two services means they are one service that has been split.** The network is doing what a function call should.

💡 **The fix is to merge them, not to add caching or batching.** Caching a chatty boundary hides the problem and adds staleness.

### The distributed monolith

```
Every deploy requires deploying all five services in a specific order.
```

⚠️ **This is the worst of both worlds** — microservice operational cost with monolithic coupling. It happens when services share a library, share a database, or have synchronous chains with no versioning.

**The test: can you deploy service A without deploying anything else?** If not, they are one service.

### The nanoservice

```
tag-service, slug-service, thumbnail-service
```

⚠️ **A service that does one small thing has a fixed operational cost — pipeline, monitoring, on-call, deployment — that dwarfs its value.**

💡 **A service should be big enough to justify its own on-call runbook.** If nobody would ever page for it alone, it should not be a service.

### The shared database

```
documents-service ─┐
billing-service   ─┼─→ one database, shared tables
search-service    ─┘
```

⚠️ **This is not microservices.** Any schema change requires coordinating every service, which is exactly what you were trying to avoid ([[10.4 - Data Ownership]]).

## The Practical Sequence

💡 **Do not design boundaries up front. Discover them.**

```
1. Build a monolith with modules
2. Enforce module boundaries in code and in the database
3. Let it run. Watch where the boundaries strain
4. Move boundaries freely — it is a refactor
5. When a boundary has been stable for months AND a team needs
   independent deployment, extract it
```

⚠️ **Boundaries drawn before you understand the domain are drawn at the moment of least information.** ([[10.1 - Monolith Modular Monolith Microservices]])

💡 **The modular monolith is not a stepping stone you must eventually leave.** It is a valid destination, and the module boundaries are the valuable artefact whether or not you ever split.

## In Production

### Watching a boundary strain

```python
# Instrument cross-module calls even in a monolith
module_call_total.labels(source="billing", target="documents", op=op).inc()
module_call_duration.labels(...).observe(elapsed)
```

💡 **Instrumenting module calls in a monolith tells you what the network traffic would be if you split.** A boundary with 10,000 calls per second is a boundary you should not put a network across.

**Track cross-boundary transaction spans too:**

```python
if len(modules_touched_in_transaction) > 1:
    cross_module_transaction_total.labels(modules=tuple(sorted(...))).inc()
```

⚠️ **Every cross-module transaction is a future saga.** Counting them before you split tells you exactly how much work the split is.

### The extraction readiness checklist

Before extracting a module:

```
□  It has a public API and nothing bypasses it
□  Its tables are in their own schema, with no cross-schema queries
□  No foreign keys cross the boundary — or you know how to replace them
□  No transaction spans it — or you have designed the saga
□  Its change rate is independent of other modules
□  A team owns it and needs independent deployment
□  You have the observability to debug across the boundary
□  You have measured what the network traffic would be
```

⚠️ **The last item is the one that most often stops an extraction**, and it should. Discovering after the split that the boundary carries 5,000 calls per second is an expensive way to learn.

### Boundaries that change

💡 **A boundary is not permanent.** Domains evolve, and a boundary that was right two years ago may be wrong now.

```
Symptoms of a boundary going wrong:
  - Sagas being added between two services
  - Data increasingly duplicated across a boundary
  - Deploy coordination creeping back
  - The same feature repeatedly touching both sides
```

⚠️ **Moving a boundary between services is expensive** — data migration, API changes, deployment coordination. **Merging two services is usually cheaper than moving the line between them**, and it is an underused option.

**Merging services is not an admission of failure.** It is what you do when you learn the boundary was wrong.

### Conduit's boundaries

Applying the five tests to each candidate:

| Candidate boundary | Transactions | FKs | Co-change | Verdict |
|---|---|---|---|---|
| documents ↔ chunks | **Same transaction** | Many | Always | **Same service** |
| documents ↔ sources | Same transaction | Several | Often | **Same service** |
| documents ↔ search index | None — eventual | Zero | Sometimes | **Splittable** |
| documents ↔ ingestion | None — async | One (document_id) | Sometimes | **Splittable** |
| documents ↔ billing | None — eventual usage | One (org_id) | Rarely | **Splittable** |
| documents ↔ notifications | None | Zero | Rarely | **Splittable** |

💡 **Four splittable boundaries and two hard ones.** The hard ones are where atomicity is required, and that is exactly the signal.

⚠️ **Splittable does not mean should split.** Of the four, only `ingestion` has a genuine reason — different scaling and GPU placement in phase 9 ([[10.1 - Monolith Modular Monolith Microservices]]).

**And even that is achievable as a separate deployment of the same image.** The ADR should say so.

```
└── ADR.md
```

**Part 1 — Analyse the evidence.** Against a real codebase — Conduit, or an open-source project — compute:

- **Co-change clusters** from git history. Which modules appear together in commits?
- **Foreign keys** crossing each candidate boundary
- **Query patterns** — which tables are joined together, weighted by call frequency
- **Transaction spans** — which modules appear in one transaction

**Four analyses, one boundary map.** Where do all four agree?

**Part 2 — Instrument the monolith.** Add cross-module call counting and cross-module transaction counting.

Run a realistic workload for an hour. **Produce the traffic matrix** — calls per second between every pair of modules.

💡 **This matrix is what the network would carry if you split.** Identify any pair above 1,000 calls per second and mark it as un-splittable.

**Part 3 — Score five candidates.** Propose five boundaries, including at least one you believe is wrong.

Apply the five questions to each. **Score them, and rank.**

Then check your ranking against the evidence from part 1. **Where they disagree, work out which is right.**

**Part 4 — Build a wrong boundary and feel it.** Split by layer: `api-service`, `logic-service`, `data-service`.

Implement three features. **Measure: services deployed per feature, latency per operation, and lines of code added versus the monolith.**

**Every feature should require all three deploys.** That is the demonstration.

**Part 5 — The chatty pair.** Split `documents` and `chunks`, which share transactions.

**Measure: calls per document creation, latency, and the saga required to keep them consistent.**

Then measure what happens when the chunk service is slow. Then merge them back and measure the improvement.

**Report the total cost of that boundary**, in latency, code and failure modes.

**Part 6 — The nanoservice.** Extract something small — slug generation, or thumbnail sizing.

**Count the operational surface it required**: pipeline, manifests, dashboard, alerts, runbook, client, contract tests.

**Then compare that to the lines of business logic it contains.** The ratio is the argument.

**Part 7 — Extraction readiness.** Take the one boundary that scored best and run the eight-item checklist.

For each failure, **estimate the work to fix it.** Then produce the traffic simulation: what would this boundary carry, and is that acceptable?

**Part 8 — The ADR.** Conduit's boundaries, with evidence.

For each candidate: the four analyses, the five questions, and the verdict. **For every "do not split", name the signal that would change the answer.**

**Done when:**
- Your four analyses produce a boundary map, and you know where they disagree
- The traffic matrix identifies at least one un-splittable pair
- You ranked five candidates and reconciled the ranking with the evidence
- Layer-based splitting demonstrably requires every deploy for every feature
- You quantified the total cost of one chatty boundary
- The nanoservice's operational-surface-to-logic ratio is measured
- The ADR justifies every boundary with evidence and names the reconsideration signals
