# Consistency Models: Strong vs Eventual, ACID vs BASE

> **Revision tags:** #fundamentals #consistency #databases  
> **Related:** [[01.5 - CAP and PACELC]] | [[03.6 - Databases SQL and NoSQL]]

---

## Consistency Is Not One Thing

"Consistency" means something different in each of these contexts:
- **The C in ACID** → A transaction leaves the database in a valid state
- **The C in CAP** → Linearizability (every read sees the latest write)
- **Consistency model** → The rules about what values a read can return

These overlap but are not the same. Know which one you're talking about.

---

## Consistency Models (Strongest to Weakest)

### 1. Linearizability (Strong Consistency)

Every operation appears to take effect *instantaneously* at some point between its start and end.  
After a write completes, all subsequent reads — anywhere in the cluster — see that write.

**Real feel:** Behaves like a single-threaded system even across distributed nodes.  
**Cost:** High latency (requires coordination), low availability during partitions.  
**Used in:** etcd, ZooKeeper, CockroachDB, Google Spanner.

### 2. Sequential Consistency

All operations happen in *some* total order, and each node sees operations in that order.  
Unlike linearizability, the order doesn't have to match real-time.

**Real feel:** All replicas agree on the order of operations, but may lag behind real-time.  
**Used in:** Some multi-core CPU memory models.

### 3. Causal Consistency

Operations that are causally related (A caused B) are seen in that order by all nodes.  
Unrelated operations can be seen in any order.

**Real feel:** If you post a comment in reply to a post, everyone sees the post before the comment. But two unrelated posts may appear in different orders for different users.  
**Used in:** MongoDB (causally consistent sessions), some CRDT systems.

### 4. Read-Your-Writes Consistency

After you write something, your own subsequent reads will see it.  
Other clients may still see stale data.

**Real feel:** You post a photo; you see it immediately. Your friend may not see it for a second.  
**Used in:** Most user-facing applications as a minimum guarantee.

### 5. Eventual Consistency

If no new writes occur, all replicas will *eventually* converge to the same value.  
No guarantee on when. No guarantee on order during divergence.

**Real feel:** DNS propagation, social feeds, product ratings.  
**Used in:** DynamoDB (default), Cassandra, CouchDB.

---

## The Practical Hierarchy

```
Linearizability        ← hardest to achieve, highest latency
Sequential Consistency
Causal Consistency
Read-Your-Writes       ← minimum for good UX
Eventual Consistency   ← easiest to achieve, highest availability
```

Most systems don't need the top. Most systems need at least read-your-writes.

## ACID

ACID is a set of properties that database *transactions* guarantee.

### A — Atomicity

A transaction is all-or-nothing. If any part fails, the whole transaction is rolled back.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- Both updates succeed, or neither does
```

Without atomicity: You debit account 1 and crash before crediting account 2.

### C — Consistency

A transaction takes the database from one valid state to another valid state. All constraints, rules, and cascades are honored.

> Note: This is application-level correctness, not the CAP C. The database enforces the rules you defined (foreign keys, NOT NULL, CHECK constraints).

### I — Isolation

Concurrent transactions are isolated from each other — they behave as if running serially.

**Isolation levels (weakest to strongest):**

| Level | What You Allow | Problem Prevented |
|---|---|---|
| Read Uncommitted | Read uncommitted writes | — |
| Read Committed | Only read committed data | Dirty reads |
| Repeatable Read | Same rows read twice, same result | Non-repeatable reads |
| Serializable | Full serial equivalence | Phantom reads |

Higher isolation = more locking/blocking = less throughput.

### D — Durability

Once a transaction is committed, it persists — even if the system crashes immediately after.

Achieved via: Write-Ahead Logging (WAL), fsync to disk, synchronous replication.

### Databases with ACID

PostgreSQL, MySQL (InnoDB), Oracle, SQL Server, CockroachDB, Google Spanner.

---

## BASE

BASE is the alternative philosophy for systems that prioritize availability and scale over strict ACID guarantees.

### BA — Basically Available

The system guarantees availability (responds to requests) even during partial failures. Some responses may be stale or incomplete.

### S — Soft State

State may change over time even without input, due to eventual consistency propagation. You can't assume state is frozen.

### E — Eventually Consistent

Given no new writes, all replicas will converge. *When* is not guaranteed.

### Databases with BASE

Cassandra, DynamoDB, CouchDB, Riak, MongoDB (default).

---

## ACID vs BASE — When to Use Each

| Situation | Use ACID | Use BASE |
|---|---|---|
| Financial transactions | ✅ | ❌ |
| Inventory counts | ✅ | ❌ |
| User profile updates | ❌ | ✅ |
| Social feed posts | ❌ | ✅ |
| Shopping cart | Depends | Often ok |
| Analytics ingestion | ❌ | ✅ |
| Order state machine | ✅ | ❌ |

## Conflict Resolution in Eventual Consistency

When two nodes accept writes for the same key during a partition, there's a conflict on merge. Common resolution strategies:

1. **Last-Write-Wins (LWW):** Timestamp-based. Simple but loses data silently.
2. **Multi-Version Concurrency Control (MVCC):** Keep all versions; let the application resolve.
3. **CRDTs (Conflict-free Replicated Data Types):** Mathematical structures that merge without conflicts (e.g., a grow-only set, a counter).
4. **Operational Transformation:** Used in Google Docs for real-time collaboration.
