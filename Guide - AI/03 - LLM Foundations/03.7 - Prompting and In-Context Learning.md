# Prompting and In-Context Learning

## Definition

**Prompting** is the process of constructing the input to an LLM to reliably elicit the desired output. It's a software engineering discipline, not a magic trick.

**In-context learning (ICL)** is the model's ability to adapt its behavior based on examples provided in the prompt — no weight updates, purely from context.

---

## Why Prompting is an Engineering Problem

LLMs are instruction-following engines. The quality of your prompt determines:

- Whether the model understands the task
- The format of the output
- The model's behavior on edge cases
- Latency and cost (prompt length × token price)
- Safety and reliability

A 10-minute prompt improvement can outperform a week of fine-tuning. Always exhaust prompting before reaching for fine-tuning.

---

## Prompt Structure

A well-structured prompt has distinct components:

```
┌─────────────────────────────────────────────────────────┐
│ SYSTEM PROMPT                                           │
│ - Role and persona                                      │
│ - Task definition                                       │
│ - Constraints and rules                                 │
│ - Output format specification                           │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│ USER TURN                                               │
│ - Context (retrieved documents for RAG)                 │
│ - Few-shot examples (if needed)                         │
│ - The actual query                                      │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│ ASSISTANT PREFILL (optional)                            │
│ - Pre-fill the beginning of the assistant response      │
│   to constrain output format or activate CoT           │
└─────────────────────────────────────────────────────────┘
```

## Prompting Techniques

### Zero-Shot

Directly ask the task with no examples. Works well for well-defined tasks that the model has seen in training:

```
"Classify this review as positive or negative: 'The food was amazing!'"
```

### Few-Shot

Provide 2–5 examples of input/output before the actual query. Significantly improves performance on:

- Novel output formats
- Nuanced classification
- Tasks with implicit rules

```
Examples:
Review: "The food was amazing!" → Positive
Review: "Waited 45 minutes, terrible service." → Negative
Review: "Good but pricey." → Mixed

Now classify: "Absolutely loved it, will return!"
```

**Key insight**: The examples don't teach the model new skills — they _activate_ and constrain already-learned patterns. This is why ICL works.

### Chain-of-Thought (CoT)

Add "Think step by step" or show reasoning in examples. Forces the model to externalize intermediate reasoning:

```
Q: If a train travels 120 miles in 2 hours, how far in 5 hours?
A: Let me think step by step.
   - Speed = 120 miles / 2 hours = 60 mph
   - Distance in 5 hours = 60 × 5 = 300 miles
   Answer: 300 miles
```

CoT dramatically improves performance on math, logic, and multi-step reasoning. Covered in depth in [[03.10 - Chain of Thought and Reasoning]].

## System Prompt Engineering

The system prompt is the highest-leverage component. Patterns that work:

### Role + Task Framing

```
You are an expert financial analyst at a top investment bank.
Your task is to analyze earnings call transcripts and extract key insights.
```

Role framing activates relevant knowledge and writing style.

### Explicit Format Specification

Don't describe the format — show it:

```
Respond in this exact JSON format:
{
  "sentiment": "positive" | "negative" | "neutral",
  "confidence": 0.0-1.0,
  "key_phrases": ["phrase1", "phrase2"]
}
Output only the JSON. No explanation.
```

### Explicit Constraints

```
Rules:
- Only use information from the provided documents
- If the answer is not in the documents, say "I don't have enough information"
- Never speculate or infer beyond what's stated
- Cite sources by document title
```

### Negative Constraints

Tell the model what NOT to do — often more effective than just positive instructions:

```
Do NOT:
- Add disclaimers about seeking professional advice
- Pad responses with unnecessary context
- Repeat the question back to the user
```

## RAG Prompt Pattern

The standard RAG prompt structure:

```
System: You are a helpful assistant. Answer questions based ONLY on the provided context.
If the context doesn't contain enough information, say "I don't have that information."

Context:
[Document 1: {title}]
{content}

[Document 2: {title}]
{content}

User: {question}
```

Key decisions:

- **Context placement**: Before or after the question? Research shows beginning is best for long contexts.
- **Document framing**: Including titles helps the model cite correctly.
- **Strict grounding instruction**: "ONLY from context" reduces hallucination.

## In-Context Learning: Why It Works

ICL is not "the model is learning during inference" — weights don't update. Instead:

Current theory: The attention mechanism can implement a form of **meta-learning**. The model learned during pretraining how to pattern-match to examples and generalize from them. ICL activates that capability.

Evidence: Research shows that ICL performance correlates with example quality, not just quantity. Wrong examples hurt performance. Formatting consistency matters.

**Practical implications**:

- 3 high-quality examples > 10 mediocre examples
- Examples should match the distribution of real inputs
- Ordering matters: recent examples (closer to query) have higher influence

## Prompt Failure Modes

|Failure|Cause|Fix|
|---|---|---|
|Model ignores format instructions|Format described abstractly|Show exact example output|
|Model refuses valid request|Phrasing triggers safety filter|Rephrase more neutrally|
|Inconsistent behavior|Ambiguous instructions|Add edge cases explicitly|
|Hallucination|Weak grounding instruction|"ONLY from provided context"|
|Verbose output|No length constraint|"Respond in 1-2 sentences"|
|Wrong language|System in English, user in French|Explicitly handle multilingual|

## Prompt Versioning

Prompts are code. Treat them as such:

- Store in version control (git)
- Track which prompt version produced which evaluation result
- Run regression tests when modifying prompts
- A/B test prompt changes before full rollout
