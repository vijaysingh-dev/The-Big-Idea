# Case Study: Ride-Sharing Platform (Uber-style)

> **Revision tags:** #case-study #geo #real-time #matching  
> **Related:** [[06.4 - Food Delivery]] | [[03.12 - Distributed Locks]]

---

## Requirements Clarification

**Functional:**
- Rider: request a ride, see nearby drivers, track driver in real-time, see fare estimate
- Driver: go online/offline, accept/reject ride requests, navigate to pickup and destination
- Matching: assign nearest available driver to a ride request
- Payments: charge rider on trip completion

**Non-functional:**
- Driver location updates: every 4–5 seconds
- Ride matching: < 30 seconds to match or notify "no drivers available"
- Fare display: < 1s after request
- 99.99% availability for the matching pipeline
- Consistency: no two riders assigned the same driver simultaneously

**Out of scope:** Surge pricing algorithm details, driver ratings, carpooling, scheduling

---

## Estimation

```
DAU drivers:      3M globally (500K peak online at any time)
DAU riders:       20M globally
Ride requests:    10M/day = ~115/s; peak ~500/s

Location updates:
  500K online drivers × 1 update/5s = 100K location writes/s

Location storage:
  Only current location per driver matters
  500K drivers × ~50 bytes = 25 MB → trivially fits in memory
```

**Key challenge:** 100K location writes/s combined with geospatial proximity queries for matching — all with low latency.

```

     ▼                              ▼

     ▼                              │
[Location Service]                  ▼
     │                      [Matching Service]

     │   (driver locations)         │
     └── Kafka ──────────────────── │

                                    │
                             [PostgreSQL]
                             (trips, drivers, riders)
```

## Driver Location Service

The highest-throughput component: 100K writes/s of lat/lng updates.

### Write Path

```
Driver app → gRPC stream → Location Service
Location Service:
  1. Validate driver is online and authenticated
  2. GEOADD drivers:online {lng} {lat} {driver_id}   (O(log N))
  3. Publish to Kafka: driver-locations topic
     → downstream: ETA recalculation, analytics, surge detection
```

**Why Redis GEO over PostGIS:**
- Redis GEO is in-memory → < 1ms writes
- We only need current location (last-write-wins) → no history in Redis
- PostGIS is better for complex polygon queries; Redis GEO is better for "nearest N within radius"

### Driver Status

```
Key:   driver:status:{driver_id}
Value: JSON {status: "available|on_trip|offline", trip_id: null|id}
TTL:   120s (refreshed with each location update)
       If driver app crashes and stops updating → auto-marked offline after 2 minutes
```

## Matching Algorithm

When a rider requests a ride:

```
1. Fare estimation (immediate, < 500ms):
   - Query MapService for route distance and estimated time
   - Apply base rate + per-km + surge multiplier
   - Return estimate to rider UI

2. Driver matching (up to 30s):
   a. GEOSEARCH drivers:available FROMLONLAT {rider_lat} {rider_lng}
                  BYRADIUS 3 km ASC COUNT 10
      → returns 10 nearest available drivers

   b. For each candidate driver (in order of distance):
      - Check driver is still available (not just picked up by another request)
      - Acquire distributed lock: SETNX driver_lock:{driver_id} {request_id} EX 30
      - If lock acquired: send ride offer to driver

3. Driver accepts/rejects:
   - Accept: create trip, release lock on success, notify rider
   - Reject or timeout (15s): release lock, move to next candidate

4. If all 10 candidates exhausted: expand radius to 5km, retry
   If still no match after 30s: "No drivers available" to rider
```

### Preventing Double Assignment

The distributed lock (`SETNX driver_lock:{driver_id}`) is the critical correctness mechanism:

```
Request A and Request B both see Driver 42 as nearest and try to assign:

Request A: SETNX driver_lock:42 request_A EX 30 → 1 (acquired)
Request B: SETNX driver_lock:42 request_B EX 30 → 0 (failed)

Request B moves to next candidate.
Request A sends offer to Driver 42.
```

## Real-Time Tracking

Once a trip is created, rider tracks driver location in real-time.

```
Rider connects WebSocket: /trips/{trip_id}/track

Tracking Service:
  - Subscribe to Redis channel: driver_location:{driver_id}
  - Location Service publishes to this channel on each driver update
  - Tracking Service pushes to rider's WebSocket
  - Every 4-5s, rider sees driver moving on map
```

ETA is recalculated on each location update:
```
ETA = route_distance_remaining / avg_speed
    + traffic_factor (from traffic API)
```

## Trip State Machine

```
REQUESTED
    │ (driver accepts)
    ▼
DRIVER_ASSIGNED
    │ (driver arrives at pickup)
    ▼
DRIVER_AT_PICKUP
    │ (rider boards, driver starts trip)
    ▼
IN_PROGRESS
    │ (driver arrives at destination)
    ▼
COMPLETED
```

Cancellations: `REQUESTED` → `CANCELLED` (by rider, before assignment)  
`DRIVER_ASSIGNED` → `CANCELLED` (by rider, cancellation fee if driver is close)

All transitions stored in a `trip_events` append-only table for audit.

## Surge Pricing (High Level)

When demand > supply in a geographic area:

```
Supply signal: GEOSEARCH drivers:available ... COUNT → low count in area
Demand signal: ride requests per minute in that h3 cell > threshold

Surge calculation:
  surge_multiplier = f(demand / supply)
  Typical: 1.0× (normal) to 3.0× (extreme surge)

Displayed to rider before confirming:
  "Prices are 2.1× higher due to high demand in your area"
```

H3 (Uber's hexagonal geospatial indexing library) divides the globe into hexagonal cells at various resolutions. Surge is calculated per H3 cell — provides smooth geographic boundaries.

## Data Model

```sql
-- Trips: source of truth
CREATE TABLE trips (
    trip_id      UUID PRIMARY KEY,
    rider_id     BIGINT NOT NULL,
    driver_id    BIGINT,
    status       VARCHAR(30) NOT NULL,
    pickup_lat   DECIMAL(9,6),
    pickup_lng   DECIMAL(9,6),
    dest_lat     DECIMAL(9,6),
    dest_lng     DECIMAL(9,6),
    fare_cents   INT,
    created_at   TIMESTAMPTZ NOT NULL,
    started_at   TIMESTAMPTZ,
    completed_at TIMESTAMPTZ
);

-- Trip events: append-only audit log
CREATE TABLE trip_events (
    event_id     UUID PRIMARY KEY,
    trip_id      UUID NOT NULL,
    event_type   VARCHAR(50) NOT NULL,  -- REQUESTED, ACCEPTED, STARTED, etc.
    actor_id     BIGINT NOT NULL,
    lat          DECIMAL(9,6),
    lng          DECIMAL(9,6),
    timestamp    TIMESTAMPTZ NOT NULL
);

-- Driver route (sampled GPS during trip for billing/disputes)
CREATE TABLE trip_gps_samples (
    trip_id      UUID NOT NULL,
    sample_at    TIMESTAMPTZ NOT NULL,
    lat          DECIMAL(9,6),
    lng          DECIMAL(9,6),
    PRIMARY KEY (trip_id, sample_at)
);
```

`trip_gps_samples` is insert-only and queried rarely (disputes, billing verification). Good candidate for Cassandra or cold storage after 30 days.

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Location Redis crashes | Can't find nearby drivers | Redis Cluster with replicas; brief unavailability during failover |
| Driver lock expires during offer | Another request can acquire driver | Lock TTL > offer timeout; driver must accept within TTL |
| Driver app disconnects during trip | Location tracking lost | Show "GPS signal lost"; continue trip using last known location for billing |
| Matching service crash mid-match | Rider waits | Idempotent matching: resume from Kafka offset on restart |
| Payment failure at trip end | Trip completed but rider not charged | Retry queue; trip held in PAYMENT_PENDING state |

## Key Differences from Food Delivery

| Dimension | Food Delivery | Ride Sharing |
|---|---|---|
| Asset being matched | Delivery partner (to restaurant) | Driver (to rider) |
| Location update rate | 5–10s | 4–5s |
| Trip duration | 20–45 min | 5–60 min |
| Multiple concurrent assignments | One partner, one restaurant | One driver, one rider (typically) |
| Route complexity | Partner navigates two points | Driver navigates from location to pickup to destination |
| Cancellation policy | After preparation starts → fee | After driver arrives at pickup → fee |

## What This Design Demonstrates

- Geospatial proximity queries with Redis GEO at 100K writes/s
- Distributed locking to prevent driver double-assignment
- H3 hexagonal indexing for surge pricing zones
- Append-only trip_events table as audit log
- State machine transitions with event sourcing
