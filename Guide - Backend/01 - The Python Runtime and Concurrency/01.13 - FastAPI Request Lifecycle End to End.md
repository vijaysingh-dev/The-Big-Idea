# FastAPI Request Lifecycle End to End

#backend #python #fastapi #asgi #interview

> **In one line:** A request passes through about a dozen layers between the user's browser and your endpoint, each with its own timeout, queue and failure mode. [[01.9 - ASGI and How Uvicorn Serves a Request]] covers the ASGI and uvicorn part. This note covers everything **around** it: the network hops before uvicorn, and FastAPI's own work after Starlette routes the request.

---

## The Whole Path on One Page

```
CLIENT ─────────────────────────────────────────────────────────────────────────────
 1. DNS lookup                 api.example.com → load balancer IP        (cached; TTL)
 2. TCP handshake              SYN / SYN-ACK / ACK                        (1 RTT)
 3. TLS handshake              cert + keys                                (1 RTT on TLS 1.3)
 4. HTTP request bytes sent    over a kept-alive connection if one exists

EDGE ───────────────────────────────────────────────────────────────────────────────
 5. CDN / WAF (optional)       cache hit? blocked? rate limited?
 6. Load balancer / Ingress    TLS terminated here, picks a healthy pod,
                               adds X-Forwarded-For / X-Forwarded-Proto
 7. Reverse proxy (optional)   nginx: buffering, body size limits, timeouts

APP HOST ───────────────────────────────────────────────────────────────────────────
 8. Kernel                     connection sits in the accept queue (backlog)
 9. uvicorn worker             event loop accepts, parses HTTP, builds scope   ← 01.9
10. Starlette                  ServerErrorMiddleware → your middleware
                               → ExceptionMiddleware → Router                  ← 01.9
11. FastAPI route handler      ┌ parse body
                               ├ solve dependencies (Depends graph)
                               ├ validate params + body with Pydantic → 422?
                               ├ run endpoint: async def on loop / def in threadpool
                               ├ validate + serialize return value (response_model)
                               └ build JSONResponse
12. Starlette                  send(http.response.start), send(http.response.body)
13. Background tasks           run AFTER the response is sent, same worker
14. Dependency teardown        `yield` dependencies' cleanup code runs

BACK OUT ───────────────────────────────────────────────────────────────────────────
15. Proxy → LB → client        each hop may buffer, compress, or time out
```

> 💡 **The interview move:** draw this in three bands (client → edge → app) and say that every hop has a **timeout**, a **queue**, and a **way to fail**. Then go deep on whichever band the interviewer picks. Most candidates only know band three, and only the "my endpoint runs" part of it.

## Band 1 — Client to Edge

### DNS, TCP, TLS — the cost before any byte of HTTP

| Step | Cost | What makes it cheap |
|---|---|---|
| DNS | 0 ms (cached) to 100+ ms | OS/browser cache and TTL. See [[02.8 - DNS]] |
| TCP handshake | 1 RTT | **Keep-alive**: reuse the connection ([[03.2 - Connection Reuse and Keep Alive]]) |
| TLS 1.3 handshake | 1 RTT (0-RTT on resumption) | Session resumption, and terminating TLS close to the user ([[02.9 - TLS]]) |

On a 100 ms RTT link, a cold request pays roughly **300 ms before your server sees anything**, and a warm keep-alive request pays almost none of it. That's why "the API is slow from India but fast from the office" is often a connection-reuse or edge-placement problem, not a code problem.

### Load balancer / Ingress

What it does to your request:

- **Terminates TLS.** From here inward, traffic is often plain HTTP (or re-encrypted for mTLS).
- **Picks a backend** with an algorithm (round robin, least connections) among **healthy** targets. Health comes from your readiness probe ([[13.4 - Probes Resources and Autoscaling]]).
- **Rewrites and adds headers.** `X-Forwarded-For` (client IP), `X-Forwarded-Proto` (was it https?), `X-Request-ID` (sometimes).
- **Enforces its own timeouts.** An idle connection timeout (AWS ALB: 60 s by default) and a request timeout.

> ⚠️ **The keep-alive mismatch 502.** The LB keeps an idle connection to your app open for 60 s. uvicorn closes idle connections after **5 s** by default (`--timeout-keep-alive`). If the app closes the connection at the moment the LB sends a new request down it, the LB gets a reset and returns **502** to a user whose request never reached your code. **Rule: the app's keep-alive timeout must be *longer* than the LB's idle timeout** (e.g. `--timeout-keep-alive 65` behind a 60 s ALB). This is one of the most common "random 502s" in production.

### Reverse proxy (nginx), if there is one

Still common on VMs, and less common in Kubernetes where the ingress controller *is* the proxy.

| nginx setting | Effect on your request |
|---|---|
| `client_max_body_size` (default 1 MB) | Large uploads rejected with **413** before reaching Python |
| `proxy_buffering on` (default) | nginx buffers your response. **This breaks SSE/streaming** unless you disable it or send `X-Accel-Buffering: no` ([[04.3 - SSE in Production]]) |
| `proxy_read_timeout` (default 60 s) | If your app doesn't respond in time, nginx returns **504** while your handler is still running |
| `keepalive` in `upstream` | Without it, nginx opens a new TCP connection to the app for every request |

> 💡 **A 504 at the proxy doesn't cancel work in the app.** The handler keeps running, using a DB connection, and its result goes nowhere. Under load this is how a slow dependency turns into pool exhaustion. The fix is **deadlines that shrink inward**: proxy 30 s > app 25 s > DB statement timeout 20 s. See [[03.11 - Timeouts and Deadlines Across Hops]].

## Band 2 — Into the Process

### Kernel accept queue and worker model

The connection completes the TCP handshake in the kernel and waits in the **accept queue** (`--backlog`, default 2048) until a uvicorn worker's event loop calls `accept()`.

```
                           ┌── worker 1 (own process, own event loop, own GIL)
socket :8000 (one bind) ───┼── worker 2
                           └── worker 3
```

- With `--workers N` (or gunicorn + `UvicornWorker`), there are N **processes**. Each has its own event loop, its own DB pool and its own memory. A pool of 10 connections × 4 workers × 6 pods = **240 DB connections**, which is a classic way to exhaust Postgres ([[01.10 - Connection Pools and Limits]], [[06.9 - Connection Pooling and PgBouncer]]).
- In Kubernetes, prefer **1 worker per pod** and scale pods.

From here, uvicorn parses bytes, builds `scope`, starts a Task for `app(scope, receive, send)`, and Starlette's middleware and router take over. This is all covered step by step in [[01.9 - ASGI and How Uvicorn Serves a Request#The Full Path of One Request]].

### Starlette's middleware stack, in order

FastAPI's `app` is a Starlette app. On the first request it builds this onion:

```
ServerErrorMiddleware        ← outermost. Catches anything unhandled → 500 (debug page if debug=True)
  └─ your middleware, LAST added = OUTERMOST
       └─ CORSMiddleware, GZipMiddleware, TrustedHost, custom...
            └─ ExceptionMiddleware   ← maps HTTPException / registered handlers → responses
                 └─ Router           ← finds the route
```

```python
app.add_middleware(TimingMiddleware)    # added first  → runs INSIDE
app.add_middleware(CORSMiddleware, ...) # added second → runs OUTSIDE (sees request first)
```

> ⚠️ **Middleware order is the reverse of `add_middleware` order.** Put CORS outermost or preflight `OPTIONS` requests can be rejected by auth middleware before CORS headers are added, and the browser reports a CORS error that's really a 401.

### Routing

`Router` walks the route list **in order** and asks each route whether it matches:

| Result | Meaning | Outcome |
|---|---|---|
| `FULL` | Path and method match | Handle it. Stop looking |
| `PARTIAL` | Path matches, method doesn't | Remember it. If nothing better matches, return **405** |
| `NONE` | No match | Keep going. Nothing at all → **404** |

Two consequences:
- **Order matters.** `/users/me` must be declared before `/users/{user_id}`, or `"me"` is parsed as a `user_id` (and fails validation with a 422 if the type is `int`).
- Matching is a linear scan over compiled regexes. It's fast enough with hundreds of routes, but it's why a huge app with path-heavy routing shows routing in profiles.

## Band 3 — What FastAPI Does for One Request

This is the part people say "FastAPI handles it" about. Here's what's actually in `fastapi/routing.py` (`get_request_handler`) and `fastapi/dependencies/utils.py` (`solve_dependencies`).

### Step 1 — Read and parse the body

If the endpoint declares a body (a Pydantic model, `Body()`, `Form()`, `File()`), FastAPI calls `await request.body()` / `request.json()` / `request.form()`. That is where ASGI `receive()` actually pulls the body off the socket.

- Malformed JSON → **422** with a `json_invalid` error, before any of your code runs.
- `UploadFile` spools to a `SpooledTemporaryFile` (memory, then disk above a threshold), so large uploads don't sit in RAM.

### Step 2 — Solve the dependency graph

```python
async def get_db():                       # yield dependency: setup + teardown
    async with SessionLocal() as session:
        yield session

async def get_current_user(token: str = Depends(oauth2_scheme), db = Depends(get_db)):
    return await users.from_token(db, token)

@app.get("/orders/{order_id}")
async def get_order(order_id: int, user = Depends(get_current_user), db = Depends(get_db)):
    ...
```

At startup FastAPI turned each endpoint signature into a **dependency tree** (`Dependant`). Per request, `solve_dependencies` walks it depth-first:

1. Extract **path / query / header / cookie** params from `scope`.
2. Resolve every `Depends(...)`, recursively, children first.
3. **Cache per request:** `get_db` appears twice above (directly and via `get_current_user`), but runs **once**. Both get the same session. (`Depends(fn, use_cache=False)` opts out.)
4. `async def` dependencies are awaited on the loop. **`def` dependencies run in the threadpool**, exactly like `def` endpoints.
5. `yield` dependencies are entered into an exit stack. Their code after `yield` runs **after** the endpoint returns.

> ⚠️ **When `yield` teardown runs relative to the response being sent has changed across FastAPI versions** (notably 0.106 and again in later releases). Don't rely on a `yield`-dependency's session still being open inside a `BackgroundTask` or a `StreamingResponse` generator without checking the docs for your version. Open a fresh session there instead.

### Step 3 — Validate everything with Pydantic

All the extracted values (path, query, headers, cookies, body) are validated against their declared types **together**, and all errors are collected:

```json
HTTP 422
{
  "detail": [
    {"type": "int_parsing", "loc": ["path", "order_id"], "msg": "Input should be a valid integer", "input": "abc"},
    {"type": "missing", "loc": ["query", "limit"], "msg": "Field required", "input": null}
  ]
}
```

This is `RequestValidationError`, turned into a 422 by FastAPI's default exception handler. You can override it with `@app.exception_handler(RequestValidationError)`, which is useful when your API contract demands a different error shape ([[05.3 - Error Design]]).

### Step 4 — Call your endpoint, on the loop or in a thread

This is the single most important fork in the whole lifecycle:

| You wrote | FastAPI does | Safe for |
|---|---|---|
| `async def endpoint()` | `await endpoint()` **directly on the event loop** | Async I/O only (`asyncpg`, `httpx.AsyncClient`, async SDKs) |
| `def endpoint()` | `await run_in_threadpool(endpoint)` → anyio worker thread, **max 40 at once** by default | Blocking libraries (`requests`, `psycopg2`, sync SDKs) |

```python
@app.get("/bad")
async def bad():
    return requests.get("https://slow.api").json()   # blocks the WHOLE worker: every request stalls

@app.get("/ok-sync")
def ok_sync():
    return requests.get("https://slow.api").json()   # runs in a thread: loop stays free

@app.get("/ok-async")
async def ok_async(client: httpx.AsyncClient = Depends(get_http)):
    return (await client.get("https://slow.api")).json()
```

> ⚠️ **The two failure modes are different, and both are common:**
> - **Blocking call in `async def`** → one slow request freezes *every* request on that worker. Latency spikes across all endpoints at once, including the health check. See [[01.6 - The Blocking Call Problem]].
> - **Too many slow `def` endpoints** → the 40-thread limiter fills up and requests **queue for a thread** before your code runs. Endpoint timers look fine while user latency is terrible, because the wait happens before your code starts. See [[01.8 - Offloading Work]].

### Step 5 — Validate and serialize the return value

```python
class OrderOut(BaseModel):
    id: int
    total: Decimal
    status: str
    # no 'internal_notes' field

@app.get("/orders/{order_id}", response_model=OrderOut)   # or: -> OrderOut return annotation
async def get_order(order_id: int, db = Depends(get_db)):
    return await orders.get(db, order_id)   # ORM object with internal_notes on it
```

FastAPI:
1. **Validates** the return value against `OrderOut`. If your code returns something that doesn't fit, that's a **500** (`ResponseValidationError`). It's your bug, not the client's.
2. **Filters** it to only `OrderOut`'s fields, so `internal_notes` never leaks. This is a real security feature: `response_model` is your allow-list.
3. **Serializes** to JSON bytes and wraps them in a `JSONResponse`.

If you return a `Response` object directly (`JSONResponse`, `StreamingResponse`, `ORJSONResponse`), FastAPI **skips** validation and filtering. That's faster, but you lose the allow-list.

> 💡 For large responses, serialization can be the slowest step in the whole lifecycle. A 5,000-row list through Pydantic validation and JSON encoding can take longer than the query that produced it. The fixes, in order: paginate ([[05.2 - Versioning Pagination and Filtering]]), return less, then skip the extra validation pass with a direct response.

### Step 6 — Send, then background tasks, then teardown

```python
@app.post("/signup")
async def signup(user: UserIn, background: BackgroundTasks):
    created = await users.create(user)
    background.add_task(send_welcome_email, created.email)   # runs after the response is sent
    return created
```

- Starlette sends `http.response.start` and the body through uvicorn ([[01.9 - ASGI and How Uvicorn Serves a Request]]).
- **Then** background tasks run, **in the same worker, on the same event loop** (or in the threadpool if `def`).
- `BackgroundTasks` is **not a job queue.** If the pod restarts, the task is lost. There are no retries and no visibility, and a slow task occupies the worker. Use it for fire-and-forget extras like cache warming or analytics pings. Anything that must happen (emails, payments, webhooks) goes to a real queue ([[08.1 - Why Background Work Exists]]).

### Where errors go

| Raised | Caught by | Client sees |
|---|---|---|
| Validation failure on input | FastAPI → `RequestValidationError` handler | 422 |
| `HTTPException(404)` in your code or a dependency | `ExceptionMiddleware` | 404 with `{"detail": ...}` |
| A custom exception with `@app.exception_handler(MyError)` | `ExceptionMiddleware` | Whatever your handler returns |
| Return value doesn't match `response_model` | `ResponseValidationError` → 500 | 500 |
| Any other unhandled exception | `ServerErrorMiddleware` | 500 (and the traceback is logged) |
| Client disconnects mid-request | uvicorn sends `http.disconnect`, the task may be cancelled | Nothing, because they're gone |

## Lifespan — The Request's Prerequisites

None of the above works unless startup ran:

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.db = await asyncpg.create_pool(DSN, min_size=5, max_size=20)
    app.state.http = httpx.AsyncClient(timeout=httpx.Timeout(5.0))
    app.state.redis = redis.asyncio.from_url(REDIS_URL)
    yield                                    # ← app serves requests here
    await app.state.http.aclose()
    await app.state.redis.aclose()
    await app.state.db.close()

app = FastAPI(lifespan=lifespan)
```

> 💡 **Create clients once per process, never per request.** A new `httpx.AsyncClient()` per request means a new connection pool per request, so every call pays TCP and TLS handshakes again (band 1 costs, on every outbound call). This is one of the most common performance bugs in FastAPI codebases.

## Where Latency Hides — A Debugging Map

User says "the endpoint takes 2 s", but your handler logs say 50 ms. The time went somewhere else:

| Symptom | Likely hop | How to confirm |
|---|---|---|
| Slow only on first request / new clients | DNS, TCP, TLS (band 1) | Browser devtools timing tab. `curl -w "%{time_connect} %{time_appconnect} %{time_starttransfer}"` |
| Random 502s, no app error logs | Keep-alive mismatch at the LB | LB logs show `backend connection reset`. Compare idle timeouts |
| 504 at nginx/LB while the app logs success later | Proxy timeout shorter than handler time | Compare proxy and app timestamps for the same request ID |
| All endpoints slow at once, including `/health` | Blocking call inside `async def` | `py-spy dump`, asyncio debug mode ([[01.12 - Profiling and Debugging Async Services]]) |
| `def` endpoints slow, handler timers fine | Threadpool (40) saturated | Log time-to-first-line-of-handler vs request start |
| Slow under load only, DB fine | Connection pool wait | Pool wait-time metric ([[01.10 - Connection Pools and Limits]]) |
| Slow for big responses only | Pydantic validation and serialization | Profile. Time spent in `serialize_response` / `model_dump` |
| SSE arrives in one big lump | Proxy buffering or `BaseHTTPMiddleware` | Disable buffering, use pure ASGI middleware |

The universal tool is a **request ID propagated across every hop** plus **timing at each boundary**. Without it you are guessing which band the time is in ([[12.3 - Instrumenting Conduit End to End]]).

## The Two-Minute Interview Answer

> *"What happens when a request hits a FastAPI service?"*

"I'd split it into three parts. First, the network: DNS, then a TCP and TLS handshake, which keep-alive mostly removes. Then a load balancer or ingress terminates TLS, adds forwarded headers and picks a healthy pod. Each hop has its own timeout, so I keep deadlines shrinking inward, and the app's keep-alive timeout longer than the LB's to avoid 502s.

Second, the server: the connection waits in the kernel's accept queue until a uvicorn worker's event loop accepts it. Uvicorn parses the HTTP into an ASGI scope and calls the app with scope, receive and send. Starlette runs the middleware stack, with server-error handling outermost and exception handling around the router, and the router matches the path. That's where 404 and 405 come from.

Third, FastAPI itself: it reads the body, solves the dependency graph with per-request caching, and validates every input with Pydantic, returning 422 with all the errors if anything fails. Then it calls the endpoint. `async def` runs on the event loop, so it must never block. `def` runs in a 40-thread pool. The return value is validated and filtered against the response model, serialized and sent. Background tasks run after the response, and yield dependencies clean up.

In production the things that bite are blocking calls in async endpoints, threadpool or connection-pool exhaustion, proxy buffering breaking streaming, and timeout mismatches between hops."

**Likely follow-ups:**
- *Why does a `requests.get` in an `async def` hurt other users?* Because one worker runs one event loop on one thread. A blocking call stops the loop, so no other coroutine runs until it returns.
- *What's `Depends` caching?* The same dependency used several times in one request's graph resolves once and is shared. That's why a `get_db` dependency gives the endpoint and `get_current_user` the same session.
- *Is `BackgroundTasks` enough for sending emails?* For a demo, yes. In production, no: it isn't durable, has no retries and dies with the pod. Use Celery, arq or a broker.
- *How many requests can one worker handle concurrently?* For async I/O, thousands. The limits are memory, `--limit-concurrency`, and downstream pools (DB, HTTP), not the worker. For `def` endpoints, about 40 at a time per worker, set by the anyio limiter.

## Exercise

Build a small FastAPI service and **measure each band**:

1. **Band 1:** `curl -w` with `time_namelookup`, `time_connect`, `time_appconnect`, `time_starttransfer`, cold vs with `--keepalive`. Put nginx in front and compare.
2. **Keep-alive 502:** run uvicorn with `--timeout-keep-alive 1` behind nginx with a long upstream keepalive, send requests spaced ~1 s apart with `hey` or `k6`, and capture the 502s. Fix it by inverting the timeouts.
3. **Band 2:** add three middlewares that log on enter and exit. Confirm the onion order is the reverse of `add_middleware`.
4. **Band 3:** endpoint `async def` with `time.sleep(1)` vs `def` with `time.sleep(1)` vs `async def` with `await asyncio.sleep(1)`. Hit each with 100 concurrent requests and record p50, p99 and throughput. Then set the anyio limiter to 5 and repeat the `def` case.
5. **Serialization:** return 10,000 rows via `response_model` vs a direct `ORJSONResponse`. Measure the difference.

**Done when** you have a table with your own numbers for every row, and you can explain each one without looking at this note.
