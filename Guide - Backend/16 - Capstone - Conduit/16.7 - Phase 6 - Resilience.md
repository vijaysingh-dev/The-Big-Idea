## What You Build

### Timeouts everywhere, from a budget

```
Browser patience:      10s
  Gateway budget:       8s
    Document service:   5s
      Postgres:         2s
      Redis:          200ms
    Search service:     2s
```

```python
remaining = deadline - time.monotonic()
if remaining <= 0:
    raise DeadlineExceeded()
headers["x-deadline-ms"] = str(int(remaining * 1000))
```

⚠️ **Propagate a deadline, not a duration.** A chain of fixed timeouts sums to more than the client will wait ([[03.11 - Timeouts and Deadlines Across Hops]]).

💡 **Redis at 200ms is deliberately aggressive.** A cache lookup slower than that is worse than a cache miss — **fail fast and go to the database.**

**Every client needs all four phases**: connect, read, write, and **pool** — the last is the one people forget ([[11.2 - Timeouts Retries and Jitter]]).

### Retry budgets, not just retry counts

```python
class RetryBudget:
    def allow(self) -> bool:
        return self.retries / max(self.requests, 1) < 0.20
```

⚠️ **Per-call retry limits do not bound system-wide amplification.** At a 90% failure rate, three retries per call triples your load on a dependency that is already failing.

**Cap retries at 10–20% of total traffic**, regardless of failure rate.

### Bulkheads per dependency

```python
LIMITS = {"search": 20, "embedding": 10, "storage": 30}

async with semaphore_for("search"):
    return await search_client.query(q)
```

💡 **Without a bulkhead, one slow dependency consumes every worker** — including those serving requests that do not use it ([[11.3 - Circuit Breakers and Bulkheads]]).

### Circuit breakers with degradation

```python
async def get_related(doc_id: str) -> list[Document]:
    if breaker["search"].is_open():
        degraded_responses_total.labels(reason="search_unavailable").inc()
        return []
    try:
        async with asyncio.timeout(remaining_budget()):
            return await search_client.similar(doc_id)
    except (TimeoutError, ConnectionError):
        breaker["search"].record_failure()
        return []
```

⚠️ **A breaker without a degradation path just fails faster.** The value is entirely in what you do when it is open ([[11.6 - Graceful Degradation]]).

### The degradation ladder

| Level | Trigger | Behaviour |
|---|---|---|
| **0 — Full** | Normal | Everything |
| **1 — No enrichment** | Search circuit open, or Redis down | No related documents, no recommendations |
| **2 — Stale OK** | Database pool pressure > 80% | Serve cached data past freshness |
| **3 — Read-only** | Primary unavailable | Reads from a replica; writes rejected clearly; ingestion queued |
| **4 — Maintenance** | Manual only | Static page |

💡 **Level 3 is the valuable one.** A Postgres primary failure becomes "you can read your documents, editing is temporarily unavailable" rather than a blank page ([[06.12 - Replication and Failover]]).

⚠️ **Ingestion queues rather than fails at level 3.** Documents uploaded during the degradation are processed when writes return, and the user is told so.

**Every level needs a manual override**, so an operator can drop to level 2 immediately without waiting for automation.

### Load shedding

```python
if await current_level() >= ServiceLevel.STALE_OK and priority == Priority.BACKGROUND:
    raise HTTPException(503, headers={"Retry-After": "5"})
```

**Shed by priority, at the edge, where rejection is cheapest** ([[11.4 - Backpressure and Load Shedding]]).

```
CRITICAL     health checks, auth
HIGH         interactive user requests
NORMAL       list views, search
BACKGROUND   prefetch, analytics
```

### Rate limiting

| Scope | Limit | Where |
|---|---|---|
| IP, anonymous | 100/min | Gateway |
| Organisation | Plan-based, token bucket | Gateway |
| Uploads | 20/min per org | Application |
| Exports | 5/hour per org | Application |
| **GraphQL** | Cost-based points | Application |
| **Embedding API (outbound)** | Global token bucket | Client |

⚠️ **The outbound limit is global across all workers**, not per worker ([[11.5 - Rate Limiting and Quotas]]).

### Graceful shutdown

```python
async def shutdown():
    shutting_down.set()                    # /readyz fails immediately
    await asyncio.sleep(10)                # endpoint removal propagates
    await server.shutdown()                # finish in-flight requests
    await pool.close()
```

```yaml
lifecycle:
  preStop:
    exec: {command: ["sleep", "10"]}
terminationGracePeriodSeconds: 120         # > longest task
```

⚠️ **Endpoint removal and `SIGTERM` are concurrent, not ordered** ([[11.7 - Graceful Shutdown and Draining]]). The sleep is the fix, not a hack.

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Deadline propagation** | Fixed timeouts per hop | A chain must fit inside the client's patience |
| **Retry budget** | Retry count only | Bounds amplification at high failure rates |
| **Retries at one layer** | Every layer | 3 × 3 × 3 = 27 requests |
| **Bulkhead per dependency** | A global limit | One slow dependency should degrade one path |
| **Four degradation levels** | All-or-nothing | Level 3 turns an outage into degraded service |
| **Shed at the gateway** | In the service | Cheapest rejection point |
| Manual level override | Automation only | Operators need to act faster than automation notices |

## What Will Go Wrong

### Slow is worse than down

```
Dependency latency 50ms → 5s
In-flight requests 50 → 5,000
Worker pool: exhausted
Your service: down, on every endpoint
```

💡 **Measure both cases.** The down case fails fast and cleanly; the slow case is the one that takes you out ([[11.1 - How Systems Fail]]).

### The Redis outage, again

⚠️ **Phase 3 measured this. Now test it with the full defence set** — bulkheads, shedding, and a local fallback cache.

**Confirm you survive at production load. If not, you have not finished phase 6.**

### The liveness cascade

⚠️ **A dependency check in the liveness probe turns a slow database into a fleet-wide restart loop** ([[13.4 - Probes Resources and Autoscaling]]).

**Reproduce it once.** It is self-sustaining and it is memorable.

### Metastable failure

```
30-second 3× spike on a system at 70% capacity
Spike ends → the system does not recover
```

⚠️ **Retries from timed-out requests, stale queued work, and cold caches mean the effort per request has risen** ([[11.1 - How Systems Fail]]).

**Induce it, then confirm load shedding prevents it entirely.**

### The untested degradation path

⚠️ **A fallback that has never run is broken.** The classic finding is a degradation path that throws on the fallback line.

**Parameterise a test over every dependency, down and slow.**

### The abandoned task

```
terminationGracePeriodSeconds: 60
Longest task: 90 seconds
→ every deploy abandons work
```

**Measure tasks redone per rollout.**

## Acceptance Criteria

```
□  Every network call: connect, read, write and pool timeouts
□  Deadline propagated; no hop works past the client's budget
□  Retry budget bounds amplification at a 90% failure rate
□  Retries at exactly one layer, documented
□  Bulkhead per dependency, with the limit derived from capacity
□  Circuit breaker plus a degradation path for every optional dependency
□  Four degradation levels, each tested, with a manual override
□  Read-only mode works: every write path found and handled
□  Load shedding by priority at the gateway
□  Redis outage survived at production load, measured
□  Metastable failure induced, then prevented by shedding
□  Liveness checks only the process; the cascade reproduced and fixed
□  Zero requests dropped and zero tasks abandoned per rollout
□  Ten chaos experiments run, with at least three hypotheses disproved
```

⚠️ **The last criterion is the point of the phase.** If every hypothesis held, you did not inject hard enough.

**Question to answer:** How does Hystrix bound fallback concurrency separately from the primary, and why does that matter? Then: what does AWS argue about fallbacks, and which forms are safe?

**Read, in order:**

3. `Netflix/Hystrix` — `HystrixCommand.getFallback` and the `FALLBACK_REJECTION` state. **The separate fallback pool is the answer to the first question**

5. **Google SRE Book — "Addressing Cascading Failures"** — the mechanisms and the recovery procedures

💡 The Hystrix detail worth stealing: **the fallback has its own bounded pool.** If the primary is failing and everything falls back, the fallback cannot consume unbounded resources — **it sheds too.** Most hand-rolled fallbacks miss this.

## Exercise

**Drill 16.7 — Break every dependency, on purpose**

```
conduit/phases/06/
├── resilience/{timeouts.py, budgets.py, bulkheads.py, breakers.py,
│               degradation.py, shedding.py, shutdown.py}

└── PHASE6.md
```

**Part 1 — Slow versus down.** For each of the seven dependencies, inject "down" and "slow" separately with toxiproxy.

**Measure for both: your throughput, in-flight requests, worker utilisation, and the error rate on endpoints not using that dependency.**

**Fourteen measurements. Slow should be dramatically worse.**

Then add the full defence set and repeat. **Chart before and after.**

**Part 2 — The dependency matrix.** For every dependency: required or optional, if-slow behaviour, if-down behaviour, and a test.

**Then the parameterised test:**

```python
@pytest.mark.parametrize("dep,mode", product(DEPENDENCIES, ["down", "slow"]))
async def test_degrades(dep, mode, toxiproxy): ...
```

⚠️ **Most codebases pass the "down" half and fail the "slow" half.**

**Part 3 — Read-only mode, thoroughly.** Implement level 3.

**Then run your full test suite in read-only mode and find every write path it breaks.**

**Report how many you did not know about** — it is usually three or four: a last-seen timestamp, an audit row, a session refresh.

**Part 4 — The Redis outage at production load.** Steady load, 85% hit ratio. **Kill Redis.**

**Chart database CPU, pool wait, and p99 for two minutes.** Determine survival.

Then add: shedding at pool pressure, a small local fallback cache, and request coalescing. **Re-run until you survive**, and report which mitigation contributed most.

**Part 5 — Metastable failure.** 70% capacity, a 30-second 3× spike, retries on, no shedding.

**Confirm the system does not recover after the spike ends.** Chart latency and throughput for ten minutes after.

Then execute the recovery procedure — shed, drain, warm, restore gradually — and measure time to recovery.

**Then add shedding below the knee and confirm it never enters the state.**

**Part 6 — The liveness cascade.** Put a database check in the liveness probe. Make the database slow.

**Confirm every pod restarts, and that it is self-sustaining.**

Then remove the check and confirm the service degrades instead.

**Part 7 — Retry amplification.** Retries at gateway, client library and mesh-equivalent layers.

**Confirm 27 requests per logical call.** Chart downstream load against failure rate.

Then pick one layer and add budgets. **Chart again** — the budgeted version must stay bounded as failure approaches 100%.

**Part 8 — Ten chaos experiments.** Write ten hypotheses with measurable steady states before running any ([[11.9 - Chaos and Failure Injection]]).

**Run them all at staging scale.**

**Record which hypotheses were disproved, why your model was wrong, and what you changed.**

⚠️ **Target: at least three disproved.** Then fix and re-run until all hold.

**Part 9 — Shutdown.** Under load, measure requests dropped and tasks abandoned per rollout.

**Sweep grace period and `preStop` duration.** Find the values that produce zero of both, and report the rollout duration cost.

**Done when:**
- Your fourteen slow-versus-down measurements are charted before and after defences
- The parameterised degradation test passes for every dependency, both modes
- Read-only mode revealed write paths you did not know about
- You survive a Redis outage at production load, with the key mitigation identified
- Metastable failure is induced and then prevented by shedding
- The liveness cascade is reproduced as self-sustaining, then fixed
- Retry budgets bound amplification at a 90% failure rate
- Three chaos hypotheses were disproved and fixed
- Zero dropped requests and zero abandoned tasks per rollout
