# Aura Architecture and Where It Survives

## Why this section is short

Aura is superseded. LWC does everything Aura does, faster, on web standards, and with skills that transfer outside Salesforce.

This section exists for three reasons: you will inherit Aura components, a small number of things still require Aura, and interviews ask about it.

Four notes, not twenty. That allocation is deliberate.

## What Aura was

The component framework Salesforce built in 2014, before web standards caught up. It has its own component model, its own markup language, its own event system, and its own expression syntax — all of which had to be learned separately from anything else in web development.

```xml
<!-- claimSummary.cmp -->
<aura:component implements="flexipage:availableForRecordHome,force:hasRecordId"
                access="global">

    <aura:attribute name="recordId" type="Id"/>
    <aura:attribute name="claim" type="Object"/>
    <aura:attribute name="isLoading" type="Boolean" default="true"/>

    <aura:handler name="init" value="{!this}" action="{!c.doInit}"/>

    <lightning:card title="Claim Summary">
        <aura:if isTrue="{!v.isLoading}">
            <lightning:spinner alternativeText="Loading"/>
            <aura:set attribute="else">
                <p>{!v.claim.Claim_Number__c}</p>
            </aura:set>
        </aura:if>
    </lightning:card>
</aura:component>
```

```javascript
// claimSummaryController.js
({
    doInit: function(component, event, helper) {
        helper.loadClaim(component);
    }
})
```

```javascript
// claimSummaryHelper.js
({
    loadClaim: function(component) {
        const action = component.get("c.getClaim");
        action.setParams({ claimId: component.get("v.recordId") });

        action.setCallback(this, function(response) {
            if (response.getState() === "SUCCESS") {
                component.set("v.claim", response.getReturnValue());
                component.set("v.isLoading", false);
            }
        });

        // the action must be explicitly enqueued — it does not fire on its own
        $A.enqueueAction(action);
    }
})
```

The same functionality in LWC is roughly a third of the code, in two files rather than three.

## The bundle

An Aura component is a folder of typed files, most of which are optional:

```
force-app/main/default/aura/claimSummary/
    claimSummary.cmp             markup
    claimSummaryController.js    event handlers
    claimSummaryHelper.js        shared logic
    claimSummaryRenderer.js      render lifecycle overrides
    claimSummary.css             styles
    claimSummary.design          App Builder properties
    claimSummary.svg             App Builder icon
    claimSummary.auradoc         documentation
```

**Controller and helper are separate by convention.** Controller methods handle events; helper methods hold reusable logic and are callable from both. The split exists because controller functions cannot call each other directly, which is one of Aura's more arbitrary constraints.

## The concepts, briefly

**Attributes** are the state, declared with types:

```xml
<aura:attribute name="claims" type="List" default="[]"/>
<aura:attribute name="selectedId" type="Id"/>
<aura:attribute name="isEditable" type="Boolean" default="false" access="private"/>
```

`access` controls visibility: `private`, `public`, or `global`. Public attributes are the Aura equivalent of `@api`.

**Expressions** use `{!v.attributeName}` for value providers, `{!c.methodName}` for the controller.

```xml
<p>{!v.claim.Claim_Number__c}</p>
<lightning:button onclick="{!c.handleApprove}"/>
<p>{!v.amount > 500000}</p>          <!-- expressions can contain logic -->
```

**Aura allows logic in expressions**, which LWC deliberately does not. It is convenient and it puts business logic in markup where it cannot be unit tested.

**Two-way binding** with `{!v.x}` versus one-way with `{#v.x}` — a distinction with no LWC equivalent and a frequent source of confusing behaviour, since two-way binding means a child mutating an attribute changes the parent's value invisibly.

**Interfaces** declare where a component can be used:

```xml
implements="flexipage:availableForRecordHome,force:hasRecordId,force:lightningQuickAction"
```

The LWC equivalent is the `targets` in the metadata file.

## Where Aura still survives

The list is short and shrinking.

**Some quick action types.** A few action configurations still expect an Aura component, though `lightning__RecordAction` covers most cases now.

**Lightning Out bootstrapping.** Embedding an LWC in an external page requires an Aura dependency application:

```xml
<aura:application access="GLOBAL" extends="ltng:outApp">
    <aura:dependency resource="c:claimList"/>
</aura:application>
```

This is the most common surviving requirement, and the Aura app is a three-line wrapper containing no logic. See [[14.19 - Deploying and Exposing Components]].

**A handful of console APIs** and some Experience Cloud contexts, though the gap narrows each release.

**Existing components that work.** The largest category by far.

## The one-way nesting rule

**An LWC can be placed inside an Aura component. An Aura component cannot be placed inside an LWC.**

```xml
<!-- Works: an Aura component containing an LWC -->
<aura:component>
    <c:claimList recordId="{!v.recordId}"/>
</aura:component>
```

```html
<!-- Not possible -->
<template>
    <c-legacy-aura-component></c-legacy-aura-component>
</template>
```

This asymmetry shapes every migration. The Aura shell stays and its internals are replaced piece by piece, working inward. A migration that tries to start at the outside stalls immediately.

## Aura versus LWC, honestly

| | Aura | LWC |
| --- | --- | --- |
| Foundation | Proprietary framework | Web standards |
| Performance | Heavier — framework overhead per component | Lighter |
| Files per component | Up to 8 | 2 to 4 |
| Skills transfer | Salesforce only | Any web development |
| Logic in markup | Allowed | Not allowed |
| Two-way binding | Yes | No |
| Events | Framework-specific system | Standard DOM events |
| Testing | Limited | Jest |
| Investment | Maintenance only | Active |

The performance difference is real rather than marginal. Aura's framework overhead per component is significant, and a page with many Aura components loads noticeably slower than the LWC equivalent.

## When to leave Aura alone

The honest position, because "migrate everything" is bad advice.

**Leave it when:**

- It works and nothing about it is changing
- The component is stable and rarely touched
- The business value of the rewrite is zero
- It is a Lightning Out bootstrap app, which cannot be LWC

**Migrate when:**

- You are substantially changing it anyway
- It is on a performance-critical page
- It is breaking each release
- It blocks something else
- The component is being extended significantly

A working Aura component is not technical debt in any meaningful sense. Rewriting it consumes budget and introduces risk for no business outcome, and "we migrated everything to LWC" is not an achievement anyone outside the team notices.

The pragmatic policy most teams settle on: **no new Aura, migrate opportunistically, and never as a project.**

## Recognizing Aura in an org

```bash
sf data query --use-tooling-api \
  --query "SELECT Id, DeveloperName, ApiVersion, Description FROM AuraDefinitionBundle ORDER BY DeveloperName" \
  --target-org production
```

Worth running when inheriting an org, alongside the trigger and flow inventories. Components on very old API versions are the ones most likely to break on a release.

The count also tells you something about the org's history and where the migration effort would land.
