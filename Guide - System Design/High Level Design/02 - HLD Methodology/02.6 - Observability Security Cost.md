## Observability

### What It Is

Observability is the ability to understand the internal state of a system from its external outputs. A system is observable if you can answer "why is this broken?" without deploying new code.

The three pillars:

```
Logs    → What happened (discrete events)
Metrics → How the system is behaving over time (numbers)
Traces  → How a single request moved through the system
```

### Logs

**What to log:**
- Every request in/out (with status code, latency)
- Every error with full context (user ID, request ID, stack trace)
- Every significant state change (order placed, payment charged)
- Every external call (DB query, API call, cache hit/miss)

**Structured logging (JSON):**
```json
{
  "timestamp": "2024-01-15T10:23:45Z",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "abc123",
  "user_id": "u_9281",
  "event": "payment_failed",
  "payment_id": "pay_7731",
  "error": "timeout after 2000ms",
  "duration_ms": 2001
}
```

Structured logs are queryable. Plain-text logs are not.

**Log levels:**
```
DEBUG   → fine-grained, dev only (never in prod by default)
INFO    → normal operations, key business events
WARN    → unexpected but handled (retry triggered, cache miss spike)
ERROR   → failure that was caught and handled
FATAL   → unrecoverable failure (service will crash)
```

**Log pipeline:**  
Application → Log shipper (Fluentd/Filebeat) → Aggregator (Kafka) → Storage (Elasticsearch, S3) → Query (Kibana, Grafana Loki)

### Metrics

Metrics answer "is the system healthy right now?"

**The RED method (for services):**
```
Rate     → Requests per second
Errors   → Error rate (%)
Duration → Latency (p50, p95, p99)
```

**The USE method (for resources):**
```
Utilization → % of time resource is busy (CPU, disk)
Saturation  → Queue depth, backlog
Errors      → Hardware errors, disk errors
```

**Key metrics to expose for every service:**
```
http_requests_total{method, endpoint, status_code}
http_request_duration_seconds{quantile}
db_query_duration_seconds{query_type}
cache_hit_rate
queue_depth
active_connections
error_rate_percent
```

**Metrics pipeline:**  
Services expose `/metrics` → Prometheus scrapes → Grafana visualizes → Alertmanager fires alerts

### Distributed Tracing

In a microservices system, a single user request touches 5–15 services. A trace follows that request across all of them.

```
Request: GET /checkout

Trace:
  [API Gateway]         5ms
    └── [Order Service] 120ms
          ├── [Payment Service] 80ms  ← slow!
          │     └── [Fraud Service]   45ms
          └── [Inventory Service]     15ms
```

Without tracing, you see the 120ms but can't tell which downstream call caused it.

**Trace anatomy:**
- **Trace ID:** Unique ID for the entire request journey
- **Span:** One unit of work (one service call, one DB query)
- **Parent span:** The span that caused this one

**Implementation:** Inject `trace-id` and `span-id` headers on every outbound call. Propagate through the call chain. Collect spans centrally.

**Tools:** Jaeger, Zipkin, AWS X-Ray, OpenTelemetry (standard instrumentation layer).

### Alerting Strategy

Alerts should fire on **symptoms**, not causes.

```
Bad alert:  CPU > 80%        (cause — not every CPU spike means users are affected)
Good alert: p99 latency > 500ms (symptom — users are experiencing slowness)

Bad alert:  Disk usage > 70% (premature — doesn't mean users are affected yet)
Good alert: Disk will fill in < 4 hours at current growth rate
```

**SLO-based alerting:**
Define your SLO (e.g., 99.9% of requests succeed in < 200ms). Alert when your error budget is being burned too fast.

### Observability Design in HLD

Always include in your design:
- Centralized log aggregation (ELK stack, Grafana Loki, Datadog)
- Metrics collection and dashboards (Prometheus + Grafana, Datadog)
- Distributed tracing (Jaeger, OpenTelemetry)
- On-call alerting (PagerDuty, OpsGenie) on SLO breaches

## Security Boundaries

### Authentication vs Authorization

**Authentication:** Who are you? (identity verification)  
**Authorization:** What are you allowed to do? (permission check)

These are separate systems. Don't conflate them.

### Authentication Patterns

**JWT (JSON Web Token):**
```
Client logs in → server issues signed JWT containing claims
Client sends JWT on every request → server verifies signature → extracts claims
```
- Stateless — server holds no session state
- Can't revoke before expiry without a blocklist (adds state back)
- Good for: APIs, microservices, mobile apps

**Session cookie:**
```
Client logs in → server creates session record in DB/Redis → sends session_id cookie
Client sends cookie → server looks up session → gets user info
```
- Stateful — requires session store (Redis)
- Easy to revoke (just delete session record)
- Good for: web applications

**OAuth2 / OpenID Connect:**
- Delegate authentication to an identity provider (Google, Okta, Auth0)
- Your service trusts the IdP's assertion about user identity
- Good for: SSO, third-party integrations

> Full coverage: [[03.17 - Auth and Sessions]]

### Authorization Patterns

**RBAC (Role-Based Access Control):**
```
User → has Roles → Roles have Permissions
User "alice" has role "editor" → editors can write posts
```
Simple, auditable, widely understood.

**ABAC (Attribute-Based Access Control):**
```
Decision based on attributes: user.department == resource.department
```
More flexible than RBAC, more complex to manage.

**Resource-level permissions:**
```
User can read own orders but not others'
check: order.user_id == requesting_user.id
```

### Security in HLD — What to Cover

**Network boundaries:**
```
Public internet → Load Balancer / WAF (Web Application Firewall)
  → API Gateway (auth enforcement)
    → Internal services (no direct internet access)
      → Databases (no public exposure, VPC only)
```

**Data in transit:** TLS everywhere — client to LB, LB to services, service to service, service to DB.

**Data at rest:** Encrypt sensitive data (PII, payment info) at the storage layer. Use managed encryption (AWS KMS, GCP KMS) rather than rolling your own.

**Secrets management:** No hardcoded credentials. Use Vault, AWS Secrets Manager, or GCP Secret Manager. Rotate secrets automatically.

**PII handling:**
- Minimize collection (don't store what you don't need)
- Mask in logs (never log passwords, card numbers, SSNs)
- Isolate in dedicated services (don't spread PII across all services)
- Implement right-to-deletion (GDPR)

**API security:**
- Rate limiting (prevent abuse)
- Input validation (prevent injection)
- Output encoding (prevent XSS)
- CORS policy (prevent cross-origin misuse)

## Cost Awareness

### Why Cost Belongs in HLD

Architecture decisions have direct cost implications. A solution that works technically but is 10× more expensive than necessary is a bad solution.

Senior engineers think about cost as a constraint, not an afterthought.

### Cost Dimensions

| Component | Cost Driver | Optimization |
|---|---|---|
| Compute | Instance hours, CPU utilization | Right-size instances, autoscale down |
| Storage | GB stored per month | Tiered storage (hot → warm → cold → archive) |
| Network | Egress bandwidth | CDN for static, keep data close to compute |
| Database | Instance size + I/O + backup storage | Read replicas only if needed, use caching |
| Managed services | Per-request or per-GB fees | Batch where possible, cache aggressively |

### Storage Tiering

Not all data is accessed equally. Move infrequently accessed data to cheaper storage:

```
Hot   (SSD, Redis)         → active last 30 days      → most expensive
Warm  (HDD, S3 Standard)   → last 6 months            → moderate cost
Cold  (S3-IA, Glacier)     → last 2 years             → cheap
Archive (Glacier Deep)     → compliance, > 2 years    → very cheap
```

A naive "keep everything in primary DB" design can cost 100× more than a tiered design.

### Cost vs Performance Tradeoffs

Common tensions:
- **More replicas** → higher availability, higher cost
- **More cache** → lower latency, higher memory cost
- **Multi-region** → lower global latency, 2–3× infrastructure cost
- **Managed services** → less ops burden, higher per-unit cost
- **Larger instances** → simpler architecture, more cost

In HLD, call these out: "We could add a second Redis replica for availability, but given the cost and the fact that Redis can be rebuilt from the DB in minutes, I'd start without it."

### Build vs Buy

When should you use a managed service vs self-host?

**Use managed (buy):**
- The operational burden of self-hosting is high
- The service is not a core differentiator
- The managed service cost is justified by the engineering time saved

**Self-host (build):**
- Managed service cost is prohibitive at your scale
- You need customization that managed services don't support
- The component is a core differentiator (your own search engine, your own ML infra)
