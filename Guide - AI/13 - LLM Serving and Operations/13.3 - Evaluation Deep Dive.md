# Evaluation Deep Dive

## What It Is

Evaluation is the discipline of systematically measuring whether your AI system does what it's supposed to do — and detecting when it stops doing so. It spans four interconnected concerns:

1. **Metric design** — what signals actually capture quality (RAGAS and beyond)
2. **LLM-as-judge** — using LLMs to score LLM outputs, and calibrating those judges
3. **Dataset engineering** — building golden sets, synthetic data, and adversarial probes
4. **Regression infrastructure** — running evals continuously, detecting degradations, A/B testing changes

Most teams do evaluation badly — they run it once before launch and never again, or they use metrics that don't correlate with real quality. This file covers what production evaluation actually looks like at companies that do it well.

---

## Why It Matters

- A RAG system with 70% retrieval recall *cannot* answer 30% of questions correctly no matter how good the LLM is. You need to measure retrieval quality separately to know this.
- Prompt changes that "feel better" often regress on specific query types. Without a regression suite, you ship degradations.
- LLM-as-judge is your primary automated quality signal — but uncalibrated judges introduce systematic bias. A judge that rates its own model's outputs higher than competitors is worthless for cross-model comparison.
- For your target companies: Vellum, Langfuse, Arize, and Helicone are all fundamentally evaluation infrastructure companies. Being able to discuss RAGAS internals, judge calibration, and regression suite design at implementation depth is a strong interview signal.

## RAGAS — Internals

RAGAS (Retrieval Augmented Generation Assessment) defines component-specific metrics for RAG evaluation. Understanding what each metric *actually computes* — not just the name — is what matters.

### Faithfulness

**What it measures**: What fraction of claims in the generated answer are supported by the retrieved context?

**Internal computation**:

```
Step 1: Decompose answer into atomic statements
  LLM prompt: "Break this answer into a list of atomic factual statements.
               Each statement should be independently verifiable.
               Answer: {answer}"
  Output: ["Apple's revenue was $85.8B", "Revenue grew 12% YoY", "iPhone drove growth"]

Step 2: For each statement, check if it can be inferred from context
  LLM prompt: "Consider the following context and statement.
               Is the statement directly supported by the context?
               Context: {context}
               Statement: {statement}
               Answer YES or NO."

Step 3: Faithfulness = supported_statements / total_statements
```

**What it catches**: Hallucination — model adding facts not in context.
**What it misses**: Model ignoring relevant context (that's answer relevance or recall).

```python
from ragas.metrics import faithfulness
from ragas import evaluate
from datasets import Dataset

# RAGAS expects this exact schema
data = {
    "question": ["What was Apple's Q3 revenue?"],
    "answer": ["Apple's Q3 2024 revenue was $85.8B, up 12% year-over-year."],
    "contexts": [["Apple reported net sales of $85.8 billion for Q3 2024, an increase of 5%..."]],  # retrieved chunks
    "ground_truth": ["$85.8 billion"],  # optional, needed for answer_correctness
}
dataset = Dataset.from_dict(data)

result = evaluate(dataset, metrics=[faithfulness])
print(result["faithfulness"])  # float 0-1
```

**Production gotcha**: The decomposition step is itself an LLM call. Faithfulness is therefore sensitive to the *judge model's* ability to decompose and verify. Test your faithfulness scores against human labels before trusting them.

### Answer Relevance

**What it measures**: Does the answer actually address the question asked?

**Internal computation**:

```
Step 1: Generate N questions that the answer would address
  LLM prompt: "Generate {n} questions for which the following would be a good answer.
               Answer: {answer}"
  Output: ["What was Apple's Q3 revenue?", "How much did Apple earn in Q3 2024?"]

Step 2: Embed original question and generated questions
Step 3: Answer Relevance = mean cosine_similarity(original_question, generated_questions_i)
```

**Insight**: If the answer is off-topic (answering a different question), the reverse-engineered questions won't match the original. If the answer is a non-answer ("I don't know"), the generated questions will be vague and won't match well.

**What it catches**: Irrelevant, tangential, or evasive answers.
**What it misses**: Factual correctness (answer can be relevant but wrong).

### Context Recall

**What it measures**: Was the information needed to answer the question actually present in retrieved context? (Requires ground truth)

**Internal computation**:

```
Step 1: Decompose ground truth answer into statements
  ["Revenue was $85.8B", "Growth was 12% YoY"]

Step 2: For each statement, check if it can be attributed to retrieved context
  → If found in context: attributed
  → If not found: missing from retrieval

Step 3: Context Recall = attributed_statements / total_statements
```

This measures retrieval quality — did you retrieve the right documents? Low context recall means your retrieval pipeline is failing, not your LLM.

### Context Precision

**What it measures**: Of what was retrieved, how much was actually useful?

**Internal computation**:

```
For each retrieved chunk (in order):
  Is this chunk relevant to answering the question?
  → Marked relevant or irrelevant

Context Precision = weighted_sum(relevant_at_rank_k * (relevant_up_to_rank_k / k))
                    / total_relevant_chunks
```

This is a precision-at-K metric with position weighting — relevant chunks ranked higher contribute more. Low context precision means you're retrieving noise.

### Answer Correctness

**What it measures**: Is the factual content of the answer correct, compared to ground truth?

**Internal computation**: Combines semantic similarity (embedding cosine) and factual overlap (F1 of atomic facts). Requires ground_truth annotation.

```python
from ragas.metrics import answer_correctness
# Needs "ground_truth" column in dataset
```

### RAGAS Metric Selection Guide

```
Building RAG system, no ground truth labels yet?
  → faithfulness, answer_relevance, context_precision (all reference-free)

Have a golden dataset with correct answers?
  → Add: context_recall, answer_correctness

Want to isolate retrieval failures?
  → Focus on: context_recall (retrieval found what was needed?)
              context_precision (retrieved results are signal, not noise?)

Want to isolate generation failures?
  → Focus on: faithfulness (model stayed grounded?)
              answer_relevance (model answered the question?)
```

## LLM-as-Judge — Calibration

Using a strong LLM to score outputs is powerful but introduces systematic biases that must be understood and mitigated.

### Known Biases

**Verbosity bias**: Judges prefer longer, more elaborate responses even when a short answer is correct and complete.

```
Answer A: "Paris"
Answer B: "The capital of France is Paris, a vibrant city known for the Eiffel Tower..."
Judge often rates B higher despite A being perfectly correct.
```

**Position bias**: In pairwise comparisons, judges prefer the response shown first.

```
Comparison: (Response A, Response B) → judge picks A 60% of time
Comparison: (Response B, Response A) → judge picks B 60% of time
Both preferences driven by position, not quality.
```

**Self-enhancement bias**: Models rate outputs from their own family higher.
OpenAI models tend to prefer OpenAI model outputs. Anthropic models show similar effects.

**Sycophancy**: Judges agree with assertions in the prompt. If you say "Is the following excellent?", they'll say yes.

### Calibration Techniques

**1. Position randomization** (for pairwise comparisons)

```python
import random

def calibrated_pairwise_judge(question, response_a, response_b, judge_llm):
    # Randomize order to cancel position bias
    if random.random() < 0.5:
        order = ("a", response_a, "b", response_b)
    else:
        order = ("b", response_b, "a", response_a)

    label1, resp1, label2, resp2 = order

    prompt = f"""Which response better answers the question?

Question: {question}
Response {label1}: {resp1}
Response {label2}: {resp2}

Output only the label of the better response ({label1} or {label2})."""

    winner_label = judge_llm.call(prompt, temperature=0).strip()
    # Map back to actual response
    return "a" if winner_label == "a" else "b"
```

**2. Multi-judge consensus** (reduces variance, catches model-specific bias)

```python
def multi_judge_score(question, answer, context, judges):
    scores = []
    for judge in judges:
        score = judge.score_faithfulness(question, answer, context)
        scores.append(score)

    # Disagreement > 0.3 → flag for human review
    if max(scores) - min(scores) > 0.3:
        return None, "HIGH_DISAGREEMENT"

    return sum(scores) / len(scores), "CONSENSUS"

judges = [
    OpenAIJudge("gpt-4o"),
    AnthropicJudge("claude-opus-4-5"),
    # Using models from different families cancels self-enhancement bias
]
```

**3. Reference anchoring** (reduces verbosity and other positional effects)

```python
ANCHORED_JUDGE_PROMPT = """Score this response on a 1-5 scale.

Scoring rubric:
1 = Completely wrong or hallucinated
2 = Partially correct but missing key information
3 = Correct but contains irrelevant content
4 = Correct and concise
5 = Correct, concise, and cites source

A score of 4 means: "{example_4_star_response}"
A score of 2 means: "{example_2_star_response}"

Question: {question}
Response: {response}
Context: {context}

Score (1-5) and one-sentence justification:"""
```

Providing concrete examples anchors the judge's scale. Without anchors, "4" means different things each call.

**4. Calibration against human labels**

```python
def calibrate_judge(judge, human_labeled_set):
    """Measure judge agreement with human labels."""
    agreements = []
    for example in human_labeled_set:
        judge_score = judge.score(example)
        human_score = example["human_label"]

        # Normalize to binary: >= 4 is "good"
        agreements.append(
            int(judge_score >= 4) == int(human_score >= 4)
        )

    accuracy = sum(agreements) / len(agreements)
    print(f"Judge accuracy vs humans: {accuracy:.1%}")
    # Target: > 80% agreement for primary metric
    # < 70% → judge is unreliable, find a better model or prompt
    return accuracy
```

Run this calibration quarterly or after major model updates.

## Golden Dataset Engineering

### What a Golden Dataset Is

A golden dataset is a curated collection of (input, expected_output, metadata) examples that represent the real distribution of your system's usage. It is the ground truth against which all automated evaluation runs.

```python
# Golden set example schema
golden_example = {
    "id": "gs_001",
    "question": "What was Apple's free cash flow in Q3 2024?",
    "expected_answer": "$29.0 billion",           # what the correct answer is
    "relevant_doc_ids": ["aapl_q3_2024_10q"],     # which docs should be retrieved
    "difficulty": "medium",                        # easy | medium | hard
    "category": "financial_metric",               # for per-category analysis
    "adversarial": False,                         # is this a trick question?
    "created_at": "2024-01-15",
    "created_by": "human",
}
```

### Synthetic Generation for Scale

Manual annotation is expensive — use LLMs to generate synthetic examples, then filter:

```python
SYNTHETIC_QA_PROMPT = """Given this document chunk, generate 3 question-answer pairs.

Rules:
- Questions must be answerable from the chunk alone
- Include 1 easy (direct lookup), 1 medium (requires inference), 1 hard (requires synthesis)
- Hard questions should require combining 2+ pieces of information
- Do NOT generate questions about things not in the chunk

Chunk:
{chunk_text}

Output JSON array:
[{{"question": "...", "answer": "...", "difficulty": "easy|medium|hard"}}]"""

def generate_synthetic_golden_set(chunks, llm, filter_llm=None):
    synthetic = []
    for chunk in chunks:
        examples = json.loads(llm.call(SYNTHETIC_QA_PROMPT.format(chunk_text=chunk.text)))
        for ex in examples:
            ex["relevant_doc_ids"] = [chunk.document_id]
            ex["created_by"] = "synthetic"
            synthetic.append(ex)

    # Filter: remove examples that require knowledge outside the chunk
    if filter_llm:
        synthetic = [e for e in synthetic if verify_answerable(e, chunk, filter_llm)]

    return synthetic
```

**Quality gate for synthetic examples**: Use a second LLM pass to verify that the generated question is actually answerable from the cited chunk. Synthetic data that requires outside knowledge introduces noise.

## Regression Suite Infrastructure

A regression suite is an automated eval run that gates deployments and detects quality degradation over time.

### Architecture

```
Code / prompt / model change
    │
    ▼
CI/CD pipeline triggers eval
    │
    ▼
Run golden set through current system
    │
    ▼
Score each example (automated metrics + LLM judge)
    │
    ▼
Compare to baseline (previous deployment)
    │
    ├── All metrics within threshold? → PASS → allow deployment
    └── Any metric regressed beyond threshold? → FAIL → block deployment
                                                        + alert on-call
```

### Threshold Configuration

```python
REGRESSION_THRESHOLDS = {
    # Absolute minimums — hard floor
    "faithfulness":         {"min": 0.80, "max_drop": 0.05},
    "answer_relevance":     {"min": 0.75, "max_drop": 0.05},
    "context_recall":       {"min": 0.80, "max_drop": 0.05},

    # Retrieval-specific
    "recall_at_10":         {"min": 0.85, "max_drop": 0.03},
    "mrr_at_10":            {"min": 0.70, "max_drop": 0.05},

    # Performance
    "p95_latency_ms":       {"max": 3000, "max_increase": 500},
    "avg_cost_per_query":   {"max": 0.02, "max_increase": 0.005},

    # Per-category — check specific categories don't regress
    "faithfulness_financial":   {"min": 0.85},  # higher bar for financial
    "faithfulness_unanswerable": {"min": 0.90},  # must say "I don't know"
}

def check_regression(current_scores, baseline_scores, thresholds):
    failures = []
    for metric, rules in thresholds.items():
        current = current_scores.get(metric)
        baseline = baseline_scores.get(metric)
        if current is None:
            continue

        # Absolute minimum
        if "min" in rules and current < rules["min"]:
            failures.append(f"{metric}: {current:.3f} below minimum {rules['min']}")

        # Max drop from baseline
        if "max_drop" in rules and baseline:
            drop = baseline - current
            if drop > rules["max_drop"]:
                failures.append(f"{metric}: dropped {drop:.3f} from {baseline:.3f} → {current:.3f}")

    return failures
```

### Per-Category Analysis

Don't just track averages — a system that improves on easy questions while breaking on hard ones has average improvement but real regression:

```python
def analyze_by_category(results):
    """Break down eval results by difficulty, category, and adversarial type."""
    from collections import defaultdict
    import statistics

    category_scores = defaultdict(list)
    for result in results:
        category = result["example"]["category"]
        difficulty = result["example"]["difficulty"]
        adversarial = result["example"]["adversarial"]

        category_scores[f"cat_{category}"].append(result["faithfulness"])
        category_scores[f"diff_{difficulty}"].append(result["faithfulness"])
        if adversarial:
            category_scores["adversarial"].append(result["faithfulness"])

    report = {}
    for key, scores in category_scores.items():
        report[key] = {
            "mean": statistics.mean(scores),
            "p10": sorted(scores)[int(0.1 * len(scores))],
            "count": len(scores),
        }

    return report
```

## A/B Testing Prompt and Model Changes

### The Setup

```python
class PromptExperiment:
    def __init__(self, experiment_id, control_version, treatment_version, traffic_pct=0.10):
        self.id = experiment_id
        self.control = control_version      # e.g., "rag_prompt/v2"
        self.treatment = treatment_version  # e.g., "rag_prompt/v3"
        self.traffic_pct = traffic_pct      # 10% to treatment

    def assign(self, user_id: str) -> tuple[str, str]:
        """Deterministic assignment — same user always gets same variant."""
        bucket = int(hashlib.md5(f"{self.id}:{user_id}".encode()).hexdigest(), 16) % 100
        if bucket < self.traffic_pct * 100:
            return "treatment", self.treatment
        return "control", self.control
```

### Statistical Significance

Never declare an A/B winner without statistical significance:

```python
from scipy import stats

def analyze_ab_result(control_scores, treatment_scores, alpha=0.05):
    """
    Determine if treatment is significantly better/worse than control.
    Uses two-sample t-test for continuous metrics (faithfulness, etc.)
    """
    t_stat, p_value = stats.ttest_ind(control_scores, treatment_scores)
    significant = p_value < alpha

    control_mean = sum(control_scores) / len(control_scores)
    treatment_mean = sum(treatment_scores) / len(treatment_scores)
    relative_change = (treatment_mean - control_mean) / control_mean

    # Minimum detectable effect: don't declare winner if change is too small
    MIN_MEANINGFUL_CHANGE = 0.02  # 2 percentage points
    meaningful = abs(relative_change) >= MIN_MEANINGFUL_CHANGE

    return {
        "control_mean": control_mean,
        "treatment_mean": treatment_mean,
        "relative_change": f"{relative_change:+.1%}",
        "p_value": p_value,
        "significant": significant,
        "meaningful": meaningful,
        "conclusion": (
            "SHIP" if significant and meaningful and relative_change > 0 else
            "REVERT" if significant and meaningful and relative_change < 0 else
            "INCONCLUSIVE"
        ),
        "required_sample": required_sample_size(control_mean, MIN_MEANINGFUL_CHANGE),
    }

def required_sample_size(baseline_rate, min_effect, alpha=0.05, power=0.80):
    """How many samples needed to detect a given effect size?"""
    from statsmodels.stats.power import TTestIndPower
    analysis = TTestIndPower()
    effect_size = min_effect / (baseline_rate * (1 - baseline_rate)) ** 0.5
    return int(analysis.solve_power(effect_size=effect_size, alpha=alpha, power=power))
```

**Common mistake**: Declaring a winner after 50 samples. At typical quality metric variance, you need 200–500 samples per variant to detect a 5% improvement with 80% power.

### Shadow Evaluation

Run a new model/prompt in shadow mode — execute it for real traffic but don't serve its responses to users:

```python
async def shadow_eval_query(question, user_id, production_config, shadow_config):
    # Execute both in parallel
    prod_future = asyncio.create_task(
        rag_pipeline(question, user_id, config=production_config)
    )
    shadow_future = asyncio.create_task(
        rag_pipeline(question, user_id, config=shadow_config)
    )

    prod_result, shadow_result = await asyncio.gather(prod_future, shadow_future)

    # Log shadow result for offline evaluation — don't serve it
    log_shadow_evaluation(
        user_id=user_id,
        question=question,
        production_answer=prod_result,
        shadow_answer=shadow_result,
        shadow_config=shadow_config,
    )

    # Serve only production result
    return prod_result
```

Shadow evaluation lets you accumulate a large sample of real-query comparisons before doing a live A/B test, reducing the time users are exposed to potentially worse performance.

## Eval Pipeline Implementation

A minimal but complete eval pipeline:

```python
import asyncio
from dataclasses import dataclass

@dataclass
class EvalResult:
    example_id: str
    faithfulness: float
    answer_relevance: float
    context_recall: float
    retrieval_recall_at_10: bool
    latency_ms: float
    cost_usd: float
    answer: str
    retrieved_chunks: list

async def run_eval_example(example, rag_system, judge):
    start = time.perf_counter()
    chunks, answer = await rag_system.query(example["question"])
    latency = (time.perf_counter() - start) * 1000

    faithfulness = await judge.score_faithfulness(answer, chunks)
    relevance = await judge.score_relevance(example["question"], answer)
    recall = any(c.doc_id in example["relevant_doc_ids"] for c in chunks[:10])

    return EvalResult(
        example_id=example["id"],
        faithfulness=faithfulness,
        answer_relevance=relevance,
        context_recall=await judge.score_context_recall(example, chunks),
        retrieval_recall_at_10=recall,
        latency_ms=latency,
        cost_usd=estimate_cost(answer, chunks),
        answer=answer,
        retrieved_chunks=chunks,
    )

async def run_full_eval(golden_set, rag_system, judge, concurrency=10):
    semaphore = asyncio.Semaphore(concurrency)

    async def limited(example):
        async with semaphore:
            return await run_eval_example(example, rag_system, judge)

    results = await asyncio.gather(*[limited(ex) for ex in golden_set])

    # Aggregate
    return {
        "faithfulness":           sum(r.faithfulness for r in results) / len(results),
        "answer_relevance":       sum(r.answer_relevance for r in results) / len(results),
        "retrieval_recall_at_10": sum(r.retrieval_recall_at_10 for r in results) / len(results),
        "p95_latency_ms":         sorted(r.latency_ms for r in results)[int(0.95 * len(results))],
        "total_cost_usd":         sum(r.cost_usd for r in results),
        "per_example":            results,
    }
```

## Revision Anchors

- **RAGAS faithfulness**: Decompose answer → atomic statements → verify each against context. Faithfulness = supported/total. Measures hallucination.
- **RAGAS answer relevance**: Generate N questions from answer → embed → cosine with original question. Measures whether answer addresses the question.
- **Context recall vs precision**: Recall = did you retrieve what was needed? Precision = was what you retrieved useful? Low recall = retrieval failure. Low precision = retrieval noise.
- **LLM judge biases**: Verbosity (longer = better), position (first = better), self-enhancement (own model = better). Calibrate: position-randomize, use multi-judge consensus, anchor with examples, validate against human labels.
- **Golden set stratification**: 30% easy, 50% medium, 20% hard. 80% answerable, 20% unanswerable. 10-15% adversarial. Audit coverage explicitly.
- **A/B significance**: Need 200–500 samples per variant at typical metric variance to detect 5% improvement. Don't declare winners early.
- **Shadow eval**: Run new config on real traffic, log results, don't serve — accumulate samples safely before live test.
