# Spread vs Rest

Same three dots, opposite jobs. The distinguishing question is which side of the assignment (or which part of a call) they appear in.

- **Spread** — expands an iterable or object into individual elements. Appears where values are *consumed*.
- **Rest** — collects remaining elements into one binding. Appears where values are *declared*.

```js
const merged = [...a, ...b];              // spread — expanding
const [first, ...others] = arr;           // rest — collecting
function f(...args) {}                    // rest — collecting
f(...args);                               // spread — expanding
```

## Spread with arrays

```js
const copy = [...arr];                    // shallow copy
const merged = [...a, ...b];
const inserted = [...a.slice(0, 2), "x", ...a.slice(2)];
const fromString = [..."abc"];            // ["a", "b", "c"]
const fromSet = [...new Set(arr)];        // dedupe
const fromNodeList = [...document.querySelectorAll("li")];
const max = Math.max(...numbers);
```

Array spread works on **any iterable** ([[06.6 - Iterators and Generators]]), which is why it converts `Set`, `Map`, `NodeList`, strings and generators uniformly.

Two limits worth knowing. Spreading into a function call is subject to the engine's argument-count cap — roughly 65k to 125k — so `Math.max(...millionItems)` throws a `RangeError`. And spread in a loop is quadratic:

```js
// O(n²) — allocates a new array every iteration
let result = [];
for (const item of items) result = [...result, item];

// O(n)
const result = [];
for (const item of items) result.push(item);
```

The same applies to `reduce((acc, x) => [...acc, x], [])`, which looks functional and is a performance trap on large inputs.

## Spread with objects

```js
const copy = { ...obj };
const merged = { ...defaults, ...overrides };     // later wins
const withExtra = { ...obj, id: 1 };
const overridden = { id: 1, ...obj };             // obj.id wins
```

Object spread copies **own enumerable** properties, including symbol keys. It does not copy the prototype, non-enumerable properties, or property descriptors — getters are invoked and their values copied ([[03.1 - Objects and Property Descriptors]]).

Order matters, and it is the mechanism for both defaults and overrides:

```js
function Button({ variant = "primary", ...rest }) {
  return <button className={styles[variant]} {...rest} />;
}
```

Spreading `rest` onto the DOM element forwards `onClick`, `aria-label`, `data-*` and anything else without enumerating them. This is the standard escape hatch in component library design ([[28.3 - Component Design and API Design]]).

Object spread differs from `Object.assign` in one meaningful way: spread *defines* properties on a fresh object, while `Object.assign` *assigns* to the target — so `Object.assign` triggers setters and spread does not.

Spreading a non-object is safe and produces nothing useful:

```js
{ ...null }      // {}
{ ...undefined } // {}
{ ..."ab" }      // { 0: "a", 1: "b" }
{ ...[1, 2] }    // { 0: 1, 1: 2 }
```

That `null`/`undefined` tolerance makes conditional spread work:

```js
const payload = {
  name,
  ...(includeEmail && { email }),   // false spreads to nothing
  ...(extras ?? {}),
};
```

## Rest in parameters

```js
function sum(...nums) {
  return nums.reduce((a, b) => a + b, 0);
}

function log(level, ...messages) {}  // must be last
```

Rest parameters are a real array, unlike `arguments`, and they work in arrow functions. `arguments` should be considered obsolete.

Note that rest parameters do not count toward `fn.length`, which matters for currying implementations that use arity ([[02.9 - Currying and Partial Application]]).

## Rest in destructuring

```js
const [first, ...others] = arr;
const { id, ...withoutId } = obj;
```

Object rest is the idiomatic way to omit a key immutably:

```js
const { password, ...safeUser } = user;
```

Both must be last in the pattern; `const [...rest, last] = arr` is a `SyntaxError` because there is no way to know where the rest ends.

## Everything spread copies is shallow

```js
const state = { user: { name: "a" }, tags: ["x"] };
const copy = { ...state };

copy.user.name = "b";
state.user.name;  // "b" — same nested object
```

This is the root of the React immutability rules ([[03.5 - Shallow vs Deep Copy]]). Every level you intend to change needs its own spread:

```js
setState(s => ({
  ...s,
  user: { ...s.user, name: "b" },
}));
```

## How senior engineers actually use this

**They spread props at the end** in component wrappers so callers can override defaults, and at the beginning when the component's own values must win. Getting the order wrong is a subtle bug in design systems — `{...rest}` before `className` silently drops the caller's class.

**They avoid spread inside loops and reducers** on anything that could be large. The quadratic behavior is invisible in development with ten items and painful in production with ten thousand.

**They use conditional spread for optional payload fields** rather than building an object and deleting keys, because `delete` deoptimizes the object shape ([[01.1 - How JavaScript Runs]]).

**They rely on `{...obj}` producing a new reference** for React state updates, and equally, they know a spread of an unchanged object still breaks referential equality — so spreading state that did not change causes unnecessary re-renders ([[19.1 - What Causes Re-renders]]).

## Common pitfalls

- Assuming spread is a deep copy.
- Spreading a class instance and losing its prototype methods.
- `[...arr]` inside a reduce or loop, producing O(n²) behavior.
- Getting `{...defaults, ...props}` order backwards.
- `Math.max(...hugeArray)` exceeding the argument limit.
- Forgetting rest must be the last element in a destructuring pattern.
- Spreading an object with getters and freezing their current values.

## Interview angle

"Difference between spread and rest" is a quick one: same syntax, spread expands where values are consumed, rest collects where they are declared. Follow with the practical points — spread is shallow, object spread copies own enumerable properties only, and spreading in a loop is quadratic. The last one is the detail that reads as production experience rather than syntax familiarity.
