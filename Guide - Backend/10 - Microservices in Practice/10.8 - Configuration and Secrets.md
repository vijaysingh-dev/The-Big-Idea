# Configuration and Secrets

#backend #microservices #operations #security

> **In one line:** Configuration that varies by environment belongs outside the image, secrets belong somewhere auditable and rotatable, and the thing that determines whether either is safe is what happens when a value is wrong.

---

## The Idea

```
Code        the same in every environment
Config      differs by environment      → environment variables, config maps
Secrets     differs, and must not leak  → a secret manager
```

💡 **The twelve-factor rule: config is anything that varies between deploys of the same code.** Database URLs, feature flags, external endpoints, log levels.

⚠️ **The corollary people miss: if it does not vary between environments, it is not config — it is code.** A "configurable" timeout that is 30 seconds everywhere is a constant with extra indirection and an extra failure mode.

---

## Configuration

### Typed, validated, at startup

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: PostgresDsn
    redis_url: RedisDsn
    kafka_brokers: list[str]

    request_timeout_seconds: float = 10.0
    max_document_size_mb: int = 100
    log_level: Literal["debug", "info", "warning", "error"] = "info"

    model_config = SettingsConfigDict(env_prefix="CONDUIT_", frozen=True)


settings = Settings()      # ← raises immediately if anything is missing or malformed
```

💡 **Fail at startup, not at first use.** A missing `DATABASE_URL` should crash the process on line one, not produce a `NoneType` error at 3am when a rarely-used code path runs.

⚠️ **`frozen=True` matters more than it looks.** Configuration mutated at runtime is a category of bug that is very hard to reproduce, because the value differs between processes and between requests.

### The startup assertion

```python
def validate_startup(s: Settings) -> None:
    assert s.request_timeout_seconds < s.gateway_timeout_seconds, \
        "request timeout must be inside the gateway budget"
    assert s.pool_size * s.worker_count <= s.db_max_connections, \
        f"pool arithmetic: {s.pool_size} × {s.worker_count} > {s.db_max_connections}"
```

💡 **Assertions about relationships between values catch the errors that per-field validation cannot** ([[01.10 - Connection Pools and Limits]]). The pool arithmetic assertion alone prevents one of the most common production incidents.

**Run these in CI against every environment's configuration**, not just at startup.

### Where it comes from

| Source | For |
|---|---|
| **Environment variables** | The default. Twelve-factor, universally supported |
| **ConfigMap** | Kubernetes-native, mounted as env or files |
| Config file in the image | ⚠️ Only for values that never vary |
| **Remote config service** | Feature flags, dynamic values |
| Command-line flags | CLI tools, not services |

⚠️ **Do not build a config file hierarchy with environment overrides.** `base.yaml` + `production.yaml` + `production.eu.yaml` + environment variables produces a value nobody can trace to a source.

💡 **One layer of environment variables, one typed schema, one validation step.** When someone asks "why is the timeout 8 seconds", the answer should be one lookup.

## Secrets

⚠️ **A secret in an environment variable is visible in `/proc/<pid>/environ`, in `docker inspect`, in crash dumps, and in any log line that dumps the environment.**

```python
log.info("starting", extra={"config": settings.model_dump()})   # ⚠️ leaks everything
```

```python
class Settings(BaseSettings):
    database_url: PostgresDsn
    api_key: SecretStr                    # ← repr() is '**********'

log.info("starting", extra={"config": settings.model_dump()})
# api_key: SecretStr('**********')
```

💡 **`SecretStr` makes accidental logging fail safe**, and it costs one type annotation.

### Where secrets live

| Option | |
|---|---|
| **Environment variables** | Simple, and visible in several places |
| **Kubernetes Secrets** | ⚠️ Base64, not encrypted, unless encryption at rest is enabled |
| **Mounted files** | Better than env — not in `/proc/environ`, and can be rotated in place |
| **Secret manager** (Vault, AWS Secrets Manager) | **Auditable, rotatable, dynamic** |
| **Workload identity** | **No secret at all** — the best option |

⚠️ **Kubernetes Secrets are base64-encoded, not encrypted, by default.** Anyone with `get secrets` in the namespace can read them, and they are stored in etcd in plaintext unless encryption at rest is configured.

```yaml
# Enable etcd encryption at rest
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - aescbc: {keys: [{name: key1, secret: <base64>}]}
```

💡 **Verify this is on before treating Kubernetes Secrets as a secret store.** Many clusters do not have it.

### The best secret is no secret

```python
# ❌ A static database password
DATABASE_URL = "postgresql://app:hunter2@db:5432/conduit"

# ✅ Workload identity — the platform proves who you are
credentials = await google.auth.default()
# or IRSA on AWS, or Managed Identity on Azure
```

💡 **Workload identity eliminates the secret entirely.** The platform issues a short-lived token based on the pod's service account, and there is nothing to rotate, leak or store.

**Where it is available, it is strictly better than any secret manager.**

⚠️ **It does not cover third-party credentials** — a Stripe key or an OpenAI key still has to come from somewhere.

### Dynamic secrets

```python
# Vault issues a database credential valid for one hour
creds = await vault.read("database/creds/app")
# username: v-app-x7k2..., password: ..., lease_duration: 3600
```

💡 **A credential that expires in an hour has a bounded blast radius if leaked**, and rotation is automatic rather than a project.

⚠️ **Your connection pool must handle credential expiry** — reconnect with fresh credentials before the lease ends, and handle the case where a pooled connection's credentials were revoked ([[01.10 - Connection Pools and Limits]]).

## Rotation

⚠️ **A secret that has never been rotated cannot be rotated**, because nobody knows what depends on it and the procedure has never been tested.

### Dual-secret rotation

```python
# Accept both during the rotation window
def verify_signature(payload: bytes, signature: str) -> bool:
    return any(
        hmac.compare_digest(sign(payload, secret), signature)
        for secret in (settings.webhook_secret_current, settings.webhook_secret_previous)
    )
```

```
1. Add the new secret as `previous` alongside `current`   → deploy
2. Swap: new becomes `current`, old becomes `previous`    → deploy
3. Remove `previous`                                       → deploy
```

💡 **Three deploys, zero downtime**, and it is expand/contract applied to secrets ([[06.11 - Zero Downtime Migrations]]).

**Design every secret-consuming code path to accept two values from the start.** Retrofitting it during an incident is much harder.

### What forces a rotation

| Trigger | |
|---|---|
| Scheduled policy | Every 90 days, typically |
| **An employee leaves** | Anything they could have read |
| **A leak** | A key in a git commit, a log, a screenshot |
| Compliance | |

⚠️ **A key committed to git is compromised even after you delete the commit**, because the git history and every clone still contain it. **Rotate, do not just remove.**

```bash
# Prevent it: pre-commit secret scanning
gitleaks protect --staged
```

💡 **Secret scanning in pre-commit and in CI catches the majority of leaks before they happen**, and it costs nothing to install.

## Feature Flags

Configuration that changes without a deploy.

```python
if await flags.enabled("new_indexing_pipeline", org_id=org.id):
    return await new_pipeline(doc)
return await old_pipeline(doc)
```

| Use | |
|---|---|
| **Decouple deploy from release** | Ship dark, enable later |
| **Gradual rollout** | 1% → 10% → 100% |
| **Kill switch** | Disable a broken feature without a deploy |
| Per-tenant enablement | Beta features for specific customers |

💡 **The kill switch is the most valuable use.** A feature that can be disabled by flipping a flag turns a rollback into a thirty-second config change.

⚠️ **Flags accumulate and become permanent.** A codebase with 200 flags has 2²⁰⁰ possible configurations and nobody knows which are tested.

```python
@flag("new_indexing_pipeline", remove_by=date(2026, 10, 1))
```

**Give every flag an expiry and fail the build when it passes.** This is the discipline that stops flags from becoming permanent branching.

### Flags are configuration, and they must fail safe

```python
async def enabled(name: str, **ctx) -> bool:
    try:
        return await flag_service.evaluate(name, ctx)
    except Exception:
        flag_evaluation_errors.inc()
        return DEFAULTS[name]                     # ← a known default, never a crash
```

⚠️ **A flag service outage must not take down your application.** Cache aggressively, default explicitly, and never let flag evaluation raise.

## In Production

### Configuration per environment

```
CONDUIT_DATABASE_URL          differs
CONDUIT_LOG_LEVEL             debug / info
CONDUIT_REQUEST_TIMEOUT       10.0 everywhere      ← should be a constant
CONDUIT_MAX_DOCUMENT_SIZE_MB  100 everywhere       ← should be a constant
```

💡 **Audit your configuration for values that are identical everywhere.** Each one is a constant that has been given an environment variable, an extra failure mode, and a place to be wrong.

⚠️ **The opposite failure is a value that should differ and does not** — a production database URL in a staging config, or a test API key in production. **A startup assertion checking the environment name against the URL catches it.**

```python
if s.environment == "production":
    assert "staging" not in str(s.database_url), "staging database in production"
```

### Configuration drift

```
Pod A: CONDUIT_TIMEOUT=10
Pod B: CONDUIT_TIMEOUT=30      ← from a ConfigMap updated after A started
```

⚠️ **A ConfigMap change does not restart pods.** Mounted-file ConfigMaps update in place (eventually); environment variables do not update at all.

💡 **Use a checksum annotation to force a rollout on config change:**

```yaml
metadata:
  annotations:
    checksum/config: "{{ sha256sum (toJson .Values.config) }}"
```

**Every configuration change becomes a rolling deploy**, which means every pod has the same values — and it means a bad config is caught by your rollout health checks.

### Auditing what is deployed

```python
@app.get("/debug/config")
async def config(user: AdminUser):
    return settings.model_dump()          # SecretStr masks secrets automatically
```

💡 **An endpoint showing the effective configuration answers "what is this pod actually running with"** in seconds, and it is the first question during a configuration incident.

⚠️ **Restrict it to administrators**, and rely on `SecretStr` rather than manual exclusion — a manually-maintained exclusion list will eventually miss a new field.

### The config checklist

```
□  Typed schema, validated at startup
□  Startup assertions for relationships between values
□  Secrets as SecretStr, never logged
□  No config file hierarchy — one source
□  Values identical everywhere are constants, not config
□  Environment-mismatch assertions (staging URL in production)
□  Config changes force a rollout
□  Secret rotation supports two values simultaneously
□  Secret scanning in pre-commit and CI
□  A debug endpoint showing effective config
□  Every feature flag has an expiry date
□  Flag evaluation fails to a known default
```

### Conduit's configuration

| Value | Source | Notes |
|---|---|---|
| Database URL | Environment | **Workload identity where available** |
| Redis URL | Environment | |
| Kafka brokers | Environment | |
| Object storage credentials | **Workload identity** | No secret |
| Third-party API keys | **Secret manager**, mounted as files | Rotatable, audited |
| Webhook signing secret | Secret manager, **dual-value** | Rotation without downtime |
| Timeouts and limits | Constants in code | Identical everywhere |
| Feature flags | Flag service, cached, with defaults | |

💡 **Note how few things are actually configuration.** Most values a team would reflexively make configurable are the same in every environment, and making them constants removes a failure mode.

⚠️ **The webhook secret is dual-value from day one**, because [[05.12 - Webhooks and Callbacks]] requires rotation and retrofitting it is painful.

## Codebase

**Repo:** `hashicorp/vault`, `external-secrets/external-secrets`, `pydantic/pydantic-settings`

**Question to answer:** How does Vault issue a dynamic database credential, and what happens when the lease expires? Then: how does External Secrets Operator get a secret from a manager into a pod, and what is the refresh behaviour?

**Read, in order:**

1. `pydantic-settings/pydantic_settings/sources/` — **how settings are resolved from environment, files and secrets directories.** Small, and it clarifies precedence
2. `pydantic/pydantic/types.py` — **`SecretStr`.** How `__repr__` and serialisation are overridden. **The mechanism that makes accidental logging safe**
3. `vault/builtin/logical/database/` — **dynamic credential generation and lease revocation.** How a credential is created on demand and revoked at expiry. **The answer to the first question**
4. `external-secrets/pkg/controller/externalsecret/` — **the reconcile loop.** How a secret is fetched, written to a Kubernetes Secret, and refreshed. **The answer to the second question**
5. `external-secrets/pkg/provider/` — how different backends are abstracted, which tells you what portability costs

💡 The Vault lease mechanism is worth understanding even if you use a different tool: **a credential with a TTL that the database will reject after expiry means a leaked credential has a bounded lifetime with no human action required.** That property is what makes dynamic secrets qualitatively better than rotated static ones.

**Size:** 1 session.

**Part 1 — Ten broken configurations.** Write ten realistic misconfigurations: a missing required value, a malformed URL, a timeout larger than the gateway budget, pool arithmetic exceeding `max_connections`, a staging URL in production, a log level typo, an invalid enum, a negative limit, a secret with a trailing newline, and a list parsed as a string.

**For each: does the application fail at startup, at first use, or silently?**

Then add typed validation and startup assertions. **Confirm all ten now fail at startup with a message naming the problem.**

**The trailing-newline one is worth attention** — it is the most common real cause of "the credentials are correct and authentication fails".

**Part 2 — Secret leakage.** A secret in an environment variable.

Find it in: `/proc/<pid>/environ`, `docker inspect`, a crash traceback, a `model_dump()` in a log line, and an error message from a failed connection.

**Five leak paths.** Then use `SecretStr` and a mounted file, and confirm which paths are closed.

**Part 3 — Four secret backends.** The same third-party API key delivered via: environment variable, Kubernetes Secret, mounted file from a secret manager, and workload identity.

Compare: who can read it, is it encrypted at rest, is access audited, how is it rotated, and what happens when the backing store is unavailable.

**The audit column is the one that decides it for most compliance requirements.**

**Part 4 — Rotation with and without downtime.** A webhook signing secret with active senders.

**Single-value:** rotate it and measure how long signatures fail.

**Dual-value:** rotate through the three-deploy sequence and confirm zero failures.

Then rotate a database credential with an active connection pool. **Confirm pooled connections with the old credential fail**, then implement `pool_recycle` shorter than the rotation window and confirm.

**Part 5 — Configuration drift.** Update a ConfigMap consumed as environment variables. **Confirm running pods keep the old values indefinitely.**

Then as a mounted file. **Measure how long until pods see the change**, and confirm your application does not re-read it anyway.

Then add the checksum annotation and confirm every change triggers a rollout.

**Measure the case that matters: a bad config value with and without the forced rollout.** With it, your rollout health checks catch it; without it, half your pods are wrong.

**Part 6 — Flags that fail safe.** A flag service, with a feature gated behind it.

**Take the flag service down.** Confirm the application continues with defaults rather than erroring.

Then make the flag service slow — 5 seconds per evaluation. **Confirm your caching means it does not affect request latency.**

Then implement the expiry check and confirm CI fails on a flag past its date.

**Part 7 — The audit.** Run the twelve-item checklist against Conduit.

**Then audit for values identical in every environment** and convert them to constants. Count how many.

Then write the ADR: what is configuration, what is a secret, what is a constant, and the rotation procedure for each secret.

**Done when:**
- All ten broken configurations fail at startup with clear messages
- You found a secret through five leak paths and closed the ones `SecretStr` can
- Your four-backend comparison includes the audit and revocation columns
- Dual-value rotation achieved zero signature failures
- A ConfigMap change without a checksum annotation left pods stale
- Your application survives the flag service being down and being slow
- You converted at least three fake config values into constants
