# Lesser Known Hooks

The hooks that come up less often but solve problems the common ones cannot.

## useId

Generates a stable, unique id that matches between server and client.

```jsx
function Field({ label }) {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-describedby={`${id}-hint`} />
      <p id={`${id}-hint`}>Must be at least 8 characters</p>
    </>
  );
}
```

The problem it solves is hydration: a counter or `Math.random()` produces different ids on the server and the client, causing a mismatch. `useId` derives the id from the component's position in the tree, so both environments agree.

Rules: **one `useId` per component**, with suffixes for multiple ids (as above), and **never use it as a list key** — it is not derived from data ([[16.6 - Lists and Keys]]).

The generated value contains colons (`:r0:`), which is valid in an HTML id but breaks CSS selectors and `querySelector`. Use `document.getElementById` or `CSS.escape` if you need to select it.

## useSyncExternalStore

Subscribes to a mutable external source safely under concurrent rendering.

```jsx
function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,      // (callback) => unsubscribe
    getSnapshot,    // () => current value on the client
    getServerSnapshot   // () => value during SSR
  );
}

function subscribe(callback) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);
  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

const getSnapshot = () => navigator.onLine;
const getServerSnapshot = () => true;
```

The problem it solves is **tearing**: during an interruptible render, an external value can change between rendering two components, so one part of the UI shows the old value and another shows the new one ([[18.5 - Concurrent Rendering and the Scheduler]]). A `useState` + `useEffect` subscription cannot prevent this; `useSyncExternalStore` forces a synchronous, consistent read.

Two requirements that trip people up:

**`getSnapshot` must return a cached value**, not a new object each call. React calls it repeatedly and compares with `Object.is`; returning `{ ...state }` causes an infinite render loop.

```jsx
// Infinite loop
const getSnapshot = () => ({ items: store.items });

// Correct — return the same reference until it actually changes
const getSnapshot = () => store.state;
```

**`getServerSnapshot` is required for SSR**, and must return something the client's first render will agree with.

This is the hook every store library uses internally — Zustand, Redux and Jotai all build on it ([[20.8 - Zustand Jotai and Modern Alternatives]]). You rarely call it directly unless you are integrating a non-React source: a WebSocket, `matchMedia`, `localStorage` across tabs, or a legacy event emitter.

## useDebugValue

Labels a custom hook in React DevTools.

```jsx
function useOnlineStatus() {
  const isOnline = useSyncExternalStore(...);
  useDebugValue(isOnline ? "Online" : "Offline");
  return isOnline;
}
```

Only useful in shared hooks or libraries. The second argument is a formatter called lazily, so expensive formatting does not run unless DevTools is open:

```jsx
useDebugValue(date, d => d.toISOString());
```

## useImperativeHandle

Customizes what a parent receives through a ref. Covered fully in [[22.3 - forwardRef and useImperativeHandle]].

```jsx
function Input({ ref }) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current.focus(),
    clear: () => { inputRef.current.value = ""; },
  }), []);

  return <input ref={inputRef} />;
}
```

Exposing a narrow, intentional API rather than the raw DOM node. Use sparingly — imperative escapes fight the declarative model, and a prop usually does the job.

## use

React 19's resource reader. It is not subject to the rules of hooks — it can be called conditionally and inside loops ([[17.1 - Rules of Hooks and How They Work]]).

```jsx
function Comments({ commentsPromise }) {
  const comments = use(commentsPromise);   // suspends until resolved
  return comments.map(c => <p key={c.id}>{c.text}</p>);
}

<Suspense fallback={<Spinner />}>
  <Comments commentsPromise={promise} />
</Suspense>
```

It also reads context:

```jsx
function Heading({ children }) {
  if (children == null) return null;
  const theme = use(ThemeContext);   // after an early return — legal
  return <h1 className={theme}>{children}</h1>;
}
```

Important constraint: the promise must be **created outside the component that reads it** — typically in a Server Component or a cache — because a promise created during render is recreated on every render and would suspend forever.

## useTransition and useDeferredValue

Both mark work as non-urgent so the UI stays responsive. Covered in [[22.4 - useTransition and startTransition]] and [[22.5 - useDeferredValue]].

```jsx
const [isPending, startTransition] = useTransition();

startTransition(() => setSearchQuery(value));   // interruptible, low priority
```

```jsx
const deferredQuery = useDeferredValue(query);   // lags behind during heavy renders
```

The distinction: `useTransition` wraps the **update**, `useDeferredValue` wraps the **value** — use the latter when you do not control the state setter, such as when the value arrives as a prop.

## useOptimistic

Shows an expected result immediately while an async action is in flight.

```jsx
function Thread({ messages, sendMessage }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (state, newMessage) => [...state, { ...newMessage, pending: true }]
  );

  async function action(formData) {
    addOptimistic({ text: formData.get("text") });
    await sendMessage(formData);
  }
}
```

React automatically reverts to the real state when the action completes or fails, which is the part hand-rolled optimistic updates usually get wrong ([[24.5 - Optimistic UI]]).

## useActionState

Manages form submission state with a reducer-shaped async function.

```jsx
const [state, formAction, isPending] = useActionState(
  async (prevState, formData) => {
    const result = await save(formData);
    return result.error ? { error: result.error } : { success: true };
  },
  {}
);

<form action={formAction}>
  <input name="email" />
  <button disabled={isPending}>Save</button>
</form>
```

Pending state, error state and progressive enhancement handled by React ([[21.2 - Validation Strategies]]).

## useFormStatus

Reads the status of the nearest parent `<form>` from a child, without prop drilling:

```jsx
function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Saving..." : "Save"}</button>;
}
```

It must be called from a component **rendered inside** the form, not from the component that renders the form.

## useInsertionEffect

Fires before all layout effects, for injecting `<style>` tags. It exists solely for CSS-in-JS libraries — inserting styles in a layout effect is too late and causes a re-layout ([[11.5 - CSS Architecture]]). Application code should never need it.

## How senior engineers actually use this

**They use `useId` for every generated id in SSR applications**, since hydration mismatches from ad-hoc ids are common and confusing.

**They use `useSyncExternalStore` for any external subscription**, rather than `useState` plus an effect — it is the only correct answer under concurrent rendering.

**They know `useDeferredValue` versus `useTransition`** by whether they own the setter.

**They reach for `useImperativeHandle` rarely** and treat it as a design smell in application code.

## Common pitfalls

- `useId` used as a list key.
- `getSnapshot` returning a new object each call, causing an infinite loop.
- Missing `getServerSnapshot`, breaking SSR.
- A promise created inside the component that calls `use`.
- `useFormStatus` called in the component that renders the form rather than inside it.
- Reaching for `useImperativeHandle` where a prop would work.

## Interview angle

These hooks rarely get direct questions, but `useSyncExternalStore` is an excellent one to raise unprompted when discussing state libraries or concurrent rendering — explaining tearing and why a `useState` subscription cannot prevent it demonstrates real depth. `useId` comes up naturally in SSR and accessibility discussions. Knowing the React 19 additions (`use`, `useOptimistic`, `useActionState`) signals you keep current.
