# Multi-Tenant Data Models

#backend #databases #postgres #multi-tenancy

> **In one line:** Shared table, schema per tenant, or database per tenant — the choice trades isolation against operational cost, and the failure mode of the cheapest option is showing one customer another customer's data.

---

## The Idea

```
Pool     one table, a tenant_id column     ← cheapest, weakest isolation
Bridge   one database, a schema per tenant
Silo     one database per tenant           ← strongest isolation, highest cost
```

| | Pool | Bridge | Silo |
|---|---|---|---|
| Tenants per instance | Millions | Hundreds | Tens |
| Cost per tenant | Very low | Low | High |
| **Isolation** | **Application-enforced** | Schema-enforced | **Physical** |
| Noisy neighbour | Full impact | Partial | None |
| Per-tenant backup/restore | Hard | Medium | **Trivial** |
| Schema migration | One | N schemas | N databases |
| Cross-tenant analytics | Trivial | Medium | Hard |

💡 **Pool is right for the vast majority of SaaS products**, and the entire question becomes: how do you make application-enforced isolation trustworthy?

---

## The Pool Model

```sql
CREATE TABLE documents (
    id      uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id  uuid NOT NULL REFERENCES organisations(id),
    ...
);
CREATE INDEX ON documents (org_id, created_at DESC);
```

**Every table gets `org_id`, and every index starts with it** ([[06.10 - Schema Design]]).

⚠️ **Denormalise `org_id` onto child tables even when it is derivable.** An `annotations` table could reach the organisation through `document_id`, and putting `org_id` directly on it means:

- Every index is naturally tenant-partitioned
- Row-level security is a single-column policy with no joins
- A missing tenant filter is a missing `WHERE`, easier to audit than a missing join
- Future partitioning by tenant becomes possible

💡 **This single denormalisation is the highest-value multi-tenancy decision you make, and it costs 16 bytes per row.**

### The failure mode

```python
docs = await conn.fetch("SELECT * FROM documents WHERE status = 'indexed'")
```

**Every tenant's documents. No error, no warning, and it may not be noticed for months.**

⚠️ **This is a data breach caused by one missing clause**, and it is the reason the pool model needs enforcement rather than discipline.

## Row-Level Security

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY;    -- applies to the table owner too

CREATE POLICY tenant_isolation ON documents
    USING (org_id = current_setting('app.current_org_id')::uuid);
```

```python
async with pool.acquire() as conn:
    await conn.execute("SET LOCAL app.current_org_id = $1", str(org_id))
    docs = await conn.fetch("SELECT * FROM documents")   # automatically scoped
```

💡 **RLS moves tenant isolation from something every developer must remember to something the database enforces on every query, from every code path, including `psql`.** That is a genuine security boundary rather than a convention.

### The details that matter

**`FORCE ROW LEVEL SECURITY`** — without it, the table owner bypasses policies, and your application user is often the owner.

**`SET LOCAL`, not `SET`** — `LOCAL` is transaction-scoped and resets on commit.

⚠️ **This is the RLS-plus-PgBouncer trap and it is severe.** In transaction mode, forgetting `LOCAL` means **the next tenant to use that server connection inherits your `org_id`** ([[06.9 - Connection Pooling and PgBouncer]]). **Always `SET LOCAL`, always inside an explicit transaction.**

**Separate policies per operation:**

```sql
CREATE POLICY tenant_select ON documents FOR SELECT
    USING (org_id = current_setting('app.current_org_id')::uuid);

CREATE POLICY tenant_insert ON documents FOR INSERT
    WITH CHECK (org_id = current_setting('app.current_org_id')::uuid);
```

⚠️ **`USING` filters what you can see; `WITH CHECK` validates what you write. Without `WITH CHECK` on insert, a tenant can create rows belonging to another tenant.**

### The performance cost

The policy becomes a predicate. **With `(org_id, ...)` as the leading index column, it is essentially free.**

⚠️ **Without a matching index it is a sequential scan on every query.** RLS makes a missing `org_id` index catastrophic rather than merely slow.

⚠️ **RLS predicates can prevent some optimisations**, particularly partition pruning and certain join reorderings. **Measure your critical queries with RLS on and off** — usually negligible, occasionally not.

💡 **Mark simple, provably-safe functions as `LEAKPROOF`** to let the planner push predicates through policies. An advanced fix, and worth knowing when a query is inexplicably slow under RLS.

## Defence in Depth

```python
# Layer 1: the query builder always scopes
class TenantRepository:
    async def documents(self, **filters):
        return await self._conn.fetch(
            "SELECT * FROM documents WHERE org_id = $1 AND ...", self._org_id, ...)
```

```python
# Layer 3: assert on the way out
def assert_tenant(rows, org_id):
    bad = [r for r in rows if r["org_id"] != org_id]
    if bad:
        tenant_leak_total.inc()
        log.critical("cross-tenant data in response", extra={"count": len(bad)})
        raise TenantIsolationError()
```

💡 **The third layer is cheap and it turns a silent breach into a loud error.** Run it in every environment — **a leak that raises a 500 is enormously better than one that renders in a customer's browser.**

**Layer 4: the loader.** In GraphQL, enforce the boundary inside every DataLoader batch function ([[05.6 - The N+1 Problem and DataLoader]]) — every path to an entity goes through it.

## The Bridge Model: Schema per Tenant

```sql
CREATE SCHEMA tenant_acme;
SET search_path TO tenant_acme, public;
```

| Good | Bad |
|---|---|
| Strong isolation without separate databases | **N schemas to migrate** |
| Per-tenant backup via `pg_dump -n` | Postgres catalogue bloat above ~500 schemas |
| Per-tenant customisation possible | Connection pooling fights `search_path` |

⚠️ **The catalogue problem is real.** 1,000 tenants × 30 tables is 30,000 tables — `pg_class` becomes large, autovacuum has 30,000 relations to consider, and planning time rises. **Several hundred schemas is a practical ceiling.**

💡 **The migration problem is the one that ends this model.** Running one `ALTER TABLE` becomes running it 500 times, with partial failure leaving tenants on different schema versions. **Teams that adopt bridge usually migrate to pool or silo within a few years.**

---

## The Silo Model: Database per Tenant

| Good | Bad |
|---|---|
| **Complete isolation** | Cost per tenant is high |
| Per-tenant restore is trivial | N databases to migrate, monitor, back up |
| Per-tenant scaling and placement | **Connection pool per tenant** |
| Data residency per tenant | Cross-tenant analytics needs ETL |

💡 **Silo is right for a small number of large, high-value tenants** — enterprise deals where isolation is contractual, or where regulation demands residency.

⚠️ **Connection management is the practical killer.** 100 tenants × a pool of 5 = 500 connections, each database with its own `max_connections`. **This is why silo does not scale to many tenants regardless of infrastructure cost.**

### The hybrid most mature SaaS converges on

```
Pool:  free and standard tiers, thousands of tenants, one database
Silo:  enterprise tenants, dedicated databases
```

```python
async def connection_for(tenant_id: UUID):
    cfg = await registry.get(tenant_id)
    if cfg.mode == "silo":
        return await silo_pools[cfg.database].acquire()
    conn = await pool_db.acquire()
    await conn.execute("SET LOCAL app.current_org_id = $1", str(tenant_id))
    return conn
```

💡 **Design the tenant registry indirection from the start even if every tenant starts pooled.** Retrofitting it means changing every data access path; adding it early costs one function.

## In Production

### Noisy neighbours

| Problem | Defence |
|---|---|
| One tenant with 40% of the data | Ensure `org_id` leads every index |
| One tenant issuing expensive queries | Per-tenant rate limiting and query timeouts |
| One tenant's bulk import | Throttle by tenant; separate the write path |
| A hot row in shared data | Shard it ([[06.8 - Locking and Deadlocks]]) |

⚠️ **Per-tenant query cost accounting is the thing most pooled systems lack**, and it is what turns "one customer is slow" into "everyone is slow".

```python
sql = f"/* org:{org_id} */ SELECT ..."
```

💡 **Query tagging costs nothing and makes per-tenant attribution possible in every log and monitoring tool. Do it from day one.**

### Per-tenant operations in a pool

⚠️ **A point-in-time restore of one tenant from a pooled database means restoring the whole database elsewhere and extracting that tenant's rows.** It works, it is slow, **and you should have practised it before a customer asks.**

💡 **This is one of the strongest practical arguments for silo for enterprise tenants** — "we can restore your data to any point in the last 30 days without affecting anyone else" is a real contractual capability.

### Offboarding and deletion

⚠️ **Deletion must be complete and provable** — GDPR erasure applies to backups, derived stores, caches and logs too.

| Location | |
|---|---|
| Primary database | `CASCADE` delete, verified |
| Read replicas | Follows automatically |
| Search index | Must be explicitly deleted |
| Cache | Invalidate by tenant prefix |
| Object storage | Delete by tenant prefix |
| Backups | Documented retention window, then expiry |
| **Logs and analytics** | **Often forgotten. Include it** |

**Write a deletion checklist and a verification query per store.** "We deleted them from the database" is not compliance.

### Migrating from pool to silo

```
1. Create the target database with the same schema
2. Copy the tenant's rows
3. Dual-write during the switchover window
4. Verify counts and checksums
5. Switch the registry entry
6. Delete from the pool after a safety period
```

💡 **This is expand/contract applied to tenancy** ([[06.11 - Zero Downtime Migrations]]), and **having the registry indirection from the start is what makes step 5 a configuration change rather than a deploy.**

### Conduit's choice

| Aspect | Decision |
|---|---|
| Model | **Pool**, with registry indirection for future silo |
| Isolation | `org_id` on every table, RLS with `FORCE`, response assertions |
| Indexes | Every index leads with `org_id` |
| Cost control | Per-tenant concurrency limits and query tagging |
| Enterprise path | Silo, when a customer requires it |

**Defend it: Conduit's tenants are small and numerous, cross-tenant analytics matter for the product, and one migration is better than five hundred.**

## Codebase

**Repo:** `postgres/postgres`, `supabase/supabase`, `citusdata/citus`

**Question to answer:** How does Postgres apply an RLS policy — where in the planner does it become a predicate, and why can it block some optimisations? Then: how does Supabase use RLS as the primary authorisation mechanism, and what patterns do they recommend for performance?

**Read, in order:**

1. `postgres/src/backend/rewrite/rowsecurity.c` — **`get_row_security_policies`.** Policies are applied during query rewriting, becoming quals on the relation
2. `postgres/src/backend/optimizer/util/clauses.c` — search for `LEAKPROOF` and `contain_leaked_vars`. **This is why RLS can block predicate pushdown**: a non-leakproof function could reveal filtered rows through an error message
3. **Supabase RLS documentation** — **their production patterns**, including wrapping `auth.uid()` in a subquery so it is evaluated once rather than per row. A genuinely useful performance trick
4. `citus/src/backend/distributed/planner/` — how a distribution column enforces tenant boundaries at the shard level. **Tenancy and sharding are the same problem when the shard key is the tenant key**
5. Any large SaaS schema with tenancy — search GitLab's schema for their group isolation model

💡 The `LEAKPROOF` reasoning is subtle and worth understanding: **Postgres will not evaluate a function on rows you should not see, in case that function leaks their contents via an error message.** This is a genuine security consideration, **and it explains a whole class of "why is this query slow under RLS" questions.**

**Size:** 1–2 sessions.

## Exercise

**Drill 6.16 — Leak tenant data, then make it impossible**

⚠️ Everything runs against your own local stack.

```
├── noisy/{induce.py, limits.py, PLOT.md}
└── README.md
```

**Part 1 — Build the pool model, naively.** `org_id` everywhere, filtering in application code, no RLS. Ten endpoints.

**Part 2 — Leak data five ways.** Each a realistic mistake:

| Leak | |
|---|---|
| A forgotten `WHERE org_id` on one endpoint | |
| An `INSERT` with a client-supplied `org_id` | |
| A join to a table that is not tenant-filtered | |
| **`SET` instead of `SET LOCAL` behind PgBouncer** | |
| 403 versus 404 allowing enumeration | |

**For each, demonstrate the actual cross-tenant access**, then estimate how long it would take to notice in production.

**The PgBouncer one is the most instructive** — it requires transaction pooling plus concurrency, so it appears only under load and never in testing.

**Part 3 — Add RLS and re-test.** Policies with `FORCE`, and separate `USING`/`WITH CHECK`.

**Confirm each of the five leaks is now blocked. Note which ones RLS does *not* fix** — the enumeration one is application-level.

Then attempt to bypass RLS: as the table owner without `FORCE`, via a `SECURITY DEFINER` function, and by setting the session variable directly.

**Part 4 — Response assertions.** Add the outgoing check. Then deliberately break RLS and **confirm the assertion catches it.** Measure its overhead on a 1,000-row response, and decide whether you would run it in production.

**Part 5 — RLS performance.** Ten queries with RLS off, RLS on with a leading `org_id` index, and RLS on without one.

**Find a query where RLS blocks an optimisation** — a partition-pruning query is a good candidate — and quantify it. Then apply the Supabase subquery trick and measure the improvement.

**Part 6 — Three models, one migration.** Implement bridge (50 schemas) and silo (10 databases) alongside pool.

**Run the same schema migration across all three. Measure duration, failure modes, and what a partial failure leaves behind.**

Then measure a cross-tenant analytical query in all three.

**Part 7 — Tenant operations.** Restore one tenant from a pooled backup to a point in time. **Time it end to end.**

Then complete offboarding across database, search index, cache and object storage, **with a verification query proving each is clean.**

Then promote a tenant from pool to silo with zero downtime.

**Part 8 — Noisy neighbours.** One tenant running expensive queries against a shared pool. **Chart p99 latency for other tenants.**

Then add per-tenant concurrency limits and query timeouts, and chart again. Then add query tagging and **demonstrate attributing the cost to the right tenant from your slow log alone.**

**Done when:**
- All five leaks are demonstrated with real cross-tenant access
- RLS blocks the four it can, and you know which one it cannot
- You attempted three RLS bypasses and know which work
- You have quantified RLS overhead, including a case where it blocks an optimisation
- One migration across three tenancy models is measured, including partial failure
- You restored and fully deleted a single tenant, with verification
- Per-tenant limits demonstrably protect other tenants, with attribution from logs
