# State and useState Mental Model

State is memory that survives between renders and triggers a re-render when it changes. The mental model that makes it predictable: **each render sees a snapshot** of state, frozen for that render's entire lifetime.

```jsx
const [count, setCount] = useState(0);
```

## State is a snapshot, not a live variable

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log(count);   // 0 — not 3, and not even 1
  };
}
```

`count` is a `const` binding created during this render. `setCount` does not change it; it schedules a new render in which a *new* `count` binding will hold the new value.

All three calls compute `0 + 1`, so the result is 1, not 3. To build on the pending value, use the updater form:

```jsx
setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);   // now 3
```

Updater functions are queued and applied in order, each receiving the result of the previous. This is the correct form whenever the new value depends on the old one — and it is what makes a callback safe against stale closures ([[02.3 - Closures]]).

The same snapshot rule explains this:

```jsx
const handleClick = () => {
  setCount(count + 1);
  setTimeout(() => alert(count), 3000);   // alerts the OLD value
};
```

The timeout closed over this render's `count`.

## Batching

React batches all state updates within an event handler into a single re-render:

```jsx
const handleClick = () => {
  setA(1);
  setB(2);
  setC(3);
};   // one render, not three
```

Since React 18, batching applies **everywhere** — timeouts, promises, native event handlers — not just React events. This is "automatic batching", and it changed behavior for code that relied on a render between two setState calls in an async function.

To force a synchronous update — rarely needed, mainly for measuring the DOM immediately after an update:

```js
import { flushSync } from "react-dom";
flushSync(() => setOpen(true));
node.scrollIntoView();
```

`flushSync` opts out of batching and hurts performance; treat it as an escape hatch ([[18.6 - Batching and the Update Queue]]).

## Bailing out

React compares the new state to the old with `Object.is`. If they are identical, it may skip the re-render:

```jsx
setCount(0);   // already 0 — no re-render
setUser(user); // same object reference — no re-render
```

Which is exactly why mutation does not work:

```jsx
// Broken — same reference, no re-render
setUser(u => { u.name = "new"; return u; });

// Correct
setUser(u => ({ ...u, name: "new" }));
```

This is the practical reason React requires immutable updates ([[06.7 - Immutable Data Patterns]]).

Note React may still render once more after a bailout before stopping — it bails out of *committing*, not always of rendering.

## Lazy initialization

```jsx
const [state, setState] = useState(expensiveInit());     // runs EVERY render
const [state, setState] = useState(() => expensiveInit()); // runs once
```

The argument is evaluated on every render even though only the first value is used. Passing a function defers it to the initial render only. Relevant for reading `localStorage`, parsing a large payload, or any non-trivial computation.

Note the same syntax means you cannot store a function *as* state directly:

```jsx
useState(myFunction);        // calls it — stores the return value
useState(() => myFunction);  // stores the function
```

## Structuring state

**Avoid redundant state.** Anything derivable should be computed during render:

```jsx
// Redundant — two sources of truth that can desync
const [items, setItems] = useState([]);
const [count, setCount] = useState(0);

// Derived — always correct
const [items, setItems] = useState([]);
const count = items.length;
```

Storing derived values means every update path must remember to update both. The bug appears when someone adds a third update path.

**Group state that changes together:**

```jsx
const [x, setX] = useState(0);
const [y, setY] = useState(0);
// vs
const [position, setPosition] = useState({ x: 0, y: 0 });
```

If two values always change in the same event, one object is simpler. If they change independently, separate state avoids unnecessary spread.

**Avoid deep nesting.** Deeply nested state makes updates painful ([[06.7 - Immutable Data Patterns]]) and usually indicates the shape should be flattened or normalized ([[20.7 - State Normalization]]).

**Avoid contradictory state:**

```jsx
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
// both true is meaningless but representable

const [status, setStatus] = useState("idle");  // "idle" | "loading" | "error" | "success"
```

A single status field makes invalid combinations unrepresentable. For more transitions, `useReducer` ([[17.10 - useReducer]]).

## Resetting state with key

```jsx
<ProfileForm key={userId} user={user} />
```

Changing a component's `key` makes React treat it as a different component: unmount, remount, fresh state. This is the idiomatic way to reset a form when the entity changes, and it is far cleaner than an effect that resets state when a prop changes.

The general rule: if you find yourself writing an effect to synchronize state with a prop, consider whether `key` or deriving during render solves it instead.

## State is per component instance

```jsx
<Counter />
<Counter />   // two independent counters
```

State is tied to a position in the tree, not to the component function. Two elements of the same type at the same position share state across renders; the same element at a different position gets fresh state. This is why conditionally swapping components at the same position preserves state unexpectedly:

```jsx
{isChecked ? <Counter /> : <Counter />}   // same position, same type — state persists
```

Adding a distinguishing `key` separates them.

## How senior engineers actually use this

**They default to the updater form** whenever the next value depends on the previous, which makes state updates immune to stale closures.

**They derive rather than store.** Every piece of state is a thing that can go out of sync; a computed value cannot.

**They use `key` for resets** instead of synchronizing effects.

**They model status as a union**, not as parallel booleans.

**They keep state as local as possible** and lift only when a sibling needs it ([[20.1 - Where State Should Live]]).

## Common pitfalls

- Expecting `setState` to update the variable synchronously.
- Multiple `setCount(count + 1)` calls in one handler producing one increment.
- Mutating state and getting no re-render.
- `useState(compute())` running on every render.
- Storing derived values, which then desync.
- Parallel booleans allowing impossible states.
- An effect that copies props into state, causing an extra render and stale values.

## Interview angle

"Why doesn't state update immediately" is the canonical question, and the answer is the snapshot model — `count` is a const from this render, `setState` schedules a new render with a new binding. Follow with the updater form and why three `setCount(count+1)` calls yield 1. Automatic batching in React 18 and the `Object.is` bailout explaining the immutability requirement are both strong additions.
