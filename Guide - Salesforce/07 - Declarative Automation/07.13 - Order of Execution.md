# Order of Execution

## The most important page on the platform

When a record is saved, roughly twenty things happen in a fixed sequence. Engineers who have internalized that sequence debug in minutes what others debug in days.

This note is referenced from a dozen places in this course, and it is worth reading more than once — the second reading, after you have written triggers and flows, tells you more than the first.

## The sequence

```
 1.  The record is loaded from the database, or initialized for an insert
 2.  New field values from the request overwrite the old ones
 3.  System validation runs
        required fields, field types, field length, foreign key validity
        (for API requests only; the UI validates some of this earlier)
 4.  Before-save record-triggered flows run
 5.  Before triggers run
 6.  System validation runs again
        plus custom validation rules
        plus duplicate rules
 7.  The record is saved to the database — but NOT committed
 8.  After triggers run
 9.  Assignment rules run
10.  Auto-response rules run
11.  Workflow rules run
        (legacy; field updates here re-run steps 5 through 8 for that record)
12.  Escalation rules run
13.  After-save record-triggered flows run
        (any DML here re-enters this pipeline for the affected records)
14.  Entitlement processes run
15.  Roll-up summary fields on parent records recalculate
        (which can send the parent through its own save pipeline, recursively)
16.  Criteria-based sharing rules are evaluated
17.  Everything is COMMITTED to the database
18.  Post-commit logic runs
        email sending, platform event publishing, asynchronous jobs enqueued
```

The numbering varies slightly between documentation versions as features are added and retired. The shape is stable and is what matters.

## The five things this explains

**1. Nothing is committed until step 17.**

An exception anywhere before that rolls back everything. This is why a validation rule failure discards a trigger's work, why a limit exception in an after-save flow undoes the original save, and why partial saves do not happen.

It is also why a fault path writing a log record inside a record-triggered flow does not survive — the write is inside the transaction being discarded. See [[07.8 - Flow Error Handling and Fault Paths]].

**2. Before-save flows run before validation rules.**

Step 4 precedes step 6. A before-save flow can populate a field that a validation rule requires, and the validation passes.

This is genuinely useful for defaults. It also means a validation rule cannot assume a field was empty when the user submitted, because automation may have filled it.

**3. Before triggers run after before-save flows.**

Step 5 follows step 4. If both write the same field, the **trigger wins**, because it runs later.

Nobody intends this, and it surfaces as "the flow is not working" when the flow worked perfectly and was overwritten. This is the concrete reason behind the guidance in [[07.1 - Automation Landscape and Tool Selection]]: one mechanism per concern per object.

**4. Roll-up recalculation at step 15 can cascade.**

Updating a child record recalculates the parent's roll-up, which updates the parent, which sends the parent through its own save pipeline — its triggers, its flows, its validation rules — and if the parent has a grandparent with a roll-up, further still.

A single child insert can therefore consume limits belonging to three objects' automation. This is the usual explanation for `Apex CPU time limit exceeded` on an operation that looks trivial.

**5. Callouts cannot happen after DML in the same transaction.**

Because the transaction holds open database work between steps 7 and 17, an HTTP callout during that window would hold a database transaction open for the duration of an external system's response time. The platform forbids it.

This is why notification and integration work belongs in step 18 — a platform event published post-commit, or an async job enqueued. See [[12.8 - Platform Events]].

## Recursion

Steps 11, 13, and 15 can all cause a record to re-enter the pipeline. Without control, this loops.

The platform provides some protection — a limited number of save recursions before `maximum trigger depth exceeded` — but relying on that is relying on a crash.

The standard control in Apex is a static variable, which persists for the transaction and resets between transactions:

```java
public with sharing class TriggerControl {

    private static Set<String> completed = new Set<String>();

    public static Boolean hasRun(String key) {
        return completed.contains(key);
    }

    public static void markRun(String key) {
        completed.add(key);
    }
}
```

```java
public with sharing class OpportunityTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isUpdate) {
            if (TriggerControl.hasRun('Opportunity_AfterUpdate')) {
                return;
            }
            TriggerControl.markRun('Opportunity_AfterUpdate');
            OpportunityService.rollUpWonRevenue(Trigger.new, Trigger.oldMap);
        }
    }
}
```

A caution that matters: a blanket "run once per transaction" guard is too blunt in a bulk context. If 200 records are updated and a subsequent update in the same transaction affects 50 more, the guard skips them entirely. The safer form tracks **which record IDs** have been processed rather than whether the handler ran at all. See [[11.6 - Recursion Control and Static Guards]].

## Debugging with the sequence

The diagnostic method that makes this note pay for itself.

**"My field update is being overwritten."**
Something later in the sequence is writing it. Check, in order: before triggers (step 5), after triggers (step 8), workflow field updates (step 11), after-save flows (step 13). Whatever runs latest wins.

**"My validation rule fires when it should not."**
Something before step 6 is changing the field. Check before-save flows and before triggers.

**"My trigger cannot see a field another automation sets."**
That automation runs later. An after-save flow setting a field is invisible to an after trigger, because step 8 precedes step 13.

**"CPU limit exceeded on a simple update."**
Roll-up cascade at step 15, or layered automation. Enumerate what fires on the object and its parents.

**"My callout throws 'uncommitted work pending'."**
DML happened earlier in the transaction. Move the callout to async or to a platform event subscriber.

**"The record saved but the related record did not."**
Everything rolls back together, so this cannot happen within one transaction. If it appears to, the related work is asynchronous — a platform event or a queued job — and it failed separately.

## Reading the sequence in a debug log

The log shows the pipeline directly, and learning to read it is the practical skill.

```
CODE_UNIT_STARTED  [EXTERNAL] execute_anonymous_apex
DML_BEGIN          [1] Op:Update Type:Opportunity Rows:200
  CODE_UNIT_STARTED  [EXTERNAL] Flow:Opportunity_BeforeSave        ← step 4
  CODE_UNIT_STARTED  [EXTERNAL] Trigger:OpportunityTrigger before  ← step 5
  VALIDATION_RULE    [Opportunity] Require_Close_Reason            ← step 6
  CODE_UNIT_STARTED  [EXTERNAL] Trigger:OpportunityTrigger after   ← step 8
  CODE_UNIT_STARTED  [EXTERNAL] Flow:Opportunity_AfterSave         ← step 13
  DML_BEGIN          [2] Op:Update Type:Account Rows:47            ← step 15 cascade
    CODE_UNIT_STARTED [EXTERNAL] Trigger:AccountTrigger before     ← the parent's pipeline
DML_END
LIMIT_USAGE_FOR_NS ...
```

Nested `DML_BEGIN` blocks are cascades. A log with four levels of nesting on a single user action is the picture of an org where automation has accumulated without an owner. See [[20.1 - Debug Logs and Log Levels]].

## The org audit

Enumerating what fires on an object takes two queries and is the first thing to do when inheriting an org:

```sql
SELECT ApiName, Label, TriggerType, TriggerObjectOrEventLabel, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerObjectOrEventLabel = 'Opportunity'
```

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status FROM ApexTrigger WHERE TableEnumOrId = 'Opportunity'" \
  --target-org production
```

Add the validation rules, the roll-up summaries on the object and its parents, and the assignment or escalation rules, and that is the complete picture of one save.

## Section 07 in one paragraph

Salesforce offers many ways to react to a record change, and the skill is choosing the least powerful tool that works: formula, then roll-up, then validation rule, then flow, then Apex, then async. Flows are code with a canvas — they consume the same limits, run once per record rather than per batch, and cannot collect across a bulk save the way a trigger can, which is why anything bulk-sensitive belongs in invocable Apex. Before-save flows are an order of magnitude cheaper than after-save flows for same-record assignment, and an after-save flow updating its own record is always a mistake. All of it runs in one fixed sequence per save, nothing commits until the end, and roll-up recalculation can send parent records back through the whole pipeline. Knowing that sequence is what separates debugging from guessing.
