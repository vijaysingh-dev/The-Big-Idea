# Replay, Backfill and Reprocessing

#backend #streaming #operations

> **In one line:** The ability to re-run history against fixed code is the single largest benefit of a log — and it only works if you designed for it before you needed it.

---

## The Idea

```
A bug in the indexer for the last three days
→ reset the consumer offset to three days ago
→ replay
→ the index is correct
```

💡 **That is the capability a log gives you and a queue does not** ([[09.1 - Queue vs Log]]). Consumed messages are gone from a queue; a log retains them and lets you read from any position.

Three related operations, and they are not the same:

| Operation | |
|---|---|
| **Replay** | Re-run the same events through the same or fixed code |
| **Reprocessing** | Re-run history to produce a different output — a new derived store |
| **Backfill** | Populate a new consumer with historical data it never saw |

⚠️ **All three assume your consumer can safely process the same event twice.** A consumer that is not idempotent cannot be replayed, and discovering that during an incident is the worst time.

---

## What Makes a Consumer Replayable

Four properties, and all four are required.

### 1. Idempotent effects

```python
# ✅ replayable — upsert
await conn.execute(
    "INSERT INTO search_index (doc_id, content) VALUES ($1, $2) "
    "ON CONFLICT (doc_id) DO UPDATE SET content = $2",
    event["document_id"], event["content"],
)

# ❌ not replayable — accumulates
await conn.execute(
    "UPDATE org_stats SET doc_count = doc_count + 1 WHERE org_id = $1",
    event["org_id"],
)
```

💡 **Absolute writes replay; relative writes do not** ([[07.5 - Idempotency Keys and Deduplication]]). A counter incremented on every event double-counts on replay, and the fix is either a dedup record or recomputing the count from scratch.

### 2. No external side effects, or guarded ones

```python
async def handle(event):
    await update_index(event)                    # ✅ idempotent
    await send_email(event["author_email"])      # ⚠️ replay sends it again
```

⚠️ **Replaying a month of events would send a month of emails.** This is the failure people discover on their first replay, and it is memorable.

```python
REPLAY_MODE = os.environ.get("REPLAY_MODE") == "true"

async def handle(event):
    await update_index(event)
    if not REPLAY_MODE:
        await send_email(event["author_email"])
```

💡 **A replay flag that suppresses external side effects is the practical answer**, and it must be designed in rather than added under pressure.

**Better: separate consumers.** The indexer replays freely; the notifier never does.

### 3. Event-time semantics

```python
# ❌ uses wall clock — a replay produces different results
if event_age(event) < timedelta(hours=1):
    mark_recent(event)

# ✅ uses event time — a replay is deterministic
window = window_start(event["occurred_at"], HOUR)
```

⚠️ **Anything using `now()` produces different output on replay** ([[09.5 - Stream Processing Basics]]). That includes TTLs, "is this recent", and any timestamp written into the output.

**A replayable consumer's output is a pure function of its input.**

### 4. No dependency on external state that has moved on

```python
async def handle(event):
    org = await api.get_organisation(event["org_id"])    # ← may be deleted now
    ...
```

⚠️ **Replaying a three-month-old event calls the API with current state**, which may not match what was true then. **Fat events avoid this** by carrying what the consumer needs ([[09.2 - Event Modeling]]).

💡 **This is the strongest practical argument for event-carried state transfer.** A consumer that reads only the event replays correctly; one that calls back does not.

## Replaying: The Mechanics

```bash
# Reset a consumer group to a point in time
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group search-indexer --topic documents \
  --reset-offsets --to-datetime 2026-08-14T00:00:00.000 --execute
```

⚠️ **The group must have no active members**, so you stop the consumers, reset, and restart.

```bash
--to-earliest                    # from the beginning
--to-latest                      # skip everything
--to-offset 145823
--to-datetime 2026-08-14T00:00:00.000
--shift-by -100000               # relative
--by-duration PT72H              # 72 hours ago
```

💡 **`--dry-run` first, always.** It prints the new offsets per partition without applying them, and it is the difference between resetting the right group and resetting production analytics.

### Replaying with the offset stored in your database

If you store offsets transactionally ([[09.1 - Queue vs Log]]), the reset is a database write:

```sql
UPDATE consumer_offsets SET "offset" = 0 WHERE topic = 'documents' AND consumer = 'indexer';
```

💡 **This is cleaner** — the reset is transactional with any state truncation you also need, so you cannot end up with reset offsets and stale derived data.

```sql
BEGIN;
TRUNCATE search_index;
UPDATE consumer_offsets SET "offset" = 0 WHERE consumer = 'indexer';
COMMIT;
```

## Reprocessing: The Parallel Pipeline

⚠️ **Resetting a production consumer group means the derived store is wrong while the replay runs.** For a search index being replayed from three months ago, that is hours of degraded search.

💡 **The better pattern is to build a new one alongside and switch.**

```
1. Create search_index_v2 (empty)
2. Start a NEW consumer group writing to v2, from offset 0
3. It catches up to the live position
4. Verify v2 against v1 or the source of truth
5. Switch reads to v2
6. Delete v1 and the old consumer group
```

| Property | |
|---|---|
| **Zero downtime** | v1 serves reads throughout |
| **Verifiable before switching** | Compare counts and content |
| **Reversible** | Switch back if v2 is wrong |
| Costs double storage temporarily | |

💡 **This is expand/contract applied to derived state** ([[06.11 - Zero Downtime Migrations]]), and it is the shape every safe reprocessing takes. **The alias-swap pattern from Elasticsearch is exactly this** ([[06.15 - Search - Postgres vs Elasticsearch]]).

⚠️ **Step 4 is the one people skip.** Verifying that v2 matches before switching is what turns a risky operation into a routine one.

## Backfill: New Consumers on Old Data

```
A new analytics consumer needs 90 days of history
```

```bash
kafka-consumer-groups.sh --group analytics --reset-offsets --to-earliest --execute
```

⚠️ **Retention bounds what you can backfill.** With 30 days of retention, 90 days of history does not exist in the log.

| Source for history beyond retention | |
|---|---|
| **Tiered storage** | Kafka can offload old segments to object storage |
| **Infinite retention** on key topics | Storage is cheap; decide per topic |
| **Snapshot plus recent events** | Bootstrap from the database, then stream |
| **Rebuild from the source of truth** | Read the database directly, then switch to the stream |

💡 **The snapshot-plus-stream pattern is what Debezium does** ([[09.4 - Change Data Capture]]), and it is the general answer:

```python
async def bootstrap():
    lsn = await current_position()               # 1. record the position
    async for row in read_table_in_chunks():     # 2. snapshot
        await apply(row)
    await seek_to(lsn)                           # 3. stream from the recorded point
```

⚠️ **The handoff must not miss or duplicate.** Record the position *before* the snapshot, and let the idempotent consumer absorb the overlap.

## Throughput

⚠️ **A replay is a load spike.** 90 days of events consumed as fast as possible hits every downstream system at a rate they were never sized for.

```
Normal:  100 events/second
Replay:  50,000 events/second
→ the database, the search index and every downstream API are saturated
```

| Control | |
|---|---|
| **Rate limit the consumer** | The simplest and most effective |
| Separate consumer group and instances | Do not compete with live traffic |
| Larger batches, fewer round trips | Bulk upserts rather than per-record |
| **Run against a replica** | Where the target supports it |
| Off-peak scheduling | |

```python
limiter = AsyncLimiter(max_rate=1000, time_period=1)

async for msg in consumer:
    async with limiter:
        await handle(msg)
```

💡 **Rate-limit the replay to a multiple of normal throughput — 5× or 10× — rather than as fast as possible.** A replay that takes six hours and does not affect production is better than one that takes twenty minutes and causes an incident.

⚠️ **Watch the target's health, not just your own throughput.** A replay that saturates the database affects every other service using it.

```python
if await database_pressure() > THRESHOLD:
    await asyncio.sleep(1)                       # adaptive backoff
```

## In Production

### The pre-replay checklist

```
□  Is the consumer idempotent? Verified, not assumed
□  Are external side effects suppressed or separated?
□  Does it use event time, not wall clock?
□  Does it depend on external state that has moved on?
□  Is the target being rebuilt, or updated in place?
□  Is the rate limited?
□  Is there a way to verify correctness afterwards?
□  Is there a way to abort partway?
□  What does the derived store serve while this runs?
```

⚠️ **The first item is the one to actually test rather than believe.** Run the replay against a staging copy and compare the result to the original — if they differ, the consumer is not idempotent and you have just learned that safely.

### Verification

```python
async def verify(v1: str, v2: str) -> bool:
    counts_match = await count(v1) == await count(v2)
    sample = await random_sample(v1, n=1000)
    content_match = all(
        await get(v1, doc_id) == await get(v2, doc_id) for doc_id in sample
    )
    return counts_match and content_match
```

💡 **Count plus a content sample catches almost everything.** A full comparison of a large derived store is expensive; counts catch missing records and a sample catches wrong ones.

**Verify per tenant** for a multi-tenant system — a global count can match while one organisation's data is wrong.

### Aborting

```python
if await error_rate() > 0.01 or await target_pressure() > THRESHOLD:
    log.error("aborting replay")
    await stop_consumer()
```

⚠️ **A replay you cannot stop is a replay you should not start.** Build the kill switch first.

💡 **With the parallel-pipeline pattern, aborting is trivial** — stop the consumer, delete v2, and nothing production-facing was ever touched.

### Monitoring a replay

```python
replay_progress_ratio.set(processed / total)
replay_events_per_second.set(rate)
replay_estimated_completion_seconds.set(remaining / rate)
replay_target_lag_seconds.set(now - last_event_time)
replay_errors_total.inc()
```

💡 **`replay_estimated_completion_seconds` is what stops someone asking every ten minutes.** Compute it from the remaining offset range and the current rate.

**Track the target's health metrics alongside**, on the same dashboard, so the effect is visible.

### Retention as a policy decision

```
Topic                Retention    Rationale
documents            90 days      rebuild the search index from any point in the quarter
document.indexed     30 days      consumers are never more than days behind
org-config           infinite     compacted. It IS the state
analytics-raw        7 days       aggregated downstream; raw is not needed
audit                infinite     regulatory
```

💡 **Retention is "how far back can I rebuild".** Decide it per topic from that question rather than from a default, and write the rationale down.

⚠️ **Storage is cheap and 90 days is often the right answer for anything you might need to rebuild from.** The cost of insufficient retention is discovering during an incident that the data you need was deleted last week.

### Conduit's replay scenarios

| Scenario | Approach |
|---|---|
| Indexer bug, last 3 days | Parallel index, replay 3 days, verify, switch |
| New analytics consumer | Backfill from earliest, rate-limited |
| Search schema change | Parallel index from offset 0, alias swap |
| Organisation offboarding missed a store | Replay `organisation.deleted` for that org |
| Embedding model upgrade (phase 9) | **Parallel index, re-embed everything, verify, switch** |

💡 **The last one is why replay matters most for Conduit.** Upgrading an embedding model means re-embedding every chunk, and being able to do that from the event log — building a new index alongside and switching — is the difference between a routine operation and a multi-day outage.

**Design for it in phase 5**, before you need it in phase 9.

## Codebase

**Repo:** `apache/kafka`, `debezium/debezium`, `elastic/elasticsearch`

**Question to answer:** How does Kafka's offset reset by timestamp work — how does it find the offset for a given time? Then: how does Debezium's incremental snapshot interleave historical chunks with live streaming without missing or duplicating?

**Read, in order:**

1. `kafka/core/src/main/scala/kafka/log/UnifiedLog.scala` — **`fetchOffsetByTimestamp`.** How the time index maps a timestamp to an offset. **The answer to the first question** — and note that it is approximate, resolving to a segment boundary
2. `kafka/core/src/main/scala/kafka/admin/ConsumerGroupCommand.scala` — the reset logic, including why the group must be inactive
3. `debezium/debezium-core/src/main/java/io/debezium/pipeline/source/snapshot/incremental/AbstractIncrementalSnapshotChangeEventSource.java` — **the watermarking algorithm.** Open and close markers around each chunk, with deduplication against concurrent stream events. **The answer to the second question, and it is genuinely clever**
4. `elasticsearch` — the alias and reindex APIs. **The parallel-pipeline pattern as a product feature**
5. `kafka/core/src/main/scala/kafka/tier/` — tiered storage, for retention beyond local disk

💡 The Debezium incremental snapshot algorithm is the best reading here. **It reads a chunk of the table, emits an open marker, reads the chunk, emits a close marker, and drops any streamed events for rows in that chunk that arrived between the markers** — because the snapshot read already has the current value. Understanding it teaches you how to bootstrap any derived store correctly.

**Size:** 1–2 sessions.

**Part 1 — Produce history and four consumers.** 90 days of realistic document events, and four consumers: one correctly idempotent, one that accumulates counters, one that uses wall clock, and one that calls back for current state.

**Part 2 — Prove which are replayable.** Run each consumer over the full history to produce a baseline. Then replay from offset 0 and compare.

| Consumer | Expected |
|---|---|
| Idempotent | Identical |
| Accumulating | **Double-counted** |
| Wall clock | **Different values** |
| Callback | **Different, or errors** for deleted entities |

**Quantify each divergence.** Then fix all three and re-verify.

**Part 3 — Side effects on replay.** Add email sending to a consumer, with a mock provider that counts.

Replay 90 days. **Count the emails.** It should be alarming.

Then implement the replay flag, and separately the split-consumer approach. **Compare which is more robust** — a flag can be forgotten; a separate consumer cannot send emails at all.

**Part 4 — In-place versus parallel.** A search index with live read traffic.

**In-place:** reset the production consumer group and replay 30 days. Measure search availability and correctness throughout.

**Parallel:** build v2 with a new consumer group, verify, alias-swap. Measure the same.

**Chart search correctness over time for both.** The in-place version should be visibly degraded for the whole replay.

Then abort each partway and measure what state you are left in.

**Part 5 — Throughput and target pressure.** Replay 90 days as fast as possible into a Postgres-backed index, with live production traffic on the same database.

**Measure production query latency during the replay.** It should degrade badly.

Then rate-limit to 5× normal throughput and measure again. Then implement adaptive backoff based on connection pool wait time.

**Chart production p99 and replay throughput on the same axes for all three.**

**Part 6 — Beyond retention.** Set retention to 7 days, then attempt to backfill 90 days.

**Confirm it is impossible.** Then implement snapshot-plus-stream: read the database directly for history, record the position, and switch to the stream.

**Verify no records are missed or duplicated at the handoff** by modifying rows during the snapshot.

**Part 7 — Operations.** Progress metrics with completion estimate, a kill switch, and per-tenant verification.

Then run a full replay and **have someone else monitor it using only your dashboard** — confirm they can answer "how long left" and "is it working".

Write `runbook.md`: the pre-replay checklist, the procedure, the abort criteria, and the verification steps.

**Part 8 — The phase-9 rehearsal.** Simulate the embedding model upgrade: every chunk must be re-embedded and the index rebuilt.

Execute it with the parallel pattern, rate-limited, verified per organisation, with an alias swap.

**Measure total time, cost, and production impact.** This is the operation Conduit will actually need, and rehearsing it now is the point of the drill.

**Done when:**
- You have quantified the divergence for all three non-replayable consumers
- A replay sent an alarming number of emails, and two fixes prevent it
- Your search-correctness chart shows in-place degrading and parallel not
- Adaptive rate limiting keeps production p99 flat during a replay
- Snapshot-plus-stream handles concurrent modification at the handoff
- Someone else can monitor a replay from your dashboard alone
- The embedding-upgrade rehearsal completed with measured production impact
