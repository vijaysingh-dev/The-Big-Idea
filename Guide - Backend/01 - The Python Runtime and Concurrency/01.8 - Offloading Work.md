# Offloading Work

#backend #python #concurrency

> **In one line:** When code cannot be made async, push it into a thread or a process — but every offload has a limited pool behind it, and the pool becomes your new bottleneck.

---

## The Idea

You have code that blocks. You cannot rewrite it — it is a vendor SDK, a C library, or CPU-heavy work with no async equivalent.

The fix is to run it somewhere that is allowed to block, and `await` the result:

```python
result = await asyncio.to_thread(blocking_function, arg)
```

The event loop stays free. A worker thread does the blocking. When it finishes, the loop resumes your coroutine.

The thing people miss: **that pool has a fixed size.** You have not removed the limit, you have moved it. And a moved limit that you are not measuring is worse than one you can see.

---

## The Three Destinations

| Destination | For | Cost |
|---|---|---|
| **Thread** | Blocking I/O, or C code that releases the GIL | ~1–10 µs to hand off. Shares memory |
| **Process** | Pure-Python CPU work | ~10–50 µs plus pickling both ways |
| **Task queue** | Anything heavy, slow or retryable | Milliseconds, but survives restarts |

The third one is not usually presented as an offload option, and it should be. Most work that reaches for a process pool actually belongs in a queue — see [[08.1 - Why Background Work Exists]].

## Threads

### The API

```python
# Simplest, 3.9+
result = await asyncio.to_thread(func, *args, **kwargs)

# Explicit executor
loop = asyncio.get_running_loop()
result = await loop.run_in_executor(executor, func, arg)

# anyio, which is what FastAPI actually uses underneath
result = await anyio.to_thread.run_sync(func, arg)
```

### The default pool

`asyncio.to_thread` uses the loop's default executor: a `ThreadPoolExecutor` with `min(32, cpu_count + 4)` workers.

`anyio.to_thread.run_sync` uses a different mechanism — an unbounded set of reusable worker threads governed by a **capacity limiter**, default **40 tokens**. FastAPI's `def` endpoints go through this.

⚠️ **These are two different pools with two different limits in the same process.** `asyncio.to_thread` and `anyio.to_thread.run_sync` do not share a budget. In a FastAPI app you can have `def` endpoints queueing on anyio's 40 while `to_thread` calls have their own separate limit. Knowing which one your code path uses matters during an incident.

### Bulkheads: one limiter per dependency

The single most valuable pattern in this note.

```python
import anyio

sdk_limiter = anyio.CapacityLimiter(10)
hash_limiter = anyio.CapacityLimiter(4)

async def call_vendor(arg):
    return await anyio.to_thread.run_sync(vendor.fetch, arg, limiter=sdk_limiter)

async def hash_password(pw: str):
    return await anyio.to_thread.run_sync(bcrypt.hashpw, pw, salt,
                                          limiter=hash_limiter)
```

Without separate limiters, one slow dependency consumes every thread and everything else queues behind it. With them, the vendor can be completely down and your login endpoint is unaffected.

💡 This is the **bulkhead** pattern — named after ship compartments, where one flooded section does not sink the vessel. It appears again at the service level in [[11.3 - Circuit Breakers and Bulkheads]]. Applying it inside a single process is cheap and almost nobody does it.

### Sizing a thread pool

Threads are for waiting, so the useful formula is Little's Law:

```
threads needed = arrival rate × average duration
```

20 calls per second, 200ms each → `20 × 0.2 = 4` threads to keep up. Add headroom for variance: 8–10.

⚠️ **Do not just make it large.** 500 threads means 500 concurrent requests hitting the dependency, which usually makes the dependency slower, which makes you need more threads. That loop ends in an outage. The right size is slightly above what you need, so that overload becomes queueing (visible, measurable) rather than dependency collapse (not).

### Thread safety is now your problem

Once code runs in a thread, the GIL stops protecting your logic ([[01.2 - The GIL]]).

```python
cache = {}

def blocking_work(key):
    if key not in cache:          # two threads can both pass this
        cache[key] = expensive()  # and both compute it
    return cache[key]
```

Also: **thread-local state does not follow you across `to_thread`.** `contextvars` do — asyncio copies the context into the thread — but a library storing state in `threading.local()` will see an empty slate. This bites with database session managers and some tracing libraries.

## Processes

### The API

```python
from concurrent.futures import ProcessPoolExecutor

pool = ProcessPoolExecutor(max_workers=4)

loop = asyncio.get_running_loop()
result = await loop.run_in_executor(pool, cpu_heavy, data)
```

### The pickling tax

Everything in and out is serialized.

```
call:    args ──pickle──► pipe ──unpickle──► worker
return:  result ──pickle──► pipe ──unpickle──► you
```

```python
# Bad: 200MB across the boundary to do 10ms of work
await loop.run_in_executor(pool, process, huge_dataframe)

# Good: send a reference, let the worker load it
await loop.run_in_executor(pool, process_from_path, "/tmp/data.parquet")
```

⚠️ **Not everything pickles.** Database connections, open sockets, lambdas, local functions, and most class instances holding those will raise `PicklingError` — sometimes only under load, when a particular code path is hit.

### Start method

```python
import multiprocessing as mp
ctx = mp.get_context("spawn")
pool = ProcessPoolExecutor(max_workers=4, mp_context=ctx)
```

⚠️ **Never use `fork` from a process that has threads.** A lock held by another thread at fork time is held forever in the child, and the child deadlocks. Your web server has threads — the anyio pool, the logging handler, the database pool's background tasks. Use `spawn` or `forkserver`. Python 3.14 changed the Linux default to `forkserver` for exactly this reason.

### Create the pool once

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = ProcessPoolExecutor(max_workers=4, mp_context=ctx)
    yield
    app.state.pool.shutdown(wait=True, cancel_futures=True)
```

Creating a pool per request costs 50–200ms of process startup per call and will silently dominate your latency.

## Going the Other Way: Threads Calling Async

Sometimes you have a thread and need to reach the loop.

```python
# From a non-async thread, submit to a running loop and wait
future = asyncio.run_coroutine_threadsafe(coro, loop)
result = future.result(timeout=10)

# Schedule a plain callback on the loop — cheapest option
loop.call_soon_threadsafe(callback, arg)
```

⚠️ **`call_soon_threadsafe` is the only asyncio method that is safe to call from another thread.** Everything else — `create_task`, `Queue.put_nowait`, touching a Future — is not, and misuse produces corruption that shows up as impossible errors much later.

This matters for callback-based SDKs — a Kafka consumer, a gRPC callback, a C library's notification thread. The bridge is always `call_soon_threadsafe` or `run_coroutine_threadsafe`.

## In Production

### Choosing, in order

```
Is there an async library?              → use it
Is the work heavy, slow or retryable?   → task queue
Does the C code release the GIL?        → thread pool (with its own limiter)
Is it blocking I/O with no async lib?   → thread pool (with its own limiter)
Is it pure-Python CPU work?             → process pool
```

Ask the queue question early. "Generate a PDF report" in a process pool works until two users click at once; in a queue it works forever and survives a deploy.

### Real mappings

| Work | Where | Why |
|---|---|---|
| `bcrypt` / `argon2` password hash | Thread, limiter 4 | Releases the GIL. Limit it or logins DoS you |
| Vendor SOAP/SDK call | Thread, limiter 10 | Blocking, no async version |
| `boto3` S3 upload | Thread, or `aioboto3` | Prefer the async client |
| Pillow image resize | Queue | Too slow for a request, and a memory risk |
| 5MB `json.loads` | `orjson` in the loop, or a thread | Measure first — orjson may be fast enough |
| Pandas aggregation | Process pool, or move to the database | Usually the database was the right answer |
| PDF generation | Queue | Seconds of CPU, must survive restarts |
| `hashlib` over a large file | Thread | Releases the GIL, streams nicely |

### Observing your pools

Pool exhaustion is invisible by default. Make it visible.

```python
limiter = anyio.CapacityLimiter(10)

async def call_with_metrics(func, *args):
    queued = limiter.statistics().tasks_waiting
    pool_waiting.set(queued)
    start = time.perf_counter()
    async with limiter:
        acquired = time.perf_counter()
        pool_wait_seconds.observe(acquired - start)
        try:
            return await anyio.to_thread.run_sync(func, *args, limiter=limiter)
        finally:
            pool_work_seconds.observe(time.perf_counter() - acquired)
```

💡 **The two numbers that matter are wait time and work time.** If wait time is climbing while work time is flat, your pool is too small. If work time is climbing, the dependency is degrading. That distinction tells you whether to change your config or page someone else, and having it in a dashboard turns a 40-minute investigation into a 40-second one.

### Timeouts must cover the whole thing

```python
async with asyncio.timeout(5):
    result = await anyio.to_thread.run_sync(vendor.fetch, arg, limiter=lim)
```

⚠️ **The timeout cancels your coroutine, not the thread.** The thread keeps running to completion, still holding its slot. If the vendor hangs for 5 minutes, you have returned an error to the user but the slot is gone for 5 minutes. Threads in Python cannot be killed.

The real fix is a timeout **inside** the blocking call — most SDKs support one, and if yours does not, that is a strong argument for moving the work to a process pool (which you *can* kill) or a queue.

This is a genuine limitation, not a workaround you have missed. Say so in an interview and it lands well.

## Codebase

**Repo:** `agronholm/anyio` and the Python standard library

**Question to answer:** Trace what happens when 50 tasks call `anyio.to_thread.run_sync` at once with a limiter of 10. Where do the other 40 wait, in what order are they released, and how are worker threads reused rather than recreated?

**Read, in order:**

1. `anyio/to_thread.py` — the public API, short
2. `anyio/_backends/_asyncio.py` — find `WorkerThread` and `run_sync_in_worker_thread`. Look at the idle-thread reuse logic and the context propagation
3. `anyio/_core/_synchronization.py` — `CapacityLimiter`. Note the fairness of the wait queue
4. `concurrent/futures/thread.py` (stdlib) — the much simpler design. Compare: what does anyio add and why?
5. `concurrent/futures/process.py` (stdlib) — read `_queue_management_worker`. This is where pickling and worker lifecycle live. Also read what happens when a worker dies mid-task

**Bonus:** `Lib/asyncio/base_events.py` — `run_in_executor` and `set_default_executor`, to see how the loop's default pool is created lazily.

**Size:** 1 session.

**Part 1 — The matrix.** Three workloads × five strategies. Measure throughput, p99, memory, and CPU. Predict each cell before running it.

The interesting result: `gil_releasing_cpu` in a thread pool should beat a process pool, because you skip pickling. Most people expect the opposite.

**Part 2 — Bulkhead proof.** Build the FastAPI app twice. Version A: all blocking calls share the default pool. Version B: each dependency has its own limiter.

Use toxiproxy from [[00.4 - Setting Up Your Lab]] to make one dependency take 5 seconds. Load test both. In version A, unrelated endpoints should degrade badly. In version B, they should not move.

**Chart both.** This chart is one of the strongest things you can bring to a system design interview.

**Part 3 — The pickling wall.** Send progressively larger objects to a process pool: 1KB, 100KB, 10MB, 100MB. Chart total time versus actual compute time. Find the size at which serialization dominates. Then rewrite it to pass a path instead and show the difference.

**Part 4 — The bridge.** Write a fake SDK that calls your callback from its own thread. Get those events into the event loop correctly. Then deliberately do it wrong — call `queue.put_nowait` directly from the SDK thread — and demonstrate a failure under load.

**Part 5 — The timeout that does not.** Show that `asyncio.timeout` around a `to_thread` call returns control to you but leaves the thread running and the slot occupied. Prove it by exhausting the pool with calls that have all "timed out". Then implement the two real mitigations: a timeout inside the call, and a killable process pool.

**Part 6 — Instrument.** Add wait-time and work-time metrics to every pool. Build a Grafana panel. Run part 2 again and show the metrics identifying the problem before latency does.

**Done when:**
- The part 2 chart shows the bulkhead working, with numbers
- You know the pickling break-even size for your machine
- Part 5's pool is exhausted purely by "timed out" calls, and your fix prevents it
- Your dashboard distinguishes "pool too small" from "dependency slow" at a glance
