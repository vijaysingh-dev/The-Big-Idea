# Change Data Capture

#backend #streaming #databases

> **In one line:** Your database already keeps a durable, ordered log of every change — the WAL — and CDC turns that into an event stream you can consume, with no application code involved at all.

---

## The Idea

```
Application → Postgres → WAL → [ CDC ] → Kafka → consumers
                                  ▲
                          reads the replication stream
```

💡 **The insight: the write-ahead log is already an event log** ([[06.2 - Postgres Architecture]]). Every insert, update and delete is recorded there in commit order for replication and crash recovery. CDC decodes it into logical row changes and publishes them.

| Property | |
|---|---|
| **No application changes** | Nothing to remember, nothing to forget |
| **Commit order** | The WAL is written in commit order, not visibility order |
| **Captures everything** | Migrations, admin scripts, other services |
| **Cannot be bypassed** | Any write to the database produces an event |

⚠️ **That last property is the strongest argument for CDC over the outbox** ([[09.3 - The Outbox Pattern]]). An outbox row is only written by code that remembers to write it; a WAL record is written by the database.

---

## How It Works in Postgres

### Logical replication

```sql
ALTER SYSTEM SET wal_level = logical;      -- requires a restart

CREATE PUBLICATION conduit_cdc FOR TABLE documents, annotations, sources;

SELECT pg_create_logical_replication_slot('debezium', 'pgoutput');
```

| Component | |
|---|---|
| **`wal_level = logical`** | Adds the information needed to decode rows, not just pages |
| **Publication** | Which tables to capture |
| **Replication slot** | Tracks the consumer's position and **retains WAL until it is consumed** |
| **Output plugin** | Decodes WAL into a logical format. `pgoutput` is built in |

### Replica identity

```sql
ALTER TABLE documents REPLICA IDENTITY DEFAULT;   -- primary key only (default)
ALTER TABLE documents REPLICA IDENTITY FULL;      -- entire old row
```

⚠️ **With `DEFAULT`, an update event contains the new row and only the primary key of the old one.** If a consumer needs to know what changed, or needs the previous value, you need `FULL`.

💡 **`REPLICA IDENTITY FULL` roughly doubles WAL volume for updates**, because every update writes the complete old row. **Enable it per table, only where consumers need before-images** — a document's status transition might need it; an annotation's text does not.

⚠️ **A table with no primary key and `REPLICA IDENTITY DEFAULT` cannot be replicated at all** — updates and deletes fail. This surfaces as a Debezium error that is confusing until you know.

## Debezium

The standard implementation.

```json
{
  "name": "conduit-postgres",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.dbname": "conduit",
    "plugin.name": "pgoutput",
    "slot.name": "debezium",
    "publication.name": "conduit_cdc",
    "table.include.list": "public.documents,public.annotations",
    "topic.prefix": "conduit",
    "snapshot.mode": "initial",
    "heartbeat.interval.ms": "10000"
  }
}
```

### The event shape

```json
{
  "before": {"id": "doc_42", "status": "pending", "title": "Q3"},
  "after":  {"id": "doc_42", "status": "indexed", "title": "Q3"},
  "source": {
    "db": "conduit", "schema": "public", "table": "documents",
    "lsn": 24576123, "txId": 4291, "ts_ms": 1755439927500
  },
  "op": "u",
  "ts_ms": 1755439927600
}
```

| `op` | |
|---|---|
| `c` | create (insert) |
| `u` | update |
| `d` | delete — `after` is null |
| `r` | read (from the initial snapshot) |
| `t` | truncate |

💡 **`before` and `after` together are more information than an application event usually carries.** A consumer can compute exactly what changed without the producer having decided that in advance.

⚠️ **`before` is only populated with `REPLICA IDENTITY FULL`.** With `DEFAULT` it contains only the primary key, and a consumer expecting to diff will silently see nothing changed.

### The snapshot

```
snapshot.mode = initial       read the whole table, then stream  (default)
             = never          stream only from now
             = when_needed    snapshot if the slot position is lost
             = initial_only   snapshot then stop
```

⚠️ **The snapshot-to-stream transition is the subtle part.** Debezium takes a consistent snapshot at a specific LSN, then begins streaming from that LSN — so a row changed during the snapshot appears once as `r` and again as `u`, and nothing is lost or missed.

💡 **The correctness of that handoff is a large part of why you use Debezium rather than writing your own.** Getting it right involves an exported snapshot, a consistent read, and careful LSN bookkeeping.

⚠️ **An initial snapshot of a very large table holds a transaction open for its duration**, which blocks vacuum ([[06.7 - MVCC Vacuum and Bloat]]). For large tables use incremental snapshots, which Debezium supports via a signalling table and does in chunks.

## The Replication Slot Danger

⚠️ **The most important operational fact about CDC.**

```sql
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
```

**A slot guarantees the database retains WAL until the consumer has read it.** That guarantee is exactly what makes CDC reliable, and it is exactly what makes it dangerous.

| Failure | Consequence |
|---|---|
| Debezium down for an hour | An hour of WAL retained |
| Debezium down for a day | **Disk fills. The database stops** |
| Slot created and forgotten | WAL grows forever |
| **Vacuum cannot advance** | Bloat accumulates across the whole database |

```ini
max_slot_wal_keep_size = 100GB      # PG 13+
```

💡 **`max_slot_wal_keep_size` converts "the primary dies with a full disk" into "the CDC connector needs a re-snapshot".** The second is enormously preferable, and setting it is not optional ([[06.12 - Replication and Failover]]).

**Alert on any inactive slot, immediately.** This single alert prevents a whole class of outage.

### Heartbeats

⚠️ **A subtle version of the same problem:** if the captured tables receive no writes but *other* tables do, the slot's position does not advance, and WAL accumulates for changes the connector does not care about.

```json
"heartbeat.interval.ms": "10000",
"heartbeat.action.query": "INSERT INTO cdc_heartbeat (ts) VALUES (now())"
```

**The heartbeat writes to a captured table periodically**, so the slot advances even on a quiet system. **Configure it** — the failure without it looks exactly like a stuck connector.

## CDC versus the Outbox

The comparison that matters.

| | Outbox | CDC |
|---|---|---|
| Application changes | **Yes** — write outbox rows | **None** |
| Captures writes from anywhere | No — only instrumented code | **Yes** |
| Event shape | **You design it** | Database rows |
| Domain semantics | **Explicit** | Inferred from column changes |
| Ordering | Visibility order, needs care | **Commit order** |
| Latency | Poll interval, or NOTIFY | **Sub-second** |
| Infrastructure | A table plus a relay | **Kafka Connect plus a slot** |
| Coupling to schema | Loose | **Tight — consumers see your columns** |
| Operational risk | Low | **Slot retention** |

⚠️ **The schema coupling is the real cost of CDC.** A consumer reading `documents` row changes is coupled to your table structure. **Rename a column and you break every consumer**, and there is no schema negotiation because there was never a contract — only your table.

💡 **The distinction that resolves it: CDC is excellent for data synchronisation, and poor for domain events.**

| Use CDC for | Use the outbox for |
|---|---|
| Replicating to a search index | Domain events other services react to |
| Feeding an analytics warehouse | Events with business meaning |
| Cache invalidation | Events consumed by other teams |
| A read model or materialised view | Anything with a public contract |
| Auditing every change | |

**Conduit uses both**: CDC to keep the search index in sync with `documents`, and the outbox for `document.indexed` which the notification service consumes.

### The hybrid: CDC on the outbox table

```json
"transforms": "outbox",
"transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter"
```

💡 **Debezium reads the outbox table via CDC and routes rows to topics.** You get the outbox's designed event shape and domain semantics, **plus CDC's commit ordering and sub-second latency, with no polling relay to operate.**

**This is the strongest version of the pattern** ([[09.3 - The Outbox Pattern]]) and it is what mature event-driven systems converge on.

## In Production

### Monitoring

```python
cdc_slot_lag_bytes.set(lag)
cdc_slot_active.set(1 if active else 0)              # ← alert on 0
cdc_connector_state.set(state)
cdc_event_lag_seconds.set(now - source_ts_ms / 1000)
cdc_snapshot_progress_ratio.set(ratio)
```

| Alert | Condition |
|---|---|
| **Inactive slot** | Any. Immediately |
| **Slot lag** | > 10 GB, or your `max_slot_wal_keep_size` × 0.5 |
| Connector failed | Kafka Connect task state != RUNNING |
| Event lag | > 60 seconds |
| Snapshot running too long | Blocking vacuum |

⚠️ **The inactive slot alert is the one that prevents an outage.** Everything else is degradation; a forgotten slot is a database that stops accepting writes when the disk fills.

### Schema changes

```sql
ALTER TABLE documents ADD COLUMN indexed_at timestamptz;
```

Debezium detects it and includes the new column in subsequent events. **Adding a nullable column is safe.**

⚠️ **Renaming or dropping a column breaks consumers** with no warning — CDC has no schema negotiation, and the consumer simply stops finding the field.

💡 **Apply the expand/contract discipline to CDC-captured tables** ([[06.11 - Zero Downtime Migrations]]): add the new column, dual-write, migrate consumers, then drop. **The consumers are now part of your migration plan**, which is a real coupling cost.

**With a schema registry and Avro, breaking changes are caught at publish time** rather than at consumption ([[09.6 - Schema Registry and Compatibility]]).

### Deletes and tombstones

```json
{"before": {"id": "doc_42", ...}, "after": null, "op": "d"}
{"key": "doc_42", "value": null}          // ← tombstone, for compaction
```

Debezium emits a delete event followed by a tombstone.

⚠️ **Soft deletes are invisible to a consumer that does not know about them.** `deleted_at` being set is an `op: u`, and a consumer treating it as an ordinary update keeps the row in the search index ([[06.10 - Schema Design]]).

```json
"transforms.dropDeleted.type": "io.debezium.transforms.Filter",
"transforms.dropDeleted.condition": "value.after.deleted_at != null"
```

**Handle soft deletes explicitly**, either with a transform or in the consumer.

### Initial load of a large table

```
100 million rows, initial snapshot
→ hours of a held transaction
→ vacuum blocked for the duration
→ bloat across the entire database
```

💡 **Use incremental snapshots.** Debezium chunks the table and interleaves chunks with streaming, so no long transaction is held and the connector stays current with live changes throughout.

```sql
INSERT INTO debezium_signal (id, type, data)
VALUES (gen_random_uuid()::text, 'execute-snapshot',
        '{"data-collections": ["public.documents"]}');
```

⚠️ **A signalling table means Debezium needs write access to your database**, which some organisations resist. It is worth arguing for.

### Filtering and transforms

```json
"transforms": "unwrap,route",
"transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
"transforms.unwrap.drop.tombstones": "false",
"transforms.route.type": "org.apache.kafka.connect.transforms.RegexRouter",
"transforms.route.regex": "conduit.public.(.*)",
"transforms.route.replacement": "$1"
```

💡 **`ExtractNewRecordState` flattens the before/after envelope into just the row**, which is what most consumers want. **Keep the envelope only where a consumer genuinely needs the before-image.**

⚠️ **Do not do heavy transformation in Kafka Connect.** Single Message Transforms are for shape, not logic — routing, flattening, field masking. Business logic belongs in a consumer where it is testable.

### Personal data

```json
"transforms.mask.type": "org.apache.kafka.connect.transforms.MaskField$Value",
"transforms.mask.fields": "email,phone"
```

⚠️ **CDC captures everything in the table, including columns you did not think about.** A new column holding personal data flows into Kafka automatically, with the retention of that topic ([[09.2 - Event Modeling]]).

**Use column include-lists rather than exclude-lists**, so a new column is opt-in rather than automatically captured.

## Codebase

**Repo:** `debezium/debezium`, `postgres/postgres`

**Question to answer:** How does Debezium transition from the initial snapshot to streaming without missing or duplicating rows? Then: in Postgres, what does logical decoding actually do — how does a WAL record become a row change?

**Read, in order:**

1. `postgres/src/backend/replication/logical/decode.c` — **`LogicalDecodingProcessRecord`.** How a WAL record is turned into a logical change. **The answer to the second question**
2. `postgres/src/backend/replication/pgoutput/pgoutput.c` — the built-in output plugin, and how replica identity affects what is emitted
3. `debezium/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresSnapshotChangeEventSource.java` — **the snapshot.** Look for the exported snapshot and the LSN at which streaming begins. **The answer to the first question**
4. `debezium/debezium-connector-postgres/.../PostgresStreamingChangeEventSource.java` — the streaming loop and slot position management
5. `debezium/debezium-core/src/main/java/io/debezium/pipeline/source/snapshot/incremental/` — **incremental snapshots.** The chunking and watermarking that avoid a long-held transaction
6. `debezium/debezium-core/.../transforms/outbox/EventRouter.java` — the hybrid pattern

💡 The snapshot-to-stream handoff is the part worth understanding properly. **Debezium opens a repeatable-read transaction, records the LSN, reads the table, then streams from that exact LSN** — so a row modified during the snapshot appears in the snapshot with its old value and again in the stream with its new one. **The consumer's idempotent upsert makes that correct**, which is why CDC consumers must be idempotent ([[07.5 - Idempotency Keys and Deduplication]]).

**Size:** 2 sessions.

```
│   ├── rebuild.py        # drop the index, replay
│   └── RESULTS.md
└── README.md
```

**Part 1 — See the raw stream.** Postgres with logical replication, a publication and a slot.

Read raw changes with `pg_logical_slot_get_changes` before involving Debezium. **Annotate the output for an insert, an update and a delete.**

Then start Debezium and compare its envelope to the raw output.

**Part 2 — Replica identity, measured.** The same update workload with `DEFAULT` and `FULL`.

Measure: WAL bytes generated, event size, and whether `before` is populated.

**Report the WAL volume multiplier.** Then decide per Conduit table whether `FULL` is justified.

**Part 3 — The snapshot handoff.** A 10-million-row table, initial snapshot with concurrent writes.

**Instrument to detect any row missed or any row whose final state is wrong.** Then verify the `r` then `u` sequence for rows modified during the snapshot.

Measure vacuum impact: dead tuples that could not be removed during the snapshot, and bloat afterwards.

Then incremental snapshot, same table, same concurrent writes. **Measure the vacuum impact again** — it should be dramatically lower.

**Part 4 — The slot danger.** ⚠️ Throwaway instance only.

Stop the connector under sustained write load. Chart `pg_wal` directory size and slot lag over 30 minutes.

**Extrapolate to disk exhaustion.** Then set `max_slot_wal_keep_size` and confirm the slot is invalidated instead of the disk filling.

Then the quiet-table case: write heavily to an uncaptured table while the captured tables are idle. **Confirm the slot does not advance and WAL accumulates.** Then configure heartbeats and confirm it does.

**Part 5 — CDC versus outbox on ordering.** Two transactions where the lower `bigserial` commits later ([[09.3 - The Outbox Pattern]]).

Publish via a polling outbox relay and via CDC. **Confirm the relay publishes out of commit order and CDC does not.**

Then measure end-to-end latency for both, and the database load each imposes.

**Part 6 — Schema changes break consumers.** With a consumer running:

- Add a nullable column. **Confirm nothing breaks.**
- Rename a column. **Count consumer failures and measure time to detection.**
- Soft-delete a row. **Confirm the consumer treats it as an update and keeps it in the index.**

Then implement fixes: a filter transform for soft deletes, and expand/contract for the rename.

**Part 7 — Build the pipeline.** Postgres `documents` → CDC → Kafka → Elasticsearch, with an idempotent sink.

**Then the test that matters: drop the Elasticsearch index entirely and rebuild it by replaying from Kafka offset 0.**

Verify the result is identical to the source database — same document count, same content hashes.

Then do the same after a full re-snapshot, and confirm idempotency handles the duplicate `r` and `u` records.

**Done when:**
- You have annotated raw logical decoding output
- You know the WAL volume cost of `REPLICA IDENTITY FULL`
- Incremental snapshots demonstrably reduce vacuum impact versus initial
- You watched WAL grow with a stopped connector, and `max_slot_wal_keep_size` bounded it
- Heartbeats fixed the quiet-table slot problem
- CDC published in commit order where the outbox relay did not
- A column rename broke consumers, and you measured detection time
- Your search index rebuilds identically from Kafka offset 0
