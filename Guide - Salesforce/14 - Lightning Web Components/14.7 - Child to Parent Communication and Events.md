# Child to Parent Communication and Events

## Standard DOM events

LWC uses `CustomEvent` and `dispatchEvent` — browser APIs, not a framework construct.

```javascript
// claimRow.js
handleApprove() {
    this.dispatchEvent(new CustomEvent('claimapproved', {
        detail: {
            claimId: this.claim.Id,
            claimNumber: this.claim.Claim_Number__c
        }
    }));
}
```

```html
<c-claim-row claim={claim} onclaimapproved={handleClaimApproved}></c-claim-row>
```

```javascript
// parent
handleClaimApproved(event) {
    const { claimId, claimNumber } = event.detail;
    this.refreshList();
}
```

## The naming rule

**Event names must be lowercase, with no hyphens, no underscores, no camelCase.**

```javascript
// Correct
new CustomEvent('claimapproved')
new CustomEvent('rowselected')
new CustomEvent('filterchange')

// Broken — the handler will never fire
new CustomEvent('claimApproved')
new CustomEvent('claim-approved')
new CustomEvent('claim_approved')
```

The reason is HTML attribute case-insensitivity: `onclaimApproved` in markup is read as `onclaimapproved`, so a camelCase event name never matches its handler. It fails silently, which makes it a frustrating first bug.

For readability, some teams prefix by domain — `claimapproved`, `claimrejected`, `claimselected` — which keeps names distinct in a component with several event sources.

## The detail payload

```javascript
this.dispatchEvent(new CustomEvent('claimapproved', {
    detail: { claimId, approvedAmount, approvedBy }
}));
```

**Pass primitives, not object references.** Handing the parent an object the child still holds means both can mutate it, and neither knows when the other does.

```javascript
// Leaks a mutable reference to the child's state
detail: { claim: this.claim }

// Passes only what the parent needs
detail: { claimId: this.claim.Id, amount: this.claim.Claim_Amount__c }
```

Where a whole object genuinely must travel, send a copy:

```javascript
detail: { claim: { ...this.claim } }
```

In an Experience Cloud or Lightning Out context, `detail` is serialized, so anything non-serializable — a function, a DOM node — does not survive.

## Bubbling and composed

Two flags that determine how far an event travels, and the defaults matter.

```javascript
// Default: stops at the parent, does not cross the shadow boundary
new CustomEvent('claimapproved', { detail })

// Bubbles up the DOM, but stops at the shadow boundary
new CustomEvent('claimapproved', { detail, bubbles: true })

// Bubbles and crosses shadow boundaries — reaches anywhere
new CustomEvent('claimapproved', { detail, bubbles: true, composed: true })
```

| bubbles | composed | Reaches |
| --- | --- | --- |
| false | false | The immediate parent only — **the default and usually right** |
| true | false | Ancestors within the same shadow root |
| true | true | Everything up to the document |

**Default to `{ bubbles: false, composed: false }`.**

An event that only the parent hears keeps the component boundary meaningful. A `composed: true` event can be caught by anything on the page, which couples the component to consumers it does not know about, and makes refactoring risky.

The legitimate uses of `composed: true` are narrow: a deeply nested component needing to reach an ancestor several levels up, where threading the event through each intermediate parent would be worse. Even then, **Lightning Message Service is usually the better answer** — it is explicit about the channel rather than relying on DOM position. See [[14.8 - Lightning Message Service]].

## Re-dispatching through intermediates

With the default flags, an event from a grandchild does not reach a grandparent. The intermediate component re-dispatches:

```javascript
// claimList.js — the intermediate
handleRowApproved(event) {
    // re-dispatching keeps each level's contract explicit
    this.dispatchEvent(new CustomEvent('claimapproved', {
        detail: event.detail
    }));
}
```

More verbose than a composed event, and it means each component's public event surface is documented by its own code rather than inherited from a descendant.

Where several levels of re-dispatch become tedious, that is the signal to use LMS rather than to reach for `composed: true`.

## Reading the event target

```javascript
handleApprove(event) {
    // currentTarget is the element with the handler; target is what was clicked
    const claimId = event.currentTarget.dataset.claimId;
}
```

**`event.target`** is the element that originated the event, which inside a base component may be something you did not write.

**`event.currentTarget`** is the element the handler is attached to, which is what you usually want.

For a list, `data-` attributes identify the item:

```html
<template for:each={claims} for:item="claim">
    <lightning-button key={claim.Id}
                      label="Approve"
                      data-claim-id={claim.Id}
                      onclick={handleApprove}>
    </lightning-button>
</template>
```

```javascript
handleApprove(event) {
    const claimId = event.target.dataset.claimId;
}
```

`data-claim-id` becomes `dataset.claimId`.

## Base component events

Base components dispatch their own events, and their payloads follow a convention:

```javascript
handleInputChange(event) {
    const value = event.target.value;        // lightning-input
    const detail = event.detail.value;       // lightning-combobox
    const checked = event.target.checked;    // checkbox
}
```

The inconsistency is real: some base components put the value on `event.target`, others on `event.detail`. The component reference is the authority, and checking it rather than guessing saves time.

`lightning-datatable` dispatches `rowaction`, `rowselection`, and `save`, each with its own payload shape. See [[14.13 - Base Components and lightning-datatable]].

## Platform events dispatched to the framework

Some events are dispatched to the component and handled by the platform rather than by a parent.

```javascript
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

this.dispatchEvent(new ShowToastEvent({
    title: 'Claim approved',
    message: 'Claim {0} has been approved',
    messageData: [this.claim.Claim_Number__c],
    variant: 'success',
    mode: 'dismissable'
}));
```

`ShowToastEvent` bubbles and is composed by construction, so it reaches the platform's handler regardless of where the component sits.

**Toasts do not work in every context** — they are unavailable in Experience Cloud in some configurations, and in flow screens. A component that must work in both needs a fallback. See [[14.16 - Error Handling and Toasts]].

## Preventing default and stopping propagation

```javascript
handleSubmit(event) {
    event.preventDefault();     // stop the browser's default behaviour
    event.stopPropagation();    // stop the event travelling further
}
```

`preventDefault` matters for form submission and anchor navigation. `stopPropagation` is occasionally needed when a nested clickable element would otherwise trigger its container's handler:

```javascript
handleRowActionClick(event) {
    // stops the row's own click handler firing when a button inside it is clicked
    event.stopPropagation();
    this.approve(event.target.dataset.claimId);
}
```

## A worked example

A row component with several outward events, and a list coordinating them:

```javascript
// claimRow.js
import { LightningElement, api } from 'lwc';

export default class ClaimRow extends LightningElement {
    @api claim;
    @api showActions = false;

    handleApprove() {
        this.notify('claimapproved');
    }

    handleReject() {
        this.notify('claimrejected');
    }

    handleSelect() {
        this.notify('claimselected');
    }

    notify(eventName) {
        // one dispatch helper keeps the payload shape consistent across events
        this.dispatchEvent(new CustomEvent(eventName, {
            detail: {
                claimId: this.claim.Id,
                claimNumber: this.claim.Claim_Number__c,
                amount: this.claim.Claim_Amount__c
            }
        }));
    }
}
```

```javascript
// claimList.js
export default class ClaimList extends LightningElement {
    @api claims;

    handleApproved(event) {
        this.processDecision(event.detail.claimId, 'Approved');
    }

    handleRejected(event) {
        this.processDecision(event.detail.claimId, 'Rejected');
    }

    handleSelected(event) {
        this.selectedClaimId = event.detail.claimId;
        this.dispatchEvent(new CustomEvent('selectionchange', {
            detail: { claimId: event.detail.claimId }
        }));
    }
}
```

```html
<template for:each={claims} for:item="claim">
    <c-claim-row key={claim.Id}
                 claim={claim}
                 show-actions
                 onclaimapproved={handleApproved}
                 onclaimrejected={handleRejected}
                 onclaimselected={handleSelected}>
    </c-claim-row>
</template>
```

Each level has an explicit event contract, and no component reaches past its immediate neighbour.

## Documenting the event surface

A component's events are part of its public interface, and nothing enforces documenting them.

```javascript
/**
 * Displays a single warranty claim.
 *
 * @fires claimapproved  { claimId, claimNumber, amount }
 * @fires claimrejected  { claimId, claimNumber, amount }
 * @fires claimselected  { claimId, claimNumber, amount }
 */
export default class ClaimRow extends LightningElement { }
```

Without this, the only way to know what a component emits is to read every `dispatchEvent` in it. For a shared component used across several features, that comment is the difference between reusable and rediscovered.

## Practical guidance

**Lowercase event names**, always. camelCase fails silently.

**Default to `bubbles: false, composed: false`.**

**Pass primitives in `detail`**, not object references.

**Re-dispatch through intermediates** rather than reaching for `composed: true`.

**Use LMS when an event needs to cross unrelated parts of the page.**

**Use `currentTarget`** unless you specifically want the originating element.

**Identify list items with `data-` attributes.**

**Check the component reference** for base component event payload shapes — they are inconsistent.

**Document the event surface** in a class comment.
