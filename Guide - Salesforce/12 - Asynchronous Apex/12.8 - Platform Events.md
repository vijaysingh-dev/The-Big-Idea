# Platform Events

## What they are

A platform event is a message published to an event bus and delivered to any number of subscribers. The publisher does not know or care who is listening.

That decoupling is the point. Everything else in section 12 is "run this code later". Platform events are "announce that something happened, and let whoever cares respond".

Events are defined like objects, with the `__e` suffix:

```
Object: Claim_Approved__e
Fields:
    Claim_Id__c          Text(18)
    Claim_Number__c      Text(30)
    Approved_Amount__c   Number(16,2)
    Approved_By__c       Text(18)
    Approved_At__c       DateTime
Publish Behavior: Publish After Commit
```

## Publishing

```java
List<Claim_Approved__e> events = new List<Claim_Approved__e>();

for (Warranty_Claim__c claim : newlyApproved) {
    events.add(new Claim_Approved__e(
        Claim_Id__c = claim.Id,
        Claim_Number__c = claim.Claim_Number__c,
        Approved_Amount__c = claim.Approved_Amount__c,
        Approved_By__c = UserInfo.getUserId(),
        Approved_At__c = Datetime.now()
    ));
}

List<Database.SaveResult> results = EventBus.publish(events);

for (Database.SaveResult result : results) {
    if (!result.isSuccess()) {
        for (Database.Error err : result.getErrors()) {
            System.debug('Publish failed: ' + err.getMessage());
        }
    }
}
```

`EventBus.publish` takes a list, returns `SaveResult` per event, and counts as **one DML statement** regardless of the number of events.

## The two publish behaviours

This is the most consequential setting on a platform event, and it is chosen when the event is created.

**Publish After Commit.** The event is delivered only if the transaction commits successfully. A rollback means no event.

Right for business events. A claim-approved event should not fire if the approval was rolled back.

**Publish Immediately.** The event is delivered as soon as `publish` is called, **even if the transaction later rolls back.**

Right for logging and error reporting. This is the property that makes platform events the recommended mechanism for recording a failure that rolls back its own transaction — a fault path in a flow, a catch block in a trigger.

```java
try {
    processClaims(claims);
} catch (Exception e) {
    // published immediately, so it survives the rollback that follows
    EventBus.publish(new Automation_Error__e(
        Context__c = 'ClaimProcessing',
        Message__c = e.getMessage(),
        Stack_Trace__c = e.getStackTraceString()
    ));
    throw e;
}
```

See [[09.10 - Exception Handling and Custom Exceptions]] and [[20.5 - Custom Logging Frameworks]].

## Subscribing in Apex

A trigger on the event, and only `after insert` exists:

```java
trigger ClaimApprovedTrigger on Claim_Approved__e (after insert) {
    ClaimApprovedHandler.handle(Trigger.new);
}
```

```java
public with sharing class ClaimApprovedHandler {

    public static void handle(List<Claim_Approved__e> events) {
        Set<Id> claimIds = new Set<Id>();
        for (Claim_Approved__e event : events) {
            claimIds.add(event.Claim_Id__c);
        }

        try {
            ErpNotificationService.notify(claimIds);
            SlackNotificationService.postApprovals(events);
        } catch (Exception e) {
            // setResumeCheckpoint tells the bus to retry from this event rather than
            // reprocessing the whole batch
            EventBus.TriggerContext.currentContext().setResumeCheckpoint(
                events[0].ReplayId
            );
            throw e;
        }
    }
}
```

The subscriber runs **asynchronously, in its own transaction**, with its own limits. It can make callouts, which is why events are a clean way to move integration work out of a save.

## The behaviours that matter

**Runs as the Automated Process user by default.** Not the publishing user. This affects sharing, field-level security, `UserInfo.getUserId()`, and which records the subscriber can see.

The running user can be changed per event trigger in Setup, and doing so deliberately is worth it when the subscriber needs specific access.

**Delivery is at-least-once.** A subscriber can receive the same event twice — after a retry, or after a platform-level redelivery. **Handlers must be idempotent.**

```java
// Idempotent: the upsert on an external key means a duplicate delivery updates rather than duplicates
List<Integration_Record__c> records = new List<Integration_Record__c>();
for (Claim_Approved__e event : events) {
    records.add(new Integration_Record__c(
        Event_Key__c = event.Claim_Id__c + '|' + event.Approved_At__c.getTime(),
        Claim__c = event.Claim_Id__c
    ));
}
Database.upsert(records, Integration_Record__c.Event_Key__c, false);
```

**Order is not guaranteed** across events, though events published in one `EventBus.publish` call are delivered in order.

**Events are not stored as records.** They live in the bus for a retention window — 72 hours for high-volume events — and are then gone. They cannot be queried with SOQL after publishing.

**No `Id` in the usual sense.** Events have a `ReplayId` and an `EventUuid`, used for replay and deduplication.

## Retry and the checkpoint

A subscriber trigger that throws is retried, up to a limited number of times. Without a checkpoint, the **entire batch** of events is reprocessed — including the ones that succeeded.

`setResumeCheckpoint` marks the position to resume from:

```java
public static void handle(List<Claim_Approved__e> events) {
    for (Claim_Approved__e event : events) {
        try {
            process(event);
        } catch (Exception e) {
            // resume from this event on retry, so earlier successes are not repeated
            EventBus.TriggerContext.currentContext().setResumeCheckpoint(event.ReplayId);
            logFailure(event, e);
            return;
        }
    }
}
```

`EventBus.TriggerContext.currentContext().retries` gives the current retry count, which is how a handler gives up after a threshold rather than retrying indefinitely.

After the retry limit, the event is discarded. If that matters, the handler must record the failure somewhere durable before giving up.

## Subscribing outside Apex

**Flows.** A platform event-triggered flow, which is the declarative subscriber. See [[07.6 - Scheduled and Autolaunched Flows]].

**Lightning components**, using the `empApi` module, which is how a component reacts to a server-side event in real time:

```javascript
import { LightningElement } from 'lwc';
import { subscribe, unsubscribe, onError } from 'lightning/empApi';

export default class ClaimApprovalMonitor extends LightningElement {
    subscription = {};
    channelName = '/event/Claim_Approved__e';

    connectedCallback() {
        subscribe(this.channelName, -1, (response) => {
            this.handleApproval(response.data.payload);
        }).then((sub) => {
            this.subscription = sub;
        });

        onError((error) => {
            console.error('Event subscription error', error);
        });
    }

    disconnectedCallback() {
        unsubscribe(this.subscription);
    }
}
```

The `-1` replay Id means "from now on". `-2` means "everything retained".

**External systems**, through the Pub/Sub API over gRPC, or the older Streaming API. This is how an external service subscribes to Salesforce events without polling. See [[13.9 - Pub-Sub API and Event Relay]].

## Where events earn their place

**Decoupling a trigger from its consequences.** A claim approval publishes one event; the ERP notification, the Slack post, and the audit log are three independent subscribers. Adding a fourth consumer requires no change to the publisher.

**Moving callouts out of a save.** The subscriber runs in its own transaction where callouts are permitted.

**Logging that survives rollback**, using immediate publish.

**Real-time UI updates** without polling.

**Integration with external systems**, replacing outbound messages.

**Serializing contended work.** Publishing from many transactions and processing in one subscriber removes lock contention on a shared resource — an alternative to `FOR UPDATE` on a counter. See [[08.6 - FOR UPDATE and Record Locking]].

## Where they are the wrong tool

**When you need the result.** The publisher gets no response. If the caller must know the outcome, use a Queueable and check the job, or do the work synchronously.

**When order matters strictly.** Delivery order is not guaranteed across publish calls.

**When the work must happen exactly once.** At-least-once delivery means designing for duplicates regardless.

**For high-volume record replication.** Change Data Capture is purpose-built for that. See [[12.9 - Change Data Capture]].

**When a Queueable would do.** A single consumer, in the same org, with no need for decoupling, is simpler as a Queueable. Events add a definition, a trigger, and a debugging indirection that is only worth it when the decoupling has value.

## Limits

- **Standard-volume events** are effectively retired; **high-volume events** are the current model
- **Daily publish allocation** based on edition, plus purchasable add-ons
- **Daily delivery allocation** to CometD and Pub/Sub subscribers, counted per subscriber
- **72-hour retention** in the bus
- Subscriber triggers process events in batches, with a configurable batch size
- Publishing counts as **one DML statement** per call

The delivery allocation is the one that surprises orgs — it counts per external subscriber, so five systems subscribing to the same event consume five deliveries.

## Debugging

Events are harder to debug than synchronous code, because the publisher and subscriber are separate transactions.

**Correlate with a key.** Including a correlation Id in the event payload lets you trace a business operation across both logs.

```java
String correlationId = String.valueOf(Crypto.getRandomLong());

EventBus.publish(new Claim_Approved__e(
    Claim_Id__c = claim.Id,
    Correlation_Id__c = correlationId
));
```

**Debug logs on the Automated Process user** capture subscriber execution. Setting a trace flag on that user is how you see what the subscriber did.

**`EventBusSubscriber`** shows subscriber position and any lag:

```sql
SELECT Topic, Type, Position, Tip, Status, ExternalId
FROM EventBusSubscriber
WHERE Topic = 'Claim_Approved__e'
```

A `Position` falling well behind `Tip` means the subscriber is not keeping up, which is the signal that batch size or subscriber performance needs attention.

## Testing

```java
@IsTest
static void approvalPublishesEventAndSubscriberNotifiesErp() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock());
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    claim.Status__c = 'Approved';
    update claim;

    // events do not deliver until this is called
    Test.getEventBus().deliver();
    Test.stopTest();

    Warranty_Claim__c refreshed = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c,
        'The subscriber should have run and updated the claim');
}
```

**`Test.getEventBus().deliver()` is required.** Without it, events are published but subscribers never run, and the test passes while proving nothing about the subscriber.

Calling `deliver()` more than once, in a loop, is how a chain of events triggering further events is tested.

See [[19.6 - Testing Async Apex]].

## Practical guidance

**Choose the publish behaviour deliberately.** After Commit for business events, Immediately for logging.

**Make every subscriber idempotent.** At-least-once delivery is a certainty, not a risk.

**Use `setResumeCheckpoint`** so a retry does not reprocess successful events.

**Include a correlation Id** for cross-transaction debugging.

**Set a trace flag on the Automated Process user** when debugging a subscriber.

**Call `Test.getEventBus().deliver()`** in tests, or the subscriber never runs.

**Do not use an event where a Queueable would do.** Decoupling has a cost, and it should buy something.
