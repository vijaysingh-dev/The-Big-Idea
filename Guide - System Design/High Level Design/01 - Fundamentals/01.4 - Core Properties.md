# Core System Properties

> **Revision tags:** #fundamentals #nfr

## Scalability

**What it is:** The system's ability to handle increasing load by adding resources.

**Two axes:**
- **Vertical (scale up):** Add more CPU/RAM to an existing machine. Simple but has a hard ceiling and is expensive.
- **Horizontal (scale out):** Add more machines. Complex (requires statelessness or partitioning) but theoretically unlimited.

**Dimensions of scale:**
- **Read scalability:** More replicas, CDN, caching
- **Write scalability:** Sharding, partitioning, write-optimized stores
- **Storage scalability:** Distributed file systems, object storage
- **Compute scalability:** Horizontal service instances behind a load balancer

**Trap:** Scalability is not the same as performance. A slow system can be scalable (it just needs more machines). An unscalable system has a design bottleneck that no amount of hardware fixes.

> See [[01.8 - Scaling Strategies]] for depth.

## Availability

**What it is:** The percentage of time a system is operational and can serve requests.

```
Availability = Uptime / (Uptime + Downtime)
```

**Common SLAs:**

| Nines | Availability | Annual Downtime |
|---|---|---|
| 99% ("two nines") | 99% | ~87.6 hours |
| 99.9% ("three nines") | 99.9% | ~8.7 hours |
| 99.99% ("four nines") | 99.99% | ~52 minutes |
| 99.999% ("five nines") | 99.999% | ~5 minutes |

**How to achieve high availability:**
- Eliminate single points of failure (SPOF)
- Add redundancy at every layer
- Implement health checks and automatic failover
- Use multi-AZ or multi-region deployments

**Availability of composed systems:**  
If Service A = 99.9% and Service B = 99.9%, then A→B = 99.9% × 99.9% = **99.8%**. Chained dependencies reduce availability. This is why graceful degradation matters.

## Reliability

**What it is:** The system produces correct results and doesn't lose or corrupt data, even under load or during failures.

Reliability ≠ Availability.  
A system can be *available* (responding) but *unreliable* (returning wrong data or dropping writes).

**Reliability mechanisms:**
- Checksums and data validation
- Write-ahead logs (WAL) in databases
- Idempotent operations
- End-to-end acknowledgment
- Retry with deduplication

---

## Durability

**What it is:** Once data is written and acknowledged, it is not lost — not even if machines crash, disks fail, or the datacenter burns down.

**Durability tiers:**
- In-memory only (Redis default, no durability)
- Single-disk write (durable unless disk fails)
- Replicated (durable unless all replicas fail simultaneously)
- Cross-region replicated (extremely durable)

**Example:** S3 advertises 11 nines of durability (99.999999999%) — meaning you'd expect to lose one file out of 100 billion per year.

## Latency

**What it is:** The time between a request being sent and a response being received for a *single request*.

**Key percentiles:**
- **p50 (median):** 50% of requests are faster than this
- **p95:** 95% of requests are faster
- **p99:** 99% of requests are faster — the "tail latency"
- **p999:** The worst 0.1% — critical for SLA compliance

**Why tail latency matters:** In a system with 100 microservice calls, a p99 = 100ms at each service means the combined p99 is much worse due to the "long tail" effect.

**Latency budget:** Senior engineers allocate a total latency budget (e.g., 200ms end-to-end) and reason about how each component consumes part of it.

**Typical values to remember:**
```
L1 cache:         ~1 ns
L2 cache:         ~4 ns
RAM access:       ~100 ns
SSD random read:  ~100 µs
HDD random read:  ~10 ms
Network (same DC): ~1 ms
Network (cross DC): ~10-100 ms
```

---

## Throughput

**What it is:** The number of requests/operations processed per unit of time across the system.

- **RPS:** Requests per second (for web services)
- **TPS:** Transactions per second (for databases)
- **MB/s:** For data pipelines

**Throughput vs latency:** They are related but independent. A system can have high throughput (processing many requests) with high latency (each request takes a long time). Batch systems are an example.

**Bottleneck identification:** Throughput is limited by the slowest component — the bottleneck. Classic bottlenecks: database writes, network I/O, CPU-bound processing.

---

## Fault Tolerance

**What it is:** The ability to continue operating correctly when one or more components fail.

**Failure types to design for:**
- Machine crash (process/OS failure)
- Disk failure (data loss)
- Network partition (nodes can't communicate)
- Cascading failure (overloaded downstream causes upstream failures)
- Byzantine failure (node sends wrong/corrupted data)

**Design approaches:**
- **Redundancy:** N+1 replicas so failure of one doesn't stop operation
- **Bulkheads:** Isolate failures to prevent cascade (separate thread pools, circuit breakers)
- **Timeouts:** Don't wait forever; fail fast
- **Fallbacks:** Return stale data, cached results, or degraded functionality

---

## Resilience

**What it is:** The ability to *recover* from failures quickly and return to normal operation.

Fault tolerance is about *surviving* failures. Resilience is about *recovering* from them.

**Key metrics:**
- **RTO (Recovery Time Objective):** Maximum acceptable downtime
- **RPO (Recovery Point Objective):** Maximum acceptable data loss

**Resilience mechanisms:**
- Automatic service restart (Kubernetes, systemd)
- Circuit breakers that stop cascading calls
- Chaos engineering (deliberately inject failures to test recovery)
- Graceful degradation (return partial results instead of hard failures)

---

## Maintainability

**What it is:** How easily can engineers change, debug, and operate the system over time?

Three dimensions (from Designing Data-Intensive Applications):

1. **Operability:** Can the ops team keep it running? Good logging, monitoring, runbooks.
2. **Simplicity:** Can new engineers understand it? Avoid accidental complexity.
3. **Evolvability:** Can it be changed without heroic effort? Clean interfaces, no tight coupling.

**Maintainability traps in HLD:**
- Too many microservices = complex distributed debugging
- Shared databases between services = coupling
- No observability = undetectable failures

---

## Summary — The NFR Hierarchy

```
              Correctness (it does what it should)
                    ↑
              Reliability (results are right, data is safe)
                    ↑
              Durability (data survives failures)
                    ↑
         Fault Tolerance + Availability (keeps running)
                    ↑
              Resilience (recovers quickly)
                    ↑
         Scalability + Performance (handles growth)
                    ↑
              Maintainability (survives time)
```

You can't have the higher layers without the lower layers being solid.
