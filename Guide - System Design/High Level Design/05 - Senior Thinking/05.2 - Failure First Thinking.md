# Failure-First Thinking

> **Revision tags:** #senior-thinking #resilience #failure  
> **Related:** [[02.5 - Failure and Resilience]] | [[05.3 - Design For Change]]

---

## What It Is

Failure-first thinking means designing from failure scenarios outward, rather than designing the happy path and hoping failure doesn't happen.

Junior engineers ask: "How does this work when everything is fine?"  
Senior engineers ask: "What happens when X fails? What about Y? And what if both fail at the same time?"

The goal is not pessimism. It's preventing the 3 AM PagerDuty call.

---

## The Failure Enumeration Exercise

For every component you add to a design, run through this checklist:

```
□ What happens when this component crashes?
□ What happens when it's slow (high latency)?
□ What happens when it returns wrong data?
□ What happens when the network between this and its dependencies fails?
□ What happens when it's overloaded?
□ What happens during deployment (rolling restart)?
□ What happens when its backing storage is corrupted?
□ What happens when a dependency it calls fails?
```

Not all of these apply to every component. The discipline is in asking the questions, not in having a perfect answer to each.

## Failure Categories and Their Mitigations

### Crash Failures

Component stops responding.

```
Mitigation:
  - Multiple instances (redundancy)
  - Health checks → remove unhealthy instances from load balancer
  - Auto-restart (Kubernetes, systemd)
  - Circuit breakers in callers to fail fast
```

### Latency Failures (The Dangerous One)

Component responds, but slowly. This is more dangerous than crash failures because:
- Callers don't fail fast — they wait
- Threads/connections accumulate waiting for slow responses
- Slow downstream service can bring down its callers (cascading)

```
Mitigation:
  - Timeouts on all outbound calls (mandatory)
  - Circuit breakers that trip after latency threshold
  - Bulkhead thread pools (isolate slow callers from others)
  - Async processing where possible (don't block on slow calls)
```

**Rule:** Every network call must have a timeout. No exceptions.

### Partial Failures

Some instances fail, but not all. Traffic routes to surviving instances.

```
Scenario: 3 DB replicas, 1 goes down
  - Load balancer health check detects failure
  - Traffic rerouted to remaining 2 replicas
  - They receive 50% more traffic → may become overloaded

Mitigation:
  - Capacity planning: surviving instances can absorb extra load
  - Auto-scaling to add capacity when instances fail
  - Read load shedding: drop low-priority reads during degraded state
```

### Data Corruption Failures

Incorrect data written or returned.

```
Scenario: Bug causes wrong price written to product catalog
  - Cache serves wrong price to millions of users
  - Hard to detect (no error — just wrong data)

Mitigation:
  - Data validation at write time
  - Checksums for critical data
  - Canary reads: compare new path to old path
  - Monitoring for data anomalies (price outside plausible range → alert)
  - Point-in-time backups for recovery
```

### Cascading Failures

One component's failure triggers failures in dependent components.

```
Classic cascade:
  Payment DB is slow
  → Payment Service threads blocked waiting for DB
  → Order Service calls Payment Service, waits, threads blocked
  → API Gateway calls Order Service, waits, threads blocked
  → Users see total system failure even for non-payment operations
```

**Prevention mechanisms:**

1. **Bulkheads:** Each downstream service gets its own thread pool.
   ```
   Order Service thread pools:
     payment-pool:    max 20 threads
     inventory-pool:  max 20 threads
     notification-pool: max 10 threads
   ```
   Payment slowness exhausts payment-pool but doesn't starve inventory calls.

2. **Circuit breakers:** Stop making calls to a failing service.
   ```
   After 50% error rate in 10s window:
     → Open circuit: reject all calls immediately (don't wait for timeout)
     → Return fallback: cached result, default value, or error
     → Try again in 30s (half-open state)
   ```

3. **Timeouts:** Don't let slow downstream hold threads indefinitely.
   ```
   All calls: connection_timeout=500ms, read_timeout=2000ms
   Never: no timeout
   ```

4. **Graceful degradation:** Return partial results rather than failing.
   ```
   If recommendation service is down:
     → Return empty recommendations (don't fail the page)
   If search service is down:
     → Return "search unavailable" message (don't fail the homepage)
   ```

## The Blast Radius Mindset

Every design decision should include: "If this fails, who is affected?"

**High blast radius (bad):** Single shared database for all services → one DB issue affects everything.

**Low blast radius (good):** Per-service databases + per-service circuit breakers → payment DB issue only affects payment flows.

```
Ask for every failure scenario:
  - What % of users are affected?
  - What % of features are affected?
  - Is it detectable immediately?
  - How do we recover?
```

**Cell-based architecture:** Divide the system into independent cells (by user shard, geography, or product line). A failure in Cell A doesn't affect Cell B.

## Designing for Observability of Failure

You can't fix what you can't see.

**Every failure mode should have a corresponding alert:**
```
Component fail → alert within 2 minutes
Latency spike  → alert when p99 > SLO threshold
Error rate     → alert when error budget burn rate > 10×
Data anomaly   → alert on outlier values (price = $0, quantity = -1)
```

**Failure drills:** Don't wait for failures to happen. Cause them intentionally:
- Chaos engineering: randomly kill instances, inject latency, disconnect dependencies
- Gameday exercises: simulate a major failure scenario, practice the response
- Load testing: find the breaking point before production finds it for you

## The Pre-Mortem

Before launching a new system, run a pre-mortem: "It's 6 months from now. The system has completely failed. What went wrong?"

This surfaces failure modes that post-mortems find too late.

**Questions to ask:**
- What's the most likely single point of failure?
- What's the failure mode that would take longest to detect?
- What's the failure that would be hardest to recover from?
- What could cause data loss (not just downtime)?

For each: add a mitigation before launch.

## Common Failure-First Gaps in HLD Interviews

| What candidates skip | What should be there |
|---|---|
| What if the cache fails? | "Cache-aside handles this — fall through to DB. If Redis is down, we accept DB load." |
| What if the message queue is full? | "Producer gets backpressure error → client retries with backoff" |
| What if the DB primary fails? | "Replica promotion via Patroni, ~30s failover, clients reconnect" |
| What if a deploy breaks things? | "Rolling deploy, canary at 1%, feature flags for instant rollback" |
| What if the third-party API is down? | "Circuit breaker trips, serve cached/default response, alert on-call" |
