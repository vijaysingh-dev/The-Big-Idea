# useEffect and the Dependency Array

`useEffect` synchronizes a component with an **external system** — the DOM, a subscription, a network connection, a timer, a third-party widget. It is not "run after render" and it is not a lifecycle hook ([[16.9 - Lifecycle in the Hooks Era]]).

```jsx
useEffect(setup, dependencies);
```

## The three forms

```jsx
useEffect(() => {});           // after every render
useEffect(() => {}, []);       // after mount only
useEffect(() => {}, [a, b]);   // when a or b changes (by Object.is)
```

The third form is the normal case. The other two are usually either a mistake or a deliberate escape hatch.

## Cleanup

```jsx
useEffect(() => {
  const connection = connect(roomId);
  return () => connection.disconnect();
}, [roomId]);
```

The returned function runs **before the next effect** and on unmount. Not after — before. So when `roomId` changes:

```
disconnect(old room) → connect(new room)
```

Setup and teardown sitting in one block is the main structural improvement over class lifecycles: they cannot drift apart, and every dependency change is handled correctly without a manual `prevProps` comparison.

Every effect that creates something needs cleanup: subscriptions, timers, listeners, observers, connections, animation frames.

## Reading the dependency array correctly

The dependencies are not a configuration knob. They are a **declaration of what the effect reads**. The linter derives them mechanically:

```jsx
useEffect(() => {
  const conn = connect(serverUrl, roomId);
  conn.on("message", msg => onMessage(msg));
  return () => conn.disconnect();
}, [serverUrl, roomId, onMessage]);
```

Every reactive value used inside — props, state, context, and anything derived from them — must be listed. Values that are not reactive (module-level constants, `setState` functions, refs) do not.

Suppressing the linter is almost always wrong:

```jsx
// eslint-disable-next-line react-hooks/exhaustive-deps
```

That comment converts a visible dependency problem into an invisible stale-closure bug. The fix is to change the code so the dependency genuinely is not needed — which is what the rest of this note is about.

## Removing dependencies legitimately

**Use the updater form** so the effect does not read the state at all:

```jsx
// Depends on count — interval recreated every second
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);

// No dependency
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

**Move the value inside** if it can be computed there:

```jsx
// options is a new object every render
const options = { serverUrl, roomId };
useEffect(() => connect(options), [options]);   // reconnects every render

// Construct inside
useEffect(() => {
  const options = { serverUrl, roomId };
  return connect(options).disconnect;
}, [serverUrl, roomId]);
```

Object and function dependencies are the most common cause of effects firing every render, because a new literal has a new identity each time ([[19.1 - What Causes Re-renders]]).

**Move the function inside**, or memoize it with `useCallback` if it must be shared ([[17.7 - useCallback]]).

**Split the effect** when it does two unrelated things:

```jsx
// One effect, two concerns — reconnects when the theme changes
useEffect(() => {
  connect(roomId);
  logVisit(userId);
}, [roomId, userId]);

// Two effects, correct dependencies each
useEffect(() => connect(roomId).disconnect, [roomId]);
useEffect(() => { logVisit(userId); }, [userId]);
```

Each effect should synchronize one thing. Two effects with different dependency sets is better than one with the union.

## Effect Events

For values an effect should **read but not react to** — the "latest props in a non-reactive way" problem:

```jsx
function Chat({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showToast("Connected!", theme);   // reads the latest theme
  });

  useEffect(() => {
    const conn = connect(roomId);
    conn.on("connected", onConnected);
    return () => conn.disconnect();
  }, [roomId]);   // theme is NOT a dependency
}
```

Without this, changing the theme reconnects the chat — clearly wrong, since the theme has nothing to do with the connection.

`useEffectEvent` is still experimental. The established workaround is a ref updated on every render:

```jsx
const themeRef = useRef(theme);
useEffect(() => { themeRef.current = theme; });
```

This is what most libraries use internally, and it is what `useEffectEvent` is designed to replace.

## Async effects

```jsx
// Invalid — an async function returns a promise, not a cleanup function
useEffect(async () => { ... }, []);

// Correct
useEffect(() => {
  const controller = new AbortController();

  (async () => {
    try {
      const res = await fetch(url, { signal: controller.signal });
      setData(await res.json());
    } catch (e) {
      if (e.name !== "AbortError") setError(e);
    }
  })();

  return () => controller.abort();
}, [url]);
```

The abort handles both unmount and the dependency-change race, where a slow earlier request resolves after a fast later one ([[04.6 - AbortController and Cancellation]]).

## Timing

```
render → DOM mutated → useLayoutEffect → paint → useEffect
```

Effects run **after paint**, asynchronously. `useLayoutEffect` runs before paint and blocks it ([[17.5 - useLayoutEffect vs useEffect]]).

Effects also run **child-first** — a child's effect fires before its parent's, because the child commits first. This surprises people writing a parent effect that expects a child's registration to already exist.

## Strict Mode

In development every effect runs `setup → cleanup → setup` on mount. This verifies the effect is safely re-runnable, which concurrent features require ([[18.7 - Strict Mode and Double Invocation]]).

If double-firing causes a visible bug, the effect is missing cleanup or is not idempotent. Do not add a ref guard — fix the effect.

## When not to use an effect

This deserves its own note ([[17.4 - useEffect Pitfalls]]), but the short version: if the effect is not talking to something outside React, it probably should not exist. Deriving values, transforming data, responding to user actions and resetting state on prop change all have better answers.

## How senior engineers actually use this

**They ask "what external system does this synchronize with".** If there is no answer, the effect is wrong.

**They never suppress `exhaustive-deps`.** They restructure until the dependency is genuinely unnecessary.

**They write cleanup first**, before the setup body, so it cannot be forgotten.

**They keep one concern per effect**, which keeps dependency arrays small and correct.

**They use a data library for server state** rather than effect-based fetching, because caching, deduplication and cancellation are all rebuilt badly otherwise.

## Common pitfalls

- `async` directly as the effect callback.
- Suppressing the dependency linter.
- `[]` used as "on mount" when the effect does depend on something.
- Object or function dependencies created inline, firing every render.
- Missing cleanup for timers, listeners and subscriptions.
- One effect handling two unrelated concerns.
- Reacting to a value that should only be read — reconnecting on a theme change.
- Assuming parent effects run before child effects.

## Interview angle

"When does useEffect run" and "what does the dependency array do" are the entry questions; the depth is in framing effects as synchronization rather than lifecycle. Explain that dependencies declare what the effect reads, that cleanup runs before the next effect rather than after, and that removing a dependency means restructuring rather than suppressing the lint rule. The updater-form trick for removing a state dependency from an interval is a compact, convincing example.
