# Component Lifecycle Hooks

## The sequence

```
constructor()          the instance is created
                       ↓
@api properties set    the parent's values arrive
                       ↓
connectedCallback()    inserted into the DOM
                       ↓
render()               optional, chooses a template
                       ↓
[ children go through the same sequence ]
                       ↓
renderedCallback()     the DOM exists
                       ↓
                       ... state changes ...
                       ↓
renderedCallback()     fires again on every rerender
                       ↓
disconnectedCallback() removed from the DOM
```

**Parents construct before children; children render before parents finish.** A parent's `renderedCallback` fires after its children have rendered, which is what makes it safe to query child elements there.

## constructor

```javascript
constructor() {
    super();   // must be first
    this.claims = [];
}
```

Rarely needed, and heavily constrained:

- **`super()` must be the first statement.**
- **`@api` properties are not set yet.** Reading `this.recordId` here gives undefined.
- **No DOM access.** `this.template.querySelector` returns null.
- **Do not dispatch events** — nothing is listening yet.

Field initializers handle most of what a constructor would do:

```javascript
claims = [];
isLoading = false;
```

## connectedCallback

The workhorse. Fires when the component is inserted into the DOM, with `@api` properties populated.

```javascript
connectedCallback() {
    this.subscribeToChannel();
    this.loadInitialData();
    window.addEventListener('resize', this.handleResize);
}
```

What belongs here: subscriptions, event listeners on `window` or `document`, imperative Apex calls, and any initialization needing the public properties.

What does not: DOM queries, because the template has not rendered.

**It can fire more than once.** A component moved in the DOM, or one inside a conditionally rendered branch that toggles, disconnects and reconnects. Anything set up here must be idempotent or paired with cleanup in `disconnectedCallback`.

```javascript
connectedCallback() {
    // guarding against a repeated connect avoids duplicate subscriptions
    if (this.subscription) {
        return;
    }
    this.subscribeToChannel();
}
```

## renderedCallback

Fires after every render, including the first.

```javascript
renderedCallback() {
    const input = this.template.querySelector('lightning-input');
    input?.focus();
}
```

This is where the DOM is available, and it is the hook most often misused.

**It fires on every rerender.** Any state change that touches the template calls it again. Work done here without a guard runs repeatedly.

```javascript
libraryLoaded = false;

renderedCallback() {
    if (this.libraryLoaded) {
        return;
    }
    this.libraryLoaded = true;

    loadScript(this, CHART_JS + '/chart.min.js')
        .then(() => this.initializeChart());
}
```

**Setting reactive state here causes an infinite loop.** Assigning to a field used in the template triggers a rerender, which calls `renderedCallback`, which assigns again.

```javascript
// Infinite loop
renderedCallback() {
    this.rowCount = this.template.querySelectorAll('.claim-row').length;
}
```

If a measurement must feed back into state, guard it so it happens once, or compare before assigning.

**Use it only when the DOM is genuinely needed:** focusing an input, measuring an element, initializing a third-party library, or calling an imperative method on a child component.

## render

Overriding it selects a template at runtime.

```javascript
import { LightningElement } from 'lwc';
import compactTemplate from './claimSummaryCompact.html';
import fullTemplate from './claimSummaryFull.html';

export default class ClaimSummary extends LightningElement {
    @api displayMode = 'full';

    render() {
        return this.displayMode === 'compact' ? compactTemplate : fullTemplate;
    }
}
```

Genuinely useful when the two layouts differ enough that `lwc:if` branches would be unreadable — a compact mobile view against a full desktop one, or a read-only view against an edit view.

Both templates live in the same bundle, and the component name file remains the default.

Overusing this produces components with four templates and unclear behaviour. Two is usually the practical ceiling.

## disconnectedCallback

Cleanup. Fires when the component is removed from the DOM.

```javascript
disconnectedCallback() {
    // unsubscribing prevents orphaned subscriptions accumulating as tabs open and close
    if (this.subscription) {
        unsubscribe(this.subscription, () => {});
        this.subscription = null;
    }

    window.removeEventListener('resize', this.handleResize);
    clearInterval(this.pollingIntervalId);
}
```

**Everything set up in `connectedCallback` should be torn down here.**

The consequences of skipping it are real and cumulative:

**Streaming subscriptions** leak. A console user opening and closing forty tabs accumulates forty subscriptions against the concurrent client limit. See [[13.8 - Streaming API and PushTopics]].

**Window listeners** leak, and fire against a component that no longer exists.

**Intervals and timeouts** keep running, sometimes calling Apex indefinitely.

In a console app, where components mount and unmount constantly as agents switch tabs, this is not a theoretical concern.

## errorCallback

The component-level error boundary.

```javascript
errorCallback(error, stack) {
    // catches errors thrown by descendant components, not by this one
    this.hasError = true;
    this.errorMessage = error.message;

    LoggingService.reportComponentError({
        component: 'claimDashboard',
        message: error.message,
        stack
    });
}
```

```html
<template lwc:if={hasError}>
    <div class="slds-notify slds-notify_alert slds-theme_error">
        <p>This section could not be loaded. {errorMessage}</p>
    </div>
</template>
<template lwc:else>
    <c-claim-list claims={claims}></c-claim-list>
</template>
```

**It catches errors from descendant components**, not from the component's own lifecycle hooks or handlers. A parent wrapping several children can prevent one failing child taking down the whole page.

This is underused. A dashboard with six child components, where one throwing blanks the entire dashboard, is a worse experience than one showing five components and an error panel.

## The wire timing question

Wires execute as part of initialization, and **their results usually arrive after `connectedCallback`**.

```javascript
@wire(getRecord, { recordId: '$recordId', fields: FIELDS })
claim;

connectedCallback() {
    // this.claim.data is almost certainly undefined here
    console.log(this.claim.data);
}
```

Code depending on wire data belongs in the wire handler itself, not in a lifecycle hook.

```javascript
@wire(getRecord, { recordId: '$recordId', fields: FIELDS })
wiredClaim({ data, error }) {
    if (data) {
        this.claimNumber = getFieldValue(data, CLAIM_NUMBER);
        this.initializeFromRecord(data);
    }
}
```

## A worked example

A component that subscribes to a platform event, loads data, focuses an input, and cleans up:

```javascript
import { LightningElement, api, wire } from 'lwc';
import { subscribe, unsubscribe, onError } from 'lightning/empApi';
import getClaims from '@salesforce/apex/ClaimController.getClaims';
import { refreshApex } from '@salesforce/apex';

export default class ClaimMonitor extends LightningElement {
    @api accountId;

    subscription;
    hasRenderedOnce = false;
    claimResult;

    @wire(getClaims, { accountId: '$accountId' })
    wiredClaims(result) {
        // keeping the whole result enables refreshApex later
        this.claimResult = result;
    }

    connectedCallback() {
        if (this.subscription) {
            return;
        }

        onError((error) => this.handleStreamingError(error));

        subscribe('/event/Claim_Approved__e', -1, () => {
            refreshApex(this.claimResult);
        }).then((response) => {
            this.subscription = response;
        });
    }

    renderedCallback() {
        if (this.hasRenderedOnce) {
            return;
        }
        this.hasRenderedOnce = true;
        this.template.querySelector('lightning-input')?.focus();
    }

    disconnectedCallback() {
        if (this.subscription) {
            unsubscribe(this.subscription, () => {});
            this.subscription = null;
        }
    }

    errorCallback(error, stack) {
        this.hasError = true;
        LoggingService.reportComponentError({ component: 'claimMonitor', error, stack });
    }
}
```

Every hook doing exactly what it should: subscription in connect, DOM work guarded in render, teardown in disconnect, and wire data handled in the wire.

## Hooks and testing

Jest tests exercise these hooks by attaching and detaching the element:

```javascript
it('unsubscribes when removed from the DOM', () => {
    const element = createElement('c-claim-monitor', { is: ClaimMonitor });
    document.body.appendChild(element);       // connectedCallback fires

    document.body.removeChild(element);       // disconnectedCallback fires

    expect(unsubscribe).toHaveBeenCalled();
});
```

Testing that cleanup happens is worth doing, because the failure mode — leaked subscriptions — is invisible in manual testing and appears only under sustained use. See [[14.18 - Jest Testing for LWC]].

## Practical guidance

**Use field initializers rather than a constructor.**

**`connectedCallback` for subscriptions, listeners, and imperative loads.**

**Guard `connectedCallback`** against firing twice.

**Guard `renderedCallback`** with a flag for one-time work.

**Never set reactive state unguarded in `renderedCallback`.**

**Tear down in `disconnectedCallback` everything set up in connect.**

**Handle wire data in the wire handler**, not in a lifecycle hook.

**Add `errorCallback` to container components**, so one failing child does not blank the page.
