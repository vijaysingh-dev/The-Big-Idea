# Closures

A **closure** is a function together with the lexical environment it was created in. When a function is defined inside another function and then outlives it, the inner function keeps the outer scope alive.

The one-line definition people memorize — "a function that remembers its outer variables" — is accurate but hides the mechanism. The mechanism is simply that [[02.2 - Lexical Scope]] fixes each function's outer-environment pointer at definition time, and the garbage collector cannot free an environment that is still referenced.

## The canonical example

```js
function makeCounter() {
  let count = 0;

  return {
    increment: () => ++count,
    decrement: () => --count,
    value: () => count,
  };
}

const counter = makeCounter();
counter.increment(); // 1
counter.increment(); // 2
counter.value();     // 2
counter.count;       // undefined — genuinely inaccessible
```

`makeCounter` returned long ago; its stack frame is gone. But its *environment* lives on the heap because three functions reference it. All three share the same `count` — closures capture the binding, not a snapshot of the value.

That sharing is the point and also the trap:

```js
function make() {
  let n = 0;
  return [() => n++, () => n];
}
const [inc, read] = make();
inc(); inc();
read(); // 2 — both closures see the same binding
```

## Every function is a closure

Strictly, any function that references a variable from an outer scope closes over it — including top-level functions closing over module scope. Engines optimize this: V8 only captures variables the inner function actually uses, not the whole parent scope. A function that references nothing outer has no closure allocation at all.

This matters practically. A callback that touches one small variable does not retain a large object that merely happens to be in the same scope — usually. The exception is that all closures created in the same scope share one context object in V8, so if *any* of them references a large variable, that variable stays alive for all of them. This is a real and non-obvious memory leak source ([[07.2 - Memory Leaks from Closures and Timers]]).

## The loop problem

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3
```

One `var i` binding, function-scoped, shared by all three callbacks. By the time they run, the loop has finished and `i` is 3.

Three fixes, in historical order:

```js
// IIFE captures the current value in a new scope
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j), 0);
  })(i);
}

// let creates a fresh binding per iteration
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

// bind fixes the argument
for (var i = 0; i < 3; i++) {
  setTimeout(console.log.bind(null, i), 0);
}
```

The `let` version works because the spec explicitly copies the loop variable into a new environment on each iteration. This is the single most-asked closure question in interviews.

## Closures in React

Hooks are built on closures, and the most common React bug is a **stale closure** — an effect or callback that captured an old value.

```js
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1); // captured count from the first render, always 0
  }, 1000);
  return () => clearInterval(id);
}, []); // empty deps, so this closure never updates
```

The interval callback closed over `count` at mount. Two correct fixes: use the functional updater `setCount(c => c + 1)`, which does not read the captured value, or include `count` in the dependency array so the effect re-creates its closure. This pattern recurs throughout [[17.4 - useEffect Pitfalls]].

Event handlers have the same shape. A handler registered once but reading state from an outer render sees that render's values forever.

## How senior engineers actually use this

**They use closures for encapsulation over class privacy.** A factory returning an object of functions gives truly private state with no `#` fields, no `this`, and no binding concerns. This is the foundation of most modern store libraries (Zustand's `create` is exactly this shape).

**They use closures to bind configuration once.** An API client factory closes over base URL, auth token getter and retry policy, so every call site gets a pre-configured function rather than passing options repeatedly. See [[02.4 - Closure Patterns in Production]].

**They treat "why is this value stale" as a closure question first.** In React and in any event-driven code, an unexpected old value almost always means a closure captured an earlier binding.

**They watch closures in long-lived callbacks.** Anything registered once and living for the page's lifetime — an interval, a global listener, a WebSocket handler — pins whatever it closed over. That is fine for a token, expensive for a 5 MB dataset.

## Common pitfalls

- Assuming closures capture values. They capture bindings; later mutations are visible.
- `var` in loops with async callbacks.
- Stale closures in React effects and handlers with incomplete dependency arrays.
- Retaining large objects inadvertently because a sibling closure in the same scope references them.
- Creating closures inside hot render paths and then wondering why memoized children still re-render — a new function identity every render defeats `React.memo` ([[19.2 - React.memo and Memoization Strategy]]).

## Interview angle

Expect "what is a closure", the `var` loop snippet, and often "implement `once`" or "implement a private counter". Define it mechanically — function plus its captured lexical environment, kept alive because the environment is still referenced — then show the loop fix and explain *why* `let` works, which is the part most candidates hand-wave. Mentioning stale closures in React connects the concept to real work.
