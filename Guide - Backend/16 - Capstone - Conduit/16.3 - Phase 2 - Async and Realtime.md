# Phase 2: Async and Realtime

#backend #project #capstone

> **In one line:** Move extraction out of the request path, discover that the user now has no idea what is happening, and build the progress mechanism that fixes it.

---

## The Problem Phase 1 Created

```
p99 latency:  4.2s with 10% large files
Capacity:     1,200 rps, collapsing to 400 with large uploads
Crash mid-upload → a document stuck in `pending` forever
```

💡 **You measured this.** Phase 2 fixes it, and **the measurement is what tells you the fix worked.**

⚠️ **Backgrounding the work creates three new problems**: the user cannot see progress, failures are invisible, and the work can now run twice ([[08.1 - Why Background Work Exists]]).

## What You Build

### The pipeline, staged

```
document.uploaded
  → extract_text      (10s)
    → chunk           (2s)
      → index         (3s)
```

⚠️ **Not one 15-second task.** A failure at the index stage that retries the whole chain redoes extraction ([[08.5 - Task Design Rules]]).

```python
@app.task(bind=True, acks_late=True, max_retries=5)
def extract_text(self, org_id: str, document_id: str):
    with tenant_context(org_id):
        doc = repo.get(document_id)
        if doc.status != "pending":
            return                                  # idempotent: already done
        text = extract(storage.get(doc.storage_key))
        repo.save_text(document_id, text)
        repo.set_status(document_id, "chunking")
    chunk_document.delay(org_id=org_id, document_id=document_id)
```

💡 **`org_id` as an explicit argument, and every query scoped.** A task that takes only a resource ID trusts its caller completely ([[14.6 - Multi Tenant Isolation]]).

**The status check at the top makes it idempotent** — a redelivered message does nothing.

### The status resource

```python
@app.post("/v1/documents")
async def upload(file: UploadFile, org: Organisation):
    doc = await service.create_pending(file, org)
    await enqueue_extraction(org.id, doc.id)
    return JSONResponse(202, {"id": doc.id, "status": "pending"},
                        headers={"Location": f"/v1/documents/{doc.id}"})
```

```json
{
  "id": "doc_01HQZX", "status": "chunking", "progress": 0.45,
  "stage": "chunking", "estimated_completion": "2026-08-17T14:35:00Z",
  "error": null
}
```

💡 **Modelling the operation as a resource gives you polling, progress, cancellation and an error location for free** ([[05.1 - REST Done Properly]]) — **it is just a row.**

### SSE for progress

```python
@app.get("/v1/documents/{doc_id}/events")
async def document_events(doc_id: str, request: Request, org: Organisation,
                          last_event_id: str | None = Header(None)):
    if not await service.can_read(org, doc_id):
        raise HTTPException(404)

    async def stream():
        if last_event_id:
            for event in await log.since(doc_id, last_event_id):
                yield sse(event)

        queue = await broker.subscribe(f"doc:{doc_id}")
        try:
            while True:
                try:
                    event = await asyncio.wait_for(queue.get(), timeout=15)
                    yield sse(event)
                except asyncio.TimeoutError:
                    yield ": heartbeat\n\n"
        finally:
            await broker.unsubscribe(queue)          # ⚠️ mandatory

    return EventSourceResponse(stream())
```

⚠️ **The `finally` is not optional.** Without it, every disconnected client leaks a broker subscription ([[04.3 - SSE in Production]]).

⚠️ **The heartbeat is not optional either.** Proxies close idle connections at 30–60 seconds, and the client cannot distinguish that from a stalled pipeline.

💡 **`Last-Event-ID` replay is what makes reconnection lossless.** Without it, a client that reconnects misses everything that happened in between — **including on every deploy** ([[04.2 - Server Sent Events]]).

### The backplane

```
Worker (pod A) → publishes progress → Redis pub/sub → SSE handler (pod B) → browser
```

⚠️ **In-process pub/sub works with one pod and silently breaks with two.** The worker publishing on pod A reaches nobody if the client's SSE connection is on pod B ([[04.6 - Scaling Long Lived Connections]]).

💡 **Redis pub/sub is fire-and-forget.** Pair it with the event log for replay — **pub/sub for liveness, the log for correctness.**

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Celery** | arq, Dramatiq, RQ | Mature, and you will read its source in [[15.4 - Reading the Celery Worker Loop]] |
| **Redis as broker** | RabbitMQ | Already deployed. ⚠️ Note `visibility_timeout` |
| **`acks_late=True`** | Default | At-least-once. Tasks must be idempotent ([[08.2 - Queue Semantics]]) |
| **Staged tasks** | One long task | Independent retry, visible progress |
| **SSE** | WebSocket, polling | One-way push. Reconnection is free ([[04.1 - Choosing a Realtime Transport]]) |
| **Status in Postgres** | Redis, Celery result backend | Durable, queryable, joinable |
| Chained via `.delay()` | Celery `chain` | Simpler failure semantics; explicit |

⚠️ **The Redis broker decision needs `visibility_timeout > longest task`**, or a slow extraction is delivered to a second worker while the first is still running ([[08.4 - Brokers and Result Backends]]).

## What Will Go Wrong

### Tasks vanish on deploy

⚠️ **`acks_late=False` is Celery's default**, and a `SIGKILL` mid-task loses it silently ([[15.4 - Reading the Celery Worker Loop]]).

**Measure it:** 1,000 tasks, kill the worker halfway, count completions.

### The visibility timeout duplicate

```
visibility_timeout = 3600 (default)
Extraction of a 200MB PDF = 90 minutes
→ two workers process the same document
```

💡 **Instrument the task with its worker ID** and you will see it. **This is the most common Celery-on-Redis production bug.**

### Prefetch starvation

⚠️ **Default `worker_prefetch_multiplier=4` with concurrency 8 reserves 32 messages per worker.** One worker takes a 90-minute extraction and 31 quick tasks sit behind it ([[08.7 - Routing Queues Priorities and Prefetch]]).

**Set it to 1. Measure the difference in tail completion time.**

### The SSE leak

```python
sse_connections_active.set(len(active))
broker_subscriptions.set(await broker.subscription_count())
```

⚠️ **Open 500 connections, kill the clients abruptly, and check both.** They must return to zero.

### The reconnect storm

⚠️ **A deploy disconnects every SSE client simultaneously, and they all reconnect at the same instant** ([[11.2 - Timeouts Retries and Jitter]]).

```javascript
const delay = Math.random() * Math.min(30000, 1000 * 2 ** attempt);
```

**Stagger the server-side close too.**

### Failure is now invisible

⚠️ **In phase 1 a failure was a 500 in your error rate. Now it is a log line nobody reads.**

```python
queue_oldest_message_age_seconds.labels(queue=...).set(age)
```

💡 **Alert on oldest-age, not depth.** 10,000 messages seconds old is healthy; 5 messages three hours old is broken ([[08.1 - Why Background Work Exists]]).

### The grace period

```
terminationGracePeriodSeconds: 30
Longest task: 90 seconds
→ every deploy abandons work
```

**Measure tasks redone per rollout, then fix it** ([[11.7 - Graceful Shutdown and Draining]]).

## Acceptance Criteria

```
□  p99 upload latency < 300ms regardless of file size
□  Capacity restored to phase-1 levels with 25% large files
□  Three pipeline stages, each independently retryable and idempotent
□  A crash at any point in any stage leaves a recoverable state
□  1,000 tasks, worker killed mid-run: zero lost, zero duplicated effects
□  visibility_timeout > longest task, verified by a 90-minute task
□  prefetch_multiplier=1, with the fairness improvement measured
□  SSE progress works across two pods via the backplane
□  Last-Event-ID replay: zero events lost across a forced disconnect
□  500 abrupt disconnects leave zero leaked subscriptions
□  Reconnect storm after a deploy is measurably flattened by jitter
□  Alerting on queue oldest-age, with a measured time-to-detection
□  Grace period > longest task; zero abandoned tasks per deploy
```

⚠️ **The fourth criterion is the hard one.** Test a crash at every point in every stage ([[07.5 - Idempotency Keys and Deduplication]]).

```
  → p99 was 4.2s with 10% large files. Now it is 240ms.
     Here is the chart

"How does the user know what is happening?"
  → A status resource, polled or streamed over SSE, backed by the same row

"What happens if a worker dies mid-extraction?"
  → acks_late means redelivery. The task is idempotent — it checks status
     first. Here is the crash-point matrix

"Why SSE rather than WebSocket?"
  → One-way push. Automatic reconnection, Last-Event-ID replay, no upgrade
     handshake, works through every proxy. We would need WebSocket only for
     client-to-server messages, which we do not have

"What is wrong with this system now?"
  → Every request hits Postgres. No caching. Search is a sequential scan
     above 100k documents. Phase 3
```

**Part 1 — Build the staged pipeline.** Three tasks, `acks_late=True`, idempotent by status check, `org_id` explicit, chained by explicit `.delay()`.

**Part 2 — The crash matrix.** For each stage, kill the worker at: before starting, mid-execution, after the effect before the status update, and after the status update.

**Twelve crash points. Restart and assert exactly-once effect at every one.**

⚠️ **The "mid-execution" points are the hard ones.** For the storage write and the index write specifically, confirm redelivery does not duplicate.

**Part 3 — Prove the latency fix.** Re-run phase 1's load test with 0%, 5%, 10% and 25% large files.

**Chart p99 upload latency for phase 1 and phase 2 on the same axes.**

**Then find the new capacity and name the new bottleneck** — it should have moved.

**Part 4 — The visibility timeout bug.** `visibility_timeout=60`, a task taking 90 seconds, worker ID logged.

**Confirm two workers process the same document.** Measure the overlap.

Then fix it and confirm. **Then compute the correct value from your p99 task duration plus headroom.**

**Part 5 — Prefetch fairness.** One 90-second extraction followed by 40 short tasks, two workers.

**Sweep `prefetch_multiplier`: 1, 2, 4, 8.** Chart total completion time and per-worker idle time.

**Report which is best for this workload and why the default is wrong for it.**

**Part 6 — SSE at scale, across pods.** Two pods, 500 SSE clients, ingestion running.

**Part 7 — The deploy storm.** 500 SSE clients, then a rolling deploy.

**Chart reconnections per second on the surviving pods**, with and without client jitter and staggered server close.

**Part 9 — Grace period.** Sweep `terminationGracePeriodSeconds`: 30, 60, 120, 180 with a 90-second task.

**Measure abandoned tasks and total rollout duration for 10 pods at each.**

**Then split the extraction stage into three shorter tasks and re-measure with a 30-second grace period.**

**Report both options with their tradeoffs.**
