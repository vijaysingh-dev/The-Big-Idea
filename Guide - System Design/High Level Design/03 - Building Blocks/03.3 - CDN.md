# Content Delivery Networks (CDN)

> **Revision tags:** #building-blocks #cdn #caching  
> **Related:** [[03.4 - Caching Systems]] | [[03.11 - Object Storage]]

---

## What It Is

A CDN is a geographically distributed network of servers (called **edge nodes** or **Points of Presence / PoPs**) that cache and serve content from locations close to end users.

```
Without CDN:
User in Mumbai ──────────────────────────→ Origin Server (Virginia)
                    ~200ms latency

With CDN:
User in Mumbai → Edge PoP (Mumbai) → Origin (Virginia, only on cache miss)
                    ~5ms latency      (one-time fetch, then cached)
```

---

## Why It Exists

- **Latency reduction:** Content served from a nearby PoP instead of a distant origin. Physics limits how fast data can travel — CDNs minimize distance.
- **Throughput relief:** Cached content is served from edge without hitting origin. Origin only receives cache misses (a small fraction of total traffic).
- **Availability:** If origin is slow or down, edge can serve stale cached content.
- **DDoS mitigation:** CDNs have massive capacity to absorb traffic floods at the edge before they reach origin.
- **Bandwidth cost savings:** Outbound bandwidth from edge PoPs (CDN) is cheaper than origin bandwidth at scale.

## Pull CDN vs Push CDN

### Pull CDN (Lazy caching)

On first request, edge fetches content from origin and caches it. Subsequent requests are served from cache until TTL expires.

```
Request 1: Cache miss → fetch from origin → cache at edge → serve
Request 2–N: Cache hit → serve from edge (no origin contact)
TTL expires: Next request becomes a cache miss again
```

**Pros:** Zero configuration for content deployment. Content is cached automatically when first requested.  
**Cons:** First request always goes to origin (cold start). Low-traffic content may never benefit from caching (expires before second request).

**Best for:** Large websites with many URLs, dynamic content that needs CDN occasionally, user-generated content.

### Push CDN (Eager caching)

You explicitly upload content to the CDN. Edge nodes serve from their storage — origin is not involved in serving.

```
Deployment pipeline → upload to CDN → CDN replicates to all PoPs
Request arrives → edge serves from local storage (no origin)
```

**Pros:** First request is fast (already cached everywhere). Full control over what's cached.  
**Cons:** Must upload everything upfront. Stale content if you forget to invalidate. Storage costs for everything pushed.

**Best for:** Known static assets (JS bundles, CSS, images with known URLs), software downloads, firmware updates.

## What Should (and Shouldn't) Be on a CDN

### Good CDN candidates

- Static assets: JavaScript bundles, CSS, fonts, images
- Videos and media files
- Software downloads
- API responses that are the same for all users (public product catalog, pricing)
- HTML pages with long cache TTLs (pre-rendered pages)

### Poor CDN candidates

- User-specific API responses (`GET /my/orders` — different per user)
- Responses containing auth tokens or session data
- Frequently changing data without cache control headers
- POST/PUT/DELETE requests (CDNs only cache GET/HEAD)

## Cache Invalidation

Getting content off the CDN is harder than putting it there.

### TTL-based expiry

Content expires after a set time (Cache-Control: max-age). Simple but inflexible — you can't remove content early without explicit invalidation.

```
Cache-Control: max-age=86400     # cache for 1 day
Cache-Control: max-age=31536000  # cache for 1 year (for versioned assets)
Cache-Control: no-store          # never cache
```

### Cache-busting (preferred for static assets)

Include a hash of the file content in the URL. When content changes, the URL changes → no invalidation needed — old URL simply stops being requested.

```
app.js        → bad (same URL, content changes → stale cache)
app.a3f9b2.js → good (URL changes when content changes → no cache conflict)
```

Modern build tools (Webpack, Vite) do this automatically.

### Explicit invalidation

Send a purge/invalidation API call to the CDN to remove specific URLs or patterns.

```
CloudFront: CreateInvalidation API call
  Paths: ["/index.html", "/api/products/*"]
```

**Cons:** Invalidation propagates to all PoPs with some delay (seconds to minutes). At high volume, invalidation API calls have rate limits and cost money (AWS charges per invalidation path after the first 1,000/month).

### Version prefix pattern

Prefix all assets with a version in the path. Deploy new version at new path, update references, let old version expire naturally.

```
/v1/app.js → /v2/app.js  (deploy new, update HTML to reference new)
```

## CDN and Dynamic Content

Modern CDNs do more than static file caching:

**Edge compute (Cloudflare Workers, Lambda@Edge):** Run code at the edge. Use for: auth at the edge, A/B testing, geo-routing, request modification.

**Dynamic caching with Vary headers:** Cache different versions of a response based on request attributes (language, device type, auth status).

```
Vary: Accept-Language
→ CDN caches separate versions for en-US, fr-FR, etc.
```

**Stale-while-revalidate:** Serve stale content immediately while refreshing in the background.
```
Cache-Control: max-age=60, stale-while-revalidate=600
→ Serve stale if content is under 10 min old, refresh in background
```

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Edge PoP goes offline | Requests for that region hit origin or next nearest PoP | CDN handles internally; minimal user impact |
| Cache stampede | TTL expires simultaneously for popular content → flood of origin requests | Stagger TTLs with jitter; use stale-while-revalidate |
| Wrong content cached | All users see wrong content | Cache-busting by URL; explicit invalidation for critical bugs |
| Origin goes down (pull CDN) | Cache misses fail; cache hits still work | Set long TTLs for critical content; serve stale on origin error |
| CDN provider outage | Entire CDN layer down | Fallback DNS to origin (at cost of origin load) |

## Real Production Examples

- **Cloudflare:** Most widely used; CDN + DDoS protection + edge compute + DNS. Free tier available.
- **AWS CloudFront:** Integrated with S3, EC2, ALB. Lambda@Edge for serverless at the edge.
- **Akamai:** Enterprise, oldest CDN. Used by major financial and media companies.
- **Fastly:** Real-time purging (< 150ms). Used by GitHub, Shopify, The New York Times.
- **Google Cloud CDN:** Integrated with GCP load balancers.

---

## Interview Expectations

- Always mention CDN for global, read-heavy, media-heavy systems
- Know pull vs push and when each is appropriate
- Know cache-busting as the solution for static asset versioning
- Know that CDNs cache at the edge, reducing origin load dramatically
- Mention CDN as the first line of defense for DDoS
