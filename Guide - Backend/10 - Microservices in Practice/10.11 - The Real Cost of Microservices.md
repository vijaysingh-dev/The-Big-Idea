# The Real Cost of Microservices

#backend #microservices #architecture

> **In one line:** Every note in section 10 described work that a monolith does not require — this note adds it up, so that "should we split" becomes an arithmetic question rather than a taste question.

---

## The Idea

Sections 10.1 through 10.10 each covered one consequence of splitting:

| Note | The cost it described |
|---|---|
| 10.1 | Transactions become sagas, joins become network calls |
| 10.2 | Boundaries must be discovered, and they are usually wrong first |
| 10.3 | Availability multiplies down through synchronous dependencies |
| 10.4 | Data must be duplicated, reconciled and rebuilt |
| 10.5 | Every cross-boundary operation needs compensation |
| 10.6 | An edge layer, and it becomes a single point of failure |
| 10.7 | Discovery, mTLS, retries — a mesh, or a library everyone must adopt |
| 10.8 | Configuration and secrets, multiplied per service |
| 10.9 | The test pyramid inverts; contract tests become load-bearing |
| 10.10 | Deploys must be compatible in both directions, per service |

💡 **None of those is optional.** They are the work that makes a distributed system function, and a team that splits without doing them has a distributed monolith that fails in more ways than the original.

**This note is the tally.**

---

## The Fixed Cost Per Service

```
CI/CD pipeline
Dockerfile and build
Deployment manifests, resource limits, probes, PDB
Monitoring dashboard
Alerts and runbook
On-call knowledge
Client library or generated stubs
Contract tests
Circuit breakers and timeouts on every caller
Trace propagation
Auth between services
Configuration and secret delivery
Database, backups, migrations
```

⚠️ **Thirteen things per service, and none of them shrink for a small service.** A service with 200 lines of business logic needs the same pipeline, dashboard and runbook as one with 20,000.

💡 **This is why the nanoservice is an anti-pattern** ([[10.2 - Finding Service Boundaries]]): the fixed cost dominates.

**A useful heuristic: a service should be big enough that someone would page for it alone.**

### The per-boundary cost

```
An API contract, and its evolution
Data ownership decisions, and any duplication
A saga for any operation that spans it
Reconciliation for duplicated data
Timeout budget allocation
Failure and degradation behaviour
```

⚠️ **Boundaries grow quadratically if every service talks to every other.** Four services fully connected is six boundaries; eight services is twenty-eight.

💡 **In practice a well-designed system is sparse**, and the boundary count is closer to `n` than to `n²`. **If your boundary count is approaching `n²`, the decomposition is wrong** — everything talks to everything and nothing is independent ([[10.2 - Finding Service Boundaries]]).

## The Costs That Are Not Obvious

### Latency compounds

```
Monolith:      one process, function calls          8 ms
4 services:    gateway → A → B → C                 28 ms
with retries:  one retry somewhere                 45 ms
```

⚠️ **Depth is the killer, not breadth** ([[10.3 - Communication Patterns]]). A chain of four adds four round trips; four in parallel adds one.

💡 **The latency budget must be allocated top-down** ([[03.11 - Timeouts and Deadlines Across Hops]]), and every service gets a fraction of the whole. In a monolith, every operation has the whole budget.

### Availability multiplies down

```
5 services at 99.9% each, in a synchronous chain
→ 99.5% effective = 3.6 hours of downtime per month
```

⚠️ **Your SLO cannot exceed the product of your required synchronous dependencies' availability.** ([[10.3 - Communication Patterns]])

💡 **The fix is making dependencies optional**, which requires degradation paths, which is more work ([[11.6 - Graceful Degradation]]). **The architecture that meets a 99.9% SLO with five services has done real work to get there.**

### Debugging cost

```
Monolith:      a stack trace
Microservices: a trace ID, four log streams, and a tracing backend
```

⚠️ **Without distributed tracing, a microservice system is undebuggable**, and tracing is not free — instrumentation, a backend, sampling decisions, and retention ([[12.3 - Instrumenting Conduit End to End]]).

💡 **Budget the observability work as part of the split**, not as a follow-up. A team that splits and then plans to add tracing has an undebuggable system in the interim.

### Local development

```
Monolith:      docker compose up
Microservices: eight services, four databases, Kafka, and a mesh
```

⚠️ **Local development degrades sharply with service count.** At some point a developer cannot run the system on a laptop, and the responses — remote development environments, service virtualisation, running against shared staging — all have their own costs.

💡 **This is a real productivity tax that shows up in every ticket**, and it is rarely counted in the decision.

### Cognitive load

```
"Where does this logic live?"
"Which service owns this data?"
"Why is this slow?"
"Which version of which service is deployed?"
```

⚠️ **A new engineer must learn the system topology before they can make a change.** In a monolith they follow a function call.

💡 **This is the cost that compounds with team turnover**, and it is invisible until you hire.

## When It Is Worth It

The genuine cases, restated honestly.

| Reason | Strength |
|---|---|
| **Multiple teams blocked by deploy coordination** | **Strong** — the reason microservices exist |
| **Regulatory or data residency isolation** | **Strong** — non-negotiable |
| **Genuinely different availability requirements** | Strong — payments must survive what search does not |
| Genuinely different scaling profile | **Weak** — separate deployments of one image ([[10.1 - Monolith Modular Monolith Microservices]]) |
| Technology diversity | Weak — usually a liability |
| Fault isolation | **Weak** — you get more failure modes, not fewer |
| Codebase too large | **Weak** — modules solve this |

💡 **Only the first two are unambiguous, and both are organisational or legal rather than technical.**

⚠️ **"Different scaling profile" deserves particular scepticism**, because it is the most common stated reason and it is almost always satisfiable without a network boundary:

```yaml
# One image, three deployments, three resource profiles
deployment: api        replicas: 6   cpu: 1
deployment: worker     replicas: 4   cpu: 2
deployment: embedder   replicas: 2   gpu: 1
```

**You get independent scaling, independent placement and independent resource limits. You do not get independent deployment, and that is usually not what you wanted.**

## The Middle Ground

```
Monolith → Modular monolith → Separate deployments of one image → Microservices
```

💡 **The third option is under-used and it covers a large fraction of real requirements.**

| Capability | Modular monolith | One image, N deployments | Microservices |
|---|---|---|---|
| Independent scaling | No | **Yes** | Yes |
| Independent resource limits | No | **Yes** | Yes |
| GPU / specialised nodes | No | **Yes** | Yes |
| Blast radius isolation | No | **Partial** | Yes |
| Independent deployment | No | No | **Yes** |
| ACID across modules | **Yes** | **Yes** | No |
| Cheap refactoring | **Yes** | **Yes** | No |
| One trace, one stack | **Yes** | Partial | No |

⚠️ **Notice that the only thing microservices add over "one image, N deployments" is independent deployment**, and independent deployment only matters when multiple teams are blocked on each other.

💡 **If you are one team, the third column is almost certainly your answer.**

## In Production

### The decision worksheet

Before splitting, fill this in with numbers.

```
Teams blocked by deploy coordination:        ____
Deploys per week currently:                  ____
Time lost to coordination per week:          ____ hours

Services after the split:                    ____
Fixed cost per service (13 items):           ____ engineer-days
Boundaries created:                          ____
Cost per boundary:                           ____ engineer-days

Cross-boundary transactions today:           ____   → each becomes a saga
Cross-boundary joins today:                  ____   → each becomes a call or duplication
Foreign keys crossing boundaries:            ____   → each must be removed

Current p99 latency:                         ____ ms
Estimated p99 after (add hops):              ____ ms
Current effective availability:              ____ %
Estimated after (multiply deps):             ____ %
```

⚠️ **If the coordination time saved is less than the ongoing operational cost, do not split.** That comparison is usually not close, and it usually points the other way for small teams.

💡 **The numbers you need are all measurable before you split** ([[10.2 - Finding Service Boundaries]]): cross-boundary transactions, foreign keys, join patterns, and the traffic matrix from instrumenting module calls.

### The signals you split too early

| Signal | |
|---|---|
| **Sagas being added between two services** | The boundary is in the wrong place |
| Deploys must be ordered | You have a distributed monolith |
| A shared library that every service imports | Same |
| The same feature repeatedly touches two services | Same |
| More time on infrastructure than features | The fixed cost is dominating |
| **Nobody can run it locally** | |
| Debugging requires four people | |

💡 **The strongest signal is the first one.** A saga is expensive; adding one between two services you split means you split in the wrong place ([[10.5 - Distributed Transactions and Sagas]]).

### Merging services back

⚠️ **Merging is a legitimate and under-used response.** It is not an admission of failure — it is what you do when the evidence says the boundary was wrong.

```
1. Deploy both services in one process (import, do not call)
2. Replace network calls with function calls
3. Merge the databases — schemas first, then one database
4. Restore the transactions that were sagas
5. Delete the saga machinery
```

💡 **Merging is usually easier than moving a boundary**, because you are removing constraints rather than adding them.

**Amazon's Prime Video team publicly moved from microservices back to a monolith for one workload and reduced costs by 90%.** That is a normal engineering outcome, not a scandal.

### What to do instead, in order

```
1. Fix the queries               (indexes, N+1 — sections 06.3–06.5)
2. Add read replicas             (if read-bound)
3. Scale vertically              (a 64-core machine is not exotic)
4. Modularise                    (enforced boundaries, one deployable)
5. Separate deployments of one image   (independent scaling)
6. Extract ONE service            (the one with a real reason)
7. Only then: more services
```

⚠️ **Most teams jump from step 1 to step 7.** Steps 4 and 5 solve most of what step 7 is meant to solve, at a fraction of the cost.

### Conduit's honest accounting

Conduit splits in phase 4. **Here is what it cost, stated plainly:**

| Cost | |
|---|---|
| Two services | 26 fixed-cost items |
| Three boundaries | Gateway↔documents, gateway↔search, documents↔billing |
| **Two sagas** | Organisation offboarding, plan upgrade |
| One duplication | `org_cache`, with reconciliation and a rebuild procedure |
| Latency | +12ms p99 |
| Effective availability | 99.9% → 99.7% |
| Local development | Four containers instead of two |

💡 **The benefit: none, organisationally.** One developer, no deploy coordination, no compliance requirement.

⚠️ **The ADR should say exactly that:** *"We split to experience the cost of a distributed system, and it cost 12ms of p99, 0.2% of availability, two sagas, and roughly three weeks of infrastructure work. A modular monolith with a separately-deployed ingestion worker would have provided the same scaling flexibility for none of that."*

💡 **That sentence is worth more in an interview than a clean architecture diagram**, because it demonstrates you can quantify a tradeoff rather than recite a preference.

## Codebase

**Repo:** `GoogleCloudPlatform/microservices-demo`, `saleor/saleor`, `gitlabhq/gitlabhq`

**Question to answer:** Count the operational surface of Online Boutique versus Saleor for comparable functionality. Then: GitLab is one of the largest monoliths in production — what does it do instead of splitting?

**Read, in order:**

1. `microservices-demo/kubernetes-manifests/` — **count the manifests, services, deployments and configuration files** for eleven services. This is the fixed cost, visible
2. `microservices-demo/src/checkoutservice/main.go` — **one operation, five network calls, no compensation** ([[10.5 - Distributed Transactions and Sagas]])
3. `saleor/saleor/order/actions.py` — **the same operation as one transaction.** Compare the line count and the failure modes
4. `gitlab/doc/development/` — **their architecture documentation.** Note the emphasis on boundaries, database review and query performance rather than on splitting
5. `gitlab/doc/development/software_design.md` — how they keep a very large monolith maintainable

💡 GitLab is the strongest counter-example to microservices inevitability: **a codebase of millions of lines, thousands of contributors, and a very large production deployment, structured as a monolith with enforced internal boundaries.** Reading their engineering documentation is the best antidote to the assumption that scale requires splitting.

**Size:** 1–2 sessions.

## Exercise

**Drill 10.11 — Do the arithmetic, then decide**

```
drills/10-cost/
├── inventory/
│   ├── count_surface.py      # manifests, pipelines, dashboards, runbooks
│   ├── monolith.md
│   ├── microservices.md
│   └── COMPARISON.md
├── measure/
│   ├── latency.py            # same operations, both architectures
│   ├── availability.py       # inject failures, measure effective
│   ├── local_dev.py          # time to a working local environment
│   ├── onboarding.py         # time for a new engineer to ship a change
│   └── RESULTS.md
├── worksheet/
│   └── decision.md           # the numbers, filled in
├── merge/
│   ├── plan.md
│   ├── execute.py            # merge two services back
│   └── RESULTS.md
└── ADR.md
```

**Part 1 — Count the surface.** For both the monolith and the split version of Conduit, count:

pipelines, Dockerfiles, deployment manifests, dashboards, alerts, runbooks, contract test suites, client libraries, secret entries, and database instances.

**Two columns. Report the ratio.**

**Part 2 — Measure the four costs.**

| Cost | Measure |
|---|---|
| **Latency** | The same five operations, p50 and p99, both architectures |
| **Availability** | Inject 0.1% failures per service, measure end-to-end success |
| **Local development** | Time from a clean machine to a working environment |
| **Onboarding** | Have someone unfamiliar ship a small change. Time it |

**The last two are the ones nobody measures**, and they are the ones developers feel every day.

**Part 3 — Count the code that exists only because you split.**

```
Saga orchestration
Compensation handlers
Reconciliation jobs
Duplicated data sync consumers
Circuit breakers and retry logic
Contract tests
Client libraries
Trace propagation
```

**Count the lines.** Then count the lines of business logic.

**Report the ratio of distribution machinery to domain logic.** For a small system it is often above 1:1, and that number is the argument.

**Part 4 — Fill in the worksheet.** Every field, with a real number from your own measurements.

**Then compute:** does the coordination time saved exceed the ongoing operational cost?

**Part 5 — Merge two services back.** Take the split Conduit and merge `documents` and `billing`.

Execute the five-step merge. Measure: time taken, lines deleted, sagas removed, and latency recovered.

**Then re-measure availability and local development time.**

**Part 6 — The counterfactual.** Implement the "one image, N deployments" middle option: a modular monolith deployed as an API, a worker and an embedder, with different resource profiles.

**Measure what you gained relative to the monolith** — independent scaling, GPU placement — **and what you did not have to pay** relative to microservices.

**Part 7 — The honest ADR.** Write Conduit's architecture decision with every number from parts 1 through 6.

Include:

- What splitting cost, quantified across all four dimensions
- What it bought, honestly
- **The counterfactual** — what "one image, N deployments" would have given you
- The specific, measurable trigger that would justify splitting for real

⚠️ **If the honest conclusion is "we should not have split", write that.** It is the more valuable document.

**Done when:**
- Your surface-count ratio is measured for both architectures
- You have onboarding time and local-development time as numbers
- You know the ratio of distribution machinery to business logic
- The decision worksheet is filled with your own measurements
- You merged two services back and measured what was recovered
- The counterfactual is implemented and measured
- The ADR reaches an honest conclusion, whichever way it points
