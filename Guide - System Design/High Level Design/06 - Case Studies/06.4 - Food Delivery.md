## Requirements Clarification

**Functional:**
- Customer: browse restaurants, place order, track delivery in real-time
- Restaurant: receive orders, update order status (accepted, preparing, ready)
- Delivery partner: receive delivery requests, navigate to restaurant, navigate to customer
- Payments: charge on order, refund on cancellation

**Non-functional:**
- Order placement: < 500ms p99
- Real-time location tracking for delivery partner: update every 5 seconds
- 99.99% availability for order service (revenue-critical)
- Strong consistency for order state — no duplicate orders, no lost state transitions
- Eventually consistent for restaurant listings, menus, ratings

**Out of scope:** Restaurant onboarding, loyalty points, subscription plans, surge pricing model

## Estimation

```
DAU: 10M customers, 500K delivery partners
Peak orders: 500K orders/hour (lunch peak) = ~140 orders/s
Location updates: 500K partners × 1 update/5s = 100K location writes/s
Menu reads: 10M × 20 browsing sessions = 200M reads/day = ~2,300 reads/s

Order storage: ~2KB/order (items, addresses, timestamps, status history)
  500K/hour × 2KB × 24h = ~24 GB/day → manageable
```

**Key challenges:**
- 100K location writes/s (high write throughput, geospatial)
- Order state machine with strong consistency
- Real-time order tracking for customers
- Matching delivery partners to orders efficiently

## Order State Machine

The order lifecycle is a state machine. Every transition must be atomic and audited.

```
CREATED
    │ (restaurant accepts)
    ▼
ACCEPTED
    │ (restaurant starts cooking)
    ▼
PREPARING
    │ (restaurant marks ready for pickup)
    ▼
READY_FOR_PICKUP
    │ (delivery partner picks up)
    ▼
OUT_FOR_DELIVERY
    │ (delivery partner marks delivered)
    ▼
DELIVERED
```

Plus failure states: `CANCELLED` (from CREATED or ACCEPTED), `FAILED_DELIVERY`.

### State Transition Enforcement

```python
VALID_TRANSITIONS = {
    "CREATED":           {"ACCEPTED", "CANCELLED"},
    "ACCEPTED":          {"PREPARING", "CANCELLED"},
    "PREPARING":         {"READY_FOR_PICKUP"},
    "READY_FOR_PICKUP":  {"OUT_FOR_DELIVERY"},
    "OUT_FOR_DELIVERY":  {"DELIVERED", "FAILED_DELIVERY"},
}

def transition_order(order_id, new_status, actor_id):
    # Optimistic lock: UPDATE only if current status matches expected
    rows = db.execute("""
        UPDATE orders
        SET status = %s, updated_at = NOW(), updated_by = %s
        WHERE id = %s
          AND status = %s
          AND %s = ANY(valid_next_statuses(status))
        RETURNING id
    """, [new_status, actor_id, order_id, current_status, new_status])

    if not rows:
        raise InvalidTransitionError(f"Cannot transition to {new_status}")

    # Emit event for async processing
    kafka.publish("order-events", {
        "order_id": order_id,
        "new_status": new_status,
        "timestamp": now()
    })
```

All state transitions go through this function. Optimistic locking prevents concurrent conflicting updates.

## Real-Time Location Tracking

### Write Path (100K updates/s)

```
Delivery partner app → POST /location { lat, lng, timestamp }
  │
  ▼
Location Service
  │
  ├── Write to Redis GEO: GEOADD locations {lng} {lat} {partner_id}
  │      (overwrites previous location — only current location matters)
  │
  └── Publish to Kafka: location-updates topic
        (for analytics, ETA recalculation, assignment algorithms)
```

**Redis GEO commands:**
```redis
GEOADD delivery_partners 77.5946 12.9716 "partner:42"
GEOPOS delivery_partners "partner:42"          → current location
GEODIST delivery_partners "partner:42" "restaurant:7" km → distance
GEOSEARCH delivery_partners FROMMEMBER "restaurant:7" BYRADIUS 3 km ASC
  → all partners within 3km of restaurant 7
```

Redis GEO is a sorted set with geohash scores — O(log N) for proximity queries.

### Read Path (Customer tracks order)

```
Customer app polls: GET /orders/{order_id}/tracking
  │
  ▼
Tracking Service
  1. Get assigned delivery_partner_id from order
  2. GEOPOS delivery_partners {partner_id} → current lat/lng
  3. Calculate ETA (simple: distance / avg speed)
  4. Return { partner_location, eta_minutes, order_status }
```

For real-time push (vs polling), use WebSocket or SSE:
```
Customer connects WS
Tracking Service subscribes to Redis channel: location:partner:{partner_id}
Location Service publishes updates to that channel
Tracking Service pushes to customer WS
```

## Restaurant Discovery and Search

Restaurant browsing is read-heavy and eventually consistent. Perfect for a CQRS read model.

```
Write path: Restaurant updates menu → PostgreSQL (source of truth)
              │ (Kafka change event)
              ▼
Read path:  Elasticsearch index
  - Full-text search on restaurant name, cuisine, dish names
  - Geo filter: restaurants within X km of user
  - Facets: cuisine type, dietary options, price range, rating
  - Sorted by: rating, delivery time, distance
```

**Elasticsearch query for "pizza near me":**
```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "cuisine": "pizza" }}],
      "filter": [
        { "geo_distance": {
            "distance": "5km",
            "location": { "lat": 12.97, "lon": 77.59 }
        }},
        { "term": { "is_open": true }}
      ]
    }
  },
  "sort": [{ "_score": "desc" }, { "rating": "desc" }]
}
```

## Delivery Partner Assignment

When an order is ready for pickup, the system assigns the nearest available partner.

```
READY_FOR_PICKUP event
    │
    ▼
Assignment Service
  1. GEOSEARCH: partners within 3km of restaurant, ordered by distance
  2. Filter: only AVAILABLE status partners
  3. Offer to nearest partner (push notification + in-app request)
  4. If partner accepts within 60s → assign
  5. If timeout or reject → offer to next nearest partner
  6. Repeat up to N partners before escalating
```

**Race condition:** Two orders might offer to the same partner simultaneously.

```
Solution: Distributed lock on partner assignment
  SETNX partner_lock:{partner_id} {order_id} EX 60
  Only one order acquires the lock → gets the partner
  Other order moves to next candidate
```

## Payment Flow

```
Order placed
    │
    ├── Payment Service: pre-authorize card (hold funds, don't charge)
    │      → If fails: ORDER not created (fail early, before restaurant notified)
    │
Order DELIVERED
    │
    └── Payment Service: capture pre-authorized hold → actual charge
           → If fails: queue for retry + alert operations
```

**Idempotency:** Payment capture uses `order_id` as idempotency key. Retried captures don't double-charge.

**Cancellation:**
```
Cancel before PREPARING → release pre-auth hold (no charge)
Cancel after PREPARING  → charge cancellation fee + release remainder
Order never delivered   → full refund
```

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Location service down | Can't track delivery | Show last known location; degrade gracefully |
| Restaurant app offline | Order not accepted | Auto-cancel after 5 min + notify customer; reroute to other restaurants |
| Delivery partner drops connection | Location tracking lost | Show "last seen" location; ETA from last update |
| Payment capture fails at delivery | Order delivered but not charged | Queue retry with alert; operations SLA to resolve within 1 hour |
| State transition race condition | Order in inconsistent state | Optimistic locking (UPDATE WHERE status = expected_status) |
| Kafka consumer lag | Order events processed slowly | Alert on lag > 30s; scale consumers |

## What This Design Demonstrates

- State machine with optimistic locking for order consistency
- Redis GEO for real-time geospatial queries (partner proximity)
- CQRS: PostgreSQL for writes, Elasticsearch for read queries
- Pre-auth → capture payment pattern (only charge on successful delivery)
- Distributed lock for partner assignment race condition
- Separation of concerns: order service, location service, assignment service
