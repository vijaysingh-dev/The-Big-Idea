# Vector Database Comparison

## Overview

The vector DB landscape has consolidated significantly. This is an engineering comparison — not marketing.

Candidates evaluated: **Vespa, Qdrant, Pinecone, Weaviate, Chroma, Elasticsearch hybrid**

---

## Chroma

**What it is**: Embeds-and-searches library. Designed for local development and small-scale use.

```python
import chromadb
client = chromadb.Client()
collection = client.create_collection("my_docs")
collection.add(documents=["text1", "text2"], ids=["1", "2"])  # auto-embeds
results = collection.query(query_texts=["search query"], n_results=5)
```

**Strengths**:

- Zero setup — pure Python, no Docker
- Built-in embedding (calls your embedding model automatically)
- Excellent for prototyping and learning

**Weaknesses**:

- Not production-grade: no distributed operation, limited performance at scale
- No native BM25 hybrid search
- Limited metadata filtering
- No access control

**Use when**: Prototyping, development, local demos, learning RAG. **Don't use when**: Production, >100K documents, multi-user, requires reliability.

---

## Qdrant

**What it is**: Purpose-built vector database in Rust. Best general-purpose production vector DB.

**Architecture**: Distributed, replicates with Raft consensus, segments-based storage.

```python
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct

client = QdrantClient("localhost", port=6333)

client.create_collection("docs", vectors_config=VectorParams(size=1536, distance=Distance.COSINE))

client.upsert("docs", points=[
    PointStruct(id=1, vector=embedding, payload={"source": "confluence", "date": "2024-01-01"})
])

results = client.search("docs", query_vector=query_emb, limit=10,
    query_filter=Filter(must=[FieldCondition(key="source", match=MatchValue(value="confluence"))]))
```

**Strengths**:

- Best-in-class filtering (in-traversal, doesn't degrade with selective filters)
- Sparse vector support (SPLADE/BM42 for hybrid search)
- Quantization options (scalar, product, binary) — reduces memory 4–32×
- Multi-vector support (store multiple embeddings per document)
- On-disk storage option (DiskANN) for large collections
- Excellent documentation
- Managed cloud (Qdrant Cloud) or self-hosted

**Weaknesses**:

- Hybrid search requires sparse vectors (SPLADE embeddings), not BM25 directly
- Younger ecosystem than Elasticsearch
- Less battle-tested at extreme scale (vs Elasticsearch)

**Use when**: Most production RAG systems. The default choice for new systems in 2024+.

---

## Pinecone

**What it is**: Fully managed vector database SaaS. Zero infra management.

```python
import pinecone
pc = pinecone.Pinecone(api_key="...")
index = pc.Index("my-index")
index.upsert(vectors=[{"id": "1", "values": embedding, "metadata": {...}}])
results = index.query(vector=query_emb, top_k=10, filter={"source": "confluence"})
```

**Strengths**:

- Zero operational overhead
- Scales to billions of vectors
- Good performance
- Managed updates, backups, replication

**Weaknesses**:

- Expensive at scale (pricing per vector × dimension × time)
- Vendor lock-in
- No native BM25 (sparse vector support exists but requires generating sparse vectors)
- Limited query expressiveness vs Qdrant/Vespa
- Cold start for serverless tier

**Use when**: MVP that needs to scale quickly without infra overhead. Budget isn't primary concern. **Don't use when**: Cost-sensitive, need BM25 hybrid, or need complex filtering.

---

## Weaviate

**What it is**: Open-source vector database with GraphQL API and built-in BM25 hybrid search.

```python
import weaviate

client = weaviate.connect_to_local()
collection = client.collections.get("Document")

results = collection.query.hybrid(
    query="search query",          # runs both BM25 and vector search
    alpha=0.5,                     # balance: 0=BM25 only, 1=vector only
    limit=10
)
```

**Strengths**:

- Native BM25 hybrid search built in
- GraphQL API is expressive for complex queries
- Module system (OpenAI, Cohere integrations built in)
- Good for teams that want a unified semantic + keyword system

**Weaknesses**:

- Java/Go internals — heavier resource usage than Qdrant (Rust)
- GraphQL can be verbose for simple use cases
- Module system is opinionated (tightly couples to specific embedding models)
- Operational complexity for self-hosted production

**Use when**: Team is comfortable with Java ecosystem, needs native hybrid search + has budget for operational overhead.

---

## Elasticsearch (with KNN / Hybrid)

**What it is**: Battle-hardened distributed search engine with vector search added (v8.x). Not a native vector DB but handles the job.

```json
POST /my-index/_search
{
  "knn": {"field": "embedding", "query_vector": [...], "k": 10, "num_candidates": 100},
  "query": {"match": {"content": "search terms"}},
  "rank": {"rrf": {}}
}
```

**Strengths**:

- Best BM25 implementation (decades of optimization)
- Proven at massive scale (petabytes)
- Rich query DSL for complex filtering
- Large ecosystem (Kibana, Logstash, elastic stack)
- Your team may already run it

**Weaknesses**:

- Vector search is an add-on, not the native use case — quality/perf trails Qdrant
- High JVM memory overhead
- Operationally complex
- Expensive licensing for Elastic Cloud

**Use when**: You're already running Elasticsearch and don't want another system. Or need enterprise-scale BM25 with vector as secondary.

---

## Vespa

**What it is**: Yahoo's production search engine, open-sourced. Built for hybrid search at scale from the ground up.

**Strengths**:

- Genuinely native hybrid search — BM25 + ANN in one query, one network call
- Highly configurable ranking (ML ranking, custom rank profiles)
- Strong performance at scale
- Used by major companies (Yahoo, Spotify, Bloomberg)

**Weaknesses**:

- Steep learning curve (custom schema language, YQL query language)
- Heavy infrastructure requirements (minimum cluster size)
- Smaller community than Elasticsearch/Qdrant
- Documentation assumes search engineering background

**Use when**: Enterprise scale, need tight BM25+ANN integration, team has search engineering expertise. Onyx chose Vespa for this reason. **Don't use when**: Small team, early stage, learning RAG.

---

## Decision Framework

```
Stage of project:
├── Prototyping / learning  →  Chroma
└── Production

  Production, and:
  ├── Want managed (no infra)        →  Pinecone
  ├── Already on Elasticsearch       →  ES Hybrid
  ├── Need BM25 hybrid + simple API  →  Weaviate
  ├── Need advanced filtering        →  Qdrant (best default)
  └── Enterprise scale + hybrid      →  Vespa
```
