# Record Locking and Deadlocks

## What the platform locks, without being asked

Every DML operation takes locks you did not request:

**The record being modified.**

**The master-detail parent**, so its roll-up summaries can be recalculated safely.

**The lookup parent**, in some configurations, for the same reason.

**Related records** touched by cascading automation.

That second one is the source of most lock contention on the platform, and it is entirely invisible in the code that triggers it. See [[02.6 - Roll-Up Summary Fields]].

## UNABLE_TO_LOCK_ROW

```
System.DmlException: UNABLE_TO_LOCK_ROW, unable to obtain exclusive access to this record
```

A transaction waited for a lock and gave up. The default wait is around ten seconds.

The common causes, in order of frequency:

**Parallel batches touching children of the same parent.** A data load inserting 10,000 claims across 50 assets, processed in parallel, means several threads competing for the same asset row.

**Ownership or account skew.** One account owning hundreds of thousands of child records means every operation on those children contends on that one row. See [[10.9 - Data Skew]].

**Sharing recalculation** running concurrently with data modification.

**Long-running automation holding a lock.** A trigger that queries, computes, and updates keeps the lock for the whole duration.

**Explicit `FOR UPDATE`** held while doing unrelated work. See [[08.6 - FOR UPDATE and Record Locking]].

## Deadlocks

Two transactions each holding a lock the other needs.

```
Transaction A: locks Asset 1, then requests Asset 2
Transaction B: locks Asset 2, then requests Asset 1
```

Neither can proceed. The platform detects this and kills one, which surfaces as `UNABLE_TO_LOCK_ROW` to the loser.

The defence is **consistent lock ordering**. If every code path acquires locks in the same order — sorted by Id, say — a cycle cannot form.

```java
public with sharing class OrderedUpdateService {

    public static void updateSafely(List<SObject> records) {
        // sorting by Id gives every transaction the same lock acquisition order,
        // which makes a deadlock cycle impossible
        List<SObject> sorted = new List<SObject>(records);
        sorted.sort();

        Database.update(sorted, false);
    }
}
```

sObject lists sort by Id when no other comparator applies, which makes this cheaper than it looks.

## The data loading fix

Most lock errors appear during bulk loads rather than in application code, and the fixes are operational rather than architectural.

**Sort by parent Id before loading.** The single most effective change. Grouping children of the same parent into the same batch means one lock acquisition per parent rather than contention across parallel batches.

**Use serial mode in the Bulk API** where sorting is not enough. Slower, and it eliminates parallel contention entirely.

**Reduce batch size.** Smaller batches hold locks for less time.

**Defer sharing calculation** during the load, then run it once at the end.

**Load parents fully before children.**

See [[23.5 - Bulk Data Loading at Scale]].

## Handling it in code

A batch job should treat a lock failure as transient and everything else as permanent.

```java
public with sharing class ClaimUpdateBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Status__c, Asset__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Under Review'
            ORDER BY Asset__c
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        List<Database.SaveResult> results = Database.update(scope, false);

        Set<Id> retryable = new Set<Id>();
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                continue;
            }
            for (Database.Error err : results[i].getErrors()) {
                if (err.getStatusCode() == StatusCode.UNABLE_TO_LOCK_ROW) {
                    retryable.add(scope[i].Id);
                } else {
                    AutomationLogger.logError('ClaimUpdateBatch', scope[i].Id, err.getMessage());
                }
            }
        }

        if (!retryable.isEmpty()) {
            System.enqueueJob(new ClaimRetryQueueable(retryable));
        }
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

Two details. `ORDER BY Asset__c` in the query locator groups children of the same parent into the same chunk, which is the in-code equivalent of sorting a data file. And retrying only lock failures avoids burning limits reprocessing records that failed validation.

## Reducing lock duration

Locks are held from the DML until the transaction commits, so the whole transaction duration matters, not just the DML.

**Do not make callouts while holding locks.** This is enforced — a callout after DML throws — and the reason is exactly this.

**Query before you write.** Doing all the reads first, then all the writes, keeps the locked window short.

```java
// Locks held for the whole loop
for (Warranty_Claim__c claim : claims) {
    update claim;
    Asset asset = [SELECT Id, Open_Claim_Count__c FROM Asset WHERE Id = :claim.Asset__c];
    // more work while the lock is held
}

// Locks held only for the final DML
Map<Id, Asset> assets = new Map<Id, Asset>([
    SELECT Id, Open_Claim_Count__c FROM Asset WHERE Id IN :assetIds
]);
// all computation happens here, unlocked
update claims;
update assets.values();
```

**Keep triggers fast.** Heavy automation on a frequently updated object extends every lock on it.

**Move work async.** A Queueable runs in its own transaction with its own locks, and the original transaction commits sooner.

## Roll-up contention specifically

The most common architectural cause, worth stating plainly.

Every insert, update, or delete of a master-detail child locks the parent so its roll-up summaries can update. Two threads touching children of the same parent collide.

Mitigations, in order of preference:

**Sort by parent** in the query or the data file.

**Reduce roll-up count** on hot parents. Forty roll-ups on Account means forty recalculations per child change.

**Consider whether the roll-up is needed.** A number only used in a report can often come from the report's own grouping.

**Move to a scheduled recalculation** for aggregates that do not need to be real-time, replacing per-save contention with one batch job. See [[02.6 - Roll-Up Summary Fields]].

## Diagnosing it

Lock errors are intermittent and load-dependent, which makes them hard to reproduce.

**Debug logs** show the failing DML and the record.

**The bulk job error file** lists every failed row, and the pattern in it is usually the answer — if every failure shares a parent, the cause is obvious.

**Event Monitoring**, with Shield, logs concurrency and long-running requests. See [[20.6 - Event Monitoring and Operational Visibility]].

**Reproducing under load** in a Full sandbox is the only reliable way to confirm a fix, because the error does not appear at low concurrency.

The diagnostic question that resolves most cases: **what do the failing records have in common?** Almost always a shared parent, a shared owner, or a shared queue.

## Practical guidance

**Sort by parent Id** in batch query locators and in data files.

**Sort records before DML** where several transactions may touch overlapping sets, so lock order is consistent.

**Do all reads before all writes**, to shorten the locked window.

**Retry lock failures, log everything else.**

**Use partial-success DML** in any job that might meet a locked record.

**Watch roll-up count on hot parent objects.**

**Investigate ownership concentration** when lock errors cluster. It is usually skew.

**Reproduce under load**, not with a single record.
