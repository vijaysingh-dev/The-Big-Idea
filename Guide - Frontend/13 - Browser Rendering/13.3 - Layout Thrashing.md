# Layout Thrashing

Layout thrashing is repeatedly forcing the browser to recompute layout within a single frame by interleaving DOM reads and writes. It is the most common cause of scroll and interaction jank in JavaScript-heavy pages.

## The mechanism

The browser maintains a dirty flag. Writes mark layout as dirty and queue the recalculation for the next frame. A read of a layout-dependent property must return an accurate value, so it forces the queue to flush immediately.

```js
// One write, one read — one layout. Fine.
el.style.width = "100px";
const h = el.offsetHeight;
```

```js
// N writes, N reads, interleaved — N layouts. Thrashing.
for (const el of elements) {
  el.style.height = el.offsetHeight * 2 + "px";
}
```

Each iteration writes (dirty), then reads (flush). With 200 elements that is 200 full-document layout calculations in one frame.

## The fix: batch reads, then writes

```js
// Phase 1: read everything
const heights = elements.map(el => el.offsetHeight);

// Phase 2: write everything
elements.forEach((el, i) => {
  el.style.height = heights[i] * 2 + "px";
});
```

One layout instead of 200. The measured difference on a mid-range device is routinely 10–50× on this exact pattern.

## Properties that force layout

Reading any of these flushes pending layout:

**Element:** `offsetTop`, `offsetLeft`, `offsetWidth`, `offsetHeight`, `offsetParent`, `clientTop`, `clientLeft`, `clientWidth`, `clientHeight`, `scrollTop`, `scrollLeft`, `scrollWidth`, `scrollHeight`, `getBoundingClientRect()`, `getClientRects()`, `innerText`, `focus()`, `scrollIntoView()`, `scrollBy()`.

**Window:** `scrollX`, `scrollY`, `innerHeight`, `innerWidth`, `getComputedStyle()`, `getMatchedCSSRules()`.

**Others:** `document.scrollingElement.scrollTop`, `range.getBoundingClientRect()`, `svg.getBBox()`, `input.selectionStart`.

`getComputedStyle()` forces layout only for properties whose value depends on layout, but treating it as always forcing is the safer habit.

## Where it hides in real code

The loop above is obvious. These are not.

**Inside a helper function:**

```js
function isVisible(el) {
  return el.getBoundingClientRect().top < window.innerHeight;   // forces layout
}

items.forEach(item => {
  item.classList.toggle("visible", isVisible(item));   // write + read, per item
});
```

The read is hidden two frames down the call stack, which is why thrashing survives code review so often.

**Across a library boundary:**

```js
items.forEach(item => {
  jQuery(item).height(newHeight);   // jQuery reads before writing internally
});
```

**Inside a framework render.** A React component that measures in `useLayoutEffect` and then sets state that changes layout, repeated across many instances, produces the same pattern.

**Via `innerText`:**

```js
elements.forEach(el => {
  if (el.innerText.length > 100) el.classList.add("long");   // innerText forces layout
});
```

`textContent` does not force layout; `innerText` does, because it reflects rendered appearance ([[12.1 - The DOM Tree and Node APIs]]).

## FastDom and the read/write scheduler

The generalized solution is a scheduler that queues reads and writes into separate phases per frame:

```js
const scheduler = (() => {
  let reads = [], writes = [], scheduled = false;

  const flush = () => {
    const r = reads, w = writes;
    reads = []; writes = []; scheduled = false;
    r.forEach(fn => fn());
    w.forEach(fn => fn());
  };

  const schedule = () => {
    if (!scheduled) { scheduled = true; requestAnimationFrame(flush); }
  };

  return {
    read: fn => { reads.push(fn); schedule(); },
    write: fn => { writes.push(fn); schedule(); },
  };
})();

elements.forEach(el => {
  scheduler.read(() => {
    const h = el.offsetHeight;
    scheduler.write(() => { el.style.height = h * 2 + "px"; });
  });
});
```

Callers do not need to know about each other's phases. FastDom is the well-known library implementation of this.

## Avoiding the read entirely

The best fix is often to not measure at all.

**Use `IntersectionObserver` instead of `getBoundingClientRect()` in scroll handlers.** It reports visibility asynchronously without forcing layout ([[12.5 - Custom Events and Observer APIs]]):

```js
new IntersectionObserver(entries => {
  entries.forEach(e => e.target.classList.toggle("visible", e.isIntersecting));
}).observe(el);
```

**Use `ResizeObserver` instead of measuring on resize.** The measurement arrives in the entry.

**Use CSS.** `position: sticky`, `scroll-snap`, container queries and `:has()` each replace measurement code that used to be necessary.

**Cache measurements** that do not change between frames — a container width read once per resize rather than per item.

## In React

```jsx
useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setPosition(computePosition(rect));
}, [deps]);
```

This is the correct place to measure — after DOM mutation, before paint, so no flash. But it is synchronous and blocks painting, so heavy measurement there directly delays the frame.

Measuring many children individually is the React version of thrashing. Prefer one measurement on the container, or a `ResizeObserver` on the container, over per-child `getBoundingClientRect()`.

The `useLayoutEffect` → `setState` → re-render → `useLayoutEffect` cycle is worth watching for; it runs entirely before paint, so an unstable dependency creates a synchronous loop that freezes the frame.

## Detecting it

In the Performance panel, forced synchronous layout appears as a **Recalculate Style** or **Layout** entry with a **red triangle** in the corner and a warning: "Forced reflow is a likely performance bottleneck." Clicking it shows the exact stack frame that triggered it.

A frame containing dozens of these purple blocks in a row is thrashing, and the pattern is unmistakable once you have seen it.

For a quick check without profiling, `performance.now()` around a suspect loop tells you whether the cost scales linearly or worse with element count.

## How senior engineers actually use this

**They separate measure and mutate phases** as a habit, not as an optimization applied after a problem appears.

**They prefer observers to measurement.** Most measurement in scroll and resize handlers is unnecessary with `IntersectionObserver` and `ResizeObserver`.

**They look for the red triangle first** when investigating jank. It points directly at the offending line.

**They measure once at the container level** rather than per item, and derive per-item values arithmetically where possible.

**They avoid `innerText` in loops**, using `textContent` when rendered appearance is not needed.

## Common pitfalls

- Interleaved reads and writes, especially when the read is inside a helper.
- `getBoundingClientRect()` in a scroll handler.
- `innerText` where `textContent` would do.
- Measuring every child instead of the container.
- `useLayoutEffect` measurement loops in React.
- Assuming a single forced layout is a problem — it usually is not; the loop is.
- Optimizing suspected thrashing without profiling, and finding the real cost was elsewhere.

## Interview angle

"What is layout thrashing and how do you fix it" is a strong senior-level performance question. Explain the dirty-flag mechanism, give the interleaved loop as an example, and present read/write batching as the fix. Then go further: name the properties that force layout, mention that the read is often hidden inside a helper or library, and note that observers usually remove the need to measure at all. That progression — mechanism, fix, prevention — is the complete answer.
