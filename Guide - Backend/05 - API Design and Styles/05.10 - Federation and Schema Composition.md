# Federation and Schema Composition

#backend #api-design #graphql #microservices

> **In one line:** Federation lets many services contribute to one graph so clients see a single API — and it moves the N+1 problem from your database to your service mesh, where it is much more expensive.

---

## The Idea

You have split into services. Each owns its data. The client still wants one query.

```graphql
query {
  document(id: "doc_42") {      # documents service
    title
    author {                     # users service
      name
      organisation { plan }      # billing service
    }
  }
}
```

| Approach | Shape |
|---|---|
| **Client stitches** | Calls three APIs and joins. Defeats the point |
| **Monolithic gateway** | One GraphQL service calls the others. Simple, owns everyone's schema |
| **Federation** | Each service declares its part; a gateway composes them |

⚠️ **Federation is an organisational solution to an organisational problem.** If one team owns everything, a single GraphQL service calling internal APIs is simpler and faster.

💡 **The honest test: do you have multiple teams that need to deploy schema changes independently?** If not, you are buying distributed query planning to solve a problem you do not have.

---

## How It Works

### Entities

```graphql
# users service — owns User
type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}
```

```graphql
# documents service — references User
type User @key(fields: "id") { id: ID! }        # only the key

type Document @key(fields: "id") {
  id: ID!
  title: String!
  author: User!                                  # returns a stub with just an ID
}
```

The documents service says "there is a User with this ID"; the gateway asks the users service to fill it in.

### The entity resolver

```python
@strawberry.federation.type(keys=["id"])
class User:
    id: strawberry.ID
    name: str

    @classmethod
    async def resolve_reference(cls, id: strawberry.ID, info) -> "User":
        return await info.context.loaders.user.load(id)
```

💡 **`resolve_reference` is the federation equivalent of a DataLoader batch function**, and the gateway calls it with *many* representations at once. **If it is not batched, every federated query becomes N+1 across the network.**

### The query plan

```
1. documents service:  { document(id:"doc_42") { title author { id } } }
2. users service:      { _entities(representations:[{__typename:"User",id:"usr_7"}]) { ... } }
3. billing service:    { _entities(representations:[{__typename:"Organisation",id:"org_3"}]) { ... } }
```

⚠️ **Three sequential network calls, each depending on the previous one's result.** This is the fundamental cost: a deeply nested cross-service query becomes a chain of round trips.

## Federated N+1

```graphql
query { documents(first: 100) { author { organisation { plan } } } }
```

```
1. documents:  100 documents
2. users:      _entities with 100 user IDs         ← batched
3. billing:    _entities with N organisation IDs   ← batched
```

Batched at each hop, and **three sequential round trips** — hop 3 cannot start until hop 2 returns.

💡 **The rule: federation batches within a level and serialises between levels.** Query *depth* across services costs you, not breadth.

⚠️ **Inside `_entities`, you must batch again.** A hundred representations arriving at once must become one database query, not a hundred. **Without a DataLoader inside `resolve_reference`, the network is batched and the database is not** — and the second is where the time goes.

## Ownership Rules

```graphql
# users service
type User @key(fields: "id") { id: ID!, name: String! }

# documents service — extends User with a field it owns
type User @key(fields: "id") { id: ID!, documentCount: Int! }
```

💡 **This is the genuinely useful capability federation provides** — the client sees a natural `user.documentCount` without knowing two services were involved.

⚠️ **Two services cannot own the same field.** Composition fails at build time, which is correct — and it means schema conflicts are now a cross-team coordination problem.

### The directives that matter

| Directive | Purpose |
|---|---|
| `@key(fields: "id")` | This type is an entity |
| `@external` | Owned elsewhere; I only reference it |
| **`@requires(fields: "...")`** | To compute my field, I need these from the owner |
| **`@provides(fields: "...")`** | I can supply these without a round trip |
| `@shareable` | More than one service may resolve this |
| `@override` | I am taking ownership from another service |

💡 **`@provides` is the optimisation that removes a network hop.** If the documents service already joined the author's name, it can declare it and the gateway skips the users service entirely — turning a three-hop query into one.

⚠️ It creates a duplication risk: you are returning data you do not own, which can go stale. **Use it for fields that rarely change.**

`@override` is how you migrate a field between services without a breaking change.

## Composition

```bash
rover supergraph compose --config supergraph.yaml > supergraph.graphql
```

**Composition can fail** — conflicting field types, ambiguous ownership, unresolvable entity references.

💡 **Run composition in CI on every subgraph change.** A service that ships a schema change breaking composition breaks the entire graph for everyone. **This check is the equivalent of a contract test and it is non-negotiable.**

⚠️ **Composition checks must run against the *currently deployed* versions of all other subgraphs**, not the latest in git. Otherwise you validate against a state that does not exist in production ([[05.13 - Contract Testing and Schema Evolution]]).

## In Production

### The latency budget

```
Client → gateway              5ms
Gateway → documents          20ms
Gateway → users              20ms   (sequential)
Gateway → billing            20ms   (sequential)
                            ──────
                             70ms   for a query that would be 20ms in a monolith
```

⚠️ **Deadline propagation is essential** ([[03.11 - Timeouts and Deadlines Across Hops]]) — the gateway must pass a shrinking budget to each subgraph, or a slow billing service consumes the whole request.

### Failure handling

```graphql
type Document {
  title: String!
  author: User          # nullable — deliberately
}
```

💡 **Nullability is your degradation strategy in a federated graph.** If the users service is down and `author` is non-null, the entire response nulls out ([[05.5 - How GraphQL Execution Works]]). Nullable means you return the document with a null author and an error entry.

**Make every cross-service field nullable.** This is one of the clearest cases where schema design and operational resilience are the same decision.

Then add circuit breakers per subgraph ([[11.3 - Circuit Breakers and Bulkheads]]).

### Observability

```python
federation_subgraph_duration.labels(subgraph=...).observe(elapsed)
federation_query_plan_depth.observe(depth)
federation_entity_batch_size.labels(subgraph=..., type=...).observe(size)
```

⚠️ **`federation_entity_batch_size` consistently at 1 means batching is broken and you have network-level N+1.** This is the single most important federation metric and it is easy to miss.

**Distributed tracing is mandatory** — one client query becomes four service calls ([[12.3 - Instrumenting Conduit End to End]]).

### When federation is wrong

| Situation | Better option |
|---|---|
| One team owns everything | A single GraphQL service |
| Two or three services | A gateway calling them directly |
| **Services are chatty across boundaries** | **The boundaries are wrong. Fix those first** |
| Highly relational data spanning services | Reconsider the split |
| You need subscriptions everywhere | Federation makes them much harder |

💡 **Federation amplifies bad service boundaries.** If your documents service needs three round trips to users for a common query, federation makes that visible and expensive rather than fixing it. **The right response is usually to move data, not to add a gateway** ([[10.2 - Finding Service Boundaries]]).

### The alternatives

⚠️ **The BFF option is underrated.** One GraphQL service calling internal gRPC APIs gives clients a unified graph, keeps query planning in one process, and requires no federation infrastructure. **Its only cost is that one team owns the graph schema** — a problem only if you have many teams.

**For Conduit at phase 4, a BFF is almost certainly correct and federation almost certainly is not. Say so in the ADR.**

## Codebase

**Repo:** `apollographql/router`, `apollographql/federation`, `strawberry-graphql/strawberry`

**Question to answer:** How does the gateway build a query plan, and how does it decide what can run in parallel versus sequentially? Then: what does `@requires` cause the planner to do, and why is it expensive?

**Read, in order:**

1. **Apollo Federation specification** — the directives, `_entities`, `_service`. **Short, and it is the contract every implementation follows**
2. `apollographql/federation/query-planner-js/src/buildPlan.ts` — **the query planner.** Look for `FetchGroup` and the dependency graph. **Fetches with no dependency run in parallel; entity resolution creates dependencies**
3. `apollographql/router/apollo-router/src/query_planner/` — the Rust gateway's execution, including deduplication and batching
4. `strawberry/federation/` — the subgraph side: `@key`, `resolve_reference`, the generated `_entities` field
5. `strawberry/federation/schema.py` — how subgraph SDL is exposed for composition

💡 The `@requires` answer is instructive: **it forces the planner to fetch the required fields from the owning service first, then pass them to the requiring service — turning one fetch into two sequential fetches.** It is powerful and it is the most expensive directive in federation.

**Size:** 2 sessions.

## Exercise

**Drill 5.10 — Federate, then decide whether you should have**

```
drills/05-federation/
├── subgraphs/{documents/, users/, billing/, compose.yaml}
├── gateway/{router.yaml, plans/}
├── experiments/{latency_chain.py, entity_batching.py, provides.py, failure.py}
├── alternative/{bff.py, COMPARISON.md}
├── composition/{ci_check.sh, conflicts.md}
└── ADR.md
```

**Part 1 — Build three subgraphs.** Documents, users and billing, each with its own database. Entities with `@key`. Batched `resolve_reference` using DataLoader.

**Part 2 — Capture query plans.** For five queries of increasing cross-service depth, capture and read the generated plan.

Chart subgraph calls, sequential depth, and total latency against query depth. **Confirm that depth serialises and breadth parallelises** — that is the mental model to carry away.

**Part 3 — Federated N+1.** Query 100 documents with authors.

Version A: `resolve_reference` without a loader. Version B: with one. **Measure database queries in the users subgraph — A should be 100, B should be 1.**

Then break it more subtly: **batch at the network level but not the database level**, and show that the gateway metrics look fine while the subgraph is doing N queries.

**Part 4 — `@provides`, measured.** A query needing `document { author { name } }`.

Without: two subgraph calls. With, where documents already has the name: one. **Measure the latency difference.**

Then simulate the staleness risk — change a user's name and show the documents service serving the old one. **Write down the tradeoff.**

**Part 5 — Failure modes.** Kill the billing subgraph.

With `organisation: Organisation!`: observe the whole response nulling. With `organisation: Organisation`: observe partial success with an error entry.

Then add per-subgraph timeouts and circuit breakers, and **measure the latency difference between a fast circuit-breaker rejection and waiting for a timeout.**

**Part 6 — Break composition.** Three conflicts: the same field owned by two subgraphs, incompatible types for a shared field, and an entity reference with no owner.

Confirm composition fails usefully each time. Then build the CI check that composes against the **deployed** versions of the other subgraphs, and demonstrate it catching a change that would have broken the graph.

**Part 7 — The alternative.** The same unified API as a single GraphQL BFF calling three gRPC services.

Compare on: p50 and p99 for the five test queries, total infrastructure components, lines of configuration, time to add a field, blast radius of one service failing, and independent deployability.

**Then write the ADR for Conduit phase 4** choosing one. **"We chose the BFF because we are one team" is a strong and correct answer** — the point is defending it with measurements rather than preference.

**Done when:**
- Your latency chart shows depth serialising and breadth parallelising
- Federated N+1 is reproduced and fixed at both the network and database layers
- You have measured `@provides` removing a hop, and its staleness cost
- Nullable cross-service fields demonstrably survive a subgraph outage
- CI catches all three composition conflicts against deployed schemas
- The ADR chooses between federation and a BFF using your own numbers
