## Service Discovery

### What It Is

In a static world, services know each other's addresses at deploy time. In a dynamic cloud environment, service instances come and go — IPs change on restart, autoscaling adds/removes instances, deployments replace containers.

Service discovery is the mechanism by which services find each other's current network location at runtime.

```
Without service discovery:
  Order Service hardcodes: payment-service → 10.0.1.42:8080
  Payment Service restarts → new IP: 10.0.1.87:8080
  Order Service: can't reach payment → broken

With service discovery:
  Order Service queries registry: "where is payment-service?"
  Registry: "10.0.1.87:8080" (updated when payment-service restarted)
  Order Service: connects successfully
```

---

### Client-Side vs Server-Side Discovery

**Client-side discovery:**  
The client queries the service registry and decides which instance to call (applying load balancing itself).

```
Client → Registry: "give me instances of payment-service"
Registry → Client: [10.0.1.87:8080, 10.0.1.91:8080]
Client picks one (round-robin, random, least-connections)
Client → selected instance
```

Used by: Netflix Eureka (with Ribbon client-side load balancer), Consul with client-side SDKs.

**Server-side discovery:**  
The client calls a router/load balancer. The router queries the registry and forwards the request.

```
Client → Load Balancer/API Gateway
LB → Registry: "current instances of payment-service?"
LB → routes to selected instance
```

Used by: Kubernetes (kube-proxy + kube-dns), AWS ALB with ECS service discovery.

Server-side is more common in modern cloud deployments — the infrastructure handles routing, not the application.

---

### Service Registry Implementations

**Consul (HashiCorp):**
- Agents run on every node, gossip protocol for cluster state
- Health checks built in (TCP, HTTP, script-based)
- DNS interface (services resolvable as `payment-service.service.consul`)
- KV store for config
- Multi-datacenter support

**etcd:**
- Consistent KV store (Raft consensus)
- Used by Kubernetes for all cluster state
- Leases for ephemeral registration (TTL-based, auto-removed on crash)
- Not specifically for service discovery but commonly used for it

**ZooKeeper:**
- Oldest of the group (Apache)
- Ephemeral nodes for registration (auto-removed when session expires)
- More complex operationally; largely superseded by Consul/etcd for new systems

**Kubernetes DNS:**
- Every Service gets a DNS name: `payment-service.namespace.svc.cluster.local`
- CoreDNS resolves to the ClusterIP
- kube-proxy maintains iptables rules for load balancing to pods
- Zero configuration for services within a cluster — just use the DNS name

---

### Health Checks in Service Discovery

The registry only returns healthy instances. Health checks are how it knows.

```
Registration:
  Service starts → registers with Consul (name, IP, port, health check endpoint)

Health check (every 10s):
  Consul → GET http://payment-service:8080/health → 200 OK → healthy
  Consul → GET http://payment-service:8080/health → timeout → mark critical
  After 3 failures → deregister from registry (traffic stops routing to it)
```

This is how the system self-heals: a crashed instance stops receiving traffic without manual intervention.

## Configuration Systems

### What They Are

Centralized stores for application configuration — database connection strings, feature flags, API keys, timeouts, thresholds — that can be read and updated without redeploying code.

```
Without config system:
  Config in environment variables or config files baked into image
  To change a timeout: update code → build → deploy → restart all instances
  Downtime risk, slow iteration

With config system:
  Config stored centrally
  To change a timeout: update value in config store → propagates to all instances in seconds
  Zero downtime
```

---

### Types of Config

**Static config:** Set at deploy time, doesn't change until redeploy. Environment variables, config files mounted into containers.

**Dynamic config:** Can change at runtime without restart. Fetched from a config service.

```
Static (env vars):
  DATABASE_URL=postgres://...
  LOG_LEVEL=info

Dynamic (config service):
  payment_timeout_ms = 3000       → change without redeploy
  max_retry_attempts = 3          → change without redeploy
  enable_new_checkout_flow = true → feature flag
```

---

### Config System Implementations

**etcd:**
- Strongly consistent KV store (Raft)
- Watch API: clients receive real-time updates when a key changes
- Used for Kubernetes cluster config, but also general application config

```python
# Watch for config changes
for event in etcd_client.watch("/config/payment_timeout_ms"):
    update_timeout(event.value)
```

**Consul KV:**
- Same Consul cluster used for service discovery can store config
- Watch (blocking queries) for change notification

**AWS Systems Manager Parameter Store:**
- Managed AWS service
- Hierarchical keys: `/myapp/production/db_url`
- Supports SecureString (encrypted via KMS) for secrets
- Integrates with IAM for access control

**AWS AppConfig / LaunchDarkly / ConfigCat:**
- Full config management platforms with deployment strategies, rollback, and validation
- More appropriate for feature flags with targeting rules

**Spring Cloud Config / Consul Template:**
- Application-framework-level config management
- Templates rendered with values from Consul/etcd

---

### Secrets vs Config

Config (non-sensitive): timeouts, URLs, feature flags → store in config system  
Secrets (sensitive): passwords, API keys, certificates → store in a secrets manager

**Secrets managers:**
- HashiCorp Vault: industry standard; dynamic secrets, secret rotation, fine-grained access control
- AWS Secrets Manager: managed, integrates with RDS (auto-rotates DB passwords), IAM access
- GCP Secret Manager: similar

**Never:**
- Hardcode secrets in code
- Store secrets in config files checked into git
- Log secrets

---

### Config Propagation Patterns

**Push:** Config service pushes changes to all registered clients immediately.  
Fast propagation. Requires clients to maintain a connection.

**Pull with polling:** Clients poll the config service every N seconds.  
Simple. Propagation delay = polling interval. Works even if config service is briefly down.

**Watch/long-poll:** Client opens a request that blocks until a change occurs.  
Near-instant propagation. Less overhead than short polling.

Most real systems use watch/long-poll (etcd watch, Consul blocking queries).

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Registry unavailable | Services can't discover new instances | Cache last known addresses, use DNS TTL |
| Health check false positive | Healthy instance deregistered | Tune check thresholds, use multiple check types |
| Config service unavailable | Services can't fetch new config | Cache last known config locally, start with defaults |
| Config pushed with bad value | All services pick up bad config simultaneously | Canary rollout, validation before push, instant rollback |
| Stale config cache | Service uses outdated config | Set cache TTL appropriately, watch-based updates |
