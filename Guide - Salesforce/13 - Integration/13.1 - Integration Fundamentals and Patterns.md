# Integration Fundamentals and Patterns

## The three questions

Before choosing an API or writing any code, three decisions determine the shape of everything that follows.

**1. Which system is the source of truth for each field?**

Not for each object — for each **field**. SAP owns the customer's billing address and credit status; Salesforce owns their industry, owner, and segment. Writing that down is the single most valuable artifact in an integration project, and its absence is the most common cause of update loops where two systems overwrite each other indefinitely.

**2. Which direction does data flow, and who initiates?**

Salesforce calling out, or the external system calling in. These are entirely different implementations with different limits, different authentication, and different failure modes.

**3. Does the caller need the answer now?**

Synchronous means the caller waits and gets a result. Asynchronous means fire and forget, with reconciliation later. This decision drives everything about error handling.

## The patterns

Salesforce's own integration guidance names a small set of patterns, and nearly every real integration is one of them.

**Request and Reply.** Salesforce calls an external system and waits for the response. The user sees the result.

*Use for:* a credit check, an address lookup, an inventory query, a pricing call.
*Constraints:* the callout cannot follow DML, and the user waits for the external system's latency. Use a Continuation if it is slow. See [[12.7 - Apex Continuations]].

**Fire and Forget.** Salesforce notifies an external system and does not wait.

*Use for:* pushing a closed-won deal to the ERP, notifying a warehouse of a shipment.
*Implementation:* a Queueable from a trigger, or a platform event with a subscriber that calls out.

**Batch Data Synchronization.** Bulk movement on a schedule.

*Use for:* nightly product catalogue sync, warehouse extract, periodic reconciliation.
*Implementation:* Bulk API in both directions, scheduled.

**Remote Call-In.** The external system calls Salesforce.

*Use for:* an ERP pushing order status, a web form creating a lead, a partner system querying accounts.
*Implementation:* REST API, or a custom Apex REST endpoint.

**Data Virtualization.** Salesforce displays external data without storing it.

*Use for:* twelve years of invoice history that should stay in the ERP.
*Implementation:* External objects through Salesforce Connect. See [[02.14 - External Objects and Salesforce Connect]].

**Publish and Subscribe.** Events flow between systems with no direct coupling.

*Use for:* event-driven architectures where several systems react to a change.
*Implementation:* Platform events, CDC, Pub/Sub API, Event Relay.

## Choosing among them

| Requirement | Pattern |
| --- | --- |
| User needs the answer on screen | Request and Reply |
| Notify another system of something that happened | Fire and Forget, or Publish and Subscribe |
| Keep two systems' data aligned, nightly is fine | Batch Synchronization |
| External system needs to create or update records | Remote Call-In |
| Show data you should not store | Data Virtualization |
| Several consumers, added over time | Publish and Subscribe |

The mistake worth naming: **using Request and Reply where Fire and Forget would do.** Making a user wait for an external system, and coupling your save to its availability, when nothing about the interaction requires it. If the ERP being down should not stop a claim being approved, the notification is fire-and-forget.

## Idempotency

The property that makes an integration survivable, and the one most often missing.

An operation is **idempotent** if performing it twice has the same effect as performing it once. This matters because retries are inevitable — a timeout where the request actually succeeded, a redelivered event, a replayed batch.

In Salesforce, idempotency comes from **external IDs and upsert**:

```java
public with sharing class ClaimIngestService {

    public static void ingest(List<ErpClaimDto> payload) {
        List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();

        for (ErpClaimDto dto : payload) {
            claims.add(new Warranty_Claim__c(
                ERP_Claim_Id__c = dto.claimId,
                Claim_Amount__c = dto.amount,
                Status__c = dto.status
            ));
        }

        // the external id decides insert versus update, so a replay updates rather than duplicates
        Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);
    }
}
```

Outbound, idempotency means sending a key the receiver can deduplicate on:

```java
req.setHeader('Idempotency-Key', claim.Id + '-' + claim.LastModifiedDate.getTime());
```

Without this, a timeout that actually succeeded produces a duplicate on the next retry, and nobody discovers it until reconciliation. See [[10.3 - Upsert, Merge and External IDs]] and [[13.17 - Error Handling, Retries and Idempotency]].

## The limits that shape design

**Daily API request allocation.** Calculated from edition and user count, and shared across every inbound API call. An integration polling every minute per record exhausts it before lunch.

This is the single biggest constraint on integration design, and it is why bulk and composite APIs exist. See [[01.4 - Salesforce Editions and Licensing]].

```java
Map<String, System.OrgLimit> limits = OrgLimits.getMap();
System.OrgLimit api = limits.get('DailyApiRequests');
System.debug('API: ' + api.getValue() + ' of ' + api.getLimit());
```

Logging this figure daily catches exhaustion before users do.

**Callout limits per transaction.** 100 callouts, 120 seconds total.

**No callouts after DML.** The constraint that pushes most outbound integration into async.

**Bulk API job and batch limits** for high-volume loads.

## Choosing the API

Covered individually through this section; the summary:

| Need | API |
| --- | --- |
| CRUD on records, moderate volume | REST API |
| Legacy system with WSDL tooling | SOAP API |
| Millions of records | Bulk API 2.0 |
| Several operations in one round trip | Composite API |
| Related records in one request | Composite Graph API |
| Flexible field selection, nested data | GraphQL API |
| Org configuration | Metadata API |
| Code and configuration at runtime | Tooling API |
| Subscribe to events | Pub/Sub API |
| Custom business operation | Apex REST |

The one worth highlighting: **Composite API for round-trip reduction.** An external system creating an account, a contact, and an opportunity makes three calls and consumes three of the daily allocation. One composite call does the same and consumes one. See [[13.5 - Composite and Composite Graph API]].

## Middleware

The question of whether to integrate point-to-point or through a broker — MuleSoft, Boomi, Kafka, or a custom service.

**Point-to-point** is right when there are few integrations, the systems are stable, and the transformations are simple. Fewer moving parts, less to operate.

**Middleware** earns its place when several systems integrate with several others, transformation and orchestration are complex, retry and monitoring must be centralized, or the systems have very different availability.

The tipping point is roughly when the number of point-to-point connections becomes hard to reason about — four systems each talking to each other is twelve connections to maintain.

Middleware also solves a specific Salesforce problem: it can **absorb bursts**, queueing requests rather than consuming the daily API allocation in a spike. See [[13.18 - MuleSoft and Middleware Basics]].

## Security

Every integration is an authentication decision.

**Outbound:** Named Credentials, always. They keep credentials out of code and configuration, handle token refresh, and are deployable. See [[13.13 - Named Credentials and External Credentials]].

```java
// The credential is resolved by the platform; no secret appears in code
req.setEndpoint('callout:ERP_System/api/claims');
```

**Inbound:** a Connected App with OAuth, scoped to what the integration needs. The JWT bearer flow for server-to-server, with no interactive login and no stored password. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**The integration user** should be a dedicated account with a permission set granting exactly the objects and fields required — not System Administrator, and not View All Data. Per-object View All and Modify All where full access is genuinely needed. See [[03.5 - Object Level Security - CRUD]].

Scoping the integration user properly is usually the highest-value security improvement available in an org, because it is so often skipped.

## Designing for failure

Every integration fails. The design question is what happens when it does.

**Log everything, durably.** An `Integration_Log__c` record with the payload, the response, the record Ids, and a correlation Id. Without it, "the sync did not work" has no answer.

**Distinguish transient from permanent failures.** A timeout is worth retrying; a validation failure is not. See [[13.17 - Error Handling, Retries and Idempotency]].

**Make retries safe.** Idempotency, again.

**Reconcile.** A periodic job comparing record counts or checksums between systems, because silent divergence is the failure mode nobody notices.

**Alert on absence.** An integration that stopped running is as serious as one that failed, and only a run log detects it.
