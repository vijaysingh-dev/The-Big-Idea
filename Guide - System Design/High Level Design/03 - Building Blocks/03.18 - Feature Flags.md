# Feature Flags

> **Revision tags:** #building-blocks #deployment #feature-flags  
> **Related:** [[03.13 - Service Discovery and Config]] | [[05.3 - Design For Change]]

---

## What It Is

A feature flag (also called a feature toggle or feature switch) is a conditional in code that enables or disables a feature at runtime without deploying new code.

```python
if feature_flags.is_enabled("new_checkout_flow", user_id=42):
    return new_checkout_flow(cart)
else:
    return old_checkout_flow(cart)
```

The flag's state is read from a config store at runtime. Flipping the flag takes effect in seconds — no deploy, no restart.

---

## Why It Exists

Without feature flags, releasing a feature means:
- Feature is complete → merge → deploy → all users see it immediately
- If it breaks → rollback deploy (slow, risky)
- No way to test in production with real traffic before full release

With feature flags:
- Deploy code with flag off → zero user impact
- Turn flag on for internal users → test in prod
- Gradual rollout: 1% → 10% → 50% → 100%
- Something breaks → turn flag off instantly (no deploy needed)

Feature flags decouple **code deployment** from **feature release**.

---

## Types of Feature Flags

### Release Flags (Most Common)

Control rollout of a new feature. Temporary — removed once fully released.

```
new_checkout_flow: false  → code deployed but feature invisible
new_checkout_flow: true   → feature live for all users
```

### Experiment Flags (A/B Testing)

Different users see different variants. Used for product experiments.

```
checkout_button_color:
  user_id % 2 == 0 → "blue"   (control)
  user_id % 2 == 1 → "green"  (variant)

Track conversion rate per variant → pick winner → flag becomes permanent value
```

### Ops Flags (Kill Switches)

Disable a feature under load or during incidents. Often permanent — the flag exists as a safety valve.

```
enable_recommendations: false  → during DB incident, disable heavy recommendation queries
                                  core checkout still works
```

### Permission Flags

Enable features for specific user segments (beta users, premium tier, internal employees).

```
enable_advanced_analytics:
  user.plan == "enterprise" → true
  otherwise → false
```

## Flag Evaluation Rules

Production flag systems evaluate flags based on rules, not just on/off:

```yaml
flag: new_checkout_flow
rules:
  - if: user.email ends_with "@mycompany.com"  → ON   (internal users always see it)
  - if: user.id in [42, 99, 157]               → ON   (specific beta users)
  - if: user.created_at < "2024-01-01"         → percentage_rollout(10%)
  - default: OFF
```

Evaluation order matters — first matching rule wins.

### Percentage Rollout

Stable assignment: same user always gets same variant. Prevents "flickering" between sessions.

```python
def get_rollout_bucket(user_id, flag_name):
    # Hash user+flag → consistent 0-99 bucket
    hash_input = f"{flag_name}:{user_id}"
    return int(hashlib.md5(hash_input.encode()).hexdigest(), 16) % 100

def is_enabled(flag_name, user_id, rollout_percent):
    bucket = get_rollout_bucket(user_id, flag_name)
    return bucket < rollout_percent
```

User 42 is always in bucket 37 for `new_checkout_flow` — their experience is stable across sessions.

## Architecture

### Simple: Config File / Environment Variable

```python
ENABLE_NEW_FEATURE = os.getenv("ENABLE_NEW_FEATURE", "false") == "true"
```

Requires a redeploy or restart to change. Not truly dynamic. Only suitable for dev/staging toggles.

### Dynamic: Centralized Flag Store

```
[Flag Service / Store]
     │
     ├── Admin UI (change flag values)
     ├── API (read flag for a given user + context)
     └── SDK (client library for services to call)

[Service A] → SDK.is_enabled("flag", user_id) → Flag Store
[Service B] → SDK.is_enabled("flag", user_id) → Flag Store (cached)
```

**Caching in the SDK:** The SDK caches flag values locally (e.g., 30-second TTL) to avoid a network call on every request. Acceptable tradeoff: flag changes propagate within 30 seconds, not instantly.

### Production Systems

**LaunchDarkly:** Industry standard SaaS. Streaming updates (flags change in <200ms), full targeting rules, A/B testing, audit log.

**Unleash:** Open-source, self-hostable. Good for teams that want control.

**AWS AppConfig:** Managed, integrates with CloudWatch for automated rollback on alarm.

**Flagsmith:** Open-source with hosted option. Good mid-point between Unleash and LaunchDarkly.

**Homegrown (Redis + config):** For simple use cases — store flag state in Redis, services read with caching. Fine for kill switches; limited for complex targeting.

## The Flag Lifecycle

Flags must be managed as first-class objects, not left to accumulate forever.

```
1. Create flag (off by default)
2. Deploy code with flag
3. Enable for internal users → test
4. Gradual rollout: 1% → 10% → 50% → 100%
5. Monitor metrics and error rates at each stage
6. If problem: flip flag off instantly (rollback without deploy)
7. Once fully rolled out and stable: remove flag from code and flag store
```

**Flag debt:** Old flags never removed are a maintenance burden and create confusing conditional logic. Teams should have a policy — e.g., "release flags must be removed within 2 sprints of full rollout."

## Flags in a Distributed System

### Consistency Across Services

If Service A and Service B both check a flag, they may see different values during the propagation window (flag flipped but SDK cache not expired yet).

**Design for this:** Ensure that flag-gated behavior in one service doesn't create inconsistency when another service hasn't yet seen the new flag state.

```
flag: use_new_pricing_engine

Order Service:     sees new_pricing_engine = true  → calculates price with new engine
Payment Service:   sees new_pricing_engine = false → validates with old expected price
→ price mismatch!
```

**Solutions:**
- Pass flag evaluation result downstream in the request context (evaluate once at entry point)
- Keep TTLs short so propagation lag is minimal
- Design for idempotent, backward-compatible flag behavior

### Context Propagation

Evaluate the flag at the request entry point (API gateway or top-level service), then pass the result through the call chain.

```python
# At API gateway / BFF layer
flag_context = {
    "use_new_checkout": flags.is_enabled("new_checkout", user_id=user.id),
    "show_recommendations": flags.is_enabled("recommendations", user_id=user.id)
}
# Pass flag_context as request metadata to downstream services
```

Services downstream use the pre-evaluated context rather than independently evaluating — avoids inconsistency during propagation windows.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Flag service down | SDK can't fetch flags | Local cache serves stale values; define safe defaults per flag |
| Flag accidentally flipped globally | Entire user base affected | Staged rollouts, require confirmation for 100% changes |
| Too many flags | Slow evaluation, complex conditions | Regular cleanup, flag owner policy |
| Stale cache | Flag change takes 30s to propagate | Acceptable for most use cases; use streaming SDKs (LaunchDarkly) for instant |
| Missing default | Undefined behavior when flag not found | Always define a default value in the SDK call |
