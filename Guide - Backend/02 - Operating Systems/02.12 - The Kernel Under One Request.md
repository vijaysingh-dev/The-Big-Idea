# The Kernel Under One Request

#backend #os #linux #capstone

> **In one line:** One HTTP request to your FastAPI service passes through interrupts, the network stack, epoll, the scheduler, syscalls, the page cache and the allocator before your code runs, and again on the way out. This note walks the whole path and links every step to the note that explains it.

---

## The Idea

[[01.13 - FastAPI Request Lifecycle End to End]] traced a request through Python. This note traces the **same request through the kernel**. Read the two side by side. Together they cover every place latency can hide on a single machine.

The setup: one uvicorn worker, asyncio with uvloop or the default selector loop, running in a container with a 2-CPU limit. The endpoint reads one row from Postgres over an existing pooled connection and returns JSON.

---

## The Path In

```
 NIC                                              your process
  │ 1. packet arrives, DMA into a ring buffer
  │ 2. hardware interrupt → softirq (NAPI)
  ▼
 kernel network stack
  │ 3. IP → TCP: checksum, sequence numbers, ACK
  │    data copied into the socket's receive buffer
  │ 4. socket marked readable → epoll ready list updated
  │    → the thread sleeping in epoll_wait is woken
  ▼
 scheduler
  │ 5. worker thread made RUNNABLE; waits for a CPU
  │    (cgroup quota left? other threads ahead?)
  ▼
 user space (uvicorn)
  │ 6. epoll_wait returns [fd 12 readable]
  │ 7. recv(fd 12) → copy bytes from the kernel buffer to Python
  │ 8. h11/httptools parses; your endpoint runs
```

| Step | What happens | Typical cost | Can go wrong as | Note |
|---|---|---|---|---|
| 1–2 | NIC DMA, interrupt, softirq | µs | Softirq overload on one core (all interrupts on CPU 0) | [[03.1 - The Stack in One Picture]] |
| 3 | TCP processing, receive buffer | µs | Buffer full → zero window → sender stalls | [[03.4 - Flow Control and Congestion Control]] |
| 4 | epoll wakeup | µs | — | [[03.12 - Event Driven Servers]] |
| 5 | Waiting for a CPU | µs, or **ms when throttled** | cgroup throttling, run-queue contention | [[02.3 - Threads and the Scheduler]] |
| 6–7 | `epoll_wait` returns, `recv` | ~1–2 µs per syscall | — | [[02.7 - File Descriptors and the IO Model]] |
| 8 | Your Python | ms | Blocking call stalls the loop | [[01.6 - The Blocking Call Problem]] |

If this is a **new** connection, there is more before step 1: the SYN lands in the listen socket's SYN queue, then the accept queue (sized by `backlog` and `somaxconn`), and uvicorn calls `accept4` to get a new fd. A full accept queue silently drops connections. See [[03.6 - TCP Settings That Matter]].

## The Database Call

Your endpoint does `await conn.fetchrow(...)`:

```
 9.  asyncpg encodes the query → send(fd 7)            kernel copies to the socket send buffer
10.  coroutine suspends at await → back to the loop → epoll_wait (thread sleeps)
     ── Postgres, on another host, does its own version of this whole note ──
11.  reply arrives → NIC → softirq → TCP → fd 7 readable → epoll wakes the thread
12.  recv(fd 7) → asyncpg decodes → your coroutine resumes
```

While the thread is asleep in `epoll_wait` at step 10, it uses no CPU, and other requests' coroutines run on the same thread. That is the whole value of async, visible at the syscall level.

On the Postgres side, if the row is not in `shared_buffers` or the page cache, there is a disk read: a **major cost difference** between ~1 µs and ~100 µs to several ms. See [[02.8 - Files Disks and the Page Cache]] and [[07.2 - Postgres Architecture]].

## Memory Along the Way

| Moment | What the OS does |
|---|---|
| Parsing headers, building the request object | pymalloc hands out small blocks from existing arenas. No syscalls in the steady state. |
| Building a large JSON response (say 5 MB) | libc `malloc` → a fresh anonymous `mmap` → minor page faults as the buffer is filled |
| Response sent and freed | That `mmap` is returned with `munmap`. Small objects go back to pymalloc's free lists, not to the OS. |
| Memory over the cgroup limit | The kernel reclaims page cache; if that is not enough, the OOM killer sends `SIGKILL` |

Notes: [[02.5 - Virtual Memory]], [[02.6 - Memory in Practice]].

## The Path Out

```
13. endpoint returns → JSON encoded → uvicorn calls send(fd 12)
14. kernel copies into the socket send buffer → TCP segments → qdisc → NIC → wire
15. if the send buffer is full (slow client): send returns EAGAIN,
    uvicorn waits for EPOLLOUT → your coroutine waits at `await send`
16. access log line: write(1, ...) to stdout → a pipe to the container runtime → a log file
```

⚠️ **Step 16 is a blocking write on the event loop.** If the log pipe fills because the log shipper is slow, `write` to stdout blocks, and **the entire event loop stops**. A slow logging pipeline can take down a healthy async service. Use a non-blocking log handler (`QueueHandler` plus `QueueListener`), or make sure the runtime drains stdout fast.

---

## And on Shutdown

```
kubectl rollout → SIGTERM to PID 1 → uvicorn's signal handler (self-pipe → loop)
→ stop accepting (close the listening fd) → finish in-flight requests
→ lifespan shutdown closes the DB pool (close fds) → exit(0)
→ the kernel frees memory, closes leftover fds, sends SIGCHLD to the parent (containerd-shim)
```

See [[02.9 - Signals and Process Lifecycle]] and [[12.7 - Graceful Shutdown and Draining]].

## Where Latency Hides: The Summary Table

| Layer | Hidden cost | The tool that finds it |
|---|---|---|
| NIC / softirq | All interrupts on one core | `mpstat -P ALL` (high `%soft` on one CPU), `/proc/interrupts` |
| TCP | Retransmits, small windows, accept-queue overflow | `ss -ti`, `nstat`, `tcpretrans` |
| Scheduler | Run-queue wait, cgroup throttling | `runqlat`, `cpu.stat` |
| Syscalls | Too many small ones | `strace -c`, `perf trace -s` |
| Locks | GIL or futex contention | `py-spy`, `perf` |
| Memory | Major faults, swap, OOM | `pidstat -r`, `vmstat`, `dmesg` |
| Disk | fsync latency, IOPS cap | `iostat -x`, `biolatency` |
| Logging | Blocking stdout write | `py-spy dump` shows the loop stuck in `write` |

## Codebase

**Repos:** `torvalds/linux` (targeted reading only), `MagicStack/uvloop` or `python/cpython`

**Question to answer:** Between a packet arriving and `epoll_wait` returning, which kernel functions run? Name five.

**Read, in order:** (use [elixir.bootlin.com](https://elixir.bootlin.com/linux/latest/source) to browse with cross-references)

1. `net/ipv4/tcp_ipv4.c` — `tcp_v4_rcv()`: the entry to TCP for an incoming segment
2. `net/ipv4/tcp_input.c` — `tcp_rcv_established()` and `tcp_data_queue()`: the fast path that queues data into the receive buffer
3. `net/core/sock.c` — `sock_def_readable()`: wakes whoever waits on the socket
4. `fs/eventpoll.c` — `ep_poll_callback()`: puts the fd on the epoll ready list and wakes the waiter. Then `ep_poll()`: the sleeping side of `epoll_wait`.
5. CPython `Lib/asyncio/base_events.py` — `_run_once()`: where `epoll_wait` returns into Python

Do not try to understand every line. Follow one packet's path by function name and write down the call chain.

**Size:** 2 sessions. This is the hardest reading in the section, and the most rewarding.

## Exercise

**Drill 2.12 — Trace one request through everything**

```
drills/02-one-request/
├── app.py                 # FastAPI + asyncpg, one endpoint
├── trace.sh               # runs everything below against a single curl
├── strace.txt             # strace -f -tt -T for one request, annotated
├── perf_trace.txt         # perf trace -s summary
├── bpftrace/
│   ├── syscalls.bt        # syscall latency histogram for the worker PID
│   └── wakeup.bt          # time from socket readable → epoll_wait return (sock_def_readable → ep_poll)
├── timeline.md            # a single timeline: µs offset → layer → event
└── FINDINGS.md
```

1. Capture one request with `strace -f -tt -T`. Annotate every syscall with its step number from this note.
2. Build `timeline.md`: a microsecond timeline from `accept4`/`recv` to the final `send`, combining strace timestamps with your app's own timing logs.
3. Stretch: write `wakeup.bt` to measure kernel wakeup latency, then rerun the whole thing in a CPU-throttled container and watch step 5 grow.
4. Make the log pipe slow (pipe stdout through `pv -L 1k`) and show the event loop stalling in `write`.

**Done when:** `timeline.md` accounts for at least 90% of the request's wall time, layer by layer, and you can point to the exact step that grew in the throttled run.
