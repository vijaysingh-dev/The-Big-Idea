# HTTP/2

#backend #http #protocols #performance

> **In one line:** HTTP/2 is the same semantics as HTTP/1.1 with a binary framing layer that lets many requests share one connection — which fixes application-level queueing and makes you newly vulnerable to packet loss.

---

## The Idea

HTTP/2 changes nothing about what HTTP *means*. Methods, status codes, headers and bodies are identical. What changes is how bytes are arranged on the wire.

```
HTTP/1.1:  text, one message at a time per connection
HTTP/2:    binary frames, many interleaved streams per connection
```

Three consequences:

| Change | Benefit |
|---|---|
| **Multiplexing** | Many concurrent requests on one connection |
| **Header compression** | Repeated headers cost almost nothing |
| **Binary framing** | Unambiguous parsing, no request smuggling |

And one cost, which is the thing to actually remember: **all streams now share one TCP connection, so one lost packet stalls all of them** ([[02.5 - Head of Line Blocking]]).

---

## Frames and Streams

Everything is a frame:

```
+-----------------------------------------------+
| Length (24 bits)                               |
+---------------+---------------+---------------+
| Type (8)      | Flags (8)     |
+---------------+---------------+---------------+
| R | Stream Identifier (31)                     |
+===============================================+
| Frame Payload                                  |
+-----------------------------------------------+
```

| Frame type | Purpose |
|---|---|
| `HEADERS` | Request or response headers |
| `DATA` | Body bytes |
| `SETTINGS` | Connection parameters, exchanged at start |
| `WINDOW_UPDATE` | Flow control credit |
| `RST_STREAM` | Cancel one stream |
| `GOAWAY` | Shutting down; do not open new streams |
| `PING` | Liveness and RTT measurement |
| `PRIORITY` | Stream priority (effectively deprecated) |

A **stream** is a bidirectional sequence of frames sharing a stream ID. Client-initiated streams are odd-numbered, server-initiated even.

```
Connection
├── Stream 1:  HEADERS → DATA → (response) HEADERS → DATA
├── Stream 3:  HEADERS → (response) HEADERS → DATA → DATA
└── Stream 5:  HEADERS → DATA
```

Frames from different streams interleave freely on the wire. That is multiplexing.

⚠️ **Stream IDs only increase and are never reused.** After roughly 2³¹ streams the connection must be replaced. At high request rates this is a real event — clients handle it by opening a new connection when the ID space nears exhaustion. If you build long-lived HTTP/2 infrastructure, know this exists.

## HPACK: Header Compression

HTTP/1.1 sends the same headers on every request. On a page with 100 requests, `User-Agent`, `Accept`, `Cookie` and the rest are repeated 100 times — often more bytes than the actual data.

HPACK uses three techniques:

**1. A static table** of 61 common header name/value pairs, known to both sides:

```
2  :method: GET
3  :method: POST
8  :status: 200
```

Sending "GET" costs one byte: the index `2`.

**2. A dynamic table** built during the connection. The first time you send `authorization: Bearer eyJ...`, it costs full size and is added to the table. Every subsequent request references it by index — **one byte**.

**3. Huffman coding** for anything not in either table.

```
HTTP/1.1 request headers:  ~700 bytes
HTTP/2 first request:      ~500 bytes
HTTP/2 subsequent:         ~20 bytes
```

💡 **This is where a large part of HTTP/2's real-world benefit comes from**, and it is invisible in most explanations. For an API where clients send a large bearer token on every call, HPACK removes almost all of that overhead. On a mobile connection, that is meaningful.

### Pseudo-headers

```
:method: POST
:scheme: https
:authority: api.example.com        ← replaces Host
:path: /documents
```

They must come first, and header names must be **lowercase**. A server that emits `Content-Type` in HTTP/2 is producing a protocol error.

⚠️ **CRIME/HPACK attacks.** Because compression is stateful across requests, an attacker who can inject headers can infer secrets from compressed size — the same class of problem as BREACH ([[03.6 - Compression and Streaming Responses]]). HPACK mitigates it by allowing sensitive headers to be marked never-indexed, which good implementations use for `Authorization` and `Cookie`.

## Flow Control

Two levels, both credit-based:

```
Connection-level window:  applies to all streams together
Stream-level window:      applies to one stream
```

A sender may send `DATA` up to the smaller of the two remaining windows. The receiver issues `WINDOW_UPDATE` frames as it consumes data.

```
Initial window: 65,535 bytes per stream (the default)
```

⚠️ **The 65KB default is far too small for high-throughput links.** With a 100ms RTT, 65KB per window means roughly 5 Mbps per stream regardless of your bandwidth — the same bandwidth-delay product problem as TCP ([[02.4 - Flow Control and Congestion Control]]), reproduced one layer up.

```python
# h2 / hypercorn / most servers expose this
SETTINGS_INITIAL_WINDOW_SIZE = 1024 * 1024      # 1MB
```

💡 **This is the single most impactful HTTP/2 tuning parameter** and almost nobody changes it. If you are moving large payloads over HTTP/2 on a high-latency link and throughput is disappointing, check the window size before anything else.

Note that this is application-level flow control sitting on top of TCP's flow control. Both must be large enough. Fixing one and not the other achieves nothing.

## Server Push Is Dead

HTTP/2 allowed the server to push resources the client had not asked for. It sounded excellent.

In practice it was worse than useless: servers pushed resources already in the client's cache, wasting bandwidth; the cache-awareness problem was never solved; and measurements showed it rarely helped.

**Chrome removed support in 2022.** Do not build on it.

The replacement is `103 Early Hints`:

```http
HTTP/1.1 103 Early Hints
Link: </style.css>; rel=preload; as=style

HTTP/1.1 200 OK
...
```

The server sends hints while still generating the response. The client starts fetching in parallel. Same benefit, client stays in control of what it actually needs.

## Prior Knowledge and ALPN

How does a client know the server speaks HTTP/2?

**Over TLS — ALPN.** The protocol is negotiated during the TLS handshake, at no extra cost:

```
ClientHello: ALPN = ["h2", "http/1.1"]
ServerHello: ALPN = "h2"
```

**Over plaintext — prior knowledge.** The client just starts speaking HTTP/2. Used for internal service-to-service traffic where you control both ends. This is how gRPC works inside a cluster without TLS.

There was an `Upgrade`-header path (h2c) for plaintext negotiation. It was rarely implemented and is effectively dead.

⚠️ **Practical consequence: browsers only support HTTP/2 over TLS.** There is no plaintext HTTP/2 in any browser. For internal traffic you can use plaintext with prior knowledge, and gRPC does exactly that.

## In Production

### When HTTP/2 helps

| Situation | Verdict |
|---|---|
| Many small requests to one host | **Big win.** Multiplexing plus HPACK |
| Large repeated headers (bearer tokens) | **Big win.** HPACK |
| Clean, low-loss network | Win |
| Lossy network (mobile, WiFi) | **Can be worse than HTTP/1.1** |
| One large download | Neutral |
| Long-lived streaming | Win — no connection per stream |
| gRPC | Required |

💡 **The honest position: HTTP/2 is a clear win internally and on good networks, and a genuine tradeoff on the public internet with mobile clients.** Saying "HTTP/2 is faster" without that caveat is a sign of not having measured it. The loss sensitivity is real and it is why HTTP/3 exists.

### The gRPC load balancing trap

This is the most consequential HTTP/2 gotcha in backend work.

```
gRPC client ──── one TCP connection ──── L4 load balancer ──── backend A
                                                               backend B  (idle)
                                                               backend C  (idle)
```

An L4 load balancer balances **connections**. gRPC opens one connection and multiplexes every request over it. So every request goes to one backend.

⚠️ **Your load balancing silently stops working.** You do not get an error. You get one pod at 100% CPU and two idle, and it looks like a scheduling problem.

Fixes:

| Fix | Notes |
|---|---|
| **L7 proxy** (Envoy, nginx `grpc_pass`) | Balances per-request. The standard answer |
| **Client-side load balancing** | Client resolves all backends and opens a connection to each |
| **Service mesh** | Sidecar does L7 balancing transparently |
| `MAX_CONNECTION_AGE` on the server | Forces periodic reconnection, redistributing load |

That last one is worth knowing: gRPC servers can be configured to send `GOAWAY` after a duration, forcing clients to reconnect and hit the load balancer again. It is a partial mitigation that works even with an L4 balancer.

### Connection limits and SETTINGS

```
SETTINGS_MAX_CONCURRENT_STREAMS: 100        (typical default)
```

A client may have at most this many in-flight requests per connection. Exceed it and requests queue client-side — which looks like server slowness but is not.

```python
# httpx
limits = httpx.Limits(max_connections=10, max_keepalive_connections=10)
client = httpx.AsyncClient(http2=True, limits=limits)
```

⚠️ With HTTP/2 you need far fewer connections, but not one. Multiple connections give you loss isolation and let an L4 balancer distribute. **Two to four is a reasonable default for high-throughput internal clients**, rather than one.

### Debugging

```bash
curl --http2 -v https://api.example.com/          # check ALPN negotiation
curl --http2-prior-knowledge http://localhost:8000/   # plaintext h2c

# Which protocol was actually used?
curl -w '%{http_version}\n' -o /dev/null -s https://api.example.com/

# nghttp gives frame-level detail
nghttp -nv https://api.example.com/
```

In Wireshark, `http2` as a display filter shows decoded frames — provided you can decrypt the TLS ([[02.11 - Reading Real Traffic]]).

⚠️ **A common surprise: your load balancer speaks HTTP/2 to the client and HTTP/1.1 to your app.** That is usually fine and often correct. But it means your application never sees HTTP/2, HPACK savings apply only on the external hop, and any HTTP/2-specific behaviour you configured in your app does nothing. Check what protocol actually reaches your process.

## Codebase

**Repo:** `python-hyper/h2`, `grpc/grpc`, `envoyproxy/envoy` (docs)

**Question to answer:** How does h2 interleave frames from multiple streams, and what prevents one stream from consuming the whole connection window? Then: find where the HPACK dynamic table is maintained, and what happens if the two sides' tables get out of sync.

**Read, in order:**

1. `h2/connection.py` — `H2Connection`, the central state machine. Look at how outbound frames from different streams are ordered
2. `h2/stream.py` — the per-stream state machine. Compare it to h11's connection state machine from [[03.1 - HTTP1.1 Message Format]] — same idea, one level down
3. `h2/windows.py` — **the two-level flow control.** Small file, and it is the answer to the first question
4. `hpack/hpack.py` (the `hpack` package) — encoder and decoder, static and dynamic tables. Find the never-indexed handling for sensitive headers
5. Envoy docs: `arch_overview/http/http_connection_management` and the gRPC load balancing section — the operational view

💡 The out-of-sync question in part two has a stark answer: **the connection is unrecoverable and must be torn down.** HPACK is stateful, so a decoder that loses sync cannot resynchronise. This is why HPACK bugs are catastrophic rather than degraded, and why implementations are conservative about the dynamic table.

**Size:** 1–2 sessions.

**Part 1 — Multiplexing measured.** 100 concurrent requests to one host. HTTP/1.1 with a pool of 6 versus HTTP/2 on one connection.

Measure total time, p99, and connections opened. Then repeat with 1000 concurrent requests and observe `SETTINGS_MAX_CONCURRENT_STREAMS` becoming the limit.

**Part 2 — HPACK, quantified.** Capture actual bytes on the wire for 100 sequential requests carrying a 1.5KB bearer token, over HTTP/1.1 and HTTP/2.

Use `tcpdump` and measure real transmitted bytes, not what your client reports.

**The ratio should be large.** This is HTTP/2's most underrated benefit and having your own number for it is worth more than any blog post.

**Part 3 — The loss crossover.** The important experiment. Three configurations: HTTP/1.1 with 6 connections, HTTP/2 with 1 connection, HTTP/2 with 4 connections.

Sweep loss with `tc netem`: 0%, 0.1%, 0.5%, 1%, 2%, 5%. Fixed 100ms RTT.

Chart completion time for a realistic workload (50 mixed-size requests) in all three.

**Find the crossover point where HTTP/1.1 starts beating single-connection HTTP/2.** Then note where HTTP/2 with 4 connections sits — it should be the best compromise. This chart is the honest answer to "should we use HTTP/2", and it is specific to your network rather than generic advice.

**Part 4 — Window size.** Transfer 100MB over HTTP/2 with initial window sizes of 65KB, 256KB, 1MB and 8MB, at RTTs of 10ms, 100ms and 300ms.

Chart throughput. Confirm the bandwidth-delay product relationship: window must be at least `bandwidth × RTT` for full utilisation.

Then set the window large but leave the TCP receive buffer small, and show that fixing one layer alone does nothing.

**Part 5 — The gRPC load balancing trap.** Three identical gRPC backends behind a simple L4 balancer (HAProxy in TCP mode). One client, one channel, 10,000 requests.

Count requests per backend. **You should see roughly 100/0/0.**

Then fix three ways and count again:
- Envoy in front, doing L7
- `MAX_CONNECTION_AGE` on the server
- Client-side load balancing with multiple channels

Chart the distribution for all four configurations. Note the failover behaviour when you kill one backend in each.

**Part 6 — What protocol actually reaches your app?** Deploy behind nginx configured with `listen 443 ssl http2;` and a plain `proxy_pass`.

Log the protocol version your application sees. **It will be HTTP/1.1.** Then measure whether HPACK savings applied on the external hop only.

Write in `FINDINGS.md` when this arrangement is fine and when it is not.

**Done when:**
- Your HPACK byte-count ratio is measured from real captures
- The loss-crossover chart has all three configurations across six loss rates
- You can state the loss rate at which HTTP/2 stops winning on your setup
- The window-size chart demonstrates the BDP relationship
- The gRPC distribution is 100/0/0 before the fix and even after
- You know what protocol your app actually receives in a typical deployment
