# Sessions, Tokens and Rotation

#backend #security #authentication

> **In one line:** A session is a credential you can revoke and a JWT is one you cannot, so the design question is always how quickly you need revocation to take effect.

---

## The Idea

```
Session:  an opaque ID → server-side state lookup on every request
JWT:      a signed claim → verified locally, no lookup
```

| | Session | JWT |
|---|---|---|
| Storage | **Server-side** | Client-side |
| Verification | A lookup (Redis/DB) | **Signature only** |
| **Revocation** | **Immediate** | **Not possible before expiry** |
| Scales across services | Shared store needed | **Stateless** |
| Size | ~32 bytes | 500–2,000 bytes |
| Contains user data | No | **Yes, and visible to anyone** |

💡 **The entire tradeoff is revocation versus statelessness.** Everything else is secondary.

⚠️ **"Just use JWTs" is the most common bad security advice in backend engineering.** They solve a distributed-verification problem most applications do not have, at the cost of a revocation problem every application does have.

## Sessions

```python
session_id = secrets.token_urlsafe(32)
await redis.setex(f"session:{session_id}", 86400,
                  orjson.dumps({"user_id": user.id, "org_id": org.id,
                                "created_at": now, "ip": ip}))

response.set_cookie(
    "session", session_id,
    httponly=True,          # JavaScript cannot read it
    secure=True,            # HTTPS only
    samesite="lax",         # CSRF mitigation
    max_age=86400,
    path="/",
)
```

⚠️ **All four cookie flags matter, and `httponly` is the most important** — it means an XSS vulnerability cannot steal the session ([[03.7 - Cookies Sessions and CORS]]).

💡 **`samesite="lax"` blocks CSRF for state-changing requests from other origins**, and it is the default in modern browsers. **`strict` breaks legitimate cross-site navigation; `none` requires `secure` and reopens CSRF.**

### Session hygiene

| Practice | Why |
|---|---|
| **Regenerate the ID on login** | Prevents session fixation |
| **Regenerate on privilege change** | Elevation should invalidate the old ID |
| Idle timeout | Absolute and sliding, both |
| Bind to a device fingerprint | ⚠️ Loosely — IP changes on mobile |
| **List and revoke sessions** | A user should see and terminate their sessions |

⚠️ **Session fixation: an attacker sets a known session ID before the victim logs in, and the server keeps it.** Regenerating on login is a one-line fix and it is frequently missing.

```python
await redis.delete(f"session:{old_id}")
new_id = secrets.token_urlsafe(32)          # always a fresh ID after auth
```

## JWTs

```
header.payload.signature
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c3JfNyIsImV4cCI6MTc1NTQ0MDAwMH0.abc...
```

⚠️ **The payload is base64, not encrypted. Anyone can read it.** Never put anything sensitive in a JWT.

```python
claims = jwt.decode(token, key=jwks_key, algorithms=["RS256"],
                    audience="conduit-api", issuer="https://auth.conduit.local")
```

### The verification mistakes

⚠️ **Three of them, all historically exploited:**

**Algorithm confusion.** A token with `"alg": "none"` accepted as valid. **Always pass an explicit `algorithms` list.**

**RS256 → HS256 confusion.** An attacker takes your public RSA key, signs a token with it as an HMAC secret, and a naive verifier that reads `alg` from the token validates it. **Pinning `algorithms=["RS256"]` prevents this.**

**Missing audience and issuer checks.** A token issued by the same provider for a *different* service is accepted by yours. **Verify both.**

```python
# ❌ Every one of these has caused a real breach
jwt.decode(token, key)                          # algorithm from the token
jwt.decode(token, options={"verify_signature": False})
jwt.decode(token, key, algorithms=["RS256"])    # no audience check
```

### The revocation problem

```
User is fired at 14:00
Their JWT expires at 14:45
→ 45 minutes of valid access
```

| Mitigation | Cost |
|---|---|
| **Short expiry (5–15 min)** | More refresh traffic |
| **A denylist of revoked JTIs** | ⚠️ You now have server-side state — the thing JWTs avoided |
| Check a "session valid" flag per request | Same |
| Accept the window | **A deliberate decision, and often correct** |

💡 **Notice that every real mitigation reintroduces server-side state.** A JWT system with immediate revocation is a session system with extra steps and a larger token.

**Be honest about which you are building.**

## The Access + Refresh Pattern

```
Access token:   JWT, 15 minutes,  sent on every request
Refresh token:  opaque, 30 days,  sent only to /auth/refresh
```

💡 **This is the design that resolves the tradeoff.** The access token is stateless and short-lived; the refresh token is a session — server-side, revocable, and used rarely.

```python
@app.post("/auth/refresh")
async def refresh(refresh_token: str = Cookie(...)):
    row = await repo.get_refresh_token(hash_token(refresh_token))
    if row is None or row.revoked or row.expires_at < now():
        raise HTTPException(401)

    if row.used_at is not None:
        # ⚠️ REUSE DETECTED — this token was already exchanged
        await repo.revoke_family(row.family_id)
        security_log.warning("refresh token reuse", family=row.family_id)
        raise HTTPException(401)

    await repo.mark_used(row.id)
    new_refresh = await repo.create_refresh_token(row.user_id, family=row.family_id)
    return {"access_token": mint_access_token(row.user_id), "refresh_token": new_refresh}
```

### Rotation with reuse detection

💡 **The key idea: every refresh issues a *new* refresh token and marks the old one used. If a used token is presented again, either it was stolen or the legitimate client is replaying — and you cannot tell which, so you revoke the whole family.**

⚠️ **Without reuse detection, a stolen refresh token grants access for its full 30-day lifetime with no way to notice.** With it, the theft is detected the moment either party refreshes.

**Store refresh tokens hashed**, exactly like passwords — a database leak should not yield usable credentials.

### Where to store tokens in a browser

| Location | XSS | CSRF |
|---|---|---|
| `localStorage` | ⚠️ **Readable by any script** | Safe |
| Memory only | Safer, lost on refresh | Safe |
| **`httpOnly` cookie** | **Not readable by script** | **Needs SameSite/CSRF token** |

💡 **`httpOnly` cookies plus `SameSite=lax` is the right default for a browser client.** The common advice to use `localStorage` for JWTs trades a solved problem (CSRF) for an unsolved one (XSS token theft).

**For a mobile or server client, `Authorization: Bearer` is fine** — there is no cookie to steal and no CSRF surface.

## API Keys

```python
key = f"ck_live_{secrets.token_urlsafe(32)}"
await repo.store_api_key(
    key_hash=hashlib.sha256(key.encode()).hexdigest(),
    prefix=key[:12],                   # for display and lookup
    org_id=org.id, scopes=["documents:read"],
)
# return `key` once, and never again
```

| Requirement | |
|---|---|
| **Stored hashed** | A database leak must not yield working keys |
| **Shown once** | Regeneration, not recovery |
| **A recognisable prefix** | So secret scanners can detect leaks |
| Scoped | Not full account access |
| Expiring, or at least rotatable | |
| **Last-used tracking** | To find and revoke dormant keys |

💡 **The prefix matters more than it looks.** `ck_live_` lets GitHub's secret scanning recognise your keys and notify you when one is committed — **and that has prevented a great many breaches.**

⚠️ **A fast hash is correct here and wrong for passwords.** An API key is high-entropy random, so it cannot be brute-forced; a password is low-entropy, so it needs a slow KDF.

## In Production

### Password storage

```python
ph = argon2.PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)
hash_ = ph.hash(password)
```

⚠️ **Argon2id or bcrypt. Never SHA-256, never MD5, never anything fast.**

💡 **Rehash on login when parameters change**, so hardening applies to existing users without forcing a reset:

```python
if ph.check_needs_rehash(stored_hash):
    await repo.update_password_hash(user.id, ph.hash(password))
```

**Check credentials against a breach corpus** (Have I Been Pwned's k-anonymity API) rather than enforcing composition rules — **NIST's current guidance is length plus breach-checking, not "one uppercase and a symbol".**

### Key rotation for signing

```python
claims = jwt.decode(token, key=jwks.get(unverified_header["kid"]), algorithms=["RS256"])
```

💡 **The `kid` header plus a JWKS endpoint is what makes signing key rotation possible without downtime** — publish the new key, start signing with it, and keep the old one until every token signed with it has expired.

⚠️ **Cache the JWKS with a short TTL and serve stale on failure.** A JWKS endpoint outage must not break authentication for tokens you can already verify ([[11.6 - Graceful Degradation]]).

### Timing attacks

```python
if not secrets.compare_digest(provided_hash, stored_hash):
    raise Unauthorized()
```

⚠️ **`==` short-circuits on the first differing byte.** Use `compare_digest` for every secret comparison ([[05.12 - Webhooks and Callbacks]]).

**And equalise the login path:** if a nonexistent user returns faster than a wrong password, you have built a user-enumeration oracle. **Hash a dummy password when the user is not found.**

### Monitoring

```python
auth_attempts_total.labels(result="success"|"invalid_password"|"unknown_user").inc()
token_refresh_total.inc()
refresh_reuse_detected_total.inc()          # ← page on this
session_revoked_total.labels(reason=...).inc()
jwt_verification_failures_total.labels(reason=...).inc()
```

⚠️ **`refresh_reuse_detected_total` being non-zero means a token was stolen or a client is buggy.** It is one of the few authentication metrics worth paging on.

**Alert on failed-login rate per account** (credential stuffing) **and per IP** (brute force), with different thresholds ([[11.5 - Rate Limiting and Quotas]]).

### The checklist

```
□  Sessions: httponly, secure, samesite, regenerated on login
□  JWTs: explicit algorithms, audience and issuer verified
□  Access tokens short-lived (≤ 15 min)
□  Refresh tokens: opaque, hashed, rotated, with reuse detection
□  Refresh token family revocation on reuse
□  Passwords: Argon2id or bcrypt, rehash on parameter change
□  Breach-corpus checking, not composition rules
□  API keys: hashed, prefixed, scoped, shown once, last-used tracked
□  compare_digest everywhere, and equal timing on the login path
□  JWKS cached with stale-on-failure
□  Users can list and revoke their own sessions
□  Reuse detection alerting
```

### Conduit's design

| Credential | Form | Lifetime |
|---|---|---|
| **Browser session** | `httpOnly` cookie → **opaque session in Redis** | 24h idle, 30d absolute |
| **Service-to-service** | JWT, RS256, audience-scoped | 5 minutes |
| **API keys** | Hashed, prefixed `ck_live_`, scoped | Until revoked |
| Webhook signing | HMAC secret, dual-value rotation | ([[05.12 - Webhooks and Callbacks]]) |

💡 **The browser uses sessions rather than JWTs, deliberately.** Conduit needs immediate revocation — an admin removing a user must take effect now, not in fifteen minutes — **and the "JWTs scale better" argument does not apply to a single application with a Redis it already runs.**

⚠️ **JWTs are used only where they genuinely help: short-lived, audience-scoped tokens between internal services**, where the verifier should not need a shared store ([[10.6 - API Gateway and BFF]]).

**Write down the trigger for reconsidering: a second independent application needing to verify user identity without access to the session store.**

## Codebase

**Repo:** `jpadilla/pyjwt`, `ory/kratos`, `django/django`

**Question to answer:** In a JWT library, where is the algorithm chosen, and what makes algorithm confusion possible? Then: how does a mature session system handle regeneration, and what does it store?

**Read, in order:**

1. `pyjwt/jwt/api_jws.py` — **`decode_complete`.** Look at how `algorithms` is used and **what happens if you omit it.** The answer to the first question, and the library's own defensive changes over time are visible in the code
2. `pyjwt/jwt/algorithms.py` — the algorithm registry, and how HMAC and RSA verification differ. **This is where RS256/HS256 confusion becomes possible**
3. `django/django/contrib/sessions/backends/base.py` — **`cycle_key`.** Session regeneration done properly, and what is preserved across it
4. `django/django/contrib/auth/hashers.py` — password hashing, including `must_update` for rehashing on login
5. `ory/kratos/session/` and `selfservice/` — **a full identity system.** Refresh handling, session management, and the self-service revocation flows

💡 The PyJWT history is instructive on its own: **the library moved from accepting the token's declared algorithm to requiring an explicit list, because the original design was exploitable.** Reading the current code alongside that context makes the class of bug memorable rather than abstract.

**Size:** 1–2 sessions.

## Exercise

**Drill 14.2 — Steal your own tokens**

⚠️ Everything runs against your own local stack.

```
drills/14-tokens/
├── sessions/{redis_sessions.py, fixation.py, cookie_flags.py, RESULTS.md}
├── jwt/{verify.py, alg_none.py, rs256_hs256.py, no_audience.py, FINDINGS.md}
├── refresh/{rotation.py, reuse_detection.py, family_revoke.py, tests/}
├── passwords/{argon2.py, rehash.py, timing.py, breach_check.py}
├── apikeys/{issue.py, scopes.py, scanning.md}
├── revocation/{measure_window.py, RESULTS.md}
└── README.md
```

**Part 1 — Sessions, done properly.** Redis-backed sessions with all four cookie flags, regeneration on login, idle and absolute timeouts, and a user-facing session list with revocation.

**Then session fixation:** set a known session ID before login, log in, and **confirm the ID is unchanged** in a version without regeneration. Then add regeneration and confirm the attack fails.

**Part 2 — Three JWT attacks.** Against a deliberately naive verifier:

| Attack | |
|---|---|
| **`alg: none`** | Forge a token with no signature |
| **RS256 → HS256** | Sign with the public key as an HMAC secret |
| **Missing audience** | Use a token issued for a different service |

**Demonstrate each succeeding.** Then fix the verifier and confirm each fails.

💡 **The RS256/HS256 one is the most instructive** — it requires understanding why the same key material can be used two ways.

**Part 3 — Cookie flags, tested.** For each flag, remove it and demonstrate the consequence:

| Removed | Demonstrate |
|---|---|
| `httponly` | A script reads the session cookie |
| `secure` | The cookie sent over plain HTTP |
| `samesite` | A cross-origin form performs a state change |

**Part 4 — Refresh rotation and reuse detection.** Implement the full flow with families.

**Then simulate theft:** an attacker copies a refresh token, both parties refresh, and **confirm the family is revoked and both are logged out.**

Then measure: **how long is an attacker's window with and without reuse detection?**

Then handle the legitimate race — a client refreshing twice concurrently — **and confirm you do not lock out a real user.** This is the hard case.

**Part 5 — The revocation window.** JWT-only auth with a 15-minute expiry.

**Revoke a user and measure how long their access persists.**

Then implement a denylist, then session-based auth. **Measure the revocation window and the per-request cost of each.**

**Report the three-way tradeoff with your own numbers.**

**Part 6 — Passwords.** Argon2id with tuned parameters. **Measure hash time and target ~250ms.**

Then rehash-on-login: change the parameters and confirm existing users are upgraded transparently.

Then the timing oracle: **measure login response time for a nonexistent user versus a wrong password.** If they differ, fix it and re-measure.

Then implement breach checking with the k-anonymity API.

**Part 7 — API keys.** Hashed storage, prefix, scopes, one-time display, last-used tracking.

**Then attempt to use a key beyond its scope** and confirm it fails.

Then simulate a database leak: **confirm the stored hashes cannot be used to authenticate.**

**Part 8 — Attack detection.** Simulate credential stuffing (many accounts, one IP) and brute force (one account, many attempts).

**Confirm your rate limiting and alerting catch both, with different thresholds.**

Then simulate refresh token reuse and confirm the page fires.

**Done when:**
- Session fixation succeeds without regeneration and fails with it
- All three JWT attacks succeed against a naive verifier and fail against yours
- Each removed cookie flag has a demonstrated consequence
- Reuse detection revokes a family, and a concurrent legitimate refresh does not lock out a user
- You have measured the revocation window for three auth designs
- Your login path has no measurable timing difference between failure modes
- Leaked API key hashes cannot be used to authenticate
- Credential stuffing and brute force are detected with different thresholds
