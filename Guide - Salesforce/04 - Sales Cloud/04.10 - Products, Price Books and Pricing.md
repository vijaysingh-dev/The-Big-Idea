# Products, Price Books and Pricing

## The four-object chain

This confuses everyone the first time. Hold the logic and it becomes obvious:

**Product2** — the catalogue item. A product exists once, regardless of price.

**Pricebook2** — a named price list. There is always a **Standard Price Book**, plus optional custom ones for regions, currencies, customer tiers, or channels.

**PricebookEntry** — a product's price *in* a particular price book. This is the junction, and it is why the same product can cost different amounts in different lists.

**OpportunityLineItem** — a product on a specific deal, referencing a PricebookEntry, with a quantity and a possibly-discounted unit price.

```
Product2: Industrial Press Model P400
    ├── PricebookEntry in Standard Price Book:  1,200,000 INR
    ├── PricebookEntry in EMEA Price Book:         14,000 EUR
    └── PricebookEntry in Partner Price Book:   1,020,000 INR

OpportunityLineItem on "Northwind - Press Line Upgrade"
    references the Standard PricebookEntry
    Quantity 2, UnitPrice 1,140,000 (5% discount applied)
```

## The rule that causes most failures

**A product must have an entry in the Standard Price Book before it can have an entry in any custom price book.**

This ordering requirement is the single largest cause of data-loading failures in Sales Cloud. A migration script that creates products and then immediately creates EMEA price book entries fails on every row.

The correct load order:

1. Product2
2. PricebookEntry in the Standard Price Book, with `IsStandard` price book resolved by query
3. PricebookEntry in each custom price book
4. Opportunity, with `Pricebook2Id` set
5. OpportunityLineItem

```java
public with sharing class ProductLoadService {

    public static void loadProducts(List<Product2> products, Map<String, Decimal> standardPrices) {
        insert products;

        Pricebook2 standardBook = [SELECT Id FROM Pricebook2 WHERE IsStandard = true LIMIT 1];

        List<PricebookEntry> standardEntries = new List<PricebookEntry>();
        for (Product2 p : products) {
            standardEntries.add(new PricebookEntry(
                Product2Id = p.Id,
                Pricebook2Id = standardBook.Id,
                UnitPrice = standardPrices.get(p.ProductCode),
                IsActive = true,
                UseStandardPrice = false
            ));
        }
        insert standardEntries;
    }
}
```

The standard price book is found by `IsStandard = true` rather than by name, because its label can be renamed and translated.

## Testing with price books

A specific and well-known problem: **the standard price book ID is not available in test context** in the normal way, because test data is isolated from org data.

`Test.getStandardPricebookId()` exists exactly for this:

```java
@IsTest
static void opportunityWithProductsCalculatesAmount() {
    Id standardPricebookId = Test.getStandardPricebookId();

    Product2 product = new Product2(Name = 'Press P400', ProductCode = 'P400', IsActive = true);
    insert product;

    PricebookEntry entry = new PricebookEntry(
        Pricebook2Id = standardPricebookId,
        Product2Id = product.Id,
        UnitPrice = 1200000,
        IsActive = true
    );
    insert entry;

    Opportunity opp = new Opportunity(
        Name = 'Test Deal',
        StageName = 'Qualification',
        CloseDate = Date.today().addDays(30),
        Pricebook2Id = standardPricebookId
    );
    insert opp;

    Test.startTest();
    insert new OpportunityLineItem(
        OpportunityId = opp.Id,
        PricebookEntryId = entry.Id,
        Quantity = 2,
        UnitPrice = 1140000
    );
    Test.stopTest();

    Opportunity result = [SELECT Amount FROM Opportunity WHERE Id = :opp.Id];
    Assert.areEqual(2280000, result.Amount, 'Amount should be the sum of line items');
}
```

Every test factory in a Sales Cloud org needs this pattern, and forgetting it produces the confusing error that no standard price is defined.

## The Amount behaviour

Once an opportunity has line items, **`Amount` becomes read-only** and is maintained as the sum of `TotalPrice` across the lines.

```java
// Fails when line items exist
opp.Amount = 500000;
update opp;
```

Integrations that push deal values from an external system need to know this. Either they create line items, or the opportunity must have no products.

`OpportunityLineItem` fields worth knowing: `Quantity`, `UnitPrice`, `TotalPrice` (quantity times unit price, and read-only when both are set), `ListPrice` (the price book price, read-only), `Discount` (percentage), `ServiceDate`, `Description`.

Setting `Discount` recalculates `UnitPrice` from `ListPrice`, and setting `UnitPrice` recalculates `Discount`. Setting both in the same DML is an error. This is a small thing that produces a confusing failure.

## Price books and access

Price book access is unusual — it does not follow the normal sharing model. Each user's access to a price book is one of:

- **Use** — can see the price book and add its products to opportunities
- **View Only** — can see prices but not select the book
- **No Access**

This is configured through sharing on Pricebook2 and is a common source of "the rep cannot find the product". A rep with no access to the EMEA price book sees no products when they select it.

## Multi-currency

In a multi-currency org, price book entries carry a `CurrencyIsoCode`, and a product needs an entry per currency within a price book.

Two approaches to international pricing:

**One price book, entries per currency.** Simpler structure, and prices in each currency are set explicitly rather than converted. Right when local pricing is genuinely different rather than a conversion of a base price.

**One price book per region, each in its local currency.** Cleaner when regions have genuinely different catalogues as well as different prices.

Advanced Currency Management adds dated exchange rates, which matters for historical reporting — a deal closed last year should be reported at last year's rate, not today's.

## When to reach for CPQ

The native product and price book model handles: a catalogue, list prices, per-line discounts, and multiple price lists.

It does not handle: product bundles and configuration rules, tiered or volume pricing, subscription terms and proration, contracted pricing per customer, amendment and renewal of existing subscriptions, or approval routing driven by pricing rules.

Those are **CPQ** — Configure, Price, Quote — which is a separate licensed product delivered as a managed package. It brings its own objects (`SBQQ__Quote__c` and dozens more), its own calculation engine, and its own considerable complexity.

The signal that a business needs CPQ: sales reps maintaining pricing spreadsheets outside Salesforce because the native model cannot express the rules. The signal that they do not: a catalogue of fewer than a few hundred products, simple percentage discounts, and no subscriptions.

Building a partial CPQ on custom objects is a well-trodden path to an unmaintainable system. If the requirements genuinely need it, the licensing conversation is cheaper than the build.

## Querying products on deals

```sql
SELECT Id, Name, Amount,
       (SELECT Product2.Name, Product2.ProductCode, Quantity, UnitPrice, ListPrice,
               Discount, TotalPrice
        FROM OpportunityLineItems
        ORDER BY SortOrder)
FROM Opportunity
WHERE IsWon = true AND CloseDate = THIS_FISCAL_QUARTER
```

Product-level revenue analysis, which is one of the main reasons to use products at all:

```sql
SELECT Product2.Family family, SUM(TotalPrice) revenue, SUM(Quantity) units
FROM OpportunityLineItem
WHERE Opportunity.IsWon = true AND Opportunity.CloseDate = THIS_FISCAL_YEAR
GROUP BY Product2.Family
ORDER BY SUM(TotalPrice) DESC
```

Without products on opportunities, this analysis is impossible, which is the practical argument for adopting products even when reps find them tedious.

## Practical guidance

**Load in the right order, and always resolve the standard price book by `IsStandard`.**

**Use `Test.getStandardPricebookId()` in every test factory.**

**Do not set `Amount` on opportunities with line items.**

**Keep the product catalogue clean.** Deactivate rather than delete, since deletion fails when line items reference the product.

**Add a product external ID.** The ERP or PIM is nearly always the source of truth for the catalogue, and the sync needs to be idempotent.

**Push back on building CPQ features natively.** The gap between "a few discount rules" and "a pricing engine" is much larger than it looks from the requirements document.
