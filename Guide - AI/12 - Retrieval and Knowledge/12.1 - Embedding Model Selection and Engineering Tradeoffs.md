# Embedding Model Selection and Engineering Tradeoffs

## What It Is

An embedding model maps a piece of text (token, sentence, paragraph, document) to a dense vector in a fixed-dimensional space such that semantic relationships are preserved geometrically. Choosing the wrong embedding model is one of the most common and expensive mistakes in production RAG — because it affects every downstream component: index quality, retrieval recall, reranker effectiveness, and ultimately answer quality.

This file covers: how to choose, how they differ internally, what engineering tradeoffs matter at scale, and what breaks in production.

---

## Why It Matters

- The embedding model is **frozen** once you build the index. Changing it requires re-embedding the entire corpus (expensive).
- A 5% improvement in retrieval recall translates directly to 5% better answers — often more impactful than prompt engineering.
- Embedding API cost compounds: at 10M chunks × 1536 dims × re-embed every time you upgrade = real money.
- Latency at query time: embedding the query is on the critical path. A 200ms embedding call on a 800ms latency budget is 25% of your budget.
- For your target companies: Haptik/Yellow.ai handle multilingual Indian queries; generic English embeddings degrade significantly on Hindi/Tamil/Telugu.

## How Embedding Models Work Internally

### Bi-Encoder Architecture

All production embedding models are **bi-encoders**: independent encoder for query and document, similarity computed post-hoc.

```
Query:    "revenue growth Q3 2024"    → Encoder → q_vec ∈ ℝ^d
Document: "Apple reported 12% growth" → Encoder → d_vec ∈ ℝ^d

Score = cosine_similarity(q_vec, d_vec)
```

The encoder is almost always a Transformer (BERT-family or newer). The final embedding is typically:
- **[CLS] token representation**: the special classification token's hidden state after all encoder layers
- **Mean pooling**: average of all token hidden states — generally superior to CLS
- **Weighted mean pooling**: attention-weighted average

```python
# Mean pooling — the standard for sentence-transformers
def mean_pool(token_embeddings, attention_mask):
    # token_embeddings: (batch, seq_len, hidden_dim)
    # attention_mask: (batch, seq_len)
    
    input_mask_expanded = attention_mask.unsqueeze(-1).expand(token_embeddings.size()).float()
    sum_embeddings = torch.sum(token_embeddings * input_mask_expanded, dim=1)
    sum_mask = torch.clamp(input_mask_expanded.sum(dim=1), min=1e-9)
    return sum_embeddings / sum_mask  # (batch, hidden_dim)
```

### Training Objective

Embedding models are trained on (query, positive_document, negative_documents) triplets:

**Contrastive loss (InfoNCE)**:
```
L = -log( exp(sim(q, d+) / τ) / Σ exp(sim(q, dᵢ) / τ) )
```
Where `d+` is the positive doc, `dᵢ` are all docs in the batch (in-batch negatives), and `τ` is temperature.

**Key insight**: In-batch negatives — other queries' positive docs act as negatives. Large batch size = more negatives = better training. This is why OpenAI trained on massive batches and why their embeddings generalize well.

**Hard negative mining**: Deliberately include near-miss negatives (BM25 top results that aren't the true answer). Models trained with hard negatives are much better at distinguishing truly relevant from superficially similar.

### Matryoshka Representation Learning (MRL)

OpenAI's `text-embedding-3-*` and several newer models support MRL: the embedding is trained so that truncating to a smaller dimension still produces a good embedding.

```python
# Full embedding: 1536 dimensions
full_emb = openai.embeddings.create(model="text-embedding-3-small", input=text)

# Truncated to 256 dims — still works, less memory, faster ANN
truncated_emb = full_emb[:256]
# Quality ~90% of full at ~17% of storage
```

This is genuinely useful for cost/quality tradeoffs at scale.

## The Model Landscape

### Benchmark: MTEB (Massive Text Embedding Benchmark)

Before choosing a model, check [MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard). It covers 56 tasks across retrieval, clustering, classification, reranking, STS. Key columns:
- **Retrieval** (NDCG@10): most relevant for RAG
- **Model size**: larger = slower/more expensive
- **Max tokens**: hard ceiling on input length

**Do not pick the highest MTEB model blindly.** Check performance on the retrieval tasks closest to your domain. A model that dominates code retrieval may be mediocre for financial documents.

### When to Use Each Category

**Use OpenAI `text-embedding-3-small`** when:
- English-only
- Don't want embedding infra
- Cost is moderate concern
- Integrating with other OpenAI services

**Use Cohere `embed-v3-multilingual`** when:
- Hindi/Tamil/multilingual queries (your target companies)
- Need API-based with language support

**Use `bge-m3`** when:
- Self-hosting required (data privacy, on-prem enterprise)
- Multilingual corpus
- Long documents (8192 token context)

**Use `e5-mistral-7b-instruct`** when:
- Maximum retrieval quality matters, cost secondary
- Have GPU infra for self-hosting

**Use `nomic-embed-text-v1.5`** when:
- Need long context (documents up to 8K tokens)
- Self-hosting, open weights

## Engineering Tradeoffs

### Dimension vs Quality vs Cost

```
Storage cost for 10M chunks:
  dims=384  (MiniLM): 10M × 384 × 4 bytes = 15.4 GB
  dims=768  (nomic):  10M × 768 × 4 bytes = 30.7 GB
  dims=1024 (bge):    10M × 1024 × 4 bytes = 41 GB
  dims=1536 (ada):    10M × 1536 × 4 bytes = 61.4 GB
  dims=3072 (large):  10M × 3072 × 4 bytes = 122.9 GB

ANN index overhead (HNSW): roughly 2× vector storage
```

With MRL, you can halve dimensions with ~5% quality loss. Often worth it at 10M+ chunks.

### Context Window Mismatch

This is a major production pitfall. If your chunks are 512 tokens but your embedding model has a 256-token limit:

```python
# This silently truncates — the last half of the chunk is ignored
embedding = model.encode("very long text that exceeds model max tokens...")
# No error raised. Quality degrades silently.
```

**Always check**: model max tokens vs your chunk size. `bge-large-en-v1.5` has 512 token limit. If you're chunking at 512 tokens, you're at the edge. Add overlap and you're over.

```python
from sentence_transformers import SentenceTransformer
import tiktoken

model = SentenceTransformer("BAAI/bge-large-en-v1.5")
max_seq_len = model.max_seq_length  # 512

enc = tiktoken.get_encoding("cl100k_base")

def safe_embed(texts: list[str]) -> list[list[float]]:
    for text in texts:
        n_tokens = len(enc.encode(text))
        if n_tokens > max_seq_len:
            # This is a bug in your chunking pipeline
            raise ValueError(f"Chunk has {n_tokens} tokens, model max is {max_seq_len}")
    return model.encode(texts).tolist()
```

### Asymmetric vs Symmetric Embeddings

Some models are trained asymmetrically: queries and documents are encoded differently. **Using these without the correct prefix degrades quality significantly.**

| Model | Query prefix | Document prefix |
|-------|-------------|-----------------|
| `e5-*` | `"query: "` | `"passage: "` |
| `bge-*` | `"Represent this sentence for searching relevant passages: "` | (none) |
| `jina-v3` | task=`"retrieval.query"` | task=`"retrieval.passage"` |
| OpenAI / Cohere | None needed | None needed |

```python
# BGE: MUST add prefix to queries, not documents
query = "Represent this sentence for searching relevant passages: What is the capital of France?"
doc = "Paris is the capital of France."  # no prefix

query_emb = model.encode(query)
doc_emb = model.encode(doc)
# Correct — asymmetric encoding
```

### Batch Size and Throughput

For ingestion pipelines embedding millions of chunks:

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("BAAI/bge-large-en-v1.5", device="cuda")

def embed_corpus(texts: list[str], batch_size: int = 256) -> np.ndarray:
    # show_progress_bar=True for long jobs
    embeddings = model.encode(
        texts,
        batch_size=batch_size,
        show_progress_bar=True,
        convert_to_numpy=True,
        normalize_embeddings=True,  # L2 normalize → cosine = dot product (faster ANN)
    )
    return embeddings

# GPU throughput: bge-large on A100 ≈ 2000–3000 sentences/sec at batch_size=256
# 10M chunks / 2500 per sec = ~67 minutes
```

**Normalize embeddings at embedding time**, not at query time. Pre-normalized → dot product = cosine (ANN libraries can use MIPS instead of cosine, which is faster).

### API Embeddings vs Self-Hosted

| Factor | API (OpenAI/Cohere) | Self-Hosted (bge/nomic) |
|--------|---------------------|------------------------|
| Setup | Zero | GPU infra, serving setup |
| Latency (query) | 50–150ms | 5–30ms on GPU |
| Latency (batch) | Rate limited | GPU throughput bound |
| Cost (10M chunks) | ~$10 (ada-002 rate) | ~$0 (GPU amortized) |
| Privacy | Data leaves org | On-prem |
| Model upgrade | Easy (call new model) | Re-deploy container |
| Quality control | Provider managed | Your responsibility |

**At what scale does self-hosting pay off?** Roughly: > 50M embedding calls/month, or strict data privacy requirements.

## Fine-Tuning Embedding Models

When off-the-shelf models underperform on your domain (financial jargon, internal terminology, code):

### When to Fine-tune

- Domain-specific vocabulary not well-represented in training data
- Your queries are structurally different from web queries (SQL, code, product IDs)
- Retrieval recall is below 80% on your golden set after trying multiple models
- You have (query, relevant_document) pairs to train on

### What You Need

Minimum: ~1,000–10,000 (query, positive, hard_negative) triplets. Hard negatives matter most — use BM25 top results that aren't the true answer.

### Fine-tuning with sentence-transformers

```python
from sentence_transformers import SentenceTransformer, losses
from sentence_transformers.training_args import SentenceTransformerTrainingArguments
from sentence_transformers.trainer import SentenceTransformerTrainer
from datasets import Dataset

# Training data format
train_data = Dataset.from_list([
    {
        "anchor": "What was Q3 2024 iPhone revenue?",
        "positive": "iPhone revenue in Q3 2024 was $39.3 billion, up 6% year-over-year.",
        "negative": "Apple launched the iPhone 16 series in September 2024.",  # hard negative: topically related but not the answer
    },
    # ... more examples
])

model = SentenceTransformer("BAAI/bge-large-en-v1.5")

# MultipleNegativesRankingLoss: treats all other positives in batch as negatives
# Best loss for retrieval fine-tuning
loss = losses.MultipleNegativesRankingLoss(model)

args = SentenceTransformerTrainingArguments(
    output_dir="models/bge-finetuned-finance",
    num_train_epochs=3,
    per_device_train_batch_size=64,   # larger batch = more in-batch negatives = better
    learning_rate=2e-5,
    warmup_ratio=0.1,
)

trainer = SentenceTransformerTrainer(
    model=model,
    args=args,
    train_dataset=train_data,
    loss=loss,
)
trainer.train()
model.save_pretrained("models/bge-finetuned-finance")
```

**Expected gain**: 5–15% retrieval recall improvement on domain-specific queries. Well worth it if you have the data.

## Production Embedding Service

Self-hosted embedding behind an internal API:

```python
from fastapi import FastAPI
from sentence_transformers import SentenceTransformer
import torch

app = FastAPI()

# Load once at startup
model = SentenceTransformer(
    "BAAI/bge-large-en-v1.5",
    device="cuda" if torch.cuda.is_available() else "cpu"
)
# Compile for faster inference (PyTorch 2.0+)
# model = torch.compile(model)

@app.post("/embed")
async def embed(texts: list[str]) -> list[list[float]]:
    # batch automatically — model.encode handles this
    embeddings = model.encode(
        texts,
        normalize_embeddings=True,
        batch_size=128,
        show_progress_bar=False,
    )
    return embeddings.tolist()

# Health check with latency tracking
@app.get("/health")
async def health():
    import time
    start = time.perf_counter()
    model.encode(["health check"], normalize_embeddings=True)
    latency_ms = (time.perf_counter() - start) * 1000
    return {"status": "ok", "latency_ms": round(latency_ms, 1)}
```

**Deployment**: One GPU instance handles ~500 query embeddings/sec. For ingestion scale, run multiple workers behind a load balancer.

## Onyx / Reference Codebase

Onyx's embedding layer lives in `backend/danswer/indexing/embedder.py`. Key patterns:
- Abstraction over local vs API embedders (`IndexingEmbedder` base class)

## Revision Anchors

- **Bi-encoder**: query and doc encoded independently; score = cosine post-hoc. Enables pre-computation and ANN search.
- **MRL**: truncatable embeddings. OpenAI 3-small: 1536 → 256 with ~5% quality loss. Storage/speed tradeoff.
- **Asymmetric models**: BGE, E5 need query prefix at query time, no prefix for documents. Missing this silently degrades recall.
- **Context window mismatch**: model max tokens < chunk tokens = silent truncation. Always assert this in your chunking pipeline.
- **Fine-tuning trigger**: < 80% recall@10 on golden set after trying top-3 off-the-shelf models. Need 1K+ (query, positive, hard_negative) triplets.
- **MTEB is a starting point**: filter by retrieval tasks close to your domain. Highest average ≠ best for your use case.
