## What Pub/Sub Is

Pub/Sub (Publish-Subscribe) is a messaging pattern where **publishers** emit messages to named **topics** without knowing who will receive them, and **subscribers** receive messages from topics they're interested in — without knowing who sent them.

```
[Order Service]  ──publishes──→  "order-events" topic
                                        │
                              ┌─────────┼──────────┐
                              ▼         ▼          ▼
                    [Email Worker] [Analytics] [Inventory]
                    (subscriber)  (subscriber) (subscriber)
```

Publisher and subscribers are fully decoupled. Adding a new subscriber requires no change to the publisher.

---

## Pub/Sub vs Message Queue

These are often confused. The distinction matters for design.

| Dimension | Message Queue | Pub/Sub |
|---|---|---|
| **Delivery model** | One consumer gets each message (competing consumers) | All subscribers get every message (fan-out) |
| **Coupling** | Producer knows there's a consumer | Producer is blind to consumers |
| **Use for** | Work distribution (one worker processes each job) | Event broadcasting (all interested parties react) |
| **Example** | "Process this image" → one worker does it | "Order placed" → email + analytics + inventory all react |

In practice, Kafka blurs this line — it supports both patterns depending on consumer group configuration.

## Fan-Out Pattern

The defining feature of pub/sub: one message reaches N subscribers.

```
Event: OrderPlaced { order_id: 42, user_id: 99, total: 150 }

Fan-out to:
  → Email Service       (send confirmation email)
  → Inventory Service   (reserve stock)
  → Analytics Service   (record revenue metric)
  → Loyalty Service     (award points)
  → Fraud Service       (check for anomalies)
```

Each subscriber processes independently, at its own pace, with its own retry logic. Publisher is unaffected by any subscriber's success or failure.

## Event Bus

An **event bus** is the infrastructure that implements pub/sub within a system. It's the "bus" over which events travel between services.

### Types of Event Buses

**In-process event bus:**  
Used within a single service/monolith. Components emit events; other components in the same process subscribe.

```python
# Django signals, Spring ApplicationEventPublisher, etc.
event_bus.emit("user.registered", {"user_id": 42})

@subscribe("user.registered")
def send_welcome_email(event):
    email_service.send_welcome(event["user_id"])
```

No network. No durability (if process crashes, event is lost). Good for decoupling within a service.

**Distributed event bus:**  
A shared broker that multiple services connect to. Events survive process crashes.

```
Service A ──event──→ [Kafka / SNS / EventBridge] ──→ Service B
                                                  ──→ Service C
```

## Real-World Pub/Sub Systems

### AWS SNS + SQS (Fan-out to queues)

The standard AWS pattern for durable fan-out:

```
[Publisher] → SNS Topic
                 ├──→ SQS Queue A → Consumer A (with retries, DLQ)
                 ├──→ SQS Queue B → Consumer B
                 └──→ Lambda Function C
```

- SNS provides fan-out (push to all subscribers)
- SQS provides durability and retry per subscriber
- Each consumer has its own queue — one slow/failing consumer doesn't affect others

### Google Cloud Pub/Sub

- Managed, scalable, at-least-once delivery
- Push (HTTP webhook to subscriber) or pull model
- Message retention for replay (up to 7 days)
- Dead letter topics

### Redis Pub/Sub

- Ephemeral — messages lost if no subscriber connected
- No persistence, no replay, no consumer groups
- Use for: live notifications, cache invalidation signals, real-time dashboards
- Not suitable for durable event pipelines

### Kafka as Pub/Sub

Kafka supports pub/sub via consumer groups:
- Each consumer group gets all messages (pub/sub)
- Within a group, messages are distributed across members (queue)

This makes Kafka the most flexible — it supports both patterns simultaneously on the same topic.

## Event Schema and Versioning

Events are contracts between services. Changing an event schema without coordination breaks consumers.

### Event Envelope Pattern

Wrap every event in a standard envelope:

```json
{
  "event_id": "evt_a3f9b2",
  "event_type": "order.placed",
  "event_version": "1.0",
  "timestamp": "2024-01-15T10:23:45Z",
  "source": "order-service",
  "payload": {
    "order_id": 42,
    "user_id": 99,
    "total": 150.00
  }
}
```

`event_type` + `event_version` lets consumers handle multiple versions.

### Schema Evolution Rules

**Backward-compatible changes (safe):**
- Add optional fields to payload
- Add new event types

**Breaking changes (require versioning):**
- Remove or rename fields
- Change field types
- Change event semantics

**Schema Registry:** A central registry (Confluent Schema Registry, AWS Glue Schema Registry) enforces schema compatibility and stores versions. Producers validate schema before publishing; consumers validate on receipt.

## Ordering and Causality

Pub/Sub systems generally don't guarantee global ordering across topics or even within a topic at high scale.

**Problem:**
```
Event 1: OrderPlaced (order_id: 42)
Event 2: OrderCancelled (order_id: 42)

If Event 2 is processed before Event 1:
  → Inventory Service tries to cancel a non-existent order
```

**Solutions:**

1. **Partition by entity key:** All events for `order_id=42` go to the same Kafka partition → ordered within that entity.

2. **Sequence numbers:** Include a sequence number in events; consumer buffers out-of-order events.

3. **Idempotent consumers with state checks:** Consumer checks current state before applying event ("can only cancel a placed order, not a non-existent one").

## The Outbox Pattern

**Problem:** Writing to the DB and publishing an event are two separate operations. If the service crashes between them, you get inconsistency.

```
# WRONG — not atomic
db.save(order)         # succeeds
event_bus.publish(...)  # crashes here → event never sent
```

**Solution: Outbox pattern**

```
# In same DB transaction:
BEGIN;
  INSERT INTO orders VALUES (...);
  INSERT INTO outbox VALUES (event_type, payload, published=false);
COMMIT;

# Separate outbox publisher process:
SELECT * FROM outbox WHERE published = false;
FOR each event:
    event_bus.publish(event)
    UPDATE outbox SET published = true WHERE id = event.id
```

The outbox row is written atomically with the business record. A separate process reliably publishes it. Even if the publisher crashes and restarts, it picks up unpublished events from the outbox.

This is the standard pattern for reliable event emission from a transactional service.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Subscriber is down | Events accumulate (if durable broker) | DLQ, retention, subscriber recovery |
| Slow subscriber | Queue depth grows | Scale subscribers, backpressure |
| Event published but not saved (no outbox) | Inconsistency between DB and downstream | Outbox pattern |
| Schema breaking change | Consumers crash on new event format | Schema registry, versioning, canary deploy |
| Fan-out too wide | Broker becomes bottleneck | Tiered fan-out, filter at subscriber |
