# The Data Layer

The data layer is everything between a component and the network. Its purpose is that no component ever knows a URL, a header, a status code, or a retry policy.

```
Components
   ↓  hooks — useProducts(), useCreateOrder()
Query layer          caching, deduplication, background refetch
   ↓
Resource modules     productsApi.list(), ordersApi.create()
   ↓
HTTP client          base URL, auth, errors, validation, cancellation
   ↓
fetch
```

Each layer knows only the one below it. A component calls a hook; the hook calls a resource function; the resource function calls the client.

## Why the separation earns its keep

Without it, every call site independently handles base URLs, auth headers, `res.ok` checking, JSON parsing, error shapes, retries and cancellation — and does so slightly differently. When the auth scheme changes, you touch forty files.

The concrete tests:

- **Can you change the API base URL in one place?**
- **Can you add a request header globally?**
- **Can you change retry policy without touching components?**
- **Can you test business logic without a network or a renderer?**

If any answer is no, the layering is not real.

## The resource module

```ts
export const productsApi = {
  list: async (params: ListParams, opts?: RequestOptions): Promise<Product[]> => {
    const raw = await client.get(`/products?${new URLSearchParams(params)}`, opts);
    return productListSchema.parse(raw);
  },

  byId: async (id: string, opts?: RequestOptions): Promise<Product> => {
    const raw = await client.get(`/products/${id}`, opts);
    return productSchema.parse(raw);
  },

  create: async (input: CreateProduct): Promise<Product> => {
    const raw = await client.post("/products", input);
    return productSchema.parse(raw);
  },
};
```

One place per resource where the URL shape lives, so an endpoint rename is a one-line change rather than a search.

Schema parsing at this boundary does three jobs at once: validates, derives the type, and **normalizes** — converting ISO strings to `Date`, defaulting missing collections to `[]`, mapping snake_case to camelCase ([[25.7 - Typing API Responses and Zod]]).

Normalizing here means no component ever writes `?.` for a field the server sometimes omits ([[24.1 - Building an API Layer]]).

## Query options factories

```ts
export const productQuery = (id: string) => ({
  queryKey: productKeys.detail(id),
  queryFn: ({ signal }) => productsApi.byId(id, { signal }),
  staleTime: 5 * 60_000,
});
```

Defining the query once and reusing it across components, router loaders and prefetches keeps the cache key and the fetcher from drifting:

```ts
useQuery(productQuery(id));                        // component
queryClient.ensureQueryData(productQuery(id));     // loader
queryClient.prefetchQuery(productQuery(id));       // hover prefetch
```

This is the single most valuable structural habit with a query library ([[24.6 - TanStack Query Fundamentals]]).

## Feature-facing hooks

```ts
export function useProducts(filters: Filters) {
  return useQuery({
    ...productsQuery(filters),
    select: (data) => data.filter(p => p.available),
  });
}

export function useCreateProduct() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: productsApi.create,
    onSuccess: (created) => {
      queryClient.setQueryData(productKeys.detail(created.id), created);
      queryClient.invalidateQueries({ queryKey: productKeys.lists() });
    },
  });
}
```

Components import these, not the query library and not the resource module. That indirection means cache strategy, invalidation and derived shapes can change without touching a single component ([[24.7 - Caching Stale Time and Invalidation]]).

It also means swapping the data library — or moving a query into a server component — is a change in one file per resource.

## Cross-cutting concerns

Everything that applies to *every* request belongs in the client, not at call sites:

```ts
export function createClient({ baseUrl, getToken, onUnauthorized }) {
  async function request(path, { signal, ...options } = {}) {
    const res = await fetch(`${baseUrl}${path}`, {
      ...options,
      signal: signal ?? AbortSignal.timeout(30_000),
      headers: {
        "Content-Type": "application/json",
        ...(getToken() && { Authorization: `Bearer ${getToken()}` }),
        "X-Request-Id": crypto.randomUUID(),
        ...options.headers,
      },
    });

    if (res.status === 401) onUnauthorized();
    if (!res.ok) throw new HttpError(res.status, await res.json().catch(() => null), path);
    if (res.status === 204) return null;
    return res.json();
  }
}
```

Three details worth copying:

**`getToken` is a function**, not a value — closing over a token string captures a stale one after refresh ([[02.4 - Closure Patterns in Production]]).

**`X-Request-Id`** correlates a frontend error with a backend log entry, which turns "the API failed" into a traceable incident ([[28.13 - Frontend Observability]]).

**Error body parsing is guarded**, since a 500 returning an HTML page would otherwise throw a `SyntaxError` masking the real status.

## Error normalization

```ts
type AppError =
  | { kind: "cancelled" }
  | { kind: "network" }
  | { kind: "timeout" }
  | { kind: "validation"; fields: Record<string, string> }
  | { kind: "forbidden" }
  | { kind: "notFound" }
  | { kind: "server"; status: number };
```

Converting every failure into one small union means downstream code branches on `kind` rather than inspecting raw responses ([[05.9 - Error Handling and Custom Errors]]).

The `cancelled` case matters most in practice — an abort is normal control flow and must never reach a toast or an error reporter ([[04.6 - AbortController and Cancellation]]).

## Cancellation must be threaded

```ts
byId: (id, opts) => client.get(`/products/${id}`, opts)
```

Every function in the layer accepts and forwards `signal`. Query libraries and router loaders both supply one automatically, and failing to forward it silently disables cancellation — which is what fixes the search race where a slow earlier response overwrites a newer one.

This is a common oversight because nothing breaks visibly; the requests simply keep running.

## REST, GraphQL, RPC

| | Strengths | Costs |
| --- | --- | --- |
| **REST** | HTTP caching, simple, universal | over/under-fetching, waterfalls |
| **GraphQL** | precise fetching, one round trip, typed schema | server complexity, harder caching, N+1 risk |
| **tRPC** | end-to-end inference, no codegen | TypeScript monorepo only |
| **RSC** | zero client fetching for initial data | requires a server and framework |

The layering above is unchanged by the choice — only the client implementation differs. That is the point of having it.

For an interview: REST with a query cache is the safe default; GraphQL is justified when many clients need different shapes of the same data; tRPC when the whole stack is TypeScript in one repo.

## What belongs where

| Concern | Layer |
| --- | --- |
| URL construction | resource module |
| Auth headers, timeouts, retries | HTTP client |
| Response validation and normalization | resource module |
| Caching, deduplication, invalidation | query layer |
| Derived/filtered shapes | hook (`select`) |
| Loading and error UI | component |
| Business rules | pure functions in the feature |

The recurring mistake is business logic in components. `calculateDiscount` in a JSX file cannot be tested without a renderer and cannot be reused on the server ([[28.2 - Project Structure and Architecture]]).

## Testing

```ts
server.use(
  http.get("/api/products/:id", ({ params }) =>
    HttpResponse.json({ id: params.id, name: "Test", price: 100 })
  )
);
```

Mocking at the **network** boundary exercises the real client, real error handling and real validation. Mocking the resource module skips exactly the code most likely to contain bugs ([[26.4 - Mocking the Network with MSW]]).

## How senior engineers actually use this

**They ban `fetch` in components** and route everything through feature hooks.

**They define query options once** and reuse them across components, loaders and prefetches.

**They normalize errors into a small union**, so every consumer branches the same way.

**They thread `signal` through every function**, since cancellation is silently absent otherwise.

**They keep business rules in pure functions**, outside both components and hooks.

**They mock the network, not the modules**, in tests.

## Common pitfalls

- `fetch` called directly from components.
- Endpoint URLs duplicated across files.
- Capturing a token value instead of a getter.
- `signal` not forwarded, disabling cancellation.
- Raw server shapes reaching components, forcing defensive optional chaining.
- Aborts surfacing as user-visible errors.
- Business logic embedded in JSX.
- Tests mocking the API module rather than the network.

## Interview angle

"How would you structure API calls in a large application" wants the layering with a clear statement of what each layer owns — and the tests that prove the layering is real: can you change the base URL, add a header, or change retry policy in one place. The details that mark experience: normalize responses at the boundary so components never see raw server shapes, normalize errors into a discriminated union, thread `AbortSignal` end to end, and inject a token *getter* rather than a value.
