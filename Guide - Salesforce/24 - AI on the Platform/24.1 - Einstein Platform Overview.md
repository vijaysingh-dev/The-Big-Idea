# Einstein Platform Overview

## Two different things called Einstein

**Predictive Einstein** — machine learning over your CRM data. Scoring, forecasting, classification. It has existed since 2016 and it is statistical rather than generative.

**Generative Einstein** — large language models producing text, summaries, and replies. Newer, and it is what "Einstein" now usually means in conversation.

**They solve different problems**, and confusing them produces a project that fits neither. A lead scoring requirement is predictive; a "draft a reply to this email" requirement is generative.

## The predictive features

Configured rather than built, and each trains on the org's own history.

```
Einstein Lead Scoring          which leads convert
Einstein Opportunity Scoring   which deals close
Einstein Account Insights
Einstein Forecasting           predicted attainment
Einstein Case Classification   predicted field values on intake
Einstein Case Routing
Einstein Article Recommendations
Einstein Bots                  intent-based, pre-generative
Einstein Prediction Builder    a custom prediction on any object
Einstein Next Best Action      recommendations from rules plus models
```

**Einstein Prediction Builder** is the one worth knowing as a developer, because it is the general-purpose case:

```
Predict:      whether a warranty claim will be rejected
On:           Warranty_Claim__c
Using:        Claim_Amount__c, Asset age, Account history, Coverage level
Trained on:   closed claims from the last two years
Output:       Rejection_Likelihood__c, a score field on the record
```

**The output is a field**, which means it is usable in formulas, validation rules, flows, reports, and Apex like any other field. That is what makes it practical — the prediction is not a separate system, it is a number on the record.

**What it requires:** enough history. A few hundred examples is not enough; a few thousand with a reasonable balance of outcomes is the working minimum.

**Where it fails:** the model learns the historical pattern, including the biases in it. A claims process that historically rejected claims from one region disproportionately produces a model that predicts rejection for that region. See [[24.7 - Designing AI Features Responsibly on CRM Data]].

## The generative features

```
Einstein Copilot / Agentforce   conversational agent over CRM data and actions

Einstein for Sales              email drafting, call summaries
Einstein for Service            reply drafting, case summaries, knowledge articles
Einstein for Developers         code assistance
Einstein Trust Layer            masking, grounding, zero retention
```

## Grounding

The concept that makes generative AI on CRM data useful rather than a novelty.

**An ungrounded prompt:**

```
"Write a reply to a customer about a warranty claim."
```

The model produces something plausible and generic, with no knowledge of this claim, this customer, or this contract.

**A grounded prompt:**

```
"Write a reply to {!Contact.FirstName} about warranty claim
 {!Warranty_Claim__c.Claim_Number__c} for machine
 {!Warranty_Claim__c.Asset__r.SerialNumber}.

 Status: {!Warranty_Claim__c.Status__c}
 Approved amount: {!Warranty_Claim__c.Approved_Amount__c}
 Coverage ends: {!Warranty_Claim__c.Asset__r.Coverage_End_Date__c}"
```

**Grounding is merge fields plus retrieved context**, and it is where the engineering work sits. The prompt itself is the small part; assembling the right context is the substantial part.

**Sources of grounding:**

```
Record fields              merge fields, cross-object
Related records            via a flow or Apex
Knowledge articles         retrieval from the knowledge base
Data Cloud                 unified profile, external data
Apex                       anything you can compute
```

**A grounded prompt with the wrong context produces a confident wrong answer**, which is worse than a generic one — because it looks authoritative.

## Where a developer fits

The features are largely configured. The developer's work is at four seams.

**Apex-invoked prompt templates**, where the grounding needs logic:

```java
ConnectApi.EinsteinPromptTemplateGenerationsInput input =
    new ConnectApi.EinsteinPromptTemplateGenerationsInput();
input.inputParams = buildGroundingParameters(claimId);
input.additionalConfig = config;

ConnectApi.EinsteinPromptTemplateGenerationsRepresentation response =
    ConnectApi.EinsteinLLM.generateMessagesForPromptTemplate('Claim_Reply', input);
```

**Custom Agentforce actions**, built as invocable Apex or as flows. See [[24.6 - Extending AI Features with Apex and LWC]].

**Retrieval logic** — assembling the context a prompt needs, which is frequently a selector method returning a shaped summary.

**Components rendering AI output**, with the review and editing surface a generated draft needs.

## What the platform does not do for you

Worth being direct about, because the marketing suggests otherwise.

**It does not know what "good" looks like.** There is no built-in evaluation. Whether the generated reply is accurate, appropriate, and useful is something the team must define and check.

**It does not prevent a confident wrong answer.** Grounding reduces hallucination; it does not eliminate it. A prompt grounded on a claim with a null approved amount will produce something for that field.

**It does not handle the failure case.** A prompt that returns nothing, or something inappropriate, needs a designed fallback.

**It does not decide whether AI is the right answer.** A "summarize this case" requirement is frequently better served by a well-designed compact layout.

## When AI is the right tool

**Yes when:**

- The output is text, and drafting it is genuinely time-consuming
- The input is unstructured — a long email thread, a call transcript
- The pattern is genuinely learnable from history, with enough of it
- A human reviews the output before it has consequence

**No when:**

- A formula, a validation rule, or a report gives a deterministic answer
- The consequence is automatic and unreviewed
- The training data is thin or biased
- The requirement is really "we should use AI"

**The test:** would a deterministic rule produce a correct answer? If yes, use the rule. AI earns its place where the input is unstructured or the pattern is genuinely statistical.

**A worked example.** "Predict which claims need executive approval" is a threshold — a formula field, not a model. "Draft a rejection letter explaining why coverage does not apply" is generative, because the explanation varies with circumstances that no template enumerates.

## Licensing and availability

Changes frequently, and the shape is stable:

```
Some predictive features       included in higher editions
Einstein Prediction Builder    licensed
Agentforce                     licensed, consumption-based in part
Prompt Builder                 licensed
Data Cloud                     licensed, consumption-based
Einstein Trust Layer           included with the generative features
```

**Generative features are consumption-priced in part**, which makes cost a design consideration — a prompt invoked on every case save has a different cost profile from one invoked on demand.

**Verify current availability rather than assuming.** This area changes faster than any other on the platform, and documentation written six months ago is frequently wrong.

## The architecture, in outline

```
User or automation
    ↓
Prompt template or Agentforce topic
    ↓
Grounding — merge fields, flow, Apex, retrieval
    ↓
Einstein Trust Layer
    masking of sensitive data
    prompt defense
    ↓
The model — Salesforce-hosted, or a customer-provided model
    ↓
Trust Layer
    toxicity detection
    zero retention — the provider does not keep the prompt
    audit trail
    ↓
Response
    ↓
Rendered for review, or passed to an action
```

**The Trust Layer is the part that makes this usable with customer data**, and understanding what it does and does not do is the subject of [[24.5 - Einstein Trust Layer]].

## What this section covers

Data Cloud, Prompt Builder, Agentforce, the Trust Layer, extending features with Apex and LWC, and responsible design.

**The recurring theme:** the model is the easy part. **The engineering is in the grounding, the guardrails, and the evaluation** — assembling the right context, constraining what the output can do, and knowing whether it is any good.
