# Custom Logging Frameworks

## Why debug logs are not enough

**Logs are not retroactive.** An error at 09:32 with no trace flag set produced nothing. The most common production incident — "it failed yesterday for three users" — has no debug log at all.

**Logs are transient.** Seven days, and a 1,000 MB org-wide cap that a busy integration user fills in hours.

**Logs are not queryable.** "How often has this failed this month" cannot be answered.

**Logs are per-transaction.** Correlating a publish with its subscriber means matching request Ids by hand.

A custom logging framework writes a **record** — durable, queryable, reportable, and always on.

## The log object

```
Application_Log__c
    Context__c            Text(255)      'ClaimApproval'
    Severity__c           Picklist       Debug / Info / Warning / Error / Fatal
    Message__c            Long Text
    Stack_Trace__c        Long Text
    Record_Id__c          Text(18)
    Related_Record__c     Lookup or Text
    Correlation_Id__c     Text(64)       ties a transaction together
    Transaction_Id__c     Text(64)       Request.getCurrent().getRequestId()
    Running_User__c       Lookup(User)
    Class_Name__c         Text(255)
    Method_Name__c        Text(255)
    Line_Number__c        Number
    Queries_Used__c       Number
    Cpu_Ms__c             Number
    Logged_At__c          DateTime
    Source__c             Picklist       Apex / Flow / LWC / Integration
```

**`Correlation_Id__c` and `Transaction_Id__c` are the two that make it useful.** Without them, a log is a list of unrelated messages; with them, a business operation can be traced across a trigger, a Queueable, and a platform event subscriber.

## The rollback problem

The defining constraint, and the reason a naive implementation fails.

```java
try {
    processClaims(claims);
} catch (Exception e) {
    insert new Application_Log__c(Message__c = e.getMessage());
    throw e;   // the log insert is rolled back with everything else
}
```

**Catch without rethrowing and the log survives, but the error is swallowed. Rethrow and the log is gone.**

Three mechanisms solve it, each for a different context.

**Platform events with immediate publish behaviour**, which survive rollback by design:

```java
public with sharing class Logger {

    private static final List<Application_Log__e> buffer = new List<Application_Log__e>();

    public static void error(String context, Id recordId, Exception e) {
        buffer.add(buildEvent(context, 'Error', recordId, e.getMessage(),
            e.getStackTraceString()));
    }

    public static void flush() {
        if (buffer.isEmpty()) {
            return;
        }
        // immediate publish behaviour means these survive a rollback
        EventBus.publish(buffer);
        buffer.clear();
    }
}
```

```java
trigger ApplicationLogEventTrigger on Application_Log__e (after insert) {
    ApplicationLogHandler.persist(Trigger.new);
}
```

The subscriber runs in its own transaction and writes the records.

**Transaction Finalizers**, for async failures — the finalizer runs in a fresh transaction where a plain insert works:

```java
public void execute(FinalizerContext ctx) {
    if (ctx.getResult() == ParentJobResult.SUCCESS) {
        return;
    }
    insert new Application_Log__c(
        Context__c = context,
        Severity__c = 'Error',
        Message__c = ctx.getException()?.getMessage(),
        Transaction_Id__c = ctx.getRequestId()
    );
}
```

See [[12.6 - Transaction Finalizers]].

**A savepoint rollback, then insert** — the log written after the rollback commits:

```java
Savepoint sp = Database.setSavepoint();
try {
    processClaims(claims);
} catch (Exception e) {
    Database.rollback(sp);
    // after the rollback, so this survives
    insert buildLog('ClaimProcessing', e);
}
```

Simplest when you are already catching, and it does not work when the exception propagates.

## Buffering

Writing a log per message is expensive — a DML statement each time.

```java
public with sharing class Logger {

    private static final List<Application_Log__e> buffer = new List<Application_Log__e>();
    private static final String CORRELATION_ID = generateCorrelationId();

    public static void info(String context, String message) {
        add('Info', context, null, message, null);
    }

    public static void warn(String context, Id recordId, String message) {
        add('Warning', context, recordId, message, null);
    }

    public static void error(String context, Id recordId, Exception e) {
        add('Error', context, recordId, e.getMessage(), e.getStackTraceString());
    }

    private static void add(String severity, String context, Id recordId,
                            String message, String stackTrace) {
        buffer.add(new Application_Log__e(
            Context__c = context,
            Severity__c = severity,
            Message__c = message?.left(131072),
            Stack_Trace__c = stackTrace?.left(131072),
            Record_Id__c = recordId,
            Correlation_Id__c = CORRELATION_ID,
            Transaction_Id__c = Request.getCurrent().getRequestId(),
            Queries_Used__c = Limits.getQueries(),
            Cpu_Ms__c = Limits.getCpuTime(),
            Logged_At__c = Datetime.now()
        ));
    }

    public static void flush() {
        if (buffer.isEmpty()) {
            return;
        }
        EventBus.publish(buffer);
        buffer.clear();
    }
}
```

**One `EventBus.publish` at the end of the transaction** is one DML statement regardless of how many messages accumulated.

**`Request.getCurrent().getRequestId()`** is the platform's own transaction identifier, and it correlates with debug logs and Event Monitoring — which is what lets a custom log entry be traced back to a platform log.

**Capturing `Limits.getQueries()` and `getCpuTime()`** at log time turns the log into a performance record as well as an error record.

## Where to flush

The buffer must be flushed, and forgetting is the common defect.

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        try {
            dispatch();
        } finally {
            // finally, so logs are published whether or not the handler threw
            Logger.flush();
        }
    }
}
```

**`finally` rather than at the end of the happy path.** A handler that throws should still publish its logs.

For Lightning controllers, the same pattern wraps the `@AuraEnabled` method. For batch jobs, `finish` is the right place, plus a flush in `execute` for per-chunk logs.

## Severity discipline

```
Debug     developer diagnostics, off in production
Info      significant business events — a claim approved, a batch completed
Warning   something unexpected that was handled — a retry, a missing optional record
Error     an operation failed and a user or process is affected
Fatal     the system is in a bad state — a data integrity problem, an exhausted allocation
```

**The discipline that keeps the log useful:** if everything is logged at Error, nobody reads the Error list.

**Info is where most value sits in practice** — a record of what the system did, which answers "was this claim ever synced" without a debug log.

**Debug should be off in production**, gated by a Custom Setting so it can be enabled per user during an incident:

```java
private static Boolean debugEnabled() {
    Logging_Settings__c settings = Logging_Settings__c.getInstance();
    return settings?.Enable_Debug_Logging__c == true;
}
```

The hierarchy setting means an administrator can turn it on for one user, live, without a deployment. See [[17.2 - Custom Settings]].

## Logging from flows

The gap most implementations miss.

```java
public with sharing class LoggerActions {

    public class Request {
        @InvocableVariable(required=true) public String context;
        @InvocableVariable(required=true) public String message;
        @InvocableVariable public String severity;
        @InvocableVariable public String recordId;
    }

    @InvocableMethod(label='Log Message'
                     description='Writes an entry to the application log')
    public static void log(List<Request> requests) {
        for (Request request : requests) {
            Logger.add(request.severity ?? 'Info', request.context,
                request.recordId, request.message, null);
        }
        // flows have no transaction hook, so flush immediately
        Logger.flush();
    }
}
```

**Attached to a flow's fault path**, this is what turns a silent flow failure into a record. A flow with no fault handling fails invisibly — the user sees a generic error and nothing is recorded. See [[07.8 - Flow Error Handling and Fault Paths]].

## Logging from LWC

```javascript
import logClientError from '@salesforce/apex/ClientLogController.log';

async reportError(context, error) {
    try {
        await logClientError({
            context,
            message: error?.message ?? String(error),
            stack: error?.stack,
            pageUrl: window.location.href
        });
    } catch (loggingError) {
        // logging must never throw — a failed log is not worth breaking the page
        console.error('Failed to log', loggingError);
    }
}
```

The nested try/catch is essential. A logging call that throws inside an error handler produces a second error and frequently a loop.

## Retention

Logs grow, and they consume data storage.

```java
public with sharing class LogPurgeBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id FROM Application_Log__c
            WHERE Logged_At__c < LAST_N_DAYS:90
              AND Severity__c IN ('Debug', 'Info')
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Application_Log__c> scope) {
        Database.delete(scope, false);
        // purging inside execute keeps the recycle bin from overflowing mid-job
        Database.emptyRecycleBin(scope);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Different retention by severity.** Debug and Info for 90 days; Error and Fatal for a year or archived to a big object.

Scheduled weekly, staggered away from other jobs. See [[12.5 - Scheduled Apex]].

## Making it operational

A log nobody looks at is storage consumption with no benefit.

**A dashboard** — errors by context over time, top failing operations, error rate trend.

**A daily alert** on Fatal and on error-rate spikes.

**Alert on absence**, which is the failure mode monitoring usually misses:

```sql
SELECT Context__c, MAX(Logged_At__c) lastSeen
FROM Application_Log__c
WHERE Severity__c = 'Info' AND Logged_At__c = LAST_N_DAYS:7
GROUP BY Context__c
```

An integration that logged a success every hour and has logged nothing for six is broken. No error was raised, no job failed, and only this query notices.

**Export to an external platform** — Splunk, Datadog, or a warehouse — for anything with real operational scale, since Salesforce reports are a poor log-analysis tool.

## Nebula Logger

Rather than building this, **Nebula Logger** is a mature open-source implementation covering all of it: Apex, flow, and LWC logging, platform event durability, correlation, retention, and a log viewer component.

For most orgs it is the better choice than a hand-rolled framework — it is more complete than what a team will build, and it is maintained.

Building your own is justified when the requirements are unusual, when a dependency is unacceptable, or when the org already has one that works.

## What not to log

**Personal data, payment details, and health information.** A log table full of customer detail is a compliance problem created by well-intentioned debugging. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

**Credentials and tokens**, obviously, and it happens — a logged request body containing an Authorization header.

**Entire request and response payloads** as a matter of routine. On failure, truncated, is reasonable.

**Every record processed.** A batch job logging per record produces 200,000 rows and no insight.

## Practical guidance

**Publish through platform events** so logs survive rollback.

**Buffer and flush once**, in a `finally` block.

**Capture a correlation Id and the request Id** — they are what make the log traceable.

**Capture limit consumption** so the log doubles as a performance record.

**Use severity meaningfully**, and gate Debug behind a hierarchy setting.

**Provide an invocable action** so flows can log from fault paths.

**Never let logging throw.**

**Purge on a schedule**, with different retention by severity.

**Alert on absence**, not just on errors.

**Consider Nebula Logger** before building your own.
