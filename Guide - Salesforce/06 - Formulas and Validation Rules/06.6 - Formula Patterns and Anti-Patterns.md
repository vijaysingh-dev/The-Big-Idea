# Formula Patterns and Anti-Patterns

## Patterns worth knowing

### The checkbox formula

A formula returning a checkbox expresses a condition **once** and reuses it in reports, list views, validation rules, flow entry criteria, and other formulas.

```
// Is_At_Risk__c
AND(
  NOT(ISBLANK(End_Date__c)),
  End_Date__c <= TODAY() + 90,
  ISPICKVAL(Status__c, "Active"),
  ISBLANK(TEXT(Renewal_Opportunity__c))
)
```

Now the definition of "at risk" lives in one place. Without it, the same logic gets restated in a report filter, a list view filter, a flow, and a validation rule — four copies that drift apart.

This is the highest-value formula pattern and the most underused.

### Status indicators

```
// Traffic light against an SLA target
IMAGE(
  CASE(
    SIGN(Days_Open__c - SLA_Days__c),
    -1, "/resource/StatusIcons/green.png",
     0, "/resource/StatusIcons/amber.png",
        "/resource/StatusIcons/red.png"
  ),
  "SLA status"
)
```

`SIGN()` returning -1, 0, or 1 combined with `CASE` is cleaner than nested `IF` for three-way comparisons.

Reference a Static Resource rather than the built-in sample images, which are undocumented and could change. See [[17.4 - Static Resources]].

### Hierarchy display

```
// Readable position for a record in a hierarchy
IF(
  ISBLANK(Parent_Machine__c),
  "Top level",
  IF(
    ISBLANK(Parent_Machine__r.Parent_Machine__c),
    "Level 2: under " & Parent_Machine__r.Name,
    "Level 3+: under " & Parent_Machine__r.Name
  )
)
```

Two spanning relationships, bounded depth. Deeper than this and a stamped level field is the better answer. See [[02.9 - Hierarchical and Self Relationships]].

### Safe division

Division by zero produces an error that blocks the save, not a null.

```
// Guarded percentage
IF(
  OR(ISBLANK(Claim_Amount__c), Claim_Amount__c = 0),
  0,
  ROUND(Approved_Amount__c / Claim_Amount__c * 100, 1)
)
```

Every division in a formula needs this guard. It is the most common cause of a formula field that works in testing and throws in production, because the test data never had a zero.

### Custom permission gating

```
// Only holders of the permission may change this field
AND(
  ISCHANGED(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims)
)
```

The maintainable alternative to profile name checks, and it makes "who can do this" a queryable question.

## Anti-patterns

### Hardcoded IDs

```
// Breaks in every org except the one it was written in
RecordTypeId = "0125g000000XyZaAAK"
OwnerId = "0055g00000ABCDeAAN"
```

Record type and user IDs differ per org. Sandbox works, production fails.

```
// Portable
RecordType.DeveloperName = "Warranty_Claim"
```

For user references, a lookup field populated by automation, or a hierarchy custom setting holding the ID per org.

### Hardcoded profile names

```
// Breaks when a new profile is created that should also qualify
$Profile.Name = "Warranty Approver"
```

Profile names change, orgs accumulate profiles, and this silently excludes people who should be included. Use `$Permission` instead.

### Comparing picklists to labels

```
// Breaks in translated orgs and when a label is renamed
TEXT(Status__c) = "Approved"
```

`TEXT()` returns the API name. If the label happens to match the API name today, this works by coincidence. Use `ISPICKVAL`, which compares against the API name explicitly.

### Formulas that should be stored fields

A formula filtered on across a multi-million-row object produces a non-selective query. The symptom is a report or list view that times out, and the cause is invisible in the formula itself.

If it is filtered at volume, store it. See [[08.9 - Indexes and Selective Queries]].

### Formula chains

Formula A references B references C references D. Each is readable. The compiled size of A is enormous, and changing D breaks A in a way nobody predicts.

Two levels is a reasonable ceiling. Beyond that, stamp a value with automation.

### Ignoring nulls

```
// Returns null, not the amount, when Discount__c is empty
Amount__c - Discount__c
```

Relying on the "treat blanks as zeroes" checkbox works and is invisible to whoever reads the formula next. Be explicit with `BLANKVALUE`.

### Validation rules with no bypass

A rule with no escape hatch gets deactivated during the first data migration and stays deactivated. Build the bypass in when you build the rule. See [[06.5 - Validation Rules]].

### Business day arithmetic in formulas

The weekend-exclusion formula is unreadable and still ignores holidays. Use entitlement milestones or `BusinessHours` in Apex.

### Unreadable nesting

A forty-line nested `IF` that works is still a liability, because the next person to change it will get it wrong. Where nesting exceeds three or four levels, either restructure with `CASE`, split into helper fields, or move to Apex.

## Choosing the right tool

The decision that section 06 and section 07 together are really about:

| Need | Tool |
| --- | --- |
| Derived value from this record or a parent, always current | Formula field |
| Aggregate of children, master-detail | Roll-up summary |
| Aggregate of children, lookup | Flow or Apex |
| Value filtered at high volume | Stored field, set by flow or trigger |
| Value a user must be able to override | Stored field |
| Value that must trigger downstream automation | Stored field |
| Simple invariant, expressible in one expression | Validation rule |
| Invariant needing a query or child records | Apex `addError` |
| Logic needing loops, callouts, or bulk processing | Apex |

Three of those rows exist because of things formulas cannot do, and they are worth restating:

**A formula field changing does not fire automation.** The record was never updated, so no trigger and no record-triggered flow runs. Automation that must react to a derived value cannot watch a formula field.

**A formula field cannot be written to.** Not by a user, not by an integration, not by Apex. If a value ever needs manual override, it cannot be a formula.

**A formula field is generally not indexed.** Filtering on it at scale does not perform.

## Section 06 in one paragraph

Formulas are a single-expression language with no variables and no loops, evaluated at read time for formula fields and at save time for validation rules. Nulls propagate rather than defaulting to zero, picklists need `ISPICKVAL` or `TEXT()`, and dates are simpler than datetimes because they carry no time zone. The binding constraints are the 5,000-byte compiled size, which expands when formulas reference formulas, and the fifteen spanning relationships shared across every formula, validation rule, and roll-up filter on an object. Validation rules invert the logic — true blocks the save — apply to every entry path including integrations and data loads, and therefore need a deliberate bypass mechanism built in from the start. The recurring judgement is when a derived value should stop being computed and start being stored: the answer is whenever it must be filtered at volume, overridden by a user, or reacted to by automation.
