# LIMIT, OFFSET, ORDER BY and Pagination

## ORDER BY

```sql
SELECT Id, Claim_Number__c, Claim_Amount__c, Claim_Date__c
FROM Warranty_Claim__c
WHERE Status__c = 'Submitted'
ORDER BY Claim_Amount__c DESC, Claim_Date__c ASC NULLS LAST
LIMIT 50
```

`ASC` is the default. `NULLS FIRST` and `NULLS LAST` control where empty values land — the default is `NULLS FIRST` for ascending, which puts empty amounts at the top of a "largest claims" list and is almost never what you want.

Always specify `NULLS LAST` when sorting on a nullable field descending. It is a one-word fix for a confusing display.

**Sorting on a non-indexed field forces the engine to sort the full result set**, which on a large object is expensive. Sorting on an indexed field, or on a field the query already filters selectively, is much cheaper.

**Without `ORDER BY`, row order is not guaranteed.** It often looks stable and is not a contract. Any code depending on order needs an explicit `ORDER BY`, and pagination absolutely requires one — without it, the same row can appear on two pages.

## LIMIT

```sql
SELECT Id, Name FROM Account ORDER BY CreatedDate DESC LIMIT 10
```

`LIMIT` caps rows returned and, importantly, **caps what counts toward the 50,000-row transaction limit**. Adding a `LIMIT` to an exploratory query is the difference between a slow anonymous Apex block and a failed one.

A bind variable works:

```java
Integer pageSize = 50;
List<Account> accounts = [SELECT Id, Name FROM Account ORDER BY Name LIMIT :pageSize];
```

## OFFSET, and why it does not scale

```sql
SELECT Id, Name FROM Account ORDER BY Name LIMIT 25 OFFSET 50
```

**`OFFSET` is capped at 2,000.** Beyond that the query fails. This is a hard limit and there is no way around it.

Worse, `OFFSET` is inefficient even below the cap: the engine retrieves and discards every row before the offset. `OFFSET 1900` scans 1,925 rows to return 25.

`OFFSET` is acceptable for a small result set a user browses — a picklist of options, a short list. It is the wrong tool for paginating a large table, and building a UI on it means the user hits a wall at page 81.

## Keyset pagination

The correct approach for anything sizeable: remember the last record's sort value and filter past it.

```java
public with sharing class ClaimPagingService {

    public class Page {
        @AuraEnabled public List<Warranty_Claim__c> records;
        @AuraEnabled public String nextCursor;
        @AuraEnabled public Boolean hasMore;
    }

    @AuraEnabled(cacheable=true)
    public static Page getPage(String cursor, Integer pageSize) {
        Integer fetchSize = pageSize + 1;
        List<Warranty_Claim__c> claims;

        if (String.isBlank(cursor)) {
            claims = [
                SELECT Id, Claim_Number__c, Claim_Date__c, Claim_Amount__c, Status__c
                FROM Warranty_Claim__c
                WHERE Status__c = 'Submitted'
                WITH USER_MODE
                ORDER BY Claim_Date__c DESC, Id DESC
                LIMIT :fetchSize
            ];
        } else {
            // the cursor carries the sort value of the last row on the previous page
            Datetime lastDate = (Datetime) JSON.deserialize(cursor, Datetime.class);
            claims = [
                SELECT Id, Claim_Number__c, Claim_Date__c, Claim_Amount__c, Status__c
                FROM Warranty_Claim__c
                WHERE Status__c = 'Submitted' AND Claim_Date__c < :lastDate
                WITH USER_MODE
                ORDER BY Claim_Date__c DESC, Id DESC
                LIMIT :fetchSize
            ];
        }

        Page page = new Page();
        page.hasMore = claims.size() > pageSize;
        if (page.hasMore) {
            claims.remove(pageSize);
        }
        page.records = claims;
        page.nextCursor = claims.isEmpty()
            ? null
            : JSON.serialize(claims[claims.size() - 1].Claim_Date__c);
        return page;
    }
}
```

Two techniques in there worth naming.

**Fetching one extra row** determines whether a next page exists without a separate count query.

**Including `Id` as a tiebreaker** in `ORDER BY` makes the sort deterministic when the primary sort field has duplicates. Without it, two claims on the same date can appear on both pages or neither.

The tradeoff: keyset pagination supports next and previous, but not "jump to page 40". In practice users rarely need that, and a filter is a better answer than a page number.

## Counting

```java
Integer total = [SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Submitted'];
```

`COUNT()` does not consume the row limit for the rows counted, so it is cheap in that sense. It still scans, so it is subject to the same selectivity constraints as any query.

For a paginated UI, avoid a total count if you can. Showing "showing 25 of many" is honest and free; computing an exact total on a large filtered set is expensive and rarely worth it.

## Query more, in the API

The REST and SOAP APIs paginate automatically. A query returning more than the batch size includes a `nextRecordsUrl`, and the client follows it.

```
GET /services/data/v62.0/query?q=SELECT+Id,Name+FROM+Account

{
  "totalSize": 4213,
  "done": false,
  "records": [ ... 2000 records ... ],
  "nextRecordsUrl": "/services/data/v62.0/query/01g5g00000ABCDeAAN-2000"
}
```

The batch size can be requested through the `Sforce-Query-Options` header, up to 2,000.

This is server-side cursor pagination and it has none of `OFFSET`'s problems. For an external integration reading a large table, this is the mechanism — not `OFFSET`, and not manually constructed date ranges. See [[13.2 - REST API]].

## Bulk processing in Apex

For processing rather than display, `OFFSET` is never the answer.

**A `for` loop over the query** processes in chunks of 200 with bounded heap:

```java
for (List<Warranty_Claim__c> chunk : [
    SELECT Id, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
]) {
    for (Warranty_Claim__c claim : chunk) {
        claim.Status__c = 'Under Review';
    }
    update chunk;
}
```

Still bounded by the 50,000-row transaction limit.

**`Database.getQueryLocator` in Batch Apex** handles up to 50 million rows and is the correct tool for anything larger. See [[12.4 - Batch Apex]].

**`Database.QueryLocatorIterator`** allows manual cursor iteration outside a batch context, which is occasionally useful:

```java
Database.QueryLocator locator = Database.getQueryLocator([
    SELECT Id, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
]);
Database.QueryLocatorIterator iterator = locator.iterator();

while (iterator.hasNext()) {
    Warranty_Claim__c claim = (Warranty_Claim__c) iterator.next();
}
```

## Sorting in Apex instead

When the result set is already retrieved and small, sorting in memory avoids a second query.

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Amount__c, Claim_Date__c FROM Warranty_Claim__c WHERE Asset__c = :assetId
];
claims.sort();  // uses the object's default sort order
```

For custom ordering, implement `Comparable`:

```java
public class ClaimByValue implements Comparable {
    public Warranty_Claim__c claim;

    public ClaimByValue(Warranty_Claim__c claim) {
        this.claim = claim;
    }

    public Integer compareTo(Object other) {
        Decimal thisAmount = claim.Claim_Amount__c == null ? 0 : claim.Claim_Amount__c;
        Decimal otherAmount = ((ClaimByValue) other).claim.Claim_Amount__c;
        otherAmount = otherAmount == null ? 0 : otherAmount;
        return thisAmount > otherAmount ? -1 : (thisAmount < otherAmount ? 1 : 0);
    }
}
```

Null handling in the comparator matters — comparing a null Decimal throws.

In-memory sorting consumes CPU rather than a query, so it is the right trade when the set is small and a query is scarce, and the wrong one when the set is large.

## Practical guidance

**Always `ORDER BY` when order matters**, and always include `Id` as a tiebreaker for pagination.

**Specify `NULLS LAST`** on descending sorts over nullable fields.

**Do not build pagination on `OFFSET`.** The 2,000 cap arrives sooner than expected.

**Use keyset pagination** for user-facing lists, fetching one extra row to detect the next page.

**Use `nextRecordsUrl`** for API consumers.

**Use Batch Apex** for processing large sets, never a paging loop.

**Avoid exact total counts** on large filtered sets in a UI.
