# Classes, Constructors and Access Modifiers

## Class structure

```java
public with sharing class WarrantyClaimService {

    private static final Decimal AUTO_APPROVE_THRESHOLD = 50000;

    private final ClaimSelector selector;
    private final NotificationService notifier;

    public WarrantyClaimService() {
        this(new ClaimSelector(), new NotificationService());
    }

    // the injectable constructor is what makes this class testable with mocks
    public WarrantyClaimService(ClaimSelector selector, NotificationService notifier) {
        this.selector = selector;
        this.notifier = notifier;
    }

    public void approveEligible(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = selector.selectOpenByIds(claimIds);
        List<Warranty_Claim__c> approved = new List<Warranty_Claim__c>();

        for (Warranty_Claim__c claim : claims) {
            if (isAutoApprovable(claim)) {
                claim.Status__c = 'Approved';
                claim.Approved_Amount__c = claim.Claim_Amount__c;
                approved.add(claim);
            }
        }

        if (!approved.isEmpty()) {
            update approved;
            notifier.notifyApproval(approved);
        }
    }

    private Boolean isAutoApprovable(Warranty_Claim__c claim) {
        return claim.Claim_Amount__c != null
            && claim.Claim_Amount__c <= AUTO_APPROVE_THRESHOLD
            && claim.Evidence_Attached__c;
    }
}
```

The pattern in that constructor pair — a no-argument constructor delegating to one that accepts dependencies — is the simplest form of dependency injection and it is what makes the class unit-testable without touching the database. See [[18.8 - Dependency Injection and Testability]].

## Access modifiers

**`private`** — the class only. **This is the default**, including at class level, which differs from Java's package-private default.

**`protected`** — the class and its subclasses.

**`public`** — anywhere in the same namespace. In an unpackaged org that is the whole org.

**`global`** — across namespaces. Required for anything a managed package exposes, for `@RestResource`, for `webservice` methods, and for some interface implementations like `Schedulable` used from a package.

The guidance: **use `public` for the org's own code and `global` only when genuinely required.** A `global` method in a managed package can never be removed or have its signature changed, because subscribers may depend on it. Even outside packaging, `global` is a signal that the method is an external contract.

Members are `private` unless declared otherwise. Being explicit about `private` on fields and helper methods reads better than relying on the default.

## Sharing keywords

Every class should declare one. See [[03.13 - Enforcing Security in Apex and SOQL]].

```java
public with sharing class ClaimService { }        // record access enforced
public without sharing class ClaimAdminService { } // record access ignored
public inherited sharing class ClaimUtils { }      // takes the caller's mode
```

A class with **no keyword runs without sharing** when entered directly — from a Lightning controller, a REST endpoint, or an anonymous block. Omitting it is a security decision made by accident, which is why every class should declare one explicitly.

`inherited sharing` is the right default for reusable utilities: it neither opens access silently nor restricts a caller that needed system mode.

Inner classes inherit the outer class's sharing and cannot override it.

## Inner classes

```java
public with sharing class ClaimResponse {

    @AuraEnabled public Boolean success;
    @AuraEnabled public String message;
    @AuraEnabled public List<ClaimSummary> claims;

    public class ClaimSummary {
        @AuraEnabled public Id claimId;
        @AuraEnabled public String claimNumber;
        @AuraEnabled public Decimal amount;
        @AuraEnabled public String status;
    }
}
```

Inner classes are the standard way to define wrapper and data-transfer types. They can be one level deep only — no inner class inside an inner class.

`@AuraEnabled` on properties is what makes them serializable to a Lightning Web Component. Without it, the property is invisible on the client side, which is a frequent and confusing omission. See [[14.10 - Calling Apex - Wire vs Imperative]].

Inner classes are also how `@InvocableMethod` request and result types are defined ([[07.9 - Invocable Apex and Flow-Apex Interop]]).

## Properties

Apex supports property syntax, which is cleaner than explicit getters and setters:

```java
public class ClaimSummary {

    // auto-implemented, publicly readable, privately writable
    public Id claimId { get; private set; }

    public Decimal claimAmount { get; set; }

    // computed on read
    public Boolean isHighValue {
        get { return claimAmount != null && claimAmount > 500000; }
    }

    // with validation in the setter
    private Decimal approvedAmount;
    public Decimal approvedValue {
        get { return approvedAmount; }
        set {
            if (value != null && value < 0) {
                throw new IllegalArgumentException('Approved amount cannot be negative');
            }
            approvedAmount = value;
        }
    }
}
```

`value` is the implicit parameter in a setter. Different access levels on get and set is the useful part — `{ get; private set; }` gives an externally read-only field without writing a getter method.

## Constructors

```java
public class ClaimRequest {
    public Id assetId;
    public Decimal amount;
    public String description;

    public ClaimRequest() { }

    public ClaimRequest(Id assetId, Decimal amount) {
        this.assetId = assetId;
        this.amount = amount;
    }

    public ClaimRequest(Id assetId, Decimal amount, String description) {
        this(assetId, amount);   // delegate to the shorter constructor
        this.description = description;
    }
}
```

`this(...)` must be the first statement. Overloading is supported and resolved by signature.

**Defining any constructor removes the implicit no-argument one.** A class with a two-argument constructor and no explicit no-arg constructor cannot be instantiated with `new ClaimRequest()`. This matters for JSON deserialization, which needs a no-argument constructor.

## Method overloading

```java
public void approve(Id claimId) { }
public void approve(Set<Id> claimIds) { }
public void approve(Set<Id> claimIds, Decimal amount) { }
```

The convention worth adopting: **every public method that touches records takes a collection.** A single-record overload invites someone to call it in a loop, which reintroduces the problem bulkification exists to prevent.

Where a single-record convenience method is genuinely useful, implement it by delegating:

```java
public void approve(Id claimId) {
    approve(new Set<Id>{ claimId });
}
```

The bulk-safe path is then the only implementation.

## Static versus instance

```java
public with sharing class ClaimService {

    // stateless utility — static is appropriate
    public static Boolean isAutoApprovable(Warranty_Claim__c claim) { }

    // holds dependencies — instance is appropriate
    private final ClaimSelector selector;
    public List<Warranty_Claim__c> loadOpen(Set<Id> ids) { }
}
```

Static methods are simpler to call and harder to mock. Instance methods with injected dependencies are more testable.

The practical split most codebases settle on: **static for genuinely stateless helpers, instance for anything with dependencies you might want to replace in a test.** Service layers that call selectors and other services benefit from being instance-based; pure calculation utilities do not.

Static state persists for the whole transaction, which is a separate concern covered in [[09.8 - Static Members and Class Level State]].

## Naming

Class names must be unique across the org — there is no package system. Conventions that hold up:

```
WarrantyClaimService          business logic
WarrantyClaimSelector         queries
WarrantyClaimTriggerHandler   trigger dispatch
WarrantyClaimController       Lightning controller
ClaimApprovalQueueable        async job
WarrantyClaimServiceTest      tests
ClaimSharingService           a specific concern
```

Suffixes carrying the role make the codebase navigable, and they matter more here than in a language with namespaces. The layered structure behind these names is covered in section 18.

## File structure

One class per file, `.cls`, with a `.cls-meta.xml` alongside carrying the API version and status.

```
force-app/main/default/classes/
    WarrantyClaimService.cls
    WarrantyClaimService.cls-meta.xml
    WarrantyClaimServiceTest.cls
    WarrantyClaimServiceTest.cls-meta.xml
```

Test classes conventionally live beside the class they test with a `Test` suffix, and some teams place them in a separate directory. Either works; consistency matters more than the choice.

## Practical guidance

**Declare a sharing keyword on every class.** No keyword means without sharing.

**Use `public`, reserve `global`** for genuine external contracts.

**Take collections in every public method** that touches records.

**Use inner classes for wrappers**, with `@AuraEnabled` where a component consumes them.

**Use `{ get; private set; }`** rather than writing accessor methods.

**Inject dependencies through a constructor** where the class calls other services.

**Name by role**, since there is no namespace to disambiguate.
