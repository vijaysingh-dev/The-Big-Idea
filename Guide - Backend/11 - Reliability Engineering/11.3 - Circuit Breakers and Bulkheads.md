# Circuit Breakers and Bulkheads

#backend #reliability #patterns

> **In one line:** A circuit breaker stops you from calling a dependency that is already failing; a bulkhead stops that dependency's failure from consuming resources the rest of your system needs.

---

## The Circuit Breaker

```
CLOSED ──failures exceed threshold──► OPEN
   ▲                                    │
   │                              after a timeout
   │                                    ▼
   └──── success ──── HALF-OPEN ── failure ──► OPEN
```

| State | Behaviour |
|---|---|
| **Closed** | Requests pass through. Failures are counted |
| **Open** | **Requests fail immediately** without calling |
| **Half-open** | A limited number of probes are allowed through |

💡 **The point is not to protect the failing service — it is to protect the caller.** A caller that keeps calling a dead dependency holds workers, exhausts its pool, and fails at everything else it does ([[11.1 - How Systems Fail]]).

⚠️ **Without a breaker, a dependency's outage becomes your outage** — you spend your entire capacity waiting for timeouts.

### The implementation

```python
class CircuitBreaker:
    def __init__(self, *, failure_threshold: float = 0.5, minimum_requests: int = 20,
                 window: float = 10.0, open_duration: float = 30.0,
                 half_open_max: int = 3):
        self.state = "closed"
        self.opened_at = 0.0
        self.half_open_inflight = 0
        self._window = SlidingWindow(window)
        ...

    def allow(self) -> bool:
        if self.state == "closed":
            return True

        if self.state == "open":
            if time.monotonic() - self.opened_at >= self.open_duration:
                self.state = "half_open"
                self.half_open_inflight = 0
            else:
                return False

        if self.state == "half_open":
            if self.half_open_inflight >= self.half_open_max:
                return False
            self.half_open_inflight += 1
            return True

    def record(self, success: bool) -> None:
        self._window.add(success)

        if self.state == "half_open":
            self.half_open_inflight -= 1
            if success:
                self.state = "closed"
                self._window.reset()
            else:
                self.state = "open"
                self.opened_at = time.monotonic()
            return

        if self._window.total() >= self.minimum_requests \
           and self._window.failure_ratio() >= self.failure_threshold:
            self.state = "open"
            self.opened_at = time.monotonic()
```

### The parameters that matter

| Parameter | Getting it wrong |
|---|---|
| **`minimum_requests`** | Too low: a breaker trips on 2 failures out of 3 during quiet periods |
| **`failure_threshold`** | Too low: trips on normal error rates. Too high: never trips |
| **`window`** | Too long: slow to react. Too short: noisy |
| **`open_duration`** | Too short: hammers a recovering service. Too long: stays down after recovery |
| **`half_open_max`** | Too high: a thundering herd on a fragile service |

💡 **`minimum_requests` is the one most often omitted, and it causes the most confusion.** A breaker with no minimum will trip on a single failure at 3am when traffic is low, and stay open — producing an outage from a blip.

⚠️ **Use a ratio over a sliding window, not a consecutive-failure count.** Consecutive counting misses a service failing 50% of the time, which is often worse than one failing completely.

### What counts as a failure

```python
except (ConnectionError, TimeoutError, ServiceUnavailable):
    breaker.record(success=False)
except HTTPStatusError as e:
    breaker.record(success=e.response.status_code < 500)     # 4xx is not their fault
```

⚠️ **A 400 means your request was wrong, not that the service is unhealthy.** Counting 4xx toward the breaker means a client sending bad requests trips the breaker for everyone.

💡 **Timeouts should count as failures**, and they are usually the dominant signal — a service that is slow rather than down produces timeouts, not errors.

## Bulkheads

Named after ship compartments: a breach floods one section, not the vessel.

```
❌  One connection pool of 50, shared
    → a slow dependency consumes all 50, everything blocks

✅  documents:  20
    search:     10
    billing:     5
    → search failing consumes 10, leaving 25 for everything else
```

### Per-dependency pools

```python
pools = {
    "documents": httpx.AsyncClient(limits=httpx.Limits(max_connections=20)),
    "search":    httpx.AsyncClient(limits=httpx.Limits(max_connections=10)),
    "billing":   httpx.AsyncClient(limits=httpx.Limits(max_connections=5)),
}
```

💡 **The isolation is the point, not the sizing.** A dependency that hangs can consume at most its own allocation.

⚠️ **The sum of the pools must fit your worker count**, or you have simply moved the exhaustion point.

### Concurrency limits

```python
limits = {
    "documents": asyncio.Semaphore(20),
    "search":    asyncio.Semaphore(10),
    "embedding": asyncio.Semaphore(4),      # expensive, protect it
}

async def call(service: str, fn):
    try:
        await asyncio.wait_for(limits[service].acquire(), timeout=0.1)
    except TimeoutError:
        bulkhead_rejected.labels(service=service).inc()
        raise ServiceOverloaded(service)     # ← fail fast, do not queue
    try:
        return await fn()
    finally:
        limits[service].release()
```

💡 **The acquire timeout is what makes it a bulkhead rather than a queue.** Waiting indefinitely for a semaphore is the same failure as waiting for the dependency ([[01.11 - Backpressure Inside One Process]]).

⚠️ **Bulkheads must fail fast when full.** A bulkhead with an unbounded wait queue provides isolation of the dependency and not of your workers.

### Thread and process isolation

```python
# CPU-bound work in its own executor, so it cannot starve I/O handling
cpu_pool = ProcessPoolExecutor(max_workers=4)
result = await loop.run_in_executor(cpu_pool, parse_pdf, content)
```

💡 **Separate pools per work type** ([[01.8 - Offloading Work]]). A slow PDF parse should not consume the executor that image thumbnailing needs.

### Deployment-level bulkheads

```yaml
deployment: api-critical      # auth, payments
deployment: api-standard      # everything else
```

💡 **Separate deployments are the strongest bulkhead**, because they isolate memory, CPU and process crashes — not just logical resources ([[10.1 - Monolith Modular Monolith Microservices]]).

⚠️ **Shuffle sharding is the advanced version**: assign each tenant a random subset of instances, so one abusive tenant affects only the instances it shares — and the probability that two tenants share *all* their instances is tiny.

## Combined

```python
async def call(service: str, fn, *, required: bool = True):
    if not breakers[service].allow():
        breaker_rejected.labels(service=service).inc()
        if required:
            raise DependencyUnavailable(service)
        return None                                       # degrade

    try:
        await asyncio.wait_for(limits[service].acquire(), timeout=0.1)
    except TimeoutError:
        if required:
            raise ServiceOverloaded(service)
        return None

    try:
        async with asyncio.timeout(timeout_for(service)):
            result = await fn()
        breakers[service].record(True)
        return result
    except RETRYABLE:
        breakers[service].record(False)
        if required:
            raise
        return None
    finally:
        limits[service].release()
```

💡 **Breaker, bulkhead, timeout and degradation in one place** — the same template as [[11.2 - Timeouts Retries and Jitter]], extended.

**Build it once. Every call site gets all four.**

## In Production

### Breakers are per-instance by default

⚠️ **Each application instance has its own breaker state.** With 20 pods, a failing dependency must fail enough on each pod independently before all 20 breakers open.

| Approach | |
|---|---|
| **Per-instance** | Simple, no coordination. Slower collective reaction |
| Shared state in Redis | Faster collective reaction, adds a dependency to the breaker |
| **Adaptive concurrency** | Each instance limits itself based on observed latency |

💡 **Per-instance is almost always right.** Sharing breaker state means your breaker depends on Redis, which is a dependency that can fail — and the failure mode is that no breaker works.

**The slower collective reaction is usually acceptable**, because each pod protects itself within seconds.

### Adaptive concurrency limits

```python
# Little's Law: L = λ × W
# Estimate the concurrency the dependency can handle from observed latency
if latency_now > latency_baseline * 2:
    limit = max(MIN_LIMIT, limit * 0.9)     # back off
else:
    limit = min(MAX_LIMIT, limit + 1)       # probe upward
```

💡 **Netflix's `concurrency-limits` implements this properly**, using algorithms borrowed from TCP congestion control ([[02.4 - Flow Control and Congestion Control]]).

**It removes the need to tune a fixed bulkhead size**, which is the hardest part of configuring one — and it adapts as the dependency's capacity changes.

⚠️ **It reacts to latency, so it handles the "slow" failure mode that a fixed limit does not.** A dependency that is up but 10× slower has effectively lost 90% of its capacity, and a fixed bulkhead does not notice.

### Monitoring

```python
breaker_state.labels(service=s).set({"closed": 0, "open": 1, "half_open": 2}[state])
breaker_transitions_total.labels(service=s, to=state).inc()
breaker_rejected_total.labels(service=s).inc()
bulkhead_in_use.labels(service=s).set(n)
bulkhead_rejected_total.labels(service=s).inc()
bulkhead_wait_seconds.labels(service=s).observe(elapsed)
```

⚠️ **`bulkhead_in_use` consistently at the limit means the bulkhead is your bottleneck**, not a safety net. Either the dependency is slow or the limit is too low.

💡 **`breaker_transitions_total` flapping — repeatedly open, half-open, open — means `open_duration` is too short** for the dependency's recovery time, and you are hammering something that is trying to come back.

**Alert on a breaker being open for longer than a few minutes**, because that is a dependency outage that is not resolving.

### Testing them

⚠️ **A circuit breaker that has never opened in a test does not work.**

```python
async def test_breaker_opens_and_recovers(toxiproxy):
    await toxiproxy.disable("search")
    for _ in range(25):
        with suppress(Exception):
            await call("search", fetch)
    assert breakers["search"].state == "open"

    start = time.monotonic()
    with pytest.raises(DependencyUnavailable):
        await call("search", fetch)
    assert time.monotonic() - start < 0.01          # ← fails immediately

    await toxiproxy.enable("search")
    await asyncio.sleep(OPEN_DURATION + 0.1)
    assert await call("search", fetch) is not None
    assert breakers["search"].state == "closed"
```

💡 **The "fails in under 10ms" assertion is the one that matters.** An open breaker that still takes 5 seconds to fail is not providing the protection you built it for.

### When not to use a breaker

| Situation | |
|---|---|
| **A local, in-process call** | There is nothing to protect against |
| Very low traffic | `minimum_requests` will never be reached meaningfully |
| **The dependency is already fast-failing** | A breaker adds no value over a 50ms timeout |
| Idempotent writes that must eventually happen | Use a queue and retry, not a breaker |

⚠️ **A breaker on a write path means the write is lost when it opens.** For writes that must happen, the answer is a durable queue ([[08.1 - Why Background Work Exists]]), not a breaker that drops them.

### Conduit's configuration

| Dependency | Breaker | Bulkhead | On open |
|---|---|---|---|
| Auth service | 50% / 20 req / 30s | 15 | **Fail — required** |
| Documents service | 50% / 20 req / 30s | 25 | Fail — required |
| Search service | 30% / 10 req / 20s | 10 | **Degrade — empty results** |
| Postgres | **None** | Pool of 20 | Fail — the pool is the bulkhead |
| Redis cache | 60% / 30 req / 10s | 10 | **Degrade — go to the database** |
| Embedding API | 40% / 10 req / 60s | 4 | **Queue and retry later** |
| Webhook targets | **Per endpoint** | 5 per endpoint | Retry schedule ([[05.12 - Webhooks and Callbacks]]) |

💡 **No breaker on Postgres**, because it is not optional — degrading means failing, and the connection pool already provides the bulkhead and the fast-fail ([[06.9 - Connection Pooling and PgBouncer]]).

⚠️ **The Redis breaker has a high threshold and a short open duration**, because falling back to the database is cheap and Redis usually recovers fast. **Different dependencies genuinely want different tuning**, and copying one configuration everywhere is a mistake.

**The per-endpoint webhook breaker is the important one** — one customer's dead endpoint must not affect delivery to anyone else.

## Codebase

**Repo:** `Netflix/concurrency-limits`, `resilience4j/resilience4j`, `envoyproxy/envoy`

**Question to answer:** How does an adaptive concurrency limit decide the current limit, and what signal does it use? Then: how does Envoy implement outlier detection, and how does it differ from a circuit breaker?

**Read, in order:**

1. `resilience4j/resilience4j-circuitbreaker/.../CircuitBreakerStateMachine.java` — **the state machine, properly implemented.** Sliding windows, minimum calls, and the half-open permit logic
2. `Netflix/concurrency-limits/.../limit/Gradient2Limit.java` — **the adaptive algorithm.** It compares short-term to long-term latency and adjusts. **The answer to the first question, and it is borrowed from TCP congestion control**
3. `Netflix/concurrency-limits/.../limiter/AbstractLimiter.java` — how the limit is enforced and how rejections are signalled
4. `envoy/source/extensions/outlier_detection/` — **ejecting unhealthy hosts from a load balancing pool.** **The answer to the second question**: outlier detection removes one bad *instance*, a breaker stops calling the whole *service*
5. `envoy/source/common/upstream/` — circuit breaker settings per cluster, and note they are concurrency limits rather than a state machine

💡 The Envoy distinction is worth internalising: **Envoy's "circuit breakers" are actually bulkheads — maximum connections, requests and retries — while outlier detection is what ejects failing hosts.** Two different mechanisms with overlapping names, and knowing which is which prevents a lot of configuration confusion.

**Size:** 1 session.

**Part 1 — The shared pool failure.** One connection pool of 50, three dependencies.

Make one dependency take 30 seconds. **Chart pool utilisation and the success rate of requests that do not touch it.**

**They should fail too.** That is the demonstration.

Then per-dependency pools, same test. **Confirm only the affected requests fail**, and measure the success rate of the others.

**Part 2 — Build the breaker.** Full state machine with a sliding window, minimum requests, half-open probes.

Test: opens on sustained failure, rejects immediately when open, transitions to half-open, closes on success, reopens on a failed probe, and **does not open on a small number of failures at low traffic.**

**Assert that an open breaker fails in under 10ms.**

**Part 3 — Four failure modes.** With Toxiproxy: down, slow (5s), flaky (30% errors), and slow-and-flaky.

**For each, measure:** does the breaker open, how long until it does, requests attempted before it opens, and the effect on unrelated requests.

⚠️ **The "slow" case is the one that catches naive implementations** — no errors are returned, only timeouts, and a breaker counting only exceptions never opens.

**Part 4 — Tuning failures.** Reproduce three misconfigurations:

- **`minimum_requests=0` at low traffic:** two failures at 3am open the breaker for everyone. **Measure the false outage duration**
- **`open_duration` too short:** a service taking 60 seconds to recover with a 5-second open duration. **Chart the flapping** and count how many times it reopens
- **`failure_threshold` too low:** a service with a normal 5% error rate and a 3% threshold. **Confirm the breaker is permanently open**

Then tune each correctly and confirm the problem disappears.

**Part 5 — Adaptive versus fixed.** A dependency whose capacity changes — 100 concurrent requests, then 20 after a deploy.

**Fixed bulkhead of 50:** measure errors and latency after the capacity drop.
**Adaptive limit:** measure the same.

**Chart the limit value over time for the adaptive version** and confirm it tracks the actual capacity.

**Part 6 — Per-instance versus shared.** 20 instances, a dependency that fails completely.

**Per-instance:** measure time until all 20 breakers are open, and total requests sent to the dead dependency.

**Shared in Redis:** measure the same. **Then take Redis down and confirm the shared version fails open** — which is why per-instance is usually right.

**Part 7 — Degradation.** Make search fail with the breaker open.

**Confirm the page still renders**, with empty search results and a visible indication ([[11.6 - Graceful Degradation]]).

Then remove the degradation handling and confirm the page 500s. **Compare the user experience.**

**Part 8 — The ADR.** Conduit's breaker and bulkhead configuration per dependency.

**Justify every parameter from a measurement**: the dependency's normal error rate, its recovery time, and its capacity.

**For each, state what happens when the breaker opens** — fail, degrade, or queue.

**Done when:**
- A shared pool demonstrably failed unrelated requests, and per-dependency pools did not
- Your breaker fails in under 10ms when open
- The "slow" failure mode opens the breaker via timeouts
- All three misconfigurations are reproduced with measured impact
- Your adaptive limit tracks a changing dependency capacity
- Shared breaker state fails open when Redis is down
- Search degrades to an empty result rather than a 500
- Every ADR parameter is derived from a measurement
