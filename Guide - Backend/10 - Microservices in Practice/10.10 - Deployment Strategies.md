# Deployment Strategies

#backend #microservices #operations

> **In one line:** Every deploy runs two versions of your code at once, so the strategy is really about how much traffic sees the new one and how fast you can stop.

---

## The Idea

```
Recreate       stop all, start all              downtime
Rolling        replace gradually                 mixed versions
Blue-green     two environments, switch          instant, expensive
Canary         a small percentage first          gradual, observable
```

| | Downtime | Mixed versions | Rollback speed | Cost |
|---|---|---|---|---|
| Recreate | **Yes** | No | Redeploy | Low |
| **Rolling** | No | **Yes** | Redeploy | Low |
| Blue-green | No | **No** | **Instant** | 2× |
| Canary | No | Yes | **Instant** | Low |

💡 **Rolling is the default and it is the one with mixed versions**, which is the source of most deploy incidents. Everything in [[06.11 - Zero Downtime Migrations]] and [[05.13 - Contract Testing and Schema Evolution]] exists because of that window.

---

## Rolling

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

```
v1 v1 v1 v1
v1 v1 v1 v1 v2      ← surge: add one new
v1 v1 v1 v2         ← remove one old
...
v2 v2 v2 v2
```

⚠️ **`maxUnavailable: 0` means you never drop below the desired replica count**, which matters if you are near capacity. It requires `maxSurge ≥ 1` and slightly more resources during the rollout.

### The mixed-version window

```
For several minutes:
  - Half your pods run v1, half run v2
  - Both read and write the same database
  - Both consume the same queues
  - Both serve the same clients
```

⚠️ **Everything must be compatible in both directions**, because a client's two consecutive requests can hit different versions.

| Concern | Requirement |
|---|---|
| Database schema | v1 and v2 both work against it ([[06.11 - Zero Downtime Migrations]]) |
| API responses | v2's response is acceptable to a v1 client |
| **Task messages** | v1 workers can process v2's messages, and vice versa ([[08.5 - Task Design Rules]]) |
| Event schemas | Compatible ([[09.6 - Schema Registry and Compatibility]]) |
| Cached values | A v1-shaped cache entry does not break v2 |
| Session data | Readable by both |

💡 **The cached-value case is the one people miss.** v2 caches an object with a new field; v1 reads it and crashes on the unexpected shape — or worse, silently ignores it.

**Version your cache keys** when the cached shape changes:

```python
key = f"doc:v2:{doc_id}"
```

### Probes decide whether it works

```yaml
readinessProbe:
  httpGet: {path: /readyz, port: 8080}
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3

livenessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 10
  failureThreshold: 3
```

⚠️ **A readiness probe that returns 200 before the service can actually serve traffic makes a rolling deploy an outage** — pods are added to the load balancer while still connecting to the database, warming caches, or loading models.

```python
@app.get("/readyz")
async def readyz():
    if not await db.is_connected():
        raise HTTPException(503)
    if not cache_warmed.is_set():
        raise HTTPException(503)
    return {"ready": True}
```

💡 **Readiness means "send me traffic"; liveness means "I am not wedged, do not restart me".** Confusing them is the most common probe mistake.

⚠️ **A liveness probe that checks a dependency causes cascading restarts.** If the database is slow, every pod fails liveness and restarts — turning a degraded dependency into a total outage ([[11.6 - Graceful Degradation]]).

**Liveness must check only the process itself.**

## Blue-Green

```
Blue (v1)  ← 100% traffic
Green (v2) ← 0%, fully deployed and warmed

switch → Green 100%, Blue idle
```

| | |
|---|---|
| **Good** | **No mixed versions.** Instant rollback. Test green before switching |
| **Bad** | **Double the infrastructure.** The database is still shared |

⚠️ **Blue-green does not solve the database problem.** Both environments share one database, so schema compatibility is still required — you have eliminated mixed *application* versions and not mixed schema access.

💡 **The genuine benefit is instant rollback**: switch traffic back to blue in seconds rather than waiting for a rolling redeploy.

⚠️ **Long-lived connections do not switch instantly.** WebSocket and SSE clients stay on blue until they reconnect ([[04.6 - Scaling Long Lived Connections]]), so blue must stay running until they drain.

## Canary

```
95% → v1
 5% → v2      ← watch the metrics
```

```yaml
# Istio traffic split
http:
  - route:
      - destination: {host: documents, subset: v1}
        weight: 95
      - destination: {host: documents, subset: v2}
        weight: 5
```

💡 **The point of a canary is not the small percentage — it is that you compare metrics between the two versions before proceeding.**

```
                    v1        v2
error rate         0.1%      2.3%     ← ⚠️ stop
p99 latency        180ms     195ms
CPU per request    12ms      14ms
```

⚠️ **A canary without automated metric comparison is just a slow rollout.** Someone has to look, and during a busy day nobody does.

### Automated analysis

```yaml
# Flagger / Argo Rollouts
analysis:
  interval: 1m
  threshold: 5
  metrics:
    - name: error-rate
      thresholdRange: {max: 1}
    - name: latency-p99
      thresholdRange: {max: 500}
  steps:
    - setWeight: 5
    - pause: {duration: 5m}
    - setWeight: 25
    - pause: {duration: 5m}
    - setWeight: 50
    - pause: {duration: 5m}
    - setWeight: 100
```

💡 **Automated rollback on metric regression is what makes canaries worth the machinery.** The deploy either promotes itself or reverts, with no human in the loop.

⚠️ **The metrics must be comparable.** If v2 receives 5% of traffic, its error rate is computed from 5% of the sample — which is noisy. **Give the canary enough traffic and enough time for statistical significance**, or you will roll back on noise and promote on luck.

### Sticky canaries

```yaml
# Route by header, so the same user always sees the same version
- match:
    - headers: {x-canary: {exact: "true"}}
  route:
    - destination: {host: documents, subset: v2}
```

💡 **Random 5% routing means a user's requests bounce between versions**, which is fine for stateless reads and confusing for a multi-step workflow. **Hash on user ID for consistency.**

## Feature Flags: Decoupling Deploy from Release

```python
if await flags.enabled("new_pipeline", org_id=org.id):
    return await new_pipeline(doc)
return await old_pipeline(doc)
```

💡 **The deploy ships the code disabled; the release is a flag change** ([[10.8 - Configuration and Secrets]]).

| Advantage over a canary | |
|---|---|
| **Per-user or per-tenant targeting** | Not just a traffic percentage |
| **Instant disable** | No deploy, no traffic shift |
| Both code paths in one binary | No version skew |
| **Rollback in seconds** | Flip the flag |

⚠️ **Both code paths exist in production, and both must work.** A flag that has been off for three months is untested code that will fail when someone turns it on.

💡 **The strongest combination: deploy with a rolling update, release with a flag.** The deploy is boring; the release is instantly reversible.

## Rollback

⚠️ **The question that matters is not "can we roll back" but "is rolling back safe".**

| Blocker | |
|---|---|
| **A migration that removed a column** | v1 needs it |
| **Data written in a v2-only format** | v1 cannot read it |
| **Events published with a new schema** | v1 consumers reject them |
| A cache populated with v2 shapes | v1 crashes on them |
| An external system called with a new contract | |

💡 **This is why expand/contract exists** ([[06.11 - Zero Downtime Migrations]]). If your migration only added things, rollback is safe. If it removed anything, it is not.

**The rule: N must work against N+1's schema.** Test it:

```python
# In CI: run the previous release's test suite against the new schema
pytest --version=$PREVIOUS_TAG --schema=$NEW_SCHEMA
```

⚠️ **A deploy you cannot roll back is a deploy that must be right.** That is a much higher bar, and the correct response is usually to split it into two deploys that are each reversible.

### Forward fix versus rollback

```
Rollback:    fast, safe if the change was additive
Forward fix: necessary when rollback is unsafe, slower under pressure
```

💡 **Decide before you deploy which one applies**, and write it in the deploy notes. Deciding during an incident, at 3am, with a partial understanding, is how a bad deploy becomes a long outage.

## In Production

### The deploy checklist

```
□  Is the schema change backward compatible?
□  Can N-1 code run against the new schema?
□  Are task and event message formats compatible both ways?
□  Are cache keys versioned if the shape changed?
□  Is the readiness probe accurate?
□  Is terminationGracePeriodSeconds > the longest in-flight operation?
□  Is there a preStop drain?
□  Is rollback safe, or is forward-fix the only option?
□  What metric would tell you this deploy is bad?
□  Who is watching, and for how long?
```

⚠️ **The second-to-last item is the one that turns a deploy into an observable event.** "Error rate above 1% for five minutes" is a rollback criterion; "keep an eye on it" is not.

### Graceful shutdown

```yaml
terminationGracePeriodSeconds: 90
lifecycle:
  preStop:
    exec: {command: ["sleep", "10"]}       # let the LB stop sending traffic
```

```python
@app.on_event("shutdown")
async def shutdown():
    ready.clear()                           # fail readiness immediately
    await asyncio.sleep(5)                  # let the LB notice
    await server.shutdown()                 # finish in-flight requests
    await pool.close()
```

⚠️ **`SIGTERM` and load balancer deregistration are not synchronised.** The pod receives `SIGTERM` and the load balancer may keep sending traffic for several seconds — so shutting down immediately drops requests ([[11.7 - Graceful Shutdown and Draining]]).

💡 **The `preStop` sleep is not a hack, it is the fix.** It gives the load balancer time to remove the endpoint before the process stops accepting.

### Pod disruption budgets

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
  selector:
    matchLabels: {app: documents}
```

💡 **A PDB protects you from voluntary disruptions — node drains, cluster upgrades, autoscaler scale-down — not just your own deploys.** Without one, a node drain can take every replica of a service at once.

⚠️ **A PDB that cannot be satisfied blocks node drains indefinitely**, which turns a routine cluster upgrade into a stuck operation. `minAvailable` equal to `replicas` is a common mistake.

### Deploy observability

```python
deploy_version_info.labels(version=v, service=s).set(1)
```

```
error_rate by version
p99_latency by version
```

💡 **Label every metric with the version.** A canary comparison is impossible without it, and a rolling deploy where only the new pods are broken looks like a 50% error rate rather than a version problem.

**Annotate your dashboards with deploy events**, so a graph that changes shape has an obvious candidate cause.

### Deploy frequency and risk

```
Weekly deploys:  large changes, high risk per deploy, slow rollback
Daily deploys:   smaller changes, easier to attribute failures
```

💡 **Small frequent deploys are safer**, because when something breaks the change set is small enough to identify. **The instinct to deploy less often after an incident makes the next incident harder to diagnose.**

⚠️ **This only holds if the deploy pipeline is fast and reliable.** A 40-minute deploy with a flaky test suite makes frequent deploys impossible, and fixing that is the prerequisite ([[10.9 - Testing Microservices]]).

### Conduit's deployment

| Component | Strategy |
|---|---|
| Gateway | **Rolling**, `maxUnavailable: 0`, PDB `minAvailable: 2` |
| Document service | Rolling |
| Workers | Rolling, **long grace period** for in-flight tasks |
| **Risky changes** | Rolling deploy + **feature flag** |
| Database migrations | **Separate job**, before the deploy ([[06.11 - Zero Downtime Migrations]]) |

💡 **No canary infrastructure, because it requires a mesh or a gateway that supports traffic splitting** ([[10.7 - Service Discovery and Service Mesh]]). **Feature flags give most of the benefit** — per-tenant targeting and instant disable — without it.

⚠️ **The worker grace period is the one that needs attention.** With tasks taking up to 60 seconds, `terminationGracePeriodSeconds` must exceed that or every deploy abandons work ([[08.9 - Celery in Production]]).

**Write down the trigger for adding canary infrastructure: a change where a feature flag cannot isolate the risk**, such as a framework upgrade or a runtime change.

## Codebase

**Repo:** `kubernetes/kubernetes`, `argoproj/argo-rollouts`, `fluxcd/flagger`

**Question to answer:** How does the Kubernetes Deployment controller sequence a rolling update, and what exactly do `maxSurge` and `maxUnavailable` control? Then: how does Flagger decide to promote or roll back a canary?

**Read, in order:**

1. `kubernetes/pkg/controller/deployment/rolling.go` — **`reconcileNewReplicaSet` and `reconcileOldReplicaSet`.** The scale-up and scale-down sequencing. **The answer to the first question**
2. `kubernetes/pkg/controller/deployment/util/deployment_util.go` — `MaxSurge`, `MaxUnavailable`, and how the available replica count is computed from readiness
3. `kubernetes/pkg/kubelet/prober/` — **how probes are evaluated**, and the distinction between readiness and liveness in the code
4. `fluxcd/flagger/pkg/controller/scheduler.go` — **the canary state machine**: analyse, promote, or rollback. **The answer to the second question**
5. `argoproj/argo-rollouts/rollout/canary.go` — a different implementation of the same idea, with explicit steps and pauses

💡 The Flagger scheduler is worth reading because **it makes the promotion decision explicit and mechanical**: query the metrics, compare against thresholds, increment a failure counter, and roll back at the limit. **Seeing it as a state machine removes the mystique from progressive delivery.**

**Size:** 1 session.

```
│   ├── no_drain.py       # requests dropped

│   ├── n_minus_one.py    # old tests, new schema
│   └── FINDINGS.md
├── canary/
│   ├── manual.py
│   ├── automated.py      # metric-based promotion
│   ├── noise.py          # false rollback on 5% traffic
│   └── RESULTS.md
└── ADR.md
```

**Part 1 — Four strategies, measured.** The same service, deployed four ways, under continuous load.

Measure for each: requests dropped, deploy duration, **time to roll back**, and peak resource usage.

**Recreate should drop everything; rolling should drop nothing if the probes and drain are right.**

**Part 2 — Three version-skew failures.** During a rolling deploy:

- **API skew:** v2 returns a new required field; a v1 client rejects it. **Count client errors**
- **Task skew:** v2 enqueues a task with a new required parameter; v1 workers fail. **Count failures**
- **Cache skew:** v2 caches a new shape; v1 reads it. **Confirm the crash or the silent wrong behaviour**

Then apply the compatibility rules and confirm all three produce zero errors.

**Part 3 — The lying readiness probe.** A service returning 200 from `/readyz` before its database pool is connected.

**Deploy under load and count the 500s.** They come from pods added to the load balancer too early.

Then make the probe accurate and confirm zero.

Then the liveness cascade: put a database check in the liveness probe, make the database slow, and **confirm every pod restarts, turning a degraded dependency into a total outage.**

**Part 4 — Shutdown.** A service with 2-second requests, deployed under load.

**Without `preStop`:** count requests dropped per rollout.
**With a 10-second `preStop`:** count again.

Then a worker with 60-second tasks and a 30-second grace period. **Measure tasks abandoned per deploy.** Then set it correctly and measure the rework saved.

**Part 5 — Rollback safety.** Two migrations: one additive, one removing a column.

For each: deploy v2, then roll back to v1. **Confirm the additive one works and the destructive one breaks.**

Then implement the N-1 test: run the previous release's test suite against the new schema in CI. **Confirm it catches the destructive migration before it ships.**

**Part 6 — Canary with real analysis.** A canary at 5%, with a v2 that has a 3% error rate.

**Manual:** how long until someone notices? Time it honestly.

**Automated:** metric comparison with a rollback threshold. **Measure time to automatic rollback.**

Then the noise problem: a v2 with the *same* error rate as v1, at 5% traffic. **Run the analysis 20 times and count false rollbacks.**

**Find the traffic percentage and duration where the comparison is statistically meaningful.**

**Part 7 — Flags versus canary.** The same risky change, released both ways.

Compare: targeting granularity, time to disable, infrastructure required, and what happens when the change is bad for only one tenant.

**Part 8 — The ADR.** Conduit's deployment strategy per component, with the ten-item checklist applied.

**For every deploy, name the metric that would trigger a rollback and the threshold.**

**Done when:**
- Your four-strategy comparison includes rollback time
- All three version-skew failures are reproduced and fixed
- A lying readiness probe dropped requests, and a liveness cascade restarted your fleet
- `preStop` and a correct grace period eliminated dropped requests and abandoned tasks
- The N-1 test catches a destructive migration in CI
- You know the traffic percentage at which canary analysis stops being noise
- Every Conduit component has a named rollback metric and threshold
