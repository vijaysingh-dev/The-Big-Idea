# HTTP/1.1 Message Format

#backend #http #protocols

> **In one line:** HTTP/1.1 is text separated by `\r\n` with a blank line before the body, and the only genuinely hard part is knowing where the body ends.

---

## The Idea

HTTP/1.1 is a text protocol. You can type it by hand.

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n' | nc example.com 80
```

That is a complete, valid HTTP request. Being able to write one by hand is a good test of whether you actually understand the protocol.

The structure:

```
<start line>\r\n
<header>: <value>\r\n
<header>: <value>\r\n
\r\n                          ← blank line: headers end here
<body>
```

The whole difficulty is in that last line. **How does the receiver know how long the body is, or whether there is one at all?** That question is called *framing*, and it is where the bugs and the security problems live.

---

## The Message

### Request

```
POST /documents?source=drive HTTP/1.1
Host: api.conduit.local
Content-Type: application/json
Content-Length: 34
User-Agent: httpx/0.27.0

{"title": "notes", "size": 1024}
```

The start line is `METHOD SP TARGET SP VERSION`.

⚠️ **`Host` is mandatory in HTTP/1.1.** Without it you get 400. It exists because one IP serves many sites — the same reason SNI exists in TLS ([[02.9 - TLS]]). The difference is that `Host` is inside the encrypted stream and SNI is not.

### Response

```
HTTP/1.1 201 Created
Content-Type: application/json
Content-Length: 27
Location: /documents/42

{"id": 42, "status": "ok"}
```

Start line is `VERSION SP STATUS SP REASON`. The reason phrase (`Created`) is decorative — clients must use the number. HTTP/2 dropped it entirely.

---

## Headers

### The rules that catch people out

**Names are case-insensitive.** `Content-Type`, `content-type` and `CONTENT-TYPE` are the same header. HTTP/2 requires lowercase.

**Values are ASCII.** Non-ASCII needs encoding (RFC 8187):

```
Content-Disposition: attachment; filename*=UTF-8''caf%C3%A9.pdf
```

**Headers can repeat.** This is why ASGI's `scope["headers"]` is a list of tuples, not a dict ([[01.9 - ASGI and How Uvicorn Serves a Request]]) — a dict silently loses duplicates.

```
Set-Cookie: session=abc
Set-Cookie: theme=dark
```

⚠️ Most headers can be merged with commas (`Accept: a, b`). **`Set-Cookie` cannot** — it is the special case that breaks naive header handling everywhere. Any code that flattens headers into a dict will corrupt cookies.

**Whitespace around the colon.** Leading whitespace in the value is stripped. **Whitespace *before* the colon is illegal** and must be rejected — it is a request smuggling vector.

### Size limits

There is no limit in the spec, so every server picks one:

| Server | Default |
|---|---|
| nginx | 8KB per header line |
| Apache | 8KB |
| uvicorn (h11) | ~16KB total |
| Most cloud load balancers | 8–16KB |

⚠️ **Large JWTs in cookies routinely exceed 8KB** and produce a 431 or a 400 that appears random — it depends on how many claims and cookies the user has accumulated. If a login works for most users and fails for a few, check header size.

## Framing: Where the Body Ends

Four possibilities, checked in order.

### 1. Content-Length

```
Content-Length: 1024
```

Read exactly 1024 bytes. Simple, and it requires knowing the size in advance.

### 2. Transfer-Encoding: chunked

For when you do not know the size — a streamed response, a generated report.

```
HTTP/1.1 200 OK
Transfer-Encoding: chunked

1a\r\n
Twenty-six bytes of data..\r\n
10\r\n
Sixteen more....\r\n
0\r\n
\r\n
```

Each chunk is a hex length, `\r\n`, the data, `\r\n`. A zero-length chunk ends the body.

⚠️ **The lengths are hexadecimal.** `10` means 16 bytes, not 10. This trips up every hand-written parser at least once.

This is the mechanism behind `StreamingResponse` and SSE ([[04.2 - Server Sent Events]]).

### 3. Connection close

```
HTTP/1.1 200 OK
Connection: close

...data until the connection closes...
```

HTTP/1.0 style. The body ends when the connection ends. Works, but you cannot tell a complete response from a truncated one — which is a real problem, and why chunked encoding exists.

### 4. No body at all

- Responses to `HEAD`
- `204 No Content`, `304 Not Modified`
- `1xx` informational responses

⚠️ **A `HEAD` response includes `Content-Length` but no body.** A parser that trusts `Content-Length` without checking the method will wait forever for bytes that are not coming. This is a classic bug in hand-written clients.

## Request Smuggling

Worth understanding because it is the main reason HTTP parsing must be strict.

If a request has **both** `Content-Length` and `Transfer-Encoding`, which wins? The spec says `Transfer-Encoding`. Not every implementation agrees.

```
POST / HTTP/1.1
Content-Length: 6
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
...
```

If a front-end proxy honours `Content-Length` and the back-end honours `Transfer-Encoding`, they disagree about where the request ends. The leftover bytes get treated by the back-end as the *start of the next request* — which may be another user's request, now prefixed with attacker-controlled data.

⚠️ **The consequences are severe:** bypassing front-end access controls, poisoning another user's request, stealing session cookies.

Defences:

- Reject any request with both headers (modern servers do)
- Reject obfuscated `Transfer-Encoding` values (`Transfer-Encoding: chunked ` with a trailing space, or duplicated)
- Reject whitespace before a colon
- Use HTTP/2 end to end, where framing is explicit and length-prefixed
- Do not write your own HTTP parser for production

💡 **This is the strongest argument for using a well-tested parser like h11 or httptools.** The bugs here are not performance bugs, they are security bugs, and they come from being lenient about malformed input. "Be liberal in what you accept" is actively wrong for HTTP.

## Methods and Status Codes

### Methods

| Method | Safe | Idempotent | Body |
|---|---|---|---|
| `GET` | Yes | Yes | No |
| `HEAD` | Yes | Yes | No |
| `OPTIONS` | Yes | Yes | No |
| `PUT` | No | **Yes** | Yes |
| `DELETE` | No | **Yes** | Sometimes |
| `POST` | No | **No** | Yes |
| `PATCH` | No | No | Yes |

**Safe** means no side effects. **Idempotent** means doing it twice has the same effect as once.

💡 **Idempotency determines whether a proxy or client may safely retry automatically.** This is not a philosophical distinction — it changes real behaviour in load balancers, HTTP clients and service meshes. `POST` is not retried automatically, which is why you need idempotency keys ([[03.4 - Idempotency and Safe Retries]]).

### The status codes that matter

| Code | Meaning | Notes |
|---|---|---|
| `200` / `201` / `204` | Success | `201` should include `Location` |
| `202` | Accepted | For async work. The pattern in [[01.7 - Cancellation and Structured Concurrency]] |
| `304` | Not Modified | Caching. See [[03.5 - HTTP Caching]] |
| `400` | Bad request | Malformed. Client's fault, do not retry |
| `401` / `403` | Not authenticated / not allowed | `401` means "who are you", `403` means "not you" |
| `404` | Not found | |
| `409` | Conflict | Version mismatch, duplicate |
| `422` | Unprocessable | Well-formed but semantically wrong. FastAPI's validation default |
| `429` | Too many requests | **Must include `Retry-After`** |
| `499` | Client closed request | nginx-specific, not a real code. Very useful in logs |
| `500` | Server error | |
| `502` / `503` / `504` | Bad gateway / unavailable / timeout | Distinguish these — see below |

⚠️ **`502` vs `503` vs `504` should be meaningfully different in your system**, because they point at different problems:

- `502` — the upstream returned something invalid or died mid-response
- `503` — you are deliberately shedding load, or a dependency is out. **Include `Retry-After`**
- `504` — the upstream did not answer in time

If everything returns 500, you have thrown away information your on-call engineer needs.

## Writing a Parser

The core is a state machine. This is why h11's state machine is worth reading.

```python
class RequestParser:
    def __init__(self, max_line=8192, max_headers=100, max_body=10 * 1024 * 1024):
        self.buf = bytearray()
        self.state = "START_LINE"
        self.headers = []
        self.max_line = max_line
        self.max_headers = max_headers
        self.max_body = max_body

    def feed(self, data: bytes):
        self.buf.extend(data)
        while True:
            if self.state == "START_LINE":
                line = self._read_line()
                if line is None:
                    return
                self.method, self.target, self.version = line.split(b" ", 2)
                self.state = "HEADERS"

            elif self.state == "HEADERS":
                line = self._read_line()
                if line is None:
                    return
                if line == b"":
                    self.state = self._body_state()
                    continue
                if len(self.headers) >= self.max_headers:
                    raise ProtocolError("too many headers")
                name, _, value = line.partition(b":")
                if name != name.strip():
                    raise ProtocolError("whitespace in header name")
                self.headers.append((name.lower(), value.strip()))
            ...
```

Every limit in that code is a denial-of-service defence, not a nicety:

| Limit | Attack it prevents |
|---|---|
| Max line length | A request line that never ends, growing your buffer forever |
| Max header count | Thousands of headers exhausting memory |
| Max body size | Memory exhaustion, and slow CPU in JSON parsing |
| Header read timeout | Slowloris — headers sent one byte per second, holding connections open |

💡 **Slowloris is worth knowing by name.** An attacker opens many connections and sends headers extremely slowly, never finishing. Each connection is valid and costs the attacker almost nothing. Without a header-completion timeout, a handful of clients can exhaust your connection capacity. The defence is a deadline on receiving complete headers, separate from the body read timeout.

## In Production

### Debugging with curl

```bash
curl -v https://api.example.com/users        # request and response headers
curl -sD - -o /dev/null https://x.com        # headers only, to stdout
curl --raw -v ...                            # no automatic decompression
curl --http1.1 ...                           # force version
curl -X POST -H 'Content-Type: application/json' -d '{"a":1}' url
curl -H 'Transfer-Encoding: chunked' -d @big.json url    # force chunked
```

`--raw` matters when debugging encoding problems — without it curl silently decompresses and you cannot see what actually arrived.

### Header size in the real world

```nginx
large_client_header_buffers 4 16k;
client_max_body_size 10m;
client_header_timeout 10s;        # slowloris defence
client_body_timeout 30s;
```

Set `client_max_body_size` deliberately. The default 1MB in nginx will reject legitimate uploads, and an unbounded value invites memory exhaustion. Reject oversized bodies **at the proxy**, before your application spends CPU parsing them — this is the same reasoning as [[01.6 - The Blocking Call Problem]]'s warning about large JSON.

### Logging what matters

```
$request_method $uri $status $body_bytes_sent $request_time $upstream_response_time
```

The gap between `request_time` and `upstream_response_time` is time spent in the proxy or the network — including a slow client uploading a body. A large gap with a fast upstream means a slow client, not a slow service.

## Codebase

**Repo:** `python-hyper/h11` and `nodejs/llhttp` (which httptools wraps)

**Question to answer:** What states can an HTTP/1.1 connection be in, and which transitions are illegal? Then: what does h11 do when a request has both `Content-Length` and `Transfer-Encoding`, and where in the code is that decision made?

**Read, in order:**

1. `h11/_state.py` — **read the comment at the top first.** It contains the full state machine diagram, and it is one of the best pieces of documentation in any Python library
2. `h11/_events.py` — the event types. Note that h11 models HTTP as a stream of events, not as request/response objects
3. `h11/_readers.py` — one reader per framing mode. `ContentLengthReader`, `ChunkedReader`, `Http10Reader`. This is section "Framing" as code
4. `h11/_writers.py` — the mirror image
5. `h11/_connection.py` — where the two state machines (client and server) are coordinated. Find the `Content-Length` + `Transfer-Encoding` handling

**Then, for contrast:** `llhttp/src/llhttp/http.ts` — the parser used by Node and httptools. It is generated from a state machine description, which is a different approach to the same correctness problem.

💡 h11 is **sans-IO** — it never touches a socket. You feed it bytes and it gives you events. This separation makes it testable in a way that socket-coupled parsers are not, and it is a design pattern worth stealing for any protocol work you do. The [sans-io.readthedocs.io](https://sans-io.readthedocs.io/) writeup explains the philosophy.

**Size:** 1–2 sessions.

## Exercise

**Drill 3.1 — Write an HTTP/1.1 server**

The flagship drill of section 03. No `http.server`, no framework, no `h11`. Bytes in, bytes out.

```
drills/03-http-server/
├── parser/
│   ├── state.py          # the state machine
│   ├── reader.py         # content-length, chunked, close-delimited
│   ├── writer.py
│   ├── limits.py         # every DoS defence
│   └── errors.py
├── server/
│   ├── connection.py     # keep-alive, timeouts, pipelining
│   ├── server.py         # on your own event loop from drill 1.3
│   └── app.py            # a few endpoints to serve
├── tests/
│   ├── test_parser.py
│   ├── test_framing.py
│   ├── test_hostile.py   # malformed and adversarial input
│   ├── test_keepalive.py
│   └── fuzz.py
├── compat/
│   └── COMPAT.md         # curl, browser, ab, httpx — who works?
└── README.md
```

**Part 1 — The parser.** Handle: request line, headers, all four framing modes, chunked with extensions, trailers, and `HEAD` responses.

**Part 2 — Every hostile input.** One test per attack. This part is the real value of the drill.

| Input | Expected |
|---|---|
| Request line with no `\r\n`, 10MB long | Reject at the line limit |
| 10,000 headers | Reject at the header count limit |
| Whitespace before a header colon | Reject |
| Both `Content-Length` and `Transfer-Encoding` | Reject |
| Two different `Content-Length` values | Reject |
| Chunk size in decimal instead of hex | Reject or interpret as hex, consistently |
| Chunk size of `FFFFFFFFFFFFFFFF` | Reject before allocating |
| `Content-Length: -1` | Reject |
| Headers sent one byte per second | Timeout (slowloris) |
| Body shorter than `Content-Length`, then close | Clean error, not a hang |
| Null bytes in the header value | Reject |

**Part 3 — Fuzz it.** Generate random and mutated requests. Run for an hour. **It must not crash, hang, or allocate unbounded memory** on any input. Fix everything you find and add a regression test for each.

**Part 4 — Keep-alive and pipelining.** Multiple requests on one connection, correct `Connection: close` handling, an idle timeout, and correct behaviour when a client pipelines three requests at once.

Then test the case from the note: an endpoint that returns early without reading the request body. Confirm your server does the right thing on the next request rather than parsing at the wrong offset.

**Part 5 — Compatibility.** Serve real traffic from `curl`, a browser, `ab`, `httpx` and `wrk`. Document in `COMPAT.md` what worked and what each client did that surprised you.

Browsers in particular will send things you did not anticipate.

**Part 6 — Reproduce a smuggling desync.** Put your server behind nginx. Deliberately make your server prefer `Content-Length` while nginx prefers `Transfer-Encoding`. Send a crafted request and show the desynchronisation — the second request being interpreted from attacker-controlled bytes.

Then fix it by rejecting the ambiguous request and confirm the attack fails.

⚠️ Do this only against your own local stack, never against a system you do not own.

**Done when:**
- All eleven hostile inputs are rejected cleanly with a test each
- One hour of fuzzing produces no crash, hang or memory blowup
- Keep-alive works with `curl`, a browser, and `ab`
- `COMPAT.md` documents at least three surprises
- You have produced a desync and then prevented it
