# Testing Philosophy

The purpose of a test is **confidence that a change did not break anything**. Every decision below follows from that, and most bad test suites come from optimizing for something else — coverage numbers, or the aesthetic of testing "units".

## The guiding rule

> The more your tests resemble the way your software is used, the more confidence they give you.

A test that clicks a button and asserts the resulting screen mirrors what a user does. A test that asserts a component's internal state does not — it can pass while the feature is broken, and fail when nothing is broken.

That single criterion resolves most testing debates.

## The shape of a good suite

The classic pyramid — many unit tests, fewer integration, very few end-to-end — was written when integration tests were slow and brittle. Modern tooling changed that, and the **testing trophy** is a better fit for frontend work:

```
        ╱‾‾‾‾‾‾‾‾╲        E2E          few — critical user journeys
       ╱          ╲
      │ INTEGRATION │     the bulk — components with real dependencies
       ╲          ╱
        ╲  UNIT  ╱        pure logic, utilities, reducers
         ╲______╱
          STATIC          TypeScript, ESLint — free, always on
```

Integration tests get the largest share because they hit the best ratio of confidence to cost. A test that renders a form, fills it, submits it and asserts the outcome exercises the component, its hooks, its validation, its API layer and its rendering — the things that actually break together.

**Static analysis is the base and it is free.** TypeScript catches an entire class of bugs that would otherwise need tests ([[25.6 - Discriminated Unions and Narrowing]]). A codebase with `strict` on and a good lint config needs meaningfully fewer tests than one without.

## Test behavior, not implementation

```jsx
// Implementation — breaks on any refactor, passes when the feature is broken
expect(wrapper.state("isOpen")).toBe(true);
expect(wrapper.find("Dropdown").props().visible).toBe(true);

// Behavior — survives refactors, fails when the feature breaks
await user.click(screen.getByRole("button", { name: /options/i }));
expect(screen.getByRole("menu")).toBeInTheDocument();
```

The test for whether a test is implementation-coupled: **could I rewrite the component's internals — hooks to reducer, class to function, one component to three — without changing the test?** If not, the test is measuring structure rather than behavior.

This is why Enzyme fell out of use and React Testing Library replaced it: Enzyme's API made implementation testing the path of least resistance ([[26.3 - React Testing Library]]).

## What to test

**High value:**

- Critical user paths — signup, checkout, the core workflow
- Complex logic — pricing, permissions, date handling, state machines
- Bug fixes — a regression test is the cheapest test you will ever write, because the failure is already known
- Boundaries — API layer, form validation, data transforms
- Edge cases — empty, error, loading, permission-denied ([[24.2 - Loading Error and Empty States]])

**Low value:**

- That a component renders without crashing
- Third-party library behavior
- Static markup with no logic
- Getters, setters, trivial mappers
- Implementation details of any kind

The question for each test: **what bug would this have caught?** If the answer is "none realistically", it is maintenance cost with no return.

## Coverage is a diagnostic, not a target

100% coverage means every line executed, not that the behavior is correct:

```js
function divide(a, b) { return a / b; }

test("divides", () => expect(divide(6, 2)).toBe(3));   // 100% coverage, b=0 untested
```

Coverage is useful for **finding untested areas** — a critical module at 20% is a real signal. It is harmful as a target, because the cheapest way to hit a number is to write tests that assert nothing meaningful.

A reasonable policy: track coverage, investigate low-coverage critical paths, and do not gate merges on a percentage.

## Costs to weigh

Every test has ongoing cost:

**Maintenance.** Tests coupled to implementation must be rewritten on every refactor. Poorly-written tests actively discourage refactoring, which is the opposite of their purpose.

**Runtime.** A suite that takes fifteen minutes gets skipped locally and slows every PR.

**False confidence.** A test that mocks everything it touches passes regardless of whether the pieces work together.

**Flakiness.** An intermittently failing test is worse than no test — teams learn to re-run rather than investigate, and eventually ignore real failures.

Flaky tests should be fixed or deleted, never retried into submission.

## Mocking discipline

The more you mock, the less the test proves.

```js
// Mocks everything — tests the mocks
vi.mock("./api");
vi.mock("./useAuth");
vi.mock("./analytics");

// Mocks the network boundary — tests the real code path
server.use(http.get("/api/user", () => HttpResponse.json(mockUser)));
```

Mock at the **network boundary** rather than the module boundary. The test then exercises the real API layer, error handling and validation ([[26.4 - Mocking the Network with MSW]]).

Legitimate mocking: the network, time, randomness, browser APIs unavailable in the test environment, and genuinely slow or paid third-party services.

## Writing tests that read well

```js
test("shows a validation error when email is invalid", async () => {
  const user = userEvent.setup();
  render(<SignupForm />);

  await user.type(screen.getByLabelText(/email/i), "not-an-email");
  await user.click(screen.getByRole("button", { name: /sign up/i }));

  expect(screen.getByRole("alert")).toHaveTextContent(/valid email/i);
});
```

The name states the behavior, not the mechanism. `renders correctly` and `works` tell a future reader nothing when they fail.

Arrange–act–assert, with a blank line between each, makes the structure scannable without comments.

Avoid over-abstraction. A test with three layers of helper functions is hard to debug precisely when you need it most — a failing test should be readable top to bottom. Some duplication in tests is acceptable and often preferable.

## Test independence

Each test must pass in isolation and in any order:

```js
beforeEach(() => {
  queryClient.clear();
  server.resetHandlers();
});
```

Shared state between tests produces failures that depend on execution order, which are among the hardest to diagnose. Most runners randomize order by default for exactly this reason.

## TDD, pragmatically

Writing the test first genuinely helps for pure logic with a clear specification — a pricing calculator, a date utility, a reducer. It forces you to define the interface before the implementation.

It helps less for exploratory UI work, where the design is discovered while building. Writing tests after, once the shape settles, is a reasonable and common approach.

The non-negotiable case is **bug fixes**: reproduce with a failing test first, then fix. Otherwise you cannot be certain the fix works or that the bug stays fixed.

## How senior engineers actually use this

**They test user-visible behavior** and treat implementation-coupled tests as a defect.

**They weight integration tests most heavily**, with a handful of E2E tests on critical journeys.

**They mock at the network boundary**, not the module boundary.

**They write a regression test for every bug**, before the fix.

**They delete tests that no longer earn their maintenance cost**, rather than accumulating them indefinitely.

**They fix flaky tests immediately**, because tolerating one teaches the team to ignore failures.

## Common pitfalls

- Testing state, props and internal methods rather than behavior.
- Coverage percentage as a merge gate.
- Mocking so much that the test only exercises mocks.
- Tests that depend on execution order.
- Names like "works correctly" that say nothing on failure.
- Retrying flaky tests instead of fixing them.
- Writing tests for trivial code to raise a number.
- Heavily abstracted test helpers that obscure what is being asserted.

## Interview angle

"How do you decide what to test" is a judgement question, and the strongest framing is confidence per unit of cost: test behavior the user depends on, weight integration tests most heavily because they exercise the pieces that break together, and treat static analysis as the free base layer. Adding that coverage is a diagnostic rather than a target, and that heavy mocking trades away the confidence the test was supposed to provide, shows you have maintained a suite rather than only written one.
