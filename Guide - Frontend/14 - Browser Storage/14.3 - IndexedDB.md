# IndexedDB

An asynchronous, transactional, indexed database in the browser. It is the only client storage suitable for substantial structured data — hundreds of megabytes, real objects rather than strings, and queryable by index.

## Why it exists

`localStorage` is synchronous, string-only, ~5 MB, and has no query capability beyond a key lookup ([[14.2 - LocalStorage and SessionStorage]]). IndexedDB fixes all four:

| | localStorage | IndexedDB |
| --- | --- | --- |
| API | synchronous | asynchronous |
| Types | strings | structured clone — objects, `Date`, `Blob`, `File`, `Map` |
| Size | ~5 MB | large, quota-based |
| Queries | key only | indexes, ranges, cursors |
| Transactions | none | ACID within a database |

The structured-clone support is genuinely useful: a `Date` stored in IndexedDB comes back as a `Date`, and a `Blob` comes back as a `Blob` ([[08.5 - Serialization and Structured Clone]]).

## The raw API

It is event-based and verbose. This is why nearly everyone uses a wrapper.

```js
const request = indexedDB.open("app-db", 2);

request.onupgradeneeded = (e) => {
  const db = e.target.result;

  if (!db.objectStoreNames.contains("posts")) {
    const store = db.createObjectStore("posts", { keyPath: "id" });
    store.createIndex("by-author", "authorId");
    store.createIndex("by-date", "createdAt");
  }
};

request.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction("posts", "readwrite");
  const store = tx.objectStore("posts");

  store.put({ id: 1, authorId: 7, title: "Hello", createdAt: new Date() });

  tx.oncomplete = () => console.log("done");
  tx.onerror = () => console.error(tx.error);
};
```

Key concepts:

**Version and `onupgradeneeded`** — schema changes (creating stores and indexes) can only happen here, triggered by opening with a higher version number. This is the migration mechanism.

**Object stores** — the equivalent of tables. `keyPath` designates the primary key from the object; `autoIncrement: true` generates one instead.

**Indexes** — secondary lookup paths. `{ unique: true }` and `{ multiEntry: true }` (for array values, so a post with three tags is findable by each) are the options worth knowing.

**Transactions** — `readonly` or `readwrite`, scoped to named stores. They auto-commit when the microtask queue drains with no pending requests, which means **you cannot `await` a non-IndexedDB promise inside a transaction** — the transaction will have committed by the time you resume. This catches everyone once.

## Using idb

Jake Archibald's `idb` wraps the API in promises and is roughly 1 KB:

```js
import { openDB } from "idb";

const db = await openDB("app-db", 2, {
  upgrade(db, oldVersion) {
    if (oldVersion < 1) {
      const store = db.createObjectStore("posts", { keyPath: "id" });
      store.createIndex("by-author", "authorId");
    }
    if (oldVersion < 2) {
      db.createObjectStore("drafts", { keyPath: "id", autoIncrement: true });
    }
  },
});

await db.put("posts", post);
const post = await db.get("posts", 1);
const all = await db.getAll("posts");
const byAuthor = await db.getAllFromIndex("posts", "by-author", 7);
await db.delete("posts", 1);
```

The `oldVersion` cascade in `upgrade` is the correct migration pattern — each block runs only for users below that version, so a user jumping from version 1 to 4 gets every intervening migration in order.

## Queries with ranges and cursors

```js
const range = IDBKeyRange.bound(startDate, endDate);
const recent = await db.getAllFromIndex("posts", "by-date", range);

IDBKeyRange.only(value);
IDBKeyRange.lowerBound(value, exclusive);
IDBKeyRange.upperBound(value, exclusive);
```

Cursors iterate lazily, which matters when the result set is large enough that loading it all would blow memory:

```js
let cursor = await db.transaction("posts").store.index("by-date").openCursor(range);

while (cursor) {
  process(cursor.value);
  cursor = await cursor.continue();
}
```

There are no joins and no SQL. Anything relational must be modeled with indexes and multiple lookups, which is why IndexedDB suits document-shaped data rather than normalized relational data.

## Quota and eviction

Storage is quota-based, typically a percentage of available disk — often several gigabytes on desktop, less on mobile.

```js
const { usage, quota } = await navigator.storage.estimate();

const persisted = await navigator.storage.persist();   // request exemption from eviction
```

Without persistence, browsers evict origin storage under disk pressure, in best-effort order. `navigator.storage.persist()` requests durable storage; browsers grant it based on engagement heuristics — a site the user has installed or visits frequently is more likely to be granted it.

**This means IndexedDB is not a source of truth.** Data can vanish. Design for it: sync to the server, or treat local data as a cache that can be rebuilt.

Quota errors surface as `QuotaExceededError` on the transaction, and need explicit handling with an eviction strategy of your own.

## What it is actually used for

**Offline-first applications.** The canonical case — store the working dataset locally, queue mutations, sync when online ([[28.12 - Real Time and Offline First]]).

**Caching API responses beyond memory.** Survives reloads, unlike an in-memory query cache.

**Large binary data.** Storing `Blob`s directly — uploaded images awaiting upload, downloaded media for offline playback.

**Client-side search indexes.** A full-text index over a document set, built once and queried locally.

**Draft persistence.** Editor content saved continuously without the synchronous cost of `localStorage`.

**Service worker coordination.** Service workers cannot access `localStorage` at all, but can use IndexedDB — so it is the only shared storage between a page and its service worker ([[14.4 - Cache API and Service Workers]]).

## Performance notes

Asynchronous, so it never blocks the main thread the way `localStorage` does — but the work is real. Bulk writes should share one transaction:

```js
const tx = db.transaction("posts", "readwrite");
await Promise.all([...posts.map(p => tx.store.put(p)), tx.done]);
```

One transaction for a thousand writes is dramatically faster than a thousand transactions.

Reads on an indexed field are fast; reads requiring a full scan over a large store are not. Index anything you query by.

## How senior engineers actually use this

**They use a wrapper.** `idb` for direct use, or `Dexie` when the querying needs are richer. The raw event API is a maintenance liability.

**They treat it as a cache, not a database.** Anything that matters is on the server; local storage is an optimization that can be rebuilt.

**They version schemas properly** with an `oldVersion` cascade, because users will open the app after skipping several releases.

**They never await external promises inside a transaction.** Gather the data first, then open the transaction.

**They request persistence** for offline-capable applications, and handle the case where it is denied.

## Common pitfalls

- Awaiting a `fetch` inside a transaction, which auto-commits before resuming.
- Assuming data persists forever — eviction is real.
- Schema changes outside `onupgradeneeded`.
- One transaction per write in a bulk operation.
- Forgetting that a `readwrite` transaction blocks other `readwrite` transactions on the same store.
- Using it for small key-value preferences where `localStorage` is simpler.
- Not handling the "user has an old schema version" path.

## Interview angle

IndexedDB usually appears inside "how would you build an offline-capable app". The expected content: asynchronous and transactional so it does not block, stores structured objects including Blobs, indexes for querying, versioned schema migrations, and quota-based storage that can be evicted unless persistence is granted. Mentioning that it is the only storage a service worker can share with the page is a good detail, as is the transaction auto-commit trap.
