# MVCC, Vacuum and Bloat

#backend #databases #postgres #operations

> **In one line:** Postgres never modifies a row in place — it writes a new version and leaves the old one behind — so a background process must clean up, and when it falls behind your database quietly gets larger and slower.

---

## The Idea

```sql
UPDATE documents SET title = 'new' WHERE id = 42;
```

```
Old tuple:  (id=42, title='old', xmin=100, xmax=200)   ← marked dead at txn 200
New tuple:  (id=42, title='new', xmin=200, xmax=null)  ← written elsewhere on the page
```

Every row version carries `xmin` (the transaction that created it) and `xmax` (the one that superseded it). A transaction sees a version if `xmin` is committed and visible to its snapshot, and `xmax` is not.

💡 **The payoff is enormous: readers never block writers and writers never block readers.** A long analytics query sees a consistent snapshot while writes continue at full speed. **That property is why Postgres behaves so well under mixed workloads.**

⚠️ **The cost is that dead tuples accumulate.** An `UPDATE` is really an insert plus a mark-dead; a `DELETE` is only a mark-dead. **Nothing frees space until vacuum runs.**

---

## What Dead Tuples Cost You

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
```

| Cost | Effect |
|---|---|
| **Disk space** | A 10GB table can occupy 40GB |
| **Buffer pool waste** | Dead tuples cached alongside live ones |
| Slower scans | Every sequential scan reads the dead rows too |
| Slower index scans | Indexes point at dead tuples; each must be checked and skipped |
| **Broken index-only scans** | The visibility map goes stale |

💡 **The buffer pool point is the one people miss.** If 60% of your table is dead tuples, 60% of the memory holding it is holding garbage — your effective cache has shrunk by more than half, pushing your working set past the memory cliff ([[06.2 - Postgres Architecture]]).

**Bloat is a performance problem before it is a disk problem.**

---

## Vacuum

### What plain VACUUM does

1. Scans for dead tuples
2. Removes their index entries
3. Marks their space free in the **Free Space Map**
4. Updates the **Visibility Map**
5. Advances `relfrozenxid`

⚠️ **Plain `VACUUM` does not return space to the operating system.** It makes space reusable *within* the table. A 40GB bloated table stays 40GB on disk.

**That is usually right — reusing space avoids extending the file. It also means bloat is sticky: once a table has grown, only a rewrite shrinks it.**

### VACUUM FULL

⚠️ **`VACUUM FULL` takes an `ACCESS EXCLUSIVE` lock — no reads, no writes — for however long it takes.** On a 100GB table that is hours of complete unavailability. **Never run it on a production table casually.**

```bash
pg_repack --table documents --no-superuser-check mydb
```

**`pg_repack` builds a new copy while the table stays online, using a trigger to capture concurrent changes, then swaps with a brief lock.** This is the standard production answer to bloat, and knowing it exists is worth more than knowing `VACUUM FULL`.

---

## Autovacuum

```ini
autovacuum_vacuum_scale_factor = 0.2      # vacuum after 20% of rows are dead
autovacuum_vacuum_cost_limit = 200        # throttling
```

⚠️ **On a 100-million-row table, `scale_factor = 0.2` means waiting for 20 million dead tuples.** By then the table is massively bloated and the vacuum will take hours.

```sql
ALTER TABLE documents SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 1000,
    autovacuum_analyze_scale_factor = 0.005,
    autovacuum_vacuum_cost_limit = 2000
);
```

💡 **Per-table autovacuum settings for your largest and busiest tables are one of the highest-value pieces of Postgres tuning**, and almost nobody does it. **The global defaults cannot be right for both a 100-row lookup table and a 500-million-row event table.**

### The cost limit is a throttle

Vacuum accumulates "cost" per page and sleeps when it hits the limit — **deliberately slowing down to avoid starving your queries of I/O.**

⚠️ **On modern SSD hardware the default limit is far too conservative**, and it is the most common reason vacuum cannot keep up. **Raising `autovacuum_vacuum_cost_limit` to 2000+ is usually safe and often transformative.**

## The Long Transaction Problem

⚠️ **Vacuum cannot remove a dead tuple that any open transaction might still need to see.**

```
Transaction A opens at 10:00 and stays open
10:01–11:00  millions of rows are updated
             every old version must be kept
11:00        A finally commits
```

**One forgotten transaction can bloat your entire database.** This is the most common cause of catastrophic bloat, and it usually comes from application code that opened a transaction and then did something slow ([[06.6 - Transactions and Isolation Levels]]).

```sql
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;
```

Four things hold back vacuum the same way:

| Cause | Check |
|---|---|
| **Long-running transactions** | `pg_stat_activity.xact_start` |
| **Abandoned replication slots** | `pg_replication_slots` where `active = false` |
| Long queries on a hot standby | `hot_standby_feedback = on` propagates the hold |
| Prepared transactions | `pg_prepared_xacts` — orphaned two-phase commits |

⚠️ **An inactive replication slot is a silent database killer.** A replica decommissioned without dropping its slot means WAL accumulates forever and vacuum can never advance. **Disks fill, and the cause is invisible unless you know to look.**

```sql
SELECT slot_name, active, pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
```

**Alert on inactive slots.** This one query would have prevented a large number of production outages.

## Transaction ID Wraparound

The failure mode that can take a database fully offline.

Transaction IDs are 32-bit — about 4 billion values, used circularly. To prevent old rows appearing to be from the future, vacuum **freezes** old tuples.

```sql
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY xid_age DESC;
```

| Age | Status |
|---|---|
| < 200 million | Healthy |
| 200M | Aggressive autovacuum starts, even with no dead tuples |
| **1 billion** | **Alert. Investigate now** |
| ~2 billion | **Postgres refuses new transactions. The database is down** |

⚠️ **This has taken down major companies**, most publicly Sentry and Mailchimp. **Recovery requires a single-user-mode vacuum that can take many hours, during which you are completely offline.**

💡 **It is entirely preventable with one alert.** Monitor `age(datfrozenxid)` and page someone at 1 billion — roughly half your budget, which is plenty of time to find the cause. **The cause is almost always a long transaction, an abandoned replication slot, or autovacuum being unable to keep up.**

## Measuring Bloat

```sql
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('documents');
SELECT * FROM pgstatindex('documents_pkey');
```

| Metric | Healthy | Concerning |
|---|---|---|
| `dead_tuple_percent` | < 5% | > 20% |
| `free_percent` | < 20% | > 40% |
| `avg_leaf_density` (index) | > 80% | < 60% |

⚠️ **`pgstattuple` scans the whole table.** Use `pgstattuple_approx` on large tables.

## In Production

### The monitoring set

```sql
-- 1. Dead tuples by table
-- 2. Transaction ID age  ← the one that can take you offline
SELECT max(age(datfrozenxid)) FROM pg_database;
-- 3. Oldest transaction
-- 4. Inactive replication slots
-- 5. Currently running vacuums
SELECT * FROM pg_stat_progress_vacuum;
```

💡 **`pg_stat_progress_vacuum` shows a running vacuum's phase and progress**, which is invaluable when you are waiting for one during an incident. **Most people do not know it exists.**

| Metric | Alert |
|---|---|
| `age(datfrozenxid)` | > 1 billion |
| Oldest transaction | > 10 minutes |
| **Inactive replication slot** | **Any, immediately** |
| Dead tuple ratio on a large table | > 25% |

### The bloat prevention checklist

1. **`idle_in_transaction_session_timeout`** — the single most effective defence
2. **Per-table autovacuum settings** for large and hot tables
3. **Raised `autovacuum_vacuum_cost_limit`** for SSD hardware
4. **No network calls inside transactions**
5. **`fillfactor` below 100** on update-heavy tables ([[06.1 - Storage Engines]])
6. **Alerting on all five queries above**

### HOT updates avoid the problem entirely

```sql
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables WHERE n_tup_upd > 0 ORDER BY n_tup_upd DESC;
```

💡 **A high HOT update percentage is one of the strongest health signals for an update-heavy table.** Below 50% means most updates are writing to every index and generating bloat. **Raising `fillfactor` and removing unused indexes both improve it.**

### The delete-heavy anti-pattern

⚠️ **Large periodic deletes create bloat spikes** that vacuum must then clean, during which scans are slow.

```sql
CREATE TABLE jobs (...) PARTITION BY RANGE (created_at);
DROP TABLE jobs_2026_07;      -- instant, zero dead tuples
```

💡 **`DROP TABLE` on a partition is O(1) and produces no bloat, where `DELETE` of the same rows is O(n) and produces maximum bloat.** For any table with a retention policy, this is the correct design ([[06.13 - Partitioning and Sharding]]).

## Codebase

**Repo:** `postgres/postgres`, `reorg/pg_repack`

**Question to answer:** How does a tuple's visibility get decided — trace `HeapTupleSatisfiesMVCC`. Then: how does vacuum decide a dead tuple is safe to remove, and what does the "oldest transaction" constraint mean in code?

**Read, in order:**

1. `src/backend/access/heap/README.HOT` — **HOT updates by their authors.** Short, and it explains the `fillfactor` tuning directly
2. `src/backend/utils/time/heapam_visibility.c` — **`HeapTupleSatisfiesMVCC`.** MVCC visibility in one function: the `xmin`/`xmax` checks against a snapshot
3. `src/backend/access/heap/vacuumlazy.c` — `lazy_scan_heap` and the pruning logic
4. `src/backend/storage/ipc/procarray.c` — **`GetOldestNonRemovableTransactionId`.** **The answer to the second question**, and where long transactions, replication slots and standby feedback all converge into one number
5. `src/backend/commands/vacuum.c` — freezing and wraparound protection
6. `pg_repack/lib/repack.c` — how an online rewrite works: the trigger, the log table, and the swap

💡 `GetOldestNonRemovableTransactionId` is the function worth understanding properly. **Every cause of bloat in this note ultimately produces a small value from that one function**, and seeing them converge in code makes the diagnostic instinct — "something is holding back the horizon, find it" — permanent.

**Size:** 2 sessions.


**Part 1 — See MVCC directly.**

```sql
CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('documents', 0));
```

Update one row five times and **watch five versions appear on the page.** Then vacuum and watch four disappear.

Then, with two concurrent transactions at different isolation levels, show each seeing a different version of the same row.

**Part 2 — Bloat, and its cost.** Update every row in a 5-million-row table repeatedly with autovacuum disabled.

Sample every 30 seconds: table size, dead tuple count, and latency of a sequential scan and an index scan.

**Chart query latency against bloat percentage.** Then check `Heap Fetches` on an index-only scan before and after — **this is [[06.3 - Indexes Deep Dive]]'s point about vacuum affecting reads.**

**Part 3 — The three blockers.** For each, hold back vacuum and measure the resulting bloat over 10 minutes of write load: an idle open transaction, an unconsumed replication slot, and a long query on a hot standby with feedback on.

**For each, find the single query that identifies it as the cause.** Write them into a runbook — during an incident, "why can vacuum not clean" needs a three-command answer.

**Part 4 — Autovacuum tuning, measured.** A table receiving 5,000 updates per second.

With defaults: chart dead tuples over an hour. **Autovacuum should fall behind and never catch up.**

Then sweep `autovacuum_vacuum_cost_limit`: 200, 800, 2000, 5000. **Find the setting where vacuum keeps up without degrading queries.** That number depends entirely on your storage, which is why the default cannot be right.

**Part 5 — HOT updates.** A table with 0, 2, 4 and 8 indexes, at `fillfactor` 100 and 85.

Update a non-indexed column 100,000 times in each. Measure HOT ratio, WAL generated, table growth, and index growth. **Eight cells.**

**Part 6 — Repair, three ways.** A 5GB table bloated to 15GB, fixed with `VACUUM FULL`, `pg_repack`, and `REINDEX CONCURRENTLY`.

Measure duration, lock type and duration, peak extra disk, and impact on concurrent queries.

**`VACUUM FULL` should be completely unavailable throughout. Time it and extrapolate to a 500GB table** — that number is why `pg_repack` exists.

**Part 7 — Approach wraparound.** In a throwaway database, burn transaction IDs rapidly while holding a long transaction open.

Watch `age(datfrozenxid)` climb, watch aggressive autovacuum trigger, watch the log warnings.

⚠️ **Do not push this to the actual shutdown threshold** unless the database is genuinely disposable and you have time to recover it.

**Write the alert rule and the runbook entry**: symptom, diagnostic queries, remediation in order.

**Done when:**
- You have seen multiple row versions on a page and watched vacuum remove them
- Your latency-versus-bloat chart shows the cost concretely
- You have a three-query runbook for "what is blocking vacuum"
- You know the `cost_limit` at which vacuum keeps up on your hardware
- Your HOT ratio table covers all eight configurations
- You have timed `VACUUM FULL`'s lock and can extrapolate it
- You have watched `age(datfrozenxid)` climb and written the alert
