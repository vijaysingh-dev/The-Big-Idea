# Record Types and Page Layouts

## The problem they solve

One object, several business processes.

A manufacturer sells new machines and also sells spare parts. Both are opportunities. But a new machine sale has stages like Site Survey and Installation Planning, while a parts sale is essentially quote and ship. Same object, same reporting, different process.

**Record types** let one object support multiple processes: different picklist values, different page layouts, different business processes, assigned to different users.

## What a record type controls

- **Which picklist values are available** for each picklist on the object
- **Which page layout** each profile sees
- **Which sales process, support process, or lead process** applies, meaning which stages or statuses are valid
- **Which Lightning record page** is assigned
- Which compact layout applies

What it does **not** control:

- Field-level security, which comes from profiles and permission sets
- Record access, which comes from the sharing model
- Validation rules, which apply to all record types unless the rule itself checks `RecordTypeId`
- Required fields at the field level

That last group is where misunderstandings start. A record type does not make a field required for one process and optional for another — a page layout can do that visually, and a validation rule can do it properly.

## The mechanics

Each record has a `RecordTypeId` field. The record type is metadata; the assignment is data.

```sql
SELECT Id, Name, StageName, RecordType.DeveloperName
FROM Opportunity
WHERE RecordType.DeveloperName = 'New_Machine_Sale' AND IsClosed = false
```

In Apex, never hardcode the ID — it differs in every org.

```java
Id partsSaleRt = Schema.SObjectType.Opportunity
    .getRecordTypeInfosByDeveloperName()
    .get('Parts_Sale')
    .getRecordTypeId();

Opportunity opp = new Opportunity(
    Name = 'Spare parts - Northwind',
    AccountId = accountId,
    RecordTypeId = partsSaleRt,
    StageName = 'Quote Sent',
    CloseDate = Date.today().addDays(14)
);
insert opp;
```

`getRecordTypeInfosByDeveloperName()` is the portable approach. There is also a `ByName` variant that matches the label, but labels can be translated or renamed, so developer name is the safer key. Both are describe calls, so cache the result rather than calling them inside a loop.

## Layout assignment

Page layout is assigned by the combination of **profile and record type**. That grid is the actual control surface: the same record type can show a different layout to sales, to service, and to finance.

This is how a single object serves audiences with different needs without duplicating anything. A support agent viewing an opportunity does not need the discount approval section; a sales manager does.

In Lightning, **Lightning record pages** built in App Builder are assigned similarly, by app, record type, and profile. They largely supersede page layouts for the overall page structure, but page layouts still control which fields appear in the details section, field-level required and read-only settings, and related lists — so both still matter and both are still maintained.

## Business processes

Record types tie to a process object that controls the master picklist values for the key status field:

- **Sales Process** — which Opportunity stages are available
- **Support Process** — which Case statuses are available
- **Lead Process** — which Lead statuses are available
- **Solution Process** — for the legacy Solutions object

The order is: create the process first, then the record type that references it. Missing this ordering produces record types with the full default stage list, which then have to be fixed.

## Where record types get misused

This is worth being blunt about, because record type proliferation is one of the most common causes of unmaintainable orgs.

**Using record types for security.** They are not a security feature. Making a record type unavailable to a profile stops that profile *creating* records of that type; it does not stop them seeing or editing existing ones. Access is controlled by sharing, full stop.

**Creating a record type per department, region, or product.** Each record type multiplies the layout assignment grid, the validation rule complexity, and the testing surface. Twelve record types on Opportunity means every change must be considered twelve times. If the only difference is which fields are shown, dynamic forms or a layout assignment is usually enough.

**Using them to vary required fields.** Marking a field required on a layout only enforces it in the user interface. An integration, Data Loader, or Apex bypasses it entirely. If a field must be required for a process, write a validation rule that checks the record type.

```
AND(
  RecordTypeId = $Record.RecordType.Id,
  TEXT(RecordType.DeveloperName) = "New_Machine_Sale",
  ISPICKVAL(StageName, "Installation Planning"),
  ISBLANK(Site_Survey_Date__c)
)
```

**Forgetting that new record types are invisible by default.** After creating one, it must be enabled on every profile or permission set that needs it, and layouts assigned. Users reporting "the new type does not appear" is nearly always this.

## Record types in code, safely

Two patterns worth having.

Checking a record's type without a describe call in a loop:

```java
public with sharing class OpportunityService {

    private static final Id NEW_MACHINE_RT = Schema.SObjectType.Opportunity
        .getRecordTypeInfosByDeveloperName().get('New_Machine_Sale').getRecordTypeId();

    public static void applyInstallationRules(List<Opportunity> opps) {
        for (Opportunity opp : opps) {
            if (opp.RecordTypeId != NEW_MACHINE_RT) {
                continue;
            }
            // process-specific logic
        }
    }
}
```

The static final field means the describe runs once per transaction rather than once per record.

Listing what the running user can actually create, which is how a dynamic UI should build its options:

```java
List<Schema.RecordTypeInfo> available = new List<Schema.RecordTypeInfo>();
for (Schema.RecordTypeInfo info : Opportunity.SObjectType.getDescribe().getRecordTypeInfos()) {
    if (info.isAvailable() && !info.isMaster()) {
        available.add(info);
    }
}
```

`isAvailable()` reflects the running user's profile assignment, and `isMaster()` filters out the default Master record type that always exists and should never be offered.

## Page layouts, compact layouts, and dynamic forms

**Page layouts** define the detail section fields, their required and read-only state, buttons, and related lists.

**Compact layouts** define the highlights panel at the top of a record and what appears in mobile previews and hover cards. Small, and disproportionately useful — the first five fields a user sees.

**Dynamic Forms** allow fields to be placed individually on a Lightning record page with visibility rules, rather than in a fixed layout block. This is increasingly the answer to "show this section only when the stage is X", and it reduces the need for extra record types purely for layout variation. Where available, it is usually the better tool.

## Practical guidance

**Start with one record type, add more only when the process genuinely differs.** Different picklist values or a different stage sequence justify one. Different field visibility usually does not.

**Name developer names carefully.** They appear in code, validation rules, and flows, and renaming them breaks references.

**Document what each record type is for**, in its description. Six months later nobody remembers why there are five.

**Audit periodically.** Record types that no longer have records, or profiles with access to types they never use, accumulate silently.

```sql
SELECT RecordType.DeveloperName recordType, COUNT(Id) total
FROM Opportunity
GROUP BY RecordType.DeveloperName
ORDER BY COUNT(Id) DESC
```
