# REST Done Properly

#backend #api-design #rest

> **In one line:** REST is a set of constraints, most APIs follow half of them, and the half people skip — cacheability and a genuinely uniform interface — is the half that buys you something.

---

## The Idea

Fielding's 2000 dissertation defined six constraints. Almost nobody implements all six, and that is mostly fine.

| Constraint | Meaning | Followed? |
|---|---|---|
| Client–server | Separate concerns | Yes |
| Stateless | No session state between requests | Mostly |
| **Cacheable** | Responses declare cacheability | **Rarely** |
| Uniform interface | Resources, representations, standard methods | Partly |
| Layered system | Client cannot tell if it is talking to the origin | By accident |
| Code on demand | Server can send executable code | No, and fine |

💡 **The two worth taking seriously are statelessness and cacheability**, because both have concrete operational payoffs: any server can handle any request, and infrastructure you do not own can serve traffic for you ([[03.5 - HTTP Caching]]).

HATEOAS is the constraint purists argue about and almost nobody needs. Skip the argument.

## Resources, Not Actions

```
Bad                              Good
POST /createDocument             POST /documents
POST /getDocument                GET  /documents/42
POST /updateDocumentTitle        PATCH /documents/42
POST /deleteDocument             DELETE /documents/42
POST /searchDocuments            GET  /documents?q=...
```

The right column gets you caching, safe retries, conditional requests and standard client behaviour for free ([[03.3 - Methods Status Codes and Semantics]]).

### URL structure

```
/documents                       collection
/documents/42                    item
/documents/42/annotations        sub-collection
/organisations/3/documents       scoped collection
```

- **Plural nouns**, lowercase, hyphens for multi-word
- **No file extensions** — use `Accept`
- **No trailing slash**, consistently

⚠️ **Do not nest beyond two levels.** Once an annotation has a unique ID, `/annotations/7/replies` is enough. Deep nesting forces the client to know your whole hierarchy just to build a URL.

### Actions that are not CRUD

```
POST /documents/42/reindex
POST /sources/7/sync
POST /documents/42/publish
```

💡 **This is fine and it is not a failure of REST.** Contorting "reindex this document" into a PUT on an invented `/documents/42/index-state` resource obscures intent and buys nothing.

The better alternative when the operation is slow: **model the result as a resource.**

```
POST /exports              → 202 Accepted, Location: /exports/91
GET  /exports/91           → {"status": "running", "progress": 0.4}
```

**Reach for this whenever the operation takes more than a second.** It gives you polling, cancellation, progress and a place to put errors.

## Representations

```json
{
  "id": "doc_01HQZX...",
  "title": "Q3 Report",
  "created_at": "2026-08-17T14:32:07.500Z",
  "size_bytes": 104857,
  "status": "indexed",
  "source": {"id": "src_01HQZW...", "name": "Google Drive"}
}
```

| Rule | Why |
|---|---|
| **RFC 3339 UTC timestamps with `Z`** | Unambiguous, sortable as strings |
| **Suffix units on numbers** | `size_bytes`, `timeout_ms`. `size: 100` is a bug waiting |
| **IDs are opaque strings** | Integers leak volume and invite enumeration |
| **Enums are lowercase strings** | `"status": 3` needs a lookup table forever |
| **Money is integer minor units + currency** | Never floats |
| Nullable means unknown; absent means not requested | Distinguish deliberately |

💡 **Prefixed IDs are worth adopting.** `doc_01HQZX` means a support engineer reading a log knows the object type immediately, and a client passing a source ID where a document ID belongs fails fast rather than 404ing confusingly.

**Use ULIDs or UUIDv7, not UUIDv4** — they sort by creation time, which matters enormously for index locality ([[06.3 - Indexes Deep Dive]]).

## Collections

### Use an envelope

```json
{"data": [...], "has_more": true, "next_cursor": "eyJpZCI6..."}
```

💡 **A bare array leaves nowhere for pagination, and adding it later is a breaking change.** Keep the envelope identical across every collection endpoint so clients write one pagination helper.

### Filtering and sorting

```
GET /documents?status=indexed&created_after=2026-01-01&sort=-created_at&fields=id,title
```

| Concern | Convention |
|---|---|
| Equality | `field=value` |
| Range | `created_after`, `size_min` |
| Sort | `sort=field`, `-field` for descending |
| Sparse fields | `fields=id,title` |
| Search | `q=` |

⚠️ **Whitelist everything.** Filter fields, sort fields and field selection must all be validated against an allow-list. Passing user input into a query builder gives you SQL injection, unindexed sorts, and disclosure of fields the user should not see.

**Cap what a sort can cost.** Allowing `sort=` on an unindexed column lets any client trigger a full table scan.

## Statelessness

```
Stateful:   POST /search {"q":"x"} → server stores it
            GET /search/next       → server remembers where you were

Stateless:  GET /search?q=x&cursor=abc
```

The payoff is concrete: any pod serves any request, so load balancing works, deploys are safe, scaling is trivial ([[03.10 - Proxies and Load Balancers]]).

⚠️ **Server-side sessions are a common violation and usually acceptable** — but only with a shared store. In-process session state means sticky sessions, uneven load, and state lost on deploy.

## In Production

### What is actually a breaking change

| Change | Breaking? |
|---|---|
| Adding an optional request field | No |
| Adding a response field | **Usually no** — a strict client validator will reject it |
| Removing or renaming anything | **Yes** |
| Changing a type (`"3"` → `3`) | **Yes** |
| **Adding an enum value** | **Yes, in practice** |
| Making an optional field required | Yes |
| Tightening validation | **Yes** — previously-accepted requests now fail |
| Changing default sort order | **Yes, silently** — which is worse |

⚠️ **Adding an enum value is the one people ship without thinking.** A client with an exhaustive `switch` hits an unhandled branch. Document from day one that clients must handle unknown enum values, and treat it as a contract term.

### Errors

```json
{
  "type": "https://api.conduit.local/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "errors": [{"field": "title", "code": "too_long", "max": 200}]
}
```

**Clients branch on `type` and `code`, never on message strings** ([[05.3 - Error Design]]).

### Bulk operations

```http
POST /documents/bulk
→ 207 Multi-Status
{"results": [{"id": "doc_1", "status": 200}, {"id": "doc_2", "status": 404}]}
```

⚠️ **Decide and document whether bulk is atomic.** All-or-nothing is easier to reason about and harder to scale; partial success is more useful and easier to get wrong client-side. Either is defensible; leaving it undefined is not.

## Codebase

**Repo:** `kubernetes/kubernetes`, `saleor/saleor`, `stripe` (docs)

**Question to answer:** Take three large real APIs and find where each deviates from textbook REST, and why. Specifically: how does Kubernetes handle long-running operations and partial updates, and what does its `spec`/`status` split buy it?

**Read, in order:**

1. **Kubernetes API Conventions** (`contributors/devel/sig-architecture/api-conventions.md`) — **the best public API design document there is.** Read resources, verbs, spec/status, and optional versus required fields
2. `kubernetes/staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go` — `ObjectMeta`, `ListMeta`. Note `resourceVersion` for optimistic concurrency and `continue` for pagination
3. **Google API Design Guide** — resource-oriented design and long-running operations. Different house style, same reasoning
4. **Stripe API reference** — the best-executed public REST API. Prefixed IDs, expandable objects, date-based versioning, idempotency keys
5. `saleor/saleor/graphql/` — for contrast. Understanding what GraphQL solved for them sets up [[05.4 - GraphQL - The Core Model]]

💡 The `spec`/`status` split is the idea most worth stealing. **`spec` is what the user wants; `status` is what the system observes.** The user only writes `spec`; the system only writes `status`. That eliminates an entire category of "who owns this field" bugs and maps naturally onto async operations.

**Size:** 2 sessions.

## Exercise

**Drill 5.1 — Design an API twice**

```
drills/05-rest/
├── v0/{api.py, CRITIQUE.md}          # a plausible, mediocre API
├── v1/{api.py, models.py, errors.py, ids.py, DESIGN.md}
├── contract/{openapi.yaml, breaking.py, FINDINGS.md}
├── operations/{long_running.py, bulk.py}
├── clients/{strict.py, tolerant.py}
└── README.md
```

**Part 1 — Build the bad version first.** POST for everything, 200 for errors, integer IDs, inconsistent field names, no pagination envelope, float timestamps, integer enums.

**Do not caricature it.** Make it the kind of API a competent engineer ships under time pressure — that is what makes the critique useful.

**Part 2 — Critique it.** For each flaw, write what breaks concretely: which infrastructure behaviour is lost, which client bug it causes, which future change it blocks.

Then **verify three empirically** — put a cache in front and measure the hit rate, run a crawler over it, or write a client and see what confuses you.

**Part 3 — Redesign it.** Proper resources, methods, status codes, prefixed ULIDs, envelope pagination, RFC 3339 timestamps, unit-suffixed numbers, string enums, Problem Details errors.

`DESIGN.md` documenting every convention with its reasoning **is the deliverable** — writing it forces you to notice which conventions you cannot justify.

**Part 4 — Long-running and bulk.** Reindexing as `202` plus an operation resource, with polling and an SSE variant sharing the same state. Bulk with 207, then atomically. Write down which you would choose for Conduit and why.

**Part 5 — A breaking-change detector.** Diff two OpenAPI specs using the table above.

Test it: add a response field, remove one, add an enum value, tighten a validation rule. **Confirm it catches the enum addition.** Then wire it into CI against the previous released spec.

**Part 6 — Strict versus tolerant clients.** One rejecting unknown response fields, one ignoring them.

Add a field. Add an enum value. See which breaks. Write in `FINDINGS.md` the contract terms your documentation must state about client tolerance — that determines whether "additive changes are non-breaking" is actually true for you.

**Done when:**
- `CRITIQUE.md` names a concrete consequence for every flaw, three verified
- `DESIGN.md` justifies every convention
- Long-running operations work via polling and SSE from one state model
- Your detector catches enum additions and runs in CI
- You know which client tolerance assumptions your API depends on

| Resource | Why It's Worth Your Time |
|---|---|
| [Kubernetes API Conventions](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md) | The most rigorous public API design document. The spec/status idea alone is worth it |
