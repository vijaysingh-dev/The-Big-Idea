# FOR UPDATE and Record Locking

## The problem it solves

Two transactions read the same record, both compute a new value from it, and both write. The second write overwrites the first, and the first update is silently lost.

This is a **race condition**, and it is invisible in testing because tests run one transaction at a time. It appears in production under concurrent load and produces data that is wrong in ways nobody can reproduce.

## FOR UPDATE

Appending `FOR UPDATE` to a query places a **pessimistic lock** — a lock taken before reading, held until the transaction ends — on the returned rows. Another transaction attempting to lock the same rows waits.

```java
public with sharing class ClaimNumberService {

    public static String getNextClaimNumber(String prefix) {
        // FOR UPDATE serializes access, so two transactions cannot read the same counter value
        Claim_Counter__c counter = [
            SELECT Id, Next_Value__c FROM Claim_Counter__c
            WHERE Prefix__c = :prefix
            LIMIT 1
            FOR UPDATE
        ];

        Integer next = Integer.valueOf(counter.Next_Value__c);
        counter.Next_Value__c = next + 1;
        update counter;

        return prefix + '-' + String.valueOf(next).leftPad(6, '0');
    }
}
```

Without `FOR UPDATE`, two simultaneous claims get the same number. With it, the second transaction waits for the first to commit and reads the incremented value.

The same pattern applies to round-robin assignment counters ([[04.3 - Lead Assignment Rules and Queues]]), inventory decrements, and any shared counter.

## The cost

Locks are held until the transaction commits or rolls back, and they serialize access. Consequences:

**Throughput drops.** Every transaction touching the locked row waits its turn. A single counter row locked by a high-volume process becomes the bottleneck for the whole operation.

**Waiting transactions can time out.** A transaction that cannot acquire a lock within about ten seconds fails with `UNABLE_TO_LOCK_ROW`.

**Deadlocks are possible** if two transactions lock the same rows in different orders. The platform detects and kills one of them.

So `FOR UPDATE` is correct and expensive. Use it where correctness genuinely requires serialization, and not as a general precaution.

## Alternatives to a locked counter

For high-volume sequential numbering, the lock is often the wrong answer entirely:

**Auto Number fields.** The platform generates them without a lock you manage. If the requirement is a unique sequential identifier and gaps are acceptable, this is free and correct. See [[02.3 - Custom Objects and Object Settings]].

**Platform events with a single subscriber**, serializing the work into one stream rather than contending on a row.

**Accepting gaps.** Much of the pressure for locked counters comes from a requirement for gap-free sequences, which is usually a business preference rather than a legal one. Gap-free numbering under concurrency is genuinely expensive, and it is worth asking whether it is really required.

## UNABLE_TO_LOCK_ROW

The error you will actually meet, most often during bulk data loads rather than in code you wrote.

The common causes:

**Roll-up summary contention.** Inserting child records locks the parent so its roll-up can update. Two batches touching children of the same parent collide. This is the single most common cause during data loads. See [[02.6 - Roll-Up Summary Fields]].

**Master-detail parents.** Same mechanism.

**Ownership or account skew.** One account owning 300,000 child records means every operation on those children contends on that one parent row. See [[10.9 - Data Skew]].

**Sharing recalculation** running concurrently with data modification.

**Explicit `FOR UPDATE`** held too long.

## Preventing lock contention in data loads

The techniques, in order of effectiveness:

**Sort records by parent ID before loading.** This is the big one. Grouping children of the same parent into the same batch means one lock acquisition per parent rather than contention across parallel batches.

**Use serial mode in Bulk API** where sorting is not enough. Slower, and it eliminates parallel contention entirely.

**Reduce batch size.** Smaller batches hold locks for less time.

**Defer sharing calculation** during the load, then run it once. See [[23.5 - Bulk Data Loading at Scale]].

**Load parents fully before children**, so parent records are not being modified while children reference them.

## Handling it in code

A batch job touching records that may be locked should degrade rather than fail:

```java
public with sharing class ClaimUpdateBatch implements Database.Batchable<SObject> {

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        List<Database.SaveResult> results = Database.update(scope, false);

        List<Id> retryable = new List<Id>();
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                continue;
            }
            for (Database.Error err : results[i].getErrors()) {
                // lock failures are transient; other errors are not worth retrying
                if (err.getStatusCode() == StatusCode.UNABLE_TO_LOCK_ROW) {
                    retryable.add(scope[i].Id);
                } else {
                    AutomationLogger.logError('ClaimUpdateBatch', scope[i].Id, err.getMessage());
                }
            }
        }

        if (!retryable.isEmpty()) {
            System.enqueueJob(new ClaimRetryQueueable(new Set<Id>(retryable)));
        }
    }
}
```

Distinguishing transient lock failures from real errors is what makes the retry useful. Retrying a validation rule failure a hundred times achieves nothing.

`Database.update(scope, false)` is essential here — with all-or-none, one locked record aborts the entire batch.

## Optimistic concurrency

The alternative strategy: do not lock, but detect that someone else changed the record and react.

```java
public with sharing class OptimisticUpdateService {

    public static Boolean updateIfUnchanged(Id claimId, Datetime expectedModified, Decimal newAmount) {
        Warranty_Claim__c current = [
            SELECT Id, SystemModstamp, Approved_Amount__c
            FROM Warranty_Claim__c WHERE Id = :claimId
        ];

        if (current.SystemModstamp != expectedModified) {
            return false;  // someone else changed it since the caller read it
        }

        current.Approved_Amount__c = newAmount;
        update current;
        return true;
    }
}
```

The Lightning UI does something similar automatically, warning when a record has changed since it was loaded.

This is cheaper than locking and appropriate when conflicts are rare and the correct response to one is to tell the user rather than to wait. It is not appropriate for counters, where the conflict is guaranteed under load.

## FOR VIEW and FOR REFERENCE

Two related clauses, unrelated to locking:

```sql
SELECT Id, Name FROM Account WHERE Id = :accountId FOR VIEW
SELECT Id, Name FROM Account WHERE Id = :accountId FOR REFERENCE
```

`FOR VIEW` updates `LastViewedDate` and the user's recently viewed list. `FOR REFERENCE` updates `LastReferencedDate`.

Useful when building a custom record viewer that should feed the standard "recent items" experience, and irrelevant otherwise.

## Practical guidance

**Use `FOR UPDATE` only where serialization is genuinely required.** Counters, inventory, anything with a read-modify-write cycle on shared state.

**Keep the locked window short.** Query, modify, commit. Never make a callout or perform unrelated work while holding a lock.

**Lock rows in a consistent order** across the codebase, to avoid deadlocks.

**Prefer Auto Number to a locked counter** where gaps are acceptable.

**Sort by parent before bulk loading.** It fixes most `UNABLE_TO_LOCK_ROW` failures.

**Retry lock failures, log everything else.** They are different classes of problem.

**Use `Database.update(records, false)`** in any job that might meet a locked record.
