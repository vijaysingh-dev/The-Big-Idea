# Threads and the Scheduler

#backend #os #linux #scheduling #performance

> **In one line:** The scheduler decides which thread runs on which core and for how long. Context switches, run-queue length and cgroup CPU quotas explain most "the CPU looks fine but latency is terrible" mysteries.

---

## The Idea

You have more threads than cores. Right now your laptop has a few thousand threads and maybe 8–16 cores. The **scheduler** is the kernel code that keeps picking which thread runs next, many times a second, on every core.

It has to balance three goals that fight each other:

| Goal | Wants | Example |
|---|---|---|
| **Throughput** | Long time slices, few switches | A batch job crunching numbers |
| **Latency** | Short slices, wake the waiting thread fast | Your API handler that just got a request |
| **Fairness** | Everyone gets their share | Ten tenants on one box |

Your Python service is a latency workload. Most of the time its threads are asleep in `epoll_wait`. What matters is how quickly it gets a core back when a packet arrives.

---

## Threads at the Kernel Level

In [[01.3 - Threads Processes and Coroutines]] you met threads from Python's side. From the kernel's side:

- A Linux thread is a `task_struct` created by `clone()` with flags that say "share memory, share file table, share signal handlers".
- The kernel schedules **threads**, not processes. A process with 40 threads has 40 entries competing for CPU.
- Each thread has its own kernel stack, register set and scheduling state.

```bash
ps -eLf | grep uvicorn          # one line per thread (LWP column = thread id)
ls /proc/$PID/task | wc -l      # thread count
top -H -p $PID                  # per-thread CPU usage
```

A typical uvicorn worker has more threads than you expect: the main thread running the event loop, the anyio thread pool for `def` endpoints, threads from your DB driver or gRPC client, and maybe an OpenTelemetry exporter thread.

---

## How Linux Picks the Next Thread

Linux used the **Completely Fair Scheduler (CFS)** from 2007 and replaced it with **EEVDF** in kernel 6.6 (2023). The core idea carries over:

1. Each runnable thread tracks how much CPU time it has had, weighted by its priority. This is its **virtual runtime**.
2. The scheduler runs the thread that is furthest behind, the one that has had the least.
3. A thread that sleeps (waiting on I/O) falls behind, so when it wakes up it gets the CPU quickly.

That third point is why I/O-bound services feel responsive on a busy box: they are always "owed" time.

```
Per-core run queue (sorted by virtual runtime)

  least ◄───────────────────────────────────► most
  [api-thread] [worker-3] [log-shipper] [batch-job]
       ▲
   runs next
```

**Priorities:** `nice` values go from −20 (greedy) to +19 (polite). Each step is roughly a 10% change in CPU share. `nice -n 10 python batch.py` is the cheapest isolation you can buy.

**Real-time classes** (`SCHED_FIFO`, `SCHED_RR`) bypass all of this and always win. Do not use them for application code. A real-time thread in a busy loop can lock a core forever.

## Context Switches

A **context switch** is the kernel saving one thread's registers and loading another's.

| Kind | Cause | Seen in |
|---|---|---|
| **Voluntary** | The thread blocked: `read`, `epoll_wait`, `futex`, `sleep` | `voluntary_ctxt_switches` in `/proc/<pid>/status` |
| **Involuntary** | Its time slice ran out, or a higher-priority thread woke | `nonvoluntary_ctxt_switches` |

The direct cost is about 1–5 µs. The **indirect** cost is bigger: the new thread finds the CPU caches and TLB full of someone else's data and runs slowly for a while.

```bash
pidstat -w -p $PID 1        # cswch/s (voluntary), nvcswch/s (involuntary)
vmstat 1                    # "cs" column: system-wide switches per second
```

How to read it:

- **High voluntary switches** in a service is normal. It is waiting on I/O.
- **High involuntary switches** means threads are being kicked off the CPU before they are done. There are too many runnable threads for the cores. That is CPU contention, and it shows up as latency.

## Load Average, Honestly

`uptime` shows three numbers: the 1, 5 and 15 minute load averages.

On Linux, load is the average number of threads that are **runnable (`R`) or in uninterruptible sleep (`D`)**. That second part surprises people.

| Box | Load | CPU idle | Meaning |
|---|---|---|---|
| 8 cores | 4 | 50% | Half busy. Fine |
| 8 cores | 16 | 0% | Twice as much work as cores. Threads are queuing; latency is climbing |
| 8 cores | 30 | 70% | Not CPU. Threads stuck in `D`: slow disk, NFS, or a hung storage device |

💡 Load average alone is a weak signal. Use **PSI (pressure stall information)** on kernels 4.20 and later. It reports what fraction of time tasks were stalled waiting for CPU, memory or I/O:

```bash
cat /proc/pressure/cpu
# some avg10=12.50 avg60=8.20 avg300=4.10 total=...
#   → 12.5% of the last 10 s, at least one task was waiting for CPU
cat /proc/pressure/io
cat /proc/pressure/memory
```

## cgroups and CPU Throttling: The Container Trap

In Kubernetes or Docker, a CPU limit is enforced by the **CFS bandwidth controller** in cgroups. A limit of `cpu: 2` means "2 cores' worth of time per 100 ms period", i.e. **200 ms of CPU time every 100 ms**, spread across any number of threads.

Here is the trap:

```
limit: 1 CPU  →  100 ms of CPU per 100 ms period

Your service has 8 threads. A burst of requests arrives.
All 8 threads run in parallel on 8 host cores.

  t=0 ms     8 threads start running
  t=12.5 ms  8 × 12.5 ms = 100 ms used. Quota gone.
  t=12.5–100 ms  THROTTLED. No thread in the cgroup runs at all.
  t=100 ms   new period, quota refilled

A request that needed 15 ms of CPU now takes over 100 ms.
Average CPU usage over a minute: maybe 30%. Dashboards look healthy.
```

Detect it:

```bash
cat /sys/fs/cgroup/cpu.stat
# nr_periods 120000
# nr_throttled 18000      ← 15% of periods throttled
# throttled_usec 940000000
```

In Prometheus, the cAdvisor metric is `container_cpu_cfs_throttled_periods_total`. Alert on its ratio to `container_cpu_cfs_periods_total`.

**Fixes, in order of preference:**

1. Size thread pools and worker counts to the **limit**, not the host core count. `os.cpu_count()` returns host cores. Read the quota from `/sys/fs/cgroup/cpu.max`, or set worker counts explicitly from config.
2. Raise the limit, or remove CPU limits and keep **requests** (many teams do this for latency-sensitive services).
3. Do not run CPU-heavy work in the same container as the request path.

⚠️ This is one of the most common hidden causes of p99 latency in containerised Python services. It does not show up in average CPU graphs. Covered from the Kubernetes side in [[14.4 - Probes Resources and Autoscaling]].

## CPU Affinity and NUMA (Briefly)

- **Affinity** pins a thread to particular cores (`taskset`, `os.sched_setaffinity`). Useful for benchmarks and some high-performance network setups. Rarely needed in application code.
- **NUMA:** on big multi-socket servers, each socket has its own local RAM. Memory on the other socket is slower to reach. Databases on large machines care about this. Your API container usually does not.

```python
import os
len(os.sched_getaffinity(0))   # cores this process may run on — respects cpusets, not CFS quota
```

## In Production

| Symptom | Likely cause | Check |
|---|---|---|
| p99 spikes, average CPU 30% | cgroup throttling | `cpu.stat` `nr_throttled` |
| Load high, CPU idle | Threads in `D` state on I/O | `ps -eo stat,pid,cmd \| grep ^D`, `iostat -x 1` |
| High `nvcswch/s` | More runnable threads than cores | `pidstat -w`, reduce workers or threads |
| One core at 100%, others idle | Single-threaded bottleneck: the event loop, a Redis instance, a GIL-holding thread | `top -H`, `mpstat -P ALL 1` |
| Batch job slows the API on the same host | No priority separation | `nice`, separate cgroups, separate nodes |

## Codebase

**Repos:** `mit-pdos/xv6-riscv`, then `torvalds/linux` (skim only)

**Question to answer:** What happens, instruction by instruction, when the timer interrupt fires and the kernel decides to run a different thread?

**Read, in order:**

1. xv6 `kernel/trap.c` — `devintr()` and the `which_dev == 2` timer branch that calls `yield()`
2. xv6 `kernel/proc.c` — `yield()`, `sched()`, `scheduler()`. xv6's scheduler is a round-robin loop of about 30 lines. Read it fully.
3. xv6 `kernel/swtch.S` — the context switch itself: 28 lines that save and restore registers. This is the "1–5 µs".
4. Linux `kernel/sched/fair.c` — skim `pick_next_task_fair` and search for `vruntime` (renamed or extended under EEVDF in newer trees). Do not try to understand it all; notice the gap between 30 lines and 13,000.

**Size:** 1–2 sessions.
