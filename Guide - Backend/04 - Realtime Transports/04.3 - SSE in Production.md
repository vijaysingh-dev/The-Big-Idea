# SSE in Production

#backend #realtime #sse #operations

> **In one line:** SSE is simple to write and full of operational traps — buffering proxies, worker starvation, deploy storms and leaked subscriptions — and every one of them is silent.

---

## The Idea

[[04.2 - Server Sent Events]] covers the protocol. This note is about what breaks when you run it.

The common thread: **SSE failures do not produce errors.** A buffered stream looks like a slow stream. A leaked subscription looks like a slow memory leak. A starved worker looks like a slow service. There is no exception, no 500, no log line — which is why the diagnostic techniques matter more here than the protocol does.

---

## Trap 1: Buffering

The most common SSE problem, and it has a dozen possible causes.

```
App yields chunks → something buffers → client receives everything at the end
```

### Every place it can happen

| Layer | Cause | Fix |
|---|---|---|
| nginx | `proxy_buffering on` (default) | `proxy_buffering off` or `X-Accel-Buffering: no` |
| nginx | `gzip on` | `gzip off` for the location |
| App middleware | `GZipMiddleware` | Exclude SSE routes |
| App middleware | `BaseHTTPMiddleware` | Use pure ASGI middleware |
| CDN | Buffers by content type | Bypass the CDN for SSE, or configure streaming |
| AWS ALB | Does not buffer, but 60s idle timeout | Heartbeats |
| Cloudflare | Buffers some responses | `Cache-Control: no-transform` plus config |
| Python | Not flushing the generator | `yield` immediately, do not accumulate |

### The test

```bash
curl -N -v https://api.example.com/events
```

`-N` disables curl's buffering. Events should appear one at a time as they are generated.

Better, timestamp them:

```bash
curl -N -s https://api.example.com/events | while IFS= read -r line; do
    echo "$(date +%s.%N) $line"
done
```

💡 **Run this test against your full production path, not just your app.** Buffering is almost always introduced by something between your app and the client, so testing locally proves nothing.

### The nginx configuration that works

```nginx
location /events {
    proxy_pass http://app;

    proxy_buffering off;
    proxy_cache off;
    gzip off;

    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;

    chunked_transfer_encoding on;
}
```

⚠️ **`proxy_read_timeout` defaults to 60 seconds.** Even with heartbeats every 15 seconds this is fine, but if your heartbeat interval is longer than this the connection dies. Set it high anyway — heartbeats are for the middleboxes you do not control.

## Trap 2: Worker Starvation

The trap that catches people who scale SSE without thinking about it.

```
uvicorn --workers 4
1000 SSE clients connect
```

Each SSE connection holds a task for its entire lifetime. That is fine for asyncio — 1,000 idle tasks cost almost nothing. But:

```bash
uvicorn app:app --limit-concurrency 100
```

⚠️ **`--limit-concurrency` counts SSE connections.** 100 SSE clients and your service returns 503 to everything else, including health checks. The setting that protects you from overload has become the thing causing an outage.

Worse, with `def` endpoints anywhere in the app, SSE connections in the anyio thread pool would exhaust the 40-thread limit ([[01.3 - Threads Processes and Coroutines]]) — though a correctly written `async def` SSE handler does not use threads at all.

### The fix: separate the SSE service

```
                 ┌── api-service     (short requests, --limit-concurrency 1000)
LB ──────────────┤
                 └── events-service  (SSE only, no concurrency limit, more replicas)
```

💡 **Separating SSE from your request-response API is the standard production shape**, and it is worth doing before you need to. Different scaling characteristics (memory-bound versus CPU-bound), different deploy tolerance, different limits. Conduit phase 4 does this.

If you cannot separate them, at minimum ensure your concurrency limit accounts for the expected SSE connection count plus headroom for normal requests.

## Trap 3: Leaked Subscriptions

```python
async def event_stream(user_id: str):
    queue = await broker.subscribe(user_id)
    while True:
        event = await queue.get()
        yield format_sse(event)
    # unsubscribe never runs
```

The client disconnects, the task is cancelled, and the subscription stays in the broker forever. Memory grows slowly. Redis pub/sub subscriptions accumulate. Nothing errors.

```python
async def event_stream(user_id: str):
    queue = await broker.subscribe(user_id)
    try:
        while True:
            event = await queue.get()
            yield format_sse(event)
    finally:
        await broker.unsubscribe(user_id, queue)
```

⚠️ **`finally` runs on cancellation, which is exactly what a client disconnect produces** ([[01.7 - Cancellation and Structured Concurrency]]). But if your cleanup itself awaits and a second cancellation arrives during shutdown, it can be interrupted — use `asyncio.shield` around cleanup if it must complete.

**Test for it explicitly:**

```python
async def test_no_subscription_leak():
    baseline = broker.subscription_count()
    tasks = [connect_sse() for _ in range(100)]
    await asyncio.gather(*tasks)
    for t in tasks:
        t.cancel()
    await asyncio.sleep(0.5)
    assert broker.subscription_count() == baseline
```

This test is worth having permanently. The leak is invisible until it is an incident.

## Trap 4: The Deploy Storm

1,000 SSE clients. You deploy. Every connection drops.

```
t=0     deploy starts, pods terminate
t=0-30  1000 clients reconnect
t=30    all reconnect simultaneously → 1000 auth calls, 1000 replay queries
```

⚠️ **The reconnect burst is often larger than your normal peak load**, and it arrives while your service is mid-deploy with reduced capacity.

Three mitigations, all needed:

**1. Server-controlled retry with jitter:**

```python
# Send a randomised retry interval so clients do not sync up
yield f"retry: {random.randint(2000, 8000)}\n\n".encode()
```

**2. Graceful shutdown that spreads disconnects:**

```python
async def shutdown_handler():
    clients = list(active_connections)
    random.shuffle(clients)
    for i, conn in enumerate(clients):
        await conn.close()
        await asyncio.sleep(0.01)      # 100/sec instead of all at once
```

**3. Rate limit reconnections:**

```python
if not await reconnect_limiter.allow(user_id):
    return Response(status_code=429, headers={"Retry-After": "5"})
```

💡 **The `retry:` field is your lever and almost nobody uses it.** You can tell every client to back off before you start a deploy — send `retry: 30000` a minute ahead, and the reconnect storm spreads over 30 seconds instead of arriving at once.

## Trap 5: Slow Clients

A client on a poor connection reads slowly. Your server keeps generating.

Covered in principle in [[01.11 - Backpressure Inside One Process]]; here is the SSE-specific shape:

```python
class ClientStream:
    def __init__(self, maxsize: int = 100):
        self.queue = asyncio.Queue(maxsize=maxsize)
        self.dropped = 0

    def publish(self, event: Event) -> bool:
        try:
            self.queue.put_nowait(event)
            return True
        except asyncio.QueueFull:
            self.dropped += 1
            slow_client_drops.inc()
            if self.dropped > 50:
                self.disconnect()      # give up on this client
            return False
```

The policy depends entirely on the data:

| Data | Policy |
|---|---|
| Progress percentage | **Drop oldest.** Only the latest matters |
| Chat messages | **Disconnect and force resync.** Gaps are unacceptable |
| Log lines | Drop, with a `{"dropped": n}` marker so the user knows |
| LLM tokens | Disconnect. A gap makes the output nonsense |

⚠️ **Never block on a slow client.** `await queue.put()` on a full queue in a fanout loop means the slowest client sets the pace for everyone. Use `put_nowait` and a policy.

## Trap 6: Multi-Pod Fanout

```
User connects to pod-3
Ingestion worker on pod-7 generates an event
```

pod-3 has the connection. pod-7 has the event. You need a backplane.

```python
# Publisher, anywhere
await redis.publish(f"events:{org_id}", orjson.dumps(event))

# Each pod subscribes and fans out to its local connections
async def backplane_listener():
    pubsub = redis.pubsub()
    await pubsub.psubscribe("events:*")
    async for msg in pubsub.listen():
        org_id = msg["channel"].decode().split(":")[1]
        for stream in local_streams_for(org_id):
            stream.publish(orjson.loads(msg["data"]))
```

⚠️ **Redis pub/sub is fire-and-forget.** A message published while a pod is momentarily disconnected from Redis is gone. For SSE this is usually acceptable *because* you have a replay log — the client reconnects with `Last-Event-ID` and catches up.

**The replay log is what makes an unreliable backplane safe.** Redis Streams give you both in one primitive: `XADD` to publish with an ID, `XREAD BLOCK` to consume live, `XRANGE` to replay. If you are building this fresh, use Streams rather than pub/sub.

Full treatment in [[04.6 - Scaling Long Lived Connections]].

## In Production

### The metrics that matter

```python
sse_connections_active.set(len(active))
sse_connection_duration_seconds.observe(duration)
sse_events_sent_total.inc()
sse_client_queue_depth.observe(depth)
sse_slow_client_drops_total.inc()
sse_reconnects_total.labels(reason=...).inc()
sse_replay_events_total.observe(count)
sse_resync_required_total.inc()
```

💡 **`sse_resync_required_total` is the quality metric.** It counts clients that were disconnected long enough to lose events. If it is climbing, either your replay buffer is too small or connections are dropping more than you think. It is the number that tells you whether your realtime feature is actually reliable.

**Reconnect rate** is the health signal. Steady state should be near zero. A spike means something is killing connections — a proxy timeout change, a heartbeat failure, or a crash loop.

### The pre-production checklist

| Check | How to verify |
|---|---|
| No buffering anywhere in the path | `curl -N` with timestamps, through production infrastructure |
| Heartbeats under every timeout in the path | Enumerate every proxy and NAT timeout, take the minimum |
| Subscriptions cleaned up on disconnect | The leak test above |
| Concurrency limits account for SSE connections | Read your `--limit-concurrency` and do the arithmetic |
| Replay buffer sized for realistic outages | How long is a laptop asleep? |
| Resync path implemented and tested end to end | The overflow test |
| Slow-client policy chosen and implemented | Per data type |
| Reconnect jitter configured | `retry:` field, randomised |
| Compression disabled on SSE routes | Check response headers |
| HTTP/2 at the edge | Or accept the 6-connection limit |

⚠️ **The "heartbeats under every timeout" check requires actually enumerating the path.** Client → CDN → load balancer → ingress → service. Each has a timeout, and the shortest one wins. People set a 30-second heartbeat and discover a corporate proxy with a 20-second timeout.

### Debugging a broken SSE deployment

```
1. curl -N directly against the pod
   Works → the problem is in the path, not your app
   Fails → your app is buffering or not yielding

2. curl -N through each layer in turn
   Add one layer at a time. The layer where it breaks is the culprit

3. Check for heartbeats in the output
   Absent → your heartbeat logic is broken
   Present but connection still dies → interval too long for some timeout

4. Check sse_connections_active vs actual clients
   Server count higher → leaked subscriptions

5. Check reconnects_total
   High → something is killing connections. Find which layer

6. Check resync_required_total
   High → replay buffer too small for your actual disconnect durations
```

### When to give up on SSE

SSE is the right default, but not always:

| Situation | Consider instead |
|---|---|
| Client needs to send frequently | WebSocket |
| Binary payloads | WebSocket, or base64 with 33% overhead |
| Tens of thousands of events per second per client | WebSocket — lower per-message overhead |
| Corporate proxies mangling streams | Long polling |
| You need guaranteed delivery | A durable queue plus polling |

## Codebase

**Repo:** `sysid/sse-starlette`, `vllm-project/vllm`, `centrifugal/centrifugo`

**Question to answer:** How does each of these handle a client that disconnects mid-stream, and how do they detect it? Then: what is Centrifugo's policy when a client's outbound queue fills, and what is it configurable to?

**Read, in order:**

1. `sse-starlette/sse_starlette/sse.py` — **the whole file.** The ping task, the disconnect listener, and the interaction between them. Note how it races the disconnect detection against the generator
2. `vllm/entrypoints/openai/serving_chat.py` — find the abort path. **A disconnected client should stop GPU work immediately**, and seeing how they detect it is instructive
3. `centrifugo/internal/client/client.go` — the per-client write queue and the `client_queue_max_size` handling. This is the slow-client policy as a production feature with a configuration knob
4. `centrifugo/internal/` — the Redis broker with history. Note that they use Redis Streams for exactly the replay reason in this note
5. `zulip/zerver/tornado/event_queue.py` — queue garbage collection for clients that never come back. **The leak problem, solved properly**

💡 The Zulip queue GC is the part most implementations lack. A client that disconnects without a clean close leaves a queue that will never be drained. Zulip expires them on a timer. If you are building a realtime backend, copy this — it is the difference between a service that runs for months and one that needs weekly restarts.

**Size:** 1 session.

## Exercise

**Drill 4.2 — Break SSE six ways, then fix it**

Every part reproduces a real incident.

```
drills/04-sse-prod/
├── stack/
│   ├── compose.yml       # app + nginx + redis + 3 replicas
│   └── nginx/
├── traps/
│   ├── 1_buffering/
│   ├── 2_starvation/
│   ├── 3_leak/
│   ├── 4_deploy_storm/
│   ├── 5_slow_client/
│   └── 6_multipod/
├── tools/
│   ├── timestamped_curl.sh
│   ├── leak_test.py
│   └── metrics.py
├── production/
│   ├── app.py            # everything fixed
│   ├── checklist.md
│   └── runbook.md
└── README.md
```

**Part 1 — Buffering, layer by layer.** Working SSE endpoint. Add layers one at a time: nginx with defaults, then gzip, then `GZipMiddleware`, then `BaseHTTPMiddleware`.

After each, run the timestamped curl test and record time-to-first-event.

Build the table: which layers break it and which fix works for each. **Then remove the fixes one at a time to confirm each is actually necessary** — people often carry configuration that does nothing.

**Part 2 — Starve the workers.** `--limit-concurrency 100`. Connect 100 SSE clients. Then make a normal request.

Watch it 503. Watch the health check 503. Watch Kubernetes restart the pod. Watch all 100 clients reconnect to another pod and repeat.

**This cascade is the incident.** Record the full sequence with timestamps.

Then fix it by separating the SSE service and confirm the API stays healthy under the same load.

**Part 3 — Leak subscriptions.** SSE endpoint with no `finally`. Connect and abruptly kill 1,000 clients over 10 minutes.

Chart: server-side subscription count, process RSS, and Redis `pubsub_channels`. All should climb and never fall.

Then fix and repeat. Then write the permanent regression test.

**Part 4 — The deploy storm.** 1,000 connected clients. Rolling restart.

Chart requests per second during recovery, and compare to steady-state peak.

Then apply all three mitigations — jittered `retry:`, staggered shutdown, and reconnect rate limiting — and chart again.

**Measure how much longer full recovery takes with mitigations, and decide whether that trade is right.** It usually is, and being able to state the tradeoff numerically is the point.

**Part 5 — Slow client isolation.** 100 clients, 5 of them reading at 1 byte per second, generating 100 events per second.

Naive version: measure event latency for the 95 fast clients. It should track the slow ones.

Then per-client bounded queues with each of the three policies. Measure fast-client latency and slow-client data loss for each.

**Build the policy table** and write which you would choose for each of Conduit's four event types.

**Part 6 — Multi-pod fanout.** Three replicas behind a load balancer. A client connected to pod-1. Generate an event on pod-3.

Without a backplane: the client receives nothing. With Redis pub/sub: it works, but kill Redis briefly during publishing and show the event lost.

With Redis Streams plus replay: kill Redis, restart it, and confirm the client catches up on reconnect with no gap.

**Part 7 — The production build.** Assemble everything: separated service, no buffering, heartbeats, bounded queues, Streams backplane with replay, resync signalling, jittered reconnect, full metrics.

Load test: 2,000 concurrent clients, 500 events per second total, one rolling deploy mid-test, one Redis restart mid-test.

**Requirement: zero silent data loss.** Every client either receives every event or receives an explicit `resync_required`. Prove it by having each client verify event ID continuity and report gaps.

Then write `runbook.md`: for each of the six traps, the symptom, the first command to run, and the fix.

**Done when:**
- Your buffering table shows which layers break it and which fixes are load-bearing
- You reproduced the full starvation-to-restart-loop cascade with timestamps
- The leak test is a permanent regression test
- Your deploy storm charts show mitigation working, with the recovery-time tradeoff quantified
- The slow-client policy table covers all four Conduit event types
- Part 7 survives a deploy and a Redis restart with zero silent gaps
- The runbook covers all six traps
