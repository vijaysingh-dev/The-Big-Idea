# Real Time and Offline First

Both problems share a shape: the client holds state that may diverge from the server, and something must reconcile them.

## Real-time: choosing a transport

The transport decision is covered in [[15.8 - WebSockets and Server Sent Events]]. The architectural summary:

```
Updates every 30s+?             → polling. Costs nothing operationally.
Server → client only?           → SSE. Free reconnection and event replay.
Bidirectional, low latency?     → WebSocket.
Streaming one response?         → fetch + ReadableStream.
```

**Start with polling.** A dashboard refreshing every thirty seconds does not need a persistent connection, and persistent connections carry real infrastructure cost — sticky sessions or a pub/sub layer, connection-count scaling, and every deploy dropping every connection.

The most common architectural mistake here is adopting WebSockets for something polling handles, and then owning the operational complexity permanently.

## Integrating real-time with the cache

A common failure is treating live updates as a parallel state system. They should feed the same cache everything else reads ([[24.6 - TanStack Query Fundamentals]]):

```ts
socket.on("message:new", (message) => {
  queryClient.setQueryData(messageKeys.list(message.roomId), (old) =>
    old ? { ...old, items: [...old.items, message] } : old
  );
});

socket.on("product:updated", (product) => {
  queryClient.setQueryData(productKeys.detail(product.id), product);
  queryClient.invalidateQueries({ queryKey: productKeys.lists() });
});
```

One source of truth, one set of components, no synchronization between a socket store and a query cache.

Two operational details:

**Batch high-frequency updates.** A message per second re-rendering the tree is fine; fifty per second is not. Buffer and flush on an interval or inside a transition ([[22.4 - useTransition and startTransition]]).

**Reconcile on reconnect.** After a dropped connection the client has missed events. Refetch rather than assuming continuity:

```ts
socket.on("reconnect", () => queryClient.invalidateQueries());
```

Reconnection is not an edge case — it happens on every deploy, every network handoff, and every laptop lid close.

## Offline-first: the model

```
action → apply locally → persist to a durable queue → sync when online
```

The application reads and writes local storage as the primary source of truth, and synchronization happens in the background. This is what makes an app usable on a train.

```ts
async function updateTodo(id: string, changes: Partial<Todo>) {
  await db.todos.update(id, { ...changes, _dirty: true, _updatedAt: Date.now() });
  await db.outbox.add({ op: "update", entity: "todo", id, changes, ts: Date.now() });
  void trySync();
}
```

IndexedDB is the storage layer — `localStorage` is synchronous, ~5MB, and string-only, which makes it unsuitable for anything substantial ([[14.3 - IndexedDB]]).

The **outbox** is the critical piece: a durable, ordered log of pending operations. Without it, a mutation attempted while offline is simply lost.

## Sync requirements

A correct sync layer needs all of these, and each is easy to miss:

**Ordering.** Operations must replay in the order they were made, or a create-then-delete becomes a delete-then-create.

**Idempotency.** A retried operation must not apply twice. Every operation carries a client-generated id, and the server deduplicates on it ([[24.3 - Retries Timeouts and Cancellation]]).

**Id reconciliation.** Records created offline have temporary client ids that must be mapped to server ids once synced — and any local reference to the temporary id updated ([[24.5 - Optimistic UI]]).

**Conflict resolution.** The same record changed on two devices. Someone must decide what wins.

**Partial failure.** One operation in the queue fails permanently — a validation rejection — and must not block the rest forever.

That last one is the most commonly overlooked. A poison message in the outbox that retries indefinitely silently stops all synchronization.

## Conflict resolution

Four approaches, in increasing order of cost and correctness:

**Last write wins.** Simple, and silently loses data. Adequate when concurrent edits are rare and the data is low-stakes.

**Server wins.** The client discards its version. Safe, and discards user work.

**Field-level merge.** Different fields changed on each side are merged; only genuine field collisions conflict. Substantially better than record-level LWW and not much harder.

**CRDTs.** Conflict-free replicated data types merge deterministically without a server arbiter. Yjs and Automerge are the practical implementations, and they are what collaborative editors use.

```ts
const doc = new Y.Doc();
const text = doc.getText("content");
// Concurrent edits from any number of peers converge to the same result
```

CRDTs genuinely solve merging, at the cost of larger payloads, a different data model, and metadata that grows with edit history. Worth it for collaborative editing; overkill for a todo list.

**Ask the user.** For high-stakes data, showing both versions and letting the user choose is more honest than any automatic rule.

The choice should follow the data: a document body needs CRDTs or explicit resolution; a "last read at" timestamp is fine with LWW.

## Service Worker as the network layer

```js
self.addEventListener("fetch", (event) => {
  if (event.request.method !== "GET") return;

  event.respondWith(
    caches.match(event.request).then((cached) => {
      const network = fetch(event.request).then((res) => {
        caches.open("api-v1").then((c) => c.put(event.request, res.clone()));
        return res;
      });
      return cached ?? network;
    })
  );
});
```

The Service Worker makes offline reads possible and gives cache-first behavior for the app shell ([[14.4 - Cache API and Service Workers]]).

Background Sync defers mutations until connectivity returns, handled by the worker even if the page is closed — though support is uneven, so a foreground retry loop is still required as a fallback.

Two operational warnings: a Service Worker can pin users to an old build indefinitely if the update logic is wrong, and it must be cleared on logout or it serves the previous user's cached data ([[28.6 - Caching Strategy Across Layers]]).

Always ship a kill switch — a way to unregister and clear caches remotely.

## Detecting connectivity

```ts
navigator.onLine        // only reports a network interface, not reachability
```

A captive portal, a dead backend and a firewalled network all report `online`. Treat it as a hint that improves the error message, never as a reliable signal.

The trustworthy signal is whether requests actually succeed:

```ts
const isReachable = lastSuccessfulRequest > Date.now() - 30_000;
```

Combine both: `navigator.onLine === false` is reliable evidence of *offline*; `true` is not evidence of online.

## Communicating state to the user

Offline-capable applications must be honest about what has been saved:

```jsx
{pendingCount > 0 && (
  <div role="status">{pendingCount} changes will sync when you are back online</div>
)}
```

Three states worth surfacing: **synced**, **pending** (queued locally), and **failed** (needs attention). An interface that looks identical whether or not data reached the server is the worst possible outcome — users lose work and do not know it.

## Sync engines

Building this correctly is a large project. Purpose-built options exist:

| | Model |
| --- | --- |
| **Replicache / Zero** | client-side mutations with server reconciliation |
| **ElectricSQL / PowerSync** | Postgres replicated to local SQLite |
| **Yjs / Automerge** | CRDT documents with pluggable transport |
| **RxDB / WatermelonDB** | offline-first local databases with sync adapters |
| **TanStack Query persistence** | cache persistence and offline mutations — the lightest option |

For most applications, the lightest option is enough: persist the query cache, queue mutations with `networkMode: "offlineFirst"`, and accept last-write-wins ([[24.7 - Caching Stale Time and Invalidation]]).

Reach for a sync engine when offline is a core product requirement rather than a resilience improvement.

## How senior engineers actually use this

**They start with polling** and escalate only with a measured reason.

**They feed real-time updates into the existing cache**, never a parallel store.

**They treat reconnection as the normal path**, refetching rather than assuming continuity.

**They choose conflict resolution per data type**, not one global rule.

**They surface pending and failed sync state**, so users are never misled about what was saved.

**They ship a Service Worker kill switch** before shipping the Service Worker.

## Common pitfalls

- WebSockets where polling would do, taking on permanent operational cost.
- Real-time updates in a store parallel to the query cache.
- No reconnection reconciliation, leaving permanently stale data.
- High-frequency updates re-rendering per message.
- Mutations lost while offline because there is no durable queue.
- A poison message blocking the entire outbox.
- Trusting `navigator.onLine`.
- Last-write-wins on data where silent loss is unacceptable.
- A Service Worker with no kill switch or logout clearing.

## Interview angle

For "how would you add real-time updates", justify the transport from the requirements rather than defaulting to WebSockets, and show the updates feeding the existing cache with reconnect reconciliation. For "how would you support offline", give the model — apply locally, queue durably, sync in the background — and then the requirements that make it correct: ordering, idempotency, id reconciliation and conflict resolution. Naming CRDTs as the answer for collaborative text, and last-write-wins as adequate elsewhere, shows you scale the solution to the problem.
