# Control Flow and Loops

## Conditionals

```java
if (claim.Claim_Amount__c > 500000) {
    claim.Approval_Tier__c = 'Executive';
} else if (claim.Claim_Amount__c > 100000) {
    claim.Approval_Tier__c = 'Director';
} else {
    claim.Approval_Tier__c = 'Manager';
}
```

**Braces are optional for single statements and should always be used anyway.** A later edit adding a second line to a braceless branch is a classic defect, and it reads as correct.

The ternary and null-coalescing operators handle simple cases more cleanly:

```java
String tier = claim.Claim_Amount__c > 100000 ? 'Senior' : 'Standard';
Decimal amount = claim.Approved_Amount__c ?? 0;
```

## Switch

`switch on` handles Integer, Long, String, Enum, and sObject types.

```java
switch on claim.Status__c {
    when 'Submitted', 'Under Review' {
        processOpenClaim(claim);
    }
    when 'Approved' {
        processApproval(claim);
    }
    when 'Rejected' {
        processRejection(claim);
    }
    when null {
        claim.Status__c = 'Submitted';
    }
    when else {
        logUnexpectedStatus(claim);
    }
}
```

Three differences from Java worth knowing:

**No fall-through.** Each `when` block ends implicitly, and there is no `break`.

**Multiple values per `when`**, comma-separated.

**`when null` is a distinct case**, which is genuinely useful — in Java a null switch value throws.

Switching on an sObject type is the readable way to handle polymorphic records:

```java
switch on someRecord {
    when Warranty_Claim__c claim {
        // claim is typed here, no cast needed
        handleClaim(claim);
    }
    when Case c {
        handleCase(c);
    }
    when else {
        handleOther(someRecord);
    }
}
```

The variable is typed inside the block, which removes the cast that `instanceof` would require.

Switching on an enum is where `switch` earns its place, because the compiler warns on unhandled values. See [[09.9 - Enums and Constants]].

## Loops

```java
// Classic for
for (Integer i = 0; i < claims.size(); i++) { }

// Enhanced for — the default
for (Warranty_Claim__c claim : claims) { }

// While
while (iterator.hasNext()) { }

// Do-while
do { } while (condition);
```

**Use the enhanced for loop unless you need the index.** Calling `size()` in the condition of a classic loop evaluates it every iteration, which is a small cost that compounds in a hot loop.

`break` exits the loop; `continue` skips to the next iteration. Both are worth using to reduce nesting:

```java
for (Warranty_Claim__c claim : claims) {
    if (claim.Status__c == 'Closed') {
        continue;
    }
    if (claim.Asset__c == null) {
        continue;
    }
    // the main path is now unindented and readable
    process(claim);
}
```

Early `continue` for the cases you do not handle, rather than wrapping the body in a conditional, keeps the important code at one level of indentation.

## The SOQL for loop

Two forms, and the difference matters at scale.

```java
// Record form: retrieves everything into memory first
for (Warranty_Claim__c claim : [SELECT Id, Status__c FROM Warranty_Claim__c]) {
    // heap holds all records at once
}

// List form: retrieves 200 at a time
for (List<Warranty_Claim__c> chunk : [SELECT Id, Status__c FROM Warranty_Claim__c]) {
    for (Warranty_Claim__c claim : chunk) {
        claim.Status__c = 'Under Review';
    }
    update chunk;
}
```

**The list form keeps heap bounded**, because only 200 records exist at any moment. This is the form to use for anything that might return many rows, and it also gives you a natural chunk to perform DML on — one update per 200 records rather than one per record.

Both forms remain bound by the 50,000-row transaction limit. Beyond that, Batch Apex. See [[12.4 - Batch Apex]].

## The rule that matters most

**Never put SOQL or DML inside a loop.**

```java
// Fails at 101 records
for (Warranty_Claim__c claim : claims) {
    Asset asset = [SELECT Id, Name FROM Asset WHERE Id = :claim.Asset__c];
    update claim;
}
```

Each iteration consumes one query and one DML statement. At 101 iterations the transaction dies, having already done 100 queries and roughly 100 updates that are then rolled back.

The correct structure — collect, query once, act once:

```java
Set<Id> assetIds = new Set<Id>();
for (Warranty_Claim__c claim : claims) {
    if (claim.Asset__c != null) {
        assetIds.add(claim.Asset__c);
    }
}

Map<Id, Asset> assetsById = new Map<Id, Asset>([
    SELECT Id, Name, SerialNumber FROM Asset WHERE Id IN :assetIds
]);

List<Warranty_Claim__c> toUpdate = new List<Warranty_Claim__c>();
for (Warranty_Claim__c claim : claims) {
    Asset asset = assetsById.get(claim.Asset__c);
    if (asset != null) {
        claim.Asset_Serial__c = asset.SerialNumber;
        toUpdate.add(claim);
    }
}

if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

This is the single most important structural pattern in Apex, covered fully in [[10.6 - Bulkification Patterns]]. Every experienced reviewer looks for it first.

The `if (!toUpdate.isEmpty())` guard matters: DML on an empty list is allowed but still counts as a DML statement, so guarding it conserves the budget in code paths that often find nothing.

## Nested loops

Nested loops over record collections are the second most common cause of CPU limit failures, and they contain no query so they pass a casual review.

```java
// O(n × m)
for (Account acc : accounts) {
    for (Contact con : contacts) {
        if (con.AccountId == acc.Id) { }
    }
}
```

Always resolve with a map. See [[09.3 - Collections - Lists, Sets and Maps]].

Nesting **is** acceptable when the inner collection is a subquery result belonging to that parent, because the total iterations equal the number of child records rather than parents times children:

```java
for (Asset asset : [
    SELECT Id, Name, (SELECT Id, Status__c FROM Warranty_Claims__r)
    FROM Asset WHERE Id IN :assetIds
]) {
    if (asset.Warranty_Claims__r == null) {
        continue;
    }
    for (Warranty_Claim__c claim : asset.Warranty_Claims__r) {
        // total iterations = total claims, not assets × claims
    }
}
```

The null guard on the child list is required — a subquery with no matches gives null, not an empty list.

## Loop-invariant work

Anything not depending on the loop variable should be hoisted out.

```java
// Describe call runs once per record
for (Warranty_Claim__c claim : claims) {
    if (Schema.sObjectType.Warranty_Claim__c.fields.Approved_Amount__c.isUpdateable()) {
        claim.Approved_Amount__c = amount;
    }
}

// Hoisted
Boolean canUpdate = Schema.sObjectType.Warranty_Claim__c.fields.Approved_Amount__c.isUpdateable();
for (Warranty_Claim__c claim : claims) {
    if (canUpdate) {
        claim.Approved_Amount__c = amount;
    }
}
```

Describe calls, `getGlobalDescribe()`, `Custom_Metadata__mdt.getAll()`, and date construction are the usual culprits. Describe calls in particular are expensive enough that repeating them 200 times is measurable.

## CPU cost

The 10-second synchronous CPU limit is consumed by computation, not by waiting. Queries and DML do not count toward it; loops, string manipulation, describe calls, and JSON serialization do.

The operations that cost most:

- Describe calls, particularly `getGlobalDescribe()`
- String concatenation in a loop — use a `List<String>` and `String.join()`
- JSON serialization and deserialization of large structures
- Sorting large collections
- Regular expressions on long strings
- Nested loops

```java
// Repeated concatenation creates a new String each time
String output = '';
for (Warranty_Claim__c claim : claims) {
    output += claim.Claim_Number__c + ', ';
}

// Joining once is dramatically cheaper
List<String> numbers = new List<String>();
for (Warranty_Claim__c claim : claims) {
    numbers.add(claim.Claim_Number__c);
}
String output = String.join(numbers, ', ');
```

See [[16.3 - CPU Time and Heap Size]].

## Practical guidance

**Always use braces.**

**Use the enhanced for loop** unless the index is needed.

**Use the list form of the SOQL for loop** for large result sets.

**Never query or perform DML inside a loop.**

**Never nest loops over record collections** — build a map.

**Guard DML with `isEmpty()`.**

**Hoist describe calls and other invariant work** out of loops.

**Use `String.join()`** rather than concatenating in a loop.

**Use `continue` early** to keep the main path unindented.
