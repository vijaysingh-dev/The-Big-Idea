# Reading Session: Redis Networking

#backend #reading #networking

> **In one line:** Redis is a single-threaded event loop serving a million operations a second, and reading its networking layer teaches you more about async I/O than any tutorial because there is no framework hiding it.

## The Path

### 1. The event loop — `src/ae.c`

```c
void aeMain(aeEventLoop *eventLoop) {
    while (!eventLoop->stop) {
        aeProcessEvents(eventLoop, AE_ALL_EVENTS|AE_CALL_BEFORE_SLEEP|AE_CALL_AFTER_SLEEP);
    }
}
```

**Read `aeProcessEvents` in full.** It is about 100 lines and it is a complete event loop:

```
1. Find the nearest timer
2. Call aeApiPoll (epoll_wait) with that as the timeout
3. For each ready fd, call its registered handler
4. Process expired timers
```

💡 **This is exactly what asyncio does**, minus coroutines. **Reading it makes the Python event loop stop being magic** — the same `epoll_wait` loop, the same handler dispatch, the same timer heap.

`src/ae_epoll.c` is the Linux backend. **`aeApiPoll` is a thin wrapper over `epoll_wait`** — about 40 lines, and it is where [[02.12 - Event Driven Servers]] becomes concrete.

⚠️ **Note `beforeSleep` in `server.c`.** Called every iteration before blocking — it flushes the AOF, handles expired keys, and processes pending replies. **This is where "work done between polls" lives**, and every event-loop system has an equivalent.

### 2. Accepting a connection — `src/networking.c`

```c
void acceptTcpHandler(aeEventLoop *el, int fd, void *privdata, int mask) {
    while (max--) {
        cfd = anetTcpAccept(server.neterr, fd, cip, sizeof(cip), &cport);
        if (cfd == ANET_ERR) break;
        acceptCommonHandler(connCreateAcceptedSocket(cfd, NULL), 0, cip);
    }
}
```

💡 **Note the loop with `max`.** It accepts up to 1,000 connections per event loop iteration — **accepting one at a time would starve everything else, and accepting unboundedly would too.** That bounded batch is a pattern worth stealing.

`createClient` sets the socket non-blocking, disables Nagle, and registers `readQueryFromClient` for readability ([[02.3 - TCP Connection Lifecycle]]).

### 3. Reading and parsing — `readQueryFromClient` → `processInputBuffer`

```c
nread = connRead(c->conn, c->querybuf+qblen, readlen);
```

⚠️ **A `read` can return a partial command.** The parser must handle "half of `SET key value` arrived" — and this is the detail every hand-rolled protocol implementation gets wrong.

```c
int processMultibulkBuffer(client *c) {
    if (c->multibulklen == 0) {
        newline = strchr(c->querybuf+c->qb_pos,'\r');
        if (newline == NULL) {
            if (sdslen(c->querybuf)-c->qb_pos > PROTO_INLINE_MAX_SIZE) {
                addReplyError(c,"Protocol error: too big mbulk count string");
                setProtocolError("too big mbulk count string",c);
            }
            return C_ERR;          // ← incomplete: return and wait for more
        }
    }
    ...
}
```

💡 **The state lives on the client struct (`multibulklen`, `bulklen`, `qb_pos`), not on a stack.** That is what makes a single thread able to parse 10,000 half-finished commands simultaneously — **and it is the same reason coroutines need their state heap-allocated.**

⚠️ **Note the size checks.** `PROTO_INLINE_MAX_SIZE` and the bulk length limits exist because **an unbounded parser is a memory exhaustion vector** ([[02.11 - Reading Real Traffic]]).

### 4. Dispatch — `src/server.c:processCommand`

```c
c->cmd = c->lastcmd = lookupCommand(c->argv, c->argc);
```

**Then a long sequence of checks** — authentication, ACLs, cluster redirection, memory limits, read-only replica, subscribe mode.

💡 **Read this function in full.** It is the complete list of reasons a command can be rejected, **and it is a good model for how to structure request validation: every check is explicit, ordered, and returns a specific error.**

```c
call(c, flags);
```

### 5. Execution — `src/t_string.c:setGenericCommand`

```c
void setGenericCommand(client *c, int flags, robj *key, robj *val, ...) {
    if ((flags & OBJ_SET_NX && lookupKeyWrite(c->db,key) != NULL) || ...) {
        addReply(c, abort_reply ? abort_reply : shared.null[c->resp]);
        return;
    }
    setKey(c,c->db,key,val,setkey_flags);
    server.dirty++;
    notifyKeyspaceEvent(NOTIFY_STRING,"set",key,c->db->id);
    addReply(c, ok_reply ? ok_reply : shared.ok);
}
```

💡 **This is the whole of `SET`, and it is about 40 lines.** The `NX` and `EX` handling you use for distributed locks is right here ([[07.4 - Distributed Locks Done Right]]) — **and its atomicity comes entirely from the fact that nothing else runs during this function.**

⚠️ **That is the single-threaded guarantee, made concrete.** No locks, no compare-and-swap, no memory barriers — **just "nothing interleaves".**

### 6. Replying — `addReply` and the output buffer

```c
void addReply(client *c, robj *obj) {
    if (prepareClientToWrite(c) != C_OK) return;
    if (_addReplyToBuffer(c,obj->ptr,sdslen(obj->ptr)) != C_OK)
        _addReplyProtoToList(c,obj->ptr,sdslen(obj->ptr));
}
```

💡 **Two tiers: a fixed 16KB static buffer, then a linked list of dynamic blocks.** The fast path avoids allocation entirely; the slow path handles large replies.

⚠️ **The reply is not written to the socket here.** The client is added to `server.clients_pending_write`, and **`handleClientsWithPendingWrites` in `beforeSleep` does the actual `write`.**

**Batching writes until the end of the event loop iteration is what lets Redis reply to many clients with few syscalls.**

### 7. Backpressure — `closeClientOnOutputBufferLimitReached`

```c
if (checkClientOutputBufferLimits(c)) {
    freeClient(c);          // or async close
}
```

```
client-output-buffer-limit pubsub 32mb 8mb 60
```

⚠️ **A slow consumer that cannot keep up is disconnected.** Redis chooses to drop the client rather than buffer unboundedly and run out of memory.

💡 **This is the backpressure decision from [[04.7 - Presence Fanout and Backpressure]], made by a production system.** There are only three options — block, drop, or grow — and Redis picks drop, with a configurable threshold. **Seeing that choice made explicitly is worth the whole session.**

## What to Take Away

### The event loop is not magic

⚠️ **After reading `ae.c`, asyncio should feel ordinary.** `epoll_wait` with a timeout, dispatch handlers, run timers, repeat. **Coroutines are a way of writing handlers, not a different execution model** ([[01.4 - Building an Event Loop From Scratch]]).

### Single-threaded is a design, not a limitation

💡 **Redis serves ~1M ops/second on one core because it does no locking, no context switching, and no cache-line bouncing.**

⚠️ **The cost: one slow command blocks everything.** `KEYS *` on a large keyspace, or a Lua script in a loop, stalls every client.

**This is exactly the blocking-call problem from [[01.6 - The Blocking Call Problem]]**, in C, with the same consequence — and it is why `SCAN` exists.

### Bounded everything

```
Accept:          up to 1000 per iteration
Read:            PROTO_IOBUF_LEN per read
Query buffer:    client-query-buffer-limit
Output buffer:   client-output-buffer-limit, then disconnect
Clients:         maxclients
Memory:          maxmemory, then eviction
```

💡 **Every resource has a limit and an action when the limit is hit.** That is the difference between a system that degrades and one that falls over ([[11.4 - Backpressure and Load Shedding]]).

**Audit your own service against this list.**

### Comments that explain why

```c
/* Note that we specifically do not want to reset the client here, because
 * ... */
```

💡 **Redis's comments consistently explain the non-obvious.** When you find one, it usually marks a bug that took someone a week to find — **and reading them is faster than rediscovering the bug.**

## In Production

### What this changes about your own code

| Redis does | You should |
|---|---|
| Bounds every buffer | Bound yours, with an explicit limit |
| Batches writes until end-of-loop | Batch where you can |
| Disconnects slow consumers | Decide your backpressure policy explicitly |
| Keeps parser state per connection | Never assume a complete message per read |
| Explicit, ordered validation | Structure request checks the same way |
| Comments the surprising parts | Do the same |

### The commands to be careful with

⚠️ **Now that you know it is single-threaded, this list makes sense:**

```
KEYS *              O(n), blocks everything     → use SCAN
SMEMBERS            on a large set              → SSCAN
HGETALL             on a large hash             → HSCAN
FLUSHALL            synchronous by default      → ASYNC
DEBUG SLEEP         blocks entirely
Lua scripts         run to completion, atomically
```

💡 **`SCAN` exists precisely because the event loop cannot be blocked.** It returns a cursor and does bounded work per call — **which is the general answer for any long operation in a single-threaded system.**

## Codebase

**Repo:** `redis/redis`

**Question to answer:** What happens between `SET key value` arriving on a socket and the `+OK` reply being written back?

**Read, in order:**

💡 **Read `beforeSleep` carefully.** It is where the work that is not request handling happens — AOF flushing, expiry sampling, pending writes — **and every event-loop system has an equivalent you should know about.**

## Exercise

**Drill 15.2 — Trace it, then build a smaller one**

```
drills/15-redis/
├── trace/{TRACE.md, gdb_session.md, surprises.md}
├── experiments/{blocking_command.py, output_buffer_limit.py,
│                partial_command.py, pipeline.py, RESULTS.md}
├── mini_redis/{loop.py, protocol.py, commands.py, buffers.py, tests/}
└── README.md
```

**Part 1 — Trace with a debugger.** Build Redis, attach `gdb`, and set breakpoints at each of the six stages.

**Send `SET foo bar` from `redis-cli` and step through.**

**Write `TRACE.md`** with the call stack, the boundaries, and where the reply is actually written.

⚠️ **Confirm that `addReply` does not write to the socket.** Set a breakpoint in `handleClientsWithPendingWrites` and observe when it fires relative to the command.

**Part 2 — Prove single-threadedness.** Two clients connected.

Run `DEBUG SLEEP 5` from one and a `GET` from the other. **Measure the second client's latency.**

Then `KEYS *` on a keyspace of 5 million keys, and **measure the p99 latency of concurrent normal commands.**

**Chart latency against keyspace size for `KEYS` versus `SCAN`.**

**Part 3 — Partial commands.** Connect with a raw socket and send `SET foo bar` **one byte at a time, with a 100ms delay between bytes.**

**Confirm Redis waits and executes correctly.**

Then send half a command and disconnect. **Confirm the partial state is cleaned up.**

Then exceed `proto-max-bulk-len` and **confirm the protocol error and disconnect.**

**Part 4 — Output buffer limits.** Set `client-output-buffer-limit normal 1mb 512kb 10`.

**Subscribe a client, then stop reading from its socket while publishing heavily.**

**Confirm the client is disconnected** and find the log line. Then measure how much data Redis buffered before giving up.

💡 **This is backpressure in a production system**, and observing it directly makes [[04.7 - Presence Fanout and Backpressure]] concrete.

**Part 5 — Pipelining.** Send 10,000 commands one at a time, then pipelined in one write.

**Measure total time, syscall count (`strace -c`), and throughput.**

**Explain the difference from what you read in `beforeSleep`** — the batching of pending writes is why pipelining is so effective.

**Part 6 — Build mini-Redis.** In Python, without a framework:

```
- An event loop using selectors (epoll)
- RESP protocol parsing with partial-read handling
- GET, SET, DEL, EXPIRE, INCR
- A fixed output buffer with overflow to a list
- Output buffer limits, and disconnect on breach
- Bounded accept per iteration
```

⚠️ **No `asyncio`.** Use `selectors` directly, so you write the loop yourself.

**Then run `redis-benchmark` against it** and compare throughput to real Redis. **Being 10–50× slower is expected; the point is that the protocol and the loop work.**

**Part 7 — Break your mini-Redis the same ways.** Partial commands, a slow consumer, an oversized bulk string, and a blocking command.

**Confirm your implementation handles each the way Redis does.** Where it does not, fix it.

**Part 8 — The takeaways.** Write `surprises.md`: three things that contradicted your model.

**Then audit one of your own services against Redis's bounded-everything list.** For each resource, state the limit and what happens when it is reached. **Fill in the gaps.**

**Done when:**
- Your trace is verified with a debugger at all six stages
- You confirmed `addReply` does not write to the socket
- Your `KEYS` versus `SCAN` chart shows the blocking cost
- A byte-at-a-time command executes correctly
- You observed a slow consumer being disconnected by the buffer limit
- Pipelining's syscall reduction is measured with `strace`
- mini-Redis passes `redis-benchmark` and handles all four failure cases
- Your own service is audited against the bounded-everything list
