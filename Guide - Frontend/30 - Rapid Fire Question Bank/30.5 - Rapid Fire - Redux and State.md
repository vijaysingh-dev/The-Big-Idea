# Rapid Fire - Redux and State

## Placement

**Where should state live?**
Classify first: server data belongs in a query cache; shareable state (filters, sort, pagination, tabs) belongs in the URL; ephemeral UI state belongs in `useState`; genuinely shared client state belongs in a store. Most applications need far less global state than they think. → [[20.1 - Where State Should Live]]

**What is the difference between server state and client state?**
Server state is a *cache* of something you do not own — it goes stale, needs revalidation, deduplication, retries and cancellation. Client state is owned by the app and changes only when the app changes it. → [[20.1 - Where State Should Live]]

**Why put filters in the URL?**
Refresh survival, shareable links, back-button support, and it removes an entire category of state synchronization. The test: should refreshing preserve this? → [[23.3 - Dynamic Routes and Params]]

**When is prop drilling actually a problem?**
Past about four or five levels, or when intermediate components take props purely to forward them. Two or three levels is fine and more traceable than context. Try composition — passing elements as props — before reaching for context. → [[16.3 - Components and Props]]

## Context

**Context vs Redux?**
Context is dependency injection with **no subscription granularity** — every consumer re-renders when the provider value changes, regardless of which part they read. A store gives selector-based subscriptions so only components reading changed data re-render. → [[20.2 - Context API and Its Limits]]

**Does `React.memo` stop context re-renders?**
No. Memo compares props, and context is not a prop. A memoized consumer still re-renders on every context value change. → [[20.2 - Context API and Its Limits]]

**Why memoize a context value?**
`<Ctx.Provider value={{ user, setUser }}>` creates a new object every render, so every consumer re-renders every time the provider does. Wrap it in `useMemo`. → [[17.9 - useContext]]

**How do you reduce context re-renders?**
Split contexts by change frequency, and separate state from dispatch — `dispatch` from `useReducer` is guaranteed stable, so components that only dispatch never re-render on state changes. → [[17.9 - useContext]]

**What is a good use of context?**
Values read widely and changing rarely: theme, locale, current user, feature flags, a router or query client instance, and component-scoped state in compound components. → [[20.2 - Context API and Its Limits]]

## Redux core

**What are the three Redux principles?**
A single source of truth, state is read-only (changed only by dispatching actions), and changes are made by pure reducers. → [[20.3 - Redux Core Concepts]]

**Why must reducers be pure?**
Determinism is what makes replay, time-travel debugging and safe middleware possible. It also means React can call an updater twice in Strict Mode without corrupting state. → [[20.3 - Redux Core Concepts]]

**Why immutable updates?**
`useSelector` and `React.memo` compare by reference. Mutating in place leaves the reference identical, so nothing re-renders. Structural sharing also preserves references for unchanged entities, keeping memoization working. → [[06.7 - Immutable Data Patterns]]

**How should actions be designed?**
As **events that happened**, not setters. `{ type: "checkout/submitted" }` rather than `{ type: "SET_LOADING", payload: true }`. Event-style actions keep transition logic in the reducer and let several reducers respond to one action. → [[20.3 - Redux Core Concepts]]

**Why does my selector re-render on every action?**
It returns a new reference each call — `state.todos.filter(...)` creates a new array. Use `createSelector` to memoize, or `shallowEqual`. → [[20.3 - Redux Core Concepts]]

**What is `createSelector`?**
Memoized selectors from Reselect. It recomputes only when its input selectors change, so the output reference stays stable. RTK 2 uses `weakMapMemoize` by default, which caches across argument combinations rather than only the most recent. → [[20.3 - Redux Core Concepts]]

## Redux Toolkit

**How does RTK simplify Redux?**
`createSlice` generates action types, action creators and the reducer from one definition. `configureStore` sets up DevTools, thunk middleware and development-mode immutability and serializability checks. Immer allows mutation-style writes. → [[20.4 - Redux Toolkit]]

**Why do RTK reducers look like they mutate?**
Immer wraps them and passes a `Proxy` draft. Writes are recorded and used to build a structurally-shared immutable result. Rule: either mutate the draft or return a new value, never both. → [[20.6 - Immer and Immutable Updates]]

**What is `createEntityAdapter`?**
Generated CRUD reducers and selectors over a normalized `{ ids, entities }` shape, with optional sorting maintained automatically. The default for any collection keyed by id. → [[20.4 - Redux Toolkit]]

**When would you use `createAsyncThunk`?**
Client-side async logic that is not a plain request — conditional dispatch, sequencing, reading full state. For server data, RTK Query removes the boilerplate entirely. → [[20.5 - Middleware and Thunks]]

**What is RTK Query?**
Redux's own data-fetching layer: caching, deduplication, background refetch and tag-based invalidation, generating hooks from endpoint definitions. If you already use Redux, this is the answer to "don't put server data in Redux". → [[20.4 - Redux Toolkit]]

## Middleware

**What is middleware?**
A pipeline every action passes through between `dispatch` and the reducer. Signature: `store => next => action`. It is where side effects and cross-cutting concerns live, since reducers must be pure. → [[20.5 - Middleware and Thunks]]

**What is a thunk?**
A function dispatched instead of an object. The thunk middleware — four lines — calls it with `dispatch` and `getState`. Everything thunks can do follows from that. → [[20.5 - Middleware and Thunks]]

**When would you use the listener middleware over a thunk?**
For **reactive** logic — responding to actions rather than being dispatched. It supports cancellation, debouncing, `takeLatest` behavior and state-diff predicates, which thunks cannot express. It is the modern replacement for most saga use cases. → [[20.5 - Middleware and Thunks]]

**When are sagas still justified?**
Genuinely complex orchestration — long-running background processes, multi-step flows with cancellation, WebSocket lifecycle. Their concurrency vocabulary (`race`, `fork`, `cancel`) has no simple equivalent. Otherwise the listener middleware is lighter. → [[20.5 - Middleware and Thunks]]

## Normalization

**What is state normalization?**
Storing each entity once keyed by id, referencing by id, with order kept in a separate array. Gives O(1) lookups, single-place updates, no duplication, and preserved references for unchanged entities. → [[20.7 - State Normalization]]

**Why does normalization help performance?**
A nested update creates new references all the way up the tree, so everything re-renders. A normalized update touches one entry at one level, leaving every other reference intact — so memoized components skip. → [[20.7 - State Normalization]]

**When should you *not* normalize?**
Small, flat or read-only data, and anything a query library already caches and invalidates. Normalize entities that are shared and editable. → [[20.7 - State Normalization]]

## Modern alternatives

**Why Zustand over Redux?**
Roughly 1KB, no provider, minimal boilerplate, selector-based subscriptions, and readable and writable outside React. Redux earns its place when you need middleware, time-travel DevTools, or enforced conventions across a large team. → [[20.8 - Zustand Jotai and Modern Alternatives]]

**What is Jotai's model?**
Bottom-up atoms rather than one store. Derived atoms form a dependency graph, so only what actually depends on a change recomputes — memoization is structural rather than manual. Suits fine-grained, highly derived state. → [[20.8 - Zustand Jotai and Modern Alternatives]]

**What do all modern stores have in common?**
They build on `useSyncExternalStore`, which is what makes them concurrent-safe by preventing tearing. → [[17.12 - Lesser Known Hooks]]

**Why has React not adopted signals?**
The React team's position is that fine-grained reactivity conflicts with concurrent rendering's ability to discard and restart renders, and that the React Compiler achieves comparable performance while keeping the simpler "re-render the component" model. → [[20.8 - Zustand Jotai and Modern Alternatives]]

## Server state

**Why not use `useEffect` for data fetching?**
It reimplements — usually badly — caching, deduplication, retries, cancellation, background refetch and race-condition handling. The naive version has at least four bugs. → [[24.6 - TanStack Query Fundamentals]]

**`staleTime` vs `gcTime`?**
`staleTime` is how long data is considered fresh, during which no refetch happens for any reason. `gcTime` is how long an **unused** entry stays in memory before eviction. Stale data is still served while revalidating. → [[24.7 - Caching Stale Time and Invalidation]]

**What does a query key do?**
It is both the cache identity — two components with the same key share one entry and one in-flight request — and the dependency array: when it changes, the query refetches. → [[24.6 - TanStack Query Fundamentals]]

**Invalidate or write to the cache directly?**
Invalidate by default — the server is the source of truth. Write directly only when the mutation response contains the complete new state, since server-computed fields otherwise drift. → [[24.7 - Caching Stale Time and Invalidation]]

**What is the first step of an optimistic update?**
`cancelQueries`. Without it, a background refetch already in flight can land after the optimistic write and silently revert it. Then snapshot, apply, roll back from the snapshot on error, and invalidate on settle. → [[24.8 - Optimistic Updates with TanStack Query]]
