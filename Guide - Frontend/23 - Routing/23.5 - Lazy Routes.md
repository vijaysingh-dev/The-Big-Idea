# Lazy Routes

Routes are the natural code-splitting boundary: a user landing on `/login` has no reason to download the admin dashboard. Route-level splitting typically removes 40–70% of the initial bundle with no per-component decisions ([[19.3 - Code Splitting and React.lazy]]).

## The data router way

```jsx
const router = createBrowserRouter([
  {
    path: "dashboard",
    lazy: async () => {
      const { Dashboard, dashboardLoader } = await import("./Dashboard");
      return { Component: Dashboard, loader: dashboardLoader };
    },
  },
]);
```

React Router's `lazy` property loads the **entire route definition** — component, loader, action and error element — in one chunk. That matters: with `React.lazy`, the loader must be defined eagerly in the route config, so its imports stay in the main bundle even though the component is split.

```jsx
// Splits the component but NOT the loader's dependencies
{
  path: "dashboard",
  element: <Suspense fallback={<Skeleton />}><LazyDashboard /></Suspense>,
  loader: dashboardLoader,     // this import is eager
}
```

The `lazy` property avoids that entirely, which is the main reason to use it over `React.lazy` in a data router.

A cleaner form when the module exports the right names:

```jsx
{ path: "dashboard", lazy: () => import("./routes/dashboard") }
```

with the module exporting `Component`, `loader`, `action` and `ErrorBoundary`.

## React.lazy in a non-data router

```jsx
const Dashboard = lazy(() => import("./Dashboard"));

<Route
  path="dashboard"
  element={
    <Suspense fallback={<PageSkeleton />}>
      <Dashboard />
    </Suspense>
  }
/>
```

A single Suspense boundary in the layout covers all child routes:

```jsx
function RootLayout() {
  return (
    <>
      <Header />
      <Suspense fallback={<PageSkeleton />}>
        <Outlet />
      </Suspense>
    </>
  );
}
```

Wrapping the `Outlet` rather than each route keeps the header and navigation visible during the load, which reads far better than a full-page spinner.

## Prefetching on intent

Splitting moves the delay from initial load to navigation. Prefetching recovers most of it:

```jsx
function PrefetchLink({ to, prefetch, children }) {
  return (
    <Link
      to={to}
      onMouseEnter={prefetch}
      onFocus={prefetch}
      onTouchStart={prefetch}
    >
      {children}
    </Link>
  );
}

<PrefetchLink to="/dashboard" prefetch={() => import("./Dashboard")}>
  Dashboard
</PrefetchLink>
```

Calling `import()` twice with the same specifier does not fetch twice — the module registry caches by resolved URL ([[08.2 - Dynamic Imports]]).

Hover-to-click is typically 100–300ms, which covers most chunk downloads on a reasonable connection. `onFocus` gives keyboard users the same benefit; `onTouchStart` fires before the click on mobile.

React Router v7 provides this declaratively:

```jsx
<Link to="/dashboard" prefetch="intent" />   // on hover/focus
<Link to="/dashboard" prefetch="render" />   // when the link renders
<Link to="/dashboard" prefetch="viewport" /> // when scrolled into view
```

`viewport` uses `IntersectionObserver` and is well suited to link-heavy pages ([[12.5 - Custom Events and Observer APIs]]).

Be selective: prefetching every link on a page with fifty links wastes bandwidth and competes with resources the user actually needs ([[29.2 - Prefetching and Preloading]]).

## Handling load failures

The most common cause is a deploy — an open tab references hashed filenames that no longer exist on the CDN ([[15.7 - HTTP Caching and CDNs]]).

```jsx
function lazyWithRetry(importFn, retries = 2) {
  return async () => {
    for (let i = 0; i <= retries; i++) {
      try {
        return await importFn();
      } catch (err) {
        if (i === retries) throw err;
        await new Promise(r => setTimeout(r, 400 * 2 ** i));
      }
    }
  };
}
```

And a global recovery for the stale-manifest case:

```js
window.addEventListener("vite:preloadError", (e) => {
  e.preventDefault();
  window.location.reload();
});
```

Without this, users who leave a tab open overnight see a blank screen on their next navigation. It does not appear in testing because deploys are rare in development, and it is one of the most common production issues in code-split SPAs.

Pair every lazy route with an `errorElement` so a failure shows a retry rather than a blank page ([[23.2 - React Router Setup and Nested Routes]]).

## What not to split

**The landing route.** Splitting the first thing the user sees adds a round trip to the critical path for no benefit.

**Tiny routes.** A 4KB chunk is not worth a request.

**Routes sharing most of their dependencies.** If three routes all import the same heavy chart library, splitting them produces three chunks that each pull in a shared chunk anyway — the win is smaller than expected.

Verify with the bundle analyzer rather than assuming; a single shared import can quietly pull a "lazy" dependency into the main bundle ([[19.7 - Bundle Analysis and Optimization]]).

## Avoiding layout shift

```jsx
<Suspense fallback={<div style={{ minHeight: "60vh" }}><PageSkeleton /></div>}>
```

A small spinner replaced by a full page of content is a large CLS penalty. Skeletons sized to approximate the real layout avoid it and read as faster ([[13.5 - Core Web Vitals]]).

## Transitions prevent fallback flashes

```jsx
startTransition(() => navigate("/dashboard"));
```

Without a transition, navigating to a lazy route immediately replaces the current page with the fallback. Inside a transition, React keeps the current page visible while the new one loads ([[22.4 - useTransition and startTransition]]).

React Router's data router does this internally for navigations, which is why data-router navigations feel smoother than manual `React.lazy` setups.

## Nested route splitting

```jsx
{
  path: "settings",
  lazy: () => import("./settings/layout"),
  children: [
    { index: true, lazy: () => import("./settings/general") },
    { path: "billing", lazy: () => import("./settings/billing") },
  ],
}
```

React Router loads only the chunks for the matched chain, in parallel. Navigating to `/settings/billing` fetches the layout and billing chunks simultaneously rather than sequentially — which a naive nested `React.lazy` setup would serialize.

## How senior engineers actually use this

**They split at the route level first** and stop there unless the analyzer shows a specific heavy dependency worth isolating.

**They use the router's `lazy` property** rather than `React.lazy` in a data router, so loaders are split too.

**They prefetch on hover and focus**, since splitting without prefetching just relocates the delay.

**They handle chunk-load failure globally** with reload-on-stale-manifest.

**They put the Suspense boundary around the `Outlet`**, keeping navigation visible during loads.

## Common pitfalls

- Splitting the initial route.
- Using `React.lazy` in a data router, leaving loader dependencies eager.
- No prefetching, so every navigation stalls.
- No error boundary, so a failed chunk renders a blank page.
- Stale chunk references after deploy.
- Undersized fallbacks causing layout shift.
- Over-splitting into many tiny chunks.
- A full-page spinner replacing the layout on every navigation.

## Interview angle

"How do you code-split a React application" should lead with routes as the natural boundary and the rough magnitude of the win. The details that mark experience are prefetching on hover to recover navigation latency, handling chunk-load failures after a deploy, and — in a data router — that the `lazy` route property splits the loader too, whereas `React.lazy` leaves loader dependencies in the main bundle.
