# Reactivity and Decorators

## Fields are reactive by default

Every field in a component is reactive. Assigning to one that the template uses triggers a rerender.

```javascript
export default class ClaimSummary extends LightningElement {
    claimNumber;        // reactive
    isLoading = false;  // reactive

    handleLoad() {
        this.isLoading = true;   // rerenders
    }
}
```

This was not always true. Early LWC required `@track` on every field you wanted reactive, and a great deal of code and documentation still shows it. **`@track` is no longer needed for primitive fields or for reassignment.**

## The reassignment rule

Reactivity is triggered by **assignment to the field**, not by mutation of what it holds.

```javascript
// Rerenders — the field is reassigned
this.claims = [...this.claims, newClaim];
this.filters = { ...this.filters, status: 'Approved' };

// Does NOT rerender — the field still points at the same object
this.claims.push(newClaim);
this.filters.status = 'Approved';
this.claim.Claim_Amount__c = 150000;
```

This is the single most common source of "my UI is not updating". The data changed; the field did not.

The fix is to create a new object or array:

```javascript
addClaim(newClaim) {
    this.claims = [...this.claims, newClaim];
}

updateFilter(key, value) {
    this.filters = { ...this.filters, [key]: value };
}

updateClaimAmount(claimId, amount) {
    // map produces a new array, and a new object for the changed row
    this.claims = this.claims.map((claim) =>
        claim.Id === claimId ? { ...claim, Claim_Amount__c: amount } : claim
    );
}
```

Treating component state as immutable — always producing new values rather than mutating — removes this whole class of bug.

## @track, and when it is still useful

`@track` makes **deep mutations** reactive, observing changes inside an object or array.

```javascript
import { LightningElement, track } from 'lwc';

export default class ClaimForm extends LightningElement {
    @track formState = {
        amount: null,
        description: '',
        parts: []
    };

    handleAmountChange(event) {
        // with @track, mutating a nested property does rerender
        this.formState.amount = event.target.value;
    }
}
```

Without `@track`, that assignment changes the data and does not rerender.

**When it earns its place:** a form with many fields where spreading the whole object on every keystroke is noisy.

**When to avoid it:** everywhere else. Deep observation costs performance, and immutable updates are clearer about what changed. The modern guidance is to prefer reassignment and reach for `@track` only when the object is genuinely deep and frequently mutated.

## @api — the public interface

`@api` exposes a property or method to the parent component.

```javascript
import { LightningElement, api } from 'lwc';

export default class ClaimRow extends LightningElement {
    @api claim;
    @api showActions = false;
    @api recordId;

    @api
    refresh() {
        this.loadData();
    }
}
```

```html
<c-claim-row claim={claim} show-actions record-id={recordId}></c-claim-row>
```

**Property names translate to kebab-case** in markup. `showActions` becomes `show-actions`, and a boolean attribute present with no value is `true`.

**Public properties are read-only from inside the component.** Assigning to `this.claim` in the child throws.

```javascript
@api claim;

connectedCallback() {
    this.claim.Status__c = 'Approved';   // mutating a public property — wrong
}
```

If a child needs to change something, it dispatches an event and the parent updates. Data flows down, events flow up. See [[14.7 - Child to Parent Communication and Events]].

## Getter and setter pairs

Reacting to a public property being set requires a getter and setter pair:

```javascript
_claimId;

@api
get claimId() {
    return this._claimId;
}

set claimId(value) {
    this._claimId = value;
    // the setter is where a property change triggers work
    if (value) {
        this.loadClaim(value);
    }
}
```

**`@api` goes on the getter only**, never on both.

The backing field conventionally has an underscore prefix.

The important caution: **a setter can fire before the component is connected**, so avoid doing anything requiring the DOM in it. Store the value and act in `connectedCallback` if the DOM is needed.

## @wire — reactive data

`@wire` connects a component to a data source that pushes updates.

```javascript
import { LightningElement, api, wire } from 'lwc';
import { getRecord } from 'lightning/uiRecordApi';
import CLAIM_AMOUNT from '@salesforce/schema/Warranty_Claim__c.Claim_Amount__c';
import CLAIM_STATUS from '@salesforce/schema/Warranty_Claim__c.Status__c';

const FIELDS = [CLAIM_AMOUNT, CLAIM_STATUS];

export default class ClaimSummary extends LightningElement {
    @api recordId;

    @wire(getRecord, { recordId: '$recordId', fields: FIELDS })
    claim;
}
```

**The `$` prefix makes a parameter reactive.** When `recordId` changes, the wire re-executes automatically. Without the `$`, the value is captured once and the wire never refreshes.

Forgetting the `$` is a common and quiet bug — the component works on first load and never updates.

## Wire to a property or a function

**To a property**, giving `{ data, error }`:

```javascript
@wire(getClaims, { accountId: '$accountId' })
claimResult;

get claims() {
    return this.claimResult.data ?? [];
}

get hasError() {
    return !!this.claimResult.error;
}
```

**To a function**, when the result needs processing:

```javascript
@wire(getClaims, { accountId: '$accountId' })
wiredClaims({ data, error }) {
    if (data) {
        // transforming in the wire handler keeps the getter cheap
        this.claims = data.map((claim) => ({
            ...claim,
            statusClass: claim.Status__c === 'Rejected' ? 'slds-theme_error' : ''
        }));
        this.error = undefined;
    } else if (error) {
        this.error = error;
        this.claims = [];
    }
}
```

The function form is preferable whenever the raw result needs shaping, because doing it in a getter recomputes on every rerender.

**Keep a reference to the wire result** if you need `refreshApex` later. See [[14.11 - refreshApex and Cache Invalidation]].

## Wire limitations

**Wires are read-only.** They fetch; they do not write.

**They fire on component initialization**, before `connectedCallback` completes, and cannot be triggered on demand.

**Both `data` and `error` are initially undefined**, so the template must handle the loading state:

```javascript
get isLoading() {
    return !this.claimResult.data && !this.claimResult.error;
}
```

**A wire cannot be conditional.** It runs whenever its reactive parameters have values. The usual way to defer it is to leave a parameter undefined until you want it to run:

```javascript
searchTerm;   // undefined until the user types

@wire(searchClaims, { term: '$searchTerm' })
results;
```

A wire with an undefined reactive parameter does not execute, which is the mechanism for "do not run until the user has entered something".

## Wire versus imperative

The decision covered fully in [[14.10 - Calling Apex - Wire vs Imperative]], summarized:

**Wire** for read-only data that should refresh when its inputs change, and where caching helps.

**Imperative** for anything triggered by a user action, anything that writes, and anything needing ordered execution.

## Static fields and shared state

A field declared outside the class is module-scoped and shared across every instance:

```javascript
// shared by every instance of this component on the page
let requestCount = 0;

export default class ClaimSummary extends LightningElement {
    connectedCallback() {
        requestCount++;
    }
}
```

Occasionally useful for a shared cache. Usually a bug waiting to happen, because two instances of the component interfere with each other.

## Getters and rerender cost

A getter used in the template is called on **every rerender**.

```javascript
// Recomputed on every rerender, including ones unrelated to claims
get sortedClaims() {
    return [...this.claims].sort((a, b) => b.Claim_Amount__c - a.Claim_Amount__c);
}
```

For a small list this is invisible. For a few hundred rows with a sort and a map, it is measurable — particularly in a console where the component renders on every tab switch.

Where a getter is expensive, compute once on data change instead:

```javascript
@wire(getClaims, { accountId: '$accountId' })
wiredClaims({ data }) {
    if (data) {
        // sorted once, when the data arrives, rather than on every rerender
        this.sortedClaims = [...data].sort((a, b) => b.Claim_Amount__c - a.Claim_Amount__c);
    }
}
```

See [[14.17 - Performance and Rendering]].

## Practical guidance

**Do not use `@track` for primitives or reassignment.** Fields are reactive already.

**Reassign, do not mutate.** Spread arrays and objects rather than pushing and setting.

**Use `$` on reactive wire parameters.** Forgetting it is silent.

**`@api` on the getter only** in a getter-setter pair.

**Never assign to a public property from inside the component.**

**Handle the loading state** — `data` and `error` are both undefined at first.

**Transform data in the wire handler**, not in a getter, when the transformation is not trivial.

**Leave a parameter undefined** to prevent a wire running before it should.
