# Delete, Undelete and the Recycle Bin

## Deletes are soft

A deleted record goes to the **Recycle Bin** rather than disappearing. `IsDeleted` is set to true, and the record is recoverable for 15 days before being purged.

```java
delete claims;
Database.delete(claims, false);
```

Three consequences that matter in code:

**Deleted records still count toward storage** until purged. Deleting a million rows does not free storage immediately.

**They remain queryable** with `ALL ROWS`:

```java
List<Warranty_Claim__c> deleted = [
    SELECT Id, Claim_Number__c, IsDeleted, LastModifiedDate
    FROM Warranty_Claim__c
    WHERE IsDeleted = true AND LastModifiedDate = LAST_N_DAYS:7
    ALL ROWS
];
```

`ALL ROWS` also returns archived activities, which is the only way to query old Tasks and Events past the archival threshold.

**The 15 days is a maximum, not a guarantee.** The bin has a capacity derived from your storage allocation, and when it overflows the oldest records are purged early. Relying on the Recycle Bin as a backup is a mistake for exactly this reason.

## Undelete

```java
List<Warranty_Claim__c> restorable = [
    SELECT Id FROM Warranty_Claim__c WHERE IsDeleted = true ALL ROWS
];
undelete restorable;
```

Undelete restores the record and most of its relationships, including cascade-deleted children. This makes it a genuine recovery mechanism after an accidental parent delete — provided you act within the retention window.

What does not always come back cleanly: manual shares, some sharing rows, and relationships to records that were themselves deleted and purged.

`Database.undelete(records, false)` gives the same partial-success behaviour as other operations.

## Cascade delete

Deleting a master-detail parent deletes its children, and the cascade can run three levels deep.

The behaviour that matters: **cascade deletes bypass the child's automation in important ways.** Validation rules on the child do not stop it, and the child's delete trigger behaviour is not what you would expect from a direct delete.

So a validation rule on `Claim_Part__c` saying "cannot delete an approved part" is defeated entirely by deleting the parent claim.

**Prevention belongs on the parent**, in a before-delete trigger:

```java
public with sharing class ClaimTriggerHandler {

    public static void preventDeletionOfSettledClaims(List<Warranty_Claim__c> claims) {
        Set<Id> claimIds = new Map<Id, Warranty_Claim__c>(claims).keySet();

        Set<Id> withPayments = new Set<Id>();
        for (Claim_Payment__c payment : [
            SELECT Warranty_Claim__c FROM Claim_Payment__c WHERE Warranty_Claim__c IN :claimIds
        ]) {
            withPayments.add(payment.Warranty_Claim__c);
        }

        for (Warranty_Claim__c claim : claims) {
            if (withPayments.contains(claim.Id)) {
                claim.addError('This claim has payments recorded and cannot be deleted. Cancel it instead.');
            }
        }
    }
}
```

`addError()` in a before-delete trigger blocks that record's deletion. With `Database.delete(records, false)` the others still delete; with a plain `delete` statement the whole operation rolls back.

See [[02.10 - Delete Behaviour - Cascade and Restrict]].

## What blocks a delete

Beyond your own logic, the platform refuses some deletions:

- A record referenced by a lookup marked "don't allow deletion"
- A record locked by an in-progress approval process
- A parent whose child deletion itself fails
- Records referenced by an active flow or process definition
- Some standard objects with related records, depending on configuration

The error messages frequently name an internal relationship rather than the actual blocker. When a delete fails inexplicably, check related lists, then approval status, then restricted lookups, in that order.

## Hard delete

`Database.emptyRecycleBin()` purges permanently and cannot be reversed.

```java
List<Warranty_Claim__c> purgeable = [
    SELECT Id FROM Warranty_Claim__c
    WHERE IsDeleted = true AND LastModifiedDate < LAST_N_DAYS:1
    ALL ROWS
    LIMIT 10000
];

if (!purgeable.isEmpty()) {
    Database.emptyRecycleBin(purgeable);
}
```

The legitimate uses: freeing storage during a large migration, and complying with a right-to-erasure request where the record must genuinely be gone.

The Bulk API also supports a **hard delete** operation that bypasses the bin entirely, which is substantially faster for large volumes and requires a specific user permission. See [[02.13 - Data Import and Export Tools]].

## Deleting at scale

Deletion is slower than insertion, because the platform maintains sharing rows, indexes, and the recycle bin.

A batch job for large cleanup, with the purge in the finish method:

```java
public with sharing class ClaimPurgeBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id FROM Warranty_Claim__c
            WHERE Status__c = 'Closed' AND Claim_Date__c < LAST_N_YEARS:7
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        Database.delete(scope, false);
        // purging inside execute keeps the bin from overflowing during a long-running job
        Database.emptyRecycleBin(scope);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

Purging inside `execute` rather than only in `finish` matters for a job deleting millions of rows — otherwise the bin overflows partway through and starts purging arbitrarily.

Deleting children before parents avoids cascade overhead, and reducing the batch scope size helps when the object has heavy automation.

## Archiving instead of deleting

For most business data, **deletion is the wrong answer.**

A status of `Cancelled` or `Archived` preserves the audit trail, keeps historical reporting consistent, and leaves the record available if a question comes up later. Actual deletion should be reserved for genuine mistakes and for data that must legally be removed.

Where volume is the driver rather than correctness, the pattern is to move records to a big object and then delete the originals — retaining the data at a fraction of the storage cost, with a component surfacing it in context so it does not feel like data loss. See [[23.4 - Archiving with Big Objects and External Storage]].

## Delete triggers

`before delete` and `after delete` both fire, and `Trigger.old` holds the records. `Trigger.new` is null.

**Before delete** is for prevention and for reading related data while it still exists.

**After delete** is for cleanup — recalculating a roll-up on a parent, logging, publishing an event.

```java
public with sharing class ClaimTriggerHandler {

    public static void run() {
        if (Trigger.isBefore && Trigger.isDelete) {
            ClaimService.preventDeletionOfSettledClaims(Trigger.old);
        }
        if (Trigger.isAfter && Trigger.isDelete) {
            ClaimRollupService.recalculate(assetIdsFrom(Trigger.old));
        }
        if (Trigger.isAfter && Trigger.isUndelete) {
            // undelete restores the record, so any derived aggregate must be recomputed
            ClaimRollupService.recalculate(assetIdsFrom(Trigger.new));
        }
    }
}
```

**The undelete event is the one most hand-rolled roll-ups forget.** A record restored from the bin must be counted again, and omitting the handler leaves the aggregate permanently wrong. See [[02.6 - Roll-Up Summary Fields]].

## Compliance deletion

A right-to-erasure request under privacy regulation requires more than a `delete` statement:

- The record must be hard-deleted, not left in the bin
- Field history and audit trail entries may retain values
- Feed items, email messages, and files reference the data separately
- Backups and sandboxes contain copies
- External systems that received the data need their own deletion

This is a design problem rather than a code problem, and it is worth establishing what the org's obligation actually is before building anything. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

## Practical guidance

**Prefer archiving to deletion** for business data.

**Guard deletion on the parent**, since cascade defeats child validation.

**Handle the undelete event** wherever you handle delete, particularly for roll-ups.

**Use `ALL ROWS`** to query deleted records, and remember they still consume storage.

**Purge inside `execute`** in a large deletion batch, not only in `finish`.

**Delete children before parents** to avoid cascade overhead.

**Do not treat the Recycle Bin as a backup.** The 15 days is a ceiling, not a guarantee.
