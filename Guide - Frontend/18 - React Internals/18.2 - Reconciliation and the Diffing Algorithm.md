# Reconciliation and the Diffing Algorithm

**Reconciliation** is the process of comparing the new element tree with the previous one and deciding what to change. The general problem — finding the minimum edit distance between two trees — is O(n³). React uses heuristics to make it **O(n)**.

## The two heuristics

**1. Different element types produce entirely different trees.**

If `type` changes, React does not attempt to diff further. It unmounts the old subtree and mounts a new one from scratch.

```jsx
{isEditing ? <Input value={v} /> : <Text value={v} />}
```

Switching between these destroys the old component instance, its state, its DOM node and its effects, then builds the new one.

```jsx
<div><Counter /></div>
// becomes
<span><Counter /></span>
```

Changing the wrapper from `div` to `span` destroys `Counter` and its state, even though `Counter` itself is unchanged. Type identity at the parent determines the fate of the whole subtree.

**2. Keys identify children across renders.**

Within a list, `key` tells React which new element corresponds to which old one, so elements can be **moved** rather than destroyed and recreated ([[16.6 - Lists and Keys]]).

Both heuristics are assumptions, not guarantees. They can produce more work than an optimal diff — but they run in linear time, which optimal diffing does not.

## Same type: update in place

When `type` matches, React keeps the existing fiber and DOM node, and updates only what changed:

```jsx
<div className="before" title="x" />
<div className="after"  title="x" />
```

React sets `className` and leaves `title` alone. The DOM node itself is reused, so focus, scroll position, selection and any imperatively-set state survive.

For a component type, React keeps the fiber — including its hooks and state — and re-runs the function with the new props.

## Position determines identity

Outside of keyed lists, React matches children by **position**:

```jsx
// Both branches render Counter at position 0 → same fiber, state preserved
{isFancy ? <Counter isFancy /> : <Counter />}
```

The counter's state survives the toggle, which surprises people expecting a "different" component. Adding distinct keys separates them:

```jsx
{isFancy ? <Counter key="fancy" isFancy /> : <Counter key="plain" />}
```

Conversely, rendering the same component at a *different* position gives it fresh state:

```jsx
{showA && <Panel />}
{showB && <Panel />}    // different position → different instance
```

## Conditional rendering and holes

```jsx
<div>
  {condition && <A />}
  <B />
</div>
```

When `condition` is false, React still reserves position 0 — the falsy value is a placeholder, not a removal. So `B` stays at position 1 in both cases and keeps its state.

This is why `&&` is safe for conditional children, while reordering array output is not.

## The list diffing algorithm

React's keyed list diff is a **single-pass heuristic**, not an optimal minimal-move algorithm:

1. Walk both lists from the start while keys match, updating in place.
2. On the first mismatch, build a map from key to old fiber for the remaining old children.
3. Walk the remaining new children, reusing fibers from the map and marking moves.
4. Delete any old fibers left in the map.

The consequence: React tracks a "last placed index" and marks a node for a move whenever its old index is less than that. A full reversal therefore produces many move operations, where an optimal algorithm would produce few. In practice this is rarely a bottleneck, but it explains benchmark differences against frameworks using longest-increasing-subsequence diffing (Vue 3, Inferno).

## Bailing out

React skips re-rendering a subtree in several cases:

**Identical element reference:**

```jsx
const child = <ExpensiveChild />;   // created once, e.g. passed as a prop
```

If the element object is `===` to the previous one, React knows nothing can have changed and skips the whole subtree. This is the mechanism behind elements-as-props ([[16.3 - Components and Props]]).

**`React.memo` with unchanged props** ([[19.2 - React.memo and Memoization Strategy]]).

**State set to the same value** — the `Object.is` bailout ([[17.2 - useState in Depth]]).

Note that a bailout at one level does not stop React from re-rendering elsewhere; it prunes a subtree from the work, nothing more.

## What "re-render" means

Re-rendering a component means calling its function and diffing the result. It does **not** mean touching the DOM.

```jsx
function Component({ count }) {
  return <div className="static">Hello</div>;   // same output every time
}
```

Re-rendering this a thousand times performs a thousand diffs and zero DOM mutations. This is why chasing every re-render is usually wasted effort — the expensive part is the DOM commit, and unchanged output produces none ([[19.1 - What Causes Re-renders]]).

The exception is when the render function itself is expensive — a large list, heavy computation — where the JS cost matters even with no DOM output.

## Practical consequences

**Do not change element types unnecessarily.** Wrapping a subtree conditionally in a different element destroys everything inside it:

```jsx
// Destroys the subtree whenever isModal flips
{isModal ? <Dialog><Form /></Dialog> : <div><Form /></div>}

// Preserves Form's state
<Wrapper isModal={isModal}><Form /></Wrapper>
```

**Do not define components inside components.** A new function identity every render means a new `type`, so React unmounts and remounts the entire subtree on every parent render — the cause of "my input loses focus while typing" ([[16.3 - Components and Props]]).

**Use `key` deliberately for resets**, since changing a key is exactly a type-change-like reset.

## Reconciliation is not the same as rendering

Worth separating: "render" is calling component functions to produce elements; "reconciliation" is diffing those elements against the previous tree and building the updated fiber tree; "commit" is applying the result to the DOM ([[18.4 - Render Phase vs Commit Phase]]).

All three are often loosely called "rendering", which makes performance discussions confusing.

## How senior engineers actually use this

**They reason about element type and position** when debugging unexpected state loss or unexpected state persistence — those are always reconciliation outcomes.

**They stabilize element identity** by passing elements as props where a subtree is expensive and independent.

**They never define components inline.**

**They distinguish re-render cost from commit cost** when profiling, since optimizing renders that produce no DOM changes rarely moves the metric.

## Common pitfalls

- Conditionally wrapping a subtree in different element types, destroying state.
- Component definitions nested inside components.
- Expecting a component at the same position to reset when a condition flips.
- Assuming every re-render causes DOM work.
- Index keys causing state to attach to the wrong list item.
- Optimizing re-renders without profiling which ones actually cost anything.

## Interview angle

"How does React's reconciliation algorithm work" wants the two heuristics — different type means full subtree replacement, keys identify children — and the reason for them: optimal tree diffing is O(n³), the heuristics make it O(n). The differentiating additions are that position determines identity outside keyed lists (so a component at the same position keeps its state across a conditional), and that a re-render does not imply DOM work. Both correct common misconceptions.
