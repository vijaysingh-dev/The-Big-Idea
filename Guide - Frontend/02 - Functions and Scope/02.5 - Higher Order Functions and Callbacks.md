# Higher Order Functions and Callbacks

A **higher-order function** (HOF) is one that takes a function as an argument, returns a function, or both. A **callback** is a function passed to another function to be invoked later. These are two views of the same first-class-functions capability.

## The two shapes

```js
// Takes a function
[1, 2, 3].map(n => n * 2);

// Returns a function
const withPrefix = prefix => msg => `${prefix}: ${msg}`;
const error = withPrefix("ERROR");
error("disk full"); // "ERROR: disk full"

// Both
function withLogging(fn) {
  return (...args) => {
    console.time(fn.name);
    const result = fn(...args);
    console.timeEnd(fn.name);
    return result;
  };
}
```

The third form — take a function, return an enhanced function — is the **decorator** pattern, and it is how retry logic, caching, logging, auth checks and instrumentation get layered onto existing functions without editing them.

## Synchronous vs asynchronous callbacks

The distinction matters more than it seems.

```js
// Synchronous — runs before map returns
[1, 2, 3].map(n => n * 2);

// Asynchronous — runs on a later tick
setTimeout(() => console.log("later"), 0);
element.addEventListener("click", handler);
```

A function that *sometimes* calls back synchronously and sometimes asynchronously is a known API hazard: consumers cannot reason about whether their state has been updated by the time the call returns. The rule, sometimes called "don't release Zalgo", is to pick one and be consistent — and if the callback is ever async, always make it async.

```js
// Bad: sync on cache hit, async on miss
function getUser(id, cb) {
  if (cache.has(id)) return cb(null, cache.get(id));
  fetchUser(id).then(u => cb(null, u), e => cb(e));
}

// Fixed: always async
function getUser(id, cb) {
  if (cache.has(id)) return queueMicrotask(() => cb(null, cache.get(id)));
  fetchUser(id).then(u => cb(null, u), e => cb(e));
}
```

Promises solve this for you — a `.then` reaction is *always* scheduled as a microtask, never called synchronously ([[04.2 - Promises from First Principles]]).

## Composition

```js
const pipe = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x);
const compose = (...fns) => x => fns.reduceRight((acc, fn) => fn(acc), x);

const slugify = pipe(
  s => s.trim(),
  s => s.toLowerCase(),
  s => s.replace(/[^a-z0-9]+/g, "-"),
  s => s.replace(/^-|-$/g, "")
);

slugify("  Hello World!  "); // "hello-world"
```

`pipe` reads left-to-right (data flows forward), `compose` right-to-left (mathematical convention). Both are just `reduce` over functions. Redux middleware is composed exactly this way ([[20.5 - Middleware and Thunks]]).

## Callbacks as strategy

Passing behavior instead of branching on flags produces far more flexible APIs:

```js
// Flag-based — grows a new parameter for every variation
function sortUsers(users, byName, descending, caseInsensitive) {}

// Strategy-based — one parameter, unlimited variations
function sortUsers(users, comparator) {
  return [...users].sort(comparator);
}

sortUsers(users, (a, b) => a.name.localeCompare(b.name));
```

The same idea underlies React's render props and the `children`-as-function pattern ([[22.7 - Render Props and HOCs]]).

## The error-first convention

Pre-promise Node APIs pass errors as the first argument:

```js
fs.readFile("config.json", (err, data) => {
  if (err) return handle(err);
  use(data);
});
```

You still meet this in Node libraries and older browser SDKs. `util.promisify` converts them; in the browser, wrap manually:

```js
const promisify = fn => (...args) =>
  new Promise((resolve, reject) =>
    fn(...args, (err, result) => (err ? reject(err) : resolve(result)))
  );
```

## Callback hell and why it happened

```js
getUser(id, (err, user) => {
  if (err) return handle(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handle(err);
    getDetails(orders[0].id, (err, details) => {
      if (err) return handle(err);
      render(details);
    });
  });
});
```

The nesting is cosmetic; the real problems are that error handling must be repeated at every level, there is no way to express "run these in parallel", and control flow cannot be composed. Promises fixed all three ([[04.1 - Callbacks and Callback Hell]]).

## Inversion of control

When you hand a callback to third-party code, you surrender control of *whether*, *when*, *how many times* and *with what* it is called. A buggy or malicious library can invoke your callback twice, never, or with wrong arguments. Promises constrain this — a promise settles once and only once — which is a genuine safety property, not just ergonomics.

## How senior engineers actually use this

**They build cross-cutting concerns as decorators.** `withRetry(withTimeout(withAuth(fetchUser)))` keeps retry, timeout and auth logic in one place each, testable in isolation, rather than scattered through every call site.

**They keep callbacks pure where possible.** A comparator, mapper or predicate that mutates its input or reaches outside its arguments makes the calling code unpredictable — this is why React requires render to be pure ([[16.5 - Rendering and Purity]]).

**They watch for callback identity in React.** A new inline function every render is a new prop value, which defeats `React.memo` on the child. The fix is `useCallback` — but only where the child is actually memoized, otherwise it costs more than it saves ([[17.7 - useCallback]]).

**They avoid deep `pipe` chains in application code.** Composition is excellent for data transforms and middleware; a fifteen-stage pipe in business logic is harder to debug than fifteen named steps, because stack traces show anonymous frames and you cannot set a breakpoint between stages.

## Common pitfalls

- APIs that call back synchronously in some paths and asynchronously in others.
- Forgetting that array HOFs pass `(element, index, array)`. `["1","2","3"].map(parseInt)` yields `[1, NaN, NaN]` because `parseInt` reads the index as its radix argument.
- Passing a method as a callback and losing `this`: `setTimeout(obj.method, 0)` unbinds it ([[02.8 - call apply and bind]]).
- Assuming a third-party callback runs exactly once.
- Creating decorated functions inside render, so every render produces a fresh wrapper with a fresh cache.

## Interview angle

You may be asked to implement `pipe`, `compose`, or a `withRetry` decorator, or to explain why callbacks led to promises. The strongest framing is that callbacks invert control — you hand execution to someone else — and that promises restore guarantees (settled once, always async, composable, errors propagate) while `async/await` restores readable sequential syntax on top.
