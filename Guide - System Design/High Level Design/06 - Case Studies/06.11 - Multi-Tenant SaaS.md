# Case Study: Multi-Tenant SaaS Platform

> **Revision tags:** #case-study #saas #multi-tenancy  
> **Related:** [[01.11 - Distributed Concepts]] | [[03.6 - Databases SQL and NoSQL]]

## Requirements Clarification

**Functional:**
- Organizations (tenants) sign up, create workspaces, invite members
- Each tenant's data is isolated — Tenant A cannot see Tenant B's data
- Feature availability varies by subscription tier (free, pro, enterprise)
- Enterprise tenants can have custom domains, SSO, and compliance settings
- Multi-region data residency (some enterprises require EU data to stay in EU)

**Non-functional:**
- Strict data isolation: a bug must never leak one tenant's data to another
- 99.9% availability (shared infrastructure for free/pro; higher for enterprise)
- Support 100K tenants, up to 10M users across all tenants
- Tenant onboarding: immediate (self-serve) or within hours (enterprise)
- Compliance: SOC 2, GDPR, HIPAA (for healthcare tenants)

**Out of scope:** Billing system internals, specific product features, ML features

## Multi-Tenancy Models

This is the core design decision. Three options:

### Model 1: Shared Database, Shared Schema

All tenants share one database. Every table has a `tenant_id` column.

```sql
CREATE TABLE documents (
    id          UUID PRIMARY KEY,
    tenant_id   UUID NOT NULL,    -- ← critical partition column
    title       TEXT,
    content     TEXT,
    created_by  BIGINT,
    created_at  TIMESTAMPTZ
);

-- Every query MUST include tenant_id filter
SELECT * FROM documents WHERE tenant_id = 'tenant-abc' AND id = 'doc-xyz';
```

**Pros:** Simple ops (one DB), easy to add tenants, efficient resource use  
**Cons:** Data isolation is purely logical (a missing `WHERE tenant_id =` leaks data); noisy neighbors; compliance complexity (GDPR deletion affects rows in shared tables)

**Good for:** Free/pro tiers, startups, teams with few enterprise customers

### Model 2: Shared Database, Separate Schemas

Each tenant gets their own PostgreSQL schema (namespace) within a shared database.

```sql
-- Tenant A
CREATE SCHEMA tenant_a;
CREATE TABLE tenant_a.documents (id UUID PRIMARY KEY, title TEXT, ...);

-- Tenant B
CREATE SCHEMA tenant_b;
CREATE TABLE tenant_b.documents (id UUID PRIMARY KEY, title TEXT, ...);

-- Query (set schema at connection time)
SET search_path = tenant_a;
SELECT * FROM documents WHERE id = 'doc-xyz';
```

**Pros:** Strong logical isolation (no `tenant_id` column needed), easier GDPR deletion (drop schema)  
**Cons:** Schema migrations must run N times (one per tenant); 100K tenants = 100K schemas (PostgreSQL supports this but it gets slow); connection pool fragmentation  
**Good for:** Hundreds to low-thousands of tenants

### Model 3: Separate Database per Tenant

Each tenant gets their own database instance.

```
Tenant A → dedicated PostgreSQL instance
Tenant B → dedicated PostgreSQL instance
Enterprise Tenant C → dedicated instance in EU region
```

**Pros:** Maximum isolation, dedicated resources, compliance-friendly, can run in different regions  
**Cons:** Expensive, complex ops (N databases to manage), slow onboarding (provision DB per tenant)  
**Good for:** Enterprise-only, high-compliance tenants (HIPAA, finance, government)

## Recommended: Tiered Hybrid Model

The production standard: combine models based on tier.

```
Free / Pro tenants:   Shared schema model (shared DB, tenant_id column)
                      → Simple, cheap, scales to 100K tenants

Enterprise tenants:   Dedicated schema or dedicated DB
                      → Isolation, compliance, SLA guarantees
                      → Premium pricing justifies the cost

Enterprise + region:  Dedicated DB in customer's required region (EU, APAC)
                      → Data residency compliance
```

**Tenant routing:** The application must route requests to the correct database.

```python
class TenantRouter:
    def get_connection(self, tenant_id: str) -> Connection:
        tenant = tenant_registry.get(tenant_id)

        if tenant.isolation_model == "shared":
            return shared_db_pool.get_connection()

        elif tenant.isolation_model == "dedicated_schema":
            conn = shared_db_pool.get_connection()
            conn.execute(f"SET search_path = {tenant.schema_name}")
            return conn

        elif tenant.isolation_model == "dedicated_db":
            return self._get_dedicated_pool(tenant.db_config)
```

## Data Isolation Enforcement

The most critical correctness requirement: no cross-tenant data leakage.

### Application-Level Enforcement

Every data access function must enforce tenant context:

```python
class DocumentRepository:
    def __init__(self, tenant_context: TenantContext):
        self.tenant_id = tenant_context.tenant_id

    def get_document(self, doc_id: str) -> Document:
        # tenant_id always injected — can't forget it
        result = db.query(
            "SELECT * FROM documents WHERE id = %s AND tenant_id = %s",
            [doc_id, self.tenant_id]
        )
        if not result:
            raise NotFoundError(f"Document {doc_id} not found")
        return Document.from_row(result)
```

Repository layer always injects `tenant_id`. Individual developers never write raw SQL with tenant filtering — the repository does it.

### Database-Level Enforcement (Row-Level Security)

PostgreSQL Row-Level Security (RLS) as a defense-in-depth layer:

```sql
-- Enable RLS on documents table
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- Policy: users can only see their tenant's rows
CREATE POLICY tenant_isolation ON documents
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Application sets the tenant context at connection time
SET app.current_tenant_id = 'tenant-abc-uuid';
-- Now all queries on 'documents' automatically filter by tenant_id
-- Even a "SELECT * FROM documents" only returns tenant-abc's rows
```

RLS at the DB layer means even a bug that omits the `tenant_id` filter is safe. Defense in depth.

## Tenant-Aware Service Architecture

```
[Request]
    │
    ▼
[API Gateway]
  1. Extract tenant from:
     - Subdomain: tenant-a.myapp.com
     - Custom domain: app.tenant-a.com (mapped in DNS)
     - JWT claim: { tenant_id: "abc" }

  2. Resolve tenant config from Tenant Registry
     { isolation_model, db_host, feature_flags, rate_limits }

  3. Inject TenantContext into request

[Service Layer]
  All repositories initialized with TenantContext
  All DB queries include tenant_id
  All cache keys prefixed: "tenant:{id}:..."
  All logs include tenant_id field
```

### Tenant Registry

Central store of tenant configuration:

```python
@dataclass
class TenantConfig:
    tenant_id: str
    name: str
    tier: str              # free, pro, enterprise
    isolation_model: str   # shared, dedicated_schema, dedicated_db
    db_host: Optional[str] # for dedicated DB
    schema_name: Optional[str]
    features: dict         # feature flags per tenant
    rate_limits: dict      # API rate limits by tier
    region: str            # data residency region
    custom_domain: Optional[str]
    sso_config: Optional[dict]
```

Stored in PostgreSQL, cached in Redis with 5-minute TTL. Every request resolves the tenant config from cache.

## Schema Migration Strategy

Migrating shared schema (100K tenants all in one table) is standard. Migrating per-tenant schemas (Model 2) requires running migrations N times.

**Shared schema:** One migration, run once. Standard.

**Per-tenant schema migration:**
```python
def run_migration_for_all_tenants(migration_sql: str):
    tenants = db.query("SELECT schema_name FROM tenants WHERE isolation_model = 'schema'")
    for tenant in tenants:
        db.execute(f"SET search_path = {tenant.schema_name}")
        db.execute(migration_sql)
        logger.info(f"Migrated {tenant.schema_name}")

# Run in batches with throttling to avoid DB overload
```

For dedicated DB tenants: run migration against each DB independently, possibly in parallel.

## Compliance Considerations

**GDPR "Right to Be Forgotten":**
```
Tenant deletes their account:
  - Shared schema: DELETE FROM all_tables WHERE tenant_id = X
                   OR anonymize PII fields
  - Dedicated schema: DROP SCHEMA tenant_x CASCADE
  - Dedicated DB: de-provision or wipe the database
```

**HIPAA (healthcare tenants):**
- Business Associate Agreement (BAA) required
- All data encrypted at rest and in transit
- Audit logs for all access to PHI (Protected Health Information)
- Dedicated infrastructure (no shared resources with non-HIPAA tenants)

**Audit logging (enterprise):**
```sql
CREATE TABLE audit_log (
    id          UUID PRIMARY KEY,
    tenant_id   UUID NOT NULL,
    user_id     BIGINT NOT NULL,
    action      VARCHAR(100),     -- DOCUMENT_READ, USER_INVITED, etc.
    resource_id UUID,
    resource_type VARCHAR(50),
    ip_address  INET,
    user_agent  TEXT,
    timestamp   TIMESTAMPTZ NOT NULL
);
```

All sensitive actions written to audit log. Immutable (no UPDATE/DELETE on audit_log).

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Tenant registry cache miss | Slower request (DB lookup) | Warm cache on startup; short TTL avoids stale config |
| Shared DB overloaded by one tenant | Noisy neighbor affects all | Per-tenant rate limiting; connection pool limits per tenant; move heavy tenants to dedicated |
| Schema migration failure partway | Some tenants on new schema, some on old | Track migration version per tenant; rollback-capable migrations |
| Dedicated DB tenant loses connectivity | That tenant down, others unaffected | Isolation benefit realized; standard DB HA (replicas, failover) |
| Cross-tenant data bug | Severe — data breach | RLS as second layer; automated tests that verify isolation |

## What This Design Demonstrates

- Three isolation models and when to use each
- Hybrid tiered approach (shared for most, dedicated for enterprise)
- Row-Level Security as defense-in-depth
- TenantContext injected at request entry, propagated through all layers
- Feature flag system based on subscription tier
- GDPR compliance differs by isolation model
