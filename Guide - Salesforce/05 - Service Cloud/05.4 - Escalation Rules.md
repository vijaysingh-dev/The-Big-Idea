# Escalation Rules

## What escalation is for

A case has been open too long, or a critical issue has had no response. Somebody senior needs to know before the customer complains.

An **escalation rule** monitors open cases and takes action when a time threshold passes: reassign the owner, notify someone, and set the `IsEscalated` flag.

## The structure

Like assignment and auto-response rules, one active escalation rule per object, containing ordered entries. Each entry has criteria and one or more **escalation actions**, each with its own age threshold.

```
Rule: Standard Case Escalation

Entry 1: Priority = "Critical" AND Status != "Closed"
  Action A: after 1 hour   → notify Support Manager, set IsEscalated
  Action B: after 4 hours  → reassign to Tier 2 queue, notify Service Director

Entry 2: Type = "Warranty Claim" AND Status = "Submitted"
  Action A: after 24 hours → notify Warranty Team Lead

Entry 3: Status != "Closed"
  Action A: after 72 hours → notify case owner's manager
```

Multiple actions on one entry, each with a different age, is how a staircase of escalation is built.

## How the age is measured

This is where most misconfiguration happens. Each entry specifies what the age is measured from:

- **Case creation time**
- **When the case was last modified**
- **When the case was last modified, only if the owner has not responded**

The third option is the useful one for response-time escalation, because a case being actively worked should not escalate.

**Business hours apply.** An escalation rule can be tied to a business hours record, so a case created at 5pm on Friday does not escalate over the weekend for a support team that works weekdays. Getting this wrong produces escalations firing at 3am and managers who stop reading the notifications.

## Business hours and holidays

`BusinessHours` is a standard object defining working hours per day and a time zone. Multiple records can exist — one per region, one per support tier — with one marked as the default.

`Holiday` records mark non-working days, optionally recurring annually, and are associated with business hours records.

Business hours matter well beyond escalation: entitlement milestones use them ([[05.5 - Entitlements, Milestones and SLAs]]), and any custom duration calculation should too.

Apex can use them directly, which is the correct way to calculate elapsed working time:

```java
public with sharing class BusinessHoursService {

    public static Long workingMillisecondsBetween(Id businessHoursId, Datetime start, Datetime finish) {
        return BusinessHours.diff(businessHoursId, start, finish);
    }

    public static Datetime addWorkingHours(Id businessHoursId, Datetime start, Integer hours) {
        return BusinessHours.add(businessHoursId, start, hours * 60L * 60L * 1000L);
    }

    public static Boolean isWithinBusinessHours(Id businessHoursId, Datetime moment) {
        return BusinessHours.isWithin(businessHoursId, moment);
    }
}
```

`BusinessHours.diff()` returns milliseconds of working time between two moments, excluding evenings, weekends, and holidays. Writing that calculation by hand is a well-trodden road to subtle bugs, particularly around daylight saving and holidays, so use the platform method.

## The limitation worth knowing

Escalation rules are a fixed feature with fixed capabilities. They can reassign, notify, and set `IsEscalated`. They cannot:

- Create a record
- Call an external system
- Post to Slack or Teams
- Apply logic beyond field criteria and age
- Escalate based on a related record's state

When the requirement exceeds that, the answer is a scheduled job or a time-based flow.

## Escalation in Apex

The pattern is a scheduled batch evaluating open cases against thresholds held in Custom Metadata:

```java
public with sharing class CaseEscalationBatch implements Database.Batchable<SObject>, Schedulable {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, CaseNumber, Subject, Priority, Status, OwnerId, CreatedDate,
                   Last_Agent_Response__c, IsEscalated, Escalation_Level__c,
                   Entitlement.BusinessHoursId, Account.Name
            FROM Case
            WHERE IsClosed = false AND Status != 'Awaiting Customer'
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Case> scope) {
        Map<String, Escalation_Threshold__mdt> thresholds = getThresholds();
        List<Case> toEscalate = new List<Case>();
        List<Escalation_Notification__e> events = new List<Escalation_Notification__e>();

        for (Case c : scope) {
            Escalation_Threshold__mdt threshold = thresholds.get(c.Priority);
            if (threshold == null) {
                continue;
            }

            Datetime measureFrom = c.Last_Agent_Response__c == null ? c.CreatedDate : c.Last_Agent_Response__c;
            Id businessHoursId = c.Entitlement.BusinessHoursId != null
                ? c.Entitlement.BusinessHoursId
                : defaultBusinessHoursId;

            Long elapsedMinutes = BusinessHours.diff(businessHoursId, measureFrom, Datetime.now()) / 60000;
            Integer level = levelFor(elapsedMinutes, threshold);

            if (level > (c.Escalation_Level__c == null ? 0 : c.Escalation_Level__c)) {
                toEscalate.add(new Case(
                    Id = c.Id,
                    IsEscalated = true,
                    Escalation_Level__c = level
                ));
                events.add(new Escalation_Notification__e(
                    Case_Id__c = c.Id,
                    Level__c = level,
                    Case_Number__c = c.CaseNumber
                ));
            }
        }

        Database.update(toEscalate, false);
        EventBus.publish(events);
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 200);
    }
}
```

Three design points in there.

**Comparing against a stored escalation level** makes the job idempotent. Running every fifteen minutes without it would re-escalate the same case repeatedly and flood the notification channel.

**Excluding Awaiting Customer** means the clock stops when the customer owes a reply, which is the whole reason that status exists ([[05.2 - Cases and the Case Lifecycle]]).

**Publishing a Platform Event rather than making a callout** keeps the Slack or Teams notification outside this transaction, with its own limits and its own retry behaviour. See [[12.8 - Platform Events]].

## Scheduling frequency

A scheduled Apex job can run at most hourly through the standard scheduler, which is often not responsive enough for a one-hour critical threshold.

Options for finer granularity:

**Schedule several jobs at offsets** — four schedules at 0, 15, 30, and 45 minutes past the hour. Crude and effective.

**A self-rescheduling Queueable chain** that runs, waits, and enqueues itself. More elegant, and it needs careful guarding against runaway chains.

**Time-based flow actions**, which schedule an action at a specific future time when a record meets criteria. Better suited to per-record timing than a polling job, and the natural declarative equivalent of the batch above.

**Entitlement milestones**, which are the platform's purpose-built answer and handle business hours, pausing, and completion natively. If the requirement is genuinely about response and resolution targets, milestones are usually the right tool rather than a custom escalation job. See [[05.5 - Entitlements, Milestones and SLAs]].

## Escalation as an organizational signal

Worth stating, because it shapes what to build.

Escalation is a symptom. A support desk where twenty percent of cases escalate does not have an escalation configuration problem; it has a capacity, skills, or process problem. The escalation data is valuable precisely because it points at that.

```sql
SELECT Type, Priority, Product_Line__c, COUNT(Id) escalated
FROM Case
WHERE IsEscalated = true AND CreatedDate = LAST_N_DAYS:90
GROUP BY Type, Priority, Product_Line__c
ORDER BY COUNT(Id) DESC
```

If one product line accounts for most escalations, the answer is a product fix or a training gap, not a routing change.

## Practical guidance

**Tie escalation to business hours.** Escalations firing overnight are ignored, and being ignored is the failure mode that matters.

**Stop the clock when waiting on the customer.** Otherwise the metric measures the customer's response time, not yours.

**Make escalation jobs idempotent.** Store the level reached and compare against it.

**Use platform events for outbound notification** rather than callouts inside the job.

**Prefer entitlement milestones for contractual response targets.** Escalation rules are for internal attention, milestones are for contractual obligations, and using one where the other belongs produces a system that satisfies neither.

**Report on escalation rate by category.** It is a diagnostic for the support operation, not just an alerting mechanism.
