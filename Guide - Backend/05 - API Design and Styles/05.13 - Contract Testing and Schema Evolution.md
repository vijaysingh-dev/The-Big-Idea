# Contract Testing and Schema Evolution

#backend #api-design #testing

> **In one line:** Integration tests tell you two services worked together once; contract tests tell you they will keep working after either one deploys — and the difference matters most when you have stopped watching.

---

## The Idea

```
Documents service:  renames `author_id` → `authorId`
Search service:     still reads `author_id`
```

Nothing catches this until production. Unit tests pass on both sides — **each mocks the other, and both mocks are now wrong.**

💡 **Mocks encode your *belief* about the other service, and beliefs go stale silently.** A test suite full of hand-written mocks gives you confidence that is entirely disconnected from reality.

| Approach | Catches it | Cost |
|---|---|---|
| End-to-end tests | Yes | Slow, flaky, needs every service running |
| **Schema diffing** | Yes, structurally | Cheap, but does not know who uses what |
| **Contract tests** | Yes, **and names the affected consumer** | Setup cost, then cheap |

---

## Schema Diffing

```bash
graphql-inspector diff schema-prod.graphql schema-new.graphql
buf breaking --against 'https://github.com/org/repo.git#branch=main'
oasdiff breaking openapi-prod.yaml openapi-new.yaml
```

```
✖ Field `Document.authorId` was removed
✖ Field `Document.status` changed type from `String` to `DocumentStatus`
✓ Field `Document.indexedAt` was added
```

**Wire it into CI against the deployed schema, not against `main`.**

⚠️ **Schema diffing tells you a change is *potentially* breaking. It cannot tell you whether anyone is affected.** Removing a field nobody uses is safe; removing one used by your biggest customer is not. **The diff looks identical.**

**That gap is what contract testing fills.**

## Consumer-Driven Contract Testing

```python
# In the CONSUMER's test suite
(pact.given("a document exists")
     .upon_receiving("a request for a document")
     .with_request("GET", "/documents/doc_42")
     .will_respond_with(200, body={"id": Like("doc_42"), "author_id": Like("usr_7")}))
```

```python
# In the PROVIDER's test suite — replays the consumer's expectations
verifier.verify_with_broker(provider="documents-service", broker_url=PACT_BROKER)
```

Two things happen with the pact file:

1. **The consumer tests against a mock built from the pact**, so the mock cannot drift — it *is* the contract
2. **The provider replays the pact against its real implementation**

💡 **If the documents service renames `author_id`, its own test suite fails, naming the search service.** That property is the whole value — the team making the change learns about the break in their own CI, before merging.

### Provider states

```python
@app.post("/_pact/setup")
async def setup_state(state: str):
    if state == "a document exists":
        await db.execute("INSERT INTO documents ...")
```

⚠️ **This is the main friction of Pact** — every state needs setup code, and states proliferate.

**Keep states few and generic.** "A document exists" is good; "a document exists with 3 annotations, a deleted author, and status INDEXED" is a state you will maintain forever. **Push specificity into the request, not the state.**

### Matchers, not values

```python
"id": Like("doc_42")          # any string
"items": EachLike({...})      # array of matching shape
"status": Term(r"^(PENDING|INDEXED|FAILED)$", "INDEXED")
```

⚠️ **Never assert exact values in a contract.** The contract is about *shape and type*, not data — asserting `"id": "doc_42"` makes the provider test depend on that exact row existing.

## The Pact Broker

```bash
pact-broker can-i-deploy \
  --pacticipant documents-service --version $GIT_SHA \
  --to-environment production
```

💡 **`can-i-deploy` is the feature that makes this operational rather than academic.** It answers: given what is currently in production, is this version safe to deploy? **That is the actual question, and no other testing approach answers it directly.**

⚠️ **It requires accurate deployment records.** If your pipeline does not record what is deployed where, the answer is meaningless. **Wiring `record-deployment` into CD is a prerequisite.**

## Compatibility Rules by Protocol

### Protobuf — the clearest

The wire format encodes **field numbers**, not names.

```protobuf
message Document {
  string id = 1;
  reserved 3;                    // was author_id, removed
  reserved "author_id";
  string author = 4;
}
```

| Change | Safe? |
|---|---|
| Adding a field with a new number | **Yes** |
| Renaming a field, keeping the number | **Yes on the wire** — breaks generated code |
| Removing a field | Yes, **if you reserve the number** |
| **Changing a field's number** | **No** |
| Adding an enum value | Yes on the wire — breaks exhaustive switches |

⚠️ **`reserved` is not optional.** Removing field 3 and later adding a different field with number 3 means old clients silently misinterpret it.

💡 **Protobuf's "rename is wire-safe" property is a trap in practice.** The wire is fine and every generated client stops compiling. **Treat renames as breaking for humans even though the bytes disagree.**

### GraphQL

| Change | Safe? |
|---|---|
| Adding a field | **Yes** |
| Removing a field | **No, but you can measure usage first** |
| `T` → `T!` (narrowing) | Yes |
| `T!` → `T` (widening) | No |
| Adding an enum value | **No** in practice |

💡 **GraphQL's field-usage measurability is its best evolution property** ([[05.4 - GraphQL - The Core Model]]). You can prove nobody uses a field before removing it.

### REST / JSON

⚠️ **"Adding a response field is safe" is only true if clients ignore unknown fields**, and it is a contract term you must state explicitly ([[05.1 - REST Done Properly]]). **Some client generators produce strict validators by default.**

**Keep a strict client in your test suite** that fails on unknown fields, so you know which assumptions hold.

## In Production

### The layered testing strategy

```
Unit tests           fast, many, no network
Contract tests       per consumer-provider pair, no full environment
Integration tests    a few critical paths, real dependencies
E2E tests            a handful of smoke tests
```

💡 **Contract tests replace most integration tests, not unit tests.** Their value is running in each service's own CI without spinning up the world, while still catching cross-service breaks.

⚠️ **They do not catch semantic changes.** If the documents service starts returning sizes in kilobytes instead of bytes, the contract still passes — the shape is identical. **Contract tests verify shape, not meaning.** That gap needs a strongly-typed unit (`size_bytes`) or an integration test.

### Expand and contract

```
1. EXPAND    Add the new thing alongside the old. Both work
2. MIGRATE   Move consumers to the new one, one at a time
3. VERIFY    Confirm usage of the old one is zero
4. CONTRACT  Remove the old one
```

⚠️ **Step 3 requires measurement, and it is the step people skip.** Without per-field usage metrics you can never prove it is safe to remove, so you never do, and the deprecated field lives forever.

💡 **This is a genuine argument for GraphQL in a multi-team environment:** it is the only one of the three where field-level usage is directly observable.

### When contract testing is not worth it

| Situation | Verdict |
|---|---|
| One team owns both sides | Usually not worth the setup |
| **Public API with unknown consumers** | **Contract testing cannot help** — use versioning and deprecation |
| Two or three internal services | Marginal. Schema diffing may be enough |
| Many teams, many services | **Clearly worth it** |
| A monorepo with atomic deploys | Not needed — the compiler catches it |

⚠️ **In a monorepo where all services deploy together, contract testing solves a problem you do not have.** Its value is specifically in *independent deployability*.

**For Conduit at phase 4 with one developer, schema diffing in CI is proportionate and Pact is not. Say so.**

## Codebase

**Repo:** `pact-foundation/pact-python`, `bufbuild/buf`, `kamilkisiela/graphql-inspector`

**Question to answer:** How does Pact verification work on the provider side — what does it replay, and how does it handle state setup? Then: how does `buf` determine that a change is wire-breaking versus source-breaking, and why does it distinguish them?

**Read, in order:**

1. `pact-python/src/pact/verifier.py` — **what a verification run does**: fetch pacts, set up state, replay requests, compare with matchers
2. `pact-foundation/pact-specification` — the pact file format. **Short, and reading it makes the model concrete** — a pact is a list of request/response pairs with matching rules
3. `bufbuild/buf` — `private/bufpkg/bufcheck/bufbreaking/`. **The rule set is the answer**: `WIRE` catches what breaks deployed binaries, `WIRE_JSON` adds JSON names, `FILE` adds source compatibility
4. `graphql-inspector` — `packages/core/src/diff/` — one rule per change type, classified as breaking, dangerous or safe
5. `kubernetes/kubernetes` — the API compatibility rules in `api-conventions.md`, and how they test against previous releases

💡 The `buf` distinction between wire-breaking and source-breaking is the sharpest treatment of compatibility anywhere. **A rename is wire-safe and source-breaking; changing a field number is both.** Having those as separate categories lets you make a deliberate choice — "we accept source breakage because we control all clients" is a valid position, and most tools do not let you express it.

**Size:** 1–2 sessions.

## Exercise

**Drill 5.13 — Break a contract, then make it impossible**

```
drills/05-contracts/
├── services/{documents/, search/, analytics/}
├── breaks/{rename.py, type_change.py, enum_add.py, tighten.py, semantic.py, FINDINGS.md}
├── diffing/{graphql_diff.sh, openapi_diff.sh, proto_diff.sh, ci.yaml}
├── pact/{consumer_tests.py, provider_verify.py, broker/, can_i_deploy.sh}
├── evolution/{expand_contract.py, usage_tracking.py}
└── README.md
```

**Part 1 — Three services, two consumers.** Documents (provider), search and analytics (consumers with different field needs). Hand-written mocks in each consumer's tests, as most codebases have.

**Part 2 — Break it five ways.** For each, record: did the provider's tests pass, did the consumers' tests pass, did it fail in production?

| Break | Expected |
|---|---|
| Rename `author_id` → `authorId` | All tests pass, production breaks |
| `size` int → string | Same |
| Add an enum value | Same |
| Tighten `title` max length | Same |
| **Change `size` from bytes to KB** | Same — **and this one is the interesting case** |

**All five should pass every test. That table is the motivation for everything that follows.**

**Part 3 — Schema diffing in CI.** Add diffing for all three protocols against the *deployed* schema.

Re-run the five breaks. **Four should be caught; the semantic change should not.** Write down what schema diffing cannot see, and what would catch it.

**Part 4 — Contract tests.** Pact for both consumers, with a broker.

Re-run the breaks. **Now the provider's own CI fails, naming the affected consumer.**

Then add a break affecting only analytics and confirm the failure identifies it specifically.

**Part 5 — `can-i-deploy`.** Wire deployment recording into your pipeline.

**The scenario that matters:** analytics deploys a version needing a new field; documents has not shipped it. **Confirm `can-i-deploy` blocks the analytics deploy.** Then ship the field and confirm it unblocks.

**This is the workflow contract testing exists for, and running it once makes the value obvious.**

**Part 6 — Expand and contract, fully.** Migrate `author_id: string` to `author: User` across all three services with zero downtime, in four commits.

**Between each, all services must work with any combination of old and new versions deployed.** Test all four combinations at each step.

Then implement usage tracking and **prove the old field's usage is zero before the contract step. Do not remove it on faith.**

**Part 7 — The proportionality question.** Measure the cost: lines of test code, CI time added, and time to add a new endpoint with contract tests versus without.

**Then write the ADR for Conduit.** Argue it honestly — the answer is probably "schema diffing yes, Pact no", and being able to say that with numbers is more valuable than adopting it reflexively.

**Done when:**
- All five breaks initially pass every test
- Schema diffing catches four, and you can name what it misses
- Provider CI fails on a break, naming the specific affected consumer
- `can-i-deploy` blocks a deploy that would break a consumer
- Your expand/contract migration works across all four version combinations
- The ADR reaches a proportionate conclusion with measured cost
