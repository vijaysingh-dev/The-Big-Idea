# Contributing to Open Source

#backend #open-source #career #git

> **In one line:** Reading production code teaches you how systems work. Getting a change merged into one teaches you how real teams work: reproducing bugs, writing the test first, keeping a diff small, and taking review well. Start with the projects you already read in this section.

---

## The Idea

Sections 01–16 had you **read** uvicorn, Starlette, Celery, Redis, asyncpg and others. The next step is to change one of them and get the change accepted by people who do not know you.

Why it is worth the effort for a backend engineer:

| You get | Because |
|---|---|
| **Deep knowledge of one tool** | You cannot fix a bug in Celery's retry logic without understanding it better than 99% of its users |
| **Real code review** | Maintainers review harder than most employers. You learn the standards of a widely used codebase. |
| **Public, verifiable proof of skill** | A merged PR in `encode/httpx` says more than any line on a résumé |
| **Practice at the hardest part of the job** | Working in an unfamiliar codebase, with incomplete docs, asynchronously, with strangers |

What it is **not**: a numbers game. Ten typo fixes are worth less than one well-reproduced bug fix with a regression test.

---

## Picking a Project

Pick something **you use and have read**. Your advantage is context.

| Good first targets (from this vault) | Why |
|---|---|
| `encode/httpx`, `encode/starlette`, `encode/uvicorn` | Medium-sized, readable, active maintainers, and you read them in [[16.3 - Reading Uvicorn and Starlette]] |
| `fastapi/fastapi`, `pydantic/pydantic` | Huge user base. Docs and tests are welcome. Core changes are hard to land. |
| `celery/celery`, `celery/kombu` | Many open bugs with reproductions. Your [[16.4 - Reading the Celery Worker Loop]] notes are directly useful. |
| `MagicStack/asyncpg`, `redis/redis-py`, `aio-libs/*` | Async client libraries: exactly the code you write daily |
| `open-telemetry/opentelemetry-python(-contrib)` | Large, well organised, and instrumentations for many libraries are always needed |
| `python/cpython` | Possible and rewarding, but slow. Start with docs or tests. The devguide is excellent. |

Check before you commit time:

- **Is it alive?** Recent merges and maintainer replies in the last month.
- **Is there a `CONTRIBUTING.md`?** Read it fully. It tells you the test command, the style tools, whether you need an issue first, and any CLA.
- **How are outside PRs treated?** Look at a few closed PRs from non-maintainers. Were they reviewed kindly and quickly, or left to rot?

## Finding Something to Work On

In order of value:

1. **A bug you hit yourself.** You already have the reproduction and the motivation. This is the best kind of first contribution.
2. **Issues labelled `bug` with a clear reproduction and no linked PR.** Comment first: "I'd like to work on this. My plan is X." Wait for a nod on anything non-trivial.
3. **`good first issue` / `help wanted` labels.** Often taken quickly. Check for existing PRs.
4. **Missing tests or docs** for behaviour you had to discover by reading the source. Maintainers love these and they merge fast.
5. **Type hints, deprecation warnings and CI failures on new Python versions.** Unglamorous, always needed.

⚠️ **Do not open large, unsolicited refactors or new features.** They are the most common reason first PRs are closed. Every line you add is a line someone must maintain forever. Propose in an issue first.

## The Workflow

```bash
# 1. Fork on GitHub, then:
gh repo fork encode/httpx --clone
cd httpx
git remote -v                          # origin = your fork, upstream = the project

# 2. Set up exactly as CONTRIBUTING.md says
scripts/install    # or: uv sync / pip install -e ".[dev]" / tox / nox
scripts/test       # run the full suite BEFORE changing anything; it must pass

# 3. Branch from up-to-date main
git fetch upstream
git switch -c fix-timeout-on-redirect upstream/main

# 4. Write a FAILING test that reproduces the bug
# 5. Fix it, with the smallest change that makes the test pass
# 6. Run tests, linters, type checkers locally
scripts/check

# 7. Commit with a clear message, push, open the PR
git commit -m "Respect read timeout when following redirects (#1234)"
git push -u origin fix-timeout-on-redirect
gh pr create --fill
```

### The test comes first

A bug report becomes a contribution when it becomes a **failing test**. It proves the bug exists, proves your fix works, and stops the bug from coming back. Many maintainers will merge a PR that adds only a failing test (marked `xfail`) because it makes the bug concrete.

### Keeping in sync

```bash
git fetch upstream
git rebase upstream/main        # replay your commits on the latest main
git push --force-with-lease     # safe force-push to your own PR branch
```

Never force-push to a branch other people are working on. Your own PR branch is fine, and `--force-with-lease` refuses if someone else pushed in the meantime.

## Writing a PR That Gets Merged

```markdown
## What
Fix `ReadTimeout` not being applied when following redirects.

## Why
Closes #1234. With `follow_redirects=True`, the second request used the
default timeout instead of the client's configured one.

## How
`_send_handling_redirects` built the new request without copying
`extensions["timeout"]`. It now does.

## Tests
- Added `test_redirect_preserves_timeout`, which fails on main and passes here.
- Full suite passes locally on 3.9–3.13.
```

| Do | Do not |
|---|---|
| One logical change per PR | Mix a fix, a refactor and a formatting pass |
| Keep the diff small; follow existing style exactly | Reformat files you did not need to touch |
| Link the issue; explain the *why* | Leave the description empty |
| Respond to every review comment, even with "done" | Argue style; the project's conventions win |
| Be patient, and ping politely after 1–2 weeks | Ping daily, or tag many maintainers |

💡 **Review is the lesson, not an obstacle.** When a maintainer says "this breaks for HTTP/2 because…", they just taught you something about the codebase it would have taken you a week to find. Write those comments down.

## Beyond Code

Contributions that are less visible but just as valuable, and good on-ramps:

- **Triage:** reproduce open bug reports and comment with minimal reproductions or "cannot reproduce on version X".
- **Docs:** fix what confused you. You are the target reader the maintainers can no longer imitate.
- **Answer questions** in Discussions, on Stack Overflow, or in the project's chat.
- **Review other PRs:** test them locally and report what you found.

## A Realistic Path

| Month | Goal |
|---|---|
| 1 | One docs or test PR merged in a project from this section |
| 2–3 | One bug fix with a regression test, in the same project. Familiarity compounds. |
| 4–6 | Become a regular: triage issues, review others' PRs, take on a `help wanted` item |
| 6+ | Own a small area (an instrumentation, a backend, a module), or build a small library of your own and maintain it properly: CI, releases, a changelog |

Consistency in **one** project beats one PR in each of ten.

## Codebase

**Repo:** the project you picked.

**Question to answer:** What does a PR need to pass before a maintainer even looks at it?

**Read, in order:**

1. `CONTRIBUTING.md`, plus the PR template under `.github/`
2. `.github/workflows/*.yml` — exactly what CI runs: test matrix, linters, type checks, coverage thresholds
3. `pyproject.toml` (or `setup.cfg`, `tox.ini`, `noxfile.py`) — the dev dependencies and tool configuration
4. The 10 most recently merged PRs from outside contributors — their size, their descriptions, and the review comments they got
5. The test directory for the module you want to touch — how its tests are structured and which fixtures exist

**Size:** 1 session before you write any code.

## Exercise

**Drill 16.7 — Ship one real contribution**

```
oss-log/
├── PROJECT.md          # which project, why, links to CONTRIBUTING and CI config
├── ISSUE.md            # the issue: reproduction script, versions, root-cause notes
├── repro.py            # minimal standalone reproduction
├── PR.md               # the PR description as submitted, plus a link
├── REVIEW.md           # every review comment and what you learned from it
└── NEXT.md             # the next issue you will take in the same project
```

1. Pick a project from this section. Read everything in the Codebase box.
2. Find a bug with a reproduction, or reproduce an open one. Write `repro.py`.
3. Write the failing test, fix it, pass CI locally, and open the PR.
4. Handle review to completion: merged, or closed with a reason you understand.

**Done when:** one PR is merged, and `REVIEW.md` lists at least three things you learned from review that you did not know before.
