# Locks and Synchronization

#backend #os #concurrency #locks #deadlock

> **In one line:** When two threads touch the same data, you need a rule for who goes first. Mutexes, semaphores and condition variables are those rules, futexes make them cheap, and deadlock is what happens when the rules form a circle.

---

## The Idea

A **race condition** happens when the result depends on the timing of threads you do not control.

```python
counter = 0

def work():
    global counter
    for _ in range(1_000_000):
        counter += 1      # LOAD counter, ADD 1, STORE counter: three steps
```

Two threads run `work()`. You expect 2,000,000. You sometimes get less. The interleaving that loses an update:

```
Thread A                 Thread B
LOAD counter (=5)
                         LOAD counter (=5)
ADD → 6
                         ADD → 6
STORE 6
                         STORE 6        ← A's increment is lost
```

The three steps need to happen as one indivisible unit. The span of code that must not interleave is a **critical section**, and a **lock** is how you make it indivisible.

⚠️ **The GIL does not save you.** CPython can switch threads between any two bytecodes, and `counter += 1` is several bytecodes. The GIL makes single bytecodes atomic, not your logic. Free-threaded Python (3.13t and later) removes even that. See [[01.2 - The GIL]].

## The Primitives

| Primitive | Rule | Python | Use it for |
|---|---|---|---|
| **Mutex / Lock** | One holder at a time | `threading.Lock` | Protect shared state |
| **Reentrant lock** | Same thread may acquire it again | `threading.RLock` | Recursive code that takes the same lock |
| **Semaphore** | Up to N holders | `threading.Semaphore(n)` | Limit concurrency: N DB connections, N outbound calls |
| **Condition variable** | Sleep until another thread says something changed | `threading.Condition` | Producer/consumer, "wait until the queue is non-empty" |
| **Event** | A one-bit flag threads can wait on | `threading.Event` | "Shutdown has started" |
| **Read-write lock** | Many readers or one writer | Not in stdlib | Read-heavy caches |
| **Atomic operations** | A single CPU instruction: compare-and-swap, fetch-and-add | Not exposed in pure Python | The building block under every lock |

The asyncio versions (`asyncio.Lock`, `asyncio.Semaphore`, `asyncio.Event`) have the same shapes but are **not thread-safe**. They coordinate coroutines on one loop, not threads. See [[01.11 - Backpressure Inside One Process]].

### Condition variables, done right

```python
import threading
from collections import deque

items = deque()
cond = threading.Condition()

def produce(x):
    with cond:
        items.append(x)
        cond.notify()

def consume():
    with cond:
        while not items:          # WHILE, not IF
            cond.wait()
        return items.popleft()
```

⚠️ **Always wait in a `while` loop.** A thread can wake up with nothing to do. Another consumer may have taken the item first, or the wakeup may be spurious. Re-check the condition after every wake. This is the most common condition-variable bug in every language. (`queue.Queue` does all of this for you. Use it.)

## Spinlocks vs Sleeping Locks

There are two ways to wait for a lock:

| | Spinlock | Sleeping lock (mutex) |
|---|---|---|
| **How it waits** | Loops on the CPU checking "is it free yet?" | Asks the kernel to put it to sleep until it is free |
| **Cost when free** | A few ns | A few ns |
| **Cost when contended** | Burns CPU while waiting | One or two syscalls, plus a context switch |
| **Good for** | Very short critical sections, inside the kernel | Everything in user space |

### Futex: why uncontended locks are free

Linux mutexes are built on the **futex** ("fast user-space mutex"):

1. Try to take the lock with one atomic compare-and-swap **in user space**. If it was free, you are done. No syscall.
2. Only if it was taken do you call `futex(FUTEX_WAIT)` and sleep in the kernel.
3. The unlocker calls `futex(FUTEX_WAKE)` only if someone is waiting.

So an uncontended lock costs about 20 ns. A contended one costs microseconds. When `strace -c` or `perf` shows lots of `futex` time, you are looking at **lock contention**: threads queuing on the same lock. In Python, the GIL itself is the usual suspect.

## Deadlock

A deadlock is a set of threads each waiting for a lock another one holds. Nobody can move.

```
Thread A holds L1, wants L2
Thread B holds L2, wants L1
→ both wait forever
```

Deadlock needs **all four** of these conditions (the Coffman conditions). Break any one and deadlock cannot happen.

| Condition | Meaning | How you break it |
|---|---|---|
| Mutual exclusion | Resources cannot be shared | Use lock-free or immutable data where you can |
| Hold and wait | Hold one lock while waiting for another | Take all locks at once, or release before waiting |
| No preemption | A lock cannot be taken away | Use `acquire(timeout=...)` and back off on failure |
| **Circular wait** | A cycle in the wait-for graph | **Always take locks in one global order.** This is the fix you will use 90% of the time |

```python
def transfer(a, b, amount):
    first, second = sorted([a, b], key=lambda acct: acct.id)   # global order
    with first.lock, second.lock:
        a.balance -= amount
        b.balance += amount
```

💡 **The same four conditions explain database deadlocks.** Two transactions update rows in opposite orders, and Postgres detects the cycle and kills one with `deadlock detected`. The fix is the same: update rows in a consistent order (sort by primary key). See [[07.8 - Locking and Deadlocks]]. It also explains distributed lock problems in [[08.4 - Distributed Locks Done Right]].

### Other ways threads get stuck

| Problem | What happens | Example |
|---|---|---|
| **Livelock** | Threads keep reacting to each other and never progress | Two retry loops backing off in lockstep. Add jitter. |
| **Starvation** | One thread never gets the lock | An unfair lock under heavy contention |
| **Priority inversion** | A low-priority thread holds a lock that a high-priority thread needs, while medium-priority work runs | The Mars Pathfinder resets in 1997 |
| **Fork while locked** | A child inherits a locked mutex whose owner thread does not exist in the child | Forking after starting threads. See [[01.3 - Threads Processes and Coroutines]] |

## Memory Visibility (The Part People Skip)

Modern CPUs and compilers reorder memory operations for speed. Without a lock or a memory barrier, one thread's write might not be visible to another thread when you expect.

Locks do two things: mutual exclusion **and** a memory barrier. Everything written before `release()` is visible to whoever does the next `acquire()`.

In Python you rarely have to think about this, because the GIL acts as a barrier. In Go, Rust, Java or C, and in free-threaded Python, you do. Rule: **if two threads touch the same data and one writes, use a lock or an atomic. "It is just a boolean flag" is not an exception.**

## In Production

| Symptom | Likely cause | How to confirm |
|---|---|---|
| Throughput flat as you add threads, CPU partly idle | Lock contention, often the GIL | `py-spy dump`, `perf top` showing `futex`, `strace -c -f` |
| Process alive, 0% CPU, not serving | Deadlock | `py-spy dump --pid` shows every thread's stack. Look for two threads in `acquire` |
| Child process hangs right after start | Fork while another thread held a lock (logging, DB driver) | Use the `forkserver` or `spawn` start method, or fork before starting threads |
| `deadlock detected` in Postgres logs | Inconsistent row update order | Sort updates by key |

💡 **`py-spy dump --pid <pid>` is the deadlock debugger for Python.** It prints every thread's current stack without stopping the process. Two threads, each sitting in `lock.acquire`, each holding what the other wants: that is your answer in one screen. See [[01.12 - Profiling and Debugging Async Services]].
