# Vector DB Internals: ANN, HNSW, IVF, PQ

## Why You Need ANN

Exact nearest-neighbor search (brute-force KNN) compares the query vector against every vector in the database:

```
Time = O(N × d)
N = 10 million vectors, d = 1536 dimensions
= 15.36 billion multiply-adds per query
= ~400ms on modern hardware
```

Unacceptable for real-time retrieval. ANN (Approximate Nearest Neighbor) indexes trade a small accuracy loss for orders-of-magnitude speed improvement.

---

## HNSW (Hierarchical Navigable Small World)

The dominant ANN algorithm. Used by Qdrant, Weaviate, Milvus, pgvector, and optionally Vespa.

### Core Idea

Builds a multi-layer graph where:

- **Bottom layer**: Contains all vectors; edges connect nearby vectors
- **Upper layers**: Progressively fewer vectors; longer "express lane" connections
- **Navigation**: Start at top layer, greedily descend to closer nodes, move down when local minimum found

```
Layer 2 (few nodes, long-range connections):
  A ─────────────────────── F

Layer 1 (more nodes):
  A ──── C ──── E ──── F

Layer 0 (all nodes, short-range connections):
  A─B─C─D─E─F─G─H
  
Query: find nearest to X
  Start at layer 2, navigate toward X
  Descend to layer 1, continue
  Descend to layer 0, fine-grained search
```

### HNSW Construction Parameters

```python
index = hnswlib.Index(space='cosine', dim=1536)
index.init_index(
    max_elements=1_000_000,
    ef_construction=200,   # Search width during construction; higher = better index, slower build
    M=16,                  # Max connections per node; higher = better recall, more memory
)
```

|Parameter|Effect on Recall|Effect on Memory|Effect on Build Time|
|---|---|---|---|
|`M` ↑|Better|Higher (2× M per node)|Slower|
|`ef_construction` ↑|Better (up to limit)|Same|Slower|

### HNSW Query Parameters

```python
# ef = search width at query time; higher = more accurate but slower
index.set_ef(50)  # ef must be >= k (number of results requested)
labels, distances = index.knn_query(query_vector, k=10)
```

`ef=50` vs `ef=200`: Recall goes from ~95% to ~99.5% at 4× latency cost.

### HNSW Characteristics

|Property|Value|
|---|---|
|Build complexity|O(N log N)|
|Query complexity|O(log N)|
|Recall (typical)|95–99.5%|
|Memory usage|~(M × 2 × 4 bytes × N) for graph|
|Supports deletion?|Yes (mark deleted, periodic cleanup)|
|Best for|In-memory indexes, moderate to large N|

## IVF (Inverted File Index)

Partitions the vector space into clusters. Search only explores the nearest clusters.

### How It Works

**Index build (offline)**:

1. Run K-means clustering on all vectors → K centroids
2. Assign each vector to its nearest centroid
3. Each centroid maintains an "inverted list" of nearby vectors

```
Centroid 1: [vec_12, vec_45, vec_89, ...]
Centroid 2: [vec_3, vec_77, vec_102, ...]
...
Centroid K: [vec_55, vec_200, ...]
```

**Query (online)**:

1. Find the `nprobe` centroids nearest to query
2. Linearly scan only the vectors in those centroids
3. Return top-K from scanned set

```python
# Faiss IVF
quantizer = faiss.IndexFlatL2(d)           # exact centroid search
index = faiss.IndexIVFFlat(quantizer, d, nlist=1000)  # nlist = number of centroids
index.train(training_vectors)              # K-means clustering
index.add(vectors)

index.nprobe = 10                          # search 10 of 1000 clusters
D, I = index.search(query, k=10)
```

### IVF Trade-offs

|Parameter|Recall|Speed|
|---|---|---|
|`nlist` (clusters) ↑|Better (finer partitions)|Worse build, same query|
|`nprobe` ↑|Better|Slower (more clusters scanned)|

**Rule of thumb**: `nlist` ≈ sqrt(N). Start with `nprobe` = 10-20% of `nlist`.

**Best for**: Very large datasets (100M+) where HNSW's memory overhead is prohibitive. IVF can be stored on disk with memory-mapped access.

## Product Quantization (PQ)

Compresses vectors to reduce memory usage at the cost of some accuracy. Often combined with IVF (→ IVF-PQ).

### How It Works

1. Split each vector into `m` equal sub-vectors
2. For each sub-vector space, train a codebook of 256 centroids (k-means)
3. Replace each sub-vector with the index of its nearest centroid (1 byte)

```
Original: [f32×1536] = 6144 bytes per vector
PQ compressed: [uint8×m] = m bytes per vector (typically m=96 → 96 bytes)
Compression ratio: 64× !
```

**Distance approximation**: Distances are computed using precomputed centroid-to-centroid distances — fast table lookups instead of float multiplications.

**Recall impact**: PQ reduces recall by ~5–10 percentage points. Usually acceptable given 64× memory reduction.

### IVF-PQ (Most Common in Faiss)

```python
m = 96  # sub-vectors (must divide d evenly: 1536/96=16)
index = faiss.IndexIVFPQ(quantizer, d, nlist=1000, m=m, nbits=8)
```

At 1 billion vectors:

- Without PQ: 6TB of RAM
- With IVF-PQ: ~100GB — fits on a large server

## ScaNN (Google)

Google's ANN library, optimized for high-recall at high-throughput. Uses anisotropic quantization rather than standard PQ — prioritizes preserving the direction of large components.

**When to consider**: When you need both high recall (>99%) and high QPS (>10K/sec). More complex to operate than HNSW.

---

## Comparison: HNSW vs IVF vs PQ

|Dimension|HNSW|IVF|IVF-PQ|
|---|---|---|---|
|Memory|High (graph overhead)|Medium|Low|
|Query speed|Fast (log N)|Moderate|Fast (approx)|
|Recall|Very high (99%+)|High with nprobe|Moderate (93–97%)|
|Build time|Slow|Moderate|Moderate|
|Supports updates|Yes|Yes (rebuild clusters)|Limited|
|Best for|≤100M vectors, accuracy-first|100M+ vectors|Billion-scale, memory-constrained|

**Production default (most RAG systems)**: HNSW with M=16, ef_construction=200, ef=100.

---

## Disk ANN

A variant enabling HNSW-like quality from an SSD-backed index. The HNSW graph is stored on disk; hot nodes cached in RAM. Enables billion-scale HNSW without proportional RAM.

Used by: Azure AI Search, some Qdrant configurations.
