# BM25 and Hybrid Search

## BM25: The Workhorse of Keyword Retrieval

BM25 (Best Match 25) is the dominant keyword retrieval algorithm. It's been the backbone of search engines for decades, and it remains highly competitive against dense retrieval for many query types.

Understanding BM25 makes you a better AI engineer — it tells you _exactly_ why a document did or didn't rank, which black-box dense retrieval can't.

---

## BM25 Internals

BM25 scores a document D for query Q by summing term scores across all query terms:

```
BM25(D, Q) = Σ IDF(qᵢ) × [f(qᵢ, D) × (k₁ + 1)] / [f(qᵢ, D) + k₁ × (1 - b + b × |D|/avgdl)]
```

Looks complex; break it into components:

### IDF (Inverse Document Frequency)

```
IDF(q) = log((N - n(q) + 0.5) / (n(q) + 0.5))
```

- `N` = total documents in corpus
- `n(q)` = documents containing term `q`

**Meaning**: Rare terms get high weight; common terms ("the", "is") get low weight. A query term that appears in 1 of 1000 documents is more informative than one that appears in 900 of 1000.

### TF with Saturation (k₁ term)

```
tf_component = f(q, D) × (k₁ + 1) / [f(q, D) + k₁ × ...]
```

- `f(q, D)` = frequency of term q in document D
- `k₁` ≈ 1.2–2.0 (typical default: 1.5)

**Meaning**: Term frequency matters, but with diminishing returns. Seeing "cat" 10 times vs 5 times doesn't double the relevance score. The `k₁` parameter controls this saturation.

### Document Length Normalization (b term)

```
length_norm = 1 - b + b × |D| / avgdl
```

- `|D|` = document length (tokens)
- `avgdl` = average document length across corpus
- `b` ≈ 0.75 (typical default)

**Meaning**: A document matching "cat" 5 times is more relevant if it's short (50 words) than if it's long (5000 words). Longer documents naturally have more term occurrences.

### Intuition Summary

BM25 = "How many query terms appear in this document, weighted by rarity of those terms, penalized for document verbosity, with diminishing returns on repetition."

## BM25 Implementation

In Python, via `rank-bm25`:

```python
from rank_bm25 import BM25Okapi

# Build index
corpus = [
    "The cat sat on the mat",
    "The dog played in the yard",
    "Cats and dogs are common pets",
]
tokenized_corpus = [doc.lower().split() for doc in corpus]
bm25 = BM25Okapi(tokenized_corpus)

# Query
query = "cat mat"
scores = bm25.get_scores(query.lower().split())
top_indices = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)
```

In production: use Elasticsearch, OpenSearch, or Vespa which implement BM25 at scale with inverted indexes.

## BM25 Failure Modes

1. **Vocabulary mismatch**: "automobile" query doesn't find "car" documents
2. **Stopwords**: High-frequency query terms ("how", "what", "is") dilute signal
3. **No phrase understanding**: "New York" treated as "New" OR "York"
4. **No semantic context**: "Python" (programming language) vs "Python" (snake) — no disambiguation

## Hybrid Search

Hybrid search combines dense (semantic) and sparse (BM25) retrieval to get the benefits of both.

### Architecture

```
Query
  ├──→ [BM25 Index]      → top-K sparse candidates (e.g., top-50)
  └──→ [Vector DB]       → top-K dense candidates (e.g., top-50)
              │
        [Score Fusion]   ← merge and re-score combined candidate set
              │
        top-K final results
```

### Reciprocal Rank Fusion (RRF)

The most common and robust fusion method. Doesn't require scores to be on the same scale — only ranks matter:

```
RRF_score(doc) = Σ_retriever  1 / (k + rank_in_retriever)
```

Where `k` is a constant (typically 60) that reduces the impact of top-ranked results and prevents any single retrieval system from dominating.

```python
def rrf_fusion(sparse_results, dense_results, k=60):
    scores = {}
    
    for rank, doc_id in enumerate(sparse_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    
    for rank, doc_id in enumerate(dense_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

RRF is robust because it doesn't require score normalization and handles the common case where BM25 and dense scores use incompatible scales.

### Weighted Linear Combination

Alternatively, normalize both score distributions and combine:

```
final_score = α × dense_score_normalized + (1-α) × bm25_score_normalized
```

Requires tuning `α` (typically 0.3–0.7 for dense-heavy). More fragile than RRF but allows explicit control of the balance.

## How Onyx Implements Hybrid Search

Onyx uses Vespa which natively supports hybrid search. The query specifies both a keyword and a vector component:

```
Vespa YQL:
select * from documents where
  (userQuery()) or            ← BM25 component
  ({targetHits: 100}nearestNeighbor(embedding, query_embedding))  ← dense component
```

Vespa then fuses the results internally using its native ranking framework. The fusion weights are configurable per deployment.

Key file: `backend/danswer/search/retrieval/search_runner.py`

## When Hybrid Wins vs Single-Mode

|Query type|BM25 alone|Dense alone|Hybrid|
|---|---|---|---|
|"error code E-0x4F2"|✅|❌|✅|
|"what causes inflation"|❌|✅|✅|
|"RFC 2616 HTTP spec"|✅|⚠️|✅|
|"explain recursion simply"|❌|✅|✅|
|Named person/company|✅|⚠️|✅|
|Long conceptual question|❌|✅|✅|

**Production rule**: Hybrid almost always beats either system alone. The marginal infra cost (running both indexes) is low. Default to hybrid.
