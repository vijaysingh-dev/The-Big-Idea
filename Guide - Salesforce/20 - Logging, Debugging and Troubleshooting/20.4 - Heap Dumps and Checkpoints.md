# Heap Dumps and Checkpoints

## The question logs cannot answer

```java
for (Warranty_Claim__c claim : claims) {
    Asset asset = assetsById.get(claim.Asset__c);
    claim.Region__c = asset.Account.BillingCountry;   // null pointer, sometimes
}
```

The log says a null pointer occurred at that line. It does not say **which entry in the map was missing**, or **what the map actually contained**.

A checkpoint captures the complete state at that line — every variable, every collection, with contents.

## Setting a checkpoint

**Developer Console → open the class → click the line number gutter.** A red dot appears.

Then run the code — through the UI, through Execute Anonymous, or through a test. The checkpoint fires the **first time** that line executes.

**Debug → View Checkpoints** opens the results.

```
Checkpoints
  ClaimService.cls, line 47, 12 Aug 2026 09:32:14
```

Double-clicking opens the heap dump.

## Reading a heap dump

Three panels.

**Symbols** — the variables in scope, with types and values.

```
this            ClaimService
claims          List<Warranty_Claim__c>    size: 200
assetsById      Map<Id,Asset>              size: 48
claim           Warranty_Claim__c
asset           Asset                      null
```

**`asset` is null and `assetsById` has 48 entries for 200 claims** — the map is missing parents. That is the answer, visible immediately.

**Extents** — every object on the heap grouped by type, with counts and total size. This is the memory view.

```
Type                        Count    Size
Warranty_Claim__c             200   184320
Asset                          48    36864
String                       1420    52108
Map<Id,Asset>                   1     4096
```

**Search** — find a specific value or reference across the dump.

Clicking any collection expands it to show its actual contents, which is what makes this different from anything a log provides.

## The constraints

```
Maximum 5 checkpoints per user
Each fires ONCE, on the first execution of that line
Results expire after 30 minutes
Only in the Developer Console — no VS Code equivalent
Only for Apex, not for flows
```

**Firing only once** is the constraint that shapes usage. A checkpoint inside a loop captures the first iteration, which is frequently not the failing one.

The workaround is a conditional wrapper:

```java
for (Warranty_Claim__c claim : claims) {
    Asset asset = assetsById.get(claim.Asset__c);

    if (asset == null) {
        // a checkpoint on the next line fires only for the failing case
        System.debug('Missing asset for claim ' + claim.Id);
    }

    claim.Region__c = asset?.Account?.BillingCountry;
}
```

Placing the checkpoint inside the `if` means it captures the state at the moment the problem occurs rather than at the first iteration.

## Checkpoint actions

A checkpoint can also **execute code** and **log a result** when it fires.

**Right-click the checkpoint → Checkpoint Actions:**

```
SOQL:        SELECT Id, AccountId FROM Asset WHERE Id = :claim.Asset__c
Apex:        System.debug('Map keys: ' + assetsById.keySet());
Heap Dump:   capture the full state
```

The SOQL action runs against the live database at the moment the checkpoint fires, which answers "does this record actually exist" without a second reproduction.

## Diagnosing heap exhaustion

The other main use, and the one with no alternative tool.

```
System.LimitException: Apex heap size too large: 6291456
```

The log says the limit was exceeded. It does not say **what was holding the memory**.

A checkpoint set just before the failure gives the Extents panel, and the answer is usually one of four things:

**A query returning too many wide rows.**

```
Type                    Count      Size
Warranty_Claim__c       18420   4915200
```

18,000 claims with long text areas. The fix is fewer fields, a `LIMIT`, or chunked processing.

**A static collection accumulating.**

```
Type                    Count      Size
Map<Id,Warranty_Claim__c>   1   2097152
```

A cache in a static, holding everything for the transaction's duration. In a batch job with `Database.Stateful`, this persists across chunks and grows until it fails. See [[12.4 - Batch Apex]].

**String concatenation in a loop.**

```
Type      Count      Size
String    94210   3145728
```

Ninety thousand String instances is `+=` in a loop — each iteration allocates a new one. `String.join` on a list allocates once. See [[16.3 - CPU Time and Heap Size]].

**Deserialized JSON.** A large payload exists twice — as the string and as the object graph.

## Reducing heap, once identified

**Select fewer fields.** The largest lever, and usually sufficient.

**Process in chunks** with the list form of the SOQL for loop:

```java
for (List<Warranty_Claim__c> chunk : [
    SELECT Id, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
]) {
    // only 200 records in memory at a time
    update chunk;
}
```

**Cap stateful collections** in batch jobs:

```java
if (errors.size() < 100) {
    errors.add(message);
}
```

**Release large references** when finished:

```java
List<Warranty_Claim__c> claims = loadClaims();
Map<Id, Decimal> totals = summarize(claims);
claims = null;
processTotals(totals);
```

Apex garbage collection makes this help less than it would elsewhere, and on a long batch chunk it is not nothing.

**Move to async** for 12 MB, or to Batch Apex where each chunk gets a fresh heap.

## Measuring without a dump

For a quick check where a full dump is unnecessary:

```java
System.debug('Heap: ' + Limits.getHeapSize() + ' of ' + Limits.getLimitHeapSize());
```

Bracketing sections narrows it down:

```java
Integer before = Limits.getHeapSize();
List<Warranty_Claim__c> claims = loadClaims();
System.debug('Load consumed ' + (Limits.getHeapSize() - before) + ' bytes');
```

That identifies the expensive section, and the dump identifies what within it.

## Checkpoints in a test

Checkpoints fire during test execution, which is often the most convenient way to trigger one.

```java
@IsTest
static void diagnoseTheMissingAssetMapping() {
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(assets, 200);

    Test.startTest();
    insert claims;   // the checkpoint in ClaimService fires here
    Test.stopTest();
}
```

Reproducible, isolated, and it does not require finding a user who can trigger the problem.

## When a checkpoint is the right tool

**Worth it when:**

- A variable is unexpectedly null and the log does not explain why
- A collection has the wrong contents or the wrong size
- Heap is exhausted and the cause is unclear
- A conditional takes an unexpected branch
- The state at a specific line is the question

**Not worth it when:**

- A `System.debug` would answer it — faster, and it works in production
- The problem is timing or ordering, which a dump does not show
- It is a flow, which checkpoints do not support
- The problem cannot be reproduced

**The practical default is `System.debug` first**, and a checkpoint when the debug output raises more questions than it answers.

## The Apex Replay Debugger, as an alternative

For stepping rather than snapshotting, VS Code's Replay Debugger is frequently better.

```
Command Palette → SFDX: Turn On Apex Debug Log for Replay Debugger
[reproduce the issue]
Command Palette → SFDX: Get Apex Debug Logs
Command Palette → SFDX: Launch Apex Replay Debugger with Current File
```

Breakpoints, step over and into, a call stack, and a variables panel — a real debugging experience against a downloaded log.

**Replay Debugger for following execution; checkpoints for inspecting memory.** They answer different questions, and the Replay Debugger is the more comfortable tool for most investigations.

Its limitation: it replays a log, so it shows only what the log captured. A variable not logged at the configured level is not visible, and raising the level risks truncation.

## Practical guidance

**Set the checkpoint inside a conditional** so it fires on the failing case, not the first iteration.

**Read the Symbols panel first**, then Extents for a memory question.

**Use checkpoint actions** to run a live query at the moment of failure.

**Trigger checkpoints from a test** for a reproducible, isolated capture.

**Try `System.debug` first** — it is faster and works in production.

**Use the Replay Debugger** for following execution.

**Remember the 30-minute expiry** and the five-checkpoint cap.
