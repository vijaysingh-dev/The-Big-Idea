# Automation Landscape and Tool Selection

## The question this section answers

Salesforce gives you many ways to make something happen when a record changes. Choosing badly produces an org where nobody can tell what runs when, and where a simple change requires archaeology.

Choosing well is one of the clearest signals of an experienced Salesforce engineer, and it is not "use the most powerful tool available".

## What is actually available in 2026

**Formula field** — a derived value, always current, no automation at all. See section 06.

**Roll-up summary** — an aggregate of child records, stored. See [[02.6 - Roll-Up Summary Fields]].

**Validation rule** — an invariant enforced at save. See [[06.5 - Validation Rules]].

**Flow** — the primary declarative automation tool, in several varieties. Record-triggered, screen, scheduled, autolaunched, platform event-triggered.

**Approval process** — routed approvals with record locking. See [[07.11 - Approval Processes]].

**Assignment, escalation and auto-response rules** — object-specific routing features on Lead and Case.

**Apex trigger** — code running in the save pipeline. Section 11.

**Asynchronous Apex** — Queueable, Batch, Scheduled, Platform Events. Section 12.

**Retired:** Workflow Rules and Process Builder. Both are end-of-life, cannot be created new, and existing ones should be migrated. See [[07.12 - Legacy Workflow and Process Builder Migration]].

## The decision sequence

Run these in order and stop at the first that fits.

**1. Can a formula field do it?**
A value derived from this record or a parent, needed for display or light filtering. No automation, no maintenance, always correct. The cheapest possible answer.

**2. Can a roll-up summary do it?**
An aggregate over a master-detail relationship. Stored, indexed, maintained by the platform.

**3. Can a validation rule do it?**
An invariant expressible in one expression.

**4. Can a record-triggered flow do it?**
Field updates, related record creation, simple conditional logic, notifications. Admin-maintainable, no test coverage required, visible in Setup.

**5. Does it need Apex?**
Complex logic, bulk processing across many records, callouts, recursion control, or anything needing real error handling and testability.

**6. Does it need to be asynchronous?**
Callouts, heavy processing, or work that must not block the user's save.

The instinct to correct: developers reach for step 5 too early, and administrators sometimes push step 4 further than it should go. Both produce orgs that are harder to maintain than necessary.

## Flow versus Apex, honestly

The comparison that matters most, stated without advocacy.

**Flow is better when:**

- The logic is simple enough to read on a canvas
- Administrators should own and change it
- No test coverage burden is desirable
- The change should be visible in Setup without reading code
- Speed of change matters more than precision

**Apex is better when:**

- The logic involves loops, complex branching, or aggregation
- Bulk behaviour must be precisely controlled
- Recursion must be prevented
- Errors need structured handling and logging
- The logic must be unit tested with real assertions
- It must be callable from several contexts
- Callouts are involved
- Performance at volume is a concern

The honest summary: **flow is faster to build and harder to reason about at scale; Apex is slower to build and far easier to test, debug, and control.**

The failure mode of flow-heavy orgs is a record save that runs eleven flows in an order nobody controls, where a change to one breaks another and there is no test suite to catch it. The failure mode of Apex-heavy orgs is that administrators cannot make a simple field-update change without a developer and a release.

## What actually goes wrong

**Mixing flows and triggers on the same object for overlapping work.** The order between a record-triggered flow and an Apex trigger is defined but not fully controllable, and debugging becomes guesswork. The rule most mature orgs adopt: **one object, one mechanism for a given concern.** Flows may handle notifications and simple field defaults; triggers handle the business logic. They do not both update the same field.

**Cascading automation.** Flow A updates Record B, whose flow updates Record C, whose flow updates Record A. This is not hypothetical; it is a common cause of `Apex CPU time limit exceeded` on records nobody touched directly.

**No inventory.** Nobody knows what runs on save. The first thing to do in an unfamiliar org is enumerate it:

```sql
SELECT Id, ApiName, Label, ProcessType, TriggerType, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerType != null
ORDER BY ApiName
```

Combined with the trigger list, that is the automation inventory for the org, and it takes one minute.

**Shared limits.** Flows, triggers, validation rules, roll-up recalculation, and installed managed packages all consume the same per-transaction budget. Perfectly written Apex can fail because a flow used 90 SOQL queries first. See [[16.1 - Why Governor Limits Exist]].

## A working policy

The convention that scales, worth writing down in an org:

**Formula and roll-up first**, for anything derived.

**Validation rules for invariants**, with a bypass mechanism.

**One record-triggered flow per object per timing** — one before-save, one after-save — using decision elements internally rather than several flows on the same object. This makes the execution order within the flow explicit and controllable.

**One Apex trigger per object**, routing to a handler, dispatching to services that take collections. See [[11.5 - Trigger Handler Pattern]].

**Ownership split by concern.** Flows own notifications, task creation, and simple field defaults. Apex owns cross-object business logic, anything bulk-sensitive, and anything with callouts.

**Everything in version control**, flows included. They are metadata, and a declarative change causes outages as readily as a code change. See [[21.7 - Git Branching Strategies for Salesforce]].

## The order everything runs in

Whichever tools you choose, they execute in a fixed sequence on every save: validation, before-save flows, before triggers, validation rules, save, after triggers, after-save flows, assignment rules, roll-ups, sharing recalculation, commit, post-commit.

Knowing that sequence is what makes automation debuggable. It is the single most important page on the platform, and it closes this section: [[07.13 - Order of Execution]].
