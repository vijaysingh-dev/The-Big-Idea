# Accessibility Fundamentals

Accessibility is not a feature layered on at the end. Most of it comes from using the right elements ([[09.1 - Semantic HTML and Document Structure]]); the rest is keyboard support, focus management, and communicating state changes.

## The accessibility tree

Browsers build a parallel tree alongside the DOM, containing each element's **role**, **name**, **state** and **properties**. Assistive technology reads this tree, not your CSS.

```
button "Submit"  focusable, pressed: false
textbox "Email"  required: true, invalid: true
```

Chrome DevTools' Accessibility pane shows it directly. Checking it is the fastest way to find a control with no accessible name or the wrong role — problems that are invisible in the DOM inspector.

## The four principles (POUR)

WCAG organizes requirements under four headings, and they are a useful mental checklist:

- **Perceivable** — content is available to sight, hearing or touch. Alt text, captions, contrast.
- **Operable** — everything works by keyboard, with enough time and no seizure triggers.
- **Understandable** — predictable behavior, clear labels, helpful errors.
- **Robust** — works with assistive technology, now and as it changes.

**WCAG 2.2 Level AA** is the practical target and the legal standard in most jurisdictions.

## Keyboard access

Every interactive element must be reachable and operable by keyboard. The test takes thirty seconds: unplug the mouse and try to complete a task.

```html
<button>Native — focusable, Enter and Space work</button>

<div tabindex="0" role="button">Requires manual key handling</div>
```

Rules for `tabindex`:

- **`tabindex="0"`** — insert into the natural tab order. For custom controls only.
- **`tabindex="-1"`** — focusable by script but not by Tab. For elements you focus programmatically, such as a modal container or an error summary.
- **`tabindex` above 0** — never. It overrides document order and creates an unmaintainable focus sequence.

Expected key behavior for common patterns:

| Component | Keys |
| --- | --- |
| Button | Enter, Space |
| Link | Enter only |
| Checkbox | Space |
| Radio group | Arrows move and select; Tab enters and exits the group |
| Tabs | Arrows between tabs, Tab moves out |
| Menu | Arrows, Escape closes, Home/End |
| Modal | Escape closes, focus trapped inside |
| Combobox | Arrows navigate, Enter selects, Escape closes |

The APG (ARIA Authoring Practices Guide) documents the full expected keyboard interaction for every widget pattern, and it is the reference to use rather than inventing behavior.

## Focus management

Focus must never be lost. Three situations require explicit handling:

**Opening a dialog** — move focus into it, trap it there, and return focus to the trigger on close.

```jsx
useEffect(() => {
  if (!isOpen) return;
  const previouslyFocused = document.activeElement;
  dialogRef.current?.focus();
  return () => previouslyFocused?.focus();
}, [isOpen]);
```

The native `<dialog>` element with `showModal()` does all of this — trapping, Escape handling, background inertness — which is a strong argument for using it instead of a custom modal.

**Route changes in an SPA** — a client-side navigation does not reset focus, so a screen reader user stays where they were while the page content changes entirely. Move focus to the main heading or the `<main>` element:

```jsx
useEffect(() => {
  mainRef.current?.focus();
}, [pathname]);
```

**Removing the focused element** — deleting a row while its delete button has focus sends focus to `<body>`. Move it deliberately to the next row or a nearby landmark first.

Never remove focus indicators:

```css
/* Never */
:focus { outline: none; }

/* Use this instead — shows for keyboard, not for mouse clicks */
:focus-visible { outline: 2px solid currentColor; outline-offset: 2px; }
```

## ARIA, used sparingly

The five rules of ARIA, compressed:

1. **Use a native element if one exists.** `<button>` over `role="button"`, always.
2. **Do not change native semantics** unless you must. `<h2 role="button">` is wrong; put a button inside the heading.
3. **All interactive ARIA must be keyboard operable.**
4. **Do not use `role="presentation"` or `aria-hidden="true"` on a focusable element** — it becomes invisible to screen readers but still reachable by Tab.
5. **All interactive elements must have an accessible name.**

The attributes that earn their place:

```html
<button aria-expanded="false" aria-controls="menu">Menu</button>
<input aria-invalid="true" aria-describedby="err">
<div role="status" aria-live="polite">3 results found</div>
<span aria-hidden="true">★</span>
<nav aria-label="Breadcrumb">
<button aria-pressed="true">Bold</button>
<div aria-busy="true">
```

`aria-label` overrides the visible text for screen readers, which creates a mismatch for voice-control users who say what they see. Prefer visible labels; when using `aria-label` on a control with visible text, the label should contain that text.

## Live regions

Content that changes without a page load needs announcing:

```html
<div role="status" aria-live="polite">Saved</div>
<div role="alert" aria-live="assertive">Payment failed</div>
```

- **`polite`** waits for a pause. Use for status updates, search result counts, autosave confirmations.
- **`assertive`** interrupts. Reserve for errors and time-critical information.

The container must exist in the DOM **before** the content changes. Rendering the whole live region conditionally often means nothing is announced, because the screen reader never observed a change within an existing region. Render an empty region and populate it.

## Colour and contrast

- **4.5:1** for normal text, **3:1** for large text (18pt, or 14pt bold) and for UI component boundaries.
- **Never convey information by colour alone.** A red border needs accompanying text; a status dot needs a label.
- Respect user preferences:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

Motion sensitivity is a real accessibility need, and this three-line rule covers most of it.

## Screen reader only content

```css
.sr-only {
  position: absolute;
  width: 1px; height: 1px;
  padding: 0; margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}
```

For skip links, icon-button labels, and additional context. Note that `display: none` and `visibility: hidden` remove content from the accessibility tree entirely — they hide it from *everyone*, which is sometimes what you want and often not.

## Testing

**Automated** — axe DevTools, Lighthouse, `eslint-plugin-jsx-a11y`. These catch roughly 30–40% of issues: missing alt, contrast, missing labels, invalid ARIA. Cheap and worth running in CI.

**Manual** — keyboard-only navigation, then a screen reader. VoiceOver on macOS (Cmd+F5) and NVDA on Windows are free. Twenty minutes with a screen reader teaches more than any amount of reading.

**Zoom to 200%** and check nothing is clipped or overlapping.

## How senior engineers actually use this

**They fix it at the component level.** Getting `Button`, `Modal`, `Input` and `Menu` right in a design system fixes accessibility across the whole application at once ([[28.10 - Design Systems and Component Libraries]]).

**They use a headless component library for complex widgets.** Comboboxes, date pickers, menus and tabs have long specifications in the APG, and Radix, React Aria or Headless UI have implemented them correctly. Rebuilding these from scratch is rarely justified.

**They run axe in CI** and keyboard-test new features before review.

**They treat it as a requirement, not a nice-to-have.** Accessibility is legally mandated in many markets, and retrofitting is far more expensive than building it in.

## Common pitfalls

- `outline: none` with no replacement.
- Clickable divs without keyboard support.
- Focus lost on route change or on removing the focused element.
- Live regions rendered conditionally, so nothing announces.
- `aria-hidden` on something focusable.
- Placeholder text as the only label.
- Icon-only buttons with no accessible name.
- Colour as the sole indicator of state.
- Positive `tabindex` values.

## Interview angle

"How do you make a web app accessible" is common and often answered with a shallow list. A strong answer is layered: semantic HTML first because it provides roles, names and keyboard behavior for free; then keyboard operability and focus management, which SPAs break by default; then ARIA only where no native element exists; then live regions for dynamic content; then automated plus manual testing, noting that automation catches well under half the issues. Mentioning that route changes require explicit focus movement is a detail that shows real SPA experience.
