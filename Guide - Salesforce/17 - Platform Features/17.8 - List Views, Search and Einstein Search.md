# List Views, Search and Einstein Search

## List views are underrated

A list view gives filtering, sorting, inline editing, mass actions, charts, and a Kanban board — with no code and no test coverage.

A great many custom components exist because nobody checked whether a list view would do.

```
Filters:        Status equals Submitted, Approved
                Claim Date equals LAST 90 DAYS
                Owner: My Claims / All Claims / a queue
Columns:        chosen per view
Sharing:        only me / all users / specific groups and roles
```

**Filter by owner** covers the "my records" case that people frequently build a component for. **Filter by a queue** gives a work list. **List view charts** give a summary without a report.

## Inline editing and mass actions

```
Inline edit           double-click a cell, edit, save several rows at once
Mass update           select rows, apply a field update
Mass quick actions    a custom quick action applied to selected rows
```

**Mass quick actions** are the mechanism for "approve twenty claims at once" without a custom component:

```
Setup → Object Manager → Warranty Claim → Buttons, Links and Actions
    → New Action → Action Type: LWC
    → add to the List View Button Layout
```

The component receives the selected record Ids and runs headlessly:

```javascript
import { LightningElement, api } from 'lwc';
import approveClaims from '@salesforce/apex/ClaimController.approveBulk';

export default class BulkApproveAction extends LightningElement {
    // populated by the platform for a list view action
    @api recordIds;

    @api
    async invoke() {
        await approveClaims({ claimIds: this.recordIds });
        this.dispatchEvent(new ShowToastEvent({
            title: `${this.recordIds.length} claims approved`,
            variant: 'success'
        }));
    }
}
```

`recordIds` is the list-view equivalent of `recordId` on a record page — named exactly, marked `@api`, and populated automatically. See [[14.2 - Component Structure and Metadata]].

## List views are filtered queries

Which means the same performance rules apply.

**A list view on a large object with a non-selective filter times out.** `Status != 'Closed'` on eight million claims scans the table.

The mitigations are the same: a date bound, a positive `IN` filter rather than `!=`, and an index on the filtered field. See [[16.9 - Skinny Tables and Custom Indexes]].

**The record count limit** on a list view means a view returning too many rows shows a truncated count rather than an exact one, which confuses users who use it as a metric. A report is the right tool for a count.

## List views in Apex and LWC

```java
List<ListView> views = [
    SELECT Id, Name, DeveloperName, SobjectType

```

```javascript
import { getListUi } from 'lightning/uiListApi';

@wire(getListUi, {
    objectApiName: WARRANTY_CLAIM_OBJECT,
    listViewApiName: 'Open_Claims',
    pageSize: 50

```

Navigating to a list view from a component:

```javascript
this[NavigationMixin.Navigate]({
    type: 'standard__objectPage',
    attributes: { objectApiName: 'Warranty_Claim__c', actionName: 'list' },
    state: { filterName: 'Open_Claims' }

```

`filterName` takes the list view's developer name. See [[14.14 - Navigation and NavigationMixin]].

## Search: how it works

Salesforce search is not SOQL. It runs against a **search index** built asynchronously as records are saved.

```
Record saved → indexed asynchronously → available to search
```

Two consequences:

**There is a delay.** A record created and immediately searched for may not appear. This is normal and it is the answer to "why can't I find the record I just created".

**Search finds different things than a query.** The index tokenizes text, handles stemming and synonyms, and ranks by relevance. A SOQL `LIKE` does none of that.

## What is searchable

Not every field. The index covers:

```
Text, Text Area, Long Text Area, Rich Text
Email, Phone, URL
Name and auto-number fields
Picklist values (searchable, though not always the primary path)
Some standard fields per object
```

**Not searchable:** numbers, dates, checkboxes, currency, and formula fields in most cases.

**Custom objects are only searchable if "Allow Search" is enabled** on the object — a checkbox that is off by default on some object creation paths, and the cause of "my custom object doesn't appear in search results".

## SOSL

The Apex interface to the search index.

```sql
FIND :searchTerm IN ALL FIELDS
RETURNING
    Warranty_Claim__c (Id, Claim_Number__c, Status__c WHERE Status__c != 'Closed' LIMIT 20),
    Asset (Id, Name, SerialNumber LIMIT 20),
    Account (Id, Name LIMIT 10)
```

**One SOSL query across several objects** beats several SOQL queries, both for limits and for relevance. See [[08.8 - SOSL and Full Text Search]].

```java
List<List<SObject>> results = [
    FIND :term IN NAME FIELDS
    RETURNING Warranty_Claim__c (Id, Claim_Number__c), Asset (Id, Name)
];

List<Warranty_Claim__c> claims = (List<Warranty_Claim__c>) results[0];
List<Asset> assets = (List<Asset>) results[1];
```

Results come back in the order the objects were listed, which is positional and easy to get wrong when editing the query later.

**Search groups** narrow the scope and improve performance:

```
IN ALL FIELDS      everything indexed
IN NAME FIELDS     name and auto-number only
IN EMAIL FIELDS
IN PHONE FIELDS
IN SIDEBAR FIELDS
```

`IN NAME FIELDS` is substantially faster than `IN ALL FIELDS` and is usually what a lookup or type-ahead needs.

## SOSL versus SOQL

| | SOSL | SOQL |
| --- | --- | --- |
| Purpose | Find records matching text | Retrieve records matching criteria |
| Objects | Several at once | One, plus relationships |
| Matching | Tokenized, stemmed, ranked | Exact, or `LIKE` patterns |
| Leading wildcard | Effectively supported | Cannot use an index |
| Limits | 20 queries, 2,000 rows | 100 queries, 50,000 rows |
| Index | Search index, async | Database index, immediate |
| Just-created records | May not appear | Always appear |

**Use SOSL when the user typed text** and you want the best matches. **Use SOQL when you know the criteria.**

The specific case where SOSL wins decisively: `WHERE Name LIKE '%press%'` cannot use an index and scans; `FIND {press} IN NAME FIELDS` uses the search index.

## Search behaviour worth knowing

**Wildcards:**

```
FIND {press*}      prefix match
FIND {*press}      supported, though slower
FIND {pr?ss}       single-character wildcard
```

**Operators:**

```
FIND {press AND bearing}
FIND {press OR pump}
FIND {"hydraulic press"}     exact phrase
```

**Stemming** means "running" matches "run" in supported languages. **Synonym groups** can be configured in Setup, so "machine" matches "equipment" if the org defines it.

**Search is scoped by sharing.** A user only sees records they can access, which is correct and means two users searching the same term get different results.

## Einstein Search

The current search experience, enabled by default in most orgs.

What it adds over classic search:

**Natural language queries.** "my open claims this month" is parsed into a filtered result set rather than treated as literal text.

**Personalized ranking** based on what the user has interacted with recently.

**Instant results** as the user types, before pressing enter.

**Recommended results** promoting the most likely record type for the query.

Most of it is automatic. What an administrator controls:

```
Setup → Search → Search Manager
    Searchable objects and their field order
    Search layouts per object
    Synonym groups
    Promoted search terms for Knowledge
```

**Search layouts determine which fields appear in results**, and getting them right is what makes search usable — a claim result showing only the auto-number is not identifiable, while one showing the machine serial and account name is.

## Improving findability

The practical levers, in order of impact.

**Set a meaningful Name field.** An object whose Name is an auto-number is unfindable by search unless another indexed text field carries the identity. A formula Name combining the account and machine is a common fix:

```
Name = Account__r.Name & " — " & Asset__r.SerialNumber
```

That is not possible on a standard Name field, so the pattern is an auto-number Name plus a searchable text field populated by a before trigger.

**Configure search layouts** so results are identifiable.

**Enable "Allow Search"** on custom objects.

**Add synonym groups** for domain vocabulary — "press" and "stamping machine" in the Northwind case.

**Keep indexed text fields populated.** A search index cannot find what is not there.

## Lookup search behaviour

A lookup field's search uses the same index, and its behaviour is configurable:

```
Setup → Object Manager → field → Lookup Filters
Search layouts → Lookup Dialogs, Lookup Phone Dialogs
```

**Lookup filters** restrict which records can be selected — an optional filter offers a default the user can clear, a required filter enforces it:

```
Field: Asset__c on Warranty_Claim__c
Filter: Asset.AccountId equals Warranty_Claim__c.Account__c
Required: yes
```

That prevents selecting a machine belonging to a different account, declaratively, with a clear error message. It is a validation rule that runs at selection time rather than at save, which is a better experience.

`lightning-record-picker` in a component honours these filters and adds its own. See [[14.13 - Base Components and lightning-datatable]].

## Practical guidance

**Check whether a list view solves it** before building a component.

**Use mass quick actions** for bulk operations on list views.

**Use SOSL when the user typed text**, SOQL when you know the criteria.

**Use `IN NAME FIELDS`** rather than `IN ALL FIELDS` where it suffices.

**Remember the indexing delay** — a just-created record may not be searchable.

**Enable "Allow Search"** on custom objects.

**Configure search layouts** so results are identifiable.

**Give records a meaningful, searchable identity**, not just an auto-number.

**Use lookup filters** to constrain selection at the point of choice.
