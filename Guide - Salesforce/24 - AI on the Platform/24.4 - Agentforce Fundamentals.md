# Agentforce Fundamentals

## What it is

An agent that receives a request in natural language, decides what to do, and does it — by calling actions you define.

The distinction from a chatbot: **a bot follows a decision tree you drew. An agent chooses an action based on the request.**

```
Bot:     "Press 1 for claim status, 2 for a new claim"
Agent:   "What's happening with the press claim from last week?"
             → recognizes the intent
             → calls Get Claim Status with the resolved claim
             → answers in context
```

## The building blocks

```
Agent          the assembly — its role, its topics, its instructions
Topic          a domain of capability, with its own scope and instructions
Action         something the agent can do
Instructions   natural language guidance, per topic
Grounding      the data available to it
```

**A topic is the unit of design.** An agent with one topic covering everything performs badly; an agent with well-scoped topics performs well, because the model has a smaller decision to make at each step.

## Topics

```
Topic: Warranty Claim Status

Classification description:
    Use this topic when the customer asks about the status, progress, or
    outcome of an existing warranty claim, or when they ask what happens next
    with a claim they have already submitted.

Scope:
    This topic can look up claims, report their status, and explain the
    approval process. It cannot create claims, change amounts, or make
    commitments about timing.

Instructions:
    Always confirm which machine the claim relates to before answering, since
    a customer may have several.
    State the current status factually. Do not estimate a resolution date.
    If the claim was rejected, explain the reason from the coverage data.
    If no claim is found, offer to help create one rather than saying no.

Actions:
    Get Claims For Contact
    Get Claim Detail
    Get Coverage For Asset
```

**The classification description is what the model uses to route a request to this topic.** It is the most consequential text in the configuration, and it should describe the situations rather than the capability.

```
Weak:    "Handles claim status."
Better:  "Use when the customer asks about the status, progress, or outcome
          of an existing claim, or what happens next with one they submitted."
```

**Scope constrains the model** — stating what the topic cannot do reduces the chance of it attempting something outside its actions.

**Instructions are behaviour**, and negative instructions work: "do not estimate a resolution date" is a guardrail that holds reasonably well.

## Actions

Three kinds, and the choice matters.

**Standard actions** ship with the platform — record lookup, record creation, knowledge search, case escalation.

**Flow actions** wrap an autolaunched flow. Admin-maintainable, and adequate for straightforward retrieval.

**Apex actions** wrap an invocable method. The right choice for anything with logic, bulk behaviour, or real security requirements.

```java
public with sharing class ClaimAgentActions {

    public class ClaimLookupRequest {
        @InvocableVariable(required=true
            label='Contact Id'
            description='The contact asking about their claims')
        public Id contactId;

        @InvocableVariable(
            label='Machine serial number'
            description='Optional. Narrows to claims for one machine.')
        public String serialNumber;
    }

    public class ClaimLookupResult {
        @InvocableVariable(description='A summary of the claims found')
        public String summary;

        @InvocableVariable(description='How many claims matched')
        public Integer claimCount;

        @InvocableVariable(description='True if the contact has no claims')
        public Boolean noClaimsFound;
    }

    @InvocableMethod(
        label='Get Claims For Contact'
        description='Returns open warranty claims for a contact, optionally '
                  + 'filtered to one machine by serial number. Use this when '
                  + 'a customer asks about their claims.'
    )
    public static List<ClaimLookupResult> getClaims(List<ClaimLookupRequest> requests) {
        List<ClaimLookupResult> results = new List<ClaimLookupResult>();

        for (ClaimLookupRequest request : requests) {
            // the contact Id comes from the agent's session context, and the
            // sharing model constrains what this returns regardless
            List<Warranty_Claim__c> claims = ClaimSelector.openForContact(
                request.contactId, request.serialNumber
            );

            ClaimLookupResult result = new ClaimLookupResult();
            result.claimCount = claims.size();
            result.noClaimsFound = claims.isEmpty();
            result.summary = summarizeForAgent(claims);
            results.add(result);
        }
        return results;
    }
}
```

**The `description` attributes are read by the model.** They are how it decides which action to call and what to pass — which makes them functional rather than documentation.

```
Weak:    @InvocableMethod(label='Get Claims')
Better:  @InvocableMethod(label='Get Claims For Contact'
             description='Returns open warranty claims for a contact, optionally
                        filtered to one machine by serial number. Use this when
                        a customer asks about their claims.')
```

**Describing when to use it** is what distinguishes an action the model calls correctly from one it calls at the wrong moment.

**Every `@InvocableVariable` needs a description too**, particularly optional ones — the model needs to know that omitting the serial number is acceptable.

## Formatting output for an agent

The action returns text the model incorporates into its reply, and how it is shaped matters.

```java
private static String summarizeForAgent(List<Warranty_Claim__c> claims) {
    if (claims.isEmpty()) {
        // explicit absence, so the model does not treat this as unavailable data
        return 'No open claims found for this contact.';
    }

    List<String> lines = new List<String>();
    for (Warranty_Claim__c claim : claims) {
        lines.add(String.format(
            'Claim {0} | Machine {1} | Status: {2} | Claimed: {3} | Approved: {4}',
            new List<Object>{
                claim.Claim_Number__c,
                claim.Asset__r.SerialNumber,
                claim.Status__c,
                claim.Claim_Amount__c?.format() ?? 'not stated',
                claim.Approved_Amount__c?.format() ?? 'not yet decided'
            }
        ));
    }
    return String.join(lines, '\n');
}
```

**`'not yet decided'` rather than an empty string** tells the model the absence is known, which stops it inventing a value.

**Labelled, one record per line, compact.** A JSON dump works and reads worse; a screen-formatted block wastes tokens.

## Security

**The agent runs as a user**, and that user's permissions and sharing apply.

**For an internal agent**, the running agent user. **For a customer-facing agent on an Experience Cloud site**, the site's guest or authenticated user.

**Every action must enforce its own security**, exactly as an `@AuraEnabled` method must:

```java
@InvocableMethod(label='Get Claim Detail')
public static List<ClaimDetailResult> getDetail(List<ClaimDetailRequest> requests) {
    List<ClaimDetailResult> results = new List<ClaimDetailResult>();

    for (ClaimDetailRequest request : requests) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c, Contact__c
            FROM Warranty_Claim__c
            WHERE Claim_Number__c = :request.claimNumber
            WITH USER_MODE
            LIMIT 1
        ];

        // a claim number is guessable, so ownership is verified rather than assumed
        if (claims.isEmpty() || claims[0].Contact__c != request.contactId) {
            results.add(ClaimDetailResult.notFound());
            continue;
        }

        results.add(ClaimDetailResult.from(claims[0]));
    }
    return results;
}
```

**A claim number is a guessable identifier.** An action that returns a claim by number, without verifying it belongs to the person asking, is an enumeration vulnerability reachable through a chat interface.

**Returning "not found" rather than "not permitted"** avoids confirming existence.

**The class declares `with sharing`, uses `WITH USER_MODE`, and verifies ownership** — the same three controls as any reachable endpoint. See [[22.5 - Secure Apex Coding and OWASP on Platform]].

## Read versus write actions

**Read actions are low risk.** Wrong output is a bad answer.

**Write actions are not.** An agent that creates a case, updates a record, or issues a refund can be wrong in ways that persist.

**The pattern for a write action:**

```java
@InvocableMethod(label='Submit Warranty Claim')
public static List<ClaimSubmissionResult> submit(List<ClaimSubmissionRequest> requests) {
    List<ClaimSubmissionResult> results = new List<ClaimSubmissionResult>();

    for (ClaimSubmissionRequest request : requests) {
        // validating in the action rather than trusting the agent's extraction
        ValidationOutcome outcome = ClaimValidationService.validate(request);

        if (!outcome.isValid) {
            results.add(ClaimSubmissionResult.rejected(outcome.reason));
            continue;
        }

        Warranty_Claim__c claim = ClaimSubmissionService.submit(request.toSubmission());
        results.add(ClaimSubmissionResult.created(claim.Claim_Number__c));
    }
    return results;
}
```

**Validate in the action.** The agent extracted the values from a conversation, and the extraction can be wrong — a serial number misheard, an amount misread.

**Confirm before writing**, for anything consequential. Agentforce supports a confirmation step, and using it for write actions is the default worth adopting.

**Return the outcome clearly**, so the agent can report success or explain the rejection accurately.

## Testing

**The Agent Builder preview** runs a conversation against the configured agent, showing which topic was selected and which actions were called.

**The action trace is the useful part** — it shows the model's routing decision and the parameters it passed, which explains most unexpected behaviour.

**Test the routing, not just the actions:**

```
"What's happening with my press claim?"           → Claim Status
"I need to raise a claim for the P400"            → Claim Submission
"Why was my claim rejected?"                      → Claim Status
"Can you approve this for me?"                    → should decline; out of scope
"What's my contract renewal date?"                → Contract topic, not Claims
```

**Ambiguous and out-of-scope requests matter more than clean ones.** An agent that handles "what's my claim status" and mishandles "why hasn't anyone called me back" is not ready.

**Apex actions are unit-tested normally:**

```java
@IsTest
static void theActionDoesNotReturnAnotherContactsClaim() {
    Contact requester = TestDataFactory.createContact();
    Warranty_Claim__c otherClaim = TestDataFactory.createClaimForAnotherContact();

    ClaimAgentActions.ClaimDetailRequest request = new ClaimAgentActions.ClaimDetailRequest();
    request.contactId = requester.Id;
    request.claimNumber = otherClaim.Claim_Number__c;

    Test.startTest();
    List<ClaimAgentActions.ClaimDetailResult> results =
        ClaimAgentActions.getDetail(new List<ClaimAgentActions.ClaimDetailRequest>{ request });
    Test.stopTest();

    Assert.isTrue(results[0].notFound,
        'An action must not return a claim belonging to another contact');
}
```

**That test is the one that matters**, and it is testable in the normal way because the action is Apex.

## Where agents fit

**Yes:**

```
Repetitive informational requests    status, eligibility, next steps
Guided data entry                    a conversational form
Retrieval from unstructured content  knowledge, documentation
Triage                               classify and route
Internal assistance                  drafting, summarizing, looking up
```

**No:**

```
Anything with automatic financial consequence
Anything requiring judgement the model cannot ground
Anything a deterministic flow handles correctly
Anything where a wrong answer is unrecoverable
Anything requiring a guarantee
```

**The test:** if the agent is wrong, what happens? If the answer is "the user reads a wrong sentence", proceed. If it is "money moves", do not.

## Design guidance

**Scope topics narrowly.** Three well-scoped topics outperform one broad one, because each routing decision is simpler.

**Write classification descriptions as situations**, not capabilities.

**Say what a topic cannot do**, in its scope.

**Describe actions and their parameters for the model**, since it reads them.

**Return explicit absences** — "not yet decided" rather than blank.

**Enforce security in every action.** The agent is an entry point.

**Validate in write actions**, and confirm before writing.

**Design the failure path.** What the agent says when an action fails, when nothing is found, and when the request is out of scope.

**Provide an escalation route.** An agent that cannot hand off to a person will eventually trap someone.

## Practical guidance

**A topic is the unit of design; keep them narrow.**

**The classification description is functional text**, not documentation.

**Action and parameter descriptions are read by the model** — write them accordingly.

**Enforce sharing, `USER_MODE`, and ownership** in every action.

**Verify ownership on guessable identifiers.**

**Validate in write actions**, and confirm before acting.

**Test routing with ambiguous and out-of-scope requests.**

**Unit-test the actions**, particularly the security cases.

**Always provide an escalation path to a human.**
