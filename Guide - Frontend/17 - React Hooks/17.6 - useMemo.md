# useMemo

`useMemo` caches a computed value between renders, recomputing only when its dependencies change.

```jsx
const value = useMemo(() => expensiveComputation(a, b), [a, b]);
```

It exists for two distinct reasons, and confusing them leads to misuse.

## Reason 1: skipping expensive computation

```jsx
const sorted = useMemo(
  () => [...items].sort((a, b) => b.score - a.score),
  [items]
);
```

Without the memo, the sort runs on every render — including renders triggered by unrelated state, like a hover or an input elsewhere in the component.

The bar for "expensive" is higher than most people assume. React's own guidance is roughly **1ms or more**, and modern hardware sorts a few thousand items well under that. Measure before assuming:

```jsx
console.time("sort");
const sorted = [...items].sort(cmp);
console.timeEnd("sort");
```

Test with CPU throttling at 4–6× in DevTools, since a mid-range phone is where it matters.

## Reason 2: preserving referential identity

This is the more common and more important reason.

```jsx
const config = useMemo(() => ({ theme, locale }), [theme, locale]);

useEffect(() => {
  initialize(config);
}, [config]);        // without the memo, fires every render
```

A new object literal has a new identity every render, so any dependency array or memoized child comparing it sees a change ([[19.1 - What Causes Re-renders]]).

The three cases where identity matters:

**Dependency arrays** — `useEffect`, `useMemo`, `useCallback`.
**Memoized children** — a new prop reference defeats `React.memo` ([[19.2 - React.memo and Memoization Strategy]]).
**Context values** — a new value object re-renders every consumer ([[20.2 - Context API and Its Limits]]).

```jsx
// Every consumer re-renders on every provider render
<Ctx.Provider value={{ user, logout }}>

// Stable
const value = useMemo(() => ({ user, logout }), [user, logout]);
<Ctx.Provider value={value}>
```

The context case is the one most worth internalizing — it silently costs performance across an entire subtree.

## When not to use it

```jsx
// Pointless — the memo costs more than the work
const doubled = useMemo(() => count * 2, [count]);
const name = useMemo(() => `${first} ${last}`, [first, last]);
const isValid = useMemo(() => value.length > 0, [value]);
```

`useMemo` is not free: it allocates a hook slot, stores the dependency array, and runs an `Object.is` comparison per dependency on every render. For trivial computations that overhead exceeds the work being avoided.

It also costs readability — every memo is a dependency array that can go wrong.

## Guarantees

`useMemo` is a **performance hint, not a semantic guarantee**. React may discard the cache — the documentation explicitly reserves the right to, and future versions may drop memoized values to free memory for offscreen content.

So this is a bug:

```jsx
const id = useMemo(() => crypto.randomUUID(), []);   // may regenerate
```

Use `useState(() => crypto.randomUUID())` or `useRef` for values that must be stable ([[17.8 - useRef]]). `useId` is the right answer for DOM ids ([[17.12 - Lesser Known Hooks]]).

## Dependencies

Same rules as `useEffect` ([[17.3 - useEffect and the Dependency Array]]): every reactive value read inside must be listed, and the linter derives them mechanically.

The recurring problem is a dependency that is itself unstable:

```jsx
// options is new every render, so the memo never hits
const options = { sortBy, order };
const sorted = useMemo(() => sort(items, options), [items, options]);

// Depend on the primitives
const sorted = useMemo(() => sort(items, { sortBy, order }), [items, sortBy, order]);
```

Memoization is only as stable as its least stable dependency. A chain of memos anchored on one unstable value is entirely wasted — a common and invisible failure.

## Memoizing JSX

```jsx
const header = useMemo(() => <Header user={user} />, [user]);
return <div>{header}{content}</div>;
```

A React element is just an object, so memoizing it means React can skip re-rendering that subtree during reconciliation ([[18.2 - Reconciliation and the Diffing Algorithm]]).

This works, but passing the element as a prop or child usually achieves the same thing more clearly:

```jsx
<Layout header={<Header user={user} />}>{content}</Layout>
```

The element is created in the parent's render, so `Layout` re-rendering does not recreate it.

## useMemo vs useCallback

```jsx
useCallback(fn, deps);
useMemo(() => fn, deps);      // identical
```

`useCallback` is sugar for memoizing a function ([[17.7 - useCallback]]). Same mechanism, same dependency rules.

## The React Compiler changes the calculus

The React Compiler automatically inserts memoization for values and components based on static analysis ([[19.9 - The React Compiler]]). In a compiled codebase, most manual `useMemo` calls become unnecessary — the compiler memoizes more thoroughly and more accurately than hand-written dependency arrays.

Two implications: on a compiled project, do not add manual memos preemptively; and the compiler only optimizes code that follows the rules of React, so purity and correct hook usage now have a direct performance payoff ([[16.5 - Rendering and Purity]]).

Manual memoization is not obsolete — the compiler is not yet universal, and it does not memoize across component boundaries in every case — but the default is shifting from "memoize proactively" to "memoize when measured".

## How senior engineers actually use this

**They memoize for identity far more often than for computation.** Context values, effect dependencies and props to memoized children are the real use cases.

**They profile before memoizing for cost.** The React DevTools Profiler shows actual render durations; guessing usually leads to memoizing the wrong thing.

**They check the whole dependency chain.** A memo whose dependency is unstable does nothing, and this is invisible without checking.

**They never rely on the cache surviving.** Anything that must be stable goes in state or a ref.

**They memoize context values as a habit**, since the cost of forgetting is subtree-wide.

## Common pitfalls

- Memoizing trivial computations, adding overhead and noise.
- A memo whose dependency is itself recreated every render.
- Relying on `useMemo` for semantic stability of ids or instances.
- Forgetting to memoize a context provider's value.
- Memoizing a value passed to a child that is not wrapped in `React.memo`, so nothing is saved.
- Missing dependencies producing stale computed values.

## Interview angle

"When should you use useMemo" separates people who have profiled from people who have read a tutorial. The strong answer names both reasons — expensive computation and referential stability — and stresses that identity is the more common one, with context values as the canonical example. Add that it is a hint rather than a guarantee, and that the React Compiler is shifting the default away from manual memoization.
