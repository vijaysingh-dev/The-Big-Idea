# Interfaces and Polymorphism

## The contract

An interface declares method signatures with no implementation. A class implementing it must provide all of them.

```java
public interface DiscountStrategy {
    Decimal discountFor(Warranty_Claim__c claim);
    String describe();
}
```

```java
public with sharing class PremiumContractDiscount implements DiscountStrategy {

    public Decimal discountFor(Warranty_Claim__c claim) {
        return claim.Service_Contract__r.Coverage_Level__c == 'Premium' ? 0.15 : 0;
    }

    public String describe() {
        return 'Premium contract holders receive 15% off parts';
    }
}
```

Interface methods are implicitly `public` — the modifier is not written in the interface and **is** required in the implementing class.

A class can implement any number of interfaces, which is how Apex compensates for having no multiple inheritance.

## Why interfaces matter here specifically

Two reasons, and the second is the one that shapes real codebases.

**Polymorphism.** Several implementations behind one type, chosen at runtime.

**Testability.** An interface is a seam. A test can substitute a stub where production code uses the real implementation, without touching the database or making a callout.

That second point is the practical argument. Apex tests are slow and constrained — every test inserting records pays for it in runtime and limits. Code written against interfaces can be tested without any of that.

## The strategy pattern

```java
public with sharing class ClaimCalculator {

    private final DiscountStrategy strategy;

    public ClaimCalculator(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    public Decimal calculate(Warranty_Claim__c claim) {
        Decimal base = claim.Claim_Amount__c ?? 0;
        return base * (1 - strategy.discountFor(claim));
    }
}
```

Selecting the implementation from configuration rather than hardcoding it:

```java
public with sharing class DiscountStrategyFactory {

    public static DiscountStrategy forClaim(Warranty_Claim__c claim) {
        Discount_Rule__mdt rule = Discount_Rule__mdt.getInstance(claim.Region__c);
        if (rule == null) {
            return new NoDiscount();
        }

        // instantiating by class name means a new strategy is a deployment, not a code change
        Type strategyType = Type.forName(rule.Strategy_Class__c);
        if (strategyType == null) {
            return new NoDiscount();
        }
        return (DiscountStrategy) strategyType.newInstance();
    }
}
```

`Type.forName()` plus `newInstance()` is Apex's reflection mechanism. The class must have a public no-argument constructor.

This combination — an interface, implementations, and Custom Metadata naming which implementation applies — is the foundation of configuration-driven architecture on the platform. Adding a new discount rule becomes deploying a class and a metadata record, with no change to the calling code. See [[18.10 - Custom Metadata Driven Architecture]].

## Platform interfaces

Much of the platform is exposed through interfaces you implement:

```java
Queueable                        System.enqueueJob
Database.Batchable<SObject>      Database.executeBatch
Schedulable                      System.schedule
Database.AllowsCallouts          marker: permits callouts in async context
Database.Stateful                marker: preserves state across batch chunks
Comparable                       custom sort order
Iterator<T> / Iterable<T>        custom iteration
HttpCalloutMock                  test mocking for callouts
StubProvider                     the Apex stub API for mocking
Messaging.InboundEmailHandler    inbound email processing
Callable                         loosely coupled cross-package invocation
Finalizer                        post-Queueable handling
```

Several are **marker interfaces** — no methods, just a signal to the runtime. `Database.AllowsCallouts` and `Database.Stateful` declare capability rather than behaviour.

`Callable` deserves a mention: it defines a single `call(String action, Map<String, Object> args)` method and is the standard way for one package to invoke another without a compile-time dependency. Where a managed package must be called optionally, this is the mechanism.

## instanceof and casting

```java
if (someObject instanceof DiscountStrategy) {
    DiscountStrategy strategy = (DiscountStrategy) someObject;
    Decimal discount = strategy.discountFor(claim);
}
```

`switch on` types more cleanly for sObjects:

```java
switch on record {
    when Warranty_Claim__c claim {
        handleClaim(claim);      // typed, no cast
    }
    when Case c {
        handleCase(c);
    }
}
```

A failed cast throws `TypeException`. Where the type is uncertain, test with `instanceof` first.

## The selector pattern

The most common real use of interfaces in Apex — separating queries from logic so the logic can be tested without a database.

```java
public interface ClaimSelector {
    List<Warranty_Claim__c> selectOpenByAsset(Set<Id> assetIds);
    List<Warranty_Claim__c> selectByIds(Set<Id> claimIds);
}
```

```java
public with sharing class ClaimSelectorImpl implements ClaimSelector {

    public List<Warranty_Claim__c> selectOpenByAsset(Set<Id> assetIds) {
        return [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c, Asset__c
            FROM Warranty_Claim__c
            WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
            WITH USER_MODE
        ];
    }

    public List<Warranty_Claim__c> selectByIds(Set<Id> claimIds) {
        return [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c, Asset__c
            FROM Warranty_Claim__c WHERE Id IN :claimIds WITH USER_MODE
        ];
    }
}
```

```java
@IsTest
private class ClaimServiceTest {

    // an in-memory selector, so the service can be tested with no DML at all
    private class StubSelector implements ClaimSelector {
        public List<Warranty_Claim__c> records = new List<Warranty_Claim__c>();

        public List<Warranty_Claim__c> selectOpenByAsset(Set<Id> assetIds) { return records; }
        public List<Warranty_Claim__c> selectByIds(Set<Id> claimIds) { return records; }
    }

    @IsTest
    static void highValueClaimsRequireEngineerReport() {
        StubSelector stub = new StubSelector();
        stub.records = new List<Warranty_Claim__c>{
            new Warranty_Claim__c(Claim_Amount__c = 1500000, Engineer_Report_Attached__c = false)
        };

        ClaimService service = new ClaimService(stub, new StubNotifier());

        Test.startTest();
        List<String> errors = service.validate(new Set<Id>{ fakeId });
        Test.stopTest();

        Assert.areEqual(1, errors.size(), 'High value claim without a report should fail validation');
    }
}
```

No records inserted, no queries consumed, and the test runs in milliseconds. On a codebase with a thousand tests, this is the difference between a suite that runs in three minutes and one that runs in forty.

The tradeoff is honest: this tests the logic, not the query. Selector implementations still need integration tests that exercise the real SOQL. Splitting them means most tests are fast and a small number are slow. See [[18.5 - Selector Layer]] and [[19.1 - Apex Testing Fundamentals]].

## Generating an ID without inserting

The stub test above needs a record ID for a record that was never inserted. The standard technique:

```java
public class TestIdFactory {

    private static Integer counter = 1;

    public static Id generate(Schema.SObjectType objectType) {
        String prefix = objectType.getDescribe().getKeyPrefix();
        String suffix = String.valueOf(counter++).leftPad(12, '0');
        return Id.valueOf(prefix + suffix);
    }
}
```

Constructing an ID from the object's key prefix produces a valid, unique identifier with no DML. This is what makes database-free testing practical.

## The stub API

For mocking without hand-writing stub classes, Apex provides `System.StubProvider` and `Test.createStub()`:

```java
@IsTest
private class ClaimServiceStubTest {

    private class SelectorMock implements System.StubProvider {
        public Object handleMethodCall(Object stubbedObject, String methodName,
                                       Type returnType, List<Type> paramTypes,
                                       List<String> paramNames, List<Object> args) {
            if (methodName == 'selectByIds') {
                return new List<Warranty_Claim__c>{
                    new Warranty_Claim__c(Claim_Amount__c = 250000)
                };
            }
            return null;
        }
    }

    @IsTest
    static void serviceUsesStubbedSelector() {
        ClaimSelector stub = (ClaimSelector) Test.createStub(ClaimSelector.class, new SelectorMock());
        ClaimService service = new ClaimService(stub, new StubNotifier());
        // ...
    }
}
```

`Test.createStub()` works on classes and interfaces and only inside tests. For simple cases a hand-written stub class is clearer; the stub API earns its place when mocking many methods or asserting on call arguments. See [[18.8 - Dependency Injection and Testability]].

## Interface design

**Keep them small.** An interface with twelve methods forces every implementation and every stub to provide twelve. Several focused interfaces compose better than one large one.

**Name by capability**, not by implementation. `DiscountStrategy`, `NotificationSender`, `ClaimSelector` — not `ClaimHelperInterface`.

**Do not create an interface for a single implementation with no test seam.** The indirection costs readability and buys nothing. The test for whether it earns its place: will there be a second implementation, or does a test need to substitute one?

**Return collections, take collections**, for the same bulkification reasons as everywhere else.

## Practical guidance

**Use interfaces as test seams**, particularly for queries and callouts.

**Combine an interface with Custom Metadata** to make behaviour configurable without deployment.

**Prefer interfaces and composition to inheritance** for varying one behaviour.

**Use `Type.forName()` and `newInstance()`** for dynamic selection, with a null check and a fallback.

**Keep interfaces small.**

**Do not add an interface without a reason.** One implementation and no test seam is indirection for its own sake.
