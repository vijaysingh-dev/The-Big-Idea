# fflib Apex Commons in Practice

## What it is

**fflib Apex Commons** is the open-source reference implementation of the layered architecture — service, domain, selector, and unit of work — originally from FinancialForce and now maintained by the Apex Enterprise Patterns community.

It is the closest thing the ecosystem has to a standard, and you will meet it in large orgs and hear it in interviews.

Two repositories:

```
fflib-apex-common    the patterns: Domain, Selector, UnitOfWork, Application factory
fflib-apex-mocks     the mocking framework for testing against them
```

## The Application class

The entry point that ties everything together, and the piece that makes mocking possible.

```java
public with sharing class Application {

    public static final fflib_Application.UnitOfWorkFactory UnitOfWork =
        new fflib_Application.UnitOfWorkFactory(new List<SObjectType>{
            Account.SObjectType,
            Asset.SObjectType,
            Warranty_Claim__c.SObjectType,
            Claim_Part__c.SObjectType
        });

    public static final fflib_Application.ServiceFactory Service =
        new fflib_Application.ServiceFactory(new Map<Type, Type>{
            IClaimApprovalService.class => ClaimApprovalServiceImpl.class
        });

    public static final fflib_Application.SelectorFactory Selector =
        new fflib_Application.SelectorFactory(new Map<SObjectType, Type>{
            Warranty_Claim__c.SObjectType => ClaimsSelector.class,
            Asset.SObjectType => AssetsSelector.class
        });

    public static final fflib_Application.DomainFactory Domain =
        new fflib_Application.DomainFactory(Application.Selector, new Map<SObjectType, Type>{
            Warranty_Claim__c.SObjectType => Claims.Constructor.class
        });
}
```

**Every factory can be replaced with a mock in a test**, which is the whole point:

```java
Application.Selector.setMock(mockClaimsSelector);
Application.UnitOfWork.setMock(mockUow);
```

That single capability is what makes fflib's tests fast — no DML, no queries, no trigger execution.

## The domain

```java
public with sharing class Claims extends fflib_SObjectDomain {

    public Claims(List<Warranty_Claim__c> records) {
        super(records);
    }

    public override void onApplyDefaults() {
        for (Warranty_Claim__c claim : (List<Warranty_Claim__c>) Records) {
            if (String.isBlank(claim.Status__c)) {
                claim.Status__c = 'Submitted';
            }
        }
    }

    public override void onValidate() {
        for (Warranty_Claim__c claim : (List<Warranty_Claim__c>) Records) {
            if (claim.Claim_Amount__c != null && claim.Claim_Amount__c <= 0) {
                claim.Claim_Amount__c.addError(Label.Claim_Error_Amount_Must_Be_Positive);
            }
        }
    }

    public override void onValidate(Map<Id, SObject> existingRecords) {
        // the update-context overload receives the prior values
        for (Warranty_Claim__c claim : (List<Warranty_Claim__c>) Records) {
            Warranty_Claim__c prior = (Warranty_Claim__c) existingRecords.get(claim.Id);
            if (prior.Status__c == 'Closed' && claim.Status__c != 'Closed') {
                claim.addError(Label.Claim_Error_Cannot_Reopen);
            }
        }
    }

    public override void onAfterUpdate(Map<Id, SObject> existingRecords) {
        ClaimApprovalService.handleStatusTransitions(
            (List<Warranty_Claim__c>) Records,
            (Map<Id, Warranty_Claim__c>) existingRecords
        );
    }

    // the constructor class is how the framework instantiates the domain generically
    public class Constructor implements fflib_SObjectDomain.IConstructable {
        public fflib_SObjectDomain construct(List<SObject> records) {
            return new Claims(records);
        }
    }
}
```

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    fflib_SObjectDomain.triggerHandler(Claims.class);
}
```

**`onApplyDefaults` and `onValidate` are called at the right times automatically** — the base class handles the event dispatch, so the domain only overrides what it needs.

The `Constructor` inner class exists because Apex cannot instantiate a class with a parameterized constructor reflectively. It is boilerplate, and it is required. See [[09.12 - Generics, Type Casting and Reflection]].

## The selector

```java
public with sharing class ClaimsSelector extends fflib_SObjectSelector implements IClaimsSelector {

    public static IClaimsSelector newInstance() {
        return (IClaimsSelector) Application.Selector.newInstance(
            Warranty_Claim__c.SObjectType
        );
    }

    public Schema.SObjectType getSObjectType() {
        return Warranty_Claim__c.SObjectType;
    }

    public List<Schema.SObjectField> getSObjectFieldList() {
        return new List<Schema.SObjectField>{
            Warranty_Claim__c.Id,
            Warranty_Claim__c.Claim_Number__c,
            Warranty_Claim__c.Status__c,
            Warranty_Claim__c.Claim_Amount__c,
            Warranty_Claim__c.Asset__c
        };
    }

    public List<Warranty_Claim__c> selectById(Set<Id> ids) {
        return (List<Warranty_Claim__c>) selectSObjectsById(ids);
    }

    public List<Warranty_Claim__c> selectOpenByAsset(Set<Id> assetIds) {
        // newQueryFactory applies the field list and security enforcement automatically
        return (List<Warranty_Claim__c>) Database.query(
            newQueryFactory()
                .setCondition('Asset__c IN :assetIds AND Status__c != \'Closed\'')
                .setOrdering('Claim_Date__c', fflib_QueryFactory.SortOrder.DESCENDING)
                .toSOQL()
        );
    }
}
```

**`newQueryFactory()` applies the declared field list and enforces field-level security**, which is a genuine benefit — the field list is declared once and every query gets it.

The interface plus static `newInstance` is what makes the selector mockable.

## The service

```java
public interface IClaimApprovalService {
    void approve(Set<Id> claimIds, Decimal amount);
}
```

```java
public with sharing class ClaimApprovalService {

    // the static facade delegates to the injected implementation
    public static void approve(Set<Id> claimIds, Decimal amount) {
        service().approve(claimIds, amount);
    }

    private static IClaimApprovalService service() {
        return (IClaimApprovalService) Application.Service.newInstance(
            IClaimApprovalService.class
        );
    }
}
```

```java
public with sharing class ClaimApprovalServiceImpl implements IClaimApprovalService {

    public void approve(Set<Id> claimIds, Decimal amount) {
        fflib_ISObjectUnitOfWork uow = Application.UnitOfWork.newInstance();

        List<Warranty_Claim__c> claims = ClaimsSelector.newInstance().selectById(claimIds);

        for (Warranty_Claim__c claim : claims) {
            claim.Status__c = 'Approved';
            claim.Approved_Amount__c = amount;
            uow.registerDirty(claim);

            uow.registerNew(new Claim_Payment__c(
                Warranty_Claim__c = claim.Id,
                Amount__c = amount
            ));
        }

        uow.commitWork();
    }
}
```

The static facade with an injectable implementation is the fflib service convention. It keeps call sites clean while allowing the implementation to be mocked.

## Testing with fflib-apex-mocks

The payoff.

```java
@IsTest
static void approvalRegistersAPaymentPerClaim() {
    fflib_ApexMocks mocks = new fflib_ApexMocks();

    IClaimsSelector mockSelector = (IClaimsSelector) mocks.mock(ClaimsSelector.class);
    fflib_ISObjectUnitOfWork mockUow =
        (fflib_ISObjectUnitOfWork) mocks.mock(fflib_SObjectUnitOfWork.class);

    Id claimId = fflib_IDGenerator.generate(Warranty_Claim__c.SObjectType);

    mocks.startStubbing();
    mocks.when(mockSelector.sObjectType()).thenReturn(Warranty_Claim__c.SObjectType);
    mocks.when(mockSelector.selectById(new Set<Id>{ claimId }))
        .thenReturn(new List<Warranty_Claim__c>{
            new Warranty_Claim__c(Id = claimId, Status__c = 'Submitted')
        });
    mocks.stopStubbing();

    Application.Selector.setMock(mockSelector);
    Application.UnitOfWork.setMock(mockUow);

    Test.startTest();
    // no DML, no queries, no triggers — the logic alone is exercised
    ClaimApprovalService.approve(new Set<Id>{ claimId }, 150000);
    Test.stopTest();

    ((fflib_ISObjectUnitOfWork) mocks.verify(mockUow, 1)).registerNew(
        (SObject) fflib_Match.sObjectOfType(Claim_Payment__c.SObjectType)
    );
    ((fflib_ISObjectUnitOfWork) mocks.verify(mockUow, 1)).commitWork();
}
```

Milliseconds, and it verifies exactly what the service did rather than what the database ended up holding.

**This is the strongest argument for fflib**, and it is worth being clear that it is the argument — the layering alone is achievable without the framework; the mocking infrastructure is what fflib uniquely provides.

## The honest assessment

**What it gives you:**

A coherent, well-documented architecture with a large body of practice behind it. Excellent testability. A consistent shape across every object, which matters when several teams work in one codebase. Recognized by developers who have used it elsewhere.

**What it costs:**

Substantial ceremony — a domain, a domain constructor, a selector, a selector interface, a service, a service interface, and a service implementation for one object's behaviour. A learning curve measured in weeks, not days. A dependency to keep current. And it is all-or-nothing: half-adopting produces the worst of both worlds, where some code is layered and mockable and some is not, and nobody is sure which.

**The verbosity is real.** The casting between `List<SObject>` and the concrete type appears everywhere, because Apex has no generics. See [[09.12 - Generics, Type Casting and Reflection]].

## When to adopt it

**Adopt when:**

- The org is large and long-lived, with several developers or teams
- Test execution time is a genuine problem
- You want the mocking infrastructure specifically
- The team has, or will invest in, the learning curve
- Someone will own the pattern and enforce it

**Do not adopt when:**

- The org has a handful of triggered objects
- One or two developers maintain it
- Nobody on the team has used it before and there is no time to learn it
- It is being adopted because it appeared in a blog post

**The failure mode worth naming:** a team adopts fflib, finds it verbose, applies it inconsistently, and ends up with a codebase where the pattern is followed in three places and ignored in twenty. That is worse than never adopting it, because the structure implies a guarantee that does not hold.

## A middle path

Many teams take the ideas without the framework.

```
Trigger → Handler → Service → Selector
```

Static selectors with `WITH USER_MODE`. Services taking collections. Interfaces at the two or three seams that genuinely need mocking, using the **Stub API** directly rather than fflib-apex-mocks:

```java
public class MockClaimsSelector implements System.StubProvider {

    public Object handleMethodCall(
        Object stubbedObject, String methodName, Type returnType,
        List<Type> paramTypes, List<String> paramNames, List<Object> args
    ) {
        if (methodName == 'selectById') {
            return this.claimsToReturn;
        }
        return null;
    }
}
```

The Stub API is built into the platform, needs no dependency, and covers the common cases. See [[18.8 - Dependency Injection and Testability]].

**This is the right answer for most orgs**: the architecture's benefits, without a framework nobody on the team fully understands.

## Inheriting an fflib codebase

When you arrive at an org already using it.

**Read `Application.cls` first.** It is the map — every registered selector, service, and domain is listed there.

**Find the domain classes** to understand per-object behaviour, and the trigger to confirm the dispatch.

**Check whether the pattern is applied consistently.** Grep for `Database.query` and `insert` outside selectors and units of work; the exceptions tell you where the discipline broke down.

**Do not introduce a second pattern alongside it.** Consistency matters more than which pattern.

**Keep the version current-ish.** The community repository receives updates, and a fork three years behind is a maintenance problem of its own.

## Practical guidance

**Understand the layering before evaluating the framework** — they are separable, and the layering is the valuable part.

**Adopt fflib for the mocking**, primarily. That is what it uniquely provides.

**Do not adopt it in a small org.**

**Adopt it fully or not at all.** Partial adoption is the worst outcome.

**Consider the Stub API** if mocking is the only thing you want.

**Read `Application.cls`** first in an inherited codebase.

**Ensure someone owns the pattern**, or it will erode.
