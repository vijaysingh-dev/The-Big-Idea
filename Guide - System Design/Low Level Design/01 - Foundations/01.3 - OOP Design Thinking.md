# OOP Design Thinking

OOP is not about classes and objects. It's about **organizing behavior around data** and **managing change through encapsulation and abstraction**. Most engineers learn the syntax; senior engineers internalize the thinking.

---

## The Four Pillars — What They Actually Mean

|Pillar|What It Really Is|Why It Matters|
|---|---|---|
|**Encapsulation**|Hiding change behind a boundary|Protects callers from internal churn|
|**Abstraction**|Defining "what" without "how"|Enables swap-ability and testing|
|**Inheritance**|Sharing contract + (optionally) impl|Powerful for contracts, dangerous for impl|
|**Polymorphism**|One interface, many behaviors|Eliminates `if/switch` type dispatch|

---

## Encapsulation — The Most Underrated Pillar

### What It Really Means

Not just "make fields private." Encapsulation means: **don't expose what can change**. The public interface should be stable; the internal implementation should be free to evolve.

```python
# ❌ Leaky encapsulation — internal list exposed
class ShoppingCart:
    def __init__(self):
        self.items = []  # public — callers can do cart.items.append(...)
    
    def get_total(self):
        return sum(item.price for item in self.items)

# Callers now:
cart.items.append(item)        # bypasses business rules
cart.items[0].price = 0        # bypasses validation
del cart.items[:]              # bypasses any cart-cleared logic


# ✅ Proper encapsulation — behavior, not data, is the interface
class ShoppingCart:
    def __init__(self):
        self._items: list[CartItem] = []    # private
        self._coupon: Optional[Coupon] = None
    
    def add_item(self, item: CartItem) -> None:
        """Business rule: duplicate items merge, don't duplicate."""
        existing = self._find_item(item.sku)
        if existing:
            existing.increment_qty(item.qty)
        else:
            self._items.append(item)
    
    def remove_item(self, sku: str) -> None:
        self._items = [i for i in self._items if i.sku != sku]
    
    def apply_coupon(self, coupon: Coupon) -> None:
        if self._coupon:
            raise BusinessError("A coupon is already applied")
        coupon.validate()
        self._coupon = coupon
    
    @property
    def total(self) -> Decimal:
        subtotal = sum(i.subtotal for i in self._items)
        return self._coupon.apply(subtotal) if self._coupon else subtotal
    
    @property
    def item_count(self) -> int:
        return sum(i.qty for i in self._items)
    
    def _find_item(self, sku: str) -> Optional[CartItem]:
        return next((i for i in self._items if i.sku == sku), None)
```

### Rule of Thumb

If callers are accessing your object's internals to _compute something_ — that computation belongs inside the object. **Tell, don't ask.**

## Abstraction — Design the Interface, Then the Implementation

### The Right Approach

Design the _interface_ first from the caller's perspective. What does the caller need? What level of detail should they care about? Then implement.

```python
# Wrong approach: write the implementation, then expose what falls out
class EmailService:
    def __init__(self):
        self.smtp = smtplib.SMTP("smtp.gmail.com", 587)
        self.smtp.starttls()
    
    def send(self, to, subject, body, html_body=None, attachments=None,
             reply_to=None, cc=None, bcc=None, headers=None):
        # implementation details leaking into the interface


# Right approach: design from caller's perspective
class NotificationChannel(ABC):
    """What callers need: send a message to a recipient."""
    
    @abstractmethod
    def send(self, recipient: str, subject: str, body: str) -> DeliveryResult:
        """Returns DeliveryResult, never raises — callers don't want SMTP exceptions."""
        pass


class EmailChannel(NotificationChannel):
    """Implementation details hidden here."""
    def send(self, recipient, subject, body) -> DeliveryResult:
        try:
            self._smtp_client.send(...)
            return DeliveryResult.success()
        except SMTPException as e:
            return DeliveryResult.failure(str(e))
```

### Abstraction Levels

Good abstractions operate at **one level of abstraction**. A function should either deal with high-level concepts or low-level details — not both.

```python
# ❌ Mixed abstraction levels
def process_payment(order):
    # High-level
    validate_order(order)
    
    # Suddenly low-level
    cursor = db.cursor()
    cursor.execute("SELECT * FROM payment_methods WHERE user_id = ?", order.user_id)
    row = cursor.fetchone()
    
    # Back to high-level
    if row:
        charge_payment_method(row, order.total)
```

## Polymorphism — Eliminating Type Dispatch

### What It Enables

Replace explicit type-checking with polymorphic dispatch. The object knows what it is; you don't need to ask.

```python
# ❌ Type dispatch — the smell of missing polymorphism
def calculate_shipping(order):
    if order.shipping_type == "standard":
        return order.weight * 0.5
    elif order.shipping_type == "express":
        return order.weight * 1.5 + 10
    elif order.shipping_type == "overnight":
        return order.weight * 3.0 + 25
    # Every new type = modify this function


# ✅ Polymorphic dispatch
class ShippingMethod(ABC):
    @abstractmethod
    def calculate_cost(self, weight: float) -> Decimal: pass

class StandardShipping(ShippingMethod):
    def calculate_cost(self, weight): return Decimal(weight * 0.5)

class ExpressShipping(ShippingMethod):
    def calculate_cost(self, weight): return Decimal(weight * 1.5 + 10)

class OvernightShipping(ShippingMethod):
    def calculate_cost(self, weight): return Decimal(weight * 3.0 + 25)


def calculate_shipping(order):
    return order.shipping_method.calculate_cost(order.weight)
    # Zero if/else — works for any ShippingMethod subtype
```

## Composition vs Inheritance — Decision Framework

```
Ask yourself:
     Is this truly an "is-a" relationship (not just "looks like" or "shares code")?
             ↓ Yes                               ↓ No
     Is the hierarchy stable?              Use Composition
     (won't need to be mixed,                    │
      won't grow beyond 2 levels)                ▼
             ↓ Yes             Inject behaviors as dependencies
     Inheritance is OK         or assemble from component objects
```

### The Composition Pattern in Practice

```python
# Building an auditable, rate-limited, retrying HTTP client via composition
class HttpClient:
    """Core — makes HTTP calls."""
    def request(self, method, url, **kwargs) -> Response: ...


class RetryMiddleware:
    """Adds retry behavior by wrapping another client."""
    def __init__(self, client: HttpClient, max_retries: int = 3):
        self._client = client
        self._max_retries = max_retries
    
    def request(self, method, url, **kwargs) -> Response:
        for attempt in range(self._max_retries):
            try:
                return self._client.request(method, url, **kwargs)
            except TransientError:
                if attempt == self._max_retries - 1:
                    raise
                time.sleep(2 ** attempt)


class AuditMiddleware:
    """Adds audit logging."""
    def __init__(self, client, audit_log: AuditLog):
        self._client = client
        self._audit_log = audit_log
    
    def request(self, method, url, **kwargs) -> Response:
        self._audit_log.record(method, url, user=kwargs.get("user"))
        response = self._client.request(method, url, **kwargs)
        self._audit_log.record_response(response.status_code)
        return response


# Compose: base + retry + audit
client = AuditMiddleware(
    RetryMiddleware(HttpClient(), max_retries=3),
    audit_log=AuditLog()
)
# Each concern is independently testable and swappable
```

## Object Responsibilities — CRC Cards Mental Model

Before writing code, mentally assign **responsibilities** using CRC (Class, Responsibility, Collaborator):

```
┌─────────────────────────────────────────────┐
│ Class: Order                                │
├─────────────────────────────────────────────┤
│ Responsibilities:                           │
│  - Know its items and total                 │
│  - Know its current status                  │
│  - Enforce status transition rules          │
├─────────────────────────────────────────────┤
│ Collaborators:                              │
│  - OrderItem (for item detail)              │
│  - User (for owner identity)                │
│  - PaymentRecord (for payment status)       │
└─────────────────────────────────────────────┘
```

If a class's "responsibilities" list has more than 3-4 items, it's probably doing too much.

## Value Objects vs Entities — Critical Distinction

```python
# Entity — identity matters, mutable over time
class User:
    def __init__(self, user_id: UUID, email: str):
        self.id = user_id        # identity
        self.email = email       # can change
    
    def __eq__(self, other):
        return self.id == other.id  # equality by identity


# Value Object — no identity, equality by value, immutable
@dataclass(frozen=True)  # frozen = immutable
class Money:
    amount: Decimal
    currency: str
    
    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise CurrencyMismatchError()
        return Money(self.amount + other.amount, self.currency)
    
    # No id field — two Money(100, "USD") are identical
    # __eq__ auto-generated by dataclass, compares all fields


# Why it matters:
price = Money(Decimal("9.99"), "USD")
tax = Money(Decimal("0.89"), "USD")
total = price + tax   # creates new Money — original unchanged
```

**Use Value Objects for:** Money, Address, DateRange, PhoneNumber, Email, Coordinate, Color — anything defined by its attributes, not its identity.

## Interface Design Heuristics

|Heuristic|Guidance|
|---|---|
|**Command-Query Separation**|Methods either _do_ something (command) or _return_ something (query) — not both|
|**Tell, Don't Ask**|Give objects work to do; don't ask for their state to decide what to do|
|**Minimal surface area**|Expose only what callers need — every public method is a commitment|
|**Return domain objects**|Return `Order`, not `dict` — lets callers use the object's behavior|
|**Raise domain exceptions**|Raise `InsufficientInventoryError`, not `ValueError("not enough stock")`|

```python
# ❌ Ask-then-act (breaks Tell Don't Ask)
if order.get_status() == "PENDING":
    order.set_status("CONFIRMED")
    order.set_confirmed_at(datetime.now())

# ✅ Tell the object to do the work
order.confirm()  # Order knows how to confirm itself, including validation

class Order:
    def confirm(self):
        if self.status != OrderStatus.PENDING:
            raise InvalidStateTransition(f"Cannot confirm order in {self.status} state")
        self.status = OrderStatus.CONFIRMED
        self.confirmed_at = datetime.now()
        self._events.append(OrderConfirmed(order_id=self.id))
```
