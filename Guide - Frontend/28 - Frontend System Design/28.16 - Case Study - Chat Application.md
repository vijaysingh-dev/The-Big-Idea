# Case Study - Chat Application

The most demanding of the standard case studies, because it combines bidirectional real-time, optimistic writes, reverse-scrolling pagination and connection lifecycle in one screen.

## Scope it

- One-to-one, group, or both? How large can a group get?
- Message history depth — hours, or years?
- Attachments? Reactions? Threads? Edits and deletes?
- Read receipts and typing indicators?
- Offline support?
- End-to-end encryption?

A reasonable scope: **group chat, full history, text plus images, reactions, typing indicators, read receipts, no E2EE, works on flaky mobile networks.**

## Transport

Bidirectional and low-latency, so a WebSocket is justified here — unlike a feed, where SSE usually suffices ([[15.8 - WebSockets and Server Sent Events]]).

The browser API gives almost nothing. Production chat needs:

```ts
function createConnection(url, { onMessage }) {
  let ws, attempt = 0, closed = false;
  const outbox = [];

  const open = () => {
    ws = new WebSocket(url);

    ws.onopen = () => {
      attempt = 0;
      startHeartbeat();
      outbox.splice(0).forEach(m => ws.send(m));   // flush queued sends
      resync();                                     // fetch what we missed
    };

    ws.onmessage = (e) => onMessage(JSON.parse(e.data));

    ws.onclose = () => {
      stopHeartbeat();
      if (closed) return;
      const delay = Math.min(30_000, 500 * 2 ** attempt++);
      setTimeout(open, delay + Math.random() * delay * 0.3);
    };
  };

  const send = (msg) => {
    const data = JSON.stringify(msg);
    ws?.readyState === WebSocket.OPEN ? ws.send(data) : outbox.push(data);
  };

  open();
  return { send, close: () => { closed = true; ws.close(); } };
}
```

Four things, all necessary:

**Reconnection with backoff and jitter.** Without jitter, every client reconnects simultaneously after a server restart and knocks it over again ([[04.7 - Async Concurrency Patterns]]).

**Heartbeat.** A dropped connection often does not fire `onclose` — a closed laptop lid or a mobile network handoff leaves a half-open socket that looks healthy. Ping periodically; treat a missing pong as disconnected.

**An outbox.** Sending while `readyState !== OPEN` throws. Queue and flush on reconnect.

**Resync on reconnect.** The client missed events while disconnected. Fetch messages since the last known id rather than assuming continuity — reconnection happens on every deploy, so this is the normal path, not an edge case.

Given all of this, using a library — Socket.IO, or a thin wrapper — is usually correct.

## Authentication

The browser WebSocket API cannot set headers, so `Authorization: Bearer` is unavailable.

The options: a short-lived ticket obtained from a normal HTTP call and passed in the query string, cookie-based auth (cookies are sent on the handshake — but verify `Origin` server-side or you have cross-site connection hijacking), or authenticating as the first message after connect.

Never put a long-lived token in the URL; query strings end up in logs and referrers ([[28.7 - Authentication Flow Design]]).

## Message ordering

Client clocks are unreliable, so ordering must come from the server.

```json
{ "id": "m_88", "seq": 4021, "roomId": "r_1", "authorId": "u_9",
  "text": "...", "clientId": "c_abc", "createdAt": "..." }
```

A monotonic `seq` per room gives total ordering and makes gap detection trivial:

```ts
if (incoming.seq > lastSeq + 1) {
  fetchMessagesBetween(lastSeq, incoming.seq);   // fill the gap
}
```

`clientId` is the client-generated id used for deduplication and to reconcile the optimistic message with the server's version ([[24.3 - Retries Timeouts and Cancellation]]).

Deduplicate on arrival — a reconnect resync will re-deliver messages the client already has:

```ts
const byId = new Map(existing.map(m => [m.id, m]));
for (const m of incoming) byId.set(m.id, m);
```

## Optimistic sending

```ts
function sendMessage(text) {
  const clientId = crypto.randomUUID();

  const optimistic = {
    id: `local-${clientId}`,
    clientId,
    text,
    authorId: currentUser.id,
    createdAt: new Date().toISOString(),
    status: "sending",
  };

  queryClient.setQueryData(messageKeys.list(roomId), (old) =>
    appendMessage(old, optimistic)
  );

  connection.send({ type: "message:send", clientId, roomId, text });
}
```

The message appears instantly with a `sending` state. When the server acknowledges, replace by `clientId`:

```ts
socket.on("message:ack", ({ clientId, message }) => {
  queryClient.setQueryData(messageKeys.list(roomId), (old) =>
    replaceByClientId(old, clientId, { ...message, status: "sent" })
  );
});
```

Three states the UI must express: **sending**, **sent**, **failed** — the last with a retry affordance. A message that silently fails to send is the worst possible outcome in a chat product ([[24.5 - Optimistic UI]]).

The temporary id must be distinguishable (`local-` prefix) so nothing tries to use it in a request.

## Reverse pagination

History loads **upward**, which is the awkward direction:

```ts
const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
  queryKey: messageKeys.list(roomId),
  queryFn: ({ pageParam, signal }) =>
    api.getMessages({ roomId, before: pageParam, signal }),
  initialPageParam: null,
  getNextPageParam: (last) => last.pageInfo.oldestSeq ?? undefined,
});
```

Prepending content shifts everything below it, so scroll position must be preserved manually:

```ts
useLayoutEffect(() => {
  const el = containerRef.current;
  if (prevHeight.current) {
    el.scrollTop = el.scrollHeight - prevHeight.current;
  }
  prevHeight.current = el.scrollHeight;
}, [messages.length]);
```

`useLayoutEffect` is required — running this after paint produces a visible jump ([[17.5 - useLayoutEffect vs useEffect]]).

Modern CSS handles some of this:

```css
.messages { overflow-anchor: auto; scroll-behavior: smooth; }
```

`flex-direction: column-reverse` is a common trick that anchors to the bottom automatically, at the cost of inverted keyboard scrolling and awkward accessibility.

## Auto-scroll, conditionally

Scroll to a new message **only if the user is already near the bottom**:

```ts
const isNearBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 100;

if (isNearBottom) {
  el.scrollTop = el.scrollHeight;
} else {
  setUnreadCount(c => c + 1);      // show a "N new messages" pill instead
}
```

Yanking someone away from history they are reading is the most-complained-about chat behavior. The unread pill is what every mature chat client does.

## Typing indicators and presence

```ts
const notifyTyping = useMemo(
  () => throttle(() => connection.send({ type: "typing", roomId }), 3000),
  [roomId]
);
```

Throttle, not debounce — you want a signal every few seconds while typing continues, not one after it stops ([[29.1 - Debounce and Throttle]]).

The receiving side expires the indicator locally after ~5 seconds rather than waiting for a "stopped typing" event that may never arrive if the connection drops.

Presence is expensive at scale — a 500-person room broadcasting every status change is a lot of traffic for little value. Aggregate ("12 online"), send deltas rather than full lists, and consider omitting it for large rooms.

## Read receipts

```ts
const observer = new IntersectionObserver(
  (entries) => {
    const seen = entries.filter(e => e.isIntersecting).map(e => e.target.dataset.id);
    if (seen.length) markReadThrottled(Math.max(...seen.map(Number)));
  },
  { threshold: 0.8 }
);
```

Batch to the highest seq seen rather than sending one event per message ([[12.5 - Custom Events and Observer APIs]]).

Also flush on `visibilitychange`, since a user switching tabs has stopped reading:

```ts
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") flushReadReceipts();
});
```

## Virtualization

A long conversation is thousands of variable-height messages. Virtualizing is necessary above roughly 200 rendered items, and it interacts badly with everything above ([[19.5 - Virtualization and Windowing]]):

- Scroll anchoring on prepend must account for virtual offsets
- Jumping to a specific message requires estimating its position before measurement
- Screen reader announcement of new messages needs an explicit live region, since virtualized items are not in the DOM

Many production chat clients virtualize only above a threshold, keeping the simpler path for typical conversations.

## Offline

```
send → append optimistically → persist to IndexedDB outbox → flush on reconnect
```

Messages composed offline must survive a reload, which means a durable queue rather than an in-memory array ([[28.12 - Real Time and Offline First]]).

Ordering and idempotency matter: replay in order, and the server deduplicates on `clientId` so a retry cannot double-post.

## Accessibility

```jsx
<div role="log" aria-live="polite" aria-relevant="additions">
  {messages.map(m => <Message key={m.id} {...m} />)}
</div>
```

`role="log"` is the correct pattern for a message stream — it announces additions without re-reading the whole history.

Use `polite`, not `assertive`; interrupting the user on every message is intolerable. For a busy room, announcing every message is also too much — announce only messages directed at the user, or a summary.

Keyboard: Enter sends, Shift+Enter newlines, Escape cancels an edit, and focus must return to the composer after sending.

## How senior engineers approach this

**They design the reconnect path first**, because it runs on every deploy and every network handoff.

**They order by server sequence**, never by client timestamp, and detect gaps.

**They make send state visible** — sending, sent, failed with retry.

**They auto-scroll only when the user is at the bottom**, and show an unread pill otherwise.

**They deduplicate on `clientId`** so resync and retry cannot double-post.

**They add virtualization above a measured threshold**, given how much it complicates scroll behavior.

## Common pitfalls

- No heartbeat, so half-open connections look healthy.
- Reconnect storms without jitter.
- Sending while `readyState` is CONNECTING, throwing.
- No resync after reconnect, leaving permanent gaps.
- Ordering by client timestamp.
- Auto-scrolling users away from history they are reading.
- Optimistic messages with no failure state.
- Scroll jump when prepending history.
- Debouncing typing indicators instead of throttling.
- Per-message read receipts instead of batched.

## Interview angle

Lead with the transport justification — bidirectional and low-latency, so WebSocket rather than SSE — then immediately with what the browser API does not provide: reconnection with jitter, heartbeat, send queue and resync. That list is the substance of the question. Follow with server-assigned sequence numbers for ordering and gap detection, `clientId` for optimistic reconciliation and deduplication, and the conditional auto-scroll with an unread pill. Mentioning that reconnection is the normal path rather than an edge case is the framing that signals production experience.
