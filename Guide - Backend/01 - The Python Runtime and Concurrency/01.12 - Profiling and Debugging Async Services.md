# Profiling and Debugging Async Services

#backend #python #production #debugging

> **In one line:** Measure before you change anything, use tools that work on a running production process, and know the four questions — is it CPU, is it waiting, is it memory, is it the loop — because each has a different tool.

---

## The Idea

The function you think is slow is almost never the function that is slow. This is not a failure of intelligence; it is that systems have too many interacting parts to reason about from a chair.

So: measure first, always.

Async makes this harder in one specific way. In a synchronous program, a stack trace tells you where time is going. In an async program, most tasks are suspended inside `epoll_wait` and the stack is nearly empty. A traditional profiler reports that your program spends 99% of its time waiting, which is true and useless.

---

## The Four Questions

Start every investigation by working out which of these it is. Each has a different tool and a different fix.

| Question | Signal | Tool |
|---|---|---|
| **Is the loop blocked?** | Loop lag high, CPU low | Loop lag metric, py-spy dump |
| **Is it CPU?** | CPU near 100% on one core per worker | py-spy record, flamegraph |
| **Is it waiting?** | Both low, latency high | Distributed tracing, per-call timers |
| **Is it memory?** | RSS climbing, or OOM kills | tracemalloc, memray |

⚠️ **Getting this wrong wastes days.** Optimizing Python code when the answer is a missing database index is the classic version, and it is extremely common.

---

## py-spy — The One That Matters

A sampling profiler that attaches to a **running process** with no code change, no restart, and negligible overhead. It reads the target's memory directly.

### The three commands

```bash
# What is it doing RIGHT NOW? First command in any incident
py-spy dump --pid 1234

# Live top-style view of where time goes
py-spy top --pid 1234

# 30 seconds into a flamegraph
py-spy record --pid 1234 --duration 30 --output flame.svg
```

### Reading a dump

Healthy async process:

```
Thread 1 (active): "MainThread"
    _run_once (asyncio/base_events.py:1900)
    select (selectors.py:468)
    epoll_wait                                    ← sleeping. Correct
```

Blocked async process:

```
Thread 1 (active): "MainThread"
    _run_once (asyncio/base_events.py:1900)
    __step (asyncio/tasks.py:314)
    generate_report (app/reports.py:88)
    loads (json/__init__.py:346)                  ← 50MB JSON parse. Found it
```

💡 **`py-spy dump` is the single most useful command in this note.** Thirty seconds into an unexplained incident, run it three times a few seconds apart. If the same non-`epoll_wait` frame appears every time, you have your answer.

### Useful flags

```bash
py-spy dump --pid 1234 --locals          # show local variable values in each frame
py-spy record --pid 1234 --idle          # include sleeping threads
py-spy record --pid 1234 --native        # include C extension frames
py-spy top --pid 1234 --subprocesses     # follow uvicorn's forked workers
```

`--locals` is excellent — it will often show you the actual query, URL or document ID that is stuck.

⚠️ **In Kubernetes you need `SYS_PTRACE` or a shared process namespace.** Configure this before you need it. A tool you cannot run during an incident does not exist.

```yaml
securityContext:
  capabilities:
    add: ["SYS_PTRACE"]
```

## Loop Lag — Your Best Health Metric

```python
async def loop_lag_monitor(interval=0.1):
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        lag = time.perf_counter() - start - interval
        loop_lag_seconds.observe(max(0, lag))
        if lag > 0.05:
            log.warning("loop blocked", extra={"lag_ms": round(lag * 1000)})
```

Loop lag predicts user-visible p99 far better than CPU does, and unlike CPU it points at the cause.

| Lag | Meaning |
|---|---|
| < 5ms | Healthy |
| 5–50ms | Some pressure. Watch it |
| 50–500ms | Something is blocking. Investigate now |
| > 500ms | Users are affected. Health checks are at risk |

Run this in every async service. It costs nothing.

## Task Introspection

Async's own kind of visibility: what tasks exist and what are they waiting on?

```python
@app.get("/debug/tasks")
async def debug_tasks():
    now = asyncio.get_running_loop().time()
    return [
        {
            "name": t.get_name(),
            "coro": t.get_coro().__qualname__,
            "done": t.done(),
            "stack": [
                f"{f.f_code.co_filename}:{f.f_lineno}" for f in t.get_stack()[-3:]
            ],
        }
        for t in asyncio.all_tasks()
    ]
```

⚠️ **Name your tasks or this is useless.**

```python
asyncio.create_task(sync_source(sid), name=f"sync-source-{sid}")
```

Four hundred tasks named `Task-1` through `Task-400` tell you nothing. Four hundred named `sync-source-<id>` tell you immediately that one source is stuck and which one.

Signal-triggered dumps are even better, because they work when HTTP is not responding:

```python
import signal, faulthandler

faulthandler.register(signal.SIGUSR1)      # SIGUSR1 → full stack dump to stderr

def dump_tasks(signum, frame):
    for t in asyncio.all_tasks():
        print(t.get_name(), t.get_coro().__qualname__, file=sys.stderr)

signal.signal(signal.SIGUSR2, dump_tasks)
```

```bash
kill -USR1 1234        # thread stacks
kill -USR2 1234        # async task list
```

Both survive a wedged event loop. Add them to every service.

## CPU Profiling

### Flamegraphs

```bash
py-spy record --pid 1234 --duration 60 --output flame.svg
```

Reading one:

- **Width** = time spent. Wide is what matters
- **Height** = call depth. Tall is irrelevant on its own
- **Look for wide plateaus**, not tall spikes
- In an async process, most width will be `epoll_wait`. Ignore it and look at the rest

### For a specific block

`cProfile` does not understand async well. Use `yappi`, which does.

```python
import yappi

yappi.set_clock_type("wall")     # wall, not CPU — you care about elapsed time
yappi.start()
await the_thing_you_suspect()
yappi.stop()
yappi.get_func_stats().sort("ttot").print_all()
```

⚠️ **`set_clock_type("cpu")` is the default and it is wrong for async.** CPU time excludes waiting, which is where all your latency is.

### Timing individual awaits

Sometimes the simplest tool wins.

```python
@asynccontextmanager
async def timed(name: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        elapsed = time.perf_counter() - start
        stage_seconds.labels(name).observe(elapsed)
        if elapsed > 0.1:
            log.info("slow stage", extra={"stage": name, "ms": elapsed * 1000})

async def handler():
    async with timed("fetch_user"):
        user = await get_user(uid)
    async with timed("fetch_docs"):
        docs = await search(q)
```

This turns one 400ms number into five numbers, one of which is 380ms. That is the whole job.

## Memory

### tracemalloc — built in, always available

```python
import tracemalloc

tracemalloc.start(25)                     # keep 25 frames of context

snap1 = tracemalloc.take_snapshot()
# ... let the service run ...
snap2 = tracemalloc.take_snapshot()

for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)
```

Output points at the allocating line. Good enough for most leaks.

### memray — better, when you can restart

```bash
memray run -o out.bin --live-remote -m uvicorn app:app
memray flamegraph out.bin
```

Tracks every allocation including in C extensions, with a live view. Higher overhead, so staging or a reproduction rather than production.

### The four common leaks in async services

| Leak | Cause | Fix |
|---|---|---|
| Unbounded queue | No `maxsize` | [[01.11 - Backpressure Inside One Process]] |
| Task set grows forever | `add` without `discard` in the done callback | `task.add_done_callback(set.discard)` |
| Cache with no eviction | A plain dict used as a cache | `cachetools.TTLCache` or Redis |
| Closure holding a large object | A callback capturing a big request body | Capture only the ID |

⚠️ **RSS not returning to baseline after a spike is often not a leak.** Python's allocator holds freed memory in arenas rather than returning it to the OS. Check `tracemalloc` before assuming a leak — if tracked allocations are flat but RSS is high, it is fragmentation, and the fix is `--limit-max-requests` to recycle workers rather than a code change.

## Debugging Techniques

### asyncio debug mode

```bash
PYTHONASYNCIODEBUG=1 uvicorn app:app
```

Gives you: slow-callback warnings with source locations, never-awaited coroutine warnings, never-retrieved exception warnings, and the source of task creation in tracebacks.

Development and staging only — the overhead is real.

### The exception handler

```python
def handler(loop, context):
    log.error("async exception", extra={
        "message": context.get("message"),
        "task": str(context.get("task")),
    }, exc_info=context.get("exception"))

loop.set_exception_handler(handler)
```

Without this, an exception in a fire-and-forget task goes to stderr at garbage collection time — or nowhere at all. **Set it in every service.** It is your last line of defence against silent failure.

### Reproducing intermittent failures

```python
async def chaos_delay():
    if random.random() < 0.1:
        await asyncio.sleep(random.uniform(0.1, 2.0))
```

Injecting random delays at await points surfaces ordering assumptions that only break under production timing. Combine with toxiproxy from [[00.4 - Setting Up Your Lab]] for the network layer.

## In Production

### The incident playbook

```
1. Is it one pod or all pods?
   One  → py-spy dump that pod. Compare to a healthy one
   All  → a shared dependency. Check the database and downstreams first

2. py-spy dump --pid 1 --locals, three times, five seconds apart
   Same non-epoll frame each time → blocking call, you are done

3. Check loop lag metric
   High → blocking or CPU. Continue with py-spy record
   Low  → you are waiting on something. Go to traces

4. Check pool wait times
   High → pool exhaustion. See [[01.10 - Connection Pools and Limits]]

5. Check queue depths
   Growing → backpressure failure. See [[01.11 - Backpressure Inside One Process]]

6. Check memory trend
   Climbing → tracemalloc comparison, or recycle workers as a stopgap

7. Still nothing → kill -USR1 for full stacks, kill -USR2 for the task list
```

Put this in your runbook with real commands and real pod names filled in. During an incident nobody composes commands well.

### Build it in before you need it

| Item | Why |
|---|---|
| py-spy in the image, `SYS_PTRACE` granted | Cannot install during an incident |
| Loop lag exported as a metric | Your earliest and most specific signal |
| Named tasks everywhere | The difference between 5 minutes and an hour |
| `/debug/tasks` behind auth | Works when logs do not |
| SIGUSR1 and SIGUSR2 handlers | Work when HTTP does not |
| Exception handler set | Catches what would otherwise vanish |
| Per-stage timing metrics | Turns one number into five |

### Optimize in this order

```
1. Fix the algorithm         N+1 query, wrong data structure       10–1000x
2. Remove the work           cache it, precompute it, drop it      ∞
3. Move it off the path      queue it                              user-visible only
4. Parallelize               gather instead of sequential          up to N x
5. Faster library            orjson, polars, asyncpg               2–10x
6. Faster runtime            newer Python, uvloop                  1.1–2x
7. Rewrite in another language                                     2–5x, huge cost
```

⚠️ **Almost everyone starts at 5 or 6.** The gains at 1 and 2 are one to three orders of magnitude larger and usually take less time.

## Codebase

**Repo:** `benfred/py-spy` and `bloomberg/memray`

**Question to answer:** How does py-spy read another process's Python stack without stopping it, and how does it avoid reading a half-updated frame? Then: how does memray intercept every allocation without changing your code?

**Read, in order:**

1. `py-spy/src/python_spy.rs` — you do not need Rust fluency. Find where it locates the interpreter state, then how it walks frames. Compare with the frame chain from [[01.1 - How Python Actually Runs Your Code]]
2. `py-spy/src/python_interpreters.rs` — how it handles different Python versions' differing internal structures. This is why py-spy needs updating for each new Python
3. `memray/_memray/tracking_api.cpp` — how allocation hooks are installed
4. `Lib/tracemalloc.py` plus `Modules/_tracemalloc.c` — the stdlib version of the same idea

**Then, most practically:** find `--locals` in py-spy and understand what it can and cannot show you. Knowing its limits is what makes you trust it during an incident.

**Size:** 1 session.

## Exercise

**Drill 1.11 — The diagnosis game**

The most useful drill in section 01, because it trains the skill you will actually use at 3am.

```
drills/01-profiling/
├── patients/
│   ├── patient_1.py      # blocking call in a coroutine
│   ├── patient_2.py      # pool exhaustion
│   ├── patient_3.py      # unbounded queue, memory growth
│   ├── patient_4.py      # N+1 queries
│   ├── patient_5.py      # CPU-heavy serialization
│   ├── patient_6.py      # task leak from a missing done callback
│   ├── patient_7.py      # slow downstream, no timeout
│   └── patient_8.py      # thread pool starvation from a `def` endpoint
├── toolkit/
│   ├── lag.py            # loop lag monitor + metric
│   ├── debug_routes.py   # /debug/tasks, /debug/stacks, /debug/pools
│   ├── signals.py        # SIGUSR1 and SIGUSR2 handlers
│   └── timing.py         # the timed() context manager
├── diagnosis/
│   └── LOG.md            # your work, one entry per patient
├── runbook/
│   └── RUNBOOK.md
└── README.md
```

**Part 1 — Build the toolkit.** Loop lag monitor, debug endpoints, signal handlers, timing context manager, exception handler. This becomes a library you paste into every service, including Conduit.

**Part 2 — Build eight patients.** Each is a FastAPI app with exactly one problem. **Make them realistic, not obvious.** The problem should be buried in a plausible-looking service, not on line 3.

Write each one and then **wait a week before diagnosing them**, so you have genuinely forgotten the details. This matters more than it sounds — diagnosing code you wrote yesterday teaches nothing.

**Part 3 — Diagnose blind.** For each patient, in order:

1. Start it under load. Do not read the source
2. Look only at metrics and tools
3. Write your hypothesis in `LOG.md` **before** confirming
4. Confirm with the appropriate tool
5. Record: time to diagnose, which tool gave it away, whether the first hypothesis was right

Track your accuracy across all eight. It should improve noticeably from patient 1 to patient 8, and watching that number move is the actual reward here.

**Part 4 — Time yourself.** Second pass, target: under five minutes per patient. This is a speed drill and speed is the thing that matters during a real incident.

**Part 5 — Write the runbook.** For each of the eight failure modes: symptom, first command to run, how to confirm, immediate mitigation, real fix. Write it for someone who has never read this note.

Then have someone else (or yourself in a month) run one patient and follow only the runbook. If they cannot diagnose it from your document, the document is wrong.

**Part 6 — Wire it into Conduit.** Add the whole toolkit to Conduit phase 1. Every service you build from here on has loop lag, named tasks, debug endpoints and signal handlers from day one.

**Done when:**
- All eight patients exist and are non-obvious
- `LOG.md` has eight entries with hypothesis-before-confirmation
- Your average diagnosis time is under five minutes
- `RUNBOOK.md` is usable by someone who has not read this note
- Conduit has the toolkit installed
