# SOSL and Full Text Search

## What SOSL is for

**SOSL** — Salesforce Object Search Language — searches a **text index** rather than scanning rows. It is the mechanism behind global search, and it is the correct answer whenever the requirement is "find records containing this word".

The distinction from SOQL:

| | SOQL | SOSL |
| --- | --- | --- |
| Mechanism | Row filtering | Text index lookup |
| Objects per query | One (plus relationships) | Up to 20 |
| Finds text within a field | Only with `LIKE '%term%'` | Yes, natively |
| Leading wildcard performance | Cannot use an index | Designed for it |
| Returns | Records matching filters | Records matching terms, ranked |
| Limit per transaction | 100 queries | 20 searches |
| Rows returned | 50,000 | 2,000 |

The rule of thumb: **filter with SOQL, search with SOSL.** A query that knows exactly which field equals which value is SOQL. A user typing words into a box is SOSL.

## Syntax

```sql
FIND {press bearing}
IN ALL FIELDS
RETURNING
    Warranty_Claim__c (Id, Claim_Number__c, Status__c WHERE Status__c != 'Closed' LIMIT 20),
    Asset (Id, Name, SerialNumber LIMIT 20),
    Knowledge__kav (Id, Title, UrlName WHERE PublishStatus = 'Online' LIMIT 10)
LIMIT 50
```

The pieces:

**`FIND {terms}`** — the search string, in braces.

**`IN <scope>`** — `ALL FIELDS`, `NAME FIELDS`, `EMAIL FIELDS`, `PHONE FIELDS`, or `SIDEBAR FIELDS`. Narrowing the scope is faster and more precise.

**`RETURNING`** — which objects, which fields, and optional per-object filters, ordering, and limits.

**`LIMIT`** — total across all objects, capped at 2,000.

## In Apex

```java
public with sharing class GlobalSearchService {

    @AuraEnabled(cacheable=true)
    public static SearchResults search(String searchTerm) {
        if (String.isBlank(searchTerm) || searchTerm.length() < 2) {
            return new SearchResults();
        }

        String term = String.escapeSingleQuotes(searchTerm) + '*';

        // the result is a list of lists, one per RETURNING clause, in declaration order
        List<List<SObject>> results = [
            FIND :term
            IN ALL FIELDS
            RETURNING
                Asset (Id, Name, SerialNumber, Account.Name WHERE Status = 'Installed' LIMIT 10),
                Warranty_Claim__c (Id, Claim_Number__c, Status__c, Claim_Amount__c
                                   WHERE Status__c != 'Closed' LIMIT 10),
                Case (Id, CaseNumber, Subject, Status WHERE IsClosed = false LIMIT 10)
            LIMIT 30
        ];

        SearchResults output = new SearchResults();
        output.assets = (List<Asset>) results[0];
        output.claims = (List<Warranty_Claim__c>) results[1];
        output.cases = (List<Case>) results[2];
        return output;
    }
}
```

The result is `List<List<SObject>>`, ordered by the `RETURNING` clauses. Index 0 is the first object listed, regardless of how many results each returned. An object with no matches gives an empty list at its index, not a missing entry — so the indexes stay stable.

Binding the search term with `:term` is safe. `String.escapeSingleQuotes` on top is belt and braces for the cases where a bind is not used.

## Wildcards and operators

```
FIND {press*}              prefix match
FIND {*ring}               suffix match — supported, and slower
FIND {pre?s}               single character wildcard
FIND {press AND bearing}   both terms
FIND {press OR bearing}    either
FIND {press AND NOT belt}  exclusion
FIND {"drive belt"}        exact phrase
```

Multiple terms without an operator default to `AND`.

Appending `*` to a user's input is the standard behaviour for a type-ahead search — a user typing "pres" expects to find "press". Without it, only exact word matches return.

Leading wildcards are supported but degrade performance, which is the one place SOSL shares a weakness with `LIKE '%term%'`.

## The search index

SOSL searches an index, and that has consequences worth knowing.

**The index is updated asynchronously.** A record created a moment ago may not be findable immediately. The delay is usually short and it is not zero, and it is a real source of confusing test failures.

**Not everything is indexed.** Long text areas are indexed with limits. Some field types are not indexed at all. Formula fields are not searchable.

**In test context, SOSL returns nothing by default.** Test data is not indexed. This is the single most common SOSL testing problem, and the fix is `Test.setFixedSearchResults()`:

```java
@IsTest
static void searchReturnsMatchingAssets() {
    Asset asset = TestDataFactory.createAsset('Press P400', 'SN-88213');

    // the search index does not exist in test context, so results must be injected
    Test.setFixedSearchResults(new List<Id>{ asset.Id });

    Test.startTest();
    SearchResults results = GlobalSearchService.search('press');
    Test.stopTest();

    Assert.areEqual(1, results.assets.size(), 'Fixed search results should be returned');
}
```

`setFixedSearchResults` forces any SOSL in the test to return exactly those IDs, subject to the `RETURNING` filters. It tests the code around the search, not the search itself — which is the honest limit of what can be tested here. See [[19.1 - Apex Testing Fundamentals]].

## SOSL versus SOQL for a search box

The decision that matters in practice.

A user types into a search box. Two implementations:

```java
// SOQL with a leading wildcard: scans, does not use an index
List<Asset> assets = [
    SELECT Id, Name FROM Asset WHERE Name LIKE :('%' + term + '%') LIMIT 20
];
```

```java
// SOSL: uses the text index
List<List<SObject>> results = [
    FIND :(term + '*') IN NAME FIELDS RETURNING Asset (Id, Name LIMIT 20)
];
```

At 5,000 assets both work. At two million, the first is slow or times out and the second is fine.

The general guidance: **any user-entered search term across an object of meaningful size should be SOSL.** The `LIKE '%term%'` form is the pattern people write first and the one that fails as data grows. The phone-number lookup in [[05.12 - CTI and Voice]] is the same problem in a different guise.

## Search across many objects

SOSL's ability to search up to 20 objects in one call is its other main advantage. A global search component needs one SOSL query where SOQL would need one query per object — and SOQL's 100-query limit makes that approach fragile.

For a console component surfacing everything relevant to a caller, one SOSL query across Contact, Account, Case, Asset, and Warranty Claim is both faster and simpler than five SOQL queries.

## Ranking

SOSL returns results ranked by relevance, using term frequency, field weighting (name fields weigh more than description fields), and record activity.

The ranking is not directly controllable. `ORDER BY` within a `RETURNING` clause overrides it with an explicit sort, which loses the relevance ordering — usually the wrong trade for a search box, and the right one for a filtered list.

## Limits

- **20 SOSL queries** per synchronous transaction, 20 asynchronous
- **2,000 records** returned per query, across all objects
- **200 records per object** by default without an explicit `LIMIT`
- Search terms must be at least two characters after wildcards

The 20-query limit is much tighter than SOQL's 100, which is another reason a single multi-object SOSL beats several single-object ones.

## Practical guidance

**Use SOSL for user-entered search terms**, SOQL for known filters.

**Append `*` to user input** for type-ahead behaviour.

**Narrow the scope** — `NAME FIELDS` rather than `ALL FIELDS` where appropriate.

**Filter within `RETURNING`** to exclude closed and inactive records.

**Always `Test.setFixedSearchResults()`** in tests, or SOSL returns nothing.

**Search several objects in one query** rather than issuing several.

**Do not use `LIKE '%term%'` on a large object.** It is the pattern that fails at scale.
