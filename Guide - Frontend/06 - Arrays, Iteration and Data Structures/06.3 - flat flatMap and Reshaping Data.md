# flat, flatMap and Reshaping Data

Most frontend work is reshaping: an API returns one structure and the UI needs another. This note covers the flattening methods and the standard transformations between arrays and objects.

## flat

```js
[1, [2, 3], [4, [5]]].flat();          // [1, 2, 3, 4, [5]]  — depth 1 by default
[1, [2, [3, [4]]]].flat(2);            // [1, 2, 3, [4]]
[1, [2, [3, [4]]]].flat(Infinity);     // [1, 2, 3, 4]
[1, , 3].flat();                       // [1, 3] — removes holes
```

`flat(Infinity)` on deeply nested data is recursive internally and can be slow on very large structures, but the depth is almost always small in practice.

The hole-removal behavior is occasionally useful on its own: `arr.flat(0)` is a way to compact a sparse array.

## flatMap

`map` then `flat(1)`, in one pass:

```js
const allTags = posts.flatMap(p => p.tags);

// map + flat equivalent
const allTags = posts.map(p => p.tags).flat();
```

The genuinely useful property is that returning `[]` removes an element and returning multiple items expands one — so `flatMap` is filter and map simultaneously:

```js
// Filter + transform in one pass
const activeNames = users.flatMap(u => u.isActive ? [u.name] : []);

// One-to-many
const words = lines.flatMap(line => line.split(" "));
```

It only flattens one level. Nested arrays inside the result stay nested.

## Array to object

```js
// Index by id — the most common shape change in frontend code
const byId = Object.fromEntries(users.map(u => [u.id, u]));

// Equivalent with reduce
const byId = users.reduce((acc, u) => { acc[u.id] = u; return acc; }, {});
```

`Object.fromEntries` is the inverse of `Object.entries` and reads far better than the reduce. Note object keys are strings, so numeric ids become `"1"`, `"2"` — a `Map` preserves the original type ([[06.5 - Map and Set]]).

This indexing step is the core of state normalization ([[20.7 - State Normalization]]): store entities in a lookup keyed by id, and store order as an array of ids.

```js
const normalized = {
  byId: Object.fromEntries(users.map(u => [u.id, u])),
  allIds: users.map(u => u.id),
};
```

Lookups become O(1), updating one entity does not touch the others, and duplicated copies of the same entity disappear.

## Grouping

```js
const byRole = Object.groupBy(users, u => u.role);
// { engineer: [...], designer: [...] }

const byRoleMap = Map.groupBy(users, u => u.role);
```

`Object.groupBy` and `Map.groupBy` are recent additions. The `Object` version returns a null-prototype object, so inherited-property collisions are impossible. The manual equivalent:

```js
const byRole = users.reduce((acc, u) => {
  (acc[u.role] ??= []).push(u);
  return acc;
}, {});
```

The `??=` here is doing real work — it initializes the array only on first encounter.

## Object to array

```js
Object.keys(obj);      // ["a", "b"]
Object.values(obj);    // [1, 2]
Object.entries(obj);   // [["a", 1], ["b", 2]]

// Transform values
const doubled = Object.fromEntries(
  Object.entries(obj).map(([k, v]) => [k, v * 2])
);

// Filter keys
const picked = Object.fromEntries(
  Object.entries(obj).filter(([k]) => allowed.includes(k))
);
```

All three read only **own enumerable string-keyed** properties, so symbols and inherited properties are excluded ([[03.1 - Objects and Property Descriptors]]).

## Joining related collections

The pattern that most often gets written as a nested loop:

```js
// O(n * m) — a full scan of authors per post
const enriched = posts.map(p => ({
  ...p,
  author: authors.find(a => a.id === p.authorId),
}));

// O(n + m) — index once
const authorById = new Map(authors.map(a => [a.id, a]));
const enriched = posts.map(p => ({ ...p, author: authorById.get(p.authorId) }));
```

With 1,000 posts and 1,000 authors that is a million comparisons versus two thousand operations. This is the single most valuable reshaping habit to build.

## Building trees from flat lists

Comment threads, category hierarchies and file trees all arrive flat with a `parentId`:

```js
function buildTree(items) {
  const byId = new Map(items.map(i => [i.id, { ...i, children: [] }]));
  const roots = [];

  for (const node of byId.values()) {
    const parent = node.parentId != null ? byId.get(node.parentId) : null;
    (parent ? parent.children : roots).push(node);
  }

  return roots;
}
```

One pass to index, one pass to link. Note that `{ ...i, children: [] }` must happen during indexing so that parents and children reference the same node objects.

## Chunking and partitioning

```js
function chunk(arr, size) {
  return Array.from({ length: Math.ceil(arr.length / size) }, (_, i) =>
    arr.slice(i * size, i * size + size)
  );
}

function partition(arr, predicate) {
  return arr.reduce(
    ([pass, fail], item) => predicate(item)
      ? [[...pass, item], fail]
      : [pass, [...fail, item]],
    [[], []]
  );
}
```

The `partition` above is the readable-but-quadratic version; in production, push into two pre-allocated arrays instead ([[05.6 - Spread vs Rest]]).

`Array.from({ length: n }, fn)` is the standard way to generate a sequence — `new Array(n)` produces holes that `map` skips.

## How senior engineers actually use this

**They normalize server data once, at the boundary.** Components receive a shape designed for the UI, not the shape the API happened to return. This keeps transformation logic in one testable place instead of scattered through render functions.

**They index before joining, always.** Any `find` inside a `map` is a red flag in review.

**They memoize expensive reshaping in React.** A grouping or tree build in a component body runs every render; `useMemo` with the source array as a dependency is the standard fix ([[17.6 - useMemo]]).

**They prefer `Object.fromEntries` and `groupBy` over hand-rolled reduces** for readability, falling back to `reduce` only for shapes the built-ins do not cover.

## Common pitfalls

- `find` inside `map`, producing quadratic behavior.
- Object keys stringifying numeric ids, so `byId[1]` and `byId["1"]` are the same but `Object.keys` returns strings.
- `flat()` defaulting to depth 1 when deeper flattening was intended.
- `new Array(n).map(...)` doing nothing, because holes are skipped.
- Building a tree without sharing node references, so children attach to copies.
- Reshaping large arrays inside render without memoization.

## Interview angle

Reshaping shows up constantly in practical rounds — "group these records", "build a comment tree", "join these two lists". The expected signal is recognizing the O(n·m) trap and reaching for a `Map` index. Mentioning `Object.groupBy` and `Object.fromEntries` shows current knowledge, but be ready to write the `reduce` equivalent since they are recent.
