# Schedulers and Cron Systems

> **Revision tags:** #building-blocks #scheduling #distributed-systems  
> **Related:** [[04.6 - Job Scheduler]] | [[03.8 - Message Queues and Kafka]]

---

## What It Is

A scheduler triggers tasks at specified times or intervals — without a human or incoming request initiating them. The simplest form is Unix cron. At scale, distributed schedulers coordinate job execution across many workers.

```
Cron expression: "0 2 * * *"  → run at 2:00 AM every day
Job: GenerateDailyReport
  → scheduler triggers at 2:00 AM → worker executes → sends report
```

---

## Why It Exists

Many operations are time-driven, not event-driven:
- Send weekly digest emails every Monday 9 AM
- Archive records older than 90 days, nightly
- Refresh a materialized view every 5 minutes
- Expire unpaid orders after 30 minutes
- Poll an external API every minute for updates
- Run billing calculations at end of month

Without a scheduler, these require a long-running process with a sleep loop — fragile, unmonitored, doesn't survive restarts.

---

## The Problem with Simple Cron at Scale

Unix cron on a single machine has critical limitations in distributed production systems:

1. **Single point of failure:** If the cron machine dies, jobs don't run
2. **No distributed locking:** If you run cron on 3 servers for HA, all 3 fire the same job simultaneously (duplicate execution)
3. **No observability:** No history of what ran, when, and whether it succeeded
4. **No retries:** If a job fails, cron doesn't retry it
5. **No dependency management:** Job B depends on Job A finishing first — cron can't express this

## Distributed Scheduler Design

### The Core Components

```
[Scheduler / Trigger]  → determines when a job should run
[Job Store]            → persists job definitions and schedules
[Executor / Worker]    → actually runs the job
[Lock Service]         → ensures only one worker runs a job at a time
[State Store]          → tracks run history, status, results
```

### Leader Election for Trigger

Only one node should fire each trigger — the leader. Others are hot standbys.

```
All scheduler nodes compete for leadership via distributed lock (etcd/ZooKeeper)
Leader node: fires triggers, enqueues jobs
Follower nodes: stand by, watch for leader failure
If leader dies: followers re-elect, new leader takes over within seconds
```

### At-Least-Once Execution

The scheduler enqueues a job to a message queue. Workers pick it up and process it.

```
Scheduler → "run DailyReport at 2:00 AM" → Message Queue
Worker 1 picks up message → executes job → ACKs message
```

If Worker 1 crashes mid-execution: message redelivered → Worker 2 picks it up → executes again.

**Consequence:** Jobs may run more than once. Design jobs to be idempotent.

```python
def generate_daily_report(date):
    if ReportStore.exists(date):
        return  # already generated — idempotent guard
    report = compute_report(date)
    ReportStore.save(date, report)
```

### Exactly-Once Execution

Harder. Requires:
1. Idempotency key per job run (deduplication)
2. Transactional update: mark job as "running" + execute atomically
3. Distributed lock held for the duration of the job

Used for: financial calculations, billing, anything where double-execution causes real harm.

## Job Types

### Cron Jobs (Time-based)

Run at a fixed schedule expressed as a cron expression.

```
"0 * * * *"     → every hour at :00
"*/5 * * * *"   → every 5 minutes
"0 9 * * MON"   → every Monday at 9 AM
"0 0 1 * *"     → first day of every month at midnight
```

### Delayed Jobs (One-shot)

Run once, at a specific time in the future.

```python
# Schedule an order expiry check for 30 minutes from now
scheduler.run_at(
    job=expire_order,
    run_at=now() + timedelta(minutes=30),
    args={"order_id": 42}
)
```

### Periodic Jobs with Rate Limiting

Run frequently but with controlled parallelism — don't run a new instance if the previous one is still running.

```
Job: SyncExternalPrices
Schedule: every 1 minute
Concurrency: 1 (if previous run hasn't finished, skip)
```

## Production Scheduler Systems

### Celery Beat (Python)

- Beat process reads the schedule and enqueues tasks to Celery workers via Redis/RabbitMQ
- Good for: Python applications, medium scale
- Limitation: Beat is a single process — needs HA configuration to avoid SPOF

### APScheduler (Python)

- In-process scheduler, or distributed with a persistent job store (Redis, SQLAlchemy)
- Good for: simpler Python apps that don't need Celery's full ecosystem

### Kubernetes CronJob

- Native k8s object for scheduled containers
- Each run creates a Job → creates Pods → executes → cleans up
- Leader election handled by k8s controller manager
- Good for: containerized workloads with k8s infrastructure

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-report
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: reporter
            image: myapp/reporter:latest
          restartPolicy: OnFailure
```

### Apache Airflow

- DAG-based (Directed Acyclic Graph) workflow scheduler
- Jobs are Python DAGs with explicit dependencies between tasks
- Web UI for monitoring, backfilling, manual triggers
- Good for: data pipelines, ETL, ML workflows with complex task dependencies

### Temporal / Cadence

- Workflow engine for long-running, stateful workflows
- Survives process restarts — workflow state persisted externally
- Good for: business processes (order lifecycle, user onboarding), anything that spans hours/days/retries

## Handling Missed Jobs (Catch-up)

If the scheduler is down and misses scheduled runs, what happens on restart?

**Options:**
1. **Skip missed runs:** Just run the next scheduled time. Simple. Good for idempotent jobs where the missed run is not critical.
2. **Run once for the missed period:** On restart, fire exactly one catch-up run. Good for "should happen daily" jobs.
3. **Run all missed executions:** Backfill every missed schedule. Used in data pipelines where every run matters.

Configure this based on job semantics — most schedulers support all three modes.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Scheduler crash | Jobs don't fire until recovery | Leader election + hot standby |
| Worker crashes mid-job | Job not completed | At-least-once delivery + idempotent jobs |
| Job takes longer than interval | Concurrent executions pile up | Concurrency limit (skip if previous still running) |
| Clock skew | Job fires at wrong time | Use UTC everywhere, NTP sync |
| Job queue full | Scheduler can't enqueue new jobs | Backpressure, queue size monitoring |
