# Error Design

#backend #api-design #reliability

> **In one line:** An error is an API response like any other — it needs a stable machine-readable contract, enough context to act on, and a clear signal about whether retrying will help.

---

## The Idea

Errors get designed last, by whoever hit the failure case first, and the result is four shapes for the same problem.

```json
{"error": "not found"}
{"message": "Document not found", "code": 404}
{"errors": [{"detail": "not found"}]}
"Internal Server Error"
```

A client cannot write reliable handling against that, so it parses message strings — which then break when someone improves the wording.

💡 **The most important property of an error response is a stable machine-readable identifier.** Everything else — messages, hints, documentation links — is presentation and must be free to change.

---

## The Three Questions an Error Must Answer

1. **What went wrong?** — a stable code to branch on
2. **Can I retry?** — and if so, when
3. **What do I do about it?** — which field, which value, which permission

⚠️ **If a caller cannot answer all three from your response, they will guess, and their guess will be wrong.**

## Problem Details (RFC 9457)

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.conduit.local/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "2 fields are invalid",
  "request_id": "req_01HQZX...",
  "errors": [
    {"field": "title", "code": "too_long", "message": "Maximum 200 characters", "max": 200},
    {"field": "source_id", "code": "not_found", "message": "No source with that ID"}
  ]
}
```

| Field | Purpose |
|---|---|
| **`type`** | **The stable identifier.** A URI. Clients branch on this |
| `title` | Short human summary. May change |
| `status` | The HTTP status, repeated |
| `detail` | Explanation of *this* occurrence |
| Extensions | Anything else — structured and typed |

⚠️ **`type` is the contract; `title` and `detail` are not.** Document this explicitly, because clients will otherwise match on `detail` and you will be unable to improve your messages.

**Making the `type` URI resolve to documentation is a genuine kindness** — a developer pastes it and lands on the explanation.

## Error Codes

```python
class ErrorCode(str, Enum):
    VALIDATION_FAILED       = "validation_failed"
    RESOURCE_NOT_FOUND      = "resource_not_found"
    ALREADY_EXISTS          = "already_exists"
    QUOTA_EXCEEDED          = "quota_exceeded"
    RATE_LIMITED            = "rate_limited"
    UNAUTHENTICATED         = "unauthenticated"
    PERMISSION_DENIED       = "permission_denied"
    INTERNAL_ERROR          = "internal_error"
    DEPENDENCY_UNAVAILABLE  = "dependency_unavailable"
    OVERLOADED              = "overloaded"
```

- **Codes are added, never renamed or removed** — renaming one is a breaking change
- **Lowercase snake_case strings**, never integers
- **Field-level codes are separate** — `too_long`, `not_found`, `invalid_format`

⚠️ **Do not create a code per call site.** Fifty codes meaning "something was invalid" is worse than one plus a structured field list. **Twenty to forty top-level codes is healthy for a large API.**

### Retryability must be explicit

```json
{"type": ".../dependency-timeout", "status": 504, "retryable": true, "retry_after_seconds": 2}
```

💡 **Make retryability a field, not something the client infers from the status.** A 500 from a transient database blip is retryable; a 500 from a bug that will recur identically is not. **Only you know which**, and telling the client saves them from retrying forever or giving up on something that would have worked.

| Status | Retryable? |
|---|---|
| 400, 401, 403, 404, 409, 422 | No |
| 408, 429 | **Yes**, honour `Retry-After` |
| 500 | **Depends. Say so** |
| 502, 503, 504 | Yes, with backoff |

This connects to [[03.4 - Idempotency and Safe Retries]] — retryability is only meaningful if repeating the request is safe.

## Validation Errors

```json
{
  "errors": [{
    "field": "annotations[2].position.start",
    "code": "out_of_range",
    "message": "Must be between 0 and 4096",
    "min": 0, "max": 4096, "received": 9001
  }]
}
```

Four properties that make this good:

- **Path notation for nested fields** — a UI can highlight exactly the right input
- **Machine-readable field codes** — the client localises `out_of_range`; your English is the fallback
- **Structured constraints** — `min`, `max`, `pattern`, so no prose parsing
- **All errors at once** — a form revealing one error per submission is miserable

⚠️ **Never echo back a rejected value that could be sensitive.** `"received": 9001` is fine; `"received": "hunter2"` ends up in logs, devtools and error trackers.

### FastAPI's default is not good enough

```python
@app.exception_handler(RequestValidationError)
async def validation_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=422,
        media_type="application/problem+json",
        content={
            "type": f"{ERROR_BASE}/validation-failed",
            "title": "Validation failed",
            "status": 422,
            "request_id": request.state.request_id,
            "errors": [translate(e) for e in exc.errors()],
        },
    )
```

💡 **Doing this once, early, means your error contract does not leak your framework choice.** Migrating off Pydantic later becomes an internal change rather than a breaking API change.

## What Not to Leak

```python
# NEVER
except Exception as e:
    return {"error": str(e), "traceback": traceback.format_exc()}
```

Stack traces reveal file paths, library versions, database schema and internal service names — all useful to an attacker, none useful to a legitimate client.

```python
@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    request_id = request.state.request_id
    log.exception("unhandled error", extra={"request_id": request_id})
    return JSONResponse(500, {
        "type": f"{ERROR_BASE}/internal-error",
        "title": "Internal server error",
        "status": 500,
        "detail": "An unexpected error occurred",
        "request_id": request_id,          # ← the bridge
    })
```

💡 **The request ID is the entire mechanism.** The client reports `req_01HQZX`, you find the full trace in your logs. **Return a request ID on every response, not just errors** — it is also how a user reports a slow request or wrong data.

### Messages must not leak existence

```
403 Forbidden  → "you may not access document 42"  ← confirms it exists
404 Not Found  → "no such document"                ← reveals nothing
```

```
"No account with that email"     ← account enumeration
"Invalid email or password"      ← correct
```

## Internal vs External Errors

```python
class ConduitError(Exception):
    """Internal. Rich. Never serialised directly."""
    def __init__(self, code, message, *, status=500, retryable=False,
                 context=None, cause=None): ...


def to_problem(exc: ConduitError, request_id: str) -> dict:
    return {
        "type": f"{ERROR_BASE}/{exc.code.value.replace('_', '-')}",
        "title": TITLES[exc.code],
        "status": exc.status,
        "detail": exc.message if exc.status < 500 else GENERIC_5XX_DETAIL,
        "retryable": exc.retryable,
        "request_id": request_id,
    }
```

⚠️ **The `detail` for 5xx must be generic.** `connection to replica-3 refused` is excellent in logs and a disclosure in responses.

**The `context` dict is where structured internal detail lives** — the failing query, the timed-out upstream, the tenant ID. Logs and traces, never responses.

## In Production

### Errors are a metric

```python
api_errors_total.labels(code=..., status=..., endpoint=..., retryable=...).inc()
```

💡 **A 4xx spike is a signal about your clients or your documentation, not a page-worthy incident.** A rise in `validation_failed` usually means a client deployed a bug — or your API is confusing. A rise in `permission_denied` may mean someone is probing you.

**Track 4xx by client ID.** One client generating 90% of your validation errors is a support conversation, not an alert.

### The error catalogue as documentation

```python
@error(code=ErrorCode.QUOTA_EXCEEDED, status=413, retryable=False,
       docs="Organisation storage quota exceeded.")
class QuotaExceeded(ConduitError): ...
```

⚠️ **A hand-maintained catalogue will be wrong within a month.** Derive it from the definitions, publish it, and link every `type` URI to it.

### Partial failure

```json
{
  "data": {"documents": [...]},
  "warnings": [{"code": "source_unavailable", "message": "Showing cached results", "source_id": "src_7"}]
}
```

💡 **A 200 with warnings is often better than a 500.** If four of five sources responded, partial results with an explicit warning is more useful than failing entirely ([[11.6 - Graceful Degradation]]).

**The rule: the client must be able to tell the result is incomplete.** Silent partial results are worse than an error, because nothing looks wrong.

### Errors in streams

Once you have sent `200 OK`, you cannot change the status ([[03.6 - Compression and Streaming Responses]]).

```
data: {"token": "The"}
data: {"error": {"type": ".../model-overloaded", "retryable": true}}
data: [DONE]
```

⚠️ **Document that clients must inspect stream events for errors.** A client checking only the HTTP status treats a failed generation as a successful short one.

## Codebase

**Repo:** `kubernetes/kubernetes`, `googleapis/googleapis`, `stripe` (docs)

**Question to answer:** Compare three mature error models. How does each signal retryability, handle field-level validation, and avoid leaking internal detail? Then: what does Kubernetes' `StatusDetails` add over a flat error object?

**Read, in order:**

1. **Stripe error documentation** — the `type`/`code`/`decline_code` hierarchy. Payment errors carry structured detail a client can act on programmatically
2. `kubernetes/staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go` — `Status` and `StatusDetails`. **`Causes` is field-level validation and `RetryAfterSeconds` is explicit retryability** — this predates RFC 9457 and reached the same conclusions
3. `kubernetes/staging/src/k8s.io/apimachinery/pkg/api/errors/errors.go` — constructors per error kind and the `IsNotFound`/`IsConflict` helpers. **This is what a good client-side error API looks like**
4. `googleapis/googleapis/google/rpc/code.proto` and `error_details.proto` — canonical codes and typed details (`QuotaFailure`, `RetryInfo`). A strongly-typed alternative to Problem Details extensions
5. `saleor/saleor/graphql/core/types/common.py` — GraphQL's different approach, with errors in the body and a 200 status. Sets up [[05.4 - GraphQL - The Core Model]]

💡 The Kubernetes `IsNotFound(err)` helper is the detail worth stealing. **Shipping a client library with predicates rather than string comparison** means you can restructure your error model without breaking callers, and it makes correct handling the path of least resistance.

**Size:** 1 session.

## Exercise

**Drill 5.3 — An error contract you can rely on**

```
drills/05-errors/
├── model/{codes.py, exceptions.py, problem.py, handlers.py, catalogue.py}
├── validation/{translate.py, nested.py, tests/}
├── leakage/{audit.py, enumeration.py, FINDINGS.md}
├── client/{sdk.py, retry.py, tests/}
├── partial/warnings.py
└── README.md
```

**Part 1 — The model.** Error code enum with status, retryability and docs attached. Internal exception hierarchy. Problem Details serialisation. Handlers for validation, your exceptions, and unhandled exceptions.

**Generate the catalogue from the definitions and check in CI that it is current.**

**Part 2 — Validation done properly.** Path notation, field codes, structured constraints.

Test with a deeply nested payload — a document containing annotations containing positions — and confirm the path points at exactly the right element.

Then confirm **all** errors return, not just the first. **Compare the experience by actually filling in a form against each.**

**Part 3 — Audit for leakage.** A tool that exercises every endpoint with malformed, hostile and unauthorised input, then scans responses for file paths, stack frames, library names, SQL fragments, internal hostnames, and table names.

**Run it against your v0 API from drill 5.1 first.** It should find several.

Then the enumeration test: as a user in org A, probe for resources in org B. **Confirm 404 rather than 403, and confirm timing does not differ measurably** — a timing side channel defeats the 404 entirely.

**Part 4 — A client SDK.** Typed exceptions, predicate helpers (`is_not_found(err)`), retry driven by `retryable` and `Retry-After`.

**The compatibility test: change every `title` and `detail` string in the API.** The SDK's tests must still pass. If they do not, your client depends on presentation.

Then add an unknown error code and confirm it degrades to a generic error rather than crashing.

**Part 5 — Retry behaviour.** A transient 503 with `Retry-After`, a permanent 500 marked non-retryable, a 429 with a long `Retry-After`, and a 400.

**Confirm your client retries exactly the right ones and counts match.**

**Part 6 — Partial failure.** A search over five sources with two failing. Implement 500 and 200-with-warnings.

**The rule you write in `FINDINGS.md` matters more than the answer** — "return partial results when the client can tell what is missing and act on it" is the kind of principle that generalises.

**Part 7 — Stream errors.** Add error events to your SSE endpoint. Write a correct client, then a naive one that only checks the HTTP status, and **show it silently accepting a truncated result.**

**Done when:**
- The catalogue is generated and CI-checked
- Nested validation points at exact paths, all errors at once
- Your leakage audit finds problems in v0 and none in v1
- Enumeration shows 404 with no timing difference
- The SDK survives every message string changing, and handles unknown codes
- Retry counts are exactly correct across four failure types
- A naive stream client demonstrably misses an error your correct client catches
