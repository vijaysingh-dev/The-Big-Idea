# Observer Pattern

## At a Glance

|||
|---|---|
|**Type**|Behavioral|
|**Intent**|Define a one-to-many dependency so when one object changes state, dependents are notified automatically|
|**Also Known As**|Event, Publish-Subscribe, Listener|
|**Frequency in Backend**|★★★★★ — foundational for event-driven systems|

---

## The Problem It Solves

When something happens (order placed, user registered, payment failed), multiple systems need to react. Without Observer, the source directly calls each subscriber — tightly coupling it to everyone who cares.

```python
# ❌ Tight coupling — OrderService knows about every downstream system
class OrderService:
    def place_order(self, order):
        self._save(order)
        
        # Now knows about inventory, email, analytics, fraud — all coupled
        self.inventory_service.reserve(order)
        self.email_service.send_confirmation(order)
        self.analytics_service.track("order_placed", order)
        self.fraud_service.analyze(order)
        # Adding loyalty points = modify OrderService = risk breaking core logic
```

---

## Structure

```
┌─────────────┐  subscribes  ┌──────────────────────┐
│  Observer   │◀─────────────│     Subject          │
│ (interface) │              │  (Observable)        │
├─────────────┤              ├──────────────────────┤
│ + update()  │              │ - observers: list    │
└─────────────┘              │ + subscribe(obs)     │
       △                     │ + unsubscribe(obs)   │
┌──────┴──────┐              │ + notify()           │
│ConcreteObs  │              └──────────────────────┘
│             │                        △
│+ update()   │              ┌─────────┴──────────┐
└─────────────┘              │  ConcreteSubject    │
                             │ - state             │
                             │ + do_something()    │
                             └────────────────────-┘
```

## Full Backend Example: Order Event System

```python
# domain_events.py
from dataclasses import dataclass
from uuid import UUID
from decimal import Decimal
from datetime import datetime

@dataclass(frozen=True)
class OrderEvent:
    order_id: UUID
    occurred_at: datetime

@dataclass(frozen=True)
class OrderPlacedEvent(OrderEvent):
    user_id: UUID
    total: Decimal
    items: tuple   # immutable snapshot

@dataclass(frozen=True)
class OrderCancelledEvent(OrderEvent):
    reason: str
    refund_amount: Decimal


# event_bus.py
from abc import ABC, abstractmethod
from typing import Callable, Type, dict

EventHandler = Callable[[OrderEvent], None]

class EventBus:
    """
    In-process synchronous event bus.
    For production: swap internals for Kafka/SQS publisher.
    """
    
    def __init__(self):
        self._handlers: dict[Type[OrderEvent], list[EventHandler]] = {}
    
    def subscribe(self, event_type: Type[OrderEvent], handler: EventHandler):
        if event_type not in self._handlers:
            self._handlers[event_type] = []
        self._handlers[event_type].append(handler)
    
    def unsubscribe(self, event_type: Type[OrderEvent], handler: EventHandler):
        if event_type in self._handlers:
            self._handlers[event_type].remove(handler)
    
    def publish(self, event: OrderEvent):
        """Notify all handlers; failures in one don't block others."""
        handlers = self._handlers.get(type(event), [])
        for handler in handlers:
            try:
                handler(event)
            except Exception as e:
                logger.error(f"Handler {handler.__name__} failed for {event}: {e}")
                # In production: dead-letter queue, alert, retry


# handlers.py — each observer is independent
class InventoryReservationHandler:
    def __init__(self, inventory_repo: InventoryRepository):
        self._repo = inventory_repo
    
    def handle(self, event: OrderPlacedEvent):
        for item in event.items:
            self._repo.reserve(item.product_id, item.quantity, event.order_id)


class OrderConfirmationEmailHandler:
    def __init__(self, email_service: EmailService):
        self._email = email_service
    
    def handle(self, event: OrderPlacedEvent):
        self._email.send_order_confirmation(
            user_id=event.user_id,
            order_id=event.order_id,
            total=event.total
        )


class FraudAnalysisHandler:
    def __init__(self, fraud_service: FraudService):
        self._fraud = fraud_service
    
    def handle(self, event: OrderPlacedEvent):
        risk_score = self._fraud.analyze(event)
        if risk_score > 0.8:
            self._fraud.flag_for_review(event.order_id)


class LoyaltyPointsHandler:
    """New requirement: add points. Zero changes to OrderService."""
    def __init__(self, loyalty_repo: LoyaltyRepository):
        self._repo = loyalty_repo
    
    def handle(self, event: OrderPlacedEvent):
        points = int(event.total)  # 1 point per rupee
        self._repo.add_points(event.user_id, points, f"Order {event.order_id}")


# order_service.py — clean, unaware of downstream
class OrderService:
    def __init__(self, repo: OrderRepository, event_bus: EventBus):
        self._repo = repo
        self._bus = event_bus
    
    def place_order(self, command: PlaceOrderCommand) -> Order:
        order = Order.create(command)
        self._repo.save(order)
        
        # Publish — doesn't know who listens
        for event in order.get_events():
            self._bus.publish(event)
        
        return order


# wiring.py (composition root)
bus = EventBus()

inventory_handler = InventoryReservationHandler(inventory_repo)
email_handler = OrderConfirmationEmailHandler(email_service)
fraud_handler = FraudAnalysisHandler(fraud_service)
loyalty_handler = LoyaltyPointsHandler(loyalty_repo)

bus.subscribe(OrderPlacedEvent, inventory_handler.handle)
bus.subscribe(OrderPlacedEvent, email_handler.handle)
bus.subscribe(OrderPlacedEvent, fraud_handler.handle)
bus.subscribe(OrderPlacedEvent, loyalty_handler.handle)
```

## Sync vs Async Observer

```
In-process (sync):           Message Queue (async):
───────────────────          ──────────────────────
OrderService                 OrderService
    │ publish()                  │ publish to Kafka/SQS
    │                            │
    ├──► InventoryHandler        └──► Kafka topic "order.placed"
    │    (same thread)                       │
    ├──► EmailHandler                ┌───────┼───────┐
    │    (same thread)               ▼       ▼       ▼
    └──► FraudHandler         Inventory  Email  Fraud
         (same thread)        Consumer  Consumer Consumer
                              (independent services, retry, DLQ)

Use sync when:               Use async when:
- All in one service         - Microservices
- Handlers are fast          - Handlers can be slow
- Failure should bubble up   - Loose coupling needed
- Simplicity is priority     - Scale independently
```

## Observer vs Pub/Sub vs Event Bus

||Observer|Pub/Sub|Event Bus|
|---|---|---|---|
|Coupling|Subject knows observer interface|No direct knowledge|No direct knowledge|
|Transport|In-process|Network (Kafka, SQS)|In-process or network|
|Delivery|Synchronous|Asynchronous|Either|
|Ordering|Guaranteed|Usually not|Usually not|
|Use when|Single service|Cross-service|Single service, extensible|

---

## When NOT to Use Observer

- **Simple sequential steps** — just call them in order; Observer adds indirection
- **Order matters strictly** — Observer doesn't guarantee order (without extra work)
- **All observers must succeed** — if email fails should the order still be placed? Maybe direct call is clearer
- **Heavy debugging environment** — event flows can be hard to trace

---

## Tradeoffs

|Pro|Con|
|---|---|
|Decoupled — publisher doesn't know subscribers|Hard to trace "what happens when X"|
|Open/Closed — new subscriber = no changes|Memory leaks if observers aren't unsubscribed|
|Single responsibility — each handler does one thing|Unexpected cascades — one event triggers another|
|Easy to add/remove features|Debugging requires following event chain|

---

## Common Mistakes

1. **Not unsubscribing** — in long-lived apps, removed UI components/services still hold references → memory leak
2. **Subscribers modifying shared state** — multiple subscribers updating same entity = race condition
3. **Throwing from a subscriber** — blocks other subscribers; always catch-and-log inside observer
4. **Circular events** — Observer A emits event B, Observer B emits event A → infinite loop
5. **Order-dependent observers** — if correctness depends on subscriber order, Observer is wrong pattern

## Interview Perspective

> "Design a notification system."

Observer is the right answer. Show:

- Event types (`OrderEvent`, `PaymentEvent`)
- Observer interface (`NotificationHandler.handle(event)`)
- Concrete handlers per channel
- Event bus with subscribe/unsubscribe/publish

Follow-up: "What if email takes 30s?" → Async via queue. Handler publishes to SQS, email worker consumes separately.

## Senior Engineer Lens

In production systems, "Observer" often means Kafka/SQS topics. The pattern is the same; the transport is a message broker. Key production concerns:

- **Idempotency** — events may be delivered more than once; handlers must be idempotent
- **Dead-letter queues** — failed events should not be silently lost
- **At-least-once vs at-most-once** — design for at-least-once, handle duplicates
- **Event schema evolution** — add fields, don't remove or rename (consumers may lag)
