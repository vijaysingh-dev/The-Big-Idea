## What It Is

Redis is an in-memory data store that supports multiple data structures. It's most commonly used as a cache, but its rich data type support makes it the Swiss Army knife of distributed systems infrastructure.

**Key properties:**
- All data in memory → sub-millisecond latency
- Single-threaded command execution → naturally atomic operations, no locking needed at the Redis level
- Optional persistence (RDB snapshots, AOF log)
- Pub/sub built in
- Lua scripting for atomic multi-step operations
- Clustering for horizontal scale

## Core Data Structures

### String

The most basic type. Holds any byte sequence (text, JSON, binary, integers).

```redis
SET user:42:name "Vijay"
GET user:42:name           # "Vijay"
INCR page:views            # atomic increment (thread-safe counter)
SETNX lock:resource "1"    # set if not exists (distributed lock primitive)
SET session:abc123 "{...}" EX 3600  # set with TTL (expires in 1 hour)
```

**Use cases:** Caching any value, counters, rate limit windows, session tokens, distributed locks.

### Hash

Key-value pairs within a key. Like a dictionary nested inside Redis.

```redis
HSET user:42 name "Vijay" email "v@example.com" age 26
HGET user:42 name          # "Vijay"
HGETALL user:42            # all fields
HINCRBY user:42 login_count 1  # increment one field
```

**Use cases:** User profiles, session data, object representation. More memory-efficient than storing JSON in a String when you need to update individual fields.

### List

Ordered list of strings. Can be used as a queue (LPUSH + BRPOP) or stack (LPUSH + LPOP).

```redis
LPUSH notifications:user:42 "Your order shipped"
LPUSH notifications:user:42 "Payment confirmed"
LRANGE notifications:user:42 0 9  # get latest 10
BRPOP task_queue 30               # blocking pop (waits up to 30s)
```

**Use cases:** Activity feeds, notification queues, simple message queues, recent items.

### Set

Unordered collection of unique strings. O(1) membership check.

```redis
SADD user:42:following 10 20 30
SISMEMBER user:42:following 20   # 1 (is following)
SCARD user:42:following          # 3 (count)
SINTER user:42:following user:99:following  # mutual follows
```

**Use cases:** Tags, unique visitors, mutual friends, deduplication.

### Sorted Set (ZSet)

Set where each member has a floating-point score. Members ordered by score.

```redis
ZADD leaderboard 1500.0 "alice"
ZADD leaderboard 2200.0 "bob"
ZADD leaderboard 1800.0 "carol"
ZREVRANGE leaderboard 0 9 WITHSCORES   # top 10 with scores
ZRANK leaderboard "carol"               # rank (0-indexed)
ZADD rate_limit:user:42 1705000000 "req:001"  # score = timestamp
```

**Use cases:** Leaderboards, priority queues, rate limiting (sliding window), time-ordered feeds, range queries by score.

### Bitmap

Bit-level operations on a string. Memory-efficient for tracking boolean states over large sets.

```redis
SETBIT user:42:login:2024-01-15 0 1   # user logged in today
GETBIT user:42:login:2024-01-15 0     # 1
BITCOUNT user:42:login:2024-01-15     # days active (count set bits)
```

**Use cases:** Daily active user tracking, feature flag state per user, bloom filter approximation.

### HyperLogLog

Probabilistic data structure for counting unique items with ~0.81% error using very little memory.

```redis
PFADD unique_visitors:2024-01-15 "user:42" "user:99" "user:55"
PFCOUNT unique_visitors:2024-01-15  # ~3 (approximate)
```

**Use cases:** Unique visitor counts, cardinality estimation at scale. A billion unique items costs only ~12KB of memory.

## Key Expiry and TTL

```redis
SET session:abc123 "{...}" EX 3600    # expires in 3600 seconds
EXPIRE user:42:cache 300               # set TTL on existing key
TTL user:42:cache                      # remaining seconds (-1 = no expiry, -2 = doesn't exist)
PERSIST user:42:cache                  # remove TTL (make permanent)
```

Always set TTLs on cache keys. A Redis instance without TTLs fills up and starts evicting data unexpectedly.

## Atomic Operations and Lua Scripting

Redis executes one command at a time — no concurrent command interleaving. But multi-step operations across commands are not atomic by default.

**Problem:**
```redis
# These two commands are NOT atomic — another client can run between them
GET rate_limit:user:42   # get current count
INCR rate_limit:user:42  # increment
```

**Solution 1: Lua script (atomic execution)**
```lua
-- Rate limiter: increment and check in one atomic operation
local count = redis.call("INCR", KEYS[1])
if count == 1 then
  redis.call("EXPIRE", KEYS[1], ARGV[1])
end
return count
```

**Solution 2: MULTI/EXEC (transaction)**
```redis
MULTI
INCR rate_limit:user:42
EXPIRE rate_limit:user:42 60
EXEC
```
Note: Redis transactions don't roll back on error — they're not ACID. They just queue commands and execute them atomically.

## Redis as a Distributed Lock

```python
# Acquire lock
acquired = redis.set("lock:order:42", "unique_token", nx=True, ex=30)
if not acquired:
    raise LockNotAcquiredError()

try:
    # Critical section
    process_order(42)
finally:
    # Release lock (only if we own it — check token)
    script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """
    redis.eval(script, 1, "lock:order:42", "unique_token")
```

The Lua script ensures the check-and-delete is atomic — avoids releasing another client's lock.

## Redis Pub/Sub

```python
# Publisher
redis.publish("order_events", json.dumps({"event": "OrderPlaced", "order_id": 42}))

# Subscriber
pubsub = redis.pubsub()
pubsub.subscribe("order_events")
for message in pubsub.listen():
    process(message['data'])
```

**Limitations:**
- No persistence — messages are lost if no subscriber is connected at publish time
- No consumer groups — all subscribers get all messages (fan-out only)
- No replay — can't re-read old messages

For reliable messaging, use Kafka or Redis Streams instead. Pub/Sub is appropriate for ephemeral fan-out (live notifications, cache invalidation signals).

## Redis Streams

A persistent, log-based data structure added in Redis 5.0. More powerful than Pub/Sub.

```redis
XADD orders * event OrderPlaced order_id 42 user_id 99
XREAD COUNT 10 STREAMS orders 0    # read from beginning
XREADGROUP GROUP consumers worker1 COUNT 10 STREAMS orders >  # consumer group
XACK orders consumers msg_id       # acknowledge processed
```

**Supports:** Persistence, consumer groups, message acknowledgment, replay from offset.  
**Use case:** Lightweight alternative to Kafka for lower-throughput event streaming.

## Redis Cluster

Redis Cluster shards data across multiple nodes using consistent hashing (16,384 hash slots).

```
Key → CRC16(key) % 16384 → hash slot → assigned node
```

- Automatic failover (each master has replicas)
- No single point of failure
- Linear write scale (add more shards)
- Cross-slot operations (multi-key) not supported unless keys share a hash tag: `{user:42}:orders` and `{user:42}:profile` share a slot

---

## Persistence Options

| Mode | How | Durability | Performance |
|---|---|---|---|
| **No persistence** | Data in memory only | None — lost on restart | Fastest |
| **RDB (snapshots)** | Periodic full dump to disk | Data loss since last snapshot | Fast (async) |
| **AOF (append-only file)** | Log every write command | Near-zero loss (fsync every second) | Moderate |
| **RDB + AOF** | Both | Best of both | Moderate |

For a cache: no persistence is fine (can be rebuilt from source). For a primary data store: AOF required.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Redis server crash (no persistence) | All cache data lost | Cache-aside handles gracefully — rebuild from DB |
| Redis OOM | Eviction of hot keys | Monitor memory, set maxmemory + eviction policy |
| Replication lag | Replica serves stale data | Use synchronous replication for critical data |
| Thundering herd on restart | All cache misses simultaneously flood DB | Pre-warm cache, circuit breaker on DB |
| Network partition in cluster | Some keys inaccessible | Multi-AZ replicas, circuit breaker |
