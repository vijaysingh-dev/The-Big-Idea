# Generics, Type Casting and Reflection

## Generics, such as they are

Apex has generics for **collections only**. You cannot write your own generic class or method.

```java
List<Warranty_Claim__c> claims;
Map<Id, List<Case>> casesByAccount;
Set<String> statuses;
```

```java
// Not possible in Apex
public class Repository<T> { }
public <T> T firstOrNull(List<T> items) { }
```

This is a genuine limitation with real consequences: reusable utilities must work with `SObject` or `Object` and rely on casting at the call site.

```java
public with sharing class CollectionUtils {

    // works across objects, at the cost of losing compile-time typing
    public static Map<Id, SObject> byId(List<SObject> records) {
        Map<Id, SObject> result = new Map<Id, SObject>();
        for (SObject record : records) {
            result.put(record.Id, record);
        }
        return result;
    }
}
```

```java
Map<Id, SObject> claimsById = CollectionUtils.byId(claims);
Warranty_Claim__c claim = (Warranty_Claim__c) claimsById.get(claimId);
```

The cast at every call site is the price. For `Map<Id, SObject>` specifically, the built-in constructor is better:

```java
Map<Id, Warranty_Claim__c> claimsById = new Map<Id, Warranty_Claim__c>(claims);
```

Typed, no cast, no utility needed. Reaching for a generic helper where a platform construct exists is a common over-engineering trap.

## Casting collections

Apex allows casting a `List<SObject>` to a concrete list type, which is what makes dynamic SOQL usable:

```java
List<SObject> results = Database.query(dynamicQuery);
List<Warranty_Claim__c> claims = (List<Warranty_Claim__c>) results;
```

The reverse — a concrete list to `List<SObject>` — is implicit and always safe.

Casting to the wrong concrete type throws `TypeException` at runtime, not at compile time. With dynamic queries this is a real risk, and validating the object name before querying is the defence. See [[08.7 - Dynamic SOQL]].

## Type.forName and newInstance

Apex's reflection mechanism, and the basis of every configuration-driven design on the platform.

```java
Type strategyType = Type.forName('PremiumContractDiscount');
if (strategyType == null) {
    throw new ConfigurationException('Unknown strategy class');
}

DiscountStrategy strategy = (DiscountStrategy) strategyType.newInstance();
```

Requirements: the class must be **public or global**, and it must have a **public no-argument constructor**. A class with only a parameterized constructor cannot be instantiated this way.

`Type.forName` returns null for an unknown name rather than throwing, so a null check is mandatory. For a namespaced class:

```java
Type t = Type.forName('mypackage', 'ClaimProcessor');
```

Combined with Custom Metadata this gives runtime pluggability:

```java
public with sharing class HandlerFactory {

    public static List<ClaimHandler> handlersFor(String context) {
        List<ClaimHandler> handlers = new List<ClaimHandler>();

        for (Claim_Handler_Config__mdt config : [
            SELECT Handler_Class__c FROM Claim_Handler_Config__mdt
            WHERE Context__c = :context AND Active__c = true
            ORDER BY Execution_Order__c
        ]) {
            Type handlerType = Type.forName(config.Handler_Class__c);
            if (handlerType == null) {
                AutomationLogger.logError('HandlerFactory', null,
                    'Unknown handler class: ' + config.Handler_Class__c);
                continue;
            }
            handlers.add((ClaimHandler) handlerType.newInstance());
        }
        return handlers;
    }
}
```

Adding a handler becomes deploying a class and a metadata record, with no change to the factory. Logging rather than throwing on an unknown class means one bad configuration row does not break the whole pipeline — a judgement call worth making deliberately either way. See [[18.10 - Custom Metadata Driven Architecture]].

## Schema describe

The other half of reflection: inspecting the org's own metadata at runtime.

```java
// Object level
Schema.SObjectType claimType = Warranty_Claim__c.SObjectType;
Schema.DescribeSObjectResult describe = claimType.getDescribe();

describe.getName();              // 'Warranty_Claim__c'
describe.getLabel();
describe.getKeyPrefix();         // 'a0X'
describe.isCustom();
describe.isAccessible();
describe.isCreateable();
describe.isUpdateable();
describe.isDeletable();
describe.getRecordTypeInfos();
describe.getChildRelationships();
```

```java
// Field level
Map<String, Schema.SObjectField> fields = describe.fields.getMap();
Schema.DescribeFieldResult fieldDescribe = fields.get('status__c').getDescribe();

fieldDescribe.getType();         // Schema.DisplayType.PICKLIST
fieldDescribe.getLabel();
fieldDescribe.isNillable();
fieldDescribe.isAccessible();
fieldDescribe.isUpdateable();
fieldDescribe.getPicklistValues();
fieldDescribe.getReferenceTo();  // for lookups: the target object types
```

**The field map key is lowercase.** `fields.get('Status__c')` returns null; `fields.get('status__c')` works. This catches people constantly.

## Describe cost

Describe calls consume CPU, and `getGlobalDescribe()` walks every object in the org.

```java
// Expensive — never in a loop
Map<String, Schema.SObjectType> global = Schema.getGlobalDescribe();
```

Cache it in a static, once per transaction:

```java
public with sharing class SchemaCache {

    private static Map<String, Schema.SObjectType> globalDescribe;
    private static Map<String, Map<String, Schema.SObjectField>> fieldCache =
        new Map<String, Map<String, Schema.SObjectField>>();

    public static Schema.SObjectType objectType(String objectName) {
        if (globalDescribe == null) {
            globalDescribe = Schema.getGlobalDescribe();
        }
        return globalDescribe.get(objectName.toLowerCase());
    }

    public static Schema.SObjectField field(String objectName, String fieldName) {
        String key = objectName.toLowerCase();
        if (!fieldCache.containsKey(key)) {
            fieldCache.put(key, objectType(objectName).getDescribe().fields.getMap());
        }
        return fieldCache.get(key).get(fieldName.toLowerCase());
    }
}
```

Where the object is known at compile time, the direct form avoids `getGlobalDescribe()` entirely:

```java
Schema.SObjectType type = Warranty_Claim__c.SObjectType;   // cheap
Schema.SObjectType type = Schema.getGlobalDescribe().get('Warranty_Claim__c');  // expensive
```

Prefer the first wherever possible. `getGlobalDescribe()` is only necessary when the object name is genuinely dynamic.

## Dynamic sObject manipulation

```java
SObject record = Warranty_Claim__c.SObjectType.newSObject();
record.put('Status__c', 'Submitted');
record.put('Claim_Amount__c', 150000);
Object value = record.get('Claim_Amount__c');
insert record;
```

`put` and `get` take field API names as strings. A wrong name throws `SObjectException` at runtime — there is no compile-time check, which is the trade you make for dynamism.

Traversing a relationship dynamically works with `getSObject`:

```java
SObject asset = claim.getSObject('Asset__r');
String serial = (String) asset?.get('SerialNumber');
```

`getSObjects` returns a child list from a subquery:

```java
List<SObject> parts = claim.getSObjects('Claim_Parts__r');
```

## Common dynamic patterns

**A field-agnostic copy utility**, which appears in most codebases:

```java
public with sharing class RecordUtils {

    public static void copyFields(SObject source, SObject target, Set<String> fieldNames) {
        Map<String, Object> populated = source.getPopulatedFieldsAsMap();

        for (String fieldName : fieldNames) {
            // copying only populated fields avoids overwriting the target with nulls
            if (populated.containsKey(fieldName)) {
                target.put(fieldName, populated.get(fieldName));
            }
        }
    }
}
```

**Finding all lookup fields to a given object**, useful for cascade logic and impact analysis:

```java
public static List<String> lookupsTo(String childObject, String parentObject) {
    List<String> matches = new List<String>();

    for (Schema.SObjectField field : SchemaCache.objectType(childObject).getDescribe().fields.getMap().values()) {
        Schema.DescribeFieldResult d = field.getDescribe();
        if (d.getType() != Schema.DisplayType.REFERENCE) {
            continue;
        }
        for (Schema.SObjectType target : d.getReferenceTo()) {
            if (target.getDescribe().getName() == parentObject) {
                matches.add(d.getName());
            }
        }
    }
    return matches;
}
```

`getReferenceTo()` returns a list because polymorphic lookups point at several types.

## Where dynamic code is worth it

**Justified:** generic components rendering any object, managed packages adapting to subscriber schema, configuration-driven handler registration, admin tooling and org scanners, data migration utilities.

**Not justified:** anything where the object and fields are known. Dynamic code loses compile-time validation, is harder to read, costs CPU, and hides field dependencies from impact analysis. A dynamic query where a static one would do is a net loss.

The test: **would a field rename break this silently?** If yes, and the object is known, use static references.

## Practical guidance

**Prefer `Object__c.SObjectType`** to `getGlobalDescribe()`.

**Cache describes in statics**, never call them in a loop.

**Remember the field map key is lowercase.**

**Null-check `Type.forName()`** — it returns null rather than throwing.

**Use `Map<Id, ConcreteType>(records)`** rather than a generic utility.

**Use `getPopulatedFieldsAsMap()`** to distinguish unqueried from null.

**Reach for dynamic code only when the schema is genuinely unknown at compile time.**
