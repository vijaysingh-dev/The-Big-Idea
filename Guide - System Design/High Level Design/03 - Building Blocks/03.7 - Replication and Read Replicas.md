# Replication and Read Replicas

> **Revision tags:** #building-blocks #databases #replication  
> **Related:** [[03.6 - Databases SQL and NoSQL]] | [[01.11 - Distributed Concepts]] | [[01.6 - Consistency Models]]

---

## What It Is

Replication is the process of copying data from one database node (the **leader/primary**) to one or more other nodes (**followers/replicas**), so that multiple nodes hold copies of the same data.

```
All writes → [Primary]
                 │  (replication stream)
                 ├──→ [Replica 1] ← serves reads
                 └──→ [Replica 2] ← serves reads
```

---

## Why It Exists

- **High availability:** If the primary fails, a replica can be promoted to primary. No data loss (if sync replication), minimal downtime.
- **Read scalability:** Distribute read traffic across replicas. 10 replicas = ~10× read throughput.
- **Disaster recovery:** Keep a replica in a different AZ or region. Hardware failure in one location doesn't lose data.
- **Analytics isolation:** Run heavy analytics queries on a replica without slowing down the production primary.

---

## Single-Leader Replication (Most Common)

One node accepts all writes (primary). Changes flow to followers.

```
Application writes → Primary → WAL/binlog → Replica 1
                                           → Replica 2
Application reads  → Any replica (or primary for strong consistency)
```

**Write-ahead log (WAL) shipping:** Most relational DBs replicate by shipping the WAL — the log of all changes — to replicas. Replicas replay the log to stay in sync.

### Sync vs Async Replication

**Synchronous:**
```
Client writes → Primary → waits for Replica ACK → confirms to client
```
- Durability: Replica is guaranteed up-to-date before client gets confirmation
- Risk: If replica is slow/down, write is blocked
- Use: When losing even one committed write is unacceptable (financial ledgers)

**Asynchronous (default for most DBs):**
```
Client writes → Primary → confirms to client → replicates to Replica (soon)
```
- Performance: Write latency is just local disk write
- Risk: If primary crashes before replication, the last writes are lost (data loss window = replication lag)
- Use: Most production systems accept this tradeoff

**Semi-synchronous (MySQL default):**
- Wait for at least one replica to acknowledge. Balances durability and performance.

---

## Replication Lag

In async replication, replicas trail behind the primary. The gap is the **replication lag**.

Typical lag: **< 100ms** in same datacenter under normal load.  
Under heavy write load or across regions: **seconds to minutes**.

### Problems Caused by Replication Lag

**Read-your-writes violation:**
```
User updates profile photo (write → primary)
User immediately refreshes profile (read → replica, which hasn't caught up)
User sees old photo → confusing experience
```
**Solution:** Route reads to primary for the same user's session for a short window after a write. Or use sticky routing (user always reads from primary for their own data).

**Monotonic reads violation:**
```
User reads from Replica A (sees latest post)
User refreshes, routed to Replica B (further behind, doesn't see the post)
Post appears to disappear
```
**Solution:** Route each user's reads to the same replica consistently (via user ID hash).

**Causality violation:**
```
User A writes comment in response to User B's post
Observer sees User A's comment before seeing User B's post
```
**Solution:** Causal consistency tracking (vector clocks). Most systems don't implement this — they accept the inconsistency.

## Read Replica Architecture

```
[App Servers]
    │
    ├── writes ──→ [Primary DB]
    │                   │
    │                   ├──→ [Read Replica 1] ←── analytics queries
    │                   └──→ [Read Replica 2] ←── user read traffic
    │
    └── reads ──→ [Read Replica 1 or 2] (via read-routing logic or ProxySQL)
```

### Read/Write Splitting

Application (or middleware) routes writes to primary, reads to replicas.

**Application-level:**
```python
def get_user(user_id):
    return read_db.query("SELECT * FROM users WHERE id = ?", user_id)

def update_user(user_id, data):
    write_db.execute("UPDATE users SET ... WHERE id = ?", user_id, data)
```

**Middleware (ProxySQL, RDS Proxy):** Transparent routing based on whether the query is read-only. No application code change needed.

### How Many Replicas?

- Read:write = 10:1 → 2–3 replicas usually sufficient
- Analytics running on the same DB → dedicate a separate replica
- Cross-region reads → one replica per region
- HA requirement → minimum 1 replica in a different AZ

## Failover

When the primary fails, a replica must be promoted to primary.

### Manual Failover

Human triggers promotion. Safe but slow (minutes to hours RTO).

### Automatic Failover

An orchestration layer (Patroni for PostgreSQL, MHA for MySQL, AWS RDS Multi-AZ) detects primary failure and promotes a replica.

```
1. Primary health check fails (timeout)
2. Consensus: majority of replicas agree primary is dead
3. Most up-to-date replica elected as new primary
4. DNS / VIP updated to point to new primary
5. Old replicas reconfigure to follow new primary
6. Application reconnects (connection pool reconnect logic)
```

**Failover time:** 20–60 seconds for automatic failover in well-configured systems.

### Split-Brain Risk

If network partition causes replicas to believe the primary is dead (but it isn't), two nodes may both act as primary → data divergence.

**Prevention:** Fencing — ensure old primary is definitively stopped before new one takes over. In cloud: forcibly stop the instance via API before promoting replica.

---

## Multi-Leader Replication

Multiple nodes accept writes. Changes replicate between leaders.

```
DC1: [Leader A] ←───────────────→ [Leader B] :DC2
     (accepts writes)             (accepts writes)
```

**Use cases:**
- Multi-datacenter deployment where each region needs to accept writes
- Offline-capable applications (mobile, desktop) — device is a "leader" that syncs when online
- Collaborative editing

**Challenge: Write conflicts.**  
Two clients update the same record on different leaders simultaneously → conflict on sync.

**Conflict resolution strategies:**
- Last-write-wins (LWW): Timestamp-based. Silently loses data.
- Custom conflict resolution: Application-defined merge logic (Git merge concept)
- CRDTs: Data structures that merge mathematically without conflict (grow-only sets, counters)

---

## Leaderless Replication (Dynamo-style)

No single primary. Any node accepts reads and writes. Consistency via quorums.

```
Write quorum W: write must succeed on W of N nodes
Read quorum  R: read from R of N nodes, take latest version

If W + R > N → at least one node overlaps → always reads latest write
```

**Common config:** N=3, W=2, R=2 (quorum = majority).

**Used by:** Cassandra, DynamoDB, Riak.

**Repair mechanisms:**
- **Read repair:** On a read, if one node returns a stale value, update it to the latest.
- **Anti-entropy:** Background process continuously compares and syncs nodes.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Primary crashes | Writes unavailable until failover | Automatic failover (Patroni, RDS Multi-AZ) |
| Replica lags heavily | Stale reads, read-your-writes violations | Monitor replication lag, route recent reads to primary |
| Split-brain | Two primaries, data divergence | Fencing, STONITH, cloud-level instance termination |
| Replication slot fills disk | Primary disk full → crash | Monitor slot lag, set max_replication_slots limit |
| Failover to stale replica | Data loss equal to replication lag at time of failure | Synchronous replication for critical data |

---

## Interview Expectations

- Know the difference between sync and async replication and the durability/performance tradeoff
- Know what replication lag is and its practical consequences (read-your-writes)
- Know the read replica pattern for read scalability
- Know automatic failover at a high level (health check → consensus → promote → update routing)
- Know that multi-leader introduces write conflicts
