# Rapid Fire - Async and Event Loop

## The event loop

**Explain the event loop.**
JavaScript has one call stack. Host APIs (timers, network, DOM) do work off-thread and queue callbacks when done. The loop takes one task from the task queue only when the stack is empty, runs it to completion, drains the entire microtask queue, then possibly renders. → [[01.4 - The Event Loop]]

**Microtasks vs macrotasks?**
One task per loop iteration; **all** microtasks after each task. Microtasks: promise reactions, `await` continuations, `queueMicrotask`, `MutationObserver`. Tasks: timers, DOM events, `postMessage`, I/O. → [[01.6 - Microtasks vs Macrotasks]]

**Predict the output:**

```js
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
```

`1, 4, 3, 2`. Synchronous first, then microtasks drain fully, then one task. → [[01.6 - Microtasks vs Macrotasks]]

**Can a microtask starve the loop?**
Yes. Because the queue is drained completely, a microtask that queues another microtask hangs the page permanently — no rendering, no input, no timers. The same pattern with `setTimeout` is harmless, because each callback is a separate task. → [[01.6 - Microtasks vs Macrotasks]]

**Does `setTimeout(fn, 0)` run immediately?**
No. It queues the callback after a *minimum* delay; it runs when the loop next takes a task. Nested timers are clamped to 4ms, and background tabs throttle heavily. → [[01.5 - Web APIs and the Task Queue]]

**Where does rendering happen?**
Inside the loop, between tasks: run a task, drain microtasks, then `requestAnimationFrame` callbacks, style, layout, paint, composite. This is why `await` does not let the browser repaint — it yields to microtasks, not to a task boundary. → [[01.7 - The Rendering Cycle]]

**Is JavaScript single-threaded?**
The engine executes your JS on one thread with one call stack. The runtime is multi-threaded — network, timers and I/O happen elsewhere and hand results back via the loop. → [[01.1 - How JavaScript Runs]]

## Promises

**What is a promise?**
An object representing a future value, in one of three states — pending, fulfilled, rejected — settling exactly once and immutably. Reactions are always scheduled as microtasks, never called synchronously. → [[04.2 - Promises from First Principles]]

**Does the promise executor run asynchronously?**
No. The function passed to `new Promise` runs immediately and synchronously. Only the `.then` reactions are deferred. → [[04.2 - Promises from First Principles]]

**How does error handling work in a chain?**
A rejection skips forward to the nearest rejection handler. `.catch` **recovers** — whatever it returns fulfills the next promise — so re-throw to keep the chain rejected. Put `.catch` last unless you deliberately want to recover mid-chain. → [[04.3 - Promise Chaining and Error Handling]]

**`.then(f, g)` vs `.then(f).catch(g)`?**
The two-argument form attaches both to the same promise, so `g` cannot catch errors thrown by `f`. The chained form can. → [[04.3 - Promise Chaining and Error Handling]]

**Does `fetch` reject on a 404?**
No. It rejects only on network-level failure — DNS, connection refused, CORS block, abort. A 404 or 500 is a successful HTTP exchange, so you must check `res.ok` yourself. → [[04.3 - Promise Chaining and Error Handling]]

**`Promise.all` vs `allSettled` vs `any` vs `race`?**
`all` — fulfils when all fulfil, rejects fast on the first rejection. `allSettled` — never rejects, returns status per entry. `any` — first fulfilment wins, rejects with `AggregateError` if all fail. `race` — first to settle either way. → [[04.5 - Promise Combinators]]

**Does `Promise.race` cancel the losers?**
No. They run to completion and their results are discarded. Pair it with `AbortController`, or use `AbortSignal.timeout` for the common timeout case. → [[04.5 - Promise Combinators]]

**Are promises cancellable?**
No. A settled promise cannot be undone and a pending one cannot be stopped. Cancellation is layered on with `AbortController`, which the operation must explicitly honour. → [[04.6 - AbortController and Cancellation]]

**Are promises lazy?**
No, eager — the work starts when the promise is created, not when you `.then` it. `Promise.all` coordinates waiting; it does not start anything. → [[04.2 - Promises from First Principles]]

## async/await

**How does `async/await` work internally?**
Syntax over promises, compiled to a generator-driven state machine. The function runs synchronously until the first `await`, then returns a pending promise and schedules its continuation as a microtask. → [[04.4 - async await]]

**Predict the output:**

```js
async function f() { console.log("A"); await null; console.log("B"); }
f();
console.log("C");
```

`A, C, B`. Everything before the first `await` is synchronous, even when awaiting a non-promise. → [[04.4 - async await]]

**What is wrong with this?**

```js
const user = await getUser();
const posts = await getPosts();
```

If they are independent, this serializes two requests that could run in parallel. Use `Promise.all`. → [[04.4 - async await]]

**Why does this not work?**

```js
items.forEach(async (item) => { await save(item); });
```

`forEach` ignores the returned promise, so it completes immediately and rejections go unhandled. Use `for...of` for sequential or `Promise.all(items.map(...))` for parallel. → [[04.4 - async await]]

**Why can't `useEffect` take an async function?**
An async function returns a promise, and React expects the return value to be a cleanup function. Use an inner async IIFE and return the cleanup separately. → [[17.4 - useEffect Pitfalls]]

**Does `await` yield to rendering?**
No. It yields to the microtask queue, which drains before the browser paints. Only a real task boundary — a timer, a message, `scheduler.yield` — lets a frame through. → [[01.6 - Microtasks vs Macrotasks]]

**What is top-level await?**
Awaiting at module scope, available in ES modules only. Every importing module waits for it, so it delays the dependent graph and should stay off critical paths. → [[04.4 - async await]]

## Cancellation and concurrency

**How do you cancel a fetch?**
`AbortController` — pass its `signal` to `fetch` and call `abort()`. It is one-way and permanent, so create a new controller per operation. Treat `AbortError` as normal control flow, never as an error to report. → [[04.6 - AbortController and Cancellation]]

**How do you fix the search race condition?**
A slow earlier response can resolve after a fast later one and overwrite it. Abort on every dependency change — not just on unmount. Query libraries do this automatically by aborting when the key changes. → [[04.6 - AbortController and Cancellation]]

**Which errors should you retry?**
Network failures, 5xx, 429 and timeouts. Never 4xx (they fail identically) and never aborts. Retrying a POST needs an idempotency key, or you risk duplicates. → [[24.3 - Retries Timeouts and Cancellation]]

**Why does retry backoff need jitter?**
Without random spread, every client that failed at the same moment retries at the same moment, knocking a recovering server over again. → [[04.7 - Async Concurrency Patterns]]

**How do you limit concurrency?**
Track in-flight promises in a `Set` and `await Promise.race(inFlight)` when the limit is reached, freeing one slot at a time. Unbounded `Promise.all` over user-sized data hits rate limits. → [[04.7 - Async Concurrency Patterns]]

**How do you deduplicate in-flight requests?**
Store the promise in a `Map` keyed by request, return the same promise to every caller, and delete on `finally`. This works because a promise settles once and can have any number of consumers. → [[04.7 - Async Concurrency Patterns]]

## React scheduling

**What is automatic batching?**
React 18 batches state updates everywhere — timers, promises, native handlers — not just inside React event handlers. `flushSync` opts out when you need the DOM updated immediately. → [[18.6 - Batching and the Update Queue]]

**What is concurrent rendering?**
Rendering is interruptible: React can pause, resume, prioritize and discard renders. It does not make rendering faster; it stops non-urgent work from blocking urgent input. → [[18.5 - Concurrent Rendering and the Scheduler]]

**`useTransition` vs `useDeferredValue`?**
One wraps the state **update**, the other wraps a **value**. Use `useTransition` when you own the setter, `useDeferredValue` when the value arrives as a prop. → [[22.5 - useDeferredValue]]

**What is tearing?**
Two components reading a mutable external value during an interrupted render observing different values, then committing together. `useSyncExternalStore` prevents it by forcing a consistent snapshot. → [[17.12 - Lesser Known Hooks]]
