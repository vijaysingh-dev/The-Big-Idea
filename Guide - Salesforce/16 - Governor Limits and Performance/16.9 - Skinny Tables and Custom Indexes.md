# Skinny Tables and Custom Indexes

## The underlying problem

Salesforce stores every tenant's data in shared tables. A query that cannot use an index scans rows belonging to everyone on that instance, which is why **selectivity** matters more here than in a single-tenant database.

The query optimizer decides whether an index is usable based on how many rows the filter is likely to return. Below the threshold it uses the index; above it, it scans. See [[08.9 - Indexes and Selective Queries]].

## What is indexed by default

```
Id
Name
OwnerId
CreatedDate, CreatedById
LastModifiedDate, LastModifiedById
SystemModstamp
RecordTypeId
Division
Lookup and master-detail relationship fields
External ID fields
Unique fields
```

**External ID and Unique fields are indexed**, which is why marking an integration key as an external ID improves both upsert and query performance. See [[10.3 - Upsert, Merge and External IDs]].

## Selectivity thresholds

Roughly:

```
Standard index    selective under ~30% of the first million rows,
                  then ~15% beyond that, capped around 1 million rows
Custom index      selective under ~10%, capped around 333,000 rows
```

The numbers are approximate and Salesforce adjusts them. The principle is stable: **an index is only used when the filter is narrow enough to be worth it.**

A `Status__c = 'Open'` filter on an object where 80% of records are Open is not selective, and no index will help. That is a data model problem rather than an indexing one.

## Custom indexes

Requested through Salesforce Support, not created in Setup.

```
"Please add a custom index on Warranty_Claim__c.ERP_Claim_Id__c
 in org 00D5g0000012345.

 Query: SELECT Id, Status__c FROM Warranty_Claim__c
        WHERE ERP_Claim_Id__c = :externalId
 Volume: 4.2 million records
 Frequency: ~40,000 times per day from the ERP integration
 Current cost: full scan, 8-12 seconds"
```

Support wants the query, the volume, the frequency, and the current performance. A request without them is usually declined.

**What cannot be indexed:**

```
Multi-select picklists
Long text and rich text areas
Encrypted text fields
Formula fields referencing other objects
Formula fields that are non-deterministic
Some currency fields in multi-currency orgs
```

**Formula fields can be indexed** when deterministic — referencing only fields on the same record, with no `TODAY()`, `NOW()`, or cross-object traversal. That restriction is why a formula intended for filtering should be kept simple. See [[06.4 - Cross-Object Formulas and Limits]].

## Two-column indexes

For queries filtering on two fields together, a composite index is more effective than two separate ones:

```sql
SELECT Id FROM Warranty_Claim__c
WHERE Account__c = :accountId AND Status__c = 'Submitted'
```

A two-column index on `(Account__c, Status__c)` serves this directly. Support can create these, and the column order matters — the more selective field should come first.

## Null handling

**Standard indexes do not include null values by default.** A query filtering `WHERE Field__c = null` cannot use the index and scans.

```sql
-- Cannot use a standard index
SELECT Id FROM Warranty_Claim__c WHERE Approved_Date__c = null

-- Can, if the field is indexed
SELECT Id FROM Warranty_Claim__c WHERE Approved_Date__c < :today
```

Custom indexes **can** be built to include nulls, which must be requested explicitly. Worth asking for when a null check is a common filter — an integration finding unprocessed records, for example:

```sql
SELECT Id FROM Warranty_Claim__c WHERE ERP_Confirmation__c = null LIMIT 200
```

Without a null-inclusive index that query scans the whole table, and it is exactly the shape an idempotent integration uses.

## Skinny tables

A **skinny table** is a Salesforce-maintained copy of an object containing a subset of frequently queried fields, kept in sync automatically.

```
Warranty_Claim__c            60 fields, 8 million rows
Skinny table                 6 fields, 8 million rows
```

The query optimizer uses it transparently — no code change, no different object name.

**What they solve:** wide objects where reports and list views are slow because every query reads a large row. Reading six columns rather than sixty is a substantial difference at volume.

**They also avoid a join.** Salesforce stores standard and custom fields separately; a query touching both requires a join, and a skinny table containing both eliminates it.

## Skinny table constraints

```
Up to 100 columns
Cannot contain fields from other objects
Not copied to sandboxes automatically — must be requested per org
Enabled through Salesforce Support
Not available on all objects
```

**Supported types:** Checkbox, Date, Date and Time, Email, Number, Percent, Phone, Picklist (single-select), Text, Text Area, URL.

**Not supported:** multi-select picklists, long text areas, rich text, and some others.

**The sandbox point causes real confusion.** A skinny table exists in production and not in a refreshed sandbox, so a query performing acceptably in production is slow in the sandbox and vice versa. Requesting them per environment is part of the setup.

## Requesting one

```
"Please create a skinny table on Warranty_Claim__c in org 00D5g0000012345.

 Fields: Id, Claim_Number__c, Status__c, Claim_Amount__c,
         Claim_Date__c, Account__c, Asset__c

 Volume: 8.1 million records
 Use case: the Open Claims list view and the weekly claims report,
           both currently timing out for users in the EMEA region
 Current performance: list view 14s, report times out at 10 minutes"
```

The same evidence requirement as a custom index. Support declines vague requests, and rightly — a skinny table is real storage and real maintenance overhead on their side.

## When they help, and when they do not

**Help:** reports and list views on wide, high-volume objects; queries selecting a consistent small set of fields; anything where the row width is the cost.

**Do not help:** a query already selective on an indexed field; queries needing fields not in the skinny table, which fall back to the main table; small objects, where row width is irrelevant.

**They are a last resort**, after the query itself has been made selective. A non-selective query against a skinny table is still non-selective.

## Diagnosing first

The sequence that avoids requesting an index you do not need.

**1. Read the query plan.**

```bash
sf apex run --file query-plan.apex --target-org production
```

Or the Developer Console's Query Plan tool, which shows the cardinality, the cost, and which index — if any — the optimizer chose. A cost above 1 means a table scan. See [[08.10 - Query Plan Tool and Query Optimization]].

**2. Check whether the filter is selective at all.**

```sql
SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
SELECT COUNT() FROM Warranty_Claim__c
```

If the filter returns 60% of the rows, no index will help. The fix is a narrower filter, a different access pattern, or a data model change.

**3. Try a more selective filter.**

Adding a date bound frequently turns a scan into an index seek:

```sql
-- Non-selective across 8 million rows
WHERE Status__c = 'Submitted'

-- Selective, and usually what the user actually wants
WHERE Status__c = 'Submitted' AND Claim_Date__c = LAST_N_DAYS:90
```

**4. Remove the anti-patterns.**

```sql
-- Leading wildcard: cannot use an index
WHERE Claim_Number__c LIKE '%00042'

-- Negative operators: cannot use an index
WHERE Status__c != 'Closed'
WHERE Status__c NOT IN ('Closed', 'Cancelled')

-- A formula field in the filter: only indexable if deterministic
WHERE Days_Open_Formula__c > 30
```

`!=` and `NOT IN` are the ones that appear most often, and rewriting them as a positive `IN` list is usually possible:

```sql
WHERE Status__c IN ('Submitted', 'Under Review', 'Approved')
```

**5. Then consider an index or skinny table.**

## Archiving as an alternative

Often the better answer, and the one people reach for last.

An object with 40 million rows where users only ever query the last two years does not need a skinny table. It needs the older rows moved out.

```java
public with sharing class ClaimArchiveBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Number__c, Claim_Amount__c, Asset__c, Claim_Date__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Closed' AND Claim_Date__c < LAST_N_YEARS:3
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        // big objects hold the history at a fraction of the cost, with no index pressure
        Database.insertImmediate(toArchiveRecords(scope));
        Database.delete(scope, false);
        Database.emptyRecycleBin(scope);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

Fewer rows makes every query faster, every index more selective, every report quicker, and every data load cheaper. See [[23.4 - Archiving with Big Objects and External Storage]] and [[02.15 - Big Objects]].

## Practical guidance

**Diagnose before requesting.** Read the query plan and check whether the filter is selective at all.

**Remove the anti-patterns first** — leading wildcards, `!=`, `NOT IN`.

**Add a date bound** to narrow a filter; it is the most common fix.

**Mark integration keys as External ID**, which indexes them for free.

**Request custom indexes with evidence** — query, volume, frequency, current performance.

**Ask for null-inclusive indexes** where a null filter is a common access pattern.

**Consider a skinny table** for wide, high-volume objects with slow reports and list views.

**Request skinny tables per environment.** They do not follow a sandbox refresh.

**Consider archiving first.** Fewer rows beats better indexes.
