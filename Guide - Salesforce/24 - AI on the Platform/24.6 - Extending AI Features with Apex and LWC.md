# Extending AI Features with Apex and LWC

## Where custom code fits

The configured features cover a lot. The four places code is genuinely needed:

```
Grounding that requires logic       computing context a merge field cannot express
Custom agent actions                anything with validation, bulk behaviour, or security
Invoking prompts from code          triggering generation from Apex
The review surface                  rendering, editing, and accepting generated output
```

**Everything else should be configuration.** A prompt template written in Apex when Prompt Builder would do is a maintenance liability with no benefit.

## Grounding through Apex

The most common custom code in an AI feature.

```java
public with sharing class ClaimGroundingService {

    public class Request {
        @InvocableVariable(required=true) public Id claimId;
    }

    public class Result {
        @InvocableVariable public String context;
    }

    @InvocableMethod(label='Build Claim Context'
                     description='Assembles coverage and history context for a claim prompt')
    public static List<Result> build(List<Request> requests) {
        Set<Id> claimIds = new Set<Id>();
        for (Request request : requests) {
            claimIds.add(request.claimId);
        }

        // one query set for the whole batch, since a prompt may be invoked in bulk
        Map<Id, Warranty_Claim__c> claims = ClaimSelector.withAssetAndAccount(claimIds);
        Map<Id, Machine_Coverage__c> coverage =
            CoverageSelector.activeByAsset(assetIds(claims));
        Map<Id, List<Warranty_Claim__c>> history =
            ClaimSelector.recentByAsset(assetIds(claims), 3);

        List<Result> results = new List<Result>();
        for (Request request : requests) {
            Result result = new Result();
            result.context = format(
                claims.get(request.claimId),
                coverage.get(claims.get(request.claimId)?.Asset__c),
                history.get(claims.get(request.claimId)?.Asset__c)
            );
            results.add(result);
        }
        return results;
    }
}
```

**Bulkified like any invocable method**, because a prompt template invoked from a record-triggered flow receives the whole batch.

**The formatting is the interesting part:**

```java
private static String format(
    Warranty_Claim__c claim,
    Machine_Coverage__c coverage,
    List<Warranty_Claim__c> priorClaims
) {
    List<String> lines = new List<String>();

    // explicit absence, so the model knows the value is missing rather than unknown
    lines.add('Coverage level: ' + (coverage?.Coverage_Level__c ?? 'No active coverage'));
    lines.add('Coverage limit: ' + (coverage?.Coverage_Limit__c?.format() ?? 'n/a'));
    lines.add('Coverage ends: ' + (coverage?.Coverage_End_Date__c?.format() ?? 'n/a'));

    if (priorClaims == null || priorClaims.isEmpty()) {
        lines.add('Prior claims on this machine: none');
    } else {
        lines.add('Prior claims on this machine (most recent first):');
        for (Warranty_Claim__c prior : priorClaims) {
            lines.add(String.format('  {0} on {1}: {2}, {3}',
                new List<Object>{
                    prior.Claim_Number__c,
                    prior.Claim_Date__c.format(),
                    prior.Status__c,
                    prior.Approved_Amount__c?.format() ?? 'no amount approved'
                }));
        }
    }

    return String.join(lines, '\n');
}
```

**Three principles:**

**State absences explicitly.** `'No active coverage'` rather than an empty string — the model treats a blank as unknown and fills it in.

**Label everything.** The model reads the label as much as the value.

**Bound the volume.** Three prior claims, not thirty. More context is not better; it dilutes and it costs.

**Never ground on what should not leave.** Masking is pattern-based and will not catch an internal margin field. See [[24.5 - Einstein Trust Layer]].

## Invoking a prompt from Apex

```java
public with sharing class ClaimSummaryService {

    private static final String TEMPLATE = 'Claim_Resolution_Summary';

    public static String generate(Id claimId) {
        ConnectApi.EinsteinPromptTemplateGenerationsInput input =
            new ConnectApi.EinsteinPromptTemplateGenerationsInput();

        ConnectApi.WrappedValue claimValue = new ConnectApi.WrappedValue();
        claimValue.value = claimId;
        input.inputParams = new Map<String, ConnectApi.WrappedValue>{
            'Input:Warranty_Claim__c' => claimValue
        };

        ConnectApi.EinsteinLlmAdditionalConfigInput config =
            new ConnectApi.EinsteinLlmAdditionalConfigInput();
        // traceable per feature in the audit trail
        config.applicationName = 'ClaimSummary';
        input.additionalConfig = config;

        try {
            ConnectApi.EinsteinPromptTemplateGenerationsRepresentation response =
                ConnectApi.EinsteinLLM.generateMessagesForPromptTemplate(TEMPLATE, input);

            return response.generations.isEmpty() ? null : response.generations[0].text;

        } catch (Exception e) {
            // generation failure must not break the calling operation
            Logger.error('ClaimSummary', claimId, e);
            return null;
        }
    }
}
```

**It behaves as a callout**, so it cannot follow DML in the same transaction and it belongs in a Queueable when triggered by a save:

```java
public static void handleStatusTransitions(
    List<Warranty_Claim__c> claims, Map<Id, Warranty_Claim__c> priorClaims
) {
    Set<Id> newlyClosed = findNewlyClosed(claims, priorClaims);

    if (!newlyClosed.isEmpty()) {
        // generation is a callout, and DML has already occurred
        System.enqueueJob(new ClaimSummaryQueueable(newlyClosed));
    }
}
```

See [[13.14 - Apex Callouts]] and [[12.3 - Queueable Apex]].

**Returning null on failure rather than throwing** is the right default — a summary that could not be generated should not prevent a claim from closing.

## Parsing structured output

Where the prompt requests JSON:

```java
public class ClaimAssessment {
    public String summary;
    public String sentiment;
    public Boolean requiresEscalation;
    public String escalationReason;

    public Boolean isAvailable = true;

    public static ClaimAssessment unavailable() {
        ClaimAssessment assessment = new ClaimAssessment();
        assessment.isAvailable = false;
        return assessment;
    }
}
```

```java
private static ClaimAssessment parse(String response) {
    if (String.isBlank(response)) {
        return ClaimAssessment.unavailable();
    }

    try {
        // a model can return fences or preamble despite the instruction not to
        String cleaned = response
            .replaceAll('(?s)```json|```', '')
            .trim();

        return (ClaimAssessment) JSON.deserialize(cleaned, ClaimAssessment.class);

    } catch (Exception e) {
        Logger.warn('ClaimAssessment', 'Unparseable response: ' + response.left(500));
        return ClaimAssessment.unavailable();
    }
}
```

**Always assume the response may not parse.** The instruction reduces the probability and does not eliminate it, and an unhandled `JSONException` in a Queueable is a silent failure.

**Return an `unavailable` state rather than null**, so the caller can distinguish "not generated" from "generated as empty".

## Custom agent actions

Covered in [[24.4 - Agentforce Fundamentals]]; the extension points worth restating.

**The descriptions are functional:**

@InvocableMethod(

              + 'Use when a customer asks whether something is covered, or before '
              + 'helping them submit a claim.'

    SELECT Id, Claim_Number__c, Status__c, Contact__c
    FROM Warranty_Claim__c WHERE Claim_Number__c = :request.claimNumber
    WITH USER_MODE LIMIT 1

// a claim number is guessable; ownership is verified rather than assumed
if (claims.isEmpty() || claims[0].Contact__c != request.contactId) {

ValidationOutcome outcome = ClaimValidationService.validate(request);

## The review surface

The component that renders generated output, and where most of the LWC work sits.

```javascript
import { LightningElement, api } from 'lwc';
import generateSummary from '@salesforce/apex/ClaimSummaryService.generate';
import saveSummary from '@salesforce/apex/ClaimSummaryService.save';
import submitFeedback from '@salesforce/apex/AiFeedbackService.submit';

export default class ClaimSummaryDraft extends LightningElement {
    @api recordId;

    draft;
    generationId;
    isGenerating = false;
    error;

    async handleGenerate() {
        this.isGenerating = true;
        this.error = undefined;

        try {
            const result = await generateSummary({ claimId: this.recordId });

            if (!result?.text) {
                // a failed generation gets an explanation, not a blank panel
                this.error = 'A summary could not be generated. Please write one manually.';
                return;
            }

            this.draft = result.text;
            this.generationId = result.generationId;

        } catch (e) {
            this.error = reduceErrors(e);
        } finally {
            this.isGenerating = false;
        }
    }

    handleEdit(event) {
        this.draft = event.target.value;
    }

    async handleAccept() {
        await saveSummary({ claimId: this.recordId, summary: this.draft });
        await submitFeedback({ generationId: this.generationId, isPositive: true });
        this.dispatchEvent(new CustomEvent('summarysaved'));
    }

    async handleReject() {
        await submitFeedback({
            generationId: this.generationId,
            isPositive: false,
            comment: this.rejectionReason
        });
        this.draft = undefined;
    }
}
```

```html
<template>
    <lightning-card title="Claim Summary">
        <div class="slds-p-horizontal_small">

            <template lwc:if={isGenerating}>
                <lightning-spinner alternative-text="Generating"></lightning-spinner>
            </template>

            <template lwc:elseif={error}>
                <div class="slds-notify slds-notify_alert slds-theme_warning" role="alert">
                    <p>{error}</p>
                </div>
            </template>

            <template lwc:elseif={draft}>
                <!-- editable, because a draft is a starting point rather than an answer -->
                <lightning-textarea
                    label="Generated draft — review before saving"
                    value={draft}
                    onchange={handleEdit}>
                </lightning-textarea>

                <div class="slds-m-top_small">
                    <lightning-button variant="brand" label="Save"
                                      onclick={handleAccept}></lightning-button>
                    <lightning-button label="Discard"
                                      onclick={handleReject}></lightning-button>
                    <lightning-button label="Regenerate"
                                      onclick={handleGenerate}></lightning-button>
                </div>
            </template>

            <template lwc:else>
                <lightning-button label="Generate summary"
                                  onclick={handleGenerate}></lightning-button>
            </template>
        </div>
    </lightning-card>
</template>
```

**The design decisions that matter:**

**Generated output is editable.** Presenting it as final invites acceptance without reading.

**Label it as generated.** "Generated draft — review before saving" sets the expectation.

**Regenerate is available**, because the first attempt is sometimes poor and the user should not have to abandon the feature.

**Failure is explained**, not blank.

**Feedback is captured on accept and on reject**, which is the only quality signal available.

**Generate is on demand**, not on load — which controls cost and avoids generating for records nobody looks at.

## Feedback capture

```java
public with sharing class AiFeedbackService {

    @AuraEnabled
    public static void submit(String generationId, Boolean isPositive, String comment) {
        ConnectApi.EinsteinLlmFeedbackInput feedback = new ConnectApi.EinsteinLlmFeedbackInput();
        feedback.id = generationId;
        feedback.feedback = isPositive
            ? ConnectApi.EinsteinLlmFeedbackEnum.GOOD
            : ConnectApi.EinsteinLlmFeedbackEnum.BAD;
        feedback.feedbackText = comment;
        feedback.source = 'ClaimSummaryComponent';
        feedback.appGenerationId = generationId;

        ConnectApi.EinsteinLLM.submitFeedback(feedback);
    }
}
```

**Feedback lands in the audit trail in Data Cloud**, alongside the prompt and response.

**Reviewing the negative feedback is how a prompt improves** — the resolved prompt for a rejected response usually explains the problem in one glance. See [[24.7 - Designing AI Features Responsibly on CRM Data]].

## Testing

**Grounding services test normally**, and they are the most valuable thing to test:

```java
@IsTest
static void groundingStatesAbsentCoverageExplicitly() {
    Warranty_Claim__c claim = TestDataFactory.createClaimWithoutCoverage();

    ClaimGroundingService.Request request = new ClaimGroundingService.Request();
    request.claimId = claim.Id;

    Test.startTest();
    List<ClaimGroundingService.Result> results =
        ClaimGroundingService.build(new List<ClaimGroundingService.Request>{ request });
    Test.stopTest();

    Assert.isTrue(results[0].context.contains('No active coverage'),
        'Missing coverage must be stated explicitly, or the model will invent it');
}
```

**Parsing tests are worth having**, because the failure is otherwise silent:

```java
@IsTest
static void anUnparseableResponseYieldsAnUnavailableAssessment() {
    ClaimAssessment assessment = ClaimAssessmentService.parseForTest('I cannot help with that.');

    Assert.isFalse(assessment.isAvailable,
        'A non-JSON response should produce an unavailable assessment, not an exception');
}
```

**The generation call itself cannot be tested meaningfully** — it is a callout to a model, and mocking it tests the mock. Injecting the generation behind an interface lets the surrounding logic be tested without it:

```java
public interface IGenerationService {
    String generate(Id recordId);
}
```

```java
@TestVisible
private static IGenerationService generationService = new PromptTemplateService();
```

See [[18.8 - Dependency Injection and Testability]].

## Cost and invocation design

Generative calls are consumption-priced, and where they are invoked from determines the bill.

```
On demand, from a button                  the user asked; low volume
On record view                            every page load; expensive and wasteful
From a record-triggered flow              every save; expensive at volume
From a batch job                          bounded, and predictable
```

**On demand is the default worth adopting.** A summary generated on every page load, for a record viewed forty times, is thirty-nine wasted generations.

**Caching where the input has not changed:**

```java
public static String getOrGenerate(Id claimId) {
    Warranty_Claim__c claim = ClaimSelector.byId(claimId);

    // regenerate only when the record changed since the summary was written
    if (String.isNotBlank(claim.AI_Summary__c)
        && claim.AI_Summary_Generated_At__c > claim.LastModifiedDate) {
        return claim.AI_Summary__c;
    }

    return generateAndStore(claimId);
}
```

## Practical guidance

**Ground with logic in Apex**, bulkified, with absences stated explicitly.

**Bound the context.** More is not better.

**Never ground on what should not leave the platform.**

**Set `applicationName`** on every invocation.

**Treat generation as a callout** — async after DML, and failure must not break the caller.

**Parse defensively**, and return an unavailable state rather than throwing.

**Make generated output editable**, labelled as generated, and regenerable.

**Capture feedback on accept and reject.**

**Generate on demand**, and cache where the input has not changed.

**Test the grounding and the parsing**, and inject the generation itself.
