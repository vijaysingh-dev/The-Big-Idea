# Queueable Apex

## The general-purpose async tool

```java
public with sharing class ErpNotificationQueueable
    implements Queueable, Database.AllowsCallouts {

    private final Set<Id> claimIds;

    public ErpNotificationQueueable(Set<Id> claimIds) {
        this.claimIds = claimIds;
    }

    public void execute(QueueableContext context) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Claim_Amount__c, Status__c, Asset__r.SerialNumber
            FROM Warranty_Claim__c WHERE Id IN :claimIds
        ];

        if (claims.isEmpty()) {
            return;
        }

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/claims/approved');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(ClaimPayload.from(claims)));
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() >= 300) {
            throw new IntegrationException(
                'ERP notification failed: ' + res.getStatusCode() + ' ' + res.getBody()
            );
        }

        markSynced(claims);
    }
}
```

```java
Id jobId = System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

`Database.AllowsCallouts` is a marker interface — no methods, just permission to make HTTP calls. Omitting it produces a runtime failure the first time a callout is attempted, which is easy to miss in a job that only sometimes calls out.

## What it gives you over future

**Any parameter type.** sObjects, custom classes, collections of anything — passed through the constructor and serialized with the job.

**A job Id**, returned by `enqueueJob`, which makes monitoring possible:

```java
Id jobId = System.enqueueJob(new ErpNotificationQueueable(claimIds));

AsyncApexJob job = [
    SELECT Id, Status, NumberOfErrors, ExtendedStatus, CompletedDate
    FROM AsyncApexJob WHERE Id = :jobId
];
```

**Chaining**, with guaranteed order.

**Transaction Finalizers**, giving a guaranteed post-execution hook for retry and logging. See [[12.6 - Transaction Finalizers]].

**Callable from other async contexts**, within limits.

## Serialization

The job object is serialized when enqueued and deserialized when it runs. Two consequences.

**Everything held must be serializable.** Primitives, collections, sObjects, and custom classes are fine. A `Type`, a `Blob` over a certain size, or a reference to something non-serializable throws at enqueue time.

**Held sObjects are a snapshot.** A record passed to the constructor holds the values as of enqueue, not as of execution.

```java
// The claim's status may have changed by the time this runs
public ErpNotificationQueueable(List<Warranty_Claim__c> claims) {
    this.claims = claims;
}

// Better: ids, re-queried in the job's own transaction
public ErpNotificationQueueable(Set<Id> claimIds) {
    this.claimIds = claimIds;
}
```

Passing Ids is the default recommendation. It keeps the payload small and guarantees the job works from current data.

The exception: when you genuinely need the values as they were — an audit snapshot, or a comparison against the current state.

## Chaining

A Queueable can enqueue exactly **one** more from within `execute`, and the chain is ordered.

```java
public with sharing class ClaimSyncQueueable implements Queueable, Database.AllowsCallouts {

    private final List<Id> remaining;
    private static final Integer CHUNK = 150;

    public ClaimSyncQueueable(List<Id> remaining) {
        this.remaining = remaining;
    }

    public void execute(QueueableContext context) {
        List<Id> batch = new List<Id>();
        List<Id> rest = new List<Id>();

        for (Integer i = 0; i < remaining.size(); i++) {
            if (i < CHUNK) {
                batch.add(remaining[i]);
            } else {
                rest.add(remaining[i]);
            }
        }

        ClaimSyncService.sync(new Set<Id>(batch));

        // test context executes only one chained level, so the guard prevents a failure there
        if (!rest.isEmpty() && !Test.isRunningTest()) {
            System.enqueueJob(new ClaimSyncQueueable(rest));
        }
    }
}
```

Chaining is how work exceeding one transaction's limits gets processed, and it needs a **termination condition**. A chain with no exit runs until the daily async allocation is exhausted, which affects every job in the org.

Ordering is guaranteed within a chain, which future methods cannot offer. This matters for sequenced integrations — header before lines, parent before children.

For volumes beyond a few thousand records, Batch Apex is the better tool: it chunks automatically, has proper monitoring, and does not depend on your chunking logic being right. See [[12.4 - Batch Apex]].

## Job Ids and monitoring

```java
public with sharing class ClaimSyncService {

    public static Id startSync(Set<Id> claimIds) {
        Id jobId = System.enqueueJob(new ClaimSyncQueueable(new List<Id>(claimIds)));

        // storing the job id makes the run traceable from the records it touched
        insert new Integration_Run__c(
            Job_Id__c = jobId,
            Context__c = 'ClaimSync',
            Record_Count__c = claimIds.size(),
            Started_At__c = Datetime.now()
        );

        return jobId;
    }
}
```

Storing the job Id against a run record is what turns "the sync failed" into "run 4417 failed at 09:32 with this message on these 150 records". Without it, `AsyncApexJob` gives you a failure with no business context.

```sql
SELECT Id, ApexClass.Name, Status, ExtendedStatus, NumberOfErrors,
       CreatedDate, CompletedDate, CreatedBy.Name
FROM AsyncApexJob
WHERE JobType = 'Queueable' AND CreatedDate = LAST_N_DAYS:7
ORDER BY CreatedDate DESC
```

`ExtendedStatus` holds the failure message.

## Delayed enqueue

A Queueable can be scheduled to run after a delay, up to ten minutes:

```java
System.enqueueJob(new ErpNotificationQueueable(claimIds), 5);   // 5 minute delay
```

Useful for a deliberate pause — letting related automation settle before reading, or backing off after a transient failure.

For anything longer than ten minutes, use Scheduled Apex or a scheduled path on a flow.

## Limits

Async transaction limits: 200 SOQL queries, 12 MB heap, 60 seconds CPU, 200 DML statements.

Enqueue caps:

- **50 jobs enqueued per synchronous transaction**
- **1 job enqueued from within a Queueable** — the chain
- **The 250,000 daily async execution limit**, shared org-wide

The chain depth is effectively unlimited, which is why the termination condition matters.

## Where Queueable is the right answer

**Callouts from a trigger.** The most common use, because the callout cannot happen in the save transaction.

**Setup-object DML** after normal DML. See [[10.7 - Mixed DML and Setup Objects]].

**Work with rich parameters** that future cannot accept.

**Sequenced work**, using the chain.

**Anything needing failure handling**, using a Finalizer.

**Moderate-volume processing** — thousands rather than millions.

## Where it is not

**Very large volumes.** Batch Apex chunks automatically and monitors properly.

**Scheduled work.** Scheduled Apex, or a scheduled flow.

**Decoupled reactions**, where several unrelated things should respond. Platform events.

**Anything the user waits for.** Queueable gives no response to the caller.

## Testing

```java
@IsTest
static void syncJobUpdatesStatusOnSuccess() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock());
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(10);

    Test.startTest();
    System.enqueueJob(new ClaimSyncQueueable(new List<Id>(
        new Map<Id, Warranty_Claim__c>(claims).keySet()
    )));
    Test.stopTest();   // the job runs here

    List<Warranty_Claim__c> synced = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id IN :claims
    ];
    for (Warranty_Claim__c claim : synced) {
        Assert.areEqual('Synced', claim.ERP_Sync_Status__c);
    }
}
```

Two constraints in test context:

**Only one chained level runs.** A job that enqueues another works; the second cannot enqueue a third. This is why chained jobs carry a `Test.isRunningTest()` guard.

**Assertions go after `Test.stopTest()`.** The job has not run before it.

Testing the failure path matters as much as the success path:

```java
@IsTest
static void syncJobLogsFailureOnHttpError() {
    Test.setMock(HttpCalloutMock.class, new ErpErrorMock(500));
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(5);

    Test.startTest();
    System.enqueueJob(new ClaimSyncQueueable(claimIds(claims)));
    Test.stopTest();

    List<Integration_Log__c> logs = [
        SELECT Id, Message__c FROM Integration_Log__c WHERE Context__c = 'ClaimSync'
    ];
    Assert.areEqual(1, logs.size(), 'A failed callout should produce a log entry');
}
```

See [[19.6 - Testing Async Apex]].

## Practical guidance

**Implement `Database.AllowsCallouts`** if the job might ever call out.

**Pass Ids, not records**, and re-query in the job.

**One job per batch of records**, never one per record.

**Give every chain a termination condition**, and guard it in test context.

**Store the job Id** against a run record for traceability.

**Attach a Finalizer** for anything where failure needs handling.

**Prefer Batch Apex above a few thousand records.**
