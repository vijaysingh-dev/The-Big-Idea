# The Stack in One Picture

#backend #networking

> **In one line:** Each layer wraps the one above it in its own header and hands it down, and every network problem you will ever debug is a question of which layer to look at.

---

## The Idea

You call `requests.get("https://api.example.com/users")`. Something has to turn that into electrical signals on a wire and back.

The work is split into layers. Each layer does one job and does not care what the layer above it is doing.

```
Your code          "GET /users"
   │
HTTP               adds method, headers, framing
   │
TLS                encrypts everything above
   │
TCP                adds ports, sequence numbers, reliability
   │
IP                 adds source and destination addresses
   │
Ethernet / WiFi    adds MAC addresses, puts it on the wire
   │
   ▼
   physical signal
```

At the other end it unwraps in reverse.

The reason this matters is not academic. **Every network bug lives at a specific layer, and the fix is different at each one.** "The API is slow" could be a DNS problem, a TCP problem, a TLS problem, an HTTP problem, or an application problem — and the five investigations look nothing alike.

---

## The Layers That Actually Matter

The textbook OSI model has seven layers. Three of them you will never think about. Here is the useful version.

| Layer | Unit | Adds | Example |
|---|---|---|---|
| **Application** | Message | Meaning | HTTP, gRPC, Postgres wire protocol |
| **Security** | Record | Encryption, identity | TLS |
| **Transport** | Segment | Ports, reliability, ordering | TCP, UDP |
| **Network** | Packet | Global addressing, routing | IP |
| **Link** | Frame | Local delivery on one hop | Ethernet, WiFi |

💡 **TLS is not really a layer in the model — it sits between transport and application.** That awkwardness is exactly why HTTPS proxies, TLS termination and mTLS are confusing. Knowing that TLS is a bolt-on rather than a native layer explains most of the confusion.

---

## What Each Layer Actually Adds

### IP — addressing and routing

IP's job: get a packet from address A to address B across an arbitrary number of networks.

What IP promises: nothing. Packets may be lost, duplicated, reordered, or corrupted. There is no acknowledgement and no retry.

```
Source IP | Dest IP | TTL | Protocol | ...payload...
```

Two fields worth knowing:

- **TTL** (time to live) — decremented at each router, dropped at zero. This is what stops routing loops, and it is how `traceroute` works: send packets with TTL 1, 2, 3... and see who complains
- **Protocol** — says whether the payload is TCP, UDP, ICMP

### TCP — making an unreliable network look reliable

TCP takes IP's "maybe it arrives" and builds "it arrives, in order, exactly once, or you get an error."

| Problem | TCP's solution |
|---|---|
| Packets lost | Acknowledgements and retransmission |
| Packets arrive out of order | Sequence numbers, reorder before delivery |
| Sender too fast for receiver | Flow control (receive window) |
| Sender too fast for network | Congestion control |
| Which program gets it? | Port numbers |

The cost of all this is covered in [[02.3 - TCP Connection Lifecycle]] and [[02.4 - Flow Control and Congestion Control]]. The short version: reliability is not free, and its cost shows up as latency.

### UDP — the honest one

UDP adds ports and a checksum to IP. That is all. No ordering, no retransmission, no connection.

This sounds useless and is not. If you are streaming live audio, a packet from 200ms ago is worthless — retransmitting it makes things worse, not better. See [[02.7 - UDP and Lossy Transport]].

### TLS — encryption and identity

TLS wraps the application data before TCP sees it. It provides:

- **Confidentiality** — nobody in between can read it
- **Integrity** — nobody in between can change it undetected
- **Identity** — you are talking to who you think you are, via certificates

It costs one or two extra round trips to set up. Full treatment in [[02.9 - TLS]].

## A Real Packet

`GET /users` over HTTPS, seen as bytes on the wire:

```
┌──────────────────────────────────────────────────────┐
│ Ethernet header (14 bytes)                           │
│   dest MAC, source MAC, type=IPv4                    │
│ ┌──────────────────────────────────────────────────┐ │
│ │ IP header (20 bytes)                             │ │
│ │   src 10.0.0.5, dst 93.184.216.34, TTL 64        │ │
│ │ ┌──────────────────────────────────────────────┐ │ │
│ │ │ TCP header (20+ bytes)                       │ │ │
│ │ │   src port 51234, dst port 443               │ │ │
│ │ │   seq, ack, flags, window                    │ │ │
│ │ │ ┌──────────────────────────────────────────┐ │ │ │
│ │ │ │ TLS record                               │ │ │ │
│ │ │ │ ┌──────────────────────────────────────┐ │ │ │ │
│ │ │ │ │ HTTP: GET /users HTTP/1.1            │ │ │ │ │
│ │ │ │ │       Host: example.com              │ │ │ │ │
│ │ │ │ └──────────────────────────────────────┘ │ │ │ │
│ │ │ └──────────────────────────────────────────┘ │ │ │
│ │ └──────────────────────────────────────────────┘ │ │
│ └──────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

Roughly 60+ bytes of headers before your first byte of HTTP. For a small request that is significant overhead, and it is one reason batching and connection reuse matter.

## MTU and Fragmentation

**MTU** (Maximum Transmission Unit) is the largest frame a link can carry. Ethernet is 1500 bytes.

Subtract IP (20) and TCP (20) headers and you get an **MSS** (Maximum Segment Size) of 1460 bytes of actual payload per packet.

⚠️ **MTU problems produce one of the most confusing failure modes in networking:** small requests work perfectly, large ones hang forever.

The mechanism: a router in the path has a smaller MTU (a VPN or tunnel, typically 1400). It cannot forward your 1500-byte packet, so it sends back an ICMP "fragmentation needed" message telling you to use smaller packets. A firewall blocks ICMP. You never get the message. You keep sending 1500-byte packets that keep being silently dropped.

Result: the TCP handshake succeeds (small packets), headers go through (small), and the connection dies the moment there is a large body.

```bash
# Find the real MTU to a host: send a 1472-byte payload that must not fragment
ping -M do -s 1472 target-host      # Linux
ping -D -s 1472 target-host         # macOS
```

💡 If you have ever seen "the API works from my laptop but hangs from the VPN, but only for large payloads", this is it. Knowing this one failure mode will save you a day at some point.

## In Production

### Which layer is your problem?

| Symptom | Likely layer | First check |
|---|---|---|
| Name does not resolve | DNS (application) | `dig`, `nslookup` |
| Connection refused, immediately | TCP — nothing listening | `ss -tlnp` on the server |
| Connection times out, no response | Firewall dropping silently | `tcpdump` — do SYNs arrive? |
| Connects, then hangs on large payloads | MTU | `ping -M do` with increasing size |
| Certificate errors | TLS | `openssl s_client -connect host:443` |
| Slow to establish, fast once connected | DNS or TLS handshake | `curl -w` timing breakdown |
| Fast to establish, slow transfer | TCP congestion, or the server | `ss -ti` for retransmits |
| Intermittent resets | Middlebox, idle timeout, or the server | `tcpdump` for RST packets |

### The one command that separates the layers

```bash
curl -w "@-" -o /dev/null -s https://api.example.com/users <<'EOF'
    dns:      %{time_namelookup}s
    tcp:      %{time_connect}s
    tls:      %{time_appconnect}s
    sent:     %{time_pretransfer}s
    firstbyte:%{time_starttransfer}s
    total:    %{time_total}s
EOF
```

```
    dns:      0.004s      ← DNS resolution
    tcp:      0.028s      ← + TCP handshake (24ms)
    tls:      0.089s      ← + TLS handshake (61ms)
    sent:     0.089s
    firstbyte:0.341s      ← + server thinking (252ms)  ← the problem
    total:    0.348s
```

💡 **Each number is cumulative, so subtract to get each phase.** This one command tells you whether "the API is slow" means DNS, connection setup, TLS, or the server. Put it in your runbook. It answers a question that otherwise takes twenty minutes of guessing.

### Why layers matter for architecture

Layer knowledge shows up directly in design decisions:

| Decision | The layer reason |
|---|---|
| L4 vs L7 load balancer | L4 sees TCP only; L7 parses HTTP. gRPC needs L7 because it multiplexes over one connection |
| Where to terminate TLS | At the edge is cheap but the internal hop is plaintext; end-to-end is safer and costs more |
| Connection pooling | Avoids paying TCP + TLS handshake per request |
| Why HTTP/3 uses UDP | To escape TCP's head-of-line blocking, which is a transport-layer property |
| Service mesh sidecars | Intercept at L4/L7 to add retries, mTLS and observability without changing your code |

## Codebase

**Repo:** `shopify/toxiproxy` — plus tools, not source, for the rest

**Question to answer:** At which layer does Toxiproxy operate, and what can it therefore simulate and not simulate? Specifically: can it simulate packet loss? Reordering? A bad certificate?

**Read:**

1. `toxiproxy/link.go` and `stream/` — follow one byte from client to upstream
2. `toxiproxy/toxics/` — one file per toxic. Read `latency.go`, `bandwidth.go`, `slow_close.go`, `timeout.go`

The answer to the question is instructive: Toxiproxy sits at TCP, so it can delay and throttle a byte stream but cannot drop individual IP packets. For real packet loss you need `tc netem`. Knowing which tool operates at which layer is the practical form of this note.

**Then, the real work of this session is tooling, not reading:**

```bash
# Capture a full request and read every layer
sudo tcpdump -i any -w capture.pcap 'host example.com and port 443'
curl https://example.com
# open capture.pcap in Wireshark

# Simulate real packet loss (layer 3, which toxiproxy cannot do)
sudo tc qdisc add dev lo root netem loss 5% delay 100ms
sudo tc qdisc del dev lo root
```

**Size:** 1 session.

**Drill 2.0 — See every layer**


**Part 1 — Annotate one packet.** Capture a single HTTPS request. Open it in Wireshark. Write out every field of the Ethernet, IP, TCP and TLS headers, with what each one is for.

Tedious, and it converts the diagram in this note from something you have read into something you have seen.

**Part 2 — Timing breakdown.** Run the curl timing command against ten different hosts: local, same region, other continent, behind a CDN, with a slow DNS server. Build a table.

Then deliberately make DNS slow (point at an unreachable resolver with a fallback) and confirm that only `time_namelookup` moves. Being able to attribute a delay to a layer from one command is the skill.

**Part 3 — Break MTU on purpose.** Set your interface MTU to 1400 and block ICMP with a firewall rule. Then make requests with small and large bodies.

Small works. Large hangs. **This is the exact failure this note warns about**, and having caused it yourself means you will recognise it in about ninety seconds when it happens for real. Capture the traffic and show the retransmissions of the oversized packet.

**Part 4 — netem experiments.** With `tc netem` on loopback, apply each of these and measure the effect on a 10MB HTTP download:

| Condition | Predict, then measure |
|---|---|
| 100ms delay | |
| 1% loss | |
| 5% loss | |
| 10ms delay + 1% loss | |
| Packet reordering | |
| Duplication | |

Write your prediction first. **The 1%-loss result is the one that will surprise you** — a small loss rate destroys throughput far more than intuition suggests, and understanding why is the entire content of [[02.4 - Flow Control and Congestion Control]].

**Done when:**
- `ANNOTATED.md` explains every field of one real packet
- Your timing table covers ten hosts and you can attribute any delay to a layer
- You have broken MTU yourself and captured the failure
- `RESULTS.md` has predictions and measurements for all six netem conditions
