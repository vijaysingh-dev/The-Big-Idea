# Webhooks and Callbacks

#backend #api-design #integration

> **In one line:** A webhook is an HTTP request you make to a stranger's server that will be slow, unreliable and occasionally hostile — so every part of the design is about delivery guarantees and blast radius.

---

## The Idea

```http
POST https://customer.example.com/hooks/conduit
Conduit-Signature: t=1755439927,v1=5257a869e7...
Conduit-Event-Id: evt_01HQZX...

{"type": "document.indexed", "data": {"id": "doc_42"}}
```

💡 **The hard part is not sending the request. It is that you are now making outbound HTTP calls to thousands of endpoints you do not control** — some down, some taking 30 seconds, and some pointing at internal addresses in your own network on purpose.

---

## Delivery Guarantees

**At-least-once, always.** Exactly-once is impossible ([[03.4 - Idempotency and Safe Retries]]).

```json
{
  "id": "evt_01HQZX7C4M8N",
  "type": "document.indexed",
  "created_at": "2026-08-17T14:32:07.500Z",
  "api_version": "2026-08-17",
  "data": {"id": "doc_42", "title": "Q3 Report"}
}
```

1. **Every event carries a stable ID** — the consumer deduplicates on it
2. **You retry until you get a 2xx**
3. **You document that duplicates happen**, so consumers build for it

⚠️ **Ordering is not guaranteed either.** Retries and parallel delivery mean `document.updated` can arrive before `document.created`. Include a sequence number or timestamp so consumers can detect it, **and say so explicitly in your documentation.**

💡 **Most mature APIs send thin events with an ID and let consumers fetch** — it avoids sending stale data and keeps payloads small.

## Signing

```python
def sign(payload: bytes, secret: str, timestamp: int) -> str:
    signed = f"{timestamp}.".encode() + payload
    return hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
```

```python
def verify(payload: bytes, header: str, secret: str, tolerance: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts = int(parts["t"])
    if abs(time.time() - ts) > tolerance:
        return False                                # replay protection
    return hmac.compare_digest(sign(payload, secret, ts), parts["v1"])
```

⚠️ **Three details, all mandatory:**

**Sign the timestamp with the payload.** Without it, an attacker who captures a valid request can replay it forever.

**Use `hmac.compare_digest`, never `==`.** String comparison short-circuits on the first differing byte, leaking the signature through timing.

**Verify against the raw body, not the parsed JSON.** Re-serialising changes key order and whitespace. In FastAPI, read `await request.body()` before parsing.

### Secret rotation

```
Conduit-Signature: t=1755439927,v1=abc...,v1=def...
```

Send two signatures during rotation; the consumer accepts either.

💡 **Design for rotation from day one.** A scheme that cannot rotate means a leaked secret requires every consumer to change simultaneously — which in practice means it never gets rotated.

## Retries

```python
RETRY_SCHEDULE = [10s, 1m, 5m, 30m, 2h, 6h, 12h, 1d]      # jittered
```

| Response | Action |
|---|---|
| 2xx | Success |
| **3xx** | **Do not follow redirects.** Treat as failure — a redirect is an SSRF vector |
| **410 Gone** | Disable the endpoint permanently |
| 4xx (other) | Retry — the consumer may have deployed a bug |
| 5xx, timeout | Retry |

⚠️ **Retrying 4xx is debatable and usually correct.** A consumer returning 400 because of a bug will fix it in an hour; giving up immediately loses their events. **`410 Gone` is the documented way for them to say "stop permanently".**

### Automatic disabling

```python
if consecutive_failures > 100 or failing_duration > timedelta(days=3):
    await disable_endpoint(endpoint_id, reason="sustained_failure")
    await notify_customer(endpoint_id)
```

⚠️ **You must disable dead endpoints or they consume your delivery capacity forever.**

**Notify before disabling, and make re-enabling self-service.**

## SSRF: The Serious Risk

The customer supplies a URL. Your server fetches it. **That is textbook Server-Side Request Forgery.**

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/   ← cloud metadata
http://localhost:6379/                                              ← your Redis
http://10.0.0.5:5432/                                               ← your database
```

⚠️ **This is not theoretical.** Webhook endpoints are one of the most reliable SSRF vectors in SaaS products, because the feature *requires* fetching a user-controlled URL.

```python
BLOCKED_NETWORKS = [
    ip_network("127.0.0.0/8"), ip_network("10.0.0.0/8"),
    ip_network("172.16.0.0/12"), ip_network("192.168.0.0/16"),
    ip_network("169.254.0.0/16"),     # link-local — cloud metadata
    ip_network("::1/128"), ip_network("fc00::/7"), ip_network("fe80::/10"),
]

async def validate_url(url: str) -> None:
    parsed = urlparse(url)
    if parsed.scheme != "https" or parsed.port not in (None, 443):
        raise ValueError("https on 443 only")
    for info in await loop.getaddrinfo(parsed.hostname, 443):
        addr = ip_address(info[4][0])
        if any(addr in net for net in BLOCKED_NETWORKS) or not addr.is_global:
            raise ValueError("private address not allowed")
```

⚠️ **Validation at registration is not sufficient.** DNS can change between registration and delivery — **DNS rebinding**. The hostname resolves to a public IP when you check and `127.0.0.1` when you connect.

**The robust fix is to resolve once and connect to the resolved IP**, with the hostname in the `Host` header and SNI.

| Additional layer | Effect |
|---|---|
| **Deliver from an egress-restricted network** | Even a bypass reaches nothing |
| **Block redirects entirely** | A 302 to `localhost` defeats URL validation |
| Require HTTPS with a valid certificate | Prevents plaintext interception |
| Separate delivery workers with no credentials | Limits blast radius |

💡 **The strongest architectural defence is running delivery in a network segment with no route to anything internal.** URL validation is necessary and will eventually have a bypass; network isolation means the bypass reaches nothing ([[14.4 - Common Vulnerabilities]]).

## Delivering at Scale

### One slow endpoint must not block others

⚠️ **A shared queue means one customer with a 30-second endpoint starves everyone else** ([[02.5 - Head of Line Blocking]]).

```python
queue_name = f"webhooks:{endpoint_id % NUM_PARTITIONS}"      # partition
sem = per_endpoint_semaphore(endpoint_id, limit=5)           # or bound concurrency
```

### Timeouts must be aggressive

```python
timeout = httpx.Timeout(connect=3.0, read=10.0, write=5.0, pool=2.0)
```

⚠️ **A 30-second read timeout on a million deliveries a day is a capacity disaster.**

💡 **Tell consumers prominently: acknowledge within 10 seconds, then process in the background.** Consumers processing synchronously inside the handler are the main source of slow endpoints.

### Circuit breaking per endpoint

An endpoint failing every request should not receive full-rate traffic. Break the circuit, back off, probe occasionally ([[11.3 - Circuit Breakers and Bulkheads]]).

## In Production

### The consumer-facing features that matter

| Feature | Why |
|---|---|
| **Delivery log with request and response** | The first support question is always "did you send it?" |
| **Manual replay** | Lets customers recover from their own outages without a ticket |
| Test/ping event | Verify an endpoint at registration |
| Event type filtering | Do not send events they do not want |
| Signing secret rotation UI | Otherwise nobody rotates |

💡 **The delivery log is the highest-value feature** and it separates a good implementation from a frustrating one. Store request body, headers, response status, truncated response body and timing for every attempt, for 30 days. **It turns an unanswerable support question into a link.**

⚠️ Storage grows fast — a million deliveries a day at 2KB is 2GB/day. Truncate response bodies and use a TTL.

### Idempotency is the consumer's job, and you must help

```markdown
## Handling duplicates
Every event has a unique `id`. Store processed IDs and skip repeats.
```

**Insert the marker and apply the effect in one transaction** ([[07.5 - Idempotency Keys and Deduplication]]).

### Offer polling too

💡 **Offer webhooks *and* a polling endpoint.** Some consumers cannot expose a public endpoint — corporate networks, on-premise deployments, local development. **A `GET /events?since=cursor` endpoint costs little and removes a whole category of integration blocker.**

It also gives every consumer a recovery path when their endpoint was down, without needing your replay feature.

## Codebase

**Repo:** `stripe` (docs), `svix/svix-webhooks`, `standard-webhooks/standard-webhooks`

**Question to answer:** How does Stripe structure webhook events, and what exactly do they guarantee about ordering and delivery? Then: in Svix, how is delivery isolated per endpoint, and how do they handle SSRF?

**Read, in order:**

1. **Stripe webhooks documentation** — **the reference implementation.** Signature verification, the retry schedule, best practices, and the explicit statement that ordering is not guaranteed
2. `standard-webhooks/standard-webhooks` — a signing specification several providers have adopted. **Short, and it is the format to implement** rather than inventing your own
3. `svix/svix-webhooks` — production webhook-delivery-as-a-service, open source. Queue partitioning, retry logic, endpoint circuit breaking
4. `svix` — search for their URL validation and SSRF protections
5. **GitHub webhooks documentation** — a different design with a large event catalogue. Note how they version payloads and handle redelivery

💡 The Svix source is unusually valuable because **webhook delivery is a full product with real scaling constraints, and someone has open-sourced their solution.** The partitioning and per-endpoint state handling are exactly the problems you would otherwise solve badly on the first attempt.

**Size:** 1–2 sessions.

## Exercise

**Drill 5.12 — Deliver to hostile endpoints**

⚠️ Everything runs against your own local stack only.

```
drills/05-webhooks/
├── sender/{models.py, signing.py, validate.py, deliver.py, retry.py, log.py, replay.py}
├── receiver/{consumer.py, naive.py}
├── hostile/{slow.py, flaky.py, dead.py, redirector.py, rebinding.py}
├── security/{ssrf_attacks.py, timing_attack.py, replay_attack.py, FINDINGS.md}
├── scale/{load.py, isolation.py, RESULTS.md}
└── README.md
```

**Part 1 — Build the sender.** Signing with timestamps, retry schedule with jitter, delivery log, per-endpoint circuit breaker, automatic disabling, manual replay.

**Part 2 — Build hostile receivers.** Five of them: slow (25s), flaky (50% failure), dead (connection refused), redirector (302 to localhost), rebinding (DNS changes between check and connect). Plus one correct receiver that deduplicates.

Run a realistic mix and verify: the slow endpoint does not block others, the flaky one eventually succeeds, the dead one is disabled, and the correct receiver processes each event exactly once despite duplicates.

**Part 3 — SSRF, thoroughly.** Attempt: `localhost`, `127.0.0.1`, `169.254.169.254`, RFC1918, IPv6 loopback, a hostname resolving to a private IP, `0.0.0.0`.

**Then the two hard ones:**

- **Redirect:** a public URL returning 302 to `http://localhost:6379`. Confirm redirects are not followed
- **DNS rebinding:** a DNS server returning a public IP first and `127.0.0.1` second. **Confirm your validation is bypassed.** Then implement resolve-then-connect-to-IP and confirm it holds

**The rebinding bypass is the one that will actually work against a naive implementation, and reproducing it is the point.**

**Part 4 — Signature attacks.**

- **Timing:** implement comparison with `==`, measure whether signature bytes can be recovered by timing, fix with `compare_digest`, measure again
- **Replay:** capture a valid delivery and resend an hour later. Confirm the timestamp tolerance rejects it. **Then remove the timestamp from the signed payload and confirm the replay succeeds**
- **Body mutation:** verify against reserialised JSON and show the signature failing on valid requests with reordered keys

**Part 5 — Isolation at scale.** 10,000 endpoints: 9,000 fast (20ms), 900 slow (5s), 100 dead.

Version A: one shared queue, unbounded concurrency. Version B: partitioned queues with per-endpoint limits and circuit breaking.

**Measure p99 delivery latency for the *fast* endpoints in both.** Version A's should be badly delayed. Chart it.

**Part 6 — Secret rotation.** Dual-signature rotation. Verify old and new both work during the window, and only new after.

**Part 7 — The polling alternative.** A `GET /events?since=cursor` endpoint over the same log.

For a consumer down for 2 hours, compare recovery via webhook replay versus polling. **Measure time-to-full-recovery and events delivered.** Write down which you would offer — the answer is "both", and the reasoning matters.

**Done when:**
- All five hostile receivers are handled correctly
- Every SSRF attempt is blocked, **including DNS rebinding**
- The timing attack works against `==` and fails against `compare_digest`
- Replay is blocked, and removing the timestamp demonstrably reopens it
- Fast endpoints are unaffected by slow ones after the fix
- Secret rotation works without any consumer downtime
- You have measured recovery via replay against recovery via polling
