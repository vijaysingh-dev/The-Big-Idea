# Postgres Architecture

#backend #databases #postgres

> **In one line:** A process per connection, a shared buffer pool between them, and a write-ahead log that makes a commit one sequential `fsync` instead of many random writes — everything about Postgres's behaviour follows from those three facts.

---

## The Idea

```
                      postmaster (supervisor)
                            │ forks one backend per connection
 backend               backend                  backend
    └──────────── shared memory ────────────────┘
                 ├── shared_buffers  (the page cache)
                 ├── WAL buffers
                 └── lock tables
              background processes
                 ├── walwriter      flushes WAL
                 ├── checkpointer   flushes dirty pages
                 ├── bgwriter       trickles dirty pages out
                 └── autovacuum     cleans dead tuples
```

💡 **A process per connection is the single most consequential design decision in Postgres.** Each backend is a full OS process with its own memory — several megabytes minimum. That is why 500 connections is expensive, why PgBouncer exists, and why pool sizing matters so much ([[01.10 - Connection Pools and Limits]]).

⚠️ **A connection is not free even when idle.** It holds a process, a slot in shared memory structures, and a share of the lock table. **`max_connections` is not a soft limit** — several shared structures are sized from it, so raising it increases the fixed memory cost of every backend.

---

## The Memory Layout

### shared_buffers

```
shared_buffers = 25% of RAM     (the standard starting point)
```

⚠️ **Why only 25%, when other databases take 80%?** Because Postgres relies on the **OS page cache** as a second layer. A page not in `shared_buffers` may still be in the kernel's cache. **Setting it too high steals memory from the OS cache and can make things worse.**

```sql
SELECT sum(blks_hit) * 100.0 / nullif(sum(blks_hit + blks_read), 0) AS hit_ratio
FROM pg_stat_database;
```

💡 **Above 99% for OLTP is healthy. Below 95% means your working set does not fit** and you are reading from disk constantly — the cliff from [[06.1 - Storage Engines]].

### work_mem

**Per-operation, not per-connection.**

⚠️ **`work_mem` is allocated per sort, per hash join, per hash aggregate — and one query can use several.**

```
Worst case ≈ max_connections × work_mem × operations_per_query
100 × 64MB × 3 = 19 GB
```

💡 **Set it low globally and raise it per session for known-heavy queries:**

```sql
SET LOCAL work_mem = '256MB';   -- inside a transaction, for one report
```

The symptom of it being too low:

```
Sort Method: external merge  Disk: 24560kB   ← spilled
```

**Disk sorts are 10–100× slower than in-memory sorts.** Finding one in a hot query and raising `work_mem` for it is often the single largest available win.

### maintenance_work_mem

```
maintenance_work_mem = 1GB      (be generous — few run concurrently)
```

Raising this dramatically speeds up index builds and vacuum.

## The Write-Ahead Log

```
COMMIT
  1. Write the change to the WAL buffer          (memory)
  2. Flush WAL to disk and fsync                 (sequential — one I/O)
  3. Return success
  ...later...
  4. Checkpointer writes dirty pages             (random I/O, batched)
```

💡 **A commit only needs the *log* to be durable, not the data pages.** After a crash, replay the WAL against the last checkpoint. **That turns many random writes into one sequential write per commit.**

### fsync latency is your commit latency

```
Local NVMe fsync:        ~50–200 µs
Cloud network storage:   ~500 µs – 2 ms
```

⚠️ **Your maximum transaction rate is bounded by fsync latency**, unless commits are grouped. Postgres does group them, which is why throughput often improves with more concurrent writers up to a point.

### synchronous_commit

```sql
SET synchronous_commit = off;      -- return before the WAL is flushed
```

⚠️ **On crash you lose up to `wal_writer_delay` (200ms) of committed transactions.** The database stays *consistent* — no corruption — but recent commits vanish.

💡 **This is a legitimate per-transaction choice.** Analytics events or session updates can use `off` for a large latency win while payments use the default. **Setting it per-transaction rather than globally is the sophisticated version.**

### Checkpoints

```ini
checkpoint_timeout = 15min
max_wal_size = 8GB
checkpoint_completion_target = 0.9
```

⚠️ **Checkpoint spikes are a classic Postgres latency problem.** A checkpoint flushing gigabytes saturates disk I/O and every query slows.

```sql
SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;
```

💡 **`checkpoints_req` should be near zero.** If not, checkpoints are forced by WAL volume rather than time, they are happening too often, and `max_wal_size` is too small. **One of the most commonly under-tuned settings on busy systems.**

## The Path of a Query

```
1. Parse → 2. Analyse → 3. Rewrite → 4. Plan → 5. Execute
```

**Prepared statements skip steps 1–4.** After five executions, Postgres may switch to a **generic plan** ignoring parameter values.

⚠️ **Generic plan flips are a real production surprise.** A query fast for 5,000 executions suddenly gets slow.

```sql
SET plan_cache_mode = force_custom_plan;
```

**Execution is a tree of nodes pulling rows from each other**, one at a time — which is why `EXPLAIN ANALYZE` shows `loops` and per-row costs ([[06.4 - Reading EXPLAIN ANALYZE]]).

## Physical Layout

```
$PGDATA/base/16384/
├── 24576          the heap — 1GB segments
├── 24576_fsm      free space map
└── 24576_vm       visibility map
```

**The Free Space Map** tracks which pages have room. A stale FSM means inserts extend the table instead of reusing space.

**The Visibility Map** marks pages where every tuple is visible to all transactions, enabling **index-only scans**.

💡 **The visibility map is why `VACUUM` affects read performance, not just space.** An unvacuumed table has a stale VM, so index-only scans degrade into regular scans — appearing as `Heap Fetches: 48291` in `EXPLAIN` ([[06.7 - MVCC Vacuum and Bloat]]).

### TOAST

Values over ~2KB are compressed and, if still large, moved to a separate TOAST table.

⚠️ **TOASTed columns are not read unless selected.** `SELECT *` on a table with a large `content` column fetches and decompresses every value; `SELECT id, title` does not touch TOAST at all.

💡 **This makes `SELECT *` genuinely expensive on tables with large text or JSONB columns** — often the difference between a 5ms and a 200ms query, and the most concrete argument against it in application code.

## In Production

### The settings that matter most

```ini
shared_buffers = 8GB                    # 25% of RAM
effective_cache_size = 24GB             # 50-75% — a PLANNER HINT, allocates nothing
work_mem = 16MB
maintenance_work_mem = 2GB

max_wal_size = 8GB
checkpoint_timeout = 15min
checkpoint_completion_target = 0.9

random_page_cost = 1.1                  # SSDs — default 4.0 assumes spinning disks
effective_io_concurrency = 200

max_connections = 100                   # keep low; use PgBouncer

log_min_duration_statement = 100ms
log_lock_waits = on
log_checkpoints = on
log_autovacuum_min_duration = 0
```

⚠️ **`random_page_cost = 4.0` is the default and it is wrong on SSDs.** It tells the planner random reads cost four times sequential ones — true on spinning disks, false on NVMe. **Leaving it makes the planner avoid index scans**, and it is one of the most impactful single-line fixes on a modern deployment.

💡 **`effective_cache_size` allocates nothing.** It tells the planner how much memory it can assume is available for caching. **Setting it too low makes the planner pessimistic about index usage.**

### The extensions you should always install

```sql
CREATE EXTENSION pg_stat_statements;    -- query-level statistics
CREATE EXTENSION pgstattuple;           -- bloat measurement
CREATE EXTENSION pg_buffercache;        -- what is cached
CREATE EXTENSION auto_explain;          -- log plans for slow queries
```

```sql
SELECT calls, total_exec_time, mean_exec_time, rows, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

💡 **Order by `total_exec_time`, not `mean_exec_time`.** A 2ms query called ten million times costs far more than a 5-second query called twice, **and the expensive queries in aggregate are almost never the ones people suspect.**

### Monitoring

```sql
-- Are we vacuuming enough?
SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- What is blocking what?
SELECT pid, wait_event_type, wait_event, state, query FROM pg_stat_activity
WHERE state != 'idle';

-- Transaction ID wraparound risk
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
```

⚠️ **The last one is the most important query nobody runs.** If `age(datfrozenxid)` approaches 2 billion, **Postgres shuts down to prevent data corruption.** It is entirely preventable and it has taken down large companies. **Alert at 1 billion** ([[06.7 - MVCC Vacuum and Bloat]]).

### Connection handling in practice

```
Application (pool of 5 per worker)
    → PgBouncer (transaction mode, 1000 client slots)
        → Postgres (max_connections = 100)
```

**Given that each backend is a process, this is not optional at scale — it is the standard architecture** ([[06.9 - Connection Pooling and PgBouncer]]).

## Codebase

**Repo:** `postgres/postgres`

**Question to answer:** Trace a single `INSERT` from SQL text to durability on disk. Which shared memory structures are touched, when is the WAL written, when is `fsync` called, and when does the heap page actually reach disk?

**Read, in order:**

1. `src/backend/access/transam/README` — **an essay on transactions, WAL and recovery.** Read this first; it frames everything else
2. `src/backend/storage/buffer/README` — the buffer manager, pinning, and clock-sweep replacement. **Explains `shared_buffers` behaviour precisely**
3. `src/backend/access/transam/xlog.c` — find `XLogInsert` and `XLogFlush`. **This is the commit path.** Large file; search rather than read linearly
4. `src/backend/storage/buffer/bufmgr.c` — `ReadBuffer` and `FlushBuffer`
5. `src/backend/postmaster/checkpointer.c` — the checkpoint loop and how `checkpoint_completion_target` spreads the writes
6. `src/backend/tcop/postgres.c` — `exec_simple_query`, tying parse, plan and execute together

💡 The Postgres source has an unusual property: **the READMEs are better than most published books on the subject.** `transam/README` and `buffer/README` are each an hour well spent, and they will make every `EXPLAIN` output and tuning decision comprehensible rather than superstitious.

**Size:** 3 sessions.

## Exercise

**Drill 6.2 — Watch Postgres work**

```
drills/06-postgres-arch/
├── memory/{buffer_watch.py, work_mem.sql, RESULTS.md}
├── wal/{volume.py, fsync_latency.py, sync_commit.py, RESULTS.md}
├── checkpoint/{induce_spike.py, tune.sql, PLOT.md}
├── toast/{select_star.py, FINDINGS.md}
├── planner_cost/random_page_cost.sql
└── README.md
```

**Part 1 — Watch the buffer pool.** With `pg_buffercache`, sample what is cached every second while running a workload.

Start with an empty cache and a table larger than `shared_buffers`. **Chart cache hit ratio and query latency over 10 minutes.**

**Find the point where the working set stops fitting and watch the hit ratio collapse.** Chart latency against hit ratio — the relationship should be dramatic, not gradual.

**Part 2 — Find the `work_mem` cliff.** A query sorting a large result set. Sweep `work_mem`: 1MB → 256MB.

Use `EXPLAIN (ANALYZE, BUFFERS)` to see `quicksort` versus `external merge`.

**Find the exact value where it stops spilling**, measure the latency difference either side, and **compute what that `work_mem` × `max_connections` would cost in worst-case memory.**

**Part 3 — WAL volume by operation.** Measure WAL bytes for: an `INSERT`, an `UPDATE` of one column with 0 indexes, the same with 8 indexes, a HOT-eligible update, and a `DELETE`.

```sql
SELECT pg_current_wal_lsn();  -- before and after
```

**The 8-index update should generate dramatically more WAL** — the index write amplification from [[06.1 - Storage Engines]], measured.

**Part 4 — fsync is your commit rate.** Measure single-threaded commit throughput and compute the implied fsync latency.

Then sweep concurrency 1 → 200 and chart total throughput. **Group commit should make throughput rise well past what single-threaded fsync latency would suggest.**

Then `synchronous_commit = off`, measure the speedup, and **state precisely what you gave up.**

**Part 5 — Induce a checkpoint spike.** `max_wal_size = 256MB`, heavy write load. Watch `checkpoints_req` climb and **chart query p99 over time** — periodic spikes aligned with checkpoints.

Then raise `max_wal_size` to 8GB with `checkpoint_completion_target = 0.9` and chart again.

**Part 6 — The `SELECT *` tax.** A table with a 100KB `content` column. Compare `SELECT id, title` against `SELECT *` over 10,000 rows.

Measure time, buffers read, and TOAST relation reads. **Report the ratio.**

**Part 7 — `random_page_cost`, measured.** A query where an index scan and a sequential scan are both plausible.

Capture the plan and actual execution time at 4.0 and 1.1. **Find a query where the default makes Postgres choose the wrong plan, and quantify how much slower it is.**

**This is the single most impactful default in a modern deployment, and having your own number for it is worth having.**

**Done when:**
- Your hit-ratio-versus-latency chart shows the memory cliff
- You know the exact `work_mem` where your query stops spilling, and its worst-case memory cost
- Your WAL table shows index write amplification
- Group commit throughput visibly exceeds single-threaded fsync limits
- Checkpoint spikes appear and then disappear after tuning
- You have the `SELECT *` TOAST ratio for a realistic table
- You found a query where `random_page_cost = 4.0` picks the wrong plan
