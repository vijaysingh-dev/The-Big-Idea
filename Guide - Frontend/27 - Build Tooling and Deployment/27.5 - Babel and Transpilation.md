# Babel and Transpilation

**Transpilation** converts source in one language or syntax level into another — TypeScript to JavaScript, JSX to function calls, modern syntax to older syntax. **Polyfilling** adds missing runtime APIs. They are different problems, and conflating them causes real bugs.

```
Syntax  → transpiled  → optional chaining, class fields, async/await
API     → polyfilled  → Promise, Array.prototype.at, structuredClone
```

A transpiler cannot invent `Promise` for an environment that lacks it. A polyfill cannot make an old parser understand `?.`.

## What Babel does

```
source → parse → AST → transform (plugins) → generate → output
```

Everything is a plugin. A **preset** is a curated list of plugins:

```json
{
  "presets": [
    ["@babel/preset-env", { "targets": { "chrome": "100" } }],
    ["@babel/preset-react", { "runtime": "automatic" }],
    "@babel/preset-typescript"
  ]
}
```

`preset-env` reads your browser targets and applies **only** the transforms those targets need. Setting targets accurately is the single most impactful configuration choice — an unnecessarily broad target inflates output and slows the build for everyone.

`runtime: "automatic"` is the modern JSX transform, which imports from `react/jsx-runtime` so files no longer need `import React` ([[16.2 - JSX]]).

## browserslist

```json
{
  "browserslist": [">0.5%", "last 2 versions", "not dead", "not op_mini all"]
}
```

Read by Babel, PostCSS, Autoprefixer and most bundlers — one declaration drives every tool.

```bash
npx browserslist              # see what the query resolves to
npx browserslist --coverage   # what percentage of users it covers
```

Check the query against your actual analytics. Supporting a browser with 0.1% of your traffic can cost 30KB of polyfills and noticeably worse output for the other 99.9%.

A modern default for most products:

```json
["defaults and fully supports es6-module"]
```

This targets browsers with native ES module support, which eliminates most legacy transforms entirely.

## Polyfills

```json
["@babel/preset-env", {
  "useBuiltIns": "usage",
  "corejs": { "version": "3.38", "proposals": false }
}]
```

- **`"entry"`** — you import `core-js` once and Babel expands it to what your targets need
- **`"usage"`** — Babel injects polyfills per file based on what the code actually uses
- **`false`** — no polyfills at all

`"usage"` is the right default. It only includes what is used, which is dramatically smaller than a blanket import.

For libraries, injecting global polyfills is antisocial — it mutates the consumer's environment. Use `@babel/plugin-transform-runtime` instead, which imports non-global helpers:

```json
{ "plugins": [["@babel/plugin-transform-runtime", { "corejs": 3 }]] }
```

The alternative to shipping polyfills at all is a service like `polyfill.io` (now community-maintained forks after a supply-chain incident) — worth knowing about, but self-hosting is safer.

## The faster transpilers

Babel is JavaScript, single-threaded, and typically the slowest step in a build.

| | Language | Relative speed |
| --- | --- | --- |
| **esbuild** | Go | ~20–50× |
| **SWC** | Rust | ~20× |
| **Babel** | JavaScript | baseline |

```js
// webpack
{ test: /\.tsx?$/, use: "swc-loader" }

// Vite uses esbuild for dev transforms automatically
```

```json
// .swcrc
{
  "jsc": {
    "parser": { "syntax": "typescript", "tsx": true },
    "target": "es2020",
    "transform": { "react": { "runtime": "automatic" } }
  }
}
```

Replacing `babel-loader` with `swc-loader` is usually the single largest build-speed improvement available ([[27.4 - Webpack Basics]]).

**When Babel is still needed:** custom AST transforms, macro-based libraries, and plugins with no SWC equivalent. A shrinking list — the React Compiler ships an SWC plugin, styled-components has an SWC transform, and most common Babel plugins have been ported ([[19.9 - The React Compiler]]).

## TypeScript transpilation

Two distinct things happen to TypeScript:

**Type checking** — verifying correctness. Only `tsc` does this.

**Type stripping** — removing annotations to produce JavaScript. Babel, SWC and esbuild all do this, very quickly, **without checking types**.

```json
{
  "scripts": {
    "build": "tsc --noEmit && vite build",
    "typecheck": "tsc --noEmit"
  }
}
```

The bundler strips types for speed; `tsc --noEmit` checks them separately. Skipping the check means type errors reach production — a common oversight when a team optimizes build time by removing the `tsc` step.

Because these transpilers work **file by file** with no cross-file type information, some TypeScript features do not work:

- `const enum` — requires whole-program knowledge
- Legacy namespace merging
- Decorator metadata emit without configuration

`isolatedModules: true` in `tsconfig.json` makes `tsc` flag anything a single-file transpiler cannot handle. It should be on in any project using esbuild or SWC.

The related requirement:

```ts
import type { User } from "./types";     // explicit — erased correctly
import { User } from "./types";           // ambiguous for a single-file transpiler
```

`verbatimModuleSyntax` enforces the `type` modifier where needed.

## What transpilation costs

**Bundle size.** Async/await down-compiled to ES5 pulls in a regenerator runtime of several KB. Class fields, spread and generators all expand significantly.

**Performance.** Down-compiled code is often slower than native. `for...of` over an array becomes an iterator protocol loop in ES5, which is meaningfully slower than the native version.

**Debuggability.** Output diverges from source, making source maps essential ([[27.7 - Source Maps]]).

This is why targeting modern browsers matters so much: less transformation means smaller, faster, more debuggable output.

## Differential serving

```html
<script type="module" src="/modern.js"></script>
<script nomodule src="/legacy.js"></script>
```

Modern browsers load the module version and ignore `nomodule`; legacy browsers do the reverse. Two builds, each optimal for its audience.

`@vitejs/plugin-legacy` and webpack equivalents automate this. It roughly doubles build time and adds deployment complexity, so it is worth it only when legacy support is genuinely required and the modern bundle savings are substantial.

For most products in 2026, dropping the legacy build entirely is the better trade.

## How senior engineers actually use this

**They set browser targets from real analytics**, not from a copied default.

**They use SWC or esbuild** for transpilation and reserve Babel for cases needing custom AST work.

**They run `tsc --noEmit` separately** in CI, because bundler-based type stripping checks nothing.

**They enable `isolatedModules`** so `tsc` catches single-file-transpiler incompatibilities.

**They use `useBuiltIns: "usage"`** rather than a blanket polyfill import.

## Common pitfalls

- Assuming the bundler type-checks TypeScript — it does not.
- Overly broad browser targets inflating output for everyone.
- No polyfill strategy, so modern APIs crash on older browsers.
- Blanket `core-js` imports adding tens of KB unnecessarily.
- Libraries injecting global polyfills into consumer environments.
- `const enum` and namespaces breaking under esbuild or SWC.
- Missing `import type`, so a type-only import becomes a runtime import.
- Keeping `babel-loader` when SWC would be an order of magnitude faster.

## Interview angle

"What is Babel and why do we need it" should distinguish transpilation from polyfilling — syntax versus runtime APIs — and note that `preset-env` uses browserslist targets to apply only what is needed. The follow-up worth volunteering: bundlers now strip TypeScript types without checking them, so `tsc --noEmit` must run separately, and single-file transpilers cannot support `const enum` or ambiguous type imports, which is what `isolatedModules` exists to catch.
