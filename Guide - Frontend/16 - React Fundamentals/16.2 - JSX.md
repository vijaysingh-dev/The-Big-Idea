# JSX

JSX is syntax sugar for function calls. It is not HTML, it is not a template language, and it is not part of React — it is a syntax extension that compiles to plain JavaScript.

## What it compiles to

```jsx
const el = <div className="card" onClick={handle}>Hello {name}</div>;
```

With the modern JSX transform (React 17+):

```js
import { jsx as _jsx } from "react/jsx-runtime";

const el = _jsx("div", {
  className: "card",
  onClick: handle,
  children: ["Hello ", name],
});
```

The result is a plain object — a **React element** — not a DOM node:

```js
{ type: "div", props: { className: "card", children: [...] }, key: null, ... }
```

It is a description of what should be rendered, produced cheaply, and thrown away after reconciliation ([[18.1 - Virtual DOM and React Elements]]).

The classic transform (`React.createElement`) required `React` in scope in every file. The modern one imports from `react/jsx-runtime` automatically, which is why `import React from "react"` is no longer needed.

## Expressions, not statements

```jsx
{value}                          // any expression
{a + b}
{items.map(i => <li key={i.id}>{i.name}</li>)}
{isActive ? <On /> : <Off />}
{isVisible && <Panel />}
{/* comment */}

{if (x) {}}                      // SyntaxError — statements not allowed
```

Because `{}` holds an expression, conditionals use ternaries or `&&`, and loops use `map`.

## What React renders and what it skips

```jsx
{null}       // nothing
{undefined}  // nothing
{false}      // nothing
{true}       // nothing
{0}          // renders "0"
{""}         // nothing visible, but not skipped
{NaN}        // renders "NaN"
```

The `0` case is the single most common JSX bug:

```jsx
{items.length && <List items={items} />}     // renders "0" when empty
{items.length > 0 && <List items={items} />} // correct
{items.length ? <List items={items} /> : null}
```

`&&` returns the left operand when it is falsy, and `0` is renderable while `false` is not ([[05.4 - null vs undefined]]).

## Attribute differences from HTML

```jsx
className          // not class — `class` is a reserved word
htmlFor            // not for
onClick            // camelCase events
tabIndex
readOnly
style={{ marginTop: 8 }}       // object, camelCased, numbers become px
dangerouslySetInnerHTML={{ __html: html }}
```

`style` takes an object, and numeric values get `px` appended except for unitless properties (`lineHeight`, `zIndex`, `flex`, `opacity`).

Note that inline style objects create a new object every render, which breaks referential equality for memoized children — hoist static styles to module scope.

Custom attributes and `data-*`/`aria-*` pass through as written:

```jsx
<div data-testid="cart" aria-label="Cart" custom-attr="x" />
```

## Fragments

```jsx
<>
  <td>A</td>
  <td>B</td>
</>

<React.Fragment key={item.id}>
  <dt>{item.term}</dt>
  <dd>{item.def}</dd>
</React.Fragment>
```

Fragments return multiple elements without a wrapper node. The long form is required when you need a `key`, which comes up when mapping over pairs of elements.

They matter beyond tidiness: a stray `<div>` inside a `<tbody>`, `<ul>` or flex container breaks HTML validity or layout ([[09.1 - Semantic HTML and Document Structure]]).

## Components must be capitalized

```jsx
<button />      // string type "button" — a DOM element
<Button />      // the Button variable — a component
```

The compiler distinguishes them by case. A lowercase component name silently produces an unknown DOM element and renders nothing useful.

For dynamic components, assign to a capitalized variable first:

```jsx
const Component = isLink ? "a" : "button";
return <Component {...props} />;
```

## Props spreading

```jsx
<Button {...props} />
<Button {...props} type="submit" />       // type wins — later overrides
<Button type="submit" {...props} />       // props.type wins if present
```

Order matters, and it is the mechanism behind sensible component defaults ([[05.6 - Spread vs Rest]]).

The common pattern for a wrapper component:

```jsx
function Button({ variant = "primary", className = "", ...rest }) {
  return <button className={`btn btn--${variant} ${className}`} {...rest} />;
}
```

Spreading `rest` forwards `onClick`, `aria-*`, `data-*` and anything else without enumeration.

## children

`children` is a normal prop with special syntax:

```jsx
<Card>Hello</Card>
// identical to
<Card children="Hello" />
```

Which means components can take multiple "slots":

```jsx
<Layout
  header={<Header />}
  sidebar={<Nav />}
>
  <Content />
</Layout>
```

Passing elements as props is a genuinely underused technique. It avoids prop drilling and, because the element is created in the parent, it does not re-render when the child's state changes ([[19.1 - What Causes Re-renders]]).

## JSX is safe by default

```jsx
<div>{userInput}</div>    // escaped — always safe
```

React escapes interpolated strings, so `<img src=x onerror=...>` renders as text. The only escape hatch is the deliberately verbose:

```jsx
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />
```

The name is a warning. Anything passed here must be sanitized ([[15.6 - Frontend Security]]).

Note one gap: React does not sanitize `href`. A `javascript:` URL from user data still executes.

```jsx
<a href={url} />   // validate the protocol yourself
```

## Keys

```jsx
{items.map(item => <Row key={item.id} item={item} />)}
```

`key` is not a prop the component receives — it is a hint to the reconciler about element identity across renders. Covered fully in [[16.6 - Lists and Keys]], but note it belongs on the outermost element of the map, including on a `Fragment` when mapping pairs.

## JSX without React

Because JSX is just a transform, it works with any library that provides a compatible factory. Preact, Solid and Hono all use JSX with different runtimes, configured through `jsxImportSource`. This is worth knowing mostly to reinforce that JSX and React are separable.

## How senior engineers actually use this

**They keep JSX shallow.** Deeply nested ternaries inside JSX are hard to read; extracting a variable or an early return above the JSX is almost always clearer.

**They use `&&` only with genuine booleans**, or use a ternary with `null`.

**They pass elements as props** for layout composition instead of drilling data down to build the same element deeper in the tree.

**They avoid inline object and array literals** in props on memoized components, since a new reference every render defeats memoization.

**They treat `dangerouslySetInnerHTML` as a review-required change.**

## Common pitfalls

- `{count && <X />}` rendering a stray `0`.
- Lowercase component names silently rendering nothing.
- `class` and `for` instead of `className` and `htmlFor`.
- Inline `style` or object props creating new references every render.
- Missing keys, or index keys on reorderable lists.
- Unsanitized `dangerouslySetInnerHTML`, or an unvalidated `href`.
- Wrapper `<div>`s breaking table or list semantics where a Fragment was needed.

## Interview angle

"What is JSX" should get: a syntax extension compiled to function calls producing plain objects, not HTML and not part of React itself. Follow with the practical differences — expressions only, `className`, camelCase events, capitalization determining component vs element — and the falsy-rendering rules with the `0` bug. Mentioning that JSX is escaped by default, with `href` as the exception, adds a security dimension most answers miss.
