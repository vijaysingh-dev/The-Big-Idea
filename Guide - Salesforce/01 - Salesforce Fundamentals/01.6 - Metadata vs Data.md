# Metadata vs Data

## The distinction the whole platform runs on

**Metadata** is configuration. The definition of an object, a field, a validation rule, a page layout, a flow, an Apex class, a permission set. It describes how the org is built.

**Data** is records. The Account named Northwind Manufacturing. The Opportunity worth 40,000. The Case someone logged this morning.

Everything you deploy is metadata. Everything users create is data. Almost every deployment mistake in Salesforce traces back to blurring this line.

## Why the line exists

In a normal application, code lives in files and data lives in a database. On Salesforce, both are stored in the same database. What separates them is that metadata is *versioned, retrievable as XML, and deployable between orgs*, and data is not.

When you create a custom field in Setup, you are creating a metadata record. Salesforce can serialize that into a file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<CustomField xmlns="http://soap.sforce.com/2006/04/metadata">
    <fullName>Total_Revenue__c</fullName>
    <label>Total Revenue</label>
    <type>Currency</type>
    <precision>16</precision>
    <scale>2</scale>
    <trackHistory>true</trackHistory>
</CustomField>
```

That file can go into Git, be reviewed in a pull request, and be deployed to another org. The Account records holding values in that field cannot. They move only through data loading tools.

## The practical rule

**Metadata moves through deployment. Data moves through data loading.**

| Thing | Type | How it moves between orgs |
| --- | --- | --- |
| Custom object, fields | Metadata | Deployment |
| Apex class, trigger, LWC | Metadata | Deployment |
| Validation rule, flow | Metadata | Deployment |
| Profile, permission set | Metadata | Deployment |
| Record types, page layouts | Metadata | Deployment |
| Report and dashboard definitions | Metadata | Deployment |
| Account, Contact, Opportunity records | Data | Data Loader, Bulk API |
| Custom Settings values | Data | Data Loader |
| Custom Metadata Type records | Metadata | Deployment |
| Users | Data (mostly) | Created per org |

The last two rows are where it gets interesting.

## The awkward middle: configuration stored as records

Some configuration is naturally data-shaped. Tax rates by region. API endpoints per environment. Discount thresholds by product family. It changes without a code deployment, but it drives behaviour like configuration does.

Salesforce offers two mechanisms, and choosing correctly is a real design decision.

**Custom Settings** are essentially custom objects with a caching layer. Their *definition* is metadata, but their *values* are data. That means a deployment carries the setting but not the values, and someone has to populate them in every org, by hand or by script. Values can be edited by admins at runtime without a deployment, which is sometimes exactly what you want.

**Custom Metadata Types** are the newer answer. Their definition *and* their records are both metadata. Records deploy with the package. They are queryable in Apex, they do not count against SOQL query limits when accessed through the type's `getAll()` method, and they can be protected inside a managed package.

```java
// Custom Metadata: deploys with the code, no SOQL limit consumed
Integration_Setting__mdt erpConfig = Integration_Setting__mdt.getInstance('ERP_Primary');
String endpoint = erpConfig.Endpoint_Path__c;

// Custom Setting: values must exist in each org, read is cached but org-specific
Feature_Toggle__c toggles = Feature_Toggle__c.getInstance(UserInfo.getUserId());
Boolean useNewPricing = toggles.Enable_New_Pricing__c;
```

The practical guidance most experienced teams follow: use Custom Metadata Types for configuration that should travel with the code and be the same in every environment, and Custom Settings when values must legitimately differ per org, per profile, or per user at runtime. Full detail in [[17.1 - Custom Metadata Types]] and [[17.2 - Custom Settings]].

## Where this bites in real projects

**Reference data does not deploy.** A picklist's *values* are metadata and deploy fine. But a lookup to a `Country__c` custom object holding 195 records is data, and those 195 records must be loaded separately into every sandbox and into production. Teams forget this constantly, and the symptom is a flow or validation rule that works in one org and fails in another because a lookup target does not exist.

**Record IDs differ across orgs.** A Record Type, a Queue, a Profile, or a reference record has a different 18-character ID in each org. Code that hardcodes an ID works in the sandbox and breaks in production. This is one of the most common production bugs in the ecosystem.

```java
// Breaks in every org except the one it was written in
if (opp.RecordTypeId == '0125g000000XyZaAAK') { ... }

// Resolves by developer name at runtime, portable across orgs
Id enterpriseRt = Schema.SObjectType.Opportunity
    .getRecordTypeInfosByDeveloperName()
    .get('Enterprise_Sale')
    .getRecordTypeId();

if (opp.RecordTypeId == enterpriseRt) { ... }
```

**Sandboxes carry metadata but not always data.** A Developer sandbox copies configuration and no records. A Full sandbox copies both, at the cost of a long refresh cycle. Sandbox strategy is really a question about which of the two you need. See [[01.10 - Org Types and Org Strategy]] and [[21.11 - Sandbox Strategy and Data Seeding]].

**Metadata is queryable, which is powerful for tooling.** You can inspect the org's own configuration at runtime, both in Apex and through the Tooling API. This is how documentation generators, org-health scanners, and dynamic user interfaces work.

```java
// Field-level introspection without hardcoding anything
Map<String, Schema.SObjectField> fields = Schema.SObjectType.Account.fields.getMap();
for (String apiName : fields.keySet()) {
    Schema.DescribeFieldResult describe = fields.get(apiName).getDescribe();
    if (describe.isCustom() && !describe.isUpdateable()) {
        System.debug('Read-only custom field: ' + describe.getLabel());
    }
}
```

This pattern shows up throughout mature codebases. A component that renders any object's fields, a validation utility that checks field-level security before writing, a dynamic query builder — all of them read metadata at runtime instead of hardcoding field names. See [[03.13 - Enforcing Security in Apex and SOQL]] and [[09.12 - Generics, Type Casting and Reflection]].

## How senior engineers use the distinction

**Configuration-driven architecture.** Instead of writing `if (country == 'IN') { taxRate = 0.18; }`, put the rule in a Custom Metadata Type. Business changes then become a deployment of a record rather than a code change with a test class and a release cycle. Taken far enough this becomes a design style in its own right. See [[18.10 - Custom Metadata Driven Architecture]].

**Everything in Git, including declarative work.** Because flows, validation rules, and layouts are metadata, they belong in version control alongside Apex. Teams that only version their code lose the ability to review or roll back declarative changes, and declarative changes cause just as many outages. See [[21.7 - Git Branching Strategies for Salesforce]].

**Feature toggles as metadata.** Deploy code disabled, enable it with a setting change, disable it instantly when something goes wrong. Without a toggle, disabling a bad feature means an emergency deployment. See [[21.10 - Deployment Strategies, Rollback and Hotfixes]].

**Beware metadata bloat.** Every field, layout, and record type is metadata that must be deployed, tested, and maintained forever. Deleting metadata is far harder than creating it, because of dependencies. The discipline of not adding is a real one.
