# Arrow Functions

Arrow functions are not just shorter syntax. They differ from regular functions in five behavioral ways, and every one of them has a practical consequence.

## Syntax forms

```js
const a = () => 42;                       // implicit return
const b = x => x * 2;                     // single param, no parens needed
const c = (x, y) => x + y;
const d = x => ({ value: x });            // returning an object literal needs parens
const e = x => {                          // block body requires explicit return
  const y = x * 2;
  return y + 1;
};
const f = async x => await fetch(x);
```

The `({ ... })` wrapping in `d` is the one syntax gotcha: without parentheses the braces are parsed as a block, and the function returns `undefined`.

## The five differences

**1. Lexical `this`** — arrows have no own `this`. They inherit it from the enclosing scope at definition time, and no call-site mechanism can change it.

```js
class Timer {
  seconds = 0;

  startBroken() {
    setInterval(function () {
      this.seconds++; // `this` is undefined or window, not the instance
    }, 1000);
  }

  startWorking() {
    setInterval(() => {
      this.seconds++; // inherits `this` from startWorking
    }, 1000);
  }
}
```

This is the reason arrows exist. Before them, every callback needed `const self = this` or `.bind(this)`.

**2. No `arguments`** — an arrow sees the enclosing function's `arguments`. Use rest parameters instead.

```js
const sum = (...nums) => nums.reduce((a, b) => a + b, 0);
```

**3. Not constructible** — `new (() => {})` throws. Arrows have no `prototype` property and no `[[Construct]]` internal method.

**4. No `super` or `new.target`** — both resolve lexically, which is usually what you want inside a class method's callback.

**5. Cannot be a generator** — there is no `function*` arrow form.

## Where arrows are wrong

**Object methods that need dynamic `this`:**

```js
const counter = {
  count: 0,
  incBroken: () => this.count++,  // `this` is module scope, not counter
  incWorks() { this.count++; },
};
```

**Prototype methods** — same reason. Attaching an arrow to a prototype gives every instance the same lexically captured `this`.

**DOM event handlers that use `this` as the element:**

```js
button.addEventListener("click", function () {
  this.classList.toggle("active"); // `this` is the button
});

button.addEventListener("click", (e) => {
  e.currentTarget.classList.toggle("active"); // use the event instead
});
```

Both work; the arrow version just requires reading `this` from the event object. Most codebases standardize on the arrow + `currentTarget` form because it survives refactoring into React.

**Anything needing hoisting** — arrows are always expressions, so they follow `const` TDZ rules and cannot be called before definition.

## Class fields vs methods

```js
class Button {
  handleClick = () => {          // class field: per-instance, bound
    this.setState({ clicked: true });
  };

  render() {                     // prototype method: shared, dynamic this
    return <button onClick={this.handleClick} />;
  }
}
```

The class-field arrow was the standard fix for passing handlers as props in class components. The tradeoff is memory: a field arrow allocates one function per instance, while a prototype method is shared by all instances. With a few hundred components that is irrelevant; with thousands of list items it is measurable. In hooks-based React this whole question disappears.

## Arrows and referential identity in React

```js
function Parent() {
  return <Child onSelect={() => doSomething()} />;
}
```

A new function is created on every render, so `Child`'s `onSelect` prop is a new value every time and `React.memo` on `Child` never prevents a re-render. This is the most common reason memoization "doesn't work". The fix is `useCallback`, but only when the child is memoized or the function feeds a dependency array ([[17.7 - useCallback]]).

The allocation itself is cheap — modern engines handle millions of closure allocations per second. The cost is always the downstream re-render, never the allocation.

## How senior engineers actually use this

**They default to arrows for callbacks and non-method functions, and regular functions for object and class methods.** This is close to universal convention now, and most style guides encode it (`prefer-arrow-callback` plus `object-shorthand` in ESLint).

**They avoid implicit returns that hide side effects.** `arr.forEach(x => doThing(x))` returns a value nobody uses; worse, `arr.map(x => { store.add(x) })` looks like a transform but is a loop. Use block bodies when the function is executed for effect.

**They still write named functions at module top level.** Stack traces and hoisting both favor declarations there, and top-level functions rarely need lexical `this`.

**They know arrows do not fix async `this` in every case.** An arrow captures `this` from where it was *written*. If the enclosing function itself has the wrong `this`, the arrow faithfully inherits the wrong value.

## Common pitfalls

- Returning an object literal without wrapping parentheses.
- Using an arrow as an object or prototype method and finding `this` is `undefined`.
- Expecting `arguments` inside an arrow.
- Using an arrow where the DOM's `this`-as-element behavior was relied upon.
- Assuming inline arrows in JSX are a performance problem in themselves. They are only a problem when they break memoization boundaries.

## Interview angle

"Difference between arrow and regular functions" is asked constantly. Lead with lexical `this` and explain *why* it was introduced — replacing `var self = this` and `.bind(this)` in callbacks — then list no `arguments`, not constructible, no `prototype`, no generator form. Following up with "and here is where you must not use one" (object methods, prototype methods) demonstrates judgment rather than memorization.
