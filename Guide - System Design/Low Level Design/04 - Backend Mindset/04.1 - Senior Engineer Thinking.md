# Senior Engineer Thinking

The gap between mid-level and senior isn't knowledge of more patterns. It's a different _mode of thinking_ — systems thinking, failure-first design, and ruthless prioritization of what matters.

---

## The Senior Mental Model Shift

|Mid-level Thinks|Senior Thinks|
|---|---|
|"Does this work?"|"Does this fail gracefully?"|
|"Is this correct?"|"Is this correct _under load_?"|
|"Can I add this?"|"Should I add this at all?"|
|"What pattern fits?"|"Do I need a pattern here?"|
|"How do I build this?"|"What can I delete?"|
|"I'll refactor later"|"What's the cost of this decision in 2 years?"|
|"Make it flexible"|"Make it deletable"|

## Designing for Evolution

### The Stable Core vs Variable Shell

```
┌─────────────────────────────────────┐
│         Stable Core                 │  ← Domain logic, rarely changes
│   (entities, business rules,        │     Put abstractions here
│    domain events, value objects)    │
├─────────────────────────────────────┤
│         Variable Shell              │  ← Infrastructure, frequently changes
│   (DB, cache, queue, email,         │     Implement behind interfaces
│    third-party APIs, UI)            │
└─────────────────────────────────────┘
```

Design rule: **The core should never import from the shell.** Dependencies always point inward (Dependency Inversion).

### Planning for Change Without Overengineering

```
Question: "Will this change?"
     │
     ├── "Yes, we have 2+ known variants today"
     │        → Abstract now
     │
     ├── "Likely yes, but unknown shape"  
     │        → Design clean seams (interfaces at boundaries),
     │          don't build the plugin system yet
     │
     └── "Maybe someday"
              → YAGNI. Write the simplest thing.
                Refactor when the requirement appears.
```

## Abstraction Thinking

### Levels of Abstraction

```
High:   "Process a payment"          → PaymentService.process(order)
        "Send a notification"        → Notifier.send(user, message)
        
Medium: "Charge via Stripe"          → StripeGateway.charge(amount, token)
        "Send email via SMTP"        → SmtpEmailSender.send(to, subject, body)
        
Low:    "POST to https://api.stripe.com/v1/charges"
        "Open TCP connection to smtp.gmail.com:587"
```

**Rule:** Each layer should operate at one level. A method that mixes "process a payment" logic with "POST to Stripe API" has a leaky abstraction.

### Signs of a Good Abstraction

- The name makes sense without knowing the implementation
- Callers don't need to know _how_ it works
- You can explain the interface in one sentence
- Swapping the implementation doesn't require changing callers

### Signs of a Bad Abstraction

- The interface exposes implementation details (e.g., `UserRepository.execute_sql(query)`)
- Every implementation implements differently or throws `NotImplementedError`
- The abstraction is used in only one place and provides no flexibility
- You created it "just in case" it would be needed

## Identifying Good Boundaries

### Cohesion Test

If two things always change together → same module If two things rarely change together → separate modules

```
OrderItem and Order → always change together (order domain) → same module
Order and Invoice → change independently → separate modules
PaymentGateway and OrderService → completely independent → separate modules
```

### Coupling Test

"If I change X, what else breaks?"

- Change propagates to 1-2 places → acceptable coupling
- Change propagates to 5+ places → bad coupling, need interface

### The "Strangler Fig" Boundary Test

Can I replace this component with a completely different implementation without changing its clients? If yes → good boundary. If no → the interface is leaky.

## Reliability and Failure-First Thinking

### Failure Mode Analysis

For every dependency, ask:

1. What happens if it's **slow**? (timeout, async, degrade)
2. What happens if it's **down**? (circuit breaker, fallback, queue)
3. What happens if it returns **wrong data**? (validate, compensate)
4. What happens if the **caller crashes mid-operation**? (idempotency, transactions)

```
Dependency: Payment API
  Slow?     → Timeout after 10s, retry 3 times with backoff
  Down?     → Circuit breaker → fail fast → return error (don't queue payments)
  Wrong?    → Validate response schema, raise domain error
  Crash?    → Idempotency key prevents double-charge on retry
```

### Circuit Breaker Mental Model

```
CLOSED → OPEN → HALF-OPEN → CLOSED

CLOSED:     Requests pass through normally
            Tracking failure rate
            
OPEN:       Too many failures — stop calling downstream
            Return error immediately (fail fast)
            Wait for timeout
            
HALF-OPEN:  Let one request through — test if service recovered
            Success → back to CLOSED
            Failure → back to OPEN
```

### Designing for Observability

Every service should answer: "What is it doing right now?"

```python
# Bad: silent black box
def process_batch(orders):
    for order in orders:
        process(order)

# Good: observable
def process_batch(orders):
    logger.info(f"Starting batch processing of {len(orders)} orders")
    
    success_count = 0
    failure_count = 0
    
    for order in orders:
        try:
            process(order)
            success_count += 1
            metrics.increment("order.processed", tags={"status": "success"})
        except Exception as e:
            failure_count += 1
            metrics.increment("order.processed", tags={"status": "error"})
            logger.error(f"Failed to process order {order.id}: {e}", exc_info=True)
    
    logger.info(f"Batch complete: {success_count} success, {failure_count} failed")
    
    if failure_count / len(orders) > 0.1:   # >10% failure rate
        alerts.trigger("high_batch_failure_rate", failure_count=failure_count)
```

## How to Avoid Overengineering

### The "Three Strikes" Rule

- First time: just write it
- Second time: write it again, note the duplication
- Third time: refactor to shared abstraction

### Overengineering Checklist

Before adding complexity, ask:

- [ ] Do I have at least 2 known variations of this behavior?
- [ ] Will callers care about this abstraction boundary?
- [ ] Can I explain _why_ I added this layer to a junior?
- [ ] Will this make testing easier or harder?
- [ ] What's the cost of _not_ having this? (YAGNI test)

### Accidental vs Essential Complexity

- **Essential complexity**: inherent in the problem (e.g., distributed transactions are hard)
- **Accidental complexity**: introduced by the design (e.g., unnecessary abstraction layers)

Senior engineers ruthlessly minimize accidental complexity.

## Designing Reusable Internal Frameworks

### When to Extract a Framework

- 3+ services/teams need the same behavior (auth, logging, retry, tracing)
- The behavior is stable enough to not change often
- The cost of standardization is lower than divergence

### Framework Design Principles

1. **Convention over configuration** — sensible defaults, opt-in customization
2. **Small surface area** — fewer public APIs = easier to maintain
3. **Escape hatches** — always let advanced users bypass the abstraction
4. **Version stability** — breaking changes require major version bump + migration guide
5. **Fail loudly** — misuse should raise clear errors, not silent misbehavior

```python
# Good internal framework design
class BaseService:
    """
    Base for all application services.
    Provides: logging, metrics, transaction management.
    Override: _execute() with your business logic.
    """
    
    def execute(self, command):
        """Template method — wraps _execute with cross-cutting concerns."""
        with self._tracer.span(f"{self.__class__.__name__}.execute"):
            self._logger.info(f"Executing {command.__class__.__name__}")
            try:
                result = self._execute(command)
                self._metrics.increment(f"{self._metric_prefix}.success")
                return result
            except DomainError:
                self._metrics.increment(f"{self._metric_prefix}.domain_error")
                raise
            except Exception as e:
                self._metrics.increment(f"{self._metric_prefix}.error")
                self._logger.error(f"Unexpected error: {e}", exc_info=True)
                raise
    
    @abstractmethod
    def _execute(self, command):
        """Override this in subclasses."""
        pass
```

## Making Tradeoff Decisions

### The ADR Format (Architecture Decision Record)

When you make a significant design decision, document:

```markdown
## ADR-001: Use Event-Driven Architecture for Order Processing

**Status:** Accepted
**Date:** 2024-01-15

**Context:**
Order placement triggers: inventory reservation, email confirmation,
analytics tracking, fraud analysis. These need to happen but shouldn't
block the order creation response.

**Decision:**
Publish OrderPlaced domain event. Downstream handlers consume asynchronously
via Kafka. Order service only owns order creation.

**Consequences:**
✅ Order service is simple, fast, independently deployable
✅ New requirements (loyalty points) = new consumer, zero changes to order service
❌ Eventual consistency — inventory may briefly show stock that's reserved
❌ Added operational complexity (Kafka cluster, consumer monitoring)

**Alternatives Rejected:**
- Synchronous calls: tight coupling, shared failure domain, slower
- Choreography via REST: polling complexity, even tighter coupling
```

## The Senior Engineer's Heuristics Cheat Sheet

|Situation|Heuristic|
|---|---|
|Complex service with 10 methods|Each method should be explainable in 1 sentence|
|Need to add 5th `if/elif`|Extract to Strategy or registry|
|Same code in 3 places|DRY — extract shared abstraction|
|Abstraction used in 1 place|YAGNI — inline it|
|New requirement needs changing 5 files|Wrong boundaries — find the seam|
|Test requires 10 mocks|Class doing too much — split it|
|Junior can't understand it|Too clever — simplify|
|It's fast enough|Don't optimize until you measure|
