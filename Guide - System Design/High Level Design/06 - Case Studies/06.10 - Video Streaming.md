# Case Study: Video Streaming Platform (YouTube/Netflix-style)

> **Revision tags:** #case-study #video #cdn #storage  
> **Related:** [[03.3 - CDN]] | [[03.11 - Object Storage]]

---

## Requirements Clarification

**Functional:**
- Upload videos (up to 10 GB)
- Automatic transcoding to multiple resolutions and formats
- Adaptive bitrate streaming (ABR): player switches quality based on bandwidth
- Video playback globally with low buffering
- Search and recommendations (high level)
- View count, likes, comments

**Non-functional:**
- Upload: support resumable uploads; processing within 10 minutes
- Playback: first-frame latency < 3s; buffering ratio < 0.5%
- Scale: 500 hours of video uploaded per minute (YouTube scale)
- Storage: 1 billion videos, average 500 MB each = 500 PB
- 1B daily active viewers, peak 100M concurrent streams

**Out of scope:** Live streaming, ML recommendation model, ad insertion

---

## Estimation

```
Uploads/min: 500 hours = 30,000 minutes of video
  Storage per minute of video (1080p source): ~500 MB
  Transcoded versions (360p, 480p, 720p, 1080p, 4K): ~3× source = 1.5 GB/minute
  Storage: 30,000 min × 1.5 GB = 45 TB/min = 2.7 PB/hour

Streaming:
  100M concurrent viewers × 5 Mbps (1080p) = 500 Tbps peak
  → Must be served entirely from CDN edge (origin servers can't handle this)

CDN cache hit rate:
  Top 1% of videos = 90% of views → CDN caches top 1% → 90% cache hit
  Remaining 10% hits origin → 10M concurrent × 5 Mbps = 50 Tbps origin
  → Still requires large multi-CDN setup
```

**Key architectural driver:** This is fundamentally a CDN problem. The video bits must be at the edge, not in a central origin.

## Architecture Overview

```
UPLOAD PATH:
[Creator] ──HTTPS──→ [Upload Service] → S3 (raw video)
                           │
                     [Kafka: upload-events]
                           │
                     [Transcoding Service]
                       (FFmpeg workers)
                           │
                       S3 (transcoded segments)
                           │
                     [CDN Pre-warm] → [Global CDN PoPs]

PLAYBACK PATH:
[Viewer] ──→ [API: /videos/{id}/manifest]
                     → returns HLS manifest URL
[Viewer] ──→ [CDN Edge PoP] ──→ video segments served from edge
                               (origin S3 only on cache miss)
```

## Upload and Transcoding Pipeline

### Resumable Upload

Large video files need resumable upload to handle network interruptions:

```
1. Creator: POST /v1/uploads/init
   { filename: "my_video.mp4", file_size: 2_000_000_000, content_type: "video/mp4" }
   → Response: { upload_id: "up_abc123", chunk_size: 10_485_760 }  # 10 MB chunks

2. Creator: PUT /v1/uploads/up_abc123/chunks/0
   Body: first 10 MB of file
   → Response: { chunk_id: "ck_001", received: 10485760 }

3. Creator: PUT /v1/uploads/up_abc123/chunks/1..N
   (repeat for each chunk; can resume from last confirmed chunk if disconnected)

4. Creator: POST /v1/uploads/up_abc123/complete
   → Triggers transcoding pipeline

Internally: Upload Service assembles chunks in S3 using S3 Multipart Upload API.
```

### Transcoding Service

```
Raw video in S3
    │
    ▼
[Transcoding Workers] (stateless, horizontally scalable)
  For each video:
    1. Download raw from S3
    2. FFmpeg transcode to multiple profiles:
       - 360p  (400 Kbps)
       - 480p  (800 Kbps)
       - 720p  (2 Mbps)
       - 1080p (5 Mbps)
       - 4K    (15 Mbps)    [if source is 4K]
    3. Segment each profile into 6-second HLS segments (.ts files)
    4. Generate HLS master manifest (.m3u8) referencing all profiles
    5. Upload all segments and manifests to S3
    6. Emit video-ready event → update video record, notify creator
```

**FFmpeg parallelism:** Each resolution is transcoded in parallel on different workers. A 1-hour video at 5 profiles = 5 parallel transcoding jobs, each taking ~10 minutes → total wall time ~10 minutes.

**Segment-based transcoding:** Divide source video into 60-second segments, transcode each independently, then concatenate. Reduces latency for long videos (first segment available in 2 minutes even for a 3-hour video).

## Adaptive Bitrate Streaming (ABR)

### HLS (HTTP Live Streaming) Format

```
master.m3u8 (manifest):
  #EXT-X-STREAM-INF:BANDWIDTH=400000,RESOLUTION=640x360
  360p/playlist.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=2000000,RESOLUTION=1280x720
  720p/playlist.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
  1080p/playlist.m3u8

720p/playlist.m3u8 (per-quality playlist):
  #EXTINF:6.000,
  segment_000.ts
  #EXTINF:6.000,
  segment_001.ts
  ...
```

### ABR Algorithm (Player-side)

```
Player logic:
  1. Fetch master.m3u8 → know available bitrates
  2. Start with lowest quality (360p) for instant playback start
  3. Measure download speed of each segment
  4. If available_bandwidth > current_bitrate × 1.5:
       switch up to next quality for next segment
  5. If buffer < 10 seconds:
       switch down immediately
  6. Never switch more than 2 quality levels per second (avoid thrashing)
```

The player switches quality **per segment** (every 6 seconds). The user experiences smooth playback regardless of bandwidth fluctuations.

## CDN Strategy

### Why Single Origin Doesn't Work

```
100M viewers × 5 Mbps = 500 Tbps
Largest CDN PoPs have ~10 Tbps capacity
→ Need ~50 PoPs globally just to serve peak traffic
No single data center can handle this → CDN is mandatory
```

### Multi-CDN Setup

Use multiple CDN providers (Akamai + CloudFront + Cloudflare) for:
- Geographic coverage (different providers have better PoPs in different regions)
- Redundancy (one CDN has issues → route traffic to another)
- Cost optimization (different pricing for different traffic types)

```
DNS-based traffic routing:
  Viewer in India → route to CDN with best Indian PoP (lowest latency)
  Viewer in US East → route to CloudFront (best coverage)
  CDN health check fails → reroute to backup CDN
```

### Pre-warming Popular Content

When a trending video is published:
```
1. Detect: video getting high view velocity in first 10 minutes
2. Pre-warm: proactively push video segments to CDN PoPs in predicted high-traffic regions
3. Cache: segments stay cached until evicted (LRU) or TTL expires
```

Without pre-warming: first viewers in each region cause cache misses → origin hit → slow load.

## Video Metadata Service

```sql
CREATE TABLE videos (
    video_id        UUID PRIMARY KEY,
    creator_id      BIGINT NOT NULL,
    title           VARCHAR(500),
    description     TEXT,
    status          VARCHAR(20),  -- uploading, processing, ready, deleted
    duration_secs   INT,
    manifest_url    TEXT,          -- CDN URL to master.m3u8
    thumbnail_url   TEXT,
    view_count      BIGINT DEFAULT 0,
    like_count      BIGINT DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL,
    published_at    TIMESTAMPTZ
);
```

**View count:** Don't update on every view (hot row problem at YouTube scale). Aggregate in Redis (`INCR views:{video_id}`), flush to DB every minute. Accept ~1 minute of count staleness.

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Transcoding worker crashes | Video stuck in processing | Kafka at-least-once: message redelivered; idempotent transcoding (check if output already exists in S3) |
| CDN PoP outage | Some users see slow loads | Multi-CDN failover; fallback to origin for critical content |
| S3 region outage | Can't serve raw video | Cross-region replication for popular content; CDN cache serves most traffic |
| Upload service down | Creators can't upload | Multiple upload service instances; resumable upload handles mid-upload failures |
| Manifest not yet cached | First viewer triggers origin hit | Pre-warm on publish; low TTL for manifests (frequent updates), high TTL for segments (immutable) |

## Storage Optimization

**500 PB total** requires tiered storage:
```
Hot (S3 Standard):      Recently uploaded, trending content  (top 5%)
Warm (S3 Intelligent-Tiering): Videos 30-180 days old
Cold (S3 Glacier):      Videos > 180 days, rarely watched
Archive (Glacier Deep): Legal/compliance hold, practically never accessed
```

Automated lifecycle policies transition videos based on view recency:
```
< 30 days or > 1000 views/month → Hot
30–180 days → Warm
> 180 days AND < 100 views/month → Cold
```

## What This Design Demonstrates

- Multipart / resumable upload for large files
- Transcoding pipeline with FFmpeg in parallel per resolution
- HLS segmentation enabling adaptive bitrate streaming
- CDN as the primary serving layer (origin can't handle 500 Tbps)
- Hot-row problem solution for view counts (Redis aggregation)
- Storage tiering for 500 PB at manageable cost
