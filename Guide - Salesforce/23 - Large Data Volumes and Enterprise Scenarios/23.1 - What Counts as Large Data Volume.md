# What Counts as Large Data Volume

## The thresholds

Salesforce's own guidance names these, approximately:

```
Records per object              a few million and above
Records under one parent        10,000
Records owned by one user       10,000
Sharing rows per object         tens of millions
Data storage                    tens of GB
Records in a single query       50,000 (the hard limit)
```

**"Large" is not one number.** An object with two million rows performs fine if queries are selective and ownership is distributed. The same object with 400,000 records under one account is a problem at a fraction of the volume.

**Distribution matters more than count.** That is the single most useful thing to understand about LDV on this platform.

## The symptoms

Volume announces itself indirectly. What people actually report:

```
"The list view times out"
"The report never finishes"
"The data load fails on some rows with UNABLE_TO_LOCK_ROW"
"The nightly batch used to take an hour and now takes six"
"Changing a user's role locks the org for two hours"
"Deleting the account timed out"
"Search doesn't find records that exist"
"The page takes eight seconds to load"
```

**None of these says "large data volume"**, which is why the diagnosis is frequently wrong. The first response is usually to optimize the code, and the code is fine.

## Why volume behaves differently here

Three platform characteristics that do not apply in a single-tenant database.

**Shared tables.** Your records sit alongside every other tenant's on that instance. A query that cannot use an index scans across data that is not yours, which is why the optimizer refuses non-selective queries rather than merely running them slowly. See [[08.9 - Indexes and Selective Queries]].

**Sharing is materialized.** Record access is not computed at query time; it is stored in sharing tables. Every record, every user with access, every rule — rows in a table. **The sharing tables are frequently larger than the data tables**, and every query joins against them.

**Everything is per transaction.** Governor limits do not scale with data. Two million records must be processed 200 at a time, in transactions that each get the same budget as one processing five. See [[16.1 - Why Governor Limits Exist]].

## The three kinds of skew

Uneven distribution, and each has a different failure mode. Covered in [[10.9 - Data Skew]]; restated here because it is the LDV problem more often than raw volume is.

**Account data skew.** One account with a very large number of children.

*Failure:* every operation on a child locks the parent for roll-up recalculation. Concurrent operations contend, producing `UNABLE_TO_LOCK_ROW` under load. Changing the account's owner recalculates sharing for every child.

*Cause:* a catch-all account — "Unknown Customer", "Web Leads" — or a consumer business modelling individuals under one corporate account.

**Ownership skew.** One user owning a very large number of records.

*Failure:* ownership drives sharing. Changing the owner, or moving that user in the role hierarchy, recalculates sharing for every record they own. At 400,000 records that is hours, during which the org is degraded.

*Cause:* an integration user owning everything it created, or a departed employee's records never reassigned.

**Lookup skew.** Very many records pointing at one record through a lookup.

*Failure:* the platform locks the lookup target on insert and update of referencing records. A default value used by 90% of records means every insert contends on that one row.

*Cause:* a lookup with a default value on a high-volume object. The least visible of the three, because nothing in the schema suggests a problem.

**Detecting all three:**

```sql
SELECT AccountId, Account.Name, COUNT(Id) FROM Contact
GROUP BY AccountId, Account.Name ORDER BY COUNT(Id) DESC LIMIT 20

SELECT OwnerId, Owner.Name, COUNT(Id) FROM Warranty_Claim__c
GROUP BY OwnerId, Owner.Name ORDER BY COUNT(Id) DESC LIMIT 20

SELECT Region__c, COUNT(Id) FROM Warranty_Claim__c
GROUP BY Region__c ORDER BY COUNT(Id) DESC LIMIT 20
```

**Run these on every high-volume object.** Ten minutes of querying identifies the problem more reliably than a week of profiling.

## Assessing an org

The checks worth running before assuming volume is the issue.

**Record counts per object:**

```sql
SELECT COUNT() FROM Warranty_Claim__c
```

Or, for everything at once, the Setup storage page — which shows record counts and storage by object.

**Storage consumption:**

```
Setup → Storage Usage
```

Data storage and file storage are allocated separately, and hitting either produces `STORAGE_LIMIT_EXCEEDED` on operations that worked yesterday.

**Query selectivity**, for the queries that matter:

```
Developer Console → Query Plan
```

Cost above 1 means a table scan. See [[08.10 - Query Plan Tool and Query Optimization]].

**Sharing table size** is not directly queryable, and the proxies are: how many sharing rules exist, how deep the role hierarchy is, and how many records have manual or Apex shares.

**Batch job duration**, trended:

```sql
SELECT ApexClass.Name, CreatedDate, CompletedDate, JobItemsProcessed, NumberOfErrors
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND CreatedDate = LAST_N_DAYS:30
ORDER BY CreatedDate DESC
```

**A job whose duration has doubled over six months is the earliest warning available**, and nobody watches it.

## What breaks first

Roughly in order, as an object grows.

**List views and reports** stop completing. The filter is not selective and the row count has passed the optimizer's threshold.

**Data loads slow, then fail** with lock errors as parallel batches contend.

**Batch jobs lengthen** until they overrun their window.

**Sharing recalculation** becomes disruptive — a role change locks users out for hours.

**Deletion becomes impractical.** Deleting a parent with 300,000 children times out.

**Search degrades**, since the index grows with the data.

**The API allocation** comes under pressure as integrations retrieve more.

**Reports and list views break first**, which is why business users report the problem before developers notice it.

## The strategies, in order of preference

**Reduce the data.** Archiving is the most effective intervention available and the one reached for last. Fewer rows makes every query faster, every index more selective, every report quicker, every load cheaper, and every batch job shorter. See [[23.4 - Archiving with Big Objects and External Storage]].

**Fix the distribution.** Correcting skew removes contention that no amount of query tuning addresses.

**Make queries selective.** Date bounds, positive filters rather than `!=`, and indexed fields. See [[23.6 - Query Performance at Scale]].

**Simplify sharing.** A flat hierarchy with fewer rules produces fewer sharing rows. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

**Add indexes and skinny tables.** Effective, and after the above rather than instead of it. See [[16.9 - Skinny Tables and Custom Indexes]].

**Tune the processing.** Batch scope size, parallelism, and load ordering. See [[23.5 - Bulk Data Loading at Scale]].

**The order matters.** A custom index on a table that should have been archived is a solution to a self-inflicted problem.

## Designing for volume up front

Cheaper than remediating, and the questions are few.

**Estimate the distribution, not just the volume.** "Two million claims" is fine. "Two million claims, 60% under one account" is not. Asking about distribution during data modelling is the whole preventive measure.

**Be suspicious of catch-all records.** Anything named "Unknown", "Default", "Unassigned", or "Various" is a skew candidate.

**Prefer picklists to lookups** for categorization. A lookup to an eight-record object used to constrain a value is a picklist with lock contention.

**Do not default lookup fields** on high-volume objects.

**Keep integration users out of the role hierarchy**, so their owned records generate no hierarchy shares.

**Plan the retention policy before launch**, not after the object reaches ten million rows. Retrofitting archiving onto a populated object is a project. See [[22.3 - Field Audit Trail and Data Retention]].

**Add external IDs from the start.** They index the field for free and make every integration write idempotent. Retrofitting one onto a populated object means a backfill. See [[10.3 - Upsert, Merge and External IDs]].

## Testing at volume

**A developer sandbox proves nothing about volume.** Neither does a scratch org.

**Full sandboxes are the only environment where volume-dependent problems are real** — query selectivity, lock contention, skew, and batch duration all need production-scale data.

**Generating volume** where a Full sandbox is unavailable:

```java
// Deliberate skew, to reproduce the contention
Account catchAll = new Account(Name = 'Unknown Customer');
insert catchAll;

List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
for (Integer i = 0; i < 10000; i++) {
    claims.add(new Warranty_Claim__c(
        Account__c = catchAll.Id,
        Claim_Amount__c = 10000,
        Claim_Date__c = Date.today().addDays(-Math.mod(i, 365))
    ));
}
insert claims;
```

**Reproducing the distribution matters more than the count.** Ten thousand records under one parent demonstrates contention that a million evenly distributed records will not.

See [[21.11 - Sandbox Strategy and Data Seeding]].

## What this section covers

Data modelling for volume, sharing at scale, archiving, bulk loading, query performance, async processing, real failure scenarios with their root causes, and capacity planning.

**The recurring theme:** at scale, the platform's behaviour is dominated by two things — whether queries can use an index, and how much work a change causes the sharing engine to do. Almost every LDV problem reduces to one of those.
