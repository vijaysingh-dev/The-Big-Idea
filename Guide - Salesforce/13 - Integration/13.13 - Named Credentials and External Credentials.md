# Named Credentials and External Credentials

## What they replace

Without them, an outbound callout looks like this:

```java
// Endpoint in a custom setting, credentials in a custom setting, token refresh by hand
Integration_Settings__c settings = Integration_Settings__c.getInstance();

HttpRequest req = new HttpRequest();
req.setEndpoint(settings.ERP_Endpoint__c + '/api/claims');
req.setHeader('Authorization', 'Bearer ' + getOrRefreshToken(settings));
```

Everything wrong with that: credentials stored as data, visible to anyone who can query the setting; a hand-written refresh routine that fails in ways nobody notices; the endpoint duplicated across classes; and a Remote Site Setting to maintain separately.

With a Named Credential:

```java
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:ERP_System/api/claims');
req.setMethod('POST');
```

The platform resolves the URL, obtains and refreshes the token, injects the header, and permits the callout. No secret appears in code or in data.

## The two-object model

Named Credentials were split into two objects, and the separation is the point.

**External Credential** — how to authenticate. The protocol, the identity, the token endpoint, the principals.

**Named Credential** — where to call. The URL, which external credential to use, and the callout options.

One external credential can serve several named credentials, which matters when an external system exposes several base URLs under one identity.

```
External Credential: ERP_OAuth
  Authentication Protocol: OAuth 2.0
  Authentication Flow Type: Browser Flow / JWT / Client Credentials
  Identity Provider URL: https://erp.northwind.com
  Scope: claims:write assets:read

  Principals:
    Name: ERP_Named_Principal
    Sequence Number: 1
    Authentication Parameters: (any additional headers or values)

Named Credential: ERP_System
  URL: https://erp.northwind.com
  External Credential: ERP_OAuth
  Generate Authorization Header: checked
  Allow Formulas in HTTP Header: checked
```

## Authentication protocols

**OAuth 2.0** — with a flow type of browser (authorization code), JWT bearer, or client credentials. The platform handles the token lifecycle entirely.

**Basic** — username and password, stored encrypted in the credential rather than in a custom setting.

**AWS Signature Version 4** — for calling AWS services directly, with the request signing the platform performs.

**JWT** — signing an assertion with a certificate from the org's key store.

**Custom** — you supply headers yourself, with the values held securely in the credential.

**No Authentication** — for public endpoints, still useful because it gives you the URL abstraction and removes the Remote Site Setting.

## Named Principal versus Per User

The decision inside the external credential, and it determines the whole design.

**Named Principal.** One identity for every Salesforce user. The external system sees one caller regardless of who initiated.

Right for system integrations — an ERP sync, a pricing service, a data enrichment API. The external system does not care which Salesforce user triggered the call.

**Per User.** Each Salesforce user authorizes individually, and the token carries their identity in the external system.

Right when the external system enforces per-user permissions — a document repository where each user sees their own files, or a calendar service.

The cost: **every user must complete an authorization once**, through the Named Credentials section of their personal settings. That is friction, and it means the callout fails for users who have not done it.

```java
// Per-user credentials need handling for the unauthorized case
try {
    HttpResponse res = new Http().send(req);
} catch (System.CalloutException e) {
    if (e.getMessage().contains('not authorized')) {
        throw new AuraHandledException(
            'Connect your account under Settings before using this feature.'
        );
    }
    throw e;
}
```

**Permission sets grant access to a principal.** A user without the permission set cannot use the credential at all, which is how access to an external system is controlled from Salesforce.

## Formulas in the endpoint and headers

A Named Credential can carry merge fields, which is how per-user or per-context values reach the external system without code.

```
Named Credential: ERP_System
  Allow Formulas in HTTP Header: checked

Custom Header:
  Name:  X-Salesforce-User
  Value: {!$User.Email}

  Name:  X-Org-Id
  Value: {!$Organization.Id}
```

Available globals include `$User`, `$Organization`, and `$Credential` — the last being how a custom authentication protocol's stored values are injected.

This keeps context out of the Apex and in configuration, which means changing it needs no deployment.

## Calling out

```java
public with sharing class ErpClient {

    public static ClaimResponse submitClaim(Warranty_Claim__c claim) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/v2/claims');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(ClaimPayload.from(claim)));
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() == 401) {
            // the platform refreshes tokens automatically; a persistent 401 means the
            // credential itself is misconfigured or revoked
            throw new IntegrationException('ERP authentication failed — check the named credential');
        }
        if (res.getStatusCode() >= 300) {
            throw new IntegrationException(
                'ERP rejected the claim: ' + res.getStatusCode() + ' ' + res.getBody()
            );
        }

        return (ClaimResponse) JSON.deserialize(res.getBody(), ClaimResponse.class);
    }
}
```

The path after the credential name is appended to the credential's URL. Query strings work normally, and anything user-supplied still needs encoding:

```java
req.setEndpoint('callout:ERP_System/api/assets?serial='
    + EncodingUtil.urlEncode(serialNumber, 'UTF-8'));
```

## No Remote Site Setting needed

A Named Credential replaces the Remote Site Setting for that endpoint. Callouts to a raw URL still require one:

```java
// Requires a Remote Site Setting, and hardcodes the environment
req.setEndpoint('https://erp.northwind.com/api/claims');

// Requires only the named credential, and points at the right environment per org
req.setEndpoint('callout:ERP_System/api/claims');
```

The second point matters as much as the first: the same code deployed to a sandbox calls the sandbox ERP, because the credential in that org points there. Hardcoded URLs mean environment-specific code or a custom setting lookup.

## Calling Salesforce from Salesforce

A frequently useful pattern: a Named Credential pointing at the org's own API.

Necessary because `UserInfo.getSessionId()` is **not available in asynchronous contexts** — a Queueable or Batch job calling the org's own REST API cannot use it. See [[13.10 - Authentication and OAuth Flows]].

```
External Credential: Self_Org
  Protocol: OAuth 2.0, JWT Bearer
  (a connected app in the same org, with the integration user as principal)

Named Credential: Self
  URL: https://myorg.my.salesforce.com
```

```java
public with sharing class MetadataQueryService implements Queueable, Database.AllowsCallouts {

    public void execute(QueueableContext context) {
        HttpRequest req = new HttpRequest();
        // the org's own Tooling API, callable from async because the credential handles auth
        req.setEndpoint('callout:Self/services/data/v62.0/tooling/query/'
            + '?q=' + EncodingUtil.urlEncode(
                'SELECT Name, TableEnumOrId FROM ApexTrigger', 'UTF-8'));
        req.setMethod('GET');

        HttpResponse res = new Http().send(req);
        processTriggerInventory(res.getBody());
    }
}
```

## Deployment

Named credentials and external credentials deploy as metadata, **without their secrets**.

```
force-app/main/default/
    namedCredentials/ERP_System.namedCredential-meta.xml
    externalCredentials/ERP_OAuth.externalCredential-meta.xml
```

The structure deploys; the client secret, private key, or password does not. Each org needs its secrets populated, once, by someone with the permission.

That is correct behaviour — secrets should not live in a repository — and it means the deployment checklist includes a manual step. Documenting which credentials need which secrets per environment is worth doing, because the failure mode is a deployed integration that authenticates in the sandbox and not in production.

**Permission set assignments for principals** do deploy, which is the part that is easy to forget: deploying the credential without the permission set means no user can use it.

## Migrating from the old model

Legacy Named Credentials held authentication inline rather than referencing an external credential. Both forms work; the new one is where the platform is going, and it is required for some newer authentication options.

Migrating an org with hardcoded endpoints and stored credentials, in order:

1. Create the external credential and named credential
2. Assign the permission set granting access to the principal
3. Replace `setEndpoint` calls with `callout:` references, one class at a time
4. Remove the Remote Site Settings
5. Delete the custom setting holding the credentials — and **rotate those credentials**, because they were stored in queryable data and should be considered compromised

Step 5's rotation is the part people skip. A password that lived in a custom setting has been visible to every user who could query it.

## Practical guidance

**Use a Named Credential for every callout**, including unauthenticated ones — the URL abstraction alone is worth it.

**Never store credentials in a custom setting or custom metadata.**

**Named Principal for system integrations, Per User only when the external system enforces per-user permissions.**

**Grant principal access through permission sets.**

**Use formulas in headers** for per-user context rather than building it in Apex.

**Point at the org itself** when async code needs the org's own API.

**Document the per-environment secrets** that deployment does not carry.

**Rotate any credential you find in a custom setting.**
