# Aura Events

## The part with no LWC equivalent

LWC uses standard DOM events. Aura built its own system, with two event types and a registration model that must be declared in markup on both sides.

This is the concept most worth understanding when reading inherited Aura, because event flow is where the behaviour lives and it is not visible from the component that fires it.

## Component events

Travel **up** the containment hierarchy, from the firing component to its ancestors. The Aura equivalent of a bubbling `CustomEvent`.

**Define the event:**

```xml
<!-- ClaimSelected.evt -->
<aura:event type="COMPONENT" description="Fired when a claim row is selected">
    <aura:attribute name="claimId" type="Id"/>
    <aura:attribute name="claimNumber" type="String"/>
</aura:event>
```

**Register it in the firing component:**

```xml
<!-- claimRow.cmp -->
<aura:component>
    <aura:attribute name="claim" type="Object"/>
    <aura:registerEvent name="claimSelected" type="c:ClaimSelected"/>

    <div onclick="{!c.handleClick}">{!v.claim.Claim_Number__c}</div>
</aura:component>
```

**Fire it:**

```javascript
({
    handleClick: function(component, event, helper) {
        const claim = component.get("v.claim");

        // getEvent uses the registered NAME, not the event type
        const selectEvent = component.getEvent("claimSelected");
        selectEvent.setParams({
            claimId: claim.Id,
            claimNumber: claim.Claim_Number__c
        });
        selectEvent.fire();
    }
})
```

**Handle it in the parent:**

```xml
<!-- claimList.cmp -->
<aura:component>
    <aura:iteration items="{!v.claims}" var="claim">
        <c:claimRow claim="{!claim}" onclaimSelected="{!c.handleClaimSelected}"/>
    </aura:iteration>
</aura:component>
```

```javascript
({
    handleClaimSelected: function(component, event, helper) {
        const claimId = event.getParam("claimId");
        component.set("v.selectedClaimId", claimId);
    }
})
```

Four places to get right: the event definition, the registration, the fire, and the handler attribute. Missing any one produces silence.

**`component.getEvent()` takes the registered name**, not the event type — using `c:ClaimSelected` there is a common error.

## Application events

Broadcast to **every** component in the application that handles them, regardless of hierarchy. There is no equivalent in LWC, and that is deliberate.

```xml
<!-- ClaimApproved.evt -->
<aura:event type="APPLICATION" description="A claim has been approved">
    <aura:attribute name="claimId" type="Id"/>
    <aura:attribute name="approvedAmount" type="Decimal"/>
</aura:event>
```

```javascript
// firing
const appEvent = $A.get("e.c:ClaimApproved");
appEvent.setParams({ claimId: claimId, approvedAmount: amount });
appEvent.fire();
```

```xml
<!-- handling, in any component anywhere -->
<aura:handler event="c:ClaimApproved" action="{!c.handleClaimApproved}"/>
```

**`$A.get("e.namespace:EventName")`** rather than `component.getEvent` — application events are global rather than component-scoped.

**No registration needed in the firing component.**

## Why application events were a problem

They are the reason LWC does not have them.

**No visible contract.** Any component can fire; any component can handle. Reading a component tells you nothing about who responds to what it fires.

**Debugging is hard.** An event fires and five components react, in an order you cannot control, none of which are referenced from the firing component.

**Loops happen.** Component A handles an event and fires another that B handles by firing the first. There is nothing structural preventing it.

**Performance.** Every handling component is notified on every fire, whether the event concerns it or not.

Lightning Message Service is the modern answer, and it is better in the ways that matter: the channel is declared metadata, subscriptions are explicit in code, and scope is controllable. See [[14.8 - Lightning Message Service]].

When migrating an application event, **LMS is the target**, not a composed DOM event.

## Standard platform events

Aura has a set of built-in application events, and these are what most inherited code actually uses.

```javascript
// A toast
const toast = $A.get("e.force:showToast");
toast.setParams({
    title: "Success",
    message: "Claim approved",
    type: "success",
    mode: "dismissible"
});
toast.fire();

// Navigate to a record
const navEvent = $A.get("e.force:navigateToSObject");
navEvent.setParams({ recordId: claimId, slideDevName: "detail" });
navEvent.fire();

// Refresh the view
$A.get("e.force:refreshView").fire();

// Close a quick action modal
$A.get("e.force:closeQuickAction").fire();

// Tell the platform a record changed
const updateEvent = $A.get("e.force:recordSaveSuccess");
```

Their LWC equivalents:

| Aura event | LWC |
| --- | --- |
| `force:showToast` | `ShowToastEvent` |
| `force:navigateToSObject` | `NavigationMixin.Navigate` |
| `force:navigateToURL` | `NavigationMixin.Navigate` with `standard__webPage` |
| `force:refreshView` | `refreshApex` and `notifyRecordUpdateAvailable` |
| `force:closeQuickAction` | `CloseActionScreenEvent` |
| `force:createRecord` | `NavigationMixin.Navigate` with `actionName: 'new'` |

**`force:refreshView` has no exact LWC equivalent.** It refreshes the entire page — every component, standard and custom. `refreshApex` refreshes one wire; `notifyRecordUpdateAvailable` refreshes LDS consumers of one record.

That difference matters during migration: code relying on `force:refreshView` to update several unrelated components needs each of them handled explicitly. See [[14.11 - refreshApex and Cache Invalidation]].

## Handling events from an LWC child

An Aura component can handle a standard DOM `CustomEvent` fired by a nested LWC, which is the key interoperability mechanism.

```xml
<aura:component>
    <!-- the handler attribute is the lowercase event name prefixed with on -->
    <c:claimList onclaimselected="{!c.handleClaimSelected}"/>
</aura:component>
```

```javascript
({
    handleClaimSelected: function(component, event, helper) {
        // detail is on the raw event, not accessed via getParam
        const claimId = event.getParam("claimId");
        component.set("v.selectedId", claimId);
    }
})
```

The LWC fires a plain `CustomEvent`; Aura receives it through the `on` attribute and reads the payload with `getParam`, which maps onto the event's `detail`.

**This works in one direction only.** An LWC cannot contain an Aura component, so an Aura child cannot fire an event to an LWC parent. See [[15.4 - Aura to LWC Migration]].

## Event phases

Component events have `bubble`, `capture`, and `default` phases, with `stopPropagation` and `preventDefault` available in handlers.

Almost never used in practice, and worth recognizing if you meet it — a handler with `phase="capture"` fires before the ones below it, which is occasionally used to intercept and cancel.

## Firing from a helper

A small mechanical point that trips people up:

```javascript
// helper
({
    notifySelection: function(component, claim) {
        // the component reference must be passed in; helpers have no implicit component
        const selectEvent = component.getEvent("claimSelected");
        selectEvent.setParams({ claimId: claim.Id });
        selectEvent.fire();
    }
})
```

Helper functions receive no automatic `component`, so it is always the first parameter by convention.

## Debugging events

Aura events failing is usually silence rather than an error, and the causes are a short list.

**The event was never registered** in the firing component.

**The handler attribute name is wrong** — it is `on` plus the **registered name** with its original casing, so `onclaimSelected` not `onClaimSelected`.

**`getEvent` was given the type instead of the name.**

**The event was created but never fired.**

**For application events, `$A.get` returned null** because the event name or namespace is wrong. Firing on null throws a confusing error.

```javascript
const appEvent = $A.get("e.c:ClaimApproved");
if (!appEvent) {
    console.error("Event not found — check the namespace and name");
    return;
}
```

Enabling **Debug Mode** in Setup makes the framework's error messages readable, which for event problems is the difference between a five-minute fix and an hour.

## Migrating events

The mapping when converting a component:

| Aura | LWC |
| --- | --- |
| Component event | `CustomEvent`, default flags |
| Component event across several levels | Re-dispatch at each level |
| Application event | Lightning Message Service |
| `force:showToast` | `ShowToastEvent` |
| `force:navigateToSObject` | `NavigationMixin` |
| `force:refreshView` | `refreshApex` plus `notifyRecordUpdateAvailable`, per consumer |
| Two-way attribute binding | Property down, event up |

**Application events are the hardest part of a migration**, because there is no equivalent and the consumers are not discoverable from the firing code. Finding them means searching the metadata:

```bash
grep -rl "ClaimApproved" force-app/main/default/aura/
```

That grep, run before changing anything, is the practical substitute for a dependency graph.

## Practical guidance

**Component events for parent notification**, and they map cleanly to `CustomEvent`.

**Application events are the thing to migrate first** — they are the source of most Aura debugging difficulty.

**Check all four places** when an event does nothing: definition, registration, fire, handler.

**Null-check `$A.get`** for application events.

**Use the registered name in `getEvent`**, not the type.

**Search the metadata for consumers** before changing an application event.

**Prefer LMS over composed DOM events** when replacing an application event.
