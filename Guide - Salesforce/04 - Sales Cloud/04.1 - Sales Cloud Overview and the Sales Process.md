# Sales Cloud Overview and the Sales Process

## What Sales Cloud is

Sales Cloud is the set of standard objects, automation, and features that model a company's sales process, built on the Lightning Platform. It is not a separate system — it is Account, Contact, Lead, Opportunity, and their surrounding features, plus the reporting and forecasting built on them.

For a developer, the useful framing is that Sales Cloud is **a set of conventions the platform enforces**. Opportunity has an `IsWon` field the platform maintains. Forecasting reads from `ForecastCategory`. Lead conversion is a platform operation, not something you code. Understanding which parts are platform-managed and which are yours to build is most of what makes Sales Cloud work well.

## The pipeline

The flow that everything else supports:

```
Campaign  →  Lead  →  [conversion]  →  Account + Contact + Opportunity
                                              ↓
                                       Products / Price Book
                                              ↓
                                           Quote
                                              ↓
                                     Order / Contract
                                              ↓
                                     Forecast / Renewal
```

Each arrow is a place where automation, validation, and integration typically live.

## The objects and what each is really for

**Campaign.** A marketing program. Generates leads and, later, attributes revenue back to itself. See [[04.12 - Campaigns and Campaign Influence]].

**Lead.** Unqualified interest. A holding pen, deliberately unlinked from Account and Contact so unverified data stays out of the clean database. See [[04.2 - Leads and Lead Management]].

**Account.** The company. The centre of the model in business-to-business selling. See [[04.5 - Accounts - Business vs Person Accounts]].

**Contact.** A person at the company. See [[04.6 - Contacts and Contact Roles]].

**Opportunity.** A potential sale with an amount, a close date, and a stage. Where revenue reporting comes from, and therefore the most politically sensitive object in the org. See [[04.8 - Opportunities and Sales Stages]].

**Product2, Pricebook2, PricebookEntry, OpportunityLineItem.** What is being sold and at what price. See [[04.10 - Products, Price Books and Pricing]].

**Quote, Order, Contract.** The commercial documents. See [[04.11 - Quotes, Orders and Contracts]].

**Forecast.** The aggregated prediction of what will close. See [[04.13 - Forecasting and Revenue Management]].

## The sales process as configuration

The **Sales Process** is a metadata object that defines which Opportunity stages are available. It is tied to a Record Type, which is how one org supports several different sales motions on the same object.

For our manufacturing example, two motions:

```
New Machine Sale
  Qualification → Site Survey → Technical Proposal → Commercial Proposal
  → Negotiation → Closed Won / Closed Lost

Spare Parts Sale
  Quote Requested → Quote Sent → Negotiation → Closed Won / Closed Lost
```

Each stage carries configuration that other features depend on:

- **Probability** — default likelihood, used in weighted pipeline reports
- **Forecast Category** — Pipeline, Best Case, Commit, Closed, or Omitted; drives forecasting
- **Type** — Open, Closed/Won, or Closed/Lost; drives the `IsClosed` and `IsWon` fields

That last point matters for developers. `IsClosed` and `IsWon` are **read-only fields the platform derives** from the stage's Type. You cannot set them. Changing `StageName` to a stage configured as Closed/Won is what sets `IsWon = true`.

```java
// Correct: change the stage, the platform derives the rest
opp.StageName = 'Closed Won';
update opp;

// Fails: these fields are not writeable
opp.IsWon = true;
```

## Designing a stage model

The stage list looks like a simple picklist and is actually one of the highest-impact decisions in a Sales Cloud implementation. Changing it later invalidates historical reporting, breaks saved reports and dashboards, confuses forecast history, and requires migrating existing records.

Principles that hold up:

**Stages should be about the buyer, not the seller.** "Proposal Sent" describes what your team did. "Proposal Under Review" describes where the deal is. The second is more useful because it tells you what is actually blocking.

**Every stage needs an exit criterion.** If nobody can say what must be true to move from stage three to stage four, the stage is decoration and reps will guess, which makes the pipeline report meaningless.

**Six to eight stages is the practical range.** Fewer and the pipeline gives no signal; more and reps skip stages, which is worse than having none.

**Do not encode approvals or internal process as stages.** "Awaiting Legal Review" is a status field or an approval process, not a pipeline stage. Mixing them makes conversion-rate analysis impossible.

## Where automation typically lives

The recurring patterns in a real Sales Cloud implementation:

- **Validation on stage progression** — required fields per stage, enforced by validation rules that check `ISPICKVAL(StageName, ...)` and `ISCHANGED`
- **Stage change history** — capturing when each stage was entered, for cycle-time analysis
- **Discount approval** — an approval process triggered by a discount threshold ([[04.16 - Approval Processes in the Sales Cycle]])
- **Roll-ups to Account** — total won revenue, open pipeline, last won date
- **Renewal creation** — generating next year's opportunity when this one closes won
- **ERP integration** — pushing closed-won deals downstream
- **Territory or team assignment** on creation

A representative example, capturing stage timing so the business can measure cycle time per stage:

```java
public with sharing class OpportunityStageService {

    public static void recordStageEntry(List<Opportunity> newOpps, Map<Id, Opportunity> oldOpps) {
        List<Opportunity_Stage_History__c> entries = new List<Opportunity_Stage_History__c>();
        Datetime now = Datetime.now();

        for (Opportunity opp : newOpps) {
            Opportunity prior = oldOpps == null ? null : oldOpps.get(opp.Id);
            if (prior != null && prior.StageName == opp.StageName) {
                continue;
            }
            entries.add(new Opportunity_Stage_History__c(
                Opportunity__c = opp.Id,
                Stage__c = opp.StageName,
                Previous_Stage__c = prior == null ? null : prior.StageName,
                Entered_On__c = now,
                Amount_At_Entry__c = opp.Amount
            ));
        }

        if (!entries.isEmpty()) {
            insert entries;
        }
    }
}
```

Called from an after-insert and after-update handler. Salesforce does track stage duration natively through `OpportunityHistory`, but that object has limitations around custom reporting, which is why many orgs maintain their own.

## What Sales Cloud gives you for free

Worth listing, because rebuilding any of it is a classic expensive mistake:

- Forecasting, including quota tracking and forecast hierarchy
- Lead conversion, including the mapping of custom fields
- Products, price books, and multi-currency pricing
- Quote generation with PDF output
- Campaign influence and attribution
- Sales Path and Kanban views
- Opportunity teams and splits
- Einstein lead and opportunity scoring
- A large library of standard reports and report types
- The mobile experience for all of it

The corollary: **model your sales process onto Opportunity even if the fit is imperfect.** A custom `Deal__c` object loses every item on that list.
