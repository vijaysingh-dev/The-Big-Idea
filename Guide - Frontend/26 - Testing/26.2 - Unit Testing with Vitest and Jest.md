# Unit Testing with Vitest and Jest

## Vitest or Jest

Both provide the same API surface — `describe`, `test`, `expect`, mocking, coverage. The practical differences:

| | Vitest | Jest |
| --- | --- | --- |
| Config | reuses your Vite config | separate, plus a transform setup |
| ESM | native | requires transformation |
| TypeScript | via Vite, no extra step | needs `ts-jest` or Babel |
| Speed | faster, especially in watch mode | slower cold start |
| Ecosystem | growing | larger, more articles and plugins |

If the project uses Vite, use Vitest — it shares the same transform pipeline, so a module that builds correctly also tests correctly, which removes an entire category of "works in the app, fails in tests" problems ([[27.3 - Vite]]).

Jest remains the default for Next.js, Create React App legacy projects, and React Native.

The API compatibility means most of this note applies to both; `vi` and `jest` are largely interchangeable.

## Setup

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    globals: true,
    setupFiles: "./src/test/setup.ts",
    css: false,
  },
});
```

```ts
// src/test/setup.ts
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(() => cleanup());
```

`environment: "jsdom"` gives a simulated DOM. For pure logic tests, `node` is faster — Vitest supports per-file environments via a comment:

```ts
// @vitest-environment node
```

`globals: true` avoids importing `describe`/`test`/`expect` in every file. Some teams prefer explicit imports; either is fine, but be consistent.

## Structure

```ts
import { describe, test, expect, beforeEach, vi } from "vitest";

describe("formatCurrency", () => {
  test("formats whole rupees without decimals", () => {
    expect(formatCurrency(1000)).toBe("₹1,000");
  });

  test("rounds to two decimal places", () => {
    expect(formatCurrency(1000.456)).toBe("₹1,000.46");
  });

  test("handles zero", () => {
    expect(formatCurrency(0)).toBe("₹0");
  });
});
```

`test.each` removes repetition for table-driven cases:

```ts
test.each([
  [0, "₹0"],
  [1000, "₹1,000"],
  [-500, "-₹500"],
])("formats %i as %s", (input, expected) => {
  expect(formatCurrency(input)).toBe(expected);
});
```

The failure message names the specific row, which is what makes this better than a loop inside one test.

## Useful matchers

```ts
expect(value).toBe(3);                    // Object.is — primitives, references
expect(obj).toEqual({ a: 1 });            // deep equality, ignores undefined keys
expect(obj).toStrictEqual({ a: 1 });      // also checks undefined keys and class
expect(arr).toContain(item);
expect(obj).toMatchObject({ a: 1 });      // partial match
expect(fn).toThrow(/not found/);
expect(value).toBeCloseTo(0.3);           // floating point
await expect(promise).rejects.toThrow(HttpError);
await expect(promise).resolves.toEqual(data);
```

`toBe` versus `toEqual` is the most common mistake: `toBe` compares references, so `expect({a:1}).toBe({a:1})` fails ([[05.3 - Types Coercion and Equality]]).

`toBeCloseTo` exists because `0.1 + 0.2 !== 0.3` in floating point.

For partial matching inside deep structures:

```ts
expect(result).toEqual({
  id: expect.any(String),
  createdAt: expect.any(Date),
  name: "Product",
});
```

`expect.any`, `expect.objectContaining` and `expect.arrayContaining` avoid asserting on values you do not control, such as generated ids and timestamps.

## Mocking

```ts
const fn = vi.fn();
const fn = vi.fn(() => "result");
const fn = vi.fn().mockResolvedValue(data);
const fn = vi.fn().mockRejectedValueOnce(new Error("fail")).mockResolvedValue(ok);

expect(fn).toHaveBeenCalledWith("arg");
expect(fn).toHaveBeenCalledTimes(2);
expect(fn).toHaveBeenNthCalledWith(1, "first");
```

Module mocking:

```ts
vi.mock("./analytics", () => ({
  track: vi.fn(),
}));

// Partial — keep the real module, replace one export
vi.mock("./config", async (importOriginal) => ({
  ...(await importOriginal<typeof import("./config")>()),
  API_URL: "http://test",
}));
```

`vi.mock` is **hoisted** above imports, so referencing a variable declared with `const` inside the factory fails. Use `vi.hoisted` when the mock needs a shared reference:

```ts
const { mockTrack } = vi.hoisted(() => ({ mockTrack: vi.fn() }));
vi.mock("./analytics", () => ({ track: mockTrack }));
```

Reset between tests:

```ts
afterEach(() => {
  vi.clearAllMocks();     // clears call history
  vi.resetAllMocks();     // also resets implementations
  vi.restoreAllMocks();   // restores spies to originals
});
```

Or `mockReset: true` in config. Forgetting this produces tests that pass alone and fail in a suite ([[26.1 - Testing Philosophy]]).

**Prefer network-level mocking** over module mocking for anything that fetches — it exercises the real API layer ([[26.4 - Mocking the Network with MSW]]).

## Spies

```ts
const spy = vi.spyOn(console, "error").mockImplementation(() => {});
const spy = vi.spyOn(storage, "setItem");

expect(spy).toHaveBeenCalledWith("key", "value");
spy.mockRestore();
```

`spyOn` wraps the real implementation, so you can assert calls while keeping behavior. Silencing `console.error` is a common use — though a test that needs to silence it often indicates a genuine warning worth fixing.

## Time

```ts
beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

test("debounces", () => {
  const fn = vi.fn();
  const debounced = debounce(fn, 300);

  debounced();
  debounced();
  expect(fn).not.toHaveBeenCalled();

  vi.advanceTimersByTime(300);
  expect(fn).toHaveBeenCalledTimes(1);
});
```

```ts
vi.setSystemTime(new Date("2026-01-15T10:00:00Z"));
```

Fake timers are essential for debounce, throttle, polling and timeout logic ([[29.1 - Debounce and Throttle]]). Freezing the clock makes date-dependent tests deterministic.

With React Testing Library, fake timers need `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`, or user interactions hang waiting for real timers ([[26.3 - React Testing Library]]).

## Testing pure logic

The easiest and highest-value unit tests are on code with no dependencies:

```ts
test("reducer handles success", () => {
  const state = reducer({ status: "loading" }, { type: "success", data: [1] });
  expect(state).toEqual({ status: "success", data: [1] });
});
```

Reducers, validators, formatters, sorting comparators, permission checks and pricing logic are all pure functions with clear inputs and outputs ([[17.10 - useReducer]]). Extracting logic into pure functions specifically to make it testable is a legitimate design pressure.

## Snapshots, sparingly

```ts
expect(result).toMatchInlineSnapshot(`{ "total": 1200 }`);
```

Inline snapshots for small, meaningful values are useful — the expected value sits next to the assertion.

Large component snapshots are close to worthless: nobody reads a 200-line diff, so they get updated reflexively with `-u`, which means they catch nothing. If a snapshot is longer than a screen, it is not being reviewed.

## Coverage

```bash
vitest run --coverage
```

```ts
coverage: {
  provider: "v8",
  exclude: ["**/*.config.*", "**/types/**", "**/*.d.ts"],
}
```

Use it to find untested critical paths, not as a merge gate ([[26.1 - Testing Philosophy]]).

## How senior engineers actually use this

**They match the test runner to the build tool**, so transforms cannot diverge.

**They extract pure logic** specifically to make it cheap to test.

**They reset mocks globally** rather than per file, since forgetting is the default failure.

**They use `test.each` for table-driven cases**, which gives named failures.

**They avoid large snapshots**, and use inline snapshots for small values.

**They mock at the network boundary** and reserve `vi.mock` for genuinely unavoidable cases.

## Common pitfalls

- `toBe` on objects and arrays.
- Mocks not reset, so tests pass alone and fail together.
- `vi.mock` referencing a variable it cannot see due to hoisting.
- Fake timers without `advanceTimers` in `userEvent.setup`, hanging the test.
- Large snapshots updated reflexively.
- Floating-point comparison with `toBe` instead of `toBeCloseTo`.
- Asserting on generated ids and timestamps instead of `expect.any`.
- Mocking modules where network-level mocking would exercise more real code.

## Interview angle

Runner specifics rarely get direct questions, but they appear in practical exercises. The details worth having ready: `toBe` compares references while `toEqual` compares structure, `vi.mock` is hoisted above imports, mocks must be reset between tests or state leaks, and fake timers are what make debounce and polling testable. Mentioning that you prefer network-level mocking over module mocking connects the tooling back to the confidence argument.
