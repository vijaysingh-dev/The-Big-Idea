# Many-to-Many and Junction Objects

## The problem

Salesforce relationship fields point one way: a child holds a reference to one parent. That handles one-to-many perfectly.

It does not handle many-to-many. A machine can be covered by several service contracts, and a service contract can cover several machines. Neither side is the parent.

## The solution

Create a third object that sits between them, holding two relationships. This is a **junction object**, and the pattern is identical to a join table in a relational database.

```
Machine__c                                    Service_Contract__c
    |                                                |
    |            Machine_Coverage__c                 |
    +---- master-detail (primary) ----+---- master-detail (secondary) ----+
```

Each `Machine_Coverage__c` record represents one machine being covered by one contract. Two hundred machines on one contract means two hundred junction records.

## Building it

1. Create the junction object. Its name field is almost always Auto Number, because a junction record has no meaningful name of its own.
2. Add the first master-detail relationship. This becomes the **primary** relationship.
3. Add the second master-detail relationship. This becomes the **secondary**.

Both should normally be master-detail. Two lookups technically work and are sometimes used, but you lose roll-ups and you allow orphaned junction records with an empty side, which is nearly always a data quality problem waiting to happen.

## Primary versus secondary, and why it matters

The order you create the relationships is not cosmetic. The first master-detail becomes the primary, and that has three real effects:

**Ownership and sharing come from the primary parent.** Who can see a coverage record is determined by who can see the machine, not the contract.

**Deleting either parent deletes the junction record.** This is true of both, and it is correct — a coverage record without one of its two sides is meaningless.

**The junction appears under the primary parent by default** in list views and reports, and the record's detail page emphasizes it.

Choose the primary as the parent whose sharing model should govern, and whose perspective is the more natural one for users. If service technicians own machines and contract managers own contracts, and coverage records should follow the technicians, machine is primary.

Changing which relationship is primary later is possible but disruptive, because it changes sharing on every existing junction record.

## Roll-ups from a junction

Because both relationships are master-detail, both parents can have roll-up summaries over the junction. This is one of the main reasons to use master-detail on both sides.

```
Roll-Up Summary on Service_Contract__c
  Summarized object: Machine_Coverage__c
  Operation: COUNT
  Field label: Machines Covered

Roll-Up Summary on Machine__c
  Summarized object: Machine_Coverage__c
  Operation: MAX
  Field: Contract__r.End_Date__c is not allowed; use a formula field on the junction instead
  Field label: Latest Coverage End
```

That second one shows a real constraint: a roll-up can only summarize a field on the junction object itself, not a field on its other parent. The standard workaround is a formula field on the junction that pulls the value across, and then a roll-up over that formula.

```
// Formula field Coverage_End_Date__c on Machine_Coverage__c
Service_Contract__r.End_Date__c
```

Then roll up MAX of `Coverage_End_Date__c` onto Machine. This two-step pattern comes up constantly and is worth recognizing on sight.

## Extra fields on the junction

The junction is a real object, so it can carry data of its own — and this is where the pattern earns its value beyond a simple link.

`Machine_Coverage__c` can hold `Coverage_Start_Date__c`, `Coverage_Level__c`, `Included_Parts__c`, `Monthly_Fee__c`. None of these belong on the machine or on the contract; they describe the *combination*.

Recognizing when a requirement needs data on the relationship rather than on either side is a mark of a good data modeller. "Which machines are on this contract, and at what service level each" is a junction with fields, not a multi-select picklist.

## Querying across a junction

Getting from one side to the other requires two hops, because there is no direct relationship.

```sql
-- From contract to machines
SELECT Id, Name,
       (SELECT Machine__r.Name, Machine__r.Serial_Number__c, Coverage_Level__c
        FROM Machine_Coverages__r
        WHERE Coverage_End_Date__c >= TODAY)
FROM Service_Contract__c
WHERE Status__c = 'Active'
```

```sql
-- From machine to contracts
SELECT Id, Serial_Number__c,
       (SELECT Service_Contract__r.Name, Service_Contract__r.End_Date__c
        FROM Machine_Coverages__r)
FROM Machine__c
WHERE Account__c = :accountId
```

In Apex, building a usable structure from the junction is a routine task:

```java
public with sharing class CoverageService {

    public static Map<Id, List<Service_Contract__c>> contractsByMachine(Set<Id> machineIds) {
        Map<Id, List<Service_Contract__c>> result = new Map<Id, List<Service_Contract__c>>();

        for (Machine_Coverage__c coverage : [
            SELECT Machine__c, Service_Contract__r.Id, Service_Contract__r.Name,
                   Service_Contract__r.End_Date__c
            FROM Machine_Coverage__c
            WHERE Machine__c IN :machineIds AND Coverage_End_Date__c >= TODAY
        ]) {
            if (!result.containsKey(coverage.Machine__c)) {
                result.put(coverage.Machine__c, new List<Service_Contract__c>());
            }
            result.get(coverage.Machine__c).add(coverage.Service_Contract__r);
        }
        return result;
    }
}
```

## Standard junction objects to recognize

The pattern is used throughout the standard model, and recognizing it saves time:

- **OpportunityContactRole** — Opportunity to Contact, with a Role field
- **CampaignMember** — Campaign to Lead or Contact, with a Status field
- **AccountContactRelation** — Contact to additional Accounts, with a Role field
- **OpportunityLineItem** — Opportunity to PricebookEntry, with quantity and price
- **AccountTeamMember**, **OpportunityTeamMember** — record to User, with an access level
- **EntitlementContact** — Entitlement to Contact

Every one of them carries fields describing the relationship itself. That is the tell.

## Preventing duplicates

Nothing stops the same machine being linked to the same contract twice. The platform has no composite unique key.

Two approaches, and mature orgs usually use both:

**A duplicate-prevention key.** Add a text field marked Unique, populated by a before-save flow or trigger with the two IDs concatenated. The database then rejects duplicates regardless of how they arrive — user interface, API, or Data Loader.

```java
// In a before insert/update trigger handler
for (Machine_Coverage__c cov : coverages) {
    cov.Unique_Key__c = cov.Machine__c + '-' + cov.Service_Contract__c;
}
```

**A validation rule or Apex check.** Catches it earlier with a friendlier message, but only on the paths it covers.

The unique field is the one that actually guarantees it, because it is enforced at the database level. This pattern is worth knowing because the requirement appears on nearly every junction object eventually.

## When not to use a junction

**When one side is a small fixed list.** Linking a machine to a set of three certification types does not need an object; a multi-select picklist or three checkboxes is lighter. The threshold is roughly whether the list is data that business users maintain, or metadata that changes rarely.

**When the relationship carries no information and volume is enormous.** Hundreds of millions of junction records will hit storage and query problems. Consider whether the relationship can be derived instead of stored.

**When Salesforce already provides it.** Contacts to Multiple Accounts, Campaign Members, and Opportunity Contact Roles all exist. Building a parallel custom junction alongside a standard one splits the data and breaks standard reporting.
