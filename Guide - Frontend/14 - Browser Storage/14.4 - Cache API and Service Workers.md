# Cache API and Service Workers

A **service worker** is a script that runs separately from any page and acts as a programmable network proxy. Every request from pages under its scope can be intercepted, answered from a cache, modified, or passed through.

It is what makes offline web applications possible, and it is also the most dangerous thing you can deploy — a broken service worker can render a site permanently unloadable for users who already have it installed.

## Registration and lifecycle

```js
if ("serviceWorker" in navigator) {
  const reg = await navigator.serviceWorker.register("/sw.js", { scope: "/" });
}
```

Requirements: HTTPS (localhost exempt), and the script must be served from within the scope it claims. A worker at `/js/sw.js` cannot control `/` unless the server sends a `Service-Worker-Allowed` header.

The lifecycle has four states and they matter:

```
install -> waiting -> activate -> active
```

**`install`** — precache assets. Fires once per new worker version.

**`waiting`** — the new worker is installed but the old one still controls open pages. It stays here until every page controlled by the old worker closes. This is the safety mechanism that prevents two versions of your app coexisting.

**`activate`** — clean up old caches. Fires when the new worker takes control.

```js
self.addEventListener("install", (e) => {
  e.waitUntil(
    caches.open(CACHE_NAME).then(c => c.addAll(PRECACHE_URLS))
  );
});

self.addEventListener("activate", (e) => {
  e.waitUntil(
    caches.keys().then(keys =>
      Promise.all(keys.filter(k => k !== CACHE_NAME).map(k => caches.delete(k)))
    )
  );
});
```

`self.skipWaiting()` and `clients.claim()` bypass the waiting phase and take control of existing pages immediately. Convenient, and risky: a page loaded with version 1's JavaScript suddenly gets version 2's assets, which can produce chunk-load failures ([[08.2 - Dynamic Imports]]). The safer pattern is to prompt the user:

```js
// In the page
reg.addEventListener("updatefound", () => {
  const newWorker = reg.installing;
  newWorker.addEventListener("statechange", () => {
    if (newWorker.state === "installed" && navigator.serviceWorker.controller) {
      showUpdateToast(() => newWorker.postMessage({ type: "SKIP_WAITING" }));
    }
  });
});
```

## The Cache API

A separate store from HTTP cache, holding `Request`/`Response` pairs. Available in both pages and workers.

```js
const cache = await caches.open("v1");

await cache.add("/style.css");                 // fetch and store
await cache.addAll(["/", "/app.js"]);
await cache.put(request, response);            // store a specific pair

const cached = await cache.match("/style.css");
await cache.delete("/style.css");
await caches.keys();                           // all cache names
```

Two things to know: a `Response` body can be consumed only once, so caching a response you also want to return requires `response.clone()`. And `caches.match()` searches all caches, while `cache.match()` searches one.

## Caching strategies

The five standard patterns, and where each fits:

**Cache first** — check cache, fall back to network. For hashed static assets that never change.

```js
const cached = await caches.match(request);
return cached ?? fetch(request);
```

**Network first** — try network, fall back to cache. For content that should be fresh but must work offline.

**Stale-while-revalidate** — return the cache immediately, fetch and update in the background. Fast and eventually fresh; the best default for most content.

```js
const cached = await cache.match(request);
const fetching = fetch(request).then(res => {
  cache.put(request, res.clone());
  return res;
});
return cached ?? fetching;
```

**Network only** — never cache. Analytics, mutations, anything non-idempotent.

**Cache only** — precached assets exclusively.

A complete fetch handler routes by request type:

```js
self.addEventListener("fetch", (event) => {
  const { request } = event;

  if (request.method !== "GET") return;              // never cache mutations

  if (request.mode === "navigate") {
    event.respondWith(networkFirst(request));        // HTML — prefer fresh
  } else if (request.destination === "image") {
    event.respondWith(cacheFirst(request));
  } else if (url.pathname.startsWith("/api/")) {
    event.respondWith(staleWhileRevalidate(request));
  }
  // no respondWith = normal browser handling
});
```

Not calling `respondWith` lets the request proceed normally, which is the correct default for anything you have not deliberately decided about.

## Offline navigation fallback

```js
async function networkFirst(request) {
  try {
    const response = await fetch(request);
    const cache = await caches.open(CACHE_NAME);
    cache.put(request, response.clone());
    return response;
  } catch {
    return (await caches.match(request)) ?? caches.match("/offline.html");
  }
}
```

An offline page is the minimum viable offline experience and takes fifteen minutes to add.

## Background sync

Queue failed mutations and retry when connectivity returns:

```js
self.addEventListener("sync", (event) => {
  if (event.tag === "sync-posts") {
    event.waitUntil(sendQueuedPosts());
  }
});
```

The queue lives in IndexedDB — service workers cannot access `localStorage` ([[14.3 - IndexedDB]]). Browser support is limited to Chromium, so treat it as an enhancement over an in-page retry queue rather than the primary mechanism.

## Workbox

Hand-writing correct service workers is difficult — cache versioning, precache manifests, navigation fallbacks, expiration, and the update flow all have subtle failure modes. Workbox handles them:

```js
import { precacheAndRoute } from "workbox-precaching";
import { registerRoute } from "workbox-routing";
import { StaleWhileRevalidate, CacheFirst } from "workbox-strategies";
import { ExpirationPlugin } from "workbox-expiration";

precacheAndRoute(self.__WB_MANIFEST);

registerRoute(
  ({ request }) => request.destination === "image",
  new CacheFirst({
    cacheName: "images",
    plugins: [new ExpirationPlugin({ maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 })],
  })
);
```

`vite-plugin-pwa` and `next-pwa` wrap Workbox with build integration, which is what most projects should use.

## The kill switch

A broken service worker persists on users' devices. You must be able to unregister it remotely:

```js
self.addEventListener("install", () => self.skipWaiting());
self.addEventListener("activate", async () => {
  await self.registration.unregister();
  const clients = await self.clients.matchAll();
  clients.forEach(c => c.navigate(c.url));
});
```

Deploying this as `sw.js` replaces the broken worker and removes it. Ensure `sw.js` itself is served with `Cache-Control: no-cache` — otherwise the browser may serve a cached copy of the broken worker and you cannot reach users at all. Browsers now cap service worker script caching at 24 hours, but explicit headers are still correct.

## What a service worker cannot do

- Access the DOM (it has no page). Communicate via `postMessage` or the Broadcast Channel API.
- Use `localStorage` (synchronous APIs are unavailable). Use IndexedDB or the Cache API.
- Run continuously. It is terminated when idle and restarted on the next event, so all state must be persisted.
- Intercept requests outside its scope, or requests made before it activated.

## How senior engineers actually use this

**They use Workbox rather than hand-rolling.** The failure modes are severe and well-known enough that the library is the correct default.

**They prompt for updates rather than calling `skipWaiting()` unconditionally**, avoiding mid-session asset mismatches.

**They deploy a kill switch path** before shipping their first service worker.

**They never cache non-GET requests or authenticated API responses** by default — a cached response served to a different user on a shared device is a real incident class.

**They test with DevTools' Application panel** — the Service Workers pane has "Update on reload", "Bypass for network" and "Offline", which make the lifecycle observable rather than mysterious.

## Common pitfalls

- `skipWaiting()` unconditionally, causing chunk mismatches mid-session.
- Caching hashed assets under a cache name that is never versioned, so old entries accumulate forever.
- Caching authenticated responses.
- No offline fallback, so offline navigation shows the browser's error page.
- Forgetting `response.clone()` and consuming the body twice.
- No kill switch, and no way to recover from a bad deploy.
- Assuming `localStorage` is available inside the worker.
- Testing only in a fresh browser profile, missing the update path entirely.

## Interview angle

Service workers appear in "how would you make an app work offline" and PWA discussions. Cover the lifecycle including the waiting state and why it exists, the Cache API as separate from HTTP cache, and the strategy taxonomy with stale-while-revalidate as a sensible default. The details that signal real experience: the update-prompt pattern rather than blind `skipWaiting()`, and having a kill switch — because the failure mode of a bad service worker is uniquely bad among frontend bugs.
