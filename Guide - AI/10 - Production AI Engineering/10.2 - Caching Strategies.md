# Caching Strategies

## Why Caching Matters for AI Systems

LLM calls are 100–1000× more expensive than a database lookup. Caching lets you serve repeated or similar requests without hitting the LLM again.

Three distinct caching layers exist in AI systems:

---

## Layer 1: Embedding Cache

Embeddings are deterministic — the same text always produces the same vector. Cache aggressively.

```python
import hashlib, redis

class CachedEmbedder:
    def __init__(self, embedding_model, cache: redis.Redis, ttl=86400*7):
        self.model = embedding_model
        self.cache = cache
        self.ttl = ttl  # 7 days
    
    def embed(self, text: str) -> list[float]:
        cache_key = f"emb:{hashlib.sha256(text.encode()).hexdigest()}"
        
        cached = self.cache.get(cache_key)
        if cached:
            return json.loads(cached)
        
        embedding = self.model.encode(text).tolist()
        self.cache.setex(cache_key, self.ttl, json.dumps(embedding))
        return embedding
```

**Cache hit rate**: Very high for re-indexed documents (same chunks embed repeatedly), user queries (same queries asked frequently).

**Invalidation**: Only when embedding model changes (at which point you re-index everything anyway).

---

## Layer 2: LLM Response Cache (Exact Match)

Cache full LLM responses for identical prompts. Works best for:

- Static content (document summaries that don't change)
- FAQ-style Q&A where questions repeat exactly
- Background jobs with fixed prompts

```python
class LLMResponseCache:
    def get_or_call(self, prompt: str, model: str, **kwargs) -> str:
        cache_key = f"llm:{hashlib.sha256(f'{model}:{prompt}'.encode()).hexdigest()}"
        
        cached = redis.get(cache_key)
        if cached:
            metrics.increment("llm.cache.hit")
            return json.loads(cached)
        
        metrics.increment("llm.cache.miss")
        response = llm.call(prompt, model=model, **kwargs)
        redis.setex(cache_key, ttl=3600, value=json.dumps(response))
        return response
```

**Limitation**: Even minor prompt changes (different context, different conversation history) produce a cache miss. Low hit rate for conversational or dynamic RAG queries.

---

## Layer 3: Semantic Cache

Instead of exact prompt matching, cache by semantic similarity of the query. If a new query is very similar to a cached query, return the cached answer:

```python
class SemanticCache:
    def __init__(self, vector_store, similarity_threshold=0.97):
        self.store = vector_store
        self.threshold = similarity_threshold
    
    def get(self, query: str) -> Optional[str]:
        query_emb = embedding_model.encode(query)
        results = self.store.search(query_emb, top_k=1)
        
        if results and results[0].score > self.threshold:
            return results[0].metadata["cached_answer"]
        return None
    
    def set(self, query: str, answer: str):
        query_emb = embedding_model.encode(query)
        self.store.upsert(
            id=hashlib.sha256(query.encode()).hexdigest(),
            vector=query_emb,
            metadata={"query": query, "cached_answer": answer, "cached_at": now()}
        )
```

**Production use**: Works well for FAQ systems, support bots with repetitive queries. Less useful for open-ended research queries.

**Caution**: Cache poisoning — if you cache a wrong answer, it serves wrong answers to similar queries. Set aggressive TTLs and monitor cache hit rate vs user feedback correlation.

---

## Layer 4: Prompt Caching (API-Level)

OpenAI and Anthropic support caching at the API level — if the beginning of your prompt (system prompt + context) matches a previously seen prefix, processing is faster and cheaper.

```python
# Anthropic prompt caching — mark large context as cacheable
response = anthropic.messages.create(
    model="claude-opus-4-5",
    messages=[{
        "role": "user",
        "content": [
            {
                "type": "text",
                "text": large_document_context,
                "cache_control": {"type": "ephemeral"}  # Cache this prefix
            },
            {"type": "text", "text": user_question}
        ]
    }]
)
```

**Impact**: 50–90% cost reduction and latency improvement when the same large context is reused. Ideal for: document QA where the same document is queried multiple times, RAG where the same chunks recur frequently.

---

## Cache Invalidation

The hardest problem in caching:

|Cache Type|Invalidation Trigger|
|---|---|
|Embedding cache|Embedding model version change|
|LLM response cache|TTL expiry (1–24h), source document update|
|Semantic cache|TTL expiry, significant index update|
|Prompt cache|Managed by API provider (automatic)|

For RAG caches: invalidate when any source document contributing to the cached answer is updated.
