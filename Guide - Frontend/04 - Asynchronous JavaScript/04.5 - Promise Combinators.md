# Promise Combinators

Four static methods that coordinate multiple promises. Choosing the right one is mostly a question of what should happen when some of them fail.

| Method | Fulfills when | Rejects when | Result shape |
| --- | --- | --- | --- |
| `Promise.all` | all fulfill | any rejects (immediately) | array of values |
| `Promise.allSettled` | all settle | never | array of `{status, value/reason}` |
| `Promise.any` | any fulfills | all reject | first fulfilled value |
| `Promise.race` | first settles | first settles (if rejection) | first settled outcome |

All four accept any iterable and none of them start anything — the promises are already running from the moment they were created.

## Promise.all

```js
const [user, posts, settings] = await Promise.all([
  fetchUser(id),
  fetchPosts(id),
  fetchSettings(id),
]);
```

Order of results matches input order regardless of completion order. Total time is the slowest, not the sum.

The defining behavior is **fail-fast**: the first rejection rejects the whole thing immediately, and the other promises keep running but their results are discarded. There is no way to see partial success.

```js
try {
  await Promise.all([critical(), optional()]);
} catch (err) {
  // Which one failed? Only the first rejection's reason is available.
}
```

Use it only when *every* result is required. It is the right choice for a page that cannot render without all three payloads, and the wrong choice for a dashboard of independent widgets.

Note it works with any iterable and mixed values:

```js
await Promise.all([fetchA(), 42, "plain"]); // non-promises pass through
```

## Promise.allSettled

```js
const results = await Promise.allSettled([
  fetchWidget("chart"),
  fetchWidget("feed"),
  fetchWidget("stats"),
]);

const loaded = results
  .filter(r => r.status === "fulfilled")
  .map(r => r.value);

const failures = results
  .filter(r => r.status === "rejected")
  .map(r => r.reason);
```

Never rejects. Every entry is `{ status: "fulfilled", value }` or `{ status: "rejected", reason }`.

This is the right default for anything where partial results are useful: independent dashboard widgets, bulk operations, prefetching several routes, sending a batch of analytics events. In practice it is used less often than it should be, because `Promise.all` is the one people remember.

## Promise.any

```js
const data = await Promise.any([
  fetch("https://cdn1.example.com/data"),
  fetch("https://cdn2.example.com/data"),
  fetch("https://cdn3.example.com/data"),
]);
```

Resolves with the first **fulfillment**, ignoring rejections. If all reject, it rejects with an `AggregateError` whose `.errors` array holds every reason.

```js
try {
  await Promise.any(sources);
} catch (err) {
  console.log(err.errors); // all individual failures
}
```

Use for redundant sources: mirror endpoints, a cache and a network in parallel, several geolocation providers.

## Promise.race

```js
function withTimeout(promise, ms) {
  return Promise.race([
    promise,
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error("Timeout")), ms)
    ),
  ]);
}

const data = await withTimeout(fetchData(), 5000);
```

Settles with the first promise to settle **either way**. A fast rejection wins over a slow fulfillment, which is the difference from `Promise.any`.

Two cautions. First, the losing promises are not cancelled — they run to completion and their results are discarded. In the timeout example the request is still in flight, still consuming a connection. Pair `race` with `AbortController` for real cancellation ([[04.6 - AbortController and Cancellation]]). Second, `Promise.race([])` stays pending forever, since nothing can ever settle.

Modern browsers have `AbortSignal.timeout(ms)`, which makes the manual race unnecessary for fetch:

```js
await fetch(url, { signal: AbortSignal.timeout(5000) });
```

## Choosing, in practice

```
Do I need every result?           -> all
Are partial results useful?       -> allSettled
Do I want the first success?      -> any
Do I want the first outcome?      -> race
```

A useful reframing: `all` and `allSettled` wait for everything; `any` and `race` wait for one. `all` and `race` propagate failure; `allSettled` and `any` tolerate it.

## Combining with concurrency limits

`Promise.all` over a large array fires everything at once:

```js
await Promise.all(tenThousandIds.map(id => fetch(`/api/${id}`)));
```

Browsers cap concurrent connections per origin at around six, so the rest queue invisibly at the network layer — but you have still allocated ten thousand promises and, more importantly, you will hit server rate limits. Bound it explicitly ([[04.7 - Async Concurrency Patterns]]):

```js
async function mapWithLimit(items, limit, fn) {
  const results = [];
  const executing = new Set();

  for (const item of items) {
    const p = Promise.resolve(fn(item)).finally(() => executing.delete(p));
    results.push(p);
    executing.add(p);
    if (executing.size >= limit) await Promise.race(executing);
  }

  return Promise.all(results);
}
```

`Promise.race` over the in-flight set is the standard way to wait for "any one slot to free up".

## How senior engineers actually use this

**They default to `allSettled` for anything user-facing that has independent parts.** One failed widget should not blank the page. `Promise.all` is reserved for genuine all-or-nothing requirements.

**They always pair `race` timeouts with abort.** A timeout that leaves the request running is a resource leak under load, and it makes retry storms worse.

**They report `AggregateError` contents.** When `Promise.any` fails, logging only the top-level error loses every underlying reason.

**They watch for the "start everything, await later" pattern's rejection risk.** A promise created and not immediately awaited can produce an unhandled rejection before you get to it.

## Common pitfalls

- Using `all` where one failure should not kill the batch.
- Assuming `all` runs things in parallel. It coordinates; the promises were already running.
- Expecting `race` to cancel the losers.
- `Promise.race([])` hanging forever.
- Forgetting `any` rejects with `AggregateError`, not a normal error, so `err.message` is unhelpful.
- Unbounded `Promise.all` over large collections, triggering server rate limits.

## Interview angle

The comparison table is asked directly and often — "difference between `all` and `allSettled`", "`any` versus `race`". Answer along two axes: how many must settle, and what happens on failure. Then add the practical points that show real usage: `race` does not cancel, `any` rejects with `AggregateError`, and unbounded `all` needs a concurrency limit. Implementing `Promise.all` from scratch is a common follow-up — track a completion counter and preserve index order.
