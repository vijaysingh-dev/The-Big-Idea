# Developer Console and Log Inspector

## What it is still good for

The Developer Console is dated, and VS Code has replaced it for writing code. Three things keep it relevant:

**The Log Inspector**, which attributes execution time per operation — the only tool that does.

**The Query Plan tool**, for diagnosing non-selective queries.

**Checkpoints and heap dumps**, for inspecting memory state.

Everything else — editing, deploying, running tests — is better in VS Code with the Salesforce extensions.

## The Log Inspector

Open a log, then **Debug → Switch Perspective → Analysis**.

Four panels, and two of them matter.

**Execution Tree** — the call hierarchy, nested. This is the shape of the transaction.

**Execution Overview** — a table of operations by **total duration**, sortable. This is the diagnostic view.

**Stack Tree** — cumulative time per method, aggregated across calls.

**Timeline** — a visual bar chart of where time went.

## The Execution Overview

The single most useful view in the tool.

```
Operation                                     Duration  Count
─────────────────────────────────────────────────────────────
Trigger: WarrantyClaimTrigger after update      4,218ms      1
  Flow: Claim_Approval_Routing                  2,940ms    200
  ClaimRollupService.recalculate                  810ms      1
  SOQL: SELECT Id FROM Machine_Coverage__c        290ms      1
DML: Update Asset                               1,120ms      1
```

**Sort by duration and read the top three.** In the example, the flow running 200 times accounts for most of the transaction — which is a flow with an element inside a per-record execution, not an Apex problem.

That attribution is what a raw log does not give you. Reading 40,000 lines tells you what happened; this tells you what it cost.

## The Execution Tree

```
Execute Anonymous
  └── DML BEGIN Op:Update Type:Warranty_Claim__c Rows:200
        ├── WarrantyClaimTrigger before update
        │     └── ClaimService.applyDerivedFields
        │           └── SOQL: SELECT Id, SerialNumber FROM Asset ...
        ├── Flow: Claim_Approval_Routing
        ├── WarrantyClaimTrigger after update
        │     └── ClaimRollupService.recalculate
        │           ├── SOQL: SELECT Asset__c, COUNT(Id) ...
        │           └── DML BEGIN Op:Update Type:Asset Rows:48
        │                 └── AssetTrigger after update
        │                       └── DML BEGIN Op:Update Type:Account Rows:12
```

**Nesting depth is cascade depth.** Three or four levels on one save is where a CPU limit failure usually originates, and this view makes it visible in a way the raw log does not. See [[11.9 - Triggers and Order of Execution]].

**Checking "Executed Units" and "Filter"** narrows the tree to the units you care about, which matters on a large log.

## Query Plan

**Help → Preferences → Enable Query Plan**, then paste a query into the Query Editor and click **Plan**.

```
Cardinality  Fields              Leading Operation Type  Cost   sObject Cardinality
     18420   Status__c           TableScan              2.84    412000
      1240   Account__c          Index                   0.11    412000
```

**Cost above 1 means a table scan.** Below 1 means the optimizer will use an index.

**Leading Operation Type** names what it chose:

```
Index        an index will be used
TableScan    the whole table is read
Other        a sharing or ownership-based plan
```

**Cardinality** is the estimated matching rows; **sObject Cardinality** is the total.

The workflow: paste the query, read the cost, and if it is above 1, narrow the filter — a date bound, a positive `IN` rather than `!=`, removal of a leading wildcard. See [[08.10 - Query Plan Tool and Query Optimization]] and [[16.9 - Skinny Tables and Custom Indexes]].

This tool has no equivalent in VS Code, which is one of the two reasons the Developer Console is still open on most developers' screens.

## The Query Editor

```sql
SELECT Id, Claim_Number__c, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
```

Results are **inline editable**, and changes save with the button. Convenient for a quick data fix and dangerous in production — a mistyped value is saved immediately with no confirmation.

**`USING SCOPE` and `ALL ROWS`** work here, which makes it the fastest way to check whether a record was deleted:

```sql
SELECT Id, Claim_Number__c, IsDeleted, LastModifiedDate
FROM Warranty_Claim__c WHERE Id = 'a0X5g000001AbCdEAK' ALL ROWS
```

The **Tooling API** checkbox switches the editor to metadata objects, which is how `ApexLog`, `TraceFlag`, and `ApexCodeCoverage` are queried without the CLI:

```sql
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate ORDER BY NumLinesUncovered DESC
```

## Execute Anonymous

**Debug → Open Execute Anonymous Window**, or Ctrl+E.

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Status__c FROM Warranty_Claim__c
    WHERE Status__c = 'Under Review' AND Claim_Date__c < LAST_N_DAYS:90
    LIMIT 200
];

System.debug('Found ' + claims.size() + ' stale claims');

for (Warranty_Claim__c claim : claims) {
    claim.Status__c = 'Closed';
}

// deliberately commented until the count above has been verified
// update claims;
```

**Checking "Open Log"** returns the log immediately, which makes this the fastest diagnostic loop available — write a snippet, run it, read the result.

Three cautions for production use:

**It runs as you**, with your permissions and sharing.

**It is a real transaction.** DML commits, triggers fire, and there is no undo.

**It is subject to normal governor limits** — 100 queries, 150 DML statements, 10 seconds CPU.

The discipline that prevents incidents: **run it with the DML commented out first**, verify the count and the records, then uncomment.

For anything scripted or repeated, the CLI is better because the script is versioned:

```bash
sf apex run --file scripts/close-stale-claims.apex --target-org production
```

That also makes post-deployment steps repeatable rather than a manual checklist item. See [[21.10 - Deployment Strategies, Rollback and Hotfixes]].

## Running tests

**Test → New Run**, select classes, run.

The **Tests** tab shows pass and fail per method, and the **Overall Code Coverage** panel shows per-class percentages with a click-through to highlighted covered and uncovered lines.

**The line highlighting is the useful part** — seeing exactly which branches are untested is faster than reading a percentage.

For anything routine, the CLI is better:

```bash
sf apex run test --tests ClaimApprovalServiceTest --result-format human --wait 10
```

## Checkpoints

Covered fully in [[20.4 - Heap Dumps and Checkpoints]]; in outline:

**Click the line number gutter** in a class to set a checkpoint, then run the code. The checkpoint captures a heap dump at that line — every variable, every collection, with its contents.

Up to five checkpoints, and they expire after 30 minutes.

**This is the tool for "why is this variable null"** when the log does not say. It is the second reason the Developer Console stays open.

## Perspectives

```
Analysis     execution tree, overview, stack tree — the debugging default
Debug        raw log plus execution overview
Log Only     the raw log
```

**Debug → Switch Perspective → Analysis** is the setting worth making immediately, since the default perspective is the least useful.

Custom perspectives can be saved with a chosen panel arrangement, which is worth doing once if you use the tool regularly.

## Filtering a large log

**Debug → Filter** in the Log panel:

```
FATAL_ERROR
LIMIT_USAGE
SOQL_EXECUTE
DML_BEGIN
USER_DEBUG
```

Filtering to `USER_DEBUG` alone shows only your own debug statements, which for a targeted diagnostic is the fastest read.

**For anything over a few megabytes, download and use command-line tools.** The console's filtering is slow on large logs, and `grep` is not:

```bash
sf apex get log --log-id 07L5g00000ABCDeAAN > debug.log
grep -c "SOQL_EXECUTE_BEGIN" debug.log
grep "CODE_UNIT_STARTED" debug.log
```

## What VS Code does better

Being clear about the division, since neither tool covers everything.

**VS Code with the Salesforce extensions:** writing code, retrieving and deploying, source control, running tests, the Apex Replay Debugger, and Apex Interactive Debugger with a licence.

**The Apex Replay Debugger** deserves mention — it steps through a downloaded log with breakpoints and variable inspection, which is closer to a real debugger than anything in the Developer Console:

```
Command Palette → SFDX: Turn On Apex Debug Log for Replay Debugger
[reproduce the issue]
Command Palette → SFDX: Get Apex Debug Logs
Command Palette → SFDX: Launch Apex Replay Debugger with Current File
```

**The Developer Console:** the Log Inspector's timing attribution, the Query Plan tool, and checkpoints.

Most developers work in VS Code and open the console for those three.

## A debugging workflow

```
1. VS Code           reproduce, add targeted System.debug
2. sf apex tail log  stream the log live while reproducing
3. Developer Console → Analysis perspective → Execution Overview
                     sort by duration, find the expensive operation
4. Query Plan        if a query dominates
5. Checkpoint        if a variable's state is the question
6. Replay Debugger   if stepping through is needed
```

**Step 3 is where most performance investigations resolve**, because it turns "the save is slow" into "the flow ran 200 times".

## Practical guidance

**Switch to the Analysis perspective** immediately.

**Sort the Execution Overview by duration** — it is the fastest attribution available.

**Read nesting depth in the Execution Tree** to spot a cascade.

**Use Query Plan** for any query over a large object; cost above 1 is a scan.

**Run Execute Anonymous with DML commented out first**, in production.

**Move repeated scripts to the CLI** so they are versioned.

**Download large logs** and use `grep` rather than the console's filter.

**Use VS Code for everything else.**
