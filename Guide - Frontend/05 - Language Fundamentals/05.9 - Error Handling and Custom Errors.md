# Error Handling and Custom Errors

Good error handling is mostly about preserving information and distinguishing expected failures from bugs. The syntax is the easy part.

## try / catch / finally

```js
try {
  risky();
} catch (err) {
  handle(err);
} finally {
  cleanup();
}
```

`finally` runs on every exit path — success, caught error, uncaught error, and even `return` inside `try`. A `return` in `finally` overrides any earlier return or throw, which is almost always a bug:

```js
function f() {
  try { return 1; }
  finally { return 2; }  // returns 2, swallows everything
}
```

Optional catch binding is available when you do not need the error:

```js
try { JSON.parse(s); } catch { return null; }
```

**`try/catch` only catches synchronous errors on the current stack** ([[01.3 - The Call Stack]]):

```js
try {
  setTimeout(() => { throw new Error("x"); }, 0);
} catch (e) {
  // never runs
}
```

With `await`, it works again, because the rejection is thrown back into the suspended function ([[04.4 - async await]]).

## Throwing

You can throw anything, but throw `Error` instances.

```js
throw new Error("Something failed");   // has message, name, stack
throw "Something failed";              // no stack, breaks instanceof checks
```

A thrown string loses the stack trace entirely, which makes production debugging near-impossible. Linters enforce this via `no-throw-literal`.

## Built-in error types

| Type | When |
| --- | --- |
| `Error` | generic / your own |
| `TypeError` | wrong type — calling a non-function, reading a property of `undefined` |
| `RangeError` | value out of range — stack overflow, invalid array length |
| `ReferenceError` | undeclared identifier, TDZ access |
| `SyntaxError` | parse failure, including `JSON.parse` |
| `AggregateError` | multiple errors — thrown by `Promise.any` |
| `DOMException` | platform errors — `AbortError`, `QuotaExceededError`, `NotAllowedError` |

Note that `fetch` throws a plain `TypeError` on network failure, which is why network errors are awkward to distinguish from programming errors without a wrapper.

## Custom error classes

```js
class AppError extends Error {
  constructor(message, options = {}) {
    super(message, { cause: options.cause });
    this.name = new.target.name;
    Error.captureStackTrace?.(this, new.target);
  }
}

class HttpError extends AppError {
  constructor(status, body, options) {
    super(`HTTP ${status}`, options);
    this.status = status;
    this.body = body;
  }

  get isRetryable() {
    return this.status >= 500 || this.status === 429;
  }
}

class ValidationError extends AppError {
  constructor(fieldErrors) {
    super("Validation failed");
    this.fieldErrors = fieldErrors;
  }
}
```

Four details:

- **`new.target.name`** sets `name` to the actual subclass, so `HttpError` reports as `"HttpError"` rather than `"AppError"`.
- **`Error.captureStackTrace`** (V8 only, hence the `?.`) removes the constructor frame from the trace, so the top frame is the caller's code.
- **`cause`** chains errors without losing the original.
- Subclassing `Error` works correctly only with `class` syntax; the ES5 pattern broke `instanceof` and the stack ([[03.4 - Classes vs Prototypes]]).

## Error.cause

```js
try {
  await saveUser(user);
} catch (err) {
  throw new AppError("Could not complete signup", { cause: err });
}
```

Preserves the original error while adding context. Without `cause`, wrapping an error destroys the root cause — a very common mistake:

```js
// Loses everything
catch (err) { throw new Error("save failed"); }
```

DevTools and modern error reporters display the full cause chain.

## Discriminating errors

```js
try {
  await submit(form);
} catch (err) {
  if (err instanceof ValidationError) return setFieldErrors(err.fieldErrors);
  if (err instanceof HttpError && err.status === 401) return redirectToLogin();
  if (err.name === "AbortError") return;                 // expected, ignore
  reportToMonitoring(err);
  showGenericError();
}
```

`instanceof` fails across realms (iframes, workers) and across bundle boundaries where two copies of a library exist. For library code, a discriminator property is more robust:

```js
class HttpError extends Error {
  static [Symbol.hasInstance](x) { return x?.__isHttpError === true; }
  __isHttpError = true;
}
```

Or more simply, check a `code` field rather than the class.

## Expected vs unexpected

The distinction that matters most in application design:

**Expected failures** — a 404, a validation error, a user cancellation. These are part of normal operation. They should be handled locally, shown in the UI, and not reported to monitoring.

**Unexpected failures** — a `TypeError`, a failed invariant, an unhandled state. These are bugs. They should be reported, and the UI should degrade to a boundary.

Conflating them produces one of two failure modes: monitoring dashboards flooded with 404s, or real crashes buried in noise.

Some codebases model expected failures as return values rather than throws:

```js
async function getUser(id) {
  const res = await fetch(`/api/users/${id}`);
  if (res.status === 404) return { ok: false, error: "not_found" };
  if (!res.ok) throw new HttpError(res.status);
  return { ok: true, data: await res.json() };
}
```

This makes the expected cases visible in the type signature and reserves exceptions for genuine faults. It is more verbose and worth it at API boundaries.

## Global handlers

```js
window.addEventListener("error", e => report(e.error));
window.addEventListener("unhandledrejection", e => report(e.reason));
```

The safety net. Both should feed your error reporter. Note the `error` event's `e.error` can be `null` for cross-origin script errors unless the script is served with CORS headers and the tag has `crossorigin` — the infamous "Script error." with no detail.

In React, `ErrorBoundary` catches render errors but not event handler or async errors ([[22.1 - Error Boundaries]]), so global handlers remain necessary.

## How senior engineers actually use this

**They define an error hierarchy once, at the API layer.** Every network call produces a `HttpError`, `NetworkError` or `ValidationError` with a consistent shape, and application code branches on that instead of inspecting raw responses.

**They always attach `cause` when re-throwing.** Losing the root cause turns a five-minute fix into an hour of guessing.

**They never catch without either handling or re-throwing.** An empty catch block is how failures become invisible.

**They separate the user message from the developer message.** `err.message` goes to logs; a mapped, human-readable string goes to the UI. Showing raw error messages to users leaks implementation detail and occasionally security-relevant information.

**They ship source maps.** Without them, production stack traces point into minified code and are worthless ([[27.7 - Source Maps]]).

## Common pitfalls

- `try/catch` around async code without `await`.
- Throwing strings.
- Wrapping errors without `cause`.
- `return` inside `finally`.
- Catching everything at the top of a function, so a rendering bug is reported as a network failure.
- Reporting expected errors (404s, aborts) to monitoring.
- `instanceof` failing across bundles or realms.

## Interview angle

Error handling questions are usually practical: "how do you handle errors in an async function", "how would you design error handling for an app". Cover the layered answer — typed errors at the API boundary, local handling for expected failures, error boundaries for render errors, global handlers as the net — and mention `cause` for preserving context. The expected-versus-unexpected distinction is the part that signals design thinking rather than syntax knowledge.
