## Section A: How an LLM works

### Q1. At a high level, how does a large language model generate text?

**Answer**
An LLM is a neural network trained to do one thing: **predict the next token**, given all the tokens before it.

- A **token** is a chunk of text, often a word piece. For example, "unbelievable" might become `un`, `believ`, `able`.

Generation is a loop:
1. Your prompt is split into tokens, and each token is turned into a vector of numbers.
2. The model processes all of them and outputs a **logit** for every token in its vocabulary. A logit is a raw score; the vocabulary is the fixed set of tokens the model knows, typically 32k–200k.
3. A **softmax** turns those scores into probabilities. Softmax exponentiates each score and divides by the sum, so all probabilities add up to 1.
4. A **sampling** strategy picks one token from that distribution.
5. That token is appended to the input, and the loop repeats until a stop token or a length limit.

This is called **autoregressive** generation: each output becomes part of the next input. It explains three practical things:
- Output is generated **one token at a time**. That's why streaming is natural, and why long outputs are slow.
- **Output tokens cost more and take longer than input tokens.** The input is processed in one parallel pass; output needs one pass per token.
- The model has **no plan** beyond what's in its weights and the text so far. Any "reasoning" has to happen in the tokens it produces, which is why "think step by step" helps.

**Likely follow-ups**
- *Does the model "know" facts?* It has learned statistical patterns that often encode facts, but it has no lookup table and no notion of truth. That's the root cause of hallucination (Q15).
- *Why can't it just generate the whole answer at once?* Each token depends on the ones before it. Research on parallel decoding exists (e.g. speculative decoding, Q11), but standard generation is sequential.

**What a strong answer shows:** You can explain it simply without hand-waving, and you connect the mechanism to practical behaviour: cost, latency, streaming, hallucination.

### Q2. What is tokenization, and why should an engineer care?

**Answer**
Tokenization converts text into the integer IDs the model actually consumes. Most modern LLMs use **BPE (Byte Pair Encoding)** or a variant.
- BPE starts from bytes or characters.
- It repeatedly merges the most frequent adjacent pair into a new token, until the vocabulary reaches a target size.
- Common words become single tokens; rare words split into pieces.

Why it matters in practice:
- **Cost and limits are in tokens, not characters.** A rough English rule is ~4 characters or ~0.75 words per token. Code, JSON and non-English text (including Hindi or other Indic scripts) often use many more tokens per word.
- **Context window budgets.** If the limit is 128k tokens, you budget the prompt, retrieved context, history *and* the expected output inside it.
- **Odd model behaviour.** Arithmetic, counting letters ("how many r's in strawberry") and reversing strings are hard. The model sees `straw`+`berry`, not individual letters.
- **Mismatched tokenizers.** Every model family has its own. Counting tokens with the wrong tokenizer gives wrong budgets.
- **Whitespace and formatting.** `" Hello"` and `"Hello"` are often different tokens. This matters for few-shot formatting and stop sequences.

**Likely follow-ups**
- *How would you count tokens before calling the API?* Use the provider's tokenizer library (e.g. `tiktoken` for OpenAI models) or its token-counting endpoint. Budget with a safety margin.
- *Why not use characters or whole words as tokens?* Characters make sequences very long, and attention cost grows with length. Whole words can't handle new or rare words. Sub-word tokens are the compromise.

**What a strong answer shows:** You treat tokens as the real unit of cost, latency and limits, and you know where they cause surprising behaviour.

### Q3. What are embeddings? How are token embeddings different from sentence embeddings?

**Answer**
An **embedding** is a vector (a list of numbers, e.g. 384 or 1536 of them) that represents meaning, so that similar things land close together in that space.

- **Token embeddings** live *inside* the LLM. The first layer is a lookup table from token ID to vector. These vectors are then transformed layer by layer, so by the end each token's vector reflects its context ("bank" next to "river" vs. next to "loan").
- **Sentence / text embeddings** are what you use for search and RAG. A separate **embedding model** (usually an encoder, Q6) reads a whole passage and produces **one** vector for it. It usually does this by **pooling**: averaging the token vectors, or taking a special token's vector.

  These models are trained with **contrastive learning**: pairs that should match (a question and its answer) are pulled together, and non-matching pairs are pushed apart. That training makes them good at similarity, which a raw LLM's internal vectors are not.

**Likely follow-ups**
- *Can I use an LLM's hidden states as embeddings?* You can, but purpose-trained embedding models usually retrieve much better and are far cheaper.
- *What does the dimension number mean?* More dimensions can hold more nuance, but they cost more memory and slower search. Some models support truncating vectors (Matryoshka embeddings, see Part 2).

**What a strong answer shows:** You don't confuse the internal representations of an LLM with the embedding models used for retrieval.

## Section B: The Transformer

### Q4. Explain the Transformer architecture.

**Answer**
The Transformer (from "Attention Is All You Need", 2017) is the architecture behind almost every modern LLM. A **decoder-only** model like GPT, Llama or Claude is a stack of identical **blocks**.

1. **Input:** tokens become embedding vectors, plus position information (Q7).
2. **Each block has two sub-layers:**
   - **Self-attention:** each token looks at the other tokens and pulls in the information relevant to it (Q5). This is how context flows between words.
   - **Feed-forward network (FFN / MLP):** a small two-layer neural network applied to each token separately. It's often described as where much of the "knowledge" is stored. It holds most of the parameters.
3. **Residual connections:** each sub-layer's output is *added* to its input (`x + sublayer(x)`). This lets very deep stacks train stably and lets information pass through unchanged when a layer has nothing to add.
4. **Layer normalization:** rescales the vectors to a stable range so training doesn't blow up.
5. **Output head:** after the last block, a final layer maps each vector to logits over the vocabulary.

Stack this 30–100+ times and you have an LLM.

The key advantage over older **RNNs** (recurrent networks, which read text one word at a time) is **parallelism**. During training, every position is processed at once, which is what made training on internet-scale data feasible.

**Likely follow-ups**
- *What does "decoder-only" mean?* See Q6. It means the model uses causal attention, so each token can only see earlier tokens.
- *Where are most of the parameters?* Mostly in the FFN layers, plus the embedding table in smaller models.

**What a strong answer shows:** You can sketch the block from memory and say *why* each piece exists, not just name it.

### Q5. Explain self-attention. What are Q, K and V?

**Answer**
Self-attention lets each token build a new representation of itself by taking a weighted mix of all the tokens it's allowed to see.

For each token, the model creates three vectors by multiplying its embedding by three learned weight matrices:
- **Query (Q):** "what am I looking for?"
- **Key (K):** "what do I contain?" (used to be matched against)
- **Value (V):** "what will I hand over if you attend to me?"

Then:
1. Score every pair: the dot product `Q_i · K_j` says how relevant token *j* is to token *i*.
2. Scale by `√d_k` (the square root of the key dimension). Without this, dot products grow with dimension, and the softmax becomes nearly one-hot, which hurts learning.
3. Apply softmax so the weights sum to 1.
4. Take a weighted sum of the V vectors.

In one line:

```
Attention(Q, K, V) = softmax(Q·Kᵀ / √d_k) · V
```

**Multi-head attention** runs this several times in parallel with different weight matrices. Each "head" can specialise: one tracks grammar, another tracks which noun a pronoun refers to, and so on. The heads' outputs are concatenated and projected back.

**Causal masking:** in a decoder, token *i* must not see tokens after it, or training would be cheating. The scores for future positions are set to −∞ before the softmax, so their weight becomes 0.

**Likely follow-ups**
- *What is cross-attention?* The queries come from one sequence and the keys/values from another. It's used in encoder-decoder models (translation) and in many multimodal models.
- *What are GQA and MQA?* Grouped-Query and Multi-Query Attention. Several query heads share the same K/V heads. This shrinks the KV cache (Q10) a lot, with little quality loss, and is common in modern models.

**What a strong answer shows:** You can write the formula, explain the √d scaling and the mask, and connect attention variants to inference cost.

### Q6. Encoder-only, decoder-only, encoder-decoder: what's the difference, and where is each used?

**Answer**

| Type | Attention | Examples | Good for |
|---|---|---|---|
| **Encoder-only** | Bidirectional: every token sees every other token | BERT, RoBERTa, most embedding models, cross-encoder rerankers | Understanding: classification, embeddings, reranking |
| **Decoder-only** | Causal: each token sees only earlier tokens | GPT, Llama, Claude, Mistral | Generation |
| **Encoder-decoder** | Encoder is bidirectional; decoder is causal plus cross-attention to the encoder | T5, BART, many translation models | Transforming input → output (translation, summarisation) |

Decoder-only won for general-purpose LLMs. It's simple, it scales well, and "predict the next token" turns every task into the same problem.

For RAG this matters directly. Your **embedding model** and **reranker** are usually encoders, because seeing the whole text in both directions gives better understanding of a passage. Your **generator** is a decoder.

**Likely follow-ups**
- *Why is a cross-encoder reranker accurate but slow?* It feeds the query and the document *together* through an encoder, so every query token can attend to every document token. That has to run once per (query, doc) pair at query time, and nothing can be precomputed. (Part 2, Q14.)

**What a strong answer shows:** You map architecture types to the components of a real system.

### Q7. How does the model know word order? Explain positional encoding.

**Answer**
Attention by itself is order-blind. It treats the input as a set, so "dog bites man" and "man bites dog" would look the same. Position information has to be added.

- **Sinusoidal (original Transformer):** add fixed sine/cosine waves of different frequencies to each embedding. Each position gets a unique pattern.
- **Learned absolute positions (GPT-2, BERT):** a learned vector per position. Simple, but it can't go beyond the trained length.
- **RoPE (Rotary Position Embedding):** used by most modern LLMs. It *rotates* the Q and K vectors by an angle proportional to position. The dot product between two tokens then depends on their **relative** distance, which generalises better.

  "Context extension" tricks stretch or interpolate the rotation frequencies so a model can handle longer inputs than it was trained on.
- **ALiBi:** adds a distance-based penalty to the attention scores. Also relative, and it extrapolates well.

**Likely follow-ups**
- *Why do models degrade near their maximum context?* They saw few very long examples in training, and position extension isn't perfect. Effective context is often shorter than advertised (Q14).

**What a strong answer shows:** You know attention needs position added, and you know RoPE and relative positions exist and why.

### Q8. What is a Mixture-of-Experts (MoE) model?

**Answer**
In an MoE model, the FFN in each block is replaced by many smaller "expert" FFNs plus a **router**.
- For each token, the router picks the top-k experts (often 2) to process it.
- The model can have a huge **total** parameter count while each token only uses a small **active** subset.

Result: the quality of a big model at closer to the compute cost of a small one, per token.

Tradeoffs:
- **All experts still have to sit in memory**, so serving needs a lot of GPU RAM.
- Training is trickier: the router must spread the load, or a few experts get all the traffic.
- Throughput depends on how evenly tokens spread across experts.

**What a strong answer shows:** You understand total vs. active parameters, and that "cheaper compute" doesn't mean "cheaper memory".

## Section C: Inference and decoding

### Q9. Explain temperature, top-k and top-p. When would you change them?

**Answer**
These control how the next token is picked from the probability distribution.

- **Greedy:** always take the most likely token. Deterministic in theory, but prone to repetitive, bland text.
- **Temperature (T):** divide the logits by T before the softmax.
  - T < 1 sharpens the distribution: more confident, more repetitive.
  - T > 1 flattens it: more random and creative, and more errors.
  - T → 0 approaches greedy.
- **Top-k:** keep only the k most likely tokens, renormalise, and sample.
- **Top-p (nucleus sampling):** keep the smallest set of tokens whose probabilities add up to p (e.g. 0.9), then sample. It adapts: when the model is confident the set is tiny, when it's unsure the set is wider.

Practical settings:
- **Extraction, classification, SQL/code generation, structured output, RAG answers:** low temperature (0–0.3). You want consistency and faithfulness.
- **Brainstorming, creative writing, generating varied test data:** higher (0.7–1.0).
- Generally **tune temperature or top-p, not both**, because they interact.

**Likely follow-ups**
- *Is temperature 0 fully deterministic?* Not reliably. Floating-point non-associativity on GPUs (the order of additions changes the result slightly), batching with other requests, and MoE routing can all change outputs between runs. Design tests and evals for **non-determinism** (Part 3).
- *What are frequency/presence penalties?* They reduce the probability of tokens that have already appeared, which reduces repetition.

**What a strong answer shows:** You know the mechanics, and you pick settings by task, including knowing that "temperature 0" isn't a determinism guarantee.

### Q10. What is the KV cache? Explain prefill vs. decode.

**Answer**
When generating token *n+1*, attention needs the K and V vectors of all previous tokens. Recomputing them every step would be wasteful, so they are stored: that's the **KV cache**.

Inference has two phases:
- **Prefill:** process the whole prompt in one parallel pass and fill the KV cache. It's **compute-bound** (limited by GPU arithmetic). It determines **TTFT (time to first token)**.
- **Decode:** generate one token at a time, each step reading the entire KV cache. It's **memory-bandwidth-bound** (limited by how fast data moves from GPU memory). It determines **tokens per second**.

Why engineers care:
- **Long prompts raise TTFT.** Long outputs raise total latency. Both cost money.
- **The KV cache uses a lot of GPU memory.** Its size is roughly `2 × layers × kv_heads × head_dim × sequence_length × bytes`. It grows linearly with context and with the number of concurrent requests. This is why long context is expensive to serve, and why GQA/MQA exist.
- **Prompt caching** (offered by Anthropic, OpenAI and others) reuses the KV cache for an identical prompt *prefix* across requests. Put stable content first (system prompt, tool definitions, documents) and varying content last, to get large cost and latency savings.
- Serving engines like **vLLM** use **PagedAttention**, which manages the KV cache in pages like an operating system manages virtual memory. That allows **continuous batching**: new requests join a running batch without waiting for the batch to finish.

**Likely follow-ups**
- *How would you reduce TTFT for a RAG app?* Shorter prompts (fewer, better chunks), prompt caching for static prefixes, a smaller or faster model, and streaming so the user sees progress.
- *How would you raise throughput?* Batching, quantization (Q13), GQA models, and a serving engine like vLLM or TGI.

**What a strong answer shows:** You link model internals to latency, cost and serving decisions. This is one of the clearest signals that someone is senior on the AI side.

### Q11. What is speculative decoding?

**Answer**
A small, fast **draft model** guesses several next tokens. The big model then checks all of them in **one** parallel pass (checking is like prefill, which is cheap per token) and accepts the longest prefix it agrees with.
- When the draft is usually right, you get 2–3× faster generation.
- The output distribution is mathematically the same as the big model's alone.

As an application engineer you rarely implement this, but it explains why some providers get faster without changing quality.

**What a strong answer shows:** Awareness of inference optimisations beyond "use a smaller model".

## Section D: Training and adaptation

### Q12. Walk me through how a model like ChatGPT or Claude is trained.

**Answer**
1. **Pretraining:** next-token prediction on trillions of tokens of text and code. This produces a **base model** that has broad knowledge and can continue text, but doesn't follow instructions well. This is by far the most expensive step.
2. **Supervised fine-tuning (SFT) / instruction tuning:** train on curated (instruction → good response) examples, so the model learns to act as a helpful assistant.
3. **Preference tuning (alignment):**
   - **RLHF** (Reinforcement Learning from Human Feedback): humans rank pairs of responses, a **reward model** learns those preferences, and the LLM is optimised to score well on it (often with an algorithm called PPO).
   - **DPO** (Direct Preference Optimization) skips the separate reward model and optimises on preference pairs directly. It's simpler and widely used.
   - Some labs add AI-generated feedback guided by written principles (e.g. Anthropic's Constitutional AI).
4. **Reasoning training (newer models):** reinforcement learning on tasks with checkable answers (maths, code tests), which teaches the model to produce long internal chains of reasoning before answering.

**Likely follow-ups**
- *What is a "reasoning model", and when would you use one?* A model trained to think at length before answering (it spends extra tokens on reasoning). Use it for multi-step logic, planning and hard code. Avoid it for simple, latency-sensitive tasks: it's slower and more expensive.
- *Why do models have a knowledge cutoff?* Pretraining data stops at a date. Anything after that has to come from context (RAG or tools).

**What a strong answer shows:** A clear map of the stages and what each one contributes, without overclaiming details of proprietary pipelines.

### Q13. Prompting vs. RAG vs. fine-tuning: how do you choose? Also explain LoRA and quantization.

**Answer**
The rule: **fine-tuning changes *behaviour*; RAG supplies *knowledge*.**

| Need | Best first tool |
|---|---|
| Better task instructions, format or tone | **Prompting:** iterate fast, cheapest |
| Facts the model doesn't have, or that change, need citations, or need access control | **RAG** |
| Consistent style or format at scale, a narrow specialised task, shorter prompts, a smaller/cheaper model matching a larger one | **Fine-tuning** |
| Brand-new knowledge baked into weights | Rarely the right answer. Fine-tuning is poor at reliably adding facts and can't cite them |

The usual order: prompt → add RAG → add evals → fine-tune only when evals show a gap that prompting and RAG can't close. You often end up combining a fine-tuned model *with* RAG.

**LoRA (Low-Rank Adaptation):**
- Instead of updating a huge weight matrix W, freeze it and learn a small update `ΔW = B·A`, where A and B are thin matrices (rank r, e.g. 8–64).
- That's often <1% of the parameters, so you can train on a single GPU and store many small "adapters" for one base model.
- **QLoRA** does this on top of a quantized (4-bit) base model, which saves even more memory.

**Quantization** stores weights in fewer bits (fp16 → int8 → 4-bit):
- Big reductions in memory and cost, often small quality loss.
- It's the reason you can run a 7–8B model on a laptop (common formats: GGUF for llama.cpp/Ollama, AWQ, GPTQ).
- Tradeoff: quality drops more at very low bit widths and on harder tasks. Always evaluate on *your* task.

**Likely follow-ups**
- *What data do you need to fine-tune?* Hundreds to thousands of high-quality examples in exactly the format you'll use at inference, plus a held-out evaluation set. Data quality matters more than quantity.
- *What risks come with fine-tuning?* Catastrophic forgetting (the model loses general skills), overfitting, maintenance burden when the base model updates, and possibly weakened safety behaviour.

**What a strong answer shows:** You default to the cheapest effective option, you have a decision rule, and you're evaluation-driven.

## Section E: Limits and failure modes

### Q14. What is a context window? What actually happens with very long contexts?

**Answer**
The context window is the maximum number of tokens (input plus output) the model can attend to in one call. Modern models advertise 128k to 1M+.

What happens in practice:
- **"Lost in the middle":** research (Liu et al., 2023) showed models use information at the **start and end** of a long context better than information in the middle. Put critical instructions and the most relevant documents near the edges.
- **Effective context < advertised context.** Accuracy on multi-fact reasoning often drops well before the limit. "Needle in a haystack" tests (finding one sentence) overstate real-world ability.
- **Cost and latency grow** with every input token: prefill compute plus KV-cache memory.
- **Distraction:** irrelevant context can actively lower answer quality. More context isn't free.

So "just put everything in the context" works for small corpora and prototypes. RAG still wins on cost, latency, freshness, access control and citations at scale. Often the best approach is a mix: retrieve well, then use generous context for the retrieved material.

**Likely follow-ups**
- *How does attention cost grow with length?* Standard attention compute is O(n²) in sequence length. **FlashAttention** reorganises the computation to be memory-efficient and much faster, but it is still exact attention, so compute remains quadratic.

**What a strong answer shows:** You don't accept marketing numbers, and you reason about quality, cost and latency together.

### Q15. Why do LLMs hallucinate, and how do you reduce it in a product?

**Answer**
**Why:**
- The model is trained to produce *plausible* continuations, not *true* ones. When it lacks the knowledge, the most plausible continuation is a confident-sounding guess.
- Training rewards answering over saying "I don't know".
- Knowledge is compressed into the weights in a lossy way, so rare facts blur.

**Mitigations, roughly in order of impact:**
1. **Grounding:** give the facts in context (RAG or tools) and instruct the model to answer *only* from them.
2. **Permission to abstain:** say explicitly "If the context doesn't contain the answer, say you don't know." Then test that it actually does.
3. **Citations:** require the answer to reference source IDs, and verify in code that those IDs were actually provided.
4. **Lower temperature** for factual tasks.
5. **Structured output** with validation, so made-up fields fail loudly.
6. **Post-checks:** an LLM-as-judge or NLI check that each claim is supported by the context. NLI (natural language inference) models classify whether text A supports, contradicts, or is neutral to text B.
7. **Design the UX for uncertainty:** show sources, confidence, and an easy path to a human.
8. **Measure it:** track a **faithfulness** metric in evals (Part 2) so you know whether changes help.

**Likely follow-ups**
- *Can RAG itself cause hallucinations?* Yes. Bad retrieval gives the model wrong or partial context, and it will confidently use it. Many "hallucinations" are really retrieval failures. Debug retrieval first.

**What a strong answer shows:** You treat hallucination as an engineering problem with layered defences and measurement, not a mystery.

## Section F: Prompting and structured output

### Q16. What prompting techniques actually matter in production?

**Answer**
- **A clear role and task.** Say who the model is, what to do, the audience, and the constraints. Most prompt failures are really specification failures.
- **Separate instructions from data.** Use delimiters (XML-style tags work well) around documents and user input. This improves accuracy and is a first, partial line of defence against prompt injection.
- **Few-shot examples.** 2–5 examples of the input → output you want. They're very powerful for format and edge cases. Use diverse examples, or the model copies their quirks.
- **Chain-of-thought (CoT).** Asking the model to reason before answering improves multi-step tasks. In production, keep the reasoning separate from the final answer (e.g. a separate field), or use a reasoning model.
- **Structured output.** Ask for JSON that matches a schema and validate it (Q17).
- **Break up complex tasks.** Chain several focused calls (extract → validate → write) instead of one giant prompt. Each step is easier to test and debug.
- **Put the right content in the right place.** System prompt for durable rules; user turn for the task; the most important instructions repeated near the end for long prompts.
- **Version and test prompts like code.** Every prompt change runs against an eval set (Part 3).

**Likely follow-ups**
- *System prompt vs. user prompt?* The system prompt sets persistent behaviour and is usually weighted more heavily. But it's not a security boundary: users can still try to override it.
- *How do you make prompts robust to model upgrades?* Eval suites, avoiding reliance on quirks, and pinning model versions with a planned upgrade-and-evaluate process.

**What a strong answer shows:** A practical, test-driven approach rather than "magic phrases".

### Q17. How do function calling and structured outputs work under the hood?

**Answer**
- **Function / tool calling:**
  1. You send tool definitions (name, description, JSON Schema for the parameters) alongside the messages.
  2. The model has been fine-tuned to output a special structured "tool call" (tool name plus JSON arguments) when a tool would help.
  3. **The model never runs anything.** *Your code* executes the tool and sends the result back as a message.
  4. The model then continues: answers, or calls another tool. That loop is the core of every agent (Part 3).
- **Structured outputs / JSON mode:** there are two levels of guarantee.
  - *Prompt-only*: "Return JSON…". It usually works but can break.
  - *Constrained decoding*: the provider restricts which tokens can be sampled at each step, so the output **must** match the JSON Schema. Libraries like Outlines do the same with open models.
  - Even with schema guarantees, **validate the semantics** in code: an enum value that parses fine can still be wrong for the business.

**Pattern in Python:** define a Pydantic model → pass its JSON Schema → parse the response with `Model.model_validate_json(...)`. On a validation error, re-prompt with the error message, with a cap on retries. Libraries like **Instructor** package this loop.

**Likely follow-ups**
- *What if the model calls a tool with bad arguments?* Validate them, return a clear error message *to the model* as the tool result, and let it retry within a limit. Don't crash the request.
- *How many tools can you give a model?* Accuracy drops as the tool list grows (descriptions compete with each other). Group tools, route to subsets, or load them dynamically.

**What a strong answer shows:** You know the model only *proposes* calls, and you design validation and error loops around that.

## Section G: Choosing and running models

### Q18. How do you choose a model for a feature?

**Answer**
Start from requirements, not from a leaderboard:
1. **Quality on *your* task.** Build a small eval set (30–100 real examples) and test 2–3 candidates. Public benchmarks are only a rough filter.
2. **Latency:** TTFT and tokens/sec at your expected prompt and output sizes.
3. **Cost:** (input tokens × price) + (output tokens × price), times volume. Include retries and agent loops, which multiply the calls.
4. **Context window and features:** tool calling, structured output, vision, prompt caching, streaming.
5. **Data and compliance:** where the data is processed, retention policies, regional hosting (e.g. via a cloud provider like AWS Bedrock), and whether you need open weights on your own infrastructure.
6. **Operations:** rate limits, availability, deprecation schedules, provider lock-in.

Common pattern, **model routing**: a cheap, fast model handles simple or classification tasks, and a stronger model handles the hard ones. Have a fallback provider for outages.

**Likely follow-ups**
- *Open-weight vs. API models?* Open weights give you control, data locality, fine-tuning and possibly lower cost at very high volume, but you take on serving, scaling and upgrades. APIs are faster to ship and usually stronger at the frontier.
- *How do you handle a model being deprecated?* Abstract the provider behind an interface, keep evals ready, pin versions, and test the replacement before switching.

**What a strong answer shows:** You make the choice with evals and constraints, and you think about operations, not just "which model is smartest".

### Q19. What does "LLM-powered feature" mean architecturally? Where does the LLM sit in a normal backend?

**Answer**
Treat the LLM as an **unreliable, slow, expensive, non-deterministic external dependency**, like a third-party API with extra quirks.

```
Client → API (FastAPI) → Service layer → [Prompt builder → LLM client (retries, timeouts, fallback)]
                                       → [Retriever / tools]
                                       → [Validators / guardrails] → Response (often streamed)
                       → Tracing, cost logging, evals pipeline (async)
```

Principles:
- **Isolate the LLM behind your own interface** (`LLMClient.complete(...)`) so you can swap providers, add caching and mock it in tests.
- **Timeouts, retries with backoff + jitter, and circuit breakers**, exactly as for any remote dependency (Part 4).
- **Stream** to the user for anything that takes more than about a second.
- **Validate outputs** before acting on them, especially before side effects like writing to a database, sending emails or running code.
- **Make it observable:** log the prompt version, model, tokens, latency, cost, and a trace ID for every call (Part 3).
- **Use async** for I/O-bound LLM calls, so one slow call doesn't block the server.

**What a strong answer shows:** You bring normal backend engineering discipline to AI features. Interviewers for "AI + backend" roles are often checking exactly this.

### Q20. What are the biggest misconceptions you see about LLMs on engineering teams?

**Answer** (an opinion question: they want judgement, not a right answer)
- *"A better prompt will fix it"*, when the real problem is missing data, bad retrieval, or an unclear spec.
- *"It worked on my 5 examples, so ship it"*, without an eval set covering edge cases.
- *"Temperature 0 means deterministic and testable."*
- *"Longer context means we don't need retrieval."*
- *"Agents for everything"*, when a fixed workflow would be cheaper, faster and more reliable.
- *"The system prompt is a security boundary."*
- *"The model's self-reported confidence is calibrated."* Usually it isn't.

**What a strong answer shows:** Experience and calm, practical scepticism. Give one example of how you'd steer a team away from each misconception.
