# Token Economics, KV Cache, and Prefix Caching

## What It Is

Token economics is the discipline of understanding, measuring, and minimizing the cost and latency implications of token usage in LLM systems. It spans three tightly coupled concerns:

1. **Token pricing** — how API providers bill, and where cost actually accumulates
2. **KV cache** — how the GPU stores computation during inference, why it's the primary memory bottleneck, and what it means for system design
3. **Prefix caching** — how repeated prompt prefixes can be cached across requests, and how to architect systems to exploit this

These are not peripheral optimizations. At any meaningful scale, ignoring token economics makes systems economically unviable. At Haptik or Yellow.ai handling millions of conversations, a 2× token reduction is a 2× cost reduction.

---

## Why It Matters

- A 4K-token RAG prompt at GPT-4o pricing = $0.01 per query. At 100K queries/day = $1,000/day = $365K/year — just for one feature.
- KV cache size dictates maximum context length on a given GPU. A 70B model needs ~140GB for weights alone; KV cache for 32K context adds another ~80GB. Understanding this determines what hardware you need.
- Prefix caching can reduce input token costs by 50–90% for RAG systems where the same documents are queried repeatedly. Anthropic and OpenAI both offer this — but you have to architect your prompts to exploit it.
- Batch APIs offer 50% cost reduction for non-real-time workloads. Most teams don't use them.

## Token Pricing Mechanics

### How Providers Bill

All major providers bill separately for input and output tokens:

```
Cost = (input_tokens / 1M) × input_rate + (output_tokens / 1M) × output_rate
```

Current rates (approximate, verify before using):

| Model | Input ($/1M) | Output ($/1M) | Cached input ($/1M) |
|-------|-------------|--------------|-------------------|
| GPT-4o | $2.50 | $10.00 | $1.25 |
| GPT-4o-mini | $0.15 | $0.60 | $0.075 |
| Claude Sonnet 4.5 | $3.00 | $15.00 | $0.30 |
| Claude Haiku 3.5 | $0.80 | $4.00 | $0.08 |
| Gemini 1.5 Pro | $1.25 | $5.00 | $0.3125 |
| Llama 3.1 70B (Together) | $0.88 | $0.88 | — |

**Key insight**: Output tokens cost 4–5× more than input tokens. This is because output is generated autoregressively (one token per forward pass), while input is processed in parallel. This means verbose responses are disproportionately expensive — instruct the model to be concise.

### Where Cost Accumulates in RAG

For a typical RAG call:

```
Token breakdown per query:
┌─────────────────────────────────┬────────┬──────────┐
│ Component                       │ Tokens │ % of cost│
├─────────────────────────────────┼────────┼──────────┤
│ System prompt                   │  500   │   8%     │
│ Conversation history (5 turns)  │ 1,000  │  16%     │
│ Retrieved chunks (5 × 400 tok)  │ 2,000  │  32%     │
│ User query                      │   50   │   1%     │
│ ─────────────────────────────── │ ────── │ ──────── │
│ Total input                     │ 3,550  │  57%     │
│ Output response                 │  400   │  43%     │
│ ─────────────────────────────── │ ────── │ ──────── │
│ Total tokens                    │ 3,950  │  100%    │
└─────────────────────────────────┴────────┴──────────┘

At GPT-4o: 3550 × $2.50/1M + 400 × $10.00/1M = $0.0089 + $0.004 = $0.013/query
At GPT-4o-mini: 3550 × $0.15/1M + 400 × $0.60/1M = $0.0005 + $0.00024 = $0.00077/query
```

**Lever ranking by impact**:
1. Model choice (GPT-4o → GPT-4o-mini): 17× cost reduction
2. Fewer/smaller chunks: 30% of input cost
3. Prefix caching on system prompt: 8% of input cost (or more with large prompts)
4. Shorter output via better instructions: 43% of total cost

## KV Cache — How It Works

### The Problem Without KV Cache

LLM generation is autoregressive: each token is generated by a full forward pass through the model. Without caching:

```
Prompt: [T1, T2, T3, T4, T5]
Generate T6: forward pass over [T1..T5]          → uses T1..T5 attention
Generate T7: forward pass over [T1..T5, T6]      → recomputes T1..T5 attention
Generate T8: forward pass over [T1..T5, T6, T7]  → recomputes T1..T5 attention again
...
```

The computation for T1..T5 is recomputed at every generation step. For a 4K-token prompt generating 500 tokens, you're recomputing 4000-token attention 500 times. This is quadratically wasteful.

### The KV Cache Solution

During the forward pass, each attention layer computes Keys (K) and Values (V) for each token. These K and V tensors depend only on the input tokens, not on future generated tokens. They can be cached.

```
Prompt processing (prefill phase):
  Compute K, V for all prompt tokens [T1..T5]
  Cache: KV_cache = {layer_0: (K0, V0), layer_1: (K1, V1), ...}

Generation step for T6:
  Compute Q for T6 only
  Attention: Q6 @ KV_cache[all prev tokens] → attention output
  Append K6, V6 to cache
  → Only ONE token's computation, not 5 tokens

Generation step for T7:
  Compute Q for T7 only
  Attend to cache (now contains T1..T6)
  → Still ONE token's computation
```

**Net effect**: The prefill phase is O(n²) (unavoidable for the initial prompt), but each generation step is O(n) — linear in current sequence length, not quadratic.

### KV Cache Memory Cost

This is where hardware requirements come from:

```
KV cache size per token:
  = 2 (K and V) × num_layers × num_heads × head_dim × bytes_per_element
  
For Llama 3 8B (fp16):
  = 2 × 32 layers × 8 heads × 128 head_dim × 2 bytes
  = 131,072 bytes = 128 KB per token

For 8K context: 8192 × 128KB = 1 GB of KV cache
For 128K context: 131,072 × 128KB = 16 GB of KV cache
```

For Llama 3 70B (fp16):
```
= 2 × 80 layers × 8 GQA groups × 128 head_dim × 2 bytes
= 327,680 bytes = 320 KB per token

For 128K context: 131,072 × 320KB = 40 GB of KV cache
Model weights alone: ~140 GB
Total GPU memory needed: ~180 GB
```

This is why **long-context models require massive GPU clusters** and why reducing context length directly reduces infra cost.

### GQA (Grouped Query Attention) and MQA

These are optimizations specifically targeting KV cache memory:

**MHA (Multi-Head Attention)**: Every head has its own K, V matrices. KV cache = `num_heads × head_dim × 2 × layers`.

**GQA (Grouped Query Attention)**: Multiple query heads share a single K, V pair (group). Llama 3 uses 8 KV heads for 32 query heads (4:1 ratio). KV cache = `num_kv_heads × head_dim × 2 × layers` — 4× smaller.

**MQA (Multi-Query Attention)**: Extreme case — all query heads share one K, V. Maximum cache reduction, small quality loss.

```
KV cache size comparison for 128K context, Llama 3 70B:
  MHA (hypothetical): 80 layers × 64 heads × 128 dim × 2 × 2 bytes × 128K = 160GB
  GQA (actual):       80 layers × 8 groups × 128 dim × 2 × 2 bytes × 128K = 40GB ← 4× saving
```

## Prefix Caching

### The Core Idea

If multiple requests share a common prefix (same system prompt, same document context), the KV cache for that prefix can be computed once and reused across requests.

```
Without prefix caching:
  Request 1: [system_prompt | context_doc | query_1] → compute KV for ALL tokens
  Request 2: [system_prompt | context_doc | query_2] → recompute KV for ALL tokens again
  Request 3: [system_prompt | context_doc | query_3] → recompute again

With prefix caching:
  Request 1: Compute + cache KV for [system_prompt | context_doc]
             Compute KV for [query_1] only
  Request 2: Cache HIT for [system_prompt | context_doc]
             Compute KV for [query_2] only
  Request 3: Cache HIT for [system_prompt | context_doc]
             Compute KV for [query_3] only

Cost reduction: (system_prompt + context) / total_tokens × 100%
= (500 + 2000) / 3550 = 70% of input tokens cached → 70% cost reduction on input
```

### How Providers Implement It

**OpenAI**: Automatic prefix caching on all requests ≥ 1024 tokens. No code changes needed. Cached tokens billed at 50% of normal input rate. Cache lifetime ~5–10 minutes.

**Anthropic**: Explicit opt-in via `cache_control` parameter. More control, longer TTL (5 minutes for ephemeral, potentially longer). Billed at 10% of normal rate for cache hits (90% reduction vs standard).

```python
# Anthropic explicit prefix caching
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "You are a financial analyst. Answer questions only from provided context.",
        },
        {
            "type": "text",
            "text": large_document_context,  # 5000 tokens of retrieved docs
            "cache_control": {"type": "ephemeral"},  # ← cache this prefix
        },
    ],
    messages=[{"role": "user", "content": user_question}],
)

# First call: cache miss — full input cost
# Subsequent calls with same system + context: 90% reduction on those tokens
```

### Architecting for Cache Hit Rate

The prefix must be **identical** (byte-for-byte) to get a cache hit. This constrains your prompt architecture:

```python
# BAD for caching — dynamic data mixed into the stable prefix
def build_prompt_bad(user_name, docs, question):
    return f"""
    You are helping {user_name}.    ← changes per user, breaks prefix cache
    
    Context:
    {docs}                          ← retrieved docs, may vary
    
    Question: {question}
    """

# GOOD for caching — stable prefix first, dynamic content last
def build_prompt_good(docs, question, user_name):
    system = """
    You are a helpful assistant. Answer using only the provided context.
    If context is insufficient, say "I don't have that information."
    """  # ← ALWAYS the same → high cache hit rate for system prompt
    
    # Context goes second — if same docs are queried repeatedly, this also caches
    context_block = f"Context:\n{docs}"
    
    # User-specific and dynamic content goes LAST
    user_message = f"User: {user_name}\nQuestion: {question}"
    
    return system, context_block, user_message
```

**Golden rule**: Stable content first, dynamic content last. The cache key is a prefix — any change in the middle invalidates everything after it.

### Cache Hit Rate Estimation

```python
def estimate_cache_benefit(queries_per_hour: int, system_prompt_tokens: int,
                           avg_context_tokens: int, avg_query_tokens: int,
                           cache_ttl_minutes: int = 5) -> dict:
    
    total_input = system_prompt_tokens + avg_context_tokens + avg_query_tokens
    cacheable = system_prompt_tokens + avg_context_tokens  # stable portion
    
    # Requests within cache TTL reuse the cache
    requests_per_ttl = queries_per_hour * (cache_ttl_minutes / 60)
    cache_hit_rate = min(0.95, (requests_per_ttl - 1) / requests_per_ttl)
    
    # Cost per query with and without caching
    rate_per_token = 2.50 / 1_000_000  # GPT-4o input rate
    cached_rate = rate_per_token * 0.5   # 50% discount
    
    cost_without = total_input * rate_per_token
    cost_with = (
        cacheable * rate_per_token * (1 - cache_hit_rate) +
        cacheable * cached_rate * cache_hit_rate +
        avg_query_tokens * rate_per_token
    )
    
    return {
        "cache_hit_rate": f"{cache_hit_rate:.1%}",
        "cost_per_query_without": f"${cost_without:.5f}",
        "cost_per_query_with": f"${cost_with:.5f}",
        "savings_pct": f"{(1 - cost_with/cost_without):.1%}",
    }

# Example: 1000 queries/hour, 500 system + 2000 context + 50 query tokens
print(estimate_cache_benefit(1000, 500, 2000, 50))
# cache_hit_rate: 94.0%, savings_pct: ~62%
```

## Batch API

Both OpenAI and Anthropic offer batch processing APIs at 50% cost reduction for non-real-time workloads:

```python
# OpenAI Batch API
import json, openai

client = openai.OpenAI()

# Prepare batch requests
requests = []
for i, (doc_id, doc_text) in enumerate(documents):
    requests.append({
        "custom_id": f"summary-{doc_id}",
        "method": "POST",
        "url": "/v1/chat/completions",
        "body": {
            "model": "gpt-4o-mini",
            "messages": [
                {"role": "system", "content": "Summarize this document in 3 bullet points."},
                {"role": "user", "content": doc_text},
            ],
            "max_tokens": 300,
        }
    })

# Write to JSONL file
with open("batch_requests.jsonl", "w") as f:
    for req in requests:
        f.write(json.dumps(req) + "\n")

# Upload and submit batch
batch_file = client.files.create(file=open("batch_requests.jsonl", "rb"), purpose="batch")
batch = client.batches.create(
    input_file_id=batch_file.id,
    endpoint="/v1/chat/completions",
    completion_window="24h",  # SLA: results within 24 hours
)

print(f"Batch submitted: {batch.id}")
# Poll for completion
import time
while batch.status not in ("completed", "failed", "cancelled"):
    time.sleep(60)
    batch = client.batches.retrieve(batch.id)

# Download results
results = client.files.content(batch.output_file_id)
```

**Use cases**: Document summarization pipelines, evaluation runs, nightly indexing enrichment, bulk entity extraction. Anything that doesn't need real-time response.

## Token Reduction Techniques

### 1. Output Length Control

```python
# Instead of: "Explain X in detail"
# Use: "Explain X in 2 sentences"
# Or: "Answer in under 100 words"
# Or: set max_tokens explicitly

response = openai.chat.completions.create(
    model="gpt-4o",
    messages=[...],
    max_tokens=300,   # hard cap — model stops at 300 tokens regardless
)
```

**Don't rely on the model to be concise** — set `max_tokens` as a hard guard, especially in production.

### 2. Prompt Compression (LLMLingua)

Compresses prompts by removing low-information tokens while preserving meaning:

```python
from llmlingua import PromptCompressor

compressor = PromptCompressor(model_name="microsoft/llmlingua-2-bert-base-multilingual-cased-meetingbank")

compressed = compressor.compress_prompt(
    context=retrieved_chunks_text,
    instruction=system_prompt,
    question=user_query,
    target_token=1000,           # target: compress to 1000 tokens
    rank_method="longllmlingua",
)

# Use compressed["compressed_prompt"] instead of original
# Typically 3–5× compression with ~5% quality loss
```

### 3. Selective Context Inclusion

Don't send all retrieved chunks — score and trim before sending to LLM:

```python
def trim_context_to_budget(chunks: list[Chunk], query: str,
                            token_budget: int = 2000) -> list[Chunk]:
    """Keep only chunks until token budget is exhausted."""
    selected = []
    tokens_used = 0
    
    for chunk in chunks:  # chunks already ranked by relevance
        chunk_tokens = count_tokens(chunk.text)
        if tokens_used + chunk_tokens > token_budget:
            break
        selected.append(chunk)
        tokens_used += chunk_tokens
    
    return selected
```

### 4. Cached Long Documents (Anthropic)

For systems that repeatedly query the same large document:

```python
# Load document into Anthropic's cache ONCE per session
# Then query it multiple times cheaply
CACHED_DOCUMENT = {
    "type": "text",
    "text": full_10k_filing,  # 50K tokens
    "cache_control": {"type": "ephemeral"},
}

def query_document(question: str) -> str:
    return client.messages.create(
        model="claude-opus-4-5",
        max_tokens=500,
        system=[
            {"type": "text", "text": analyst_system_prompt},
            CACHED_DOCUMENT,  # cached — billed at 10% rate after first call
        ],
        messages=[{"role": "user", "content": question}],
    ).content[0].text

# First call: ~$0.15 (50K tokens input at $3/1M)
# Each subsequent call: ~$0.015 (90% discount on 50K tokens)
# After 10 queries: 73% cost savings
```

## Revision Anchors

- **KV cache size**: `2 × layers × kv_heads × head_dim × bytes × context_length`. GQA reduces this 4–8× vs MHA. Long context = large KV cache = large GPU requirement.
- **Prefill vs decode**: Prefill (processing prompt) is O(n²), parallel. Decode (generation) is O(n) per token, sequential. TTFT dominated by prefill; throughput dominated by decode.
- **Prefix caching rule**: Stable content FIRST, dynamic content LAST. Any change in the middle invalidates the cache for everything after it.
- **Output tokens cost 4–5×**: Always set `max_tokens` hard limits. Verbose outputs are disproportionately expensive.
- **Batch API = 50% discount**: No code needed beyond batching — use for all non-real-time LLM workloads.
- **Cached input = 10–50% of normal rate**: Anthropic explicit (`cache_control`), OpenAI automatic (≥1024 token prefix). Design prompts to maximize stable prefix length.
