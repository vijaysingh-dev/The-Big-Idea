# Utility Types

Built-in type transformations. Using them instead of hand-writing derived shapes means a change to the source type propagates automatically.

## The everyday set

```ts
type User = {
  id: string;
  name: string;
  email: string;
  role: "admin" | "member";
};

Partial<User>                    // all properties optional
Required<User>                   // all required
Readonly<User>                   // all readonly
Pick<User, "id" | "name">        // subset
Omit<User, "id">                 // everything except
Record<string, User>             // dictionary
```

`Pick` and `Omit` are the two you will use constantly:

```ts
type CreateUser = Omit<User, "id">;                    // server assigns the id
type UserSummary = Pick<User, "id" | "name">;          // list view
type UpdateUser = Partial<Omit<User, "id">>;           // PATCH payload
```

The important property: rename `email` to `emailAddress` on `User` and every derived type updates. Hand-written duplicates silently drift.

**`Omit` does not check its keys.** `Omit<User, "emial">` compiles and silently omits nothing — a typo produces a wrong type with no error. `Pick` does check, which is one reason to prefer it where either works.

A stricter version:

```ts
type StrictOmit<T, K extends keyof T> = Omit<T, K>;
```

## Union utilities

```ts
type Status = "idle" | "loading" | "success" | "error";

Exclude<Status, "idle">             // "loading" | "success" | "error"
Extract<Status, "success" | "x">    // "success"
NonNullable<string | null>          // string
```

`Exclude` and `Extract` operate on union members; `Omit` and `Pick` operate on object keys. Mixing them up is a common early mistake.

## Function utilities

```ts
function createUser(name: string, role: "admin" | "member") {
  return { id: "1", name, role };
}

ReturnType<typeof createUser>        // { id: string; name: string; role: ... }
Parameters<typeof createUser>        // [name: string, role: "admin" | "member"]
Awaited<ReturnType<typeof fetchUser>> // unwraps the Promise
```

`Awaited<ReturnType<...>>` is the standard way to derive a component's data type from its API function ([[24.1 - Building an API Layer]]):

```ts
type Product = Awaited<ReturnType<typeof productsApi.byId>>;
```

Changing the fetcher's return type updates every consumer with no manual edits.

## String manipulation

```ts
Uppercase<"hello">        // "HELLO"
Capitalize<"hello">       // "Hello"

type EventName<T extends string> = `on${Capitalize<T>}`;
type Handlers = EventName<"click" | "focus">;   // "onClick" | "onFocus"
```

Template literal types combined with mapped types generate whole shapes:

```ts
type Setters<T> = {
  [K in keyof T as `set${Capitalize<string & K>}`]: (value: T[K]) => void;
};

type UserSetters = Setters<User>;
// { setId: (v: string) => void; setName: (v: string) => void; ... }
```

Powerful, and easy to overuse — a generated type nobody can read is worse than an explicit one.

## Composing them

```ts
type Draft<T> = Partial<Omit<T, "id" | "createdAt">>;
type Entity<T> = T & { id: string; createdAt: Date };
type FormValues = Record<keyof CreateUser, string>;   // all fields as strings
```

The `Record<keyof T, string>` pattern is useful for form state, where every field starts as a string regardless of its eventual type ([[21.1 - Controlled Forms in Practice]]).

## Useful custom utilities

Not built in, but worth having in a shared file:

```ts
// Deep readonly
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};

// Require at least one of a set
type RequireAtLeastOne<T, K extends keyof T = keyof T> =
  Omit<T, K> & { [P in K]-?: Required<Pick<T, P>> & Partial<Omit<T, P>> }[K];

// Union to a discriminated shape
type Prettify<T> = { [K in keyof T]: T[K] } & {};
```

`Prettify` is the most useful of these day to day — it forces the checker to expand an intersection into a flat object in hover tooltips, which turns an unreadable `A & B & C` into the actual shape ([[25.1 - Types vs Interfaces]]).

## React-specific utilities

```tsx
import type { ComponentProps, ComponentPropsWithoutRef, ElementRef } from "react";

type ButtonProps = ComponentPropsWithoutRef<"button">;      // all native button props
type InputProps = ComponentProps<typeof CustomInput>;        // another component's props
type DivRef = ElementRef<"div">;                             // HTMLDivElement
```

`ComponentPropsWithoutRef<"button">` is how a wrapper component inherits every native prop — `onClick`, `disabled`, `aria-*`, `data-*` — without enumerating them ([[25.4 - Typing Props and Children]]):

```tsx
type Props = { variant?: "primary" | "ghost" } & ComponentPropsWithoutRef<"button">;
```

Overriding a native prop requires omitting it first, or the intersection produces `never`:

```tsx
type Props = Omit<ComponentPropsWithoutRef<"input">, "onChange"> & {
  onChange: (value: string) => void;
};
```

This is the single most common typing error in component libraries.

## satisfies

Not a utility type, but the operator that most changes how these are used:

```ts
const config = {
  api: "/v1",
  timeout: 5000,
} satisfies Record<string, string | number>;

config.api.toUpperCase();     // string — the literal type is preserved
```

With an annotation (`const config: Record<string, string | number>`), `config.api` widens to `string | number` and the method call fails. `satisfies` checks conformance **without widening**, keeping the precise inferred type.

The pattern is especially useful for route maps, theme objects and config:

```ts
const routes = {
  home: "/",
  product: "/products/:id",
} satisfies Record<string, `/${string}`>;

type RouteName = keyof typeof routes;   // "home" | "product"
```

## Deriving from values

```ts
const STATUSES = ["idle", "loading", "error"] as const;
type Status = typeof STATUSES[number];        // "idle" | "loading" | "error"

const theme = { primary: "#0b5", surface: "#fff" } as const;
type ThemeToken = keyof typeof theme;
```

`as const` plus `typeof` derives types from runtime values, so the array or object stays the single source of truth. Adding an entry updates the type automatically, and the runtime list and the type cannot drift.

This is one of the highest-value TypeScript patterns in application code.

## Restraint

Every derived type is indirection. A reader following `Draft<Entity<Omit<User, "meta">>>` has to unwind four layers to know what they are holding.

The threshold: derive when the source type genuinely owns the shape and will change; write it out when the derivation is more complex than the result.

`Prettify` helps when a composed type must be read in tooltips, and is worth applying at public API boundaries.

## How senior engineers actually use this

**They derive rather than duplicate**, so a schema change propagates.

**They use `satisfies` for config objects** instead of annotations, keeping literal types.

**They derive unions from `as const` arrays**, so the runtime list and the type stay in sync.

**They use `ComponentPropsWithoutRef` for every wrapper component**, and remember to `Omit` before overriding.

**They keep a small shared utilities file** rather than reinventing `Prettify` and friends per project.

## Common pitfalls

- `Omit` silently accepting a misspelled key.
- Confusing `Omit`/`Pick` (keys) with `Exclude`/`Extract` (union members).
- Overriding a native prop without `Omit`, producing `never`.
- Annotating a config object instead of using `satisfies`, losing literal types.
- Forgetting `as const`, so an array widens to `string[]`.
- Composed types so deep that hover tooltips are unreadable.
- Hand-writing derived shapes that then drift from the source.

## Interview angle

Utility types rarely get a dedicated question but appear throughout practical TypeScript tasks. The ones worth naming fluently are `Pick`, `Omit`, `Partial`, `Record`, `ReturnType` and `Awaited`. The details that stand out: `Omit` does not validate its keys while `Pick` does, `satisfies` checks without widening, and `as const` plus `typeof x[number]` derives a union from a runtime array — which keeps the value and the type from drifting.
