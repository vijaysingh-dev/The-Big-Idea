# Bulkification Patterns

## The one rule

Your code will be handed one record on Monday and two hundred records on Tuesday, and you do not get to choose which. Bulkification means writing code that behaves identically either way.

This is not a style preference. It is the difference between code that works and code that throws an exception in production. Salesforce enforces **governor limits** — hard runtime caps on how much a single transaction can consume, applied because thousands of customers share the same servers. Two of them matter most here:

- 100 SOQL queries per transaction
- 150 DML statements per transaction (DML = Data Manipulation Language: insert, update, delete, upsert)

Put a query inside a loop and you burn one query per record. At 101 records the transaction dies. There is no retry, no partial credit, no graceful degradation.

## Where the 200 records come from

New developers test with one record in the UI and conclude their code is fine. Records arrive in bulk from many places:

- **Data Loader or an integration** loading a CSV of 50,000 rows, which the platform hands to your trigger in chunks of 200
- **Batch Apex** processing records in scopes of up to 2,000
- **A list view mass update**, where a user selects rows and edits them together
- **A parent record update** cascading to thousands of children through automation
- **A record-triggered flow** calling your invocable Apex with a collection

The 200-record chunk is the important one. A trigger does not fire once per record in a bulk load. It fires once per chunk, with `Trigger.new` holding up to 200 records. Your code runs twelve times for a 2,400-row load, not 2,400 times.

## The broken version

Real scenario. When an Opportunity closes as won, stamp the Account with the close date and bump a lifetime revenue field.

```java
trigger OpportunityTrigger on Opportunity (after update) {
    for (Opportunity opp : Trigger.new) {
        if (opp.StageName == 'Closed Won') {
            Account acc = [SELECT Id, Total_Revenue__c FROM Account WHERE Id = :opp.AccountId];
            acc.Total_Revenue__c = (acc.Total_Revenue__c == null ? 0 : acc.Total_Revenue__c) + opp.Amount;
            acc.Last_Won_Date__c = opp.CloseDate;
            update acc;
        }
    }
}
```

This passes a demo. It fails the moment sales operations mass-closes a quarter's deals. It also breaks a separate rule that matters just as much: business logic never belongs inside a trigger body. Both problems get fixed below.

With 200 opportunities it issues 200 queries and 200 DML statements. It dies at query 101 with `Too many SOQL queries: 101`. Worse, it dies *after* doing 100 queries and roughly 100 updates, and since the whole transaction rolls back, the user sees a cryptic error and none of their work saved.

There is a second bug hiding here that only appears in bulk: if two opportunities in the same batch belong to the same Account, the second query reads a stale copy from the database that does not include the first one's update. One of the two revenue amounts silently vanishes.

## The correct version

Two things need fixing. The trigger should contain no logic at all, and the logic itself needs the three-move pattern: **collect, query once, act once.**

The trigger becomes a router and nothing else:

```java
trigger OpportunityTrigger on Opportunity (after update) {
    OpportunityTriggerHandler.run();
}
```

The handler decides what runs for which event:

```java
public with sharing class OpportunityTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isUpdate) {
            OpportunityService.rollUpWonRevenue(Trigger.new, Trigger.oldMap);
        }
    }
}
```

The service holds the business logic and never touches `Trigger` context directly, which is what makes it callable from a flow, a batch job, or a test with arbitrary data:

```java
public with sharing class OpportunityService {

    public static void rollUpWonRevenue(List<Opportunity> newOpps, Map<Id, Opportunity> oldOpps) {
        Set<Id> accountIds = new Set<Id>();
        List<Opportunity> newlyWon = new List<Opportunity>();

        for (Opportunity opp : newOpps) {
            Opportunity prior = oldOpps.get(opp.Id);
            if (opp.StageName == 'Closed Won' && prior.StageName != 'Closed Won' && opp.AccountId != null) {
                accountIds.add(opp.AccountId);
                newlyWon.add(opp);
            }
        }

        if (accountIds.isEmpty()) {
            return;
        }

        Map<Id, Account> accountsById = new Map<Id, Account>([
            SELECT Id, Total_Revenue__c, Last_Won_Date__c
            FROM Account
            WHERE Id IN :accountIds
        ]);

        for (Opportunity opp : newlyWon) {
            Account acc = accountsById.get(opp.AccountId);
            if (acc == null) {
                continue;
            }
            // accumulating in memory keeps repeated accounts in the same batch consistent
            acc.Total_Revenue__c = (acc.Total_Revenue__c == null ? 0 : acc.Total_Revenue__c)
                                   + (opp.Amount == null ? 0 : opp.Amount);
            if (acc.Last_Won_Date__c == null || opp.CloseDate > acc.Last_Won_Date__c) {
                acc.Last_Won_Date__c = opp.CloseDate;
            }
        }

        update accountsById.values();
    }
}
```

One query. One DML statement. Identical behaviour at 1 record or 200. The full reasoning behind the trigger, handler and service split is in [[11.5 - Trigger Handler Pattern]] and [[18.3 - Service Layer]].

Four things in there are worth naming, because they show up in every bulkified class you will ever write:

**`Set<Id>` for collecting.** Sets deduplicate automatically. If fifty opportunities belong to one account, you query that account once.

**`Map<Id, SObject>` from a query.** Constructing a `Map` directly from a SOQL result gives you record-ID lookup with no loop. This single trick removes most nested loops from Apex.

**The `oldMap` comparison.** `Trigger.oldMap` holds the pre-update version of each record. Checking that the stage *changed* to Closed Won, rather than merely *is* Closed Won, stops the revenue from being added again every time anyone edits the opportunity afterwards. Bulkification and correctness are separate problems and you need both.

**Accumulating in memory.** Because the same `Account` instance is mutated across iterations, duplicate accounts in one batch add up correctly. The broken version could not do this.

## The nested loop trap

The second most common bulkification failure has no query in a loop at all, so it survives code review and then times out in production.

```java
// runs accounts × contacts times
for (Account acc : accounts) {
    for (Contact con : contacts) {
        if (con.AccountId == acc.Id) {
            acc.Primary_Contact_Email__c = con.Email;
        }
    }
}
```

With 200 accounts and 10,000 contacts that is two million iterations. You will hit `Apex CPU time limit exceeded` — a 10-second ceiling on computation in a synchronous transaction, and the hardest limit to debug because the error points nowhere useful.

Restructure into a map first, then loop once:

```java
Map<Id, List<Contact>> contactsByAccount = new Map<Id, List<Contact>>();
for (Contact con : contacts) {
    if (!contactsByAccount.containsKey(con.AccountId)) {
        contactsByAccount.put(con.AccountId, new List<Contact>());
    }
    contactsByAccount.get(con.AccountId).add(con);
}

for (Account acc : accounts) {
    List<Contact> related = contactsByAccount.get(acc.Id);
    if (related != null && !related.isEmpty()) {
        acc.Primary_Contact_Email__c = related[0].Email;
    }
}
```

Two passes instead of a multiplication. 10,200 iterations instead of two million.

## Parent-to-child in one query

A related pattern: you need children of the records in your trigger. Do not query per parent. Use a subquery, or query children filtered by parent ID.

Real scenario — when an Account's billing country changes, update the shipping country on all its open opportunities:

```java
List<Opportunity> toUpdate = new List<Opportunity>();

for (Account acc : [SELECT Id, BillingCountry,
                           (SELECT Id, Shipping_Country__c FROM Opportunities WHERE IsClosed = false)
                    FROM Account WHERE Id IN :changedAccountIds]) {
    for (Opportunity opp : acc.Opportunities) {
        opp.Shipping_Country__c = acc.BillingCountry;
        toUpdate.add(opp);
    }
}

if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

The nested loop here is fine, because the inner collection is only that parent's own children, not the full list. Total iterations equal the number of child records, not parents times children.

Be aware of the ceiling: a query returns at most 50,000 rows across all parents and children combined. If an account can have 20,000 open opportunities, this pattern breaks and you move to Batch Apex ([[12.4 - Batch Apex]]).

## Bulkifying callouts

Bulkification applies to external calls too, and the limit is tighter: 100 callouts per transaction, each capped at 120 seconds total.

Real scenario — sync closed-won opportunities to an ERP. The wrong instinct is one HTTP request per opportunity. The right approach is one request containing all of them, if the receiving API supports batch:

```java
@future(callout=true)
public static void syncClosedWon(Set<Id> opportunityIds) {
    List<Opportunity> opps = [SELECT Id, Name, Amount, CloseDate, Account.ERP_Id__c
                              FROM Opportunity WHERE Id IN :opportunityIds];

    HttpRequest req = new HttpRequest();
    req.setEndpoint('callout:ERP_System/api/orders/batch');
    req.setMethod('POST');
    req.setHeader('Content-Type', 'application/json');
    req.setBody(JSON.serialize(OrderPayload.fromOpportunities(opps)));

    HttpResponse res = new Http().send(req);
    if (res.getStatusCode() >= 300) {
        throw new IntegrationException('ERP sync failed: ' + res.getStatusCode() + ' ' + res.getBody());
    }
}
```

If the external API has no batch endpoint, you chunk the work across Queueable jobs instead of trying to fit it into one transaction. See [[12.3 - Queueable Apex]] and [[13.17 - Error Handling, Retries and Idempotency]].

## Proving it works

A test that inserts one record proves nothing about bulk safety. Every trigger and service class needs a test that pushes at least 200 records through it.

```java
@IsTest
static void closedWonUpdatesAccountsInBulk() {
    List<Account> accounts = TestDataFactory.createAccounts(50);
    insert accounts;

    List<Opportunity> opps = new List<Opportunity>();
    for (Integer i = 0; i < 200; i++) {
        opps.add(new Opportunity(
            Name = 'Deal ' + i,
            AccountId = accounts[Math.mod(i, 50)].Id,
            StageName = 'Prospecting',
            CloseDate = Date.today(),
            Amount = 1000
        ));
    }
    insert opps;

    for (Opportunity opp : opps) {
        opp.StageName = 'Closed Won';
    }

    Test.startTest();
    update opps;
    Test.stopTest();

    Map<Id, Account> refreshed = new Map<Id, Account>([
        SELECT Id, Total_Revenue__c FROM Account WHERE Id IN :accounts
    ]);
    for (Account acc : accounts) {
        Assert.areEqual(4000, refreshed.get(acc.Id).Total_Revenue__c,
            'Each account had four opportunities of 1000 each');
    }
}
```

Note the deliberate design: 200 opportunities spread across only 50 accounts, so multiple records in the batch share a parent. That is exactly the case the broken version silently got wrong, and a test with a one-to-one mapping would never catch it.

## What senior engineers actually watch for

**Bulkification lives in the service layer, not the trigger.** In a mature org the trigger is three lines that hand `Trigger.new` to a handler class. The bulk-safe logic sits in a service method that takes a `List<SObject>` and never assumes a size. See [[11.5 - Trigger Handler Pattern]] and [[18.3 - Service Layer]].

**Every public method takes a collection.** A method signature of `processOpportunity(Opportunity opp)` invites someone to call it in a loop. `processOpportunities(List<Opportunity> opps)` makes the bulk-safe path the only path. This convention alone prevents most bulkification bugs in a large codebase.

**Governor limits are shared across everything in the transaction.** Your trigger is not alone. Flows, validation rules, other triggers, managed packages, and roll-up recalculation all draw from the same 100 queries. Perfectly bulkified code can still fail because a managed package consumed 90 queries before yours ran. This is why orgs consolidate to one trigger per object and audit total automation on hot objects. See [[07.13 - Order of Execution]].

**`Limits` methods for defensive code.** In long-running jobs, check remaining capacity and defer rather than crash:

```java
if (Limits.getQueries() > Limits.getLimitQueries() - 10) {
    System.enqueueJob(new ContinueProcessing(remainingIds));
    return;
}
```

**Bulkification is not always enough.** If genuinely bulk-safe code still exceeds limits at real volumes, the answer is architectural, not a tighter loop: move to Batch Apex, split work across Queueables, or push the aggregation to a nightly job. Recognizing that boundary is the difference between an experienced developer and a stubborn one. See [[16.7 - Designing Around Limits]].
