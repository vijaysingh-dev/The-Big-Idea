# Processes

#backend #os #linux #processes

> **In one line:** A process is a running program plus everything the kernel tracks for it: memory, open files, a PID, a parent. Unix makes new ones with `fork` then `exec`, and cleans them up only when the parent calls `wait`.

---

## The Idea

A program is a file on disk. A **process** is that program running, with:

| Part | What it is |
|---|---|
| **PID** | A number, unique while the process is alive |
| **Address space** | Its own virtual memory: code, heap, stacks, mapped files ([[02.5 - Virtual Memory]]) |
| **File descriptor table** | Its open files and sockets ([[02.7 - File Descriptors and the IO Model]]) |
| **Credentials** | User ID, group ID, capabilities |
| **Parent** | The PID that created it (`PPID`) |
| **Threads** | One or more. Each has its own registers and stack, and all share the rest |
| **State** | Running, sleeping, stopped, zombie |
| **Limits and cgroup** | `ulimit` values, which cgroup it is charged to |

Inside the kernel, all of this hangs off one struct: `task_struct` in Linux, `struct proc` in xv6. On Linux a thread is also a `task_struct` that shares its memory and file table with others. That is the whole difference between a process and a thread at the kernel level.

## fork, exec, wait

Unix creates processes in two steps, and the split is deliberate.

```
parent (PID 100)
   │
   │ fork()
   ├──────────────────────────────► child (PID 101)
   │                                  an exact copy of the parent:
   │                                  same code, same memory (copy-on-write),
   │                                  same open file descriptors
   │                                  │
   │                                  │ execve("/usr/bin/python3", ...)
   │                                  │ replaces the memory with a new program.
   │                                  │ Same PID, same fds (unless CLOEXEC)
   │                                  │
   │ wait4(101)  ◄─── exit(0) ────────┘
   │ collects the exit status
   ▼
```

- **`fork()`** returns twice: the child's PID in the parent, `0` in the child.
- **`execve()`** never returns if it works. The old program is gone.
- **`wait()`** collects the child's exit status, and only then does the kernel free the child's last record.

💡 **Why two steps?** Between `fork` and `exec`, the child can rearrange its own world: redirect stdout to a file, change directory, drop privileges, close fds. That is how a shell does `cmd > out.txt`. `subprocess.Popen` does exactly this dance in C (`Modules/_posixsubprocess.c`).

```python
import os

pid = os.fork()
if pid == 0:
    # child
    os.execvp("ls", ["ls", "-l"])
else:
    # parent
    _, status = os.waitpid(pid, 0)
    print("child exited with", os.waitstatus_to_exitcode(status))
```

### Copy-on-write makes fork cheap

`fork` does not copy memory. Parent and child share the same physical pages, all marked read-only. The first write to a page by either side triggers a page fault, and the kernel copies just that 4 KB page. A 2 GB process forks in a few milliseconds, because only the page tables are copied.

⚠️ **CPython defeats copy-on-write.** Every Python object has a reference count in its header. Merely *reading* an object changes its refcount, which writes to its page, which copies it. A gunicorn master that preloads a 1 GB model and forks 8 workers slowly turns into 9 GB as the workers touch objects. `gc.freeze()` (3.7+) helps by moving objects out of the GC's way, and 3.12's immortal objects help for some built-ins, but the effect never fully goes away. Instagram wrote a well-known post on this.

## Process States

```
               scheduler picks it
   ┌────────┐ ─────────────────► ┌─────────┐
   │ RUNNABLE│                    │ RUNNING │
   │   (R)   │ ◄───────────────── │   (R)   │
   └────────┘   time slice up     └─────────┘
        ▲                           │     │
        │ event arrives             │     │ exit()
        │                           ▼     ▼
   ┌─────────────────────┐     ┌──────────────┐
   │ SLEEPING            │     │ ZOMBIE (Z)   │ ── parent wait()s ──► gone
   │ S = interruptible   │     └──────────────┘
   │ D = uninterruptible │
   └─────────────────────┘
```

What you see in `ps` or `top` in the `STAT` column:

| State | Meaning | When it is a problem |
|---|---|---|
| `R` | Running or ready to run | Many `R` processes and high load means CPU saturation |
| `S` | Sleeping, can be woken by a signal | Normal. An idle server is all `S` |
| `D` | Uninterruptible sleep, usually waiting on disk or NFS | Cannot be killed, even by `kill -9`. Many `D` means storage trouble |
| `Z` | Zombie: exited, parent has not called `wait` | A few is fine. Thousands means a buggy parent and you will run out of PIDs |
| `T` | Stopped (`SIGSTOP`, or a debugger) | Someone pressed Ctrl-Z or attached a debugger |

⚠️ **Load average counts `D` processes too.** A load average of 40 on an 8-core box with idle CPUs usually means processes stuck on I/O, not CPU pressure. See [[02.3 - Threads and the Scheduler]].

## Zombies, Orphans and PID 1

**Zombie:** a child that has exited but whose parent has not called `wait`. It uses no memory, just a slot in the process table with its exit code. You cannot kill a zombie, because it is already dead. You fix it by fixing or killing the parent.

**Orphan:** a child whose parent exits first. The kernel re-parents it to PID 1 (or to the nearest "subreaper"). PID 1 is then responsible for `wait`ing on it.

**This is why PID 1 matters in containers.** In a container, your app *is* PID 1. If your Python app spawns subprocesses and never reaps orphans, zombies pile up. PID 1 also gets special signal treatment: the kernel will not apply default signal actions to it, so `SIGTERM` does nothing unless you installed a handler. Both problems are solved by a tiny init such as `tini` or `docker run --init`. Covered in full in [[02.9 - Signals and Process Lifecycle]].

## /proc: The Process as a Directory

Linux exposes every process as a directory under `/proc/<pid>/`. Everything `ps`, `top` and `lsof` show comes from here.

```bash
PID=$(pgrep -f uvicorn | head -1)

cat /proc/$PID/cmdline | tr '\0' ' '      # full command line
cat /proc/$PID/status                      # state, threads, memory (VmRSS), signals
ls -l /proc/$PID/fd                        # every open file and socket
cat /proc/$PID/limits                      # ulimits, including max open files
cat /proc/$PID/cgroup                      # which cgroup it is charged to
cat /proc/$PID/environ | tr '\0' '\n'      # environment (secrets live here — careful)
cat /proc/$PID/smaps_rollup                # detailed memory breakdown
ls /proc/$PID/task                         # one directory per thread
```

⚠️ `/proc/<pid>/environ` holds every environment variable, including secrets passed by env var. Anyone who can read it can read your database password. That is one reason [[15.5 - Secrets and Key Management]] prefers mounted files with tight permissions.

## Processes in Backend Systems

| System | Process model | Why |
|---|---|---|
| **gunicorn / uvicorn workers** | Prefork: a master forks N workers that share the listening socket | Use every core despite the GIL, and survive a worker crash |
| **Postgres** | One process per connection, forked from the postmaster | Isolation. A crash in one backend cannot corrupt another's memory. The cost is why you need PgBouncer ([[07.9 - Connection Pooling and PgBouncer]]) |
| **Redis** | One main process. `BGSAVE` forks a child to write the snapshot | Copy-on-write gives the child a frozen snapshot for free |
| **nginx** | Master plus a few event-driven workers | Workers do the I/O; the master reloads config without dropping connections |
| **Celery prefork pool** | Main process forks worker children | Isolation from memory leaks, using `max_tasks_per_child` ([[09.9 - Celery in Production]]) |

💡 **The Redis `BGSAVE` trick is worth remembering.** `fork` gives the child a point-in-time view of the whole dataset without a lock and without copying. The parent keeps serving writes, and only the pages it changes get copied. During a save under heavy writes, memory can nearly double, which is why Redis docs tell you to leave headroom and to disable Transparent Huge Pages.
