# Databases: SQL, NoSQL, and How to Choose

> **Revision tags:** #building-blocks #databases

## The Core Mental Model

A database is an engine optimized for a specific access pattern. There is no universally best database — only the best database for a given workload.

The two fundamental questions:
1. **What does your data look like?** (structure, relationships, nesting)
2. **How do you query it?** (point lookup, range scan, full-text, joins, aggregations)

---

## Relational Databases (SQL)

### What They Are

Structured data organized into tables with rows and columns. Relationships expressed via foreign keys. Queried via SQL.

```sql
-- Normalized schema
CREATE TABLE users (id BIGINT PRIMARY KEY, name TEXT, email TEXT);
CREATE TABLE orders (id BIGINT PRIMARY KEY, user_id BIGINT REFERENCES users(id), total DECIMAL);

-- Query with join
SELECT u.name, COUNT(o.id) as order_count
FROM users u JOIN orders o ON u.id = o.user_id
GROUP BY u.name;
```

### Strengths

- **ACID transactions:** Multi-row, multi-table atomicity. Critical for financial systems.
- **Flexible querying:** JOIN any tables, GROUP BY, aggregate, filter — schema enforced.
- **Referential integrity:** Foreign keys prevent orphaned records.
- **Mature tooling:** Decades of optimization, monitoring, backup, replication tooling.
- **Schema enforcement:** Data quality guaranteed at the DB layer.

### Weaknesses

- **Vertical scaling is the primary lever:** Horizontal write scaling requires sharding, which is complex.
- **Schema migrations are painful at scale:** ALTER TABLE on 1B row tables requires careful strategy.
- **JOIN-heavy queries degrade under massive data:** Denormalization becomes necessary.
- **Not suited for highly variable schemas:** Adding columns is expensive.

### When to Use

- Transactional data (payments, orders, inventory, user accounts)
- Complex relational queries with multiple JOIN conditions
- Data integrity is non-negotiable
- Team is comfortable with SQL

### Major Systems

| DB | Best For |
|---|---|
| **PostgreSQL** | Feature-rich, JSONB support, extensions (PostGIS, TimescaleDB), open-source |
| **MySQL / MariaDB** | Widely deployed, fast reads, good for web applications |
| **CockroachDB** | Distributed SQL (PostgreSQL-compatible), global ACID |
| **Google Spanner** | Global, strongly consistent, horizontally scalable SQL |

## Connection Pooling

Database connections are expensive to establish (TLS handshake, auth, memory allocation). Opening a new connection per request is slow and exhausts DB resources.

**Connection pooling** maintains a pool of pre-established connections that are reused.

```
App Instances (100)  ────────→  PgBouncer (pool: 20 conns) ────→  PostgreSQL (max 100 conns)
(each want up to 10 conns)      (reuses 20 connections)
Without pooler: 100 × 10 = 1000 connections → DB crashes
With pooler: 20 connections → DB healthy
```

**PgBouncer** (PostgreSQL): Most widely used. Transaction-mode pooling means a DB connection is held only during a transaction.

**Connection pool sizing rule:** `connections ≈ (num_cores × 2) + effective_spindle_count`  
For most modern SSDs: a 4-core DB can handle ~10 effective connections well. More causes context switching overhead.

## NoSQL Databases

### Why NoSQL Exists

Relational databases were designed for a different era. As web scale emerged (billions of users, petabytes of data), three problems arose:
1. Horizontal scaling of writes is hard in relational DBs
2. Rigid schemas slow down fast-moving products
3. Some data shapes (documents, graphs, time-series) are unnatural in tables

NoSQL is not "no SQL" — it's "not only SQL." Each NoSQL type optimizes for a specific data model and access pattern.

---

## Key-Value Stores

**Model:** Each record is a key → value pair. Lookup by key only.

```
key: "user:42:session"   value: "{token: ..., expires: ...}"
key: "product:sku:X900"  value: "{price: 29.99, stock: 150}"
```

**Strengths:** O(1) lookup, extreme throughput, simple operational model.  
**Weaknesses:** No querying by value. No relationships. Schema-free (good and bad).

**Examples:** Redis (in-memory), DynamoDB (persistent), etcd (consistent, for config).

**Use when:** Session storage, cache backing store, feature flags, rate limit counters, shopping cart.

---

## Document Stores

**Model:** Each record is a self-describing document (JSON/BSON). Documents can nest arrays and sub-objects. Queryable by any field.

```json
{
  "_id": "prod_9821",
  "name": "Laptop",
  "specs": { "ram": "16GB", "cpu": "M3" },
  "tags": ["electronics", "computing"],
  "price": 1299.99,
  "inventory": [
    { "warehouse": "Mumbai", "stock": 50 },
    { "warehouse": "Delhi", "stock": 30 }
  ]
}
```

**Strengths:** Flexible schema, natural fit for hierarchical data, no joins needed for contained data.  
**Weaknesses:** No cross-document joins (expensive), consistency guarantees weaker than SQL, data duplication common.

**Examples:** MongoDB, CouchDB, Firestore, DynamoDB (as document store).

**Use when:** Product catalogs, content management, user profiles with variable attributes, any domain with heterogeneous records.

---

## Wide-Column Stores

**Model:** Table with rows, but columns are dynamic per row and organized into column families. Optimized for massive write throughput and horizontal scale.

```
Row key: "user:42"
  Column family "profile":   { name: "Vijay", email: "..." }
  Column family "activity":  { 2024-01-15: "login", 2024-01-16: "purchase" }
```

**Strengths:** Linear write scale (add nodes → proportionally more write throughput), tunable consistency, excellent for time-series and event data.  
**Weaknesses:** No ad-hoc queries. Query patterns must be designed into the schema upfront (partition key = your only efficient lookup).

**Examples:** Apache Cassandra, HBase, Google Bigtable.

**Use when:** IoT sensor data, event logs, user activity history, time-series metrics, any "write once, read by key" workload at massive scale.

**Cassandra data modeling rule:** Design your tables for your queries, not for normalization. One query pattern = one table.

---

## Search Engines

**Model:** Documents are indexed by content for full-text search. Inverted index maps words to documents. Results ranked by relevance.

**Strengths:** Full-text search, relevance ranking, faceted filtering, fuzzy matching.  
**Weaknesses:** Not a source of truth (sync lag from primary DB), eventual consistency, expensive indexing.

**Examples:** Elasticsearch, OpenSearch, Apache Solr, Typesense, Meilisearch.

**Use when:** Product search, log analysis, document search, anything requiring "search by keyword."

## Time-Series Databases

**Model:** Optimized for sequences of timestamped data points. Columnar storage, high compression for repetitive values.

```
timestamp            metric              value    tags
2024-01-15 10:00:00  cpu_usage_percent   72.3     host=web-01
2024-01-15 10:00:01  cpu_usage_percent   74.1     host=web-01
```

**Strengths:** Extreme compression, fast time-range queries, built-in downsampling and retention policies.

**Examples:** InfluxDB, TimescaleDB (PostgreSQL extension), Prometheus (short-term), ClickHouse (analytics).

**Use when:** Metrics, monitoring, IoT sensor data, financial tick data, any "value over time" workload.

---

## Graph Databases

**Model:** Data stored as nodes and edges (relationships). Optimized for traversing relationships.

```
(User:Alice)-[:FOLLOWS]->(User:Bob)-[:LIKES]->(Post:42)
```

**Strengths:** Graph traversals that would require many JOINs in SQL are native and fast.  
**Weaknesses:** Poor for non-graph workloads. Limited ecosystem.

**Examples:** Neo4j, Amazon Neptune, JanusGraph.

**Use when:** Social graphs, recommendation engines, fraud detection (detecting rings), knowledge graphs.

## The Database Selection Matrix

| Data Shape | Access Pattern | Use |
|---|---|---|
| Relational, transactional | Joins, ACID, complex queries | PostgreSQL |
| Key → value, low latency | Point lookup by key | Redis / DynamoDB |
| Hierarchical documents | Lookup + range by any field | MongoDB |
| High write throughput, wide rows | Write-heavy, key-based reads | Cassandra |
| Full-text search, ranking | Keyword search, facets | Elasticsearch |
| Time-stamped metrics | Range by time, aggregation | TimescaleDB / InfluxDB |
| Graph traversal | Relationship hops, paths | Neo4j |
| Large files / blobs | Store and retrieve by key | S3 |
| Analytics / OLAP | Aggregation over billions of rows | ClickHouse / BigQuery |

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Single DB node crash | All writes unavailable | Read replicas + failover, multi-AZ |
| Slow queries under load | Latency spike for all users | Query optimization, read replicas, caching |
| Disk full | DB stops accepting writes | Alerting at 70%, storage autoscaling |
| Bad schema migration | Table locked, service down | Online schema change tools (pt-online-schema-change, gh-ost) |
| Connection pool exhaustion | New requests can't connect | PgBouncer, right-size pool |
