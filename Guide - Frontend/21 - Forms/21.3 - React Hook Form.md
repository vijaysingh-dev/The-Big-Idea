# React Hook Form

React Hook Form (RHF) keeps form values in **refs** rather than state, so typing does not re-render the form. Only components that explicitly subscribe to a field re-render when it changes.

## The basic shape

```jsx
import { useForm } from "react-hook-form";

function SignupForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm({
    defaultValues: { email: "", password: "" },
  });

  const onSubmit = async (data) => {
    await api.signup(data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <input {...register("email", { required: "Email is required" })} />
      {errors.email && <p role="alert">{errors.email.message}</p>}

      <button disabled={isSubmitting}>Sign up</button>
    </form>
  );
}
```

`register` returns `{ name, onChange, onBlur, ref }` and spreads them onto the input. The input stays uncontrolled — RHF reads its value through the ref when needed ([[16.8 - Controlled vs Uncontrolled Components]]).

`handleSubmit` validates first and only calls your function with the validated values.

Always pass `defaultValues`. Without it, fields start as `undefined` and the reset behavior is inconsistent.

## Why it is fast

```
Controlled form:  keystroke → setState → re-render entire form
RHF:              keystroke → ref update → no render
```

A fifty-field form re-renders zero times while typing. Errors and derived state re-render only the components that subscribe to them.

That subscription model is the point: `formState: { errors }` subscribes to errors; a component that never reads `formState` never re-renders.

## Schema resolvers

```jsx
import { zodResolver } from "@hookform/resolvers/zod";

const { register, handleSubmit } = useForm({
  resolver: zodResolver(signupSchema),
  defaultValues: { email: "", password: "" },
});
```

One schema drives validation, error messages and — with `z.infer` — the TypeScript types ([[21.2 - Validation Strategies]]). Resolvers exist for Zod, Valibot, Yup, Joi and others.

This is the recommended setup: inline `register` rules are fine for a single field, but a schema keeps rules in one place and shareable with the server.

## Controlled components

Custom components and UI libraries usually need controlled values. `Controller` bridges them:

```jsx
import { Controller } from "react-hook-form";

<Controller
  name="country"
  control={control}
  rules={{ required: "Select a country" }}
  render={({ field, fieldState }) => (
    <Select
      {...field}                       // value, onChange, onBlur, ref, name
      error={fieldState.error?.message}
    />
  )}
/>
```

Only this field re-renders on change, not the form. Use `Controller` for date pickers, rich selects, editors, and any component that does not forward a ref to a native input.

`useController` is the hook form of the same thing, useful when building a reusable field component.

## Watching values

```jsx
const plan = watch("plan");                    // re-renders this component on change
const values = watch();                        // re-renders on ANY change — avoid
const email = useWatch({ control, name: "email" });   // isolated subscription
```

`watch` at the top of a form re-subscribes the whole form and undoes the performance benefit. `useWatch` inside a small child component isolates the re-render to that component:

```jsx
function PlanFields({ control }) {
  const plan = useWatch({ control, name: "plan" });
  return plan === "custom" ? <CustomOptions /> : null;
}
```

For reading a value without subscribing at all — inside a handler, for instance:

```jsx
const values = getValues();   // no subscription, no re-render
```

## formState

```jsx
const {
  errors,
  isDirty,          // any field changed from defaults
  dirtyFields,      // which ones
  touchedFields,    // which have been blurred
  isValid,          // requires mode: "onChange" or "onBlur"
  isSubmitting,
  isSubmitSuccessful,
  submitCount,
} = formState;
```

`formState` is a Proxy — subscribing happens on **read**. Destructuring a property subscribes to it; not reading it means no re-render for it. This is why destructuring only what you need matters:

```jsx
const { errors } = formState;              // subscribes to errors only
const { isDirty, errors } = formState;     // subscribes to both
```

`isDirty` is the correct guard for "unsaved changes" prompts. `isValid` requires a validation mode other than the default `onSubmit`.

## Validation modes

```jsx
useForm({
  mode: "onTouched",           // validate on first blur
  reValidateMode: "onChange",  // then on every change
});
```

`onTouched` plus `onChange` re-validation is the timing users prefer — not told they are wrong while typing the first character, but immediate confirmation once they fix it ([[21.2 - Validation Strategies]]).

## Server errors

```jsx
const onSubmit = async (data) => {
  try {
    await api.signup(data);
  } catch (err) {
    if (err.fieldErrors) {
      Object.entries(err.fieldErrors).forEach(([field, message]) =>
        setError(field, { type: "server", message })
      );
    } else {
      setError("root.serverError", { message: "Something went wrong" });
    }
  }
};

{errors.root?.serverError && <p role="alert">{errors.root.serverError.message}</p>}
```

`root` is a reserved namespace for form-level errors that do not belong to a field.

Note that server errors set this way are cleared on the next validation pass, which is usually what you want.

## Reset

```jsx
reset();                                 // back to defaultValues
reset(newValues);                        // new defaults
reset(values, { keepDirty: true });      // selective

useEffect(() => {
  if (user) reset(user);                 // populate from async data
}, [user, reset]);
```

The async-population case is the one exception where an effect is appropriate — the alternative is remounting with `key`, which also works and is often cleaner ([[16.6 - Lists and Keys]]).

`reset` after a successful submit clears `isDirty` and prevents the "unsaved changes" prompt from firing incorrectly.

## Building reusable fields

```jsx
function TextField({ name, label, ...rest }) {
  const { register, formState: { errors } } = useFormContext();
  const error = errors[name];

  return (
    <div>
      <label htmlFor={name}>{label}</label>
      <input
        id={name}
        {...register(name)}
        {...rest}
        aria-invalid={Boolean(error)}
        aria-describedby={error ? `${name}-error` : undefined}
      />
      {error && <p id={`${name}-error`} role="alert">{error.message}</p>}
    </div>
  );
}

<FormProvider {...methods}>
  <form onSubmit={methods.handleSubmit(onSubmit)}>
    <TextField name="email" label="Email" />
  </form>
</FormProvider>
```

`FormProvider` and `useFormContext` avoid drilling `register` and `control` through every layer. This is how most design systems wrap RHF.

Note the accessibility attributes belong in the shared field component so they cannot be forgotten per form.

## When not to use it

**Very small forms.** A login form with two fields does not need a dependency — `FormData` on submit is less code ([[09.2 - Forms and Native Input Behavior]]).

**When React 19 form actions fit.** `useActionState` with a server action handles pending state and progressive enhancement natively, and covers a growing share of simple form cases.

**When every field is controlled anyway.** If a design system exposes only controlled components, `Controller` wraps every field and much of the performance benefit is lost — though the validation, error handling and state tracking are still worth it.

## How senior engineers actually use this

**They use RHF with a Zod resolver** as the default for anything past a few fields.

**They use `useWatch` in small child components**, never `watch()` at the form root.

**They build a shared field component** with `useFormContext` so accessibility attributes and error rendering are consistent.

**They destructure only the `formState` keys they need**, since reading is subscribing.

**They wire server field errors back with `setError`** rather than rendering them separately.

## Common pitfalls

- Omitting `defaultValues`, causing uncontrolled-to-controlled warnings and broken resets.
- `watch()` at the form root, re-rendering everything on every keystroke.
- Reading unnecessary `formState` properties and subscribing to them.
- Using `register` on a component that does not forward a ref — needs `Controller`.
- Forgetting `reset` after a successful submit, leaving `isDirty` true.
- Setting server errors without a `root` namespace for form-level failures.
- Reaching for RHF on a two-field form.

## Interview angle

"How does React Hook Form achieve better performance" is the question. The answer: values live in refs rather than state, so typing does not trigger re-renders, and components subscribe to specific fields via `useWatch` or to specific `formState` keys via a Proxy that tracks reads. Then note the tradeoff — `Controller` is needed for controlled components, which partially reintroduces re-renders — and that a schema resolver keeps validation rules and types in one place.
