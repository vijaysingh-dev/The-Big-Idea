# Authentication, Authorization, and Session Management

> **Revision tags:** #building-blocks #security #auth  
> **Related:** [[03.2 - Reverse Proxies and API Gateways]] | [[02.6 - Observability Security Cost]]

---

## The Distinction

**Authentication (AuthN):** Verifying *who* you are. "Is this really user 42?"  
**Authorization (AuthZ):** Verifying *what* you can do. "Can user 42 delete this order?"  
**Session management:** Maintaining authenticated state across requests.

These are separate concerns. Build them separately. Conflating them leads to tangled, unmaintainable security code.

---

## Authentication

### Password Authentication

The baseline. Store passwords as hashes, never plaintext.

```python
# Storing
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
db.save(user_id, hashed)

# Verifying
bcrypt.checkpw(submitted_password.encode(), stored_hash)
```

**Use bcrypt, scrypt, or Argon2** — they are slow by design (tunable cost factor), making brute force expensive. Never use MD5, SHA1, or SHA256 for passwords — they're fast, making them easy to brute force.

**Additional hardening:**
- Rate limit login attempts (10/min per IP + per username)
- Lock account after N failures (with alert to user)
- Require email verification on registration
- Check against known breached password lists (HaveIBeenPwned API)

### Multi-Factor Authentication (MFA)

A second factor beyond password:
- **TOTP** (Time-based One-Time Password): Google Authenticator, Authy — generates 6-digit code every 30s using a shared secret
- **SMS OTP:** Code sent via SMS — convenient but phishable/SIM-swappable
- **Hardware keys:** FIDO2/WebAuthn — most secure, phishing-resistant

## Session Management

After authentication, the server must recognize subsequent requests from the same user without re-authenticating every time.

### Server-Side Sessions (Stateful)

```
1. User logs in
2. Server creates session: { session_id: "abc123", user_id: 42, roles: ["user"], created: ... }
3. Server stores in Redis: SET session:abc123 {...} EX 3600
4. Server returns session_id as cookie: Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict
5. Subsequent requests: browser sends cookie → server looks up session in Redis → gets user context
```

**Pros:** Server controls session state completely. Instant revocation (delete from Redis).  
**Cons:** Every request requires a Redis lookup. Horizontal scaling requires shared session store (Redis).

**Cookie security flags:**
- `HttpOnly`: JavaScript cannot read the cookie (prevents XSS theft)
- `Secure`: Only sent over HTTPS
- `SameSite=Strict`: Not sent with cross-origin requests (prevents CSRF)

### JWT (Stateless)

```
1. User logs in
2. Server creates JWT: header.payload.signature
   Payload: { user_id: 42, roles: ["user"], exp: 1705003600 }
   Signed with server's secret key (HMAC-SHA256 or RSA)
3. Client stores JWT (localStorage or httpOnly cookie)
4. Subsequent requests: client sends JWT in Authorization header
5. Server: verify signature → decode payload → get user context (no DB lookup)
```

**JWT Structure:**
```
eyJhbGciOiJIUzI1NiJ9.          ← header (base64: {"alg":"HS256"})
eyJ1c2VyX2lkIjo0Mn0.           ← payload (base64: {"user_id":42,"exp":...})
SflKxwRJSMeKKF2QT4fwpMeJf36P   ← signature
```

**Pros:** Stateless — no session store needed. Scales trivially.  
**Cons:** Cannot be revoked before expiry without a blocklist (which reintroduces state). Keep access token TTL short (15 min).

**Access + Refresh token pattern:**
```
Access token:  short-lived (15 min), sent with every request
Refresh token: long-lived (7–30 days), stored securely, used only to get new access tokens

Flow:
  Access token expires → client sends refresh token → server issues new access token
  If refresh token compromised: revoke it (small set to track vs all access tokens)
```

This gives the usability of long sessions with the security of short-lived tokens.

## OAuth 2.0 and OpenID Connect

### OAuth 2.0

An authorization framework that lets a user grant a third-party application limited access to their account on another service — without sharing their password.

```
User wants to let App X post to their Twitter:
1. App X redirects user to Twitter's authorization page
2. User logs in to Twitter, approves "post tweets" permission
3. Twitter redirects back to App X with an authorization code
4. App X exchanges code for access token (server-to-server)
5. App X uses access token to post tweets on user's behalf
```

**Key roles:**
- **Resource Owner:** The user
- **Client:** The application (App X) wanting access
- **Authorization Server:** Issues tokens (Twitter in this example)
- **Resource Server:** The API being accessed (Twitter API)

**Grant types:**
- **Authorization Code + PKCE:** For web and mobile apps. Most secure. Use this.
- **Client Credentials:** For service-to-service (no user involved). Use for internal API calls.
- **Implicit:** Deprecated. Never use for new systems.

### OpenID Connect (OIDC)

OAuth 2.0 handles authorization. OIDC adds authentication on top — it defines how to use OAuth 2.0 to verify the user's identity.

OIDC adds an `id_token` (a JWT with user identity claims) to the OAuth 2.0 flow.

```
Auth response contains:
  access_token  → for calling the resource API
  id_token      → JWT with user's identity (sub, email, name, ...)
  refresh_token → for getting new tokens
```

**Use OIDC when:** You want SSO (sign in with Google/GitHub/Okta). Your service trusts the identity provider's authentication.

## Authorization

### RBAC (Role-Based Access Control)

Users are assigned roles. Roles have permissions.

```
Roles: viewer, editor, admin
Permissions:
  viewer:  read:posts
  editor:  read:posts, write:posts
  admin:   read:posts, write:posts, delete:posts, manage:users

User "alice" has role "editor"
→ alice can read and write posts, cannot delete or manage users
```

**Implementation:**
```python
def check_permission(user_id, required_permission):
    user_roles = db.get_roles(user_id)
    user_permissions = set()
    for role in user_roles:
        user_permissions.update(ROLE_PERMISSIONS[role])
    return required_permission in user_permissions
```

Simple, auditable, widely understood. Good for most applications.

### ABAC (Attribute-Based Access Control)

Decisions based on attributes of the user, resource, and environment.

```
Policy: "user can edit document if user.department == document.department AND time is business_hours"
```

More expressive than RBAC but harder to audit and reason about. Use when RBAC is too coarse.

### Resource-Level Authorization

Check ownership or relationship before allowing access.

```python
# Can user 42 access order 8827?
order = db.get_order(8827)
if order.user_id != requesting_user_id and not requesting_user.is_admin():
    raise Forbidden()
```

Always enforce in the service, not just the API gateway. Defense in depth.

## Where to Enforce Auth

```
API Gateway:    authenticate all requests (validate JWT or session)
                coarse-grained authorization (is this user allowed to access this service?)

Service layer:  fine-grained authorization (can this user access this specific resource?)
                business rule enforcement ("only the order owner can cancel")
```

Never rely solely on the gateway for authorization. Services must also check.

## Common Vulnerabilities

| Vulnerability | Prevention |
|---|---|
| Storing passwords in plaintext | bcrypt/Argon2 hashing |
| JWT with `alg: none` | Always validate algorithm; reject `none` |
| JWT stored in localStorage | XSS can steal it; use httpOnly cookie instead |
| Missing rate limit on login | Brute force → add rate limiting + lockout |
| CSRF attacks | SameSite cookie attribute, CSRF tokens |
| Privilege escalation | Check permissions server-side, never trust client |
| Insecure direct object reference | Always check resource ownership |
