# Middleware and Thunks

Reducers must be pure ([[20.3 - Redux Core Concepts]]), so side effects need somewhere else to live. **Middleware** is that place — a pipeline every action passes through on its way to the reducer.

## The middleware signature

```js
const logger = (store) => (next) => (action) => {
  console.group(action.type);
  console.log("prev", store.getState());
  const result = next(action);
  console.log("next", store.getState());
  console.groupEnd();
  return result;
};
```

Triple-curried: store, then the next middleware in the chain, then the action ([[02.9 - Currying and Partial Application]]).

The chain composes:

```
dispatch(action)
  → middleware A → middleware B → middleware C → reducer
```

Each middleware can inspect the action, modify it, delay it, swallow it, or dispatch others. Calling `next(action)` passes it along; not calling it stops the action there.

Note `store.dispatch` inside a middleware restarts the chain from the top, while `next` continues from the current position — a distinction that matters when writing middleware that dispatches.

## Thunks

A thunk is a function dispatched instead of an object. The thunk middleware intercepts it and calls it with `dispatch` and `getState`:

```js
const thunkMiddleware = ({ dispatch, getState }) => (next) => (action) =>
  typeof action === "function" ? action(dispatch, getState) : next(action);
```

That is the entire implementation. Everything thunks do follows from those four lines.

```js
function fetchTodos(userId) {
  return async (dispatch, getState) => {
    if (getState().todos.status === "loading") return;   // read state before acting

    dispatch({ type: "todos/loading" });
    try {
      const res = await fetch(`/api/todos?user=${userId}`);
      dispatch({ type: "todos/received", payload: await res.json() });
    } catch (err) {
      dispatch({ type: "todos/failed", payload: err.message });
    }
  };
}

dispatch(fetchTodos(1));
```

Thunks are included by default in `configureStore`, so no setup is needed.

## What thunks are good at

**Conditional dispatch** — checking state before doing work, as above.

**Sequencing** — dispatching several actions around an async operation.

**Reusable logic** — the same operation dispatched from several components.

**Access to the whole state** — a component only knows its slice; a thunk sees everything.

What they are **not** good for: complex orchestration, cancellation, debouncing, or reacting to actions rather than being dispatched. A thunk runs when you call it and has no built-in way to be cancelled or to respond to something else happening.

## createAsyncThunk

RTK's wrapper generates the three lifecycle actions automatically ([[20.4 - Redux Toolkit]]):

```js
export const fetchTodos = createAsyncThunk(
  "todos/fetch",
  async (userId, { getState, dispatch, rejectWithValue, signal }) => {
    const res = await fetch(`/api/todos?user=${userId}`, { signal });
    if (!res.ok) return rejectWithValue(await res.text());
    return res.json();
  },
  {
    condition: (userId, { getState }) =>
      getState().todos.status !== "loading",   // skip if already in flight
  }
);
```

Two features worth knowing: the `condition` option prevents duplicate requests declaratively, and `signal` supports abort — dispatching the same thunk again aborts the previous one if you wire it up ([[04.6 - AbortController and Cancellation]]).

## Listener middleware

The modern answer for **reactive** side effects — logic that responds to actions rather than being dispatched directly:

```js
import { createListenerMiddleware } from "@reduxjs/toolkit";

const listener = createListenerMiddleware();

listener.startListening({
  actionCreator: searchQueryChanged,
  effect: async (action, api) => {
    api.cancelActiveListeners();        // cancel the previous run — debounce
    await api.delay(300);
    const results = await search(action.payload);
    api.dispatch(searchResultsReceived(results));
  },
});

listener.startListening({
  predicate: (action, currentState, previousState) =>
    currentState.cart.items.length !== previousState.cart.items.length,
  effect: (action, api) => {
    localStorage.setItem("cart", JSON.stringify(api.getState().cart));
  },
});
```

Capabilities thunks lack: cancellation, debouncing, `takeLatest`-style behavior, state-diff predicates, and `api.condition()` for waiting on a future action.

This covers most of what people historically used sagas for, and it is now the recommended approach for reactive logic in Redux.

## Sagas and observables

**redux-saga** uses generators to express side effects as yielded descriptions ([[06.6 - Iterators and Generators]]):

```js
function* searchSaga() {
  yield takeLatest("search/queryChanged", function* (action) {
    yield delay(300);
    const results = yield call(api.search, action.payload);
    yield put(searchResultsReceived(results));
  });
}
```

Because the generator yields *descriptions* rather than performing effects, sagas are synchronously testable without mocking. `takeLatest`, `race`, `fork` and `cancel` give a genuine concurrency vocabulary.

The costs are real: a generator-based mental model, substantial API surface, and bundle weight. For most applications the listener middleware now covers the same ground with far less to learn. Sagas remain justified for genuinely complex orchestration — long-running background processes, multi-step wizards with cancellation, WebSocket lifecycle management.

**redux-observable** does the same with RxJS. Powerful if the team already knows RxJS; a large learning investment otherwise.

## Common middleware

```js
// Analytics on specific actions
const analytics = () => (next) => (action) => {
  if (action.meta?.track) sendEvent(action.type, action.payload);
  return next(action);
};

// Crash reporting with context
const crashReporter = (store) => (next) => (action) => {
  try {
    return next(action);
  } catch (err) {
    report(err, { action, state: store.getState() });
    throw err;
  }
};
```

Middleware is the right place for cross-cutting concerns because every state change passes through it. Adding analytics as middleware means it cannot be forgotten at a call site.

## Ordering

```js
middleware: (getDefault) => getDefault().concat(listener.middleware, analytics)
```

Order matters. Logging middleware placed before the thunk middleware sees function actions rather than the resolved ones; placed after, it sees the plain objects. `getDefault()` returns thunk plus the development checks, and `.concat` appends after them.

The listener middleware should generally be **prepended** so it sees actions before other middleware can transform them:

```js
middleware: (getDefault) => getDefault().prepend(listener.middleware)
```

## Choosing

```
Simple async request              → createAsyncThunk, or RTK Query
Conditional / sequenced logic     → thunk
Reacting to actions, debouncing   → listener middleware
Complex orchestration, cancellation → listener middleware, then saga
Cross-cutting concerns            → custom middleware
Server data                        → RTK Query, and none of the above
```

The last line matters most: most thunks in most codebases are data fetching, and a query library removes all of them ([[24.6 - TanStack Query Fundamentals]]).

## How senior engineers actually use this

**They use RTK Query for server data** and reserve thunks for genuine client-side async logic.

**They use the listener middleware instead of sagas** for new work unless there is orchestration that genuinely needs saga's vocabulary.

**They put cross-cutting concerns in middleware** — analytics, persistence, crash context — so they cannot be forgotten.

**They keep thunks thin.** Business logic belongs in reducers and plain functions; a thunk coordinates, it does not compute.

**They use `condition` on async thunks** to prevent duplicate in-flight requests declaratively.

## Common pitfalls

- Thunks that grow into business logic, bypassing the reducer.
- No cancellation, so a stale response overwrites a newer one.
- Duplicate requests from repeated dispatches with no `condition` guard.
- Middleware that forgets to call `next(action)`, silently swallowing actions.
- Adopting sagas for what the listener middleware handles.
- Hand-written fetch thunks alongside a query library.

## Interview angle

"What is middleware" and "what is a thunk" are standard. Give the triple-curried signature and explain that middleware sits between dispatch and the reducer, so it is where side effects and cross-cutting concerns live. For thunks, the four-line implementation is the most convincing answer — it makes clear that a thunk is just a function the middleware calls with `dispatch` and `getState`. Then position the options honestly: RTK Query for data, listener middleware for reactive logic, sagas only for genuine orchestration complexity.
