# Why Async and the Async Landscape

## The four reasons to go async

**1. Callouts after DML.** A callout cannot be made once DML has occurred in the transaction. This is the most common driver, and it is not negotiable.

**2. Limits.** Async transactions get higher limits — 200 SOQL queries instead of 100, 12 MB heap instead of 6, 60 seconds CPU instead of 10. More importantly, each async execution is a **new transaction with a fresh budget**.

**3. Volume.** Batch Apex processes up to 50 million records in chunks, each chunk with its own limits. Nothing synchronous comes close.

**4. User experience.** Work the user does not need to wait for — a notification, an integration push, a recalculation — should not sit inside their save.

## The options

| Tool | Trigger | Records | Callouts | State | Typical use |
| --- | --- | --- | --- | --- | --- |
| `@future` | Method call | Small | Yes, with flag | None | Legacy; avoid in new code |
| Queueable | `System.enqueueJob` | Small to medium | Yes, with interface | Constructor args | The general-purpose default |
| Batch Apex | `Database.executeBatch` | Up to 50 million | Yes, with interface | `Database.Stateful` | Large volume |
| Scheduled Apex | The scheduler | Any | Via a job it starts | None | Time-based |
| Platform Events | `EventBus.publish` | Event payloads | Yes, in the subscriber | Event fields | Decoupled reactions |
| Change Data Capture | Record changes | Automatic | Yes, in the subscriber | Event fields | Replication, audit |
| Continuations | A Visualforce or LWC request | One request | Yes, that is the point | Request state | Long callouts in a UI |
| Async paths in flow | A record save | Per record | Yes | Flow variables | Declarative equivalent |

## The decision, in order

**Does it need to happen for the user right now?** If yes, it is synchronous and the question does not arise.

**Is it a callout after DML?** Queueable, or a platform event with a subscriber that calls out.

**Is it more than a few thousand records?** Batch Apex.

**Does it run on a clock?** Scheduled Apex, or a scheduled flow.

**Should other systems or components react without the caller knowing?** Platform events.

**Is it a long-running callout during a user interaction?** Continuations.

**Otherwise?** Queueable. It is the general-purpose tool and the right default when nothing more specific applies.

## What changes when you go async

Six behaviours differ, and each one produces a class of bug when overlooked.

**A new transaction.** Static variables reset. A recursion guard set synchronously is gone. State must be passed explicitly. See [[09.8 - Static Members and Class Level State]].

**Different limits.** Higher, and separately counted.

**Different running user in some contexts.** Platform event subscribers run as the Automated Process user by default, which affects sharing, field access, and `UserInfo`.

**No user to report failure to.** An async failure has no screen to show an error on. Logging and monitoring are not optional.

**Delay is not guaranteed to be short.** Async jobs queue. Under load, a Queueable may run seconds or minutes later. Anything with a real deadline needs that acknowledged in the design.

**At-least-once delivery for events.** A platform event subscriber can run twice for the same event. Handlers must be idempotent. See [[12.8 - Platform Events]].

## The enqueue limits

The ones that catch people:

- **50 async calls per synchronous transaction** — combined across `@future`, `System.enqueueJob`, and `Database.executeBatch`
- **1 Queueable enqueued from within a Queueable** (higher in some contexts)
- **5 batch jobs queued or active** at once, org-wide
- **100 scheduled jobs** at once
- **250,000 async executions per day**, or 200 times the user licence count, whichever is higher

The daily limit is org-wide and shared across every async mechanism. An integration enqueuing per record burns through it, which is the practical reason for the rule below.

```java
// Wrong: one job per record, 200 of the 50 available
for (Warranty_Claim__c claim : claims) {
    System.enqueueJob(new ErpNotificationQueueable(new Set<Id>{ claim.Id }));
}

// Correct: one job for the whole batch
System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

## Enqueuing from a trigger

The standard pattern, and the details that make it correct:

```java
public with sharing class ClaimService {

    public static void queueErpNotification(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) {
        Set<Id> toNotify = new Set<Id>();

        for (Warranty_Claim__c claim : newClaims) {
            Warranty_Claim__c prior = oldClaims == null ? null : oldClaims.get(claim.Id);
            if (claim.Status__c == 'Approved'
                && (prior == null || prior.Status__c != 'Approved')) {
                toNotify.add(claim.Id);
            }
        }

        if (toNotify.isEmpty()) {
            return;
        }

        // passing ids, not records: the job queries fresh data in its own transaction
        System.enqueueJob(new ErpNotificationQueueable(toNotify));
    }
}
```

**Pass Ids, not records.** By the time the job runs, the records may have changed. Querying fresh in the async transaction is correct, and it also keeps the serialized job payload small.

**Enqueue once, not per record.**

**Enqueue only when there is work**, so the guard clause matters.

**The job does not start if the transaction rolls back.** Enqueuing is part of the transaction, which is the correct behaviour — nothing happened, so nothing should be notified.

## Chaining

A Queueable can enqueue another, which is how work that exceeds one transaction's limits gets processed.

```java
public with sharing class ClaimEnrichmentQueueable implements Queueable {

    private final List<Id> remaining;
    private static final Integer CHUNK_SIZE = 200;

    public ClaimEnrichmentQueueable(List<Id> remaining) {
        this.remaining = remaining;
    }

    public void execute(QueueableContext context) {
        Integer take = Math.min(CHUNK_SIZE, remaining.size());
        List<Id> batch = new List<Id>();
        for (Integer i = 0; i < take; i++) {
            batch.add(remaining[i]);
        }

        ClaimEnrichmentService.enrich(new Set<Id>(batch));

        List<Id> rest = new List<Id>();
        for (Integer i = take; i < remaining.size(); i++) {
            rest.add(remaining[i]);
        }

        // chaining continues the work with a fresh limit budget; the test guard prevents
        // an infinite chain in test context, where only one level is allowed
        if (!rest.isEmpty() && !Test.isRunningTest()) {
            System.enqueueJob(new ClaimEnrichmentQueueable(rest));
        }
    }
}
```

Chaining is powerful and needs a termination condition. A chain with no exit runs until the daily async limit is exhausted, which affects the whole org rather than just that job.

For genuinely large volumes, Batch Apex is the better tool — it chunks automatically and has proper monitoring. See [[12.4 - Batch Apex]].

## Monitoring

Async failures are silent unless you look. Three things worth having from day one.

**The Apex Jobs page** in Setup, and its queryable form:

```sql
SELECT Id, ApexClass.Name, Status, JobType, NumberOfErrors,
       JobItemsProcessed, TotalJobItems, CreatedDate, CompletedDate, ExtendedStatus
FROM AsyncApexJob
WHERE CreatedDate = LAST_N_DAYS:7 AND Status IN ('Failed', 'Aborted')
ORDER BY CreatedDate DESC
```

`ExtendedStatus` carries the failure message, which is the first thing to read when a job fails.

**A custom log object**, written by the job's error handling, so failures are reportable and can be put on a dashboard.

**Alerting.** A daily query for failed jobs, sent to a monitored address. A batch job that has been failing for three weeks is not unusual in orgs without this.

See [[20.5 - Custom Logging Frameworks]].

## Testing async

`Test.stopTest()` forces queued async work to run synchronously before the assertions.

```java
@IsTest
static void approvalEnqueuesErpNotification() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock());
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    claim.Status__c = 'Approved';
    update claim;
    Test.stopTest();   // the queued job runs here

    Warranty_Claim__c refreshed = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c, 'Job should have run and updated status');
}
```

Assertions belong **after** `Test.stopTest()`, not before. This is the single most common async testing mistake — asserting inside the block, before the job has run.

Only **one level** of chaining executes in test context, which is why the `Test.isRunningTest()` guard appears in chained jobs. See [[19.6 - Testing Async Apex]].
