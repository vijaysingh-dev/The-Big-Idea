# WebSockets and Server Sent Events

HTTP is request-response: the client asks, the server answers. Real-time features need the server to push. There are four ways to arrange that, and choosing correctly matters more than implementing any of them well.

## The four options

| Approach | Direction | Transport | Best for |
| --- | --- | --- | --- |
| Polling | client pulls | HTTP | infrequent updates, simple infrastructure |
| Long polling | server pushes on a held request | HTTP | fallback where WebSockets are blocked |
| Server-Sent Events | server → client | HTTP | feeds, notifications, streaming text |
| WebSocket | bidirectional | TCP upgrade | chat, collaboration, games, trading |

**The default should be polling.** A dashboard refreshing every 30 seconds does not need a persistent connection, and polling costs nothing operationally. Reach for the others when latency requirements or update frequency genuinely justify the infrastructure.

## Server-Sent Events

```js
const source = new EventSource("/api/notifications");

source.onmessage = (e) => {
  const data = JSON.parse(e.data);
  render(data);
};

source.addEventListener("price-update", (e) => { /* named event */ });

source.onerror = () => {
  // EventSource reconnects automatically — do not create a new one here
};

source.close();
```

The wire format is plain text over a normal HTTP response:

```
event: price-update
id: 42
retry: 3000
data: {"symbol":"INFY","price":1540}

```

What SSE gives you that WebSockets do not:

- **Automatic reconnection** with an exponential-ish backoff, controlled by the `retry` field.
- **Resumption** via `Last-Event-ID` — on reconnect the browser sends the last received id, so the server can replay missed events. This is genuinely hard to implement correctly over WebSockets.
- **Works over plain HTTP**, so proxies, CDNs and corporate firewalls handle it without special configuration.
- **Compression and HTTP/2 multiplexing** apply normally.

Limitations: text only, one direction, and over HTTP/1.1 the six-connections-per-origin limit applies — several tabs each holding an SSE connection can exhaust it. HTTP/2 removes that constraint.

SSE is the right choice more often than it is used. Notification feeds, live dashboards, build logs, progress updates and streaming LLM responses are all one-directional.

## WebSockets

```js
const ws = new WebSocket("wss://example.com/socket");

ws.onopen = () => ws.send(JSON.stringify({ type: "subscribe", room: "general" }));
ws.onmessage = (e) => handle(JSON.parse(e.data));
ws.onclose = (e) => { e.code; e.reason; e.wasClean; };
ws.onerror = () => { /* always followed by close */ };

ws.readyState;   // CONNECTING 0, OPEN 1, CLOSING 2, CLOSED 3
ws.close(1000, "done");
```

A WebSocket starts as an HTTP request with `Upgrade: websocket`, then the connection becomes a persistent full-duplex channel with minimal framing overhead — a few bytes per message versus hundreds for HTTP headers.

Always use `wss://`. Plain `ws://` is blocked from HTTPS pages and is trivially interceptable.

**The browser API gives you almost nothing.** No reconnection, no heartbeat, no message acknowledgment, no queueing while disconnected. Everything below is your responsibility.

## What production WebSocket code needs

**Reconnection with backoff and jitter:**

```js
function connect(url, { onMessage }) {
  let ws, attempt = 0, closed = false;

  const open = () => {
    ws = new WebSocket(url);

    ws.onopen = () => { attempt = 0; flushQueue(); };
    ws.onmessage = (e) => onMessage(JSON.parse(e.data));

    ws.onclose = () => {
      if (closed) return;
      const delay = Math.min(30000, 500 * 2 ** attempt++);
      setTimeout(open, delay + Math.random() * delay * 0.3);
    };
  };

  open();
  return { send, close: () => { closed = true; ws.close(); } };
}
```

The jitter matters for the same reason it does in HTTP retries ([[04.7 - Async Concurrency Patterns]]) — without it, every client reconnects simultaneously after a server restart and immediately knocks it over again.

**Heartbeats.** A dropped connection often does not fire `onclose` — a laptop closing its lid or a mobile network handoff leaves a half-open socket that looks connected. Send a ping periodically and treat a missing pong as a disconnect.

**An outbound queue.** Messages sent while `readyState !== OPEN` throw. Queue them and flush on reconnect.

**Message correlation.** For request-response over a socket, include an id and resolve a promise on the matching reply — the same pattern as worker RPC ([[08.4 - Web Workers]]).

**Auth.** The browser WebSocket API cannot set headers, so `Authorization: Bearer` is unavailable. Options: a short-lived ticket in the query string obtained from a normal HTTP call, cookie-based auth (works, since cookies are sent on the handshake — but check `Origin` server-side to prevent cross-site hijacking), or authenticating as the first message after connect.

Never put a long-lived token in the URL; query strings end up in logs and referrers.

Given all of this, using a library — Socket.IO, or a small wrapper — is usually correct. Socket.IO adds reconnection, heartbeats, rooms, acknowledgments and a long-polling fallback, at the cost of a non-standard protocol requiring its own server.

## In React

```jsx
useEffect(() => {
  const socket = connect(url, { onMessage: setMessages });
  return () => socket.close();
}, [url]);
```

Two recurring problems:

**Strict Mode double-mounting** in development connects, disconnects and reconnects. That is the point — it surfaces missing cleanup. Do not work around it with a ref guard; fix the cleanup ([[18.7 - Strict Mode and Double Invocation]]).

**A message per second re-rendering the whole tree.** Batch incoming messages into a buffer flushed on an interval or in a transition, rather than calling `setState` per message.

`useSyncExternalStore` is the correct hook for subscribing to an external mutable source like a socket, since it handles tearing during concurrent rendering ([[17.12 - Lesser Known Hooks]]).

## Scaling considerations

Persistent connections change server architecture. Each connection holds memory and file descriptors, so a stateless HTTP server autoscaling by CPU no longer fits.

- **Sticky sessions or a shared pub/sub layer** (Redis, NATS) are needed, because a message published on one server must reach clients connected to another.
- **Deploys drop every connection**, so reconnection is not an edge case — it happens on every release.
- **Load balancers need idle-timeout configuration**; the default is often 60 seconds, which kills idle sockets.

Managed services — Ably, Pusher, Supabase Realtime, or a cloud provider's WebSocket gateway — exist because this is genuinely operationally heavy. For most product teams, buying it is the right call.

## Choosing, concretely

```
Do I need client -> server messages at low latency?   -> WebSocket
Server -> client only?                                -> SSE
Updates less often than every ~10 seconds?            -> polling
Streaming a response to one request?                  -> fetch + ReadableStream
```

That last one is worth noting: streaming a single HTTP response with `fetch` and reading `response.body` covers LLM token streaming and progressive results without any persistent-connection infrastructure.

```js
for await (const chunk of response.body.pipeThrough(new TextDecoderStream())) {
  append(chunk);
}
```

## How senior engineers actually use this

**They start with polling and escalate only with a measured reason.** Persistent connections carry real operational cost, and most "real-time" requirements tolerate a few seconds of delay.

**They pick SSE when the flow is one-directional**, because free reconnection and event replay solve the two hardest problems.

**They never ship a raw `new WebSocket` without reconnection, heartbeat and a send queue.**

**They treat reconnection as the normal path**, designing the protocol so a client can resume from a known point rather than needing a full state refetch.

## Common pitfalls

- No reconnection logic, so the feature dies silently after the first network blip.
- No heartbeat, so half-open connections look healthy.
- Reconnect storms without jitter after a server restart.
- Sending while `readyState` is `CONNECTING`, throwing an exception.
- Tokens in the WebSocket URL.
- Not verifying `Origin` on cookie-authenticated sockets, allowing cross-site connection hijacking.
- Re-rendering per message instead of batching.
- Creating a new `EventSource` in `onerror` — it already reconnects, so this doubles connections.

## Interview angle

"How would you implement real-time updates" is a system design question. Walk the four options and justify the choice from the requirements — direction, frequency, latency tolerance — rather than defaulting to WebSockets. Then cover what production WebSocket code needs beyond the browser API: reconnection with jitter, heartbeats, a send queue, and auth without headers. Mentioning SSE's `Last-Event-ID` replay and the sticky-session/pub-sub scaling requirement shows you have thought past the client.
