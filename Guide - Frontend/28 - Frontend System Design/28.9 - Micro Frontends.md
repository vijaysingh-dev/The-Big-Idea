# Micro Frontends

Splitting a frontend into independently developed and deployed applications, composed into one experience for the user.

## The problem it actually solves

Micro frontends are an **organizational** solution, not a technical one. The problem is not that a codebase is large — it is that too many teams share one deployment pipeline.

Symptoms that justify considering it:

- Several teams blocked on one release train
- A merge queue where changes wait hours
- Teams unable to ship independently despite owning separate product areas
- An acquisition or migration where two stacks must coexist

Symptoms that do **not** justify it:

- The codebase feels big
- Build times are slow — fix the build ([[27.4 - Webpack Basics]])
- Code is tangled — fix the module boundaries ([[28.2 - Project Structure and Architecture]])
- It sounds modern

The honest heuristic: **below roughly four or five independent teams, a well-structured monolith with enforced boundaries is better on every axis.** Micro frontends trade runtime complexity for organizational autonomy, and that trade only pays when the organizational pain is real.

## Composition strategies

**Build-time composition** — each team publishes an npm package, the shell imports them.

```json
{ "dependencies": { "@company/checkout": "^2.1.0" } }
```

Simple, one bundle, good tree shaking, straightforward types. But shipping requires a version bump, a shell PR and a shell deploy — which means teams are **not** independently deployable. This is really a monorepo in disguise, and for most teams it is the right answer.

**Runtime composition via Module Federation** — the shell loads remote modules at runtime.

```js
// remote (checkout team)
new ModuleFederationPlugin({
  name: "checkout",
  exposes: { "./CheckoutPage": "./src/CheckoutPage" },
  shared: { react: { singleton: true, requiredVersion: "^19.0.0" } },
});

// host (shell)
new ModuleFederationPlugin({
  remotes: { checkout: "checkout@https://cdn.example.com/checkout/remoteEntry.js" },
  shared: { react: { singleton: true } },
});
```

```jsx
const Checkout = lazy(() => import("checkout/CheckoutPage"));
```

Genuine independent deployment — the checkout team publishes a new `remoteEntry.js` and it is live. This is the main technical enabler and originated in webpack, though Rspack and Vite now have implementations ([[27.4 - Webpack Basics]]).

**Route-level split** — separate applications behind a reverse proxy, each owning a path prefix.

```
/            → marketing app
/app/*       → dashboard app
/checkout/*  → checkout app
```

The simplest option by a wide margin: no shared runtime, no version negotiation, complete isolation, any framework per app. The cost is a full page load when crossing boundaries, and no shared client state.

For products where those boundaries align with genuinely separate user journeys, this is usually the right choice and is under-considered.

**Web Components** — each app exposes a custom element. Real encapsulation via Shadow DOM, framework-agnostic, but styling coordination and prop passing across the boundary are awkward, and SSR support is limited ([[12.1 - The DOM Tree and Node APIs]]).

## The shared dependency problem

The hardest technical issue in runtime composition.

```js
shared: {
  react: { singleton: true, requiredVersion: "^19.0.0", eager: true },
  "react-dom": { singleton: true, requiredVersion: "^19.0.0" },
}
```

Two copies of React break hooks entirely ([[17.1 - Rules of Hooks and How They Work]]). Two copies of a state library mean two independent stores. Two copies of a router mean two histories fighting over the URL.

`singleton: true` forces one instance — but then **every remote must be compatible with that version**. A remote requiring React 18 and a shell running React 19 either fails at runtime or silently loads a second copy.

The consequence people underestimate: **upgrading React becomes an organization-wide coordinated event.** Independent deployment holds for features and breaks for shared infrastructure, which is precisely the thing you most want to be able to change.

## Cross-application communication

Keep it minimal and explicitly contracted.

```ts
// A shared event bus — decoupled, but untyped and untraceable by default
eventBus.emit("cart:updated", { itemCount: 3 });

// A shared store — more coupling, better ergonomics
sharedStore.setState({ cart });

// Props from the shell — the clearest contract
<Checkout cartId={cartId} onComplete={handleComplete} />
```

Props passed down from the shell are the best option where the composition allows it: explicit, typed, traceable.

Whatever the mechanism, the **contract must be versioned and owned**. Two teams sharing an untyped event bus rediscover every problem that microservices had with untyped messages — and the failure mode is a runtime error in production, not a compile error.

Shared state across micro frontends is where most of the complexity lives. Minimizing it is a design goal, not an afterthought.

## Styling isolation

Independent teams will produce conflicting CSS unless isolation is structural.

- **Shadow DOM** — real isolation, but global styles and design tokens do not reach in without explicit forwarding
- **CSS Modules or scoped hashing** — collision-free class names, no runtime cost ([[11.5 - CSS Architecture]])
- **Prefix conventions** — `checkout-*`, enforced by lint; fragile but simple
- **Shared design tokens as custom properties** — cascade through Shadow DOM boundaries, which makes them the natural theming mechanism ([[10.4 - Units Custom Properties and Theming]])

CSS custom properties crossing Shadow DOM is one of the few things that makes web-component composition tractable for theming.

## Performance costs

**Duplicated dependencies.** Anything not shared is bundled per remote. Three remotes each including a date library is three copies.

**Extra requests.** Each remote is a separate manifest fetch plus its chunks. Sequential remote loading produces waterfalls ([[19.7 - Bundle Analysis and Optimization]]).

**No cross-application tree shaking.** A remote's bundle is optimized in isolation; the host cannot eliminate code it does not use ([[27.6 - Tree Shaking]]).

**Larger total payload.** A well-optimized monolith is almost always smaller.

Expect 20–40% more JavaScript in practice. The autonomy has to be worth that.

## Operational reality

**Version skew.** The shell and a remote deploy independently, so incompatible versions coexist in production. This needs contract testing and backwards-compatible interfaces — the same discipline distributed systems require.

**Failure isolation.** A failed remote must not blank the page:

```jsx
<ErrorBoundary fallback={<RemoteUnavailable name="checkout" />}>
  <Suspense fallback={<Skeleton />}>
    <Checkout />
  </Suspense>
</ErrorBoundary>
```

Every remote boundary needs this ([[22.1 - Error Boundaries]]).

**Debugging across boundaries.** A stack trace crossing remotes needs source maps from multiple deployments, each with its own release identifier ([[27.7 - Source Maps]]).

**Testing.** Integration tests need every remote available, which means either a shared staging environment or contract tests per boundary.

**Local development.** Running six applications to develop one is a real productivity tax. Most teams end up loading remotes from a shared environment and running only their own locally.

## Alternatives that usually work better

Before adopting micro frontends, consider whether the organizational problem has a cheaper solution:

**A monorepo with enforced boundaries and CODEOWNERS.** Teams own directories, lint prevents cross-imports, CI runs only affected packages. Independent development without independent deployment ([[28.2 - Project Structure and Architecture]]).

**Trunk-based development with feature flags.** Teams merge continuously and control their own release timing via flags rather than deploy timing ([[28.8 - Feature Flags and Progressive Rollout]]).

**Route-level splitting behind a proxy.** Independent deployment with almost none of the runtime complexity.

The last one deserves more consideration than it gets. If the boundaries between teams align with distinct user journeys, separate applications behind a proxy delivers most of the autonomy at a fraction of the cost.

## How senior engineers actually use this

**They treat it as an organizational decision** and ask how many teams are actually blocked before considering it.

**They prefer route-level splitting** where the product boundaries allow it.

**They pin shared runtime dependencies as singletons** and accept that upgrading them is a coordinated event.

**They wrap every remote in an error boundary**, since a failed remote otherwise takes down the page.

**They version and own cross-application contracts** with the same rigour as a public API.

**They exhaust monorepo and feature-flag options first**, because those are reversible and this is not.

## Common pitfalls

- Adopting it for a codebase-size problem rather than a team-coordination problem.
- Duplicate React from a missing or mismatched `singleton` declaration.
- Untyped event buses as the primary communication channel.
- No error boundary per remote, so one failure blanks the page.
- Version skew with no contract tests.
- CSS collisions from no isolation strategy.
- Shared state spread across remotes, recreating the coupling it was meant to remove.
- Underestimating the local development cost.

## Interview angle

"When would you use micro frontends" is partly a judgement test. The strong answer states plainly that it solves an organizational problem — independent deployment for multiple teams — and costs real runtime complexity, larger bundles and shared-dependency coordination. Below a handful of teams, a monorepo with enforced boundaries is better. If asked to design one, cover Module Federation with singleton shared dependencies, per-remote error boundaries, versioned contracts, and route-level splitting as the simpler alternative.
