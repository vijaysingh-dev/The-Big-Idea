# Distributed Transactions and Sagas

#backend #microservices #distributed-systems

> **In one line:** There is no ACID transaction across services, so you get a sequence of local transactions with compensating actions — and the hard part is that compensation can also fail.

---

## The Idea

```python
# Monolith
async with conn.transaction():
    await inventory.reserve(item_id, qty)
    await payments.charge(order.total)
    await orders.create(order)
# ← all or nothing, enforced by the database
```

```python
# Across services
await inventory_service.reserve(item_id, qty)     # committed
await payment_service.charge(order.total)         # ← fails
# inventory is now reserved for an order that will not exist
```

⚠️ **There is no mechanism that makes three services commit atomically**, and the ones that claim to — two-phase commit — have costs that make them unusable at scale.

💡 **The replacement is a saga: a sequence of local transactions, each with a compensating action that semantically undoes it** ([[08.11 - Durable Workflows and Sagas]]).

---

## Why Not Two-Phase Commit

```
Coordinator → prepare → all participants vote
            → commit  → all participants commit
```

It genuinely provides atomicity. It is also almost never used, for four reasons:

| Problem | |
|---|---|
| **Blocking** | Participants hold locks from prepare until commit |
| **Coordinator failure** | Participants are stuck holding locks, indefinitely |
| **Availability** | Every participant must be up. Availability multiplies down ([[10.3 - Communication Patterns]]) |
| **Support** | Most modern services and databases do not implement XA |

⚠️ **The blocking problem is the fatal one.** A participant that has voted to commit cannot release its locks until the coordinator decides — and if the coordinator dies in between, those locks are held until a human intervenes.

💡 **2PC trades availability for consistency, and in a distributed system that trade is usually wrong** — which is CAP stated concretely. **Sagas trade consistency for availability instead**, and accept that the system is temporarily inconsistent.

---

## The Saga

```
T1 → T2 → T3 → T4          each a local transaction, each committed
 ↓    ↓    ↓
C1 ← C2 ← C3               compensate in reverse on failure
```

⚠️ **Compensation is not rollback.** T2 committed and was visible to everyone. C2 is a *new* transaction that semantically reverses it.

| Step | Compensation | What the user sees |
|---|---|---|
| Reserve inventory | Release the reservation | Nothing |
| Charge the card | **Refund** | **A charge and a refund on their statement** |
| Send confirmation | Send a cancellation | **Two emails** |

💡 **The system is eventually consistent, not atomic**, and the intermediate state was real. **Design compensations to be honest about that** rather than pretending nothing happened.

### Semantic locks

⚠️ **Between T1 and T4, the data is in an intermediate state that other transactions can observe.**

```
Inventory reserved but the order does not exist yet.
Another request sees reduced availability for an order that may never happen.
```

**The standard mitigation is a semantic lock — a status field marking the intermediate state:**

```sql
UPDATE inventory SET reserved = reserved + $1 WHERE item_id = $2;
-- other readers see `available = total - reserved` and behave correctly
```

```sql
INSERT INTO orders (id, status) VALUES ($1, 'pending');
-- the order exists but is not yet valid; consumers filter on status
```

💡 **A `pending` status is a semantic lock**, and it is how you make the intermediate state safe to observe. **Without it, other transactions make decisions based on state that is about to be undone.**

## Compensation Design

### Make compensations always succeed

```
Reserve inventory      → release: a local database write. Always succeeds
Arrange shipping       → cancel: an API call. Can fail
Charge the card        → refund: an API call. Can fail
```

💡 **Order the steps so that the operations hardest to compensate happen last.**

```
1. Reserve inventory   (local, trivially compensable)
2. Arrange shipping    (compensable via the provider's cancel API)
3. Charge the card     (LAST — nothing after it to fail)
```

**With charging last, there is nothing to compensate when it fails** — you release the reservation and cancel the shipment, both of which are reliable.

⚠️ **This is not always possible.** Sometimes you must charge before shipping, and then a shipping failure requires a refund that might fail.

### Make compensations idempotent

```python
async def release_reservation(reservation_id: str):
    await conn.execute(
        "UPDATE reservations SET released = true WHERE id = $1 AND NOT released",
        reservation_id,
    )
```

⚠️ **A compensation will be retried.** If it is not idempotent, retrying a refund refunds twice ([[07.5 - Idempotency Keys and Deduplication]]).

**Pass an idempotency key to every external compensating call**, so the provider deduplicates.

### Handle "nothing to compensate"

```python
async def cancel_shipment(shipment_id: str | None):
    if shipment_id is None:
        return                                    # T2 never completed
    ...
```

💡 **Compensation must handle the case where the step being compensated did not actually happen** — because a crash between the effect and recording it means you do not know ([[08.11 - Durable Workflows and Sagas]]).

**The safe rule: compensations must be safe to run whether or not the forward step succeeded.**

## When Compensation Fails

The case that separates a real implementation from a demonstration.

```
Payment charged. Shipping failed. Refund → the payment provider is down.
```

⚠️ **You are now in an inconsistent state that no automatic mechanism can resolve.**

| Response | |
|---|---|
| **Retry with long backoff** | Usually works. Hours, not seconds |
| **Escalate to a human** | With full context, after N attempts |
| **Reconciliation job** | Periodically retries stuck compensations |
| **A dedicated `compensation_failed` state** | Visible, alerted, actionable |

```python
async def compensate_step(run_id, step, ctx):
    for attempt in range(MAX_COMPENSATION_ATTEMPTS):
        try:
            await step.compensate(ctx)
            return await mark_compensated(run_id, step.name)
        except Exception:
            await asyncio.sleep(backoff(attempt))

    await set_state(run_id, "compensation_failed")
    await alert_human(run_id, step.name, ctx)          # ⚠️ needs intervention
```

💡 **`compensation_failed` is not a failure of design — it is the design.** Some inconsistencies genuinely require a human decision, and having an explicit state for them is far better than an infinite retry loop or a silent give-up.

⚠️ **The alert must contain enough context to act on**: which saga, which step, what was attempted, what the external system's last known state was, and what the operator should do.

## Choreography versus Orchestration

Two shapes, and the choice matters more for sagas than for ordinary communication ([[10.3 - Communication Patterns]]).

### Choreography

```
OrderPlaced → [inventory] → InventoryReserved → [payment] → PaymentFailed
                                                          ↓
                          [inventory] ← InventoryReleaseRequested
```

⚠️ **Compensation in a choreographed saga requires every service to know about every other's failures.** Inventory must subscribe to `PaymentFailed`, and shipping must subscribe to it too, and adding a fifth step means editing four services' subscriptions.

💡 **Choreographed compensation is where this pattern breaks down.** The forward path is elegant; the reverse path is a distributed conditional that nobody can see in one place.

### Orchestration

```python
async def place_order(order_id: str):
    state = await load_or_create(order_id)
    completed = []

    for step in STEPS:
        if step.name in state.completed:
            completed.append(step)
            continue
        try:
            result = await step.execute(state)
            await record_completed(order_id, step.name, result)
            completed.append(step)
        except Exception as e:
            await record_failed(order_id, step.name, e)
            await compensate(order_id, reversed(completed), state)
            raise
```

💡 **The whole process is visible in one function**, which means it can be read, tested and debugged. **For a saga, that visibility is worth the coupling.**

**Use orchestration for sagas. Use choreography for event fan-out.**

## In Production

### Persisting the saga state

```sql
CREATE TABLE saga_runs (
    id           uuid PRIMARY KEY,
    saga         text NOT NULL,
    entity_id    text NOT NULL,
    state        text NOT NULL,      -- running | compensating | completed | failed | compensation_failed
    context      jsonb NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (saga, entity_id)
);

CREATE TABLE saga_steps (
    run_id  uuid REFERENCES saga_runs(id),
    step    text NOT NULL,
    state   text NOT NULL,           -- completed | compensated | failed
    result  jsonb,
    PRIMARY KEY (run_id, step)
);
```

⚠️ **Without persisted state, a coordinator crash loses the saga's position** and you do not know what to compensate. **The state table is not optional.**

💡 **`UNIQUE (saga, entity_id)` makes the saga itself idempotent** — starting it twice for the same order is a conflict, not a second run.

### The crash points

⚠️ **A saga has roughly `2N + 1` crash points for N steps**, and each must leave a recoverable state.

| Crash point | Recovery |
|---|---|
| Before a step | Retry the step |
| **During a step** | **Ambiguous — did it happen?** |
| After a step, before recording | Retry; idempotency makes it safe |
| After recording | Continue |
| During compensation | Retry the compensation |

💡 **"During a step" is the hard one**, and the answer is the two-phase pattern with an idempotency key passed downstream ([[07.5 - Idempotency Keys and Deduplication]]):

```python
result = await payment_service.charge(order_id, idempotency_key=f"{run_id}:{step.name}")
```

**On retry, the downstream service returns the original result rather than charging again.**

⚠️ **If the downstream service does not support idempotency keys, you must reconcile** — ask it what actually happened before deciding.

### Observability

```python
saga_started_total.labels(saga=name).inc()
saga_completed_total.labels(saga=name, outcome="completed"|"compensated"|"failed").inc()
saga_duration_seconds.labels(saga=name).observe(elapsed)
saga_step_failures_total.labels(saga=name, step=s).inc()
saga_compensations_total.labels(saga=name, step=s).inc()
saga_stuck_total.labels(state="compensation_failed").set(count)     # ← page on this
```

⚠️ **`saga_stuck_total` must page someone.** A saga in `compensation_failed` means money or inventory is in limbo, and every hour it sits there is a customer-visible problem.

💡 **The operational question a saga system must answer instantly: "where is order 4271?"** With a persisted state table it is one query. **Test that you can answer it in under thirty seconds.**

### The dashboard that matters

```
Sagas in flight:           142
  running:                 138
  compensating:              3
  compensation_failed:       1     ← ⚠️
Oldest running saga:      4m 12s
Compensation rate (1h):    2.1%
```

💡 **Compensation rate is a business metric, not just a technical one.** A rising rate means orders are failing partway, and product people should see it.

### Avoiding sagas entirely

⚠️ **The best saga is the one you did not need.**

| Alternative | |
|---|---|
| **Keep the operation in one service** | The boundary was wrong ([[10.2 - Finding Service Boundaries]]) |
| **Make the steps independently valid** | Each commits and is meaningful alone |
| **Reorder so failure is impossible after the irreversible step** | |
| **Accept eventual consistency without compensation** | If a partial state is acceptable |
| **Use a reservation pattern** | Reserve, then confirm — no compensation needed |

💡 **The reservation pattern is underused:**

```
1. Reserve inventory with a 15-minute expiry
2. Charge the card
3. Confirm the reservation
   ← if step 2 fails, the reservation simply expires. No compensation
```

**A time-bounded reservation compensates itself**, and it removes an entire failure path.

⚠️ **If your saga has four steps and three compensations, ask whether the boundaries are right.** Three compensating actions is a lot of failure surface for one business operation.

### Conduit's sagas

| Operation | Saga? |
|---|---|
| Document ingestion | **No** — a failure means "not indexed", which is a state, not an inconsistency |
| Source sync | No — idempotent and retryable |
| Export generation | No — a single long task |
| **Organisation offboarding** | **Yes** — delete across database, search, object storage and cache |
| **Plan upgrade with payment** | **Yes** — charge, provision, notify |

💡 **Two out of five, and both involve external systems where something has moved that must be undone.** That is the signal.

**For plan upgrade, apply the ordering rule:**

```
1. Provision the new limits    (local write, trivially compensable)
2. Send the notification       (compensable with a correction email)
3. Charge the card             (LAST)
```

⚠️ **This ordering means a customer briefly has the new plan before paying**, which is a business decision, not a technical one. **Charging first means a refund on failure, which is worse for the customer and worse operationally.**

**Write down which tradeoff you chose and why.** That is the kind of decision an ADR exists for.

💡 The Eventuate documentation on **countermeasures for the lack of isolation** is the part most saga material skips: semantic locks, commutative updates, pessimistic view, re-read value, version files, and by-value. **Those are the techniques for making intermediate states safe to observe**, and they are what separates a saga that works from one that occasionally produces impossible data.

**Part 1 — The naive version.** A four-step order across four services, sequential, no compensation.

Fail step 3. **Inspect every service's state and enumerate the inconsistencies.**

Then measure how many distinct inconsistent states are reachable by failing at different points.

**Part 2 — Build the orchestrator.** Persisted state, four steps with compensations, reverse-order compensation.

Test the happy path, then failure at each step, confirming the final state is consistent.

**Part 3 — The crash matrix.** For a four-step saga, kill the coordinator at all nine points: before each step, during each step, after each step before recording, and at each point during compensation.

**Restart and let it recover. Assert consistency at every point.**

⚠️ **The "during a step" points are the hard ones.** Implement idempotency-key passthrough and confirm the retry returns the original result rather than repeating the effect.

Then remove the idempotency key and **confirm you double-charge.**

**Part 4 — Isolation, three ways.** The reserve-then-charge flow.

**Version A:** no semantic lock. **Confirm another request can observe inventory that is about to be released**, and make a decision based on it.

**Version B:** a semantic lock via a `reserved` counter. Confirm concurrent readers behave correctly.

**Version C:** a time-bounded reservation that expires. **Confirm no compensation is needed at all when step 2 fails.**

**Compare the three on correctness, code, and failure surface.**

**Part 5 — When compensation fails.** Make the refund permanently fail.

**Confirm the saga reaches `compensation_failed` and stops rather than looping.**

Then implement: retry with long backoff, escalation with full context, and a reconciliation job.

**Measure: time until a human is alerted, and whether the alert contains enough to act.**

Then have someone else attempt to resolve it using only your alert. **If they cannot, the alert is wrong.**

**Part 6 — Ordering.** Reorder so the irreversible step is last.

**Re-run the crash matrix and count how many points now require compensation at all.**

Then find a case where you cannot reorder, and document why.

**Part 7 — "Where is order 4271?"** Answer it during: normal execution, mid-compensation, and stuck.

**Measure time to answer.** Build the dashboard showing sagas in flight by state, oldest running, and compensation rate.

Then write `runbook.md`: what each state means, how to investigate, how to manually resolve a stuck saga, and when to escalate.

**Part 8 — Conduit's two sagas.** Implement organisation offboarding and plan upgrade.

For offboarding: delete across four stores with acknowledgement, and **verify completeness** ([[10.4 - Data Ownership]]).

For plan upgrade: apply the ordering rule, and **write the ADR explaining the customer-facing tradeoff** of provisioning before charging.

**Done when:**
- You enumerated the inconsistent states the naive version can reach
- All nine crash points leave a recoverable state
- Removing the idempotency key demonstrably double-charges
- A semantic lock prevents a wrong decision based on intermediate state
- The reservation pattern eliminates a compensation entirely
- A stuck saga alert is actionable by someone who did not write it
- "Where is order 4271" is answerable in under thirty seconds
- Conduit's offboarding saga proves completeness across four stores
