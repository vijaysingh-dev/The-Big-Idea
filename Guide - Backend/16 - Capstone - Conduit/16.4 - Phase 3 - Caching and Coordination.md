# Phase 3: Caching, Coordination and Search

#backend #project #capstone

> **In one line:** Every request still hits Postgres, external source connectors need coordination and rate limiting, and search stops working somewhere above a hundred thousand documents.

---

## The Problem Phase 2 Created

```
Every request → Postgres. No cache at any layer
Two workers can sync the same Google Drive source simultaneously
The embedding-adjacent external API has a global rate limit you exceed
Search: sequential scan above ~100k documents
```

💡 **Phase 2 made the system correct under load; phase 3 makes it fast**, and introduces the coordination problems that come with external sources.

---

## What You Build

### The cache, at the right layers

```python
async def get_document(org_id: str, doc_id: str) -> Document | None:
    key = f"org:{org_id}:doc:{doc_id}"

    raw = await redis.get(key)
    if raw == NULL_SENTINEL:
        return None
    if raw is not None:
        entry = deserialise(raw)
        if entry.is_fresh() or not await claim_refresh(key):
            return entry.value
        spawn(reload(key, org_id, doc_id))
        return entry.value                          # stale-while-revalidate

    return await load_with_lock(key, org_id, doc_id)
```

⚠️ **The tenant is in the key, and it is a mandatory argument.** An unscoped cache key on a query result is a cross-tenant leak ([[14.6 - Multi Tenant Isolation]]).

💡 **Build one resilient cache helper with all the defences** — stale-while-revalidate, single-flight, negative caching, jittered TTLs — **rather than ad-hoc `redis.get` calls** ([[07.3 - Stampede Hot Keys and Negative Caching]]).

**Never cache permissions** ([[14.1 - AuthN vs AuthZ]]).

### Source connectors, coordinated

```python
@app.task(acks_late=True)
def sync_source(org_id: str, source_id: str):
    with tenant_context(org_id), db.transaction() as conn:
        got = conn.fetchval("SELECT pg_try_advisory_xact_lock(hashtext($1))",
                            f"sync:{source_id}")
        if not got:
            sync_skipped_total.inc()
            return                                  # another worker has it
        ...
```

💡 **`pg_try_advisory_xact_lock` releases automatically when the transaction ends or the connection drops** — no TTL, no renewal, no expiry-while-working ([[07.4 - Distributed Locks Done Right]]).

⚠️ **Efficiency only.** A duplicate sync is wasteful, not incorrect — **and the unique constraint on `(org_id, content_hash)` is what makes it safe** ([[06.10 - Schema Design]]).

### The outbound rate limit

```python
async def call_provider(request):
    async with global_limiter(provider="google_drive", rate=100, burst=200):
        return await client.request(request)
```

⚠️ **The limit is global across all workers, not per worker.** Celery's `rate_limit` is per worker and multiplies by worker count — **a genuine and common bug** ([[11.5 - Rate Limiting and Quotas]]).

**Token bucket in Redis, via a Lua script for atomicity.**

### Search, properly

```sql
ALTER TABLE documents
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(content, '')), 'B')
) STORED;

CREATE INDEX ON documents USING gin (search_vector);
```

```sql
SELECT id, title,
       ts_rank_cd(search_vector, query) * 0.6
     + (1.0 / (1 + extract(epoch from now() - created_at) / 86400)) * 0.3
     + (view_count::float / (view_count + 100)) * 0.1 AS score
FROM documents, websearch_to_tsquery('english', $2) query
WHERE org_id = $1 AND search_vector @@ query AND deleted_at IS NULL
ORDER BY score DESC LIMIT 20;
```

⚠️ **`websearch_to_tsquery`, never `to_tsquery`** — the latter raises a syntax error on user input ([[06.15 - Search - Postgres vs Elasticsearch]]).

💡 **Blend text relevance with business signals.** Postgres has no BM25, so recency and popularity often matter more than the text score.

**Add `pg_trgm` for typo tolerance and indexable `ILIKE`.**

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Redis cache** | In-process only | Shared, invalidatable, already deployed |
| **Cache entities, not queries** | Query result caching | Invalidation is tractable ([[07.2 - Cache Strategies and Invalidation]]) |
| **Write-around (delete on write)** | Write-through | A race produces a miss, not a wrong value |
| **Advisory locks** | Redis locks | Auto-release on disconnect. No TTL to tune |
| **Unique constraint for dedup** | A distributed lock | Stronger, and it needs no coordination |
| **Postgres FTS** | Elasticsearch | Measured relevance is acceptable |
| Global outbound limiter in Redis | Per-worker | Celery's per-worker limit multiplies |

⚠️ **The search decision must cite a number.** Build a golden set of 50 judged queries and measure precision@10 **before** deciding ([[06.15 - Search - Postgres vs Elasticsearch]]).

## What Will Go Wrong

### The Redis outage

```
95% hit ratio → Redis down → 20× database load, instantly
```

⚠️ **If your database is sized assuming the cache, a Redis outage takes it down too** ([[07.1 - Cache Layers Across One Request]]).

**Test it.** Turn Redis off under production-level load and see whether you survive. **If not, you need headroom, load shedding, or a local fallback.**

### The stampede

```
TTL expires on a hot document → 200 concurrent misses → 200 identical queries
```

💡 **The signature is periodic latency spikes at exactly your TTL interval.** Jitter plus single-flight plus stale-while-revalidate ([[07.3 - Stampede Hot Keys and Negative Caching]]).

### Cache penetration

⚠️ **Requesting non-existent document IDs bypasses the cache entirely** and hits the database at full rate.

**Negative caching with a shorter TTL than positives.**

### The unscoped key

⚠️ **The highest-severity bug available in this phase.** A cached search result without `org_id` in the key serves one tenant's documents to another.

**Make the tenant a required positional argument of the cache helper**, so an unscoped key is impossible rather than discouraged.

### Search degrades on broad queries

```
Query matching 10 documents:       12ms
Query matching 500,000 documents:  4.2s
```

⚠️ **Postgres must fetch every matching row to rank it** ([[15.2 - Reading Redis Networking]] shows the equivalent constraint elsewhere; the search version is in [[06.15 - Search - Postgres vs Elasticsearch]]).

**Chart latency against match count. Find your cliff, and write it into the ADR as the Elasticsearch trigger.**

### The connector rate limit

⚠️ **Ten workers each respecting a 100/minute limit produces 1,000/minute** and gets your API key suspended.

**Measure the actual outbound rate under load and confirm it matches the intended global limit.**

## Acceptance Criteria

```
□  Cache hit ratio > 80% on the document read path, measured per prefix
□  The cache helper makes an unscoped key impossible
□  Stampede: 200 concurrent misses produce 1 database query
□  Negative caching bounds a random-ID attack
□  Redis outage under production load: the system survives, measured
□  Two workers cannot sync one source concurrently, verified
□  Outbound provider rate is global, verified across 10 workers
□  Search relevance measured: precision@10, MRR, NDCG on 50 golden queries
□  Search latency charted against match count; the cliff identified
□  websearch_to_tsquery handles hostile input without erroring
□  Cross-tenant cache probe test for every cached type
□  The Elasticsearch trigger written as a measurable threshold
```

⚠️ **The Redis-outage criterion is the one most likely to fail**, and it is the most important.

---

## What You Should Be Able To Explain

```
"What is your cache hit ratio, and what happens when Redis is down?"
  → 84% on documents. Redis down means 19× database load. We survive
     because we shed load at pool pressure > 0.8. Here is the chart

"How do you stop two workers syncing the same source?"
  → A Postgres advisory transaction lock. It releases on disconnect,
     so there is no TTL to get wrong. And it is only for efficiency —
     the unique constraint on content hash is what makes it correct

"Why is search still in Postgres?"
  → Precision@10 of 0.72 against our golden set. Elasticsearch scored
     0.81 and costs $450/month plus operational burden. We move when
     precision drops below 0.65 or when p99 on broad queries exceeds 1s.
     Currently that cliff is at 400k matched documents

"What is wrong with this system now?"
  → It is one process. Ingestion competes with the API for resources,
     and we cannot scale them independently. Phase 4
```

2. `onyx/backend/onyx/connectors/interfaces.py` — **the abstraction.** How they made connectors uniform

💡 Onyx's connector interface is worth studying before writing your own. **They abstracted "poll a source, yield documents, track a cursor" across a dozen very different APIs**, and the shape of that interface is most of the design work.

## Exercise

**Drill 16.4 — Cache it, coordinate it, and measure search**

```
conduit/phases/03/
├── src/{cache/, connectors/, search/, limits/}
├── golden/{queries.json, judgements.json}
├── measure/{hit_ratio.py, redis_outage.py, search_relevance.py,
│            search_latency.py, PLOT.md}
├── coordination/{advisory_lock.py, global_limit.py, RESULTS.md}
├── tests/{cache_isolation/, stampede/, penetration/}
├── adr/{015-cache.md ... 019-search.md}
└── PHASE3.md
```

**Part 1 — The resilient cache helper.** One utility: tenant-scoped keys, stale-while-revalidate, single-flight, negative caching, jittered TTL, and degradation on Redis failure.

**Then write the test that proves an unscoped key is impossible** — attempt it and confirm it does not type-check or raises.

**Part 2 — Prove each defence.** Individually:

| Defence | Test |
|---|---|
| Stampede | 200 concurrent misses → 1 database query |
| Penetration | 5,000 random non-existent IDs → bounded database load |
| Isolation | Tenant B cannot read tenant A's cached document |
| Degradation | Redis unavailable → requests succeed, slower |

**Part 3 — The Redis outage, at production load.** Steady load with an 85% hit ratio. **Kill Redis.**

**Chart database CPU, pool wait time, and application p99 for two minutes.**

**Determine whether you survive.** If not, implement load shedding at pool pressure and a small local fallback cache, then re-run until you do.

**Part 4 — Source coordination.** Ten workers, one source, sync triggered concurrently.

**Confirm exactly one executes.** Then kill the holding worker mid-sync and **confirm the lock releases immediately** — no TTL wait.

**Compare against a Redis lock:** measure the release delay after a hard kill for both.

**Part 5 — The global rate limit.** A mock provider API with a hard 100 requests/minute limit that returns 429 above it.

**Run 10 workers with Celery's per-worker `rate_limit=100/m`.** Measure the actual outbound rate — **it should be ~1,000/minute and get you throttled.**

Then implement the Redis token bucket and **confirm the global rate holds at 100/minute regardless of worker count.**

**Part 6 — Build the golden set.** 50 realistic queries against your seeded corpus, each with a judged list of documents that should rank in the top 10.

⚠️ **This is the hard part and it is the point.** Without it you can only measure speed.

**Part 7 — Measure search, both ways.** Run all 50 queries against Postgres FTS and against Elasticsearch.

**Compute precision@10, MRR and NDCG@10 for each.**

**Then find the queries where they differ most** and work out why — the IDF cases should stand out.

**Then chart latency against match count for both**, and identify the Postgres cliff.

**Part 8 — Write the search ADR.** With your relevance numbers, your latency cliff, and the Elasticsearch cost.

⚠️ **Name the specific threshold that would change the decision.** "Precision@10 below 0.65, or p99 above 1s on broad queries" is an engineering commitment.

**Part 9 — Hostile search input.** Unbalanced quotes, `&`, `|`, `!`, a 10,000-character query, and SQL metacharacters.

**Confirm none errors and none injects.** Then measure the cost of the most expensive query a user can construct.

**Done when:**
- An unscoped cache key is structurally impossible
- All four cache defences are individually proven
- You know whether you survive a Redis outage at production load
- An advisory lock releases faster than a Redis lock after a hard kill
- Global outbound rate limiting holds across 10 workers
- Your golden set has 50 judged queries
- The relevance comparison has precision@10, MRR and NDCG for both engines
- Your search ADR names a measurable Elasticsearch trigger
- Hostile search input neither errors nor injects
