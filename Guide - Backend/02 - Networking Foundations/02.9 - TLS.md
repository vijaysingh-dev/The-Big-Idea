# TLS

#backend #networking #security #tls

> **In one line:** TLS proves who you are talking to, then encrypts the conversation — and the expensive part is the proving, which is why connection reuse matters more than any cipher choice.

---

## The Idea

TLS gives you three things:

| Property | Meaning | Mechanism |
|---|---|---|
| **Confidentiality** | Nobody in between can read it | Symmetric encryption |
| **Integrity** | Nobody in between can change it undetected | Message authentication |
| **Authentication** | You are talking to who you think | Certificates |

The third one is the hard one, and the one people understand least. Encryption without authentication is worthless — an attacker in the middle can just encrypt with their own key. **The certificate chain is what makes TLS meaningful**, and it is where all the operational pain lives.

---

## The Handshake

### TLS 1.3 — one round trip

```
Client                                          Server
  │                                               │
  │ ── ClientHello ─────────────────────────────► │
  │    versions, cipher suites, key share,        │
  │    SNI (which hostname I want)                │
  │                                               │
  │ ◄─ ServerHello ────────────────────────────── │
  │    chosen cipher, key share, certificate,     │
  │    certificate verify, finished               │
  │                                               │
  │ ── Finished ────────────────────────────────► │
  │ ── application data ────────────────────────► │
```

**One round trip.** Both sides send a key share in the first message and derive the shared secret immediately.

### TLS 1.2 — two round trips

```
ClientHello ──►
            ◄── ServerHello, Certificate, ServerHelloDone
ClientKeyExchange, ChangeCipherSpec, Finished ──►
            ◄── ChangeCipherSpec, Finished
application data ──►
```

Twice the latency, and it supported a lot of weak options that had to be disabled one by one over the years. TLS 1.3 removed them from the protocol entirely — no RSA key exchange, no CBC modes, no compression, no renegotiation.

💡 **TLS 1.3's real innovation is deletion.** Roughly half the historical TLS vulnerabilities came from downgrade attacks and weak legacy options. Removing them was worth more than any new feature.

### The cost

```
DNS lookup      20ms
TCP handshake   1 RTT   (100ms on a cross-region link)
TLS 1.3         1 RTT   (100ms)
────────────────────────
Before your first byte:  ~220ms
```

⚠️ **This is why connection reuse is the highest-leverage networking optimisation you can make.** A warm connection skips all of it. On a cross-region call, reusing connections often beats every code optimisation you could do — see [[01.10 - Connection Pools and Limits]].

### Session resumption and 0-RTT

```
First connection:   1 RTT, full handshake, server issues a session ticket
Later connection:   0 RTT — send application data in the first flight
```

⚠️ **0-RTT data is replayable.** An attacker who captures it can send it again, and the server cannot tell the difference. So 0-RTT must only carry **idempotent** requests — GETs, not POSTs. Most implementations restrict it accordingly, but if you build on it yourself, this is your responsibility. Idempotency is covered in [[03.4 - Idempotency and Safe Retries]].

## Certificates

### The chain

```
Root CA          (in your OS/browser trust store, self-signed)
  └── Intermediate CA     (signed by root)
        └── Your certificate   (signed by intermediate)
```

The client verifies each signature up the chain until it reaches something in its trust store.

⚠️ **The most common TLS misconfiguration in the world: serving your certificate without the intermediate.** Browsers often paper over it by fetching the missing intermediate themselves. `curl`, Python, Java and Go usually do not.

Symptom: **it works in my browser but fails from the server.** If you have ever heard that sentence about a TLS problem, this is almost always it.

```bash
openssl s_client -connect example.com:443 -showcerts
# Count the certificates. You should see yours AND the intermediate.
```

Fix: concatenate your certificate and the intermediate into the file you serve — the "full chain" file that Let's Encrypt gives you as `fullchain.pem`. Serving `cert.pem` instead of `fullchain.pem` is the single most common cause of this.

### What is actually verified

| Check | Failure looks like |
|---|---|
| Signature chains to a trusted root | `unable to get local issuer certificate` |
| Not expired, not yet valid | `certificate has expired` |
| Hostname matches CN or SAN | `hostname mismatch` |
| Not revoked | Usually not checked — see below |

⚠️ **The Common Name field is deprecated.** Modern clients only look at Subject Alternative Names. A certificate with the hostname only in CN will fail on current Python, Go and browsers. If you generate certificates yourself, you must include SANs.

### Revocation barely works

If a private key leaks, the certificate should be revoked. In practice:

- **CRLs** (revocation lists) got too large to be practical
- **OCSP** requires an extra network call per connection, is a privacy leak, and most clients "soft fail" — if the OCSP server is unreachable, they proceed anyway
- **OCSP stapling** lets the server attach a fresh proof, which helps, but is not universally deployed
- **OCSP is being wound down** by major CAs in favour of short-lived certificates

💡 **The industry answer to revocation is short lifetimes rather than revocation.** Certificate lifetimes have fallen from 5 years to 1 year to 90 days, and the direction of travel is shorter still. A 90-day certificate that leaks is a bounded problem. This is why automated renewal (ACME/Let's Encrypt) is not a convenience but a requirement.

### mTLS — both sides prove identity

```
Server presents a certificate  → client verifies it   (normal TLS)
Client presents a certificate  → server verifies it   (mutual TLS)
```

Standard for service-to-service authentication inside a mesh. Instead of passing API keys around, each service has a certificate identifying it, and the mesh rotates them automatically.

The hard part is not the TLS — it is certificate lifecycle at scale: issuing, rotating, revoking, and handling a service whose certificate expired at 3am. This is most of what a service mesh actually does for you. See [[10.7 - Service Discovery and Service Mesh]].

## SNI — Server Name Indication

One IP can host many sites. But the server must choose which certificate to send **before** encryption starts, and at that point it does not know which hostname you want.

SNI solves it: the client puts the hostname in the ClientHello, in **plaintext**.

```
ClientHello: "I want api.example.com"     ← visible to anyone watching
```

⚠️ **SNI leaks which sites you visit even though the traffic is encrypted.** This is how many national firewalls and corporate filters work — they read SNI and block accordingly.

**Encrypted Client Hello (ECH)** fixes this by encrypting the ClientHello with a public key fetched from DNS. Deployed at Cloudflare and in Firefox and Chrome; not yet universal. Worth knowing about because it changes what network-level filtering can see.

For backend work, the practical SNI issue is simpler: **if your client does not send SNI, a multi-tenant server sends its default certificate and you get a hostname mismatch.** Old libraries and hand-rolled TLS code sometimes forget.

## TLS in Python

### The defaults are good — do not fight them

```python
import httpx

r = httpx.get("https://api.example.com")     # verifies properly by default
```

```python
# NEVER do this
httpx.get(url, verify=False)
requests.get(url, verify=False)
ssl._create_default_https_context = ssl._create_unverified_context
```

⚠️ **`verify=False` removes authentication entirely.** You still get encryption, but to whoever intercepted you. It is worse than plain HTTP because it looks secure. Every instance of this in a codebase is a real vulnerability, and it is depressingly common in internal tooling.

The legitimate need behind it is almost always "our internal CA is not trusted", and the correct fix is to trust the internal CA:

```python
client = httpx.Client(verify="/etc/ssl/certs/internal-ca.pem")
```

### Custom contexts

```python
import ssl

ctx = ssl.create_default_context(cafile="/etc/ssl/internal-ca.pem")
ctx.minimum_version = ssl.TLSVersion.TLSv1_2
ctx.load_cert_chain("/etc/ssl/client.crt", "/etc/ssl/client.key")   # for mTLS

client = httpx.AsyncClient(verify=ctx)
```

### The certificate bundle problem in containers

```
ssl.SSLCertVerificationError: unable to get local issuer certificate
```

A minimal container image often has no CA bundle at all.

```dockerfile
RUN apt-get update && apt-get install -y ca-certificates
# or, for alpine
RUN apk add --no-cache ca-certificates
```

Python may also use `certifi`'s bundle rather than the system one, which means **your container can trust a different set of CAs than the OS does**. Worth knowing when a request works from the shell and fails from Python in the same container.

### TLS costs CPU

Modern CPUs have AES instructions, so bulk encryption is nearly free. The handshake is not — the asymmetric cryptography costs real CPU.

```
Handshake (ECDSA):  ~1ms of CPU
Bulk encryption:    ~1 GB/s per core with AES-NI
```

At 10,000 new connections per second you are spending 10 cores purely on handshakes. **Which is, again, the argument for connection reuse and session resumption.**

## In Production

### Where to terminate

| Pattern | Where TLS ends | Trade |
|---|---|---|
| Edge termination | At the load balancer | Simplest. Internal traffic is plaintext |
| Re-encryption | LB decrypts, re-encrypts to backend | Inspection at the edge, encryption throughout |
| Passthrough | At your service | Full end-to-end, no L7 features at the LB |
| mTLS everywhere | Every hop, both directions | Best security, needs a mesh to be manageable |

Edge termination is the common default. It is fine when your internal network is trusted and you have no compliance requirement otherwise. It becomes untenable in multi-tenant clusters and regulated environments, which is where meshes appear.

⚠️ **If you terminate at the edge, your load balancer sees plaintext.** That is the point — it is how you get L7 routing, header-based routing and HTTP/2 to HTTP/1.1 translation. But it also means the load balancer is now a very high-value target and must be treated as such.

### Certificate expiry is a real outage class

Expired certificates have taken down Microsoft Teams, Spotify, Ericsson's mobile network, and many others. It is one of the most preventable outage causes that keeps happening.

```bash
# Check expiry from outside
echo | openssl s_client -connect api.example.com:443 2>/dev/null \
  | openssl x509 -noout -dates

# Monitor it as a metric
```

Every certificate should have:
1. Automated renewal (ACME, cert-manager, or your cloud provider's)
2. An alert at 30 days remaining
3. A second alert at 7 days that pages someone

The 30-day alert catches renewal failures. The 7-day alert catches the fact that nobody looked at the 30-day alert.

### Diagnosing

```bash
# The everything command
openssl s_client -connect api.example.com:443 -servername api.example.com

# Just the certificate details
echo | openssl s_client -connect host:443 2>/dev/null | openssl x509 -noout -text

# Verify the chain explicitly
openssl s_client -connect host:443 -showcerts -verify_return_error

# What does curl think?
curl -vI https://api.example.com

# Test a specific version
openssl s_client -connect host:443 -tls1_2

# For mTLS
openssl s_client -connect host:443 -cert client.crt -key client.key
```

`-servername` matters: without it, `openssl s_client` does not send SNI, and you may get a different certificate than your application does. **That discrepancy has confused a lot of people for a lot of hours.**

### Failure modes

| Error | Cause |
|---|---|
| `unable to get local issuer certificate` | Missing intermediate, or missing CA bundle in the container |
| `certificate verify failed: hostname mismatch` | Wrong SAN, or SNI not sent |
| `certificate has expired` | The obvious one. Check your renewal automation |
| `sslv3 alert handshake failure` | No shared cipher or version. Usually a very old client |
| Works in browser, fails from server | Missing intermediate. Almost always |
| Works locally, fails in container | Missing `ca-certificates` package |
| Intermittent failures after a deploy | Certificate rotated, some pods have the old one |

## Codebase

**Repo:** `openssl/openssl` (targeted), `rustls/rustls`, and `cert-manager/cert-manager`

**Question to answer:** Trace a TLS 1.3 handshake through a real implementation: where is the key share generated, where is the certificate chain verified, and where is the hostname checked against the SANs? Then: how does cert-manager renew a certificate without dropping connections?

**Read, in order:**

1. `rustls/rustls/src/client/hs.rs` and `tls13/` — **start here, not with OpenSSL.** Rustls is modern, TLS 1.3-first, and dramatically more readable than OpenSSL. The handshake state machine is clear
2. `rustls/rustls/src/verify.rs` — certificate chain verification and hostname matching. This is the security-critical part and it is worth reading carefully
3. `openssl/ssl/statem/statem_clnt.c` — the same thing in OpenSSL, for contrast. Note how much harder it is to follow, and think about why that is a security concern in itself
4. `cert-manager/pkg/controller/certificates/` — the renewal lifecycle. How it decides when to renew and how the new certificate reaches pods

💡 The comparison between rustls and OpenSSL is the point of this session. OpenSSL's complexity is a direct consequence of supporting twenty years of legacy protocol versions and options. Heartbleed lived in that complexity. **Simplicity is a security property**, and reading both makes that concrete rather than abstract.

**Size:** 2 sessions.

## Exercise

**Drill 2.8 — Run your own CA**

Building a certificate authority yourself is the fastest way to understand chains permanently.

```
drills/02-tls/
├── ca/
│   ├── make_ca.sh        # root CA
│   ├── make_intermediate.sh
│   ├── issue.sh          # issue a server cert with SANs
│   └── issue_client.sh   # for mTLS
├── server/
│   ├── full_chain.py     # serves cert + intermediate
│   ├── broken_chain.py   # serves only the leaf
│   └── mtls.py
├── clients/
│   ├── test_clients.py   # browser, curl, python, go — who accepts what?
│   └── FINDINGS.md
├── handshake/
│   ├── capture.sh        # tcpdump a full handshake
│   ├── ANNOTATED.md      # every message, every field
│   └── resumption.py     # measure full vs resumed
├── cost/
│   ├── bench.py          # handshakes/sec vs bulk throughput
│   └── reuse.py          # connection reuse, measured
├── failures/
│   ├── expired.sh
│   ├── wrong_san.sh
│   ├── no_sni.py
│   └── verify_false.py   # demonstrate the MITM
└── README.md
```

**Part 1 — Build a CA.** Root, intermediate, server certificate with proper SANs. Serve it. Trust the root locally and confirm a clean connection.

**Part 2 — Break the chain.** Serve only the leaf certificate. Then test with: a browser, `curl`, Python `httpx`, and `openssl s_client`.

Build the table of who accepts it. **You will find the browser works and the others do not.** This is the "works in my browser" bug, produced deliberately, and after this you will diagnose it in thirty seconds forever.

**Part 3 — Annotate a handshake.** Capture a full TLS 1.3 handshake in Wireshark. Annotate every message and field. Then capture TLS 1.2 and compare the round trips visually.

Then capture a resumed handshake and confirm it is faster. Measure the difference.

**Part 4 — Measure the cost.** Benchmark: new connections per second (handshake-bound) versus bulk throughput on a warm connection (encryption-bound).

Then measure a realistic API workload with connection reuse off and on. **Report the ratio.** On a cross-region link it should be dramatic, and this number is the single best argument for connection pooling you can put in front of a colleague.

**Part 5 — Every failure mode.** Produce each deliberately and record the exact error message from Python, curl and a browser:

- Expired certificate
- Certificate with the hostname only in CN, not SAN
- Client that does not send SNI, against a multi-cert server
- Self-signed certificate with no trust
- Missing `ca-certificates` in a container

The error message table is the deliverable. Half of TLS debugging is recognising the message.

**Part 6 — The `verify=False` demonstration.** Set up a proxy that intercepts TLS with its own certificate. Show a client with `verify=True` refusing to connect and a client with `verify=False` connecting happily — and print the intercepted plaintext.

**Do this once.** Seeing your own credentials in the interceptor's log is more persuasive than any amount of documentation, and you will never write `verify=False` again.

**Part 7 — mTLS.** Issue client certificates. Configure a server to require them. Confirm a client without one is rejected. Then rotate the server certificate while connections are live and observe what happens to existing versus new connections.

**Done when:**
- Your broken-chain table shows the browser/non-browser split
- `ANNOTATED.md` covers a full TLS 1.3 handshake message by message
- You can quote your own connection-reuse ratio
- The error message table covers all five failure modes across three clients
- You have watched your own traffic in an interceptor's log
- mTLS works, and you know what certificate rotation does to live connections
