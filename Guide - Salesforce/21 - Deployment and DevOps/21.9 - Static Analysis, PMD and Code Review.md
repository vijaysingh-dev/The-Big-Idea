# Static Analysis, PMD and Code Review

## What automation should catch

Code review time is expensive and finite. Spending it on "you have a query in a loop" wastes it.

**Automate the mechanical; review the design.**

```
Automated:  SOQL in loops, missing sharing keywords, empty catch blocks,
            hardcoded Ids, unescaped output, injection paths, complexity,
            dead code, vulnerable dependencies

Reviewed:   is this the right approach, does it belong here, will it scale,
            is the automation consolidated, are the tests meaningful
```

## Salesforce Code Analyzer

The wrapper around several engines, and the standard tool.

```bash
sf plugins install @salesforce/sfdx-scanner

sf scanner run --target force-app --format table
sf scanner run --target force-app --severity-threshold 3 --format json --outfile results.json
sf scanner run dfa --target force-app --projectdir force-app --format table
```

**The engines it wraps:**

```
PMD             Apex and Visualforce rules
ESLint          JavaScript in LWC
RetireJS        known-vulnerable JavaScript libraries
Graph Engine    data-flow analysis across method calls
```

**`--severity-threshold 3`** fails the command on anything at severity 3 or above, which is what makes it a CI gate rather than a report.

## What PMD catches

The rules that matter, grouped by why.

**Performance and limits:**

```
OperationWithLimitsInLoop       SOQL, DML, or callouts inside a loop
AvoidSoqlInLoops
AvoidDmlStatementsInLoops
AvoidDebugStatements            System.debug costs CPU even when suppressed
CyclomaticComplexity            a method with too many branches
ExcessiveClassLength
```

**Security:**

```
ApexSharingViolations           no sharing keyword declared
ApexCRUDViolation               no CRUD or FLS check
ApexSOQLInjection               unbound variable in dynamic SOQL
ApexXSSFromURLParam
ApexOpenRedirect
ApexInsecureEndpoint            http:// rather than https://
```

**Correctness:**

```
EmptyCatchBlock                 a swallowed exception
AvoidHardcodedId
ApexUnitTestClassShouldHaveAsserts    a test with no assertions
ApexUnitTestMethodShouldHaveIsTestAnnotation
UnusedLocalVariable
```

**`ApexUnitTestClassShouldHaveAsserts` is worth enabling deliberately.** It catches the coverage-only test — the single most common quality failure in Salesforce codebases. See [[19.2 - Assertions and Test Design]].

## The Graph Engine

What PMD cannot do, and the reason to run `scanner run dfa` separately.

PMD analyses one method at a time. The Graph Engine traces **data flow across method calls**.

```java
@AuraEnabled
public static List<Warranty_Claim__c> search(String filterField, String filterValue) {
    return ClaimSelector.dynamicSearch(filterField, filterValue);
}
```

```java
public static List<Warranty_Claim__c> dynamicSearch(String field, String value) {
    // the injection is here, and the untrusted input arrived two calls ago
    String query = 'SELECT Id FROM Warranty_Claim__c WHERE ' + field + ' = \'' + value + '\'';
    return Database.query(query);
}
```

**PMD flags the concatenation. The Graph Engine traces it back to the `@AuraEnabled` entry point**, which is what makes it a real finding rather than a possible one.

```bash
sf scanner run dfa --target force-app --projectdir force-app --format table
```

It is slow — minutes on a large codebase — so it belongs on merge rather than on every commit.

**This is the analysis that most often produces a security review finding**, which makes running it before submission worth the time for anything packaged. See [[21.6 - Managed Packages and ISV Basics]].

## Custom rules

The default ruleset does not know your conventions.

```xml
<!-- config/pmd-ruleset.xml -->
<?xml version="1.0"?>
<ruleset name="Northwind Apex Rules"
         xmlns="http://pmd.sourceforge.net/ruleset/2.0.0">

    <description>Project rules, extending the Apex quickstart</description>

    <rule ref="category/apex/performance.xml/OperationWithLimitsInLoop"/>
    <rule ref="category/apex/security.xml/ApexSharingViolations"/>
    <rule ref="category/apex/bestpractices.xml/ApexUnitTestClassShouldHaveAsserts"/>
    <rule ref="category/apex/errorprone.xml/EmptyCatchBlock"/>

    <rule ref="category/apex/design.xml/CyclomaticComplexity">
        <properties>
            <property name="classReportLevel" value="40"/>
            <property name="methodReportLevel" value="10"/>
        </properties>
    </rule>

    <!-- a project convention: services take collections, not single records -->
    <rule name="ServiceMethodsTakeCollections"
          language="apex"
          class="net.sourceforge.pmd.lang.rule.XPathRule"
          message="Service methods should accept collections, not single sObjects">
        <properties>
            <property name="xpath">
                <value>
//UserClass[matches(@Image, '.*Service$')]
  //Method[@Visibility='PUBLIC']
    /FormalParameters/Parameter[matches(@Type, '^(Warranty_Claim__c|Account|Case)$')]
                </value>
            </property>
        </properties>
    </rule>
</ruleset>
```

```bash
sf scanner run --target force-app --pmdconfig config/pmd-ruleset.xml --format table
```

**A custom rule enforcing the collection signature** is worth writing, because it catches the single-record service method that invites a loop at the call site. See [[18.3 - Service Layer]].

Writing XPath rules is fiddly. Two or three well-chosen ones are worth the effort; twenty are not.

## Suppressing findings

```java
@SuppressWarnings('PMD.ApexCRUDViolation')
private static Decimal totalExposure(Id accountId) {
    // deliberately elevated: the aggregate is authorized, individual records are not
    return (Decimal) [
        SELECT SUM(Claim_Amount__c) total FROM Warranty_Claim__c WHERE Account__c = :accountId
    ][0].get('total');
}
```

**Every suppression needs a comment explaining why.** A codebase where suppressions accumulate without justification has disabled the tool rather than configured it.

**Suppress at the narrowest scope** — a method, not a class, and never a file.

**Review suppressions periodically.** A suppression added for a temporary reason two years ago is now permanent by default.

## ESLint for LWC

```json
{
  "extends": ["@salesforce/eslint-config-lwc/recommended"],
  "rules": {
    "@lwc/lwc/no-inner-html": "error",
    "@lwc/lwc/no-document-query": "error",
    "@lwc/lwc/no-async-operation": "warn",
    "no-console": ["warn", { "allow": ["error"] }]
  }
}
```

```bash
npm run lint
```

**`no-document-query`** catches the shadow DOM violation — `document.querySelector` cannot see inside a component. See [[14.15 - Styling, SLDS and Design Tokens]].

**`no-inner-html`** prevents an XSS vector.

**`no-async-operation`** flags `setTimeout` and `setInterval`, which are frequently leaked without a matching cleanup in `disconnectedCallback`.

## In the pipeline

```yaml
- name: Static analysis
  run: |
    sf scanner run \
      --target force-app \
      --pmdconfig config/pmd-ruleset.xml \
      --severity-threshold 3 \
      --format table

- name: Lint LWC
  run: npm run lint

- name: Data-flow analysis
  if: github.event_name == 'push'      # slow, so on merge rather than every commit
  run: sf scanner run dfa --target force-app --projectdir force-app --severity-threshold 3
```

**Fail the build on severity 3 and above.** A report nobody must act on is a report nobody reads.

**Introducing this to an existing codebase** produces hundreds of findings on day one. The approach that works:

**Gate the diff, not the codebase.** Fail only on findings in changed files.

```bash
CHANGED=$(git diff --name-only origin/main -- 'force-app/**/*.cls')
if [ -n "$CHANGED" ]; then
    sf scanner run --target "$CHANGED" --severity-threshold 3
fi
```

That stops the problem growing without requiring a remediation project, and the codebase improves as files are touched.

## What review is for

The things automation cannot judge.

**Is this the right place?** A validation rule that should be a service method. A trigger that should be a flow. Logic in a controller that belongs in a service.

**Does this duplicate something?** A new flow doing what an existing one does. A second trigger on an object. A query already in a selector.

**Will this scale?** Two hundred records, eight million rows, fifty concurrent users. Automation cannot see the data volume.

**Are the tests meaningful?** PMD checks that assertions exist; it cannot check that they verify the right thing. The mutation check — break a line, does a test fail — is a human judgement. See [[19.2 - Assertions and Test Design]].

**Is the automation consolidated?** One trigger per object, one flow per object per timing. See [[11.4 - One Trigger Per Object]].

**What breaks?** The dependency question, which only a person familiar with the org can answer.

## A review checklist

```
Design
  [ ] Right layer — trigger routes, handler dispatches, service does the work
  [ ] Not duplicating existing automation
  [ ] Consolidated with the existing trigger or flow

Bulk safety
  [ ] Methods take collections
  [ ] No SOQL, DML, or callouts in loops
  [ ] Tested with 200+ records, several children per parent

Security
  [ ] Sharing keyword declared
  [ ] WITH USER_MODE, as user
  [ ] stripInaccessible on inbound sObjects
  [ ] Ownership verified for client-supplied Ids

Correctness
  [ ] Change detection against oldMap where relevant
  [ ] Null guards on relationship traversal
  [ ] Empty-collection guards before DML
  [ ] Delete and undelete both handled

Tests
  [ ] Assertions with messages
  [ ] Bulk case
  [ ] Negative case
  [ ] runAs for permission-dependent behaviour

Deployment
  [ ] Manual post-deployment steps documented
  [ ] No unintended profile or layout changes in the diff
```

**The last line catches the most incidents.** A retrieval artefact in a profile removing permissions is invisible unless someone reads the diff.

## Metrics worth watching

```bash
sf scanner run --target force-app --format json --outfile scanner.json
jq '[.[] | .violations[]] | group_by(.ruleName) | map({rule: .[0].ruleName, count: length})' scanner.json
```

**Findings by rule, trended.** A rising count means the gate is not working or is being suppressed.

**Suppression count.** Rising is a warning.

**Coverage per class**, from `ApexCodeCoverageAggregate`. See [[19.10 - Code Coverage, Quality and CI Gates]].

**Average pull request size.** Large ones get reviewed badly, and the correlation with defects is real.

## What not to automate

**Formatting arguments.** Adopt Prettier with the Apex plugin and stop discussing it:

```json
{
  "plugins": ["prettier-plugin-apex"],
  "printWidth": 100,
  "tabWidth": 4
}
```

**Naming**, beyond a convention rule or two. Enforcing it mechanically produces more noise than value.

**Comment requirements.** Mandating a comment per method produces `// gets the claim` above `getClaim()`.

**Coverage as the only quality gate.** It measures execution, not verification.

## Practical guidance

**Automate the mechanical, review the design.**

**Fail the build on severity 3 and above.**

**Run the Graph Engine on merge**, not every commit — it is slow and it is the analysis that finds real injection paths.

**Gate the diff** when introducing analysis to an existing codebase.

**Enable `ApexUnitTestClassShouldHaveAsserts`.**

**Write two or three custom rules** for project conventions, not twenty.

**Require a comment on every suppression**, and review them periodically.

**Adopt a formatter** and stop arguing about style.

**Read the diff for unintended profile changes.**
