# Prefetching and Preloading

Fetching something before it is needed, so that when it is needed there is no wait. The whole discipline is about **predicting correctly** — a wrong prediction costs bandwidth, competes with what the user actually needs, and can make the page slower.

## Resource hints

```html
<link rel="dns-prefetch" href="https://cdn.example.com">
<link rel="preconnect" href="https://api.example.com" crossorigin>
<link rel="preload" as="font" href="/fonts/inter.woff2" type="font/woff2" crossorigin>
<link rel="modulepreload" href="/assets/main.js">
<link rel="prefetch" href="/assets/dashboard.js">
```

| Hint | What it does | Priority |
| --- | --- | --- |
| `dns-prefetch` | DNS lookup only | lowest |
| `preconnect` | DNS + TCP + TLS | — |
| `preload` | fetch a resource this page needs | high |
| `modulepreload` | fetch **and parse** an ES module and its dependencies | high |
| `prefetch` | fetch for a *future* navigation | lowest |

The distinction that matters: **`preload` is for the current page, `prefetch` is for the next one.** Using `prefetch` for something the current page needs gets it at the lowest priority, which is worse than not hinting at all.

`preconnect` saves roughly 100–300ms on a cross-origin request by doing the handshake early. It costs a held connection, so limit it to two or three critical origins — preconnecting to ten wastes resources and can slow the critical path.

## What actually needs preloading

The preload scanner already finds resources in the initial HTML very quickly ([[13.1 - The Critical Rendering Path]]). Preloading something it can already see adds nothing.

Preload only what the scanner **cannot** discover:

**Fonts**, which are found only after CSS is parsed *and* an element using them is matched:

```html
<link rel="preload" as="font" type="font/woff2" href="/fonts/inter.woff2" crossorigin>
```

`crossorigin` is mandatory even same-origin — fonts are always fetched in CORS mode, and omitting it causes a duplicate download ([[19.6 - Image and Asset Optimization]]).

**An LCP image set by CSS or injected by JavaScript.** The better fix is making it a real `<img>` in the HTML, which needs no preload at all.

**Critical resources loaded from within a module**, which the scanner cannot see.

Everything else is usually noise. Preloading ten resources dilutes priority so effectively that nothing is prioritized — the browser's own heuristics are good, and over-hinting fights them.

Chrome warns in the console when a preloaded resource goes unused within a few seconds, which is a useful audit signal.

## Prefetching routes on intent

The highest-value technique in a code-split application. Splitting moves the delay from initial load to navigation; prefetching recovers most of it ([[19.3 - Code Splitting and React.lazy]]).

```jsx
const preload = () => import("./Dashboard");

<Link
  to="/dashboard"
  onMouseEnter={preload}
  onFocus={preload}
  onTouchStart={preload}
>
  Dashboard
</Link>
```

Calling `import()` twice with the same specifier does not fetch twice — the module registry caches by resolved URL ([[08.2 - Dynamic Imports]]).

**Hover-to-click is typically 100–300ms**, which covers most chunk downloads on a reasonable connection. `onFocus` gives keyboard users the same benefit; `onTouchStart` fires before the click on mobile.

React Router provides this declaratively ([[23.5 - Lazy Routes]]):

```jsx
<Link to="/dashboard" prefetch="intent" />     // hover or focus
<Link to="/dashboard" prefetch="viewport" />   // when scrolled into view
<Link to="/dashboard" prefetch="render" />     // immediately
```

Next.js prefetches links in the viewport automatically, which is why navigation there usually feels instant.

## Prefetching data, not just code

A prefetched route chunk that then has to fetch its data has only solved half the problem:

```jsx
function ProductLink({ id }) {
  const queryClient = useQueryClient();

  const prefetch = () => {
    void import("./ProductPage");
    void queryClient.prefetchQuery(productQuery(id));
  };

  return <Link to={`/products/${id}`} onMouseEnter={prefetch}>...</Link>;
}
```

`prefetchQuery` respects `staleTime`, so a fresh entry is not refetched ([[24.7 - Caching Stale Time and Invalidation]]).

Prefetching both code and data on hover is what makes a navigation feel like it has no loading state at all.

## Prediction strategies

**Hover and focus** — high confidence, short lead time. The default.

**Viewport** — a link scrolled into view is more likely to be clicked. Moderate confidence, longer lead time. Good for link-heavy pages, wasteful on a page with fifty links.

**The obvious next step** — page 2 of paginated results, the next item in a wizard, the next image in a gallery. High confidence when the flow is linear.

```jsx
useEffect(() => {
  if (data?.hasMore) {
    queryClient.prefetchQuery(productsQuery({ page: page + 1 }));
  }
}, [page, data?.hasMore]);
```

**Analytics-driven** — if 80% of users on the pricing page go to signup, prefetch it. Requires data and only pays off on high-traffic paths.

**Idle time** — prefetch during a lull, at the lowest priority:

```js
requestIdleCallback(() => import("./LikelyNext"), { timeout: 5000 });
```

The `timeout` matters; under sustained load `requestIdleCallback` may never fire ([[01.7 - The Rendering Cycle]]).

## Speculation Rules

The newest and most powerful mechanism — the browser prerenders a full page, not just fetches assets:

```html
<script type="speculationrules">
{
  "prerender": [{
    "where": { "href_matches": "/products/*" },
    "eagerness": "moderate"
  }],
  "prefetch": [{
    "where": { "href_matches": "/*" },
    "eagerness": "conservative"
  }]
}
</script>
```

`eagerness` values: `immediate`, `eager`, `moderate` (hover ~200ms), `conservative` (pointerdown).

Prerendering executes the target page fully in a hidden tab, so navigation is genuinely instant — near-zero LCP. The cost is running a whole page speculatively, so it must be restricted to high-confidence targets.

Two operational cautions: analytics can double-count prerendered pages unless the code checks `document.prerendering`, and prerendering a page with side effects (a POST on load, a view counter) causes real problems.

Chromium-only at present, so treat it as an enhancement.

## Respect the user's constraints

```ts
const conn = navigator.connection;
const shouldPrefetch =
  conn?.effectiveType?.includes("4g") &&
  !conn.saveData;

if (shouldPrefetch) preload();
```

`saveData` reflects an explicit user preference for reduced data usage. Ignoring it on a metered connection is a real cost to that user.

For a product with users across varied network conditions — which describes most consumer products in India — gating prefetch on connection quality is not a nicety.

```css
@media (prefers-reduced-data: reduce) { }
```

## When it hurts

Prefetching is not free:

**Bandwidth competition.** Prefetched resources compete with what the user actually needs. `prefetch` is lowest priority for this reason, but `preload` is not.

**Wasted data.** A wrong prediction is pure waste, and on a metered connection it is money.

**Server load.** Prefetching data multiplies backend requests by the miss rate.

**Cache pressure.** Prefetched entries can evict useful ones.

The rough rule: **prefetch when confidence exceeds about 50%.** Below that, the expected cost outweighs the expected saving. Hover clears that bar easily; "every link on the page" does not.

## Measuring

Chrome DevTools' Network panel shows prefetched resources and whether they were used. The console warns about unused preloads.

The real measure is field data: did p75 navigation latency actually improve after adding prefetching, and did total bytes transferred increase disproportionately ([[28.13 - Frontend Observability]])?

Both numbers matter. A prefetch strategy that halves navigation latency while doubling data usage is a bad trade for a mobile-heavy audience.

## How senior engineers actually use this

**They preload only what the scanner cannot find** — fonts, and an LCP image that is not a plain `<img>`.

**They prefetch route code and data together on hover and focus.**

**They gate prefetching on `saveData` and connection quality.**

**They keep preconnect to two or three origins**, since over-hinting dilutes priority.

**They measure both latency and bytes**, not just the improvement.

## Common pitfalls

- `prefetch` used for a current-page resource, getting lowest priority.
- Preloading a font without `crossorigin`, causing a duplicate fetch.
- Preloading ten resources and prioritizing nothing.
- Prefetching every link on a link-heavy page.
- Ignoring `saveData` and metered connections.
- Prerendering pages with side effects, or double-counting analytics.
- Prefetching code but not data, leaving half the wait.
- Adding hints without measuring the result.

## Interview angle

"How would you make navigation feel instant" leads here. The core answer is prefetching route code and data on hover or focus, exploiting the 100–300ms gap between intent and click, with the module registry deduplicating repeat calls. Then the distinction between `preload` (current page, high priority) and `prefetch` (next navigation, lowest priority), and the point that preloading is only useful for resources the preload scanner cannot discover. Raising `saveData` and the confidence threshold shows you weigh the cost rather than treating prefetching as free.
