# Connection Pools and Limits

#backend #python #production

> **In one line:** Every pool in your system multiplies by every process you run, and the total has to fit inside what the dependency can accept — get that arithmetic wrong and you find out during your busiest hour.

---

## The Idea

Opening a connection is expensive. TCP handshake, TLS handshake, authentication, session setup. For Postgres that is 20–50ms and a new server-side process. Doing it per request is unacceptable.

So you keep connections open and reuse them. That is a pool.

The problem is that a pool is a **fixed resource with a queue in front of it**, and almost nobody does the arithmetic:

```
total connections = replicas × workers-per-replica × pool-size
```

```
10 pods × 4 uvicorn workers × pool of 20 = 800 connections
Postgres max_connections = 100
```

Your service works fine in staging with one pod and falls over the moment you scale.

⚠️ **This is one of the most common production incidents in Python backends, and it is pure arithmetic.** Doing the multiplication before you deploy takes 30 seconds.

---

## How Pools Work

```
Your code ──► acquire() ──► [idle: 3] [in use: 17] [max: 20]
                                │
                                └── all busy? wait in queue
                                      └── waited too long? raise PoolTimeout
```

Four states matter:

| State | Meaning |
|---|---|
| Idle | Open, unused, ready |
| In use | Checked out by a task |
| Waiting | Tasks queued for a connection |
| Overflow | Temporary connections above the base size, closed after use |

The metric that tells you the truth is **wait time**, not pool size. A pool of 5 with zero wait is perfectly sized. A pool of 100 with 200ms of wait is too small.

## Sizing

### The formula

Little's Law:

```
connections needed = arrival rate × time each connection is held
```

100 requests/second, each holding a connection for 20ms:

```
100 × 0.02 = 2 connections
```

Two. Not twenty. People are consistently shocked by this.

Add headroom for variance and latency spikes — a factor of 2 to 4 is reasonable. So 5–8, not 20.

💡 **A pool larger than needed does not make anything faster. It makes things slower**, because more concurrent queries mean more contention inside the database — more lock waits, more context switching, more memory per connection. The classic result from HikariCP's documentation is that reducing a pool from 50 to 10 *improved* throughput.

### Postgres specifically

Each Postgres connection is a separate OS process with its own memory (`work_mem` and friends). A few hundred is a lot.

```
recommended max ≈ (core_count × 2) + effective_spindle_count
```

For an 8-core database server that is roughly 20 active connections. Beyond that you are queueing inside the database instead of in your app, which is worse because you cannot see it.

This is what PgBouncer is for: thousands of client connections multiplexed onto a few dozen real ones. See [[06.9 - Connection Pooling and PgBouncer]].

### Work the arithmetic backwards

```
Postgres max_connections            100
  reserved for superuser             -3
  reserved for migrations/admin      -7
  available to apps                  90
  ÷ number of services (3)           30 per service
  ÷ replicas (5)                      6 per replica
  ÷ uvicorn workers (2)               3 per worker
```

Pool size 3, max_overflow 2. That looks alarmingly small and it is almost certainly correct.

## The Libraries

### asyncpg

```python
pool = await asyncpg.create_pool(
    dsn,
    min_size=2,
    max_size=10,
    max_inactive_connection_lifetime=300,
    command_timeout=10,
    timeout=5,                    # how long to wait for a free connection
)
```

⚠️ **`timeout` and `command_timeout` are different things and both matter.** `timeout` bounds waiting for the pool; `command_timeout` bounds the query itself. Without the first, an exhausted pool makes requests hang forever instead of failing fast.

### SQLAlchemy async

```python
engine = create_async_engine(
    dsn,
    pool_size=5,
    max_overflow=5,           # burst capacity above pool_size
    pool_timeout=5,
    pool_recycle=1800,        # close connections older than 30 min
    pool_pre_ping=True,       # test before handing out
)
```

`pool_recycle` and `pool_pre_ping` exist because of a specific failure: a firewall, load balancer or cloud database silently drops idle TCP connections. Your pool still thinks they are alive and hands out a dead socket. `pool_pre_ping` costs one round trip and eliminates a whole class of intermittent errors.

⚠️ **With PgBouncer in transaction mode, disable client-side statement caching** (`prepared_statement_cache_size=0` for asyncpg, `statement_cache_size` settings elsewhere). Otherwise your prepared statement was created on a server connection you no longer have, and you get errors that only appear under concurrency.

### httpx

```python
client = httpx.AsyncClient(
    limits=httpx.Limits(
        max_connections=100,
        max_keepalive_connections=20,
        keepalive_expiry=30,
    ),
    timeout=httpx.Timeout(connect=2, read=10, write=5, pool=3),
)
```

💡 **httpx's four separate timeouts are one of its best features and most people set one number.** `connect` catches an unreachable host quickly. `read` catches a slow response. `pool` catches your own exhaustion. Setting only a total timeout means you cannot tell those apart in your metrics — and they need completely different fixes.

⚠️ **Create one client for the app lifetime, not one per request.** A new client per request means a new pool, no connection reuse, and a full TLS handshake every time. This single mistake can triple your outbound latency.

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(limits=..., timeout=...)
    yield
    await app.state.http.aclose()
```

### redis.asyncio

```python
pool = redis.ConnectionPool.from_url(
    url,
    max_connections=50,
    socket_timeout=5,
    socket_connect_timeout=2,
    health_check_interval=30,
)
```

⚠️ **`socket_timeout` defaults to `None`**, meaning a Redis that stops responding will hang your task forever rather than raising. Always set it. This one default has caused a lot of outages.

Also note: blocking commands (`BLPOP`, `XREAD BLOCK`) hold a connection for their whole duration. If you use them, they need their own pool, or they will consume your entire cache pool.

## Timeouts Everywhere

Every layer needs a bound, and they must nest.

```
Client-side total budget         30s
└── Your endpoint timeout        10s
    ├── Pool acquire timeout      2s
    ├── Query timeout             5s
    └── HTTP call to service B    3s
        ├── connect               1s
        └── read                  2s
```

The inner budgets must sum to less than the outer, or the outer is decorative.

⚠️ **A missing timeout is not "no limit" — it is "the limit is whatever TCP does", which is often 15 minutes.** Fifteen minutes of a held connection, a held pool slot, and a held worker. One unresponsive dependency with no timeout will exhaust every pool you have.

Audit rule: every network call in your codebase has an explicit timeout, and you can name the number.

## In Production

### Symptoms of exhaustion

| Symptom | What it looks like |
|---|---|
| Latency cliff at a specific concurrency | Flat, then vertical, at exactly your pool size |
| `PoolTimeout` / `QueuePool limit ... overflow` | The honest error. Be grateful for it |
| Requests hang forever | The same problem with no acquire timeout set |
| `FATAL: sorry, too many clients already` | You did the multiplication wrong |
| p99 terrible, p50 fine | Some requests wait for a connection, most do not |
| Latency fine on one pod, awful at 10 | Classic pool arithmetic failure |

💡 **The distinguishing signature is a latency graph that is flat and then vertical.** Genuine capacity limits curve upward gradually. A pool limit is a wall, because it is a hard queue. If your graph has a corner in it, look for a pool.

### The metrics to export

```python
pool_size.set(pool.get_size())
pool_idle.set(pool.get_idle_size())
pool_waiting.set(len(pool._queue._getters))     # library-specific

# The one that actually matters
start = time.perf_counter()
async with pool.acquire() as conn:
    pool_wait_seconds.observe(time.perf_counter() - start)
    ...
```

Alert on **acquire wait time p99 > 50ms**, not on pool utilisation. Utilisation at 100% with zero wait is a perfectly healthy, correctly sized pool.

### Connections held too long

```python
async with pool.acquire() as conn:
    user = await conn.fetchrow(query)        # 5ms
    profile = await http.get(url)            # 200ms ← holding the DB connection
    await conn.execute(update, profile)      # 5ms
```

That connection is checked out for 210ms to do 10ms of database work. Your effective pool just shrank by 20x.

```python
async with pool.acquire() as conn:
    user = await conn.fetchrow(query)

profile = await http.get(url)                # connection released

async with pool.acquire() as conn:
    await conn.execute(update, profile)
```

⚠️ Two acquisitions means the two writes are no longer in one transaction. If you need atomicity you must hold it — but then you must accept a larger pool, and you should know you made that trade. This is a genuine design decision, not an oversight, and being able to articulate it is a senior-level answer.

### Transactions hold longer than you think

```python
async with conn.transaction():
    await conn.execute(update_a)
    await slow_external_call()          # transaction open, locks held
    await conn.execute(update_b)
```

Now you are holding a connection **and** database locks across a network call. Other transactions block on those locks. This is how one slow third-party API turns into a database-wide stall. See [[06.8 - Locking and Deadlocks]].

**Rule: no network calls inside a transaction. Ever.**

### Fork breaks pools

```python
pool = create_pool()          # module level — created before fork
```

With `--workers 4`, uvicorn forks. Every child inherits the same file descriptors. Multiple processes now read and write the same socket, and you get corrupted protocol state — errors that look like data corruption and are impossible to reproduce.

Create pools inside the lifespan handler, which runs per worker after the fork.

## Codebase

**Repo:** `MagicStack/asyncpg`, `encode/httpx`, and `brettwooldridge/HikariCP` (docs)

**Question to answer:** When a pool is exhausted and 50 tasks are waiting, in what order are they served? Is it fair (FIFO) or arbitrary? And what happens to a waiter that is cancelled while queued — does it release its place cleanly, or can it leak?

**Read, in order:**

1. `asyncpg/pool.py` — `Pool.acquire`, `_acquire`, `release`. Look at the queue and the cancellation path
2. `httpx/_transports/default.py` then `httpcore/_async/connection_pool.py` — how a request finds or creates a connection, and how keepalive expiry works
3. `sqlalchemy/pool/base.py` — `QueuePool`. Read `_do_get` and the overflow logic. Note how `pool_pre_ping` is implemented
4. `redis/asyncio/connection.py` — `ConnectionPool.get_connection`. Note the health check

**Then read prose, not code:** HikariCP's "About Pool Sizing" wiki page. It has the best empirical argument anywhere for small pools, with graphs. It is Java, and it is entirely applicable.

**Size:** 1 session.

**Part 1 — Find the real optimum.** One service, one Postgres. Sweep pool size from 1 to 200. Chart throughput and p99 against pool size.

You should find a peak at a surprisingly small number and a decline after it. Note where the peak is and compare it to what Little's Law predicted.

**Part 2 — The cliff.** Set pool size to 5. Ramp concurrency from 1 to 50. Chart p99.

Find the corner. Then run it with no `pool_timeout` and show requests hanging instead of failing. Chart both. This is the difference between an incident that self-heals and one that requires a restart.

**Part 3 — Holding time.** Implement `bad.py` and `good.py`. Same work, same pool size. Measure maximum throughput of each.

Then `txn_lock.py`: an external call inside a transaction. Use toxiproxy to make it slow, and watch *other* endpoints that touch the same rows block. Capture `pg_locks` during the incident.

**Part 4 — The multiplication incident.** Compose file: 4 replicas × 2 workers × pool 20 against a Postgres with `max_connections=50`. Start it. Watch it fail.

Fix it three ways and compare: reduce pool size, add PgBouncer, reduce replicas. Write which you would choose in production and why.

**Part 5 — Four timeouts.** Use toxiproxy to trigger each httpx timeout independently: an unreachable host (connect), a slow first byte (read), a slow body (read), an exhausted pool (pool). Show that each raises a distinct exception, and build a metric labelled by timeout type.

**Done when:**
- Your part 1 chart has a clear peak, and you can explain the decline
- Your part 2 chart shows a corner, not a curve, and you know the exact concurrency where it happens
- `good.py` handles measurably more throughput than `bad.py` with the same pool
- Part 4's `FINDINGS.md` recommends one fix with reasoning
- Your metric distinguishes all four timeout types
