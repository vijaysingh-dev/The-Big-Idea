# AbortController and Cancellation

Promises cannot be cancelled. Once created, a promise will settle, and nothing you do stops the underlying work. `AbortController` is the platform's answer: a separate signalling channel that operations can *choose* to listen to.

## The mechanism

```js
const controller = new AbortController();
const { signal } = controller;

fetch("/api/data", { signal })
  .then(res => res.json())
  .catch(err => {
    if (err.name === "AbortError") return;  // expected, not a failure
    throw err;
  });

controller.abort();
```

- **`AbortController`** — the object you hold to trigger cancellation.
- **`AbortSignal`** — the read-only object you hand to operations. It has `aborted`, `reason`, and fires an `abort` event.

Aborting is **one-way and permanent**. A controller cannot be reset; create a new one per operation.

```js
signal.aborted;        // boolean
signal.reason;         // DOMException "AbortError", or your custom reason
signal.throwIfAborted(); // throws if already aborted
controller.abort(new Error("user navigated away")); // custom reason
```

## What actually supports it

`AbortSignal` is a convention, not magic. An operation must explicitly honour it.

Supported natively: `fetch`, `addEventListener`, `ReadableStream`, `WritableStream`, `IndexedDB` transactions in some engines, `navigator.locks`, and — usefully — `AbortSignal` itself via `AbortSignal.any()`.

Not supported: `setTimeout`, `XMLHttpRequest` (has its own `.abort()`), most third-party libraries unless they document it, and any promise you wrote yourself unless you wire it up.

## The listener shortcut

This one is underused and removes a lot of cleanup code:

```js
const controller = new AbortController();

window.addEventListener("resize", onResize, { signal: controller.signal });
window.addEventListener("scroll", onScroll, { signal: controller.signal });
element.addEventListener("click", onClick, { signal: controller.signal });

controller.abort(); // removes all three at once
```

No need to keep handler references for `removeEventListener` ([[02.8 - call apply and bind]] explains why identity matters there). In React this collapses effect cleanup to a single line ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

## Making your own operations abortable

```js
function delay(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);

    const id = setTimeout(resolve, ms);

    signal?.addEventListener("abort", () => {
      clearTimeout(id);
      reject(signal.reason);
    }, { once: true });
  });
}
```

Three things every abortable wrapper needs: check `aborted` up front (the signal may already have fired), clean up the underlying resource on abort, and use `{ once: true }` so the listener does not leak.

For a long computation, check between chunks:

```js
async function processLarge(items, { signal }) {
  for (let i = 0; i < items.length; i++) {
    if (i % 500 === 0) {
      signal?.throwIfAborted();
      await new Promise(r => setTimeout(r, 0)); // yield to the event loop
    }
    process(items[i]);
  }
}
```

## Timeouts and combining signals

```js
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });
```

`AbortSignal.timeout(ms)` produces a signal that aborts itself, with reason `TimeoutError` rather than `AbortError` — so you can distinguish "timed out" from "user cancelled".

To respect both a user cancellation and a timeout:

```js
const userController = new AbortController();

const signal = AbortSignal.any([
  userController.signal,
  AbortSignal.timeout(5000),
]);

await fetch(url, { signal });
```

`AbortSignal.any` fires when any input signal fires. Before it existed, people wired listeners manually between controllers.

## The React pattern

```js
useEffect(() => {
  const controller = new AbortController();

  (async () => {
    try {
      const res = await fetch(`/api/search?q=${query}`, { signal: controller.signal });
      if (!res.ok) throw new HttpError(res.status);
      setResults(await res.json());
    } catch (err) {
      if (err.name === "AbortError") return;
      setError(err);
    }
  })();

  return () => controller.abort();
}, [query]);
```

This solves two problems at once. It stops setting state after unmount, and — the more important one — it fixes the **race condition** where an older request resolves after a newer one:

```
type "re"  -> request A sent
type "rea" -> request B sent, A aborted
A would have resolved last and overwritten B's results
```

Without abort, a `cancelled` boolean flag fixes the state overwrite but still wastes the network request. Abort fixes both.

## Cancellation in practice with data libraries

TanStack Query passes an `AbortSignal` to every query function automatically:

```js
useQuery({
  queryKey: ["search", query],
  queryFn: ({ signal }) => fetch(`/api/search?q=${query}`, { signal }).then(r => r.json()),
});
```

Queries are aborted when the component unmounts or the key changes. This is one of the concrete reasons to use a data library rather than raw effects ([[24.6 - TanStack Query Fundamentals]]).

Axios supports signals too (`axios.get(url, { signal })`), replacing its old `CancelToken` API.

## How senior engineers actually use this

**They abort on every dependency change, not just unmount.** Search-as-you-type, filtered tables, and paginated views all produce request races. Aborting the previous request is the standard fix.

**They treat `AbortError` as normal control flow.** It should never reach an error boundary, a toast, or an error-reporting service. Filtering it out is the first thing in every catch block that handles an abortable operation.

**They thread signals through their API layer.** Every function in the data layer accepts an optional `signal` and forwards it, so cancellation composes from the component down to the network call ([[24.3 - Retries Timeouts and Cancellation]]).

**They use signals for non-network cleanup too.** Long computations, polling loops, WebSocket subscriptions and animation loops all take a signal, which makes teardown uniform across the codebase.

## Common pitfalls

- Reusing an aborted controller. It stays aborted forever.
- Treating `AbortError` as a real failure and showing the user an error.
- Assuming abort stops the server. The request may already have been processed; abort only stops the client from waiting. For non-idempotent operations like payments, this matters ([[15.1 - HTTP Fundamentals]]).
- Forgetting `{ once: true }` on the `abort` listener, leaking a listener per call.
- Not checking `signal.aborted` at the start, so an already-aborted signal is ignored.
- Aborting a shared/deduplicated request and cancelling it for other consumers too.

## Interview angle

"How do you cancel a fetch request" and "how do you handle race conditions in search-as-you-type" both land here. Explain that promises are not cancellable, that `AbortController` is a separate signalling channel, and that the operation must opt in. Then describe the search race concretely — an older response arriving after a newer one — and show abort-on-dependency-change as the fix. Mentioning `AbortSignal.timeout` and `AbortSignal.any` shows current knowledge.
