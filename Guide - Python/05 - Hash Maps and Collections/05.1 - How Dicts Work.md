# How Dicts Work

#python #dict #hashing #data-structures

> **In one line:** A dict is a hash table: it hashes the key to pick a slot, probes until it finds the key or an empty slot, and resizes when it gets two-thirds full. Since 3.6 it is also compact and keeps insertion order. Lookups are O(1) on average because hashing spreads keys evenly, and only as long as it does.

---

## Why Dicts Matter So Much

Python runs on dicts. Module globals, class attributes, instance attributes (mostly), keyword arguments, `sys.modules`, JSON objects: all dicts. Understanding them explains a surprising amount of the language's performance.

---

## Hashing in One Paragraph

`hash(key)` turns a key into an integer. Equal keys **must** have equal hashes. Different keys should *usually* have different hashes. The dict uses the low bits of the hash to choose a slot in a table of size 2ⁿ.

```python
hash(42)          # 42 — small ints hash to themselves
hash("user:42")   # randomised per process (PYTHONHASHSEED) to prevent hash-flooding attacks
hash((1, "a"))    # tuples hash their contents
hash([1, 2])      # TypeError: unhashable type: 'list'
```

💡 **String hashes are randomised per process**, since 3.3. An attacker who could predict hashes could send a JSON body whose keys all collide, turning O(1) inserts into O(n) and the whole request into O(n²). It is a real attack, from 2011. Side effect: never persist `hash(str)` or use it to shard data across processes. Use a stable hash such as `hashlib.blake2b` or `zlib.crc32`.

## The Layout: Compact Dict (3.6+)

```python
d = {"name": "ana", "age": 31, "city": "Lima"}
```

```
indices (sparse, 1 byte per slot when small)    entries (dense, insertion order)
┌───┬───┬───┬───┬───┬───┬───┬───┐               ┌──────────┬────────┬────────┐
│ – │ 1 │ – │ – │ 0 │ – │ 2 │ – │               │ hash     │ key    │ value  │
└───┴───┴───┴───┴───┴───┴───┴───┘           0   │ h("name")│ "name" │ "ana"  │
  slot = hash & 7, then probe                1   │ h("age") │ "age"  │ 31     │
                                             2   │ h("city")│ "city" │ "Lima" │
                                                 └──────────┴────────┴────────┘
```

- A small **indices** array is the actual hash table. Each slot holds an index into **entries**, or "empty", or "deleted".
- **Entries** are stored densely in insertion order.

That design gives you two things at once: **less memory** (the big entries array has no gaps) and **insertion order for free**. Order was an implementation detail in 3.6 and a language guarantee from 3.7.

## Lookup and Collisions

```
lookup(key):
    h = hash(key)
    i = h & mask
    loop:
        idx = indices[i]
        if idx is EMPTY: → KeyError
        entry = entries[idx]
        if entry.key is key or (entry.hash == h and entry.key == key): → found
        i = next probe (perturbed by higher bits of h)
```

Note the comparison order: **identity first**, then hash, then `==`. Interned strings make most lookups an identity hit.

CPython uses **open addressing**: on collision it probes other slots in the same table (with a pseudo-random sequence that mixes in more hash bits), instead of chaining lists. Deleting an entry leaves a "dummy" marker so probe chains are not broken.

### Resizing

When the table is about **two-thirds full**, the dict allocates a bigger table and reinserts everything. That costs O(n), but it happens rarely, so insertion is **amortised O(1)**. Dicts do not shrink when you delete; they compact on the next resize.

---

## Costs

| Operation | Average | Worst case |
|---|---|---|
| `d[k]`, `d[k] = v`, `del d[k]`, `k in d` | O(1) | O(n), when hashes collide |
| Iteration | O(n) | |
| `d.copy()`, `dict(d)` | O(n) | |
| Memory | ~ 100+ bytes overhead, plus ~ 24–30 bytes per entry, plus the key and value objects | |

```python
import sys
sys.getsizeof({})                         # 64
sys.getsizeof({i: i for i in range(1000)})  # ~36 KB, not counting the int objects
```

⚠️ **A million small dicts is a lot of memory.** Rows loaded as dicts from an ORM or JSON easily cost 10x the raw data size. For large homogeneous records, use tuples, `__slots__` classes ([[06.4 - Slots]]), dataclasses with `slots=True`, or columnar storage (Polars, Arrow, numpy).

---

## Instance `__dict__` and Key Sharing

Every normal instance stores attributes in a dict. CPython saves memory with **key-sharing dicts** (PEP 412): instances of the same class share one keys table and store only their values. This works best when `__init__` assigns the same attributes in the same order. Adding attributes ad hoc to some instances breaks sharing for them. Since 3.11–3.13, CPython goes further and stores values inline in the object, materialising the `__dict__` only when you ask for it.

## Dict API Worth Knowing

```python
d.get(k, default)                 # no KeyError
d.setdefault(k, []).append(x)     # get, or insert the default and return it
d.pop(k, None)                    # remove if present
d | other, d |= other             # merge (3.9+); right side wins
{**a, **b}                        # merge into a new dict
d.keys() & other.keys()           # views support set operations
for k, v in d.items(): ...
dict.fromkeys(keys, 0)            # careful: the same value object for every key
list(d)                           # keys, in insertion order
next(iter(d))                     # first key inserted
```

⚠️ **Do not mutate a dict while iterating over it.** Adding or removing keys raises `RuntimeError: dictionary changed size during iteration`. Iterate over `list(d)` or build a new dict.

⚠️ `dict.fromkeys(keys, [])` gives **every key the same list**, the shared-reference trap from [[01.2 - Mutability Equality and Copying]]. Use `{k: [] for k in keys}`.
