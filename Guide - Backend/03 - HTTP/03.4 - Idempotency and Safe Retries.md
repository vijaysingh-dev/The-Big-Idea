# Idempotency and Safe Retries

#backend #http #reliability #distributed-systems

> **In one line:** A failed request tells you nothing about whether the work happened, so the only safe design is one where doing it twice is the same as doing it once.

---

## The Idea

```
Client → POST /payments → Server processes it → response lost in the network
Client sees: timeout
```

Did the payment go through? The client cannot know. There is no way to find out from the failure itself.

Two options:

1. **Retry** and risk charging twice
2. **Do not retry** and risk the payment never happening

Both are wrong. The answer is to change the problem: make retrying safe.

💡 **This is the single most important idea in distributed systems reliability.** Networks fail partially — a request can succeed while the response is lost. Every distributed system must handle this, and idempotency is how.

---

## The Two-Generals Problem, Practically

You cannot achieve certainty about a remote operation's outcome through an unreliable channel. This is not an engineering limitation; it is proven impossible.

So systems do not try. They pick a delivery guarantee and design around it:

| Guarantee | Means | Cost |
|---|---|---|
| **At-most-once** | Never retry | Work can be lost |
| **At-least-once** | Always retry until confirmed | Work can be duplicated |
| **Exactly-once** | Impossible over an unreliable network | — |

⚠️ **"Exactly-once delivery" does not exist.** What systems that claim it actually provide is **at-least-once delivery plus deduplication**, producing *exactly-once effects*. Kafka's "exactly-once semantics" is this. So is Stripe's idempotency. So is your task queue.

Saying this precisely in an interview is a strong signal. The sentence is: *"Exactly-once delivery is impossible, so you build at-least-once delivery with idempotent handlers, which gives you exactly-once effects."*

## Naturally Idempotent Operations

Some operations are already safe. Recognise them and stop worrying.

```python
# Idempotent — absolute assignment
user.status = "active"
await repo.set_status(user_id, "active")

# NOT idempotent — relative change
user.balance -= 100
await repo.increment_views(doc_id)

# Idempotent — set semantics
await repo.add_tag(doc_id, "urgent")     # adding twice = one tag

# NOT idempotent — list semantics
await repo.append_comment(doc_id, text)  # twice = two comments

# Idempotent — DELETE
await repo.delete(doc_id)                # already gone? still fine, still 204
```

💡 **The pattern: absolute is idempotent, relative is not.** "Set balance to 500" is safe to repeat. "Subtract 100" is not. Where you can express an operation absolutely, do — it removes the problem entirely rather than managing it.

## Idempotency Keys

For operations that are not naturally idempotent, the client supplies a key.

```http
POST /payments
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7
Content-Type: application/json

{"amount": 5000, "currency": "usd"}
```

The server remembers the key and its result. A repeat with the same key returns the stored result without doing the work again.

### The naive version, and why it is broken

```python
async def create_payment(key: str, data: PaymentIn):
    if await cache.exists(key):              # ← race window
        return await cache.get(key)
    result = await process_payment(data)
    await cache.set(key, result)
    return result
```

⚠️ **Two concurrent retries both pass the check before either writes.** Both process the payment. This is the exact failure the mechanism was meant to prevent, and it happens precisely when it matters — during a network problem, when clients are retrying aggressively.

### The correct version

Three states, and an atomic claim.

```python
from enum import Enum

class KeyState(str, Enum):
    IN_PROGRESS = "in_progress"
    COMPLETED = "completed"
    FAILED = "failed"
```

```sql
CREATE TABLE idempotency_keys (
    key             TEXT PRIMARY KEY,
    org_id          UUID NOT NULL,
    endpoint        TEXT NOT NULL,
    request_hash    TEXT NOT NULL,
    state           TEXT NOT NULL,
    response_status INT,
    response_body   JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    locked_until    TIMESTAMPTZ
);
```

```python
async def with_idempotency(key: str, org_id: UUID, endpoint: str,
                           request_body: dict, handler):
    request_hash = hashlib.sha256(
        json.dumps(request_body, sort_keys=True).encode()
    ).hexdigest()

    async with db.transaction():
        row = await db.fetchrow(
            """
            INSERT INTO idempotency_keys
                (key, org_id, endpoint, request_hash, state, locked_until)
            VALUES ($1, $2, $3, $4, 'in_progress', now() + interval '60 seconds')
            ON CONFLICT (key) DO UPDATE
                SET locked_until = CASE
                    WHEN idempotency_keys.state = 'in_progress'
                     AND idempotency_keys.locked_until < now()
                    THEN now() + interval '60 seconds'
                    ELSE idempotency_keys.locked_until
                END
            RETURNING *
            """,
            key, org_id, endpoint, request_hash,
        )

    if row["request_hash"] != request_hash:
        raise HTTPException(422, "idempotency key reused with a different body")

    if row["state"] == KeyState.COMPLETED:
        return JSONResponse(row["response_body"], status_code=row["response_status"])

    if row["state"] == KeyState.IN_PROGRESS and row["locked_until"] > now():
        raise HTTPException(409, "request already in progress")

    result = await handler()

    await db.execute(
        """UPDATE idempotency_keys
           SET state = 'completed', response_status = $2, response_body = $3
           WHERE key = $1""",
        key, result.status_code, result.body,
    )
    return result
```

The pieces that matter:

| Piece | Why |
|---|---|
| `INSERT ... ON CONFLICT` | Atomic claim. No check-then-act race |
| `request_hash` | Catches a client reusing a key with different content — a client bug you want to surface loudly |
| `locked_until` | A crashed request does not block the key forever |
| Storing the response | A retry gets the *same* answer, not a fresh one |
| `409` on concurrent duplicate | Honest: "I am already doing this, ask again shortly" |
| Scoped by `org_id` | One tenant cannot guess or collide with another's keys |

⚠️ **The `request_hash` check catches a real and dangerous client bug**: reusing an idempotency key for a genuinely different request. Without it, the client sends a $10 payment, gets back the cached result of a $5000 payment, and everyone is confused for a long time.

### Scoping the write to the same transaction

The strongest version puts the key write in the **same transaction** as the effect:

```python
async with db.transaction():
    payment = await create_payment_row(data)
    await mark_key_completed(key, payment)
```

Now the key and the effect commit or roll back together. If the process dies between them, neither happened.

This is the same reasoning as the outbox pattern — [[09.3 - The Outbox Pattern]].

## Retry Policy

Idempotency makes retrying safe. It does not make retrying free.

### What to retry

| Failure | Retry? |
|---|---|
| Connection refused | **Yes** — nothing happened |
| Connection reset before the request was sent | **Yes** |
| Timeout | **Only if idempotent.** The work may have happened |
| `500` | Only if idempotent |
| `502` / `503` / `504` | **Yes**, with backoff. Honour `Retry-After` |
| `429` | **Yes**, honour `Retry-After` exactly |
| `400` / `422` | **No.** It will fail identically |
| `401` | No — refresh credentials first, then retry once |
| `403` / `404` / `409` | No |

### Exponential backoff with jitter

```python
async def retry(fn, attempts=4, base=0.2, cap=10.0):
    for attempt in range(attempts):
        try:
            return await fn()
        except RetryableError as e:
            if attempt == attempts - 1:
                raise
            delay = min(cap, base * 2 ** attempt)
            delay = random.uniform(0, delay)          # full jitter
            await asyncio.sleep(delay)
```

⚠️ **Jitter is not optional.** Without it, every client that failed at the same moment retries at the same moment. Your struggling service gets a synchronised wave of retries exactly when it can least handle it — a **thundering herd** that turns a brief blip into a sustained outage.

"Full jitter" — a random delay between 0 and the computed backoff — is the AWS-recommended variant and it measurably outperforms fixed backoff and half-jitter.

### Retry amplification

```
Client retries 3× → Gateway retries 3× → Service retries 3× → Database
```

One user request becomes **27** database calls. During an incident, when everything is retrying, your load multiplies by 27 exactly when you are least able to serve it.

💡 **Retry at exactly one layer.** Usually the outermost one that has enough context to know whether retrying is safe. If your service mesh retries, your application should not, and vice versa. Two retry layers is the same mistake as TCP-over-TCP ([[02.7 - UDP and Lossy Transport]]).

Better still, use a **retry budget**: cap retries at a percentage of total requests.

```yaml
# Envoy retry budget
retry_budget:
  budget_percent: 20         # retries may be at most 20% of traffic
  min_retry_concurrency: 3
```

This is strictly better than per-request retry limits, because it bounds the *system-wide* amplification rather than the per-request one.

## In Production

### Where idempotency keys belong

| Operation | Needs a key? |
|---|---|
| `GET`, `HEAD` | No — already safe |
| `PUT` with complete state | No — already idempotent |
| `DELETE` | No — already idempotent |
| `POST` creating a resource | **Yes** |
| `POST` triggering an action (payment, email, job) | **Yes** |
| `PATCH` with absolute values | Usually no |
| `PATCH` with relative values | **Yes** |

### Key lifetime

```sql
DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours';
```

24 hours is the common choice — Stripe's. Long enough to cover any realistic client retry, short enough to bound storage.

⚠️ **Tell clients the retention window**, because it determines whether a retry after a long outage will be deduplicated or will double-charge. This belongs in your API documentation, not in a code comment.

### Consumer-side idempotency

The same problem appears in message consumers, and it is where at-least-once delivery lives most visibly.

```python
async def handle_document_indexed(event: Event):
    async with db.transaction():
        inserted = await db.fetchval(
            """INSERT INTO processed_events (event_id) VALUES ($1)
               ON CONFLICT DO NOTHING RETURNING event_id""",
            event.id,
        )
        if inserted is None:
            return                      # already handled

        await apply_effect(event)
```

Insert the marker and apply the effect in **one transaction**. Two workers processing the same message concurrently — which happens during a rebalance — and only one wins.

This is directly Conduit phase 2 and 5 material.

### Testing it

Idempotency is a correctness property that only fails under concurrency, so it needs a specific kind of test:

```python
async def test_concurrent_duplicates_produce_one_effect():
    key = str(uuid4())
    results = await asyncio.gather(
        *[create_payment(key, {"amount": 100}) for _ in range(20)],
        return_exceptions=True,
    )
    successes = [r for r in results if not isinstance(r, Exception)]
    assert await count_payments() == 1
    assert len({r.payment_id for r in successes}) == 1
```

⚠️ **Sequential retries are the easy case and they will pass regardless.** The bug lives in concurrent retries, which is exactly what happens when a client times out, retries, and the original request is still running. **If your idempotency test is not concurrent, it is not testing idempotency.**

## Codebase

**Repo:** `stripe` API docs, `apache/kafka`, and `temporalio/temporal`

**Question to answer:** Kafka claims "exactly-once semantics". Find the actual mechanism — what makes it work, and what are its real limits? Then: how does Temporal guarantee an activity runs exactly once when the worker can crash at any point?

**Read, in order:**

1. Stripe's idempotency documentation — **read this first.** It is the clearest public specification of the pattern, including the retention window, the request-mismatch behaviour, and the concurrent-request response
2. `kafka/clients/src/main/java/org/apache/kafka/clients/producer/internals/TransactionManager.java` — the producer ID and sequence number mechanism. **This is deduplication, not magic**
3. `kafka/core/src/main/scala/kafka/log/UnifiedLog.scala` — search for the producer state and duplicate detection on append. The broker rejects duplicate sequence numbers
4. `temporalio/temporal` — read the docs on activity idempotency and the `WorkflowIdReusePolicy`. Temporal's model is different: it records every result durably so replays never re-execute
5. `celery/celery/app/task.py` — look at how Celery does **not** solve this for you. `acks_late` plus at-least-once means your task must be idempotent, and Celery says so explicitly

💡 The Kafka reading is the payoff. Its "exactly-once" is a producer ID plus a per-partition sequence number, with the broker rejecting duplicates. It works **within Kafka**. The moment your consumer writes to Postgres, you are back to needing your own idempotency. Understanding that boundary precisely is what separates people who have read the marketing from people who have run it.

**Part 1 — Prove the naive version is broken.** Implement check-then-act. Then fire 50 concurrent requests with the same key.

Count the effects. **You should see more than one.** Then add an artificial 50ms delay between the check and the write to make it fail every time rather than occasionally — this is how you turn a flaky race into a deterministic test.

**Part 2 — Build it correctly.** The full three-state implementation with atomic claim, request hash, lock expiry and stored responses.

Test each of these separately:

| Scenario | Expected |
|---|---|
| 50 concurrent identical requests | Exactly one effect, one shared response |
| Sequential retry after success | Cached response, no new effect |
| Same key, different body | 422 |
| Process crash mid-request, then retry | Lock expires, retry proceeds, one effect |
| Retry after key expiry | New effect. **Document this as expected** |
| Key from another org | Not found — no cross-tenant leakage |

**Part 3 — Retry amplification, measured.** Three layers, each retrying 3 times. Instrument the innermost layer to count calls.

Send one request that fails at the bottom. Count. It should be 27.

Then implement a retry budget at each layer and measure again. Chart total inner calls against failure rate for both designs. **The budget version should stay bounded while the naive one grows quadratically.**

**Part 4 — Thundering herd.** 500 clients, all failing at the same instant, all retrying.

Version A: fixed backoff. Version B: exponential with full jitter.

Chart requests-per-second at the server over time for both. Version A should show sharp synchronised spikes. Version B should be smooth.

**This chart is worth keeping** — it is the clearest possible argument for jitter and it takes ten minutes to produce.

**Part 5 — Consumer deduplication.** A queue that deliberately delivers every message twice, plus two concurrent workers.

Naive consumer: count duplicate effects. Then the marker-in-transaction version: verify exactly one effect per message.

Then kill a worker between the marker insert and the effect (without a transaction) and show the message being lost — proving the transaction is doing real work, not ceremony.

**Part 6 — Refactor to natural idempotency.** Take five relative operations from any codebase you have and rewrite them as absolute ones:

```
increment_views(doc_id)          →  set_views(doc_id, count)
append_tag(doc_id, tag)          →  set_tags(doc_id, tags)
add_credit(user_id, 100)         →  record_transaction(txn_id, 100)
```

Write in `refactor.md` what each change costs — usually the client must know more state, or you introduce a transaction ID. **The tradeoff is real and worth articulating.**

**Done when:**
- The naive version demonstrably produces duplicates
- All six correct-version scenarios pass, and the concurrency test uses at least 20 parallel requests
- Your amplification chart shows budgets bounding the growth
- Your jitter chart shows the herd flattening
- The consumer test survives a worker being killed at the worst moment
- `refactor.md` states the cost of each natural-idempotency rewrite
