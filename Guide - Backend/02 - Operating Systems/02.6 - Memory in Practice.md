# Memory in Practice

#backend #os #memory #python #oom

> **In one line:** Know which memory number you are looking at (VSZ, RSS, PSS, cgroup usage), know why a Python process's memory rarely goes back down, and know how the OOM killer chooses its victim, because exit code 137 is the most common way containers die.

---

## The Numbers, Untangled

| Metric | What it counts | Where | Trust it for |
|---|---|---|---|
| **VSZ / VIRT** | All mapped address space, touched or not | `ps`, `top` | Almost nothing. It is routinely 10x RSS. |
| **RSS / RES** | Pages of this process currently in RAM, **including shared ones** | `ps`, `top`, `VmRSS` in `/proc/<pid>/status` | A rough per-process number |
| **PSS** | RSS, with shared pages divided among the processes sharing them | `smem`, `/proc/<pid>/smaps_rollup` | True cost when many workers share libraries or copy-on-write pages |
| **USS** | Pages only this process uses | `smem` | What you would free by killing it |
| **cgroup `memory.current`** | Everything charged to the container: process RSS **plus page cache from its file I/O**, kernel memory and more | `/sys/fs/cgroup/memory.current` | What the OOM killer compares against the limit |
| **`working_set`** (Kubernetes) | `memory.current` minus inactive file cache | `container_memory_working_set_bytes` | What kubelet uses for eviction. The number to alert on. |

⚠️ **Adding up RSS across gunicorn workers overcounts.** Eight workers that each show 400 MB RSS might use 1.2 GB total, because they share libpython, libc and copy-on-write pages from the master. Use PSS.

⚠️ **The container number includes page cache.** A service that writes a lot of log files or reads big files can show `memory.current` near its limit while its RSS is small. The kernel will reclaim clean cache before it OOM-kills, so look at `working_set`, not raw usage.

## How Python Uses Memory

Three layers sit between `x = [1, 2, 3]` and RAM:

```
Python objects
   │
pymalloc  ← CPython's own allocator for objects ≤ 512 bytes
   │        arenas (1 MB on 3.10+, 256 KB before) → pools (16 KB / 4 KB) → fixed-size blocks
   │
libc malloc (glibc ptmalloc / jemalloc / mimalloc)
   │        heap via brk, big allocations via mmap
   │
kernel pages
```

1. **Small objects** (ints, small strings, list headers, dicts) come from **pymalloc** arenas.
2. **Larger objects** (big lists' arrays, large strings, numpy buffers) go to libc `malloc`.
3. **Very large** allocations, over about 128 KB in glibc, become their own `mmap`, and go straight back to the OS on `free`.

### Why memory does not go down

You load 2 million rows into dicts, process them, delete them. RSS stays high. Not a leak, usually:

| Reason | Detail |
|---|---|
| **Arena fragmentation** | pymalloc returns an arena to the OS only when **every** block in it is free. One surviving object pins its whole arena. |
| **glibc heap fragmentation** | Freed chunks in the middle of the `brk` heap cannot be returned. glibc keeps them for reuse. |
| **glibc per-thread arenas** | Each thread may get its own malloc arena (up to 8 × cores). Thread-heavy Python processes can use far more memory than needed. |
| **Free lists and caches** | CPython keeps small free lists for some object types for speed |

**What helps:**

```bash
# Fewer glibc arenas: a big win for thread-heavy services
export MALLOC_ARENA_MAX=2

# Or swap the allocator entirely
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 python app.py
```

- Process large batches in a **child process** or a task worker with `max_tasks_per_child`. When the process exits, all its memory goes back. This is the reliable fix. See [[09.9 - Celery in Production]].
- Stream instead of loading everything (generators, server-side cursors).
- `gunicorn --max-requests 1000 --max-requests-jitter 100` recycles workers before fragmentation adds up.

### Real leaks in Python

| Leak | Example |
|---|---|
| Unbounded caches | A module-level `dict` used as a cache with no eviction. `functools.lru_cache(maxsize=None)` on a method with many distinct arguments |
| Growing globals | Appending every request to a list "for debugging" |
| Reference cycles holding big objects plus `__del__` | Rarer since 3.4, but still possible with C extensions |
| C extension leaks | The leak is outside Python's view; `tracemalloc` will not see it |
| Tasks that never finish | Pending `asyncio` Tasks keep their frames, and everything those frames hold, alive |

Find them with `tracemalloc` snapshots (Python objects), `memray` (Python and native allocations, with flame graphs), and `objgraph` for reference chains.

```python
import tracemalloc
tracemalloc.start(25)
snap1 = tracemalloc.take_snapshot()
# ... run 1000 requests ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "traceback")[:5]:
    print(stat)
    for line in stat.traceback.format()[-6:]:
        print("   ", line)
```

## The OOM Killer

When the kernel cannot find memory (system-wide, or inside a cgroup that hit its limit), it must free some. After reclaiming cache, it kills a process.

**How it picks:** each process gets an `oom_score` (0–1000), roughly its share of memory, adjusted by `oom_score_adj` (−1000 to +1000). The highest score dies.

```bash
cat /proc/$PID/oom_score
cat /proc/$PID/oom_score_adj
echo -1000 > /proc/$PID/oom_score_adj   # never kill this one (use sparingly)
```

**How to tell it happened:**

| Where | What you see |
|---|---|
| Container exit code | **137** = 128 + 9 = killed by `SIGKILL` |
| Kubernetes | `Last State: Terminated, Reason: OOMKilled` |
| Kernel log | `dmesg -T \| grep -i -E "killed process\|out of memory"` |
| Your app logs | **Nothing.** `SIGKILL` cannot be caught. No traceback, no shutdown hook. |

⚠️ **Because `SIGKILL` gives no warning, an OOM kill looks like the process just vanished.** In-flight requests fail, buffered logs are lost, and nothing runs in `finally`. If your service "restarts randomly with no error", check for exit code 137 first.

### cgroup memory controls

```
/sys/fs/cgroup/memory.max     hard limit → OOM kill inside the cgroup when exceeded
/sys/fs/cgroup/memory.high    soft limit → heavy throttling and reclaim, no kill
/sys/fs/cgroup/memory.events  counts of high, max, oom, oom_kill events
```

In Kubernetes, the container's memory **limit** becomes `memory.max`. Unlike CPU (which throttles), going over the memory limit kills. Size limits from measured peak PSS plus headroom, and see [[14.4 - Probes Resources and Autoscaling]].

## Sizing a Python Service's Memory

```
per-worker steady state   = measured PSS after warm-up (e.g. 180 MB)
per-worker peak           = steady + largest request's working set (e.g. +120 MB)
container limit           ≥ workers × peak + page-cache headroom + ~20%

4 workers × 300 MB = 1.2 GB  →  limit 1.5 GB
```

Measure, do not guess. Load-test with realistic payloads, then read PSS and `memory.peak` (cgroup v2, kernel 5.19+).

## In Production

| Symptom | Likely cause | First check |
|---|---|---|
| Exit code 137, no logs | OOM kill | `kubectl describe pod`, `dmesg` |
| RSS climbs slowly forever | Real leak or fragmentation | `tracemalloc` diff over time. If Python objects are flat but RSS grows, it is fragmentation or a native leak; try `MALLOC_ARENA_MAX=2` or jemalloc |
| Memory jumps after one big request, never comes down | Fragmentation from one large batch | Move that work to a short-lived process |
| Workers each "use" 500 MB but the node is fine | You are summing RSS | Use PSS |
| Container near its limit but RSS small | Page cache charged to the cgroup | Look at `working_set`, `memory.stat` (`file` vs `anon`) |

## Codebase

**Repo:** `python/cpython`, plus `bloomberg/memray`

**Question to answer:** When you create and destroy a million small dicts, where does the memory come from, and why does RSS not return to the starting point?

**Read, in order:**

1. `Objects/obmalloc.c` — read the big comment at the top first. Then `pymalloc_alloc`, `pymalloc_free`, and find the condition under which an arena is freed back to the OS.
2. `Lib/tracemalloc.py` and the docs — how snapshots and tracebacks are kept
3. `memray`'s README and `src/memray/_memray/tracking_api.cpp` — skim to see how it intercepts `malloc` below Python

**Size:** 1–2 sessions. `obmalloc.c` is long, but the header comment alone is worth the session.
