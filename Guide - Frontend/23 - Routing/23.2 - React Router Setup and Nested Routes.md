# React Router Setup and Nested Routes

React Router v6.4+ introduced a data-aware API built around a route **object** configuration rather than route components. That shift is what enables loaders, actions and deferred data ([[23.6 - Data Loading with Loaders and Actions]]).

## Setup

```jsx
import { createBrowserRouter, RouterProvider } from "react-router-dom";

const router = createBrowserRouter([
  {
    path: "/",
    element: <RootLayout />,
    errorElement: <RootError />,
    children: [
      { index: true, element: <Home /> },
      {
        path: "products",
        element: <ProductsLayout />,
        children: [
          { index: true, element: <ProductList /> },
          { path: ":id", element: <ProductDetail /> },
        ],
      },
      { path: "*", element: <NotFound /> },
    ],
  },
]);

createRoot(el).render(<RouterProvider router={router} />);
```

The older `<BrowserRouter><Routes><Route>` JSX form still works but does not support loaders or actions. New projects should use the object form, or React Router v7's framework mode.

## Nested routes and Outlet

```jsx
function RootLayout() {
  return (
    <div>
      <Header />
      <nav><Link to="/products">Products</Link></nav>
      <main><Outlet /></main>      {/* child route renders here */}
      <Footer />
    </div>
  );
}
```

`<Outlet />` is where the matched child renders. This is the core of the design: the URL maps to a **chain** of components, each rendering the next.

For `/products/42`, the tree is:

```
RootLayout
  └── ProductsLayout
        └── ProductDetail
```

The layouts stay mounted across navigations within their branch, so their state, scroll position and data persist. Navigating from `/products/1` to `/products/2` re-renders only `ProductDetail`.

## Index routes

```jsx
{ index: true, element: <ProductList /> }
```

An index route renders in the parent's `Outlet` when the parent's path matches exactly. It is what shows at `/products` rather than `/products/something`.

Index routes have no `path` and cannot have children — a common source of confusion when a nested default view is needed.

## Layout routes

A route with no `path` groups children under a shared layout without adding a URL segment:

```jsx
{
  element: <AuthLayout />,      // no path
  children: [
    { path: "login", element: <Login /> },
    { path: "register", element: <Register /> },
  ],
}
```

`/login` and `/register` share `AuthLayout` without becoming `/auth/login`. This is the standard way to group routes by layout rather than by URL hierarchy.

The inverse — a **pathless prefix** — adds URL structure without a layout, by using a path with no element.

## Navigation

```jsx
import { Link, NavLink, useNavigate, Navigate } from "react-router-dom";

<Link to="/products">Products</Link>
<Link to="../settings" relative="path">Up one level</Link>
<Link to="/products" state={{ from: "home" }}>With state</Link>

<NavLink
  to="/products"
  className={({ isActive }) => isActive ? "active" : ""}
  end                                  // exact match only
>
  Products
</NavLink>

const navigate = useNavigate();
navigate("/products");
navigate(-1);                          // back
navigate("/login", { replace: true }); // no history entry

<Navigate to="/login" replace />       // declarative redirect
```

`NavLink`'s `end` prop matters: without it, a link to `/products` is active on `/products/42` too, because matching is prefix-based by default.

`replace: true` is correct for redirects — otherwise the back button returns the user to the page that redirected them, producing a loop.

Relative links resolve against the **route hierarchy** by default, not the URL path. `relative="path"` switches to URL-relative, which is usually what people expect from `../`.

## Route ranking

React Router ranks matches by specificity rather than declaration order:

```
/products/new      → static segment wins
/products/:id      → dynamic
/products/*        → splat, lowest priority
```

So `/products/new` matches the static route even if `:id` is declared first. This differs from older versions and from Express-style routers, where order decided.

The `*` splat route catches everything and should be last conceptually, though ranking handles it regardless.

## Reading route information

```jsx
const { id } = useParams();
const [searchParams, setSearchParams] = useSearchParams();
const location = useLocation();          // pathname, search, hash, state, key
const matches = useMatches();            // the full matched chain
const navigation = useNavigation();      // "idle" | "loading" | "submitting"
```

`useNavigation` is the data-router addition that makes global pending states straightforward:

```jsx
function RootLayout() {
  const navigation = useNavigation();
  return (
    <div className={navigation.state === "loading" ? "loading" : ""}>
      <Outlet />
    </div>
  );
}
```

`useMatches` combined with route `handle` objects is how breadcrumbs are usually built:

```jsx
{ path: "products", handle: { crumb: () => "Products" } }

const crumbs = useMatches()
  .filter(m => m.handle?.crumb)
  .map(m => m.handle.crumb(m.data));
```

## Error boundaries per route

```jsx
{
  path: "products",
  element: <Products />,
  errorElement: <ProductsError />,
}
```

An `errorElement` catches render errors, loader errors and action errors in that branch. Errors bubble to the nearest one, so a route-level boundary keeps the layout and navigation working while only the content area shows the error ([[22.1 - Error Boundaries]]).

```jsx
function ProductsError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error)) {
    return <p>{error.status} — {error.statusText}</p>;
  }
  return <p>Something went wrong</p>;
}
```

Always provide a root `errorElement` — without one, an error unmounts the entire router.

## Scroll and focus

```jsx
<ScrollRestoration />
```

Restores scroll position on back/forward and resets to top on new navigations. Placed once in the root layout.

Focus is **not** handled automatically. Every navigation should move focus and update the title ([[23.1 - Client Side Routing Fundamentals]]).

## Framework mode (v7)

React Router v7 merges Remix into React Router, adding file-based routing, server rendering, and type generation:

```
app/routes/products.$id.tsx
```

The library mode described above remains fully supported. Framework mode is the option when you want SSR and data loading conventions without adopting Next.js.

## How senior engineers actually use this

**They use the data router API**, since loaders and actions are the main reason to use React Router over a simpler solution.

**They nest layouts to match shared UI**, not to match URL structure — layout routes exist precisely for that.

**They put an `errorElement` at the root and on each major branch**, so a failure degrades to a section rather than a blank page.

**They use `replace` for redirects** to avoid back-button loops.

**They centralize route definitions** in one file, which makes the application's shape readable at a glance.

## Common pitfalls

- Missing root `errorElement`, so any error blanks the app.
- `NavLink` without `end`, marking parent links active on child routes.
- Redirects without `replace`, creating back-button loops.
- Assuming declaration order decides matching — ranking does.
- Index routes given children or a path.
- Relative links resolving against the route hierarchy when path-relative was intended.
- No focus management on navigation.

## Interview angle

"How do nested routes work" wants: the URL maps to a chain of matched routes, each rendering the next through `<Outlet />`, so layouts stay mounted across navigations within their branch. The details worth adding are layout routes without a path for grouping, index routes for the parent's default view, specificity-based ranking rather than declaration order, and per-route `errorElement` so failures degrade locally rather than blanking the app.
