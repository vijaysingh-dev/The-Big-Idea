# Telling Similar Patterns Apart

> **The problem this note solves:** Adapter, Strategy, Factory, Decorator, Proxy, State, Bridge… once you've read them all, the code samples look the same. An interface, a few classes that implement it, and something that holds one of them. You can recite each definition and still not say which one is in front of you.
>
> **The fix:** Stop identifying patterns by their **shape**. Identify them by their **intent**, meaning the reason the extra layer of indirection exists. This note gives you four questions that separate every common pair, one running example where all the patterns show up side by side, and real library code to check yourself against.

---

## Why They Look Identical

Almost every GoF pattern is built from the same three parts:

```
┌─────────────┐        ┌───────────────────┐
│   Client    │──uses──▶│  «interface» X    │
└─────────────┘        └───────────────────┘
                              ▲      ▲
                              │      │
                         ┌────┴─┐ ┌──┴───┐
                         │  X1  │ │  X2  │
                         └──────┘ └──────┘
```

That skeleton is just **"program to an interface"**, the Dependency Inversion principle ([[01.1 - SOLID Principles]]). Strategy has it. State has it. Adapter has it. Bridge has it. Factory *returns* it. Decorator and Proxy *are* it.

So if you try to tell them apart from a class diagram, you will fail. GoF diagrams for Strategy and State are literally the same picture. In Python it's worse, because duck typing removes even the explicit interface.

> 💡 **A pattern name is a sentence about *why* the indirection exists, not about *what* the code looks like.** Two identical code snippets can be different patterns. When you're stuck, ask "why is this layer here? What would break if I deleted it?" The answer names the pattern.

---

## The Four Questions

Ask these in order. Each one cuts the candidates down.

### Q1. What is the layer *about* — creating, wrapping, or behaving?

| Answer | Family | Candidates |
|---|---|---|
| "It decides **which object to make**, and then it's out of the picture" | Creational | Factory Method, Abstract Factory, Builder, Prototype, Singleton |
| "It **wraps an existing object** and sits between the client and it" | Structural | Adapter, Decorator, Proxy, Facade, Bridge, Composite |
| "It is **the behaviour itself** that varies, or how objects talk" | Behavioral | Strategy, State, Command, Template Method, Chain, Observer, Mediator |

This is the biggest single split, and it resolves the classic **Factory vs Strategy** confusion on its own:

- A **Factory** runs **once, at construction**. It answers *"which class?"* and hands back an object. After that, nobody calls the factory again for that object.
- A **Strategy** is called **every time the work happens**. It *is* the work.

A factory often *returns* a strategy. They are different moments in time, not competing choices.

### Q2. Does the interface the client sees change?

Only for the wrapping (structural) patterns:

| What the client sees | Pattern |
|---|---|
| A **different** interface from the wrapped object (translated) | **Adapter** |
| The **same** interface, with extra behaviour added | **Decorator** |
| The **same** interface, with access controlled (lazy, remote, guarded, cached) | **Proxy** |
| A **new, simpler** interface over **several** objects | **Facade** |
| The **same** interface for a single item and for a group | **Composite** |

> 💡 **Adapter changes the shape. Decorator and Proxy keep the shape. Facade replaces many shapes with one.**

### Q3. Who picks the implementation, and when?

Only for the behavioural ones:

| Who chooses | Pattern |
|---|---|
| The **client or configuration**, from **outside**, usually once | **Strategy** |
| The **object itself**, from **inside**, and it changes as the object's lifecycle moves on | **State** |
| A **subclass**, at **class-definition time**, by overriding a step | **Template Method** |
| **Each handler** decides whether to handle the request or pass it on | **Chain of Responsibility** |

### Q4. Was the indirection designed in, or retrofitted?

| | Pattern |
|---|---|
| **Retrofitted:** "this thing exists and doesn't fit, make it fit" | **Adapter** |
| **Designed up front:** "two dimensions will vary independently, keep them apart" | **Bridge** |

## One Running Example — Payments

Every pattern below shows up in the same small checkout system, so you can see them side by side and notice where each one sits.

The domain interface everybody codes against:

```python
from dataclasses import dataclass
from decimal import Decimal
from typing import Protocol


@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str


@dataclass(frozen=True)
class ChargeResult:
    ok: bool
    provider_ref: str
    error: str | None = None


class PaymentGateway(Protocol):
    def charge(self, money: Money, card_token: str, idempotency_key: str) -> ChargeResult: ...
```

### Adapter — make a third-party SDK fit *our* interface

Stripe and Razorpay each have their own SDK, units, field names and errors. Neither looks like `PaymentGateway`.

```python
import razorpay
import stripe


class StripeAdapter:
    """Translates our PaymentGateway call into Stripe's API. Shape changes here."""

    def __init__(self, api_key: str):
        self._api_key = api_key

    def charge(self, money: Money, card_token: str, idempotency_key: str) -> ChargeResult:
        try:
            intent = stripe.PaymentIntent.create(
                api_key=self._api_key,
                amount=int(money.amount * 100),              # Stripe wants minor units
                currency=money.currency.lower(),
                payment_method=card_token,
                confirm=True,
                idempotency_key=idempotency_key,
            )
            return ChargeResult(ok=intent.status == "succeeded", provider_ref=intent.id)
        except stripe.StripeError as e:                       # their error → our result
            return ChargeResult(ok=False, provider_ref="", error=str(e))


class RazorpayAdapter:
    # Simplified: real Razorpay card flows go through orders + checkout.
    # The point is that the SDK's shape is nothing like Stripe's.
    def __init__(self, key_id: str, secret: str):
        self._client = razorpay.Client(auth=(key_id, secret))

    def charge(self, money: Money, card_token: str, idempotency_key: str) -> ChargeResult:
        payment = self._client.payment.create(data={          # completely different API
            "amount": int(money.amount * 100),
            "currency": money.currency,
            "token": card_token,
            "receipt": idempotency_key,
        })
        return ChargeResult(ok=payment["status"] == "captured", provider_ref=payment["id"])
```

**The tell:** the body is all **translation**: units, field names, error types. There's no decision-making and no added behaviour. If Stripe's SDK already matched our interface, this class would not exist.

### Factory — decide *which* adapter to build

```python
def gateway_for(country: str, settings) -> PaymentGateway:
    """Runs once per request/startup. Answers 'which class?', then steps away."""
    if country == "IN":
        return RazorpayAdapter(settings.razorpay_key, settings.razorpay_secret)
    return StripeAdapter(settings.stripe_key)
```

**The tell:** it returns an object and is done. No one calls `gateway_for` *during* the charge.

This is the moment people mix up Factory and Strategy, because "pick Razorpay for India" *feels* like a strategy. The test is Q1: is this code running **when the object is made** or **when the work is done**? It runs when the object is made, so it's a factory. The *object it returns* is what gets used every time.

### Strategy — vary *how* a piece of work is done, chosen from outside

The checkout has to choose which gateway to try first when several are available. Ops want to switch between "cheapest fee" and "highest success rate" without a deploy.

```python
class RoutingStrategy(Protocol):
    def order(self, gateways: list["GatewayInfo"]) -> list["GatewayInfo"]: ...


class CheapestFirst:
    def order(self, gateways):
        return sorted(gateways, key=lambda g: g.fee_bps)


class HighestSuccessFirst:
    def order(self, gateways):
        return sorted(gateways, key=lambda g: g.success_rate_1h, reverse=True)


class Checkout:
    def __init__(self, routing: RoutingStrategy):       # injected from outside
        self._routing = routing

    def pay(self, money, token, key, candidates):
        for info in self._routing.order(candidates):   # called on EVERY payment
            result = info.gateway.charge(money, token, key)
            if result.ok:
                return result
        return ChargeResult(ok=False, provider_ref="", error="all gateways failed")


checkout = Checkout(routing=HighestSuccessFirst())     # config picks it
```

**The tells:**
- The client (`Checkout`) **does not know or care** which strategy it has.
- The strategy is picked **from outside** and doesn't change itself.
- All strategies take the same input and produce the same *kind* of output. They are interchangeable algorithms for one job.

> In Python, a strategy is very often **just a function**: `sorted(items, key=...)`, `Checkout(routing=lambda gs: ...)`. A one-method strategy class with no state is a function wearing a costume. Use the function.

### Decorator — same interface, extra behaviour, stackable

```python
import logging
import time

log = logging.getLogger(__name__)


class LoggingGateway:
    def __init__(self, inner: PaymentGateway):
        self._inner = inner

    def charge(self, money, card_token, idempotency_key):
        start = time.perf_counter()
        result = self._inner.charge(money, card_token, idempotency_key)   # ALWAYS delegates
        log.info("charge ok=%s ms=%.0f", result.ok, (time.perf_counter() - start) * 1000)
        return result


class RetryingGateway:
    def __init__(self, inner: PaymentGateway, attempts: int = 3):
        self._inner, self._attempts = inner, attempts

    def charge(self, money, card_token, idempotency_key):
        for i in range(self._attempts):
            result = self._inner.charge(money, card_token, idempotency_key)
            if result.ok or i == self._attempts - 1:
                return result
            time.sleep(0.2 * 2**i)


gateway = LoggingGateway(RetryingGateway(StripeAdapter(key)))   # stacked, order matters
```

**The tells:**
- The interface is **identical** to what it wraps, so the client can't tell it's there.
- It **always delegates**, adding something before or after.
- You can **stack** several, and the order means something. Logging outside retry logs once per payment. Retry outside logging logs every attempt.

### Proxy — same interface, but *controls access* to the real thing

```python
class LazyGateway:
    """Doesn't construct the real SDK client (network, secrets fetch) until first use."""

    def __init__(self, factory):
        self._factory, self._real = factory, None

    def charge(self, money, card_token, idempotency_key):
        if self._real is None:
            self._real = self._factory()
        return self._real.charge(money, card_token, idempotency_key)


class KillSwitchGateway:
    """Protection proxy: may refuse to forward the call at all."""

    def __init__(self, real: PaymentGateway, flags):
        self._real, self._flags = real, flags

    def charge(self, money, card_token, idempotency_key):
        if self._flags.is_on("payments_disabled"):
            return ChargeResult(ok=False, provider_ref="", error="payments temporarily disabled")
        return self._real.charge(money, card_token, idempotency_key)
```

**Decorator vs Proxy is the one pair where the code really can be identical.** The difference is intent:

| | Decorator | Proxy |
|---|---|---|
| Purpose | **Add** behaviour | **Control access** to the real object |
| Does it always call the wrapped object? | Yes | Not necessarily: may delay, deny, or answer from cache |
| Who builds the wrapped object? | Usually the client, then passes it in | Often the proxy itself (lazy/remote) |
| Stacking | Normal, expected | Usually one |
| Typical names | `Logging*`, `Retrying*`, `Timed*` | `Lazy*`, `Remote*`/stub, `Cached*`, `Guarded*` |

If you're asked and the code is ambiguous, say so: *"structurally it's the same thing; I'd call it a proxy because its job is gating access, not adding behaviour."* That answer is better than picking one confidently.

### Facade — one simple entry point over several subsystems

```python
class CheckoutFacade:
    """What the API handler calls. Hides inventory, payments, orders, email."""

    def __init__(self, inventory, checkout: Checkout, orders, notifier):
        self._inventory, self._checkout = inventory, checkout
        self._orders, self._notifier = orders, notifier

    def place_order(self, cart, card_token, idempotency_key) -> "Order":
        self._inventory.reserve(cart.items)
        try:
            result = self._checkout.pay(cart.total, card_token, idempotency_key, cart.gateways)
            if not result.ok:
                raise PaymentFailed(result.error)
        except Exception:
            self._inventory.release(cart.items)
            raise
        order = self._orders.create(cart, result.provider_ref)
        self._notifier.order_confirmed(order)
        return order
```

**The tells:** it wraps **many** objects, not one, and exposes a **new, coarser** interface (`place_order`) that none of them had. Your "service layer" classes are usually facades.

**Adapter vs Facade:** an adapter wraps **one** object to match an interface that **already exists** (the client defined it). A facade wraps **several** and **invents** a new, simpler interface.

### State — the object changes its own behaviour as its lifecycle moves

A `Payment` behaves differently depending on where it is in its life. You can't refund something that was never captured, and capturing twice is a bug.

```python
class PaymentState(Protocol):
    def capture(self, p: "Payment") -> None: ...
    def refund(self, p: "Payment") -> None: ...


class Authorized:
    def capture(self, p):
        p.gateway_capture()
        p.state = Captured()            # the STATE moves the object to the next state
    def refund(self, p):
        p.gateway_void()
        p.state = Voided()


class Captured:
    def capture(self, p):
        raise InvalidTransition("already captured")
    def refund(self, p):
        p.gateway_refund()
        p.state = Refunded()


class Refunded:
    def capture(self, p): raise InvalidTransition("refunded")
    def refund(self, p):  raise InvalidTransition("already refunded")


class Voided(Refunded): ...


class Payment:
    def __init__(self):
        self.state: PaymentState = Authorized()
    def capture(self): self.state.capture(self)
    def refund(self):  self.state.refund(self)
```

**Strategy vs State, the most-asked pair:**

| | Strategy | State |
|---|---|---|
| Who swaps it | The **client**, from outside | The **object/state itself**, from inside |
| How often | Rarely, often once at construction | Whenever the lifecycle advances |
| Do implementations know each other? | **No.** `CheapestFirst` has never heard of `HighestSuccessFirst` | **Yes.** `Authorized` creates `Captured`. They form a graph |
| What it models | Interchangeable **algorithms** for the same job | **Modes** of one object, with legal transitions |
| Question it answers | "*How* should this be done?" | "What am I allowed to do *right now*?" |

> 💡 **One-line test:** if the implementations reference each other, it's State. If they're strangers, it's Strategy.

In real Python backends, State is usually an `Enum` plus a transition table, and the full State pattern only earns its place when each state has a lot of distinct behaviour. See [[02.16 - State]].

### Template Method — fixed skeleton, subclasses fill in steps

```python
from abc import ABC, abstractmethod


class ReconciliationJob(ABC):
    def run(self, day):                       # the skeleton: fixed, not overridden
        rows = self.fetch_settlements(day)    # varies per provider
        ours = self.load_our_payments(day)    # same for all
        diffs = self.compare(rows, ours)      # same for all
        self.report(diffs)                    # same for all

    @abstractmethod
    def fetch_settlements(self, day): ...


class StripeReconciliation(ReconciliationJob):
    def fetch_settlements(self, day):
        ...
```

**Strategy vs Template Method:** both vary *part* of an algorithm.

| | Strategy | Template Method |
|---|---|---|
| Mechanism | **Composition**: pass in an object | **Inheritance**: override a method |
| What varies | The **whole** algorithm | **One or more steps** in a fixed skeleton |
| Swappable at runtime? | Yes | No, it's fixed per subclass |

Modern advice leans toward Strategy (composition over inheritance, [[01.2 - Other Design Principles]]), but frameworks use Template Method everywhere. `unittest.TestCase.setUp` and Django's `get_queryset` are both template-method hooks.

### Bridge — two dimensions that vary independently, separated on purpose

Suppose payment *flows* (one-off, subscription, split-payment) and *providers* (Stripe, Razorpay) both grow. With inheritance you'd get `StripeSubscription`, `RazorpaySubscription`, `StripeSplit`… which is M×N classes.

```python
class PaymentFlow(ABC):
    def __init__(self, gateway: PaymentGateway):   # ← the "bridge" is this reference
        self.gateway = gateway


class OneOff(PaymentFlow):
    def execute(self, order): return self.gateway.charge(order.total, order.token, order.key)


class Subscription(PaymentFlow):
    def execute(self, sub):
        for invoice in sub.due_invoices():
            self.gateway.charge(invoice.total, sub.token, invoice.key)


flow = Subscription(gateway=RazorpayAdapter(...))   # M flows + N gateways, not M×N
```

**Adapter vs Bridge:** the code can look the same. The difference is timing and intent:
- **Adapter** is a **retrofit**: the thing exists and doesn't fit, so you make it fit.
- **Bridge** is **designed up front**: you know two hierarchies will grow, so you keep them apart.

Notice that the *implementations* behind a bridge are often adapters (`RazorpayAdapter` above).

### Chain of Responsibility — each handler may handle, or pass along

```python
class FraudCheck:
    def __init__(self, next_): self.next = next_
    def handle(self, payment):
        if risk_score(payment) > 0.9:
            return Reject("fraud")            # STOPS the chain
        return self.next.handle(payment)
```

**Chain vs Decorator:** both wrap a `next`. A **decorator always passes the call on**; its job is to add behaviour. A **chain handler may stop the call**; its job is to decide who handles it. Web middleware is a hybrid: most middleware decorates, and auth middleware short-circuits with a 401.

### Command — package *a request* as an object

```python
@dataclass
class RefundCommand:
    payment_id: str
    amount: Money
    reason: str

    def execute(self, gateway): ...
    def undo(self, gateway): ...    # optional
```

**Command vs Strategy:** a **strategy is *how*** to do something; it's an algorithm with no particular inputs. A **command is *what* to do, with its arguments baked in.** That's why a command can be queued, logged, retried, scheduled, or undone. A Celery task signature (`refund.s(payment_id, amount)`) is a command.

### Observer vs Mediator vs Pub/Sub

| | Who knows whom | Example |
|---|---|---|
| **Observer** | The subject keeps a list of observers and calls them directly. Same process | Django signals, `Future.add_done_callback` |
| **Mediator** | Components only know the mediator, and the mediator holds the **coordination logic** | A chat room object, a workflow orchestrator |
| **Pub/Sub** | Publishers and subscribers only know a **topic**. A broker sits between them, usually across processes | Kafka, Redis Pub/Sub ([[03.9 - PubSub and Event Bus]]) |

Observer **broadcasts** ("this happened") and doesn't care what listeners do. Mediator **directs** ("you do this, then you do that").

### Factory Method vs Abstract Factory vs Builder vs a plain function

| | Creates | Varies by | Python reality |
|---|---|---|---|
| **Simple factory** | One object | A parameter (`if country == ...`) | A function. 90% of real "factories" |
| **Factory Method** | One object | **Subclass** overriding `create_x()` | A hook in a base class, as in Template Method |
| **Abstract Factory** | A **family** of related objects that must match | Which family | `AWSFactory` → S3 + SQS + KMS vs `GCPFactory` → GCS + PubSub + KMS |
| **Builder** | One **complex** object, step by step | Which steps you call | `select(User).where(...).order_by(...).limit(10)` |

The factory question is "*which* class?" The builder question is "*how many settings*, and in what order?"

## The Whole Checkout, Labelled

All of the above sit in the same system at the same time:

```
API handler
  └── CheckoutFacade.place_order()                  ← FACADE (one call over many subsystems)
        ├── inventory.reserve()
        ├── Checkout(routing=HighestSuccessFirst()) ← STRATEGY (how to order gateways)
        │     └── for each gateway:
        │           LoggingGateway(                  ← DECORATOR (adds logging)
        │             RetryingGateway(               ← DECORATOR (adds retry)
        │               KillSwitchGateway(           ← PROXY (may refuse access)
        │                 StripeAdapter(...))))      ← ADAPTER (Stripe SDK → our interface)
        │           built by gateway_for(country)    ← FACTORY (which adapter?)
        ├── orders.create() → Payment(state=Authorized())  ← STATE (lifecycle)
        └── notifier.order_confirmed()               ← OBSERVER (listeners react)

Nightly: StripeReconciliation(ReconciliationJob)    ← TEMPLATE METHOD
Refunds queued as RefundCommand(...)               ← COMMAND
```

> 💡 Patterns don't compete. They **compose**. "Should this be a Factory or a Strategy?" is usually the wrong question. Most real designs have a factory that builds an adapter, wrapped in decorators, used by a strategy.

## Cheat Table — The Look-Alike Pairs

| Pair | One-question test |
|---|---|
| **Factory vs Strategy** | Does it run once to **make** an object (Factory), or every time to **do** the work (Strategy)? |
| **Adapter vs Decorator** | Does the interface **change** (Adapter) or stay **identical** (Decorator)? |
| **Adapter vs Facade** | Wrapping **one** object to fit an **existing** interface (Adapter), or **many** behind a **new** one (Facade)? |
| **Adapter vs Bridge** | **Retrofit** to fix a mismatch (Adapter), or **designed up front** for two varying dimensions (Bridge)? |
| **Decorator vs Proxy** | **Adds** behaviour and always delegates (Decorator), or **controls access** and might not delegate (Proxy)? |
| **Decorator vs Chain** | Always passes the call on (Decorator), or may **stop** it (Chain)? |
| **Strategy vs State** | Swapped from **outside**, implementations are strangers (Strategy)? Or swaps **itself**, implementations know each other (State)? |
| **Strategy vs Template Method** | **Composition**, whole algorithm swapped (Strategy), or **inheritance**, one step overridden (Template)? |
| **Strategy vs Command** | **How** to do a job (Strategy), or **what** to do, with its arguments (Command)? |
| **Observer vs Mediator** | Broadcasts "it happened" (Observer), or coordinates "do this next" (Mediator)? |
| **Factory Method vs Abstract Factory** | One product (Factory Method), or a **matching family** of products (Abstract Factory)? |
| **Factory vs Builder** | Picks **which** class (Factory), or assembles **one** complex object step by step (Builder)? |

## Check Yourself Against Real Code

These are real, well-known libraries. For each, cover the right-hand column and name the pattern.

| Code you've used | Pattern | Why |
|---|---|---|
| `sorted(items, key=len)` | Strategy | You pass in *how* to compare. It's called for every element |
| `tenacity.retry(wait=wait_exponential(), stop=stop_after_attempt(5))` | Strategy objects inside a Decorator | `@retry` decorates your function. `wait=`/`stop=` are pluggable strategies |
| `@functools.lru_cache` | Decorator (also a caching proxy) | Same call signature, adds caching |
| `sqlalchemy.create_engine("postgresql+asyncpg://...")` | Factory returning an Adapter | The URL picks a **dialect**, and each dialect **adapts** a driver (asyncpg, psycopg) to SQLAlchemy's interface |
| LangChain `ChatOpenAI`, `ChatAnthropic` | Adapter | Each one adapts a vendor API to the common `BaseChatModel` interface |
| `requests.get(url)` | Facade | One call over sessions, connection pools, urllib3, retries, encoding |
| `subprocess.run()` | Facade | A simpler API over `Popen` + `communicate` + `wait` |
| `io.BufferedReader(raw_stream)` | Decorator | Same read interface, adds buffering. Wrap again with `TextIOWrapper` to add decoding |
| `open(path, "rb")` vs `open(path, "r")` | Factory | Returns `BufferedReader` or `TextIOWrapper` depending on `mode` |
| Django `request.user` (`SimpleLazyObject`) | Proxy (virtual/lazy) | Doesn't hit the DB until you touch an attribute |
| A gRPC client stub | Proxy (remote) | Looks like a local object, forwards over the network |
| SQLAlchemy `select(User).where(...).order_by(...)` | Builder | Builds one complex query object step by step |
| Starlette / Django middleware stack | Chain of Responsibility + Decorator | Each layer can short-circuit (auth → 401) or wrap (timing) |
| `unittest.TestCase.setUp` / `tearDown` | Template Method | The runner owns the skeleton. You fill in the hooks |
| Django signals, SQLAlchemy events | Observer | Subjects notify registered listeners |
| Celery `task.s(args)` | Command | The request plus its arguments as an object you can queue, chain and retry |
| Python generators | Iterator | Sequential access without exposing the source |
| `logging.getLogger("app.db")` | Factory + registry | Returns the same logger per name, creating it if needed |

> ⚠️ **Library names don't always follow GoF.** `logging.LoggerAdapter` keeps the same interface and *adds* context to every message. By the definitions above it's a decorator, even though it's called an adapter. Name the pattern by what the code does, not by the class name.

## Practice — Name the Pattern

Cover the answers.

1. Your service talks to an old SOAP inventory system. You write `InventoryClient` with `get_stock(sku) -> int` that builds XML, calls SOAP, and parses the response.
2. Your LLM service supports OpenAI, Anthropic and a local vLLM server. At startup it reads `LLM_PROVIDER` and builds the right client.
3. Users can choose "fastest", "cheapest" or "best" as an answer mode, and the request handler passes the choice to the generator.
4. Every outgoing HTTP call needs a trace header, a timeout, and a retry. You wrap the client three times.
5. An `Order` can be `Draft`, `Placed`, `Shipped` or `Cancelled`. `cancel()` works differently in each, and is illegal after shipping.
6. `ReportService.generate_monthly()` calls the warehouse, the PDF renderer, S3 and the email service.
7. An admin-only `DeleteUserService` wraps the real one and checks the caller's role before forwarding.
8. All three of your ETL jobs do extract → validate → load. Only `extract` differs.
9. Failed webhook deliveries are stored as `{url, payload, attempt}` rows and replayed by a worker.
10. An `ImageVariantFactory` creates a matching thumbnail generator, watermarker and compressor for "web" or "print".

<details>
<summary>Answers</summary>

1. **Adapter.** Pure translation of a foreign interface. (It's also arguably a facade over SOAP plumbing, but its *reason* to exist is the mismatch.)
2. **Factory** returning **Adapters.** The factory picks which client. Each client adapts a vendor API to your `LLMClient` interface.
3. **Strategy.** Chosen from outside, interchangeable, and the options don't know about each other.
4. **Decorator** ×3. Same interface, behaviour added, stacked, and the order matters (retry should sit outside the timeout).
5. **State.** The object's behaviour depends on its lifecycle, transitions are legal or illegal, and states lead to each other.
6. **Facade.** One coarse operation over several subsystems.
7. **Proxy** (protection). It controls access and may not forward the call.
8. **Template Method** (or Strategy for `extract`, if you'd rather compose than inherit).
9. **Command.** The request and its arguments stored as data, then replayed.
10. **Abstract Factory.** A family of products that must match each other.

</details>

## Interview Angle

**"What's the difference between Strategy and State?"**
> "Structurally they're the same, a context holding an interface. The difference is who switches the implementation. With Strategy, the client picks it from outside, and the strategies don't know about each other. Sorting with different comparators is the example. With State, the object switches itself as its lifecycle moves on, and the states know their successors. An order going from placed to shipped is the example. One quick test is whether the implementations reference each other."

**"Adapter vs Decorator vs Proxy?"**
> "All three wrap one object. An adapter changes the interface: it makes a foreign API fit ours, like a Stripe SDK behind our `PaymentGateway`. Decorator and proxy keep the interface. A decorator adds behaviour and always delegates, and you stack them for logging, retry or metrics. A proxy controls access. It might lazy-load, forward to a remote service, serve from cache, or refuse the call. Decorator and proxy can be the same code, so I name them by intent."

**"Isn't Factory just Strategy?"**
> "They happen at different times. A factory runs once to decide which object to construct, and then it's done. A strategy is the behaviour that runs every time the work happens. They often appear together: a factory reads config and returns the right strategy or adapter."

**Signals interviewers look for:**
- You name patterns by **intent**, and you admit when two patterns are the same code.
- You show patterns **composing** rather than competing.
- You prefer **functions over one-method classes** in Python, and say why.
- You know when **not** to use one: two `if` branches don't need a Strategy hierarchy ([[01.2 - Other Design Principles#KISS — Keep It Simple, Stupid]]).
