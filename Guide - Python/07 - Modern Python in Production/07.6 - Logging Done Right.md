# Logging Done Right

#python #logging #observability #production

> **In one line:** Python's `logging` is a tree of named loggers that pass records up to handlers. Libraries only create loggers, applications configure handlers once at startup, production logs are structured JSON with a request ID, and nothing in the request path should ever block on writing a log line.

---

## The Model

```
logger "app.orders.service"   ─┐  records propagate UP the dotted tree
logger "app.orders"            │
logger "app"                   │
root logger  ◄─────────────────┘  handlers usually live here
   │
   ├── Handler: StreamHandler(stdout)  ─► Formatter (JSON)
   └── Handler: (optional) file / syslog / OTel exporter
```

| Piece | Job |
|---|---|
| **Logger** | Named by module (`logging.getLogger(__name__)`). Has a level. Creates `LogRecord`s. |
| **Handler** | Sends records somewhere: stdout, a file, the network. Has its own level. |
| **Formatter** | Turns a record into text or JSON |
| **Filter** | Drops or enriches records: adding a request ID, redacting secrets |

```python
# in every module
import logging
log = logging.getLogger(__name__)

def charge(order_id: int) -> None:
    log.info("charging order", extra={"order_id": order_id})
```

---

## The Two Rules

**1. Libraries never configure logging.** They call `getLogger(__name__)` and log. They do not add handlers, call `basicConfig`, or set levels. (A library may add a `NullHandler`.)

**2. The application configures logging exactly once, at startup.**

```python
import logging.config

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,           # do not silence libraries' loggers
    "formatters": {
        "json": {"()": "pythonjsonlogger.json.JsonFormatter",
                 "fmt": "%(asctime)s %(levelname)s %(name)s %(message)s"},
    },
    "handlers": {
        "stdout": {"class": "logging.StreamHandler", "formatter": "json", "stream": "ext://sys.stdout"},
    },
    "root": {"level": "INFO", "handlers": ["stdout"]},
    "loggers": {
        "uvicorn.access": {"level": "WARNING"},  # quiet noisy libraries
        "sqlalchemy.engine": {"level": "WARNING"},
        "app": {"level": "DEBUG"},
    },
}
logging.config.dictConfig(LOGGING)
```

In containers, **log to stdout**. The runtime collects it, and log files inside containers are a disk-full incident waiting to happen ([[02.8 - Files Disks and the Page Cache]]).

## Levels

| Level | Use for | In production |
|---|---|---|
| `DEBUG` | Detailed internals | Off, or enabled per logger temporarily |
| `INFO` | Business events: order placed, job finished | On |
| `WARNING` | Unexpected but handled: a retry, a fallback, a deprecated call | On, and watched |
| `ERROR` | A failed operation that needs attention | On, and alerted on (by rate) |
| `CRITICAL` | The process cannot continue | Rare |

## The Common Mistakes

```python
# ❌ f-strings: formatted even if the level is disabled; breaks aggregation by message
log.debug(f"user {user_id} fetched {len(rows)} rows")

# ✅ lazy %-args, or structured fields
log.debug("user fetched rows", extra={"user_id": user_id, "rows": len(rows)})
```

```python
# ❌ loses the traceback
except Exception as e:
    log.error(f"failed: {e}")

# ✅ keeps it
except Exception:
    log.exception("payment failed", extra={"order_id": oid})
    raise
```

| Mistake | Fix |
|---|---|
| `print()` in services | A logger; prints have no level, no timestamp, no structure |
| Logging the same error at every layer | Log once where it is **handled**; elsewhere add context and re-raise ([[06.7 - Exceptions]]) |
| Logging secrets, tokens, full request bodies, personal data | Redaction filter; `SecretStr`; `repr=False` on sensitive fields |
| `basicConfig()` called inside a library or on import | Configure only in the app entry point |
| A new message string per value (`f"user {id} failed"`) | A constant message plus fields, so you can group and count |

## Structured Logs and Request Context

Plain text is for humans tailing a terminal. Production logs are **queried**, so make them JSON, with a stable message and fields:

```json
{"ts":"2026-11-15T10:01:02.123Z","level":"error","logger":"app.payments",
 "msg":"charge failed","order_id":42,"provider":"stripe","request_id":"7f3a...","trace_id":"4bf9..."}
```

Every line in a request should carry the same `request_id` (and the OpenTelemetry `trace_id`), so one search finds everything about one request. Use a `ContextVar` and a filter, which are safe across concurrent asyncio tasks ([[02.3 - Scopes and Closures#contextvars — Scope for Concurrent Code]]):

```python
from contextvars import ContextVar
request_id: ContextVar[str] = ContextVar("request_id", default="-")

class ContextFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id.get()
        return True
```

**structlog** makes this pattern first-class: bind context once, and every later log call includes it.

```python
import structlog
structlog.contextvars.bind_contextvars(request_id=rid, user_id=uid)   # in middleware
log = structlog.get_logger()
log.info("order placed", order_id=42, total="19.99")                  # includes request_id, user_id
```

Connecting logs to traces and metrics is covered in [[Observability]] and [[13.3 - Instrumenting Conduit End to End]].

## Do Not Block the Event Loop

`StreamHandler.emit` does a synchronous `write()`. If stdout is a pipe and the log collector falls behind, that write **blocks**, and in an async service it blocks every request at once ([[02.12 - The Kernel Under One Request]]). Use a queue:

```python
import logging, logging.handlers, queue

log_queue: queue.Queue = queue.Queue(-1)
queue_handler = logging.handlers.QueueHandler(log_queue)       # fast: just enqueues
stdout_handler = logging.StreamHandler()
listener = logging.handlers.QueueListener(log_queue, stdout_handler, respect_handler_level=True)

logging.getLogger().addHandler(queue_handler)
listener.start()            # a background thread does the slow writing
# at shutdown: listener.stop()  — flushes the queue
```

Since 3.12, `dictConfig` can set this up directly with a `"class": "logging.handlers.QueueHandler"` handler that lists the real handlers.

⚠️ An unbounded queue can grow without limit if the sink is down. For very high log volumes, use a bounded queue that drops (and counts) records rather than consuming all memory. That is backpressure again ([[01.11 - Backpressure Inside One Process]]).
