# Flow Control and Congestion Control

#backend #networking #tcp #performance

> **In one line:** Flow control stops you overwhelming the receiver, congestion control stops you overwhelming the network, and together they explain why your transfer is slow even though nothing is broken.

---

## The Idea

TCP has two separate throttles, and people constantly confuse them.

| | Flow control | Congestion control |
|---|---|---|
| Protects | The **receiver** | The **network** |
| Signal | The receiver's advertised window | Packet loss, or delay |
| Set by | Receiver | Sender's own estimate |
| Limit | `rwnd` | `cwnd` |

The sender may have in flight, at most:

```
min(receive window, congestion window)
```

One is told to you. The other you have to guess, and the guessing is where all the interesting behaviour comes from.

---

## Flow Control

The receiver has a buffer. If the application is not reading fast enough, the buffer fills. TCP must not keep pushing data into a full buffer.

So every ACK carries a **window** — "I have room for this many more bytes."

```
Receiver buffer: 64KB, app has read nothing
  → advertises window = 64KB

Sender sends 64KB, app still has not read
  → receiver advertises window = 0
  → sender stops entirely

App finally reads 32KB
  → receiver sends a window update: 32KB
  → sender resumes
```

💡 **This is the mechanism behind everything in [[01.11 - Backpressure Inside One Process]].** When you do not call `recv()`, the kernel buffer fills, the window goes to zero, and the sender is throttled by the protocol itself. Backpressure reaches all the way across the network with no application code at all.

### Zero window probes

If the window is zero, the sender cannot send — including the packet that would ask "any room yet?". So it sends periodic **zero window probes** to check.

```bash
ss -ti          # look for "zwp" or a rwnd of 0
```

A connection stuck at a zero window means the receiving **application** is not reading. That is almost always your bug, not a network one. In an async service it usually means the event loop is blocked.

### Window scaling

The window field is 16 bits — maximum 65,535 bytes. On a fast, long link that is far too small.

```
Bandwidth-Delay Product = bandwidth × round-trip time
1 Gbps × 100ms = 12.5 MB of data can be "in flight"
```

With a 64KB window you would send 64KB and then wait 100ms for an ACK. That is **5 Mbps on a 1 Gbps link** — 0.5% utilisation.

**Window scaling** (RFC 1323) adds a multiplier negotiated during the handshake, allowing windows up to 1GB. On by default everywhere.

⚠️ **Window scaling is negotiated in the SYN only.** Some old middleboxes strip the option, and the result is a connection that works but is inexplicably capped at a few Mbps regardless of the link. Rare now, and memorable when you meet it.

## Congestion Control

Nobody tells you how much capacity the network has. So TCP probes: send more until something is lost, then back off.

### Slow start

Despite the name, this is exponential growth.

```
cwnd starts at ~10 packets (~14KB)
Each ACK received → cwnd increases
Effectively cwnd doubles every round trip

RTT 1:  10 packets
RTT 2:  20
RTT 3:  40
RTT 4:  80
```

⚠️ **Slow start is why small transfers never reach full speed.** A 100KB response on a 100ms link needs about 3 round trips = 300ms, regardless of bandwidth. Your gigabit link is irrelevant; you are latency-bound, not bandwidth-bound.

💡 **This is one of the most practically important facts in networking.** For typical web payloads, round trips dominate. Reducing round trips beats increasing bandwidth every time — which is the reasoning behind connection reuse, HTTP/2 multiplexing, and TLS 1.3's shorter handshake.

### Congestion avoidance

Above a threshold, growth becomes linear — roughly one extra packet per round trip. Cautious probing rather than doubling.

### Loss, and what it means

```
Fast retransmit (3 duplicate ACKs)  → mild signal → halve cwnd, continue
Timeout (nothing came back at all)  → severe signal → cwnd back to ~10, restart slow start
```

⚠️ **A timeout is catastrophic for throughput.** You lose everything congestion control has learned and start over. One timeout on a long-lived connection can cost seconds.

### The algorithms

| Algorithm | Signal | Where |
|---|---|---|
| **Reno / NewReno** | Loss | Old, still the textbook example |
| **CUBIC** | Loss | Linux default. Recovers faster on high-bandwidth links |
| **BBR** | Delay and bandwidth estimate | Google. Much better on lossy links |

```bash
sysctl net.ipv4.tcp_congestion_control     # what you are using
sysctl net.ipv4.tcp_available_congestion_control
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

💡 **BBR is worth knowing about specifically because loss-based algorithms misread wireless.** On WiFi or mobile, packets are lost due to interference, not congestion. CUBIC interprets that as "the network is full" and backs off when it should not. BBR measures actual delivery rate and delay instead, and can be several times faster on lossy links. Google enabled it on YouTube for exactly this reason.

## Why 1% Loss Destroys Throughput

The result that surprises everyone.

```
Approximate throughput ≈ MSS / (RTT × √loss)
```

With MSS 1460 bytes and RTT 100ms:

| Loss | Approximate throughput |
|---|---|
| 0.01% | ~117 Mbps |
| 0.1% | ~37 Mbps |
| 1% | ~11 Mbps |
| 2% | ~8 Mbps |
| 5% | ~5 Mbps |

**1% loss costs you roughly 90% of throughput.** Not 1%.

The reason: every loss halves the congestion window, and recovery is linear. A little loss means you spend most of your time recovering rather than transmitting.

⚠️ **Practical consequence: a slightly faulty cable, an overloaded switch, or a marginal WiFi signal does not degrade throughput slightly — it destroys it.** "The network is only dropping a few packets" is never a reassuring statement.

```bash
ss -ti | grep -o 'retrans:[0-9]*/[0-9]*'
# retrans:0/1523 → 0 current, 1523 total retransmits on this connection
```

Any meaningful retransmit count on an internal network is a hardware or capacity problem, not a tuning problem.

## Bufferbloat

Someone puts a large buffer in a router, believing buffers prevent loss. They do — by adding enormous delay instead.

```
No buffer:   packet dropped → sender backs off quickly → low latency
Big buffer:  packet queued for 2 seconds → sender has no idea → latency is terrible
```

Because loss-based congestion control uses loss as its only signal, a big buffer hides the congestion. The sender keeps increasing until the buffer overflows, by which point the queue holds seconds of data.

Symptom: a large download makes everything else on the network unusable, with ping times going from 20ms to 2000ms.

Fixes are `fq_codel` and `cake` queueing disciplines, which drop early and deliberately, and BBR, which uses delay rather than loss as its signal.

You will rarely fix bufferbloat yourself. You should recognise it, because "downloads are fine but interactive latency is terrible under load" is a specific and diagnosable thing.

## In Production

### Reading `ss -ti`

```bash
ss -ti dst 10.0.0.5
```

```
cubic wscale:7,7 rto:204 rtt:3.5/1.2 mss:1448 cwnd:143 ssthresh:87
bytes_sent:8912384 retrans:0/12 delivery_rate:284Mbps
```

| Field | What it tells you |
|---|---|
| `rtt:3.5/1.2` | Round trip 3.5ms, variance 1.2ms. High variance means queueing |
| `cwnd:143` | 143 packets in flight allowed ≈ 200KB. Small means congestion |
| `ssthresh:87` | Below cwnd, so we are past slow start |
| `retrans:0/12` | 12 total retransmits. Non-zero on a LAN is a problem |
| `delivery_rate` | Actual achieved throughput |
| `rto:204` | Retransmit timeout. A timeout costs you this much |

💡 **`cwnd` small plus `retrans` non-zero means the network is the problem. `cwnd` large plus low throughput means the application or the receive window is the problem.** That one distinction saves hours of arguing with the network team.

### The practical implications

| Situation | Implication |
|---|---|
| Small API responses | You are latency-bound. Bandwidth is irrelevant. Reduce round trips |
| Cross-region calls | Handshake + slow start dominate. Connection reuse is the biggest single win |
| Large file transfers | Bandwidth-bound. Check window scaling and BDP |
| Mobile or WiFi clients | Loss-based congestion control underperforms badly. Consider BBR, or HTTP/3 |
| Many small requests | Consider batching, or HTTP/2 multiplexing over one warm connection |

### Why HTTP/3 exists

Everything above applies **per TCP connection**. HTTP/2 multiplexes many streams onto one connection, so one lost packet stalls *every* stream while TCP waits for the retransmit — TCP delivers bytes in order and cannot skip ahead.

HTTP/3 moves to QUIC over UDP and implements per-stream ordering, so a loss in stream 3 does not stall streams 1, 2 and 4.

That is the entire motivation, and it is a direct consequence of this note. See [[02.5 - Head of Line Blocking]] and [[03.9 - HTTP3 and QUIC]].

### Tuning, honestly

```bash
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
```

⚠️ **Do not do this without measuring first.** Modern Linux auto-tunes buffers well. The realistic cases where tuning helps are: very high bandwidth-delay product links (cross-continent bulk transfer), and switching to BBR for lossy client networks.

For a typical API service, the wins are elsewhere entirely — connection reuse, fewer round trips, smaller payloads. Kernel tuning is where people go when they have run out of real ideas.

## Codebase

**Repo:** `torvalds/linux` (targeted) and `google/bbr` documentation

**Question to answer:** In CUBIC, exactly what happens to `cwnd` on a fast retransmit versus a timeout? Find both code paths. Then answer: what signal does BBR use instead of loss, and why does that make it better on WiFi?

**Read, in order:**

1. `net/ipv4/tcp_cubic.c` — `bictcp_cong_avoid` and `bictcp_recalc_ssthresh`. The cubic growth function is right there and it is well commented
2. `net/ipv4/tcp_input.c` — find `tcp_fastretrans_alert`. This is loss detection. Large, so search rather than read linearly
3. `net/ipv4/tcp_bbr.c` — read the long comment block at the top of the file. It is an excellent essay on why loss-based control is wrong for modern networks
4. `net/ipv4/tcp_output.c` — `tcp_write_xmit`, where the window limits are actually applied

⚠️ This is kernel C and it is dense. **Read the comments, skim the code.** The comment at the top of `tcp_bbr.c` alone is worth the session.

**Much more practical alternative if kernel source is too much:** read `Lib/asyncio/selector_events.py`'s `_maybe_pause_protocol` and uvicorn's `pause_reading`, and trace how application-level backpressure becomes TCP-level backpressure. Same concept, code you can act on.

**Size:** 1 session.

## Exercise

**Drill 2.3 — Make the network bad on purpose**

`tc netem` and `ss -ti` throughout. This drill produces numbers you will quote for years.

```
drills/02-congestion/
├── setup/
│   ├── netem.sh          # apply and clear conditions
│   └── measure.sh        # ss -ti sampling during a transfer
├── loss/
│   ├── sweep.py          # 0, 0.1, 0.5, 1, 2, 5% loss vs throughput
│   └── PLOT.md
├── latency/
│   ├── bdp.py            # throughput vs RTT at fixed bandwidth
│   └── slow_start.py     # time to full speed for various payload sizes
├── flow/
│   ├── slow_reader.py    # receiver reads 1KB/sec
│   ├── watch_window.sh   # observe the window shrink to zero
│   └── FINDINGS.md
├── algorithms/
│   ├── compare.sh        # cubic vs bbr under identical conditions
│   └── RESULTS.md
├── payload/
│   ├── sizes.py          # 1KB..10MB transfer time vs size
│   └── ROUNDTRIPS.md
└── README.md
```

**Part 1 — The loss curve.** Fixed 100ms RTT. Sweep loss from 0% to 5%. Transfer 10MB each time. Chart throughput against loss.

**Predict the shape before you run it.** Almost everyone predicts linear. The actual curve is a cliff. This chart is the single most useful artifact in section 02.

**Part 2 — Slow start, visible.** Fixed 100ms RTT, no loss. Transfer 10KB, 100KB, 1MB, 10MB. Chart time-to-completion against size, and separately chart effective throughput.

Sample `ss -ti` every 10ms during the 10MB transfer and plot `cwnd` over time. You will see the exponential ramp and the transition to linear growth with your own eyes.

Then compute: for a 100KB payload, what fraction of total time was slow start? **This number is the argument for connection reuse.**

**Part 3 — Bandwidth-delay product.** Fixed bandwidth (say 100 Mbps via netem). Sweep RTT: 1ms, 10ms, 50ms, 100ms, 300ms. Chart throughput.

Then deliberately cap the receive buffer small (`SO_RCVBUF`) and repeat. Show that a small window makes throughput collapse on high-RTT links even with zero loss. Calculate the BDP for each RTT and confirm the window needs to match it.

**Part 4 — Flow control, watched.** Server sending as fast as it can, client reading 1KB per second.

Sample `ss -ti` on both sides. Watch the receive window shrink to zero. Watch the sender stop. Watch `Send-Q` on the sender fill.

Then make the client stop reading entirely and observe zero window probes in `tcpdump`. **This is the exact mechanism behind [[01.11 - Backpressure Inside One Process]], seen at the packet level.**

**Part 5 — CUBIC vs BBR.** Identical conditions, both algorithms, three scenarios:

| Scenario | Expect |
|---|---|
| Clean link, 100ms RTT | Similar |
| 1% loss, 100ms RTT | BBR substantially better |
| Deep buffer (bufferbloat) | BBR much lower latency |

For the third, add a large netem buffer and measure ping latency **during** a bulk transfer. CUBIC will fill the buffer and destroy interactive latency. BBR will not.

**Part 6 — Round trips are what cost.** Measure the total time to transfer payloads from 1KB to 10MB, at 5ms and 200ms RTT.

Compute how many round trips each took. Then rerun with a pre-warmed connection (skipping handshake and slow start) and show the difference.

**Done when:**
- Your loss curve shows the cliff, and you can explain the `1/√loss` relationship
- You have plotted `cwnd` over time during a real transfer
- Part 3 shows the receive window limiting throughput independently of loss
- You have watched the window go to zero and seen the sender obey
- The BBR comparison table has all three scenarios
- `ROUNDTRIPS.md` states, with your numbers, how much of a small transfer is handshake and slow start
