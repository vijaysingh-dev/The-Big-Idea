# Cookies

Small key-value pairs the browser stores per domain and **sends automatically with every matching request**. That automatic transmission is both their defining feature and their main hazard.

## Anatomy

```
Set-Cookie: session=abc123; Domain=example.com; Path=/; Max-Age=3600;
            Secure; HttpOnly; SameSite=Lax
```

| Attribute | Effect |
| --- | --- |
| `Domain` | which host and subdomains receive it |
| `Path` | which URL prefix receives it |
| `Expires` / `Max-Age` | when it is deleted; absent means session cookie |
| `Secure` | HTTPS only |
| `HttpOnly` | invisible to `document.cookie` |
| `SameSite` | whether it is sent on cross-site requests |
| `Partitioned` | separate storage per top-level site (CHIPS) |

Size limit is about 4 KB per cookie, with roughly 50 cookies per domain. Since they ride along on every request, large cookies add latency to every single request to that origin — a real cost that people underestimate.

## SameSite

The most consequential attribute, and the one that changed most recently.

- **`Strict`** — never sent on cross-site requests, including top-level navigation. A user clicking a link to your site from an email arrives logged out.
- **`Lax`** — sent on top-level GET navigations, not on cross-site POST, iframes, images or fetches. This is the modern default when the attribute is absent.
- **`None`** — sent on all cross-site requests. **Requires `Secure`.**

`Lax` blocks the classic CSRF vector, where an attacker's page submits a form to your site and the browser attaches the session cookie ([[15.6 - Frontend Security]]).

`None` is needed for genuinely cross-site use — a third-party widget, an embedded iframe, an SSO provider on a different registrable domain. But third-party cookies are being restricted or blocked entirely across browsers, so `SameSite=None` is increasingly unreliable.

**CHIPS** (`Partitioned`) is the sanctioned path forward: a third-party cookie that is partitioned by top-level site, so an embed on `a.com` and the same embed on `b.com` get separate cookie jars. No cross-site tracking, but the embed still works.

Note that "same-site" is not "same-origin": `app.example.com` and `api.example.com` are the same site (same registrable domain) but different origins. A `SameSite=Lax` cookie works fine between them; CORS still applies separately ([[15.3 - Same Origin Policy and CORS]]).

## HttpOnly

```
Set-Cookie: session=abc; HttpOnly
```

Makes the cookie unreadable from JavaScript. If an XSS vulnerability exists, the attacker cannot exfiltrate the session token — which is the single strongest argument for storing auth tokens in cookies rather than `localStorage` ([[15.5 - JWT Sessions and Token Storage]]).

It is not a complete defense: an attacker with XSS can still *make requests* using the cookie, since the browser attaches it automatically. But they cannot steal it for later use on their own machine, which meaningfully limits the damage.

## Reading and writing from JavaScript

```js
document.cookie = "theme=dark; path=/; max-age=31536000; samesite=lax";
document.cookie;   // "theme=dark; lang=en" — all readable cookies, no attributes
```

The API is genuinely poor: assignment sets one cookie, reading returns a concatenated string with no attributes, and there is no delete — you overwrite with a past expiry:

```js
document.cookie = "theme=; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT";
```

Deletion requires matching `path` and `domain` exactly, which is a common source of "the cookie won't go away".

The Cookie Store API is the modern replacement, async and sane, but support is still incomplete:

```js
await cookieStore.set({ name: "theme", value: "dark", sameSite: "lax" });
await cookieStore.get("theme");
await cookieStore.delete("theme");
```

For most projects, `js-cookie` remains the pragmatic choice.

## Cookies vs Web Storage

| | Cookies | localStorage / sessionStorage |
| --- | --- | --- |
| Sent to server | automatically, every request | never |
| Size | ~4 KB | ~5–10 MB |
| Server-writable | yes | no |
| JS-readable | unless `HttpOnly` | always |
| Expiry | built in | manual |
| API | string parsing | key-value, synchronous |
| SSR-readable | yes | no |

The last row matters more than it appears: in a server-rendered application, cookies are the only client storage the server can read during the initial request. Theme preference, locale and auth state that must affect the first HTML render all belong in cookies for this reason — storing the theme in `localStorage` causes the flash-of-wrong-theme problem ([[10.4 - Units Custom Properties and Theming]]).

## What belongs in a cookie

**Yes:** session identifiers, auth tokens (with `HttpOnly`, `Secure`, `SameSite`), CSRF tokens, locale, theme when SSR needs it, A/B test assignment when it affects server rendering.

**No:** anything large, anything the server does not need, user preferences that only affect client behavior, cached data. Every kilobyte in a cookie is a kilobyte on every request.

## Consent and regulation

In the EU, non-essential cookies require consent before being set — and the ePrivacy Directive covers `localStorage` too, despite the common belief that it applies only to cookies. India's DPDP Act and similar regimes elsewhere impose comparable requirements.

Practically this means: strictly necessary cookies (session, CSRF, load balancing) may be set immediately; analytics and advertising cookies must wait for consent. Third-party scripts that set cookies must be loaded conditionally, not merely blocked from firing.

Note that consent banners injected above content are a common CLS cause ([[13.5 - Core Web Vitals]]) — overlay them rather than pushing the page down.

## A secure default

For an authenticated application:

```
Set-Cookie: session=<opaque-id>; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1800
```

Plus a `__Host-` prefix where possible:

```
Set-Cookie: __Host-session=abc; Path=/; Secure; HttpOnly; SameSite=Lax
```

The `__Host-` prefix is enforced by the browser: the cookie must be `Secure`, must have `Path=/`, and must **not** have a `Domain` attribute. That last constraint prevents a compromised subdomain from setting a cookie that the parent domain will accept — a real attack class known as subdomain cookie tossing.

## How senior engineers actually use this

**They keep auth in `HttpOnly` cookies** rather than `localStorage`, accepting the CSRF mitigation work in exchange for XSS resistance.

**They set `SameSite=Lax` as the baseline** and only relax it with a specific documented reason.

**They keep cookies small.** A 2 KB cookie on a page making 40 requests is 80 KB of pure overhead per page load.

**They use `__Host-` prefixes** for session cookies where the deployment allows it.

**They read cookies server-side for anything affecting the first render** — theme, locale, feature flags.

## Common pitfalls

- `SameSite=None` without `Secure`, so the cookie is silently rejected.
- Deleting a cookie without matching `path` and `domain`.
- Storing JWTs in `localStorage` and treating XSS as a theoretical risk.
- Large cookies adding latency to every request.
- Assuming `SameSite=Lax` prevents all CSRF — it does not cover GET-based state changes, which is one more reason state changes should never be GET.
- Setting analytics cookies before consent.
- Confusing same-site with same-origin when debugging cross-subdomain auth.

## Interview angle

"Cookies vs localStorage vs sessionStorage" is a standard question — cover automatic transmission, size, server access, and the SSR-readability point which most candidates miss. Follow-ups usually go to security: `HttpOnly` for XSS resistance, `SameSite` for CSRF, `Secure` for transport. Being able to explain why an `HttpOnly` cookie is safer than `localStorage` for tokens, *and* that it is not a complete XSS defense, is the nuanced answer.
