# Inheritance Composition and Protocols

#python #oop #inheritance #protocols

> **In one line:** Inheritance shares behaviour along the MRO, and `super()` follows that MRO, not "the parent". ABCs enforce an interface by inheritance, `Protocol` describes one structurally without inheritance, and most of the time composition is simpler than either.

---

## Single Inheritance

```python
class Notifier:
    def __init__(self, sender):
        self.sender = sender
    def send(self, user, msg):
        raise NotImplementedError
    def notify(self, user, msg):
        if user.opted_in:
            self.send(user, msg)

class EmailNotifier(Notifier):
    def __init__(self, sender, smtp):
        super().__init__(sender)       # always call the parent __init__
        self.smtp = smtp
    def send(self, user, msg):
        self.smtp.send(self.sender, user.email, msg)
```

Rules worth remembering:

- A subclass that defines `__init__` must call `super().__init__(...)`, or parent state is never set up.
- Overriding a method replaces it. Call `super().method()` to extend instead.
- `isinstance(x, Notifier)` is true for subclasses. `type(x) is Notifier` is not. Use `isinstance`.

## The MRO and super()

With multiple inheritance, Python computes a **method resolution order** (MRO) using the C3 algorithm: a single linear order where each class appears before its parents and the order of bases is kept.

```python
class Base:
    def save(self): print("Base")
class TimestampMixin(Base):
    def save(self): print("Timestamp"); super().save()
class AuditMixin(Base):
    def save(self): print("Audit"); super().save()
class Order(TimestampMixin, AuditMixin):
    def save(self): print("Order"); super().save()

Order.__mro__
# (Order, TimestampMixin, AuditMixin, Base, object)
Order().save()
# Order → Timestamp → Audit → Base
```

💡 **`super()` means "the next class in the MRO of the instance's type", not "my parent".** Inside `TimestampMixin.save`, `super()` reaches `AuditMixin`, a class `TimestampMixin` knows nothing about. That is what lets mixins cooperate, and it is why every method in a cooperative chain must call `super()` and accept `**kwargs` it does not use.

## Mixins

A mixin is a small class that adds one capability and is not meant to stand alone:

```python
class JsonMixin:
    def to_json(self):
        return json.dumps(self.__dict__, default=str)

class ReprMixin:
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}" for k, v in vars(self).items())
        return f"{type(self).__name__}({fields})"

class User(ReprMixin, JsonMixin):
    def __init__(self, name): self.name = name
```

Django class-based views and DRF viewsets are built this way (`ListModelMixin`, `CreateModelMixin`, ...). Mixins are fine for small, orthogonal behaviours. Deep mixin stacks become hard to follow: to understand one method call you must read the whole MRO.

## Abstract Base Classes

An ABC declares methods subclasses **must** implement, and refuses to instantiate incomplete subclasses:

```python
from abc import ABC, abstractmethod

class PaymentProvider(ABC):
    @abstractmethod
    def charge(self, amount_cents: int, token: str) -> str: ...
    @abstractmethod
    def refund(self, charge_id: str) -> None: ...

class Stripe(PaymentProvider):
    def charge(self, amount_cents, token): ...

Stripe()   # TypeError: Can't instantiate abstract class Stripe without an implementation for abstract method 'refund'
```

The error comes at **instantiation**, not when `refund` is first called in production. ABCs also provide `register()` for "virtual subclasses" and are what `collections.abc` is built on.

## Protocols: Structural Typing

A `Protocol` describes what an object must look like, and **any** class with those methods matches, without inheriting:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class SupportsSend(Protocol):
    def send(self, to: str, body: str) -> None: ...

class SmtpClient:                       # does not inherit SupportsSend
    def send(self, to: str, body: str) -> None: ...

class FakeSender:                       # a test double, also no inheritance
    def __init__(self): self.sent = []
    def send(self, to: str, body: str) -> None: self.sent.append((to, body))

def welcome(sender: SupportsSend, email: str) -> None:
    sender.send(email, "Welcome!")

welcome(SmtpClient(), "a@x.com")        # type checker: OK
welcome(FakeSender(), "a@x.com")        # OK
isinstance(FakeSender(), SupportsSend)  # True (runtime_checkable checks method NAMES only)
```

| | ABC | Protocol |
|---|---|---|
| Matching | Nominal: must inherit (or `register`) | Structural: has the right methods |
| Checked | At runtime (instantiation) | By the type checker. Runtime `isinstance` only with `@runtime_checkable`, and only method presence |
| Good for | Frameworks and plugin bases you own, where shared implementation helps | Interfaces for dependencies: repositories, clients, senders. Third-party classes match without changes. |

Protocols are Python's version of Go interfaces, and they make dependency inversion easy: the business logic declares the protocol it needs, and infrastructure satisfies it. See [[01.1 - SOLID Principles]] (the D in SOLID) and [[02.20 - Repository Pattern]] in the LLD guide.

## Composition Over Inheritance

```python
# Inheritance: an OrderService IS-A Repository? No.
class OrderService(PostgresRepository): ...

# Composition: an OrderService HAS-A repository, a payment provider, a notifier
class OrderService:
    def __init__(self, repo: OrderRepo, payments: PaymentProvider, notifier: SupportsSend):
        self.repo, self.payments, self.notifier = repo, payments, notifier
```

| Prefer inheritance when | Prefer composition when |
|---|---|
| There is a true "is-a" relationship and subclasses really are substitutable (Liskov) | You want to reuse behaviour, not identity |
| A framework expects it (Django models, `Exception` subclasses, Pydantic models) | Parts vary independently: swap the payment provider without touching notifications |
| The hierarchy is shallow (one or two levels) | You want to test with fakes: pass a `FakeSender` |

⚠️ **Inheriting from built-in types (`dict`, `list`, `str`) is a trap**: their C methods skip your overrides. Use `UserDict` and friends, or composition ([[05.3 - The collections Module]]).
