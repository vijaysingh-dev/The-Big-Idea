# Platform Encryption

## What it actually does

Encrypts field data **at rest**, with a key you control.

Salesforce already encrypts data at rest at the infrastructure level. Platform Encryption adds **key management** — a tenant secret you generate, rotate, and can destroy.

**Why that distinction matters:** for some contracts and regulations, "the vendor encrypts it" is not sufficient and "we hold the key" is the requirement. If that is not your requirement, Platform Encryption is buying functional restrictions for no benefit.

**What it does not protect against:** an authorized user reading the data, a compromised account, or a query returning data the sharing model should have hidden. Encryption is not access control.

## The two modes

The most consequential decision, made per field.

**Probabilistic** — the same plaintext encrypts to a different ciphertext each time. Cryptographically stronger.

```
'Priya Sharma' → 8f3a2b...
'Priya Sharma' → c91d47...   (same input, different output)
```

**Deterministic** — the same plaintext always encrypts to the same ciphertext. Weaker, and it enables filtering.

```
'Priya Sharma' → 8f3a2b...
'Priya Sharma' → 8f3a2b...   (same every time)
```

**The tradeoff:**

| | Probabilistic | Deterministic |
| --- | --- | --- |
| Cryptographic strength | Stronger | Weaker |
| Exact-match `WHERE` | No | Yes |
| Sorting | No | No |
| Range filtering | No | No |
| `LIKE` | No | No |
| Unique fields | No | Case-sensitive only |
| Vulnerable to frequency analysis | No | Yes |

**Deterministic encryption leaks information.** An attacker with database access can see that two records share a value, and can infer which value from frequency — a field where 60% of records share one ciphertext is probably the most common value.

**Choose deterministic only where filtering is genuinely required**, and understand that it is a weaker guarantee.

## What breaks

The list to work through before encrypting anything.

```
SOQL WHERE            probabilistic: no filtering at all
                      deterministic: exact match only, no LIKE, no ranges
ORDER BY              not supported in either mode
Formula fields        cannot reference an encrypted field
Roll-up summaries     cannot aggregate an encrypted field
External IDs          cannot be encrypted
Unique fields         deterministic only, case-sensitive
SOSL                  encrypted fields are not searchable
Report filtering      severely limited
List view filtering   severely limited
Custom indexes        not available on encrypted fields
Skinny tables         encrypted fields cannot be included
Duplicate rules       matching on an encrypted field does not work
Lookup filters
Territory rules
Some managed packages fail if they filter on an encrypted field
```

**The one that surprises people most:** an encrypted field cannot be used in a formula. A `Full_Name__c` formula concatenating `FirstName` and `LastName` breaks the moment either is encrypted.

**The second:** search. Encrypting a field removes it from the search index, so users cannot find records by it. Encrypting `Phone` means nobody can search by phone number.

## Choosing fields

The design exercise that determines whether the implementation succeeds.

**Encrypt what the requirement names**, and nothing more. "Encrypt all PII" is not a requirement; it is a phrase that produces a broken org.

For each candidate field:

```
[ ] Is it filtered in any report, list view, or query?
[ ] Is it sorted anywhere?
[ ] Is it referenced by a formula or roll-up?
[ ] Is it searched?
[ ] Is it used by an integration for matching?
[ ] Is it a unique field or an external ID?
[ ] Does a managed package filter on it?
```

**Any yes means the field either stays unencrypted or the dependent functionality changes.**

**A worked example.** Northwind wants customer contact details encrypted:

```
Contact.Email          filtered by an integration matching on email → deterministic
Contact.Phone          searched by agents → do not encrypt; mask instead
Contact.MailingStreet  never filtered or sorted → probabilistic
Contact.Name           formula fields reference it → do not encrypt
Warranty_Claim__c.Fault_Description__c   free text, never filtered → probabilistic
```

**Three of five encrypted, two rejected for functional reasons.** That is a normal outcome, and it is why the analysis matters more than the enablement.

## What can be encrypted

```
Standard fields        a defined subset — Account.Name, Contact.Email, Case.Subject,
                       and many others, not all
Custom fields          Text, Text Area, Long Text Area, Rich Text, URL, Date, DateTime,
                       Email, Phone, Number (in some releases)
Files and attachments  ContentVersion, Attachment bodies
Chatter feed
Search index
Event Monitoring log files
CRM Analytics datasets
```

**Not everything.** Picklists, checkboxes, lookups, formula fields, and auto-numbers cannot be encrypted, which is occasionally the answer to a requirement — the data cannot be encrypted, so a different control is needed.

## Key management

```
Setup → Platform Encryption → Key Management

Generate Tenant Secret     Salesforce generates and stores the key material
Bring Your Own Key (BYOK)  you supply the key material
Cache-Only Key Service     the key is fetched from your endpoint per session, never stored
```

**Tenant secret** is the default. Salesforce holds the derived key.

**BYOK** means you generate the key material and upload it, which satisfies "we control the key" for most contractual purposes.

**Cache-Only Key Service** is the strongest — Salesforce never stores the key, fetching it from an endpoint you host on each session. **If your endpoint is unavailable, encrypted data is unreadable.** That is the point and it is an availability commitment worth understanding before adopting it.

**Key rotation:**

```
Generate a new tenant secret → new data uses the new key
                             → existing data continues using the old key
                             → run "Sync Data" to re-encrypt with the current key
```

**Old keys must be retained** until every record has been re-encrypted. Destroying a key before syncing makes that data permanently unreadable.

**Destroying a key destroys the data.** That is sometimes deliberate — a crypto-shredding approach to data deletion — and it is irreversible.

## Enabling it

```
Setup → Platform Encryption → Encryption Policy → Encrypt Fields
```

**Encryption applies to new data immediately.** Existing data is encrypted by a background process, which for a large object takes hours to days.

```
Setup → Platform Encryption → Encryption Statistics → Sync Data
```

**Check the statistics before assuming it worked.** A field marked encrypted with unsynced existing data is partially encrypted, and queries behave inconsistently across the two sets.

## Testing before committing

Encrypting a field in production without testing is how a reporting outage happens.

**In a Full sandbox with production-shaped data:**

```
1. Enable encryption on the candidate fields
2. Run every report that references them
3. Run every list view
4. Test every integration that filters on them
5. Test search
6. Run the full Apex test suite
7. Test the managed packages
```

**Reports and list views are where the failures appear**, and they fail in a way that produces an error rather than wrong data — which is at least visible.

**Integrations fail more quietly.** An integration filtering on an encrypted field returns nothing rather than erroring, and the sync silently stops working.

```java
// Returns nothing once Email is probabilistically encrypted, with no error
List<Contact> matches = [SELECT Id FROM Contact WHERE Email = :incomingEmail];
```

**That silent failure is the main operational risk**, and it argues for reviewing every integration's filter fields before enabling encryption.

## Apex and encrypted fields

Reading and writing work normally — the platform decrypts for authorized users.

```java
// Works: the field is decrypted transparently
Contact contact = [SELECT Id, Email FROM Contact WHERE Id = :contactId];
String email = contact.Email;
```

```java
// Fails with probabilistic encryption
List<Contact> matches = [SELECT Id FROM Contact WHERE Email = :searchEmail];

// Works with deterministic encryption
List<Contact> matches = [SELECT Id FROM Contact WHERE Email = :searchEmail];

// Fails in both modes
List<Contact> matches = [SELECT Id FROM Contact WHERE Email LIKE '%northwind.com'];
```

**Detecting encryption at runtime:**

```java
Schema.DescribeFieldResult field = Contact.Email.getDescribe();
Boolean isEncrypted = field.isEncrypted();
```

Useful in a packaged application that must behave differently when a subscriber has encrypted a field it filters on.

**The pattern for a filter that may be encrypted:**

```java
public static List<Contact> findByEmail(String email) {
    // deterministic encryption supports equality; probabilistic supports nothing,
    // so the fallback matches in memory over a bounded set
    if (Contact.Email.getDescribe().isEncrypted() && !isDeterministic()) {
        return filterInMemory(email);
    }
    return [SELECT Id, Email FROM Contact WHERE Email = :email WITH USER_MODE];
}
```

Awkward, and it is what encryption forces on code that filters.

## Masking versus encryption

Frequently the better answer, and frequently overlooked.

**Encryption** protects data at rest from someone with database access.

**Masking** hides data from users who should not see it, in the interface.

**For most requirements, the actual concern is who can see the data** — which is field-level security, not encryption.

```
Requirement                                  Control
"Agents should not see full card numbers"    field-level security, or a masked formula
"Data must be encrypted at rest with our key" Platform Encryption
"Sandbox data must not contain real PII"     Data Mask
"Only the account team should see this"      sharing model
```

**Encrypting a field that field-level security already hides adds nothing** and breaks reports.

## The permission to view encrypted data

```
Permission: View Encrypted Data
```

Without it, a user sees masked values. With it, plaintext.

**This is Classic Encryption's model**, not Platform Encryption's — Platform Encryption decrypts for anyone with field-level access, and the permission applies to the older encrypted text field type.

Confusing the two is common. Platform Encryption is not a visibility control.

## Costs and limits

```
Included with Shield, or purchasable separately
Encrypted fields cannot exceed a per-object limit
Deterministic encryption has a lower field limit than probabilistic
Some editions restrict which standard fields can be encrypted
Filtering performance is affected even in deterministic mode
```

**Performance:** encrypted field access has overhead, and a query filtering on a deterministically encrypted field is slower than one on a plain indexed field. Measurable at volume rather than at small scale.

## A decision framework

```
1. What is the actual requirement?
     "customer-managed keys" → Platform Encryption
     "hide from some users"   → field-level security
     "no PII in sandboxes"    → Data Mask
     "prove who accessed it"  → Event Monitoring

2. For each candidate field, is it filtered, sorted, searched,
   or referenced by a formula, roll-up, or integration?

3. Probabilistic unless filtering is required.

4. Test in a Full sandbox with production data — reports,
   list views, integrations, search, and the test suite.

5. Enable, sync, and verify the statistics.
```

**Step 1 is the one that gets skipped**, and skipping it produces encryption on fields that did not need it and functional breakage nobody predicted.

## Practical guidance

**Establish the actual requirement first.** Encryption is one control among several and rarely the right one.

**Encrypt the fewest fields that satisfy it.**

**Probabilistic by default**, deterministic only where filtering is required and the weaker guarantee is acceptable.

**Check every filter, sort, formula, roll-up, and integration** before encrypting a field.

**Test in a Full sandbox with production data** — reports and integrations are where it breaks.

**Watch for silent integration failure**, where a filter returns nothing rather than erroring.

**Verify the encryption statistics** after enabling; existing data syncs in the background.

**Retain old keys** until the sync completes.

**Understand that destroying a key destroys the data.**
