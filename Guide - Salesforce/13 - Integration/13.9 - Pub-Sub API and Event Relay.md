# Pub-Sub API and Event Relay

## The current mechanism for external subscribers

The Pub/Sub API is a **gRPC** service for publishing and subscribing to platform events and change events from outside Salesforce. It replaces CometD for external consumers.

What it improves over Streaming API:

**Binary protocol.** Events are Avro-encoded rather than JSON over long-polling, which is meaningfully more efficient at volume.

**Flow control.** The subscriber requests a number of events and receives up to that many. It cannot be overwhelmed, which CometD subscribers can be.

**Bidirectional.** The same connection publishes and subscribes.

**Explicit replay handling**, with a documented recovery model.

**One connection for many topics**, rather than one per channel.

## The service

Three RPCs matter:

```protobuf
service PubSub {
  rpc Subscribe (stream FetchRequest) returns (stream FetchResponse);
  rpc Publish (PublishRequest) returns (PublishResponse);
  rpc GetSchema (SchemaRequest) returns (SchemaInfo);
}
```

`Subscribe` is a **bidirectional stream**: the client sends `FetchRequest` messages asking for N events, and the server streams `FetchResponse` messages back. That request-driven model is the flow control.

`GetSchema` returns the Avro schema for a topic, which the client needs to decode payloads.

## Subscribing, in outline

```python
import grpc, avro.schema, avro.io, io
import pubsub_api_pb2 as pb2
import pubsub_api_pb2_grpc as pb2_grpc

channel = grpc.secure_channel('api.pubsub.salesforce.com:7443',
                              grpc.ssl_channel_credentials())
stub = pb2_grpc.PubSubStub(channel)

auth = (
    ('accesstoken', access_token),
    ('instanceurl', instance_url),
    ('tenantid', org_id),
)

def fetch_requests(replay_id=None):
    # requesting a fixed number of events is the flow control mechanism
    yield pb2.FetchRequest(
        topic_name='/event/Claim_Approved__e',
        replay_preset=pb2.ReplayPreset.CUSTOM if replay_id else pb2.ReplayPreset.LATEST,
        replay_id=replay_id,
        num_requested=100
    )

schema_cache = {}

for response in stub.Subscribe(fetch_requests(last_replay_id), metadata=auth):
    for event in response.events:
        schema_id = event.event.schema_id
        if schema_id not in schema_cache:
            schema_json = stub.GetSchema(pb2.SchemaRequest(schema_id=schema_id),
                                         metadata=auth).schema_json
            schema_cache[schema_id] = avro.schema.parse(schema_json)

        payload = decode(schema_cache[schema_id], event.event.payload)
        process(payload)

        # persisting the replay id after processing is what makes recovery possible
        persist_replay_id(event.replay_id)
```

Three things in that shape matter.

**Schemas are cached by Id.** Fetching the schema on every event is a wasted round trip; the schema Id changes only when the event definition changes.

**`num_requested` bounds the flow.** The subscriber asks for what it can handle.

**The replay Id is persisted after successful processing**, not on receipt. Persisting on receipt loses events that failed mid-processing.

## Replay presets

```
LATEST     new events only, from the moment of subscription
EARLIEST   everything currently retained
CUSTOM     resume from a specific replay Id
```

`CUSTOM` with a stored replay Id is the recovery path. A subscriber down for an hour resumes and catches up.

**Retention is 72 hours.** Down longer than that and the gap is permanent, requiring a reconciliation pass — usually a `SystemModstamp` query for the affected window.

Handling the case where a stored replay Id has aged out is not optional in a production subscriber:

```python
try:
    subscribe(replay_preset=CUSTOM, replay_id=stored_id)
except ReplayIdExpiredError:
    # the stored position is older than retention; reconcile, then resume from LATEST
    reconcile_from_systemmodstamp(since=last_successful_timestamp)
    subscribe(replay_preset=LATEST)
```

## Publishing into Salesforce

The same connection publishes, which is how an external system raises a platform event that Salesforce subscribers react to:

```python
payload = encode(schema, {
    'Claim_Id__c': 'a0X5g000001AbCdEAK',
    'External_Status__c': 'Payment Released',
    'CreatedDate': int(time.time() * 1000),
    'CreatedById': user_id
})

stub.Publish(pb2.PublishRequest(
    topic_name='/event/Erp_Update__e',
    events=[pb2.ProducerEvent(schema_id=schema_id, payload=payload)]
), metadata=auth)
```

Inside Salesforce, a platform event trigger or a platform event-triggered flow reacts:

```java
trigger ErpUpdateTrigger on Erp_Update__e (after insert) {
    ErpUpdateHandler.handle(Trigger.new);
}
```

This is a clean inbound pattern. The external system publishes an event rather than calling a REST endpoint, and Salesforce processes it asynchronously with its own limits — no synchronous coupling, no API allocation consumed per record in the same way. See [[12.8 - Platform Events]].

## Event Relay

For AWS-based architectures, **Event Relay** forwards Salesforce events to **Amazon EventBridge** with no subscriber code at all.

```
Platform Event or CDC
    → Event Relay configuration
        → Amazon EventBridge partner event bus
            → Lambda, Step Functions, SQS, Kinesis, whatever
```

Setup is configuration: a Named Credential pointing at AWS, an `EventRelayConfig` naming the channel, and the partner event source accepted on the AWS side.

What it removes: writing and operating a gRPC subscriber, handling replay, managing connections, and monitoring a long-lived process. For a team already on AWS, that is most of the integration work.

What it costs: less control. Filtering, transformation, and error handling all move to the AWS side, and the relay itself is a black box when something does not arrive.

**Channels and filtering.** A custom channel can group several event types and apply a filter, so the relay forwards only what matters rather than everything:

```
ChannelName:  Claim_Events__chn
Members:      Claim_Approved__e, Claim_Rejected__e
Filter:       Claim_Amount__c > 100000
```

Filtering at the source is worth doing — every relayed event counts against the delivery allocation.

## Pub/Sub versus the alternatives

| Need | Mechanism |
| --- | --- |
| External subscriber, high volume | Pub/Sub API |
| External subscriber on AWS, low effort | Event Relay |
| Lightning component | `empApi` over Streaming API |
| External system publishing into Salesforce | Pub/Sub API publish, or REST |
| Legacy subscriber already working | CometD, migrate when convenient |
| Bulk extract, latency not critical | Bulk API query on `SystemModstamp` |

That last row deserves emphasis. **Event streaming is not always the right answer.** A nightly warehouse load is simpler, cheaper, and more robust as a Bulk API query filtered on `SystemModstamp` than as a streaming subscriber that must be operated continuously.

Streaming earns its place when **latency matters** or **deletions must be tracked** — a polling query cannot see a deleted record. See [[12.9 - Change Data Capture]].

## Limits

- **Daily delivery allocation**, counted **per subscriber**. Five systems on one event is five deliveries.
- **Concurrent subscriber connections** per org
- **72-hour retention**
- **Publish allocation** by edition, with purchasable add-ons
- **Maximum event size**

The per-subscriber delivery count is the one that surprises orgs adding consumers over time. Each new subscriber multiplies consumption on every event it receives, and the allocation is org-wide.

## Operating a subscriber

The things that make the difference between a subscriber that works and one that quietly stops.

**Persist the replay Id after processing**, transactionally with whatever the processing wrote.

**Handle expired replay Ids** with a reconciliation path.

**Reconnect with backoff.** gRPC streams drop; a subscriber must reconnect rather than exit.

**Monitor lag.** `EventBusSubscriber` shows position against tip:

```sql
SELECT Topic, Type, Position, Tip, Status, ExternalId
FROM EventBusSubscriber
WHERE Type = 'PubSub'
```

**Alert on absence.** A subscriber that has processed nothing for an hour, on a topic that normally sees traffic, is broken. Only a heartbeat or lag check detects this — the process appears healthy.

That last point is the one most often missing. A crashed subscriber produces no errors in Salesforce; it simply stops consuming, and the events age out of retention while nobody notices.

## Practical guidance

**Use Pub/Sub API for new external subscribers**, not CometD.

**Consider Event Relay first** if the consumer is on AWS. It removes most of the work.

**Cache schemas by Id.**

**Persist the replay Id after successful processing**, never on receipt.

**Handle expired replay Ids** with a reconciliation path.

**Filter at the source** with a custom channel, to conserve delivery allocation.

**Monitor lag and alert on silence**, not just on errors.

**Ask whether polling would do.** Streaming is more machinery, and it is only worth it when latency or deletions matter.
