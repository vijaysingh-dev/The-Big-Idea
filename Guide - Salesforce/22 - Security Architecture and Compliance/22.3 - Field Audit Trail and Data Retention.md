# Field Audit Trail and Data Retention

## Standard field history

Free, and limited.

```
Setup → Object Manager → object → Fields & Relationships → Set History Tracking
```

```
20 fields per object
Retained 18 months in the org, 24 months via the API
One row per tracked field per change
```

```sql
SELECT ParentId, Field, OldValue, NewValue, CreatedById, CreatedDate
FROM Warranty_Claim__History
WHERE ParentId = 'a0X5g000001AbCdEAK'
ORDER BY CreatedDate DESC
```

**History rows are created per field, per change.** Updating four tracked fields on 200 records creates 800 history rows, which is worth knowing before tracking everything.

**Long text areas record that the field changed, not the values.** `OldValue` and `NewValue` are null.

## What history is actually for

Three distinct uses, and they pull in different directions.

**Audit.** Regulatory or contractual proof of what changed and who changed it.

**Diagnosis.** "The status was wrong yesterday" — history is frequently the only record of the prior state, and it is what makes an incident correctable. See [[20.8 - Production Incident Playbook]].

**Analysis.** Time-in-stage reporting, approval cycle times, and similar. History is a poor tool for this; a snapshot object or explicit stage-history records are better. See [[04.8 - Opportunities and Sales Stages]].

**Choosing fields by use case rather than tracking broadly** is what keeps the volume manageable.

## Choosing which fields

The 20-field cap forces a decision, and the questions that resolve it:

```
[ ] Would we need to prove this value at a point in time?
[ ] Would we need to reverse a bad change to this field?
[ ] Does a regulation require it?
[ ] Is the field changed frequently enough to matter?
```

**For Northwind's warranty claim:**

```
Track:      Status__c            the approval state, needed for audit and reversal
            Approved_Amount__c   financial, needed for both
            Approver__c          who decided
            Asset__c             reparenting affects roll-ups; history explains discrepancies

Do not:     Fault_Description__c free text, changed often, no audit value
            Last_Contacted__c    high churn, no audit value
```

**High-churn fields with no audit value are the ones to exclude**, because they consume the cap and generate volume.

## Field Audit Trail

The Shield capability.

```
60 fields per object
Retained up to 10 years
History beyond 18 months moves to a big object
```

```
Setup → Field Audit Trail → Retention Policies
```

Retention is set per object per field-history type:

```java
Metadata.HistoryRetentionPolicy policy = new Metadata.HistoryRetentionPolicy();
policy.archiveAfterMonths = 18;
policy.archiveRetentionYears = 10;
policy.description = 'Warranty claim audit retention';
```

**Archived history lives in `FieldHistoryArchive`**, a big object:

```sql
SELECT FieldHistoryType, ParentId, Field, OldValue, NewValue, CreatedDate, CreatedById
FROM FieldHistoryArchive
WHERE FieldHistoryType = 'Warranty_Claim__c'
  AND ParentId = 'a0X5g000001AbCdEAK'
```

**Big object query constraints apply** — filtering must follow the index definition, which for `FieldHistoryArchive` means `FieldHistoryType`, then `ParentId`, then `CreatedDate`. Filtering on `Field` alone does not work. See [[02.15 - Big Objects]].

**Archived history does not appear in standard reports.** Surfacing it means a component, an Async SOQL job, or CRM Analytics.

## When Field Audit Trail is worth it

**Yes when:**

- A regulation names a retention period beyond 18 months
- Financial or medical data requires long-horizon audit
- Contractual obligations to customers require it
- More than 20 fields per object genuinely need tracking

**No when:**

- 18 months is sufficient
- The requirement is analysis rather than audit — a snapshot object serves better
- Nobody has defined the retention period

**The question that decides it:** what is the stated retention requirement, in writing? Without one, this is a purchase with no acceptance criterion.

## Setup Audit Trail

Different from field history, and frequently the more useful of the two.

**Records configuration changes**, not data changes.

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display, DelegateUser
FROM SetupAuditTrail
WHERE CreatedDate = LAST_N_DAYS:30
ORDER BY CreatedDate DESC
```

```
Six months of retention
Downloadable as CSV from Setup
Covers: deployments, field changes, permission changes, flow activation,
        user creation and deactivation, login policy changes, and much else
```

**This is the first query to run when something worked yesterday and does not today.** "Who deactivated the flow" has an answer here.

**Six months is the limit**, which means anything needing longer retention must be exported on a schedule:

```java
public with sharing class AuditTrailArchiveBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Action, Section, CreatedById, CreatedDate, Display
            FROM SetupAuditTrail
            WHERE CreatedDate = LAST_N_DAYS:7
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<SetupAuditTrail> scope) {
        List<Setup_Audit_Archive__b> archives = new List<Setup_Audit_Archive__b>();

        for (SetupAuditTrail entry : scope) {
            archives.add(new Setup_Audit_Archive__b(
                Changed_Date__c = entry.CreatedDate,
                Changed_By__c = entry.CreatedById,
                Action__c = entry.Action,
                Section__c = entry.Section,
                Detail__c = entry.Display
            ));
        }

        // insertImmediate is the big object write path; ordinary DML does not apply
        Database.insertImmediate(archives);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

A weekly job archiving to a big object gives indefinite retention at low storage cost, and it costs nothing beyond the job.

## Login and access history

```sql
SELECT UserId, LoginTime, SourceIp, LoginType, Status, Browser, Platform,
       Application, ApiType, ApiVersion, CountryIso
FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:30
```

**Six months of retention.**

**`Application` and `ApiVersion`** identify which integrations are connecting and on which API version — the retirement question, available without Shield. See [[01.11 - Release Cycle, Trust and Status]].

**`SourceIp` and `CountryIso`** are the anomaly signals. A login from an unexpected country, or from an IP outside the expected range, is worth an alert.

```sql
SELECT Id, UserId, EventDate, EventType, Application, SourceIp, LoginKey
FROM LoginIp
```

`LoginIp` records the IP addresses a user has activated, which is what the platform uses for its own verification challenges.

## Other retention constraints

The ones that appear in a retention conversation.

```
Debug logs            7 days, 1,000 MB org-wide
Recycle Bin           15 days, capacity-limited
Platform events       72 hours
CDC events            72 hours
PushTopic events      24 hours
Field history         18 months, or 10 years with Field Audit Trail
Setup Audit Trail     6 months
Login History         6 months
Event Monitoring logs 30 days, or 1 year with the add-on
Async job records     retained for a limited period
Email logs            30 days
```

**The 72-hour event retention is the one with operational consequence.** A subscriber down longer than that has a permanent gap requiring reconciliation. See [[13.9 - Pub-Sub API and Event Relay]].

## Designing a retention policy

The questions that produce a defensible answer.

**What must be retained, for how long, and why?** A regulation, a contract, or a business need — with the source named.

**What must be deleted, and when?** Right-to-erasure obligations and data minimization principles work the other way. See [[22.6 - GDPR, HIPAA and Compliance Patterns]].

**Where does it live?** In the org, in a big object, in a warehouse, or in a backup.

**Who can access it?** Archived audit data is still sensitive.

**How is it produced when asked for?** A retention policy nobody can satisfy on request is not a policy.

**A worked policy for Northwind:**

```
Warranty claim field history      7 years   regulatory — warranty liability period
Setup Audit Trail                 3 years   internal governance
Login History                     1 year    security
Application logs                  90 days   operational, Error and Fatal for 1 year
Closed claims                     7 years, then archived to a big object
Debug logs                        7 days    platform default, no requirement
```

**Each line names a reason.** A retention period with no stated reason is a guess that will be argued about later.

## Archiving records themselves

Beyond field history, the records.

```java
public with sharing class ClaimArchiveBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Number__c, Claim_Amount__c, Asset__c, Claim_Date__c, Status__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Closed' AND Claim_Date__c < LAST_N_YEARS:3
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        List<Claim_Archive__b> archives = new List<Claim_Archive__b>();

        for (Warranty_Claim__c claim : scope) {
            archives.add(new Claim_Archive__b(
                Asset_Id__c = claim.Asset__c,
                Claim_Date__c = claim.Claim_Date__c,
                Claim_Number__c = claim.Claim_Number__c,
                Claim_Amount__c = claim.Claim_Amount__c
            ));
        }

        Database.insertImmediate(archives);
        Database.delete(scope, false);
        // purging inside execute keeps the recycle bin from overflowing mid-job
        Database.emptyRecycleBin(scope);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Archiving improves everything else** — fewer rows makes queries faster, indexes more selective, reports quicker, and data loads cheaper. It is frequently the better answer to a performance problem than an index. See [[16.9 - Skinny Tables and Custom Indexes]] and [[23.4 - Archiving with Big Objects and External Storage]].

**Field history does not follow the record.** Deleting a claim deletes its history, which is why archiving must capture what the retention policy requires.

## Surfacing archived data

Archived data nobody can see is data that was effectively deleted.

```java
public with sharing class ClaimArchiveController {

    @AuraEnabled(cacheable=true)
    public static List<Claim_Archive__b> getArchivedClaims(Id assetId) {
        // big object filtering must follow the index definition, in order
        return [
            SELECT Claim_Number__c, Claim_Date__c, Claim_Amount__c
            FROM Claim_Archive__b
            WHERE Asset_Id__c = :assetId
            LIMIT 100
        ];
    }
}
```

A component on the Asset page showing archived claims alongside current ones means the archive is not a loss from the user's perspective — which is what makes archiving politically acceptable.

## Practical guidance

**Track history on fields needed for audit or reversal**, not broadly — the cap and the volume both matter.

**Do not use field history for analysis.** A snapshot object serves better.

**Archive `SetupAuditTrail` weekly** to a big object; six months is short.

**Name a reason for every retention period.**

**Buy Field Audit Trail only against a written retention requirement.**

**Remember archived history is not reportable** in the usual way.

**Archive old records**, and surface them so the archive is not a loss.

**Capture what the retention policy requires before deleting** — field history goes with the record.
