# Methods Status Codes and Semantics

#backend #http #api-design

> **In one line:** Methods and status codes are a contract that caches, proxies, browsers and client libraries act on automatically — get them wrong and infrastructure you do not control starts making bad decisions on your behalf.

---

## The Idea

It is tempting to treat HTTP semantics as etiquette. It is not. Real systems make real decisions based on them:

| Who | Decides based on |
|---|---|
| Browsers | Whether to warn on refresh, whether to cache |
| CDNs | Whether a response is cacheable at all |
| Load balancers | Whether it is safe to retry after a failure |
| Service meshes | Whether to retry, and how many times |
| HTTP clients | Whether to follow a redirect and with which method |
| Monitoring | What counts as an error |

💡 **The practical framing: methods and status codes are how you talk to infrastructure you did not write and cannot configure.** If you return 200 for a failure, your alerting is blind. If you make GET mutate state, a prefetcher or a retry will corrupt your data.

---

## Safe, Idempotent, Cacheable

Three properties that drive everything.

| Method | Safe | Idempotent | Cacheable | Body |
|---|---|---|---|---|
| `GET` | ✓ | ✓ | ✓ | No |
| `HEAD` | ✓ | ✓ | ✓ | No |
| `OPTIONS` | ✓ | ✓ | ✗ | No |
| `TRACE` | ✓ | ✓ | ✗ | No |
| `PUT` | ✗ | ✓ | ✗ | Yes |
| `DELETE` | ✗ | ✓ | ✗ | Rarely |
| `POST` | ✗ | ✗ | Rarely | Yes |
| `PATCH` | ✗ | ✗ | ✗ | Yes |

**Safe** — no intended side effect. The server may still log or count, but the client's *intent* is read-only.

**Idempotent** — sending it N times has the same effect as sending it once.

**Cacheable** — a shared cache may store and reuse the response.

### Why safe matters concretely

```python
@app.get("/documents/{id}/delete")     # WRONG
async def delete_document(id: int):
    await db.delete(id)
```

This will be triggered by: browser prefetching, a link crawler, a security scanner, a mesh retry, a user's browser extension. All of them assume GET is safe because the spec says so.

⚠️ **This is not a hypothetical.** The classic case is an admin panel with delete links, indexed by a crawler, which then deletes everything. It has happened to real companies more than once.

### Why idempotent matters concretely

A service mesh, load balancer or HTTP client will **automatically retry** idempotent methods on connection failure. It will not retry POST.

```
Client → POST /payments → (network fails after the server processed it)
```

Nobody retries automatically, because nobody can know whether the payment went through. That is correct behaviour, and it is why you need idempotency keys — [[03.4 - Idempotency and Safe Retries]].

## PUT vs POST vs PATCH

The distinction people get wrong most often.

### PUT — replace at a known URL

```http
PUT /documents/42
{"title": "Notes", "body": "..."}
```

The client chooses the URL. The body is the **complete** new state. Send it twice, same result — idempotent.

```python
@app.put("/documents/{doc_id}")
async def replace(doc_id: str, doc: DocumentIn):
    existing = await repo.get(doc_id)
    await repo.upsert(doc_id, doc)
    return Response(status_code=200 if existing else 201)
```

⚠️ **PUT replaces, so omitted fields must be cleared.** A PUT that only updates the fields you sent is not a PUT — it is a PATCH wearing the wrong label, and it breaks the idempotency guarantee clients rely on.

### POST — create, or anything else

```http
POST /documents
{"title": "Notes"}

201 Created
Location: /documents/42
```

The server chooses the URL. Not idempotent — twice means two documents.

POST is also the catch-all for operations that are not CRUD:

```http
POST /documents/42/reindex
POST /sources/7/sync
POST /exports
```

💡 **This is legitimate and not a REST failure.** Trying to model "reindex this document" as a PUT to some invented resource is worse than an honest POST to an action endpoint. Purity is not the goal; predictability is.

### PATCH — partial update

```http
PATCH /documents/42
Content-Type: application/merge-patch+json

{"title": "New title"}
```

Not idempotent **in general**, because a patch can be relative:

```json
{"op": "increment", "path": "/views", "value": 1}
```

Two standard formats exist:

| Format | Content-Type | Notes |
|---|---|---|
| JSON Merge Patch (RFC 7386) | `application/merge-patch+json` | Simple. `null` means delete. **Cannot set a field to null** |
| JSON Patch (RFC 6902) | `application/json-patch+json` | Operation list. Handles arrays and tests |

⚠️ **Merge Patch's inability to distinguish "delete this field" from "set it to null" is a real limitation.** If your domain has nullable fields that clients must be able to set to null, you need JSON Patch or a custom convention. Decide this early; retrofitting is painful.

### The decision

```
Client knows the URL, sends complete state       → PUT
Server assigns the URL                           → POST
Partial update of an existing resource           → PATCH
An action that is not really CRUD                → POST to an action endpoint
```

## Conditional Requests

Where methods and caching meet, and where you get optimistic concurrency for free.

```http
GET /documents/42
→ 200 OK
  ETag: "a1b2c3"
```

```http
GET /documents/42
If-None-Match: "a1b2c3"
→ 304 Not Modified          (no body — saves bandwidth)
```

```http
PUT /documents/42
If-Match: "a1b2c3"
→ 412 Precondition Failed   (someone else changed it since you read it)
```

💡 **`If-Match` on writes is optimistic concurrency control built into HTTP**, and almost nobody uses it. It solves the lost-update problem — two users editing the same document, the second silently overwriting the first — with no custom protocol.

```python
@app.put("/documents/{doc_id}")
async def replace(doc_id: str, doc: DocumentIn, request: Request):
    current = await repo.get(doc_id)
    if_match = request.headers.get("if-match")
    if if_match and if_match != current.etag:
        raise HTTPException(412, "document was modified")
    return await repo.update(doc_id, doc)
```

For Conduit's collaborative annotation this is directly relevant, and it is a strong thing to have implemented when someone asks how you handle concurrent edits.

`If-Unmodified-Since` is the date-based equivalent, with one-second resolution — usually too coarse. Prefer ETags.

## Status Codes, Properly

### The ones with behavioural consequences

| Code | Infrastructure behaviour |
|---|---|
| `201` | Should include `Location`. Clients follow it |
| `202` | Work accepted, not done. Client must poll or subscribe |
| `204` | **No body allowed.** Sending one breaks strict clients |
| `301` vs `308` | `301` allows changing POST→GET; `308` preserves the method |
| `302` vs `307` | Same distinction, temporary |
| `304` | No body. Client uses its cached copy |
| `401` | **Must include `WWW-Authenticate`.** Means "authenticate and retry" |
| `403` | Do not retry. Authentication will not help |
| `405` | **Must include `Allow`** listing permitted methods |
| `409` | Conflict. Retrying identically will fail again |
| `412` | Precondition failed. Re-read and retry |
| `413` / `414` / `431` | Too large: body / URI / headers |
| `422` | Well-formed but semantically invalid |
| `429` | **Must include `Retry-After`.** Clients and meshes honour it |
| `499` | nginx only. Client disconnected before the response |
| `503` | **Should include `Retry-After`.** Meshes back off accordingly |

⚠️ **`301`/`302` versus `307`/`308` is a real trap.** Historically browsers changed POST to GET on a 301 or 302 redirect. `307` and `308` were introduced to forbid that. If you redirect a POST with a 302, most clients will silently turn it into a GET and drop the body — and the resulting bug looks like your endpoint mysteriously received nothing.

### 401 vs 403

- **`401` Unauthorized** — actually means *unauthenticated*. "I do not know who you are. Send credentials." Must include `WWW-Authenticate`
- **`403` Forbidden** — "I know who you are, and you may not do this." Retrying with the same credentials is pointless

💡 A third option is worth considering: for resources a user must not even know exist, return **`404`** rather than `403`. `403` confirms the resource exists, which is an information leak in a multi-tenant system. Conduit needs this — a user in org A probing for org B's document IDs should get 404, not 403.

### 400 vs 422

- **`400`** — the request is malformed. Broken JSON, missing required header
- **`422`** — the request parsed fine but the content is wrong. Email field is not an email, end date before start date

FastAPI returns `422` for Pydantic validation failures. Some API style guides prefer `400` for everything. Either is defensible; **be consistent**, and document which you use.

### Error bodies

A status code alone is not enough. Use RFC 9457 Problem Details:

```json
{
  "type": "https://api.conduit.local/errors/quota-exceeded",
  "title": "Storage quota exceeded",
  "status": 413,
  "detail": "Organisation is using 10.2 GB of a 10 GB quota",
  "instance": "/documents",
  "quota_bytes": 10737418240,
  "used_bytes": 10952166605
}
```

`Content-Type: application/problem+json`.

💡 **The `type` URI is the machine-readable error code.** Clients branch on it. The `title` and `detail` are for humans. Extension members carry structured data. This is much better than a bare `{"error": "something went wrong"}` and it costs nothing to adopt. Covered further in [[05.3 - Error Design]].

## In Production

### Getting semantics wrong has costs

| Mistake | Consequence |
|---|---|
| GET that mutates | Crawlers, prefetchers and retries corrupt data |
| 200 for errors | Alerting is blind. Every dashboard lies |
| POST for everything | No caching, no safe retries, no conditional requests |
| 500 for client errors | Your error rate looks terrible; real problems are hidden |
| No `Retry-After` on 429 | Clients retry immediately and make it worse |
| 302 on a POST | Body silently dropped |
| 403 instead of 404 in multi-tenant | Existence leaked across tenants |
| `Allow` missing from 405 | Clients cannot discover the right method |

### The error rate problem

If your service returns 200 with `{"success": false}`, then:

- Your load balancer thinks every request succeeded
- Your SLO dashboard shows 100% availability during an outage
- Your alerting never fires
- Your mesh never retries or trips a circuit breaker

⚠️ **This is a genuinely common anti-pattern**, usually introduced because "the frontend team finds error codes awkward". The cost is that your entire observability stack becomes useless. Fix the client instead.

### Separating client errors from server errors

```
4xx → the client's fault. Do not page anyone. Track it, and if it spikes, something changed
5xx → your fault. Page someone
```

Keep them as separate metrics. A 4xx spike usually means a client deployed a bug or someone is probing you. A 5xx spike means you broke something. **Alerting on a combined error rate produces noise and trains people to ignore it.**

### Method-based routing decisions

```nginx
# Only cache safe methods
proxy_cache_methods GET HEAD;

# Retry only idempotent requests
proxy_next_upstream error timeout non_idempotent;   # careful with this flag
```

```yaml
# Envoy / Istio
retryOn: 5xx,reset,connect-failure
retryRemoteLocalities: true
# by default, only idempotent methods are retried
```

If you make POST idempotent via idempotency keys, you can *safely* opt it into retries. But that is your decision to make explicitly, not a default to accept.

## Codebase

**Repo:** `saleor/saleor`, `encode/starlette`, and `kubernetes/kubernetes` (API conventions)

**Question to answer:** How does a real, large API map its operations onto HTTP methods and status codes, and where does it deviate from strict REST? Then: how does the Kubernetes API implement optimistic concurrency, and what does it return on conflict?

**Read, in order:**

1. `starlette/status.py` — every status code with its official name. Two minutes, and it is a useful reference
2. `starlette/exceptions.py` and `starlette/responses.py` — how status codes become responses, and note the special handling for 204 and 304 (no body)
3. `saleor/graphql/core/mutations.py` — an interesting contrast. GraphQL abandons HTTP status codes almost entirely and puts errors in the body. **Read this and form an opinion on whether that was a good idea.** It is a genuine tradeoff and a good interview topic
4. `kubernetes/staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go` — find `ResourceVersion`. This is optimistic concurrency, and the `Status` type is a well-designed structured error format that predates RFC 9457
5. Kubernetes API conventions doc: `contributors/devel/sig-architecture/api-conventions.md` — **the best written API design guide in any open-source project.** Read the sections on verbs, status codes and error responses

💡 The Kubernetes conventions document is worth reading in full even though it is not Python. It is the most rigorous treatment of resource-oriented API design that exists in public, and it was written by people who had to make it work across thousands of resource types.

**Size:** 1 session.

## Exercise

**Drill 3.3 — Semantics that infrastructure respects**

```
drills/03-semantics/
├── api/
│   ├── correct.py        # properly semantic API
│   ├── incorrect.py      # same functionality, wrong semantics
│   └── domain.py         # shared logic
├── consequences/
│   ├── crawler.py        # crawl both APIs, see what breaks
│   ├── cache_test.sh     # put a CDN-like cache in front of both
│   ├── retry_test.py     # mesh-style retry against both
│   └── FINDINGS.md
├── conditional/
│   ├── etags.py          # If-None-Match and If-Match
│   ├── lost_update.py    # demonstrate the race, then prevent it
│   └── FINDINGS.md
├── errors/
│   ├── problem_details.py
│   ├── error_catalogue.md
│   └── tenant_leak.py    # 403 vs 404 in multi-tenant
├── redirects/
│   └── post_redirect.py  # 302 vs 307 with a POST body
└── README.md
```

**Part 1 — Two APIs, same features.** Build the same small document API twice. `correct.py` uses proper methods, status codes and headers. `incorrect.py` uses POST for everything and returns 200 with `{"ok": false}`.

**Part 2 — Let infrastructure punish you.**

- **Crawler:** write a crawler that follows every link with GET. Point it at both. `incorrect.py` should lose data
- **Cache:** put nginx with `proxy_cache` in front of both. Measure cache hit rate. `incorrect.py` should be uncacheable
- **Retry:** write a client that retries idempotent methods on connection failure, like a mesh. Inject failures with toxiproxy. Count duplicate side effects in each
- **Monitoring:** compute the error rate from access logs for both during an injected outage. `incorrect.py` should report 100% success while failing

The `FINDINGS.md` table — four infrastructure behaviours × two APIs — **is the entire argument for HTTP semantics, demonstrated rather than asserted.**

**Part 3 — Conditional requests.** Implement ETags on your documents.

- `If-None-Match` returning 304. Measure the bandwidth saved over 1000 polls
- `If-Match` on PUT returning 412

Then demonstrate the lost update: two clients read the same document, both write, the second overwrites the first silently. Then add `If-Match` and show the second getting 412 and being forced to re-read.

**This is the drill that makes optimistic concurrency real.** It is also directly reusable in Conduit phase 3.

**Part 4 — Error catalogue.** Design a Problem Details error catalogue for your API: at least eight error types with stable `type` URIs, appropriate status codes, and extension fields.

Then write a client that branches on `type` rather than parsing message strings. Change a message string and confirm the client still works.

**Part 5 — The tenant leak.** Two organisations, one document each. Implement authorization returning 403 for cross-tenant access. Write a script that enumerates document IDs and identifies which exist — using only the difference between 403 and 404.

Then switch to returning 404 and show the enumeration failing.

**Part 6 — The redirect trap.** An endpoint that redirects a POST with 302, and another with 307. Send a POST with a body through both using `curl -L`, `httpx(follow_redirects=True)` and a browser.

Record what each client does with the method and the body. **The results differ between clients**, which is exactly why this is a trap.

**Done when:**
- The four-behaviour × two-API table is complete with real observations
- Your crawler deleted data from `incorrect.py`
- You demonstrated a lost update and then prevented it with `If-Match`
- Your error catalogue has eight types and a client that branches on `type`
- The enumeration attack works with 403 and fails with 404
- The redirect table shows at least two clients behaving differently
