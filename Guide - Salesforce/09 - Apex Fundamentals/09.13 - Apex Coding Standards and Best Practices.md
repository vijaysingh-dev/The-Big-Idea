# Apex Coding Standards and Best Practices

## What a senior reviewer looks for

Not style. The things that cause production incidents, roughly in the order they are checked.

## The blocking issues

**SOQL or DML inside a loop.** The first thing anyone looks for, and an automatic rejection.

```java
for (Warranty_Claim__c claim : claims) {
    Asset asset = [SELECT Id FROM Asset WHERE Id = :claim.Asset__c];  // reject
}
```

**Methods taking a single record.** A signature of `process(Warranty_Claim__c claim)` invites a loop at the call site.

```java
public void process(Set<Id> claimIds) { }        // correct
public void process(List<Warranty_Claim__c> claims) { }  // correct
public void process(Warranty_Claim__c claim) { }         // only as a delegating convenience
```

**Missing sharing keyword.** A class with none runs without sharing when entered directly. Every class declares one.

**No security enforcement on reachable code.** `@AuraEnabled`, `@RestResource`, and `@InvocableMethod` are public endpoints. `WITH USER_MODE` on queries and `as user` on DML, or an explicit justification.

**Hardcoded IDs.** Record types, queues, profiles, users. Different in every org.

```java
if (opp.RecordTypeId == '0125g000000XyZaAAK') { }   // reject

Id enterpriseRt = Schema.SObjectType.Opportunity
    .getRecordTypeInfosByDeveloperName().get('Enterprise_Sale').getRecordTypeId();
```

**Swallowed exceptions.** An empty catch block is never acceptable.

**No null guards on relationship traversal.** Use `?.`.

**Describe calls in loops.** Particularly `getGlobalDescribe()`.

**Nested loops over record collections.** Build a map.

## Structure

The layering this course uses throughout, covered fully in section 18:

```
Trigger                → routes only, no logic
  TriggerHandler       → dispatches by event, no logic
    Service            → business logic, takes collections, no Trigger context
      Selector         → queries
      Domain           → per-object behaviour
```

The rule that makes it work: **a service never reads `Trigger.new`.** It takes a `List<SObject>` and a `Map<Id, SObject>` as parameters. That single constraint makes the service callable from a flow, a batch job, a REST endpoint, and a test with arbitrary data.

```java
// Trigger
trigger WarrantyClaimTrigger on Warranty_Claim__c (before insert, before update, after update) {
    WarrantyClaimTriggerHandler.run();
}

// Handler: reads Trigger context, passes plain collections onward
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (Trigger.isBefore && Trigger.isInsert) {
            ClaimService.applyDefaults(Trigger.new);
        }
        if (Trigger.isAfter && Trigger.isUpdate) {
            ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
        }
    }
}

// Service: no Trigger reference anywhere
public with sharing class ClaimService {

    public static void handleStatusChanges(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) { }
}
```

## Naming

```
WarrantyClaimService          business logic
WarrantyClaimSelector         queries
WarrantyClaimTriggerHandler   trigger dispatch
WarrantyClaimController       Lightning controller
ClaimApprovalQueueable        async job
ClaimSyncBatch                batch job
WarrantyClaimServiceTest      tests
ClaimValidationException      custom exception
```

Class names are globally unique in the org — there is no package system — so the role suffix matters more here than in most languages.

Methods: verbs. `approveClaims`, `loadOpenByAsset`, `calculateCoverage`. Not `doStuff`, not `handler2`.

Booleans: `isApproved`, `hasCoverage`, `canApprove`. The prefix makes the type obvious at the call site.

Constants: `UPPER_SNAKE_CASE`.

## Comments

The convention this course follows, and a reasonable default: **comment where the intent is not obvious from the code, and nowhere else.**

```java
// Good: explains a non-obvious decision
// FOR UPDATE serializes access so two transactions cannot read the same counter value
Claim_Counter__c counter = [SELECT Id, Next_Value__c FROM Claim_Counter__c
                            WHERE Prefix__c = :prefix LIMIT 1 FOR UPDATE];

// Good: explains why, not what
// resetting first means assets whose last claim was closed go to zero rather than keeping a stale count
for (Asset a : assets.values()) {
    a.Open_Claim_Count__c = 0;
}

// Bad: restates the code
// loop through the claims
for (Warranty_Claim__c claim : claims) {

// Bad: instructional narration
// Step 3: now we update the records
update claims;
```

A comment explaining *why* survives refactoring. A comment explaining *what* becomes wrong the moment the code changes and is worse than nothing, because someone will believe it.

## Method size

No hard rule, and a useful signal: **a method that needs section comments should be several methods.**

```java
// Signals a method doing too much
public void processClaims(List<Warranty_Claim__c> claims) {
    // validate
    ...
    // enrich from asset
    ...
    // apply approval rules
    ...
    // notify
    ...
}
```

Each section becomes a named private method, and the public method reads as a summary of what happens.

## Guard clauses

Early returns beat nested conditionals.

```java
// Nested
public void approve(List<Warranty_Claim__c> claims) {
    if (claims != null) {
        if (!claims.isEmpty()) {
            if (hasPermission()) {
                // the real work, three levels deep
            }
        }
    }
}

// Guarded
public void approve(List<Warranty_Claim__c> claims) {
    if (claims == null || claims.isEmpty()) {
        return;
    }
    if (!hasPermission()) {
        throw new SecurityException('Not authorized to approve claims.');
    }
    // the real work, at one level
}
```

## DML discipline

**Guard against empty lists.** DML on an empty list counts as a DML statement.

```java
if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

**Use partial success for bulk operations**, so one bad record does not abort the batch.

```java
Database.update(claims, false);
```

**Collect and perform one DML per operation type**, never per record.

## Testing expectations

Covered fully in section 19; what a reviewer checks:

**A bulk test with at least 200 records.** A test with one record proves nothing about bulk safety.

**Real assertions.** A test with no `Assert` is coverage theatre.

**Negative cases.** The validation that should fail, the permission that should be denied.

**`System.runAs()`** for anything permission-dependent. Tests run as an administrator by default, who bypasses sharing and field-level security entirely.

**No `SeeAllData=true`** except where genuinely unavoidable. It makes tests dependent on org data and therefore unreliable.

## Static analysis

**PMD with the Apex ruleset** catches most of the blocking issues mechanically:

```bash
pmd check -d force-app -R rulesets/apex/quickstart.xml -f text
```

It flags SOQL in loops, missing sharing declarations, empty catch blocks, hardcoded IDs, unused variables, and excessive complexity.

Running it in the pipeline means review time goes to design rather than to mechanical issues. See [[21.9 - Static Analysis, PMD and Code Review]].

**Salesforce Code Analyzer** wraps PMD, ESLint, and a graph engine that traces data flow for security issues — it catches an injection path across several method calls, which PMD alone does not.

## Coverage as a floor

75% org-wide coverage is a **deployment gate**, not a quality measure. Code can be 100% covered and completely untested if the tests contain no assertions.

The honest framing: coverage tells you what was executed, not what was verified. A codebase at 78% with meaningful assertions is in better shape than one at 95% with none. See [[19.10 - Code Coverage, Quality and CI Gates]].

## A review checklist

```
Bulk safety
  [ ] No SOQL or DML in loops
  [ ] Methods take collections
  [ ] Tested with 200+ records

Security
  [ ] Sharing keyword declared
  [ ] WITH USER_MODE / as user on reachable code
  [ ] stripInaccessible on sObjects from the client
  [ ] Bind variables in dynamic SOQL, allowlist for field names

Correctness
  [ ] Null guards on relationship traversal
  [ ] Null guards on arithmetic
  [ ] No hardcoded IDs
  [ ] Empty-list guards before DML
  [ ] oldMap comparison where change detection matters

Structure
  [ ] Trigger routes only
  [ ] Service does not reference Trigger context
  [ ] Method does one thing
  [ ] Named by role

Errors
  [ ] Nothing swallowed
  [ ] Stack trace logged
  [ ] addError on the field, message written for the user

Tests
  [ ] Real assertions
  [ ] Bulk case
  [ ] Negative case
  [ ] runAs for permission-dependent behaviour
  [ ] No SeeAllData
```

## Section 09 in one paragraph

Apex is Java-shaped with the database in the language and a hard limit budget shared with everything else in the transaction. The constraints that shape real code are: collections everywhere, because every entry point can hand you 200 records; queries are scarce, so collect and query once rather than querying per record; statics live for one transaction, which makes them right for recursion guards and describe caching and wrong for behaviour flags; limit exceptions cannot be caught, so you design not to approach limits rather than recovering from them; and nothing enforces security by default, so `USER_MODE`, sharing keywords, and `stripInaccessible` are the developer's responsibility. Everything else — interfaces as test seams, wrapper classes for JSON, describe caching, guard clauses — follows from making code that respects those constraints readable by the next person.
