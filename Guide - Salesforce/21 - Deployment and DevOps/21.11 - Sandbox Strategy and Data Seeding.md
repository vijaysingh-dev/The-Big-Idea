# Sandbox Strategy and Data Seeding

## The four types

```
                Metadata   Data              Refresh    Storage
Developer       yes        none              1 day      200 MB
Developer Pro   yes        none              1 day      1 GB
Partial Copy    yes        sampled           5 days     5 GB
Full            yes        complete copy     29 days    production-sized
```

**Developer and Developer Pro carry no data**, only metadata. Everything must be seeded.

**Partial Copy** takes a sample defined by a template — a percentage of records per object, up to 10,000 per object.

**Full** copies everything, including field history if selected, and is the only environment representing production reality.

**The refresh interval is the constraint that shapes the strategy.** A Full sandbox refreshed once a month is stale for most of that month.

## What each is for

**Developer / Developer Pro** — feature development, when a scratch org will not do because the repository is incomplete or a managed package makes creation slow.

**Partial Copy** — integration testing and training, where representative data matters but volume does not.

**Full** — UAT, performance testing, release rehearsal, and data migration rehearsal. **The only environment where a query plan or a lock contention problem is real.**

A workable chain:

```
Scratch orgs / Developer  →  feature work
Developer Pro (integration) →  merged work, integration testing
Partial Copy (UAT)          →  business testing with representative data
Full (staging)              →  release rehearsal, performance, migration rehearsal
Production
```

**Not every org needs four tiers.** Two — a developer sandbox and a Full — covers a great deal, and adding tiers adds refresh coordination.

## What a refresh destroys

The list that catches teams out.

```
All data in the sandbox
Custom Setting records
Named Credential secrets
Connected app consumer keys
Certificate private keys
Scheduled jobs
Deliverability settings — reset to "System email only"
Email addresses — appended with .invalid
User passwords
Sandbox-specific configuration
```

**Deliverability resets to "System email only"**, which is why tested email does not arrive after a refresh and everyone assumes the code is broken. It is a deliberate safeguard against a sandbox emailing real customers. See [[17.6 - Email Services - Inbound and Outbound]].

**Email addresses get `.invalid` appended**, for the same reason.

## The post-refresh script

Everything a refresh destroys, automated.

```java
// scripts/apex/sandbox-post-refresh.apex

// Custom Settings, which do not survive a refresh
insert new Automation_Settings__c(
    SetupOwnerId = UserInfo.getOrganizationId(),
    Disable_All_Automation__c = false
);

insert new Integration_Settings__c(
    SetupOwnerId = UserInfo.getOrganizationId(),
    ERP_Environment__c = 'Sandbox'
);

// scheduled jobs, which are not copied
System.schedule('Claim Reconciliation Daily', '0 0 2 * * ?', new ClaimReconciliationBatch());
System.schedule('Log Purge Weekly', '0 0 3 ? * SUN', new LogPurgeBatch());

// email addresses, so notifications can be tested by the team
List<User> testUsers = [SELECT Id, Email FROM User WHERE IsActive = true AND Email LIKE '%.invalid'];
for (User u : testUsers) {
    u.Email = u.Email.replace('.invalid', '');
}
update testUsers;
```

```bash
sf apex run --file scripts/apex/sandbox-post-refresh.apex --target-org uat
```

**A `SandboxPostCopy` class runs automatically** after a refresh, which is better than remembering to run a script:

```java
global with sharing class SandboxPostRefresh implements SandboxPostCopy {

    global void runApexClass(SandboxContext context) {
        // runs automatically after every refresh of this sandbox
        createCustomSettings();
        scheduleJobs();
        maskSensitiveData();
        deactivateIntegrationUsers();
    }
}
```

Selected when creating or refreshing the sandbox, and it removes the whole class of "we forgot the post-refresh steps" failure.

## Data masking

Personal data in a sandbox is a compliance exposure. A developer sandbox with real customer emails, phone numbers, and addresses is production data with weaker access controls.

**Data Mask** is the Salesforce product, installed as a managed package and configured per sandbox:

```
Anonymization    replace with random values
Pseudonymization replace with realistic fake values, preserving format
Deletion         remove the field's contents entirely
Pattern-based    preserve format while changing content
```

**Pseudonymization is usually right** — a phone number that still looks like a phone number keeps validation and formatting working.

Without Data Mask, a masking script:

```java
public with sharing class DataMaskBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Email, Phone, MailingStreet FROM Contact
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Contact> scope) {
        for (Contact contact : scope) {
            // deterministic from the Id, so the same record masks the same way each run
            contact.Email = 'masked.' + contact.Id + '@example.invalid';
            contact.Phone = '+91 90000 ' + String.valueOf(contact.Id).right(5);
            contact.MailingStreet = 'Masked Address';
        }
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Run it from `SandboxPostCopy`**, so masking happens before anyone can access the data — not as a step someone remembers.

**Also deactivate integration users** in the post-copy, or a refreshed sandbox starts calling the production ERP with test data. That is a real incident and it happens.

## Seeding a sandbox with no data

**`data import tree`** for reference and small related sets:

```bash
sf data export tree \
  --query "SELECT Id, Name, BillingCountry, (SELECT Id, Name, SerialNumber FROM Assets) FROM Account LIMIT 20" \
  --prefix seed --output-dir data --target-org production

sf data import tree --plan data/seed-Account-plan.json --target-org dev-sandbox
```

**200 records per file**, with relationships resolved at import. Right for reference data, wrong for volume.

**Anonymous Apex** for anything needing logic or volume:

```java
List<Account> accounts = new List<Account>();
for (Integer i = 0; i < 50; i++) {
    accounts.add(new Account(Name = 'Northwind Customer ' + i, BillingCountry = 'India'));
}
insert accounts;

List<Asset> assets = new List<Asset>();
for (Account account : accounts) {
    for (Integer i = 0; i < 10; i++) {
        assets.add(new Asset(
            AccountId = account.Id, Name = 'Press P400',
            SerialNumber = 'SN-' + account.Id + '-' + i, Status = 'Installed'
        ));
    }
}
insert assets;
```

**Generating volume in code beats maintaining a large data file**, and it is the only practical way to create the 200-records-across-50-parents distribution that bulk testing needs. See [[19.7 - Testing Triggers and Bulk Behaviour]].

**SFDMU** for complex hierarchical migration:

```bash
sf plugins install sfdmu
sf sfdmu run --sourceusername production --targetusername uat --path data/
```

```json
{
  "objects": [
    {
      "query": "SELECT Id, Name, BillingCountry FROM Account WHERE Industry = 'Manufacturing' LIMIT 100",
      "operation": "Upsert",
      "externalId": "ERP_Account_Id__c"
    },
    {
      "query": "SELECT Id, Name, SerialNumber, AccountId FROM Asset",
      "operation": "Upsert",
      "externalId": "ERP_Asset_Id__c"
    }
  ]
}
```

**SFDMU resolves relationships by external ID across objects**, which `import tree` cannot do at scale. It is the right tool for moving a coherent slice of production data into a sandbox. See [[10.3 - Upsert, Merge and External IDs]].

## Partial Copy templates

```
Setup → Sandboxes → Sandbox Templates → New

Objects:  Account, Contact, Asset, Warranty_Claim__c, Service_Contract__c
Records:  up to 10,000 per object
```

**A template selects objects, not filters.** You cannot say "accounts in India" — you get a sample.

**Related records may not come with their parents**, which produces orphans. A claim whose asset was not sampled has a broken lookup.

That inconsistency is the main weakness of Partial Copy, and it means the post-refresh script frequently has to clean up or supplement.

## Refresh coordination

The operational reality in a multi-sandbox org.

**A refresh takes hours to days.** A Full sandbox for a large org can take a day or more, during which it is unavailable.

**Refreshing loses in-flight work.** Anything in that sandbox not committed to Git is gone.

**Refresh intervals differ** — 1 day for Developer, 5 for Partial, 29 for Full — which means they cannot all be refreshed together.

**A workable cadence:**

```
Developer sandboxes    on demand, whenever a developer needs a clean start
Integration            monthly, or after a production release
UAT (Partial)          before each UAT cycle
Full (staging)         monthly, and before a major release
```

**Refresh Full before a release rehearsal**, so the rehearsal happens against current data.

**Announce refreshes.** Someone always has uncommitted work.

## The staleness problem

A Full sandbox refreshed on the 1st is a month out of date by the 29th.

**What that breaks:**

**Performance testing** against data volumes that have grown.

**Migration rehearsal** against a data shape that has changed.

**UAT** where the business tests against records that no longer reflect reality.

**Mitigations:**

**Refresh immediately before the activity that needs current data**, rather than on a fixed schedule.

**Top up with SFDMU** for specific objects between refreshes.

**Accept it for most purposes.** A month-old sandbox is fine for functional testing and wrong for performance work.

## Licences and storage

**Sandbox allocations are by edition:**

```
Enterprise      25 Developer, 25 Developer Pro, 1 Partial, 1 Full (typical)
Unlimited       significantly more
```

Additional sandboxes are purchasable, and Full sandboxes are expensive.

**Storage caps matter.** A Developer sandbox at 200 MB fills quickly with generated test data, and hitting the cap produces `STORAGE_LIMIT_EXCEEDED` on operations that worked yesterday.

**User licences in a sandbox** mirror production, so a sandbox has the same licence counts — which is occasionally the constraint when a team needs many test users.

## Sandbox versus scratch org

The division most teams settle on:

| Need | Environment |
| --- | --- |
| Feature development | Scratch org |
| Development needing production metadata not in Git | Developer sandbox |
| Integration testing | Developer Pro or Partial |
| UAT with business users | Partial or Full |
| Performance testing | **Full only** |
| Data migration rehearsal | **Full only** |
| Release rehearsal | **Full only** |
| CI validation | Scratch org |

**Full sandboxes are the only environment where volume-dependent problems are real.** Query selectivity, lock contention, skew, and batch job duration all need production-scale data. See [[16.9 - Skinny Tables and Custom Indexes]] and [[10.9 - Data Skew]].

**Scratch orgs keep the repository honest**, because an incomplete repository produces a broken org. Sandboxes hide that, since they inherit whatever production has.

Running both is not redundancy — each catches what the other cannot.

## A post-refresh checklist

```
[ ] SandboxPostCopy ran, or the script was run manually
[ ] Custom Setting records created
[ ] Named Credential secrets populated
[ ] Connected app keys updated in dependent systems
[ ] Certificates uploaded
[ ] Deliverability set appropriately
[ ] Email addresses corrected for the team
[ ] Integration users deactivated or repointed to test endpoints
[ ] Personal data masked
[ ] Scheduled jobs rescheduled
[ ] Test data seeded
[ ] Permission sets assigned to test users
[ ] Smoke test passed
```

**The integration user line is the one that causes incidents.** A refreshed sandbox whose integration user still points at production endpoints will start writing test data into the live ERP.

## Section 21 in one paragraph

Salesforce deployment is a merge into a live, editable system rather than a replacement, which explains nearly every practice in this section: components not in a deployment are not removed, so orgs accumulate; administrators change production directly, so repositories drift; and profiles retrieve only the permissions for metadata included alongside them, which is why permission sets belong in source control and profiles frequently do not. The CLI is what everything sits on — JWT for CI authentication, `sfdx-git-delta` to deploy only what changed, and validate-then-quick-deploy to compress a thirty-minute test run into a two-minute release window. There is no rollback, so releases are designed additively and recovered forward, with feature toggles and a tested bypass as the only levers that work in seconds rather than minutes. And scratch orgs and sandboxes are complementary rather than alternatives: the scratch org keeps the repository honest by breaking when it is incomplete, and the Full sandbox is the only place where query selectivity, lock contention, and batch duration are real.
