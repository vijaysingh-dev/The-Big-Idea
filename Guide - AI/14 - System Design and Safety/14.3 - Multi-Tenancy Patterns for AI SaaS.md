# Multi-Tenancy Patterns for AI SaaS

## What It Is

Multi-tenancy is the architecture where a single deployment serves multiple customers (tenants), each with complete data isolation. For AI SaaS specifically, this means every component — vector index, document store, LLM call logs, credentials, rate limits — must be scoped per tenant with zero possibility of cross-tenant data leakage.

This extends [[../11 - Architecture Case Studies/11.4 - Multi-Tenant RAG Platform|11.4 Multi-Tenant RAG Platform]] from case study to implementation depth.

---

## Why It Matters

- Every AI SaaS company in your target list (Haptik, Yellow.ai, Leena, DevRev, Nanonets) serves enterprise tenants with strict data isolation requirements
- A cross-tenant data leak is an existential event — not a bug, a company-ending incident
- LLM-specific multi-tenancy adds dimensions traditional SaaS doesn't have: per-tenant embedding models, per-tenant prompts, per-tenant rate limits against provider APIs, and per-tenant evaluation datasets
- SOC 2 Type II (required by most enterprise customers) has specific requirements for tenant isolation that auditors check at the code level

---

## Isolation Models

Three models exist on a spectrum:

```
Silo                    Bridge                  Pool
────────────────────────────────────────────────────────
One deployment          Shared infra,           All tenants share
per tenant              separate data           everything
                        
Strongest isolation     Middle ground           Weakest isolation
Most expensive          Most common             Cheapest
Best compliance         Good enough for most    Compliance risk
```

Most AI SaaS uses the **Bridge** model: shared compute and application tier, but strictly isolated data stores.

## Tenant Identity and Scoping

Every request must carry tenant context from authentication through to the database layer.

### JWT-Based Tenant Context

```python
import jwt
from fastapi import HTTPException, Depends
from fastapi.security import HTTPBearer

security = HTTPBearer()

def get_tenant_context(token: str = Depends(security)) -> dict:
    try:
        payload = jwt.decode(token.credentials, JWT_SECRET, algorithms=["HS256"])
        tenant_id = payload.get("tenant_id")
        user_id = payload.get("user_id")
        if not tenant_id:
            raise HTTPException(403, "No tenant_id in token")
        return {"tenant_id": tenant_id, "user_id": user_id}
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "Token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(401, "Invalid token")

# Inject into every route
@app.post("/chat")
async def chat(body: ChatRequest, ctx: dict = Depends(get_tenant_context)):
    return await rag_pipeline(
        question=body.question,
        tenant_id=ctx["tenant_id"],
        user_id=ctx["user_id"],
    )
```

### Propagating Tenant Context Through Layers

The anti-pattern: passing tenant_id as a parameter through 10 function calls. The pattern: use a context variable that propagates automatically.

```python
from contextvars import ContextVar

# Per-request context — safe in async code
_tenant_ctx: ContextVar[str] = ContextVar("tenant_id")
_user_ctx: ContextVar[str] = ContextVar("user_id")

def set_tenant_context(tenant_id: str, user_id: str):
    _tenant_ctx.set(tenant_id)
    _user_ctx.set(user_id)

def get_tenant_id() -> str:
    tenant_id = _tenant_ctx.get(None)
    if tenant_id is None:
        raise RuntimeError("No tenant context set — all DB/vector operations require tenant scope")
    return tenant_id

# Middleware sets context for every request
@app.middleware("http")
async def tenant_context_middleware(request: Request, call_next):
    token = request.headers.get("Authorization", "").replace("Bearer ", "")
    if token:
        payload = decode_jwt(token)
        set_tenant_context(payload["tenant_id"], payload["user_id"])
    return await call_next(request)

# Deep in the call stack, no parameter passing needed
def search_documents(query: str):
    tenant_id = get_tenant_id()  # automatically available
    return vector_store.search(query, collection=f"tenant_{tenant_id}")
```

## Vector Store Isolation

### Strategy: Collection-per-Tenant

Each tenant gets an isolated Qdrant collection or Vespa namespace:

```python
class TenantVectorStore:
    def __init__(self, qdrant_client):
        self.client = qdrant_client

    def collection_name(self, tenant_id: str) -> str:
        # Sanitize tenant_id to be safe as a collection name
        safe_id = tenant_id.replace("-", "_").lower()
        return f"t_{safe_id}"

    def provision_tenant(self, tenant_id: str, embedding_dim: int = 1536):
        name = self.collection_name(tenant_id)
        if not self.client.collection_exists(name):
            self.client.create_collection(
                collection_name=name,
                vectors_config=VectorParams(size=embedding_dim, distance=Distance.COSINE),
            )
            # Create indexes for tenant's commonly filtered fields
            self.client.create_payload_index(name, "document_id", PayloadSchemaType.KEYWORD)
            self.client.create_payload_index(name, "user_group", PayloadSchemaType.KEYWORD)
            self.client.create_payload_index(name, "source_type", PayloadSchemaType.KEYWORD)

    def search(self, tenant_id: str, query_vec: list[float],
               user_groups: list[str], top_k: int = 10):
        # The collection name IS the tenant boundary — no filter needed
        return self.client.search(
            collection_name=self.collection_name(tenant_id),
            query_vector=query_vec,
            query_filter=Filter(
                should=[
                    FieldCondition(key="user_group", match=MatchAny(any=user_groups)),
                    FieldCondition(key="public", match=MatchValue(value=True)),
                ]
            ),
            limit=top_k,
        )

    def deprovision_tenant(self, tenant_id: str):
        """Hard delete — all data gone. No recovery."""
        self.client.delete_collection(self.collection_name(tenant_id))
```

### Why Not a Single Collection with Tenant Filter?

```python
# RISKY PATTERN — single collection with filter
results = client.search(
    collection_name="all_documents",
    query_filter=Filter(must=[
        FieldCondition(key="tenant_id", match=MatchValue(value=tenant_id))
    ]),
)
# Risk: if the filter is forgotten somewhere in the codebase,
#       any tenant can see all tenants' data.
# Risk: an auth bypass bug → catastrophic cross-tenant exposure.
# One collection per tenant: the collection name is the boundary.
#   There is NO code path that can accidentally cross it.
```

Collection-per-tenant provides **architectural isolation** — the boundary is enforced by the infrastructure, not by application logic that can have bugs.

## Relational Database Isolation

### Row-Level Security (PostgreSQL)

```sql
-- Enable RLS on all tenant-scoped tables
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE connectors ENABLE ROW LEVEL SECURITY;

-- Policy: only see rows belonging to current tenant
CREATE POLICY tenant_isolation ON documents
    FOR ALL
    USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- Application sets context before every query
CREATE OR REPLACE FUNCTION set_tenant(tid uuid) RETURNS void AS $$
BEGIN
    PERFORM set_config('app.tenant_id', tid::text, true);
END;
$$ LANGUAGE plpgsql;
```

```python
# asyncpg connection with RLS
async def get_db_connection(tenant_id: str):
    conn = await asyncpg.connect(DATABASE_URL)
    await conn.execute(f"SELECT set_tenant('{tenant_id}'::uuid)")
    return conn

# All queries on this connection are automatically scoped
async def get_documents(tenant_id: str):
    async with get_db_connection(tenant_id) as conn:
        return await conn.fetch("SELECT * FROM documents")
        # RLS automatically adds: AND tenant_id = current_tenant_id
```

**Defense in depth**: Even if application code forgets to filter by tenant_id, RLS at the database layer prevents cross-tenant access.

## Credential Management

### Per-Tenant Encrypted Credentials

```python
import boto3, json
from cryptography.fernet import Fernet

# Option A: AWS KMS (recommended for production)
kms_client = boto3.client("kms", region_name="us-east-1")

def store_connector_credentials(tenant_id: str, connector: str, credentials: dict):
    # Encrypt with tenant-specific KMS key
    key_id = f"alias/tenant-{tenant_id}"
    encrypted = kms_client.encrypt(
        KeyId=key_id,
        Plaintext=json.dumps(credentials).encode(),
    )["CiphertextBlob"]

    db.execute(
        "INSERT INTO connector_credentials (tenant_id, connector, encrypted_creds) "
        "VALUES ($1, $2, $3) ON CONFLICT (tenant_id, connector) DO UPDATE "
        "SET encrypted_creds = $3, updated_at = NOW()",
        tenant_id, connector, encrypted,
    )

def get_connector_credentials(tenant_id: str, connector: str) -> dict:
    row = db.fetchone(
        "SELECT encrypted_creds FROM connector_credentials "
        "WHERE tenant_id = $1 AND connector = $2",
        tenant_id, connector,
    )
    if not row:
        raise CredentialNotFoundError(f"No {connector} credentials for tenant {tenant_id}")

    decrypted = kms_client.decrypt(
        CiphertextBlob=row["encrypted_creds"],
        KeyId=f"alias/tenant-{tenant_id}",
    )["Plaintext"]

    return json.loads(decrypted)

# Rotate KMS key per tenant during offboarding
def offboard_tenant_credentials(tenant_id: str):
    kms_client.schedule_key_deletion(
        KeyId=f"alias/tenant-{tenant_id}",
        PendingWindowInDays=7  # 7-day recovery window
    )
    # After key deletion, stored encrypted credentials are permanently unreadable
```

## Per-Tenant Rate Limiting

Prevent one tenant from exhausting shared LLM API quotas:

```python
import redis.asyncio as redis

class TenantRateLimiter:
    def __init__(self, redis_client):
        self.redis = redis_client

    async def check_and_consume(self, tenant_id: str, tokens: int) -> bool:
        """Sliding window rate limit on LLM tokens per tenant."""
        plan = await get_tenant_plan(tenant_id)
        limits = PLAN_LIMITS[plan]

        pipe = self.redis.pipeline()
        now = time.time()
        window_key = f"ratelimit:{tenant_id}:tokens:1h"

        # Sliding window: remove entries older than 1 hour
        pipe.zremrangebyscore(window_key, 0, now - 3600)
        # Add current usage
        pipe.zadd(window_key, {f"{now}:{tokens}": now})
        # Count total tokens in window
        pipe.zrange(window_key, 0, -1, withscores=False)
        pipe.expire(window_key, 3600)

        results = await pipe.execute()
        token_entries = results[2]
        total_tokens = sum(int(e.split(":")[1]) for e in token_entries)

        if total_tokens > limits["tokens_per_hour"]:
            raise RateLimitError(
                f"Tenant {tenant_id} exceeded {limits['tokens_per_hour']:,} tokens/hour"
            )
        return True

PLAN_LIMITS = {
    "free":       {"tokens_per_hour": 10_000,   "queries_per_day": 100},
    "starter":    {"tokens_per_hour": 100_000,  "queries_per_day": 1_000},
    "pro":        {"tokens_per_hour": 1_000_000,"queries_per_day": 10_000},
    "enterprise": {"tokens_per_hour": 10_000_000,"queries_per_day": 100_000},
}
```

## Per-Tenant Configuration

Different tenants need different behavior: custom prompts, different embedding models, different LLM configurations:

```python
from dataclasses import dataclass
from typing import Optional
import json

@dataclass
class TenantConfig:
    tenant_id: str
    # LLM configuration
    llm_provider: str = "openai"           # "openai" | "anthropic" | "azure"
    llm_model: str = "gpt-4o"
    llm_temperature: float = 0.1
    max_output_tokens: int = 1024
    # Embedding configuration
    embedding_model: str = "text-embedding-3-small"
    embedding_dim: int = 1536
    # RAG configuration
    retrieval_top_k: int = 10
    reranker_enabled: bool = True
    # Prompts
    system_prompt_override: Optional[str] = None
    # Feature flags
    streaming_enabled: bool = True
    citations_enabled: bool = True

async def get_tenant_config(tenant_id: str) -> TenantConfig:
    """Load from DB with caching."""
    cache_key = f"tenant_config:{tenant_id}"
    cached = await redis.get(cache_key)
    if cached:
        return TenantConfig(**json.loads(cached))

    row = await db.fetchone(
        "SELECT config FROM tenants WHERE id = $1", tenant_id
    )
    config = TenantConfig(tenant_id=tenant_id, **json.loads(row["config"]))
    await redis.setex(cache_key, 300, json.dumps(config.__dict__))
    return config
```

## Tenant Provisioning and Offboarding

### Provisioning

```python
async def provision_tenant(signup: TenantSignup) -> Tenant:
    tenant_id = str(uuid4())

    async with db.transaction():
        # 1. Create tenant record
        await db.execute(
            "INSERT INTO tenants (id, name, plan, status) VALUES ($1, $2, $3, 'provisioning')",
            tenant_id, signup.company_name, signup.plan,
        )
        # 2. Create admin user
        await create_user(tenant_id, signup.admin_email, role="admin")

    # 3. Provision isolated data stores (outside transaction — these are idempotent)
    await vector_store.provision_tenant(tenant_id)
    await create_kms_key(f"alias/tenant-{tenant_id}")

    # 4. Mark active
    await db.execute("UPDATE tenants SET status = 'active' WHERE id = $1", tenant_id)

    # 5. Send welcome email asynchronously
    await welcome_email.delay(tenant_id, signup.admin_email)

    return Tenant(id=tenant_id, status="active")
```

### Offboarding (GDPR-compliant hard delete)

```python
async def offboard_tenant(tenant_id: str, requested_by: str):
    """Permanently delete all tenant data. Irreversible."""

    # Log intent before deletion (audit trail survives the deletion)
    await audit_log.record("tenant_offboard_initiated",
                           tenant_id=tenant_id, requested_by=requested_by)

    # 1. Deactivate tenant (stop all new requests)
    await db.execute("UPDATE tenants SET status = 'offboarding' WHERE id = $1", tenant_id)

    # 2. Delete vector data (immediate)
    await vector_store.deprovision_tenant(tenant_id)

    # 3. Delete relational data (cascade)
    await db.execute("DELETE FROM tenants WHERE id = $1", tenant_id)
    # Cascades to: documents, conversations, connectors, users, usage_events

    # 4. Schedule KMS key deletion (7-day grace period)
    await schedule_kms_key_deletion(f"alias/tenant-{tenant_id}", days=7)

    # 5. Delete object storage
    await s3.delete_prefix(f"tenants/{tenant_id}/")

    # 6. Final audit record (written to separate, non-tenant-scoped audit log)
    await audit_log.record("tenant_offboard_completed",
                           tenant_id=tenant_id, timestamp=now())
```

Track LLM costs per tenant for billing and chargeback:

async def track_llm_usage(tenant_id: str, user_id: str, usage: dict):
    cost = calculate_cost(usage["model"], usage["input_tokens"], usage["output_tokens"])

    # Write to time-series store for billing aggregation
    await db.execute(
        "INSERT INTO usage_events (tenant_id, user_id, model, input_tokens, "
        "output_tokens, cost_usd, ts) VALUES ($1,$2,$3,$4,$5,$6,NOW())",
        tenant_id, user_id, usage["model"],
        usage["input_tokens"], usage["output_tokens"], cost,
    )

    # Update real-time counter for rate limiting
    await redis.incrbyfloat(f"usage:{tenant_id}:cost:month:{current_month()}", cost)

    # Alert if approaching plan limit
    monthly_cost = float(await redis.get(f"usage:{tenant_id}:cost:month:{current_month()}") or 0)
    limit = (await get_tenant_plan(tenant_id))["monthly_cost_limit_usd"]
    if monthly_cost > limit * 0.8:
        await notify_tenant_approaching_limit(tenant_id, monthly_cost, limit)

## Revision Anchors

- **Isolation model**: Silo (own deployment) > Bridge (shared compute, isolated data) > Pool (fully shared). Most AI SaaS uses Bridge.
- **Collection-per-tenant in vector DBs**: The collection name IS the boundary. Not a filter that can be forgotten — an architectural guarantee.
- **ContextVar for tenant propagation**: Set once in middleware, read anywhere in the call stack. No parameter threading needed.
- **RLS in PostgreSQL**: Database-level enforcement. Even if application code forgets to filter, cross-tenant access is blocked at the query layer.
- **KMS key per tenant**: Encrypts credentials with tenant-specific keys. Offboarding = schedule key deletion → stored credentials permanently unreadable.
- **Per-tenant config**: Different tenants need different models, prompts, RAG parameters. Cache configs in Redis with 5-minute TTL.
- **Offboarding sequence**: Deactivate → delete vector data → cascade delete relational → schedule KMS deletion → delete object storage → audit log.
