# Apex Callouts

## The basic shape

```java
public with sharing class ErpClient {

    public static ClaimResponse submitClaim(Warranty_Claim__c claim) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/v2/claims');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setHeader('Accept', 'application/json');
        req.setBody(JSON.serialize(ClaimPayload.from(claim)));
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() >= 300) {
            throw new IntegrationException(
                'ERP rejected the claim: ' + res.getStatusCode() + ' ' + res.getBody()
            );
        }

        return (ClaimResponse) JSON.deserialize(res.getBody(), ClaimResponse.class);
    }
}
```

Three classes: `HttpRequest`, `HttpResponse`, and `Http` to send.

Always a Named Credential endpoint, never a raw URL. See [[13.13 - Named Credentials and External Credentials]].

## The rules that constrain every callout

**No callout after DML in the same transaction.**

```
You have uncommitted work pending. Please commit or rollback before calling out.
```

The transaction holds open database work from step 7 to step 17 of the order of execution, and an HTTP call during that window would hold it open for the external system's response time. See [[07.13 - Order of Execution]].

This is why outbound integration from a trigger is nearly always a Queueable:

```java
// The service enqueues rather than calling out, because DML has occurred
System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

A callout **before** any DML works fine, which is what makes read-then-write integrations viable synchronously.

**Async contexts need a marker interface.**

```java
public class ErpQueueable implements Queueable, Database.AllowsCallouts { }
public class ErpBatch implements Database.Batchable<SObject>, Database.AllowsCallouts { }
@future(callout=true)
```

Omitting it produces a runtime failure on the first callout, in a job that may only sometimes call out — which is exactly the kind of bug that reaches production.

**Limits:** 100 callouts per transaction, **120 seconds total** across all of them, 6 MB request and 6 MB response (12 MB async), and a default timeout of 10 seconds with a maximum of 120.

The 120-second cumulative budget is the one people forget. Ten callouts at 30 seconds each is 300 seconds and fails partway through, having already done some of the work.

## Timeouts

```java
req.setTimeout(30000);   // milliseconds, max 120000
```

**Set it explicitly.** The 10-second default is often too short for a slow enterprise system and too long for a fast one that has hung.

The tradeoff is direct: a long timeout ties up the transaction and consumes the 120-second budget; a short one produces spurious failures. Setting it to roughly twice the external system's observed 95th percentile is a reasonable starting point.

## Building requests

```java
// Query parameters — always encoded
req.setEndpoint('callout:ERP_System/api/assets?serial='
    + EncodingUtil.urlEncode(serialNumber, 'UTF-8')
    + '&includeHistory=true');

// Headers
req.setHeader('Authorization', 'Bearer ' + token);   // usually unnecessary with a named credential
req.setHeader('X-Correlation-Id', correlationId);
req.setHeader('Idempotency-Key', claim.Id + '-' + claim.LastModifiedDate.getTime());

// Body
req.setBody(JSON.serialize(payload));
req.setBodyAsBlob(fileBlob);
req.setCompressed(true);   // gzip the request
```

`EncodingUtil.urlEncode` on anything user-supplied is not optional. A serial number containing an ampersand silently truncates the query string otherwise.

The `Idempotency-Key` header is the outbound half of the idempotency story — it lets the receiver deduplicate a retried request. See [[13.17 - Error Handling, Retries and Idempotency]].

## Reading responses

```java
HttpResponse res = new Http().send(req);

res.getStatusCode();              // 200
res.getStatus();                  // 'OK'
res.getBody();                    // String
res.getBodyAsBlob();              // Blob, for binary
res.getHeader('Content-Type');
res.getHeaderKeys();
```

For binary responses — a PDF, an image — `getBodyAsBlob()` is what you want, and the 6 MB response ceiling applies.

```java
public with sharing class DocumentFetchService {

    public static Id fetchAndAttach(Id claimId, String documentReference) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/documents/'
            + EncodingUtil.urlEncode(documentReference, 'UTF-8'));
        req.setMethod('GET');
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);
        if (res.getStatusCode() != 200) {
            throw new IntegrationException('Document fetch failed: ' + res.getStatusCode());
        }

        ContentVersion version = new ContentVersion(
            Title = 'ERP Document ' + documentReference,
            PathOnClient = documentReference + '.pdf',
            VersionData = res.getBodyAsBlob(),
            FirstPublishLocationId = claimId
        );
        insert version;
        return version.Id;
    }
}
```

Note the ordering: the callout happens first, then the DML. Reversed, it throws.

## Structuring a client

A single class per external system, with the HTTP details in one place and the business logic elsewhere.

```java
public with sharing class ErpClient {

    private static final String NAMED_CREDENTIAL = 'callout:ERP_System';
    private static final Integer DEFAULT_TIMEOUT = 30000;

    public class Response {
        public Integer statusCode;
        public String body;
        public Boolean isSuccess;
        public String correlationId;
    }

    public static Response get(String path) {
        return send('GET', path, null);
    }

    public static Response post(String path, Object payload) {
        return send('POST', path, JSON.serialize(payload));
    }

    public static Response patch(String path, Object payload) {
        return send('PATCH', path, JSON.serialize(payload));
    }

    private static Response send(String method, String path, String body) {
        String correlationId = String.valueOf(Crypto.getRandomLong());

        HttpRequest req = new HttpRequest();
        req.setEndpoint(NAMED_CREDENTIAL + path);
        req.setMethod(method);
        req.setTimeout(DEFAULT_TIMEOUT);
        req.setHeader('Accept', 'application/json');
        req.setHeader('X-Correlation-Id', correlationId);

        if (body != null) {
            req.setHeader('Content-Type', 'application/json');
            req.setBody(body);
        }

        Long startedAt = System.currentTimeMillis();
        Response result = new Response();
        result.correlationId = correlationId;

        try {
            HttpResponse res = new Http().send(req);
            result.statusCode = res.getStatusCode();
            result.body = res.getBody();
            result.isSuccess = res.getStatusCode() < 300;
        } catch (System.CalloutException e) {
            // a transport failure is different from an application error and is worth
            // distinguishing for retry purposes
            result.statusCode = 0;
            result.body = e.getMessage();
            result.isSuccess = false;
        }

        logCallout(method, path, result, System.currentTimeMillis() - startedAt);
        return result;
    }
}
```

Centralizing this gives you one place to add logging, correlation Ids, timeout policy, and retry — rather than scattering them across every caller.

Distinguishing a `CalloutException` (transport failure, timeout, DNS) from an HTTP error status matters: the first is usually transient, the second frequently is not.

## Logging callouts

An integration with no callout log is undiagnosable. The minimum worth recording:

```java
private static void logCallout(String method, String path, Response result, Long durationMs) {
    Integration_Log__e log = new Integration_Log__e(
        System__c = 'ERP',
        Method__c = method,
        Path__c = path,
        Status_Code__c = result.statusCode,
        Duration_Ms__c = durationMs,
        Correlation_Id__c = result.correlationId,
        Response_Body__c = result.isSuccess ? null : result.body?.left(5000)
    );
    EventBus.publish(log);
}
```

A **platform event** rather than a direct insert, so the log survives a rollback of the surrounding transaction. See [[12.8 - Platform Events]].

Recording the body only on failure keeps volume manageable. Recording duration is what lets you notice an external system degrading before it starts failing.

**Do not log request bodies containing personal or payment data.** A log table full of customer detail is a compliance problem, and it is created by well-intentioned debugging code.

## Certificates and mutual TLS

Where the external system requires a client certificate, generate or upload one in Setup under Certificate and Key Management, and reference it:

```java
req.setClientCertificateName('ERP_Client_Cert');
```

The certificate is then presented during the TLS handshake. Named Credentials can also carry this, which is the better place for it.

Certificates expire, and an expired one stops the integration with no warning. Tracking expiry dates is the same discipline as for JWT signing certificates. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

## Testing

Callouts cannot be made in tests, so every one must be mocked.

```java
@IsTest
public class ErpSuccessMock implements HttpCalloutMock {

    private final Integer statusCode;
    private final String body;

    public ErpSuccessMock(Integer statusCode, String body) {
        this.statusCode = statusCode;
        this.body = body;
    }

    public HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(statusCode);
        res.setHeader('Content-Type', 'application/json');
        res.setBody(body);
        return res;
    }
}
```

```java
@IsTest
static void claimSubmissionStoresConfirmationNumber() {
    Test.setMock(HttpCalloutMock.class,
        new ErpSuccessMock(200, '{"confirmationNumber":"ERP-4471"}'));

    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    System.enqueueJob(new ErpNotificationQueueable(new Set<Id>{ claim.Id }));
    Test.stopTest();

    Warranty_Claim__c refreshed = [
        SELECT ERP_Confirmation__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('ERP-4471', refreshed.ERP_Confirmation__c);
}
```

For several different responses in one test, a multi-mock keyed on the endpoint:

```java
@IsTest
public class MultiEndpointMock implements HttpCalloutMock {

    private final Map<String, HttpResponse> responsesByPath = new Map<String, HttpResponse>();

    public MultiEndpointMock addResponse(String pathFragment, Integer status, String body) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(status);
        res.setBody(body);
        responsesByPath.put(pathFragment, res);
        return this;
    }

    public HttpResponse respond(HttpRequest req) {
        for (String fragment : responsesByPath.keySet()) {
            if (req.getEndpoint().contains(fragment)) {
                return responsesByPath.get(fragment);
            }
        }
        throw new CalloutException('No mock configured for ' + req.getEndpoint());
    }
}
```

Throwing on an unmatched endpoint rather than returning a default is deliberate — a test hitting an unexpected endpoint should fail loudly.

**Test the failure paths**, not just success: a 500, a timeout, a malformed body. Those are the paths that run in production. See [[19.5 - Mocking Callouts]].

## The patterns that recur

**Read then write.** Callout first, DML after. Works synchronously.

**Write then notify.** DML first, so the callout must be async. Queueable or platform event.

**Fetch on demand.** A component calls Apex which calls out. Synchronous, and a Continuation if slow. See [[12.7 - Apex Continuations]].

**Bulk push.** Batch Apex with `Database.AllowsCallouts`, one callout per chunk with the chunk's records batched into the payload.

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    // one callout for the whole chunk, not one per record
    ErpClient.Response response = ErpClient.post('/api/claims/batch',
        ClaimPayload.from(scope));

    if (response.isSuccess) {
        markSynced(scope, response);
    } else {
        markFailed(scope, response);
    }
}
```

One callout per chunk rather than per record is the bulkification rule applied to integration, and it is the difference between a job that completes and one that exhausts the callout budget.

## Practical guidance

**Always use a Named Credential endpoint.**

**Set the timeout explicitly.**

**Encode anything user-supplied** going into a URL.

**Implement `Database.AllowsCallouts`** wherever a job might call out.

**Move callouts async when DML has occurred.**

**Centralize HTTP handling in one client class per system.**

**Log every callout** through a platform event, with a correlation Id and duration, and without sensitive payload data.

**Batch the payload** rather than calling out per record.

**Mock every callout in tests**, including the failure paths.
