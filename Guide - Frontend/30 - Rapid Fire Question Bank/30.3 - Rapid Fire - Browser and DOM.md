# Rapid Fire - Browser and DOM

## The DOM

**Live vs static collections?**
`getElementsByClassName` and `getElementsByTagName` return live `HTMLCollection`s that re-query on every access — iterating while modifying causes infinite loops. `querySelectorAll` returns a static `NodeList`. → [[12.1 - The DOM Tree and Node APIs]]

**`textContent` vs `innerText` vs `innerHTML`?**
`textContent` returns all text including hidden elements, does not parse, and does not trigger layout. `innerText` returns only rendered text and **forces a reflow**. `innerHTML` parses HTML and is the primary XSS vector. → [[12.1 - The DOM Tree and Node APIs]]

**Why is `innerHTML +=` bad?**
It re-parses the entire subtree, destroying event listeners on existing children and resetting form state. Use `insertAdjacentHTML` or `append`. → [[12.2 - DOM Manipulation]]

**Attribute vs property?**
Attributes are strings from markup; properties are live JS state. For `input.value`, the attribute is the *default* and the property is the current value after user input. `href` as an attribute is what you wrote; as a property it is resolved to absolute. → [[12.1 - The DOM Tree and Node APIs]]

**How do you efficiently insert many nodes?**
Build in a `DocumentFragment` and append once, or build in a detached element. Work outside the document causes no layout. → [[12.2 - DOM Manipulation]]

## Events

**Explain bubbling and capturing.**
An event travels down from `window` to the target (capture phase), fires at the target, then travels back up (bubble phase). `addEventListener` defaults to bubble; pass `{ capture: true }` for the descent. → [[12.3 - The Event Model]]

**`target` vs `currentTarget`?**
`target` is the deepest element actually clicked; `currentTarget` is the element the listener is attached to. Delegation relies on the distinction. → [[12.3 - The Event Model]]

**`preventDefault` vs `stopPropagation`?**
`preventDefault` cancels the browser's default action but the event keeps travelling. `stopPropagation` stops travel but the default action still happens. They are independent. → [[12.3 - The Event Model]]

**Which events do not bubble?**
`focus`, `blur`, `mouseenter`, `mouseleave`, `load`, `error`. Use `focusin`/`focusout` and `mouseover`/`mouseout` for delegation. → [[12.3 - The Event Model]]

**What is event delegation and why use it?**
One listener on a common ancestor handling events from any descendant. Fewer listeners, dynamic content works automatically, and cleanup is one removal. Use `e.target.closest(selector)` plus a containment check. → [[12.4 - Event Delegation]]

**Why is `stopPropagation` usually a mistake?**
It silently breaks anything relying on delegation higher up — analytics, outside-click handlers, focus management — and the connection is invisible from either side. → [[12.3 - The Event Model]]

**What does `{ passive: true }` do?**
Promises the handler will not call `preventDefault`, so the browser can scroll without waiting for it. Measurably improves scroll smoothness on touch devices. → [[12.3 - The Event Model]]

**Why does `removeEventListener` sometimes not work?**
It matches by function reference *and* capture flag. An inline arrow creates a new function each time. `{ signal }` from an `AbortController` removes any number of listeners in one call. → [[12.3 - The Event Model]]

**How do React's events differ?**
React attaches one listener per event type at the root container and delegates. Events bubble through the **React tree**, not the DOM tree — so a click inside a portal bubbles to its React parent. `e.stopPropagation()` stops the synthetic event only. → [[12.3 - The Event Model]]

## Observers

**When would you use `IntersectionObserver`?**
Anything visibility-based: infinite scroll sentinels, lazy loading, scroll-triggered animation, impression tracking. It runs off the main thread and needs no layout reads, unlike a scroll handler. `rootMargin` triggers early. → [[12.5 - Custom Events and Observer APIs]]

**`ResizeObserver` vs the `resize` event?**
`ResizeObserver` fires when an *element* changes size for any reason and delivers the measurement without forcing layout. `window.resize` only fires for the viewport. → [[12.5 - Custom Events and Observer APIs]]

**What is a `MutationObserver` for?**
Observing DOM tree changes — enhancing third-party or CMS-injected content, browser extensions. Callbacks are delivered as microtasks. In your own code, react at the source instead. → [[12.5 - Custom Events and Observer APIs]]

## Rendering

**Explain the critical rendering path.**
HTML → DOM, CSS → CSSOM, both → render tree → layout → paint → composite. CSS is render-blocking; a classic `<script>` is parser-blocking. → [[13.1 - The Critical Rendering Path]]

**`async` vs `defer`?**
Both download in parallel with parsing. `async` executes as soon as it arrives, order not guaranteed. `defer` executes after parsing, in document order. Use `defer` for application code, `async` for independent third-party scripts. → [[13.1 - The Critical Rendering Path]]

**What causes reflow and repaint?**
Reflow (layout) comes from geometry changes — width, height, position, font size, adding or removing nodes. Repaint comes from visual changes with no geometry impact — colour, shadow, visibility. Reflow always implies repaint. → [[13.2 - Reflow Repaint and Composite]]

**What is layout thrashing?**
Interleaving layout reads (`offsetHeight`, `getBoundingClientRect`) with writes, forcing a synchronous recalculation each time. Batch all reads, then all writes. → [[13.3 - Layout Thrashing]]

**Which properties animate cheaply?**
`transform` and `opacity` only — they are handled by the compositor, skipping layout and paint entirely. Animating `width`, `top` or `margin` triggers layout every frame. → [[13.2 - Reflow Repaint and Composite]]

**What are the Core Web Vitals?**
LCP (largest element painted, < 2.5s), INP (interaction responsiveness, < 200ms), CLS (layout stability, < 0.1). All measured at the p75 of real user sessions. → [[13.5 - Core Web Vitals]]

**How do you fix CLS?**
Set `width`/`height` or `aspect-ratio` on images and video, reserve space for ads and embeds, avoid inserting content above existing content, and use `font-display: optional` or metric-matched fallbacks. → [[13.5 - Core Web Vitals]]

## Storage

**Cookies vs localStorage vs sessionStorage?**
Cookies: ~4KB, sent with every request, `httpOnly` option makes them unreadable to JS. `localStorage`: ~5MB, persistent, shared across tabs, synchronous, JS-readable. `sessionStorage`: same but per-tab and cleared on close. → [[14.1 - Cookies]], [[14.2 - LocalStorage and SessionStorage]]

**Where should an auth token live?**
An `httpOnly` cookie by default — an XSS can read `localStorage` and exfiltrate a token but cannot read an `httpOnly` cookie. Add `Secure`, `SameSite` and CSRF protection. → [[15.5 - JWT Sessions and Token Storage]]

**When would you use IndexedDB?**
Structured data beyond the `localStorage` quota, binary data, or offline support. It is asynchronous and stores real `Date` and `Blob` objects without serialization. → [[14.3 - IndexedDB]]

**What can a Service Worker do?**
Intercept network requests, so it enables offline support and programmable caching. It is also the layer most capable of permanently breaking a site — always ship a kill switch. → [[14.4 - Cache API and Service Workers]]

## Networking and security

**What is the Same-Origin Policy?**
Scripts can only read responses from the same scheme, host and port. It is what prevents a malicious page reading your bank's responses. → [[15.3 - Same Origin Policy and CORS]]

**What is CORS?**
A mechanism for a server to opt in to cross-origin reads via `Access-Control-Allow-*` headers. Non-simple requests trigger a preflight `OPTIONS`. With `credentials: "include"`, the server must name a specific origin — `*` is rejected. → [[15.3 - Same Origin Policy and CORS]]

**Which HTTP methods are idempotent?**
`GET`, `PUT`, `DELETE`, `HEAD` — repeating them has the same effect as doing them once. `POST` and `PATCH` are not, which is why retrying them needs an idempotency key. → [[15.1 - HTTP Fundamentals]]

**`no-cache` vs `no-store`?**
`no-cache` means store it but revalidate before every use. `no-store` means never write it to disk or memory. Sensitive data needs `no-store`. → [[15.7 - HTTP Caching and CDNs]]

**How does the two-tier caching strategy work?**
Content-hashed assets get `max-age=31536000, immutable`; HTML gets `no-cache`. The filename changes when the content does, so there is no invalidation problem. → [[15.7 - HTTP Caching and CDNs]]

**What is XSS and how do you prevent it?**
Injecting executable script into a page. React escapes interpolated values by default; the risks are `dangerouslySetInnerHTML` (sanitize with DOMPurify) and unvalidated `href` values, since `javascript:` URLs still execute. A Content Security Policy is the defence in depth. → [[15.6 - Frontend Security]]

**What is CSRF and how do you prevent it?**
A third-party site causing an authenticated request using the user's cookies. `SameSite=Lax` blocks most of it; anti-CSRF tokens cover the rest. → [[15.6 - Frontend Security]]

**WebSocket vs SSE vs polling?**
Polling for updates every 10s or more — no infrastructure cost. SSE for server-to-client only — free reconnection and event replay. WebSocket for bidirectional low-latency. → [[15.8 - WebSockets and Server Sent Events]]
