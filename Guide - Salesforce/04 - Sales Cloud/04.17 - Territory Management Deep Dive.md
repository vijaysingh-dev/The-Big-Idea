# Territory Management Deep Dive

## The problem territories solve

A user has exactly one role. Coverage is rarely that simple.

A rep covers manufacturing accounts in western India. A second rep covers all accounts above a revenue threshold nationally. A product specialist covers every account that owns a particular machine line. One account may fall into all three, and all three people need access and credit.

No single hierarchy expresses overlapping, multi-dimensional coverage. That is what **Enterprise Territory Management** is for.

## The model

**Territory Model.** A complete territory structure, versioned. An org can hold several models but only one is active. This is the feature that makes annual realignment survivable — build next year's structure, test it, activate it when ready.

**Territory Type.** A classification such as Geographic, Named Account, Product Specialist. Organizational rather than functional.

**Territory.** A node in a hierarchy, with assigned users and assigned accounts.

**Territory Hierarchy.** Parent and child territories, separate from the role hierarchy.

**Assignment Rules.** Criteria that place accounts into territories automatically, evaluated on account create and update.

**UserTerritory2Association.** Users assigned to territories, with an access level.

**ObjectTerritory2Association.** Accounts assigned to territories, either by rule or manually.

```sql
SELECT Territory2.Name, Territory2.Territory2Type.MasterLabel,
       ObjectId, AssociationCause
FROM ObjectTerritory2Association
WHERE ObjectId = :accountId
```

`AssociationCause` distinguishes `Territory2Manual` from `Territory2AssignmentRule`, which is the first thing to check when an account is in a territory nobody expected.

## Assignment rules

Rules place accounts into territories by field criteria:

```
Territory: India West Manufacturing
Rule: BillingState IN ('Maharashtra', 'Gujarat', 'Goa')
      AND Industry = 'Manufacturing'
      AND AnnualRevenue < 500000000
```

Rules can be set to run automatically on account create and edit, or only when explicitly triggered. Automatic evaluation is convenient and means an account changing state or industry silently changes territory — and therefore changes who can see it.

Rules can also be inherited by child territories, which reduces duplication in a deep hierarchy.

Accounts can additionally be assigned manually, which overrides nothing — manual and rule-based assignments coexist.

## Sharing through territories

Territory access is granted through the sharing model. An **Account Access Level** is set per territory: View, Edit, or none, with separate settings for the account's opportunities and cases.

Sharing rules can also target territories and "territories and subordinates" as a group type, exactly as they target roles and public groups. See [[03.9 - Sharing Rules]].

The share rows carry `RowCause = 'Territory2AssociationManual'` or `'TerritoryManual'` depending on configuration, so territory-granted access is visible in the standard diagnostic queries from [[03.10 - Manual, Team and Implicit Sharing]].

Opportunities are assigned a territory too, through `Territory2Id`, which drives territory-based forecasting and reporting. Assignment happens through a filter that can be customized with Apex:

```java
global class OpportunityTerritoryAssignmentFilter implements TerritoryMgmt.OpportunityTerritory2AssignmentFilter {

    global Map<Id, Id> getOpportunityTerritory2Assignments(List<String> opportunityIds) {
        Map<Id, Id> assignments = new Map<Id, Id>();

        for (Opportunity opp : [
            SELECT Id, AccountId, Product_Line__c,
                   (SELECT Territory2Id, Territory2.Territory2Type.DeveloperName
                    FROM Account.Territory2Associations__r)
            FROM Opportunity WHERE Id IN :opportunityIds
        ]) {
            // choose the geographic territory rather than an overlay when several apply
            for (ObjectTerritory2Association assoc : opp.Account.Territory2Associations__r) {
                if (assoc.Territory2.Territory2Type.DeveloperName == 'Geographic') {
                    assignments.put(opp.Id, assoc.Territory2Id);
                    break;
                }
            }
        }
        return assignments;
    }
}
```

This filter is where the "which territory gets the deal when three apply" question is answered, and it is a genuine business decision rather than a technical one.

## Realignment

The annual territory change is where this feature earns its complexity, and where it hurts.

The process:

1. Clone the active model into a new Planning-state model
2. Adjust the hierarchy, rules, and user assignments in the clone
3. Run assignment rules in the new model and review which accounts land where
4. Compare against the current model to see what moves
5. Activate the new model
6. The platform recalculates all territory-based sharing

Step 6 is the expensive part. On a large org this is a substantial background job, and access changes for many users at once. It should be scheduled deliberately, communicated in advance, and ideally rehearsed in a Full sandbox first with realistic data volume.

**Deferred sharing calculation** should be enabled around the activation to avoid repeated recalculation. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

Only one model can be Active. Others sit in Planning or Archived states, which is what allows next year's structure to be built alongside this year's.

## Territories versus the alternatives

The decision that should be made deliberately, because enabling territory management is a significant commitment:

| Requirement | Use |
| --- | --- |
| Simple, non-overlapping geographic coverage | Role hierarchy plus sharing rules |
| A fixed set of people per account | Account Teams |
| Overlapping coverage across several dimensions | Territory Management |
| Coverage that changes annually and needs planning | Territory Management |
| One rep per account, assigned by rule | Account ownership plus assignment automation |

The honest guidance: **do not enable territory management unless coverage genuinely overlaps.** It adds objects, a second hierarchy, a realignment process, and considerable sharing recalculation cost. A sales organization with clean geographic split and one owner per account gets nothing from it that sharing rules do not provide.

The signal that it is needed: the business maintains a territory spreadsheet outside Salesforce because the sharing model cannot express the coverage.

## Reporting

Territory-based reporting is one of the main reasons to adopt it:

```sql
SELECT Territory2.Name territory, COUNT(Id) accounts
FROM ObjectTerritory2Association
WHERE Territory2.Territory2Model.State = 'Active'
GROUP BY Territory2.Name
ORDER BY COUNT(Id) DESC
```

Pipeline by territory, which requires opportunity territory assignment to be working:

```sql
SELECT Territory2.Name territory, SUM(Amount) pipeline, COUNT(Id) deals
FROM Opportunity
WHERE IsClosed = false AND Territory2Id != null
GROUP BY Territory2.Name
```

Coverage gaps — accounts in no territory — are the report worth running after every realignment:

```sql
SELECT Id, Name, BillingState, Industry
FROM Account
WHERE Id NOT IN (SELECT ObjectId FROM ObjectTerritory2Association)
  AND Type = 'Customer'
```

Accounts in no territory are invisible to the sales organization, and after a realignment there are always some.

## Practical guidance

**Enable it only when coverage genuinely overlaps.** Otherwise roles and sharing rules are simpler and cheaper.

**Use the model versioning.** Building next year's structure in a Planning model and comparing before activation is the feature that makes realignment manageable.

**Rehearse activation in a Full sandbox.** The recalculation duration on production-scale data is the thing you need to know before scheduling it.

**Run a coverage gap report after every realignment.** Uncovered accounts are the most common realignment defect.

**Decide the opportunity territory assignment rule explicitly.** When several territories apply, something has to choose, and leaving it to the default is a decision by omission.

**Keep the hierarchy shallow.** As with roles, depth multiplies recalculation cost.
