# Transaction Finalizers

## The problem they solve

A Queueable throws an uncaught exception. Its transaction rolls back — including any log record it tried to write.

```java
public void execute(QueueableContext context) {
    try {
        callErpSystem();
    } catch (Exception e) {
        insert new Integration_Log__c(Message__c = e.getMessage());
        throw e;   // the log insert is rolled back with everything else
    }
}
```

Catch without rethrowing and the log survives, but the job is recorded as successful. Rethrow and the job is correctly marked failed, and there is no record of why.

Worse, an **uncatchable** failure — a `LimitException`, or the transaction being killed — leaves no opportunity to log at all.

A **Transaction Finalizer** runs after the Queueable completes, in its **own transaction**, whether the job succeeded or failed. It is the guaranteed hook that makes async failure handling possible.

## The interface

```java
public with sharing class ErpSyncFinalizer implements Finalizer {

    private final Set<Id> claimIds;
    private final Integer attemptNumber;

    public ErpSyncFinalizer(Set<Id> claimIds, Integer attemptNumber) {
        this.claimIds = claimIds;
        this.attemptNumber = attemptNumber;
    }

    public void execute(FinalizerContext context) {
        // this runs in a fresh transaction, so the log write is not rolled back
        if (context.getResult() == ParentJobResult.SUCCESS) {
            logSuccess(context.getAsyncApexJobId());
            return;
        }

        Exception cause = context.getException();
        logFailure(context.getAsyncApexJobId(), cause, attemptNumber);

        if (attemptNumber < 3 && isRetryable(cause)) {
            System.enqueueJob(new ErpSyncQueueable(claimIds, attemptNumber + 1));
        } else {
            markPermanentlyFailed(claimIds, cause);
        }
    }

    private Boolean isRetryable(Exception cause) {
        return cause instanceof CalloutException
            || (cause != null && cause.getMessage().contains('UNABLE_TO_LOCK_ROW'));
    }
}
```

Attaching it inside the Queueable:

```java
public with sharing class ErpSyncQueueable implements Queueable, Database.AllowsCallouts {

    private final Set<Id> claimIds;
    private final Integer attemptNumber;

    public ErpSyncQueueable(Set<Id> claimIds, Integer attemptNumber) {
        this.claimIds = claimIds;
        this.attemptNumber = attemptNumber;
    }

    public void execute(QueueableContext context) {
        // attaching before the work, so the finalizer runs even if the work throws immediately
        System.attachFinalizer(new ErpSyncFinalizer(claimIds, attemptNumber));

        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Claim_Amount__c
            FROM Warranty_Claim__c WHERE Id IN :claimIds
        ];

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/claims');
        req.setMethod('POST');
        req.setBody(JSON.serialize(ClaimPayload.from(claims)));

        HttpResponse res = new Http().send(req);
        if (res.getStatusCode() >= 300) {
            throw new IntegrationException('ERP sync failed: ' + res.getStatusCode());
        }
    }
}
```

**Attach the finalizer first**, before any work. A job that throws before attaching has no finalizer.

## FinalizerContext

```java
context.getAsyncApexJobId()   // the Queueable's job Id
context.getRequestId()        // the request Id, for log correlation
context.getResult()           // ParentJobResult.SUCCESS or UNHANDLED_EXCEPTION
context.getException()        // the exception, if it failed
```

`getResult()` returns an enum with two values. There is no partial state — the job either completed or it did not.

`getRequestId()` correlates with debug logs and Event Monitoring, which is what turns a failure log entry into something you can trace.

## What makes them different

**Only Queueable supports finalizers.** Not future, not Batch, not Scheduled.

Batch has `finish`, which serves a similar purpose but runs in the same job context and does not fire on every failure mode. Future has nothing at all.

This is the strongest argument for Queueable over future in any code where failure matters.

**The finalizer runs in a new transaction**, so:

- Its DML is not rolled back by the job's failure
- It gets a fresh limit budget
- It can make callouts
- It can enqueue another job

**Exactly one finalizer per Queueable.** Attaching a second replaces the first.

**A finalizer can enqueue one Queueable**, which is what makes retry possible.

## The retry pattern

The main practical use, and worth building once properly.

```java
public with sharing class RetryableFinalizer implements Finalizer {

    private static final Integer MAX_ATTEMPTS = 3;

    private final String context;
    private final Set<Id> recordIds;
    private final Integer attempt;
    private final Type jobType;

    public RetryableFinalizer(String context, Type jobType, Set<Id> recordIds, Integer attempt) {
        this.context = context;
        this.jobType = jobType;
        this.recordIds = recordIds;
        this.attempt = attempt;
    }

    public void execute(FinalizerContext ctx) {
        if (ctx.getResult() == ParentJobResult.SUCCESS) {
            return;
        }

        Exception cause = ctx.getException();

        insert new Integration_Log__c(
            Context__c = context,
            Attempt__c = attempt,
            Job_Id__c = ctx.getAsyncApexJobId(),
            Request_Id__c = ctx.getRequestId(),
            Message__c = cause?.getMessage(),
            Stack_Trace__c = cause?.getStackTraceString(),
            Severity__c = attempt >= MAX_ATTEMPTS ? 'Error' : 'Warning'
        );

        if (attempt >= MAX_ATTEMPTS || !isTransient(cause)) {
            markFailed(recordIds, cause);
            return;
        }

        // exponential backoff, capped at the ten-minute maximum delay
        Integer delayMinutes = Math.min((Integer) Math.pow(2, attempt), 10);
        RetryableJob job = (RetryableJob) jobType.newInstance();
        job.initialize(recordIds, attempt + 1);
        System.enqueueJob(job, delayMinutes);
    }

    private Boolean isTransient(Exception cause) {
        if (cause == null) {
            return false;
        }
        return cause instanceof CalloutException
            || cause.getMessage().contains('UNABLE_TO_LOCK_ROW')
            || cause.getMessage().contains('Read timed out');
    }
}
```

Three things make this correct rather than merely working:

**Distinguishing transient from permanent.** Retrying a validation failure three times achieves nothing and burns the async allocation. Retrying a timeout usually succeeds. See [[13.17 - Error Handling, Retries and Idempotency]].

**A maximum attempt count.** Without it, a permanently broken endpoint produces an infinite retry chain consuming the org's daily async budget.

**Backoff.** Immediately retrying against a system that is down makes the outage worse. The ten-minute cap is the platform's maximum enqueue delay.

## Logging that survives

The second main use, and the reason finalizers appear throughout this course as the answer to "how do I log an async failure".

Because the finalizer runs in its own transaction, a plain `insert` works:

```java
public void execute(FinalizerContext ctx) {
    insert new Automation_Log__c(
        Context__c = context,
        Job_Id__c = ctx.getAsyncApexJobId(),
        Result__c = String.valueOf(ctx.getResult()),
        Message__c = ctx.getException()?.getMessage(),
        Stack_Trace__c = ctx.getException()?.getStackTraceString()
    );
}
```

No platform event needed, no savepoint dance. This is the cleanest failure logging available on the platform, and it is available only in this one place.

For synchronous code, platform events remain the mechanism. See [[20.5 - Custom Logging Frameworks]].

## Notifying on failure

A finalizer can call out, which means it can post to Slack or an alerting system directly:

```java
public void execute(FinalizerContext ctx) {
    if (ctx.getResult() == ParentJobResult.SUCCESS) {
        return;
    }

    logFailure(ctx);

    if (attempt >= MAX_ATTEMPTS) {
        // callouts are permitted here, since this is a fresh transaction
        AlertingService.notifyIntegrationFailure(
            context, ctx.getException()?.getMessage(), recordIds.size()
        );
    }
}
```

Alerting only on final failure, rather than on every attempt, is what stops the channel becoming noise that nobody reads.

## Limits

- **One finalizer per Queueable.**
- **One Queueable enqueued from a finalizer**, which is what bounds the retry chain to one job at a time.
- The finalizer's transaction has normal async limits.
- **A finalizer that itself throws** is not retried, and the failure is recorded against the job. Keeping finalizer logic simple and defensive matters.

That last point deserves attention: a finalizer doing complex work can fail, and there is no finalizer for the finalizer. Log first, then do anything else.

## Testing

```java
@IsTest
static void finalizerRetriesOnCalloutFailure() {
    Test.setMock(HttpCalloutMock.class, new ErpErrorMock(503));
    Set<Id> claimIds = TestDataFactory.createClaimIds(5);

    Test.startTest();
    System.enqueueJob(new ErpSyncQueueable(claimIds, 1));
    Test.stopTest();

    List<Integration_Log__c> logs = [
        SELECT Attempt__c, Severity__c FROM Integration_Log__c WHERE Context__c = 'ErpSync'
    ];
    Assert.areEqual(1, logs.size(), 'The finalizer should have logged the failure');
    Assert.areEqual('Warning', logs[0].Severity__c,
        'A retryable failure below the attempt cap should log as a warning');
}
```

The constraint: **only one level of chaining runs in test context**, so a test cannot verify that attempt three gives up. Testing the decision logic directly is the workaround:

```java
@IsTest
static void permanentFailuresAreNotRetried() {
    RetryableFinalizer finalizer = new RetryableFinalizer(
        'ErpSync', ErpSyncQueueable.class, claimIds, 1
    );

    Assert.isFalse(
        finalizer.isTransientForTest(new DmlException('FIELD_CUSTOM_VALIDATION_EXCEPTION')),
        'A validation failure should not be retried'
    );
    Assert.isTrue(
        finalizer.isTransientForTest(new CalloutException('Read timed out')),
        'A timeout should be retried'
    );
}
```

`@TestVisible` on the private method makes this possible without widening the public surface. See [[19.6 - Testing Async Apex]].

## Practical guidance

**Attach the finalizer as the first statement** in `execute`.

**Use it for logging** — it is the only place an async failure can be recorded reliably.

**Distinguish transient from permanent failures** before retrying.

**Cap retry attempts**, and back off between them.

**Alert only on final failure.**

**Keep finalizer logic simple.** There is no safety net beneath it.

**Prefer Queueable over future** in anything where failure needs handling, because this is the capability future lacks entirely.
