# Platform Cache

## What it is

An in-memory key-value store on the Salesforce servers, surviving across transactions. Statics reset at the transaction boundary; Platform Cache does not.

Two partitions, with different scopes:

**Org cache** — shared by every user in the org. Right for reference data, configuration, and expensive shared computations.

**Session cache** — per user session, cleared on logout or after eight hours. Right for user-specific state such as wizard progress or a filter selection.

## The allocation

Cache capacity is **purchased**, not free. Developer Edition and trial orgs get a small trial allocation; production orgs have whatever was bought.

```
Setup → Platform Cache → allocate capacity to partitions
```

A partition splits its allocation between org and session cache:

```
Partition: ClaimData
  Org cache:     5 MB
  Session cache: 2 MB
```

**The whole design assumption is that the cache may be empty.** Capacity is finite, entries are evicted under pressure, and an org that has not purchased capacity has almost none. Code that requires a cache hit is broken code.

## Reading and writing

```java
public with sharing class CoverageCache {

    private static final String PARTITION = 'local.ClaimData';
    private static final Integer TTL_SECONDS = 3600;

    public static Coverage_Rule__mdt[] getRules() {
        Cache.OrgPartition partition = Cache.Org.getPartition(PARTITION);
        List<Coverage_Rule__mdt> rules = (List<Coverage_Rule__mdt>) partition.get('coverageRules');

        // a miss is normal, not exceptional — always have a fallback path
        if (rules == null) {
            rules = [
                SELECT Coverage_Level__c, Max_Claim_Amount__c, Requires_Approval__c
                FROM Coverage_Rule__mdt WHERE Active__c = true
            ];
            partition.put('coverageRules', rules, TTL_SECONDS);
        }
        return rules;
    }
}
```

`local.` is the namespace prefix for a partition in your own org; a packaged partition uses the package namespace.

**The default TTL is 24 hours for org cache and 8 hours for session cache**, with a maximum of 48 hours. Setting it explicitly makes the staleness window a deliberate decision rather than a default.

## The cache builder

The pattern that removes the null check from every call site.

```java
public with sharing class CoverageRuleCacheBuilder implements Cache.CacheBuilder {

    public Object doLoad(String cacheKey) {
        // called only on a miss; the platform handles the rest
        return [
            SELECT Coverage_Level__c, Max_Claim_Amount__c, Requires_Approval__c
            FROM Coverage_Rule__mdt
            WHERE Active__c = true AND Coverage_Level__c = :cacheKey
        ];
    }
}
```

```java
List<Coverage_Rule__mdt> rules = (List<Coverage_Rule__mdt>) Cache.Org
    .get(CoverageRuleCacheBuilder.class, 'Premium');
```

`doLoad` runs only when the key is absent. The caller never checks for null, and the loading logic lives in one place.

**This is the better pattern** for anything read repeatedly. The manual get-check-put form is fine for one-off use and duplicates the fallback everywhere else.

## What belongs in the cache

**Configuration and reference data.** Custom metadata records, rule tables, mapping data — read often, changed rarely.

**Expensive computed results.** A pricing matrix, a hierarchy resolution, an aggregation whose inputs change daily.

**External data with a tolerable staleness window.** An exchange rate, a product catalogue fetched from an ERP.

**Describe results**, though a static usually suffices since describes are cheap once cached per transaction.

**Session-scoped user state.** A multi-step wizard's progress, a console filter selection.

## What does not

**Anything that must be current.** Cached data is stale by definition. A claim's approval status, an inventory count, a balance — read them.

**Anything security-sensitive without care.** Org cache is shared across all users. Caching a query result filtered by the running user's sharing means the next user gets someone else's data.

```java
// Wrong: the result depends on who ran it, and the cache does not
List<Warranty_Claim__c> claims = [
    SELECT Id FROM Warranty_Claim__c WITH USER_MODE
];
Cache.Org.put('userClaims', claims);
```

Cache **user-independent** data in org cache. Anything user-scoped belongs in session cache, or in the key:

```java
String key = 'claims_' + UserInfo.getUserId();
Cache.Session.put(key, claims);
```

**Large objects.** Entries are capped, and a large entry crowds out everything else.

**Anything you cannot recompute.** A cache is not storage. Entries are evicted without warning.

## Keys

```
Alphanumeric only, no spaces or special characters
Maximum 50 characters
Case-sensitive
```

```java
// Invalid
partition.put('claim-rules:premium', rules);

// Valid
partition.put('claimRulesPremium', rules);
```

Encoding a version into the key is a useful invalidation technique:

```java
private static String key(String base) {
    // bumping the version constant invalidates every entry without deleting them
    return base + 'v3';
}
```

Deploying a change to the version constant makes every old entry unreachable, which is simpler than enumerating and removing keys.

## Invalidation

The hard part of any cache.

**TTL** is the simplest and usually sufficient. Set it to the tolerable staleness window and accept it.

**Explicit removal** when the underlying data changes:

```java
public with sharing class CoverageRuleTriggerHandler {

    public static void run() {
        if (Trigger.isAfter) {
            // clearing on change keeps the window short without a short TTL
            Cache.Org.getPartition('local.ClaimData').remove('coverageRules');
        }
    }
}
```

Custom Metadata cannot have triggers, so for metadata-driven configuration the practical options are a short TTL or a version-bumped key deployed alongside the change.

**A key naming convention** that makes bulk invalidation possible:

```java
Cache.OrgPartition partition = Cache.Org.getPartition('local.ClaimData');
for (String cacheKey : partition.getKeys()) {
    if (cacheKey.startsWith('coverage')) {
        partition.remove(cacheKey);
    }
}
```

## Handling a miss gracefully

The thing that separates a working cache from an outage.

```java
public static List<Coverage_Rule__mdt> getRules() {
    try {
        Cache.OrgPartition partition = Cache.Org.getPartition(PARTITION);
        List<Coverage_Rule__mdt> cached = (List<Coverage_Rule__mdt>) partition.get('coverageRules');
        if (cached != null) {
            return cached;
        }
    } catch (Cache.Org.OrgCacheException e) {
        // a missing or unallocated partition must not break the feature
        AutomationLogger.logWarning('CoverageCache', 'Cache unavailable: ' + e.getMessage());
    }

    return loadFromDatabase();
}
```

**A missing partition throws.** An org that has not allocated capacity, or where the partition was renamed, produces an exception rather than a null — and code assuming a null return breaks.

Wrapping cache access so it degrades to the uncached path is the difference between a slower feature and a broken one.

## Diagnostics

```java
Cache.OrgPartition partition = Cache.Org.getPartition('local.ClaimData');

partition.contains('coverageRules');
partition.getKeys();
partition.remove('coverageRules');
partition.getCapacity();          // percentage used
partition.getAvgGetTime();
partition.getAvgValueSize();
partition.getNumKeys();
```

The Platform Cache page in Setup shows hit rate per partition, which is the number that matters.

**A low hit rate means the cache is not helping** — usually because entries are evicted under capacity pressure, or the TTL is shorter than the access interval. Either fix the sizing or accept that the cache is not the right tool for that data.

## Does it help with limits?

Directly and indirectly.

**Query count.** A cached configuration lookup is a query that does not run. In a transaction where flows and packages have consumed most of the budget, that matters.

**CPU.** A cached computation is CPU not spent.

**Transaction duration**, which feeds the concurrency limit from [[16.6 - Concurrency and Long Running Requests]].

**What it does not help:** DML, heap within the transaction, or anything about the write path. Platform Cache is a read optimization.

## Cache versus the alternatives

| Need | Mechanism |
| --- | --- |
| Within one transaction | A static variable |
| Across transactions, shared, slow-changing | Org cache |
| Across transactions, per user | Session cache |
| Configuration deployed with code | Custom Metadata — already cached by the platform |
| Client-side, per component | The LWC wire cache |
| Client-side, per user, persistent | Not available in LWC — no browser storage |

**Custom Metadata is already cached by the platform.** Querying a custom metadata type does **not** consume a SOQL query, which makes Platform Cache redundant for most configuration.

That is worth stating plainly: **before caching configuration, check whether Custom Metadata already solves it.** It usually does, with no allocation to purchase and no invalidation to manage. See [[17.1 - Custom Metadata Types]].

## When Platform Cache is genuinely the answer

Narrower than it first appears.

- An expensive **aggregation** whose inputs change daily, read on every page load
- **External data** fetched by callout, with a tolerable staleness window
- A large **computed structure** — a resolved hierarchy, a pricing matrix — that costs real CPU to build
- **Session state** across a multi-step process

For plain configuration, Custom Metadata is simpler and free.

## Practical guidance

**Use `Cache.CacheBuilder`** rather than manual get-check-put.

**Always handle a miss.** The cache may be empty, unallocated, or evicted.

**Wrap access in try/catch** so a missing partition degrades rather than breaks.

**Never cache user-scoped data in org cache.**

**Set TTL deliberately** to the tolerable staleness window.

**Use a version suffix in keys** for deploy-time invalidation.

**Check the hit rate.** A low one means the cache is not earning its allocation.

**Check whether Custom Metadata already covers it** before buying cache capacity.
