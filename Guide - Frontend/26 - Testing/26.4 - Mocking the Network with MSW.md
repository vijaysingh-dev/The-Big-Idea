# Mocking the Network with MSW

Mock Service Worker intercepts requests at the **network layer** rather than by replacing modules. Your code calls the real `fetch`, through the real API layer, with real error handling — only the response is synthetic.

## Why this matters

```ts
// Module mocking — the test exercises the mock
vi.mock("./api", () => ({ getProducts: vi.fn().mockResolvedValue([]) }));
```

That test proves the component renders when `getProducts` resolves. It proves nothing about URL construction, auth headers, `res.ok` checking, JSON parsing, schema validation, or retry behavior — all of which live in the code you just replaced ([[24.1 - Building an API Layer]]).

```ts
// Network mocking — the test exercises everything
server.use(
  http.get("/api/products", () => HttpResponse.json([{ id: "1", name: "Shoe" }]))
);
```

The same handlers also work in the browser during development, and in Playwright E2E runs — one set of mocks for three environments ([[26.1 - Testing Philosophy]]).

## Setup

```ts
// src/mocks/handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("/api/products", () => HttpResponse.json(products)),

  http.get("/api/products/:id", ({ params }) => {
    const product = products.find(p => p.id === params.id);
    if (!product) return new HttpResponse(null, { status: 404 });
    return HttpResponse.json(product);
  }),

  http.post("/api/products", async ({ request }) => {
    const body = await request.json();
    return HttpResponse.json({ id: crypto.randomUUID(), ...body }, { status: 201 });
  }),
];
```

```ts
// src/mocks/server.ts
import { setupServer } from "msw/node";
import { handlers } from "./handlers";

export const server = setupServer(...handlers);
```

```ts
// src/test/setup.ts
import { server } from "../mocks/server";

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

`onUnhandledRequest: "error"` is the setting that makes MSW valuable. Without it, an unmocked request silently hits the real network and produces a confusing failure. With it, you get an immediate error naming the URL — which also catches accidental requests to third-party services in tests.

`resetHandlers()` after each test removes per-test overrides so they cannot leak ([[26.2 - Unit Testing with Vitest and Jest]]).

## Per-test overrides

```ts
test("shows an error when the request fails", async () => {
  server.use(
    http.get("/api/products", () => new HttpResponse(null, { status: 500 }))
  );

  renderWithProviders(<ProductList />);

  expect(await screen.findByRole("alert")).toHaveTextContent(/went wrong/i);
});
```

The base handlers describe the happy path; individual tests override for the case they are testing. This keeps most tests short and makes the exceptional case obvious.

Common overrides:

```ts
// Network failure — not an HTTP error
http.get("/api/products", () => HttpResponse.error());

// Slow response, for testing loading states
http.get("/api/products", async () => {
  await delay(1000);
  return HttpResponse.json(products);
});

// Fail once, then succeed — for retry logic
let attempt = 0;
http.get("/api/products", () => {
  if (attempt++ === 0) return new HttpResponse(null, { status: 500 });
  return HttpResponse.json(products);
});
```

`HttpResponse.error()` simulates a genuine network failure, which `fetch` surfaces as a `TypeError` — a different code path from a 500 ([[24.3 - Retries Timeouts and Cancellation]]).

## Asserting on requests

```ts
test("sends the auth header", async () => {
  let capturedAuth: string | null = null;

  server.use(
    http.get("/api/me", ({ request }) => {
      capturedAuth = request.headers.get("Authorization");
      return HttpResponse.json(user);
    })
  );

  renderWithProviders(<Profile />);
  await screen.findByText(user.name);

  expect(capturedAuth).toBe("Bearer test-token");
});
```

Capturing the request lets you assert on headers, query parameters and body — verifying the API layer builds requests correctly, which module mocking cannot check.

For search parameters:

```ts
http.get("/api/products", ({ request }) => {
  const url = new URL(request.url);
  const page = url.searchParams.get("page");
  return HttpResponse.json(pageOf(Number(page)));
});
```

This is how you test pagination without a backend ([[24.4 - Pagination and Infinite Scroll]]).

## Browser mode for development

```ts
// src/mocks/browser.ts
import { setupWorker } from "msw/browser";
export const worker = setupWorker(...handlers);
```

```ts
// main.tsx
if (import.meta.env.DEV && import.meta.env.VITE_MOCK_API === "true") {
  const { worker } = await import("./mocks/browser");
  await worker.start({ onUnhandledRequest: "bypass" });
}
```

```bash
npx msw init public/ --save
```

A Service Worker intercepts requests in the browser ([[14.4 - Cache API and Service Workers]]). This lets frontend work proceed before the backend exists, and makes error and empty states trivially reproducible during development — set a handler to return 500 and see the real error UI.

Note `onUnhandledRequest: "bypass"` in the browser, so unmocked assets and third-party requests pass through normally.

Conditionally importing the mock module keeps it out of the production bundle ([[08.2 - Dynamic Imports]]).

## Fixtures

```ts
export function makeProduct(overrides: Partial<Product> = {}): Product {
  return {
    id: crypto.randomUUID(),
    name: "Test Product",
    price: 1000,
    tags: [],
    createdAt: new Date("2026-01-01"),
    ...overrides,
  };
}
```

Factories with overrides keep tests readable — each test specifies only what it cares about:

```ts
const outOfStock = makeProduct({ stock: 0 });
```

Validate fixtures against the real schema in development so they cannot drift from the API contract ([[25.7 - Typing API Responses and Zod]]):

```ts
export const makeProduct = (o = {}) => productSchema.parse({ ...defaults, ...o });
```

This catches the common problem of tests passing against fixtures the backend would never produce.

## GraphQL

```ts
import { graphql, HttpResponse } from "msw";

graphql.query("GetProducts", () =>
  HttpResponse.json({ data: { products } })
);

graphql.mutation("CreateProduct", ({ variables }) =>
  HttpResponse.json({ data: { createProduct: { id: "1", ...variables.input } } })
);
```

Same model, matched by operation name rather than URL.

## Limitations

**Service Workers need HTTPS or localhost**, so browser mode does not work on an arbitrary HTTP staging host.

**Not for E2E against a real backend.** Playwright tests that exercise the actual system should not mock — though MSW is useful in Playwright for isolating the frontend from a flaky third-party dependency ([[26.5 - End to End Testing with Playwright]]).

**Handlers are code that can drift.** A mock returning a shape the server no longer produces gives false confidence. Contract testing, or generating handlers from an OpenAPI schema, addresses this.

**WebSockets** have support but it is newer and less complete than the HTTP interception.

## How senior engineers actually use this

**They mock at the network boundary by default** and treat `vi.mock` of an API module as a smell.

**They set `onUnhandledRequest: "error"`** so unmocked requests fail loudly.

**They keep happy-path handlers global** and override per test for error, empty and slow cases.

**They share handlers between tests and development**, which makes error states easy to demonstrate.

**They validate fixtures against the response schema**, so mocks cannot drift from the contract.

## Common pitfalls

- Unhandled requests silently hitting the network — fix with `onUnhandledRequest: "error"`.
- Missing `resetHandlers()`, so a per-test override leaks.
- Mocking API modules instead of the network, skipping the code under test.
- Fixtures that drift from the real response shape.
- Confusing `HttpResponse.error()` (network failure) with a 500 status.
- Forgetting `msw init` so the browser worker file is missing.
- Bundling the mock setup into production.

## Interview angle

"How do you test components that fetch data" is where this belongs. The strong answer contrasts module mocking with network mocking: replacing the API module means the test never exercises URL building, headers, status checking, parsing or error handling, while intercepting at the network layer keeps all of it in the code path. Adding that the same handlers drive local development — so error and empty states are reproducible without a backend — shows you use it as a workflow tool rather than just a test dependency.
