# Promises from First Principles

A **promise** is an object representing a value that is not available yet. Its power is that it is a *value* — it can be returned, stored in a variable, passed to a function, put in an array. That is the fundamental upgrade over callbacks ([[04.1 - Callbacks and Callback Hell]]).

## States

A promise is in exactly one of three states:

- **pending** — not settled yet
- **fulfilled** — settled with a value
- **rejected** — settled with a reason

Once settled it is **immutable**. It can never change state again, and its value can never change. Later calls to `resolve` or `reject` are silently ignored. "Settled" means fulfilled or rejected; "resolved" is a subtly different term meaning the promise has been locked to a fate, which may still be pending if it was resolved with another pending promise.

```js
const p = new Promise((resolve, reject) => {
  resolve("first");
  resolve("second");  // ignored
  reject("error");    // ignored
});
```

This one-shot guarantee is what makes promises safe to hand to untrusted code.

## Constructing

```js
const delay = ms => new Promise(resolve => setTimeout(resolve, ms));

const fromCallback = new Promise((resolve, reject) => {
  legacyApi((err, data) => (err ? reject(err) : resolve(data)));
});

Promise.resolve(42);          // already fulfilled
Promise.reject(new Error()); // already rejected
```

The executor function runs **synchronously**, immediately, before the constructor returns. Only the `.then` reactions are deferred.

```js
console.log("A");
new Promise(res => { console.log("B"); res(); }).then(() => console.log("D"));
console.log("C");
// A, B, C, D
```

This surprises people. The promise body is not "background work" — it is synchronous setup that happens to kick off something asynchronous.

## The three consumption methods

```js
fetchUser()
  .then(user => console.log(user))
  .catch(err => console.error(err))
  .finally(() => setLoading(false));
```

- **`.then(onFulfilled, onRejected)`** — the second argument catches rejections from the *previous* promise, but not from `onFulfilled` itself. `.catch(fn)` is exactly `.then(undefined, fn)` and catches both, which is why it is preferred.
- **`.finally(fn)`** — runs on either outcome, receives no arguments, and passes the original value or rejection through unchanged. Returning a value from it does nothing; returning a *promise* delays settlement until it resolves.

## Every handler returns a new promise

This is the mechanism behind chaining ([[04.3 - Promise Chaining and Error Handling]]):

```js
const p1 = fetchUser();
const p2 = p1.then(u => u.name);
p1 === p2; // false
```

What you return from a handler determines the next promise's fate:

| Return value | Next promise |
| --- | --- |
| a plain value | fulfilled with it |
| a promise | adopts that promise's eventual state |
| nothing | fulfilled with `undefined` |
| a thrown error | rejected with it |

Returning a promise and having the chain *wait* for it is called **assimilation**, and it is what lets a chain flatten rather than nest.

## Promises are always asynchronous

```js
Promise.resolve(1).then(v => console.log(v));
console.log(2);
// 2, then 1
```

Even an already-fulfilled promise schedules its reaction on the microtask queue ([[01.6 - Microtasks vs Macrotasks]]). This eliminates the sync/async inconsistency that plagued callbacks — behavior never depends on whether a cache was warm.

## Thenables

Anything with a `.then` method is a **thenable** and is treated as a promise by the machinery:

```js
const fake = {
  then(resolve) { resolve("from a thenable"); },
};

Promise.resolve(fake).then(console.log); // "from a thenable"
await fake;                              // works too
```

This is how jQuery deferreds and Bluebird promises interoperate with native ones. It also means an object with an unrelated `then` property will be mistakenly awaited — a genuine bug source when API responses contain a field named `then`.

## A minimal implementation

Writing this once makes the semantics permanent. This is a frequent senior-level machine-coding question.

```js
class MyPromise {
  #state = "pending";
  #value;
  #callbacks = [];

  constructor(executor) {
    const settle = (state, value) => {
      if (this.#state !== "pending") return;
      this.#state = state;
      this.#value = value;
      this.#callbacks.forEach(cb => queueMicrotask(cb));
      this.#callbacks = [];
    };

    try {
      executor(v => settle("fulfilled", v), e => settle("rejected", e));
    } catch (e) {
      settle("rejected", e);
    }
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const handle = () => {
        const handler = this.#state === "fulfilled" ? onFulfilled : onRejected;

        if (typeof handler !== "function") {
          // pass through when no handler is supplied
          this.#state === "fulfilled" ? resolve(this.#value) : reject(this.#value);
          return;
        }

        try {
          resolve(handler(this.#value));
        } catch (e) {
          reject(e);
        }
      };

      this.#state === "pending" ? this.#callbacks.push(handle) : queueMicrotask(handle);
    });
  }

  catch(onRejected) { return this.then(undefined, onRejected); }
}
```

The pieces an interviewer looks for: the state guard making settlement one-shot, `queueMicrotask` for async scheduling, `then` returning a new promise, the `try/catch` converting thrown errors into rejections, and the pass-through when a handler is missing (which is what lets `.catch` at the end of a chain see errors from anywhere in it).

A fully spec-compliant `resolve` must also detect thenables and adopt them; the version above resolves them only because the outer `MyPromise` constructor is given the returned value directly.

## How senior engineers actually use this

**They avoid the `new Promise` constructor in application code.** Almost everything already returns a promise. The constructor is for wrapping callback or event APIs at a boundary, and using it elsewhere usually means an unnecessary layer — the "deferred antipattern".

```js
// Unnecessary
function get(url) {
  return new Promise((res, rej) => fetch(url).then(res, rej));
}
// Just return fetch(url)
```

**They rely on the one-shot guarantee.** Deduplicating in-flight requests works because a stored promise can be handed to any number of callers and each gets the same settled result:

```js
const inFlight = new Map();

function dedupedFetch(url) {
  if (!inFlight.has(url)) {
    inFlight.set(url, fetch(url).finally(() => inFlight.delete(url)));
  }
  return inFlight.get(url);
}
```

**They treat a promise as a value, not an operation.** Storing promises in a cache, mapping an array of ids to an array of promises, passing a promise into a component — these all follow from promises being ordinary values.

**They know promises are not cancellable.** A settled promise cannot be undone and a pending one cannot be stopped. Cancellation is layered on with `AbortController` ([[04.6 - AbortController and Cancellation]]).

## Common pitfalls

- Expecting the executor to run asynchronously. It runs immediately and synchronously.
- Wrapping an existing promise in `new Promise` for no reason.
- Forgetting that a rejection with no `.catch` anywhere becomes an unhandled rejection, which crashes Node and logs loudly in browsers.
- Assuming a promise starts work when you `.then` it. The work started when the promise was created — promises are **eager**, unlike observables or `async` thunks.
- Objects with an incidental `then` property being auto-awaited.

## Interview angle

"What is a promise" should get: an object representing a future value, in one of three states, settling exactly once and immutably, with reactions always scheduled asynchronously as microtasks. "Implement a promise" is common at senior level — get the state guard, microtask scheduling, `then` returning a new promise, and error-to-rejection conversion right, and mention thenable assimilation even if you do not implement it fully.
