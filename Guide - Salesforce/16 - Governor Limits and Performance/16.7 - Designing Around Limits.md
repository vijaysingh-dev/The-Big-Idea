# Designing Around Limits

## The shift in thinking

Limits cannot be caught, so they cannot be recovered from. That means limit handling is an **architectural** activity, not an error-handling one.

The question is never "what do I do when I hit 100 queries". It is "why is this transaction anywhere near 100 queries".

## The five structural patterns

Everything in this note reduces to five moves.

**1. Collect, query once, act once.** The bulkification discipline.

**2. Split the transaction.** Async gives a fresh budget per execution.

**3. Move work off the synchronous path.** Users wait for less.

**4. Reduce what runs at all.** Change detection, guard clauses, and less automation.

**5. Cache what does not change.** Platform Cache and statics.

## Bulkification

The first and most important, covered in [[10.6 - Bulkification Patterns]]. Restated as the design rule:

**Every method takes a collection.**

```java
public static void process(Set<Id> claimIds)                    // correct
public static void process(List<Warranty_Claim__c> claims)      // correct
public static void process(Warranty_Claim__c claim)             // invites a loop
```

A single-record signature is an invitation to call it in a loop, and someone eventually will. The signature is the design decision; everything else follows.

## Splitting the transaction

The fundamental scaling move on the platform.

```java
// One transaction, one budget, fails at volume
ClaimEnrichmentService.enrichAll(tenThousandIds);

// Fifty transactions, fifty budgets
Database.executeBatch(new ClaimEnrichmentBatch(), 200);
```

Batch Apex chunks automatically with monitoring; a Queueable chain does it manually and is right below a few thousand records. See [[12.10 - Choosing the Right Async Tool]].

**The important framing:** async is not a way to avoid limits. It is a way to get more budget by having more transactions.

## Deferring from the synchronous path

```java
public with sharing class ClaimSubmissionService {

    public static SubmissionResult submit(Warranty_Claim__c claim) {
        ClaimValidationService.validate(claim);
        insert claim;

        // everything the user does not need to see happens elsewhere
        System.enqueueJob(new ClaimEnrichmentQueueable(new Set<Id>{ claim.Id }));

        return SubmissionResult.success(claim.Id);
    }
}
```

The test: **does the user need this to have happened before the page returns?**

Synchronous: validation, the save, anything the response depends on.
Asynchronous: enrichment, notification, integration, aggregate recalculation, logging.

Most transactions have far more in the first category than they need, and moving work out helps three limits at once — CPU, queries, and concurrency. See [[16.6 - Concurrency and Long Running Requests]].

## Doing less work

Often the cheapest fix, and the one people skip in favour of restructuring.

**Change detection.** Most trigger work should fire on a transition, not on every save.

```java
for (Warranty_Claim__c claim : newClaims) {
    Warranty_Claim__c prior = oldClaims.get(claim.Id);
    // a save that did not change the status does no work at all
    if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') {
        newlyApproved.add(claim);
    }
}

if (newlyApproved.isEmpty()) {
    return;   // no query, no DML, no CPU
}
```

An after-update handler without this comparison runs its full cost on every edit, including the recursive pass from a roll-up recalculation. See [[11.2 - Trigger Context Variables]].

**Early exit.** A guard at the top of a handler is free.

```java
if (AutomationBypass.isBypassed('WarrantyClaim')) {
    return;
}
```

**Update only what changed.**

```java
List<Asset> changed = new List<Asset>();
for (Asset asset : assets.values()) {
    // skipping unchanged parents stops an entire downstream cascade
    if (asset.Open_Claim_Count__c != originalCounts.get(asset.Id)) {
        changed.add(asset);
    }
}
if (!changed.isEmpty()) {
    update changed;
}
```

That comparison removes DML rows, the parent's trigger execution, its flows, and its own roll-up cascade. It is the highest-leverage three lines in most roll-up implementations.

## Reducing automation, not just code

A limit failure on an object with four flows, two triggers, and a managed package is an automation problem rather than a code problem.

The audit:

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status FROM ApexTrigger WHERE TableEnumOrId = 'Warranty_Claim__c'"
```

```sql
SELECT ApiName, Label, TriggerType, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerObjectOrEventLabel = 'Warranty Claim'
```

Plus the validation rules, the roll-up summaries on the object **and its parents**, and any assignment or escalation rules.

**Consolidation is a limits activity.** One trigger per object and one record-triggered flow per object per timing reduces total consumption, not just ordering ambiguity. See [[07.13 - Order of Execution]].

**Roll-up count on hot parents** deserves specific attention. Forty roll-ups on Account means forty recalculations on every child change, each of which sends the account through its own save pipeline.

## Caching

**Statics** for transaction-scoped caching:

```java
public with sharing class SchemaCache {
    private static Map<String, Schema.SObjectType> globalDescribe;

    public static Schema.SObjectType objectType(String name) {
        if (globalDescribe == null) {
            globalDescribe = Schema.getGlobalDescribe();
        }
        return globalDescribe.get(name.toLowerCase());
    }
}
```

Statics reset at transaction boundaries, including async ones. They are right for describe results and recursion guards, wrong for behaviour flags. See [[09.8 - Static Members and Class Level State]].

**Platform Cache** for cross-transaction caching of expensive, slow-changing data. See [[16.8 - Platform Cache]].

## The selector pattern

Centralizing queries makes consumption visible and reusable.

```java
public with sharing class ClaimSelector {

    public static Map<Id, List<Warranty_Claim__c>> openByAsset(Set<Id> assetIds) {
        Map<Id, List<Warranty_Claim__c>> byAsset = new Map<Id, List<Warranty_Claim__c>>();

        for (Warranty_Claim__c claim : [
            SELECT Id, Asset__c, Status__c, Claim_Amount__c
            FROM Warranty_Claim__c
            WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
            WITH USER_MODE
        ]) {
            if (!byAsset.containsKey(claim.Asset__c)) {
                byAsset.put(claim.Asset__c, new List<Warranty_Claim__c>());
            }
            byAsset.get(claim.Asset__c).add(claim);
        }
        return byAsset;
    }
}
```

Two benefits for limits: queries are in one place where they can be counted, and a selector method returning a keyed map discourages the per-record query that would otherwise follow.

Section 18 covers the layering properly. See [[18.5 - Selector Layer]].

## Defensive limit checks

For genuinely variable work, where the record count is not known in advance.

```java
public static void enrich(List<Id> claimIds) {
    List<Id> remaining = new List<Id>();

    for (Integer i = 0; i < claimIds.size(); i++) {
        // headroom, so the deferral itself has budget to run
        if (Limits.getQueries() > Limits.getLimitQueries() - 10
            || Limits.getCpuTime() > Limits.getLimitCpuTime() - 2000) {

            for (Integer j = i; j < claimIds.size(); j++) {
                remaining.add(claimIds[j]);
            }
            break;
        }
        processClaim(claimIds[i]);
    }

    if (!remaining.isEmpty()) {
        System.enqueueJob(new ClaimEnrichmentQueueable(remaining));
    }
}
```

**This is not a substitute for bulkification.** Code needing it for ordinary processing is code that should be restructured. It earns its place where the work genuinely varies — a configuration-driven rule engine, or processing whose cost depends on the data.

## Designing for headroom

The design target is not "under the limit". It is **well under**, because the margin absorbs data growth, added automation, and the managed package installed next year.

A useful rule: **a routine transaction should sit below 50 percent of any limit.**

```
Number of SOQL queries: 94 out of 100     ← fails next quarter
Number of SOQL queries: 31 out of 100     ← healthy
```

The 94 is not "working". It is one flow away from failing, and the person who adds that flow will not know.

## Assert on consumption

Making the margin verifiable rather than aspirational.

```java
@IsTest
static void handlerStaysWellWithinLimitsAtBulk() {
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(assets, 200);

    Test.startTest();
    insert claims;

    // a query added inside a loop passes every functional test and fails this one
    Assert.isTrue(Limits.getQueries() < 30,
        'Expected well under the query limit for 200 records, used ' + Limits.getQueries());
    Assert.isTrue(Limits.getCpuTime() < 4000,
        'CPU headroom is thin: ' + Limits.getCpuTime() + 'ms');
    Test.stopTest();
}
```

`Test.startTest()` resets the counters, so the assertion measures only the code under test.

Worth having on every hot object. It is the only mechanism that catches a limit regression before production.

## A design checklist

```
Structure
  [ ] Every method takes a collection
  [ ] No SOQL or DML in a loop
  [ ] No nested loops over record collections
  [ ] Queries centralized in selectors

Work reduction
  [ ] Change detection against oldMap
  [ ] Early exit when nothing matches
  [ ] Only records that changed are updated
  [ ] Guard against empty collections before DML

Transaction shape
  [ ] Non-essential work moved async
  [ ] Callouts after DML are enqueued
  [ ] Large volumes handled by Batch Apex
  [ ] Async enqueued once per batch, not per record

Environment
  [ ] Total automation on the object audited
  [ ] Roll-up count on hot parents reviewed
  [ ] Describe calls cached in statics
  [ ] Queries selective — query plan checked

Verification
  [ ] Bulk test with 200+ records
  [ ] Limit consumption asserted
  [ ] Consumption is below 50% of any limit
```

## Practical guidance

**Bulkify first.** It resolves most limit problems.

**Do less** before restructuring — change detection and early exit are cheaper than refactoring.

**Split the transaction** when the work genuinely exceeds one budget.

**Move everything off the synchronous path** that the user does not wait for.

**Audit the object's total automation**, not just your code.

**Cache describes in statics.**

**Target below 50 percent**, not below 100.

**Assert on consumption** in bulk tests for hot objects.
