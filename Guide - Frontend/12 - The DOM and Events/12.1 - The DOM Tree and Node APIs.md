# The DOM Tree and Node APIs

The **DOM** (Document Object Model) is the browser's in-memory object representation of a parsed HTML document. It is an API contract, not a data structure defined by JavaScript — the objects live in the browser's C++ implementation and are exposed to JavaScript through host objects.

That distinction matters practically: DOM memory is not part of the JS heap ([[07.1 - How Garbage Collection Works]]), and DOM property access crosses a boundary that is far more expensive than reading a plain JavaScript object.

## Nodes vs elements

Every node has a `nodeType`:

```
1  ELEMENT_NODE          <div>
3  TEXT_NODE             whitespace and text between tags
8  COMMENT_NODE          <!-- ... -->
9  DOCUMENT_NODE         document
11 DOCUMENT_FRAGMENT     DocumentFragment, shadow roots
```

Two parallel traversal APIs exist, and mixing them causes bugs:

| Node-based (includes text and comments) | Element-based |
| --- | --- |
| `childNodes` | `children` |
| `firstChild` | `firstElementChild` |
| `lastChild` | `lastElementChild` |
| `nextSibling` | `nextElementSibling` |
| `parentNode` | `parentElement` |

```html
<div>
  <span>a</span>
</div>
```

`div.childNodes.length` is 3 — whitespace text node, the span, whitespace text node. `div.children.length` is 1. Almost always you want the element-based API.

`parentNode` and `parentElement` differ only at the root: `document.documentElement.parentNode` is `document`, while `parentElement` is `null`.

## Querying

```js
document.querySelector(".card");            // first match, or null
document.querySelectorAll(".card");         // static NodeList
document.getElementById("main");            // fastest, id only
document.getElementsByClassName("card");    // LIVE HTMLCollection
document.getElementsByTagName("div");       // LIVE HTMLCollection

element.closest(".container");              // nearest ancestor (or self) matching
element.matches(".active");                 // boolean test
element.contains(otherNode);                // ancestor test
```

The **live versus static** distinction is the one that causes real bugs:

```js
const live = document.getElementsByClassName("item");   // live
const staticList = document.querySelectorAll(".item");  // static snapshot

document.body.append(newItemWithClass);

live.length;        // increased
staticList.length;  // unchanged
```

Live collections re-query the document on every access, which makes this a classic infinite loop:

```js
const items = document.getElementsByClassName("item");
for (let i = 0; i < items.length; i++) {
  items[i].classList.add("item");   // collection grows as you iterate
}
```

Prefer `querySelectorAll`. Its `NodeList` is static and has `forEach`, though it is not an array — use `[...list]` or `Array.from` for `map` and `filter`.

`closest()` is the workhorse for event delegation ([[12.4 - Event Delegation]]).

## Reading and writing content

```js
el.textContent = "safe";       // text only, no parsing, fast
el.innerText;                  // rendered text — triggers reflow, respects CSS
el.innerHTML = "<b>parsed</b>";// parses HTML — XSS risk with untrusted input
el.outerHTML;                  // includes the element itself
```

**`textContent` versus `innerText`:** `textContent` returns everything including hidden elements and script contents, and does not trigger layout. `innerText` returns what is visually rendered — it respects `display: none`, collapses whitespace like CSS does, and **forces a reflow** to compute this. In a loop, `innerText` is a layout thrashing source ([[13.3 - Layout Thrashing]]).

**`innerHTML` with untrusted data is the primary XSS vector.** Note that `<script>` tags inserted via `innerHTML` do not execute, but `<img src=x onerror=alert(1)>` does — which is why "I stripped script tags" is not a defense ([[15.6 - Frontend Security]]).

```js
el.textContent = userInput;                    // always safe
el.innerHTML = DOMPurify.sanitize(userInput);  // when HTML is required
el.setHTML(userInput);                         // sanitizer API, rolling out
```

## Creating and inserting

```js
const el = document.createElement("div");
el.className = "card";
el.textContent = "Hello";

parent.append(el, "text", anotherEl);   // multiple nodes and strings
parent.prepend(el);
el.before(sibling);
el.after(sibling);
el.replaceWith(newEl);
el.remove();

parent.insertAdjacentHTML("beforeend", "<p>x</p>");
parent.insertAdjacentElement("afterbegin", el);
```

The modern methods (`append`, `prepend`, `before`, `after`, `replaceWith`, `remove`) accept multiple arguments and plain strings, and are strictly better than `appendChild`, `insertBefore` and `removeChild`.

`insertAdjacentHTML` positions: `beforebegin`, `afterbegin`, `beforeend`, `afterend`. It parses HTML without destroying and recreating existing children the way `innerHTML +=` does — `innerHTML +=` re-parses everything, discards event listeners on existing children, and resets form state.

## Attributes vs properties

```js
input.getAttribute("value");   // the value in the HTML source
input.value;                    // the current live value

el.setAttribute("data-id", "5");
el.dataset.id;                  // "5" — camelCased access to data-* attributes

el.hasAttribute("disabled");
el.toggleAttribute("hidden");
```

Attributes are strings from the markup. Properties are the live JavaScript state. For most attributes they stay in sync; for a few they deliberately diverge:

- **`input.value`** — the attribute is the *default*; the property is the current value after user input.
- **`input.checked`** — same relationship.
- **`href`** — the attribute is what you wrote, the property is the resolved absolute URL.
- **`class`** — the attribute; the property is `className`, and `classList` is the useful interface.

```js
el.classList.add("a", "b");
el.classList.remove("a");
el.classList.toggle("open", isOpen);   // second argument forces the state
el.classList.contains("active");
el.classList.replace("old", "new");
```

The two-argument `toggle` is underused and removes most `if/else` class code.

## Fragments

```js
const fragment = document.createDocumentFragment();

for (const item of items) {
  const li = document.createElement("li");
  li.textContent = item.name;
  fragment.append(li);
}

list.append(fragment);   // one DOM insertion
```

A `DocumentFragment` is a lightweight container that is not part of the document, so building inside it causes no layout or paint. Appending it moves its children and leaves the fragment empty.

For a hundred rows this is the difference between a hundred layout invalidations and one ([[12.2 - DOM Manipulation]]).

## Templates

```html
<template id="row">
  <tr><td class="name"></td><td class="value"></td></tr>
</template>
```

```js
const tpl = document.getElementById("row");
const clone = tpl.content.cloneNode(true);
clone.querySelector(".name").textContent = data.name;
tbody.append(clone);
```

`<template>` content is inert — not rendered, images not fetched, scripts not run — until cloned. It is the correct way to define reusable markup in vanilla JS, and it preserves table and list nesting rules that string concatenation breaks.

## Shadow DOM

```js
const shadow = el.attachShadow({ mode: "open" });
shadow.innerHTML = `<style>p { color: red }</style><p>Scoped</p>`;
```

A separate DOM subtree with encapsulated styles. Outside CSS does not reach in (except inherited properties and custom properties), and inside CSS does not leak out. This is the foundation of Web Components, and it is why custom elements from third parties do not break your styling.

The tradeoffs are real: global stylesheets do not apply, `querySelector` from outside cannot see in, and form participation requires explicit opt-in.

## How senior engineers actually use this

**They rarely touch the DOM directly in React applications.** Direct manipulation conflicts with React's model — React may overwrite it on the next render. Refs plus `useLayoutEffect` for measurement, and portals for placement, cover almost every legitimate case ([[17.8 - useRef]]).

**They know it anyway**, because integrating a non-React library, writing a browser extension, debugging a hydration mismatch, or working in a legacy codebase all require it.

**They use `textContent` by default and treat every `innerHTML` as a security decision.**

**They batch with fragments** when building lists imperatively.

**They prefer `dataset` and `closest()`** for the delegation pattern, which is the one piece of DOM API that remains genuinely useful even inside frameworks.

## Common pitfalls

- Iterating a live `HTMLCollection` while modifying it.
- `childNodes` including whitespace text nodes.
- `innerHTML +=` destroying listeners and form state on existing children.
- `innerText` in a loop forcing repeated reflows.
- Confusing `getAttribute("value")` with `.value` on inputs.
- Assuming `querySelectorAll` returns an array.
- Manipulating DOM that React controls, and having it silently reverted.

## Interview angle

DOM questions cluster around the live-versus-static collection distinction, `textContent` versus `innerHTML` versus `innerText` (correctness, security and performance respectively), and attributes versus properties. The `innerText` reflow detail and the `innerHTML +=` listener loss are both good signals of practical experience. Fragments come up naturally in "how would you efficiently render 1,000 rows".
