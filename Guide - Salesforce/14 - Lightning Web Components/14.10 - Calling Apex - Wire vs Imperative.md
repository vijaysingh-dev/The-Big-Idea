# Calling Apex - Wire vs Imperative

## Exposing a method

```java
public with sharing class ClaimController {

    @AuraEnabled(cacheable=true)
    public static List<Warranty_Claim__c> getClaims(Id accountId, String status) {
        return [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c, Claim_Date__c,
                   Asset__r.Name, Asset__r.SerialNumber
            FROM Warranty_Claim__c
            WHERE Account__c = :accountId
              AND (:status = 'All' OR Status__c = :status)
            WITH USER_MODE
            ORDER BY Claim_Date__c DESC
            LIMIT 200
        ];
    }

    @AuraEnabled
    public static Id approveClaim(Id claimId, Decimal approvedAmount) {
        ClaimApprovalService.approve(new Set<Id>{ claimId }, approvedAmount);
        return claimId;
    }
}
```

**`@AuraEnabled`** exposes a static method to Lightning components.

**`cacheable=true`** is required for `@wire` and forbids DML. The result is cached client-side.

**`WITH USER_MODE`** on every query. An `@AuraEnabled` method is effectively a public endpoint — anyone with a session can invoke it directly, regardless of what the component displays. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Wire

```javascript
import { LightningElement, api, wire } from 'lwc';
import getClaims from '@salesforce/apex/ClaimController.getClaims';

export default class ClaimList extends LightningElement {
    @api recordId;
    selectedStatus = 'All';

    @wire(getClaims, { accountId: '$recordId', status: '$selectedStatus' })
    claimResult;

    get claims() {
        return this.claimResult?.data ?? [];
    }

    get error() {
        return this.claimResult?.error;
    }

    get isLoading() {
        return !this.claimResult?.data && !this.claimResult?.error;
    }
}
```

**The `$` prefix makes a parameter reactive.** Changing `selectedStatus` re-executes the wire. Without the `$`, the value is captured once and never refreshes — a silent bug where the component works on load and never updates.

**Wires run automatically**, before `connectedCallback` completes, and cannot be triggered on demand.

**Both `data` and `error` start undefined**, so the loading state must be handled explicitly.

## Imperative

```javascript
import { LightningElement, api } from 'lwc';
import getClaims from '@salesforce/apex/ClaimController.getClaims';
import approveClaim from '@salesforce/apex/ClaimController.approveClaim';

export default class ClaimActions extends LightningElement {
    @api recordId;
    claims = [];
    isLoading = false;
    error;

    async loadClaims() {
        this.isLoading = true;
        this.error = undefined;

        try {
            this.claims = await getClaims({
                accountId: this.recordId,
                status: 'Submitted'
            });
        } catch (e) {
            this.error = this.reduceError(e);
        } finally {
            this.isLoading = false;
        }
    }

    async handleApprove(event) {
        const claimId = event.target.dataset.claimId;
        try {
            await approveClaim({ claimId, approvedAmount: this.approvedAmount });
            await this.loadClaims();
        } catch (e) {
            this.error = this.reduceError(e);
        }
    }
}
```

**Parameters are passed as an object** whose keys must exactly match the Apex parameter names. A mismatch produces an unhelpful runtime error rather than a compile failure.

**`async`/`await` with try/catch** is cleaner than `.then().catch()` and is the modern convention.

## Choosing

| | Wire | Imperative |
| --- | --- | --- |
| Triggered by | Reactive parameters | Code |
| Requires `cacheable=true` | Yes | No |
| Can perform DML | No | Yes |
| Cached | Yes | No |
| Refreshes automatically | Yes | No |
| Order controllable | No | Yes |
| Runs conditionally | Only by leaving a parameter undefined | Freely |

**Use wire for** read-only data tied to reactive inputs, where caching helps and automatic refresh is wanted.

**Use imperative for** anything a user triggers, anything that writes, anything needing sequencing, and anything conditional.

Many components use both: a wire for the list, imperative calls for the actions.

## The caching consequence

`cacheable=true` means the client caches by method and parameters. Two components calling the same method with the same arguments make one server call.

That is a genuine benefit and the source of a common complaint: **the data does not refresh after an update.**

```javascript
async handleApprove() {
    await approveClaim({ claimId: this.claimId });
    // the wire does not know anything changed
}
```

The fix is `refreshApex` on the stored wire result, which requires keeping the whole result rather than just its data:

```javascript
import { refreshApex } from '@salesforce/apex';

@wire(getClaims, { accountId: '$recordId' })
claimResult;   // the whole result, not destructured

async handleApprove() {
    await approveClaim({ claimId: this.claimId });
    await refreshApex(this.claimResult);
}
```

Covered fully in [[14.11 - refreshApex and Cache Invalidation]].

## Deferring a wire

A wire cannot be conditional, but it does not execute while a reactive parameter is undefined.

```javascript
searchTerm;   // undefined until the user types

@wire(searchClaims, { term: '$searchTerm' })
results;

handleSearchChange(event) {
    const value = event.target.value;
    // leaving it undefined below the threshold keeps the wire from firing
    this.searchTerm = value.length >= 3 ? value : undefined;
}
```

This is the standard technique for "do not search until three characters" and for waiting on a dependency.

## Returning structured data

```java
public with sharing class ClaimController {

    public class ClaimContext {
        @AuraEnabled public List<Warranty_Claim__c> claims;
        @AuraEnabled public Decimal totalValue;
        @AuraEnabled public Boolean hasActiveCoverage;
        @AuraEnabled public String coverageLevel;
        public String internalDiagnostics;   // no @AuraEnabled — stays server-side
    }

    @AuraEnabled(cacheable=true)
    public static ClaimContext getContext(Id assetId) {
        ClaimContext context = new ClaimContext();
        context.claims = ClaimSelector.openByAsset(assetId);
        context.totalValue = calculateTotal(context.claims);
        context.hasActiveCoverage = CoverageService.isCovered(assetId);
        return context;
    }
}
```

**Every property needs `@AuraEnabled`** to cross to the client. A property without it is simply absent in JavaScript — the most common cause of "the field is undefined".

That absence is also useful: a field without the annotation stays server-side deliberately.

**One method returning a composed object beats three wires**, because it is one round trip instead of three. In a console, where every millisecond multiplies across an agent's day, this matters. See [[05.8 - Service Console and Agent Productivity]].

## Error handling

Apex errors arrive with an inconsistent shape depending on how they were thrown.

```javascript
reduceError(error) {
    if (Array.isArray(error.body)) {
        return error.body.map((e) => e.message).join(', ');
    }
    if (error.body?.message) {
        return error.body.message;
    }
    if (error.body?.pageErrors?.length) {
        return error.body.pageErrors.map((e) => e.message).join(', ');
    }
    if (error.body?.fieldErrors) {
        return Object.values(error.body.fieldErrors)
            .flat()
            .map((e) => e.message)
            .join(', ');
    }
    return error.message ?? 'An unexpected error occurred';
}
```

DML errors, `AuraHandledException`, and validation failures all produce different structures. A shared reducer in a utility module is worth having rather than repeating this in every component.

**`AuraHandledException` is what to throw** for anything the user should see:

```java
try {
    ClaimApprovalService.approve(claimIds, amount);
} catch (ClaimValidationException e) {
    // AuraHandledException surfaces the message; anything else shows a generic error
    throw new AuraHandledException(e.getMessage());
}
```

An uncaught exception surfaces as "An internal server error has occurred", which tells the user nothing. See [[14.16 - Error Handling and Toasts]].

## Security

An `@AuraEnabled` method is callable by any authenticated user through the API, regardless of what the component renders.

The checklist:

- **Declare a sharing keyword** on the class
- **`WITH USER_MODE`** on queries, **`as user`** on DML
- **`stripInaccessible`** on any sObject arriving from the client
- **Verify ownership** — a caller supplying a record Id must not receive someone else's data
- **Validate every parameter**, including sizes and ranges

```java
@AuraEnabled
public static void saveClaim(Warranty_Claim__c claim) {
    // stripping before DML prevents a crafted request writing fields the UI never showed
    SObjectAccessDecision decision = Security.stripInaccessible(
        AccessType.UPSERTABLE, new List<Warranty_Claim__c>{ claim }
    );
    upsert as user decision.getRecords();
}
```

Without the strip, a component rendering three fields can be used to write to any field on the object.

## Continuations

For a long-running callout where the user is waiting:

```java
@AuraEnabled(continuation=true cacheable=true)
public static Object getInventory(String serialNumber) { }
```

The component calls it like any other method; the parking and resumption are handled by the platform. See [[12.7 - Apex Continuations]].

## Performance

**Compose rather than making several calls.** One method returning a structured object beats three wires.

**Select only the fields the component uses.** A query pulling forty fields including cross-object formulas is expensive per row.

**Cap the row count.** A `LIMIT` on every list query, and pagination beyond it.

**Use `cacheable=true` wherever the method is read-only.** The client cache is free performance.

**Prefer Lightning Data Service to Apex** for single-record reads and writes — no Apex to write, no security code to get wrong, and a shared cache. See [[14.12 - Lightning Data Service and Record Forms]].

That last point is worth emphasizing: **the best Apex controller is often no Apex controller.** LDS and the GraphQL wire adapter cover a large share of what components actually need.

## Practical guidance

**`cacheable=true` for reads**, plain `@AuraEnabled` for writes.

**Use `$` on reactive wire parameters.**

**Keep the whole wire result** so `refreshApex` works.

**Leave a parameter undefined** to defer a wire.

**Annotate every wrapper property with `@AuraEnabled`.**

**Throw `AuraHandledException`** for user-facing errors.

**Share one error reducer** across components.

**Treat every `@AuraEnabled` method as a public endpoint**, with sharing, `USER_MODE`, and ownership checks.

**Compose responses** to reduce round trips.
