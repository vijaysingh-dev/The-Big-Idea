# Change Sets

## What they are

The point-and-click deployment mechanism, built into Setup. Select components in a sandbox, upload to production, validate, deploy.

**No tooling, no Git, no command line.** That is their entire appeal, and it is a real one — an administrator can deploy without a developer.

## The mechanism

```
Deployment Connection
    Sandbox → Production must be authorized to receive
    Production → Sandbox for inbound the other way

Outbound Change Set (in the source org)
    Add components
    Add dependent components (via View/Add Dependencies)
    Upload to the target

Inbound Change Set (in the target org)
    Validate
    Deploy
```

**Deployment connections must be authorized in the receiving org**, which is a one-time setup people forget when a new sandbox is created.

**A change set moves in one direction and is not editable after upload.** A missing component means a new change set.

## Cloning

The one genuinely useful feature.

```
Inbound Change Set → Clone
```

Creates an outbound set in the current org with the same components — which is how a change set moves through a chain of environments without being rebuilt at each step.

```
Dev sandbox → UAT (deploy) → clone in UAT → Production
```

Without cloning, each hop means re-selecting every component by hand.

## Where they fail

Being specific, because "change sets are bad" is not useful guidance.

**Dependencies are not automatic.** "Add Dependent Components" finds some and misses others — most reliably it misses profile permissions, field-level security, and layout assignments. The deployment fails on a missing component, you add it, upload a new set, and repeat. Four or five rounds on a substantial release is normal.

**No history.** Six months later, "what was in the March release" has no answer. The change set list shows names and dates, not contents in any usable form.

**No branching or merging.** Two developers working on the same object cannot merge their work. One overwrites the other, and nothing warns them.

**No code review.** Nothing sits between a developer and production except the person clicking Deploy.

**No automation.** Every deployment is manual, which means every deployment is an opportunity for a mistake at 11pm.

**Deletions are not supported.** A change set cannot remove a component. Deletion is manual in the target org, which is why deleted metadata accumulates.

**Slow.** Selecting 200 components through a paginated picker takes a long time and is error-prone.

**Not all metadata is available.** Some types cannot be added to a change set at all, requiring the Metadata API anyway.

## The profile trap

The same trap as everywhere, in a form specific to change sets.

**A profile in a change set carries only the permissions for components also in the set.**

```
Change set contains:  Warranty_Claim__c, Claim_Amount__c, Profile: Support Agent
Deployed:             permissions for that object and field only
Not deployed:         every other permission on that profile
```

That is usually the behaviour you want — a change set does not wipe a profile. It also means **a profile in a change set does not deploy the whole profile**, and people expect it to.

The practical guidance is the same as for source deployments: **use permission sets.** They deploy completely, they are assignable, and they avoid the whole class of confusion. See [[03.4 - Permission Sets and Permission Set Groups]].

## Making them work

For teams that must use them, the practices that reduce pain.

**Build the change set incrementally, throughout development.** Adding components as you create them beats reconstructing the list at the end.

**Keep a manual manifest.** A shared document listing every component in the release, maintained as work proceeds. It is a poor substitute for Git and far better than nothing.

**Validate early and often** against the target. A validation catches missing dependencies without deploying.

**Deploy to a full-copy sandbox first**, with production-shaped data, to catch what a developer sandbox does not.

**Use "Add Dependent Components", then check manually** — particularly for field-level security, layout assignments, and record type visibility.

**Document manual steps separately.** Custom Setting records, Named Credential secrets, deliverability settings, list view sharing, and anything else that does not deploy. See [[21.1 - Metadata, Source of Truth and Deployment Concepts]].

**Clone through the chain** rather than rebuilding at each hop.

## The common failures

**"Missing component" errors, repeatedly.** A dependency chain not fully discovered. Each round adds one and reveals the next.

**Coverage failures on unrelated classes.** `RunLocalTests` runs everything, so a test broken by someone else's work blocks your release.

**A deployment that succeeds and breaks something.** A component was overwritten by an older version from a stale sandbox — the failure mode with no warning at all.

**A test failing only in production.** Data-dependent tests, or tests relying on org configuration that differs.

**"Cannot modify a scheduled Apex class."** Abort the job, deploy, reschedule.

## Migrating away

The realistic path from change sets to source-driven deployment, because a switch is not available.

**1. Retrieve the org into a repository.**

```bash
sf project retrieve start --manifest manifest/package.xml --target-org production
```

Building the manifest for a mature org takes a while, and `sf project generate manifest --from-org` gives a starting point.

**2. Commit it, unmodified.** This is the baseline, and it will be large and untidy. That is fine.

**3. Keep deploying with change sets** while the repository catches up. Both mechanisms coexist.

**4. Retrieve after each change-set deployment** so the repository stays current. Tedious, and it is the bridge.

**5. Move one team or one area to source deployment.** A new feature area is easier than an existing one.

**6. Add CI validation** before switching the deployment mechanism — a pipeline that validates on every pull request, while change sets still deploy.

**7. Switch deployment**, once validation has been running cleanly for a few releases.

**8. Retire change sets.**

The order matters: **validation before deployment**. A pipeline that validates builds confidence without risk, and switching the deployment step is then a small change rather than a leap.

## When change sets are defensible

Not never, and the honest cases:

**An org with no developers.** An admin-only org where the alternative is nothing.

**A small, infrequent set of changes.** Two fields and a validation rule, quarterly.

**A team with no capacity to adopt tooling.** Introducing Git, the CLI, and CI to a team that cannot support it produces a broken pipeline and a worse outcome than change sets.

**As a transitional mechanism** during migration.

**When they are not defensible:** any org with more than one developer, any org deploying weekly, and any org where "what changed" needs an answer.

## The honest comparison

| | Change Sets | Source Deployment |
| --- | --- | --- |
| Tooling required | None | CLI, Git |
| History | None | Full |
| Branching and merging | Impossible | Standard |
| Code review | None | Pull requests |
| Automation | None | CI/CD |
| Deletions | Manual | Destructive changes |
| Dependency handling | Partial, manual | Manifest-driven |
| Speed for a large release | Very slow | Fast |
| Learning curve | Minimal | Real |

**The learning curve is the only column where change sets win**, and it is a genuine consideration for a team without developers.

## Practical guidance

**Build the set incrementally**, not at the end.

**Keep a manual manifest** of what is in the release.

**Validate against the target early.**

**Use permission sets, not profiles.**

**Document every manual post-deployment step.**

**Clone through the environment chain** rather than rebuilding.

**Start retrieving into Git now**, even while still deploying with change sets.

**Add CI validation before switching deployment**, not after.
