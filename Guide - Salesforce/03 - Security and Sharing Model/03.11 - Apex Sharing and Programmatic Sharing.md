# Apex Sharing and Programmatic Sharing

## When declarative sharing runs out

Criteria-based sharing rules handle "share records where a field equals a value". They cannot handle:

- Access depending on a **related record** — share a claim with the users on its machine's service contract
- Access depending on a **calculation** — share deals above a threshold that varies by region
- Access depending on **multiple related objects** — share a claim with everyone assigned to any active contract covering that machine
- Access to a **specific individual** determined at runtime
- More than 50 criteria-based rules on an object

For these, you write share records yourself. This is **Apex managed sharing**.

## The share object

Every object with restrictive OWD has a companion share object. Custom objects use `ObjectName__Share`; standard objects use `AccountShare`, `OpportunityShare`, and so on.

Its fields:

- **ParentId** — the record being shared
- **UserOrGroupId** — who gets access; a user, public group, role group, or queue
- **AccessLevel** — `Read` or `Edit`. Custom objects also technically allow `All`, which you cannot set
- **RowCause** — why the share exists

For custom objects the field is `ParentId`; for standard objects it is named after the object, such as `AccountId` or `OpportunityId`. This inconsistency catches people writing generic sharing code.

## Sharing reasons

`RowCause` is the mechanism that makes Apex sharing maintainable. Custom sharing reasons are metadata you define on the object — for example `Contract_Coverage__c` — and they matter for three reasons:

**They are not deleted on owner change.** Shares with `RowCause = 'Manual'` disappear when ownership changes. Shares with a custom reason survive.

**They identify your shares.** When recalculating, you delete only shares with your reason, leaving sharing rules, teams, and implicit shares untouched.

**They are documented in the UI.** Users viewing the sharing detail see your reason's label rather than "Manual", which makes the access explicable.

A custom sharing reason is defined in the object's metadata:

```xml
<sharingReasons>
    <fullName>Contract_Coverage__c</fullName>
    <label>Contract Coverage</label>
</sharingReasons>
```

Custom sharing reasons are only available on **custom objects**. Standard objects must use `Manual`, which is a real limitation — programmatic sharing on Opportunity or Case cannot be distinguished from a user's manual share.

## A working implementation

Requirement: a warranty claim should be visible to every user assigned to an active service contract covering that claim's machine.

No criteria-based rule can express this, because the condition lives two objects away.

```java
public with sharing class ClaimSharingService {

    private static final String SHARE_REASON = Schema.Warranty_Claim__Share.RowCause.Contract_Coverage__c;

    public static void recalculateShares(Set<Id> claimIds) {
        if (claimIds.isEmpty()) {
            return;
        }

        Map<Id, Id> machineByClaim = new Map<Id, Id>();
        for (Warranty_Claim__c claim : [
            SELECT Id, Machine__c FROM Warranty_Claim__c
            WHERE Id IN :claimIds AND Machine__c != null
        ]) {
            machineByClaim.put(claim.Id, claim.Machine__c);
        }

        Map<Id, Set<Id>> usersByMachine = getCoverageUsers(new Set<Id>(machineByClaim.values()));

        List<Warranty_Claim__Share> newShares = new List<Warranty_Claim__Share>();
        for (Id claimId : machineByClaim.keySet()) {
            Set<Id> users = usersByMachine.get(machineByClaim.get(claimId));
            if (users == null) {
                continue;
            }
            for (Id userId : users) {
                newShares.add(new Warranty_Claim__Share(
                    ParentId = claimId,
                    UserOrGroupId = userId,
                    AccessLevel = 'Edit',
                    RowCause = SHARE_REASON
                ));
            }
        }

        // remove only shares this service created, leaving rules, teams and manual shares intact
        delete [
            SELECT Id FROM Warranty_Claim__Share
            WHERE ParentId IN :claimIds AND RowCause = :SHARE_REASON
        ];

        if (!newShares.isEmpty()) {
            Database.insert(newShares, false);
        }
    }

    private static Map<Id, Set<Id>> getCoverageUsers(Set<Id> machineIds) {
        Map<Id, Set<Id>> result = new Map<Id, Set<Id>>();
        for (Machine_Coverage__c coverage : [
            SELECT Machine__c, Service_Contract__r.Assigned_Engineer__c,
                   Service_Contract__r.Account_Manager__c
            FROM Machine_Coverage__c
            WHERE Machine__c IN :machineIds
              AND Service_Contract__r.Status__c = 'Active'
        ]) {
            if (!result.containsKey(coverage.Machine__c)) {
                result.put(coverage.Machine__c, new Set<Id>());
            }
            Set<Id> users = result.get(coverage.Machine__c);
            if (coverage.Service_Contract__r.Assigned_Engineer__c != null) {
                users.add(coverage.Service_Contract__r.Assigned_Engineer__c);
            }
            if (coverage.Service_Contract__r.Account_Manager__c != null) {
                users.add(coverage.Service_Contract__r.Account_Manager__c);
            }
        }
        return result;
    }
}
```

Four details make this correct rather than merely working:

**`Database.insert(shares, false)` uses partial success.** Duplicate shares — where the user already has access through another mechanism — fail individually rather than aborting the batch. Trying to prevent duplicates by querying first is both slower and unreliable.

**The delete is scoped to the custom reason.** Deleting all shares on the record would destroy sharing rule shares, team shares, and implicit shares, and they would have to be recalculated by the platform.

**The class is bulkified.** Sharing recalculation typically runs from a trigger or batch job with hundreds of records.

**It reads coverage through a single query.** Walking from claim to machine to coverage to contract per record would be four queries per claim.

## Where to call it from

Shares must be recalculated whenever anything that affects them changes. For this example that means:

- Claim insert, and update when the machine changes
- Coverage record insert, update, delete, undelete
- Service contract status change or engineer reassignment

That last one is the expensive case. Changing the engineer on a contract covering 500 machines means recalculating shares on every claim for all of them. This must be asynchronous:

```java
public with sharing class ClaimShareRecalculationQueueable implements Queueable {

    private final Set<Id> machineIds;

    public ClaimShareRecalculationQueueable(Set<Id> machineIds) {
        this.machineIds = machineIds;
    }

    public void execute(QueueableContext context) {
        Set<Id> claimIds = new Map<Id, Warranty_Claim__c>([
            SELECT Id FROM Warranty_Claim__c WHERE Machine__c IN :machineIds LIMIT 10000
        ]).keySet();

        ClaimSharingService.recalculateShares(claimIds);
    }
}
```

For genuinely large volumes, Batch Apex with a scope tuned down — sharing DML is heavy — is the right tool. See [[12.4 - Batch Apex]].

## Sharing to groups rather than users

Sharing to individual users produces one share row per user per record. Ten users on ten thousand claims is a hundred thousand rows, and every recalculation rewrites them.

Sharing to a **public group** produces one row per record. If the set of people is stable enough to be a group, this is dramatically cheaper, and changing group membership does not require recalculating any shares at all.

This is the single most effective optimization available in Apex sharing, and it is worth restructuring a design to allow it.

```java
newShares.add(new Warranty_Claim__Share(
    ParentId = claimId,
    UserOrGroupId = serviceTeamGroupId,
    AccessLevel = 'Edit',
    RowCause = SHARE_REASON
));
```

## Sharing keywords, which are a different thing

`with sharing`, `without sharing`, and `inherited sharing` control whether *your code* respects the sharing model. They do not create shares.

```java
public with sharing class ClaimService { }        // queries filtered by user's access
public without sharing class ClaimAdminService { } // queries return everything
public inherited sharing class ClaimUtils { }      // takes on the caller's mode
```

Note the interaction: the sharing service above is declared `with sharing`, but the share records it creates are the mechanism that grants access to others. Writing shares does not require `without sharing` — inserting a share row is DML on the share object, subject to the object permissions on it, not to the sharing of the parent.

`inherited sharing` is the correct choice for reusable utility classes, because it takes the mode of whatever called it rather than silently opening or restricting access. A class with no keyword at all defaults to `without sharing` in some entry points, which is why omitting the keyword is a security review finding.

## Testing it

Sharing behaviour must be tested as a real user, because administrators bypass it entirely.

```java
@IsTest
static void coveredEngineerCanSeeClaim() {
    User engineer = TestDataFactory.createUser('Service_Engineer');
    Machine__c machine = TestDataFactory.createMachineWithCoverage(engineer.Id);
    Warranty_Claim__c claim = TestDataFactory.createClaim(machine.Id);

    Test.startTest();
    ClaimSharingService.recalculateShares(new Set<Id>{ claim.Id });
    Test.stopTest();

    System.runAs(engineer) {
        List<Warranty_Claim__c> visible = [
            SELECT Id FROM Warranty_Claim__c WHERE Id = :claim.Id
        ];
        Assert.areEqual(1, visible.size(), 'Engineer on the covering contract should see the claim');
    }
}
```

`System.runAs()` is the only way to test record access. A test that inserts and queries as the running test user proves nothing. See [[19.8 - Testing Security and Sharing]].

## Guidance

**Exhaust declarative options first.** Criteria-based rules, public groups, and teams cover most requirements and cost nothing to maintain.

**Always use a custom sharing reason on custom objects.** Without it, your shares are indistinguishable from manual ones and will be destroyed on ownership change.

**Share to groups where possible.** Orders of magnitude fewer rows.

**Recalculate asynchronously.** Share DML is slow, and any non-trivial recalculation will exceed synchronous limits.

**Have a full recalculation job.** Shares drift out of sync — a failed batch, a data load that bypassed the trigger, a deployment gap. A scheduled job that rebuilds shares for the object is the safety net, and every org that relies on Apex sharing eventually needs one.
