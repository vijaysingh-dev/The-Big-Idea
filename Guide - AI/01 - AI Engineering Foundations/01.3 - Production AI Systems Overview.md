# Production AI Systems Overview

## What Real Production AI Systems Look Like

Most tutorials show: `user_query → LLM → answer`. Production systems look nothing like this.

A real system has 5–8 independently deployable services, async background jobs, multiple storage systems, and an evaluation layer that runs continuously.

## Key Subsystems and Their Engineering Challenges

### 1. Connectors / Ingestion

- Poll or webhook from source systems (Google Drive, Confluence, Slack, Jira)
- Handle pagination, rate limits, auth token refresh
- Extract text from diverse formats (PDF, DOCX, HTML, code)
- Detect changes for incremental indexing
- **Hard problem**: knowing what changed without re-processing everything

### 2. Chunking + Embedding

- Split documents into retrieval-sized pieces
- Embed each chunk via model API (or self-hosted)
- Store vectors + metadata in vector DB
- **Hard problem**: chunk size affects retrieval quality dramatically

### 3. Query Pipeline

- User query arrives → possibly rewritten/expanded
- Dual retrieval: dense (semantic) + sparse (keyword) → merged
- Reranker re-scores top-K results
- Permission filter removes docs the user can't see
- **Hard problem**: getting all of this under 300ms

### 4. Context Assembly + LLM Call

- Select chunks that fit in context window
- Construct system prompt + injected context
- Call LLM, handle streaming, retry on failure
- **Hard problem**: token budget management across dynamic context

### 5. Evaluation

- Does the answer match the reference? (if available)
- Is the answer grounded in retrieved context?
- Did retrieval return the right documents?
- **Hard problem**: ground truth is expensive; LLM-as-judge introduces its own bias

## Infrastructure Components

|Component|Purpose|Common Tech|
|---|---|---|
|Vector DB|Dense retrieval, ANN search|Vespa, Qdrant, Weaviate|
|Keyword index|Sparse retrieval (BM25)|Elasticsearch, Vespa|
|Document store|Raw document storage|PostgreSQL, S3|
|Queue|Async ingestion jobs|Celery + Redis, Kafka|
|Cache|Embedding cache, prompt cache|Redis|
|Model API|LLM inference|OpenAI, Anthropic, self-hosted|
|Embedding API|Chunk embedding|OpenAI, Cohere, self-hosted|
|Observability|Logs, traces, metrics|LangSmith, Langfuse, Datadog|

## Onyx as a Reference Architecture

Onyx (formerly Danswer) is an open-source enterprise search + QA system. It implements nearly all of the above. Key files to read:

- `backend/danswer/connectors/` — connector implementations per source
- `backend/danswer/indexing/` — chunking + embedding pipeline
- `backend/danswer/search/` — retrieval, reranking, permission filtering
- `backend/danswer/llm/` — LLM abstraction layer
- `backend/danswer/chat/` — context assembly, answer generation

## What "Production-Grade" Actually Means

|Concern|Production requirement|
|---|---|
|Latency|P95 < 2s for query, < 5s for full answer|
|Reliability|LLM API failures handled with fallback|
|Cost|Token usage tracked, alerts on spikes|
|Security|No cross-tenant data leakage, ACL enforced|
|Freshness|Index updated within minutes/hours of source changes|
|Observability|Every query logged with retrieval results + LLM response|
|Evaluation|Quality metrics measured weekly, regressions caught before deploy|
