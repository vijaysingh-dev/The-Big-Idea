# Legacy Workflow and Process Builder Migration

## Why this note exists

Workflow Rules and Process Builder are retired. Neither can be created new, and both are on a path to being switched off entirely.

Any org more than a few years old carries them, often dozens, often undocumented, and often doing things nobody currently understands. Migrating them is real work that lands on developers, and it is a common task on a first project in an established org.

## What each was

**Workflow Rules** (2006) — criteria plus actions: field updates, email alerts, tasks, outbound messages, and time-based actions. Simple, fast, and limited to those four action types.

**Process Builder** (2015) — a visual builder with multiple criteria nodes, more action types including record creation and Apex invocation, and the ability to update related records.

Both are superseded by record-triggered flows, which do everything both did and more.

## The inventory

The first task is finding what exists.

```sql
SELECT Id, Name, TableEnumOrId
FROM WorkflowRule
```

Workflow rules are queryable through the Tooling API rather than standard SOQL. From the CLI:

```bash
sf data query --use-tooling-api \
  --query "SELECT Id, Name, TableEnumOrId FROM WorkflowRule" \
  --target-org production

sf data query --use-tooling-api \
  --query "SELECT Id, DeveloperName, TableEnumOrId FROM FlowDefinition" \
  --target-org production
```

Process Builder processes appear as flows with `ProcessType = 'Workflow'`:

```sql
SELECT ApiName, Label, ProcessType, TriggerType, Status, LastModifiedDate
FROM FlowDefinitionView
WHERE ProcessType IN ('Workflow', 'InvocableProcess')
```

Salesforce also provides a **Migrate to Flow** tool in Setup, which converts many workflow rules and processes automatically. It handles the straightforward cases well and leaves the complex ones, which is a reasonable division of labour.

## What the tool cannot convert

The cases needing manual work:

- Outbound messages, which have no flow equivalent and must become a platform event, a callout, or middleware
- Time-based workflow actions with complex re-evaluation rules
- Processes invoking Apex with particular signatures
- Cross-object field updates on relationships flow handles differently
- Processes whose criteria depend on formula fields that no longer exist

## Do not port literally

The temptation is to convert each rule one-for-one. That reproduces the original problem: fourteen separate automations on one object, running in an order nobody controls.

The migration is an opportunity to consolidate, and taking it is the difference between a migration that improves the org and one that just changes the technology.

**Before:**
```
Opportunity
  Workflow Rule 1: set stage-based probability
  Workflow Rule 2: email on large deals
  Workflow Rule 3: task on stage change
  Process Builder A: update account roll-up
  Process Builder B: create renewal on close
  Process Builder C: stamp region from account
```

**After:**
```
Opportunity_BeforeSave
  Decision: set probability defaults
  Decision: stamp region from account

Opportunity_AfterSave
  Decision: what changed?
    Stage changed          → Subflow: notify and create task
    Closed Won             → Subflow: create renewal
    Amount changed         → Invocable Apex: recalculate account rollup
```

Two flows instead of six automations, with explicit internal ordering and the same behaviour.

The two field updates moved to **before-save**, which removes two extra passes through the save pipeline. This alone is usually the largest performance gain in a migration, because Process Builder had no before-save equivalent and every field update it performed re-saved the record. See [[07.4 - Before-Save vs After-Save Flows]].

## Behaviour differences to watch

Migration is not always semantically identical, and these are where behaviour changes silently.

**Re-evaluation.** Workflow rules had "Evaluate the rule when a record is created, and every time it's edited" versus "created, and any time it's edited to subsequently meet criteria". The flow equivalent is the **"only when a record is updated to meet the condition requirements"** checkbox. Picking the wrong one changes how often the automation fires — often from once to every save.

**Field update recursion.** A workflow field update could re-trigger workflow rules, up to a limited depth. Flow behaves differently. A migrated automation relying on that cascade may stop working, or may now recurse further than intended.

**Order.** Workflow rules ran in an unspecified order among themselves, but always after Process Builder. Flows have their own ordering. Anything depending on the old sequence needs checking explicitly.

**Time-based actions.** Workflow time triggers become **scheduled paths** on a record-triggered flow. The re-evaluation semantics differ: a scheduled path re-checks entry conditions when it fires, which workflow time triggers did not always do the same way.

**Email alerts.** Reusable in flow as actions, and worth keeping rather than rebuilding as flow email elements, since the templates and recipient configuration transfer directly.

**Outbound messages.** No direct equivalent. The replacement is a platform event with a subscriber, or an invocable Apex callout. This is the largest single piece of manual work in most migrations. See [[12.8 - Platform Events]].

## A migration sequence that works

**1. Inventory everything**, per object, with what it does and when it fires.

**2. Identify what is dead.** A meaningful fraction of legacy automation references fields nobody uses, sends email to people who left, or fires on statuses that no longer exist. Deleting these is the cheapest part of the migration and the part most often skipped.

**3. Group by object and by timing.** This is where consolidation opportunities appear.

**4. Design the target flows** before building. One before-save, one after-save per object, with subflows for distinct concerns.

**5. Build in a sandbox, with the legacy automation still active but the new flows deactivated.**

**6. Test both in parallel.** Deactivate legacy for a test user or in a sandbox, activate the new flow, and compare outcomes on the same input records. Where the org has good data, this can be automated by running a set of representative saves and diffing the resulting field values.

**7. Migrate one object at a time.** Deactivate the legacy automation and activate the flow together, in one deployment.

**8. Monitor.** Error volume, and the specific business outcomes the automation was responsible for.

Step 6 is the one that gets cut under time pressure and is the one that catches the re-evaluation and ordering differences above.

## Testing a migration

Flow has no unit test framework, which is the central difficulty.

Three practical approaches:

**Apex tests that exercise the flow indirectly.** A test that inserts and updates records, then asserts the resulting field values, tests the flow even though it is not a flow test. This is the most reliable option and works identically before and after the migration — the same test should pass against both implementations.

```java
@IsTest
static void stageChangeCreatesFollowUpTask() {
    Opportunity opp = TestDataFactory.createOpportunity('Qualification');

    Test.startTest();
    opp.StageName = 'Commercial Proposal';
    update opp;
    Test.stopTest();

    List<Task> tasks = [
        SELECT Id, Subject FROM Task WHERE WhatId = :opp.Id
    ];
    Assert.areEqual(1, tasks.size(), 'Stage change should create one follow-up task');
}
```

Writing these **before** the migration, against the legacy automation, is the highest-value thing you can do. They become the regression suite.

**Flow Tests**, which Salesforce provides for record-triggered flows. Useful and limited — single record, no bulk. See [[19.9 - Flow Testing]].

**Manual parallel comparison** in a sandbox with realistic data.

## Deactivating safely

Deactivate rather than delete initially. A deactivated workflow rule can be reactivated in seconds if something was missed; a deleted one cannot.

Delete only after a full business cycle has passed — a month for daily processes, a quarter for anything tied to quarter-end.

Keep a record of what was deactivated and when, so that "did we turn something off" has an answer during an incident.

## Practical guidance

**Use the Migrate to Flow tool for the simple cases** and hand-build the rest.

**Consolidate rather than porting one-for-one.** The migration is the only chance you get.

**Move field updates to before-save.** Usually the biggest performance win available.

**Write Apex regression tests against the legacy behaviour first.**

**Check the re-evaluation setting on every update trigger.** It is the most common behavioural difference.

**Plan the outbound message replacement separately.** It is the largest manual piece.

**Deactivate, do not delete, until a full cycle has passed.**
