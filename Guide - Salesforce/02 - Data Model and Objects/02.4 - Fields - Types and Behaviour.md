# Fields - Types and Behaviour

## Why field type is a design decision

A field type is not just storage. It decides what can be filtered on, what can be indexed, what can be rolled up, whether the field can be an external ID, and whether it can be changed later without a data migration.

Changing a field's type after records exist is sometimes allowed, sometimes lossy, and sometimes impossible. Choosing correctly the first time is worth the ten minutes.

## The types, grouped by what they are for

**Text.** `Text` (up to 255 characters, indexable, filterable), `Text Area` (255, no line breaks in practice), `Long Text Area` (up to 131,072 characters), `Rich Text Area` (formatted HTML).

The critical distinction: **Long Text and Rich Text cannot be filtered on, sorted, indexed, used in roll-ups, or made external IDs.** They also count heavily toward the record's heap size when queried in bulk. Using a Long Text Area for something you will later want to search is a decision you cannot undo without a migration.

**Number, Currency, Percent.** Numeric with precision and scale. Currency behaves specially in multi-currency orgs, storing both the record's currency and a converted value. Percent stores 0.15 for 15 percent in the API while displaying as 15, which causes a predictable class of integration bug.

**Date, Date/Time, Time.** `Date` has no time component and no time zone. `Date/Time` is stored in UTC and displayed in the user's time zone. This distinction causes an enormous amount of confusion; see the time zone section below.

**Checkbox.** Boolean. Never null — it is always true or false, which means "unknown" cannot be represented. If a business process has three states, a checkbox is the wrong field.

**Picklist and Multi-Select Picklist.** A constrained set of values. Multi-select stores values separated by semicolons in a single field, which makes reporting and filtering genuinely awkward. Most experienced engineers avoid multi-select picklists where a related object or several checkboxes would do.

**Email, Phone, URL.** Text with validation and click-to-action behaviour in the UI.

**Lookup, Master-Detail, Hierarchical.** Relationships. See [[02.7 - Relationships - Lookup vs Master-Detail]].

**Formula.** Calculated at read time, never stored. See [[02.5 - Formula Fields]].

**Roll-Up Summary.** Aggregated from children, stored. See [[02.6 - Roll-Up Summary Fields]].

**Auto Number.** Sequential, generated by the platform, read-only.

**Geolocation.** A compound field storing latitude and longitude, enabling distance calculations. Counts as three fields against the field limit, and cannot be used in some contexts including certain formula operations.

**Encrypted Text.** Classic encrypted fields, masked in the UI, with heavy restrictions — not filterable, not usable in most automation. Distinct from Shield Platform Encryption, which is the modern approach. See [[22.2 - Platform Encryption]].

**Time.** Time of day with no date.

## Field attributes that matter more than the type

**Required.** Enforced at the database level, meaning it applies to the API, Data Loader, and Apex, not just the user interface. A field required at field level cannot be bypassed by an integration, which is either exactly what you want or an integration outage.

Required on the page layout is different — that is a UI-only rule and does not apply to the API. Knowing which of the two a requirement means is important.

**Unique.** Enforces uniqueness across the object and creates an index. Can be case-sensitive or case-insensitive.

**External ID.** Marks the field as an identifier from an outside system. Creates an index, allows upsert to match on it, and is the foundation of every reliable integration. Up to 25 per object, and only Text, Number, Email, and Auto Number can be external IDs.

```java
// Upsert matching on the external identifier, so reruns do not create duplicates
List<Machine__c> machines = new List<Machine__c>();
for (ErpMachineDto dto : payload) {
    machines.add(new Machine__c(
        ERP_Machine_Id__c = dto.machineId,
        Name = dto.model,
        Install_Date__c = dto.installedOn
    ));
}
upsert machines ERP_Machine_Id__c;
```

That single line is why external IDs matter: the integration can run twice, or replay a failed batch, without creating duplicates. See [[13.17 - Error Handling, Retries and Idempotency]].

**Default value.** Can be a formula. Applies on record creation through the UI and, for some field types, through the API.

**Help text.** Shown on hover. Underused, and the cheapest documentation available.

**Track history.** Records old and new values in the object's history table, limited to twenty fields per object.

## Time zones, properly

This causes more production bugs than any other field behaviour, so it is worth being precise.

A **Date/Time** field is stored in UTC. When a user in Mumbai sees "5 August 2026, 09:00", the database holds "2026-08-05T03:30:00Z". Apex handles this for you if you use the right methods, and gets it wrong if you do not.

```java
Datetime dt = Datetime.now();

dt.format();                        // user's time zone, user's locale
dt.formatGMT('yyyy-MM-dd HH:mm:ss'); // explicit UTC, correct for integrations
dt.date();                          // date in GMT, which may be yesterday for the user
dt.dateGMT();                       // explicitly the GMT date
```

The trap: `Datetime.date()` returns the date in GMT, not the user's time zone. For a user in Mumbai at 02:00 local, that returns the previous day. Reports built on it disagree with what users see, and nobody can explain why.

A **Date** field has no time zone at all. It is the same date for everyone. This makes Date the right choice for things like close dates, birthdays, and contract dates — anything where "the fifth of August" means the same thing in every office.

Choosing Date/Time when Date would do is a common and avoidable source of off-by-one-day reporting disputes.

## Picklists in Apex

Picklist values are metadata, so code that hardcodes them breaks when the business adds a value.

```java
// Reading the current values rather than assuming them
Schema.DescribeFieldResult statusField = Warranty_Claim__c.Status__c.getDescribe();
for (Schema.PicklistEntry entry : statusField.getPicklistValues()) {
    if (entry.isActive()) {
        System.debug(entry.getValue() + ' / ' + entry.getLabel());
    }
}
```

Two further points. **Global Value Sets** let several picklist fields share one list of values, which is how you avoid the same country list existing in eleven slightly different versions. And **restricted picklists** reject values not in the list when set through the API — unrestricted ones silently accept anything, which is how orgs end up with `Closed`, `closed`, and `Closed ` as three distinct statuses.

## Changing field types later

Some conversions are safe, some lose data, some are blocked entirely:

- Text to Picklist: allowed, and existing values that do not match become inactive picklist entries
- Text to Number: allowed, and non-numeric values are lost
- Picklist to Multi-Select: allowed, one way only
- Multi-Select to Picklist: blocked
- Anything to or from Formula: blocked, requires a new field
- Text to Long Text Area: allowed; the reverse truncates
- Lookup to Master-Detail: allowed only if every child record has a parent populated

The reliable pattern when a conversion is not possible: create a new field, migrate the data with a script, update all references, then delete the old field. Plan for it to take a release cycle rather than an afternoon.

## What experienced engineers watch for

**They resist adding fields.** Field count is a hard limit, layouts become unusable, and query heap grows. The question "can an existing field, a formula, or a report grouping answer this" comes first.

**They mark external IDs immediately.** Retrofitting one onto a populated object requires backfilling a million rows.

**They never use a checkbox for a three-state concept.** Yes, no, and not yet answered is a picklist.

**They use Date rather than Date/Time unless the time genuinely matters.** It removes a whole category of bugs.

**They avoid multi-select picklists.** Reporting on them is painful, filtering is limited, and a junction object or a set of checkboxes is nearly always better.
