# Reading Session: Online Boutique

#backend #reading #microservices

> **In one line:** Eleven services in five languages that you can deploy in one command — and the most valuable thing in it is a checkout flow with a failure mode that a Google reference architecture shipped without compensation.

---

## Why This Codebase

💡 **It is the only complete, deployable, readable microservice system in open source.** Everything else is either a toy or too large to trace.

## The Path

### 1. The whole system, in one file — `protos/demo.proto`

```protobuf
service CartService {
  rpc AddItem(AddItemRequest) returns (Empty) {}
  rpc GetCart(GetCartRequest) returns (Cart) {}
  rpc EmptyCart(EmptyCartRequest) returns (Empty) {}
}

service CheckoutService {
  rpc PlaceOrder(PlaceOrderRequest) returns (PlaceOrderResponse) {}
}

service PaymentService {
  rpc Charge(ChargeRequest) returns (ChargeResponse) {}
}
...
```

💡 **Read this first, in full.** In fifteen minutes you have the entire system's architecture — every service, every operation, every message shape.

⚠️ **This is the strongest argument for a schema-first contract.** No amount of reading eleven codebases would give you what one proto file does ([[05.11 - REST vs GraphQL vs gRPC]]).

**Apply the boundary tests from [[10.2 - Finding Service Boundaries]] to each service:**

| Service | Verdict |
|---|---|
| `productcatalogservice` | Reasonable — owns product data |
| `cartservice` | Reasonable — owns cart state |
| `checkoutservice` | An orchestrator, not a data owner |
| **`currencyservice`** | ⚠️ **A nanoservice.** Currency conversion does not need a service |
| **`emailservice`** | ⚠️ Arguably. Should be asynchronous |
| `recommendationservice` | Reasonable — different scaling, ML workload |
| `adservice` | Reasonable |

💡 **`currencyservice` exists to demonstrate polyglot microservices, not because the domain required it.** Recognising a demo-driven boundary from a domain-driven one is exactly the judgement [[10.11 - The Real Cost of Microservices]] is about.

### 2. The BFF — `src/frontend/handlers.go`

```go
func (fe *frontendServer) homeHandler(w http.ResponseWriter, r *http.Request) {
	currencies, err := fe.getCurrencies(r.Context())
	if err != nil {
		renderHTTPError(log, r, w, errors.Wrap(err, "could not retrieve currencies"), http.StatusInternalServerError)
		return
	}
	products, err := fe.getProducts(r.Context())
	if err != nil {
		renderHTTPError(...)
		return
	}
	cart, err := fe.getCart(r.Context(), sessionID(r))
	...
}
```

⚠️ **Sequential, and every failure returns a 500.**

💡 **Count the calls and compute the effective availability** ([[10.3 - Communication Patterns]]). With each service at 99.9%, a page calling four sequentially is 99.6% — **and none of them degrades.**

**Ask for each: is this dependency genuinely required to render the page?** The currency list is not — **a default currency would serve.**

⚠️ **Note that they are not called in parallel.** Four sequential calls where three could be concurrent is three round trips of avoidable latency.

**`src/frontend/main.go`:**

```go
mustConnGRPC(ctx, &svc.currencySvcConn, svc.currencySvcAddr)
```

**Look at the connection setup.** Are there deadlines? Retries? Circuit breakers? **What is missing is the finding** ([[11.2 - Timeouts Retries and Jitter]]).

### 3. Checkout — `src/checkoutservice/main.go`

**The most important file in this repository.**

```go
func (cs *checkoutService) PlaceOrder(ctx context.Context, req *pb.PlaceOrderRequest) (*pb.PlaceOrderResponse, error) {
	orderID, err := uuid.NewUUID()
	...
	prep, err := cs.prepareOrderItemsAndShippingQuoteFromCart(ctx, req.UserId, req.UserCurrency, req.Address)
	if err != nil { return nil, status.Errorf(codes.Internal, err.Error()) }

	total := ...

	txID, err := cs.chargeCard(ctx, &total, req.CreditCard)
	if err != nil { return nil, status.Errorf(codes.Internal, "failed to charge card: %+v", err) }
	log.Infof("payment went through (transaction_id: %s)", txID)

	shippingTrackingID, err := cs.shipOrder(ctx, req.Address, prep.cartItems)
	if err != nil { return nil, status.Errorf(codes.Unavailable, "shipping error: %+v", err) }

	_ = cs.emptyUserCart(ctx, req.UserId)

	orderResult := &pb.OrderResult{...}

	if err := cs.sendOrderConfirmation(ctx, req.Email, orderResult); err != nil {
		log.Warnf("failed to send order confirmation to %q: %+v", req.Email, err)
	} else {
		log.Infof("order confirmation email sent to %q", req.Email)
	}
	return &pb.PlaceOrderResponse{Order: orderResult}, nil
}
```

⚠️ **Read the failure path carefully.**

```
1. Prepare order and shipping quote     → fail: nothing happened. Fine
2. CHARGE THE CARD                       → fail: nothing happened. Fine
3. Ship the order                        → fail: THE CARD IS ALREADY CHARGED
                                            No refund. No compensation. Returns an error
4. Empty the cart                        → error ignored entirely
5. Send confirmation email               → failure only logged
```

💡 **Step 3 is the finding.** A shipping failure after a successful charge leaves the customer charged with no order and no shipment, **and the code returns an error as though nothing happened.**

⚠️ **There is no saga, no compensating refund, and no record of the charge anywhere the system can reconcile from.**

**This is [[10.5 - Distributed Transactions and Sagas]] made concrete: the failure it describes, in a Google reference architecture, shipped.**

💡 **Note also the ordering violation.** The irreversible step — charging — happens *before* the compensable one. **Reversing them (ship, then charge) would eliminate the failure mode entirely.**

**Step 4's ignored error is a second finding:** a charged, shipped order with a cart that still contains the items means the customer can order again.

### 4. A service implementation — `src/cartservice/`

```csharp
public class RedisCartStore : ICartStore {
    public async Task AddItemAsync(string userId, string productId, int quantity) {
        ...
        var value = await db.HashGetAsync(userId, CART_FIELD_NAME);
        ...
        await db.HashSetAsync(userId, new[]{ new HashEntry(CART_FIELD_NAME, cart.ToByteArray()) });
    }
}
```

⚠️ **Read-modify-write with no atomicity.** Two concurrent `AddItem` calls for the same user lose one ([[06.6 - Transactions and Isolation Levels]]).

💡 **This is the lost update problem, in a demo everyone deploys.** The fix is a Lua script or a Redis list append — **and finding it yourself is the exercise.**

### 5. Resilience — `istio-manifests/` and the deployment specs

```yaml
readinessProbe:
  grpc: {port: 7070}
livenessProbe:
  grpc: {port: 7070}
resources:
  requests: {cpu: 200m, memory: 64Mi}
  limits: {cpu: 300m, memory: 128Mi}
```

**Check against [[13.4 - Probes Resources and Autoscaling]]:**

⚠️ **Is the liveness probe checking dependencies?** Are CPU limits set? Are there PDBs? Topology spread constraints? A `preStop` hook?

💡 **Note what a reference architecture includes and omits.** The gaps are as informative as the contents.

## What to Take Away

### The cost, made visible

💡 **Compare `checkoutservice/main.go` to `saleor/order/actions.py`** ([[15.5 - Reading Saleor GraphQL]]).

```
Saleor (monolith):        one transaction. Atomic. ~60 lines
Online Boutique:          five network calls, partial failure, no compensation
```

⚠️ **The monolith version cannot leave a customer charged without an order.** The microservice version can, and does.

**That comparison is the single most useful thing in this session** — it is [[10.11 - The Real Cost of Microservices]] with code on both sides.

### What a proto file buys you

💡 **Fifteen minutes with `demo.proto` gives you more architectural understanding than a day of reading service code.**

**Apply this to your own systems:** a single file describing every service boundary is worth maintaining even if you do not use gRPC ([[05.13 - Contract Testing and Schema Evolution]]).

### Polyglot is a liability

```
Go, C#, Node.js, Python, Java
```

⚠️ **Five languages means five dependency ecosystems, five sets of CVEs, five build pipelines, five debugging skill sets, and five implementations of every cross-cutting concern.**

💡 **Online Boutique is polyglot to demonstrate that it is possible, not because it is wise.** In a real system, the ability to use different languages is rarely worth the cross-cutting tax ([[10.11 - The Real Cost of Microservices]]).

## In Production

### The findings, as a checklist for your own system

```
□  Is there an irreversible step followed by a fallible one?
□  Does a partial failure leave a customer-visible inconsistency?
□  Are errors ignored anywhere (`_ = someCall()`)?
□  Are dependencies called sequentially where they could be parallel?
□  Does every synchronous dependency have a degradation path?
□  Are there timeouts, retries and circuit breakers on every call?
□  Is any read-modify-write non-atomic?
□  Would you notice any of the above in production?
```

⚠️ **Run this against Conduit.** Online Boutique is small enough that its problems are visible; **yours are the same problems, hidden in more code.**

### The reconciliation gap

💡 **The deepest issue in the checkout code is not the missing refund — it is that there is no record from which to reconcile.**

**No order row is written before the charge, so a charged-but-not-shipped order exists nowhere** except the payment provider's records and a log line.

⚠️ **Even a manual fix requires cross-referencing payment provider transactions against shipments.**

**The lesson: write the durable record first, then perform the side effects** ([[08.1 - Why Background Work Exists]], [[10.5 - Distributed Transactions and Sagas]]). **A `pending` order row makes every failure recoverable.**

### Instrumenting it

```bash
kubectl apply -f ./release/istio-manifests.yaml
```

💡 **Online Boutique ships with OpenTelemetry instrumentation.** Deploy it, place an order, and **look at the trace** — five services in one request, exactly the shape from [[12.3 - Instrumenting Conduit End to End]].

**Then break one service and look at the trace again.** The failure's position in the trace is immediately visible, **which is the argument for distributed tracing in one screenshot.**

## Exercise

**Drill 15.6 — Break checkout, then fix it**

```
drills/15-boutique/
├── deploy/{setup.sh, load.py}
├── analysis/{boundaries.md, availability.py, call_graph.md}
├── failures/{charge_no_ship.py, cart_race.py, cascade.py, RESULTS.md}
├── fixes/{saga.go, reorder.md, parallel_frontend.go, atomic_cart.lua}
├── tracing/{trace_order.md, broken_service.md}
└── FINDINGS.md
```

**Part 1 — Deploy and map it.** Run it locally on kind, place an order, and confirm it works.

**Then write `call_graph.md`** from the proto file alone, before reading any service code. **Then verify it against a trace.**

**Part 2 — Score the boundaries.** Apply the five tests from [[10.2 - Finding Service Boundaries]] to all eleven services.

**Identify which exist for domain reasons and which for demonstration.**

**Then compute the effective availability** of the home page and the checkout flow, assuming each service is 99.9%.

**Part 3 — Reproduce the charge-without-order failure.** Make `shippingservice` fail (scale to zero, or inject an error).

**Place an order. Confirm the card is charged.** Check the payment service logs.

**Then answer: where in the system is there a record that this customer was charged?**

⚠️ **The answer should be "only in logs", and that is the finding.**

**Part 4 — Fix it three ways.** Implement and compare:

| Fix | |
|---|---|
| **Reorder** — ship before charging | Simplest. What does it cost? |
| **Saga** — compensating refund on shipping failure | ([[10.5 - Distributed Transactions and Sagas]]) |
| **Durable record first** — write a pending order, then perform steps | |

**For each, kill the process at every step and confirm the state is recoverable.**

**Then measure the code added for each**, and state which you would ship.

**Part 5 — The cart race.** Send 50 concurrent `AddItem` calls for the same user and product.

**Count the resulting quantity.** It should be less than 50.

**Then fix it with a Lua script and confirm exactly 50** ([[06.6 - Transactions and Isolation Levels]]).

**Part 6 — Cascading failure.** Make `currencyservice` slow — 10 seconds, not down.

**Measure the frontend's behaviour**: latency, error rate, and whether pages not needing currency still work.

**Then add a timeout and a degradation path** — default to USD — and measure again ([[11.6 - Graceful Degradation]]).

Then parallelise the frontend's four calls and **measure the latency improvement.**

**Part 7 — Trace a failure.** With OpenTelemetry deployed, place an order successfully and capture the trace.

**Then break `shippingservice` and capture it again.**

**Screenshot both.** The failing span should be immediately obvious — **and that contrast is the argument for tracing, in one image** ([[12.3 - Instrumenting Conduit End to End]]).

**Part 8 — Audit Conduit.** Run the eight-item checklist against your own system.

⚠️ **Look specifically for an irreversible step followed by a fallible one.** Charging, sending an email, calling an external API, and publishing an event are all irreversible.

**For each finding, fix it or write down why the risk is accepted.**

**Done when:**
- You built the call graph from the proto file before reading any service code
- You scored all eleven boundaries and identified the demo-driven ones
- You produced a charge with no order, and located the only record of it
- Three fixes are implemented, with the code cost of each measured
- The cart race is reproduced and fixed atomically
- A slow dependency is contained by a timeout and a degradation path
- Your two traces make the failure position immediately visible
- Conduit is audited for irreversible-then-fallible sequences
