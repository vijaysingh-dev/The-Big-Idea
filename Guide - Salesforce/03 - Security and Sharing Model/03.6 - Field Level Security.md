# Field Level Security

## What it controls

Field-level security, usually shortened to FLS, controls whether a user can see and edit each individual field. It is set per profile and per permission set, with two settings per field:

- **Visible** — the user can read the field
- **Read Only** — the user can read but not write

A field that is not visible is invisible everywhere: page layouts, list views, reports, search results, the API, and SOQL results. This is the important property — FLS is enforced at the platform level, not just in the user interface.

## FLS versus page layout

These are constantly confused, and the difference has real security consequences.

| | Page layout | Field-level security |
| --- | --- | --- |
| Where enforced | User interface only | Everywhere: UI, API, SOQL, reports |
| Removing a field | Hides it from that layout | Hides it from that user, everywhere |
| Read-only setting | UI only | Enforced by the API and DML |
| Applies to | Everyone using that layout | Specific profiles and permission sets |

A field removed from a page layout is still fully readable and writable through the API, Data Loader, reports, and Apex. It is a presentation choice, not a security control.

A field hidden by FLS is genuinely inaccessible.

The rule: **if a user must not see the data, use FLS. If they simply do not need it on screen, use the layout.** Using a layout for something that is actually confidential is a real exposure, and it is one of the most common findings in a security review.

## Where FLS is enforced, and where it is not

Enforced automatically:

- Standard record pages and layouts
- List views
- Reports and dashboards
- Search results
- REST and SOAP API access
- Lightning Data Service and `lightning-record-form`

**Not enforced automatically:**

- SOQL queries in Apex
- DML in Apex
- Apex controllers returning data to a Lightning component
- Formula fields that reference a hidden field
- Roll-up summaries that summarize a hidden field
- Validation rules and workflow that reference a hidden field
- Reports built on a formula that exposes a hidden value

That second list is the one to internalize. The formula field case is particularly worth knowing: **a formula field is not subject to the FLS of the fields it references.** A user who cannot see `Approved_Amount__c` can see a formula field that displays or derives it. This is a documented behaviour, not a bug, and it is a well-known way that supposedly protected data leaks.

The same applies to roll-up summaries: a sum of hidden child field values is visible to anyone who can see the roll-up.

## Enforcing FLS in Apex

By default, Apex ignores field-level security entirely. A query returns every field you select, and DML writes every field you set, regardless of the running user's permissions.

Three approaches, in increasing order of preference.

**Explicit describe checks.** Verbose, but precise, and still necessary in some cases:

```java
if (!Schema.sObjectType.Warranty_Claim__c.fields.Approved_Amount__c.isAccessible()) {
    throw new SecurityException('You cannot view the approved amount.');
}

if (Schema.sObjectType.Warranty_Claim__c.fields.Approved_Amount__c.isUpdateable()) {
    claim.Approved_Amount__c = newAmount;
}
```

**stripInaccessible.** Removes fields the user cannot access from a collection of records, returning a cleaned copy. Useful when you want to return whatever the user is allowed to see rather than throwing:

```java
public with sharing class ClaimController {

    @AuraEnabled(cacheable=true)
    public static List<Warranty_Claim__c> getClaims(Id accountId) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Status__c, Approved_Amount__c, Internal_Notes__c
            FROM Warranty_Claim__c
            WHERE Account__c = :accountId
        ];

        // removes fields the running user cannot read, rather than failing the whole request
        SObjectAccessDecision decision = Security.stripInaccessible(
            AccessType.READABLE, claims
        );
        return decision.getRecords();
    }
}
```

`decision.getRemovedFields()` tells you what was stripped, which is useful for logging or for adjusting the UI.

`AccessType` also supports `CREATABLE`, `UPDATABLE`, and `UPSERTABLE`, which is how you sanitize incoming data before DML — particularly important when a component posts a record built from user input.

**USER_MODE.** The cleanest option, and the current recommendation:

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c, Approved_Amount__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
    WITH USER_MODE
];

update as user claims;
```

`WITH USER_MODE` enforces object permissions, field-level security, and record sharing together, and throws if the user lacks access to a selected field. `as user` does the same for DML.

The choice between `USER_MODE` and `stripInaccessible` is really a choice about failure behaviour. `USER_MODE` fails loudly, which is right when the code should not be running at all for that user. `stripInaccessible` degrades gracefully, which is right for a display component that should show what it can.

## The component layer

Lightning components that use Lightning Data Service — `lightning-record-form`, `lightning-record-edit-form`, `lightning-record-view-form`, and the `getRecord` wire adapter — enforce FLS automatically. Fields the user cannot see simply do not render.

This is a strong argument for using them wherever possible instead of a custom Apex controller. See [[14.12 - Lightning Data Service and Record Forms]].

When custom Apex is genuinely needed, the controller is responsible for enforcement, and `WITH USER_MODE` in the query is the minimum bar.

## Auditing FLS

```sql
SELECT Parent.Label, Parent.Profile.Name, Field, PermissionsRead, PermissionsEdit
FROM FieldPermissions
WHERE SobjectType = 'Warranty_Claim__c'
  AND Field = 'Warranty_Claim__c.Approved_Amount__c'
```

Finding fields nobody can see, which usually indicates dead metadata:

```sql
SELECT Field, COUNT(Id) grantCount
FROM FieldPermissions
WHERE SobjectType = 'Warranty_Claim__c' AND PermissionsRead = true
GROUP BY Field
```

## Practical guidance

**Hide the field, not the layout, for anything confidential.** Salary, cost, margin, internal notes, personal data.

**Watch formula fields.** Before creating a formula that references a restricted field, ask who will see the formula. This is the most common way FLS is defeated accidentally.

**Set FLS when the field is created.** New fields default to visible for administrators and hidden for others, and the resulting "the field is not showing for anyone" question is nearly always this.

**Prefer `WITH USER_MODE` in new Apex.** It is shorter than describe checks, covers more than `WITH SECURITY_ENFORCED` did, and makes the intent obvious to a reviewer.

**Test as a real user.** Administrators bypass FLS through Modify All Data, so nothing about field security is visible from an admin login. `System.runAs()` in tests, and a real test user in the sandbox. See [[19.8 - Testing Security and Sharing]].

**Remember that hiding a field does not hide its history.** Field history tracking and audit trail can expose values, and so can reports built before the field was restricted.
