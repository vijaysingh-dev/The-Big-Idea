# Case Study - Autocomplete

A deceptively small component. The interesting parts are request management, race conditions and keyboard accessibility — and the last one is where most implementations fail.

## Scope it

- Search-as-you-type over a remote dataset, or a local list?
- Single or multi-select?
- Free text allowed, or must the user pick from the list?
- Grouped results? Recent searches? Highlighted matches?
- How large is the dataset — hundreds or millions?
- Mobile keyboard behavior?

A reasonable scope: **remote search, single select, keyboard navigable, grouped results with recent searches, roughly 200ms server latency.**

## Request management

Three mechanisms, each solving a different problem. All three are needed.

**Debounce** reduces request volume ([[29.1 - Debounce and Throttle]]):

```ts
const [query, setQuery] = useState("");
const debouncedQuery = useDebounce(query, 250);
```

Debounce the **derived work**, never the input value — debouncing the value makes typing feel laggy ([[21.1 - Controlled Forms in Practice]]).

250ms is the usual balance. Below ~150ms the saving is marginal; above ~400ms it feels sluggish.

**Cancellation** prevents stale responses overwriting fresh ones ([[04.6 - AbortController and Cancellation]]):

```
type "re"   → request A sent
type "rea"  → request B sent
A resolves AFTER B  →  results for "re" overwrite results for "rea"
```

This is the classic autocomplete bug, and it is intermittent, so it survives testing.

**Caching** makes backspacing instant:

```ts
const { data, isFetching } = useQuery({
  queryKey: ["search", debouncedQuery],
  queryFn: ({ signal }) => api.search(debouncedQuery, { signal }),
  enabled: debouncedQuery.length >= 2,
  staleTime: 5 * 60_000,
  placeholderData: keepPreviousData,
});
```

Four things this gives you:

- **Automatic cancellation** — the `signal` aborts the previous request when the key changes ([[24.6 - TanStack Query Fundamentals]])
- **Cache by query string**, so backspacing from "react" to "rea" is instant
- **`enabled`** avoids querying on one character, which matches nearly everything
- **`keepPreviousData`** keeps the previous results visible while the new ones load, rather than flashing empty

The library handles the race condition that hand-rolled implementations get wrong.

## Guard against an empty flash

```jsx
<ul style={{ opacity: isFetching ? 0.6 : 1 }}>
  {results.map(...)}
</ul>
```

Showing stale results dimmed reads far better than a spinner replacing them ([[24.2 - Loading Error and Empty States]]).

Never show "No results" while a request is in flight — it appears, then vanishes, on every keystroke.

## The ARIA combobox pattern

This is where most implementations are wrong, and it is not optional — a combobox that does not follow the pattern is unusable with a screen reader.

```jsx
<div>
  <input
    role="combobox"
    aria-expanded={isOpen}
    aria-controls={listboxId}
    aria-activedescendant={activeIndex >= 0 ? `${listboxId}-opt-${activeIndex}` : undefined}
    aria-autocomplete="list"
    autoComplete="off"
    value={query}
    onChange={e => setQuery(e.target.value)}
    onKeyDown={handleKeyDown}
  />

  {isOpen && (
    <ul role="listbox" id={listboxId}>
      {results.map((item, i) => (
        <li
          key={item.id}
          id={`${listboxId}-opt-${i}`}
          role="option"
          aria-selected={i === activeIndex}
          onMouseDown={e => e.preventDefault()}
          onClick={() => select(item)}
        >
          {item.label}
        </li>
      ))}
    </ul>
  )}

  <div role="status" aria-live="polite" className="sr-only">
    {results.length} results available
  </div>
</div>
```

The mechanism that matters: **focus never leaves the input.** `aria-activedescendant` points at the visually-highlighted option, so the screen reader announces it while the input keeps focus and typing continues to work.

Moving actual DOM focus into the list breaks typing and is the most common implementation error.

`onMouseDown` with `preventDefault` stops the input blurring before the click registers — otherwise the list closes and the click lands on nothing.

The live region announces the result count, which is otherwise silent for screen reader users. It must exist in the DOM before the count changes ([[12.5 - Custom Events and Observer APIs]]).

## Keyboard interaction

```ts
function handleKeyDown(e) {
  switch (e.key) {
    case "ArrowDown":
      e.preventDefault();
      setActiveIndex(i => Math.min(i + 1, results.length - 1));
      break;
    case "ArrowUp":
      e.preventDefault();
      setActiveIndex(i => Math.max(i - 1, -1));
      break;
    case "Enter":
      if (activeIndex >= 0) { e.preventDefault(); select(results[activeIndex]); }
      break;
    case "Escape":
      if (isOpen) { setIsOpen(false); setActiveIndex(-1); }
      else setQuery("");
      break;
    case "Home": case "End":
      if (isOpen) { e.preventDefault(); setActiveIndex(e.key === "Home" ? 0 : results.length - 1); }
      break;
    case "Tab":
      setIsOpen(false);
      break;
  }
}
```

`preventDefault` on the arrow keys stops the caret moving within the input.

`Escape` has two behaviors by convention — close the list first, clear the input on a second press. Small, and users notice it.

`Tab` closes without selecting. Some implementations select on Tab; the APG says it should not, since Tab means "move on", not "choose this".

Scroll the active option into view as it changes:

```ts
useEffect(() => {
  optionRefs.current[activeIndex]?.scrollIntoView({ block: "nearest" });
}, [activeIndex]);
```

## Result rendering

Highlight the matched substring, safely:

```jsx
function Highlight({ text, query }) {
  const i = text.toLowerCase().indexOf(query.toLowerCase());
  if (i === -1 || !query) return <>{text}</>;

  return (
    <>
      {text.slice(0, i)}
      <mark>{text.slice(i, i + query.length)}</mark>
      {text.slice(i + query.length)}
    </>
  );
}
```

Never build this with `dangerouslySetInnerHTML` and a regex replace — the text comes from a server and the query comes from the user, which is an XSS vector on both sides ([[15.6 - Frontend Security]]).

Grouped results need the right ARIA structure:

```jsx
<ul role="listbox">
  <li role="group" aria-labelledby="grp-recent">
    <span id="grp-recent" role="presentation">Recent</span>
    <ul role="presentation">{/* role="option" items */}</ul>
  </li>
</ul>
```

## Large local datasets

If the data is already client-side, the work is filtering rather than fetching:

```jsx
const deferredQuery = useDeferredValue(query);

const results = useMemo(
  () => index.search(deferredQuery).slice(0, 50),
  [deferredQuery]
);
```

`useDeferredValue` keeps typing responsive while an expensive filter runs at lower priority ([[22.5 - useDeferredValue]]). It requires `useMemo` around the computation, or nothing is actually deferred.

For tens of thousands of records, a prebuilt index — FlexSearch, MiniSearch, Fuse.js — beats a linear `filter` substantially. For hundreds of thousands, move it to a Web Worker so the main thread stays free ([[08.4 - Web Workers]]).

Always cap the rendered results. Nobody scrolls past twenty options, and rendering 5,000 is pure cost.

## Mobile

```jsx
<input
  type="search"
  inputMode="search"
  enterKeyHint="search"
  autoCapitalize="off"
  autoCorrect="off"
  spellCheck={false}
/>
```

`autoCorrect` and `autoCapitalize` off matter for names, codes and technical terms — iOS will otherwise "helpfully" rewrite the query.

The virtual keyboard covers roughly half the screen, so the dropdown must be positioned or scrolled into view accordingly.

**IME composition** must be handled for Chinese, Japanese, Korean and phonetic Indic input — searching on intermediate composition states produces nonsense queries ([[16.8 - Controlled vs Uncontrolled Components]]):

```jsx
onCompositionStart={() => setComposing(true)}
onCompositionEnd={() => setComposing(false)}
```

Skip the search while composing.

## Use a headless library

The APG combobox pattern is long, and every detail above is one of its requirements. Downshift, Radix Combobox and React Aria's `useComboBox` implement it correctly, including edge cases like screen-reader-specific announcement quirks and mobile focus behavior.

Building it from scratch is a legitimate exercise and rarely the right production choice ([[28.10 - Design Systems and Component Libraries]]).

## How senior engineers approach this

**They use debounce, cancellation and caching together**, since each solves a different problem.

**They keep DOM focus on the input** and use `aria-activedescendant` for the visual selection.

**They announce result counts via a live region**, which is otherwise silent.

**They cap rendered results** and index rather than linearly filter large local datasets.

**They handle IME composition** for any product with a non-Latin-script audience.

**They use a headless library** unless the interaction is genuinely novel.

## Common pitfalls

- Stale responses overwriting fresh ones from missing cancellation.
- Debouncing the input value, making typing feel laggy.
- Moving DOM focus into the list, breaking typing.
- Blur closing the list before a click registers — needs `onMouseDown` prevention.
- "No results" flashing during in-flight requests.
- Match highlighting via `innerHTML`, creating an XSS hole.
- No live region, leaving screen reader users unaware of results.
- Arrow keys moving the text caret instead of the selection.
- Searching on IME composition states.

## Interview angle

Lead with request management — debounce to reduce volume, cancellation to prevent stale overwrites, caching for instant backspace — and explain the race condition explicitly, since it is the substantive technical problem. Then the ARIA combobox pattern with the key insight that focus stays on the input and `aria-activedescendant` conveys selection. Mentioning IME composition and the mobile keyboard covering the dropdown shows you have built this for real users rather than for a demo.
