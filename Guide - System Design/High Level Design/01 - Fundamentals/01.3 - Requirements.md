# Requirements: Functional vs Non-Functional

> **Revision tags:** #fundamentals #requirements  
> **Related:** [[02.2 - Requirements Clarification]] | [[01.4 - Core Properties]]

---

## Why Requirements Come First

Every HLD decision is driven by requirements. A URL shortener that needs to handle 10 RPS is architected completely differently from one handling 10 million RPS. No requirement = no basis for any design choice.

Getting requirements wrong is the most expensive mistake in engineering. Changing a database choice after launch is painful. Changing it after 3 years of production data is catastrophic.

---

## Functional Requirements (FR)

**Definition:** What the system *does* — its features and behaviors from a user/caller perspective.

Functional requirements describe **inputs and outputs**, not how the system achieves them.

### Examples

| System | Functional Requirements |
|---|---|
| URL Shortener | Create short URL, redirect to original, expire links |
| Chat App | Send messages, receive messages in real-time, read receipts |
| Payment Gateway | Charge card, refund, handle disputes, generate receipts |
| Feed System | Post content, follow users, see posts from followed users |

### How to Write Good FRs

Bad: "The system should be fast."  
Good: "Users can retrieve their feed within 200ms at p99."

Bad: "Handle payments."  
Good: "Process card charges, support refunds within 30 days, handle idempotent retries."

---

## Non-Functional Requirements (NFR)

**Definition:** How well the system performs its functions — quality attributes, constraints, and operational properties.

NFRs determine the *architecture*. Two systems with identical FRs but different NFRs often look completely different.

### The Core NFR Vocabulary

| NFR | What It Means | Typical Metric |
|---|---|---|
| **Availability** | % of time the system is operational | 99.9% = 8.7h downtime/year |
| **Reliability** | Requests succeed without errors | Error rate < 0.1% |
| **Durability** | Data is not lost once written | 11 nines (S3) |
| **Latency** | Time to respond to a single request | p99 < 100ms |
| **Throughput** | Requests handled per unit time | 100,000 RPS |
| **Scalability** | Ability to grow capacity with load | Linear scale-out |
| **Consistency** | All readers see the same data | Strong / Eventual |
| **Fault Tolerance** | System continues despite component failures | Survives AZ outage |
| **Resilience** | System recovers from failures | RTO < 1 min |
| **Maintainability** | Cost and ease of changing the system | Deploy independently |

> Each of these is covered in depth in [[01.4 - Core Properties]].

## FR vs NFR — The Critical Distinction

A useful mental test:

- **FR:** "Can I demonstrate this in a demo?" → Yes = Functional
- **NFR:** "Would a user notice this only under load, failure, or over time?" → Yes = Non-Functional

| Statement | FR or NFR? |
|---|---|
| Users can upload profile photos | FR |
| Photos must load within 300ms | NFR (Latency) |
| Users can't see other users' private photos | FR (partially) + NFR (Security) |
| The system must survive a datacenter going down | NFR (Fault Tolerance) |
| The system must support 1M concurrent users | NFR (Scalability) |
| Users can search posts by keyword | FR |
| Search results must appear in under 500ms | NFR (Latency) |

## Implicit vs Explicit NFRs

Not all NFRs are stated. Experienced engineers know to ask for — or assume — certain implicit NFRs:

**Always implicit:**
- Data must not be lost (durability)
- System must be secure (no unauthorized access)
- The system must be operable (logs, alerts, deploys)

**Often unstated but important:**
- "Users expect real-time behavior" → implies low latency + WebSockets
- "This is a financial system" → implies strong consistency + audit logs
- "Global users" → implies CDN + geo-distributed deployment

---

## Implicit Tradeoffs Between NFRs

NFRs conflict with each other. This is where architecture decisions live.

| NFR Conflict | The Tradeoff |
|---|---|
| Consistency vs Availability | Strong consistency requires coordination → higher latency/unavailability during partitions (CAP theorem) |
| Latency vs Durability | Writing to disk synchronously is slower than writing to memory |
| Scalability vs Consistency | Scaling out requires partitioning, which makes global consistency harder |
| Cost vs Performance | More replicas = more availability, also more cost |
| Simplicity vs Fault Tolerance | Redundancy adds operational complexity |

In HLD, you don't solve these conflicts — you **make a deliberate choice** and justify it.

## How to Use Requirements in HLD Interviews

1. **Never start designing before clarifying requirements.** Spend 5 minutes upfront.
2. **Ask specifically:** "Is this read-heavy or write-heavy? What's the expected scale? What's the consistency requirement? Is this global?"
3. **Write down your assumptions.** "I'm assuming 99.9% availability, 10M DAU, reads 10x writes."
4. **Revisit requirements during design.** New NFRs emerge as you dig deeper.
