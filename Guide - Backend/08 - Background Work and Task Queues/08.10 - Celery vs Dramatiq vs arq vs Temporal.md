# Celery vs Dramatiq vs arq vs Temporal

#backend #queues #architecture

> **In one line:** Celery has the ecosystem and the sharpest edges, Dramatiq has better defaults, arq is native async, and Temporal is a different category — a workflow engine, not a task queue.

---

## The Idea

Four tools, three of which do the same thing and one of which does something else.

| | Celery | Dramatiq | arq | Temporal |
|---|---|---|---|---|
| Category | Task queue | Task queue | Task queue | **Workflow engine** |
| Async native | **No** | No | **Yes** | Yes |
| Brokers | Redis, RabbitMQ, SQS | Redis, RabbitMQ | **Redis only** | Its own service |
| Lines of code | ~30,000 | ~5,000 | ~2,000 | Very large |
| DLQ by default | **No** | **Yes** | No | N/A — different model |
| Durable state | No | No | No | **Yes** |
| Ecosystem | **Large** | Small | Small | Growing |

💡 **The honest summary: if you are writing a new async Python service, arq is the better fit; if you need the ecosystem, Celery; if you need durable multi-step workflows, none of the first three and Temporal is a genuine category shift.**

---

## Celery

**The default, and the reason is inertia plus ecosystem.**

| Strength | |
|---|---|
| **Everyone knows it** | Hiring, documentation, Stack Overflow answers |
| Every broker | Redis, RabbitMQ, SQS, and more |
| Rich feature set | Canvas, beat, remote control, events |
| Django and Flask integration | First-class |
| Battle-tested at scale | Fifteen years of production use |

⚠️ **The costs, all covered in earlier notes:**

| Problem | |
|---|---|
| **No asyncio support** | `asyncio.run` per task, no shared connection pools ([[08.3 - Celery Architecture]]) |
| **Dangerous defaults** | `acks_late=False`, no time limits, prefetch 4 |
| **No DLQ** | You build it ([[08.6 - Retries Backoff and Dead Letters]]) |
| Redis broker emulation | Visibility timeouts, restore threads ([[08.4 - Brokers and Result Backends]]) |
| Beat is a singleton | Your problem ([[08.8 - Periodic Tasks and Distributed Cron]]) |
| Large surface area | Many ways to configure it wrong |

💡 **The asyncio gap is the one that matters most for a modern codebase.** Your service is async, your database driver is async, your HTTP client is async — and then every task creates a fresh event loop and a fresh connection pool.

```python
@app.task
def process_document(document_id: str):
    return asyncio.run(_process(document_id))     # new loop, new pools, every task
```

⚠️ **Measure this cost before dismissing it.** For a task doing 200ms of work, creating an event loop and a connection pool can be a meaningful fraction of the total.

## Dramatiq

**Celery's design, revisited with better defaults.**

```python
import dramatiq

@dramatiq.actor(max_retries=5, time_limit=300_000, queue_name="ingestion")
def process_document(document_id: str):
    ...

process_document.send(document_id="doc_42")
```

| Better than Celery | |
|---|---|
| **DLQ by default** | Every queue gets one automatically |
| **Late acking by default** | At-least-once out of the box |
| Middleware architecture | Retries, age limits and time limits are all middleware |
| Much smaller | ~5,000 lines, readable in a weekend |
| Explicit and predictable | Fewer implicit behaviours |

```python
broker.add_middleware(dramatiq.middleware.Retries(max_retries=5))
broker.add_middleware(MyCustomMiddleware())
```

💡 **The middleware architecture is genuinely cleaner than Celery's mix of task options, signals and settings.** Cross-cutting concerns — tracing, metrics, tenant context — become one middleware rather than three signal handlers.

⚠️ **The costs:**

| | |
|---|---|
| Small ecosystem | Fewer integrations, fewer answers online |
| **No asyncio** | Same problem as Celery |
| No built-in scheduler | Use `apscheduler` or a CronJob |
| Fewer people know it | A hiring and onboarding consideration |

💡 **Dramatiq is what Celery would look like if it were designed today with the same architecture.** It is a better tool and the ecosystem gap is real — which is a legitimate reason to choose the worse tool.

## arq

**Native asyncio, and small enough to read in an afternoon.**

```python
from arq import create_pool
from arq.connections import RedisSettings

async def process_document(ctx, document_id: str):
    async with ctx["db"].acquire() as conn:        # ← shared pool
        ...

class WorkerSettings:
    functions = [process_document]
    redis_settings = RedisSettings()
    max_jobs = 100
    job_timeout = 300
    keep_result = 0
    on_startup = setup_pools
    on_shutdown = close_pools
```

```python
redis = await create_pool(RedisSettings())
await redis.enqueue_job("process_document", document_id="doc_42")
```

| Genuine advantages | |
|---|---|
| **Native async** | No `asyncio.run`, no loop per task |
| **Shared connection pools** | Created once in `on_startup`, used by every job |
| High concurrency cheaply | `max_jobs=100` is 100 coroutines, not 100 processes |
| ~2,000 lines | You can read the whole thing |
| **Built-in cron** | No separate beat process |
| Simple, predictable semantics | Very little to configure wrong |

💡 **The shared-pool point is the big one.** In arq, `ctx["db"]` is a pool created at worker startup, shared by every concurrently-running job. In Celery, each `asyncio.run` gets its own. **For an I/O-bound task workload that is a substantial efficiency difference**, and it is the reason arq exists.

⚠️ **The limitations:**

| | |
|---|---|
| **Redis only** | No RabbitMQ, no SQS |
| Small ecosystem | Very few integrations |
| **CPU-bound work is awkward** | Coroutines share one thread; you need an executor |
| Fewer features | No canvas, no remote control, minimal introspection |
| Smaller community | You will read the source when something is unclear |

💡 **arq is the right choice for an async-first service doing I/O-bound background work on Redis** — which describes a large fraction of modern Python backends, including Conduit.

**For CPU-bound work, you still need processes**, and arq handles that less gracefully than Celery's prefork pool ([[01.3 - Threads Processes and Coroutines]]).

## Temporal

**Not a task queue. A durable execution engine.**

```python
@workflow.defn
class DocumentIngestion:
    @workflow.run
    async def run(self, document_id: str) -> str:
        text = await workflow.execute_activity(
            extract_text, document_id,
            start_to_close_timeout=timedelta(minutes=5),
            retry_policy=RetryPolicy(maximum_attempts=3),
        )
        chunks = await workflow.execute_activity(chunk_text, text, ...)
        await workflow.execute_activity(index_chunks, chunks, ...)
        return "indexed"
```

💡 **The workflow function runs to completion even if the process running it dies.** Temporal records every activity result durably; on restart it **replays** the workflow code against that history, skipping completed steps and resuming exactly where it stopped.

**That is the fundamental difference.** A Celery chain is a sequence of independent messages with no shared state; a Temporal workflow is a program whose execution state is durable.

### What that buys you

| Capability | |
|---|---|
| **Resume after a crash** | Mid-workflow, at the exact step |
| Long-running workflows | Days or months, with `workflow.sleep(timedelta(days=30))` |
| **Compensation / sagas** | `try/except` in the workflow code |
| Signals and queries | Send events into a running workflow; query its state |
| Complete visibility | Every step, input, output and retry is recorded |
| Versioning | Run old and new workflow code simultaneously |

```python
@workflow.run
async def run(self, order_id: str):
    reserved = await workflow.execute_activity(reserve_inventory, order_id, ...)
    try:
        await workflow.execute_activity(charge_payment, order_id, ...)
    except ActivityError:
        await workflow.execute_activity(release_inventory, reserved, ...)   # compensate
        raise
```

⚠️ **Expressing this in Celery requires hand-building a state machine, persisting it, and handling every crash point yourself** ([[08.11 - Durable Workflows and Sagas]]). Temporal makes it ordinary control flow.

### The costs, which are substantial

| | |
|---|---|
| **A cluster to operate** | Temporal server plus Cassandra or Postgres, or Temporal Cloud |
| **Determinism constraints** | Workflow code must be replayable — no `random`, no `datetime.now()`, no direct I/O |
| Steep learning curve | Workflows versus activities, replay semantics, versioning |
| Heavier per-task overhead | Not for high-volume simple tasks |
| Small Python community | Growing, still small |

⚠️ **The determinism constraint is the real learning cost.** Workflow code is replayed from history, so anything non-deterministic produces divergence. `workflow.now()`, `workflow.random()` and `workflow.uuid4()` exist precisely because the standard library versions are forbidden — and that is a genuinely different way to write code.

💡 **Temporal is right when the work is a multi-step process with state, compensation and long duration.** It is wrong for "resize this image", and using it for that is paying a large operational bill for nothing.

## Choosing

```
Is the work a multi-step process with state and compensation?
├── YES → Temporal (or a hand-rolled saga if the cluster is too much)
│
└── NO — it is discrete tasks
    ├── Is the service async, I/O-bound, and on Redis?
    │   └── arq
    ├── Do you need RabbitMQ/SQS, or heavy CPU work?
    │   ├── Want better defaults and can accept a small ecosystem?  → Dramatiq
    │   └── Need the ecosystem, Django integration, or team familiarity? → Celery
    └── Already running Celery successfully?
        └── Stay. Migration cost rarely justifies the improvement
```

### The honest position on migration

⚠️ **Do not migrate a working Celery deployment to Dramatiq or arq for the improvements alone.** The gains are real and modest; the migration touches every background code path and every operational runbook.

💡 **Do choose deliberately for a new service.** The cost of picking arq for a new async service is zero, and the shared-pool and native-async benefits accrue from day one.

**Migrating to Temporal is different** — it is a capability change, not an efficiency one, and it can be justified when you have hand-built a fragile state machine that Temporal would make ordinary.

### The gradual path

```python
# Both can run side by side, consuming different queues
celery worker -Q legacy
arq app.worker.WorkerSettings          # new tasks
```

**New work goes to the new system; old work stays until it is touched anyway.** No big-bang migration.

## In Production

### What you give up leaving Celery

| Feature | Dramatiq | arq | Temporal |
|---|---|---|---|
| Flower | ✗ | ✗ | Its own UI, better |
| `inspect` remote control | ✗ | ✗ | N/A |
| Canvas (chain, group, chord) | Partial | ✗ | Native, better |
| Beat | Use apscheduler | **Built in** | Native |
| Django integration | Manual | Manual | Manual |
| SQS support | ✗ | ✗ | N/A |
| **Stack Overflow answers** | Few | Few | Few |

⚠️ **The last row is not a joke.** At 2am, the difference between a well-documented problem and one nobody has written about is real.

### The Conduit decision

**arq**, for a new async service.

**Defend it:**

| Reason | |
|---|---|
| Conduit is async throughout | FastAPI, asyncpg, httpx |
| Work is I/O-bound | API calls, database, embedding requests |
| Redis is already deployed | For caching and the SSE backplane |
| **Shared connection pools** | Measurably cheaper than a pool per task |
| Built-in cron | One fewer process than Celery beat |
| Small enough to read | When something is unclear, read the source |

⚠️ **What we accept:** a smaller ecosystem, Redis-only, and CPU-bound tasks needing an executor.

💡 **The phase-9 caveat:** embedding work is GPU-bound and long-running, and it may want its own worker type. **arq for the I/O pipeline, a dedicated worker for embedding** is a reasonable split, and it is worth designing the boundary now.

**If Conduit later needs multi-step compensation** — a document ingestion that must undo partial indexing on failure — **that is the signal to evaluate Temporal**, not to build a state machine in arq.

### Migration checklist

If you do migrate:

```
□  Both systems running, different queues
□  New tasks on the new system only
□  Old queue drained before removing the old workers
□  Metrics and alerts ported before any traffic moves
□  Runbooks updated
□  Idempotency verified — semantics differ subtly
□  DLQ behaviour understood in the new system
□  Deploy and shutdown behaviour tested
```

⚠️ **Ack semantics differ between systems.** Celery's `acks_late=False` default versus Dramatiq's late-ack default means a migration changes your delivery guarantees — **usually for the better, and you must know it happened** ([[08.2 - Queue Semantics]]).

## Codebase

**Repo:** `Bogdanp/dramatiq`, `python-arq/arq`, `temporalio/sdk-python`

**Question to answer:** In arq, where are shared resources created and how does a job access them? Then: in Temporal, how does workflow replay work — what is recorded, and what makes non-determinism a problem?

**Read, in order:**

1. `arq/arq/worker.py` — **the whole file, it is short.** `Worker.main`, `start_jobs`, and the `ctx` dict. **The answer to the first question is in `on_startup` and how `ctx` is passed to every job**
2. `arq/arq/jobs.py` — job serialisation and result handling. Compare to Celery's message format ([[08.3 - Celery Architecture]])
3. `dramatiq/dramatiq/middleware/` — **read three or four middlewares.** `retries.py`, `age_limit.py`, `time_limit.py`. The architecture is the point
4. `dramatiq/dramatiq/brokers/rabbitmq.py` — the automatic DLQ setup
5. `temporalio/sdk-python/temporalio/worker/_workflow_instance.py` — **the replay mechanism.** How activity results are fed back from history rather than re-executed. **The answer to the second question**
6. `temporalio/sdk-python/temporalio/workflow.py` — `workflow.now()`, `workflow.random()` and the determinism helpers. **Reading these makes the constraint concrete**

💡 The Temporal replay code is the most conceptually interesting reading in section 08. **The workflow function is re-executed from the beginning on every recovery, with completed activities returning their recorded results instead of running.** Once that clicks, the determinism rules stop feeling arbitrary and become obviously necessary.

**Size:** 2 sessions.

**Drill 8.10 — The same pipeline, four ways**

```

│   └── RESULTS.md

│   ├── compensation.py   # undo on failure
│   └── COMPARISON.md
├── operations/

│   ├── deploy.py
│   └── FINDINGS.md
├── decision/
│   └── ADR.md
└── README.md
```

**Part 1 — One pipeline, four implementations.** A five-stage document pipeline: fetch, extract, chunk, embed, index.

**The domain logic goes in `domain/pipeline.py` and is imported by all four** ([[08.5 - Task Design Rules]]). If your logic imports a framework, the comparison is invalid.

**Part 2 — Throughput and overhead.** 10,000 documents through each.

Measure: total time, per-task overhead (enqueue plus dispatch minus actual work), memory per worker, and CPU.

Then isolate the connection pool cost: **measure how long `asyncio.run` plus pool creation takes in Celery versus using a shared pool in arq.**

**Report it as a percentage of a 200ms task.** That number is the concrete case for arq.

**Part 3 — Crash recovery.** Kill a worker mid-pipeline, at stage 3 of 5.

For each framework measure: work lost, work redone, time to recovery, and whether stages 1–2 were repeated.

**Temporal should skip stages 1–2 entirely on replay.** The others should redo them unless you built explicit state tracking.

**This is the clearest demonstration of what a workflow engine gives you**, and it is worth measuring rather than reading about.

**Part 4 — Compensation.** Add a requirement: if indexing fails, undo the chunk writes and mark the document failed.

Implement it in all four.

**Count lines of code and failure cases you had to handle explicitly.**

Then crash at each of six points during the compensation itself. **Confirm the final state is consistent in each framework** — and note how much work that took in each.

**Part 5 — Out-of-the-box operations.** For each framework, without writing custom code, determine:

| Question | |
|---|---|
| Is there a DLQ? | |
| Can you see what a worker is doing? | |
| Can you see why a task failed? | |
| Can you replay a failure? | |
| Are there time limits? | |
| Is there a scheduler? | |
| What are the default ack semantics? | |

**Fill in the matrix.** Then measure how much code each needed to reach a common baseline.

**Part 6 — Deploy behaviour.** A rolling deploy while each is processing 5-minute pipelines.

Measure work redone, and whether in-flight work completed or was abandoned.

**Part 7 — The ADR.** Choose one for Conduit.

**Cite your own numbers.** State what you are giving up, and name the specific future signal that would make you reconsider — for Conduit, "we need compensation across stages" is the Temporal trigger and it should be written down.

**Done when:**
- One domain module serves all four implementations
- You have the connection-pool overhead as a percentage of task time
- Crash recovery shows Temporal skipping completed stages
- Compensation line counts differ substantially and you know why
- The out-of-the-box operations matrix is complete
- The ADR cites measurements and names its reconsideration trigger
