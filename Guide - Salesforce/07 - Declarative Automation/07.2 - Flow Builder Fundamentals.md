# Flow Builder Fundamentals

## What a flow is

A flow is a program built on a canvas. It has variables, conditionals, loops, and data operations, and it runs on the Salesforce server in the same transaction as everything else.

The critical framing for a developer: **a flow is code.** It consumes the same governor limits, participates in the same transaction, throws the same errors, and needs the same care about bulk behaviour. The canvas hides that, which is why flow-heavy orgs accumulate performance problems that nobody can attribute.

## Flow types

**Record-Triggered** — runs when a record is created, updated, or deleted. The most common type by far. See [[07.3 - Record-Triggered Flows]].

**Screen Flow** — presents a user interface, collecting input across steps. Launched from a button, a record page, an Experience Cloud site, or a quick action. See [[07.5 - Screen Flows]].

**Autolaunched Flow** — no user interface, no trigger. Called from Apex, another flow, a process, or a REST API. The reusable building block. See [[07.7 - Subflows and Reusability]].

**Scheduled Flow** — runs on a schedule against a set of records. See [[07.6 - Scheduled and Autolaunched Flows]].

**Platform Event-Triggered** — runs when an event is published. See [[12.8 - Platform Events]].

**Orchestration** — multi-step, multi-user processes with waiting and assignment. Sits between a flow and an approval process.

## Elements

**Interaction:** Screen, Action, Subflow.

**Logic:** Assignment, Decision, Loop, Collection Sort, Collection Filter, Wait.

**Data:** Get Records, Create Records, Update Records, Delete Records, Roll Back Records.

The two that matter most for correctness are **Get Records** and the **Loop**, and specifically what you must never combine.

## Resources

Flow's equivalent of variables.

**Variable** — a value that can change. Typed: Text, Number, Record, or a collection of any of these.

**Collection Variable** — a list. The flow equivalent of `List<SObject>`.

**Constant** — a fixed value.

**Formula** — an expression evaluated when referenced, using the same syntax as section 06.

**Text Template** — formatted text with merge fields, for emails and rich output.

**Choice** and **Record Choice Set** — options for screen inputs.

Variables can be marked **Available for Input** and **Available for Output**, which is what makes a flow callable as a subflow or from Apex.

## The rule that matters most

**Never put a Get Records, Create, Update, or Delete element inside a Loop.**

This is the flow equivalent of SOQL-in-a-loop, and it is the single most common cause of flows that work in testing and fail in production. Each iteration consumes a query or a DML statement. At 101 iterations the transaction dies.

The correct pattern is identical in structure to bulkified Apex ([[10.6 - Bulkification Patterns]]):

```
Get Records            → fetch everything you need, once
Loop over collection
    Assignment         → modify the record in memory
    Assignment         → add it to an output collection
End Loop
Update Records         → one DML on the whole collection
```

Building the output collection inside the loop and performing the DML after it is the whole technique. Flow Builder will let you put an Update inside the loop, and nothing warns you.

## A worked example

Requirement: when a service contract's status changes to Cancelled, mark all its coverage records inactive and create a task for the account owner.

```
Start: Record-Triggered on Service_Contract__c
       After Save, Update
       Entry condition: Status__c = "Cancelled"
                        AND ISCHANGED(Status__c)

Get Records: Machine_Coverage__c
       Where Service_Contract__c = {!$Record.Id}
       Store all records in collection {!coverageRecords}

Decision: Any coverage found?
       {!coverageRecords} is null → go to Create Task
       Otherwise → go to Loop

Loop over {!coverageRecords} as {!currentCoverage}
       Assignment: {!currentCoverage.Active__c} = false
       Assignment: {!currentCoverage.End_Reason__c} = "Contract cancelled"
       Assignment: add {!currentCoverage} to {!coverageToUpdate}
End Loop

Update Records: {!coverageToUpdate}

Create Records: Task
       Subject = "Contract cancelled — review account coverage"
       WhatId = {!$Record.Account__c}
       OwnerId = {!$Record.Account__r.OwnerId}
       ActivityDate = TODAY() + 3
```

One query, one update, one insert, regardless of whether the contract covers one machine or two hundred.

The `$Record` global variable holds the triggering record. `$Record__Prior` holds its previous state in an update context, which is flow's equivalent of `Trigger.oldMap`.

## Debugging

**Flow Debug** in Flow Builder runs the flow with inputs you supply and shows the path taken, the value of every resource at each step, and where it failed. It can run in the context of a specific user, which is essential for testing anything permission-dependent.

Debug does not simulate bulk. A flow debugged with one record proves nothing about its behaviour with 200, which is the central weakness of flow testing and the strongest argument for Apex where bulk correctness matters.

**Flow interviews** — paused or errored flow runs — are visible in Setup and queryable:

```sql
SELECT Id, InterviewLabel, CurrentElement, PauseLabel, CreatedDate, CreatedBy.Name
FROM FlowInterview
WHERE CreatedDate = LAST_N_DAYS:7
```

**Debug logs** include flow execution when the Workflow log level is set high enough. The output is verbose and it is the only way to see what a flow did during a real transaction rather than a debug run.

**Error emails.** By default, flow errors email the flow's last modifier, which is usually wrong — the person who last touched it is not necessarily who should be paged. Setting the error recipient in Process Automation Settings to a monitored address is a small fix worth making on day one.

## Flows as metadata

A flow is a `.flow-meta.xml` file. It deploys, it belongs in version control, and it can be diffed in a pull request.

The practical caveat: **flow XML diffs are close to unreadable.** A small canvas change produces a large diff with reordered elements and changed coordinates. Reviewing a flow change means opening it in Flow Builder, not reading the diff, which is a genuine weakness compared to code review.

Flows are **versioned**. Each save creates a version, one is active, and older versions are retained. This is genuinely useful for rollback — activating the previous version undoes a bad change instantly, with no deployment. It is also a trap: the version in your repository may not be the active one in the org.

```sql
SELECT Id, ApiName, Label, ProcessType, TriggerType, VersionNumber, Status,
       LastModifiedBy.Name, LastModifiedDate
FROM FlowDefinitionView
WHERE Status = 'Active'
ORDER BY LastModifiedDate DESC
```

That query answers "what changed recently and who changed it", which is the first question during an incident.

## Naming and documentation

Flows accumulate faster than any other metadata type, and an org with sixty flows named "Opportunity Update 3" is unmaintainable.

Conventions that hold up:

**Name by object, timing, and purpose.** `Case_AfterSave_AssignEntitlement`, `ServiceContract_AfterSave_CancelCoverage`.

**Use the description field.** It is the only documentation, and it is visible in the flow list.

**Name every element meaningfully.** `Get_Active_Coverage` rather than `Get_Records_1`. Element names appear in error messages and debug logs, and default names make both useless.

**Record the entry conditions in the description.** The most common question about a flow is "when does this actually run", and answering it in the description saves opening the flow.

## Practical guidance

**Never query or perform DML inside a loop.**

**Use one flow per object per timing**, with internal decisions, rather than several flows on the same object competing for order.

**Set the error recipient to a monitored address.**

**Name elements meaningfully.** They appear in errors.

**Test with more than one record.** Debug proves the logic; it does not prove bulk safety.

**Treat flows as code in version control**, and review them in Flow Builder rather than in the diff.
