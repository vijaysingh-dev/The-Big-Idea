# Phase 1: The Monolith

#backend #project #capstone

> **In one line:** One process, one database, and every hard decision about schema, tenancy and API shape made properly — because these are the ones you cannot change later.

---

## The Problem

You have nothing. **Build the smallest system that is genuinely correct.**

⚠️ **The temptation is to rush this because it is "just CRUD".** It is not — **the schema, the tenant model and the API contract are the decisions with the longest half-life in the whole project.** Everything after phase 1 is built on them.

💡 **A monolith done properly, with enforced module boundaries, is a legitimate destination** ([[10.1 - Monolith Modular Monolith Microservices]]). Phase 4 splits it to learn what that costs — not because phase 1 is inadequate.

```
conduit/

│   ├── documents/         api.py  service.py  repository.py  models.py
│   ├── sources/
│   ├── organisations/

│   ├── shared/            db.py  config.py  errors.py  ids.py
│   └── main.py
├── migrations/
├── tests/
└── docker-compose.yml
```

**Modules with public interfaces, enforced.**

```ini
[importlinter:contract:module-boundaries]
name = Modules use only public APIs
type = forbidden
source_modules = conduit.search, conduit.sources
forbidden_modules = conduit.documents.repository, conduit.documents.models
```

```sql
CREATE SCHEMA documents;
CREATE SCHEMA organisations;
REVOKE ALL ON SCHEMA documents FROM search_role;
```

💡 **Schema separation with role permissions makes a cross-module query a database error**, which is stronger than any review ([[10.2 - Finding Service Boundaries]]).

⚠️ **Without enforcement, a modular monolith degrades into a monolith within one sprint.**

### The API

```
POST   /v1/documents              upload
GET    /v1/documents              list, cursor-paginated
GET    /v1/documents/{id}
PATCH  /v1/documents/{id}
DELETE /v1/documents/{id}

POST   /v1/documents/{id}/annotations
GET    /v1/search?q=...
POST   /v1/sources
```

**REST, with the conventions from [[05.1 - REST Done Properly]]:** prefixed ULIDs, envelope pagination, `timestamptz`, string enums, Problem Details errors.

### The schema

```sql
CREATE TABLE documents (
    id           uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id       uuid NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
    source_id    uuid REFERENCES sources(id) ON DELETE SET NULL,
    title        text NOT NULL CHECK (length(title) BETWEEN 1 AND 500),
    status       text NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','extracting','indexed','failed')),
    size_bytes   bigint NOT NULL CHECK (size_bytes >= 0),
    content_hash bytea,
    storage_key  text NOT NULL,
    metadata     jsonb NOT NULL DEFAULT '{}',
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    version      integer NOT NULL DEFAULT 1,

    CONSTRAINT indexed_has_hash CHECK (status <> 'indexed' OR content_hash IS NOT NULL),
    CONSTRAINT unique_hash_per_org UNIQUE NULLS NOT DISTINCT (org_id, content_hash)
);

CREATE INDEX ON documents (org_id, created_at DESC, id DESC);
CREATE INDEX ON documents (org_id, status) WHERE deleted_at IS NULL;
```

💡 **`unique_hash_per_org` is doing real work.** It makes duplicate uploads impossible at the database level — **no lock, no check-then-act, no race** ([[07.5 - Idempotency Keys and Deduplication]]).

⚠️ **Every index leads with `org_id`.** That is what makes RLS free and future partitioning possible ([[06.16 - Multi Tenant Data Models]]).

### Tenancy

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON documents
    USING (org_id = current_setting('app.current_org_id')::uuid);
```

```python
async with pool.acquire() as conn:
    async with conn.transaction():
        await conn.execute("SET LOCAL app.current_org_id = $1", str(org_id))
        ...
```

⚠️ **`SET LOCAL`, always, inside a transaction.** Plain `SET` behind a transaction-mode pooler leaks the tenant to the next request ([[06.9 - Connection Pooling and PgBouncer]]).

### Ingestion, inline for now

```python
async def upload(file: UploadFile, org: Organisation) -> Document:
    content = await file.read()
    hash_ = hashlib.sha256(content).digest()

    async with conn.transaction():
        doc = await repo.create(org_id=org.id, title=file.filename,
                                content_hash=hash_, size_bytes=len(content),
                                storage_key=key, status="pending")

    await storage.put(key, content)
    text = extract_text(content)                    # ⚠️ blocking, slow
    await repo.update_content(doc.id, text)         # tsvector generated column
    await repo.set_status(doc.id, "indexed")
    return doc
```

⚠️ **This is deliberately wrong and you should feel it.** A 30MB PDF blocks a worker for 20 seconds ([[01.6 - The Blocking Call Problem]]), and a crash mid-upload leaves a `pending` document forever.

💡 **Phase 2 fixes it. Measure the pain first**, so the fix has a number attached.

## The Decisions

| Decision | Alternative rejected | Because |
|---|---|---|
| Modular monolith | Microservices | One developer. No deploy coordination problem ([[10.1 - Monolith Modular Monolith Microservices]]) |
| **REST** | GraphQL | One client so far. Revisit at phase 4 ([[05.11 - REST vs GraphQL vs gRPC]]) |
| **UUIDv7** | UUIDv4, bigserial | Sequential index behaviour, non-guessable |
| **Pool + RLS** | Schema or database per tenant | Many small tenants; one migration ([[06.16 - Multi Tenant Data Models]]) |
| **Postgres FTS** | Elasticsearch | Measure first ([[06.15 - Search - Postgres vs Elasticsearch]]) |
| Object storage for files | Bytea in Postgres | Bloats backups and replication ([[06.10 - Schema Design]]) |
| **Cursor pagination** | Offset | Correct under concurrent inserts ([[05.2 - Versioning Pagination and Filtering]]) |
| Alembic, run as a job | On startup | N pods racing ([[06.11 - Zero Downtime Migrations]]) |

⚠️ **Write each of these as an ADR with a reconsideration trigger**, not just a choice.

## What Will Go Wrong

### The blocking extraction

```
30MB PDF → 20 seconds of a blocked event loop → every concurrent request stalls
```

💡 **Measure it.** Run a load test with 10% large files and **chart p99 latency against the proportion of large uploads.** That chart is the justification for phase 2.

### The connection pool

```
4 uvicorn workers × pool of 20 = 80 connections
max_connections = 100
```

⚠️ **Add one more service and you exceed it** ([[01.10 - Connection Pools and Limits]]).

**Compute the arithmetic now and write it as a startup assertion** ([[10.8 - Configuration and Secrets]]):

```python
assert settings.pool_size * settings.worker_count <= settings.db_max_connections
```

### The missing index

⚠️ **`ORDER BY created_at DESC` without `id` as a tiebreaker returns duplicate rows across pages** when timestamps collide ([[06.17 - Database Anti Patterns]]).

**Seed 5 million rows and test pagination under concurrent inserts.** It will fail without the tiebreaker.

### The N+1

```python
docs = await repo.list(org_id)
for doc in docs:
    doc.source = await sources.get(doc.source_id)      # 51 queries
```

💡 **Add a query-count assertion to your tests now**, before the codebase is large enough for this to hide ([[05.6 - The N+1 Problem and DataLoader]]).

### The `SELECT *`

⚠️ **A `content` column of 100KB fetched on every list query.** Measure the TOAST cost ([[06.2 - Postgres Architecture]]) — **it is often 40× on a list endpoint.**

## Acceptance Criteria

```
□  All nine endpoints work, with Problem Details errors
□  import-linter and database roles both block a cross-module access
□  RLS blocks a cross-tenant read, verified with RLS as the only defence
□  Cursor pagination correct under 10 inserts/second across 50 pages
□  Every list query's plan verified with EXPLAIN on 5M rows
□  Query-count assertions in every database test
□  Startup assertions for pool arithmetic and required config
□  Migrations run as a separate job; a failing migration blocks deploy
□  Duplicate upload returns the existing document, not an error
□  A cross-tenant probe test per resource type
□  Load test: known capacity number and the bottleneck named
□  p99 latency charted against large-file proportion
```

⚠️ **The last two are the ones that make phase 2 justified.** Without a measured capacity and a measured blocking cost, phase 2 is a guess.

💡 **The last answer is the most valuable.** Knowing your system's weakness, with a measurement, is what distinguishes an engineer from someone who has built something.

## Exercise

**Drill 16.2 — Build it, then find its limits**

```
conduit/phases/01/
├── src/
├── tests/{unit/, integration/, isolation/, pagination/}
├── load/{seed.py, scenarios.py, RESULTS.md}
├── measure/{blocking.py, toast.py, pool.py, PLOT.md}
├── adr/{001-monolith.md ... 008-migrations.md}
└── PHASE1.md
```

**Part 1 — Build it.** Modules, enforcement, schema, RLS, nine endpoints, cursor pagination, Problem Details errors.

**Part 2 — Seed production-scale data.** 5 million documents across 1,000 organisations, with a realistic size distribution and a skewed tenant distribution — one organisation with 30% of the data.

⚠️ **Everything measured on 10,000 rows is wrong** ([[06.4 - Reading EXPLAIN ANALYZE]]).

**Part 3 — Verify every plan.** `EXPLAIN (ANALYZE, BUFFERS)` on every list, search and detail query.

**For each: is the index used, are there heap fetches, is there a sort?**

**Then drop each index in turn and measure the cost.** Any index whose removal changes nothing should not exist.

**Part 4 — Prove isolation four ways.** Cross-tenant probe per resource type; then disable the repository scoping and confirm RLS holds; then a raw query and confirm RLS holds; then remove RLS and confirm the repository holds.

**Document which layer is load-bearing** ([[14.6 - Multi Tenant Isolation]]).

**Part 5 — Break pagination.** 50 pages at one page per second, with 10 inserts per second running concurrently.

**Count duplicated and skipped rows** with offset pagination, then with cursor pagination and a tiebreaker, then with cursor pagination *without* the tiebreaker.

**Three results. The third should surprise you.**

**Part 6 — Measure the blocking cost.** Load test with 0%, 5%, 10% and 25% large files.

**Chart p99 latency and throughput against the large-file proportion.**

**Then find your capacity:** ramp arrival rate until throughput collapses ([[11.8 - Capacity Planning and Load Testing]]).

**Name the bottleneck with evidence** — pool wait time, CPU, or event loop lag.

**Part 7 — Measure the `SELECT *` tax.** `SELECT id, title` versus `SELECT *` over 10,000 documents with a large `content` column.

**Report time, buffers, and TOAST reads.** Then fix every query that does not need `content`.

**Part 8 — Write the ADRs.** Eight of them, each citing a number from parts 3–7.

**Then write `PHASE1.md`:** what you built, what it can handle, what is wrong with it, and what phase 2 must fix.

**Done when:**
- Cross-module access is blocked by both tooling and the database
- You know which isolation layer is load-bearing, by removing the others
- Pagination without a tiebreaker demonstrably duplicates rows
- Your latency-versus-large-file chart justifies phase 2
- You have a capacity number and a named bottleneck
- Every index earns its place, verified by removal
- Eight ADRs each cite your own measurement
- `PHASE1.md` states what is wrong with the system you just built
