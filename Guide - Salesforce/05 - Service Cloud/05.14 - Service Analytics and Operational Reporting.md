# Service Analytics and Operational Reporting

## What support leaders actually watch

Not a list of every possible metric — the small set that drives decisions.

**Backlog.** Open cases, trended. Rising backlog means demand exceeds capacity, and it is the earliest warning available.

**First Response Time.** How long until a human replied. Usually the contractual number and the one customers judge you on.

**Resolution Time.** Creation to closure, excluding time waiting on the customer.

**First Contact Resolution.** Percentage resolved without a second interaction. The strongest single correlate of satisfaction.

**Reopen rate.** Cases closed and reopened. High reopen rate means cases are being closed prematurely, which is often a symptom of agents measured on closure volume.

**Case volume by reason and product.** What is actually breaking, which is what product and engineering need.

**SLA compliance.** Milestone violation rate, by customer where contracts carry penalties.

**Deflection.** Self-service resolutions that never became cases.

**CSAT.** Customer satisfaction from post-closure surveys.

Everything in the design of section 05 exists to make these computable. A `Reason` picklist nobody fills in means the third-from-last metric does not exist.

## Reports and report types

Standard report types cover Cases, Cases with Milestones, Cases with Articles, Live Chat Transcripts, and Agent Work.

**Custom report types** are where the useful reporting comes from, because the standard ones rarely join what you need. A custom report type on Case with Case Status History, or Case with Work Orders, unlocks analysis the standard types cannot express.

Two report features worth knowing well:

**Bucket fields** group values without adding a field. Priority into "Urgent" and "Normal", or case age into bands, computed at report time.

**Row-level formulas** calculate per row — the difference between two dates, a percentage — without a formula field on the object. Useful specifically because it avoids consuming a field slot and the query cost that comes with a formula field. See [[02.5 - Formula Fields]].

## The reports that matter, as queries

Backlog trend needs a snapshot object, because a report shows current state and cannot show what backlog was last Tuesday:

```java
public with sharing class ServiceSnapshotBatch implements Database.Batchable<SObject>, Schedulable {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Status, Priority, Type, OwnerId, CreatedDate
            FROM Case WHERE IsClosed = false
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Case> scope) {
        Map<String, Service_Snapshot__c> snapshots = new Map<String, Service_Snapshot__c>();
        Date today = Date.today();

        for (Case c : scope) {
            String key = c.Status + '|' + c.Priority;
            Service_Snapshot__c snapshot = snapshots.get(key);
            if (snapshot == null) {
                snapshot = new Service_Snapshot__c(
                    Snapshot_Date__c = today,
                    Status__c = c.Status,
                    Priority__c = c.Priority,
                    Case_Count__c = 0,
                    Total_Age_Days__c = 0
                );
                snapshots.put(key, snapshot);
            }
            snapshot.Case_Count__c += 1;
            snapshot.Total_Age_Days__c += c.CreatedDate.date().daysBetween(today);
        }

        insert snapshots.values();
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 2000);
    }
}
```

The same pattern as the forecast snapshot in [[04.13 - Forecasting and Revenue Management]], for the same reason: the platform shows current state, and leadership wants the trend.

Note the per-chunk aggregation caveat — a status and priority combination spanning two batch chunks produces two rows, which the reporting must sum. Acceptable, and worth knowing rather than discovering.

**Reporting Snapshots** are the declarative alternative: a scheduled job that runs a report and writes the results to a custom object. Less flexible than Apex, no code to maintain, and usually sufficient. Reach for Apex only when the aggregation is more complex than a report can express.

SLA compliance, which needs no snapshot because milestones carry their own timestamps:

```sql
SELECT Case.Account.Name customer, MilestoneType.Name milestone,
       COUNT(Id) total,
       SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) breaches
FROM CaseMilestone
WHERE Case.CreatedDate = THIS_QUARTER
GROUP BY Case.Account.Name, MilestoneType.Name
HAVING SUM(CASE WHEN IsViolated = true THEN 1 ELSE 0 END) > 0
```

The knowledge gap report, which is the highest-value single query in Service Cloud:

```sql
SELECT Reason, Product_Line__c, COUNT(Id) volume
FROM Case
WHERE ClosedDate = LAST_N_DAYS:90
  AND Id NOT IN (SELECT CaseId FROM CaseArticle)
GROUP BY Reason, Product_Line__c
ORDER BY COUNT(Id) DESC
LIMIT 20
```

High-volume case reasons with no article attached tells you exactly what to write next. See [[05.10 - Salesforce Knowledge]].

## Dashboards for different audiences

The same data serves three audiences with different needs, and building one dashboard for all three serves none.

**Agent dashboard.** My open cases, my cases breaching soon, my closures this week. Individual and immediate.

**Team lead dashboard.** Queue depth, longest waiting case, agent workload, escalations today. Operational and live — this is the one that should be on a wall screen.

**Executive dashboard.** Backlog trend, SLA compliance, CSAT, volume by product. Trended and aggregated, with no individual agent names.

That last point is worth stating: putting individual agent metrics on an executive dashboard changes behaviour in ways that are rarely intended. Agents optimize for whatever is visible to leadership, and closure count is the easiest metric to game.

## Omni-Channel Supervisor

A purpose-built live view: agents online, current presence status, work in progress, queue depth, and longest waiting item.

This is the tool team leads use during the day, and it needs no building. Configuring it properly — the right queues, the right agent groups — is a setup task worth doing rather than leaving to defaults.

## CRM Analytics and external warehouses

Standard reports handle most operational reporting. Two situations push beyond them:

**Cross-source analysis.** Correlating case volume with product telemetry, or with warranty cost from the ERP. Salesforce reports cannot join across systems.

**Very large volumes.** Reports on tens of millions of case records are slow, and the underlying queries hit selectivity problems. See [[23.6 - Query Performance at Scale]].

The options are CRM Analytics, which builds its own datasets from replicated CRM data, or a data warehouse fed from Salesforce.

The design point: **do not build heavy analytical queries in Apex against the transactional objects.** A batch job aggregating five years of cases will time out, and the correct answer is to move the analysis to a system designed for it.

## Survey and CSAT

Salesforce Feedback Management, or a third-party survey tool, sends a survey on case closure and writes the response back.

Two design details that determine whether the data is usable:

**Do not survey every case.** Response rates fall, and customers get annoyed. Sampling — every fifth case, or all cases above a priority threshold — produces better data and less irritation.

**Link the response to the case, agent, product, and reason.** A satisfaction score with no dimensions is a number nobody can act on. With dimensions it tells you which product line, which case type, or which process produces unhappy customers.

## Practical guidance

**Build the backlog snapshot early.** The trend is the metric, and it cannot be reconstructed retroactively.

**Run the knowledge gap report monthly.** It is one query and it directs the whole knowledge programme.

**Separate agent, team lead, and executive dashboards.**

**Keep individual metrics off executive dashboards.** What is measured is optimized, including in unhelpful ways.

**Sample surveys rather than sending them all.**

**Move heavy analysis off the transactional objects** before volume forces it.

**Measure reopen rate.** It is the counterweight to closure volume, and without it closure targets produce prematurely closed cases.
