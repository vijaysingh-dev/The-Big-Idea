# Concurrent Rendering and the Scheduler

Concurrent rendering means React can work on **several versions of the UI at once**, prioritize between them, and abandon work that is no longer needed. It is not multithreading — everything still runs on the single main thread ([[01.4 - The Event Loop]]).

The capability is that rendering became interruptible when Fiber replaced recursion with a resumable work loop ([[18.3 - Fiber Architecture]]).

## The problem

```jsx
function Search() {
  const [query, setQuery] = useState("");
  const results = filterHugeList(query);   // 300ms

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <Results items={results} />
    </>
  );
}
```

Every keystroke triggers a 300ms synchronous render. The input freezes, characters appear late, and the app feels broken — a classic long task ([[13.5 - Core Web Vitals]]).

Both updates — the input's value and the results list — were treated as equally urgent. They are not.

## Marking work as non-urgent

```jsx
const [query, setQuery] = useState("");
const [results, setResults] = useState([]);
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  setQuery(e.target.value);                    // urgent — input must respond
  startTransition(() => {
    setResults(filterHugeList(e.target.value)); // non-urgent — can be interrupted
  });
}
```

Now React commits the input update immediately, then begins rendering the results at transition priority. If another keystroke arrives mid-render, React discards the in-progress results render and starts over with the new query.

The input never blocks. `isPending` lets you show a subtle loading state during the transition ([[22.4 - useTransition and startTransition]]).

## How yielding works

React's scheduler slices work into ~5ms chunks:

```js
function workLoopConcurrent() {
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
}

function shouldYield() {
  return getCurrentTime() >= deadline;   // ~5ms slice
}
```

After each unit of work — roughly one fiber — React checks whether its time slice has expired. If so, it yields to the browser, which can paint and process input, then schedules a continuation.

The continuation is scheduled with `MessageChannel` rather than `setTimeout`, because `setTimeout` is clamped to 4ms after nested calls ([[01.5 - Web APIs and the Task Queue]]). A `postMessage` to yourself creates a task boundary with no clamp. Newer browsers offer `scheduler.postTask` and `scheduler.yield`, which React is moving toward.

Note that yielding after each fiber means a **single very slow component** still blocks — the granularity is one component, not one millisecond. A component doing 200ms of synchronous work cannot be interrupted mid-function.

## Lanes and priority

Updates are assigned lanes based on how they were triggered ([[18.3 - Fiber Architecture]]):

```
SyncLane            click, keypress, input — must feel instant
InputContinuousLane drag, scroll, hover
DefaultLane         normal setState outside an event
TransitionLane      startTransition
IdleLane            offscreen, prerendering
```

React renders the highest-priority pending lanes first. A transition render in progress is interrupted when a discrete input update arrives.

Lanes are a bitmask, so React can express and test sets of priorities with single bitwise operations — which is why they replaced the earlier expiration-timestamp model.

## Automatic batching

React 18 extended batching to everywhere, not just React event handlers:

```jsx
setTimeout(() => {
  setA(1);
  setB(2);
}, 0);   // React 17: two renders. React 18: one.
```

Promises, native event handlers and timeouts all batch now ([[18.6 - Batching and the Update Queue]]).

## Suspense

Concurrent rendering is what makes Suspense work. A component that suspends does not force React to throw away the whole tree:

```jsx
<Suspense fallback={<Skeleton />}>
  <Comments />
</Suspense>
```

React can keep the previous UI on screen while rendering the new one in the background, and only swap when it is ready — avoiding the "flash of loading spinner" on navigation. Wrapping the navigation in a transition tells React to prefer the old content over a fallback ([[19.4 - Suspense]]).

## Tearing

The genuine hazard concurrent rendering introduces.

If a component reads a **mutable external value** during render, and the render is interrupted while that value changes, two components can observe different values and commit together:

```
Component A renders → reads store.count === 5
   → interrupted; store mutates to 6
Component B renders → reads store.count === 6
   → both commit → UI shows 5 in one place, 6 in another
```

React state cannot tear, because React controls it. External stores can. This is exactly why `useSyncExternalStore` exists — it forces a consistent snapshot and re-renders from scratch if the store changed mid-render ([[17.12 - Lesser Known Hooks]]).

Every store library now builds on it, which is why Redux, Zustand and Jotai are concurrent-safe without you doing anything.

## Purity is the precondition

If a render can be discarded or repeated, any side effect during render happens without a corresponding commit and cannot be undone ([[16.5 - Rendering and Purity]]).

Strict Mode's double-invocation exists to surface exactly these violations in development ([[18.7 - Strict Mode and Double Invocation]]).

## What you get without doing anything

Simply upgrading to React 18+ with `createRoot` gives you automatic batching and a concurrent-capable renderer. The opt-in features — `useTransition`, `useDeferredValue`, streaming SSR with Suspense — must be used deliberately.

Concurrent rendering is not a blanket speedup. It does not make renders faster; it makes them **interruptible**, which improves responsiveness. If the total work is too large, it is still too large — the fix is doing less work (virtualization, memoization, moving work off-thread), not scheduling it differently.

## How senior engineers actually use this

**They reach for transitions when an update is expensive but not urgent** — search filtering, tab switching, chart re-rendering, route changes.

**They do not use transitions to fix genuinely slow code.** A 2-second render wrapped in a transition is still a 2-second render; it just stops blocking input.

**They use `useSyncExternalStore` for any external subscription**, since tearing is otherwise a real possibility.

**They keep renders pure**, understanding it as an architectural requirement rather than a lint rule.

## Common pitfalls

- Expecting concurrent rendering to make the application faster on its own.
- Wrapping urgent updates (input values, clicks) in transitions, making them feel laggy.
- Subscribing to external state with `useState` + `useEffect`, risking tearing.
- Side effects during render, which discarded renders leave stranded.
- Assuming a component renders exactly once per commit.
- One very slow component blocking despite time slicing — yielding is per fiber, not mid-function.

## Interview angle

"What is concurrent rendering" should get: rendering is interruptible, so React can prioritize urgent updates over non-urgent ones, pause and resume work, and discard renders that are superseded. Make clear it is not multithreading and not a speedup — it is a responsiveness mechanism. The strong follow-ups are the concrete `useTransition` search example, the ~5ms time slicing with `MessageChannel` scheduling, and tearing as the new hazard that `useSyncExternalStore` addresses.
