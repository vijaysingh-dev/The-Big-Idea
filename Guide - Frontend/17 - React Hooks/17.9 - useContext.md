# useContext

Context passes a value down the tree without threading it through every intermediate component's props.

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Layout />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext);
  return <button className={theme} />;
}
```

React 19 allows the provider without `.Provider`:

```jsx
<ThemeContext value="dark">
```

## How lookup works

`useContext` walks **up** the tree from the calling component to find the nearest matching provider. If none exists, it returns the default passed to `createContext`.

```jsx
const Ctx = createContext("default");   // used only when there is NO provider above
```

That default is a frequent source of confusion: it does not apply when a provider exists with `value={undefined}` — in that case the value genuinely is `undefined`.

A common guard:

```jsx
const ThemeContext = createContext(null);

function useTheme() {
  const value = useContext(ThemeContext);
  if (value === null) throw new Error("useTheme must be used within ThemeProvider");
  return value;
}
```

Exporting a custom hook instead of the raw context is standard practice — it centralizes the guard, gives a better error message, and keeps the context object private so consumers cannot create their own provider by accident.

## The re-render behavior

**Every consumer re-renders when the provider's value changes**, compared with `Object.is`. Not just consumers whose part of the value changed — all of them.

```jsx
// New object every render → every consumer re-renders on every App render
<Ctx.Provider value={{ user, setUser }}>

// Stable
const value = useMemo(() => ({ user, setUser }), [user]);
<Ctx.Provider value={value}>
```

Forgetting the memo is the single most common context performance bug, and it is invisible until you profile ([[17.6 - useMemo]]).

Note `React.memo` does **not** stop context-driven re-renders. A memoized component that calls `useContext` still re-renders when the context value changes — memo compares props, and context is not a prop.

## Splitting contexts

Because consumers cannot subscribe to part of a value, mixing rarely-changing and frequently-changing data in one context re-renders everything on every change:

```jsx
// Bad — theme consumers re-render whenever the cursor moves
<AppContext.Provider value={{ theme, user, cursorPosition }}>
```

Split by change frequency:

```jsx
<ThemeContext value={theme}>
  <UserContext value={user}>
    <CursorContext value={cursor}>
```

A particularly effective split separates **state** from **dispatch**:

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <StateContext value={state}>
      <DispatchContext value={dispatch}>{children}</DispatchContext>
    </StateContext>
  );
}
```

`dispatch` from `useReducer` is guaranteed stable, so components that only dispatch never re-render on state changes. That covers a lot of buttons and forms ([[17.10 - useReducer]]).

## Context is not a state manager

Context is a **dependency injection** mechanism. It does not store state, batch updates, memoize selectors, or support subscribing to a slice.

For state that changes frequently or is read by many components, a store library provides selector-based subscriptions so only components reading the changed slice re-render:

```jsx
const count = useStore(s => s.count);   // re-renders only when count changes
```

Zustand, Jotai and Redux all work this way ([[20.8 - Zustand Jotai and Modern Alternatives]]). The common pattern is context to *provide* the store instance, and the store's own subscription mechanism for reads.

Context is a good fit for: theme, locale, current user, feature flags, a router instance, a query client — values that are read widely and change rarely.

## Try composition first

Context is often reached for to solve prop drilling that composition solves better:

```jsx
// Drilling
<Page user={user}><Sidebar user={user}><Profile user={user} /></Sidebar></Page>

// Composition — no drilling, no context
<Page sidebar={<Sidebar><Profile user={user} /></Sidebar>} />
```

Passing elements as props flattens the tree and avoids the indirection entirely ([[16.3 - Components and Props]]). The official guidance is explicit: try passing props, then try composition, then use context.

Two or three levels of drilling is not a problem worth solving.

## Nesting and overriding

```jsx
<ThemeContext value="dark">
  <Section>
    <ThemeContext value="light">
      <Button />   {/* light */}
    </ThemeContext>
  </Section>
</ThemeContext>
```

Nearest provider wins. This is genuinely useful for scoped overrides — a light-themed modal inside a dark app, or a nested form with its own validation context.

## use() for reading context

React 19's `use` can read context conditionally:

```jsx
function Heading({ children }) {
  if (children == null) return null;
  const theme = use(ThemeContext);    // legal after an early return
  return <h1 className={theme}>{children}</h1>;
}
```

Unlike `useContext`, it is exempt from the rules of hooks ([[17.1 - Rules of Hooks and How They Work]]) and can be called inside conditions and loops.

## Server Components

Context requires state and interactivity, so it works only in Client Components. A Server Component cannot call `useContext` or render a provider directly ([[22.8 - Server Components]]).

The pattern is a client provider component wrapping server-rendered children:

```jsx
// providers.tsx — "use client"
export function Providers({ children }) {
  return <ThemeContext value={theme}>{children}</ThemeContext>;
}
```

Children passed through remain server components; only the provider itself is client-side.

## How senior engineers actually use this

**They memoize every provider value**, as a reflex.

**They split contexts by change frequency**, and separate state from dispatch.

**They export a custom hook, not the context object**, with a guard for missing providers.

**They use context for injection and a store for state.** Context providing a store instance is the common production shape.

**They reach for composition before context** when the problem is prop drilling through two or three levels.

## Common pitfalls

- Unmemoized provider values re-rendering every consumer.
- One large context mixing fast- and slow-changing data.
- Expecting `React.memo` to block context updates.
- Using context as a global state manager for frequently-changing values.
- Relying on `createContext`'s default when a provider exists with `undefined`.
- Reaching for context to avoid two levels of prop passing.
- Rendering a provider in a Server Component.

## Interview angle

"Context API vs Redux" is the standard question, and the strong answer distinguishes their purposes rather than comparing features: context is dependency injection with no subscription granularity — every consumer re-renders on any value change — while a store provides selector-based subscriptions so only affected components re-render. Add the memoized-value requirement and the state/dispatch split as concrete mitigations, and note that composition often removes the need for context entirely.
