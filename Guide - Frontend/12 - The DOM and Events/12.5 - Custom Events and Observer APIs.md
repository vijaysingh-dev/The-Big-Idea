# Custom Events and Observer APIs

Observers let the browser tell you when something changed, instead of you polling for it. Each one replaces a category of scroll or resize handler that used to force layout on every frame.

## IntersectionObserver

Fires when an element enters or leaves a viewport or ancestor's bounds — asynchronously, off the main thread, with no layout reads.

```js
const observer = new IntersectionObserver(
  (entries) => {
    for (const entry of entries) {
      if (entry.isIntersecting) {
        entry.target.classList.add("visible");
        observer.unobserve(entry.target);   // one-shot
      }
    }
  },
  {
    root: null,              // null = viewport; or a scrollable ancestor
    rootMargin: "0px 0px 200px 0px",   // grow the trigger area 200px below
    threshold: 0,            // 0 = any pixel; 1 = fully visible; array for multiple
  }
);

document.querySelectorAll(".fade-in").forEach(el => observer.observe(el));
```

The three options do a lot of work:

- **`rootMargin`** expands or shrinks the detection box. Positive bottom margin triggers *before* an element is visible — how infinite scroll loads the next page early enough to feel seamless.
- **`threshold`** is the fraction of the element that must be visible. `[0, 0.25, 0.5, 0.75, 1]` gives progress-style callbacks.
- **`entry.intersectionRatio`** gives the current fraction, and `entry.boundingClientRect` gives the measurement without you forcing a layout.

The canonical uses: infinite scroll sentinels, lazy loading (though `loading="lazy"` covers images natively now), scroll-triggered animations, ad and impression tracking, and sticky-header state.

```js
// Infinite scroll sentinel
const sentinel = document.querySelector("#sentinel");
new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting) loadNextPage();
}, { rootMargin: "400px" }).observe(sentinel);
```

Compared with a scroll handler calling `getBoundingClientRect()`, this does not run per scroll event and does not force synchronous layout ([[13.3 - Layout Thrashing]]).

## ResizeObserver

Fires when an element's size changes — for any reason, including content changes, CSS changes and container resizes that `window.resize` never sees.

```js
const ro = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const { inlineSize, blockSize } = entry.contentBoxSize[0];
    entry.target.dataset.narrow = inlineSize < 400;
  }
});

ro.observe(chartContainer);
ro.observe(el, { box: "border-box" });
```

The measurement arrives in the entry, so you never call `getBoundingClientRect()` yourself.

The classic error is the resize loop: changing an observed element's size inside the callback triggers the callback again. The browser detects this and logs "ResizeObserver loop completed with undelivered notifications", skipping the extra frame. If you must resize in response, guard it:

```js
const ro = new ResizeObserver((entries) => {
  requestAnimationFrame(() => {
    // deferring breaks the synchronous loop
    adjust(entries);
  });
});
```

Container queries now handle most *styling* responses to element size declaratively ([[11.3 - Responsive Design]]), so `ResizeObserver` is best reserved for cases needing JavaScript — canvas resizing, chart libraries, virtualized list measurement, text truncation detection.

## MutationObserver

Fires when the DOM tree changes.

```js
const mo = new MutationObserver((mutations) => {
  for (const m of mutations) {
    if (m.type === "childList") {
      m.addedNodes.forEach(enhance);
    }
    if (m.type === "attributes") {
      console.log(m.attributeName, m.oldValue);
    }
  }
});

mo.observe(container, {
  childList: true,
  subtree: true,
  attributes: true,
  attributeFilter: ["data-state"],
  attributeOldValue: true,
  characterData: true,
});

mo.disconnect();
mo.takeRecords();   // drain pending records without waiting
```

Callbacks are delivered as **microtasks** ([[01.6 - Microtasks vs Macrotasks]]), so they run before the next paint but after the current task — batched, not per-mutation.

Legitimate uses are narrower than the other two: enhancing third-party or CMS-injected content, browser extensions, detecting when a library's element finally appears, and syncing with a non-React widget. In your own application code, if you control the mutation, react at the source instead.

Watch `subtree: true` on a large container — it fires for every descendant change and can become expensive. Use `attributeFilter` and the narrowest possible root.

## PerformanceObserver

Reports performance entries as they are recorded — the correct way to collect Core Web Vitals ([[13.5 - Core Web Vitals]]).

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report(entry.name, entry.startTime, entry.duration);
  }
}).observe({ type: "largest-contentful-paint", buffered: true });
```

`buffered: true` delivers entries recorded *before* the observer was created, which matters because LCP and FCP happen early. Entry types include `largest-contentful-paint`, `layout-shift`, `event` (for INP), `longtask`, `navigation`, `resource` and `paint`.

In practice, use the `web-vitals` library rather than assembling this by hand — the metric definitions have subtleties (which LCP candidate counts, how CLS sessions are windowed) that are easy to get wrong.

## Custom events

```js
class Cart extends EventTarget {
  add(item) {
    this.items.push(item);
    this.dispatchEvent(new CustomEvent("change", { detail: { count: this.items.length } }));
  }
}

const cart = new Cart();
cart.addEventListener("change", e => render(e.detail.count));
```

Extending `EventTarget` gives any object the full listener API — including `{ once }` and `{ signal }` — for free. This is a clean way to build an observable model without a library.

For DOM-dispatched events:

```js
el.dispatchEvent(new CustomEvent("widget:ready", {
  detail: { id },
  bubbles: true,
  composed: true,
}));
```

Remember `bubbles` defaults to `false`, unlike native events, and `composed: true` is required to cross a shadow DOM boundary.

`dispatchEvent` is synchronous — handlers complete before it returns.

## Cleanup

Every observer holds strong references to what it observes ([[07.3 - Memory Leaks from Listeners and Detached DOM]]):

```jsx
useEffect(() => {
  const observer = new IntersectionObserver(callback);
  const el = ref.current;
  if (el) observer.observe(el);
  return () => observer.disconnect();
}, []);
```

`disconnect()` stops all observations; `unobserve(el)` stops one. Capturing `ref.current` into a local variable matters — reading it inside the cleanup can give a different (or null) value by the time cleanup runs.

## Choosing

| Question | API |
| --- | --- |
| Is this element visible? | IntersectionObserver |
| Did this element's size change? | ResizeObserver (or container queries) |
| Did the DOM structure change? | MutationObserver |
| How is the page performing? | PerformanceObserver |
| Did my application state change? | a store, not an observer |

The last row matters: observers watch the *browser*. Watching your own state with a `MutationObserver` because it is easier than plumbing a callback is a design smell.

## How senior engineers actually use this

**They replace scroll handlers with `IntersectionObserver`** as a default. It is cheaper, more accurate, and does not need throttling.

**They use `rootMargin` deliberately** to trigger work early enough that the user never sees a loading state during infinite scroll.

**They prefer container queries to `ResizeObserver`** for anything purely visual, and keep the observer for measurement that JavaScript genuinely needs.

**They treat `MutationObserver` as an integration tool**, not an application pattern.

**They always disconnect in cleanup**, and they reuse a single observer instance across many elements rather than creating one per element — an observer can observe any number of targets.

## Common pitfalls

- Creating one `IntersectionObserver` per element instead of one observer with many targets.
- Forgetting `disconnect()`, leaking observed elements.
- ResizeObserver loops from resizing inside the callback.
- `MutationObserver` with `subtree: true` on a large container, firing constantly.
- Expecting a custom event to bubble when `bubbles` was not set.
- Missing `buffered: true` on a PerformanceObserver and losing early entries.
- Observing an element before it is mounted, so `observe()` receives `null`.

## Interview angle

`IntersectionObserver` comes up in "how would you implement infinite scroll" and "how would you lazy-load images" — the expected answer contrasts it with scroll handlers on the grounds that it is asynchronous, off the main thread, and requires no layout reads. `rootMargin` for early triggering is the detail that shows real use. `ResizeObserver` appears in "how would you make a chart responsive", and mentioning container queries as the declarative alternative signals current knowledge.
