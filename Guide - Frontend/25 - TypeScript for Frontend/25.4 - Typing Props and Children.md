# Typing Props and Children

## The baseline

```tsx
type ButtonProps = {
  label: string;
  onClick: () => void;
  variant?: "primary" | "ghost";
  children?: React.ReactNode;
};

function Button({ label, onClick, variant = "primary", children }: ButtonProps) {
  return <button onClick={onClick}>{children ?? label}</button>;
}
```

Annotate the destructured parameter. That is the whole pattern for most components.

## Why not React.FC

```tsx
const Button: React.FC<ButtonProps> = ({ label }) => { ... };
```

Historically it added an implicit `children` prop, so a component that should not accept children silently did. That was removed in React 18's types, but two objections remain:

**It cannot express generics.** `React.FC<Props<T>>` does not work, so any generic component has to abandon it — leading to inconsistency within a codebase.

**It adds nothing.** The return type is inferred correctly without it, and `FC` mainly constrains what the component can return.

The current convention is a plain function with an annotated parameter.

## children

```tsx
children: React.ReactNode        // anything renderable — the default choice
children: React.ReactElement     // exactly one element
children: string                 // text only
children: (value: T) => ReactNode // render prop
children: ReactNode[]            // avoid — a single child is not an array
```

`ReactNode` covers elements, strings, numbers, `null`, `undefined`, booleans and arrays of those. It is what you want unless there is a specific reason to narrow.

`JSX.Element` is narrower than `ReactNode` and rejects strings, which surprises people who use it for `children`.

Note that TypeScript cannot enforce *which* components appear as children:

```tsx
type TabsProps = { children: ReactElement<typeof Tab>[] };   // does NOT actually check
```

React's type system has no way to validate child component types. Runtime validation or a compound-component context guard is the practical alternative ([[22.6 - Compound Components]]).

## Inheriting native props

```tsx
import type { ComponentPropsWithoutRef, ComponentPropsWithRef } from "react";

type ButtonProps = {
  variant?: "primary" | "ghost";
} & ComponentPropsWithoutRef<"button">;

function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}
```

This inherits `onClick`, `disabled`, `type`, every `aria-*` and every `data-*` attribute without enumeration — and keeps them correct as React's types evolve ([[25.3 - Utility Types]]).

**Overriding a native prop requires `Omit` first:**

```tsx
type InputProps = Omit<ComponentPropsWithoutRef<"input">, "onChange" | "value"> & {
  value: number;
  onChange: (value: number) => void;
};
```

Without the `Omit`, the intersection of two incompatible `onChange` signatures produces `never`, and every call site fails with a confusing error. This is the most common typing bug in component libraries.

To extend another component's props:

```tsx
type Props = ComponentProps<typeof CustomInput> & { label: string };
```

## Refs

In React 19, `ref` is a normal prop ([[22.3 - forwardRef and useImperativeHandle]]):

```tsx
type InputProps = ComponentPropsWithRef<"input"> & { label: string };

function Input({ label, ref, ...rest }: InputProps) {
  return <input ref={ref} {...rest} />;
}
```

Pre-19, with `forwardRef`:

```tsx
const Input = forwardRef<HTMLInputElement, InputProps>(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});
```

Note the argument order — element type first, props second — which is the reverse of what most people guess.

## Discriminated union props

The most valuable typing pattern for components with mutually exclusive modes:

```tsx
type AlertProps =
  | { variant: "error"; error: Error; onRetry: () => void }
  | { variant: "success"; message: string }
  | { variant: "info"; message: string; dismissible?: boolean };

function Alert(props: AlertProps) {
  switch (props.variant) {
    case "error":
      return <div>{props.error.message} <button onClick={props.onRetry} /></div>;
    case "success":
      return <div>{props.message}</div>;   // props.error would be an error here
  }
}
```

Invalid combinations become unrepresentable — you cannot pass `error` with `variant="success"` — and narrowing inside the component is automatic ([[25.6 - Discriminated Unions and Narrowing]]).

This replaces the pattern of many optional props where only certain combinations are valid, which is the shape that produces runtime bugs.

The same technique enforces "either A or B, not both":

```tsx
type LinkProps =
  | { href: string; onClick?: never }
  | { onClick: () => void; href?: never };
```

`?: never` makes the excluded prop a compile error rather than silently ignored.

## Generic components

```tsx
type ListProps<T> = {
  items: T[];
  renderItem: (item: T, index: number) => React.ReactNode;
  getKey: (item: T) => string;
};

function List<T>({ items, renderItem, getKey }: ListProps<T>) {
  return <ul>{items.map((item, i) => <li key={getKey(item)}>{renderItem(item, i)}</li>)}</ul>;
}

<List
  items={products}
  getKey={(p) => p.id}           // p inferred as Product
  renderItem={(p) => p.name}     // fully typed, no annotations
/>
```

Type flows from `items` through every callback. In a `.tsx` file, an arrow function needs `<T,>` to disambiguate from JSX ([[25.2 - Generics]]).

## Polymorphic components

A component that can render as different elements:

```tsx
type PolymorphicProps<E extends React.ElementType> = {
  as?: E;
  children?: React.ReactNode;
} & Omit<React.ComponentPropsWithoutRef<E>, "as" | "children">;

function Text<E extends React.ElementType = "span">({
  as,
  ...rest
}: PolymorphicProps<E>) {
  const Component = as ?? "span";
  return <Component {...rest} />;
}

<Text as="a" href="/about">About</Text>      // href is valid
<Text as="button" href="/about" />           // Error — button has no href
```

Genuinely useful for design systems, and genuinely awkward to type correctly with refs added. The `asChild` composition pattern from Radix avoids most of this complexity and is often the better choice ([[22.6 - Compound Components]]).

## Event handlers

```tsx
onClick: React.MouseEventHandler<HTMLButtonElement>;
onChange: React.ChangeEventHandler<HTMLInputElement>;
onSubmit: (e: React.FormEvent<HTMLFormElement>) => void;
onKeyDown: React.KeyboardEventHandler<HTMLInputElement>;
```

The `*EventHandler` aliases are shorter than writing the function signature, and the element type parameter is what makes `e.currentTarget` correctly typed ([[25.5 - Typing Events Refs and Hooks]]).

## Default props

```tsx
function Card({ padding = "md", items = EMPTY }: CardProps) {}
```

`defaultProps` is deprecated for function components. Destructuring defaults is the replacement.

One hazard: a default object or array literal creates a new reference every render, breaking memoization and dependency arrays. Hoist it to module scope ([[16.3 - Components and Props]]).

## Common typing errors

```tsx
// children typed as JSX.Element rejects strings
type Props = { children: JSX.Element };
<Wrapper>text</Wrapper>            // Error

// Overriding without Omit
type Props = ComponentProps<"input"> & { onChange: (v: string) => void };
// onChange becomes never

// Optional prop accessed without a guard
function C({ user }: { user?: User }) {
  return <p>{user.name}</p>;       // Error — object is possibly undefined
}
```

## How senior engineers actually use this

**They inherit native props** with `ComponentPropsWithoutRef` on every component wrapping a DOM element, so consumers are never blocked on a missing prop.

**They use discriminated unions for variant props**, making invalid combinations uncompilable.

**They avoid `React.FC`**, for consistency with generic components.

**They omit before overriding**, without exception.

**They export prop types** from component modules, since consumers need them for wrappers and tests.

## Common pitfalls

- `React.FC` breaking on generic components.
- Overriding a native prop without `Omit`, producing `never`.
- `JSX.Element` for `children`, rejecting strings.
- `ReactNode[]` for children, when a single child is not an array.
- Believing `ReactElement<typeof Tab>` validates child component types — it does not.
- Default object literals in destructuring, breaking referential stability.
- `<T>` in a `.tsx` arrow function parsed as JSX.

## Interview angle

"How do you type React props" moves quickly past the basics. The material worth raising: inheriting native props with `ComponentPropsWithoutRef` and the `Omit`-before-override requirement, discriminated unions to make invalid prop combinations unrepresentable, and why `React.FC` fell out of favour — it cannot express generics. A generic list component whose `renderItem` is typed from `items` is the clearest demonstration of type flow.
