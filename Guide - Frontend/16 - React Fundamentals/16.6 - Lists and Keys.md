# Lists and Keys

```jsx
{items.map(item => <Row key={item.id} item={item} />)}
```

A `key` tells React which element in the new list corresponds to which element in the old one. Without it, React can only match by position.

## What keys actually do

During reconciliation, React compares the previous children with the new ones ([[18.2 - Reconciliation and the Diffing Algorithm]]). For a list, the default heuristic is positional: first child matched to first child, second to second.

Keys override that with **identity**. React builds a map from key to element and matches by key, so an element that moved is *moved*, not destroyed and recreated.

The practical difference:

```
Before:  [A, B, C]
After:   [Z, A, B, C]

Without keys (positional):
  slot 0: A -> Z   (update)
  slot 1: B -> A   (update)
  slot 2: C -> B   (update)
  slot 3: new C    (create)
  => 4 operations, and every component's state shifts to a different item

With keys:
  Z is new     (create)
  A, B, C match existing keys  (move)
  => 1 creation
```

## Why index keys break things

```jsx
{items.map((item, i) => <Row key={i} item={item} />)}
```

`key={i}` is exactly equivalent to no key at all — position is the identity again. It is fine when the list is static and never reordered, filtered or prepended to. Otherwise it produces a specific class of bug.

The problem is that React reuses the **component instance** for a key, keeping its state and DOM. If item identity shifts under a stable key, state attaches to the wrong item:

```jsx
{todos.map((todo, i) => (
  <li key={i}>
    <input type="checkbox" />
    {todo.text}
  </li>
))}
```

Check the second checkbox, then delete the first todo. The list re-renders with the remaining items at new indices — but React sees `key={1}` still exists, so it keeps that DOM node and its checked state. The checkbox now appears checked next to a different todo.

The same bug hits uncontrolled inputs (text typed into row 2 appears in row 1 after a delete), focus, scroll position inside rows, CSS transitions, and any local state inside the row component.

It is invisible in a read-only list and appears the moment the list becomes editable — which is why it so often ships.

## What makes a good key

**Stable** — the same item gets the same key across renders.
**Unique among siblings** — not globally unique, just within that array.
**Derived from the data**, not from the render.

```jsx
key={item.id}                                  // best
key={`${item.type}-${item.id}`}                // composite, for merged lists
key={item.slug}
key={JSON.stringify(item)}                     // works but expensive and brittle
key={Math.random()}                            // catastrophic
key={crypto.randomUUID()}                      // catastrophic
```

A random key changes every render, so React destroys and recreates every element every time — losing all state, all DOM, all focus, and doing maximum work.

If the data genuinely has no id, generate one **when the item is created**, not during render:

```jsx
setItems(items => [...items, { id: crypto.randomUUID(), text }]);
```

## Keys on fragments

When mapping produces multiple sibling elements, the key goes on a `Fragment` in its long form:

```jsx
{entries.map(entry => (
  <React.Fragment key={entry.id}>
    <dt>{entry.term}</dt>
    <dd>{entry.definition}</dd>
  </React.Fragment>
))}
```

The shorthand `<>` cannot take a key.

## Keys are not props

```jsx
function Row({ key, item }) {   // key is undefined
  return <li>{item.name}</li>;
}
```

`key` is consumed by React and not passed through. If the component needs the identifier, pass it separately:

```jsx
<Row key={item.id} id={item.id} item={item} />
```

React warns about this in development.

## Key as a reset mechanism

The same identity rule works deliberately outside lists:

```jsx
<ProfileForm key={userId} user={user} />
```

Changing the key unmounts the old instance and mounts a fresh one with fresh state. This is the idiomatic way to reset a form when the selected entity changes, and it replaces an effect that manually resets every field ([[16.4 - State and useState Mental Model]]).

Useful variants: resetting an error boundary after a retry, remounting a chart when its dimensions change categorically, and forcing a video element to reload on source change.

## Keys and animation

Exit animations depend entirely on stable keys — a library like Framer Motion tracks which elements left by comparing keys between renders. Index keys make an item "become" a different item rather than leaving, so exit animations play on the wrong element or not at all.

## Performance

Keys do not make React faster in general; they make it **correct** and avoid unnecessary DOM work when lists change. For a list that only ever appends, index keys and id keys produce nearly identical work.

The real performance lever for large lists is not keys but rendering fewer of them — virtualization ([[19.5 - Virtualization and Windowing]]).

One relevant detail: React's list diffing does not compute an optimal minimal edit script. It is a single-pass heuristic, so a full reversal of a keyed list produces many moves. This is rarely worth worrying about, but it explains why some benchmarks show React handling reorders less efficiently than fine-grained reactive frameworks.

## How senior engineers actually use this

**They require a stable id in the data model.** If the API does not provide one, that is a conversation with the backend, not a workaround with indices.

**They allow index keys only for static lists** — a fixed set of tabs, a rendered constant array — and lint for it otherwise (`react/no-array-index-key`).

**They use `key` deliberately for resets**, which removes a category of synchronizing effects.

**They check keys first** when debugging "state attached to the wrong row", "input lost focus", or "the wrong item animated out". It is the cause more often than anything else.

## Common pitfalls

- `key={index}` on a list that can be reordered, filtered or prepended.
- `key={Math.random()}` destroying and recreating everything.
- Missing keys entirely, falling back to positional matching.
- Expecting to read `key` as a prop.
- Key on the inner element instead of the outermost element returned by `map`.
- Non-unique keys among siblings, producing duplicate-key warnings and unpredictable matching.
- Generating ids during render instead of at creation time.

## Interview angle

"Why are keys important" and "why shouldn't you use array indexes as keys" are near-guaranteed. Explain that keys give React element identity so it can match, move and preserve state across renders instead of matching by position — then give the concrete failure: delete an item from the middle of a list with index keys and the local state of subsequent rows shifts to the wrong items. Mentioning `key` as a deliberate reset mechanism shows understanding beyond the memorized answer.
