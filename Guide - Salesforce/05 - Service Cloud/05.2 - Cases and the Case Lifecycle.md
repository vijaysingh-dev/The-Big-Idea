# Cases and the Case Lifecycle

## Designing the status model

The status list is to Service Cloud what the stage list is to Sales Cloud: the decision everything else depends on, and expensive to change later because it invalidates historical reporting.

A model that works:

```
New                → created, nobody has touched it
In Progress        → an agent is actively working it
Awaiting Customer  → waiting on the customer for information
Awaiting Third Party → waiting on a supplier, partner, or engineering
Resolved           → agent believes it is fixed, awaiting confirmation
Closed             → confirmed complete
```

Each of the waiting statuses exists for a specific reason.

**Awaiting Customer is the most important status in any support model.** Without it, every duration metric charges the team for time the customer was sitting on a question. Support leaders who cannot separate those two numbers cannot manage the team, and this single status is the difference.

**Awaiting Third Party** does the same for supplier and engineering delays, which in a manufacturing context is a large fraction of total elapsed time — waiting for a part to ship is not the support team failing.

**Resolved versus Closed** matters when customers get a window to reopen. Resolved stops the clock; Closed is final after the window passes.

The design principle: **status describes the state of the case, not the last action taken.** "Agent Called Customer" is an activity, not a status. Statuses answer "who are we waiting for and what happens next".

## Status configuration

Statuses live in a **Support Process**, tied to a Record Type. Each status is marked as Closed or not, which drives the read-only `IsClosed` and `ClosedDate` fields.

Deciding which statuses count as closed has consequences beyond reporting: milestones stop on closure, escalation rules stop evaluating, and entitlement consumption stops. Marking Resolved as closed and Closed as closed produces different metrics than marking only Closed, and the business needs to choose deliberately.

## The fields that carry the analytics

Three picklists do most of the work, and all three are commonly neglected:

**`Type`** — the nature of the request. Problem, Question, Feature Request, Warranty Claim.

**`Reason`** — why it happened. Installation error, Component failure, User error, Documentation gap.

**`Origin`** — which channel it arrived through. Email, Web, Phone, Chat, Portal.

`Reason` is the one that answers "what is actually breaking", which is the question the product and engineering teams care about most. It is also the one agents skip because it does not help them close the case. Making it required on closure is the standard fix, and it is worth the friction.

```
// Validation rule: reason required before closing
AND(
  ISPICKVAL(Status, "Closed"),
  ISBLANK(TEXT(Reason))
)
```

Beyond the standard three, most manufacturing support implementations add a product or asset lookup, a resolution text field, and a root cause picklist maintained by the specialist rather than the front line.

## Time tracking

The metrics from [[05.1 - Service Cloud Overview and the Support Model]] need timestamps the platform does not maintain by default.

Entitlements and milestones provide first response and resolution tracking properly, including business hours ([[05.5 - Entitlements, Milestones and SLAs]]). Where entitlements are not in use, or where the business wants metrics beyond what milestones provide, a status history object is the usual answer.

```java
public with sharing class CaseStatusHistoryService {

    public static void recordStatusChange(List<Case> newCases, Map<Id, Case> oldCases) {
        List<Case_Status_History__c> entries = new List<Case_Status_History__c>();
        Datetime now = Datetime.now();

        for (Case c : newCases) {
            Case prior = oldCases == null ? null : oldCases.get(c.Id);
            if (prior != null && prior.Status == c.Status) {
                continue;
            }
            entries.add(new Case_Status_History__c(
                Case__c = c.Id,
                Status__c = c.Status,
                Previous_Status__c = prior == null ? null : prior.Status,
                Entered_On__c = now,
                Owner_At_Entry__c = c.OwnerId
            ));
        }

        if (!entries.isEmpty()) {
            insert entries;
        }
    }
}
```

From that, the metric support leaders actually want — elapsed time excluding customer-waiting periods — becomes computable:

```sql
SELECT Case__c, Status__c, SUM(Duration_Minutes__c) totalMinutes
FROM Case_Status_History__c
WHERE Case__r.ClosedDate = LAST_N_DAYS:30
  AND Status__c NOT IN ('Awaiting Customer', 'Awaiting Third Party')
GROUP BY Case__c, Status__c
```

On a high-volume support desk this object grows fast — 80,000 cases with six status changes each is nearly half a million records a year. It is a candidate for archiving to a big object after a couple of years. See [[23.4 - Archiving with Big Objects and External Storage]].

## Case comments, emails and feed

Three ways of recording what was said, and they are not interchangeable.

**Case Comments** are the legacy mechanism — plain text, with a public or private flag. Public comments are visible to the customer in a portal.

**Email Messages** (`EmailMessage`) record inbound and outbound email on the case, and are what Email-to-Case creates. This is the object that holds the actual correspondence in most implementations. See [[05.6 - Email-to-Case and Web-to-Case]].

**Case Feed** is the Chatter-based interface presenting emails, comments, status changes, and posts in a single chronological view. It is the standard agent experience in the console, and enabling it is effectively mandatory for a modern implementation.

The practical point for developers: when asked "where is the conversation stored", the answer is usually `EmailMessage` plus `FeedItem`, not `CaseComment`. Reporting on conversation volume needs to query the right one.

## Auto-response and notification

An **Auto-Response Rule** sends an acknowledgement when a case is created, with criteria-based template selection — a different acknowledgement for a warranty claim than for a billing question.

Its value is that it starts the relationship immediately, and it is genuinely the cheapest improvement to perceived responsiveness available. Its limitation is that it fires only on creation, not on update.

Like assignment rules, auto-response rules **do not fire for records created by the API unless requested**:

```java
Database.DMLOptions options = new Database.DMLOptions();
options.assignmentRuleHeader.useDefaultRule = true;
options.emailHeader.triggerAutoResponseEmail = true;
options.emailHeader.triggerUserEmail = true;

for (Case c : cases) {
    c.setOptions(options);
}
Database.insert(cases, false);
```

Three separate flags: `triggerAutoResponseEmail` for the customer acknowledgement, `triggerUserEmail` for owner notification, and `useDefaultRule` for assignment. An integration creating cases needs all three considered explicitly, and forgetting them is silent.

## Closing cases well

What happens on closure determines whether the case data is worth anything afterwards.

**Require a resolution.** A closed case with no description of what was done is useless to the next agent who sees a similar problem.

**Require a reason.** As above.

**Prompt for a knowledge article.** The moment of closure is when the agent knows the answer. Salesforce supports attaching or drafting an article from the case, and orgs that use it build a knowledge base as a side effect of working cases rather than as a separate project. See [[05.10 - Salesforce Knowledge]].

**Send a satisfaction survey.** Usually a flow triggered on closure, sending a link.

**Consider reopening rules.** A customer replying to a closed case can reopen it automatically, which is usually better than creating a duplicate case with no history.

```java
public with sharing class CaseReopenService {

    public static void reopenOnCustomerReply(List<EmailMessage> messages) {
        Set<Id> caseIds = new Set<Id>();
        for (EmailMessage msg : messages) {
            if (msg.Incoming && msg.ParentId != null) {
                caseIds.add(msg.ParentId);
            }
        }
        if (caseIds.isEmpty()) {
            return;
        }

        List<Case> toReopen = new List<Case>();
        for (Case c : [
            SELECT Id, Status, ClosedDate FROM Case
            WHERE Id IN :caseIds AND IsClosed = true
        ]) {
            // only reopen within the reopen window; older replies get a fresh case instead
            if (c.ClosedDate > Datetime.now().addDays(-14)) {
                toReopen.add(new Case(Id = c.Id, Status = 'In Progress', Reopened__c = true));
            }
        }

        if (!toReopen.isEmpty()) {
            update toReopen;
        }
    }
}
```

The reopen window matters. Without it, a customer replying "thanks" to a case closed eight months ago reopens it, and the reopen rate metric becomes meaningless.

## Practical guidance

**Design the status model around who you are waiting for.** Awaiting Customer is not optional.

**Make Reason required on closure.** It is the field that answers what is breaking.

**Enable Case Feed.** The alternative agent experience is meaningfully worse.

**Set the DML email and assignment flags on every integration that creates cases.**

**Track reopen rate.** A high reopen rate means cases are being closed prematurely, which is often a symptom of agents being measured on closure volume.

**Plan for volume.** Case and its related objects are among the fastest-growing tables in any org, and archiving should be designed before it is urgent.
