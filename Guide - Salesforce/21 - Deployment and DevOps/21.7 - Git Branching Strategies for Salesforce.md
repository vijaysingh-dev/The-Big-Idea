# Git Branching Strategies for Salesforce

## Why the usual advice needs adjusting

Standard branching models assume the repository is the complete truth and that a deployment replaces the target.

On Salesforce, neither holds. **The org is a live system with its own state**, administrators change it directly, and a deployment merges rather than replaces.

Three consequences shape every branching decision:

**Metadata does not merge like code.** Two developers adding a picklist value to the same field produce an XML conflict that Git resolves badly.

**A branch is not an environment.** A feature branch has no org unless someone creates one.

**Production drifts.** An administrator adds a field on Tuesday, and the repository does not know.

## Environment-branch mapping

The model most Salesforce teams settle on, because it mirrors the org chain.

```
main         ←→  Production
uat          ←→  UAT sandbox
integration  ←→  Integration sandbox
feature/*    ←→  scratch orgs or developer sandboxes
```

```
feature/claim-approval-tiers
        ↓ pull request
integration        → deploys to the integration sandbox
        ↓
uat                → deploys to UAT
        ↓
main               → deploys to production
        ↓
tag v2026.08.1
```

**Each long-lived branch has an org**, and merging into it deploys there. That direct mapping is what makes the model comprehensible to a mixed team of developers and administrators.

**The cost:** promoting a change means merging three times, and cherry-picking a hotfix past two branches is awkward.

## Trunk-based, with the caveat

```
main         ←→  Production, always deployable
feature/*    short-lived, merged within days
release/*    cut from main when a release is prepared
hotfix/*     cut from main, merged back
```

**The theory is better** — fewer long-lived branches, less merge pain, faster integration.

**The Salesforce caveat is real.** Trunk-based development assumes feature flags let unfinished work sit in production safely. On Salesforce, a half-built object with a validation rule and a required field is visible to users the moment it deploys.

Feature toggles help for code paths and not for schema:

```java
if (FeatureToggles.isEnabled('New_Approval_Flow')) {
    return ClaimApprovalServiceV2.approve(claimIds, amount);
}
return ClaimApprovalService.approve(claimIds, amount);
```

That works for Apex and LWC. It does not hide a new required field, a changed page layout, or an active flow. See [[18.10 - Custom Metadata Driven Architecture]].

**Trunk-based works well** for a mature team shipping code-heavy changes frequently, with packages providing the isolation. It works less well for schema-heavy declarative work.

## What merges badly

The specific metadata that causes conflicts, and how to avoid them.

**Picklist values on the same field.** Two developers each adding a value produces an XML conflict.

```xml
<valueSet>
    <valueSetDefinition>
        <value><fullName>Under Review</fullName><label>Under Review</label></value>
        <value><fullName>Escalated</fullName><label>Escalated</label></value>
    </valueSetDefinition>
</valueSet>
```

Git merges these badly, and the resolution frequently loses one.

**Page layouts.** Enormous XML files where any change touches many lines. Two people editing one layout is a conflict nobody wants to resolve by hand.

**Profiles.** Already problematic for retrieval reasons; also large and conflict-prone. See [[21.1 - Metadata, Source of Truth and Deployment Concepts]].

**Flows.** A single XML file per version, with element positions embedded. Two people editing one flow produces a conflict that cannot be merged meaningfully.

**Translations and label files.**

**The practical defences:**

**Coordinate on shared metadata.** Two people should not edit the same layout or flow simultaneously — a convention, not a tool.

**Prefer permission sets to profiles.**

**Accept "take theirs, redo mine"** for flows and layouts. Merging them by hand is worse than reapplying the change.

**Split flows** where several people work on one object, so each owns a smaller file.

## Handling org drift

The problem with no clean solution.

An administrator adds a field in production. The repository does not know. The next deployment does not remove it — deployments merge — so nothing breaks immediately, and the repository is now wrong.

**Detection:**

```bash
sf project retrieve start --manifest manifest/package.xml --target-org production
git status
```

Anything that appears is drift. Running this weekly, on a schedule, surfaces it before it accumulates.

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail
WHERE CreatedDate = LAST_N_DAYS:7
ORDER BY CreatedDate DESC
```

`SetupAuditTrail` names who changed what, which is the faster check.

**The organizational fix, in order of effectiveness:**

**Restrict production configuration access.** Fewer people with the ability to change things directly.

**Provide a fast path for small changes**, or people will bypass the process. A pipeline that takes two days to add a field guarantees someone adds it directly.

**Schedule a weekly drift check** and reconcile.

**Accept some drift.** Reports, dashboards, list views, and email templates are frequently better managed in the org than in Git, and insisting otherwise creates friction with no benefit.

## Pull requests

```yaml
on: pull_request

jobs:
  validate:
    steps:
      - name: Static analysis
        run: sf scanner run --target force-app --severity-threshold 3

      - name: LWC tests
        run: npm run test:unit -- --coverage

      - name: Generate delta manifest
        run: sf sgd source delta --to HEAD --from origin/main --output manifest/

      - name: Validate against the target org
        run: |
          sf project deploy validate \
            --manifest manifest/package/package.xml \
            --test-level RunSpecifiedTests \
            --tests $(node scripts/affected-tests.js) \
            --target-org integration
```

**`deploy validate` is the meaningful check** — it runs the actual deployment and its tests against the real target without committing. See [[21.8 - CI-CD Pipelines]].

**What a reviewer should look at**, beyond the code:

```
[ ] Are new fields on the right object, in the right package?
[ ] Is field-level security in a permission set, not a profile?
[ ] Does a new trigger consolidate with the existing one?
[ ] Does new automation duplicate an existing flow?
[ ] Are there tests, with assertions?
[ ] Is there a bulk test?
[ ] Are post-deployment manual steps documented?
[ ] Does the diff show unintended profile or layout changes?
```

**That last line catches the most incidents.** A retrieval artefact in a profile removing permissions is invisible unless someone reads the diff.

## Commits and history

```
feat(claims): add tiered approval routing
fix(integration): handle null coverage in the ERP payload
refactor(core): extract ClaimSelector from ClaimService
chore(deps): update sfdx-scanner
```

Conventional commit prefixes make the history readable and support automated release notes.

**Reference the work item** — `NW-1247` — because six months later "why does this exist" is answered by the ticket, not the code.

**Do not commit:**

```
.sf/
.sfdx/
node_modules/
*.log
server.key
.env
```

A committed JWT private key is a security incident, and it happens.

## Release tagging

```bash
git tag -a v2026.08.1 -m "August release: tiered approval, ERP retry handling"
git push origin v2026.08.1
```

**A tag on main at each production deployment** gives "what was in the March release" a precise answer:

```bash
git diff v2026.07.1..v2026.08.1 --stat
git log v2026.07.1..v2026.08.1 --oneline
```

That is the capability change sets cannot provide, and the reason source control is worth the effort. See [[21.2 - Change Sets]].

## Hotfixes

```bash
git checkout main
git checkout -b hotfix/claim-approval-null-pointer

# fix, test, commit
git push origin hotfix/claim-approval-null-pointer

# validate and deploy to production
sf project deploy validate --manifest manifest/package.xml \
  --test-level RunLocalTests --target-org production

# merge back into main AND into every long-lived branch
git checkout main && git merge hotfix/claim-approval-null-pointer
git checkout uat && git merge main
git checkout integration && git merge main
```

**Merging back into every long-lived branch is the step that gets forgotten**, and the result is the bug reappearing in the next release because uat still has the old code.

In an environment-branch model that is three merges. It is the main operational cost of the model and worth automating.

## Choosing

**Environment branches when:**

- The team includes administrators as well as developers
- Releases are periodic rather than continuous
- Each environment needs a distinct state
- The model's directness matters more than merge convenience

**Trunk-based when:**

- Developers only, shipping frequently
- Packages provide isolation
- Feature toggles cover the code paths
- The team is disciplined about small, short-lived branches

**Most Salesforce teams run environment branches**, and that is a reasonable default rather than a compromise. The model's clarity — this branch is that org — matters in a mixed team more than the merge overhead costs.

## Practical guidance

**Map long-lived branches to orgs** and keep the mapping obvious.

**Keep feature branches short.** Metadata conflicts grow with age.

**Coordinate on flows, layouts, and picklists** — they do not merge.

**Use permission sets, not profiles**, in source control.

**Check for drift weekly** and reconcile.

**Provide a fast path for small changes**, or the process gets bypassed.

**Read the diff for unintended profile changes.**

**Tag every production release.**

**Merge hotfixes back into every long-lived branch.**
