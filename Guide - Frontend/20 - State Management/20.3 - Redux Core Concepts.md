# Redux Core Concepts

Redux is a predictable state container built on three principles:

1. **A single source of truth** — one store object for the whole application
2. **State is read-only** — the only way to change it is dispatching an action
3. **Changes are made by pure reducers** — `(state, action) => newState`

Modern Redux means **Redux Toolkit** ([[20.4 - Redux Toolkit]]), which removes almost all of the boilerplate below. But the underlying model is unchanged, and understanding it is what makes RTK make sense.

## The data flow

```
UI event
  ↓ dispatch(action)
Store
  ↓ (state, action)
Reducer  → new state
  ↓
Subscribers notified
  ↓
Components re-render (those whose selected slice changed)
```

Strictly unidirectional. State never changes except through a dispatched action, which means every change has a named cause that can be logged, replayed and inspected.

## Actions

A plain object with a `type`:

```js
{ type: "todos/added", payload: { id: 1, text: "Learn Redux" } }
{ type: "todos/toggled", payload: 1 }
```

The `domain/eventName` convention is the modern one, and it matters more than it looks: it makes the DevTools log readable as a narrative of what happened.

Design actions as **events that occurred**, not setters:

```js
// Setter-style — the reducer becomes a dumb assignment, logic leaks to callers
dispatch({ type: "SET_LOADING", payload: true });
dispatch({ type: "SET_ERROR", payload: null });

// Event-style — one action, transition logic lives in the reducer
dispatch({ type: "checkout/submitted" });
```

Event-style actions mean adding a field to the state changes only the reducer, not every dispatch site. It also lets several reducers respond to the same action, which is the mechanism behind cross-slice coordination.

## Reducers

```js
function todosReducer(state = [], action) {
  switch (action.type) {
    case "todos/added":
      return [...state, action.payload];
    case "todos/toggled":
      return state.map(t =>
        t.id === action.payload ? { ...t, done: !t.done } : t
      );
    default:
      return state;
  }
}
```

Three requirements, all consequences of the same design:

**Pure.** Same inputs, same output. No fetching, no `Date.now()`, no `Math.random()`, no mutation of arguments.

**Immutable updates.** Return new objects for what changed, preserve references for what did not ([[06.7 - Immutable Data Patterns]]).

**No side effects.** Those belong in middleware or in the code that dispatches ([[20.5 - Middleware and Thunks]]).

Why purity is non-negotiable here: it is what makes time-travel debugging possible. The DevTools can replay any sequence of actions from the initial state and reproduce the exact UI, which only works if reducers are deterministic.

The `default: return state` case is essential — every reducer sees every action, and returning `undefined` for unhandled ones would wipe that slice.

## The store

```js
import { configureStore } from "@reduxjs/toolkit";

const store = configureStore({
  reducer: {
    todos: todosReducer,
    filters: filtersReducer,
  },
});

store.getState();
store.dispatch(action);
store.subscribe(listener);
```

`configureStore` combines slice reducers into a root reducer where each key owns its slice, and sets up DevTools, thunk middleware and development-mode immutability checks automatically.

## Selectors

```jsx
const todos = useSelector(state => state.todos.items);
const visible = useSelector(selectVisibleTodos);
```

`useSelector` subscribes the component to the store and re-runs the selector after every dispatch. If the returned value changed by reference (`===` by default), the component re-renders.

This is the granularity context lacks ([[20.2 - Context API and Its Limits]]) — a component reading `state.todos` is unaffected by changes to `state.filters`.

The classic mistake:

```jsx
// New array every call — re-renders after EVERY action
const visible = useSelector(state => state.todos.filter(t => !t.done));
```

The selector returns a new array reference each time, so the reference check always fails. Fixes:

```jsx
// Memoized selector
const selectVisible = createSelector(
  [state => state.todos, state => state.filter],
  (todos, filter) => todos.filter(t => filter === "all" || t.status === filter)
);

// Or a shallow-equality comparison
const visible = useSelector(selectVisible, shallowEqual);
```

`createSelector` (from Reselect, re-exported by RTK) memoizes on its input selectors, so the output reference is stable while the inputs are unchanged.

Note that as of RTK 2, `createSelector` uses `weakMapMemoize` by default, which caches across many argument combinations rather than only the most recent — this fixed a long-standing problem with parameterized selectors used across list items.

## Where Redux is worth it

- **Complex state with many interdependent transitions** — the reducer model shines
- **A need for an auditable change log** — DevTools with time travel
- **Middleware needs** — logging, analytics, persistence, optimistic updates, offline queueing
- **State read and written from far apart in the tree**
- **Large teams** — the constraints are the point; there is exactly one way to change state

## Where it is not

- **Server data.** Cache invalidation, deduplication and revalidation are a different problem. Use RTK Query or TanStack Query ([[24.6 - TanStack Query Fundamentals]]).
- **Local UI state.** An open dropdown does not belong in a global store.
- **Small applications.** `useState` plus `useReducer` plus context covers a great deal.

Redux's reputation for boilerplate came from a period when it was used for everything, including server data. Scoped to genuine shared client state, it is compact.

## Time-travel debugging

Redux DevTools lets you inspect every dispatched action, see the state diff it caused, jump to any previous state, and replay a sequence. For reproducing a bug from a user report — dispatch the recorded action log and watch it happen — nothing else in the ecosystem matches it.

This capability is the payoff for the purity constraints, and it is a legitimate reason to choose Redux over a simpler store.

## How senior engineers actually use this

**They use Redux Toolkit exclusively.** Hand-written action types, action creators and switch reducers are legacy.

**They keep server data out of the store**, or use RTK Query, which is Redux's own answer to the problem.

**They design actions as events**, which keeps the reducer as the single description of how state can change.

**They memoize any selector that derives or transforms**, since an unstable return reference re-renders on every action.

**They keep the store small** — genuinely shared client state only.

## Common pitfalls

- Mutating state in a reducer outside of RTK's Immer-wrapped `createSlice`.
- Selectors returning new object or array references every call.
- Side effects inside reducers.
- Setter-style actions that push transition logic into components.
- Server data in the store, hand-managed for staleness.
- Local UI state in the global store.
- Forgetting `default: return state`.

## Interview angle

"Why Redux" and "why are reducers pure" are the standard questions. Answer with the three principles and, crucially, connect purity to what it enables: deterministic replay, time-travel debugging, and safe middleware. Then be honest about scope — Redux is for shared client state, not server data, and modern practice is RTK plus a data library. The selector-reference pitfall is a good practical detail to volunteer.
