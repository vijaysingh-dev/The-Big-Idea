# Trigger Interview Scenarios

## How to use this note

Triggers are the highest-frequency topic in Salesforce developer interviews, and the questions are usually scenarios rather than definitions. Work through each before reading the answer.

These are also the situations you will actually debug.

---

## Scenario 1

> A trigger works in the sandbox and fails in production with `Too many SOQL queries: 101`. Nothing changed. Why?

**Answer.** The query is inside a loop, and production processes records in bulk while the sandbox test used one record.

The trigger fires once per batch of up to 200. A query inside the loop consumes one query per record; at 101 it dies.

The fix is collect, query once, act once ([[10.6 - Bulkification Patterns]]).

**The follow-up worth anticipating:** *how would you have caught this before production?* A test inserting 200 records rather than one. Flow Debug and single-record tests prove nothing about bulk safety.

---

## Scenario 2

> An after-update trigger creates a payment record when a claim's status becomes Approved. Finance reports duplicate payments. What is wrong?

**Answer.** The trigger is not comparing against `Trigger.oldMap`.

```java
// Fires on every save of an approved claim
if (claim.Status__c == 'Approved') { }

// Fires once, on the transition
Warranty_Claim__c prior = Trigger.oldMap.get(claim.Id);
if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') { }
```

Any subsequent edit — a note added, a field corrected, a roll-up recalculating — re-runs the trigger and creates another payment.

There may also be recursion involved if something else updates the claim, which compounds it.

## Scenario 3

> A before-insert trigger reads `claim.Asset__r.SerialNumber` and gets null, even though `Asset__c` is populated. Why?

**Answer.** Relationship traversal does not work in before insert. The record has not been saved, so the platform has not resolved the relationship.

The fix is to query the parents explicitly:

```java
Set<Id> assetIds = new Set<Id>();
for (Warranty_Claim__c claim : Trigger.new) {
    if (claim.Asset__c != null) {
        assetIds.add(claim.Asset__c);
    }
}
Map<Id, Asset> assets = new Map<Id, Asset>([
    SELECT Id, SerialNumber FROM Asset WHERE Id IN :assetIds
]);
```

The same code works in an **after** trigger with `__r` traversal, because the record was saved. That inconsistency between before and after insert is exactly what makes this a good interview question.

## Scenario 4

> Two triggers exist on Opportunity. One sets a tier field, the other routes based on it. Routing is intermittently wrong. Explain.

**Answer.** Trigger execution order on the same object is **undefined**. When routing runs first, it reads a stale tier.

Nothing errors, the sandbox works, and the order can change after any deployment or release.

The fix is one trigger per object, with the services called in a deliberate order in the handler. Ordering then becomes the order of statements, which is explicit and controllable. See [[11.4 - One Trigger Per Object]].

**Follow-up:** *what if one of them is from a managed package?* You cannot consolidate. Do not depend on its output within the same save — react to the field changing in a later transaction, or move the work async.

## Scenario 5

> A recursion guard uses `private static Boolean hasRun = false`. A data load of 400 records processes only 200. Why?

**Answer.** A static persists for the whole transaction. The load arrives as two chunks of 200; the first sets the flag, the second is skipped entirely.

No error, no log entry — 200 records silently unprocessed.

The fix is to track **which record Ids** have been processed rather than whether the handler ran:

```java
List<Warranty_Claim__c> unprocessed = TriggerControl.filterUnprocessed(
    'WarrantyClaim_AfterUpdate', Trigger.new
);
```

This is the single most common defect in hand-rolled recursion control. See [[11.6 - Recursion Control and Static Guards]].

## Scenario 6

> A trigger makes an HTTP callout after updating a record. It throws `You have uncommitted work pending`. Why, and how do you fix it?

**Answer.** A callout cannot be made after DML in the same transaction.

The transaction holds open database work between steps 7 and 17 of the order of execution. An HTTP call during that window would hold it open for the duration of an external system's response, so the platform forbids it.

The fix is to move the callout out of the transaction:

```java
System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

The Queueable runs after commit, in its own transaction, with its own limits and retry behaviour.

**Follow-up:** *what if the trigger needs the callout response?* It cannot have it synchronously. Either the process becomes asynchronous end to end, or the callout happens **before** any DML — which works, and constrains the design.

## Scenario 7

> Inserting 200 claim parts causes `Apex CPU time limit exceeded`. The part trigger is twenty lines and does nothing expensive. Explain.

**Answer.** The cascade at step 15 of the order of execution.

Each part insert recalculates its parent claim's roll-up, which updates the claim, which fires the claim trigger, which updates the asset, which fires the asset trigger. One insert runs four objects' automation, all against the same CPU budget.

The diagnostic is nested `DML_BEGIN` blocks in the debug log. The fixes are architectural: fewer roll-ups on hot parents, updating only records whose values changed, and moving non-urgent aggregation to a scheduled job. See [[11.9 - Triggers and Order of Execution]].

## Scenario 8

> A validation rule on Claim Part says approved parts cannot be deleted. A user deletes the parent claim and the parts go with it. Explain.

**Answer.** Cascade delete from a master-detail parent bypasses the child's validation rules.

Prevention must live on the **parent**, in a before-delete trigger:

```java
public static void preventDeletionOfClaimsWithApprovedParts(List<Warranty_Claim__c> claims) {
    Set<Id> claimIds = new Map<Id, Warranty_Claim__c>(claims).keySet();

    Set<Id> withApprovedParts = new Set<Id>();
    for (Claim_Part__c part : [
        SELECT Warranty_Claim__c FROM Claim_Part__c
        WHERE Warranty_Claim__c IN :claimIds AND Status__c = 'Approved'
    ]) {
        withApprovedParts.add(part.Warranty_Claim__c);
    }

    for (Warranty_Claim__c claim : claims) {
        if (withApprovedParts.contains(claim.Id)) {
            claim.addError('This claim has approved parts and cannot be deleted.');
        }
    }
}
```

See [[02.10 - Delete Behaviour - Cascade and Restrict]].

## Scenario 9

> A roll-up maintained by a trigger is correct after inserts and updates, but wrong after a record is restored from the recycle bin. Why?

**Answer.** The handler has no `after undelete` case.

Undelete restores the record, and the aggregate must be recomputed. Omitting the event leaves the parent's count permanently low.

```java
when AFTER_DELETE {
    ClaimRollupService.recalculate(assetIds(Trigger.old));
}
when AFTER_UNDELETE {
    ClaimRollupService.recalculate(assetIds(Trigger.new));
}
```

**The related bug worth mentioning:** the same handler is probably wrong when a claim is reparented, because it collects only the new asset Id and not the old one. Both parents need recalculating. See [[11.7 - Bulkified Trigger Patterns]].

## Scenario 10

> A trigger on a custom object assigns a permission set based on the record's content. It throws `MIXED_DML_OPERATION`. Why, and what are the options?

**Answer.** `PermissionSetAssignment` is a setup object. One transaction cannot perform DML on both a setup object and a normal object, and the DML that fired the trigger already set the category.

A trigger on a normal object therefore cannot perform setup DML at all. The only option is async:

```java
System.enqueueJob(new PermissionAssignmentQueueable(userIds, permissionSetName));
```

The Queueable runs in its own transaction, where setup DML is unconstrained. See [[10.7 - Mixed DML and Setup Objects]].

## Scenario 11

> Design the trigger architecture for an object with validation, field defaults, a roll-up to a parent, an approval submission, and an ERP notification.

**Answer.**

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    WarrantyClaimTriggerHandler.run();
}
```

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (AutomationBypass.isBypassed('WarrantyClaim')) {
            return;
        }

        switch on Trigger.operationType {
            when BEFORE_INSERT {
                ClaimService.applyDerivedFields(Trigger.new, null);
                ClaimValidationService.validateCoverage(Trigger.new);
            }
            when BEFORE_UPDATE {
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
                ClaimValidationService.validateCoverage(Trigger.new);
            }
            when BEFORE_DELETE {
                ClaimValidationService.preventDeletionOfSettled(Trigger.old);
            }
            when AFTER_INSERT {
                ClaimRollupService.recalculate(ClaimService.assetIds(Trigger.new));
                ClaimApprovalService.submitIfRequired(Trigger.new, null);
            }
            when AFTER_UPDATE {
                ClaimRollupService.recalculate(
                    ClaimService.affectedAssetIds(Trigger.new, Trigger.oldMap)
                );
                ClaimApprovalService.submitIfRequired(Trigger.new, Trigger.oldMap);
                ClaimService.queueErpNotification(Trigger.new, Trigger.oldMap);
            }
            when AFTER_DELETE, AFTER_UNDELETE {
                ClaimRollupService.recalculate(
                    ClaimService.assetIds(Trigger.isDelete ? Trigger.old : Trigger.new)
                );
            }
        }
    }
}
```

The reasoning an interviewer is listening for:

- **Defaults and validation are before**, so no DML and validation rules see the derived values
- **Roll-up, approval, and notification are after**, because they need the Id
- **The ERP notification is enqueued**, not called, because a callout after DML is prohibited
- **Every service takes collections** and tolerates a null `oldMap`
- **Delete and undelete are both handled**, and the affected-asset method covers reparenting
- **A bypass check** sits at the top for migrations and incidents

## Scenario 12

> How do you test a trigger properly?

**Answer.** Four things, and the first is the one people skip.

**A bulk test with at least 200 records**, with a parent distribution that exposes aggregation bugs — 200 children across 50 parents, not one-to-one.

**Real assertions**, on the resulting field values and related records. Coverage without assertions proves nothing.

**Negative cases** — the validation that should block, the record that should be skipped.

**`System.runAs`** for anything permission-dependent, since tests run as an administrator by default and administrators bypass sharing and field-level security entirely.

```java
@IsTest
static void rollupIsCorrectWhenClaimsShareAnAsset() {
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
    for (Integer i = 0; i < 200; i++) {
        claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 10000));
    }

    Test.startTest();
    insert claims;
    Test.stopTest();

    Map<Id, Asset> refreshed = new Map<Id, Asset>([
        SELECT Id, Open_Claim_Count__c FROM Asset WHERE Id IN :assets
    ]);
    for (Asset asset : assets) {
        Assert.areEqual(4, refreshed.get(asset.Id).Open_Claim_Count__c,
            'Each asset should have four claims');
    }
}
```

Four-to-one distribution is deliberate. A one-to-one test passes even with a broken aggregation.

---

## Section 11 in one paragraph

A trigger declares events and calls a handler; the handler is the only place `Trigger` is referenced; services take collections and never know they were called from a trigger. Before triggers modify the record in memory with no DML and run before validation rules; after triggers do everything else and are the only place the record Id exists on insert. Relationship traversal fails in before insert and works in after, which is the inconsistency that catches people. Every after-update handler compares against `oldMap`, or it fires on every save rather than on the transition. Recursion guards track record Ids, never a boolean, or a multi-chunk transaction silently skips records. One trigger per object, because order between triggers is undefined. And most trigger failures at scale are not the trigger — they are the cascade at step 15 sending parents back through their own pipeline.
