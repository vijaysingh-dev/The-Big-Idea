# Callout and Async Limits

## Callout limits

```
Callouts per transaction               100
Cumulative callout time         120 seconds
Default timeout per callout      10 seconds
Maximum timeout per callout     120 seconds
Request size                          6 MB
Response size                         6 MB
```

**The 120-second cumulative budget is the one people forget.** Ten callouts at 30 seconds each is 300 seconds, and the transaction dies partway through — having already completed some of the work.

```java
req.setTimeout(30000);   // set it explicitly; 10 seconds is often wrong in both directions
```

A long timeout ties up the transaction and consumes the shared budget; a short one produces spurious failures. Roughly twice the external system's observed 95th percentile is a reasonable starting point. See [[13.14 - Apex Callouts]].

## No callouts after DML

```
You have uncommitted work pending. Please commit or rollback before calling out.
```

The transaction holds open database work between steps 7 and 17 of the order of execution, and an HTTP call during that window would hold it open for the duration of an external system's response. See [[07.13 - Order of Execution]].

The consequences:

**A callout before any DML works.** Read-then-write integrations run synchronously.

**A callout after DML must be async.** Write-then-notify integrations use a Queueable or a platform event.

```java
// Fails
insert claim;
HttpResponse res = new Http().send(req);

// Correct
insert claim;
System.enqueueJob(new ErpNotificationQueueable(new Set<Id>{ claim.Id }));
```

## Batching the payload

The bulkification rule applied to integration.

```java
// 200 callouts — exhausts the budget
for (Warranty_Claim__c claim : claims) {
    ErpClient.post('/api/claims', ClaimPayload.from(claim));
}

// One callout for the batch
ErpClient.post('/api/claims/batch', ClaimPayload.from(claims));
```

Where the external API has no batch endpoint, chunking across separate transactions is the answer:

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    // one callout per chunk, and each chunk is its own transaction with a fresh budget
    ErpClient.Response response = ErpClient.post('/api/claims/batch',
        ClaimPayload.from(scope));

    if (response.isSuccess) {
        markSynced(scope, response);
    }
}
```

Batch Apex gives **100 callouts per chunk**, which is why it is the right tool for a large integration push rather than a Queueable chain.

## The async marker interfaces

```java
public class ErpQueueable implements Queueable, Database.AllowsCallouts { }
public class ErpBatch implements Database.Batchable<SObject>, Database.AllowsCallouts { }

@future(callout=true)
public static void notify(Set<Id> claimIds) { }
```

Omitting the marker produces a runtime failure on the first callout — in a job that may only sometimes call out, which is exactly the kind of defect that reaches production.

## Async enqueue limits

```
Async calls per synchronous transaction        50
   combined across @future, enqueueJob, executeBatch
Queueable jobs enqueued from within a Queueable  1
Batch jobs queued or active, org-wide            5
Scheduled Apex jobs at once                    100
Async executions per day     250,000 or 200 × user licences
```

The 50-per-transaction cap catches the same mistake as everywhere else:

```java
// 200 jobs, fails at 50
for (Warranty_Claim__c claim : Trigger.new) {
    System.enqueueJob(new ErpNotificationQueueable(new Set<Id>{ claim.Id }));
}

// One job for the batch
System.enqueueJob(new ErpNotificationQueueable(claimIds));
```

**The daily allocation is org-wide and shared across every async mechanism.** An integration enqueuing per record can starve every other job in the org — a batch job, a scheduled reconciliation, a platform event subscriber all draw from the same pool.

```java
Map<String, System.OrgLimit> limits = OrgLimits.getMap();
System.OrgLimit async = limits.get('DailyAsyncApexExecutions');
System.debug(async.getValue() + ' of ' + async.getLimit());
```

Worth logging daily. Exhaustion is org-wide and the symptom — jobs that simply do not run — is confusing.

## Queueable chaining

**One job enqueued from within a Queueable.** That is what bounds a chain to one job at a time, and it makes chaining a sequential pipeline rather than a fan-out.

```java
public void execute(QueueableContext context) {
    processChunk();

    // the termination condition is not optional
    if (!remaining.isEmpty() && !Test.isRunningTest()) {
        System.enqueueJob(new ClaimSyncQueueable(remaining));
    }
}
```

A chain with no exit runs until the daily allocation is exhausted, affecting the whole org.

**Only one chained level runs in test context**, which is why the `Test.isRunningTest()` guard appears. See [[12.3 - Queueable Apex]].

## The batch flex queue

Only **5 batch jobs** can be queued or active at once, org-wide. Beyond that they sit in the flex queue in Holding status, up to 100.

```sql
SELECT Id, ApexClass.Name, Status, JobItemsProcessed, TotalJobItems, CreatedDate
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND Status IN ('Holding', 'Queued', 'Preparing', 'Processing')
ORDER BY CreatedDate
```

The failure this produces is specific: **six nightly jobs all scheduled for 02:00.** Five start, the sixth waits, and if the first five are slow it runs during the business day.

**Stagger scheduled jobs** — 02:00, 02:30, 03:00 — rather than scheduling them all at once. See [[12.5 - Scheduled Apex]].

Jobs in the flex queue can be reordered in Setup, which matters when a critical job is behind four slow ones.

## Future method limits

```
50 future calls per synchronous transaction
Parameters must be primitives or collections of primitives
Cannot be called from a future method, a batch job, or another async context
No job Id, no chaining, no failure hook
```

The parameter restriction is why records get serialized to JSON, and the absence of a failure hook is why Queueable with a Finalizer replaces it in any code where failure matters. See [[12.2 - Future Methods]] and [[12.6 - Transaction Finalizers]].

## Email limits

```
10 sendEmail invocations per transaction
Daily limit on external addresses, by edition
5,000 external recipients per day in most editions
```

The per-transaction cap is a common surprise in a batch job that emails per record.

```java
// 200 invocations — fails at 10
for (Warranty_Claim__c claim : claims) {
    Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{ buildEmail(claim) });
}

// One invocation with all the messages
List<Messaging.SingleEmailMessage> messages = new List<Messaging.SingleEmailMessage>();
for (Warranty_Claim__c claim : claims) {
    messages.add(buildEmail(claim));
}
Messaging.sendEmail(messages);
```

The daily external-recipient limit is org-wide, and exhausting it silently stops every email in the org until the window resets. A batch job emailing thousands of customers needs that limit checked first.

## Checking async capacity

```java
public with sharing class AsyncCapacityService {

    public static Boolean canEnqueueBatch() {
        Integer running = [
            SELECT COUNT() FROM AsyncApexJob
            WHERE JobType = 'BatchApex'
              AND Status IN ('Holding', 'Queued', 'Preparing', 'Processing')
        ];
        return running < 5;
    }

    public static Boolean hasDailyCapacity(Integer required) {
        System.OrgLimit async = OrgLimits.getMap().get('DailyAsyncApexExecutions');
        // leaving headroom means other jobs in the org are not starved
        return (async.getLimit() - async.getValue()) > (required + 1000);
    }
}
```

Checking before enqueuing a large job is worth doing in anything that runs unattended. Discovering the allocation was exhausted after the fact means the work silently did not happen.

## Monitoring

```sql
SELECT Id, ApexClass.Name, JobType, Status, ExtendedStatus,
       NumberOfErrors, JobItemsProcessed, TotalJobItems, CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE Status IN ('Failed', 'Aborted') AND CreatedDate = LAST_N_DAYS:7
ORDER BY CreatedDate DESC
```

`ExtendedStatus` carries the failure message, including limit exceptions.

**Alert on absence as well as failure.** A job that stopped running produces no failed record — the only way to detect it is a run log with a last-run timestamp per job. See [[12.10 - Choosing the Right Async Tool]].

## Practical guidance

**Set callout timeouts explicitly**, and watch the 120-second cumulative budget.

**Batch the payload** — one callout per chunk, never per record.

**Implement `Database.AllowsCallouts`** wherever a job might call out.

**Enqueue once per batch**, never per record.

**Give every Queueable chain a termination condition.**

**Stagger scheduled batch jobs**, given the 5-concurrent limit.

**Batch email into one `sendEmail` invocation.**

**Check daily async capacity** before large unattended jobs.

**Monitor `AsyncApexJob`**, and alert on jobs that stopped running.
