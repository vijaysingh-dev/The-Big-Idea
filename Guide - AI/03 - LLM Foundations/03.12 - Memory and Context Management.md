# Memory and Context Management

## The Statelessness Problem

Every LLM API call is stateless — the model has no memory of previous conversations. If you send:

```
Call 1: "My name is Vijay."
Call 2: "What's my name?"  → Model: "I don't know your name."
```

The model genuinely doesn't know. Each call starts fresh. Memory is an engineering problem, not a model problem.

---

## Types of Memory

|Type|What it stores|Duration|Where|
|---|---|---|---|
|**In-context (short-term)**|Current conversation + injected context|Single conversation|Prompt itself|
|**External (long-term)**|Summaries, facts, conversation history|Persistent across sessions|Database|
|**Episodic**|Specific past events/interactions|Days-weeks|Vector DB (retrieved by similarity)|
|**Semantic**|Facts about the user/domain|Persistent|Structured store (key-value, graph)|
|**Procedural**|"How this user likes to work"|Persistent|Prompt injected from profile|

---

## In-Context Memory (Conversation History)

The simplest approach: include the full conversation in every API call.

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user",   "content": "My name is Vijay."},
    {"role": "assistant", "content": "Nice to meet you, Vijay!"},
    {"role": "user",   "content": "What's my name?"},  # ← new turn
]
response = llm.call(messages)
# Model now has context: "My name is Vijay"
```

**Problem**: Context window is finite. Long conversations eventually exceed the limit.

**Cost**: Every token in history is billed as input tokens on every call. A 10-turn conversation doubles your input token cost.

---

## Context Window Management Strategies

### Strategy 1: Fixed Window (Last N Turns)

Keep only the most recent N turns:

```python
def trim_history(messages, max_turns=10):
    # Keep system prompt + last N*2 messages (N turns = N user + N assistant)
    system = [m for m in messages if m["role"] == "system"]
    conversation = [m for m in messages if m["role"] != "system"]
    return system + conversation[-max_turns * 2:]
```

**Problem**: Loses early context (user's stated preferences, initial instructions).

### Strategy 2: Summarization

When history grows long, summarize older turns into a compressed representation:

```python
def summarize_old_history(old_messages, llm):
    return llm.call([
        {"role": "user", "content": f"Summarize this conversation concisely, preserving key facts:\n{format_messages(old_messages)}"}
    ])

# Store summary + recent turns:
context = [summary_message] + recent_messages[-10:]
```

**Tradeoff**: Loses detail. Summarization itself costs tokens and may drop important context.

### Strategy 3: Token Counting + Budget Allocation

Track token usage per component and enforce budgets:

```python
TOKEN_BUDGETS = {
    "system_prompt": 500,
    "memory_injection": 1000,
    "conversation_history": 3000,
    "rag_context": 8000,
    "output": 2000,
}

def build_prompt(query, history, rag_chunks, system_prompt):
    # Trim each component to budget
    trimmed_history = trim_to_tokens(history, TOKEN_BUDGETS["conversation_history"])
    trimmed_rag = trim_to_tokens(rag_chunks, TOKEN_BUDGETS["rag_context"])
    return assemble(system_prompt, trimmed_history, trimmed_rag, query)
```

## External Memory Systems

For persistent memory across sessions:

### Key-Value Memory

Store user preferences, facts, profile as structured data:

```python
user_memory = {
    "name": "Vijay",
    "location": "India",
    "preferences": ["concise answers", "code examples"],
    "expertise": "backend engineer",
}

# Inject into system prompt
memory_str = format_memory(user_memory)
system_prompt = f"{base_system_prompt}\n\nUser context:\n{memory_str}"
```

Managed by the application layer, not the model.

### Vector Memory (Episodic)

Store conversation summaries or important facts as embeddings. Retrieve relevant memories based on current query:

```python
# Store after each conversation
memory_store.add(
    text=summarize(conversation),
    metadata={"user_id": user_id, "timestamp": now()}
)

# Retrieve at start of new conversation
relevant_memories = memory_store.search(
    query=current_user_message,
    filter={"user_id": user_id},
    top_k=3
)
```

Used by: AI assistants that remember past interactions (e.g., ChatGPT's memory feature).

### Graph Memory

Store entities and relationships explicitly:

```
User → works_at → Company
Company → industry → Finance
User → is_interested_in → ["AI", "stock market", "philosophy"]
```

More structured than vector memory; better for reasoning about relationships. More complex to maintain.

---

## Context Window ≠ Effective Memory

Even with a 128K context window, having everything in context doesn't guarantee the model uses it effectively.

Research findings:

- **Lost in the middle**: Information in the middle of a long context is less reliably used
- **Recency bias**: Models weight recent context more heavily
- **Needle in a haystack failures**: Models miss specific facts buried in long contexts even when those facts exist

**Implication**: Filling the context window isn't the same as effective memory. Active retrieval (RAG for memory) often works better than passive injection of everything.

---

## Memory in Agent Systems

Agents need richer memory for multi-step tasks:

```
Agent memory architecture:
├── Working memory (in-context)      ← current task state, recent observations
├── Episodic memory (vector DB)      ← "what happened in past tasks"
├── Semantic memory (KV store)       ← "what do I know about this user/domain"
└── Procedural memory (prompt rules) ← "how do I approach this type of task"
```

See [[../08 - Agents/08.3 - Memory Planning and Reflection]] for agent memory in depth.

---

## Practical Recommendations

|Scenario|Recommended Approach|
|---|---|
|Single-session chatbot|In-context history + trim by token count|
|Multi-session assistant|Summarize old sessions, store in DB, inject summaries|
|RAG system|No conversation history needed; focus on retrieval|
|Agent with tools|Working memory in-context, episodic memory in vector DB|
|Enterprise AI (user profiles)|Persistent KV store for user facts, injected at session start|
