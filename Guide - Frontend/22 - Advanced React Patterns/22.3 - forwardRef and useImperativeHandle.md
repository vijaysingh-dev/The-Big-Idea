# forwardRef and useImperativeHandle

Refs are not props. Passing `ref` to a function component historically did nothing — React consumed it, and the component never saw it.

```jsx
// Pre-React 19 — ref is undefined inside Input
function Input(props) { ... }
<Input ref={myRef} />     // warning: function components cannot be given refs
```

## React 19: ref is a normal prop

```jsx
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

<Input ref={inputRef} />
```

`forwardRef` is no longer needed for new code. It still works and will for some time, so you will read both forms.

## forwardRef (the pre-19 form)

```jsx
const Input = forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});
```

The second parameter is the ref. Note the named function — an anonymous `forwardRef((props, ref) => ...)` shows as "ForwardRef" in DevTools and in stack traces, which makes debugging harder.

## Why forwarding matters

Any component wrapping a native element should forward the ref, or consumers cannot:

- focus an input
- scroll an element into view
- measure it
- integrate a library that needs the node
- use it as a positioning anchor for a tooltip

A design-system `<Input>` that swallows the ref is a component people have to work around ([[16.3 - Components and Props]]).

```jsx
function Field({ label, id, ref, ...rest }) {
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} ref={ref} {...rest} />
    </div>
  );
}
```

## useImperativeHandle

Exposes a **custom object** through the ref instead of the DOM node:

```jsx
function VideoPlayer({ src, ref }) {
  const videoRef = useRef(null);

  useImperativeHandle(ref, () => ({
    play: () => videoRef.current.play(),
    pause: () => videoRef.current.pause(),
    seek: (time) => { videoRef.current.currentTime = time; },
    get duration() { return videoRef.current.duration; },
  }), []);

  return <video ref={videoRef} src={src} />;
}
```

```jsx
const player = useRef(null);
player.current.play();
player.current.seek(30);
// player.current.remove() — not available; the DOM node is hidden
```

The point is **encapsulation**: consumers get a narrow, intentional API rather than the raw node. Without it, any consumer could call `videoRef.current.remove()` or mutate styles directly, and those usages become de facto API you cannot change.

The dependency array works like `useMemo` — the handle is recreated when dependencies change. An empty array is correct when the methods only close over refs.

## When it is justified

Genuinely imperative operations that cannot be expressed declaratively:

- `focus()`, `blur()`, `select()`
- `scrollIntoView()`
- Media playback control
- Triggering an animation
- Form `reset()` or `submit()` on a custom component
- Measuring for a parent's layout decision

The common thread: **one-off actions, not state**. Anything that describes a persistent condition should be a prop.

## When it is not

```jsx
// Wrong — this is state
useImperativeHandle(ref, () => ({
  setValue: (v) => setInternalValue(v),
  getValue: () => internalValue,
  setError: (e) => setError(e),
}));
```

If the parent needs to control or read a value, lift the state and pass props ([[16.8 - Controlled vs Uncontrolled Components]]). An imperative getter/setter pair is a state management problem wearing a ref.

Warning signs that the design is wrong:

- The handle has more than three or four methods
- Methods named `get*`/`set*`
- The parent calls methods in an effect to synchronize
- The handle exposes internal state

## Callback refs are often simpler

```jsx
function List({ onItemMount }) {
  return items.map(item => (
    <li key={item.id} ref={node => onItemMount(item.id, node)}>{item.name}</li>
  ));
}
```

A callback ref handles cases object refs do not: conditional mounting, collections of nodes, and running logic at attach time ([[17.8 - useRef]]).

React 19 lets a callback ref return a cleanup function:

```jsx
<div ref={node => {
  observer.observe(node);
  return () => observer.unobserve(node);
}} />
```

Previously the callback was invoked with `null` on unmount, which was easy to forget and leaked detached nodes ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

## Merging refs

A component that needs its own ref *and* forwards one:

```jsx
function useMergedRef(...refs) {
  return useCallback((node) => {
    for (const ref of refs) {
      if (typeof ref === "function") ref(node);
      else if (ref) ref.current = node;
    }
  }, refs);
}

function Input({ ref, ...props }) {
  const localRef = useRef(null);
  const merged = useMergedRef(ref, localRef);

  useEffect(() => { localRef.current?.focus(); }, []);

  return <input ref={merged} {...props} />;
}
```

Both object refs and callback refs must be handled, since consumers may pass either. Libraries ship this as `useMergeRefs` or `composeRefs`.

## Typing

```tsx
type PlayerHandle = {
  play: () => void;
  pause: () => void;
};

function VideoPlayer({ ref }: { ref?: React.Ref<PlayerHandle> }) {
  useImperativeHandle(ref, () => ({ play, pause }), []);
}

const playerRef = useRef<PlayerHandle>(null);
```

Defining and exporting the handle type is important — it is the component's imperative API, and consumers need it ([[25.5 - Typing Events Refs and Hooks]]).

## Refs and Server Components

Refs require the DOM, so they only work in Client Components. A Server Component cannot hold or forward a ref ([[22.8 - Server Components]]).

## How senior engineers actually use this

**They forward refs from every component wrapping a native element**, as a design-system rule.

**They use `useImperativeHandle` rarely**, and treat a handle with many methods as a signal the design should be declarative.

**They name the inner function** in `forwardRef` for readable stack traces.

**They export the handle type** so the imperative API is typed for consumers.

**They prefer callback refs** for measurement and registration, where object refs plus effects miss conditional mounts.

## Common pitfalls

- A wrapper component swallowing the ref, forcing consumers to work around it.
- Anonymous `forwardRef` producing unnamed components in DevTools.
- `useImperativeHandle` used to expose state rather than actions.
- Forgetting the dependency array, recreating the handle every render.
- Not handling both object and callback refs when merging.
- Expecting a ref on a Server Component.
- Reading `ref.current` during render ([[17.8 - useRef]]).

## Interview angle

"What is forwardRef and why is it needed" now has a two-part answer: historically, refs were not props, so a function component could not receive one — `forwardRef` bridged that; in React 19, `ref` is a normal prop and `forwardRef` is unnecessary for new code. Then `useImperativeHandle` as the way to expose a curated API rather than the raw node, with the important caveat that it should expose **actions, not state** — an imperative getter/setter pair means the design should have been declarative.
