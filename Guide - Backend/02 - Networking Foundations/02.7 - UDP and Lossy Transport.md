# UDP and Lossy Transport

#backend #networking #udp

> **In one line:** UDP gives you ports and nothing else, which is exactly right when late data is worthless — and it is the foundation everything modern is being rebuilt on.

---

## The Idea

UDP adds four things to IP: a source port, a destination port, a length, and a checksum. Eight bytes of header.

No connection. No acknowledgement. No retransmission. No ordering. No flow control. No congestion control.

That sounds like a downgrade, and for most work it is. But TCP's guarantees have a cost, and the cost is **time**:

```
Packet lost at t=0
Detected at t≈RTT (duplicate ACKs) or t≈RTO (timeout)
Retransmitted, arrives at t≈2×RTT
Everything behind it waited that long
```

For a live voice call, a 200ms-old audio packet is useless. Playing it late is worse than not playing it. Retransmission actively harms the experience.

💡 **The principle: TCP is right when every byte matters more than when it arrives. UDP is right when when-it-arrives matters more than every byte.**

---

## The API

```python
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("0.0.0.0", 9999))

while True:
    data, addr = sock.recvfrom(65535)
    sock.sendto(b"pong", addr)
```

Two differences from TCP that shape everything:

**1. Datagrams are messages, not a stream.** One `sendto` becomes exactly one `recvfrom` — or zero, if it is lost. No framing needed. This is genuinely simpler than TCP, where you must build framing yourself ([[02.2 - Sockets From First Principles]]).

**2. There is no connection.** One socket serves all peers. `recvfrom` tells you who sent each datagram. No `accept`, no per-connection state — unless you create it yourself.

```python
sock.connect(("10.0.0.5", 9999))   # optional: fixes the peer
sock.send(b"data")                  # now you can use send/recv
```

`connect` on a UDP socket sends nothing. It just filters incoming datagrams and sets a default destination. It also lets you receive ICMP errors like "port unreachable", which you otherwise never see.

## Size Limits

Theoretical maximum is 65,507 bytes. Practical maximum is much smaller.

```
IPv4 MTU 1500
  − IP header  20
  − UDP header  8
  = 1472 bytes of safe payload
```

Larger datagrams get **fragmented** by IP into multiple packets. If any fragment is lost, the whole datagram is lost — because UDP has no partial delivery.

```
8KB datagram → 6 fragments
1% packet loss → ~6% datagram loss
```

⚠️ **Fragmentation multiplies your effective loss rate.** Keep datagrams under ~1200 bytes to be safe across tunnels and VPNs. QUIC uses 1200 as its floor for exactly this reason.

If you need to send more, do your own fragmentation with sequence numbers, so you can retransmit just the missing piece.

## Loss Is Not Uniform

An important detail people miss: packet loss on real networks is **bursty**, not evenly spread.

```
Uniform 1% loss:    ▫▫▫▪▫▫▫▫▫▫▪▫▫▫▫▫▫▪▫▫    (easy to conceal)
Real 1% loss:       ▫▫▫▫▫▫▫▪▪▪▪▫▫▫▫▫▫▫▫▫    (a 4-packet gap)
```

A router queue overflows and drops several consecutive packets. A WiFi interference burst kills 50ms of traffic.

This matters because concealment strategies assume gaps are short. Losing 4 consecutive audio packets is an audible dropout that no amount of interpolation fixes. It is also why forward error correction schemes interleave data — so a burst loss becomes several isolated losses that can each be recovered.

## Who Uses UDP, and Why

| Protocol | Why UDP |
|---|---|
| **DNS** | One small request, one small response. A connection costs more than a retry |
| **QUIC / HTTP/3** | Needs per-stream ordering, which TCP cannot provide ([[02.5 - Head of Line Blocking]]) |
| **WebRTC media** | Late audio and video are worthless |
| **NTP** | Time sync. A retransmitted timestamp is wrong by definition |
| **DHCP** | You do not have an IP address yet, so you cannot open a connection |
| **Game state** | Position updates 60×/sec. The newest one supersedes all older ones |
| **StatsD metrics** | Losing a sample is fine. Blocking the application is not |
| **Syslog (UDP mode)** | Same reasoning as metrics |
| **VPN tunnels** | Avoids TCP-over-TCP meltdown (see below) |

### TCP over TCP is a trap

Running a TCP tunnel inside another TCP connection produces a well-known meltdown:

```
Inner TCP:  detects loss, retransmits
Outer TCP:  ALSO detects the same loss, ALSO retransmits
            → duplicate retransmissions
            → inner timer backs off
            → the tunnel collapses under load
```

Two independent reliability mechanisms fighting each other. This is why OpenVPN and WireGuard default to UDP.

💡 A good interview answer when asked why VPNs use UDP. It also generalises: **stacking two retry mechanisms is usually a mistake**, which is exactly the argument against retrying in both a service mesh and your application code ([[11.2 - Timeouts Retries and Jitter]]).

## Building Reliability On UDP

If you need *some* guarantees but not all of TCP's, you build only the parts you need. This is what QUIC does.

### Sequence numbers — detect loss and reordering

```python
@dataclass
class Packet:
    seq: int
    timestamp: float
    payload: bytes
```

Now you can detect a gap, measure loss rate, and reorder or discard as appropriate.

### Selective retransmission

Retransmit only what actually matters:

```python
if packet.is_keyframe or packet.is_control:
    schedule_retransmit(packet)
else:
    conceal_loss()
```

Video does this: a keyframe loss is retransmitted because everything after it depends on it; a single delta frame is dropped and concealed.

### Forward error correction

Send redundant data so the receiver can reconstruct losses without asking:

```
Send packets A, B, C, and a parity packet P = A ⊕ B ⊕ C
Lose any one of the four → reconstruct it
```

Costs bandwidth, saves a round trip. The right trade when RTT is high and bandwidth is cheap — which describes most modern networks.

### Jitter buffer

Trade a little latency for smoothness:

```
Packets arrive: 0ms, 22ms, 19ms, 45ms, 20ms    (jittery)
Buffer 40ms, play out: 20ms, 20ms, 20ms, 20ms  (smooth)
```

Every real-time audio system does this. Buffer too small and you get dropouts; too large and the conversation feels laggy. Adaptive jitter buffers adjust continuously based on measured jitter.

### Congestion control — you must build it

⚠️ **This is the responsibility people forget.** TCP backs off when the network is congested. UDP does not, unless you make it.

A UDP application that keeps sending at full rate during congestion makes things worse for everyone, including itself. It is also actively antisocial — TCP flows sharing the link will back off while yours does not, so you take an unfair share.

QUIC implements CUBIC or BBR in userspace for exactly this reason. WebRTC uses Google Congestion Control. If you build a UDP protocol that sends more than a trickle, **you must implement congestion control** — and if that sounds like a lot of work, that is a strong argument for using QUIC rather than raw UDP.

## In Production

### When to actually choose UDP

Almost never directly. Be honest about this.

```
Do you need real-time media?          → WebRTC (which uses UDP for you)
Do you want HTTP without HOL blocking? → HTTP/3 (QUIC, which uses UDP for you)
Are you writing a custom protocol
  with genuine latency requirements?   → QUIC as a library, not raw UDP
Metrics or logs where loss is fine?    → UDP, and this is a real case
Anything else?                         → TCP
```

💡 **The modern answer to "should I use UDP" is usually "use QUIC".** You get UDP's stream independence plus connection management, congestion control, encryption and loss recovery, all already built and debugged. Writing your own reliable UDP protocol in 2026 is almost always reinventing QUIC badly.

The one place raw UDP still makes clear sense in backend work is fire-and-forget telemetry — StatsD-style metrics, where blocking the application to guarantee a metric arrives is worse than losing the metric.

### The UDP metrics trap

```python
sock.sendto(f"api.requests:1|c".encode(), ("statsd", 8125))
```

This never blocks and never fails visibly. That is the feature. It is also the trap:

⚠️ **UDP metrics silently disappear under load, and load is exactly when you need them.** Receive buffers overflow, the kernel drops datagrams, and your dashboard shows a *decrease* in traffic during an incident because the metrics themselves were dropped.

```bash
netstat -su | grep -i "receive errors\|packet receive errors"
```

Watch that counter. And prefer a pull-based system like Prometheus, where the absence of data is visible as a scrape failure rather than as a plausible-looking zero.

### Firewalls and NAT hate UDP

With no connection, a firewall cannot tell "a reply to my request" from "an unsolicited packet". So it guesses, using a timeout on the source/destination pair.

| Consequence | Effect |
|---|---|
| NAT mappings expire (often 30s) | Long-lived UDP flows die silently |
| Some corporate networks block UDP entirely except DNS | HTTP/3 fails, must fall back to TCP |
| No handshake to detect blocking | You discover the problem by timeout, not by refusal |

This is why every QUIC client keeps a TCP fallback, and why WebRTC needs TURN servers ([[02.10 - NAT Firewalls and Middleboxes]]).

### Receive buffer sizing

A UDP receiver with a full buffer drops datagrams with no notification to anyone.

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 4 * 1024 * 1024)
```

```bash
sysctl net.core.rmem_max          # your ceiling
netstat -su                       # drop counters
```

For a high-rate UDP receiver, buffer size and how fast you drain it are the whole game. There is no backpressure to save you — the sender does not know and does not slow down.

## Codebase

**Repo:** `quic-go/quic-go` and `coturn/coturn`

**Question to answer:** QUIC runs on UDP, so it must implement everything TCP gives you for free. Find where it does each of: loss detection, retransmission, congestion control, and flow control. Then answer: how does QUIC keep a connection alive when your phone switches from WiFi to cellular and its IP changes?

**Read, in order:**

1. `quic-go/internal/ackhandler/sent_packet_handler.go` — loss detection and retransmission. Note that it is packet-level, not byte-level, which is a deliberate difference from TCP
2. `quic-go/internal/congestion/cubic_sender.go` — CUBIC reimplemented in userspace
3. `quic-go/internal/flowcontrol/` — connection-level and stream-level windows
4. `quic-go/connection.go` — search for connection ID handling. **This is the answer to the migration question**: a QUIC connection is identified by an ID, not by the IP/port four-tuple, so the address can change without breaking it
5. `coturn/src/apps/relay/` — a production TURN server. Read how it relays UDP when direct connection is impossible

💡 The reading takeaway: QUIC is roughly "TCP, rebuilt in userspace, on UDP, with per-stream ordering and encryption built in." Seeing how much code that takes is the strongest possible argument against writing your own reliable UDP protocol.

**Part 1 — Feel the rawness.** UDP echo server. Then:

- Send 10,000 datagrams and count how many come back with no loss injected. Note that some may be missing even on loopback under load
- Send datagrams of 500, 1400, 1500, 8000 and 60000 bytes with 1% netem loss. Chart datagram loss rate against size. **Confirm that fragmentation multiplies loss**
- Send from two clients to one server and confirm one socket handles both

**Part 2 — Rebuild TCP, badly.** Design and document a reliable protocol on UDP in `SPEC.md`, then implement:

1. Sequence numbers and gap detection
2. ACKs and retransmission on timeout
3. A sliding window
4. AIMD congestion control — additive increase, multiplicative decrease

Test under 0%, 1%, 5% loss and with reordering. Compare your throughput to real TCP under identical conditions.

**You will lose to TCP.** That is the lesson. Write down in `SPEC.md` the three things TCP does that you did not implement, and what each would cost you.

**Part 3 — Real-time media.** Simulate 50 packets/sec of audio. Implement a jitter buffer and measure the tradeoff: buffer size versus dropout count versus added latency. Chart all three.

Then add XOR-based FEC — one parity packet per three data packets — and measure the recovery rate under 5% loss and the bandwidth cost.

Finally, use **bursty** loss (netem's `loss 5% 25%` correlated model) instead of uniform, and show that FEC performs much worse against bursts. Then interleave the packets before applying FEC and show the improvement. **This is a real technique and understanding why it works is the best part of this drill.**

**Part 4 — Head to head.** Same 5MB payload over TCP and over your protocol, at 0%, 1%, 5% loss and 10ms, 100ms, 300ms RTT. Nine cells, two protocols.

Where does UDP-based transport win, if anywhere? Be honest in `RESULTS.md`.

**Part 5 — The metrics trap.** A StatsD-style sender at 100, 1000, 10000, 100000 metrics/sec to a receiver that is deliberately slow to drain.

Chart metrics sent against metrics received. Watch `netstat -su` drop counters. Find the rate at which you start silently losing data.

Then write the scenario in `FINDINGS.md`: your service is under heavy load, and your metrics show traffic *decreasing*. Explain what actually happened and how you would detect it.

**Done when:**
- Your fragmentation chart shows loss multiplying with datagram size
- Your reliable protocol works and you can name three things TCP does that it does not
- Your jitter buffer chart shows the three-way tradeoff
- Interleaving measurably improves FEC against bursty loss
- Part 5's chart shows the point where metrics silently vanish
