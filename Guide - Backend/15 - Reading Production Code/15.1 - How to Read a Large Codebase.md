# How to Read a Large Codebase

#backend #skills #reading

> **In one line:** Reading a large codebase is not reading — it is answering a specific question by tracing one path, and the skill is choosing the right question and knowing when to stop.

---

## The Idea

⚠️ **The instinct is to start at the top and read down. It does not work.** A 500,000-line codebase has no top, and after two hours of wandering you will have absorbed nothing you can use.

💡 **The method that works: pick one concrete question, find the entry point, trace the path that answers it, and stop.**

```
❌  "I want to understand Postgres"
✅  "What happens on disk when I run one UPDATE?"

❌  "I want to learn Celery"
✅  "How does a task get from apply_async to executing in a worker?"

❌  "I want to understand Kubernetes"
✅  "What happens between kubectl apply and a container running?"
```

⚠️ **A good question has a start point, an end point, and a path between them.** If you cannot name where the trace begins, the question is too broad.

---

## The Method

### 1. Orient before reading

```bash
tokei .                       # what languages, how much
git log --oneline | wc -l     # how mature
ls docs/ *.md                 # what they wrote down
cat CONTRIBUTING.md
```

💡 **Read the architecture documents first if they exist.** Postgres's `README` files, Kubernetes' design proposals and Kafka's design page are frequently better than any book, **and they tell you the vocabulary the code uses** ([[06.2 - Postgres Architecture]]).

```bash
git log --format="%H" --name-only | sort | uniq -c | sort -rn | head -30
```

⚠️ **The most-changed files are the ones that matter.** They are where the domain complexity lives, and they are usually a tiny fraction of the repository.

### 2. Find the entry point

| Kind | Look for |
|---|---|
| Library | The public API — `__init__.py`, `index.js`, the README example |
| Service | `main`, the HTTP router, the CLI parser |
| Framework | The request lifecycle |
| Database | The command dispatcher |

```bash
rg "def main|if __name__|func main" --type py --type go
```

💡 **The tests are often the best entry point.** A test names a behaviour and shows the minimum code to invoke it — **it is a worked example the authors maintain.**

### 3. Trace one path

```
Question: how does a Celery task get executed?

apply_async()          celery/app/task.py
  → send_task()        celery/app/base.py
    → publish()        kombu — the message goes to the broker
                       ─── broker boundary ───
  → blueprint          celery/worker/consumer/consumer.py
    → on_task_received()
      → strategy       celery/worker/strategy.py
        → Request      celery/worker/request.py
          → execute()  celery/app/trace.py
```

💡 **Write the path down as you go.** The artefact is the trace, not the reading — **and a written trace is something you can return to in six months** ([[Assets.1 - Codebase Study Map]]).

⚠️ **Note the boundaries.** The broker boundary above is where the trace stops being a call stack and becomes two processes — **and boundaries are where the interesting design decisions live.**

### 4. Use the debugger, not just your eyes

```python
import pdb; pdb.set_trace()

import sys
def tracer(frame, event, arg):
    if event == "call" and "celery" in frame.f_code.co_filename:
        print(f"{frame.f_code.co_filename}:{frame.f_lineno} {frame.f_code.co_name}")
    return tracer
sys.settrace(tracer)
```

💡 **A breakpoint answers "does this path actually execute" in seconds, where reading answers it in an hour and sometimes wrongly.** Dynamic dispatch, plugin registries and dependency injection all defeat static reading — **and a debugger walks straight through them.**

**For compiled languages:** `dlv` for Go, `gdb` or `rr` for C. **`rr` in particular lets you step *backwards***, which is transformative when tracing how a value became wrong.

### 5. Change something and see what breaks

⚠️ **The fastest way to learn what a piece of code does is to break it.**

```
Change a constant → run the tests → see what fails
Add a log line in a hot path → run the workload → see the order
Delete a check → see which test catches it
```

💡 **If nothing breaks, either you have found dead code or the tests are weak — and both are interesting findings.**

## Reading Strategies by Goal

| Goal | Approach |
|---|---|
| **Understand a mechanism** | Trace one path end to end |
| **Fix a bug** | Reproduce, bisect, then read only the implicated code |
| **Add a feature** | Find the most similar existing feature and copy its shape |
| **Evaluate a library** | Read the tests and the issue tracker, not the source |
| **Learn a pattern** | Find where it appears three times, and compare |

### Bisecting

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.1.0
git bisect run pytest tests/test_thing.py::test_case
```

💡 **`git bisect run` with an automated test finds a regression in a 10,000-commit range in about fourteen steps**, with no reading at all. **Most people know bisect exists and have never used the `run` form.**

### Reading the issue tracker

⚠️ **The most under-used source.** For any subtle behaviour, someone has already asked why.

```
"Why does X do Y?" → search issues → the maintainer explains the design decision
```

💡 **Closed issues and pull request discussions often contain the reasoning the code does not.** For a design question, ten minutes in the issue tracker frequently beats two hours in the source.

## What to Look For

### The domain model

```bash
rg "^class |^type |^struct " --type py | head -50
```

💡 **The core types are the vocabulary.** Understanding what a `Request`, a `Task` and a `Consumer` mean in Celery is most of understanding Celery.

### The boundaries

⚠️ **Where does data enter and leave the system?** Network, disk, other processes. **Boundaries are where serialisation, error handling and the genuinely hard decisions live.**

### The comments that explain "why"

```bash
rg "XXX|HACK|NOTE:|WARNING:|why|because" --type py -i | head -40
```

💡 **A comment explaining why something is unusual is worth more than a hundred lines of ordinary code.** It usually marks a bug fix, a performance constraint, or an interaction nobody expected.

**Postgres's `README` files and Redis's inline comments are exceptional at this.**

### The tests

```bash
ls tests/
rg "def test_" tests/ | wc -l
```

**The test names are a specification.** A file called `test_rebalance_during_shutdown.py` tells you that case matters and is handled.

## In Production

### Reading before contributing

```
1. Build and run it locally
2. Run the test suite. Note how long it takes
3. Find a "good first issue"
4. Reproduce it
5. Trace to the cause
6. Read CONTRIBUTING.md properly
7. Small patch, with a test
```

💡 **Step 1 filters more than expected.** A project you cannot build locally is one you cannot contribute to, and finding that out first saves hours.

### Reading to evaluate a dependency

⚠️ **Do not read the implementation.** Read:

```
□  The issue tracker — open bug count, response time, tone
□  The commit history — is it maintained, or abandoned?
□  The test suite — does it exist, and what does it cover?
□  The dependency tree — how much are you actually adding?
□  The maintainer count — one person is a risk
□  Breaking change history — how disruptive are upgrades?
```

💡 **A library's issue tracker tells you more about what it will be like to depend on than its source ever will** ([[14.4 - Common Vulnerabilities]]).

### Reading production code you own

⚠️ **The same skill applies to your own unfamiliar code, and it is where you will use it most.**

```bash
git log --format="%an" --follow path/to/file.py | sort | uniq -c    # who to ask
git log -S "function_name" --oneline                                # when it appeared
git blame -L 40,60 path/to/file.py                                  # why this line
```

💡 **`git log -S` searches for when a string was added or removed**, which finds the commit that introduced a behaviour far faster than reading. **It is the single most useful git command for archaeology.**

### Keeping what you learn

```markdown
## Celery: task execution path

**Question:** how does a task get from apply_async to running?

**Trace:**
1. `app/task.py:apply_async` — builds the message
2. `app/base.py:send_task` — applies routing
3. kombu publishes to the broker
   ─── process boundary ───
4. `worker/consumer/consumer.py:on_task_received`
5. `worker/strategy.py` — chooses the execution strategy
6. `worker/request.py:Request.execute_using_pool`
7. `app/trace.py:build_tracer` — the actual call

**Surprises:**
- The message is built entirely client-side; the worker does no routing
- `acks_late` changes step 6's ordering, not step 4's
- The strategy is compiled once per task type, not per message

**Answered:** yes. **Time:** 90 minutes.
```

💡 **The "surprises" section is the valuable part.** It is where your model was wrong, **and that is what you will remember.**

### The time budget

⚠️ **Set one before you start, and honour it.**

```
Simple mechanism      30–60 minutes
Complex subsystem     2–3 hours
Whole architecture    a day, and expect only a map
```

💡 **If you have not answered your question in the budget, the question was too broad.** Split it and try again — **do not keep reading hoping it will resolve.**

**Stop when you can explain the answer to someone else without looking.**

## Codebase

**Repo:** Practice on `redis/redis`, `celery/celery`, `postgres/postgres`

**Question to answer:** Apply the method to three codebases of increasing difficulty, producing a written trace for each.

**Read, in order:**

1. **`redis/redis` — "What happens when I run `SET key value`?"** Start at `src/server.c:processCommand`, follow to `t_string.c:setCommand`. **Redis is single-threaded C with excellent comments — the ideal first trace**
2. **`celery/celery` — "How does a task reach a worker?"** The path above. **Crosses a process boundary, which makes it a genuinely different exercise**
3. **`encode/starlette` — "What happens between a request arriving and my handler running?"** Middleware, routing, dependency resolution. **Small enough to read completely**
4. **`postgres/postgres` — "What happens on disk for one `INSERT`?"** ([[06.2 - Postgres Architecture]]). **Large, C, and the READMEs carry you**
5. **Your own codebase — pick the file you understand least** and trace one path through it

💡 Redis is the best codebase in open source for learning to read code. **Single-threaded, no framework magic, thoroughly commented, and every command is a self-contained function.** An hour there teaches the method better than a day in a Java monolith.

**Size:** 2–3 sessions.

## Exercise

**Drill 15.1 — Trace five paths, write five documents**

```
drills/15-reading/
├── traces/{redis_set.md, celery_task.md, starlette_request.md,
│           postgres_insert.md, own_codebase.md}
├── tools/{tracer.py, bisect_practice.sh, git_archaeology.md}
├── evaluation/{dependency_review.md}
└── METHOD.md
```

**Part 1 — Redis `SET`.** Build Redis from source, run it under `gdb`, and set a breakpoint in `setCommand`.

**Trace from the socket read to the value in the hash table.**

**Write `redis_set.md`** with the trace, the boundaries, and three surprises.

⚠️ **Use the debugger, not just reading.** Confirm your traced path is the one that actually executes.

**Part 2 — Celery, across a boundary.** Trace `apply_async` to execution.

**Mark clearly where the process boundary is** and what crosses it.

Then change one thing — set `acks_late=True` — and **trace how the path differs.** Confirm your prediction with a breakpoint.

**Part 3 — Starlette, completely.** Small enough to read in full.

Trace a request through middleware, routing and dependency resolution. **Then write the middleware execution order from memory and verify it.**

⚠️ **This one is worth doing thoroughly** — you use this framework daily, and the request lifecycle explains a whole class of behaviour you currently take on faith.

**Part 4 — Postgres, with the READMEs.** The hardest of the four.

**Read `access/transam/README` first**, then trace an `INSERT` to WAL and to the heap page.

**Budget three hours. Stop when it expires** and write down how far you got — **the discipline of stopping is part of the exercise.**

**Part 5 — Your own codebase.** Pick the file you understand least.

Trace one path through it. **Then use `git log -S` to find when the confusing part was introduced, and `git log --format="%an"` to find who to ask.**

**Write down what the code does and why it is shaped that way.** If you cannot determine why, that is a finding.

**Part 6 — Bisect a real regression.** Take a project with a good test suite, find a commit that broke something (or introduce one in a fork), and **use `git bisect run` to find it automatically.**

**Count the steps.** For a 1,000-commit range it should be about ten.

**Part 7 — Evaluate a dependency without reading it.** Pick a library you are considering.

Answer the six evaluation questions from the issue tracker, commit history and dependency tree — **without reading the implementation.**

**Then write a recommendation.** Compare how long this took against how long reading the source would have.

**Part 8 — Write `METHOD.md`.** Your own version of the method, with what worked and what did not.

**Include your time budgets and how accurate they were.**

**Done when:**
- Five written traces exist, each with boundaries and surprises noted
- At least three traces were verified with a debugger, not just read
- You predicted a behaviour change and confirmed it with a breakpoint
- You stopped one trace at its time budget and documented how far you got
- `git bisect run` found a regression automatically, with the step count recorded
- You evaluated a dependency without reading its source
- `METHOD.md` reflects your actual experience, including what failed
