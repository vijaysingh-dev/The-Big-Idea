# Why React

React exists to solve one problem: **keeping the UI synchronized with application state**. Everything else — the virtual DOM, hooks, the component model — follows from that.

## The problem with imperative DOM code

```js
function updateCart(items) {
  const list = document.querySelector("#cart");
  list.innerHTML = "";

  for (const item of items) {
    const li = document.createElement("li");
    li.textContent = `${item.name} × ${item.qty}`;
    list.append(li);
  }

  document.querySelector("#count").textContent = items.length;
  document.querySelector("#total").textContent = sum(items);
  document.querySelector("#checkout").disabled = items.length === 0;
  document.querySelector("#empty").hidden = items.length > 0;
}
```

This works. The problem appears at scale:

**Every state change needs a matching set of DOM instructions.** Adding a "free shipping over ₹500" badge means touching this function, and every other function that changes items. The number of update paths grows with (state × views), not with either alone.

**The DOM becomes the source of truth.** To know whether checkout is enabled, you read the DOM. Two pieces of code can disagree about the current state, and there is no single place to look.

**Updates are destructive.** `innerHTML = ""` discards event listeners, focus, scroll position and input values ([[12.1 - The DOM Tree and Node APIs]]). Preserving them means writing careful diffing logic by hand, per view.

**Order dependencies accumulate.** Handler A must run before handler B because B reads what A wrote. Nothing in the code says so.

## The declarative alternative

```jsx
function Cart({ items }) {
  return (
    <>
      <ul>{items.map(i => <li key={i.id}>{i.name} × {i.qty}</li>)}</ul>
      <span>{items.length}</span>
      <span>{sum(items)}</span>
      <button disabled={items.length === 0}>Checkout</button>
      {items.length === 0 && <p>Your cart is empty</p>}
    </>
  );
}
```

You describe what the UI **is** for a given state, not what to **do** when state changes. The framework computes the difference and applies the minimum DOM operations.

The mental model becomes `UI = f(state)`. There is exactly one code path from state to UI, so there is exactly one place a rendering bug can be.

## What React actually provides

**Declarative rendering.** Describe the target; React figures out the transition ([[18.2 - Reconciliation and the Diffing Algorithm]]).

**Component composition.** A component is a function from props to UI. They nest, compose and are independently testable — the same reuse model as functions, applied to interfaces.

**Unidirectional data flow.** Data goes down through props, events go up through callbacks. When something is wrong on screen, you trace upward to find the state that produced it. Two-way binding, which frameworks of the 2010s favoured, makes that trace ambiguous.

**A scheduler.** React can interrupt, pause and prioritize rendering work so the main thread stays responsive ([[18.5 - Concurrent Rendering and the Scheduler]]). Hand-written DOM code cannot do this without enormous effort.

## What React does not provide

This is worth being explicit about, because it shapes what else you will need:

- **No routing** — React Router, TanStack Router, or a framework ([[23.1 - Client Side Routing Fundamentals]])
- **No data fetching** — TanStack Query, RTK Query, or a framework's loader ([[24.6 - TanStack Query Fundamentals]])
- **No global state solution** — Context, Redux, Zustand ([[20.1 - Where State Should Live]])
- **No styling opinion** ([[11.5 - CSS Architecture]])
- **No build tooling** — Vite, or a framework

React is a rendering library. The ecosystem around it is the framework, which is a genuine cost: you assemble and maintain those choices yourself, or adopt a meta-framework that makes them for you.

## Is the virtual DOM fast?

The common claim that "React is fast because of the virtual DOM" is wrong and worth correcting, because interviewers ask.

Hand-written, optimal DOM updates are **faster** than React. Diffing a tree is work that a direct `element.textContent = x` does not do.

What React actually offers is **fast enough, without requiring you to be optimal**. It makes the naive approach — re-describe the whole UI on every change — performant enough by avoiding a full DOM rebuild. The value is in the constraint being cheap to maintain, not in raw speed.

Frameworks like Svelte and Solid make a different bet: compile the declarative description into fine-grained updates at build time, skipping the runtime diff entirely. They are genuinely faster. React's counter-argument is that its runtime model enables concurrent rendering and Server Components, which a compile-time approach handles less naturally — and the React Compiler now recovers some of the performance gap ([[19.9 - The React Compiler]]).

## When React is the wrong choice

Reaching for React by default is a real failure mode.

- **A static content site** — a static site generator or plain HTML is faster to build, faster to load and cheaper to host.
- **A page with a few interactive widgets** — vanilla JS, Alpine, or web components carry far less weight than a React runtime.
- **Extreme performance requirements** — data grids with 100k live cells, or 60fps canvas work, often do better with direct DOM or canvas rendering.

React's cost is real: bundle size, a hydration step, and a mental model the whole team must learn. It pays for itself when the application has substantial interactive state, and not before.

## How senior engineers actually use this

**They keep state as the source of truth, always.** Reading the DOM to determine application state is the imperative habit reasserting itself, and it is the root of a whole class of desync bugs.

**They think in `UI = f(state)`.** When something renders wrong, the question is "what state produced this", not "which handler forgot to update this element".

**They know the constraint they accepted.** Re-rendering more than strictly necessary is the price of the model. Optimizing it is a separate discipline ([[19.1 - What Causes Re-renders]]), and premature optimization of it is a common waste of effort.

**They choose React deliberately**, and are comfortable saying a project does not need it.

## Common pitfalls

- Manipulating the DOM directly alongside React, so React overwrites the change on the next render.
- Storing derived values in state instead of computing them during render.
- Using refs to hold state that should trigger re-renders.
- Assuming React is fast by default and skipping measurement.
- Choosing React for a page that has no meaningful state.

## Interview angle

"Why React instead of direct DOM manipulation" should get the declarative-versus-imperative distinction with a concrete cost: every new piece of state multiplies the update paths in imperative code, while declarative code has one. Then `UI = f(state)`, unidirectional flow, and component composition. The differentiating move is refusing the "virtual DOM is fast" claim — it is not faster than optimal manual updates; it makes a maintainable approach fast enough. That answer is unusual and correct.
