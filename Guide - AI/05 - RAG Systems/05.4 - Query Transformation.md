# Query Transformation

## The Query Problem

User queries are often poor retrieval inputs:

- Too short: "Q3 results" → ambiguous, insufficient signal
- Too conversational: "what did they say about growth" → vague pronouns
- Phrased differently from how documents are written
- Multi-part: one query needs multiple searches
- Presupposes context from conversation history

Query transformation closes the gap between how users ask and how documents are indexed.

---

## Technique 1: Query Rewriting

Rewrite the query to be more explicit, specific, and retrieval-optimized:

```python
REWRITE_PROMPT = """
You are a search query optimizer. Rewrite the user's query to be more specific 
and effective for document retrieval.

Rules:
- Make implicit context explicit
- Use precise terminology
- Remove conversational language
- Expand abbreviations
- Resolve pronoun references using conversation history

Conversation history: {history}
User query: {query}

Output only the rewritten query, nothing else.
"""

def rewrite_query(query, history, llm):
    return llm.call(REWRITE_PROMPT.format(query=query, history=history))

# Example:
# Input:  "what did they say about it last quarter?"
# Output: "What did Apple executives say about iPhone revenue in Q3 2024?"
```

**When to use**: Always, especially for conversational interfaces where pronouns and context from previous turns are common.

**Latency cost**: One extra LLM call (~100–300ms). Optimize by using a fast/small model for rewriting.

---

## Technique 2: Query Expansion (Multi-Query)

Generate multiple reformulations of the same query, search with all of them, merge results:

```python
EXPANSION_PROMPT = """
Generate {n} different search queries that would retrieve relevant documents 
for the following question. Each query should approach the topic differently
(different terminology, different aspect, different specificity level).

Question: {question}
Output as JSON array: ["query1", "query2", ...]
"""

def multi_query_retrieve(question, n=3, top_k=10, retriever, llm):
    # Generate multiple queries
    queries_json = llm.call(EXPANSION_PROMPT.format(question=question, n=n))
    queries = json.loads(queries_json) + [question]  # include original
    
    # Retrieve with each query
    all_results = []
    for query in queries:
        results = retriever.search(query, top_k=top_k)
        all_results.extend(results)
    
    # Deduplicate by document ID, keep highest score
    seen = {}
    for result in all_results:
        if result.id not in seen or result.score > seen[result.id].score:
            seen[result.id] = result
    
    return sorted(seen.values(), key=lambda x: x.score, reverse=True)[:top_k]
```

**Why it works**: Different phrasings retrieve different (but relevant) documents. Union of results has higher recall than any single query. Works especially well when:

- Query is ambiguous
- Synonyms matter (the document may use "revenue" but you searched "sales")
- Different aspects of the question are covered in different documents

**Latency**: N × retrieval latency + 1 LLM call. Parallelize all retrieval calls.

## Technique 3: HyDE (Hypothetical Document Embeddings)

Generate a hypothetical ideal answer, embed that, search with the answer embedding:

```python
HYDE_PROMPT = """
Write a brief, factual paragraph that would directly answer this question.
Write as if you have access to relevant documents. Be specific.

Question: {question}
"""

def hyde_retrieve(question, top_k=10, retriever, llm):
    # Generate hypothetical answer
    hypothetical_answer = llm.call(HYDE_PROMPT.format(question=question))
    
    # Embed the hypothetical answer (not the question)
    hyde_embedding = embedding_model.encode(hypothetical_answer)
    
    # Search using hypothetical answer embedding
    return retriever.search_by_vector(hyde_embedding, top_k=top_k)
```

**Why it works**: A hypothetical answer has similar vocabulary and style to real documents, whereas a short question may not. The embedding of "Apple's Q3 2024 revenue was $85B, up 12% year-over-year" is more similar to the actual earnings document than the embedding of "Q3 Apple revenue".

**Risk**: If the hypothetical answer is hallucinated in a misleading direction, it can pull retrieval off-course. Mitigate by combining HyDE with standard query retrieval and merging.

## Technique 4: Step-Back Prompting

For specific queries that require general context, first ask a more abstract question:

```python
STEPBACK_PROMPT = """
Given the specific question below, generate a more general background question 
whose answer would help answer the specific question.

Specific question: {question}
General question:
"""

def stepback_retrieve(question, retriever, llm):
    # Generate abstract question
    general_question = llm.call(STEPBACK_PROMPT.format(question=question))
    
    # Retrieve for both specific and general
    specific_results = retriever.search(question, top_k=5)
    general_results = retriever.search(general_question, top_k=5)
    
    return deduplicate(specific_results + general_results)

# Example:
# Specific: "What was Tesla's free cash flow in Q2 2024?"
# General:  "How does Tesla typically report cash flow metrics?"
```

**When to use**: Highly specific technical queries where general context helps interpretation.

## Technique 5: Decomposition (Sub-Question Generation)

For complex multi-part questions, decompose into atomic sub-questions:

```python
DECOMPOSE_PROMPT = """
Break this complex question into 2-4 simpler sub-questions that can each 
be answered independently. Together, answers to sub-questions should 
enable answering the original question.

Question: {question}
Sub-questions (JSON array):
"""

def decomposed_retrieve(question, retriever, llm):
    sub_questions_json = llm.call(DECOMPOSE_PROMPT.format(question=question))
    sub_questions = json.loads(sub_questions_json)
    
    # Retrieve for each sub-question
    all_context = []
    for sub_q in sub_questions:
        results = retriever.search(sub_q, top_k=3)
        all_context.extend(results)
    
    return deduplicate(all_context)

# Example:
# Original: "How did Apple's iPhone sales in China compare to its competitors last year?"
# Sub-questions:
#   1. "What were Apple's iPhone sales in China in 2023?"
#   2. "What were Samsung's smartphone sales in China in 2023?"
#   3. "What were the major smartphone brands' China market share in 2023?"
```

## Query Transformation Decision Framework

```
Is the query short/ambiguous?
├── Yes → Query rewriting

Does vocabulary mismatch matter?
├── Yes → Multi-query expansion

Is the query very specific (numeric, entity-heavy)?
├── Yes → HyDE (embed hypothetical answer)

Is the query conceptually complex?
├── Yes → Decomposition

Is the query highly specific with needed general background?
└── Yes → Step-back prompting
```

In practice, **rewriting + multi-query** covers 80% of cases. Add others based on your eval.

---

## Latency Considerations

Query transformation adds latency. Strategies to manage:

```
Parallel execution:
  ├── Rewrite query          (LLM call, 150ms)
  ├── Start BM25 search with original query immediately
  └── When rewrite returns, start dense search with rewritten query

Result: total latency ≈ max(rewrite_time, bm25_time) not sum
```

Use small, fast models (GPT-4o-mini, Claude Haiku) for transformation — they don't need to be high-quality reasoners, just good query reformulators.
