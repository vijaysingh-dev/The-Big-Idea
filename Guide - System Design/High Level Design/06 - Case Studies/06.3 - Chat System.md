# Case Study: Chat System (WhatsApp-style)

> **Revision tags:** #case-study #chat #websockets  
> **Related:** [[01.7 - System Patterns]] | [[03.8 - Message Queues and Kafka]]

---

## Requirements Clarification

**Functional:**
- 1-on-1 messaging between users
- Group chats (up to 500 members)
- Message delivery status: sent → delivered → read
- Message history (last N messages per conversation)
- Online presence (show when a user was last active)

**Non-functional:**
- Messages delivered in < 500ms p99 (online users)
- Messages must not be lost (at-least-once delivery)
- Order preserved within a conversation
- 99.99% availability for message delivery
- Scale: 2B users, 100B messages/day

**Out of scope:** Voice/video calls, file sharing > 16MB, end-to-end encryption (design implications noted), bots

---

## Estimation

```
DAU: 500M active users
Messages/day: 100B / 500M DAU = 200 messages/user/day
Peak writes: 100B / 86,400 ≈ 1.16M messages/s
             Peak (3×) ≈ 3.5M messages/s

Storage per message:
  message_id:       8 bytes
  conversation_id:  8 bytes
  sender_id:        8 bytes
  body (avg):       100 bytes
  timestamp:        8 bytes
  status:           1 byte
  ≈ 135 bytes/message

Storage: 100B × 135 bytes = 13.5 TB/day
  → ~5 PB/year → requires distributed storage (Cassandra/HBase)

Concurrent WebSocket connections:
  500M DAU, assume 20% online at peak = 100M concurrent connections
  → Requires dedicated connection management infrastructure
```

**Key challenge:** 100M concurrent WebSocket connections can't fit on a few servers. Connection state must be distributed across a fleet of chat servers.

## Core Design: WebSocket Architecture

### Why WebSockets?

Chat is the canonical use case for WebSockets:
- Server must push messages to clients the instant they arrive (not poll every second)
- Connection is persistent — no HTTP handshake overhead per message
- Bidirectional — client sends, server sends, simultaneously

```
Client A  ──WS──  [Chat Server 1]
Client B  ──WS──  [Chat Server 2]
Client C  ──WS──  [Chat Server 1]
```

### The Routing Problem

Client A (on Server 1) sends a message to Client B (on Server 2). Server 1 doesn't have Client B's WebSocket connection. How does the message get there?

**Solution: Message routing via pub/sub**

```
1. Client A sends message to Server 1 via WebSocket
2. Server 1 persists message to DB
3. Server 1 publishes to Kafka topic: "messages:{conversation_id}"
4. Server 2 (subscribed to that topic) receives message
5. Server 2 pushes to Client B's WebSocket
```

Or more directly using Redis Pub/Sub for lower latency:
```
Server 1 → PUBLISH channel:user:{B_id} {message}
Server 2 (subscribed to channel:user:{B_id}) → receives → pushes to B's WebSocket
```

## Architecture

```
[Client A]  ──WS──  [Chat Server 1]
                           │ (publish)
                           ▼
[Client B]  ──WS──  [Chat Server 2]
                           │ (subscribe)
                    [Redis Pub/Sub]
                           │
                    [Message Store]  (Cassandra)
                           │
                    [Presence Service] (Redis)
                           │
                    [Notification Service] (for offline users)
```

### Detailed Message Flow

```
1. Client A (online, WS to Server 1):
   Sends: { to: B_id, body: "Hello!", client_seq: 1 }

2. Server 1:
   a. Validate sender auth (from WS session)
   b. Generate message_id (Snowflake ID — timestamp + server_id + seq)
   c. Write to Cassandra: messages table
   d. ACK to Client A: { message_id, status: "sent" }
   e. Check presence: is B online?

3a. If B is online (has active WS):
   Server 1 → PUBLISH to Redis: channel:user:{B_id}
   Server 2 (has B's WS) → receives from Redis → pushes to B
   B's client → sends ACK: { message_id, status: "delivered" }
   Server 2 → updates message status → notifies A: "delivered"

3b. If B is offline:
   Server 1 → enqueue push notification → APNs/FCM
   B opens app → WS connects → fetches missed messages from Cassandra
```

## Data Model

### Message Storage (Cassandra)

Cassandra is ideal: write-heavy, partition by conversation, query by time range.

```cql
CREATE TABLE messages (
    conversation_id  UUID,
    message_id       BIGINT,    -- Snowflake ID (embeds timestamp)
    sender_id        BIGINT,
    body             TEXT,
    msg_type         TINYINT,   -- 0=text, 1=image, 2=video
    status           TINYINT,   -- 0=sent, 1=delivered, 2=read
    created_at       TIMESTAMP,
    PRIMARY KEY (conversation_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

**Why Cassandra:**
- Partition key `conversation_id` → all messages for a conversation on the same node
- Clustering key `message_id` (DESC) → newest messages first
- Linear write scale — add nodes, get proportionally more write throughput
- Compaction handles the massive write volume efficiently

### Conversations Table

```cql
CREATE TABLE user_conversations (
    user_id          BIGINT,
    conversation_id  UUID,
    last_message_id  BIGINT,
    last_message_preview TEXT,
    updated_at       TIMESTAMP,
    PRIMARY KEY (user_id, updated_at)
) WITH CLUSTERING ORDER BY (updated_at DESC);
```

Query: "show this user's conversations, newest first" → partition by `user_id`, cluster by `updated_at DESC`.

### Presence Store (Redis)

```
Key:   presence:{user_id}
Value: last_seen timestamp (unix ms)
TTL:   60 seconds (refreshed while user is online)

User online:  SET presence:{user_id} {now} EX 60
User opens:   GET presence:{user_id} → if exists, online
Last seen:    on disconnect, SET presence:{user_id} {now} PX 86400000 (1 day, no refresh)
```

## Message Ordering and Sequence Numbers

### The Problem

Messages sent from different devices or after reconnects can arrive out of order.

### Solution: Snowflake IDs as message_id

Snowflake IDs embed a timestamp — sorting by `message_id` gives chronological order without a separate `created_at` sort.

```
Snowflake ID (64 bits):
  [41 bits: ms timestamp][10 bits: machine_id][12 bits: sequence]
```

Within a single conversation, this guarantees monotonically increasing IDs in real time.

**Client-side gap detection:** Client tracks the highest `message_id` seen. If a new message arrives with `id > last_id + 1`, it knows it missed a message and requests a backfill from the server.

## Group Chat Fan-Out

For a group of 500 members:

```
User A sends message to group G
    │
    ▼
Server writes message to Cassandra (once)
    │
    ▼
Server publishes to topic: group:{G_id}
    │
All chat servers subscribed to group:{G_id}:
  Server 1 → pushes to members [B, C, D] connected here
  Server 2 → pushes to members [E, F] connected here
  ...
```

**Offline members:** Push notification via APNs/FCM at delivery time.  
**Very large groups (10K+ members):** Fan-out is expensive. WhatsApp limits groups to 1024 members partially for this reason. Beyond that, use broadcast channels (one-way, like Telegram channels).

## End-to-End Encryption (Design Note)

WhatsApp uses the Signal Protocol. Key design implication:

```
Server never sees plaintext message content.
Server stores:
  - Encrypted ciphertext
  - Envelope metadata (sender, recipient, timestamp)
  - Key exchange messages (for session establishment)

Server CANNOT:
  - Read messages
  - Decrypt on behalf of law enforcement
  - Restore message history on new device (no server-side plaintext)
```

This shifts the architecture significantly: message storage is just ciphertext blobs. The content model is simpler (no search, no server-side rendering). Key management is the complex part.

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Chat server crashes | WebSocket connections dropped | Clients reconnect + fetch missed messages from Cassandra |
| Redis Pub/Sub unavailable | Messages not forwarded between servers | Fall back to polling Cassandra for new messages; degrade to 1s delivery |
| Cassandra node down | Write failures for some partitions | Replication factor 3; quorum writes (W=2) tolerate 1 node loss |
| Message delivery confirmed but DB write failed | Message lost | Write to DB before ACKing client |
| Network partition (client offline) | Messages missed | Store in Cassandra; deliver as offline messages on reconnect |

## What This Design Demonstrates

- WebSocket connection state distributed across a fleet of servers
- Redis Pub/Sub for cross-server message routing
- Cassandra data model designed for the access pattern (partition by conversation)
- Snowflake IDs for ordered message_ids without coordination
- Presence as a TTL-based Redis key
- Online vs offline delivery path distinction
