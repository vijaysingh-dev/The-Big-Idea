# Cache Strategies and Invalidation

#backend #caching #patterns

> **In one line:** Four ways to read through a cache, four ways to write through one, and one genuinely hard problem — knowing when a cached value has become wrong.

---

## The Read Strategies

### Cache-aside (lazy loading)

```python
async def get_document(doc_id: str) -> Document:
    key = f"doc:{doc_id}"
    if cached := await redis.get(key):
        return Document.model_validate_json(cached)

    doc = await repo.get(doc_id)
    if doc:
        await redis.setex(key, 300, doc.model_dump_json())
    return doc
```

| Good | Bad |
|---|---|
| Only caches what is actually read | Every miss pays full latency |
| Cache failure degrades to the database | Cold cache after a deploy |
| Simple, and the code is obvious | The stampede problem ([[07.3 - Stampede Hot Keys and Negative Caching]]) |

💡 **The application owns the caching logic**, so it is visible in the code rather than hidden in a library. **That transparency is worth more than it sounds when debugging.**

### Read-through

Same behaviour, logic centralised. **Better when many code paths need the same cached entity** — the loader is defined once and every caller benefits.

### Refresh-ahead

```python
if remaining < ttl * threshold:
    spawn(load_and_cache(key))        # refresh in the background
return value
```

💡 **Users never wait for a refresh on a hot key.** The cost is refreshing keys that were about to stop being read anyway.

**This is `stale-while-revalidate` at the application layer** ([[03.5 - HTTP Caching]]), and one of the most effective stampede defences.

### Cache warming

⚠️ **Warming matters more than people expect after a deploy.** A rolling deploy replaces every pod, every in-memory cache is empty, and if you rely on a 95% hit ratio the database sees a large spike ([[07.1 - Cache Layers Across One Request]]).

💡 **Warm in the readiness probe path**, so a pod does not receive traffic until its cache is populated. **That turns a deploy spike into a slower deploy, which is a much better trade.**

## The Write Strategies

### Write-around (the default)

```python
doc = await repo.update(doc_id, data)
await redis.delete(f"doc:{doc_id}")
```

**Delete, do not update.** The next read repopulates with the authoritative value.

💡 **Deleting is safer than writing a new value into the cache**, because a concurrent write ordering problem produces a miss rather than a permanently wrong value.

⚠️ **The ordering matters and the naive version has a race:**

```
Reader:  cache miss, reads DB → gets old value
Writer:  updates DB
Writer:  deletes cache key
Reader:  writes the OLD value into the cache      ← stale forever
```

```python
await redis.delete(key)
doc = await repo.update(doc_id, data)
await redis.delete(key)                # "delayed double delete"
```

Or use a short TTL so the damage is bounded, or versioned keys (below).

### Write-through

The cache is always warm. **The cost is writing on every write, including for data nobody reads**, and the write path now depends on the cache.

### Write-behind

⚠️ **Fast writes, and you can lose data.** If the cache dies before the flush, those writes are gone.

**Only acceptable when loss is tolerable** — view counters, analytics, last-seen timestamps. **Never for anything a user believes they saved.**

| Data | Strategy |
|---|---|
| Standard entities | Write-around (delete on write) |
| Read constantly right after writing | Write-through |
| High-volume counters where loss is fine | Write-behind |
| **Anything a user expects to persist** | **Never write-behind** |

## Key Design

### Versioned keys

```python
async def get_document(doc_id: str) -> Document:
    version = await redis.get(f"doc:{doc_id}:ver") or "0"
    key = f"doc:{doc_id}:v{version}"
    ...

async def update_document(doc_id: str, data):
    doc = await repo.update(doc_id, data)
    await redis.incr(f"doc:{doc_id}:ver")     # old keys become unreachable
```

💡 **Versioned keys make invalidation atomic and race-free.** You never delete anything — you bump a counter, and every old key becomes unreachable and expires naturally. **This eliminates the read-writes-stale-value race entirely.**

**Reach for this when correctness matters more than the extra round trip.**

### Namespace invalidation

```python
async def invalidate_org(org_id: str):
    await redis.incr(f"ns:org:{org_id}")

async def cache_key(org_id: str, suffix: str) -> str:
    ns = await redis.get(f"ns:org:{org_id}") or "0"
    return f"org:{org_id}:v{ns}:{suffix}"
```

**One `INCR` invalidates every cached value for an organisation.**

⚠️ **Do not use `KEYS` or `SCAN` for invalidation.** `KEYS` blocks Redis entirely on a large keyspace; `SCAN` is non-blocking, slow and racy. **Namespace versioning is the correct alternative and it is O(1).**

### Query result caching

⚠️ **Query results are much harder to invalidate than entities**, because one document changing affects an unknowable number of cached queries.

| Approach | |
|---|---|
| **Short TTL** | 30–60s. Simple, and usually sufficient |
| Namespace version per org | One write invalidates all that org's query caches |
| Dependency tracking | Record which entities each query touched; purge by entity |
| **Do not cache queries** | Cache the entities, let the query run |

💡 **The last option is underrated.** If your query is fast because it is well-indexed and only the entity fetches were slow, **caching entities and running the query fresh gives you correctness with most of the benefit.**

## Invalidation

| Approach | Consistency | Complexity |
|---|---|---|
| **TTL only** | Stale up to the TTL | Trivial |
| Event-driven | Near-immediate | Medium |
| Dependency tracking | Precise | High |

**TTL is the right default**, and the honest reason is that most data can be a minute stale without anyone noticing.

⚠️ **Match the TTL to how often the data actually changes, not to how fresh you would like it.** A configuration value changing monthly, cached for 30 seconds, gives you 86,000 needless database queries per day.

### Event-driven invalidation

💡 **CDC-driven invalidation is the most robust version**, because it catches writes from migrations, admin scripts and other services — **everything that touches the database, not just the code paths you remembered** ([[09.4 - Change Data Capture]]).

### Multi-layer invalidation

⚠️ **Invalidating Redis does not invalidate the in-process caches on forty pods.**

```python
async def invalidate(key: str):
    await redis.delete(key)
    await redis.publish("cache:invalidate", key)
```

⚠️ **Redis pub/sub is fire-and-forget** — a pod briefly disconnected misses the message and keeps a stale value indefinitely ([[04.6 - Scaling Long Lived Connections]]).

**Always pair pub/sub invalidation with a short local TTL as a backstop**, so a missed message costs you seconds rather than forever.

## In Production

### TTL with jitter

```python
ttl = base_ttl + random.randint(0, base_ttl // 4)
```

💡 **Without jitter, everything cached during a warm-up expires together**, producing a synchronised miss storm at exactly the same interval forever. **Same reasoning as retry jitter, and it is one line.**

### Serialisation matters more than you think

```
json.dumps(doc)            ~1.2 ms for a 50KB object
orjson.dumps(doc)          ~0.25 ms
msgpack.packb(doc)         ~0.20 ms, ~30% smaller
pickle.dumps(doc)          fast, and ⚠️ never for untrusted data
```

⚠️ **For a large cached object, deserialisation frequently costs more than the Redis round trip.** A cache hit taking 3ms to deserialise against a 5ms database query is barely worth having.

**Measure the full cost of a hit**, then consider caching a smaller projection rather than the whole object.

### Negative caching

```python
if doc is None:
    await redis.setex(f"doc:{doc_id}", 30, NULL_SENTINEL)   # cache the absence
    return None
```

⚠️ **Without it, repeated requests for a non-existent key hit the database every time** — a trivially exploitable amplification vector.

**Use a shorter TTL for negatives than positives** ([[07.3 - Stampede Hot Keys and Negative Caching]]).

### Memory and eviction

| Policy | Use for |
|---|---|
| `allkeys-lru` | A pure cache |
| **`allkeys-lfu`** | **Better when access frequency is skewed** — which most caches have |
| `volatile-lru` | Only evict keys with a TTL. For mixed cache and non-cache data |
| `noeviction` | Writes fail when full. Not for a cache |

⚠️ **Using one Redis for caching and durable data (queues, locks, sessions) with `allkeys-lru` means your locks can be evicted.** Either separate the instances, or use `volatile-lru` with TTLs only on cache keys.

💡 **`allkeys-lfu` is usually better than LRU for a skewed access pattern.** LRU evicts a very popular item that happened not to be read in the last minute; LFU keeps it.

### Monitoring

```python
cache_hit_ratio.labels(prefix="doc").set(hits / (hits + misses))
cache_serialisation_duration.observe(elapsed)
cache_invalidations_total.labels(reason="write").inc()
cache_stale_served_total.inc()
```

⚠️ **A rising `evicted_keys` count means your working set exceeds `maxmemory`**, and your hit ratio will be degrading. **It is the leading indicator that you need more memory or shorter TTLs.**

### The consistency you are actually offering

```
Documents:      eventually consistent, up to 60s
Permissions:    strongly consistent — never cached
Org config:     eventually consistent, up to 5m, invalidated on write
Search results: eventually consistent, up to 30s
Counters:       eventually consistent, up to 5m, may lose recent increments
```

💡 **This table belongs in your architecture documentation**, and producing it usually reveals at least one value cached with a consistency guarantee nobody would have agreed to if asked directly.

## Codebase

**Repo:** `redis/redis`, `django/django`, `sqlalchemy/dogpile.cache`

**Question to answer:** How does Redis decide which key to evict under `allkeys-lru`, and why is it approximate? Then: how does dogpile.cache prevent a stampede, and what does it do with the stale value while regenerating?

**Read, in order:**

1. `redis/src/evict.c` — **`performEvictions` and the eviction pool.** Redis samples N keys rather than maintaining a true LRU list. **The comments explain why: a true LRU would cost memory and a linked-list update on every access**
2. `redis/src/expire.c` — lazy plus active expiry, and why memory does not free at the TTL
3. `django/django/core/cache/backends/base.py` — the cache API design, including `get_or_set` and the atomic operations
4. `dogpile.cache/dogpile/lock.py` — **`Lock.__enter__`.** The stampede answer: one caller regenerates while others receive the stale value
5. `dogpile.cache/dogpile/cache/region.py` — `get_or_create`, and the `expiration_time` versus hard-expiry distinction

💡 dogpile.cache is worth reading because **it separates "this value is stale" from "this value is gone"** — the distinction that makes `stale-while-revalidate` possible at the application layer. **Most naive implementations conflate them and therefore cannot avoid the stampede.**

**Size:** 1 session.

**Part 1 — Six strategies, one workload.** Measure for each: hit ratio, p50 and p99 latency, database queries per second, cache writes per second, and cold-start behaviour.

**Six rows, six columns.** Then state which you would use for each of Conduit's five main cached values.

**Part 2 — The stale-write race.** Reproduce it deterministically:

```
1. Reader begins, cache miss, reads the database (add a delay here)
2. Writer updates the database and deletes the cache key
3. Reader writes its stale value into the cache
```

**Confirm the cache now holds a permanently stale value.**

Then fix it three ways — delayed double delete, versioned keys, and a short TTL — and measure the residual staleness window for each. **Versioned keys should eliminate it entirely.**

**Part 3 — Namespace invalidation versus `KEYS`.** 1 million keys under one organisation prefix.

Invalidate with `KEYS ... DEL` and **measure how long Redis is blocked. Confirm other operations stall.**

Then with `SCAN`, measuring duration and the race window. Then with namespace versioning — **a single `INCR`.**

**Part 4 — Query result caching.** Cache paginated, filtered document lists.

Update one document and determine which cached queries are now wrong. **Implement three invalidation approaches and measure staleness, invalidation cost per write, and complexity.**

Then implement the "cache entities, not queries" alternative and compare end-to-end latency. **It may well win, and knowing that prevents a lot of unnecessary complexity.**

**Part 5 — Serialisation benchmark.** Objects of 1KB, 50KB and 1MB with `json`, `orjson`, `msgpack` and `pickle`.

**Then compute total cache hit cost — network plus deserialisation — and compare against the database query it replaces.**

**Find the object size at which caching stops being worthwhile with `json` and is still worthwhile with `msgpack`.**

**Part 6 — Multi-layer invalidation.** Three pods with in-memory caches plus shared Redis.

**Measure how long each pod serves stale data** with: no local invalidation, pub/sub invalidation, and pub/sub plus a 5-second local TTL.

Then disconnect one pod from Redis for 10 seconds during an invalidation and **confirm it misses the message. Show that the TTL backstop bounds the damage.**

**Part 7 — Eviction under pressure.** `maxmemory` below your working set.

Compare `allkeys-lru` and `allkeys-lfu` under a skewed pattern (80% of reads to 5% of keys).

Then put distributed locks in the same Redis with `allkeys-lru` and drive it to eviction. **Confirm a lock gets evicted and demonstrate the resulting correctness failure** ([[07.4 - Distributed Locks Done Right]]). Then fix with `volatile-lru`.

**Done when:**
- Your six-strategy table is complete, with a recommendation per Conduit value
- The stale-write race is reproduced deterministically and eliminated by versioned keys
- You have measured `KEYS` blocking Redis, and namespace versioning replacing it
- You know whether caching queries beats caching entities for your workload
