# DNS

#backend #networking #dns

> **In one line:** DNS turns names into addresses through a chain of caches you do not control, and almost every DNS incident is a caching problem rather than a lookup problem.

---

## The Idea

Your code says `db.internal`. The network needs `10.0.4.17`. DNS is the lookup.

It sounds like a solved problem, and the lookup itself is. What is not solved is that **the answer is cached in five different places with five different lifetimes**, and when you change a record, those caches update at their own pace. Every serious DNS incident lives in that gap.

There is a well-worn joke — *"it's always DNS"* — and the reason it is always DNS is that DNS is the only part of your infrastructure where a change takes effect at an unpredictable time in an unpredictable order across your fleet.

---

## The Resolution Path

```
Your app: getaddrinfo("api.example.com")
   │
   ├─► process-level cache?           (your language runtime, your HTTP client)
   ├─► OS cache?                      (nscd, systemd-resolved, macOS mDNSResponder)
   ├─► /etc/hosts?                    (always wins if present)
   ├─► recursive resolver             (your ISP, 8.8.8.8, or coredns in your cluster)
   │      ├─► its own cache?
   │      ├─► root servers      "who handles .com?"
   │      ├─► TLD servers       "who handles example.com?"
   │      └─► authoritative     "api.example.com is 93.184.216.34"
   │
   └─► answer, plus a TTL
```

A cold lookup is 3–4 round trips. A cached one is microseconds. In practice almost every lookup is cached — which is the whole point and the whole problem.

---

## Record Types Worth Knowing

| Type | Holds | Used for |
|---|---|---|
| `A` | IPv4 address | The common case |
| `AAAA` | IPv6 address | Increasingly the common case |
| `CNAME` | Another name | Aliases. Cannot coexist with other records at the same name |
| `TXT` | Arbitrary text | Domain verification, SPF, DKIM |
| `MX` | Mail servers | Email routing |
| `NS` | Nameservers | Delegation |
| `SRV` | Host **and port** | Service discovery — used by Kubernetes and Consul |
| `PTR` | Name from an IP | Reverse lookups, logging |
| `SOA` | Zone metadata | Includes the negative-caching TTL |

⚠️ **`CNAME` cannot exist at the zone apex** (`example.com` itself), because the apex must have `SOA` and `NS` records and `CNAME` cannot coexist with anything. This is why cloud providers invented `ALIAS` and `ANAME` records — non-standard, provider-specific, and the reason apex domain setup is annoying on every platform.

## TTL and the Caching Problem

Every answer comes with a TTL — how long it may be cached.

```
api.example.com.    300    IN    A    93.184.216.34
                     ▲
                   cache for 300 seconds
```

### What TTL actually controls

| TTL | Meaning | Cost |
|---|---|---|
| 30s | Fast failover | More queries, more resolver load |
| 300s | Common default | Up to 5 minutes of stale answers |
| 3600s | Low query volume | An hour of staleness. Painful during an incident |
| 86400s | Static records only | A full day. Never for anything that moves |

⚠️ **TTL is a promise about the *maximum* cache time, and plenty of resolvers ignore it.** Some enforce a minimum. Some cache indefinitely on failure. Java historically cached DNS **forever** by default (`networkaddress.cache.ttl=-1`), which caused years of outages during failovers.

### Lowering TTL before a migration

The standard playbook:

```
T−48h:  lower TTL from 3600 to 60
        (must wait a full old-TTL period for caches to pick up the new TTL)
T−0:    change the record
T+5m:   verify from multiple resolvers
T+24h:  raise TTL back
```

💡 **The step people forget is the first wait.** Lowering the TTL only helps once the *old* TTL has expired everywhere. Lowering it an hour before a cutover, when the old TTL was 3600, achieves nothing.

### Negative caching

A failed lookup is also cached, with a TTL from the zone's `SOA` record.

⚠️ This is a genuinely nasty failure mode. You create a new record; a client looked it up 30 seconds before it existed; that client now has a cached `NXDOMAIN` for however long the negative TTL says — often an hour. Your new service is unreachable from some clients and perfectly reachable from others, and nothing in your logs explains why.

**Check the negative TTL in your `SOA` record.** Most people have never looked at it.

## DNS Is Not Load Balancing

Multiple `A` records look like load balancing:

```
api.example.com.  60  IN  A  10.0.1.5
api.example.com.  60  IN  A  10.0.1.6
api.example.com.  60  IN  A  10.0.1.7
```

Resolvers typically return them in rotating order. But:

| Problem | Effect |
|---|---|
| No health awareness | A dead server keeps being returned until you edit DNS |
| Clients cache one answer | A client may pin to one IP for the TTL, or forever |
| Uneven distribution | Depends entirely on client behaviour |
| Failover is TTL-limited | Minutes at best |
| Many clients use only the first result | Effectively no balancing at all |

💡 **DNS round-robin is a crude distribution mechanism, not load balancing.** Use it to spread traffic across load balancers, never as your load balancing layer. Real load balancing needs health checks and per-request decisions — see [[03.10 - Proxies and Load Balancers]].

## DNS in Python

### The blocking problem

```python
socket.getaddrinfo("api.example.com", 443)
```

This is **synchronous and blocking**. In an async service it stalls the event loop ([[01.6 - The Blocking Call Problem]]).

asyncio runs it in a thread pool by default:

```python
await loop.getaddrinfo(host, port)     # runs in the default executor
```

⚠️ **Two consequences.** First, DNS lookups consume threads from a shared pool — a slow resolver can exhaust it and block unrelated work. Second, the default executor is `min(32, cpu+4)` threads, so a burst of cold lookups queues.

Symptom: connections that intermittently take 5 seconds to establish, with no pattern, while the service is otherwise healthy.

For a fix, use a genuinely async resolver:

```python
import aiodns
resolver = aiodns.DNSResolver()
result = await resolver.query("api.example.com", "A")
```

`aiohttp` can use this directly. `httpx` currently goes through `getaddrinfo`.

### Python does not cache DNS

Unlike Java, Python has no built-in DNS cache. Every `getaddrinfo` goes to the OS, which may or may not cache depending on configuration.

This is usually good — you get fresh answers — but it means a resolver outage hits you immediately and hard. Some HTTP clients add their own caching layer; check yours.

## DNS in Kubernetes

Kubernetes DNS deserves its own section because it has a distinctive and very common performance problem.

### How it works

```
my-service.my-namespace.svc.cluster.local
    │          │          │        │
  service  namespace   type    cluster domain
```

CoreDNS runs as a cluster service and resolves these names to service ClusterIPs.

### The ndots problem

```
# /etc/resolv.conf in a typical pod
search my-namespace.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`ndots:5` means: **if a name has fewer than 5 dots, try each search domain first before trying the name as-is.**

So looking up `api.example.com` (2 dots) does:

```
1. api.example.com.my-namespace.svc.cluster.local   → NXDOMAIN
2. api.example.com.svc.cluster.local                → NXDOMAIN
3. api.example.com.cluster.local                    → NXDOMAIN
4. api.example.com                                  → finally, the answer
```

**Four lookups**, and with IPv4 and IPv6 queried in parallel, eight DNS queries for one external hostname.

⚠️ This is one of the most common sources of unexplained latency and CoreDNS load in Kubernetes clusters. At scale it can saturate CoreDNS entirely.

Fixes:

```yaml
# Per-pod: reduce ndots
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
```

```python
# Or use a fully qualified name with a trailing dot — skips the search list entirely
httpx.get("https://api.example.com./users")
```

That trailing dot is real, valid, and almost unknown. It tells the resolver the name is absolute.

Also worth knowing: **NodeLocal DNSCache**, a per-node caching DNS agent that removes most of this traffic. If your cluster is large and CoreDNS is hot, this is the standard fix.

## In Production

### Diagnosing

```bash
# Basic lookup with timing
dig api.example.com

# Follow the full delegation chain from the root
dig +trace api.example.com

# Ask a specific resolver — bypasses your local cache
dig @8.8.8.8 api.example.com

# What TTL is left on the cached answer?
dig api.example.com | grep -A1 "ANSWER SECTION"

# The negative caching TTL
dig SOA example.com

# What is your app actually using?
cat /etc/resolv.conf
```

💡 **`dig +trace` is the one to know.** It bypasses caches entirely and walks from the root, showing you the real current state of the record versus what your cache believes. During a DNS incident, comparing `dig` and `dig +trace` immediately tells you whether the problem is the record or the cache.

### The failure modes

| Symptom | Likely cause |
|---|---|
| Some clients see the new IP, some the old | TTL expiry in progress. Wait |
| New record unreachable from some places | Negative caching from a lookup before it existed |
| Intermittent 5s connection delays | Resolver timeout and retry, often ndots |
| Works with IP, fails with hostname | Resolver config, or search domain issues |
| Fails only in the cluster | CoreDNS, ndots, or NetworkPolicy blocking port 53 |
| Fails only after hours of uptime | A client caching DNS forever |
| Latency spike affecting everything | CoreDNS overloaded. Check its CPU and query rate |

### Timeouts

```
/etc/resolv.conf:
  options timeout:2 attempts:2
```

Defaults are often `timeout:5 attempts:2` — **ten seconds** before a lookup fails. That is far longer than most services' entire request budget.

Set these explicitly in your pod spec. A DNS lookup should fail fast and let your retry logic handle it, not consume your whole timeout budget.

### Monitor DNS as a dependency

It is a dependency like any other, and it is usually the least monitored.

```python
start = time.perf_counter()
addrs = await loop.getaddrinfo(host, port)
dns_lookup_seconds.labels(host=host).observe(time.perf_counter() - start)
```

Alert on p99 lookup time. In a well-behaved cluster this should be single-digit milliseconds. When it is not, you find out before your users do.

## Codebase

**Repo:** `coredns/coredns` and `saghul/aiodns` / `c-ares`

**Question to answer:** In CoreDNS, trace a query for `my-service.default.svc.cluster.local` through the plugin chain. Which plugin answers it, and where does caching happen? Then: how does c-ares perform lookups without blocking, and what does it do that `getaddrinfo` cannot?

**Read, in order:**

1. `coredns/plugin/kubernetes/` — how a service name becomes an IP. Start at `kubernetes.go` and `handler.go`
2. `coredns/plugin/cache/` — the caching plugin. Note how it handles negative caching separately
3. `coredns/plugin/forward/` — what happens to names CoreDNS does not own
4. `coredns/core/dnsserver/server.go` — the plugin chain assembly
5. `c-ares` — `ares_process.c` and `ares_send.c`. It is C, but the design is the interesting part: fully non-blocking, its own socket handling, no `getaddrinfo`

💡 The insight from the c-ares reading: `getaddrinfo` is blocking because it is a *system* call path that also consults `/etc/hosts`, NSS modules, mDNS and more. c-ares talks DNS directly over UDP and skips all of it. That is why it is async-friendly — **and also why it can behave differently from the rest of your system.** That tradeoff is worth understanding before you swap resolvers.

Then time a cold lookup versus a warm one. Then flush your OS cache and do it again. Build a table of cold/warm/OS-cached timings.

**Part 2 — Run your own zone.** Docker with `bind9` or `coredns` as an authoritative server for a test zone.

- Set a record with TTL 60. Change it. Measure exactly how long until resolvers see the change
- Repeat with TTL 3600. Measure again
- Now do the migration playbook properly: lower the TTL, wait a full old-TTL period, change the record. Measure. **Then do it wrong** — lower the TTL and change immediately — and measure the difference

That comparison is the entire content of the TTL section, proven.

**Part 3 — The negative caching trap.** Look up a name that does not exist. Then create it. Measure how long before it resolves.

**Part 4 — DNS blocks your event loop.** Run a resolver that takes 3 seconds to answer. Point an async service at it. Have it make 50 concurrent requests to 50 different hostnames.

Then fix it with `aiodns` and measure again. Then fix it a second way — a DNS cache in front — and compare.

**Part 5 — ndots, measured.** In a local Kubernetes cluster (kind or k3s), run a pod that resolves an external hostname 1000 times. Count actual DNS queries with `tcpdump` on port 53.

Then set `ndots:2` and repeat. Then use a trailing-dot FQDN and repeat.

Three numbers. The first one will be roughly 4–8× the third. **This is the most immediately actionable thing in this note** and you should be able to quote the ratio from memory afterwards.

**Part 6 — Instrument it.** Add DNS lookup timing metrics to Conduit. Set explicit resolver timeouts. Add an alert rule. Write the runbook entry for "DNS latency high" with the exact `dig` commands.
