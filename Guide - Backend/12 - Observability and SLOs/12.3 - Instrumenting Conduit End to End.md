# Instrumenting Conduit End to End

#backend #observability #project

> **In one line:** One document upload crosses HTTP, a database, an outbox, a broker, four consumers and an object store — and this note makes that entire journey one trace, one set of metrics, and one answerable question.

---

## The Journey

```
Browser
  │ POST /documents
Gateway ─────────────────────────────────── span: gateway.upload
  │ gRPC
Document service ────────────────────────── span: documents.create
  ├─ object storage put ───────────────────── span: s3.put
  ├─ postgres INSERT (document + outbox) ──── span: db.insert
  │
Outbox relay ────────────────────────────── span: outbox.publish
  │
Kafka ─────────────────────────────────────── (headers carry trace context)
  │
Ingestion worker ────────────────────────── span: ingest.extract
  ├─ text extraction ──────────────────────── span: extract.pdf
  ├─ chunking ─────────────────────────────── span: chunk
  ├─ embedding API ────────────────────────── span: embed.openai
  └─ postgres INSERT chunks ───────────────── span: db.insert_chunks
  │
Search indexer ──────────────────────────── span: index.upsert
```

💡 **The question this must answer: "the user uploaded a document 12 minutes ago and it is still not searchable — where is it?"**

⚠️ **Without end-to-end tracing that question takes an hour and five log searches. With it, it takes thirty seconds.**

## Trace Context Across the Boundaries

### HTTP → gRPC

```python
# Gateway
with tracer.start_as_current_span("gateway.upload") as span:
    span.set_attribute("org.id", org_id)
    span.set_attribute("document.size_bytes", size)
    response = await documents_client.create(request)      # auto-instrumented
```

**gRPC and HTTP propagation are handled by the OpenTelemetry instrumentation libraries.** Install them and it works.

### Application → Database

```python
DatabaseInstrumentor().instrument()
```

⚠️ **Enable statement capture carefully.** Full SQL in span attributes is useful and can leak data — **capture the statement without parameters.**

```python
span.set_attribute("db.statement", "SELECT * FROM documents WHERE org_id = $1")
```

### The outbox → Kafka boundary

**This is the one that must be done by hand, and the one that is usually missing** ([[12.1 - Observability Recap and Gaps]]).

```python
# Writing the outbox row — capture the CURRENT trace context
carrier: dict[str, str] = {}
TraceContextTextMapPropagator().inject(carrier)

await conn.execute(
    "INSERT INTO outbox (event_type, payload, trace_context) VALUES ($1, $2, $3)",
    "document.created", payload, json.dumps(carrier),
)
```

```python
# Relay — restore the context and continue the trace
ctx = TraceContextTextMapPropagator().extract(json.loads(row["trace_context"]))
with tracer.start_as_current_span("outbox.publish", context=ctx):
    await producer.send(topic, value=row["payload"], headers=list(carrier.items()))
```

```python
# Consumer — extract from the message headers
ctx = TraceContextTextMapPropagator().extract(dict(msg.headers))
with tracer.start_as_current_span("ingest.extract", context=ctx):
    await process(msg)
```

💡 **Storing the trace context in the outbox row is what makes the whole thing work.** The relay runs seconds or minutes later, in a different process, with no ambient context — **the row carries it.**

⚠️ **Use links rather than a parent-child relationship when the consumer runs much later.** A trace spanning 12 minutes is unwieldy, and most backends have a maximum trace duration.

```python
link = trace.Link(trace.get_current_span(ctx).get_span_context())
with tracer.start_as_current_span("ingest.extract", links=[link]):
    ...
```

💡 **Links preserve the causal connection without forcing one enormous trace**, and this is the right choice for anything asynchronous with a long delay.

### The business-level correlation

⚠️ **Even with links, jumping between traces is manual.** Add a stable business identifier to every span:

```python
span.set_attribute("document.id", doc_id)
span.set_attribute("org.id", org_id)
```

💡 **Now "show me everything that happened to `doc_42`" is one query across all traces.** This is the single most useful attribute in the whole system, **and it costs one line per span.**

## The Metrics That Answer Conduit's Questions

### "Is the pipeline keeping up?"

```python
ingestion_queue_depth.labels(stage=...).set(depth)
ingestion_oldest_pending_seconds.labels(stage=...).set(age)
ingestion_stage_duration_seconds.labels(stage=...).observe(elapsed)
ingestion_documents_total.labels(stage=..., result=...).inc()
```

💡 **Per stage, not per pipeline.** The stage with the rising oldest-age is the bottleneck ([[08.1 - Why Background Work Exists]]).

### "How long from upload to searchable?"

```python
document_time_to_searchable_seconds.observe(
    (indexed_at - uploaded_at).total_seconds()
)
```

⚠️ **This is the freshness SLI from [[12.2 - SLI SLO and Error Budgets]]**, and it is the metric users actually care about. **Everything else is a component of it.**

**Record it at the end of the pipeline, computed from the original upload timestamp** — which means carrying that timestamp through every stage.

### "Which stage is the bottleneck?"

```python
ingestion_stage_duration_seconds.labels(stage="extract").observe(...)
ingestion_stage_duration_seconds.labels(stage="chunk").observe(...)
ingestion_stage_duration_seconds.labels(stage="embed").observe(...)
ingestion_stage_duration_seconds.labels(stage="index").observe(...)
```

💡 **A stacked chart of stage durations summing to time-to-searchable makes the bottleneck obvious at a glance**, and it is the dashboard panel you will look at most.

### "Is a specific tenant having a bad time?"

```python
sql = f"/* org:{org_id} doc:{doc_id} */ SELECT ..."
log.info("stage completed", org_id=org_id, document_id=doc_id, stage=stage)
```

⚠️ **Not a metric label** — cardinality ([[12.1 - Observability Recap and Gaps]]). **Logs and traces carry the tenant; metrics carry the aggregate.**

### "Is the external dependency hurting us?"

```python
embedding_api_duration_seconds.observe(elapsed)
embedding_api_errors_total.labels(kind=...).inc()
embedding_api_rate_limited_total.inc()
embedding_tokens_total.inc(count)          # ← cost
circuit_state.labels(dep="embedding").set(state)
```

💡 **`embedding_tokens_total` is a cost metric, and cost is an operational concern in an AI system.** Track it per organisation in logs, aggregate in metrics.

## The Dashboards

### 1. Service health (the on-call view)

```
Request rate, error rate, p50/p99 latency   — by route
SLO compliance and error budget burn         — the four SLOs
Dependency health                            — circuit states, latencies
Saturation                                   — pools, loop lag, in-flight
```

⚠️ **This must fit on one screen and answer "is anything wrong" in five seconds.** Anything requiring scrolling belongs on a different dashboard.

### 2. Pipeline health

```
Time to searchable                p50 / p95 / p99
Stage durations                   stacked
Queue depth and oldest age        per stage
Throughput                        documents/minute per stage
Failure rate                      per stage, with DLQ counts
```

### 3. Per-request investigation

Not a dashboard — **a query path.**

```
Alert (p99 breach)
  → exemplar
    → trace
      → the slow span
        → logs with that trace_id
```

💡 **Exemplars are what make this one click instead of five searches** ([[12.1 - Observability Recap and Gaps]]).

### 4. Cost

```
Embedding tokens per day, per org
Database rows read per endpoint
Object storage volume
Infrastructure cost per document processed
```

## In Production

### The five questions the instrumentation must answer

```
1. Is the system healthy right now?              → dashboard 1, 5 seconds
2. Where is document X?                          → business-ID trace query
3. Why was this request slow?                    → exemplar → trace
4. Which tenant is causing this load?            → log aggregation by org_id
5. What did this cost?                           → dashboard 4
```

⚠️ **Test each of these by actually doing it, timed.** An instrumentation setup that cannot answer question 2 in under a minute is not finished.

### The alerts

| Alert | Condition | Severity |
|---|---|---|
| SLO fast burn | 14.4× over 1h and 5m | **Page** |
| SLO slow burn | 6× over 6h and 30m | **Page** |
| Pipeline stalled | `oldest_pending_seconds` > 900 on any stage | **Page** |
| DLQ growing | `dead_letter_total` rate > 0 for 10m | Ticket |
| **Replication slot inactive** | Any | **Page** ([[06.7 - MVCC Vacuum and Bloat]]) |
| **Transaction ID age** | > 1 billion | **Page** |
| Circuit open | Any circuit open > 5m | Ticket |
| Degraded responses | Sustained > 5% for 15m | Ticket |
| Certificate expiry | < 14 days | Ticket |
| Cost anomaly | Embedding tokens > 2× the 7-day average | Ticket |

💡 **Only five page.** Everything else is a ticket, **and keeping the page list short is what stops alert fatigue** ([[11.10 - Incidents and Postmortems]]).

⚠️ **The two Postgres alerts are causes rather than symptoms, and they belong on the page list anyway** — the consequence is severe, the lead time is long, and nobody will notice them otherwise.

### The scheduled job that stopped

⚠️ **The quietest failure in a backend system** ([[08.8 - Periodic Tasks and Distributed Cron]]): no error, no log line, no alert.

```python
job_last_success_timestamp.labels(job=...).set(time.time())
```

```yaml
- alert: JobNotRunning
  expr: time() - job_last_success_timestamp > 2 * expected_interval_seconds
```

💡 **Alert on the *absence* of success, not on failure.** A job that stopped being scheduled never fails — it simply never runs.

### Sampling for Conduit

```yaml
policies:
  - name: errors
    type: status_code
    status_code: {status_codes: [ERROR]}      # keep 100%
  - name: slow
    type: latency
    latency: {threshold_ms: 1000}              # keep 100%
  - name: baseline
    type: probabilistic
    probabilistic: {sampling_percentage: 1}
```

💡 **All errors, all slow requests, 1% of the rest.** For a system with a 0.5% error rate, this is roughly 1.5% of traces and covers essentially everything you would want to look at.

### The instrumentation checklist

```
□  One trace from browser to search index, across the queue
□  Business IDs (document.id, org.id) on every span
□  Exemplars on latency histograms
□  Trace ID in every log line
□  All three connection pools instrumented
□  Event loop lag
□  Per-stage pipeline metrics with oldest-age
□  Time-to-searchable as the freshness SLI
□  Cost metrics (tokens, rows, storage)
□  Version label on every metric
□  Job last-success timestamps
□  Tail-based sampling keeping all errors and slow requests
□  Five questions answerable, timed
```

### What this costs

⚠️ **Instrumentation is not free**, and for Conduit at moderate scale:

| | |
|---|---|
| Metrics | ~5,000 series. Small |
| Traces | ~1.5% sampled. Moderate |
| **Logs** | **Usually the largest line item** |
| CPU overhead | 2–5% for tracing |

💡 **Logs dominate cost in most systems.** Structured logging at `INFO` with a trace ID, and `DEBUG` disabled in production, is the discipline that keeps it bounded.

**Audit which metrics are actually queried and delete the rest** — most systems export hundreds of series nobody has ever looked at.

## Codebase

**Repo:** `open-telemetry/opentelemetry-python-contrib`, `onyx-dot-app/onyx`, `open-telemetry/opentelemetry-collector-contrib`

**Question to answer:** How does the auto-instrumentation for a message broker propagate context, and where does it put the headers? Then: how does a real ingestion product instrument its pipeline stages?

**Read, in order:**

1. `opentelemetry-python-contrib/instrumentation/opentelemetry-instrumentation-aiokafka/` — **producer and consumer instrumentation.** **Where headers are injected and extracted**, and how the span kind is set
2. `opentelemetry-python-contrib/instrumentation/opentelemetry-instrumentation-asyncpg/` — database spans, and **what it captures from the statement**
3. `opentelemetry-python/opentelemetry-api/src/opentelemetry/trace/__init__.py` — `Link`, and when to use it instead of a parent
4. `onyx/backend/onyx/background/` — **a real ingestion pipeline's stage tracking.** Compare their status model to the metrics in this note
5. `opentelemetry-collector-contrib/processor/tailsamplingprocessor/` — the policy configuration used above

💡 The aiokafka instrumentation is worth reading because **it shows exactly what "propagate through the broker" means mechanically** — inject into headers on produce, extract on consume. **Once you have seen it, doing it by hand for the outbox is obvious.**

**Size:** 1–2 sessions.

## Exercise

**Drill 12.3 — Make one document traceable end to end**

The capstone drill for section 12.

```
drills/12-conduit/
├── tracing/{setup.py, outbox_context.py, kafka_context.py, links.py}
├── metrics/{http.py, pipeline.py, deps.py, cost.py, jobs.py}
├── dashboards/{health.json, pipeline.json, cost.json}
├── alerts/{rules.yaml, tuning.md}
├── questions/{q1.md, q2.md, q3.md, q4.md, q5.md, TIMINGS.md}
├── sampling/{collector.yaml, RESULTS.md}
└── README.md
```

**Part 1 — One trace, seven hops.** Instrument the full path: gateway → document service → object storage → Postgres → outbox → Kafka → ingestion worker → embedding API → Postgres → search indexer.

**Confirm it appears as one connected trace** (or a properly linked set).

**Then break the outbox context propagation and confirm it splits.** Screenshot both.

**Part 2 — Links versus parent-child.** Implement the asynchronous portion both ways.

**For a document taking 12 minutes to index, compare:** trace duration, whether the backend renders it correctly, and how easy it is to navigate.

**Report which you would use and why.**

**Part 3 — Business ID queries.** Add `document.id` and `org.id` to every span.

**Then answer "show me everything that happened to document X" as a single query**, and confirm it returns spans from every service and every stage.

**Time it.** This is question 2, and it should take under 30 seconds.

**Part 4 — The pipeline metrics.** Per-stage duration, depth, oldest-age, throughput and failure rate. Plus `document_time_to_searchable_seconds`.

**Then build the stacked stage-duration chart** and confirm the stages sum to time-to-searchable.

**Then deliberately slow one stage and confirm the chart identifies it immediately.**

**Part 5 — The five questions, timed.** Have someone else answer each using only your dashboards and queries:

| Question | Target |
|---|---|
| Is the system healthy? | 5 seconds |
| Where is document X? | 30 seconds |
| Why was this request slow? | 60 seconds |
| Which tenant is causing this load? | 2 minutes |
| What did today cost? | 30 seconds |

**Record actual times in `TIMINGS.md`. Fix whatever is slow.**

**Part 6 — The silent job failure.** Stop a scheduled sync job from running — do not make it fail, make it not run.

**Measure how long until anything notices.** Then add `job_last_success_timestamp` with an absence alert and measure again.

**Part 7 — Sampling.** Configure tail-based sampling with the three policies.

Run load with a 2% error rate. **Measure: fraction of errors captured, fraction of slow requests captured, storage volume, and collector memory.**

**Then switch to 1% head-based and measure the same.** The error capture difference should be stark.

**Part 8 — Cost audit.** Measure total observability data volume: metric series, trace bytes, log bytes per day.

**Then apply the levers** — drop unqueried metrics, disable `DEBUG`, tighten sampling — and **report the reduction and what you gave up.**

**Done when:**
- One document traces cleanly across seven hops including the outbox and Kafka
- Breaking context propagation visibly splits the trace
- "Everything that happened to document X" is one query, under 30 seconds
- Your stacked stage chart sums to time-to-searchable and identifies a slowed stage
- All five questions are answered by someone else within target times
- An absence alert catches a job that silently stopped running
- Tail sampling captures 100% of errors where head-based missed most
- You have measured observability cost and reduced it deliberately
