# find, some, every and includes

Search and predicate methods. All of them **short-circuit** — they stop as soon as the answer is determined, unlike `map` and `filter` which always traverse everything.

## The set

```js
users.find(u => u.id === 3);        // first match, or undefined
users.findIndex(u => u.id === 3);   // index, or -1
users.findLast(u => u.active);      // last match, or undefined
users.findLastIndex(u => u.active); // index from the end, or -1

users.some(u => u.isAdmin);         // true if any match
users.every(u => u.isActive);       // true if all match

nums.includes(3);                   // true if the value is present
nums.indexOf(3);                    // index, or -1
nums.lastIndexOf(3);                // last index, or -1
```

## find vs filter

```js
const user = users.find(u => u.id === id);      // stops at the first match
const user = users.filter(u => u.id === id)[0]; // scans everything, allocates
```

`find` is both faster and clearer when you want one result. The `filter()[0]` pattern also silently returns `undefined` on an empty result, which looks the same but hides the fact that a full pass just happened.

`find` returns `undefined` when nothing matches, so guard before using the result:

```js
const user = users.find(u => u.id === id);
if (!user) return notFound();
```

## findIndex vs indexOf

`indexOf` compares with `===`; `findIndex` takes a predicate.

```js
[NaN].indexOf(NaN);        // -1  — NaN !== NaN
[NaN].findIndex(Number.isNaN); // 0

objects.indexOf(someObject);   // works only for the same reference
objects.findIndex(o => o.id === someObject.id);  // structural match
```

`indexOf` on objects compares references, so it finds an item only if you have the exact same object. For anything with an id, use `findIndex`.

## includes vs indexOf

```js
arr.includes(x);          // reads better
arr.indexOf(x) !== -1;    // the old idiom

[NaN].includes(NaN);      // true
[NaN].indexOf(NaN);       // -1
```

`includes` uses **SameValueZero**, which treats `NaN` as equal to itself; `indexOf` uses `===`, which does not ([[05.3 - Types Coercion and Equality]]). This is the only behavioral difference, and it is why `includes` is the default choice.

`includes` on a large array is still O(n). If you are checking membership repeatedly, use a `Set` ([[06.5 - Map and Set]]):

```js
// O(n) per check
if (allowedIds.includes(id)) {}

// O(1) per check
const allowed = new Set(allowedIds);
if (allowed.has(id)) {}
```

Building the `Set` costs one pass, so it pays off from roughly the second lookup onward. A `.includes()` inside a `.filter()` over two large arrays is O(n·m) and is a very common hidden performance problem.

## some and every

```js
const hasErrors = fields.some(f => f.error);
const allValid = fields.every(f => f.isValid);
```

Both short-circuit: `some` stops at the first `true`, `every` at the first `false`.

The empty-array behavior is worth memorizing because it surprises people:

```js
[].some(x => true);   // false
[].every(x => false); // true  — vacuous truth
```

`every` on an empty array is always `true`. In a form validator, an empty field list therefore reports "all valid", which may or may not be what you want.

`some` also doubles as a breakable loop:

```js
items.some(item => {
  if (item.id === target) { found = item; return true; }
  return false;
});
```

Legitimate, but `for...of` with `break` says the same thing more directly.

## at

```js
arr.at(-1);    // last element
arr[arr.length - 1];
```

`at` accepts negative indices, which removes the `length - 1` boilerplate. Note `arr[-1]` is `undefined` — negative bracket access reads a property named `"-1"`, not an offset from the end.

## Complexity summary

| Operation | Cost |
| --- | --- |
| `find` / `findIndex` / `some` / `every` | O(n), short-circuits |
| `includes` / `indexOf` | O(n) |
| `Set.has` / `Map.get` | O(1) average |
| `filter().length > 0` | O(n), no short-circuit |

The last row is a frequent inefficiency: `if (arr.filter(pred).length > 0)` should be `if (arr.some(pred))`.

## How senior engineers actually use this

**They convert to a `Set` or `Map` before repeated lookups.** Any `includes` or `find` inside a loop over another collection is a signal to build an index first. This single change turns O(n·m) into O(n+m) and is one of the highest-leverage frontend optimizations available.

**They use `some` and `every` for validation aggregation** rather than counting matches, because short-circuiting matters when predicates are expensive.

**They guard `find` results.** A `find` that returns `undefined` and is then dereferenced is the second most common `TypeError` in frontend code, after DOM nulls.

**They avoid `findIndex` + `splice` for immutable updates.** In React state, `map` with a conditional is cleaner and non-mutating:

```js
setItems(items => items.map(i => i.id === id ? { ...i, done: true } : i));
```

## Common pitfalls

- `filter()[0]` where `find` was meant.
- `indexOf` failing on `NaN` or on structurally-equal objects.
- `[].every()` returning `true` and passing a validation check.
- `arr[-1]` returning `undefined` instead of the last element.
- `includes` inside a nested loop over large arrays.
- Using `find` and immediately accessing a property without a null check.

## Interview angle

These come up inside larger problems more than as questions in their own right. The two things worth volunteering: `includes` uses SameValueZero so it handles `NaN` where `indexOf` does not, and any repeated membership check should use a `Set`. In a coding round, reaching for a `Set` to avoid a nested loop is often exactly the optimization the interviewer is waiting for.
