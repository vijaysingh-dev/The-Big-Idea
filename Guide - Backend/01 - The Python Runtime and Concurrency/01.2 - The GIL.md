# The GIL

#backend #python #concurrency

> **In one line:** One lock lets only one thread run Python bytecode at a time. It does not stop threads from waiting on I/O in parallel, which is why threads still work fine for the kind of work backend services actually do.

---

## The Idea

The **GIL** — Global Interpreter Lock — is a single mutex (a lock that only one holder can have at a time) inside the Python interpreter. To execute bytecode, a thread must hold it.

So on an 8-core machine, 8 Python threads doing arithmetic use **one** core. Seven of them are waiting for the lock.

But here is the part people miss: **a thread releases the GIL whenever it is going to wait.** Reading a socket, querying a database, reading a file, sleeping — the GIL is released for the whole duration. Other threads run during that time.

Which means:

| Your work is mostly... | Threads help? |
|---|---|
| Waiting on network or disk | **Yes, a lot** |
| Doing CPU work in Python | **No** |
| Doing CPU work inside numpy / a C library | **Yes** — those release the GIL too |

Backend services are overwhelmingly the first row. That is why the GIL is famous but rarely the thing actually hurting you.

---

## How It Really Works

### Why it exists

Every Python object has a reference count ([[01.1 - How Python Actually Runs Your Code]]). Every assignment, every function argument, every list append changes counts.

```
Thread A: refcount++     ─┐
Thread B: refcount++     ─┴─► both read 5, both write 6. Should be 7.
```

A count that goes too low frees an object still in use — a use-after-free crash. So refcounts need protecting.

Two options:

1. **One lock for everything.** Simple, fast for one thread, kills multi-core Python.
2. **A lock per object, or atomic counters.** Correct and parallel, but adds cost to every single operation, slowing down the common single-threaded case.

CPython chose option 1 in 1992, when multi-core machines did not exist. Every attempt to remove it since then made single-threaded Python slower, which is why it survived — until the free-threaded work finally found an acceptable trade.

### What it does and does not protect

The GIL protects **the interpreter's own internals**. It does not protect **your logic**.

```python
counter = 0

def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1

# Two threads doing this do NOT produce 2,000,000
```

Because `counter += 1` is several bytecode instructions:

```
LOAD_FAST    counter
LOAD_CONST   1
BINARY_OP    +
STORE_FAST   counter
```

The GIL can be handed to another thread between any two of them. You still need your own locks for your own shared state.

⚠️ **This is the single most common GIL misunderstanding.** "The GIL makes Python thread-safe" is wrong. It makes the *interpreter* thread-safe, not your code.

### When the GIL is handed over

Two triggers:

**1. A thread does something blocking.** The C code wraps the blocking call:

```c
Py_BEGIN_ALLOW_THREADS       /* GIL released */
result = recv(fd, buf, len); /* other threads run freely here */
Py_END_ALLOW_THREADS         /* GIL re-acquired */
```

Every I/O function in the standard library does this. So does numpy for large array operations, and most well-written C extensions.

**2. The switch interval expires.** A CPU-bound thread is asked to drop the lock every 5ms by default.

```python
import sys
sys.getswitchinterval()      # 0.005
sys.setswitchinterval(0.001) # more responsive, more overhead
```

Note the word "asked." The running thread checks a flag between bytecode instructions. A single C call that takes 10 seconds — a huge regex, a giant `json.loads`, a big `sorted()` — holds the GIL for all 10 seconds and nothing else runs.

💡 This is why one enormous regex or one 50MB JSON parse can freeze an entire async service. It is not an async problem — it is a GIL problem, and no amount of `await` fixes it. See [[01.6 - The Blocking Call Problem]].

### The convoy effect

Historically, an I/O thread that woke up would immediately lose the GIL to a CPU-bound thread and go back to sleep, over and over. The GIL was rewritten in Python 3.2 to be much fairer, but the effect still shows up in mixed workloads: a CPU-heavy background thread measurably degrades the latency of I/O threads in the same process.

⚠️ **Practical rule: never run CPU-heavy work in a thread inside your web server process.** It does not just use a core — it degrades every request the process is serving.

## Proving It To Yourself

Run this. It takes a minute and it settles the question permanently.

```python
import time, threading, multiprocessing

def cpu_work(n=8_000_000):
    x = 0
    for _ in range(n):
        x += 1

def io_work():
    time.sleep(1)

def timed(label, fn, count, worker_cls):
    workers = [worker_cls(target=fn) for _ in range(count)]
    t = time.perf_counter()
    for w in workers: w.start()
    for w in workers: w.join()
    print(f"{label:32} {time.perf_counter() - t:.2f}s")

timed("CPU, 1 thread",  cpu_work, 1, threading.Thread)
timed("CPU, 4 threads", cpu_work, 4, threading.Thread)
timed("CPU, 4 processes", cpu_work, 4, multiprocessing.Process)
timed("IO,  1 thread",  io_work,  1, threading.Thread)
timed("IO,  4 threads", io_work,  4, threading.Thread)
```

Typical result on an 8-core machine:

```
CPU, 1 thread                    0.42s
CPU, 4 threads                   1.71s    ← 4x slower. No parallelism, plus lock overhead
CPU, 4 processes                 0.45s    ← real parallelism
IO,  1 thread                    1.00s
IO,  4 threads                   1.00s    ← perfect parallelism, all waiting together
```

Those last two lines are the whole reason threads are still useful in Python.

## Free-Threaded Python

Python 3.13 shipped an optional build with no GIL (PEP 703). In 3.14 it moved from experimental to officially supported, though still not the default.

```bash
uv python install 3.14t     # the 't' suffix means free-threaded
python3.14t -c "import sys; print(sys._is_gil_enabled())"   # False
```

How it works, briefly:

- **Biased reference counting** — the thread that created an object uses cheap non-atomic counts; other threads use atomic ones. Most objects are only touched by one thread, so most counting stays fast
- **Immortal objects** — `None`, `True`, small ints and interned strings are never counted at all
- **Per-object locks** — dicts and lists get fine-grained locking
- **Deferred reference counting** for objects the interpreter itself holds

The trade:

| | Benefit | Cost |
|---|---|---|
| CPU-bound multithreaded work | Real parallel speedup | — |
| Single-threaded code | — | A single-digit percentage slower |
| C extensions | — | Must be rebuilt and audited for thread safety |
| Your own code | — | Races that the GIL used to hide now surface |

⚠️ **Do not switch production to free-threaded yet unless you have a specific CPU-bound problem and have tested every dependency.** The ecosystem is still catching up, and the failure mode — a rare data race under load — is one of the worst kinds to debug.

There is also **per-interpreter GIL** (PEP 684, Python 3.12+): multiple interpreters in one process, each with its own GIL, isolated from each other. Useful for embedding scenarios, not yet for typical web services.

## In Production

### What this means for how you deploy

The standard Python web deployment is **multiple processes, async inside each**:

```
Machine (8 cores)
├── uvicorn worker 1  (process, own GIL, own event loop)
├── uvicorn worker 2
├── ...
└── uvicorn worker 8
```

```bash
uvicorn app:app --workers 8
# or gunicorn -k uvicorn.workers.UvicornWorker -w 8 app:app
```

Processes give you cores. The event loop inside each gives you concurrency. Threads are used only for the specific job of running blocking code without stalling the loop ([[01.8 - Offloading Work]]).

⚠️ **Worker count is not simply `cpu_count()`.** In a container, `os.cpu_count()` reports the *host's* cores, not your cgroup limit. A pod limited to 2 CPUs on a 64-core node will happily start 64 workers, exhaust memory, and get OOMKilled. Read the cgroup quota, or just set the number explicitly from config.

### Where the GIL actually bites in real services

| Situation | What happens | Fix |
|---|---|---|
| Parsing a 50MB JSON body | Whole process frozen for seconds | Stream it, size-limit it, or offload to a process |
| A catastrophic regex on user input | Whole process frozen, possibly forever | Timeouts, `re2`, validate input length |
| Image resize in the request handler | Every concurrent request stalls | Celery task |
| `pandas` on a big frame in an endpoint | Same | Move it out of the request path |
| Password hashing (bcrypt/argon2) | Deliberately slow, blocks the loop | Run in a thread pool — bcrypt releases the GIL |
| Compression of a large response | Blocks | Let the proxy do it |

💡 **The pattern:** any single operation that takes more than ~50ms of pure CPU should not be in your request path. Not because of the GIL specifically, but because the GIL turns "one slow request" into "all requests are slow."

### Interview framing

If asked "how do you handle CPU-bound work in Python", a weak answer is "use multiprocessing." A strong answer is:

> First I'd check it's actually CPU-bound with py-spy rather than assuming. If it is, the options in order of preference are: get it out of the request path entirely into a task queue; use a library that releases the GIL, like numpy or a Rust extension; use a process pool if it must be synchronous; and only consider free-threaded Python or another language if none of those work. The reason multiprocessing isn't first is that it costs you memory and serialization on every call, and most "CPU-bound" work in web services turns out to be a bad query or a serialization problem.

## Codebase

**Repo:** `python/cpython`

**Question to answer:** Find the exact place where a thread gives up the GIL because the switch interval expired, and the exact place where a socket read releases it. They are different mechanisms — what is the difference?

**Read, in order:**

1. `Python/ceval_gil.c` — `take_gil` and `drop_gil`. Read the comments at the top of the file, they explain the 3.2 redesign
2. `Python/ceval.c` — find the "eval breaker" check in the dispatch loop. This is the flag a running thread checks
3. `Modules/socketmodule.c` — search for `Py_BEGIN_ALLOW_THREADS` and see it wrapping the actual `recv`
4. `Include/internal/pycore_gil.h` — the GIL structure itself. It is small

**Bonus:** `Python/pystate.c` for how thread states are tracked. This is what py-spy reads.

**Size:** 1–2 sessions.
