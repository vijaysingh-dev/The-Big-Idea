# Relationship Queries

## Two directions, two syntaxes

**Child to parent** — traverse upward using dot notation. Up to **5 levels**.

**Parent to child** — a subquery in the `SELECT` list. Only **1 level** deep.

The asymmetry is deliberate: traversing upward reads one record per hop; traversing downward can return an unbounded set.

## Child to parent

```sql
SELECT Id, Claim_Number__c,
       Asset__r.Name,
       Asset__r.Account.Name,
       Asset__r.Account.Owner.Email,
       Service_Contract__r.Account__r.Ultimate_Parent_Account__r.Name
FROM Warranty_Claim__c
WHERE Status__c = 'Submitted'
```

Custom relationships use `__r` in place of the field's `__c`. Standard relationships use the relationship name — `Account`, `Owner`, `CreatedBy`.

The relationship name for a custom lookup is derived from the field API name: `Asset__c` becomes `Asset__r`. Renaming the field changes it, which breaks every query referencing it.

In Apex the traversal is read as nested objects:

```java
for (Warranty_Claim__c claim : claims) {
    String accountName = claim.Asset__r.Account.Name;
    String ownerEmail = claim.Asset__r.Account.Owner.Email;
}
```

**Null safety matters.** If `Asset__c` is null, `claim.Asset__r` is null, and reading `.Account` throws a null pointer exception. The query itself does not throw — it returns the row with a null relationship — so the failure happens in your loop.

```java
for (Warranty_Claim__c claim : claims) {
    if (claim.Asset__r != null && claim.Asset__r.Account != null) {
        String accountName = claim.Asset__r.Account.Name;
    }
}
```

Or with the safe navigation operator, which returns null rather than throwing:

```java
String accountName = claim.Asset__r?.Account?.Name;
```

`?.` is the cleaner form and is worth using consistently for relationship traversal.

## Parent to child

```sql
SELECT Id, Name, SerialNumber,
       (SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c
        FROM Warranty_Claims__r
        WHERE Status__c != 'Closed'
        ORDER BY Claim_Date__c DESC
        LIMIT 10)
FROM Asset
WHERE AccountId = :accountId
```

The subquery uses the **child relationship name**, which is set when the relationship field is created and defaults to the pluralized object name. Leaving it as an unhelpful default makes every subquery in the org harder to read.

Standard relationships have fixed child relationship names: `Contacts`, `Opportunities`, `Cases`, `Tasks`, `Assets`.

In Apex the subquery result is a list on the parent:

```java
for (Asset asset : assets) {
    // the child list is null when the subquery returned nothing, not an empty list
    if (asset.Warranty_Claims__r != null) {
        for (Warranty_Claim__c claim : asset.Warranty_Claims__r) {
            total += claim.Claim_Amount__c;
        }
    }
}
```

A subquery returning no rows gives a **null** child list on that parent, not an empty list. Iterating without the guard throws. This is a frequent and easily missed defect.

## The row limits

**The 50,000-row limit counts parents and children together.** A query returning 1,000 accounts each with 60 contacts is 61,000 rows and fails.

**Subqueries are limited to 200 rows per parent by default** in some contexts, and to 20 subqueries per query.

For an object where a parent may have very many children, a subquery is the wrong shape. Query the children directly with a filter on the parent IDs instead:

```java
// Instead of a subquery that could return tens of thousands of rows per parent
Map<Id, List<Warranty_Claim__c>> claimsByAsset = new Map<Id, List<Warranty_Claim__c>>();

for (Warranty_Claim__c claim : [
    SELECT Id, Asset__c, Claim_Amount__c, Status__c
    FROM Warranty_Claim__c
    WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
    ORDER BY Claim_Date__c DESC
]) {
    if (!claimsByAsset.containsKey(claim.Asset__c)) {
        claimsByAsset.put(claim.Asset__c, new List<Warranty_Claim__c>());
    }
    claimsByAsset.get(claim.Asset__c).add(claim);
}
```

Two queries instead of one, bounded row count, and a structure that is easier to work with.

## Filtering on a parent's fields

A child query can filter on parent fields, which is often overlooked:

```sql
SELECT Id, Claim_Number__c
FROM Warranty_Claim__c
WHERE Asset__r.Account.BillingCountry = 'India'
  AND Asset__r.Product2.Family = 'Press'
  AND Service_Contract__r.Status__c = 'Active'
```

This is genuinely useful and has a performance cost: each traversal in a `WHERE` clause is work the engine performs per candidate row, and parent fields are generally **not selective** unless the parent field is indexed and the filter narrows well. See [[08.9 - Indexes and Selective Queries]].

## Polymorphic relationships and TYPEOF

`WhoId`, `WhatId`, `OwnerId` on Case, and `ParentId` on some objects can point at several object types. Dot notation cannot be used for fields that exist on only one of them.

`TYPEOF` handles this:

```sql
SELECT Id, Subject, ActivityDate,
       TYPEOF What
           WHEN Opportunity THEN Amount, StageName, CloseDate
           WHEN Account THEN Industry, AnnualRevenue
           WHEN Case THEN CaseNumber, Status
           ELSE Name
       END
FROM Task
WHERE WhatId != null
```

```sql
SELECT Id, CaseNumber, Status,
       TYPEOF Owner
           WHEN User THEN Email, ManagerId, IsActive
           WHEN Group THEN DeveloperName, Type
       END
FROM Case
WHERE Status = 'New'
```

In Apex the result is read by casting:

```java
for (Task t : tasks) {
    if (t.What instanceof Opportunity) {
        Opportunity opp = (Opportunity) t.What;
        Decimal amount = opp.Amount;
    }
}
```

Without `TYPEOF`, only fields common to every possible type — `Id`, `Name` — can be selected through the polymorphic relationship.

Determining a record's type from an ID without querying uses the key prefix or the describe:

```java
// Both work; getSObjectType() is more readable
Schema.SObjectType type = recordId.getSObjectType();
if (type == Opportunity.SObjectType) { ... }

Boolean isQueue = String.valueOf(caseOwnerId).startsWith('00G');
```

## Self relationships

An object with a lookup to itself traverses like any other relationship, to the same 5-level depth:

```sql
SELECT Id, Name,
       Parent.Name,
       Parent.Parent.Name,
       Parent.Parent.Parent.Name
FROM Account
WHERE Id = :accountId
```

Beyond a fixed depth this does not work, because SOQL has no recursive query. Walking an unbounded hierarchy means querying level by level in a loop, at one query per level, or maintaining a materialized path field. See [[02.9 - Hierarchical and Self Relationships]].

## Relationship queries in practice

The pattern that appears constantly — fetch parents and children together for a set of records:

```java
public with sharing class ClaimContextService {

    public static Map<Id, ClaimContext> loadContext(Set<Id> claimIds) {
        Map<Id, ClaimContext> contexts = new Map<Id, ClaimContext>();

        for (Warranty_Claim__c claim : [
            SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c,
                   Asset__r.Name, Asset__r.SerialNumber,
                   Asset__r.Account.Name, Asset__r.Account.Owner.Email,
                   (SELECT Id, Product__r.Name, Quantity__c, Cost__c FROM Claim_Parts__r)
            FROM Warranty_Claim__c
            WHERE Id IN :claimIds
            WITH USER_MODE
        ]) {
            contexts.put(claim.Id, new ClaimContext(claim));
        }

        return contexts;
    }
}
```

One query, parent data and child data together, bounded by the input set. This is what "query once for everything you need" looks like in practice.

## Practical guidance

**Use `?.` for relationship traversal.** It removes an entire class of null pointer exception.

**Guard child lists for null**, not just empty. A subquery with no matches gives null.

**Name child relationships meaningfully** when creating lookup fields. The default is often wrong and it appears in every query.

**Do not subquery children that could be numerous.** Query them separately and build a map.

**Remember parents and children share the 50,000-row limit.**

**Use `TYPEOF` for polymorphic fields**, and `getSObjectType()` when you only need the type.
