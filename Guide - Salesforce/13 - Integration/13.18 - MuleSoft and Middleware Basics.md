# MuleSoft and Middleware Basics

## The question

Should systems talk to each other directly, or through a broker?

**Point-to-point** means Salesforce calls the ERP, and the ERP calls Salesforce. Fewer moving parts, less to operate, and every integration is its own implementation.

**Middleware** means both talk to a layer in between, which handles routing, transformation, retry, and monitoring centrally.

Neither is right in general. The decision depends on how many systems there are and how complex the flows between them become.

## When point-to-point is correct

- Two or three systems
- Simple transformations
- Stable interfaces
- A team comfortable operating each integration
- No shared retry or monitoring requirement

A Salesforce org syncing with one ERP does not need MuleSoft. Adding it means an extra platform to license, operate, and staff, for a problem that does not exist yet.

**Do not adopt middleware because it appears in a reference architecture.** The cost is real and the benefit is proportional to the number of connections.

## When middleware earns its place

**Connection count.** Four systems each integrating with each other is twelve point-to-point connections. Through a broker it is four. The arithmetic is what drives most adoptions.

**Transformation complexity.** Mapping between three different customer representations is work that belongs in one place, not duplicated in each system.

**Orchestration.** A business process spanning four systems, with compensation when step three fails, is not something to build in Apex.

**Buffering.** Middleware absorbs bursts, queueing requests rather than consuming the daily API allocation in a spike. This is a genuinely Salesforce-specific benefit — see [[01.4 - Salesforce Editions and Licensing]].

**Protocol translation.** A partner speaking SOAP, a warehouse speaking flat files over SFTP, and a payment provider speaking REST, all needing to reach Salesforce.

**Centralized retry and monitoring.** One place to see what failed and replay it, rather than a log table in each system.

**Different availability profiles.** A batch system available four hours a night, integrating with a system expecting real-time calls.

## MuleSoft, in outline

Salesforce owns MuleSoft, so it is the middleware most often proposed in Salesforce architectures. The concepts, at the level a Salesforce developer needs:

**Mule application** — a deployable unit containing flows.

**Flow** — a sequence of processing steps. Confusingly named, and unrelated to Salesforce Flow.

**Connector** — a pre-built integration to a system. The Salesforce connector wraps the REST, Bulk, Streaming, and Composite APIs.

**DataWeave** — the transformation language, and where most of the actual work happens.

**API Gateway** — policy enforcement: rate limiting, authentication, logging, applied without changing the application.

**Anypoint Exchange** — the catalogue of reusable APIs and connectors.

A DataWeave transformation, to show the shape:

```
%dw 2.0
output application/json
---
{
  claimNumber: payload.Claim_Number__c,
  amount: payload.Claim_Amount__c,
  serialNumber: payload.Asset__r.SerialNumber,
  submittedAt: payload.CreatedDate as DateTime {format: "yyyy-MM-dd'T'HH:mm:ss'Z'"},
  parts: payload.Claim_Parts__r map (part) -> {
    partCode: part.Product__r.ProductCode,
    quantity: part.Quantity__c
  }
}
```

That mapping lives in the middleware rather than in Apex, which is the point — the transformation is owned by the integration layer, and Salesforce sends its native shape.

## API-led connectivity

MuleSoft's architectural model, worth knowing because it appears in every proposal:

**System APIs** — one per backing system, exposing it in a normalized form. A Salesforce System API, an SAP System API, a warehouse System API.

**Process APIs** — business logic composed from system APIs. "Submit a warranty claim" calls the Salesforce and SAP system APIs and orchestrates between them.

**Experience APIs** — tailored to a consumer. A mobile app API, a partner portal API, each shaped for its client.

The intent is that the system layer changes when a backing system changes, the process layer when business rules change, and the experience layer when a consumer's needs change — so a change in one does not ripple through the others.

Whether an organization achieves that depends on discipline rather than tooling. A three-layer architecture built without it is three times the code with the same coupling.

## Where Salesforce sits

With middleware in place, Salesforce's integration code simplifies considerably.

**Outbound:** a Named Credential pointing at the middleware, not at each backing system.

```java
// Salesforce calls one endpoint; the middleware routes and transforms
req.setEndpoint('callout:Integration_Layer/api/claims/submit');
```

**Inbound:** the middleware calls Salesforce's standard REST API or Bulk API. Custom Apex REST endpoints become less necessary, because the transformation and orchestration happen upstream.

**Events:** the middleware subscribes to platform events or CDC through the Pub/Sub API and fans out to consumers. This is often the cleanest arrangement — Salesforce publishes one event, and the middleware decides who needs it. See [[13.9 - Pub-Sub API and Event Relay]].

The practical effect on Salesforce code: **fewer named credentials, fewer client classes, and no transformation logic in Apex.** The Apex sends its own data model and lets the middleware map it.

## The alternatives

MuleSoft is not the only option, and it is frequently not the cheapest.

**Boomi, Workato, Jitterbit, Informatica** — comparable integration platforms, some substantially cheaper for straightforward use cases.

**Kafka** — an event streaming platform rather than an integration platform. Right when the architecture is genuinely event-driven and volume is high. Salesforce integrates through the Pub/Sub API or a Kafka connector.

**AWS EventBridge, Step Functions, Lambda** — for an organization already on AWS, Event Relay gets Salesforce events into EventBridge with no code, and the rest is native AWS. Often the lowest-effort option for an AWS-centric estate.

**Azure Logic Apps, Service Bus** — the equivalent for Azure.

**A custom service.** A small application handling two or three integrations, deployed on Heroku or a container platform. Genuinely reasonable for a modest set of integrations, and far cheaper than a licensed platform.

The honest framing: **middleware is a category, not a product.** The question is whether a broker is needed, and only then which one.

## What does not change

Middleware does not remove the Salesforce-side constraints.

**API limits still apply.** The middleware calling Salesforce consumes the same daily allocation. It can buffer and batch — which helps — and it does not create headroom that was not there.

**Governor limits still apply** to any Apex the middleware triggers.

**Bulk is still the right tool for volume.** Middleware calling the REST API record by record is as expensive as anything else doing so. A well-configured Salesforce connector uses Bulk API for large operations, and a badly configured one does not.

**Idempotency is still your responsibility.** The middleware retries; without external IDs and upsert, those retries duplicate. See [[13.17 - Error Handling, Retries and Idempotency]].

That last point causes real incidents. Teams assume the middleware's retry handling makes duplicates impossible, and it does the opposite — automatic retry plus non-idempotent writes is exactly how duplicates are created at scale.

## Working with a middleware team

The Salesforce developer's side of the interface, and where the friction usually is.

**Agree the contract, not the implementation.** Define the payload shape and the error codes; how the middleware achieves it is theirs.

**Own the source-of-truth decision.** Which system owns which field is a business decision, and the middleware team cannot make it. Writing it down is the artifact that prevents update loops. See [[13.1 - Integration Fundamentals and Patterns]].

**Insist on external IDs.** The middleware should upsert on your key, not insert.

**Ask for correlation Ids.** A shared identifier in both logs is what makes cross-system debugging possible.

**Provide a scoped integration user.** Not System Administrator, and not one shared user for five integrations — one per system, with a permission set granting exactly the objects and fields needed. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**Agree the volume profile.** The middleware team needs to know the daily API allocation, and you need to know their expected call pattern. This conversation happening late is a common cause of an integration that works in testing and exhausts the allocation in production.

## Deciding

| Situation | Approach |
| --- | --- |
| Two systems, simple mapping | Point-to-point |
| Three or four systems, growing | Consider middleware |
| Many systems, complex orchestration | Middleware |
| Already on AWS, event-driven | Event Relay plus native AWS |
| High-volume event streaming | Kafka or Pub/Sub |
| Bursty load threatening API limits | Middleware, for buffering |
| Protocol translation needed | Middleware |
| One team, modest budget, three integrations | Point-to-point, or a small custom service |

The signal that point-to-point has run out: **the same transformation logic exists in three places**, or nobody can say what would break if a system's interface changed.

## Practical guidance

**Do not adopt middleware before the connection count justifies it.**

**Evaluate the category, not just MuleSoft.** Cheaper options exist for straightforward cases.

**Point Salesforce at one endpoint** when middleware is in place, and let it route.

**Keep transformation out of Apex.**

**Insist on external IDs and upsert**, because the middleware's retries will otherwise duplicate.

**Agree the source of truth per field**, in writing, before anything is built.

**Provide a scoped integration user per system.**

**Have the volume conversation early**, against the daily API allocation.
