# Custom Settings

## The one thing they do that metadata cannot

**Hierarchy.** A value can differ per user, per profile, or org-wide, with the most specific match winning.

```
Org default:              Disable_Triggers__c = false
Profile "Data Migration": Disable_Triggers__c = true
User integration@...:     Disable_Triggers__c = true
```

```java
// Resolves the hierarchy automatically for the running user
Automation_Settings__c settings = Automation_Settings__c.getInstance();
if (settings.Disable_Triggers__c) {
    return;
}
```

That resolution — user, then profile, then org default — is the entire reason Custom Settings still exist. Custom Metadata has no equivalent. See [[17.1 - Custom Metadata Types]].

## The two types

**Hierarchy** — org, profile, and user levels, resolved automatically.

**List** — a flat set of named records, like a simple lookup table.

```java
// Hierarchy
Automation_Settings__c forMe = Automation_Settings__c.getInstance();
Automation_Settings__c orgDefault = Automation_Settings__c.getOrgDefaults();
Automation_Settings__c forUser = Automation_Settings__c.getInstance(userId);
Automation_Settings__c forProfile = Automation_Settings__c.getInstance(profileId);

// List
Country_Config__c india = Country_Config__c.getInstance('IN');
Map<String, Country_Config__c> all = Country_Config__c.getAll();
```

**List custom settings are largely obsolete.** Everything they do, Custom Metadata does better — deployable data, metadata relationships, and the same cache behaviour. A new list custom setting is almost always the wrong choice.

## The critical difference from metadata

**Custom Setting data does not deploy.**

The definition is metadata and moves between environments. The **records are data** and do not. A deployment creates the setting object in production with no rows in it, and every read returns null until someone populates them.

```java
Automation_Settings__c settings = Automation_Settings__c.getInstance();
// null in a freshly deployed org — this line throws
if (settings.Disable_Triggers__c) { }
```

**Always null-check**, or use `getOrgDefaults()` with a constructed fallback:

```java
public static Boolean triggersDisabled() {
    Automation_Settings__c settings = Automation_Settings__c.getInstance();
    // the null coalescing handles both a missing record and a null field
    return settings?.Disable_Triggers__c == true;
}
```

This is the single most common Custom Setting defect, and it appears as a null pointer exception in production immediately after a release.

## No query cost

Like custom metadata, **Custom Settings do not consume SOQL queries** when read through the provided methods:

```java
Automation_Settings__c.getInstance();       // no query
Country_Config__c.getAll();                 // no query

[SELECT Id FROM Automation_Settings__c];    // this DOES consume a query
```

The SOQL form counts. The convenience methods do not — they read from the application cache.

## The bypass pattern

The main legitimate use in a modern org, and the reason this note exists.

```java
public with sharing class AutomationBypass {

    private static Set<String> sessionBypasses = new Set<String>();

    public static Boolean isBypassed(String handlerName) {
        if (sessionBypasses.contains(handlerName)) {
            return true;
        }

        Automation_Settings__c settings = Automation_Settings__c.getInstance();
        if (settings == null) {
            return false;
        }

        // the hierarchy means an admin can disable automation for one user, live
        if (settings.Disable_All_Automation__c == true) {
            return true;
        }
        return isNamed(settings.Disabled_Handlers__c, handlerName);
    }

    public static void bypass(String handlerName) {
        sessionBypasses.add(handlerName);
    }

    public static void clearBypass(String handlerName) {
        sessionBypasses.remove(handlerName);
    }

    @TestVisible
    private static void reset() {
        sessionBypasses.clear();
    }
}
```

Two paths, for two situations:

**The static path** for code — a migration script disabling a handler for its own run.

**The hierarchy setting path** for runtime — an administrator disabling automation during an incident, for one user or one profile, **without a deployment**.

That second capability is what makes a Custom Setting the right tool here. Deactivating a trigger requires a deployment; flipping a hierarchy setting does not. During an incident, that difference is everything. See [[11.5 - Trigger Handler Pattern]].

## Feature toggles per user

The other genuine use.

```
Feature_Flags__c
  Enable_New_Claim_Wizard__c    Checkbox
  Enable_Beta_Search__c         Checkbox
```

```java
public static Boolean isEnabled(String feature) {
    Feature_Flags__c flags = Feature_Flags__c.getInstance();
    if (flags == null) {
        return false;
    }
    return feature == 'ClaimWizard' ? flags.Enable_New_Claim_Wizard__c == true : false;
}
```

A pilot group gets the setting at the profile or user level; everyone else gets the org default. Rolling out means changing the org default; rolling back means changing it again — no deployment either way.

**Custom Permissions are usually better** for permission-shaped toggles, because they are assignable through permission sets and appear in formulas and validation rules. Custom Settings are right when the flag is genuinely operational rather than a permission. See [[03.4 - Permission Sets and Permission Set Groups]].

## Writing them

Unlike custom metadata, Custom Settings use ordinary DML.

```java
Automation_Settings__c settings = Automation_Settings__c.getOrgDefaults();
if (settings == null) {
    settings = new Automation_Settings__c(SetupOwnerId = UserInfo.getOrganizationId());
}
settings.Disable_All_Automation__c = true;
upsert settings;
```

**`SetupOwnerId`** determines the level: the org Id for the default, a profile Id, or a user Id.

Because writes are ordinary DML, they count toward the DML limit and are subject to the usual transaction semantics — including rollback.

## The setup object problem

**Custom Settings are not setup objects** for the mixed-DML rule, which surprises people who assume they are. DML on a Custom Setting and on a normal object can share a transaction.

`User`, `PermissionSetAssignment`, and `GroupMember` are setup objects; `Automation_Settings__c` is not. See [[10.7 - Mixed DML and Setup Objects]].

## Testing

**Custom Setting data does not exist in tests**, because tests run without org data.

```java
@IsTest
static void bypassPreventsHandlerWork() {
    // the record must be created in the test; deployed data is invisible
    insert new Automation_Settings__c(
        SetupOwnerId = UserInfo.getOrganizationId(),
        Disable_All_Automation__c = true
    );

    Warranty_Claim__c claim = TestDataFactory.buildClaim(600000);

    Test.startTest();
    insert claim;
    Test.stopTest();

    Warranty_Claim__c saved = [
        SELECT Approval_Tier__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.isNull(saved.Approval_Tier__c, 'Bypass should have prevented the derived field');
}
```

A test data factory method creating the settings is worth having, since nearly every test in an org with a bypass mechanism needs it:

```java
@IsTest
public static void setupDefaultSettings() {
    insert new Automation_Settings__c(
        SetupOwnerId = UserInfo.getOrganizationId(),
        Disable_All_Automation__c = false
    );
}
```

This is the opposite of custom metadata, where deployed records **are** visible in tests. Knowing which behaves which way avoids a confusing hour.

## Limits

```
Total custom setting data          10 MB, or 1 MB per 10 user licences, whichever is greater
Fields per setting                 300
No long text areas
No relationships
Data does not deploy
```

The size cap is org-wide across all Custom Settings and is genuinely small. Anything approaching it should be a custom object.

## Custom Settings versus Custom Metadata

| | Custom Settings | Custom Metadata |
| --- | --- | --- |
| Data deploys | **No** | **Yes** |
| Hierarchy (user/profile/org) | **Yes** | No |
| SOQL cost | None via methods | None |
| Written by Apex | Ordinary DML | Async deployment |
| Visible in tests | No | Yes |
| Relationships | No | Yes, to metadata |
| Protected in packages | Limited | Yes |
| Size limit | 10 MB org-wide | Larger |

**Choose Custom Metadata unless you need the hierarchy or Apex-driven writes.**

That reduces to two real use cases for Custom Settings in a new org: the **automation bypass** and **per-user feature flags**. Everything else — thresholds, mappings, endpoints, reference data — belongs in Custom Metadata.

## Migrating away

An older org typically has a dozen Custom Settings holding what should be metadata.

The signals to migrate:

- No hierarchy is used — only `getOrgDefaults()` is ever called
- The values are the same in every environment
- Someone has to remember to populate them after a refresh
- The values are business configuration rather than operational switches

The sequence: create the metadata type, deploy the records, change the reader to check metadata with a fallback to the setting, verify, remove the fallback, delete the setting.

The fallback step matters — it lets both coexist during the transition rather than requiring a coordinated cutover.

## Practical guidance

**Use Custom Settings only for the hierarchy** — bypass switches and per-user flags.

**Always null-check.** The data does not deploy, so a fresh org has none.

**Create the records in tests.** Deployed data is invisible there.

**Use the convenience methods**, not SOQL, to avoid consuming a query.

**Build the bypass mechanism with both a static and a setting path**, and test it.

**Prefer Custom Permissions** for permission-shaped toggles.

**Migrate list Custom Settings to Custom Metadata.** There is no remaining reason to use them.

**Document which settings must be populated after a sandbox refresh** — it is otherwise discovered by failure.
