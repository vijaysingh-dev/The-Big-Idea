# Data Ownership

#backend #microservices #databases

> **In one line:** One service owns each piece of data and nobody else writes it — which means the joins you took for granted become either network calls or deliberate duplication, and choosing which is most of the work.

---

## The Idea

⚠️ **A shared database is not microservices.** If two services write the same table, a schema change requires coordinating both deployments, which is exactly the coupling you were trying to remove ([[10.1 - Monolith Modular Monolith Microservices]]).

```
❌  documents-service ─┐
    billing-service   ─┼─→ one database
    search-service    ─┘

✅  documents-service → documents_db
    billing-service   → billing_db
    search-service    → search_db
```

| Rule | |
|---|---|
| **One writer per table** | Exactly one service |
| **No cross-service queries** | No joins across a boundary |
| **No shared schema migrations** | Each service owns its own |
| Read access to another service's data | **Only through its API or its events** |

💡 **The ownership rule is what makes independent deployment possible.** A service that can change its schema without telling anyone can deploy without telling anyone.

---

## What You Lose

### Joins

```sql
-- Monolith
SELECT d.title, u.name, o.plan
FROM documents d JOIN users u ON u.id = d.author_id JOIN orgs o ON o.id = d.org_id
WHERE d.org_id = $1 ORDER BY d.created_at DESC LIMIT 20;
```

```python
# Split across three services
docs = await document_service.list(org_id, limit=20)
users = await user_service.get_many([d.author_id for d in docs])     # batch
org = await billing_service.get_org(org_id)
# assemble in application code
```

⚠️ **Three round trips instead of one query**, and if you forget to batch it becomes N+1 across the network ([[05.6 - The N+1 Problem and DataLoader]]).

**Filtering and sorting are worse:**

```sql
-- Impossible across services
SELECT * FROM documents d JOIN orgs o ON o.id = d.org_id
WHERE o.plan = 'enterprise' ORDER BY d.created_at LIMIT 20;
```

💡 **You cannot filter service A's data by service B's attributes without either fetching everything or duplicating the attribute.** This is the constraint that forces the duplication decisions below.

### Foreign keys

```sql
ALTER TABLE documents ADD FOREIGN KEY (org_id) REFERENCES organisations(id);
```

⚠️ **Across services, this is impossible.** The database cannot enforce a reference to a table it does not have.

| Consequence | |
|---|---|
| Orphaned references | A document pointing at a deleted organisation |
| No `ON DELETE CASCADE` | Cleanup becomes an event-driven process |
| No referential integrity check | Your application is the only guard |

💡 **You now need reconciliation** — a periodic job finding documents whose organisation no longer exists.

### Transactions

Covered in [[10.1 - Monolith Modular Monolith Microservices]] and [[08.11 - Durable Workflows and Sagas]]. **Every operation spanning a boundary becomes a saga.**

## The Three Strategies

For data a service needs but does not own.

### 1. Call the owner

```python
org = await billing_service.get_org(org_id)
```

| | |
|---|---|
| **Good** | Always current. No duplication. No sync |
| **Bad** | **Availability coupling.** Latency. N+1 risk |

💡 **Right for data that changes often, is read rarely, and where staleness matters** — a current account balance, a live quota.

⚠️ **Every such call is a synchronous required dependency** unless you degrade ([[10.3 - Communication Patterns]]).

### 2. Duplicate via events

```python
# billing-service publishes
await publish("organisation.plan_changed", {"org_id": ..., "plan": "enterprise"})

# documents-service maintains a local copy
async def on_plan_changed(event):
    await conn.execute(
        "INSERT INTO org_cache (org_id, plan, updated_at) VALUES ($1, $2, now()) "
        "ON CONFLICT (org_id) DO UPDATE SET plan = $2, updated_at = now()",
        event["org_id"], event["plan"],
    )
```

```sql
-- Now the join is local again
SELECT d.* FROM documents d JOIN org_cache o ON o.org_id = d.org_id
WHERE o.plan = 'enterprise';
```

| | |
|---|---|
| **Good** | **Local joins. No availability coupling. Fast** |
| **Bad** | Eventually consistent. Duplicated data. Sync can drift |

💡 **This is the strategy that makes microservices workable**, and it is what "event-carried state transfer" means in practice ([[09.2 - Event Modeling]]).

⚠️ **The local copy is a cache, not a source of truth.** It must be rebuildable from the event log, and it must never be edited locally.

**Name it accordingly** — `org_cache`, not `organisations` — so nobody mistakes it for owned data.

### 3. Snapshot at the time of the event

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY,
    customer_id uuid NOT NULL,
    shipping_address jsonb NOT NULL,      -- ← copied, deliberately
    ...
);
```

⚠️ **This is not duplication, it is a different fact.** The order's shipping address is where the order went, and it must not change when the customer moves ([[06.10 - Schema Design]]).

💡 **Recognising snapshot data is important**, because it looks like denormalisation and it is not — there is no sync to maintain and no drift to reconcile.

**Every historical record should snapshot the values that made it meaningful**: the price at purchase, the plan at billing, the permissions at the time of an audit entry.

### Choosing

```
Does the value change after the fact matters?
├── NO  → snapshot it. It is a different fact
└── YES → is staleness acceptable?
    ├── NO  → call the owner (accept the coupling)
    └── YES → duplicate via events
```

| Data | Strategy |
|---|---|
| Organisation name, for display | **Duplicate** |
| Organisation plan, for filtering | **Duplicate** |
| Current quota usage | **Call the owner** — must be current |
| Author display name | **Duplicate** |
| Shipping address on an order | **Snapshot** |
| Permission check | **Call the owner** — never stale for security |

⚠️ **The permission row is worth stating explicitly.** A duplicated permission cache means a revoked user retains access until the event propagates. **Never duplicate authorisation state** ([[07.1 - Cache Layers Across One Request]]).

## Keeping Duplicates Correct

⚠️ **Every duplicate drifts eventually.** A missed event, a bug, a manual database edit, a replay gone wrong.

### Reconciliation

```python
async def reconcile_org_cache():
    local = await conn.fetch("SELECT org_id, plan, updated_at FROM org_cache")
    remote = await billing_service.list_orgs([r["org_id"] for r in local])

    for row in local:
        actual = remote.get(row["org_id"])
        if actual is None:
            reconcile_orphan_total.inc()
            await conn.execute("DELETE FROM org_cache WHERE org_id = $1", row["org_id"])
        elif actual["plan"] != row["plan"]:
            reconcile_drift_total.inc()
            await update_local(actual)
```

💡 **A nightly reconciliation job is not optional for duplicated data.** It is what turns "we hope the events all arrived" into "we know they did".

⚠️ **Alert on `reconcile_drift_total` being non-zero.** Drift means an event was lost or a consumer had a bug, and it will happen again.

**A checksum comparison is cheaper than a full compare for large datasets:**

```python
local_hash = await conn.fetchval(
    "SELECT md5(string_agg(org_id || plan, ',' ORDER BY org_id)) FROM org_cache"
)
remote_hash = await billing_service.checksum()
```

### Rebuildability

💡 **Every duplicated dataset must be rebuildable from the event log** ([[09.7 - Replay Backfill and Reprocessing]]).

```python
async def rebuild_org_cache():
    await conn.execute("TRUNCATE org_cache")
    await reset_consumer_offset("organisation-events", 0)
    # replay
```

**Test the rebuild.** A duplicate you cannot rebuild is a second source of truth, and now you have a consistency problem with no resolution procedure.

⚠️ **Rebuild requires either infinite retention on the source topic, or a compacted topic** ([[09.1 - Queue vs Log]]). **Compacted topics are the natural fit for reference data** — a consumer reading from offset 0 gets the current state of every key.

## The Migration

Splitting a shared database is the hard part of extracting a service.

```
1. Separate schemas in one database
2. Separate database roles — cross-schema access becomes an error
3. Replace cross-schema joins with API calls or duplication
4. Remove cross-schema foreign keys
5. Replace cross-schema transactions with sagas
6. Move the schema to its own database
```

⚠️ **Step 4 is where the design decisions become irreversible.** Dropping a foreign key means the database no longer guards that reference, and every code path that relied on it must now be checked.

💡 **Steps 1–3 are all reversible and all deliverable in a monolith** ([[10.2 - Finding Service Boundaries]]). Only step 6 requires the split.

```sql
-- Step 2: make the boundary enforceable
CREATE SCHEMA documents;
CREATE ROLE documents_role;
GRANT ALL ON SCHEMA documents TO documents_role;
REVOKE ALL ON SCHEMA documents FROM billing_role;
```

**Now a cross-boundary query is a permission error, not a code review comment.**

### Finding the crossings

```sql
-- Foreign keys crossing a boundary
SELECT tc.table_schema, tc.table_name, ccu.table_schema AS target_schema
FROM information_schema.table_constraints tc
JOIN information_schema.constraint_column_usage ccu ON tc.constraint_name = ccu.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
  AND tc.table_schema <> ccu.table_schema;
```

```sql
-- Queries joining across schemas
SELECT query, calls FROM pg_stat_statements
WHERE query LIKE '%documents.%' AND query LIKE '%billing.%'
ORDER BY calls DESC;
```

💡 **Run both before deciding to split.** They tell you exactly how much work the boundary is, and sometimes they tell you not to.

## In Production

### The ownership register

```markdown
| Data           | Owner              | Duplicated in       | Sync mechanism      |
|----------------|--------------------|---------------------|---------------------|
| documents      | documents-service  | search-service      | CDC                 |
| organisations  | billing-service    | documents, search   | organisation.* events |
| users          | auth-service       | documents (name only) | user.* events     |
| permissions    | auth-service       | **nowhere**         | always called       |
| chunks         | documents-service  | search-service      | CDC                 |
```

💡 **This register is the most useful microservices document you will write.** It answers "who can change this", "what breaks if this is wrong", and "where do I look when it drifts".

⚠️ **Every row in the "duplicated in" column needs a reconciliation job and a rebuild procedure.** If it does not have both, it will drift silently.

### Monitoring duplicated data

```python
duplicate_staleness_seconds.labels(dataset="org_cache").set(now - oldest_update)
duplicate_row_count.labels(dataset="org_cache", side="local").set(n)
duplicate_row_count.labels(dataset="org_cache", side="remote").set(n)
reconcile_drift_total.labels(dataset="org_cache").inc()
reconcile_orphan_total.labels(dataset="org_cache").inc()
```

⚠️ **`duplicate_staleness_seconds` climbing means the sync has stopped**, and the local copy is quietly getting more wrong. **It is the metric that catches a dead consumer before the drift becomes visible.**

### Deleting across services

```
organisation.deleted → every service holding org data must clean up
```

⚠️ **There is no `ON DELETE CASCADE` across a boundary.** Deletion becomes a distributed process, and it must be verifiable ([[06.16 - Multi Tenant Data Models]]).

```python
async def on_organisation_deleted(event):
    org_id = event["org_id"]
    await conn.execute("DELETE FROM documents WHERE org_id = $1", org_id)
    await conn.execute("DELETE FROM org_cache WHERE org_id = $1", org_id)
    await publish("documents.org_cleanup_completed", {"org_id": org_id})
```

💡 **Each service acknowledges completion**, and a coordinator tracks which have finished. **Without that, "did we actually delete everything" is unanswerable** — which is a compliance problem, not just an engineering one.

**Reconciliation catches what the event missed:** a periodic job finding documents whose organisation no longer exists.

### Read models

```
documents-service    owns documents
search-service       owns a read model built from document events
analytics-service    owns a read model built from the same events
```

💡 **Multiple read models over one event stream is the natural shape**, and each is independently rebuildable ([[09.7 - Replay Backfill and Reprocessing]]).

⚠️ **A read model is not a duplicate to reconcile — it is derived state.** The distinction: a duplicate mirrors another service's data; a read model is a transformation you own. **Read models need rebuild procedures, not reconciliation.**

### Conduit's ownership

| Data | Owner | Duplicated | Mechanism |
|---|---|---|---|
| Documents, chunks | **documents-service** | search index | CDC |
| Sources, credentials | documents-service | — | — |
| Organisations, plans | billing-service | documents (`org_cache`) | events |
| Users | auth-service | documents (name only) | events |
| **Permissions** | auth-service | **nowhere** | **always called** |
| Annotations | documents-service | search index | CDC |
| Usage counters | billing-service | — | built from events |

💡 **Two duplications and one absolute prohibition.** The permission row is the security boundary, and the cost of calling auth synchronously on every request is accepted deliberately.

⚠️ **`org_cache` exists solely so that "list enterprise organisations' documents" is a local join.** Without it, that query would fetch every organisation from billing and filter in application code. **The duplication is buying a specific query**, and that is the right justification.

## Codebase

**Repo:** `GoogleCloudPlatform/microservices-demo`, `saleor/saleor`, `debezium/debezium`

**Question to answer:** In Online Boutique, which service owns which data, and where does one service need another's data? Then: how does Saleor snapshot data onto orders, and why?

**Read, in order:**

1. `microservices-demo/protos/demo.proto` — **the ownership map, implied by the APIs.** For each service, what does it own and what does it fetch?
2. `microservices-demo/src/checkoutservice/main.go` — **the assembly.** It fetches cart, products, shipping and currency to build one order. **Count the calls and note what is snapshotted onto the order**
3. `saleor/saleor/order/models.py` — **`OrderLine`.** Note `product_name`, `variant_name` and `unit_price` copied onto the line rather than referenced. **This is snapshot data and the reasoning is in the field names**
4. `saleor/saleor/order/models.py` — the shipping and billing address fields. **Copied, not referenced**, for the same reason
5. `debezium/debezium-connector-postgres/` — how CDC keeps a read model in sync, and what happens when it falls behind ([[09.4 - Change Data Capture]])

💡 The Saleor `OrderLine` is the clearest example of snapshot data in an open codebase. **An order line records what was bought at what price with what name**, and none of those change when the product does. **Recognising which of your fields are snapshots removes them from the sync problem entirely.**

**Size:** 1 session.

**Part 1 — Analyse the crossings.** A shared-database schema with documents, organisations, users and annotations.

Run both analysis queries: foreign keys crossing candidate boundaries, and queries joining across them, weighted by frequency.

**Produce the crossing map**, and identify which boundaries are cheap and which are expensive.

**Part 2 — Three strategies, measured.** The query "list enterprise organisations' documents, with author names".

Implement it three ways: call the owners, duplicate organisation and user data locally, and a hybrid.

Measure: latency p50 and p99, network calls per request, and **effective availability** with each dependency at 99.9%.

**Then take the billing service down.** Confirm the call-owner version fails and the duplicate version does not.

**Part 3 — Snapshot versus duplicate.** An order-like record with a price and an address.

Implement one as a duplicate synced by events and one as a snapshot.

**Then change the source values** — the product price and the customer address. **Confirm the snapshot does not change and the duplicate does**, and confirm that is the correct behaviour for each.

**Part 4 — Induce drift.** With `org_cache` synced by events:

- Drop 5% of events randomly
- Manually edit a row in the billing database, bypassing the event
- Replay events out of order
- Let the consumer be down for an hour, then restart

**Measure drift after each**, using a full comparison and a checksum comparison.

Then implement reconciliation and confirm it repairs every case. **Measure the cost of a full reconciliation at 1 million rows** versus a checksum comparison.

**Part 5 — Rebuild from events.** Truncate `org_cache` and rebuild from the event log.

**Verify byte-identical to the source.**

Then set the source topic's retention below your rebuild window and **confirm the rebuild is incomplete.** Then switch to a compacted topic and confirm it works.

**Part 6 — Distributed deletion.** Delete an organisation with 10,000 documents, 50,000 chunks, cache entries and a search index.

**Without coordination:** publish the event and hope. **Count what is left behind after a consumer misses it.**

**With acknowledgement:** each service reports completion, and a coordinator tracks it. **Confirm you can answer "is this organisation fully deleted" definitively.**

Then write the verification query per store, and run it.

**Part 7 — The migration, six steps.** Starting from the shared database, execute all six steps while serving traffic.

For each step measure: downtime, code changed, and what broke.

**Step 4 — dropping foreign keys — should be the one that requires the most thought.** Enumerate every code path that relied on the constraint.

**Part 8 — The ownership register.** Write it for Conduit: every dataset, its owner, where it is duplicated, the sync mechanism, the reconciliation job, and the rebuild procedure.

**For every duplication, justify what query it buys you.** If it does not buy a specific query, remove it.

**Done when:**
- Your crossing map identifies cheap and expensive boundaries with numbers
- The three-strategy comparison includes effective availability
- A snapshot demonstrably does not change when its source does
- Four kinds of drift are induced and repaired by reconciliation
- A rebuild fails on a non-compacted topic and succeeds on a compacted one
- You can definitively answer "is this organisation fully deleted"
- The six-step migration completed with zero downtime
- Every duplication in the register buys a named query
