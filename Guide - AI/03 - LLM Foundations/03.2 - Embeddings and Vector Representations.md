# Embeddings and Vector Representations

## Definition

An **embedding** is a dense vector of floating-point numbers that represents the meaning of a piece of text in a high-dimensional space.

```
"The cat sat on the mat"  →  [0.12, -0.83, 0.45, ..., 0.67]  (768 or 1536 numbers)
```

The key property: **semantically similar texts produce geometrically similar vectors**.

```
"The cat sat on the mat"   →  [0.12, -0.83, 0.45, ...]
"A feline rested on a rug" →  [0.14, -0.81, 0.47, ...]  ← very close
"How to invest in stocks"  →  [-0.67, 0.23, -0.88, ...] ← far away
```

This is what makes semantic search possible: find documents with vectors close to the query vector.

---

## How Embeddings are Produced

### From Encoder Models (Recommended for RAG)

Pass text through an encoder model; take the output vector as the embedding:

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")
embedding = model.encode("The cat sat on the mat")
# shape: (384,)  — 384-dimensional vector
```

The model's weights encode everything learned during training about semantic relationships.

### From Embedding APIs

```python
import openai
response = openai.embeddings.create(
    model="text-embedding-3-small",
    input="The cat sat on the mat"
)
embedding = response.data[0].embedding
# shape: (1536,)
```

### Common Embedding Models

|Model|Dimensions|Context|Use case|
|---|---|---|---|
|`text-embedding-3-small`|1536|8191 tokens|General purpose, cheap|
|`text-embedding-3-large`|3072|8191 tokens|Higher quality|
|`all-MiniLM-L6-v2`|384|256 tokens|Fast, local, smaller docs|
|`bge-large-en-v1.5`|1024|512 tokens|Strong open-source|
|`nomic-embed-text`|768|8192 tokens|Long-context open-source|
|`cohere-embed-v3`|1024|512 tokens|Strong for multilingual|

## What the Vector Dimensions Mean

Individual dimensions are **not interpretable** — there's no "dimension 47 = sentiment." The meaning is encoded in relationships between dimensions across the full vector.

What _is_ meaningful:

- **Direction**: semantically similar texts point in similar directions
- **Distance**: closer vectors = more similar meaning
- **Arithmetic**: `king - man + woman ≈ queen` (classic demo)

The geometry of the embedding space encodes the semantic structure of language.

---

## Embedding Space Properties

### Isotropy Problem

Real embedding spaces are not uniformly distributed — they cluster in certain regions. This can hurt retrieval quality. Some embedding models apply post-processing (e.g., Whitening) to spread vectors more uniformly.

### Dimensionality and Quality

Higher dimensions can encode more nuance but:

- Cost more memory in the vector DB
- Slow down similarity search
- Sometimes overfit to training data

OpenAI's `text-embedding-3` models support **Matryoshka Representation Learning (MRL)** — you can truncate to fewer dimensions (e.g., 256) with graceful quality degradation, saving cost.

### Late Chunking

A newer technique: rather than embedding each chunk independently, embed the full document and then slice the output vectors for each chunk. This preserves more cross-chunk context in each chunk's embedding. Used by Jina AI's embedding models.

---

## Embedding Different Content Types

### Queries vs Documents

In asymmetric retrieval, the query and documents are semantically different in structure:

- Query: "What is the capital of France?"
- Document: "Paris is the capital and most populous city of France."

Some embedding models (like `bge`, `e5`) support explicit query/document prefixes:

```python
query_embedding = model.encode("query: What is the capital of France?")
doc_embedding = model.encode("passage: Paris is the capital of France.")
```

Using the wrong prefix degrades retrieval quality.

### Code Embeddings

Code has different structure than natural language. Specialized models exist:

- `code-search-net` (HuggingFace)
- OpenAI `text-embedding-3` performs reasonably on code
- For serious code search: `voyage-code-2` (Voyage AI)

### Multimodal Embeddings

CLIP-style models embed both images and text into the same space, enabling cross-modal retrieval. Relevant for document pipelines that include images/diagrams.

## The Embedding Pipeline in RAG

```
Document text
      │
  [Chunker]           ← split into retrieval-sized pieces
      │
  [Embedding model]   ← encode each chunk into a vector
      │
  [Vector DB]         ← store (vector, chunk_text, metadata)

Query text
      │
  [Embedding model]   ← encode query into a vector (same model!)
      │
  [ANN Search]        ← find top-K vectors closest to query vector
      │
  Retrieved chunks
```

**Critical**: Query and documents must use the **same embedding model**. Mixing models produces garbage results because the vector spaces are different.

---

## Embedding Drift and Staleness

If you switch embedding models (e.g., upgrade from `text-embedding-ada-002` to `text-embedding-3-small`), you **must re-embed your entire corpus**. The new model's vector space is different — old document vectors are incompatible with new query vectors.

In production systems, this means:

- Embedding model version is tracked in the index metadata
- Upgrades require a background re-indexing job
- Zero-downtime upgrades require dual indices during migration
