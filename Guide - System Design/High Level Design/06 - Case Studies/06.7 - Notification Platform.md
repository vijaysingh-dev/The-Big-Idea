# Case Study: Notification Platform at Scale

> **Revision tags:** #case-study #notifications #fan-out  
> **Related:** [[03.16 - Notification Systems]] | [[04.10 - Notification System]]

---

## Requirements Clarification

**Functional:**
- Multi-channel delivery: push, email, SMS, in-app
- Template-based notifications with variable substitution
- User preference management (opt-in/out per category, quiet hours)
- Scheduled notifications (send at a specific time)
- Broadcast notifications (send to all users or large segments)
- Delivery tracking (sent, delivered, opened, clicked)

**Non-functional:**
- Transactional notifications (order confirmation): < 5s end-to-end
- Marketing campaigns: up to 100M recipients within 1 hour
- 99.9% delivery rate for transactional
- Deduplication: same notification must not be sent twice
- Scale: 1B notifications/day

**Out of scope:** A/B testing of notification content, ML-based send-time optimization, in-app inbox UI

---

## Estimation

```
1B notifications/day:
  Push:  600M/day = 7,000/s average; peak 50,000/s (campaign sends)
  Email: 300M/day = 3,500/s average
  SMS:   100M/day = 1,160/s average

Campaign burst:
  Send to 100M users in 1 hour = 100M / 3600 = 27,800/s sustained

APNs/FCM batch API:
  FCM: 500 tokens per batch call
  27,800/s ÷ 500 = 56 batch API calls/s to FCM → very manageable

Storage:
  Per notification record: ~200 bytes
  1B × 200 bytes = 200 GB/day → partition by date, archive after 30 days
```

**Key challenge:** Campaign burst. Sending 100M notifications in 1 hour requires a fan-out architecture that can scale horizontally on demand.

## Architecture

```
[Event Sources]                [Campaign API]
  (order-service,              (manual/scheduled sends)
   payment-service, etc.)
        │                            │
        └────────────────┬───────────┘
                         ▼
              [Notification API Service]
                         │
                    [Kafka: notification-requests]
                         │
              ┌──────────┼──────────────┐
              ▼          ▼              ▼
      [Preference   [Template      [Rate Limiter]
        Filter]       Engine]
              │          │              │
              └──────────┼──────────────┘
                         ▼
              [Kafka: delivery-tasks]
              (partitioned by user_id)
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
   [Push Workers]  [Email Workers]  [SMS Workers]
   (APNs/FCM)      (SendGrid/SES)   (Twilio)
         │               │               │
         └───────────────┼───────────────┘
                         ▼
                [Delivery Log DB]
                (ClickHouse / Cassandra)
```

## Campaign Fan-Out Design

Sending to 100M users efficiently requires partitioned parallel processing.

### Step 1: Segment Resolution

```
Campaign: "Send to all premium users in India"
    │
    ▼
Segment Service
  SELECT user_id FROM users
  WHERE plan = 'premium' AND country = 'IN'
  → Returns 10M user_ids
```

For large segments, don't load all IDs into memory. Stream them:

```python
# Stream user_ids in batches, emit to Kafka
cursor = db.execute_cursor("SELECT user_id FROM users WHERE ...", batch_size=10000)
for batch in cursor:
    for user_id in batch:
        kafka.produce("notification-requests", key=user_id, value={
            "campaign_id": "camp_123",
            "user_id": user_id,
            "template": "summer_sale",
            "scheduled_at": send_time
        })
```

### Step 2: Per-User Fan-Out Workers

Kafka partitioned by `user_id` — all messages for a user go to the same partition, processed in order.

```
Workers (50 instances) consume from notification-requests:
  For each message:
    1. Fetch user preferences (Redis cache, 60s TTL)
    2. Check opt-out (has user opted out of this category?)
    3. Check quiet hours
    4. Check rate limit (max N notifications/day per user)
    5. Resolve channel (email, push, SMS based on preferences)
    6. Render template with user variables
    7. Emit to delivery-tasks topic (partitioned by channel)
```

### Step 3: Channel Workers

```
Push workers (100 instances):
  Consume from delivery-tasks:push
  Batch tokens: accumulate up to 500 tokens
  Call FCM batch API → track delivery receipts

Email workers (50 instances):
  Consume from delivery-tasks:email
  Call SendGrid batch API (up to 1000 emails per call)

SMS workers (20 instances):
  Consume from delivery-tasks:sms
  Call Twilio API (individual calls — no batch API)
```

### Throughput Math

```
Campaign: 100M users in 1 hour
  = 27,800 notifications/s

Fan-out workers (50 instances):
  Each handles 27,800 / 50 = 556/s
  With 60ms per user (preference check + render): 1000/60 = 16/s per thread
  50 workers × 20 threads each = 1000 concurrent → 1000 × 16/s = 16,000/s → too slow

Scale to 200 workers:
  200 × 20 threads = 4,000 concurrent
  4,000 × 16/s = 64,000/s → sufficient for 27,800/s with headroom
```

Worker count scales with campaign size. Auto-scale consumer group based on Kafka lag.

## Template Engine

Templates use variable substitution with fallbacks:

```
Template: "order_shipped"
Subject:  "Your order #{{order_id}} has shipped!"
Body:     "Hi {{user.first_name | 'there'}},
           Your order {{order_id}} is on its way.
           Track at: {{tracking_url}}"
```

Templates stored in a CMS or config store. Rendered at send time — not at campaign creation. This allows personalizing millions of messages with current data.

**Multi-language:** Template has variants per locale. Locale looked up from user preferences.

## Delivery Tracking

Every notification is tracked through its lifecycle:

```
States: QUEUED → SENT → DELIVERED → OPENED → CLICKED
                     ↘ FAILED → RETRY → PERMANENT_FAILED

Push: FCM/APNs return delivery receipts per device token
Email: SendGrid webhooks (delivered, opened, clicked, bounced, spam)
SMS: Twilio status callbacks (sent, delivered, failed)
```

**Storage:** ClickHouse (columnar, fast aggregations for reporting):

```sql
CREATE TABLE notification_events (
    notification_id  UUID,
    campaign_id      UUID,
    user_id          BIGINT,
    channel          Enum('push','email','sms'),
    event_type       Enum('queued','sent','delivered','opened','clicked','failed'),
    timestamp        DateTime,
    metadata         String   -- JSON blob: error_code, device_type, etc.
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (campaign_id, user_id, timestamp);
```

Query: "What's the open rate for campaign_123?"
```sql
SELECT
  countIf(event_type = 'opened') / countIf(event_type = 'delivered')
FROM notification_events
WHERE campaign_id = 'camp_123';
```

## Deduplication

Retries in Kafka (at-least-once delivery) can cause duplicate sends.

```python
def send_notification(notification_id, user_id, channel, content):
    dedup_key = f"notif:{notification_id}:{channel}"

    # Atomic check-and-set: only proceed if key didn't exist
    if redis.set(dedup_key, 1, nx=True, ex=86400):
        dispatch_to_provider(user_id, channel, content)
        log_to_clickhouse(notification_id, "sent")
    else:
        log_to_clickhouse(notification_id, "deduplicated")
```

The `notification_id` is the idempotency key — generated once when the notification is first created, carried through the pipeline.

## Scheduled Notifications

Send at a specific future time (e.g., "weekly digest every Monday 9 AM user's local time"):

```
Notification creation → stored with scheduled_at timestamp
                              │
                   [Scheduler Worker]
                   Polls DB: SELECT * FROM scheduled_notifications
                             WHERE scheduled_at <= NOW() AND status = 'PENDING'
                   For each due notification:
                     → Emit to notification-requests Kafka topic
                     → Mark as DISPATCHED
```

For time-zone-aware scheduling (Monday 9 AM in user's timezone):
- Store user timezone in preferences
- Convert "Monday 9 AM local" to UTC at scheduling time
- Or: re-calculate UTC time daily for rolling schedules

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| FCM API down | Push notifications not delivered | Retry with exponential backoff; fall back to SMS/email if critical |
| Stale device token | APNs returns 410 | Remove token from DB; don't retry push, fall back to other channel |
| Email provider rate limit | Email queue backs up | Multiple providers (failover: SES → SendGrid); rate limit per provider |
| Consumer worker crash | Messages reprocessed on restart | Dedup key prevents double-send |
| ClickHouse slow | Delivery log write delayed | Async write via Kafka → ClickHouse; not on hot path |
| Campaign fan-out too slow | Late deliveries | Monitor Kafka lag; auto-scale workers; pre-warm worker pool |

---

## What This Design Demonstrates

- Two-stage fan-out: segment resolution → per-user enrichment → per-channel dispatch
- Kafka partitioned by user_id for ordered, parallel per-user processing
- Deduplication with Redis NX for idempotent sends
- ClickHouse columnar store for delivery analytics
- Auto-scaling workers based on Kafka lag
- Channel fallback strategy
