# The Event Model

Every DOM event travels through the tree in three phases. Understanding the path is what makes delegation, modals and "why did my handler fire twice" tractable.

## The three phases

```
                  window
                     |          1. CAPTURE  (down)
                  document
                     |
                    body
                     |
                   <div>
                     |
                  <button>      2. TARGET
                     |
                   <div>
                     |          3. BUBBLE   (up)
                  document
```

1. **Capture** — from `window` down to the target. Handlers registered with `{ capture: true }` fire here.
2. **Target** — at the element itself. Both capture and bubble handlers on the target fire, in registration order.
3. **Bubble** — back up to `window`. Default for `addEventListener`.

```js
el.addEventListener("click", handler);                  // bubble
el.addEventListener("click", handler, true);            // capture
el.addEventListener("click", handler, { capture: true });
```

Not all events bubble. `focus`, `blur`, `load`, `error`, `mouseenter` and `mouseleave` do not. Their bubbling counterparts are `focusin`/`focusout` and `mouseover`/`mouseout` — which is why event delegation for focus uses `focusin`.

`event.bubbles` tells you at runtime.

## target vs currentTarget

```js
list.addEventListener("click", (e) => {
  e.target;         // the deepest element actually clicked
  e.currentTarget;  // the element the listener is attached to (list)
  this;             // same as currentTarget, in a non-arrow function
});
```

This distinction is the entire basis of delegation ([[12.4 - Event Delegation]]). `e.target` could be a `<span>` inside a `<button>` inside the `<li>` you care about — which is why `e.target.closest(".item")` is the standard idiom rather than using `e.target` directly.

`e.composedPath()` returns the full array of nodes the event will traverse, including through shadow DOM boundaries. Useful for "did this click happen inside my component" checks that must work with web components.

## Stopping propagation

```js
e.stopPropagation();          // stop travelling further up (or down)
e.stopImmediatePropagation(); // also skip other handlers on THIS element
e.preventDefault();           // cancel the default browser action
```

These are independent. `preventDefault()` stops the browser's built-in behavior — following a link, submitting a form, checking a checkbox — but the event keeps propagating. `stopPropagation()` stops travel but the default action still happens.

`e.defaultPrevented` lets a later handler check whether someone already cancelled.

**`stopPropagation()` is usually a mistake.** It breaks anything relying on delegation higher up — analytics, dropdown close-on-outside-click, focus management in a modal library. The event disappearing at an arbitrary depth is very hard to debug from the outside.

Better alternatives:

```js
// Instead of stopping propagation, check the origin
document.addEventListener("click", (e) => {
  if (menu.contains(e.target)) return;
  closeMenu();
});
```

Or use a capture-phase listener on the container when you genuinely need to intercept before children see it.

## Return value and passive

```js
el.addEventListener("wheel", handler, { passive: true });
```

`{ passive: true }` promises the handler will not call `preventDefault()`. Without it, the browser must run your handler before scrolling, because you might cancel the scroll — adding latency to every scroll and touch. Browsers now default `touchstart`, `touchmove` and `wheel` on `window`/`document` to passive for this reason.

Calling `preventDefault()` in a passive listener is ignored, with a console warning.

## Listener options

```js
el.addEventListener("click", handler, {
  once: true,        // auto-remove after firing once
  capture: false,
  passive: true,
  signal: controller.signal,   // remove via AbortController
});
```

`{ once: true }` removes the need for self-removing handlers. `{ signal }` removes any number of listeners with one `abort()` call and is the cleanest teardown mechanism available ([[04.6 - AbortController and Cancellation]]).

Note that removal requires the same function reference *and* the same capture value — a listener added with `capture: true` is not removed by a call without it.

## Event objects worth knowing

```js
// Mouse
e.clientX / clientY      // viewport-relative
e.pageX / pageY          // document-relative (includes scroll)
e.offsetX / offsetY      // relative to the target's padding box
e.button                 // 0 left, 1 middle, 2 right
e.ctrlKey / metaKey / shiftKey / altKey

// Keyboard
e.key                    // "a", "Enter", "ArrowDown" — what you want
e.code                   // "KeyA", "Enter" — physical key, layout-independent
e.repeat                 // held down

// Pointer — unifies mouse, touch and pen
e.pointerType            // "mouse" | "touch" | "pen"
e.pressure
e.isPrimary
```

`e.keyCode` is deprecated; use `e.key` for character intent and `e.code` for physical position (WASD in a game, where the layout should not matter).

**Pointer events** replace separate mouse and touch handling. One set of handlers works across input types, and `setPointerCapture()` makes drag interactions reliable by routing all subsequent events to the captured element even when the pointer leaves it:

```js
el.addEventListener("pointerdown", (e) => {
  el.setPointerCapture(e.pointerId);
});
```

This is far more robust than the old `mousemove` on `document` pattern.

## Custom events

```js
const event = new CustomEvent("cart:updated", {
  detail: { itemCount: 3 },
  bubbles: true,
  composed: true,     // crosses shadow DOM boundaries
  cancelable: true,
});

el.dispatchEvent(event);

document.addEventListener("cart:updated", (e) => {
  console.log(e.detail.itemCount);
});
```

Note `bubbles` defaults to `false` for custom events, which is the opposite of most native events and a common surprise.

`dispatchEvent` is **synchronous** — handlers run before it returns, and its return value is `false` if any handler called `preventDefault()`.

Custom events are the standard communication channel out of a web component, and they are occasionally useful for decoupling in vanilla code. In a React application, props, context and stores are almost always better.

## React's event system

React attaches a single listener per event type at the **root container** and delegates from there. What you receive is a `SyntheticEvent` — a cross-browser wrapper around the native event.

```jsx
<button onClick={e => {
  e.nativeEvent;      // the underlying DOM event
  e.stopPropagation();// stops propagation within React's tree
}} />
```

Practical consequences:

**React events fire after native ones on ancestors** below the root container, because React's listener is at the root. So a native `document` listener added in an effect sees the click *before* a React `onClick` deeper in the tree — the classic reason "click outside to close" fires immediately when opening a menu. Attaching the outside-click listener in the capture phase, or checking the event origin, resolves it.

**`e.stopPropagation()` in React stops the synthetic event only.** Native listeners on ancestors still fire.

**Portals bubble through the React tree, not the DOM tree.** A click inside a portaled modal bubbles to the modal's React parent even though the DOM node is elsewhere ([[22.2 - Portals]]). This is usually what you want, and occasionally surprising.

React 17 moved delegation from `document` to the root container specifically to make multiple React versions on one page coexist.

## How senior engineers actually use this

**They avoid `stopPropagation()`** and check the event origin instead, because it does not break unrelated code higher in the tree.

**They use `{ signal }` for teardown**, which makes forgotten removals structurally unlikely.

**They use pointer events for anything drag-related**, with `setPointerCapture`.

**They mark scroll, wheel and touch listeners passive** unless they genuinely need to cancel.

**They know React's delegation model**, because the interaction between native and synthetic listeners is behind a whole class of confusing bugs.

## Common pitfalls

- `stopPropagation()` breaking delegation elsewhere.
- Expecting `focus` and `blur` to bubble — use `focusin`/`focusout`.
- Custom events not bubbling because `bubbles` defaults to `false`.
- `removeEventListener` failing because of a different function reference or a mismatched capture flag.
- Non-passive scroll listeners causing jank.
- Using `e.target` where `e.currentTarget` or `closest()` was needed.
- Outside-click handlers firing immediately because the opening click reaches `document` after React's root listener.

## Interview angle

"Explain event bubbling and capturing" is guaranteed, and often paired with `target` versus `currentTarget` and the difference between `preventDefault` and `stopPropagation`. Draw the three phases, note which events do not bubble, and explain why `stopPropagation` is usually the wrong tool. React-specific follow-ups about synthetic events and root delegation are common at mid-to-senior level.
