# Data Loading with Loaders and Actions

Fetching in components produces a **waterfall**: render, discover the need for data, fetch, render children, discover their data need, fetch again. Each level of nesting costs a round trip ([[19.4 - Suspense]]).

Loaders move data fetching into the route definition, so the router starts every request for the matched chain **in parallel, before rendering anything**.

## Loaders

```jsx
{
  path: "products/:id",
  loader: async ({ params, request }) => {
    const res = await fetch(`/api/products/${params.id}`, {
      signal: request.signal,
    });
    if (!res.ok) throw new Response("Not found", { status: 404 });
    return res.json();
  },
  element: <ProductDetail />,
  errorElement: <ProductError />,
}
```

```jsx
function ProductDetail() {
  const product = useLoaderData();     // already resolved — no loading state
  return <h1>{product.name}</h1>;
}
```

The component renders with data already present. There is no `isLoading` branch, no `data?.name` optional chaining, no effect.

Three things the router supplies:

**`request.signal`** aborts the fetch when the user navigates away, so a slow request for an abandoned route does not complete ([[04.6 - AbortController and Cancellation]]).

**Throwing a `Response`** routes to the nearest `errorElement` with the status intact — the idiomatic way to signal 404 or 403 from a loader.

**Parallelism.** All loaders in the matched chain run at once, so a layout loader and a detail loader do not serialize.

## Actions

The mutation counterpart, wired to form submissions:

```jsx
{
  path: "products/:id/edit",
  action: async ({ request, params }) => {
    const formData = await request.formData();

    const result = schema.safeParse(Object.fromEntries(formData));
    if (!result.success) {
      return { errors: result.error.flatten().fieldErrors };   // returned, not thrown
    }

    await updateProduct(params.id, result.data);
    return redirect(`/products/${params.id}`);
  },
  element: <EditProduct />,
}
```

```jsx
function EditProduct() {
  const errors = useActionData();
  const navigation = useNavigation();
  const isSubmitting = navigation.state === "submitting";

  return (
    <Form method="post">
      <input name="name" />
      {errors?.name && <p role="alert">{errors.name}</p>}
      <button disabled={isSubmitting}>Save</button>
    </Form>
  );
}
```

The distinction between returning and throwing matters: **return** validation errors so the form re-renders with them; **throw** for genuine failures so the error boundary handles them.

`<Form>` (capital F) intercepts submission and routes it to the action. Using `FormData` rather than controlled state means the form works with browser autofill and, in a server-rendering setup, without JavaScript at all ([[09.2 - Forms and Native Input Behavior]]).

**After an action, all loaders on the page automatically revalidate.** This is the piece that removes most cache-invalidation code — save a product and the list refetches without any explicit instruction.

## Pending states

```jsx
function RootLayout() {
  const navigation = useNavigation();

  return (
    <div className={navigation.state === "loading" ? "opacity-60" : ""}>
      <Outlet />
    </div>
  );
}
```

`navigation.state` is `"idle"`, `"loading"` or `"submitting"`. Because loaders run *before* the new route renders, the previous page stays on screen during the fetch — so the convention is dimming rather than a spinner, which reads as faster ([[22.4 - useTransition and startTransition]]).

`navigation.location` tells you where the user is heading, which enables optimistic highlighting of the target nav item.

## Deferred data

Waiting for everything means the page is as slow as the slowest request. `Promise` values returned from a loader stream in:

```jsx
{
  loader: async ({ params }) => {
    const product = await getProduct(params.id);      // fast — await it
    const reviews = getReviews(params.id);             // slow — don't await
    return { product, reviews };
  },
}
```

```jsx
function ProductDetail() {
  const { product, reviews } = useLoaderData();

  return (
    <>
      <h1>{product.name}</h1>
      <Suspense fallback={<ReviewsSkeleton />}>
        <Await resolve={reviews} errorElement={<ReviewsError />}>
          {(data) => <Reviews items={data} />}
        </Await>
      </Suspense>
    </>
  );
}
```

Critical data blocks the navigation; secondary data streams in. This is the same shape as Suspense-based streaming in a Server Components setup ([[22.8 - Server Components]]).

## fetcher — mutations without navigation

```jsx
function LikeButton({ postId, liked }) {
  const fetcher = useFetcher();
  const optimistic = fetcher.formData
    ? fetcher.formData.get("liked") === "true"
    : liked;

  return (
    <fetcher.Form method="post" action={`/posts/${postId}/like`}>
      <input type="hidden" name="liked" value={String(!optimistic)} />
      <button>{optimistic ? "Unlike" : "Like"}</button>
    </fetcher.Form>
  );
}
```

`useFetcher` calls a loader or action **without navigating** — for likes, deletes, inline edits, and any repeated action on a list.

Reading `fetcher.formData` gives the submitted values before the server responds, which is optimistic UI with no manual rollback logic: if the action fails, `formData` clears and the value reverts ([[24.5 - Optimistic UI]]).

Each fetcher is independent, so several rows can be in flight simultaneously without interfering.

## Loaders versus a query library

They solve overlapping problems differently:

| | Loaders | TanStack Query |
| --- | --- | --- |
| Fetches | before render, in parallel | on render |
| Caching | none by default | full cache with staleness |
| Revalidation | after every action | configurable |
| Background refetch | no | yes — focus, interval, reconnect |
| Works outside routes | no | yes |
| Loading state | previous page stays | per-query |

Loaders eliminate waterfalls and remove loading branches from components. Query libraries provide caching, deduplication and background updates ([[24.6 - TanStack Query Fundamentals]]).

The combination is common and effective:

```jsx
{
  loader: async ({ params }) => {
    await queryClient.ensureQueryData(productQuery(params.id));
    return null;
  },
  element: <ProductDetail />,
}

function ProductDetail() {
  const { id } = useParams();
  const { data } = useSuspenseQuery(productQuery(id));   // reads the warmed cache
}
```

The loader prefetches into the query cache before rendering; the component reads from it and gets caching, background refetch and invalidation as well. This pattern is the current best of both.

## Revalidation control

```jsx
function shouldRevalidate({ currentUrl, nextUrl, formMethod, defaultShouldRevalidate }) {
  if (currentUrl.pathname === nextUrl.pathname) return false;   // only search params changed
  return defaultShouldRevalidate;
}
```

By default every loader in the matched chain re-runs after an action and on most navigations. `shouldRevalidate` opts out where the data cannot have changed — worth adding for expensive loaders on routes with frequently-changing search params.

`useRevalidator()` triggers a manual revalidation, useful after a WebSocket event or a change made outside the router.

## How senior engineers actually use this

**They move fetching into loaders** to kill waterfalls, then layer a query cache on top for background updates.

**They defer secondary data** so the page is as fast as its critical request, not its slowest.

**They return validation errors and throw real failures**, keeping the two paths distinct.

**They use `fetcher` for list-level actions** rather than navigating for every like or delete.

**They rely on automatic revalidation after actions** instead of writing manual invalidation.

## Common pitfalls

- Awaiting slow secondary data and blocking the whole navigation.
- Throwing validation errors, so the form is replaced by an error page.
- Ignoring `request.signal`, leaving abandoned requests in flight.
- Using `<form>` instead of `<Form>`, causing a full page reload.
- No `errorElement`, so a loader failure blanks the app.
- Expensive loaders re-running on every search param change without `shouldRevalidate`.
- Mixing loaders and component-level fetching in the same route, reintroducing waterfalls.

## Interview angle

"How do you avoid data fetching waterfalls" is the question this answers. Explain that fetching in components means each nesting level discovers its data need only after rendering, so requests serialize; loaders declare data needs alongside the route, so the router starts all of them in parallel before rendering. Then the follow-ups: deferred data for streaming secondary content, automatic revalidation after actions, and the loader-plus-query-cache combination that gets both parallelism and caching.
