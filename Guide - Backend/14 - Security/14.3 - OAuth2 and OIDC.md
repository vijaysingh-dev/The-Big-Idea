# OAuth2 and OIDC

#backend #security #authentication

> **In one line:** OAuth 2.0 is a delegation protocol — it lets an application act on a user's behalf without knowing their password — and OIDC is the thin layer on top that also tells you who the user is.

---

## The Idea

⚠️ **The most common misconception: OAuth 2.0 is not an authentication protocol.** It grants *access*, not identity. An access token means "the bearer may call this API"; it says nothing about who they are.

💡 **OIDC (OpenID Connect) adds an ID token — a JWT with verified identity claims — and that is what "Sign in with Google" actually uses.**

```
OAuth 2.0  → authorisation. "This app may read your documents"
OIDC       → authentication. "This user is alice@example.com"
```

| Role | |
|---|---|
| **Resource owner** | The user |
| **Client** | Your application |
| **Authorization server** | Google, Okta, Auth0, your own |
| **Resource server** | The API holding the data |

---

## Authorization Code with PKCE

**The only flow you should use for user-facing authentication.**

```
1. Client generates:
     code_verifier   = random 43–128 chars
     code_challenge  = base64url(sha256(code_verifier))

2. Redirect the user:
   GET https://auth.example.com/authorize
       ?response_type=code
       &client_id=abc
       &redirect_uri=https://app.conduit.local/callback
       &scope=openid%20profile%20email
       &state=<random>
       &code_challenge=<challenge>
       &code_challenge_method=S256

3. User authenticates. Redirected back:
   https://app.conduit.local/callback?code=xyz&state=<same random>

4. Client exchanges the code (server-side, over TLS):
   POST /token
     grant_type=authorization_code
     code=xyz
     code_verifier=<the original verifier>
     client_id=abc
     client_secret=...           (confidential clients only)

5. Response: access_token, refresh_token, id_token
```

### Why PKCE exists

⚠️ **Without PKCE, an attacker who intercepts the authorization code — via a malicious app registering the same redirect scheme, or a leaked referrer — can exchange it for tokens.**

💡 **PKCE binds the code to the client that started the flow.** The attacker has the code but not the `code_verifier`, so the exchange fails.

⚠️ **PKCE is now required for all clients, including confidential ones.** It was originally a mobile-app fix; the current guidance is universal.

### `state` prevents CSRF

```python
state = secrets.token_urlsafe(32)
session["oauth_state"] = state
# on callback:
if not secrets.compare_digest(request.query_params["state"], session.pop("oauth_state")):
    raise HTTPException(400, "state mismatch")
```

⚠️ **Without `state`, an attacker can start a flow with their own account and trick the victim into completing it — linking the attacker's identity to the victim's session.** This is login CSRF, and it is exploitable.

### `nonce` prevents ID token replay

```python
nonce = secrets.token_urlsafe(32)
# ... included in the authorize request ...
if id_token_claims["nonce"] != expected_nonce:
    raise HTTPException(400)
```

**`state` protects the authorization request; `nonce` protects the ID token.** Both are needed.

## Flows You Should Not Use

| Flow | Verdict |
|---|---|
| **Implicit** | ⚠️ **Deprecated.** Tokens in the URL fragment — logged, in history, in referrers |
| **Resource Owner Password Credentials** | ⚠️ **Deprecated.** Your app handles the password, defeating the entire point |
| **Client Credentials** | ✅ Correct — for machine-to-machine, no user involved |
| **Device Code** | ✅ Correct — for TVs and CLIs with no browser |
| **Authorization Code + PKCE** | ✅ **The answer for everything user-facing** |

💡 **If you find a tutorial using the implicit flow, it predates 2019 and its other advice is probably also stale.**

## Validating an ID Token

```python
claims = jwt.decode(
    id_token,
    key=jwks.get_signing_key(header["kid"]).key,
    algorithms=["RS256"],
    audience=CLIENT_ID,
    issuer="https://accounts.google.com",
)

assert claims["nonce"] == expected_nonce
assert claims["exp"] > time.time()
if claims.get("azp") and claims["azp"] != CLIENT_ID:
    raise Unauthorized()
```

⚠️ **Every one of these checks has been the subject of a real vulnerability** ([[14.2 - Sessions Tokens and Rotation]]).

### The identifier trap

```python
user = await repo.get_by_email(claims["email"])      # ❌ dangerous
user = await repo.get_by_subject(claims["iss"], claims["sub"])   # ✅
```

⚠️ **Email is mutable and, at some providers, reusable.** A user changes their email, or an organisation deletes an account and later assigns the address to someone else — **and you have just handed over the original user's account.**

💡 **`(iss, sub)` is the stable identifier.** `sub` is unique within an issuer and never reassigned.

⚠️ **Check `email_verified` before trusting an email for anything**, including account linking. **An unverified email from an OIDC provider is a user-supplied string.**

### Account linking

```
Alice signs up with a password:              alice@example.com
Alice later signs in with Google:            alice@example.com
```

⚠️ **Automatically linking these on matching email is a documented account-takeover vector**: an attacker registers a password account with the victim's email at a provider that does not verify it, then the victim's real Google login links to it.

💡 **Link only when `email_verified` is true *and* the user has proved control of the existing account** — by being logged in, or by a confirmation email. **Never link silently.**

## Scopes and Consent

```
openid              required for OIDC
profile email       identity claims
documents:read      your own API's scope
documents:write
offline_access      request a refresh token
```

⚠️ **Request the minimum.** A consent screen asking for broad access reduces conversion and increases your blast radius if tokens leak.

💡 **Incremental authorisation is better than asking for everything up front** — request `documents:read` at signup and `documents:write` when the user first tries to edit.

**Scopes are coarse. They are not a substitute for authorisation** ([[14.1 - AuthN vs AuthZ]]) — a token with `documents:read` still must not read another organisation's documents.

## Being the Authorization Server

⚠️ **Do not build one unless it is your product.** The specification surface is large, the failure modes are subtle, and every mistake is a breach.

| Instead | |
|---|---|
| **Managed** | Auth0, Okta, Clerk, WorkOS, Cognito |
| **Self-hosted** | Keycloak, Ory Hydra, Authentik, Zitadel |

💡 **Ory Hydra is worth knowing about**: it implements only the OAuth2/OIDC protocol and delegates the login UI and user store to you. **That is often exactly the split you want** — you keep control of the user experience without implementing the protocol.

**If you do implement it**, the non-negotiables:

```
□  Exact redirect URI matching — no wildcards, no prefix matching
□  PKCE required for all clients
□  Authorization codes: single-use, ≤ 60 seconds
□  Refresh token rotation with reuse detection
□  state and nonce validated
□  Client secrets hashed at rest
□  A JWKS endpoint with key rotation via `kid`
```

⚠️ **Redirect URI matching is where authorization servers get breached.** Prefix matching means `https://app.example.com.attacker.com` matches `https://app.example.com`; open redirects on your own domain let an attacker bounce the code to themselves. **Exact match, full string, always.**

## In Production

### Enterprise SSO

⚠️ **Selling to enterprises means supporting SSO, and it is usually a hard requirement rather than a feature request.**

| Protocol | |
|---|---|
| **SAML 2.0** | XML, older, **still what most enterprises use** |
| **OIDC** | Modern, simpler, increasingly accepted |
| **SCIM** | User provisioning and deprovisioning |

💡 **SCIM matters more than people expect.** Without it, an employee removed from the corporate directory retains access to your product indefinitely — **which is precisely the risk the enterprise bought SSO to eliminate.**

⚠️ **SAML validation is genuinely difficult** — XML signature wrapping attacks, canonicalisation issues, and comment-injection bugs have all produced real authentication bypasses. **Use a maintained library and keep it updated.**

### Multi-tenant SSO

```python
domain = email.split("@")[1]
connection = await repo.get_sso_connection_by_domain(domain)
if connection:
    return redirect(connection.authorize_url)
return render_password_login()
```

💡 **Home-realm discovery by email domain is the standard pattern.** The user types their email and is routed to their organisation's identity provider.

⚠️ **Domain claims must be verified** — a DNS TXT record — or one customer can claim a domain they do not own and intercept another's logins.

### Token handling

```python
# Store provider tokens encrypted, and never expose them to the client
await repo.store_oauth_tokens(
    user_id=user.id,
    provider="google",
    access_token=encrypt(tokens["access_token"]),
    refresh_token=encrypt(tokens["refresh_token"]),
    expires_at=now + timedelta(seconds=tokens["expires_in"]),
)
```

⚠️ **A provider access token in your database is a credential to someone else's system.** Encrypt at rest, and **revoke on disconnect** — deleting the row leaves a live token.

💡 **After OIDC login, issue your own session** ([[14.2 - Sessions Tokens and Rotation]]). **Do not use the provider's tokens for your own API** — you would inherit their expiry, their revocation semantics, and an unnecessary dependency on their availability.

### Monitoring

```python
oauth_flow_started_total.labels(provider=...).inc()
oauth_flow_completed_total.labels(provider=..., result=...).inc()
oauth_state_mismatch_total.inc()              # ← attack signal
oauth_token_exchange_failures_total.labels(reason=...).inc()
sso_provisioning_total.labels(action="create"|"deactivate").inc()
```

⚠️ **`oauth_state_mismatch_total` should be near zero.** A sustained rate means either a broken client or someone attempting login CSRF.

**Alert when SSO deprovisioning stops** — a SCIM integration that silently fails leaves departed employees with access ([[12.3 - Instrumenting Conduit End to End]]).

### Conduit's approach

| Need | Choice |
|---|---|
| Consumer login | **OIDC** with Google and GitHub, via a managed provider |
| Enterprise | **SAML and OIDC SSO**, plus SCIM provisioning |
| Own API auth | **Own session after login** ([[14.2 - Sessions Tokens and Rotation]]) |
| Source connectors | **OAuth2 to Google Drive, Slack** — delegation, the actual use case |
| Machine-to-machine | Client credentials, or API keys |

💡 **The source connectors are the one place Conduit uses OAuth for its intended purpose** — acting on the user's behalf against a third-party API without knowing their password. **Everything else is OIDC used for authentication.**

⚠️ **Those connector tokens are long-lived credentials to a customer's Google Drive.** Encrypted at rest, scoped to the minimum, revoked on disconnect, and **never logged** ([[10.8 - Configuration and Secrets]]).

## Codebase

**Repo:** `ory/hydra`, `lepture/authlib`, `IdentityPython/pysaml2`

**Question to answer:** In an authorization server, what exactly is validated when a code is exchanged for tokens? Then: how does PKCE verification work in code, and what does it prevent?

**Read, in order:**

1. **RFC 6749 §4.1 and RFC 7636** — **the authorization code flow and PKCE.** Shorter than expected, and reading the primary source once is worth more than ten tutorials
2. `authlib/oauth2/rfc7636/challenge.py` — **PKCE verification.** A few dozen lines: hash the verifier, compare to the stored challenge. **The answer to the second question**
3. `ory/hydra/oauth2/` — the token exchange handler. **The answer to the first question**: client authentication, code validity, single use, redirect URI match, PKCE
4. `ory/fosite/handler/oauth2/flow_authorize_code_token.go` — the underlying library's flow implementation, with the security checks made explicit
5. `authlib/oidc/core/grants/code.py` — ID token generation and the `nonce` binding

💡 The PKCE implementation is startlingly small — **a SHA-256 and a comparison** — and reading it makes clear that the security comes from the *binding*, not from cryptographic complexity. **The verifier never travels over the front channel, so an attacker who intercepts the code cannot complete the exchange.**

**Size:** 1–2 sessions.

## Exercise

**Drill 14.3 — Implement the flow, then attack it**

⚠️ Everything runs against your own local stack.

```
drills/14-oauth/
├── client/{flow.py, pkce.py, state.py, validate_id_token.py}
├── server/{authorize.py, token.py, jwks.py, tests/}
├── attacks/{no_pkce.py, no_state.py, redirect_uri.py, id_token_forge.py, FINDINGS.md}
├── linking/{account_takeover.py, safe_linking.py, RESULTS.md}
├── sso/{saml.py, oidc.py, scim.py, discovery.py}
└── README.md
```

**Part 1 — A complete client.** Authorization code with PKCE, `state`, `nonce`, and full ID token validation.

**Then a minimal authorization server** so you control both sides — issuing codes, exchanging tokens, and serving JWKS.

**Part 2 — Four attacks.** Against deliberately weakened versions:

| Attack | Weakness |
|---|---|
| **Code interception** | No PKCE — steal the code, exchange it |
| **Login CSRF** | No `state` — link the attacker's identity to the victim's session |
| **Redirect URI bypass** | Prefix matching — send the code to `app.example.com.attacker.com` |
| **ID token forgery** | Missing `alg` pinning or audience check |

**Demonstrate each succeeding.** Then fix and confirm each fails.

💡 **The redirect URI one is worth extra attention** — try prefix matching, wildcard subdomains, and an open redirect on the legitimate domain. **All three are real bypasses.**

**Part 3 — Code replay.** Exchange the same authorization code twice.

**Confirm it succeeds against a naive server.** Then enforce single use and a 60-second lifetime, and confirm the second exchange fails.

**Then check what a real provider does** — most also revoke all tokens issued from a replayed code.

**Part 4 — Account linking takeover.** Implement automatic linking by email.

**Then execute the attack:** register a password account with the victim's email at a provider that does not verify it, then have the victim sign in with their real provider and **confirm you have taken over their account.**

Then implement safe linking — `email_verified` plus proof of control — and confirm the attack fails.

**Part 5 — Stable identifiers.** Implement lookup by email, then by `(iss, sub)`.

**Simulate a user changing their email at the provider.** Confirm the email-based version creates a duplicate account or, worse, matches the wrong user.

**Part 6 — Enterprise SSO.** SAML and OIDC connections plus home-realm discovery by email domain.

**Then implement domain verification via a DNS TXT record**, and confirm an unverified domain cannot be claimed.

Then SCIM provisioning: **create a user, deactivate them in the directory, and confirm their access is revoked in your application.**

**Measure the propagation delay.**

**Part 7 — Provider token handling.** A Google Drive connector storing OAuth tokens.

Encrypt at rest. **Then confirm that disconnecting revokes the token at the provider**, not just deletes your row — **check by attempting to use it afterwards.**

Then handle token expiry and refresh transparently, and **confirm a revoked-at-provider token produces a clear reconnection prompt rather than a 500.**

**Part 8 — Monitoring.** Instrument the five metrics.

**Then run your own attacks again and confirm each produces a signal** — `state` mismatch, redirect URI rejection, code replay.

**Done when:**
- All four attacks succeed against weakened versions and fail against yours
- Three distinct redirect URI bypasses are attempted and blocked
- Code replay fails, with a single-use and short-lifetime enforcement
- The account linking takeover succeeds and is then prevented
- Email-based lookup breaks on an email change; `(iss, sub)` does not
- Domain verification prevents an unverified SSO domain claim
- SCIM deactivation revokes access, with a measured delay
- Disconnecting a connector revokes the token at the provider, verified
