# Hoisting and the Temporal Dead Zone

**Hoisting** is the name for a consequence, not a mechanism. Nothing is physically moved. During the creation phase of an execution context, the engine registers every declaration in the scope before executing a single line ([[01.2 - Execution Context and Scope Chain]]). What differs between declaration types is the *state* each binding is registered in.

## What each declaration is initialized to

| Declaration | Registered | Initial state |
| --- | --- | --- |
| `function` | yes | fully assigned |
| `var` | yes | `undefined` |
| `let` / `const` | yes | uninitialized (TDZ) |
| `class` | yes | uninitialized (TDZ) |
| `import` | yes | fully bound before execution |

```js
console.log(fn());   // "works"
console.log(v);      // undefined
console.log(l);      // ReferenceError: Cannot access 'l' before initialization
console.log(undeclared); // ReferenceError: undeclared is not defined

function fn() { return "works"; }
var v = 1;
let l = 2;
```

Note the two different `ReferenceError` messages. "Cannot access before initialization" means the binding exists but is in the TDZ. "is not defined" means no binding exists anywhere in the chain. Reading that distinction correctly saves real debugging time.

## The temporal dead zone

The TDZ is the span between entering a scope and the point where the declaration executes. During it, the binding exists but touching it throws.

```js
{
  // TDZ for x starts here
  typeof x;   // ReferenceError — even typeof throws
  let x = 1;  // TDZ ends
  typeof x;   // "number"
}
```

`typeof` on an undeclared identifier returns `"undefined"` safely; on a TDZ binding it throws. That is deliberate — the TDZ is designed to make use-before-declaration a hard error rather than a silent `undefined`.

The zone is **temporal**, not positional. It is about when code runs, not where it appears:

```js
function later() { return value; }  // fine to define
const value = 1;
later();                            // fine to call — TDZ already over
```

Compare with:

```js
function early() { return value; }
early();                            // ReferenceError
const value = 1;
```

Same source positions, different execution order, different outcome.

## Why the TDZ exists

Two reasons.

**`const` needs it.** A `const` initialized to `undefined` and later assigned would be a `const` that changed value. The only coherent option is to make it inaccessible until assignment.

**Use-before-declaration is almost always a bug.** `var` turned it into a silent `undefined` that surfaced as a mysterious `TypeError` three functions away. The TDZ turns it into an immediate, precise error at the point of misuse.

## Function declaration hoisting

Function declarations are the only thing fully available before their line:

```js
greet();  // "hi"
function greet() { console.log("hi"); }
```

Function *expressions* are not — they follow their binding's rules:

```js
greet();  // TypeError: greet is not a function
var greet = function () {};

greet();  // ReferenceError
const greet2 = function () {};
```

`var greet` is `undefined` at that point, and calling `undefined` is a `TypeError`. Distinguishing these two error types is a common interview probe.

Duplicate function declarations silently overwrite each other, last one winning:

```js
function f() { return 1; }
function f() { return 2; }
f(); // 2
```

## Blocks and functions

```js
"use strict";
{
  function inner() {}
}
inner(); // ReferenceError in strict mode
```

In strict mode and modules, function declarations are block-scoped. In sloppy mode, legacy web-compatibility rules partially leak them to function scope in inconsistent ways. Never rely on it; use a `const` function expression if you need a conditional function.

## Class hoisting

```js
new Dog();          // ReferenceError
class Dog {}

class A extends B {} // ReferenceError if B is declared later
class B {}
```

Classes are hoisted into the TDZ, so they behave like `let`. The `extends` clause is evaluated when the class declaration executes, so the parent must already be initialized.

## Imports are different

```js
console.log(config);  // works
import { config } from "./config.js";
```

ES module imports are resolved and bound before any module code runs, so they are available throughout the module regardless of statement order. This is why `import` statements are conventionally at the top — it is a readability convention, not a requirement ([[08.1 - ES Modules vs CommonJS]]).

Circular imports break this: a binding may be in the TDZ if the other module has not finished evaluating yet, producing "cannot access before initialization" at module load.

## How senior engineers actually use this

**They declare where they use.** The TDZ becomes a non-issue if variables are declared immediately before first use, which is also better for readability and lets the engine free memory earlier.

**They read the error message carefully.** "Cannot access before initialization" in production almost always means a circular import or a module evaluation-order problem, not a simple typo.

**They avoid conditional function declarations.** `if (x) { function f() {} }` behaves differently across modes. A `const f = ...` assignment is unambiguous.

**They keep `no-use-before-define` on for variables.** It catches TDZ errors at lint time rather than at runtime, and the function exception is usually enabled so mutually recursive helpers still work.

## Common pitfalls

- Expecting `typeof` to be safe on a TDZ binding.
- Assuming hoisting physically moves code to the top.
- Confusing the `TypeError` from calling an `undefined` `var` with the `ReferenceError` from a TDZ access.
- Circular imports producing TDZ errors that look unrelated to imports.
- Relying on a function declared inside a block being visible outside it.

## Interview angle

Expect "what is hoisting", "what is the TDZ and why does it exist", and a snippet contrasting `var`, `let` and `function`. The strong framing is that all declarations are registered before execution, and the only difference is initial state — assigned for functions, `undefined` for `var`, uninitialized for `let`/`const`/`class`. Then justify the TDZ: `const` cannot start as `undefined`, and turning use-before-declaration into a loud error is better than a silent one.
