# Indexes Deep Dive

#backend #databases #postgres #performance

> **In one line:** An index is a sorted copy of some columns that lets the database skip reading most rows — and knowing exactly which queries a given index can serve, and which it cannot, is the highest-leverage database skill there is.

---

## The Idea

💡 **The mental model that makes indexes intuitive: an index is a sorted list of `(indexed columns, row location)`.** Everything an index can and cannot do follows from that. It can find a value, find a range, and return rows already sorted. **It cannot help with anything that is not a prefix of that sort order.**

---

## B-tree Indexes

### What a single-column index serves

```sql
CREATE INDEX idx_status ON documents (status);
```

| Query | Uses it? |
|---|---|
| `WHERE status = 'failed'` | Yes |
| `WHERE status IN (...)` | Yes |
| `WHERE status > 'a'` | Yes — B-trees are ordered |
| `ORDER BY status` | Yes, without a sort |
| **`WHERE lower(status) = 'failed'`** | **No** — the function breaks it |
| **`WHERE status LIKE '%ailed'`** | **No** — leading wildcard |
| `WHERE status LIKE 'fail%'` | Yes — anchored prefix |

⚠️ **Any function applied to the column defeats the index**, unless you create an expression index:

```sql
CREATE INDEX ON documents (lower(title));
```

**This catches people constantly with `date(created_at)`, `lower(email)` and `cast(id AS text)`.**

### Multi-column indexes and the left-prefix rule

```sql
CREATE INDEX idx_multi ON documents (org_id, status, created_at);
```

| Query | Uses it? |
|---|---|
| `WHERE org_id = 7` | **Yes** |
| `WHERE org_id = 7 AND status = 'x'` | **Yes** |
| `WHERE org_id = 7 AND status = 'x' AND created_at > ...` | **Yes, fully** |
| **`WHERE status = 'x'`** | **No** — skips the first column |
| `WHERE org_id = 7 AND created_at > ...` | **Partially** — uses `org_id`, then filters |
| `WHERE org_id > 5 AND status = 'x'` | **Partially** — a range on the first column stops the rest |

💡 **The rule: equality conditions can chain; the first range condition ends useful index traversal.** Everything after it becomes a filter.

**So column order is: equality columns first, then the range column, then columns used only for ordering.**

```sql
-- For: WHERE org_id = ? AND status = ? AND created_at > ? ORDER BY created_at DESC
CREATE INDEX ON documents (org_id, status, created_at DESC);
```

⚠️ **This single rule explains most "why isn't my index being used" questions.** Getting column order right often turns a 2-second query into a 2-millisecond one with no other change.

### Sort order matters for multi-column ORDER BY

```sql
CREATE INDEX ON documents (org_id, created_at DESC);
-- serves: ORDER BY org_id, created_at DESC
-- and:    ORDER BY org_id DESC, created_at ASC   (full reverse scan)
-- NOT:    ORDER BY org_id, created_at ASC        (mixed — needs a sort)
```

**This is exactly the keyset pagination requirement from [[05.2 - Versioning Pagination and Filtering]].** Your pagination index must match your `ORDER BY` exactly, including directions.

## Covering and Index-Only Scans

```sql
CREATE INDEX ON documents (org_id) INCLUDE (id, title);
```

```
Index Only Scan using idx_org_include on documents
  Heap Fetches: 0
```

💡 **`INCLUDE` adds columns to the leaf pages without making them part of the sort key**, keeping the index smaller than putting them in the key while still enabling index-only scans.

⚠️ **`Heap Fetches: 48291` means it is not actually index-only.** Postgres must check the visibility map to know a row is visible; if the page is not marked all-visible, it reads the heap anyway.

**The fix is vacuum** — an unvacuumed table degrades index-only scans into regular ones ([[06.7 - MVCC Vacuum and Bloat]]).

## Partial Indexes

```sql
CREATE INDEX ON documents (created_at) WHERE status = 'failed';
CREATE INDEX ON documents (org_id, created_at) WHERE deleted_at IS NULL;
CREATE INDEX ON jobs (created_at) WHERE status IN ('pending', 'running');
```

If 0.1% of documents are failed, this index is 1,000× smaller — **it fits in memory, is faster to scan, and is cheaper to maintain on write.**

⚠️ **The query's `WHERE` clause must imply the index predicate.** `WHERE status = 'failed'` matches; `WHERE status = ANY($1)` with a runtime parameter may not, because the planner cannot prove it.

💡 **Partial indexes are the most underused index feature in Postgres.** A queue table where 99.9% of rows are completed and you only query pending ones should have one — **the difference is often two orders of magnitude in index size.**

## The Other Index Types

| Type | For |
|---|---|
| **B-tree** | Equality, ranges, sorting. The default |
| **GIN** | Multiple values per row — JSONB, arrays, full-text |
| **GiST** | Geometric, ranges, nearest-neighbour |
| **BRIN** | Huge, naturally-ordered tables |
| Hash | Equality only — rarely worth it |

### GIN

```sql
CREATE INDEX ON documents USING gin (tags);
CREATE INDEX ON documents USING gin (metadata jsonb_path_ops);   -- smaller, containment only
```

⚠️ **GIN indexes are expensive to update.** Postgres mitigates with a pending list (`fastupdate`), which batches updates — but that means reads may scan the pending list, giving unpredictable read latency.

```sql
ALTER INDEX idx_gin SET (fastupdate = off);   -- slower writes, predictable reads
```

**For a write-heavy table with a GIN index, this is a real tuning decision.**

### BRIN

```sql
CREATE INDEX ON events USING brin (created_at);
```

Stores only min/max per block range. **Tiny** — kilobytes where a B-tree would be gigabytes.

💡 **BRIN only works when physical row order correlates with the indexed value** — true for append-only time-series, false for almost everything else.

```sql
SELECT correlation FROM pg_stats WHERE tablename='events' AND attname='created_at';
-- close to 1.0 → BRIN works well. Near 0 → useless
```

⚠️ **Check that correlation before creating one.** If updates or deletes scatter rows, correlation drops and the index becomes worthless **without any error.**

## The Cost of Indexes

```
INSERT with 0 indexes:   1 heap write
INSERT with 8 indexes:   1 heap write + 8 index writes
```

⚠️ **In Postgres, an `UPDATE` writes a new row version and updates *every* index**, unless HOT-eligible ([[06.1 - Storage Engines]]).

```sql
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelid NOT IN (
    SELECT conindid FROM pg_constraint WHERE contype IN ('p','u'))
ORDER BY pg_relation_size(indexrelid) DESC;
```

💡 **Run this on any production database and you will find unused indexes.** They cost write throughput, disk, buffer pool memory and vacuum time — for nothing. **Dropping them is one of the easiest wins available.**

⚠️ **Check `idx_scan` across a full business cycle** — an index used only by a monthly report shows zero in a week.

### Redundant indexes

```sql
CREATE INDEX ON documents (org_id);                  -- redundant
CREATE INDEX ON documents (org_id, status);          -- this covers it
```

```sql
SELECT indrelid::regclass, array_agg(indexrelid::regclass)
FROM pg_index GROUP BY indrelid, indkey HAVING count(*) > 1;
```

## In Production

### Creating indexes without downtime

```sql
CREATE INDEX CONCURRENTLY idx_name ON documents (org_id, created_at);
```

⚠️ **A plain `CREATE INDEX` blocks all writes for the duration** — potentially hours on a large table. **Always use `CONCURRENTLY` in production.**

The costs: roughly twice as long, and it can **fail and leave an invalid index**.

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_broken;
```

**Always check for invalid indexes after a concurrent build.** An invalid index is not used by queries but is still maintained on writes — the worst of both worlds.

### Finding the missing index

```sql
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / nullif(seq_scan, 0) AS avg_rows_per_scan
FROM pg_stat_user_tables WHERE seq_scan > 0
ORDER BY seq_tup_read DESC LIMIT 20;
```

⚠️ **Sequential scans are not automatically bad.** For a small table, or a query returning 40% of rows, a sequential scan is genuinely faster than 400,000 random heap fetches. **The planner is usually right** ([[06.5 - The Query Planner]]).

### Index bloat

```sql
SELECT * FROM pgstatindex('documents_org_id_idx');   -- avg_leaf_density
REINDEX INDEX CONCURRENTLY documents_org_id_idx;      -- Postgres 12+
```

💡 **Bloated indexes are slower purely because they are larger** — more pages to read, less fits in the buffer pool. **Random-key indexes bloat much faster**, which is another argument for ULID over UUIDv4.

### The workflow for adding an index

```
1. Find the slow query           (pg_stat_statements, by total_exec_time)
2. EXPLAIN (ANALYZE, BUFFERS)
3. Design the index              (equality cols, then range, then sort)
4. Test on a copy with real data
5. Verify the plan changes       (hypopg tests without building)
6. CREATE INDEX CONCURRENTLY
7. Check indisvalid
8. Measure the improvement
9. Check nothing else regressed
```

```sql
CREATE EXTENSION hypopg;
SELECT hypopg_create_index('CREATE INDEX ON documents (org_id, created_at)');
EXPLAIN SELECT ...;    -- shows the hypothetical index being used
```

💡 **`hypopg` is genuinely useful and little-known.** On a large table, building an index to test it takes an hour; `hypopg` tells you in a second whether the planner would even use it.

## Codebase

**Repo:** `postgres/postgres`, `HypoPG/hypopg`

**Question to answer:** How does Postgres decide whether a multi-column index can satisfy a query — where does the left-prefix rule live in the code? Then: when an Index Only Scan needs a heap fetch, where is the visibility map consulted?

**Read, in order:**

1. `src/backend/access/nbtree/README` — the B-tree structure. **The sections on multi-column keys and `INCLUDE` columns answer the first question conceptually**
2. `src/backend/optimizer/path/indxpath.c` — **`match_clause_to_indexcol` and `build_index_paths`.** This is the left-prefix rule in code: which clauses push into the index scan versus become filters
3. `src/backend/access/nbtree/nbtsearch.c` — `_bt_first`, building the scan start position from matched clauses
4. `src/backend/executor/nodeIndexonlyscan.c` — **`VM_ALL_VISIBLE`.** The visibility map check and the source of `Heap Fetches`
5. `src/backend/access/gin/README` — how GIN handles multiple keys per row, and the pending list `fastupdate` controls
6. `hypopg/hypopg_index.c` — how a fake index is injected into the planner. Small and clever

💡 Reading `indxpath.c` converts the left-prefix rule from a memorised guideline into something you can reason about. **You can see exactly why an equality clause allows the next column to be used and a range clause does not** — the scan can only start at a single point in the sorted order, and a range destroys that.

**Size:** 2 sessions.

## Exercise

**Drill 6.3 — Index detective**

The single highest-value drill in section 06.

```
drills/06-indexes/
├── data/seed.py                  # 10M rows, varied cardinality
├── prediction/{queries.sql, PREDICTIONS.md, ACTUAL.md}
├── ordering/{column_order.sql, RESULTS.md}
├── types/{gin_vs_btree.sql, brin.sql, partial.sql, RESULTS.md}
├── cost/{write_amp.py, unused.sql, FINDINGS.md}
├── operations/{concurrent_build.sh, invalid_index.sh, bloat.sql}
└── README.md
```

**Part 1 — Predict, then check.** 10 million rows with realistic cardinality: `org_id` (1,000 values), `status` (5 values, heavily skewed), `created_at` (2 years), `title` (unique).

Write 20 queries covering: single equality, multi-column equality, range, mixed equality+range, `ORDER BY` with and without `LIMIT`, `LIKE` anchored and unanchored, function-wrapped columns, `IN` lists, `OR`, joins, aggregates, `COUNT(*)`.

**For each, write your predicted plan in `PREDICTIONS.md` before running it.** Then run `EXPLAIN (ANALYZE, BUFFERS)`.

**Target: 16 out of 20 correct. Every miss is a genuine gap in your model, and investigating it is where the learning is.**

**Part 2 — Column order, measured.** For `WHERE org_id = ? AND status = ? AND created_at > ? ORDER BY created_at DESC`, build all six orderings.

Measure index size, query time and buffers for each. **The best-to-worst difference should be large.**

Then find a *different* query where a different ordering wins, **to show there is no universally correct answer.**

**Part 3 — Index types head to head.** For a JSONB containment query: GIN default ops, GIN `jsonb_path_ops`, and a B-tree on an extracted expression.

Measure index size, build time, query time, and **insert throughput impact.**

Then BRIN on `created_at`: measure with rows physically ordered by time, then shuffle 10% and measure again. **Report the correlation value and performance in both cases.**

**Part 4 — Partial indexes.** A `jobs` table where 99% of rows are `completed`.

Full index versus partial. Compare size, query time, and insert throughput. **Then find a query the partial index does not serve** and show the planner falling back to a sequential scan.

**Part 5 — The write cost.** Insert and update throughput with 0, 2, 4, 8 and 16 indexes. Chart it, plus WAL bytes per operation.

Then repeat where the updated column is not indexed and `fillfactor = 85`, showing HOT updates avoiding the cost.

**Part 6 — Find the waste.** After running a realistic workload: find unused indexes, redundant left-prefix duplicates, and bloated indexes.

**Drop the unused ones and re-measure write throughput. Report the gain.**

**Part 7 — Operations.** Build an index `CONCURRENTLY` on a 10M-row table under continuous write load. Measure build time, write throughput impact, and confirm no writes were blocked.

Then deliberately cause a concurrent build to fail, find the invalid index, and clean it up.

Then create bloat, measure `avg_leaf_density`, and fix with `REINDEX CONCURRENTLY`.

**Done when:**
- You predicted at least 16 of 20 plans correctly, and investigated every miss
- Your column-ordering results show a large spread and a case where the winner changes
- You have the correlation threshold below which BRIN stops working
- The partial index shows a large size reduction and you know its limits
- Your index-count-versus-write-throughput chart is complete
- You dropped unused indexes and measured the write improvement
- You caused, detected and cleaned up an invalid index
