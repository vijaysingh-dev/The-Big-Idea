# Einstein for Service and Agentforce

## Why service is where AI landed first

Support is the highest-volume, most repetitive, most text-heavy part of the CRM. That combination is exactly what language models are good at, which is why the generative features arrived in Service Cloud before anywhere else.

The framing to keep: these features are **grounded in your org's data** — case history, knowledge articles, product records. Their quality is bounded by that data. An org with a thin knowledge base and inconsistent case reasons gets confidently wrong output, at scale, in front of customers.

## The predictive features

**Einstein Case Classification.** Predicts field values on incoming cases — Type, Reason, Priority, Product — from the subject and description. Either presented to the agent as a suggestion or applied automatically.

Trained on the org's own closed cases. Which means it inherits the org's data quality: if `Reason` was filled in carelessly for two years, the model learns careless classification.

**Einstein Case Routing.** Uses the predicted classification to route, so a case is in the right queue before a human reads it. Combined with Omni-Channel this removes the triage step entirely for well-classified cases.

**Einstein Article Recommendations.** Surfaces knowledge articles relevant to the case, ranked by which articles historically resolved similar cases. Better than keyword search because it learns from outcomes rather than matching text.

**Einstein Reply Recommendations.** Suggests responses in chat and messaging, learned from past agent replies. Effective in high-volume chat, less so where every case is different.

**Einstein Case Wrap-Up.** Generates a summary of the case at closure.

## The generative features

**Service Replies.** Drafts a reply grounded in the case, the customer's history, and knowledge articles. The agent reviews and edits before sending.

**Work Summaries.** Generates a case or conversation summary — what happened, what was done, what remains. This is the one agents value most, because wrap-up is the least rewarding part of the job and the first thing skipped under pressure.

**Knowledge article generation** from resolved cases, which addresses the perpetual problem that nobody writes articles.

**Search Answers.** Generates a direct answer from knowledge rather than returning a list of articles.

Every one of these depends on knowledge quality, which is the point made in [[05.10 - Salesforce Knowledge]] and worth repeating: **invest in the knowledge base before investing in generative service features.**

## Agentforce

The step beyond drafting text: an agent that reasons about a request and **takes actions**.

The structure:

**Topics** — areas the agent handles: order status, warranty claims, appointment scheduling.
**Actions** — what it can do within a topic. An action can be a flow, an Apex invocable method, a prompt template, or a standard action.
**Instructions** — natural language guidance about when to use which action and how to behave.

The difference from Einstein Bots ([[05.11 - Live Chat and Digital Engagement]]) is structural. A bot follows a dialog tree someone designed. An agent is given a set of capabilities and decides which to use.

An Apex action for an Agentforce agent:

```java
public with sharing class WarrantyClaimAgentActions {

    public class ClaimStatusRequest {
        @InvocableVariable(required=true label='Claim Number')
        public String claimNumber;
        @InvocableVariable(required=true label='Contact Email')
        public String contactEmail;
    }

    public class ClaimStatusResponse {
        @InvocableVariable public String status;
        @InvocableVariable public String submittedDate;
        @InvocableVariable public String nextStep;
        @InvocableVariable public Boolean found;
    }

    @InvocableMethod(
        label='Get Warranty Claim Status'
        description='Returns the current status of a warranty claim for a verified customer'
    )
    public static List<ClaimStatusResponse> getClaimStatus(List<ClaimStatusRequest> requests) {
        List<ClaimStatusResponse> responses = new List<ClaimStatusResponse>();

        Set<String> claimNumbers = new Set<String>();
        Set<String> emails = new Set<String>();
        for (ClaimStatusRequest req : requests) {
            claimNumbers.add(req.claimNumber);
            emails.add(req.contactEmail);
        }

        // verify the requester actually belongs to the account on the claim
        Map<String, Warranty_Claim__c> claimsByNumber = new Map<String, Warranty_Claim__c>();
        for (Warranty_Claim__c claim : [
            SELECT Claim_Number__c, Status__c, Claim_Date__c, Next_Step__c, Account__c
            FROM Warranty_Claim__c
            WHERE Claim_Number__c IN :claimNumbers
        ]) {
            claimsByNumber.put(claim.Claim_Number__c, claim);
        }

        Map<String, Id> accountByEmail = new Map<String, Id>();
        for (Contact con : [SELECT Email, AccountId FROM Contact WHERE Email IN :emails]) {
            accountByEmail.put(con.Email.toLowerCase(), con.AccountId);
        }

        for (ClaimStatusRequest req : requests) {
            ClaimStatusResponse response = new ClaimStatusResponse();
            Warranty_Claim__c claim = claimsByNumber.get(req.claimNumber);
            Id requesterAccount = accountByEmail.get(req.contactEmail.toLowerCase());

            response.found = claim != null
                && requesterAccount != null
                && claim.Account__c == requesterAccount;

            if (response.found) {
                response.status = claim.Status__c;
                response.submittedDate = String.valueOf(claim.Claim_Date__c);
                response.nextStep = claim.Next_Step__c;
            }
            responses.add(response);
        }
        return responses;
    }
}
```

Three things in that are non-negotiable for agent actions.

**Ownership verification.** The agent will pass whatever the customer said. A customer who guesses a claim number must not get someone else's data. The action verifies the requester's account matches the claim's account, and returns `found = false` otherwise rather than an error that leaks existence.

**Bulk-safe with matched ordering.** Input and output lists must correspond by index. Returning a different length or order gives the wrong customer's answer.

**Description fields written for the model.** The `label` and `description` are how the agent decides when to use this action. Vague descriptions produce an agent that calls the wrong action.

## The Trust Layer

The **Einstein Trust Layer** sits between the platform and the model provider, and it is usually what makes a generative feature approvable by an internal security review:

- **Data masking** removes personally identifiable information before the prompt leaves
- **Zero retention** means the provider does not store or train on your data
- **Grounding** injects real record data so responses are based on facts rather than generated
- **Toxicity detection** on output
- **Audit trail** of prompts and responses

Knowing this exists, and being able to explain it, is frequently the difference between a feature shipping and stalling in review. See [[24.5 - Einstein Trust Layer]].

## Where this goes wrong

**Deploying on a weak knowledge base.** The single most common failure. Generative replies grounded in stale or thin articles produce plausible, confident, wrong answers, sent to customers at volume.

**No human review on customer-facing output.** Drafting for agent review is low risk. Sending autonomously is a different risk profile and needs a much higher confidence bar.

**Actions without authorization checks.** An agent action that looks up a record by a number the customer supplied, with no ownership verification, is a data exposure.

**Measuring containment without measuring satisfaction.** A bot resolving eighty percent of conversations looks excellent until you find customers gave up rather than got helped. Containment and CSAT must be read together.

**Assuming the model knows your business.** It knows what it is grounded in. Product-specific behaviour, contractual terms, and internal process must be in knowledge articles or in the action's data, or the model will invent something reasonable-sounding.

## Practical guidance

**Fix the knowledge base first.** Everything generative reads from it.

**Fix case classification data first** for the predictive features. Models learn your carelessness.

**Start with agent-assist, not customer-facing.** Draft for review, summarize for the agent, recommend articles. Low risk, immediate value, and it builds the evidence for going further.

**Verify authorization in every action.** Treat agent actions as public endpoints, because effectively they are.

**Measure containment alongside satisfaction.**

**Write action descriptions for the model.** They are the interface, and vague ones produce wrong tool selection.
