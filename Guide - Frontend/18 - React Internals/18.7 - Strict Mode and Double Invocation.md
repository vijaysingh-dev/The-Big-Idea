# Strict Mode and Double Invocation

```jsx
import { StrictMode } from "react";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

Strict Mode is a **development-only** wrapper that runs additional checks. It renders nothing, has no production effect, and adds no bundle weight in production builds.

## What it double-invokes

In development, Strict Mode calls these **twice**:

- Component function bodies
- `useState`, `useMemo`, `useReducer` initializer functions
- State updater functions
- Class `constructor`, `render`, `shouldComponentUpdate`

And it runs this sequence for every component on mount:

```
mount → effects run → cleanup runs → effects run again
```

Refs are also detached and reattached.

React deduplicates `console.log` output from the second render in newer versions, so the doubling is less visually noisy than it once was — but the calls still happen.

## Why: purity detection

The render phase must be pure, because React may discard, restart or repeat a render ([[18.4 - Render Phase vs Commit Phase]]). Double-invoking makes impurity visible immediately rather than as a rare production bug.

```jsx
let id = 0;
function Item() {
  const myId = id++;        // impure — increments twice
  return <li>{myId}</li>;   // 1, 3, 5 instead of 0, 1, 2
}
```

```jsx
function Cart({ items }) {
  items.push(newItem);      // mutates a prop — duplicates appear
  return <List items={items} />;
}
```

Both bugs already existed. Strict Mode only surfaces them.

## Why: re-runnable effects

The mount-unmount-remount cycle verifies that every effect can be safely torn down and set up again.

```jsx
// Broken — no cleanup, so two connections
useEffect(() => {
  connection.connect();
}, []);

// Correct
useEffect(() => {
  const conn = createConnection();
  conn.connect();
  return () => conn.disconnect();
}, []);
```

The second version handles the double-run correctly: connect, disconnect, connect — ending in one connection.

This matters beyond development. React needs to be able to unmount and restore a tree while preserving state — for future features like `<Activity>` (offscreen tab content), and for fast refresh during development. An effect that cannot survive a re-run breaks in those situations.

## The common false alarms

**Two network requests in development.** With proper cleanup this is harmless — the first is aborted:

```jsx
useEffect(() => {
  const controller = new AbortController();
  fetch(url, { signal: controller.signal }).then(...);
  return () => controller.abort();
}, [url]);
```

If the request is not idempotent — a POST that creates a record — it should not be in an effect at all. It belongs in an event handler ([[17.4 - useEffect Pitfalls]]).

**Duplicate analytics events.** Same reasoning: view-tracking in an effect will fire twice in development. Either accept it (development traffic should not be in production analytics) or move it to a handler if it corresponds to a user action.

**Third-party libraries initializing twice.** Chart, map and editor libraries that allocate DOM need `destroy()` in cleanup:

```jsx
useEffect(() => {
  const chart = new Chart(ref.current, config);
  return () => chart.destroy();
}, [config]);
```

This was always necessary to avoid leaks ([[07.3 - Memory Leaks from Listeners and Detached DOM]]); Strict Mode just makes forgetting it obvious.

## What not to do

```jsx
// Anti-pattern
const hasRun = useRef(false);
useEffect(() => {
  if (hasRun.current) return;
  hasRun.current = true;
  doSetup();
}, []);
```

This defeats the check without fixing the effect. The effect is still not re-runnable, so it will break whenever React genuinely remounts the component — on a fast refresh, on a `key` change, or in a future release with offscreen rendering.

Equally, removing `<StrictMode>` because it is "noisy" removes the only mechanism that catches these bugs before production.

The two legitimate escapes:

**Module scope for genuine one-time initialization:**

```jsx
// analytics.js
initializeSDK();   // runs once per import, not per component
```

**An external cache or store**, so the effect is idempotent regardless of how often it runs — which is what data libraries do.

## Other checks

Strict Mode also warns about:

- Deprecated string refs and legacy context
- `findDOMNode` usage
- Unexpected side effects in the render phase
- Deprecated lifecycle methods (`componentWillMount` and friends)

These are largely legacy concerns in a modern codebase.

## Production behavior

Nothing in Strict Mode runs in production. No double invocation, no extra mount cycle, no warnings, no performance cost.

This means Strict Mode cannot mask a production bug — but it also means anything it catches in development is a real defect that would have shipped silently.

## Frameworks enable it by default

Next.js, Vite's React template and Create React App all wrap the app in Strict Mode by default. Encountering double effects is therefore the default experience, and understanding why is essential rather than optional.

## How senior engineers actually use this

**They keep Strict Mode on in development, always.** It is the cheapest available correctness check.

**They read a double-invocation symptom as a bug report**, not as noise — the first question is "what is impure or not cleanable here".

**They put one-time initialization at module scope**, not in an effect.

**They pair every effect with cleanup as a habit**, which makes Strict Mode a non-event.

**They use a data library for fetching**, which handles deduplication and cancellation so the double-run is invisible.

## Common pitfalls

- Ref guards added to suppress double effects.
- Removing `<StrictMode>` instead of fixing the underlying issue.
- Non-idempotent operations (POST, payment, analytics conversion) in effects.
- Third-party library instances created without a `destroy()` in cleanup.
- Impure render logic — counters, mutations, pushing to module-level arrays.
- Assuming double-rendering will happen in production, and writing defensive code for it.

## Interview angle

"Why does Strict Mode run effects twice in development" is a common React 18+ question. The answer: to verify effects are re-runnable and components are pure, because the architecture relies on both — renders can be discarded and repeated, and React needs to be able to unmount and restore trees. Then the important follow-up: the correct fix is proper cleanup or moving the work out of the effect, never a ref guard, because the guard hides a defect that will surface elsewhere.
