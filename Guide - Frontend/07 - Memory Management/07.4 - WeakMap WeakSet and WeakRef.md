# WeakMap, WeakSet and WeakRef

Collections whose references do not prevent garbage collection. They exist for one purpose: associating data with an object without controlling that object's lifetime.

## The problem they solve

```js
const metadata = new Map();

function track(element) {
  metadata.set(element, { clicks: 0, mountedAt: Date.now() });
}
```

The `Map` holds a strong reference to every element. Even after those elements are removed from the DOM and forgotten everywhere else, the `Map` keeps them — and their whole subtrees — alive forever ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

```js
const metadata = new WeakMap();
```

One word changed. Now when the element becomes unreachable everywhere else, both the element and its entry are collected.

## WeakMap

```js
const wm = new WeakMap();

wm.set(objKey, value);
wm.get(objKey);
wm.has(objKey);
wm.delete(objKey);
```

Constraints, all following from weakness:

- **Keys must be objects** (or non-registered symbols). Primitives cannot be weakly held because they have no identity.
- **Not iterable.** No `keys()`, `values()`, `entries()`, `forEach`, or `size`.
- **Values are held strongly** — but only for as long as the key is alive.

The non-iterability is not an oversight. If you could enumerate a `WeakMap`, the result would depend on when GC last ran, which would make garbage collection observable and non-deterministic behavior visible to programs. The spec forbids it deliberately.

A consequence worth knowing: a value that references its own key keeps the entry alive.

```js
const wm = new WeakMap();
wm.set(node, { owner: node });   // cycle through the value — never collected
```

## WeakSet

```js
const processed = new WeakSet();

function process(item) {
  if (processed.has(item)) return;
  processed.add(item);
  doWork(item);
}
```

Same rules: objects only, not iterable, no size. Useful for marking objects — "already validated", "already visited", "is one of ours" — without mutating them or retaining them.

The brand-check use:

```js
const instances = new WeakSet();

class Model {
  constructor() { instances.add(this); }
  static isModel(x) { return instances.has(x); }
}
```

Private class fields now cover this more directly ([[03.4 - Classes vs Prototypes]]), but `WeakSet` works on objects you did not construct.

## Practical uses

**Private data for objects you do not own:**

```js
const privates = new WeakMap();

class Counter {
  constructor() { privates.set(this, { count: 0 }); }
  increment() { return ++privates.get(this).count; }
}
```

This was the standard privacy pattern before `#` fields, and it still appears in library code targeting older environments.

**Caching derived values keyed by object:**

```js
const layoutCache = new WeakMap();

function getLayout(node) {
  if (!layoutCache.has(node)) {
    layoutCache.set(node, computeExpensiveLayout(node));
  }
  return layoutCache.get(node);
}
```

The cache never needs eviction logic — entries disappear with their keys. Compare with a `Map`-based memoizer, which grows unboundedly ([[02.4 - Closure Patterns in Production]]).

**Cycle detection in recursive algorithms:**

```js
function deepClone(value, seen = new WeakMap()) {
  if (seen.has(value)) return seen.get(value);
  // ...
}
```

The bookkeeping map is discarded automatically and never retains the cloned objects ([[03.5 - Shallow vs Deep Copy]]).

**Associating React DOM nodes with measurement data**, without keeping unmounted nodes alive.

## WeakRef

A weak reference to a single object:

```js
const ref = new WeakRef(bigObject);

const obj = ref.deref();   // the object, or undefined if collected
if (obj) use(obj);
```

`deref()` may return `undefined` at any point after the object becomes unreachable elsewhere. Once you hold the dereferenced value in a variable, it is strongly held for the rest of that job — the spec guarantees it will not be collected mid-execution.

The realistic use is a cache that yields under memory pressure:

```js
const cache = new Map();

function get(key) {
  const cached = cache.get(key)?.deref();
  if (cached) return cached;

  const value = expensiveLoad(key);
  cache.set(key, new WeakRef(value));
  return value;
}
```

Note the `Map` itself still grows with dead `WeakRef` wrappers, so this needs periodic pruning — which is what `FinalizationRegistry` is for.

## FinalizationRegistry

```js
const registry = new FinalizationRegistry(key => {
  cache.delete(key);   // clean up the dead WeakRef entry
});

registry.register(value, key);
```

Runs a callback *after* an object is collected. Two hard rules from the specification and from every piece of guidance around it:

- **It may never run.** Collection is not guaranteed, and callbacks are skipped entirely if the page closes.
- **It must not be used for essential cleanup.** Closing files, releasing locks, unsubscribing — none of these belong here. Use explicit teardown.

It is a cache-pruning optimization, nothing more.

## When not to use weak collections

Both `WeakRef` and `FinalizationRegistry` come with an explicit warning in the specification against casual use, and the reasoning is sound: they make GC timing observable, so behavior differs between engines and between runs. Code that works in development can behave differently in production under different memory pressure.

`WeakMap` and `WeakSet` are safe and unremarkable — use them freely. `WeakRef` and `FinalizationRegistry` should be a considered decision with a measured motivation.

## How senior engineers actually use this

**They reach for `WeakMap` whenever the key is a DOM node or a component instance.** Any cache keyed by something with a lifecycle should be weak by default.

**They use `WeakSet` for visited-node tracking** in traversals and serializers, where a plain `Set` would retain the whole graph.

**They avoid `WeakRef` unless there is a measured memory problem** that a bounded LRU cache cannot solve. An LRU is deterministic and testable; a `WeakRef` cache is neither.

**They never rely on `FinalizationRegistry` for correctness.**

## Common pitfalls

- Trying to use a primitive as a `WeakMap` key.
- Expecting `size` or iteration.
- Storing a value that references its own key, defeating weakness.
- Using a `Map` where a `WeakMap` was appropriate, creating an unbounded cache.
- Treating `deref()` as always returning the object.
- Putting essential cleanup in a `FinalizationRegistry` callback.

## Interview angle

"What is a `WeakMap` and when would you use it" expects: object keys, weakly held so entries disappear when the key is collected, not iterable because that would expose GC timing. The best example is caching or metadata keyed by DOM nodes. If `WeakRef` comes up, the right answer includes the caveat that it makes GC observable and should be a last resort.
