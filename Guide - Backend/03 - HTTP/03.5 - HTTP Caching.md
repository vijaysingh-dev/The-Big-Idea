# HTTP Caching

#backend #http #performance #caching

> **In one line:** The fastest request is the one that never happens, and HTTP has a complete caching protocol built in that most backend engineers never configure.

---

## The Idea

Caching in HTTP is not one cache. It is a chain of them, each obeying the same headers:

```
Browser cache → CDN edge → reverse proxy → your app → your Redis → database
     ▲             ▲            ▲
     └─────────────┴────────────┴─── all controlled by Cache-Control and ETag
```

💡 **The point that makes this worth learning: you can push work out of your infrastructure entirely.** A response cached at a CDN edge never reaches your servers. That is not an optimisation of your service — it is the removal of load from it, and no amount of application tuning competes with a request you never receive.

Most backend engineers set `Cache-Control: no-store` everywhere out of caution and then wonder why their API is expensive.

---

## Cache-Control

The primary header. Directives combine.

### Response directives

| Directive | Meaning |
|---|---|
| `max-age=3600` | Fresh for 3600 seconds |
| `s-maxage=7200` | Fresh for 7200s in **shared** caches (CDN, proxy). Overrides `max-age` there |
| `public` | Any cache may store it, even with `Authorization` present |
| `private` | Only the browser may store it. **CDNs must not** |
| `no-cache` | May store, but **must revalidate** before every use |
| `no-store` | Do not store at all, anywhere |
| `must-revalidate` | Once stale, must revalidate — no serving stale on error |
| `immutable` | Never revalidate while fresh. For content-hashed URLs |
| `stale-while-revalidate=60` | Serve stale for up to 60s while fetching fresh in the background |
| `stale-if-error=86400` | Serve stale for up to a day if the origin is failing |

⚠️ **`no-cache` does not mean "do not cache".** It means "cache, but check with me before using it". The directive that means do not cache is `no-store`. This naming has confused people for twenty-five years and it will confuse a colleague reviewing your code, so a comment is warranted when you use it.

### The two most underused directives

```http
Cache-Control: max-age=60, stale-while-revalidate=300, stale-if-error=86400
```

**`stale-while-revalidate`** — after 60 seconds, the cache serves the stale copy *immediately* and refreshes in the background. The user never waits for revalidation. Your origin sees one request instead of a burst.

**`stale-if-error`** — if your origin returns 5xx or is unreachable, the cache serves the last good copy for up to a day.

💡 **`stale-if-error` is a resilience feature disguised as a caching directive.** Your API can be completely down and cached endpoints keep serving. For read-heavy public data this is the cheapest availability improvement available to you, and it requires no code — just a header. It pairs naturally with [[11.6 - Graceful Degradation]].

### Request directives

Clients can send `Cache-Control` too:

```http
Cache-Control: no-cache        # force revalidation (browser hard refresh)
Cache-Control: only-if-cached  # fail rather than hit the network
```

## Validators: ETag and Last-Modified

When something is stale, the cache asks "has this changed?" rather than re-downloading.

### ETag

```http
GET /documents/42
→ 200 OK
  ETag: "a1b2c3d4"
  Cache-Control: max-age=60
```

After 60 seconds:

```http
GET /documents/42
If-None-Match: "a1b2c3d4"
→ 304 Not Modified            (no body)
```

You still pay the round trip; you save the bandwidth and the server-side rendering.

**Strong vs weak:**

```http
ETag: "a1b2c3"          # strong — byte-identical
ETag: W/"a1b2c3"        # weak — semantically equivalent
```

Weak ETags let you ignore differences that do not matter, like a timestamp in the response envelope. Use weak unless you need byte-range requests, which require strong.

**Generating them:**

```python
# Content hash — accurate, costs the rendering
etag = hashlib.sha256(body).hexdigest()[:16]

# Version column — cheap, and it doubles as optimistic concurrency
etag = f'W/"{doc.version}"'

# Composite for a collection
etag = f'W/"{max_updated_at.timestamp()}-{count}"'
```

💡 **The version-column approach is the good one for APIs.** It costs a single column read, it changes exactly when the resource changes, and it gives you `If-Match` optimistic concurrency for free ([[03.3 - Methods Status Codes and Semantics]]). Hashing the body means rendering the body first, which defeats most of the saving.

### Last-Modified

```http
Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT
If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT
```

One-second resolution, which is too coarse for anything that changes quickly. Prefer ETags; send `Last-Modified` as well for old clients if you like.

## Vary — the header that breaks caches

```http
Vary: Accept-Encoding, Accept-Language
```

Tells caches that the response depends on those request headers, so each combination needs its own cache entry.

⚠️ **`Vary` fragments your cache multiplicatively.** Two encodings × five languages = ten entries for one resource, each with a lower hit rate.

Worst case:

```http
Vary: User-Agent          # effectively disables caching
Vary: Cookie              # effectively disables caching
```

`User-Agent` has millions of distinct values. `Cookie` is unique per user. Either one means every request is a cache miss.

💡 **`Vary: Cookie` is the accidental cache-killer.** Frameworks add it automatically when sessions are enabled, and the result is that your entire CDN caching silently stops working. **Check what `Vary` your framework is actually sending** — this is a five-minute check with a large payoff. If you serve a mix of public and personalised content, split them into separate endpoints rather than varying.

## Cache Keys and Invalidation

### What forms the key

```
method + full URL (including query string) + Vary'd headers
```

⚠️ **Query parameter order matters.** `?a=1&b=2` and `?b=2&a=1` are different cache entries. So are `?page=1` and `?page=1&` — trailing separators, tracking parameters, and inconsistent client-side serialisation all fragment your cache.

Normalise at the edge:

```nginx
# Strip tracking parameters before the cache key is computed
if ($args ~ (.*)(^|&)utm_[^&]*(&|$)(.*)) {
    set $args $1$2$4;
}
```

### Invalidation strategies

| Strategy | How | Good for |
|---|---|---|
| **TTL only** | Short `max-age`, wait it out | Simple, tolerant data |
| **Purge** | Call the CDN API on change | Precise, needs coordination |
| **Surrogate keys** | Tag responses, purge by tag | The best option where supported |
| **Versioned URLs** | `/assets/app.a1b2c3.js` | Static assets. `immutable`, cache forever |
| **Revalidation** | `no-cache` + ETag | Always fresh, still saves bandwidth |

**Surrogate keys** (Fastly, Cloudflare Enterprise) are the strong option:

```http
Surrogate-Key: doc-42 org-7 tag-urgent
```

Later, purge everything tagged `org-7` in one call. One document change can invalidate every derived listing that included it, without you tracking which listings exist.

💡 **Versioned URLs for static assets is the cleanest cache design there is.** The URL contains a content hash, so the content at that URL can never change, so you cache it forever with `immutable`. Deploying a change produces a new URL. There is no invalidation because there is nothing to invalidate.

## Caching an API

APIs are cacheable more often than people assume.

| Endpoint | Setting |
|---|---|
| `GET /health` | `no-store` |
| `GET /config` (public) | `public, max-age=300, stale-while-revalidate=600` |
| `GET /documents?org=7` (per-user) | `private, no-cache` + ETag |
| `GET /documents/42` | `private, max-age=0, must-revalidate` + ETag |
| `GET /avatars/{hash}.png` | `public, max-age=31536000, immutable` |
| Any `POST` / `PATCH` / `DELETE` | `no-store` |
| Anything with a bearer token | `private` — never `public` |

⚠️ **The catastrophic mistake: `public` on a per-user response.** A CDN caches user A's document list and serves it to user B. This is a data breach caused by one header, and it has happened to real companies.

**Rule: if the response depends on `Authorization` or a session cookie, it is `private`. No exceptions.** Consider asserting this in a test.

### Conditional responses in FastAPI

```python
@app.get("/documents/{doc_id}")
async def get_document(doc_id: str, request: Request, response: Response):
    doc = await repo.get(doc_id)
    etag = f'W/"{doc.version}"'

    if request.headers.get("if-none-match") == etag:
        return Response(status_code=304, headers={"ETag": etag})

    response.headers["ETag"] = etag
    response.headers["Cache-Control"] = "private, no-cache"
    return doc
```

For a polling client this turns a 50KB response into a 200-byte 304, and skips serialisation entirely. On a dashboard polling every 5 seconds that is a large saving for about ten lines of code.

## In Production

### Measuring

```bash
curl -I https://api.example.com/config

Cache-Control: public, max-age=300
Age: 127                     ← seconds this has been in a cache
X-Cache: HIT                 ← CDN-specific
CF-Cache-Status: HIT
```

`Age` is the standard one and it is genuinely useful — it tells you the response came from a cache and how old it is.

Track:

| Metric | Meaning |
|---|---|
| Cache hit ratio | The headline number |
| Origin requests per second | What you actually pay for |
| `304` rate | Revalidations succeeding — bandwidth saved |
| Stale-served count | `stale-while-revalidate` and `stale-if-error` firing |

### Why your hit rate is bad

In order of likelihood:

1. **`Vary: Cookie` or `Vary: User-Agent`** — check first, it is the usual answer
2. **`private` where `public` would be safe**
3. **Query parameter fragmentation** — tracking params, ordering
4. **`max-age` too short** relative to how often content actually changes
5. **No `Cache-Control` at all** — caches then guess, usually conservatively
6. **`Set-Cookie` on responses** — many caches refuse to store these

### Cache stampede

The cached entry expires. A thousand concurrent requests all miss, all hit your origin simultaneously.

```
Cache expires at t=0
1000 requests arrive at t=0.001
1000 origin requests
```

Fixes at the HTTP layer:

```http
Cache-Control: max-age=60, stale-while-revalidate=300
```

The cache serves stale and refreshes once in the background. **One origin request instead of a thousand**, and no user waits.

```nginx
proxy_cache_lock on;              # only one request goes to origin on a miss
proxy_cache_lock_timeout 5s;
proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
```

`proxy_cache_use_stale updating` is the nginx equivalent of `stale-while-revalidate`. The application-layer version is in [[07.3 - Stampede Hot Keys and Negative Caching]].

### Debugging checklist

```bash
# What is actually being sent?
curl -sD - -o /dev/null https://api.example.com/x | grep -iE 'cache|etag|vary|age'

# Does revalidation work?
curl -H 'If-None-Match: "abc"' -I https://api.example.com/x     # expect 304

# Is the CDN caching it?
curl -I https://api.example.com/x | grep -iE 'x-cache|cf-cache|age'
```

If `Age` is always 0, nothing is caching. Work through the six reasons above.

## Codebase

**Repo:** `nginx/nginx`, `varnishcache/varnish-cache`, `caddyserver/caddy`

**Question to answer:** How does a real cache compute its key, decide whether a response is storable, and handle a stampede? Then: what does Varnish do that nginx does not, and why do CDNs choose it?

**Read, in order:**

1. `nginx/src/http/ngx_http_cache.h` and `ngx_http_file_cache.c` — key computation and the on-disk format. Find `ngx_http_file_cache_lock`, which is `proxy_cache_lock` — the stampede defence
2. `nginx/src/http/modules/ngx_http_proxy_module.c` — search for how it decides a response is cacheable, and how `Vary` is incorporated into the key
3. `varnish-cache/bin/varnishd/cache/cache_req_fsm.c` — the request state machine. Varnish's model is a **finite state machine you can program with VCL**, which is why CDNs like it
4. `varnish-cache/bin/varnishd/cache/cache_fetch.c` — look for the busy object handling. This is Varnish's stampede prevention, and it is more sophisticated than nginx's
5. `caddyserver/caddy` — the `cache-handler` module, for a modern Go implementation that is easier to read than either

💡 The Varnish comparison is the interesting part. nginx's cache is configuration-driven; Varnish's is programmable, with an explicit request lifecycle you write logic into. **That difference explains why CDN edge logic is a product category.** Understanding the state machine makes CDN configuration much less mysterious.

**Size:** 1 session.

```
│   └── public_private.py # cache a per-user response publicly. Watch the breach
├── keys/
│   └── fragmentation.py  # query param ordering and tracking params
└── README.md
```

**Part 1 — Build the API.** Endpoints covering every row of the table above: public config, per-user list, single document with ETag, immutable asset, health check.

Then implement conditional requests properly, including the `304` path skipping serialisation entirely.

**Part 2 — Measure what caching removes.** nginx with `proxy_cache` in front. Realistic load — 80% reads, mixed endpoints.

Measure origin requests per second with: no cache headers, correct headers, and correct headers plus `stale-while-revalidate`.

**Chart origin load in all three.** The drop is the entire point of this note and it will be larger than you expect.

**Part 3 — Vary damage.** Same endpoint, three `Vary` configurations: none, `Accept-Encoding`, and `Accept-Encoding, User-Agent`.

Send traffic from 100 simulated user agents. Measure the cache hit rate for each. **The third should be near zero.**

Then find what `Vary` your actual FastAPI app sends when sessions or CORS middleware are enabled. Most people are surprised.

**Part 4 — Stampede.** A slow endpoint (500ms origin) with `max-age=10`. 1000 concurrent clients polling.

Watch what happens at the expiry moment. Chart origin requests per second — you should see a spike every 10 seconds.

Then fix three ways and chart each: `proxy_cache_lock`, `stale-while-revalidate`, and both. Compare the origin load and the client-observed latency in each.

**Part 5 — `stale-if-error` as availability.** Set `stale-if-error=3600`. Warm the cache. **Now kill the origin entirely.**

Confirm clients keep getting successful responses. Measure how long availability is preserved.

Write in `RESULTS.md`: what class of endpoint is this appropriate for, and what class would it be dangerous for?

**Part 6 — Cause a data breach.** Per-user endpoint. Set `Cache-Control: public, max-age=300`. Two users behind the same cache.

Show user B receiving user A's data.

Then fix it with `private`. Then write a **test** that fails if any authenticated endpoint ever returns `public` — this is the kind of test worth having permanently, because the mistake is one word and the consequence is severe.

**Part 7 — Key fragmentation.** Same logical request, five URL variants: parameter order swapped, trailing `&`, a `utm_source` added, an empty parameter, and different case in a value.

Measure the cache entries created. Then normalise at the edge and measure again.

**Done when:**
- Your origin-load chart shows the three configurations clearly
- You have measured `Vary: User-Agent` destroying the hit rate
- The stampede chart shows spikes disappearing with each fix
- You served traffic successfully with the origin dead
- You caused and then prevented a cross-user cache leak, with a test guarding it
- Five URL variants collapse to one cache entry after normalisation
