# Formula Engine and Syntax

## Where formulas appear

Formulas are not one feature. The same expression language appears in at least eight places, with different available functions and different evaluation timing:

| Context | Evaluated | Returns |
| --- | --- | --- |
| Formula field | On every read | A value |
| Validation rule | On save, before commit | True means block |
| Default value | On record creation | A value |
| Workflow field update | On save | A value |
| Flow formula resource | When referenced | A value |
| Approval process criteria | On submission and per step | True or false |
| Roll-up summary filter | On child change | True means include |
| Report row-level formula | At report run | A value |

The syntax is shared. The available functions are not — `ISCHANGED` and `PRIORVALUE` work in validation rules and workflow but not in formula fields, because a formula field has no concept of a previous state.

Knowing which context you are in tells you which functions exist, and it is the first thing to check when a function that "should work" is unavailable.

## The mental model

A formula is a **single expression** that evaluates to one value. There are no variables, no loops, no statements, no early returns.

That constraint shapes everything. Complex logic has to be expressed as nested conditionals or as `CASE`, which is why long formulas become unreadable and why the 5,000-byte compiled limit is reached faster than people expect.

```
IF(
  AND(
    NOT(ISBLANK(Approved_Amount__c)),
    Approved_Amount__c > 0
  ),
  IF(Approved_Amount__c >= Claim_Amount__c, "Full", "Partial"),
  "Pending"
)
```

Read from the outside in. The outer `IF` tests whether an amount exists; the inner one classifies it.

## Data types and coercion

Formulas are typed, and the return type is chosen when the field is created and cannot be changed afterwards.

**Number** — decimals with configurable scale.
**Currency** — number with currency behaviour, and in multi-currency orgs it converts.
**Percent** — stored as the displayed value divided by 100 in some contexts, which is a recurring source of confusion.
**Text** — up to 3,900 characters returned.
**Date** and **Datetime** — see [[06.3 - Date and Datetime Functions]].
**Checkbox** — boolean.

There is **no implicit coercion**. Comparing a picklist to text fails unless wrapped in `TEXT()`. Concatenating a number to a string fails unless wrapped in `TEXT()`.

```
// Fails: cannot compare picklist directly to text
Status__c = "Closed"

// Correct
ISPICKVAL(Status__c, "Closed")
TEXT(Status__c) = "Closed"

// Fails: cannot concatenate number to text
"Claim value: " & Claim_Amount__c

// Correct
"Claim value: " & TEXT(Claim_Amount__c)
```

`ISPICKVAL` is more efficient than `TEXT()` comparison and is the right choice for a single value. `TEXT()` is needed when you want to compare against several values or use the value in string operations.

## Null handling, which causes the most bugs

This is the single largest source of formulas that appear correct and produce wrong results.

**Any arithmetic involving null returns null.** Not zero — null.

```
// If Discount__c is null, the whole expression is null, not 1000
Amount__c - Discount__c
```

**Any text concatenation involving null returns null** in most contexts.

There is a checkbox on numeric formula fields: "Treat blank fields as zeroes" versus "Treat blank fields as blanks". The default is blanks, which is correct semantically and surprising practically.

Relying on that setting is fragile, because it is invisible to anyone reading the formula. Being explicit is better:

```
Amount__c - BLANKVALUE(Discount__c, 0)
NULLVALUE(Discount__c, 0)
```

`BLANKVALUE` treats empty text and null as blank. `NULLVALUE` handles null only and works on numbers and dates. For text, `BLANKVALUE` is what you want, because an empty string is not null but is usually meant to be treated the same way.

Checking for emptiness:

```
ISBLANK(Field__c)        // null or empty text
ISNULL(Field__c)         // null only; deprecated for text, still used for numbers
NOT(ISBLANK(Field__c))   // has a value
```

`ISBLANK` is the modern choice and handles both cases.

## Operators

```
Arithmetic:   +  -  *  /  ^
Comparison:   =  <>  <  >  <=  >=
Logical:      &&  ||  (also AND(), OR(), NOT())
Text:         &  (concatenation, also + for text)
```

`=` is comparison, not assignment. There is no assignment in formulas.

`AND(a, b, c)` and `a && b && c` are equivalent. The function form is easier to read when there are several conditions and easier to indent, which matters for the maintainability of anything non-trivial.

## Referencing fields

Same record: the API name directly.

```
Claim_Amount__c
Status__c
CreatedDate
```

Parent record: traverse with `__r` for custom relationships, or the relationship name for standard ones.

```
Account__r.Name
Account__r.Owner.Email
Machine__r.Asset__r.SerialNumber
Owner.Manager.Email
```

Up to **10 levels** of traversal per formula, and 15 unique relationships across all formulas, validation rules, and roll-ups on the object combined. That combined limit is a scarce resource in a mature org, and someone eventually cannot add a needed validation rule because the budget is spent. See [[06.4 - Cross-Object Formulas and Limits]].

Global variables:

```
$User.Id, $User.ProfileId, $User.Email
$Profile.Name
$Organization.Id
$Setup.Feature_Toggle__c.Enable_New_Pricing__c
$Label.Warranty_Rejection_Message
$RecordType.DeveloperName
$Permission.Can_Approve_Claims
$System.OriginDateTime
```

`$Permission` is worth knowing — it lets a validation rule or formula check a custom permission rather than hardcoding a profile name, which is far more maintainable.

```
// Only users with the custom permission can set an approved amount
AND(
  ISCHANGED(Approved_Amount__c),
  NOT($Permission.Can_Approve_Claims)
)
```

## The limits

**Compiled size: 5,000 bytes.** Not what you typed — the compiled form, which expands substantially when the formula references other formula fields. This is the limit people hit first, and the error message is unhelpful.

**Characters: 3,900.**

**Spanning relationships: 10 per formula, 15 per object across all formulas, validation rules, and roll-up filters.**

When you hit the compiled size limit, the options are: simplify the logic, extract a repeated sub-expression into a helper formula field, or accept that it should be Apex. There is no way to raise it.

The helper-field approach is the usual answer and it has a cost — each helper is another field consuming the field limit and another value computed on every read.

## Formatting for maintainability

Formulas have no comments in most contexts, so structure is the only documentation.

```
IF(
  ISPICKVAL(Status__c, "Approved"),
  IF(
    Approved_Amount__c >= Claim_Amount__c,
    "Full Settlement",
    "Partial Settlement — " & TEXT(ROUND(Approved_Amount__c / Claim_Amount__c * 100, 0)) & "%"
  ),
  IF(
    ISPICKVAL(Status__c, "Rejected"),
    "Rejected — " & TEXT(Rejection_Reason__c),
    "In Progress"
  )
)
```

Indent every nesting level. Put each condition of an `AND` or `OR` on its own line. The formula editor preserves whitespace, and a formula formatted on one line is effectively unmaintainable.

Where a description field is available — on formula fields and validation rules — use it. It is the only place to explain why the logic exists.

## Debugging

The formula editor has a syntax checker that catches type errors and unknown fields, and it is worth using before saving.

For logic errors, the practical technique is decomposition: build the formula in pieces as temporary formula fields, verify each on a real record, then combine. Trying to debug a forty-line nested formula by reading it is slower than splitting it.

For validation rules specifically, temporarily changing the rule to return the value being tested rather than the boolean tells you what the formula actually sees, which is usually the fastest route to the answer.
