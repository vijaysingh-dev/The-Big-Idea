# Server-Sent Events

#backend #realtime #sse #streaming

> **In one line:** SSE is a text format sent over an ordinary HTTP response that never ends, with automatic reconnection and replay built into the browser — and it is the transport behind every LLM streaming API you have used.

---

## The Idea

An SSE endpoint is a normal HTTP GET whose response body simply keeps going.

```http
GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: {"progress": 10}

data: {"progress": 20}

data: {"progress": 30}
```

That is the whole protocol. No handshake, no upgrade, no new framing — chunked transfer encoding from [[03.1 - HTTP1.1 Message Format]] doing exactly what it was designed for.

💡 **What makes SSE genuinely good rather than merely simple is that the browser handles reconnection for you**, including telling the server which event it last received so you can replay the gap. That is the hard part of realtime, and it is free.

---

## The Format

```
field: value\n
field: value\n
\n                    ← blank line ends the event
```

Four fields, and that is all there is:

| Field | Purpose |
|---|---|
| `data` | The payload. Multiple `data` lines are joined with `\n` |
| `event` | Event type. The client listens for it by name |
| `id` | Event ID. **The browser remembers this and sends it on reconnect** |
| `retry` | Reconnection delay in milliseconds |

```
event: progress
id: 1042
data: {"documents_done": 42, "total": 100}

event: document
id: 1043
data: {"id": "doc-7", "title": "Q3 Report"}

: this is a comment — used as a heartbeat

retry: 3000
```

Rules worth knowing:

- **Lines starting with `:` are comments.** The standard heartbeat is a bare `:\n\n`
- A `data` line with no value sends an empty string
- Multiple `data` lines in one event are concatenated with newlines — the standard way to send multi-line text
- **UTF-8 text only.** Binary needs base64, which costs 33% overhead

⚠️ **Your JSON payload must not contain a raw newline**, because a newline ends the line and a blank line ends the event. `json.dumps` escapes newlines inside strings by default, so this is usually safe — but if you are hand-building payloads or using a serialiser with `indent=`, you will break the stream in a way that looks like data corruption.

## The Client

```javascript
const es = new EventSource("/events");

es.onmessage = (e) => console.log(e.data);           // unnamed events

es.addEventListener("progress", (e) => {
    const data = JSON.parse(e.data);
    updateBar(data.documents_done, data.total);
});

es.onerror = (e) => {
    // the browser is already reconnecting. Do not reconnect manually
};
```

What the browser does for you:

1. Reconnects automatically on disconnect
2. Waits the `retry` interval, with its own backoff
3. **Sends `Last-Event-ID` with the last `id` it saw**

```http
GET /events HTTP/1.1
Last-Event-ID: 1043
```

⚠️ **`EventSource` cannot send custom headers.** No `Authorization: Bearer`. Your options are cookies, a query-string token (which leaks into logs), or the `fetch`-based approach below.

### The fetch alternative

```javascript
const res = await fetch("/events", {
    headers: { "Authorization": `Bearer ${token}` },
});

const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
// parse the SSE format yourself
```

💡 **This is what every LLM client library does**, and it is why they all ship their own SSE parser. You get headers and full control; you give up automatic reconnection and `Last-Event-ID` handling, which you must then implement yourself. The `@microsoft/fetch-event-source` library packages this properly.

## The Server

```python
from fastapi.responses import StreamingResponse

async def event_stream(request: Request, last_event_id: str | None):
    # Replay anything missed
    if last_event_id:
        async for event in replay_since(int(last_event_id)):
            yield format_sse(event)

    queue = await subscribe(request.state.user_id)
    try:
        while True:
            try:
                event = await asyncio.wait_for(queue.get(), timeout=15)
                yield format_sse(event)
            except TimeoutError:
                yield b": heartbeat\n\n"          # keeps the connection alive
    finally:
        await unsubscribe(queue)


def format_sse(event: Event) -> bytes:
    lines = []
    if event.id is not None:
        lines.append(f"id: {event.id}")
    if event.type:
        lines.append(f"event: {event.type}")
    lines.append(f"data: {orjson.dumps(event.payload).decode()}")
    return ("\n".join(lines) + "\n\n").encode()


@app.get("/events")
async def events(request: Request):
    last_id = request.headers.get("last-event-id")
    return StreamingResponse(
        event_stream(request, last_id),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",
        },
    )
```

Four details in there that all matter:

**The `finally` block.** Without it, a disconnected client leaves a subscription behind. Over hours, that is a memory leak that looks like a slow leak with no obvious cause.

**`asyncio.wait_for` with a 15-second timeout.** This is the heartbeat mechanism. Rather than a separate heartbeat task, the read itself times out and emits a comment.

**`X-Accel-Buffering: no`.** Without it nginx buffers your stream and the client receives nothing ([[03.6 - Compression and Streaming Responses]]).

**Event IDs.** Without them, `Last-Event-ID` does nothing and reconnection silently loses events.

## Reconnection and Replay

This is what makes SSE worth using, and it is where implementations get it wrong.

```
Client receives events 1, 2, 3
Connection drops
Events 4, 5 are generated
Client reconnects with Last-Event-ID: 3
Server must send 4 and 5, then continue live
```

### The replay buffer

```python
class EventLog:
    def __init__(self, maxlen: int = 1000):
        self._events: deque[Event] = deque(maxlen=maxlen)
        self._next_id = 1

    def append(self, type: str, payload: dict) -> Event:
        event = Event(id=self._next_id, type=type, payload=payload)
        self._next_id += 1
        self._events.append(event)
        return event

    def since(self, last_id: int) -> list[Event] | None:
        if not self._events:
            return []
        if last_id < self._events[0].id - 1:
            return None                    # gap too large — client must resync
        return [e for e in self._events if e.id > last_id]
```

⚠️ **The `None` case is the one people forget.** If the client was disconnected long enough that the events it missed have fallen out of the buffer, you **cannot** silently continue from the newest event — the client would have a permanent invisible gap.

Tell it explicitly:

```python
missed = log.since(last_id)
if missed is None:
    yield format_sse(Event(type="resync_required", payload={}))
    # client should refetch full state via a normal GET
else:
    for e in missed:
        yield format_sse(e)
```

💡 **This resync signal is the difference between a realtime feature that is correct and one that is subtly wrong.** Without it, a user whose laptop slept for an hour sees a UI that looks fine and is missing data — the worst kind of bug, because nothing appears broken.

### Where the buffer lives

| Option | Trade |
|---|---|
| In-process `deque` | Simplest. Lost on restart, not shared across pods |
| Redis Stream | Shared, bounded with `MAXLEN`, survives restart. **The usual answer** |
| Postgres table | Durable, queryable, slower. Good when events matter |
| Kafka | Long retention, full replay. Overkill unless you already have it |

Redis Streams are a strong fit here — `XADD` with `MAXLEN ~ 1000`, and `XRANGE` to read from an ID. The existing Redis guide covers the commands.

## Heartbeats

Non-negotiable for any SSE deployment.

```python
yield b": heartbeat\n\n"
```

A comment line. The client ignores it entirely; the network sees traffic.

**What it prevents:**

| Killer | Typical timeout |
|---|---|
| nginx `proxy_read_timeout` | 60s |
| AWS ALB idle timeout | 60s |
| NAT mapping expiry | 30–300s |
| Corporate proxy | Varies, often aggressive |

**15 seconds is the standard interval** — comfortably below every common timeout, and 4 bytes per client per 15 seconds is nothing even at 100,000 connections.

⚠️ **Heartbeats also let you detect dead clients.** If the write fails, the client is gone and you can clean up. Without any writes, a disconnected client can go unnoticed indefinitely, because reading is what you were doing and there is nothing to read.

## In Production

### The connection limit problem

Over HTTP/1.1, browsers allow **6 connections per origin**. An SSE stream holds one permanently.

```
6 tabs open → 6 SSE connections → 0 remaining for normal requests
```

⚠️ **The page appears to hang.** Every fetch queues behind the SSE streams. This is a genuinely confusing bug because the SSE stream itself works perfectly.

Fixes:

1. **HTTP/2** — multiplexed, effectively no limit. The real answer
2. **One SSE connection shared between tabs** via `BroadcastChannel` or a `SharedWorker`
3. **A separate subdomain** for the SSE endpoint — its own connection budget

💡 **HTTP/2 makes SSE genuinely good.** All the streams multiplex onto one connection, the 6-connection limit disappears, and HPACK compresses the repeated headers. If you are deploying SSE, deploy HTTP/2 at the edge.

### Do not compress SSE

```python
headers={"Content-Encoding": "identity"}
```

A compressor buffers to build its dictionary. Buffering defeats streaming ([[03.6 - Compression and Streaming Responses]]). Some setups flush per chunk, which works but wastes CPU for a negligible ratio on small events.

Exclude SSE routes from your compression middleware explicitly.

### Every layer must not buffer

```nginx
location /events {
    proxy_pass http://app;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    gzip off;
}
```

And in the application, avoid `BaseHTTPMiddleware` on SSE routes ([[01.9 - ASGI and How Uvicorn Serves a Request]]).

**Test for buffering explicitly**, because it is silent:

```bash
curl -N https://api.example.com/events
```

`-N` disables curl's own buffering. Events should appear as they are generated. If they all arrive at once at the end, something in the path is buffering.

### Detecting disconnects

```python
async def event_stream(request: Request):
    try:
        while True:
            if await request.is_disconnected():
                break
            ...
    finally:
        await cleanup()
```

⚠️ **In practice the reliable signal is a write failure.** `is_disconnected()` depends on receiving the disconnect message, which may be delayed. The heartbeat write is what actually tells you — another reason heartbeats are not optional.

When the client disconnects, uvicorn cancels the task, so a `finally` block is your cleanup path ([[01.7 - Cancellation and Structured Concurrency]]).

### LLM token streaming

The reason this note matters for your AI work.

```python
async def stream_completion(prompt: str):
    async for chunk in llm.stream(prompt):
        yield format_sse(Event(type="token", payload={"text": chunk}))
    yield format_sse(Event(type="done", payload={}))
```

OpenAI, Anthropic and vLLM all use exactly this, with `data: [DONE]` as the terminator. Everything in this note — heartbeats, buffering, disconnect detection — applies directly.

💡 **Disconnect detection matters more with LLMs than anywhere else**, because generation is expensive. If the user closes the tab and you keep generating, you are burning GPU time for nobody. vLLM's server checks for disconnect and aborts the request — worth reading ([[04.4 - Streaming LLM Responses]]).

**Read, in order:**

5. `zulip/zerver/tornado/event_queue.py` — again, for the replay buffer design. Different transport, identical problem

💡 The spec reading is worth doing properly. Knowing precisely when the browser sends `Last-Event-ID`, what it does with `retry`, and what counts as a "reconnect" versus a fresh connection is the difference between a replay implementation that works and one that mostly works.

```
│   └── RESULTS.md
├── slow/
│   └── slow_client.py    # reads 1 byte/sec
└── README.md
```

**Part 1 — The format, exactly.** Encoder and decoder for all four fields. Tests for: multi-line `data`, unicode, a payload containing a newline (must be escaped), a payload containing `\r\n`, comment lines, and an event with no `data`.

Then write a Python client parser that handles a stream arriving in arbitrary chunk boundaries — a field split across two TCP reads is the realistic case and the one that breaks naive parsers.

**Part 2 — The server.** Bounded replay log, per-client queues, heartbeats, and cleanup on disconnect.

Then verify cleanup: connect 100 clients, kill them all abruptly, and confirm subscriptions and memory return to baseline. **Leaked subscriptions are the most common SSE bug** and this test catches it.

**Part 3 — Replay, both cases.**

- Connect, receive events 1–10, disconnect, generate 11–15, reconnect. Confirm exactly 11–15 arrive, with no duplicates and no gap
- Connect, receive 1–10, disconnect, generate 2,000 events (overflowing a 1,000-entry buffer), reconnect. Confirm the client receives `resync_required` rather than a silent gap

**The second case is the one that matters.** Then implement the client side of resync — refetch full state, then resume — and verify the final state is correct.

**Part 4 — Break it three ways.**

- **Buffering:** nginx with defaults. Confirm with `curl -N` that nothing arrives until the end. Fix three ways and measure time-to-first-event for each
- **Idle timeout:** `proxy_read_timeout 30s`, no heartbeat. Watch the connection die every 30 seconds. Add heartbeats and confirm it survives an hour
- **Connection limit:** an HTML page opening 6 SSE connections, then making a normal fetch. Watch it hang. Then serve over HTTP/2 and confirm it does not

**Part 5 — Slow client.** A client that reads 1 byte per second while you generate 100 events per second.

Measure server memory growth. Then implement a bounded per-client queue with a policy, and demonstrate all three policies: drop oldest, drop newest, and disconnect.

Write down which policy is right for progress updates, and which for a chat message stream. **They are different, and the reasoning is the point.**

**Part 6 — Auth three ways.** `EventSource` with cookies, query-string token, and a fetch-based client with an `Authorization` header.

For the query-string version, find the token in your nginx access log. Then implement the ticket pattern from [[04.1 - Choosing a Realtime Transport]] and confirm it does not leak.

**Part 7 — Wire it into Conduit.** Ingestion progress over SSE: events for `document_started`, `document_completed`, `document_failed`, `run_completed`. Replay from a Redis Stream. Heartbeats. Resync signalling.

Load test with 500 concurrent watchers and record memory, CPU and event latency.

**Done when:**
- Your parser handles fields split across chunk boundaries
- 100 abrupt disconnects leave zero leaked subscriptions
- Both replay cases work, including the resync path end to end
- All three failure modes are reproduced and fixed with measured results
- You can state which slow-client policy suits which data type and why
- Conduit's ingestion progress streams to 500 watchers with measured cost
