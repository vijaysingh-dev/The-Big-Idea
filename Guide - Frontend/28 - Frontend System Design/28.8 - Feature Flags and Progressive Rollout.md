# Feature Flags and Progressive Rollout

## Decoupling deploy from release

Without flags, shipping code and exposing a feature are the same event. A problem means a rollback — which for a frontend deployment is fast, but rolls back *everything* in that release, including unrelated fixes.

With flags, the code ships disabled and is enabled separately:

```
deploy (code present, flag off)
   ↓
enable for internal users
   ↓
enable for 5% → 25% → 100%
   ↓
remove the flag and the old path
```

A problem at any stage is a flag toggle taking seconds, affecting only the cohort that has it on. That difference — targeted, instant, no rebuild — is why flags are the primary release mechanism for frontend teams at scale.

## Four kinds, with different lifetimes

Conflating them is the main source of flag debt.

**Release flags** hide incomplete work so trunk-based development is possible. Short-lived — days to weeks — and removed as soon as the feature is at 100%.

**Experiment flags** drive A/B tests. Lifetime is the experiment; the losing variant is deleted.

**Operational flags** are kill switches for expensive or risky subsystems — disable recommendations under load, turn off a third-party widget that is failing. Long-lived by design.

**Permission flags** gate features by plan or entitlement. Permanent, and arguably not flags at all — they are authorization, and belong with the permissions model ([[28.7 - Authentication Flow Design]]).

Only the first two are meant to be removed. Tracking which is which, with an owner and an expiry date, is what prevents accumulation.

## Build-time versus runtime

```ts
// Build-time — dead-code eliminated, requires a redeploy to change
if (import.meta.env.VITE_NEW_CHECKOUT === "true") {
  return <NewCheckout />;
}

// Runtime — instant toggle, both paths ship
const { newCheckout } = useFlags();
```

Build-time flags remove the disabled branch entirely, so the code is smaller and cannot be reached by inspection ([[27.8 - Environment Variables and Config]]). The cost is that changing one requires a rebuild, and different builds exist per environment — which breaks build-once-deploy-many.

Runtime flags ship both paths and add a dependency on the flag service. That is the price of being able to change behavior without a deploy.

Use build-time for permanent environment differences, runtime for anything that needs to change in production.

## Evaluation and the flash problem

```tsx
function useFlag(key: string): boolean {
  const flags = useContext(FlagContext);
  return flags[key] ?? DEFAULTS[key] ?? false;
}
```

Fetching flags on the client creates a **flash of the wrong variant** — the default renders, then the real value arrives and the UI changes. Visible, jarring, and it invalidates experiment measurement because some users see both variants.

Three fixes, in increasing order of quality:

**Bootstrap from the server.** Evaluate flags during SSR and inline them, so the first paint is already correct:

```html
<script>window.__FLAGS__ = { "new-checkout": true };</script>
```

**Evaluate at the edge.** Middleware assigns the variant and sets a cookie or rewrites the response before the page reaches the browser.

**Block on the first load only**, with a cached value for subsequent visits.

The flash is the single most common flag implementation problem, and it is worth designing for explicitly rather than accepting.

## Targeting

```ts
{
  key: "new-checkout",
  rules: [
    { if: { userId: { in: internalUserIds } }, value: true },
    { if: { plan: "enterprise" }, value: false },
    { if: { country: "IN" }, rollout: 25 },
    { default: false },
  ],
}
```

Rules evaluate in order, first match wins.

**Bucketing must be deterministic.** A user assigned to the 25% cohort must stay there across sessions and devices:

```ts
const bucket = hash(`${flagKey}:${userId}`) % 100;
const enabled = bucket < rolloutPercentage;
```

Hashing the flag key with the user id means the same user gets different buckets for different flags — otherwise the same 25% receives every experiment, which correlates results and skews measurement.

Random assignment per session is the failure mode to avoid: the user sees the feature appear and disappear, and experiment data becomes meaningless.

## Instrumentation

```ts
const enabled = useFlag("new-checkout");

useEffect(() => {
  analytics.track("flag_evaluated", { flag: "new-checkout", variant: enabled });
}, [enabled]);
```

An experiment without exposure tracking cannot be analysed — you need to know which users actually *saw* each variant, not just which were assigned.

Errors and performance metrics should carry the flag state too, so a regression can be attributed:

```ts
Sentry.setTag("flag.new-checkout", String(enabled));
```

Without this, a spike in errors is a mystery rather than an obvious signal to turn something off ([[28.13 - Frontend Observability]]).

## Keeping the code manageable

```tsx
// Scattered conditionals — hard to remove later
{flags.newNav ? <NewNav /> : <OldNav />}
{flags.newNav && <NewSidebar />}
{flags.newNav ? "New" : "Classic"}

// One boundary
{flags.newNav ? <NewLayout /> : <ClassicLayout />}
```

Branching once at the highest sensible level makes removal a matter of deleting one branch and one component tree. Flags sprinkled through a component are the reason old flags never get removed — nobody is confident they found every reference.

Naming conventions help removal:

```
release.checkout-v2
experiment.pricing-page-headline
ops.recommendations-enabled
```

The prefix communicates expected lifetime at a glance.

## Flag debt

Every unremoved flag is a branch that must keep working, a test matrix that doubles, and a path nobody exercises.

Practical controls:

- **An expiry date on every release and experiment flag**, with a CI warning past it
- **An owner** recorded with the flag
- **A grep in CI** for flags no longer present in the provider, and vice versa
- **Removal as part of the definition of done**, not a follow-up ticket

Ten stale flags mean 1,024 theoretical code paths. Nobody tests that, so most of them are untested by definition.

## Failure modes

**The flag service is down.** Every call must have a local default, and the SDK should serve the last known values from cache. A flag service outage taking down the product is an avoidable single point of failure.

```ts
const flags = { ...DEFAULTS, ...cached, ...remote };
```

**Both paths must work.** With a runtime flag, the disabled branch still ships and must not error — a common bug is the new code path importing something the old one needs.

**Testing both.** Tests should cover both variants, at minimum for release flags:

```ts
test.each([true, false])("checkout works with newCheckout=%s", (enabled) => {
  render(<Checkout />, { flags: { newCheckout: enabled } });
});
```

## Build or buy

Managed services — LaunchDarkly, Statsig, PostHog, Unleash, GrowthBook — provide targeting rules, a UI for non-engineers, audit logs, experiment analysis and SDK caching. That last set is what makes a homegrown solution expensive to match.

A minimal in-house version is a JSON file served from a CDN with a short TTL, plus deterministic bucketing. Adequate for release flags and kill switches; inadequate for experimentation, where the statistical analysis is the hard part.

The decision usually turns on whether product and growth teams need to control flags without engineering involvement.

## How senior engineers actually use this

**They classify every flag by kind** and record an owner and expiry.

**They branch at one boundary** rather than sprinkling conditionals.

**They bootstrap flags server-side or at the edge**, so there is no variant flash.

**They bucket deterministically on flag key plus user id**, so cohorts are stable and uncorrelated.

**They tag errors and metrics with flag state**, making regressions attributable.

**They treat flag removal as part of shipping**, not as cleanup.

## Common pitfalls

- Flash of the wrong variant from client-side evaluation.
- Random bucketing per session, ruining experiment data.
- Bucketing on user id alone, so the same cohort gets every experiment.
- Flags scattered through components, making removal risky.
- No local defaults, so a flag service outage breaks the app.
- The disabled path never tested.
- Flags never removed, producing an untestable combinatorial space.
- Permission gating implemented as feature flags.

## Interview angle

"How would you roll out a risky feature" is where this belongs. The core answer is decoupling deploy from release: ship the code disabled, enable progressively with deterministic bucketing, and treat a problem as a flag toggle rather than a rollback. The details that mark experience: the variant flash from client-side evaluation and how server or edge bootstrapping fixes it, hashing flag key plus user id so cohorts stay stable and uncorrelated, and flag debt as a real cost requiring owners and expiry dates.
