# Capacity Planning and Load Testing

#backend #reliability #performance

> **In one line:** Find the load at which your system stops behaving, work out which resource ran out, and size for the peak you will actually see — not the average.

---

## The Idea

```
"Can we handle Black Friday?"
```

Answering it requires three things:

| Question | |
|---|---|
| **What is our current capacity?** | Measured, not assumed |
| **What is the expected load?** | Peak, not average |
| **What breaks first?** | The bottleneck, not a guess |

⚠️ **Most capacity planning is arithmetic on averages, and traffic is not average.** A service handling 1,000 rps on average may see 8,000 rps for ten minutes a day.

💡 **Size for the peak, and know what happens beyond it** — which is what load shedding is for ([[11.4 - Backpressure and Load Shedding]]).

---

## Little's Law

The one piece of theory worth knowing.

```
L = λ × W

L = concurrent requests in the system
λ = arrival rate (requests/second)
W = average time in the system (seconds)
```

```
1,000 rps × 0.05s = 50 concurrent
1,000 rps × 0.50s = 500 concurrent      ← 10× latency, 10× resources
```

💡 **Latency and required concurrency are directly proportional**, which is why a slow dependency exhausts your workers ([[11.1 - How Systems Fail]]).

**Use it to size:**

```
Target: 2,000 rps at 100ms p99
Required concurrency: 2,000 × 0.1 = 200
Workers per pod: 8
→ 25 pods, minimum, with zero headroom
```

⚠️ **Size on p99, not the mean.** A service with a 20ms mean and a 300ms p99 has occasional requests occupying a worker 15× longer, and mean-based sizing produces periodic saturation.

## Finding the Bottleneck

```
Increase load until something breaks. Identify what.
```

| Resource | Symptom | Check |
|---|---|---|
| **CPU** | Latency rises with utilisation | Process CPU, throttling |
| **Memory** | OOM kills, GC pressure | RSS, working set |
| **Connection pool** | Requests wait, throughput plateaus | Pool wait time ([[06.9 - Connection Pooling and PgBouncer]]) |
| **Database** | Query latency rises | Active connections, lock waits |
| **Network / file descriptors** | Connection errors | `ulimit`, conntrack table |
| **Downstream service** | Your latency mirrors theirs | Their metrics |
| **The event loop** | Everything slows together | Loop lag ([[01.12 - Profiling and Debugging Async Services]]) |

💡 **The bottleneck is almost never the thing people assume.** In a Python backend it is usually the database connection pool or the event loop, not CPU.

⚠️ **Fixing the wrong bottleneck produces no improvement**, and it happens constantly — adding pods to a service whose bottleneck is the database makes the database worse ([[11.1 - How Systems Fail]]).

### The throughput curve

```
Throughput
    │        ╭──────────╮
    │      ╱             ╲          ← congestion collapse
    │    ╱                 ╲
    │  ╱                     ╲
    └────────────────────────────► Offered load
       ▲ knee        ▲ saturation
```

💡 **Three regions**: linear (adding load adds throughput), the knee (latency rises, throughput plateaus), and collapse (throughput *falls* as load increases).

⚠️ **Operating past the knee is where metastable failure lives.** Find the knee, and set your load shedding threshold below it.

## Load Testing

### The four kinds

| Test | Question |
|---|---|
| **Load** | Does it handle expected peak? |
| **Stress** | Where does it break, and how? |
| **Soak** | Does it degrade over hours? |
| **Spike** | Does it survive a sudden 10× and recover? |

⚠️ **Most teams only run the first**, which tells you the least. **Stress and soak find the problems.**

💡 **Soak tests find leaks, connection exhaustion, disk fill, and unbounded caches** — none of which appear in a ten-minute load test ([[08.9 - Celery in Production]]).

**Spike tests find metastable failure**, which a gradual ramp never triggers.

### Writing one that means something

```python
# k6
export const options = {
  stages: [
    { duration: '2m', target: 100 },     // warm up
    { duration: '5m', target: 100 },     // steady
    { duration: '2m', target: 1000 },    // ramp
    { duration: '10m', target: 1000 },   // sustain
    { duration: '2m', target: 0 },       // ramp down — watch recovery
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],
    http_req_failed: ['rate<0.01'],
  },
};
```

⚠️ **Realistic load is not one endpoint at full rate.** Model the actual mix:

```
60%  document reads
20%  search
10%  list views
 8%  writes
 2%  exports (expensive)
```

💡 **The 2% of expensive requests often determines your capacity**, and a test hitting only the cheap endpoint gives you a number that is wrong by an order of magnitude.

**Also model the data distribution:**

```python
# ❌ Every request hits the same document — 100% cache hit
doc_id = "doc_1"

# ✅ Zipfian, like real traffic
doc_id = zipf_sample(all_docs, alpha=1.2)
```

⚠️ **A load test with a 100% cache hit rate measures your cache, not your system.** Real traffic has a long tail that misses.

### Test against production-shaped data

```
10,000 rows:    every query is fast, every index fits in memory
10,000,000:     plans change, indexes do not fit, latency is different
```

⚠️ **A load test against a small dataset gives you a number that does not survive contact with production** ([[06.4 - Reading EXPLAIN ANALYZE]]).

💡 **Seed to production scale, or at least to the point where the working set exceeds memory.** That cliff is what you need to know about.

## In Production

### Measure your actual peak

```sql
SELECT date_trunc('minute', ts) AS minute, count(*) AS rps
FROM request_log
GROUP BY 1 ORDER BY rps DESC LIMIT 20;
```

```python
peak_to_mean_ratio = p99_minute_rps / mean_rps
```

💡 **The peak-to-mean ratio is the number that determines your headroom.** A ratio of 3 means sizing for the mean gives you a third of what you need at peak.

⚠️ **Look at minute granularity, not hourly.** An hourly average smooths away the ten-minute spike that actually breaks you.

### Headroom

```
Required capacity = peak × safety_factor
```

| Factor | Reason |
|---|---|
| **1.0** | Peak, exactly. No margin |
| **1.5** | Growth, and error in your estimate |
| **2.0** | Plus the ability to lose a zone |
| **N/(N-1)** | To survive losing one of N zones |

💡 **Three zones means you need 1.5× to survive losing one**, because the remaining two must absorb the third's traffic. **That is the most commonly forgotten multiplier.**

⚠️ **Autoscaling is not a substitute for headroom.** Scaling up takes 30–120 seconds — image pull, startup, cache warm, readiness — and a spike arrives in seconds.

**Headroom covers the scaling delay.** Size the baseline to survive a spike long enough for autoscaling to catch up.

### Scaling limits

```
Pods:                easy, until you hit the next limit
Database connections: max_connections ([[06.9 - Connection Pooling and PgBouncer]])
Database CPU:        vertical scaling has a ceiling
Third-party quotas:  a hard cap you do not control
Kafka partitions:    consumer parallelism ceiling ([[09.1 - Queue vs Log]])
```

⚠️ **Scaling one tier moves the bottleneck to the next.** Doubling pods without raising PgBouncer's pool size means twice the pods waiting on the same connections.

💡 **Write down the scaling ladder**: at what request rate does each tier become the constraint, and what is the fix at each step? That document is what turns "we need to scale" into a plan.

```
1,000 rps   → current, fine
3,000 rps   → pods 10 → 30, PgBouncer pool 25 → 50
8,000 rps   → add read replicas, route reads
20,000 rps  → partition documents by org ([[06.13 - Partitioning and Sharding]])
```

### Cost

```
cost_per_request = monthly_infra_cost / monthly_requests
```

💡 **Knowing your cost per request turns capacity from an engineering question into a business one.** "Doubling capacity costs $4,000/month" is a decision someone can make.

⚠️ **Track it per endpoint.** One expensive endpoint often dominates cost while being a small fraction of traffic — and it is usually the one worth optimising or rate limiting ([[11.5 - Rate Limiting and Quotas]]).

### Continuous load testing

```yaml
# Nightly, against staging with production-shaped data
schedule: "0 2 * * *"
thresholds:
  p99_latency: 500ms
  error_rate: 1%
```

💡 **A nightly load test catches performance regressions before they ship.** A change that doubles a query's cost is invisible in unit tests and obvious in a load test.

⚠️ **It only works if the environment and data are stable.** A test against an environment someone reseeded yesterday produces noise, and noise gets ignored.

### Monitoring capacity, not just health

```python
capacity_utilisation.labels(resource="workers").set(in_use / total)
capacity_utilisation.labels(resource="db_pool").set(in_use / total)
capacity_utilisation.labels(resource="cpu").set(usage / limit)
headroom_ratio.set(current_rps / measured_capacity)
```

💡 **`headroom_ratio` above 0.7 is the signal to scale**, and it is a better trigger than latency — which only rises after you are already in trouble.

⚠️ **Alert on trend, not just threshold.** "Utilisation has risen 10% week over week" gives you weeks to act; "utilisation is at 95%" gives you minutes.

### Conduit's capacity model

| Tier | Capacity | Bottleneck at |
|---|---|---|
| Gateway | 5,000 rps | CPU |
| Document service | **1,200 rps** | **Database pool** |
| Search | 3,000 rps | Search backend CPU |
| Ingestion workers | 40 docs/min | **Embedding API quota** |
| Postgres | 2,500 queries/sec | CPU |

💡 **The document service is the binding constraint at 1,200 rps**, and the bottleneck is the connection pool — not CPU, not the database itself.

⚠️ **The ingestion ceiling is a third-party quota**, which no amount of scaling fixes. **That is worth knowing before promising a customer a bulk import.**

```
Measured peak:        800 rps
Peak-to-mean ratio:   3.2
Zones:                3 → need 1.5× to lose one
Required:             800 × 1.5 = 1,200 rps
Current capacity:     1,200 rps
Headroom:             0%              ← ⚠️
```

**The model says Conduit is at exactly its capacity with no margin**, which is the kind of conclusion this exercise exists to produce.

## Codebase

**Repo:** `grafana/k6`, `locustio/locust`, `google/sre` (docs)

**Question to answer:** How does k6 model virtual users and arrival rate, and why does the distinction matter? Then: how does Google approach capacity planning, and what do they mean by "demand forecasting"?

**Read, in order:**

1. `k6/lib/executors/` — **`constant-arrival-rate` versus `constant-vus`.** **The answer to the first question and it is important**: VU-based tests reduce load when the system slows, hiding the problem; arrival-rate tests keep pushing, which is what real traffic does
2. `k6/lib/executors/ramping_arrival_rate.go` — how a ramp is scheduled, and what happens when the system cannot keep up
3. `locustio/locust/env.py` and `runners.py` — the alternative model, and why its default is VU-based
4. **Google SRE Book — "Software Engineering in SRE"** and the capacity planning chapter — **demand forecasting, provisioning, and the relationship to SLOs** ([[12.2 - SLI SLO and Error Budgets]])
5. **Google SRE Workbook — "Managing Load"** — the practical version

💡 The arrival-rate versus VU distinction is the single most important load testing insight. **A VU-based test with 100 users on a system that slows down sends *fewer* requests, so throughput looks stable while latency climbs.** An arrival-rate test keeps sending 1,000 rps regardless — which is what actually happens in production, and it is how you find the collapse region.

**Part 1 — VU versus arrival rate.** The same system, tested both ways, pushed past capacity.

**Chart throughput and latency for both.**

**The VU-based test should show throughput plateauing and latency stable-ish; the arrival-rate test should show throughput collapsing.** That difference is why the executor choice matters, and most teams use the one that hides the problem.

**Part 2 — Find the knee.** Ramping arrival rate from 100 to 5,000 rps against production-shaped data with a realistic endpoint mix and Zipfian access.

**Chart throughput, p50, p99 and error rate against offered load.**

**Identify the three regions and mark the knee.** That number is your capacity.

**Part 3 — Identify the bottleneck.** At the knee, capture: CPU per pod, memory, connection pool utilisation and wait time, database active connections and lock waits, event loop lag, and downstream latency.

**Name the bottleneck.** Then remove it — raise the pool, add an index, whatever it is — and **re-run.**

**Repeat four times**, building the ladder: what breaks at each level and what fixes it.

**Part 4 — Realistic mix matters.** Run the stress test twice: once hitting only the cheapest endpoint, once with the realistic mix including 2% exports.

**Compare the capacity numbers.** They should differ substantially.

Then vary the expensive endpoint's share — 0%, 1%, 5%, 10% — and chart capacity against it. **That curve tells you how much an expensive feature costs your capacity.**

**Part 5 — Data distribution matters.** The same test with every request hitting one document, and with Zipfian access across a million.

**Compare cache hit rate and capacity.** The single-document version will report a capacity you cannot achieve.

**Part 6 — Soak.** Four hours at 70% of the measured capacity.

Chart over the whole run: memory, connections, disk, latency, and error rate.

**Look for anything that only rises.** Memory that grows and never falls is a leak; connections that grow are a leak too ([[08.9 - Celery in Production]]).

**Part 7 — Spike and recovery.** A sudden 10× for 60 seconds, then back to baseline.

**Measure time to recover.** If it does not recover, you have found metastable failure ([[11.1 - How Systems Fail]]).

Then add load shedding below the knee and repeat. **Confirm it never enters the state.**

**Part 8 — The model.** Compute:

- Little's Law sizing for your target
- Your actual peak-to-mean ratio from production or simulated traffic
- Headroom required for growth and zone loss
- Cost per request, and per endpoint

**Write `MODEL.md`**: current capacity, required capacity, headroom, the scaling ladder, and the cost of each step.

**Then answer the question honestly: can you handle 3× current traffic, and what would it cost?**

**Done when:**
- Your VU-versus-arrival-rate charts show why the executor matters
- You have identified the knee with production-shaped data and a realistic mix
- Four bottlenecks are found and removed, in order, with the ladder written
- You know how much capacity the expensive endpoint costs
- A soak test found something that only rises, or proved nothing does
- A 10× spike either recovers or reveals metastable failure
- `MODEL.md` answers "can we handle 3×" with a number and a cost
