# The Call Stack

The call stack is the data structure the engine uses to track where it is in your program. It is a **LIFO** stack — last in, first out, like a stack of plates: the most recently added item is the first removed. Each entry is a **stack frame** holding one execution context.

There is exactly one call stack per JavaScript thread. That single fact is the mechanical reason JavaScript is single-threaded.

## How frames push and pop

```js
function third() {
  console.log("in third");
}

function second() {
  third();
}

function first() {
  second();
}

first();
```

Stack over time:

```
[global]
[global, first]
[global, first, second]
[global, first, second, third]
[global, first, second]        third returns
[global, first]                second returns
[global]                       first returns
```

The engine only ever executes the frame at the top. When a function returns, its frame is popped and its local variables become unreachable — unless a closure still holds a reference to them, which is exactly what [[02.3 - Closures]] describes.

## Reading a stack trace

An error captures the stack at the moment it was thrown, top frame first.

```js
function parseConfig(raw) {
  return JSON.parse(raw);
}

function loadSettings() {
  return parseConfig(undefined);
}

loadSettings();
```

```
SyntaxError: "undefined" is not valid JSON
    at JSON.parse (<anonymous>)
    at parseConfig (config.js:2:15)
    at loadSettings (config.js:6:10)
    at config.js:9:1
```

Read it top-down as "where it broke", bottom-up as "how we got here". The most useful line is usually the topmost frame that belongs to *your* code, not a library.

Two practical notes. `Error.captureStackTrace` (V8-specific) lets you hide wrapper frames when building custom error classes — useful in an SDK or API client so consumers see their own call site. And `Error.stackTraceLimit` defaults to 10 frames in V8; raising it during debugging surfaces deeper chains.

## Stack overflow

The stack has a fixed size, typically around 10,000–15,000 frames depending on browser and frame size. Exceeding it throws:

```js
function recurse(n) {
  return recurse(n + 1);
}
recurse(0); // RangeError: Maximum call stack size exceeded
```

Real causes are rarely this obvious. The usual culprits are a recursive tree walk over a structure that turns out to be cyclic, two functions that call each other through an unexpected path, or a React component that renders itself without a termination condition.

JavaScript engines do **not** implement tail-call optimization in practice — the technique of reusing a stack frame when a function's last action is calling another function. It is in the ES2015 spec but only Safari ever shipped it. So deep recursion must be rewritten iteratively:

```js
function flattenTree(root) {
  const out = [];
  const stack = [root];

  while (stack.length) {
    const node = stack.pop();
    out.push(node.value);
    if (node.children) stack.push(...node.children);
  }

  return out;
}
```

Moving recursion onto an explicit array turns a stack-depth limit into a heap-size limit, which is orders of magnitude larger.

## Async work leaves the stack

This is the crucial connection to the rest of this section:

```js
function fetchUser() {
  setTimeout(() => {
    throw new Error("boom");
  }, 0);
}

try {
  fetchUser();
} catch (e) {
  console.log("caught"); // never runs
}
```

By the time the callback executes, `fetchUser` and the `try` block have long been popped. The callback runs on a fresh, nearly empty stack, so the `catch` cannot see it. `try/catch` only guards synchronous work on the current stack — the reason `async/await` exists is to make asynchronous errors catchable again ([[04.4 - async await]]).

Modern DevTools stitch async frames together ("Async call stack") so a trace through a promise chain still shows the originating call site, but that is a debugging convenience, not runtime behavior.

## How senior engineers actually use this

**They use the stack to find the real caller.** In a large codebase, `console.trace()` inside a suspicious function answers "who is calling this and why" faster than searching the code, especially when calls come through a framework.

**They wire stack traces into error reporting.** Tools like Sentry group errors by stack signature. This only works if production builds ship source maps ([[27.7 - Source Maps]]); without them, every trace points into minified `chunk-4f2a.js` and is useless.

**They watch for long frames rather than deep ones.** Stack depth is rarely a production problem. A single frame doing 300 ms of synchronous work is, because nothing else can run while it sits on the stack. The Performance panel's flame chart is literally a picture of the call stack over time — width is duration, depth is nesting.

**They avoid recursion over user-supplied data.** Any recursive function that walks JSON, a DOM subtree or a comment tree can be handed pathological input. Either bound the depth explicitly or use an iterative walk.

## Common pitfalls

- Wrapping async code in `try/catch` and assuming errors are caught. They are not, unless you `await`.
- Losing the original stack by re-throwing a new error: `throw new Error("failed")` inside a `catch` discards the cause. Use `throw new Error("failed", { cause: err })` instead.
- Reading the top frame of a trace and stopping there, when it is library code and the actual bug is three frames down in your own module.
- Assuming recursion is free because the algorithm is elegant. Depth is bounded and the limit is lower than people expect.

## Interview angle

Expect "what is the call stack" and "what causes a stack overflow". Strong answers connect it forward: one stack means one thing executes at a time, which is why long synchronous work freezes the UI, and why asynchronous callbacks must wait for the stack to empty before the event loop can run them — the setup for [[01.4 - The Event Loop]].
