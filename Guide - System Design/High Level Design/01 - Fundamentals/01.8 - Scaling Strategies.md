# Scaling Strategies: Horizontal vs Vertical

> **Revision tags:** #fundamentals #scaling  
> **Related:** [[01.4 - Core Properties]] | [[01.11 - Distributed Concepts]] | [[01.9 - Architecture Styles]]

---

## Vertical Scaling (Scale Up)

Add more resources to a single machine: more CPU cores, more RAM, faster disk, more network bandwidth.

```
Before:  [Server: 4 CPU, 16GB RAM]
After:   [Server: 32 CPU, 256GB RAM]
```

**Pros:**
- Simple — no code changes, no architectural changes
- No distributed systems complexity
- ACID transactions remain easy (single machine)
- Good for stateful systems

**Cons:**
- Hard ceiling — the largest cloud VM is still finite
- Expensive per unit at the high end (price scales nonlinearly)
- Single point of failure — one big machine, one point of failure
- Downtime to upgrade (usually)

**When it's the right answer:**  
Databases are often the first thing to scale vertically because they're hard to distribute. A larger Postgres instance is often cheaper operationally than a distributed SQL cluster.

---

## Horizontal Scaling (Scale Out)

Add more machines, distribute load across them.

```
Before:  [Server A]
After:   [Server A] [Server B] [Server C]
         Load Balancer distributes requests
```

**Pros:**
- Theoretically unlimited — add as many machines as needed
- Commodity hardware (cheap, replaceable)
- High availability — losing one machine doesn't stop the system
- Cost-efficient at large scale

**Cons:**
- Requires statelessness or distributed state management
- Network overhead between nodes
- Distributed systems complexity (consensus, consistency, partitioning)
- Debugging is harder

**Prerequisite for horizontal scaling of stateful services:**  
Move state out of the application into a shared layer (database, Redis, distributed cache). Otherwise requests from the same user must always hit the same server (sticky sessions).

## The Scaling Hierarchy

When your system is slow or overloaded, apply solutions in this order (cheapest to most complex):

```
1. Optimize the code           (free, if you have the bug)
2. Add caching                 (cheap, high impact)
3. Scale vertically            (simple, finite)
4. Read replicas / CDN         (moderate complexity)
5. Scale horizontally          (significant complexity)
6. Shard / partition           (high complexity)
7. Redesign architecture       (very high cost)
```

Don't jump to distributed sharding before adding a Redis cache. Most systems never need step 6.

## Scaling Different Tiers

### Web / API Tier

Easiest to scale horizontally. Stateless request handling is trivially distributed.

```
Load Balancer → [API Server 1]
              → [API Server 2]
              → [API Server 3]
```

Auto-scaling groups (AWS ASG, GKE HPA) do this automatically.

### Database Tier

Hardest to scale. The state makes distribution expensive.

**Read-heavy workloads:**
- Add read replicas (replicate writes to multiple read-only nodes)
- Add a caching layer (Redis) in front

**Write-heavy workloads:**
- Vertical scaling first (bigger Postgres instance)
- Then: sharding / partitioning
- Or: switch to a write-optimized NoSQL store

**General purpose:**
- Connection pooling (PgBouncer) to handle many app connections to fewer DB connections
- Read/write splitting

### Cache Tier

Redis scales horizontally via **Redis Cluster** (hash-slot-based partitioning).

### Compute / Worker Tier

Stateless workers (e.g., Kafka consumers, job processors) scale horizontally trivially — add more instances.

## Autoscaling

Modern systems don't manually provision servers. They autoscale based on load signals:

- **CPU-based:** Add instances when CPU > 70% for 2 minutes
- **Request-rate-based:** Add instances when RPS > threshold
- **Queue-depth-based:** Add workers when queue depth > N messages
- **Scheduled:** Pre-scale before known traffic spikes (Black Friday)

**Key concern:** Autoscaling has latency — it takes 1-3 minutes to spin up new instances. Pre-warming is needed for predictable spikes.

## Stateful vs Stateless Scaling Complexity

| Component | Scaling Difficulty | Reason |
|---|---|---|
| API servers (stateless) | Very easy | Any instance handles any request |
| Cache servers | Easy | Hash partitioning, no consistency required |
| Search indexes | Moderate | Sharded indexes, replicated for reads |
| Message brokers | Moderate | Partition assignment, consumer group coordination |
| Relational databases | Hard | ACID + consistency across shards is complex |
| Distributed transactions | Very hard | Requires consensus protocols |

---

## Key Interview Point

When asked "how would you scale this system?" — walk through the tiers:

1. **Which tier is the bottleneck?** (Compute? DB? Network?)
2. **Is it read or write heavy?**
3. **What's stateful?** (That's the hard part)
4. **What's the order of operations?** (Cache before shard)

Don't immediately jump to "we'd shard the database." Show you know the cheaper options first.
