# Code Splitting and React.lazy

Code splitting breaks a bundle into chunks loaded on demand. It is the highest-leverage frontend performance technique, because the fastest JavaScript is the JavaScript you never ship ([[13.1 - The Critical Rendering Path]]).

## React.lazy

```jsx
import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

<Suspense fallback={<Skeleton />}>
  <Dashboard />
</Suspense>
```

`lazy` takes a function returning a promise for a module with a **default export**. React calls it on first render, suspends until it resolves, then renders the component ([[19.4 - Suspense]]).

Named exports need remapping:

```jsx
const Chart = lazy(() =>
  import("./charts").then(m => ({ default: m.BarChart }))
);
```

The `Suspense` boundary is mandatory. Without one, React throws.

## Where to split

**Routes first.** Natural boundaries, and the payoff is proportional — a user landing on `/login` should not download the admin dashboard.

```jsx
const routes = [
  { path: "/", element: <Home /> },
  { path: "/dashboard", Component: lazy(() => import("./Dashboard")) },
  { path: "/admin", Component: lazy(() => import("./Admin")) },
];
```

Route-level splitting typically cuts the initial bundle by 40–70% in a multi-page application, and it requires no per-component decisions ([[23.5 - Lazy Routes]]).

**Heavy dependencies second.** A library used on one screen should not be in the main bundle:

```jsx
async function exportPdf(data) {
  const { jsPDF } = await import("jspdf");        // ~300KB
  new jsPDF().text(data).save();
}

const Editor = lazy(() => import("./RichTextEditor"));   // ~500KB
const Chart = lazy(() => import("./AnalyticsChart"));    // ~200KB
```

Rich text editors, charting libraries, PDF generators, date pickers, map SDKs, syntax highlighters and code editors are the usual suspects. Check the bundle analyzer for what is actually large ([[19.7 - Bundle Analysis and Optimization]]).

**Modals and drawers third.** Content that is conditionally mounted and often never opened.

## Where not to split

- Anything rendered on the initial screen — you add a round trip to the critical path
- Small modules; a 3KB chunk is not worth a request
- Components inside a tight interaction loop, where the loading flash is worse than the bytes

A workable threshold: split when the chunk exceeds roughly 30KB gzipped and is not needed for first paint.

Over-splitting has real costs — more HTTP requests, duplicated module boilerplate across chunks, and a larger total payload.

## Prefetching on intent

Splitting moves the delay from load time to interaction time. Prefetching recovers most of it:

```jsx
const Settings = lazy(() => import("./Settings"));
const preloadSettings = () => import("./Settings");

<Link
  to="/settings"
  onMouseEnter={preloadSettings}
  onFocus={preloadSettings}
>
  Settings
</Link>
```

Calling `import()` twice with the same specifier does not fetch twice — the module registry caches by resolved URL. The hover call warms the cache and the render resolves instantly.

Hover-to-click is typically 100–300ms, which covers most chunk downloads. Add `onFocus` so keyboard users get the same benefit.

For higher-confidence predictions, use `IntersectionObserver` to prefetch when a link scrolls into view, or a bundler prefetch hint ([[29.2 - Prefetching and Preloading]]):

```jsx
import(/* webpackPrefetch: true */ "./Settings");
```

## Handling load failures

Chunk loads fail. The most common cause is a deploy: the user's open tab references hashed filenames that no longer exist on the CDN ([[15.7 - HTTP Caching and CDNs]]).

```jsx
function lazyWithRetry(importFn, retries = 2) {
  return lazy(async () => {
    for (let i = 0; i <= retries; i++) {
      try {
        return await importFn();
      } catch (err) {
        if (i === retries) throw err;
        await new Promise(r => setTimeout(r, 500 * 2 ** i));
      }
    }
  });
}
```

And a global recovery for the stale-manifest case:

```jsx
window.addEventListener("vite:preloadError", (e) => {
  e.preventDefault();
  window.location.reload();
});
```

Without this, users with a long-lived tab see a blank screen on their next navigation after a deploy. It is one of the most common production issues in code-split SPAs, and it does not appear in testing because deploys are rare in development.

Wrap lazy boundaries in an error boundary so a failure shows a retry rather than a white page ([[22.1 - Error Boundaries]]):

```jsx
<ErrorBoundary fallback={<ReloadPrompt />}>
  <Suspense fallback={<Skeleton />}>
    <Dashboard />
  </Suspense>
</ErrorBoundary>
```

## Avoiding layout shift

```jsx
<Suspense fallback={<div style={{ minHeight: 400 }} />}>
```

A fallback that is much smaller than the loaded content causes a large CLS penalty ([[13.5 - Core Web Vitals]]). Skeletons should approximate the real dimensions.

## Bundler behavior

Every `import()` is a split point. The bundler emits the target and its unique dependencies as a chunk; shared dependencies go into a common chunk rather than being duplicated.

Bundlers need enough static information to know what to emit:

```jsx
await import(userPath);                      // cannot analyze
await import(`./locales/${lang}.js`);        // emits one chunk per matching file
```

The template form works because the static prefix bounds the possibilities, but forty locales produce forty chunks — usually correct for locales, rarely correct elsewhere.

Verify the result with the analyzer rather than assuming: a single shared import can pull a "lazy" dependency into the main bundle, silently undoing the split.

## React 19 and Server Components

In a Server Components architecture, much of this shifts. Server Component code never ships to the client at all, so the split happens at the server/client boundary rather than through explicit `lazy` calls ([[22.8 - Server Components]]).

`React.lazy` remains relevant for client-side conditional loading — modals, heavy widgets, editor components.

## How senior engineers actually use this

**They split by route first and by heavy dependency second**, and stop there unless the analyzer shows more.

**They always pair splitting with prefetching on intent**, since otherwise the delay just moves.

**They handle chunk-load failure globally**, with reload-on-stale-manifest.

**They verify with the bundle analyzer**, because assumptions about what landed in which chunk are frequently wrong.

**They size skeletons to match content** to avoid trading a bundle-size win for a CLS regression.

## Common pitfalls

- Forgetting the `Suspense` boundary.
- Named exports without the `.default` remapping.
- No error boundary, so a failed chunk renders a blank screen.
- Stale chunk references after a deploy.
- Lazy-loading something rendered immediately, adding a spinner for no benefit.
- Over-splitting into dozens of tiny chunks.
- Undersized fallbacks causing layout shift.

## Interview angle

"What is code splitting and how do you implement it in React" wants `React.lazy` plus `Suspense`, dynamic `import()` creating bundler split points, and route-level splitting as the default strategy. The details that stand out are prefetching on hover to recover the interaction latency, and handling chunk-load failures after a deploy — both are things you only learn from running a code-split app in production.
