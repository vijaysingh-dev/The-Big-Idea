# Phase 7: Observability and SLOs

#backend #project #capstone

> **In one line:** You built defences in phase 6 that you cannot see working — this phase makes the system's behaviour visible, sets targets you are willing to be held to, and proves someone else can diagnose an incident with it.

---

## The Problem Phase 6 Created

```
Seven dependencies, four degradation levels, circuit breakers,
load shedding, and no way to tell whether any of it is working.

"Where is document X?"           → five log searches
"Is the system healthy?"          → no answer
"Which tenant is causing this?"   → no answer
```

⚠️ **A system that degrades silently looks healthy.** Error rates low, latency fine, users getting a worse product ([[11.6 - Graceful Degradation]]).

---

## What You Build

### The four SLOs

| Journey | SLI | SLO |
|---|---|---|
| Document read | 2xx/3xx/4xx in < 500ms | 99.5% |
| Search | Results in < 1s | 99.0% |
| **Upload to searchable** | **Indexed within 5 minutes** | **95.0%** |
| Ingestion correctness | Indexed without error | 99.5% |

💡 **Four SLIs of four types** — availability, latency, freshness, correctness ([[12.2 - SLI SLO and Error Budgets]]).

⚠️ **The "good" definition must be precise and written down:**

```
429 → not a failure. Working as designed
4xx → not a failure
499 (client disconnect) → not a failure
Degraded response → SUCCESS, tracked separately
```

**The degraded case needs a decision.** A document page loading without related documents is a success — **otherwise a minor degradation burns the same budget as a total outage.**

```yaml
- record: sli:document_read_good:rate5m
  expr: sum(rate(http_requests_total{route="/v1/documents/:id",status!~"5.."}[5m]))
- record: slo:document_read:ratio_rate5m
  expr: sli:document_read_good:rate5m / sli:document_read_total:rate5m
```

💡 **Define SLIs as recording rules**, so dashboards, alerts and reports share one definition.

### Burn-rate alerting

```yaml
- alert: ErrorBudgetBurnFast
  expr: burn_rate_1h > 14.4 and burn_rate_5m > 14.4
  severity: page
- alert: ErrorBudgetBurnSlow
  expr: burn_rate_6h > 6 and burn_rate_30m > 6
  severity: page
- alert: ErrorBudgetBurnGradual
  expr: burn_rate_24h > 3 and burn_rate_2h > 3
  severity: ticket
```

⚠️ **The two-window requirement is what stops flapping.** A one-hour burn rate stays elevated after the incident ends; requiring the short window too means the alert resolves when the problem does.

### The trace, end to end

```
Browser → gateway → documents → object storage → Postgres
  → outbox → Kafka → ingestion → embedding API → Postgres → indexer
```

**The queue boundary must be crossed by hand:**

```python
carrier = {}
TraceContextTextMapPropagator().inject(carrier)
await conn.execute("INSERT INTO outbox (..., trace_context) VALUES (..., $1)",
                   json.dumps(carrier))
```

💡 **Use links rather than parent-child for the async portion.** A trace spanning twelve minutes is unwieldy, and most backends cap trace duration ([[12.3 - Instrumenting Conduit End to End]]).

**Add business identifiers to every span:**

```python
span.set_attribute("document.id", doc_id)
span.set_attribute("org.id", org_id)
```

⚠️ **This is the single most useful attribute in the system.** "Show me everything that happened to `doc_42`" becomes one query across all traces.

### The metrics that answer real questions

```python
# Pipeline
ingestion_stage_duration_seconds.labels(stage=...).observe(elapsed)
ingestion_oldest_pending_seconds.labels(stage=...).set(age)
document_time_to_searchable_seconds.observe(indexed_at - uploaded_at)

# Resilience — proving phase 6 works
circuit_state.labels(dep=...).set(0|1|2)
degraded_responses_total.labels(reason=...).inc()
requests_shed_total.labels(priority=...).inc()
retry_budget_consumed_ratio.labels(dep=...).set(r)
concurrency_in_use.labels(dep=...).set(n)

# Cost
embedding_tokens_total.inc(count)
db_rows_read_total.labels(route=...).inc(rows)
```

💡 **`degraded_responses_total` by reason names the dependency hurting users right now** — more actionable than a raw error rate.

⚠️ **`concurrency_in_use` per dependency rises before latency does**, because requests queue internally before they time out ([[11.1 - How Systems Fail]]).

### Per-tenant attribution, without cardinality

```python
sql = f"/* org:{org_id} */ SELECT ..."
log.info("stage completed", org_id=org_id, document_id=doc_id, stage=stage)
```

⚠️ **Never label a metric by tenant** — unbounded cardinality will take down your metrics backend ([[12.1 - Observability Recap and Gaps]]).

**Logs and traces carry the tenant; metrics carry the aggregate.**

### The dashboards

**1. Service health** — one screen, five seconds to answer "is anything wrong": request rate, error rate, latency by route, SLO burn, dependency circuit states, saturation.

**2. Pipeline health** — time-to-searchable percentiles, stacked stage durations, queue depth and oldest-age per stage, failure rate with DLQ counts.

**3. Cost** — tokens per day per org, rows read per endpoint, cost per document, top tenant by cost.

💡 **A stacked stage-duration chart that sums to time-to-searchable makes the bottleneck obvious at a glance**, and it is the panel you will look at most.

### The alerts that page

| Alert | Severity |
|---|---|
| SLO fast burn (14.4× / 1h) | **Page** |
| SLO slow burn (6× / 6h) | **Page** |
| Pipeline stalled (oldest-age > 15m) | **Page** |
| **Replication slot inactive** | **Page** |
| **`age(datfrozenxid)` > 1 billion** | **Page** |
| DLQ growing | Ticket |
| Circuit open > 5m | Ticket |
| Sustained degradation > 5% | Ticket |
| Job last-success stale | Ticket |
| Cost anomaly (2× the 7-day average) | Ticket |

💡 **Only five page.** Keeping the page list short is what prevents alert fatigue ([[11.10 - Incidents and Postmortems]]).

⚠️ **The two Postgres alerts are causes, not symptoms, and they belong here anyway** — the consequence is severe and nobody notices them otherwise.

### The absence alert

```python
job_last_success_timestamp.labels(job=...).set(time.time())
```

```yaml
- alert: JobNotRunning
  expr: time() - job_last_success_timestamp > 2 * expected_interval_seconds
```

⚠️ **A scheduled job that stops being scheduled never fails.** It is the quietest failure in a backend system ([[08.8 - Periodic Tasks and Distributed Cron]]).

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Four SLOs** | One per endpoint | Coverage of journeys, not surface area |
| **Search at 99.0%** | 99.5%, matching documents | It is optional and degrades |
| **Freshness at 95%** | 99% | Large files legitimately take longer |
| **Burn-rate alerting** | Threshold on error rate | Normalises across SLOs; catches both shapes |
| **Tail-based sampling** | Head-based at 1% | Keeps 100% of errors and slow requests |
| **Links for async spans** | One long parent-child trace | Twelve-minute traces are unusable |
| Tenant in logs, not metric labels | Per-tenant metrics | Cardinality |
| Degraded counted as success | Counted as failure | Otherwise degradation dominates the budget |

## What Will Go Wrong

### The cardinality explosion

⚠️ **Add `document_id` as a metric label and watch Prometheus fall over.**

**Reproduce it once** — series count, memory, query latency — **then remove it.** It is the most common self-inflicted observability outage ([[12.1 - Observability Recap and Gaps]]).

### The trace splits at the outbox

⚠️ **Without the trace context in the outbox row and the Kafka headers, one upload is two disconnected traces.**

**Break it deliberately and measure the diagnosis time difference.**

### Alert fatigue

⚠️ **Ten paging alerts becomes zero paging alerts within a month**, because people mute them.

**Count actionable versus non-actionable firings over two weeks. Anything below 50% actionable should be a ticket, not a page.**

### The observability bill

⚠️ **Logs usually dominate, and the volume scales with your traffic** ([[13.6 - Cost Awareness]]).

**Audit which metric series appear in any dashboard or alert.** Typically 40–60% do not. **Delete them.**

### Symptom versus cause alerts

```
❌  "CPU above 80%"                  fires constantly, rarely actionable
✅  "Document read SLO burning fast"  fires when users are affected
```

**Measure both over a week and count actionable firings.**

## Acceptance Criteria

```
□  Four SLIs as recording rules, with precise "good" definitions
□  Four weeks of baseline data; targets derived from it, not guessed
□  Burn-rate alerting with two windows; flapping eliminated, measured
□  One trace spans upload → outbox → Kafka → indexer, verified by breaking it
□  Business IDs on every span; "everything about doc X" is one query
□  Exemplars: p99 alert → slow trace in one click
□  Trace ID in every log line
□  Stacked stage chart sums to time-to-searchable
□  Per-tenant attribution from logs, with no tenant metric labels
□  Absence alert catches a job that silently stopped
□  Cardinality explosion reproduced and prevented
□  Tail sampling keeps 100% of errors; head-based comparison measured
□  Five questions answered by someone else, within target times
□  Observability cost measured and reduced deliberately
```

⚠️ **The "someone else" criterion is the real test.** Instrumentation you can use and nobody else can is not finished.

| Question | Target |
|---|---|
| Is the system healthy? | **5 seconds** |
| Where is document X? | **30 seconds** |
| Why was this request slow? | **60 seconds** |

## What You Should Be Able To Explain

```
"What are your SLOs and where did the numbers come from?"
  → Four, one of each type. Measured for four weeks with no targets,
     then set slightly above observed performance. Search is 99.0%
     rather than 99.5% because it degrades

"How do you know a deploy is bad?"
  → Burn-rate alerting on the SLOs, two windows so it does not flap.
     A fast burn pages within about five minutes

"Where is document 42?"
  → One trace query on document.id. Thirty seconds, including the
     asynchronous stages, because the outbox row carries the trace context

"Which customer is costing you money?"
  → Query tagging plus per-tenant token counting. org_7 costs $1,840
     a month against $499 of plan revenue

"What is wrong with this system now?"
  → It is deployed by hand, the image runs as root, and secrets are in
     environment variables. Phase 8
```

## Codebase

**Repo:** `open-telemetry/opentelemetry-python-contrib`, `slok/sloth`, `grafana/tempo`

**Question to answer:** How is trace context propagated through a broker, and how does tail-based sampling decide what to keep?

**Read, in order:**

1. `opentelemetry-python-contrib/instrumentation/.../aiokafka/` — **where headers are injected and extracted.** Then apply the same by hand to the outbox
2. `opentelemetry-python/.../trace/__init__.py` — `Link`, and when to use it instead of a parent
3. `slok/sloth/internal/alert/` — **the burn-rate windows and thresholds as code.** Makes the arithmetic concrete
4. `slok/sloth/internal/prometheus/` — one SLO definition generating SLI, budget and alert rules
5. `opentelemetry-collector-contrib/processor/tailsamplingprocessor/` — **why it buffers spans, and where the memory cost comes from**

💡 The Sloth rule generator is worth reading even if you write the rules by hand — **it shows exactly which recording rules an SLO needs**, and it is easy to miss one.

**Size:** 2 sessions.

## Exercise

**Drill 16.8 — Make it diagnosable by someone else**

```
conduit/phases/07/
├── slo/{recording_rules.yaml, definitions.md, baseline.md}
├── alerts/{burn_rate.yaml, absence.yaml, tuning.md}
├── tracing/{outbox_context.py, kafka_context.py, links.py, business_ids.py}
├── dashboards/{health.json, pipeline.json, cost.json}
├── questions/{q1..q5.md, TIMINGS.md}
├── cost/{volume_audit.py, RESULTS.md}
├── adr/{037-slos.md ... 040-sampling.md}
└── PHASE7.md
```

**Part 1 — Baseline before targets.** Instrument the four SLIs as recording rules with precise "good" definitions.

**Run for four weeks (or simulate four weeks of realistic traffic including incidents) with no targets.**

**Chart each distribution. Then set targets slightly above observed performance** and compute what the error budget would have been. **How many breaches?**

**Part 2 — Where you measure matters.** Compute document-read availability from application metrics, load balancer metrics, and a synthetic check.

**Inject a failure between the load balancer and the application.**

**Confirm the application-side SLI does not see it. Report the gap.**

**Part 3 — Burn-rate alerting, tuned.** Implement all three tiers.

**Replay your four weeks of data. Count true positives, false positives, and missed incidents.**

Then remove the second window from each rule and replay again. **Chart alert count with and without** — the flapping difference is the argument.

**Part 4 — The full trace.** Instrument the seven-hop path with trace context in the outbox row and Kafka headers, business IDs on every span.

**Confirm one connected trace (or a properly linked set).**

Then remove the outbox context and **confirm it splits. Screenshot both.**

**Then time the diagnosis of a slow ingestion in each case.**

**Part 5 — The cardinality explosion.** Add `document_id` as a metric label. Run realistic traffic.

**Measure series count, Prometheus memory and query latency over 30 minutes.**

**Remove it and confirm recovery.** Then audit which existing series appear in a dashboard or alert, **delete the rest, and report the volume reduction.**

**Part 6 — The silent job.** Stop a scheduled sync from running — do not make it fail, make it not run.

**Measure how long until anything notices.** Then add the absence alert and measure again.

**Part 7 — Sampling.** Tail-based with three policies against head-based at 1%, under load with a 2% error rate.

**Measure: fraction of errors captured, fraction of slow requests, storage volume, collector memory.**

**Head-based should miss most errors.**

**Part 8 — The five questions.** Have someone who did not build this answer each, timed, using only your dashboards.

**Record actual times in `TIMINGS.md`.** Fix whatever exceeds target and re-test.

**Part 9 — Cost.** Measure metric series, trace bytes and log bytes per day, with the cost of each.

**Apply the levers** — drop unqueried series, disable `DEBUG`, tighten sampling — **and report the reduction and what you gave up.**

**Done when:**
- Targets are derived from four weeks of baseline, not guessed
- Your measurement-point gap is quantified
- Two-window alerting demonstrably eliminates flapping your data produces
- One trace spans seven hops, verified by breaking the propagation
- A cardinality explosion is reproduced and prevented
- An absence alert catches a job that silently stopped
- Tail sampling keeps 100% of errors where head-based missed most
- Someone else answered all five questions within target times
- Observability cost is measured and deliberately reduced
