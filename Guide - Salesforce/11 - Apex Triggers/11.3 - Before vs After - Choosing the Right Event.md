# Before vs After - Choosing the Right Event

## The decision rule

**Is the work changing a field on the record being saved?**

Yes → **before trigger**. Assign directly to `Trigger.new`. No DML.

No → **after trigger**. Everything else: related records, roll-ups, notifications, async work.

That single question resolves most cases correctly.

## Why before is cheaper

A before trigger modifies the record while it is in memory, before it is written. The assignment costs nothing beyond the CPU of the assignment itself.

An after trigger updating the same record must issue DML, which **saves the record again** — running validation rules again, before triggers again, after triggers again, every flow again, and every roll-up again.

That is not a small inefficiency. It is doubling the entire save pipeline for something that could have been one line of memory assignment.

```java
// before update: one assignment, no DML
for (Warranty_Claim__c claim : Trigger.new) {
    claim.Region__c = claim.Asset__r?.Account?.BillingCountry;
}

// after update: a full second pass through the save pipeline
List<Warranty_Claim__c> toUpdate = new List<Warranty_Claim__c>();
for (Warranty_Claim__c claim : Trigger.new) {
    toUpdate.add(new Warranty_Claim__c(Id = claim.Id, Region__c = derived));
}
update toUpdate;   // re-enters everything
```

The second form also risks recursion, because the update fires the trigger again.

## What only before can do

**Modify the record with no DML.** The defining capability.

**Run before validation rules.** Before triggers execute at step 5 of the order of execution; validation rules at step 6. A before trigger can populate a field that a validation rule requires, and the validation passes.

This is genuinely useful for defaults, and it is also why a validation rule cannot assume a field was empty when the user submitted.

**Prevent a save with `addError`**, before anything is written.

## What only after can do

**See the record Id on insert.** Anything creating a child record, a share row, or a log entry referencing the record must be after insert.

**Access fields the platform populates on save** — auto-number, formula fields, and roll-up summaries are not available on the in-memory record in a before trigger.

**Perform DML on other objects safely.** Doing this in a before trigger works and is a poor idea: the triggering record is not yet saved, so a failure later in the pipeline rolls back the triggering record while the other DML has already been performed and may or may not roll back cleanly depending on the failure path.

**Query relationships reliably.** In a before insert trigger, relationship fields on `Trigger.new` are set but the related records cannot be traversed with `__r` notation, because the record has not been saved. You must query for them explicitly.

```java
// before insert: this is null, even though Asset__c is populated
String serial = claim.Asset__r?.SerialNumber;

// correct in a before trigger: query for the parents
Set<Id> assetIds = new Set<Id>();
for (Warranty_Claim__c claim : Trigger.new) {
    if (claim.Asset__c != null) {
        assetIds.add(claim.Asset__c);
    }
}
Map<Id, Asset> assets = new Map<Id, Asset>([
    SELECT Id, SerialNumber, AccountId FROM Asset WHERE Id IN :assetIds
]);
```

This catches people constantly. Relationship traversal on `Trigger.new` works in **after** triggers because the record was saved, and returns null in **before insert** because it was not.

## The self-update anti-pattern

The most common performance defect in Apex triggers, and the direct equivalent of the flow anti-pattern in [[07.4 - Before-Save vs After-Save Flows]]:

```java
// after update
List<Warranty_Claim__c> toUpdate = new List<Warranty_Claim__c>();
for (Warranty_Claim__c claim : Trigger.new) {
    toUpdate.add(new Warranty_Claim__c(
        Id = claim.Id,
        Approval_Tier__c = tierFor(claim.Claim_Amount__c)
    ));
}
update toUpdate;
```

Every instance of this should be a before trigger. Auditing an org for after triggers that update their own object is a reliable way to find easy performance improvements, and it usually finds several.

The exception: when the value depends on a field the platform populates during save — a formula, a roll-up, or the record Id itself. Then after is genuinely required, and a recursion guard is mandatory.

## A worked comparison

Requirement: when a claim is created or its amount changes, set the approval tier, stamp the region from the asset's account, and if the tier is Executive, create a task for the regional director.

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        switch on Trigger.operationType {
            when BEFORE_INSERT {
                ClaimService.applyDerivedFields(Trigger.new, null);
            }
            when BEFORE_UPDATE {
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
            }
            when AFTER_INSERT {
                ClaimService.createExecutiveReviewTasks(Trigger.new, null);
            }
            when AFTER_UPDATE {
                ClaimService.createExecutiveReviewTasks(Trigger.new, Trigger.oldMap);
            }
        }
    }
}
```

```java
public with sharing class ClaimService {

    public static void applyDerivedFields(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) {
        Set<Id> assetIds = new Set<Id>();
        for (Warranty_Claim__c claim : newClaims) {
            if (claim.Asset__c != null) {
                assetIds.add(claim.Asset__c);
            }
        }

        // querying parents explicitly, since __r traversal is unavailable in before insert
        Map<Id, Asset> assets = assetIds.isEmpty()
            ? new Map<Id, Asset>()
            : new Map<Id, Asset>([
                SELECT Id, Account.BillingCountry FROM Asset WHERE Id IN :assetIds
              ]);

        for (Warranty_Claim__c claim : newClaims) {
            claim.Approval_Tier__c = tierFor(claim.Claim_Amount__c);

            Asset asset = assets.get(claim.Asset__c);
            if (asset != null) {
                claim.Region__c = asset.Account?.BillingCountry;
            }
        }
    }

    public static void createExecutiveReviewTasks(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) {
        List<Task> tasks = new List<Task>();

        for (Warranty_Claim__c claim : newClaims) {
            Warranty_Claim__c prior = oldClaims == null ? null : oldClaims.get(claim.Id);

            // fires on the transition into Executive, not on every save of an Executive claim
            Boolean becameExecutive = claim.Approval_Tier__c == 'Executive'
                && (prior == null || prior.Approval_Tier__c != 'Executive');

            if (becameExecutive) {
                tasks.add(new Task(
                    WhatId = claim.Id,
                    Subject = 'Executive review required',
                    ActivityDate = Date.today().addDays(2),
                    OwnerId = claim.Approver__c
                ));
            }
        }

        if (!tasks.isEmpty()) {
            insert tasks;
        }
    }
}
```

The field assignments are before; the task creation is after, because it needs the claim's Id. Both services take collections and tolerate a null `oldClaims`, so the same method serves insert and update.

## Ordering within the pipeline

From [[07.13 - Order of Execution]]:

```
4.  Before-save flows
5.  Before triggers
6.  Validation rules
7.  Record saved, not committed
8.  After triggers
10. After-save flows
12. Roll-up recalculation
17. Commit
```

Two consequences worth holding:

**A before trigger overwrites a before-save flow**, because it runs later. If both write the same field, the trigger wins silently. This is the concrete reason for the one-mechanism-per-concern rule in [[07.1 - Automation Landscape and Tool Selection]].

**An after trigger cannot see a field set by an after-save flow**, because the flow runs later. Ordering assumptions between triggers and flows are a specific and confusing source of bugs.

## A checklist

Use **before** when:
- Setting a field on the triggering record
- Validating with `addError`
- Populating a field a validation rule requires
- Normalizing data — trimming, uppercasing, formatting

Use **after** when:
- The record Id is needed
- Creating or updating related records
- Recalculating a parent aggregate
- Sending a notification or publishing an event
- Enqueuing async work
- Reading a platform-populated field
- Traversing relationships with `__r`

## Practical guidance

**Assign in before, act in after.**

**Never update the triggering records from an after trigger** unless the value genuinely depends on something the save produced.

**Query parents explicitly in before insert** — `__r` traversal does not work there.

**Compare against `oldMap`** so after-trigger work fires on the transition rather than every save.

**Remember before triggers run before validation rules**, which is useful for defaults and means validation cannot assume a field was blank.
