# Lexical Scope

**Lexical scope** means scope is determined by where code is *written*, not by where it is *called from*. "Lexical" refers to the lexing phase of compilation — the scope structure is fixed the moment the parser reads your source, before anything runs.

The alternative, **dynamic scope**, resolves variables by walking the call stack at runtime. Bash and older Lisps work that way. JavaScript does not, with one exception: the value of `this` is dynamically determined ([[02.7 - this in JavaScript]]), which is exactly why `this` confuses people while variables rarely do.

## The mechanism

```js
const config = { env: "production" };

function logEnv() {
  console.log(config.env);
}

function test() {
  const config = { env: "test" };
  logEnv();
}

test(); // "production"
```

`logEnv` was written at module level, so its outer environment reference points at module scope. It cannot see `test`'s local `config` no matter who calls it. Under dynamic scoping this would print `"test"`.

The lookup order is always: current scope, then enclosing scope, then outward, ending at global. Not found anywhere means `ReferenceError`.

## Scope units

Four things create a scope in modern JavaScript:

| Unit | Scopes | Notes |
| --- | --- | --- |
| Global / module | everything | Modules get their own top-level scope |
| Function body | `var`, `let`, `const`, params | `var` stops here |
| Block `{ }` | `let`, `const`, `class` | `var` passes straight through |
| `catch (e)` | the error binding | `e` is block-scoped to the catch |

```js
function demo() {
  if (true) {
    var a = 1;
    let b = 2;
  }
  console.log(a); // 1  — var is function scoped
  console.log(b); // ReferenceError — let is block scoped
}
```

## Shadowing

An inner declaration with the same name hides the outer one for the rest of that scope.

```js
const user = { id: 1 };

function process(user) {
  user.id = 2;      // the parameter, not the outer binding
}
```

Shadowing is legitimate and common — parameters shadow module constants all the time. It becomes a problem when unintentional, particularly in long functions where the shadowed name is declared far from its use. Linters flag this with `no-shadow`.

There is one form that always fails:

```js
let x = 1;
{
  console.log(x); // ReferenceError, not 1
  let x = 2;
}
```

The inner `let x` exists from the start of the block in an uninitialized state, so the reference hits the temporal dead zone rather than resolving outward ([[05.2 - Hoisting and the Temporal Dead Zone]]).

## Scope determines closures

Because the scope chain is fixed at definition time and a function keeps a reference to its defining environment, a function that outlives its enclosing call still reaches those variables. That is a closure, covered next in [[02.3 - Closures]]. Lexical scope is the rule; closure is the observable consequence.

```js
function counter() {
  let count = 0;
  return () => ++count;
}

const next = counter();
next(); // 1
next(); // 2
```

`counter` has returned and its frame is off the call stack, but the returned arrow still holds its environment, so `count` cannot be garbage collected.

## Modules change the top level

```js
// script.js loaded as <script>
var x = 1;
console.log(window.x); // 1

// module.js loaded as <script type="module">
var y = 1;
console.log(window.y); // undefined
```

Each ES module has its own top-level scope. Top-level `var` does not touch the global object, `this` is `undefined` rather than `window`, and strict mode is always on. This removes an entire category of collision bugs and is one of the strongest practical reasons to use modules ([[08.1 - ES Modules vs CommonJS]]).

## How senior engineers actually use this

**They colocate declarations with use.** Declaring variables at the narrowest scope that works reduces the surface where a name can be shadowed or mutated, and lets the engine free memory earlier.

**They avoid the global object entirely.** Cross-module communication goes through imports, a store, or explicit dependency passing. Attaching things to `window` makes code untestable and unmountable, and prevents garbage collection for the page's lifetime.

**They lean on scope for encapsulation instead of conventions.** A value that is not exported is genuinely inaccessible. This is stronger than an underscore prefix and is the basis of every module-based API design.

**They read minified code with scope in mind.** Minifiers rename variables per scope. When a production stack trace shows `a.b.c`, knowing which scope a name belonged to is how you map it back — which is what source maps automate ([[27.7 - Source Maps]]).

## Common pitfalls

- Expecting a function to see the caller's variables. It sees only its own lexical ancestors.
- Using `var` inside a loop and capturing the shared binding in callbacks, producing the classic "all three log 3" bug.
- Accidentally shadowing a parameter or import inside a long function.
- Assigning to an undeclared name in sloppy mode, silently creating a global. Modules and strict mode make this throw.
- Assuming `this` follows the same rules as variables. It does not.

## Interview angle

"Explain lexical scope" is often paired with a snippet designed to look dynamically scoped. Answer with: scope is fixed at author time by the nesting structure of the source; each function stores a reference to the environment it was defined in; lookups walk that chain outward. Contrasting it explicitly with dynamic scope, and noting that `this` is the one dynamically bound piece, tends to end the line of questioning.
