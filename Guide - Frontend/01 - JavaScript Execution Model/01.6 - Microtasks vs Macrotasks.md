# Microtasks vs Macrotasks

Two queues, two very different scheduling rules. Getting this right lets you predict the output of any async ordering question, and explains a class of production bugs where the UI never repaints.

## The rule in one sentence

**One task per loop iteration; all microtasks after each task.**

Expanded:

1. Take one task from the task queue and run it to completion.
2. Drain the microtask queue completely — including microtasks added *while draining*.
3. Possibly render.
4. Repeat.

## What goes where

**Microtasks** (drained fully, higher priority)

- `.then` / `.catch` / `.finally` reactions
- `await` continuations
- `queueMicrotask()`
- `MutationObserver` callbacks
- `process.nextTick` in Node (technically its own queue, ahead of promises)

**Macrotasks / tasks** (one per turn)

- `setTimeout`, `setInterval`
- `setImmediate` (Node, and legacy IE)
- DOM event callbacks
- `postMessage` / `MessageChannel`
- I/O completion

The microtask queue is drained *between every* task, and also after the initial script finishes.

## Worked example

```js
console.log("script start");

setTimeout(() => console.log("timeout 1"), 0);

Promise.resolve()
  .then(() => {
    console.log("promise 1");
    return Promise.resolve();
  })
  .then(() => console.log("promise 2"));

setTimeout(() => console.log("timeout 2"), 0);

queueMicrotask(() => console.log("microtask"));

console.log("script end");
```

Output:

```
script start
script end
promise 1
microtask
promise 2
timeout 1
timeout 2
```

Reasoning: the synchronous lines run first. Microtasks were queued in order — the first `.then` reaction, then the `queueMicrotask` callback. Draining runs `promise 1`, then `microtask`; `promise 1` returning a resolved promise queues `promise 2` *during* the drain, so it still runs before any timer. Only when the microtask queue is empty does the loop take a task.

## await is a microtask boundary

```js
async function run() {
  console.log("A");
  await null;
  console.log("B");
}

run();
console.log("C");

// A, C, B
```

Everything before the first `await` runs synchronously. `await` suspends the function and schedules the remainder as a microtask reaction, even when awaiting a non-promise. This is why an `async` function is not "run in the background" — it runs synchronously until it hits an `await`.

## Microtask starvation

Because the queue is drained *completely*, a microtask that keeps queuing microtasks will hang the page permanently. No rendering, no input, no timers — ever.

```js
function starve() {
  queueMicrotask(starve);
}
starve(); // page is now frozen forever
```

The same shape with `setTimeout` is harmless, because each callback is a separate task and the loop can render between them. This asymmetry is the single most important practical difference between the two queues.

A subtler production version: a promise chain that retries by recursing without any timer between attempts. Always insert a real delay in retry loops ([[04.7 - Async Concurrency Patterns]]).

## Why your UI does not repaint inside an async function

```js
async function onClick() {
  setLoading(true);
  await heavyComputation(); // synchronous work inside
  setLoading(false);
}
```

If `heavyComputation` is synchronous, this never shows the spinner. Rendering happens between *tasks*, and `await` only yields to the microtask queue. To let a frame through you need an actual task boundary:

```js
await new Promise(resolve => setTimeout(resolve, 0));
```

Or, better, do the work in a Worker or split it into chunks. This trips up nearly everyone at least once.

## Node's extra layer

Node adds `process.nextTick`, whose queue is drained *before* the promise microtask queue:

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
Promise.resolve().then(() => console.log("promise"));
process.nextTick(() => console.log("nextTick"));

// nextTick, promise, then timeout/immediate (order between those two varies)
```

`process.nextTick` can starve the loop just like a runaway microtask. Node's own docs recommend `setImmediate` for most deferral needs.

## How senior engineers actually use this

**They use microtasks for consistency, tasks for yielding.** If you need something to happen "after the current synchronous work but before anything else observes the state", `queueMicrotask` is the right tool — batching state updates, flushing a write buffer, coalescing multiple calls into one. If you need the browser to breathe, you need a task.

**They recognize the pattern in framework code.** React batches updates by collecting them synchronously and flushing later; Vue's `nextTick` is literally a microtask; MutationObserver-based libraries rely on microtask timing to observe DOM changes before paint. Once you see the queues, framework scheduling stops being magic.

**They debug ordering with the queues, not with logs.** When something runs "too early", the question is which queue it landed in. Promise-adjacent code is almost always earlier than people expect.

**They avoid mixing the two in one flow.** Code that resolves promises inside timers inside promises becomes untestable. Pick one scheduling primitive per abstraction layer.

## Common pitfalls

- Expecting a repaint after `await`. Microtasks run before rendering.
- Recursive promise retries with no delay, which starve the loop.
- Assuming `Promise.resolve().then()` and `setTimeout(fn, 0)` are interchangeable "defer to later" calls. They are not remotely equivalent.
- Porting Node ordering assumptions (`nextTick`, `setImmediate`) into browser code, where neither exists.

## Interview angle

The classic question is an output-prediction snippet mixing `setTimeout`, promises and synchronous logs. Walk it out loud in the order: synchronous first, then drain microtasks fully (including newly added ones), then one task at a time. Adding that a runaway microtask can freeze the page while a runaway timer cannot shows you understand *why* the two queues differ rather than just their contents.
