# Connected Apps and Auth Providers

## Two directions

**A Connected App** describes an external application allowed to access Salesforce. Inbound.

**An Auth Provider** describes an external identity service Salesforce authenticates against. Outbound, or for single sign-on into Salesforce.

They are frequently confused because both live near each other in Setup and both involve OAuth. The distinction is direction: **connected app = something calling in; auth provider = Salesforce calling out, or trusting an external identity.**

## Connected app configuration

```
Setup → App Manager → New Connected App

Basic Information
  Connected App Name:  ERP Integration
  Contact Email:       platform-team@northwind.com

API (Enable OAuth Settings)
  Callback URL:        https://erp.northwind.com/oauth/callback
  Use digital signatures: server.crt        (for JWT)
  Selected OAuth Scopes: api, refresh_token
  Require Secret for Web Server Flow:  checked
  Require Secret for Refresh Token Flow: checked
  Enable Client Credentials Flow: unchecked unless needed
  Require Proof Key for Code Exchange (PKCE): checked
```

The consumer key and consumer secret are generated on save. The key is public-ish; **the secret is a credential** and belongs in a secrets manager, not in a repository or a custom setting.

## The policies that decide whether it works

Configured separately, under Manage after saving, and they matter more than the OAuth settings.

**Permitted Users**

- *All users may self-authorize* — any user can approve the app for themselves
- *Admin approved users are pre-authorized* — only users granted access through a profile or permission set

**Admin approved is the right default for internal integrations**, and it is **required** for the JWT bearer flow. The most common JWT setup failure is leaving this on self-authorize. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**IP Relaxation**

- *Enforce IP restrictions*
- *Relax IP restrictions* — the app bypasses the org's IP controls
- *Enforce IP restrictions, but relax for refresh tokens*

Integration users generally need relaxation, because source IPs change with cloud infrastructure. Relying on IP allowlisting for an integration is fragile; the connected app policy and a scoped user are the better controls.

**Refresh Token Policy**

- *Valid until revoked* — the usual choice for integrations
- *Immediately expire*
- *Expire if not used for N days*
- *Expire after N hours*

**This is the setting behind the classic "works for ninety days then stops" failure.** An integration with quiet periods and a use-based expiry policy loses its refresh token during a lull.

**Session Policies** — a separate timeout and high-assurance requirement for this app, independent of the org default.

## Granting access

With admin-approved users, access is granted through a **profile or permission set**:

```
Connected App → Manage → Manage Profiles / Manage Permission Sets
```

Permission sets are better, for the same reasons as everywhere else — granular, assignable, auditable, and removable without changing a profile.

```sql
SELECT Id, Name, ConsumerKey, OptionsAllowAdminApprovedUsersOnly
FROM ConnectedApplication
```

Auditing which users can reach which connected apps is worth doing periodically; access accumulates and is invisible unless someone looks.

## Session-based permission sets

A useful control for high-privilege integrations: a permission set activated only when a session originates from a specific connected app.

```
Permission Set: ERP_Integration_Elevated
  Session Activation Required: checked
  Connected App: ERP Integration
```

The permissions apply only to sessions from that app. The same user logging in through the UI does not have them.

This is how an integration user can hold `Modify All` on one object for its API work without a person being able to use those permissions interactively. It is underused and it is a genuinely good pattern for anything sensitive.

## Monitoring connected app usage

```sql
SELECT UserId, LoginTime, SourceIp, Application, ApiType, ApiVersion, Status, Browser
FROM LoginHistory
WHERE Application != 'Browser' AND LoginTime = LAST_N_DAYS:7
ORDER BY LoginTime DESC
```

`Application` names the connected app. This query answers three useful questions: which integrations are actually connecting, from where, and **on which API version** — which is what tells you what breaks when Salesforce retires old versions. See [[01.11 - Release Cycle, Trust and Status]].

`OAuthToken` shows issued tokens:

```sql
SELECT AppName, User.Name, LastUsedDate, UseCount, DeleteToken
FROM OAuthToken
ORDER BY LastUsedDate DESC
```

Tokens with an old `LastUsedDate` are candidates for revocation — an app nobody uses holding a valid token is unnecessary exposure.

## Auth Providers

The outbound direction: Salesforce authenticating against an external identity service.

Two uses, and they are different.

**Single sign-on into Salesforce.** Users authenticate with Google, Microsoft Entra, Okta, or a custom OpenID Connect provider, and Salesforce accepts the identity.

**Outbound authentication.** Salesforce obtains a token from an external OAuth provider to call its API — the credential half of a Named Credential.

```
Setup → Auth. Providers → New

Provider Type:        Open ID Connect
Name:                 ERP Identity
Consumer Key:         {from the external system}
Consumer Secret:      {from the external system}
Authorize Endpoint:   https://erp.northwind.com/oauth/authorize
Token Endpoint:       https://erp.northwind.com/oauth/token
User Info Endpoint:   https://erp.northwind.com/oauth/userinfo
Default Scopes:       openid profile claims:read
Registration Handler: ErpRegistrationHandler
```

Built-in provider types cover Google, Facebook, LinkedIn, Microsoft, GitHub, Janrain, Salesforce, OpenID Connect, and a custom option for anything else.

## Registration handlers

For SSO, the **registration handler** decides what happens when someone authenticates who has no Salesforce user — create one, match an existing one, or refuse.

```java
global with sharing class ErpRegistrationHandler implements Auth.RegistrationHandler {

    global User createUser(Id portalId, Auth.UserData data) {
        // matching on email prevents creating a duplicate user for someone who already exists
        List<User> existing = [
            SELECT Id FROM User WHERE Email = :data.email AND IsActive = true LIMIT 1
        ];
        if (!existing.isEmpty()) {
            return existing[0];
        }

        if (!isAllowedDomain(data.email)) {
            throw new Auth.RegistrationHandlerException('Domain not permitted');
        }

        Profile p = [SELECT Id FROM Profile WHERE Name = 'Minimum Access - Salesforce' LIMIT 1];

        return new User(
            Username = data.email + '.northwind',
            Email = data.email,
            FirstName = data.firstName,
            LastName = data.lastName,
            Alias = data.username.left(8),
            ProfileId = p.Id,
            TimeZoneSidKey = 'Asia/Kolkata',
            LocaleSidKey = 'en_IN',
            EmailEncodingKey = 'UTF-8',
            LanguageLocaleKey = 'en_US'
        );
    }

    global void updateUser(Id userId, Id portalId, Auth.UserData data) {
        update new User(Id = userId, FirstName = data.firstName, LastName = data.lastName);
    }
}
```

`createUser` returns an unsaved User; the platform inserts it. Throwing `Auth.RegistrationHandlerException` refuses the login, which is how a domain allowlist is enforced.

The handler is a security boundary. A handler that creates a user for anyone who authenticates, with no domain check, is a real exposure.

## Auth providers behind Named Credentials

The most common developer use. An external credential references an auth provider, a named credential references the external credential, and Apex calls out with no token handling at all.

```
Auth Provider:        ERP Identity
External Credential:  ERP_OAuth  (Authentication Protocol: OAuth 2.0)
Named Credential:     ERP_System (URL + External Credential)
```

```java
req.setEndpoint('callout:ERP_System/api/claims');
```

The platform obtains, caches, and refreshes the token. See [[13.13 - Named Credentials and External Credentials]].

**Per-user versus named principal** is the decision inside the external credential:

**Named Principal** — one shared identity for all Salesforce users. Right for a system integration where the external system does not care who initiated.

**Per User** — each Salesforce user authorizes individually, and the token carries their external identity. Right when the external system enforces per-user permissions, and it requires each user to complete an authorization once.

## Canvas and other app types

A connected app can also describe:

**Canvas apps** — an external application embedded in the Salesforce UI, receiving a signed request with the user's context.

**Mobile apps** — with policies for PIN, session timeout, and remote wipe.

**SAML service providers** — Salesforce as an identity provider for other applications.

These are less common in integration work and worth recognizing when you meet a connected app configured for one.

## Deployment

Connected apps deploy as metadata, and there is a wrinkle.

**The consumer key and secret are not deployed.** Deploying a connected app to another org creates a new app with new credentials, which means the target system's configuration must be updated.

For integrations, this usually means the connected app is **created manually per org** and only its policies are managed as metadata — or that the deployment includes a post-step to retrieve and distribute the new key.

Documenting which connected apps exist in which org, and what each is for, is worth doing. An org accumulates connected apps that nobody can identify, and nobody dares delete.

## Practical guidance

**Admin approved users, not self-authorize**, for internal integrations.

**Set the refresh token policy deliberately.** Use-based expiry breaks quiet integrations.

**Grant access through permission sets**, not profiles.

**Use session-based permission sets** to scope elevated permissions to the integration's own sessions.

**Audit `LoginHistory` by application** to see what is actually connecting and on which API version.

**Revoke stale tokens** from `OAuthToken`.

**Validate the domain in a registration handler.** It is a security boundary.

**Document each connected app's purpose**, since credentials do not deploy and the apps accumulate.
