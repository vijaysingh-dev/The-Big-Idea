# Phase 4: The Service Split

#backend #project #capstone

> **In one line:** Split ingestion out, measure everything it costs, and be honest in the ADR about whether you needed to.

---

## The Problem Phase 3 Created

```
One process. Ingestion competes with the API for CPU and connections.
A memory-heavy extraction affects request latency.
You cannot scale them independently — or so it appears.
```

⚠️ **That last clause is the trap.** You *can* scale them independently with one image and two deployments ([[10.1 - Monolith Modular Monolith Microservices]]).

💡 **Phase 4 splits anyway, deliberately, to feel the cost.** The ADR at the end should say so honestly — **and that honesty is worth more than a clean architecture.**

---

## What You Build

### Three services

```
gateway            HTTP, GraphQL, SSE, auth, rate limiting
documents-service  the core domain, owns the database
ingestion-service  extraction, chunking, indexing
```

⚠️ **Not five, not eleven.** Every service you add is a pipeline, a dashboard, a runbook and an on-call surface ([[10.11 - The Real Cost of Microservices]]).

### The boundary, chosen deliberately

**Apply the tests from [[10.2 - Finding Service Boundaries]] before splitting:**

| Boundary | Transactions | FKs | Co-change | Verdict |
|---|---|---|---|---|
| documents ↔ chunks | **Same transaction** | Many | Always | **Do not split** |
| documents ↔ sources | Same transaction | Several | Often | **Do not split** |
| **documents ↔ ingestion** | **None — async** | One (`document_id`) | Sometimes | **Splittable** |
| documents ↔ search | None — eventual | Zero | Sometimes | Splittable |

💡 **The ingestion boundary was chosen because no transaction spans it, one ID crosses it, and no data needs duplicating** — **which means no saga and no reconciliation** ([[10.5 - Distributed Transactions and Sagas]]).

**That is what a good boundary looks like, and choosing it deliberately is the exercise.**

### gRPC between services

```protobuf
service DocumentService {
  rpc GetDocument(GetDocumentRequest) returns (Document);
  rpc UpdateStatus(UpdateStatusRequest) returns (Empty);
  rpc SaveChunks(SaveChunksRequest) returns (Empty);
}
```

⚠️ **Kubernetes Services load-balance at L4**, so one gRPC connection sends every request to one pod ([[10.7 - Service Discovery and Service Mesh]]).

```python
channel = grpc.aio.insecure_channel(
    "dns:///documents:8080",
    options=[("grpc.service_config", json.dumps({
        "loadBalancingConfig": [{"round_robin": {}}]
    })), ("grpc.dns_min_time_between_resolutions_ms", 30000)],
)
```

💡 **A headless Service plus client-side round-robin solves this without a mesh**, and it is the fix most people do not know about.

### The shared client library

```python
class ServiceClient:
    async def call(self, method: str, *, deadline: float, idempotent: bool = False, **kw):
        attempt = 0
        while True:
            remaining = deadline - time.monotonic()
            if remaining <= 0:
                raise DeadlineExceeded(self.name)
            if self.breaker.is_open():
                raise DependencyUnavailable(self.name)
            try:
                return await self._stub(method, timeout=min(remaining, 5.0), **kw)
            except RETRYABLE:
                if not idempotent or not self.budget.allow() or attempt >= 3:
                    raise
                await asyncio.sleep(min(delay(attempt), remaining))
                attempt += 1
```

💡 **One library, used by every service.** This is what makes a mesh unnecessary for a single-language system ([[10.7 - Service Discovery and Service Mesh]]).

**Deadline propagation, retry budget, circuit breaker, trace context — all in one place.**

### The gateway

```
Browser → Gateway (auth, rate limit, GraphQL, SSE) → gRPC → services
```

⚠️ **Authenticate at the edge, authorise in the service** ([[14.1 - AuthN vs AuthZ]]).

**Forward the token, do not just forward claims.** Header-trust is one misconfigured network policy from a breach.

### GraphQL, now that it earns its place

**Three clients with different needs is the condition** ([[05.11 - REST vs GraphQL vs gRPC]]).

⚠️ **Adopting GraphQL means adopting DataLoaders, complexity limits and per-operation observability on the same day** ([[05.8 - GraphQL Security and Limits]]) — **not later.**

```python
@strawberry.type
class Document:
    @strawberry.field
    async def source(self, info: Info) -> Source:
        return await info.context.loaders.source.load((self.org_id, self.source_id))
```

💡 **The loader key includes the tenant.** Following Saleor's `ChannelContext` pattern, **make the tenant part of the type so a resolver cannot forget it** ([[15.5 - Reading Saleor GraphQL]]).

## The Decisions

| Decision | Alternative | Because |
|---|---|---|
| **Three services** | Stay monolithic | **To learn the cost. Say so** |
| Split at ingestion | Split at search or billing | No transaction crosses it |
| **gRPC internally** | REST, HTTP+JSON | Typed, fast, deadline propagation built in |
| **Shared client library** | Service mesh | One language, four services ([[10.7 - Service Discovery and Service Mesh]]) |
| **Headless Service + client LB** | A mesh for gRPC balancing | Solves the L4 problem for free |
| **GraphQL at the gateway** | REST | Three clients, different data needs |
| Gateway is also the BFF | Separate gateway and BFF | One team owns both ([[10.6 - API Gateway and BFF]]) |
| Forward the user token | Trust gateway headers | Defence in depth |

## What Will Go Wrong

### The gRPC distribution

```
3 replicas, 10,000 requests from one client → 10,000 / 0 / 0
```

⚠️ **Reproduce this before fixing it.** It is the single most common gRPC-on-Kubernetes surprise.

### Availability multiplies

```
Gateway 99.9% × documents 99.9% × auth 99.9% = 99.7%
```

💡 **Compute your effective availability and compare it to your SLO** ([[10.3 - Communication Patterns]]).

⚠️ **If it does not meet the target, make a dependency optional or asynchronous** — that is an architectural fix, not a monitoring one.

### The retry amplification

```
Gateway retries 3× → documents retries 3× → 9 requests per logical call
```

**Pick one layer. Add a retry budget** ([[11.2 - Timeouts Retries and Jitter]]).

### The GraphQL N+1, across the network

⚠️ **Without loaders, a document list with sources becomes 51 gRPC calls.** With loaders but without batching at the database, the network is batched and the database is not.

**Instrument both** — gRPC calls per request and database queries per request ([[05.6 - The N+1 Problem and DataLoader]]).

### The trace splits

⚠️ **A trace ending at "gRPC call" and starting again in the other service is two disconnected halves.**

**Auto-instrumentation handles gRPC; the queue boundary does not** ([[12.3 - Instrumenting Conduit End to End]]).

### The deploy coordination

⚠️ **If a change requires deploying both services in a specific order, you have a distributed monolith** ([[10.11 - The Real Cost of Microservices]]).

```python
deploys_requiring_coordination_ratio
```

**Track it.** It is the metric that tells you whether the split achieved anything.

## Acceptance Criteria

```
□  Three services, each independently deployable
□  gRPC request distribution even across replicas, verified
□  Every cross-service call: deadline, retry budget, circuit breaker
□  Effective availability computed and meeting the SLO
□  GraphQL with loaders: query count flat against result size
□  Complexity limits rejecting expensive queries before execution
□  One trace spans gateway → documents → ingestion
□  A slow documents-service does not exhaust the gateway's workers
□  Token forwarded and validated per service; header-trust bypass blocked
□  deploys_requiring_coordination_ratio measured over 20 changes
□  Contract tests: a breaking change fails the provider's own CI
□  The full cost measured: latency per hop, operational surface, code added
```

⚠️ **The last two are what make the ADR honest.**

## What You Should Be Able To Explain

```
"Why did you split?"
  → Deliberately, to measure the cost. With one developer, a separate
     deployment of the same image would have given the same independent
     scaling. Here is what the split actually cost

"What did it cost?"
  → 8ms per request in coordination latency, effective availability
     from 99.9% to 99.7%, 3× the operational surface, and about
     2,400 lines of client and contract code. Here are the numbers

"Why no service mesh?"
  → One language, three services. A shared client library gives us
     retries, breakers and tracing with zero latency overhead and
     zero sidecar memory. We would adopt a mesh for mTLS at scale
     or a second language

"How did you avoid a saga?"
  → The boundary was chosen so no transaction crosses it. Ingestion
     failure means 'not indexed', which is a state, not an inconsistency

"Would you do it again?"
  → [Your honest answer, with numbers]
```

💡 **The last question is the one that matters**, and "no, and here is why" is a strong answer.

## Exercise

**Drill 16.5 — Split it, measure it, and be honest**

```
conduit/phases/04/
├── services/{gateway/, documents/, ingestion/}
├── protos/
├── client/{service_client.py, tests/}
├── measure/{latency_per_hop.py, availability.py, operational_surface.md,
│            code_delta.py, RESULTS.md}
├── failures/{slow_dependency.py, grpc_distribution.py, retry_storm.py}
├── graphql/{schema.py, loaders.py, limits.py}
├── adr/{020-split.md ... 025-graphql.md}
└── PHASE4.md
```

**Part 1 — Score the boundaries first.** Before splitting, apply the four tests to five candidate boundaries.

**Instrument cross-module calls in the phase-3 monolith** and produce the traffic matrix — **calls per second between every pair.**

⚠️ **Any pair above 1,000 calls/second is un-splittable.** Confirm your chosen boundary is not one.

**Part 2 — Split, and measure the latency cost.** The same five operations before and after.

**Chart p50 and p99 for both**, and compute the per-hop overhead.

**Part 3 — The gRPC distribution problem.** Three replicas, 10,000 requests from one client.

**Count per pod. Confirm 10,000/0/0.**

Then headless Service with client-side round-robin. **Count again.** Then scale to five mid-test and measure how long until the new pods receive traffic.

**Part 4 — Availability, computed and measured.** Compute the effective availability of your dependency chain.

**Then verify empirically:** inject failures at the configured rate and measure end-to-end success over 100,000 requests.

**Confirm the measurement matches the arithmetic.**

**Then make one dependency optional and re-measure the improvement.**

**Part 5 — The slow dependency.** Make documents-service take 5 seconds, not fail.

**Measure the gateway's behaviour**: in-flight requests, worker utilisation, and the error rate on endpoints that do not use documents.

**Then add timeouts, a bulkhead and a circuit breaker.** Measure again ([[11.3 - Circuit Breakers and Bulkheads]]).

**Part 6 — Retry amplification.** Retries at both layers, downstream instrumented to count.

**Confirm nine requests per logical call.** Chart downstream load against failure rate.

Then add a retry budget at each layer and chart again. **The budgeted version should stay bounded as the failure rate approaches 100%.**

**Part 7 — GraphQL with the full defence set.** Schema, loaders with tenant-scoped keys, complexity limits, and per-operation metrics.

**Then attack it:** deep nesting, wide `first`, and 1,000 aliases. **Confirm each is rejected at validation, with zero resolver calls.**

**Then measure query count against result size** — it must be flat.

**Part 8 — Count the cost.** For monolith and split:

| Metric | |
|---|---|
| Lines of domain logic | Should be identical |
| Lines of coordination code | The addition |
| Pipelines, manifests, dashboards, alerts, runbooks | |
| p99 latency for five operations | |
| Effective availability | |
| Mean time to diagnose an injected bug | **Have someone else do this, timed** |

**Part 9 — The honest ADR.** `020-split.md` with every number from parts 2–8.

⚠️ **State plainly whether the split was necessary.** If a separate deployment of one image would have achieved the same scaling, **say so.**

**Then write the interview answer, with your numbers in it.**

**Done when:**
- Your traffic matrix confirms the chosen boundary is not chatty
- gRPC distribution went from 10,000/0/0 to even, without a mesh
- Measured availability matches your arithmetic
- A slow dependency does not degrade unrelated endpoints
- Retry budgets bound amplification as failure rate rises
- Three GraphQL attacks are rejected before any resolver runs
- Query count is flat against result size
- Mean time to diagnose is measured for both architectures
- The ADR states honestly whether the split was necessary
