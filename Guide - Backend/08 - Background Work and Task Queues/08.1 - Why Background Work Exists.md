# Why Background Work Exists

#backend #queues #architecture

> **In one line:** A request has a latency budget measured in hundreds of milliseconds and a user waiting at the end of it — anything that does not fit in that budget, or that must survive a restart, belongs somewhere else.

---

## The Idea

```python
@app.post("/documents")
async def upload(file: UploadFile):
    doc = await store(file)
    text = await extract_text(doc)         # 8 seconds
    chunks = await chunk_and_embed(text)   # 30 seconds
    await index(chunks)                    # 5 seconds
    await notify_collaborators(doc)        # 2 seconds
    return doc                              # 45 seconds later
```

| Problem | |
|---|---|
| The user waits 45 seconds | Or their browser times out first |
| A worker is occupied for 45 seconds | Throughput collapses |
| A deploy mid-request loses everything | No durability |
| One failure loses all the work | No partial progress |
| Retries redo everything | Including what succeeded |
| Load spikes have nowhere to go | Every upload is 45 seconds of capacity |

```python
@app.post("/documents")
async def upload(file: UploadFile):
    doc = await store(file)
    await enqueue(process_document, doc.id)
    return {"id": doc.id, "status": "processing"}      # 200ms
```

💡 **The request path and the work path have fundamentally different requirements.** The request path optimises for latency and has a user attached; the work path optimises for throughput and durability and has nobody waiting. **Conflating them means neither is done well.**

---

## What Belongs in the Background

| Work | Why |
|---|---|
| Anything over ~1 second | The latency budget |
| Anything calling a slow third party | You do not control its latency |
| Anything that must survive a restart | Durability |
| Anything retryable | The request is gone; the retry needs somewhere to live |
| Anything fan-out | 1,000 emails is not one request's work |
| Anything scheduled | There is no request at all |
| Anything CPU-heavy | It blocks the event loop ([[01.6 - The Blocking Call Problem]]) |

### The judgement cases

⚠️ **Sending a welcome email inline means signup fails if the email provider is down.** Queue it.

**The general rule: if the operation can fail independently of the primary action, and the primary action is still valid without it, it belongs in the background.**

⚠️ **Charging a card during checkout: inline.** The user needs to know whether it succeeded — backgrounding it means telling them "we'll let you know" for something they expect an answer to.

💡 **The test: does the user need the result to make their next decision?** If yes, inline. If no, queue.

---

## The Cost of Queueing

**Background work is not free, and pretending otherwise leads to queueing everything.**

| Cost | |
|---|---|
| **Eventual consistency** | The user sees "processing" instead of a result |
| **Failure is invisible** | Nobody is watching; you need alerting |
| Debugging is harder | The stack trace is in a worker, hours later |
| State to manage | Job status, progress, results |
| Infrastructure | A broker, workers, monitoring |
| Duplicates | At-least-once delivery ([[07.5 - Idempotency Keys and Deduplication]]) |

⚠️ **The user-experience cost is the one people underestimate.** "Your document is processing" requires a progress UI, a notification mechanism, and a way to handle failure the user can understand. **That is real product work, not just infrastructure.**

💡 **Queue when the benefit is clear, not reflexively.** A 200ms operation moved to a queue trades 200ms of latency for eventual consistency, a progress UI, and a whole failure surface. **That is a bad trade.**

## The Shapes of Background Work

### 1. Fire and forget

One task, no result needed, retryable. **The standard case.**

### 2. Request-response with a status resource

```python
@app.post("/exports")
async def create_export(spec: ExportSpec):
    op_id = await repo.create_operation("export", spec)
    await enqueue(run_export, op_id)
    return Response(202, headers={"Location": f"/operations/{op_id}"})
```

💡 **Modelling the operation as a resource is the right pattern for anything a user initiates and waits for** ([[05.1 - REST Done Properly]]). **It gives you polling, cancellation, progress and a place to put errors — all for free, because it is just a row.**

**Pair it with SSE for live progress** ([[04.2 - Server Sent Events]]) and the same state serves both polling and pushing clients.

### 3. Pipeline

```
fetch → parse → chunk → embed → index
```

⚠️ **Do not implement a pipeline as one long task.** A failure at stage 4 that retries the whole chain redoes the expensive stages 1–3, **and a 30-minute task that fails at minute 28 has wasted 28 minutes.**

💡 **Small tasks that hand off to the next stage** give you independent retry, independent concurrency limits per stage, visible progress, and the ability to scale the slow stage separately.

**This is Conduit's ingestion pipeline, and it is worth designing as a chain from the start.**

### 4. Fan-out

```python
async def notify_all(doc_id: str):
    for user_id in await repo.collaborators(doc_id):
        await enqueue(send_notification, user_id, doc_id)   # one task each
```

⚠️ **One task per recipient, not one task that loops.** A loop over 10,000 recipients failing at 9,000 either retries all 10,000 or needs its own progress tracking.

💡 **A fan-out task whose only job is to enqueue other tasks is small, fast and cheaply retryable** — and if the enqueueing is idempotent, retrying it is harmless.

### 5. Scheduled

Covered in [[08.8 - Periodic Tasks and Distributed Cron]], with the coordination question in [[07.6 - Leader Election and Coordination]].

### 6. Long-running workflow

⚠️ **A chain of tasks is not a workflow.** There is no way to express "if step 3 fails, undo steps 1 and 2", no visibility into where a given order is, and no way to resume after a crash mid-step.

💡 **The distinguishing signal: the work has state that persists across steps and needs compensation on failure** ([[08.11 - Durable Workflows and Sagas]]).

---

## Where the Work Goes

| Signal | Choose |
|---|---|
| One producer, one consumer, retryable | **Task queue** |
| Many consumers of the same event | **Event log** ([[09.1 - Queue vs Log]]) |
| Need to replay history | **Event log** |
| Multi-step with compensation | **Workflow engine** |
| Time-triggered | **Cron** |
| Continuous aggregation over a stream | **Stream processor** |

💡 **The most common mistake is using a task queue for something that wants an event log**, because a queue consumes destructively — a second consumer needs a second queue and a producer that knows about it. **Events want a log; commands want a queue.**

## In Production

### The user-facing contract

```json
{"id": "doc_42", "status": "processing", "progress": 0.35,
 "estimated_completion": "2026-08-17T14:35:00Z", "error": null}
```

| Every asynchronous operation needs | |
|---|---|
| **A status the user can poll or subscribe to** | Otherwise it is a black box |
| **Progress, where meaningful** | "Processing" for 10 minutes feels broken |
| **A terminal error state with a reason** | Not just "failed" |
| **A way to retry or cancel** | Users will want both |

⚠️ **A background job with no user-visible status is a support ticket generator.** "I uploaded it an hour ago and nothing happened" has no answer without one.

### Failure is invisible by default

**In a request, a failure returns a 500 and appears in your error rate. In a queue, a failure is a log line nobody reads.**

```python
task_started_total.labels(task=name).inc()
task_completed_total.labels(task=name, status="success"|"failure").inc()
task_duration_seconds.labels(task=name).observe(elapsed)
queue_depth.labels(queue=name).set(depth)
queue_oldest_message_age_seconds.labels(queue=name).set(age)
dead_letter_total.labels(task=name).inc()
```

💡 **`queue_oldest_message_age_seconds` is the single best queue health metric.** Depth tells you how much work is waiting; **oldest-age tells you whether anything is stuck.** A queue with 10,000 messages all seconds old is healthy; one with 5 messages 3 hours old is broken.

**Alert on oldest-age, not on depth.**

### Sizing the boundary

```
Request budget:     500 ms p99
Available for work: ~200 ms after framework, DB and serialisation
```

⚠️ **Anything above roughly 200ms is a candidate for the background**, and anything above one second almost certainly belongs there.

💡 **Fix the operation before backgrounding it.** Moving a slow query to a queue makes the request fast and leaves the slow query, **now invisible, running on your database** ([[06.3 - Indexes Deep Dive]]).

### The disconnect problem

```python
@app.post("/orders")
async def create_order(data: OrderIn):
    order = await repo.create(data)
    await charge_payment(order)          # ← client disconnects here
    await send_confirmation(order)       # never runs
```

⚠️ **A client disconnect cancels your task** ([[01.7 - Cancellation and Structured Concurrency]]), leaving multi-step work half done.

```python
order_id = await repo.create_pending(data)
await enqueue(process_order, order_id)      # survives disconnect
return {"id": order_id, "status": "pending"}
```

💡 **Writing one durable record and enqueueing the rest is the pattern that makes a request path robust.** The database row is the commitment; everything after it is recoverable work.

**Combine with the outbox pattern so the enqueue cannot be lost either** ([[09.3 - The Outbox Pattern]]).

### Conduit's boundaries

| Operation | Where | Why |
|---|---|---|
| Create a document record | **Request** | The user needs the ID |
| Extract text | Queue | Seconds, retryable |
| Chunk and embed | Queue | Expensive, GPU work in phase 9 |
| Index | Queue | Depends on the previous stage |
| Notify collaborators | Queue | Fan-out, independent failure |
| Search | **Request** | The user is waiting for the result |
| Sync a source | Queue, scheduled | Long, periodic, retryable |
| Export | Queue, with an operation resource | Minutes, and the user polls |
| **Authorisation check** | **Request** | **Never background a security decision** |

💡 **The last row is worth stating explicitly.** Backgrounding an authorisation check means the operation proceeds before permission is confirmed. **It sounds obviously wrong and it happens, usually as "we'll validate it in the worker".**

## Codebase

**Repo:** `onyx-dot-app/onyx`, `getsentry/sentry`, `celery/celery`

**Question to answer:** In Onyx, where is the boundary between request and background work in the document ingestion path, and how does the user learn what is happening? Then: how does Sentry decide what to process inline versus asynchronously?

**Read, in order:**

1. `onyx/backend/onyx/background/celery/` — **the task definitions and queue routing.** Note how the pipeline is split into stages rather than one long task
2. `onyx/backend/onyx/server/documents/` — the request handlers. **Find the exact line where the request ends and the queue begins**, and what the API returns
3. `onyx/backend/onyx/db/` — the models tracking indexing status. **This is the status resource pattern**, and it is what the UI polls
4. `sentry/src/sentry/tasks/` — a very large set of background tasks. **Note the granularity**: small, single-purpose, individually retryable
5. `sentry/src/sentry/web/frontend/` and the ingest path — **the inline portion is deliberately tiny**, because ingest volume is enormous

💡 Sentry's ingest boundary is instructive: **they accept the event, do the cheapest possible validation, persist it, and return.** Everything else — grouping, deduplication, alerting, notification — is background. **That shape is what lets them absorb enormous spikes.**

**Size:** 1–2 sessions.

## Exercise

**Drill 8.1 — Move the boundary and measure everything**

```
drills/08-boundary/
├── inline/{app.py, load.py}
├── queued/{app.py, tasks.py, status.py, sse.py}
├── measure/{latency.py, throughput.py, deploy.py, spike.py, RESULTS.md}

├── disconnect/{inline_multistep.py, durable_then_queue.py, FINDINGS.md}
├── observability/{metrics.py, silent_failure.py, runbook.md}
└── README.md
```

**Part 1 — Build both versions.** The same document-processing pipeline: inline in the request, and split into queued stages with a status resource.

**Part 2 — Measure the four differences.** Request p50 and p99 under steady load; sustained throughput under increasing concurrency; work lost on a rolling restart mid-processing; behaviour under a 10× spike.

**Chart all four side by side.** The deploy and spike columns are where the queued version should win decisively.

**Part 3 — Task granularity.** The same pipeline as one 45-second task, and as five 9-second tasks.

**Inject a failure at 80% completion. Measure total work performed including the retry for both** — the monolithic version should redo roughly 36 seconds, the staged version 9.

Then go too far — twenty 2-second tasks — and measure the overhead of queueing, serialisation and state transitions. **Find the granularity sweet spot for your setup.**

**Part 4 — The disconnect.** A multi-step operation inline, with the client disconnecting after step 2 of 4.

**Inspect the database and confirm the inconsistent state.** Measure how often this happens under realistic client timeout settings.

Then the durable-record-then-queue version. **Confirm the state is always consistent and the work completes.**

**Part 5 — The status resource.** Polling plus SSE, sharing the same state.

Test the four requirements: progress visible, terminal error with a reason, retry, and cancel.

**Measure the load difference between 500 clients polling every 2 seconds and 500 clients on SSE** ([[04.1 - Choosing a Realtime Transport]]).

**Part 6 — Silent failure.** Break a background task so it fails 100% of the time. **Do not add alerting yet.**

Run normally for 30 minutes. **Record how you would have found out** — check every dashboard you have.

Then add the six metrics plus an alert on `queue_oldest_message_age_seconds`. Break it again and **measure time to detection.**

**Part 7 — The boundary audit.** For every operation in Conduit phase 1, decide inline or background using the test from this note.

For each background decision, specify the shape, the infrastructure, the user-facing status, and the failure behaviour.

**For each inline decision, measure it and confirm it fits the latency budget.** Anything above 200ms either gets an index or gets queued.

**Done when:**
- Your four-measure comparison chart shows where each version wins
- You know the rework cost of monolithic versus staged tasks, with numbers
- You have found the granularity sweet spot for your infrastructure
- The disconnect test shows inconsistent state inline and consistent state queued
- Your status resource serves both polling and SSE from one state model
- You measured time-to-detection for a silent task failure, before and after alerting
- Every Conduit operation has a justified boundary decision with a measurement
