# Probes, Resources and Autoscaling

#backend #kubernetes #operations

> **In one line:** Probes decide whether you get traffic and whether you get restarted, requests and limits decide where you run and when you get throttled — and the default configuration of all three is wrong in ways that cause outages.

---

## Probes

| Probe | Question | Failure means |
|---|---|---|
| **Startup** | "Has it finished starting?" | Suppresses the other two until it passes |
| **Readiness** | "Should I send traffic?" | Removed from the Service endpoints |
| **Liveness** | "Is the process wedged?" | **The container is restarted** |

⚠️ **The most consequential mistake in Kubernetes: putting a dependency check in the liveness probe.**

```
Database slows
→ every pod fails liveness
→ every pod restarts
→ cold caches, cold pools, reconnection storm
→ the database is now under MORE load
→ every pod fails liveness again
```

💡 **A degraded dependency becomes a total, self-sustaining outage** ([[11.1 - How Systems Fail]]).

**Liveness checks the process. Readiness checks whether you can serve. Nothing else.**

```python
@app.get("/healthz")                     # liveness
async def healthz():
    return {"ok": True}                  # if the process responds, it is alive

@app.get("/readyz")                      # readiness
async def readyz():
    if not await db.is_connected():
        raise HTTPException(503)
    if not cache_warmed.is_set():
        raise HTTPException(503)
    return {"ready": True}
```

### The lying readiness probe

⚠️ **A readiness probe returning 200 before the service can actually serve makes a rolling deploy an outage.** Pods are added to the load balancer while still connecting to the database or warming caches ([[10.10 - Deployment Strategies]]).

**Readiness must mean "I can serve a real request right now."**

### Startup probes solve slow starts

```yaml
startupProbe:
  httpGet: {path: /healthz, port: 8000}
  failureThreshold: 30
  periodSeconds: 5              # up to 150 seconds to start
livenessProbe:
  httpGet: {path: /healthz, port: 8000}
  periodSeconds: 10
  failureThreshold: 3           # ~30 seconds once running
```

💡 **Without a startup probe you must set `initialDelaySeconds` on liveness to cover the worst-case start**, which means a wedged pod also takes that long to be restarted. **A startup probe decouples the two.**

### Probe tuning

```yaml
readinessProbe:
  periodSeconds: 5
  failureThreshold: 3           # 15s to remove from endpoints
  timeoutSeconds: 2             # ⚠️ default is 1 — often too tight
```

⚠️ **`timeoutSeconds: 1` is the default and it is a common cause of spurious failures** under load, when even a trivial handler can take longer than a second.

⚠️ **Probes run against the pod, so a saturated event loop fails them** — even though the process is fine ([[01.12 - Profiling and Debugging Async Services]]). **That is arguably correct behaviour for readiness and disastrous for liveness.**

### Readiness must fail during shutdown

```python
@app.on_event("shutdown")
async def shutdown():
    shutting_down.set()          # /readyz now returns 503
    await asyncio.sleep(5)       # let endpoint removal propagate
    ...
```

**This is the first step of graceful shutdown** ([[11.7 - Graceful Shutdown and Draining]]).

## Requests and Limits

```yaml
resources:
  requests: {cpu: "200m", memory: "256Mi"}
  limits:   {memory: "512Mi"}
```

| | Requests | Limits |
|---|---|---|
| Used for | **Scheduling** | **Enforcement** |
| Memory exceeded | — | **OOMKilled** |
| CPU exceeded | — | **Throttled** |

### QoS classes

| Class | Condition | Eviction order |
|---|---|---|
| **Guaranteed** | requests == limits, both set | Last |
| **Burstable** | requests < limits, or only requests | Middle |
| **BestEffort** | Neither set | **First** |

⚠️ **Never run production workloads as BestEffort.** They are evicted first under node pressure, and they get whatever CPU is left over.

### The CPU limit argument

⚠️ **CPU limits throttle rather than kill, and the throttling is invisible in average CPU usage.**

```
cpu.max = 50000 100000     # 50ms per 100ms period
```

**A process that exhausts its quota is frozen until the next period — up to 100ms of dead time** ([[13.1 - Containers From First Principles]]).

```bash
cat /sys/fs/cgroup/cpu.stat        # nr_throttled, throttled_usec
```

💡 **"The service is slow and CPU usage is only 40%" is almost always throttling.** The average is low precisely because the process spent part of each period frozen.

**The emerging consensus:**

| | |
|---|---|
| **Always set CPU requests** | Scheduling needs them |
| **Usually do not set CPU limits** | Let bursty workloads use idle capacity |
| **Always set memory requests and limits** | Memory is not compressible |

⚠️ **The counterargument is noisy neighbours** — without limits, one pod can consume a node's CPU. **Requests provide proportional shares under contention, which usually handles this**, and a `ResourceQuota` bounds the namespace.

💡 **Set CPU limits when you need predictable performance for capacity planning or have a genuinely hostile workload. Otherwise measure `nr_throttled` before adding them.**

### Sizing from measurement

```promql
quantile_over_time(0.95, container_memory_working_set_bytes[7d])
quantile_over_time(0.95, rate(container_cpu_usage_seconds_total[5m])[7d:])
```

```
memory request ≈ p95 working set
memory limit   ≈ p99 × 1.3
cpu request    ≈ p95 usage
```

⚠️ **Use `working_set_bytes`, not `usage_bytes`.** Usage includes reclaimable page cache; **working set is what the OOM killer actually considers.**

💡 **The Vertical Pod Autoscaler in recommendation mode does this for you** without changing anything:

```yaml
spec:
  updatePolicy: {updateMode: "Off"}     # recommend only
```

**Run it for a week and read the recommendations. Free, and usually more accurate than your guess.**

## Horizontal Autoscaling

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: {kind: Deployment, name: documents}
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}
```

⚠️ **`averageUtilization` is a percentage of the *request*, not the limit.** With a request of 200m and 70% target, it scales at 140m per pod — **and pods can exceed 100% of their request.**

### Scaling on the wrong metric

⚠️ **Scaling on latency creates a feedback loop when the bottleneck is downstream:**

```
Latency rises (database is slow) → HPA scales up → more pods
→ more database connections → the database is slower → scale up more
```

💡 **Scale on a metric reflecting *your* saturation, not everyone else's** ([[11.1 - How Systems Fail]]).

| Workload | Scale on |
|---|---|
| CPU-bound API | CPU utilisation |
| **I/O-bound API** | **Concurrent in-flight requests** |
| **Queue workers** | **Queue depth or oldest-message age** |
| Anything with a hard downstream limit | **Do not autoscale past it** |

```yaml
    - type: External
      external:
        metric: {name: queue_oldest_message_age_seconds}
        target: {type: AverageValue, averageValue: "60"}
```

💡 **For workers, oldest-age is better than depth** ([[08.1 - Why Background Work Exists]]) — it scales on lateness rather than volume, which is what users experience.

### Behaviour: scale up fast, down slow

```yaml
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{type: Percent, value: 100, periodSeconds: 30}]
    scaleDown:
      stabilizationWindowSeconds: 300
      policies: [{type: Percent, value: 20, periodSeconds: 60}]
```

⚠️ **The default 5-minute scale-down stabilisation is right and people often shorten it.** Aggressive scale-down causes flapping — scale down, load rises, scale up, repeat — **with a cold cache each time.**

### Autoscaling cannot beat a spike

```
Spike arrives:        seconds
HPA notices:          15-30s (metric scrape interval)
Pod scheduled:        1-5s
Image pull:           0-60s
Startup + warm:       10-60s
→ 30 seconds to 2 minutes
```

⚠️ **Autoscaling is not a substitute for headroom** ([[11.8 - Capacity Planning and Load Testing]]). **Size `minReplicas` to survive a spike long enough for scaling to catch up.**

💡 **Pre-pulled images and fast startup are what make autoscaling responsive.** A 60-second startup makes your HPA nearly useless for spikes.

### The downstream ceiling

⚠️ **Scaling to 50 pods × a pool of 10 is 500 database connections.**

```
maxReplicas ≤ (pgbouncer_pool_size) / (pool_size_per_pod)
```

💡 **Compute `maxReplicas` from your downstream limits, not from your budget.** An HPA that can exhaust the database is a mechanism for turning a load spike into an outage ([[06.9 - Connection Pooling and PgBouncer]]).

## In Production

### The complete workload spec

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      image: ghcr.io/org/conduit@sha256:...
      resources:
        requests: {cpu: "200m", memory: "384Mi"}
        limits: {memory: "512Mi"}
      startupProbe:
        httpGet: {path: /healthz, port: 8000}
        failureThreshold: 30
        periodSeconds: 5
      readinessProbe:
        httpGet: {path: /readyz, port: 8000}
        periodSeconds: 5
        timeoutSeconds: 2
        failureThreshold: 3
      livenessProbe:
        httpGet: {path: /healthz, port: 8000}
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 3
      lifecycle:
        preStop:
          exec: {command: ["sleep", "10"]}
```

### The audit

```
□  Liveness checks ONLY the process
□  Readiness checks real serving capability
□  Startup probe for slow starts
□  timeoutSeconds ≥ 2
□  Readiness fails immediately on SIGTERM
□  preStop sleep covers endpoint propagation
□  Grace period > preStop + drain + longest operation
□  Memory requests and limits set from measurement
□  CPU requests set; limits only with a measured reason
□  No BestEffort pods
□  HPA scales on your saturation, not downstream latency
□  maxReplicas bounded by downstream capacity
□  Scale-down stabilisation ≥ 300s
```

### Monitoring

```promql
rate(kube_pod_container_status_restarts_total[15m])       # restart loops
container_cpu_cfs_throttled_seconds_total                  # throttling
kube_pod_container_resource_requests / container_memory_working_set_bytes
kube_horizontalpodautoscaler_status_current_replicas
```

💡 **Alert on `nr_throttled` rising.** It is invisible in CPU utilisation and it is the explanation for a whole class of latency mysteries.

**Alert when an HPA is pinned at `maxReplicas`** — it means either you need a higher ceiling or the bottleneck is elsewhere.

### Conduit's configuration

| Component | Requests | Limits | HPA metric | min/max |
|---|---|---|---|---|
| Gateway | 200m / 256Mi | — / 512Mi | CPU 70% | 3 / 15 |
| Document service | 500m / 512Mi | — / 1Gi | **In-flight requests** | 3 / 12 |
| **Workers** | 1 / 2Gi | — / 4Gi | **Queue oldest-age** | 2 / 10 |
| Scheduler | 100m / 128Mi | — / 256Mi | none | 1 / 1 |

⚠️ **`maxReplicas: 12` on the document service is derived from PgBouncer's pool of 60 divided by 5 connections per pod**, not chosen for convenience. **That constraint should be written into the manifest as a comment.**

💡 **No CPU limits anywhere**, because measured `nr_throttled` was non-zero with them and the workloads are bursty. **Memory limits everywhere, because memory is not compressible.**

**The scheduler is a singleton with no HPA** — leader election handles the coordination ([[07.6 - Leader Election and Coordination]]).

## Codebase

**Repo:** `kubernetes/kubernetes`, `kubernetes/autoscaler`

**Question to answer:** How does the kubelet evaluate probes, and what exactly happens on a liveness failure? Then: how does the HPA compute the desired replica count, and what stops it from oscillating?

**Read, in order:**

1. `pkg/kubelet/prober/worker.go` — **`doProbe`.** The three probe types, `failureThreshold` accounting, and the startup-probe suppression logic
2. `pkg/kubelet/prober/prober.go` — how a probe result becomes a container restart or an endpoint removal
3. `pkg/controller/podautoscaler/horizontal.go` — **`computeReplicasForMetrics`.** **The answer to the second question**: `desired = ceil(current × currentMetric / targetMetric)`
4. `pkg/controller/podautoscaler/replica_calculator.go` — the tolerance band (10% by default) that prevents oscillation on small deviations
5. `kubernetes/autoscaler/vertical-pod-autoscaler/pkg/recommender/` — **how VPA derives recommendations from histograms of observed usage.** Directly the sizing method in this note

💡 The HPA formula is simpler than people expect — **it is one line of arithmetic plus a tolerance band and a stabilisation window.** Seeing that makes HPA behaviour predictable rather than mysterious, **and it makes clear why scaling on a downstream-influenced metric produces a feedback loop.**

**Size:** 1–2 sessions.

## Exercise

**Drill 13.4 — Make the defaults wrong, then right**

```
drills/13-probes/
├── probes/{lying_readiness.py, liveness_cascade.py, startup.py, timeout.py, RESULTS.md}
├── resources/{oom.py, throttle.py, sizing.py, qos.yaml, RESULTS.md}
├── hpa/{cpu.yaml, inflight.yaml, queue_depth.yaml, feedback_loop.py, PLOT.md}
├── spike/{response_time.py, headroom.py, RESULTS.md}
├── ceiling/{connection_exhaustion.py, FINDINGS.md}
└── audit.md
```

**Part 1 — The lying readiness probe.** A service returning 200 from `/readyz` before its database pool is connected.

**Deploy under load and count the 500s** from pods added to the load balancer too early.

Then make the probe accurate. **Confirm zero.**

**Part 2 — The liveness cascade.** Put a database check in the liveness probe. Make the database slow (5-second queries).

**Confirm every pod fails liveness and restarts.** Chart restarts per minute and application availability.

**Confirm it is self-sustaining** — the restarts increase database load, which causes more restarts.

Then remove the dependency check and repeat. **The service should degrade, not die.**

**Part 3 — Probe timing.** Sweep `timeoutSeconds` at 1 and 2 under increasing load.

**Find the load at which `timeoutSeconds: 1` produces spurious failures.**

Then a slow-starting service (60 seconds). Configure it with `initialDelaySeconds` on liveness, then with a startup probe. **Measure how long a wedged pod takes to be restarted in each** — the startup probe version should be much faster.

**Part 4 — OOM and throttling.** A memory-growing workload with a 256Mi limit.

**Confirm exit 137, and that no shutdown handler ran and nothing was logged.**

Then a CPU-bound workload with limits at 0.25, 0.5, 1, 2 and none.

**Chart p99 latency, reported CPU utilisation, and `nr_throttled` for each.**

⚠️ **Confirm that at a limiting value, reported utilisation is well below 100% while latency is badly degraded.** That is the misdiagnosis this drill exists to prevent.

**Part 5 — Size from measurement.** Run a realistic workload for 24 hours (or simulate it).

Compute p95 and p99 working set and CPU. **Set requests and limits from them.**

Then install VPA in recommendation mode and **compare its recommendations to yours.**

Then test all three QoS classes under node memory pressure and **confirm the eviction order.**

**Part 6 — The autoscaling feedback loop.** An I/O-bound service whose bottleneck is the database.

**Configure the HPA on latency. Apply load. Chart replicas, database connections, and latency over time.**

**Confirm the loop: latency rises → scale up → more connections → latency rises further.**

Then reconfigure on in-flight requests and repeat. **Chart both.**

**Part 7 — Queue-based scaling.** Workers with an HPA on queue depth, then on oldest-message age.

**Inject a burst of small tasks and a burst of large ones.** Compare how each metric responds.

**Oldest-age should scale appropriately for both; depth should over-scale for small tasks.**

**Part 8 — Spike response and the ceiling.** Measure end-to-end HPA response time: metric scrape → decision → schedule → pull → start → ready.

**Then find `minReplicas` such that a 5× spike is survived during that window.**

Then set `maxReplicas` high enough to exhaust PgBouncer. **Apply enough load to trigger it and confirm the database becomes the failure.**

**Then compute the correct `maxReplicas` and write the derivation as a comment in the manifest.**

**Done when:**
- A lying readiness probe dropped requests, and an accurate one did not
- The liveness cascade is reproduced as a self-sustaining outage
- You know the load at which `timeoutSeconds: 1` fails spuriously
- Your latency-versus-CPU-limit chart shows throttling with low reported usage
- Requests and limits are derived from measurement and compared to VPA
- The latency-based HPA feedback loop is charted, and in-flight scaling fixes it
- Oldest-age scaling handles both small and large task bursts correctly
- `maxReplicas` is derived from downstream capacity, with the arithmetic documented
