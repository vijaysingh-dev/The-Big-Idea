# Slots and Composition

## What a slot is

A placeholder in a child's template that the parent fills with markup.

```html
<!-- claimCard.html -->
<template>
    <article class="card">
        <header class="card-header">
            <slot name="title">Untitled claim</slot>
        </header>

        <div class="card-body">
            <slot></slot>
        </div>

        <footer class="card-footer">
            <slot name="actions"></slot>
        </footer>
    </article>
</template>
```

```html
<!-- parent -->
<c-claim-card>
    <h2 slot="title">{claim.Claim_Number__c}</h2>

    <p>{claim.Description__c}</p>
    <lightning-formatted-number value={claim.Claim_Amount__c}
                                format-style="currency"
                                currency-code="INR">
    </lightning-formatted-number>

    <lightning-button slot="actions" label="Approve" onclick={handleApprove}></lightning-button>
</c-claim-card>
```

**A named slot** is filled by elements with a matching `slot` attribute. **The default slot** — the one with no name — takes everything else.

Content inside the `<slot>` tag is **fallback**, shown only when the parent supplies nothing for it.

## The ownership rule

Slotted content belongs to the **parent**, not the child that renders it.

That is the single most important thing about slots, and it has three consequences:

**The parent's event handlers work.** `onclick={handleApprove}` calls a method on the parent, even though the button appears inside the child.

**The parent's styles apply.** A CSS class defined in the parent's stylesheet styles the slotted element; the child's styles generally do not reach it.

**The parent's data bindings work.** `{claim.Claim_Number__c}` resolves against the parent's properties.

The child only decides **where** the content appears, not what it is or how it behaves.

## Querying slotted content

```javascript
// In the CHILD — finds the slot element, not its content
this.template.querySelector('slot[name="actions"]');

// In the CHILD — reaches the light DOM content the parent passed in
this.querySelector('lightning-button');

// In the PARENT — the slotted content is in the parent's own template
this.template.querySelector('lightning-button');
```

`this.template` searches the component's own shadow root. `this` without `.template` searches the light DOM — the slotted content.

This distinction catches people, and in practice a child rarely needs to reach into slotted content at all. If it does, that is usually a signal the design should use a property instead.

## Knowing whether a slot was filled

```javascript
handleSlotChange(event) {
    // assignedElements tells you what the parent actually supplied
    this.hasActions = event.target.assignedElements().length > 0;
}
```

```html
<footer class="card-footer" lwc:if={hasActions}>
    <slot name="actions" onslotchange={handleSlotChange}></slot>
</footer>
```

The `slotchange` event fires when the slot's content changes. Without it, a card renders an empty footer whenever the parent supplies no actions.

There is a subtlety: the `lwc:if` wrapping the slot means the slot may not exist to fire the event in the first place. The usual workaround is to render the container always and hide it with CSS, or to have the parent declare whether it will supply actions:

```html
<c-claim-card show-actions>
```

The explicit property is less elegant and more reliable.

## When slots earn their place

**Layout components.** A card, a panel, a modal, a section — where the container owns the structure and the consumer owns the content.

**Consistent chrome across varied content.** Every claim card, asset card, and contract card shares a header and footer treatment while showing entirely different bodies.

**Wrapping with behaviour.** A collapsible section, a permission gate, a loading wrapper.

```html
<!-- permissionGate.html -->
<template>
    <template lwc:if={hasPermission}>
        <slot></slot>
    </template>
    <template lwc:else>
        <p class="slds-text-color_weak">You do not have access to this section.</p>
    </template>
</template>
```

```javascript
import { LightningElement, api } from 'lwc';
import CAN_APPROVE from '@salesforce/customPermission/Can_Approve_Claims';

export default class PermissionGate extends LightningElement {
    @api permission;

    get hasPermission() {
        // the custom permission import is a compile-time-checked boolean
        return this.permission === 'Can_Approve_Claims' ? CAN_APPROVE : false;
    }
}
```

```html
<c-permission-gate permission="Can_Approve_Claims">
    <lightning-button label="Approve" onclick={handleApprove}></lightning-button>
</c-permission-gate>
```

The gate knows nothing about what it wraps. Note that this hides UI rather than enforcing security — the Apex behind the button must still check the permission. See [[03.13 - Enforcing Security in Apex and SOQL]].

## When not to use slots

**When the parent is passing data, not markup.** A property is clearer, typed, and testable.

```html
<!-- Passing data as markup — awkward -->
<c-claim-card>
    <span slot="amount">{claim.Claim_Amount__c}</span>
</c-claim-card>

<!-- Passing data as data -->
<c-claim-card amount={claim.Claim_Amount__c}></c-claim-card>
```

**When the content varies by type rather than by markup.** Three slots for three possible bodies is a component doing too much; three separate components is clearer.

**When the child needs to inspect or transform the content.** Slotted content is opaque to the child by design; fighting that means the design is wrong.

## Composition without slots

Most composition in LWC is plain nesting with properties and events, not slots.

```html
<template>
    <c-claim-filter-bar filters={filters} onfilterchange={handleFilterChange}></c-claim-filter-bar>

    <template lwc:if={isLoading}>
        <lightning-spinner alternative-text="Loading claims"></lightning-spinner>
    </template>
    <template lwc:else>
        <c-claim-list claims={filteredClaims}
                      onclaimselected={handleClaimSelected}>
        </c-claim-list>
    </template>

    <c-claim-detail claim-id={selectedClaimId}></c-claim-detail>
</template>
```

Each child has a defined property interface and a defined event surface. The parent orchestrates.

**Slots are for structure; properties and events are for data and behaviour.** Reaching for slots where properties would do produces components that are harder to test, because the content is markup rather than a value.

## Designing composable components

The distinction worth holding, since it decides how a component is built.

**Presentational components** take data through properties, render it, and dispatch events. No Apex, no wires, no knowledge of where their data came from.

```javascript
export default class ClaimRow extends LightningElement {
    @api claim;
    @api showActions = false;
}
```

**Container components** fetch data, hold state, and coordinate children.

```javascript
export default class ClaimDashboard extends LightningElement {
    @api recordId;

    @wire(getClaims, { accountId: '$recordId' })
    claimResult;
}
```

The value of the split: presentational components are trivially testable — construct one, set a property, assert on the rendered output, with no Apex to mock. Containers need mocking, and there are fewer of them.

Mixing the two — a component that both fetches its own data and is meant to be reusable — produces something that can only be tested with a mocked wire and can only be used where that wire makes sense. See [[14.18 - Jest Testing for LWC]].

## Component granularity

Too coarse and the component is untestable and unreusable. Too fine and the org fills with components nobody can find.

Practical signals for splitting:

- The template exceeds roughly 150 lines
- Two distinct concerns share one class
- Part of it would be useful elsewhere
- Part of it rerenders frequently and the rest does not
- The class has more than a handful of `@api` properties

Practical signals against:

- The child would have a single property and no events
- It exists only to shorten the parent's template
- Nothing else will ever use it

A component per row in a list is usually justified — it isolates rerendering and keeps the row's logic contained. A component per field is not.

## A worked structure

```
claimDashboard          container: wires, state, orchestration
  claimFilterBar        presentational: filters in, filterchange out
  claimList             presentational: claims in, claimselected out
    claimRow            presentational: one claim in, actions out
  claimDetailPanel      container: wires the selected claim
    claimCard           layout: slots for title, body, actions
  claimApprovalModal    container: handles the approval interaction
```

Three containers, four presentational components, one layout component using slots. The presentational ones have no dependencies and test in milliseconds.

## Practical guidance

**Use slots for layout and wrapping**, not for passing data.

**Remember slotted content belongs to the parent** — its handlers, its styles, its data.

**Handle the empty slot case** with `slotchange` or an explicit property.

**Split presentational from container components.** It is what makes testing cheap.

**Prefer nesting with properties and events** to slots for most composition.

**Split when the template grows past readability**, not to shorten it cosmetically.
