# Dynamic Routes and Params

## Path params

```jsx
{ path: "products/:id", element: <ProductDetail /> }
{ path: "users/:userId/posts/:postId", element: <Post /> }
{ path: "docs/*", element: <Docs /> }              // splat — matches the rest
{ path: "files/:name?", element: <Files /> }       // optional segment
```

```jsx
const { id } = useParams();
const { "*": splat } = useParams();      // everything after "docs/"
```

**Params are always strings.** `useParams()` never gives you a number:

```jsx
const { id } = useParams();
const productId = Number(id);
if (!Number.isInteger(productId)) return <NotFound />;
```

Validate rather than trusting. A URL is user input — `/products/abc` and `/products/999999999999999999999` both arrive as strings, and passing them straight into a query or an array index is how injection and crash bugs happen ([[05.3 - Types Coercion and Equality]]).

For anything non-trivial, parse with a schema:

```ts
const paramsSchema = z.object({ id: z.coerce.number().int().positive() });
const parsed = paramsSchema.safeParse(useParams());
```

## Search params

```jsx
const [searchParams, setSearchParams] = useSearchParams();

const page = Number(searchParams.get("page") ?? 1);
const tags = searchParams.getAll("tag");           // repeated keys
const sort = searchParams.get("sort") ?? "recent";

setSearchParams({ page: "2", sort: "price" });     // replaces ALL params
setSearchParams(prev => {                          // updater — preserves others
  prev.set("page", "2");
  return prev;
});
```

The functional updater matters: the object form **replaces the entire query string**, silently dropping unrelated params. A sort control that wipes the active filters is a common bug from the object form.

`setSearchParams(next, { replace: true })` avoids creating a history entry — appropriate for a filter that changes on every keystroke, so back does not step through twenty intermediate states.

## Why search params beat state

```jsx
// Lost on refresh, unshareable, no back-button support
const [filters, setFilters] = useState({ category: "all", sort: "recent" });

// Shareable, refresh-safe, back-button works
const [params, setParams] = useSearchParams();
```

Filters, sort order, pagination, active tab, search query and open panels all belong in the URL ([[20.1 - Where State Should Live]]).

The test: **should refreshing preserve this, and should a colleague be able to paste the link?** If yes, it belongs in the URL.

This also removes an entire category of state synchronization code — the URL is the single source of truth, and components derive from it.

## A typed params hook

Raw `useSearchParams` is stringly-typed and repetitive. Wrapping it once pays off:

```jsx
function useFilters() {
  const [params, setParams] = useSearchParams();

  const filters = useMemo(() => ({
    page: Math.max(1, Number(params.get("page") ?? 1)),
    sort: SORTS.includes(params.get("sort")) ? params.get("sort") : "recent",
    tags: params.getAll("tag"),
  }), [params]);

  const setFilter = useCallback((key, value) => {
    setParams(prev => {
      if (value == null || value === "") prev.delete(key);
      else prev.set(key, String(value));
      if (key !== "page") prev.delete("page");   // reset pagination on filter change
      return prev;
    }, { replace: true });
  }, [setParams]);

  return { filters, setFilter };
}
```

Two details worth copying: **deleting empty values** keeps URLs clean rather than accumulating `?sort=&tag=`, and **resetting the page** when a filter changes prevents landing on page 7 of a 2-page result set.

Libraries like `nuqs` provide this with type inference and serializers if the hand-rolled version grows.

## Location state

```jsx
navigate("/products/42", { state: { from: location.pathname } });

const location = useLocation();
const from = location.state?.from;
```

Data attached to a history entry rather than the URL. Useful for "return to where you came from" after login, or passing a list item's data to a detail view to render immediately while the full record loads.

Three constraints: it must be **serializable** (it goes through structured clone, so no functions or class instances — [[08.5 - Serialization and Structured Clone]]); it is **lost on refresh** since it lives in the history entry, not the URL; and it is **not shareable**.

Always handle the absent case — a user who pastes the URL directly has no state.

## Params changing without unmounting

```jsx
// Navigating /products/1 → /products/2
function ProductDetail() {
  const { id } = useParams();
  // The component does NOT unmount — same route, same position
}
```

React Router keeps the component mounted when only the param changes, because the element type and position are unchanged ([[18.2 - Reconciliation and the Diffing Algorithm]]).

That means local state persists across the navigation — a scroll position, an open accordion, a form draft from the previous product. Sometimes desirable, often a bug.

To reset:

```jsx
<Route path=":id" element={<ProductDetail key={id} />} />
```

Or from inside, using the key on the content:

```jsx
const { id } = useParams();
return <ProductContent key={id} id={id} />;
```

Changing the key remounts with fresh state ([[16.6 - Lists and Keys]]).

## Encoding

```jsx
<Link to={`/search/${encodeURIComponent(query)}`}>
```

Path params containing slashes, spaces or `#` must be encoded. `useParams` decodes automatically on read, so encode on write and read plainly.

For search params, `URLSearchParams` handles encoding — never build a query string by concatenation ([[23.1 - Client Side Routing Fundamentals]]).

Slugs are usually better than raw text in paths:

```
/products/wireless-headphones-42     // readable, stable, SEO-friendly
/products/42?name=Wireless%20Head... // avoid
```

The convention is `slug-id` so the id is authoritative and the slug is cosmetic — changing the product name does not break existing links.

## Optional and catch-all segments

```jsx
{ path: "docs/*", element: <Docs /> }
```

Splat routes are how documentation sites, file browsers and CMS-driven pages map arbitrary depth onto one route. Read the remainder with `useParams()["*"]`.

Note that `*` matches greedily and ranks lowest, so more specific routes still win ([[23.2 - React Router Setup and Nested Routes]]).

## How senior engineers actually use this

**They put filter, sort, pagination and tab state in the URL** by default, and treat component state for those as a smell.

**They validate every param** rather than trusting it, since URLs are user input.

**They use the functional `setSearchParams` updater** so unrelated params survive.

**They reset pagination when filters change**, which is invisible until a user reports an empty page.

**They use `key` on param-driven routes** when stale local state across param changes would be wrong.

## Common pitfalls

- Treating params as numbers without conversion or validation.
- `setSearchParams({...})` wiping unrelated params.
- Every filter keystroke creating a history entry — needs `replace`.
- Stale component state when only a param changes.
- Location state assumed to survive a refresh.
- Unencoded values in path segments.
- Empty params accumulating in the URL.

## Interview angle

"How do you handle URL parameters" is a chance to make the state-placement argument: params and search params are shareable, refresh-safe state, so filters, sort and pagination belong there rather than in `useState`. The practical details that stand out are that params are always strings and must be validated, that the object form of `setSearchParams` replaces everything, and that a component does not unmount when only a param changes — so local state persists unless you key it.
