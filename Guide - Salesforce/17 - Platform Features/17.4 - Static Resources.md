# Static Resources

## What they are

Files stored as metadata and served from Salesforce — JavaScript libraries, stylesheets, images, fonts, and archives.

```
Setup → Static Resources → New

Name:         chartjs
File:         chart.min.js
Cache Control: Public
```

They deploy with your code, version with it, and are served over the org's domain — which matters for Content Security Policy, since a script loaded from a third-party CDN needs a CSP Trusted Site entry and a static resource does not.

## Loading in LWC

```javascript
import { LightningElement } from 'lwc';
import { loadScript, loadStyle } from 'lightning/platformResourceLoader';
import CHART_JS from '@salesforce/resourceUrl/chartjs';

export default class ClaimChart extends LightningElement {
    chartInitialized = false;

    renderedCallback() {
        // renderedCallback fires on every rerender; without the guard the library reloads
        if (this.chartInitialized) {
            return;
        }
        this.chartInitialized = true;

        loadScript(this, CHART_JS)
            .then(() => this.initializeChart())
            .catch((error) => this.handleError(error));
    }
}
```

**The guard is essential**, and its absence is the most common static resource bug — a chart that renders four times, or a library that throws on redefinition. See [[14.5 - Component Lifecycle Hooks]].

Loading several resources:

```javascript
Promise.all([
    loadScript(this, CHART_JS + '/chart.min.js'),
    loadScript(this, CHART_JS + '/chart-adapter.js'),
    loadStyle(this, CHART_JS + '/chart.min.css')
])
    .then(() => this.initializeChart())
    .catch((error) => this.handleError(error));
```

`Promise.all` loads in parallel. Where one script depends on another being defined first, chain them instead:

```javascript
loadScript(this, LIB + '/core.js')
    .then(() => loadScript(this, LIB + '/plugin.js'))
    .then(() => this.initialize());
```

## Zip archives

A zip lets one resource hold many files, referenced by path.

```
chartjs.zip
    chart.min.js
    chart.min.css
    fonts/
        chart-icons.woff2
```

```javascript
import CHART_JS from '@salesforce/resourceUrl/chartjs';

loadScript(this, CHART_JS + '/chart.min.js');
loadStyle(this, CHART_JS + '/chart.min.css');
```

**Use a zip for anything with more than one file**, which is nearly every library. It keeps relative paths inside the library working, and it keeps the static resource list navigable — an org with sixty individual resources is unmanageable.

The zip must be **flat or shallow**; deeply nested paths work and become unwieldy to reference.

## Images and other assets

```javascript
import LOGO from '@salesforce/resourceUrl/companyAssets';

export default class ClaimHeader extends LightningElement {
    logoUrl = LOGO + '/images/northwind-logo.svg';
}
```

```html
<img src={logoUrl} alt="Northwind Industrial"/>
```

In CSS, the URL cannot be imported, so a static resource image in a stylesheet needs the full path — which is why images used in CSS are often better as a data URI or an SLDS icon.

**For a formula field:**

```
IMAGE("/resource/statusIcons/warning.png", "Overdue", 16, 16)
```

The `/resource/` path is stable, and adding a cache-busting timestamp is possible but rarely necessary. See [[06.6 - Formula Patterns and Anti-Patterns]].

## Cache control

```
Public    cached by the browser and any intermediary, shared across users
Private   cached per user session only
```

**Public for anything not user-specific**, which is nearly everything — libraries, images, stylesheets. Private forces a fetch per session and is only correct where the content genuinely varies by user, which for a static file it should not.

Setting this to Private by mistake is a quiet performance cost on every page load.

## The shadow DOM problem

The constraint that decides whether a library is usable at all.

**Libraries that attach to a passed element work:**

```javascript
initializeChart() {
    const canvas = this.template.querySelector('canvas');
    // the library receives the element, so it never needs to search the document
    this.chart = new window.Chart(canvas.getContext('2d'), this.chartConfig);
}
```

**Libraries that search the global DOM do not:**

```javascript
// Cannot find an element inside a component's shadow root
$('#claimChart').someJqueryPlugin();
document.getElementById('claimChart');
```

Shadow DOM encapsulation means `document` queries cannot see inside a component. This rules out a whole class of older libraries.

The options when a library needs global DOM access:

**Check for a modern build.** Most actively maintained libraries now accept an element.

**Use light DOM** on that component, accepting the loss of encapsulation and documenting why. See [[14.15 - Styling, SLDS and Design Tokens]].

**Choose a different library.**

Checking this before committing to a library saves a substantial amount of rework, and the check is quick: does its initialization take an element, or a selector string?

## Locker Service and Lightning Web Security

Even a library that respects the DOM boundary may fail under the platform's JavaScript security layer, which restricts access to certain globals and APIs.

**Lightning Web Security** replaced Locker Service and is substantially more permissive — many libraries that failed under Locker work under LWS.

The practical approach: **test the library in a scratch org early**, before building around it. A library that works in a local Jest test may still fail in the org, because Jest does not apply the security layer.

## Size and limits

```
5 MB per static resource
250 MB total across all static resources
Counts toward file storage
```

The 5 MB per-resource cap is the one that bites — a large charting or mapping library with its fonts and locales can exceed it.

The mitigations:

**Use a minified production build**, not the development one.

**Split into several resources** where the library allows partial loading.

**Strip unused locales and plugins** from the archive.

**Reconsider the library.** A 4 MB dependency to draw a bar chart is worth questioning; `chart.js` or a hand-written SVG may serve.

## Third-party CDN, as an alternative

```javascript
// Requires a CSP Trusted Site entry
const script = document.createElement('script');
script.src = 'https://cdn.example.com/library.min.js';
```

**Generally the wrong choice on Salesforce.**

The reasons: it needs a CSP Trusted Site, it introduces an external dependency that can change or disappear, it fails when the CDN is unreachable, and it raises a supply-chain question that security reviews take seriously.

A static resource is versioned with your code, served from your domain, and cannot change underneath you. **Bundle it.**

## Versioning

Static resources have no built-in version, so an upgrade replaces the file.

Two approaches:

**Overwrite in place.** Simple, and every consumer gets the new version at once — which is what you want for a security patch and risky for a breaking change.

**Version in the name:**

```
chartjs_v3
chartjs_v4
```

Components migrate individually, and the old resource is deleted once nothing references it. Worth doing for a major version upgrade where behaviour changes.

**Deployment overwrites without warning**, so a resource updated in a sandbox and deployed replaces production's copy entirely. There is no merge.

## Visualforce and Aura

```html
<!-- Visualforce -->
<apex:includeScript value="{!URLFOR($Resource.chartjs, 'chart.min.js')}"/>
<apex:stylesheet value="{!URLFOR($Resource.chartjs, 'chart.min.css')}"/>
<apex:image value="{!URLFOR($Resource.companyAssets, 'images/logo.svg')}"/>
```

```javascript
// Aura
({
    afterRender: function(component, helper) {
        this.superAfterRender();
        $A.get("e.c:LoadResource");   // or ltng:require in markup
    }
})
```

```xml
<ltng:require scripts="{!$Resource.chartjs + '/chart.min.js'}"
              afterScriptsLoaded="{!c.initializeChart}"/>
```

`URLFOR` with a second argument is how a path inside a zip is referenced in Visualforce.

## Testing

Jest does not load static resources, so a component depending on one needs the library mocked:

```javascript
jest.mock(
    'lightning/platformResourceLoader',
    () => ({
        loadScript: jest.fn(() => Promise.resolve()),
        loadStyle: jest.fn(() => Promise.resolve())
    }),
    { virtual: true }
);

beforeEach(() => {
    // the component reads window.Chart, so the global must exist in the test
    global.Chart = jest.fn(() => ({ destroy: jest.fn(), update: jest.fn() }));
});
```

Testing that the library is loaded once rather than on every render is worth an assertion:

```javascript
it('loads the charting library only once', async () => {
    const element = createElement('c-claim-chart', { is: ClaimChart });
    document.body.appendChild(element);
    await flushPromises();

    element.claims = [{ Id: 'a1' }];
    await flushPromises();

    expect(loadScript).toHaveBeenCalledTimes(1);
});
```

See [[14.18 - Jest Testing for LWC]].

## Practical guidance

**Guard loading in `renderedCallback`.** It fires on every rerender.

**Use a zip** for anything with more than one file.

**Set cache control to Public** unless the content is genuinely user-specific.

**Check whether the library accepts an element** before committing to it — global DOM access does not work.

**Test the library in a scratch org early**, since Jest does not apply the platform's security layer.

**Bundle rather than using a CDN.**

**Use minified production builds**, and strip unused locales.

**Version in the name** for a breaking upgrade.

**Mock `platformResourceLoader`** in Jest tests.
