## Requirements Clarification

**Functional:**
- Product catalog: browse, search, filter by category/price/brand
- Shopping cart: add/remove items, persist across sessions
- Checkout: address, payment, order placement
- Inventory: real-time stock levels, prevent overselling
- Order management: track status, cancel, return/refund
- Flash sales: limited inventory items available for a short time

**Non-functional:**
- Product browse: < 100ms p99
- Checkout: < 500ms p99
- Inventory consistency: never oversell (strong consistency for stock deduction)
- Flash sale: handle 100× normal traffic spike in < 30 seconds
- 99.99% availability for checkout path
- Cart persistence: survive user browser close/restart

**Out of scope:** Seller onboarding, warehouse management, logistics, ads

## Estimation

```
DAU: 50M users
Product catalog: 100M SKUs
Peak browsing: 50M × 10 page views/day = 500M page views/day = 5,800/s
Peak orders: 1M orders/day = ~12/s; flash sale peak: 120/s

Cart sessions: 50M × 1 cart = 50M carts
  Cart size: avg 3 items × 100 bytes = 300 bytes
  Total: 50M × 300 bytes = 15 GB → fits in Redis

Inventory writes (stock deductions):
  1M orders/day × avg 2 items = 2M deductions/day = ~23/s
  Flash sale: 23/s × 100 = 2,300 deductions/s in 1 minute
```

## Product Catalog

### Read Path (browse/search)

Catalog reads are high-volume, read-heavy, eventually consistent:

```
Product listing page:
  1. Elasticsearch query (search/filter/facets)
  2. Hydrate with pricing from Redis cache
  3. Return to user

Cache strategy:
  Product detail (rarely changes): Redis, TTL 5 min
  Pricing (changes often): Redis, TTL 30s
  Stock level (changes constantly): don't cache — fetch from Inventory Service
```

### Product Data Model

```sql
-- Core product table (PostgreSQL, source of truth)
CREATE TABLE products (
    id           UUID PRIMARY KEY,
    sku          VARCHAR(100) UNIQUE NOT NULL,
    name         TEXT NOT NULL,
    description  TEXT,
    category_id  INT REFERENCES categories(id),
    brand_id     INT REFERENCES brands(id),
    status       VARCHAR(20) DEFAULT 'active'  -- active, discontinued, draft
);

-- Pricing (separate table — changes frequently)
CREATE TABLE product_pricing (
    product_id   UUID REFERENCES products(id),
    price_cents  INT NOT NULL,
    currency     CHAR(3) NOT NULL DEFAULT 'INR',
    sale_price   INT,                           -- null if no sale
    sale_ends_at TIMESTAMPTZ,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (product_id, currency)
);

-- Variants (size, color, etc.)
CREATE TABLE product_variants (
    id           UUID PRIMARY KEY,
    product_id   UUID REFERENCES products(id),
    sku          VARCHAR(100) UNIQUE NOT NULL,
    attributes   JSONB,   -- {"color": "red", "size": "L"}
    price_delta  INT DEFAULT 0  -- added to base price
);
```

## Inventory Service — The Hard Part

Inventory is the most consistency-sensitive component. Overselling is a P0 incident.

### Storage: Redis for Hot Path

```
Key:   inventory:{variant_id}
Value: available quantity (integer)
Type:  Redis integer (DECR is atomic)

DECR inventory:sku-001 → new quantity
  If result >= 0: success (stock reserved)
  If result < 0:  failure (INCR back, out of stock)
```

**Atomic decrement:** Redis is single-threaded; DECR is atomic. No two concurrent requests can both succeed for the last unit.

```python
def reserve_stock(variant_id: str, quantity: int) -> bool:
    """Atomically reserve stock. Returns True if successful."""
    script = """
    local current = redis.call('GET', KEYS[1])
    if current == false or tonumber(current) < tonumber(ARGV[1]) then
        return 0
    end
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
    """
    result = redis.eval(script, 1, f"inventory:{variant_id}", quantity)
    return bool(result)
```

### Durability: PostgreSQL as Source of Truth

Redis is fast but not durable by default. PostgreSQL holds the true inventory:

```sql
CREATE TABLE inventory (
    variant_id    UUID PRIMARY KEY,
    quantity      INT NOT NULL CHECK (quantity >= 0),
    reserved      INT NOT NULL DEFAULT 0,    -- held by in-flight orders
    available     INT GENERATED ALWAYS AS (quantity - reserved) STORED,
    updated_at    TIMESTAMPTZ
);
```

**Sync strategy:**
```
On stock deduction:
  1. DECR Redis (fast, for throughput)
  2. Write to Kafka: stock-events
  3. Async consumer: UPDATE inventory SET reserved = reserved + 1 WHERE variant_id = X

On order completion/cancellation:
  1. UPDATE inventory SET quantity = quantity - 1, reserved = reserved - 1 (completed)
     OR quantity unchanged, reserved = reserved - 1 (cancelled → stock returns)
  2. INCR Redis if cancellation (return stock)
```

**Redis cold start:** On service restart, populate Redis from PostgreSQL:
```python
def warm_inventory_cache():
    rows = db.query("SELECT variant_id, available FROM inventory")
    pipe = redis.pipeline()
    for row in rows:
        pipe.set(f"inventory:{row.variant_id}", row.available)
    pipe.execute()
```

## Shopping Cart

Cart is user-specific, session-length data — perfect for Redis.

```
Key:   cart:{user_id}
Type:  Redis Hash
Fields: {variant_id: quantity, ...}

HSET cart:42 "sku-001" 2   # add 2 units of sku-001
HSET cart:42 "sku-002" 1   # add 1 unit of sku-002
HGETALL cart:42            # get full cart
HDEL cart:42 "sku-001"     # remove item
DEL cart:42                # clear cart after checkout
TTL: 30 days
```

**Guest cart → logged-in cart merge:**
```python
def merge_carts(guest_cart_id, user_id):
    guest_items = redis.hgetall(f"cart:{guest_cart_id}")
    for variant_id, quantity in guest_items.items():
        # Add guest quantities to existing user cart
        redis.hincrby(f"cart:{user_id}", variant_id, int(quantity))
    redis.delete(f"cart:{guest_cart_id}")
```

## Checkout Flow

Checkout is the most critical path. Every step must be correct and atomic.

```
1. User clicks "Place Order"

2. Checkout Service:
   a. Validate cart (items still exist, prices haven't changed significantly)
   b. Reserve inventory for all items (atomic multi-item reservation)
   c. Create order in PENDING state (PostgreSQL)
   d. Return order_id to client

3. Client shows payment UI

4. Payment:
   a. Client tokenizes card client-side
   b. POST /checkout/{order_id}/pay { payment_token, idempotency_key }
   c. Payment Service charges card
   d. On success: ORDER → CONFIRMED, inventory deducted permanently
   e. On failure: ORDER → PAYMENT_FAILED, inventory reservation released

5. Post-order (async):
   → Email confirmation
   → Warehouse notified
   → Analytics event
```

### Multi-Item Inventory Reservation

Reserving multiple items atomically (all-or-nothing):

```python
def reserve_cart_inventory(cart_items: List[CartItem]) -> bool:
    """
    Reserve all items atomically using Lua script.
    If any item is out of stock, roll back all reservations.
    """
    keys = [f"inventory:{item.variant_id}" for item in cart_items]
    quantities = [item.quantity for item in cart_items]

    script = """
    -- First pass: check all have sufficient stock
    for i, key in ipairs(KEYS) do
        local stock = tonumber(redis.call('GET', key))
        if not stock or stock < tonumber(ARGV[i]) then
            return 0  -- insufficient stock
        end
    end
    -- Second pass: deduct all
    for i, key in ipairs(KEYS) do
        redis.call('DECRBY', key, ARGV[i])
    end
    return 1  -- success
    """

    result = redis.eval(script, len(keys), *keys, *quantities)
    return bool(result)
```

## Flash Sale Architecture

Flash sales create 100× traffic spikes on specific SKUs.

### Problem

Normal traffic: 23 inventory deductions/s  
Flash sale: 10,000 users simultaneously hit "Buy Now" for 100 units

### Solution: Pre-Sale Queue + Token-Based Access

```
Pre-sale phase (before sale starts):
  Users register interest → waiting room

Sale start:
  1. Issue "purchase tokens" to first N users in waiting room
     N = flash sale quantity × 1.2 (20% buffer for abandonment)
  2. Only token holders can add to cart and checkout

Checkout:
  Token validated at checkout → proceed
  No token → "Sale ended" message
```

This bounds the concurrent users who can actually hit the inventory service — preventing thundering herd.

### Rate Limiting by SKU

```
For flash_sale products:
  Rate limit: max 100 reserve attempts/s per SKU (not per user)
  Excess requests: queue + try again (or reject with retry-after)

Redis-based rate limiter key: rate_limit:inventory:{variant_id}
```

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Redis inventory cache miss/down | Fall back to PostgreSQL | Circuit breaker; accept higher latency; block flash sales (too risky without Redis) |
| Payment fails after inventory reserved | Stock held but not deducted | Release reservation on PAYMENT_FAILED; timeout sweeper releases stuck reservations |
| Order placed but notification not sent | Customer not notified | Async retry queue for notifications; order status page shows truth |
| Inventory oversold (Redis + PostgreSQL diverge) | More orders than stock | Reconciliation job detects divergence; oversold orders get apology + refund |
| Flash sale bot abuse | Bots buy all stock instantly | CAPTCHA, device fingerprinting, purchase token lottery, account verification |

---

## What This Design Demonstrates

- Atomic Redis DECRBY for inventory (prevents overselling without DB lock)
- Lua script for multi-item atomic reservation (all-or-nothing)
- Two-phase checkout: reserve first, charge second (release reservation on failure)
- Cart in Redis with hash data structure
- Flash sale waiting room + purchase token pattern
