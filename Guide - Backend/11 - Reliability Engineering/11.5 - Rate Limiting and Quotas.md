# Rate Limiting and Quotas

#backend #reliability #api-design

> **In one line:** A rate limit protects your capacity from one caller, a quota enforces a commercial agreement, and the algorithm you pick determines whether a legitimate burst is served or rejected.

---

## The Idea

```
Rate limit   protects the system      "100 requests per second"
Quota        enforces an agreement    "1 million requests per month"
```

| | Rate limit | Quota |
|---|---|---|
| Window | Seconds | Days or months |
| Purpose | **Capacity protection** | **Commercial** |
| Response | 429, retry shortly | 402/403, upgrade or wait |
| Enforced at | Gateway | Application |
| Reset | Continuous | Billing period |

💡 **They are frequently conflated and they need different answers.** A user hitting a rate limit should retry in a second; a user hitting a quota should be told to upgrade.

⚠️ **Returning 429 for a quota exhaustion sends clients into a retry loop against something that will not clear for three weeks.**

---

## The Algorithms

### Fixed window

```python
key = f"rl:{client}:{int(time.time()) // 60}"
count = await redis.incr(key)
if count == 1:
    await redis.expire(key, 120)
return count <= LIMIT
```

Simple, and it has a real flaw:

```
Limit: 100/minute
12:00:59 → 100 requests    ✅
12:01:00 → 100 requests    ✅
→ 200 requests in one second
```

⚠️ **A fixed window permits twice the limit across a boundary.** For a limit protecting capacity, that burst is exactly what you were preventing.

### Sliding window log

```python
now = time.time()
await redis.zremrangebyscore(key, 0, now - WINDOW)
count = await redis.zcard(key)
if count < LIMIT:
    await redis.zadd(key, {str(uuid4()): now})
```

**Exact**, and it stores one entry per request.

⚠️ **Memory is proportional to the limit.** A 10,000/hour limit for 100,000 clients is a billion entries.

### Sliding window counter

```python
current = await redis.get(f"rl:{client}:{cur_window}") or 0
previous = await redis.get(f"rl:{client}:{prev_window}") or 0
elapsed = (now % WINDOW) / WINDOW
estimate = previous * (1 - elapsed) + current
return estimate < LIMIT
```

💡 **Approximate, two counters per client, and it eliminates the boundary burst.** This is the practical default for HTTP rate limiting.

### Token bucket

```python
async def allow(key: str, rate: float, burst: int, cost: int = 1) -> bool:
    now = time.time()
    tokens, last = await redis.hmget(key, "tokens", "ts")
    tokens = min(burst, float(tokens or burst) + (now - float(last or now)) * rate)
    if tokens < cost:
        return False
    await redis.hset(key, mapping={"tokens": tokens - cost, "ts": now})
    return True
```

💡 **Allows a burst up to `burst` and sustains `rate`**, which matches how real clients behave — idle, then a batch of requests.

⚠️ **Must be atomic.** Read-modify-write across two clients double-spends the bucket. **Use a Lua script**, or Redis's `CL.THROTTLE` from redis-cell.

**Token bucket is the right default for anything where cost varies** — a GraphQL query costing 50 points, an expensive export costing 1,000 ([[05.8 - GraphQL Security and Limits]]).

### Leaky bucket

Requests queue and drain at a fixed rate. **Smooths output**, and it adds latency and needs a queue.

💡 **Use when the downstream requires a strictly constant rate** — a third-party API with a hard cap.

### Choosing

| Need | Algorithm |
|---|---|
| Simple HTTP limiting | **Sliding window counter** |
| Bursty clients, variable cost | **Token bucket** |
| Exact enforcement, small limits | Sliding window log |
| Smoothing to a constant rate | Leaky bucket |
| Protecting a fixed downstream capacity | Concurrency limit, not a rate limit |

⚠️ **The last row is under-appreciated.** If your constraint is "the database handles 50 concurrent queries", a rate limit is the wrong tool — **limit concurrency directly** ([[11.4 - Backpressure and Load Shedding]]).

## What to Limit On

```
IP address          anonymous traffic. Shared by NAT and corporate networks
API key             the caller
User ID             the person
Organisation        the tenant. Usually the right unit for SaaS
Endpoint            expensive endpoints separately
Cost                weighted, for variable-cost operations
```

💡 **For a multi-tenant product, limit per organisation.** A large customer with 500 employees legitimately makes more requests than a small one, and per-user limiting makes them all equal ([[06.16 - Multi Tenant Data Models]]).

⚠️ **IP-based limiting punishes NAT.** An entire office behind one address shares a limit, and a single abusive user blocks their colleagues.

**Layer them:**

```python
checks = [
    ("ip", client_ip, 1000, 60),               # coarse abuse protection
    ("org", org_id, plan_limit(org), 60),      # the commercial limit
    ("org_endpoint", f"{org_id}:{route}", 100, 60),   # expensive endpoints
]
```

💡 **A global limit and a per-endpoint limit together** stop both "too many requests" and "too many expensive requests".

## Telling the Client

```http
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 1000
RateLimit-Remaining: 0
RateLimit-Reset: 34
Retry-After: 34
```

⚠️ **`Retry-After` is what stops a client retrying immediately.** Without it, a rate-limited client hammers you continuously.

💡 **Return the headers on *successful* responses too**, not just 429s. A client that can see it has 12 requests remaining can slow down before being blocked, which is much better for both sides.

```json
{
  "type": "https://api.conduit.local/errors/rate-limited",
  "title": "Rate limit exceeded",
  "status": 429,
  "detail": "1000 requests per minute for organisation org_7",
  "retry_after_seconds": 34,
  "limit": 1000,
  "remaining": 0
}
```

**Say which limit was hit** ([[05.3 - Error Design]]). "Rate limited" is unactionable when a client is subject to four different limits.

## Distributed Enforcement

⚠️ **A per-instance limit multiplies by your instance count.**

```
Limit: 100/min per instance
10 instances → 1,000/min actual
Autoscale to 20 → 2,000/min
```

💡 **The limit changes when you scale, which is exactly when you least want it to.**

### Shared state in Redis

```lua
-- Atomic token bucket
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens') or ARGV[2])
local last = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3])
tokens = math.min(tonumber(ARGV[2]), tokens + (ARGV[3] - last) * ARGV[1])
if tokens < tonumber(ARGV[4]) then return 0 end
redis.call('HSET', KEYS[1], 'tokens', tokens - ARGV[4], 'ts', ARGV[3])
redis.call('EXPIRE', KEYS[1], 3600)
return 1
```

⚠️ **A Redis round trip per request adds latency and makes Redis a dependency of every request.**

```python
try:
    allowed = await redis_limiter.allow(key)
except RedisError:
    rate_limit_degraded_total.inc()
    allowed = local_limiter.allow(key)          # ← fail open, with a local fallback
```

💡 **Decide explicitly whether to fail open or closed.** Failing closed on a Redis outage means a cache problem becomes a total outage; failing open means you are briefly unprotected. **Fail open with a conservative local limit** is usually right.

### Local-with-sync

```python
# Each instance enforces locally, syncing its usage periodically
local_count += 1
if time.monotonic() - last_sync > 1.0:
    global_count = await redis.incrby(key, local_count)
    my_share = LIMIT / instance_count
```

💡 **Approximate, and one Redis call per second instead of per request.** For high-throughput limiting where exactness does not matter, this removes Redis from the request path entirely.

## In Production

### Where to enforce

```
Gateway      IP limits, coarse per-key limits    ← cheapest rejection
Application  per-org, per-endpoint, cost-based   ← needs domain knowledge
Downstream   concurrency limits                   ← protects a specific resource
```

💡 **Reject as early as possible.** A request rejected at the gateway costs a fraction of one rejected after authentication and a database lookup ([[10.6 - API Gateway and BFF]]).

⚠️ **But per-organisation limiting requires knowing the organisation**, which requires authentication — so it cannot be at the very edge. **The layering exists for this reason.**

### Limits are a product decision

```
Free:        100 req/min,   10k/month
Pro:       1,000 req/min,  500k/month
Enterprise: custom
```

⚠️ **Setting limits from engineering intuition produces limits that block legitimate use.** Measure the distribution of actual usage first.

```sql
SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY requests_per_minute)
FROM usage_by_org WHERE plan = 'pro';
```

💡 **Set the limit above the p99.9 of legitimate usage**, then run in log-only mode for a week before enforcing ([[05.8 - GraphQL Security and Limits]]).

**The log-only phase always reveals someone doing something outrageous that nobody knew about.**

### Monitoring

```python
rate_limit_checks_total.labels(scope=s, result="allowed"|"limited").inc()
rate_limit_remaining.labels(org=o).set(n)          # ⚠️ cardinality
rate_limit_check_duration_seconds.observe(elapsed)
rate_limit_degraded_total.inc()                     # Redis unavailable
quota_consumed_ratio.labels(org=o, plan=p).set(r)
```

⚠️ **Per-organisation metrics are unbounded cardinality.** Export the top N by usage, or aggregate by plan tier, rather than labelling by organisation.

💡 **`quota_consumed_ratio` above 0.8 is a sales signal, not just an operational one.** A customer consistently at 90% of their quota is ready to upgrade, and telling them before they hit the wall is better product behaviour than a 402.

### Graceful quota exhaustion

```python
if usage > quota:
    if usage < quota * 1.1:
        return await handle(request, degraded=True)     # soft limit, warn
    raise QuotaExceeded(...)
```

💡 **A hard cutoff at exactly the quota is hostile.** A soft limit with a warning period, then a hard limit, gives customers time to react — and it converts a support ticket into an upgrade conversation.

⚠️ **Never cut off in the middle of a critical operation.** Check the quota at the start of a workflow, not before every step ([[10.5 - Distributed Transactions and Sagas]]).

### Rate limiting is not abuse prevention

⚠️ **A rate limit slows an attacker; it does not stop them.**

| Attack | Rate limit helps? |
|---|---|
| Accidental client loop | **Yes** |
| Scraping | Somewhat — they distribute across IPs |
| Credential stuffing | Somewhat — needs per-account limiting too |
| **Distributed DDoS** | **No** — needs upstream filtering |
| Cache penetration | Partially ([[07.3 - Stampede Hot Keys and Negative Caching]]) |

💡 **A client with a 100% cache miss rate over many requests is either broken or hostile**, and that signal is cheaper to compute than most abuse heuristics.

### Conduit's limits

| Scope | Limit | Algorithm | Where |
|---|---|---|---|
| IP, anonymous | 100/min | Sliding window counter | Gateway |
| Organisation, all endpoints | Plan-based | **Token bucket** | Gateway |
| Organisation, uploads | 20/min | Token bucket | Application |
| Organisation, exports | 5/hour | Token bucket | Application |
| **GraphQL** | Cost-based points | Token bucket | Application ([[05.8 - GraphQL Security and Limits]]) |
| Embedding API (outbound) | **Global**, shared | Token bucket in Redis | Client |
| Monthly documents | Plan quota | Counter | Application |

💡 **The outbound limit is the one people forget.** Your own calls to a third-party API with a global quota must be limited across all your workers, not per worker ([[08.7 - Routing Queues Priorities and Prefetch]]).

⚠️ **Per-worker `rate_limit` in Celery multiplies by worker count** — a genuine and common bug.

## Codebase

**Repo:** `redis/redis` (+ redis-cell), `envoyproxy/envoy`, `github` (docs)

**Question to answer:** How does a distributed token bucket stay atomic under concurrency? Then: how does GitHub's GraphQL rate limiting compute cost, and how does it expose the budget?

**Read, in order:**

1. `brandur/redis-cell` — **`CL.THROTTLE`, a generic cell rate algorithm implemented as a Redis module.** Small, and it is the reference atomic token bucket. **The answer to the first question**
2. `envoy/source/extensions/filters/http/local_ratelimit/` and `ratelimit/` — **local versus global rate limiting**, and the tradeoff between a per-instance limit and a shared service
3. `envoyproxy/ratelimit` — the reference global rate limit service. Note the descriptor model, which allows layered limits
4. **GitHub GraphQL resource limitations** — **the cost formula and the budget exposed in every response.** The answer to the second question
5. `redis/redis/src/script_lua.c` — why a Lua script is atomic: it runs to completion with no interleaving ([[07.4 - Distributed Locks Done Right]])

💡 The redis-cell implementation is worth reading in full — it is a few hundred lines implementing the GCRA (generic cell rate algorithm), which is a token bucket that stores a single timestamp rather than a token count. **That representation is cleverer and cheaper than the naive version**, and it is directly portable.

**Size:** 1 session.

**Then the boundary test specifically:** 100 requests at 12:00:59 and 100 at 12:01:00 against a 100/minute limit.

**Confirm fixed window allows 200 and sliding counter does not.**

**Part 2 — Distributed enforcement.** A token bucket enforced per instance, across 1, 5 and 20 replicas.

**Measure the actual rate.** Confirm it multiplies by replica count.

**Part 3 — Atomicity.** Implement the token bucket with a read-modify-write in Python rather than Lua.

**Part 4 — Redis down.** Take Redis out during limiting.

**Fail closed:** measure the error rate. **Fail open:** measure the requests that got through unprotected. **Fail open with a local fallback:** measure both.

**Write down which you would choose and the reasoning.**

**Part 5 — Layered limits.** IP, organisation and per-endpoint limits together.

Simulate: one abusive IP, one organisation exceeding its plan, and one organisation hammering an expensive endpoint while staying under its global limit.

**Confirm each is caught by the right layer**, and that the error response identifies which limit was hit.

**Part 6 — Calibration.** Generate realistic per-organisation traffic with a long tail.

**Part 7 — Client behaviour.** Two clients: one that respects `Retry-After`, one that retries immediately.

**Measure the load each generates while rate limited**, and the time until each completes its work.

**The respectful client should finish sooner**, which is the argument for the header.

Then add `RateLimit-Remaining` to successful responses and implement a client that slows down proactively. **Measure how often it hits the limit at all.**

**Done when:**
- Your five-algorithm comparison covers accuracy, memory, latency and burst
- Fixed window demonstrably allows 2× across a boundary
- Per-instance limiting multiplied by replica count, and shared state fixed it
- A non-atomic bucket over-admitted under concurrency
- You have chosen and justified a Redis-failure policy
- Three abuse patterns are each caught by the right layer
- Your limits are calibrated from a measured distribution
- A `Retry-After`-respecting client finishes faster than one that ignores it
