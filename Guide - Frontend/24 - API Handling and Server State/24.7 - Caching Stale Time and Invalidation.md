# Caching, Stale Time and Invalidation

Two independent timers govern every cache entry, and confusing them is the most common source of "why is it refetching" and "why is it not refetching".

## staleTime vs gcTime

**`staleTime`** — how long data is considered **fresh**. While fresh, no refetch happens for any reason. Default: `0`.

**`gcTime`** — how long an **unused** entry stays in memory before being garbage collected. Default: 5 minutes.

```jsx
useQuery({
  queryKey: ["products"],
  queryFn: getProducts,
  staleTime: 5 * 60_000,     // fresh for 5 minutes
  gcTime: 30 * 60_000,       // kept for 30 minutes after nothing uses it
});
```

The lifecycle:

```
fetch → fresh (staleTime) → stale → [still cached, still shown]
                                   ↓ no observers
                            unused → (gcTime) → removed
```

Stale data is **still served immediately**. Staleness triggers a background refetch, it does not blank the screen. This is the stale-while-revalidate model, and it is why the default `staleTime: 0` does not cause loading spinners — it causes background refetches ([[15.7 - HTTP Caching and CDNs]]).

`gcTime` must be greater than `staleTime`, or entries are evicted before they can be revalidated.

## What triggers a refetch

A **stale** query refetches when:

- A new component mounts with that key (`refetchOnMount`)
- The window regains focus (`refetchOnWindowFocus`)
- The network reconnects (`refetchOnReconnect`)
- `invalidateQueries` marks it stale
- `refetch()` is called explicitly
- `refetchInterval` fires

A **fresh** query does none of these. That is the whole purpose of `staleTime`.

```jsx
useQuery({
  staleTime: 30_000,
  refetchOnWindowFocus: true,     // default
  refetchOnMount: true,           // default
  refetchInterval: 60_000,        // polling
  refetchIntervalInBackground: false,   // pause when the tab is hidden
});
```

Refetch-on-focus surprises people initially — switching browser tabs and returning triggers refetches. It is usually correct behavior (the data may have changed while you were away), and the fix for it being too aggressive is a longer `staleTime`, not disabling the trigger.

## Choosing staleTime

The question is: **how long is it acceptable to show data that may have changed?**

```
Reference data (countries, categories)     Infinity
User profile, settings                     5-30 min
Product catalogue                          1-5 min
Dashboard metrics                          30-60s
Notification count, live prices            0-10s
Cart, inventory                            0
```

Setting a global default and overriding per query is the practical approach:

```jsx
new QueryClient({
  defaultOptions: { queries: { staleTime: 60_000 } },
});
```

`staleTime: Infinity` means "never refetch automatically" — appropriate for data that only changes through your own mutations, which you will invalidate explicitly.

## Invalidation

```jsx
queryClient.invalidateQueries({ queryKey: ["products"] });
```

Marks matching queries stale and refetches those currently mounted. Unmounted ones refetch on their next mount.

Matching is by **key prefix**, which is why hierarchical keys matter ([[24.6 - TanStack Query Fundamentals]]):

```jsx
["products"]                          // invalidating this...
["products", "list", { page: 1 }]     // ...matches this
["products", "detail", 42]            // ...and this
```

Narrower targeting:

```jsx
queryClient.invalidateQueries({ queryKey: productKeys.lists() });          // lists only
queryClient.invalidateQueries({ queryKey: ["products"], exact: true });    // no children
queryClient.invalidateQueries({
  predicate: (q) => q.queryKey[0] === "products" && q.state.dataUpdatedAt < cutoff,
});
```

Invalidation is the default tool after a mutation because it is **correct by construction** — the server is the source of truth and you refetch it. Direct cache writes are faster but can drift.

## Direct cache updates

```jsx
useMutation({
  mutationFn: updateProduct,
  onSuccess: (updated) => {
    queryClient.setQueryData(productKeys.detail(updated.id), updated);

    queryClient.setQueriesData(
      { queryKey: productKeys.lists() },
      (old) => old && {
        ...old,
        items: old.items.map(p => p.id === updated.id ? updated : p),
      }
    );
  },
});
```

Avoids a round trip when the mutation response contains the complete new state.

Three cautions: the updater must handle `undefined` (the entry may not exist); the update must be **immutable**, since the cache compares by reference ([[06.7 - Immutable Data Patterns]]); and if the server computes anything the client cannot predict — a derived total, a modified timestamp, a re-sorted position — the cache diverges silently.

A pragmatic combination: `setQueryData` for the entity that was returned, `invalidateQueries` for lists whose ordering or membership may have changed.

## Prefetching

```jsx
// On hover
<Link onMouseEnter={() => queryClient.prefetchQuery(productQuery(id))} />

// In a router loader — blocks navigation until the data is ready
loader: ({ params }) => queryClient.ensureQueryData(productQuery(params.id)),
```

`prefetchQuery` is fire-and-forget and respects `staleTime` — a fresh entry is not refetched. `ensureQueryData` returns the data, fetching only if absent ([[23.5 - Lazy Routes]]).

Prefetching on hover typically buys 100–300ms, which is enough to make a navigation feel instantaneous.

## Placeholder and initial data

```jsx
// placeholderData — shown but treated as absent; still fetches
useQuery({ ...productQuery(id), placeholderData: { name: "Loading..." } });

// initialData — treated as real, cached, respects staleTime
useQuery({ ...productQuery(id), initialData: cachedFromList });

// keepPreviousData — show the previous key's data during a key change
useQuery({ ...productsQuery(page), placeholderData: keepPreviousData });
```

The distinction matters: `initialData` is written to the cache and starts the staleness clock, so stale seed data will not refetch until `staleTime` elapses. `placeholderData` is display-only and always fetches.

Seeding a detail query from a list entry is a common optimisation:

```jsx
placeholderData: () =>
  queryClient.getQueryData(productKeys.lists())?.items.find(p => p.id === id),
```

The detail view renders instantly with partial data and fills in when the full record arrives.

## Persistence

```jsx
persistQueryClient({
  queryClient,
  persister: createSyncStoragePersister({ storage: window.localStorage }),
  maxAge: 24 * 60 * 60 * 1000,
  buster: APP_VERSION,
});
```

Survives page reloads, so a returning user sees content immediately while it revalidates.

Two requirements: a **buster** keyed to the app version, or a schema change leaves incompatible cached shapes in place; and care about **what** is persisted — never persist queries containing tokens or sensitive personal data to `localStorage` ([[14.2 - LocalStorage and SessionStorage]]).

## Cache size

The cache grows with distinct keys. A query keyed by a search string accumulates one entry per search:

```jsx
useQuery({
  queryKey: ["search", query],
  gcTime: 2 * 60_000,        // short — searches are rarely revisited
});
```

`gcTime` is the eviction control. Set it short for high-cardinality keys and long for stable ones. Unbounded growth is otherwise a slow memory leak in a long-lived SPA ([[07.1 - How Garbage Collection Works]]).

## Debugging

The DevTools panel shows every entry with its state — fresh, stale, fetching, inactive — plus the last fetch time and the cached data. For "why did this refetch" and "why is this not updating", it answers in seconds what would otherwise be guesswork.

The two questions to ask: is the key what I expect, and is the entry fresh or stale?

## How senior engineers actually use this

**They set `staleTime` per data type**, derived from how long stale data is acceptable, rather than leaving the default.

**They invalidate rather than write** by default, and use `setQueryData` only when the response contains the complete new state.

**They keep a key factory** so invalidation targets are unambiguous.

**They prefetch on hover and in loaders**, which removes most perceived navigation latency.

**They set short `gcTime` for high-cardinality keys** like searches and filters.

## Common pitfalls

- Confusing `staleTime` with `gcTime`.
- Leaving `staleTime: 0` and being surprised by constant refetching.
- Disabling `refetchOnWindowFocus` instead of raising `staleTime`.
- `setQueryData` updaters that mutate, or that assume the entry exists.
- Direct cache writes drifting from server-computed fields.
- `initialData` with stale seed data blocking a refetch.
- Unbounded cache growth from search-keyed queries.
- Persisting sensitive data to `localStorage`.

## Interview angle

"How do you handle caching and invalidation" is the question, and the `staleTime` versus `gcTime` distinction is the core: one controls freshness and refetch triggers, the other controls memory eviction of unused entries. Add that stale data is still served while revalidating — the stale-while-revalidate model — and that hierarchical query keys make prefix invalidation possible. Noting when to write to the cache directly versus invalidate, and the drift risk of the former, shows practical judgement.
