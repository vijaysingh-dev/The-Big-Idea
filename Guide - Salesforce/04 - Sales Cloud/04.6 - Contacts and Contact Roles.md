# Contacts and Contact Roles

## Contact basics

A Contact is a person, related to an Account through `AccountId`. `FirstName`, `LastName`, `Email`, `Phone`, `MobilePhone`, `Title`, `Department`, `ReportsToId`, `MailingAddress`.

`ReportsToId` is a self-lookup building an internal org chart within the account. Useful in enterprise selling, where knowing who reports to whom shapes the strategy, and almost always under-maintained because nobody has an incentive to keep it current.

`AccountId` is technically optional. A Contact with no Account is a **private contact**, visible only to its owner. Most orgs make the field required, because contacts floating without a company are not useful and are invisible to everyone else.

## The one-account limitation

`AccountId` holds exactly one value. Real people frequently relate to several organizations — a consultant advising three clients, a director on multiple boards, a person who changed jobs but whose history matters at both employers.

**Contacts to Multiple Accounts** is the standard solution. It creates `AccountContactRelation` junction records linking a Contact to additional Accounts, each with its own role and its own active or inactive status.

```
Contact: Priya Sharma
  Primary AccountId: Northwind Manufacturing        (direct relationship)
  AccountContactRelation → Acme Consulting          (Role: Advisor)
  AccountContactRelation → Beta Industries          (Role: Board Member, Inactive)
```

The direct `AccountId` relationship still exists and is called the **direct** relationship; the junction records are **indirect** ones. A Contact has one direct account and any number of indirect ones.

```sql
SELECT Id, Name, Account.Name,
       (SELECT Account.Name, Roles, IsActive, IsDirect FROM AccountContactRelations)
FROM Contact
WHERE Id = :contactId
```

`Roles` on the relation is a multi-select picklist, which brings the usual awkwardness of multi-select fields to reporting.

Enable this when the requirement genuinely exists. Building a custom junction object alongside it instead splits the data and loses the standard related lists and reporting.

## Opportunity Contact Roles

A different object solving a different problem: **which people are involved in this specific deal, and in what capacity.**

`OpportunityContactRole` is a junction between Opportunity and Contact with a `Role` picklist — Decision Maker, Economic Buyer, Technical Buyer, Influencer, Evaluator — and an `IsPrimary` flag.

This object matters more than its low profile suggests.

**It is the foundation of buying-committee visibility.** An enterprise deal involves five to ten people. Recording who they are and what role they play is the difference between a deal that survives a champion leaving and one that does not.

**It drives campaign influence.** Attribution of revenue back to marketing campaigns works through contact roles — a campaign that touched a contact who has a role on a won opportunity gets credit. Without contact roles, campaign ROI reporting produces nothing. See [[04.12 - Campaigns and Campaign Influence]].

**It is the most under-adopted object in Sales Cloud.** Reps do not fill it in because it does not help them personally. Most orgs that want the reporting have to make it mandatory through validation.

```
// Validation rule on Opportunity: require a primary contact role before advancing
AND(
  ISPICKVAL(StageName, "Commercial Proposal"),
  Primary_Contact_Role_Count__c = 0
)
```

That validation needs a roll-up, which is not natively possible because the relationship is not master-detail. The standard approach is a trigger maintaining a count field:

```java
public with sharing class ContactRoleRollupService {

    public static void updateRoleCounts(Set<Id> opportunityIds) {
        if (opportunityIds.isEmpty()) {
            return;
        }

        Map<Id, Opportunity> opps = new Map<Id, Opportunity>([
            SELECT Id, Contact_Role_Count__c, Primary_Contact_Role_Count__c
            FROM Opportunity WHERE Id IN :opportunityIds
        ]);

        for (Opportunity opp : opps.values()) {
            opp.Contact_Role_Count__c = 0;
            opp.Primary_Contact_Role_Count__c = 0;
        }

        for (AggregateResult ar : [
            SELECT OpportunityId oppId, COUNT(Id) total,
                   SUM(CASE WHEN IsPrimary = true THEN 1 ELSE 0 END) primaryCount
            FROM OpportunityContactRole
            WHERE OpportunityId IN :opportunityIds
            GROUP BY OpportunityId
        ]) {
            Opportunity opp = opps.get((Id) ar.get('oppId'));
            opp.Contact_Role_Count__c = (Integer) ar.get('total');
            opp.Primary_Contact_Role_Count__c = (Integer) ar.get('primaryCount');
        }

        update opps.values();
    }
}
```

Resetting the counters before the aggregate query is what handles opportunities whose last contact role was deleted. Omitting that step leaves stale counts, which is the most common bug in hand-rolled roll-ups.

Note that `OpportunityContactRole` triggers exist but are limited — the object supports before and after insert, update, and delete, but not all standard trigger features behave identically to a normal object. Testing this specific behaviour is worthwhile rather than assuming.

## Contacts and Cases

Case has a `ContactId`, linking a support case to the person who raised it. This is what makes the shared Sales-Service model work: the same Contact appears on opportunities and on cases.

For Experience Cloud, the Contact record is also what an external user is *based on* — a community user is created from a Contact, and that Contact's Account determines what the user can see through sharing sets. This is why contact data quality matters for portals in a way it does not for internal-only orgs. See [[17.9 - Experience Cloud Basics]].

## Email and communication fields

`HasOptedOutOfEmail` is a standard checkbox that suppresses the contact from Salesforce-sent emails and, importantly, from most marketing tools that integrate. Respecting it is a legal requirement in most jurisdictions, not a preference.

`DoNotCall`, `HasOptedOutOfFax`, and the email bounce fields (`IsEmailBounced`, `EmailBouncedReason`, `EmailBouncedDate`) round out the communication preference set.

Any custom outbound communication — a flow sending email, an integration pushing to a messaging platform — should check these. Sending to an opted-out contact because the code did not check is a compliance incident, and it is entirely preventable.

```java
List<Contact> contactable = [
    SELECT Id, Email, FirstName
    FROM Contact
    WHERE Id IN :contactIds
      AND Email != null
      AND HasOptedOutOfEmail = false
      AND IsEmailBounced = false
];
```

## Contact duplicates and merging

Contacts duplicate heavily, particularly when the same person is entered by sales, by support, and by an integration.

Duplicate rules apply. Contact merge combines up to three records, moving related activities, cases, opportunity contact roles, and campaign members to the survivor.

The complication specific to Contact: **merging contacts across different accounts** is allowed but changes the account association, which can silently move opportunity contact roles and case history to a different customer. Merging across accounts should be treated as a deliberate data-correction operation, not routine cleanup.

## Practical guidance

**Make `AccountId` required.** Private contacts are almost never intentional.

**Enable Contacts to Multiple Accounts if the business needs it** rather than building a custom junction.

**Enforce Opportunity Contact Roles through validation.** They will not be maintained otherwise, and campaign attribution depends on them.

**Check opt-out flags in every custom communication path.** This is a compliance obligation.

**Maintain `ReportsToId` only if someone will actually use it.** An org chart that is half-populated is worse than none, because people trust it.

**Treat contact email as an identifier.** It is the most reliable natural key for matching against inbound leads and external systems, and marking a unique external ID field on it makes integrations idempotent.
