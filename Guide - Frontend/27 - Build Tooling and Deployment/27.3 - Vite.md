# Vite

Vite's central idea is that development and production are different problems, and should use different strategies ([[27.2 - Module Bundling Concepts]]).

## Why the dev server is fast

**Traditional bundler dev server:** bundle the entire application, then serve it. Startup time scales with project size — a large app takes 30–60 seconds before the first page load.

**Vite:** serve source files as **native ES modules**, transforming each one on request. The browser's own module loader walks the import graph and requests what it needs.

```
Request /src/App.tsx
  → Vite transforms TS+JSX with esbuild (~1ms)
  → browser requests its imports
  → repeat, on demand
```

Startup is near-instant regardless of project size, because nothing is bundled. Only files the current page actually imports are ever transformed.

Two supporting pieces:

**Dependency pre-bundling.** `node_modules` packages are bundled once with esbuild and cached in `node_modules/.vite`. This converts CommonJS to ESM and collapses packages like lodash — which would otherwise be hundreds of separate module requests — into one file.

**Hot Module Replacement over ESM.** Editing a file invalidates only that module and its importers, so update time is constant rather than proportional to project size. React Fast Refresh preserves component state across edits.

The pre-bundle cache is the source of the most common Vite annoyance: after changing dependencies, a stale cache causes strange resolution errors. `rm -rf node_modules/.vite` or `vite --force` fixes it.

## Configuration

```ts
import { defineConfig, loadEnv } from "vite";
import react from "@vitejs/plugin-react";
import path from "node:path";

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), "");

  return {
    plugins: [react()],

    resolve: {
      alias: { "@": path.resolve(__dirname, "./src") },
    },

    server: {
      port: 5173,
      proxy: {
        "/api": {
          target: env.API_URL ?? "http://localhost:3000",
          changeOrigin: true,
        },
      },
    },

    build: {
      sourcemap: true,
      rollupOptions: {
        output: {
          manualChunks: { react: ["react", "react-dom"] },
        },
      },
    },
  };
});
```

The dev proxy is the standard way to avoid CORS in development — requests to `/api` are forwarded server-side, so the browser sees a same-origin request ([[15.3 - Same Origin Policy and CORS]]).

Aliases must be mirrored in `tsconfig.json`, or TypeScript and Vite disagree:

```json
{ "compilerOptions": { "paths": { "@/*": ["./src/*"] } } }
```

## Environment variables

```
.env                 all modes
.env.local           all modes, gitignored
.env.production      production only
.env.development     development only
```

```ts
import.meta.env.VITE_API_URL;
import.meta.env.MODE;
import.meta.env.DEV;
import.meta.env.PROD;
```

**Only variables prefixed `VITE_` are exposed to client code.** This is a deliberate guard — without it, every server secret in `.env` would be inlined into the bundle.

The critical property: these are **replaced at build time**, not read at runtime. The value is baked into the JavaScript, so anything placed there is public. Never put a secret in a `VITE_` variable ([[27.8 - Environment Variables and Config]]).

Typing them:

```ts
// vite-env.d.ts
interface ImportMetaEnv {
  readonly VITE_API_URL: string;
}
```

## The production build

`vite build` uses Rollup — full bundling, tree shaking, minification, chunk splitting and content hashing.

```bash
vite build
vite preview      # serve the build locally
```

**Always test with `preview` before deploying.** Dev and build use different pipelines, so problems that only appear in the bundled output — a dependency that breaks under tree shaking, a dynamic import the bundler cannot analyze, a CSS ordering difference — surface here rather than in production.

Vite is migrating its build from Rollup to **Rolldown** (a Rust reimplementation with a compatible API), which will unify the dev and build transformers and remove most of the remaining dev/prod divergence.

## Asset handling

```ts
import logoUrl from "./logo.svg";              // → hashed URL string
import logoRaw from "./logo.svg?raw";          // → file contents as a string
import Logo from "./logo.svg?react";           // → React component (with a plugin)
import styles from "./Card.module.css";        // → scoped class map
import workerUrl from "./worker.ts?worker";    // → Worker constructor
```

The query-suffix system is Vite-specific and worth knowing — `?raw`, `?url`, `?inline`, `?worker` cover most asset needs without extra configuration.

Assets under a configured size threshold are inlined as data URIs; larger ones are emitted with hashed filenames.

Files placed in `public/` are copied verbatim with no hashing and no processing — correct for `robots.txt`, `favicon.ico` and anything referenced by an absolute path that must not change.

`import.meta.glob` handles dynamic sets of files:

```ts
const pages = import.meta.glob("./pages/*.tsx");           // lazy — returns loaders
const icons = import.meta.glob("./icons/*.svg", { eager: true });
```

Useful for file-based routing and content collections.

## Plugins

Vite plugins extend Rollup's plugin interface with Vite-specific hooks. The commonly used ones:

```ts
plugins: [
  react(),
  tsconfigPaths(),                    // read aliases from tsconfig automatically
  svgr(),                             // import SVGs as components
  visualizer({ gzipSize: true }),     // bundle analysis
  VitePWA({ registerType: "autoUpdate" }),
  compression({ algorithm: "brotliCompress" }),
]
```

`vite-tsconfig-paths` removes the alias duplication problem entirely by deriving Vite's resolution from `tsconfig.json` — worth adding to every project.

`rollup-plugin-visualizer` should be in every project; assumptions about bundle composition are frequently wrong ([[19.7 - Bundle Analysis and Optimization]]).

## Vitest integration

```ts
export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    setupFiles: "./src/test/setup.ts",
  },
});
```

Vitest reuses the Vite config, so aliases, plugins and transforms apply identically in tests. This removes an entire class of "builds fine, fails in tests" problems that arise when Jest has its own separate transform configuration ([[26.2 - Unit Testing with Vitest and Jest]]).

## SSR and frameworks

Vite provides SSR primitives rather than a full framework:

```ts
const { render } = await vite.ssrLoadModule("/src/entry-server.tsx");
```

In practice you use a framework built on it — Remix / React Router v7, TanStack Start, Nuxt, SvelteKit, Astro, or Vike. Hand-rolling SSR on raw Vite is possible and rarely worth it ([[28.11 - Rendering Strategies]]).

The `environments` API in recent versions generalizes this for edge, worker and node targets from one config.

## Common problems

**"Failed to resolve import"** — usually a missing alias in one of `vite.config.ts` or `tsconfig.json`, or a stale pre-bundle cache.

**A CommonJS-only dependency failing** — add it to `optimizeDeps.include` so it is pre-bundled and converted:

```ts
optimizeDeps: { include: ["problematic-cjs-package"] }
```

**`process is not defined`** — Vite targets the browser, so Node globals do not exist. Use `import.meta.env`, or define a shim if a dependency requires it.

**Works in dev, breaks in build** — almost always tree shaking removing something with an undeclared side effect, or a dynamic import the bundler could not analyze. `vite preview` catches these.

## How senior engineers actually use this

**They add `vite-tsconfig-paths`** so aliases are defined once.

**They use the dev proxy** rather than configuring CORS for local development.

**They run `vite preview` before every deploy**, because the dev and build pipelines differ.

**They keep a bundle visualizer in the build**, gated behind a flag.

**They clear `node_modules/.vite` first** when resolution behaves strangely after a dependency change.

## Common pitfalls

- Secrets in `VITE_` variables, inlined into the public bundle.
- Aliases configured in Vite but not TypeScript, or vice versa.
- Stale pre-bundle cache after changing dependencies.
- Assuming `import.meta.env` is read at runtime — it is replaced at build time.
- Putting hashable assets in `public/`, losing content hashing.
- Deploying without testing the production build.
- Expecting Node globals like `process` and `Buffer` to exist.

## Interview angle

"Why is Vite faster than webpack" is a good question to answer precisely: in development it does not bundle at all — it serves source files as native ES modules and transforms them on demand with esbuild, so startup is independent of project size and HMR is proportional to the changed file rather than the graph. Then note the tradeoff: dev and production use different pipelines, so a production build must be tested separately. Mentioning dependency pre-bundling and the Rolldown migration shows current awareness.
