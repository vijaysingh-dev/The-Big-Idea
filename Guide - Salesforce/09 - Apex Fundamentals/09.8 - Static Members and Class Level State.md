# Static Members and Class Level State

## The lifetime rule

**A static variable lives for the duration of one transaction and is reset for the next.**

Not the session. Not the user. Not the org. One transaction — one save, one API request, one batch chunk, one Queueable execution.

That single fact makes statics the standard mechanism for recursion control, per-transaction caching, and cross-class coordination. It also makes them a source of subtle bugs when the lifetime is misunderstood.

## Recursion control

The most common use, and the one every codebase needs.

```java
public with sharing class TriggerControl {

    private static Set<Id> processedClaimIds = new Set<Id>();

    public static Boolean alreadyProcessed(Id recordId) {
        return processedClaimIds.contains(recordId);
    }

    public static void markProcessed(Set<Id> recordIds) {
        processedClaimIds.addAll(recordIds);
    }
}
```

```java
public with sharing class ClaimTriggerHandler {

    public static void run() {
        if (Trigger.isAfter && Trigger.isUpdate) {
            List<Warranty_Claim__c> toProcess = new List<Warranty_Claim__c>();

            // tracking record ids rather than a single boolean keeps later records in the
            // same transaction from being skipped
            for (Warranty_Claim__c claim : Trigger.new) {
                if (!TriggerControl.alreadyProcessed(claim.Id)) {
                    toProcess.add(claim);
                }
            }

            if (toProcess.isEmpty()) {
                return;
            }

            TriggerControl.markProcessed(new Map<Id, Warranty_Claim__c>(toProcess).keySet());
            ClaimService.processApprovals(toProcess, Trigger.oldMap);
        }
    }
}
```

**The record-ID form is correct; the boolean form is not.**

```java
// Too blunt: skips every subsequent record in the same transaction
private static Boolean hasRun = false;

public static void run() {
    if (hasRun) {
        return;
    }
    hasRun = true;
    // ...
}
```

A boolean guard works for the simple case and fails the moment a transaction updates records in two passes — a data load of 400 records in two chunks, or a trigger updating other records of the same object. The second batch is silently skipped, and the symptom is records that did not get processed with no error anywhere.

Tracking IDs costs a Set and removes the whole class of problem. See [[11.6 - Recursion Control and Static Guards]].

## Per-transaction caching

Describe calls and Custom Metadata queries are expensive enough to be worth caching for the transaction.

```java
public with sharing class SchemaCache {

    private static Map<String, Schema.SObjectType> globalDescribe;
    private static Map<String, Map<String, Schema.SObjectField>> fieldsByObject =
        new Map<String, Map<String, Schema.SObjectField>>();

    public static Schema.SObjectType objectType(String objectName) {
        if (globalDescribe == null) {
            // getGlobalDescribe walks every object in the org; once per transaction is enough
            globalDescribe = Schema.getGlobalDescribe();
        }
        return globalDescribe.get(objectName.toLowerCase());
    }

    public static Map<String, Schema.SObjectField> fields(String objectName) {
        String key = objectName.toLowerCase();
        if (!fieldsByObject.containsKey(key)) {
            fieldsByObject.put(key, objectType(objectName).getDescribe().fields.getMap());
        }
        return fieldsByObject.get(key);
    }
}
```

`Schema.getGlobalDescribe()` called inside a loop is a well-known cause of `Apex CPU time limit exceeded` in code that looks harmless. Caching it in a static is the fix.

The same applies to any query whose result is stable within a transaction:

```java
public with sharing class QueueCache {

    private static Map<String, Id> queueIdsByName;

    public static Id queueId(String developerName) {
        if (queueIdsByName == null) {
            queueIdsByName = new Map<String, Id>();
            for (Group q : [SELECT Id, DeveloperName FROM Group WHERE Type = 'Queue']) {
                queueIdsByName.put(q.DeveloperName, q.Id);
            }
        }
        return queueIdsByName.get(developerName);
    }
}
```

One query per transaction instead of one per caller. On a trigger that routes 200 records this is the difference between one query and two hundred.

## Static initialization

```java
public with sharing class ClaimConstants {

    public static final Set<String> OPEN_STATUSES;
    public static final Id DEFAULT_QUEUE_ID;

    static {
        OPEN_STATUSES = new Set<String>{ 'Submitted', 'Under Review', 'Awaiting Evidence' };

        List<Group> queues = [
            SELECT Id FROM Group WHERE Type = 'Queue' AND DeveloperName = 'Claim_Triage' LIMIT 1
        ];
        DEFAULT_QUEUE_ID = queues.isEmpty() ? null : queues[0].Id;
    }
}
```

A static initializer block runs **once per transaction**, the first time the class is touched.

Two cautions:

**A query in a static initializer consumes a SOQL query** whether or not the value is used. If the class is loaded in a transaction that does not need the value, the query is wasted.

**An exception in a static initializer is hard to debug.** It surfaces as an obscure error at the point of first class access, often far from the actual cause. Lazy initialization inside a getter is generally safer.

## Statics and asynchronous boundaries

**Static state does not cross a transaction boundary**, which includes every async boundary.

```java
public with sharing class ClaimService {

    public static Boolean skipValidation = false;

    public static void bulkLoad(List<Warranty_Claim__c> claims) {
        skipValidation = true;
        insert claims;

        // the Queueable runs in a NEW transaction; skipValidation is false there
        System.enqueueJob(new PostLoadQueueable(new Map<Id, Warranty_Claim__c>(claims).keySet()));
    }
}
```

Each of these starts fresh: a Queueable execution, each Batch chunk, a future method, a platform event subscriber, a scheduled job.

State that must survive an async boundary has to be passed explicitly — as constructor arguments to the Queueable, or through `Database.Stateful` in a batch class. See [[12.3 - Queueable Apex]] and [[12.4 - Batch Apex]].

`Database.Stateful` is the exception that proves the rule: it preserves **instance** variables across batch chunks, not statics. Statics reset every chunk regardless.

## Statics in tests

`Test.startTest()` does **not** reset static variables. State set before it persists into the test block, and state set during a test persists to the end of that test method.

```java
@IsTest
static void secondCallIsSkippedByRecursionGuard() {
    // explicit reset, because the previous test in this class may have set state
    TriggerControl.reset();

    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    update claim;
    update claim;
    Test.stopTest();

    Assert.areEqual(1, ClaimService.processedCount, 'The guard should prevent a second pass');
}
```

Each test **method** gets a fresh transaction, so statics reset between methods. Within a method they do not.

Providing a `reset()` method on any class holding static state is worth doing purely for test clarity — relying on transaction boundaries makes tests order-dependent in ways that are hard to diagnose.

```java
@TestVisible
private static void reset() {
    processedClaimIds.clear();
}
```

`@TestVisible` exposes a private member to tests without making it public in production code.

## Where statics go wrong

**Hidden coupling.** A static flag set in one class and read in another creates a dependency invisible in the signatures. Someone changing the first class breaks the second with no compile error.

**Order dependence.** Behaviour depending on which code ran first in the transaction is fragile, and the order can change when a new flow or trigger is added.

**Untestable behaviour.** A method whose result depends on static state set elsewhere cannot be tested in isolation.

**Memory.** Static collections count toward heap. A static cache accumulating records across a large batch will exhaust it.

The guidance: **use statics for recursion control and per-transaction caching, and prefer explicit parameters for anything else.** A static flag controlling business behaviour — `skipValidation`, `bypassAutomation` — is a design smell that is occasionally the pragmatic answer and should be rare and documented.

## The bypass pattern

The one case where a static behaviour flag is genuinely defensible, usually paired with a hierarchy custom setting so it can also be controlled without a deployment:

```java
public with sharing class AutomationBypass {

    private static Set<String> bypassed = new Set<String>();

    public static Boolean isBypassed(String handlerName) {
        if (bypassed.contains(handlerName)) {
            return true;
        }
        Automation_Settings__c settings = Automation_Settings__c.getInstance();
        return settings != null && settings.Disable_All_Triggers__c;
    }

    public static void bypass(String handlerName) {
        bypassed.add(handlerName);
    }

    public static void clearBypass(String handlerName) {
        bypassed.remove(handlerName);
    }
}
```

The static path handles code-driven bypass — a data migration script disabling a handler for its own run. The custom setting path handles runtime bypass without a deployment. Both are needed for different situations. See [[17.2 - Custom Settings]].

## Practical guidance

**Track record IDs, not a boolean**, in recursion guards.

**Cache describes and stable queries in statics**, particularly `getGlobalDescribe()`.

**Remember statics reset at every async boundary**, and pass state explicitly.

**Prefer lazy initialization to static initializer blocks** with queries in them.

**Provide a `@TestVisible reset()`** on any class holding static state.

**Do not use statics for cross-class behaviour flags** except for a deliberate, documented bypass mechanism.

**Watch heap** on static collections in long-running jobs.
