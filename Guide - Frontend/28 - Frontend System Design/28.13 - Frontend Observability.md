# Frontend Observability

Backend observability watches machines you control. Frontend observability watches thousands of devices you do not — different hardware, networks, browsers, extensions and locales. You cannot reproduce most of what users experience, so you have to measure it.

## The three signals

**Errors** — what broke, where, for whom ([[28.5 - Global Error Handling]]).

**Performance** — how slow it was, on real devices.

**Behavior** — what users actually did before it broke.

Most teams instrument the first, half instrument the second, and the third is usually owned by a separate analytics stack that engineering never looks at. Combining them is what turns a bug report into a diagnosis.

## Real user monitoring versus lab data

**Lab data** — Lighthouse, CI performance runs. Reproducible, good for catching regressions before release, and unrepresentative of your actual users.

**Field data** — Core Web Vitals from real sessions. Representative, noisy, and the only thing that reflects reality.

```ts
import { onLCP, onINP, onCLS, onTTFB } from "web-vitals";

function report({ name, value, rating, id, attribution }) {
  navigator.sendBeacon("/api/vitals", JSON.stringify({
    name, value, rating, id,
    element: attribution?.element,
    url: location.pathname,
    release: import.meta.env.VITE_COMMIT_SHA,
    connection: navigator.connection?.effectiveType,
    deviceMemory: navigator.deviceMemory,
  }));
}

onLCP(report); onINP(report); onCLS(report); onTTFB(report);
```

Two details that make this useful rather than decorative:

**`attribution`** tells you *which element* was the LCP candidate or *which interaction* caused a bad INP. Without it you know the score and not the cause ([[13.5 - Core Web Vitals]]).

**`sendBeacon`** survives page unload, where a normal `fetch` is cancelled. INP in particular is only final at page hide, so beacon delivery is not optional.

Tag every report with the release SHA and route, or a regression cannot be attributed.

## Percentiles, not averages

```
p50   the typical experience
p75   the Core Web Vitals threshold
p95   where the pain is
p99   the worst experiences — often the most valuable users
```

An average LCP of 2.1s can hide a p95 of 8s. Averages are dominated by the fast majority and hide exactly the population that is suffering.

Segment by the dimensions that actually vary:

- **Device memory and CPU class** — a 2GB Android phone is a different product
- **Connection type** — 4G in a metro versus 3G elsewhere
- **Route** — one slow page can drag the site aggregate
- **Geography** — CDN coverage varies enormously

For a product with users across India, segmenting by connection type and device memory usually reveals that the p75 experience is far worse than the development team assumes.

## Error monitoring that stays useful

```ts
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_COMMIT_SHA,
  environment: import.meta.env.MODE,

  beforeSend(event, hint) {
    const err = hint.originalException;
    if (err?.name === "AbortError") return null;
    if (err?.status === 404) return null;
    if (isExtensionNoise(event)) return null;
    return event;
  },
});
```

The signal-to-noise ratio determines whether anyone reads the dashboard. Aborts, expected 404s and browser-extension errors are the three biggest noise sources on a consumer product, and extension noise is larger than most people expect.

Context is what makes a report actionable:

```ts
Sentry.setUser({ id: user.id });                 // an id, never PII
Sentry.setTag("route", pathname);
Sentry.setTag("flag.new-checkout", String(enabled));
Sentry.addBreadcrumb({ category: "action", message: "clicked_pay" });
```

**Breadcrumbs are usually more useful than the stack trace** — the sequence of actions before the error is what lets you reproduce it.

**Source maps are mandatory.** Without them every trace points into `chunk-4f2a.js` and the whole system is decorative ([[27.7 - Source Maps]]).

Tagging with feature flag state means a regression from a rollout is immediately attributable rather than mysterious ([[28.8 - Feature Flags and Progressive Rollout]]).

## Correlating frontend and backend

```ts
headers: { "X-Request-Id": crypto.randomUUID() }
```

A request id generated by the client and logged on both sides turns "the API failed" into a specific backend log entry ([[28.4 - The Data Layer]]).

Full distributed tracing extends this — a trace id propagated from the browser through every backend service, so one timeline shows the whole request path:

```ts
headers: { traceparent: `00-${traceId}-${spanId}-01` }
```

OpenTelemetry's browser support is the standard mechanism. The payoff is largest in a microservice backend, where a slow page might be one of eight services.

## Session replay

Records DOM mutations and reconstructs the session as video-like playback. It answers "what did the user actually do" better than any amount of logging.

The cost is privacy, and it is serious:

```ts
replaysSessionSampleRate: 0.01,
replaysOnErrorSampleRate: 1.0,
maskAllText: true,
blockAllMedia: true,
```

**Mask by default and unmask deliberately.** A replay capturing a payment form or a health record is a compliance incident. Sampling errors at 100% and normal sessions at 1% keeps cost and exposure bounded while still capturing what matters.

Check the legal position for your jurisdiction and users — replay is regulated in several.

## Custom performance marks

```ts
performance.mark("checkout:start");
await submitOrder();
performance.mark("checkout:end");
performance.measure("checkout", "checkout:start", "checkout:end");

const [entry] = performance.getEntriesByName("checkout");
report({ name: "checkout_duration", value: entry.duration });
```

Core Web Vitals measure page loading. They say nothing about whether *your* critical interaction is fast.

Measure the things the product cares about: time to first meaningful result, search latency, save duration, editor keystroke lag. These are the metrics a product team will actually act on.

`PerformanceObserver` with `longtask` identifies main-thread blocking ([[12.5 - Custom Events and Observer APIs]]):

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 100) report({ name: "long_task", value: entry.duration });
  }
}).observe({ type: "longtask", buffered: true });
```

## Alerting

Alert on **user-visible degradation**, not on raw counts:

```
Error rate > 2% of sessions, sustained 5 min      → page
p75 LCP regression > 20% after a release          → notify
New error affecting > 50 users in an hour         → notify
API failure rate > 5% for a critical endpoint     → page
```

Two rules that keep alerting alive:

**Compare against a baseline**, not a threshold. Absolute numbers drift with traffic; a percentage regression against last week is stable.

**Every alert must be actionable.** An alert nobody can act on gets muted, and then the ones that matter get muted too.

Watch the release dimension specifically — a spike confined to the newest release identifies the cause immediately.

## Budgets in CI

```json
{
  "size-limit": [{ "path": "dist/assets/index-*.js", "limit": "150 kB" }]
}
```

```yaml
- run: npx lhci autorun --collect.url=$PREVIEW_URL
```

Catching a regression before release is far cheaper than detecting it in production. Bundle size in particular regresses invisibly — a dependency here, an import pattern there — and a CI budget converts that into a decision at the PR that causes it ([[27.9 - CI CD and Frontend Deployment]]).

Lighthouse scores in CI are noisy; gate on specific audits and byte budgets rather than the composite score.

## Privacy

Frontend observability collects data about people, which brings obligations:

- **Never send PII** — no emails, names or free-text input. An opaque user id only.
- **Scrub URLs** — tokens and personal identifiers leak through query strings and referrers.
- **Respect consent** — in GDPR jurisdictions, non-essential collection requires it.
- **Honour Do Not Track and Global Privacy Control** where applicable.
- **Set retention limits** — indefinite retention is both a liability and a cost.

The default in most SDKs is more collection than you want. Configure it down deliberately.

## How senior engineers actually use this

**They read p75 and p95, never averages**, and segment by device and connection.

**They tag every signal with the release**, making regressions attributable within minutes.

**They filter noise aggressively in `beforeSend`**, because an unread dashboard is worthless.

**They add custom marks for product-critical interactions**, not just page-load vitals.

**They mask session replay by default** and sample normal sessions at a low rate.

**They alert on user-visible degradation against a baseline**, not on raw thresholds.

## Common pitfalls

- No source maps, making every production trace unusable.
- Averages hiding a bad tail.
- Aborts and expected 404s drowning real errors.
- Metrics not tagged by release, so regressions cannot be traced to a deploy.
- PII in error reports or session replay.
- Measuring only page-load vitals and ignoring the product's critical interaction.
- `fetch` instead of `sendBeacon`, losing reports at page unload.
- Alerts that are not actionable, leading to muted alerting.

## Interview angle

"How would you know if the frontend is broken for users" wants the three signals and the RUM-versus-lab distinction — lab data catches regressions before release, field data is the only representation of reality. The specifics that mark experience: read p75 and p95 rather than averages, tag every error and metric with the release SHA so a regression is attributable, filter aborts and expected 404s or the dashboard becomes unreadable, and correlate with the backend through a request id. Raising the privacy constraints on session replay unprompted also lands well.
