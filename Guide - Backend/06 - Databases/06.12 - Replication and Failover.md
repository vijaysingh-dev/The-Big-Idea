# Replication and Failover

#backend #databases #postgres #reliability

> **In one line:** Replicas ship the WAL and replay it, which means they are always slightly behind — every correctness problem with read replicas comes from that lag, and every availability problem comes from deciding who is primary.

---

## The Idea

```
Primary ──── WAL stream ────► Replica 1  (read-only)
        └─── WAL stream ────► Replica 2  (read-only)
```

The primary writes WAL records ([[06.2 - Postgres Architecture]]); replicas receive and replay them against their own copy of the data files. **Physical replication: byte-for-byte identical files.**

| Goal | |
|---|---|
| **Availability** | If the primary dies, promote a replica |
| **Read scaling** | Route read queries to replicas |

⚠️ **These are different goals with different requirements**, and conflating them causes trouble. A standby kept purely for failover should have `hot_standby_feedback = off` and no query traffic; a read replica serving queries needs the opposite, **and it will hold back vacuum on the primary.**

---

## Streaming Replication

```bash
pg_basebackup -h primary -D /var/lib/postgresql/data -U replicator -R -X stream -P
```

The replica connects, streams WAL continuously, and replays it. **Replay is single-threaded on the replica.**

💡 **That single-threaded replay is the fundamental limit.** A primary with 16 cores generating WAL from 16 concurrent writers has one replica process applying it. **Under heavy write load, replicas fall behind — and the fix is not more replica cores.**

### Measuring lag

```sql
-- On the primary
SELECT client_addr, state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication;

-- On the replica
SELECT now() - pg_last_xact_replay_timestamp() AS lag;
```

⚠️ **The time-based measure returns a large value on an idle primary**, because it measures "time since the last replayed transaction". **Use byte lag for alerting and time lag for human interpretation.**

## Synchronous vs Asynchronous

| `synchronous_commit` | Waits for | Data loss on primary failure |
|---|---|---|
| `off` | Nothing | Up to 200ms of commits |
| `local` | Local WAL flush | All un-replicated commits |
| `remote_write` | Replica received it | Only if the replica also crashes |
| `on` | Replica flushed to disk | **None** |
| **`remote_apply`** | Replica **applied** it | None, **and reads are consistent** |

💡 **`remote_apply` is the setting that makes read replicas safe to read from immediately** — a commit does not return until the replica has applied it. **The cost is that commit latency now includes replica replay time**, which can be substantial under load.

⚠️ **A synchronous replica that goes down blocks all writes on the primary.** With `synchronous_standby_names = 'replica1'` and replica1 unreachable, **every commit hangs forever.**

```ini
synchronous_standby_names = 'ANY 1 (r1, r2, r3)'   # any one of three confirms
```

**Always use the quorum form with more replicas than required confirmations**, so losing one does not stop the world.

## The Read Replica Correctness Problem

```python
await db.execute("INSERT INTO documents ...")                     # primary
docs = await replica.fetch("SELECT * FROM documents WHERE ...")   # 200ms behind
# the document the user just created is not there
```

⚠️ **"Read your own writes" is violated by default.** The user creates something, is redirected to a list page, and their creation is missing — so they create it again.

| Strategy | How | Cost |
|---|---|---|
| **Sticky to primary after write** | For N seconds after any write by that user | Loses some read scaling |
| **LSN tracking** | Record the LSN at commit, wait for the replica to reach it | Precise, needs plumbing |
| **`remote_apply`** | Synchronous with apply confirmation | Commit latency includes replay |
| Route by operation type | Only stale-tolerant reads go to replicas | Manual, error-prone |

```python
# LSN tracking — the precise version
lsn = await conn.fetchval("SELECT pg_current_wal_lsn()")
session["min_lsn"] = lsn

replica_lsn = await replica.fetchval("SELECT pg_last_wal_replay_lsn()")
if replica_lsn < session["min_lsn"]:
    return await primary.fetch(query)          # fall back
return await replica.fetch(query)
```

💡 **This gives you monotonic reads without giving up read scaling**, and it degrades gracefully — under high lag, more reads go to the primary. **It is the correct answer when staleness is user-visible.**

### What is genuinely safe to read from a replica

```
✅  Analytics and reporting
✅  Full-text search over slowly-changing content
✅  Public content with no user-specific state
✅  Export jobs and batch processing

❌  Anything immediately after a write by the same user
❌  Read-modify-write sequences
❌  Uniqueness checks before insert
❌  Authorisation checks
```

⚠️ **The authorisation case is a security issue, not just correctness.** A permission revoked on the primary and not yet replicated means the replica still grants access. **Never check permissions against a replica.**

## Failover

### Split brain

⚠️ **The failure mode that destroys data.** A network partition makes the primary unreachable from the failover controller, which promotes a replica. **Now two nodes accept writes, and their histories diverge irreconcilably.**

| Defence | |
|---|---|
| **Fencing / STONITH** | Forcibly kill or isolate the old primary before promoting |
| **Quorum** | Only promote if a majority agree the primary is gone |
| **Watchdog** | The primary self-demotes if it loses contact with the cluster |

💡 **A failover system without fencing is not safe, it is lucky.** Patroni's default — distributed consensus (etcd or Consul) for leader election plus a watchdog — is why it is the standard choice.

### The tools

| Tool | Notes |
|---|---|
| **Patroni** | The de facto standard. etcd/Consul/Kubernetes for leader election |
| repmgr | Simpler, less automatic |
| pg_auto_failover | Microsoft's, with a monitor node |
| Cloud managed | RDS Multi-AZ, Cloud SQL HA |

⚠️ **Do not build your own failover.** The failure modes are subtle, the consequences are permanent data loss, and the problem is genuinely solved.

### Application-side failover

```
postgresql://host1,host2,host3/db?target_session_attrs=read-write
```

libpq tries each host and connects to whichever accepts writes. **Simple and effective**, supported by asyncpg and psycopg.

⚠️ **Your application must handle the failover window.** For 10–60 seconds there is no primary and every write fails. **You need retries with backoff and, ideally, a circuit breaker so the failure is fast rather than a pile-up** ([[11.3 - Circuit Breakers and Bulkheads]]).

## Logical Replication

```sql
CREATE PUBLICATION docs_pub FOR TABLE documents, annotations;
CREATE SUBSCRIPTION docs_sub CONNECTION '...' PUBLICATION docs_pub;
```

Decodes the WAL into logical row changes and applies them as SQL.

| | Physical | Logical |
|---|---|---|
| Granularity | Whole cluster | Selected tables |
| **Target version** | Must match | **Can differ** |
| Target writable | No | **Yes** |
| DDL replicated | Yes | **No** |

💡 **Logical replication's killer use is major-version upgrades with near-zero downtime**: replicate from PG 15 to PG 17, wait for it to catch up, then switch over. **Physical replication cannot cross versions.**

It is also the mechanism behind CDC ([[09.4 - Change Data Capture]]).

⚠️ **Logical replication does not replicate DDL.** Add a column on the publisher and the subscriber breaks until you add it there too.

## In Production

### Replication slots: powerful and dangerous

```sql
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
```

A slot guarantees the primary retains WAL until the consumer has it. **That guarantee is the danger.**

⚠️ **An inactive slot causes unbounded WAL retention.** A replica decommissioned without dropping its slot means WAL accumulates until the disk fills — **and vacuum cannot advance either** ([[06.7 - MVCC Vacuum and Bloat]]).

```ini
max_slot_wal_keep_size = 100GB      # PG 13+: bound it
```

💡 **`max_slot_wal_keep_size` converts "the primary dies with a full disk" into "the replica needs rebuilding".** The second is enormously preferable. **Set it on every production primary.**

**Alert on any inactive slot immediately.**

### hot_standby_feedback

| Setting | Effect |
|---|---|
| `off` | Long replica queries get cancelled: `ERROR: canceling statement due to conflict with recovery` |
| `on` | Replica queries survive, but **the primary's vacuum is held back** |

⚠️ **`hot_standby_feedback = on` means a long analytics query on a replica causes bloat on the primary.** This surprises people — a read-only replica affecting the primary's health.

💡 **A failover standby: `off`. A dedicated analytics replica: `on`, accepting the bloat**, or use `max_standby_streaming_delay` as a middle ground.

### Cascading replication

```
Primary → Replica 1 → Replica 2
                   → Replica 3
```

Reduces load on the primary with many replicas. **Adds lag, and a failure of replica 1 orphans its children.**

### The monitoring set

| Metric | Alert |
|---|---|
| Replay lag bytes | > 100MB, or your staleness budget |
| **Inactive replication slot** | **Any** |
| Replication disconnected | Any |
| Standby conflicts | Rising |
| **Synchronous replica unavailable** | **Immediately — writes may be blocked** |

### RPO and RTO, stated honestly

| Configuration | RPO (data loss) | RTO (downtime) |
|---|---|---|
| Async, manual failover | Seconds to minutes | Minutes to hours |
| Async, Patroni | Seconds | 30–60 seconds |
| **Sync, Patroni** | **Zero** | 30–60 seconds |
| Managed multi-AZ | Zero to seconds | 60–120 seconds |

💡 **Write down your actual RPO and RTO, and test them.** "We have a replica" is not an availability strategy.

⚠️ **Practise the failover.** A procedure that has never been executed will not work when you need it, and discovering that during an outage is the worst possible time.

## Codebase

**Repo:** `postgres/postgres`, `zalando/patroni`

**Question to answer:** How does a replica receive and apply WAL, and why is apply single-threaded? Then: how does Patroni prevent split brain — what does it check before promoting, and what is the watchdog for?

**Read, in order:**

1. `src/backend/replication/README` — the replication architecture overview
2. `src/backend/replication/walsender.c` and `walreceiver.c` — the two sides of the stream
3. `src/backend/access/transam/xlogrecovery.c` — **the redo loop.** Where WAL records are applied, and where the single-threaded answer lives
4. `src/backend/replication/logical/decode.c` — how WAL becomes logical row changes. **The foundation of CDC**
5. `patroni/patroni/ha.py` — **the high-availability state machine.** `run_cycle` is the heart: what it checks each iteration and when it decides to promote or demote
6. `patroni/patroni/watchdog/` — **the split-brain answer**: if Patroni cannot renew the leader lock in the consensus store, the watchdog reboots the node rather than letting it keep accepting writes

💡 Patroni's `ha.py` is worth reading carefully even if you use a managed database. **It is a working, well-tested implementation of leader election with fencing**, and understanding what it checks — leader lock TTL, replica health, whether promotion is safe — **is a compact education in distributed systems failure handling.**

**Size:** 2 sessions.

## Exercise

**Drill 6.12 — Fail over without losing data**

```
drills/06-replication/
├── cluster/{compose.yml, setup.sh}
├── lag/{induce.py, measure.py, PLOT.md}
├── consistency/{read_your_writes.py, lsn_tracking.py, sticky_primary.py, COMPARISON.md}
├── sync/{modes.py, replica_down.py, RESULTS.md}
├── failover/{kill_primary.sh, measure_rto.py, measure_rpo.py, RESULTS.md}
├── split_brain/{partition.sh, FINDINGS.md}
├── slots/runaway.sh
└── README.md
```

**Part 1 — Build a real cluster.** Primary, two replicas, etcd, Patroni. Verify replication works and lag is near zero.

**Part 2 — Induce and measure lag.** Heavy write load — bulk inserts, large updates, index builds.

Chart replay lag in bytes and seconds. **Find the write rate at which replicas cannot keep up, and confirm that adding a third replica does not help** (because replay is per-replica single-threaded).

Then run a large backfill ([[06.11 - Zero Downtime Migrations]]) and watch lag spike. Implement lag-aware throttling and confirm it holds lag under a threshold.

**Part 3 — Reproduce the read-your-writes bug.** Write to the primary, immediately read from a replica under 200ms of lag.

**Measure the failure rate across 1,000 write-then-read cycles.**

Then implement both fixes — LSN tracking and sticky-to-primary — and measure correctness (should be 100%) and **what fraction of reads ended up on the primary. LSN tracking should route fewer reads to the primary for the same correctness.**

Then try `remote_apply` and measure the commit latency cost.

**Part 4 — Synchronous commit levels.** Measure commit latency and throughput at all five levels.

**Then, for each, kill the primary immediately after 1,000 commits and count how many were lost.**

**This gives you a measured RPO per configuration**, which is the number you actually need for a design conversation.

**Part 5 — The synchronous replica trap.** `synchronous_standby_names = 'replica1'` (single, not quorum). Stop replica1.

**Confirm all writes on the primary hang indefinitely.** Then switch to `ANY 1 (replica1, replica2)` and repeat — writes should continue.

**Part 6 — Failover, measured.** With continuous write load, kill the primary.

Measure time to detection, time to promotion, total write unavailability (RTO), and committed transactions lost (RPO). Then repeat with synchronous replication and confirm RPO is zero.

**Then measure how long your *application* took to recover** — connection strings, pool reconnection, retry behaviour. **The application recovery is often longer than the database failover, and that is the number your users experience.**

**Part 7 — Split brain.** Partition the network so the primary is isolated but still running.

**Without a watchdog:** confirm you can get two nodes accepting writes with irreconcilably diverged data.
**With Patroni's watchdog:** confirm the isolated primary demotes or reboots itself before the new primary is promoted.

⚠️ Throwaway cluster only.

**Part 8 — The runaway slot.** Create a replication slot, never consume it, run write load.

**Chart WAL directory size over time. Confirm it grows without bound.** Then set `max_slot_wal_keep_size` and confirm the slot is invalidated instead of the disk filling. Write the alert rule.

**Done when:**
- You know the write rate at which your replicas fall behind
- You have measured the read-your-writes failure rate and fixed it two ways
- Your synchronous-commit table has latency and measured RPO for all five levels
- A single synchronous replica going down blocked writes, and quorum fixed it
- You have measured RTO and RPO for a real failover, including application recovery
- You produced split brain without a watchdog and prevented it with one
- An inactive slot filled your disk, and `max_slot_wal_keep_size` prevented it
