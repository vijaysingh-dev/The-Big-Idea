# Suspense

`Suspense` lets a component tell React "I am not ready yet" and have React render a fallback for the nearest boundary above it.

```jsx
<Suspense fallback={<Skeleton />}>
  <Profile userId={id} />
</Suspense>
```

The value is declarative loading states: the loading UI is defined **where the boundary is**, not inside every component that might be loading.

## How suspension works

A component suspends by throwing a promise (in practice, by calling `use(promise)` or being a `lazy` component). React catches it, renders the nearest `Suspense` fallback, and retries the subtree when the promise resolves ([[18.3 - Fiber Architecture]]).

Nothing below the boundary commits until it is ready, so there are no partially-loaded states to handle.

## What can suspend

- **`React.lazy` components** while their chunk downloads ([[19.3 - Code Splitting and React.lazy]])
- **`use(promise)`** in React 19 ([[17.12 - Lesser Known Hooks]])
- **Framework data fetching** — Next.js server components, React Router loaders, Relay
- **Libraries with Suspense support** — TanStack Query with `useSuspenseQuery`

What **cannot** suspend: a plain `useEffect` fetch. Writing `useState` + `useEffect` and expecting Suspense to catch it does not work — there is nothing to throw.

## Boundary placement

```jsx
// One boundary — everything waits for the slowest thing
<Suspense fallback={<PageSkeleton />}>
  <Header />
  <Feed />
  <Sidebar />
</Suspense>

// Separate boundaries — each region reveals independently
<Header />
<Suspense fallback={<FeedSkeleton />}>
  <Feed />
</Suspense>
<Suspense fallback={<SidebarSkeleton />}>
  <Sidebar />
</Suspense>
```

Boundary granularity is a UX decision. Too coarse and fast content is held back by slow content; too fine and the page becomes a cascade of popping skeletons, which measures badly on CLS and feels worse than a single wait ([[13.5 - Core Web Vitals]]).

A reasonable default: one boundary per meaningful page region.

## Transitions prevent fallback flashes

The most important interaction. Without a transition, changing state that causes a suspension replaces already-visible content with the fallback:

```jsx
// Content vanishes, skeleton appears, new content appears
setTab("photos");

// Old content stays visible while the new tab loads
startTransition(() => setTab("photos"));
```

Inside a transition, React keeps the previous UI on screen and renders the new one in the background, swapping only when ready ([[22.4 - useTransition and startTransition]]). `isPending` lets you dim the stale content or show a progress indicator.

This is the difference between a navigation that feels smooth and one that flashes. It is also why router-driven navigations should be wrapped in transitions — React Router and Next.js do this internally.

## The waterfall problem

```jsx
<Suspense fallback={<Spinner />}>
  <Profile />       {/* fetches the user */}
  <Posts />         {/* fetches posts — starts only after Profile resolves */}
</Suspense>
```

If `Posts` renders only after `Profile` commits, the requests serialize. Each level of nesting adds a round trip.

The fix is starting the requests before rendering — passing promises down rather than creating them inside components:

```jsx
// Both requests start immediately
const userPromise = fetchUser(id);
const postsPromise = fetchPosts(id);

<Suspense fallback={<Skeleton />}>
  <Profile userPromise={userPromise} />
  <Posts postsPromise={postsPromise} />
</Suspense>
```

This is what "render-as-you-fetch" means, versus the "fetch-on-render" waterfall. Frameworks solve it structurally: route loaders start all requests in parallel before rendering ([[23.6 - Data Loading with Loaders and Actions]]), and Server Components start them on the server.

## Streaming SSR

Suspense enables progressive server rendering. The server sends HTML for ready parts immediately and streams the rest as it resolves:

```jsx
<Layout>
  <Header />                          {/* sent immediately */}
  <Suspense fallback={<Skeleton />}>
    <SlowDataSection />               {/* streamed in later */}
  </Suspense>
</Layout>
```

Without Suspense, SSR is all-or-nothing — the server waits for every data dependency before sending a byte. With it, TTFB and FCP improve substantially because the shell arrives first.

React also hydrates selectively: a boundary hydrates when its content arrives, and React prioritizes hydrating whatever the user interacts with first. This means interactivity is no longer gated on the whole page hydrating ([[28.11 - Rendering Strategies]]).

## Suspense and errors

Suspense handles the pending state only. Errors need a separate boundary:

```jsx
<ErrorBoundary fallback={<ErrorState onRetry={retry} />}>
  <Suspense fallback={<Skeleton />}>
    <Profile />
  </Suspense>
</ErrorBoundary>
```

The error boundary goes **outside**, so a failed load replaces the whole region rather than leaving a stuck skeleton ([[22.1 - Error Boundaries]]).

## Fallback design

The fallback should approximate the final layout:

```jsx
<Suspense fallback={<div className="skeleton" style={{ minHeight: 320 }} />}>
```

A 40px spinner replaced by 400px of content is a large layout shift. Skeleton screens sized to the real content avoid it and read as faster even when they are not.

Avoid nesting spinners inside spinners — a boundary whose fallback itself suspends creates a confusing double-loading state.

## What Suspense is not

**It is not a data-fetching library.** It is a coordination mechanism. Caching, deduplication, revalidation and cancellation all still need a data layer ([[24.6 - TanStack Query Fundamentals]]).

**It does not make anything faster.** It changes when and how loading states appear.

**It is not a replacement for loading flags** in every case. For a single request in a single component, `isLoading` is simpler and clearer.

## How senior engineers actually use this

**They wrap navigations in transitions**, so Suspense never blanks already-visible content.

**They place boundaries at region granularity**, matching how the design degrades.

**They start requests outside render** — loaders, server components, or promises passed as props — to avoid waterfalls.

**They pair every Suspense boundary with an error boundary.**

**They size fallbacks to the content** to protect CLS.

## Common pitfalls

- Expecting a `useEffect` fetch to suspend.
- No transition, so existing content is replaced by a fallback on every navigation.
- Nested components each fetching, producing a request waterfall.
- A single coarse boundary making the whole page wait for the slowest request.
- Missing error boundary, leaving a permanent skeleton on failure.
- Undersized fallbacks causing layout shift.
- Creating the promise inside the component that calls `use`, so it never resolves.

## Interview angle

"What is Suspense" should get: a boundary that renders a fallback while a descendant is not ready, letting loading states be declared structurally rather than per component. The strong follow-ups are the transition interaction — without `startTransition`, an update that suspends blanks visible content — the fetch-on-render waterfall and how render-as-you-fetch avoids it, and streaming SSR with selective hydration. Those three show you understand Suspense as a coordination primitive rather than a spinner API.
