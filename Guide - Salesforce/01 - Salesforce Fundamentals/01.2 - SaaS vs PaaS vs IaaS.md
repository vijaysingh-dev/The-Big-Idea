# SaaS vs PaaS vs IaaS

## Why a developer should care about this

This looks like a certification-trivia topic. It is not. Where Salesforce sits in the cloud stack directly determines what you are allowed to do in code, why your query throws an exception at row 50,001, and why you cannot install a library.

Get this note right and half the platform's strange rules stop feeling arbitrary.

## The three models

The standard way to explain these is renting a place to live.

**IaaS (Infrastructure as a Service).** You rent an empty apartment. Walls, plumbing, electricity. Everything inside is yours to install and maintain. In software: you rent virtual machines, storage, and networking. You install the operating system, the database, the runtime, the monitoring. Examples: AWS EC2, Azure Virtual Machines, Google Compute Engine.

**PaaS (Platform as a Service).** You rent a furnished apartment. Kitchen, bed, wifi already there. You bring your things and live your life, but you do not choose the boiler. In software: you write and deploy application code, and the vendor runs the servers, the database, the scaling, and the patching. Examples: Heroku, AWS Lambda, Google App Engine.

**SaaS (Software as a Service).** You book a hotel room. You do not install anything. You use the service as it is, adjusting settings the hotel allows. In software: finished applications you log into. Examples: Gmail, Slack, Dropbox.

The dividing line is who is responsible for what:

| Layer | IaaS | PaaS | SaaS |
| --- | --- | --- | --- |
| Application | You | You | Vendor |
| Runtime and middleware | You | Vendor | Vendor |
| Operating system | You | Vendor | Vendor |
| Servers, storage, network | Vendor | Vendor | Vendor |

## Salesforce is SaaS and PaaS at the same time

This is the part people get wrong. Salesforce is not one of these three, it is two of them stacked.

**Sales Cloud and Service Cloud are SaaS.** They are finished applications. You log in, you get Accounts, Opportunities, and Cases already built, with reports, mobile apps, and a support process ready to use. Configure them, do not build them.

**The Lightning Platform underneath is PaaS.** You can create your own objects, write Apex code, build Lightning Web Components, expose REST endpoints, and deploy them, all without touching a server.

The two are the same system. Your custom object sits in the same database as Account. Your Apex runs in the same transaction as the standard Opportunity save logic. That merge is the platform's real selling point, and the source of most of its constraints.

## What "you do not manage servers" actually costs you

This is where the abstract model becomes concrete. Because Salesforce runs your code on shared servers alongside thousands of other customers, you lose a long list of things that are normal elsewhere.

**No filesystem.** There is no `File.open()`, no temp directory, no writing a log to disk. Files live as records in `ContentVersion` ([[17.5 - Files, ContentDocument and ContentVersion]]). Static assets go in Static Resources ([[17.4 - Static Resources]]).

**No threads.** You cannot spawn a thread or run anything in parallel yourself. Background work goes to Queueable, Batch, or Scheduled Apex ([[12.1 - Why Async and the Async Landscape]]).

**No arbitrary libraries.** There is no package manager for Apex. No Maven, no npm, no pip. If you need JSON parsing, cryptography, or HTTP, you use the built-in classes. For JavaScript in a Lightning Web Component you can bundle a library as a Static Resource, but Apex has no equivalent.

**No control over runtime version.** Salesforce upgrades your org three times a year whether you are ready or not ([[01.11 - Release Cycle, Trust and Status]]).

**Hard runtime limits on everything.** This is the big one. Because your code shares a server with other tenants, Salesforce caps what a single transaction may consume: queries, records retrieved, DML statements, CPU seconds, heap memory, HTTP callouts. These are **governor limits**, and they are enforced by throwing an exception mid-execution rather than by slowing you down. Full treatment in section 16.

Compare the same task in a normal server environment and in Apex:

```java
// Not possible on Salesforce
FileWriter log = new FileWriter("/var/log/sync.log");
Thread worker = new Thread(() -> processBatch(records));
Connection db = DriverManager.getConnection(jdbcUrl);
```

```java
// The Salesforce equivalents
insert new Integration_Log__c(Message__c = 'Sync started', Level__c = 'INFO');
System.enqueueJob(new BatchProcessorQueueable(recordIds));
List<Account> accounts = [SELECT Id, Name FROM Account WHERE Industry = 'Manufacturing'];
```

You never open a database connection. There is no connection string, no pool, no credentials. SOQL is compiled into the language itself and runs against your org automatically. That is a genuine convenience and a genuine cage, at the same time.

## The tradeoff, stated honestly

**What you gain:** no infrastructure work at all. No patching, no scaling, no failover, no backups, no capacity planning, no on-call for a database that ran out of disk. A two-person team can run a system used by ten thousand employees. Authentication, permissions, audit trails, mobile apps, and an API come free and are already compliant with most enterprise requirements.

**What you give up:** control. You cannot tune the database. You cannot cache in Redis. You cannot choose your runtime. You cannot avoid an upgrade. When performance is bad, your options are the ones Salesforce provides, and sometimes the answer is a support ticket asking them to add an index or build a skinny table for you ([[16.9 - Skinny Tables and Custom Indexes]]).

Senior engineers coming from a normal backend background usually spend their first months frustrated by this, then discover the actual skill: designing so you never approach the limits, rather than fighting them at the edge.

## Where this shows up in architecture decisions

**"Should this run in Salesforce or outside it?"** is one of the most common design questions in a large org, and the SaaS-PaaS boundary is how you answer it. Work that is heavy computation, needs a specialized library, processes very large data volumes, or requires sub-second latency belongs outside — on Heroku, AWS, or a middleware layer — with results pushed back in. Work that is tightly coupled to CRM records, needs the sharing model, or must run inside the record save transaction belongs in Apex.

**Heroku exists for exactly this reason.** Salesforce owns Heroku, a true PaaS with no governor limits, real databases, and any language you like. Enterprise architectures frequently pair the two: Salesforce as the system of record and user interface, Heroku as the place where the heavy or unusual work happens. See [[17.10 - Slack, Heroku and Mobile SDK Touchpoints]].

**Licensing is a technical constraint, not just a commercial one.** Because it is SaaS, you pay per user, and what each user can do depends on their license. An architecture that needs a hundred thousand external users cannot simply create a hundred thousand Salesforce users. That is why Experience Cloud licenses exist and why they behave differently. See [[01.4 - Salesforce Editions and Licensing]].
