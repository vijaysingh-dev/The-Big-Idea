# What an Operating System Does

#backend #os #linux #kernel

> **In one line:** The kernel is a referee that owns the CPU, the memory and every device. Your program asks it for anything real by making a system call, and every system call has a cost you can measure.

---

## The Idea

Your Python service never touches hardware. It cannot read a disk, send a packet, start a thread or even get the time on its own. It asks the kernel, and the kernel does it, or says no.

The OS has three jobs:

| Job | What it means | Where you feel it as a backend engineer |
|---|---|---|
| **Virtualise** | Give each program the illusion of its own CPU and its own memory | Processes, threads, virtual memory, containers |
| **Share fairly** | Decide who runs, who gets memory, who gets the disk | Scheduler, OOM killer, cgroup throttling |
| **Persist and connect** | Turn raw disks and NICs into files and sockets | File descriptors, the page cache, `fsync`, TCP |

That split comes straight from OSTEP, the best free OS book: **virtualisation, concurrency, persistence**. This section follows that order.

---

## User Space and Kernel Space

The CPU runs in one of two modes.

```
┌─────────────────────────────────────────────────┐
│ USER SPACE  (ring 3)                            │
│   python  ·  postgres  ·  nginx  ·  redis       │
│   Can only touch its own memory.                │
│   Cannot run privileged instructions.           │
├──────────────── system call ────────────────────┤
│ KERNEL SPACE  (ring 0)                          │
│   scheduler · memory manager · VFS · TCP/IP     │
│   device drivers · cgroups · namespaces         │
│   Can touch everything.                         │
├─────────────────────────────────────────────────┤
│ HARDWARE   CPU · RAM · disk · NIC · timers      │
└─────────────────────────────────────────────────┘
```

The wall between them is enforced by the **CPU itself**, not by software. A user-space program that tries to execute a privileged instruction or touch kernel memory gets a hardware fault, and the kernel kills it. That is what a segfault is.

💡 This is why a bug in your Python code cannot crash the machine, but a bug in a kernel driver can.

## System Calls: The Only Door

A system call is a controlled jump into the kernel. The program puts a number (which call) and arguments in registers, then executes a special instruction (`syscall` on x86-64). The CPU switches to kernel mode, jumps to a fixed entry point, the kernel does the work, and returns.

```
Python:     f.read(4096)
  │
  ▼
CPython:    _io.FileIO.read → read(fd, buf, 4096)       (C call)
  │
  ▼
glibc:      read() wrapper → puts 0 in rax, args in rdi/rsi/rdx
  │         executes `syscall`
  ▼
Kernel:     entry_SYSCALL_64 → sys_read → vfs_read → ext4 / page cache
  │
  ▼
Back to user space with the byte count in rax
```

There are about 350 system calls on Linux x86-64. A backend service uses maybe 40 of them. Learn these and you can read any `strace`:

| Group | Calls |
|---|---|
| Files | `openat`, `read`, `write`, `close`, `lseek`, `fstat`, `fsync`, `pread64`, `pwrite64` |
| Network | `socket`, `bind`, `listen`, `accept4`, `connect`, `sendto`, `recvfrom`, `setsockopt` |
| Waiting | `epoll_create1`, `epoll_ctl`, `epoll_wait`, `poll`, `futex`, `nanosleep` |
| Memory | `mmap`, `munmap`, `brk`, `madvise` |
| Processes | `clone` / `clone3`, `execve`, `wait4`, `exit_group`, `kill` |
| Signals | `rt_sigaction`, `rt_sigprocmask`, `rt_sigreturn` |
| Time | `clock_gettime` (usually not a real syscall — see vDSO below) |

### What a syscall costs

| Thing | Rough cost |
|---|---|
| Function call in C | ~1 ns |
| Minimal syscall (`getpid`) | ~50–100 ns |
| Syscall after Spectre/Meltdown mitigations | ~100–500 ns |
| `read` of 4 KB from the page cache | ~1 µs |
| Context switch between threads | ~1–5 µs, plus cache misses afterward |

A single syscall is cheap. **Millions of tiny ones are not.** A logging library that calls `write` once per line, at 50,000 lines a second, spends real CPU just crossing the wall. This is why buffered I/O exists, and why `sendfile`, `writev` and `io_uring` exist — they do more work per crossing.

💡 **The vDSO.** Some calls are so hot that the kernel maps a small piece of read-only code into every process so they skip the crossing. `clock_gettime` and `gettimeofday` work this way. That is why `time.time()` is fast in Python and does not show up in `strace`.

## Watching Syscalls With strace

`strace` uses `ptrace` to stop the process at every syscall and print it. It is the single most useful OS tool for a backend engineer.

```bash
# Every syscall a command makes
strace -f python -c "open('/etc/hostname').read()"

# Only file and network calls, with timing, attached to a running process
sudo strace -f -tt -T -e trace=%file,%network -p $(pgrep -f uvicorn | head -1)

# A summary table: which calls, how many, how long
strace -c -f python app.py
```

Read the output line by line:

```
openat(AT_FDCWD, "/etc/hostname", O_RDONLY|O_CLOEXEC) = 3
fstat(3, {st_mode=S_IFREG|0644, st_size=7, ...}) = 0
read(3, "laptop\n", 8192)               = 7
read(3, "", 8185)                       = 0
close(3)                                = 0
```

- `= 3` is the return value: file descriptor 3 (0, 1, 2 are stdin, stdout, stderr).
- The second `read` returns 0. That is how a program learns it reached end of file.
- `O_CLOEXEC` means "close this fd if the process calls `execve`". Python sets it on everything by default (PEP 446).

⚠️ **`strace` slows the traced process down by 10–100x.** Never leave it attached to a production process under load. For production, use `perf trace` or eBPF tools (`bpftrace`, `bcc`'s `syscount`), which are far cheaper. See [[02.11 - Linux Observability Tools]].

## How Python Sits on the OS

```
your code
   │
CPython interpreter (C)          ← Modules/posixmodule.c wraps ~200 syscalls as os.*
   │
libc (glibc or musl)             ← malloc, buffered stdio, DNS resolver, pthreads
   │
Linux kernel                     ← the real work
```

Three consequences you will meet in production:

1. **`os.*` is a thin skin.** `os.read`, `os.fork`, `os.kill` are one syscall each. When Python behaves oddly at the OS level, read the man page of the syscall, not the Python docs.
2. **libc matters.** Alpine images use musl instead of glibc. musl's `malloc` and DNS resolver behave differently, and Python wheels built for glibc do not work on it. Many "it is slower in Docker" stories are really musl stories.
3. **The GIL does not stop the kernel.** While a thread waits in `read` or `epoll_wait`, CPython releases the GIL. The kernel is doing the waiting, not Python. See [[01.2 - The GIL]].

## Interrupts: How the Kernel Gets Control Back

A syscall is the program asking the kernel for something. An **interrupt** is the hardware getting the kernel's attention.

| Source | Example | What happens |
|---|---|---|
| Timer interrupt | Fires every 1–4 ms per CPU | The scheduler checks whether the current thread has used its time slice. This is how preemption works. |
| Device interrupt | NIC got a packet, disk finished a read | The driver queues the work, often deferring it to a **softirq** |
| Exception or fault | Page fault, divide by zero, illegal access | The kernel fixes it (loads a page) or kills the process (`SIGSEGV`) |

The timer interrupt is why a `while True: pass` loop in one process does not freeze your laptop. The kernel takes the CPU back whether the program likes it or not. Coroutines do not get this — see [[01.3 - Threads Processes and Coroutines#Preemptive vs Cooperative]].

## In Production

| Symptom | The OS-level cause | Where it is covered |
|---|---|---|
| High `sys` CPU in `top` with low traffic | Too many small syscalls, or lock contention via `futex` | This note, [[02.4 - Locks and Synchronization]] |

## Codebase

**Repo:** `mit-pdos/xv6-riscv` — a complete teaching Unix kernel in about 10,000 lines of C. You can read all of it.

**Question to answer:** When a user program calls `read()`, trace every function from the user-space stub to the line that copies bytes into the user's buffer. Where does the CPU change mode, and where does it change back?

**Read, in order:**

1. `user/usys.pl` — generates the user-side stubs. Each one loads a number into a register and executes `ecall`.
2. `kernel/trampoline.S` — `uservec`, where the CPU lands on entry to the kernel
3. `kernel/trap.c` — `usertrap()`, which decides "this was a syscall"
4. `kernel/syscall.c` — the syscall table and `syscall()` dispatch
5. `kernel/sysfile.c` — `sys_read()` → `fileread()` in `kernel/file.c`
6. Back out via `usertrapret()` in `kernel/trap.c`

Then, for the real thing:

7. In the Linux source, `arch/x86/entry/entry_64.S` — `entry_SYSCALL_64`. Do not read all of it. Find where it calls `do_syscall_64`, and notice how much more is going on.

**Size:** 1–2 sessions. Have the xv6 book open alongside (chapter 2 and chapter 4).

## Exercise

**Drill 2.1 — The cost of crossing the wall**

```
drills/02-syscalls/
├── bench_syscall.c        # getpid() in a loop, 10M times, ns per call
├── bench_syscall.py       # os.getpid(), os.stat(), os.read() of 1 byte vs 64 KB
├── write_patterns.py      # write 100 MB: 1 byte/write, 4 KB/write, 1 MB/write, buffered file
├── strace_tour.md         # annotated strace of `python -c "import requests"`
└── FINDINGS.md
```

1. Measure the cost of a syscall in C and in Python. The gap between them is the interpreter, not the kernel.
2. Run `write_patterns.py` under `strace -c`. Record the number of `write` calls and the wall time for each pattern. Chart it.
3. Run `strace -f -c python -c "import requests"`. Count the `openat` and `newfstatat` calls. Explain why importing one package makes hundreds of filesystem calls (hint: the import system searches `sys.path`).
4. Attach `strace -f -e trace=%network` to a local uvicorn server and send one HTTP request. Annotate every line from `accept4` to the final `close`.

**Done when:** you can predict, before running it, roughly how many syscalls a small program makes, and you have one chart showing throughput versus bytes per `write`.
