# Frontend Security

## XSS — Cross-Site Scripting

Attacker-controlled script executing in your origin. It is the most consequential frontend vulnerability because it inherits everything the user has: cookies, tokens, session, DOM access.

**Three types:**

- **Stored** — the payload is saved server-side and served to every visitor. A comment field that renders raw HTML.
- **Reflected** — the payload comes from the URL and is echoed into the page. `?search=<script>...`
- **DOM-based** — never touches the server; client-side code writes untrusted data into a dangerous sink.

**The dangerous sinks:**

```js
el.innerHTML = untrusted;
el.outerHTML = untrusted;
document.write(untrusted);
eval(untrusted);
new Function(untrusted);
setTimeout(untrusted);              // string form
el.setAttribute("onclick", untrusted);
location.href = untrusted;          // javascript: URLs
element.srcdoc = untrusted;
```

Note that `<script>` inserted via `innerHTML` does **not** execute — so "I stripped script tags" is not a defense. These do:

```html
<img src=x onerror="alert(1)">
<svg onload="alert(1)">
<iframe srcdoc="<script>alert(1)</script>">
<a href="javascript:alert(1)">click</a>
<div style="background:url(javascript:alert(1))">
```

**Defenses, in order of reliability:**

```js
el.textContent = untrusted;                     // never interprets HTML
el.innerHTML = DOMPurify.sanitize(untrusted);   // when HTML is genuinely required
```

Context matters — escaping for HTML body is different from escaping for an attribute, a URL, or inside a `<script>`. Never hand-roll this; use a library that knows the context.

**URL validation** for anything user-supplied:

```js
function safeUrl(url) {
  try {
    const parsed = new URL(url, location.origin);
    return ["http:", "https:", "mailto:"].includes(parsed.protocol) ? url : "#";
  } catch {
    return "#";
  }
}
```

`javascript:` and `data:` URLs in an `href` are executable.

**In React**, JSX escapes interpolated values automatically, which eliminates most XSS by default. The escape hatches are:

```jsx
<div dangerouslySetInnerHTML={{ __html: sanitized }} />
<a href={userUrl}>                              {/* javascript: still works */}
<div {...userControlledProps} />                {/* could inject dangerouslySetInnerHTML */}
```

The deliberately alarming name of `dangerouslySetInnerHTML` exists to make it grep-able in review.

Third-party dependencies are the other major vector — a compromised npm package runs with full page privileges. Lockfiles, `npm audit`, and Subresource Integrity for CDN scripts all help:

```html
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-..." crossorigin="anonymous"></script>
```

## Content Security Policy

A response header restricting what the page may load and execute — defense in depth for when an XSS hole exists.

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'none';
  object-src 'none';
  report-uri /csp-report
```

**A nonce-based policy with `strict-dynamic` is the current recommendation.** Allowlisting domains is weak — most large CDNs host something that can be used to bypass the policy.

```html
<script nonce="r4nd0m">...</script>
```

The nonce must be regenerated per response and be unguessable.

Two directives worth calling out: **`frame-ancestors 'none'`** prevents clickjacking and supersedes `X-Frame-Options`; **`base-uri 'none'`** prevents an injected `<base>` tag from redirecting every relative URL on the page.

Deploy with `Content-Security-Policy-Report-Only` first and collect violations before enforcing. A CSP that breaks the application gets removed, which is worse than a slightly loose one.

`'unsafe-inline'` in `script-src` defeats the entire policy. `'unsafe-inline'` in `style-src` is a much smaller concern and is often unavoidable with CSS-in-JS or inline style attributes.

## CSRF — Cross-Site Request Forgery

An attacker's page causes the victim's browser to make an authenticated request to your site. It works because cookies are attached automatically ([[15.3 - Same Origin Policy and CORS]]).

```html
<!-- On attacker.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

**Defenses:**

**`SameSite` cookies** — `Lax` blocks cross-site POST entirely and is now the browser default ([[14.1 - Cookies]]). This is the primary defense.

**CSRF tokens** — a random value in the page, echoed in the request, verified server-side. The attacker cannot read it due to SOP. Still worth having for defense in depth and for browsers or configurations where `SameSite` is unreliable.

**Double-submit cookie** — the token is stored in a non-`HttpOnly` cookie and echoed in a header. Simpler for stateless backends, but weaker against subdomain compromise.

**Origin header check** — verify `Origin` or `Referer` matches on state-changing requests.

CSRF applies only to credentials the browser sends automatically. An `Authorization: Bearer` header set by JavaScript is not automatically attached, so token-in-header architectures are not CSRF-vulnerable — but they are more XSS-exposed ([[15.5 - JWT Sessions and Token Storage]]). The two threats trade off.

**GET must never change state.** `SameSite=Lax` permits top-level GET navigation, so a state-changing GET is exploitable by a plain link.

## Clickjacking

The attacker frames your page invisibly over their own UI, so the user's clicks land on your buttons.

```
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
```

Both, since some older intermediaries only honour the latter.

## Other headers

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

**HSTS** forces HTTPS for the specified duration, preventing downgrade attacks. `preload` submits your domain to a list baked into browsers — effective and effectively irreversible, so understand the commitment.

**`nosniff`** stops the browser guessing a content type, which prevents a text file being executed as script.

**`Referrer-Policy`** stops full URLs — which may contain tokens or ids — leaking to third parties.

## Prototype pollution

A JavaScript-specific class where an attacker sets `__proto__` through a merge or query-string parser, affecting every object:

```js
merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
({}).isAdmin;   // true
```

Defenses: `Object.create(null)` or `Map` for user-keyed data ([[06.5 - Map and Set]]), rejecting `__proto__`, `constructor` and `prototype` keys in merge utilities, and `Object.freeze(Object.prototype)` in some hardened setups.

## Dependency and supply chain

The largest practical risk for most teams. A single compromised transitive dependency executes in your users' browsers.

Practices that help: commit lockfiles, run `npm audit` in CI, pin versions rather than using ranges for critical dependencies, review what a package actually does before adding it, and use SRI for anything loaded from a CDN.

## How senior engineers actually use this

**They rely on the framework's escaping and treat every escape hatch as a review trigger.** A `dangerouslySetInnerHTML` in a diff gets read carefully every time.

**They ship a nonce-based CSP**, starting in report-only mode.

**They set the security header set once**, at the edge or in the server framework, rather than per route.

**They keep state changes out of GET**, without exception.

**They treat dependencies as attack surface**, and are reluctant to add packages for trivial functionality.

## Common pitfalls

- Sanitizing by stripping `<script>` tags.
- `dangerouslySetInnerHTML` with unsanitized content.
- Unvalidated `href` values allowing `javascript:` URLs.
- `'unsafe-inline'` in `script-src`, nullifying CSP.
- Relying on `SameSite` alone with no origin check.
- State-changing GET endpoints.
- Missing `frame-ancestors`, allowing clickjacking.
- Open redirects via unvalidated `returnTo` parameters.
- Secrets in frontend environment variables — anything in the bundle is public.

## Interview angle

XSS and CSRF are the two you will be asked about. For XSS: the three types, the dangerous sinks, why stripping script tags fails, and that React escapes by default with named escape hatches. For CSRF: why it works (automatic cookie attachment), and the defenses in order — `SameSite`, tokens, origin checks — plus the observation that Bearer-token architectures are not CSRF-prone but are more XSS-exposed. That tradeoff framing is what distinguishes a considered answer.
