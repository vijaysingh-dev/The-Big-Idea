# Production Dockerfiles

#backend #containers #operations

> **In one line:** A production image should be small, reproducible, non-root, and built so that a code change rebuilds one layer rather than all of them.

---

## The Idea

```dockerfile
# The plausible first attempt
FROM python:3.13
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD python -m app
```

| Problem | Cost |
|---|---|
| **Full base image** | ~1GB instead of ~150MB |
| **`COPY . .` before install** | Every code change reinstalls every dependency |
| Unpinned tag | Not reproducible; the base moves under you |
| **Runs as root** | The largest single security issue |
| **Shell-form `CMD`** | Signals are not forwarded ([[13.1 - Containers From First Principles]]) |
| Build tools in the final image | Attack surface, and size |
| No `.dockerignore` | `.git` and `.venv` shipped to the daemon and into the image |

---

## Layer Ordering

**Least-frequently-changing first.**

```dockerfile
FROM python:3.13-slim
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt    # cached until deps change

COPY . .                                              # invalidated per commit
CMD ["python", "-m", "app"]
```

💡 **A layer's cache is invalidated by its own change or any change above it.** Getting these two lines in the right order is the difference between a 5-second rebuild and a 3-minute one, on every single commit.

### Cache mounts

```dockerfile
RUN --mount=type=cache,target=/root/.cache/uv \
    uv pip install --system -r requirements.txt
```

💡 **A cache mount persists across builds without becoming a layer.** Even when the layer is invalidated, the downloaded packages are still there — **so a one-package change re-downloads one package, not all of them.**

**This requires BuildKit**, which is the default in modern Docker.

## Multi-Stage Builds

```dockerfile
FROM python:3.13-slim AS builder
RUN apt-get update && apt-get install -y --no-install-recommends gcc python3-dev \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.13-slim
COPY --from=builder /install /usr/local
COPY --chown=10001:10001 . /app
WORKDIR /app
USER 10001
CMD ["python", "-m", "app"]
```

💡 **The compiler, headers and build caches exist only in the builder stage.** The final image contains the installed packages and nothing that produced them.

⚠️ **This matters for security as much as size.** `gcc` in a production image is a tool available to anyone who achieves code execution.

## Base Image Choice

| Base | Size | Trade |
|---|---|---|
| `python:3.13` | ~1 GB | Everything, including build tools |
| **`python:3.13-slim`** | **~150 MB** | **The sensible default** |
| `python:3.13-alpine` | ~50 MB | ⚠️ musl libc |
| **distroless** | ~50 MB | No shell, no package manager |

⚠️ **Alpine's musl libc is a real problem for Python.** Many wheels are built for glibc, so pip compiles from source — **builds are much slower, and there are documented performance differences in DNS resolution and memory allocation.**

💡 **`slim` is the right default for Python.** The size difference against Alpine is small once your dependencies are installed, and the compatibility difference is large.

### Distroless

```dockerfile
FROM gcr.io/distroless/python3-debian12
COPY --from=builder /install /usr/local/lib/python3.13/site-packages
COPY . /app
WORKDIR /app
USER 10001
CMD ["-m", "app"]
```

**No shell, no package manager, no `curl`.** An attacker with code execution has almost no tooling.

⚠️ **`kubectl exec` does not work.** Debug with an ephemeral container instead ([[13.1 - Containers From First Principles]]):

```bash
kubectl debug -it pod --image=nicolaka/netshoot --target=app
```

💡 **This technique is what makes distroless practical**, and not knowing it is the main reason teams avoid distroless.

## Non-Root

```dockerfile
RUN groupadd -r -g 10001 app && useradd -r -u 10001 -g app app
COPY --chown=10001:10001 . /app
USER 10001
```

⚠️ **Use a numeric UID, not a name.** Kubernetes' `runAsNonRoot` check cannot verify a username — it needs a number to confirm it is not 0.

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  capabilities: {drop: ["ALL"]}
```

⚠️ **A read-only root filesystem breaks anything writing to disk** — temp files, matplotlib caches, some libraries' scratch directories.

```yaml
volumeMounts:
  - {name: tmp, mountPath: /tmp}
volumes:
  - {name: tmp, emptyDir: {}}
```

💡 **Find what your application writes by running with a read-only root and watching it fail.** It is usually one or two paths, and mounting `tmpfs` for them is cheap.

## Reproducibility

```dockerfile
FROM python:3.13-slim@sha256:1a2b3c...
```

⚠️ **A tag is mutable.** `python:3.13-slim` today is not the same image as last week, so **a rebuild of the same commit produces a different image.** For debugging "it worked yesterday", that is fatal.

**Pin dependencies with hashes too:**

```
fastapi==0.115.0 \
    --hash=sha256:abc123...
```

```dockerfile
RUN pip install --require-hashes -r requirements.txt
```

💡 **`--require-hashes` means a compromised package on the index cannot be silently substituted.** This is supply-chain security, and it costs one flag plus a lockfile.

## Build Speed

| Technique | |
|---|---|
| **Correct layer order** | The biggest win |
| **Cache mounts** | Dependency downloads survive invalidation |
| `.dockerignore` | Do not send `.git`, `.venv`, `node_modules` to the daemon |
| Registry cache | `--cache-from` in CI, where the local cache is empty |
| **`uv` instead of `pip`** | Often 10× faster dependency resolution |

```
.git
.venv
__pycache__
*.pyc
.pytest_cache
node_modules
.env
```

⚠️ **Without `.dockerignore`, `COPY . .` includes `.git`** — which can be hundreds of megabytes, and which may contain secrets from deleted commits.

### CI cache

```yaml
- uses: docker/build-push-action@v6
  with:
    cache-from: type=registry,ref=ghcr.io/org/app:buildcache
    cache-to: type=registry,ref=ghcr.io/org/app:buildcache,mode=max
```

💡 **CI runners start with an empty cache every time.** Without a registry cache, every CI build is a cold build — **and this one configuration block often halves pipeline time** ([[13.5 - CI CD Pipelines]]).

## In Production

### Scanning

```bash
trivy image --severity HIGH,CRITICAL ghcr.io/org/app:sha-abc123
grype ghcr.io/org/app:sha-abc123
```

⚠️ **Most CVEs in a base image are in packages your application never invokes.** Failing the build on every HIGH means the build is always failing and everyone learns to bypass it.

💡 **Fail on CRITICAL with a known fix; report the rest.** And **track the age of your base image** — rebuilding weekly against the latest patch version fixes more real vulnerabilities than any scanner policy.

**A smaller image has fewer CVEs simply because it contains less**, which is a genuine security argument for distroless.

### SBOM and provenance

```bash
docker buildx build --sbom=true --provenance=true -t ghcr.io/org/app:sha .
```

💡 **An SBOM answers "are we affected by this new CVE" in seconds instead of a day.** When the next Log4Shell-scale vulnerability lands, that is the difference between a calm afternoon and a scramble.

### Tagging

```
ghcr.io/org/app:sha-a1b2c3d      ← immutable, what you deploy
ghcr.io/org/app:v1.4.2           ← release
ghcr.io/org/app:main             ← moving, for convenience only
```

⚠️ **Deploy by digest or commit SHA, never by a moving tag.** `image: app:latest` means you cannot know what is running, and a pod restart can silently change the version.

### One image, many roles

```yaml
- name: api
  command: ["uvicorn", "app.main:app"]
- name: worker
  command: ["arq", "app.worker.Settings"]
- name: scheduler
  command: ["arq", "app.scheduler.Settings"]
```

💡 **One image, three deployments.** You get independent scaling and placement without separate services, separate pipelines or version skew between components ([[10.1 - Monolith Modular Monolith Microservices]]).

**This is the answer to "we need to scale the worker separately" that most people miss.**

### The final Dockerfile

```dockerfile
# syntax=docker/dockerfile:1.10
FROM python:3.13-slim@sha256:... AS builder

RUN apt-get update && apt-get install -y --no-install-recommends gcc python3-dev \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /build
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --prefix=/install --require-hashes -r requirements.txt

FROM python:3.13-slim@sha256:...

RUN groupadd -r -g 10001 app && useradd -r -u 10001 -g app app

COPY --from=builder /install /usr/local
WORKDIR /app
COPY --chown=10001:10001 . .

USER 10001
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

⚠️ **`PYTHONUNBUFFERED=1` is not optional.** Without it, Python buffers `stdout` when it is not a TTY, **so your logs appear in chunks or vanish entirely when the container is killed** — which is exactly when you need them.

### The checklist

```
□  Multi-stage; no build tools in the final image
□  Base pinned by digest
□  Dependencies before source code
□  Cache mounts for dependency downloads
□  .dockerignore excluding .git, .venv, caches
□  Non-root numeric UID
□  Exec-form CMD
□  PYTHONUNBUFFERED=1
□  Requirements pinned with hashes
□  Scanned, with a policy that does not block on noise
□  SBOM generated
□  Tagged by commit SHA
□  Read-only root filesystem, with tmpfs where needed
□  Image size measured and justified
```

## Codebase

**Repo:** `docker-library/python`, `GoogleContainerTools/distroless`, `astral-sh/uv`

**Question to answer:** What is actually in `python:3.13-slim` versus `python:3.13`, and where does the size difference come from? Then: how does distroless produce an image with no shell, and what is still in it?

**Read, in order:**

1. `docker-library/python` — the `slim` and full Dockerfiles side by side. **The answer to the first question**: `slim` omits the build toolchain and most of the Debian package set
2. `GoogleContainerTools/distroless/base/BUILD` and the language-specific targets — **Bazel rules assembling an image from packages, with no package manager.** The answer to the second question
3. `moby/buildkit` — the cache mount and `--mount=type=cache` documentation. **How the cache persists outside the layer graph**
4. `astral-sh/uv` — the README and benchmarks. **Worth evaluating; the resolution speed difference in CI is substantial**
5. Any well-maintained project's Dockerfile — **Sentry's and Onyx's are worth comparing** to the checklist above

💡 Reading the official Python Dockerfiles is more instructive than it sounds. **You can see exactly what `slim` removes and decide whether you need it**, rather than choosing a base by reputation.

**Size:** 1 session.

## Exercise

**Drill 13.2 — Take an image from 1.2GB to 90MB**

```
drills/13-dockerfiles/
├── v0/{Dockerfile, MEASURE.md}
├── iterations/{v1_slim, v2_layers, v3_multistage, v4_distroless, v5_hardened}
├── build_speed/{cold.sh, warm.sh, cache_mount.sh, ci_cache.yaml, RESULTS.md}
├── security/{scan.sh, sbom.sh, escape.sh, FINDINGS.md}
├── runtime/{signals.py, readonly.yaml, roles.yaml}
└── README.md
```

**Part 1 — Build the bad version, and measure it.** The plausible first attempt from this note.

**Measure: image size, cold build time, warm build time after a one-line code change, layer count, CVE count, and whether it runs as root.**

**Part 2 — Five iterations.** Apply one change at a time, measuring all six metrics at each step:

| Step | Change |
|---|---|
| v1 | `slim` base |
| v2 | Layer reordering + `.dockerignore` |
| v3 | Multi-stage |
| v4 | Distroless |
| v5 | Non-root + read-only + capabilities dropped |

**Build the table. Six metrics × six versions.**

💡 **The v2 warm-build-time improvement should be dramatic** — from minutes to seconds — and it is the change with the largest daily impact on your life.

**Part 3 — Build speed properly.** Measure cold and warm builds for: no cache, layer cache only, layer cache plus cache mounts, and `uv` instead of `pip`.

**Then simulate CI:** empty local cache every time. **Measure with and without a registry cache.**

**Report the CI pipeline time saved.** This is usually the highest-value optimisation in the whole drill.

**Part 4 — Signals and shutdown.** Test all four combinations of shell/exec form and handler/no handler.

**Time `docker stop` for each.** Confirm exec form alone is insufficient without a handler.

Then confirm `PYTHONUNBUFFERED=1` matters: **log continuously, kill the container, and compare logs captured with and without it.**

**Part 5 — Read-only root.** Run with `readOnlyRootFilesystem: true`.

**Record every path your application tries to write to.** Then mount `tmpfs` for each and confirm it works.

**Report how many paths you did not expect.**

**Part 6 — Security comparison.** Scan all six versions.

**Chart CVE count against image size** — the correlation should be strong.

Then, in each version, attempt: spawn a shell, install a package, read `/etc/shadow`, write to `/app`, and escalate to root.

**Confirm distroless plus hardening blocks nearly all of it.**

**Part 7 — One image, three roles.** Build one image and deploy it as api, worker and scheduler with different commands and resource limits.

**Confirm all three run correctly from one build**, and measure the pipeline time saved versus three separate images.

**Part 8 — SBOM in anger.** Generate an SBOM. Then pick a real CVE in one of your dependencies.

**Time how long it takes to answer "are we affected" with the SBOM and without it.**

**Done when:**
- Your six-metric table covers all six versions
- Warm build time after a code change dropped from minutes to seconds
- Registry caching measurably cut CI pipeline time
- All four signal-handling combinations are timed
- You found every path your application writes to under a read-only root
- CVE count correlates with image size across your versions
- One image serves three roles in production
- The SBOM answers a CVE question in seconds
