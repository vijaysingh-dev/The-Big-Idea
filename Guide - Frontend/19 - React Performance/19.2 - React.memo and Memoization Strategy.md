# React.memo and Memoization Strategy

`React.memo` wraps a component so React skips re-rendering it when its props are unchanged.

```jsx
const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});
```

Without it, a component re-renders whenever its parent does, regardless of props ([[19.1 - What Causes Re-renders]]).

## The comparison

React compares each prop with `Object.is` — a shallow comparison. Any prop whose reference changed fails:

```jsx
<Row item={item} onSelect={() => select(item.id)} />   // new function every render
<Row item={{ ...item }} onSelect={onSelect} />          // new object every render
<Row item={item} style={{ padding: 8 }} />             // new object every render
```

Each of these defeats the memo entirely. The component is now slower than an unmemoized one, because it pays for the comparison and re-renders anyway.

This is the single most common memoization failure, and it is silent — nothing warns you.

## Making it work

Every non-primitive prop must have a stable reference:

```jsx
function List({ items }) {
  const handleSelect = useCallback((id) => select(id), []);

  return items.map(item => (
    <Row key={item.id} item={item} onSelect={handleSelect} />
  ));
}
```

`item` comes from the array and is stable as long as the array is not recreated. `handleSelect` is stabilized with `useCallback` ([[17.7 - useCallback]]).

The chain matters: if `items` is recreated every render (`items.filter(...)` in the body), every `item` reference is still stable but the array is not — which affects the parent, not the rows. Trace which reference actually reaches the memoized boundary.

## The custom comparator

```jsx
const Row = React.memo(
  function Row({ item }) { ... },
  (prev, next) => prev.item.id === next.item.id && prev.item.name === next.item.name
);
```

Returns `true` to **skip** the render — the opposite of `shouldComponentUpdate`, which returns `true` to render. This inversion catches people constantly.

Use it sparingly. A deep comparison can cost more than the render it prevents, and a comparator that forgets a prop produces a component that silently stops updating — a much worse bug than an extra render.

The legitimate case is a prop that is structurally stable but referentially unstable and cannot be fixed upstream, such as data from a third-party library.

## When memo is worth it

**Large subtrees.** A memoized component that would have rendered two hundred descendants saves two hundred function calls.

**Expensive render logic.** Charts, editors, syntax highlighters, anything doing real computation in the body.

**List rows in long lists.** A thousand rows where only one changes.

**Components rendering on high-frequency parent updates.** A sidebar next to an input whose parent re-renders per keystroke.

## When memo does nothing

```jsx
const Text = React.memo(({ label }) => <span>{label}</span>);
```

A trivial component costs less to render than to compare. Memoizing it adds overhead.

```jsx
const Child = React.memo(({ onClick }) => ...);
<Child onClick={() => x()} />     // new function — memo never hits
```

An always-changing prop makes the memo pure overhead.

```jsx
const Child = React.memo(() => {
  const theme = useContext(ThemeContext);   // context changes bypass memo
});
```

`React.memo` compares props. Context is not a prop, so a context change re-renders the component regardless ([[17.9 - useContext]]).

Same for its own state — memo only blocks parent-driven renders.

## Composition usually beats memo

```jsx
// Memoization approach
const ExpensiveChild = React.memo(Child);
const handler = useCallback(..., []);
const config = useMemo(() => ({ ... }), []);
<ExpensiveChild onAction={handler} config={config} />

// Composition approach — no memo, no hooks, cannot go stale
<Parent>
  <Child />
</Parent>
```

Passing an element as `children` means it is created in the outer render, so its reference is stable and React skips the subtree during reconciliation ([[18.1 - Virtual DOM and React Elements]]).

The composition version has no dependency arrays, so it cannot break when someone adds a prop and forgets to update a memo. Try this before reaching for memoization.

## The memoization cascade

The real cost of `React.memo` is that it is never one change:

```
memo(Child)
  → useCallback for every function prop
    → its dependencies must also be stable
      → useMemo for every object prop
        → their dependencies must also be stable
```

One unstable link at the bottom invalidates the whole chain, silently. Maintaining this by hand across a codebase is genuinely difficult, and half-applied memoization is worse than none.

This is precisely the problem the React Compiler solves ([[19.9 - The React Compiler]]) — it inserts memoization automatically at every level, correctly, based on static analysis. On a compiled codebase, manual `React.memo` becomes largely unnecessary.

## Measuring the benefit

```jsx
<Profiler id="List" onRender={(id, phase, actualDuration) => log(id, actualDuration)}>
  <List items={items} />
</Profiler>
```

Or use the DevTools Profiler and compare actual durations before and after ([[19.8 - Profiling with React DevTools]]).

Test with CPU throttling at 4–6×, since the difference is usually invisible on a development machine and visible on a mid-range phone.

If the profiler does not show a measurable improvement, remove the memo — it is cost with no benefit plus a maintenance burden.

## memo in lists

The pattern where memo genuinely earns its place:

```jsx
const Row = React.memo(function Row({ item, onToggle }) {
  return (
    <li>
      <input type="checkbox" checked={item.done} onChange={() => onToggle(item.id)} />
      {item.text}
    </li>
  );
});

function TodoList({ todos, onToggle }) {
  const handleToggle = useCallback(onToggle, []);
  return <ul>{todos.map(t => <Row key={t.id} item={t} onToggle={handleToggle} />)}</ul>;
}
```

Toggling one todo produces a new array with one new item object; the other 999 items keep their references, so 999 rows skip rendering. This requires immutable updates that preserve unchanged references — structural sharing ([[06.7 - Immutable Data Patterns]]).

A deep clone of the array would give every item a new reference and defeat the memo entirely, which is a good illustration of why deep cloning state is harmful.

## How senior engineers actually use this

**They memoize at boundaries, not everywhere.** A memo on a list row or an expensive panel; nothing on a `<Label>`.

**They verify the memo actually holds.** The Profiler's "why did this render" shows "Props changed: onSelect" when a callback is unstable — that is the confirmation the memo is working or not.

**They prefer composition** and treat reaching for memo as an admission that composition did not fit.

**They preserve references in state updates**, since memoized lists depend entirely on structural sharing.

**They remove memos that do not measure.**

## Common pitfalls

- Inline objects, arrays or functions as props to a memoized component.
- A `useCallback` whose own dependencies are unstable.
- Expecting memo to block context or state-driven re-renders.
- Custom comparators returning the wrong boolean, or omitting a prop.
- Memoizing trivial components.
- Deep-cloning state and destroying the reference stability memo relies on.

## Interview angle

"What is React.memo and when should you use it" wants: a higher-order component that shallowly compares props and skips re-rendering when they are unchanged, useful for expensive components and list rows. The stronger material is why it so often fails — inline object and function props — and the memoization cascade that follows from needing every dependency to be stable. Closing with "composition usually beats memoization, and the React Compiler is removing the manual work" positions you as current rather than reciting 2019 advice.
