# Service Discovery and Service Mesh

#backend #microservices #infrastructure

> **In one line:** Service discovery answers "where is the payments service right now", and a mesh moves retries, timeouts, mTLS and traffic policy out of your code into a sidecar — which is powerful and is a substantial operational commitment.

---

## Service Discovery

```
payments-service is at 10.0.4.17:8080
  ...until it is rescheduled, and now it is at 10.0.7.203:8080
```

⚠️ **In a container platform, instances come and go constantly.** Hardcoded addresses are impossible, and a static configuration file is out of date within minutes.

### The three mechanisms

| Mechanism | How |
|---|---|
| **DNS** | Resolve `payments.default.svc.cluster.local` |
| **Registry** | Services register; clients query Consul, etcd or Eureka |
| **Platform-native** | Kubernetes Services, with the platform maintaining the endpoints |

### Kubernetes: the default answer

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payments
spec:
  selector:
    app: payments
  ports:
    - port: 8080
```

```python
await client.get("http://payments:8080/charge")
```

The kubelet and kube-proxy maintain routing to whichever pods are currently ready. **You get discovery, load balancing and health-based removal from one object.**

⚠️ **The load balancing is L4** — it balances connections, not requests ([[03.10 - Proxies and Load Balancers]]).

💡 **For HTTP/1.1 that is fine.** For gRPC and HTTP/2, one connection carries every request, so every request goes to one pod ([[03.8 - HTTP2]]).

**This is the single most common gRPC-on-Kubernetes surprise**, and it is the problem a mesh solves most convincingly.

### Headless services and client-side balancing

```yaml
spec:
  clusterIP: None          # headless
```

DNS now returns every pod's IP rather than one virtual IP.

```python
channel = grpc.aio.insecure_channel(
    "dns:///payments:8080",
    options=[("grpc.service_config", json.dumps({
        "loadBalancingConfig": [{"round_robin": {}}]
    }))],
)
```

💡 **gRPC's built-in client-side load balancing resolves all endpoints and opens a connection to each**, balancing requests across them. **This solves the L4 problem without a mesh**, and it is the option people skip.

⚠️ **It requires the client library to support it and to re-resolve DNS periodically.** A client that resolves once at startup never learns about new pods ([[02.8 - DNS]]).

```python
options=[("grpc.dns_min_time_between_resolutions_ms", 30000)]
```

## The Service Mesh

```
Service A ──► [ sidecar ] ══mTLS══► [ sidecar ] ──► Service B
```

**A proxy next to every service**, intercepting all traffic. Your application talks to localhost; the sidecar does everything else.

| Capability | Otherwise implemented in |
|---|---|
| **mTLS between services** | Every service, or nowhere |
| **Retries and timeouts** | Every client library |
| **Circuit breaking** | Every client library |
| **Load balancing (L7)** | Client libraries, or lost |
| **Traffic splitting** | Your deployment tooling |
| **Observability** | Every service's instrumentation |
| **Authorisation policy** | Every service |

💡 **The argument is uniformity: every service gets the same retry policy, the same mTLS, the same metrics, regardless of language — without any of them implementing it.**

⚠️ **For a single-language shop, that argument is much weaker.** A shared Python client library gives you the same uniformity with none of the sidecar's cost.

### What it costs

| Cost | |
|---|---|
| **Latency** | Two extra proxy hops per call, typically 1–3ms |
| **Resources** | 50–200MB and a fraction of a CPU **per pod** |
| **Complexity** | A control plane, sidecar injection, certificate rotation |
| **Debugging** | An extra layer between your code and the network |
| **Upgrades** | Control plane and data plane, coordinated |
| **Cognitive load** | A second networking model your team must know |

⚠️ **At 200 pods, sidecars alone can be 20–40GB of memory and a meaningful CPU bill.** That is a real line item.

💡 **Ambient mode (Istio) and sidecar-less designs address this** by moving L4 handling to a per-node proxy and making L7 features opt-in. **Worth evaluating** if the resource cost is the blocker.

## When a Mesh Is Worth It

```
Do you have multiple languages, or many services?
├── NO (one language, under ~10 services)
│   └── A shared client library. Do not add a mesh
│
└── YES
    ├── Do you need mTLS everywhere for compliance?
    │   └── Strong argument for a mesh
    ├── Do you need traffic splitting for canaries?
    │   └── Strong argument
    ├── Is gRPC L4 load balancing your only problem?
    │   └── Use gRPC client-side balancing instead
    └── Do you want uniform observability across languages?
        └── Good argument
```

💡 **The strongest genuine reasons are mTLS at scale and polyglot uniformity.** Both are organisational — they are about not trusting every team to implement the same thing correctly.

⚠️ **"We need retries and circuit breakers" is not a reason to adopt a mesh** if you have one language. A library gives you that ([[11.3 - Circuit Breakers and Bulkheads]]).

### The library alternative

```python
# One shared client, used by every service
class ServiceClient:
    def __init__(self, name: str):
        self.breaker = CircuitBreaker(...)
        self.client = httpx.AsyncClient(
            base_url=f"http://{name}:8080",
            timeout=httpx.Timeout(connect=2, read=5),
        )

    async def call(self, method: str, path: str, *, required: bool = True, **kw):
        if self.breaker.is_open():
            if required:
                raise DependencyUnavailable(self.name)
            return None
        ...
```

| | Library | Mesh |
|---|---|---|
| Languages | **One** | Any |
| Latency overhead | **Zero** | 1–3ms |
| Resource overhead | **Zero** | Per pod |
| Upgrade | Redeploy services | Restart sidecars |
| Consistency | Depends on adoption | **Enforced** |
| Debuggability | **In your stack trace** | Two layers away |

💡 **For Conduit — one language, a handful of services — the library is clearly right**, and the ADR should say so with the resource arithmetic.

## mTLS

The capability that most justifies a mesh.

```
Service A ──► sidecar ══mTLS══► sidecar ──► Service B
              ▲ presents A's cert    ▲ verifies it is A
```

💡 **Every service gets an identity backed by a certificate, rotated automatically**, and services authorise based on that identity rather than on network position ([[02.9 - TLS]]).

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
spec:
  selector:
    matchLabels: {app: payments}
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/default/sa/checkout"]
```

**Only the checkout service may call payments**, enforced by the mesh, regardless of network policy.

⚠️ **Without a mesh, mTLS between services means certificate issuance, distribution and rotation in every service** — which is exactly the work nobody does, so it does not happen.

💡 **"We need mTLS everywhere and nobody wants to build certificate rotation" is the most honest reason to adopt a mesh**, and it is a good one.

## Traffic Management

```yaml
# Canary: 5% to the new version
apiVersion: networking.istio.io/v1
kind: VirtualService
spec:
  http:
    - route:
        - destination: {host: payments, subset: v1}
          weight: 95
        - destination: {host: payments, subset: v2}
          weight: 5
```

💡 **Traffic splitting at the mesh layer is independent of deployment**, so a canary is a configuration change rather than a rollout ([[10.10 - Deployment Strategies]]).

**Other capabilities worth knowing:**

| Feature | |
|---|---|
| **Fault injection** | Inject latency or errors to test resilience |
| **Mirroring** | Send a copy of traffic to a new version, discard the response |
| **Locality-aware routing** | Prefer same-zone endpoints, reducing cross-AZ cost |
| **Outlier detection** | Eject unhealthy endpoints automatically ([[03.10 - Proxies and Load Balancers]]) |

⚠️ **Traffic mirroring is genuinely useful and underused.** Send real production traffic to a new version, compare the responses, and discard them — a load test with real data and zero user risk.

## The Double-Retry Trap

⚠️ **The mesh retries. Your client library also retries. Now you have nine attempts.**

```
Application: 3 retries
Mesh:        3 retries
→ 9 requests per logical call
```

💡 **This is retry amplification** ([[03.4 - Idempotency and Safe Retries]]), and adopting a mesh without removing application-level retries is a common way to make an outage worse.

**Pick one layer:**

| Layer | When |
|---|---|
| **Mesh** | Uniform policy, no application knowledge needed |
| **Application** | Retry decisions need domain knowledge — idempotency, business rules |

⚠️ **The mesh does not know whether your POST is idempotent.** By default Istio retries only on connection failures and specific status codes, and configuring it to retry more aggressively without idempotency keys is dangerous.

💡 **The pragmatic split: let the mesh retry connection failures and 503s; let the application retry anything requiring judgement.** Document which layer owns which failure class.

**The same applies to timeouts, circuit breakers and rate limiting** — two layers doing the same thing produces behaviour neither team predicted.

## In Production

### Adopting incrementally

```
1. Install the control plane, inject nothing
2. Enable sidecars for one non-critical service, permissive mTLS
3. Verify: latency impact, resource usage, observability
4. Expand service by service
5. Switch to strict mTLS once everything is meshed
6. Remove application-level retries and circuit breakers
```

⚠️ **Step 5 before everything is meshed breaks unmeshed services**, because strict mTLS rejects plaintext.

💡 **Permissive mode — accept both mTLS and plaintext — is what makes incremental adoption possible.** It is also what you forget to turn off, leaving the security benefit unrealised.

**Audit for permissive mode.** A mesh in permissive mode provides observability and not security.

### The sidecar lifecycle problems

⚠️ **Two ordering problems that cause real incidents:**

**Startup race:** the application starts before the sidecar is ready and its first outbound calls fail.

```yaml
# Kubernetes native sidecars (1.29+) solve this properly
initContainers:
  - name: istio-proxy
    restartPolicy: Always      # a sidecar that starts first and stops last
```

**Shutdown race:** the sidecar terminates before the application finishes in-flight requests.

```yaml
lifecycle:
  preStop:
    exec: {command: ["sleep", "5"]}
```

💡 **Native sidecar containers fix both**, and if you are on an older Kubernetes you must work around them manually ([[11.7 - Graceful Shutdown and Draining]]).

⚠️ **Jobs and CronJobs are the classic victim** — the pod never completes because the sidecar never exits. Native sidecars fix this too.

### Observability from the mesh

```
istio_requests_total{source_app, destination_service, response_code}
istio_request_duration_milliseconds
```

💡 **The mesh gives you a complete service dependency graph and golden signals for every call, with no instrumentation.** That is genuinely valuable and it is the benefit teams notice first.

⚠️ **It is not a substitute for application tracing.** The mesh sees requests between services; it does not see what happened inside one, or work that went through a queue ([[12.3 - Instrumenting Conduit End to End]]).

**You still need OpenTelemetry in the application**, and the mesh must propagate the trace headers.

### Debugging with a mesh

```bash
istioctl proxy-config routes <pod>          # what routes does this sidecar know?
istioctl proxy-config endpoints <pod>       # what endpoints?
istioctl analyze                            # configuration problems
kubectl logs <pod> -c istio-proxy           # the sidecar's own logs
```

⚠️ **A request failing between two healthy services is now a mesh configuration question**, and diagnosing it requires knowing these commands. **That is the cognitive cost, made concrete.**

💡 **The most common mesh failure is a configuration change with an unintended blast radius** — an `AuthorizationPolicy` or `VirtualService` matching more than intended. **`istioctl analyze` catches many of them; a staging environment catches the rest.**

### Conduit's decision

**No mesh. A shared client library.**

| Reason | |
|---|---|
| One language | Python throughout |
| Four services | The uniformity argument does not apply |
| No compliance mTLS requirement | Network policy is sufficient |
| gRPC L4 balancing | **Solved by client-side balancing**, not by a mesh |
| Resource cost | Sidecars would be a significant fraction of the footprint |

💡 **The gRPC point is the important one**, because it is the problem most likely to push you toward a mesh. **`dns:///` with a headless service and gRPC's built-in round-robin solves it for free.**

⚠️ **Write down the triggers for reconsidering:** a second language, mTLS as a compliance requirement, or more than about ten services where library adoption becomes inconsistent.

## Codebase

**Repo:** `istio/istio`, `envoyproxy/envoy`, `grpc/grpc`

**Question to answer:** How does a sidecar intercept traffic without the application knowing? Then: how does gRPC's client-side load balancing discover and track endpoints, and how does it differ from what a mesh does?

**Read, in order:**

1. `istio/tools/istio-iptables/` — **the iptables rules that redirect traffic to the sidecar.** This is the interception mechanism, and seeing it makes the whole model concrete. **The answer to the first question**
2. `istio/pilot/pkg/xds/` — **how the control plane pushes configuration to sidecars** via xDS. Compare to a static proxy config ([[10.6 - API Gateway and BFF]])
3. `envoy/source/common/upstream/load_balancer_impl.cc` — the L7 load balancing the sidecar performs, including power-of-two-choices ([[03.10 - Proxies and Load Balancers]])
4. `grpc/grpc/src/core/ext/filters/client_channel/resolver/dns/` and `lb_policy/round_robin/` — **client-side discovery and balancing.** **The answer to the second question — and note it does the same job with no proxy**
5. `istio/pilot/pkg/security/` — certificate issuance and rotation for mTLS. **The work you would otherwise do yourself**

💡 The iptables reading is the one that removes the magic. **A sidecar works because `REDIRECT` rules send all outbound traffic on the pod's network namespace to port 15001, where Envoy is listening.** Once you have seen the rules, mesh debugging becomes ordinary networking debugging.

**Size:** 1–2 sessions.


**Part 1 — The gRPC L4 problem, reproduced.** Three replicas of a gRPC service behind a standard Kubernetes Service.

Send 10,000 requests from one client. **Count requests per pod.**

**It should be roughly 10,000 / 0 / 0.**

Then switch to a headless service with gRPC client-side round-robin. **Count again.**

Then scale to five replicas mid-test and measure how long until the client sends to the new pods. **Then set `dns_min_time_between_resolutions_ms` and measure again.**

**Part 2 — The client library.** Build the shared client: timeouts from a request budget, retries with jitter, a circuit breaker, trace propagation, and metrics.

Use it in four services. **Then have one service not use it** — hand-rolled `httpx` calls.

**Take a dependency down and measure the difference in behaviour** between the service using the library and the one not.

**Part 3 — Install a mesh.** Istio or Linkerd, on the same four services.

Measure before and after: p50 and p99 latency, memory per pod, CPU per pod, and total cluster resource usage.

**Extrapolate the resource cost to 50 and 200 pods.** That number is usually decisive.

**Part 4 — Capability comparison.** For each of eight capabilities — mTLS, retries, timeouts, circuit breaking, L7 load balancing, traffic splitting, fault injection, dependency graph — record whether the library or the mesh provides it, and how much work each required.

**Eight rows, two columns.** The mesh should win on mTLS, traffic splitting and the dependency graph, and tie or lose on the rest.

**Part 5 — Double retry.** Application retrying three times, mesh retrying three times.

Instrument the downstream to count. **Confirm nine requests per logical call.**

Chart total downstream load against failure rate, with both layers and with one. **The two-layer version should grow quadratically.**

Then decide the split and document which layer owns which failure class.

**Part 6 — The lifecycle races.**

- **Startup:** an application making an outbound call immediately on start. **Confirm it fails before the sidecar is ready.** Then use native sidecars and confirm it does not
- **Shutdown:** in-flight requests during pod termination. **Measure requests dropped** with and without the `preStop` workaround
- **Job:** a Kubernetes Job with a sidecar. **Confirm it never completes.** Then fix it

**Part 7 — Permissive mTLS.** Enable the mesh in permissive mode.

**Call a meshed service from an unmeshed pod, in plaintext, and confirm it succeeds.**

Then switch to strict and confirm it is rejected — and confirm that any unmeshed service you forgot is now broken.

**Write down the audit query for finding namespaces still in permissive mode.**

**Part 8 — Fault injection and mirroring.** Use the mesh to inject 5% 503s and 2 seconds of latency into one dependency.

**Verify your circuit breakers and degradation actually work** under real injected failure rather than a mock ([[11.3 - Circuit Breakers and Bulkheads]]).

Then mirror production traffic to a second version and compare responses without any user impact.

**Part 9 — The ADR.** Mesh, library, or hybrid for Conduit.

**Cite: your gRPC distribution numbers, your resource extrapolation, and your capability comparison.** Name the specific triggers that would change the decision.

**Done when:**
- You reproduced 10,000/0/0 gRPC distribution and fixed it without a mesh
- Your resource extrapolation to 200 pods has a real number
- The eight-capability comparison shows exactly what a mesh buys you
- Double retry produced nine requests, and you have a documented split
- All three lifecycle races are reproduced and fixed
- You called a meshed service in plaintext under permissive mode
- Fault injection verified your circuit breakers against real failures
- The ADR cites your numbers and names its triggers
