# Compound Components

Several components that work together, sharing implicit state through context, exposed as one cohesive API.

```jsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">Profile</Tabs.Trigger>
    <Tabs.Trigger value="settings">Settings</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Panel value="profile"><Profile /></Tabs.Panel>
  <Tabs.Panel value="settings"><Settings /></Tabs.Panel>
</Tabs>
```

The user arranges the parts; the parts coordinate themselves.

## The problem it solves

The alternative is configuration, which grows without bound:

```jsx
<Tabs
  tabs={[
    { label: "Profile", content: <Profile />, icon: <Icon />, disabled: false, badge: 3 },
  ]}
  variant="pills"
  align="center"
  renderTab={(tab) => ...}
  tabClassName="..."
/>
```

Every new requirement adds a prop, and eventually a `renderTab` escape hatch that admits the API failed. The component ends up knowing about layout, badges, icons and ordering — none of which are its concern ([[16.3 - Components and Props]]).

Compound components move those decisions to the consumer, who already knows them.

## Implementation

```jsx
import { createContext, useContext, useId, useState } from "react";

const TabsContext = createContext(null);

function useTabsContext(component) {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error(`<${component}> must be used within <Tabs>`);
  return ctx;
}

export function Tabs({ defaultValue, value: controlled, onValueChange, children }) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = controlled !== undefined;
  const value = isControlled ? controlled : internal;
  const baseId = useId();

  const setValue = (next) => {
    if (!isControlled) setInternal(next);
    onValueChange?.(next);
  };

  const ctx = useMemo(() => ({ value, setValue, baseId }), [value, baseId]);

  return <TabsContext value={ctx}>{children}</TabsContext>;
}

function List({ children }) {
  return <div role="tablist">{children}</div>;
}

function Trigger({ value, children }) {
  const { value: active, setValue, baseId } = useTabsContext("Tabs.Trigger");
  const selected = active === value;

  return (
    <button
      role="tab"
      id={`${baseId}-trigger-${value}`}
      aria-selected={selected}
      aria-controls={`${baseId}-panel-${value}`}
      tabIndex={selected ? 0 : -1}
      onClick={() => setValue(value)}
    >
      {children}
    </button>
  );
}

function Panel({ value, children }) {
  const { value: active, baseId } = useTabsContext("Tabs.Panel");
  if (active !== value) return null;

  return (
    <div
      role="tabpanel"
      id={`${baseId}-panel-${value}`}
      aria-labelledby={`${baseId}-trigger-${value}`}
      tabIndex={0}
    >
      {children}
    </div>
  );
}

Tabs.List = List;
Tabs.Trigger = Trigger;
Tabs.Panel = Panel;
```

Points worth noting:

**The context guard** gives a useful error when a part is used outside its parent, rather than a cryptic null dereference.

**`useId`** generates hydration-safe ids for the ARIA relationships ([[17.12 - Lesser Known Hooks]]).

**Controlled and uncontrolled** are both supported via the `prop !== undefined` check — the standard dual-mode pattern ([[16.8 - Controlled vs Uncontrolled Components]]).

**The context value is memoized**, or every part re-renders on every `Tabs` render ([[17.9 - useContext]]).

## Why context, not cloneElement

The older approach used `React.Children.map` with `cloneElement` to inject props:

```jsx
// Legacy — breaks the moment anything is nested
React.Children.map(children, child =>
  cloneElement(child, { active, setActive })
);
```

It only works for **direct** children. Wrap a trigger in a `<div>` for styling and it stops receiving props. Context has no such constraint — parts can be nested arbitrarily deep, wrapped in other components, or conditionally rendered.

`cloneElement` is effectively deprecated for this purpose.

## Composition with the `asChild` pattern

Radix popularized a way to merge a component's behavior onto a caller-supplied element:

```jsx
<Tabs.Trigger asChild>
  <Link to="/profile">Profile</Link>
</Tabs.Trigger>
```

The trigger's props and ref merge onto the `Link` instead of rendering its own `<button>`. This solves the "I need your behavior but my element" problem without adding an `as` prop with awkward typing.

Implementation uses `cloneElement` on a single child — one of its few remaining legitimate uses.

## Where it fits

Any component with **multiple parts and shared state**:

- Tabs, accordions, disclosure
- Select, combobox, listbox
- Dialog with header, body, footer
- Menu with items, groups, separators
- Table with header, body, sortable columns
- Form field with label, input, hint, error

The test: does the component have parts the consumer needs to arrange, order or style independently? If yes, compound. If it renders one thing, plain props are simpler.

## Cost

**More components to learn.** Six exports instead of one prop-driven component.

**Nothing enforces correct structure at compile time.** A `Tabs.Panel` outside `Tabs` fails at runtime, not in the type checker. The context guard makes the failure clear, which is the best available mitigation.

**More boilerplate for the author.** Justified for a design system used across an application; overkill for a one-off component.

**Context re-renders.** All parts re-render when the shared value changes. Fine for a tab set; worth splitting contexts for something with many parts and frequent updates.

## The headless alternative

Rather than building these, headless libraries provide the behavior and leave the styling entirely to you:

- **Radix UI** — compound components with full ARIA and keyboard support
- **React Aria** — hooks-based, from Adobe, with the most rigorous accessibility work
- **Headless UI** — from the Tailwind team
- **Base UI** — from the MUI team

The keyboard interaction alone is substantial — arrow-key navigation, roving tabindex, typeahead, focus management, and the correct ARIA relationships are all specified in detail by the APG ([[09.5 - Accessibility Fundamentals]]).

Building a combobox correctly is roughly a week of work. Use a library and spend the time on the product.

Compound components remain worth understanding because that is the API shape these libraries expose, and because domain-specific components in your own codebase benefit from the pattern.

## How senior engineers actually use this

**They use compound components for anything with arrangeable parts** in a design system.

**They use a headless library for complex widgets** rather than reimplementing APG patterns.

**They add a context guard** so misuse produces a clear error.

**They support both controlled and uncontrolled modes** via the `undefined` check.

**They memoize the context value** without thinking about it.

## Common pitfalls

- `cloneElement` instead of context, breaking on any nesting.
- Unmemoized context value, re-rendering every part.
- No guard, so misuse produces a null dereference.
- Missing ARIA relationships and keyboard handling.
- Hardcoded ids instead of `useId`, breaking with multiple instances and SSR.
- Reaching for the pattern on a single-element component.

## Interview angle

"How would you design a Tabs component API" is a common design question. Compare configuration (a `tabs` array prop) against composition (compound components), and explain the failure mode of the first — every variation adds a prop until a render-prop escape hatch appears. Then describe context as the coordination mechanism and why `cloneElement` is inadequate (direct children only). Mentioning dual controlled/uncontrolled support and the ARIA requirements shows you have built these rather than only used them.
