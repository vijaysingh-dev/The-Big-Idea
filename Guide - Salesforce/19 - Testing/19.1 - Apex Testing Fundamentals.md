# Apex Testing Fundamentals

## The two reasons tests exist

**The platform requires them.** 75% org-wide coverage and every trigger covered, or the deployment is rejected.

**They catch defects.** Which is the actual point, and which the coverage requirement does not measure.

Confusing these produces the most common failure in Salesforce codebases: tests that execute code, assert nothing, and pass forever regardless of behaviour.

## The mechanics

```java
@IsTest
private class ClaimApprovalServiceTest {

    @IsTest
    static void approvalSetsTheStatusAndAmount() {
        Warranty_Claim__c claim = TestDataFactory.createClaim(150000);

        Test.startTest();
        ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 120000);
        Test.stopTest();

        Warranty_Claim__c refreshed = [
            SELECT Status__c, Approved_Amount__c
            FROM Warranty_Claim__c WHERE Id = :claim.Id
        ];
        Assert.areEqual('Approved', refreshed.Status__c);
        Assert.areEqual(120000, refreshed.Approved_Amount__c);
    }
}
```

**`@IsTest` on the class**, and on each method. Test classes are `private` by convention — they are not part of the API and marking them public serves nothing.

**Test code does not count toward org coverage**, and it does count toward the org's code size limit.

## Test data isolation

**Tests see no org data.** No accounts, no custom settings, no configuration records. Everything a test needs, it creates.

```java
@IsTest
static void tierIsDerivedFromTheAmount() {
    // this returns nothing — the org's records are invisible
    List<Account> existing = [SELECT Id FROM Account];
    Assert.isTrue(existing.isEmpty());
}
```

**The exceptions, which are visible:**

```
Custom Metadata records          deployed records ARE visible
Custom Settings                  data is NOT visible
User, Profile, Role              visible
Organization, RecordType         visible
Static resources                 visible
Labels, page layouts             visible
```

**Custom Metadata visible, Custom Settings not** is the pairing that catches people. A test relying on a hierarchy setting must create it; a test using an approval tier metadata record does not. See [[17.1 - Custom Metadata Types]] and [[17.2 - Custom Settings]].

## SeeAllData

```java
@IsTest(SeeAllData=true)
static void thisTestDependsOnOrgData() { }
```

**Avoid it.** A test using it depends on data that differs between sandboxes, changes when someone edits a record, and behaves differently in a scratch org.

The narrow cases where it is genuinely unavoidable: objects that cannot be created in a test, such as some pricebook scenarios, `ContentWorkspace`, and certain standard configuration.

For pricebooks specifically, use the built-in instead:

```java
Id standardPricebookId = Test.getStandardPricebookId();
```

That method exists precisely so pricing tests do not need `SeeAllData`. See [[04.10 - Products, Price Books and Pricing]].

## Test.startTest and Test.stopTest

Two things, and both matter.

**They reset governor limits**, so the measured consumption is the code under test rather than the setup.

```java
@IsTest
static void handlerStaysWithinQueryLimits() {
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(200);   // setup, not measured

    Test.startTest();
    insert claims;
    // the assertion measures only what happened between start and stop
    Assert.isTrue(Limits.getQueries() < 30, 'Queries: ' + Limits.getQueries());
    Test.stopTest();
}
```

**`Test.stopTest()` forces queued async work to execute** — Queueables, future methods, and batch jobs run synchronously at that point.

```java
Test.startTest();
ClaimSubmissionService.submit(claim);   // enqueues a Queueable
Test.stopTest();                        // the Queueable runs here

// assertions go AFTER stopTest, or the job has not run
Warranty_Claim__c refreshed = [SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id];
Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c);
```

**Asserting before `stopTest` is the most common async testing mistake.** See [[19.4 - Test.startTest and Test.stopTest]].

**One pair per test method.** They cannot be nested or repeated.

## @TestSetup

Runs once per class, and the resulting data is rolled back and restored between methods.

```java
@IsTest
private class ClaimApprovalServiceTest {

    @TestSetup
    static void setup() {
        // created once, restored fresh for every test method in the class
        Account account = TestDataFactory.createAccount();
        List<Asset> assets = TestDataFactory.createAssets(account.Id, 5);
        TestDataFactory.createCoverage(assets);
    }

    @IsTest
    static void approvalRequiresActiveCoverage() {
        Asset asset = [SELECT Id FROM Asset LIMIT 1];
    }
}
```

**It is faster** — creating data once rather than per method matters on a class with fifteen tests.

**The data is restored, not shared.** Changes one method makes are rolled back before the next runs, so tests remain independent.

**One `@TestSetup` method per class**, and it cannot be used with `SeeAllData=true`.

The caveat: **records created in `@TestSetup` must be re-queried in the test method**, since the setup method's variables are out of scope. See [[19.3 - TestSetup and Test Data Factories]].

## Assert, not System.assert

```java
// Current
Assert.areEqual(expected, actual, 'A message explaining what should have happened');
Assert.areNotEqual(unexpected, actual, message);
Assert.isTrue(condition, message);
Assert.isFalse(condition, message);
Assert.isNull(value, message);
Assert.isNotNull(value, message);
Assert.isInstanceOfType(value, Type.class, message);
Assert.fail(message);
```

`System.assertEquals` and friends still work and are superseded. The `Assert` class has better failure messages and a clearer API.

**Always supply the message.** A failure reading `Assertion Failed: Expected: Approved, Actual: Submitted` is less useful than one reading `A claim within its coverage limit should be approved`, particularly when it fails in CI six months later.

## Testing exceptions

```java
@IsTest
static void approvalRejectsClaimsOverTheCoverageLimit() {
    Warranty_Claim__c claim = TestDataFactory.createClaim(900000);

    Test.startTest();
    try {
        ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 900000);
        // this line must not be reached
        Assert.fail('An over-limit claim should have thrown');
    } catch (ClaimValidationException e) {
        Assert.isTrue(e.getMessage().contains('coverage limit'),
            'The message should explain the coverage limit: ' + e.getMessage());
    }
    Test.stopTest();
}
```

**`Assert.fail()` after the call** is what makes this a real test. Without it, a method that silently stops throwing passes.

**Catch the specific exception type**, not `Exception`. Catching broadly means a `NullPointerException` from a bug would satisfy the test.

For DML errors, `Database.insert(records, false)` and asserting on the result is cleaner than a try/catch:

```java
Database.SaveResult result = Database.insert(claim, false);

Assert.isFalse(result.isSuccess());
Assert.areEqual(StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION,
    result.getErrors()[0].getStatusCode());
```

## Running tests

```bash
sf apex run test --tests ClaimApprovalServiceTest --result-format human --wait 10
sf apex run test --class-names ClaimApprovalServiceTest,ClaimSelectorTest --wait 10
sf apex run test --test-level RunLocalTests --code-coverage --wait 30
```

**Test levels:**

```
NoTestRun               no tests — sandbox only
RunSpecifiedTests       named classes
RunLocalTests           all tests except managed packages — the production default
RunAllTestsInOrg        including managed package tests
```

**Production deployments run `RunLocalTests` by default**, which means every test in the org runs on every release. A slow suite is a slow release, and that is the practical pressure toward fast tests.

## What makes a test valuable

Four properties, in rough order of importance.

**It asserts something.** A test with no assertions is coverage, not a test.

**It fails when the behaviour breaks.** The check worth running: comment out a line of the code under test — does the test fail? If not, it is testing nothing.

**It is fast.** A test that inserts fifty records and fires four triggers is slow, and a slow suite is one people stop running.

**It is deterministic.** No dependence on the current date, on org data, on record order, or on another test having run.

The date one is worth a note: a test using `Date.today()` in an assertion will fail at a month boundary or in a different time zone. Injecting the clock removes the whole class of problem. See [[18.8 - Dependency Injection and Testability]].

## The shape of a healthy suite

```
Service tests, no DML          the majority — milliseconds each
Selector tests, real data      verifying queries
Domain tests, constructed      pure functions over records
Handler tests, real DML        the wiring and bulk behaviour — the slow ones
```

**Most tests should be service and domain tests with constructed records**, which is only achievable when services take collections and do not read `Trigger`. That architectural constraint is what makes the test suite fast. See [[18.2 - Layered Architecture on the Platform]].

```java
@IsTest
static void alreadyApprovedClaimsAreNotTreatedAsNewApprovals() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

    // no DML, no queries, no triggers — milliseconds
    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };
    Map<Id, Warranty_Claim__c> prior = new Map<Id, Warranty_Claim__c>{
        claimId => new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };

    Test.startTest();
    List<Warranty_Claim__c> result = ClaimService.findNewlyApproved(claims, prior);
    Test.stopTest();

    Assert.isTrue(result.isEmpty(), 'An already-approved claim is not a new approval');
}
```

## Naming

The test name should describe the behaviour, so a failure report is readable without opening the file.

```java
// Says nothing
static void testApprove()
static void test1()
static void testApproveNegative()

// Says what should happen
static void approvalSetsStatusAndAmount()
static void claimsOverCoverageLimitAreRejected()
static void reparentedClaimsRecalculateBothAssets()
static void bypassPreventsAllHandlerWork()
```

A CI report listing twelve failures named `claimsOverCoverageLimitAreRejected` tells you what broke; one listing `testApprove3` does not.

## Organizing test classes

**One test class per production class** is the default, named `ClassNameTest`.

```
ClaimApprovalService      →  ClaimApprovalServiceTest
ClaimSelector             →  ClaimSelectorTest
WarrantyClaimTrigger      →  WarrantyClaimTriggerHandlerTest
```

**Test utilities are separate**, marked `@IsTest` so they do not count toward the org's code size:

```java
@IsTest
public class TestDataFactory { }

@IsTest
public class TestIdFactory { }

@IsTest
public class TestUserFactory { }
```

Marking a utility `@IsTest` also means it can only be called from test context, which prevents it leaking into production code.

## What not to test

**Salesforce's own behaviour.** A test asserting that `insert` inserts is testing the platform.

**Getters and setters** with no logic.

**Base component rendering.**

**Every branch of a trivial method**, when the branches are one line each and obviously correct.

Coverage pressure produces tests for all of these, and they add execution time without adding confidence. **Coverage is a floor, not a target.** See [[19.10 - Code Coverage, Quality and CI Gates]].

## Practical guidance

**Assert something, and supply a message.**

**Use `Assert`**, not `System.assert`.

**Create all data in the test** — no `SeeAllData`.

**Use `@TestSetup`** for shared data, and re-query in the method.

**Put assertions after `Test.stopTest()`** when async is involved.

**Use `Assert.fail()`** after a call that should throw.

**Catch the specific exception type.**

**Name tests after the behaviour**, not the method.

**Write most tests against services with constructed records.**

**Check that the test fails** when the code is broken.
