# Data Skew

## What skew is

**Data skew** is an uneven distribution where one record has a very large number of related records or one user owns a very large number of records.

The rough threshold is **10,000 child records under a single parent**, or 10,000 records owned by a single user. Below that it is normal; above it, platform operations that are ordinarily cheap become expensive, and eventually they fail.

Three kinds, each with a different failure mode.

## Ownership skew

One user owns a very large number of records.

The usual causes are entirely accidental: an integration user owning everything it created, a "House Accounts" placeholder holding unassigned records, or a departed employee's records never reassigned.

**Why it hurts:** record ownership drives sharing. When ownership changes, or when the owner's role moves in the hierarchy, the platform recalculates sharing for every record that user owns. With 400,000 records, that recalculation runs for hours and locks contended rows throughout.

It also makes the role hierarchy expensive — every role above that user inherits access to all of those records, and every hierarchy change recalculates them.

**Detection:**

```sql
SELECT OwnerId, Owner.Name, COUNT(Id) recordCount
FROM Account
GROUP BY OwnerId, Owner.Name
ORDER BY COUNT(Id) DESC
LIMIT 20
```

**Mitigations:**

**Distribute ownership** across several placeholder users rather than one.

**Place bulk-owning users in a role with no subordinates and no parent**, or with no role at all. A user with no role does not participate in hierarchy sharing, so their records generate no hierarchy share rows — which is the single most effective fix.

**Reassign departed users' records promptly**, in batches, during a quiet period.

## Account data skew

One Account with a very large number of child records — contacts, opportunities, cases, assets.

The classic case is a catch-all account: "Unknown Customer", "Web Leads", or a consumer business modelling every individual as a contact under one corporate account.

**Why it hurts:** every operation on a child record locks the parent account, so its roll-ups and implicit sharing can update. With hundreds of thousands of children, concurrent operations on any of them contend on that one row, producing `UNABLE_TO_LOCK_ROW` under load. See [[10.8 - Record Locking and Deadlocks]].

Changing the account's owner recalculates sharing for every child, which on a skewed account is a very long-running operation.

**Detection:**

```sql
SELECT AccountId, Account.Name, COUNT(Id) contactCount
FROM Contact
GROUP BY AccountId, Account.Name
ORDER BY COUNT(Id) DESC
LIMIT 20
```

Run the same for Case, Opportunity, and Asset.

**Mitigations:**

**Split the catch-all** into several — by region, by year, by source. Ten accounts of 50,000 children each contend far less than one of 500,000.

**Reconsider the model.** A consumer business with individuals under one account is usually a Person Accounts question rather than a skew question. See [[04.5 - Accounts - Business vs Person Accounts]].

**Do not use a placeholder account** where the lookup could be left blank, if the business process allows it.

## Lookup skew

A very large number of records pointing at the same record through a **lookup** field, rather than a master-detail.

The usual cause is a default value: a `Region__c` lookup defaulting to "Unassigned", or a `Product_Family__c` lookup where one value dominates.

**Why it hurts:** the platform locks the lookup target when a record referencing it is inserted or updated. A default value used by 90% of records means every insert contends on that one row.

Lookup skew is the least visible of the three, because nothing in the object structure suggests a problem — the field is a lookup precisely because the relationship is loose.

**Detection:**

```sql
SELECT Region__c, COUNT(Id) claimCount
FROM Warranty_Claim__c
GROUP BY Region__c
ORDER BY COUNT(Id) DESC
LIMIT 20
```

**Mitigations:**

**Avoid a default lookup value** on a high-volume object. Leaving it null is cheaper than pointing everything at one record.

**Spread defaults** across several records if a default is genuinely required.

**Use a picklist instead of a lookup** where the value is a category rather than a real relationship. A picklist has no target record and therefore no lock contention — and this is frequently the right answer, since many lookups exist only to constrain values.

That last point is worth emphasizing. A lookup to a `Region__c` object with eight records, used to constrain a value, is a picklist with extra steps and extra contention.

## The symptoms

Skew rarely announces itself. What you actually see:

- Intermittent `UNABLE_TO_LOCK_ROW` during data loads, clustered around certain records
- A sharing recalculation job running for hours after a role change
- An ownership transfer timing out
- Queries against the skewed parent's children performing badly
- A batch job failing on some chunks and not others

The diagnostic question from [[10.8 - Record Locking and Deadlocks]] applies: **what do the failing records have in common?** With skew, the answer is a shared parent or a shared owner.

## Designing to avoid it

Skew is cheap to prevent and expensive to fix, because fixing it means moving hundreds of thousands of records.

**Estimate the distribution, not just the volume.** "Two million claims" is fine. "Two million claims, 60% under one account" is not. Asking about distribution during data modelling is the whole preventive measure. See [[02.12 - Schema Builder and Data Modelling Practice]].

**Be suspicious of catch-all records.** Any record named "Unknown", "Default", "Unassigned", or "Various" is a skew candidate.

**Prefer picklists to lookups** for categorization.

**Do not default lookup fields** on high-volume objects.

**Keep integration users out of the role hierarchy**, or give them no role, so their owned records generate no hierarchy shares.

**Monitor the distribution periodically.** Skew develops gradually and is much easier to correct at 20,000 children than at 400,000.

## Fixing existing skew

Remediation is a project, and the sequence matters.

**1. Measure.** Run the aggregate queries above and quantify the problem before doing anything.

**2. Design the target distribution.** How many parents, split by what.

**3. Create the new parents.**

**4. Reassign in batches**, with a small scope size, during a quiet period. Reassignment triggers sharing recalculation on every record moved, so this is the expensive step.

```java
public with sharing class SkewRemediationBatch implements Database.Batchable<SObject> {

    private final Id sourceAccountId;
    private final List<Id> targetAccountIds;

    public SkewRemediationBatch(Id sourceAccountId, List<Id> targetAccountIds) {
        this.sourceAccountId = sourceAccountId;
        this.targetAccountIds = targetAccountIds;
    }

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, AccountId, Region__c FROM Contact WHERE AccountId = :sourceAccountId
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Contact> scope) {
        for (Integer i = 0; i < scope.size(); i++) {
            // distributing round-robin keeps the new parents evenly loaded
            scope[i].AccountId = targetAccountIds[Math.mod(i, targetAccountIds.size())];
        }
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

A small scope size — 50 or 100 rather than the default 200 — reduces lock duration per chunk, which matters when the source parent is exactly the contended record.

**5. Enable deferred sharing calculation** around the whole exercise, so recalculation runs once at the end rather than continuously. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

**6. Verify** with the same aggregate queries.

## Section 10 in one paragraph

DML is a whole save pipeline per record, not one operation, and it counts against 150 statements and 10,000 records per transaction. The statement form is all-or-none; `Database.method(records, false)` reports per record and is the right default for anything bulk, with results index-aligned to the input. External IDs give an index and make upsert idempotent, which is what lets an integration retry safely, and they let a lookup be set by the parent's external key with no ID mapping. Savepoints roll back data but not limits, and a rollback does not clear the Id on an in-memory record. Setup objects and normal objects cannot share a transaction, so user and permission DML goes async or into a `runAs` block. And most production DML failures are contention rather than logic: locking on master-detail parents, made much worse by skew, and fixed by sorting on the parent, reducing roll-ups, and distributing ownership.
