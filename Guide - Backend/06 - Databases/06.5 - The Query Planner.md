# The Query Planner

#backend #databases #postgres #performance

> **In one line:** The planner enumerates ways to run your query, estimates the cost of each using statistics, and picks the cheapest — so when it picks badly, the fix is almost always the statistics, not the query.

---

## The Idea

For a five-table join the search space runs to thousands of plans. The planner:

1. **Enumerates** candidate plans
2. **Estimates** how many rows each step produces, using statistics
3. **Costs** each plan with a formula
4. **Picks** the cheapest

💡 **The critical dependency: cost estimates are built on row-count estimates, and row-count estimates come from statistics.** If the statistics say 100 rows and the truth is 800,000, every downstream decision is wrong.

⚠️ **Bad plans are almost always an estimation failure, not a planning failure.**

---

## Statistics

```sql
SELECT attname, null_frac, n_distinct, most_common_vals, most_common_freqs, correlation
FROM pg_stats WHERE tablename = 'documents';
```

| Statistic | Used for |
|---|---|
| `null_frac` | Fraction of NULLs |
| `n_distinct` | Distinct values (negative = a ratio of table size) |
| **`most_common_vals` / `_freqs`** | The MCV list — exact frequencies for common values |
| `histogram_bounds` | Distribution of everything else |
| `correlation` | How well physical order matches logical order |

### How selectivity is computed

If the value is in the MCV list, use its recorded frequency — **exact**. If not:

```
selectivity = (1 - sum(mcv_freqs) - null_frac) / (n_distinct - len(mcv))
```

⚠️ **This is why skewed data with many distinct values estimates badly.** With 10,000 distinct statuses where the top 100 cover 99% of rows, anything outside the MCV list is assumed to be `1% / 9,900` of the table — off by orders of magnitude for the more common of the rare values.

```sql
ALTER TABLE documents ALTER COLUMN status SET STATISTICS 1000;
ANALYZE documents;
```

**This raises the MCV list and histogram size for that column, sampling 300,000 rows instead of 30,000.** Do it for skewed columns appearing in `WHERE` clauses.

### `correlation`

```
correlation = 1.0    physical order matches logical order exactly
correlation = 0.0    no relationship
```

💡 **High correlation makes index scans much cheaper**, because heap fetches are nearly sequential rather than random. **This is why a `created_at` index on an append-only table performs far better than the same index on a randomly-updated table**, and it is what makes BRIN viable ([[06.3 - Indexes Deep Dive]]).

## The Cost Model

```ini
seq_page_cost = 1.0            # reading a page sequentially — the unit
random_page_cost = 4.0         # reading a page randomly
cpu_tuple_cost = 0.01
cpu_index_tuple_cost = 0.005
cpu_operator_cost = 0.0025
```

Costs are in arbitrary units where `seq_page_cost = 1.0`. **Only the ratios matter.**

⚠️ **`random_page_cost = 4.0` is the most consequential wrong default in Postgres.** It encodes the assumption that a random read costs four times a sequential one — true for spinning disks, false for SSDs where the ratio is closer to 1.1.

```ini
random_page_cost = 1.1         # SSD / NVMe
random_page_cost = 1.5         # cloud network storage
```

💡 **Leaving it at 4.0 systematically biases the planner away from index scans**, because index scans do random heap fetches. **On a modern deployment this one line changes plans across your whole application.**

### Working an example

```
Seq Scan (1,000,000 rows, 12,000 pages)
  = 12,000 × 1.0 + 1,000,000 × 0.01 = 22,000

Index Scan (returning 5,000 rows)
  ≈ 25 + 25 + 5,000 × random_page_cost
  ≈ 20,050  at rpc=4.0        ← sequential scan may win
  ≈  5,550  at rpc=1.1        ← index scan wins decisively
```

⚠️ **A sequential scan is genuinely faster when returning a large fraction of the table** — roughly above 5–20% of rows. **The planner is usually right about this**, and "why isn't it using my index" often has the answer "because your index would be slower".

## Join Planning

```ini
join_collapse_limit = 8
geqo_threshold = 12          # above this, use a genetic algorithm
```

⚠️ **Above 12 tables, Postgres switches to a randomised genetic search.** Plans become non-deterministic — the same query can get different plans on different runs. **If you have queries joining 12+ tables and see inconsistent performance, this is why.**

💡 **Planning time itself becomes a cost with many joins.** If `Planning Time` exceeds `Execution Time`, consider lowering `join_collapse_limit` to force your written join order.

⚠️ **Nested loop is chosen based on the estimated outer row count.** If that estimate is 100 and the reality is 800,000, you get the disaster plan from [[06.4 - Reading EXPLAIN ANALYZE]]. **The fix is never `SET enable_nestloop = off`. It is fixing the estimate.**

## When the Planner Gets It Wrong

### The diagnostic order

```
1. Are statistics fresh?              → ANALYZE
2. Is a single-column estimate bad?   → SET STATISTICS higher
3. Are two columns correlated?        → CREATE STATISTICS
4. Is random_page_cost wrong?         → set it for your hardware
5. Is the query shape unplannable?    → rewrite it
6. Is it a generic plan flip?         → plan_cache_mode
7. Only now: planner hints            → and there aren't any
```

⚠️ **Postgres deliberately has no query hints.** The `enable_*` settings exist for debugging, not production.

💡 **Use them to *diagnose*, not to fix.** Turning off sequential scans to see whether the index plan is genuinely faster tells you whether the cost model or the estimates are at fault. **Then fix that.**

### Extended statistics, in detail

```sql
CREATE STATISTICS doc_stats (dependencies, ndistinct, mcv)
ON org_id, source_id, status FROM documents;
ANALYZE documents;
```

| Kind | Fixes |
|---|---|
| `dependencies` | `WHERE a = x AND b = y` where `b` is determined by `a` |
| `ndistinct` | `GROUP BY a, b` where the combination has far fewer distinct values |
| `mcv` | Common *combinations* of values |

💡 **Extended statistics are the single most effective fix for bad plans that survive `ANALYZE`**, and almost nobody uses them. **If you have a query where the estimate is wrong by 100× and the statistics are fresh, this is the answer roughly half the time.**

### Rewriting for the planner

```sql
-- OR across different columns: often a poor plan
WHERE org_id = 7 OR author_id = 42

-- Usually much better
SELECT * FROM documents WHERE org_id = 7
UNION
SELECT * FROM documents WHERE author_id = 42;
```

```sql
WHERE id NOT IN (SELECT doc_id FROM archived)        -- cannot use anti-join
WHERE NOT EXISTS (SELECT 1 FROM archived a WHERE a.doc_id = documents.id)   -- proper anti-join
```

⚠️ **`NOT IN` with a NULL in the subquery returns no rows at all** — SQL's three-valued logic. **This is a correctness bug as well as a performance one, and `NOT EXISTS` fixes both.**

### CTEs are no longer optimisation fences

⚠️ **Before Postgres 12, a CTE was always materialised.** From 12 onwards, single-use CTEs are inlined and predicates are pushed down.

```sql
WITH recent AS MATERIALIZED (...)      -- force the old behaviour
WITH recent AS NOT MATERIALIZED (...)  -- force inlining
```

💡 **`MATERIALIZED` is occasionally exactly what you want**: an expensive CTE referenced three times should be computed once.

## In Production

### Generic plan flips

After five executions, Postgres may switch to a **generic plan** ignoring the parameter value.

```
Custom plan:   org_id = 7  → 200 rows → index scan
Generic plan:  org_id = ?  → average selectivity → sequential scan
```

⚠️ **For skewed data this is a real production surprise.** A query fast for thousands of executions suddenly becomes slow, with no deployment and no data change — just the sixth execution.

```sql
SET plan_cache_mode = force_custom_plan;
```

💡 **For a multi-tenant application where one tenant has a million rows and another has ten, `force_custom_plan` is often correct.** The extra planning time is far cheaper than the wrong plan.

### Autovacuum keeps statistics fresh

⚠️ **`autovacuum_analyze_scale_factor = 0.1` on a 100-million-row table means 10 million changes before statistics update** — far too lax for skewed, fast-moving data.

```sql
ALTER TABLE documents SET (autovacuum_analyze_scale_factor = 0.02);
```

**After a bulk load, always `ANALYZE` explicitly.** The most common cause of a terrible plan immediately after a migration is statistics still describing an empty table.

### Monitoring for bad estimates

```sql
SELECT query, calls, mean_exec_time, stddev_exec_time
FROM pg_stat_statements
WHERE stddev_exec_time > mean_exec_time
ORDER BY calls * stddev_exec_time DESC;
```

💡 **High standard deviation relative to the mean is the signature of plan instability** — the same query getting different plans, or the same plan behaving differently on different parameter values. **A better early warning than mean latency, which averages the problem away.**

### The planner is usually right

⚠️ **Before concluding the planner is wrong, check whether it is.**

```sql
SET enable_seqscan = off;
EXPLAIN ANALYZE SELECT ...;
```

**If the forced index plan is genuinely slower, the planner was correct and your intuition was wrong.** This happens more often than people expect.

## Codebase

**Repo:** `postgres/postgres`

**Question to answer:** Trace how the planner estimates the selectivity of `WHERE status = 'indexed'`. Where does it consult the MCV list, and what does it do when the value is not in it? Then: where is the decision made between a nested loop and a hash join?

**Read, in order:**

1. `src/backend/optimizer/README` — **the planner's design by its authors.** The path/plan distinction, dynamic programming for join order, and the cost model. Read this first
2. `src/backend/utils/adt/selfuncs.c` — **`eqsel` and `var_eq_const`.** The MCV lookup and the fallback formula. **The answer to the first question**
3. `src/backend/optimizer/path/costsize.c` — `cost_seqscan`, `cost_index`, `cost_nestloop`, `cost_hashjoin`. **The formulas from this note, in code.** Note exactly where `random_page_cost` enters
4. `src/backend/optimizer/path/joinpath.c` — **`add_paths_to_joinrel`**, generating and comparing join methods. **The answer to the second question**
5. `src/backend/statistics/extended_stats.c` — how dependency and ndistinct statistics adjust selectivity
6. `src/backend/optimizer/plan/planner.c` — `standard_planner`, the top-level entry point

💡 `costsize.c` is unusually rewarding because **you can compute the numbers yourself and check them against `EXPLAIN` output.** Take a sequential scan, read the formula, plug in `relpages` and `reltuples` from `pg_class`, and confirm you get the same cost. **That exercise makes the cost model concrete rather than mystical.**

**Size:** 2–3 sessions.

## Exercise

**Drill 6.5 — Make the planner wrong, then right**

```
drills/06-planner/
├── data/{skewed.py, correlated.py}
├── statistics/{inspect.sql, selectivity.py, RESULTS.md}
├── cost_model/{verify.py, random_page_cost.sql, RESULTS.md}
├── breaking/{stale_stats.sql, correlated_cols.sql, skew.sql, generic_plan.py, FINDINGS.md}
├── fixing/{extended_stats.sql, statistics_target.sql, rewrites.sql, RESULTS.md}
└── README.md
```

**Part 1 — Compute a selectivity by hand.** Pick a skewed column and read its `pg_stats` row.

**Manually compute the expected row count** for: a value in the MCV list, a value not in it, and a range using the histogram.

Then run `EXPLAIN` and compare. **Match all three within a few percent.**

**If you cannot, you have misunderstood the formula — go back to `selfuncs.c`.** Getting this right is what turns estimates from magic into arithmetic.

**Part 2 — Verify the cost model.** For a sequential scan, read `relpages` and `reltuples` from `pg_class` and compute the cost by hand.

**Match the planner's number exactly.** Then do the same for an index scan and identify precisely where `random_page_cost` enters.

**Part 3 — `random_page_cost`, measured.** Find a query whose plan changes between 4.0 and 1.1.

Measure actual execution time under both plans. **Determine empirically which value is correct for your hardware**, by finding the ratio at which the planner's choice matches the faster plan.

**Part 4 — Break it four ways.** For each, produce a bad plan and quantify the damage:

| Break | Method |
|---|---|
| Stale statistics | Insert 5M rows without `ANALYZE` |
| Correlated columns | `WHERE country = ? AND currency = ?` |
| Skewed data outside the MCV | A value just below the MCV cutoff |
| **Generic plan flip** | A prepared statement, executed 6 times with a skewed parameter |

**The generic plan flip is the most instructive** — run the same prepared statement with the same parameter repeatedly and **watch execution six suddenly take 100× longer.**

**Part 5 — Fix each one.** For each, confirm the estimate improved *and* the plan changed *and* the runtime improved. **All three — fixing the estimate without changing the plan achieves nothing.**

**Part 6 — Query rewrites.** Capture both plans and measure for each pair: `OR` versus `UNION`, `NOT IN` versus `NOT EXISTS` (including the NULL correctness bug), a CTE with and without `MATERIALIZED`, and a correlated subquery versus `LATERAL`.

**Part 7 — Prove the planner right.** Find three queries where you believe an index should be used and it is not.

Force the index plan with `enable_seqscan = off` and measure. **Report how many times the planner was actually correct.**

**The honest answer is usually two or three out of three, and internalising that changes how you approach these investigations.**

**Done when:**
- You computed three selectivities by hand matching the planner
- You reproduced a cost calculation exactly
- You determined the correct `random_page_cost` for your hardware empirically
- All four breaks are reproduced with quantified damage
- Each fix demonstrably changed the estimate, the plan and the runtime
- You have a case where forcing your preferred plan made things worse
