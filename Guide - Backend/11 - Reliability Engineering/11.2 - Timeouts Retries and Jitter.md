# Timeouts, Retries and Jitter

#backend #reliability #patterns

> **In one line:** A missing timeout is not "no limit", it is whatever TCP decides — and a retry without jitter and a budget turns a dependency's bad minute into your outage.

---

## Timeouts

⚠️ **Every network call has a timeout. If you did not set one, the operating system did, and its value is minutes.**

```python
await httpx.get(url)                          # ⚠️ no timeout: can hang for minutes
await httpx.get(url, timeout=5.0)             # better
```

### The four timeouts that matter

```python
httpx.Timeout(
    connect=2.0,       # establish the TCP connection
    read=5.0,          # ⚠️ between bytes, not total
    write=5.0,
    pool=1.0,          # wait for a connection from the pool
)
```

💡 **`read` is per-read, not total.** A server dribbling one byte every four seconds keeps the connection open indefinitely without ever tripping a 5-second read timeout.

```python
async with asyncio.timeout(10.0):             # ← the total deadline
    response = await client.get(url)
```

⚠️ **You need both.** The granular timeouts catch a stalled connection; the overall deadline catches a slow-drip response ([[02.4 - Flow Control and Congestion Control]]).

**The `pool` timeout is the one people omit**, and it is what turns pool exhaustion from a fast error into a hang ([[01.10 - Connection Pools and Limits]]).

### Choosing a value

```
timeout = p99.9 of the healthy response time × a small factor
```

| Too short | Too long |
|---|---|
| Fails healthy slow requests | Holds a worker while a dependency is broken |
| Wasted work already done | Cascading failure ([[11.1 - How Systems Fail]]) |
| Retries amplify load | Users wait for something that will not succeed |

💡 **Measure, do not guess.** A dependency whose p99 is 200ms and p99.9 is 800ms should have a timeout around 1–2 seconds, not 30.

⚠️ **A 30-second default timeout is almost always wrong.** It is long enough to hold a worker through an entire outage and short enough to feel like you set one.

### Budget propagation

```
Client budget:     10s
Gateway:           uses 200ms, passes 9.8s
Service A:         uses 500ms, passes 9.3s
Service B:         must finish within 9.3s
```

```python
deadline = time.monotonic() + budget
headers["x-deadline-ms"] = str(int(budget * 1000))

remaining = deadline - time.monotonic()
if remaining <= 0:
    raise DeadlineExceeded()
async with asyncio.timeout(remaining):
    ...
```

💡 **Without propagation, service B works for 30 seconds on a request the client abandoned 20 seconds ago** ([[03.11 - Timeouts and Deadlines Across Hops]]). That is wasted capacity precisely when capacity is scarce.

**gRPC does this natively.** Over HTTP you pass a header, and every service must honour it.

⚠️ **Check the remaining budget before starting work, not just before the next call.** A service with 50ms left should reject immediately rather than begin a 2-second operation.

## Retries

### Retry only what can succeed

```python
RETRYABLE = (ConnectionError, TimeoutError, RateLimitError, ServiceUnavailable)
```

| Retry | Do not retry |
|---|---|
| Connection refused | 400, 422 — the input is wrong |
| Timeout | 401, 403 — permission will not change |
| 429 (honour `Retry-After`) | 404 — it is gone |
| 502, 503, 504 | 409 — a real conflict |
| | **Non-idempotent operations without a key** |

⚠️ **The last row is the one that causes damage.** Retrying a `POST /charges` without an idempotency key charges twice ([[07.5 - Idempotency Keys and Deduplication]]).

💡 **500 is genuinely ambiguous** — it might be transient or a deterministic bug. **Retry it once or twice**, and let repeated failures reach a dead letter queue where a human classifies it ([[08.6 - Retries Backoff and Dead Letters]]).

### Backoff with full jitter

```python
def delay(attempt: int, base: float = 0.1, cap: float = 10.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))
```

```
attempt 0:  0–0.1s
attempt 1:  0–0.2s
attempt 2:  0–0.4s
attempt 3:  0–0.8s
```

⚠️ **Without jitter, every client that failed at the same moment retries at the same moment.** A dependency that recovers is immediately knocked over by a synchronised wave.

💡 **Full jitter — uniform between 0 and the computed backoff — measurably outperforms both fixed backoff and half jitter**, and it recovers faster despite doing less work. AWS published the data.

| Strategy | Behaviour |
|---|---|
| Immediate | A hammering wall |
| Fixed delay | Synchronised waves |
| Exponential, no jitter | Synchronised waves, further apart |
| **Full jitter** | **Smooth. Fastest recovery** |

**The cap matters:** uncapped exponential backoff reaches hours, by which time the work is irrelevant.

### Retry budgets

```python
class RetryBudget:
    def __init__(self, ratio: float = 0.2, window: int = 60):
        self.ratio, self.window = ratio, window

    async def allow(self, service: str) -> bool:
        bucket = int(time.time()) // self.window
        retries = await redis.get(f"rb:{service}:{bucket}:r") or 0
        total = await redis.get(f"rb:{service}:{bucket}:t") or 1
        return int(retries) < self.ratio * int(total)
```

💡 **A budget bounds system-wide amplification in a way per-request limits cannot.** Three retries per request means a total dependency failure produces 3× load; a 20% budget means 1.2×.

⚠️ **This is the difference between a dependency having a bad minute and your system having an outage.** ([[11.1 - How Systems Fail]])

### Retry at exactly one layer

```
Client library retries 3×
Service retries 3×
Mesh retries 3×
→ 27 requests per logical call
```

⚠️ **Nested retries multiply**, and each layer is unaware of the others ([[10.7 - Service Discovery and Service Mesh]]).

💡 **Pick one layer and document it.** For background work it is the task; for synchronous calls it is the client library or the mesh, not both.

**Only the layer with domain knowledge can decide whether an operation is safe to retry**, which usually argues for the application.

## Hedged Requests

The technique for tail latency, and it is under-used.

```python
async def hedged(fn, hedge_after: float = 0.05):
    first = asyncio.create_task(fn())
    done, _ = await asyncio.wait({first}, timeout=hedge_after)
    if done:
        return first.result()

    second = asyncio.create_task(fn())          # send a duplicate
    done, pending = await asyncio.wait({first, second}, return_when=FIRST_COMPLETED)
    for t in pending:
        t.cancel()
    return done.pop().result()
```

💡 **Send a second request after the p95 latency, take whichever returns first.** A slow tail — a GC pause, a cold cache, an unlucky node — is bypassed rather than waited out.

⚠️ **Only for idempotent reads**, and it costs roughly 5% extra load for a large p99 improvement.

**Google's "The Tail at Scale" paper is where this comes from**, and the results are striking: p99 latency approaching p50 for a small constant overhead.

## In Production

### The call template

```python
async def call(service: str, method: str, path: str, *,
               required: bool = True, idempotent: bool = True, **kw):
    remaining = deadline_remaining()
    if remaining <= 0:
        raise DeadlineExceeded()

    if breaker.is_open(service):
        if required:
            raise DependencyUnavailable(service)
        return None

    attempts = MAX_ATTEMPTS if idempotent else 1
    for attempt in range(attempts):
        try:
            async with asyncio.timeout(min(remaining, PER_ATTEMPT_TIMEOUT)):
                r = await client.request(method, path, **kw)
            breaker.record_success(service)
            return r

        except RETRYABLE as e:
            breaker.record_failure(service)
            if attempt == attempts - 1 or not await budget.allow(service):
                break
            await asyncio.sleep(delay(attempt))

    if required:
        raise DependencyUnavailable(service)
    return None
```

💡 **Everything in this note is in that function**, and it is the thing to build once and use everywhere ([[10.7 - Service Discovery and Service Mesh]]).

⚠️ **`idempotent: bool` being an explicit parameter is the important part.** It forces the caller to decide, rather than defaulting to retrying something unsafe.

### The timeout budget table

```
Client-facing SLO:              1000 ms
  Gateway overhead:               50 ms
  Auth check:                    100 ms
  Primary service:               700 ms
    Database:                    200 ms
    Cache:                        20 ms
    Downstream service:          300 ms
      its database:              150 ms
  Serialisation and buffer:      150 ms
```

💡 **Write this down and assert it in tests.** Every timeout should be derived from this table, not chosen independently.

```python
def test_timeout_budget_is_consistent():
    assert DB_TIMEOUT + CACHE_TIMEOUT + DOWNSTREAM_TIMEOUT < SERVICE_TIMEOUT
    assert SERVICE_TIMEOUT + AUTH_TIMEOUT + GATEWAY_OVERHEAD < CLIENT_SLO
```

⚠️ **A downstream timeout longer than the caller's is always wrong**, and it happens constantly because each is set in isolation.

### Monitoring

```python
call_duration_seconds.labels(service=s, outcome=...).observe(elapsed)
call_timeouts_total.labels(service=s).inc()
call_retries_total.labels(service=s, attempt=n).inc()
retry_budget_exhausted_total.labels(service=s).inc()
deadline_exceeded_before_start_total.labels(service=s).inc()
```

💡 **`deadline_exceeded_before_start_total` tells you the budget is too tight somewhere upstream** — work is being abandoned before it begins, which means a timeout earlier in the chain is too generous.

⚠️ **Retry rate is a leading indicator that rises before the error rate** ([[08.6 - Retries Backoff and Dead Letters]]). Alert on it.

### The common mistakes

| Mistake | Consequence |
|---|---|
| No timeout | A worker held for minutes |
| One timeout value everywhere | Either too tight for slow calls or too loose for fast ones |
| Timeout longer than the caller's | Work continues after abandonment |
| Retrying non-idempotent operations | Duplicate effects |
| No jitter | Synchronised retry waves |
| Retries at multiple layers | Multiplicative amplification |
| No retry budget | 3× load during an outage |
| Retrying 4xx | Wasted capacity, delayed alerts |
| `read` timeout only | A slow-drip response hangs forever |

💡 **The first and the last are the two that produce hangs**, and hangs are worse than errors because they consume resources while producing nothing.

### Conduit's budgets

| Call | Connect | Per-attempt | Total | Retries |
|---|---|---|---|---|
| Gateway → auth | 200ms | 300ms | 500ms | 1, idempotent |
| Gateway → documents | 200ms | 800ms | 1s | 2, idempotent |
| Gateway → search | 200ms | 500ms | 600ms | **0** — optional, degrade |
| Documents → Postgres | 1s | 2s | 3s | 0 — the pool retries |
| Documents → Redis | 100ms | 200ms | 300ms | 1 |
| Ingestion → embedding API | 2s | 30s | 60s | **5**, long backoff |
| Webhook delivery | 3s | 10s | 10s | 8, over 3 days ([[05.12 - Webhooks and Callbacks]]) |

💡 **Note the variation.** A 300ms Redis timeout and a 30-second embedding timeout in the same system, because the expected latencies differ by two orders of magnitude.

⚠️ **Search has zero retries because it is optional** — a failed search degrades the page rather than retrying and consuming the budget that documents needs.

## Codebase

**Repo:** `encode/httpx`, `grpc/grpc`, `Netflix/concurrency-limits`

**Question to answer:** In httpx, what does each of the four timeouts actually measure, and where in the request lifecycle is each checked? Then: how does gRPC propagate a deadline, and what does a server do with it?

**Read, in order:**

1. `httpx/_config.py` — the `Timeout` class. **The four values and their defaults**
2. `httpx/_transports/default.py` and `httpcore` — **where each timeout is applied.** Note that `read` wraps a single socket read, not the whole response. **The answer to the first question**
3. `grpc/grpc/src/core/lib/surface/call.cc` — deadline handling. **The deadline is a wire-level concept**, sent as `grpc-timeout` and enforced on both sides
4. `grpc/grpc/src/python/grpcio/grpc/_channel.py` — how a Python client sets and propagates it. **The answer to the second question**
5. `Netflix/concurrency-limits` — **adaptive limits based on observed latency**, which is timeouts and load shedding unified. A more sophisticated alternative to fixed values

💡 The httpx reading corrects a misconception most people have: **`timeout=5` in a client library usually means five seconds between reads, not five seconds total.** Once you know that, the need for an outer `asyncio.timeout` is obvious rather than belt-and-braces.

**Part 4 — Amplification and budgets.** Three layers each retrying three times.

Then measure the cost: how many requests that would have succeeded on retry now fail because the budget was exhausted?
