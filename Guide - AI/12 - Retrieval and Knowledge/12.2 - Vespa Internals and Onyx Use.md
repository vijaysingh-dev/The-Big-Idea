# Vespa Internals and Onyx's Use of It

## What It Is

Vespa is an open-source distributed search and ranking engine built by Yahoo (now independent). Unlike most vector databases that added BM25 as an afterthought, or search engines that bolted on ANN — Vespa was designed from day one to do **both** in a single query, at production scale, with configurable ML-based ranking.

Onyx chose Vespa over Elasticsearch + Qdrant specifically because Vespa eliminates the dual-system fan-out problem: one query, one network round trip, hybrid results. This is a non-trivial architectural decision that's worth understanding deeply.

---

## Why It Matters

- **Onyx uses Vespa as its primary search backend** — if you're interviewing at companies with similar architectures or contributing to Onyx, you need to understand why specific query patterns look the way they do
- Vespa is used in production at Yahoo (News, Search), Spotify (music/podcast search), Bloomberg (financial search), Verizon Media — learning it signals serious search engineering knowledge
- The design patterns in Vespa (two-phase ranking, rank profiles, native embedding support) apply conceptually to any hybrid search system
- Interview signal: being able to explain *why* Onyx uses Vespa instead of Qdrant + Elasticsearch demonstrates genuine system design depth

## Vespa Architecture

### Core Components

```
Client
  │
  ▼
[Container Nodes]           ← Stateless. Handle: query parsing, ranking logic,
  │  (Java/JDisc)              document processing, ML model serving
  │
  ▼
[Content Nodes]             ← Stateful. Handle: document storage, inverted index (BM25),
     (proton)                  vector index (HNSW), attribute storage
```

**Container nodes** are horizontally scalable, stateless query processors. They:
- Parse YQL queries
- Execute ranking profiles (first phase, second phase)
- Run ONNX models for re-ranking
- Handle document ingestion preprocessing

**Content nodes** (the `proton` search core) are stateful and own the data:
- Inverted index for BM25 text search
- HNSW graph for ANN vector search
- Attribute store for fast metadata filtering
- Document store for raw document retrieval

### Data Distribution

Content nodes partition data using consistent hashing. Each document is placed on `redundancy` nodes (typically 2) for fault tolerance. Queries fan out to all content node groups and results are merged at the container.

```
10M documents, 4 content nodes, redundancy=2:
  Node 1: documents 0-2.5M (primary) + 7.5M-10M (replica)
  Node 2: documents 2.5M-5M (primary) + 0-2.5M (replica)
  Node 3: documents 5M-7.5M (primary) + 2.5M-5M (replica)
  Node 4: documents 7.5M-10M (primary) + 5M-7.5M (replica)
```

## Schema Definition

Everything in Vespa starts with the schema. This is the most important file to understand.

### Onyx's Actual Schema (simplified from source)

```
# backend/danswer/document_index/vespa/app_config/schemas/danswer_chunk.sd

schema danswer_chunk {
    document danswer_chunk {

        # ── Identity ──────────────────────────────────────────────
        field document_id type string {
            indexing: summary | attribute    # attribute = fast filtering
        }
        field chunk_id type int {
            indexing: summary | attribute
        }

        # ── Content (BM25 searchable) ──────────────────────────────
        field content type string {
            indexing: summary | index         # index = BM25 inverted index
            index: enable-bm25               # explicit BM25 activation
        }
        field title type string {
            indexing: summary | index
            index: enable-bm25
        }
        field content_summary type string {
            indexing: summary                 # summary only = retrievable, not searchable
        }

        # ── Vector (ANN searchable) ────────────────────────────────
        field embeddings type tensor<float>(x[1536]) {
            indexing: attribute | index      # attribute = stored, index = HNSW
            attribute {
                distance-metric: angular     # angular distance = cosine similarity
            }
            index {
                hnsw {
                    max-links-per-node: 16   # M parameter — connections per node
                    neighbors-to-explore-at-insert: 200  # ef_construction
                }
            }
        }

        # ── Access Control ─────────────────────────────────────────
        field access_control_list type weightedset<string> {
            indexing: summary | attribute
        }
        field tenant_id type string {
            indexing: summary | attribute
        }

        # ── Metadata ───────────────────────────────────────────────
        field source_type type string {
            indexing: summary | attribute
        }
        field document_sets type weightedset<string> {
            indexing: summary | attribute
        }
        field metadata_suffix type string {
            indexing: summary | index        # BM25 searchable metadata
        }
        field updated_at type int {
            indexing: summary | attribute    # for recency ranking/filtering
        }
        field boost type float {
            indexing: summary | attribute    # manual relevance boost per document
        }
    }

    # ── Rank Profiles ─────────────────────────────────────────────
    rank-profile default {
        # First phase: cheap, runs on all candidates
        first-phase {
            expression: nativeRank(content) + nativeRank(title) * 2.0
        }
    }

    rank-profile semantic_similarity {
        inputs {
            query(query_embedding) tensor<float>(x[1536])
        }
        first-phase {
            expression: closeness(field, embeddings)  # cosine similarity
        }
    }

    rank-profile hybrid {
        inputs {
            query(query_embedding) tensor<float>(x[1536])
        }
        first-phase {
            # Linear interpolation of BM25 and cosine similarity
            expression {
                0.5 * closeness(field, embeddings) +
                0.5 * (nativeRank(content) + nativeRank(title))
            }
        }
        # Second phase: more expensive re-ranking on top-N from first phase
        second-phase {
            rerank-count: 100     # re-rank top 100 from first phase
            expression {
                # Could call an ONNX cross-encoder model here
                # Or apply recency decay
                firstPhase * attribute(boost)
            }
        }
    }
}
```

### Key Schema Concepts

**`indexing` directives** control where and how data is stored:
- `attribute`: stored in memory, fast for filtering/sorting, not tokenized
- `index`: creates inverted index (BM25), tokenized
- `summary`: included in result payload returned to client

A field can have multiple directives: `attribute | index | summary` means it's filterable, BM25-searchable, and returned in results.

**`weightedset<string>`**: A map of string → weight. Used for access control lists and document sets. Enables efficient membership queries: "is user_id in this document's ACL?"

**`tensor<float>(x[1536])`**: Vespa's native tensor type. The HNSW index is built automatically on tensor fields with `index` directive.

## YQL — Vespa Query Language

YQL (Yahoo Query Language) is the SQL-like query language Vespa uses. Understanding it is essential for reading Onyx's search code.

### Basic Structure

```sql
select field1, field2 from schema_name
where [filter conditions]
order by [ranking]
limit N
```

### Hybrid Search Query (Core Onyx Pattern)

```python
# From backend/danswer/document_index/vespa/vespa_query.py

yql = """
select
    document_id, chunk_id, content, title, source_type,
    metadata_suffix, content_summary, updated_at, boost,
    matchfeatures
from danswer_chunk
where
    (
        {targetHits: 200}
        nearestNeighbor(embeddings, query_embedding)
    )
    or
    (
        userQuery()
    )
"""

# Query parameters sent alongside YQL
params = {
    "yql": yql,
    "query": user_query_text,          # for userQuery() BM25 component
    "input.query(query_embedding)": query_embedding_json,  # for ANN component
    "ranking": "hybrid",               # which rank profile to use
    "hits": 20,                        # how many results to return
    "timeout": "5s",
    "ranking.matchPhase.maxHits": 1000,  # first phase candidate set size
}
```

**`{targetHits: 200}`**: Hint to Vespa — retrieve at least 200 ANN candidates before ranking. More candidates = better recall, more compute. Vespa uses this to explore the HNSW graph sufficiently.

**`nearestNeighbor(field, query_input)`**: The ANN search operator. `field` is the tensor field in the schema; `query_input` is the name of the query tensor passed in params.

**`userQuery()`**: The BM25 component. The actual query text is passed as the `query` parameter. Vespa tokenizes and searches the `index`-directive fields.

**`or` between ANN and BM25**: Vespa's native hybrid — both retrieve candidates, results are merged before ranking. The rank profile's expression then scores all merged candidates.

### ACL Filtering in YQL

```python
# Add permission filter as a where clause condition
acl_filter = " or ".join([
    f'access_control_list contains "{user_id}"',
    f'access_control_list contains "group:{group_id}"',
    'access_control_list contains "PUBLIC"',
])

yql = f"""
select * from danswer_chunk
where
    (
        {{targetHits: 200}}nearestNeighbor(embeddings, query_embedding)
        or userQuery()
    )
    and ({acl_filter})
"""
```

The ACL check is pushed into the Vespa query itself — no post-filtering needed in application code. This is both faster and safer (no risk of accidentally returning unauthorized documents if the filter is forgotten).

### Date/Recency Filtering

```python
# Filter to documents updated in the last 6 months
import time
six_months_ago = int(time.time()) - (6 * 30 * 24 * 3600)

yql += f" and updated_at > {six_months_ago}"
```

## Two-Phase Ranking

Vespa's most powerful feature for production. Allows cheap first-pass scoring over many candidates followed by expensive scoring over a small set.

```
All matching documents (potentially millions)
    │
    ▼ First phase: cheap formula (BM25 + cosine)
    │              runs on ALL content nodes in parallel
    │
Top-N per node → merged → global top-N (e.g., top 1000)
    │
    ▼ Second phase: expensive scoring
    │              runs only on top-N
    │              can call ONNX model (cross-encoder)
    │
Final top-K returned to client
```

```
# In schema rank profile:
rank-profile production_hybrid {
    inputs {
        query(query_embedding) tensor<float>(x[1536])
    }

    # Phase 1: fast, runs on all candidates across all content nodes
    first-phase {
        expression {
            0.4 * closeness(field, embeddings) +
            0.4 * bm25(content) +
            0.2 * freshness(updated_at)
        }
    }

    # Phase 2: expensive, runs only on top rerank-count
    second-phase {
        rerank-count: 200
        expression {
            onnxModel(cross_encoder).logit *    # cross-encoder score
            attribute(boost)                     # manual boost
        }
    }
}
```

**Deploying an ONNX cross-encoder to Vespa** eliminates the separate reranking API call — Vespa scores with the cross-encoder inside the content node, co-located with the data.

## Vespa Feeding (Document Ingestion)

Onyx writes documents to Vespa via the document API:

```python
# backend/danswer/document_index/vespa/vespa_client.py pattern

import requests

VESPA_DOCUMENT_URL = "http://vespa:8080/document/v1"

def upsert_chunk(chunk: IndexChunk) -> None:
    doc_id = f"id:danswer:danswer_chunk::{chunk.chunk_id}"

    payload = {
        "fields": {
            "document_id": chunk.document_id,
            "chunk_id": chunk.chunk_id,
            "content": chunk.content,
            "title": chunk.title,
            "embeddings": {"values": chunk.embedding},  # list of floats
            "access_control_list": {
                user: 1 for user in chunk.permitted_users
            },
            "source_type": chunk.source_type,
            "updated_at": chunk.updated_at_unix,
            "boost": 1.0,
        }
    }

    response = requests.put(
        f"{VESPA_DOCUMENT_URL}/danswer/danswer_chunk/{doc_id}",
        json=payload,
        timeout=10,
    )
    response.raise_for_status()

def delete_chunks_by_document(document_id: str) -> None:
    # Delete all chunks for a document using selection
    requests.delete(
        f"{VESPA_DOCUMENT_URL}/danswer/danswer_chunk",
        params={"selection": f"danswer_chunk.document_id == \"{document_id}\""},
        timeout=30,
    )
```

**Batch feeding**: For high-throughput ingestion, use Vespa's feed client (Java library) or the HTTP feed endpoint with async POSTs. The single PUT pattern above works for moderate volumes; at 100K+ docs/hour use the feed API with connection pooling.

## Vespa Deployment (Docker / Kubernetes)

Onyx ships a `docker-compose.yml` that includes Vespa as a service:

```yaml
# From Onyx's docker-compose
vespa:
  image: vespaengine/vespa:8
  ports:
    - "8080:8080"   # Document + Query API
    - "19071:19071" # Config server
  volumes:
    - vespa_data:/opt/vespa/var
  environment:
    - VESPA_CONFIGSERVER_JVMARGS=-Xms512m -Xmx512m
```

**Application package**: The schema files, rank profiles, and ONNX models are packaged and deployed to Vespa's config server:

```bash
# Deploy application package
vespa deploy backend/danswer/document_index/vespa/app_config/
```

Every schema change requires a re-deploy. Index schema changes that affect indexed fields require re-feeding all documents (this is a breaking change — handle with shadow indexing in production).

## Performance Characteristics

| Operation | Typical latency | Notes |
|-----------|----------------|-------|
| Single document PUT | 5–20ms | Including HNSW graph update |
| Hybrid query (1M docs) | 30–80ms | ANN + BM25 + rank |
| Pure ANN query | 10–30ms | HNSW traversal only |
| Pure BM25 query | 5–20ms | Inverted index lookup |
| Second-phase ONNX | +50–200ms | Cross-encoder inference |
| Batch feed (10K docs) | ~10–30s | CPU bound on HNSW insert |

**HNSW insert cost**: Inserting into the HNSW graph is O(M × ef_construction) per document. At M=16 and ef_construction=200, this dominates write latency. For bulk ingestion, Vespa supports feeding without graph updates and then building the index batch-wise.

## Why Onyx Chose Vespa Over Alternatives

| Decision | Alternative | Why Vespa Won |
|----------|------------|---------------|
| Single search system | Qdrant + Elasticsearch | One query, one network hop, no score normalization needed |
| Native hybrid ranking | RRF in app code | Rank profiles express complex multi-signal ranking in schema, not application code |
| Built-in ONNX | Separate reranker service | Cross-encoder runs co-located with data; no extra round trip |
| Access control in query | Post-filter in app code | ACL filter pushed to Vespa = no code path that can accidentally skip it |
| Attribute-based filtering | Post-filter in app code | In-query filtering leverages HNSW graph pruning |

**The tradeoff Onyx accepted**: Vespa has significant operational complexity (schema language, YQL, application deployment, config server) vs simpler alternatives. This is appropriate for an enterprise product with dedicated infra — not for a 2-week prototype.

## Revision Anchors

- **Container vs Content nodes**: Container = stateless query processing + ranking logic. Content (proton) = stateful data storage + ANN + inverted index.
- **Schema indexing directives**: `attribute` = memory, fast filter. `index` = BM25 inverted index. `summary` = returned in results. Field can have multiple.
- **YQL hybrid pattern**: `nearestNeighbor(field, query_input) or userQuery()` — `or` merges both candidate sets, rank profile scores them together.
- **`targetHits`**: How many ANN candidates to explore in HNSW graph. Higher = better recall, more compute. Set to 5–10× your final `hits` count.
- **Two-phase ranking**: First phase (cheap, all candidates) → Second phase (ONNX cross-encoder, top-N only). Eliminates separate reranker service.
- **ACL in YQL not app code**: Push permission filter into the query. Never rely on application-layer post-filtering as the sole security control.
- **Why Onyx chose Vespa**: Single system for hybrid search eliminates dual-system fan-out + score normalization. Native ONNX support enables co-located reranking.
