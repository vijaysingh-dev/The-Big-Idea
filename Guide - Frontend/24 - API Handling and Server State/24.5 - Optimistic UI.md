# Optimistic UI

Update the interface immediately, assuming the server will agree, and reconcile when it responds.

```
Pessimistic:  click → spinner → 400ms → updated
Optimistic:   click → updated instantly → (reconcile silently)
```

The difference is not perceived speed alone — it is that the interface stops feeling like a form submission and starts feeling like direct manipulation.

## When it is appropriate

Three conditions, all required:

**High success probability.** A like, a checkbox toggle, a rename — these succeed >99% of the time. A payment does not.

**Cheap, obvious rollback.** The user can see what reverted and understand why.

**Low cost of being briefly wrong.** A like that un-likes itself is a minor annoyance. A "transfer complete" message that reverses is a serious problem.

Good candidates: toggles, likes, reordering, inline edits, adding an item to a list, marking as read, drag-and-drop.

Bad candidates: payments, irreversible deletes, anything with a server-computed result the client cannot predict (a generated id displayed to the user, a calculated total, an availability check).

## React 19: useOptimistic

```jsx
function MessageThread({ messages, sendMessage }) {
  const [optimisticMessages, addOptimistic] = useOptimistic(
    messages,
    (current, newMessage) => [...current, { ...newMessage, pending: true }]
  );

  async function action(formData) {
    const text = formData.get("text");
    addOptimistic({ id: crypto.randomUUID(), text });
    await sendMessage(text);
  }

  return (
    <>
      {optimisticMessages.map(m => (
        <div key={m.id} style={{ opacity: m.pending ? 0.5 : 1 }}>{m.text}</div>
      ))}
      <form action={action}>
        <input name="text" />
      </form>
    </>
  );
}
```

React discards the optimistic state automatically when the action settles and the real state arrives. There is no manual rollback, and no snapshot to restore.

Two requirements: it must be used inside an action or a transition, and the reducer must be pure ([[22.4 - useTransition and startTransition]]).

The `pending` flag is worth including — showing in-flight items at reduced opacity tells the user the operation has not completed without blocking them.

## The manual pattern

Without `useOptimistic`, the shape is snapshot → apply → rollback on failure:

```jsx
async function toggleLike(postId) {
  const previous = posts;                                    // 1. snapshot

  setPosts(ps => ps.map(p =>
    p.id === postId ? { ...p, liked: !p.liked } : p
  ));                                                        // 2. apply

  try {
    await api.toggleLike(postId);
  } catch (err) {
    setPosts(previous);                                      // 3. rollback
    toast.error("Could not update. Try again.");
  }
}
```

The rollback must restore the snapshot, not apply the inverse operation — if two toggles are in flight, inverting produces the wrong result.

## Concurrent operations

The hardest part of hand-rolled optimistic updates.

```
toggle A (optimistic) → toggle B (optimistic) → A fails
Rolling back to A's snapshot also undoes B.
```

Three approaches:

**Cancel in-flight requests** before starting a new one for the same entity ([[04.6 - AbortController and Cancellation]]).

**Track pending operations per entity** and reconcile against the current state rather than a snapshot:

```jsx
setPosts(ps => ps.map(p =>
  p.id === postId ? { ...p, liked: serverValue } : p
));
```

**Use a library that handles it.** TanStack Query's mutation cache tracks in-flight mutations and reconciles on settle ([[24.8 - Optimistic Updates with TanStack Query]]).

This is the main argument for not hand-rolling: the single-operation case is easy and the concurrent case is genuinely subtle.

## Temporary ids

New items need an id before the server assigns one:

```jsx
const tempId = `temp-${crypto.randomUUID()}`;

addOptimistic({ id: tempId, text, pending: true });

const created = await api.createTodo({ text });
// The refetch or cache update replaces the temp item with the real one
```

Two constraints. The temp id must be **unique and stable** for the item's lifetime, or React reconciliation attaches state to the wrong row ([[16.6 - Lists and Keys]]). And it must be **distinguishable** from a real id, so code that navigates or links does not use it — a `temp-` prefix makes that check trivial.

Never navigate to a detail route using a temporary id.

## Handling failure well

```jsx
catch (err) {
  rollback();

  toast.error("Could not save your change", {
    action: { label: "Retry", onClick: () => retry() },
  });
}
```

Three things a good failure does:

**Reverts visibly.** A silent revert leaves the user believing the change stuck.

**Explains what failed**, specifically enough to act on.

**Offers a retry**, since transient network failures are the most common cause and a retry usually works.

For an error the user cannot fix — a 403, a validation rejection — do not offer retry; explain the constraint instead ([[24.2 - Loading Error and Empty States]]).

## Router fetchers

React Router's `useFetcher` gives optimistic UI with no rollback code:

```jsx
function LikeButton({ postId, liked }) {
  const fetcher = useFetcher();

  const optimistic = fetcher.formData
    ? fetcher.formData.get("liked") === "true"
    : liked;

  return (
    <fetcher.Form method="post" action={`/posts/${postId}/like`}>
      <input type="hidden" name="liked" value={String(!optimistic)} />
      <button>{optimistic ? "Liked" : "Like"}</button>
    </fetcher.Form>
  );
}
```

Reading the submitted `formData` gives the pending value. If the action fails, `formData` clears and the value reverts automatically ([[23.6 - Data Loading with Loaders and Actions]]).

Each fetcher is independent, so many rows can be in flight without interfering — which solves the concurrency problem structurally.

## Offline queueing

Taken further, optimistic updates plus a durable queue give offline-capable apps:

```
action → apply locally → persist to IndexedDB → sync when online
```

The complications are real: conflict resolution when the server state diverged, ordering guarantees across queued operations, and reconciling temporary ids after sync. CRDTs or a sync engine (Replicache, Yjs, PowerSync) handle this properly ([[28.12 - Real Time and Offline First]]).

Worth knowing the shape; not worth hand-rolling beyond simple append-only cases.

## Accessibility

```jsx
<div aria-live="polite" className="sr-only">
  {isPending ? "Saving" : lastResult}
</div>
```

An optimistic update is visually instant but silent. Screen reader users need the eventual outcome announced — particularly the failure case, which must use `role="alert"` so it interrupts ([[09.5 - Accessibility Fundamentals]]).

## How senior engineers actually use this

**They apply it selectively** — toggles and inline edits yes, anything financial or irreversible no.

**They use `useOptimistic` or a mutation library** rather than hand-rolling snapshots, because the concurrent case is where hand-rolled versions break.

**They show pending state subtly** — reduced opacity, a small indicator — so the user knows the operation is not yet confirmed without being blocked.

**They make failures loud and actionable**, with a retry where retry can help.

**They prefix temporary ids** and guard against using them in navigation.

## Common pitfalls

- Optimistic updates on operations that frequently fail.
- Rolling back by inverting rather than restoring a snapshot.
- Concurrent updates where one rollback undoes another.
- Temporary ids leaking into URLs or requests.
- Silent rollback, leaving the user believing the change saved.
- No pending indicator, so failures appear as random reversions.
- Optimistically showing server-computed values the client cannot predict.

## Interview angle

"What is optimistic UI and when would you use it" wants the definition plus the three preconditions — high success rate, cheap rollback, low cost of being briefly wrong — with concrete examples on each side. The depth comes from the failure path: rollback must restore a snapshot rather than invert, concurrent mutations make naive rollback incorrect, and the revert must be visible with a retry. Mentioning `useOptimistic` and router fetchers as mechanisms that handle reconciliation automatically shows current knowledge.
