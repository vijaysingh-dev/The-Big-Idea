# Choosing a Realtime Transport

#backend #realtime #architecture

> **In one line:** Pick the simplest transport that matches your data direction — most "we need WebSockets" projects need Server-Sent Events, and most of the rest need neither.

---

## The Idea

"Realtime" covers a wide range of requirements that need completely different solutions:

| What you actually need | Right answer |
|---|---|
| Data that is a few seconds stale is fine | Polling |
| Server pushes updates, client only reads | **SSE** |
| Both directions, low latency, frequent | WebSocket |
| Both directions, typed contract, internal | gRPC streaming |
| Audio or video between peers | WebRTC |
| Notify a user who is not on your page | Push notifications |

💡 **The most common architectural mistake in this area is reaching for WebSockets by default.** WebSockets are a full-duplex protocol with their own handshake, their own framing, their own auth story, and their own scaling problems. If your data flows one way — progress updates, notifications, live dashboards, LLM tokens — SSE does the job over ordinary HTTP with a fraction of the operational cost.

---

## The Options

### Polling

```javascript
setInterval(() => fetch("/api/status").then(update), 5000);
```

| | |
|---|---|
| **Good** | Trivial. Works everywhere. Caches. No connection state |
| **Bad** | Latency is half the interval on average. Wasteful when nothing changed |

⚠️ **Polling is underrated.** For a status that changes every few minutes, polling every 10 seconds with an ETag returning `304` costs almost nothing ([[03.5 - HTTP Caching]]) and has none of the operational complexity of a persistent connection.

Do the arithmetic before dismissing it: 1,000 users polling every 10 seconds is 100 requests per second. That is not a lot.

### Long polling

```
Client: GET /events?since=42
Server: (holds the request open until something happens, or 30s)
Server: 200 OK with the event
Client: immediately requests again
```

| | |
|---|---|
| **Good** | Low latency without a special protocol. Works through every proxy |
| **Bad** | A held request per client. Reconnection overhead per message |

Still runs a great deal of the internet, and it is the fallback for every realtime library. See [[04.5 - Long Polling]].

### Server-Sent Events

```
GET /events
Accept: text/event-stream

data: {"progress": 42}

data: {"progress": 43}
```

| | |
|---|---|
| **Good** | Plain HTTP. Auto-reconnect with replay built in. Works with HTTP/2 multiplexing. Trivial to proxy |
| **Bad** | Server → client only. Text only. Browser connection limits on HTTP/1.1 |

💡 **SSE is the correct default for one-way realtime**, and it is the transport behind every LLM streaming API you have used. Covered in [[04.2 - Server Sent Events]].

### WebSocket

```
GET /ws
Upgrade: websocket

→ 101 Switching Protocols
→ full-duplex binary/text frames
```

| | |
|---|---|
| **Good** | True bidirectional. Low per-message overhead. Binary |
| **Bad** | Separate protocol. Own auth. Own reconnection logic. Harder to proxy, load balance and observe |

Correct when the client sends frequently: collaborative editing, multiplayer games, chat with typing indicators, live cursors.

### gRPC streaming

Four modes: unary, server-streaming, client-streaming, bidirectional. Typed contracts, HTTP/2 underneath.

Excellent for internal service-to-service streaming. Browser support requires gRPC-Web and a proxy, which usually makes it not worth it for client-facing work.

### WebRTC

Peer-to-peer media over UDP, with a data channel for arbitrary data. The right answer for audio and video and essentially nothing else. See the existing WebRTC guide.

### Push notifications

Web Push, APNs, FCM. The only option when the user is not currently on your page — which is a different problem from everything above and is often what someone actually means by "realtime notifications".

## The Decision

```
Does the client need to send frequently?
├── NO
│   ├── Is a few seconds of staleness fine?
│   │   └── YES → polling with ETags
│   └── NO → SSE
│
└── YES
    ├── Is it audio or video?
    │   └── YES → WebRTC
    ├── Is it internal service-to-service?
    │   └── YES → gRPC streaming
    └── NO → WebSocket

Is the user not on your page at all?
└── Push notifications
```

### Applied to Conduit

| Feature | Transport | Why |
|---|---|---|
| Ingestion progress | **SSE** | One-way. Server pushes, client reads |
| Document annotation | **WebSocket** | Both sides send constantly; presence and cursors |
| Search results streaming | **SSE** | One-way, and it becomes LLM token streaming in phase 9 |
| Source sync status | **Polling** | Changes every few minutes. Not worth a connection |
| "Your export is ready" | **Push / email** | The user has left the page |

💡 **Conduit deliberately uses three different transports** because the requirements genuinely differ. A design that used WebSockets for all of it would be simpler to describe and worse to operate. Being able to justify each choice individually is exactly the kind of thing that distinguishes a senior design conversation.

## The Shared Problems

Every persistent-connection transport has the same four problems. Solve them once, conceptually, and the transport choice becomes a detail.

### 1. Connections die silently

NAT mappings expire, load balancers time out, mobile networks change ([[02.10 - NAT Firewalls and Middleboxes]]).

**Every long-lived connection needs a heartbeat**, typically every 15–30 seconds. This is not optional and it is not transport-specific.

### 2. State lives on one server

```
User connects to pod-3
Event is generated on pod-7
```

You need a pub/sub backplane so any pod can reach any connection ([[04.6 - Scaling Long Lived Connections]]).

### 3. Slow consumers

A client that reads slowly makes the server buffer. Unbounded buffering is a memory leak; blocking on it makes one slow client slow everyone ([[04.7 - Presence Fanout and Backpressure]]).

Every fanout needs a per-client bounded queue and an explicit policy for when it fills.

### 4. Reconnection and gaps

A client reconnects. Did it miss anything? How does it catch up without duplicating?

SSE has `Last-Event-ID` built in. WebSocket makes you build it. Either way you need monotonic event IDs and a bounded replay buffer.

⚠️ **This is the requirement people discover last and it is the hardest to retrofit.** Decide your replay semantics — at-least-once with client-side deduplication is usually right — before you ship.

## In Production

### The costs of a persistent connection

```
Memory:  ~10–50 KB per connection in Python (task, buffers, app state)
FDs:     1 per connection
Backplane: 1 subscription per topic per node
```

100,000 connections is achievable in Python across a few processes, but everything about your deployment changes:

| Change | Consequence |
|---|---|
| Deploys drop connections | Clients must reconnect and resume. Every deploy is a reconnection storm |
| Scaling is slow | New pods only get *new* connections. Existing load does not move |
| Load balancing is uneven | Long connections pin to whichever pod accepted them |
| Memory scales with users, not requests | Capacity planning is completely different |
| One slow client can affect others | Needs deliberate isolation |

💡 **The deploy problem is the one people underestimate.** With 50,000 WebSocket connections, a rolling deploy means 50,000 reconnections in a few minutes, each doing an auth handshake and a state resync. **That burst is often larger than your normal peak load.** Design for it: jittered reconnect on the client, and a reconnect rate limit on the server.

### Auth

| Transport | Auth |
|---|---|
| SSE | Normal HTTP — cookies or `Authorization`. Nothing special |
| WebSocket | Handshake carries cookies, **but browsers cannot set headers** on the upgrade |

⚠️ **The WebSocket auth problem is real.** The browser `WebSocket` constructor takes no headers, so you cannot send `Authorization: Bearer`. The options:

1. **Cookies** — work, but reintroduce CSRF concerns and cross-site restrictions
2. **Token in the query string** — `wss://api/ws?token=...` — **leaks into access logs and browser history**
3. **Ticket pattern** — call an authenticated HTTP endpoint to get a short-lived single-use ticket, then connect with it

The ticket pattern is the right answer and it is worth knowing by name. Get a 30-second single-use ticket over normal authenticated HTTP, present it on the WebSocket connect, exchange it for a session. Short-lived, single-use, and safe in logs.

### Expiring credentials mid-connection

A connection that lives for hours outlives a 15-minute access token. You need either periodic re-authentication over the connection, or a rule that connections are closed and re-established when credentials expire.

**Decide this explicitly.** The default — never rechecking — means a revoked user stays connected indefinitely, which is a real security gap.

### Observability

Persistent connections break standard HTTP monitoring: one request that lasts hours produces one log line and one latency measurement of "3 hours".

Track instead:

```python
connections_active.labels(transport="sse").set(count)
connection_duration_seconds.observe(duration)
messages_sent_total.labels(transport="sse").inc()
client_queue_depth.observe(depth)
slow_client_disconnects_total.inc()
reconnects_total.labels(reason="server_shutdown").inc()
```

**Reconnect rate is the health signal to watch.** A rising reconnect rate means connections are dying — a proxy timeout, a heartbeat problem, or a crash loop — and it is visible long before users complain.

Find where the transport-specific code ends and the shared logic begins — what is genuinely common across all three? Then: how does Zulip let a client that was offline for ten minutes catch up without missing or duplicating events?

**Read, in order:**

1. `centrifugo/internal/client/` — the client hub and the transport abstraction. **The interesting part is how small the transport-specific code is** compared to the shared connection, subscription and presence logic
2. `centrifugo/internal/` — the Redis broker. How a message published on node A reaches a client on node B
3. `zulip/zerver/tornado/event_queue.py` — **the best real implementation of resumable event streams in an open codebase.** Per-client queues, event IDs, and the catch-up path
4. `zulip/zerver/tornado/handlers.py` — long polling done properly, with all the edge cases handled
5. `vllm/entrypoints/openai/serving_chat.py` — SSE for LLM tokens, including client-disconnect detection

💡 The Zulip reading is the highest value here. Their realtime layer has been in production for over a decade at scale, is thoroughly documented in-repo, and is Python — so you can steal the design directly for Conduit phase 3.

## Exercise

**Drill 4.0 — Same feature, four transports**

The point is to feel the cost difference directly rather than reading about it.

```
drills/04-transports/
├── feature/
│   └── SPEC.md           # one feature, implemented four ways
├── polling/
│   ├── server.py
│   └── client.py
├── longpoll/
│   ├── server.py
│   └── client.py
├── sse/
│   ├── server.py
│   └── client.py
├── websocket/
│   ├── server.py
│   └── client.py
├── bench/
│   ├── load.py           # 1000 clients, measure everything
│   ├── latency.py        # event generated → client received
│   └── RESULTS.md
├── failure/
│   ├── proxy_timeout.sh  # kill idle connections
│   ├── deploy.sh         # rolling restart under load
│   └── FINDINGS.md
├── auth/
│   ├── ticket.py         # the WebSocket ticket pattern
│   └── query_token.py    # the wrong way, and why
└── README.md
```

**Part 1 — One feature, four ways.** The feature: a job progress tracker. A job runs for 60 seconds and emits progress events. Clients watch it live.

Implement it with polling, long polling, SSE and WebSocket. Same server-side event source.

**Part 2 — Measure the real costs.** 1,000 concurrent clients watching, for each transport:

| Metric | |
|---|---|
| Server memory | Total and per client |
| File descriptors | |
| Requests per second | |
| Bytes transferred | Total for the whole 60s job |
| Event latency | Generated → received, p50 and p99 |
| CPU | |

**Chart it.** You should find polling using the most bandwidth and the least memory, WebSocket the reverse, and SSE close to WebSocket at a fraction of the complexity.

**Part 3 — Latency versus cost.** For polling, sweep the interval: 1s, 5s, 10s, 30s. Chart event latency against requests per second.

Find the point where polling's cost exceeds SSE's. **For your event rate, is polling actually worse?** Be honest about the answer — it is often "no", and knowing that prevents a lot of unnecessary complexity.

**Part 4 — Kill the connections.** Put nginx in front with a 30-second `proxy_read_timeout`.

Run all four transports. Which break? What does each client observe?

Then add heartbeats and confirm the fix. Measure the heartbeat overhead at 1,000 clients — bytes per minute and CPU.

**Part 5 — The deploy storm.** 1,000 connected clients. Perform a rolling restart.

Measure: how many reconnect, how quickly, and what the peak request rate during recovery is compared to steady state.

Then add jittered client reconnect (random 0–5 seconds) and measure again. **Chart the reconnection rate over time in both cases.** The unjittered version is a spike; the jittered version is a hill. This is the same lesson as retry jitter ([[03.4 - Idempotency and Safe Retries]]) in a different setting.

**Part 6 — WebSocket auth.** Implement all three approaches: cookie, query-string token, and the ticket pattern.

For the query-string version, check your nginx access log and confirm the token is sitting there in plaintext. Also check the browser's history and the `Referer` header behaviour.

Then implement the ticket pattern properly: short expiry, single use, bound to the user, exchanged on connect. Write tests for ticket replay and expiry.

**Part 7 — Write the decision doc.** For Conduit, an ADR choosing a transport for each of the five features in the table above. Each choice must state what you rejected and why.

**Done when:**
- Your four-transport cost table is complete with real measurements
- You know the event rate at which polling stops being competitive for your case
- All four transports survive a 30-second proxy timeout with heartbeats
- Your reconnection charts show jitter flattening the deploy storm
- The ticket pattern works and you have seen a token in your own access log
- The ADR justifies five transport choices independently
