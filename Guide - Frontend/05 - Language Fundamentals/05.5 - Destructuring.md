# Destructuring

Destructuring extracts values from arrays and objects into bindings. It reads as pattern matching on the left-hand side.

## Object destructuring

```js
const user = { id: 1, name: "Vijay", role: "engineer" };

const { name, role } = user;
const { name: userName } = user;                  // rename
const { city = "Delhi" } = user;                  // default
const { name: n = "anon" } = user;                // rename + default
const { id, ...rest } = user;                     // rest — { name, role }
```

Order does not matter; matching is by key. Renaming reads backwards at first — `{ name: userName }` means "take `name`, call it `userName`" — but becomes natural quickly.

Defaults apply **only when the value is `undefined`**, never for `null`, `0` or `""` ([[05.4 - null vs undefined]]):

```js
const { count = 10 } = { count: 0 };     // 0
const { count = 10 } = { count: null };  // null
const { count = 10 } = {};               // 10
```

## Array destructuring

```js
const [first, second] = [1, 2, 3];
const [, , third] = [1, 2, 3];            // skip with holes
const [head, ...tail] = [1, 2, 3];        // tail is [2, 3]
const [a = 5] = [];                       // default
[x, y] = [y, x];                          // swap without a temp
```

Array destructuring works on **any iterable** ([[06.6 - Iterators and Generators]]), not just arrays:

```js
const [r, g, b] = "rgb";
const [firstEntry] = new Map([["a", 1]]);
const [x, y] = new Set([10, 20]);
```

This is why `const [state, setState] = useState()` works — the hook returns an array and the naming is entirely up to the caller, which is the whole reason hooks return arrays rather than objects.

## Nested destructuring

```js
const response = {
  data: { user: { profile: { city: "Delhi" } } },
  meta: { page: 1 },
};

const { data: { user: { profile: { city } } } } = response;
```

Concise but fragile: if `data.user` is `undefined`, this throws. Nested defaults help but get ugly fast:

```js
const { data: { user: { profile = {} } = {} } = {} } = response;
```

Past two levels, optional chaining is clearer ([[05.7 - Optional Chaining and Nullish Coalescing]]):

```js
const city = response?.data?.user?.profile?.city ?? "Unknown";
```

Note that `const { a: { b } } = obj` does **not** create a binding named `a` — only `b`. The intermediate name is part of the pattern, not a variable.

## Function parameters

The most valuable use in practice:

```js
function createUser({ name, email, role = "member", ...meta }) {
  // named arguments with defaults
}

createUser({ name: "Vijay", email: "a@b.com", team: "platform" });
```

This gives you named arguments, defaults, and freedom from argument order. Compare with `createUser(name, email, role, isActive, team)` where every call site must remember the sequence and pass `undefined` for skipped values.

**Always supply a default for the whole parameter object** if the function can be called with no arguments:

```js
function fetchData({ retries = 3 } = {}) {}
fetchData();   // works
```

Without `= {}`, `fetchData()` throws because you cannot destructure `undefined`.

## Common patterns

**Swapping and rotating:**

```js
[a, b] = [b, a];
[a, b, c] = [c, a, b];
```

**Return multiple values:**

```js
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return [on, () => setOn(v => !v)];
}
```

**Removing a key immutably:**

```js
const { password, ...safeUser } = user;
```

A single-expression way to strip a field. Linters flag `password` as unused — the usual escape is an ESLint `ignoreRestSiblings` option, which is enabled in most configs precisely for this pattern.

**Destructuring in loops:**

```js
for (const { id, name } of users) {}
for (const [key, value] of Object.entries(obj)) {}
for (const [key, value] of map) {}
```

**Regex named groups:**

```js
const { groups: { year, month } } = /(?<year>\d{4})-(?<month>\d{2})/.exec("2026-08");
```

## Assignment without declaration

Destructuring into existing variables requires parentheses at statement level, because `{` starts a block:

```js
let a, b;
({ a, b } = { a: 1, b: 2 });  // parentheses required
[a, b] = [1, 2];              // arrays are fine
```

## How senior engineers actually use this

**They destructure props at the top of components,** which doubles as documentation of what the component consumes:

```jsx
function Card({ title, subtitle, onClick, variant = "default" }) {}
```

**They use object parameters for anything past two arguments.** Positional arguments stop being readable at three, and adding a fourth is a breaking change; adding a key to an options object is not.

**They avoid deep destructuring on API responses.** Server shapes change, and a five-level pattern throws an unhelpful "cannot destructure property of undefined" rather than failing gracefully. Optional chaining with explicit fallbacks is more robust.

**They watch the memoization consequence in React.** Destructuring a prop object creates new bindings each render but does not create new *values* — the identity of nested objects is unchanged. However, `const { config = {} } = props` creates a **new** `{}` on every render when `config` is absent, which then breaks dependency arrays and memoized children. Hoist such defaults to module scope.

## Common pitfalls

- Destructuring `undefined` or `null` — throws `TypeError`.
- Forgetting `= {}` on a destructured parameter, so calling with no arguments throws.
- Expecting defaults to apply for `null`.
- Assuming the intermediate key in a nested pattern becomes a variable.
- Forgetting parentheses when destructuring into existing variables.
- Creating fresh default objects/arrays inline every render in React.

## Interview angle

Destructuring rarely gets a dedicated question but appears constantly in code-reading exercises and output prediction — particularly defaults not applying to `null`, and nested patterns not creating intermediate bindings. Being able to say "array destructuring works on any iterable, which is why `useState` returns an array" is a good connective detail.
