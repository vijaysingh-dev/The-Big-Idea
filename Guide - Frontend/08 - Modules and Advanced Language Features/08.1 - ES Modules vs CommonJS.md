# ES Modules vs CommonJS

Two module systems that coexist uncomfortably. ESM is the standard and the future; CJS is what most of npm was written in.

## Syntax

```js
// ESM
import defaultExport from "./mod.js";
import { named, other as alias } from "./mod.js";
import * as everything from "./mod.js";
import "./side-effect.js";

export const value = 1;
export function fn() {}
export default class {}
export { a, b as c };
export * from "./other.js";

// CommonJS
const mod = require("./mod");
const { named } = require("./mod");

module.exports = { a, b };
module.exports.c = 1;
exports.d = 2;      // shorthand — breaks if you reassign module.exports
```

## The fundamental difference: static vs dynamic

**ESM is static.** Imports and exports are determined at parse time, before any code executes. The module graph is known without running anything.

**CJS is dynamic.** `require()` is a function call that runs at execution time, so it can be conditional, computed, or inside a loop:

```js
// Legal in CJS
if (isProduction) {
  config = require("./config.prod");
}
const mod = require(`./locales/${lang}`);

// Illegal in ESM — import is not a function
if (x) import "./mod.js";        // SyntaxError
```

ESM's static structure is what enables **tree shaking** — the bundler can prove which exports are unused and drop them ([[27.6 - Tree Shaking]]). It also enables faster startup, since the entire graph can be fetched in parallel rather than discovered one `require` at a time.

Dynamic loading in ESM uses `import()`, which returns a promise ([[08.2 - Dynamic Imports]]).

## Live bindings vs value copies

The difference people trip over:

```js
// counter.js (ESM)
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from "./counter.js";
console.log(count);  // 0
increment();
console.log(count);  // 1 — the binding is live
```

```js
// counter.js (CJS)
let count = 0;
module.exports = { count, increment: () => count++ };

// main.js
const { count, increment } = require("./counter");
increment();
console.log(count);  // 0 — a copy was taken at require time
```

ESM imports are **read-only live bindings** — a view onto the exporting module's variable. CJS gives you a snapshot of whatever `module.exports` held at that moment.

You cannot assign to an imported binding:

```js
import { count } from "./counter.js";
count = 5;   // TypeError: Assignment to constant variable
```

## Hoisting and execution order

`import` declarations are hoisted and resolved before any module body runs, so imported bindings are available anywhere in the file regardless of statement position ([[05.2 - Hoisting and the Temporal Dead Zone]]).

Module evaluation is depth-first over the dependency graph, and each module runs **exactly once** no matter how many times it is imported. That single-evaluation guarantee is what makes module-scope state behave like a singleton.

## Circular dependencies

Both systems handle cycles, differently and badly.

```js
// a.js
import { b } from "./b.js";
export const a = "a";
console.log(b);        // may be in TDZ

// b.js
import { a } from "./a.js";
export const b = "b";
```

In ESM, a binding accessed before its module finished evaluating throws "Cannot access before initialization". In CJS you get `undefined` instead — a partially populated `module.exports`.

Function declarations survive cycles better than `const` because they are fully hoisted. But the real answer is to break the cycle: extract shared code into a third module, or invert the dependency. A cycle is almost always a design signal.

## Strict mode and scope

ESM is always strict mode. Top-level `this` is `undefined`, not `window`. Top-level `var` does not create a global property ([[02.2 - Lexical Scope]]).

CJS wraps each file in a function, so `this` is `module.exports` and top-level variables are function-scoped, not global. Both avoid global pollution, by different means.

CJS gives you `__dirname`, `__filename`, `require` and `module`. ESM gives you `import.meta.url` instead:

```js
const dir = path.dirname(new URL(import.meta.url).pathname);
```

## Top-level await

ESM supports it; CJS cannot, because `require` is synchronous:

```js
// Valid only in ESM
const config = await fetch("/config.json").then(r => r.json());
export { config };
```

Every module importing this one waits for it. Convenient, but it blocks the dependent graph, so keep it off critical paths ([[04.4 - async await]]).

## Interop

**ESM importing CJS** generally works — the whole `module.exports` becomes the default export:

```js
import pkg from "commonjs-package";
const { thing } = pkg;
```

Named imports from CJS work only when the bundler or Node can statically detect the export names, which is heuristic and unreliable. The default-import-then-destructure form always works.

**CJS importing ESM** requires `await import()`, since ESM loading is asynchronous. A plain `require()` of an ESM package throws `ERR_REQUIRE_ESM` — the error that dominated Node ecosystem pain for years. Recent Node versions can `require()` synchronous ESM, which softens this.

In Node, `"type": "module"` in `package.json` makes `.js` files ESM. The `.mjs` and `.cjs` extensions force one or the other explicitly. Dual-mode packages use conditional exports:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    }
  }
}
```

The **dual package hazard** is worth knowing: if a package is loaded through both entry points in one process, you get two copies with separate module state — two instances of a singleton, two React contexts, two `WeakMap` registries that do not agree.

## In the browser

```html
<script type="module" src="app.js"></script>
<script nomodule src="legacy.js"></script>
```

Module scripts are deferred by default, are always strict, use CORS for cross-origin fetches, and require explicit file extensions in specifiers. Bare specifiers (`import React from "react"`) work only with a build step or an import map:

```html
<script type="importmap">
  { "imports": { "lodash": "https://esm.sh/lodash" } }
</script>
```

Vite's dev server serves native ESM directly, which is why it starts instantly — no bundling required in development ([[27.3 - Vite]]).

## How senior engineers actually use this

**They write ESM everywhere and configure the build to emit both if publishing a library.** New code has no reason to be CJS.

**They avoid default exports** in application code. Named exports are refactor-safe (renaming is mechanical), better for tree shaking, and better for auto-import in editors. Default exports also allow inconsistent naming across import sites.

**They keep module bodies side-effect-free.** Code that runs at import time is unpredictable to order and blocks tree shaking. Export functions; let callers decide when to run them.

**They treat circular imports as bugs**, not as something to work around with lazy requires.

## Common pitfalls

- Expecting CJS destructured values to update.
- Circular imports producing TDZ errors that look unrelated to imports.
- Named imports from a CJS package failing under some bundlers and working under others.
- `require()` of an ESM-only package.
- Top-level await on a critical-path module delaying everything downstream.
- Dual package hazard producing two copies of a stateful library.

## Interview angle

"Difference between ESM and CommonJS" wants: static versus dynamic resolution, live bindings versus value copies, asynchronous versus synchronous loading, always-strict, and top-level await. Connect static analysis to tree shaking — that is the practical payoff and the reason bundlers care. Mentioning the interop friction and the dual package hazard shows you have shipped real projects.
