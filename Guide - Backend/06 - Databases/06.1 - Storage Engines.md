# Storage Engines

#backend #databases #storage

> **In one line:** Every database picks between updating data in place (B-tree) or only ever appending (LSM), and that one choice determines its read speed, write speed, space usage and operational personality.

---

## The Idea

A storage engine solves one problem: **you have far more data than memory, and disks are slow at random access.**

| | B-tree | LSM tree |
|---|---|---|
| Writes | Update the page in place | Append to a log, merge later |
| Write pattern | Random | **Sequential** |
| Reads | One tree traversal | Check several levels |
| Write amplification | Moderate | **Higher** |
| Read amplification | **Low** | Higher |
| Space amplification | Moderate (fragmentation) | Lower (compression) |
| Used by | Postgres, MySQL/InnoDB, SQLite | RocksDB, Cassandra, LevelDB, ScyllaDB |

💡 **The three amplifications are the whole vocabulary of storage engine design.** Every engine trades them against each other, and no engine wins all three.

| Amplification | Means |
|---|---|
| **Write** | Bytes written to disk ÷ bytes of data you wrote |
| **Read** | Disk reads ÷ logical reads |
| **Space** | Bytes on disk ÷ bytes of live data |

---

## B-trees

A balanced tree of fixed-size pages, typically 8KB.

```
                  [ root page ]
        [ internal ] [ internal ] [ internal ]
   [ leaf ] [ leaf ] [ leaf ]   ← the actual rows or row pointers
```

With a branching factor of ~500:

```
Depth 3:  125,000,000 rows
Depth 4:  62,500,000,000
```

⚠️ **Almost every B-tree index you will meet is 3–4 levels deep**, and the upper levels are cached. **A lookup is effectively one disk read** — which is why B-trees have dominated for fifty years.

### Writing

⚠️ **Modifying one byte writes 8KB.** Change 100 bytes across 100 pages and you write 800KB. That is write amplification.

When a page fills it **splits** — half the rows move to a new page and the parent gains a pointer. Splits cascade upward.

💡 **This is why insert order matters enormously.** Sequential keys append to the rightmost page and split cleanly. Random keys scatter across every page, causing splits everywhere, fragmentation, and a working set that will not fit in memory.

**Choosing UUIDv7 or ULID over UUIDv4 is a storage engine decision**, and it is one of the highest-leverage schema choices you can make ([[06.3 - Indexes Deep Dive]]).

### Crash safety

A page write is not atomic, so B-tree databases write everything twice:

```
1. Append the change to the write-ahead log  (sequential, fast)
2. fsync the WAL — now durable
3. Modify the page in memory
4. Write the page to disk later, at checkpoint time
```

**The WAL is what makes a commit fast** — a sequential append plus one `fsync` rather than random page writes ([[06.2 - Postgres Architecture]]).

## LSM Trees

Never update anything. Only append.

```
Write → memtable (sorted, in memory)
          │ when full
        SSTable L0 (immutable file)
          │ compaction
        L1 ─ L2 ─ L3 ...   (larger, fewer, non-overlapping)
```

**Writes are trivially fast** — an in-memory insert plus a WAL append. Nothing random touches the disk.

### Reading costs

A read may touch several files. Two mitigations:

**Bloom filters.** A small probabilistic structure per SSTable answering "is this key definitely absent?" — a negative skips the file entirely. False positives are possible; false negatives are not.

```
10 bits per key → ~1% false positive rate
```

💡 **Bloom filters are what make LSM reads viable.** Without them a point lookup would read every level.

### Compaction

| Strategy | Write amp | Read amp | Space amp | Use for |
|---|---|---|---|---|
| **Size-tiered** | Lower | Higher | **Higher** (up to 2×) | Write-heavy |
| **Levelled** | **Higher** (10–30×) | Lower | Lower (~1.1×) | Read-heavy |

⚠️ **Compaction is unscheduled background I/O competing with your queries.** The classic LSM operational problem is a latency spike when a large compaction runs.

💡 **The honest personality difference: B-tree databases have predictable performance with occasional checkpoint stalls; LSM databases have excellent write throughput with occasional compaction stalls.** Neither is free.

### Deletes are writes

```
DELETE key → write a tombstone
```

⚠️ **A range scan over heavily-deleted data reads all the tombstones.** In Cassandra this is a well-known failure mode — a queue-like table where you insert and delete produces scans that get slower over time even though the table appears empty.

**Do not build queues on LSM databases.** It is the single most common Cassandra anti-pattern.

## Which Engine, When

| Workload | Engine | Why |
|---|---|---|
| Read-heavy OLTP | **B-tree** | Low read amplification, predictable |
| Write-heavy ingest | **LSM** | Sequential writes, high throughput |
| Time-series append | LSM | Sequential keys, natural compression |
| Range scans | Either — B-tree if deletes are common | Tombstones hurt LSM scans |
| Random-key writes | **LSM** | B-trees suffer badly |
| Predictable latency | B-tree | Compaction spikes are hard to bound |

💡 **For a typical backend application, Postgres and its B-tree is almost always right.** LSM engines earn their place at very high write rates, very large scale, or specific shapes like time-series.

⚠️ **Do not choose Cassandra because it "scales better".** It scales writes better, at the cost of a data model designed around your queries, no joins, no cross-partition transactions, and compaction tuning as an ongoing job.

## In Production

### Postgres uses a B-tree with a twist

Postgres never updates a row in place. An `UPDATE` writes a **new row version** and marks the old one dead ([[06.7 - MVCC Vacuum and Bloat]]).

⚠️ **Every index on the table gets a new entry.** A table with eight indexes pays eight index writes for a one-column update.

**HOT (Heap-Only Tuple) updates avoid this**: if no indexed column changed *and* there is free space on the same page, the new version stays there and indexes are untouched.

```sql
ALTER TABLE documents SET (fillfactor = 85);
```

💡 **Leaving 15% of each page free means more updates qualify as HOT**, which can dramatically reduce write amplification. Not free — more space, slightly more pages read — but for a hot update table it often wins.

### MySQL/InnoDB differs in one important way

InnoDB uses a **clustered index**: the primary key *is* the table, rows stored in primary key order.

| Consequence | |
|---|---|
| Primary key lookups are very fast | The row is right there |
| Secondary indexes store the PK, not a pointer | Two lookups |
| **Primary key size matters enormously** | Every secondary index contains a copy |
| **Random primary keys are catastrophic** | Inserts scatter across the whole table |

⚠️ **A UUIDv4 primary key in InnoDB is a documented disaster**, far worse than in Postgres, because it randomises the physical order of the entire table rather than just one index.

### The performance cliff

```sql
SELECT pg_size_pretty(pg_relation_size('documents_created_at_idx'));
```

💡 **The cliff you care about is when your working set stops fitting in memory.** Below it, everything is a memory access; above it, everything is a disk read — a 1,000× difference.

**This is why index size matters, why `fillfactor` matters, and why bloat matters. All three are really about keeping the working set in RAM.**

### The disk underneath

| Storage | Random read | Notes |
|---|---|---|
| NVMe SSD | ~50 µs | Random is nearly free |
| SATA SSD | ~100 µs | |
| **Network storage (EBS gp3)** | ~500 µs–1 ms | **Latency is the constraint** |
| HDD | ~10 ms | Random access is fatal |

⚠️ **On network-attached storage, IOPS and latency are provisioned, not physical.** A database fine on local NVMe can be dramatically slower on a cloud volume with the same nominal throughput, because per-operation latency is 10–20× higher.

💡 **SSDs have narrowed the B-tree/LSM gap considerably.** LSM's core advantage — avoiding random writes — mattered enormously on spinning disks. **Much of the "LSM is the future" writing dates from the HDD era.**

## Codebase

**Repo:** `postgres/postgres`, `facebook/rocksdb`, `sqlite/sqlite`

**Question to answer:** In Postgres, trace what happens on disk for a single `UPDATE` — which pages are written, in what order, and what makes it crash-safe? Then: in RocksDB, follow one key from `Put()` to a levelled SSTable, and find where compaction decides which files to merge.

**Read, in order:**

1. `postgres/src/backend/access/nbtree/README` — **an essay, not code.** The best explanation of a production B-tree implementation in existence, including split handling and concurrency. **Read this even if you read nothing else**
2. `postgres/src/backend/access/nbtree/nbtinsert.c` — `_bt_insertonpg` and `_bt_split`. The README makes this readable
3. `postgres/src/backend/access/heap/README.HOT` — **HOT updates by their authors.** Short, and it explains the `fillfactor` tuning
4. `rocksdb/db/memtable.cc` and `db/version_set.cc` — the memtable and level tracking
5. `rocksdb/db/compaction/compaction_picker_level.cc` — **the compaction decision.** This is where LSM's operational personality comes from
6. `sqlite/src/btree.c` — a complete, self-contained B-tree in one well-commented file. **The best place to actually understand the algorithm** if the Postgres source feels large

💡 The Postgres `nbtree/README` is one of the genuinely great pieces of technical writing in open source. It explains not just what the code does but why the alternatives were rejected, including the Lehman-Yao B-link concurrency approach. **Two hours with that file is worth more than any book chapter on B-trees.**

**Size:** 2–3 sessions.

## Exercise

**Drill 6.1 — Build both, measure the difference**

```
drills/06-storage-engines/
├── btree/{node.py, tree.py, disk.py, tests/}
├── lsm/{memtable.py, sstable.py, bloom.py, compaction.py, engine.py, tests/}
├── bench/{workloads.py, amplification.py, keyorder.py, RESULTS.md}
├── postgres/{hot_updates.sql, uuid_vs_ulid.py, FINDINGS.md}
└── README.md
```

**Part 1 — A real B-tree on disk.** Fixed 4KB pages in a real file, search, insert with splits, range scan. Instrument every page read and write.

Test with 1 million keys inserted **sequentially**, then 1 million **randomly**. Measure tree depth, page reads per lookup, page writes per insert, and total file size.

**The random case should produce a substantially larger file with more writes per insert.** That difference is fragmentation, and it is why UUIDv4 primary keys are a problem.

**Part 2 — A real LSM engine.** Memtable, SSTable flush, bloom filters, both compaction strategies. Same 1 million keys, same metrics, plus SSTable count and compaction I/O.

**Part 3 — The amplification table.** Four workloads (sequential write, random write, point read, range scan) × three engines (your B-tree, LSM size-tiered, LSM levelled), measuring all three amplifications.

**Twelve cells × three metrics. Predict each before measuring.**

**This table will make every "should we use Cassandra" conversation for the rest of your career shorter.**

**Part 4 — Bloom filters, quantified.** Point lookups for nonexistent keys, with filters disabled and at 4, 8 and 16 bits per key.

Measure files read per lookup, latency, and filter memory. **Find the point of diminishing returns.** Then measure the false positive rate empirically and compare to theory.

**Part 5 — Tombstone accumulation.** In your LSM engine: insert 1 million keys, delete 900,000, range scan.

Measure scan time before and after compaction. **Then repeat the insert/delete cycle ten times without compacting and watch scans degrade.**

**This is the Cassandra queue anti-pattern, reproduced.** Write down what you would tell a colleague proposing it.

**Part 6 — HOT updates in real Postgres.** A table with 8 indexes. Update a non-indexed column 100,000 times, with `fillfactor` at 100 and 85.

```sql
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'documents';
```

Measure WAL bytes, index size growth, table bloat and update throughput. **The HOT ratio is the number to watch.**

**Part 7 — UUIDv4 versus ULID.** Two identical tables, 5 million rows each.

Measure insert throughput, final index size, index bloat, cache hit ratio and point lookup latency. **The index size difference should be substantial.**

Then run both under a memory constraint where one working set fits and the other does not, and **measure the cliff.**

**Done when:**
- Your B-tree handles 1M keys with correct splits, and random insertion visibly costs more
- Your LSM engine has working bloom filters and both compaction strategies
- The 12×3 amplification table is complete with predictions recorded
- You know the bloom filter bits-per-key sweet spot from measurement
- You reproduced tombstone-driven scan degradation
- You have measured HOT update ratio improving with `fillfactor`
- The UUIDv4-versus-ULID index size difference is quantified on 5M rows
