# Security Model Overview

## Why this section matters more than it looks

Salesforce security is the topic that most separates competent developers from people who guess. It is also the source of the single most common support question in every org: *why can this person see that record, and why can that person not see this one?*

The answer is always the same shape. Access is decided by a stack of independent mechanisms, evaluated in a fixed order, and each one answers a different question. Once you can name which layer is producing a result, the answer takes two minutes instead of two days.

## The two questions

Every access decision splits into two completely separate questions, and confusing them is the root of most misunderstandings.

**Question 1: What kinds of things can this user work with?**
Can they see the Opportunity object at all? Can they edit the Amount field? This comes from **profiles and permission sets**, and it applies to the object and field level, uniformly, regardless of which record.

**Question 2: Which specific records can they see?**
Of the Opportunities that exist, which ones? This comes from **the sharing model** — organization-wide defaults, role hierarchy, sharing rules, manual shares, teams.

A user can have full edit permission on Opportunity and still see zero records. A user can have access to a million records and be unable to read one field on them. The two questions are answered by different machinery and neither substitutes for the other.

## The layers, in evaluation order

```
Organization
    Login policies, IP ranges, MFA, session settings
        |
Object level (profile + permission sets)
    Can this user create/read/edit/delete this object at all?
        |
Field level (profile + permission sets)
    Which fields on that object are visible or editable?
        |
Record level (the sharing model)
    Organization-Wide Defaults      the restrictive baseline
        Role Hierarchy               opens access upward
        Sharing Rules                opens access sideways
        Manual and Team Shares       opens access individually
        Implicit and Apex Sharing    opens access by platform or code
```

Two rules govern how these combine, and they explain nearly everything:

**Object and field permissions are additive across profile and permission sets.** A permission granted anywhere is granted. There is no "deny" that overrides a grant, other than a small set of restriction rules on specific features.

**Record sharing only ever grants more access, never less.** OWD sets the floor, and everything above it opens access up. Nothing in the sharing model can take away access that a lower layer granted.

This is why the correct design approach is: **set the baseline as restrictive as the business allows, then open it up deliberately.** Trying to start open and close things off does not work, because there is no mechanism for closing.

## A worked trace

A service coordinator opens a Warranty Claim record and gets "insufficient privileges". Walk the stack in order.

1. **Can they log in at all?** If it were login policy, they would not have reached the record. Rule that out.
2. **Do they have Read on the object?** Check their profile and permission sets for object permissions on `Warranty_Claim__c`. If Read is missing, that is the answer, and it applies to every claim, not just this one — a useful diagnostic signal.
3. **Do they have record access?** If they can see *some* claims but not this one, the object permission is fine and the problem is record-level. Check ownership, OWD, role, and sharing rules.
4. **Is a field the problem instead?** If the record opens but a field is blank or missing, that is field-level security, not record access.

The diagnostic shortcut worth memorizing: **"no claims at all" is an object permission problem; "some claims but not this one" is a sharing problem; "the record opens but a field is missing" is field-level security.** That one sentence resolves most access tickets.

## The developer's obligation

Here is the part that catches people arriving from other stacks: **Apex does not enforce security by default.**

A SOQL query in an Apex class declared `without sharing` returns every record in the org, regardless of who is running it. Field-level security is not applied to query results at all unless you ask for it. A Lightning Web Component calling that Apex method will happily display data the user should never see.

This is deliberate — some code genuinely needs elevated access — but it means security enforcement in code is your responsibility, not the platform's. Getting it wrong produces a real data exposure, and it is the most common finding in Salesforce security reviews.

```java
// Runs with the user's record access
public with sharing class ClaimService { }

// Ignores record sharing entirely
public without sharing class ClaimAdminService { }

// Inherits from whatever called it; the right default for reusable utilities
public inherited sharing class ClaimUtils { }
```

Sharing keywords control *record* access only. Object and field permissions need separate handling. See [[03.13 - Enforcing Security in Apex and SOQL]].

## How to think about design

**Least privilege as the default.** Start with private OWD and minimal profiles, then grant. This is more work upfront and dramatically less work than retrofitting restrictions onto an open org, which requires recalculating sharing across every record.

**Permission sets over profiles.** Salesforce has been moving away from profiles for years. Assign a minimal profile and grant capability through permission sets and permission set groups. It scales, it is auditable, and it avoids the profile explosion that afflicts older orgs.

**Model the org chart, not the current team.** Roles and sharing rules built around specific people break at the first reorganization. Build around functions.

**Sharing decisions are data model decisions.** Master-detail children inherit the parent's sharing and cannot have their own. That choice was made in section 02 and cannot be changed here without a migration. See [[02.7 - Relationships - Lookup vs Master-Detail]].

**Complexity has a runtime cost.** Every sharing rule materializes rows in share tables. A complex model on a large object means slow recalculation, long-running sharing jobs, and locking. See [[23.3 - Sharing at Scale and Sharing Recalculation]].
