# Closure Patterns in Production

Closures are not an interview curiosity. They are the underlying mechanism for module privacy, memoization, rate limiting, dependency injection and most state libraries. This note collects the patterns you will actually write and read.

## Private state via factory

```js
function createStore(initialState) {
  let state = initialState;
  const listeners = new Set();

  return {
    getState: () => state,
    setState(partial) {
      state = { ...state, ...partial };
      listeners.forEach(l => l(state));
    },
    subscribe(listener) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}
```

`state` and `listeners` cannot be reached from outside. No `this`, so methods can be destructured and passed around freely. `subscribe` returning its own unsubscribe function is the standard shape — it makes cleanup impossible to get wrong, and maps directly onto a React `useEffect` return value.

This is essentially Redux's store and Zustand's `create` in twenty lines ([[20.8 - Zustand Jotai and Modern Alternatives]]).

## Memoization

```js
function memoize(fn, keyFn = (...args) => JSON.stringify(args)) {
  const cache = new Map();

  return (...args) => {
    const key = keyFn(...args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  };
}

const expensiveLayout = memoize(computeLayout);
```

The cache lives in the closure, one per memoized function. Two production concerns follow immediately: the cache grows without bound, and `JSON.stringify` is a poor key for objects with unstable property order. A real implementation caps size (an LRU) or uses a `WeakMap` keyed by object identity so entries are collected with their keys ([[07.4 - WeakMap WeakSet and WeakRef]]).

## once

```js
function once(fn) {
  let called = false;
  let result;

  return (...args) => {
    if (!called) {
      called = true;
      result = fn(...args);
    }
    return result;
  };
}

const initAnalytics = once(setupSDK);
```

Common in bootstrapping code where a module may be imported from several places but initialization must happen exactly once. Note that `called` is set *before* invoking `fn`, so a re-entrant call during initialization does not run it twice.

## Debounce and throttle

Both are closures over a timer handle. Covered fully in [[29.1 - Debounce and Throttle]]; the closure shape is the point here.

```js
function debounce(fn, delay) {
  let timer;

  const debounced = (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };

  debounced.cancel = () => clearTimeout(timer);
  return debounced;
}
```

Attaching `cancel` to the returned function matters in component code: without it you cannot clean up a pending invocation on unmount, and the callback fires against a dead component.

## Rate limiting and concurrency control

```js
function limitConcurrency(limit) {
  let active = 0;
  const queue = [];

  const next = () => {
    if (active >= limit || !queue.length) return;
    active++;
    const { task, resolve, reject } = queue.shift();
    task().then(resolve, reject).finally(() => {
      active--;
      next();
    });
  };

  return (task) =>
    new Promise((resolve, reject) => {
      queue.push({ task, resolve, reject });
      next();
    });
}

const limited = limitConcurrency(4);
await Promise.all(urls.map(u => limited(() => fetch(u))));
```

`active` and `queue` are shared by every call through the returned function. This exact pattern is how you avoid firing 200 simultaneous requests when mapping over a large list — browsers cap concurrent connections per origin anyway, and unbounded parallelism just moves the queue somewhere you cannot observe it.

## Dependency injection via configuration closure

```js
function createApiClient({ baseUrl, getToken, onUnauthorized }) {
  async function request(path, options = {}) {
    const res = await fetch(`${baseUrl}${path}`, {
      ...options,
      headers: { ...options.headers, Authorization: `Bearer ${getToken()}` },
    });

    if (res.status === 401) onUnauthorized();
    if (!res.ok) throw new ApiError(res.status, await res.text());
    return res.json();
  }

  return {
    get: (path) => request(path),
    post: (path, body) => request(path, { method: "POST", body: JSON.stringify(body) }),
  };
}
```

Every dependency is explicit and injected once. Tests construct a client with a fake `getToken` and a stubbed `fetch` — no module mocking required. This is the single most useful closure pattern in application code, and it is the design behind [[28.4 - The Data Layer]].

Note `getToken` is a *function*, not a value. Closing over a token string would capture a stale token after refresh; closing over a getter always reads the current one. This distinction — capture the accessor, not the value — resolves a large fraction of stale-closure bugs.

## Event handler with captured context

```js
function attachTooltip(el, text) {
  const show = () => renderTooltip(el, text);
  const hide = () => removeTooltip(el);

  el.addEventListener("mouseenter", show);
  el.addEventListener("mouseleave", hide);

  return () => {
    el.removeEventListener("mouseenter", show);
    el.removeEventListener("mouseleave", hide);
  };
}
```

The handlers close over `el` and `text`, and the returned teardown closes over the same handler references — which is essential, since `removeEventListener` matches by identity. Returning a disposer rather than exposing the handlers is the pattern that makes this safe to use inside `useEffect`.

## How senior engineers actually use this

**They return disposers, not handles.** Any function that registers something returns the function that unregisters it. This makes cleanup local to setup and removes an entire class of leaks.

**They inject accessors instead of values.** Config that can change (tokens, feature flags, current user) is closed over as a getter.

**They bound every cache.** An unbounded memoization cache in a long-lived SPA is a slow leak. Either cap it, key it weakly, or push caching into a layer that already handles eviction ([[24.7 - Caching Stale Time and Invalidation]]).

**They prefer factories to classes for stateful utilities.** No `this`, no binding, real privacy, and the result destructures cleanly. Classes still win when you need inheritance or many instances where prototype sharing saves memory.

## Common pitfalls

- Memoizing a function whose arguments are objects, using `JSON.stringify` keys, and silently caching by structural equality when identity was intended.
- Forgetting that memoized results are shared across all callers — including across users in a server-rendered context, which is a data-leak class bug.
- Creating a debounced function inside a React component body, producing a new one every render so the timer never accumulates. It must be memoized or created in a ref.
- Capturing a value that changes instead of a getter.
- Retaining large payloads in a closure attached to a long-lived listener.

## Interview angle

Machine-coding rounds ask for `memoize`, `once`, `debounce`, `throttle` and a concurrency limiter constantly. All five are closures over a small piece of mutable state. Write the closure, then volunteer the production concerns — cache eviction, cancellation, cleanup — because that is what separates a working answer from a hire-level one.
