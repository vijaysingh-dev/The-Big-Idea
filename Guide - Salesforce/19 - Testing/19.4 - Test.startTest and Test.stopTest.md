# Test.startTest and Test.stopTest

## Two jobs

**Reset governor limits**, so consumption is measured for the code under test rather than for the setup.

**Flush async work**, so queued jobs execute before the assertions run.

Both matter, and the second causes more confusion.

## Fresh limits

```java
@IsTest
static void handlerStaysWithinQueryLimits() {
    // setup: 50 assets, 200 claims — consumes queries and DML, not measured
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(assets, 200);

    Test.startTest();
    insert claims;

    // the counters were reset, so this measures the insert alone
    Assert.isTrue(Limits.getQueries() < 30,
        'Expected under 30 queries for 200 records, used ' + Limits.getQueries());
    Test.stopTest();
}
```

Without the reset, the assertion would include every query the factory made, and the number would be meaningless.

**Everything resets:** queries, query rows, DML statements, DML rows, CPU, heap, callouts, and async enqueues.

## Async flushing

```java
@IsTest
static void approvalSyncsToTheErp() {
    Test.setMock(HttpCalloutMock.class, new ErpSuccessMock());
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 120000);
    // the Queueable enqueued above executes at this line
    Test.stopTest();

    Warranty_Claim__c refreshed = [
        SELECT ERP_Sync_Status__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Synced', refreshed.ERP_Sync_Status__c);
}
```

**Assertions go after `Test.stopTest()`.** Before it, the job has not run and the assertion fails with the pre-async value — which is the single most common async testing mistake.

What flushes at `stopTest`:

```
Queueable jobs
@future methods
Batch Apex — the start, one execute, and finish
Scheduled Apex enqueued during the test
```

**Platform events do not flush automatically.** They need `Test.getEventBus().deliver()` explicitly. See [[19.6 - Testing Async Apex]].

## Batch: one chunk only

```java
@IsTest
static void archiveBatchDeletesClosedClaims() {
    TestDataFactory.createClosedClaims(250);

    Test.startTest();
    Database.executeBatch(new ClaimArchiveBatch(), 200);
    Test.stopTest();

    // only one chunk of 200 ran, not both
    Integer remaining = [SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Closed'];
    Assert.areEqual(50, remaining, 'One chunk of 200 was processed');
}
```

**Regardless of record count and scope size, exactly one `execute` runs in a test.**

That has a real consequence: **multi-chunk behaviour cannot be tested through `executeBatch`.** `Database.Stateful` accumulation, in particular, is invisible.

The workaround is calling `execute` directly:

```java
@IsTest
static void statefulCountersAccumulateAcrossChunks() {
    ClaimReconciliationBatch batch = new ClaimReconciliationBatch();
    List<Warranty_Claim__c> chunkOne = TestDataFactory.createClaims(5);
    List<Warranty_Claim__c> chunkTwo = TestDataFactory.createClaims(5);

    Test.startTest();
    // calling execute directly is the only way to exercise cross-chunk state
    batch.execute(null, chunkOne);
    batch.execute(null, chunkTwo);
    Test.stopTest();

    Assert.areEqual(10, batch.getProcessedCount(),
        'The counter should accumulate across chunks');
}
```

Passing `null` as the `BatchableContext` works as long as `execute` does not use it. Where it does — for `getJobId()` — the method needs a null guard or the context has to be mocked.

## Chaining: one level only

```java
public void execute(QueueableContext context) {
    processChunk();

    // the guard exists because a second chain level throws in test context
    if (!remaining.isEmpty() && !Test.isRunningTest()) {
        System.enqueueJob(new ClaimSyncQueueable(remaining));
    }
}
```

**A Queueable enqueued from within a Queueable does not run in a test**, and attempting to enqueue a second level throws.

The `Test.isRunningTest()` guard is the standard workaround, and it means the chaining logic itself is untested. Testing the chunking decision separately is the compensation:

```java
@IsTest
static void chunkingSplitsTheRemainderCorrectly() {
    List<Id> ids = TestIdFactory.generateMany(Warranty_Claim__c.SObjectType, 350);

    ClaimSyncQueueable job = new ClaimSyncQueueable(ids);

    Assert.areEqual(150, job.currentChunk().size(), 'The first chunk takes 150');
    Assert.areEqual(200, job.remainder().size(), 'The rest is carried forward');
}
```

## One pair per method

```java
// Throws
Test.startTest();
doSomething();
Test.stopTest();

Test.startTest();
doSomethingElse();
Test.stopTest();
```

`Test.startTest()` can be called **once** per test method, and cannot be nested.

Where a test needs two async flushes, it needs two test methods.

## What goes inside

```java
@IsTest
static void escalationAssignsTheRegionalDirector() {
    // Arrange — outside
    User director = TestUserFactory.createWithRole('Regional Director');
    Warranty_Claim__c claim = TestDataFactory.createClaim(900000);

    // Act — inside
    Test.startTest();
    ClaimRoutingService.route(new List<Warranty_Claim__c>{ claim }, null);
    Test.stopTest();

    // Assert — outside, after
    Warranty_Claim__c refreshed = [
        SELECT Approver__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual(director.Id, refreshed.Approver__c);
}
```

**Only the code under test goes between them.** Setup inside the block pollutes the limit measurement; assertions inside run before async work has flushed.

The exception is a limit assertion, which must be inside to read the reset counters — as in the first example above.

## Combining with runAs

```java
@IsTest
static void anAgentCannotApproveAnExecutiveTierClaim() {
    User agent = TestUserFactory.create('Support Agent', null);
    Warranty_Claim__c claim = TestDataFactory.createClaim(900000);

    Test.startTest();
    System.runAs(agent) {
        Database.SaveResult result = Database.update(
            new Warranty_Claim__c(Id = claim.Id, Status__c = 'Approved'), false
        );
        Assert.isFalse(result.isSuccess(),
            'An agent should not be able to approve an executive-tier claim');
    }
    Test.stopTest();
}
```

**`runAs` nests inside `startTest`**, not the other way round. The user creation happens before, since it needs its own `runAs` for the mixed-DML rule. See [[19.8 - Testing Security and Sharing]].

## What it does not do

Worth being explicit, because the method name suggests more than it delivers.

**It does not create a transaction boundary.** Everything is still one transaction, and DML before `startTest` is visible inside it.

**It does not reset static variables.** A recursion guard set during setup is still set. Tests depending on guard state need an explicit `reset()`. See [[11.6 - Recursion Control and Static Guards]].

**It does not isolate tests from each other.** Each test method is its own transaction and rolls back at the end; `startTest` has nothing to do with that.

**It does not make callouts work.** Mocks are still required.

## When to omit it

A test with no async and no limit assertion does not strictly need it.

```java
@IsTest
static void tierIsDerivedFromTheAmount() {
    Assert.areEqual('Executive', ApprovalTierService.tierFor(900000));
}
```

That is a complete, valid test. Adding `startTest` and `stopTest` around one pure function call adds nothing.

**Include them when:** async work is enqueued, limits are being asserted, or the setup is substantial enough that a fresh budget matters.

**Most teams include them by convention anyway**, which is harmless and makes the act phase visually obvious. Either position is defensible; consistency is worth more than the choice.

## A checklist

```
[ ] Setup before startTest
[ ] Only the code under test between them
[ ] Assertions after stopTest, when async is involved
[ ] Limit assertions inside, before stopTest
[ ] One pair per method
[ ] runAs nested inside, not outside
[ ] Batch multi-chunk logic tested by calling execute directly
[ ] Chained jobs guarded with Test.isRunningTest()
```

## Practical guidance

**Assertions after `stopTest`** when anything async is involved. This is the mistake to internalize.

**Limit assertions before `stopTest`**, since the counters reset at `startTest`.

**Keep setup outside** so it does not pollute the measurement.

**Expect one batch chunk**, and test cross-chunk logic by calling `execute` directly.

**Expect one chain level**, and guard the enqueue with `Test.isRunningTest()`.

**Nest `runAs` inside**, not outside.

**Remember statics do not reset** — reset guards explicitly.
