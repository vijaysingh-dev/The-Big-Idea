# Trigger and Async Questions

## The highest-frequency topic

Triggers come up in nearly every technical round, and async in most. These are the questions, with answers written as they should be delivered.

---

## Trigger fundamentals

**What are the trigger events, and how do you choose?**

Seven: before and after insert, update, and delete, plus after undelete. There is no before undelete.

The rule that decides most cases: **before triggers modify the record being saved; after triggers do everything else.** In a before trigger you assign to `Trigger.new` directly with no DML. In an after trigger it is read-only, so updating the same records needs a DML statement that re-enters the entire save pipeline.

The two things only after can do: see the record Id on insert, and access fields the platform populates on save — auto-numbers, formulas, roll-ups.

The inconsistency worth knowing: relationship traversal fails in before insert. `claim.Asset__r.SerialNumber` is null even when `Asset__c` is populated, because the record was never saved. It works in after insert. That catches people constantly, and the fix is querying the parents explicitly.

**Why one trigger per object?**

Because execution order between triggers on the same object is undefined. Salesforce does not guarantee it, does not expose a setting, and can change it.

The failure is specific: one trigger sets a tier, another routes based on it. If routing runs first it reads a stale value. Nothing errors, the sandbox works, and the order can change after any deployment.

With one trigger, ordering is the order of statements in the handler — explicit and controllable.

The other reasons follow: one place to look, one recursion guard, one bypass switch, and one query budget rather than each trigger querying independently.

**Describe the handler pattern.**

Trigger declares events and calls the handler. Handler reads `Trigger` context and dispatches by event. Service does the work, taking collections.

The rule that makes it worth the files: **nothing below the handler references `Trigger`**. That means the same service runs from a batch job, a flow action, a REST endpoint, and a test with constructed records.

I would put a bypass check at the top of the handler — a hierarchy Custom Setting, so an administrator can disable automation for one profile during a data load or an incident without a deployment. And I would test the bypass, because an untested one is the one you discover does not work during the incident.

## The classic defects

**Why would a perfectly bulkified trigger still hit the query limit?**

Because the budget is shared. Your trigger, other triggers, every flow on the object, validation rules with cross-object formulas, roll-up recalculation on parents, and any managed package all spend from the same 100 queries.

A record-triggered flow with one Get Records element, firing on a save of 200 records, issues up to 200 queries on its own. Your code can be perfect and still fail.

The diagnostic is the per-namespace limit block in the debug log, and the fix is auditing what actually runs on the object rather than optimizing your code further.

**An after-update trigger creates a payment when status becomes Approved. Finance reports duplicates. Why?**

No comparison against `Trigger.oldMap`.

```java
// fires on every save of an approved claim
if (claim.Status__c == 'Approved') { }

// fires once, on the transition
if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') { }
```

Any subsequent edit — a note added, a field corrected, a roll-up recalculating — re-runs the trigger and creates another payment.

The reason it takes months to surface is that an approved claim is not usually edited again. The affected records are the ones that were.

The test that catches it: approve, then make an unrelated edit, and assert there is still one payment.

**A recursion guard uses `private static Boolean hasRun`. A 400-record load processes 200. Explain.**

A static persists for the whole transaction. The load arrives as two chunks of 200; the first sets the flag, the second returns immediately.

No error, no log entry — 200 records silently unprocessed, discovered weeks later by someone reconciling data.

The fix is tracking which record Ids have been processed, per context key, rather than whether the handler ran. And the test that proves it: update one set, insert a second distinct set in the same transaction, and assert both were processed. A boolean guard passes the first assertion and fails the second.

**Inserting 200 child records causes a CPU limit failure. The child trigger is twenty lines. Explain.**

The cascade at roll-up recalculation. Each child insert recalculates the parent's roll-up, which sends the parent through its own save pipeline — its triggers, its flows — which may update its own parent, and so on.

One insert can run four objects' automation, all against the same CPU budget.

The diagnostic is nested `DML_BEGIN` blocks in the debug log; each nesting level is a cascade level. Four deep on one user action is an org where automation accumulated without an owner.

The fixes are architectural: fewer roll-ups on hot parents, updating only records whose values actually changed — which stops the cascade where nothing needs updating — and moving non-urgent aggregation to a scheduled job.

**A roll-up is correct on insert and update but wrong after a record is restored from the recycle bin.**

No `after undelete` handler. Undelete restores the record and the aggregate must be recomputed; omitting it leaves the parent's count permanently low.

The related bug is usually present too: the handler collects only the new parent's Id, so a reparented child leaves the old parent stale. Both parents need recalculating.

## Async

**Why does async exist?**

Four reasons. A callout cannot follow DML in the same transaction. Each async execution is a new transaction with a fresh limit budget. Batch Apex is the only way to touch millions of records. And users should not wait for work they do not need.

The framing that matters: **async is not a way to avoid limits, it is a way to get more transactions.** That is why "move it to a Queueable" answers so many limit problems.

**Walk me through the async options.**

Queueable is the general-purpose default — any parameter type, a job Id for monitoring, chaining with guaranteed order, and Transaction Finalizers for retry and failure logging.

Batch Apex above a few thousand records, because it chunks automatically with proper monitoring rather than depending on your chunking logic.

Scheduled Apex for clock-driven work, and the scheduler class should do nothing but start a batch — partly because a scheduled class cannot be modified while scheduled, so keeping it trivial avoids blocking deployments.

Platform events for decoupling, where several independent consumers should react and adding a fourth requires no change to the publisher.

Continuations only where a user is waiting on a slow external call. That is narrow, and most orgs never need one.

Future methods are legacy — Queueable does everything they do with more capability, and the only surviving case is that it is marginally less code for the mixed-DML workaround.

**When would you choose Batch over a Queueable chain?**

Above a few thousand records. Batch chunks automatically, gives per-chunk monitoring, and each chunk has a fresh limit budget with 100 callouts available.

A Queueable chain means writing the chunking yourself, and a chain with no termination condition runs until the org's daily async allocation is exhausted — which affects every other job in the org, not just yours.

**What is a Transaction Finalizer for?**

It is the only guaranteed post-execution hook in async Apex. It runs after a Queueable completes, in its own transaction, whether the job succeeded or failed — including on an uncatchable `LimitException`.

That solves two things. Logging a failure durably, because the finalizer's transaction is separate so a plain insert survives. And retry, because it can enqueue another job.

The retry logic that matters is distinguishing transient from permanent. Retrying a validation failure three times achieves nothing and burns the async allocation; retrying a timeout usually succeeds. Plus a maximum attempt count and backoff, because retrying immediately against a system that is down makes the outage worse.

Only Queueable supports finalizers, which is the strongest practical argument for it over future.

## Async testing

**How does async behave in a test?**

`Test.stopTest()` flushes queued async work — Queueables, future methods, and one batch chunk run at that point.

The consequence people get wrong: assertions go **after** `stopTest`, not before. Before it, the job has not run.

Three constraints worth knowing. Exactly one batch chunk executes regardless of record count, so multi-chunk behaviour and `Database.Stateful` accumulation cannot be tested through `executeBatch` — you call `execute` directly for that. Only one chained level runs, which is why chained jobs carry a `Test.isRunningTest()` guard. And platform events do not flush automatically — `Test.getEventBus().deliver()` is required, and omitting it produces a passing test where the subscriber never ran.

**How do you test a callout?**

`Test.setMock` with an `HttpCalloutMock`, registered before the callout.

But for testing a service's logic, mocking the HTTP layer tests more than intended. I would put the client behind an interface and substitute a stub, so the service test verifies the logic with no HTTP involved. Then a separate `HttpCalloutMock` test on the client itself verifies request construction and response parsing.

And I would test the failure paths — a 500, a timeout, a malformed body. Those are the paths that actually run in production and the ones most often untested.

## Platform events

**When would you use a platform event over a Queueable?**

When there are several independent consumers, particularly ones added over time. A claim approval publishing one event, with the ERP notification, the Slack post, and the audit log as three subscribers, means adding a fourth requires no change to the publisher.

For a single consumer in the same org, a Queueable is simpler, synchronous in ordering, traceable in the code, and testable without event delivery. Events are indirection, and indirection should buy something.

**What do you have to design for with events?**

Idempotency, primarily. Delivery is at-least-once, so a subscriber can receive the same event twice. An upsert on a unique key is the standard mechanism — without it, a redelivery produces a duplicate payment, which is the failure finance reports rather than testing.

Then the publish behaviour: after-commit for business events, so a rolled-back approval publishes nothing. Immediate for failure logging, which is the one case where surviving rollback is the point.

And `setResumeCheckpoint` in the subscriber, so a retry resumes from the failing event rather than reprocessing the whole batch — which for a non-idempotent handler creates duplicates.

The other thing to know is that the delivery allocation counts per subscriber. Five external systems on one event is five deliveries, so adding consumers multiplies consumption.

## The scenario question

**Design the trigger architecture for an object with validation, defaults, a roll-up, approval submission, and an ERP notification.**

One trigger declaring the events, calling one handler. The handler checks a bypass, then dispatches by operation type.

Before insert and before update: derived fields and validation. Both need to run before the record saves, and validation belongs there so `addError` blocks the record without a second save.

After insert and after update: roll-up recalculation, because it needs the Id; approval submission, comparing against `oldMap` so it fires on the transition; and the ERP notification, which is **enqueued rather than called**, because a callout cannot follow DML.

After delete and after undelete: roll-up recalculation, using a method that collects both the old and new parent so reparenting is handled.

Every service takes collections and tolerates a null prior map, so the same method serves insert and update.

The details I would call out: the bypass at the top for migrations and incidents, change detection in the service rather than the handler so the handler stays a readable list of what runs when, and the enqueue for the callout with a Finalizer for retry.

## What is being assessed

**Junior:** knows the events, writes a bulkified trigger, knows one trigger per object.

**Mid:** knows why order is undefined, uses `oldMap` for change detection, chooses the right async mechanism.

**Senior:** raises the cascade, the shared budget, the boolean-guard trap, and idempotency without being asked.

**The strongest single answer** to almost any trigger question is one that mentions the shared limit budget — because it demonstrates understanding that your code is one line item among several, which is the thing that actually causes production failures.
