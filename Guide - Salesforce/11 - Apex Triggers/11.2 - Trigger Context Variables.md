# Trigger Context Variables

## The full set

```java
Trigger.new          List<SObject>       records being saved, with new values
Trigger.old          List<SObject>       records as they were before this save
Trigger.newMap       Map<Id, SObject>    keyed on record Id
Trigger.oldMap       Map<Id, SObject>    keyed on record Id

Trigger.isExecuting   Boolean            true inside a trigger context
Trigger.isInsert      Boolean
Trigger.isUpdate      Boolean
Trigger.isDelete      Boolean
Trigger.isUndelete    Boolean
Trigger.isBefore      Boolean
Trigger.isAfter       Boolean
Trigger.operationType TriggerOperation   an enum covering all seven events
Trigger.size          Integer            number of records
```

## Availability by event

This table is the thing worth memorizing, because using an unavailable variable throws.

| Event | `new` | `newMap` | `old` | `oldMap` |
| --- | --- | --- | --- | --- |
| before insert | yes, writable | **null** | null | null |
| after insert | yes, read-only | yes | null | null |
| before update | yes, writable | yes | yes | yes |
| after update | yes, read-only | yes | yes | yes |
| before delete | null | null | yes | yes |
| after delete | null | null | yes | yes |
| after undelete | yes, read-only | yes | null | null |

Two entries cause most of the confusion:

**`Trigger.newMap` is null in before insert**, because the records have no Ids yet and a map needs keys. Code written for update and reused for insert breaks here.

**`Trigger.new` is null in delete contexts.** Delete handlers use `Trigger.old`.

## Writability

`Trigger.new` records are **writable in before triggers and read-only in after triggers**.

```java
// before update: assign directly, no DML
for (Warranty_Claim__c claim : Trigger.new) {
    claim.Region__c = deriveRegion(claim);
}

// after update: this throws
for (Warranty_Claim__c claim : Trigger.new) {
    claim.Region__c = 'EMEA';   // FIELD_INTEGRITY_EXCEPTION
}
```

`Trigger.old` is always read-only, in every context.

## Change detection

The single most important use of `Trigger.oldMap` — running logic only when a field actually changed.

```java
public with sharing class ClaimService {

    public static void handleStatusChanges(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) {
        List<Warranty_Claim__c> newlyApproved = new List<Warranty_Claim__c>();

        for (Warranty_Claim__c claim : newClaims) {
            Warranty_Claim__c prior = oldClaims.get(claim.Id);

            // comparing against the prior value means this fires once, on the transition
            if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') {
                newlyApproved.add(claim);
            }
        }

        if (newlyApproved.isEmpty()) {
            return;
        }

        ClaimPaymentService.createPayments(newlyApproved);
    }
}
```

Without the comparison, this creates a payment every time anyone edits an already-approved claim. The bug is silent, produces duplicate financial records, and is found by finance rather than by testing.

**Every after-update handler should ask: does this need to fire on every save, or only on a transition?** The answer is almost always the transition.

## Passing context to services

The pattern this course uses throughout: the handler reads `Trigger` context, the service takes plain collections.

```java
// Handler: the only place Trigger is referenced
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (Trigger.isBefore && Trigger.isUpdate) {
            ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
        }
        if (Trigger.isAfter && Trigger.isUpdate) {
            ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
        }
    }
}

// Service: no Trigger reference, so it is callable from anywhere
public with sharing class ClaimService {

    public static void handleStatusChanges(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) { }
}
```

That separation is what makes the service testable with constructed records, callable from a batch job, and reusable from a flow action. A service reading `Trigger.new` directly can only ever run inside a trigger. See [[11.5 - Trigger Handler Pattern]].

## Handling the null oldMap

A service taking `oldClaims` must tolerate null, because it will be called from insert contexts too.

```java
for (Warranty_Claim__c claim : newClaims) {
    Warranty_Claim__c prior = oldClaims == null ? null : oldClaims.get(claim.Id);

    Boolean isNewlyApproved = claim.Status__c == 'Approved'
        && (prior == null || prior.Status__c != 'Approved');
}
```

Treating "no prior record" as "the value changed" is usually correct for insert — a claim created as Approved is newly approved.

## operationType

An enum covering all seven events, which makes a switch cleaner than a chain of boolean checks.

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        switch on Trigger.operationType {
            when BEFORE_INSERT {
                ClaimService.applyDefaults(Trigger.new);
            }
            when BEFORE_UPDATE {
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
            }
            when AFTER_INSERT {
                ClaimService.createInitialParts(Trigger.new);
                ClaimRollupService.recalculate(assetIds(Trigger.new));
            }
            when AFTER_UPDATE {
                ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
                ClaimRollupService.recalculate(affectedAssetIds(Trigger.new, Trigger.oldMap));
            }
            when BEFORE_DELETE {
                ClaimService.preventDeletionOfSettled(Trigger.old);
            }
            when AFTER_DELETE {
                ClaimRollupService.recalculate(assetIds(Trigger.old));
            }
            when AFTER_UNDELETE {
                ClaimRollupService.recalculate(assetIds(Trigger.new));
            }
        }
    }
}
```

The enum values are `BEFORE_INSERT`, `BEFORE_UPDATE`, `BEFORE_DELETE`, `AFTER_INSERT`, `AFTER_UPDATE`, `AFTER_DELETE`, `AFTER_UNDELETE`.

The switch form makes the complete set of handled events visible in one place, and the compiler will not warn about a missing case — but a reader can see immediately which are absent.

## Collecting parent Ids across old and new

A recurring need: when a child's parent changes, both the old and new parent need recalculating.

```java
public static Set<Id> affectedAssetIds(
    List<Warranty_Claim__c> newClaims,
    Map<Id, Warranty_Claim__c> oldClaims
) {
    Set<Id> assetIds = new Set<Id>();

    for (Warranty_Claim__c claim : newClaims) {
        if (claim.Asset__c != null) {
            assetIds.add(claim.Asset__c);
        }

        // a reparented claim leaves the old asset's aggregate stale unless it is included
        Warranty_Claim__c prior = oldClaims == null ? null : oldClaims.get(claim.Id);
        if (prior != null && prior.Asset__c != null && prior.Asset__c != claim.Asset__c) {
            assetIds.add(prior.Asset__c);
        }
    }
    return assetIds;
}
```

Forgetting the old parent is the most common bug in hand-rolled roll-ups. The record moves, the new parent's count goes up, and the old parent's count stays wrong forever.

## Trigger.size and bulk awareness

`Trigger.size` is the number of records in this execution — up to 200 for a bulk save.

It is occasionally useful for logging or for choosing a strategy at volume:

```java
if (Trigger.size > 100) {
    // defer expensive work rather than doing it inline
    System.enqueueJob(new ClaimEnrichmentQueueable(Trigger.newMap.keySet()));
} else {
    ClaimEnrichmentService.enrich(Trigger.new);
}
```

This is a legitimate pattern and it should be used sparingly — branching on size means two code paths to test, and the async path behaves differently enough that bugs hide in it.

## Trigger.isExecuting

True whenever code is running inside a trigger context, including in a class called from one.

```java
public static void doWork() {
    if (Trigger.isExecuting) {
        // called from a trigger — avoid work that would recurse
    }
}
```

Occasionally useful for a shared service that must behave differently inside a save. Mostly it is a design smell: a service needing to know whether it is in a trigger usually has the wrong responsibilities, and an explicit parameter is clearer.

## Practical guidance

**Memorize which context variables are null in which events.** `newMap` in before insert and `new` in delete are the two that catch people.

**Always compare against `oldMap`** in after-update logic, unless the work genuinely should run on every save.

**Handle null `oldMap`** in services shared between insert and update.

**Include the old parent** when collecting Ids for a roll-up recalculation.

**Pass collections to services**, never `Trigger` itself.

**Use `operationType` with a switch** for a readable handler.

**Assign directly to `Trigger.new` in before triggers.** Never DML the triggering records from an after trigger.
