# Communication Patterns

#backend #microservices #architecture

> **In one line:** A synchronous call couples your availability to theirs; an asynchronous message decouples it and gives you eventual consistency instead — and the choice is about what the caller needs, not about what is modern.

---

## The Idea

```
SYNCHRONOUS       caller waits for a response
                  A ──request──► B
                    ◄─response──

ASYNCHRONOUS      caller does not wait
                  A ──message──► [ broker ] ──► B
```

| | Synchronous | Asynchronous |
|---|---|---|
| Caller knows the result | **Yes** | No |
| Caller's availability depends on callee | **Yes** | No |
| Latency | Sum of the chain | Caller's own only |
| Consistency | Immediate | **Eventual** |
| Failure handling | Retry, timeout, circuit break | Broker handles delivery |
| Backpressure | Caller must handle it | **Queue absorbs it** |
| Debugging | One trace | Trace across a broker |

💡 **The decisive question: does the caller need the result to decide what to do next?**

If yes, synchronous. If no, asynchronous — and if you make it synchronous anyway, you have coupled your availability to a service whose answer you did not need.

---

## Synchronous

```python
user = await user_service.get(user_id)         # I need this to render the page
```

**Right when:**

| Situation | |
|---|---|
| The caller needs the value | A read that shapes the response |
| The user is waiting | An interactive request |
| The operation must be rejected on failure | Validation, authorisation |
| The result changes the caller's next step | |

⚠️ **Every synchronous call multiplies your failure probability.**

```
Service A: 99.9% available
Calls B (99.9%) and C (99.9%) synchronously
→ A's effective availability: 99.9% × 99.9% × 99.9% = 99.7%
```

💡 **A chain of four services at 99.9% each gives you 99.6%** — from 43 minutes of downtime per month to nearly three hours. **Availability multiplies downward through synchronous dependencies**, and this arithmetic is the strongest argument for asynchronous where it is possible.

### The chain problem

```
Gateway → Documents → Users → Billing
```

```
Latency:      sum of all four
Availability: product of all four
Blast radius: billing down = gateway down
```

⚠️ **Depth is worse than breadth.** Four services called in parallel add one round trip; four in a chain add four ([[05.10 - Federation and Schema Composition]]).

💡 **Flatten chains where you can.** If the gateway needs data from three services, call them in parallel rather than letting each call the next.

```python
async with asyncio.TaskGroup() as tg:
    doc = tg.create_task(document_service.get(doc_id))
    user = tg.create_task(user_service.get(user_id))
    org = tg.create_task(billing_service.get_org(org_id))
```

### Making it survivable

Every synchronous call needs all four:

```python
async def get_user(user_id: str) -> User | None:
    if breaker.is_open():
        return None                                  # degrade
    try:
        async with asyncio.timeout(remaining_budget()):
            return await client.get(f"/users/{user_id}")
    except (TimeoutError, ConnectionError):
        breaker.record_failure()
        return None                                  # ← degrade, do not propagate
```

| Requirement | |
|---|---|
| **Timeout** | Bounded by the remaining request budget ([[03.11 - Timeouts and Deadlines Across Hops]]) |
| **Retry** | Only for idempotent calls, with jitter ([[03.4 - Idempotency and Safe Retries]]) |
| **Circuit breaker** | Fail fast when the callee is down ([[11.3 - Circuit Breakers and Bulkheads]]) |
| **Degradation** | What the caller does without the answer ([[11.6 - Graceful Degradation]]) |

⚠️ **The fourth is the one people skip.** A caller that propagates the failure has just made an optional dependency mandatory.

💡 **Decide, per call, whether the dependency is required or optional**, and write it in the code:

```python
author = await user_service.get(doc.author_id, required=False)
title = author.name if author else "Unknown author"
```

**An optional dependency being down should degrade one field, not fail the request.**

## Asynchronous

```python
await publish("document.indexed", event)       # I do not need to know who cares
```

**Right when:**

| Situation | |
|---|---|
| The caller does not need the result | Notifications, indexing, analytics |
| Multiple consumers, or unknown consumers | Events ([[09.2 - Event Modeling]]) |
| The work is slow | Do not hold a request open |
| The consumer may be down | The broker holds it |
| Load spikes must be absorbed | The queue is the buffer |

### Commands versus events

```
COMMAND   "index this document"      → one handler, a queue
EVENT     "this document was indexed" → many consumers, a log
```

💡 **The distinction determines the infrastructure** ([[09.1 - Queue vs Log]]), and it determines the coupling. A command means the producer knows who handles it; an event means it does not.

⚠️ **Publishing a command as an event is a common mistake** — it looks decoupled and it is not, because the producer still depends on exactly one consumer existing.

### The cost: eventual consistency

```python
await documents.create(doc)
await publish("document.created", event)
return {"id": doc.id}

# The user immediately searches. The index has not caught up.
```

⚠️ **Every asynchronous boundary introduces a window where the system is inconsistent**, and the user can observe it.

| Mitigation | |
|---|---|
| **Show the state honestly** | "Indexing..." rather than pretending it is done |
| **Read-your-writes** | Return the local state, not the derived one ([[06.12 - Replication and Failover]]) |
| **Make the window small** | Sub-second is usually invisible |
| **Design the UI for it** | Optimistic updates, progress indicators |

💡 **Users tolerate eventual consistency they can see and are confused by consistency they cannot predict.** A progress indicator is better than a page that sometimes shows the document and sometimes does not.

## Choreography versus Orchestration

Two shapes for a multi-step process across services.

### Choreography — each service reacts

```
document.created  →  [ingestion] → document.extracted
                                 →  [chunker] → document.chunked
                                              →  [indexer] → document.indexed
```

| | |
|---|---|
| **Good** | No coordinator. Services stay decoupled. Adding a step is a new subscriber |
| **Bad** | **No single place shows the state.** "Where is document 42" requires searching logs |

⚠️ **Choreography makes the process implicit.** Nobody can read the code and see the workflow, because it is distributed across four services' subscriptions.

### Orchestration — a coordinator drives

```python
async def ingest(document_id: str):
    text = await ingestion.extract(document_id)
    chunks = await chunker.chunk(text)
    await indexer.index(document_id, chunks)
```

| | |
|---|---|
| **Good** | **The process is visible in one place.** Debuggable, testable, has state |
| **Bad** | The coordinator knows all the participants |

💡 **Orchestration is almost always right for a business process** and choreography for event fan-out.

**The test: does anyone need to know the state of the whole process?** If yes — "where is this order", "did this document finish indexing" — orchestration, because that question has an answer only if something is tracking it ([[08.11 - Durable Workflows and Sagas]]).

⚠️ **Choreography for a process with compensation is very hard.** Undoing three steps that nobody coordinated requires each service to know about the others' failures — which is orchestration, badly.

## Request-Reply Over a Broker

The hybrid that occasionally makes sense.

```python
correlation_id = str(uuid4())
await publish("commands", command, reply_to="replies", correlation_id=correlation_id)
response = await wait_for_reply(correlation_id, timeout=5)
```

⚠️ **This is synchronous coupling with asynchronous machinery** — the caller still waits, still needs a timeout, still fails if the consumer is down. **You have the latency of a broker and the coupling of a direct call.**

💡 **Almost always, either make it a direct call or make it genuinely asynchronous.** The legitimate case is when you need the broker's load balancing or backpressure and cannot get it another way — which usually means you should fix the load balancing instead.

## In Production

### The pattern per interaction

| Interaction | Pattern |
|---|---|
| Gateway needs user data to render | **Sync**, optional, degrade to "Unknown" |
| Gateway needs authorisation | **Sync**, required, fail closed |
| Document created → index it | **Async event** |
| Document created → notify collaborators | **Async event** |
| Checkout needs to charge a card | **Sync**, required |
| Usage recorded → billing aggregation | **Async event** |
| Ingestion pipeline steps | **Async, orchestrated** |
| Search query → search service | **Sync**, required |

💡 **Write this table for your own system.** Every row that is synchronous and required is a service whose downtime is your downtime — and seeing them listed makes the availability arithmetic concrete.

⚠️ **"Sync, required" should be a short list.** Authorisation, payment, and the primary read path. Everything else should degrade.

### Measuring the coupling

```python
service_call_total.labels(source=s, target=t, sync=True, required=True).inc()
service_call_duration.labels(source=s, target=t).observe(elapsed)
service_call_failures.labels(source=s, target=t, degraded=bool).inc()
```

💡 **`degraded=True` versus `degraded=False` on failures is the metric that tells you whether your degradation actually works.** A required-dependency failure that propagates should be rare and alarming; an optional one that degrades should be routine.

**Compute your effective availability:**

```python
effective = product(availability[dep] for dep in required_sync_dependencies)
```

⚠️ **If that number is below your SLO, the architecture cannot meet it** regardless of how reliable each service is. That calculation belongs in your SLO document ([[12.2 - SLI SLO and Error Budgets]]).

### The async traps

| Trap | |
|---|---|
| **Fire and forget with no durability** | The message is lost if the broker is unreachable ([[09.3 - The Outbox Pattern]]) |
| **No dead letter handling** | Failures vanish ([[08.6 - Retries Backoff and Dead Letters]]) |
| **Non-idempotent consumers** | At-least-once corrupts state ([[07.5 - Idempotency Keys and Deduplication]]) |
| **Ordering assumed and not guaranteed** | ([[08.2 - Queue Semantics]]) |
| **No visibility into the async work** | The user cannot see what is happening |
| **Trace context dropped at the broker** | Debugging becomes archaeology ([[12.3 - Instrumenting Conduit End to End]]) |

⚠️ **The last one is the most commonly missed and the most painful.** A trace that ends at "published to Kafka" tells you nothing about what happened next.

```python
carrier = {}
TraceContextTextMapPropagator().inject(carrier)
await publish(topic, payload, headers=carrier)
```

### The synchronous checklist

For every synchronous call between services:

```
□  Timeout, derived from the remaining request budget
□  Retry only if idempotent, with jitter
□  Circuit breaker
□  Required or optional, decided and written down
□  Degradation path if optional
□  Trace context propagated
□  The call counted toward your effective availability
```

### Conduit's communication map

```
Browser ──GraphQL──► Gateway
                       │
                       ├──gRPC, sync, required──► Documents      (the primary read)
                       ├──gRPC, sync, optional──► Search         (degrade: no results)
                       └──gRPC, sync, required──► Auth           (fail closed)

Documents ──event──► Kafka ──► Indexer
                            ──► Notifier
                            ──► Analytics
                            ──► Billing usage

Ingestion: orchestrated internally, async between stages
```

💡 **Only two synchronous required dependencies**, and one of them is authorisation, which must be. **Search is optional and degrades to "search is temporarily unavailable"** rather than failing the page.

⚠️ **Everything else is an event**, which means the notifier, the analytics pipeline and billing can all be down without any user-visible effect beyond delay.

**That distribution is what a well-shaped system looks like**, and the availability arithmetic reflects it: the effective availability is dominated by two services, not seven.

## Codebase

**Repo:** `GoogleCloudPlatform/microservices-demo`, `saleor/saleor`, `onyx-dot-app/onyx`

**Question to answer:** In Online Boutique, which calls are synchronous and required, and what happens when each dependency fails? Then: how does Onyx split synchronous request handling from asynchronous ingestion?

**Read, in order:**

1. `microservices-demo/src/frontend/handlers.go` — **the fan-out from the gateway.** Which calls are parallel, which are sequential, and what the error handling does. **Note whether any failure degrades rather than propagating**
2. `microservices-demo/src/checkoutservice/main.go` — **a chain of five synchronous calls.** Compute the effective availability and note what happens if the email service fails after the payment succeeds
3. `saleor/saleor/plugins/manager.py` — how Saleor dispatches to plugins and webhooks. **Synchronous plugin calls versus asynchronous webhooks**, and the reasoning
4. `onyx/backend/onyx/server/` versus `onyx/backend/onyx/background/` — **the sync/async split in a real ingestion product**, which is Conduit's exact shape
5. `microservices-demo/istio-manifests/` — retry and timeout policy at the mesh layer, and how it interacts with application-level handling

💡 The checkout service is the instructive read: **it calls payment, then shipping, then email, synchronously, with no compensation.** If email fails after payment succeeds, the customer is charged and receives nothing. **Finding that failure mode in a Google reference architecture is a good lesson in how easy it is to miss.**

**Size:** 1–2 sessions.

**Part 1 — Availability multiplication, measured.** Four services, each with an injectable failure rate.

Configure each at 99.9%. **Run 100,000 requests through a chain of four and through four in parallel.**

Measure end-to-end success rate for both. **Confirm the chain is worse than any individual service**, and confirm parallel is the same success rate with a quarter of the latency.

**Chart success rate and p99 latency against chain depth from 1 to 6.**

**Part 2 — Degradation, measured.** The same four-service call, with two dependencies marked optional.

Take each dependency down in turn. For each measure: requests failed, requests degraded, and **what the user actually sees.**

**Then remove the degradation handling and measure again.** The difference between "one field says Unknown" and "the page is a 500" is the whole point.

**Part 3 — The consistency window.** Document creation publishing an event that the indexer consumes.

Measure the window from write to searchable, at p50, p99 and p99.9, under normal load and under 10× load.

**Then measure it during an indexer restart**, and during a broker restart.

**Write down the number you would put in your product documentation**, and confirm your UI handles the p99.9 case.

**Part 4 — Durability of the async path.** Fire-and-forget publishing versus the outbox.

Kill the process between the database commit and the publish, 1,000 times. **Count events lost in each** ([[09.3 - The Outbox Pattern]]).

Then take the broker down for five minutes under load and measure the same.

**Part 5 — Choreography versus orchestration.** The four-stage ingestion pipeline, implemented both ways.

For each, answer these operationally:

| Question | |
|---|---|
| Where is document 42 right now? | Measure time to answer |
| Which stage is failing most? | |
| Add a fifth stage | Measure the change required |
| Stage 3 fails — undo stages 1 and 2 | Measure lines of code |
| Reprocess one document from the start | |

**The "where is it" question should be seconds in one and minutes in the other.**

**Part 6 — Trace across the broker.** Instrument the full path: browser → gateway → document service → event → indexer → database.

**Confirm it appears as one trace.**

Then remove the header propagation at the publish, and **confirm the trace splits into two disconnected halves.** Screenshot both.

Then measure: with the broken trace, how long does it take to answer "why did this document take 40 seconds to index"?

**Part 7 — The communication map.** For every interaction in Conduit, decide the pattern and record: sync or async, required or optional, degradation path, and timeout budget.

**Then compute your effective availability** from the required synchronous dependencies, and compare it to your target SLO.

**If it does not meet the SLO, change the architecture** — usually by making a dependency optional — and recompute.

**Done when:**
- Your availability-versus-chain-depth chart shows the multiplication clearly
- Optional dependencies degrade to a field while required ones fail the request
- You know your p99.9 consistency window and your UI handles it
- Fire-and-forget lost events that the outbox did not
- "Where is document 42" is answerable in seconds under orchestration
- A broken trace is visibly two halves, and you measured the debugging cost
- Your effective availability calculation meets your SLO, or you changed the architecture
