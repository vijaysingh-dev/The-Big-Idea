# Distributed Locks Done Right

#backend #distributed-systems #coordination

> **In one line:** A distributed lock is a lease that can expire while you still think you hold it, so the only safe design is one where the protected resource rejects writes from a lock holder who has been superseded.

---

## The Idea

```python
if await redis.set("lock:sync:src_7", worker_id, nx=True, ex=30):
    try:
        await sync_source(src_7)
    finally:
        await redis.delete("lock:sync:src_7")
```

`SET NX EX` is atomic: set only if absent, with an expiry. One worker wins.

⚠️ **This code has three bugs, and they are the three bugs in every naive distributed lock.**

---

## Bug 1: Releasing Someone Else's Lock

```
Worker A acquires with a 30s TTL
Worker A is paused (GC, CPU starvation, network) for 35s
Lock expires. Worker B acquires it
Worker A resumes, runs its finally block, DELETES B's lock
Worker C now acquires it. B and C run concurrently
```

```lua
-- RELEASE: check ownership atomically
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

💡 **A Lua script is atomic in Redis** — the get and the delete happen with nothing in between. **A get-then-delete in application code has a window.**

⚠️ **Every distributed lock release must be ownership-checked.** The easiest of the three bugs to fix and the most commonly present.

---

## Bug 2: The Lock Expires While You Are Working

⚠️ **You cannot fix this by making the TTL longer.** A longer TTL means a crashed worker blocks everyone for longer, **and any TTL can be exceeded by a sufficiently long pause.**

### Lease renewal

```python
class Lease:
    async def __aenter__(self):
        if not await self.redis.set(self.key, self.owner, nx=True, ex=self.ttl):
            raise LockNotAcquired(self.key)
        self._task = asyncio.create_task(self._renew())
        return self

    async def _renew(self):
        while True:
            await asyncio.sleep(self.ttl / 3)
            if not await self.redis.eval(RENEW, 1, self.key, self.owner, self.ttl):
                self.lost.set()          # we no longer hold it
                return
```

```lua
-- RENEW: extend only if we still own it
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('expire', KEYS[1], ARGV[2])
end
return 0
```

**Renew at one third of the TTL**, so two consecutive failures still leave time to react.

💡 **The `lost` event is the important part.** Renewal failing means you no longer hold the lock — **your work must stop:**

```python
async with Lease(redis, key, worker_id) as lease:
    for item in items:
        if lease.lost.is_set():
            raise LockLost()          # stop immediately
        await process(item)
```

⚠️ **Most lock implementations renew and do not tell you when renewal fails.** That is worse than not renewing, **because you now believe you hold a lock you have lost.**

## Bug 3: You Cannot Actually Prevent Concurrency

The one that matters, and the one people resist.

```
Worker A holds the lock
Worker A's process is stopped by a GC pause / VM migration / CPU starvation
The lock expires
Worker B acquires it and begins writing
Worker A resumes — with no way of knowing time has passed — and writes
```

⚠️ **There is no code you can write inside worker A that prevents this.** A paused process cannot detect that it was paused. **Renewal helps, and it does not close the window between the last successful renewal and the pause.**

💡 **The conclusion: a distributed lock cannot guarantee mutual exclusion. It can only make concurrent execution unlikely.**

**This is the core of Kleppmann's critique of Redlock, and it applies to every lock built on timeouts — Redis, ZooKeeper, etcd, all of them.**

### Fencing tokens

The only actual fix. **The lock issues a monotonically increasing token, and the protected resource rejects stale tokens.**

```python
async def acquire_with_token(key: str, owner: str, ttl: int = 30) -> int | None:
    token = await redis.incr(f"{key}:fence")          # monotonic, never reused
    if await redis.set(key, f"{owner}:{token}", nx=True, ex=ttl):
        return token
    return None
```

```python
updated = await conn.fetchval(
    """UPDATE resources SET data = $1, fence_token = $2
       WHERE id = $3 AND fence_token < $2 RETURNING id""",
    data, token, resource_id,
)
if updated is None:
    raise FencedOut("a newer lock holder has already written")
```

```
Worker A: token 33, pauses
Worker B: token 34, writes → fence_token = 34
Worker A: resumes, writes with token 33 → 33 < 34 → REJECTED
```

💡 **The resource is now the source of truth about who is current, not the lock.** This works regardless of pauses, clock skew, or lock service failures — **and it is the only construction that does.**

⚠️ **Fencing requires the protected resource to support it.** A Postgres row can hold a `fence_token`; S3 can use conditional writes; **an external API you do not control usually cannot — and in that case you do not have mutual exclusion, and your design must tolerate double execution.**

**Say that out loud in a design review.**

---

## Redlock, and Why It Is Argued About

The multi-node algorithm: acquire on a majority of N independent Redis nodes within the TTL.

**Kleppmann's objection:** it depends on bounded clock drift and bounded process pauses, and neither is guaranteed.

**Antirez's response:** the assumptions are reasonable in practice, and Redlock is intended for efficiency, not correctness.

💡 **The resolution both sides agree on: if correctness depends on mutual exclusion, you need fencing tokens. If you only want to avoid wasted work, a simple lock is fine and Redlock is unnecessary complexity.**

⚠️ **Practical guidance: do not use Redlock.** Either you need correctness — use fencing tokens, and a single Redis instance suffices for the lock — or you do not, in which case a single-instance lock is simpler. **Redlock occupies a middle ground that does not really exist.**

---

## The Two Purposes

| Purpose | Requirement | Sufficient design |
|---|---|---|
| **Efficiency** | Avoid duplicate work | Single Redis lock. Occasional double execution is fine |
| **Correctness** | Must never execute twice | Fencing tokens, or a database constraint |

💡 **The strongest advice in this note: if your correctness depends on a distributed lock, restructure so it does not.** A unique constraint, an idempotency key, an optimistic version check or a compare-and-swap are all stronger than a lock and all simpler to reason about.

⚠️ **Locks are a coordination mechanism, not a correctness mechanism.** Treating them as the latter is the root of most distributed-locking incidents.

## The Alternatives, Which Are Usually Better

### Postgres advisory locks

```sql
SELECT pg_try_advisory_xact_lock(hashtext('sync:' || $1));
```

| Advantage over Redis | |
|---|---|
| **Released automatically on disconnect** | No TTL, no renewal, no expiry-while-working |
| Same transactional context as your data | Lock and work commit together |
| No extra infrastructure | |

💡 **`pg_try_advisory_xact_lock` is dramatically simpler than any Redis lock, and it is correct in a way Redis locks are not** — the lock is held by a connection, and if the process dies the connection drops and the lock releases immediately. **There is no window.**

⚠️ It requires a held connection, so session-level locks do not work through PgBouncer in transaction mode ([[06.9 - Connection Pooling and PgBouncer]]). **The `_xact_` variant is transaction-scoped and does work.**

**For anything already touching Postgres, this should be your first choice.**

### Unique constraints

```sql
INSERT INTO sync_runs (source_id, started_at) VALUES ($1, now())
ON CONFLICT (source_id) WHERE completed_at IS NULL DO NOTHING
RETURNING id;
```

Returns nothing if a run is already active. **Atomic, durable, and it survives every failure mode a lock does not.**

### `FOR UPDATE SKIP LOCKED`

For work distribution, this replaces locking entirely ([[06.6 - Transactions and Isolation Levels]]).

💡 **Most "we need a distributed lock" problems are actually work-distribution problems**, and `SKIP LOCKED` solves them without any lock at all.

### etcd / ZooKeeper

⚠️ **Still subject to the pause problem** — an ephemeral node disappears when the session expires, and a paused client does not know. **You still need fencing.** etcd's `revision` number serves as one, which is why it is the better choice when you genuinely need distributed coordination ([[07.6 - Leader Election and Coordination]]).

## In Production

### Choosing

```
Do you need correctness, or just efficiency?
├── Efficiency (avoid duplicate work)
│   ├── Already using Postgres?  → pg_try_advisory_xact_lock
│   └── Otherwise               → Redis SET NX EX with ownership-checked release
│
└── Correctness (must not happen twice)
    ├── Can you use a unique constraint?     → do that
    ├── Can you use an idempotency key?      → do that
    ├── Can the resource enforce a fence?    → lock + fencing token
    └── None of the above → you do not have mutual exclusion.
                             Design for double execution
```

⚠️ **The last branch is not a failure of imagination — it is an honest conclusion**, and stating it is far better than pretending a lock solved it.

### What a lock must have

```
□  TTL — always
□  Unique owner identifier, not a boolean
□  Ownership-checked release (Lua)
□  Renewal with loss notification
□  Fencing token, if correctness depends on it
□  Acquisition timeout
□  Metrics: acquisitions, contention, renewal failures, lost locks
```

```python
lock_lost_total.inc()          # ← alert on this
lock_fenced_out_total.inc()    # ← and this
```

💡 **`lock_lost_total` and `lock_fenced_out_total` being non-zero means concurrent execution actually happened.** They are the metrics that tell you whether your assumptions hold in production, **and almost nobody exports them.**

### The Redis eviction trap

⚠️ **A Redis instance with `allkeys-lru` can evict your lock key** ([[07.2 - Cache Strategies and Invalidation]]).

```
Lock acquired → memory pressure → the lock key is evicted → both workers running
```

**Never put locks in a cache instance with `allkeys-*` eviction.** Use a separate instance, or `volatile-lru` with careful TTL policy.

**This is a real and quietly common failure, invisible until it causes duplicate work.**

### Conduit's locking decisions

| Need | Mechanism | Why |
|---|---|---|
| One sync per source at a time | `pg_try_advisory_xact_lock` | Efficiency only; Postgres is already there |
| One worker per document during indexing | `FOR UPDATE SKIP LOCKED` | Work distribution, not locking |
| Preventing duplicate document creation | Unique constraint on `(org_id, content_hash)` | **Correctness — a constraint, not a lock** |
| Scheduled job leader | etcd lease, or a database row with a lease timestamp | [[07.6 - Leader Election and Coordination]] |

💡 **Only one of these is a lock, and it is the one where duplicate execution would merely be wasteful. That distribution is what a well-designed system looks like.**

## Codebase

**Repo:** `redis/redis`, `etcd-io/etcd`

**Question to answer:** In etcd, how does a lock's `revision` number provide fencing, and how does a lease expire? Then: in Redis, what makes `SET NX EX` atomic, and what happens to a lock key under memory pressure?

**Read, in order:**

1. `etcd/client/v3/concurrency/mutex.go` — **`Lock` and `unlockAndClose`.** It uses a **revision number** and waits for all lower revisions to be deleted. **The revision is a fencing token, provided by the system**
2. `etcd/client/v3/concurrency/session.go` — leases and keep-alive. **The session model is cleaner than Redis's TTL**: a session dies, all its ephemeral keys vanish
3. `redis/src/t_string.c` — `setGenericCommand` and the `NX`/`EX` flags. **Atomicity comes from Redis being single-threaded**
4. `redis/src/evict.c` — confirm that eviction does not distinguish locks from cache entries
5. `redis/src/script_lua.c` — why a Lua script is atomic: it runs to completion with no other command interleaved

💡 The etcd revision number is the detail worth internalising: **etcd gives you a fencing token for free, because every write increments a global revision.** Redis does not, which is why you must construct one with `INCR`. **That difference is a genuine argument for etcd when you need correctness-critical coordination.**

**Size:** 1–2 sessions.

## Exercise

**Drill 7.4 — Break every lock, then build one that holds**

```
drills/07-locks/
├── naive/{v1.py, v2.py, v3.py, v4.py, FINDINGS.md}
├── breaking/{crash.py, wrong_release.py, pause.py, eviction.py, RESULTS.md}
├── fencing/{tokens.py, resource.py, prove.py, RESULTS.md}
├── alternatives/{advisory.py, unique.py, skip_locked.py, etcd_lock.py, COMPARISON.md}
├── production/{lease.py, metrics.py, tests/}
└── README.md
```

**Part 1 — Four versions, four failures.**

| Version | Attack |
|---|---|
| `SET NX`, no TTL | Kill the holder. **Confirm the lock is held forever** |
| `+ TTL` | Delay a holder past the TTL. **Confirm two holders** |
| `+ ownership check` | Same delay. **Confirm the second holder's lock is not deleted** |
| `+ renewal` | `SIGSTOP` the holder past the TTL. **Confirm two holders still** |

**The fourth is the important one** — it demonstrates that renewal narrows the window and does not close it.

**Part 2 — The pause attack, properly.** Use `SIGSTOP`/`SIGCONT` to pause a worker mid-work for longer than the TTL.

**Confirm that when it resumes it believes it still holds the lock and writes.**

**Chart the probability of double execution against pause duration** at various TTLs.

⚠️ Then note that a real GC pause, VM migration or CPU starvation produces exactly this, **and you cannot prevent it from inside the process.**

**Part 3 — Fencing tokens.** Implement issuance and a resource that rejects stale tokens.

**Repeat the pause attack. Confirm the paused worker's write is rejected while the new holder's succeeds.**

Then implement it against three resources: a Postgres row with a `fence_token` column, a file with a version in its name, and an S3 object with a conditional write. **Note which resources can be fenced and which cannot.**

**Part 4 — The eviction trap.** Locks in a Redis instance with `allkeys-lru` and low `maxmemory`.

Drive memory pressure with cache writes. **Confirm a held lock is evicted and two workers proceed.** Then fix it two ways and confirm.

**Part 5 — Four alternatives.** The same "one sync per source" requirement with a Redis lock, a Postgres advisory lock, a unique constraint, and etcd.

Measure correctness under the pause attack, acquisition latency, behaviour when the coordination service is down, lines of code, and **behaviour when the holder crashes.**

**The advisory lock's crash behaviour should be notably better than Redis's, and the reason is worth stating.**

**Part 6 — The production lease.** TTL, unique owner, Lua release, renewal with a `lost` event, acquisition timeout, fencing tokens, full metrics.

Tests for: normal operation, contention, crash while holding, renewal failure, fenced-out write, acquisition timeout, and eviction. **Then run all four part-1 attacks and confirm it holds or fails loudly.**

**Part 7 — Restructure to remove the lock.** Take three places in Conduit where you might reach for a lock.

**For each, find a design that does not need one** — a constraint, `SKIP LOCKED`, an idempotency key, or an optimistic version check.

**Write down which lock-free design you chose and why it is stronger than the lock would have been.** This is the most valuable part of the drill, **because the best distributed lock is the one you did not need.**

**Done when:**
- All four naive versions are broken with a demonstrated failure
- Your pause-duration-versus-double-execution chart exists
- Fencing tokens demonstrably reject a resumed stale holder
- You know which of three resources can be fenced and which cannot
- A lock evicted under memory pressure caused duplicate execution, and you fixed it
- The four-alternative table includes crash and service-down behaviour
- You replaced three would-be locks with stronger lock-free designs
