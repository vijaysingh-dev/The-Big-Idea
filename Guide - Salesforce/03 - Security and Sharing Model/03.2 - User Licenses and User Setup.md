# User Licenses and User Setup

## The outermost ceiling

A user license is the first constraint on everything. No profile, permission set, or sharing rule can grant access beyond what the license permits.

This is why licensing appears in a security section rather than only in a commercial one. A design that assumes a user can see Cases fails immediately if that user holds a Platform license, and no amount of permission configuration will fix it.

## The main license types

**Salesforce.** Full access to all standard CRM objects and all custom objects. The most expensive, and what internal sales and service staff hold.

**Salesforce Platform.** Access to custom objects plus a restricted set of standard ones — Account, Contact, Activity, Report, Dashboard, Document, and a few others. Notably **excludes Lead, Opportunity, Case, Campaign, Forecast, Quote, Contract, Product**. Roughly a third of the cost, used for employees who need a custom internal application but not the CRM.

**Experience Cloud licenses.** For external users. Several variants:
- *Customer Community* — high volume, no roles, no reports; access is granted through Sharing Sets rather than the role hierarchy
- *Customer Community Plus* — adds roles, reports, and sharing rule participation
- *Partner Community* — adds access to Lead, Opportunity, and Campaign for channel partners

Licensed either per member (a fixed monthly count) or per login (a pool of logins consumed as used). The per-login model is what makes a million-customer portal economically possible.

**Chatter Free and Chatter External.** Collaboration only, no CRM data.

**Identity.** Single sign-on and identity services, no CRM data.

## Why the Platform license trap keeps happening

The failure pattern is consistent enough to be worth spelling out. A team designs an internal application on custom objects, correctly identifies that Platform licenses are much cheaper, and only afterwards discovers a requirement to show related Cases or link to Opportunities.

At that point the options are all bad: upgrade the licenses at several times the cost, duplicate the case data into a custom object and maintain a sync, or remove the requirement.

The check that prevents it: before committing to Platform licenses, list every standard object the application touches, including through related lists, reports, and lookup fields, and confirm each is available on that license.

```sql
SELECT Name, TotalLicenses, UsedLicenses, Status
FROM UserLicense
WHERE Status = 'Active'
ORDER BY Name
```

```sql
SELECT Id, Name, Profile.Name, Profile.UserLicense.Name, UserType, IsActive
FROM User
WHERE IsActive = true
ORDER BY Profile.UserLicense.Name
```

Running both on an unfamiliar org during discovery takes a minute and prevents the most expensive category of rework.

## Permission set licenses and feature licenses

Two additional layers people meet less often.

**Permission set licenses** grant access to specific features and are assigned alongside a permission set — for example CRM Analytics, Sales Console, or Service Cloud features. A permission set that requires one will not work without it.

**Feature licenses** are checkboxes on the user record enabling specific capabilities: Marketing User, Knowledge User, Service Cloud User, Salesforce CRM Content User, Flow User.

These cause a specific and confusing failure mode: a user has the right profile and the right permission set, and a feature still does not appear, because a checkbox on their user record is unticked. "Marketing User" is required to create Campaigns, and "Knowledge User" to work with Knowledge articles. Neither is granted by a profile.

## The User object

`User` is a standard object and behaves mostly normally, with some important exceptions.

Key fields: `Username` (must be unique across *all* of Salesforce globally, not just your org), `Email`, `Alias`, `ProfileId`, `UserRoleId`, `ManagerId`, `IsActive`, `TimeZoneSidKey`, `LocaleSidKey`, `LanguageLocaleKey`, `UserType`.

`Username` being globally unique is why sandbox usernames get a suffix appended. It is also why organizations use a convention like `firstname.lastname@company.com.prod` rather than the real email address.

**Users cannot be deleted.** Ever. They are deactivated by setting `IsActive = false`, which frees the license for reassignment. This is deliberate — every record in the org references users through `OwnerId`, `CreatedById`, and `LastModifiedById`, and deleting them would break referential integrity across the entire database.

Deactivation has consequences worth knowing: the user disappears from role hierarchy access calculations, their records remain owned by them (so a reassignment step is usually needed), and any approval processes routed to them stall.

**User is a setup object.** This means you cannot perform DML on User and on a normal object in the same transaction. Attempting it throws `MIXED_DML_OPERATION`, and the standard workaround is to move one of the two into an async context. See [[10.7 - Mixed DML and Setup Objects]].

```java
// Throws MIXED_DML_OPERATION
insert new Account(Name = 'Northwind');
insert new User(...);

// Correct: the setup object DML happens in a separate transaction
insert new Account(Name = 'Northwind');
UserProvisioningService.createUserAsync(userDetails);

public with sharing class UserProvisioningService {
    @future
    public static void createUserAsync(String serializedUser) {
        User u = (User) JSON.deserialize(serializedUser, User.class);
        insert u;
    }
}
```

## Reading the running user in code

```java
Id userId = UserInfo.getUserId();
Id profileId = UserInfo.getProfileId();
String userType = UserInfo.getUserType();      // Standard, PowerPartner, CspLitePortal, etc.
String locale = UserInfo.getLocale();
String timeZone = UserInfo.getTimeZone().getID();
Boolean isMultiCurrency = UserInfo.isMultiCurrencyOrganization();
```

`getUserType()` is genuinely useful when code must behave differently for internal versus Experience Cloud users — for example, hiding internal-only detail from a partner portal.

## Delegated administration and permission delegation

Two mechanisms that come up in larger orgs.

**Delegated Administrators** can be granted the ability to manage users within specified roles, assign a restricted set of profiles, and manage specific custom objects — without being given full System Administrator rights. This is how a regional manager can reset passwords for their own team without holding org-wide power.

**Permission set groups with muting** allow a group to combine several permission sets and then *remove* specific permissions from the combination. This is the only place in the permission model where something behaves like a deny, and it exists because combining permission sets additively sometimes grants more than intended. See [[03.4 - Permission Sets and Permission Set Groups]].

## Practical guidance

**Never give System Administrator to solve a problem.** It works, and it removes any ability to reason about the actual permission needed. It is also the finding auditors look for first.

**Audit admin count regularly.** Most orgs have several times more System Administrators than they need, usually because it was the fastest fix at some point.

```sql
SELECT Id, Name, Email, LastLoginDate
FROM User
WHERE Profile.PermissionsModifyAllData = true AND IsActive = true
```

**Deactivate promptly, and plan the record reassignment.** A departed user still owning 400 open opportunities is both a security issue and an operational one.

**Set the Manager field.** Approval processes route by it, hierarchical custom settings resolve by it, and both fail silently when it is empty.

**Check feature licenses when a feature mysteriously does not appear.** It is the checkbox, more often than not.
