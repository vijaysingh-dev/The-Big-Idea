# Compression and Streaming Responses

#backend #http #performance #streaming

> **In one line:** Compression trades CPU for bandwidth and is almost always worth it, streaming trades total throughput for time-to-first-byte, and combining them naively opens a security hole.

---

## Compression

### How it is negotiated

```http
GET /documents HTTP/1.1
Accept-Encoding: gzip, br, zstd

HTTP/1.1 200 OK
Content-Encoding: br
Vary: Accept-Encoding
```

⚠️ **`Vary: Accept-Encoding` is mandatory when you compress.** Without it, a cache may store the compressed response and serve it to a client that did not ask for compression, which sees binary garbage. Most servers add it automatically; verify yours does.

### The algorithms

| Algorithm | Ratio | Compress speed | Decompress | Use for |
|---|---|---|---|---|
| `gzip` | Baseline | Fast | Fast | Universal fallback |
| `br` (Brotli) | 15–25% better | Slower at high levels | Fast | Text over HTTPS |
| `zstd` | Similar to br | **Much** faster | Very fast | Internal traffic, high throughput |
| `deflate` | Like gzip | Fast | Fast | Avoid — implementations disagree |

💡 **The practical picks: Brotli for browser-facing text, zstd for service-to-service, gzip as the fallback.** zstd's advantage is compression *speed* — it reaches gzip's ratio at a fraction of the CPU, which matters when you compress every internal response.

### Levels

```python
gzip: 1–9        # 6 is the usual default
br:   0–11       # 11 is very slow. 4–5 for dynamic content
zstd: 1–22       # 3 is the default and is usually right
```

⚠️ **Brotli level 11 is for static files compressed once at build time.** Using it on dynamic responses will cost more CPU than the bandwidth is worth — often 100× the time of level 4 for a few percent better ratio.

```
Brotli on a 100KB JSON response:
  level 4   →  8ms,  22KB
  level 11  →  400ms, 20KB
```

Level 4 or 5 for anything generated per request.

### What not to compress

| Content | Why |
|---|---|
| JPEG, PNG, WebP, MP4 | Already compressed. You add CPU and bytes |
| Anything under ~1KB | Header and framing overhead exceeds the saving |
| Already-encrypted payloads | Random data does not compress |

```nginx
gzip on;
gzip_min_length 1024;
gzip_types application/json text/plain text/css application/javascript;
gzip_comp_level 5;
gzip_vary on;
```

### Where to compress

| Location | Trade |
|---|---|
| **At the proxy/CDN** | Offloads CPU from your app. The usual default |
| **In the application** | Needed when the proxy cannot see the body, or for streaming control |
| **At build time** | For static assets. Use the highest level, cache forever |

For FastAPI:

```python
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=1000)
```

⚠️ **`GZipMiddleware` buffers streaming responses.** It cannot compute the compressed output without seeing the whole stream in some configurations, which breaks SSE. If you have streaming endpoints, exclude them or compress at the proxy instead.

## BREACH: The Security Problem

Compressing a response that contains **both a secret and attacker-controlled input** leaks the secret.

```
Response contains:  csrf_token=A1B2C3   and   your search term
Attacker searches for: "csrf_token=A"    → response compresses slightly better
Attacker searches for: "csrf_token=B"    → less well
```

Compression ratio reveals whether the guess matched. Byte by byte, the token is extracted from response *size* alone, even over TLS.

⚠️ This is **BREACH**, and it is why TLS-level compression was removed from TLS 1.3 entirely. HTTP-level compression is still vulnerable when the conditions align.

Mitigations:

| Mitigation | Notes |
|---|---|
| Do not put secrets in compressible response bodies | The real fix |
| Rotate CSRF tokens per request | Attacker cannot accumulate information |
| Mask the token with a per-request random XOR | Standard framework approach |
| Do not reflect user input into responses containing secrets | Also good practice generally |
| Length randomisation (padding) | Weak, but raises the cost |

💡 **For a JSON API this is usually not a concern** — API responses do not typically contain both a CSRF token and reflected user input. But it is worth knowing, because "why is compression a security topic?" is a question that separates people who have read the spec from people who have read a tutorial.

## Streaming Responses

### Why stream

| Reason | Example |
|---|---|
| Time-to-first-byte | User sees results while the rest generates |
| Memory | A 2GB export never exists in memory |
| Unknown length | Live data, LLM tokens |
| Long-running | Progress updates during a slow operation |

### The mechanism

```http
HTTP/1.1 200 OK
Transfer-Encoding: chunked
Content-Type: application/json

1a\r\n
{"id": 1, "title": "..."}\r\n
1c\r\n
{"id": 2, "title": "..."}\r\n
0\r\n
\r\n
```

Chunked encoding from [[03.1 - HTTP1.1 Message Format]]. In HTTP/2 and HTTP/3 there is no `Transfer-Encoding` — framing is native, and a stream simply stays open.

### In FastAPI

```python
from fastapi.responses import StreamingResponse

async def generate_export(org_id: UUID):
    yield b'{"documents":['
    first = True
    async for doc in repo.stream_documents(org_id):
        if not first:
            yield b","
        yield orjson.dumps(doc)
        first = False
    yield b"]}"

@app.get("/exports")
async def export(org_id: UUID):
    return StreamingResponse(
        generate_export(org_id),
        media_type="application/json",
        headers={"X-Accel-Buffering": "no"},
    )
```

⚠️ **The database side must stream too.** `repo.stream_documents` must use a server-side cursor, not `fetchall()`. Otherwise you have loaded 2GB into memory and are streaming it out — solving the network problem and keeping the memory problem.

```python
async def stream_documents(org_id):
    async with pool.acquire() as conn:
        async with conn.transaction():
            async for record in conn.cursor(
                "SELECT * FROM documents WHERE org_id = $1", org_id
            ):
                yield dict(record)
```

⚠️ **A server-side cursor holds a transaction open for the whole stream.** A slow client now holds a database connection and a transaction for minutes ([[01.10 - Connection Pools and Limits]]). For large exports, prefer writing to object storage in a background job and returning a signed URL — [[08.1 - Why Background Work Exists]].

### NDJSON — the format that actually works for streaming

```
{"id": 1, "title": "a"}
{"id": 2, "title": "b"}
{"id": 3, "title": "c"}
```

One JSON object per line. The consumer parses each line as it arrives without waiting for a closing bracket.

```python
async def stream_ndjson(org_id):
    async for doc in repo.stream_documents(org_id):
        yield orjson.dumps(doc) + b"\n"

return StreamingResponse(stream_ndjson(org_id),
                         media_type="application/x-ndjson")
```

💡 **NDJSON is strictly better than a streamed JSON array for machine consumers.** A partially received array is invalid JSON and unparseable; a partially received NDJSON file is simply fewer records. It also means the consumer can process as it goes rather than buffering. Use it for exports, log shipping and bulk APIs.

## The Buffering Problem

Streaming fails silently when something in the path buffers.

```
App streams chunks
  → nginx buffers the whole response
    → client receives nothing until the end
```

The client sees a normal response that took 60 seconds instead of progressive output. For an infinite stream, it sees nothing forever.

### Where buffering happens

| Layer | Setting |
|---|---|
| nginx | `proxy_buffering off;` |
| nginx (per response) | `X-Accel-Buffering: no` header |
| AWS ALB | Does not buffer, but has a 60s idle timeout |
| Cloudflare | Buffers some content types. Streaming needs care |
| GZipMiddleware | May buffer to compute the compressed output |
| Your own middleware | `BaseHTTPMiddleware` can buffer ([[01.9 - ASGI and How Uvicorn Serves a Request]]) |

```nginx
location /stream {
    proxy_pass http://app;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    chunked_transfer_encoding on;
}
```

💡 **`X-Accel-Buffering: no` is the one to remember** because it works from your application without needing proxy configuration access. nginx honours it; several CDNs do too. When you cannot change the nginx config, this header is your lever.

## Compression and Streaming Together

They conflict, and understanding why matters.

Compression works better with more context — it builds a dictionary as it goes. Streaming wants to emit bytes immediately. Flushing the compressor after every chunk destroys the ratio.

```python
# Compressing a stream: flush per chunk, poor ratio
# Buffering to compress well: no longer streaming
```

Practical resolutions:

| Case | Choice |
|---|---|
| SSE / long-lived stream | **Do not compress.** Latency matters more |
| Large export (NDJSON) | Compress with periodic flushes. Ratio still good over MBs |
| Normal response | Compress, do not stream |

⚠️ **For SSE specifically, disable compression.** A compressed SSE stream that buffers is the single most common reason "my SSE endpoint delivers nothing" — see [[04.3 - SSE in Production]].

```python
@app.get("/events")
async def events():
    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
            "Content-Encoding": "identity",     # explicitly refuse compression
        },
    )
```

## In Production

### Zip bombs, in both directions

**Inbound:** a client sends a 1KB gzipped body that decompresses to 10GB.

```python
MAX_DECOMPRESSED = 50 * 1024 * 1024

def safe_decompress(data: bytes) -> bytes:
    decompressor = zlib.decompressobj(16 + zlib.MAX_WBITS)
    out = decompressor.decompress(data, MAX_DECOMPRESSED)
    if decompressor.unconsumed_tail:
        raise ValueError("decompressed body too large")
    return out
```

The `max_length` argument to `decompress` is the defence. Without it, one small request kills your process.

⚠️ Also enforce a limit at the proxy on the *compressed* size, and be aware that a 10:1 ratio is normal for JSON while 1000:1 indicates an attack.

**Outbound:** less common, but if you compress user-supplied content you can be tricked into spending enormous CPU.

### Measuring the trade

```python
original = len(body)
start = time.perf_counter()
compressed = gzip.compress(body, 5)
elapsed = time.perf_counter() - start

# Was it worth it?
bytes_saved = original - len(compressed)
seconds_saved = bytes_saved / bandwidth_bytes_per_sec
worth_it = seconds_saved > elapsed
```

On a fast internal network with 10 Gbps links, compressing small responses can genuinely be a net loss. On the public internet with mobile clients, it almost never is.

💡 **The rule of thumb: compress everything going to the internet, measure before compressing internal service-to-service traffic.** For internal traffic, zstd at level 1–3 usually wins where gzip at 6 does not.

### Streaming and error handling

Once you have sent `200 OK` and started streaming, you cannot change the status code.

```python
async def generate():
    yield b'{"items":['
    async for item in source():        # ← if this raises now, you have already sent 200
        yield orjson.dumps(item)
```

The client sees a truncated response with a success status. This is genuinely hard to handle well.

Approaches:

- **NDJSON with a terminal record** — end with `{"_status": "complete"}` so the consumer can detect truncation
- **Trailers** — HTTP supports trailing headers after a chunked body, but client support is patchy
- **Validate before streaming** — do the work that can fail before the first byte goes out

The NDJSON terminal record is the practical answer. **Document it in your API contract**, because a consumer that does not check it will silently process partial data.

## Codebase

**Repo:** `encode/starlette`, `nginx/nginx`, `google/brotli`

**Question to answer:** How does Starlette's `StreamingResponse` interact with `GZipMiddleware`, and under what conditions does compression break streaming? Then: how does nginx decide whether to buffer a proxied response, and what exactly does `X-Accel-Buffering` change?

**Read, in order:**

1. `starlette/responses.py` — `StreamingResponse.__call__` and `stream_response`. Note the `more_body` flag on each `http.response.body` message
2. `starlette/middleware/gzip.py` — **read this carefully.** Find where it decides to buffer versus stream, and what it does when it does not know the content length
3. `nginx/src/http/ngx_http_upstream.c` — search for `X-Accel-Buffering` handling and `p->cacheable`. This is the buffering decision
4. `nginx/src/http/modules/ngx_http_gzip_filter_module.c` — how nginx compresses a streaming response, and where it flushes
5. `google/brotli/c/enc/encode.c` — look at the flush modes. `BROTLI_OPERATION_FLUSH` versus `BROTLI_OPERATION_PROCESS` is exactly the streaming-versus-ratio tradeoff in code

💡 The Starlette `GZipMiddleware` reading is the practically valuable one. Knowing precisely when it buffers means you can predict whether adding compression will break a given streaming endpoint, rather than finding out in production.

**Part 1 — The compression matrix.** Three payload types (JSON API response, HTML page, already-compressed image), three algorithms, four levels each.

Measure: ratio, compression time, decompression time.

Then compute the break-even bandwidth: at what link speed does the CPU time exceed the transfer time saved? **Do this for 1 Gbps internal and 10 Mbps mobile.** The two answers are very different and that difference is the whole decision.

**Part 2 — Stream a million rows.** A table with a million rows. Two endpoints:

- `naive.py` — `fetchall()`, serialise, respond
- `streamed.py` — server-side cursor, NDJSON, chunked

Measure TTFB, peak process memory, and total time for both.

**The memory difference should be dramatic.** Chart peak RSS over time for both — the naive version's curve is the picture of an OOM waiting to happen.

Then push it: 10 million rows. The naive version should fail. Note the failure mode precisely.

**Part 3 — Detect buffering.** Instrument your client to record the arrival time of every chunk. Run against your streaming endpoint: directly, through nginx with default settings, through nginx with `proxy_buffering off`, and with `X-Accel-Buffering: no` but default nginx config.

Chart chunk arrival times for all four. **The default-nginx line should be flat until the end** — that flatness is what a buffering incident looks like.

**Part 4 — Compression plus streaming.** Compress your NDJSON stream three ways: flush after every record, flush every 64KB, and no flushing until the end.

Measure ratio and TTFB for each. Find the point where the ratio stops improving meaningfully — that is your flush interval.

Then try to compress an SSE stream and demonstrate that it breaks. Document exactly what the client observes.

**Part 5 — Zip bomb.** Build a small gzipped payload that expands enormously. Send it to an unprotected endpoint and watch memory climb.

Then implement bounded decompression and confirm the rejection. Also add a compressed-size limit at nginx and confirm it fires first.

Measure the largest safe ratio you should allow for your real payloads, so your limit rejects attacks without rejecting legitimate traffic.

**Part 6 — Failing mid-stream.** A streaming endpoint that raises after 1000 of 10,000 records.

Observe: the client got a 200 and a truncated body. Show that a naive consumer processes the partial data without noticing.

Then implement the terminal-record pattern and a consumer that checks it. Confirm the truncation is now detected.

**Done when:**
- Your break-even table has different answers for internal and mobile links
- The memory chart shows the naive version's growth and the streamed version's flatness
- Your chunk-arrival chart shows buffering clearly, with three working fixes
- You know your flush interval and why
- The zip bomb is rejected and your limit does not reject legitimate payloads
- A truncated stream is now detectable by the consumer
