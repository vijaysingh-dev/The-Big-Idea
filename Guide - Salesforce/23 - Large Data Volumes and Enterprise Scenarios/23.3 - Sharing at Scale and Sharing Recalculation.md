# Sharing at Scale and Sharing Recalculation

## Sharing is stored, not computed

The single fact that explains every performance problem in this note.

**Record access is not evaluated at query time.** It is **materialized** — rows in a sharing table, one per record per grant.

```
Warranty_Claim__c              2,000,000 records
Warranty_Claim__Share          how many rows?
```

**It depends on how many ways access is granted:**

```
Owner                          implicit, not stored separately
Role hierarchy                 one row per record per role above the owner
Sharing rules                  one row per record per group granted
Manual shares                  one row each
Apex shares                    one row each
Team membership                one row each
Territory                      one row each
```

**A record owned by a user five levels deep in the hierarchy, covered by three sharing rules, generates nine or more rows.** Two million records becomes eighteen million sharing rows.

**The sharing table is frequently larger than the data table**, and every query joins against it.

## What triggers recalculation

The operations that cause the sharing engine to work, in rough order of cost.

**Changing a record's owner.** Recalculates that record's sharing, and its master-detail children's.

**Moving a user in the role hierarchy.** Recalculates every record that user owns, and every record shared to them by hierarchy.

**Changing the role hierarchy structure.** Recalculates for every affected branch.

**Creating or modifying a sharing rule.** Recalculates across every matching record.

**Changing an organization-wide default.** Recalculates the entire object.

**Adding or removing a public group member.** Recalculates every rule referencing that group.

**Changing a record's criteria** where a criteria-based sharing rule matches on it.

**The last one is the quiet cost.** A criteria-based rule on `Status__c` means every status change re-evaluates sharing for that record.

## Why it hurts at scale

```
Change a user's role
    → 400,000 records owned by that user
        → recalculate hierarchy sharing for each
            → delete and reinsert sharing rows
                → hours, during which the org is degraded
```

**Sharing recalculation is asynchronous and org-wide.** While it runs, other operations contend with it, and users report slowness that has no apparent cause.

**Ownership skew makes this catastrophic.** A user owning 400,000 records cannot be moved in the hierarchy without a maintenance window. See [[10.9 - Data Skew]].

## Reducing sharing volume

The interventions, in order of effectiveness.

### Use master-detail where possible

**A master-detail child generates no sharing rows of its own.** Access is derived from the parent.

```
Warranty_Claim__c → Asset, lookup
    2,000,000 claims × sharing grants = millions of rows

Warranty_Claim__c → Asset, master-detail
    zero sharing rows for the claim
```

**This is the largest single reduction available**, and it is a data model decision made once. See [[23.2 - LDV Data Modelling Strategies]].

### Flatten the role hierarchy

**Each level above a record's owner generates a sharing row.**

```
8 levels deep    → up to 8 hierarchy rows per record
3 levels deep    → up to 3
```

**Depth is a sharing cost multiplier.** A hierarchy built to mirror the organization chart, rather than to reflect data access needs, is usually deeper than it needs to be.

**The question per level:** does someone at this level need to see everything below it? If not, the level exists for reporting or convenience, and a public group would serve better.

See [[03.8 - Role Hierarchy]].

### Prefer groups to roles in sharing rules

```
Sharing rule → Role and Subordinates
    expands to every role below, generating rows per role

Sharing rule → Public Group
    generates rows for the group
```

**Groups are cheaper and more stable.** A role hierarchy change re-evaluates every rule referencing roles; a group membership change re-evaluates only the rules referencing that group.

Groups also express intent more clearly — "the claims review team" rather than "everyone under the service director".

### Reduce sharing rule count

**Each rule generates rows for every matching record.**

```
12 sharing rules on Warranty_Claim__c
    × 2,000,000 records
        = up to 24,000,000 sharing rows
```

**Consolidating rules** — one rule granting to a group containing several teams, rather than three rules — reduces both the row count and the recalculation cost.

**Criteria-based rules are more expensive than ownership-based ones**, because a record's criteria can change and ownership rarely does.

### Consider a more open OWD

Counterintuitive, and occasionally correct.

**Private OWD with sharing rules granting broad access generates enormous sharing tables.** If most users can see most records anyway, Public Read Only with a small number of restrictions is cheaper and simpler.

**The question:** what fraction of records is the average user actually prevented from seeing? If it is small, the private model is generating millions of rows to enforce a restriction that barely applies.

**This is a genuine architectural option** and it is rarely considered, because private feels safer. See [[03.7 - Organization-Wide Defaults]].

## Deferred sharing calculation

The operational tool for large changes.

```
Setup → Defer Sharing Calculation → Suspend
    [perform the load, the reassignment, the hierarchy change]
Setup → Defer Sharing Calculation → Resume
```

**Sharing recalculation is suspended**, the work completes without it, and a single full recalculation runs at the end.

**Why it helps:** recalculating once at the end is far cheaper than recalculating continuously during a load.

**The costs:**

**Sharing is stale while suspended.** Users may see records they should not, or not see records they should.

**The final recalculation can take hours** on a large org.

**It must be requested from Salesforce** to be enabled in the org.

**Where it is worth it:** a bulk load into a private object, a large ownership reassignment, or a hierarchy restructure. On any of those, it is the difference between a job that completes overnight and one that does not. See [[23.5 - Bulk Data Loading at Scale]].

## Ownership skew remediation

The most disruptive problem, and the sequence that resolves it.

**1. Measure:**

```sql
SELECT OwnerId, Owner.Name, COUNT(Id) FROM Warranty_Claim__c
GROUP BY OwnerId, Owner.Name ORDER BY COUNT(Id) DESC LIMIT 20
```

**2. Design the target distribution.** Several owners rather than one, or a queue.

**3. Remove the owner from the role hierarchy first**, if possible.

**A user with no role generates no hierarchy sharing rows.** For an integration user owning large volumes, that alone removes most of the cost, and it is a one-field change.

**4. Reassign in batches**, with deferred sharing enabled:

```java
public with sharing class OwnershipRedistributionBatch implements Database.Batchable<SObject> {

    private final Id sourceOwnerId;
    private final List<Id> targetOwnerIds;

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, OwnerId FROM Warranty_Claim__c WHERE OwnerId = :sourceOwnerId
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        for (Integer i = 0; i < scope.size(); i++) {
            // round-robin, so the new owners stay evenly loaded
            scope[i].OwnerId = targetOwnerIds[Math.mod(i, targetOwnerIds.size())];
        }
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**A small scope size** — 50 or 100 — reduces lock duration per chunk, which matters because ownership change is itself the contended operation.

**5. Verify**, and re-run the measurement.

## Apex sharing at scale

```java
List<Warranty_Claim__Share> shares = new List<Warranty_Claim__Share>();

for (Warranty_Claim__c claim : claims) {
    shares.add(new Warranty_Claim__Share(
        ParentId = claim.Id,
        UserOrGroupId = engineerId,
        AccessLevel = 'Edit',
        RowCause = Schema.Warranty_Claim__Share.RowCause.Assigned_Engineer__c
    ));
}

Database.insert(shares, false);
```

**Every Apex share is a row**, and creating them in bulk is a large write.

**A custom row cause** is essential — it allows the share to be deleted independently of other grants, and it survives ownership changes. Without one, the share uses `Manual` and is removed when the owner changes. See [[03.11 - Apex Sharing and Programmatic Sharing]].

**At scale, prefer a sharing rule to Apex sharing** where the criteria can be expressed declaratively. The platform maintains it, and it recalculates more efficiently than a batch job recreating shares.

**Where Apex sharing is genuinely needed** — access driven by logic a rule cannot express — the shares must be maintained: created when the condition becomes true, deleted when it becomes false. A share that is created and never removed accumulates.

## Diagnosing sharing problems

**"The role change is taking hours."** Ownership skew. Measure it.

**"Users report slowness with no cause."** A recalculation is running. Check whether a hierarchy or rule change happened recently.

**"The data load fails with lock errors."** Sharing recalculation contending with the load. Defer it.

**"Deleting the user timed out."** They own too many records; reassign first, in batches.

**"Queries are slow on a private object."** The sharing join. Check the query plan — a `Leading Operation Type` of `Other` frequently indicates a sharing-based plan.

```
Cardinality  Fields    Leading Operation Type  Cost
     18420   OwnerId   Other                   3.42
```

**`Other` means the optimizer used a sharing-based plan**, which at volume is slow. Making the query selective on an indexed field is the fix. See [[23.6 - Query Performance at Scale]].

## Monitoring

```sql
SELECT OwnerId, Owner.Name, COUNT(Id) FROM Warranty_Claim__c
GROUP BY OwnerId, Owner.Name ORDER BY COUNT(Id) DESC LIMIT 10
```

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail
WHERE Section IN ('Sharing Rules', 'Roles', 'Manage Users')
  AND CreatedDate = LAST_N_DAYS:30
```

**Watching for hierarchy and sharing rule changes** is worth doing, because they are the changes that cause org-wide recalculation and the person making them frequently does not know that.

**Trending ownership concentration** catches skew before it becomes a project.

## Practical guidance

**Use master-detail on high-volume children** — it eliminates their sharing rows entirely.

**Keep the role hierarchy shallow.** Depth multiplies sharing rows.

**Grant to public groups, not roles**, in sharing rules.

**Consolidate sharing rules** — each one multiplies across every record.

**Consider whether private OWD is earning its cost.**

**Give integration users no role.** It is a one-field change that removes most of their sharing cost.

**Enable deferred sharing calculation** for large loads and reassignments.

**Reassign ownership in small batches**, and remove the role first.

**Use a custom row cause** on every Apex share.

**Watch for a `Leading Operation Type` of `Other`** in query plans — it means a sharing-based plan.
