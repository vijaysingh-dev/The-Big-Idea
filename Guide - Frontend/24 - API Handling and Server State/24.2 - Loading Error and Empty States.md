# Loading, Error and Empty States

Every asynchronous view has at least five states. Shipping only the happy path is the most common gap between a demo and a product.

```
idle → loading → success (with data)
                → success (empty)
                → error
```

Plus, once data exists: **refetching with stale data on screen**.

## Model states as a union

```jsx
// Representable but meaningless combinations
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);
// isLoading && error && data — all true is possible

// One value, one truth
type State =
  | { status: "loading" }
  | { status: "error"; error: AppError }
  | { status: "success"; data: Item[] };
```

Three booleans give eight combinations, of which perhaps four are valid. A discriminated union makes invalid states unrepresentable, and TypeScript narrows `data` per branch ([[25.6 - Discriminated Unions and Narrowing]]).

Query libraries expose exactly this:

```jsx
const { status, data, error, isFetching } = useQuery(...);
```

Note `status` and `isFetching` are separate. `status === "success"` with `isFetching === true` is a **background refetch** — data on screen, update in flight. Treating it as "loading" and showing a spinner over existing content is a regression ([[24.6 - TanStack Query Fundamentals]]).

## Rendering the branches

```jsx
function ProductList({ categoryId }) {
  const { status, data, error, refetch, isFetching } = useProducts(categoryId);

  if (status === "pending") return <ProductListSkeleton />;
  if (status === "error") return <ErrorState error={error} onRetry={refetch} />;
  if (data.length === 0) return <EmptyState categoryId={categoryId} />;

  return (
    <div aria-busy={isFetching}>
      {data.map(p => <ProductCard key={p.id} product={p} />)}
    </div>
  );
}
```

Early returns read better than nested ternaries ([[16.7 - Conditional Rendering and Composition]]).

## Loading: skeletons over spinners

```jsx
function ProductListSkeleton() {
  return (
    <div aria-busy="true" aria-live="polite">
      {Array.from({ length: 6 }, (_, i) => (
        <div key={i} className="skeleton-card" />
      ))}
    </div>
  );
}
```

Skeletons that approximate the final layout beat spinners for two reasons: they set expectations about what is coming, and they prevent layout shift when the content arrives ([[13.5 - Core Web Vitals]]).

A skeleton that is 60px tall replaced by 400px of content is a large CLS penalty — arguably worse than showing nothing.

**Delay the indicator.** For fast responses, a spinner that appears and vanishes in 80ms reads as a flicker:

```jsx
const [showLoader, setShowLoader] = useState(false);

useEffect(() => {
  if (!isLoading) { setShowLoader(false); return; }
  const id = setTimeout(() => setShowLoader(true), 200);
  return () => clearTimeout(id);
}, [isLoading]);
```

The usual guidance: nothing under ~200ms, an indicator between 200ms and ~1s, and a skeleton or progress display beyond that. Once shown, keep it visible for a minimum duration so it does not flash.

## Error states need a way forward

```jsx
function ErrorState({ error, onRetry }) {
  const message = {
    network: "Check your connection and try again.",
    timeout: "That took too long. Try again?",
    forbidden: "You do not have access to this.",
    notFound: "We could not find that.",
    server: "Something went wrong on our end.",
  }[error.kind] ?? "Something went wrong.";

  return (
    <div role="alert">
      <p>{message}</p>
      {error.kind !== "forbidden" && (
        <button onClick={onRetry}>Try again</button>
      )}
    </div>
  );
}
```

Three rules:

**Never show raw error messages.** They leak implementation detail and occasionally sensitive information. Map to friendly text and log the original ([[05.9 - Error Handling and Custom Errors]]).

**Always offer a next action** where one exists — retry, go back, contact support. A dead-end error message is a dead end for the user.

**Distinguish error kinds.** "Check your connection" for a network failure and "you do not have access" for a 403 are different problems with different remedies. Showing "something went wrong" for both wastes the user's time.

Never show a retry button for errors that cannot succeed on retry — a 403 or a 404 will fail identically.

## Partial failure

One failed section should not blank the page:

```jsx
const results = await Promise.allSettled([
  fetchProfile(id),
  fetchActivity(id),
  fetchRecommendations(id),
]);
```

`Promise.allSettled` gives partial success where `Promise.all` gives all-or-nothing ([[04.5 - Promise Combinators]]).

With independent queries, each section renders its own state, and an error boundary per widget contains failures ([[22.1 - Error Boundaries]]).

## Empty states are not errors

```jsx
function EmptyState({ hasFilters, onClearFilters }) {
  if (hasFilters) {
    return (
      <div>
        <p>No products match your filters.</p>
        <button onClick={onClearFilters}>Clear filters</button>
      </div>
    );
  }

  return (
    <div>
      <p>No products yet.</p>
      <Link to="/products/new">Add your first product</Link>
    </div>
  );
}
```

Three distinct empties, each needing different copy:

**First-use empty** — the user has nothing yet. This is an onboarding opportunity: explain what goes here and offer the action that creates the first item.

**Filtered empty** — data exists but none matches. The action is clearing or widening the filter, and the copy should say so.

**Genuinely empty** — a completed list, an archive with nothing in it. A neutral statement is enough.

Treating all three as "No results found" wastes the most valuable moment in a new user's experience.

## Stale data during refetch

```jsx
<div style={{ opacity: isFetching ? 0.6 : 1, transition: "opacity 150ms" }}>
  {data.map(...)}
</div>
```

When data already exists, showing it dimmed while refreshing is better than replacing it with a skeleton — the user keeps context and can still read what is there.

The same principle drives `keepPreviousData` for pagination and `useDeferredValue` for expensive derived renders ([[22.5 - useDeferredValue]]).

## Accessibility

```jsx
<div aria-busy={isFetching} aria-live="polite">
  {status === "pending" && <p className="sr-only">Loading products</p>}
</div>

{status === "error" && <div role="alert">{message}</div>}
```

State changes that are visually obvious are invisible to screen reader users without announcement. `aria-live="polite"` for loading and empty transitions, `role="alert"` for errors ([[09.5 - Accessibility Fundamentals]]).

The live region container must exist **before** the content changes — rendering the whole region conditionally often means nothing is announced ([[12.5 - Custom Events and Observer APIs]]).

## Offline

```jsx
const isOnline = useSyncExternalStore(
  (cb) => {
    window.addEventListener("online", cb);
    window.addEventListener("offline", cb);
    return () => {
      window.removeEventListener("online", cb);
      window.removeEventListener("offline", cb);
    };
  },
  () => navigator.onLine,
  () => true
);
```

`navigator.onLine` only reports whether there is a network interface, not whether requests succeed — a captive portal or a dead backend both report "online". Treat it as a hint that improves the error message, not as a reliable signal ([[17.12 - Lesser Known Hooks]]).

## How senior engineers actually use this

**They model status as a union**, never as parallel booleans.

**They build the four states together** — loading, error, empty, success — rather than adding them after review.

**They distinguish first-load from background refetch**, dimming rather than blanking on the latter.

**They write three empty states**, not one, and treat first-use empty as onboarding.

**They delay loading indicators** for fast responses and enforce a minimum display duration.

## Common pitfalls

- Parallel booleans permitting impossible states.
- A spinner replacing existing content during a background refetch.
- Raw error messages shown to users.
- No retry path, or a retry button on a 403.
- One generic empty state for all three cases.
- Undersized skeletons causing layout shift.
- No `role="alert"` or `aria-live`, leaving screen reader users unaware.
- Trusting `navigator.onLine` as a definitive signal.

## Interview angle

"How do you handle loading and error states" is deceptively broad, and the strong answer is structural: model the states as a discriminated union so invalid combinations are unrepresentable, then enumerate the four — loading, error, empty, success — plus the fifth, background refetch, which is where most implementations regress by showing a spinner over good data. Mentioning the three distinct empty states and delayed loading indicators shows product sense alongside technical correctness.
