# Types, Coercion and Equality

JavaScript has **seven primitives** — `string`, `number`, `boolean`, `null`, `undefined`, `symbol`, `bigint` — and one non-primitive type, `object` (which includes arrays, functions, dates, and everything else).

Primitives are immutable and compared by value. Objects are compared by reference.

```js
"abc"[0] = "x";     // silently does nothing
[1] === [1];        // false — different objects
```

## typeof

```js
typeof "s"          // "string"
typeof 1            // "number"
typeof true         // "boolean"
typeof undefined    // "undefined"
typeof Symbol()     // "symbol"
typeof 1n           // "bigint"
typeof {}           // "object"
typeof []           // "object"     — no array distinction
typeof null         // "object"     — a bug from 1995, unfixable
typeof function(){} // "function"   — a special case
```

`typeof null === "object"` is a historical artifact: the original implementation tagged values by their low bits, and `null` was the null pointer, which shared the object tag. Fixing it would break the web.

Better checks:

```js
Array.isArray(x);
Number.isInteger(x);
Number.isNaN(x);                       // not the global isNaN
x === null;
Object.prototype.toString.call(x);     // "[object Date]", "[object Map]", ...
```

The global `isNaN` coerces first (`isNaN("abc")` is `true`), while `Number.isNaN` does not. Always use the latter.

## The three coercion targets

Every implicit conversion goes to a string, a number, or a boolean.

**To boolean.** Exactly eight falsy values, and everything else is truthy:

```
false, 0, -0, 0n, "", null, undefined, NaN
```

Notably truthy: `"0"`, `"false"`, `[]`, `{}`, `function(){}`, `new Boolean(false)`.

The empty-array case bites constantly:

```js
if (results) {}          // true even for []
if (results.length) {}   // what you meant
```

**To string.** `String(x)`, template literals, and `+` when either operand is a string.

```js
String([1, 2]);      // "1,2"
String({});          // "[object Object]"
String(null);        // "null"
String([null]);      // ""     — Array#join treats null/undefined as empty
```

**To number.** Arithmetic operators (except `+` with a string), comparison operators, and `Number(x)`.

```js
Number("");          // 0
Number(" 42 ");      // 42
Number("42px");      // NaN
Number([]);          // 0
Number([5]);         // 5
Number([1, 2]);      // NaN
Number(null);        // 0
Number(undefined);   // NaN
Number(true);        // 1
```

`Number(null) === 0` but `Number(undefined) === NaN` is the inconsistency behind several of the classic quiz answers.

## The + operator

`+` is the only operator that means two things, and it prefers strings:

```js
1 + 2       // 3
"1" + 2     // "12"
1 + "2"     // "12"
[] + {}     // "[object Object]"
1 + null    // 1
1 + undefined // NaN
"3" - 1     // 2   — minus has no string meaning, so both go to number
"3" * "4"   // 12
```

Objects convert to primitives via `Symbol.toPrimitive`, then `valueOf`, then `toString` ([[03.6 - Symbols and Well Known Symbols]]). `[]` has a `valueOf` returning itself (not a primitive), so `toString` runs and gives `""`.

## == vs ===

`===` compares type and value with no conversion. `==` converts first, following these rules:

1. Same type → same as `===`
2. `null == undefined` → `true` (and neither equals anything else)
3. number vs string → string becomes number
4. boolean vs anything → boolean becomes number
5. object vs primitive → object becomes primitive, then retry

```js
0 == "";           // true
0 == "0";          // true
"" == "0";         // false  — not transitive
null == undefined; // true
null == 0;         // false  — null only equals undefined
NaN == NaN;        // false
[] == false;       // true   — [] -> "" -> 0, false -> 0
[] == ![];         // true   — same thing
```

The non-transitivity (`0 == ""`, `0 == "0"`, but `"" != "0"`) is the clearest argument that `==` is not a usable equality relation.

**The one defensible use of `==`:**

```js
if (value == null) { }  // true for null and undefined only
```

This is concise and unambiguous, and most style guides that ban `==` carve out an exception for it (`eqeqeq: ["error", "always", { null: "ignore" }]`).

## Object.is and SameValueZero

```js
Object.is(NaN, NaN);   // true
Object.is(0, -0);      // false
NaN === NaN;           // false
0 === -0;              // true
```

`Object.is` is "SameValue". A third algorithm, **SameValueZero**, treats `NaN` as equal to itself but `0` equal to `-0` — this is what `Array.prototype.includes`, `Map` keys and `Set` values use.

```js
[NaN].includes(NaN);   // true
[NaN].indexOf(NaN);    // -1  — indexOf uses ===
new Set([0, -0]).size; // 1
```

React uses `Object.is` for state comparison, which is why setting state to `NaN` twice does not re-render but setting `-0` after `0` does.

## Numbers

All numbers are IEEE-754 doubles.

```js
0.1 + 0.2;                    // 0.30000000000000004
0.1 + 0.2 === 0.3;            // false
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON; // true
Number.MAX_SAFE_INTEGER;      // 9007199254740991
9007199254740993;             // 9007199254740992 — precision lost
```

Two production consequences. Never store money as a float — use integers of the smallest unit (paise, cents) or a decimal library. And never let a 64-bit integer id from a backend pass through `JSON.parse` as a number; request it as a string, or ids will silently collide above 2^53.

`BigInt` handles arbitrary integers but cannot mix with `Number` in arithmetic.

## How senior engineers actually use this

**They use `===` everywhere except the `== null` idiom.** This is settled practice, not preference.

**They validate at boundaries rather than coercing internally.** Data from `JSON.parse`, query strings, form inputs and `localStorage` is all strings or `any`. Parse and validate once at the edge — Zod or similar ([[25.7 - Typing API Responses and Zod]]) — so internal code never guesses.

**They check `.length` or use explicit predicates rather than relying on truthiness** for arrays, and are careful with numbers where `0` is a valid value:

```js
if (count) {}              // wrong when count is 0
if (count !== undefined) {} // or use ?? — see 05.7
```

**They treat `NaN` as a signal to look upstream.** `NaN` propagates through every arithmetic operation, so by the time you see it in the UI the origin is often several steps back. `Number.isNaN` guards at the parse point.

## Common pitfalls

- Truthiness checks on `0` and `""` when those are valid values.
- `parseInt` without a radix, and `parseInt` accepting trailing garbage (`parseInt("12px")` is `12`, `Number("12px")` is `NaN`).
- `arr.map(parseInt)` — the index is passed as the radix.
- Using `==` and hitting one of the non-transitive cases.
- Float arithmetic on currency.
- Large integer ids losing precision through JSON.
- `indexOf` failing to find `NaN`.

## Interview angle

"Difference between `==` and `===`" always appears, often with `[] == false` or `null == undefined` as follow-ups. Give the conversion rules rather than "one checks type" — specifically that `null` and `undefined` equal each other and nothing else, and that objects convert to primitives before comparison. Adding the non-transitivity example and `Object.is`/SameValueZero shows depth beyond the standard answer.
