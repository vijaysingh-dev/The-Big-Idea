# How Imports Work

#python #modules #imports

> **In one line:** `import x` checks the `sys.modules` cache, otherwise finds `x` on `sys.path`, creates a module object, executes its code top to bottom once, and binds a name. Almost every import bug (circular imports, the double-module problem, side effects at import time) follows from those steps.

---

## What `import` Actually Does

```python
import app.db
```

1. **Check the cache.** If `"app.db"` is in `sys.modules`, use that object. Done.
2. **Import parents first.** `app` must be imported (its `__init__.py` runs) before `app.db`.
3. **Find.** Ask each *finder* on `sys.meta_path` for a **spec**: where the module is and how to load it. The path-based finder searches `sys.path` entries in order.
4. **Create** an empty module object and **insert it into `sys.modules` before running its code.**
5. **Execute** the module's code in the module's namespace (`module.__dict__`).
6. **Bind** the name `app` in the importing namespace.

```python
import sys
sys.modules["json"]              # the cached module object
sys.path                         # where Python looks, in order
import json; json.__spec__       # ModuleSpec(name='json', loader=..., origin='/usr/lib/python3.12/json/__init__.py')
```

💡 **A module's code runs once per process**, on first import. That is why module-level code is the natural place for singletons (a settings object, a logger), and why heavy work at import time (connecting to a database, loading a model) slows every process start, including test runs and CLI calls. Use `python -X importtime app.py 2>&1 | sort -t'|' -k2 -n | tail` to find slow imports.

## Forms of Import

```python
import os.path                 # binds `os`; os.path is reachable as an attribute
import numpy as np             # binds `np`
from app.db import Session     # imports app.db, then binds Session only
from . import models           # relative: sibling module in the same package
from ..core import config      # relative: parent package
from app.db import *           # binds names in __all__ (or all public names). Avoid in application code.
```

⚠️ **`from module import name` copies a reference at import time.** If the module later rebinds `name`, your copy does not change:

```python
# config.py
settings = None
def init(): 
    global settings
    settings = load()

# elsewhere
from config import settings     # None, forever, if imported before init() ran
import config; config.settings  # always the current value
```

This is also why `unittest.mock.patch` must target the name **where it is used**: `patch("app.handlers.send_email")`, not `patch("app.email.send_email")`, when `handlers` did `from app.email import send_email` ([[07.5 - Testing With pytest]]).

## Packages

A **package** is a directory that is a module. Regular packages have `__init__.py`, which runs when the package is imported.

```
src/app/
├── __init__.py        # runs on `import app`; keep it light
├── db.py
├── api/
│   ├── __init__.py
│   └── routes.py
└── py.typed           # tells type checkers this package ships type hints
```

**Namespace packages** (PEP 420) have no `__init__.py`. Several directories on `sys.path` can contribute to one package. Plugin systems use them (`google.cloud.*`, `opentelemetry.instrumentation.*`). Do not create them by accident by forgetting `__init__.py` in your own code. Tools then behave inconsistently.

## `__name__ == "__main__"`

When you run `python app/cli.py`, that file is executed as a module named `__main__`, not `app.cli`.

```python
def main(): ...

if __name__ == "__main__":
    main()
```

⚠️ **The double-import problem.** If `cli.py` is run as a script **and** imported elsewhere as `app.cli`, Python creates two separate module objects with two copies of every global, every class and every registry. `isinstance` checks fail between them, and singletons are no longer single.

**Fix:** run modules with `python -m app.cli` (the module is found through the package, and imports stay consistent) or through an installed entry point ([[03.2 - Packaging and Project Tooling]]). Prefer `-m` over running paths.

## Circular Imports

```python
# models.py
from services import notify      # starts importing services...
class User: ...

# services.py
from models import User           # models is in sys.modules but only half executed: User does not exist yet
def notify(u: User): ...
```

```
ImportError: cannot import name 'User' from partially initialized module 'models'
(most likely due to a circular import)
```

Because of step 4 above, a module is in `sys.modules` while it is still running. The second import gets the half-built module.

**Fixes, best first:**

| Fix | When |
|---|---|
| **Restructure.** Move shared things into a third module both can import. | Almost always. A cycle is a design smell: two modules that depend on each other are really one module, or are missing a lower layer. |
| Import the module, not the name (`import models` then `models.User` at call time) | Quick fix; attribute lookup happens later, when the module is complete |
| Import inside the function that needs it | Last resort, for rarely called code |
| `if TYPE_CHECKING:` imports plus string annotations | When the cycle exists only for type hints |

```python
from __future__ import annotations   # annotations are not evaluated at runtime (default in 3.14 via PEP 649/749 semantics)
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from models import User

def notify(u: User) -> None: ...
```

The layering view of the same problem is in [[01.1 - SOLID Principles]] in the LLD guide: dependencies should point one way.

## Reloading and Dynamic Imports

```python
import importlib
mod = importlib.import_module("plugins." + name)    # import by string: plugin systems, Celery, Django settings
importlib.reload(mod)                               # re-executes the module in the SAME module object
```

`reload` does not update objects that were already created, nor names other modules got with `from x import y`. It is useful in a REPL and almost never in production. Dev servers (`uvicorn --reload`) restart the whole process instead, for exactly this reason.

## Codebase

**Repo:** `python/cpython`

**Question to answer:** Where exactly is the module inserted into `sys.modules` before its code runs, and how does the path finder turn `"app.db"` into a file path?

**Read, in order:**

1. `Lib/importlib/_bootstrap.py` — `_find_and_load()`, `_load_unlocked()` (find the line that puts the module into `sys.modules` before `exec_module`), and `_handle_fromlist()`
2. `Lib/importlib/_bootstrap_external.py` — `PathFinder.find_spec()`, `FileFinder`, and `SourceFileLoader` (including where `.pyc` files in `__pycache__` are checked)
3. `Lib/runpy.py` — `_run_module_as_main()`: what `python -m` does differently

**Size:** 2 sessions. This is pure Python and one of the most important files in CPython.
