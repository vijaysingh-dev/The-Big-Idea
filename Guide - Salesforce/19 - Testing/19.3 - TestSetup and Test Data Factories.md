# TestSetup and Test Data Factories

## The problem

```java
@IsTest
static void approvalSetsTheStatus() {
    Account account = new Account(Name = 'Northwind Test', BillingCountry = 'India');
    insert account;

    Asset asset = new Asset(
        Name = 'Press P400', AccountId = account.Id, SerialNumber = 'SN-1',
        Status = 'Installed', InstallDate = Date.today().addYears(-1)
    );
    insert asset;

    Service_Contract__c contract = new Service_Contract__c(
        Account__c = account.Id, Status__c = 'Active',
        Start_Date__c = Date.today().addMonths(-6), End_Date__c = Date.today().addMonths(6)
    );
    insert contract;

    // twenty more lines before the test does anything
}
```

That block appears in forty test methods. When a required field is added to Asset, forty tests break.

## A factory

```java
@IsTest
public class TestDataFactory {

    public static Account createAccount() {
        Account account = buildAccount();
        insert account;
        return account;
    }

    public static Account buildAccount() {
        return new Account(
            Name = 'Test Account ' + uniqueSuffix(),
            BillingCountry = 'India',
            Industry = 'Manufacturing'
        );
    }

    public static Asset createAsset(Id accountId) {
        Asset asset = buildAsset(accountId);
        insert asset;
        return asset;
    }

    public static Asset buildAsset(Id accountId) {
        return new Asset(
            Name = 'Press P400',
            AccountId = accountId,
            SerialNumber = 'SN-' + uniqueSuffix(),
            Status = 'Installed',
            InstallDate = Date.today().addYears(-1)
        );
    }

    private static Integer counter = 0;

    private static String uniqueSuffix() {
        // a counter rather than a timestamp, so values are unique within a transaction too
        return String.valueOf(counter++).leftPad(6, '0');
    }
}
```

Now the required-field change touches one file.

## build versus create

The distinction worth adopting from the start.

**`build`** returns an unsaved record. **`create`** inserts and returns it.

```java
// One record, one DML
Warranty_Claim__c claim = TestDataFactory.createClaim(assetId, 150000);

// 200 records, one DML
List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
for (Integer i = 0; i < 200; i++) {
    claims.add(TestDataFactory.buildClaim(assetId, 10000));
}
insert claims;
```

**Without the `build` variant, bulk tests perform 200 inserts** — slow, and it consumes DML statements a test may need for something else.

Every factory method should have both forms.

## Overloads and defaults

```java
public static Warranty_Claim__c buildClaim(Id assetId) {
    return buildClaim(assetId, 150000, 'Submitted');
}

public static Warranty_Claim__c buildClaim(Id assetId, Decimal amount) {
    return buildClaim(assetId, amount, 'Submitted');
}

public static Warranty_Claim__c buildClaim(Id assetId, Decimal amount, String status) {
    return new Warranty_Claim__c(
        Asset__c = assetId,
        Claim_Amount__c = amount,
        Status__c = status,
        Claim_Date__c = Date.today(),
        Fault_Description__c = 'Test fault ' + uniqueSuffix()
    );
}
```

**Sensible defaults with overloads for what the test cares about.** A test about approval tiers should specify the amount and nothing else — every other field is noise that obscures what the test is actually about.

## A builder for complex cases

Where overloads multiply, a fluent builder reads better.

```java
@IsTest
public class ClaimBuilder {

    private final Warranty_Claim__c claim;

    public ClaimBuilder() {
        claim = new Warranty_Claim__c(
            Claim_Amount__c = 150000,
            Status__c = 'Submitted',
            Claim_Date__c = Date.today()
        );
    }

    public ClaimBuilder forAsset(Id assetId) {
        claim.Asset__c = assetId;
        return this;
    }

    public ClaimBuilder withAmount(Decimal amount) {
        claim.Claim_Amount__c = amount;
        return this;
    }

    public ClaimBuilder approved(Decimal approvedAmount) {
        claim.Status__c = 'Approved';
        claim.Approved_Amount__c = approvedAmount;
        claim.Approved_Date__c = Date.today();
        return this;
    }

    public Warranty_Claim__c build() {
        return claim;
    }

    public Warranty_Claim__c create() {
        insert claim;
        return claim;
    }
}
```

```java
Warranty_Claim__c claim = new ClaimBuilder()
    .forAsset(assetId)
    .withAmount(900000)
    .approved(750000)
    .create();
```

**The named state methods are the value** — `approved()` sets three fields consistently, so no test gets a claim with a status of Approved and no approved amount.

Builders are one of the few places the fluent pattern genuinely earns its verbosity in Apex. See [[18.9 - Factory, Strategy and Singleton in Apex]].

## Scenario methods

For a complete, valid setup that several tests need.

```java
@IsTest
public class TestScenarioFactory {

    public class CoveredAssetScenario {
        public Account account;
        public Asset asset;
        public Service_Contract__c contract;
        public Machine_Coverage__c coverage;
    }

    public static CoveredAssetScenario coveredAsset(Decimal coverageLimit) {
        CoveredAssetScenario scenario = new CoveredAssetScenario();

        scenario.account = TestDataFactory.createAccount();
        scenario.asset = TestDataFactory.createAsset(scenario.account.Id);

        scenario.contract = new Service_Contract__c(
            Account__c = scenario.account.Id,
            Status__c = 'Active',
            Start_Date__c = Date.today().addMonths(-6),
            End_Date__c = Date.today().addMonths(6)
        );
        insert scenario.contract;

        scenario.coverage = new Machine_Coverage__c(
            Asset__c = scenario.asset.Id,
            Service_Contract__c = scenario.contract.Id,
            Coverage_Limit__c = coverageLimit,
            Coverage_Start_Date__c = scenario.contract.Start_Date__c,
            Coverage_End_Date__c = scenario.contract.End_Date__c
        );
        insert scenario.coverage;

        return scenario;
    }
}
```

```java
@IsTest
static void claimsWithinTheCoverageLimitAreApproved() {
    TestScenarioFactory.CoveredAssetScenario scenario =
        TestScenarioFactory.coveredAsset(500000);

    Warranty_Claim__c claim = new ClaimBuilder()
        .forAsset(scenario.asset.Id)
        .withAmount(400000)
        .create();
}
```

**The scenario object returning every created record** matters — a test needing the contract Id should not have to query for it.

## @TestSetup

Runs once per class; the data is restored fresh for each method.

```java
@IsTest
private class ClaimApprovalServiceTest {

    @TestSetup
    static void setup() {
        Account account = TestDataFactory.createAccount();
        List<Asset> assets = TestDataFactory.createAssets(account.Id, 5);
        TestDataFactory.createCoverageFor(assets, 500000);
    }

    @IsTest
    static void claimsWithinCoverageAreApproved() {
        // the setup data must be queried; its variables are out of scope here
        Asset asset = [SELECT Id FROM Asset LIMIT 1];

        Warranty_Claim__c claim = new ClaimBuilder()
            .forAsset(asset.Id)
            .withAmount(400000)
            .create();
    }
}
```

**Records created in `@TestSetup` must be re-queried in the test method.** The setup method's local variables are gone.

**Changes made by one method are rolled back** before the next runs, so tests stay independent.

**One `@TestSetup` per class**, and it is incompatible with `SeeAllData=true`.

## When @TestSetup is worth it

**Worth it when:** every method in the class needs the same base data, and creating it is expensive. A class with fifteen tests each needing an account, five assets, and coverage saves fourteen setups.

**Not worth it when:** methods need different data. A `@TestSetup` creating everything any method might need, with each test using a fraction, is slower than per-method creation.

**A real trap:** a `@TestSetup` that fires triggers doing substantial work. That work happens once, which is good — and the restore between methods is not free either. Measure rather than assume.

## Fake Ids

For DML-free service tests, records need Ids that were never inserted.

```java
@IsTest
public class TestIdFactory {

    private static Integer counter = 1;

    public static Id generate(Schema.SObjectType objectType) {
        String prefix = objectType.getDescribe().getKeyPrefix();
        // a well-formed Id corresponding to no real record
        return Id.valueOf(prefix + String.valueOf(counter++).leftPad(12, '0'));
    }
}
```

```java
Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
    new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
};
```

This small utility is what makes the fast service tests in [[18.8 - Dependency Injection and Testability]] possible.

## Populating read-only fields

Formula fields, roll-up summaries, and relationship fields cannot be assigned. JSON deserialization can.

```java
@IsTest
public class TestRecordBuilder {

    public static Warranty_Claim__c claimWithRelationships(
        Id claimId, Integer daysOpen, String serialNumber, String accountName
    ) {
        // deserialization populates what direct assignment cannot
        Map<String, Object> shape = new Map<String, Object>{
            'Id' => claimId,
            'Claim_Number__c' => 'WC-' + String.valueOf(claimId).right(6),
            'Days_Open__c' => daysOpen,
            'Asset__r' => new Map<String, Object>{
                'SerialNumber' => serialNumber,
                'Account' => new Map<String, Object>{ 'Name' => accountName }
            }
        };

        return (Warranty_Claim__c) JSON.deserialize(
            JSON.serialize(shape), Warranty_Claim__c.class
        );
    }
}
```

A service reading `claim.Asset__r.Account.Name` can now be tested with no database at all — which is otherwise impossible, because relationship fields are only populated by a query. See [[09.11 - JSON Serialization and Deserialization]].

## Users

Creating a test user requires a `runAs` block, because `User` is a setup object.

```java
@IsTest
public class TestUserFactory {

    public static User create(String profileName, String permissionSetName) {
        User user;

        // runAs isolates the setup DML from any normal DML in the same test
        System.runAs(new User(Id = UserInfo.getUserId())) {
            Profile p = [SELECT Id FROM Profile WHERE Name = :profileName LIMIT 1];

            String unique = String.valueOf(System.currentTimeMillis())
                + String.valueOf(Math.round(Math.random() * 1000));

            user = new User(
                FirstName = 'Test',
                LastName = 'User' + unique,
                Email = 'test' + unique + '@example.com',
                // Username must be globally unique across all of Salesforce
                Username = 'test' + unique + '@northwind.test',
                Alias = unique.right(8),
                ProfileId = p.Id,
                TimeZoneSidKey = 'Asia/Kolkata',
                LocaleSidKey = 'en_IN',
                EmailEncodingKey = 'UTF-8',
                LanguageLocaleKey = 'en_US'
            );
            insert user;

            if (String.isNotBlank(permissionSetName)) {
                PermissionSet ps = [
                    SELECT Id FROM PermissionSet WHERE Name = :permissionSetName LIMIT 1
                ];
                insert new PermissionSetAssignment(AssigneeId = user.Id, PermissionSetId = ps.Id);
            }
        }
        return user;
    }
}
```

Three things this handles that hand-written user creation usually gets wrong: the `runAs` wrapper for mixed DML, the globally unique username, and the permission set assignment inside the same block. See [[10.7 - Mixed DML and Setup Objects]].

## Uniqueness

```java
private static Integer counter = 0;

private static String uniqueSuffix() {
    return String.valueOf(counter++).leftPad(6, '0');
}
```

**A counter, not a timestamp.** Two records created in the same millisecond get the same timestamp, which breaks a unique field constraint in a bulk test.

**Fields needing uniqueness:** anything marked Unique, external IDs, and `User.Username` — which must be unique across every Salesforce org, not just yours.

## Custom Settings in tests

**Custom Setting data is not visible in tests.** Every test needing one must create it.

```java
@IsTest
public class TestDataFactory {

    public static void setupDefaultSettings() {
        insert new Automation_Settings__c(
            SetupOwnerId = UserInfo.getOrganizationId(),
            Disable_All_Automation__c = false
        );
    }
}
```

Calling this from `@TestSetup` in every class with a bypass mechanism is standard. Custom Metadata records, by contrast, **are** visible — the asymmetry catches people. See [[17.2 - Custom Settings]].

## Keeping factories maintainable

**Mark everything `@IsTest`.** Test utilities annotated this way do not count toward the org's code size limit and cannot be called from production code.

**One factory per domain area** rather than one thousand-line class:

```
TestDataFactory        core records: accounts, assets, contracts
TestClaimFactory       claims, parts, payments
TestUserFactory        users and permission sets
TestScenarioFactory    complete valid scenarios
TestIdFactory          fake Ids
```

**Do not put assertions in factories.** A factory creates data; a test verifies behaviour.

**Do not query in factories** where an Id can be passed in. A factory querying for a record type or a profile on every call multiplies queries across the suite.

Where a lookup is unavoidable — a record type Id, a profile — cache it in a static:

```java
private static Map<String, Id> recordTypeCache = new Map<String, Id>();

public static Id claimRecordTypeId(String developerName) {
    if (!recordTypeCache.containsKey(developerName)) {
        recordTypeCache.put(developerName, Schema.SObjectType.Warranty_Claim__c
            .getRecordTypeInfosByDeveloperName().get(developerName).getRecordTypeId());
    }
    return recordTypeCache.get(developerName);
}
```

## Practical guidance

**Provide `build` and `create` variants** of every factory method.

**Use overloads with sensible defaults**, so tests specify only what they care about.

**Use a builder** where the combinations multiply.

**Return a scenario object** holding every created record.

**Use `@TestSetup`** when methods share base data, and re-query in the method.

**Build a `TestIdFactory`** — fast service tests depend on it.

**Use JSON deserialization** for formula and relationship fields.

**Create users inside `runAs`**, with a globally unique username.

**Use a counter, not a timestamp**, for uniqueness.

**Mark every test utility `@IsTest`.**
