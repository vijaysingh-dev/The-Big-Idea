# Account Hierarchies and Account Teams

## Account hierarchies

`ParentId` on Account is a self-lookup building a tree of corporate structure: a global parent, regional subsidiaries, individual operating sites.

The business case is straightforward. A manufacturer sells to Northwind Group, which has subsidiaries in four countries, each buying separately. Sales needs to see each subsidiary's activity individually *and* the total relationship with the group.

The platform provides the hierarchy and, notably, almost nothing that uses it.

## What the hierarchy does not do

Three assumptions people make, all wrong:

**Sharing does not follow the hierarchy.** Access to a parent account grants no access to its children. This surprises nearly everyone. If a global account manager should see all subsidiaries, that requires a sharing rule, a team, or Apex sharing — not the hierarchy.

**Roll-ups do not aggregate up the hierarchy.** There is no native way to sum opportunity amounts across an account and its children. `ParentId` is a lookup, not a master-detail relationship, so roll-up summary fields are not available even for direct children, let alone the whole tree.

**Reports do not group by hierarchy.** A standard report grouped by Account groups by the individual account. Rolling up to the ultimate parent requires a field holding that value.

## The ultimate parent pattern

Because of the above, most enterprise orgs add a lookup field — `Ultimate_Parent_Account__c` — pointing every account in a tree at the top of it, maintained by automation.

Reports then group on that one field instead of traversing. Sharing rules can target it. Roll-ups become possible by rolling child records up to the account and then aggregating by ultimate parent.

```java
public with sharing class AccountHierarchyService {

    public static void setUltimateParents(Set<Id> accountIds) {
        Map<Id, Id> parentByAccount = new Map<Id, Id>();
        for (Account acc : [SELECT Id, ParentId FROM Account WHERE ParentId != null]) {
            parentByAccount.put(acc.Id, acc.ParentId);
        }

        List<Account> toUpdate = new List<Account>();
        for (Id accountId : accountIds) {
            Id current = accountId;
            Id ultimate = accountId;
            Integer guard = 0;

            // walk upward in memory; the guard stops a cyclical hierarchy from looping forever
            while (parentByAccount.containsKey(current) && guard < 20) {
                current = parentByAccount.get(current);
                ultimate = current;
                guard++;
            }

            toUpdate.add(new Account(Id = accountId, Ultimate_Parent_Account__c = ultimate));
        }

        update toUpdate;
    }
}
```

The single query followed by an in-memory walk is the important structural choice — querying per level would cost one SOQL call per level of hierarchy depth.

Where this must be recalculated: when an account's `ParentId` changes, every descendant needs updating, not just that account. For a deep tree that is unbounded work and belongs in a Queueable or Batch job.

Cycle protection is not optional. A user setting account A's parent to its own descendant creates a loop, and without the guard the loop is infinite. A validation rule preventing self-reference plus the guard counter is the minimum. See [[02.9 - Hierarchical and Self Relationships]].

## Hierarchy depth

Nothing enforces a limit, and hierarchies of ten or more levels appear in real orgs, usually because somebody modelled legal entity structure rather than commercial structure.

The practical guidance: model the hierarchy the *sales organization* needs, which is usually three or four levels — global parent, regional entity, operating site. Legal structure belongs in the ERP.

A validation rule capping depth is worth adding, using a formula field that counts levels.

## Account Teams

An Account Team is a set of users attached to an account, each with a role and specified access levels.

```
Account: Northwind Manufacturing
  Account Manager        Read/Write on Account, Read/Write on Opportunities, Read on Cases
  Solution Architect     Read on Account, Read/Write on Opportunities
  Service Delivery Lead  Read on Account, Read/Write on Cases
  Executive Sponsor      Read on Account
```

This solves a problem the role hierarchy cannot: several people, in different parts of the org chart, all needing access to one customer's records without needing access to everyone else's.

The access levels are set per team member and cover Account, Contact, Opportunity, and Case independently. A team member can have Read/Write on opportunities and no case access at all.

```sql
SELECT AccountId, Account.Name, UserId, User.Name, TeamMemberRole,
       AccountAccessLevel, OpportunityAccessLevel, CaseAccessLevel, ContactAccessLevel
FROM AccountTeamMember
WHERE AccountId = :accountId
```

Team-granted access appears in the share table with `RowCause = 'Team'`, so it is visible in the standard diagnostic queries from [[03.10 - Manual, Team and Implicit Sharing]].

## Default teams

Each user can define a **default account team** that is added automatically to accounts they own. A rep who always works with the same solution architect and the same customer success manager configures it once.

This is what makes teams practical at scale. Without it, every account requires manual team setup and it does not happen.

Administrators can also add team members in bulk, and the team can be applied retroactively to existing accounts.

## Adding team members in code

```java
public with sharing class AccountTeamService {

    public static void addTeamMembers(Map<Id, Id> userByAccount, String role) {
        List<AccountTeamMember> members = new List<AccountTeamMember>();
        List<AccountShare> shares = new List<AccountShare>();

        for (Id accountId : userByAccount.keySet()) {
            Id userId = userByAccount.get(accountId);

            members.add(new AccountTeamMember(
                AccountId = accountId,
                UserId = userId,
                TeamMemberRole = role,
                AccountAccessLevel = 'Edit',
                OpportunityAccessLevel = 'Edit',
                CaseAccessLevel = 'Read'
            ));
        }

        Database.insert(members, false);
    }
}
```

A behaviour worth knowing: inserting an `AccountTeamMember` with access levels creates the corresponding share rows automatically. You do not insert `AccountShare` separately. Setting access levels to 'None' on the team member creates the team membership without granting access, which is occasionally what you want when the team is for visibility of *who is involved* rather than for access.

## Cost at scale

Every team member on every account is a share row, and those rows exist for Account plus each child object the access covers.

Five team members across a hundred thousand accounts, with opportunity and case access, is a very large share table. The consequences: slow sharing recalculation, long-running jobs when roles change, and locking during bulk operations.

The mitigation, as everywhere in sharing, is to **share to public groups where the set of people is stable** rather than adding individuals to teams. Teams are the right tool when membership genuinely varies per account; a group is better when the same people need access across many accounts. See [[03.11 - Apex Sharing and Programmatic Sharing]].

## Teams versus territories versus sharing rules

Three ways to give several people access to a set of accounts, and choosing correctly matters:

| Requirement | Use |
| --- | --- |
| Different people per account, varying by deal | Account Team |
| Same people for a whole segment or region | Sharing rule to a public group |
| Overlapping, criteria-driven coverage that changes annually | Territory Management |
| Manager needs their reports' accounts | Role hierarchy |

Using teams where a sharing rule would do produces an enormous share table for no benefit. Using sharing rules where teams are needed produces access that is too broad.

## Practical guidance

**Add an ultimate parent field.** Nearly every enterprise org needs it eventually, and adding it early is far cheaper than backfilling it across a million accounts.

**Cap hierarchy depth with validation.** Deep trees make every traversal expensive.

**Protect against cycles.** One cyclical account can hang every batch job that walks the hierarchy.

**Encourage default teams.** Manual team assembly per account does not happen.

**Watch share row growth on teams.** It is the most common cause of slow sharing recalculation in Sales Cloud orgs.

**Do not use the hierarchy for access without building it.** The most common misunderstanding in this note, and worth confirming explicitly whenever someone says "the parent account manager can see everything".
