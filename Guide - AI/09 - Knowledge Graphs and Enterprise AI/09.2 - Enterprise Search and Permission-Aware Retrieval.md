# Enterprise Search and Permission-Aware Retrieval

## What Makes Enterprise Search Different

Consumer search (Google) returns public results to all users identically. Enterprise search:

- Returns **different results to different users** based on permissions
- Covers **private, confidential, and access-controlled** content
- Must never surface documents a user isn't authorized to see
- Operates across **heterogeneous source systems** (Confluence, Slack, Drive, Jira, etc.)

This changes almost every architectural decision.

---

## The Multi-Source Problem

Enterprise knowledge is fragmented across dozens of tools:

```
Knowledge Silos:
├── Documentation (Confluence, Notion, GitBook)
├── Communication (Slack, Teams, Email)
├── Code (GitHub, GitLab)
├── Project Management (Jira, Linear, Asana)
├── Files (Google Drive, SharePoint, Dropbox)
├── CRM (Salesforce)
├── Ticketing (Zendesk, Freshdesk)
└── Custom internal tools
```

Each has:

- Different auth mechanisms (OAuth, SAML, API keys)
- Different permission models (user-level, group-level, role-based)
- Different content structures
- Different change notification mechanisms (webhooks, polling)

Enterprise search must unify all of these into a single coherent search experience.

## Permission Model Architecture

### Permission Inheritance

Enterprise systems have hierarchical permissions:

```
Organization
└── Space/Team (Engineering)
    ├── Project (Backend)
    │   ├── Document A (public to org)
    │   ├── Document B (restricted to Engineering)
    │   └── Document C (only Backend team)
    └── Slack Channel (only channel members)
```

When indexing, propagate the most restrictive applicable permission to each document:

```python
@dataclass
class DocumentACL:
    # All entities with read access to this document
    user_ids: set[str]           # explicit user grants
    group_ids: set[str]          # group-based access
    is_public_to_org: bool       # all org members can read
    is_public_to_all: bool       # completely public
    owner_id: str                # always has access

def resolve_effective_permissions(doc, source_connector) -> DocumentACL:
    # Walk up the permission hierarchy
    space_perms = source_connector.get_space_permissions(doc.space_id)
    page_perms = source_connector.get_page_permissions(doc.id)
    
    # Page permissions override space permissions
    if page_perms.is_restricted:
        return page_perms  # document-level restriction wins
    else:
        return merge_permissions(space_perms, page_perms)
```

### Flattening Permissions for Index Storage

Store flattened permission lists for each document to avoid runtime permission graph traversal:

```python
# At index time: flatten group membership to user lists
def flatten_permissions(acl: DocumentACL, group_member_store) -> FlatACL:
    all_user_ids = set(acl.user_ids)
    
    for group_id in acl.group_ids:
        members = group_member_store.get_members(group_id)
        all_user_ids.update(members)
    
    return FlatACL(user_ids=all_user_ids, is_public_to_org=acl.is_public_to_org)
```

**Problem with flattening**: When a user joins or leaves a group, you must re-index all documents that have that group's permissions. For large groups with many documents, this is expensive.

**Alternative**: Store group IDs (not expanded user IDs) and resolve at query time. Slower per query but more consistent.

```python
# At query time: get user's groups, then filter
def permission_aware_search(query, user_id, vector_store, group_store):
    user_groups = group_store.get_user_groups(user_id)
    
    results = vector_store.search(
        query=query,
        filter={
            "$or": [
                {"permitted_users": user_id},
                {"permitted_groups": {"$in": user_groups}},
                {"is_public_to_org": True},
            ]
        },
        top_k=100
    )
    return results
```

## Permission Sync Challenges

Permissions change continuously:

- User joins org → gains access to default content
- User leaves → loses all access immediately
- User joins team → gains access to team content
- Document shared explicitly → new user gains access

**Sync strategies**:

### Webhook-Based (Real-Time)

Subscribe to permission change events from source systems:

```python
@app.route("/webhook/google_drive/permissions", methods=["POST"])
def handle_permission_change(event):
    if event["type"] == "permission_added":
        update_document_permissions(event["file_id"], add_user=event["user_email"])
    elif event["type"] == "permission_removed":
        update_document_permissions(event["file_id"], remove_user=event["user_email"])
```

**Problem**: Not all sources support webhooks. Some (Confluence) have unreliable webhook delivery.

### Periodic Sync (Most Common)

Periodically re-fetch permissions for all documents:

```python
async def sync_permissions_batch(connector, index, batch_size=100):
    doc_ids = await index.list_all_document_ids(source=connector.name)
    
    for batch in chunked(doc_ids, batch_size):
        permissions = await connector.batch_get_permissions(batch)
        await index.batch_update_permissions(permissions)
    
    # How often: hourly for sensitive content, daily for stable content
```

### User-At-Query-Time Check

For highest-security systems: verify permissions at query time against the source system, don't cache:

```python
async def secure_search(query, user_id, results):
    # After retrieval, verify each result against source system in real-time
    authorized = []
    for result in results:
        is_authorized = await source_connector.check_permission(
            doc_id=result.doc_id, user_id=user_id
        )
        if is_authorized:
            authorized.append(result)
    return authorized
```

**Tradeoff**: Much slower (N API calls per query) but guaranteed accuracy. Use for highly sensitive content (legal, HR, finance).

## Cross-Source Search Experience

When searching across sources, the result experience must feel unified:

### Source Attribution

Always show where a result came from — users need to know context:

```
Result: "Parental leave is 16 weeks..."
Source: Confluence > HR > Benefits Guide (updated March 2024)
```

### Relevance Across Heterogeneous Content

A Slack message and a Confluence page about the same topic have very different structure. Ensure your chunking and embedding strategy handles this:

- Slack: include thread context, channel name, participants
- Confluence: include page title, space, breadcrumb
- GitHub: include repo, file path, surrounding code

### Freshness Signals

Show content age clearly — a Slack message from 2 years ago is far less authoritative than a document updated last week:

```python
def format_result_for_display(chunk):
    age = format_age(chunk.metadata["modified_at"])
    return {
        "title": chunk.metadata["title"],
        "source": f"{chunk.metadata['source']} — {age}",
        "content": chunk.text[:200] + "...",
        "url": chunk.metadata["url"],
    }
```

## Multi-Tenant Enterprise Deployment

For SaaS products selling to enterprises (like Onyx):

### Tenant Isolation

Complete isolation between customers is mandatory:

- Separate vector DB collections or namespaces per tenant
- Separate PostgreSQL schemas or databases per tenant
- No shared caches across tenant boundaries
- Row-level security on all shared tables

```python
def get_vector_store(tenant_id: str) -> VectorStore:
    # Each tenant has a separate Qdrant collection
    collection_name = f"tenant_{tenant_id}_documents"
    return QdrantVectorStore(collection=collection_name)
```

### Credential Management

Each tenant's connector credentials must be encrypted at rest and isolated:

```python
# Store encrypted per-tenant credentials
def store_connector_credentials(tenant_id, connector_type, credentials):
    encrypted = kms.encrypt(
        json.dumps(credentials),
        key_id=f"tenant/{tenant_id}/connector/{connector_type}"
    )
    db.insert("connector_credentials", {
        "tenant_id": tenant_id,
        "connector_type": connector_type,
        "encrypted_credentials": encrypted,
    })
```
