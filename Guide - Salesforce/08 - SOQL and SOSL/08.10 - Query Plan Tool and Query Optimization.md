# Query Plan Tool and Query Optimization

## Stop guessing

Selectivity is not something to reason about from first principles. The platform will tell you what it intends to do.

The **Query Plan tool** lives in the Developer Console: open the Query Editor, tick **Query Plan**, enter a query, and run it. It shows every access path the optimizer considered, ranked by cost.

## Reading the output

```
Cardinality  Fields              Leading Operation Type  Cost   sObject Cardinality
────────────────────────────────────────────────────────────────────────────────────
    12,400   [Status__c]         Index                   0.42   2,847,193
 2,847,193   []                  TableScan               2.81   2,847,193
```

The columns:

**Cost** — the number that matters. **Below 1.0 means the optimizer will use this path.** Above 1.0 means it will not, and a query whose only option is above 1.0 is non-selective.

**Leading Operation Type** — `Index` (a custom or standard index), `TableScan` (reading everything), `Other` (an internal optimization), `Sharing` (driven by the sharing table, which appears when the running user has limited access).

**Cardinality** — estimated rows this path returns.

**sObject Cardinality** — approximate total rows on the object.

**Fields** — which field's index this path uses.

A healthy query has at least one row with `Index` and a cost under 1.0. A query showing only `TableScan` will scan the object, and on a large one it will fail.

## A worked optimization

Start with a query that has become slow:

```sql
SELECT Id, Claim_Number__c, Claim_Amount__c
FROM Warranty_Claim__c
WHERE Status__c != 'Closed'
  AND Claim_Amount__c > 100000
```

Plan:

```
Cardinality  Fields    Leading Operation Type  Cost   sObject Cardinality
   890,000   []        TableScan               3.14   2,847,193
```

Only a table scan. `!=` cannot use an index, and `Claim_Amount__c` is not indexed.

**Step 1: replace negation with enumeration.**

```sql
WHERE Status__c IN ('Submitted', 'Under Review', 'Approved')
  AND Claim_Amount__c > 100000
```

```
Cardinality  Fields         Leading Operation Type  Cost   sObject Cardinality
   412,000   [Status__c]    Index                   1.87   2,847,193
   890,000   []             TableScan               3.14   2,847,193
```

Better — the index is now considered — but 412,000 of 2.8 million is about 14%, above the custom index threshold, so the cost is still over 1.0.

**Step 2: add a date filter using a standard index.**

```sql
WHERE Status__c IN ('Submitted', 'Under Review', 'Approved')
  AND Claim_Amount__c > 100000
  AND Claim_Date__c = LAST_N_MONTHS:6
```

```
Cardinality  Fields            Leading Operation Type  Cost   sObject Cardinality
    31,000   [Claim_Date__c]   Index                   0.24   2,847,193
   412,000   [Status__c]       Index                   1.87   2,847,193
   890,000   []                TableScan               3.14   2,847,193
```

Cost 0.24. The optimizer will use the date index, and the other filters are applied to the much smaller result.

The important insight from that sequence: **the fix was adding a filter, not removing one.** Narrowing the set with an indexed field is almost always the answer, and it is counterintuitive to anyone whose instinct is that fewer conditions run faster.

## When the business will not accept a narrower filter

"We need all open claims, not just the last six months" is a legitimate objection, and there are answers:

**Index the status field.** If open claims are genuinely a small fraction of the total, Support will index `Status__c` and it becomes selective. Ask.

**Add a maintained boolean.** `Is_Open__c`, set by a before-save flow, marked as an external ID so it is indexed. Selective if the true fraction is small.

**Archive.** If 2.5 million of 2.8 million claims are closed and years old, the real answer is that they should not be in the object. See [[23.4 - Archiving with Big Objects and External Storage]].

**Use Batch Apex.** `Database.getQueryLocator` in a batch context tolerates queries that would fail synchronously, because it streams rather than materializing. It is not a licence to write non-selective queries, and it is a legitimate tool for a genuinely large sweep.

## Where the sharing operation appears

A plan row with `Leading Operation Type: Sharing` means the optimizer intends to drive the query from the sharing table rather than the object.

This happens when the running user has access to a small fraction of records — a sales rep with 200 accounts out of 400,000. It is usually good: filtering by 200 share rows is far cheaper than scanning.

It becomes a problem when the running user has access to most records, because the sharing table is then no smaller than the object. This is one reason a query can be fast for a rep and slow for an administrator, which is a genuinely confusing symptom until you know to look for it.

## Notes in the plan

The tool includes a `Notes` section flagging specific problems:

- `Not considering filter for optimization because unindexed`
- `Not considering filter for optimization because the operator is not supported`
- `Filter is not selective enough`
- `Consider adding a filter on an indexed field`

Reading the notes is faster than inferring the cause from the cost numbers.

## Optimizing beyond selectivity

Selectivity dominates, and three other things matter.

**Select fewer fields.** Every field is data returned, heap consumed, and — for formula fields — computation per row. A query selecting forty fields including several cross-object formulas is expensive even when perfectly selective. See [[06.4 - Cross-Object Formulas and Limits]].

**Avoid `ORDER BY` on unindexed fields** over large result sets. The engine sorts the full set.

**Watch relationship traversal in `WHERE`.** `Asset__r.Account.Tier__c = 'Enterprise'` is work per candidate row, and it does not use an index on the child.

## Making it a habit

The practices that prevent query problems rather than fixing them:

**Check the plan for any query against an object expected to exceed a million rows.** Before writing the code around it, not after.

**Test in a Full sandbox with production volume.** A query is fast in a dev org with 500 records regardless of how it is written, which is precisely why selectivity bugs reach production.

**Read the limit block in debug logs.** Query count and rows retrieved appear at the end of every log:

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 43 out of 100
  Number of query rows: 28104 out of 50000
  Maximum CPU time: 6203 out of 10000
```

Rows approaching the limit is a signal to narrow filters before it becomes an incident.

**Watch for the failure modes.** `Non-selective query against large object type` is unambiguous. A gradual slowdown in a report or list view is the same problem arriving quietly.

## Monitoring in production

Beyond the Query Plan tool:

**Event Monitoring**, with Shield, logs slow queries and long-running requests with the actual SOQL. This is the only way to find the slow query nobody reported. See [[20.6 - Event Monitoring and Operational Visibility]].

**Debug logs** on a specific user during a slow operation.

**The Developer Console execution tree**, which attributes time per operation rather than per transaction. See [[20.3 - Developer Console and Log Inspector]].

## Section 08 in one paragraph

SOQL reads records with a deliberately narrow surface — no joins, no `SELECT *`, relationships traversed only through defined relationship fields, five levels up and one level down. Bind variables are the correct way to pass values everywhere, including in dynamic SOQL, and field names must be allowlisted because they cannot be bound. Aggregate queries push counting and summing into the database and are the answer whenever you would otherwise loop to accumulate. The constraint underlying everything is selectivity: a query needs at least one indexed filter matching a small enough fraction of rows, or the platform scans and eventually refuses. Negation, leading wildcards, `OR` across unindexed fields, and formula fields all defeat indexes, and the usual fix is adding a narrowing filter rather than removing one. Check the Query Plan rather than reasoning about it, and test against production-scale data, because none of these problems are visible in a small org.
