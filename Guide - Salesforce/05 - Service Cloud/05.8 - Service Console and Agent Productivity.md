# Service Console and Agent Productivity

## Why the console exists

A support agent handles thirty to fifty interactions a day. Every second of page load, every extra click, every context switch multiplies by that number.

The Service Console is a Lightning app configured for that reality: multiple records open at once, no navigation away from work in progress, and a utility bar holding tools that persist across everything.

For a developer, the console is where performance stops being a nice-to-have. A component taking two seconds to load costs an agent twenty-five minutes a day.

## The structure

**Console navigation.** Records open as workspace tabs. Related records open as subtabs inside the parent workspace, so a contact opened from a case stays nested under it. An agent can hold six cases open and switch between them without losing state.

**Split view.** A list of records down the left, the selected record on the right. The natural view for working a queue — click through cases without returning to a list each time.

**Utility bar.** A persistent strip at the bottom holding tools that survive tab changes: Omni-Channel, the phone softphone, notes, history, macros. Utility items keep their state, which is the whole point — a call in progress does not end because the agent opened another tab.

**Pinned regions.** Parts of the layout that stay fixed while the rest scrolls.

## Configuring for speed

The single biggest lever on agent efficiency is what the case page loads.

**Fewer components.** Every component on a record page is work at load time. A page with fourteen components, several making Apex calls, is slow in a way that no individual component owner notices.

**Dynamic Forms and Dynamic Actions.** Show fields and buttons conditionally rather than rendering everything always. A section only relevant to warranty claims should not render on billing cases. See [[04.14 - Path, Kanban and Sales Productivity]].

**Lazy-load below the fold.** Components in a tab the agent may never open should not fetch data until the tab is selected.

**Cacheable Apex.** Any read-only Apex method serving a component should be `@AuraEnabled(cacheable=true)` so results come from the client cache on repeat views.

```java
public with sharing class CaseContextController {

    @AuraEnabled(cacheable=true)
    public static CaseContext getContext(Id caseId) {
        Case c = [
            SELECT Id, AccountId, ContactId, Machine__c
            FROM Case WHERE Id = :caseId WITH USER_MODE
        ];

        return new CaseContext(
            openCasesForAccount(c.AccountId, caseId),
            activeEntitlements(c.AccountId),
            recentClaimsForMachine(c.Machine__c)
        );
    }
}
```

One method returning a composed object beats three separate wire calls — three network round trips become one. This matters more in the console than anywhere else in Salesforce.

## The 360-degree view

The recurring requirement: an agent picking up a case should see, without clicking, whether this customer is important, whether they are already unhappy, and what equipment is involved.

For Northwind that means on the case page:

- The account's entitlement tier and contract end date
- Other open cases for the same account
- The machine involved, its install date, and warranty status
- Recent warranty claims on that machine
- Open opportunities, so the agent knows a deal is in flight

That last one is the cross-cloud payoff. An agent about to tell a customer their claim is rejected benefits from knowing sales is negotiating a two crore expansion with them this week. Because Sales and Service share the same Account, this is a query rather than an integration.

```java
@AuraEnabled(cacheable=true)
public static List<Opportunity> getOpenDeals(Id accountId) {
    return [
        SELECT Id, Name, Amount, StageName, CloseDate, Owner.Name
        FROM Opportunity
        WHERE AccountId = :accountId AND IsClosed = false
        WITH USER_MODE
        ORDER BY Amount DESC
        LIMIT 5
    ];
}
```

`WITH USER_MODE` matters here specifically: service agents may not have Opportunity access at all, in which case this throws rather than leaking commercial data. The component should handle that gracefully and render nothing. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Console-specific JavaScript APIs

Lightning provides console APIs available only inside a console app.

```javascript
import { LightningElement, api, wire } from 'lwc';
import { IsConsoleNavigation, openTab, closeTab, getFocusedTabInfo,
         setTabLabel, setTabIcon } from 'lightning/platformWorkspaceApi';

export default class CaseWorkspaceActions extends LightningElement {
    @api recordId;

    @wire(IsConsoleNavigation) isConsole;

    async openRelatedMachine(machineId) {
        if (!this.isConsole) {
            return;
        }
        const { tabId } = await getFocusedTabInfo();
        await openTab({ recordId: machineId, parentTabId: tabId, focus: true });
    }

    async markTabUrgent() {
        const { tabId } = await getFocusedTabInfo();
        await setTabIcon({ tabId, iconName: 'utility:warning' });
        await setTabLabel({ tabId, label: 'URGENT — ' + this.caseNumber });
    }

    async closeAfterResolution() {
        const { tabId } = await getFocusedTabInfo();
        await closeTab(tabId);
    }
}
```

The `IsConsoleNavigation` wire guard is necessary — the same component may be placed on a standard record page where these APIs do not exist, and calling them there fails.

Practical uses: opening a related record as a subtab rather than navigating away, closing the tab after a case is resolved so the agent's workspace stays clean, and changing the tab label or icon to flag urgency.

## Keyboard shortcuts

The console supports keyboard shortcuts for tab navigation, opening the utility bar, and custom actions. Agents who use them are meaningfully faster, and custom shortcuts can be registered for LWC actions.

Underused, and worth configuring for the three or four actions an agent performs most.

## Quick actions and Dynamic Actions

The console page should surface the small number of actions relevant right now — Escalate, Request Parts, Log Site Visit, Close with Resolution — not a row of twenty buttons.

**Dynamic Actions** show buttons conditionally, so Escalate appears only on unescalated cases above a priority threshold. This is the single cheapest improvement to a cluttered console page.

Actions themselves should be quick actions or LWC screen actions opening in a modal, not navigation to another page. See [[14.19 - Deploying and Exposing Components]].

## Multi-monitor and pop-out

Console tabs can be popped out into separate browser windows, which agents with two screens use constantly — the case on one monitor, the knowledge article on the other.

Worth knowing because components must not assume they are in the main window, and anything relying on window-level state can break when popped out.

## Measuring console performance

Salesforce provides the **Lightning Usage App** and browser-based performance tooling, and both are worth using before agents complain.

The diagnostic sequence when a page is slow:

1. Count components on the page; each is load cost
2. Check which make Apex calls, and whether those are cacheable
3. Look for a component fetching a large related list
4. Check for a component doing describe calls on every render
5. Consider whether some components belong in a tab rather than the main view

A common finding: one component querying five hundred related records to display a count, when a roll-up field would do. See [[16.10 - Performance Profiling Workflow]].

## Practical guidance

**Design the case page around the first ten seconds.** What must the agent see before touching anything.

**Ruthlessly limit components.** Each one costs every agent, every case, every day.

**Compose Apex calls.** One method returning a structured response beats several wire adapters.

**Use Dynamic Forms and Dynamic Actions** rather than record type proliferation for layout variation.

**Guard console APIs with `IsConsoleNavigation`.**

**Sit with agents before building.** The gap between what a requirements document says and what an agent actually needs on screen is larger in support than anywhere else, and an hour of observation prevents months of iteration.
