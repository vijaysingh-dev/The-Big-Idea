# Apex Questions

## Language fundamentals

**What is different about Apex compared to Java?**

The database is in the language — SOQL and DML are syntax, not a library. Everything runs under governor limits shared with whatever else is in the transaction. Statics live for one transaction and reset at every async boundary. There are no generics beyond collections, so reusable utilities work with `SObject` and cast at the call site. And nothing enforces security by default — sharing, CRUD, and field-level security are all the developer's responsibility.

The one that shapes code most is the limits. Every method takes a collection, because every entry point can hand you 200 records.

**Explain the collection types and when you use each.**

`List` for ordered data and anything that goes to DML. `Set` for uniqueness and containment checks — `contains()` is constant time, whereas a list scan is linear, which matters inside a loop. `Map` for lookups by key, which is what turns a nested loop into a single pass.

The pattern that comes up constantly is `Map<Id, SObject>` from a query, so a child can find its parent without a query per record.

Worth mentioning: `new Map<Id, Account>(accounts)` is a built-in constructor. Writing a loop to build it is the kind of thing that suggests unfamiliarity.

**How do static variables behave?**

They live for the transaction, not the request and not the session. They reset at every async boundary — a Queueable, a batch chunk, a platform event subscriber all start fresh.

That makes them right for two things: describe caching and recursion guards. And wrong for anything holding business state, because a static accumulating records across a transaction is a hidden dependency that makes tests order-dependent.

The specific trap is a boolean recursion guard. A static persists for the whole transaction, so a 400-record data load arriving as two chunks of 200 sets the flag on the first and silently skips the second. No error, 200 records unprocessed. The fix is tracking record Ids rather than a boolean.

**What happens to a static after a rollback?**

Nothing — statics are not rolled back. So a savepoint rollback discards the DML and leaves the recursion guard showing those records as processed, and a retry silently skips them. Resetting the guard after a rollback is necessary and easy to forget.

## Exceptions

**How do you handle exceptions in Apex?**

Catch what you can act on, and let the rest propagate. An empty catch block is never acceptable — it converts a failure into wrong data.

The important constraint is that `LimitException` cannot be caught. That is deliberate: if it were catchable, code could swallow it and keep consuming, which defeats the mechanism. The design consequence is that you cannot recover from a limit failure, so you design not to approach one.

In a trigger, `addError` rather than throwing — it blocks one record and, with partial-success DML, lets the others through. In an `@AuraEnabled` method, `AuraHandledException` with a message written for the user, because an uncaught exception surfaces as "an internal server error has occurred", which tells nobody anything.

**How do you log an error that gets rolled back?**

That is the interesting part. A log record inserted in the same transaction as the failure is rolled back with it.

Three mechanisms. A platform event published with immediate behaviour survives rollback by design — that is what it is for. A Transaction Finalizer runs in its own transaction after a Queueable fails, so a plain insert works there. Or catch, roll back to a savepoint, and insert the log afterwards.

For synchronous code the platform event is the general answer; for async, the Finalizer.

## Design and structure

**Describe how you structure Apex.**

Trigger routes to a handler, handler dispatches by event, service does the work, selector queries, and a unit of work batches DML if the org is large enough to need one.

The constraint that makes it worthwhile is that **a service never reads `Trigger` context**. It takes a `List` and a `Map` as parameters. That single rule means the same logic runs from a trigger, a batch job, a flow action, a REST endpoint, and a test with constructed records.

The testing payoff is the real argument. A service taking collections is testable with records built in memory — no DML, no queries, milliseconds. A service reading `Trigger.new` can only be tested by inserting records and firing a trigger. On a suite of a thousand tests that is the difference between three minutes and forty.

**When do selectors earn their place?**

When the same query appears in three services, when query count is a live concern, or when `WITH USER_MODE` keeps getting forgotten.

That last one is the strongest argument — putting security enforcement in the selector means callers cannot forget it. It removes a whole category of security review finding by construction.

The design decision within a selector is the return shape. Returning a flat list where every caller then builds the same map has moved the query and left the duplication. Returning a `Map<Id, List<Child>>` is what prevents a per-record query at the call site.

**What about fflib — would you use it?**

It depends on the org, and I would be cautious about adopting it reflexively.

What it genuinely provides is the mocking infrastructure — mocked selectors and unit of work mean service tests with no DML at all. The layering itself is achievable without the framework.

The costs are real: a domain, a domain constructor, a selector, a selector interface, a service, a service interface, and an implementation, for one object's behaviour. A learning curve measured in weeks. And it is all-or-nothing — half-adopting produces a codebase where some code is layered and mockable and some is not, and nobody is sure which.

I would adopt it in a large, long-lived org with several developers where test execution time is a real problem. In an org with eight triggered objects and one developer it is more structure than the problem requires, and that is a common and expensive mistake.

**Where would you use an interface?**

Three places, mainly.

A strategy, where a calculation varies by some attribute and there are three or more real variants — a discount by coverage level, driven by a factory reading Custom Metadata, so adding a variant is a class and a metadata record rather than editing a conditional chain.

A seam for testing — a selector or a callout client behind an interface, so a test can substitute a stub with `Test.createStub`.

And a contract in a package, where the global surface must stay stable while the implementation changes.

I would not reach for one where there are two branches of one line each. That is a conditional, and three files is not an improvement.

## Security in Apex

**How do you enforce security in Apex?**

Declare a sharing keyword on every class — one with none runs without sharing when it is the entry point, which for an `@AuraEnabled` method means no record-level security at all.

`WITH USER_MODE` on queries, which nulls fields the user cannot read rather than throwing. `as user` on DML. `stripInaccessible` on any sObject arriving from the client, because otherwise a component rendering three fields can be used to write to any field on the object.

And verify entitlement for client-supplied record Ids. `WITH USER_MODE` enforces sharing, so that covers it where the sharing model is the control — but where it is not, an explicit check, returning not-found rather than not-permitted so the response does not confirm the record exists.

**Someone writes `without sharing` — when is that acceptable?**

When there is a stated reason and the scope is narrow.

The pattern that passes a security review is a private `without sharing` inner class doing one thing, called from a `with sharing` service, with a comment explaining why and an entitlement check before the elevation.

The legitimate case is usually an aggregate — a total the user is authorized to see, computed across records they cannot see individually. Elevating the whole service to get it is what makes it a finding.

## Testing

**What makes a good test?**

It asserts something meaningful, it fails when the behaviour breaks, it is fast, and it is deterministic.

The check I would apply is mutation: comment out a line of the code under test — does the test fail? If not, it was measuring coverage rather than behaviour.

The cases that matter: the happy path, the boundaries — a claim exactly at the coverage limit, because that is where off-by-one lives — nulls and empties, bulk with 200 records, and negative cases.

**Why 200 records specifically, and does the distribution matter?**

200 because that is the trigger batch size, and a single-record test proves nothing about bulk safety — a query in a loop passes it and dies in production.

The distribution matters as much as the count. 200 claims across 200 assets passes even with a broken aggregation, because every parent has exactly one child. 200 across 50 does not. Several children per parent, always.

**How do you test something that has no DML?**

Construct the records in memory with fake Ids. A small `TestIdFactory` generating a well-formed Id from the object's key prefix is what makes that possible.

For formula fields and relationship fields, which cannot be assigned, JSON deserialization populates them:

```java
Warranty_Claim__c claim = (Warranty_Claim__c) JSON.deserialize(
    '{"Id":"' + fakeId + '","Days_Open__c":45,"Asset__r":{"SerialNumber":"SN-1"}}',
    Warranty_Claim__c.class
);
```

That lets a service reading `claim.Asset__r.SerialNumber` be tested with no database at all, which is otherwise impossible because relationship fields are only populated by a query.

**Coverage is at 76% and the deployment passed. Is that fine?**

It deployed, which is what 75% buys. It says nothing about quality.

Coverage measures what executed, not what was verified. A test with no assertions produces the same number as one that verifies behaviour. A codebase at 78% with meaningful assertions is in better shape than one at 95% with none.

What I would actually measure: assertion density, whether tests fail under mutation, execution time, and coverage on the classes that change often rather than the org-wide figure — which hides untested classes behind a few heavily-covered ones.

## Practical judgement

**How do you decide between a trigger, a flow, and an invocable action called from a flow?**

Trigger when the logic is complex, needs real bulk safety, or must be testable — which for anything carrying money it does.

Flow when it is straightforward record automation an administrator will maintain, and before-save specifically for same-record field updates.

The hybrid — a flow orchestrating invocable Apex — when the process should be admin-visible but the logic should be tested. The invocable receives every row at once, which is what keeps it bulk-safe from a flow, and that matters because a flow with a Get Records element runs it per record.

**You inherit an org with four triggers on one object. What do you do?**

Not rewrite it immediately, which is the instinct.

Trigger execution order on one object is undefined, so it is a real problem — one trigger setting a field another reads produces intermittently wrong behaviour that works in the sandbox.

The sequence I would use: inventory what exists and where it is used. Then write characterization tests asserting the current behaviour, correct or not — that is the step that gets cut and the one that makes the consolidation verifiable. Then move logic into services one at a time, leaving the triggers calling them. Then create the single trigger and handler with a deliberate order. Then deactivate the old triggers rather than deleting them, so a rollback is a metadata change. Delete after a full business cycle.

The characterization tests are the part I would insist on. Without them, consolidation is a rewrite with no way to prove equivalence.

## What is being assessed

**Junior:** knows the syntax and the collections, can write a bulkified method.

**Mid:** knows why statics reset, why limits cannot be caught, structures code into services.

**Senior:** discusses tradeoffs unprompted — when fflib is over-engineering, when a selector earns its place, what characterization tests are for.

**The tell is qualified answers.** "It depends on the org, and here is what it depends on" is a stronger signal than any single correct answer.
