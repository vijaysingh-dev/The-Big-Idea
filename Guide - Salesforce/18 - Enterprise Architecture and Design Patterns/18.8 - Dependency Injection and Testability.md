# Dependency Injection and Testability

## The problem

```java
public with sharing class ClaimApprovalService {

    public static void approve(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Amount__c, Asset__c FROM Warranty_Claim__c WHERE Id IN :claimIds
        ];

        for (Warranty_Claim__c claim : claims) {
            claim.Status__c = 'Approved';
        }
        update claims;

        ErpClient.notifyApproval(claimIds);
    }
}
```

Testing this requires: inserting claims, firing every trigger on the object, mocking the HTTP callout, and querying afterwards to verify. It takes seconds rather than milliseconds, and most of what it exercises is not the logic under test.

**Dependency injection** replaces the hardcoded collaborators with ones the test can substitute.

## The seams

Three places worth making injectable, in order of value.

**Queries** — so tests supply records without DML.
**DML** — so tests verify what would be written without writing it.
**Callouts** — so tests verify the request without an HTTP mock.

Everything else is usually not worth the indirection.

## Constructor injection

The simplest form, and the one to reach for first.

```java
public with sharing class ClaimApprovalService {

    private final IClaimSelector selector;
    private final IUnitOfWork uow;

    public ClaimApprovalService() {
        this(new ClaimSelector(), UnitOfWork.newInstance(INSERT_ORDER));
    }

    // the test uses this constructor; production uses the one above
    @TestVisible
    private ClaimApprovalService(IClaimSelector selector, IUnitOfWork uow) {
        this.selector = selector;
        this.uow = uow;
    }

    public void approve(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = selector.byIds(claimIds);

        for (Warranty_Claim__c claim : claims) {
            claim.Status__c = 'Approved';
            uow.registerDirty(claim);
        }

        uow.commitWork();
    }
}
```

Two constructors: a public one wiring the real implementations, and a `@TestVisible` one taking substitutes. The call site is unchanged.

**`@TestVisible` on a private member makes it visible to test classes only**, which keeps the injection point out of the public API.

## Static injection

For services that are genuinely static, a settable static field works:

```java
public with sharing class ClaimApprovalService {

    @TestVisible
    private static IClaimSelector selector = new ClaimSelector();

    public static void approve(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = selector.byIds(claimIds);
    }
}
```

```java
@IsTest
static void approvalSkipsClaimsOverTheCoverageLimit() {
    ClaimApprovalService.selector = new MockClaimSelector(claimsToReturn);
}
```

Simpler, and the static persists for the transaction — so a test must reset it if other tests in the class depend on the real one. A `@TestVisible` reset method is worth having.

## The Stub API

Apex's built-in mocking, needing no framework.

```java
@IsTest
public class MockClaimSelector implements System.StubProvider {

    private final List<Warranty_Claim__c> claimsToReturn;
    public Integer byIdsCallCount = 0;

    public MockClaimSelector(List<Warranty_Claim__c> claimsToReturn) {
        this.claimsToReturn = claimsToReturn;
    }

    public Object handleMethodCall(
        Object stubbedObject,
        String methodName,
        Type returnType,
        List<Type> paramTypes,
        List<String> paramNames,
        List<Object> args
    ) {
        // one method handles every call on the stubbed interface
        switch on methodName {
            when 'byIds' {
                byIdsCallCount++;
                return claimsToReturn;
            }
            when else {
                return null;
            }
        }
    }

    public IClaimSelector stub() {
        return (IClaimSelector) Test.createStub(IClaimSelector.class, this);
    }
}
```

```java
@IsTest
static void approvalRegistersEachClaimAsDirty() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

    MockClaimSelector selectorMock = new MockClaimSelector(new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Claim_Amount__c = 150000, Status__c = 'Submitted')
    });
    MockUnitOfWork uowMock = new MockUnitOfWork();

    ClaimApprovalService service = new ClaimApprovalService(selectorMock.stub(), uowMock);

    Test.startTest();
    service.approve(new Set<Id>{ claimId });
    Test.stopTest();

    Assert.areEqual(1, uowMock.dirtyRecords.size(), 'The claim should be registered dirty');
    Assert.areEqual('Approved',
        ((Warranty_Claim__c) uowMock.dirtyRecords[0]).Status__c);
    Assert.isTrue(uowMock.commitCalled);
}
```

**`Test.createStub` only works on interfaces and virtual or abstract classes.** A concrete class with no interface cannot be stubbed, which is why the seams need interfaces.

**Stubs can only be created in a test context**, which is a deliberate restriction.

## Hand-written mocks

Frequently simpler than a stub provider, and perfectly legitimate:

```java
@IsTest
public class MockUnitOfWork implements IUnitOfWork {

    public List<SObject> newRecords = new List<SObject>();
    public List<SObject> dirtyRecords = new List<SObject>();
    public Boolean commitCalled = false;

    public void registerNew(SObject record) {
        newRecords.add(record);
    }

    public void registerNew(SObject child, SObjectField field, SObject parent) {
        newRecords.add(child);
    }

    public void registerDirty(SObject record) {
        dirtyRecords.add(record);
    }

    public void commitWork() {
        commitCalled = true;
    }
}
```

Twenty lines, no framework, and the assertions read plainly. **For a small number of seams, hand-written mocks beat a mocking framework** — the framework earns its place when there are dozens.

## Generating fake Ids

Testing without DML means records need Ids that were never inserted.

```java
@IsTest
public class TestIdFactory {

    private static Integer counter = 1;

    public static Id generate(Schema.SObjectType objectType) {
        String prefix = objectType.getDescribe().getKeyPrefix();
        // a valid-format Id that corresponds to no real record
        String suffix = String.valueOf(counter++).leftPad(12, '0');
        return Id.valueOf(prefix + suffix);
    }
}
```

This is the small utility that makes DML-free testing possible. Without it, every test needs an insert simply to obtain an Id.

## Setting read-only fields in tests

Formula fields, roll-up summaries, and system fields cannot be assigned. JSON deserialization bypasses that:

```java
@IsTest
public class TestRecordBuilder {

    public static Warranty_Claim__c claimWithFormulas(Id claimId, Integer daysOpen, String serial) {
        // deserialization can populate fields that direct assignment cannot
        String json = JSON.serialize(new Map<String, Object>{
            'Id' => claimId,
            'Claim_Number__c' => 'WC-TEST',
            'Days_Open__c' => daysOpen,
            'Asset__r' => new Map<String, Object>{ 'SerialNumber' => serial }
        });

        return (Warranty_Claim__c) JSON.deserialize(json, Warranty_Claim__c.class);
    }
}
```

This also populates **relationship fields** without querying, which is what lets a service reading `claim.Asset__r.SerialNumber` be tested with no database at all. See [[09.11 - JSON Serialization and Deserialization]].

## Injecting callouts

```java
public interface IErpClient {
    ErpResponse submitClaim(Warranty_Claim__c claim);
}
```

```java
public with sharing class ClaimSubmissionService {

    @TestVisible
    private static IErpClient erpClient = new ErpClient();

    public static void submit(List<Warranty_Claim__c> claims) {
        for (Warranty_Claim__c claim : claims) {
            ErpResponse response = erpClient.submitClaim(claim);
            claim.ERP_Confirmation__c = response.confirmationNumber;
        }
    }
}
```

```java
@IsTest
static void confirmationNumberIsStoredOnTheClaim() {
    // an interface mock is clearer than an HttpCalloutMock, and tests the logic not the HTTP
    ClaimSubmissionService.erpClient = new MockErpClient('ERP-4471');

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Claim_Number__c = 'WC-001')
    };

    Test.startTest();
    ClaimSubmissionService.submit(claims);
    Test.stopTest();

    Assert.areEqual('ERP-4471', claims[0].ERP_Confirmation__c);
}
```

**Both layers are worth testing:** the interface mock verifies the service's logic; an `HttpCalloutMock` test on `ErpClient` itself verifies the request construction and response parsing. Testing them separately is clearer than one test doing both. See [[19.5 - Mocking Callouts]].

## Injecting time

An underrated seam. Code calling `Date.today()` cannot be tested at a boundary.

```java
public with sharing class ClockService {

    @TestVisible
    private static Date todayOverride;

    public static Date today() {
        return todayOverride ?? Date.today();
    }

    public static Datetime now() {
        return nowOverride ?? Datetime.now();
    }
}
```

```java
@IsTest
static void claimsExpireExactlyOnTheCoverageEndDate() {
    ClockService.todayOverride = Date.newInstance(2026, 12, 31);

    Assert.isFalse(CoverageService.isExpired(coverageEndingOn(2026, 12, 31)),
        'Coverage should be valid on its final day');
}
```

Boundary conditions around dates are where date bugs live, and without an injectable clock they can only be tested by contriving data relative to today — which is fragile and often wrong.

## How much to inject

The calibration, because over-injection is a real cost.

**Always worth it:** callouts, and time where dates drive logic.

**Usually worth it in a large codebase:** queries and DML, so services test without the database.

**Rarely worth it:** utility classes, formatters, and anything with no side effects. Injecting a string formatter adds an interface, a mock, and a wiring line for no benefit.

**The test to apply:** does this dependency make the test slow, non-deterministic, or dependent on org state? If not, leave it concrete.

**The counter-pressure:** every interface is a file, every mock is a file, and a codebase where following a call means opening four files to find the implementation has traded one problem for another. In a small org, `Test.setMock` for callouts and real DML for everything else is entirely reasonable — Apex tests are slow but not prohibitively so at that scale.

## The payoff, quantified

A mature suite with injection at the query and DML seams looks like:

```
600 service tests, no DML          ~90 seconds
80 selector tests, real data       ~120 seconds
40 handler tests, real DML         ~180 seconds
```

The same suite without injection, where every test inserts records and fires triggers, is comfortably over twenty minutes — and a twenty-minute suite is one developers stop running before pushing.

**That is the argument.** Not architectural purity: feedback speed. See [[19.1 - Apex Testing Fundamentals]].

## Practical guidance

**Inject at three seams:** queries, DML, and callouts.

**Use two constructors** — public wiring the real implementations, `@TestVisible` taking substitutes.

**Interfaces are required** for `Test.createStub`.

**Hand-written mocks are fine** and often clearer than a framework for a handful of seams.

**Build a `TestIdFactory`** — DML-free testing depends on it.

**Use JSON deserialization** to populate formula and relationship fields in tests.

**Inject the clock** where dates drive logic.

**Do not inject what does not need it.** Every interface is a file.
