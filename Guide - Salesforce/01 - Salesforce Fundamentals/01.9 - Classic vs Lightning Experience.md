# Classic vs Lightning Experience

## What actually changed

Salesforce Classic was the original interface, built as server-rendered pages. Lightning Experience, introduced in 2015, replaced it with a client-side application built on components.

The important thing to be clear about: this was a **user interface change, not a platform change**. Your objects, fields, records, Apex, sharing model, and APIs are identical in both. The same org can have some users in Classic and some in Lightning at the same time, looking at the same data.

That is why this note is short on features and longer on consequences.

## What is different for users

- Lightning is component-based, so pages are assembled from building blocks arranged in the Lightning App Builder rather than fixed layouts
- Record pages get tabs, highlights panels, and a related-list layout Classic never had
- Sales-specific features exist only in Lightning: Path, Kanban board, Opportunity workspace, Einstein features
- The Service Console in Lightning is substantially more capable than its Classic predecessor
- Reports and dashboards were rebuilt with better filtering and charting
- Lightning is genuinely heavier in the browser, which is why performance complaints exist and why component design matters

Since roughly 2019, all new feature investment goes to Lightning only. Classic receives security fixes and nothing else.

## What is different for developers

This is where the practical impact lives.

**URLs changed shape.** Classic used the record ID directly. Lightning uses a routed path.

```
Classic:   https://myorg.my.salesforce.com/0015g00000XyZaAAAV
Lightning: https://myorg.lightning.force.com/lightning/r/Account/0015g00000XyZaAAAV/view
```

Any code, email template, or integration that builds a record link by concatenating the instance URL and an ID produces a Classic URL. It usually still redirects, but not always, and not in every context. Build links properly instead:

```java
// Constructs the correct URL for the user's current experience
String recordUrl = URL.getOrgDomainUrl().toExternalForm()
                   + '/lightning/r/Account/' + accountId + '/view';
```

In a Lightning Web Component, do not construct URLs at all — use the navigation service, which handles Experience Cloud sites and the mobile app correctly too. See [[14.14 - Navigation and NavigationMixin]].

**JavaScript buttons do not work in Lightning.** Classic allowed custom buttons containing arbitrary JavaScript, and orgs used them heavily. Lightning does not support them at all, for security reasons. Every one must be rebuilt as a Lightning Web Component, a quick action, or a flow. In a migration project this is often the single largest chunk of work.

**Visualforce still runs, but inside a frame.** Visualforce pages continue to work in Lightning, rendered in an iframe. That means the page cannot directly manipulate the surrounding Lightning page, styling does not match unless you opt in, and navigation needs care. Salesforce provides `sforce.one` and the Lightning Out mechanism for this, but the friction is real.

**Some styling and behaviour assumptions break.** Pages that assumed the Classic header, sidebar, or standard stylesheet look wrong. The Lightning Design System (SLDS) is the styling standard now.

**A few things still redirect to Classic.** Parts of Setup and some older features still open in the Classic interface. This is normal, and it means Classic knowledge has not fully expired.

Code can check where it is running, which matters for anything that renders differently:

```java
if (UserInfo.getUiThemeDisplayed() == 'Theme4d') {
    // Lightning Experience
} else if (UserInfo.getUiThemeDisplayed() == 'Theme3') {
    // Salesforce Classic
}
```

The theme values are unmemorable: `Theme3` is Classic, `Theme4d` is Lightning Experience, `Theme4t` is the Salesforce mobile app, `Theme4u` is a Lightning console app.

## Why any of this still matters in 2026

You might reasonably ask why a course written now spends time on an interface that is a decade old.

**Orgs are old.** A fifteen-year-old enterprise org contains Visualforce pages, JavaScript buttons that were converted badly, Aura components written during the first migration wave, and Lightning Web Components written last year. All at once. You will maintain all of it.

**Migration projects are still happening.** Plenty of large organizations moved late or partially, and some still have Classic users in specific teams.

**The debugging value is real.** When a user reports that a button does nothing, knowing that JavaScript buttons silently do nothing in Lightning turns a two-day investigation into a two-minute answer.

**Interview questions come up.** The differences, and how to migrate a Classic customization, are standard mid-level interview material.

## How a migration is actually done

Useful to know even if you never lead one, because it explains the shape of legacy code you inherit.

1. **Run the Lightning Experience Readiness Check.** A Salesforce tool that scans the org and reports what will not carry over.
2. **Inventory the customizations.** JavaScript buttons, Visualforce pages, custom links, s-controls if the org is truly old.
3. **Rebuild rather than port.** A JavaScript button becomes a quick action, a flow, or a Lightning Web Component. Porting the old logic literally usually produces something worse than a rebuild.
4. **Design record pages in App Builder.** Lightning record pages are metadata and can be assigned by app, record type, and profile, which is a genuine improvement over Classic layouts.
5. **Migrate in waves by user group,** with both interfaces live simultaneously.
6. **Train, then remove the switch.** Users can be permitted or forbidden to switch back, and eventually the option is removed.

## Practical guidance for new work

Build for Lightning. Use Lightning Web Components for new UI, quick actions and flows instead of buttons with logic, and the navigation service instead of constructed URLs. Test in both interfaces only if the org still genuinely has Classic users, and confirm that rather than assuming it.

When you encounter Visualforce in a modern org, the question is not "should this be rewritten" but "is it worth rewriting". A stable Visualforce page that works is not a defect. A Visualforce page that breaks every release is. See [[14.19 - Deploying and Exposing Components]].
