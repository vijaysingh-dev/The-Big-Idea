# Record-Triggered Flows

## The configuration that defines behaviour

Four choices when creating one, and they determine everything:

**Object** — what it runs on.

**Trigger** — created, updated, created or updated, or deleted.

**Entry conditions** — a filter deciding whether the flow runs for this record.

**Timing** — before save, after save, or scheduled paths. See [[07.4 - Before-Save vs After-Save Flows]].

## Entry conditions matter more than they look

The entry condition is the flow's most important performance feature. A flow with no conditions runs on **every** save of that object, evaluating its logic every time, consuming CPU on records it will do nothing to.

On a high-volume object — Case at 80,000 records a year, each edited several times — that is a measurable and entirely avoidable cost.

Three condition settings:

**All conditions are met (AND)** or **any condition is met (OR)** — the simple cases.

**Custom condition logic** — expression syntax like `1 AND (2 OR 3)`.

**Formula evaluates to true** — the full formula language, which is what you need for anything involving `ISCHANGED` or a comparison against a prior value.

And separately, the option that matters most on update triggers:

**Only when a record is updated to meet the condition requirements.**

This is flow's built-in change detection. With it, the flow runs only on the save where the record *transitions* into meeting the condition — not on every subsequent save while it still meets it.

Without it, a flow with the condition `Status = 'Approved'` runs on every single edit of every approved claim, forever. That is the difference between a flow that fires once and one that fires two hundred times over a record's life.

Always consider it on update triggers. It is the flow equivalent of comparing against `Trigger.oldMap`.

## Accessing the record

**`$Record`** — the triggering record, with its new values.

**`$Record__Prior`** — the record's values before this save, available in update contexts only. The equivalent of `Trigger.oldMap.get(record.Id)`.

```
// Entry condition formula: fired only when the amount increased
AND(
  ISCHANGED({!$Record.Approved_Amount__c}),
  {!$Record.Approved_Amount__c} > {!$Record__Prior.Approved_Amount__c}
)
```

`$Record` supports relationship traversal, which is genuinely useful and quietly expensive:

```
{!$Record.Account__r.Owner.Email}
{!$Record.Asset__r.Account.BillingCountry}
```

Each traversal is work the platform does per record. In a bulk save of 200 records that is 200 traversals, and deep chains multiply. Where the same parent data is needed repeatedly, a Get Records element fetching it once is cheaper than traversing per record.

## Bulk behaviour

**A record-triggered flow runs once per record**, not once per batch. Save 200 records and the flow executes 200 times.

The platform does some optimization — DML from multiple flow executions in the same transaction is batched — but queries generally are not. A Get Records element in a flow triggered on 200 records issues up to 200 queries against a 100-query limit.

This is the central limitation of record-triggered flows at scale, and it is invisible on the canvas. There is no flow equivalent of collecting IDs across the batch and querying once, the way bulkified Apex does.

The practical consequences:

**Before-save flows are dramatically cheaper**, because they do no DML at all — they modify the record in flight. Prefer them wherever the work is same-record field assignment. See [[07.4 - Before-Save vs After-Save Flows]].

**Minimize Get Records in after-save flows** on high-volume objects.

**When a flow needs to query on every record of a bulk save, that is the signal to use Apex instead.** A trigger can collect all 200 record IDs and query once.

## The order problem

Several record-triggered flows on the same object with the same timing run in an order you cannot fully control. There is a **Flow Trigger Order** setting — a number from 1 to 2000 per flow — which does control it, and it needs to be used deliberately.

Without it, the order is unspecified, which means it can change. A flow depending on a field another flow sets is a bug waiting for a deployment.

The recommendation most mature orgs adopt: **one flow per object per timing.** One before-save flow, one after-save flow, using decision elements internally to branch.

This makes ordering explicit — it is the order of elements on the canvas — and it makes the automation inventory comprehensible. Nine flows on Case, each with its own entry conditions, is a system nobody can reason about.

The counter-argument is real: one large flow is harder for several administrators to work on simultaneously, and a bad change breaks everything rather than one thing. Where an org has that problem, using subflows within the single entry-point flow gets both — one entry point, modular internals. See [[07.7 - Subflows and Reusability]].

## Scheduled paths

A record-triggered flow can schedule work for later — a path that runs a set time after the trigger, or relative to a date field on the record.

```
Start: Record-Triggered on Warranty_Claim__c, After Save
Entry: Status__c = "Approved"

Immediate path
    → send approval email
    → create fulfilment task

Scheduled path: 7 days after Approved_Date__c
    → check whether parts were dispatched
    → if not, notify the service manager

Scheduled path: 30 days after Approved_Date__c
    → send satisfaction survey
```

This replaces time-based workflow actions and is genuinely useful, but the behaviour differs from immediate paths in ways worth knowing:

**Scheduled paths run in a separate transaction**, with fresh governor limits. They also run **asynchronously**, as the automated process user in some contexts, which affects sharing and field access.

**The entry conditions are re-evaluated** when the scheduled path fires. A claim approved and then rejected does not get the seven-day chase.

**Pending scheduled paths are visible and cancellable** in Setup, and are queryable through `FlowInterview`.

**Deleting or deactivating the flow does not automatically remove pending paths**, which occasionally surprises people during a cleanup.

**There is a limit** on scheduled path executions per hour across the org, which matters on high-volume objects.

## Delete triggers

A flow can trigger on delete, running **before** the delete. `$Record` holds the record being deleted.

Uses: preventing deletion under conditions, logging what was deleted, cleaning up related records that would otherwise be orphaned.

The caveat from [[02.10 - Delete Behaviour - Cascade and Restrict]]: **cascade deletes from a master-detail parent do not reliably fire the child's delete automation.** Logic that must prevent or record deletion needs to live on the parent, not the child.

## Running user and context

A record-triggered flow runs in the context of the user who saved the record, but the flow's own **system context** setting determines whether sharing and field permissions apply:

**User or System Context — Depends on How Flow Is Launched** — the default, respecting the running user's access.

**System Context Without Sharing — Access All Data** — ignores sharing and field-level security entirely.

The second is convenient and is a security decision. A flow running without sharing that a user can indirectly trigger is a way to read or write data they should not reach. Set it deliberately, and default to the first. This is the flow equivalent of the `with sharing` decision in [[03.13 - Enforcing Security in Apex and SOQL]].

## Practical guidance

**Always set entry conditions.** A flow with none runs on every save.

**Use "only when updated to meet conditions" on update triggers.** It is the change-detection mechanism, and omitting it means the flow fires repeatedly.

**Prefer before-save for same-record field assignment.** An order of magnitude cheaper.

**One flow per object per timing.** Use subflows for modularity within it.

**Set Flow Trigger Order** if you genuinely need several flows on one object.

**Do not query per record when you could collect and query once.** That requirement is the signal for Apex.

**Set the system context option deliberately**, not by accident.
