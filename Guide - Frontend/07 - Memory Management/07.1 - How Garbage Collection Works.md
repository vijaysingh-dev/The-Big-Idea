# How Garbage Collection Works

JavaScript manages memory automatically. You never free anything — the engine reclaims memory that is no longer **reachable**. Understanding what "reachable" means is the entire skill, because every memory leak in JavaScript is a reference you forgot you were holding.

## Reachability, not reference counting

The naive approach — count references, free at zero — fails on cycles:

```js
function cycle() {
  const a = {};
  const b = {};
  a.ref = b;
  b.ref = a;
}
cycle();  // both have a reference; neither is reachable from anywhere
```

Early IE used reference counting for DOM objects and leaked exactly this pattern. Modern engines instead trace from a set of **roots**:

- the global object
- the current call stack (all active execution contexts and their variables)
- closures held by anything reachable
- values held by the DOM tree, timers and registered event listeners

Anything reachable by following references from a root survives. Everything else is garbage, cycles included.

```js
let user = { name: "Vijay" };
const admin = user;
user = null;      // still reachable via admin — not collected
```

## Mark and sweep, generationally

V8 splits the heap into a **young generation** (new space) and an **old generation** (old space), based on the observation that most objects die young.

**Minor GC (Scavenger)** — collects the small young generation frequently using a copying collector. Live objects are copied to a second semi-space; everything else is discarded wholesale. It runs in a few milliseconds and is cheap because most young objects are already dead. An object that survives two scavenges is **promoted** to the old generation.

**Major GC (Mark-Compact)** — collects the old generation. Marks reachable objects, sweeps the rest, compacts to reduce fragmentation. Expensive, so V8 does most of the marking **concurrently** on background threads and **incrementally** in small slices, pausing your code only briefly.

The practical consequence: allocating many short-lived objects is fine — that is what the scavenger is designed for. Retaining many long-lived objects is what costs you, because they get promoted and then require major GCs.

## GC pauses and frame budget

Even with concurrent marking, GC steals main-thread time. A major GC pause that overruns the ~16.7 ms frame budget drops a frame ([[01.7 - The Rendering Cycle]]).

Where this shows up in practice: an animation that stutters at a regular interval, or a scroll that hitches every few seconds. In the DevTools Performance panel, GC appears as purple "Minor GC" / "Major GC" blocks.

The fix is almost never "call GC less" — you cannot control it — but "allocate less in the hot path":

```js
// Allocates a new object every frame
function animate() {
  const pos = { x: computeX(), y: computeY() };
  draw(pos);
  requestAnimationFrame(animate);
}

// Reuses one object
const pos = { x: 0, y: 0 };
function animate() {
  pos.x = computeX();
  pos.y = computeY();
  draw(pos);
  requestAnimationFrame(animate);
}
```

This is object pooling, and it is the one place where mutation beats immutability ([[06.7 - Immutable Data Patterns]]). It matters for canvas/WebGL loops and virtually nowhere else in UI code.

## What you cannot control

There is no `free()`, and no reliable way to force collection. `window.gc()` exists only with the `--expose-gc` flag. Setting a variable to `null` does not free anything — it only removes one reference, and helps only if it was the last one.

```js
let bigData = new Array(1e7);
bigData = null;   // helps only if nothing else references it
```

Because collection is non-deterministic, you cannot test "was this freed" in application code. `FinalizationRegistry` gives a callback after collection, but the spec explicitly does not guarantee it runs, so it is unsuitable for cleanup logic.

## Memory limits

Browser tabs get a heap cap — typically a few gigabytes on 64-bit desktop, far less on mobile. Exceeding it kills the tab with an out-of-memory crash, which in a long-lived SPA looks like "the app randomly reloads after an hour". Node's default old-space limit is adjustable with `--max-old-space-size`.

`performance.memory` (Chrome only) reports `usedJSHeapSize`, which is useful for coarse monitoring in production but is quantized for privacy reasons and excludes DOM memory.

## Where the leaks come from

Every JavaScript leak is one of these:

1. **Closures** holding scope alive longer than intended ([[07.2 - Memory Leaks from Closures and Timers]])
2. **Timers and intervals** never cleared
3. **Event listeners** never removed ([[07.3 - Memory Leaks from Listeners and Detached DOM]])
4. **Detached DOM nodes** still referenced from JS
5. **Unbounded caches** — maps and arrays that only ever grow
6. **Global variables** accumulating

Note that DOM memory is separate from the JS heap but is kept alive by JS references, which is why detached nodes are the most expensive category.

## How senior engineers actually use this

**They think in terms of retainers, not allocations.** The debugging question is never "what allocated this" but "what is still pointing at this". DevTools' retainer tree answers it directly ([[07.5 - Profiling Memory in DevTools]]).

**They bound every cache.** An LRU with a size cap, a `WeakMap` keyed by object identity, or a TTL. An unbounded `Map` in a single-page app that runs for eight hours is a guaranteed leak.

**They test long sessions.** Leaks are invisible in a five-minute development session and obvious after an hour of use. Navigating between routes fifty times and comparing heap snapshots is the standard check.

**They accept allocation in normal code.** Immutable updates allocate constantly and that is fine — the scavenger handles it. Optimizing allocation is reserved for measured hot paths.

## Common pitfalls

- Assuming setting a variable to `null` frees memory.
- Trying to force GC or relying on `FinalizationRegistry` for cleanup.
- Object pooling in ordinary UI code, adding complexity for no measurable gain.
- Blaming GC for jank that is actually long synchronous tasks.
- Treating "memory grows" as a leak — the heap grows until a major GC runs; a leak is memory that survives repeated GCs.

## Interview angle

"How does garbage collection work in JavaScript" expects: reachability from roots rather than reference counting, mark-and-sweep, and the generational split with cheap frequent minor GCs and expensive infrequent major ones. Explaining why reference counting fails on cycles is a good opener. The natural follow-up is "what causes memory leaks", which is the list above — closures, timers, listeners, detached DOM, unbounded caches.
