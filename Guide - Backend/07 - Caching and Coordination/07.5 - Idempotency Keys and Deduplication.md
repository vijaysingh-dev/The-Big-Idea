# Idempotency Keys and Deduplication

#backend #distributed-systems #reliability

> **In one line:** Delivery is at-least-once, so the receiver must recognise a repeat — and the only reliable way is to record what you have already done, in the same transaction as doing it.

---

## The Idea

[[03.4 - Idempotency and Safe Retries]] covered the HTTP-facing side. This note is the general mechanism, because the same problem appears everywhere:

| Where | The duplicate |
|---|---|
| HTTP API | A client retries after a timeout |
| Message consumer | At-least-once delivery, or a rebalance |
| Webhook receiver | The sender retries ([[05.12 - Webhooks and Callbacks]]) |
| Task queue | A worker dies after executing, before acking |
| Cron job | Two schedulers both fire |
| CDC pipeline | A replay from an earlier offset |

💡 **All six are the same problem: you cannot know whether you have seen this before unless you wrote it down.** And **writing it down must be atomic with the effect, or the two can disagree.**

---

## The Three Levels

### Level 1: Naturally idempotent

```python
await repo.set_status(doc_id, "indexed")     # absolute assignment — safe
await repo.add_tag(doc_id, "urgent")         # set semantics — safe
await repo.delete(doc_id)                    # safe
```

⚠️ **Relative operations are not:**

```python
await repo.increment_views(doc_id)      # not idempotent
await repo.append_comment(doc_id, text) # not idempotent
```

💡 **Where you can express an operation absolutely, do.** "Set the count to 4,201" is safe to repeat; "add one" is not. **This removes the problem rather than managing it.**

### Level 2: A natural unique key

```sql
UNIQUE (org_id, content_hash)
```

```python
try:
    await repo.create(doc)
except UniqueViolationError:
    return await repo.get_by_hash(org_id, content_hash)   # already done
```

💡 **A unique constraint is the strongest deduplication available**, because the database enforces it against every code path, every service and every retry — **with no coordination and no extra state.**

**Look for a natural key before building anything.**

### Level 3: An explicit dedup record

```sql
CREATE TABLE processed_operations (
    key          text PRIMARY KEY,
    scope        text NOT NULL,
    request_hash text,
    state        text NOT NULL,
    result       jsonb,
    created_at   timestamptz NOT NULL DEFAULT now(),
    locked_until timestamptz
);
```

## The Atomicity Requirement

**The single most important thing in this note.**

```python
# BROKEN — two separate transactions
if await already_processed(event.id):
    return
await apply_effect(event)              # ← crash here
await mark_processed(event.id)         # never runs → reprocessed
```

```python
# BROKEN the other way
await mark_processed(event.id)         # ← crash here
await apply_effect(event)              # never runs → LOST, and marked done
```

```python
# CORRECT — one transaction
async with conn.transaction():
    inserted = await conn.fetchval(
        "INSERT INTO processed_operations (key, scope, state) "
        "VALUES ($1, $2, 'done') ON CONFLICT DO NOTHING RETURNING key",
        event.id, "document_indexed",
    )
    if inserted is None:
        return                          # already processed
    await apply_effect(event)           # same transaction
```

💡 **The marker and the effect commit together or not at all.** A crash anywhere leaves a consistent state: either both happened, or neither did, and the redelivery will work.

⚠️ **This is why the deduplication record must live in the same database as the effect.** Deduplicating in Redis while writing to Postgres means two systems that can disagree — **and they will, at exactly the moment it matters.**

## Concurrent Duplicates

Sequential retries are the easy case. **Concurrent retries are where the bugs are**, and they happen precisely during the network trouble that caused the retry.

```python
# BROKEN — check then act
if await conn.fetchval("SELECT 1 FROM processed_operations WHERE key = $1", key):
    return
# ← two concurrent requests both reach here
```

```python
async def claim(key: str, scope: str, request_hash: str) -> ClaimResult:
    row = await conn.fetchrow(
        """
        INSERT INTO processed_operations (key, scope, request_hash, state, locked_until)
        VALUES ($1, $2, $3, 'in_progress', now() + interval '60 seconds')
        ON CONFLICT (key) DO UPDATE
            SET locked_until = CASE
                WHEN processed_operations.state = 'in_progress'
                 AND processed_operations.locked_until < now()
                THEN now() + interval '60 seconds'
                ELSE processed_operations.locked_until
            END
        RETURNING *
        """,
        key, scope, request_hash,
    )

    if row["request_hash"] != request_hash:
        raise KeyReusedWithDifferentBody()
    if row["state"] == "done":
        return ClaimResult.already_done(row["result"])
    if row["state"] == "in_progress" and row["locked_until"] > now():
        return ClaimResult.in_progress()
    return ClaimResult.claimed()
```

**`INSERT ... ON CONFLICT` is atomic — there is no window between checking and claiming.**

⚠️ **`locked_until` is what stops a crashed operation blocking the key forever.** Without it, a worker that dies mid-operation leaves the key permanently `in_progress`.

---

## The Three States

```
in_progress   claimed, running. Concurrent duplicates get 409 or wait
done          completed. Return the stored result
failed        completed with an error. Return it, or allow retry
```

💡 **Storing the result is what makes a retry return the *same* answer** rather than doing the work again. **A client retrying a document creation should get back the same document ID, not a new document.**

**Whether `failed` is retryable is a design decision.** A validation failure will fail identically, so store and return it; a transient dependency failure should probably allow a fresh attempt — **which means storing whether the failure was retryable.**

---

## Key Design

```python
key = f"{org_id}:{operation_type}:{client_key}"
```

⚠️ **Scope the key by tenant.** An unscoped key space means one tenant's key can collide with another's — **accidentally, or deliberately as an attack that lets them read another tenant's stored result.**

| Source | Use when |
|---|---|
| **Client-supplied** | HTTP APIs. The client owns retry identity |
| Message ID | Queue and event consumers |
| Content hash | When the payload defines the operation |
| Natural business key | An order number, an external reference |
| Derived from inputs | A deterministic function of the parameters |

⚠️ **A derived key means two genuinely distinct operations with identical parameters are treated as duplicates.** "Send a reminder email to this user" twice, deliberately, becomes once. **Include a timestamp bucket or an explicit nonce when repetition is legitimate.**

### The request hash check

💡 **This catches a real and dangerous client bug**: reusing an idempotency key for a different request. **Without the check, a client sends a $10 charge with a key it previously used for $5,000 and receives the $5,000 result — and both parties are confused for a long time.**

---

## Retention

⚠️ **The retention window is a contract.** A retry after the window is not deduplicated and the operation happens again.

| Context | Typical window |
|---|---|
| HTTP idempotency keys | 24 hours (Stripe's choice) |
| Message consumers | Longer than the maximum redelivery window |
| **Webhook receivers** | **Longer than the sender's retry schedule** — often 3–7 days |
| CDC consumers | As long as you might replay |

💡 **Match the window to the maximum realistic redelivery time, not to convenience.** A webhook sender that retries for 3 days needs a 3-day dedup window.

**Partition the table by day** so cleanup is a `DROP` rather than a `DELETE` ([[06.13 - Partitioning and Sharding]]).

## When the Effect Is Not Transactional

```python
# 1. Claim, commit
async with conn.transaction():
    result = await claim(key, scope, request_hash)
    if result.already_done:
        return result.stored_result

# 2. Perform the effect, passing OUR key downstream
charge = await stripe.charge(..., idempotency_key=key)

# 3. Record the result, commit
async with conn.transaction():
    await mark_done(key, charge)
return charge
```

💡 **Passing your key through to the downstream service is what makes this safe.** If you crash between steps 2 and 3, the retry re-performs step 2 — **and Stripe deduplicates it using the same key, returning the original charge.**

⚠️ **This only works if the downstream supports idempotency keys.** If not, you have a genuine at-most-once-or-at-least-once choice, **and you must pick one explicitly:**

| Choice | |
|---|---|
| Record first, then call | Risk losing the operation if the call fails |
| Call first, then record | Risk duplicating if recording fails |

**Neither is wrong; pretending you avoided the choice is.**

### Reconciliation as the backstop

```python
stuck = await conn.fetch(
    "SELECT * FROM processed_operations "
    "WHERE state = 'in_progress' AND locked_until < now() - interval '5 minutes'"
)
for op in stuck:
    actual = await downstream.lookup(op["key"])   # did it actually happen?
    ...
```

💡 **A reconciliation job that asks the downstream system what actually happened is the only way to resolve an ambiguous outcome.** Unglamorous, and it is what real payment systems do.

## In Production

### Testing it properly

```python
async def test_concurrent_duplicates_produce_one_effect():
    key = str(uuid4())
    await asyncio.gather(*[create_payment(key, {"amount": 100}) for _ in range(20)],
                         return_exceptions=True)
    assert await count_payments() == 1
```

⚠️ **A sequential retry test will pass against a broken implementation.** The bug lives in concurrency, **which is exactly what happens when a client times out and retries while the original is still running.**

**If your idempotency test is not concurrent, it is not testing idempotency.**

### Monitoring

```python
idempotency_hits_total.labels(scope=..., state="done").inc()
idempotency_concurrent_total.inc()
idempotency_key_reuse_total.inc()           # ← different body, same key. Client bug
idempotency_stuck_total.set(count)
```

💡 **`idempotency_key_reuse_total` being non-zero means a client is broken.** Worth alerting on and reaching out about, **because the client is silently getting wrong results.**

**`idempotency_hits_total{state="done"}` tells you your retry rate** — a sudden rise means clients are timing out, often the first visible signal of a latency problem.

### The consumer-side pattern

```python
async def handle_message(msg: Message):
    async with conn.transaction():
        claimed = await conn.fetchval(
            "INSERT INTO processed_messages (message_id, topic) VALUES ($1, $2) "
            "ON CONFLICT DO NOTHING RETURNING message_id", msg.id, msg.topic)
        if claimed is None:
            metrics.duplicate_messages.inc()
            return
        await apply(msg)
    await msg.ack()
```

⚠️ **Ack after the transaction commits, never before.** Acking first means a crash loses the message entirely, **and at-least-once becomes at-most-once.**

### Making replay safe

💡 **A consumer that is properly idempotent can be replayed from any offset**, which is an enormously valuable property — rebuild a derived store, reprocess after a bug fix, or backfill new data by resetting the offset.

**Design consumers for replay from the start.** Adding it later usually means a full audit of every side effect.

⚠️ **Note the interaction with retention**: replaying from six months ago against a 24-hour dedup window means everything is reprocessed. **For replayable consumers, either keep dedup records as long as your retention, or make the effects naturally idempotent** — which is the better answer.

## Codebase

**Repo:** `stripe` (docs), `apache/kafka`, `celery/celery`

**Question to answer:** How does Kafka's idempotent producer prevent duplicates, and precisely where does that guarantee stop applying? Then: what does Celery provide for consumer-side deduplication, and what must you build yourself?

**Read, in order:**

1. **Stripe's idempotency documentation** — the clearest public specification. Note the retention window, the request-mismatch behaviour, and the response to a concurrent duplicate
2. `kafka/clients/src/main/java/.../producer/internals/TransactionManager.java` — **the producer ID and per-partition sequence number.** This is deduplication, **bounded to the producer session**
3. `kafka/core/src/main/scala/kafka/log/UnifiedLog.scala` — the broker's duplicate detection on append. **The guarantee ends here**: the moment your consumer writes to Postgres, Kafka's exactly-once does nothing for you
4. `celery/celery/app/task.py` — search for `acks_late`. **Celery explicitly documents that tasks must be idempotent and provides no dedup mechanism**
5. `celery/celery/backends/base.py` — the result backend stores results by task ID. **Close to a dedup record, and not atomic with your effect**

💡 The Kafka reading clarifies the whole topic. **"Exactly-once semantics" means at-least-once delivery plus deduplication, and the deduplication is scoped to Kafka.** Understanding where that boundary sits — **and that your consumer's database write is outside it** — separates people who have read the marketing from people who have operated it.

**Size:** 1–2 sessions.

**Part 1 — Three levels, one operation.** "Create a document" three ways: content-hash unique constraint, explicit dedup table, and restructured to be naturally idempotent.

Compare correctness under concurrent duplicates, storage cost, latency overhead, and lines of code.

**Part 2 — Crash at every point.** The correct version with a kill injected at six points: before claim, after claim before effect, during effect, after effect before commit, after commit before ack, and after ack.

**For each, restart and redeliver. Assert exactly one effect and no lost operations.**

Then the same against both broken versions. **`broken_before` should lose operations; `broken_after` should duplicate them. Quantify both.**

**Part 3 — The concurrency bug.** Check-then-act with 50 concurrent identical requests. **Count the effects. It will be more than one.**

Then add an artificial 50ms delay between check and act **to make it fail every time rather than occasionally** — turning a flaky demonstration into a deterministic test.

Then the atomic claim version: **exactly one effect, and every caller receives the same result.**

**Part 4 — The four claim scenarios.**

| Scenario | Expected |
|---|---|
| 20 concurrent identical requests | One effect, one shared result |
| Sequential retry after success | Cached result, no new effect |
| Same key, different body | `KeyReusedWithDifferentBody` |
| Crash mid-operation, then retry | Lock expires, retry proceeds, one effect |
| **Retry after the retention window** | **New effect. Document this as expected** |
| A key from another tenant | Not found — no cross-tenant leakage |

**Part 5 — The non-transactional effect.** A mock external payment API supporting idempotency keys.

Implement two-phase with key passthrough. **Kill the process between phases 2 and 3 and confirm the retry returns the original charge.**

Then repeat with an API that does **not** support keys. **Implement both choices — record-first and call-first — and demonstrate the failure mode of each.** Then implement reconciliation and show it resolving both.

**Part 6 — A replayable consumer.** Transactional deduplication.

Deliver 10,000 messages with 20% duplicates and two concurrent workers. **Assert exactly 10,000 effects.**

Then kill a worker mid-batch and confirm no loss and no duplication.

**Then replay the entire topic from offset 0 and confirm zero additional effects.**

Then let the dedup records expire and replay again. **Confirm everything is reprocessed, and write down what that means for your retention policy.**

**Part 7 — Retention and growth.** Partition by day with automated cleanup.

Run at 1,000 operations per second for an hour. Measure table growth, index size, and claim latency as it grows.

**Then drop a day's partition and confirm it is instant with no bloat** ([[06.7 - MVCC Vacuum and Bloat]]).

**Done when:**
- The three-level comparison table is complete
- Crashes at all six points produce exactly-once effects
- The broken versions demonstrably lose and duplicate, with counts
- All six claim scenarios pass
- The two-phase external pattern survives a crash between phases
- Your consumer replays from offset 0 with zero additional effects
- You know what dedup-record expiry means for replay
