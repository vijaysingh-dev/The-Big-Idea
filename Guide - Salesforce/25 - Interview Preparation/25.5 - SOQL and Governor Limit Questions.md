# SOQL and Governor Limit Questions

## Limits

**Why do governor limits exist?**

Because your code runs on servers shared with thousands of other customers. One badly written loop could degrade service for all of them.

There are two ways to prevent that — dedicated hardware per tenant, which destroys the economics, or capping what any single transaction may consume. Salesforce chose the cap.

**They are a fairness mechanism, not performance guidance**, and that framing explains everything else about how they behave.

**Why can't you catch a LimitException?**

Because if you could, code would swallow it and keep consuming, which defeats the mechanism entirely. A soft limit can be ignored; a hard one cannot.

The design consequence is direct: you cannot recover from a limit failure, so you design not to approach one. That is why limit handling is architectural rather than an error-handling concern.

**What are the main limits?**

Per transaction: 100 SOQL queries, 50,000 query rows, 150 DML statements, 10,000 DML rows, 10 seconds CPU, 6 MB heap, 100 callouts with 120 seconds cumulative.

Async roughly doubles queries, heap, and CPU — but not the row limits.

The two worth memorizing are 100 queries and 10 seconds CPU, because they are the ones you hit first and the ones that constrain design.

**And they're per transaction, not per day** — which is the important part. Salesforce does not care how much work you do in total; it cares that no single request monopolizes a server. That is why async exists: each execution is a new transaction with a fresh budget.

**Whose budget is it?**

Shared with everything in the transaction — your trigger, other triggers, every flow, validation rules, roll-up recalculation, and any managed package.

Perfectly bulkified Apex can fail because a flow consumed 90 queries before it ran, and the error names your code.

That is why auditing an object's total automation is a real activity, and why consolidation — one trigger per object, one flow per object per timing — is partly a limits decision rather than only an ordering one.

## SOQL

**How do you avoid hitting the query limit?**

Collect, query once, act once.

```java
Set<Id> assetIds = new Set<Id>();
for (Warranty_Claim__c claim : claims) {
    if (claim.Asset__c != null) {
        assetIds.add(claim.Asset__c);
    }
}

Map<Id, Asset> assets = new Map<Id, Asset>([
    SELECT Id, SerialNumber FROM Asset WHERE Id IN :assetIds
]);

for (Warranty_Claim__c claim : claims) {
    Asset asset = assets.get(claim.Asset__c);
    if (asset != null) {
        claim.Asset_Serial__c = asset.SerialNumber;
    }
}
```

The signature is what enforces it. A method taking `Set<Id>` rather than a single `Id` makes the correct call site the natural one.

**What is the difference between the query limit and the row limit?**

Separate limits, and the row one is easier to miss. Four queries returning 20,000 rows each hits 50,000 rows without approaching 100 queries.

Rows accumulate across every query in the transaction, including subqueries — a relationship subquery counts parents and children, so 1,000 assets with 60 claims each is 61,000 rows and fails.

Two things that help: `SELECT COUNT()` does not consume the row limit for the rows counted, and the list form of the SOQL for loop retrieves 200 at a time, which keeps heap bounded.

Beyond 50,000, Batch Apex — its `QueryLocator` handles up to 50 million and is not subject to that limit.

**What makes a query selective?**

The optimizer estimates how many rows a filter will return and decides whether using an index is worth it. Roughly, below 30% of the first million rows for a standard index, and below 10% for a custom one.

**A filter returning too many rows gets a table scan regardless of indexing**, because scanning is cheaper than an index lookup plus a fetch for that many rows.

That is why `Status__c != 'Closed'` on an object where 70% of records are open cannot be optimized. No index helps; the filter is not selective. It is a data problem, not an indexing problem.

**What prevents index use?**

Negative operators — `!=` and `NOT IN`. The fix is enumerating the positive values as an `IN` list.

Leading wildcards — `LIKE '%00042'`. For genuine text search, SOSL uses the search index and is the right tool.

Null comparisons, because standard indexes exclude nulls. A custom index can be built to include them, requested explicitly — which is worth asking for when an integration filters on a null confirmation field to find unprocessed records.

Formula fields, unless deterministic and same-record. A cross-object formula, or one using `TODAY()`, cannot be indexed.

**How would you diagnose a slow query?**

Query Plan in the Developer Console. Cost above 1 means a table scan; below 1 means an index will be used.

Then check whether the filter is selective at all — count the matching rows against the total. If it returns most of the table, no index helps and the fix is a narrower filter.

The most common fix is adding a date bound. `CreatedDate` and `SystemModstamp` are indexed by default, so a bound on either is free selectivity, and it is usually what the user actually wanted anyway.

The thing to watch in the plan is a `Leading Operation Type` of `Other` — that means the optimizer used a sharing-based plan rather than a field index, which on a private object with millions of records is slow.

## CPU and heap

**What counts toward CPU time?**

Computation only. SOQL execution, DML execution, and callout wait time do not count — a transaction taking eight seconds of wall time may use two seconds of CPU if most of it was waiting.

The expensive operations, in order of how often they cause a failure: nested loops over collections, `getGlobalDescribe()` in a loop, string concatenation with `+=`, JSON serialization of large structures, and sorting.

But the invisible consumers matter more. Flows, validation rules, roll-up recalculation, and managed packages all spend from the same 10 seconds. A CPU failure where your code is clean is usually accumulated automation.

**How would you diagnose a CPU limit failure?**

Bracket the sections with `Limits.getCpuTime()` to find where it goes.

If the cost is in your processing, look for a nested loop or a describe call in a loop. If it is in the DML, the problem is downstream — triggers, flows, and roll-ups firing on the save — and the fix is auditing the object's automation rather than optimizing your code.

The Developer Console's execution overview is the tool that attributes time per operation, which is what turns "the save is slow" into "the flow ran 200 times".

**What causes heap exhaustion?**

Usually a query returning too many wide rows — `FIELDS(ALL)` on a wide object with long text areas will exhaust 6 MB before it exhausts the row limit.

Then a static collection accumulating, which in a batch job with `Database.Stateful` persists across chunks and grows until it fails. And string building with `+=` in a loop, because strings are immutable and each iteration allocates a new one.

The diagnostic is a heap dump from a checkpoint, which shows what is actually held by type and size. That is the only tool that answers it.

The fixes: select fewer fields, process in chunks with the list form of the for loop, cap stateful collections, and move to async for 12 MB.

## Practical scenarios

**A trigger works in the sandbox and fails in production with "too many SOQL queries: 101". Nothing changed.**

The query is inside a loop, and the sandbox test used one record while production processes in bulk. The trigger fires once per batch of up to 200; a query inside the loop consumes one per record.

The follow-up worth anticipating is how it would have been caught — a test inserting 200 records rather than one. A single-record test proves nothing about bulk safety.

**A batch job that took 45 minutes now takes five hours. The code hasn't changed.**

The data grew, and a query that was selective is not any more. Selectivity is a proportion, so a filter that returned 12% of two million records returns 17% of eight million — and crosses the threshold.

I would check `JobItemsProcessed` over time to confirm growth, then the query plan on the locator.

The immediate fix is a date bound. The real fix is archiving, because reducing the object makes the original filter selective again and improves every other query on it at the same time.

**A data load fails on 8% of rows with UNABLE_TO_LOCK_ROW, and retrying fails on a different 8%.**

Lock contention, and the diagnostic question is what the failing records have in common. Grouping the failed-results file by parent usually shows two or three parents accounting for most of them.

That is skew plus an unsorted file — parallel batches each touching children of the same hot parent, and every child save locks the parent for roll-up recalculation.

The fix in order: sort the file by parent Id, which puts children of the same parent in the same batch. Then reduce roll-ups on that parent. Serial mode if sorting is not enough. And structurally, address the skew, because it will recur.

**How would you process ten million records?**

Batch Apex, scope tuned to the per-record work — smaller if it is heavy, larger if it is trivial.

The arithmetic matters: ten million at scope 200 is 50,000 chunks, and each chunk is an async execution against the 250,000 daily allocation. At scope 50 it is 200,000 executions, which is most of the day's budget for the whole org.

I would also order the query locator by parent, which groups contention into single chunks rather than spreading it across parallel ones.

And I would check whether ten million records need processing at all — frequently the answer is a filter narrowing it, or archiving reducing it.

## The design-level answer

**How do you design so limits are not a concern?**

Five things.

Bulkify — every method takes a collection, and there is no SOQL or DML in a loop.

Do less. Change detection against the prior values means most of a handler's work does not run on a save where nothing relevant changed, and updating only records whose values actually changed stops a whole cascade.

Split the transaction. Async gives more transactions rather than bigger ones.

Reduce what runs at all. Consolidating automation is a limits decision as much as an ordering one.

Cache — describes in statics, configuration in Custom Metadata which costs no query at all.

**And design for headroom rather than compliance.** A transaction at 94 of 100 queries is not working; it is one flow away from failing, and the person who adds that flow will have no way to know. Below 50% is the target.

The thing I would add is asserting on consumption in bulk tests. A query added inside a loop passes every functional test and fails an assertion on `Limits.getQueries()`. That is the only mechanism that catches a limit regression before production.

## What is being assessed

**Junior:** knows the numbers, avoids SOQL in loops.

**Mid:** knows the row limit is separate, understands selectivity, uses the query plan.

**Senior:** raises the shared budget, discusses selectivity as a proportion that changes with volume, and reaches for archiving before indexing.

**The answer that marks experience** is treating a limit failure as a design signal rather than something to work around. Code approaching 100 queries is not slightly inefficient — it is structured wrong, and the fix is collect-query-act rather than a limit check.
