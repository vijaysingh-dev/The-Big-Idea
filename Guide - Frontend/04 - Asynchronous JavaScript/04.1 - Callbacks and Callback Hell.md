# Callbacks and Callback Hell

Callbacks were JavaScript's only asynchronous primitive for its first fifteen years. Understanding what went wrong with them is the best way to understand why promises are shaped the way they are.

## The pattern

```js
function getUser(id, callback) {
  setTimeout(() => callback(null, { id, name: "Vijay" }), 100);
}

getUser(1, (err, user) => {
  if (err) return console.error(err);
  console.log(user);
});
```

The **error-first convention** — error as the first argument, result second — became standard in Node because there was no other channel for failures. `try/catch` cannot cross an asynchronous boundary ([[01.3 - The Call Stack]]), so the error had to travel as data.

## The nesting

```js
getUser(userId, (err, user) => {
  if (err) return handleError(err);

  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);

    getOrderDetails(orders[0].id, (err, details) => {
      if (err) return handleError(err);

      getShipping(details.shippingId, (err, shipping) => {
        if (err) return handleError(err);
        render({ user, orders, details, shipping });
      });
    });
  });
});
```

The nickname "callback hell" or "pyramid of doom" focuses on indentation, which is the least important problem. The real ones:

**1. Error handling is manual and repetitive.** Every level needs its own check. Miss one and the failure vanishes silently.

**2. There is no composition.** You cannot express "run these three in parallel and continue when all finish" without hand-writing a counter:

```js
let done = 0;
const results = [];

[1, 2, 3].forEach((id, i) => {
  getUser(id, (err, user) => {
    if (err) return handleError(err);
    results[i] = user;
    if (++done === 3) render(results);
  });
});
```

That counter is `Promise.all` reimplemented badly — and note it does not handle the case where two callbacks error, calling `handleError` twice.

**3. Control flow cannot be returned or passed.** A callback-based function returns nothing meaningful, so it cannot be stored, chained, or handed to a generic utility. Promises are *values*, which is the single biggest conceptual upgrade.

**4. Inversion of control.** You hand your continuation to someone else's code and lose all guarantees.

## Inversion of control, concretely

```js
thirdPartyCheckout(order, (err, receipt) => {
  chargeCustomer(receipt);
});
```

You are now trusting that library to call your callback:

- exactly once (not zero times, not five times — a double charge)
- asynchronously and consistently
- with the arguments you expect
- and to catch its own errors rather than swallowing yours

A promise removes most of this. A promise settles **once**, permanently, and later `resolve`/`reject` calls are ignored. `.then` reactions are **always** scheduled as microtasks, never called synchronously. Those two guarantees are why promises are safer, not just prettier.

## The sync/async inconsistency

```js
function load(id, cb) {
  if (cache.has(id)) return cb(null, cache.get(id));   // synchronous
  fetchRemote(id, cb);                                  // asynchronous
}

let ready = false;
load(1, () => console.log(ready));  // logs false on cache hit, true on miss
ready = true;
```

An API that is sometimes synchronous makes calling code unpredictable in a way that only shows up under specific cache states — a classic heisenbug. The rule is: if a callback is ever asynchronous, make it always asynchronous ([[02.5 - Higher Order Functions and Callbacks]]).

Promises enforce this for you. Even `Promise.resolve(1).then(fn)` schedules `fn` as a microtask ([[01.6 - Microtasks vs Macrotasks]]).

## Mitigations that predated promises

**Named functions instead of inline nesting:**

```js
function onUser(err, user) {
  if (err) return handleError(err);
  getOrders(user.id, onOrders);
}
function onOrders(err, orders) { /* ... */ }

getUser(userId, onUser);
```

Flattens the pyramid but does nothing about error repetition or composition, and scatters the flow across the file.

**Control-flow libraries** — `async.js` provided `series`, `parallel`, `waterfall`. These were essentially userland promise combinators, and they are the direct ancestors of `Promise.all` and friends.

## Converting callbacks to promises

You will still meet callback APIs — older SDKs, Node's `fs`, some browser APIs, third-party widgets. Wrap them once at the boundary:

```js
function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) =>
      fn(...args, (err, result) => (err ? reject(err) : resolve(result)))
    );
}

const getUserAsync = promisify(getUser);
```

Node ships `util.promisify` for the error-first convention, and most modern Node APIs offer a promise variant directly (`fs/promises`).

For event-based APIs, the wrapper resolves on one event and rejects on another:

```js
function loadImage(src) {
  return new Promise((resolve, reject) => {
    const img = new Image();
    img.onload = () => resolve(img);
    img.onerror = () => reject(new Error(`Failed to load ${src}`));
    img.src = src;
  });
}
```

## Where callbacks are still correct

Promises settle once. Anything that produces **many** values over time is still callback-shaped:

- `addEventListener` — a click can happen repeatedly
- `IntersectionObserver`, `MutationObserver`, `ResizeObserver`
- `setInterval`
- WebSocket `onmessage`
- Array methods like `map` and `filter` — synchronous callbacks, no async involved

For streams of async values, async iterators and observables are the composable options ([[06.6 - Iterators and Generators]]).

## How senior engineers actually use this

**They promisify at the boundary, immediately.** Callback APIs get wrapped once in the data layer, and the rest of the codebase sees only promises. Mixing both styles through an application is how you end up with three different error-handling conventions.

**They recognize the counter pattern as a smell.** Any hand-rolled "wait for N things" bookkeeping should be `Promise.all` or `Promise.allSettled` ([[04.5 - Promise Combinators]]).

**They keep event callbacks as callbacks.** Wrapping a click handler in a promise is a category error — you would only ever get the first click.

**They read callback code fluently.** Large parts of the ecosystem, jQuery-era code, and most legacy internal tooling are callback-based. This is a reading skill more than a writing one now.

## Common pitfalls

- Forgetting an error check at one level and losing failures silently.
- Calling the callback twice on an error path (`callback(err)` then falling through).
- Mixed sync/async callback APIs.
- Wrapping a multi-fire event source in a promise.
- Assuming `try/catch` around a callback-based call will catch anything. It catches only the synchronous registration.

## Interview angle

"What is callback hell and how do promises solve it" expects more than "nesting is ugly". Lead with the four real problems — repeated error handling, no composition, callbacks are not values, and inversion of control — then say what promises guarantee in return: settle once, always async, chainable, errors propagate down the chain. Being able to write `promisify` on the spot is the usual follow-up.
