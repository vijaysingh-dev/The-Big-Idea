# Base Components and lightning-datatable

## Why to use them

Base components give you accessibility, keyboard navigation, responsive behaviour, locale formatting, and the org's theme — none of which you want to rebuild.

A hand-rolled `<div>` styled to look like a button is not focusable, not announced by a screen reader, and does not respond to the theme. `lightning-button` is all three for free.

**Reach for a base component first.** Custom markup is for what they cannot do.

## The ones used most

**Layout and structure**

```html
<lightning-card title="Warranty Claims" icon-name="standard:case">
    <lightning-button slot="actions" label="New"></lightning-button>
    <div class="slds-p-horizontal_small">Body content</div>
    <div slot="footer">Footer</div>
</lightning-card>

<lightning-layout multiple-rows>
    <lightning-layout-item size="12" small-device-size="6" padding="around-small">
        Half width on small devices and up
    </lightning-layout-item>
</lightning-layout>

<lightning-accordion active-section-name="details">
    <lightning-accordion-section name="details" label="Claim Details"></lightning-accordion-section>
</lightning-accordion>

<lightning-tabset>
    <lightning-tab label="Claims"></lightning-tab>
    <lightning-tab label="Coverage"></lightning-tab>
</lightning-tabset>
```

**Input**

```html
<lightning-input type="number" label="Approved amount" value={amount}
                 onchange={handleAmountChange} min="0" required>
</lightning-input>

<lightning-combobox label="Status" value={status} options={statusOptions}
                    onchange={handleStatusChange}>
</lightning-combobox>

<lightning-textarea label="Description" value={description}></lightning-textarea>

<lightning-record-picker label="Machine" object-api-name="Asset"
                         onchange={handleAssetChange}>
</lightning-record-picker>

<lightning-dual-listbox label="Parts" options={partOptions} value={selectedParts}>
</lightning-dual-listbox>

<lightning-file-upload label="Evidence" record-id={recordId}
                       onuploadfinished={handleUpload}>
</lightning-file-upload>
```

`lightning-record-picker` is the modern replacement for hand-built lookup components — it searches, respects sharing, and supports filtering by criteria.

**Output and formatting**

```html
<lightning-formatted-number value={amount} format-style="currency" currency-code="INR">
</lightning-formatted-number>

<lightning-formatted-date-time value={claimDate} year="numeric" month="short" day="2-digit">
</lightning-formatted-date-time>

<lightning-formatted-rich-text value={description}></lightning-formatted-rich-text>
<lightning-formatted-url value={link} label="Open in ERP" target="_blank"></lightning-formatted-url>
<lightning-relative-date-time value={lastModified}></lightning-relative-date-time>
```

The formatted components apply the **user's locale** automatically. Formatting a currency in JavaScript and rendering the string bypasses that and produces the wrong format for half the org.

**Feedback**

```html
<lightning-spinner alternative-text="Loading" size="medium"></lightning-spinner>
<lightning-badge label="High Value"></lightning-badge>
<lightning-pill label={claimNumber} onremove={handleRemove}></lightning-pill>
<lightning-progress-indicator current-step="2" type="path"></lightning-progress-indicator>
<lightning-icon icon-name="utility:warning" variant="warning" size="small"></lightning-icon>
```

## The event payload inconsistency

Base components are not consistent about where the value lives, and this is worth knowing before debugging it.

```javascript
handleInputChange(event) {
    event.target.value;      // lightning-input, lightning-textarea
    event.detail.value;      // lightning-combobox, lightning-radio-group
    event.target.checked;    // lightning-input type="checkbox"
    event.detail.recordId;   // lightning-record-picker
    event.detail.value;      // lightning-slider
}
```

The component reference is the authority. Guessing costs more time than checking.

## lightning-datatable

The most capable and most fiddly base component.

```javascript
const COLUMNS = [
    { label: 'Claim', fieldName: 'claimUrl', type: 'url',
      typeAttributes: { label: { fieldName: 'Claim_Number__c' }, target: '_self' } },
    { label: 'Machine', fieldName: 'serialNumber', type: 'text' },
    { label: 'Amount', fieldName: 'Claim_Amount__c', type: 'currency',
      typeAttributes: { currencyCode: 'INR' },
      cellAttributes: { alignment: 'right' } },
    { label: 'Status', fieldName: 'Status__c', type: 'text',
      cellAttributes: { class: { fieldName: 'statusClass' } } },
    { label: 'Date', fieldName: 'Claim_Date__c', type: 'date',
      typeAttributes: { year: 'numeric', month: 'short', day: '2-digit' } },
    { type: 'action', typeAttributes: { rowActions: ROW_ACTIONS } }
];
```

```html
<lightning-datatable
    key-field="Id"
    data={rows}
    columns={columns}
    sorted-by={sortedBy}
    sorted-direction={sortDirection}
    onsort={handleSort}
    onrowaction={handleRowAction}
    onrowselection={handleRowSelection}
    draft-values={draftValues}
    onsave={handleSave}
    hide-checkbox-column={hideSelection}>
</lightning-datatable>
```

**`key-field` is required** and must be genuinely unique. Getting it wrong produces rows that behave strangely on sort and selection.

## The flattening problem

Datatable cannot read nested properties. `Asset__r.SerialNumber` in `fieldName` renders nothing.

```javascript
@wire(getClaims, { accountId: '$recordId' })
wiredClaims(result) {
    this.claimResult = result;

    if (result.data) {
        // datatable needs flat properties, so relationships are hoisted here
        this.rows = result.data.map((claim) => ({
            ...claim,
            serialNumber: claim.Asset__r?.SerialNumber,
            accountName: claim.Asset__r?.Account?.Name,
            claimUrl: `/lightning/r/Warranty_Claim__c/${claim.Id}/view`,
            statusClass: claim.Status__c === 'Rejected' ? 'slds-text-color_error' : ''
        }));
    }
}
```

Doing this in the wire handler rather than a getter means it runs once per data change rather than on every rerender. See [[14.17 - Performance and Rendering]].

## Sorting

Datatable does not sort — it announces that the user asked to.

```javascript
handleSort(event) {
    const { fieldName, sortDirection } = event.detail;
    this.sortedBy = fieldName;
    this.sortDirection = sortDirection;

    const multiplier = sortDirection === 'asc' ? 1 : -1;

    // a copy, because mutating this.rows in place would not trigger a rerender
    this.rows = [...this.rows].sort((a, b) => {
        const valueA = a[fieldName] ?? '';
        const valueB = b[fieldName] ?? '';
        if (valueA === valueB) {
            return 0;
        }
        return valueA > valueB ? multiplier : -multiplier;
    });
}
```

The null coalescing matters — comparing undefined values produces inconsistent ordering across browsers.

Only columns with `sortable: true` show the control.

## Row actions

```javascript
const ROW_ACTIONS = [
    { label: 'View', name: 'view' },
    { label: 'Approve', name: 'approve' },
    { label: 'Reject', name: 'reject' }
];

handleRowAction(event) {
    const action = event.detail.action.name;
    const row = event.detail.row;

    switch (action) {
        case 'view':
            this.navigateToRecord(row.Id);
            break;
        case 'approve':
            this.approve(row.Id);
            break;
        case 'reject':
            this.reject(row.Id);
            break;
        default:
            break;
    }
}
```

Actions can vary per row by supplying a function to `typeAttributes.rowActions`, which is how a Closed claim hides the Approve action.

## Inline editing

```javascript
async handleSave(event) {
    const updates = event.detail.draftValues.map((draft) => ({
        fields: { ...draft }
    }));

    try {
        await Promise.all(updates.map((record) => updateRecord(record)));

        // clearing draft values is what removes the unsaved-changes banner
        this.draftValues = [];
        await refreshApex(this.claimResult);
        this.showToast('Saved', 'Claims updated.', 'success');
    } catch (error) {
        this.showToast('Save failed', reduceErrors(error), 'error');
    }
}
```

Three things people miss:

**`editable: true` on the column** is what enables it.

**Clearing `draftValues` after a successful save** removes the "unsaved changes" banner. Forgetting it leaves the banner up permanently.

**`Promise.all` over `updateRecord`** is fine for a handful of rows and wrong for fifty — that is fifty round trips. For anything substantial, one Apex method taking a list is the right approach.

## Custom data types

Datatable can be extended with custom column types, which is how a picklist or a custom component appears in a cell.

```javascript
// customDatatable/customDatatable.js
import LightningDatatable from 'lightning/datatable';
import statusBadge from './statusBadge.html';

export default class CustomDatatable extends LightningDatatable {
    static customTypes = {
        statusBadge: {
            template: statusBadge,
            standardCellLayout: true,
            typeAttributes: ['status', 'variant']
        }
    };
}
```

```html
<!-- statusBadge.html -->
<template>
    <lightning-badge label={typeAttributes.status} class={typeAttributes.variant}></lightning-badge>
</template>
```

Then `<c-custom-datatable>` in place of `<lightning-datatable>`, with `type: 'statusBadge'` on the column.

Genuinely useful, and it comes with a caveat: extending a base component means inheriting its internals, and Salesforce changing them can break the extension. Keep custom types simple.

## Datatable limits

**It renders every row.** No virtualization. Beyond roughly 1,000 rows the browser struggles, and beyond a few thousand it becomes unusable.

For large datasets, `enable-infinite-loading` with `onloadmore` fetches in pages:

```html
<lightning-datatable
    data={rows}
    columns={columns}
    key-field="Id"
    enable-infinite-loading
    onloadmore={handleLoadMore}
    is-loading={isLoading}>
</lightning-datatable>
```

```javascript
async handleLoadMore(event) {
    if (this.allLoaded) {
        event.target.isLoading = false;
        return;
    }

    this.isLoading = true;
    const nextPage = await getClaims({ accountId: this.recordId, cursor: this.cursor });

    this.rows = [...this.rows, ...nextPage.records];
    this.cursor = nextPage.nextCursor;
    this.allLoaded = !nextPage.hasMore;
    this.isLoading = false;
}
```

The cursor-based paging on the Apex side avoids `OFFSET`'s 2,000-row ceiling. See [[08.5 - LIMIT, OFFSET, ORDER BY and Pagination]].

## When not to use datatable

**Complex per-row layouts.** Datatable is a grid. A card layout with several lines per item is a `for:each` over a custom row component.

**Heavy interaction per row.** Several buttons, expandable detail, nested components — a custom row component is clearer.

**Very large datasets** without paging.

**When `lightning-tree-grid` fits better** — hierarchical data with expandable rows.

The alternative is straightforward:

```html
<template for:each={claims} for:item="claim">
    <c-claim-row key={claim.Id} claim={claim} onclaimapproved={handleApproved}></c-claim-row>
</template>
```

More markup, complete control, and each row is independently testable.

## Modals

```html
<lightning-button label="Approve" onclick={openModal}></lightning-button>

<template lwc:if={isModalOpen}>
    <section role="dialog" tabindex="-1" class="slds-modal slds-fade-in-open">
        <div class="slds-modal__container">
            <header class="slds-modal__header">
                <h2 class="slds-modal__title">Approve Claim</h2>
            </header>
            <div class="slds-modal__content slds-p-around_medium">
                <lightning-input type="number" label="Approved amount"></lightning-input>
            </div>
            <footer class="slds-modal__footer">
                <lightning-button label="Cancel" onclick={closeModal}></lightning-button>
                <lightning-button variant="brand" label="Approve" onclick={handleApprove}>
                </lightning-button>
            </footer>
        </div>
    </section>
    <div class="slds-backdrop slds-backdrop_open"></div>
</template>
```

The **LightningModal** base module is the modern alternative, providing focus trapping and accessibility properly:

```javascript
import LightningModal from 'lightning/modal';

export default class ApprovalModal extends LightningModal {
    @api claimId;

    handleApprove() {
        this.close({ approved: true, amount: this.amount });
    }
}
```

```javascript
const result = await ApprovalModal.open({
    size: 'small',
    claimId: this.recordId
});

if (result?.approved) {
    await this.refresh();
}
```

`await` on `open()` resolving with the modal's result is much cleaner than the event-based alternative, and the accessibility is handled.

## Practical guidance

**Reach for a base component before writing markup.**

**Use the formatted components** for currency and dates — locale handling is free.

**Check the component reference** for event payload shapes; they are inconsistent.

**Flatten data in the wire handler** for datatable, not in a getter.

**Set `key-field` to something genuinely unique.**

**Clear `draftValues`** after a successful inline-edit save.

**Batch inline-edit saves through Apex** rather than one `updateRecord` per row.

**Page beyond a few hundred rows.** Datatable renders everything.

**Use `LightningModal`** rather than hand-built modal markup.
