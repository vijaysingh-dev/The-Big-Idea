# Custom Objects and Object Settings

## Creating one

A custom object is created in Setup, or in source and deployed. Either way the result is metadata, and it is worth seeing what that metadata contains, because every checkbox in the user interface maps to a line here.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<CustomObject xmlns="http://soap.sforce.com/2006/04/metadata">
    <label>Warranty Claim</label>
    <pluralLabel>Warranty Claims</pluralLabel>
    <nameField>
        <label>Claim Number</label>
        <type>AutoNumber</type>
        <displayFormat>WC-{00000}</displayFormat>
    </nameField>
    <deploymentStatus>Deployed</deploymentStatus>
    <sharingModel>Private</sharingModel>
    <enableActivities>true</enableActivities>
    <enableHistory>true</enableHistory>
    <enableReports>true</enableReports>
    <enableSearch>true</enableSearch>
    <enableBulkApi>true</enableBulkApi>
    <enableFeeds>false</enableFeeds>
</CustomObject>
```

The settings in that file are the ones that matter, and several of them are hard to change later.

## The Name field, and the decision inside it

Every object has a Name field, and you choose its type when you create the object. This choice is permanent in practice.

**Text.** A free-text label. Right when records have a natural human name — a project, a machine model, a product.

**Auto Number.** A sequential identifier generated by the platform, using a display format such as `WC-{00000}`. Right when records have no natural name — claims, tickets, transactions, shipments.

The tradeoff to think about before choosing Auto Number: the value is generated on insert and cannot be set, which means you cannot preserve original identifiers during a data migration from a legacy system, and you cannot upsert on it. Teams that migrate from an old system into an Auto Number field lose the old reference numbers unless they add a separate external ID field to hold them. Doing that from the start is much easier than retrofitting it.

If you need a human-readable identifier *and* a migration path, a common pattern is a Text name field plus a formula or a trigger that assigns a readable code, with an external ID field for the legacy number.

## Object settings that shape everything after

**Sharing model (OWD).** Public Read/Write, Public Read Only, or Private. This is the baseline of the entire record access model and every sharing rule builds on it. Setting it correctly at creation is far easier than tightening it later, because tightening triggers a full sharing recalculation across every existing record. See [[03.7 - Organization-Wide Defaults]].

**Allow Activities.** Enables Tasks and Events against the object. Cannot be meaningfully undone once activities exist. Cheap to enable, so enable it unless you have a reason not to.

**Track Field History.** Enables the object's history table, storing old and new values for up to twenty selected fields. Essential for anything audited, and the standard retention is limited unless the org has Field Audit Trail. See [[22.3 - Field Audit Trail and Data Retention]].

**Allow Reports.** If this is off, the object cannot be reported on at all, and turning it on later does not retroactively create report types cleanly. Leave it on.

**Allow Search.** Controls whether records appear in global search and are available to SOSL.

**Enable Chatter Feeds.** Adds a feed to each record. Useful for collaboration, but feed records consume storage and add noise on high-volume objects.

**Deployment Status.** In Development hides the object from everyone except users with Customize Application permission. Deployed makes it visible. Useful for building something over several releases without exposing a half-built object.

## What comes free

Once the object exists, the platform gives you a large amount without any further work:

- A REST and SOAP API endpoint, immediately
- SOQL and SOSL access
- Reports and dashboards
- Full sharing and field-level security
- Triggers and flow support
- Field history tracking
- The Lightning record page, list views, and the mobile app
- Import through Data Loader and the Bulk API

```java
Warranty_Claim__c claim = new Warranty_Claim__c(
    Account__c = accountId,
    Machine__c = machineId,
    Claim_Date__c = Date.today(),
    Status__c = 'Submitted'
);
insert claim;

// Claim_Number__c is populated by the platform, so re-query to read it
claim = [SELECT Id, Claim_Number__c FROM Warranty_Claim__c WHERE Id = :claim.Id];
```

That last detail catches people: auto-number and formula fields are not populated on the in-memory object after insert. You have to query the record back to read them.

## Tabs, apps, and navigation

An object with no tab is invisible in navigation, though it still works through related lists, code, and the API. Creating a tab and adding it to a Lightning App is what makes it usable by people.

Not every object needs a tab. Junction objects and child records are usually reached through their parent's related list, and giving them top-level navigation just clutters the app.

## Limits worth knowing before you design

- A few hundred custom objects per org in Enterprise Edition, more in Unlimited
- A few hundred custom fields per object, and relationship fields count toward it
- 25 lookup relationships per object
- 2 master-detail relationships per object
- 40 roll-up summary fields per object

These are hard ceilings. Large orgs hit the field limit on Account and Opportunity in particular, and the remedy at that point — moving fields to a child object, or consolidating — is a migration project. This is the practical reason behind resisting a new field for every request.

## Deleting objects, and why it is not clean

Deleting a custom object moves it to a recycle bin for fifteen days, then removes it permanently along with all its records.

It fails if anything still references it: a formula field, a validation rule, a flow, an Apex class, a report type, a page layout. Untangling those references is often more work than the deletion itself, and this is why unused objects tend to survive in orgs for years.

The realistic approach for an object that is no longer needed: remove permissions so nobody can see it, remove its tab, mark the label as deprecated, and delete it later once you have confirmed nothing depends on it.

## Practices that pay off later

**Describe the object in its description field.** Six months later, "why does this exist" is a real question, and Setup is the only place the answer will survive team changes.

**Add an External ID field on anything that will be integrated.** A unique, indexed field holding the identifier from the source system makes upserts idempotent and makes reconciliation possible. Adding it after a million records have loaded is painful. See [[10.3 - Upsert, Merge and External IDs]].

**Decide the sharing model deliberately.** Private by default is the safer starting point for anything with commercial or personal data, because opening access later is trivial and closing it later is not.

**Think about volume before you build.** An object that will hold ten million rows needs indexed fields, a query strategy, and an archiving plan from day one. Section 23 covers this properly, but the decisions start here.
