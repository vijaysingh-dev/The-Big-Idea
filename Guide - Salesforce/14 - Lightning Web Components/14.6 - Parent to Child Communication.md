# Parent to Child Communication

## Public properties

The primary mechanism. A child declares `@api` properties; the parent sets them as attributes.

```javascript
// claimRow.js
import { LightningElement, api } from 'lwc';

export default class ClaimRow extends LightningElement {
    @api claim;
    @api showActions = false;
    @api maxDescriptionLength = 100;
}
```

```html
<!-- parent -->
<template for:each={claims} for:item="claim">
    <c-claim-row key={claim.Id}
                 claim={claim}
                 show-actions
                 max-description-length="50">
    </c-claim-row>
</template>
```

**camelCase becomes kebab-case.** `showActions` is `show-actions`, `maxDescriptionLength` is `max-description-length`.

**A boolean attribute present with no value is `true`.** `show-actions` sets it true; omitting it leaves the default.

**Literal values in markup are strings.** `max-description-length="50"` passes the string `"50"`, not the number. Where the type matters, bind a property instead:

```html
<c-claim-row max-description-length={rowLimit}></c-claim-row>
```

## Public properties are read-only inside the child

```javascript
@api claim;

handleApprove() {
    this.claim.Status__c = 'Approved';   // wrong
}
```

Assigning to a public property throws. Mutating the object it holds does not throw, and it is equally wrong — the child is modifying data the parent owns, and the parent's reactivity does not fire.

**Data flows down through properties; changes flow up through events.** The child dispatches; the parent decides. See [[14.7 - Child to Parent Communication and Events]].

Where the child needs a local working copy:

```javascript
_claim;

@api
get claim() {
    return this._claim;
}

set claim(value) {
    // a shallow copy gives the child something safe to work with
    this._claim = { ...value };
}
```

## Getter and setter pairs

Reacting to a property being set requires the pair:

```javascript
_accountId;

@api
get accountId() {
    return this._accountId;
}

set accountId(value) {
    this._accountId = value;
    if (value) {
        this.loadClaimsFor(value);
    }
}
```

**`@api` goes on the getter only.**

Two cautions:

**The setter can fire before the component is connected**, so anything needing the DOM must be deferred to `connectedCallback` or `renderedCallback`.

**The setter fires on every assignment**, including when the parent re-renders and reassigns the same value. Guard against redundant work:

```javascript
set accountId(value) {
    if (value === this._accountId) {
        return;
    }
    this._accountId = value;
    this.loadClaimsFor(value);
}
```

Without that guard, a parent rerender triggers a redundant Apex call.

## Public methods

A parent can call a method on a child, which is the imperative escape hatch.

```javascript
// claimList.js
export default class ClaimList extends LightningElement {
    @api
    refresh() {
        return refreshApex(this.claimResult);
    }

    @api
    selectClaim(claimId) {
        this.selectedId = claimId;
    }

    @api
    validate() {
        return [...this.template.querySelectorAll('lightning-input')]
            .every((input) => input.reportValidity());
    }
}
```

```javascript
// parent
handleRefreshClick() {
    this.template.querySelector('c-claim-list').refresh();
}

handleSubmit() {
    const list = this.template.querySelector('c-claim-list');
    if (!list.validate()) {
        return;
    }
    this.save();
}
```

**Public methods are the right tool for imperative operations** — refresh, focus, validate, reset. They are the wrong tool for passing data, which properties do better.

The query returns null if the child is not rendered — behind an `lwc:if` that is currently false, for example — so optional chaining is worth using:

```javascript
this.template.querySelector('c-claim-list')?.refresh();
```

## Passing objects and arrays

```html
<c-claim-list claims={claims} filters={activeFilters}></c-claim-list>
```

The child receives the same object reference the parent holds. Two consequences:

**Mutating it in the child affects the parent's data** without triggering the parent's reactivity. This is how state gets out of sync in ways that are hard to trace.

**Reassigning in the parent triggers the child's setter**; mutating does not.

```javascript
// The child sees the change
this.claims = [...this.claims, newClaim];

// The child does not
this.claims.push(newClaim);
```

This is the reassignment rule from [[14.4 - Reactivity and Decorators]], and it applies across the component boundary as much as within one.

## Passing functions

A parent can pass a function as a property, and it is usually the wrong choice.

```html
<!-- Works, and couples the child to the parent's implementation -->
<c-claim-row on-approve={handleApprove}></c-claim-row>
```

The idiomatic alternative is an event: the child announces what happened, the parent decides what to do. That keeps the child reusable — a component dispatching `claimapproved` works anywhere, while one expecting an `onApprove` function only works where that function is provided.

Functions as properties are occasionally justified for a formatter or comparator, where the child genuinely needs behaviour rather than notification:

```html
<c-data-table rows={rows} row-formatter={formatRow}></c-data-table>
```

## Slots, as an alternative

Where the parent needs to supply **markup** rather than data, slots are the mechanism.

```html
<!-- claimCard.html -->
<template>
    <div class="card">
        <slot name="header"></slot>
        <slot></slot>
        <slot name="actions"></slot>
    </div>
</template>
```

```html
<c-claim-card>
    <h2 slot="header">{claim.Claim_Number__c}</h2>
    <p>{claim.Description__c}</p>
    <lightning-button slot="actions" label="Approve" onclick={handleApprove}></lightning-button>
</c-claim-card>
```

The slotted content belongs to the **parent** — its handlers, its styles, its data. The child only decides where it appears.

Covered in [[14.9 - Slots and Composition]].

## A worked example

A list passing data down and exposing an imperative refresh:

```javascript
// claimDashboard.js — the parent
import { LightningElement, api, wire } from 'lwc';
import { refreshApex } from '@salesforce/apex';
import getClaims from '@salesforce/apex/ClaimController.getClaimsForAccount';

export default class ClaimDashboard extends LightningElement {
    @api recordId;

    claimResult;
    selectedStatus = 'All';

    @wire(getClaims, { accountId: '$recordId', status: '$selectedStatus' })
    wiredClaims(result) {
        this.claimResult = result;
    }

    get claims() {
        return this.claimResult?.data ?? [];
    }

    get hasClaims() {
        return this.claims.length > 0;
    }

    handleStatusChange(event) {
        // reassigning a reactive wire parameter re-runs the wire
        this.selectedStatus = event.detail.value;
    }

    handleClaimApproved() {
        refreshApex(this.claimResult);
    }
}
```

```html
<template>
    <lightning-card title="Warranty Claims">
        <lightning-combobox
            label="Status"
            value={selectedStatus}
            options={statusOptions}
            onchange={handleStatusChange}>
        </lightning-combobox>

        <template lwc:if={hasClaims}>
            <template for:each={claims} for:item="claim">
                <c-claim-row key={claim.Id}
                             claim={claim}
                             show-actions
                             onclaimapproved={handleClaimApproved}>
                </c-claim-row>
            </template>
        </template>
        <template lwc:else>
            <p class="slds-p-around_medium">No claims match this filter.</p>
        </template>
    </lightning-card>
</template>
```

Data down through `claim`, notification up through `onclaimapproved`, and the parent owning the refresh.

## Practical guidance

**Pass data through `@api` properties.**

**Never mutate a public property in the child.** Copy it if a working version is needed.

**Guard setters** against redundant assignment.

**Use public methods for imperative operations only** — refresh, focus, validate.

**Optional-chain the child query**, since it returns null when the child is not rendered.

**Reassign, do not mutate**, when updating data the child is bound to.

**Prefer events to callback functions**, so children stay reusable.

**Use slots when the parent supplies markup rather than data.**
