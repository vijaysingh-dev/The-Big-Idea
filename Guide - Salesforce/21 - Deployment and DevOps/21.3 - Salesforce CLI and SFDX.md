# Salesforce CLI and SFDX

## The tool everything else sits on

The CLI wraps the Metadata API, the Tooling API, the REST API, and the packaging APIs. Every CI pipeline, every VS Code extension command, and every scripted deployment runs through it.

```bash
npm install --global @salesforce/cli
sf --version
sf update
```

**`sf` replaced `sfdx`.** Older documentation and scripts use `sfdx force:source:deploy` and similar; the current form is `sf project deploy start`. Both work for now, and new work should use `sf`.

## Authorizing orgs

```bash
# Interactive, opens a browser
sf org login web --alias production --instance-url https://login.salesforce.com
sf org login web --alias uat --instance-url https://test.salesforce.com

# Non-interactive, for CI
sf org login jwt \
  --client-id {consumer_key} \
  --jwt-key-file server.key \
  --username integration@northwind.com \
  --instance-url https://myorg.my.salesforce.com \
  --alias production

sf org list
sf org display --target-org production
sf config set target-org=uat
```

**JWT is the CI authentication method** — no browser, no password, no refresh token to expire. It is also the fastest way to verify a connected app's configuration in isolation from client code. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**Set a default org** to avoid `--target-org` on every command, and be careful with it — a default of production is how an accidental deployment happens.

## Retrieving

```bash
# By manifest
sf project retrieve start --manifest manifest/package.xml --target-org production

# By metadata type
sf project retrieve start --metadata "ApexClass:ClaimApprovalService" --target-org uat
sf project retrieve start --metadata "CustomObject:Warranty_Claim__c" --target-org uat

# By source path
sf project retrieve start --source-dir force-app/main/default/lwc --target-org uat

# Everything that changed in the org since the last sync (source-tracked orgs only)
sf project retrieve start --target-org scratch-org
```

**Source tracking works in scratch orgs and Developer Pro sandboxes**, letting the CLI detect what changed without a manifest. In production and full sandboxes it does not, which is why manifests remain necessary.

Generating a manifest from an existing org:

```bash
sf project generate manifest --from-org production --output-dir manifest
sf project generate manifest --metadata ApexClass,CustomObject --output-dir manifest
```

For a mature org this produces a large file that needs pruning — managed package components, in particular, should be excluded.

## Deploying

```bash
# Validate without committing
sf project deploy validate \
  --manifest manifest/package.xml \
  --test-level RunLocalTests \
  --target-org production

# Deploy a validated result quickly
sf project deploy quick --job-id 0Af5g00000ABCDeAAB --target-org production

# Deploy directly
sf project deploy start --source-dir force-app --target-org uat

# With destructive changes
sf project deploy start \
  --manifest manifest/package.xml \
  --post-destructive-changes manifest/destructiveChangesPost.xml \
  --target-org production

# Check on a running deployment
sf project deploy report --target-org production
sf project deploy cancel --target-org production
```

**`validate` then `quick` is the pattern for a short release window.** Validation runs every test and takes as long as it takes; the quick deploy commits in seconds. The validation is good for 10 days.

**Deploying only what changed**, which is what a pipeline does:

```bash
sf project deploy start \
  --source-dir $(git diff --name-only origin/main -- force-app | xargs dirname | sort -u) \
  --test-level RunSpecifiedTests \
  --tests ClaimApprovalServiceTest \
  --target-org uat
```

Several community plugins do this better by computing a delta manifest, covered below.

## Running tests

```bash
sf apex run test --tests ClaimApprovalServiceTest --result-format human --wait 10
sf apex run test --class-names ClaimApprovalServiceTest,ClaimSelectorTest --wait 10
sf apex run test --test-level RunLocalTests --code-coverage --output-dir test-results --wait 30
sf apex get test --test-run-id 707... --code-coverage --output-dir test-results
```

**`--output-dir` writes JUnit and coverage files**, which is what a CI pipeline publishes as a test report.

## Data commands

```bash
# Query
sf data query --query "SELECT Id, Name FROM Account LIMIT 10" --target-org uat
sf data query --query "SELECT Name FROM ApexTrigger" --use-tooling-api --target-org production

# Single records
sf data create record --sobject Account --values "Name='Northwind Test'" --target-org uat
sf data update record --sobject Account --record-id 001... --values "Industry='Manufacturing'"
sf data delete record --sobject Account --record-id 001...

# Bulk
sf data upsert bulk --sobject Warranty_Claim__c --file claims.csv \
  --external-id ERP_Claim_Id__c --wait 30 --target-org production

sf data query bulk --query "SELECT Id, Claim_Number__c FROM Warranty_Claim__c" \
  --output-file claims.csv --wait 30 --target-org production

# Export and import a related record tree
sf data export tree --query "SELECT Id, Name, (SELECT Id, Name FROM Assets) FROM Account" \
  --prefix seed --output-dir data --target-org production

sf data import tree --plan data/seed-Account-plan.json --target-org scratch-org
```

**`export tree` and `import tree` are the scratch org seeding mechanism** — they preserve relationships by resolving Ids at import time. Limited to 200 records per file, which makes them right for reference data and wrong for volume. See [[21.11 - Sandbox Strategy and Data Seeding]].

**The `--use-tooling-api` flag** is how `ApexLog`, `TraceFlag`, `ApexCodeCoverage`, and `MetadataComponentDependency` are queried. See [[13.6 - Metadata API and Tooling API]].

## Apex commands

```bash
# Run anonymous Apex from a file — versioned, repeatable
sf apex run --file scripts/apex/post-deploy.apex --target-org production

# Stream logs live
sf apex tail log --target-org uat --color

# Fetch a specific log
sf apex list log --target-org production
sf apex get log --log-id 07L5g00000ABCDeAAN --target-org production > debug.log
```

**`sf apex run --file` is how post-deployment steps become repeatable** rather than a manual checklist. Creating Custom Setting records, scheduling jobs, and backfilling a field all belong in a versioned script. See [[21.10 - Deployment Strategies, Rollback and Hotfixes]].

**`sf apex tail log`** creates a trace flag, streams, and cleans up on exit — the fastest interactive debugging loop available. See [[20.2 - Trace Flags and Log Management]].

## Scratch orgs

```bash
sf org create scratch --definition-file config/project-scratch-def.json \
  --alias dev-claims --duration-days 7 --set-default

sf project deploy start --source-dir force-app --target-org dev-claims
sf org open --target-org dev-claims
sf org delete scratch --target-org dev-claims --no-prompt
```

## Packaging

```bash
sf package create --name "Northwind Core" --package-type Unlocked \
  --path force-app/core --target-dev-hub my-devhub

sf package version create --package "Northwind Core" \
  --installation-key-bypass --code-coverage --wait 30

sf package version promote --package "Northwind Core@1.2.0-3"

sf package install --package "Northwind Core@1.2.0-3" --target-org production --wait 20

sf package list --target-dev-hub my-devhub
sf package version list --target-dev-hub my-devhub
```

See [[21.5 - Unlocked Packages]].

## Static analysis

```bash
sf plugins install @salesforce/sfdx-scanner

sf scanner run --target force-app --format table
sf scanner run --target force-app --severity-threshold 3 --format json --outfile scanner.json
sf scanner run dfa --target force-app --projectdir force-app --format table
```

**`scanner run dfa`** is the graph engine, which traces data flow across method calls for injection paths — the part PMD alone cannot do. See [[21.9 - Static Analysis, PMD and Code Review]].

## Plugins worth having

```bash
sf plugins install sfdx-git-delta
sf plugins install @salesforce/sfdx-scanner
sf plugins install sfdmu
sf plugins list
```

**`sfdx-git-delta`** generates a manifest from a Git diff, which is what makes incremental deployment practical:

```bash
sf sgd source delta --to HEAD --from HEAD~1 --output manifest/
# produces package/package.xml and destructiveChanges/destructiveChanges.xml
```

That one plugin turns "deploy everything" into "deploy what changed", cutting deployment time substantially on a large repository. It is close to essential in a real pipeline. See [[21.8 - CI-CD Pipelines]].

**`sfdmu`** (Salesforce Data Move Utility) handles complex data migration with relationship resolution, far beyond what `data import tree` supports.

## Output formats and scripting

```bash
sf org display --target-org production --json
sf apex run test --result-format json --wait 10
sf data query --query "SELECT COUNT() FROM Account" --json | jq '.result.totalSize'
```

**`--json` on every command** makes the CLI scriptable. A pipeline step parsing JSON is reliable; one parsing human-readable output is not.

**Exit codes are meaningful** — non-zero on failure, which is what makes a pipeline step fail correctly.

## Configuration

```bash
sf config list
sf config set target-org=uat
sf config set target-dev-hub=my-devhub
sf config set org-api-version=62.0
sf config set --global target-dev-hub=my-devhub
```

**Local configuration lives in `.sf/config.json`** in the project, global in the home directory. Committing the local file with a default org is convenient and worth thinking about — a default of production in a shared repository is a hazard.

## Common problems

**"No default environment found."** No `--target-org` and no default set.

**Deployment fails on unrelated tests.** `RunLocalTests` runs everything. Someone else's broken test blocks your release.

**"Cannot modify a scheduled Apex class."** Abort the job, deploy, reschedule.

**Retrieval brings back managed package metadata.** Prune the manifest, or exclude the namespace.

**Source tracking is confused.** In a scratch org:

```bash
sf project reset tracking --target-org scratch-org
```

**The CLI is out of date**, which produces errors that make no sense against a newer API version:

```bash
sf update
```

## A working session

```bash
# Start
sf org create scratch --definition-file config/project-scratch-def.json --alias feature-x
sf project deploy start --source-dir force-app --target-org feature-x
sf data import tree --plan data/seed-plan.json --target-org feature-x

# Work
sf project deploy start --source-dir force-app/main/default/classes --target-org feature-x
sf apex run test --tests ClaimApprovalServiceTest --result-format human
sf apex tail log --target-org feature-x --color

# Retrieve what was changed in the org UI
sf project retrieve start --target-org feature-x

# Validate against the real target
sf project deploy validate --source-dir force-app --test-level RunLocalTests --target-org uat

# Clean up
sf org delete scratch --target-org feature-x --no-prompt
```

## Practical guidance

**Use `sf`, not `sfdx`**, in new scripts.

**Authenticate CI with JWT.**

**Validate then quick-deploy** for a short release window.

**Use `sfdx-git-delta`** to deploy only what changed.

**Put post-deployment steps in a versioned Apex script.**

**Use `--json` in anything scripted.**

**Be careful with a default org set to production.**

**Keep the CLI updated** — stale versions produce confusing failures.
