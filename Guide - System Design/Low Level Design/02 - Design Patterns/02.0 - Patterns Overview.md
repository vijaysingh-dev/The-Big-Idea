# Design Patterns Overview

Design patterns are **named solutions to recurring design problems**. They're a shared vocabulary — saying "use Strategy here" communicates more than explaining the solution from scratch.

---

```
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────────┐
│   CREATIONAL     │  │   STRUCTURAL     │  │     BEHAVIORAL       │
│                  │  │                  │  │                      │
│ How objects      │  │ How objects      │  │ How objects          │
```

## Pattern Selection Quick Reference

> The most important skill is knowing _when_ to apply a pattern, not _how_ to implement it.

|Symptom|Pattern to Consider|
|---|---|
|`if/elif` chain on type/method → new type = edit|**Strategy** or **Factory Method**|
|Behavior must change at runtime|**Strategy** or **State**|
|Need to add cross-cutting behavior (logging, retry, auth)|**Decorator** or **Proxy**|
|Object creation is complex or needs multiple steps|**Builder**|
|Multiple objects need one thing to change|**Observer**|
|Complex subsystem, callers need simplicity|**Facade**|
|Incompatible third-party interface|**Adapter**|
|Multiple steps with some fixed, some variable|**Template Method**|
|Request needs to pass through multiple handlers|**Chain of Responsibility**|
|Object lifecycle has distinct states|**State**|
|Need to decouple sender from receiver|**Command** or **Observer**|
|Tree structures, uniform leaf/composite treatment|**Composite**|
|Expensive object creation / access control|**Proxy**|
|Need exactly one instance globally|**Singleton**|
|Related families of objects|**Abstract Factory**|

## How to Learn Each Pattern

For each pattern, internalize in this order:

1. **The Problem** — what pain does it solve? (without this, you can't recognize when to use it)
2. **The Structure** — participants and their roles
3. **A Real Example** — backend-focused, not toy
4. **When NOT to use it** — patterns misapplied create complexity
5. **The Interview Angle** — what interviewers look for

---

## Common Pattern Mistakes

|Mistake|What Actually Happens|
|---|---|
|Pattern for pattern's sake|Complexity without benefit|
|Over-abstracting too early|"Wrong abstraction" that fights future requirements|
|Applying pattern to wrong problem|E.g., Singleton for objects that should have multiple instances|
|Ignoring thread-safety in Singleton|Subtle race conditions in production|
|Observer without cleanup|Memory leaks from dangling listeners|
|Deep Decorator chains|Debugging hell — hard to trace execution|
|Saga without compensation logic|Partial failures leave system in inconsistent state|

## Pattern Relationships Map

```
Strategy ──────── Context uses a Strategy
    │
    └── similar to ──── State (state changes own context's state)

Factory Method ─── creates objects polymorphically
    │
    └── extends to ─── Abstract Factory (families of objects)

Decorator ─────── wraps same interface
    │
    └── similar to ─── Proxy (controls access vs adds behavior)

Observer ──────── loose coupling notification
    │
    └── enables ──── Event Sourcing, CQRS

Command ────────── encapsulates request
    │
    └── powers ──── Job queues, Undo/redo, Saga steps

Chain of Resp. ─── pipeline processing
    │
    └── similar to ─── Middleware stacks
```
