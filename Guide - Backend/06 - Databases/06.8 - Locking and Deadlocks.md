# Locking and Deadlocks

#backend #databases #postgres #operations

> **In one line:** Reads never block reads and writes never block reads, so almost every lock problem you meet is either two writers on the same row or a DDL statement that took a lock nobody expected.

---

## The Idea

MVCC means readers do not take locks ([[06.7 - MVCC Vacuum and Bloat]]), which eliminates most of the lock contention other databases suffer from.

| Conflict | Blocks? |
|---|---|
| Read vs read | No |
| **Read vs write** | **No** — MVCC |
| Write vs write on the **same row** | Yes |
| Write vs write on different rows | No |
| **DDL vs anything** | **Usually yes** |

💡 **That last row is where production incidents come from.** An `ALTER TABLE` that looks instant takes a lock blocking every query on the table, and if it waits behind a long-running transaction, it queues everything behind *it*.

---

## Table-Level Lock Modes

| Mode | Taken by | Conflicts with |
|---|---|---|
| `ACCESS SHARE` | `SELECT` | Only `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT FOR UPDATE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | `SHARE` and above |
| **`SHARE UPDATE EXCLUSIVE`** | `VACUUM`, `CREATE INDEX CONCURRENTLY`, `ANALYZE` | Itself and above |
| `SHARE` | `CREATE INDEX` (non-concurrent) | `ROW EXCLUSIVE` and above |
| **`ACCESS EXCLUSIVE`** | Most `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL` | **Everything** |

⚠️ **`ACCESS EXCLUSIVE` blocks even `SELECT`.** If you take one on a hot table, your entire application stops.

💡 **The mode to memorise is `SHARE UPDATE EXCLUSIVE`** — the "safe" mode. It conflicts with other maintenance operations and DDL, but not with reads or writes. **Any operation taking only this mode can run on a live table without blocking traffic.**

---

## The Lock Queue

The behaviour that turns a fast operation into an outage.

```
Transaction A (running 20 min):  SELECT ... FROM documents;   [ACCESS SHARE]
Transaction B:                   ALTER TABLE documents ...;   [ACCESS EXCLUSIVE] ← waits
Transaction C:                   SELECT ... FROM documents;   ← WAITS BEHIND B
...every query on the table now queues...
```

⚠️ **Lock requests queue in order and are not reordered.** C could run alongside A — reads do not conflict — but it is behind B in the queue.

**One long-running query plus one DDL statement equals a complete outage on that table, even though neither alone would cause a problem.**

💡 **This is the most important lock fact in Postgres**, and it is the reason every migration guide insists on `lock_timeout`:

```sql
SET lock_timeout = '3s';
ALTER TABLE documents ADD COLUMN ...;
```

**If the lock cannot be acquired in 3 seconds, the statement fails and the queue drains. You retry rather than take down the application.**

## Row-Level Locks

| Mode | Taken by | Blocks |
|---|---|---|
| `FOR UPDATE` | Explicit, or `UPDATE`/`DELETE` | Other row locks |
| `FOR NO KEY UPDATE` | `UPDATE` not touching a unique key | `FOR UPDATE`, `FOR NO KEY UPDATE` |
| `FOR SHARE` | Explicit | `FOR UPDATE`, `FOR NO KEY UPDATE` |
| **`FOR KEY SHARE`** | **Foreign key checks** | `FOR UPDATE` only |

⚠️ **Row locks are stored in the tuple header, not a lock table** — so Postgres can hold unlimited row locks with no memory cost, unlike table locks.

### The foreign key surprise

💡 **Inserting a child row locks the parent row.** In a high-throughput system where many rows reference one parent — every order referencing one popular product, every event referencing one organisation — **that parent row becomes a contention point.**

**This is why `FOR KEY SHARE` exists**: it is the weakest lock, so concurrent inserts referencing the same parent do not block each other. **But an update to the parent's key, or a delete, still waits for all of them.**

## Deadlocks

```
A: UPDATE accounts WHERE id = 1;   -- locks row 1
B: UPDATE accounts WHERE id = 2;   -- locks row 2
A: UPDATE accounts WHERE id = 2;   -- waits for B
B: UPDATE accounts WHERE id = 1;   -- waits for A → deadlock
```

Postgres detects the cycle after `deadlock_timeout` (1 second) and aborts one transaction.

### The fix is ordering

```python
for account_id in sorted(account_ids):
    await conn.execute("SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE", account_id)
```

💡 **Deadlocks are almost always caused by inconsistent lock ordering, and sorting the IDs before locking eliminates them entirely.** This one-line fix resolves the large majority of real deadlocks.

### Deadlocks you did not write

⚠️ **A plan change can alter lock acquisition order and introduce a deadlock that did not exist before.** If deadlocks appear after data growth or a Postgres upgrade with no code change, this is a likely cause.

```sql
UPDATE documents SET status = 'x'
WHERE id IN (SELECT id FROM documents WHERE org_id = 7 ORDER BY id FOR UPDATE);
```

### Diagnosing

```sql
SET log_lock_waits = on;
SET deadlock_timeout = '1s';
```

**Turn this on everywhere** — every deadlock is logged with both queries and the lock graph, and **a deadlock without the log entry is nearly impossible to diagnose after the fact.**

## DDL Without Downtime

### Safe — metadata only, brief `ACCESS EXCLUSIVE`

| Operation | Since |
|---|---|
| `ADD COLUMN` (nullable, no default) | Always |
| **`ADD COLUMN ... DEFAULT <constant>`** | **PG 11** — no table rewrite |
| `DROP COLUMN` | Always — marks it dead |
| `RENAME COLUMN` / `RENAME TABLE` | Always |
| `ADD CONSTRAINT ... NOT VALID` | Always |
| `VALIDATE CONSTRAINT` | Takes only `SHARE UPDATE EXCLUSIVE` |

⚠️ **These still take `ACCESS EXCLUSIVE` briefly**, so they still queue behind long transactions. **`lock_timeout` is required even for "safe" DDL.**

### Dangerous — full table rewrite

| Operation | Why |
|---|---|
| `ALTER COLUMN TYPE` (most changes) | Rewrites every row |
| `ADD COLUMN ... DEFAULT <volatile>` | Must compute per row |
| `ADD PRIMARY KEY` | Builds an index under `ACCESS EXCLUSIVE` |
| `SET NOT NULL` (before PG 12) | Full scan to verify |

💡 **`ADD COLUMN ... DEFAULT` becoming metadata-only in Postgres 11 was a genuinely significant change.** A lot of migration folklore predates it — **check your version before assuming.**

### The safe patterns

```sql
-- SET NOT NULL without a long lock (PG 12+)
ALTER TABLE documents ADD CONSTRAINT title_not_null CHECK (title IS NOT NULL) NOT VALID;
ALTER TABLE documents VALIDATE CONSTRAINT title_not_null;   -- SHARE UPDATE EXCLUSIVE
ALTER TABLE documents ALTER COLUMN title SET NOT NULL;      -- instant, uses the constraint
ALTER TABLE documents DROP CONSTRAINT title_not_null;
```

⚠️ **`NOT VALID` means existing rows are not checked; new rows are.** `VALIDATE` then checks the existing ones under a weak lock. **This two-step pattern is the foundation of safe migrations** ([[06.11 - Zero Downtime Migrations]]).

## In Production

### The lock investigation

```sql
SELECT
    blocked.pid AS blocked_pid, blocked.query AS blocked_query,
    blocking.pid AS blocking_pid, blocking.query AS blocking_query,
    now() - blocking.xact_start AS blocking_duration
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock';
```

💡 **`pg_blocking_pids(pid)` is the function that makes this tractable**, and it is not widely known — it returns exactly the processes blocking a given one, following the chain.

```sql
SELECT pg_cancel_backend(pid);      -- cancel the query, keep the connection
SELECT pg_terminate_backend(pid);   -- kill the connection
```

⚠️ **Try `pg_cancel_backend` first.** Terminating rolls back the transaction and drops the connection, which the application may not handle well.

### Timeouts as policy

```sql
ALTER ROLE app_user SET statement_timeout = '10s';
ALTER ROLE migration_user SET lock_timeout = '3s';
ALTER ROLE analytics_user SET statement_timeout = '10min';
```

💡 **Setting these per-role rather than globally is the sophisticated approach.** Your application should fail fast; analytics needs time; migrations need a short `lock_timeout` and a retry loop. **One global value cannot serve all three.**

### Hot rows

```sql
UPDATE stats SET view_count = view_count + 1 WHERE page_id = 1;
```

Every writer serialises on that row.

```sql
-- 1. Sharded counters — spread across N rows, sum on read
UPDATE stats SET count = count + 1 WHERE page_id = 1 AND shard = floor(random() * 16);

-- 2. Append and aggregate later
INSERT INTO view_events (page_id, ts) VALUES (1, now());
```

⚠️ **A single hot row can cap your entire write throughput** regardless of cores or connections, because writes to it are strictly serial. **Sharding a counter 16 ways gives roughly 16× the throughput** for a slightly more complex read.

### Monitoring

```sql
SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock';
```

**A rising count of queries waiting on locks is an early warning that precedes user-visible latency** — a better leading indicator than mean query time.

## Codebase

**Repo:** `postgres/postgres`, `ankane/strong_migrations`

**Question to answer:** How does Postgres detect a deadlock — what graph does it build, and when? Then: why does a lock request that conflicts with nothing currently held still wait if another request is queued ahead of it?

**Read, in order:**

1. `src/backend/storage/lmgr/README` — **the lock manager's design.** Lock modes, the conflict table, and the queue. **The answer to the second question is here**: the queue prevents starvation of stronger lock requests
2. `src/backend/storage/lmgr/lock.c` — `LockAcquire` and the wait queue
3. `src/backend/storage/lmgr/deadlock.c` — **`DeadLockCheck`.** The wait-for graph and cycle detection, run after `deadlock_timeout`
4. `src/backend/storage/lmgr/proc.c` — `ProcSleep`, where a backend actually waits
5. `src/include/storage/lockdefs.h` — **the lock mode conflict matrix as a literal table.** Worth reading once
6. `ankane/strong_migrations/lib/strong_migrations/checks.rb` — **the practical payoff.** A catalogue of dangerous migrations and their safe alternatives. **Read it even though it is Ruby** — the content is database knowledge

💡 The `strong_migrations` check list encodes years of accumulated production pain into rules — "this operation takes this lock, use this pattern instead" — and **reading it once will prevent several incidents.**

**Size:** 1–2 sessions.

**Drill 6.8 — Block your own database**

```
└── README.md
```

**Part 1 — Derive the conflict matrix yourself.** For each pair of the eight lock modes, hold one and request the other, and record whether it blocks. **Sixty-four cells.** Compare to `lockdefs.h`.

Tedious, and it converts the table from something you look up into something you know.

**Part 2 — Cause the queue outage.** Start a 60-second `SELECT`. Run `ALTER TABLE ADD COLUMN`. Then run 20 ordinary `SELECT`s.

**Confirm all 20 are blocked**, even though they conflict with nothing actually held.

**Chart application-visible availability over the 60 seconds — a total outage caused by a "safe" DDL statement.**

Then add `SET lock_timeout = '3s'` and confirm the DDL fails quickly and the queue never forms.

**Part 3 — Three kinds of deadlock.** The classic two-row cycle, a foreign-key-mediated deadlock, and one caused by two bulk updates scanning in different orders.

**The third is the interesting one** — force different plans and show the deadlock appearing and disappearing based on scan order.

Then apply consistent ordering and confirm all three are eliminated.

**Part 4 — Measure DDL lock duration.** For twenty operations — every row of both DDL tables — measure on a 10-million-row table: lock mode, lock duration, and whether concurrent reads and writes were blocked.

**This table is a permanent reference and it is more trustworthy than any blog post because it is measured on your version.**

**Part 5 — The `NOT VALID` pattern.** Add a `NOT NULL` constraint and a foreign key to a 10-million-row table, both ways.

Naive: measure the lock duration and confirm the table is unavailable. Two-step: measure both steps and **confirm reads and writes continue throughout.**

**Part 6 — Hot row contention.** A single counter row updated by 1, 5, 20, 50 and 200 concurrent writers.

**Chart total throughput against concurrency — it should plateau early**, because writes to one row are serial.

Then 16-way sharding, chart again, and report the improvement and the added read cost. Then the append-and-aggregate version, comparing all three.

**Part 7 — The diagnosis runbook.** A script that, given a blocked query, prints the full chain up to the root blocker with durations.

Create three different lock incidents and **confirm your tool identifies the root cause in each within seconds.**

Write `runbook.md`: symptom, the query to run, how to interpret it, and when to cancel versus terminate.

**Done when:**
- Your empirically-derived conflict matrix matches `lockdefs.h`
- You caused a full table outage with one "safe" DDL statement and prevented it with `lock_timeout`
- All three deadlock types are reproduced and fixed by consistent ordering
- Your 20-operation DDL lock table is measured on your Postgres version
- The two-step constraint pattern keeps the table available throughout
- Your hot-row chart shows the plateau and the sharding improvement
- Your blocking-tree tool finds the root cause of three different incidents
