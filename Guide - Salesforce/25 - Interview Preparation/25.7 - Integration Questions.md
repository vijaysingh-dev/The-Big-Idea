# Integration Questions

## Design

**How do you approach an integration requirement?**

Three questions before choosing anything.

**Which system owns each field?** Not each object — each field. SAP owns the billing address and credit status; Salesforce owns the industry, owner, and segment. Writing that down is the single most valuable artifact, and its absence is the most common cause of two systems overwriting each other indefinitely.

**Which direction, and who initiates?** Salesforce calling out and an external system calling in are entirely different implementations with different limits and different failure modes.

**Does the caller need the answer now?** That decides synchronous versus asynchronous, and it drives everything about error handling.

The API is a consequence of those answers, not the starting point.

**What are the integration patterns?**

Request and reply, where Salesforce calls out and waits — a credit check, an inventory lookup. Fire and forget, where it notifies and does not wait. Batch synchronization on a schedule. Remote call-in, where the external system calls Salesforce. Data virtualization, showing external data without storing it. And publish-subscribe for event-driven designs.

The mistake worth naming is using request-and-reply where fire-and-forget would do — making a user wait for an external system, and coupling the save to its availability, when nothing about the interaction requires it. If the ERP being down should not stop a claim being approved, the notification is fire-and-forget.

## APIs

**When do you use which API?**

REST for most things — moderate CRUD, JSON, straightforward.

Bulk API 2.0 above a few thousand records, because it consumes a separate allocation from the daily REST limit and processes asynchronously in parallel.

Composite for several operations in one round trip, and Composite Graph specifically for record graphs — up to 500 records, each graph its own transaction, with `@{referenceId.id}` referencing a record created earlier in the same call. That removes round trips to learn Ids.

sObject Collections for up to 200 records of one operation, which is the largest available reduction in API consumption and requires no architectural change.

Metadata API for deployments, Tooling API for inspection, Pub/Sub for event subscription.

SOAP only where a caller's tooling requires a WSDL, or for lead conversion and merge, which REST does not expose. Even then, wrapping the operation in a custom Apex REST endpoint is usually cleaner than maintaining a SOAP client for one call.

**How do you reduce API consumption?**

sObject Collections and Composite for writes — 200 records per call rather than 200 calls.

Bulk API above a few thousand.

Push rather than poll — platform events or Change Data Capture, so the external system is notified rather than asking. An integration polling every minute per record exhausts the daily allocation before lunch.

And querying incrementally on `SystemModstamp` rather than doing full extracts. `SystemModstamp` rather than `LastModifiedDate`, because some platform updates do not touch the latter.

## Authentication

**How would you authenticate a server-to-server integration?**

JWT bearer flow. No stored password, no refresh token to expire quietly after ninety days, no interactive login, and the private key never travels — the client signs an assertion locally and Salesforce verifies against a certificate it already holds.

The setup: a key pair, the certificate uploaded to a connected app with digital signatures enabled, Permitted Users set to admin-approved, and the integration user granted access to the app through a permission set.

Two things that catch people: `aud` must match the environment — `test.salesforce.com` for a sandbox — and the assertion's expiry must be within three minutes, so clock drift on the client produces a failure that looks like a configuration problem.

**What is wrong with username-password flow?**

It stores a password, and the security token silently changes on every password reset, which breaks the integration with no warning.

Salesforce blocks it by default in new orgs now. If I found one in an inherited integration, migrating it to JWT would be the single highest-value security change available, because it removes a stored credential entirely.

**How do you handle credentials for outbound calls?**

Named Credentials, always. They keep the secret out of code and out of data, handle token refresh, and deploy without their secrets so each environment is populated separately.

The alternative — storing a client secret in a custom setting and writing a refresh method — leaks the secret into queryable data, handles refresh unreliably, and is a security review finding.

If I found a credential in a custom setting, I would rotate it as well as moving it. It has been readable by every user who could query the setting.

**You get `invalid_grant`. How do you debug it?**

It is the least informative OAuth error and covers about six causes, so I would work them in order of likelihood.

Wrong login endpoint — `login.salesforce.com` for a sandbox. The user not pre-authorized for the connected app. Permitted Users not set to admin-approved, which JWT requires. An expired or already-used authorization code. Clock drift beyond the assertion window. An IP restriction.

The fastest move is verifying with the CLI first — `sf org login jwt` with the same key and consumer key. If that authenticates, the configuration is correct and the problem is in the client, which isolates the two halves.

## Callouts

**What are the constraints on callouts from Apex?**

No callout after DML in the same transaction. The transaction holds open database work between steps 7 and 17 of the order of execution, and an HTTP call during that window would hold it open for the duration of an external system's response.

So a read-then-write integration works synchronously, and a write-then-notify integration must be async — a Queueable, or a platform event with a subscriber that calls out.

The limits: 100 callouts per transaction and **120 seconds cumulative**, which is the one people forget. Ten callouts at 30 seconds each is 300 seconds and dies partway through, having already done some of the work.

And the marker interface — `Database.AllowsCallouts` on a Queueable or Batch. Omitting it produces a runtime failure on the first callout, in a job that may only sometimes call out.

**How would you push 500 claims to an ERP?**

One callout with a batched payload if the API has a batch endpoint. Not 500 callouts.

Where it has no batch endpoint, Batch Apex with a small scope — each chunk is its own transaction with its own callout budget, so it is one callout per chunk of 200 rather than one per record.

And an idempotency key on the request, so a retry after a timeout does not create duplicates.

## Reliability

**What makes an integration reliable?**

Idempotency first. An operation that can be performed twice with the same effect as once, because retries are inevitable — a timeout where the request actually succeeded, a redelivered event, a replayed batch.

Inbound, that means external IDs and upsert. Outbound, it means sending a key the receiver can deduplicate on.

Then classifying failures. A timeout, a 503, and a lock contention are transient and worth retrying with backoff. A validation failure, a 400, and a 401 are permanent — retrying them a hundred times achieves nothing and burns the async allocation.

Then durable logging with a correlation Id, so a business operation can be traced across the publishing transaction, the subscriber, and the external system's logs.

And reconciliation, because silent divergence is the failure mode nobody has a symptom for.

**The ambiguous case: a request times out. Did it succeed?**

You do not know, and that is the hardest case in integration.

Retrying risks a duplicate; not retrying risks a lost record.

Three resolutions, in order. Make the operation idempotent with an idempotency key, and then retry freely — that is why the header matters. Query before retrying, if the external system exposes a lookup by your reference. Or flag for manual review, which is unsatisfying and better than silently duplicating financial records.

That decision belongs in the integration design, agreed with the external system's owner, rather than discovered during an incident.

**How would you know an integration stopped working?**

That is the failure mode most orgs have no coverage for. A job that stopped running produces no error record — nothing failed, nothing executed.

The only thing that detects it is a last-run timestamp per integration, checked against the expected interval. Alerting on absence, not only on failure.

Alongside that, a reconciliation job — comparing record counts or checksums between systems periodically, which catches the records that were lost without anyone noticing.

## Events

**When would you use a platform event over a REST callout?**

When several independent consumers should react, particularly ones added over time. A claim approval publishing one event, with the ERP, Slack, and an audit system as three subscribers, means adding a fourth requires no change to the publisher.

Also when the callout would follow DML — the subscriber runs in its own transaction where callouts are permitted.

And for logging that must survive a rollback, which is the one place immediate publish behaviour is essential.

For a single consumer with no need for decoupling, a Queueable is simpler and traceable in the code.

**What is the difference between platform events and Change Data Capture?**

Platform events are business messages you design and publish deliberately — "a claim was approved". CDC publishes automatically on every record change — "this record's Status field changed".

One expresses intent; the other expresses a database change. A CDC subscriber has to re-derive the business meaning from a field list.

The practical consequences of CDC: it fires on every change including ones nobody cares about, the delivery allocation counts per subscriber, and it does not carry old values — only new ones and the list of changed field names. Reconstructing "changed from X to Y" means the consumer holding its own prior state.

Enabling CDC on a high-volume object with several subscribers is expensive, and it is a checkbox that produces an ongoing cost.

**What do you have to design for with events?**

Idempotency, because delivery is at-least-once. An upsert on a unique key is the standard mechanism.

`setResumeCheckpoint` in the subscriber, so a retry resumes from the failing event rather than reprocessing the whole batch — which for a non-idempotent handler creates duplicates.

A path for permanently failed events, because after the retry limit the event is discarded.

And 72-hour retention. A subscriber down longer than that has a permanent gap requiring reconciliation, which is why storing the last processed replay Id durably matters.

## Middleware

**When would you introduce MuleSoft or similar?**

When the connection count justifies it. Four systems each integrating with each other is twelve point-to-point connections; through a broker it is four. That arithmetic drives most adoptions.

Also when transformation is complex enough to be duplicated, when retry and monitoring should be centralized, when protocol translation is needed, or when bursts need buffering — middleware queueing requests rather than consuming the daily API allocation in a spike is a genuinely Salesforce-specific benefit.

What I would not do is adopt it because it appears in a reference architecture. Two systems with simple mapping do not need it, and it adds a platform to license, operate, and staff.

**What does middleware not solve?**

The Salesforce-side constraints persist. API limits still apply — the middleware calling Salesforce consumes the same allocation. Governor limits still apply to any Apex it triggers. Bulk is still the right tool for volume, and a badly configured connector calling REST record by record is as expensive as anything else doing so.

And idempotency is still your responsibility. Teams assume the middleware's retry handling makes duplicates impossible, and it does the opposite — automatic retry plus non-idempotent writes is exactly how duplicates are created at scale.

## The scenario

**Design the integration between Salesforce and an ERP for a manufacturer.**

I would start by clarifying: which system owns which fields, what volumes, what latency each direction needs, and what happens when either is down.

Then per flow rather than as one design.

**Product and price catalogue, ERP to Salesforce.** Nightly, so Bulk API 2.0 upserting on an external product code. Load order matters — a product needs a standard price book entry before any custom one, and getting that wrong fails every row of the second load.

**Closed-won opportunities, Salesforce to ERP.** A platform event published by the trigger, with a subscriber calling out — because a callout cannot follow DML, and because three consumers eventually wanted it. An idempotency key on the request, and a Finalizer for retry with backoff.

**Invoice history, read-only, twelve years.** External objects through Salesforce Connect. Several million rows that are rarely accessed and never reported on in Salesforce do not need syncing. The tradeoff accepted is no reporting and no automation on them, which the requirement did not need.

**Machine telemetry.** Filtered outside Salesforce — only faults above a severity threshold arrive, published as platform events. Sending millions of readings would exhaust the event allocation and provide no value. Historical readings go to a big object nightly.

The decisions I would call out: external IDs on every integrated object from day one, because retrofitting one onto a populated object is a backfill project. One scoped integration user per system, not System Administrator. Correlation Ids so a business operation is traceable across both logs. And a reconciliation job per flow, because silent divergence has no symptom.

**And I would question the real-time inventory lookup** if one was requested. If the ERP's 95th percentile response is eleven seconds, a Continuation makes the case page fragile. Syncing hourly into a custom object with a manual refresh action is usually what the business actually needs, and asking what latency is genuinely required frequently changes the answer.

## What is being assessed

**Junior:** knows the APIs exist and what REST does.

**Mid:** knows the callout-after-DML constraint, uses Named Credentials, understands upsert on external IDs.

**Senior:** starts with source-of-truth and latency questions, raises idempotency unprompted, and questions whether a stated real-time requirement is real.

**The strongest signal** is treating reliability as a design concern rather than an error-handling one — idempotency, reconciliation, and alerting on absence are the things learned by having an integration fail silently for three weeks.
