# Classes vs Prototypes

`class` is usually described as "just syntactic sugar over prototypes". That is roughly true and increasingly incomplete — classes have accumulated capabilities that prototypes cannot express.

## What is genuinely sugar

```js
class Dog {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} barks`; }
  static create(name) { return new Dog(name); }
}
```

is close to:

```js
function Dog(name) { this.name = name; }
Dog.prototype.speak = function () { return `${this.name} barks`; };
Dog.create = function (name) { return new Dog(name); };
```

Methods land on `Dog.prototype`. Static methods land on `Dog` itself. `extends` sets up the prototype link and `super` calls the parent. So far, pure sugar.

## What is not sugar

**Classes are not hoisted usably.** They are hoisted but sit in the temporal dead zone, so `new Dog()` before the declaration throws a `ReferenceError` rather than working.

**Class bodies are always strict mode.** No sloppy-mode fallback, ever.

**Constructors cannot be called without `new`.** `Dog()` throws a `TypeError`. Function constructors silently ran and polluted globals instead.

**Methods are non-enumerable.** `Object.keys(dog)` and `for...in` skip prototype methods, unlike hand-assigned ones.

**`super` uses `[[HomeObject]]`.** Each method stores a hidden reference to the object it was defined on, which is how `super.method()` resolves. You cannot replicate this by hand — extracting a method that uses `super` and reattaching it elsewhere breaks it.

**Private fields are genuinely private.** `#count` is not a property at all; it is stored in a separate internal slot and is invisible to `Object.keys`, `getOwnPropertyNames`, `JSON.stringify`, proxies and the debugger's normal property view. No convention or closure trick reproduces it exactly.

```js
class Counter {
  #count = 0;
  increment() { return ++this.#count; }
  static isCounter(obj) { return #count in obj; }
}

const c = new Counter();
c.#count;             // SyntaxError at parse time
Object.keys(c);       // []
```

**Derived-class `this` does not exist before `super()`.**

```js
class Puppy extends Dog {
  constructor(name) {
    // this.age = 1;  // ReferenceError
    super(name);
    this.age = 1;
  }
}
```

In a derived class, `this` is created *by* the parent constructor. This is not a lint rule; it is how the class construction protocol works.

**`extends` can subclass built-ins correctly.**

```js
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}
```

ES5-era `Error` subclassing was broken — `instanceof` failed and the stack was wrong — because the built-in constructor ignored the `this` it was given. Classes fixed this. Custom error hierarchies are one of the strongest everyday cases for `class` ([[05.9 - Error Handling and Custom Errors]]).

## Fields, and the method-vs-field decision

```js
class Widget {
  handleClick = () => { this.render(); };  // instance field, per instance
  render() {}                              // prototype method, shared
  static registry = new Map();             // static field
  static { Widget.registry.set("init", true); }  // static init block
}
```

Instance fields are assigned in the constructor, in declaration order, before the constructor body runs (and after `super()` in a derived class). So a field arrow is bound per instance and costs one allocation per instance; a prototype method is shared but has dynamic `this` ([[02.7 - this in JavaScript]]).

Field initializers cannot see later fields:

```js
class A {
  a = this.b;  // undefined — b not yet initialized
  b = 1;
}
```

## Getters, setters and accessor semantics

```js
class Temperature {
  #celsius = 0;

  get fahrenheit() { return this.#celsius * 9 / 5 + 32; }
  set fahrenheit(v) { this.#celsius = (v - 32) * 5 / 9; }
}
```

These are accessor properties on the prototype, so all instances share them and each reads the instance's own private field. This is the clean case for classes: encapsulated state with a computed public surface.

## When to use which

| Use case | Choice |
| --- | --- |
| Custom errors | `class extends Error` |
| Domain models with real hierarchy | `class` |
| Many instances where memory matters | `class` (shared prototype methods) |
| Stateful utilities, stores, clients | factory + closures |
| React components | function components |
| Web Components | `class extends HTMLElement` (required) |
| Something with one instance | plain object or module |

## How senior engineers actually use this

**They use `class` where the platform requires it or the domain is genuinely hierarchical.** Web Components, custom errors, and library base classes. Everything else in modern frontend code is functions and closures.

**They avoid inheritance depth even when using classes.** One level of `extends` is fine. Three levels means a change in the base has unpredictable reach, and JavaScript's lack of static typing on `super` calls makes that hard to audit.

**They use private fields for real encapsulation in libraries.** When you ship a package, `#` fields prevent consumers from depending on internals, which is what lets you refactor without a major version bump. TypeScript's `private` is compile-time only and does not do this.

**They know classes do not fix `this`.** Extracting a prototype method still loses binding. Field arrows or explicit binding are still required for callbacks.

## Common pitfalls

- Using `this` before `super()` in a derived constructor.
- Extracting a method and passing it as a callback, losing `this`.
- Assuming class declarations hoist like function declarations.
- Expecting `JSON.stringify` to include private fields or getters — it includes neither. Implement `toJSON()` when serialization matters.
- Defining a field arrow for every method in a component rendered thousands of times.
- Using TypeScript's `private` and assuming runtime privacy.

## Interview angle

"Are classes just syntactic sugar?" is a trap question with a nuanced answer: mostly yes for method placement and prototype linking, but no for TDZ behavior, forced strict mode, `new` enforcement, non-enumerable methods, `super`'s `[[HomeObject]]`, private fields, and correct built-in subclassing. Naming three or four of those concretely is what distinguishes a real answer from the memorized one-liner.
