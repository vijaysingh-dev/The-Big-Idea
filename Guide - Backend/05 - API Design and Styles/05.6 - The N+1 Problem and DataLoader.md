# The N+1 Problem and DataLoader

#backend #api-design #graphql #performance

> **In one line:** Twenty sibling resolvers each fetching one row become one query for twenty rows, and the trick that makes it possible is that GraphQL starts every sibling before awaiting any of them.

---

## The Idea

```graphql
query {
  documents(first: 20) {     # 1 query
    title
    author { name }          # 20 queries
    source { name }          # 20 queries
  }
}
```

**41 database round trips for one request.**

Each is fast — 2ms — so the total is 82ms of pure latency, none of it doing useful work beyond the first three queries. At 100 documents it is 201 queries. **The cost is linear in result size, so your API gets slower exactly as your data grows.**

⚠️ **This is not a GraphQL bug.** It is inherent to the execution algorithm ([[05.5 - How GraphQL Execution Works]]) — each list item resolves its children independently, and no resolver knows its siblings exist.

**It is also not unique to GraphQL.** Any ORM does this the moment you loop over a result set and touch a relationship. GraphQL just makes it happen by default, on the client's request, without anyone writing the loop.

## DataLoader

```python
async def batch_load_users(user_ids: list[str]) -> list[User | None]:
    rows = await db.fetch("SELECT * FROM users WHERE id = ANY($1)", user_ids)
    by_id = {r["id"]: User(**r) for r in rows}
    return [by_id.get(uid) for uid in user_ids]      # order must match input
```

```python
user = await loader.load(document.author_id)         # in twenty separate resolvers
```

Twenty `load()` calls become one `batch_load_users` call with twenty IDs.

### Why it works

```python
class DataLoader:
    def load(self, key) -> Awaitable:
        if key in self._cache:
            return self._cache[key]

        future = asyncio.get_running_loop().create_future()
        self._cache[key] = future
        self._queue.append((key, future))

        if not self._scheduled:
            self._scheduled = True
            asyncio.get_running_loop().call_soon(self._schedule_dispatch)

        return future

    async def _dispatch(self):
        self._scheduled = False
        queue, self._queue = self._queue, []
        for i in range(0, len(queue), self.max_batch_size):
            chunk = queue[i:i + self.max_batch_size]
            values = await self.batch_fn([k for k, _ in chunk])
            for (_, fut), value in zip(chunk, values):
                if not fut.done():
                    fut.set_result(value)
```

💡 **The mechanism is `call_soon`.** It schedules dispatch for the *next* event loop iteration, so every sibling resolver calling `load()` during the current iteration lands in the same batch. **This works precisely because GraphQL starts all siblings before awaiting any** — without that, the queue would only ever hold one key.

| Mechanism | Effect |
|---|---|
| **Batching** | N calls in one tick → 1 query |
| **Caching** | The same key twice → 1 query, both get the result |

The cache also deduplicates *within* a batch: twenty documents by one author produce one ID, not twenty.

### The three rules of a batch function

⚠️ **Get these wrong and DataLoader silently returns wrong data.**

1. **Return a list the same length as the input**
2. **Return results in the same order as the input keys** — `WHERE id = ANY($1)` does *not* guarantee order
3. **Return `None` for missing keys** — never skip them, or every subsequent result shifts

```python
# WRONG — misaligned results, and no error
async def bad(ids):
    return await db.fetch("SELECT * FROM users WHERE id = ANY($1)", ids)
```

💡 **This is the most dangerous bug in this note, because it produces *plausible* wrong answers** — user A sees user B's data — with no error at all. **Write a test that requests keys where some do not exist.**

## Scoping: Per Request, Always

```python
# CATASTROPHIC
user_loader = DataLoader(batch_load_users)     # module level, shared forever
```

⚠️ **A module-level DataLoader caches across requests and across users.** User A's data is served to user B. **This is a data breach and one of the most common GraphQL mistakes.**

```python
async def get_context(request: Request) -> Context:
    return Context(
        user=request.state.user,
        loaders=Loaders(
            user=DataLoader(batch_load_users),
            source=DataLoader(batch_load_sources),
        ),
    )
```

**New loaders per request. No exceptions.**

💡 **Request-scoped caching is a feature, not a limitation.** It guarantees consistency within a response — two fields resolving the same user see identical data even if it changed mid-request. Cross-request caching belongs in Redis with explicit invalidation ([[07.2 - Cache Strategies and Invalidation]]).

```python
async def test_loaders_are_per_request():
    assert (await get_context(r1)).loaders.user is not (await get_context(r2)).loaders.user
```

## Beyond Simple Lookups

### One-to-many

```python
async def batch_load_annotations(document_ids: list[str]) -> list[list[Annotation]]:
    rows = await db.fetch(
        "SELECT * FROM annotations WHERE document_id = ANY($1) ORDER BY document_id, created_at",
        document_ids,
    )
    grouped = defaultdict(list)
    for r in rows:
        grouped[r["document_id"]].append(Annotation(**r))
    return [grouped[doc_id] for doc_id in document_ids]     # empty list, not None
```

**Missing keys get `[]`, not `None`.** An empty relationship is not an absent one.

### Paginated one-to-many — the hard case

```graphql
documents { annotations(first: 5) { ... } }
```

You cannot `LIMIT 5` across all documents — that returns 5 total, not 5 per document.

```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY document_id ORDER BY created_at DESC) AS rn
    FROM annotations WHERE document_id = ANY($1)
) t WHERE rn <= $2;
```

⚠️ **A window function over many partitions is not cheap.** Alternatives are `LATERAL` joins (often faster in Postgres) or accepting N queries. **Measure both** — the answer depends on parent count and pagination depth.

💡 **This is the point where many teams decide deeply paginated nested collections are not worth supporting.** That is a legitimate decision, and stating it in your schema documentation beats shipping something that falls over at scale.

### Composite keys

```python
loader.load(("doc_42", "user_7"))     # keys must be hashable
```

Tuples work, dicts do not. Ensure the key type is stable — `{"a":1,"b":2}` and `{"b":2,"a":1}` must produce the same key.

## What DataLoader Does Not Fix

⚠️ **Batching reduces round trips. It does not reduce work.**

```graphql
query { documents(first: 100) { annotations(first: 100) { author { name } } } }
```

With perfect batching: 3 queries. But the third fetches up to 10,000 authors, and the response serialises 10,000 nested objects.

| Remaining problem | Fix |
|---|---|
| Huge batches | `max_batch_size`, plus complexity limits |
| Deep nesting multiplying result size | Depth and complexity limits ([[05.8 - GraphQL Security and Limits]]) |
| Serialisation cost | Response size limits |
| Memory holding 10,000 objects | Same |

💡 **DataLoader is necessary and not sufficient.** A GraphQL server with perfect batching and no cost limits can still be taken down by one query. **The two must be deployed together.**

## In Production

### Detecting N+1

```python
async def test_document_list_is_batched(graphql_client, query_counter):
    await graphql_client.execute(DOCUMENT_LIST_QUERY)
    assert query_counter.count <= 4, f"N+1 detected: {query_counter.queries}"
```

💡 **A query-count assertion in your test suite is the single most effective defence against N+1 regressions.** Someone adds a field with a naive resolver, the count jumps from 4 to 44, and CI fails. Without it, the regression ships and appears as gradual latency nobody can attribute.

```python
graphql_db_queries_per_request.observe(counter.count)
```

**Alert when p99 exceeds a threshold** — a jump means a new resolver is not using a loader.

### Batch size distribution

```python
dataloader_batch_size.labels(loader="user").observe(len(keys))
```

| Distribution | Meaning |
|---|---|
| **Mostly 1** | **Batching is not working** — misscoped loaders, or sequential awaits |
| Healthy spread up to 100 | Working correctly |
| Frequently at `max_batch_size` | Clients requesting very large result sets. Add cost limits |

⚠️ **Batch size of consistently 1 is the classic symptom of awaiting inside a loop:**

```python
for doc in documents:
    author = await loader.load(doc.author_id)         # defeats batching

authors = await asyncio.gather(*[loader.load(d.author_id) for d in documents])   # works
```

**This matters in your non-GraphQL code too.** GraphQL's engine does the `gather` for you; hand-written code must do it explicitly.

### Loaders outside GraphQL

💡 **DataLoader is a general batching primitive, not a GraphQL concept.** Use it anywhere you have a list and need related data — it is a better default than manually collecting IDs, because it composes: three code paths can each `load()` and still share one query.

### Errors in a batch

```python
async def batch_load(ids):
    results = []
    for i in ids:
        try:
            results.append(await fetch_one(i))
        except NotFound as e:
            results.append(e)         # DataLoader raises it for that key only
    return results
```

**One failing key nulls one field rather than the whole response** — which matters given null propagation ([[05.5 - How GraphQL Execution Works]]).

## Codebase

**Repo:** `graphql/dataloader`, `syrusakbary/aiodataloader`, `saleor/saleor`

**Question to answer:** In the original DataLoader, what schedules the batch dispatch, and why does the implementation care so much about *when* in the event loop it runs? Then: how does Saleor structure dozens of loaders without them becoming unmanageable?

**Read, in order:**

1. `graphql/dataloader/src/index.js` — **the original, under 400 lines.** Read `enqueuePostPromiseJob` and its comments. **The scheduling is the entire trick**, and the comments explain why `process.nextTick` versus `setTimeout` matters
2. `aiodataloader/aiodataloader/__init__.py` — the Python port. Compare `call_soon` with the JS scheduling. **Same idea, different event loop**
3. `saleor/saleor/graphql/core/dataloaders.py` — the base class and request scoping
4. `saleor/saleor/graphql/product/dataloaders/products.py` — **a real, large set of loaders.** Note the naming (`ProductByIdLoader`, `ProductVariantsByProductIdLoader`) and how loaders compose by calling other loaders
5. `strawberry/dataloader.py` — the built-in implementation, likely what you would actually use

💡 The Saleor naming convention is worth adopting wholesale: **`<Thing>By<Key>Loader`.** With forty loaders in a schema, a systematic name is the difference between finding the right one and writing a duplicate.

**Size:** 1–2 sessions.

**Part 1 — Build it.** Batching, caching, `max_batch_size`, error propagation, `prime`/`clear`.

**Test the scheduling directly:** assert twenty `load()` calls in one event loop iteration produce exactly one batch call with twenty keys.

Then break the scheduling — dispatch immediately instead of via `call_soon` — and **show batch size collapsing to 1.**

**Part 2 — The alignment bug.** Write the *wrong* batch function that returns rows in database order without reindexing.

Request five keys where two do not exist. **Confirm the results are silently misaligned** — the resolver for key 3 receives key 5's data.

Then write the test that catches it and fix the implementation. **This is the most important test in the drill, because the bug produces no error.**

**Part 3 — Prove request scoping.** Wire loaders into your engine's context.

**The breach test:** user A's request loads document 42; user B's request loads document 42; assert they hit the database twice, not once.

Then deliberately make the loader module-level and **confirm the test fails.** Seeing your own test catch a cross-user data leak is the point.

**Part 4 — Fix the N+1 from drill 5.4.** The same 20-document query that produced 41 queries.

**It should now produce 3.** Chart query count against result size for both — naive linear, batched flat.

Then scale to 1,000 documents and confirm the batched version is still 3 queries.

**Part 5 — Paginated nested collections.** Implement `documents { annotations(first: 5) }` three ways: window function, `LATERAL`, and N queries.

Benchmark at 10, 100 and 1,000 parents. **Report which wins where, and at what parent count you would refuse to support the query.**

**Part 6 — CI regression check.** Query-counting instrumentation plus assertions in every GraphQL test.

**Simulate the regression:** add a field with a naive resolver. **Confirm CI fails with a message naming the offending field.**

Then add production metrics — queries per request, batch size distribution — and build the dashboard panel.

**Part 7 — Batching is not enough.** 100 documents × 100 annotations × author, with perfect batching.

Measure query count (3), rows fetched (10,000+), response size, serialisation time and memory.

**Write in `README.md` why three queries can still be a problem**, and what limits you need. This sets up [[05.8 - GraphQL Security and Limits]] and it is the point most tutorials never reach.

**Done when:**
- Twenty `load()` calls produce exactly one batch, and breaking scheduling collapses it
- The alignment test catches silently misaligned results
- The scoping test catches a cross-user data leak
- Query count is flat at 3 regardless of result size
- You know which paginated-nested strategy wins at which scale
- CI fails on a deliberately introduced N+1
- You can articulate why perfect batching is still not sufficient
