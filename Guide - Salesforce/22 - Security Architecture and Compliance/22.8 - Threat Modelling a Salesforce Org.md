# Threat Modelling a Salesforce Org

## The point

A security checklist tells you whether you did the standard things. **A threat model tells you what an attacker would actually do.**

The difference matters because the standard things are frequently done while the actual exposure sits somewhere nobody looked — a guest user profile, an integration user with System Administrator, or an `@AuraEnabled` method that trusts a record Id.

Four questions, worked in order:

```
1. What are we protecting?
2. Who would want it, and what access do they have?
3. How would they get it?
4. What stops them, and does it work?
```

## What is worth protecting

Not everything is equally sensitive, and treating it that way produces controls nobody follows.

**For Northwind:**

```
Customer contact data          personal data, regulatory exposure
Warranty claim amounts         financial, competitively sensitive
Service contract pricing       commercially sensitive
Machine serial numbers         low value alone, identifies a customer with other data
Fault descriptions             free text — may contain anything
Integration credentials        the keys to the ERP
The org's configuration        an attacker who can change automation controls everything
```

**The last line is the one most models miss.** An attacker who can deactivate a validation rule or add a flow does not need to exfiltrate data — they can make the system do it.

## Who the actors are

The realistic list, which is broader than "hackers".

**External, unauthenticated.** Anyone on the internet reaching a public Experience Cloud page or an unauthenticated endpoint.

**External, authenticated.** A portal user — a partner engineer, a customer contact.

**Internal, low privilege.** A support agent, a sales rep.

**Internal, high privilege.** An administrator, a developer with production access.

**Integration users.** Non-human, frequently over-privileged, and rarely audited.

**Departing employees.** Authorized until the moment they are not, and the most common source of data exfiltration.

**Compromised accounts.** Any of the above, with an attacker behind them.

**Third-party packages.** Code running in your org that you did not write and cannot read.

**The insider cases dominate the realistic risk.** Salesforce's own infrastructure is not the weak point; the org's configuration and the people with access to it are.

## Working the attack paths

For each actor, what they could reach and how.

### The guest user

**The highest-risk surface**, because the actor is everyone.

```
Can reach:  every object the guest profile grants
            every @AuraEnabled class the guest profile grants
            every public Experience Cloud page
            every unauthenticated Site or Visualforce page
```

**The attack:** call an `@AuraEnabled` method directly, with a record Id the UI never exposes.

```java
@AuraEnabled(cacheable=true)
public static Warranty_Claim__c getClaim(Id claimId) {
    // the component passes an Id from its own context; the attacker passes any Id
    return [SELECT Id, Claim_Amount__c FROM Warranty_Claim__c WHERE Id = :claimId];
}
```

No sharing keyword, no `USER_MODE`, no entitlement check. That is a full enumeration of every claim in the org, from an unauthenticated browser.

**The controls:**

```
[ ] Guest profile object permissions reviewed field by field
[ ] Every guest-reachable class declares `with sharing`
[ ] WITH USER_MODE on every query
[ ] Record Ids from the client verified against entitlement
[ ] Not-found returned rather than not-permitted
[ ] Guest user has no role
[ ] Sharing rules for guest grant Read only
```

**Testing it means loading the site logged out** and calling the endpoints directly, not reviewing the configuration. See [[17.9 - Experience Cloud Basics]].

### The portal user

```
Can reach:  their account's records, via sharing sets
            every @AuraEnabled class their profile grants
            the API, with their credentials
```

**The attack:** the same Id substitution, from an authenticated session. A partner engineer requests another partner's claim.

**The control that matters:** sharing sets scoped to the account relationship, plus entitlement verification in Apex where the sharing model is not sufficient.

**The specific failure:** a component that filters by account in JavaScript and passes an unfiltered query to Apex. The client-side filter is not a control.

### The internal low-privilege user

```
Can reach:  their sharing-visible records
            reports and list views
            data export
            the API, with their credentials
```

**The attack:** export. A support agent runs a report of every contact they can see and exports it.

**That is authorized behaviour**, which is what makes it hard. The control is not prevention but detection:

```
Event Monitoring        ReportExport, ContentTransfer
Transaction Security    block exports above a row threshold
```

Without Shield, this is largely undetectable — which is worth stating plainly rather than assuming a control exists.

**The secondary attack:** field-level security assumed but not enforced. A field hidden on the layout is still readable through the API:

```bash
sf data query --query "SELECT Id, Internal_Margin__c FROM Warranty_Claim__c" --target-org production
```

**Layout visibility is not security.** Only field-level security is. See [[03.6 - Field Level Security]].

### The integration user

**The most over-privileged actor in most orgs**, and the least audited.

```
Frequently:  System Administrator profile
             Modify All Data
             no IP restrictions
             credentials shared across several integrations
             a password nobody has rotated
```

**The attack:** the credentials are found — in a configuration file, a repository, a middleware log, a support ticket — and they carry full access.

**The controls:**

```
[ ] One integration user per integration
[ ] A permission set granting exactly the objects and fields used
[ ] View All / Modify All per object, never org-wide
[ ] JWT rather than a stored password
[ ] No role, to avoid ownership skew and hierarchy access
[ ] Connected app scoped to the minimum OAuth scopes
[ ] Login history audited
```

**Scoping the integration user properly is usually the highest-value security improvement available in an org**, because it is so consistently skipped. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

### The administrator

```
Can reach:  everything
```

**The attack:** there is no technical control against an administrator. The controls are procedural.

```
[ ] Few administrators, named and reviewed
[ ] MFA enforced
[ ] SetupAuditTrail monitored, archived beyond six months
[ ] Login IP ranges applied where practical
[ ] Delegated administration for routine tasks, rather than full access
[ ] Production changes reviewed
```

**`SetupAuditTrail` is the only record of what an administrator did**, and six months of retention means archiving is necessary for anything longer. See [[22.3 - Field Audit Trail and Data Retention]].

### The departing employee

**The most common real exfiltration case.**

```
The window:  from the moment they decide to leave until access is revoked
The method:  report export, data loader, API access, file download
```

**The controls:**

```
[ ] Offboarding revokes OAuth tokens, not just deactivates the user
[ ] Event Monitoring alerts on export volume
[ ] Connected app access reviewed on departure
[ ] Refresh tokens revoked
```

**Deactivating a user does not immediately invalidate every issued token.** Revocation is a separate action, and it is the step that gets missed:

```
POST /services/oauth2/revoke
token={refresh_token}
```

### The compromised account

```
The method:  phishing, credential reuse, a compromised device
```

**MFA is the control**, and it is free. An org without enforced MFA has no answer to this actor.

**Session security** limits the blast radius — timeout, IP locking, high-assurance sessions for sensitive operations. See [[03.14 - Login Policies, MFA and Session Security]].

### The third-party package

```
Runs:  in your org, with the permissions you granted
Sees:  whatever its code queries
```

**You cannot read its Apex.** The controls are procedural: reviewing what it requests, checking whether it passed a security review, and limiting who can install packages.

**Its consumption of governor limits is visible**, which is at least some signal:

```
LIMIT_USAGE_FOR_NS|vendor_ns|Number of SOQL queries: 62 out of 100
```

## Structuring the analysis

**STRIDE**, applied to Salesforce, gives a systematic pass:

```
Spoofing            can someone impersonate a user or an integration?
                    → MFA, JWT, connected app policies

Tampering           can someone alter data or configuration they should not?
                    → sharing, field-level security, SetupAuditTrail

Repudiation         can someone deny having done something?
                    → field history, Event Monitoring, custom logging

Information         can someone read what they should not?
disclosure          → sharing, FLS, guest user review, USER_MODE

Denial of service   can someone exhaust the org's capacity?
                    → API limits, async allocation, concurrency limits

Elevation of        can someone gain more access than granted?
privilege           → without sharing, permission set assignment,
                      @AuraEnabled entry points
```

**Denial of service is underappreciated on Salesforce.** An integration user with valid credentials can exhaust the daily API allocation, and every other integration in the org stops. That is a realistic insider or compromised-account scenario with no authentication failure involved. See [[16.6 - Concurrency and Long Running Requests]].

## Prioritizing

Not every finding is worth fixing, and treating them equally means the important ones wait behind the trivial.

```
Likelihood × Impact, with a bias toward exposure surface
```

**High priority, nearly always:**

```
Guest-reachable code without sharing enforcement
Integration users with System Administrator
No MFA
Secrets in custom settings or metadata
@AuraEnabled methods trusting client-supplied Ids
```

**Lower priority than they appear:**

```
Encryption at rest, absent a specific requirement
Sandbox controls, if sandbox data is already masked
Debug log retention
```

**The first list is free to fix and produces most of the improvement.** The second costs money and produces less.

## Doing this as an exercise

A workable half-day session.

**1. List the assets**, with sensitivity. Half an hour, and it produces disagreement worth having.

**2. List the actors and their access.** Query it rather than assuming:

```sql
SELECT Name, Profile.Name, UserType, IsActive FROM User WHERE IsActive = true
SELECT Name, PermissionsModifyAllData, PermissionsViewAllData FROM Profile
SELECT Name, PermissionsModifyAllData, PermissionsViewAllData FROM PermissionSet
```

**Anyone with `ModifyAllData` is an administrator**, whatever their profile is called, and the list is frequently longer than expected.

**3. Walk each actor to each asset.** Can they reach it? How? What stops them?

**4. Test the assumptions.** Load the public site logged out. Call an `@AuraEnabled` method with an Id the user should not see. Query a hidden field through the API. **Assumptions that have not been tested are not controls.**

**5. Record the findings**, with an owner and a priority.

**6. Revisit** after significant changes — a new Experience Cloud site, a new integration, a new package.

## A findings template

```
Finding:      Guest-reachable ClaimSearchController has no sharing declaration
Actor:        Unauthenticated internet user
Asset:        All warranty claims, including amounts
Path:         Call the @AuraEnabled method directly with any record Id
Likelihood:   High — the endpoint is discoverable from the page source
Impact:       High — full enumeration of financial data
Control:      None currently
Remediation:  with sharing, WITH USER_MODE, entitlement check on the account
Owner:        Platform team
Priority:     Immediate
```

**Naming the path** is what makes a finding actionable. "The class is insecure" produces argument; "call this method with any Id and receive every claim" produces a fix.

## Section 22 in one paragraph

Most Salesforce security failures are not encryption failures — they are a missing sharing keyword on a guest-reachable class, an integration user with System Administrator, a field hidden on a layout but readable through the API, or an `@AuraEnabled` method that trusts a record Id from the client. Shield addresses a narrow set of requirements — customer-managed keys, forensic visibility, and long-horizon audit history — and buying it does not make an insecure org secure, while Platform Encryption in particular buys real functional restrictions that need field-by-field analysis before enablement. The controls that matter most are free: enforced MFA, scoped integration users, `with sharing` and `WITH USER_MODE` on every reachable class, `stripInaccessible` on the write path, Named Credentials rather than secrets in queryable data, and masked sandbox data. Compliance is a set of obligations rather than a feature, and the developer's part is building systems where erasure, access requests, and retention can actually be satisfied — including publishing an erasure event so downstream systems act, and documenting what erasure cannot reach. And a threat model is worth more than a checklist, because it asks what an attacker would actually do rather than whether the standard boxes are ticked.
