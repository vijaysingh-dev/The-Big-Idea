# Inference Internals

## What It Is

Inference internals covers everything that happens *inside* the GPU when you run an LLM — how computation is scheduled, how memory is managed, how parallelism is exploited, and what engineering choices make the difference between 10 tokens/sec and 100 tokens/sec on the same hardware.

This section connects six tightly coupled topics:
1. **KV cache lifecycle** — how it's allocated, filled, and evicted
2. **MQA/GQA** — attention head grouping to shrink the KV cache
3. **Flash Attention** — rewriting attention computation for GPU memory hierarchy
4. **Continuous batching** — the scheduling innovation that made production LLM serving viable
5. **vLLM and TGI** — the two dominant serving engines and what differentiates them
6. **Quantization** — trading precision for throughput/memory, with real tradeoff numbers

---

## Why It Matters

- **Baseten, Together AI, Fireworks AI** — all in your target list — are fundamentally inference infrastructure companies. Explaining KV cache management, PagedAttention, and continuous batching at implementation depth is table stakes for interviews there.
- Self-hosting LLMs is increasingly viable for cost or privacy reasons. Knowing when vLLM outperforms TGI (and why) determines whether you pick the right tool.
- Quantization decisions (INT8 vs INT4 vs GPTQ vs AWQ) directly affect model quality in your RAG system — wrong choice and your retrieval quality degrades invisibly.
- Flash Attention is now used in almost every production model. Knowing what problem it solves explains why attention on long contexts became practical.

## Prefill vs Decode — The Two Phases

All LLM inference has two distinct phases with different computational characters:

### Prefill Phase (Prompt Processing)

Process all input tokens in parallel. Compute K, V matrices for every prompt token across all layers. Fill the KV cache.

- **Compute-bound**: Can use matrix multiplication parallelism across all tokens simultaneously
- **Latency**: Proportional to prompt length × model size
- **Output**: KV cache is now populated; first output token generated

### Decode Phase (Token Generation)

Generate output tokens one at a time, each requiring a forward pass.

- **Memory-bandwidth-bound**: Each step reads the full KV cache + model weights. GPU cores sit idle waiting for memory reads.
- **Latency**: Each token takes roughly the same time (constant per token)
- **Throughput bottleneck**: The slow path in generation

```
Timeline:
[==Prefill==(parallel, fast)==][T1][T2][T3][T4][T5]...[Tn]
                                 ←──── Decode (sequential) ────→

TTFT (Time To First Token) = Prefill latency
Generation throughput = tokens per second during decode
```

Understanding this split explains why:
- Long prompts slow TTFT but don't slow per-token throughput
- Short prompts with long outputs are memory-bandwidth-bound
- Prefix caching reduces prefill cost for repeated prompts

## KV Cache — Full Lifecycle

From [[13.1 - Token Economics KV Cache Prefix Caching]] we know the cache exists. Here's the full lifecycle in a serving system:

### Allocation

When a request arrives, the serving engine must allocate KV cache memory for the *maximum possible sequence length* (prompt + max_new_tokens). This is done upfront before generation begins.

**The problem**: You don't know how long the output will be. If you allocate for max_new_tokens=2048 but the model outputs 50 tokens and stops, you've wasted memory. If you allocate less and the sequence grows longer, you need to reallocate — expensive.

### Naive vs PagedAttention

**Naive approach** (used in early frameworks): Allocate a contiguous block of GPU memory for each request's full KV cache. Problems:
- Memory fragmentation: gaps between blocks can't be used
- Maximum batch size is limited by the largest single-request allocation
- Under-utilization: 40-60% of allocated KV cache often wasted on padding and worst-case allocation

**PagedAttention** (vLLM's innovation): KV cache stored in non-contiguous fixed-size blocks (pages), like virtual memory in an OS.

```
Traditional:
  Request 1: [K1V1|K2V2|K3V3|K4V4|....EMPTY....EMPTY....EMPTY]  ← 50% wasted
  Request 2: [K1V1|K2V2|....EMPTY....EMPTY....EMPTY....EMPTY]    ← 75% wasted

PagedAttention:
  Physical blocks (16 tokens each):
  Block 0: [K1V1|K2V2|K3V3|...|K16V16]  → assigned to Request 1
  Block 1: [K1V1|K2V2|K3V3|...|K16V16]  → assigned to Request 1
  Block 2: [K1V1|K2V2|...|K8V8|EMPTY×8] → assigned to Request 1 (partially filled)
  Block 3: [K1V1|K2V2|...|K4V4|EMPTY×12]→ assigned to Request 2

  Block table maps logical token positions to physical blocks.
  No wasted memory between requests. Fragmentation only within last block.
```

PagedAttention reduces memory waste from ~40% to ~4% (waste only within the last block per sequence). This directly translates to supporting 2-3× more concurrent requests on the same GPU.

## MQA and GQA — Shrinking the KV Cache

From [[13.1 - Token Economics KV Cache Prefix Caching]] we have the memory formula. Here's how MQA and GQA work mechanically.

### Standard MHA (Multi-Head Attention)

Each of the H attention heads has its own independent Q, K, V projections. During inference, K and V for all heads are cached.

```
H=32 heads, d_head=128, float16:
KV cache per token per layer = 2 × 32 × 128 × 2 bytes = 16,384 bytes = 16 KB
```

### MQA (Multi-Query Attention)

All H query heads share a single K and V head. Q is still projected to H heads, but K and V are projected to just 1 head, then *broadcast* to all query heads during attention computation.

```python
# MQA implementation sketch
class MultiQueryAttention(nn.Module):
    def __init__(self, d_model, n_heads):
        self.n_heads = n_heads
        self.d_head = d_model // n_heads

        self.q_proj = nn.Linear(d_model, d_model)       # H heads
        self.k_proj = nn.Linear(d_model, self.d_head)   # 1 head — KEY DIFFERENCE
        self.v_proj = nn.Linear(d_model, self.d_head)   # 1 head — KEY DIFFERENCE
        self.o_proj = nn.Linear(d_model, d_model)

    def forward(self, x, kv_cache=None):
        B, T, C = x.shape
        q = self.q_proj(x).view(B, T, self.n_heads, self.d_head)  # H query heads
        k = self.k_proj(x).view(B, T, 1, self.d_head)             # 1 K head
        v = self.v_proj(x).view(B, T, 1, self.d_head)             # 1 V head

        # K and V broadcast to all query heads
        k = k.expand(-1, -1, self.n_heads, -1)
        v = v.expand(-1, -1, self.n_heads, -1)

        # Standard attention with shared K, V
        ...
```

**KV cache reduction**: H× smaller than MHA. For H=32: 32× smaller KV cache.
**Quality tradeoff**: ~2-5% quality degradation on benchmarks. Used in: Falcon, PaLM.

### GQA (Grouped Query Attention)

Compromise between MHA and MQA. Divide H query heads into G groups; each group shares one K, V head.

```
H=32 query heads, G=8 KV groups:
  Group 0: query heads 0-3  share K0, V0
  Group 1: query heads 4-7  share K1, V1
  ...
  Group 7: query heads 28-31 share K7, V7

KV cache = 8 heads (not 32) → 4× reduction with less quality loss than MQA
```

Used in: Llama 3 (G=8), Mistral (G=8), Gemma 2 (G=4). The modern default.

```python
# GQA: how attention is computed
# n_kv_heads = G (number of KV groups)
# n_heads = H (number of query heads)
# Each KV head serves n_heads // n_kv_heads query heads

def repeat_kv(x, n_rep):
    """Expand KV heads to match query heads by repetition."""
    if n_rep == 1:
        return x
    B, T, n_kv_heads, d_head = x.shape
    return x[:, :, :, None, :].expand(B, T, n_kv_heads, n_rep, d_head) \
                               .reshape(B, T, n_kv_heads * n_rep, d_head)

# In forward pass:
k = repeat_kv(k, n_heads // n_kv_heads)  # expand 8 → 32 heads
v = repeat_kv(v, n_heads // n_kv_heads)
```

## Flash Attention — What Problem It Solves

### The GPU Memory Hierarchy Problem

GPUs have two relevant memory tiers:
- **SRAM (on-chip)**: ~20MB on A100. Extremely fast (~19 TB/s bandwidth).
- **HBM (off-chip)**: 40–80GB on A100. Slower (~2 TB/s bandwidth). This is "GPU memory."

Standard attention computation:

```
Input: Q, K, V matrices in HBM (40GB memory)
Standard attention:

Step 1: Load Q, K from HBM → SRAM
Step 2: Compute S = QK^T in SRAM
Step 3: Write S to HBM              ← SLOW: large matrix back to slow memory
Step 4: Load S from HBM → SRAM
Step 5: Compute P = softmax(S)
Step 6: Write P to HBM              ← SLOW: again
Step 7: Load P, V from HBM → SRAM
Step 8: Compute O = PV
Step 9: Write O to HBM

HBM reads/writes: proportional to sequence_length²
For 32K tokens: S and P matrices are 32K × 32K × 4 bytes = 4GB each
```

The bottleneck is not computation — it's the memory bandwidth of reading/writing those intermediate matrices.

### Flash Attention Solution — Tiling

Instead of materializing the full S and P matrices in HBM, tile the computation so it fits in SRAM:

```
For each tile of Q (fits in SRAM):
  For each tile of K (fits in SRAM):
    Compute partial S = Q_tile @ K_tile^T in SRAM
    Compute online softmax (rescale running max/sum)
    For each tile of V:
      Accumulate O += softmax(S_tile) @ V_tile
  Write only O to HBM (not S or P)
```

**What changes**: S and P are never written to HBM. Only O (the output) is written once.

**HBM reads/writes**: Reduced from O(n²) to O(n) — only Q, K, V, and O are touched, each once.

**Computation**: Identical mathematical result. No approximation.

**Speed**: 2–4× faster for long sequences. 10–20× less memory for intermediate activations.

```python
# Flash Attention via PyTorch (uses CUDA implementation internally)
from torch.nn.functional import scaled_dot_product_attention

# Automatically uses Flash Attention when available
output = scaled_dot_product_attention(
    query, key, value,
    attn_mask=None,
    dropout_p=0.0,
    is_causal=True,   # use causal mask for decoder
)

# Flash Attention 2 (faster, better GPU utilization)
# Available via: pip install flash-attn
from flash_attn import flash_attn_func
output = flash_attn_func(q, k, v, causal=True)
```

**Flash Attention 2 improvements over v1**:
- Better parallelism across sequence length dimension
- Reduced non-matrix multiply operations
- ~2× faster than Flash Attention 1 on A100

**Flash Attention 3**: Specifically optimized for H100 (FP8 support, asynchronous memory operations). Up to 2.6× over FA2.

## Continuous Batching

### The Problem with Static Batching

Naive batch inference: group N requests together, process them as a batch, return all N results when the *slowest* request finishes.

```
Request 1: 500 tokens output  [=====]done
Request 2: 100 tokens output  [=]done                 waiting...
Request 3: 1000 tokens output [==========]done

With static batching:
  Batch {1,2,3} runs until Request 3 finishes
  Requests 4,5,6 wait in queue even though GPU is underutilized after R1,R2 finish
  GPU utilization: ~30% once short requests finish
```

### Continuous Batching (Iteration-Level Scheduling)

At every decode step, the scheduler checks: has any request finished? If yes, immediately insert a waiting request into the next iteration's batch.

```
Step 1: Batch = {R1, R2, R3}   → compute one token for each
Step 2: Batch = {R1, R2, R3}   → compute one token for each
...
Step 100: R2 finishes (100 tokens)
          Immediately add R4 to batch
Step 101: Batch = {R1, R3, R4} → compute one token for each
Step 200: R1 finishes
          Immediately add R5 to batch
...
```

**Result**: GPU is always running a full batch. No idle time waiting for slow requests.

**Throughput improvement**: 2–10× higher throughput vs static batching. This is the primary reason vLLM exists.

## vLLM — Architecture and Design

vLLM (from UC Berkeley, open-source) is the most widely used LLM serving engine. It introduced PagedAttention and continuous batching together.

### Core Architecture

```
Incoming requests → Request queue
                         │
                    Scheduler
                    (decides batch composition each step)
                         │
                    Block Manager
                    (PagedAttention KV cache allocation)
                         │
                    Workers (GPU processes)
                    - Model weights on GPU
                    - KV cache blocks allocated by block manager
                         │
                    Detokenizer → Response stream
```

### Starting vLLM

```python
from vllm import LLM, SamplingParams

# Load model
llm = LLM(
    model="meta-llama/Llama-3.1-8B-Instruct",
    tensor_parallel_size=1,          # number of GPUs for tensor parallelism
    gpu_memory_utilization=0.90,     # use 90% of GPU memory for KV cache
    max_model_len=8192,              # maximum sequence length
    quantization="awq",              # optional quantization
    enforce_eager=False,             # use CUDA graphs for faster decode
)

# Batch inference
prompts = ["Tell me about RAG systems.", "Explain tokenization."]
params = SamplingParams(temperature=0.7, max_tokens=512)
outputs = llm.generate(prompts, params)

for output in outputs:
    print(output.outputs[0].text)
```

### vLLM Key Configuration

```python
llm = LLM(
    model="...",
    tensor_parallel_size=2,     # split model across 2 GPUs (for large models)
    pipeline_parallel_size=1,   # layer pipeline (for very large models)
    gpu_memory_utilization=0.90, # fraction of GPU memory for KV cache blocks

    quantization="awq",          # INT4 quantization
)
```

## TGI — Text Generation Inference

Hugging Face's serving engine. Predates vLLM, different architectural emphasis.

### TGI vs vLLM

| Dimension | vLLM | TGI |
|-----------|------|-----|
| KV cache management | PagedAttention (non-contiguous) | Contiguous blocks |
| Scheduling | Continuous batching | Continuous batching |
| Quantization | AWQ, GPTQ, INT8 | GPTQ, AWQ, INT8, FP8 |
| Speculative decoding | Yes | Yes |
| LoRA serving | Multi-LoRA support | Supported |
| Streaming | Yes (SSE) | Yes (SSE) |
| Model support | Wide (via HuggingFace) | Wide (via HuggingFace) |
| Production maturity | Very high | High |
| HuggingFace integration | Good | Native |
| Memory efficiency | Better (PagedAttention) | Slightly worse |

**When to use TGI**: Deep HuggingFace ecosystem integration, HuggingFace Inference Endpoints.
**When to use vLLM**: Maximum throughput and memory efficiency, multi-LoRA serving, production self-hosting.

## Quantization

Quantization reduces the bit-width of model weights to decrease memory usage and increase throughput, at some quality cost.

### Weight-Only Quantization (Most Common)

Weights are stored in low precision; computation happens in higher precision (dequantize on-the-fly).

#### INT8 (W8A16 — 8-bit weights, 16-bit activations)

```python
# Using bitsandbytes for INT8
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(load_in_8bit=True)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=bnb_config,
    device_map="auto",
)
# Memory: ~8GB vs ~16GB for fp16 (2× reduction)
# Quality: <1% degradation on most benchmarks
```

#### GPTQ (Post-Training Quantization, INT4)

Calibration-based quantization. Uses a calibration dataset to find optimal quantization parameters that minimize activation error.

```python
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "TheBloke/Llama-3-8B-GPTQ",  # pre-quantized GPTQ model
    device_map="auto",
    revision="gptq-4bit-128g-actorder_True",
)
# Memory: ~4.5GB vs 16GB fp16 (3.5× reduction)
# Quality: ~3-5% degradation
```

#### AWQ (Activation-Aware Weight Quantization)

Improves on GPTQ by identifying and protecting salient weights (those that most affect activations). Better quality than GPTQ at same bit-width.

```python
from awq import AutoAWQForCausalLM

# Load pre-quantized AWQ model
model = AutoAWQForCausalLM.from_quantized(
    "Qwen/Qwen2-7B-Instruct-AWQ",
    fuse_layers=True,      # fuse linear layers for faster inference
    trust_remote_code=False,
)
# Memory: ~4GB for 7B model
# Quality: better than GPTQ (AWQ preserves more outlier weights)
```

### Quantization Comparison

| Method | Bit-width | Memory (7B) | Quality loss | Speed | Best for |
|--------|-----------|-------------|-------------|-------|---------|
| fp16 | 16-bit | 14GB | baseline | baseline | Training, max quality |
| INT8 (bitsandbytes) | 8-bit | 7GB | <1% | ~1.1× | High quality, moderate savings |
| GPTQ | 4-bit | 4GB | 3-5% | ~1.5× | Good balance, widely supported |
| AWQ | 4-bit | 3.5GB | 2-3% | ~1.5× | Better quality than GPTQ at 4-bit |
| GGUF Q4_K_M | 4-bit | 4.1GB | 3-4% | ~1.2× | CPU inference (llama.cpp) |

### FP8 (Emerging)

H100 GPUs support FP8 natively. vLLM and TGI support FP8 inference with near-fp16 quality at ~2× throughput.

```python
llm = LLM(model="...", quantization="fp8")
# Only on H100/H200; ~2× throughput vs fp16
```

### Speculative Decoding

Not quantization, but another throughput technique worth knowing:

```python
# Use a small "draft" model to generate token proposals
# Large model verifies multiple tokens in parallel
# If draft tokens accepted: effectively generated in one step

llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    speculative_model="meta-llama/Llama-3.2-1B-Instruct",  # draft model
    num_speculative_tokens=5,   # draft 5 tokens, verify in one pass
)
# Throughput: 2-3× improvement for greedy/low-temperature generation
# Memory: +small model weights
```

## Tensor Parallelism for Multi-GPU

For models larger than a single GPU:

```
70B model (fp16) = 140GB → doesn't fit in one 80GB A100

Tensor Parallel across 2 GPUs:
  Each GPU holds half the model's weight matrices
  Each attention head split across GPUs
  All-reduce communication at each layer boundary

Memory per GPU: 70GB (fits in 80GB A100 with 10GB for KV cache)
```

```python
# vLLM tensor parallel
llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=2,   # split across 2 GPUs
    # Requires: 2× GPUs connected via NVLink (fast) or PCIe (slower)
)
```

**Pipeline parallel** (splitting by layers): Alternative for very large models. Less communication overhead than tensor parallel but requires careful scheduling.

## Revision Anchors

- **Prefill vs decode**: Prefill = process all input tokens in parallel (compute-bound). Decode = generate one token per forward pass (memory-bandwidth-bound). TTFT dominated by prefill; throughput dominated by decode.
- **PagedAttention**: Non-contiguous KV cache blocks (like OS virtual memory). Reduces memory waste from 40% → 4%. Enables 2-3× more concurrent requests on same GPU.
- **GQA**: H query heads share G KV heads (G < H). Llama 3 uses G=8 of H=32 → 4× KV cache reduction vs MHA. Modern default.
- **Flash Attention**: Tiles QK^T computation to fit in SRAM. Avoids writing O(n²) intermediate matrices to slow HBM. Same math, 2-4× faster for long sequences, O(n) instead of O(n²) memory.
- **Continuous batching**: Insert new requests into the batch as existing requests finish — at every decode step. 2-10× throughput vs static batching.
- **AWQ > GPTQ**: Both 4-bit, but AWQ protects activation-salient weights. Better quality at same compression.
- **vLLM default**: PagedAttention + continuous batching + CUDA graphs. Use `enable_prefix_caching=True` for RAG workloads with repeated system prompts.
