# State Normalization

Normalization means storing each entity **once**, keyed by id, and referencing it elsewhere by id. It is the same idea as database normalization, applied to client state.

## The problem

An API returns nested data:

```js
{
  posts: [
    {
      id: 1,
      title: "Hello",
      author: { id: 10, name: "Vijay", avatar: "..." },
      comments: [
        { id: 100, text: "Nice", author: { id: 10, name: "Vijay", avatar: "..." } },
        { id: 101, text: "Thanks", author: { id: 11, name: "Asha" } },
      ],
    },
  ],
}
```

Storing this shape directly creates four problems:

**Duplication.** Vijay appears twice here and will appear in every post and comment he touches. Updating his avatar means finding and updating every copy.

**Deep updates.** Toggling a comment's like requires spreading through posts → comments → the comment ([[06.7 - Immutable Data Patterns]]).

**Broken memoization.** Updating one comment creates new references for the comment array, the post, and the posts array — so every post re-renders, not just the affected one ([[19.2 - React.memo and Memoization Strategy]]).

**O(n) lookups.** Finding a comment by id means scanning nested arrays.

## The normalized shape

```js
{
  posts: {
    byId: {
      1: { id: 1, title: "Hello", author: 10, comments: [100, 101] },
    },
    allIds: [1],
  },
  comments: {
    byId: {
      100: { id: 100, text: "Nice", author: 10 },
      101: { id: 101, text: "Thanks", author: 11 },
    },
    allIds: [100, 101],
  },
  users: {
    byId: {
      10: { id: 10, name: "Vijay", avatar: "..." },
      11: { id: 11, name: "Asha" },
    },
    allIds: [10, 11],
  },
}
```

Four rules:

1. Each entity type gets its own slice
2. Entities are stored in an object keyed by id
3. References between entities are ids, not nested objects
4. Order is kept in an `allIds` array

Now updating a comment touches exactly one object at one level, every other reference is preserved, and lookups are O(1).

`allIds` exists because object key order is unreliable for non-string-like keys and because you often need several orderings (chronological, by score) over the same entities.

## Updating

```js
// Deeply nested — every level on the path is copied
setState(s => ({
  ...s,
  posts: s.posts.map(p =>
    p.id !== postId ? p : {
      ...p,
      comments: p.comments.map(c =>
        c.id !== commentId ? c : { ...c, likes: c.likes + 1 }
      ),
    }
  ),
}));

// Normalized — one level
setState(s => ({
  ...s,
  comments: {
    ...s.comments,
    byId: {
      ...s.comments.byId,
      [commentId]: { ...s.comments.byId[commentId], likes: c.likes + 1 },
    },
  },
}));
```

Both are verbose; the second is verbose at a fixed depth regardless of how deep the conceptual nesting goes. With Immer it collapses to one line ([[20.6 - Immer and Immutable Updates]]):

```js
draft.comments.byId[commentId].likes += 1;
```

## Denormalizing for display

Components need the joined shape, so selectors reassemble it:

```js
const selectPostWithDetails = createSelector(
  [selectPostsById, selectCommentsById, selectUsersById, (_, postId) => postId],
  (posts, comments, users, postId) => {
    const post = posts[postId];
    if (!post) return null;
    return {
      ...post,
      author: users[post.author],
      comments: post.comments.map(id => ({
        ...comments[id],
        author: users[comments[id].author],
      })),
    };
  }
);
```

`createSelector` memoizes, so the join only recomputes when one of the input slices actually changes ([[20.3 - Redux Core Concepts]]).

Note the pattern: **normalize on the way in, denormalize on the way out**. The store holds the canonical shape; selectors produce the view shape.

## createEntityAdapter

RTK generates all of this ([[20.4 - Redux Toolkit]]):

```js
const commentsAdapter = createEntityAdapter({
  sortComparer: (a, b) => b.createdAt - a.createdAt,
});

const commentsSlice = createSlice({
  name: "comments",
  initialState: commentsAdapter.getInitialState({ status: "idle" }),
  reducers: {
    commentAdded: commentsAdapter.addOne,
    commentsReceived: commentsAdapter.setAll,
    commentUpdated: commentsAdapter.updateOne,
    commentRemoved: commentsAdapter.removeOne,
  },
});

export const { selectAll, selectById, selectIds } =
  commentsAdapter.getSelectors(state => state.comments);
```

It maintains `{ ids: [], entities: {} }`, keeps `ids` sorted per the comparer, and provides CRUD reducers and selectors. This is the default for any collection in a Redux application.

## Normalizing incoming data

```js
import { normalize, schema } from "normalizr";

const user = new schema.Entity("users");
const comment = new schema.Entity("comments", { author: user });
const post = new schema.Entity("posts", { author: user, comments: [comment] });

const { entities, result } = normalize(apiResponse, [post]);
// entities: { users: {...}, comments: {...}, posts: {...} }
// result: [1, 2, 3]  — the id order
```

`normalizr` handles arbitrarily nested responses declaratively. For simple shapes, a hand-written transform is fine:

```js
const byId = Object.fromEntries(items.map(i => [i.id, i]));
```

Either way, normalize at the **API boundary**, so nothing downstream ever sees the nested shape ([[24.1 - Building an API Layer]]).

## When not to normalize

**When a query library already handles it.** TanStack Query caches by query key, so the same entity fetched under two keys is stored twice — but the library handles invalidation and refetching, so duplication rarely causes stale-data bugs the way manual caching does. Normalizing on top of it adds complexity for limited benefit ([[24.7 - Caching Stale Time and Invalidation]]).

**For small, flat, or read-only data.** A list of twenty countries in a dropdown does not need normalizing.

**For data displayed once and discarded.** A single detail view fetched fresh each time is fine nested.

The signal that you *should* normalize: the same entity appears in several places and can be edited, or updates cause visibly excessive re-rendering.

## Cost

Normalization trades write simplicity for read complexity. Every read needs a selector to join; every component needs the joined shape.

That trade is worth it when entities are shared and mutable. It is overhead when they are not — which is why "normalize everything" is as wrong as "normalize nothing".

## How senior engineers actually use this

**They normalize entities that are shared and editable**, and leave one-off view data nested.

**They use `createEntityAdapter`** rather than hand-rolling the shape in Redux.

**They normalize at the API boundary**, once, so the transformation is in one testable place.

**They memoize denormalizing selectors**, since an unmemoized join returns a new object on every call and re-renders on every action ([[20.3 - Redux Core Concepts]]).

**They let a query library own server data** and reserve normalization for genuinely shared client state.

## Common pitfalls

- Normalizing everything, including data that is never shared or edited.
- Unmemoized denormalizing selectors, re-rendering on every store change.
- Losing order because it was assumed to follow object key order — keep `allIds`.
- Forgetting to remove ids from `allIds` when deleting an entity, leaving dangling references.
- Normalizing in components instead of at the API boundary.
- Adding normalization on top of a query library that already manages caching.

## Interview angle

"What is state normalization and why do it" wants: store entities once keyed by id, reference by id, keep order in a separate array — giving O(1) lookups, single-place updates, no duplication, and preserved references for unchanged entities. That last point is the one worth emphasizing: normalized updates keep memoization working, whereas nested updates create new references all the way up the tree. Mentioning `createEntityAdapter` and normalizing at the API boundary shows practical familiarity.
