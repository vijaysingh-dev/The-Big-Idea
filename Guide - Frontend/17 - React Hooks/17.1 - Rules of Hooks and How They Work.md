# Rules of Hooks and How They Work

Two rules, and one implementation detail that explains both.

**1. Only call hooks at the top level.** Not inside conditions, loops, or nested functions.
**2. Only call hooks from React function components or custom hooks.**

## Why: hooks are stored in an ordered list

React does not know hook *names*. It associates each hook call with a **position** in a linked list attached to the component's fiber ([[18.3 - Fiber Architecture]]).

```jsx
function Component() {
  const [a, setA] = useState(1);      // hook 0
  const [b, setB] = useState(2);      // hook 1
  useEffect(() => {}, []);            // hook 2
}
```

On the first render React creates three entries in order. On every subsequent render it walks the same list, matching call 0 to entry 0, call 1 to entry 1, and so on. There is no key, no name — only the sequence.

Simplified, the mechanism looks like this:

```js
let currentFiber;
let hookIndex;

function useState(initial) {
  const hooks = currentFiber.hooks;
  const index = hookIndex++;

  if (hooks[index] === undefined) {
    hooks[index] = typeof initial === "function" ? initial() : initial;
  }

  const setState = (value) => {
    hooks[index] = typeof value === "function" ? value(hooks[index]) : value;
    scheduleRerender(currentFiber);
  };

  return [hooks[index], setState];
}
```

`hookIndex` resets to 0 before each render. That is the entire trick, and it is why the rules exist.

## What breaks when you violate rule 1

```jsx
function Broken({ isLoggedIn }) {
  if (isLoggedIn) {
    const [name, setName] = useState("");   // hook 0 — sometimes
  }
  const [theme, setTheme] = useState("dark"); // hook 0 or 1, depending
}
```

When `isLoggedIn` flips from true to false, `theme` shifts from index 1 to index 0 and reads the value that belonged to `name`. State silently attaches to the wrong hook.

The same applies to loops with a variable count, early returns before hooks, and hooks inside callbacks:

```jsx
function Broken({ items }) {
  if (!items.length) return null;      // early return BEFORE hooks
  const [selected, setSelected] = useState(null);
}
```

Move all hooks above any conditional return.

The rule is about **call order being identical every render**, not about literal syntax. A loop with a fixed count technically works, but the linter flags it and it is fragile — someone will make the count dynamic later.

## Working around the constraint

You cannot call a hook conditionally, but you can make the hook itself conditional:

```jsx
// Not allowed
if (id) { const data = useQuery(id); }

// Allowed — the hook always runs, its behavior is conditional
const data = useQuery(id, { enabled: Boolean(id) });
```

Or split into components, since each has its own hook list:

```jsx
function Parent({ isLoggedIn }) {
  return isLoggedIn ? <LoggedIn /> : <LoggedOut />;
}
```

This is usually the right answer to "I need a hook only sometimes" — the conditional belongs at the component boundary.

## The `use` exception

React 19's `use` is deliberately **not** subject to rule 1:

```jsx
function Component({ shouldLoad, promise }) {
  if (shouldLoad) {
    const data = use(promise);   // legal — conditional call
  }
}
```

`use` reads a resource (a promise or a context) and can be called conditionally and inside loops. It works differently — it does not allocate a hook slot, it suspends or reads context directly. It is the only hook with this property, and it exists specifically because Suspense-based data reading needs conditional access ([[17.12 - Lesser Known Hooks]]).

## Rule 2: where hooks may be called

```jsx
function useCustomHook() { useState(); }        // custom hook — fine
function Component() { useState(); }            // component — fine

function helper() { useState(); }               // plain function — not fine
class C { render() { useState(); } }            // class — not fine
onClick={() => useState()}                      // callback — not fine
```

React tracks which fiber is "currently rendering" through a module-level variable. Outside a render, that variable is null, and the hook throws "Invalid hook call".

The naming convention (`use` prefix) is what lets the linter distinguish a custom hook from a plain function. Without it, `getFormState()` calling `useState` internally cannot be checked.

## The "Invalid hook call" error

Three causes, in order of frequency:

1. **Two copies of React.** A linked package with its own `node_modules/react` gets a different module-level state. Deduplicate with `npm dedupe`, `resolutions`, or a bundler alias.
2. **Mismatched `react` and `react-dom` versions.**
3. **Calling a hook outside a component** — including calling a component as a function, `{Component()}` instead of `<Component />` ([[16.3 - Components and Props]]).

The first cause is by far the most common in monorepos and library development, and the error message does not point at it clearly.

## Custom hooks share logic, not state

```jsx
function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);
  return { count, increment: () => setCount(c => c + 1) };
}

function A() { const a = useCounter(); }   // independent state
function B() { const b = useCounter(); }   // independent state
```

Each call site allocates its own hook slots in its own component's list. A custom hook is a code-reuse mechanism, not a shared-state mechanism — sharing state requires context or a store ([[17.11 - Custom Hooks]]).

## The linter is not optional

```json
{ "plugins": ["react-hooks"], "rules": { "react-hooks/rules-of-hooks": "error" } }
```

`rules-of-hooks` catches ordering violations statically. `exhaustive-deps` catches missing dependencies. Both should be errors, not warnings — the failures they prevent are subtle and hard to trace at runtime.

The React Compiler additionally verifies these rules and refuses to optimize components that break them, so violations now cost performance as well as correctness ([[19.9 - The React Compiler]]).

## How senior engineers actually use this

**They put every hook above any conditional return**, as a habit that removes the whole class of ordering bugs.

**They split components** rather than trying to make hooks conditional.

**They recognize "Invalid hook call" as a duplicate-React problem first** in any monorepo or library context, which saves considerable time.

**They know the mechanism**, because understanding that hooks are positional makes the rules obvious rather than arbitrary — and makes it clear why a custom hook cannot share state.

## Common pitfalls

- An early return placed before a hook.
- Hooks inside `if`, `for`, `&&`, or a ternary.
- Hooks in event handlers or callbacks.
- Calling a component as a function, so its hooks join the parent's list.
- Two copies of React in the dependency tree.
- Assuming a custom hook shares state between components.
- Disabling `exhaustive-deps` rather than fixing the dependency.

## Interview angle

"Why can't hooks be called conditionally" is a strong question because the answer requires knowing the implementation: hooks are stored positionally in a list on the fiber, matched by call order rather than by name, so a changed order makes state attach to the wrong hook. Sketching the `hookIndex` mechanism demonstrates real understanding. Mentioning that `use` is exempt, and why, signals current knowledge.
