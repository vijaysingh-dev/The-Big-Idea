# TCP Connection Lifecycle

#backend #networking #tcp

> **In one line:** Opening costs one round trip, closing is asymmetric and leaves one side holding the port for a minute, and a connection whose peer vanished will sit open forever unless you tell it not to.

---

## The Idea

A TCP connection has a state machine. Eleven states, and about six of them you will actually meet.

Every confusing connection problem — ports you cannot rebind, connections that will not die, services that stop accepting — is a state machine question. Once you can read `ss -tan` output, these stop being mysteries.

---

## Opening: The Three-Way Handshake

```
Client                                  Server
  │                                       │  (LISTEN)
  │ ──────── SYN, seq=x ────────────────► │
  │                                       │  (SYN_RECEIVED)
  │ ◄─────── SYN-ACK, seq=y, ack=x+1 ──── │
  │  (ESTABLISHED)                        │
  │ ──────── ACK, ack=y+1 ──────────────► │
  │                                       │  (ESTABLISHED)
  │ ──────── your first byte ───────────► │
```

Both sides pick a random starting sequence number and tell the other. Random, not zero, so that stale packets from an old connection cannot be mistaken for new ones.

**Cost: one full round trip before any data moves.** On a 100ms link, that is 100ms before your request even starts. Add TLS and it is 200–300ms.

💡 **This is the entire argument for connection pooling.** Reusing a warm connection saves the handshake, and if TLS is involved it saves far more. On a cross-region call, connection reuse is often a bigger win than any code optimisation you could make.

### The two queues

```
SYN arrives ──► [ SYN queue ]  half-open, handshake in progress
                     │
handshake done ──► [ accept queue ]  ready, waiting for your accept()
                     │
                     └──► your application
```

```bash
ss -tln
# On a LISTEN socket:
#   Recv-Q = connections currently in the accept queue
#   Send-Q = the backlog limit
```

⚠️ **A non-zero `Recv-Q` on a listening socket means your app is not calling `accept()` fast enough.** If it reaches `Send-Q`, new connections are dropped. Clients see a timeout, not a refusal — which looks like a network problem and is actually your event loop being blocked. See [[01.6 - The Blocking Call Problem]].

```bash
# Count of connections dropped because the accept queue was full
netstat -s | grep -i "listen queue"
```

That counter is one of the most useful and least known numbers in Linux networking.

### SYN flood

An attacker sends SYNs and never completes the handshake. The SYN queue fills with half-open connections and legitimate clients cannot get in.

```bash
sysctl net.ipv4.tcp_syncookies      # should be 1
```

SYN cookies encode the connection state into the sequence number so the server does not need to remember half-open connections at all. On by default in modern Linux. Know it exists, do not tune it.

## Closing: The Four-Way Handshake

Closing is asymmetric because TCP connections are two independent one-way streams. Each direction closes separately.

```
Initiator                              Responder
  │ ──────── FIN ───────────────────────► │
  │  (FIN_WAIT_1)                         │  (CLOSE_WAIT)
  │ ◄─────── ACK ──────────────────────── │
  │  (FIN_WAIT_2)                         │
  │                                       │  ← can still send data here
  │ ◄─────── FIN ──────────────────────── │
  │  (TIME_WAIT)                          │  (LAST_ACK)
  │ ──────── ACK ───────────────────────► │
  │                                       │  (CLOSED)
  │  wait 2×MSL (~60s)                    │
  │  (CLOSED)                             │
```

**Half-close is legal and useful.** After sending FIN, you can still receive. This is what `shutdown(SHUT_WR)` does — "I have nothing more to send, but keep talking to me." Some protocols use it to signal end-of-request while awaiting the response.

## The States You Will Meet

| State | Meaning | If you see a lot of them |
|---|---|---|
| `LISTEN` | Server waiting | Normal |
| `SYN_SENT` | Client sent SYN, no reply | Firewall dropping, or the host is down |
| `ESTABLISHED` | Connected | Normal — unless the count keeps growing |
| `FIN_WAIT_2` | You closed, peer has not | **The peer's app is not closing its socket** |
| `CLOSE_WAIT` | Peer closed, you have not | **Your app is leaking sockets. This is a bug in your code** |
| `TIME_WAIT` | You closed first, waiting out stragglers | Normal in volume. A problem only in the tens of thousands |
| `LAST_ACK` | You closed second, awaiting final ACK | Transient |

⚠️ **`CLOSE_WAIT` piling up is always your bug.** The peer said goodbye, and your application never called `close()`. Usually an exception path that skips cleanup, or a connection object that lost its owner. Sockets accumulate until you hit the fd limit.

```bash
ss -tan state close-wait
lsof -p <pid> | grep CLOSE_WAIT      # which fds, and where they came from
```

Fix it with a context manager or `try/finally`, not by tuning the kernel.

## TIME_WAIT

The state that causes the most confusion.

### Why it exists

The side that closes **first** enters `TIME_WAIT` and stays there for twice the maximum segment lifetime — 60 seconds on Linux, not tunable without recompiling.

Two reasons:

1. **Stragglers.** A delayed packet from this connection could arrive after a new connection reuses the same four-tuple, and be accepted as valid data. `TIME_WAIT` outlives any packet still in flight
2. **The final ACK might be lost.** If it is, the peer retransmits its FIN, and `TIME_WAIT` means somebody is still there to answer

### Why it bites

```python
# This is what causes it
for url in urls:
    r = requests.get(url)      # new connection each time, closed by you
```

Every closed connection holds its source port for 60 seconds. With ~28,000 ephemeral ports, you are limited to roughly 460 new connections per second to a single destination before exhaustion.

```bash
ss -tan state time-wait | wc -l
sysctl net.ipv4.ip_local_port_range
```

### The fixes, in order

| Fix | Effect |
|---|---|
| **Connection reuse** | Eliminates the problem. This is the real answer |
| Let the *server* close first | Moves `TIME_WAIT` to the server, which has one port and many peers |
| `net.ipv4.tcp_tw_reuse=1` | Allows reuse of `TIME_WAIT` sockets for outbound connections. Safe with timestamps on |
| More ephemeral ports | Buys headroom, does not fix anything |
| `tcp_tw_recycle` | **Removed from Linux. Never use it.** It broke NAT badly |

💡 **If you are tuning `TIME_WAIT` kernel parameters, you have almost certainly missed a connection reuse bug.** One `httpx.AsyncClient` for the app lifetime makes the entire problem vanish. Say this in an interview and it demonstrates that you understand the cause rather than the symptom.

### SO_REUSEADDR

```python
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
```

This is why your server can restart immediately instead of waiting 60 seconds for `Address already in use`. It lets you bind a port that has `TIME_WAIT` connections on it. Set it on every server socket, always.

## Half-Open Connections

The nastiest failure mode, because nothing tells you it happened.

```
Client ══════════ ESTABLISHED ══════════ Server
              │
        power cut / cable pulled / NAT timeout
              │
Client: gone           Server: still ESTABLISHED, forever
```

No FIN, no RST, nothing. The server holds the file descriptor, the pool slot, possibly a transaction, and waits for data that will never come.

⚠️ **TCP has no built-in liveness check.** An idle connection generates zero traffic, so there is nothing to detect. It will sit there for hours or until reboot.

### Detection

**TCP keepalive** — cheap, and off by default:

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 60)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)
```

Dead within 90 seconds instead of the 2-hour default.

**Application-level heartbeats** — better, and necessary anyway:

```python
async def heartbeat(ws, interval=15):
    while True:
        await asyncio.sleep(interval)
        await ws.send_json({"type": "ping"})
```

Application heartbeats are better than TCP keepalive for three reasons: they also detect an application that is alive but wedged, they pass through proxies that swallow TCP keepalives, and they keep NAT mappings alive. Every WebSocket and SSE implementation does this — see [[04.3 - SSE in Production]].

**Idle timeouts** — the blunt version. Close anything with no traffic for N seconds. Simple and effective if your protocol tolerates it.

## RST — The Abrupt Close

An RST tears the connection down immediately, no handshake, unsent data discarded.

You get one when:

| Cause | Meaning |
|---|---|
| Connecting to a port with nothing listening | The honest "connection refused" |
| Writing to a socket the peer already closed | Your state is stale |
| `SO_LINGER` with timeout 0, then `close()` | Deliberate abort |
| A firewall or load balancer terminating a connection | Very common, and confusing |
| Accept queue overflow on some systems | Overload |

⚠️ **`Connection reset by peer` in a Python traceback is not one thing.** It could be the peer crashing, a load balancer idle timeout, a container being killed mid-request, or a middlebox. To distinguish them you need `tcpdump` to see who sent the RST and when.

💡 A very common production version: a cloud load balancer with a 60-second idle timeout sits between your service and a database. Your pool holds a connection idle for 61 seconds. The load balancer RSTs it. Your pool hands out the dead socket and you get an apparently random `Connection reset by peer` under low traffic — the opposite of what you would expect. The fix is `pool_recycle` shorter than the idle timeout, plus `pool_pre_ping`. See [[01.10 - Connection Pools and Limits]].

## In Production

### The diagnostic sequence

```bash
# 1. State distribution — the shape of the problem
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn

# 2. Accept queue on your listener
ss -tln sport = :8000

# 3. Dropped connections from a full accept queue
netstat -s | grep -iE "listen|overflow"

# 4. Retransmissions — is it the network?
ss -ti | grep -o 'retrans:[0-9/]*' | sort | uniq -c

# 5. Who is sending RSTs?
sudo tcpdump -i any 'tcp[tcpflags] & tcp-rst != 0' -nn
```

Learn to read the first command's output at a glance. It tells you the problem class in one line:

| Pattern | Meaning |
|---|---|
| Many `CLOSE_WAIT` | Your app leaks sockets |
| Many `FIN_WAIT_2` | The peer's app leaks sockets |
| Many `TIME_WAIT` | Not reusing connections |
| Many `SYN_SENT` | Cannot reach the destination |
| `ESTABLISHED` climbing steadily | Connections created but never closed |

### The settings that matter

```python
# Every server socket
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

```bash
# Backlog: your listen() is clamped to this
sysctl -w net.core.somaxconn=4096

# Keepalive defaults — 2 hours is useless
sysctl -w net.ipv4.tcp_keepalive_time=60
sysctl -w net.ipv4.tcp_keepalive_intvl=10
sysctl -w net.ipv4.tcp_keepalive_probes=3
```

⚠️ In Kubernetes these are node-level. You either set them via an init container with privileges, or you set them per-socket in your application. **Per-socket is better** — it is explicit, it travels with the code, and it does not depend on node configuration you may not control.

### Timeout layers, and why each exists

```
connect timeout      2s     cannot reach the host
read timeout        10s     host reached, not responding
idle timeout        60s     no traffic on an open connection
keepalive probe     60s     is the peer still alive at all?
TIME_WAIT           60s     kernel, not tunable
```

Each catches a different failure. Missing any one of them leaves a hole where a connection can hang.

## Codebase

**Repo:** `redis/redis` and `pgbouncer/pgbouncer`

**Question to answer:** How does each of these detect that a peer has gone away without closing? Compare their approaches — one uses TCP keepalive, one relies on application-level activity, and the difference tells you something about their workloads.

**Read, in order:**

1. `redis/src/anet.c` — `anetKeepAlive`. Read the comments; they explain the timing choices well
2. `redis/src/networking.c` — `clientsCronHandleTimeout`. Redis's own idle-connection reaper
3. `redis/redis.conf` — the `timeout` and `tcp-keepalive` settings and their documentation
4. `pgbouncer/src/client.c` and `src/server.c` — connection lifecycle from both directions
5. `pgbouncer/src/janitor.c` — the periodic cleanup that closes idle and broken connections

**The comparison is the point.** Redis serves many short-lived clients and reaps aggressively. PgBouncer holds a small pool of long-lived server connections and is much more careful about closing them. Same problem, opposite solutions, both correct for their workload.

**Part 1 — Annotate the handshake.** Capture one full connection: open, one request, close. Annotate every packet with its flags, sequence numbers, and which state each side is in afterwards.

Then capture a connection closed by the *other* side and confirm that `TIME_WAIT` moves to whoever closed first. **This is the fact that makes TIME_WAIT tuning make sense.**

**Part 2 — Fill the accept queue.** Server with `listen(5)` that accepts one connection per second. Throw 500 clients at it.

Watch `ss -tln` Recv-Q fill. Watch `netstat -s` overflow counters climb. Observe from the client side that failures look like **timeouts, not refusals**.

Then reproduce the same symptom a different way: a normal backlog, but the event loop blocked by a CPU-heavy handler. Identical symptom, completely different cause. Write down how you would tell them apart in production.

**Part 3 — Exhaust the ports.** Client opening a new connection per request to one destination, as fast as possible. Chart `ss -tan state time-wait | wc -l` over time and find the failure point.

Then the same load with a reused connection. Chart both.

Then try to fix the first version with kernel tuning (`tcp_tw_reuse`, wider port range) and record how much headroom it actually buys. **The point is to see that tuning buys a little and reuse buys everything.**

**Part 4 — Leak sockets.** Write a server that closes connections correctly on the happy path and forgets on an exception path. Send traffic that triggers the exception. Watch `CLOSE_WAIT` accumulate until the fd limit.

Then find the leak using only `lsof` and `ss` — as if you had not written the code.

**Part 5 — The vanishing peer.** Establish a connection, then use a firewall rule to make the client disappear without closing.

Measure how long the server holds it with: default settings, `SO_KEEPALIVE` with defaults, tuned keepalive, and application heartbeats. Build the table.

The default-settings number will be genuinely alarming.

**Part 6 — Five ways to get an RST.** Produce a reset by: connecting to a closed port, writing to a closed peer, `SO_LINGER` 0, killing a container mid-request, and an idle timeout on a proxy.

For each, capture the packet and note who sent it. Then reproduce the load-balancer incident: put toxiproxy between your app and Postgres with a 10-second idle timeout, hold a pool connection idle past it, and get the mysterious `Connection reset by peer`. Fix it with `pool_recycle` and `pool_pre_ping`.

**Done when:**
- `ANNOTATED.md` covers both close directions
- You can produce accept-queue overflow two different ways and distinguish them
- Your TIME_WAIT chart shows reuse solving what tuning only softens
- You found your own socket leak with `lsof` alone
- The half-open table has all four detection strategies with real timings
