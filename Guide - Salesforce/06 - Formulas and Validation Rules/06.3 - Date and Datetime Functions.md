# Date and Datetime Functions

## The distinction that causes the most bugs

**Date** has no time and no time zone. The fifth of August is the fifth of August for everyone, everywhere.

**Datetime** is an instant, stored in UTC and displayed in the viewer's time zone. The same stored value shows as different clock times to a user in Mumbai and a user in London — and on a different **date** if the moment is near midnight.

Nearly every date-related defect traces to treating one as the other. See [[02.4 - Fields - Types and Behaviour]] for the field-level treatment; this note covers the formula side.

## Date arithmetic

Subtracting two Dates returns a **Number** of days:

```
CloseDate - CreatedDate.date()      // not valid; see conversion below
Claim_Closed_Date__c - Claim_Date__c
```

Adding a number to a Date returns a Date:

```
Claim_Date__c + 30
TODAY() + 7
```

Subtracting two Datetimes returns a **Number of days as a decimal**, which is the part people miss:

```
// Returns 1.5 for 36 hours, not 36
Resolved_At__c - Created_At__c

// Hours
(Resolved_At__c - Created_At__c) * 24

// Minutes
(Resolved_At__c - Created_At__c) * 24 * 60
```

## Conversion functions

```
TODAY()                      current date, in the user's time zone
NOW()                        current datetime
DATEVALUE(datetime)          datetime to date — in GMT, not the user's zone
DATETIMEVALUE(date)          date to datetime, at midnight GMT
DATE(year, month, day)       construct a date
DAY(date), MONTH(date), YEAR(date)
WEEKDAY(date)                1 = Sunday through 7 = Saturday
ADDMONTHS(date, n)           add months, handling month-end correctly
```

**`DATEVALUE` converts in GMT.** For a user in Mumbai at 02:00 local, `DATEVALUE(NOW())` returns yesterday's date. This produces reports that disagree with what users see and nobody can explain.

```
// Wrong for users east of GMT near midnight
DATEVALUE(CreatedDate)

// Adjusting for a known offset, if the org operates in one zone
DATEVALUE(CreatedDate + 5.5/24)
```

The offset approach works for a single-zone org and breaks in a multi-zone one, and it does not handle daylight saving. There is no clean formula solution for multi-zone date extraction, which is one of the honest arguments for doing the calculation in Apex where `Datetime.date()` and time zone handling are available. See [[09.2 - Variables, Data Types and Operators]].

**`ADDMONTHS` handles month-end properly.** Adding one month to 31 January gives 28 or 29 February, not an invalid date. Doing it with `DATE(YEAR(d), MONTH(d) + 1, DAY(d))` produces errors on month boundaries, and it is a classic bug.

```
// Correct
ADDMONTHS(Contract_Start__c, 12)

// Broken on 31st of any month, and on December
DATE(YEAR(Contract_Start__c) + 1, MONTH(Contract_Start__c), DAY(Contract_Start__c))
```

## Fiscal periods

Formulas have no fiscal year functions. Fiscal quarter and year are available as fields on Opportunity, populated by the platform from the org's fiscal settings, but not as formula functions.

For other objects, computing them means encoding the fiscal calendar:

```
// Indian financial year starting 1 April
IF(
  MONTH(Claim_Date__c) >= 4,
  "FY" & TEXT(YEAR(Claim_Date__c)) & "-" & RIGHT(TEXT(YEAR(Claim_Date__c) + 1), 2),
  "FY" & TEXT(YEAR(Claim_Date__c) - 1) & "-" & RIGHT(TEXT(YEAR(Claim_Date__c)), 2)
)
```

```
// Fiscal quarter, April start
CASE(
  CEILING((MONTH(Claim_Date__c) - 3) / 3),
  1, "Q1", 2, "Q2", 3, "Q3", 4, "Q4",
  "Q4"
)
```

The fallback in that `CASE` handles January to March, where the expression goes negative or zero. Testing formulas at period boundaries is worth doing deliberately, because those are exactly the values nobody thinks to check.

## Business days

Formulas have **no business hours awareness**. There is no function that excludes weekends or holidays.

Weekend-only exclusion can be approximated:

```
// Working days between two dates, excluding weekends but not holidays
(FLOOR((Claim_Closed_Date__c - Claim_Date__c) / 7) * 5) +
MIN(5,
  MOD(Claim_Closed_Date__c - Claim_Date__c, 7) -
  MAX(0, MOD(Claim_Closed_Date__c - Claim_Date__c, 7) - (6 - WEEKDAY(Claim_Date__c)))
)
```

That is already hard to read and it does not handle holidays, which vary by region. Any org operating across India, EMEA, and APAC has three different holiday calendars.

The honest guidance: **do not compute business days in a formula.** Use one of:

**Entitlement milestones**, which handle business hours and holidays natively and are the purpose-built answer for service level tracking. See [[05.5 - Entitlements, Milestones and SLAs]].

**`BusinessHours.diff()` in Apex**, which uses a `BusinessHours` record and its associated `Holiday` records:

```java
Long workingMillis = BusinessHours.diff(businessHoursId, startDatetime, endDatetime);
Decimal workingHours = workingMillis / 3600000.0;
```

**A stored field** populated by a trigger or flow using the above, so it can be filtered and reported on efficiently.

The formula approximation is acceptable only when weekends are the entire requirement and no region has meaningful holidays, which is rarely true.

## Age and elapsed time patterns

The common ones, written safely:

```
// Days a claim has been open, handling the null closed date
IF(
  ISBLANK(Claim_Closed_Date__c),
  TODAY() - Claim_Date__c,
  Claim_Closed_Date__c - Claim_Date__c
)
```

```
// Contract expiring soon, as a checkbox formula
AND(
  NOT(ISBLANK(End_Date__c)),
  End_Date__c >= TODAY(),
  End_Date__c <= TODAY() + 90
)
```

```
// Readable age banding for reports
IF(Days_Open__c > 30, "Over 30 days",
IF(Days_Open__c > 14, "15-30 days",
IF(Days_Open__c > 7,  "8-14 days",
                      "Under 8 days")))
```

That last one is exactly what a report **bucket field** does without consuming a field slot or a query. Reach for a bucket field when the categorization is only needed in reporting. See [[05.14 - Service Analytics and Operational Reporting]].

## Formula fields and TODAY()

A formula field using `TODAY()` recalculates on every read, so "days open" is always current with no automation. That is the main advantage of formulas.

The cost: **it cannot be filtered efficiently at scale.** Formula fields are generally not indexed, so a query filtering on a formula field against a multi-million-row object is non-selective and slow or times out. See [[08.9 - Indexes and Selective Queries]].

The rule that follows: **if you need to filter on it at volume, store it.** A nightly batch writing an `Age_Days__c` number field is more work and it is the only thing that performs.

```java
public with sharing class ClaimAgeBatch implements Database.Batchable<SObject>, Schedulable {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Date__c, Age_Days__c
            FROM Warranty_Claim__c WHERE Status__c != 'Closed'
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        Date today = Date.today();
        for (Warranty_Claim__c claim : scope) {
            claim.Age_Days__c = claim.Claim_Date__c.daysBetween(today);
        }
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 2000);
    }
}
```

Filtering on a stored, indexed number field is fast. Filtering on the equivalent formula is not.

## Date literals in SOQL

Not a formula function, but the counterpart worth knowing, because it is how the same questions get asked in queries:

```sql
WHERE CreatedDate = TODAY
WHERE CloseDate = THIS_FISCAL_QUARTER
WHERE Claim_Date__c = LAST_N_DAYS:30
WHERE End_Date__c = NEXT_N_DAYS:90
WHERE ClosedDate = LAST_N_MONTHS:12
WHERE CreatedDate = LAST_N_FISCAL_QUARTERS:4
```

These are evaluated by the platform in the **user's time zone** for Date fields and correctly for Datetime fields, which makes them safer than constructing date ranges in Apex. Prefer them.

## Practical guidance

**Use Date, not Datetime, unless the time genuinely matters.** It removes an entire class of bug.

**Be careful with `DATEVALUE`.** It converts in GMT.

**Use `ADDMONTHS`**, never manual month arithmetic.

**Do not compute business days in formulas.** Use milestones or `BusinessHours` in Apex.

**Store what you need to filter at scale.** Formulas are for display and small-volume filtering.

**Test at period boundaries.** Month-end, year-end, fiscal-year start, and daylight saving transitions are where date logic fails.
