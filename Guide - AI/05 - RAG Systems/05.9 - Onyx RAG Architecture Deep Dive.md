# Onyx RAG Architecture Deep Dive

## What Onyx Is

Onyx (formerly Danswer) is an open-source enterprise search and QA system. It implements a complete production-grade RAG pipeline with:

- 20+ source connectors (Google Drive, Confluence, Slack, Jira, Notion, GitHub, etc.)
- Hybrid search (Vespa for both dense + sparse)
- Permission-aware retrieval
- Streaming responses with citations
- Multi-model LLM support (OpenAI, Anthropic, local models)

Reading Onyx teaches you what real production RAG code looks like — not tutorial demos.

**GitHub**: https://github.com/onyx-dot-app/onyx  
**Entry point for backend**: `backend/danswer/`

## Ingestion Pipeline

### Directory: `backend/danswer/connectors/`

Each connector is a Python class implementing:

```python
class BaseConnector(ABC):
    @abstractmethod
    def load_credentials(self, credentials: dict) -> Optional[dict]:
        """Store and validate OAuth credentials"""
    
    @abstractmethod  
    def load_from_state(self) -> GenerateDocumentsOutput:
        """Full load: yield all documents"""
    
    def poll_connector(self, start: SecondsSinceUnixEpoch, end: ...) -> GenerateDocumentsOutput:
        """Incremental load: yield documents modified between start and end"""
```

Example connector structure (`connectors/google_drive/connector.py`):

- Authenticate via OAuth
- List files using Drive API with `modifiedTime` filter
- Export each file as text (Google Docs → plain text)
- Extract permissions per file
- Yield `Document` objects

### Directory: `backend/danswer/indexing/`

The indexing pipeline processes documents from connectors:

```
connector.load_from_state()
    │
    ▼ Document objects (raw text + metadata + permissions)
indexer.py
    │
    ├── chunker.py: Chunk text → List[DocAwareChunk]
    │   - Uses recursive splitting with configurable chunk size
    │   - Attaches document metadata + permissions to each chunk
    │
    ├── embedder.py: Embed chunks → List[IndexChunk]
    │   - Batches chunks for efficient API calls
    │   - Supports OpenAI, Cohere, local models
    │
    └── document_index/ (Vespa client):
        - upsert_chunks(): Store vectors + BM25 fields in Vespa
```

Key file: `backend/danswer/indexing/indexing_pipeline.py`

## Vespa Schema

Onyx uses Vespa as the single document index for both vector search and BM25.

Schema (simplified from `backend/danswer/document_index/vespa/app_config/schemas/danswer_chunk.sd`):

```
schema danswer_chunk {
    document danswer_chunk {
        field document_id type string { ... }
        field chunk_id type int { ... }
        field content type string {
            indexing: summary | index    # enables BM25
        }
        field title type string {
            indexing: summary | index
        }
        field embeddings type tensor<float>(x[1536]) {
            indexing: attribute | index   # enables ANN
            attribute { distance-metric: angular }   # cosine similarity
            index { hnsw { max-links-per-node: 16, neighbors-to-explore-at-insert: 200 } }
        }
        field access_control_list type weightedset<string> { ... }  # permissions
        field metadata_json type string { ... }   # source URL, title, etc.
    }
    
    rank-profile hybrid_search {
        inputs { query(query_embedding) tensor<float>(x[1536]) }
        first-phase {
            expression: 0.5 * closeness(field, embeddings) + 0.5 * bm25(content)
        }
    }
}
```

This schema enables:

- BM25 on `content` and `title` fields
- ANN search on `embeddings` field (HNSW index)
- Hybrid ranking combining both in a single Vespa query
- Permission filtering via `access_control_list`

## Query Pipeline

### Directory: `backend/danswer/search/`

**Entry point**: `search_runner.py` — orchestrates the full query pipeline.

**Step 1: Query preprocessing** (`models.py`, `utils.py`)

- Parse user query
- Extract time filters if present ("last month", "in 2023")
- Determine search type (semantic, keyword, hybrid)

**Step 2: Retrieval** (`retrieval/search_runner.py`)

```python
# Vespa query combining dense + sparse
yql = """
select * from danswer_chunk 
where ({targetHits: 100}nearestNeighbor(embeddings, query_embedding))
   or userQuery()
"""
```

**Step 3: Permission filtering** (`access/utils.py`)

- Each result checked against user's groups + direct access list
- Done at application layer after Vespa returns results

**Step 4: Reranking** (`postprocessing/rerank.py`)

- Optional Cohere reranker or local cross-encoder
- Re-scores top-100, returns top-K

**Step 5: Context assembly** (`chat/prompt_builder.py`)

- Formats retrieved chunks with source titles
- Manages token budget
- Inserts into chat template

**Step 6: LLM generation** (`llm/`)

- Model-agnostic LLM abstraction layer
- Supports OpenAI, Anthropic, Azure OpenAI, local Ollama
- Streaming response with token-level output

**Step 7: Citation extraction** (`chat/citations.py`)

- Parses `[source_N]` markers from streamed response
- Maps back to original document URLs and titles
- Returns citations array alongside answer

## LLM Abstraction Layer

`backend/danswer/llm/` implements a clean abstraction:

```python
class LLM(ABC):
    @abstractmethod
    def invoke(self, prompt: LanguageModelInput) -> str: ...
    
    @abstractmethod
    def stream(self, prompt: LanguageModelInput) -> Iterator[str]: ...

# Implementations:
class OpenAILLM(LLM): ...
class AnthropicLLM(LLM): ...
class AzureOpenAILLM(LLM): ...
class OllamaLLM(LLM): ...
```

This allows swapping models without changing the search pipeline — an important production pattern.

## Background Jobs

`backend/danswer/background/` contains Celery tasks:

- `celery/tasks/indexing.py`: Connector polling, incremental sync
- `celery/tasks/periodic.py`: Scheduled cleanup, permission sync
- `background/update.py`: Main indexing worker loop

The connector poll schedule is configurable per connector (e.g., Slack every 10 minutes, Google Drive every hour).

## Key Architectural Decisions and Tradeoffs

### Why Vespa (not Qdrant or Elasticsearch)?

|Decision|Tradeoff|
|---|---|
|Vespa for hybrid|Single query, single system, native BM25+ANN fusion. Vs. running ES + Qdrant separately and merging in app code|
|Vespa complexity|Vespa has a steeper learning curve than Qdrant, requires more operational knowledge|
|Vespa performance|Vespa is built for high-throughput production; better performance at scale than Chroma/Qdrant|

### Why FastAPI over Django?

Async-native, better for streaming responses (SSE for token streaming). Django's ORM is used only where needed (Postgres for metadata).

### Why Celery + Redis over Kafka?

Simpler operational overhead for the scale Onyx targets (<10M documents). Kafka would be needed for much higher ingestion volumes or strict ordering guarantees.
