# PEFT: LoRA, QLoRA, and Adapters

## The Problem PEFT Solves

Full fine-tuning of a 70B model requires:

- ~140GB GPU memory for weights (FP16)
- ~560GB for weights + gradients + optimizer states (Adam uses 3 copies)
- Multiple A100 80GB GPUs

Most teams don't have this. PEFT (Parameter-Efficient Fine-Tuning) fine-tunes only a tiny fraction of parameters while maintaining nearly full-fine-tuning quality.

---

## LoRA (Low-Rank Adaptation)

### Core Idea

Large weight matrices in neural networks are **low-rank** — they don't span their full dimensionality. Fine-tuning changes them by an update that is _also_ low-rank.

Instead of learning a full weight update ΔW (which has the same dimensions as W), LoRA decomposes the update into two small matrices:

```
ΔW = A × B

where:
  W  ∈ ℝ^(d_out × d_in)   ← original weight (frozen)
  A  ∈ ℝ^(d_out × r)      ← trainable (small)
  B  ∈ ℝ^(r × d_in)       ← trainable (small)
  r  << min(d_out, d_in)   ← rank hyperparameter (typically 4–64)
```

During the forward pass:

```
output = (W + A × B) × input
       = W × input + A × B × input  ← original + low-rank update
```

Only A and B are updated during training. W stays frozen.

### Parameter Count Comparison

For a typical attention weight matrix `W ∈ ℝ^(4096 × 4096)`:

- Full fine-tuning: 4096 × 4096 = **16.7M parameters**
- LoRA with r=16: (4096 × 16) + (16 × 4096) = **131K parameters** (0.8% of full)

Typically applied to: Q, K, V, O projection matrices in attention layers.

### LoRA Hyperparameters

```python
lora_config = LoraConfig(
    r=16,                    # Rank: 4–64; higher = more capacity, more params
    lora_alpha=32,           # Scaling factor; effective learning rate = α/r
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],  # Which layers
    lora_dropout=0.1,        # Regularization
    bias="none",             # Whether to train biases
)
```

**Choosing rank**:

- `r=4`: Minimal, style/format changes
- `r=16`: Standard for domain adaptation
- `r=64`: Near full fine-tuning quality; larger memory footprint
- `r=128+`: Rarely better than r=64; use full fine-tuning instead

### Merging LoRA Weights

After training, merge A×B back into W for zero-latency inference:

```python
merged_model = model.merge_and_unload()
# Now inference is identical speed to base model
```

Or keep them separate (smaller storage, faster iteration during development).

## QLoRA (Quantized LoRA)

**Definition**: Run the base model in 4-bit quantization (NF4) while training LoRA adapters in full precision (BF16).

This enables fine-tuning models that don't fit in GPU memory:

|Model|Full FT GPU requirement|QLoRA GPU requirement|
|---|---|---|
|7B|~28GB (FP16)|~10GB|
|13B|~52GB|~16GB|
|70B|~280GB|~40GB|

### How QLoRA Works

```
1. Load base model in 4-bit NF4 quantization (frozen)
   → 4-bit weights use custom format (NormalFloat4) that minimizes quantization error
   
2. Add LoRA adapters in BF16 (trainable)
   → Small adapter matrices remain in full precision

3. Forward pass:
   → Base model 4-bit weights are dequantized to BF16 on-the-fly for computation
   → LoRA adapters computed in BF16
   → Gradient flows through adapters only

4. Memory efficient:
   → Base model stays 4-bit in GPU memory
   → Only adapter gradients + optimizer states stored in full precision
```

### QLoRA Training Code

```python
from transformers import BitsAndBytesConfig
from peft import prepare_model_for_kbit_training, LoraConfig, get_peft_model

# Load in 4-bit
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,  # Saves more memory
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, quantization_config=bnb_config
)

# Prepare for training (cast layer norms to float32)
model = prepare_model_for_kbit_training(model)

# Add LoRA
lora_config = LoraConfig(r=16, lora_alpha=32, target_modules=[...])
model = get_peft_model(model, lora_config)

# Train normally with SFTTrainer / Trainer
```

## Adapters (Adapter Layers)

An older PEFT approach (Houlsby 2019): insert small bottleneck layers between transformer layers.

```
Transformer layer output
      ↓
  [Adapter: Linear(d→r) → Activation → Linear(r→d)]
      ↓ + residual
Next transformer layer
```

Less popular now than LoRA because:

- LoRA achieves similar quality with zero inference latency overhead
- Adapters add latency (extra computation per layer at inference time)
- LoRA is simpler to implement and maintain

---

## Prefix Tuning and Prompt Tuning

**Prefix Tuning**: Prepend a trainable sequence of "virtual tokens" to the input. Only the prefix embeddings are trained. The prefix acts as a learned continuous prompt.

**Prompt Tuning**: Even lighter than prefix tuning — just learn a few soft prompt tokens appended to the input embedding.

Both are less popular than LoRA because they achieve lower quality at equivalent parameter count. LoRA is now the default PEFT choice.

---

## Choosing Between PEFT Methods

```
Need to fine-tune an LLM?
│
├── Have ample GPU memory (8× A100)?
│   └── Full fine-tuning → maximum quality
│
├── Have moderate GPU memory (1–4× A100)?
│   └── LoRA → near full quality, much cheaper
│
└── Limited GPU memory (single consumer GPU)?
    └── QLoRA → enables 70B models on 40GB
```

**Default recommendation for production fine-tuning**: QLoRA with r=16. It fits on reasonable hardware and achieves strong results.

---

## Production Deployment with LoRA

Options for serving a base model + LoRA adapter:

1. **Merge and serve**: Merge adapter into weights, serve merged model. Zero latency overhead. One model per fine-tuned variant.
    
2. **Multi-LoRA serving**: vLLM and similar systems support loading one base model + multiple LoRA adapters simultaneously. Switch adapters per request. Efficient for multi-tenant or multi-task scenarios.
    
3. **PEFT serving**: Load base model + attach adapter at load time. Simple but one variant per server.
