# Real Failure Scenarios and Root Causes

## How to use this note

Eight scenarios, each in the form a production incident actually arrives in: a symptom, an investigation, a root cause, and a fix. Work through the investigation before reading the cause.

The pattern worth noticing across all of them: **the reported symptom is rarely where the problem is.**

---

## Scenario 1

> A nightly batch job that took 45 minutes six months ago now takes five hours and overruns its window. The code has not changed.

**Investigation.**

```sql
SELECT ApexClass.Name, CreatedDate, CompletedDate, JobItemsProcessed
FROM AsyncApexJob
WHERE ApexClass.Name = 'ClaimEnrichmentBatch' AND CreatedDate = LAST_N_DAYS:180
ORDER BY CreatedDate
```

`JobItemsProcessed` has grown from 1,100 chunks to 6,800. The record count grew.

Then the query plan on the locator:

```
Cardinality  Fields      Leading Operation Type  Cost
   1360000   Status__c   TableScan               3.14
```

**Root cause.** The query was selective at two million records and is not at eight million. The filter returns 17% of the table, which was below the threshold and now is not.

**Fix.**

```sql
-- Was
WHERE Status__c = 'Under Review'

-- Now
WHERE Status__c = 'Under Review' AND Claim_Date__c = LAST_N_DAYS:180
```

**The deeper fix is archiving.** Reducing the object to two million makes the original filter selective again, and fixes every other query on the object at the same time. See [[23.4 - Archiving with Big Objects and External Storage]].

**The lesson:** a query that is selective today may not be next year, and nothing warns you. Trending job duration is the only early signal.

## Scenario 2

> A data load of 400,000 claims fails on roughly 8% of rows with `UNABLE_TO_LOCK_ROW`. Retrying the failed file produces a different 8%.

**Investigation.** The failed-results file, grouped by asset:

```
Asset MCH-00001    2,847 failures
Asset MCH-00002    2,203 failures
Asset MCH-04412        3 failures
```

Then:

```sql
SELECT Asset__c, COUNT(Id) FROM Warranty_Claim__c
GROUP BY Asset__c ORDER BY COUNT(Id) DESC LIMIT 10
```

Two assets hold 180,000 claims between them.

**Root cause.** Account data skew, plus an unsorted file. Parallel batches each touch claims across both hot assets, and the master-detail roll-up locks the asset on every child save.

**Fix, in order.**

**Sort the file by asset Id.** Children of the same asset land in the same batch, so one lock acquisition rather than four competing.

**Reduce roll-ups on Asset** if there are many — each one recalculates on every child change.

**Serial mode** if sorting is not sufficient.

**Address the skew.** Two assets with 90,000 claims each is a data model problem, and it will recur.

See [[10.9 - Data Skew]] and [[23.5 - Bulk Data Loading at Scale]].

## Scenario 3

> Inserting 200 claim parts fails with `Apex CPU time limit exceeded`. The Claim Part trigger is twenty lines and does nothing expensive.

**Investigation.** The debug log's nesting:

```
DML_BEGIN [1] Op:Insert Type:Claim_Part__c Rows:200
  CODE_UNIT_STARTED Trigger:ClaimPartTrigger after insert
    DML_BEGIN [2] Op:Update Type:Warranty_Claim__c Rows:48
      CODE_UNIT_STARTED Trigger:WarrantyClaimTrigger before update
      CODE_UNIT_STARTED Flow:Claim_Approval_Routing
      CODE_UNIT_STARTED Trigger:WarrantyClaimTrigger after update
        DML_BEGIN [3] Op:Update Type:Asset Rows:12
          CODE_UNIT_STARTED Trigger:AssetTrigger after update
            DML_BEGIN [4] Op:Update Type:Account Rows:4
LIMIT_USAGE_FOR_NS|(default)| Maximum CPU time: 9847 out of 10000
```

**Root cause.** The cascade. One insert runs four objects' automation, and a record-triggered flow fires per claim.

The Claim Part trigger is not the problem; it is the entry point to everything else.

**Fix.**

**Reduce roll-ups** on Warranty Claim and Asset.

**Update only records whose values changed**, which stops the cascade where nothing needs updating:

```java
List<Asset> changed = new List<Asset>();
for (Asset asset : assets.values()) {
    if (asset.Open_Claim_Count__c != originalCounts.get(asset.Id)) {
        changed.add(asset);
    }
}
if (!changed.isEmpty()) {
    update changed;
}
```

**Move the claim's routing flow logic** into the existing trigger, so it runs once per batch rather than once per record.

**Move non-urgent aggregation to a scheduled job.**

See [[11.9 - Triggers and Order of Execution]] and [[16.3 - CPU Time and Heap Size]].

## Scenario 4

> Moving a sales director one level up in the role hierarchy locks the org for three hours. Users report timeouts throughout.

**Investigation.**

```sql
SELECT OwnerId, Owner.Name, COUNT(Id) FROM Opportunity
GROUP BY OwnerId, Owner.Name ORDER BY COUNT(Id) DESC LIMIT 10
```

The director owns 340,000 opportunities — records reassigned to them when three reps left over two years.

**Root cause.** Ownership skew. Moving a user in the hierarchy recalculates sharing for every record they own, and 340,000 records with a seven-level hierarchy is millions of sharing rows deleted and reinserted.

**Fix.**

**Immediately:** the change should have been made in a maintenance window, with deferred sharing calculation enabled.

**Structurally:** redistribute ownership.

```java
public void execute(Database.BatchableContext ctx, List<Opportunity> scope) {
    for (Integer i = 0; i < scope.size(); i++) {
        scope[i].OwnerId = targetOwnerIds[Math.mod(i, targetOwnerIds.size())];
    }
    Database.update(scope, false);
}
```

Small scope, deferred sharing on, outside business hours.

**Preventively:** reassign departing users' records promptly rather than accumulating them on one person.

See [[23.3 - Sharing at Scale and Sharing Recalculation]].

## Scenario 5

> An integration that has run hourly for two years stops writing records. No errors anywhere. Nobody notices for nine days.

**Investigation.**

```sql
SELECT ApexClass.Name, Status, NumberOfErrors, CreatedDate
FROM AsyncApexJob WHERE JobType = 'ScheduledApex' AND CreatedDate = LAST_N_DAYS:14
```

No records at all for the last nine days — the job is not failing; it is not running.

```sql
SELECT Id, CronJobDetail.Name, State, NextFireTime, PreviousFireTime
FROM CronTrigger WHERE CronJobDetail.Name LIKE 'ERP Sync%'
```

No rows.

```sql
SELECT Action, Section, CreatedBy.Name, CreatedDate, Display
FROM SetupAuditTrail WHERE CreatedDate = LAST_N_DAYS:14
```

A deployment nine days ago. The scheduled class was modified, which required the job to be aborted first — and nobody rescheduled it.

**Root cause.** A scheduled Apex class cannot be modified while scheduled. The deployment process aborted the job, deployed, and did not reschedule.

**Fix.**

**Immediately:** reschedule.

**Structurally:** put the reschedule in the post-deployment script:

```java
for (CronTrigger ct : [
    SELECT Id FROM CronTrigger
    WHERE CronJobDetail.Name LIKE 'ERP Sync%' AND State != 'DELETED'
]) {
    System.abortJob(ct.Id);
}
System.schedule('ERP Sync Hourly', '0 0 * * * ?', new ErpSyncScheduler());
```

**Operationally:** alert on absence.

```sql
SELECT Context__c, MAX(Logged_At__c) lastRun
FROM Integration_Run__c GROUP BY Context__c
```

**A job that stopped running produces no failure record.** Only a last-run check detects it, and this failure mode is the one most orgs have no coverage for. See [[21.10 - Deployment Strategies, Rollback and Hotfixes]].

## Scenario 6

> Finance reports that some warranty claims have two payment records. It affects roughly 3% of approved claims, over eighteen months.

**Investigation.**

```sql
SELECT Warranty_Claim__c, COUNT(Id) FROM Claim_Payment__c
GROUP BY Warranty_Claim__c HAVING COUNT(Id) > 1
```

Then field history on an affected claim:

```
Status__c   Under Review → Approved    12 Mar 09:14
Notes__c    (changed)                  18 Mar 14:22
```

The second payment was created on 18 March — an unrelated edit.

**Root cause.** The after-update handler creates a payment when `Status__c == 'Approved'`, without comparing against `Trigger.oldMap`. Every subsequent save of an approved claim creates another payment.

```java
// The defect
if (claim.Status__c == 'Approved') {
    payments.add(buildPayment(claim));
}

// The fix
Warranty_Claim__c prior = priorClaims.get(claim.Id);
if (claim.Status__c == 'Approved' && prior.Status__c != 'Approved') {
    payments.add(buildPayment(claim));
}
```

**Why it took eighteen months to surface:** an approved claim is not usually edited again. The 3% are the ones that were.

**Fix.**

**The code**, as above.

**A test** that edits an already-approved claim and asserts no second payment:

```java
@IsTest
static void editingAnApprovedClaimDoesNotCreateASecondPayment() {
    // ... approve, then make an unrelated edit
    Assert.areEqual(1, [SELECT COUNT() FROM Claim_Payment__c],
        'Only the transition into Approved should create a payment');
}
```

**Data remediation** for the duplicates, using field history to identify which payment was the spurious one.

See [[11.2 - Trigger Context Variables]] and [[19.7 - Testing Triggers and Bulk Behaviour]].

## Scenario 7

> A data load of 400 records processes only 200. No errors. The remaining 200 have null derived fields.

**Investigation.** The records that processed are the first 200 in the file. The trigger handler's recursion guard:

```java
public with sharing class TriggerControl {
    public static Boolean hasRun = false;
}
```

```java
if (TriggerControl.hasRun) {
    return;
}
TriggerControl.hasRun = true;
```

**Root cause.** A static persists for the whole transaction. The load arrives as two chunks of 200 in one transaction; the first sets the flag, and the second returns immediately.

**No error, no log entry.** Two hundred records silently unprocessed.

**Fix.** Track record Ids, not a boolean:

```java
List<Warranty_Claim__c> unprocessed = TriggerControl.filterUnprocessed(
    'WarrantyClaim_AfterUpdate', Trigger.new
);
if (unprocessed.isEmpty()) {
    return;
}
TriggerControl.markProcessed('WarrantyClaim_AfterUpdate', unprocessed);
```

**And the test that catches it:**

```java
@IsTest
static void aSecondBatchInTheSameTransactionIsStillProcessed() {
    // ... update one set, insert a distinct second set, assert both processed
}
```

**A boolean guard passes every single-batch test** and fails only when two distinct batches occur in one transaction — which is exactly what a data load produces. See [[11.6 - Recursion Control and Static Guards]].

## Scenario 8

> Support agents intermittently see `CONCURRENT_REQUESTS_LIMIT_EXCEEDED` when saving a case. It happens most mornings between 09:00 and 10:00.

**Investigation.** The failing operation is a simple case save, and the code is fine.

```sql
SELECT UserId, LoginTime, Application, ApiType FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:7 AND Application != 'Browser'
ORDER BY LoginTime DESC
```

An integration user connecting heavily at 09:00.

With Event Monitoring, `ApexExecution` filtered on `IS_LONG_RUNNING_REQUEST` shows an Apex REST endpoint taking eight seconds per call, called continuously.

**Root cause.** More than ten synchronous Apex requests running over five seconds, org-wide. The integration occupies every slot, and the agents' fast, well-written requests are rejected.

**The failing request is not the cause.** That indirection is why this is diagnosed late.

**Fix.**

**Make the endpoint faster.** The eight seconds is a non-selective query.

**Batch the integration's payload** — one request with 200 records rather than 200 requests.

**Move the work off the synchronous path**, returning 202 with a job reference:

```java
@HttpPost
global static AsyncResponse startImport() {
    Id jobId = System.enqueueJob(new BulkClaimImportQueueable(parseBody()));
    RestContext.response.statusCode = 202;
    return new AsyncResponse(jobId);
}
```

See [[16.6 - Concurrency and Long Running Requests]] and [[13.15 - Building Apex REST and SOAP Services]].

## The patterns across all eight

**The symptom is rarely the cause.** A CPU limit on a Claim Part insert is an Asset trigger. A concurrency rejection for an agent is an integration. A slow batch job is a query that stopped being selective.

**Volume changes behaviour without any code change.** Scenarios 1 and 2 are both "it worked last year".

**Distribution matters more than count.** Scenarios 2 and 4 are skew, not volume.

**Silent failures are the expensive ones.** Scenarios 5, 6, and 7 all ran for months before anyone noticed, because none of them produced an error.

**The diagnostic questions that resolve most of these:**

```
What changed?                   SetupAuditTrail, deployment history
What do the failing records share?   a parent, an owner, a queue
Is it running at all?           AsyncApexJob, CronTrigger, last-run timestamps
What else was running?          for concurrency and contention
Is the query still selective?   the query plan, and the row count
```

## What prevents them

Each scenario maps to something that would have caught it earlier.

```
1  Trending batch job duration
2  Checking distribution before the load
3  Auditing total automation on the object
4  Trending ownership concentration
5  Alerting on absence
6  A test for the transition, not just the state
7  A test with two distinct batches in one transaction
8  Event Monitoring, or a duration check on the endpoint
```

**Six of the eight are monitoring rather than code.** That is the substantive point of this section: at scale, the problems are found by watching rather than by reviewing.
