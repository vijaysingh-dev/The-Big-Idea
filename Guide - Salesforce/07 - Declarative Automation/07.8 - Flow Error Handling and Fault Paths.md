# Flow Error Handling and Fault Paths

## What happens without one

A flow element fails — a Get Records finds nothing where the flow assumed something, a Create Records hits a validation rule, an Apex action throws.

With no fault path:

- The flow stops
- The whole transaction rolls back
- A screen flow user sees "An unhandled fault has occurred", which tells them nothing
- A record-triggered flow blocks the save with an equally opaque message
- An email goes to the flow's **last modifier**, who is often not the right person and may not work there any more

That default email recipient is the detail most orgs never change, and it means failures in unattended automation are silently unmonitored.

## Fault paths

Any element that can fail — every data element, every action, every subflow — can have a **fault path**: an alternative route taken when it errors.

The fault path has access to `{!$Flow.FaultMessage}`, containing the platform's error text.

```
Create Records: Warranty_Claim__c
    ├── success → Screen: confirmation with claim number
    └── FAULT   → Assignment: build a readable message
                → Subflow: Log_Automation_Error
                → Screen: "We could not create the claim. Reference: {!logId}.
                           Please contact support."
```

Three things every fault path should do:

**Tell the user something useful**, in a screen flow. "We could not create the claim" plus a reference is worth far more than the raw fault message, which typically contains a field API name and an internal error code.

**Log it somewhere queryable.** An email nobody reads is not monitoring.

**Fail cleanly.** Do not leave half-created records behind.

## Logging failures properly

The pattern used by mature orgs: a custom object, written by a shared subflow or invocable Apex, called from every fault path.

```java
public with sharing class AutomationLogger {

    public class LogRequest {
        @InvocableVariable(required=true label='Context') public String context;
        @InvocableVariable(required=true label='Message') public String message;
        @InvocableVariable(label='Record Id') public String recordId;
        @InvocableVariable(label='Severity') public String severity;
    }

    @InvocableMethod(label='Log Automation Error'
                     description='Writes an entry to the automation log')
    public static List<String> log(List<LogRequest> requests) {
        List<Automation_Log__c> entries = new List<Automation_Log__c>();

        for (LogRequest req : requests) {
            entries.add(new Automation_Log__c(
                Context__c = req.context,
                Message__c = req.message == null ? null : req.message.left(32000),
                Related_Record_Id__c = req.recordId,
                Severity__c = String.isBlank(req.severity) ? 'Error' : req.severity,
                Logged_At__c = Datetime.now(),
                Running_User__c = UserInfo.getUserId()
            ));
        }

        insert entries;

        List<String> ids = new List<String>();
        for (Automation_Log__c entry : entries) {
            ids.add(entry.Id);
        }
        return ids;
    }
}
```

Returning the log Id lets the screen show a reference the user can quote to support, which turns an opaque failure into a traceable one.

Truncating the message matters — fault messages can exceed the field length, and a logger that itself fails is worse than no logger.

## The rollback problem

Here is the behaviour that makes flow error handling genuinely difficult.

When a flow element fails, **the transaction rolls back**, including everything the flow did before the failure. A fault path that writes a log record is writing inside a transaction that is about to be discarded.

For **screen flows**, the fault path runs and the log write survives, because a screen transition commits the transaction.

For **record-triggered flows**, if the fault path leads to a Finish and the flow ends with an error, the log write is rolled back with everything else.

Two ways around it:

**Publish a platform event.** Events published with the `publish immediately` behaviour survive rollback by design, which is precisely why they are the recommended logging mechanism for anything that might roll back.

```
Fault path
    → Create Records: Automation_Error__e (a platform event)
    → the subscriber writes the log record in its own transaction
```

**Use the Roll Back Records element** deliberately, to discard partial work and then continue on a clean path.

Platform events are the more robust answer and are worth the extra moving part for any org relying on flow for meaningful automation. See [[12.8 - Platform Events]] and [[20.5 - Custom Logging Frameworks]].

## Preventing errors rather than handling them

The better strategy for most failure modes.

**Check before you act.** A Get Records that might find nothing should be followed by a Decision testing for null, not by an element that assumes a record exists.

```
Get Records: Machine_Coverage__c
Decision: Coverage found?
    {!coverageRecord} is null → handle the uncovered case explicitly
    otherwise                 → continue
```

This is the single most common flow defect: assuming a Get Records returned something.

**Validate on screens**, so bad input is caught before the flow does work.

**Use partial-success behaviour on Create and Update elements.** The "Allow the flow to continue if some records fail" option is the flow equivalent of `Database.insert(records, false)`. Without it, one record failing a validation rule aborts the whole collection.

**Null-guard formulas.** A formula dividing by a field that might be zero throws and stops the flow.

## Where flows fail in practice

The recurring causes, worth checking when building:

**Validation rules on the target object.** A flow creating a record must satisfy every validation rule on it, including ones written with a human user in mind. This is why the bypass mechanism in [[06.5 - Validation Rules]] matters.

**Required fields not populated.** Field-level required is enforced against flows exactly as against integrations.

**Permissions.** A flow running in user context cannot create a record the user lacks Create permission on. The failure looks like a logic error and is a permission error.

**Null relationships.** `{!$Record.Account__r.Owner.Email}` throws if `Account__c` is null.

**Governor limits.** A query inside a loop, or a flow triggered in a bulk save. See [[07.10 - Flow Limits and Performance]].

**Locked records.** A record in an approval process cannot be updated. See [[07.11 - Approval Processes]].

**Mixed DML.** A flow updating a User and a normal object in one transaction throws `MIXED_DML_OPERATION`. See [[10.7 - Mixed DML and Setup Objects]].

## Monitoring

Three things worth setting up on day one of any org relying on flow:

**Change the error email recipient.** Process Automation Settings has a default workflow user and an error recipient setting. Point it at a monitored distribution list, not an individual.

**Query failed interviews:**

```sql
SELECT Id, InterviewLabel, CurrentElement, InterviewStatus, CreatedDate, CreatedBy.Name
FROM FlowInterview
WHERE InterviewStatus = 'Error' AND CreatedDate = LAST_N_DAYS:7
ORDER BY CreatedDate DESC
```

**Build a dashboard on the log object.** Error volume by flow, by day, trended. A spike after a deployment is the earliest signal that something broke, and it arrives faster than user complaints.

## Practical guidance

**Add a fault path to every data element and every action.** Not the important ones — all of them.

**Log through a platform event** so the record survives rollback.

**Give users a reference**, not the raw fault message.

**Check for null after every Get Records.** The most common flow defect.

**Enable partial success** on bulk Create and Update elements.

**Change the default error email recipient.** It is one setting and it is the difference between monitored and unmonitored automation.

**Build the error dashboard before you need it.**
