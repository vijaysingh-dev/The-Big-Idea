# CPU Time and Heap Size

## The two hardest limits to debug

```
CPU time      10 seconds synchronous, 60 seconds asynchronous
Heap size     6 MB synchronous, 12 MB asynchronous
```

Query and DML limits point at a line number. These two point at nothing useful — `Apex CPU time limit exceeded` names the transaction, not the cause, and the cause is frequently code you did not write.

## What counts toward CPU

**Computation only.** Time spent waiting does not count:

```
Counts:      loops, string operations, describe calls, JSON, sorting,
             regular expressions, collection operations, flow execution,
             validation rule and formula evaluation
Does not:    SOQL execution, DML execution, callout wait time
```

That distinction matters. A transaction taking eight seconds of wall time may use two seconds of CPU if most of it was waiting on the database, and a transaction taking three seconds may use all ten if it was computing.

**The 10-second budget is shared** with flows, validation rules, formula evaluation, and managed packages. See [[16.1 - Why Governor Limits Exist]].

## The expensive operations

Ordered by how often they cause a failure.

**Nested loops over collections.**

```java
// 200 × 10,000 = two million iterations
for (Account acc : accounts) {
    for (Contact con : contacts) {
        if (con.AccountId == acc.Id) { }
    }
}
```

No query, no DML, and it passes code review. Build a map instead — 10,200 iterations rather than two million. See [[09.3 - Collections - Lists, Sets and Maps]].

**Describe calls, especially `getGlobalDescribe()`.**

```java
// Walks every object in the org, per record
for (Warranty_Claim__c claim : claims) {
    Schema.SObjectType type = Schema.getGlobalDescribe().get('Warranty_Claim__c');
}
```

```java
// Once per transaction, cached in a static
private static Map<String, Schema.SObjectType> globalDescribe;

private static Schema.SObjectType objectType(String name) {
    if (globalDescribe == null) {
        globalDescribe = Schema.getGlobalDescribe();
    }
    return globalDescribe.get(name.toLowerCase());
}
```

Better still, avoid it entirely where the object is known at compile time:

```java
Schema.SObjectType type = Warranty_Claim__c.SObjectType;   // cheap
```

See [[09.12 - Generics, Type Casting and Reflection]].

**String concatenation in a loop.**

```java
// Creates a new String on every iteration
String output = '';
for (Warranty_Claim__c claim : claims) {
    output += claim.Claim_Number__c + ', ';
}
```

```java
// One join at the end
List<String> numbers = new List<String>();
for (Warranty_Claim__c claim : claims) {
    numbers.add(claim.Claim_Number__c);
}
String output = String.join(numbers, ', ');
```

Strings are immutable, so each `+=` allocates a new one. At 10,000 iterations this is measurable in both CPU and heap.

**JSON serialization and deserialization** of large structures.

**Sorting** large collections, particularly with a custom `Comparable`.

**Regular expressions** on long strings, and catastrophic backtracking on a badly written pattern.

**Formula fields** computed per row on read. Forty cross-object formulas on an object, queried across 200,000 records in a batch, is real CPU consumed on the server before your code runs. See [[06.4 - Cross-Object Formulas and Limits]].

## The invisible CPU consumers

The reason this limit is hard to debug: much of the consumption is not in Apex.

**Flows.** A record-triggered flow with several elements, running once per record across 200 records, consumes CPU before or after your trigger.

**Validation rules**, particularly with cross-object formulas.

**Roll-up recalculation**, which sends parents through their own pipeline including their own automation.

**Managed package logic** on the same object.

A transaction failing on CPU where your code is clean is usually accumulated automation. The diagnostic is the debug log's timing, not the code. See [[07.13 - Order of Execution]].

## Measuring CPU

```java
Long start = Limits.getCpuTime();
processClaims(claims);
System.debug('Processing used ' + (Limits.getCpuTime() - start) + 'ms');
```

Bracketing suspect sections is the fastest way to find the expensive one, and it works where the debug log's aggregate does not.

The limit block gives the total:

```
Maximum CPU time: 8214 out of 10000
```

The Developer Console's **execution tree** attributes time per operation, which is what identifies the expensive step rather than only the expensive transaction. See [[20.3 - Developer Console and Log Inspector]].

## What counts toward heap

Every object in memory: query results, collections, strings, and anything held in a static.

```java
// 50,000 records with many fields, including long text areas
List<Warranty_Claim__c> claims = [
    SELECT FIELDS(ALL) FROM Warranty_Claim__c LIMIT 50000
];
```

That will exhaust 6 MB before it exhausts the row limit. Long text areas and rich text are the largest contributors — a single 32,000-character field across 5,000 records is 160 MB of text.

## Reducing heap

**Select fewer fields.** The largest single lever.

```java
// Only what is used
SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c FROM Warranty_Claim__c
```

**Process in chunks** with the list form of the SOQL for loop:

```java
for (List<Warranty_Claim__c> chunk : [
    SELECT Id, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
]) {
    // only 200 records exist in memory at a time
    for (Warranty_Claim__c claim : chunk) {
        claim.Status__c = 'Under Review';
    }
    update chunk;
}
```

**Release references** when finished with a large collection:

```java
List<Warranty_Claim__c> claims = loadClaims();
Map<Id, Decimal> totals = summarize(claims);
claims = null;   // eligible for collection
processTotals(totals);
```

Apex garbage collection makes this help less than it would elsewhere, and it is not nothing on a long batch chunk.

**Watch static collections.** A static cache accumulating across a long-running job holds everything until the transaction ends.

**Move to async** for 12 MB, or to Batch Apex where each chunk gets a fresh heap.

## Measuring heap

```java
System.debug('Heap: ' + Limits.getHeapSize() + ' of ' + Limits.getLimitHeapSize());
```

**Heap dumps** in the Developer Console show what is actually held, per class and per collection, at a checkpoint. This is the only way to find an unexpected retention — usually a static holding more than intended. See [[20.4 - Heap Dumps and Checkpoints]].

## The batch scope-size lever

Both limits are per chunk in Batch Apex, which makes scope size the primary control:

```java
Database.executeBatch(new ClaimEnrichmentBatch(), 50);    // heavy per-record work
Database.executeBatch(new SimpleFieldUpdateBatch(), 2000); // trivial per-record work
```

**A job failing intermittently on some chunks and not others is usually a scope-size problem**, and halving it is the first thing to try. See [[12.4 - Batch Apex]].

## A worked diagnosis

A batch job fails with `Apex CPU time limit exceeded` on roughly one chunk in five.

**1. Bracket the sections.**

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    Long start = Limits.getCpuTime();

    Map<Id, Asset> assets = loadAssets(scope);
    System.debug('Load: ' + (Limits.getCpuTime() - start));

    Long afterLoad = Limits.getCpuTime();
    enrichClaims(scope, assets);
    System.debug('Enrich: ' + (Limits.getCpuTime() - afterLoad));

    Long afterEnrich = Limits.getCpuTime();
    Database.update(scope, false);
    System.debug('Update: ' + (Limits.getCpuTime() - afterEnrich));
}
```

**2. Read the output.** If `Enrich` dominates, the problem is in your code — probably a nested loop or a describe call. If `Update` dominates, the problem is downstream automation: triggers, flows, and roll-ups firing on the save.

**3. If it is the update**, audit what runs on that object:

```sql
SELECT ApiName, Label, TriggerType, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerObjectOrEventLabel = 'Warranty Claim'
```

**4. Reduce the scope size** as an immediate mitigation, and address the cause afterwards.

That sequence — bracket, attribute, then either fix the code or audit the automation — resolves most CPU failures.

## The variability problem

Both limits are affected by things outside your control: server load, data shape, and how much automation ran before your code.

This is why a job succeeds at 200 records and fails at 200 records an hour later. The margin was thin, and something else consumed slightly more.

**Design for headroom, not for the limit.** Code consistently reaching 8,000ms of CPU will fail eventually, and reducing it to 3,000ms is more valuable than any retry mechanism.

## Practical guidance

**Never nest loops over record collections.** Build a map.

**Cache describe calls in a static**, and prefer `Object__c.SObjectType` to `getGlobalDescribe()`.

**Use `String.join`**, never `+=` in a loop.

**Select only the fields you need.**

**Process large sets in chunks.**

**Tune batch scope size** — it is the main lever for both limits.

**Bracket with `Limits.getCpuTime()`** to find the expensive section.

**Use heap dumps** to find unexpected retention.

**Audit the object's automation** when the cost is in the DML rather than your code.

**Aim for headroom**, not for the ceiling.
