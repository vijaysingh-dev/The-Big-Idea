# Live Coding and Debugging Exercises

## How to approach a live coding round

**Narrate.** Silence gives the interviewer nothing to assess. "I'm collecting the asset Ids first so I can query once — inside the loop this would die at 101 records" tells them what they need to know even if the code has a bug.

**Clarify before writing.** How many records, does it run from a trigger, what happens on failure.

**Write it bulk-safe from the first line.** Going back to fix a query in a loop is a worse signal than never writing one.

**Say what you would add with more time.** Tests, error handling, a selector. Naming what is missing is better than the interviewer noticing.

## Exercise 1: fix the code

> What is wrong with this?

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (after insert) {
    for (Warranty_Claim__c claim : Trigger.new) {
        Asset asset = [SELECT Id, SerialNumber, AccountId FROM Asset WHERE Id = :claim.Asset__c];

        claim.Asset_Serial__c = asset.SerialNumber;
        claim.Account__c = asset.AccountId;
        update claim;
    }
}
```

**Five defects, and the order matters.**

Query in a loop — dies at 101 records. DML in a loop — dies at 151. Logic in the trigger body rather than a handler. Wrong event: this sets fields on the triggering record, which is a before trigger, so the after trigger plus DML re-enters the entire save pipeline and risks recursion. And no null guard on `Asset__c`, plus a query returning zero rows throws.

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (before insert, before update) {
    WarrantyClaimTriggerHandler.run();
}
```

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (Trigger.isBefore && (Trigger.isInsert || Trigger.isUpdate)) {
            ClaimService.stampAssetDetails(Trigger.new);
        }
    }
}
```

```java
public with sharing class ClaimService {

    public static void stampAssetDetails(List<Warranty_Claim__c> claims) {
        Set<Id> assetIds = new Set<Id>();
        for (Warranty_Claim__c claim : claims) {
            if (claim.Asset__c != null) {
                assetIds.add(claim.Asset__c);
            }
        }

        if (assetIds.isEmpty()) {
            return;
        }

        // relationship traversal is unavailable in before insert, so the parents
        // are queried explicitly
        Map<Id, Asset> assets = new Map<Id, Asset>([
            SELECT Id, SerialNumber, AccountId
            FROM Asset WHERE Id IN :assetIds WITH USER_MODE
        ]);

        for (Warranty_Claim__c claim : claims) {
            Asset asset = assets.get(claim.Asset__c);
            if (asset == null) {
                continue;
            }
            claim.Asset_Serial__c = asset.SerialNumber;
            claim.Account__c = asset.AccountId;
        }
    }
}
```

**The point to make aloud:** moving to before removes the DML entirely, which is the largest improvement — no second save, no recursion risk, and half the work.

## Exercise 2: a roll-up

> Maintain a count and total of open claims on the Asset. Native roll-ups are not available.

```java
public with sharing class ClaimRollupService {

    public static void recalculate(Set<Id> assetIds) {
        if (assetIds == null || assetIds.isEmpty()) {
            return;
        }

        Map<Id, Asset> assets = new Map<Id, Asset>([
            SELECT Id, Open_Claim_Count__c, Total_Claim_Value__c
            FROM Asset WHERE Id IN :assetIds WITH USER_MODE
        ]);

        Map<Id, Decimal> originalCounts = new Map<Id, Decimal>();
        Map<Id, Decimal> originalTotals = new Map<Id, Decimal>();
        for (Asset asset : assets.values()) {
            originalCounts.put(asset.Id, asset.Open_Claim_Count__c);
            originalTotals.put(asset.Id, asset.Total_Claim_Value__c);

            // resetting first means an asset whose last claim closed goes to zero
            // rather than keeping a stale value
            asset.Open_Claim_Count__c = 0;
            asset.Total_Claim_Value__c = 0;
        }

        // aggregating in the database rather than retrieving rows to sum
        for (AggregateResult result : [
            SELECT Asset__c assetId, COUNT(Id) claimCount, SUM(Claim_Amount__c) claimTotal
            FROM Warranty_Claim__c
            WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
            GROUP BY Asset__c
        ]) {
            Asset asset = assets.get((Id) result.get('assetId'));
            asset.Open_Claim_Count__c = (Integer) result.get('claimCount');
            asset.Total_Claim_Value__c = (Decimal) result.get('claimTotal');
        }

        // updating only changed parents stops an entire downstream cascade
        List<Asset> changed = new List<Asset>();
        for (Asset asset : assets.values()) {
            if (asset.Open_Claim_Count__c != originalCounts.get(asset.Id)
                || asset.Total_Claim_Value__c != originalTotals.get(asset.Id)) {
                changed.add(asset);
            }
        }

        if (!changed.isEmpty()) {
            update as user changed;
        }
    }
}
```

**And the Id collection, which is where the subtlety is:**

```java
public static Set<Id> affectedAssetIds(
    List<Warranty_Claim__c> claims, Map<Id, Warranty_Claim__c> priorClaims
) {
    Set<Id> assetIds = new Set<Id>();

    if (claims != null) {
        for (Warranty_Claim__c claim : claims) {
            if (claim.Asset__c != null) {
                assetIds.add(claim.Asset__c);
            }

            // a reparented claim leaves the old asset stale unless it is included
            Warranty_Claim__c prior = priorClaims?.get(claim.Id);
            if (prior?.Asset__c != null && prior.Asset__c != claim.Asset__c) {
                assetIds.add(prior.Asset__c);
            }
        }
    }

    if (claims == null && priorClaims != null) {
        for (Warranty_Claim__c claim : priorClaims.values()) {
            if (claim.Asset__c != null) {
                assetIds.add(claim.Asset__c);
            }
        }
    }

    return assetIds;
}
```

**Three things to say aloud:** the reset handles deletion, the change comparison prevents a cascade into the Asset trigger, and the old-parent collection is the bug most hand-rolled roll-ups have.

**And the events:** insert, update, delete, and **undelete**. Omitting undelete leaves the count permanently wrong when a record is restored.

## Exercise 3: a Queueable with retry

> Push approved claims to an ERP, retrying transient failures.

```java
public with sharing class ErpSyncQueueable implements Queueable, Database.AllowsCallouts {

    private final Set<Id> claimIds;
    private final Integer attempt;

    public ErpSyncQueueable(Set<Id> claimIds, Integer attempt) {
        this.claimIds = claimIds;
        this.attempt = attempt;
    }

    public void execute(QueueableContext context) {
        // attached first, so the finalizer runs even if the work throws immediately
        System.attachFinalizer(new ErpSyncFinalizer(claimIds, attempt));

        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, Claim_Amount__c, Approved_Amount__c
            FROM Warranty_Claim__c WHERE Id IN :claimIds AND ERP_Confirmation__c = null
        ];

        if (claims.isEmpty()) {
            return;
        }

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:ERP_System/api/v2/claims/batch');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setHeader('Idempotency-Key', idempotencyKey(claims));
        req.setBody(JSON.serialize(ClaimPayload.from(claims)));
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() >= 300) {
            throw new IntegrationException(
                'ERP sync failed: ' + res.getStatusCode() + ' ' + res.getBody()
            );
        }

        markSynced(claims, res.getBody());
    }
}
```

```java
public with sharing class ErpSyncFinalizer implements Finalizer {

    private static final Integer MAX_ATTEMPTS = 4;

    private final Set<Id> claimIds;
    private final Integer attempt;

    public void execute(FinalizerContext ctx) {
        if (ctx.getResult() == ParentJobResult.SUCCESS) {
            return;
        }

        Exception cause = ctx.getException();

        // this runs in a fresh transaction, so the log survives the job's rollback
        insert new Integration_Log__c(
            Context__c = 'ErpSync',
            Attempt__c = attempt,
            Job_Id__c = ctx.getAsyncApexJobId(),
            Message__c = cause?.getMessage(),
            Severity__c = attempt >= MAX_ATTEMPTS ? 'Error' : 'Warning'
        );

        if (attempt >= MAX_ATTEMPTS || !isTransient(cause)) {
            markForManualReview(claimIds);
            return;
        }

        // exponential backoff, capped at the platform's ten-minute maximum delay
        Integer delay = Math.min((Integer) Math.pow(2, attempt), 10);
        System.enqueueJob(new ErpSyncQueueable(claimIds, attempt + 1), delay);
    }

    @TestVisible
    private Boolean isTransient(Exception cause) {
        if (cause == null) {
            return false;
        }
        return cause instanceof CalloutException
            || cause.getMessage().contains('Read timed out')
            || cause.getMessage().contains('UNABLE_TO_LOCK_ROW');
    }
}
```

**What to point out:** the finalizer attached first; one callout for the batch rather than per record; the idempotency key so a retry does not duplicate; the `ERP_Confirmation__c = null` filter making a rerun safe; and distinguishing transient from permanent, because retrying a validation failure four times achieves nothing.

## Exercise 4: write a test

> Test that a claim over its coverage limit is blocked, and that the handler is bulk-safe.

```java
@IsTest
private class ClaimValidationServiceTest {

    @TestSetup
    static void setup() {
        Account account = TestDataFactory.createAccount();
        List<Asset> assets = TestDataFactory.createAssets(account.Id, 50);
        TestDataFactory.createCoverageFor(assets, 500000);
    }

    @IsTest
    static void aClaimOverItsCoverageLimitIsBlocked() {
        Asset asset = [SELECT Id FROM Asset LIMIT 1];
        Warranty_Claim__c claim = TestDataFactory.buildClaim(asset.Id, 900000);

        Test.startTest();
        Database.SaveResult result = Database.insert(claim, false);
        Test.stopTest();

        Assert.isFalse(result.isSuccess(), 'A claim over its coverage limit should be blocked');
        // asserting the field, which verifies addError(field, message) was used
        Assert.areEqual('Claim_Amount__c', result.getErrors()[0].getFields()[0],
            'The error belongs on the amount field, not the record');
    }

    @IsTest
    static void theBoundaryValueIsAllowed() {
        Asset asset = [SELECT Id FROM Asset LIMIT 1];
        Warranty_Claim__c claim = TestDataFactory.buildClaim(asset.Id, 500000);

        Test.startTest();
        Database.SaveResult result = Database.insert(claim, false);
        Test.stopTest();

        // exactly at the limit — the case an off-by-one gets wrong
        Assert.isTrue(result.isSuccess(), 'A claim exactly at the limit should be allowed');
    }

    @IsTest
    static void twoHundredClaimsStayWithinLimits() {
        List<Asset> assets = [SELECT Id FROM Asset];

        List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
        for (Integer i = 0; i < 200; i++) {
            // four claims per asset, which a broken aggregation gets wrong
            claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 100000));
        }

        Test.startTest();
        insert claims;

        Assert.isTrue(Limits.getQueries() < 30,
            'Expected well under the query limit, used ' + Limits.getQueries());
        Test.stopTest();

        Map<Id, Asset> refreshed = new Map<Id, Asset>([
            SELECT Id, Open_Claim_Count__c FROM Asset WHERE Id IN :assets
        ]);
        for (Asset asset : assets) {
            Assert.areEqual(4, refreshed.get(asset.Id).Open_Claim_Count__c,
                'Each asset should have four claims');
        }
    }

    @IsTest
    static void oneInvalidClaimDoesNotBlockTheOtherHundredAndNinetyNine() {
        List<Asset> assets = [SELECT Id FROM Asset];
        List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
        for (Integer i = 0; i < 200; i++) {
            claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 100000));
        }
        claims[50].Claim_Amount__c = 900000;

        Test.startTest();
        List<Database.SaveResult> results = Database.insert(claims, false);
        Test.stopTest();

        Integer succeeded = 0;
        for (Database.SaveResult result : results) {
            if (result.isSuccess()) {
                succeeded++;
            }
        }

        Assert.areEqual(199, succeeded, 'One bad record should not block the rest');
        // index-aligned results, which is what per-record error reporting depends on
        Assert.isFalse(results[50].isSuccess());
    }
}
```

**What this demonstrates:** the boundary case, the bulk case with a realistic distribution, an assertion on limit consumption, partial success with index alignment, and assertions on the error field rather than only on failure.

## Exercise 5: debug it

> This runs nightly. It worked for a year and now fails intermittently. What do you check?

```java
public with sharing class ClaimReminderBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Account__c, Claim_Number__c
            FROM Warranty_Claim__c
            WHERE Status__c != 'Closed'
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        for (Warranty_Claim__c claim : scope) {
            Account account = [SELECT Id, Name, OwnerId FROM Account WHERE Id = :claim.Account__c];
            Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{ build(claim, account) });
        }
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Walking through it aloud:**

"Query in a loop, and email in a loop — the email one fails first, because there are only ten `sendEmail` invocations per transaction and this makes one per record.

The query in the loop would fail at 101, so with a scope of 200 both are hit.

But it worked for a year, so the interesting question is what changed. Two candidates: the scope size was reduced at some point, keeping both under the threshold, or — more likely — `Status__c != 'Closed'` was selective when the object was small and is not now. A negative operator cannot use an index, so this is a table scan, and it would show as the job slowing before it started failing.

I'd check `JobItemsProcessed` over time and the query plan on the locator."

**The fix:**

```java
public Database.QueryLocator start(Database.BatchableContext ctx) {
    return Database.getQueryLocator([
        SELECT Id, Account__c, Claim_Number__c, Account__r.Name, Account__r.OwnerId
        FROM Warranty_Claim__c
        // positive list rather than !=, plus a date bound for selectivity
        WHERE Status__c IN ('Submitted', 'Under Review', 'Approved')
          AND Claim_Date__c = LAST_N_DAYS:180
        ORDER BY Account__c
    ]);
}

public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    List<Messaging.SingleEmailMessage> messages = new List<Messaging.SingleEmailMessage>();

    for (Warranty_Claim__c claim : scope) {
        messages.add(build(claim));
    }

    if (!messages.isEmpty()) {
        // one invocation for the whole chunk; the limit is 10 per transaction
        Messaging.sendEmail(messages, false);
    }
}
```

**What to note:** the relationship traversal in the locator removes the query entirely, the positive filter and date bound restore selectivity, and `ORDER BY Account__c` groups contention into single chunks.

## Exercise 6: an LWC

> A component listing a record's claims, with a refresh after an approval.

```javascript
import { LightningElement, api, wire } from 'lwc';
import { refreshApex } from '@salesforce/apex';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';
import getClaims from '@salesforce/apex/ClaimController.getClaimsForAsset';
import approveClaim from '@salesforce/apex/ClaimController.approve';
import { reduceErrors } from 'c/errorUtils';

const COLUMNS = [
    { label: 'Claim', fieldName: 'Claim_Number__c', type: 'text' },
    { label: 'Status', fieldName: 'Status__c', type: 'text' },
    { label: 'Amount', fieldName: 'Claim_Amount__c', type: 'currency',
      typeAttributes: { currencyCode: 'INR' } },
    { type: 'action', typeAttributes: { rowActions: [{ label: 'Approve', name: 'approve' }] } }
];

export default class ClaimList extends LightningElement {
    @api recordId;

    columns = COLUMNS;
    isProcessing = false;
    error;

    // the whole result is kept, because refreshApex needs the handle attached to it
    claimResult;

    @wire(getClaims, { assetId: '$recordId' })
    wiredClaims(result) {
        this.claimResult = result;
    }

    get claims() {
        return this.claimResult?.data ?? [];
    }

    get isLoading() {
        return !this.claimResult?.data && !this.claimResult?.error;
    }

    get isEmpty() {
        return this.claimResult?.data?.length === 0;
    }

    async handleRowAction(event) {
        if (event.detail.action.name !== 'approve') {
            return;
        }

        this.isProcessing = true;
        this.error = undefined;

        try {
            await approveClaim({ claimId: event.detail.row.Id });
            await refreshApex(this.claimResult);

            this.dispatchEvent(new ShowToastEvent({
                title: 'Approved', variant: 'success', mode: 'dismissable'
            }));
        } catch (e) {
            this.error = reduceErrors(e);
        } finally {
            // cleared here, so a failure does not leave the spinner running
            this.isProcessing = false;
        }
    }
}
```

**What to point out:** the `$` making `recordId` reactive, keeping the whole wire result for `refreshApex`, the four states — loading, error, empty, data — and clearing the spinner in `finally`.

**And the Apex behind it:**

```java
@AuraEnabled(cacheable=true)
public static List<Warranty_Claim__c> getClaimsForAsset(Id assetId) {
    return [
        SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c
        FROM Warranty_Claim__c
        WHERE Asset__c = :assetId AND Status__c != 'Closed'
        WITH USER_MODE
        ORDER BY Claim_Date__c DESC
        LIMIT 200
    ];
}
```

"`cacheable=true` because it is read-only, `WITH USER_MODE` because this is a public endpoint regardless of what the component renders, and a `LIMIT` because it works until the data grows."

## What is being assessed

Beyond correctness:

```
Bulkification              non-negotiable
Security                   sharing keyword, WITH USER_MODE
Naming and structure       service layer, not everything inline
Error handling             not swallowed, and a defined failure state
Tests                      assertions, a bulk case, a boundary case
Narration                  thinking aloud
```

**The strongest thing you can do** is write it bulk-safe from the first line and explain why as you go. A candidate who narrates a correct approach with a small bug reads better than one who silently produces perfect code.
