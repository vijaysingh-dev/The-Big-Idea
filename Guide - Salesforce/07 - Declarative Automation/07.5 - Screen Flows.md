# Screen Flows

## What they are for

A screen flow presents a user interface across one or more steps, collecting input and acting on it. It is the declarative answer to "we need a guided process" without building a Lightning Web Component.

The typical uses:

- Guided data entry with branching — the questions change based on earlier answers
- A wizard that creates several related records in one pass
- Agent scripting during a call
- A process that needs a confirmation step before acting
- Collecting input from an Experience Cloud user

## Where they run

**Quick action** on a record page, opening in a modal. The most common placement.

**A component on a record page, app page, or home page**, embedded rather than modal.

**A Lightning app or tab**, as a standalone process.

**An Experience Cloud page**, for external users.

**A utility bar item** in a console app, which persists across tab changes — useful for agent scripting.

**A URL**, with parameters passed in.

**Launched from Apex**, embedded in a Lightning Web Component.

Launching from a record page passes the record Id automatically into a variable named `recordId`, which must be marked Available for Input. Getting that variable name wrong is the most common reason a flow opens with no record context.

## Screen components

**Input components:** text, number, date, checkbox, picklist, radio buttons, lookup, file upload, address, long text, rich text.

**Display components:** display text, images, sections and columns.

**Data components:** the Data Table component for selecting from a list of records.

**Custom Lightning Web Components** can be placed on a screen, which is the extension point when the standard components are insufficient. A component exposed with the `lightning__FlowScreen` target and `@api` properties marked with the right access becomes available on the canvas.

```xml
<targets>
    <target>lightning__FlowScreen</target>
</targets>
<targetConfigs>
    <targetConfig targets="lightning__FlowScreen">
        <property name="assetId" type="String" label="Asset Id" role="inputOnly"/>
        <property name="selectedFaultCode" type="String" label="Selected Fault Code" role="outputOnly"/>
    </targetConfig>
</targetConfigs>
```

```javascript
import { LightningElement, api } from 'lwc';
import { FlowAttributeChangeEvent } from 'lightning/flowSupport';

export default class FaultCodeSelector extends LightningElement {
    @api assetId;
    @api selectedFaultCode;

    handleSelection(event) {
        this.selectedFaultCode = event.detail.value;
        // this event is how a flow screen component reports a value back to the flow
        this.dispatchEvent(
            new FlowAttributeChangeEvent('selectedFaultCode', this.selectedFaultCode)
        );
    }
}
```

`FlowAttributeChangeEvent` is the mechanism — without dispatching it, the flow never sees the value even though the property is set. This catches everyone building their first flow component. See [[14.19 - Deploying and Exposing Components]].

## Validation on screens

Each input component can have a validation formula and an error message, evaluated when the user clicks Next.

```
// On a number input for approved amount
{!approvedAmount} <= {!claimRecord.Claim_Amount__c}
```

True means valid here — the opposite of validation rules, which is a small inconsistency worth remembering.

Screen-level validation catches problems before the flow does work, which is a better experience than failing at the Create Records element three screens later.

## Navigation and conditional visibility

**Next, Previous, Pause, and Finish** buttons can each be shown or hidden per screen.

**Pause** lets the user save progress and resume later, creating a paused `FlowInterview`. Useful for long processes and worth disabling for short ones, since a half-finished flow interview that nobody resumes is clutter.

**Conditional visibility** on components shows or hides fields based on earlier answers, within a single screen. This is what makes a screen adaptive without needing a separate screen per branch, and it substantially reduces the number of screens in a well-built flow.

## A worked example

Requirement: an agent logging a warranty claim during a call needs to identify the machine, capture the fault, check coverage, and create the claim.

```
Screen 1: Identify the machine
    Lookup: Asset (filtered to the case's account)
    or Text input: Serial number
    Conditional visibility: serial number shown only if no asset selected

Get Records: Asset by serial number (if serial was entered)

Decision: Asset found?
    No  → Screen: "Machine not found, please verify" → back to Screen 1
    Yes → continue

Get Records: Machine_Coverage__c
    where Asset__c = {!selectedAsset.Id}
    and Service_Contract__r.Status__c = "Active"
    and Coverage_End_Date__c >= TODAY()

Decision: Covered?
    No  → Screen: warn the agent this will be a chargeable repair
          Checkbox: "Customer accepts chargeable repair"
    Yes → continue

Screen 2: Fault details
    Picklist: fault category
    Custom LWC: fault code selector, filtered by the asset's product line
    Long text: description
    File upload: photographs

Screen 3: Confirm
    Display text summarizing everything captured
    Checkbox: "I have confirmed these details with the customer"

Create Records: Warranty_Claim__c
Create Records: attach uploaded files
Screen 4: Confirmation with the claim number
```

The confirmation screen before the create is worth including in any flow that writes data. It costs the user one click and prevents a class of mistake that is expensive to unwind.

## Performance and the user

Screen flows run on the server. Every screen transition is a round trip, and every Get Records between screens adds to it.

Practical implications:

**Fewer screens is faster.** Conditional visibility within one screen beats four screens with branching.

**Do lookups once.** A Get Records in a loop between screens is as bad here as anywhere.

**Avoid heavy work between screens.** A user waiting three seconds after every Next will stop using the flow.

**Consider an LWC for anything highly interactive.** A flow screen cannot do client-side filtering, live search, or instant feedback without a round trip. When the interaction needs to feel immediate, a component is the right tool.

## Screen flow versus Lightning Web Component

The honest comparison, since this is a real decision.

**Screen flow** is faster to build, admin-maintainable, needs no test coverage, and gets accessibility and responsive layout for free. It is constrained to server round trips, limited layout control, and a fixed component set.

**LWC** gives full control over layout, interaction, and client-side behaviour, with no round trip for anything computed locally. It costs development time, tests, and a deployment cycle for every change.

The pattern that gets the best of both: **a screen flow as the container, with custom LWCs for the interactive parts.** The admin owns the process flow and the branching; the developer owns the two screens that need real interactivity.

## Error handling

A screen flow that fails shows the user a generic error, which is a poor experience when the user is on the phone with a customer.

Every data element should have a **fault path** leading to a screen that explains what happened in plain language and offers a way forward. See [[07.8 - Flow Error Handling and Fault Paths]].

## Practical guidance

**Name the record variable `recordId`** when launching from a record page.

**Use conditional visibility rather than extra screens.**

**Add a confirmation screen before creating records.**

**Dispatch `FlowAttributeChangeEvent`** from custom screen components, or the flow never sees the value.

**Add fault paths with human-readable messages.**

**Reach for an LWC when the interaction needs to feel instant**, and consider embedding it in the flow rather than replacing the flow.

**Disable Pause on short flows.** Abandoned interviews accumulate.
