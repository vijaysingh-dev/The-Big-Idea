# Threads Processes and Coroutines

#backend #python #concurrency

> **In one line:** Three ways to do more than one thing at once, with three completely different cost models. Pick by asking what you are waiting for and who does the switching.

---

## The Idea

All three let work overlap. The differences are who decides when to switch, and how much each unit of work costs.

| | Process | Thread | Coroutine |
|---|---|---|---|
| **Memory each** | ~10–50 MB | ~8 MB stack reserved, ~50 KB real | ~1–5 KB |
| **Who switches** | OS kernel | OS kernel | Your event loop |
| **Switch cost** | ~10–50 µs | ~1–10 µs | ~0.1 µs |
| **Shares memory?** | No | Yes | Yes |
| **Real parallelism?** | Yes | Not for Python bytecode | No |
| **Practical limit** | Tens | Low thousands | Hundreds of thousands |
| **Switches when** | Anytime | Anytime | Only at `await` |

That last row is the one that matters most in practice, and people skip it.

---

## Preemptive vs Cooperative

**Threads and processes are preemptive.** The OS can pause them anywhere — between two bytecode instructions, halfway through updating a data structure. You get parallel progress for free, and you get data races for free too.

**Coroutines are cooperative.** A coroutine runs until it voluntarily says "I am waiting" via `await`. Nothing interrupts it in between.

```python
# Async: this is atomic. Nothing else runs during it.
async def transfer(a, b, amount):
    a.balance -= amount
    b.balance += amount

# Threads: this can be interrupted between the two lines. Needs a lock.
def transfer(a, b, amount):
    with lock:
        a.balance -= amount
        b.balance += amount
```

💡 **This is async's biggest hidden benefit and it is rarely mentioned.** Whole categories of concurrency bugs simply do not exist, because you know exactly where switches can happen: at `await`, and nowhere else. When you read async code, every `await` is a place where the world may have changed underneath you. Everything between two `await`s is safe.

⚠️ **The flip side is the trap.** Because nothing can interrupt a coroutine, one that does not yield blocks *everything*. See [[01.6 - The Blocking Call Problem]].

## How Each One Actually Works

### Processes

`fork()` (or `spawn()`) gives you a whole separate Python interpreter with its own memory and its own GIL.

```python
from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(cpu_heavy, items))
```

Everything crossing the boundary must be **pickled** — serialized to bytes and rebuilt on the other side.

```
Parent                                  Child
  obj ──► pickle ──► pipe ──► unpickle ──► obj'
```

⚠️ **The serialization cost is usually what kills naive multiprocessing.** Sending a 100MB DataFrame to a worker to do 10ms of work is a loss. Send file paths, IDs or ranges — not data.

Start methods matter:

| Method | Behaviour | Default on |
|---|---|---|
| `fork` | Copies the parent's memory, very fast | Linux (until 3.14, which now defaults to `forkserver`) |
| `spawn` | Fresh interpreter, re-imports everything, slow but safe | macOS, Windows |
| `forkserver` | Forks from a clean minimal process. Safe and fast | Linux 3.14+ |

⚠️ **`fork` in a process that has threads is dangerous.** The child gets the parent's memory including locks — but only the calling thread. A lock held by another thread at fork time stays locked forever in the child, and the child hangs. This is why forking after your app has started a thread pool, a database pool or a logging thread causes mysterious deadlocks, and why 3.14 changed the default.

### Threads

Real OS threads, sharing memory, subject to the GIL for Python bytecode ([[01.2 - The GIL]]).

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=20) as pool:
    results = list(pool.map(fetch_url, urls))
```

Useful for exactly two things:

1. **Blocking I/O** where no async version exists — a legacy SDK, a sync database driver, a `subprocess` call
2. **C code that releases the GIL** — numpy, bcrypt, hashlib, image libraries

⚠️ **A thread's default stack is 8MB of virtual address space.** It is not all committed to physical memory, so 1000 threads does not mean 8GB of RAM — but the kernel scheduling cost and cache pressure are real. Thousands of threads is where thread-per-connection servers fall over. This is the C10k problem, covered in [[02.12 - Event Driven Servers]].

### Coroutines

A coroutine is a function that can pause and resume. Mechanically, it is built on generators — an object holding a frame that you can step forward.

```python
async def fetch(url):
    conn = await connect(url)      # pause here, resume when connected
    data = await conn.read()       # pause here, resume when data arrives
    return data
```

Calling `fetch(url)` runs **nothing**. It creates a coroutine object. Something must drive it — the event loop, via a Task.

```python
coro = fetch(url)          # nothing has happened
task = asyncio.create_task(coro)   # now the loop will drive it
result = await task
```

The mechanism is covered fully in [[01.5 - Coroutines Tasks and Futures]] and you build one in [[01.4 - Building an Event Loop From Scratch]].

Cost: an asyncio Task is a few KB. A hundred thousand of them on one thread is completely normal. This is why one Python process can hold 50,000 WebSocket connections and a thread-per-connection design cannot.

## The Decision

Ask three questions in order.

```
1. Is the work waiting on something outside this process?
   (network, disk, database, another service)
        │
        ├── YES ──► 2. Is there an async library for it?
        │              ├── YES ──► COROUTINES
        │              └── NO  ──► THREAD POOL
        │
        └── NO ───► 3. Does it release the GIL?
                       (numpy, bcrypt, hashlib, image libs, Rust ext)
                       ├── YES ──► THREAD POOL
                       └── NO  ──► PROCESS POOL
                                   (and first ask: should this be
                                    in a task queue instead?)
```

The bracket on the last line matters. Most "I need multiprocessing" problems in a web service are really "this should not be in the request path at all" problems. See [[08.1 - Why Background Work Exists]].

### Concrete mapping

| Work | Answer | Why |
|---|---|---|
| Call 50 HTTP APIs | Coroutines | httpx is async, pure waiting |
| Query Postgres | Coroutines | asyncpg exists |
| Call a legacy SOAP SDK with no async support | Thread pool | Blocking, no alternative |
| Hash a password | Thread pool | bcrypt releases the GIL |
| Resize 1000 images | Process pool, or better a task queue | Pillow is partly GIL-holding, and it does not belong in a request |
| Parse a 200MB CSV | Process pool, or polars in a thread | Pure Python parsing holds the GIL; polars releases it |
| Serve 50,000 WebSocket connections | Coroutines | Only model with the right memory cost |
| Train a model | Neither — a different machine | |

## In Production

### The standard Python service shape

```
Container (2 CPU limit)
├── uvicorn worker (process)
│   ├── event loop ──── thousands of coroutines
│   └── anyio thread pool (40 threads) ──── blocking calls
└── uvicorn worker (process)
    ├── event loop
    └── thread pool
```

All three models, each doing what it is good at. This is not a compromise — it is the correct design.

### Sizing each layer

**Processes:** number of CPU cores available *to your container*, not to the host.

```python
import os
# Respects cgroup limits on Linux; os.cpu_count() does not
workers = len(os.sched_getaffinity(0))
```

Or read the cgroup quota directly. Simplest and safest: set it explicitly from an environment variable and let your deployment config decide.

**Threads:** default in Starlette/FastAPI is 40, via anyio's capacity limiter.

```python
import anyio.to_thread
limiter = anyio.to_thread.current_default_thread_limiter()
limiter.total_tokens = 100
```

⚠️ **This 40-thread limit catches people out constantly.** If you write `def` endpoints instead of `async def` in FastAPI, every request runs in that thread pool. At 41 concurrent requests, request 41 queues — with no error, no log line, just latency. Your service looks like it has a slow database when it actually has a full thread pool. Symptom: p99 latency climbs sharply at a specific concurrency number and stays flat below it.

**Coroutines:** limit them yourself with a semaphore, or you will open 10,000 connections to a service that can handle 100.

```python
sem = asyncio.Semaphore(50)

async def fetch(url):
    async with sem:
        return await client.get(url)
```

Covered fully in [[01.11 - Backpressure Inside One Process]].

### The mixing rules

| Rule | Why |
|---|---|
| Never call blocking code directly in a coroutine | Freezes the whole loop |
| Never fork after starting threads | Inherited locks deadlock the child |
| Never share a database connection across processes | Sockets do not survive fork correctly |
| Never create an event loop per thread and expect them to talk | Use `asyncio.run_coroutine_threadsafe` explicitly |
| Never assume `cpu_count()` is your CPU count | Containers lie |

### A story you will see

A team has a FastAPI service. Latency is fine at 30 requests per second and terrible at 50. They add more replicas. It does not help. They blame the database.

The real cause: one endpoint is `def` not `async def`, and it calls a slow third-party API. Each call occupies a thread for 2 seconds. At 20 concurrent calls to that endpoint, 20 of 40 threads are gone. At 40, the pool is full — and now *every* `def` endpoint in the whole service queues behind it, including healthy fast ones.

The fix is one word: `async`. Finding it requires knowing that the thread pool exists, is shared, and is 40 wide.

**Drill 1.2 — Same job, four ways**

One task, four concurrency models, one benchmark harness, real numbers.

```
drills/01-four-ways/
```

### Part 1 — The matrix

4 workloads × 4 models × concurrency levels (1, 4, 16, 64, 256, 1024). Measure wall time, peak RSS, and CPU utilisation.

Before running each cell, **write down your prediction**. Then compare. The cells where you were wrong are the ones worth thinking about.

### Part 2 — Find the cliffs

For each model, find the concurrency level where it falls apart, and identify *what* broke:

| Model | Expect to find |
|---|---|
| Threads | Memory and scheduling cost climbing; a specific number where p99 jumps |
| Processes | Memory wall much earlier; startup cost dominating for short tasks |
| Asyncio | File descriptor limits before anything else. Raise them and find the next wall |

### Part 3 — Reproduce the thread pool incident

```
drills/01-four-ways/incident/
├── app.py          # FastAPI: 3 fast async endpoints, 1 slow `def` endpoint
├── load.js         # k6: steady load on the fast endpoints
├── poison.js       # k6: ramping load on the slow one
└── FINDINGS.md
```

Run steady load on the fast endpoints and record p99. Now ramp the slow `def` endpoint. Watch the **fast** endpoints degrade even though they touch nothing in common.

Then change one word — `def` to `async def` with `httpx` — and rerun.

**Done when:** you have a chart showing fast-endpoint p99 versus concurrency on the slow endpoint, with the cliff at 40 clearly visible, and the same chart after the fix showing no cliff.

This is the most valuable drill in section 01. It is a real production incident, reproduced on your laptop in 20 lines.
