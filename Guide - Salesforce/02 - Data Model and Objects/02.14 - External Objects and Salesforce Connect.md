# External Objects and Salesforce Connect

## The idea

An external object looks like a normal object in the user interface, in SOQL, and in Apex. But it stores nothing in Salesforce.

When someone opens a list of external records, Salesforce makes a live call to another system, receives the results, and renders them. Close the page and nothing was stored.

The feature that makes this work is **Salesforce Connect**, and external objects use the `__x` suffix.

## Why this exists

Three recurring situations.

**The data is enormous.** Twelve years of invoice history in an ERP is hundreds of millions of rows. Copying it into Salesforce would consume storage you cannot afford and create a synchronization problem forever.

**The data must stay where it is.** Regulatory or contractual requirements sometimes prohibit copying customer data into another system, particularly across jurisdictions.

**The data changes constantly and must be current.** Stock levels, shipment tracking, account balances. Any sync has latency, and for some data that latency is unacceptable.

In all three, the alternative — a nightly sync copying data in — is worse: storage cost, staleness, sync failures, and reconciliation work.

## The adapters

Salesforce Connect supports several ways of reaching the external system.

**OData 2.0 and 4.0.** The standard option. If the external system exposes an OData service, connect directly with configuration and no code. Many enterprise systems either expose OData natively or can be fronted by middleware that does.

**Cross-org adapter.** Reads data from another Salesforce org. Useful for large organizations with several orgs that need to see each other's data without merging.

**Custom Apex adapter.** You write a class extending `DataSource.Connection`, and you can front any API at all — REST, SOAP, GraphQL, a legacy service. This is the flexible option and the one that requires real work.

A minimal shape of a custom adapter, to make the mechanism concrete:

```java
global class ErpInvoiceConnection extends DataSource.Connection {

    global override List<DataSource.Table> sync() {
        List<DataSource.Column> columns = new List<DataSource.Column>{
            DataSource.Column.text('ExternalId', 255),
            DataSource.Column.url('DisplayUrl'),
            DataSource.Column.text('InvoiceNumber', 64),
            DataSource.Column.number('Amount', 16, 2),
            DataSource.Column.text('AccountErpId', 64),
            DataSource.Column.get('InvoiceDate', 'Invoice Date', DataSource.DataType.DATE_TYPE)
        };
        return new List<DataSource.Table>{
            DataSource.Table.get('ErpInvoice', 'InvoiceNumber', columns)
        };
    }

    global override DataSource.TableResult query(DataSource.QueryContext context) {
        // the framework hands you the parsed filter so it can be pushed to the source system
        String accountFilter = extractAccountFilter(context);
        List<Map<String, Object>> rows = ErpInvoiceClient.fetchInvoices(accountFilter);
        return DataSource.TableResult.get(context, rows);
    }
}
```

`ExternalId` and `DisplayUrl` are mandatory columns. `ExternalId` is the record's identifier in the source system, and `DisplayUrl` is where clicking through takes the user.

The important design point is in the `query` method: you should push filters down to the external system rather than fetching everything and filtering in Apex. A naive adapter that ignores the filter context will fetch far too much and be unusably slow.

## Connecting external objects to real ones

Two special relationship types exist for this.

**External lookup.** A field on a Salesforce object pointing at an external object, matched on the external object's `ExternalId`. Example: a Case pointing at an ERP invoice.

**Indirect lookup.** A field on an external object pointing at a Salesforce object, matched on a Salesforce external ID field rather than on the record Id. This is the one you need most often, because the external system stores its own key, not a Salesforce ID.

Example: ERP invoices carry an `AccountErpId`. Your Account has `ERP_Account_Id__c` marked as an external ID. An indirect lookup joins them, and now every Account record shows a related list of live ERP invoices.

This is where the feature genuinely earns its place. A support agent sees the customer's real invoice history on the account page, pulled live, with no copy and no sync.

## Querying them

They appear in SOQL and Apex like any other object:

```sql
SELECT ExternalId, InvoiceNumber__c, Amount__c, Invoice_Date__c
FROM ErpInvoice__x
WHERE Account__r.ERP_Account_Id__c = 'ACC-4471'
ORDER BY Invoice_Date__c DESC
LIMIT 50
```

```java
List<ErpInvoice__x> invoices = [
    SELECT ExternalId, InvoiceNumber__c, Amount__c
    FROM ErpInvoice__x
    WHERE Account__r.ERP_Account_Id__c = :erpAccountId
    LIMIT 100
];
```

Every one of those queries is a live HTTP call to the external system. That is the thing to hold in mind constantly.

## The limitations, which are substantial

Be clear-eyed about these, because they decide whether external objects fit a requirement.

- **No triggers**, and only limited flow support
- **No roll-up summaries** in either direction
- **No field history tracking**
- **No standard reports** in most cases; reporting on external objects is heavily restricted
- **Limited search**; external objects are largely absent from global search
- **No validation rules**
- **Writes are supported** with OData 4.0 and custom adapters, but with restrictions and no transactional guarantee
- **Query performance depends entirely on the external system**, and a slow source makes a slow page
- **Callout limits apply**, so pages showing many external records can exhaust them
- **Joins between external and Salesforce objects are limited** and often push filtering to the wrong side

The pattern that emerges: external objects are excellent for **displaying** related data and poor for anything that needs to be **processed, aggregated, or reported on**.

## Deciding between external objects and syncing

| Consideration | External objects | Sync into Salesforce |
| --- | --- | --- |
| Storage cost | None | Full |
| Data currency | Live | As fresh as the last sync |
| Reporting | Very limited | Full |
| Automation, roll-ups | Not available | Full |
| Offline and mobile | Not available | Available |
| Failure mode | Page shows an error when source is down | Data is stale but present |
| Volume ceiling | Effectively unlimited | Storage-bound |

A pattern many enterprise orgs settle on: **sync a small summary, link the detail.** Copy in aggregate figures that need reporting and automation — total invoiced this year, outstanding balance — and expose the individual invoice records as external objects for reference. You get reportable numbers without storing millions of rows.

## Operational notes

**Authentication uses Named Credentials**, so credentials are not embedded in configuration or code. See [[13.13 - Named Credentials and External Credentials]].

**Failure handling is limited.** If the external system is unavailable, the related list shows an error. There is no caching layer and no graceful degradation, so an unreliable source produces a visibly unreliable Salesforce page. This alone rules the feature out for some sources.

**Licensing.** Salesforce Connect is a paid add-on, priced by the number of external data sources and calls. This is frequently the deciding factor, so establish it early.

**Big objects are a different answer to a related question.** If the data is high-volume but you do own it and it must live in Salesforce, that is a big object, not an external object. See [[02.15 - Big Objects]].
