# Positioning and Stacking Contexts

## The five position values

```css
position: static;    /* default — in normal flow, ignores top/left/z-index */
position: relative;  /* offset from its normal position, space still reserved */
position: absolute;  /* removed from flow, positioned against nearest positioned ancestor */
position: fixed;     /* removed from flow, positioned against the viewport */
position: sticky;    /* relative until a scroll threshold, then fixed within its container */
```

`relative` is used more often as an anchor for absolutely-positioned children than for its own offset.

## The containing block

An absolutely positioned element positions itself against its **containing block** — the nearest ancestor that is not `static`. If none exists, it falls back to the initial containing block (roughly the viewport).

```css
.parent { position: relative; }
.child {
  position: absolute;
  inset: 0;              /* shorthand for top/right/bottom/left: 0 */
}
```

`inset: 0` with `position: absolute` makes an element fill its containing block — the standard overlay pattern.

The critical exception for `fixed`: it normally positions against the viewport, **but** any ancestor with `transform`, `filter`, `perspective`, `backdrop-filter`, `contain: paint`, or `will-change` on one of those creates a containing block for fixed descendants.

```css
.animated-wrapper { transform: translateZ(0); }
.modal { position: fixed; }   /* now positioned against .animated-wrapper, not the viewport */
```

This is the reason a fixed modal or dropdown sometimes appears in the wrong place or gets clipped, and it is one of the hardest CSS bugs to diagnose without knowing the rule. The usual fix is a portal that renders outside the transformed subtree ([[22.2 - Portals]]).

## Sticky

```css
.header {
  position: sticky;
  top: 0;
  z-index: 10;
}
```

Three requirements people miss:

1. **At least one of `top`/`right`/`bottom`/`left` must be set.** Without a threshold, sticky does nothing.
2. **The parent must be taller than the sticky element**, and the element sticks only within its parent's box. It "unsticks" when the parent scrolls out.
3. **No ancestor may have `overflow: hidden`, `scroll` or `auto`** — that ancestor becomes the scroll container and sticky behaves relative to it, usually invisibly.

The `overflow: hidden` ancestor is the overwhelmingly common cause of "sticky isn't working". Note the parent does not need `overflow: visible` explicitly; it just must not have anything else.

Sticky table headers need it on `<th>` rather than `<thead>` in some browsers, and `border-collapse: separate` for borders to render correctly.

## z-index and stacking contexts

`z-index` only works on positioned elements (and flex/grid children). More importantly, it is **scoped to a stacking context**.

A stacking context is created by:

- the root element
- `position` other than `static` **with** a `z-index` other than `auto`
- `position: fixed` or `sticky` (always, regardless of z-index)
- `opacity` less than 1
- `transform`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask`
- `mix-blend-mode` other than `normal`
- `isolation: isolate`
- `will-change` on any of the above
- `contain: paint` or `contain: strict`
- a flex or grid item with a `z-index` other than `auto`

Inside a stacking context, children are painted relative to each other only. A child with `z-index: 999999` cannot escape a parent whose context sits below another:

```css
.a { position: relative; z-index: 1; }
.a .child { position: relative; z-index: 9999; }
.b { position: relative; z-index: 2; }
/* .b paints above .child, always */
```

This is the second-hardest CSS bug to diagnose, and the answer is never "increase z-index" — it is "find which ancestor created the stacking context".

The `opacity: 0.99` trick some codebases use to force GPU compositing silently creates a stacking context, which is a frequent accidental cause.

## Painting order within a context

From back to front:

1. The stacking context's own background and borders
2. Negative `z-index` children
3. Block-level, non-positioned descendants
4. Floats
5. Inline content
6. `z-index: 0` or `auto` positioned elements
7. Positive `z-index` children, in ascending order

Note that a `z-index: -1` child paints *behind* its parent's content but in front of its parent's background — which is how decorative pseudo-element backgrounds are layered.

## isolation

```css
.card { isolation: isolate; }
```

Creates a stacking context without any side effects — no opacity change, no transform, no compositing layer. Useful for containing a component's `z-index` values so they cannot interfere with the rest of the page.

This is the right tool for component libraries: each component isolates itself, and internal z-index values become local.

## Managing z-index at scale

Arbitrary numbers scattered across a codebase produce the familiar escalation to `z-index: 99999`. The fix is a declared scale:

```css
:root {
  --z-base: 0;
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-overlay: 300;
  --z-modal: 400;
  --z-toast: 500;
  --z-tooltip: 600;
}
```

Combined with portals for anything that must escape its parent, and `isolation: isolate` on components, this eliminates most z-index problems structurally.

## Modern alternatives

**`<dialog>` and the top layer.** An element opened with `showModal()` renders in the browser's **top layer**, above everything on the page regardless of z-index or stacking contexts. Same for the Popover API and fullscreen elements. This sidesteps the entire problem:

```html
<dialog id="modal">...</dialog>
<script>modal.showModal();</script>
```

```css
dialog::backdrop { background: rgb(0 0 0 / 0.5); }
```

**CSS anchor positioning** lets a popover position itself against an arbitrary element without JavaScript measurement:

```css
.tooltip {
  position: absolute;
  position-anchor: --trigger;
  top: anchor(bottom);
  left: anchor(center);
}
```

Support is still rolling out, but it replaces libraries like Floating UI for simple cases.

## How senior engineers actually use this

**They portal anything that must escape.** Modals, dropdowns, tooltips and toasts render at the document root, which avoids both stacking context traps and `overflow: hidden` clipping ([[22.2 - Portals]]).

**They prefer `<dialog>` and popover for overlays.** Top-layer rendering, focus trapping and Escape handling for free.

**They use `isolation: isolate` on components** so internal layering cannot leak.

**They debug stacking with DevTools' Layers panel**, and by checking every ancestor for the properties that create a context. The question is always "which ancestor made a context", never "what number is high enough".

## Common pitfalls

- `position: fixed` breaking because an ancestor has a `transform`.
- Sticky failing because an ancestor has `overflow: hidden`.
- Sticky with no offset value set.
- z-index escalation instead of finding the responsible stacking context.
- `opacity: 0.99` or `will-change` accidentally creating a context.
- Assuming `z-index` works on static elements.
- A dropdown clipped by a parent's `overflow: hidden` — position cannot fix this; a portal can.

## Interview angle

"Explain z-index and stacking contexts" is the question, and the distinguishing answer covers what *creates* a stacking context beyond `position` + `z-index` — opacity, transform, filter, will-change — and the fact that a child cannot escape its parent's context no matter how large its z-index. The `transform` breaking `position: fixed` interaction is a strong practical detail. Mentioning the top layer via `<dialog>` shows current knowledge.
