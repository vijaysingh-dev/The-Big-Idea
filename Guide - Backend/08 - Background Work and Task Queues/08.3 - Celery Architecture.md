# Celery Architecture

#backend #queues #celery #python

> **In one line:** A function call becomes a serialised message on a broker, a worker process pulls it, hands it to a pool of child processes, and acknowledges it — and every Celery surprise comes from one of those four steps behaving differently than you assumed.

---

## The Idea

```
your code                broker                  worker
    │                       │                       │
    │  task.delay(doc_id)   │                       │
    ├──── serialise ───────►│                       │
    │                       │◄──── prefetch ────────┤  consumer thread
    │                       │                       │
    │                       │                  ┌────▼────┐
    │                       │                  │  pool   │  prefork children
    │                       │                  └────┬────┘
    │                       │◄──── ack ─────────────┤
```

Four components, and knowing which one is misbehaving is most of Celery debugging.

| Component | Job |
|---|---|
| **Client** | Serialises the call into a message and publishes it |
| **Broker** | Holds messages. Redis, RabbitMQ, SQS |
| **Worker** | A supervisor process: consumes, dispatches to the pool, acks |
| **Pool** | Child processes (or threads, or greenlets) that execute the task |
| **Result backend** | Optional. Stores return values and state |

---

## What `.delay()` Actually Does

```python
process_document.delay(doc_id="doc_42")
```

```json
{
  "body": "base64(json([[], {"doc_id": "doc_42"}, {...}]))",
  "content-type": "application/json",
  "headers": {
    "id": "8f3c...",
    "task": "app.tasks.process_document",
    "retries": 0,
    "eta": null,
    "expires": null,
    "root_id": "8f3c...",
    "parent_id": null,
    "group": null
  },
  "properties": {
    "correlation_id": "8f3c...",
    "delivery_mode": 2,
    "delivery_info": {"exchange": "", "routing_key": "celery"}
  }
}
```

💡 **The task name is a string.** The worker looks it up in its registry. **This means the client and worker do not need to share code** — but it also means a typo, a renamed task, or a worker running an older deploy produces `Received unregistered task of type`.

⚠️ **`.delay()` returns immediately and does not guarantee the message reached the broker** unless publisher confirms are enabled. See the enqueue gap in [[08.2 - Queue Semantics]].

### `.delay()` versus `.apply_async()`

```python
task.delay(doc_id)                              # convenience

task.apply_async(
    kwargs={"doc_id": doc_id},
    queue="ingestion",
    countdown=30,                               # delay execution
    expires=3600,                               # discard if not started in time
    priority=5,
    retry=True,
    retry_policy={"max_retries": 3},            # publishing retries, not task retries
)
```

💡 **`expires` is underused and valuable.** A task that has been queued for an hour is often no longer worth running — a stale cache refresh, a notification about something already superseded. **Expiring it is better than executing it late.**

⚠️ **`retry_policy` here is about retrying the *publish*, not the task.** Two different retry concepts with confusingly similar names.

## The Worker

```bash
celery -A app worker \
    --loglevel=info \
    --concurrency=4 \
    --pool=prefork \
    --prefetch-multiplier=1 \
    --max-tasks-per-child=100 \
    --queues=default,ingestion \
    --hostname=worker@%h
```

### The main process is a supervisor

The worker process itself does not execute tasks. It runs a **blueprint** of components:

```
Consumer     connects to the broker, receives messages
  ├── Tasks      dispatches to the pool
  ├── Heartbeat  keeps the broker connection alive
  ├── Gossip     worker-to-worker state (RabbitMQ only)
  ├── Mingle     sync state with other workers at startup
  └── Events     emit monitoring events
```

⚠️ **Gossip, mingle and events cost real overhead and are often unnecessary.**

```bash
celery worker --without-gossip --without-mingle --without-heartbeat
```

💡 **Disabling them is a common production optimisation**, particularly with many workers, where gossip traffic grows quadratically. Keep events if you use Flower.

### The pool

| Pool | Concurrency via | Use for |
|---|---|---|
| **prefork** | Child processes | CPU-bound work. **The default** |
| **threads** | Threads | I/O-bound with blocking libraries |
| **gevent** / **eventlet** | Greenlets | High-concurrency I/O |
| **solo** | None, in-process | Debugging |

```bash
--pool=prefork --concurrency=4       # 4 child processes
--pool=gevent --concurrency=1000     # 1000 greenlets, 1 process
```

💡 **The pool choice follows the same logic as [[01.3 - Threads Processes and Coroutines]]:** CPU work needs processes because of the GIL; I/O work is better served by greenlets, which cost kilobytes rather than megabytes.

⚠️ **gevent monkey-patches the standard library**, which can break libraries using native threads or C extensions that block. **Patch as the very first thing in your entry point**, before any other import:

```python
from gevent import monkey; monkey.patch_all()
```

⚠️ **Celery does not natively support asyncio.** An `async def` task is not awaited by the worker. You must wrap it:

```python
@app.task
def process_document(doc_id: str):
    return asyncio.run(_process_document(doc_id))
```

This creates a new event loop per task, so connection pools cannot be shared across tasks. **This is the single most awkward thing about Celery in an async codebase**, and it is why arq and Dramatiq are worth evaluating ([[08.10 - Celery vs Dramatiq vs arq vs Temporal]]).

## Prefetch

The setting that causes the most confusing production behaviour.

```
prefetch_count = concurrency × prefetch_multiplier
```

```bash
--concurrency=4 --prefetch-multiplier=4      # 16 messages reserved at once
```

⚠️ **The worker reserves 16 messages even though it can only run 4.** The other 12 sit in the worker's memory, unavailable to any other worker.

```
Worker A: reserves 16 messages, each taking 10 minutes
Worker B: idle, nothing left in the queue
```

💡 **This is the single most common Celery misconfiguration.** With the default multiplier of 4 and long tasks, work distributes terribly — one worker hoards while others starve.

```bash
--prefetch-multiplier=1          # for long tasks
```

| Task duration | Multiplier |
|---|---|
| Milliseconds | 4–16. Prefetch amortises broker round trips |
| Seconds | 1–2 |
| **Minutes** | **1** |
| Mixed | **Separate queues** ([[08.7 - Routing Queues Priorities and Prefetch]]) |

⚠️ **`acks_late=True` plus a high prefetch is particularly bad**, because reserved-but-unstarted messages are held unacknowledged, so a worker crash requeues all sixteen — including the twelve it never began.

## Acknowledgement

```python
@app.task(acks_late=True, reject_on_worker_lost=True)
def process_document(doc_id: str): ...
```

| Setting | Default | Meaning |
|---|---|---|
| `acks_late` | **`False`** | Ack on receipt, before execution |
| `reject_on_worker_lost` | `False` | Requeue if the worker died abruptly |

⚠️ **The default is at-most-once.** A worker killed by the OOM killer, a `SIGKILL`, or a node eviction loses every task it had received.

💡 **Set `acks_late=True` for anything that matters, and accept at-least-once** — which means every such task must be idempotent ([[07.5 - Idempotency Keys and Deduplication]]).

⚠️ **`reject_on_worker_lost` without idempotency is dangerous**: a task that was killed by the OOM killer *because of what it was doing* will be redelivered and kill the next worker too. That is a crash loop consuming your whole fleet.

**Guard against it with `max_retries` and a DLQ** ([[08.6 - Retries Backoff and Dead Letters]]).

## The Result Backend

```python
result = process_document.delay(doc_id)
result.get(timeout=30)          # ⚠️ blocks
```

⚠️ **Calling `.get()` inside a task is a deadlock risk** — the task occupies a pool slot while waiting for another task that may need that slot. Celery warns about it, and the warning is correct.

💡 **In most systems you do not need a result backend at all.** Fire-and-forget tasks that write their results to your database are simpler, and the database is a better place for state than a Redis key with a TTL.

```python
app.conf.task_ignore_result = True
```

**Turn results off by default and enable them per-task where genuinely needed.** Every stored result is a Redis write plus a key that must expire.

⚠️ **Results in Redis with `allkeys-lru` eviction can be evicted before they are read** ([[07.2 - Cache Strategies and Invalidation]]). Another reason to prefer your own database.

## Task State

```
PENDING   → unknown. Celery cannot distinguish "queued" from "never existed"
STARTED   → only if task_track_started=True
SUCCESS
FAILURE
RETRY
REVOKED
```

⚠️ **`PENDING` is the trap.** Celery has no record of a task until a worker starts it, so an invalid task ID returns `PENDING` forever, indistinguishable from a queued task.

💡 **Never expose Celery task state to users.** Model the operation in your own database ([[08.1 - Why Background Work Exists]]) where you control the states and can distinguish "queued", "does not exist" and "failed permanently".

## Canvas: Composing Tasks

```python
from celery import chain, group, chord

chain(extract.s(doc_id), chunk.s(), embed.s(), index.s())()

group(send_email.s(uid) for uid in user_ids)()

chord(
    (process_chunk.s(c) for c in chunks),
    finalise.s(doc_id),
)()
```

| Primitive | |
|---|---|
| `chain` | Sequential; each result feeds the next |
| `group` | Parallel |
| `chord` | A group with a callback when all complete |
| `chunks` | Split a large group into batches |

⚠️ **Chords require a result backend and are genuinely fragile.** The callback fires when the backend observes all results, and with Redis this involves a counter that can be lost. **Chord failures are a well-known source of tasks that never complete.**

💡 **For anything beyond a simple chain, track state in your own database instead.** A `documents_processed / documents_total` counter that a final task checks is more robust than a chord, easier to debug, and visible in your admin interface.

**Reach for a real workflow engine when you need genuine orchestration** ([[08.11 - Durable Workflows and Sagas]]).

## In Production

### The configuration that matters

```python
app.conf.update(
    # Reliability
    task_acks_late=True,
    task_reject_on_worker_lost=True,
    broker_connection_retry_on_startup=True,

    # Prefetch
    worker_prefetch_multiplier=1,

    # Memory
    worker_max_tasks_per_child=100,
    worker_max_memory_per_child=200_000,        # KB

    # Results
    task_ignore_result=True,
    result_expires=3600,

    # Serialisation
    task_serializer="json",
    accept_content=["json"],                     # ⚠️ never pickle

    # Time limits
    task_time_limit=600,                         # SIGKILL
    task_soft_time_limit=540,                    # raises SoftTimeLimitExceeded

    # Routing
    task_default_queue="default",
    task_routes={"app.tasks.index_*": {"queue": "indexing"}},
)
```

⚠️ **`accept_content=["json"]` is a security requirement.** Celery historically defaulted to pickle, and **a pickle deserialiser executes arbitrary code**. Anyone who can write to your broker can run code on your workers. Never enable it.

💡 **`worker_max_tasks_per_child` is a blunt but effective defence against memory leaks.** A child process is recycled after N tasks, releasing whatever it accumulated. It is not a fix for a leak; it is a way to survive one you have not found yet.

### Soft and hard time limits

```python
@app.task(soft_time_limit=300, time_limit=360)
def process_document(doc_id: str):
    try:
        ...
    except SoftTimeLimitExceeded:
        await mark_incomplete(doc_id)      # cleanup, then let it die
        raise
```

💡 **The soft limit raises an exception you can catch; the hard limit kills the process.** Always set the soft limit lower, so you get a chance to record what happened.

⚠️ **Time limits only work with the prefork pool.** With gevent or threads, there is no way to interrupt a running task — so a hung task in a gevent worker occupies a greenlet forever.

### Graceful shutdown

```
SIGTERM  → stop consuming, finish in-flight tasks, exit  (warm shutdown)
SIGQUIT  → terminate immediately                          (cold shutdown)
```

```yaml
# Kubernetes
terminationGracePeriodSeconds: 660      # longer than task_time_limit
```

⚠️ **If `terminationGracePeriodSeconds` is shorter than your longest task, Kubernetes `SIGKILL`s the worker mid-task on every deploy.** With `acks_late` those tasks are requeued, so nothing is lost — but you are redoing work on every rollout.

**Set the grace period longer than your hard time limit**, and split long tasks so the grace period can be short ([[11.7 - Graceful Shutdown and Draining]]).

### Monitoring

```bash
celery -A app inspect active          # what is running now
celery -A app inspect reserved        # prefetched but not started
celery -A app inspect stats
celery -A app inspect registered
```

```python
task_started_total.labels(task=name, queue=queue).inc()
task_duration_seconds.labels(task=name).observe(elapsed)
task_failures_total.labels(task=name, exception=type).inc()
task_retries_total.labels(task=name).inc()
queue_depth.labels(queue=name).set(depth)
worker_pool_available.labels(worker=name).set(free_slots)
```

💡 **`inspect reserved` is the command that reveals prefetch problems.** If one worker has 40 reserved tasks and others have none, your multiplier is too high.

⚠️ **Flower is convenient and not a monitoring system.** It holds state in memory, does not persist, and does not alert. Use it for interactive inspection; use Prometheus for alerting.

### The signals worth using

```python
from celery.signals import task_prerun, task_postrun, task_failure

@task_prerun.connect
def add_context(task_id, task, *args, **kwargs):
    structlog.contextvars.bind_contextvars(task_id=task_id, task_name=task.name)

@task_failure.connect
def report(task_id, exception, traceback, einfo, **kwargs):
    sentry_sdk.capture_exception(exception)
```

💡 **Signals are how you get request-ID propagation and tracing into tasks.** Without them, a trace that spans a request and its background work is broken at the queue boundary ([[12.3 - Instrumenting Conduit End to End]]).

## Codebase

**Repo:** `celery/celery`, `celery/kombu`

**Question to answer:** Trace one `task.delay()` from the client call to the task function executing in a child process. Where exactly is the message acknowledged, and how does that differ with `acks_late`?

**Read, in order:**

1. `celery/celery/app/task.py` — `Task.delay` and `apply_async`. **How a call becomes a message**
2. `celery/celery/app/amqp.py` — `as_task_v2`. **The message format**, matching the JSON above
3. `celery/celery/worker/consumer/consumer.py` — the worker's main loop and the blueprint of components. **Find where messages arrive and are dispatched**
4. `celery/celery/worker/request.py` — **`Request.on_accepted`, `on_success`, `on_failure`, and `acknowledge`.** **This is the answer to the question**: with `acks_late=False` the ack happens in `on_accepted`; with `acks_late=True` it happens in `on_success`/`on_failure`
5. `celery/celery/concurrency/prefork.py` — how a task reaches a child process, via billiard
6. `kombu/kombu/transport/redis.py` — the visibility timeout emulation from [[08.2 - Queue Semantics]]

💡 `request.py` is the file to read carefully. **Every question about "will my task be lost if X happens" is answered by where the acknowledge call sits relative to the failure**, and this file is where that decision lives. It is under 800 lines and it repays the time.

**Size:** 2–3 sessions.

**Part 1 — See the message.** Enqueue a task, then read the raw message off Redis or RabbitMQ before a worker consumes it.

**Annotate every field.** Then construct a message by hand, publish it directly, and have a worker execute it — confirming the client is not special.

Then send a message for an unregistered task name and observe the error. Then send one with malformed arguments.

**Part 2 — Pool comparison.** Three workloads (CPU-bound, blocking I/O, async I/O wrapped in `asyncio.run`) × four pools.

Measure throughput, memory, and per-task latency.

**Confirm prefork wins on CPU and gevent wins on I/O.** Then measure the cost of `asyncio.run` per task — creating an event loop and a connection pool every time — and quantify what you lose versus a natively-async worker.

**Part 3 — Prefetch hoarding.** Two workers, `concurrency=2`, `prefetch_multiplier=4`. Enqueue 20 tasks each taking 30 seconds.

**Use `inspect reserved` to show one worker holding 16 tasks while the other has 4.**

Chart total completion time against multiplier values 1, 2, 4, 8, 16 for long tasks and for short tasks.

**The two curves should point in opposite directions.** That contrast is the whole prefetch lesson.

**Part 4 — The ack matrix.** Kill a worker with `SIGKILL` at four points: after receive before start, mid-task, after task before ack, after ack.

Run against `acks_late=False`, `acks_late=True`, and `acks_late=True` with `reject_on_worker_lost=True`.

**Twelve cells.** Record lost, duplicated, or exactly-once for each.

Then simulate an OOM kill on a task that always OOMs, with `reject_on_worker_lost=True`. **Confirm the crash loop consuming your workers**, then fix it with `max_retries`.

**Part 5 — Time limits and memory.** A task that hangs forever, with soft and hard limits set.

Confirm the soft limit raises catchably and the hard limit kills. Then try the same with the gevent pool and **confirm the limits do not work.**

Then a task that leaks 10MB per run. Chart worker RSS over 500 tasks with and without `max_tasks_per_child`.

**Part 6 — Break a chord.** A chord over 100 tasks with a callback.

Kill Redis briefly mid-execution. **Confirm the callback never fires** and the chord hangs indefinitely.

Then implement the same coordination with a database counter and a final check, and confirm it survives the same failure.

**Write in `COMPARISON.md` when you would use canvas primitives and when you would not.**

**Part 7 — Shutdown.** A worker running 60-second tasks with `terminationGracePeriodSeconds` set to 30.

**Confirm tasks are killed mid-execution on every deploy** and requeued with `acks_late`. Measure the wasted work per rollout.

Then set the grace period correctly and confirm zero rework.

**Done when:**
- You have published a hand-constructed message that a worker executed
- Your pool comparison quantifies the `asyncio.run` overhead
- Your prefetch charts point in opposite directions for long and short tasks
- The twelve-cell ack matrix is complete
- You reproduced an OOM crash loop and stopped it
- A chord failed and your database-state alternative did not
- You measured wasted work from an incorrect grace period
