# Celery in Production

#backend #queues #celery #operations

> **In one line:** Workers leak memory, hang on network calls, die during deploys and fail silently — this note is the operational discipline that turns those from incidents into non-events.

---

## The Idea

Everything so far has been design. This is what breaks after it is running.

| Symptom | Usually |
|---|---|
| Worker memory climbs until OOM | A leak, or unbounded prefetch |
| Tasks stop being processed | Broker connection lost, or the worker is wedged |
| Queue depth grows with idle workers | Prefetch hoarding, or no consumer on that queue |
| Every deploy loses work | Grace period shorter than task duration |
| Failures nobody noticed for a week | No alerting on the DLQ |
| One task type takes down the fleet | Poison message crash loop |

💡 **The common thread: background work is invisible by default.** A failing request returns a 500 and appears in your error rate. A failing task is a log line in a worker pod nobody is watching.

---

## Memory

The most common Celery operational problem.

```bash
celery worker \
    --max-tasks-per-child=100 \
    --max-memory-per-child=250000        # KB
```

💡 **`max-tasks-per-child` recycles a prefork child after N tasks, releasing whatever it accumulated.** It is not a fix for a leak — it is a way to survive one you have not found.

⚠️ **It only works with the prefork pool.** With gevent or threads there is no child to recycle, so a leak grows until the worker dies.

### Where the memory actually goes

| Cause | |
|---|---|
| **Prefetch** | `concurrency × multiplier` messages held in memory |
| A library that caches unboundedly | Common with HTTP clients, ORMs, template engines |
| Large task results held in memory | Especially with a result backend enabled |
| **Fragmentation** | Python's allocator does not return arenas to the OS |
| Genuinely leaked references | Closures, module-level caches, unclosed resources |

⚠️ **Fragmentation looks exactly like a leak and is not one.** RSS climbs and never falls, but `tracemalloc` shows flat tracked allocations. **Recycling children is the correct fix**, and no amount of code review will find it ([[01.12 - Profiling and Debugging Async Services]]).

```python
# Distinguish them
import tracemalloc
tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
# ... 1000 tasks ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)
```

💡 **If tracked allocations are flat and RSS is high, it is fragmentation. If tracked allocations grow, you have a real leak and this output names the line.**

### The OOM kill spiral

⚠️ **A worker killed by the OOM killer with `acks_late=True` and `reject_on_worker_lost=True` requeues its task — which then kills the next worker.**

```
Worker 1 OOMs on document X → requeued
Worker 2 OOMs on document X → requeued
...entire fleet crash-looping
```

**Three defences, and you want all of them:**

```python
@app.task(bind=True, max_retries=2)
def process_document(self, document_id: str):
    size = repo.get_size(document_id)
    if size > MAX_PROCESSABLE_BYTES:
        mark_failed(document_id, "too large")
        return                                    # 1. precondition guard
    ...
```

```yaml
resources:
  limits:
    memory: 2Gi                                   # 2. bounded blast radius
```

**3. `max_retries` plus a DLQ**, so the poison message stops circulating ([[08.6 - Retries Backoff and Dead Letters]]).

## Hung Workers

A worker that is running but processing nothing.

### Causes

| Cause | Signal |
|---|---|
| **Broker connection lost silently** | `inspect ping` times out; no new tasks started |
| A task blocked on a network call with no timeout | `inspect active` shows the same task for hours |
| A deadlock between the pool and the main process | Rare, and real |
| DNS resolution hanging | Connection establishment never completes |

```bash
celery -A app inspect ping                  # is it alive?
celery -A app inspect active                # what is it running?
py-spy dump --pid <worker-pid>              # ← what is it actually doing?
```

💡 **`py-spy dump` on a wedged worker is the fastest diagnosis available** ([[01.12 - Profiling and Debugging Async Services]]). It shows the exact stack, in production, without restarting anything.

⚠️ **In Kubernetes you need `SYS_PTRACE`.** Configure it before you need it.

### Time limits are the safety net

```python
app.conf.task_soft_time_limit = 300
app.conf.task_time_limit = 360
```

⚠️ **Without a hard time limit, a hung task occupies its slot forever.** Four such tasks on a `concurrency=4` worker means the worker is permanently dead while appearing healthy.

⚠️ **Time limits only work with prefork.** With gevent there is no way to interrupt a greenlet blocked in a C call — which is a genuine argument for prefork in production despite the memory cost.

### Liveness probes

```yaml
livenessProbe:
  exec:
    command: ["celery", "-A", "app", "inspect", "ping", "-d", "celery@$(HOSTNAME)"]
  initialDelaySeconds: 30
  periodSeconds: 60
  timeoutSeconds: 30
  failureThreshold: 3
```

⚠️ **`inspect ping` requires broker fanout, so it does not work on SQS.** And it is slow, so the timeout must be generous or you restart healthy workers.

💡 **A file-based heartbeat is more robust and works on every broker:**

```python
@task_postrun.connect
def touch_heartbeat(**_):
    Path("/tmp/worker-alive").touch()
```

```yaml
livenessProbe:
  exec:
    command: ["sh", "-c", "test $(( $(date +%s) - $(stat -c %Y /tmp/worker-alive) )) -lt 300"]
```

⚠️ **This fails a worker that has simply had no work for 5 minutes.** Add a periodic no-op task on every queue, or touch the file from the consumer loop rather than from task completion.

## Deploys

```yaml
terminationGracePeriodSeconds: 660      # > task_time_limit
```

```
SIGTERM  → warm shutdown: stop consuming, finish in-flight tasks
SIGQUIT  → cold shutdown: terminate immediately
```

⚠️ **If the grace period is shorter than your longest task, Kubernetes `SIGKILL`s workers mid-task on every deploy.** With `acks_late` the work is requeued rather than lost — and you redo it on every rollout, which at scale is significant wasted capacity.

💡 **The better answer is short tasks, so the grace period can be short** ([[08.5 - Task Design Rules]]). A 660-second grace period makes every deploy slow; 60-second tasks let you use a 90-second grace period.

### Draining before shutdown

```yaml
lifecycle:
  preStop:
    exec:
      command: ["celery", "-A", "app", "control", "cancel_consumer", "--destination", "celery@$(HOSTNAME)", "default"]
```

Stop consuming immediately, then let in-flight work finish during the grace period. **Without this, the worker keeps pulling new tasks right up until SIGTERM**, so it always has fresh work to abandon.

### Rolling deploy compatibility

⚠️ **During a rollout, old and new workers consume the same queue** ([[08.5 - Task Design Rules]]).

```
□  No task renamed without pinning the old name
□  No required parameter added
□  No task deleted while messages are queued
□  Serialisation format unchanged
```

**Add a CI check** that diffs task signatures against the deployed version, in the same spirit as [[05.13 - Contract Testing and Schema Evolution]].

## Observability

### The metrics that matter

```python
task_started_total.labels(task=name, queue=q).inc()
task_completed_total.labels(task=name, status=s).inc()
task_duration_seconds.labels(task=name).observe(elapsed)
task_retries_total.labels(task=name, exception=e).inc()

queue_depth.labels(queue=q).set(depth)
queue_oldest_age_seconds.labels(queue=q).set(age)          # ← the key one

worker_active_tasks.labels(worker=w).set(n)
worker_reserved_tasks.labels(worker=w).set(n)
worker_memory_bytes.labels(worker=w).set(rss)

dead_letter_total.labels(task=name).inc()
schedule_last_success_timestamp.labels(name=s).set(ts)
```

💡 **`queue_oldest_age_seconds` is the single best queue health metric.** Depth tells you volume; age tells you whether anything is stuck, and age is what the user experiences ([[08.1 - Why Background Work Exists]]).

### The alerts

| Alert | Condition |
|---|---|
| **Queue stalled** | `oldest_age > 5 × p99_task_duration` |
| **No consumers** | `queue_depth > 0 AND active_workers == 0` |
| **Dead letter rate** | `rate(dead_letter_total[5m]) > threshold` |
| **Worker memory** | `worker_memory_bytes > 0.8 × limit` |
| **Retry rate** | `rate(task_retries) / rate(task_started) > 0.2` |
| **Scheduled job stale** | `time() - schedule_last_success > 2 × interval` |
| **Task duration regression** | `p99 > 2 × baseline` |

⚠️ **Alert on queue *age*, not depth.** A depth alert fires on every legitimate burst and gets ignored; an age alert fires when something is actually wrong.

💡 **The retry-rate alert is the best leading indicator** — it rises before failures become user-visible ([[08.6 - Retries Backoff and Dead Letters]]).

### Structured logging and tracing

```python
@task_prerun.connect
def bind(task_id, task, args, kwargs, **_):
    structlog.contextvars.clear_contextvars()
    structlog.contextvars.bind_contextvars(
        task_id=task_id,
        task_name=task.name,
        **{k: v for k, v in (kwargs or {}).items() if k.endswith("_id")},
    )
```

💡 **Binding entity IDs into logging context means every line from that task is searchable by document ID** — which is exactly what you need when a customer asks why their document failed.

**Trace propagation across the queue boundary:**

```python
def enqueue_traced(task, **kwargs):
    carrier: dict[str, str] = {}
    TraceContextTextMapPropagator().inject(carrier)
    return task.apply_async(kwargs=kwargs, headers=carrier)


@task_prerun.connect
def restore_trace(task, **_):
    ctx = TraceContextTextMapPropagator().extract(task.request.headers or {})
    context.attach(ctx)
```

⚠️ **Without this, every trace ends at the enqueue** and you cannot see the work a request caused ([[12.3 - Instrumenting Conduit End to End]]).

### Flower is not monitoring

💡 **Flower is a good interactive inspector and a bad monitoring system** — in-memory state, no persistence, no alerting, and it becomes a bottleneck at high task rates. Use it to look at things; use Prometheus to be told about things.

## The Runbook

### Queue backing up

```
1. queue_oldest_age_seconds — stuck, or just slow?
   High age + low depth  → a stuck message or no consumer
   High age + high depth → not enough capacity

2. Are workers alive?
   celery -A app inspect ping

3. Are they consuming this queue?
   celery -A app inspect active_queues

4. What are they doing?
   celery -A app inspect active
   py-spy dump --pid <pid>

5. Prefetch hoarding?
   celery -A app inspect reserved

6. Is a dependency slow?
   Check the task's downstream latency metrics
```

### Workers OOMing

```
1. Is it one task type?          → group task_failures by task name
2. tracemalloc: leak or fragmentation?
3. Fragmentation                 → lower max-tasks-per-child
4. Leak                          → the tracemalloc output names the line
5. One poison input              → precondition guard + DLQ
6. Prefetch too high             → lower the multiplier
```

### Tasks failing silently

```
1. Check the DLQ depth and rate
2. Group dead letters by exception type
3. Check task_completed_total{status="failure"}
4. Check that the queue has a consumer at all
5. Check whether the task name is registered on the workers
```

⚠️ **"Received unregistered task of type" means a producer and worker version mismatch**, and the messages are being rejected. It is the first thing to check after any deploy.

## Capacity Planning

```
required_workers = arrival_rate × avg_duration / concurrency
```

```
100 tasks/sec × 2s average / 8 concurrency = 25 workers
```

⚠️ **That is the steady-state minimum with zero headroom.** Add 50–100% for bursts, retries and slow tasks.

💡 **Size for the p99 duration, not the mean.** A task averaging 2 seconds with a p99 of 30 seconds means a worker occasionally occupied 15× longer than the average, and mean-based sizing produces periodic backlogs.

### Autoscaling

```yaml
triggers:
  - type: redis
    metadata:
      listName: ingestion
      listLength: "20"
```

⚠️ **Scale-down is the risky direction.** A terminated worker requeues its in-flight task; frequent scale-down means constant rework.

```yaml
cooldownPeriod: 300              # slow to scale down
pollingInterval: 15              # fast to scale up
```

💡 **Scale up fast, scale down slowly.** The cost of an extra worker for five minutes is trivial; the cost of thrashing is repeated wasted work.

## Codebase

**Repo:** `celery/celery`, `getsentry/sentry`, `onyx-dot-app/onyx`

**Question to answer:** In Celery, what exactly happens between receiving `SIGTERM` and the process exiting — which components stop in what order, and what happens to reserved-but-unstarted messages? Then: how does a large production deployment instrument its tasks?

**Read, in order:**

1. `celery/celery/worker/worker.py` — **the blueprint and `stop`/`terminate`.** The shutdown ordering
2. `celery/celery/worker/consumer/consumer.py` — **warm shutdown.** Find where it stops consuming and how it waits for in-flight tasks. **The answer to the first question**
3. `celery/celery/concurrency/prefork.py` — `max-tasks-per-child` and the child recycling mechanism
4. `celery/celery/worker/autoscale.py` — Celery's own autoscaler, and why it is generally worse than orchestrator-level scaling
5. `sentry/src/sentry/tasks/base.py` — **their instrumented task decorator**: metrics, error reporting, timing, all applied uniformly
6. `onyx/backend/onyx/background/celery/` — worker configuration and monitoring in a real deployment

💡 The shutdown sequence in `consumer.py` is worth reading carefully, because **"what happens to my tasks during a deploy" is a question you will be asked and should be able to answer precisely.** The answer differs based on `acks_late`, prefetch, and whether the grace period was long enough.

**Size:** 1–2 sessions.

**Part 1 — Leak versus fragmentation.** Two tasks: one with a genuine leak (a growing module-level list), one that merely fragments (allocating and freeing large objects).

Run 5,000 of each. **Chart RSS and `tracemalloc` tracked allocations for both.**

**Confirm the leak shows growth in both and fragmentation shows growth only in RSS.** Then confirm `max-tasks-per-child` fixes the second and merely delays the first.

Then use the `tracemalloc` comparison to identify the exact leaking line.

**Part 2 — The OOM spiral.** A task that OOMs on one specific input, with `acks_late` and `reject_on_worker_lost`.

**Run it and watch workers die in sequence.** Measure time until the whole fleet is crash-looping.

Then apply three fixes independently — `max_retries`, a precondition guard, and a memory limit with a DLQ — and measure which stops it and which prevents it.

**Part 3 — Hung workers.** Three ways to wedge a worker: a network call with no timeout, a killed broker connection, and a deliberate deadlock.

For each: **diagnose it using only `inspect` and `py-spy`.** Record what each tool showed and how long the diagnosis took.

Then add time limits and confirm the first is bounded. Then confirm time limits do **not** work under gevent.

**Part 4 — Deploy damage.** Workers running 5-minute tasks, `terminationGracePeriodSeconds: 30`.

**Measure work redone per rollout** across ten deploys.

Then correct the grace period. Then add `preStop` draining and measure again. Then split the task to 30 seconds and measure with a 60-second grace period.

**Chart wasted work across all four configurations.**

**Part 5 — Version skew.** Two worker pools on different commits, one queue.

Introduce a renamed task, a new required parameter, and a deleted task with messages queued. **Count failures for each.**

Then apply the safe procedures and confirm zero failures.

**Part 6 — Full observability.** Implement every metric, structured logging with entity IDs, trace propagation, and the seven alerts.

Then trace one document from an HTTP upload through five chained tasks to the search index. **Confirm it is one trace.**

**Part 7 — Five incidents, diagnosed blind.** Have a script induce one of the five scenarios at random.

**Diagnose each using only metrics and the runbook, within five minutes.**

Record: time to diagnosis, which metric gave it away, and whether the runbook was sufficient. **Fix the runbook where it was not.**

**Part 8 — Capacity.** Measure your actual arrival rate, p50 and p99 duration, and required workers.

Then load test at 2×, 5× and 10× and find where it breaks. Then configure autoscaling and measure: time to scale up under a burst, work redone during scale-down, and whether the cooldown prevents thrashing.

**Done when:**
- You can distinguish a leak from fragmentation with `tracemalloc`
- You caused a fleet-wide OOM spiral and stopped it three ways
- You diagnosed three kinds of hung worker with `py-spy`
- Your deploy-damage chart covers four grace-period configurations
- Version skew failures are reproduced and eliminated
- One document traces cleanly through five tasks
- You diagnosed all five incidents within five minutes each
- Autoscaling handles a 5× burst without thrashing
