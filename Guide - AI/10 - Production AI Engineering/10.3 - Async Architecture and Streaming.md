# Async Architecture and Streaming

## Why Async Matters for AI Systems

LLM calls take 1–30 seconds. If you block synchronously, one slow request blocks all others. Async architecture lets you handle many concurrent requests efficiently.

Additionally, for long-running background work (document ingestion, batch evaluations), you need task queues that decouple work from API requests.

---

## Async Request Handling (FastAPI)

```python
import asyncio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat")
async def chat_endpoint(request: ChatRequest):
    # ALL I/O is async — never block the event loop
    
    # Parallel: embed query + start BM25 search simultaneously
    emb_task = asyncio.create_task(async_embed(request.query))
    bm25_task = asyncio.create_task(async_bm25_search(request.query))
    
    query_emb, bm25_results = await asyncio.gather(emb_task, bm25_task)
    
    # Dense search
    dense_results = await async_vector_search(query_emb)
    
    # Fuse and rerank
    fused = rrf_fusion(dense_results, bm25_results)
    reranked = await async_rerank(request.query, fused[:20])
    
    # Stream response
    prompt = build_prompt(request.query, reranked[:5])
    return StreamingResponse(stream_llm(prompt), media_type="text/event-stream")

async def stream_llm(prompt):
    async for token in llm.astream(prompt):
        yield f"data: {json.dumps({'token': token})}\n\n"
    yield "data: [DONE]\n\n"
```

**Key rules**:

- Never use `time.sleep()` in an async context — use `asyncio.sleep()`
- Never call blocking I/O (requests, psycopg2) in async functions — use httpx, asyncpg
- Use `asyncio.gather()` to run concurrent operations

## Streaming Responses

Streaming delivers tokens to the user as they're generated rather than waiting for the full response.

### Server-Sent Events (SSE)

Most common pattern for web applications:

```python
# Backend: yield tokens as they generate
async def stream_response(prompt):
    async for chunk in openai_client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        stream=True,
    ):
        token = chunk.choices[0].delta.content
        if token:
            yield f"data: {json.dumps({'token': token, 'type': 'token'})}\n\n"
    
    # Signal completion with citation data
    yield f"data: {json.dumps({'type': 'done', 'citations': citations})}\n\n"

# Frontend: consume the stream
const es = new EventSource('/chat');
es.onmessage = (e) => {
    const data = JSON.parse(e.data);
    if (data.type === 'token') appendToResponse(data.token);
    if (data.type === 'done') showCitations(data.citations);
};
```

### Streaming with Intermediate Results

Show retrieval results while LLM generates — improves perceived responsiveness:

```python
async def full_streaming_pipeline(query, user_id, response_queue):
    # Phase 1: Retrieval (fast) — emit immediately
    chunks = await retrieve(query, user_id)
    await response_queue.put({
        "type": "sources",
        "data": [{"title": c.title, "url": c.url} for c in chunks]
    })
    
    # Phase 2: Generation (slow) — stream tokens
    prompt = build_prompt(query, chunks)
    async for token in llm.astream(prompt):
        await response_queue.put({"type": "token", "data": token})
    
    await response_queue.put({"type": "done"})
```

## Background Job Architecture

For async document ingestion and batch processing:

```
API Server           Task Queue              Workers
──────────           ──────────              ───────
POST /ingest    →    Celery/Redis/Kafka  →   Worker 1: process doc_001
(returns 202)        (job queued)             Worker 2: process doc_002
                                             Worker N: process doc_XXX
```

```python
# Celery task definition
from celery import Celery

celery = Celery("tasks", broker="redis://localhost:6379/0")

@celery.task(bind=True, max_retries=3)
def index_document(self, doc_id: str, connector_name: str):
    try:
        connector = get_connector(connector_name)
        document = connector.fetch_document(doc_id)
        chunks = chunker.chunk(document)
        embeddings = embedder.embed_batch([c.text for c in chunks])
        vector_store.upsert_chunks(doc_id, chunks, embeddings)
    except Exception as exc:
        raise self.retry(exc=exc, countdown=2 ** self.request.retries)  # exponential backoff

# Enqueue from API
@app.post("/connectors/{connector_id}/sync")
async def trigger_sync(connector_id: str):
    docs = connector.list_modified_documents()
    for doc_id in docs:
        index_document.delay(doc_id, connector_id)  # non-blocking enqueue
    return {"queued": len(docs)}
```

## Webhook vs Polling

For keeping the index fresh:

**Polling** (simpler): Check source for changes every N minutes.

```python
@celery.task
def poll_connector(connector_id):
    connector = get_connector(connector_id)
    new_docs = connector.get_modified_since(last_poll_time)
    for doc in new_docs:
        index_document.delay(doc.id, connector_id)
```

**Webhooks** (faster): Source system notifies you when content changes.

```python
@app.post("/webhooks/confluence")
async def confluence_webhook(event: ConfluenceEvent):
    if event.type in ("page_created", "page_updated"):
        index_document.delay(event.page_id, "confluence")
    elif event.type == "page_deleted":
        delete_document.delay(event.page_id)
```

**In practice**: Use webhooks where available + polling as a fallback reconciliation mechanism (catch missed webhooks).
