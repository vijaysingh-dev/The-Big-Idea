# Transactions and Isolation Levels

#backend #databases #postgres #correctness

> **In one line:** Isolation levels are a menu of which concurrency bugs you are willing to have, Postgres defaults to Read Committed which permits several of them, and the one that bites real applications is write skew.

---

## The Idea

💡 **Atomicity and durability are essentially free and always on. Isolation is the one you choose**, and the choice trades correctness against concurrency.

| Anomaly | What happens |
|---|---|
| **Dirty read** | You read uncommitted data |
| **Non-repeatable read** | You read a row twice and get different values |
| **Phantom read** | You run the same query twice and get different *rows* |
| **Lost update** | Two transactions read-modify-write; one overwrites the other |
| **Write skew** | Two transactions each read a set, each write based on it, and together they break an invariant neither could see breaking |

### The levels in Postgres

| Level | Dirty | Non-repeatable | Phantom | Lost update | Write skew |
|---|---|---|---|---|---|
| **Read Committed** (default) | No | **Yes** | **Yes** | **Yes** | **Yes** |
| Repeatable Read | No | No | No¹ | No² | **Yes** |
| Serializable | No | No | No | No | No |

¹ The standard permits phantoms here; Postgres's snapshot isolation prevents them.
² Postgres aborts the second writer with a serialization failure rather than losing the update.

⚠️ **Read Committed is the default and it permits four of the five anomalies.** Most applications run on it and most are fine — but "most are fine" is not "yours is fine", and knowing which of your transactions are exposed is the point.

---

## Read Committed

**Each statement sees a fresh snapshot taken at the start of that statement.**

⚠️ **Two statements in the same transaction can see different data.** Any read-then-write logic in your application code is racy at this level.

### The lost update

```python
balance = await conn.fetchval("SELECT balance FROM accounts WHERE id = 1")   # both read 1000
await conn.execute("UPDATE accounts SET balance = $1 WHERE id = 1", balance - 100)
```

**Two withdrawals of 100 from 1000 leave 900, not 800.** One is silently lost.

💡 **This is the most common concurrency bug in application code**, and it is invisible in testing because it requires exact timing.

```sql
-- 1. Atomic update — the database does the arithmetic. BEST when possible
UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100;

-- 2. Pessimistic lock
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

-- 3. Optimistic concurrency
UPDATE accounts SET balance = $1, version = version + 1 WHERE id = 1 AND version = $2;
```

⚠️ **Option 1 is the right default and it is under-used.** `SET balance = balance - 100` is atomic within the statement and needs no lock, no retry and no version column. **Reach for locks only when the new value cannot be expressed in terms of the old one.**

### The `UPDATE ... WHERE` re-check

If another transaction changed a row mid-statement, Postgres **waits**, then **re-evaluates the `WHERE` clause against the new version.** If it no longer matches, the row is skipped.

💡 **This makes single-statement updates safer than they look**, and it is why option 1 works. **It also means an `UPDATE` can see a mix of snapshot times** — one of the genuinely odd corners of Read Committed.

## Repeatable Read

**One snapshot for the whole transaction.** Non-repeatable reads and phantoms are gone.

```sql
ERROR:  could not serialize access due to concurrent update
SQLSTATE: 40001
```

⚠️ **Your application must handle 40001 by retrying the whole transaction** — not the failed statement, the whole thing, because the snapshot is stale.

```python
async def with_retry(fn, attempts: int = 3):
    for i in range(attempts):
        try:
            async with conn.transaction(isolation="repeatable_read"):
                return await fn()
        except asyncpg.SerializationError:
            if i == attempts - 1:
                raise
            await asyncio.sleep(random.uniform(0, 0.05 * 2 ** i))
```

💡 **Any use of Repeatable Read or Serializable requires this retry wrapper.** Without it you have moved a silent correctness bug into a loud runtime error — better, and still broken.

## Write Skew

The anomaly Repeatable Read does **not** prevent, and the one worth understanding properly.

```
Rule: at least one doctor must be on call. Currently Alice and Bob both are.
```

```sql
-- Transaction A (Alice)                  -- Transaction B (Bob)
SELECT count(*) FROM doctors              SELECT count(*) FROM doctors
  WHERE on_call = true;  -- 2               WHERE on_call = true;  -- 2
-- "2 > 1, safe to go off call"           -- "2 > 1, safe to go off call"
UPDATE doctors SET on_call = false        UPDATE doctors SET on_call = false
  WHERE name = 'Alice';                     WHERE name = 'Bob';
COMMIT;                                   COMMIT;
```

**Nobody is on call.** Neither transaction saw a violation, and they wrote to *different rows* — so there is no update conflict for Repeatable Read to detect.

⚠️ **The pattern to look for: read a set, make a decision based on it, write something that changes that set.**

| Domain | Write skew |
|---|---|
| Booking | Two people book the last seat |
| Inventory | Two orders each check stock ≥ 1, both decrement |
| Quotas | Two uploads each check usage < limit, together exceed it |
| Uniqueness in application code | Two signups check email uniqueness, both insert |

💡 **If you have ever written `if count < limit: insert()`, you have written a write skew bug.** It works until it does not.

## Serializable

Postgres implements **Serializable Snapshot Isolation (SSI)** — it tracks read/write dependencies between concurrent transactions and aborts one if a cycle would produce a non-serializable outcome.

**The guarantee: any set of successfully-committed serializable transactions produces a result equivalent to running them one at a time in some order.**

| Cost | Detail |
|---|---|
| **Predicate locks** | Tracks *what you read*, including ranges |
| Memory | Grows with concurrent transaction count and read volume |
| **Serialization failures** | More frequent, increasing with contention |
| Sequential scans hurt | A seq scan predicate-locks the whole table, causing false conflicts |
| **All participants must be serializable** | A Read Committed transaction gets no protection |

⚠️ **That last point is easy to miss.** If one code path uses the default level, the guarantee is void for that interaction.

💡 **Postgres's SSI is genuinely good — it is optimistic, so readers never block.** The practical constraint is the retry rate under contention, which is measurable and manageable.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
```

**Excellent for long analytics queries** — it may wait briefly at the start, then is guaranteed never to abort and never to block anyone.

**Good indexes reduce false conflicts** by narrowing the predicate locks.

## Explicit Locking

```sql
SELECT * FROM documents WHERE id = 42 FOR UPDATE;         -- blocks other writers
SELECT * FROM documents WHERE id = 42 FOR NO KEY UPDATE;  -- weaker; allows FK refs
SELECT * FROM documents WHERE id = 42 FOR UPDATE NOWAIT;  -- error instead of waiting
SELECT * FROM documents WHERE id = 42 FOR UPDATE SKIP LOCKED;
```

💡 **`SKIP LOCKED` turns a table into a work queue, and it is the correct way to build one in Postgres:**

```sql
UPDATE jobs SET status = 'running', worker_id = $1
WHERE id IN (
    SELECT id FROM jobs WHERE status = 'pending'
    ORDER BY created_at LIMIT 10
    FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

**Each worker takes 10 jobs nobody else has claimed, with no coordination and no blocking.** This pattern is worth memorising — it comes up constantly and the naive alternatives all have races.

### Advisory locks

```sql
SELECT pg_advisory_xact_lock(hashtext('sync:' || source_id));
```

⚠️ **Non-transactional advisory locks must be explicitly released**, and a connection returned to a pool while holding one poisons it for the next user. **Prefer the `_xact_` variant**, which releases at transaction end.

## In Production

### Choosing per transaction

💡 **Isolation level is a per-transaction decision, not a global one.** Run Read Committed by default and escalate the specific transactions that have an invariant to protect.

**The audit question for each transaction: does it read something and then write based on what it read?** If yes, it needs Serializable, an explicit lock, or a database constraint.

### Prefer constraints over isolation

```sql
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE (email);

ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, during WITH &&);

ALTER TABLE accounts ADD CONSTRAINT positive_balance CHECK (balance >= 0);
```

⚠️ **A database constraint is enforced regardless of isolation level, application bugs, or which service wrote the row.** It is strictly stronger than any application check.

💡 **`EXCLUDE` constraints are the underused one.** They solve the entire class of "these two things must not overlap" problems — room bookings, resource reservations, time-range validity — atomically and without any isolation-level reasoning. **Most people have never heard of them.**

### Transaction length

⚠️ **A long transaction holds locks, holds a connection, and holds back vacuum** ([[06.7 - MVCC Vacuum and Bloat]]). The oldest open transaction determines how far vacuum can clean, **so one forgotten transaction can bloat the entire database.**

**Rule: no network calls inside a transaction. Ever.** ([[01.10 - Connection Pools and Limits]])

```sql
SET idle_in_transaction_session_timeout = '30s';
SET statement_timeout = '10s';
SET lock_timeout = '5s';
```

💡 **`idle_in_transaction_session_timeout` is the safety net that prevents one bug from bloating your database. Set it.**

### Monitoring

```sql
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity WHERE xact_start IS NOT NULL
  AND now() - xact_start > interval '1 minute' ORDER BY duration DESC;

SELECT datname, xact_commit, xact_rollback, conflicts, deadlocks FROM pg_stat_database;
```

**Track your 40001 rate.** A rising serialization failure rate means contention is increasing, and the retry cost may be about to become the dominant cost.

## Codebase

**Repo:** `postgres/postgres`

**Question to answer:** How does Postgres detect a serialization conflict under SSI — what does it track, and when does it abort? Then: in Read Committed, where is the `UPDATE ... WHERE` re-check implemented?

**Read, in order:**

1. `src/backend/access/transam/README` — the transaction and snapshot model. Read the snapshot and visibility sections first
2. `src/backend/storage/lmgr/README-SSI` — **an outstanding document.** The full SSI algorithm: predicate locks, read/write dependencies, dangerous structures, and when a transaction is aborted. **The answer to the first question, and it is genuinely readable**
3. `src/backend/storage/lmgr/predicate.c` — SSI implemented. `CheckForSerializableConflictOut` and `PreCommit_CheckForSerializationFailure`
4. `src/backend/executor/nodeModifyTable.c` — **`ExecUpdate` and the `EvalPlanQual` path.** This is the Read Committed re-check
5. `src/backend/utils/time/snapmgr.c` — snapshot creation, and the difference between statement-level and transaction-level snapshots

💡 `README-SSI` is one of the best explanations of serializable isolation anywhere, in any form. It defines the "dangerous structure" — a specific pattern of read-write dependencies indicating a possible cycle — and shows why detecting it is sufficient. **Two hours with that file gives you a better understanding of serializability than most database courses.**

**Size:** 2–3 sessions.

## Exercise

**Drill 6.6 — Reproduce every anomaly**

The single most valuable correctness drill in the vault.

```
drills/06-isolation/
├── harness/{runner.py, barriers.py}
├── anomalies/{nonrepeatable.py, phantom.py, lost_update.py, write_skew.py, RESULTS.md}

├── queue/{skip_locked.py, naive.py, RESULTS.md}
├── hygiene/{long_txn.py, timeouts.sql}
└── README.md
```

**Part 1 — Build a controlled-interleaving harness.** Two database sessions with barriers, so you can run A step 1, B step 1, A step 2, B step 2 in an exact order.

**This harness is the reusable asset.** Without deterministic interleaving, concurrency tests are flaky and prove nothing.

**Part 2 — Reproduce all four anomalies.** Non-repeatable read, phantom, lost update, write skew — each at Read Committed, Repeatable Read and Serializable.

**Fill in the table from this note with your own results.**

**Write skew is the important one.** Implement the on-call doctors scenario and confirm it succeeds at Repeatable Read and is blocked at Serializable.

**Part 3 — Five fixes, compared.** For the lost update: atomic update, `SELECT FOR UPDATE`, optimistic versioning, Serializable, and a `CHECK` constraint.

Measure correctness under 50 concurrent writers, throughput, p99 latency, and lines of application code.

**Then state which you would use for: a bank balance, a page view counter, an inventory decrement, and a document version.** They are not all the same answer, and the reasoning is the exercise.

**Part 4 — The retry wrapper.** Measure the abort rate against concurrency: 2, 5, 10, 25, 50, 100 concurrent serializable transactions on a contended row set.

**Chart abort rate and effective throughput. Find the concurrency at which retries consume more capacity than they deliver** — that is where Serializable stops being viable for that workload, and knowing where it is turns an ideological question into an engineering one.

Then add a good index and repeat, showing false conflicts dropping.

**Part 5 — A real work queue.** Three ways: naive select-then-update (**demonstrate the double-claim race**), `SELECT FOR UPDATE` (correct but blocking), and `FOR UPDATE SKIP LOCKED`.

Measure with 20 concurrent workers: jobs claimed twice, throughput, and worker idle time.

**Part 6 — Constraints beat isolation.** A room-booking overlap problem with Serializable and with an `EXCLUDE` constraint.

Compare correctness, throughput, and **what happens when a *different service* inserts a booking without knowing the rule.**

**The second case is the argument — a constraint protects you from code you have not written.**

**Part 7 — Transaction hygiene.** Hold a transaction idle for 10 minutes during a heavy update workload.

Measure dead tuples vacuum cannot remove, table bloat, and oldest transaction age. Then set `idle_in_transaction_session_timeout` and confirm the connection is killed before damage accumulates.

**Done when:**
- Your harness produces deterministic interleavings
- All four anomalies are reproduced, and the level table is filled from your own runs
- Write skew succeeds at Repeatable Read and fails at Serializable in your tests
- The five-fix comparison includes a recommendation per scenario
- You know the concurrency at which Serializable's abort rate becomes prohibitive
- `SKIP LOCKED` demonstrably prevents a double-claim the naive version allows
- You measured a long idle transaction bloating a table
