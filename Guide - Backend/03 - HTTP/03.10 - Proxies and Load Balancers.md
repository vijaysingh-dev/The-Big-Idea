# Proxies and Load Balancers

#backend #http #infrastructure

> **In one line:** An L4 balancer moves TCP connections and an L7 balancer moves HTTP requests, and almost every load balancing surprise comes from not knowing which one you have.

---

## The Idea

A load balancer sits between clients and your servers and decides where each unit of traffic goes. The critical question is: **what is the unit?**

| | L4 (transport) | L7 (application) |
|---|---|---|
| Balances | TCP connections | HTTP requests |
| Sees | IPs, ports, bytes | Methods, paths, headers, bodies |
| Can route by | Address, port | Path, host, header, cookie |
| TLS | Passes through | Usually terminates |
| Cost | Very low | Higher — parses HTTP |
| Retries | Cannot — no request boundaries | Can |
| Health checks | TCP connect | HTTP endpoint with status codes |

💡 **The distinction matters most for multiplexed protocols.** With HTTP/1.1, one connection carries one request at a time, so balancing connections is roughly balancing requests. With HTTP/2 and gRPC, one connection carries thousands of requests — so an L4 balancer sends all of them to one backend ([[03.8 - HTTP2]]).

## Algorithms

| Algorithm | How | Good for |
|---|---|---|
| **Round robin** | Next in rotation | Uniform request cost |
| **Weighted round robin** | Proportional to capacity | Heterogeneous backends |
| **Least connections** | Fewest active | Variable request duration |
| **Least request** | Fewest in-flight (L7) | Variable duration, HTTP/2 |
| **Power of two choices** | Pick 2 at random, take the less loaded | **The best general default** |
| **Consistent hashing** | Hash a key to a backend | Cache affinity, sharding |
| **Peak EWMA** | Weighted by observed latency | Backends of differing speed |

### Power of two choices

Worth knowing specifically, because it is a surprisingly strong result.

```python
def pick(backends):
    a, b = random.sample(backends, 2)
    return a if a.active < b.active else b
```

Random selection gives poor balance. Checking **all** backends and picking the least loaded is expensive and, at scale, causes a herd — every balancer picks the same "least loaded" backend simultaneously and overwhelms it.

Picking the better of two random choices gives you nearly the quality of full least-connections at nearly the cost of random, with no herding.

💡 **This is the default in Envoy and most modern meshes**, and the reasoning is a good thing to be able to explain. The distribution improvement over pure random is dramatic — maximum load goes from `O(log n)` to `O(log log n)`.

### Consistent hashing

```
hash(key) → position on a ring → the next backend clockwise
```

Adding or removing a backend moves only `1/n` of the keys, rather than reshuffling everything.

Used for: cache affinity (the same key always hits the same cache), sticky sessions without shared state, and sharding.

⚠️ **Plain consistent hashing distributes unevenly** because hash positions cluster. Real implementations use **virtual nodes** — each backend occupies many ring positions — which smooths it out. Also worth knowing is **bounded-load consistent hashing**, which caps how much any one backend can receive before overflow goes to the next, preventing a hot key from destroying one node.

More in [[10.7 - Service Discovery and Service Mesh]] in the HLD vault, and [[06.13 - Partitioning and Sharding]] here.

## Health Checks

The mechanism that makes a load balancer useful rather than just a distributor.

### Active checks

```nginx
# The balancer polls each backend
location /health {
    access_log off;
    return 200;
}
```

⚠️ **A health check that only returns 200 tells you the process is running, which is nearly worthless.** A process can be running with an exhausted database pool, a full disk, and a blocked event loop.

### Liveness vs readiness

```python
@app.get("/health/live")
async def live():
    return {"status": "ok"}          # am I running? restart me if not

@app.get("/health/ready")
async def ready():
    checks = {
        "db": await check_db(),
        "redis": await check_redis(),
        "loop_lag_ok": current_loop_lag() < 0.1,
    }
    ok = all(checks.values())
    return JSONResponse(
        {"ready": ok, "checks": checks},
        status_code=200 if ok else 503,
    )
```

| Check | Failure means | Action |
|---|---|---|
| **Liveness** | The process is broken | Restart it |
| **Readiness** | Cannot serve right now | Remove from the pool, do not restart |

💡 **Confusing these causes restart loops.** If your liveness check depends on the database and the database has a blip, every pod fails liveness, every pod restarts, and now you have a cold cache and a thundering herd on a database that was about to recover. **Liveness must depend on nothing external.**

⚠️ **The readiness check must not be so strict that a partial dependency failure removes every backend.** If Redis is down and your readiness check requires Redis, you have taken your entire service offline to protect against degraded caching. Prefer graceful degradation ([[11.6 - Graceful Degradation]]) with readiness reserved for genuine inability to serve.

### Passive checks (outlier detection)

Rather than polling, watch real traffic:

```yaml
# Envoy outlier detection
outlier_detection:
  consecutive_5xx: 5
  interval: 10s
  base_ejection_time: 30s
  max_ejection_percent: 50
```

A backend returning errors is ejected temporarily, then gradually reintroduced.

⚠️ **`max_ejection_percent` is the important safety valve.** Without a cap, a bad deploy that makes every backend return 5xx causes every backend to be ejected, and now nothing is serving. The cap ensures you always keep some capacity, even unhealthy capacity, which is better than none.

## Sticky Sessions

Routing a client consistently to the same backend.

| Method | How |
|---|---|
| Cookie-based | Balancer sets a cookie naming the backend |
| IP hash | Hash the source IP |
| Consistent hash on a header | Hash a user or tenant ID |

⚠️ **Sticky sessions are usually a design smell.** They mean your backends hold state that should be shared. Consequences: uneven load, a lost session when a backend dies, and difficulty deploying.

Legitimate uses: WebSocket connections (inherently stateful — though a pub/sub backplane is better, see [[04.6 - Scaling Long Lived Connections]]), and cache locality where a miss is merely slow rather than incorrect.

**IP hash specifically is a poor choice** because of CGNAT ([[02.10 - NAT Firewalls and Middleboxes]]) — thousands of mobile users share one address and all land on one backend.

## What Proxies Change

A proxy is not transparent. Things you must account for:

### The client IP

```
Client → LB → Backend
                 ▲ sees the LB's IP
```

```
X-Forwarded-For: 203.0.113.9, 10.0.0.1
X-Forwarded-Proto: https
X-Forwarded-Host: api.example.com
Forwarded: for=203.0.113.9;proto=https;host=api.example.com
```

⚠️ **`X-Forwarded-For` is client-controlled unless you only trust proxy-appended entries.** Configure trusted proxy ranges explicitly. `--forwarded-allow-ips='*'` on an internet-facing service lets anyone claim any IP, defeating rate limiting and audit logging.

**PROXY protocol** is safer where supported — the real addresses arrive at the TCP layer before any client bytes.

### Timeouts stack

```
Client timeout        30s
LB idle timeout       60s
LB request timeout    30s
Backend timeout       25s
Database timeout      10s
```

⚠️ **They must nest, innermost shortest.** If the backend's timeout exceeds the load balancer's, the LB gives up first and the backend keeps working on a request nobody will receive — burning a worker and a connection for nothing. This is a common and wasteful misconfiguration.

### Buffering

Proxies buffer by default, which is right for normal responses and fatal for streaming ([[03.6 - Compression and Streaming Responses]]).

### Protocol translation

```
Client ──HTTP/2──► LB ──HTTP/1.1──► Backend
```

Common and usually fine. It means your application never sees HTTP/2, and any HTTP/2-specific tuning in your app does nothing.

## In Production

### Choosing a proxy

| Tool | Strength |
|---|---|
| **nginx** | Ubiquitous, fast, huge ecosystem. Configuration is idiosyncratic |
| **HAProxy** | Best-in-class L4 and L7 balancing, excellent observability |
| **Envoy** | Dynamic configuration via API, the foundation of service meshes |
| **Caddy** | Automatic TLS, readable config, modern defaults |
| **Traefik** | Auto-discovers services from Docker/Kubernetes labels |
| Cloud LBs | Managed, integrated, less flexible |

💡 For learning, read **Caddy** (modern Go, readable) and use **Envoy** (its configuration model teaches you what a proxy actually does, because everything is explicit).

### The load balancer as a single point of failure

```
Client → [ LB ] → backends
           ▲ if this dies, everything dies
```

Solutions in increasing order of sophistication:

1. **DNS round robin across multiple LBs** — crude, TTL-limited failover
2. **Anycast** — the same IP announced from multiple locations, routing picks the nearest
3. **Active/passive with a floating IP** — VRRP/keepalived
4. **Client-side load balancing** — no LB at all; the client knows all backends

Client-side balancing is what gRPC and service meshes do. It eliminates the SPOF and a network hop, at the cost of every client needing service discovery and balancing logic — which is exactly what a mesh sidecar provides.

### The connection draining problem

You deploy. A pod is terminating. What happens to its in-flight requests?

```
1. Pod gets SIGTERM
2. Readiness check starts failing
3. LB notices (up to one check interval later)  ← the gap
4. LB stops sending new requests
5. Pod finishes in-flight work
6. Pod exits
```

⚠️ **Steps 2–4 have a gap** where the load balancer is still sending requests to a pod that is shutting down. Those requests get connection resets, and users see errors during every deploy.

The fix is a deliberate delay:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "10"]      # fail readiness, keep serving, THEN shut down
```

The pod starts failing readiness immediately, keeps serving for 10 seconds while the LB notices, and only then begins draining. Covered in [[11.7 - Graceful Shutdown and Draining]].

💡 **This is one of the highest-value ten-line configuration changes in Kubernetes** and a large fraction of deployments do not have it. If your error rate spikes during every deploy, this is usually why.

### Diagnosing lopsided load

```bash
# Requests per backend
kubectl top pods
# or count in your access logs by upstream address
```

| Cause | Check |
|---|---|
| L4 balancing a multiplexed protocol | Is it gRPC or HTTP/2? |
| Sticky sessions | Is a session cookie or IP hash configured? |
| Long-lived connections | WebSocket, SSE, or aggressive keep-alive |
| `SO_REUSEPORT` hash imbalance | Multi-process server ([[02.6 - TCP Settings That Matter]]) |
| Uneven request cost | Round robin with heterogeneous work |
| Recently scaled up | Existing connections do not migrate |

**The last one catches people constantly.** You scale from 3 pods to 10 under load; the new pods receive nothing because all existing connections are pinned to the original three. `keepalive_requests` or `MAX_CONNECTION_AGE` forces redistribution.

## Codebase

**Repo:** `caddyserver/caddy`, `envoyproxy/envoy` (docs + config), `haproxy/haproxy`

**Question to answer:** How does Caddy's reverse proxy decide which upstream to use, and what does it do when one fails mid-request? Then: in Envoy, find where power-of-two-choices is implemented, and where outlier detection ejects a host.

**Read, in order:**

1. `caddy/modules/caddyhttp/reverseproxy/reverseproxy.go` — **the main file.** Follow one request through upstream selection, dialling, and response copying. Look for the streaming/buffering decision
2. `caddy/modules/caddyhttp/reverseproxy/selectionpolicies.go` — every algorithm in one readable file. Round robin, least connections, IP hash, header hash. Short and clear
3. `caddy/modules/caddyhttp/reverseproxy/healthchecks.go` — active and passive checks
4. `envoy/source/common/upstream/load_balancer_impl.cc` — search for `LeastRequest`. **This is power-of-two-choices**, and the comments explain the choice
5. `envoy/source/common/upstream/outlier_detection_impl.cc` — ejection logic including `max_ejection_percent`
6. Envoy docs: `arch_overview/upstream/load_balancing/` — read the whole section. It is the best written explanation of load balancing theory in any project's documentation

💡 Caddy's `selectionpolicies.go` is the single best file to read here — every algorithm side by side in about 400 lines of readable Go. You can hold the whole design space in your head after one session.

**Size:** 1–2 sessions.

```
│   ├── with_prestop.sh
│   └── RESULTS.md
└── README.md
```

**Part 1 — Build one.** An L7 HTTP load balancer with four algorithms, active health checks, passive outlier detection with an ejection cap, and graceful backend removal.

It must correctly: forward headers including `X-Forwarded-For`, not buffer streaming responses, propagate timeouts, and retry idempotent requests on connection failure only.

**Part 2 — Prove power of two choices.** Simulate 10,000 requests across 20 backends with highly variable request cost (some 1ms, some 500ms).

Compare: random, round robin, full least-connections, and P2C. Chart the **maximum** backend load and the p99 latency for each.

**P2C should be close to full least-connections and far better than random.** Then add 20 balancer instances all choosing independently, and show full least-connections developing a herding problem that P2C does not.

**Part 3 — The gRPC trap.** Three gRPC backends, HAProxy in TCP mode. 10,000 requests over one channel. Count per backend.

Then swap to Envoy in L7 mode and count again. Chart both.

Then, without changing the balancer, set `MAX_CONNECTION_AGE=30s` on the backends and show the L4 distribution improving over time. **Three fixes, three different tradeoffs** — document which you would choose and why.

**Part 4 — The scale-up trap.** Three backends under sustained load with keep-alive connections. Scale to ten. Chart requests per backend over the next five minutes.

The seven new backends should receive almost nothing. Then set `keepalive_requests 500` and repeat, showing traffic redistributing.

**Part 5 — Health check disasters.** Two scenarios, both realistic:

- **Liveness with a dependency:** liveness checks the database. Make the database unavailable for 30 seconds. Watch every pod restart. Measure how much longer full recovery takes than the outage itself
- **Readiness too strict:** readiness requires Redis. Kill Redis. Watch every backend leave the pool and the service go fully down, despite Redis being optional for most endpoints

Then fix both and quantify the improvement. **The first scenario turning a 30-second blip into a multi-minute outage is the memorable result.**

**Part 6 — Deploy without errors.** Rolling deploy under sustained load, no `preStop` hook. Chart the error rate through the rollout.

Then add the `preStop` sleep and a matching `terminationGracePeriodSeconds` and repeat.

**The error spike should disappear entirely.** Record how many requests failed in each case — this is the number to show someone who thinks the sleep is unnecessary.

**Done when:**
- Your balancer passes its tests and handles streaming and timeouts correctly
- The P2C chart shows it near-optimal and herd-free
- The gRPC distribution is 100/0/0 before and even after, with three fixes compared
- You have shown new pods receiving no traffic and fixed it
- Both health check disasters are reproduced with measured recovery times
- Your rollout error count drops to zero with `preStop`
