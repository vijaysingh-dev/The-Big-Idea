# Public Groups, Queues and Territory Management

## Three grouping constructs

Sharing rules cannot target individuals, roles are hierarchical and singular, and some work needs to be owned by a team rather than a person. These three constructs fill those gaps.

They are related but distinct, and knowing which to reach for is a common interview question and a common design mistake.

## Public groups

A named collection of people, used as a target for sharing rules, manual shares, Apex shares, folder access, and list view visibility.

A public group can contain:

- Individual users
- Roles
- Roles and subordinates
- Other public groups
- Territories and territories with subordinates

That composability is the point. A group can be built from other groups, so "All EMEA Staff" can be assembled from "EMEA Sales", "EMEA Service", and "EMEA Operations" and stays correct as those change.

Behind the scenes, public groups, roles, queues, and territories are all stored in the `Group` object with different `Type` values:

```sql
SELECT Id, Name, DeveloperName, Type
FROM Group
WHERE Type IN ('Regular', 'Queue', 'Role', 'RoleAndSubordinates', 'Territory')
```

`Regular` is a public group. Membership lives in `GroupMember`:

```sql
SELECT Group.Name, Group.Type, UserOrGroupId
FROM GroupMember
WHERE Group.DeveloperName = 'EMEA_Service_Team'
```

Note `UserOrGroupId` can point at a user *or* another group, which is how nesting is stored.

**Why groups matter for design:** they decouple the sharing model from the org structure. A sharing rule that targets a group never changes; only membership does. Adding someone to the escalation team is a membership change with no recalculation of rule definitions and no deployment.

Building sharing around groups rather than roles is one of the clearest markers of a well-designed org.

## Queues

A queue is a group that can also **own records**.

This is the essential difference. A public group is a target for access. A queue is a holder of unassigned work.

```
Queue: Tier 2 Support
    Members: the "Tier 2 Engineers" public group
    Supported objects: Case, Warranty_Claim__c
```

When a case is assigned to a queue, the queue is its owner. Any queue member can see it in the queue's list view and claim it by taking ownership, at which point the record moves from the queue to that person.

Queues are used with assignment rules for automatic routing ([[05.3 - Case Assignment and Auto-Response Rules]]), with lead assignment ([[04.3 - Lead Assignment Rules and Queues]]), and with Omni-Channel for capacity-based distribution ([[05.7 - Omni-Channel Routing]]).

The technical detail that catches developers: **`OwnerId` on a queue-enabled object is polymorphic** — it can be a User ID (starting `005`) or a Group ID (starting `00G`). Code that assumes `Owner.Name` refers to a person, or that queries `Owner.Email`, breaks when the record sits in a queue.

```java
// Handles both cases
for (Case c : cases) {
    String ownerType = String.valueOf(c.OwnerId).startsWith('00G') ? 'Queue' : 'User';
}
```

```sql
SELECT Id, CaseNumber, OwnerId, Owner.Name,
       TYPEOF Owner WHEN User THEN Email, ManagerId WHEN Group THEN DeveloperName END
FROM Case
WHERE Status = 'New'
```

`TYPEOF` is the correct way to query fields that exist on only one of the possible owner types. See [[08.2 - Relationship Queries]].

Queue membership grants access to records the queue owns, at Read/Write. Members do not gain access to anything else.

## Territory management

Territories model **overlapping, multi-dimensional coverage** — the thing roles cannot do because a user has exactly one role.

The requirement that forces territories: a rep covers manufacturing accounts in western India; a second rep covers all accounts above a revenue threshold nationally; a specialist covers all accounts using a particular product line. Any given account may fall into all three. No single hierarchy expresses that.

**Enterprise Territory Management** provides:

- A territory hierarchy, separate from the role hierarchy
- **Territory models**, allowing a proposed structure to be built and tested before activation — genuinely useful, since territory changes are annual and disruptive
- **Assignment rules** that place accounts into territories by field criteria
- Users assigned to multiple territories
- Sharing rules that target territories
- Opportunity territory assignment for reporting and forecasting

An account can be in many territories. A user can be in many territories. Access is additive, as everywhere else in the sharing model.

The tradeoffs are real. Territory management adds significant complexity, territory realignment triggers large-scale sharing recalculation, and forecasting interacts with it in ways that require care. It is worth enabling when the sales organization genuinely has overlapping coverage, and not otherwise. Full treatment in [[04.17 - Territory Management Deep Dive]].

## Choosing between them

| Requirement | Use |
| --- | --- |
| Grant a set of people access to records | Public group |
| Hold unassigned work until someone claims it | Queue |
| Route incoming records to a team | Queue plus assignment rules |
| Model overlapping sales coverage | Territories |
| Model a management reporting structure for visibility | Role hierarchy |
| Give a folder or list view to a set of people | Public group |

The distinction that matters most: **if it needs to own records, it is a queue. If it only needs access, it is a public group.**

## Working with them in code

Resolving a queue by developer name, which is the portable approach since IDs differ per org:

```java
public with sharing class QueueService {

    public static Id getQueueId(String developerName) {
        List<Group> queues = [
            SELECT Id FROM Group
            WHERE Type = 'Queue' AND DeveloperName = :developerName
            LIMIT 1
        ];
        return queues.isEmpty() ? null : queues[0].Id;
    }

    public static void routeToQueue(List<Warranty_Claim__c> claims, String queueDeveloperName) {
        Id queueId = getQueueId(queueDeveloperName);
        if (queueId == null) {
            return;
        }
        for (Warranty_Claim__c claim : claims) {
            claim.OwnerId = queueId;
        }
    }
}
```

Adding someone to a public group. `GroupMember` is a setup object, so this cannot share a transaction with DML on normal objects:

```java
public with sharing class GroupMembershipService {

    @future
    public static void addUsersToGroup(Set<Id> userIds, String groupDeveloperName) {
        Group grp = [SELECT Id FROM Group WHERE DeveloperName = :groupDeveloperName AND Type = 'Regular' LIMIT 1];

        Set<Id> existing = new Set<Id>();
        for (GroupMember gm : [SELECT UserOrGroupId FROM GroupMember WHERE GroupId = :grp.Id]) {
            existing.add(gm.UserOrGroupId);
        }

        List<GroupMember> toAdd = new List<GroupMember>();
        for (Id userId : userIds) {
            if (!existing.contains(userId)) {
                toAdd.add(new GroupMember(GroupId = grp.Id, UserOrGroupId = userId));
            }
        }
        if (!toAdd.isEmpty()) {
            insert toAdd;
        }
    }
}
```

Note that adding a user to a group triggers sharing recalculation for every record shared with that group. On a large org this is asynchronous and can take time, which is why bulk membership changes should be batched rather than done one at a time.

## Practical guidance

**Name groups by function, not by person or team name.** `Warranty_Escalation_Access` outlives "Priya's team".

**Nest groups rather than duplicating membership.** One person appearing in twelve group definitions is twelve places to update when they leave.

**Use groups as sharing targets everywhere.** Sharing rules, Apex shares, folder access, list views. It is the single decoupling decision that pays off most.

**Do not use queues where a group would do.** A queue that never owns records is a group with extra confusion.

**Audit group membership periodically.** Membership accumulates, and it is invisible unless someone looks.

```sql
SELECT Group.Name, COUNT(Id) memberCount
FROM GroupMember
WHERE Group.Type = 'Regular'
GROUP BY Group.Name
ORDER BY COUNT(Id) DESC
```
