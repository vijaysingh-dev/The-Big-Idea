# Reading EXPLAIN ANALYZE

#backend #databases #postgres #performance

> **In one line:** The plan is a tree that executes bottom-up, the gap between estimated and actual rows tells you whether to trust it, and `BUFFERS` tells you whether the time went to disk or to CPU.

---

## The Idea

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT d.title, u.name FROM documents d JOIN users u ON u.id = d.author_id
WHERE d.org_id = 7 AND d.status = 'indexed' ORDER BY d.created_at DESC LIMIT 20;
```

⚠️ **`EXPLAIN ANALYZE` actually executes the query.** For `UPDATE`, `DELETE` or `INSERT`, wrap it in `BEGIN; ... ROLLBACK;`.

💡 **Always use `BUFFERS`.** Without it you know a node was slow; with it you know whether it read 400,000 pages from disk or did expensive work in memory. **Those need completely different fixes.** `ANALYZE` alone is half the information.

---

## Reading the Tree

```
Limit  (cost=1043.21..1043.26 rows=20 width=64)
       (actual time=8.412..8.418 rows=20 loops=1)
  Buffers: shared hit=1204 read=88
  ->  Sort  (actual time=8.410..8.413 rows=20 loops=1)
        Sort Key: d.created_at DESC
        Sort Method: top-N heapsort  Memory: 28kB
        ->  Nested Loop  (actual time=0.042..7.891 rows=2092 loops=1)
              ->  Index Scan using idx_org_status on documents d
                    (cost=0.43..412.18 rows=2092 width=48)
                    (actual time=0.028..1.204 rows=2092 loops=1)
                  Index Cond: ((org_id = 7) AND (status = 'indexed'))
                  Buffers: shared hit=204 read=88
              ->  Index Scan using users_pkey on users u
                    (actual time=0.002..0.002 rows=1 loops=2092)
                  Index Cond: (id = d.author_id)
Planning Time: 0.284 ms
Execution Time: 8.467 ms
```

**Read bottom-up and inside-out.** The most indented nodes run first and feed their parents.

### The numbers on each node

```
(cost=0.43..412.18 rows=2092 width=48)
 ▲      ▲          ▲          ▲
 │      │          │          └─ estimated bytes per row
 │      │          └─ ESTIMATED rows
 │      └─ estimated total cost
 └─ estimated startup cost (before the first row)

(actual time=0.028..1.204 rows=2092 loops=1)
             ▲      ▲       ▲          ▲
             │      │       │          └─ how many times this node ran
             │      │       └─ ACTUAL rows, PER LOOP
             │      └─ time to complete, per loop
             └─ time to first row, per loop
```

⚠️ **`actual time` and `rows` are per loop, and are not multiplied for you.**

```
Index Scan on users  (actual time=0.002..0.002 rows=1 loops=2092)
```

That is 2,092 × 0.002ms ≈ **4.2ms total**, not 0.002ms. **This is the single most misread part of `EXPLAIN` output, and it hides N+1-shaped problems in plain sight.**

💡 **Whenever you see a high `loops` count, multiply before judging.** A node showing 0.01ms with `loops=50000` is 500ms and is probably your entire problem.

## Estimated vs Actual: The Key Signal

```
rows=2092 (estimated)  ...  rows=2092 (actual)     ← planner was right
rows=100 (estimated)   ...  rows=847293 (actual)   ← planner was badly wrong
```

💡 **A large estimate/actual gap is the most important diagnostic in the whole output**, because every plan decision above that node was made using the wrong number. A join strategy chosen for 100 rows is catastrophic for 800,000.

| Cause | Fix |
|---|---|
| Stale statistics | `ANALYZE tablename` |
| Not enough detail | `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000` |
| **Correlated columns** | **`CREATE STATISTICS`** |
| Complex `OR` conditions | Rewrite as `UNION` |

### Correlated columns

```sql
WHERE city = 'Bangalore' AND state = 'Karnataka'
```

The planner assumes independence: `P(city) × P(state)`. But every Bangalore row is in Karnataka, so the true selectivity is just `P(city)`. **The estimate can be off by orders of magnitude.**

```sql
CREATE STATISTICS city_state (dependencies, ndistinct) ON city, state FROM addresses;
ANALYZE addresses;
```

⚠️ **Extended statistics are underused and they fix a whole class of bad plans.** Any two columns with a real-world dependency — `country`/`currency`, `org_id`/`source_id` — produce bad estimates without them.

## The Node Types

### Scans

| Node | Meaning | Concerning when |
|---|---|---|
| `Seq Scan` | Read the whole table | The table is large and the filter is selective |
| `Index Scan` | Walk the index, fetch each row | Returning a large fraction of the table |
| `Index Only Scan` | Index alone answers it | `Heap Fetches` is high |
| `Bitmap Heap Scan` | Collect row IDs, fetch in physical order | `lossy` blocks present |

**Bitmap scans** are the middle ground: the index scan builds a bitmap of matching pages, then the heap scan reads them **in physical order**, turning random I/O into sequential.

⚠️ **`Heap Blocks: lossy=N` means the bitmap ran out of `work_mem`** and degraded to page-level granularity, forcing a recheck of every row on those pages. **Raising `work_mem` fixes it.**

### Joins

| Node | Best for |
|---|---|
| `Nested Loop` | **Small outer** side, indexed inner |
| `Hash Join` | Large, unsorted inputs |
| `Merge Join` | Both already sorted, or very large |

⚠️ **A `Nested Loop` with a large `loops` count is the classic disaster plan**, and it appears when the planner underestimated the outer side:

```
Nested Loop  (actual rows=847293 loops=1)
  ->  Seq Scan on a  (rows=100 estimated)  (actual rows=847293)   ← the mistake
  ->  Index Scan on b  (loops=847293)                              ← the consequence
```

**Fix the estimate, not the join.**

⚠️ **`Batches: 4` on a Hash node means the hash table did not fit in `work_mem`** and spilled to disk. **`Batches: 1` is what you want** — one of the most direct signals that `work_mem` is too low for this query ([[06.2 - Postgres Architecture]]).

### Sorts and aggregates

```
Sort Method: quicksort  Memory: 28kB           ← good
Sort Method: external merge  Disk: 24560kB     ← spilled, 10-100x slower
Sort Method: top-N heapsort  Memory: 28kB      ← LIMIT optimisation, good
```

💡 **`top-N heapsort` is the planner being clever**: with `ORDER BY ... LIMIT 20` it keeps only the top 20 in memory rather than sorting everything.

### Parallel plans

⚠️ **`Workers Planned: 4  Workers Launched: 0`** means no worker slots were available. **Your query silently ran single-threaded and took 4× longer, with nothing in the output explaining why.**

## In Production

### The diagnostic sequence

```
1. Execution Time vs Planning Time
   Planning > Execution → too many partitions, or too many joins

2. Find the node with the largest actual time
   Remember to multiply by loops

3. Check that node's estimated vs actual rows
   Large gap → fix statistics before anything else

4. Check Buffers on that node
   High `read` → disk I/O. High `hit` → CPU or too many pages

5. Look for spills
   external merge, Hash Batches > 1 → raise work_mem

6. Look for Rows Removed by Filter
```

### Rows Removed by Filter

```
Index Scan using idx_org on documents
  Index Cond: (org_id = 7)
  Filter: (status = 'indexed')
  Rows Removed by Filter: 98420
```

💡 **This is the clearest possible signal for a missing index column.** The index found 100,000 rows, then threw away 98,420. Adding `status` to the index turns that into an `Index Cond` reading 1,580 rows instead of 100,000.

**Look for `Rows Removed by Filter` first when hunting for index opportunities** — it points directly at what to add.

### Buffers, interpreted

```
Buffers: shared hit=1204 read=88 dirtied=12 written=4
```

⚠️ **`read` includes the OS page cache**, so a high count is not necessarily physical disk I/O.

```sql
SET track_io_timing = on;
-- now EXPLAIN shows: I/O Timings: read=234.512
```

**`I/O Timings` is what tells you the reads actually went to disk.** Without it you cannot separate "10,000 pages from the OS cache in 2ms" from "10,000 pages from disk in 2 seconds".

### auto_explain: plans for slow production queries

```sql
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 500;
SET auto_explain.log_analyze = on;
SET auto_explain.log_buffers = on;
SET auto_explain.log_nested_statements = on;
```

💡 **This is the only practical way to see the plan of a query that was slow at 3am.** Reproducing it later gives you a different plan with different data and a warm cache.

⚠️ `log_analyze` adds overhead to every query above the threshold. Set it high, and consider `sample_rate`.

### Why the plan differs between staging and production

| Cause | |
|---|---|
| Different data volume | Statistics differ |
| Different distribution | Selectivity estimates differ |
| Cold vs warm cache | Same plan, very different time |
| Different `work_mem` per session | Spilling in one, not the other |
| Generic vs custom plan | Prepared statements after 5 executions |

💡 **A plan captured on a small staging database tells you almost nothing.** Test index and query changes against a production-sized copy, or you will optimise for the wrong plan entirely. **This is the most common reason a "verified" optimisation does nothing in production.**

## Codebase

**Repo:** `postgres/postgres`, `dalibo/pev2`

**Question to answer:** Where does the executor record `actual rows` and `actual time`, and why are they per-loop rather than totalled? Then: how does `EXPLAIN` decide which nodes show `Rows Removed by Filter`?

**Read, in order:**

1. `src/backend/commands/explain.c` — **`ExplainNode`**, the function producing everything in this note. Long, but each output line has a visible source
2. `src/backend/executor/instrument.c` — **`InstrStartNode` / `InstrStopNode`.** Where timing and row counts are collected. **The per-loop answer is here**: instrumentation wraps a single node execution, and a node rescanned by a nested loop accumulates loop count
3. `src/backend/executor/nodeNestloop.c` — how the inner side is rescanned. **Makes the `loops` semantics obvious**
4. `src/backend/executor/nodeHashjoin.c` — batching, and where `Batches: N` comes from
5. `dalibo/pev2` — a plan visualiser. Read the node parsing to see which numbers a good tool highlights and why

💡 Reading `explain.c` alongside real output is unusually rewarding, because every line maps to a specific `ExplainProperty*` call. **After one session you stop guessing what a field means.**

**Size:** 1–2 sessions.

## Exercise

**Drill 6.4 — Diagnose from the plan alone**

```
drills/06-explain/
├── data/seed.py                  # 10M rows, correlated columns, skew
├── reading/{plans/, DIAGNOSIS.md, ANSWERS.md}
├── estimates/{correlated.sql, extended_stats.sql, RESULTS.md}
├── spills/{sort_spill.sql, hash_spill.sql, bitmap_lossy.sql, RESULTS.md}
├── loops/{nested_loop_disaster.sql, FINDINGS.md}
├── production/{auto_explain.sql, capture.py, analyse.py}
└── README.md
```

**Part 1 — Read 15 plans blind.** Generate plans covering: a missing index, a stale-statistics bad plan, a `work_mem` spill, a nested loop disaster, a lossy bitmap, an unused partial index, a failed index-only scan, a parallel plan with no workers, a generic-plan flip, and several healthy plans.

**Save only the plan output.** Then, a week later, diagnose each from the plan alone before looking at the query.

For each write: what is wrong, which number told you, and what you would change.

**Target: 12 of 15 correct.** This is the skill being trained and it is directly what you do in an incident.

**Part 2 — Break the estimates.** A table with strongly correlated columns.

**Measure the estimate/actual gap** — it should be large. Then add extended statistics and measure again. **Show that the *plan* changed, not just the estimate**, and quantify the runtime difference.

Then a stale-statistics case: insert 5 million rows without `ANALYZE`, capture the plan, then `ANALYZE` and capture again.

**Part 3 — Every kind of spill.** Deliberately produce an external merge sort, a hash join with `Batches > 1`, a lossy bitmap heap scan, and a hash aggregate spill.

For each: find the `work_mem` value where it starts, measure latency either side, and **compute the memory cost of setting `work_mem` high enough globally.**

Then set it per-session with `SET LOCAL` for just that query and confirm the spill disappears without the global cost.

**Part 4 — The nested loop disaster.** Construct a query where the planner underestimates the outer side by 1,000×.

**Note the `loops` count and compute the true total time of the inner node.**

Then fix it three ways — `ANALYZE`, extended statistics, and rewriting — and compare which actually changed the plan.

**Part 5 — I/O timing.** Enable `track_io_timing`. Run a query cold (restart Postgres, drop the OS cache) and warm.

**Same plan, same buffer counts, very different `I/O Timings`.** Write in `RESULTS.md` how you would tell "slow because of disk" from "slow because of CPU" from the plan alone.

**Part 6 — auto_explain in production.** Configure a 200ms threshold against a realistic workload.

Write a script parsing the logged plans and ranking them by total time, estimate/actual gap, and spill presence. **Run it against a workload with a deliberately introduced regression and confirm your tool finds it.**

**Part 7 — Staging lies.** The same query and index against a 10,000-row table and a 10-million-row table.

Show the plan differing. **Then find an index that helps on the small table and does nothing (or hurts) on the large one.**

**This is the experiment that stops you trusting staging benchmarks, and it takes twenty minutes.**

**Done when:**
- You diagnosed at least 12 of 15 plans blind
- Extended statistics measurably changed a plan, not just an estimate
- You know the `work_mem` threshold for each spill type and its global memory cost
- You computed the true cost of a high-`loops` nested loop node
- You can distinguish disk-bound from CPU-bound from a plan
- Your `auto_explain` analyser found a deliberately introduced regression
- You have a concrete case where staging gave you the wrong answer
