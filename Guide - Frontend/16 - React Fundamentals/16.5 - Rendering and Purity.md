# Rendering and Purity

React calls your component function to produce a description of the UI. That call must be a **pure function of props, state and context** — same inputs, same output, no observable side effects.

This is not a style preference. Concurrent rendering, Strict Mode, Server Components and the React Compiler all depend on it, and violating it produces bugs that only appear under load or in production builds.

## The three phases

**Trigger** — an initial render, or a state update anywhere in the tree.

**Render** — React calls component functions to build the new element tree and diffs it against the previous one. No DOM is touched. This phase can be paused, resumed, restarted or discarded entirely ([[18.4 - Render Phase vs Commit Phase]]).

**Commit** — React applies the computed changes to the DOM, runs layout effects, paints, then runs passive effects.

Everything about purity follows from the render phase being interruptible: React may call your component and throw the result away.

## What purity means concretely

```jsx
// Impure — mutates a value outside its own scope
let renderCount = 0;
function Bad() {
  renderCount++;
  return <p>{renderCount}</p>;
}

// Impure — mutates props
function Bad({ items }) {
  items.sort();                 // mutates the parent's array
  return <List items={items} />;
}

// Impure — different output for the same input
function Bad() {
  return <p>{Math.random()}</p>;
}

// Impure — side effect during render
function Bad({ id }) {
  analytics.track("viewed", id);
  return <p>Item {id}</p>;
}
```

The sorting case is the most common in real code, because `sort` and `reverse` mutate in place ([[06.7 - Immutable Data Patterns]]):

```jsx
const sorted = [...items].sort(cmp);   // or items.toSorted(cmp)
```

## What is allowed

**Mutating something created during this render** is fine, because nothing outside can observe it:

```jsx
function Fine({ items }) {
  const rows = [];                    // local — created this render
  for (const item of items) rows.push(<Row key={item.id} item={item} />);
  return <ul>{rows}</ul>;
}
```

**Reading props, state and context.** **Computing derived values.** **Calling pure functions.**

## Where side effects belong

| Effect | Location |
| --- | --- |
| Data fetching | a data library, or `useEffect` |
| Subscriptions | `useEffect` with cleanup |
| Analytics on view | `useEffect` |
| Analytics on click | the event handler |
| DOM measurement | `useLayoutEffect` |
| Timers | `useEffect` with cleanup |
| `localStorage` writes | event handler or effect |

Event handlers are **not** part of rendering, so they may do anything. When a side effect can be attached to a user action rather than to a render, the handler is almost always the better place — it runs once, deterministically, in response to a real intent.

## Strict Mode double-invocation

In development, Strict Mode calls component functions, initializers and updaters **twice**, and mounts-unmounts-remounts components once ([[18.7 - Strict Mode and Double Invocation]]).

This is a purity detector. A pure component produces identical output both times and nothing observable changes. An impure one produces a visible bug immediately — a counter incrementing by two, a list duplicated, a request fired twice.

The correct response to a double-invocation bug is to fix the impurity, never to suppress Strict Mode or add a `hasRun` ref.

## Why concurrent rendering requires it

React can start rendering, yield to the browser, and either resume or **abandon** the work:

```jsx
function Impure({ items }) {
  globalCache.push(items.length);    // ran even though the render was discarded
  return <List items={items} />;
}
```

If the render is thrown away, that push already happened and can never be undone. With `useTransition`, `useDeferredValue` or Suspense in the tree, renders are discarded routinely ([[18.5 - Concurrent Rendering and the Scheduler]]) — so an impurity that seemed harmless in React 17 becomes a live bug in React 18+.

The same reasoning explains **tearing**: if a component reads a mutable external value directly during render, two components in the same render pass can observe different values when the render is interrupted between them. `useSyncExternalStore` exists specifically to prevent this ([[17.12 - Lesser Known Hooks]]).

## Derive, do not synchronize

The most valuable practical consequence:

```jsx
// Unnecessary state + effect
const [filtered, setFiltered] = useState([]);
useEffect(() => {
  setFiltered(items.filter(i => i.active));
}, [items]);

// Just compute it
const filtered = items.filter(i => i.active);
```

The effect version renders twice per change, can show stale data for one frame, and adds a synchronization path that can break. The derived version cannot be wrong.

If the computation is genuinely expensive, `useMemo` caches it — but that is an optimization on top of deriving, not an alternative to it ([[17.6 - useMemo]]).

The same applies to props copied into state:

```jsx
// Anti-pattern — state that shadows a prop
const [value, setValue] = useState(props.initialValue);
useEffect(() => setValue(props.initialValue), [props.initialValue]);

// Better — reset with key, or lift the state
<Form key={props.id} initialValue={props.initialValue} />
```

## Purity and the React Compiler

The React Compiler automatically memoizes components and values, which is only sound if rendering is pure. It performs static analysis and **skips** components it cannot prove safe — so impure code silently loses the optimization ([[19.9 - The React Compiler]]).

This makes purity increasingly load-bearing rather than aspirational: it is now the precondition for automatic performance work.

## How senior engineers actually use this

**They treat Strict Mode failures as real bugs**, because they always are — the double invocation only reveals an impurity that already existed.

**They compute during render by default** and reach for state only when a value cannot be derived.

**They put side effects in event handlers wherever possible**, effects second, and view a growing number of effects as a design smell.

**They never mutate props or arrays received from a parent.**

**They keep `console.log` in mind as a diagnostic** — a log appearing twice in development is Strict Mode working, not a bug.

## Common pitfalls

- `items.sort()` or `items.reverse()` on a prop.
- Mutating a module-level variable or cache during render.
- Firing analytics or requests during render.
- Reading `Date.now()` or `Math.random()` during render and expecting stability.
- Copying props into state and synchronizing with an effect.
- Suppressing Strict Mode instead of fixing the underlying impurity.
- Reading a mutable external store directly during render, causing tearing.

## Interview angle

"Why must React components be pure" is a strong senior-level question. The answer is that the render phase is interruptible and may be discarded, so any side effect during render can happen zero, one or several times per commit; purity is what makes concurrent rendering, Strict Mode checks and compiler memoization sound. Following with "and this is why deriving beats synchronizing with an effect" connects the theory to the most common real-world mistake.
