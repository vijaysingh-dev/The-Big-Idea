# Code Coverage, Quality and CI Gates

## What the platform requires

```
75% org-wide Apex coverage
Every trigger covered by at least one line
All tests passing
```

Below that, a production deployment is rejected.

**The org-wide figure is what matters**, not per-class. A class at 0% deploys if the org total clears 75% — which is how untested code reaches production in an org with a few heavily-covered classes carrying the average.

## What coverage measures

**Which lines executed.** Nothing else.

```java
@IsTest
static void testApprove() {
    insert TestDataFactory.buildClaim(150000);
}
```

That produces full coverage of the trigger, the handler, and the service. It asserts nothing. It passes if the logic is inverted, if the status is set wrong, or if an exception is silently swallowed.

**A codebase at 78% with meaningful assertions is in better shape than one at 95% with none.** The number is a floor imposed by the platform, not a measure of quality.

## Reading coverage

```bash
sf apex run test --test-level RunLocalTests --code-coverage --result-format human --wait 30
```

```sql
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate
ORDER BY NumLinesUncovered DESC
```

**Sorting by uncovered lines rather than by percentage** is the more useful view — a 2,000-line class at 70% has more untested code than a 50-line class at 20%.

Per-test-class attribution:

```sql
SELECT ApexTestClass.Name, ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverage
WHERE ApexClassOrTrigger.Name = 'ClaimApprovalService'
```

This shows **which test covers which class**, which reveals a common pattern: a class covered entirely by an unrelated test class, incidentally, with no test actually verifying it.

## Coverage anti-patterns

**Tests written to raise the number.**

```java
@IsTest
static void coverTheGetters() {
    ClaimWrapper wrapper = new ClaimWrapper();
    wrapper.claimNumber = 'WC-1';
    Assert.areEqual('WC-1', wrapper.claimNumber);
}
```

That is a test asserting that Apex assignment works.

**`@TestVisible` used to reach private methods** purely for coverage, rather than because the method is a meaningful unit.

**Empty catch blocks** left in place because covering the error path is inconvenient.

**Deleting code to raise the percentage**, which occasionally happens under deployment pressure and is exactly backwards.

**Testing generated or trivial code.** Wrapper classes, constants, and enums.

The tell for all of these: **the test would still pass if the production code were deleted.**

## What is worth measuring instead

**Assertion density.** Roughly how many meaningful assertions per test. A suite averaging 0.4 assertions per test is coverage theatre.

**Mutation survival.** Break a line, run the tests, see whether they fail. Doing this on a sample of classes tells you more than any coverage number. There is no mutation testing tool for Apex, so this is manual and worth doing occasionally.

**Test execution time.** A suite over fifteen minutes is one developers stop running before pushing, which removes its value entirely.

**Failure rate over time.** Tests that fail intermittently are worse than no tests, because they train people to rerun rather than investigate.

## Setting a realistic gate

```yaml
# A CI gate that is stricter than the platform's, and achievable
- name: Run Apex tests
  run: |
    sf apex run test \
      --test-level RunLocalTests \
      --code-coverage \
      --result-format json \
      --output-dir test-results \
      --wait 30

- name: Enforce coverage
  run: node scripts/check-coverage.js --minimum 85 --per-class 70
```

**Org-wide above the platform minimum**, so a release is never blocked by being at exactly 75%.

**A per-class floor**, which is what actually prevents untested classes.

**No new class below the floor**, enforced on the diff rather than the whole org — this is the gate that improves an org over time without requiring a remediation project.

```bash
# Coverage for changed classes only
sf apex run test --tests $(git diff --name-only origin/main | grep 'Test.cls' | ...) --code-coverage
```

## Running only what changed

A full `RunLocalTests` on a large org takes tens of minutes, which is too slow for a pull request check.

```bash
# On a pull request: the tests for changed classes
sf apex run test --class-names ClaimApprovalServiceTest,ClaimSelectorTest --wait 10

# On merge to main, and before a production deploy: everything
sf apex run test --test-level RunLocalTests --code-coverage --wait 60
```

**Specified tests on a pull request, all tests before a release.** That split keeps feedback fast without letting a regression through.

Determining which tests to run from a diff requires a mapping — either a convention (`ClaimService` → `ClaimServiceTest`) or a dependency query:

```sql
SELECT MetadataComponentName, RefMetadataComponentName
FROM MetadataComponentDependency
WHERE RefMetadataComponentName = 'ClaimApprovalService'
```

## Test speed

The metric with the most practical impact, and the one nobody measures.

```sql
SELECT ApexClass.Name, MethodName, RunTime
FROM ApexTestResult
WHERE AsyncApexJobId = :jobId
ORDER BY RunTime DESC
LIMIT 20
```

**That query, run after a full suite, names the twenty slowest tests.** Fixing the top five usually halves the total.

The causes, in order:

**DML in every test.** A service test inserting fifty records to verify a calculation. The fix is constructed records and injection. See [[18.8 - Dependency Injection and Testability]].

**Triggers firing during setup.** Every insert runs the object's full automation.

**`@TestSetup` creating more than the tests need.**

**Tests that should be one test.** Four methods each doing the same expensive setup.

**Async flushing.** `Test.stopTest()` running a batch job is inherently slow.

**The target shape:** many fast service and domain tests with constructed records, few slow integration tests with real DML. See [[19.1 - Apex Testing Fundamentals]].

## Static analysis alongside coverage

Coverage says nothing about SOQL in a loop or a missing sharing declaration. Static analysis does.

```bash
sf scanner run --target force-app --format table --severity-threshold 3
```

**Salesforce Code Analyzer** wraps PMD, ESLint, RetireJS, and a graph engine that traces data flow for injection paths across method calls.

What it catches that tests do not:

```
SOQL and DML inside loops
Missing sharing declarations
Empty catch blocks
Hardcoded Ids
Unescaped output in Visualforce and Aura
SOQL injection paths
Excessive cyclomatic complexity
Unused variables and dead code
Vulnerable JavaScript libraries
```

**Running it in CI moves review time from mechanical issues to design.** A pull request where PMD has already flagged the query in a loop lets the reviewer discuss whether the approach is right. See [[09.13 - Apex Coding Standards and Best Practices]].

**The graph engine specifically** is worth enabling for anything security-sensitive — it traces a user-supplied value through several method calls into a dynamic query, which PMD alone cannot.

## A complete CI gate

```yaml
on: pull_request

jobs:
  validate:
    steps:
      - name: Static analysis
        run: sf scanner run --target force-app --severity-threshold 3

      - name: LWC unit tests
        run: npm run test:unit -- --coverage

      - name: Deploy validation
        run: |
          sf project deploy validate \
            --source-dir force-app \
            --test-level RunSpecifiedTests \
            --tests $(node scripts/affected-tests.js) \
            --wait 30

      - name: Coverage gate
        run: node scripts/check-coverage.js --minimum 85 --per-class 70
```

**`deploy validate` runs the deployment and its tests without committing**, which is the closest thing to a dry run against the target org. See [[21.8 - CI-CD Pipelines]].

**Jest tests run in seconds** with no org, making them the fastest feedback available in a Salesforce project — and the reason LWC coverage gates can be stricter than Apex ones. See [[14.18 - Jest Testing for LWC]].

## Improving a low-coverage org

The realistic approach, because a remediation project rarely gets funded.

**1. Establish the baseline** and make it visible — a dashboard, or a weekly figure in a channel.

**2. Gate the diff, not the org.** No new class below 70%. This stops the problem growing without requiring anyone to fix the past.

**3. Cover by risk, not by percentage.** The classes worth covering first are the ones that change often, carry money, or have caused an incident — not the ones with the lowest number.

**4. Write tests when fixing a bug.** A test reproducing the defect, then the fix. Coverage improves where defects actually occur.

**5. Delete dead code.** Frequently the fastest coverage improvement available, and it improves the codebase rather than the metric alone.

**6. Speed up the suite** so people run it. A fast suite is used; a slow one is bypassed.

## Coverage in packages

For a managed or unlocked package, coverage is measured **per namespace** and checked at version creation:

```bash
sf package version create --package "Northwind Claims" --code-coverage --wait 30
```

**75% is required for a package version to be promoted**, and a package's tests run during subscriber installation — so a slow suite is a slow install for every customer.

That gives an ISV a commercial reason to keep tests fast, beyond developer experience. See [[18.12 - Package Design - Unlocked, Managed, 1GP vs 2GP]].

## Section 19 in one paragraph

Coverage is a deployment gate, not a measure of quality — a test with no assertions produces the same number as one that verifies behaviour, and the mutation check separates them in seconds. What matters is that every test asserts something meaningful, that bulk tests use 200 records with several children per parent, and that security is tested as a real user rather than as an administrator, because an administrator sees everything and proves nothing. Async testing has a specific set of constraints worth memorizing: assertions after `stopTest`, one batch chunk, one chain level, and platform events that never deliver unless you ask them to. Flow testing is genuinely weaker than Apex testing, which is a real input to the flow-versus-Apex decision and an argument for pushing complex logic into invocable Apex that can be tested properly. And the metric with the most practical impact is not coverage but execution time — a suite people run before pushing catches defects, and one they skip does not.
