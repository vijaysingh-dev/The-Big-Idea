# Webpack Basics

Webpack is no longer the default for new projects, but it remains everywhere — Next.js used it for years, Create React App projects are still in production, and most large codebases predating Vite are built with it. Reading and maintaining a webpack config is a practical skill.

## The five core concepts

```js
// webpack.config.js
module.exports = {
  entry: "./src/index.tsx",

  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].[contenthash].js",
    clean: true,
    publicPath: "/",
  },

  module: {
    rules: [
      { test: /\.tsx?$/, use: "swc-loader", exclude: /node_modules/ },
      { test: /\.css$/, use: ["style-loader", "css-loader", "postcss-loader"] },
      { test: /\.(png|svg|jpg)$/, type: "asset" },
    ],
  },

  plugins: [
    new HtmlWebpackPlugin({ template: "./public/index.html" }),
    new MiniCssExtractPlugin(),
  ],

  resolve: {
    extensions: [".tsx", ".ts", ".js"],
    alias: { "@": path.resolve(__dirname, "src") },
  },
};
```

**Entry** — where the graph starts. Multiple entries produce multiple bundles, used for multi-page apps.

**Output** — where files go and how they are named. `[contenthash]` is what enables long-term caching ([[15.7 - HTTP Caching and CDNs]]).

**Loaders** transform individual files. They are applied **right to left** in the `use` array, which is a constant source of confusion:

```js
use: ["style-loader", "css-loader", "postcss-loader"]
// postcss runs first, then css-loader, then style-loader
```

**Plugins** hook into the whole build lifecycle — generating HTML, extracting CSS, analyzing output, defining constants.

**Resolve** controls how specifiers become file paths.

The mental model: **loaders transform files, plugins transform the build**.

## Development configuration

```js
module.exports = {
  mode: "development",
  devtool: "eval-cheap-module-source-map",

  devServer: {
    port: 3000,
    hot: true,
    historyApiFallback: true,       // SPA routing — serve index.html for unknown paths
    proxy: [{ context: ["/api"], target: "http://localhost:8080" }],
  },
};
```

`historyApiFallback` is the development equivalent of the server rewrite every SPA needs, or a refresh on `/products/42` returns 404 ([[23.1 - Client Side Routing Fundamentals]]).

`mode` matters more than it looks — it sets `NODE_ENV`, enables or disables minification, and controls default optimizations. Building without `mode: "production"` ships a development build of React, which is several times larger and much slower.

## Code splitting

```js
optimization: {
  splitChunks: {
    chunks: "all",
    cacheGroups: {
      react: {
        test: /[\\/]node_modules[\\/](react|react-dom)[\\/]/,
        name: "react",
        priority: 20,
      },
      vendor: {
        test: /[\\/]node_modules[\\/]/,
        name: "vendor",
        priority: 10,
      },
    },
  },
  runtimeChunk: "single",
}
```

`splitChunks` extracts shared modules automatically. `chunks: "all"` is the setting most people want — the default only splits async chunks.

`runtimeChunk: "single"` extracts webpack's module registry into its own file. Without it, the runtime is embedded in the main bundle and its content changes on every build, invalidating the cache even when application code did not change.

Dynamic imports create split points, with magic comments controlling naming and prefetching ([[08.2 - Dynamic Imports]]):

```js
const Editor = lazy(() =>
  import(/* webpackChunkName: "editor" */ /* webpackPrefetch: true */ "./Editor")
);
```

## Speeding it up

Webpack's slowness is mostly transpilation. Replacing Babel with a Rust or Go transformer is the largest single improvement:

```js
{ test: /\.tsx?$/, use: "swc-loader" }        // ~20x faster than babel-loader
{ test: /\.tsx?$/, use: "esbuild-loader" }
```

```js
cache: { type: "filesystem" },                 // persistent cache across restarts
```

```js
optimization: {
  minimizer: [new EsbuildPlugin({ target: "es2020" })],   // instead of Terser
}
```

Filesystem caching alone often halves rebuild times. `thread-loader` parallelizes transpilation but adds worker startup overhead, so it only pays off on large projects.

Measure before optimizing:

```bash
npx webpack --profile --json > stats.json
npx webpack-bundle-analyzer stats.json
```

The `speed-measure-webpack-plugin` attributes time to individual loaders and plugins, which usually identifies the culprit immediately.

## Migration paths

**To Rspack** — a Rust reimplementation with a webpack-compatible config API:

```js
// rspack.config.js — largely the same file
module.exports = { entry, output, module: { rules }, plugins };
```

Most configs work with minimal changes, and builds are typically 5–10× faster. This is the lowest-risk upgrade for an existing webpack project, and it is what Next.js-adjacent tooling and several large codebases have adopted.

**To Vite** — a larger change, since loaders and plugins have no direct equivalent, environment variables move from `process.env` to `import.meta.env`, and any `require` usage must become ESM. Worth it for the development experience on a project that is actively developed ([[27.3 - Vite]]).

Neither migration is urgent for a stable, low-change codebase. Build speed matters in proportion to how often you build.

## Module Federation

Webpack's distinctive capability, and the main reason it persists in some architectures:

```js
new ModuleFederationPlugin({
  name: "shell",
  remotes: { checkout: "checkout@https://cdn.example.com/checkout/remoteEntry.js" },
  shared: { react: { singleton: true, requiredVersion: "^19.0.0" } },
});
```

```js
const Checkout = lazy(() => import("checkout/CheckoutPage"));
```

Separately deployed applications share modules at **runtime**, so a team can deploy its part independently. `shared` with `singleton: true` prevents two copies of React, which would otherwise break hooks ([[17.1 - Rules of Hooks and How They Work]]).

This is the primary technical foundation for micro frontends, and the coordination costs are substantial ([[28.9 - Micro Frontends]]). Rspack and Vite both have federation implementations now, so it is no longer webpack-exclusive.

## Reading someone else's config

Configs accumulate. A useful order for understanding one:

1. **`entry` and `output`** — what is built and where it goes
2. **`mode`** and how environments differ
3. **`module.rules`** — which file types are handled and by what
4. **`resolve.alias`** — the import shortcuts used throughout the code
5. **`plugins`** — what else is happening
6. **`optimization`** — chunking and minification strategy

`webpack-merge` splitting configs into `common`, `dev` and `prod` files is the common structure and is worth preserving when editing.

## How senior engineers actually use this

**They swap `babel-loader` for `swc-loader` first** when build times are a problem — it is a one-line change with the largest effect.

**They enable filesystem caching**, which is free and substantial.

**They set `runtimeChunk: "single"`**, since without it every deploy invalidates the main bundle unnecessarily.

**They migrate to Rspack rather than Vite** when the goal is speed on an existing project, because the config largely carries over.

**They avoid adding webpack to new projects** unless Module Federation is a requirement.

## Common pitfalls

- Loaders applied in the wrong order, since `use` runs right to left.
- `mode` unset, shipping a development build of React.
- Missing `historyApiFallback`, so SPA routes 404 on refresh in development.
- No `runtimeChunk`, so the main bundle hash changes every build.
- `splitChunks` left at the default, which only splits async chunks.
- `babel-loader` when `swc-loader` would be an order of magnitude faster.
- Module Federation without `singleton: true` on React, producing duplicate copies.

## Interview angle

Webpack questions appear when the role involves an existing codebase. Have the five concepts ready — entry, output, loaders, plugins, resolve — with the distinction that loaders transform files while plugins hook the build lifecycle, and that loaders apply right to left. For "how would you speed up a slow webpack build", the ordered answer is: replace Babel with SWC or esbuild, enable filesystem caching, use a faster minifier, and measure with the bundle analyzer before doing anything else.
