# Platform Event and Streaming Limits

## Two categories

**Per-transaction limits** on publishing, which behave like every other governor limit.

**Daily allocations** on publishing and delivery, which are org-wide and shared — exhausting them affects everything until the window resets.

The second category is the one that causes production incidents, because the failure is org-wide and the symptom is silence rather than an error.

## Publishing limits

```
EventBus.publish() counts as one DML statement
   → subject to the 150 DML statement limit
Events published per transaction     part of the 10,000 DML row limit
Maximum event message size           1 MB
```

**One `publish` call is one DML statement regardless of how many events it contains**, which is the same bulkification rule as everywhere else:

```java
// 200 DML statements
for (Warranty_Claim__c claim : approvedClaims) {
    EventBus.publish(new Claim_Approved__e(Claim_Id__c = claim.Id));
}

// One
List<Claim_Approved__e> events = new List<Claim_Approved__e>();
for (Warranty_Claim__c claim : approvedClaims) {
    events.add(new Claim_Approved__e(Claim_Id__c = claim.Id));
}
EventBus.publish(events);
```

## Daily publish allocation

Based on edition, with add-ons purchasable. High-volume platform events and Change Data Capture events draw from allocations sized in the millions for larger editions, and much smaller ones below that.

```java
Map<String, System.OrgLimit> limits = OrgLimits.getMap();
System.OrgLimit publishes = limits.get('DailyStandardVolumePlatformEvents');
System.debug(publishes.getValue() + ' of ' + publishes.getLimit());
```

Exhausting it means `publish` starts failing, and code that does not check the `SaveResult` will not notice:

```java
List<Database.SaveResult> results = EventBus.publish(events);

for (Database.SaveResult result : results) {
    if (!result.isSuccess()) {
        // an exhausted allocation surfaces here, not as an exception
        for (Database.Error err : result.getErrors()) {
            AutomationLogger.logError('EventPublish', null,
                err.getStatusCode() + ': ' + err.getMessage());
        }
    }
}
```

Ignoring the results is the most common defect in event publishing, and it makes an allocation problem invisible.

## Delivery allocation, counted per subscriber

**This is the limit that surprises orgs.**

The daily delivery allocation counts **each delivery to each subscriber**. One event with five external subscribers consumes five deliveries.

```
1 event published
  → CometD subscriber          1 delivery
  → Pub/Sub subscriber         1 delivery
  → Event Relay to AWS         1 delivery
  → a second Pub/Sub consumer  1 delivery
                               = 4 deliveries from one publish
```

Adding a subscriber multiplies consumption on every event it receives, and the allocation is org-wide. An architecture that grows from two consumers to six has tripled its delivery consumption with no change to the publisher.

**Apex triggers and flows subscribing do not count** toward the delivery allocation — only external subscribers do. That asymmetry is worth knowing when deciding where to process an event.

## Change Data Capture volume

CDC publishes automatically on every record change, which makes it the easiest way to exhaust an allocation.

An object receiving 80,000 records a year, each updated four times, produces 320,000 change events annually — multiplied by every subscriber.

**Enable CDC only on objects an external system genuinely needs to track**, not on everything for completeness. A checkbox in Setup is a substantial ongoing cost. See [[12.9 - Change Data Capture]].

Filtering at the source with a custom channel reduces it:

```
Channel:  Claim_Events__chn
Members:  Warranty_Claim__ChangeEvent
Filter:   Claim_Amount__c > 100000
```

Filtering before delivery is far cheaper than filtering in the subscriber, because unfiltered events still consume the allocation.

## Subscriber batch size and lag

An Apex trigger on a platform event processes events in batches, up to 2,000 by default, configurable per trigger.

The batch runs as one transaction with normal governor limits. A subscriber doing per-event queries across a 2,000-event batch will exceed the query limit.

```java
public with sharing class ClaimApprovedHandler {

    public static void handle(List<Claim_Approved__e> events) {
        Set<Id> claimIds = new Set<Id>();
        for (Claim_Approved__e event : events) {
            claimIds.add(event.Claim_Id__c);
        }

        // one query for the whole batch, not one per event
        Map<Id, Warranty_Claim__c> claims = new Map<Id, Warranty_Claim__c>([
            SELECT Id, Claim_Number__c, Account__c FROM Warranty_Claim__c WHERE Id IN :claimIds
        ]);

        processAll(events, claims);
    }
}
```

Reducing the batch size on the trigger is the mitigation when per-event work is genuinely heavy:

```
Setup → Platform Events → Claim_Approved__e → Trigger → Batch Size: 200
```

**Subscriber lag** is the symptom of a subscriber that cannot keep up:

```sql
SELECT Topic, Type, Position, Tip, Status, ExternalId
FROM EventBusSubscriber
WHERE Topic = 'Claim_Approved__e'
```

`Position` well behind `Tip` means events are queueing. Since retention is 72 hours, a subscriber falling behind by more than that loses events permanently.

## Retention

```
Platform events and CDC     72 hours
PushTopics and generic streaming   24 hours
```

A subscriber down longer than the retention window has a **permanent gap** and needs a reconciliation pass — usually a `SystemModstamp` query for the affected period.

This is why storing the last processed replay Id durably matters, and why a production subscriber needs a path for an expired replay Id. See [[13.9 - Pub-Sub API and Event Relay]].

## Retry limits

A platform event trigger that throws is retried, up to a small number of attempts, after which the event is **discarded**.

```java
public static void handle(List<Claim_Approved__e> events) {
    EventBus.TriggerContext context = EventBus.TriggerContext.currentContext();

    for (Claim_Approved__e event : events) {
        try {
            process(event);
        } catch (Exception e) {
            if (context.retries < 3) {
                // resume from this event rather than reprocessing the whole batch
                context.setResumeCheckpoint(event.ReplayId);
                throw e;
            }
            // give up and record it durably, since the event is about to be discarded
            logPermanentFailure(event, e);
        }
    }
}
```

**Without `setResumeCheckpoint`, a retry reprocesses the entire batch**, including the events that already succeeded — which for a non-idempotent handler produces duplicates.

**After the retry limit the event is gone.** Anything that must not be lost has to be recorded durably before giving up.

## Concurrent streaming clients

```
Concurrent CometD clients per org    1,000 to 2,000, by edition
```

**Every browser tab with a subscribing component is a client.**

In a Service Cloud console where agents open a dozen tabs each, this arrives faster than expected. Fifty agents with ten tabs is 500 clients from one component.

The mitigations:

**Unsubscribe in `disconnectedCallback`.** A component that does not leaks a subscription per tab opened, and they accumulate for the session. See [[14.5 - Component Lifecycle Hooks]].

**Put the subscription in one place.** A utility bar component subscribing once, publishing to page components through Lightning Message Service, uses one client instead of one per tab. See [[14.8 - Lightning Message Service]].

That second pattern is worth adopting deliberately in any console app with real-time updates.

## Event size

```
1 MB maximum event message size
```

Large payloads are the wrong design regardless of the limit. **Send an Id; let the subscriber fetch what it needs.**

A subscriber querying fresh data also gets the current state rather than a snapshot from publish time, which is usually more correct.

## Monitoring

```sql
SELECT Topic, Type, Position, Tip, Status
FROM EventBusSubscriber
```

```java
System.OrgLimit deliveries = OrgLimits.getMap().get('DailyDeliveredPlatformEvents');
System.OrgLimit publishes = OrgLimits.getMap().get('DailyStandardVolumePlatformEvents');
```

Three things worth checking daily in an event-driven org:

**Publish and delivery consumption**, trended. A step change means a new subscriber or a new CDC-enabled object.

**Subscriber lag.** Position against tip.

**Failed publishes**, from the `SaveResult` logging above.

## Designing within the limits

**Publish business events, not data changes.** A `Claim_Approved__e` carrying an Id is one event; CDC on the claim object publishes on every field edit including ones nobody cares about.

**Filter at the source** with custom channels rather than in the subscriber.

**Consolidate subscribers.** Five external systems each subscribing is five deliveries per event; one subscriber fanning out on the other side is one.

**Consider whether polling would do.** A nightly warehouse load is simpler and cheaper as a Bulk API query on `SystemModstamp` than as a streaming subscriber that must be operated continuously and consumes delivery allocation on every change. Streaming earns its place when latency matters or deletions must be tracked. See [[13.9 - Pub-Sub API and Event Relay]].

## Practical guidance

**Publish once with a list**, never per record.

**Check the `SaveResult`** — an exhausted allocation surfaces there, not as an exception.

**Count deliveries per subscriber** when estimating consumption.

**Enable CDC selectively**, and filter with custom channels.

**Bulkify subscriber handlers** — a 2,000-event batch is one transaction.

**Use `setResumeCheckpoint`** so a retry does not reprocess successful events.

**Record permanently failed events** before the retry limit discards them.

**Unsubscribe on disconnect**, and prefer one utility bar subscription over one per tab.

**Send Ids, not payloads.**

**Monitor lag and allocation consumption**, not just failures.
