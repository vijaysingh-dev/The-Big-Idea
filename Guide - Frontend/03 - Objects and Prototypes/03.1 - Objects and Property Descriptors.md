# Objects and Property Descriptors

An object in JavaScript is a collection of **properties**, where each property is not just a value but a small record describing how that value behaves. Most of the time you never see that record. When you do — reading library source, freezing config, defining computed properties — knowing it is the difference between "this is magic" and "this is a descriptor".

## Property keys

Keys are **strings** or **symbols**. Nothing else. Numeric keys are silently converted to strings.

```js
const obj = {};
obj[1] = "a";
obj["1"] = "b";
console.log(obj); // { "1": "b" } — one property
```

Integer-like keys are also special-cased: they are stored in a separate indexed collection and always enumerate first, in ascending numeric order, regardless of insertion order.

```js
const o = { b: 1, 2: 2, a: 3, 1: 4 };
Object.keys(o); // ["1", "2", "b", "a"]
```

String keys enumerate in insertion order, integer-like keys in numeric order, symbols never enumerate at all. If ordering matters to your logic, use a `Map` ([[06.5 - Map and Set]]).

## Descriptors

Every property has a descriptor. There are two kinds.

**Data descriptor:**

```js
{
  value: 42,
  writable: true,      // can be reassigned
  enumerable: true,    // shows up in for...in, Object.keys, spread
  configurable: true,  // can be deleted or have its descriptor changed
}
```

**Accessor descriptor:**

```js
{
  get() {},
  set(v) {},
  enumerable: true,
  configurable: true,
}
```

Literal syntax gives you `writable: true, enumerable: true, configurable: true`. `Object.defineProperty` defaults all three to **false** — a genuine gotcha.

```js
const o = {};
Object.defineProperty(o, "hidden", { value: 1 });

o.hidden = 2;        // silently ignored (throws in strict mode)
Object.keys(o);      // []
JSON.stringify(o);   // "{}"
delete o.hidden;     // false
```

Reading a descriptor:

```js
Object.getOwnPropertyDescriptor(o, "hidden");
Object.getOwnPropertyDescriptors(o); // all of them
```

## Getters and setters

```js
const user = {
  first: "Vijay",
  last: "K",

  get fullName() {
    return `${this.first} ${this.last}`;
  },

  set fullName(value) {
    [this.first, this.last] = value.split(" ");
  },
};

user.fullName;              // "Vijay K"
user.fullName = "A B";      // sets first and last
```

Accessors look like data properties at the call site, which is their appeal and their hazard. A getter can be arbitrarily expensive, can throw, and can have side effects, while reading it looks free. Vue 2's reactivity was built entirely on `defineProperty` accessors; Vue 3 switched to `Proxy` because accessors cannot intercept property *addition* ([[08.3 - Proxy and Reflect]]).

## Freezing and sealing

```js
Object.preventExtensions(o); // no new properties
Object.seal(o);              // + no deletion (configurable: false)
Object.freeze(o);            // + no modification (writable: false)

Object.isFrozen(o);
```

All three are **shallow**. Freezing an object does not freeze nested objects:

```js
const config = Object.freeze({ api: { url: "/v1" } });
config.api.url = "/v2"; // succeeds
```

A recursive deep freeze:

```js
function deepFreeze(obj) {
  for (const value of Object.values(obj)) {
    if (value && typeof value === "object") deepFreeze(value);
  }
  return Object.freeze(obj);
}
```

Silent failure in sloppy mode is the trap — assignments to frozen properties do nothing and report nothing. Strict mode and modules throw, which is what you want.

## Enumeration methods compared

| Method | Own properties | Inherited | Non-enumerable | Symbols |
| --- | --- | --- | --- | --- |
| `for...in` | yes | yes | no | no |
| `Object.keys` | yes | no | no | no |
| `Object.getOwnPropertyNames` | yes | no | yes | no |
| `Object.getOwnPropertySymbols` | yes | no | yes | symbols only |
| `Reflect.ownKeys` | yes | no | yes | yes |
| spread `{...o}` | yes | no | no | yes |

`for...in` walking the prototype chain is why `hasOwnProperty` guards exist in older code. Modern equivalent:

```js
if (Object.hasOwn(obj, key)) { }
```

`Object.hasOwn` is safer than `obj.hasOwnProperty(key)`, which breaks on objects created with `Object.create(null)` or on any object with a property literally named `hasOwnProperty`.

## Optional but useful: null-prototype objects

```js
const dict = Object.create(null);
dict.constructor;    // undefined
dict["__proto__"] = "safe"; // just a normal key
```

A dictionary with no inherited properties. Useful for user-controlled keys, where inherited names like `toString` or `__proto__` would otherwise collide or enable prototype-pollution attacks. A `Map` is usually the better modern choice.

## How senior engineers actually use this

**They freeze exported constants.** `export const ROUTES = Object.freeze({...})` turns accidental mutation into a thrown error in strict mode, and communicates intent better than a comment.

**They use `defineProperty` for interop shims, not application code.** Adding a non-enumerable property to an object so it survives spread but stays out of `JSON.stringify` is a legitimate library technique — attaching metadata, marking objects as already-processed.

**They reach for descriptors when debugging "where did this property come from".** `getOwnPropertyDescriptor` reveals whether something is a plain value, a getter installed by a framework, or a proxy trap.

**They avoid getters that do work.** A getter that fires a network request or recomputes a large derivation makes `console.log(obj)` expensive and makes reads unpredictable in debuggers, which evaluate getters eagerly.

## Common pitfalls

- Forgetting that `defineProperty` defaults everything to `false`.
- Assuming `Object.freeze` is deep.
- Silent assignment failures on frozen objects in sloppy mode.
- Using `for...in` on an array — it enumerates inherited and non-index properties, and gives string keys.
- Calling `obj.hasOwnProperty` on an object whose prototype is `null` or whose data came from user input.
- Expecting `Object.keys` order to be pure insertion order when numeric-like keys are present.

## Interview angle

The usual questions are about `Object.freeze` being shallow, the difference between `Object.keys` and `for...in`, and how getters work. A strong answer mentions that every property has a descriptor with `writable`/`enumerable`/`configurable`, that literal syntax and `defineProperty` have opposite defaults, and that spread copies only own enumerable properties — which sets up the copying discussion in [[03.5 - Shallow vs Deep Copy]].
