# Batch Apex

## The tool for volume

Batch Apex processes up to **50 million records**, in chunks, with each chunk running as its own transaction with a fresh limit budget.

That last point is the whole mechanism. Fifty million records is not one enormous transaction; it is 250,000 transactions of 200 records each, and nothing accumulates between them except what you deliberately preserve.

## The three methods

```java
public with sharing class ClaimArchiveBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Number__c, Claim_Amount__c, Asset__c, Claim_Date__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Closed' AND Claim_Date__c < LAST_N_YEARS:3
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        List<Claim_Archive__b> archives = new List<Claim_Archive__b>();

        for (Warranty_Claim__c claim : scope) {
            archives.add(new Claim_Archive__b(
                Asset_Id__c = claim.Asset__c,
                Claim_Date__c = claim.Claim_Date__c,
                Claim_Number__c = claim.Claim_Number__c,
                Claim_Amount__c = claim.Claim_Amount__c
            ));
        }

        Database.insertImmediate(archives);
        Database.delete(scope, false);
    }

    public void finish(Database.BatchableContext ctx) {
        AsyncApexJob job = [
            SELECT Status, NumberOfErrors, JobItemsProcessed, TotalJobItems, ExtendedStatus
            FROM AsyncApexJob WHERE Id = :ctx.getJobId()
        ];

        insert new Batch_Run_Log__c(
            Job_Name__c = 'ClaimArchive',
            Status__c = job.Status,
            Chunks_Processed__c = job.JobItemsProcessed,
            Total_Chunks__c = job.TotalJobItems,
            Errors__c = job.NumberOfErrors,
            Message__c = job.ExtendedStatus
        );
    }
}
```

```java
Database.executeBatch(new ClaimArchiveBatch(), 200);
```

**`start`** returns the records to process, as a `QueryLocator` or an `Iterable`.

**`execute`** runs once per chunk, receiving up to the scope size.

**`finish`** runs once at the end, whether or not chunks failed. This is where logging, notification, and chaining the next job belong.

## QueryLocator versus Iterable

**`Database.QueryLocator`** handles up to 50 million records and is what you want almost always. It streams from the database and is not subject to the 50,000-row query limit.

**`Iterable<SObject>`** lets you build the collection yourself — from a callout response, from a computed set, from a custom iterator. It **is** subject to the 50,000-row limit, because you materialize it.

```java
// The usual form
public Database.QueryLocator start(Database.BatchableContext ctx) {
    return Database.getQueryLocator([SELECT Id FROM Warranty_Claim__c WHERE ...]);
}

// When the records do not come from a single query
public Iterable<SObject> start(Database.BatchableContext ctx) {
    return buildRecordsFromExternalSource();
}
```

## Scope size

The second argument to `executeBatch`, from 1 to 2,000, defaulting to 200.

The tradeoff is direct: **larger chunks mean fewer transactions and more work per transaction.**

Reduce it when:

- Each record involves heavy processing or several queries
- The chunk hits CPU or heap limits
- Records share parents and lock contention is a problem
- The object has heavy trigger automation

Increase it when:

- Processing per record is trivial
- You are hitting the daily async execution limit
- The job takes too long overall

```java
Database.executeBatch(new ClaimArchiveBatch(), 50);    // heavy per-record work
Database.executeBatch(new SimpleFieldUpdateBatch(), 2000);  // trivial per-record work
```

A job failing intermittently on some chunks and not others is usually a scope size problem, and halving it is the first thing to try.

## Database.Stateful

By default **instance variables reset between chunks.** Each `execute` gets a fresh instance.

`Database.Stateful` preserves them:

```java
public with sharing class ClaimReconciliationBatch
    implements Database.Batchable<SObject>, Database.Stateful {

    // these survive across chunks because of Database.Stateful
    private Integer processed = 0;
    private Integer failed = 0;
    private Decimal totalValue = 0;
    private List<String> errors = new List<String>();

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Amount__c, ERP_Claim_Id__c
            FROM Warranty_Claim__c WHERE ERP_Sync_Status__c = 'Pending'
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        for (Warranty_Claim__c claim : scope) {
            totalValue += claim.Claim_Amount__c ?? 0;
        }

        List<Database.SaveResult> results = Database.update(scope, false);
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                processed++;
            } else {
                failed++;
                // capping the collected errors keeps heap bounded across many chunks
                if (errors.size() < 100) {
                    errors.add(scope[i].Id + ': ' + results[i].getErrors()[0].getMessage());
                }
            }
        }
    }

    public void finish(Database.BatchableContext ctx) {
        insert new Batch_Run_Log__c(
            Job_Name__c = 'ClaimReconciliation',
            Records_Processed__c = processed,
            Records_Failed__c = failed,
            Total_Value__c = totalValue,
            Message__c = String.join(errors, '\n').left(32000)
        );
    }
}
```

**Statics are never preserved**, even with `Database.Stateful` — only instance variables. This catches people who assume the two behave alike.

**Stateful collections consume heap that persists across chunks**, so an unbounded list of errors accumulated over 10,000 chunks will exhaust it. Capping the collection is not optional.

## Callouts in batch

```java
public with sharing class ClaimSyncBatch
    implements Database.Batchable<SObject>, Database.AllowsCallouts {
```

Each chunk gets its own callout allowance — up to 100 per chunk. That is the main reason to use Batch for a large integration push rather than a Queueable chain.

The batch callout limit is separate from and higher than the daily total, so a large sync is genuinely feasible this way.

## Chaining batches

`finish` can start the next job:

```java
public void finish(Database.BatchableContext ctx) {
    logResults(ctx);

    // chaining from finish is how a multi-stage pipeline is built
    if (!Test.isRunningTest()) {
        Database.executeBatch(new ClaimNotificationBatch(), 200);
    }
}
```

This is how multi-stage processing is built: archive, then recalculate, then notify. Each stage is a separate job with its own monitoring.

The 5-concurrent-batch limit applies, so chaining sequentially is correct and firing several at once is not.

## The flex queue

Only **5 batch jobs can be queued or active** at once, org-wide. Beyond that they sit in the **flex queue**, in Holding status, up to 100.

Jobs in the flex queue can be reordered in Setup, which matters when a critical job is behind four slow ones.

```sql
SELECT Id, ApexClass.Name, Status, JobItemsProcessed, TotalJobItems,
       NumberOfErrors, CreatedDate, ExtendedStatus
FROM AsyncApexJob
WHERE JobType = 'BatchApex' AND Status IN ('Queued', 'Holding', 'Processing', 'Preparing')
ORDER BY CreatedDate
```

An org with several scheduled batch jobs firing at the same time needs their schedules staggered, or they queue behind each other and the last one runs hours late.

## Error handling

**A chunk that throws is rolled back entirely, and the job continues** with the next chunk. Partial failure is the default behaviour.

`NumberOfErrors` on `AsyncApexJob` counts failed chunks, not failed records.

For per-record resilience, use partial-success DML and handle the results:

```java
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    try {
        List<Database.SaveResult> results = Database.update(scope, false);
        recordFailures(results, scope);
    } catch (Exception e) {
        // catching at chunk level means one bad chunk does not abort the whole job
        logChunkFailure(ctx.getJobId(), e);
    }
}
```

Catching inside `execute` means the chunk completes and the job continues. Letting it throw means the chunk rolls back and the job records an error.

Which is right depends on whether partial chunk failure is acceptable — usually it is, for a cleanup or sync job, and it is not for a financial calculation.

## Batch versus Queueable

| | Batch | Queueable |
| --- | --- | --- |
| Volume | Up to 50 million | Thousands |
| Chunking | Automatic | You write it |
| Limits per chunk | Fresh | Fresh per job |
| Concurrency | 5 at once | Higher |
| Monitoring | Rich, per chunk | Job-level |
| Callouts | 100 per chunk | 100 per job |
| State | `Database.Stateful` | Constructor args |
| Setup cost | Three methods | One method |

The rule of thumb: **Batch above a few thousand records, Queueable below.** Batch's chunking and monitoring are worth the extra ceremony at volume, and unnecessary below it.

## Testing

```java
@IsTest
static void archiveBatchMovesClosedClaims() {
    List<Warranty_Claim__c> claims = TestDataFactory.createClosedClaims(250);

    Test.startTest();
    Database.executeBatch(new ClaimArchiveBatch(), 200);
    Test.stopTest();

    Integer remaining = [SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Closed'];
    Assert.areEqual(0, remaining, 'All closed claims should be archived and deleted');
}
```

**Only one chunk executes in test context**, regardless of scope size and record count. This is the most important testing constraint: a test cannot verify multi-chunk behaviour, including whether `Database.Stateful` accumulation is correct.

The practical consequence: **test `execute` directly** for logic that spans chunks.

```java
@IsTest
static void statefulCountersAccumulateAcrossChunks() {
    ClaimReconciliationBatch batch = new ClaimReconciliationBatch();
    List<Warranty_Claim__c> chunk1 = TestDataFactory.buildClaims(5);
    List<Warranty_Claim__c> chunk2 = TestDataFactory.buildClaims(5);
    insert chunk1;
    insert chunk2;

    Test.startTest();
    // calling execute directly is the only way to exercise multi-chunk accumulation
    batch.execute(null, chunk1);
    batch.execute(null, chunk2);
    Test.stopTest();

    Assert.areEqual(10, batch.getProcessedCount(), 'Counter should accumulate across chunks');
}
```

See [[19.6 - Testing Async Apex]].

## Practical guidance

**Use `QueryLocator`** unless the records genuinely do not come from a query.

**Tune scope size** to the per-record work. Halving it is the first fix for intermittent chunk failures.

**Use `Database.Stateful` only when needed**, and cap any collection it holds.

**Use partial-success DML** and record per-record failures.

**Log in `finish`**, reading `AsyncApexJob` for the summary.

**Stagger scheduled batch jobs**, or they queue behind each other.

**Test `execute` directly** for multi-chunk logic, since tests run one chunk.

**Sort by parent in the query locator** where children share parents, to reduce lock contention. See [[10.8 - Record Locking and Deadlocks]].
