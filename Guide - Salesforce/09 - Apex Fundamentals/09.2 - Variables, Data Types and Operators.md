# Variables, Data Types and Operators

## Primitives

```java
Integer count = 42;                    // 32-bit
Long largeNumber = 9223372036854775L;  // 64-bit
Decimal amount = 150000.50;            // arbitrary precision — use for money
Double ratio = 0.3333;                 // floating point — avoid for money
String name = 'Press P400';
Boolean isApproved = true;
Date claimDate = Date.today();
Datetime submittedAt = Datetime.now();
Time openingTime = Time.newInstance(9, 0, 0, 0);
Id recordId = '0015g00000XyZaAAAV';
Blob attachment = Blob.valueOf('content');
Object anything = someValue;
```

**Every primitive can be null**, including `Integer` and `Boolean`. There are no unboxed primitives, which means arithmetic on a null Integer throws a null pointer exception rather than treating it as zero.

```java
Integer count;
count + 1;  // NullPointerException

Integer safe = (count == null ? 0 : count) + 1;
```

This is the most frequent runtime error in Apex and the reason null guards appear throughout this course.

## Decimal versus Double

**Never use `Double` for currency.** Floating point cannot represent decimal fractions exactly.

```java
Double a = 0.1;
Double b = 0.2;
System.debug(a + b);              // 0.30000000000000004

Decimal c = 0.1;
Decimal d = 0.2;
System.debug(c + d);              // 0.3
```

`Decimal` also carries a **scale**, which propagates through arithmetic and affects results:

```java
Decimal amount = 100.00;
System.debug(amount.scale());                    // 2
System.debug(amount.divide(3, 2));               // 33.33
System.debug(amount.divide(3, 4));               // 33.3333
System.debug(amount.setScale(0, RoundingMode.HALF_UP));  // 100
```

`divide()` requires an explicit scale, because the result of dividing by 3 has no natural termination. Using `/` instead gives a default scale that may not be what you want.

Rounding modes matter in financial calculations: `HALF_UP`, `HALF_DOWN`, `HALF_EVEN` (banker's rounding), `UP`, `DOWN`, `CEILING`, `FLOOR`. Where money is involved, the business has an opinion about which, and it is worth asking.

## The Id type

`Id` is a first-class type, validated on assignment.

```java
Id claimId = 'a0X5g000001AbCdEAK';  // valid 18-character Id
Id bad = 'not-an-id';                // StringException at runtime
```

Ids come in 15-character (case-sensitive) and 18-character (case-insensitive) forms. The 18-character form is what the API returns and what should be stored. The 15-character form appears in older URLs and exports.

```java
Id eighteen = '0015g00000XyZaAAAV';
String fifteen = String.valueOf(eighteen).left(15);

// Comparing a 15-character string to an 18-character Id fails
System.debug(fifteen == eighteen);              // false
System.debug(Id.valueOf(fifteen) == eighteen);  // true
```

Converting to `Id` before comparing is the safe form, and it is a real source of bugs in integration code that receives 15-character values.

Determining an Id's object type without a query:

```java
Schema.SObjectType type = recordId.getSObjectType();
if (type == Warranty_Claim__c.SObjectType) { ... }

String prefix = String.valueOf(recordId).left(3);  // key prefix
```

`getSObjectType()` is more readable than key-prefix comparison and should be preferred.

## Strings

Case-insensitive comparison with `==` is the behaviour to internalize:

```java
'Press' == 'PRESS'                   // true
'Press'.equals('PRESS')              // false
'Press'.equalsIgnoreCase('PRESS')    // true
```

The commonly used methods:

```java
String s = '  Press P400  ';

s.trim()                             // 'Press P400'
s.isEmpty() / s.isBlank()            // blank includes whitespace-only
String.isBlank(s) / String.isNotBlank(s)   // null-safe static forms
s.contains('P400')
s.startsWith('Press') / s.endsWith('400')
s.substringBefore(' ') / s.substringAfter(' ')
s.substringBetween('[', ']')
s.split(',')
s.replaceAll('[^0-9]', '')
s.left(10) / s.right(10)
s.leftPad(10, '0') / s.rightPad(10)
s.capitalize() / s.toUpperCase() / s.toLowerCase()
String.join(someList, ', ')
String.format('Claim {0} for {1}', new List<String>{ number, customer })
String.escapeSingleQuotes(userInput)
```

**Use the static `String.isBlank(s)` rather than `s.isBlank()`** — the static form handles null, the instance form throws on it.

`String.join` and `String.format` are underused and make building messages much cleaner than concatenation chains.

## sObjects

```java
Warranty_Claim__c claim = new Warranty_Claim__c(
    Asset__c = assetId,
    Claim_Date__c = Date.today(),
    Status__c = 'Submitted'
);

// Dynamic access by field name
claim.put('Claim_Amount__c', 150000);
Object value = claim.get('Claim_Amount__c');

// Only fields that were queried or set
Map<String, Object> populated = claim.getPopulatedFieldsAsMap();

// An independent copy
Warranty_Claim__c copy = claim.clone(false, true, false, false);
```

`clone()` takes four booleans: preserve Id, deep clone, preserve read-only timestamps, preserve autonumber. The common form is `clone(false, true)` — a new record with copied field values, which is what you want when creating a related record from a template.

**`getPopulatedFieldsAsMap()` is the correct way to check whether a field was in the result set.** A field not selected reads as null, indistinguishable from a field that is genuinely null, and this method is how you tell the difference. It is also how the field-stripping assertion in [[03.13 - Enforcing Security in Apex and SOQL]] works.

Accessing a field that was not queried throws `SObjectException: SObject row was retrieved via SOQL without querying the requested field`. This is a clear error and a common one, and it is why selecting exactly the fields you need — rather than relying on `FIELDS(ALL)` — is worth the discipline.

## Operators

```java
+  -  *  /                     arithmetic
+                              string concatenation
==  !=                         equality (case-insensitive for String)
===  !==                       reference identity, for sObjects and objects
<  >  <=  >=                   comparison
&&  ||  !                      logical, short-circuiting
++  --  +=  -=  *=  /=         assignment forms
?:                             ternary
??                             null coalescing
?.                             safe navigation
instanceof                     type test
```

**`??` and `?.` are the two that most improve real code.**

```java
// Null coalescing: use the left value unless null
Decimal amount = claim.Approved_Amount__c ?? 0;
String region = claim.Region__c ?? 'Unknown';

// Safe navigation: returns null instead of throwing
String ownerEmail = claim.Asset__r?.Account?.Owner?.Email;
Integer nameLength = someString?.length();
```

Before these existed, the same code needed nested null checks at every level. Using them consistently removes most null pointer exceptions from relationship traversal. See [[08.2 - Relationship Queries]].

`===` compares object identity rather than value, which matters when checking whether two references point at the same sObject instance.

## Type conversion

```java
Integer.valueOf('42')
Decimal.valueOf('150000.50')
String.valueOf(someValue)          // works on almost anything
Date.valueOf('2026-08-07')
Datetime.valueOf('2026-08-07 09:30:00')
Id.valueOf(fifteenCharString)
Boolean.valueOf('true')
```

`String.valueOf()` on a Datetime produces a format that is not what you usually want for display — `format()` and `formatGMT()` are the correct methods, and the time zone behaviour from [[06.3 - Date and Datetime Functions]] applies.

```java
Datetime dt = Datetime.now();

dt.format()                              // user's time zone and locale
dt.format('yyyy-MM-dd HH:mm:ss')         // user's time zone, explicit pattern
dt.formatGMT('yyyy-MM-dd\'T\'HH:mm:ss\'Z\'')  // UTC — correct for integrations
dt.date()                                // date in GMT, not the user's zone
```

`dt.date()` returning the GMT date is the trap. For a user in Mumbai at 02:00 local, it returns yesterday.

## Constants and final

```java
public class ClaimConstants {
    public static final String STATUS_SUBMITTED = 'Submitted';
    public static final String STATUS_APPROVED = 'Approved';
    public static final Decimal AUTO_APPROVE_THRESHOLD = 50000;
    public static final Set<String> OPEN_STATUSES = new Set<String>{
        'Submitted', 'Under Review', 'Awaiting Evidence'
    };
}
```

`final` on a collection prevents reassignment, not mutation — the set above can still have values added. For genuinely immutable configuration, Custom Metadata is the better home, because it can be changed without a deployment. See [[17.1 - Custom Metadata Types]].

The practical rule: **string literals for picklist values belong in constants, not scattered through the code.** A value renamed in one place and missed in four others is a familiar defect.

## Practical guidance

**Use `Decimal` for money**, never `Double`.

**Null-guard every arithmetic operation** on a nullable field, or use `??`.

**Use `?.` for relationship traversal** consistently.

**Use `String.isBlank(s)`**, the null-safe static form.

**Convert to `Id` before comparing** anything that might be 15 characters.

**Remember `==` on String is case-insensitive.**

**Use `getPopulatedFieldsAsMap()`** to distinguish "not queried" from "null".

**Put picklist values in constants**, and configuration in Custom Metadata.
