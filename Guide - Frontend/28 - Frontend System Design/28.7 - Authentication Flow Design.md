# Authentication Flow Design

## Where credentials live

The decision that determines everything else.

| Storage | XSS exposure | CSRF exposure | Cross-tab | Sent automatically |
| --- | --- | --- | --- | --- |
| `localStorage` | **yes** — readable by any script | no | yes | no |
| `sessionStorage` | **yes** | no | no | no |
| JS memory | limited — lost on reload | no | no | no |
| `httpOnly` cookie | **no** — unreadable by JS | yes, needs mitigation | yes | yes |

**`httpOnly` cookies are the safer default.** An XSS vulnerability can read `localStorage` and exfiltrate a token; it cannot read an `httpOnly` cookie ([[15.5 - JWT Sessions and Token Storage]]).

```
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1209600
```

`SameSite=Lax` blocks the cookie on cross-site POST requests, which handles most CSRF. For flows that legitimately need cross-site requests, `SameSite=None; Secure` plus a CSRF token is required ([[15.6 - Frontend Security]]).

The common counter-argument — "we need a token for the Authorization header" — is usually answerable: if the API is same-site or behind the same domain via a proxy, cookies work. If it genuinely is not, the fallback is an **access token in memory** with a refresh token in an `httpOnly` cookie. Memory is lost on reload, so the app silently refreshes on startup.

Never put a long-lived token in a URL — query strings end up in logs, referrers and browser history.

## The refresh pattern

```
Access token   short-lived (5–15 min), in memory or a cookie
Refresh token  long-lived (days), httpOnly cookie, rotated on use
```

Short access tokens limit the damage window if one leaks. Refresh token rotation — issuing a new one on every use and invalidating the old — means a stolen refresh token is detectable: when both the attacker and the user present the same token, the server sees reuse and can revoke the whole family.

```ts
let refreshPromise: Promise<void> | null = null;

async function withAuth(request: () => Promise<Response>) {
  try {
    return await request();
  } catch (err) {
    if (err.status !== 401) throw err;

    refreshPromise ??= refresh().finally(() => { refreshPromise = null; });
    await refreshPromise;

    return request();          // retry ONCE
  }
}
```

Two requirements that are easy to miss:

**Deduplicate concurrent refreshes.** Five parallel requests hitting a 401 must trigger one refresh, not five — with rotation, four of them would fail and could trigger a false reuse alarm ([[04.7 - Async Concurrency Patterns]]).

**Retry exactly once.** A persistently failing refresh otherwise loops forever.

This belongs in the data layer, so no component ever handles an expired session ([[28.4 - The Data Layer]]).

## Session state as server state

```jsx
function AuthProvider({ children }) {
  const { data: user, isLoading } = useQuery({
    queryKey: ["session"],
    queryFn: fetchSession,
    retry: false,
    staleTime: 5 * 60_000,
  });

  const value = useMemo(() => ({ user, isLoading }), [user, isLoading]);
  return <AuthContext value={value}>{children}</AuthContext>;
}
```

The session has a source of truth on the server, goes stale, and needs revalidation — which makes it server state, not client state ([[20.1 - Where State Should Live]]).

The alternative — decoding a JWT client-side — tells you what the token *claims*, not whether the server still accepts it. A revoked session still decodes fine. Client-side decoding is acceptable for optimistic rendering, never for a security decision.

`retry: false` matters: an unauthenticated user gets a 401, and retrying it three times with backoff delays the redirect to login by several seconds.

## Route protection

```jsx
function RequireAuth() {
  const { user, isLoading } = useAuth();
  const location = useLocation();

  if (isLoading) return <FullPageSpinner />;
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;

  return <Outlet />;
}
```

The `isLoading` check is not optional — without it, the first render before the session resolves redirects an authenticated user to login on every refresh ([[23.4 - Protected Routes and Auth Flows]]).

**Client guards are UX, not security.** The API must authorize every request independently. Hiding a route hides the UI, not the data.

Where the framework supports it, move the check server-side so protected content is never sent:

```ts
loader: async ({ request }) => {
  const session = await getSession(request);
  if (!session) throw redirect(`/login?redirect=${encodeURIComponent(pathname)}`);
  return getData(session.userId);
}
```

Validate the redirect destination, or you have an open redirect:

```ts
const safe = target?.startsWith("/") && !target.startsWith("//") ? target : "/";
```

The `//` check matters — `//evil.com` is a protocol-relative URL, and an unvalidated redirect turns your login page into a phishing vector.

## OAuth and third-party providers

For a browser client, the correct flow is **Authorization Code with PKCE**:

```
1. Generate a random code_verifier; derive code_challenge = SHA256(verifier)
2. Redirect to the provider with code_challenge and a state parameter
3. Provider redirects back with a code
4. Exchange code + verifier for tokens — ideally on your server
```

The implicit flow, which returned tokens directly in the URL fragment, is deprecated and should not be used.

Two parameters that are security-critical: `state` prevents CSRF on the callback (verify it matches what you generated), and PKCE prevents an intercepted authorization code from being redeemed by anyone else.

Doing the token exchange **on your server** — the "backend for frontend" pattern — means the tokens never reach the browser at all, and the session becomes an ordinary `httpOnly` cookie. This is the recommended shape and it sidesteps the entire client-side token storage question.

## Logout

```ts
async function signOut() {
  await api.post("/auth/logout");     // invalidate server-side
  queryClient.clear();                 // clear cached data
  window.location.href = "/login";     // full reload clears all memory
}
```

Three parts, all necessary:

**Server-side invalidation.** Deleting a client cookie does nothing if the session remains valid — a captured token still works.

**Cache clearing.** Otherwise the next user on a shared device sees the previous user's data flash before refetching ([[28.6 - Caching Strategy Across Layers]]).

**A full reload**, not client navigation, so every in-memory store and closure is discarded.

Cross-tab logout needs a broadcast:

```ts
const channel = new BroadcastChannel("auth");
channel.onmessage = (e) => { if (e.data === "logout") window.location.href = "/login"; };
```

Without it, a user logging out in one tab remains apparently logged in elsewhere.

## Permissions

```ts
const { can } = usePermissions();

{can("invoice:refund") && <RefundButton />}
```

Capability strings scale better than role checks — roles map to capabilities in one place, so adding a role does not require editing every guard.

Hiding a control the user cannot use is good UX. It is **not** access control; the endpoint must still reject the request. A useful discipline is writing the server check first, because doing it the other way round tends to leave the server check for later.

## MFA and session lifecycle

Multi-factor adds an intermediate state:

```
credentials verified → MFA required → fully authenticated
```

The partially-authenticated state needs its own handling — a short-lived token valid only for the MFA endpoint, so it cannot be used to access data.

Session expiry deserves a warning rather than a silent redirect that loses unsaved work:

```jsx
{expiresIn < 120 && <SessionWarning onExtend={refresh} />}
```

Losing a half-written form to a silent logout is a memorable bad experience.

## How senior engineers actually use this

**They default to `httpOnly` cookies** and treat `localStorage` tokens as a decision requiring justification.

**They handle 401 centrally** with deduplicated refresh and a single retry.

**They treat the session as server state**, not as a decoded JWT.

**They validate redirect destinations**, closing the open-redirect hole.

**They clear caches and hard-reload on logout**, and broadcast it across tabs.

**They enforce authorization server-side** and treat client guards as UX only.

## Common pitfalls

- Tokens in `localStorage`, exposed to any XSS.
- No loading state in the guard, redirecting authenticated users on refresh.
- Concurrent 401s triggering parallel refresh calls.
- Retry loops when refresh itself fails.
- Unvalidated redirect parameters.
- Cache not cleared on logout.
- Client-side JWT decoding used as an authorization decision.
- Missing `state` or PKCE in an OAuth flow.
- Sending unauthorized-but-authenticated users to login instead of a 403 page.

## Interview angle

"How would you implement authentication in a SPA" should open with storage — `httpOnly` cookies versus `localStorage`, and the XSS-versus-CSRF tradeoff that follows — then the short access token plus rotating refresh token pattern with deduplicated refresh. State clearly that client-side route guards are UX and the API enforces access. The details that mark experience: the loading state that prevents the redirect flash, open-redirect validation, and clearing the cache with a hard reload on logout so a shared device does not leak the previous user's data.
