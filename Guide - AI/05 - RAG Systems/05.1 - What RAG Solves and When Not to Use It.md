# What RAG Solves and When Not to Use It

## Definition

**RAG (Retrieval-Augmented Generation)**: A pattern where relevant documents are retrieved from an external store at query time and injected into the LLM's context before generation.

```
Without RAG:
  User: "What was Apple's Q3 2024 revenue?"
  LLM:  "I don't have that information." (or hallucination)

With RAG:
  1. Retrieve: search index for "Apple Q3 2024 revenue"
  2. Return:   "Apple's Q3 2024 earnings report shows revenue of $85.8B..."
  3. Inject:   Put that into context
  4. LLM:      "According to Apple's Q3 2024 earnings report, revenue was $85.8B."
```

---

## The Three Problems RAG Solves

### Problem 1: Knowledge Cutoff

LLMs have a training cutoff date. They can't answer questions about events after that date. RAG gives them access to a live, updatable knowledge base.

### Problem 2: Private / Domain Knowledge

LLMs don't know your company's internal documents, proprietary data, or specialized domain knowledge not well-represented in training. RAG injects exactly that knowledge at query time.

### Problem 3: Hallucination on Specific Facts

Even when models "know" something, they may misremember specific numbers, dates, or names. RAG grounds answers in actual source text, dramatically reducing hallucination on factual queries.

---

## When RAG is the Right Choice

```
✅ Use RAG when:
├── Knowledge changes frequently (news, prices, docs)
├── Knowledge is private / confidential
├── Queries require citing specific source documents
├── Domain knowledge is narrow and deep (internal wikis)
├── Answers need to be auditable (show your source)
└── Multiple document types (PDFs, Slack, Confluence, Notion)
```

---

## When NOT to Use RAG

This is the more important list. RAG is overused.

### ❌ Don't Use RAG For: Behavioral Changes

If you want the model to consistently use a certain tone, format, or reasoning style — that's a **prompting or fine-tuning problem**, not a RAG problem.

### ❌ Don't Use RAG For: Pure Reasoning Tasks

"Solve this logic puzzle" or "Explain quantum entanglement" — no external knowledge needed. RAG adds latency and noise without helping.

### ❌ Don't Use RAG For: Short Factual Lookups That Can Be Hardcoded

If you have 10 key facts that never change, put them in the system prompt. Don't build an index for 10 documents.

### ❌ Don't Use RAG When: Context Window is Sufficient

If your entire knowledge base fits comfortably in the context window, just include it directly. Modern 128K–1M context windows make small knowledge bases fully ingestible without retrieval.

### ❌ Don't Use RAG to Inject General Knowledge

If you want the model to "know more" about a general topic, fine-tuning is more appropriate than building a retrieval layer. RAG for general knowledge causes retrieval noise and adds latency.

### The RAG vs Fine-tuning Decision

```
Is the knowledge:
├── Dynamic / frequently updated?     → RAG
├── Static but domain-specific?       → Fine-tuning OR RAG
│   └── Needs to be cited/auditable?  → RAG
│   └── Just needs to inform behavior?→ Fine-tuning
├── About behavior/style?             → Fine-tuning (prompting first)
└── About reasoning capability?       → Fine-tuning (or better model)
```

## RAG Failure Modes

Understanding these determines your system's architecture:

### Retrieval Failure

The relevant document exists in the index but isn't retrieved.

- Wrong chunking strategy → relevant content split across chunks
- Vocabulary mismatch → dense retrieval misses exact-match queries
- Missing metadata → can't filter to relevant subset
- **Fix**: Hybrid search, better chunking, query expansion

### Context Insufficiency

Relevant documents are retrieved but don't contain enough information.

- Question requires synthesizing across many documents
- Answer exists in the index but not in the top-K chunks
- **Fix**: Increase top-K, parent-child chunking, multi-hop retrieval

### Context Confusion

Multiple retrieved documents contradict each other or contain noise.

- Stale documents alongside fresh ones
- Multiple documents partially answering the question
- **Fix**: Freshness filtering, reranking, source trust weighting

### Generation Failure

Retrieval is good but the LLM misuses the context.

- Ignores context and uses parametric memory instead
- Garbles or misquotes the source
- **Fix**: Stronger grounding instructions, output validation

### Permission / Access Failure

Returns documents the user shouldn't see.

- Access control not enforced in retrieval layer
- **Fix**: Per-query permission filtering (critical for enterprise RAG)

## Naive RAG vs Advanced RAG

|Aspect|Naive RAG|Advanced RAG|
|---|---|---|
|Retrieval|Single dense vector search|Hybrid + reranking|
|Chunking|Fixed-size|Semantic / hierarchical|
|Query|As-is|Transformed / expanded|
|Context|Raw chunks|Compressed / reordered|
|Permissions|None|Per-user ACL enforcement|
|Freshness|Batch re-index|Incremental / near-real-time|
|Evaluation|None|RAGAS + continuous monitoring|

Most tutorials teach Naive RAG. Production systems require Advanced RAG.
