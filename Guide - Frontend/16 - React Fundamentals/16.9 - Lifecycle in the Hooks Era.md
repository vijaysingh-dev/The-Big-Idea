# Lifecycle in the Hooks Era

Class components had named lifecycle methods. Hooks have no direct equivalents, and translating one to the other mechanically produces bad code. The mapping below is for **reading legacy code**, not for structuring new code.

## The mapping

| Class method | Hooks equivalent |
| --- | --- |
| `constructor` | `useState(initial)`, or `useState(() => init())` |
| `componentDidMount` | `useEffect(fn, [])` |
| `componentDidUpdate` | `useEffect(fn, [deps])` |
| `componentWillUnmount` | the cleanup returned from `useEffect` |
| `shouldComponentUpdate` | `React.memo` |
| `getDerivedStateFromProps` | compute during render, or `key` |
| `getSnapshotBeforeUpdate` | `useLayoutEffect` |
| `componentDidCatch` | still requires a class — no hook equivalent |
| `getDerivedStateFromError` | still requires a class |

```jsx
class Old extends React.Component {
  componentDidMount() { this.sub = subscribe(this.props.id); }
  componentDidUpdate(prev) {
    if (prev.props.id !== this.props.id) {
      this.sub.unsubscribe();
      this.sub = subscribe(this.props.id);
    }
  }
  componentWillUnmount() { this.sub.unsubscribe(); }
}

function New({ id }) {
  useEffect(() => {
    const sub = subscribe(id);
    return () => sub.unsubscribe();
  }, [id]);
}
```

The hooks version is not a shorter translation — it is a different model. Three lifecycle methods that had to agree with each other collapse into one block where setup and teardown sit together and cannot drift apart.

## Why the mental shift matters

The class model is **lifecycle-oriented**: "run this when mounting, that when updating". The hooks model is **synchronization-oriented**: "keep this external thing in sync with these values".

`useEffect` does not mean "after render". It means "synchronize with the outside world whenever these dependencies change" — and the cleanup means "undo the previous synchronization". Mount and unmount are just the first and last cases of that.

This reframing is the point of the official documentation calling the relevant page "Synchronizing with Effects" rather than "Lifecycle" ([[17.3 - useEffect and the Dependency Array]]).

The practical consequence: thinking "I need a `componentDidMount`" leads to `useEffect(fn, [])`, which is very often the wrong dependency array. Thinking "what should this effect stay in sync with" produces the right one.

## The `[]` trap

```jsx
useEffect(() => {
  fetchUser(userId).then(setUser);
}, []);   // "run once on mount" — but stale when userId changes
```

An empty array is correct only when the effect genuinely depends on nothing. Using it as shorthand for `componentDidMount` is the most common hooks bug, and it produces stale closures ([[02.3 - Closures]]) and data that never updates.

## What has no hooks equivalent

**Error boundaries.** `componentDidCatch` and `getDerivedStateFromError` still require a class component ([[22.1 - Error Boundaries]]). In practice, everyone uses `react-error-boundary` rather than writing the class.

**`shouldComponentUpdate` with custom logic.** `React.memo` accepts a comparison function, but it compares props only — it cannot see state or context. In practice this is rarely a real limitation.

## The ordering of effects

Understanding when things run matters more than the class mapping:

```
render (component functions called)
  ↓
DOM mutated
  ↓
useLayoutEffect cleanup, then useLayoutEffect     ← blocks paint
  ↓
browser paints
  ↓
useEffect cleanup, then useEffect                 ← after paint
```

Cleanup of the **previous** effect runs before the next effect, not after. And effects run **child-first** — a child's effect fires before its parent's, because the child commits first.

The child-first ordering matters when a parent effect depends on something a child effect sets up; it will not be there yet.

## Strict Mode changes the sequence

In development, Strict Mode mounts, unmounts and remounts every component once:

```
mount → effect → cleanup → effect
```

This is a test that every effect can be safely re-run, which is required for the future Activity component and for concurrent features that may discard and restore trees ([[18.7 - Strict Mode and Double Invocation]]).

An effect that breaks under double-invocation has a real bug — usually a missing cleanup or a non-idempotent setup. Suppressing it with a ref guard hides the problem rather than fixing it.

## What to do instead of lifecycle thinking

Most code that reaches for a lifecycle equivalent does not need an effect at all ([[17.4 - useEffect Pitfalls]]):

| Instinct | Better approach |
| --- | --- |
| "Update state when props change" | compute during render, or use `key` |
| "Transform data after fetching" | transform in the render or the query function |
| "Run something when the user clicks" | put it in the event handler |
| "Fetch data on mount" | a data library with caching and cancellation |
| "Reset state when the id changes" | `key` on the component |
| "Notify the parent when state changes" | call the callback in the same handler that sets state |

The last one is worth expanding:

```jsx
// Anti-pattern — extra render, and fires on mount
useEffect(() => { onChange(value); }, [value]);

// Better — one path, no extra render
const handleChange = (v) => { setValue(v); onChange(v); };
```

## Class components today

They still work and are not deprecated, but function components are where all new features land — hooks, Server Components, the compiler, `use`, transitions. Legacy class code does not need urgent migration, but new code should not add classes except for error boundaries.

The one genuine advantage classes retained — instance methods callable from a parent via ref — is covered by `useImperativeHandle` ([[22.3 - forwardRef and useImperativeHandle]]).

## How senior engineers actually use this

**They do not think in lifecycles.** The question is "what external system does this synchronize with, and what are its inputs", which produces the dependency array directly.

**They treat a growing effect count as a design smell.** Most components in a well-structured application have zero or one effect.

**They know the ordering** — layout effects before paint, passive effects after, cleanup before the next run, children before parents — because timing bugs are otherwise impossible to reason about.

**They use `react-error-boundary`** rather than hand-writing the class.

## Common pitfalls

- Using `[]` as a mechanical translation of `componentDidMount`.
- Splitting setup and teardown into separate effects, so they can drift.
- Assuming parent effects run before child effects.
- Writing an effect to derive state from props.
- Expecting cleanup to run after the next effect rather than before it.
- Adding a ref guard to defeat Strict Mode double-invocation.

## Interview angle

"How do hooks map to lifecycle methods" is common, and the mapping table is the expected answer — but the better answer notes that the mapping is a reading aid rather than a design guide, because `useEffect` models synchronization rather than lifecycle points. Mentioning that most lifecycle instincts (deriving state, notifying parents, transforming fetched data) should not be effects at all is what distinguishes someone who has actually maintained hooks code.
