# Mixed DML and Setup Objects

## The error

```
System.DmlException: MIXED_DML_OPERATION, DML operation on setup object is not permitted
after you have updated a non-setup object (or vice versa)
```

One transaction cannot perform DML on both a **setup object** and a **non-setup object**.

```java
// Throws
insert new Account(Name = 'Northwind');
insert new User(...);
```

The restriction exists because setup objects are stored and cached differently — permission and metadata changes need to propagate in ways that record changes do not. Mixing them in one transaction would leave the platform unable to guarantee consistency.

## What counts as a setup object

The ones you will actually meet:

```
User
Group
GroupMember
PermissionSet
PermissionSetAssignment
PermissionSetLicenseAssign
Profile
UserRole
QueueSObject
Territory / Territory2
ObjectTerritory2Association
UserTerritory2Association
CustomPermission
SetupEntityAccess
FieldPermissions
ObjectPermissions
```

Custom Settings and Custom Metadata are **not** setup objects in this sense — Custom Settings behave as ordinary objects for DML purposes, and Custom Metadata is deployed rather than inserted.

`Account`, `Contact`, `Case`, and every custom object are non-setup.

## The standard workaround

Move one side into a separate transaction, which resets the restriction.

```java
public with sharing class UserProvisioningService {

    public static void provision(Account account, String serializedUser) {
        insert account;

        // the future method runs in its own transaction, so the setup DML is isolated
        createUserAsync(serializedUser);
    }

    @future
    private static void createUserAsync(String serializedUser) {
        User u = (User) JSON.deserialize(serializedUser, User.class);
        insert u;
    }
}
```

`@future` methods take only primitives and collections of primitives, which is why the User is serialized to JSON rather than passed directly.

A Queueable gives more flexibility, since it can take an object:

```java
public with sharing class UserProvisioningQueueable implements Queueable {

    private final List<User> usersToCreate;
    private final List<PermissionSetAssignment> assignments;

    public UserProvisioningQueueable(List<User> users, List<PermissionSetAssignment> assignments) {
        this.usersToCreate = users;
        this.assignments = assignments;
    }

    public void execute(QueueableContext context) {
        insert usersToCreate;

        for (Integer i = 0; i < assignments.size(); i++) {
            assignments[i].AssigneeId = usersToCreate[Math.mod(i, usersToCreate.size())].Id;
        }
        insert assignments;
    }
}
```

Both User and PermissionSetAssignment are setup objects, so they coexist in the same transaction without a problem. The restriction is only about mixing the two categories.

## Where this bites in practice

**Provisioning flows.** Creating an Account and a portal User together — an Experience Cloud self-registration, a partner onboarding process.

**Assigning permissions after creating records.** A trigger on a custom object that assigns a permission set based on the record's content.

**Test data setup.** Creating a test User and test records in the same method, which is the most common encounter.

**Group and queue membership automation.** A flow or trigger adding someone to a public group in response to a record change.

**Territory assignment** driven by record data.

## Test context

Tests hit this constantly, and `System.runAs()` is the sanctioned exception.

```java
@IsTest
static void claimIsVisibleToTheAssignedEngineer() {
    User engineer;

    // creating the user inside runAs isolates the setup DML from the record DML that follows
    System.runAs(new User(Id = UserInfo.getUserId())) {
        engineer = TestDataFactory.createUser('Service_Engineer');
        insert engineer;
    }

    Asset asset = TestDataFactory.createAsset();
    Warranty_Claim__c claim = TestDataFactory.createClaim(asset.Id);

    System.runAs(engineer) {
        List<Warranty_Claim__c> visible = [SELECT Id FROM Warranty_Claim__c WHERE Id = :claim.Id];
        Assert.areEqual(1, visible.size(), 'Engineer should see the claim');
    }
}
```

Wrapping the setup-object DML in a `runAs` block — even with the current user — creates the separation the platform requires. This is a documented and intended use, not a hack.

The cleanest structure is a dedicated test utility that creates users inside `runAs`, so every test class gets it right without thinking about it:

```java
@IsTest
public with sharing class TestUserFactory {

    public static User create(String profileName, String permissionSetName) {
        User u;
        System.runAs(new User(Id = UserInfo.getUserId())) {
            Profile p = [SELECT Id FROM Profile WHERE Name = :profileName LIMIT 1];
            u = new User(
                FirstName = 'Test',
                LastName = 'User' + System.currentTimeMillis(),
                Email = 'test' + System.currentTimeMillis() + '@example.com',
                Username = 'test' + System.currentTimeMillis() + '@example.com.test',
                Alias = 'tuser',
                ProfileId = p.Id,
                TimeZoneSidKey = 'Asia/Kolkata',
                LocaleSidKey = 'en_IN',
                EmailEncodingKey = 'UTF-8',
                LanguageLocaleKey = 'en_US'
            );
            insert u;

            if (String.isNotBlank(permissionSetName)) {
                PermissionSet ps = [SELECT Id FROM PermissionSet WHERE Name = :permissionSetName LIMIT 1];
                insert new PermissionSetAssignment(AssigneeId = u.Id, PermissionSetId = ps.Id);
            }
        }
        return u;
    }
}
```

`Username` must be globally unique across all of Salesforce, which is why the timestamp is appended.

See [[19.3 - TestSetup and Test Data Factories]].

## Flows and mixed DML

The restriction applies to flows exactly as it does to Apex. A record-triggered flow that updates a User and a custom object in the same transaction throws the same error.

The workaround in flow is an **asynchronous path**, which runs in a separate transaction — the declarative equivalent of moving the work to a Queueable. See [[07.3 - Record-Triggered Flows]].

## Detecting it before it happens

There is no runtime check for "am I about to mix DML", so the defence is structural: **keep setup-object DML in dedicated classes**, and make those classes async by construction.

```java
public with sharing class SetupObjectService {

    // every method here is async, so callers cannot accidentally mix
    public static void assignPermissionSetAsync(Set<Id> userIds, String permissionSetName) {
        System.enqueueJob(new PermissionAssignmentQueueable(userIds, permissionSetName));
    }

    public static void addToGroupAsync(Set<Id> userIds, String groupDeveloperName) {
        System.enqueueJob(new GroupMembershipQueueable(userIds, groupDeveloperName));
    }
}
```

A service whose public methods are all async removes the possibility of a caller getting it wrong, which is better than documenting the constraint and hoping.

## The ordering trap

The error is symmetrical — setup after non-setup, or non-setup after setup. But the **first** DML in the transaction sets the category, and everything after must match.

```java
// Fine: both setup
insert newUser;
insert new PermissionSetAssignment(AssigneeId = newUser.Id, PermissionSetId = psId);

// Fine: both non-setup
insert account;
insert contact;

// Throws on the second statement
insert account;
insert newUser;

// Also throws
insert newUser;
insert account;
```

This means a trigger on a normal object cannot perform setup DML at all, because the DML that fired the trigger already set the category. The async path is the only option there.

## Practical guidance

**Keep setup-object DML in dedicated async classes**, so callers cannot mix by accident.

**Use `System.runAs` in tests** to isolate user creation.

**Build a `TestUserFactory`** that gets it right once.

**Remember flows are subject to the same restriction**, and use an async path.

**Recognize the error immediately** — `MIXED_DML_OPERATION` always means the same thing, and the fix is always the same shape.

**Do not attempt setup DML directly in a trigger** on a normal object. It cannot work.
