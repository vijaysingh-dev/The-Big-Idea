# Error Boundaries

An error boundary catches JavaScript errors thrown during rendering in its subtree, logs them, and renders a fallback instead of crashing.

Without one, an uncaught render error unmounts the **entire React tree** — the user sees a blank white page. This behavior is deliberate: React's authors judged that a corrupted UI is worse than no UI, particularly for anything transactional.

## The implementation

Error boundaries still require a class component. There is no hook equivalent.

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                    // render phase — update state to show fallback
  }

  componentDidCatch(error, errorInfo) {
    reportToSentry(error, { componentStack: errorInfo.componentStack });
  }

  render() {
    if (this.state.error) {
      return this.props.fallback(this.state.error, () => this.setState({ error: null }));
    }
    return this.props.children;
  }
}
```

Two methods with different jobs: `getDerivedStateFromError` runs during the render phase and must be pure — it only decides what to render. `componentDidCatch` runs during commit and is where side effects like logging belong ([[18.4 - Render Phase vs Commit Phase]]).

In practice, use `react-error-boundary` rather than hand-writing this:

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  FallbackComponent={ErrorFallback}
  onError={(error, info) => report(error, info)}
  onReset={() => queryClient.resetQueries()}
  resetKeys={[userId]}
>
  <Dashboard />
</ErrorBoundary>
```

It adds reset handling, `resetKeys` for automatic recovery on prop change, and a `useErrorBoundary` hook for manually triggering the boundary.

## What they do not catch

This is the important half.

```jsx
<ErrorBoundary>
  <Component />
</ErrorBoundary>
```

**Event handlers.** A click handler that throws does not reach the boundary — handlers run outside the render lifecycle.

```jsx
const handleClick = () => {
  try {
    riskyOperation();
  } catch (err) {
    setError(err);         // then throw during render, or handle locally
  }
};
```

**Async code.** `setTimeout`, promise callbacks, `fetch` continuations all run on a fresh stack after the render completed ([[01.3 - The Call Stack]]).

**Server-side rendering.** Boundaries do not catch during SSR — the server render fails and the framework handles it.

**Errors thrown in the boundary itself.** These propagate to the next boundary above.

To route a caught async or handler error into a boundary, re-throw during render:

```jsx
import { useErrorBoundary } from "react-error-boundary";

function Component() {
  const { showBoundary } = useErrorBoundary();

  const handleClick = async () => {
    try {
      await riskyOperation();
    } catch (err) {
      showBoundary(err);
    }
  };
}
```

Because the coverage has holes, global handlers remain necessary ([[05.9 - Error Handling and Custom Errors]]):

```js
window.addEventListener("error", e => report(e.error));
window.addEventListener("unhandledrejection", e => report(e.reason));
```

## Placement

Granularity determines how much of the UI is lost when something fails.

```jsx
// Root — catches everything, but any error blanks the app
<ErrorBoundary fallback={<FullPageError />}>
  <App />
</ErrorBoundary>

// Route level — a broken page, working navigation
<ErrorBoundary fallback={<PageError />}>
  <Outlet />
</ErrorBoundary>

// Widget level — the rest of the dashboard survives
<ErrorBoundary fallback={<WidgetError />}>
  <RevenueChart />
</ErrorBoundary>
```

A workable layering:

1. **Root boundary** as the last resort, with a reload option
2. **Route boundaries** so navigation still works
3. **Widget boundaries** around independent, failure-prone sections — charts, third-party embeds, user-generated content

Do not wrap every component. Each boundary is a place the UI can silently degrade, and too many make failures hard to notice in testing.

## Recovery

A fallback with no way forward is a dead end:

```jsx
function ErrorFallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <h2>Something went wrong</h2>
      <p>{error.message}</p>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}
```

`resetErrorBoundary` clears the error state and re-renders the children. If the underlying cause persists — a failing request — it will fail again immediately, so pair it with clearing the relevant cache:

```jsx
<ErrorBoundary onReset={() => queryClient.resetQueries({ queryKey: ["dashboard"] })}>
```

`resetKeys` handles automatic recovery when the input changes:

```jsx
<ErrorBoundary resetKeys={[userId]}>   {/* clears the error when userId changes */}
```

Never show raw error messages to users in production — they leak implementation details and occasionally sensitive information. Show a friendly message and log the detail.

## With Suspense

```jsx
<ErrorBoundary fallback={<ErrorState />}>
  <Suspense fallback={<Skeleton />}>
    <Dashboard />
  </Suspense>
</ErrorBoundary>
```

The error boundary goes **outside**. Suspense handles pending, the error boundary handles failed. Inverted, a failure leaves a permanently stuck skeleton ([[19.4 - Suspense]]).

This pairing is also how data libraries expose errors — `useSuspenseQuery` throws to the nearest boundary rather than returning an error object.

## Development versus production

In development, React logs the error and shows an overlay **even when a boundary catches it**. That is intentional — a caught error is still a bug — but it means you must dismiss the overlay to see the fallback.

In production, only the fallback renders. Test error states with a production build, since the development overlay obscures them.

React 19 added `onCaughtError` and `onUncaughtError` options on `createRoot` for centralized reporting:

```jsx
createRoot(el, {
  onCaughtError: (error, errorInfo) => report(error, errorInfo),
  onUncaughtError: (error, errorInfo) => reportCritical(error, errorInfo),
});
```

## Reporting

```jsx
componentDidCatch(error, errorInfo) {
  Sentry.captureException(error, {
    contexts: { react: { componentStack: errorInfo.componentStack } },
    tags: { boundary: this.props.name },
  });
}
```

The `componentStack` is what makes a React error report useful — it shows which component tree the error occurred in, which a raw JS stack does not.

Source maps are mandatory for this to be readable in production ([[27.7 - Source Maps]]).

## How senior engineers actually use this

**They use `react-error-boundary`** rather than hand-writing the class.

**They layer boundaries** — root, route, and widget-level around independent sections — rather than one or dozens.

**They always provide a recovery path**, and clear the relevant cache on reset.

**They pair every boundary with global `error` and `unhandledrejection` handlers**, because boundaries miss handlers and async code.

**They tag reports by boundary name**, which makes it obvious in monitoring which part of the app is failing.

## Common pitfalls

- Expecting boundaries to catch event handler or async errors.
- No boundary at all, so one error blanks the entire application.
- A fallback with no retry, leaving the user stuck.
- Error boundary inside Suspense rather than outside, producing a stuck skeleton.
- Raw error messages shown to users.
- Testing error states in development and being confused by the overlay.
- Missing source maps, making production stacks unreadable.

## Interview angle

"What are error boundaries" wants: class components using `getDerivedStateFromError` and `componentDidCatch` to catch render-phase errors in their subtree and show a fallback, because otherwise React unmounts the whole tree. The differentiating part is what they **do not** catch — event handlers, async code, SSR, and errors in the boundary itself — and therefore that global handlers are still required. Mentioning the Suspense pairing order and the recovery/reset story shows practical use.
