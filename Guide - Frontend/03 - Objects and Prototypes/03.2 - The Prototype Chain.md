# The Prototype Chain

Every JavaScript object has an internal link to another object called its **prototype**. When you read a property that the object does not own, the engine follows that link and looks there, then at *that* object's prototype, and so on until it finds the property or reaches `null`.

That chain of links is the prototype chain, and it is the entire inheritance mechanism of the language. Classes are syntax on top of it ([[03.4 - Classes vs Prototypes]]).

## `prototype` vs `__proto__` — the confusion, resolved

These are two different things with unfortunately similar names.

- **`Object.getPrototypeOf(obj)`** (legacy alias `obj.__proto__`) — the link *this object* uses for lookups. Every object has one.
- **`Fn.prototype`** — a plain object hanging off a *function*, which becomes the prototype of instances created with `new Fn()`. Only functions have it, and arrow functions do not.

```js
function Dog(name) {
  this.name = name;
}
Dog.prototype.speak = function () {
  return `${this.name} barks`;
};

const rex = new Dog("Rex");

Object.getPrototypeOf(rex) === Dog.prototype; // true
rex.speak();                                  // found on Dog.prototype
```

The chain for `rex`:

```
rex  ->  Dog.prototype  ->  Object.prototype  ->  null
```

`rex.toString()` works because `Object.prototype` sits on that chain.

## What `new` actually does

```js
function myNew(Constructor, ...args) {
  const obj = Object.create(Constructor.prototype);
  const result = Constructor.apply(obj, args);
  return result !== null && typeof result === "object" ? result : obj;
}
```

Four steps: create an object whose prototype is `Constructor.prototype`, call the constructor with `this` bound to it, and return the constructor's return value if it is an object, otherwise the new object. That last rule is why a constructor can override its own result — the basis of the singleton pattern in older code.

This is a common machine-coding question, and the object-return rule is the detail interviewers look for.

## Lookup and shadowing

Reads walk the chain. **Writes never do** — assignment always creates or updates an *own* property.

```js
Dog.prototype.legs = 4;

const a = new Dog("A");
const b = new Dog("B");

a.legs;        // 4 — from the prototype
a.legs = 3;    // creates an own property on `a`
b.legs;        // 4 — prototype untouched
```

This asymmetry is why mutable state on a prototype is dangerous:

```js
Dog.prototype.toys = [];
a.toys.push("ball");   // mutates the shared array, not a copy
b.toys;                // ["ball"]
```

`a.toys` resolves through the chain to the *shared* array, and `push` mutates it in place. No assignment happened, so no own property was created. Only primitives and methods belong on a prototype; per-instance data belongs in the constructor.

## Built-in chains

```js
[] -> Array.prototype -> Object.prototype -> null
(function(){}) -> Function.prototype -> Object.prototype -> null
"str" -> String.prototype -> Object.prototype -> null   (via temporary wrapper)
Object.create(null) -> null
```

Primitives are not objects, but property access on them creates a temporary wrapper object, resolves through the corresponding prototype, then discards the wrapper. That is why `"abc".toUpperCase()` works and why `"abc".foo = 1` silently does nothing.

## instanceof

```js
rex instanceof Dog;    // true
rex instanceof Object; // true
```

`instanceof` walks the prototype chain looking for `Fn.prototype`. It therefore fails across realms — an array from an iframe or a worker is not `instanceof` the local `Array`. Use `Array.isArray()` for arrays, and `Object.prototype.toString.call()` for general type checks ([[02.8 - call apply and bind]]).

Reimplementing it:

```js
function myInstanceof(obj, Fn) {
  let proto = Object.getPrototypeOf(Object(obj));
  while (proto) {
    if (proto === Fn.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
```

## Performance and hidden classes

The chain is walked on every miss. A property found five levels up costs five lookups — though V8's inline caches ([[01.1 - How JavaScript Runs]]) memoize the resolved location per call site, so the cost is only paid when shapes change.

The real performance rule: **never mutate prototypes at runtime.** `obj.__proto__ = x` and `Object.setPrototypeOf` invalidate every inline cache that touched the object and force it into a deoptimized state. Set the prototype at creation time with `Object.create` or `new` instead.

## How senior engineers actually use this

**They read it more than write it.** Application code uses `class`. But debugging a library, understanding why a polyfill works, or figuring out why a method is missing after a bundling change all require reading the chain in DevTools' `[[Prototype]]` view.

**They never extend built-in prototypes.** Adding `Array.prototype.last` seems harmless until two libraries define it differently, or a future spec adds it with different semantics. The `Array.prototype.flatten` proposal was renamed to `flat` precisely because a popular library had shipped an incompatible `flatten` on the prototype and the web broke.

**They use `Object.create(null)` for user-keyed dictionaries.** Prototype pollution — an attacker setting `__proto__` through a merge or query-string parser — is a real vulnerability class ([[15.6 - Frontend Security]]). Null-prototype objects and `Map` are immune.

**They keep methods on prototypes for instance-heavy code.** A thousand objects sharing one prototype method allocate one function; a thousand class-field arrows allocate a thousand. Relevant for canvas engines and large data models, irrelevant for most UI code.

## Common pitfalls

- Confusing `Fn.prototype` with `Object.getPrototypeOf(instance)`.
- Putting arrays or objects on a prototype and getting shared mutable state.
- Expecting writes to update the prototype. They create own properties instead.
- Using `instanceof` on values that may cross a realm boundary.
- Mutating prototypes at runtime and destroying JIT optimization.
- Using `for...in` and picking up inherited enumerable properties from a polluted prototype.

## Interview angle

"Explain the prototype chain" and "what does `new` do" are both extremely common. Describe the link, the lookup walk terminating at `null`, and the read/write asymmetry — that last point is what most candidates miss and it explains the shared-array bug cleanly. Being able to write `myNew` and `myInstanceof` on a whiteboard covers the follow-ups.
