# JWT Bearer Flow and Server to Server Auth

## Why this is the default for integrations

An external system needs to call Salesforce continuously, with no human present. The JWT bearer flow authenticates using a **signed assertion** rather than a password or a refresh token.

What that removes:

**No stored password.** Nothing to rotate, nothing to leak, no security token that silently changes on reset.

**No refresh token.** Nothing to expire after ninety days of quiet.

**No interactive login.** MFA does not apply, because no human authenticates.

**The private key never travels.** The client signs an assertion locally; Salesforce verifies with the public certificate it already holds.

That last property is the substantive security difference from client credentials, where a secret is transmitted on every token request.

## How it works

1. Generate a key pair; upload the **certificate** to a connected app in Salesforce, keep the **private key** on the client.
2. The client builds a JWT claiming a specific user, signs it with the private key.
3. The client posts the assertion to Salesforce's token endpoint.
4. Salesforce verifies the signature against the certificate and, if the user has been pre-authorized for that app, returns an access token.

No round trip for authorization, no user interaction, and no secret exchanged.

## Setting it up

**Generate the key pair:**

```bash
openssl req -x509 -sha256 -nodes -days 730 -newkey rsa:2048 \
  -keyout server.key -out server.crt \
  -subj "/CN=northwind-erp-integration"
```

`server.crt` is uploaded to Salesforce. `server.key` stays on the client and is the thing that must be protected — in a secrets manager, not in a repository.

**Create the connected app:**

```
Setup → App Manager → New Connected App
  Enable OAuth Settings
  Callback URL: http://localhost   (unused by this flow, but required)
  Use digital signatures: upload server.crt
  Selected OAuth Scopes: api, refresh_token
```

`refresh_token` is included even though no refresh token is issued — the flow requires the scope to be present.

**Set the policies:**

```
Permitted Users: Admin approved users are pre-authorized
IP Relaxation:   Relax IP restrictions
```

**"Admin approved users are pre-authorized" is mandatory** for this flow. Without it, the token request fails with `user hasn't approved this consumer`, which is the most common setup error.

**Pre-authorize the user** by assigning a permission set or profile to the connected app, granting the integration user access to it.

## The assertion

```json
{
  "iss": "3MVG9...consumer_key",
  "sub": "integration@northwind.com",
  "aud": "https://login.salesforce.com",
  "exp": 1754553900
}
```

**`iss`** — the connected app's consumer key.
**`sub`** — the username to authenticate as. This is the integration user, and its permissions are what the token carries.
**`aud`** — `https://login.salesforce.com` for production, `https://test.salesforce.com` for sandboxes. Getting this wrong is the second most common setup error.
**`exp`** — expiry, and it must be **within three minutes** of the current time. Salesforce rejects assertions with a longer window.

Signed with RS256 using the private key.

## Requesting the token

```
POST https://login.salesforce.com/services/oauth2/token

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion={signed_jwt}
```

```json
{
  "access_token": "00D5g...!AQ...",
  "instance_url": "https://myorg.my.salesforce.com",
  "id": "https://login.salesforce.com/id/00D5g.../0055g...",
  "token_type": "Bearer",
  "scope": "api"
}
```

**No refresh token, by design.** When the access token expires, the client signs a new assertion and requests another. Signing is local and cheap, so this is simpler than refresh-token management rather than harder.

## A client implementation

```python
import jwt, time, requests

def get_access_token(is_sandbox=False):
    audience = 'https://test.salesforce.com' if is_sandbox else 'https://login.salesforce.com'

    claims = {
        'iss': CONSUMER_KEY,
        'sub': INTEGRATION_USERNAME,
        'aud': audience,
        # must be within three minutes; two is a safe margin for clock drift
        'exp': int(time.time()) + 120
    }

    assertion = jwt.encode(claims, PRIVATE_KEY, algorithm='RS256')

    response = requests.post(
        f'{audience}/services/oauth2/token',
        data={
            'grant_type': 'urn:ietf:params:oauth:grant-type:jwt-bearer',
            'assertion': assertion
        }
    )
    response.raise_for_status()
    body = response.json()
    return body['access_token'], body['instance_url']
```

**Cache the token** until it expires rather than requesting one per API call. Token requests count against a rate limit, and a client requesting a token before every call will hit it.

A simple cache with a margin before expiry is enough:

```python
_token_cache = {'token': None, 'instance_url': None, 'expires_at': 0}

def token():
    if time.time() > _token_cache['expires_at'] - 300:
        tok, url = get_access_token()
        _token_cache.update(token=tok, instance_url=url,
                            expires_at=time.time() + session_timeout_seconds)
    return _token_cache['token'], _token_cache['instance_url']
```

The five-minute margin avoids a race where a token expires between the check and the call.

## Salesforce as the JWT client

Calling **another** Salesforce org, or an external service expecting JWT auth, is configured entirely through a Named Credential — no Apex.

```
External Credential
  Authentication Protocol: OAuth 2.0
  Flow Type: JWT Bearer Token
  Identity Provider URL: https://partner.my.salesforce.com
  Scope: api

Named Credential
  URL: https://partner.my.salesforce.com
  External Credential: Partner_Org_JWT
```

```java
// The platform signs, requests, caches, and refreshes the token
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:Partner_Org/services/data/v62.0/sobjects/Account');
```

Hand-rolling JWT signing in Apex is possible — `Crypto.signWithCertificate` exists — and it is the wrong choice when Named Credentials handle it. See [[13.13 - Named Credentials and External Credentials]].

## The integration user

The most important design decision in this note, and the one most often skipped.

**Create a dedicated user**, not a person's account and not an administrator.

```
Username:  integration.erp@northwind.com.prod
Profile:   Minimum Access - Salesforce
Permission Set: ERP_Integration_Access
  Object permissions: Warranty_Claim__c (CRUD), Asset (Read), Account (Read, Edit)
  Field-level security: only the fields the integration touches
  System permissions: API Enabled
```

The permission set grants **exactly the objects and fields the integration uses**. Where full record access is genuinely needed — an integration that must update every claim — grant **View All and Modify All on that object**, not the org-wide `View All Data`. See [[03.5 - Object Level Security - CRUD]].

Three further points:

**No role, or a role with no subordinates.** An integration user owning large numbers of records creates ownership skew, and giving them a role high in the hierarchy makes every sharing recalculation expensive. See [[10.9 - Data Skew]].

**No profile-level IP restrictions.** Source IPs change; the connected app's IP relaxation is the right control instead.

**One user per integration**, not one shared across five. When something writes bad data, `LastModifiedById` should name the responsible system.

Scoping the integration user properly is usually the single highest-value security improvement available in an org, because it is so consistently skipped.

## Failure modes

The errors, and what each actually means:

**`invalid_grant: user hasn't approved this consumer`** — Permitted Users is not set to admin-approved, or the user has not been granted access to the connected app through a profile or permission set. This is the most common.

**`invalid_grant: invalid assertion`** — a signature mismatch, usually the wrong private key, or `aud` pointing at production for a sandbox.

**`invalid_grant: audience is invalid`** — wrong `aud`, or the request sent to the wrong login endpoint.

**`invalid_grant: expired assertion`** — `exp` more than three minutes out, or clock drift on the client. Clock skew is a real cause and is worth checking when everything else looks correct.

**`inactive_user`** — the integration user was deactivated, often during an offboarding sweep that did not distinguish service accounts.

**`invalid_client_id`** — wrong consumer key, or the connected app was deleted.

## Certificate rotation

Certificates expire, and an expired certificate stops the integration with no warning.

The rotation sequence that avoids downtime:

1. Generate a new key pair
2. Create a **second** connected app with the new certificate
3. Switch the client to the new consumer key and private key
4. Verify
5. Delete the old connected app

A connected app holds one certificate, so overlapping apps rather than swapping the certificate in place is what makes this zero-downtime.

**Track expiry dates.** A calendar reminder ninety days before is the difference between a planned rotation and an outage.

## Testing the setup

The fastest verification, before writing any client code:

```bash
sf org login jwt \
  --client-id {consumer_key} \
  --jwt-key-file server.key \
  --username integration@northwind.com \
  --instance-url https://myorg.my.salesforce.com \
  --alias erp-integration

sf org display --target-org erp-integration
```

If the CLI can authenticate, the connected app, certificate, and user authorization are all correct, and any remaining problem is in the client. This isolates the configuration from the code, which saves a great deal of time.

## Practical guidance

**Use JWT for every server-to-server integration.**

**Set Permitted Users to admin-approved**, and grant the user access to the app.

**Match `aud` to the environment** — sandbox and production differ.

**Keep `exp` short**, within three minutes.

**Cache the access token** with a margin before expiry.

**Create a dedicated, minimally scoped integration user** with no role.

**Verify with the CLI first** before debugging client code.

**Track certificate expiry**, and rotate through a second connected app.

**Migrate any username-password integration you inherit.** It is the highest-value security change available.
