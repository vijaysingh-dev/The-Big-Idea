# Measuring Performance

Optimization without measurement is guessing, and the guess is usually wrong. This note is the process.

## Lab versus field

**Lab** — Lighthouse, WebPageTest, CI runs. Controlled, reproducible, good for catching regressions before release. Unrepresentative of your actual users.

**Field (RUM)** — Core Web Vitals from real sessions. Noisy, representative, and the only thing that reflects reality.

Both are needed and they answer different questions. Lab tells you whether a change made things better; field tells you whether users are having a bad time.

A Lighthouse score of 95 alongside a p75 LCP of 4.5 seconds in the field is common — it usually means the lab test ran on fast hardware over a fast connection with a warm cache, and real users have none of those.

## Read percentiles, not averages

```
p50   the typical experience
p75   the Core Web Vitals threshold
p95   where the pain is
p99   the worst experiences
```

An average LCP of 2.1s can hide a p95 of 8s. Averages are dominated by the fast majority and hide exactly the population that is suffering.

Segment by the dimensions that actually vary: device memory, connection type, route and geography. For a product with users across a wide device range, segmenting usually reveals that the p75 experience is far worse than the development team assumes ([[28.13 - Frontend Observability]]).

## Throttle, always

A development laptop is four to six times faster than a mid-range Android phone. Every performance problem is invisible without throttling:

```
DevTools → Performance → CPU: 4x or 6x slowdown
DevTools → Network → Fast 4G / Slow 4G
```

This single setting changes more measurements than any other. Code that feels instant unthrottled can drop frames at 6× slowdown, which is what a large share of real users experience.

Also test with cache disabled for first-visit measurement, and with a warm cache for repeat visits — they are different problems.

## The core metrics

| Metric | Measures | Good |
| --- | --- | --- |
| **TTFB** | server response | < 800ms |
| **FCP** | first content painted | < 1.8s |
| **LCP** | largest element painted | < 2.5s |
| **INP** | interaction responsiveness | < 200ms |
| **CLS** | layout stability | < 0.1 |

Thresholds are measured at **p75** — 75% of visits must be under the value ([[13.5 - Core Web Vitals]]).

INP replaced FID in 2024 and is the harder one to satisfy, because it measures the full input-to-paint latency for every interaction rather than just the first input delay. It is also the metric most affected by React render cost.

## Custom metrics

Core Web Vitals measure page loading. They say nothing about whether *your* critical interaction is fast.

```ts
performance.mark("search:start");
const results = await search(query);
performance.mark("search:end");
performance.measure("search", "search:start", "search:end");

const [entry] = performance.getEntriesByName("search");
report({ name: "search_latency", value: entry.duration });
```

Measure what the product cares about: time to first meaningful result, save duration, editor keystroke lag, checkout completion time. These are the numbers a product team will act on, and they are invisible in any standard metric.

`PerformanceObserver` catches main-thread blocking:

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) report({ name: "long_task", value: entry.duration });
  }
}).observe({ type: "longtask", buffered: true });
```

A long task is anything over 50ms, and it is what makes an interface feel unresponsive ([[01.4 - The Event Loop]]).

## Collecting field data

```ts
import { onLCP, onINP, onCLS, onTTFB } from "web-vitals";

function report({ name, value, rating, attribution }) {
  navigator.sendBeacon("/api/vitals", JSON.stringify({
    name, value, rating,
    element: attribution?.element,          // WHICH element caused it
    url: location.pathname,
    release: import.meta.env.VITE_COMMIT_SHA,
    connection: navigator.connection?.effectiveType,
    deviceMemory: navigator.deviceMemory,
  }));
}

onLCP(report); onINP(report); onCLS(report); onTTFB(report);
```

Two details that make this useful rather than decorative:

**`attribution`** identifies the specific element or interaction responsible. Without it you know the score and not the cause.

**`sendBeacon`** survives page unload, where a normal `fetch` is cancelled. INP is only final at page hide, so beacon delivery is not optional.

Tag every report with the release SHA, or a regression cannot be attributed to a deploy ([[27.9 - CI CD and Frontend Deployment]]).

## The Performance panel

The single most useful tool, and underused because the interface is dense.

Record an interaction and read:

- **Main track** — scripting (yellow), rendering (purple), painting (green). Long yellow blocks are JavaScript; long purple blocks are layout.
- **Red triangles** — long tasks and forced synchronous layout ([[13.3 - Layout Thrashing]])
- **Frames track** — dropped frames during animation or scroll
- **Interactions track** — input latency, which maps directly onto INP
- **Bottom-up** — self time per function, which identifies the actual cost

React 18+ writes its render and commit phases into this timeline, so React work appears inline with browser work. That combined view answers the first diagnostic question: **is this React's fault at all?** Often it is a forced layout, a large paint, or a third-party script ([[19.8 - Profiling with React DevTools]]).

## Diagnosing by symptom

| Symptom | Look at | Usual cause |
| --- | --- | --- |
| Slow first paint | Network waterfall | render-blocking CSS/JS, slow TTFB |
| Slow LCP | LCP attribution | late-discovered image, blocking resource |
| Layout jumping | Performance → Layout Shift | missing image dimensions, injected content |
| Sluggish typing | Performance → Interactions | expensive render per keystroke |
| Janky scroll | Frames track | non-passive listeners, layout thrashing |
| Slow after long use | Memory panel | a leak ([[07.5 - Profiling Memory in DevTools]]) |
| Large bundle | bundle analyzer | a heavy dependency ([[19.7 - Bundle Analysis and Optimization]]) |

Matching the symptom to the tool is most of the skill. Opening the React Profiler for a layout-thrashing problem wastes time.

## CI budgets

```json
{ "size-limit": [{ "path": "dist/assets/index-*.js", "limit": "150 kB" }] }
```

```yaml
- run: npx lhci autorun --collect.url=$PREVIEW_URL
```

Catching a regression before release is far cheaper than detecting it in production. Bundle size in particular regresses invisibly — a dependency here, an import pattern there — and a budget converts that into a visible decision at the PR that causes it.

Lighthouse scores in CI are noisy; gate on specific audits and byte budgets rather than the composite number.

## The process

1. **Measure first.** Establish a baseline with realistic throttling.
2. **Identify the bottleneck.** Use the tool that matches the symptom.
3. **Form a hypothesis** about the cause.
4. **Change one thing.**
5. **Measure again**, under identical conditions.
6. **Keep it if it helped; revert if it did not.**

Step 6 is the one that gets skipped. An optimization that does not measure — an unnecessary `useMemo`, a memo wrapper on a trivial component — is cost plus a dependency array that can go stale ([[19.2 - React.memo and Memoization Strategy]]).

Verify in the field, not just the lab. A change can improve a Lighthouse score while making a common interaction slower, which only RUM will show.

## What usually matters

In rough order of impact for a typical React application:

1. **JavaScript bundle size** — route splitting, deferring heavy dependencies
2. **Images** — format, sizing, LCP prioritization
3. **Third-party scripts** — frequently the largest unexamined cost
4. **Render-blocking resources** in the head
5. **Long tasks** — chunking, transitions, workers
6. **Layout thrashing** — batched reads and writes
7. **React re-renders** — usually the *last* thing worth optimizing

The ordering matters. Teams routinely spend days on memoization while a 400KB analytics script sits in the critical path.

## How senior engineers actually use this

**They always throttle**, because unthrottled measurement is meaningless.

**They read p75 and p95**, segmented by device and connection.

**They match the tool to the symptom** rather than opening a profiler reflexively.

**They tag every field metric with the release**, making regressions attributable.

**They revert optimizations that do not measure.**

**They check bundle and third-party cost before touching React**, since that is usually where the time is.

## Common pitfalls

- Measuring on a fast machine with no throttling.
- Reading averages instead of percentiles.
- Optimizing without a baseline.
- Trusting Lighthouse scores as a proxy for real user experience.
- Adding memoization without measuring, and leaving it in.
- Optimizing React re-renders while a third-party script dominates the timeline.
- `fetch` instead of `sendBeacon`, losing reports at unload.
- No CI budget, so bundle size regresses invisibly.

## Interview angle

"How would you debug a performance problem" is a process question, and the process is the answer: reproduce with realistic throttling, measure to establish a baseline, use the tool matching the symptom, change one thing, measure again, and revert if it did not help. The points that mark experience: read p75 rather than averages, distinguish lab from field data and know why both are needed, and check bundle size and third-party scripts before optimizing React — because that is where the time usually is.
