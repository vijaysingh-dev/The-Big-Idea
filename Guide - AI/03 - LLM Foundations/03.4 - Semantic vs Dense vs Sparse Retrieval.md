# Semantic vs Dense vs Sparse Retrieval

## Overview

Retrieval is the process of finding relevant documents given a query. There are two fundamentally different paradigms:

|Paradigm|Mechanism|Best at|
|---|---|---|
|**Sparse / Keyword**|Exact token matching, inverted index|Precise terms, entity names, codes|
|**Dense / Semantic**|Embedding similarity (ANN search)|Paraphrasing, conceptual queries|

Neither is universally better. Production systems combine both — this is called **hybrid search**.

---

## Sparse Retrieval

### How It Works

Represents documents and queries as **sparse vectors** — most dimensions are zero, non-zero only for tokens that appear in the text.

Classic example: **TF-IDF vector**

```
Vocabulary: ["cat", "dog", "mat", "sat", ...]  (50,000 words)
Document: "The cat sat on the mat"
Vector:   [1.2,  0,    0.8,  0.9,  ...]   ← mostly zeros
```

BM25 is an improved version of TF-IDF with better term frequency saturation. Covered in [[03.5 - BM25 and Hybrid Search]].

### Strengths

- **Exact match**: If someone queries "RFC 2616", sparse retrieval finds documents containing exactly that string. Dense retrieval might miss it if the embedding doesn't emphasize that specific token.
- **Rare terms**: Product codes, names, jargon, typos (partially)
- **Speed**: Inverted index lookups are extremely fast
- **Interpretability**: You can see exactly which tokens drove the match

### Weaknesses

- **Vocabulary mismatch**: "car" and "automobile" are different tokens → no retrieval signal
- **No semantic understanding**: "What's good to eat near Paris?" doesn't find "Restaurant recommendations in France"
- **Multiword phrases**: Term independence assumption misses phrase meaning

---

## Dense Retrieval

### How It Works

Encodes both query and documents into dense vectors using a **bi-encoder** architecture:

```
Query:     "best restaurants in Paris"
           → embed → [0.12, -0.83, ...]

Document:  "Top dining recommendations for France's capital"
           → embed → [0.14, -0.81, ...]  ← similar vector despite different words

ANN search → finds closest document vectors
```

Both query and document go through the same (or separate specialized) encoder model independently. Then similarity search finds close vectors.

### Strengths

- **Semantic understanding**: Captures meaning regardless of exact wording
- **Paraphrase matching**: "automobile" finds "car" documents
- **Cross-lingual (with multilingual models)**: English query finds French documents
- **Conceptual queries**: "What causes inflation?" finds economics documents without those exact words

### Weaknesses

- **Exact term failure**: "error code E-0x4F2" → the specific code may not be captured well in the embedding
- **Out-of-distribution**: Embedding models trained on web text fail on specialized jargon
- **Slower index construction**: Must embed every document
- **Index size**: 1536-dim float32 vectors take significant memory (6MB per 1000 docs)
- **Black box**: Can't explain why a document was retrieved

---

## The Vocabulary Mismatch Problem (Why Dense Was Invented)

Consider:

- Query: "How do I fix a memory leak?"
- Document: "Resolving heap allocation issues in Python"

BM25 returns 0 match — no shared terms. But the document is highly relevant. Dense retrieval finds it because both embed to similar regions of semantic space.

The vocabulary mismatch problem is the primary motivation for dense retrieval.

---

## Learned Sparse Retrieval

A newer approach that bridges the gap: **SPLADE, BM42, Sparse Autoencoders**.

These models produce sparse vectors but use a neural network to add semantic expansion. A document about "cats" might get non-zero weight on "feline" even if that word doesn't appear in the text.

```
SPLADE encoding of "The cat sat on the mat":
{cat: 2.1, feline: 0.8, animal: 0.4, mat: 1.7, sat: 1.2, ...}
          ↑ added by model even though not in text
```

This gives you the speed/interpretability of sparse retrieval with some semantic understanding. Relevant for [[03.5 - BM25 and Hybrid Search|hybrid systems]].

---

## Bi-Encoder vs Cross-Encoder

Dense retrieval uses **bi-encoders** at retrieval time for speed, but bi-encoders have a quality ceiling because query and document are encoded independently.

**Cross-encoders** encode the query and document _together_ — the two texts interact through attention, producing a much higher-quality relevance score. But they're slow: you must run the model for every (query, doc) pair, which is infeasible for large-scale retrieval.

The solution: **two-stage retrieval**

1. Bi-encoder: fast, retrieve top-100 candidates
2. Cross-encoder (reranker): slow, rerank top-100 → return top-10

This is the architecture used in Onyx and most production RAG systems. See [[03.6 - Rerankers - Cross vs Bi Encoders]].

## When to Use Which

```
Query type                          Best approach
─────────────────────────────────────────────────────
Exact product code / SKU            Sparse (BM25)
Named entity (person, place)        Sparse or Hybrid
Technical jargon (domain-specific)  Sparse or Hybrid
Natural language question           Dense
Paraphrased query                   Dense
Mixed (most real-world queries)     Hybrid (BM25 + Dense)
```

**Production default: Hybrid search** — always combine both unless you have a strong reason not to. The cost is low and the quality gain is consistent.
