# map, filter, reduce and forEach

The four core iteration methods. All take `(element, index, array)` and an optional `thisArg`, all skip holes in sparse arrays, and all except `forEach` return something useful.

## map

Transforms every element into a new one. Always returns an array of the same length.

```js
const names = users.map(u => u.name);
const withIndex = users.map((u, i) => ({ ...u, position: i + 1 }));
```

Two rules: return a value from every path, and do not use `map` when you are not building a new array.

```js
// Wrong — map used as a loop, allocates an array of undefined
users.map(u => console.log(u));

// Wrong — missing return in a block body
users.map(u => { u.name.toUpperCase(); });  // [undefined, undefined, ...]
```

The classic trap:

```js
["1", "2", "3"].map(parseInt);  // [1, NaN, NaN]
```

`parseInt(string, radix)` receives the index as the radix — `parseInt("2", 1)` is `NaN` because radix 1 is invalid. Use `["1","2","3"].map(Number)` or `.map(s => parseInt(s, 10))`. Any callback whose arity is greater than one is unsafe to pass by reference.

## filter

Keeps elements where the predicate is truthy. Returns a new array, possibly empty.

```js
const active = users.filter(u => u.isActive);
const truthy = values.filter(Boolean);          // removes all falsy values
```

`filter(Boolean)` is the idiomatic way to strip `null`, `undefined`, `0`, `""` and `NaN`. Careful when `0` or `""` are valid — use `filter(v => v != null)` instead.

In TypeScript, `filter` does not narrow the type automatically; you need a type predicate:

```ts
const defined = values.filter((v): v is string => v != null);
```

## reduce

The general fold. Everything else can be built from it.

```js
const total = items.reduce((sum, item) => sum + item.price, 0);
```

**Always pass an initial value.** Without one, `reduce` uses the first element as the accumulator and starts at index 1, which means an empty array throws a `TypeError` and the accumulator type is unpredictable.

```js
[].reduce((a, b) => a + b);      // TypeError
[].reduce((a, b) => a + b, 0);   // 0
```

Common shapes:

```js
// Group by a key
const byRole = users.reduce((acc, u) => {
  (acc[u.role] ??= []).push(u);
  return acc;
}, {});

// Index by id — the normalization pattern
const byId = users.reduce((acc, u) => { acc[u.id] = u; return acc; }, {});

// Count occurrences
const counts = words.reduce((acc, w) => {
  acc[w] = (acc[w] ?? 0) + 1;
  return acc;
}, {});

// Compose functions
const pipe = (...fns) => x => fns.reduce((v, f) => f(v), x);
```

`Object.groupBy` now covers the first case natively, and `Map.groupBy` returns a `Map`.

The anti-pattern to avoid:

```js
// O(n²) — new array every iteration
items.reduce((acc, x) => [...acc, transform(x)], []);

// O(n)
items.map(transform);
```

Spreading the accumulator inside a reduce is one of the most common performance mistakes in otherwise idiomatic code ([[05.6 - Spread vs Rest]]).

`reduceRight` folds from the end — useful for right-associative composition and little else.

## forEach

Runs a function for each element and returns `undefined`. It exists for side effects.

```js
items.forEach(item => console.log(item));
```

Three things it cannot do:

**Break early.** `return` skips one iteration, not the loop. Use `for...of` with `break`, or `some`/`every` if you want a functional early exit.

**Await.** `forEach` ignores the returned promise entirely:

```js
// Broken — completes immediately, rejections go unhandled
items.forEach(async item => { await save(item); });

// Sequential
for (const item of items) await save(item);

// Parallel
await Promise.all(items.map(item => save(item)));
```

**Chain.** It returns `undefined`, so nothing follows it.

Given those limits, `for...of` is usually the better choice for side effects — it supports `break`, `continue`, `await`, and reads at least as well.

## Chaining and passes

```js
const result = users
  .filter(u => u.isActive)
  .map(u => u.name)
  .sort();
```

Each link is a full pass and a new array. For a few hundred elements this is irrelevant. For very large arrays, a single `reduce` or `for` loop does it in one pass:

```js
const names = [];
for (const u of users) {
  if (u.isActive) names.push(u.name);
}
```

Do not preemptively write loops for readability's sake — measure first. But know that `.filter().map()` over 100,000 items in a render path is a real cost.

## Mutation during iteration

The visited range is fixed when the method starts, but element values are read as visited:

```js
const arr = [1, 2, 3];
arr.forEach((v, i) => { arr.push(v); });  // terminates — new elements not visited

const arr2 = [1, 2, 3];
arr2.forEach((v, i) => { arr2.splice(i, 1); });  // skips elements
```

Never mutate the array you are iterating. If you need to remove items, `filter` into a new array.

## How senior engineers actually use this

**They pick the method that names the intent.** `map` for transformation, `filter` for selection, `reduce` for aggregation, `for...of` for side effects. Using `reduce` where `map` would do makes code harder to read for no gain.

**They avoid `reduce` for anything a named method covers.** `Object.groupBy`, `Object.fromEntries`, `flatMap` and `Object.entries` cover most historical `reduce` uses more legibly.

**They keep callbacks pure.** A `map` callback that mutates its argument produces a "copy" that shares state, which breaks React's change detection ([[03.5 - Shallow vs Deep Copy]]).

**They hoist expensive chains out of render.** A `.filter().map().sort()` chain in a component body runs on every render; `useMemo` or moving it to a selector is the fix ([[17.6 - useMemo]]).

## Common pitfalls

- `map(parseInt)`.
- `map` used as a loop, or missing a `return` in a block body.
- `reduce` without an initial value.
- Spreading the accumulator in a reduce.
- `async` callbacks in `forEach`.
- `filter(Boolean)` removing legitimate `0` or `""` values.
- Mutating an array while iterating it.

## Interview angle

Expect implementation questions — "write your own `map`", "write `reduce`" — and output-prediction with `map(parseInt)`. When implementing, handle the sparse-array skip and pass all three callback arguments; for `reduce`, handle the missing-initial-value case correctly. Explaining why `forEach` cannot await, and what to use instead, is a frequent follow-up.
