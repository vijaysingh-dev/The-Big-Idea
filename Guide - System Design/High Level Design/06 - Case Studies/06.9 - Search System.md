# Case Study: Search System

> **Revision tags:** #case-study #search #indexing  
> **Related:** [[03.10 - Search Systems]] | [[04.9 - Search Indexing]]

---

## Requirements Clarification

**Functional:**
- Full-text search over product catalog (e-commerce context)
- Typeahead / autocomplete as user types
- Faceted filtering: by category, price range, brand, rating
- Relevance ranking (by text match + popularity)
- Near-instant index updates (new products visible in search within 60s)
- Spell correction / fuzzy matching ("laptpp" → "laptop")

**Non-functional:**
- Search query latency: < 100ms p99
- Index freshness: < 60s from product write to searchable
- Scale: 500M products, 100K search queries/s
- Read:write ratio: ~1000:1 (massive read load vs catalog updates)
- 99.99% availability for search

**Out of scope:** Personalized ranking (ML model), ad injection, image search

---

## Estimation

```
Products: 500M
Product document size: ~2KB (name, description, attributes, prices)
Raw data: 500M × 2KB = 1 TB

Elasticsearch index overhead: ~3× raw = ~3 TB
With replication (3 replicas): ~9 TB of index storage

Queries/s: 100K
Query latency budget: 100ms
  - Network: 5ms
  - Query parsing: 2ms
  - Index lookup: 30ms
  - Scoring: 20ms
  - Aggregations (facets): 30ms
  - Network back: 5ms
  Total: ~92ms → tight but achievable with proper sharding

Typeahead: 5× search volume = 500K requests/s
  → Must be heavily cached (Redis, CDN)
```

## Architecture

```
[User]
  │ search query
  ▼
[API Gateway]
  │
  ├──→ [Typeahead Service]  →  Redis (prefix trie)  →  fast < 10ms
  │
  └──→ [Search Service]
            │
            ├──→ [Query Parser]    (tokenize, expand synonyms, correct spelling)
            ├──→ [Elasticsearch]   (distributed index, BM25 scoring)
            │      (5 shards × 3 replicas = 15 nodes)
            └──→ [Result Ranker]  (boost by popularity, inventory, margin)

[Product Service]
  │ product created/updated/deleted
  ▼
[Kafka: product-events]
  │
  ▼
[Index Sync Service]
  → Elasticsearch index update (upsert/delete)
  → Redis typeahead update
```

## Elasticsearch Cluster Design

### Sharding Strategy

```
500M products / 5 shards = 100M documents/shard
100M × 2KB = 200 GB/shard (well within single-node capacity)
Shard by: consistent hash of product_id
```

**5 primary shards, 2 replicas each** = 15 nodes total:
- 5 primary shards → write throughput distributed
- 10 replica shards → read throughput (2× replicas = 3× read capacity)
- Any shard can serve reads → 15 nodes serving 100K QPS = ~6,700 QPS/node

### Index Mapping

```json
{
  "mappings": {
    "properties": {
      "product_id":   { "type": "keyword" },
      "name":         { "type": "text", "analyzer": "english", "boost": 3 },
      "description":  { "type": "text", "analyzer": "english" },
      "category":     { "type": "keyword" },
      "brand":        { "type": "keyword" },
      "price_cents":  { "type": "integer" },
      "rating":       { "type": "float" },
      "review_count": { "type": "integer" },
      "in_stock":     { "type": "boolean" },
      "tags":         { "type": "keyword" },
      "created_at":   { "type": "date" },
      "name_suggest": {
        "type": "completion",
        "analyzer": "simple"
      }
    }
  }
}
```

**Field types:**
- `text` → analyzed for full-text search (tokenized, stemmed)
- `keyword` → exact match only (for facets, filtering)
- `completion` → optimized for prefix autocomplete

## Search Query Design

### Query Structure

```json
{
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query": "wireless noise cancelling headphones",
            "fields": ["name^3", "description", "tags^2"],
            "type": "best_fields",
            "fuzziness": "AUTO"
          }
        }
      ],
      "filter": [
        { "term": { "in_stock": true }},
        { "range": { "price_cents": { "gte": 100000, "lte": 1000000 }}}
      ]
    }
  },
  "aggs": {
    "by_brand": { "terms": { "field": "brand", "size": 20 }},
    "by_price": {
      "range": {
        "field": "price_cents",
        "ranges": [
          {"to": 100000},
          {"from": 100000, "to": 500000},
          {"from": 500000}
        ]
      }
    }
  },
  "sort": [
    { "_score": "desc" },
    { "review_count": "desc" }
  ],
  "from": 0,
  "size": 20
}
```

- `bool.must` → text matching (affects score)
- `bool.filter` → hard filters (no score impact, faster)
- `aggs` → facets for sidebar filters
- `sort` → relevance first, then popularity

### Query Pre-Processing

```python
def preprocess_query(raw_query: str) -> str:
    # 1. Spell correction
    corrected = spell_checker.correct(raw_query)   # "laptpp" → "laptop"

    # 2. Synonym expansion
    expanded = synonym_map.expand(corrected)
        # "phone" → "phone OR smartphone OR mobile"
        # "TV" → "television OR TV"

    # 3. Stop word handling (let Elasticsearch handle in analyzer)
    return expanded
```

**Synonym map:** Maintained as a file loaded into Elasticsearch's analysis pipeline. Updated without re-indexing (use update_settings API).

## Typeahead / Autocomplete

### Requirements
- Respond in < 10ms (user is typing)
- Show top 5–10 suggestions
- Ranked by popularity (most searched terms first)

### Architecture: Redis Sorted Set + Prefix

```python
# Indexing: store each prefix of popular search terms
def index_search_term(term: str, popularity_score: float):
    # Add all prefixes to a sorted set
    for i in range(1, len(term) + 1):
        prefix = term[:i]
        redis.zadd(f"typeahead:{prefix}", {term: popularity_score})
        redis.expire(f"typeahead:{prefix}", 86400)  # daily refresh

# Query: instant prefix lookup
def get_suggestions(prefix: str, limit: int = 10) -> List[str]:
    key = f"typeahead:{prefix.lower()}"
    # Get top N terms by popularity score (descending)
    results = redis.zrevrange(key, 0, limit - 1, withscores=False)
    return results

# Example:
# User types "wire" → GET typeahead:wire
# Returns: ["wireless headphones", "wireless mouse", "wireless charger", ...]
```

**Caching at CDN level:** Typeahead queries for common prefixes ("a", "ap", "app") are the same for all users. Cache at CDN with 60s TTL. Reduces origin load dramatically.

### Elasticsearch Completion Suggester (Alternative)

For more complex suggestions (field-level, fuzzy prefix):
```json
GET /products/_search
{
  "suggest": {
    "name_suggest": {
      "prefix": "wireless head",
      "completion": { "field": "name_suggest", "size": 10 }
    }
  }
}
```

Redis is faster (< 1ms vs 5–10ms). Use Redis for typeahead; Elasticsearch completion for "did you mean?" corrections.

## Index Sync Pipeline

```
Product Service → PostgreSQL (source of truth)
    │ (Debezium CDC reads WAL)
    ▼
Kafka: product-events
    │
    ▼
Index Sync Service:
  For each event:
    - PRODUCT_CREATED → elasticsearch.index(product_doc)
    - PRODUCT_UPDATED → elasticsearch.update(product_id, changed_fields)
    - PRODUCT_DELETED → elasticsearch.delete(product_id)
    - PRICE_CHANGED   → partial update (price_cents only, fast)

Elasticsearch update latency: ~100ms from Kafka message
Total end-to-end: Kafka lag (~1s) + ES index + refresh (~1s) = ~2-5s
```

**Elasticsearch refresh interval:** By default, new documents are visible after 1 second (refresh cycle). For near-real-time requirements, set `refresh_interval: 1s` on the index.

### Full Reindex

When the mapping changes or data drift is detected:

```
1. Create new index: products_v2 (with new mapping)
2. Start dual-write: all updates go to both products and products_v2
3. Backfill: reindex all products into products_v2
   (Elasticsearch reindex API or batch job from DB)
4. Validate: compare query results on both indexes
5. Alias switch: products alias → products_v2 (atomic, zero downtime)
6. Stop dual-write; retire products index
```

Zero-downtime reindex via alias switching is standard Elasticsearch practice.

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| ES shard unavailable | Queries for that shard fail | Replicas serve reads; cluster routes around failed shard |
| Kafka consumer lag | Search index stale | Alert on lag > 60s; scale consumers; accept temporary staleness |
| Redis typeahead down | Typeahead falls back to ES completion suggester | Degraded (slower) but functional |
| ES cluster split-brain | Two masters → split brain | Set `discovery.zen.minimum_master_nodes` = N/2+1 |
| Query spike | Latency degrades | Rate limiting at API gateway; cache popular queries in Redis |

## What This Design Demonstrates

- Elasticsearch cluster sizing (shards × replicas) based on data volume and QPS
- Separation of filter (keyword) vs search (text) field types
- Two-layer typeahead: Redis for speed, ES completion as fallback
- CDC (Debezium) → Kafka → ES for near-real-time index sync
- Zero-downtime reindex via alias switching
- Query pre-processing: spell correction and synonym expansion
