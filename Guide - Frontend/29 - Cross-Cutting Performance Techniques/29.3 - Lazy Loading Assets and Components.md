# Lazy Loading Assets and Components

Deferring work until it is needed. The counterpart to prefetching: one delays loading, the other advances it, and a good application does both — lazy for what is probably not needed, prefetch for what probably is.

## Images and iframes

```html
<img src="photo.jpg" loading="lazy" decoding="async" width="800" height="450" alt="...">
<iframe src="https://maps.example.com" loading="lazy"></iframe>
```

Native lazy loading needs no JavaScript and no observer. The browser decides when to fetch based on distance from the viewport, adjusting the threshold by connection speed.

Three rules ([[09.3 - Images Media and Loading Attributes]]):

**Never lazy-load the LCP image.** `loading="lazy"` on the largest above-the-fold element directly delays the metric it defines. Above-the-fold images should be `loading="eager"` with `fetchpriority="high"`.

**Always set dimensions.** Lazy loading without reserved space means every image arrival shifts the layout — a large CLS penalty that undoes the benefit ([[13.5 - Core Web Vitals]]).

**`decoding="async"`** lets the browser decode off the main thread, avoiding a decode-induced frame drop.

For iframes the win is much larger than for images — a YouTube embed pulls in several hundred KB of JavaScript. A click-to-load facade (a thumbnail plus play button that swaps in the real iframe on interaction) is better still.

## Components

```jsx
const Editor = lazy(() => import("./RichTextEditor"));

<Suspense fallback={<EditorSkeleton />}>
  {isEditing && <Editor />}
</Suspense>
```

Worth splitting: rich text editors, chart libraries, PDF generators, date pickers, map SDKs, code editors — anything large used on one screen or behind an interaction ([[19.3 - Code Splitting and React.lazy]]).

Not worth splitting: anything on the initial screen, anything under ~30KB, and components inside a tight interaction loop where the loading flash is worse than the bytes.

The fallback must approximate the final layout, or you trade a bundle win for a CLS regression.

## Deferring a heavy dependency

```jsx
async function exportToPdf(data) {
  const { jsPDF } = await import("jspdf");     // ~300KB, loaded on click
  new jsPDF().text(data).save();
}
```

This is often higher-value than component splitting. A library used by one button should not be in the initial bundle, and the user clicking the button expects a brief pause anyway.

Check the bundle analyzer for what is actually large rather than guessing ([[19.7 - Bundle Analysis and Optimization]]).

## Third-party scripts

Usually the largest unexamined cost on a page. Analytics, chat widgets, A/B testing, session replay and ad tags routinely add hundreds of KB and block the main thread.

```html
<script src="/analytics.js" defer></script>
```

```js
// Load a chat widget only on interaction or when idle
const loadChat = () => import("./chat-widget");

requestIdleCallback(loadChat, { timeout: 10_000 });
button.addEventListener("click", loadChat, { once: true });
```

Partytown moves third-party scripts to a Web Worker entirely, so they cannot block the main thread — worth evaluating when a vendor script is a measured problem ([[08.4 - Web Workers]]).

The most effective intervention is usually organizational: auditing which tags are still needed. Most sites carry scripts nobody has owned for years.

## Below-the-fold content

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}
```

The browser skips layout, paint and style for offscreen content entirely, without removing it from the DOM.

This is one of the highest-value single properties for long pages, and it is often overlooked because it requires no JavaScript. Unlike virtualization, the content remains findable by Ctrl+F, readable by screen readers and linkable by anchors ([[19.5 - Virtualization and Windowing]]).

`contain-intrinsic-size` supplies a placeholder height so the scrollbar does not jump as sections render.

## Fonts

```css
@font-face {
  font-family: Inter;
  src: url(/fonts/inter-latin.woff2) format("woff2");
  unicode-range: U+0000-00FF;
  font-display: swap;
}

@font-face {
  font-family: Inter;
  src: url(/fonts/inter-devanagari.woff2) format("woff2");
  unicode-range: U+0900-097F;
  font-display: swap;
}
```

`unicode-range` splits a font by script, so a page in English never downloads the Devanagari subset. For multi-script products this is a very large saving — a full CJK or Indic font can be several megabytes.

The browser fetches only the subsets it actually needs, which makes this lazy loading at the font level.

Keep weight count low. Each weight is a separate file; a variable font covers a range in one.

## Lazy hydration and islands

For mostly-static pages, hydrating everything is waste:

```astro
<StaticArticle />
<CommentSection client:visible />
<Newsletter client:idle />
```

Ship HTML for everything, hydrate only the interactive pieces, and only when needed ([[28.11 - Rendering Strategies]]).

Most of a blog or documentation page has no interactivity at all, so full-page hydration pays for nothing.

## The lazy-loading tax

Deferring is not free:

**A visible delay.** The user waits when the deferred thing is needed. For a rarely-used feature that is a good trade; for something used on every session it is not.

**Layout shift** if the placeholder does not match.

**Extra requests**, each with connection and parsing overhead.

**Failure modes.** A lazy chunk can 404 after a deploy, so error handling and reload recovery are required ([[19.3 - Code Splitting and React.lazy]]).

The rule: **defer what is probably not needed, prefetch what probably is.** A component that is lazy-loaded *and* prefetched on hover gets the bundle saving without the wait.

## What not to lazy load

- The LCP element
- Anything on the initial viewport
- Small modules where the request costs more than the bytes
- Critical CSS
- Content needed for SEO — crawlers may not trigger interaction-based loading
- Anything behind a user action that must feel instant

That last case deserves care: lazy-loading a modal's contents means every open has a delay. Prefetch it when the trigger becomes visible instead.

## Measuring

```
Lighthouse → "Defer offscreen images", "Reduce unused JavaScript"
DevTools Coverage → what executed before first interaction
Network panel → what loads and when
```

The Coverage panel is the most direct signal — high unused percentages on initial load point at code that should be deferred ([[19.7 - Bundle Analysis and Optimization]]).

Verify the result in field data, not just in Lighthouse. Lazy loading can improve a lab score while making a common interaction slower, which real user monitoring will show and a synthetic test will not ([[28.13 - Frontend Observability]]).

## How senior engineers actually use this

**They lazy-load everything below the fold and eagerly load the LCP element**, treating the second half as equally important.

**They defer heavy dependencies before splitting components**, since that is usually where the bytes are.

**They audit third-party scripts**, which are frequently the largest unexamined cost.

**They use `content-visibility` for long pages**, since it is one CSS line with a large effect.

**They pair lazy loading with prefetch on intent**, so the deferral costs no perceived latency.

## Common pitfalls

- `loading="lazy"` on the LCP image.
- Lazy images without dimensions, causing layout shift.
- Splitting components that render on the initial screen.
- Over-splitting into many tiny chunks.
- No error handling for a failed lazy chunk after a deploy.
- Third-party scripts loaded synchronously in the head.
- Lazy-loading SEO-relevant content that crawlers will not trigger.
- Deferring without prefetching, so every interaction pays the wait.

## Interview angle

"How would you improve initial load time" is where this belongs. Give the ordered levers: route-level code splitting, deferring heavy dependencies, native image lazy loading with the LCP exception, auditing third-party scripts, and `content-visibility` for long pages. The framing that stands out is the pairing — defer what is probably not needed and prefetch what probably is — plus the explicit exceptions, since knowing what *not* to lazy-load is what separates a considered answer from a checklist.
