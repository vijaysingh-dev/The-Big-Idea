# LLD vs HLD

> **Revision tags:** #fundamentals  
> **Related:** [[01.1 - What Is HLD]] | [[01.3 - Requirements]]

---

## The Core Distinction

| Dimension | HLD | LLD |
|---|---|---|
| **Question answered** | What exists and how does it connect? | How is each piece built internally? |
| **Unit of thought** | Services, databases, queues, APIs | Classes, methods, data structures, algorithms |
| **Audience** | Architects, tech leads, cross-team | The engineers building the component |
| **Output** | Architecture diagram, data flow, tech choices | Class diagrams, sequence diagrams, code structure |
| **When** | Before any code is written | After HLD is approved |
| **Interview type** | System design round | Object-oriented / low-level design round |

---

## HLD — What You're Deciding

- Which services exist (and which responsibilities each owns)
- How services communicate (REST, gRPC, event queue, etc.)
- Which database each service uses and why
- Where caching sits
- How requests are routed (load balancer, API gateway)
- How the system scales under load
- What fails gracefully and what fails hard

**Example (URL Shortener HLD):**
```
Client → Load Balancer → Shortening Service → PostgreSQL (URLs)
                                           → Redis (hot URL cache)
       → Redirect Service → Redis → PostgreSQL (cache miss)
```

---

## LLD — What You're Deciding

- Class structure and interfaces
- Which design patterns to use (Strategy, Factory, Observer, etc.)
- How internal state is managed
- Algorithm selection (hash function, tree vs hash map, etc.)
- Error handling within a function
- Thread safety

**Example (URL Shortener LLD):**
```python
class URLShortener:
    def __init__(self, db: Database, cache: Cache):
        self.db = db
        self.cache = cache

    def shorten(self, long_url: str) -> str:
        short_code = self._generate_code(long_url)
        self.db.save(short_code, long_url)
        return short_code

    def _generate_code(self, url: str) -> str:
        return base62_encode(hash(url))[:7]
```

## Common Confusion Points

**"Is database schema HLD or LLD?"**  
The *choice* of database type is HLD. The schema (tables, columns, indexes) is LLD.

**"Is API design HLD or LLD?"**  
The *existence and contract* of an API (`POST /shorten`) is HLD. The request/response schema, validation logic, and error codes are LLD.

**"Are design patterns HLD or LLD?"**  
Almost always LLD. Exception: architectural patterns like CQRS, SAGA, and Event Sourcing are HLD patterns.

---

## Why Both Matter

A brilliant LLD inside a broken HLD still produces an unmaintainable system — the individual components are clean but they're assembled wrong.

A brilliant HLD with no LLD thinking produces unmaintainable code inside cleanly connected services.

Senior engineers move fluidly between levels. In interviews, interviewers test each separately because they require different mental modes.

---

## Interview Signal

When you're in an HLD interview and you start drawing class diagrams or talking about function signatures — that's a red flag. You've slipped into LLD mode. Pull back up to system level.

The reverse is also true in LLD interviews: talking about load balancers when asked to design a parking lot system means you haven't answered the actual question.
