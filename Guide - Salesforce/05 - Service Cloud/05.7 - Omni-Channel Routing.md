# Omni-Channel Routing

## The gap it fills

Assignment rules put a case in a queue. They have no idea whether anyone in that queue is online, how much work each agent already has, or whether anyone has the right skills.

The result with queues alone is uneven distribution: easy cases are claimed quickly, hard ones sit, and workload depends on who is watching the list view.

**Omni-Channel** pushes work to agents based on availability, capacity, and skills. The agent does not choose; work arrives.

## The objects

**Service Channel.** A type of work — Cases, Chats, Leads, Messaging, or a custom object. Each channel maps to an object and defines the default capacity a unit of that work consumes.

**Routing Configuration.** How work from a queue is distributed: the routing model, the priority relative to other queues, and the capacity each item consumes.

**Presence Status.** What an agent's state means — Available for Cases, Available for Chat, Busy, On Break. Each status maps to the channels it accepts.

**Presence User Config.** Per-user or per-profile settings: total capacity, which presence statuses are available, whether the agent can decline work.

**AgentWork.** The record of a work item assigned to an agent, with timestamps for assignment, acceptance, and closure. This is the object all Omni-Channel reporting is built on.

**PendingServiceRouting.** Work waiting to be routed, which is what a routing backlog actually looks like.

```sql
SELECT UserId, WorkItemId, ServiceChannel.MasterLabel, Status,
       RequestDateTime, AcceptDateTime, CloseDateTime, SpeedToAnswer
FROM AgentWork
WHERE CreatedDate = LAST_N_DAYS:7
ORDER BY RequestDateTime DESC
```

## Routing models

**Least Active.** Work goes to the available agent with the least open work. The general-purpose default.

**Most Available.** Work goes to the agent with the largest gap between capacity and current load. Behaves differently from Least Active when agents have different capacities.

**External Routing.** A third-party routing engine makes the decision through an API. Used where an existing contact centre platform owns routing.

## Capacity

Each agent has a total capacity — commonly 10. Each work item consumes some of it: a case might cost 3, a chat 5, a phone call 10.

The model is simple and effective. An agent handling two chats at 5 each is full and receives nothing more. An agent with three cases at 3 each has 1 unit spare and can take nothing that costs more.

Two ways to set the cost:

**Per routing configuration** — every case from this queue costs 3.
**Per work item**, using a `SecondaryRoutingPriority` or a custom field, so a complex case costs more than a simple one.

Getting capacity numbers right is an operational tuning exercise, not a technical one. The starting point is what a competent agent can genuinely hold at once, and the numbers are adjusted from observed queue times.

## Skills-based routing

Rather than routing to a queue, work carries **skill requirements** and goes to an agent who has them.

Skills are defined in Setup — Hindi, Press Line Certified, Tier 2 Electrical — and assigned to agents with a proficiency level. Work items get skill requirements attached, either declaratively through Attribute-Based Routing or programmatically:

```java
public with sharing class SkillRoutingService {

    public static void routeWithSkills(Id caseId, Set<String> requiredSkillNames) {
        Map<String, Id> skillIdByName = new Map<String, Id>();
        for (Skill s : [SELECT Id, DeveloperName FROM Skill WHERE DeveloperName IN :requiredSkillNames]) {
            skillIdByName.put(s.DeveloperName, s.Id);
        }

        PendingServiceRouting routing = new PendingServiceRouting(
            CapacityWeight = 3,
            IsReadyForRouting = false,
            RoutingModel = 'LeastActive',
            RoutingPriority = 1,
            ServiceChannelId = caseServiceChannelId,
            WorkItemId = caseId,
            RoutingType = 'SkillsBased'
        );
        insert routing;

        List<SkillRequirement> requirements = new List<SkillRequirement>();
        for (String skillName : requiredSkillNames) {
            requirements.add(new SkillRequirement(
                RelatedRecordId = routing.Id,
                SkillId = skillIdByName.get(skillName),
                SkillLevel = 5
            ));
        }
        insert requirements;

        // flipping IsReadyForRouting last releases the work once all requirements are attached
        routing.IsReadyForRouting = true;
        update routing;
    }
}
```

The two-phase pattern matters: create the routing record not ready, attach the skill requirements, then mark it ready. Marking it ready first can release the work before its requirements exist.

Skills can be configured to **degrade** over time — if no agent with the full skill set becomes available within a set period, requirements are dropped so the work can be assigned to someone less specialized. Without degradation, a case needing a rare skill can wait indefinitely, which is worse than a slightly less qualified agent handling it.

## The agent experience

The **Omni-Channel widget** sits in the utility bar of a console app. The agent sets a presence status, work arrives, they accept or decline, and the record opens in a tab.

Configuration decisions that shape the experience:

**Push versus pull.** Push assigns automatically. Pull offers work the agent accepts. Push produces better distribution; pull gives agents more control and is sometimes needed for adoption.

**Decline with reason.** Agents can be permitted to decline, optionally with a reason. Useful data, and a route around the system if unrestricted.

**Auto-accept.** Work is assigned with no accept step. Right for email-based case work, wrong for chat where the agent needs a moment.

**Timeouts.** Work not accepted within a set period is pushed to someone else.

## Omni-Channel Flows

The newer and more flexible routing mechanism. Instead of routing configuration alone deciding, a flow runs when work needs routing and can query records, call Apex, evaluate business logic, and then route to a queue, a specific agent, or a skill set.

This is where routing that used to require complex assignment rules now belongs. A flow can check the account's entitlement tier, look at whether the customer has an open critical case already, check which agent last handled this customer, and route accordingly.

Routing to the previous agent is a common and genuinely valuable pattern — customers dislike re-explaining, and it measurably improves satisfaction:

```java
public with sharing class PreferredAgentService {

    @InvocableMethod(label='Find Previous Agent' description='Returns the agent who last handled this contact')
    public static List<Id> findPreviousAgent(List<Id> caseIds) {
        List<Id> results = new List<Id>();

        Map<Id, Case> casesById = new Map<Id, Case>([
            SELECT Id, ContactId FROM Case WHERE Id IN :caseIds
        ]);

        Set<Id> contactIds = new Set<Id>();
        for (Case c : casesById.values()) {
            if (c.ContactId != null) {
                contactIds.add(c.ContactId);
            }
        }

        Map<Id, Id> agentByContact = new Map<Id, Id>();
        for (Case prior : [
            SELECT ContactId, OwnerId FROM Case
            WHERE ContactId IN :contactIds AND IsClosed = true
              AND ClosedDate = LAST_N_DAYS:90 AND Owner.Type = 'User'
            ORDER BY ClosedDate DESC
        ]) {
            if (!agentByContact.containsKey(prior.ContactId)) {
                agentByContact.put(prior.ContactId, prior.OwnerId);
            }
        }

        for (Id caseId : caseIds) {
            results.add(agentByContact.get(casesById.get(caseId).ContactId));
        }
        return results;
    }
}
```

The `containsKey` guard on a descending-ordered query is the standard way to take the most recent match per group without an aggregate query.

## Reporting

`AgentWork` is where the operational metrics live:

```sql
SELECT User.Name agent,
       COUNT(Id) itemsHandled,
       AVG(SpeedToAnswer) avgSpeedToAnswer,
       AVG(HandleTime) avgHandleTime
FROM AgentWork
WHERE RequestDateTime = LAST_N_DAYS:30 AND Status = 'Closed'
GROUP BY User.Name
ORDER BY COUNT(Id) DESC
```

`SpeedToAnswer` is time from routing to acceptance. `HandleTime` is acceptance to closure. Together they separate a routing problem from a capacity problem — long speed-to-answer with normal handle time means not enough agents online; normal speed with long handle time means the work is harder than the capacity model assumes.

**Omni-Channel Supervisor** provides a live view: who is online, current queue depth, longest waiting item, agent workload. It is the tool support managers actually use during the day, and it is worth setting up properly rather than treating as an afterthought.

## Practical guidance

**Adopt Omni-Channel when volume justifies it.** A team of five sharing a queue does not need it. Thirty agents across four channels does.

**Start with simple capacity and tune from observed data.** The initial numbers will be wrong.

**Use skills sparingly.** Every skill requirement narrows the pool and increases wait time. Degradation is not optional once skills are in use.

**Prefer Omni-Channel Flows for anything conditional.** They replace the complex assignment rule chains that become unmaintainable.

**Route to the previous agent where it makes sense.** Cheap to build, and customers notice.

**Set up Supervisor.** Routing without live visibility means problems are discovered from complaints.
