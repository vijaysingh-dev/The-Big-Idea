# Typing API Responses and Zod

## Types are not runtime guarantees

```ts
type Product = { id: string; name: string; price: number };

const product = await fetch("/api/products/1").then(r => r.json()) as Product;
product.price.toFixed(2);   // compiles — crashes if the server sent a string
```

TypeScript types are **erased at build time**. The `as Product` assertion is a promise you made to the compiler, not a check. If the API changes a field, renames it, or returns `null`, nothing catches it until a component crashes at runtime — often far from the fetch.

This is the single largest gap between "typed frontend" and "safe frontend". Everything below closes it.

## Parse, do not assume

```ts
import { z } from "zod";

const productSchema = z.object({
  id: z.string(),
  name: z.string(),
  price: z.number(),
  tags: z.array(z.string()).default([]),
  createdAt: z.coerce.date(),
});

type Product = z.infer<typeof productSchema>;   // type derived from the schema

export async function getProduct(id: string, opts?: RequestOptions): Promise<Product> {
  const raw = await api.get(`/products/${id}`, opts);
  return productSchema.parse(raw);
}
```

Three things happen at once:

**Validation.** A wrong shape throws at the boundary, with a message naming the field — rather than crashing in a component three layers away.

**Type derivation.** `z.infer` means the type and the validator cannot drift. Editing the schema updates the type.

**Normalization.** `z.coerce.date()` converts the ISO string to a `Date`, and `.default([])` fills missing collections — so no component ever handles a date-shaped string or a null array ([[24.1 - Building an API Layer]]).

## safeParse for expected failures

```ts
const result = productSchema.safeParse(raw);

if (!result.success) {
  logger.warn("Schema mismatch", { issues: result.error.issues });
  throw new ValidationError(result.error.flatten());
}

return result.data;
```

`parse` throws; `safeParse` returns a discriminated union ([[25.6 - Discriminated Unions and Narrowing]]). Use `safeParse` where you want to handle the failure — logging a schema drift to monitoring is valuable, since it tells you the backend changed before users report it.

## Transforming at the boundary

```ts
const userSchema = z.object({
  first_name: z.string(),
  last_name: z.string(),
  email_address: z.string().email(),
}).transform(u => ({
  firstName: u.first_name,
  lastName: u.last_name,
  email: u.email_address,
  fullName: `${u.first_name} ${u.last_name}`,
}));

type User = z.infer<typeof userSchema>;   // the transformed shape
```

Snake case from the API becomes camel case internally, in one place. Every component sees the shape the frontend wants, and a backend rename is a one-line change.

`z.input` and `z.output` distinguish the pre- and post-transform types when both are needed.

## Composing schemas

```ts
const baseProduct = z.object({ id: z.string(), name: z.string() });

const productList = z.object({
  items: z.array(baseProduct),
  nextCursor: z.string().nullable(),
});

const createProductInput = baseProduct.omit({ id: true });
const updateProductInput = createProductInput.partial();
```

Schemas support the same derivation as types — `.pick()`, `.omit()`, `.partial()`, `.extend()`, `.merge()` — so request and response shapes derive from one definition ([[25.3 - Utility Types]]).

## Discriminated unions

```ts
const eventSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("created"), payload: productSchema }),
  z.object({ type: z.literal("deleted"), payload: z.object({ id: z.string() }) }),
]);
```

Zod checks the discriminant first and validates only the matching branch, which produces far clearer errors than a plain union — and the inferred type narrows correctly.

This is also how conditional form schemas are expressed ([[21.4 - Complex Forms]]).

## Sharing schemas with the server

```ts
// packages/shared/schemas.ts
export const createOrderSchema = z.object({
  items: z.array(z.object({ productId: z.string(), quantity: z.number().int().positive() })),
  couponCode: z.string().optional(),
});
```

The client validates before sending; the server validates on receipt. One definition, so the rules cannot drift — and both sides derive their types from it.

This is the strongest argument for a monorepo with a shared package, and it is where the pattern pays for itself most clearly.

## When not to validate everything

Validation has a cost. Parsing a 5MB response walks every field.

Reasonable policies:

**Validate at boundaries only** — API responses, `localStorage` reads, URL params, `postMessage` data. Not internal function arguments, where TypeScript already covers you.

**Validate strictly in development, loosely in production** for very large payloads:

```ts
const parsed = import.meta.env.DEV
  ? schema.parse(raw)
  : (raw as z.infer<typeof schema>);
```

This catches drift during development while avoiding the runtime cost in production. It is a compromise, not a best practice — use it only where measurement justifies it.

**Validate the fields you use.** A schema that omits fields you ignore is smaller and faster, and Zod strips unknown keys by default. Use `.passthrough()` if you need to forward the full object.

## Alternatives

| | Notes |
| --- | --- |
| **Zod** | the default; largest ecosystem, best React Hook Form integration |
| **Valibot** | modular and tree-shakeable, notably smaller bundle |
| **ArkType** | fastest, TypeScript-syntax definitions |
| **TypeBox** | JSON Schema output, useful with OpenAPI toolchains |

Zod 4 substantially reduced bundle size and improved performance, narrowing Valibot's advantage. For a bundle-sensitive application, measure both ([[19.7 - Bundle Analysis and Optimization]]).

## Generating types from the backend

Where the backend publishes a schema, generation beats hand-writing:

```bash
npx openapi-typescript ./openapi.yaml -o ./src/types/api.d.ts
```

```ts
import type { paths } from "./types/api";
type Product = paths["/products/{id}"]["get"]["responses"]["200"]["content"]["application/json"];
```

Similarly, GraphQL Code Generator produces types and typed hooks from a GraphQL schema, and tRPC gives end-to-end inference with no generation step at all in a TypeScript monorepo.

Note that generation gives **compile-time** types, not runtime validation. It guarantees you match the documented contract, not that the server honours it. Generation plus runtime validation at critical boundaries is the belt-and-braces approach.

## Validating other inputs

The same discipline applies beyond HTTP:

```ts
// localStorage — written by a previous app version, or corrupted
const stored = settingsSchema.safeParse(JSON.parse(raw ?? "null"));
const settings = stored.success ? stored.data : defaults;

// URL params — user-controlled
const params = filterSchema.safeParse(Object.fromEntries(searchParams));

// postMessage — cross-origin
window.addEventListener("message", (e) => {
  if (e.origin !== TRUSTED_ORIGIN) return;
  const msg = messageSchema.safeParse(e.data);
});
```

All three are untrusted input that TypeScript will happily type as whatever you assert ([[14.2 - LocalStorage and SessionStorage]], [[23.3 - Dynamic Routes and Params]]).

## Monitoring schema drift

```ts
if (!result.success) {
  reportToSentry(new SchemaError(endpoint, result.error.issues));
}
```

A schema failure in production means the backend changed. Reporting it turns a silent breakage into an alert — often before the failure reaches a user-visible path.

This is a genuinely underused benefit of runtime validation: it makes contract violations observable ([[28.13 - Frontend Observability]]).

## How senior engineers actually use this

**They validate every API response at the boundary** and derive types from the schema rather than the reverse.

**They normalize in the schema** — dates, casing, defaults — so no component handles raw server shapes.

**They share schemas between client and server** where the stack allows.

**They report schema failures to monitoring**, treating them as contract-violation alerts.

**They validate `localStorage`, URL params and `postMessage`** with the same discipline as HTTP.

## Common pitfalls

- `as Product` on a fetch result, which checks nothing.
- Hand-written types that drift from the schema — derive with `z.infer` instead.
- Validating internal function arguments, adding cost with no benefit.
- Forgetting `z.coerce.date()`, so dates stay strings and break at a distant call site.
- Not handling `safeParse` failure, so a schema change crashes the app.
- Assuming generated OpenAPI types guarantee runtime shape.
- Parsing very large payloads on every request without measuring the cost.

## Interview angle

"How do you make sure API responses match your types" is a question that separates people who have shipped from people who have not. The core point is that TypeScript types are erased, so an `as` assertion checks nothing — runtime validation at the boundary is what actually guarantees the shape. Then the practical benefits: derive types from the schema so they cannot drift, normalize dates and casing in one place, share the schema with the server, and report validation failures as contract-drift alerts.
