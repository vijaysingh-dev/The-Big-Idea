# Macros, Quick Text and Agent Shortcuts

## The repetition problem

Support work is repetitive by nature. The same twelve issues account for most of the volume, and the same sequence of steps closes each of them: update the status, set the reason, send a templated email, log a task.

Doing that by hand thirty times a day is both slow and inconsistent. Two agents handling the same issue produce different field values and different customer wording.

Macros and quick text address exactly this, and they are among the highest-return features in Service Cloud relative to the effort of setting them up.

## Quick Text

Reusable snippets of text, inserted with a keyboard shortcut into an email, chat, or any text field.

```
Name: Warranty Claim Received
Category: Warranty
Message: Thank you for submitting your warranty claim for {!Case.Machine__r.Serial_Number__c}.
         We have logged this as case {!Case.CaseNumber} and will confirm the outcome
         within 2 working days.
Channels: Email, Internal
```

Merge fields make the snippet contextual rather than generic — the customer sees their serial number and case number, not a form letter.

Quick text is organized by **folder** and can be shared with specific groups, so the warranty team's snippets do not clutter the billing team's list.

Its practical value is largest in chat, where agents type continuously and a three-keystroke insertion of a standard greeting or a common explanation saves real time per conversation.

## Macros

A macro runs a sequence of actions on the record the agent is viewing. It automates the click path, not the thinking.

```
Macro: Close as Duplicate

  Set Case Status         → "Closed"
  Set Case Reason         → "Duplicate"
  Set Resolution          → "Duplicate of an existing case"
  Insert email template   → "Duplicate Case Notification"
  Send email
  Save
```

Two kinds:

**Regular macros** stop for the agent at any step needing input. The agent reviews the drafted email before sending.

**Irreversible macros** run every step without stopping, including sending email and saving. Faster, and they cannot be undone — hence the name and the separate permission required to run them.

The design principle: **irreversible macros for actions with no judgement involved**, regular macros where the agent should see what is being sent. An irreversible macro that emails a customer is a decision to make deliberately.

Macros are built in the Macro Builder, which records the actions against a page layout, and they are metadata so they deploy between orgs.

## Where macros run out

Macros operate on the current record through the UI. They cannot query other records, apply conditional logic, call an external system, or create related records with computed values.

When the requirement exceeds that, the ladder is:

**Quick action** — a single create or update with prefilled fields.
**Screen flow launched from a quick action** — conditional logic, multiple steps, related record creation.
**LWC screen action** — full control over the interaction.
**Invocable Apex called from a flow** — anything requiring queries, callouts, or bulk work.

The common Service Cloud build is a flow launched from a quick action, because it handles most of what macros cannot while remaining admin-maintainable.

```java
public with sharing class CaseResolutionService {

    public class ResolutionRequest {
        @InvocableVariable(required=true) public Id caseId;
        @InvocableVariable(required=true) public String resolutionCode;
        @InvocableVariable public Boolean createKnowledgeDraft;
    }

    @InvocableMethod(label='Resolve Case' description='Applies a resolution and optional follow-up')
    public static void resolve(List<ResolutionRequest> requests) {
        Map<Id, ResolutionRequest> requestsByCase = new Map<Id, ResolutionRequest>();
        for (ResolutionRequest req : requests) {
            requestsByCase.put(req.caseId, req);
        }

        Map<String, Resolution_Code__mdt> codes = Resolution_Code__mdt.getAll();
        List<Case> toUpdate = new List<Case>();

        for (Case c : [SELECT Id, Status, Reason FROM Case WHERE Id IN :requestsByCase.keySet()]) {
            ResolutionRequest req = requestsByCase.get(c.Id);
            Resolution_Code__mdt code = codes.get(req.resolutionCode);
            if (code == null) {
                continue;
            }
            c.Status = code.Target_Status__c;
            c.Reason = code.Case_Reason__c;
            c.Resolution__c = code.Resolution_Text__c;
            toUpdate.add(c);
        }

        update toUpdate;
    }
}
```

Taking a `List` of requests is not optional — flows invoke this in bulk when called from a record-triggered context, and a method assuming one record will fail. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Email templates

Templates are the backbone of consistent customer communication, and Lightning Email Templates support merge fields, rich text, and folder-based sharing.

Two things to get right:

**Use `setWhatId()` when sending from Apex**, or case merge fields resolve to blanks. This is the most common template defect.

```java
Messaging.SingleEmailMessage message = new Messaging.SingleEmailMessage();
message.setTargetObjectId(contactId);
message.setWhatId(caseId);
message.setTemplateId(templateId);
message.setOrgWideEmailAddressId(supportAddressId);
message.setSaveAsActivity(true);
Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{ message });
```

**Send from an organization-wide address**, not the agent's, so replies thread back to the case and survive the agent leaving. See [[05.6 - Email-to-Case and Web-to-Case]].

## Keyboard shortcuts

The console supports shortcuts for navigation and for custom actions. Agents who learn them are measurably faster, and the cost of configuring a handful is negligible.

Worth mapping: run the most-used macro, open knowledge search, move to the next tab, save and close.

## Building a macro library that gets used

The failure mode is a library of ninety macros nobody can find, which agents ignore in favour of doing it by hand.

What works:

**Start from the data.** Query the most common case reason and resolution combinations, and build macros for the top ten. That covers most volume.

```sql
SELECT Type, Reason, COUNT(Id) volume
FROM Case
WHERE ClosedDate = LAST_N_DAYS:90
GROUP BY Type, Reason
ORDER BY COUNT(Id) DESC
LIMIT 20
```

**Name them by what the agent is trying to do**, not by what they change. "Close as Duplicate" beats "Set Status Closed Reason Duplicate".

**Organize by folder and share by team.** An agent scrolling past sixty irrelevant macros will stop looking.

**Review quarterly.** Macros referencing a retired status or a removed field fail silently and erode trust in the whole library.

**Measure adoption.** If a macro is not being used, either it is not needed or it cannot be found, and both are worth knowing.

## Practical guidance

**Build macros from actual case data**, not from what someone thinks agents do.

**Use quick text heavily in chat.** The return per keystroke is highest there.

**Reserve irreversible macros for actions with no judgement.**

**Escalate to a flow when a macro cannot express it** rather than building a chain of three macros the agent runs in sequence.

**Always `setWhatId()`.** Blank merge fields in a customer email is the most visible small failure in Service Cloud.

**Prune the library.** A stale macro is worse than no macro, because an agent trusted it.
