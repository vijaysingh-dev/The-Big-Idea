# Periodic Tasks and Distributed Cron

#backend #queues #scheduling

> **In one line:** Running a job on a schedule across a fleet means exactly one instance must fire it, the fire must be recorded durably, and a missed window must be either caught up or explicitly abandoned.

---

## The Idea

```
Every night at 02:00: expire old sessions
Every 5 minutes:      sync sources
Every hour:           reconcile the search index
```

On one server this is `cron`. On twenty pods it is three separate problems:

| Problem | |
|---|---|
| **Who fires it?** | Twenty pods means twenty firings, unless coordinated |
| **What if the firer is down at 02:00?** | The job silently does not run |
| **What if it fires but the work fails?** | A schedule is not a durability mechanism |

💡 **The critical distinction: a scheduler decides *when*, a queue decides *that it happens*.** A scheduler that executes work directly conflates the two, and you lose the durability that makes background work reliable ([[08.1 - Why Background Work Exists]]).

**A periodic task should enqueue, not execute.**

---

## Celery Beat

```python
app.conf.beat_schedule = {
    "sync-sources": {
        "task": "app.tasks.sync_all_sources",
        "schedule": crontab(minute="*/5"),
        "options": {"queue": "default", "expires": 240},
    },
    "expire-sessions": {
        "task": "app.tasks.expire_sessions",
        "schedule": crontab(hour=2, minute=0),
    },
}
```

```bash
celery -A app beat --loglevel=info
```

⚠️ **Beat is a singleton. Running two produces every task twice.**

There is no built-in leader election. Your options:

| Approach | |
|---|---|
| **One replica, orchestrator-restarted** | Simplest. A gap while it restarts |
| **Leader election** | K8s `Lease`, or a database lease ([[07.6 - Leader Election and Coordination]]) |
| **`redbeat`** | Redis-backed schedule with a lock |
| **Do not use beat** | Kubernetes `CronJob`, or a claim-based scheduler |

💡 **The `expires` option is underused and important.** A task scheduled every 5 minutes with `expires=240` is discarded if it has not started within 4 minutes — which prevents a backlog of stale sync tasks piling up after an outage and then all running at once.

### The state file problem

```bash
celery beat --schedule=/var/run/celerybeat-schedule
```

Beat writes the last-run time to a local file. **In a container, that file is ephemeral.**

⚠️ **A restarted beat with no state file may immediately fire every task**, because it has no record of the last run. On a deploy, that means every scheduled job runs at once.

```bash
celery beat -S redbeat.RedBeatScheduler      # state in Redis, shared
```

`redbeat` stores the schedule and last-run times in Redis and takes a lock, which solves both the state and the singleton problems.

## Kubernetes CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: sync-sources
spec:
  schedule: "*/5 * * * *"
  concurrencyPolicy: Forbid          # ⚠️ default is Allow
  startingDeadlineSeconds: 200
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: enqueue
              command: ["python", "-m", "app.enqueue", "sync_all_sources"]
```

💡 **The `command` enqueues a task rather than doing the work.** The CronJob is the trigger; Celery is the execution and retry mechanism. **This separation is the right shape** — you get Kubernetes' scheduling reliability plus your queue's durability and retries.

⚠️ **`concurrencyPolicy` defaults to `Allow`**, so a job that runs longer than its interval overlaps with itself. `Forbid` skips the new run; `Replace` kills the old one.

⚠️ **`startingDeadlineSeconds` controls catch-up behaviour**, and it has a sharp edge: if the controller misses more than 100 scheduled times within the deadline window, **it stops scheduling entirely** and logs an error most people never see.

**Set `startingDeadlineSeconds` to slightly more than one interval**, so a brief controller outage skips one run rather than triggering the 100-miss failure.

### CronJob versus Beat

| | K8s CronJob | Celery Beat |
|---|---|---|
| Singleton | **Handled by Kubernetes** | Your problem |
| State | In etcd, durable | A local file, or Redis |
| Missed runs | Configurable deadline | Fires immediately on restart |
| Schedule changes | A deploy | Config, or dynamic with redbeat |
| Sub-minute schedules | **No** | Yes |
| Observability | Job history, pod logs | Beat logs |

💡 **On Kubernetes, prefer CronJob for anything at minute granularity or coarser.** It removes the singleton problem entirely and the state is durable. Beat earns its place for sub-minute schedules and for dynamically-managed schedules.

## The Claim Pattern

The simplest correct approach, and the one worth defaulting to.

```sql
CREATE TABLE schedules (
    name          text PRIMARY KEY,
    interval_secs int NOT NULL,
    last_claimed  timestamptz,
    last_completed timestamptz,
    claimed_by    text
);
```

```python
async def try_claim(name: str) -> bool:
    row = await conn.fetchrow(
        """
        UPDATE schedules
        SET last_claimed = now(), claimed_by = $2
        WHERE name = $1
          AND (last_claimed IS NULL
               OR last_claimed < now() - make_interval(secs => interval_secs))
        RETURNING name
        """,
        name, node_id,
    )
    return row is not None


# Every pod runs this loop
async def scheduler_loop():
    while True:
        for name in SCHEDULES:
            if await try_claim(name):
                await enqueue_for(name)
        await asyncio.sleep(10)
```

💡 **Every pod tries; exactly one succeeds, because the `UPDATE` is atomic.** No leader, no election, no singleton, no state file.

| Property | |
|---|---|
| **No coordination** | The database decides |
| **No single point of failure** | Any pod can fire it |
| **Durable state** | Last-run is a row |
| **Observable** | `SELECT * FROM schedules` tells you everything |
| **Restartable** | A pod restart changes nothing |

⚠️ **This is at-least-once, not exactly-once.** A pod that claims and then dies before enqueuing means the job does not run that interval. **Add a completion marker if that matters:**

```sql
WHERE name = $1
  AND (last_completed >= last_claimed              -- previous run finished
       OR last_claimed < now() - interval '10 minutes')   -- or it is stale
  AND (last_claimed IS NULL
       OR last_claimed < now() - make_interval(secs => interval_secs))
```

💡 **For Conduit's periodic work, this is the right answer** — it is simpler than leader election, fails better, and the state is visible in a table you already back up ([[07.6 - Leader Election and Coordination]]).

## Missed Windows

The question every scheduler must answer and most do not.

```
02:00 job scheduled
02:00–02:45 the scheduler is down
02:45 the scheduler recovers
```

**What should happen?**

| Policy | Right for |
|---|---|
| **Skip** | Idempotent periodic work — a sync, a reconciliation. The next run covers it |
| **Catch up once** | Work that must happen daily — a report, a billing run |
| **Catch up all** | Work where each interval is distinct and required |

⚠️ **The default is usually "fire immediately on recovery", which is the worst of the three** — it produces a thundering herd of catch-up jobs at exactly the moment the system is recovering.

```python
if now - last_run > interval * MAX_CATCHUP_INTERVALS:
    log.warning("skipping missed runs", missed=int((now - last_run) / interval))
    await mark_run(name, now)          # skip forward
else:
    await enqueue_for(name)
```

💡 **Make the policy explicit per schedule.** "Sync sources" should skip — the next sync covers everything. "Generate the monthly invoice" must catch up, and probably needs a human to confirm.

### Time-bucketed idempotency

```python
@app.task
def daily_report(date: str):                     # ← the date is a parameter
    key = f"daily_report:{date}"
    if not await claim_once(key):
        return                                    # already ran for this date
    ...
```

⚠️ **A periodic task with no time parameter cannot tell whether it already ran for a given period.** Passing the bucket in makes it idempotent per period, which means catch-up and retries are both safe ([[07.5 - Idempotency Keys and Deduplication]]).

**This is the single best design decision for periodic tasks**, and it costs one argument.

## In Production

### Never execute in the scheduler

```python
# ⚠️ Wrong
@app.task
def nightly_cleanup():
    for org in all_orgs():                       # 10,000 organisations
        cleanup(org)                              # 4 hours in one task

# Right
@app.task
def nightly_cleanup():
    for org_id in all_org_ids():
        cleanup_org.delay(org_id, date=today())   # fan out
```

💡 **The periodic task's job is to enqueue.** It should run in seconds, be trivially retryable, and produce work that retries independently ([[08.5 - Task Design Rules]]).

⚠️ **A four-hour scheduled task exceeds every visibility timeout, blocks a worker slot, is killed on every deploy, and reports no progress.** Everything wrong with long tasks, on a schedule.

### Monitoring: the missing job

⚠️ **A scheduled job that does not run produces no error, no log line and no alert.** It is the quietest failure in a backend system.

```python
schedule_last_success_timestamp.labels(name=name).set(time.time())
schedule_runs_total.labels(name=name, status=...).inc()
schedule_duration_seconds.labels(name=name).observe(elapsed)
schedule_missed_total.labels(name=name).inc()
```

```yaml
# The alert that matters
- alert: ScheduledJobNotRunning
  expr: time() - schedule_last_success_timestamp > 2 * schedule_interval_seconds
```

💡 **Alert on staleness, not on failure.** A failed job alerts loudly; a job that never fires is silent, and it is the more common problem.

**Dead man's switch** is the external version:

```python
# The job pings a monitoring service; the service alerts if the ping stops
await httpx.get(f"https://hc-ping.com/{CHECK_UUID}")
```

⚠️ **A dead man's switch catches failures your own monitoring cannot** — including your monitoring being down, your scheduler pod never starting, and your entire cluster being unreachable. **For anything critical and infrequent, this is worth the external dependency.**

### Overlap protection

```python
@app.task(bind=True)
def sync_all_sources(self):
    if not await try_lock("sync_all_sources", ttl=600):
        log.info("previous run still active, skipping")
        overlap_skipped_total.inc()
        return
    try:
        ...
    finally:
        await release_lock("sync_all_sources")
```

⚠️ **A job scheduled every 5 minutes that takes 7 minutes overlaps forever**, and the overlap compounds until the queue is saturated with copies of the same job.

💡 **Skipping is almost always the right response to overlap for periodic work**, because the next scheduled run will pick up whatever was missed. Queueing the overlapping run makes the backlog worse.

**Track `overlap_skipped_total`** — a rising count means the job no longer fits in its interval, and the schedule or the job needs changing.

### Timezone and DST

```python
crontab(hour=2, minute=0)          # 02:00 in which zone?
```

```python
app.conf.timezone = "UTC"
app.conf.enable_utc = True
```

⚠️ **Schedule everything in UTC.** A 02:00 local schedule in a DST-observing zone runs twice on one day of the year and not at all on another.

💡 **If a job genuinely must run at a local time — sending a daily digest at 09:00 in each user's timezone — that is not a scheduling problem, it is a data problem.** Run hourly in UTC and select users whose local time is currently 09:00.

### Conduit's schedules

| Schedule | Interval | Mechanism | Missed policy | Overlap |
|---|---|---|---|---|
| Sync sources | 5 min | Claim pattern | **Skip** | Skip |
| Reconcile search index | 1 hour | Claim pattern | Skip | Skip |
| Expire dead letters | Daily | K8s CronJob | Catch up once | Forbid |
| Usage rollup for billing | Daily | K8s CronJob + date param | **Catch up all** | Forbid |
| Refresh materialised views | 15 min | Claim pattern | Skip | Skip |
| Vacuum idempotency records | Daily | K8s CronJob | Skip | Forbid |

💡 **Only one has "catch up all", and it is the one where each day is a distinct, required computation.** Everything else is a reconciliation that the next run covers — and recognising that distinction is what keeps recovery from a scheduler outage simple.

## Codebase

**Repo:** `celery/celery`, `sibson/redbeat`, `kubernetes/kubernetes`

**Question to answer:** How does Celery Beat decide a task is due, and what happens to that decision when beat restarts? Then: in the Kubernetes CronJob controller, what exactly does `startingDeadlineSeconds` control, and what is the 100-missed-schedules behaviour?

**Read, in order:**

1. `celery/celery/beat.py` — **`Scheduler.tick` and `ScheduleEntry.is_due`.** This is the scheduling loop, and it is short
2. `celery/celery/beat.py` — `PersistentScheduler` and the shelve-based state file. **The answer to the second half of the first question: on restart with no state, entries are due immediately**
3. `redbeat/redbeat/schedulers.py` — **the Redis-backed alternative**, with a lock and shared state. Compare the two designs
4. `kubernetes/pkg/controller/cronjob/cronjob_controllerv2.go` — **`getNextScheduleTime` and the `tooManyMissedTimes` check.** The answer to the second question, and the 100-miss behaviour is right there
5. `kubernetes/pkg/controller/cronjob/utils.go` — `getMostRecentScheduleTime`, which implements the deadline logic

💡 The Kubernetes 100-missed-schedules behaviour is worth knowing because **it is a silent stop, not a loud failure.** A controller outage longer than your deadline window means the CronJob simply stops scheduling and logs a message. **If you use CronJobs for anything critical, alert on job staleness rather than trusting the controller.**

**Part 1 — Break Celery Beat three ways.**

- **Two beats:** run two instances. **Count duplicate firings over 10 minutes.**
- **State loss:** run beat with a schedule containing five jobs at various intervals, kill it, delete the state file, restart. **Confirm all five fire immediately.**
- **Container restart:** the same in a container with an ephemeral filesystem, across a rolling deploy. **Measure duplicate firings per deploy.**

Then `redbeat` and confirm all three are fixed.

**Part 2 — CronJob concurrency and deadlines.** A job taking 7 minutes on a 5-minute schedule.

Test `Allow`, `Forbid` and `Replace`. **Chart concurrent job count over 30 minutes for each.**

`Allow` should grow without bound.

Then the deadline: stop the CronJob controller (or simulate by suspending the CronJob) for longer than `startingDeadlineSeconds` × 100 intervals. **Confirm it stops scheduling entirely** and find the log message.

**Part 3 — The claim pattern.** Implement it. Twenty pods, five schedules at different intervals.

Run for an hour. **Assert each schedule fired exactly the expected number of times** — no duplicates, no misses.

Then kill pods randomly throughout and confirm the count is unchanged.

Then kill the pod that just claimed, before it enqueued. **Confirm that interval is missed**, then add the completion marker and confirm it is recovered.

**Part 4 — Missed window policies.** A schedule firing every 5 minutes, stopped for 2 hours.

Implement all three policies. On recovery, measure: jobs enqueued, time to drain, and impact on other queues.

**`catch_up_all` should produce 24 jobs at once.** Chart the queue depth spike.

Then implement bounded catch-up — at most N missed intervals — and show it bounding the spike.

**Write in `COMPARISON.md` which policy suits each of Conduit's six schedules.**

**Part 5 — Overlap.** The 7-minute job on a 5-minute schedule, unprotected.

Chart concurrent executions over an hour. **It should grow without bound.**

Then with skip-if-running. Confirm concurrency stays at 1 and `overlap_skipped_total` rises.

Then measure how long until the job stops fitting its interval as data grows, and use `overlap_skipped_total` as the early warning.

**Part 6 — The silent failure.** Configure a schedule, then break it so it never fires — a wrong queue name, a crashed beat, or a suspended CronJob.

**Run normally for 30 minutes and record how you would have found out.** Check every dashboard you have.

Then add the staleness alert and repeat. **Measure time to detection.**

Then add an external dead man's switch, and break your own monitoring as well as the job. **Confirm the external check still fires.**

**Part 7 — Time-bucketed idempotency.** A daily report task, first without a date parameter and then with one.

For each: run it twice for the same day, run it as a catch-up after a 3-day outage, and retry it after a failure.

**Confirm the parameterised version produces exactly one report per day in all three cases** and the unparameterised one does not.

**Done when:**
- You have counted duplicate firings from two beats and from state loss
- Your CronJob concurrency chart shows `Allow` growing without bound
- The claim pattern fires exactly once per interval across twenty pods and random kills
- Your catch-up spike is charted and then bounded
- Overlap protection holds concurrency at 1, with a rising skip counter
- You measured time-to-detection for a silent scheduling failure, before and after alerting
- The date-parameterised task is correct across duplicates, catch-up and retries
