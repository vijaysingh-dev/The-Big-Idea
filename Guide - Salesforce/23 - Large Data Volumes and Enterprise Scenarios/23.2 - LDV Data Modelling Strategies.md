# LDV Data Modelling Strategies

## The questions that change at scale

A model that works at 100,000 records can fail at ten million for reasons that have nothing to do with correctness.

```
How will this be queried, and can that query use an index?
How will the records be distributed across parents and owners?
How much sharing work does a change to this record cause?
What is the retention policy, and how will old records leave?
```

**The last question is the one nobody asks at design time**, and retrofitting archiving onto a populated object is a project rather than a change.

## Master-detail versus lookup at scale

The choice has consequences that only appear at volume.

**Master-detail:**

```
Children inherit the parent's sharing — no separate sharing rows for the child
Roll-up summaries are available
Deleting the parent deletes the children
Every child save locks the parent for roll-up recalculation
Reparenting is restricted, and expensive
```

**Lookup:**

```
The child has its own sharing — its own sharing rows
No roll-up summaries
Independent lifecycle
The lookup target is locked on child insert and update
Reparenting is free
```

**At scale, the sharing consequence dominates.**

A master-detail child generates **no sharing rows of its own** — access is derived from the parent. A lookup child on a private object generates its own rows, and with ten million children and a role hierarchy, that is a very large sharing table.

**That argues for master-detail on high-volume child objects**, and against it where the parent has skew — because then every child save contends on one row.

**The unresolvable tension:** master-detail reduces sharing volume and increases lock contention. Which matters more depends on whether the parent distribution is even.

For Northwind's claims:

```
Warranty_Claim__c → Asset            master-detail
    Assets are evenly distributed across accounts, so contention is bounded
    Ten million claims generate no sharing rows of their own
    Roll-ups on the asset are available

Claim_Part__c → Warranty_Claim__c    master-detail
    Same reasoning, one level deeper
```

**Where the parent has skew, use a lookup and hand-roll the aggregate** — accepting the sharing cost to avoid the contention. See [[10.9 - Data Skew]].

## Roll-up summaries at scale

Each roll-up on an object is recalculated on every child change.

```
40 roll-ups on Account
    → every contact, opportunity, case, and asset change recalculates 40 values
        → the account is locked for the duration
```

**Roll-up count on hot parents is a real performance decision**, and forty is not unusual in a mature org.

**The questions per roll-up:**

```
[ ] Is it displayed, or only used in a report?
[ ] Does it need to be real-time?
[ ] Is it driving automation, or informational?
```

**A roll-up only used in a report can frequently be a report grouping instead**, which costs nothing at save time.

**A roll-up that need not be real-time can be a scheduled recalculation** — trading currency for the removal of per-save contention:

```java
public with sharing class AssetRollupBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id FROM Asset WHERE Rollup_Stale__c = true
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Asset> scope) {
        // aggregating in the database rather than per-save removes the lock entirely
        Map<Id, AggregateResult> totals = new Map<Id, AggregateResult>();

        for (AggregateResult result : [
            SELECT Asset__c assetId, COUNT(Id) claimCount, SUM(Claim_Amount__c) claimTotal
            FROM Warranty_Claim__c
            WHERE Asset__c IN :scope AND Status__c != 'Closed'
            GROUP BY Asset__c
        ]) {
            totals.put((Id) result.get('assetId'), result);
        }

        applyTotals(scope, totals);
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**A `Rollup_Stale__c` flag set by the child's trigger** means the batch only processes what changed, rather than recalculating everything nightly.

## Denormalization

At scale, a query that traverses relationships is slower than one that does not.

```sql
-- Two joins, and Account.Industry is not indexed on the claim
SELECT Id, Claim_Amount__c FROM Warranty_Claim__c
WHERE Asset__r.Account.Industry = 'Manufacturing'
```

```sql
-- One table, and the field can be indexed
SELECT Id, Claim_Amount__c FROM Warranty_Claim__c
WHERE Account_Industry__c = 'Manufacturing'
```

**Copying a parent field onto the child** makes it filterable and indexable, at the cost of keeping it synchronized.

**Formula fields do not help here.** A cross-object formula is evaluated at query time and cannot be indexed unless it is deterministic and same-record. See [[06.4 - Cross-Object Formulas and Limits]].

**The synchronization cost** is a trigger on the parent updating its children:

```java
public static void propagateIndustryChange(
    List<Account> accounts, Map<Id, Account> priorAccounts
) {
    Set<Id> changed = new Set<Id>();

    for (Account account : accounts) {
        if (account.Industry != priorAccounts.get(account.Id).Industry) {
            changed.add(account.Id);
        }
    }

    if (changed.isEmpty()) {
        return;
    }

    // a parent change cascades to potentially millions of children, so it goes async
    System.enqueueJob(new IndustryPropagationQueueable(changed));
}
```

**A parent field change cascading to millions of children must be asynchronous**, and at real volume it is a batch job rather than a Queueable.

**Denormalize deliberately, and few fields.** Every denormalized field is a synchronization obligation, and the ones that go stale are worse than useless.

## Partitioning by time

The most effective structural change for a high-volume transactional object.

```
Warranty_Claim__c              current, retained 3 years
Claim_Archive__b               older, in a big object
```

**The current object stays small**, which keeps every query, report, and load fast. The archive holds everything else at a fraction of the storage cost.

**The design decisions:**

**Where is the boundary?** Frequently a status plus an age — closed and older than three years.

**What is retained in the archive?** Not every field; the ones needed for audit and lookup.

**How is it surfaced?** A component on the parent record showing archived history, so the archive is not a loss from the user's perspective.

See [[23.4 - Archiving with Big Objects and External Storage]].

## Divisions

An older feature, rarely enabled, and occasionally the right answer.

**Divisions partition data logically**, and a user's queries are scoped to their division by default.

```sql
SELECT Id FROM Account WHERE Division = 'EMEA'
```

**What they buy:** the query optimizer treats division as a filter, which improves selectivity across very large objects.

**What they cost:** enablement is irreversible, they add a field to every object, and they complicate every query and report.

**Salesforce must enable them**, and they are not offered readily.

The realistic position: **divisions are for orgs with tens of millions of records across clearly separated business units**, where the separation is genuine and permanent. Most orgs that consider them are better served by archiving.

## Junction objects at scale

A many-to-many relationship at volume is a large object in its own right.

```
Asset            100,000
Service_Contract__c  20,000
Machine_Coverage__c  2,000,000    the junction
```

**The junction is the high-volume object**, and it is frequently modelled without that in mind.

**Design consequences:**

**Master-detail on both sides** means no sharing rows for the junction, which at two million records is a substantial saving.

**A unique composite key** enforced by a text field prevents duplicates that a query-based check misses at volume:

```java
coverage.Unique_Key__c = coverage.Asset__c + '|' + coverage.Service_Contract__c;
```

The database enforces it regardless of how the record arrives, which a trigger check does not — an in-batch duplicate arriving in the same insert is invisible to a query. See [[02.8 - Many-to-Many and Junction Objects]].

**Query from the side with fewer records** where possible, since the junction is the expensive traversal.

## Field count and object width

An object with 400 fields is expensive to query even when few are selected.

**Standard and custom fields are stored separately**, so a query touching both requires a join. A skinny table containing both eliminates it. See [[16.9 - Skinny Tables and Custom Indexes]].

**Long text areas are stored separately again**, and querying one on many rows is a heap problem.

**The practical guidance:**

**Select only the fields used.** `FIELDS(ALL)` on a wide object at volume is a heap failure waiting to happen.

**Consider a related object** for rarely-used fields on a wide, high-volume object — a `Claim_Detail__c` holding the twenty fields used by 5% of claims.

**Watch formula field count.** Each is evaluated per row on read, and cross-object ones traverse.

## External objects

Data that should not be in Salesforce at all.

```
ERP invoice history        12 years, several million rows, read-only, rarely accessed
```

**Salesforce Connect** surfaces it as an external object without storing it:

```
ErpInvoice__x        an OData or custom adapter connection
    indirect lookup on Account.ERP_Account_Id__c
        → a related list on the Account page
```

**What it avoids:** storage, sync, staleness, and every LDV consequence of holding the data.

**What it costs:** no reporting, no automation, no roll-ups, and a related list that errors when the external system is down.

**The test:** is the data ever the subject of a report or an automation? If not, an external object is frequently better than syncing it. See [[02.14 - External Objects and Salesforce Connect]].

## Big objects for high-volume writes

Not only for archives — big objects are the right store for high-volume, append-only data.

```
Machine_Reading__b        telemetry, millions of rows per month
    Composite key: Asset_Id__c, Reading_Timestamp__c
```

**What they give:** effectively unlimited volume, minimal storage cost, and no sharing rows.

**What they cost:** the index is defined at creation and cannot change, queries must filter on the index fields in order, there is no reporting in the usual sense, and updates are not supported — only insert and delete.

**The index definition is the whole design.** Getting it wrong means the data is written and unqueryable, and changing it means recreating the object.

See [[02.15 - Big Objects]].

## A worked model

Northwind at scale — eight million claims, 100,000 assets, twelve years of history.

```
Account                    50,000        standard
Asset                      100,000       standard, master-detail to Account
Service_Contract__c        20,000        lookup to Account
Machine_Coverage__c        2,000,000     junction, master-detail both sides,
                                         unique composite key
Warranty_Claim__c          2,000,000     master-detail to Asset, 3-year retention
                                         denormalized Account_Industry__c for filtering
                                         external ID on ERP_Claim_Id__c
Claim_Part__c              6,000,000     master-detail to claim
Claim_Archive__b           6,000,000     big object, claims older than 3 years
Machine_Reading__b         500,000,000   big object, telemetry
ErpInvoice__x              external      Salesforce Connect, not stored
```

**The decisions that make it work:**

**Master-detail throughout the claim hierarchy**, so eight million records generate no sharing rows of their own.

**A three-year retention boundary**, keeping the queryable object at two million rather than eight.

**Telemetry in a big object**, never in a standard object.

**Invoices external**, never synced.

**One denormalized field** for the filter that reports actually use.

**External IDs on every integrated object**, indexed for free.

## Practical guidance

**Ask about distribution, not just volume**, during data modelling.

**Prefer master-detail on high-volume children** to avoid sharing rows — unless the parent has skew.

**Audit roll-up count on hot parents**, and move non-urgent ones to a scheduled recalculation.

**Denormalize deliberately and sparingly**, with async propagation.

**Plan the retention boundary before launch.**

**Put append-only high-volume data in big objects**, and define the index carefully.

**Use external objects** for data that is never reported on or automated.

**Add external IDs from the start** — they index for free.

**Enforce junction uniqueness with a composite key field**, not a trigger check.
