# GraphQL API

## What it adds

The REST API returns whatever the resource defines. The GraphQL API lets the **client** specify exactly which fields it wants, across related objects, in one request.

```
POST /services/data/v62.0/graphql
```

```graphql
query ClaimContext($claimId: ID!) {
  uiapi {
    query {
      Warranty_Claim__c(where: { Id: { eq: $claimId } }) {
        edges {
          node {
            Id
            Claim_Number__c { value }
            Claim_Amount__c { value displayValue }
            Status__c { value }
            Asset__r {
              Name { value }
              SerialNumber { value }
              Account {
                Name { value }
                BillingCountry { value }
              }
            }
          }
        }
      }
    }
  }
}
```

The value of this over REST: **one request replaces several**, and the response contains only the fields asked for. A component needing a claim, its asset, and that asset's account makes one call rather than three, and receives no fields it will not display.

## The response shape

```json
{
  "data": {
    "uiapi": {
      "query": {
        "Warranty_Claim__c": {
          "edges": [
            {
              "node": {
                "Id": "a0X5g000001AbCdEAK",
                "Claim_Number__c": { "value": "WC-00042" },
                "Claim_Amount__c": { "value": 150000, "displayValue": "₹1,50,000.00" },
                "Asset__r": {
                  "Name": { "value": "Press P400" },
                  "SerialNumber": { "value": "SN-88213" }
                }
              }
            }
          ]
        }
      }
    }
  },
  "errors": []
}
```

Two structural details.

**Every field is an object with `value` and `displayValue`.** `value` is the raw data; `displayValue` is formatted for the running user's locale and currency. This is genuinely useful — a currency field comes back both as a number for calculation and as a locale-formatted string for display, with no client-side formatting logic.

**The `edges`/`node` wrapper** is standard GraphQL connection structure, supporting pagination metadata alongside the records.

## Filtering, ordering, pagination

```graphql
query OpenClaims($first: Int, $after: String) {
  uiapi {
    query {
      Warranty_Claim__c(
        where: {
          and: [
            { Status__c: { ne: "Closed" } }
            { Claim_Amount__c: { gt: 100000 } }
            { Claim_Date__c: { gte: { literal: LAST_N_DAYS_30 } } }
          ]
        }
        orderBy: { Claim_Date__c: { order: DESC, nulls: LAST } }
        first: $first
        after: $after
      ) {
        edges {
          node {
            Id
            Claim_Number__c { value }
            Claim_Amount__c { value }
          }
          cursor
        }
        pageInfo {
          hasNextPage
          endCursor
        }
      }
    }
  }
}
```

Pagination is **cursor-based**. `endCursor` from one page becomes `after` on the next, with none of `OFFSET`'s 2,000-row ceiling. This is the same keyset approach recommended in [[08.5 - LIMIT, OFFSET, ORDER BY and Pagination]], provided by the API rather than hand-built.

Date literals such as `LAST_N_DAYS_30` mirror SOQL's, evaluated in the user's time zone.

## Several queries in one request

The other main saving:

```graphql
query DashboardData($accountId: ID!) {
  uiapi {
    query {
      openClaims: Warranty_Claim__c(
        where: { and: [{ Account__c: { eq: $accountId } }, { Status__c: { ne: "Closed" } }] }
      ) {
        edges { node { Id Claim_Number__c { value } Claim_Amount__c { value } } }
      }

      assets: Asset(where: { AccountId: { eq: $accountId } }) {
        edges { node { Id Name { value } SerialNumber { value } } }
      }

      contracts: Service_Contract__c(
        where: { and: [{ Account__c: { eq: $accountId } }, { Status__c: { eq: "Active" } }] }
      ) {
        edges { node { Id Name { value } End_Date__c { value } } }
      }
    }
  }
}
```

Three unrelated queries, aliased, in one round trip and one API request. Achieving the same with REST needs three calls or a Composite Batch.

## Mutations

Record changes are supported through the UI API mutation surface:

```graphql
mutation UpdateClaimStatus($claimId: ID!, $status: String!) {
  uiapi {
    Warranty_Claim__cUpdate(input: {
      Id: $claimId
      Warranty_Claim__c: { Status__c: $status }
    }) {
      Record {
        Id
        Status__c { value }
      }
    }
  }
}
```

Mutations are more limited than the query surface. For anything beyond straightforward record updates — bulk operations, upsert on an external ID, composite graphs — REST remains the right tool.

## Calling it from a Lightning component

The most common use, and where it competes with a wire adapter or an Apex controller:

```javascript
import { LightningElement, api, wire } from 'lwc';
import { gql, graphql } from 'lightning/uiGraphQLApi';

export default class ClaimContext extends LightningElement {
    @api recordId;
    claim;
    error;

    @wire(graphql, {
        query: gql`
            query ClaimContext($claimId: ID!) {
                uiapi {
                    query {
                        Warranty_Claim__c(where: { Id: { eq: $claimId } }) {
                            edges {
                                node {
                                    Id
                                    Claim_Number__c { value }
                                    Claim_Amount__c { value displayValue }
                                    Asset__r { Name { value } SerialNumber { value } }
                                }
                            }
                        }
                    }
                }
            }
        `,
        variables: '$queryVariables'
    })
    graphqlResult({ data, errors }) {
        if (data) {
            this.claim = data.uiapi.query.Warranty_Claim__c.edges[0]?.node;
        }
        this.error = errors;
    }

    get queryVariables() {
        return { claimId: this.recordId };
    }
}
```

**Field-level security is enforced automatically**, like every UI API surface. A field the running user cannot see simply does not appear in the response — no Apex, no `stripInaccessible`, no risk of leaking a restricted field. See [[03.6 - Field Level Security]].

That is the strongest argument for GraphQL in a component: **it replaces a custom Apex controller with no security code to get wrong.**

## Where it fits, honestly

GraphQL is newer than the rest of this section and its surface is narrower. The realistic assessment:

**Use GraphQL when:**

- A Lightning component needs related data across objects and would otherwise need an Apex controller
- A mobile or external client wants to control its own field selection
- Several unrelated queries can be collapsed into one request
- Field-level security enforcement without code is worth having

**Use REST when:**

- Writing records in bulk
- Upserting on an external ID
- Anything composite or graph-shaped
- The client tooling is built around REST already

**Use Bulk when:** volume.

**Use Apex when:** the operation is business logic rather than data access.

The GraphQL mutation surface being limited is the main constraint. In practice most orgs use GraphQL for **reads from components** and REST for everything else, which is a reasonable split.

## Limits

- Counts against the **daily API request allocation**, one request per call regardless of how many queries it contains
- Query depth and complexity limits, to prevent expensive nested queries
- Subject to the same **UI API** constraints as other UI API surfaces — some objects and fields are unsupported
- Not available for every standard object

That last point catches people: the UI API does not cover the entire schema, and discovering an object is unsupported partway through a build is a real risk. Checking coverage early is worth the few minutes.

## Errors

Errors arrive in an `errors` array alongside partial data, rather than as an HTTP status:

```json
{
  "data": { "uiapi": { "query": { "Warranty_Claim__c": null } } },
  "errors": [
    {
      "message": "Field Approved_Amount__c is not accessible",
      "path": ["uiapi", "query", "Warranty_Claim__c"],
      "extensions": { "errorType": "INSUFFICIENT_ACCESS" }
    }
  ]
}
```

**A 200 response can contain errors.** A client treating HTTP status as the success signal will silently render incomplete data. Checking the `errors` array is not optional.

Partial success is normal in GraphQL — some fields resolve, others fail on permissions — which is different from REST's all-or-nothing response and needs handling deliberately.

## Practical guidance

**Use it in components** to replace Apex controllers that only fetch data.

**Ask for exactly the fields you need.** That is the point of the API.

**Use `displayValue`** for currency, dates, and picklists rather than formatting client-side.

**Use cursor pagination**, which has no offset ceiling.

**Alias several queries** into one request.

**Always check the `errors` array**, even on a 200.

**Confirm UI API coverage** for your objects before designing around it.

**Keep writes in REST** unless the mutation surface genuinely covers your case.
