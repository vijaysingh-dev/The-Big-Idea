# Debounce and Throttle

Two ways to reduce how often a function runs in response to a high-frequency event. They are not interchangeable, and choosing wrongly produces either a laggy interface or a flood of requests.

**Debounce** — wait until the activity **stops**, then run once.
**Throttle** — run at most once per interval **while** activity continues.

```
events:    ●●●●●    ●●●●●●●●●●●●●        ●
debounce:       ✓              ✓            ✓     (after each pause)
throttle:  ✓   ✓    ✓   ✓   ✓   ✓        ✓        (at a fixed rate)
```

The decision rule: **do you care about the final value, or about intermediate progress?**

## Implementations

```ts
function debounce(fn, delay) {
  let timer;

  const debounced = (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };

  debounced.cancel = () => clearTimeout(timer);
  debounced.flush = (...args) => { clearTimeout(timer); fn(...args); };

  return debounced;
}
```

```ts
function throttle(fn, interval) {
  let last = 0;
  let timer;

  return (...args) => {
    const now = Date.now();
    const remaining = interval - (now - last);

    if (remaining <= 0) {
      last = now;
      fn(...args);
    } else if (!timer) {
      // trailing edge — ensures the final event is not dropped
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn(...args);
      }, remaining);
    }
  };
}
```

Both are closures over a timer handle ([[02.4 - Closure Patterns in Production]]).

Two details that matter in production:

**`cancel` is not optional.** Without it a pending invocation fires after the component unmounts, against stale state ([[07.2 - Memory Leaks from Closures and Timers]]).

**The trailing edge in throttle.** A naive implementation that only checks elapsed time drops the last event — so a scroll handler never sees the final position, and the UI settles in the wrong state.

## Leading and trailing edges

```ts
debounce(fn, 300, { leading: true, trailing: false });
```

**Trailing** (default) — fires after the pause. Right for search, autosave, validation.

**Leading** — fires immediately, then suppresses. Right for actions that must feel instant: a submit button guard, opening a menu.

**Both** — fires immediately and again after the pause. Rarely what you want, and easy to double-fire.

Lodash's implementation also supports `maxWait`, which forces execution after a maximum delay regardless of continued activity — useful for autosave, where continuous typing should not defer the save indefinitely.

## Choosing

| Use case | Choice | Interval |
| --- | --- | --- |
| Search-as-you-type request | debounce trailing | 250–400ms |
| Autosave | debounce trailing + maxWait | 1–2s + 10s max |
| Form validation on input | debounce trailing | 300ms |
| Window resize recalculation | debounce trailing | 150–250ms |
| Scroll position tracking | throttle | ~100ms or rAF |
| Infinite scroll trigger | `IntersectionObserver` | — |
| Mouse move / drag | rAF | per frame |
| Button double-click guard | debounce leading | 500ms |
| Analytics on interaction | throttle | 1s |
| Typing indicator | throttle | 3s |

The typing indicator is the clearest illustration of the difference: debouncing means the indicator appears only *after* the user stops typing, which is exactly backwards ([[28.16 - Case Study - Chat Application]]).

## In React

The common bug:

```jsx
function Search() {
  const handleChange = debounce((v) => search(v), 300);   // new function every render
  // the timer is recreated each time, so it never debounces
}
```

Each render creates a fresh closure with a fresh timer, so nothing is ever cancelled.

Correct approaches, in order of preference:

**Debounce the value, not the handler:**

```jsx
const [query, setQuery] = useState("");
const debouncedQuery = useDebounce(query, 300);

const { data } = useQuery({
  queryKey: ["search", debouncedQuery],
  queryFn: ({ signal }) => api.search(debouncedQuery, { signal }),
  enabled: debouncedQuery.length >= 2,
});
```

```ts
function useDebounce<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);

  return debounced;
}
```

The input updates instantly — **never debounce the input's own value**, or typing feels laggy ([[21.1 - Controlled Forms in Practice]]). Only the derived work is delayed.

**Stabilize the debounced function** when you genuinely need one:

```jsx
const debouncedSave = useMemo(() => debounce(save, 1000), [save]);

useEffect(() => () => debouncedSave.cancel(), [debouncedSave]);
```

The cleanup is required, or a pending save fires after unmount.

## requestAnimationFrame for visual updates

For anything that changes what is on screen, rAF beats a timer:

```ts
function rafThrottle(fn) {
  let queued = false;

  return (...args) => {
    if (queued) return;
    queued = true;
    requestAnimationFrame(() => {
      queued = false;
      fn(...args);
    });
  };
}

window.addEventListener("scroll", rafThrottle(updateHeader), { passive: true });
```

It runs at most once per frame, synchronized with the browser's paint cycle, and pauses automatically in background tabs ([[01.7 - The Rendering Cycle]]).

A `setTimeout`-based throttle at 16ms drifts against the refresh rate and keeps firing when hidden.

`{ passive: true }` on scroll and touch listeners lets the browser scroll without waiting for the handler ([[12.3 - The Event Model]]).

## What replaces them

Several classic debounce/throttle uses now have better native answers:

| Old approach | Better |
| --- | --- |
| Throttled scroll for visibility | `IntersectionObserver` ([[12.5 - Custom Events and Observer APIs]]) |
| Debounced resize for element size | `ResizeObserver` |
| Throttled scroll for sticky headers | `position: sticky` |
| Debounced scroll for scroll-linked animation | `animation-timeline: scroll()` |
| Throttled render on typing | `useDeferredValue` ([[22.5 - useDeferredValue]]) |

Observers are cheaper, more accurate, and require no interval tuning. Reaching for a scroll handler in 2026 usually means an observer was the right tool.

## Debounce is not deferral

```jsx
// Debounce — always waits the full delay, regardless of machine speed
const debounced = useDebounce(query, 300);

// Defer — updates as soon as React can, adaptively
const deferred = useDeferredValue(query);
```

`useDeferredValue` is adaptive and interruptible, so on a fast machine with a small dataset it updates in the same frame. A debounce always waits.

**Debounce network requests; defer expensive renders.** They solve different problems and are often used together — debounce the fetch, defer the rendering of results.

## Cancellation belongs with debouncing

Debouncing reduces how many requests are sent. It does nothing about a slow earlier response arriving after a fast later one:

```
"re"  → request A (debounce fired)
"rea" → request B
A resolves after B → stale results displayed
```

Cancellation is the fix, and a query library gives it automatically by aborting when the key changes ([[04.6 - AbortController and Cancellation]]).

Debounce, cancel and cache are three mechanisms solving three different problems; a search implementation needs all three ([[28.15 - Case Study - Autocomplete]]).

## Testing

```ts
vi.useFakeTimers();

const fn = vi.fn();
const debounced = debounce(fn, 300);

debounced();
debounced();
expect(fn).not.toHaveBeenCalled();

vi.advanceTimersByTime(300);
expect(fn).toHaveBeenCalledTimes(1);
```

Fake timers make this deterministic. With React Testing Library, `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })` is required or interactions hang ([[26.2 - Unit Testing with Vitest and Jest]]).

## How senior engineers actually use this

**They debounce the value, not the handler**, which sidesteps the identity problem entirely.

**They never debounce a controlled input's own value.**

**They use rAF for anything visual** and observers instead of scroll handlers.

**They always cancel on unmount.**

**They pair debouncing with cancellation**, since debouncing alone does not fix response races.

## Common pitfalls

- A debounced function created inside a component body, recreated every render.
- No cancellation on unmount, firing against a dead component.
- Throttle without a trailing edge, dropping the final event.
- Debouncing the input value, making typing feel laggy.
- Debounce where throttle was needed — a typing indicator that appears after typing stops.
- `setTimeout` throttling for visual updates instead of rAF.
- Non-passive scroll listeners blocking scrolling.
- Assuming debouncing prevents out-of-order responses.

## Interview angle

"Difference between debounce and throttle" is a guaranteed question. Give the definitions with a concrete example on each side — search on debounce, scroll tracking on throttle — and be ready to implement both, including the trailing edge and a `cancel` method, which is what distinguishes a production implementation. In React, the point worth volunteering is debouncing the value rather than the handler, and that debouncing does not solve the stale-response race — cancellation does.
