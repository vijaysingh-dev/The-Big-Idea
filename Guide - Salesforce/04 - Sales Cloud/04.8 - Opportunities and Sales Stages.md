# Opportunities and Sales Stages

## The most important object in Sales Cloud

Opportunity is where revenue lives. Forecasting, commission, pipeline reporting, board reporting, and most executive dashboards all read from it.

That has a consequence developers should internalize early: **changes to Opportunity are never local.** A new required field affects every rep's daily workflow. A change to the stage list invalidates historical reporting. A validation rule that fires unexpectedly stops the sales team from working, and you will hear about it within minutes.

Treat Opportunity's schema the way a backend engineer treats a public API contract.

## The key fields

`AccountId`, `Name`, `Amount`, `CloseDate`, `StageName`, `Probability`, `ForecastCategoryName`, `Type`, `LeadSource`, `NextStep`, `OwnerId`, `Pricebook2Id`.

And the platform-derived ones:

`IsClosed`, `IsWon` — **read-only**, set from the stage's configuration. You cannot write to them.

`ExpectedRevenue` — `Amount` multiplied by `Probability`, calculated by the platform.

`HasOpportunityLineItem` — whether products have been added.

`FiscalQuarter`, `FiscalYear` — derived from `CloseDate` and the org's fiscal year settings.

`Amount` has an important behaviour: **when line items exist, `Amount` becomes read-only and is calculated as the sum of the line items.** Code that sets `Amount` directly on an opportunity with products will fail. This surprises people writing integrations.

```java
// Fails if the opportunity has line items
opp.Amount = 50000;
update opp;

// Correct when products are in use: change the line items
OpportunityLineItem line = new OpportunityLineItem(
    OpportunityId = opp.Id,
    PricebookEntryId = entryId,
    Quantity = 2,
    UnitPrice = 25000
);
insert line;
```

## Stages and the Sales Process

Stages come from a **Sales Process**, which is metadata tied to a Record Type. Each stage carries three configuration values:

**Type** — Open, Closed/Won, or Closed/Lost. This drives `IsClosed` and `IsWon`.

**Probability** — the default likelihood, used for `ExpectedRevenue` and weighted pipeline. It defaults onto the record and can be overridden per opportunity, which is a frequent source of "the weighted pipeline does not match the stage probabilities".

**Forecast Category** — Pipeline, Best Case, Commit, Closed, or Omitted. Drives forecasting. Also defaults from the stage and is overridable.

Changing `StageName` sets all three defaults, which means an update that changes the stage silently changes probability and forecast category unless they were explicitly overridden.

## Designing a stage model

This is the highest-impact design decision in Sales Cloud, and changing it later is expensive: historical reports become incomparable, dashboards break, forecast history is muddled, and existing records need migrating.

Principles that hold up:

**Stages describe the buyer's state, not the seller's activity.** "Proposal Sent" is what you did. "Proposal Under Evaluation" is where the deal is. The second tells you what is blocking; the first tells you what happened.

**Every stage needs a documented exit criterion.** If nobody can say what must be true to advance, reps guess, and the pipeline report becomes noise. The classic formulation: what evidence from the *customer* proves this stage is complete?

**Six to eight stages.** Fewer gives no signal, more and reps skip stages — which is worse than having fewer, because the data lies rather than being coarse.

**Do not encode internal process as stages.** "Awaiting Legal Review" is a status field or an approval, not a pipeline stage. Mixing them destroys conversion-rate analysis, because you cannot tell whether a deal stalled with the customer or with your own legal team.

**Closed Lost needs a reason.** Without a mandatory reason picklist, the single most useful dataset in the CRM — why deals are lost — does not exist.

## Enforcing stage progression

The standard requirement: certain fields must be populated before a deal advances.

A validation rule per stage, which is the declarative approach:

```
AND(
  ISPICKVAL(StageName, "Commercial Proposal"),
  OR(
    ISBLANK(Amount),
    ISBLANK(Decision_Maker__c),
    Primary_Contact_Role_Count__c = 0
  )
)
```

This gets unwieldy past three or four stages. The alternative is a Custom Metadata-driven check in Apex, which keeps the requirements configurable:

```java
public with sharing class OpportunityStageValidator {

    public static void validateStageRequirements(List<Opportunity> opps, Map<Id, Opportunity> oldOpps) {
        Map<String, List<Stage_Requirement__mdt>> requirementsByStage = groupRequirements();

        for (Opportunity opp : opps) {
            Opportunity prior = oldOpps == null ? null : oldOpps.get(opp.Id);
            if (prior != null && prior.StageName == opp.StageName) {
                continue;
            }

            List<Stage_Requirement__mdt> required = requirementsByStage.get(opp.StageName);
            if (required == null) {
                continue;
            }

            for (Stage_Requirement__mdt req : required) {
                Object value = opp.get(req.Field_API_Name__c);
                if (value == null || String.valueOf(value).trim() == '') {
                    opp.addError(req.Field_API_Name__c, req.Error_Message__c);
                }
            }
        }
    }

    private static Map<String, List<Stage_Requirement__mdt>> groupRequirements() {
        Map<String, List<Stage_Requirement__mdt>> result = new Map<String, List<Stage_Requirement__mdt>>();
        for (Stage_Requirement__mdt req : Stage_Requirement__mdt.getAll().values()) {
            if (!result.containsKey(req.Stage_Name__c)) {
                result.put(req.Stage_Name__c, new List<Stage_Requirement__mdt>());
            }
            result.get(req.Stage_Name__c).add(req);
        }
        return result;
    }
}
```

`addError()` on a specific field puts the message next to that field in the UI rather than at the top of the page, which is a meaningfully better experience. `getAll()` on Custom Metadata consumes no SOQL query. See [[17.1 - Custom Metadata Types]].

The tradeoff: validation rules are visible to admins in Setup, whereas Apex validation is invisible to them. Teams that choose the Apex approach should document it prominently, because "why can I not save this opportunity" with no visible validation rule is a frustrating investigation.

## Tracking stage history

`OpportunityHistory` is a standard object recording stage, amount, probability, and close date at each change. Useful, and limited in what it can report on, which is why many orgs maintain their own history object.

The metric it enables is **stage duration**, which is what tells you where deals actually stall:

```sql
SELECT StageName, AVG(Duration_Days__c) avgDays, COUNT(Id) transitions
FROM Opportunity_Stage_History__c
WHERE Entered_On__c = LAST_N_MONTHS:12
GROUP BY StageName
```

A deal spending an average of forty days in "Technical Proposal" and eight days in "Negotiation" tells the business something actionable about where to invest.

## Close date discipline

`CloseDate` is required and drives the forecast period. It is also the field most casually maintained.

Two common problems and their fixes:

**Close dates in the past on open opportunities.** A report or scheduled job flagging these is essential; without it the pipeline includes deals that were supposed to close six months ago.

**Close dates pushed repeatedly.** A field counting how many times the close date has moved, maintained by a trigger, surfaces the deals that are not real.

```java
for (Opportunity opp : newOpps) {
    Opportunity prior = oldOpps.get(opp.Id);
    if (opp.CloseDate != prior.CloseDate && !opp.IsClosed) {
        opp.Close_Date_Push_Count__c = (opp.Close_Date_Push_Count__c == null ? 0 : opp.Close_Date_Push_Count__c) + 1;
        opp.Original_Close_Date__c = opp.Original_Close_Date__c == null ? prior.CloseDate : opp.Original_Close_Date__c;
    }
}
```

Slippage is one of the strongest predictors of a deal that will not close, and this field costs almost nothing to maintain.

## Renewals

For subscription or contract businesses, closing an opportunity as won should create the renewal opportunity for the following period.

```java
public with sharing class RenewalOpportunityService {

    public static void createRenewals(List<Opportunity> newlyWon) {
        List<Opportunity> renewals = new List<Opportunity>();

        for (Opportunity opp : newlyWon) {
            if (opp.Type != 'New Business' && opp.Type != 'Renewal') {
                continue;
            }
            renewals.add(new Opportunity(
                AccountId = opp.AccountId,
                Name = opp.Account.Name + ' - Renewal ' + opp.CloseDate.addYears(1).year(),
                StageName = 'Qualification',
                CloseDate = opp.CloseDate.addYears(1),
                Amount = opp.Amount,
                Type = 'Renewal',
                OwnerId = opp.OwnerId,
                Original_Opportunity__c = opp.Id
            ));
        }

        if (!renewals.isEmpty()) {
            insert renewals;
        }
    }
}
```

Called from an after-update handler when the stage changes to a won stage. The `Original_Opportunity__c` link is what makes renewal-rate reporting possible.

## Practical guidance

**Get the stage model right before go-live.** Involve sales leadership, document exit criteria, and resist adding stages for internal process.

**Make Closed Lost Reason mandatory.** It is the most valuable field on the object and the easiest to forget.

**Do not set `Amount` when line items exist.** Integration code needs to know this.

**Track close date slippage.** Cheap to build, high signal.

**Be careful with automation volume on Opportunity.** It attracts more triggers, flows, and validation rules than any other object, and the cumulative CPU cost is a common source of `Apex CPU time limit exceeded` during bulk updates. Audit what fires on save periodically. See [[07.13 - Order of Execution]].
