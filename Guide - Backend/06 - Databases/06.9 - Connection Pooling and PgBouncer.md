# Connection Pooling and PgBouncer

#backend #databases #postgres #operations

> **In one line:** Every Postgres connection is an operating system process, so a few hundred is a lot — PgBouncer multiplexes thousands of application connections onto a few dozen real ones, and the mode you choose determines which SQL features stop working.

---

## The Idea

Each backend costs:

| Resource | Cost |
|---|---|
| Memory | ~5–10 MB baseline, more with `work_mem` allocations |
| Fork time | ~1–5 ms |
| Context switching | Every backend competes for CPU |
| Shared memory | A slot in the lock table, proc array, and snapshot machinery |

⚠️ **`max_connections` is not a soft limit.** Several shared structures are sized from it at startup, so raising it increases fixed overhead for every backend.

💡 **The arithmetic that catches people:** 10 pods × 4 workers × pool of 20 = 800 connections against a `max_connections` of 100. **This is the most common Postgres production incident in Python backends and it is pure multiplication** ([[01.10 - Connection Pools and Limits]]).

---

## Why Fewer Connections Are Faster

```
Throughput vs pool size on an 8-core database:
  pool=10   ██████████████ 14,000 tps    ← peak
  pool=100  ████████ 8,000 tps
  pool=500  ███ 3,000 tps
```

| Cause | Effect |
|---|---|
| CPU context switching | 500 processes on 8 cores thrash |
| Lock contention | More concurrent transactions competing for the same rows |
| Buffer pool contention | More processes fighting over shared buffers |
| Memory pressure | `work_mem` × more concurrent operations |

💡 **The rule of thumb from HikariCP's research: `connections ≈ (cores × 2) + effective_spindle_count`.** For an 8-core SSD database that is roughly 20 active connections **total** — not per service.

**Queueing in PgBouncer is better than queueing inside Postgres**, because PgBouncer queues cheaply while Postgres queueing means contention across every shared structure.

---

## Pooling Modes

### Session mode

A server connection is held from client connect to disconnect. **Compatible with everything, almost no multiplexing gain.**

### Transaction mode

```ini
pool_mode = transaction
```

Assigned at `BEGIN`, released at `COMMIT`. **Between transactions, the client has no server connection at all.**

💡 **This is the mode you want**, and essentially every large Postgres deployment uses it — 1,000 clients on 25 servers is normal.

⚠️ **What breaks in transaction mode:**

| Feature | Why |
|---|---|
| `SET` outside a transaction | Applies to whichever server connection you got |
| **Prepared statements** | Prepared on one server connection, executed on another |
| `LISTEN` / `NOTIFY` | Needs a persistent connection |
| Session-level advisory locks | Same |
| Temporary tables | Same |

**The prepared statement problem is the one that actually bites**, because most drivers use them by default.

---

## The Prepared Statement Problem

```
ERROR:  prepared statement "__asyncpg_stmt_1__" does not exist
```

The statement was prepared on server connection 7 and the next execution landed on connection 12.

```python
pool = await asyncpg.create_pool(dsn, statement_cache_size=0,
                                 max_cached_statement_lifetime=0)
conn = psycopg.connect(dsn, prepare_threshold=None)                    # psycopg 3
create_async_engine(dsn, connect_args={"statement_cache_size": 0})     # SQLAlchemy
```

💡 **PgBouncer 1.21+ supports protocol-level prepared statements in transaction mode:**

```ini
max_prepared_statements = 200
```

**PgBouncer tracks named prepared statements and re-prepares them on whichever server connection it hands you.** This removes the biggest objection to transaction mode, and **if you are running an older PgBouncer, upgrading for this alone is worth it.**

⚠️ Even so, you lose *plan* reuse across connections in some cases, and generic-plan behaviour becomes less predictable ([[06.5 - The Query Planner]]).

### The LISTEN/NOTIFY problem

**`LISTEN` does not work in transaction mode at all.** You need a **separate direct connection** bypassing PgBouncer.

⚠️ **Each listener holds a real backend permanently.** With many pods, this consumes your `max_connections` budget invisibly. **This is one reason Redis pub/sub is often preferred for realtime backplanes** ([[04.6 - Scaling Long Lived Connections]]).

## Configuring PgBouncer

```ini
[databases]
conduit = host=postgres port=5432 dbname=conduit

[pgbouncer]
auth_type = scram-sha-256
pool_mode = transaction

max_client_conn = 2000          # how many app connections PgBouncer accepts
default_pool_size = 25          # REAL Postgres connections
reserve_pool_size = 5
server_idle_timeout = 600
server_lifetime = 3600
query_wait_timeout = 120        # ← important
max_prepared_statements = 200   # PgBouncer 1.21+
ignore_startup_parameters = extra_float_digits
```

| Setting | Meaning |
|---|---|
| `max_client_conn` | Total application connections. Can be large — ~2KB each |
| **`default_pool_size`** | **Real Postgres connections. Keep small — 20–30** |
| `query_wait_timeout` | How long a client waits before erroring |

⚠️ **`query_wait_timeout` defaults to 120 seconds.** If the pool is exhausted, queries hang for two minutes instead of failing fast.

💡 **Set it to something your application's timeout budget can absorb — 5–10 seconds — so exhaustion produces a fast error you can retry rather than a hang that consumes a worker** ([[03.11 - Timeouts and Deadlines Across Hops]]).

### The pool sizing arithmetic

```
Postgres max_connections               100
  − superuser reserved                  -3
  − monitoring/admin                    -7
  − direct LISTEN connections          -10
  = available to PgBouncer              80
  ÷ number of databases × users          2
  = default_pool_size                   40
```

💡 **The mental shift: application pool sizes no longer need to be small.** With PgBouncer, each service can hold a generous local pool because those connections cost almost nothing. **The scarce resource is `default_pool_size`, managed in one place.**

## Monitoring

```
psql -p 6432 -U pgbouncer pgbouncer
SHOW POOLS;  SHOW STATS;  SHOW CLIENTS;  SHOW SERVERS;
```

```
 database | user | cl_active | cl_waiting | sv_active | sv_idle | maxwait
 conduit  | app  |        24 |          0 |        18 |       7 |       0
```

| Column | Meaning |
|---|---|
| **`cl_waiting`** | **Clients queued for a server connection — should be 0** |
| **`maxwait`** | **Longest current wait in seconds — should be 0** |

💡 **`maxwait` is the single metric that tells you whether your pool is big enough.** Non-zero and sustained means clients are queueing; zero with `sv_idle` consistently high means the pool is larger than needed.

**Alert on `maxwait > 1` and on `cl_waiting > 0` sustained.**

## In Production

### The deployment shape

| Placement | Trade |
|---|---|
| **Sidecar** (one per pod) | No extra hop, no SPOF, but **each has its own pool — the totals multiply again** |
| **Shared deployment** | True global pooling, one place to tune, adds a hop and needs its own HA |

⚠️ **The sidecar approach partially defeats the purpose.** 20 pods each with `default_pool_size = 25` is back to 500 Postgres connections. **Sidecars reduce connection *churn*, not total count.**

💡 **For genuine consolidation you need a shared PgBouncer layer**, usually 2–3 instances behind a load balancer. Managed offerings (RDS Proxy, Cloud SQL connectors) do this for you.

### PgBouncer is single-threaded

```ini
so_reuseport = 1     # run multiple processes on one port
```

⚠️ **A saturated PgBouncer looks exactly like a slow database** — high latency, queries waiting — **and the CPU graph you need to look at is PgBouncer's, not Postgres's.**

Alternatives if you outgrow it: **pgcat** (Rust, multithreaded, adds load balancing and sharding) or **Odyssey**.

### Read replica routing

PgBouncer does not route reads and writes. Use separate pools and choose in the application.

⚠️ **Routing reads to a replica introduces replication lag into your correctness model.** A user who writes then immediately reads may not see their own write ([[06.12 - Replication and Failover]]). **Route deliberately, not by default.**

### The complete diagnostic

When "the database is slow", check in this order:

```
1. PgBouncer:  SHOW POOLS → maxwait, cl_waiting
               → non-zero means pool exhaustion, not a slow database
2. PgBouncer:  CPU usage → saturated single thread
3. Postgres:   pg_stat_activity → wait_event_type
4. Application: pool acquire wait time metric
```

💡 **There are now three queues between your code and the database** — your application pool, PgBouncer, and Postgres. **Instrument all three, or you will spend an hour investigating the wrong one.**

## Codebase

**Repo:** `pgbouncer/pgbouncer`, `postgresml/pgcat`

**Question to answer:** In transaction mode, exactly when is a server connection assigned and released, and what state must PgBouncer reset between clients? Then: how does PgBouncer 1.21+ make prepared statements work across pooled connections?

**Read, in order:**

1. `pgbouncer/src/objects.c` — client, server and pool structures. **Small and clear — this is the whole data model**
2. `pgbouncer/src/client.c` and `src/server.c` — the protocol state machines. **`release_server` is the answer to the first question**
3. `pgbouncer/src/proto.c` — wire protocol handling. **Note what must be reset between clients**: `DISCARD ALL`, or the configured `server_reset_query`
4. `pgbouncer/src/prepare.c` — **the prepared statement tracking added in 1.21**
5. `pgbouncer/src/janitor.c` — periodic cleanup, idle timeouts, lifetime recycling
6. `postgresml/pgcat` — a modern multithreaded alternative. Read the sharding and load balancing modules to see what PgBouncer deliberately does not do

💡 PgBouncer is small enough to read in full — a few thousand lines of C — and **it teaches you the Postgres wire protocol as a side effect.** Understanding what a "server reset" must clear (settings, prepared statements, temp tables, listens, locks) **is exactly the list of what breaks in transaction mode, derived from first principles.**

**Size:** 1–2 sessions.

**Drill 6.9 — Multiplex 1,000 connections onto 20**

```
drills/06-pooling/

├── listen/{broken.py, direct.py}
├── monitoring/{scrape.py, three_queues.py}
└── README.md
```

**Part 1 — Find the real optimum, twice.** Sweep application pool size from 1 to 500 against Postgres directly. Chart throughput and p99. **Find the peak and the decline.**

Then repeat through PgBouncer with `default_pool_size` fixed at 25. **The second chart should stay flat well past where the first collapsed.**

**That contrast is the entire argument for pooling, and having your own version of it is worth more than the HikariCP graph.**

**Part 2 — Break transaction mode deliberately.** Attempt: a `SET` outside a transaction, a prepared statement, `LISTEN`, a session advisory lock, a temp table, and a held cursor.

**Record the exact error for each.** Then confirm each works in session mode.

**This table is the reference you will want when someone asks "can we use PgBouncer".**

**Part 3 — The prepared statement fix, three ways.** Reproduce the error with asyncpg.

Fix it three ways: disable the statement cache, PgBouncer 1.21+ with `max_prepared_statements`, and session mode.

**Measure the throughput cost of each.** Disabling the cache means re-parsing every query — quantify it. Session mode means losing multiplexing — quantify that too.

**Part 4 — Pool exhaustion, two failure shapes.** `default_pool_size = 5`, then 50 concurrent slow queries.

With `query_wait_timeout = 120`: measure how long clients hang and what happens to your application's worker pool. With `= 5`: measure the error rate and recovery speed.

**Chart both. This is the fast-failure-versus-slow-failure argument at the database layer** ([[11.4 - Backpressure and Load Shedding]]).

**Part 5 — `LISTEN` through a pooler.** Attempt it in transaction mode. **Confirm it silently fails to receive notifications.**

Then the separate-direct-connection pattern. Then measure: with 20 pods each holding one direct listener, what fraction of `max_connections` is consumed? **Compute at what pod count this becomes a problem, and state whether you would use `LISTEN/NOTIFY` for Conduit.**

**Part 6 — PgBouncer as the bottleneck.** Drive throughput until PgBouncer's CPU saturates.

**Confirm the symptom looks like a slow database** — high query latency, `maxwait` climbing — while Postgres CPU is low.

Then run multiple processes with `so_reuseport` and measure the improvement.

**Part 7 — Instrument three queues.** Metrics for your application pool's acquire wait, PgBouncer's `maxwait` and `cl_waiting`, and Postgres's lock wait events.

Create three incidents — application pool too small, PgBouncer pool too small, and a slow query holding connections — and **confirm your dashboard identifies which layer is at fault in each.**

**This dashboard goes into Conduit.**

**Done when:**
- Your two pool-size charts show the difference pooling makes
- The transaction-mode failure table covers all six features with exact errors
- You have quantified the cost of each prepared-statement workaround
- Both pool-exhaustion failure shapes are charted
- You know the pod count at which `LISTEN` becomes untenable
- You have saturated PgBouncer and recognised the misleading symptom
- Your three-queue dashboard correctly attributes three different incidents
