# Types vs Interfaces

Both declare the shape of an object, and for most everyday use they are interchangeable. The differences that matter are narrow but real.

```ts
interface User {
  id: string;
  name: string;
}

type User = {
  id: string;
  name: string;
};
```

## What only type aliases can do

**Unions** — the single most important capability:

```ts
type Status = "idle" | "loading" | "error";
type Result = Success | Failure;
type Id = string | number;
```

Discriminated unions are the backbone of modelling state correctly, and interfaces cannot express them ([[25.6 - Discriminated Unions and Narrowing]]).

**Primitives, tuples and functions:**

```ts
type Coordinate = [number, number];
type Handler = (event: MouseEvent) => void;
type Millis = number;
```

**Mapped and conditional types:**

```ts
type Optional<T> = { [K in keyof T]?: T[K] };
type Unwrap<T> = T extends Promise<infer U> ? U : T;
type Keys = keyof User;
```

Anything computed from another type requires a type alias.

## What only interfaces can do

**Declaration merging** — two declarations with the same name combine:

```ts
interface Window {
  myGlobal: string;
}
// merges with the built-in Window
```

This is how you extend library and global types. `Window`, `ProcessEnv`, and framework interfaces like Express's `Request` are all extended this way:

```ts
declare module "express" {
  interface Request {
    user?: AuthUser;
  }
}
```

A type alias would produce a duplicate identifier error.

This capability is why **library authors should prefer interfaces** for public types — consumers can augment them. It is also why it is a hazard in application code: an accidental duplicate `interface User` merges silently instead of erroring.

## Extension syntax

```ts
interface Admin extends User {
  permissions: string[];
}

type Admin = User & { permissions: string[] };
```

Both work. One behavioral difference: `extends` **checks compatibility** and errors on a conflicting property, while `&` produces an intersection that may be `never`:

```ts
interface A { x: string }
interface B extends A { x: number }   // Error: incompatibly overrides

type C = { x: string } & { x: number };   // no error — C["x"] is never
```

The interface version fails at the declaration; the type version fails later, at a confusing use site. That makes `extends` slightly better for catching mistakes early.

Interfaces can also extend type aliases, and a type can intersect an interface — they interoperate freely.

## Performance

For very large unions and deeply nested intersections, interfaces compile faster because the checker caches them by name and defers resolution. Type aliases with complex intersections are re-evaluated more often.

This only matters in large codebases with slow builds. If `tsc --diagnostics` shows high check time, converting hot intersection chains to interface extension is one of the documented remedies.

## Error messages

```ts
interface User { id: string }
type UserType = { id: string };
```

Interfaces keep their name in error messages and editor hovers:

```
Type 'X' is not assignable to type 'User'
```

Type aliases are often expanded to their structure, which is noisier for complex shapes. This is a small but real ergonomic difference on large object types.

## The practical rule

```
Object shapes, especially public API surfaces   → interface
Unions, tuples, functions, computed types       → type
Everything else                                 → either; be consistent
```

The TypeScript team's own guidance is to use `interface` until you need a feature only `type` provides.

In React codebases the convention is often `type` throughout, because props frequently involve unions and intersections with `ComponentProps`:

```ts
type ButtonProps = {
  variant?: "primary" | "ghost";
} & React.ComponentPropsWithoutRef<"button">;
```

That is a reasonable convention. What matters more than the choice is applying it consistently.

## Structural typing

Neither creates a nominal type. TypeScript compares **shape**, not name:

```ts
interface User { id: string }
interface Product { id: string }

const u: User = { id: "1" };
const p: Product = u;      // allowed — identical shapes
```

For domain types that must not be interchangeable, use a branded type:

```ts
type UserId = string & { readonly __brand: "UserId" };
type ProductId = string & { readonly __brand: "ProductId" };

const toUserId = (s: string) => s as UserId;

function getUser(id: UserId) {}
getUser(productId);        // Error
```

The brand exists only at compile time — the runtime value is a plain string. This is genuinely useful when an application has many id types that are all strings, which is where mixing them up is easy and the consequences are silent.

## readonly and optionality

```ts
interface Config {
  readonly apiUrl: string;
  timeout?: number;               // number | undefined
  retries: number | undefined;    // required, but may be undefined
}
```

`?` and `| undefined` are not the same: an optional property may be omitted; a required one typed `| undefined` must be present, even if the value is `undefined`. Under `exactOptionalPropertyTypes`, the distinction tightens further.

`readonly` is shallow and compile-time only — it does not freeze anything at runtime ([[03.1 - Objects and Property Descriptors]]).

For deeply immutable data:

```ts
const config = { api: { url: "/v1" } } as const;   // deeply readonly literal types
```

## Index signatures

```ts
interface Dictionary {
  [key: string]: string;
}

type Dictionary = Record<string, string>;
```

`Record` is more readable and composes better with utility types ([[25.3 - Utility Types]]).

Note that an index signature makes every access typed as present, which is a lie:

```ts
const d: Record<string, string> = {};
d.missing.toUpperCase();     // compiles, throws at runtime
```

`noUncheckedIndexedAccess` fixes this by adding `| undefined` to indexed reads. It is worth enabling — it catches a genuine class of bug — but it is noisy to adopt on an existing codebase.

## How senior engineers actually use this

**They pick one convention and enforce it with lint**, because the debate consumes more time than the difference is worth.

**They use interfaces for anything published** from a shared package, so consumers can augment.

**They reach for `type` the moment a union is involved**, which in React props is often.

**They use branded types for ids** in applications with many string-typed identifiers.

**They enable `noUncheckedIndexedAccess`** on new projects.

## Common pitfalls

- Accidental interface merging from a duplicate name, producing a silently wrong type.
- Intersecting conflicting properties and getting `never` instead of an error.
- Assuming `readonly` prevents runtime mutation.
- Confusing `?` with `| undefined`.
- Index signatures hiding missing-key bugs.
- Assuming two identically-shaped types are distinguishable — structural typing means they are not.

## Interview angle

"Difference between type and interface" is asked constantly, and the weak answer is a feature list. The strong one names what is exclusive to each — unions, tuples, mapped and conditional types only in `type`; declaration merging only in `interface` — and then the practical consequence: interfaces are right for public API surfaces because consumers can augment them, and `extends` catches conflicting properties at the declaration where `&` produces `never` at a distant use site. Mentioning structural typing and branded types adds depth.
