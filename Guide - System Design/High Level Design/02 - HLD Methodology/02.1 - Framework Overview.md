# HLD Methodology: The Repeatable Framework

> **Revision tags:** #methodology #hld-process  
> **Related:** [[02.2 - Requirements Clarification]] | [[02.3 - Estimation and Capacity]] | [[02.4 - Architecture Decisions]]

---

## Why You Need a Framework

Without a framework, HLD interviews and real design sessions go off the rails:
- You jump to solutions before understanding the problem
- You miss non-functional requirements entirely
- You design the happy path and forget failures
- You run out of time before covering critical components

A framework is a checklist you internalize — it keeps you structured under pressure.

---

## The 10-Step HLD Framework

```
1. Clarify Requirements
2. Define Scope and Constraints
3. Estimate Scale
4. Identify Bottlenecks
5. Choose Architecture Style
6. Design Data Flow and APIs
7. Choose Databases and Storage
8. Design Caching Strategy
9. Design for Failure
10. Design Observability and Security
```

Each step feeds the next. Don't skip — skipping step 1 means every subsequent decision may be solving the wrong problem.

---

## Step 1: Clarify Requirements (5 min in interviews)

Ask targeted questions to understand what you're actually building.

**Functional questions:**
- What are the core use cases? (not "what features" — "what does a user actually do?")
- What's in scope vs explicitly out of scope?
- Are there write-heavy or read-heavy patterns?

**Non-functional questions:**
- What availability SLA is expected? (99.9%? 99.99%?)
- What's the acceptable latency? (p99 < 200ms?)
- Is consistency critical or is eventual OK?
- Is this global (multi-region) or single-region?

> See [[02.2 - Requirements Clarification]] for full question bank.

---

## Step 2: Define Scope and Constraints

After clarification, write down explicit boundaries:

```
In scope:   POST /shorten, GET /{code} redirect, link expiry
Out of scope: Analytics, custom domains, link editing
Constraints: Read:write = 100:1, no custom auth (use existing SSO)
Assumptions: 99.9% availability, links expire after 1 year
```

Writing this down prevents scope creep and gives you something to refer back to.

---

## Step 3: Estimate Scale (5 min)

Back-of-envelope math to understand what you're designing for.

**Traffic:**
- DAU × actions/day ÷ 86,400 = QPS
- Peak = avg × 2-3x

**Storage:**
- records/day × record_size × retention_days

**Bandwidth:**
- requests/s × avg_response_size

> See [[02.3 - Estimation and Capacity]] for formulas and worked examples.

Estimation defines your architecture tier. 100 RPS → single server. 100,000 RPS → distributed system.

---

## Step 4: Identify Bottlenecks

Before designing, ask: **which component will break first?**

Common bottlenecks by system type:

| System Type | Likely Bottleneck |
|---|---|
| Read-heavy (feeds, catalogs) | Database reads, cache miss rate |
| Write-heavy (logging, metrics) | Database write throughput |
| Compute-heavy (video, ML) | CPU/GPU workers |
| Fan-out (notifications) | Message throughput, delivery rate |
| Real-time (chat, trading) | Connection state, latency |

Identify this early — it determines where you spend design effort.

---

## Step 5: Choose Architecture Style

Based on scale, team size, and requirements, pick your top-level style:

- **Monolith** → MVP, small team, low scale
- **Modular monolith** → medium team, moderate scale, need domain separation
- **Microservices** → large team, high scale, independent scaling needs
- **Event-driven** → async workflows, fan-out, audit trail needed

> See [[01.9 - Architecture Styles]] for tradeoffs.

In interviews, justify your choice in one sentence: "Given this is read-heavy with simple domain boundaries and a small team, I'd start with a modular monolith."

---

## Step 6: Design Data Flow and APIs

Draw the request flow **before** choosing databases or caches.

```
Client
  → Load Balancer
  → API Gateway (auth, rate limit, routing)
  → Service A
      → [synchronous call] Service B
      → [async event]      Queue → Worker
  → Response to Client
```

Then define API contracts:
- What endpoints exist?
- What does each request/response look like?
- What calls are sync vs async?

> See [[02.4 - Architecture Decisions]] for API design thinking.

---

## Step 7: Choose Databases and Storage

For each service, ask:
1. What's the query pattern? (key-value, relational, document, time-series, graph)
2. What's the read:write ratio?
3. What consistency level is needed?
4. What's the scale?

Then pick the right store — not just "use Postgres everywhere."

> See [[03.6 - Databases SQL and NoSQL]] for the decision matrix.

---

## Step 8: Design Caching Strategy

Ask: **what's expensive to compute or fetch, and how stale is acceptable?**

Caching layers to consider:
- CDN (static assets, API responses)
- Application-level cache (in-memory, per-service)
- Distributed cache (Redis — shared across instances)
- DB query cache (read replicas, materialized views)

For each cache: define TTL, invalidation strategy, and what happens on a cache miss.

> See [[03.4 - Caching Systems]] and [[03.5 - Redis Patterns]].

---

## Step 9: Design for Failure

This is where most junior engineers fall short. Go through every component and ask: **what happens when this fails?**

Checklist:
- [ ] What if a service instance crashes? (Health checks, auto-restart, multiple instances)
- [ ] What if the database goes down? (Read replica failover, circuit breaker, stale cache)
- [ ] What if a downstream call hangs? (Timeouts, circuit breakers)
- [ ] What if the queue is down? (Dead letter queue, retry, fallback)
- [ ] What if the datacenter goes down? (Multi-AZ, failover, RPO/RTO targets)

> See [[02.5 - Failure and Resilience]] for the full failure design playbook.

---

## Step 10: Observability and Security

A system you can't see is a system you can't operate.

**Observability:**
- Logs: structured, searchable, with trace IDs
- Metrics: request rate, error rate, latency (the RED method)
- Tracing: distributed trace across services
- Alerts: SLO breaches, anomaly detection

**Security:**
- Authentication: who is the caller?
- Authorization: what are they allowed to do?
- Data in transit: TLS everywhere
- Data at rest: encryption, access control
- Secrets management: no hardcoded credentials

> See [[02.6 - Observability Security Cost]] for full coverage.

---

## Interview Time Allocation (45 min)

```
0–5  min:  Requirements clarification
5–10 min:  Estimation and scope
10–15 min: High-level architecture diagram
15–30 min: Deep dive on 2–3 critical components
30–40 min: Failure handling, scaling, tradeoffs
40–45 min: Questions, alternatives, wrap-up
```

Don't spend 30 minutes on requirements. Don't skip failure handling. Both are common mistakes.
