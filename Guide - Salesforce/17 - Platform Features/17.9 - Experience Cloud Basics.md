# Experience Cloud Basics

## What it is

Externally facing sites — customer portals, partner portals, help centres, public sites — built on the same data and the same components as the internal org.

For Northwind, that means a partner portal where service engineers submit warranty claims, and a public help centre where customers look up documentation.

The developer's concern is almost entirely **security**. The rest is configuration.

## The licence types

The licence determines what a user can do, and it is decided before anything is built.

```
Customer Community            no roles, no sharing rules, sharing sets only
Customer Community Plus       roles, sharing rules, reports
Partner Community             roles, sharing rules, opportunities, leads
External Apps                 for non-CRM external applications
Guest User                    unauthenticated, per site
```

**Customer Community has no role hierarchy**, which means no manager visibility and no sharing rules — access comes from **sharing sets** and **sharing rules on the owner**. Choosing it and then discovering that a customer admin needs to see their colleagues' cases is a common and expensive mistake.

**Customer Community Plus adds roles**, so a partner account gets a small hierarchy. Each external account with Plus users gets an account role hierarchy of one to three levels, which multiplies role count quickly — a real consideration in an org with thousands of partner accounts. See [[03.8 - Role Hierarchy]].

## The guest user

The highest-risk surface on the platform, and the one worth the most attention.

Every site has one **Guest User**, with a profile, running every unauthenticated request. Its permissions apply to everyone on the internet who loads the page.

The rules Salesforce enforces by default:

```
Guest user records are owned by the guest user, and OWD for guest is Private
Guest users cannot have View All or Modify All
Guest user sharing rules can only grant Read
Guest users cannot be used in a role hierarchy
```

What still needs care:

**Object and field permissions.** A guest profile with Read on Account exposes every account the sharing model lets it see.

**Apex classes.** A guest user with access to an `@AuraEnabled` class can call it directly, regardless of what the site renders. The class must enforce its own security.

```java
@AuraEnabled(cacheable=true)
public static List<Knowledge__kav> getPublicArticles(String category) {
    // reachable by anyone on the internet; every constraint must be in the query
    return [
        SELECT Id, Title, Summary
        FROM Knowledge__kav
        WHERE PublishStatus = 'Online'
          AND IsVisibleInPkb = true
          AND Category__c = :category
        WITH USER_MODE
        LIMIT 50
    ];
}
```

**`without sharing` on a guest-reachable class is a data breach waiting to happen.** If a class must run without sharing, it should be narrowly scoped, take no user-supplied filters, and return only what is genuinely public.

**Never trust a record Id from a guest request.** A component passing `recordId` to Apex means anyone can pass any Id. The Apex must verify the record is one this guest is entitled to see, not merely that it exists.

## Sharing sets and share groups

The mechanism replacing the role hierarchy for Customer Community users.

**A sharing set** grants access based on a match between the user's Contact or Account and a field on the record:

```
Sharing Set: Claim Access
  Profile:       Customer Community User
  Object:        Warranty Claim
  Access:        Read/Write
  Criteria:      User.Contact.AccountId = Warranty_Claim__c.Account__c
```

Every community user linked to that account sees that account's claims. No sharing rules, no roles.

**A share group** grants internal users access to records **owned by** high-volume community users, which is otherwise invisible to them:

```
Share Group on the sharing set
  Members: Support Agent role and subordinates
```

Without a share group, a case created by a portal user is owned by that user and invisible to internal support — which is a confusing discovery mid-project.

## Site configuration

```
Setup → Digital Experiences → All Sites → Builder

Templates:  Customer Service, Partner Central, Build Your Own (LWR), Help Center
Pages:      standard record pages, object pages, custom pages
Theme:      branding, fonts, colours
Navigation: menus, per audience
Audiences:  show pages and components conditionally by profile, location, record field
```

**LWR (Lightning Web Runtime)** templates are the current generation — substantially faster than the older Aura-based templates, and the right default for a new site. Some older components and features are not supported on LWR, which is the main reason to choose an Aura template instead.

**Audiences** are the declarative personalization mechanism: a component shown only to partner users, or only to users whose account has a particular tier. Worth using before building conditional logic into a component.

## Components on a site

```xml
<targets>
    <target>lightningCommunity__Page</target>
    <target>lightningCommunity__Default</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightningCommunity__Default">
        <property name="recordId" type="String" label="Record Id" default="{!recordId}"/>
    </targetConfig>
</targetConfigs>
```

**`{!recordId}` binds to the page's record context.** The automatic injection that works on an internal record page does not apply the same way, so this default is required.

Behaviours that differ from the internal org:

**Toasts may not appear.** `ShowToastEvent` is unreliable in Experience Cloud. Inline messages work everywhere. See [[14.16 - Error Handling and Toasts]].

**Navigation differs.** `standard__recordPage` works only where the object has a detail page configured on the site; `comm__namedPage` is the site-specific form. See [[14.14 - Navigation and NavigationMixin]].

**Styling differs.** Site branding overrides the internal theme, so hardcoded colours look wrong. Design tokens adapt. See [[14.15 - Styling, SLDS and Design Tokens]].

**Testing in the builder preview is not enough.** Publish and test on the real site, as a real external user — several of these differences only appear there.

## The self-registration path

```
Setup → site → Administration → Login & Registration
    Allow external users to self-register
    Profile:  Customer Community Login User
    Account:  a specified account, or a registration handler
```

The **registration handler** is Apex, and it is a security boundary:

```java
global with sharing class PortalRegistrationHandler implements Auth.RegistrationHandler {

    global User createUser(Id portalId, Auth.UserData data) {
        // a domain allowlist is the difference between a partner portal and an open one
        if (!isPermittedDomain(data.email)) {
            throw new Auth.RegistrationHandlerException('Registration is not open to this domain.');
        }

        Contact contact = findOrCreateContact(data);

        Profile p = [SELECT Id FROM Profile WHERE Name = 'Partner Community User' LIMIT 1];

        return new User(
            ContactId = contact.Id,
            Username = data.email + '.portal',
            Email = data.email,
            FirstName = data.firstName,
            LastName = data.lastName,
            Alias = data.username.left(8),
            ProfileId = p.Id,
            TimeZoneSidKey = 'Asia/Kolkata',
            LocaleSidKey = 'en_IN',
            EmailEncodingKey = 'UTF-8',
            LanguageLocaleKey = 'en_US'
        );
    }

    global void updateUser(Id userId, Id portalId, Auth.UserData data) {
        update new User(Id = userId, FirstName = data.firstName, LastName = data.lastName);
    }
}
```

**A handler with no domain check creates a user for anyone who registers.** That is occasionally intended for a public community and is a serious exposure for a partner portal. See [[13.12 - Connected Apps and Auth Providers]].

## User creation from Apex

Enabling a Contact as a portal user:

```java
// Setup DML and normal DML cannot share a transaction
System.enqueueJob(new PortalUserProvisioningQueueable(contactIds));
```

`User` is a setup object, so provisioning from a trigger on Contact or Account requires an async path. See [[10.7 - Mixed DML and Setup Objects]].

## Licences and cost

Experience Cloud licences are consumed per login or per member, and the model matters:

```
Login-based      a pool of logins per month, suits infrequent users
Member-based     per named user, suits daily users
```

A partner portal where engineers log in daily needs member-based; a customer portal where people check a case twice a year is far cheaper login-based. Getting this wrong is a budgeting problem rather than a technical one, and it is worth raising early.

## Performance

External users are on worse networks than internal ones, frequently on mobile, and often outside the org's region.

**Component count matters more.** Every component is a server call.

**Cacheable Apex matters more**, since round trips are slower.

**LWR templates are substantially faster** than Aura-based ones.

**Guest pages can be cached** at the CDN level, which for a public help centre is the single largest improvement available.

The profiling approach is the same, with the caveat that testing from the office network understates the problem. See [[14.17 - Performance and Rendering]].

## A security checklist

```
[ ] Guest profile object permissions reviewed field by field
[ ] Guest-reachable Apex declares `with sharing`
[ ] Guest-reachable Apex uses WITH USER_MODE
[ ] Record Ids from the client are verified, not trusted
[ ] Sharing sets scoped to the account relationship
[ ] Share groups configured so internal users see portal-created records
[ ] Registration handler validates the email domain
[ ] Field-level security checked for external profiles
[ ] Public pages reviewed for what an unauthenticated visitor can reach
[ ] Site tested as a guest and as each external profile, on the published site
```

The last line is the one that catches what the others miss. Reviewing configuration is not the same as loading the site logged out and seeing what appears.

## Practical guidance

**Choose the licence type before designing the sharing model** — Customer Community has no roles.

**Treat the guest user as the internet**, because it is.

**Never trust a record Id** from a guest or portal request.

**Use sharing sets** for community record access, and share groups so internal users can see portal-owned records.

**Set `{!recordId}` as the default** in the component's target config.

**Use inline messages, not toasts.**

**Prefer LWR templates** for new sites.

**Validate the email domain** in the registration handler.

**Test on the published site**, as an external user, not in the builder.
