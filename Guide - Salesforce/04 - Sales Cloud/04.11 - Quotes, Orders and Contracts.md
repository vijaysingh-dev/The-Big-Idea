# Quotes, Orders and Contracts

## The commercial documents

Opportunity tracks the deal. These three objects track the paperwork.

**Quote** — a formal price offer to the customer, with line items and an expiry.
**Order** — what was actually bought, usually feeding fulfilment.
**Contract** — the agreement governing the relationship, with a term and renewal dates.

All three are optional. Many orgs use none of them, generating quotes in a separate system and pushing orders to an ERP. Whether to adopt them is a real decision rather than a default.

## Quotes

A Quote belongs to an Opportunity. `QuoteLineItem` mirrors `OpportunityLineItem`, and quote lines can be synced back to the opportunity.

Key fields: `OpportunityId`, `Name`, `Status`, `ExpirationDate`, `Subtotal`, `Discount`, `TotalPrice`, `GrandTotal`, `Tax`, `ShippingHandling`, `IsSyncing`, `ContactId`, `BillingAddress`, `ShippingAddress`.

**Quote syncing** is the feature worth understanding. One quote per opportunity can be flagged as syncing, and while it is, changes to the quote's line items propagate to the opportunity's line items and amount.

```java
// Setting IsSyncing makes this quote the source of truth for the opportunity's line items
Quote quote = [SELECT Id, IsSyncing FROM Quote WHERE Id = :quoteId];
quote.IsSyncing = true;
update quote;
```

Only one quote can sync at a time. Setting a second one to sync clears the first. This is the mechanism for "we sent three versions; version three is the one we are working from".

The practical value: reps can produce several quote variants without disturbing the opportunity, then sync the one the customer accepted.

**Quote PDFs** are generated from a template configured in Setup, or from a Visualforce page for anything custom. The native template editor is limited — no conditional sections, restricted layout control — so orgs with real document requirements usually build a Visualforce or third-party solution.

```apex
// Generating a PDF from a Visualforce page renderAs="pdf"
PageReference quotePage = Page.QuoteDocument;
quotePage.getParameters().put('id', quoteId);
Blob pdfBody = Test.isRunningTest() ? Blob.valueOf('test') : quotePage.getContentAsPDF();

ContentVersion version = new ContentVersion(
    Title = 'Quote ' + quoteNumber,
    PathOnClient = 'Quote-' + quoteNumber + '.pdf',
    VersionData = pdfBody,
    FirstPublishLocationId = quoteId
);
insert version;
```

The `Test.isRunningTest()` guard is necessary because `getContentAsPDF()` throws in test context.

## Orders

An Order records what the customer actually bought. It can be created from an Opportunity or a Quote, or independently.

Key fields: `AccountId`, `OpportunityId`, `ContractId`, `Status`, `EffectiveDate`, `EndDate`, `TotalAmount`, `Type`, `OrderNumber`.

`OrderItem` holds the line items, referencing `PricebookEntry` in the same way opportunity lines do.

**Order status is a two-level model.** `Status` is a picklist of your own values, but each maps to a `StatusCode` of either **Draft** or **Activated**. This matters because activated orders become largely read-only — line items cannot be added or changed. Deactivating requires moving the status back to a Draft-mapped value.

That behaviour is deliberate and occasionally awkward. Code that updates orders needs to handle the activated state:

```java
public with sharing class OrderAmendmentService {

    public static void amendOrder(Id orderId, List<OrderItem> newItems) {
        Order order = [SELECT Id, Status, StatusCode FROM Order WHERE Id = :orderId];

        if (order.StatusCode == 'Activated') {
            // activated orders are locked; revert to draft before modifying lines
            order.Status = 'Draft';
            update order;
        }

        insert newItems;

        order.Status = 'Activated';
        update order;
    }
}
```

**Reduction Orders** exist for returns and cancellations, referencing an original order and recording negative quantities. Useful in businesses with genuine returns processing, and ignorable otherwise.

Orders are most valuable when Salesforce is the system that fulfilment reads from. When an ERP owns fulfilment — which is common — the Order object is often redundant, and the opportunity is pushed directly to the ERP instead.

## Contracts

A Contract represents the agreement: a term, a start and end date, and a status.

Key fields: `AccountId`, `Status`, `StartDate`, `ContractTerm` (months), `EndDate` (derived), `ContractNumber`, `OwnerExpirationNotice`, `CustomerSignedId`, `CustomerSignedDate`, `CompanySignedId`, `CompanySignedDate`, `ActivatedById`, `ActivatedDate`.

`EndDate` is calculated from `StartDate` plus `ContractTerm` and is read-only.

**Contract status** works like Order status, with a two-level model. `Status` is your picklist; `StatusCode` maps to Draft, In Approval Process, or Activated. Activated contracts become read-only on most fields.

Contracts matter most for **renewal management**. A contract with an end date is what drives the renewal pipeline:

```java
public with sharing class ContractRenewalService implements Database.Batchable<SObject>, Schedulable {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, AccountId, Account.Name, EndDate, ContractTerm, OwnerId,
                   Annual_Value__c
            FROM Contract
            WHERE Status = 'Activated'
              AND EndDate = NEXT_N_DAYS:120
              AND Renewal_Opportunity__c = null
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Contract> contracts) {
        List<Opportunity> renewals = new List<Opportunity>();
        Map<Id, Contract> contractsById = new Map<Id, Contract>(contracts);

        for (Contract c : contracts) {
            renewals.add(new Opportunity(
                AccountId = c.AccountId,
                Name = c.Account.Name + ' - Renewal ' + c.EndDate.year(),
                StageName = 'Qualification',
                CloseDate = c.EndDate,
                Amount = c.Annual_Value__c,
                Type = 'Renewal',
                OwnerId = c.OwnerId,
                Source_Contract__c = c.Id
            ));
        }

        insert renewals;

        List<Contract> toUpdate = new List<Contract>();
        for (Opportunity renewal : renewals) {
            toUpdate.add(new Contract(
                Id = renewal.Source_Contract__c,
                Renewal_Opportunity__c = renewal.Id
            ));
        }
        update toUpdate;
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 100);
    }
}
```

The `Renewal_Opportunity__c = null` filter in the query is what makes the job idempotent — running it twice does not create duplicate renewal opportunities. Building that into scheduled jobs from the start avoids a familiar class of incident.

## Deciding what to adopt

A useful decision framework, since these three objects are frequently adopted without a clear reason:

**Adopt Quote when** reps produce formal price documents from Salesforce and need version control over them. Skip it when quotes are produced in a separate system or when the deal value on the opportunity is sufficient.

**Adopt Order when** Salesforce feeds fulfilment, or when order-level data is needed for reporting that the opportunity cannot provide. Skip it when an ERP owns orders and Salesforce only needs to know the deal closed.

**Adopt Contract when** the business has terms and renewals to manage, and renewal pipeline generation matters. This is the most commonly worthwhile of the three for subscription and service businesses.

The anti-pattern is adopting all three because they exist, producing four objects holding overlapping data with no clear source of truth and reps entering the same information repeatedly.

## Integration considerations

All three objects are common integration points with an ERP, and the same principles apply:

**Use external IDs** so upserts are idempotent. The ERP's order number and contract number are the natural keys.

**Push on state change, not on a schedule.** A platform event published when an order activates is more reliable and more timely than a nightly job scanning for changes.

**Handle the activated read-only behaviour.** An integration that updates orders will hit it.

**Decide which system owns each field.** Ambiguity here produces update loops where two systems overwrite each other.

See [[13.1 - Integration Fundamentals and Patterns]] and [[13.17 - Error Handling, Retries and Idempotency]].

## Practical guidance

**Do not adopt objects you have no clear use for.** Each one is more data entry for reps and more surface to maintain.

**If you adopt Quote, use quote syncing** rather than duplicating line items manually.

**Build renewal generation from Contract**, with an idempotency guard.

**Expect the activated read-only behaviour** on both Order and Contract, and design integrations around it.

**Consider whether CPQ is the real answer.** Complex quoting, subscription terms, and amendments are what CPQ exists for, and the native objects will not stretch that far. See [[04.10 - Products, Price Books and Pricing]].
