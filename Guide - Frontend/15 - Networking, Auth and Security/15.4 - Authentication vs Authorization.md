# Authentication vs Authorization

**Authentication (AuthN)** — who are you? Proving identity.
**Authorization (AuthZ)** — what may you do? Checking permissions.

The HTTP status codes encode the distinction, and their names are historically confusing:

- **`401 Unauthorized`** actually means *unauthenticated*. The client should log in or refresh a token.
- **`403 Forbidden`** means authenticated but not permitted. Logging in again will not help.

Conflating them produces a redirect loop: the app sees 403, sends the user to login, they log in successfully, hit the same page, get 403 again ([[15.1 - HTTP Fundamentals]]).

## Authentication approaches

**Session cookies** — the server creates a session, stores it (in Redis or a database), and returns an opaque session id in an `HttpOnly` cookie. The browser sends it automatically. Sessions are revocable instantly by deleting the server record.

**Token-based (JWT)** — the server issues a signed token containing claims. Stateless: the server verifies the signature without a lookup. Fast and horizontally scalable, but revocation is hard because a valid signature is valid until expiry ([[15.5 - JWT Sessions and Token Storage]]).

**OAuth 2.0 / OIDC** — delegated authentication through a provider. OAuth 2.0 is an *authorization* framework; **OpenID Connect** layers authentication on top of it, adding the `id_token`. "Log in with Google" is OIDC, not plain OAuth.

**Passkeys / WebAuthn** — public-key credentials bound to the origin, unlocked by biometrics or a device PIN. Phishing-resistant by construction, since the credential will not release for a lookalike domain. Increasingly the recommended primary method.

**Magic links and OTP** — no password; a one-time code delivered by email or SMS. Common in Indian consumer products via phone-number OTP, where `autocomplete="one-time-code"` enables autofill ([[09.2 - Forms and Native Input Behavior]]).

## The OAuth flow you should know

For browser applications, the correct flow is **Authorization Code with PKCE**. The implicit flow is deprecated — it returned tokens in the URL fragment, where they leaked into history, referrers and logs.

```
1. App generates a random `code_verifier`, derives `code_challenge` = SHA256(verifier)
2. Redirect to the provider with client_id, redirect_uri, scope, state, code_challenge
3. User authenticates with the provider
4. Provider redirects back with an authorization code
5. App exchanges code + code_verifier for tokens
6. Provider verifies the challenge matches, returns access + refresh tokens
```

**PKCE** (Proof Key for Code Exchange) prevents an intercepted authorization code from being redeemed by an attacker, because they lack the verifier. It was originally for mobile apps and is now required for browser apps too, since a public client cannot keep a secret.

**`state`** is a random value round-tripped through the flow and verified on return. It prevents CSRF on the callback — without it, an attacker can complete a flow with their own account and cause the victim's session to be bound to it.

**Never put a client secret in frontend code.** A browser application is a public client by definition; anything in the bundle is visible.

The current best practice for browser apps is the **Backend-For-Frontend (BFF)** pattern: the token exchange happens server-side, tokens stay on the server, and the browser gets an `HttpOnly` session cookie. This avoids storing tokens in the browser entirely.

## Authorization models

**RBAC (Role-Based Access Control)** — permissions attach to roles, users get roles.

```js
user.roles = ["editor"];
rolePermissions.editor = ["post:read", "post:write"];
```

Simple and adequate for most applications.

**ABAC (Attribute-Based)** — decisions computed from attributes of the user, resource and context.

```js
canEdit = user.id === post.authorId || user.role === "admin";
canEdit = user.department === doc.department && !doc.locked;
```

Necessary when permissions depend on the relationship between user and resource — "can edit their own posts", "can view documents in their team".

**ReBAC (Relationship-Based)** — permissions derived from a graph of relationships, as in Google Zanzibar and its open-source implementations. What you need for hierarchical sharing: folder permissions inheriting to documents, organization to team to project.

## The frontend's actual role

**The frontend cannot enforce authorization.** Everything in the browser is inspectable and modifiable. Hiding a delete button prevents a mistake; it does not prevent an attack.

Every permission check must exist on the server. The frontend's job is to reflect the server's decisions so the UI does not offer actions that will fail.

```jsx
function DeleteButton({ post }) {
  const { can } = usePermissions();
  if (!can("post:delete", post)) return null;
  return <button onClick={remove}>Delete</button>;
}
```

The pattern that scales: the server returns the permissions relevant to each resource alongside it, so the client does not reimplement the authorization logic.

```json
{
  "id": 42,
  "title": "Post",
  "_permissions": { "edit": true, "delete": false, "publish": false }
}
```

Duplicating rules like `user.role === "admin" || post.authorId === user.id` on both sides guarantees they drift.

## Route protection

```jsx
function RequireAuth({ children }) {
  const { user, isLoading } = useAuth();
  const location = useLocation();

  if (isLoading) return <Spinner />;
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;

  return children;
}
```

Three details: the loading state prevents a flash of the login page while the session is being verified; `state={{ from }}` preserves the intended destination so the user lands where they meant to after logging in; and `replace` keeps the login page out of the history stack so Back does not return to it.

The redirect target must be validated before use — an open redirect that accepts any URL is a real vulnerability ([[23.4 - Protected Routes and Auth Flows]]).

## Session lifecycle

**Login** — establish the session, then redirect to the intended destination.

**Refresh** — silently renew before expiry. The standard implementation queues concurrent 401s so a single refresh serves all of them:

```js
let refreshPromise = null;

async function refresh() {
  refreshPromise ??= doRefresh().finally(() => { refreshPromise = null; });
  return refreshPromise;
}
```

Without this deduplication, five concurrent requests hitting a 401 trigger five refresh calls, and with rotating refresh tokens four of them fail ([[04.7 - Async Concurrency Patterns]]).

**Logout** — clear the server session, clear client state, and broadcast to other tabs:

```js
new BroadcastChannel("auth").postMessage({ type: "logout" });
```

Clearing the client alone is not logout — the server session must be invalidated, or the token remains valid for anyone who captured it.

**Idle timeout** — for sensitive applications, expire after inactivity with a warning before it happens.

## Multi-factor and step-up

Not all actions need the same assurance. **Step-up authentication** re-verifies for sensitive operations — changing a password, transferring money — even within a valid session. The API returns a specific error indicating re-authentication is required, and the client prompts.

## How senior engineers actually use this

**They treat the client as advisory.** Every check is duplicated on the server; the client version exists for UX only.

**They have the server tell the client what it may do**, rather than encoding rules twice.

**They use `HttpOnly` cookies via a BFF** where the architecture allows, avoiding browser token storage entirely.

**They deduplicate refresh requests** and handle the "refresh failed" path explicitly — usually a clean logout rather than a retry loop.

**They distinguish 401 from 403** in the API layer, once.

## Common pitfalls

- Treating 403 as 401 and looping through login.
- Enforcing permissions only in the UI.
- Client secrets in frontend code.
- Implicit flow instead of Authorization Code with PKCE.
- Missing `state` validation on the OAuth callback.
- No loading state on protected routes, flashing the login screen.
- Concurrent refresh calls invalidating each other.
- Open redirect via an unvalidated `returnTo` parameter.
- "Logout" that only clears client state.

## Interview angle

"Difference between authentication and authorization" is the opener; the 401/403 mapping is the natural follow-up. Deeper questions go to "how would you implement auth in a React app" — cover the flow (PKCE, `state`), token storage tradeoffs, protected routes with loading states and redirect preservation, refresh deduplication, and cross-tab logout. The point that carries the most weight is that the frontend cannot enforce authorization and exists only to reflect server decisions.
