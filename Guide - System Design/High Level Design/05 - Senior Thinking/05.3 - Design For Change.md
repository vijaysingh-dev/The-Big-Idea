# Design for Change

> **Revision tags:** #senior-thinking #architecture #evolvability  
> **Related:** [[05.1 - Tradeoff Evaluation]] | [[05.4 - Build vs Buy]]

---

## The Core Insight

You will be wrong about the future. Requirements change. Traffic patterns change. The team grows. The technology landscape shifts.

Good architecture isn't architecture that's perfect today. It's architecture that's easy to change tomorrow — when you discover you were wrong.

---

## Avoiding Premature Optimization

Premature optimization is building for a scale you don't have, adding complexity you don't need, and optimizing for bottlenecks that don't exist yet.

**The cost:**
- Extra infrastructure to maintain
- More complex code to debug
- Slower development velocity
- Wrong abstractions that are hard to remove later

**The heuristic:**
```
1. Make it work      (correctness)
2. Make it right     (clean, maintainable)
3. Make it fast      (only the measured bottleneck)
```

You don't earn the right to optimize until you've measured. "I think this will be slow" is not evidence. Profiler data is.

**Practical rule:** Don't add sharding until you've hit the write ceiling on a single node. Don't add a cache until you've measured DB query times under realistic load. Don't add microservices until the monolith is actually causing team/scale pain.

## Designing for Evolvability

### Stable Interfaces, Flexible Internals

Public interfaces (APIs, events, database schemas referenced by other services) are hard to change. Internal implementations are easy to change.

```
Design for stability at boundaries:
  - API contracts (URL structure, request/response schema)
  - Event schemas (published to a message queue)
  - Database tables referenced by multiple services

Design for flexibility in implementation:
  - Algorithm selection
  - Library choice
  - Internal data model
  - Caching strategy
```

When in doubt: keep the interface narrow. You can always add; you can rarely remove.

### The Strangler Fig Pattern

When replacing a legacy system, don't rewrite it in one go. Build the new system alongside the old, route traffic gradually, and retire the old system piece by piece.

```
Phase 1: New system handles /api/v2/checkout
         Old system handles everything else

Phase 2: New system handles all /api/v2/* (feature-complete)

Phase 3: /api/v1/* proxied through new system (adapter)

Phase 4: Old system retired
```

This lets you validate the new system with real traffic before committing.

### Modular Boundaries Precede Service Extraction

If you think you'll eventually extract a service, create a clean module boundary now.

```python
# Bad: direct DB access from anywhere
def get_order_price(order_id):
    return db.query("SELECT price FROM orders WHERE id = ?", order_id)

# Good: module boundary (even in a monolith)
# pricing/service.py
class PricingService:
    def get_order_price(self, order_id: int) -> Decimal:
        order = self._order_repo.get(order_id)
        return self._calculate(order)
```

When you later extract `PricingService` as a microservice, the interface is already clean. The hard work is done.

## Schema Evolution

Database schemas are the hardest thing to change in a production system. Plan for change from day one.

### Backward-Compatible Schema Changes (Safe)

```sql
-- Adding a nullable column (existing rows get NULL)
ALTER TABLE orders ADD COLUMN discount_code VARCHAR(50) NULL;

-- Adding a table
CREATE TABLE promotions (...);

-- Adding an index (can be done online with tools)
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
```

### Breaking Schema Changes (Require a Migration Strategy)

```sql
-- Renaming a column (breaks existing queries immediately)
ALTER TABLE orders RENAME COLUMN total TO total_amount;

-- Dropping a column (data loss if anything reads it)
ALTER TABLE orders DROP COLUMN legacy_field;

-- Changing a column type (may fail if existing data can't coerce)
ALTER TABLE orders ALTER COLUMN total TYPE NUMERIC(12,2);
```

**The expand-contract pattern for breaking changes:**

```
Step 1 (Expand): Add new column alongside old one
  ALTER TABLE orders ADD COLUMN total_amount NUMERIC(12,2);

Step 2: Deploy code that writes to BOTH columns and reads from the new one

Step 3: Backfill: UPDATE orders SET total_amount = total;

Step 4 (Contract): Remove old column once no code reads it
  ALTER TABLE orders DROP COLUMN total;
```

This allows zero-downtime schema migration without a flag day.

### Online Schema Changes

`ALTER TABLE` on large tables acquires a table lock — blocking all reads and writes for potentially hours.

**Tools for online schema changes:**
- **gh-ost** (GitHub): shadow table approach, zero locking
- **pt-online-schema-change** (Percona): trigger-based, minimal locking
- **PostgreSQL**: Many operations support `CONCURRENTLY` (index creation, some ALTER TABLE operations)

## API Versioning

Public APIs need to evolve without breaking existing clients.

### URL versioning (most common)

```
/api/v1/orders   ← old clients still call this
/api/v2/orders   ← new clients call this
```

Maintain both until old clients migrate. Set a deprecation timeline and communicate it.

### Additive changes (safe to any versioned or non-versioned API)

```
+ Add optional fields to request
+ Add fields to response (clients must ignore unknown fields)
+ Add new endpoints
```

### Breaking changes (require versioning or careful migration)

```
- Remove fields from response
- Change field types
- Change endpoint behavior for existing inputs
- Change authentication requirements
```

## Event Schema Evolution

Events published to a message queue are consumed by many services. Changing them requires coordination.

**Rules for backward-compatible events:**
```
✅ Add optional fields to payload
✅ Add new event types
✅ Add new consumers (publishers don't care)

❌ Remove fields consumers depend on
❌ Change field semantics (totalPrice used to be pre-tax, now it's post-tax)
❌ Remove event types other consumers depend on
```

**Schema registry:** Enforce compatibility rules before publishing (Confluent Schema Registry supports BACKWARD, FORWARD, FULL compatibility modes).

## The Architecture Decision Record (ADR)

Document significant architecture decisions so future engineers (and future you) understand *why* the system is built the way it is.

```markdown
## ADR-007: Use Kafka instead of SQS for order events

### Status: Accepted

### Context
Order events need to be consumed by analytics, inventory, and notification services.
Analytics requires the ability to replay events from the last 7 days.

### Decision
Use Kafka (AWS MSK) for order events.

### Consequences
+ Replay capability for analytics consumer
+ Multiple independent consumer groups can consume the same events
- Adds operational complexity vs SQS
- Requires Kafka expertise on the team
- Higher cost than SQS at current volume

### Alternatives Considered
SQS was rejected because it doesn't support replay.
```

ADRs live in the repository alongside code. They're invaluable when you rejoin a project after 6 months and wonder "why did we do it this way?"
