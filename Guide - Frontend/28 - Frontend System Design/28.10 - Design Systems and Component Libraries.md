# Design Systems and Component Libraries

A component library is code. A design system is code **plus** tokens, documentation, usage guidance, contribution process and adoption — and the non-code parts are what determine whether it succeeds.

Most failed design systems are technically fine and organizationally abandoned.

## Token architecture

Two layers, and the separation is what makes theming and rebranding tractable.

```css
:root {
  /* Primitives — raw values, no meaning */
  --gray-50: oklch(98% 0 0);
  --gray-900: oklch(20% 0 0);
  --blue-500: oklch(60% 0.15 250);
  --space-1: 0.25rem;
  --space-4: 1rem;

  /* Semantic — meaning, referencing primitives */
  --color-surface: var(--gray-50);
  --color-text: var(--gray-900);
  --color-accent: var(--blue-500);
  --color-danger: var(--red-500);
  --radius-control: 0.375rem;
}

[data-theme="dark"] {
  --color-surface: var(--gray-900);
  --color-text: var(--gray-50);
}
```

**Components reference only semantic tokens.** A component using `--blue-500` directly cannot be rethemed; one using `--color-accent` can.

Dark mode then becomes a handful of reassignments rather than a parallel stylesheet, and a rebrand touches the primitive layer only ([[10.4 - Units Custom Properties and Theming]]).

CSS custom properties are the right mechanism because they cascade, can be overridden per subtree, and are readable and writable at runtime — which no build-time variable system offers.

Set `color-scheme` alongside, or a dark page renders light scrollbars and form controls.

## Tiering the components

```
Primitives    Box, Text, Stack        layout and typography
Elements      Button, Input, Badge    single-purpose, no domain knowledge
Patterns      Modal, DataTable, Combobox   composed, stateful
Templates     PageLayout, FormLayout  arrangement only
```

The boundary that matters: **nothing in the design system knows about your domain.** A `ProductCard` belongs in the product feature, not the design system, because it will need product-specific changes that the design system cannot own ([[28.2 - Project Structure and Architecture]]).

The most common failure is a design system accumulating domain components, which makes every product change require a design system release.

## Build or adopt

Building complex accessible widgets is expensive and rarely differentiating. A combobox done correctly — arrow navigation, typeahead, ARIA relationships, screen reader announcements, mobile behavior — is roughly a week of work and will still have bugs.

The pragmatic split:

```
Headless library (Radix, React Aria, Base UI)   → behavior and accessibility
Your code                                        → styling, tokens, API shape
```

```tsx
import * as Dialog from "@radix-ui/react-dialog";

export function Modal({ children, ...props }) {
  return (
    <Dialog.Root {...props}>
      <Dialog.Portal>
        <Dialog.Overlay className={styles.overlay} />
        <Dialog.Content className={styles.content}>{children}</Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

Focus trapping, escape handling, scroll locking and ARIA come from the library; the visual identity is yours ([[22.6 - Compound Components]]).

Build from scratch only when the interaction is genuinely novel. Fully-styled libraries like MUI are a different trade — faster to start, harder to make look like your brand.

## API consistency

Consistency across the library matters more than any individual API being ideal:

```tsx
<Button variant="primary" size="md" />
<Badge variant="danger" size="sm" />
<Alert variant="warning" />
```

Same prop names, same value vocabulary, same ordering everywhere. A developer who learns one component should be able to guess the next.

Non-negotiables for every component ([[28.3 - Component Design and API Design]]):

- **Forward the ref**, or consumers cannot focus, measure or position against it
- **Spread unknown props**, or every `data-testid` needs a wrapper
- **Merge `className`**, never replace it
- **Support controlled and uncontrolled** modes for anything stateful

A discriminated union for variants makes invalid prop combinations uncompilable ([[25.6 - Discriminated Unions and Narrowing]]).

## Accessibility is the core value

```tsx
<Button aria-pressed={pressed} />
<Input aria-invalid={hasError} aria-describedby={errorId} />
<Modal role="dialog" aria-modal="true" aria-labelledby={titleId} />
```

Getting focus management, keyboard interaction and ARIA right once in `Button`, `Input`, `Modal` and `Menu` fixes it across every product using them. That leverage is the strongest business argument for a design system — far stronger than visual consistency.

Automated checks in CI catch regressions:

```ts
const results = await new AxeBuilder({ page }).analyze();
expect(results.violations).toEqual([]);
```

Automation catches roughly a third of issues; keyboard-only testing of each component catches most of the rest ([[09.5 - Accessibility Fundamentals]]).

## Documentation that gets used

```tsx
export const Loading: Story = { args: { isLoading: true } };
export const Error: Story = { args: { error: new Error("Failed") } };
export const LongContent: Story = { args: { children: LOREM } };
export const RTL: Story = { parameters: { direction: "rtl" } };
```

Storybook stories serve three purposes at once: documentation, the place designers and engineers agree on behavior, and visual regression coverage.

The states worth having stories for are exactly the ones people forget to build — loading, error, empty, long content, RTL ([[24.2 - Loading Error and Empty States]]).

Documentation needs more than a props table:

- **When to use this, and when not to** — the most valuable section, and the most often missing
- **Do and don't examples**
- **Accessibility notes** — what the component handles and what the consumer must supply
- **Migration notes** for breaking changes

If the docs only list props, developers will read the source instead, and then depend on internals.

## Versioning and breaking changes

Breaking changes are expensive across an organization. Prefer additive change and a deprecation period:

```tsx
function Button({ variant, type, ...rest }) {
  if (type !== undefined && process.env.NODE_ENV !== "production") {
    console.warn("Button: `type` is deprecated, use `variant`. Removing in v3.");
  }
  return <button data-variant={variant ?? type} {...rest} />;
}
```

Support both, warn in development, remove in the next major.

**Ship a codemod with every breaking change.** It turns an organization-wide migration from weeks of manual edits into a single PR per consumer:

```bash
npx @company/design-system-codemod v2-to-v3 ./src
```

This is the difference between a design system teams upgrade and one they pin and fall behind on.

## Distribution

```json
{
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.mjs" },
    "./styles.css": "./dist/styles.css"
  },
  "sideEffects": ["*.css"],
  "peerDependencies": { "react": ">=18" }
}
```

Three details that matter for consumers:

**`sideEffects`** must list CSS, or `false` alone causes styles to vanish from production builds ([[27.6 - Tree Shaking]]).

**`peerDependencies`** for React, so consumers do not get a second copy ([[17.1 - Rules of Hooks and How They Work]]).

**Granular `exports`** so a consumer importing `Button` does not pull in the data grid.

In a monorepo, publishing internally via workspaces avoids the release cycle entirely while keeping the boundary ([[27.1 - npm and package.json]]).

## Adoption is the real problem

A technically excellent design system nobody uses has failed.

What actually drives adoption:

- **It is easier than not using it** — good defaults, good docs, quick to start
- **Requests get answered** — a Slack channel with a responsive owner
- **Contribution is possible** — teams can add what they need rather than forking
- **Migration is supported** — codemods and help, not a mandate
- **Gaps are visible** — a tracked list of what is missing

What kills adoption: mandating use before the system is ready, slow response to requests, breaking changes without migration paths, and no escape hatch — which leads teams to fork.

Measure it. Percentage of components sourced from the system, number of one-off local components, and open requests are the signals that show whether it is working.

## How senior engineers actually use this

**They separate primitive and semantic tokens** and let components reference only semantic ones.

**They build on a headless library** rather than reimplementing APG patterns.

**They keep domain components out** of the design system.

**They ship a codemod with every breaking change.**

**They treat adoption as the primary metric**, not component count.

**They document when *not* to use a component**, which is the section people actually need.

## Common pitfalls

- Components referencing primitive tokens directly, blocking theming.
- Domain components in the design system, coupling releases to product work.
- Building complex widgets from scratch and shipping inaccessible versions.
- Inconsistent prop naming across components.
- Swallowed refs and props, forcing consumer wrappers.
- `sideEffects: false` without listing CSS.
- React as a direct dependency rather than a peer.
- Breaking changes with no deprecation period or codemod.
- Mandating adoption before the system covers real needs.

## Interview angle

"How would you build a design system" should lead with token architecture — primitives and semantic layers, with components referencing only the latter — then the component tiering with the rule that domain knowledge stays out. State that accessibility is the core value proposition because fixing it once in the primitives fixes it everywhere. The points that separate strong answers: build on a headless library rather than reimplementing widgets, ship codemods with breaking changes, and treat adoption rather than component count as the measure of success.
