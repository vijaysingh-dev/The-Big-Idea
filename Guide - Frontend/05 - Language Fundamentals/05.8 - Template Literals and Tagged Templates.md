# Template Literals and Tagged Templates

Backtick strings with interpolation, multiline support, and — the part most people never use — a hook for custom string processing.

## Basics

```js
const name = "Vijay";

`Hello ${name}`;
`Sum: ${1 + 2}`;
`Nested: ${`inner ${name}`}`;
`Method: ${name.toUpperCase()}`;
`Conditional: ${isActive ? "on" : "off"}`;

`Line one
Line two`;               // newlines preserved literally
```

Any expression works inside `${}` — function calls, ternaries, further template literals. Statements do not; `${if (x) {}}` is invalid.

Interpolated values are converted with `String()`, so objects become `"[object Object]"` unless they define `toString` or `Symbol.toPrimitive` ([[03.6 - Symbols and Well Known Symbols]]).

```js
`${[1, 2]}`      // "1,2"
`${{}}`          // "[object Object]"
`${null}`        // "null"
`${undefined}`   // "undefined"
```

Escaping backticks and `${`:

```js
`a \` b`;
`literal \${notInterpolated}`;
```

## Multiline and indentation

The literal preserves whatever whitespace is in the source, including the indentation of your code:

```js
function f() {
  return `
    line one
    line two
  `;
}
// includes leading newline and eight spaces per line
```

This is the main annoyance with multiline templates. The usual fixes are a `.trim()`, a dedent helper, or `String.raw` with explicit `\n`. Libraries like `dedent` exist for exactly this.

## Tagged templates

A function placed immediately before a template literal receives the literal's parts as arguments:

```js
function tag(strings, ...values) {
  // strings: array of static parts
  // values: array of interpolated values
}

const a = 1, b = 2;
tag`x ${a} y ${b} z`;
// strings = ["x ", " y ", " z"]
// values  = [1, 2]
```

`strings.length` is always `values.length + 1`. The array also carries a `.raw` property with escape sequences uninterpreted.

This gives you a place to intercept and transform interpolated values, which is what makes the following possible.

## HTML escaping

The most defensible practical use — preventing XSS when building markup ([[15.6 - Frontend Security]]):

```js
function html(strings, ...values) {
  return strings.reduce((out, str, i) => {
    const value = values[i - 1];
    return out + escapeHtml(String(value)) + str;
  });
}

function escapeHtml(s) {
  return s.replace(/[&<>"']/g, c => ({
    "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;",
  }[c]));
}

const userInput = '<img src=x onerror="alert(1)">';
element.innerHTML = html`<div>${userInput}</div>`;  // safely escaped
```

The static parts are trusted (you wrote them); the interpolated parts are not. A tag function is the only place in the language where that distinction is structurally available.

Lit's `html` tag and several server-side templating libraries work exactly this way.

## Parameterized queries

Same principle, different injection target:

```js
const rows = await sql`SELECT * FROM users WHERE id = ${userId}`;
```

The tag builds a parameterized query with `$1` placeholders and passes values separately, so string interpolation never reaches the database. This is how libraries like `postgres.js` and Vercel's `@vercel/postgres` present a safe API that looks like string building. Worth understanding even as a frontend engineer, because it is the clearest illustration of why the pattern exists.

## CSS-in-JS

```js
const Button = styled.button`
  padding: ${p => p.size === "lg" ? "12px 24px" : "8px 16px"};
  background: ${p => p.theme.primary};
`;
```

styled-components passes props to any interpolated function and produces a class name. The runtime cost of this — parsing and injecting styles during render — is why zero-runtime alternatives exist ([[11.5 - CSS Architecture]]).

## String.raw

```js
String.raw`C:\new\table`;   // "C:\new\table" — backslashes intact
`C:\new\table`;             // contains a newline and a tab
```

The built-in tag that ignores escape sequences. Useful for Windows paths, regex sources and LaTeX.

## i18n

```js
const t = (strings, ...values) => translate(strings.raw.join("{}"), values);
t`Hello ${name}, you have ${count} messages`;
```

The static parts form a stable lookup key, so translators work with one template rather than concatenated fragments. This is a real pattern in some i18n libraries, though most use explicit key strings instead because static extraction is easier.

## How senior engineers actually use this

**They use template literals for all string building** and treat `+` concatenation as legacy. The readability difference at three or more interpolations is substantial.

**They write tag functions rarely and read them often.** styled-components, graphql-tag, and SQL clients are all tagged templates; understanding the mechanism makes their behavior obvious rather than magical.

**They never build HTML with plain template literals and `innerHTML`.** Either use a framework, `textContent`, or an escaping tag. This is one of the most common XSS vectors in vanilla JS code.

**They watch for accidental multiline whitespace** in strings sent to APIs or rendered in `<pre>` blocks.

## Common pitfalls

- Interpolating an object and getting `[object Object]`.
- Indentation leaking into multiline strings.
- Building HTML strings from user input without escaping.
- Assuming `strings` and `values` have the same length in a tag function.
- Using template literals in a hot loop where a simple concatenation was equivalent — negligible, but occasionally the source of a micro-optimization argument that is not worth having.

## Interview angle

Template literals themselves are rarely asked directly. Tagged templates come up as "how does styled-components work" or "how would you safely build HTML from user input" — and the answer is that a tag function receives static and dynamic parts separately, so the dynamic ones can be escaped or parameterized. Being able to write the `html` escaping tag on the spot is a good demonstration.
