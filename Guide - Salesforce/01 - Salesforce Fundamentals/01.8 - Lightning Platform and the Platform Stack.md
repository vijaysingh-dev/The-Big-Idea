# Lightning Platform and the Platform Stack

## What the platform is

The **Lightning Platform** is everything underneath the CRM applications: the database, the security model, the automation engine, the Apex runtime, the APIs, and the user interface framework. Sales Cloud and Service Cloud are applications built on it. Your custom work is built on the same thing, with the same tools Salesforce used.

That last point is worth pausing on. Standard objects and custom objects behave nearly identically. Your Apex trigger on a custom object and the platform's own logic on Opportunity run through the same execution pipeline. You are not writing plugins around the edges of a closed product; you are building at the same layer.

## The layers

Read this from the bottom up. Everything above depends on everything below.

**1. Storage and metadata.** The multi-tenant database, the universal data dictionary, indexes, and the metadata that defines your schema. See [[01.5 - Multi-Tenant Architecture]].

**2. Sharing and security.** Sits directly on top of storage and is unavoidable. Every read is filtered by what the running user can see, using materialized share tables. Every write is checked against object and field permissions. Section 03.

**3. Data access.** SOQL and SOSL for reading, DML for writing, and the record save pipeline that runs validation, triggers, flows, and roll-ups in a fixed sequence. Sections 08, 10, and [[07.13 - Order of Execution]].

**4. Business logic.** Two parallel tracks that meet in the save pipeline. Declarative: validation rules, flows, approval processes, assignment rules. Programmatic: Apex classes and triggers. Sections 07 and 09 to 12.

**5. Application services.** Cross-cutting capabilities the platform provides so you do not build them: search, reporting and dashboards, files, email, chatter, platform events, scheduling, caching. Section 17.

**6. Interfaces.** Everything that reaches the outside world. The APIs (REST, SOAP, Bulk, GraphQL, Pub/Sub) for machines, section 13. The user interface layer for humans: Lightning Experience, Lightning App Builder, Lightning Web Components, Visualforce, and the mobile app. Section 14.

**7. Development lifecycle.** The tooling wrapped around all of it: Salesforce CLI, scratch orgs, packaging, deployment, testing. Sections 19 and 21.

## Where your code plugs in

A useful way to hold this: the platform gives you a small number of *extension points*, and every custom feature you build enters through one of them.

| Extension point | Runs when | Typical use |
| --- | --- | --- |
| Apex trigger | A record is saved | Cross-object logic, validation needing queries |
| Record-triggered flow | A record is saved | Declarative equivalent of the above |
| Invocable Apex | A flow calls it | Code that flows can reuse |
| Apex controller | A component requests data | Serving Lightning Web Components |
| Apex REST or SOAP service | An external system calls in | Exposing custom endpoints |
| Queueable, Batch, Scheduled | Later, asynchronously | Heavy or callout work |
| Platform event subscriber | An event is published | Decoupled reactions |
| Visualforce or LWC | A user opens a page | Custom user interfaces |

Every one of these runs inside the same governed transaction model and the same security context. There is no back door — no cron on a server, no daemon, no direct database access.

## The user interface layers, in order of age

Understanding the history explains what you will find in a real org.

**Visualforce** (2008). A server-side templating framework with its own markup and Apex controllers. Still fully supported and still very common. Renders inside an iframe within Lightning Experience, which causes some of its quirks.

**Aura Components** (2014). The first client-side component framework, built before web standards caught up. Being replaced, but not gone. Section 15.

**Lightning Web Components** (2019). The current framework, built on native web standards — custom elements, shadow DOM, ES modules. Faster, and the skills transfer to and from ordinary web development. Section 14.

You will meet all three in an org of any age. They can coexist on the same page. An LWC can be placed inside an Aura component; the reverse is not allowed.

## A concrete trace

Follow a single user action all the way down, because this ties the layers together better than any diagram.

A support agent opens a Case record page and clicks a custom "Escalate to Engineering" button.

1. **Interface layer.** Lightning Experience renders the record page. A Lightning Web Component provides the button.
2. The component calls an Apex method imperatively:

```java
@AuraEnabled
public static EscalationResult escalate(Id caseId, String reason) {
    return CaseEscalationService.escalate(caseId, reason);
}
```

3. **Security layer.** The Apex runs as the logged-in agent. If the class is declared `with sharing`, queries return only records that agent can see. Field-level permissions are checked on the fields being written.
4. **Business logic layer.** The service class validates the request, creates an `Engineering_Escalation__c` record, and updates the Case.
5. **Data access layer.** The DML statement enters the save pipeline. Validation rules run, before triggers run, the record is saved, after triggers run, flows run, roll-up summaries recalculate, and sharing rules are evaluated.
6. **Application services.** An after trigger publishes a platform event; a subscriber sends a notification to the engineering team's Slack channel asynchronously, keeping the callout out of the user's transaction.
7. **Back up the stack.** The Apex method returns, the component updates, and the agent sees a toast message.

Every layer participated. Skipping any of them is not an option — you cannot bypass sharing, you cannot avoid the save pipeline, you cannot make the callout synchronously inside the trigger.

## What this means in practice

**The platform's opinions are not negotiable, so learn them rather than fight them.** Engineers arriving from other stacks routinely try to reimplement things the platform already provides — their own permission checks, their own audit trail, their own queueing. The result is code that duplicates a feature, fails to match its edge cases, and has to be maintained forever.

**Every layer has its own limits.** Query limits at the data layer, CPU limits at the logic layer, API allowances at the interface layer, storage limits underneath everything. A design that satisfies one and ignores another still fails.

**Choose the highest layer that solves the problem.** If a page layout does it, do not build a Lightning Web Component. If a flow does it, do not write Apex. If a formula field does it, do not write a trigger. This is not laziness; it is the reason the platform exists, and it is the fastest reliable signal of an experienced Salesforce engineer. See [[07.1 - Automation Landscape and Tool Selection]].

**Layers are also how you debug.** When something misbehaves, work out which layer owns it. A record the user cannot see is a sharing question, not a code question. A save that fails with no obvious cause is an order-of-execution question. Naming the layer usually names the fix.
