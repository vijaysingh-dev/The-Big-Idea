# Factory, Strategy and Singleton in Apex

## Patterns that survive the translation

Apex has no generics, no reflection beyond `Type.forName`, and a transaction-scoped runtime. Several classical patterns need adaptation; three are used constantly.

## Strategy

**The problem:** a calculation that varies by some attribute, expressed as a growing chain of conditionals.

```java
// The version that keeps growing
public static Decimal calculateDiscount(Warranty_Claim__c claim) {
    if (claim.Coverage_Level__c == 'Premium') {
        return claim.Claim_Amount__c * 0.20;
    } else if (claim.Coverage_Level__c == 'Standard') {
        return claim.Claim_Amount__c * 0.10;
    } else if (claim.Coverage_Level__c == 'Extended') {
        return claim.Claim_Amount__c * 0.15 + 5000;
    }
    return 0;
}
```

Every new coverage level means editing this method, redeploying, and retesting the whole thing.

**The strategy version:**

```java
public interface IDiscountStrategy {
    Decimal calculate(Warranty_Claim__c claim, Machine_Coverage__c coverage);
}
```

```java
public with sharing class PremiumDiscountStrategy implements IDiscountStrategy {

    public Decimal calculate(Warranty_Claim__c claim, Machine_Coverage__c coverage) {
        Decimal base = claim.Claim_Amount__c * 0.20;
        return Math.min(base, coverage.Coverage_Limit__c);
    }
}

public with sharing class StandardDiscountStrategy implements IDiscountStrategy {

    public Decimal calculate(Warranty_Claim__c claim, Machine_Coverage__c coverage) {
        return claim.Claim_Amount__c * 0.10;
    }
}
```

```java
public with sharing class DiscountService {

    public static Map<Id, Decimal> calculate(
        List<Warranty_Claim__c> claims,
        Map<Id, Machine_Coverage__c> coverageByAsset
    ) {
        Map<Id, Decimal> discounts = new Map<Id, Decimal>();
        Map<String, IDiscountStrategy> strategies = DiscountStrategyFactory.all();

        for (Warranty_Claim__c claim : claims) {
            IDiscountStrategy strategy = strategies.get(claim.Coverage_Level__c);
            Machine_Coverage__c coverage = coverageByAsset.get(claim.Asset__c);

            // an unknown coverage level yields zero rather than an exception
            discounts.put(claim.Id,
                strategy == null || coverage == null ? 0 : strategy.calculate(claim, coverage));
        }
        return discounts;
    }
}
```

Adding a coverage level means a new class and a metadata record. No existing code changes, and no existing test is affected.

**When it is worth it:** three or more variants, each with real logic, expected to grow.

**When it is not:** two branches of one line each. A conditional is clearer than three files.

## Factory

**The problem:** deciding which implementation to instantiate, without every caller knowing the options.

The Apex-specific version is metadata-driven, which is where it becomes genuinely powerful:

```java
public with sharing class DiscountStrategyFactory {

    private static Map<String, IDiscountStrategy> cached;

    public static Map<String, IDiscountStrategy> all() {
        if (cached != null) {
            return cached;
        }

        cached = new Map<String, IDiscountStrategy>();

        for (Discount_Strategy__mdt config : [
            SELECT Coverage_Level__c, Strategy_Class__c
            FROM Discount_Strategy__mdt WHERE Active__c = true
        ]) {
            Type strategyType = Type.forName(config.Strategy_Class__c);

            // logging rather than throwing means one bad row does not break every claim
            if (strategyType == null) {
                AutomationLogger.logError('DiscountStrategyFactory', null,
                    'Unknown strategy class: ' + config.Strategy_Class__c);
                continue;
            }

            cached.put(config.Coverage_Level__c,
                (IDiscountStrategy) strategyType.newInstance());
        }
        return cached;
    }
}
```

**`Type.forName` returns null for an unknown name rather than throwing**, so the null check is mandatory.

**The class must be public or global with a no-argument constructor** to be instantiated this way. See [[09.12 - Generics, Type Casting and Reflection]].

**Custom Metadata makes the registry deployable and queryable at no query cost**, which is what makes the whole arrangement practical. See [[17.1 - Custom Metadata Types]].

The tradeoff worth stating: **the compiler no longer knows about the dependency.** Deleting `PremiumDiscountStrategy` compiles fine and fails at runtime. That is the price of runtime configurability, and it argues for monitoring around the factory rather than against the pattern.

## Singleton

**In Apex, a singleton lives for one transaction.** Statics reset at the transaction boundary, including at every async boundary. That makes the pattern narrower here than elsewhere.

```java
public with sharing class SchemaCache {

    private static SchemaCache instance;

    private Map<String, Schema.SObjectType> globalDescribe;
    private final Map<String, Map<String, Schema.SObjectField>> fieldCache =
        new Map<String, Map<String, Schema.SObjectField>>();

    private SchemaCache() { }

    public static SchemaCache getInstance() {
        if (instance == null) {
            instance = new SchemaCache();
        }
        return instance;
    }

    public Schema.SObjectField field(String objectName, String fieldName) {
        String key = objectName.toLowerCase();

        if (!fieldCache.containsKey(key)) {
            // getGlobalDescribe is expensive, so it happens once per transaction
            if (globalDescribe == null) {
                globalDescribe = Schema.getGlobalDescribe();
            }
            fieldCache.put(key, globalDescribe.get(key).getDescribe().fields.getMap());
        }

        // the field map key is lowercase, which catches people constantly
        return fieldCache.get(key).get(fieldName.toLowerCase());
    }

    @TestVisible
    private static void reset() {
        instance = null;
    }
}
```

**Where it earns its place:** describe caching, configuration caching, and a transaction-scoped counter.

**Where it does not:** anything holding mutable business state. A singleton accumulating records across a transaction is a hidden dependency that makes tests order-dependent, and the `reset()` method existing at all is a warning sign.

For caching that must survive the transaction, Platform Cache is the mechanism. See [[16.8 - Platform Cache]].

## Template Method

Useful for the trigger handler base class and for batch job families.

```java
public abstract class BatchJobBase implements Database.Batchable<SObject>, Database.Stateful {

    protected Integer processed = 0;
    protected Integer failed = 0;

    // the algorithm is fixed; subclasses supply the varying parts
    public void execute(Database.BatchableContext ctx, List<SObject> scope) {
        try {
            List<SObject> toUpdate = processScope(scope);

            if (!toUpdate.isEmpty()) {
                recordResults(Database.update(toUpdate, false), toUpdate);
            }
        } catch (Exception e) {
            failed += scope.size();
            logChunkFailure(ctx.getJobId(), e);
        }
    }

    public void finish(Database.BatchableContext ctx) {
        insert new Batch_Run_Log__c(
            Job_Name__c = jobName(),
            Records_Processed__c = processed,
            Records_Failed__c = failed
        );
        onFinish(ctx);
    }

    protected abstract List<SObject> processScope(List<SObject> scope);
    protected abstract String jobName();
    protected virtual void onFinish(Database.BatchableContext ctx) { }
}
```

```java
public with sharing class ClaimEnrichmentBatch extends BatchJobBase {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Asset__c, Claim_Amount__c
            FROM Warranty_Claim__c WHERE Region__c = null
        ]);
    }

    protected override List<SObject> processScope(List<SObject> scope) {
        return ClaimEnrichmentService.enrich((List<Warranty_Claim__c>) scope);
    }

    protected override String jobName() {
        return 'ClaimEnrichment';
    }
}
```

Error handling, logging, and result recording written once across every batch job in the org. That is a real saving when there are fifteen of them.

## Patterns that translate badly

Worth naming, because attempting them wastes time.

**Generic repository.** Apex has no generics, so a generic repository works with `SObject` and requires casting at every call site. A per-object selector is better. See [[18.5 - Selector Layer]].

**Observer with in-memory listeners.** Platform events are the platform's observer implementation, and they work across transactions, across users, and to external systems. Registering listener objects in a static is a worse version of something built in. See [[12.8 - Platform Events]].

**Builder with method chaining.** Works, and the verbosity rarely pays off given that sObjects have a field-value constructor:

```java
new Warranty_Claim__c(Asset__c = assetId, Claim_Amount__c = 150000, Status__c = 'Submitted')
```

Where a builder does earn its place is **test data construction**, which is the one place the fluent form genuinely improves readability:

```java
Warranty_Claim__c claim = new ClaimBuilder()
    .withAsset(assetId)
    .withAmount(150000)
    .approved()
    .build();
```

**Decorator.** Possible with interfaces and rarely warranted; a service method with a parameter is usually clearer.

**Dependency injection containers.** A full IoC container in Apex is machinery without a payoff. The two-constructor pattern covers what is needed. See [[18.8 - Dependency Injection and Testability]].

## Choosing

| Situation | Pattern |
| --- | --- |
| Three or more algorithm variants | Strategy |
| Deciding which implementation at runtime | Factory, ideally metadata-driven |
| Expensive computation reused in a transaction | Singleton |
| Several classes sharing an algorithm skeleton | Template Method |
| Decoupled reaction to something happening | Platform events, not Observer |
| Readable test data construction | Builder |
| Two simple branches | A conditional |

**That last row is the one worth emphasizing.** The most common pattern mistake in Apex codebases is applying Strategy and Factory to something a two-line `if` expressed clearly.

## The over-engineering test

Before introducing a pattern:

**How many variants exist today?** Two is a conditional. Four is a strategy.

**How often does a new one appear?** Never is a conditional. Quarterly is a strategy.

**Who adds them?** A developer can edit a class. An administrator needs metadata-driven configuration.

**What does it cost to read?** A new developer tracing a discount calculation through an interface, a factory, a metadata query, and a dynamically instantiated class is doing four times the work of reading one method.

Patterns are for managing change that is actually happening. Applied to code that has been stable for two years, they add indirection and remove nothing.

## Practical guidance

**Strategy for three or more real variants**, not for two branches.

**Factory driven by Custom Metadata**, so adding a variant needs no code change to existing classes.

**Null-check `Type.forName`**, and log rather than throw on an unknown class.

**Singleton for transaction-scoped caching only** — describes and configuration, never business state.

**Template Method for families** of batch jobs and handlers.

**Use platform events rather than an in-memory Observer.**

**Use a builder for test data**, not for production records.

**Count the variants before introducing a pattern.**
