# Global Error Handling

An error handling strategy answers four questions: where errors are caught, how they are classified, what the user sees, and what gets reported.

## The layers

```
Error boundaries       render-phase errors in a subtree
try/catch + hooks      event handlers, mutations
Data layer             HTTP failures, validation, aborts
Global handlers        everything the above missed
```

Each catches what the layer below cannot. None of them alone is sufficient — error boundaries miss event handlers and async code, and global handlers cannot render a fallback ([[22.1 - Error Boundaries]]).

## Classify before handling

The single most important distinction:

**Expected failures** are part of normal operation — a 404, a validation rejection, a permission denial, a user cancellation. They should be handled locally, shown in the UI, and **not** reported to monitoring.

**Unexpected failures** are bugs — a `TypeError`, a broken invariant, an unhandled state. They should be reported and degrade to a boundary.

Conflating them produces one of two outcomes: a monitoring dashboard flooded with 404s that nobody reads, or real crashes buried in that noise.

```ts
type AppError =
  | { kind: "cancelled" }                                    // ignore entirely
  | { kind: "validation"; fields: Record<string, string> }   // show inline
  | { kind: "forbidden" }                                    // show, no retry
  | { kind: "notFound" }                                     // show empty state
  | { kind: "network" | "timeout" }                          // show, offer retry
  | { kind: "server"; status: number };                      // show + report
```

Normalizing at the data layer means every consumer branches on the same shape ([[28.4 - The Data Layer]]).

## Boundary placement

```jsx
<ErrorBoundary fallback={<FullPageError />}>          {/* last resort */}
  <RouterProvider router={router} />
</ErrorBoundary>
```

```jsx
{
  path: "products",
  element: <Products />,
  errorElement: <SectionError />,      {/* navigation still works */}
}
```

```jsx
<ErrorBoundary fallback={<WidgetError />}>            {/* the rest survives */}
  <RevenueChart />
</ErrorBoundary>
```

Three tiers, each containing failure to a smaller area:

1. **Root** — catches everything, offers a reload
2. **Route** — a broken page, working navigation
3. **Widget** — independent or failure-prone sections: charts, third-party embeds, user-generated content

Do not wrap every component. Each boundary is a place the UI can silently degrade, and too many make failures invisible in testing.

Order matters with Suspense — the error boundary goes **outside**, or a failed load leaves a permanently stuck skeleton ([[19.4 - Suspense]]).

## Global handlers as the net

```ts
window.addEventListener("error", (e) => {
  report(e.error ?? new Error(e.message), { source: "window.error" });
});

window.addEventListener("unhandledrejection", (e) => {
  if (e.reason?.name === "AbortError") return;
  report(e.reason, { source: "unhandledrejection" });
});
```

These catch what boundaries structurally cannot: errors in event handlers, timers, promise chains, and third-party scripts.

Two operational notes. Filter `AbortError` explicitly, or every cancelled request becomes a reported error. And cross-origin scripts report the opaque `"Script error."` with no stack unless the tag has `crossorigin` and the response sends CORS headers ([[27.7 - Source Maps]]).

## What the user sees

```jsx
function ErrorState({ error, onRetry }) {
  const copy = {
    network: "Check your connection and try again.",
    timeout: "That took too long. Try again?",
    forbidden: "You do not have access to this.",
    notFound: "We could not find that.",
    server: "Something went wrong on our end. We have been notified.",
  }[error.kind] ?? "Something went wrong.";

  const canRetry = ["network", "timeout", "server"].includes(error.kind);

  return (
    <div role="alert">
      <p>{copy}</p>
      {canRetry && <button onClick={onRetry}>Try again</button>}
    </div>
  );
}
```

Three rules:

**Never show raw error messages.** They leak implementation details and occasionally sensitive information. Map to friendly copy and log the original.

**Always offer a next action** where one exists. A dead-end message is a dead end for the user.

**Do not offer retry where retry cannot help.** A 403 or 404 will fail identically, and the button teaches users the product is unreliable.

`role="alert"` announces the error to screen readers; a red border alone is invisible to them and to users with colour vision deficiency ([[24.2 - Loading Error and Empty States]]).

## Reporting well

```ts
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_COMMIT_SHA,
  environment: import.meta.env.MODE,
  tracesSampleRate: 0.1,

  beforeSend(event, hint) {
    const err = hint.originalException;
    if (err?.name === "AbortError") return null;
    if (err?.status === 404) return null;
    if (isKnownExtensionNoise(event)) return null;
    return event;
  },
});
```

`beforeSend` is where the noise filter lives. Without it, a dashboard fills with aborts, expected 404s, and errors thrown by browser extensions injecting scripts into the page — the last category is surprisingly large on consumer products.

Context is what makes a report actionable:

```ts
Sentry.setUser({ id: user.id });                          // never PII beyond an id
Sentry.setTag("feature", "checkout");
Sentry.addBreadcrumb({ category: "action", message: "clicked_pay" });
```

Breadcrumbs — the sequence of actions before the error — are usually more useful than the stack trace for reproducing a bug.

**Source maps are mandatory.** Without them every production stack points into `chunk-4f2a.js` and is unusable. Upload them during the build and delete them from the deployment ([[27.7 - Source Maps]]).

## Sampling and volume

A high-traffic error can generate millions of events. Sampling and rate limiting protect both cost and signal:

```ts
sampleRate: 1.0,          // errors — usually keep all
tracesSampleRate: 0.1,    // performance — sample
```

Deduplication by fingerprint is what turns a million events into one issue with a count. Grouping only works well when stack traces resolve, which brings it back to source maps.

## Recovery, not just display

```jsx
<ErrorBoundary
  onReset={() => queryClient.resetQueries({ queryKey: ["dashboard"] })}
  resetKeys={[userId]}
>
```

A fallback with a retry that immediately fails again is not recovery. Resetting the boundary must also clear whatever caused the failure — usually a cached query ([[24.7 - Caching Stale Time and Invalidation]]).

`resetKeys` recovers automatically when the relevant input changes, which handles the common case of a user navigating away from the broken state.

For chunk-load failures after a deploy, the correct recovery is a full reload to pick up the new asset manifest ([[19.3 - Code Splitting and React.lazy]]):

```js
window.addEventListener("vite:preloadError", (e) => {
  e.preventDefault();
  window.location.reload();
});
```

## Mutations need explicit handling

Query errors surface through boundaries or the query result. Mutation errors do not — a failed save with no handling is silent:

```jsx
const { mutate } = useMutation({
  mutationFn: save,
  onError: (error) => {
    if (error.kind === "validation") return setFieldErrors(error.fields);
    toast.error("Could not save. Try again.", { action: { label: "Retry", onClick: retry } });
  },
});
```

Field errors go to the form; everything else goes to a toast or a form-level region ([[21.2 - Validation Strategies]]).

A global mutation cache handler catches anything a call site forgot:

```ts
new QueryClient({
  mutationCache: new MutationCache({
    onError: (error) => { if (!error.handled) toast.error("Something went wrong"); },
  }),
});
```

## Testing the error paths

Error states are the least-tested part of most applications, because they are the hardest to trigger manually.

```ts
server.use(http.get("/api/products", () => new HttpResponse(null, { status: 500 })));
```

Network-level mocking makes every failure mode trivially reproducible, in tests and in local development ([[26.4 - Mocking the Network with MSW]]). Running the app with a handler set to fail is the fastest way to see what users actually experience.

## How senior engineers actually use this

**They separate expected from unexpected failures** and report only the latter.

**They layer boundaries** — root, route, widget — rather than one or dozens.

**They filter aborts and known noise in `beforeSend`**, so the dashboard stays readable.

**They tag errors with the release SHA**, making regressions immediately attributable.

**They pair every recovery action with cache reset**, so retry can actually succeed.

**They test error paths** with network mocking rather than hoping.

## Common pitfalls

- Expecting error boundaries to catch event handler or async errors.
- Reporting expected 404s and aborts, drowning real errors.
- Raw error messages shown to users.
- Retry offered on errors that cannot succeed.
- No source maps, making every production trace unusable.
- `"Script error."` from missing `crossorigin` on CDN scripts.
- Silent mutation failures.
- Reset without clearing the cache, so retry fails identically.

## Interview angle

"How would you handle errors across an application" is a layering question. Give the four layers and what each catches — boundaries for render errors, try/catch for handlers, the data layer for HTTP, global listeners as the net — and stress that boundaries miss event handlers and async code, which is why the global handlers are not optional. The distinction that separates strong answers is expected versus unexpected failures: one is UI, the other is a bug report, and conflating them makes monitoring useless.
