# Login Policies, MFA and Session Security

## The outermost layer

Everything in this section so far assumed the user is already logged in. This note covers the layer before that: who can authenticate, from where, when, and how the session behaves afterwards.

Developers meet these settings mostly when something breaks — an integration that suddenly fails, a user locked out, a session expiring mid-process — so knowing what they do saves real time.

## Multi-factor authentication

MFA is required for direct Salesforce logins and has been for some time. Users authenticate with a password plus a second factor: an authenticator app, a security key, or a built-in authenticator.

The important nuance for architecture: **MFA is satisfied at the identity provider when single sign-on is in use.** An organization using an external identity provider with its own MFA meets the requirement there, and Salesforce accepts the assertion.

For developers, the relevant consequences:

**Integration users do not use MFA.** They authenticate through OAuth flows — typically the JWT bearer flow for server-to-server integration — which does not involve an interactive login. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**Some operations can require a fresh MFA verification.** High-assurance sessions can be required for specific actions, which is worth knowing when a user reports being challenged unexpectedly.

## IP restrictions, in two different places

There are two IP mechanisms and they behave very differently. Confusing them is common.

**Login IP Ranges on a profile.** A hard restriction. Users on that profile can only log in from within the listed ranges. Outside them, login is refused entirely, with no way through.

**Trusted IP Ranges in Network Access.** A softening mechanism, not a restriction. Logins from within these ranges skip identity verification. Logins from outside are still permitted, but require verification — a code sent to email or a second factor.

So profile ranges *restrict*, and network ranges *relax*. Setting a profile range with the intent of "make it easier from the office" locks everyone else out, which is a well-worn mistake.

The practical implication for integrations: an integration user with profile Login IP Ranges will fail the moment the calling system's IP changes — a cloud provider reassigning addresses, a new region, a proxy change. Integration users are usually better secured through OAuth scopes, a connected app policy, and named credentials than through IP allowlisting, precisely because IPs move.

## Login hours

Set per profile, restricting the hours during which users can log in. A session active when the window closes is terminated.

Rarely appropriate for real users, and genuinely harmful for integration users, whose jobs may run overnight. Worth checking when a scheduled job mysteriously fails at a consistent time.

## Session settings

Org-wide, in Setup under Session Settings, with some settings also available per profile.

**Session timeout.** How long an idle session survives, from 15 minutes to 24 hours. Shorter is more secure and more irritating; most organizations settle between two and eight hours.

**Lock sessions to the IP address they originated from.** Strong protection against session hijacking, and a genuine problem for users on mobile networks whose IP changes, or behind load-balanced proxies.

**Lock sessions to the domain.** Generally leave on.

**Force relogin after Login-As-User.** An administrator who logs in as another user is returned to their own session on exit. Should be on.

**Clickjack protection.** Prevents Salesforce pages being framed by other sites. Should be on for all settings, and turning it off to make an embedded page work is a decision to think about carefully.

**Cross-site request forgery protection.** Adds tokens to state-changing requests. Should be on.

**Cache no-store for sensitive pages.** Prevents browser caching of pages that may contain confidential data.

## What this means for developers

**Long-running processes hitting session timeout.** A user starting a long operation and returning to an expired session. The correct fix is nearly always to move the work asynchronous and notify on completion, not to extend the timeout. See [[12.3 - Queueable Apex]].

**Callouts and session IDs.** Never pass a session ID to an external system, and never store one. Named Credentials handle authentication properly and keep credentials out of code and configuration. See [[13.13 - Named Credentials and External Credentials]].

**Guest users in Experience Cloud.** Unauthenticated visitors run as a special Guest User with its own profile and a restricted sharing model. This is the highest-risk surface on the platform, and the platform now enforces strict defaults: guest users cannot own records, their access is limited to explicitly configured sharing, and write access should generally not be granted. Any Apex reachable by a guest user needs particular scrutiny.

**Login As.** Administrators with the right permission can log in as another user, which is invaluable for reproducing an access problem. It is logged, and it should be — an unlogged or overly available Login As capability is an audit finding.

## Monitoring logins

`LoginHistory` is the record of every authentication attempt, and it is one of the more useful diagnostic objects on the platform.

```sql
SELECT UserId, LoginTime, LoginType, SourceIp, Status, Application,
       Browser, Platform, ApiType, ApiVersion
FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:7 AND Status != 'Success'
ORDER BY LoginTime DESC
```

Three things it answers well:

**Failed login patterns.** Repeated failures from an unexpected address.

**Which API versions integrations use.** `ApiVersion` on integration logins tells you what will break when Salesforce retires old versions. Worth auditing annually. See [[01.11 - Release Cycle, Trust and Status]].

**Whether an integration is actually connecting.** When a nightly job silently stops working, this is the first place to look.

`SetupAuditTrail` records configuration changes, which is the companion query for "who changed this and when":

```sql
SELECT CreatedDate, CreatedBy.Name, Action, Section, Display
FROM SetupAuditTrail
WHERE CreatedDate = LAST_N_DAYS:30 AND Section LIKE '%Sharing%'
ORDER BY CreatedDate DESC
```

For orgs with Shield, **Event Monitoring** provides far richer data — every report run, every export, every API call, every page view. See [[22.1 - Salesforce Shield Overview]] and [[20.6 - Event Monitoring and Operational Visibility]].

## Connected apps and API access

Any external application accessing Salesforce does so through a **connected app**, which defines the OAuth scopes it may request and the policies applied to it.

Policies worth knowing:

- **Permitted users** — admin-approved users only, or all users who self-authorize. Admin-approved is the right default for anything internal.
- **IP relaxation** — whether the app is subject to IP restrictions
- **Refresh token policy** — how long a refresh token remains valid, which determines how often an integration must re-authenticate
- **Session policies** — separate timeout and high-assurance requirements for that app

Getting the refresh token policy wrong is a common cause of an integration that works for ninety days and then stops. See [[13.12 - Connected Apps and Auth Providers]].

## Practical guidance

**Do not use profile Login IP Ranges for integration users.** IPs change; OAuth and connected app policies are the right control.

**Set session timeout deliberately**, and solve long-running work with async rather than a longer timeout.

**Leave clickjack and CSRF protections on.** If something breaks, fix the something.

**Audit LoginHistory for API versions once a year.** It costs ten minutes and prevents an outage when a version is retired.

**Treat guest user access as the highest-risk surface in the org**, and review any Apex it can reach as if it were a public API, because it is.
