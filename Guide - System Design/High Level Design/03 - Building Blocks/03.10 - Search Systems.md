## What It Is

A search system allows users to query a large corpus of documents by keywords, phrases, or structured filters — and receive results ranked by relevance. Unlike a database (which finds exact matches), search finds approximate, ranked matches.

```
User query: "wireless noise cancelling headphones under 5000"
→ Search engine: tokenize → lookup inverted index → rank by relevance → return top 10
```

---

## Why It Exists

SQL `LIKE '%keyword%'` doesn't scale:
- Full table scan on every query
- No relevance ranking
- No fuzzy matching, stemming, or synonym expansion
- Unusable at millions of documents

Dedicated search engines solve all of these.

---

## The Inverted Index

The core data structure of every search engine.

A forward index maps: `document → list of words`  
An inverted index maps: `word → list of documents containing it`

```
Documents:
  doc1: "the quick brown fox"
  doc2: "the quick red fox"
  doc3: "the slow brown bear"

Inverted Index:
  "quick" → [doc1, doc2]
  "brown" → [doc1, doc3]
  "fox"   → [doc1, doc2]
  "slow"  → [doc3]
  "bear"  → [doc3]
```

To find documents matching "quick brown":
1. Look up "quick" → [doc1, doc2]
2. Look up "brown" → [doc1, doc3]
3. Intersect → [doc1]

This is O(result_count), not O(corpus_size). That's why search scales.

---

## Text Processing Pipeline

Before a document enters the inverted index, text is processed:

```
Raw text: "The Quick Brown Foxes jumped over the Lazy Dog"
     ↓
Tokenization:   ["The", "Quick", "Brown", "Foxes", "jumped", "over", "the", "Lazy", "Dog"]
     ↓
Lowercasing:    ["the", "quick", "brown", "foxes", "jumped", "over", "the", "lazy", "dog"]
     ↓
Stop word removal: ["quick", "brown", "foxes", "jumped", "lazy", "dog"]
     ↓
Stemming/Lemmatization: ["quick", "brown", "fox", "jump", "lazi", "dog"]
     ↓
Index tokens:   ["quick", "brown", "fox", "jump", "lazi", "dog"]
```

**Stemming:** Reduce words to their root form. "foxes" → "fox", "running" → "run"  
**Lemmatization:** More accurate root form using vocabulary. "better" → "good"  
**Stop words:** Common words ("the", "a", "is") removed — present in nearly every document, no discriminative value

The same pipeline runs on queries. "Quick brown foxes" → ["quick", "brown", "fox"] → same tokens as in the index.

## Relevance Ranking

Returning results isn't enough — they must be ranked by relevance. The core algorithm is **TF-IDF** (with BM25 as the modern refinement).

### TF-IDF

**TF (Term Frequency):** How often does the term appear in this document?  
More occurrences → document is more about this term.

```
TF("fox", doc1) = count("fox" in doc1) / total words in doc1
```

**IDF (Inverse Document Frequency):** How rare is the term across all documents?  
Rare terms are more discriminative than common ones.

```
IDF("fox") = log(total_docs / docs_containing_"fox")
```

**TF-IDF score** = TF × IDF  
High score = term appears often in this document AND is rare across the corpus = strong relevance signal.

### BM25

The modern replacement for TF-IDF. Adds two improvements:
1. **Term frequency saturation:** Having "fox" 100 times isn't 100× better than having it 10 times
2. **Document length normalization:** Long documents naturally contain more terms — normalize for fairness

BM25 is the default ranking function in Elasticsearch and Solr.

## Elasticsearch Architecture

Elasticsearch is the dominant open-source search engine. Understanding its architecture helps design search systems.

### Concepts

**Index:** Analogous to a database table. Contains documents of similar type.

**Document:** A JSON object that is indexed and searchable.

**Shard:** An index is split into shards (each shard is a Lucene index). Enables horizontal scaling.

```
Index: "products" (5 shards × 1 replica)
  Shard 0 → Node 1 (primary), Node 2 (replica)
  Shard 1 → Node 2 (primary), Node 3 (replica)
  Shard 2 → Node 3 (primary), Node 1 (replica)
  ...
```

**Node types:**
- Master node: manages cluster state, shard allocation
- Data node: stores shards, executes queries
- Coordinating node: receives queries, fans out to shards, aggregates results

### Query Flow

```
Client → Coordinating Node
              │
              ├──→ Shard 0 (partial results)
              ├──→ Shard 1 (partial results)
              └──→ Shard 2 (partial results)
              │
              ← merge, re-rank, return top N
```

Each shard ranks its local documents. Coordinating node merges the top results globally.

## Sync: Primary DB → Search Index

Search engines are never the source of truth. Data lives in the primary DB; search is a derived read model.

**The pipeline:**

```
Write → Primary DB → [Change capture] → Search Index
```

### Approaches

**Synchronous dual-write (simple, risky):**
```python
def create_product(data):
    db.insert(data)
    elasticsearch.index(data)  # if this fails, DB and search diverge
```

**Async via message queue (preferred):**
```
Write → DB → Outbox/CDC → Kafka → Search Indexer → Elasticsearch
```

Change Data Capture (CDC) tools like Debezium read the DB's WAL and emit change events to Kafka. The search indexer consumes these and updates Elasticsearch. Eventual consistency — slight lag between DB write and search visibility.

**Periodic bulk sync:**
Run a batch job every N minutes to sync recent changes. Simple but adds latency (up to N minutes for new content to appear in search).

## Typeahead / Autocomplete

A specialized search problem: given a prefix, suggest completions in < 50ms.

**Approach 1: Prefix trie in Redis**
```
Trie: {"a": {"p": {"p": {"l": {"e": [doc1, doc5]}}}}}
Query "app" → walk trie → suggestions
```

**Approach 2: Elasticsearch completion suggester**
Uses a dedicated in-memory data structure optimized for prefix queries.

**Approach 3: N-gram indexing**
Index all prefixes of each term: "apple" → ["a", "ap", "app", "appl", "apple"]. Prefix query is a standard term lookup.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Indexing pipeline lag | New content not searchable | Monitor lag, alert on delay > threshold |
| Search index and DB diverge | Stale/incorrect search results | Periodic full re-index, reconciliation job |
| Shard becomes unavailable | Some results missing | Replica shards, multi-AZ nodes |
| Mapping conflict | New fields rejected by index | Use dynamic mapping or update mapping before deploy |
| Query timeout | Slow queries block resources | Set timeout per query, paginate results |
