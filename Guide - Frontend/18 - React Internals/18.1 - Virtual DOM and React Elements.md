# Virtual DOM and React Elements

The "virtual DOM" is not a technology or a data structure with a formal definition. It is a **pattern**: keep a lightweight description of the desired UI in memory, compare it with the previous description, and apply only the differences to the real DOM.

## A React element is a plain object

```jsx
const el = <div className="card">Hello</div>;
```

produces:

```js
{
  $$typeof: Symbol.for("react.element"),
  type: "div",
  key: null,
  ref: null,
  props: { className: "card", children: "Hello" },
}
```

Cheap to create, immutable, and disposable. It describes what should be on screen; it is not on screen.

`type` is either a **string** for a host element (`"div"`, `"input"`) or a **function/class** for a component.

The `$$typeof` symbol is a security measure. Because it is a registered symbol ([[03.6 - Symbols and Well Known Symbols]]) and JSON cannot contain symbols, a malicious API response cannot masquerade as a React element and get rendered — closing an XSS vector that existed before it was added.

## Elements are immutable

```jsx
const el = <div />;
el.props.className = "x";   // frozen in development, ignored in production
```

To change the UI you create new elements, not mutate old ones. This is what makes comparing the previous and next trees meaningful — if elements were mutable, the "previous" tree would already reflect the change.

## Why the tree is not the DOM

Creating a DOM node is expensive: it allocates in the browser's C++ heap, participates in layout, and carries hundreds of properties. Creating a JavaScript object is cheap.

So React can afford to re-describe the entire UI on every state change and then compute a minimal set of DOM operations. The cost model is:

```
re-run component functions   (cheap — plain JS)
diff element trees           (cheap — object comparison)
apply DOM mutations          (expensive — but minimal)
```

The naive alternative — rebuild the DOM from scratch — would be correct but would destroy focus, scroll position, selection and input state, and would be slow ([[12.1 - The DOM Tree and Node APIs]]).

## The virtual DOM is not "fast"

Worth stating plainly because it is commonly misrepresented.

Hand-written optimal DOM updates are **faster** than React. Diffing is work that `node.textContent = x` does not do.

What React provides is a model where you never have to write those optimal updates, and the overhead of the diff is small enough that the result is fast **enough**. The value is in the constraint being cheap, not in raw throughput ([[16.1 - Why React]]).

Fine-grained reactive frameworks — Solid, Svelte, Vue's Vapor mode — skip the diff entirely by compiling the template into targeted updates at build time. They are measurably faster on update benchmarks. React's counter-argument is that a runtime tree representation is what makes concurrent rendering, Suspense and Server Components tractable.

## Elements versus components versus instances

```jsx
function Button({ label }) { return <button>{label}</button>; }   // component (function)

const element = <Button label="Save" />;                           // element (description)

// fiber: React's internal instance with state, hooks and DOM links
```

Three distinct things:

- **Component** — the function you wrote.
- **Element** — an object describing that a component should render with certain props. Creating one runs nothing.
- **Fiber** — React's persistent internal record for a position in the tree, holding hooks, state, effects and the DOM node ([[18.3 - Fiber Architecture]]).

Elements are recreated every render; fibers persist across renders. This distinction explains why state survives re-renders but not remounts.

It also explains a common mistake:

```jsx
<Component />       // element → real fiber, own state
{Component()}       // function call → hooks join the PARENT's list
```

## Elements as values

Because elements are ordinary objects, they can be stored, passed and compared:

```jsx
const header = <Header user={user} />;

<Layout header={header}>{content}</Layout>
```

`header` is created in the parent's render. When `Layout` re-renders for its own reasons, `header` is the same reference, so React skips re-rendering that subtree during reconciliation. This is why passing elements as props is a genuine performance technique, not just an organizational one ([[16.3 - Components and Props]]).

The same property makes `React.memo` work: memo compares props, and an unchanged element reference passes the comparison ([[19.2 - React.memo and Memoization Strategy]]).

## Inspecting elements

```jsx
console.log(<div className="a"><span /></div>);
```

The `children` prop holds nested elements, so the whole tree is inspectable as plain data. Useful when debugging what a component actually returns.

`React.Children` provides utilities for working with the children prop safely:

```jsx
React.Children.count(children);
React.Children.map(children, child => React.cloneElement(child, { extra: true }));
React.Children.toArray(children);   // flattens, assigns keys, removes null
```

`cloneElement` and `Children` manipulation are legacy patterns — the modern equivalents are context or render props ([[22.6 - Compound Components]]). They still appear in older component libraries.

## The rendering pipeline

```
JSX
  ↓ compile
createElement / jsx()
  ↓
element tree (plain objects)
  ↓ reconciliation
fiber tree (persistent, with state)
  ↓ commit
DOM
```

Reconciliation is the diff ([[18.2 - Reconciliation and the Diffing Algorithm]]); the fiber tree is what makes it interruptible ([[18.4 - Render Phase vs Commit Phase]]).

## How senior engineers actually use this

**They know elements are cheap and DOM nodes are not**, which is why "re-render" is not synonymous with "DOM update" — a re-render that produces identical elements results in zero DOM work.

**They use element identity deliberately.** Passing elements as props or children is a first-class technique for avoiding re-renders.

**They correct the "virtual DOM is fast" claim** when it comes up, because believing it leads to the wrong optimization decisions.

**They avoid `cloneElement`** in new code, preferring context.

## Common pitfalls

- Believing a re-render means DOM manipulation happened.
- Mutating props or elements.
- Calling a component as a function instead of rendering it.
- Assuming the virtual DOM makes React faster than direct DOM work.
- Using `React.Children.map` and `cloneElement` where context is clearer.

## Interview angle

"What is the virtual DOM" is asked constantly and usually answered shallowly. The strong answer: React elements are plain immutable objects describing the intended UI, cheap to create and throw away; React diffs the new description against the previous one and applies minimal DOM mutations. Then the correction — this is not faster than optimal manual DOM work, it makes a declarative model fast enough — followed by the element/component/fiber distinction. That combination is well above the typical response.
