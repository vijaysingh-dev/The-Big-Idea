# Graceful Degradation

#backend #reliability #design

> **In one line:** Deciding in advance which features to sacrifice means an outage becomes a worse product rather than no product — and the decision is a product decision, not a technical one.

---

## The Idea

```
All-or-nothing:  the search service is down → the page returns 500
Degraded:        the search service is down → the page loads, search says "unavailable"
```

💡 **Every dependency should have a documented answer to "what do we do without it".** The answer can be "fail" — for authorisation it must be — but it should be a decision, not an accident.

⚠️ **The default is propagation.** A caller that does not handle a dependency's failure passes it upward, which is how one optional service takes down a whole page.

---

## Required versus Optional

```python
async def get_document_page(doc_id: str) -> DocumentPage:
    doc = await documents.get(doc_id)                        # required
    author = await users.get(doc.author_id, required=False)  # optional
    related = await search.similar(doc_id, required=False)   # optional
    annotations = await annotations.list(doc_id)             # required

    return DocumentPage(
        document=doc,
        author=author or UnknownAuthor(),
        related=related or [],
        annotations=annotations,
    )
```

💡 **Marking it in the call signature makes the decision visible in code review.** A new dependency added without a `required=` argument should be a review comment.

| Dependency | Required if |
|---|---|
| **Authorisation** | **Always.** Fail closed |
| Payment | For a purchase |
| The primary entity | The page is about it |
| Enrichment (author name, related items) | Never |
| Analytics, telemetry | Never |
| Recommendations | Never |
| Search | **Depends** — required on the search page, optional elsewhere |

⚠️ **The same dependency can be required in one context and optional in another**, which means "required" is a property of the call site, not the service.

## The Degradation Ladder

Define levels before the incident, not during it.

```
Level 0  Full service
Level 1  Disable recommendations, related items, analytics
Level 2  Serve stale cached data; disable personalisation
Level 3  Read-only; reject writes
Level 4  Static maintenance page
```

💡 **Levels 3 and 4 are the ones nobody builds and the ones that save you.** Read-only mode means a database primary failure degrades to browsing rather than a total outage.

```python
class ServiceLevel(IntEnum):
    FULL = 0
    NO_ENRICHMENT = 1
    STALE_OK = 2
    READ_ONLY = 3
    MAINTENANCE = 4


async def current_level() -> ServiceLevel:
    if manual_override := await flags.get("service_level"):
        return ServiceLevel(manual_override)
    if not await db.primary_healthy():
        return ServiceLevel.READ_ONLY
    if await db.pool_pressure() > 0.9:
        return ServiceLevel.STALE_OK
    return ServiceLevel.FULL
```

⚠️ **A manual override is essential.** During an incident you want to drop a level immediately, without waiting for automation to notice or deploying a change ([[10.8 - Configuration and Secrets]]).

### Read-only mode

```python
@app.middleware("http")
async def enforce_read_only(request: Request, call_next):
    if await current_level() >= ServiceLevel.READ_ONLY and request.method not in SAFE_METHODS:
        return JSONResponse(503, {"type": ".../read-only", "retry_after_seconds": 60})
    return await call_next(request)
```

💡 **Read-only mode is achievable with a replica** ([[06.12 - Replication and Failover]]) and it converts a primary failure from total outage into degraded service.

⚠️ **Test it.** A read-only mode that has never been exercised will have a write path nobody flagged — a last-seen timestamp, an audit log, a session refresh.

**Run it in production for ten minutes on a quiet Sunday.** You will find three write paths you did not know about.

## Serving Stale Data

```python
async def get_with_stale_fallback(key: str, loader, ttl: int, stale: int):
    entry = await redis.get(key)
    if entry and entry.is_fresh():
        return entry.value

    try:
        return await load_and_cache(key, loader, ttl + stale)
    except Exception:
        if entry:
            stale_served_total.inc()
            return entry.value                     # ← stale, and better than nothing
        raise
```

💡 **Keeping data in the cache past its logical freshness gives you something to serve when the source fails** ([[07.3 - Stampede Hot Keys and Negative Caching]]).

⚠️ **Tell the user.** A page silently showing five-minute-old data is worse than one saying "showing cached results from 14:32" — because the second is a known state and the first is a lie.

```json
{"data": [...], "stale": true, "as_of": "2026-08-17T14:32:00Z"}
```

**For anything financial, authorisation-related, or where staleness is dangerous, do not do this.**

## Fallbacks Can Make It Worse

⚠️ **The counterintuitive point, and it is important.**

```python
try:
    return await primary_search()
except Exception:
    return await fallback_search()        # ← a different, slower code path
```

| Problem | |
|---|---|
| **The fallback is never exercised** | It is broken and you find out during an incident |
| **The fallback has different capacity** | It was sized for 1% of traffic, now it gets 100% |
| The fallback shares the failing dependency | It fails too |
| **The fallback path is slower** | It makes the overload worse |

💡 **AWS's position: prefer no fallback to an untested one.** A fallback that fails during an incident adds latency and confusion to an outage that was already happening.

**The safe forms of degradation are the ones that do *less*, not the ones that do something different:**

| Safe | Risky |
|---|---|
| Return an empty list | Call a different service |
| Return a cached value | Compute it a different way |
| Omit a field | Fall back to a secondary database |
| Return a static default | Retry against a different region |

⚠️ **If you do build a real fallback, exercise it continuously** — route 1% of traffic to it permanently, so you know it works.

## Load Shedding as Degradation

```python
async def should_serve(request: Request) -> bool:
    level = await current_level()
    priority = classify(request)

    if level >= ServiceLevel.STALE_OK and priority == Priority.BACKGROUND:
        return False
    if level >= ServiceLevel.READ_ONLY and priority < Priority.CRITICAL:
        return False
    return True
```

💡 **Shed by priority, not randomly** ([[11.4 - Backpressure and Load Shedding]]).

```
CRITICAL     health checks, auth, payment
HIGH         interactive user requests
NORMAL       list views, search
BACKGROUND   prefetch, analytics, recommendations
```

⚠️ **Classify requests at the edge**, where you can reject cheaply. Classifying after authentication and a database lookup means you paid most of the cost before deciding not to serve.

## In Production

### The dependency matrix

For every dependency, in a document:

```markdown
| Dependency | Required? | If slow | If down | Tested |
|---|---|---|---|---|
| Postgres primary | Yes (writes) | Shed load | **Read-only mode** | ✅ |
| Postgres replica | No | Use primary | Use primary | ✅ |
| Redis | No | Bulkhead, skip cache | Skip cache, 20× DB load ⚠️ | ✅ |
| Search | Contextual | Circuit opens | "Search unavailable" | ✅ |
| Auth | **Yes** | Fail closed | **Total outage** | ✅ |
| Embedding API | No | Queue grows | Ingestion stalls | ✅ |
| Object storage | Yes (uploads) | Slow uploads | Uploads rejected, reads cached | ✅ |
```

⚠️ **The "Tested" column is the one that matters.** An untested degradation path is a hypothesis.

💡 **The Redis row is the one to look at hardest.** "Skip cache" sounds harmless and it means your database takes 20× its normal load ([[07.1 - Cache Layers Across One Request]]). **That is only survivable with headroom or load shedding**, and it must be tested at production load.

### Making degradation visible

```python
degradation_level.set(int(level))
degraded_responses_total.labels(reason="search_unavailable").inc()
stale_data_served_total.labels(dataset=d).inc()
requests_shed_total.labels(priority=p).inc()
```

💡 **`degraded_responses_total` by reason is the metric that tells you which dependency is hurting users right now**, and it is more actionable than a raw error rate because it names the cause.

⚠️ **A system that degrades silently looks healthy.** Error rates stay low, latency is fine, and users are getting a worse product. **Alert on sustained degradation**, not only on errors.

### Telling the user

```
❌  A blank section where search results should be
❌  "An error occurred"
✅  "Search is temporarily unavailable. Documents are still accessible."
✅  "Showing cached results from 14:32."
✅  "The system is in read-only mode for maintenance. Editing will return shortly."
```

💡 **A user who knows what is broken and what still works can carry on.** A user facing an ambiguous failure retries, contacts support, and assumes everything is broken.

⚠️ **This is product work, not just engineering.** The degraded states need designs, copy, and someone to have thought about them — which is why the ladder must be agreed before the incident.

### Testing it

```python
@pytest.mark.parametrize("dep", ALL_DEPENDENCIES)
async def test_degrades_when_dependency_down(dep, toxiproxy):
    await toxiproxy.disable(dep)
    r = await api.get("/documents/doc_42")

    if dep in REQUIRED_DEPENDENCIES:
        assert r.status_code >= 500
    else:
        assert r.status_code == 200
        assert r.json()["degraded"] is True
```

💡 **A parameterised test over every dependency is how you keep the matrix honest** ([[10.9 - Testing Microservices]]). Adding a dependency without a degradation decision fails the test.

**Then the slow case**, which is different and usually worse:

```python
await toxiproxy.add_latency(dep, 10_000)
assert (await api.get("/documents/doc_42")).elapsed < timedelta(seconds=2)
```

⚠️ **Degrading on a down dependency is easy; degrading on a slow one requires the timeout and circuit breaker to work** ([[11.2 - Timeouts Retries and Jitter]], [[11.3 - Circuit Breakers and Bulkheads]]).

### The game day

💡 **Once a quarter, take a dependency down in production during low traffic and confirm the degradation works.**

```
1. Announce it
2. Take Redis down for 5 minutes
3. Watch: error rate, database load, degradation metrics, user reports
4. Restore
5. Write down what surprised you
```

⚠️ **Something always surprises you**, and finding it deliberately at 10am is better than accidentally at 3am ([[11.9 - Chaos and Failure Injection]]).

### Conduit's ladder

| Level | Trigger | Behaviour |
|---|---|---|
| **0 — Full** | Normal | Everything |
| **1 — No enrichment** | Search circuit open, or Redis down | No related documents, no recommendations, no cached enrichment |
| **2 — Stale OK** | Database pool pressure > 80% | Serve cached data past freshness, disable non-essential queries |
| **3 — Read-only** | Primary unavailable | Reads from a replica; writes rejected with a clear message; ingestion queued |
| **4 — Maintenance** | Manual only | Static page |

💡 **Level 3 is the valuable one.** A Postgres primary failure with a healthy replica becomes "you can read your documents, editing is temporarily unavailable" rather than a blank page ([[06.12 - Replication and Failover]]).

⚠️ **Ingestion queues rather than fails at level 3.** Documents uploaded during the degradation are processed when writes return, and the user is told so — which is much better than rejecting them.

**Every level has a manual override**, so an operator can drop to level 2 immediately when the database looks unhappy, without waiting for automation.

## Codebase

**Repo:** `Netflix/Hystrix` (archived), `aws` (Builders' Library), `saleor/saleor`

**Question to answer:** How does Hystrix model fallbacks, and what does it do when the fallback also fails? Then: what is AWS's argument against fallbacks, and which forms of degradation do they consider safe?

**Read, in order:**

1. **AWS Builders' Library — "Avoiding fallback in distributed systems"** — **read this first.** The argument that untested fallbacks make outages worse, with concrete examples. **The answer to the second question**
2. `Netflix/Hystrix/wiki/How-it-Works` — the command model, fallback chain, and what happens on fallback failure. **Archived, and still the clearest statement of the pattern**
3. `Netflix/Hystrix` — `HystrixCommand.getFallback` and the `FALLBACK_FAILURE` / `FALLBACK_REJECTION` states. **Note that Hystrix bounds fallback concurrency separately**, which prevents the fallback from consuming the resources the primary needed
4. **Google SRE Book — "Handling Overload"** and **"Addressing Cascading Failures"** — graceful degradation and load shedding as a system property
5. `saleor/saleor/plugins/manager.py` — how a plugin failure is contained rather than propagated

💡 The Hystrix detail worth stealing: **the fallback has its own bounded thread pool.** If the primary is failing and every request falls back, the fallback cannot consume unbounded resources — it sheds too. **Most hand-rolled fallbacks miss this and turn one saturated path into two.**

**Size:** 1 session.

**Part 1 — The matrix.** For every dependency at every call site, decide required or optional.

Then the parameterised test: **for each dependency, down and slow, assert the correct behaviour.**

**Run it and fix what fails.** Most codebases fail the "slow" half.

**Part 2 — The ladder.** Implement all five levels with automatic triggers and a manual override.

Test each transition: **confirm the right features disappear and the right ones remain.**

Then implement read-only mode and **find every write path it missed** — run your full test suite in read-only mode and see what breaks.

**Report how many write paths you did not know about.**

**Part 3 — Stale data.** Serve-stale-on-failure for three datasets.

Take the source down and confirm stale data is served. **Then confirm the response marks it as stale and the UI shows it.**

Then measure: how long can you serve stale before it becomes wrong? **Set the hard expiry from that number**, not from convenience.

**Part 4 — The fallback trap.** Build a fallback search path that queries the database directly instead of the search service.

**Never exercise it.** Then take search down and see what happens — the fallback will have a bug.

Then measure capacity: the fallback was sized for occasional use, now it gets 100% of search traffic. **Confirm it saturates the database.**

Then implement it with a bounded pool that sheds. **Confirm the fallback degrades rather than taking the database down.**

Then route 1% of traffic to it permanently and confirm it stays working.

**Part 5 — The Redis outage.** Steady load with a 95% cache hit rate. Kill Redis.

**Measure the database load spike.** Chart database CPU, pool wait time, and application p99.

**Determine whether you survive.** If not, implement: load shedding at the pool-pressure threshold, a small local fallback cache, and request coalescing.

**Re-run and confirm survival.** This is the most important test in the drill.

**Part 6 — Degradation observability.** Instrument the level, degraded responses by reason, stale data served, and shed requests.

Then degrade one dependency and **confirm the dashboard shows which one and what users are losing** — not just that the error rate is normal.

**Part 7 — The game day.** Write the runbook, then execute it against your staging environment at production-like load.

Take each dependency down in turn for five minutes. **Record what surprised you for each.**

**Fix the surprises**, then repeat until nothing surprises you.

**Done when:**
- Every dependency has a required/optional decision, tested down and slow
- Read-only mode revealed write paths you did not know about
- Stale data is served and visibly marked
- An unexercised fallback was broken, and a bounded one degraded safely
- You know whether you survive a Redis outage at production load
- Your dashboard names the degraded feature, not just an error rate
- A full game day produced no surprises on the second run
