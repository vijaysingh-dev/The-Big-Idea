# Scheduled Apex

## The interface

```java
public with sharing class ClaimReconciliationScheduler implements Schedulable {

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(new ClaimReconciliationBatch(), 200);
    }
}
```

One method. The overwhelmingly common pattern is that the scheduler does nothing but start a batch job — the scheduled transaction itself has ordinary synchronous limits, so any real work belongs in a batch.

A class can implement both, which keeps related code together:

```java
public with sharing class ClaimReconciliationBatch
    implements Database.Batchable<SObject>, Database.Stateful, Schedulable {

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 200);
    }

    public Database.QueryLocator start(Database.BatchableContext ctx) { }
    public void execute(Database.BatchableContext ctx, List<SObject> scope) { }
    public void finish(Database.BatchableContext ctx) { }
}
```

The two `execute` methods coexist because their signatures differ.

## Scheduling

**Through Setup** — Apex Classes, then Schedule Apex. Simple, and the schedule is not in source control.

**Through code**, with a cron expression:

```java
// Every day at 02:00
System.schedule(
    'Claim Reconciliation Daily',
    '0 0 2 * * ?',
    new ClaimReconciliationBatch()
);
```

The cron format is `Seconds Minutes Hours Day_of_month Month Day_of_week Optional_year`.

```
0 0 2 * * ?          daily at 02:00
0 0 2 ? * MON-FRI    weekdays at 02:00
0 0 */4 * * ?        every four hours
0 30 1 1 * ?         the 1st of each month at 01:30
0 0 22 ? * SAT       Saturdays at 22:00
```

`?` means "no specific value" and is required in one of the day fields, since specifying both day-of-month and day-of-week is ambiguous.

`System.schedule` returns the `CronTrigger` Id.

## The hourly floor

**The finest granularity the scheduler supports is hourly.** There is no every-fifteen-minutes option.

Three workarounds:

**Several schedules at offsets** — four jobs at 0, 15, 30, and 45 minutes past. Crude, effective, and it consumes four of the 100 scheduled job slots.

```java
System.schedule('Claim Sync :00', '0 0 * * * ?', new ClaimSyncScheduler());
System.schedule('Claim Sync :15', '0 15 * * * ?', new ClaimSyncScheduler());
System.schedule('Claim Sync :30', '0 30 * * * ?', new ClaimSyncScheduler());
System.schedule('Claim Sync :45', '0 45 * * * ?', new ClaimSyncScheduler());
```

**A self-rescheduling job**, which reschedules itself for a few minutes ahead:

```java
public with sharing class FrequentSyncScheduler implements Schedulable {

    private static final Integer INTERVAL_MINUTES = 5;

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(new ClaimSyncBatch(), 200);

        // abort and reschedule, since a job cannot change its own schedule in place
        System.abortJob(ctx.getTriggerId());

        Datetime next = Datetime.now().addMinutes(INTERVAL_MINUTES);
        String cron = '0 ' + next.minute() + ' ' + next.hour() + ' '
            + next.day() + ' ' + next.month() + ' ? ' + next.year();

        System.schedule('Frequent Sync ' + next.getTime(), cron, new FrequentSyncScheduler());
    }
}
```

Elegant and fragile. The chain breaks silently if one execution fails before rescheduling, and it accumulates `CronTrigger` records. Anything using this needs monitoring that detects the chain stopping.

**Platform events or a scheduled path on a flow**, where the timing is per record rather than a sweep. Usually the better answer when the requirement is "do something to this record in twenty minutes". See [[07.3 - Record-Triggered Flows]].

## Managing scheduled jobs

```sql
SELECT Id, CronJobDetail.Name, CronExpression, State,
       NextFireTime, PreviousFireTime, TimesTriggered
FROM CronTrigger
WHERE State != 'DELETED'
ORDER BY NextFireTime
```

`State` values: `WAITING`, `ACQUIRED`, `EXECUTING`, `COMPLETE`, `ERROR`, `DELETED`, `PAUSED`.

```java
System.abortJob(cronTriggerId);
```

Aborting is how a schedule is removed programmatically, and it is the only way to change one — a scheduled job's cron expression cannot be edited in place.

## The deployment problem

**A scheduled Apex class cannot be modified while a schedule exists for it.** Attempting to deploy throws.

This is the most common operational friction with Scheduled Apex, and it shapes the deployment process:

1. Abort the scheduled job
2. Deploy the class
3. Reschedule

Which means the schedule is part of the deployment, not a one-time setup.

Two ways to reduce the pain:

**Keep the scheduler class trivial.** A scheduler that only calls `Database.executeBatch(new SomeBatch())` rarely changes. The batch class, which changes often, is not itself scheduled and deploys freely.

```java
// This class almost never changes, so it rarely blocks a deployment
public with sharing class NightlyJobScheduler implements Schedulable {
    public void execute(SchedulableContext ctx) {
        Database.executeBatch(new ClaimReconciliationBatch(), 200);
    }
}
```

**Automate the abort and reschedule** in a post-deployment script:

```java
// Anonymous Apex, run after deployment
for (CronTrigger ct : [
    SELECT Id FROM CronTrigger
    WHERE CronJobDetail.Name LIKE 'Claim Reconciliation%' AND State != 'DELETED'
]) {
    System.abortJob(ct.Id);
}

System.schedule('Claim Reconciliation Daily', '0 0 2 * * ?', new ClaimReconciliationBatch());
```

Making this part of the CI pipeline rather than a manual step is what stops schedules silently disappearing after a release. See [[21.8 - CI-CD Pipelines]].

## Running user and time zone

**A scheduled job runs as the user who scheduled it**, with their permissions, their sharing, and **their time zone**.

The time zone matters more than people expect. A job scheduled at 02:00 by a user in Mumbai runs at 02:00 IST. If that user's time zone changes, or they leave and the job is rescheduled by someone in London, the job runs at a different absolute time.

For a nightly job in a global org, this is worth being deliberate about — scheduling as a dedicated integration user with a fixed time zone removes the dependency on an individual.

**If the scheduling user is deactivated**, the job may fail or run with unexpected permissions. Scheduling under a service account rather than a person avoids the whole class of problem.

## Limits

- **100 scheduled Apex jobs** at once
- Scheduled execution counts toward the **250,000 daily async executions**
- **5 batch jobs** queued or active at once, so scheduled batches queue behind each other

That last point causes a specific and common failure: six nightly jobs all scheduled for 02:00. Five start, the sixth waits, and if the first five are slow the sixth runs at 05:00 — or after the business day has started.

**Stagger scheduled jobs.** 02:00, 02:30, 03:00, rather than all at once.

## Idempotency

A scheduled job runs unattended, and it will occasionally run twice — a manual trigger during an incident, an overlapping schedule, a rerun after a failure.

Building idempotency in is not optional:

```java
public Database.QueryLocator start(Database.BatchableContext ctx) {
    return Database.getQueryLocator([
        SELECT Id, AccountId, EndDate, Annual_Value__c, OwnerId
        FROM Contract
        WHERE Status = 'Activated'
          AND EndDate = NEXT_N_DAYS:120
          AND Renewal_Opportunity__c = null
    ]);
}
```

The `Renewal_Opportunity__c = null` filter means a second run creates nothing, because the first run populated it. This is the same guard as the renewal job in [[04.11 - Quotes, Orders and Contracts]], and every scheduled job that creates records needs one.

Without it, a rerun duplicates everything, and the cleanup is manual.

## Monitoring

Scheduled jobs fail silently by default. What is worth having:

```sql
SELECT Id, ApexClass.Name, Status, ExtendedStatus, NumberOfErrors,
       CreatedDate, CompletedDate
FROM AsyncApexJob
WHERE JobType IN ('BatchApex', 'ScheduledApex')
  AND Status IN ('Failed', 'Aborted')
  AND CreatedDate = LAST_N_DAYS:7
```

A daily check on that query, sent somewhere a human reads, is the difference between noticing a failure and discovering it three weeks later during reconciliation.

Better still, a `Batch_Run_Log__c` record written in `finish`, with a dashboard showing the last run time and outcome per job. A job that has not run in four days is as important a signal as one that failed.

## Scheduled Apex versus scheduled flow

Both run on a clock. The distinction from [[07.6 - Scheduled and Autolaunched Flows]]:

**Scheduled flow** runs the flow once per matching record and queries per record inside it. Fine for thousands, not for hundreds of thousands.

**Scheduled Apex starting a batch** receives records in collections and queries once per chunk. The right tool at volume.

The signal to switch: a scheduled flow starting to fail intermittently as data grows.

## Practical guidance

**Keep the scheduler class trivial**, so it rarely blocks deployments.

**Automate abort-and-reschedule** in the deployment pipeline.

**Schedule as a service account**, not a person, for time zone and deactivation reasons.

**Stagger schedules**, given the 5-concurrent-batch limit.

**Make every job idempotent.** It will run twice eventually.

**Log every run**, and alert on both failures and jobs that stopped running.

**Use offset schedules or platform events** for sub-hourly needs, rather than a self-rescheduling chain, unless you are prepared to monitor the chain.
