# Typing Events, Refs and Hooks

## Events

```tsx
function Form() {
  const handleClick = (e: React.MouseEvent<HTMLButtonElement>) => {};
  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {};
  const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => {};
  const handleKey = (e: React.KeyboardEvent<HTMLInputElement>) => {};
}
```

The element type parameter is what makes `e.currentTarget` correctly typed:

```tsx
const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  e.currentTarget.value;   // string
  e.target.value;          // also string here, but see below
};
```

**`currentTarget` versus `target`.** `currentTarget` is the element the handler is attached to and is precisely typed. `target` is whatever was actually clicked — which for a button containing a `<span>` is the span. React types `target` as `EventTarget`, so it needs narrowing:

```tsx
if (e.target instanceof HTMLInputElement) {
  e.target.value;
}
```

Prefer `currentTarget` unless you specifically need the origin ([[12.3 - The Event Model]]).

Inline handlers infer automatically:

```tsx
<input onChange={(e) => setValue(e.currentTarget.value)} />   // e is typed
```

Only handlers declared separately need the annotation. The `*EventHandler` aliases are the shorter form:

```tsx
const handleClick: React.MouseEventHandler<HTMLButtonElement> = (e) => {};
```

The full set: `MouseEvent`, `ChangeEvent`, `FormEvent`, `KeyboardEvent`, `FocusEvent`, `PointerEvent`, `TouchEvent`, `WheelEvent`, `DragEvent`, `ClipboardEvent`, `AnimationEvent`, `TransitionEvent`.

Native (non-React) listeners use the DOM types instead:

```tsx
useEffect(() => {
  const handler = (e: KeyboardEvent) => {};   // global KeyboardEvent, not React's
  window.addEventListener("keydown", handler);
  return () => window.removeEventListener("keydown", handler);
}, []);
```

Mixing the two is a frequent confusion — `React.KeyboardEvent` and the DOM `KeyboardEvent` are different types.

## Refs

Two distinct forms, and TypeScript enforces the difference:

```tsx
const inputRef = useRef<HTMLInputElement>(null);      // RefObject — readonly .current
const timerRef = useRef<number | null>(null);         // MutableRefObject — assignable
const countRef = useRef(0);                            // MutableRefObject<number>
```

`useRef<T>(null)` produces a ref intended for React to populate, so `.current` is readonly in the type. `useRef<T | null>(null)` produces one you assign yourself.

DOM refs are always `null` during render and until commit, so access needs a guard:

```tsx
useEffect(() => {
  inputRef.current?.focus();
}, []);
```

Finding the right element type:

```tsx
import type { ElementRef } from "react";

const divRef = useRef<ElementRef<"div">>(null);        // HTMLDivElement
const videoRef = useRef<ElementRef<"video">>(null);    // HTMLVideoElement
```

`ElementRef<"tag">` avoids guessing between `HTMLDivElement`, `HTMLAnchorElement` and the less obvious ones.

Callback refs:

```tsx
const measureRef = useCallback((node: HTMLDivElement | null) => {
  if (node) setHeight(node.getBoundingClientRect().height);
}, []);
```

The `| null` is required — React calls the callback with `null` on unmount ([[17.8 - useRef]]).

An imperative handle needs an exported type:

```tsx
export type PlayerHandle = { play: () => void; pause: () => void };

const playerRef = useRef<PlayerHandle>(null);
```

## useState

```tsx
const [count, setCount] = useState(0);                    // number, inferred
const [user, setUser] = useState<User | null>(null);      // explicit — null infers as null
const [items, setItems] = useState<Item[]>([]);           // explicit — [] infers as never[]
```

Two cases always need the generic: initializing with `null` and initializing with an empty array. Without it, `useState([])` gives `never[]` and every `push` fails.

The setter type when passing it down:

```tsx
type Props = { setUser: React.Dispatch<React.SetStateAction<User | null>> };
```

`SetStateAction<T>` is `T | ((prev: T) => T)`, covering both the value and updater forms ([[17.2 - useState in Depth]]).

## useReducer

```tsx
type State = { count: number; status: "idle" | "loading" };

type Action =
  | { type: "increment"; by: number }
  | { type: "reset" }
  | { type: "setStatus"; status: State["status"] };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "increment":
      return { ...state, count: state.count + action.by };
    case "reset":
      return { ...state, count: 0 };
    case "setStatus":
      return { ...state, status: action.status };
  }
}

const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: "increment", by: 1 });      // `by` required
dispatch({ type: "reset" });                  // `by` would be an error
```

A discriminated union of actions gives per-case narrowing inside the reducer and payload checking at every dispatch site — the strongest argument for `useReducer` in a typed codebase ([[17.10 - useReducer]]).

Note `State["status"]` reuses the union rather than duplicating it, so adding a status updates both places.

The exhaustive-check pattern catches a forgotten case at compile time:

```tsx
default: {
  const _exhaustive: never = action;
  throw new Error(`Unhandled: ${JSON.stringify(action)}`);
}
```

Adding a new action type without a case makes `_exhaustive` fail to compile ([[25.6 - Discriminated Unions and Narrowing]]).

## useContext

```tsx
const ThemeContext = createContext<Theme | null>(null);

export function useTheme(): Theme {
  const ctx = useContext(ThemeContext);
  if (ctx === null) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;   // narrowed to Theme
}
```

Typing the context as `T | null` and narrowing in a custom hook gives consumers a non-nullable type without optional chaining everywhere. The runtime guard and the type narrowing are the same line of code, which is why this pattern is standard ([[17.9 - useContext]]).

The alternative — `createContext({} as Theme)` — lies about the type and produces confusing runtime errors instead of a clear one.

## Custom hooks

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle] as const;      // readonly [boolean, () => void]
}

const [isOpen, toggleOpen] = useToggle();
```

`as const` is essential on returned tuples. Without it TypeScript infers `(boolean | (() => void))[]`, and destructuring gives a useless union type ([[17.11 - Custom Hooks]]).

For object returns, inference works without help:

```tsx
function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [error, setError] = useState<Error | null>(null);
  return { data, error, isLoading: data === null && error === null };
}
```

An explicit return type is worth adding on hooks exported from a shared package — it stabilizes the public API and produces better error messages than a large inferred shape.

## useCallback and useMemo

```tsx
const handler = useCallback((id: string) => select(id), [select]);
const total = useMemo(() => items.reduce((s, i) => s + i.price, 0), [items]);
```

Both infer correctly from the callback. An explicit generic is only needed when the inferred type is too narrow:

```tsx
const [value, setValue] = useState<string | null>(null);
const handler = useCallback<(v: string | null) => void>((v) => setValue(v), []);
```

## Third-party and DOM gaps

```tsx
// Extending the global Window
declare global {
  interface Window {
    analytics?: { track: (event: string) => void };
  }
}

// A module with no types
declare module "untyped-lib" {
  export function doThing(input: string): number;
}
```

Declaration merging is what makes these possible, which is one of the few places `interface` is required rather than preferred ([[25.1 - Types vs Interfaces]]).

## How senior engineers actually use this

**They use `currentTarget`, not `target`**, unless the origin element is genuinely what they need.

**They type context as `T | null` and narrow in a custom hook**, so consumers never handle null.

**They put `as const` on every tuple returned from a hook.**

**They model reducer actions as a discriminated union** with an exhaustive default case.

**They use `ElementRef<"tag">`** rather than guessing DOM element type names.

## Common pitfalls

- `useState([])` inferring `never[]`.
- `useState(null)` without a generic, so the state can only ever be null.
- Missing `as const` on a returned tuple.
- Confusing React's synthetic event types with the DOM ones in `addEventListener`.
- `e.target` used where `currentTarget` was meant, then failing to narrow.
- `createContext({} as T)`, which hides a missing provider until a runtime crash.
- Callback refs typed without `| null`.

## Interview angle

These come up inside practical TypeScript exercises rather than as direct questions. The details that read as fluency: `currentTarget` is typed and `target` is not, `as const` is required on hook tuple returns, context should be typed nullable and narrowed in a custom hook, and a discriminated union of actions gives both dispatch-site checking and in-reducer narrowing. The exhaustive `never` check is a good pattern to demonstrate unprompted.
