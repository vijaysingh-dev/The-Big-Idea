# CI CD and Frontend Deployment

## The pipeline

```
push → install → lint + typecheck + test → build → preview deploy
                                                  ↓ (on main)
                                            production deploy
```

```yaml
name: CI
on: [push, pull_request]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: ".nvmrc"
          cache: "npm"

      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:ci
      - run: npm run build

      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: test-results
          path: playwright-report/
```

`npm ci` rather than `npm install` — deterministic, faster, and it fails if the lockfile disagrees with `package.json` ([[27.1 - npm and package.json]]).

`node-version-file: ".nvmrc"` keeps CI and local development on the same Node version from one source.

Uploading artifacts on failure is what makes a CI failure actionable. Without it, "it failed in CI" leads to a cycle of speculative pushes ([[26.5 - End to End Testing with Playwright]]).

## Ordering for fast feedback

Run cheap checks first so an obvious failure does not wait behind a five-minute test suite:

```
typecheck (~20s) → lint (~15s) → unit tests (~60s) → build (~90s) → e2e (~4min)
```

Parallelize what is independent:

```yaml
jobs:
  quality:
    strategy:
      matrix:
        task: [lint, typecheck, test]
    steps:
      - run: npm run ${{ matrix.task }}
```

For large repositories, running only what changed is the bigger win. Turborepo and Nx build a task graph with content-based hashing, so unchanged packages are skipped and results are restored from cache:

```bash
turbo run build test --filter=[origin/main]
```

## Caching

```yaml
- uses: actions/setup-node@v4
  with: { cache: "npm" }

- uses: actions/cache@v4
  with:
    path: |
      node_modules/.vite
      .turbo
    key: ${{ runner.os }}-build-${{ hashFiles('**/package-lock.json') }}
    restore-keys: ${{ runner.os }}-build-
```

Dependency caching typically saves 30–60 seconds per job. Build caches — Vite's dependency pre-bundle, Turbo's task cache, webpack's filesystem cache — save more on large projects.

`restore-keys` provides a partial fallback, so a lockfile change gets a warm-ish cache rather than a cold one.

## Quality gates

```yaml
- run: npx size-limit
- run: npx lhci autorun
```

```json
{
  "size-limit": [
    { "path": "dist/assets/index-*.js", "limit": "150 kB" },
    { "path": "dist/assets/*.css", "limit": "30 kB" }
  ]
}
```

Bundle size regresses gradually — a dependency here, an import pattern there. A CI budget converts that into a visible decision at the PR that causes it, rather than a discovery six months later ([[19.7 - Bundle Analysis and Optimization]]).

Lighthouse CI can assert performance and accessibility thresholds against a preview deployment. Treat the scores as directional — they are noisy in CI environments — and gate on the specific audits that matter rather than the composite number.

## Preview deployments

Every pull request gets its own URL. Vercel, Netlify and Cloudflare Pages do this automatically; a self-hosted equivalent uploads to a path or subdomain keyed by the PR number.

The value is disproportionate to the effort:

- Designers and product review the actual thing rather than screenshots
- E2E and Lighthouse run against a real deployment
- QA happens before merge instead of after
- Reproducing a bug means opening a URL

Two operational requirements: preview environments must not point at production data, and they should be protected — either behind auth or with `X-Robots-Tag: noindex` — since an indexed preview URL competes with the real site ([[09.4 - Head Metadata and SEO Basics]]).

## Deployment for a static SPA

```bash
npm run build
# upload dist/ to object storage, served through a CDN
```

Three things must be configured correctly:

**Cache headers**, split by content type ([[15.7 - HTTP Caching and CDNs]]):

```
/assets/*.js, *.css   Cache-Control: public, max-age=31536000, immutable
/index.html           Cache-Control: no-cache
```

Hashed filenames make the first safe; the uncached HTML is the pointer to the current filenames.

**SPA fallback**, or a refresh on `/products/42` returns 404 ([[23.1 - Client Side Routing Fundamentals]]):

```
/* /index.html 200
```

**Upload order.** Upload assets **before** replacing `index.html`, or users briefly receive HTML referencing files that are not there yet.

## Old assets must survive

The most common frontend deployment bug: a user with an open tab holds HTML referencing chunk filenames that the deploy removed. Their next lazy import 404s and the screen goes blank ([[19.3 - Code Splitting and React.lazy]]).

Two mitigations, both worth having:

**Keep old assets** for at least a day or two rather than deleting on deploy. Storage is cheap; a blank screen is not.

**Recover in the client:**

```js
window.addEventListener("vite:preloadError", (e) => {
  e.preventDefault();
  window.location.reload();
});
```

This does not appear in testing because deploys are rare in development, which is exactly why it reaches production.

## Progressive rollout

**Canary** — route a small percentage of traffic to the new version, watch error rates, then widen. Requires edge routing or a load balancer that can split by cookie or percentage.

**Feature flags** — deploy the code disabled, enable it gradually per cohort. This decouples deploy from release, so a problem is a flag toggle rather than a rollback ([[28.8 - Feature Flags and Progressive Rollout]]).

Flags are usually the better mechanism for frontend work: rolling back a static deployment is fast, but rolling back only for affected users is not something a deployment can do.

**Instant rollback** should be a single command or button. Static hosts implement this as an atomic pointer swap between immutable deployments, which is why the deploy model matters — a rollback that requires a rebuild is not a rollback.

## Monitoring the deploy

```js
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_COMMIT_SHA,
  environment: import.meta.env.MODE,
});
```

Tagging errors with the release makes a regression obvious — a spike appearing only for the new release identifies the cause immediately.

Upload source maps as part of the deploy and delete them from the served output ([[27.7 - Source Maps]]):

```yaml
- run: npx sentry-cli sourcemaps inject ./dist
- run: npx sentry-cli sourcemaps upload --release=$GITHUB_SHA ./dist
- run: rm -f dist/assets/*.map
```

Real user monitoring for Core Web Vitals should also be release-tagged, so a performance regression is attributable ([[28.13 - Frontend Observability]]).

## Secrets in CI

```yaml
env:
  SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
```

Use the platform's secret store, never a committed file. Prefer OIDC federation over long-lived cloud credentials where the provider supports it.

Two frequent leaks: printing an environment variable in a debug step, and running a workflow with secrets on a fork PR. `pull_request_target` is the specific trigger to avoid on untrusted contributions.

Remember that build-time secrets used to *fetch* something are safe; anything substituted into the bundle is not ([[27.8 - Environment Variables and Config]]).

## Branch strategy

**Trunk-based with short-lived branches** suits frontend work well. Small PRs, merge to `main` frequently, deploy `main` continuously, and use feature flags for anything incomplete.

Long-lived release branches with batched releases create large, risky merges and delay feedback. They make sense when releases are coordinated with mobile or backend versions, and rarely otherwise.

`main` should always be deployable. That is the property everything else supports.

## How senior engineers actually use this

**They run cheap checks first** so failures surface in seconds rather than minutes.

**They enforce a bundle size budget in CI**, because size regresses invisibly otherwise.

**They keep preview deployments on every PR**, which shifts review and QA before merge.

**They retain old assets for days** and ship client-side chunk-error recovery.

**They tag every error and vitals report with the release SHA**, making regressions attributable.

**They make rollback a one-click operation** and verify it works before they need it.

## Common pitfalls

- `npm install` in CI instead of `npm ci`.
- No artifact upload on failure, making CI failures undebuggable.
- Old assets deleted on deploy, breaking open tabs.
- Missing SPA fallback, so refresh 404s.
- HTML cached, or hashed assets uncached.
- Preview deployments pointing at production data, or indexed by search engines.
- Source maps left publicly served, or uploaded from a different build.
- Secrets echoed in logs, or exposed to fork PRs.
- No bundle size budget, so regressions accumulate silently.

## Interview angle

"Walk me through deploying a frontend application" is a systems question. Cover the pipeline stages and their ordering for fast feedback, then the deployment specifics that are frontend-particular: hashed assets cached immutably with uncached HTML, SPA fallback routing, and — the detail that marks experience — keeping old chunks alive after a deploy so open tabs do not break, plus client-side recovery when they do. Mentioning preview deployments per PR and release-tagged error monitoring rounds it into a complete answer.
