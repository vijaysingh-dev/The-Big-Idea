# NAT Firewalls and Middleboxes

#backend #networking

> **In one line:** The internet is full of boxes that rewrite, block and forget your connections without telling you, and most "mysterious network behaviour" is one of them doing its job.

---

## The Idea

The clean mental model is: your packet goes from A to B.

The reality is: your packet goes through a NAT gateway that rewrites its source address, a stateful firewall that remembers it for 60 seconds, a load balancer that terminates it and opens a new one, and possibly a transparent proxy that reads and modifies it.

None of these announce themselves. All of them can silently drop your connection.

💡 **The practical consequence: never assume the connection you opened is the connection the other end sees.** IP addresses change, ports change, connections get closed by things that are not either endpoint, and idle connections die for reasons that appear in no log you have access to.

---

## NAT

**Network Address Translation** lets many private addresses share one public one.

```
Private                     NAT gateway                    Internet
10.0.0.5:51234  ─────►  203.0.113.7:40001  ─────►  93.184.216.34:443
10.0.0.6:51234  ─────►  203.0.113.7:40002  ─────►
```

The gateway keeps a table mapping each internal socket to an external port. Replies come back to the external port, get looked up, and get rewritten to the internal address.

### What NAT breaks

| Problem | Consequence |
|---|---|
| No inbound connections | Nobody outside can initiate a connection to you |
| Mappings expire | Idle connections die silently |
| Source IP is shared | Rate limiting by IP hits everyone behind one NAT |
| Port exhaustion at the gateway | A busy NAT runs out of external ports |

### Mapping timeouts — the silent killer

The gateway must eventually forget mappings, or its table grows forever.

| Protocol | Typical timeout |
|---|---|
| TCP established | 300s–7200s (often ~900s) |
| TCP after FIN | 30–120s |
| **UDP** | **30–180s** |

⚠️ **When the mapping expires, the gateway just stops forwarding.** No RST, no notification. Your connection is `ESTABLISHED` on both endpoints and completely dead in the middle. Both sides wait forever.

This is the mechanism behind:

- WebSocket connections dying after a few minutes of silence
- Database pool connections that fail on first use after an idle period
- Long-polling requests that never return
- SSE streams that stop delivering with no error

**The fix is always the same: send something periodically.** Application heartbeats every 15–30 seconds, or TCP keepalive tuned well below the shortest timeout in the path. This is why every realtime protocol has a ping — see [[04.3 - SSE in Production]].

### CGNAT

Carrier-grade NAT means your mobile provider NATs thousands of subscribers behind one public IP.

Consequences you will actually meet:

- **IP-based rate limiting punishes innocent users.** Thousands of people share the address
- **IP-based geolocation is wrong.** The exit point may be in another city or country
- **Blocking an abusive IP blocks a neighbourhood**

💡 If your rate limiting is per-IP and you serve mobile users, you are limiting a carrier, not a user. Rate limit by authenticated identity where you can, and treat IP as a weak signal. See [[11.5 - Rate Limiting and Quotas]].

## Firewalls

### Stateful filtering

A stateful firewall remembers connections it has seen:

```
Outbound SYN from 10.0.0.5:51234 to 93.184.216.34:443
  → record the flow
  → allow return traffic matching it
  → forget it after an idle timeout
```

Same expiry problem as NAT, same fix.

### Drop versus reject

This distinction matters more than it seems.

| Action | Client sees | Time to fail |
|---|---|---|
| **Reject** (send RST or ICMP) | `Connection refused` | Immediate |
| **Drop** (silence) | `Connection timed out` | Your full connect timeout |

⚠️ **Most security-conscious firewalls drop rather than reject**, because silence gives an attacker less information. The cost is that your legitimate service takes the full timeout to fail instead of failing instantly.

This is why a misconfigured security group produces a 30-second hang rather than an error, and why your first diagnostic question should be "refused or timed out?" — they point at completely different causes.

```bash
# Refused: something is there, actively saying no
# Timed out: silence — firewall drop, wrong address, or host down
nc -zv host 443
```

### Egress filtering

Many production networks restrict **outbound** traffic. Your service can only reach an allow-list of destinations.

Symptoms: works in dev, times out in production, only for one particular dependency. Especially common with a newly added third-party API that nobody added to the allow-list.

## Load Balancers and Proxies

A load balancer is a middlebox you deliberately installed, and it changes things.

### Two connections, not one

```
Client ══════► Load balancer ══════► Backend
       conn A                conn B
```

Consequences:

| Effect | Meaning |
|---|---|
| Backend sees the LB's IP | Real client IP only via `X-Forwarded-For` or PROXY protocol |
| Two idle timeouts | Either can close independently |
| The LB may buffer | Streaming responses can be held until complete |
| Protocol may be translated | HTTP/2 in, HTTP/1.1 out is common |

### The idle timeout incident

This one is worth memorising because it is so common and so confusing.

```
AWS ALB idle timeout:  60 seconds (default)
Your DB pool:          holds connections idle for minutes
```

The load balancer closes the idle connection. Your pool does not know. The next request gets a dead socket.

Symptom: **intermittent `Connection reset by peer`, and it happens more during LOW traffic** — because that is when connections sit idle long enough. The inverse of what everyone expects, which is why it takes so long to diagnose.

Fix: `pool_recycle` shorter than the LB timeout, plus `pool_pre_ping` ([[01.10 - Connection Pools and Limits]]).

### Response buffering breaks streaming

Many proxies buffer a response before forwarding it. For a normal response that is fine and even helpful — it frees the backend sooner.

For SSE or a streaming response, it means nothing reaches the client until the stream ends. Which, for an infinite stream, is never.

```nginx
location /events {
    proxy_pass http://backend;
    proxy_buffering off;              # required for SSE
    proxy_read_timeout 3600s;
    proxy_set_header Connection '';
    proxy_http_version 1.1;
}
```

⚠️ **`X-Accel-Buffering: no`** as a response header also disables nginx buffering, and it is useful when you do not control the proxy config. Covered fully in [[04.3 - SSE in Production]].

### Getting the real client IP

```
X-Forwarded-For: 203.0.113.9, 10.0.0.1, 10.0.0.2
                 ▲ original    ▲ each proxy appends
```

⚠️ **`X-Forwarded-For` is client-controlled and trivially spoofable** unless you only trust the entries added by proxies you control.

```bash
uvicorn app:app --proxy-headers --forwarded-allow-ips='10.0.0.0/8'
```

Never `--forwarded-allow-ips='*'` on an internet-facing service. That lets any client claim any IP, defeating your rate limiting, your geo rules, and your audit logs.

**PROXY protocol** is the better answer where supported: the load balancer prepends a small header with the real addresses before the TLS handshake, at the TCP layer, so it cannot be forged by the client.

## NAT Traversal

For peer-to-peer connections, NAT is the central problem: neither side can accept an inbound connection.

### STUN — discover your public address

```
Client ──► STUN server: "what address do you see me as?"
       ◄── "203.0.113.7:40001"
```

Now you know your external mapping and can share it with the peer.

### Hole punching

Both peers send outbound packets to each other simultaneously. Each outbound packet creates a NAT mapping that allows the reply back in.

```
A ──► B  (creates A's mapping; dropped at B's NAT)
B ──► A  (creates B's mapping; now allowed through A's NAT)
A ──► B  (now allowed through B's NAT)
```

Works with many NAT types. Fails with **symmetric NAT**, which allocates a different external port per destination — so the port you learned from STUN is not the port your peer will see.

### TURN — give up and relay

```
A ──► TURN server ──► B
```

Always works, because both peers make outbound connections to the relay. Costs you bandwidth and adds latency, so it is the fallback, not the default. Typically 10–20% of connections need it.

### ICE — try everything

ICE gathers all candidate paths (local address, STUN-discovered address, TURN relay), tests them all in parallel, and picks the best one that works.

This is the whole reason WebRTC connection setup is complex. See the existing WebRTC guide.

## In Production

### Diagnosing a middlebox

```bash
# Refused or dropped? Different causes entirely
nc -zv host 443

# Where does it stop?
traceroute -T -p 443 host        # TCP traceroute, gets through more filters
mtr -T -P 443 host               # continuous, shows loss per hop

# Is something rewriting my address?
curl ifconfig.me                 # what the internet sees as my IP

# Is something closing my connections?
sudo tcpdump -i any 'tcp[tcpflags] & tcp-rst != 0' -nn

# How long does an idle connection survive?
nc host 443     # connect, wait, see when it dies
```

💡 **The RST capture is the key one.** If you see an RST with a TTL that does not match either endpoint, a middlebox sent it. TTL is your fingerprint for "who actually closed this."

### The middlebox checklist

When something works in one environment and not another:

1. **Refused or timed out?** Refused means something answered. Timed out means silence
2. **Does it work by IP but not by hostname?** DNS ([[02.8 - DNS]])
3. **Does it work for small payloads but not large?** MTU ([[02.1 - The Stack in One Picture]])
4. **Does it work for a while then stop?** Idle timeout
5. **Does it work for HTTP but not WebSocket?** A proxy not handling the upgrade
6. **Does streaming buffer until the end?** Proxy buffering
7. **Does it fail only under low traffic?** Idle timeout again, counterintuitively
8. **Is the client IP wrong in logs?** Missing or misconfigured forwarded headers

### Design so middleboxes cannot hurt you

| Practice | Prevents |
|---|---|
| Heartbeats every 15–30s on long-lived connections | Idle timeout death |
| `pool_recycle` below every timeout in the path | Dead pooled connections |
| Explicit connect and read timeouts | Hanging on a silent drop |
| `proxy_buffering off` for streaming endpoints | Streams that never arrive |
| PROXY protocol or carefully-scoped forwarded headers | Wrong or spoofed client IPs |
| Do not rate limit purely by IP | CGNAT collateral damage |
| Keep payloads under 1200 bytes for UDP | Fragmentation loss through tunnels |

**The heartbeat rule is the highest value one.** A 15-second heartbeat costs almost nothing and eliminates an entire category of incident.

## Codebase

**Repo:** `coturn/coturn`, `pion/webrtc`, and `haproxy/haproxy`

**Question to answer:** How does ICE decide between a direct connection and a relay, and how long does it take to fail over? Then, separately: how does the PROXY protocol carry the original client address, and why can it not be spoofed the way `X-Forwarded-For` can?

**Read, in order:**

1. `pion/ice` — `agent.go` and `candidate*.go`. Candidate gathering, pair prioritisation, connectivity checks. This is ICE made readable, which OpenSSL-era C implementations are not
2. `coturn/src/apps/relay/` — a production TURN server. See what relaying actually costs in state and bandwidth
3. `haproxy/src/proxy_protocol` handling and `doc/proxy-protocol.txt` — **read the spec document, it is short and clear**. The answer to the second question is that the header arrives before any client data, on a connection the client cannot influence
4. `haproxy/src/proto_tcp.c` — how HAProxy handles the two-connection model

💡 The ICE reading is worth doing even if you never write WebRTC. It is the clearest illustration in any codebase of "the network is hostile and you must try everything" — a design philosophy that shows up in retries, service discovery and failover generally.

**Size:** 1–2 sessions.

```
│   ├── real_ip.py        # forwarded headers, including spoofed
│   └── FINDINGS.md
├── traversal/
│   ├── stun_client.py    # discover your own mapping
│   ├── hole_punch.py     # two peers behind separate NATs
│   └── RESULTS.md
└── README.md
```

**Part 1 — Build a NAT.** Use Linux network namespaces to build a real NAT gateway with `iptables MASQUERADE`. Two private namespaces, one gateway, one "internet" namespace.

Then:

- Establish a TCP connection, go idle, and probe until it dies. **Find the actual timeout by bisection**
- Do the same for UDP. It will be dramatically shorter
- Set `conntrack` timeouts explicitly and confirm your measurement matches
- Add a 15-second heartbeat and show the connection surviving indefinitely

**This is the drill that makes heartbeats feel necessary rather than ceremonial.**

**Part 2 — Drop versus reject.** Same port, two firewall rules. Measure time-to-failure for each from a client with a 30-second connect timeout.

Then write down: given only a client-side error message, how do you tell a dropped packet from a host that is down from a wrong address? Be honest about which cases are indistinguishable.

**Part 3 — The idle timeout incident, reproduced.** nginx with a 10-second `proxy_read_timeout` between your app and Postgres (or use toxiproxy). A connection pool with a 60-second idle time.

Run light traffic — one request every 30 seconds. Watch the intermittent resets appear.

**Then run heavy traffic and watch the problem disappear**, because connections never go idle. Document this inversion clearly; it is the detail that makes the incident hard to diagnose in the real world.

Fix with `pool_recycle` and `pool_pre_ping`. Verify.

**Part 4 — Buffering breaks streaming.** SSE endpoint behind nginx with default settings. Observe that nothing arrives. Then `proxy_buffering off`, then `X-Accel-Buffering: no`, and confirm each works.

Measure the time-to-first-chunk in all three configurations.

**Part 5 — Spoof your own IP.** App behind a proxy, using `X-Forwarded-For` for rate limiting. Set `--forwarded-allow-ips='*'`.

Now send requests with a forged header and defeat your own rate limiter. Then set the trusted range correctly and show the spoofing failing.

Then set up PROXY protocol instead and show that it cannot be spoofed at all, because the client never gets to write those bytes.

**Part 6 — Hole punching.** Two namespaces behind two separate NATs. A STUN server in the "internet" namespace.

Discover both mappings, exchange them out of band, and punch a hole. Then reconfigure one NAT to be symmetric (`--random-fully` or a port-randomising rule) and show the punch failing. Then relay through TURN and show it working.

**Done when:**
- You have measured real NAT timeouts for TCP and UDP by bisection
- Heartbeats demonstrably keep a connection alive past the timeout
- You reproduced the idle-timeout incident, including the low-traffic inversion
- You have three working fixes for proxy buffering with measured TTFB
- You defeated your own rate limiter with a forged header, then fixed it
- Hole punching works, fails on symmetric NAT, and TURN rescues it
