# Linux Observability Tools

#backend #os #linux #performance #debugging

> **In one line:** When a box is slow, check every resource for utilisation, saturation and errors (the USE method) with a dozen standard tools, in a fixed order, in about 60 seconds, before you form a theory.

---

## The Idea

Most performance investigations fail the same way: someone forms a theory ("it's the database") and goes looking for evidence. Reverse it. **Look at every resource first, in the same order every time, and let the numbers point.**

### The USE method (Brendan Gregg)

For every resource, ask three questions:

| | Question | Example for CPU |
|---|---|---|
| **U**tilisation | How busy is it? | `%usr + %sys` in `mpstat` |
| **S**aturation | Is work queuing for it? | Run-queue length, PSI `cpu some`, throttled periods |
| **E**rrors | Is it failing? | Rarely for CPU; for disks and NICs, often |

Resources: **CPU, memory, disk I/O, network, file descriptors**, plus software limits (thread pools, connection pools, locks).

---

## The 60-Second Checklist

Run these in order on a slow Linux host. This is Netflix's well-known list, lightly adapted.

```bash
uptime                      # 1. load averages: rising or falling?
dmesg -T | tail             # 2. kernel errors: OOM kills, disk errors, TCP drops
vmstat 1                    # 3. r (run queue), free, si/so (swap), us/sy/wa/st
mpstat -P ALL 1             # 4. per-CPU: one hot core = single-threaded bottleneck
pidstat 1                   # 5. which processes use CPU
iostat -xz 1                # 6. disk: r_await, w_await, aqu-sz, %util
free -m                     # 7. memory: look at "available"
sar -n DEV 1                # 8. network throughput per interface
sar -n TCP,ETCP 1           # 9. TCP: active/passive opens, retransmits
top                         # 10. overview, and a sanity check
```

How to read `vmstat`:

```
procs -----memory------ ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free  ...  si   so    bi    bo   in   cs us sy id wa st
 9  0      0 812344  ...   0    0     0    24 2210 8800 82 12  6  0  0
```

| Column | Meaning | Worry when |
|---|---|---|
| `r` | Runnable threads | Consistently above the core count: CPU saturation |
| `b` | Blocked in uninterruptible sleep | Above 0 for long: I/O trouble |
| `si`/`so` | Swap in/out per second | Anything non-zero on a latency-sensitive box |
| `us`/`sy` | User / kernel CPU % | `sy` high: too many syscalls, or contention |
| `wa` | CPU idle while waiting for I/O | High: disk-bound |
| `st` | Stolen by the hypervisor | Above a few %: a noisy neighbour on your VM |

## Tool Map

| Question | Tool | Example |
|---|---|---|
| What is this process doing right now? | `py-spy dump --pid` (Python), `strace -p`, `gdb -p` | Stack of every thread |
| Where is CPU time going? | `py-spy top`, `py-spy record` (flame graph), `perf top`, `perf record -g` | See [[01.12 - Profiling and Debugging Async Services]] |
| Which syscalls, how slow? | `strace -c -f -p`, `perf trace -s`, `syscount` (bcc) | Count and latency per syscall |
| Open files and sockets | `lsof -p`, `ls -l /proc/PID/fd`, `ss -tanp` | fd leaks, who holds a port |
| Network connections | `ss -s` (summary), `ss -tan state time-wait \| wc -l`, `ss -tlnp` | See [[03.11 - Reading Real Traffic]] |
| Memory breakdown | `smem -k`, `/proc/PID/smaps_rollup`, `pmap -x` | PSS versus RSS ([[02.6 - Memory in Practice]]) |
| Disk latency | `iostat -x`, `biolatency` (bcc), `biotop` | Latency histogram, top I/O processes |
| Page cache effectiveness | `cachestat` (bcc), `vmtouch file` | Hit ratio; is the file cached? |
| Container limits | `cat /sys/fs/cgroup/cpu.stat memory.events`, `systemd-cgtop` | Throttling and OOM events |
| Pressure | `cat /proc/pressure/{cpu,memory,io}` | Stall percentages |
| Who is listening on port X? | `ss -tlnp 'sport = :8000'`, `lsof -i :8000` | |

## perf and Flame Graphs

`perf` samples the CPU's call stack many times a second across the whole system, kernel included.

```bash
sudo perf top                                   # live hottest functions
sudo perf record -F 99 -g -p $PID -- sleep 30   # sample one process for 30 s
sudo perf report                                # browse
# flame graph:
sudo perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg
```

For Python, plain `perf` shows interpreter C frames (`_PyEval_EvalFrameDefault`), not your functions. Two fixes:

- **`py-spy record -o out.svg --pid $PID --native`**: Python and native frames together. The easiest option.
- **Python 3.12+ perf support:** run with `python -X perf` and `perf` shows Python function names directly.

How to read a flame graph: the x-axis is **not time**. Width is the share of samples. Look for wide plateaus at the top. Those are the functions actually on the CPU.

## eBPF: Tracing Without the Cost

eBPF lets you run small, verified programs inside the kernel, attached to almost any event, with very low overhead. It is what makes production tracing safe where `strace` is not.

```bash
# bcc tools (package: bpfcc-tools; names may end in -bpfcc)
sudo execsnoop          # every new process: catches runaway subprocess spawns
sudo opensnoop -p PID   # every file opened
sudo tcpconnect         # every outbound TCP connect
sudo tcpretrans         # every retransmission, live
sudo biolatency         # disk I/O latency histogram
sudo runqlat            # how long threads wait for a CPU: scheduler latency

# bpftrace one-liner: count syscalls by process
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
```

💡 `runqlat` answers a question nothing else does: "how long did my thread wait to get a CPU after it became runnable?" If that number is in milliseconds, your latency problem is CPU contention or throttling, not your code.

## Containers and Kubernetes

Tools see the host by default. Inside a container you may not have them at all.

```bash
# from the host: enter a container's namespaces with host tools
PID=$(docker inspect -f '{{.State.Pid}}' mycontainer)
sudo nsenter -t $PID -n ss -tanp          # network namespace only
sudo nsenter -t $PID -p -m ps aux         # pid + mount namespaces

# Kubernetes: attach a debug container to a running pod
kubectl debug -it mypod --image=nicolaka/netshoot --target=app
```

`py-spy` in Kubernetes needs the `SYS_PTRACE` capability on the pod (or an ephemeral debug container that has it).

## A Worked Investigation

> "The API's p99 went from 80 ms to 900 ms. CPU dashboard shows 35%."

1. `uptime`: load 6 on a 4-vCPU node, rising. Something is queuing.
2. `vmstat 1`: `r` = 5–8, `wa` = 0, `st` = 0. CPU queueing, not disk.
3. `mpstat -P ALL 1`: all cores busy in bursts, then idle.
4. `cat /sys/fs/cgroup/cpu.stat`: `nr_throttled` rising fast. **The container is throttled** at its 1-CPU limit, while the 35% average hides the bursts.
5. `py-spy top`: 40% of samples in JSON serialisation of a large response.

Two fixes: raise the CPU limit or remove it ([[02.3 - Threads and the Scheduler]]), then paginate the large response. The numbers pointed; no theory was needed.

## Codebase

**Repos:** `procps-ng/procps` (or `htop-dev/htop`), `iovisor/bcc`

**Question to answer:** Where does `top` get each number it shows? Every one comes from a file under `/proc`.

**Read, in order:**

1. htop `linux/LinuxProcessTable.c` (named `LinuxProcessList.c` in older versions) — find where it reads `/proc/<pid>/stat`, `statm` and `status`, and map each column to a field
2. htop `linux/Platform.c` or procps `library/meminfo.c` — how "available" memory is computed from `/proc/meminfo`
3. bcc `tools/runqlat.py` — a whole eBPF tool in one file: the C program embedded as a string, the probe attachment, and the histogram printing
4. bcc `tools/execsnoop.py` — the simplest useful eBPF tool

**Size:** 1–2 sessions.
