# GraphQL: The Core Model

#backend #api-design #graphql

> **In one line:** GraphQL is one endpoint, a typed schema, and a query language that lets the client specify exactly which fields it wants — which solves over-fetching and creates four new problems REST never had.

---

## The Idea

REST gives fixed responses at many endpoints:

```
GET /documents/42        → the whole document
GET /documents/42/source → the source
GET /users/7             → the author
```

Three round trips, each returning fields you did not need.

```graphql
query {
  document(id: "doc_42") {
    title
    source { name }
    author { name email }
  }
}
```

One round trip. Exactly the requested fields. The response shape mirrors the query shape.

💡 **The problem GraphQL actually solves is client diversity.** When a mobile app, a web app and a partner integration need different subsets of the same data, REST forces you to over-fetch, build per-client endpoints, or bolt on a field-selection system that becomes an ad-hoc query language anyway.

⚠️ **It is not "better than REST".** It moves complexity from the client to the server, and the server's new problems — N+1, unbounded query cost, broken HTTP caching — are harder than the ones it removed. **Notes 05.6 through 05.8 are entirely about those problems.**

## The Schema

```graphql
type Document {
  id: ID!
  title: String!
  status: DocumentStatus!
  createdAt: DateTime!
  source: Source!
  annotations(first: Int = 20, after: String): AnnotationConnection!
}

type Query {
  document(id: ID!): Document
  documents(first: Int = 20, after: String, status: DocumentStatus): DocumentConnection!
}
```

`!` means non-nullable. `[Document!]!` is a non-null list of non-null documents.

### Nullability is a real decision

⚠️ **A null on a non-nullable field propagates upward.** If `source` is `Source!` and its resolver returns null, GraphQL nulls out the *parent* — and if that is also non-nullable, it keeps climbing, potentially nulling the entire `data` object.

```graphql
type Query {
  documents: [Document!]!     # one broken document nulls the whole list
}
```

💡 **The guidance large schemas converge on: be generous with nullability on fields that depend on other services.** A field backed by a flaky downstream should be nullable, so its failure degrades one field rather than the whole response ([[11.6 - Graceful Degradation]]).

**Non-nullable is right for fields from your own database that structurally always exist.**

## Queries, Mutations, Subscriptions

```graphql
type Query { ... }         # reads, may execute in parallel
type Mutation { ... }      # writes, top-level fields execute SERIALLY
type Subscription { ... }  # a stream of events
```

⚠️ **Top-level mutation fields execute in order; everything else may run in parallel.** That is the only ordering guarantee in the language.

### Mutation conventions

```graphql
input CreateDocumentInput { title: String!, sourceId: ID! }

type CreateDocumentPayload {
  document: Document
  errors: [UserError!]!
}
```

**A single `input` argument** — adding a field to an input type is non-breaking. **Errors in the payload, not thrown** — expected failures are part of the data; only unexpected ones become GraphQL errors.

💡 **This is the biggest philosophical difference from REST.** GraphQL returns `200 OK` almost always; errors live in the body. That is why [[05.3 - Error Design]]'s status-based model does not transfer directly.

⚠️ **The cost is that HTTP-level tooling stops helping you.** Your load balancer, error-rate dashboard and alerting all see 200s during an outage. **Your observability layer must parse GraphQL responses.**

## Resolvers

```python
@strawberry.type
class Document:
    id: strawberry.ID
    title: str

    @strawberry.field
    async def source(self, info: Info) -> "Source":
        return await info.context.loaders.source.load(self.source_id)
```

A resolver receives the parent value, the field arguments, per-request context, and the AST.

**Default resolvers handle the common case** — if the parent already has an attribute of that name, GraphQL just reads it.

### The execution shape

```
Query.document          → 1 call
  Document.title        → free (attribute)
  Document.source       → 1 call
  Document.annotations  → 1 call
    Annotation.author   → N calls    ← one per annotation
```

⚠️ **That last line is the N+1 problem, and it is inherent to how GraphQL executes** — twenty annotations means twenty separate author lookups.

💡 **Every GraphQL server needs a batching layer from day one.** Not "when it gets slow" — from the first nested field. Retrofitting is much harder ([[05.6 - The N+1 Problem and DataLoader]]).

## The Type System

### Interfaces and unions

```graphql
interface SearchResult { id: ID!, title: String! }
union SearchHit = Document | Annotation | Source
```

**Interfaces** share fields; **unions** do not. Use an interface when the types genuinely have common fields; a union when they only share a position in the result.

### Custom scalars

⚠️ **`scalar JSON` is a trapdoor out of the type system.** Clients get no type safety, no introspection, no validation. Every schema that adds it early regrets how much data flowed through it. **Resist until you have a real case.**

### Connections (Relay pagination)

```graphql
type DocumentConnection {
  edges: [DocumentEdge!]!
  pageInfo: PageInfo!
  totalCount: Int
}
```

Verbose, and it is the de facto standard because tooling assumes it. The `edges`/`node` split exists so edge-specific metadata has somewhere to live.

Cursor semantics are those in [[05.2 - Versioning Pagination and Filtering]] — opaque, keyset-based, with a tiebreaker.

⚠️ **`totalCount` is expensive and clients ask for it on every query.** Make it nullable, or return an estimate.

## Introspection

```graphql
query { __schema { types { name fields { name } } } }
```

This powers GraphiQL, code generation and client type checking. **Your documentation cannot drift from your API** — a genuine advantage.

⚠️ **Disable it in production for non-public APIs.** It hands an attacker your complete data model ([[05.8 - GraphQL Security and Limits]]).

## In Production

### When GraphQL is worth it

| Situation | Verdict |
|---|---|
| Many clients with different data needs | **Strong yes** |
| Mobile on poor networks | Yes |
| Highly relational domain | Yes |
| Public API for third parties | Mixed — great DX, hard to rate limit |
| **One frontend, one backend, one team** | **Usually no** |
| High-volume machine-to-machine | No. gRPC ([[05.11 - REST vs GraphQL vs gRPC]]) |
| Anything needing HTTP caching | No |

💡 **GraphQL is a client-diversity solution.** Facebook built it because they had dozens of clients on unreliable mobile networks. **If your situation does not resemble that, be sceptical.**

### Observability is genuinely harder

```
Access log:  POST /graphql 200 45ms
Access log:  POST /graphql 200 12000ms
```

Your logs, dashboards and traces see one endpoint.

```python
graphql_operation_duration.labels(operation_name=..., operation_type=...).observe(elapsed)
graphql_field_duration.labels(parent_type=..., field=...).observe(elapsed)
graphql_query_complexity.observe(complexity)
```

⚠️ **Require named operations and reject anonymous ones in production.** Without a name you cannot attribute cost, alert on a specific query regressing, or answer "which query is causing this". **It is a one-line validation rule and it transforms your ability to operate the service.**

### Schema evolution

| Change | Breaking? |
|---|---|
| Adding a field | **No** — clients only get what they ask for |
| Adding an optional argument | No |
| **Adding an enum value** | **Yes** — same problem as REST |
| Removing a field | Yes — **but you can measure who uses it** |
| `T` → `T!` (narrowing) | No |
| `T!` → `T` (widening) | Yes |

💡 **The killer feature is precise field usage measurement.** Because every query names its fields, you know exactly which clients use a field before removing it — impossible with REST, where receiving a field tells you nothing about whether it is read.

```python
for field_path in extract_fields(document_ast):
    field_usage.labels(field=field_path, client=client_id).inc()
```

**Deprecate with `@deprecated`, watch usage reach zero, then remove.** That is the deprecation process from [[05.2 - Versioning Pagination and Filtering]] with real data instead of guesswork.

## Codebase

**Repo:** `graphql-python/graphql-core`, `strawberry-graphql/strawberry`, `saleor/saleor`

**Question to answer:** How does a GraphQL server turn a query string into a response? Trace parse → validate → execute → serialise. Where in execution is the N+1 problem created, and what would need to change to avoid it?

**Read, in order:**

1. `graphql-core/src/graphql/language/parser.py` — query string to AST. Skim; structure matters more than detail
2. `graphql-core/src/graphql/validation/validate.py` and `rules/` — **each rule is a small visitor.** Read `no_unused_variables.py` and `fields_on_correct_type.py`, because this is where you will add complexity limits later
3. `graphql-core/src/graphql/execution/execute.py` — **the heart.** `execute_fields`, `resolve_field`, `complete_value`. **The N+1 answer is in `complete_list_value`** — each list item resolves its children independently
4. `strawberry/schema/schema.py` and `strawberry/extensions/` — the modern typed layer, and the hook points where tracing and cost analysis attach
5. `saleor/saleor/graphql/api.py` and any `dataloaders.py` — a large real schema and how they solve it in production

💡 Reading `complete_value` is what makes GraphQL performance intuitive rather than mysterious. **The execution algorithm is depth-first per field and has no knowledge that two sibling resolvers are about to fetch related data.**

**Size:** 2–3 sessions.

## Exercise

**Drill 5.4 — Build a GraphQL engine**

Not a wrapper around a library. The engine.

```
drills/05-graphql-core/
├── engine/{lexer.py, parser.py, schema.py, validate.py, execute.py, serialise.py}
├── tests/{test_parser.py, test_execution.py, test_nullability.py, test_errors.py}
├── schema/{conduit.graphql, resolvers.py}
├── observe/{field_timing.py, n_plus_one.py}
└── README.md
```

**Part 1 — Parse.** Lexer and parser for queries, mutations, variables, arguments, aliases, fragments, inline fragments and directives.

Test with nastier input: deep nesting, **fragment cycles (must be rejected)**, unclosed braces, a 1MB query string.

**Part 2 — Validate.** Field exists on type, argument types match, required arguments present, no fragment cycles, variables used and defined, fragments spread on compatible types.

Each rule as a separate visitor. **This is the extension point for complexity limits in drill 5.8**, so build it to be extended.

**Part 3 — Execute.** Resolve fields, complete values, handle lists and nullability propagation, collect errors with paths.

**Nullability propagation is the subtle part.** Test a resolver throwing on a `String!` nested inside a `Document!` inside a `[Document!]!` — the error must bubble to the right level and null the right thing. Get it wrong and your engine silently returns wrong shapes.

**Part 4 — Watch N+1 happen.** A schema over an in-memory dataset with a call counter on every fetch.

Query 20 documents, each with an author and a source. **You should see 41 calls.** Print the log with timestamps and observe they are sequential. Scale to 100 and confirm linear growth.

**Do not fix it yet — this number is the motivation for drill 5.6.**

**Part 5 — Field-level timing.** Instrument every resolver with path and duration:

```
Query.documents           4ms
  Document.author  × 20  38ms
  Document.source  × 20  35ms
```

Building this makes production GraphQL tracing comprehensible.

**Part 6 — A real schema.** Model Conduit properly: documents, sources, annotations, users, organisations. Connections, interfaces for search results, mutations with payload errors.

Then write five realistic client queries and run them all.

**Part 7 — Compare with the real thing.** Run the same schema and queries through Strawberry. Compare output correctness, error formatting and performance. **Where your engine is wrong, fix it.**

**Done when:**
- Your parser handles fragments, variables and aliases, and rejects cycles
- Nullability propagation is correct at three levels of nesting
- Your N+1 counter shows 41 calls and you can explain why from the algorithm
- Field timing produces a per-query breakdown
- Five realistic Conduit queries execute correctly
- Output matches Strawberry's for the same schema and queries
