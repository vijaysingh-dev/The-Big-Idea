# Testing Triggers and Bulk Behaviour

## The test that misses everything

```java
@IsTest
static void testTrigger() {
    Warranty_Claim__c claim = new Warranty_Claim__c(
        Asset__c = assetId, Claim_Amount__c = 150000
    );
    insert claim;

    Assert.areEqual('Manager', [
        SELECT Approval_Tier__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ].Approval_Tier__c);
}
```

It asserts something, which is better than nothing. It proves nothing about the property most likely to be wrong: **bulk safety.**

A query inside a loop passes this test and fails in production on the first data load.

## The bulk test

```java
@IsTest
static void derivedFieldsAreCorrectForTwoHundredClaims() {
    List<Asset> assets = TestDataFactory.createAssets(50);

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
    for (Integer i = 0; i < 200; i++) {
        // four claims per asset — the distribution that exposes aggregation bugs
        claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 600000));
    }

    Test.startTest();
    insert claims;

    Assert.isTrue(Limits.getQueries() < 30,
        'Expected well under the query limit, used ' + Limits.getQueries());
    Test.stopTest();

    List<Warranty_Claim__c> saved = [
        SELECT Approval_Tier__c, Region__c FROM Warranty_Claim__c WHERE Id IN :claims
    ];
    Assert.areEqual(200, saved.size(), 'All 200 should save');
    for (Warranty_Claim__c claim : saved) {
        Assert.areEqual('Executive', claim.Approval_Tier__c);
        Assert.isNotNull(claim.Region__c, 'The region should be stamped from the asset account');
    }
}
```

Three things this catches that the single-record test does not: a query in a loop, a DML in a loop, and derived fields computed only for the first record.

## The distribution matters

```java
// 200 claims across 200 assets — passes even with a broken aggregation
for (Integer i = 0; i < 200; i++) {
    claims.add(buildClaim(assets[i].Id, 10000));
}

// 200 claims across 50 assets — a broken aggregation fails
for (Integer i = 0; i < 200; i++) {
    claims.add(buildClaim(assets[Math.mod(i, 50)].Id, 10000));
}
```

**A one-to-one distribution hides aggregation defects.** A roll-up that overwrites rather than accumulates produces the right answer when every parent has exactly one child.

The rule: **several children per parent, always.**

```java
@IsTest
static void rollupCountsAllClaimsPerAsset() {
    List<Asset> assets = TestDataFactory.createAssets(50);
    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
    for (Integer i = 0; i < 200; i++) {
        claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 10000));
    }

    Test.startTest();
    insert claims;
    Test.stopTest();

    Map<Id, Asset> refreshed = new Map<Id, Asset>([
        SELECT Id, Open_Claim_Count__c, Total_Claim_Value__c FROM Asset WHERE Id IN :assets
    ]);

    for (Asset asset : assets) {
        Assert.areEqual(4, refreshed.get(asset.Id).Open_Claim_Count__c,
            'Each asset should have four claims');
        Assert.areEqual(40000, refreshed.get(asset.Id).Total_Claim_Value__c,
            'Each asset should total 40000');
    }
}
```

## Testing every event

A handler covering seven events needs the events exercised.

```java
@IsTest
static void deletingClaimsRecalculatesTheAssetRollup() {
    Asset asset = TestDataFactory.createAsset();
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(asset.Id, 4);

    Test.startTest();
    delete claims[0];
    Test.stopTest();

    Assert.areEqual(3, refresh(asset).Open_Claim_Count__c,
        'Deleting a claim should decrement the count');
}

@IsTest
static void undeletingAClaimRestoresTheRollup() {
    Asset asset = TestDataFactory.createAsset();
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(asset.Id, 4);
    delete claims[0];

    Test.startTest();
    undelete claims[0];
    Test.stopTest();

    // the event most hand-rolled roll-ups forget entirely
    Assert.areEqual(4, refresh(asset).Open_Claim_Count__c,
        'Restoring a claim should restore the count');
}
```

**The undelete case is the one most often missing**, and it leaves the aggregate permanently wrong when a record is restored. See [[11.2 - Trigger Context Variables]].

## Testing reparenting

The other roll-up subtlety.

```java
@IsTest
static void reparentingAClaimUpdatesBothAssets() {
    Asset oldAsset = TestDataFactory.createAsset();
    Asset newAsset = TestDataFactory.createAsset();
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(oldAsset.Id, 3);

    Test.startTest();
    claims[0].Asset__c = newAsset.Id;
    update claims[0];
    Test.stopTest();

    Assert.areEqual(2, refresh(oldAsset).Open_Claim_Count__c,
        'The old asset should lose a claim');
    Assert.areEqual(1, refresh(newAsset).Open_Claim_Count__c,
        'The new asset should gain one');
}
```

Handlers that collect only the new parent's Id pass every other test and fail this one, leaving the old parent's total stale forever.

## Testing change detection

```java
@IsTest
static void editingAnApprovedClaimDoesNotCreateASecondPayment() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();
    claim.Status__c = 'Approved';
    update claim;

    Assert.areEqual(1, [SELECT COUNT() FROM Claim_Payment__c]);

    Test.startTest();
    // an unrelated edit to an already-approved claim
    claim.Fault_Description__c = 'Updated after re-inspection';
    update claim;
    Test.stopTest();

    Assert.areEqual(1, [SELECT COUNT() FROM Claim_Payment__c],
        'Only the transition into Approved should create a payment');
}
```

**This is the duplicate-payment bug**, and it is invisible to any test that saves the record once. A handler without an `oldMap` comparison passes the approval test and fails this one.

## Testing the recursion guard

```java
@IsTest
static void aSecondBatchInTheSameTransactionIsStillProcessed() {
    TriggerControl.reset();

    List<Warranty_Claim__c> firstBatch = TestDataFactory.createClaims(200);
    List<Warranty_Claim__c> secondBatch = TestDataFactory.buildClaims(200);

    Test.startTest();
    for (Warranty_Claim__c claim : firstBatch) {
        claim.Status__c = 'Approved';
    }
    update firstBatch;

    // a distinct set in the same transaction — a boolean guard would skip all of it
    insert secondBatch;
    Test.stopTest();

    Assert.areEqual(200, [SELECT COUNT() FROM Claim_Payment__c],
        'One payment per approved claim');

    Integer processed = [
        SELECT COUNT() FROM Warranty_Claim__c
        WHERE Id IN :secondBatch AND Approval_Tier__c != null
    ];
    Assert.areEqual(200, processed,
        'A boolean recursion guard would have silently skipped this entire batch');
}
```

**That second assertion is the whole point.** A `private static Boolean hasRun` guard passes the first and fails the second, and the production symptom — 200 records silently unprocessed during a data load — has no error message. See [[11.6 - Recursion Control and Static Guards]].

## Testing the bypass

```java
@IsTest
static void bypassPreventsAllHandlerWork() {
    insert new Automation_Settings__c(
        SetupOwnerId = UserInfo.getOrganizationId(),
        Disable_All_Automation__c = true
    );

    Warranty_Claim__c claim = TestDataFactory.buildClaim(600000);

    Test.startTest();
    insert claim;
    Test.stopTest();

    Assert.isNull([
        SELECT Approval_Tier__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ].Approval_Tier__c, 'The bypass should prevent derived field assignment');
}
```

**An untested bypass is worse than none**, because you will reach for it during an incident and discover it does not work. See [[11.5 - Trigger Handler Pattern]].

## Testing partial success

```java
@IsTest
static void oneInvalidClaimDoesNotBlockTheOtherHundredAndNinetyNine() {
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(200);
    claims[50].Claim_Amount__c = -1;   // violates a validation rule

    Test.startTest();
    List<Database.SaveResult> results = Database.insert(claims, false);
    Test.stopTest();

    Integer succeeded = 0;
    for (Database.SaveResult result : results) {
        if (result.isSuccess()) {
            succeeded++;
        }
    }

    Assert.areEqual(199, succeeded, 'One bad record should not block the rest');
    Assert.isFalse(results[50].isSuccess());
    Assert.areEqual(StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION,
        results[50].getErrors()[0].getStatusCode());
}
```

**Asserting on the specific index** verifies that results are aligned with the input, which is the property code depends on when reporting per-record failures. See [[10.2 - Database Class Methods and Partial Success]].

## Testing validation

```java
@IsTest
static void aClaimOverItsCoverageLimitIsBlocked() {
    TestScenarioFactory.CoveredAssetScenario scenario =
        TestScenarioFactory.coveredAsset(500000);

    Warranty_Claim__c claim = TestDataFactory.buildClaim(scenario.asset.Id, 900000);

    Test.startTest();
    Database.SaveResult result = Database.insert(claim, false);
    Test.stopTest();

    Assert.isFalse(result.isSuccess(), 'A claim over its coverage limit should be blocked');
    Assert.areEqual('Claim_Amount__c', result.getErrors()[0].getFields()[0],
        'The error should be on the amount field, not the record');
}
```

**Asserting on the field** verifies that `addError(fieldName, message)` was used rather than the record-level form, which is a meaningfully better user experience and easy to regress.

## The mixed-DML trap in trigger tests

```java
@IsTest
static void assigningAPermissionSetFromATriggerWorks() {
    User engineer;

    // user creation inside runAs, so the setup DML does not conflict with the record DML
    System.runAs(new User(Id = UserInfo.getUserId())) {
        engineer = TestUserFactory.create('Service Engineer', null);
    }

    Test.startTest();
    insert TestDataFactory.buildClaim(600000);
    Test.stopTest();

    Assert.areEqual(1, [
        SELECT COUNT() FROM PermissionSetAssignment
        WHERE AssigneeId = :engineer.Id AND PermissionSet.Name = 'Claim_Approver'

}
```

## Practical guidance

**Always 200 records**, with several children per parent.

**Test every event the handler declares**, including undelete.

**Test reparenting** for anything maintaining a parent aggregate.

**Test that an unrelated edit does not re-fire** transition logic.

**Test the recursion guard with two distinct batches** in one transaction.

**Test the bypass** — you will need it during an incident.

**Test partial success**, asserting on the specific failing index.

**Assert on the error field**, not just that an error occurred.

**Assert on limit consumption** for anything on a hot object.
