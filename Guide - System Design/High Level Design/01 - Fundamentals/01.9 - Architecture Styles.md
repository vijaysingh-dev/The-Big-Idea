# Architecture Styles: Monolith, Microservices, Modular Monolith

> **Revision tags:** #fundamentals #architecture  
> **Related:** [[01.10 - Advanced Patterns]] | [[01.7 - System Patterns]] | [[05.4 - Build vs Buy]]

---

## The Core Question

Before choosing an architecture style, ask: **what is the primary organizational and operational pain?**  
Architecture styles are solutions to specific problems. A company of 5 engineers has different problems than a company of 500.

---

## Monolith

All application logic is in **one deployable unit**. One codebase, one process, one deploy.

```
[ Single Deployable Unit ]
  ├── User Module
  ├── Order Module
  ├── Payment Module
  ├── Notification Module
  └── Shared Database
```

### Advantages

- **Simple development:** No distributed systems complexity — function calls, not network calls
- **Simple deployment:** One binary/container to build, test, and ship
- **Easy debugging:** Single process, single stack trace
- **No network latency** between modules
- **ACID transactions** across the entire application — no distributed transactions needed
- **Refactoring is easy** — the compiler/type system catches cross-module changes

### Disadvantages

- **Deployment coupling:** A change in the Notification module forces redeployment of everything
- **Scaling coupling:** Can't scale Payment independently from Notifications
- **Tech stack lock-in:** Whole app uses the same language/framework
- **Team coupling:** Large teams step on each other in the same codebase
- **Long CI/CD times** as the codebase grows
- **Single point of failure:** A memory leak in one module can crash all modules

### When to Use

- Early-stage product (you don't know the domain boundaries yet)
- Small team (< 20 engineers)
- Low operational complexity is more valuable than scale
- You're prototyping or proving a concept

**Truth:** Most successful companies started with a monolith (Amazon, Twitter, Shopify, Airbnb). They moved to microservices when the pain of the monolith became greater than the pain of distribution.

---

## Microservices

Each business capability is a **separate independently deployable service** with its own codebase, database, and deployment pipeline.

```
[API Gateway]
     ├──→ [User Service]        → Users DB
     ├──→ [Order Service]       → Orders DB
     ├──→ [Payment Service]     → Payments DB
     └──→ [Notification Service]→ Notification DB
```

### Advantages

- **Independent deployment:** Ship the Payment service without touching Notifications
- **Independent scaling:** Scale only the services under load
- **Team autonomy:** Each team owns one service end-to-end
- **Technology diversity:** Use Rust for low-latency services, Python for ML, Go for network services
- **Fault isolation:** A crash in Notifications doesn't kill Payments

### Disadvantages

- **Distributed systems complexity:** Network failures, latency, partial failures everywhere
- **Distributed transactions are hard:** No cross-service ACID. Requires SAGA pattern.
- **Operational overhead:** N services = N pipelines, N monitoring dashboards, N on-call rotations
- **Network overhead:** Modules that were in-process function calls are now network calls
- **Service discovery and API versioning:** Services need to find each other and evolve contracts carefully
- **Testing is harder:** Need contract tests, end-to-end tests span many services
- **Data duplication:** Each service has its own DB, so shared data is replicated

### When to Use

- Large engineering organization (100+ engineers) where team autonomy matters
- Different services have dramatically different scaling needs
- Different teams need to deploy independently
- Domain boundaries are well-understood (don't decompose prematurely)

## Modular Monolith

A **single deployable unit** with **strong internal module boundaries** — modules don't share databases or bypass each other's interfaces.

```
[ Single Deployable Unit ]
  ├── [ User Module ]      → has its own schema/tables, exposes an API
  ├── [ Order Module ]     → has its own schema/tables, exposes an API
  ├── [ Payment Module ]   → has its own schema/tables, exposes an API
  └── [ Notification Module ] → has its own schema/tables
       Modules communicate via internal interfaces, NOT direct DB access
```

### Advantages

- Preserves monolith simplicity (one deploy, no network overhead, full ACID)
- Strong module boundaries prevent the "big ball of mud" degradation
- **Easy to extract into microservices later** if needed — the boundaries are already drawn
- Scales vertically easily; can be horizontally scaled behind a load balancer
- Developer productivity of a monolith with architectural discipline of microservices

### Disadvantages

- Still deployment-coupled (all modules deploy together)
- Still scaling-coupled (can't scale one module independently)
- Requires discipline to maintain module boundaries as the codebase grows
- Still single-language/framework

### When to Use

- Teams that need to grow beyond a monolith but aren't ready for microservices
- When you want to enforce domain boundaries without full distribution
- When you expect eventual extraction into services but want to defer it
- **This is often the right middle ground for 20-100 engineer teams**

## Comparison Table

| Dimension | Monolith | Modular Monolith | Microservices |
|---|---|---|---|
| Deployment | Single unit | Single unit | Independent per service |
| Scaling | All-or-nothing | All-or-nothing | Per service |
| Developer experience | Simple | Moderate | Complex |
| Operational complexity | Low | Low | High |
| Fault isolation | Low | Low | High |
| Cross-service transactions | ACID (trivial) | ACID (trivial) | Complex (SAGA) |
| Team autonomy | Low | Moderate | High |
| Good for team size | < 20 | 20–100 | 100+ |

## The Migration Path

```
Monolith → (identify pain) → Modular Monolith → (scale pain) → Microservices
```

Don't skip steps. Extracting a service from a modular monolith with clean boundaries is manageable. Extracting a service from an unstructured monolith is a multi-year nightmare (the "strangler fig" pattern exists for this reason).

---

## Common Mistake in Interviews

Saying "I would use microservices" by default signals inexperience. A senior engineer explains:
- "Given this is an early-stage system with a small team, I'd start with a modular monolith."
- "Once we see clear scaling divergence between these two components, I'd extract them as separate services."

The ability to choose the *right* style for the context — and explain the tradeoffs — is what interviewers are evaluating.
