# Trigger Frameworks in the Wild

## What a framework adds

The hand-rolled handler in [[11.5 - Trigger Handler Pattern]] works. A framework standardizes it and adds machinery you would otherwise build per object:

- A consistent shape across every triggered object
- Bypass, implemented once
- Recursion control, implemented once
- Ordered execution of several handlers on one object
- Metadata-driven registration, so adding a handler needs no code change
- Sometimes: a virtual base class subclasses extend

You will encounter these in inherited orgs and be asked about them in interviews. Knowing the common ones and their tradeoffs is more useful than knowing one deeply.

## Kevin O'Hara's TriggerHandler

The most widely used, and the smallest. A single virtual class extended per object.

```java
public with sharing class WarrantyClaimTriggerHandler extends TriggerHandler {

    protected override void beforeUpdate() {
        ClaimService.applyDerivedFields(
            (List<Warranty_Claim__c>) Trigger.new,
            (Map<Id, Warranty_Claim__c>) Trigger.oldMap
        );
    }

    protected override void afterUpdate() {
        ClaimService.handleStatusChanges(
            (List<Warranty_Claim__c>) Trigger.new,
            (Map<Id, Warranty_Claim__c>) Trigger.oldMap
        );
    }
}
```

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, after insert, after update
) {
    new WarrantyClaimTriggerHandler().run();
}
```

What the base class provides:

```java
TriggerHandler.bypass('WarrantyClaimTriggerHandler');
TriggerHandler.clearBypass('WarrantyClaimTriggerHandler');
TriggerHandler.isBypassed('WarrantyClaimTriggerHandler');

// a per-handler recursion cap
setMaxLoopCount(1);
```

**Strengths:** small enough to read in ten minutes, no dependencies, a bypass API that is genuinely useful, and near-universal familiarity in the ecosystem.

**Weaknesses:** the loop counter is a count rather than record tracking, which has the same weakness as a boolean guard in a multi-chunk transaction ([[11.6 - Recursion Control and Static Guards]]). Handler order on one object is still whatever the trigger body says.

## fflib Apex Common

Part of the Apex Enterprise Patterns library, and a different philosophy — the trigger routes into a **Domain** class representing the object's behaviour.

```java
public with sharing class WarrantyClaims extends fflib_SObjectDomain {

    public WarrantyClaims(List<Warranty_Claim__c> records) {
        super(records);
    }

    public override void onApplyDefaults() {
        for (Warranty_Claim__c claim : (List<Warranty_Claim__c>) Records) {
            if (String.isBlank(claim.Status__c)) {
                claim.Status__c = 'Submitted';
            }
        }
    }

    public override void onValidate() {
        ClaimValidationService.validateCoverage((List<Warranty_Claim__c>) Records);
    }

    public override void onAfterUpdate(Map<Id, SObject> existingRecords) {
        ClaimService.handleStatusChanges(
            (List<Warranty_Claim__c>) Records,
            (Map<Id, Warranty_Claim__c>) existingRecords
        );
    }

    public class Constructor implements fflib_SObjectDomain.IConstructable {
        public fflib_SObjectDomain construct(List<SObject> records) {
            return new WarrantyClaims(records);
        }
    }
}
```

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, after insert, after update
) {
    fflib_SObjectDomain.triggerHandler(WarrantyClaims.class);
}
```

fflib brings a whole architecture — Domain, Selector, Service, and Unit of Work — rather than only a trigger framework. See section 18.

**Strengths:** a complete, coherent architecture with strong separation of concerns, excellent testability through the mocking support, and a well-documented body of practice behind it.

**Weaknesses:** a substantial learning curve, considerable ceremony for simple objects, and a team-wide commitment — half-adopting it produces the worst of both worlds.

The honest guidance: **fflib suits large, long-lived orgs with several developers and a genuine need for layered architecture.** For an org with eight triggered objects and one developer, it is more structure than the problem requires.

## Metadata-driven frameworks

Several open-source frameworks register handlers in Custom Metadata rather than in code.

```
Trigger_Handler__mdt
  Object_API_Name__c:  Warranty_Claim__c
  Handler_Class__c:    ClaimValidationHandler
  Event__c:            BEFORE_UPDATE
  Execution_Order__c:  10
  Active__c:           true

  Object_API_Name__c:  Warranty_Claim__c
  Handler_Class__c:    ClaimRoutingHandler
  Event__c:            BEFORE_UPDATE
  Execution_Order__c:  20
  Active__c:           true
```

```java
public with sharing class MetadataTriggerDispatcher {

    public static void run() {
        String objectName = Trigger.isDelete
            ? Trigger.old[0].getSObjectType().getDescribe().getName()
            : Trigger.new[0].getSObjectType().getDescribe().getName();

        for (Trigger_Handler__mdt config : [
            SELECT Handler_Class__c FROM Trigger_Handler__mdt
            WHERE Object_API_Name__c = :objectName
              AND Event__c = :String.valueOf(Trigger.operationType)
              AND Active__c = true
            ORDER BY Execution_Order__c
        ]) {
            Type handlerType = Type.forName(config.Handler_Class__c);
            if (handlerType == null) {
                continue;
            }
            ((TriggerHandlerInterface) handlerType.newInstance()).handle();
        }
    }
}
```

**Strengths:** explicit ordering, handlers can be activated and deactivated without a deployment, and the automation inventory is queryable.

**Weaknesses:** the coupling is invisible to the compiler — deleting a handler class breaks the configuration at runtime rather than at deploy time. The dispatcher costs a query per trigger execution. And `Type.forName` failures need handling, or one bad configuration row breaks the object.

That last point is a real operational risk. A framework where a typo in a metadata record silently disables business logic needs monitoring around it.

## Evaluating a framework

The questions worth asking, whether choosing one or inheriting one:

**Does the recursion guard track record Ids or a count?** A count-based guard has the multi-chunk problem.

**Is bypass available at runtime, not just in code?** During an incident you need to disable automation without a deployment.

**Is handler order explicit?** If it depends on the order of statements in a hand-written body, that is fine and it should be visible.

**Can it be understood in an hour?** A framework nobody understands is a liability, and much of the value of a framework is that a new developer recognizes the shape.

**Does it handle all seven events**, including undelete?

**Does it force logic out of the trigger?** That is the one thing it must do.

## When to write your own

A reasonable default for most orgs, and this course's recommendation for a team starting fresh.

The handler in [[11.5 - Trigger Handler Pattern]] is about forty lines including bypass and recursion control. It has no dependency, no upgrade path to manage, and it can be read in full by anyone joining the team.

Reach for an established framework when:

- The org is large enough that consistency across many developers matters more than simplicity
- You want fflib's full architecture, not just its trigger handling
- The team already knows one

Do not adopt one because it is what a blog post recommended. The cost of a framework nobody on the team understands exceeds the cost of forty lines of handler.

## Inheriting one

When you arrive at an org with a framework already in place:

**Find the base class or dispatcher and read it.** All of it. It is usually a few hundred lines and it determines everything about how automation behaves.

**Find the bypass mechanism.** You will need it, and finding it during an incident is the wrong time.

**Check how recursion is guarded**, and whether it has the multi-chunk weakness.

**Enumerate what is registered**, particularly for metadata-driven frameworks where the wiring is not in code:

```sql
SELECT Object_API_Name__c, Handler_Class__c, Event__c, Execution_Order__c, Active__c
FROM Trigger_Handler__mdt
WHERE Active__c = true
ORDER BY Object_API_Name__c, Event__c, Execution_Order__c
```

**Do not introduce a second framework.** Two frameworks on one object is worse than no framework, and it happens more often than it should — a new developer arrives, dislikes the existing one, and adds theirs alongside.

## Practical guidance

**Any framework is better than logic in the trigger body.**

**A simple hand-rolled handler is a legitimate choice** and usually the right one for a small team.

**Check the recursion guard's design** before trusting it.

**Ensure a runtime bypass exists**, not only a code-level one.

**One framework per org.** Consistency matters more than which.

**Read the base class before using it.** It is the most consequential code in the org.
