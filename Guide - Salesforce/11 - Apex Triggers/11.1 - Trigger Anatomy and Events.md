# Trigger Anatomy and Events

## What a trigger is

Apex that runs automatically when records are saved. It has no return value, no caller, and no way to be invoked directly — the platform runs it as part of the save pipeline.

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    WarrantyClaimTriggerHandler.run();
}
```

That is what a production trigger should look like: **a declaration of events and a single call.** Everything else lives in classes. The reasons are covered in [[11.4 - One Trigger Per Object]] and [[11.5 - Trigger Handler Pattern]].

## The seven events

```
before insert     before update     before delete
after insert      after update      after delete
                                    after undelete
```

There is no `before undelete`. Restoring a record from the recycle bin fires only the after event.

Each event answers a different question:

| Event | Records have Ids | Records writable | Typical use |
| --- | --- | --- | --- |
| before insert | No | Yes, in memory | Defaults, derived fields, validation |
| before update | Yes | Yes, in memory | Same-record field changes, validation |
| before delete | Yes | No | Prevent deletion, read related data |
| after insert | Yes | No | Create related records, roll-ups |
| after update | Yes | No | Cross-object updates, notifications |
| after delete | Yes | No | Recalculate parent aggregates, log |
| after undelete | Yes | No | Restore aggregates, re-index |

## Before versus after, in one sentence

**Before triggers modify the record being saved; after triggers do everything else.**

In a before trigger, assigning to a field on `Trigger.new` is enough — the value is written as part of the same save, with no DML.

```java
// before insert or before update
for (Warranty_Claim__c claim : Trigger.new) {
    claim.Region__c = deriveRegion(claim);
}
// no DML — this is saved with the record
```

In an after trigger, `Trigger.new` is read-only. Updating the triggering records requires a DML statement, which re-enters the entire save pipeline.

An after trigger updating its own records is nearly always a mistake, for the same reason an after-save flow updating `$Record` is. See [[11.3 - Before vs After - Choosing the Right Event]] and [[07.4 - Before-Save vs After-Save Flows]].

## Why after insert exists

The Id. A record has no Id until it is saved, so anything referencing it — a child record, a share row, a log entry — must happen after insert.

```java
// after insert
List<Claim_Part__c> parts = new List<Claim_Part__c>();
for (Warranty_Claim__c claim : Trigger.new) {
    parts.add(new Claim_Part__c(
        Warranty_Claim__c = claim.Id,   // only available after insert
        Product__c = defaultPartId
    ));
}
insert parts;
```

## Delete and undelete

`before delete` and `after delete` both have `Trigger.old`; `Trigger.new` is null.

`after undelete` has `Trigger.new`; `Trigger.old` is null.

**The undelete event is the one most commonly forgotten.** A hand-rolled roll-up that handles insert, update, and delete but not undelete leaves the aggregate permanently wrong when a record is restored. Any handler with a delete case needs an undelete case.

```java
if (Trigger.isAfter && Trigger.isDelete) {
    ClaimRollupService.recalculate(assetIdsFrom(Trigger.old));
}
if (Trigger.isAfter && Trigger.isUndelete) {
    ClaimRollupService.recalculate(assetIdsFrom(Trigger.new));
}
```

A caution from [[02.10 - Delete Behaviour - Cascade and Restrict]]: cascade deletes from a master-detail parent do not reliably fire the child's delete automation. Logic that must run on deletion belongs on the parent.

## addError

Inside a trigger, blocking a save uses `addError()` rather than throwing.

```java
for (Warranty_Claim__c claim : Trigger.new) {
    if (claim.Claim_Amount__c > coverageLimit) {
        claim.addError('Claim_Amount__c',
            'This claim exceeds the coverage limit on the service contract.');
    }
}
```

Three properties that make it the right mechanism:

**It blocks one record, not the transaction.** With `Database.insert(records, false)`, the others still save. Throwing aborts everything.

**`addError(fieldName, message)` places the error next to the field** in the user interface, which is meaningfully better than a page-level message.

**The message reaches the user directly**, so it must be written for them — not for a developer reading a log.

`addError` works in before and after triggers, and in before delete to prevent deletion.

## Triggers on standard and custom objects

Syntax is identical. A few standard objects have restrictions or additional events worth knowing:

**Task and Event** support triggers, and activity behaviour is unusual in several ways.

**CaseComment, EmailMessage, FeedItem** support triggers and are frequently the right place for logic about a conversation.

**OpportunityLineItem, QuoteLineItem** support triggers, though price and total recalculation interacts with them in ways worth testing.

**User** supports triggers and is a setup object, so DML on normal objects from a User trigger throws `MIXED_DML_OPERATION`. See [[10.7 - Mixed DML and Setup Objects]].

**Some objects support no triggers at all** — external objects, big objects, and several system objects.

## Platform event triggers

A different shape, worth recognizing:

```java
trigger EscalationNotificationTrigger on Escalation_Notification__e (after insert) {
    EscalationNotificationHandler.handle(Trigger.new);
}
```

Only `after insert` is supported, because events are published rather than saved. The trigger runs asynchronously, as the Automated Process user by default, in its own transaction with its own limits.

Delivery is at-least-once, so the handler must tolerate being run twice for the same event. See [[12.8 - Platform Events]].

## Trigger metadata

A trigger is a `.trigger` file with a `.trigger-meta.xml` alongside carrying the API version and status.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ApexTrigger xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>62.0</apiVersion>
    <status>Active</status>
</ApexTrigger>
```

Setting `status` to `Inactive` disables the trigger, which is deployable and is the mechanism for turning one off during a migration. Unlike a validation rule, this requires a deployment — which is why a runtime bypass mechanism is worth building. See [[11.5 - Trigger Handler Pattern]].

**Every trigger requires test coverage** for the org to deploy, and the coverage must come from tests that actually exercise it.

## Enumerating triggers in an org

The first thing to run when inheriting an org, alongside the flow inventory from [[07.13 - Order of Execution]]:

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status, ApiVersion, LengthWithoutComments FROM ApexTrigger ORDER BY TableEnumOrId" \
  --target-org production
```

`LengthWithoutComments` is a useful proxy for whether logic lives in the trigger or in a handler. A trigger of 3,000 characters contains business logic that should not be there.

Two triggers on the same object is a signal worth investigating immediately, since their relative order is not controllable.

## What a trigger should never contain

**Business logic.** It belongs in a service class, so it is testable and callable from elsewhere.

**SOQL or DML in a loop.** The universal rule.

**A hardcoded Id.**

**A `try-catch` swallowing exceptions.**

**More than a few lines.** The body should route and nothing else.

```java
// What a production trigger looks like
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    WarrantyClaimTriggerHandler.run();
}
```

Declaring all seven events even when only some are handled is a deliberate choice some teams make — it means adding a new event later needs no trigger change, only a handler change. The cost is that the handler runs on events it does not care about, which is negligible given it returns immediately.

Others prefer declaring only the events actually handled, on the grounds that the trigger declaration documents what the object reacts to. Either is defensible; consistency across the org matters more.
