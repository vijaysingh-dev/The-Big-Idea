# Error Handling, Retries and Idempotency

## The premise

Every integration fails. Networks time out, external systems go down, payloads are rejected, and tokens expire. The design question is not whether but **what happens next**, and an integration without an answer is one that silently loses data.

Three things make an integration survivable: classifying failures correctly, retrying only what should be retried, and making retries safe.

## Classifying failures

The single most important distinction: **transient or permanent.**

A **transient** failure will probably succeed if tried again — a timeout, a 503, a lock contention, a rate limit.

A **permanent** failure will never succeed by retrying — a validation rule rejection, a missing required field, a 400 from a malformed payload, a 401 from a revoked credential.

Retrying a permanent failure a hundred times achieves nothing, burns the async allocation, and fills the log with noise that hides the real problems.

```java
public with sharing class FailureClassifier {

    public enum Outcome { SUCCESS, TRANSIENT, PERMANENT }

    private static final Set<Integer> TRANSIENT_STATUS = new Set<Integer>{
        0,     // no response at all — timeout, DNS, connection refused
        408,   // request timeout
        429,   // rate limited
        500, 502, 503, 504
    };

    public static Outcome classify(Integer statusCode) {
        if (statusCode >= 200 && statusCode < 300) {
            return Outcome.SUCCESS;
        }
        return TRANSIENT_STATUS.contains(statusCode) ? Outcome.TRANSIENT : Outcome.PERMANENT;
    }

    public static Outcome classify(Database.Error error) {
        switch on error.getStatusCode() {
            when UNABLE_TO_LOCK_ROW, ENTITY_IS_LOCKED {
                return Outcome.TRANSIENT;
            }
            when else {
                return Outcome.PERMANENT;
            }
        }
    }
}
```

**Status code 0** in that set represents no HTTP response at all — a `CalloutException` from a timeout or a connection failure. It is the most ambiguous case and is covered below.

**401 is deliberately absent** from the transient list. A single 401 might be an expired token the platform will refresh, but a persistent one means the credential is wrong or revoked — retrying makes it worse by triggering lockouts.

## Retry with backoff

Retrying immediately against a system that is down makes the outage worse. **Exponential backoff** spaces attempts out.

```java
public with sharing class ErpSyncQueueable implements Queueable, Database.AllowsCallouts {

    private final Set<Id> claimIds;
    private final Integer attempt;

    public ErpSyncQueueable(Set<Id> claimIds, Integer attempt) {
        this.claimIds = claimIds;
        this.attempt = attempt;
    }

    public void execute(QueueableContext context) {
        System.attachFinalizer(new SyncFinalizer(claimIds, attempt));
        ErpClient.pushClaims(claimIds);
    }
}
```

```java
public with sharing class SyncFinalizer implements Finalizer {

    private static final Integer MAX_ATTEMPTS = 4;

    private final Set<Id> claimIds;
    private final Integer attempt;

    public SyncFinalizer(Set<Id> claimIds, Integer attempt) {
        this.claimIds = claimIds;
        this.attempt = attempt;
    }

    public void execute(FinalizerContext ctx) {
        if (ctx.getResult() == ParentJobResult.SUCCESS) {
            return;
        }

        Exception cause = ctx.getException();
        logFailure(ctx, cause, attempt);

        if (attempt >= MAX_ATTEMPTS || !isTransient(cause)) {
            markForManualReview(claimIds, cause);
            AlertingService.integrationFailed('ErpSync', claimIds.size(), cause?.getMessage());
            return;
        }

        // 2, 4, 8 minutes — capped at the platform's ten-minute enqueue delay
        Integer delay = Math.min((Integer) Math.pow(2, attempt), 10);
        System.enqueueJob(new ErpSyncQueueable(claimIds, attempt + 1), delay);
    }
}
```

Four things make this correct:

**A Finalizer**, because it runs in its own transaction even when the job failed uncatchably. It is the only mechanism with a guaranteed post-failure hook. See [[12.6 - Transaction Finalizers]].

**A maximum attempt count.** Without it, a permanently broken endpoint produces an infinite chain consuming the org's daily async budget.

**Backoff capped at ten minutes**, the platform's maximum enqueue delay.

**Alerting on final failure only**, not on every attempt, so the channel stays readable.

## Idempotency

Retries are only safe if repeating an operation has the same effect as performing it once.

**Inbound**, this comes from external IDs and upsert:

```java
// Rerunning this updates rather than duplicating
Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);
```

**Outbound**, it comes from sending a key the receiver can deduplicate on:

```java
req.setHeader('Idempotency-Key', claim.Id + '-' + claim.LastModifiedDate.getTime());
```

Including `LastModifiedDate` means a genuinely new change produces a new key, while a retry of the same change reuses it.

Where the external system offers no idempotency support, the fallback is **checking before acting**:

```java
public with sharing class ErpSubmissionService {

    public static void submit(Set<Id> claimIds) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Claim_Number__c, ERP_Confirmation__c
            FROM Warranty_Claim__c
            WHERE Id IN :claimIds AND ERP_Confirmation__c = null
        ];

        // filtering on the confirmation field means an already-submitted claim is skipped
        if (claims.isEmpty()) {
            return;
        }

        for (Warranty_Claim__c claim : claims) {
            ErpClient.Response response = ErpClient.post('/api/claims',
                ClaimPayload.from(claim));

            if (response.isSuccess) {
                claim.ERP_Confirmation__c = parseConfirmation(response.body);
            }
        }

        Database.update(claims, false);
    }
}
```

The stored confirmation number is the idempotency marker. A retry queries again, finds the field populated, and skips.

## The ambiguous timeout

The hardest case in integration, and it deserves naming explicitly.

A request times out. Did the external system process it or not? You do not know. The connection dropped before the response arrived; the work may have completed.

Retrying risks a duplicate. Not retrying risks a lost record.

The resolutions, in order of preference:

**1. Make the operation idempotent** with an idempotency key. Then retry freely — the receiver deduplicates. This is why the header matters.

**2. Query before retrying.** If the external system exposes a lookup by your reference, check whether the record exists before resubmitting.

```java
public static void retryAfterTimeout(Warranty_Claim__c claim) {
    // confirm the state at the far end before assuming the first attempt failed
    ErpClient.Response check = ErpClient.get('/api/claims?reference=' + claim.Claim_Number__c);

    if (check.isSuccess && containsClaim(check.body)) {
        claim.ERP_Confirmation__c = parseConfirmation(check.body);
        update claim;
        return;
    }

    ErpClient.post('/api/claims', ClaimPayload.from(claim));
}
```

**3. Flag for manual review.** Where neither is possible, mark the record and let a human resolve it. Unsatisfying, and better than silently duplicating financial records.

Deciding this up front, with the external system's owner, is part of the integration design. Discovering it during an incident is worse.

## Logging

An integration with no callout log is undiagnosable.

```java
public with sharing class IntegrationLogger {

    public static void logCallout(
        String system, String method, String path,
        Integer statusCode, Long durationMs, String correlationId, String errorBody
    ) {
        // a platform event, so the log survives a rollback of the calling transaction
        EventBus.publish(new Integration_Log__e(
            System__c = system,
            Method__c = method,
            Path__c = path,
            Status_Code__c = statusCode,
            Duration_Ms__c = durationMs,
            Correlation_Id__c = correlationId,
            Error_Body__c = errorBody?.left(5000),
            Logged_At__c = Datetime.now()
        ));
    }
}
```

What to record: the system, the operation, the status, the duration, a correlation Id, and the response body **on failure only**.

What **not** to record: request bodies containing personal data, payment details, or credentials. A log table full of customer information is a compliance problem created by well-intentioned debugging.

Duration matters as much as status. An external system whose median response time doubled last week is degrading, and that is visible long before it starts returning errors.

## Correlation Ids

The thing that makes cross-system debugging possible.

```java
String correlationId = String.valueOf(Crypto.getRandomLong());

req.setHeader('X-Correlation-Id', correlationId);
IntegrationLogger.logCallout('ERP', 'POST', '/api/claims', status, duration, correlationId, null);
```

The same Id appears in your log and in the external system's log. "The claim we sent at 09:32" becomes "correlation Id 4471829", which either system can search.

For an event-driven flow, carrying the correlation Id through the event payload links the publishing transaction to the subscriber's. See [[12.8 - Platform Events]].

## Dead letter handling

Records that failed permanently, or exhausted their retries, need somewhere to go.

```java
private static void markForManualReview(Set<Id> claimIds, Exception cause) {
    List<Integration_Failure__c> failures = new List<Integration_Failure__c>();

    for (Id claimId : claimIds) {
        failures.add(new Integration_Failure__c(
            Record_Id__c = claimId,
            System__c = 'ERP',
            Operation__c = 'ClaimSync',
            Error_Message__c = cause?.getMessage(),
            Attempts__c = MAX_ATTEMPTS,
            Status__c = 'Needs Review',
            Failed_At__c = Datetime.now()
        ));
    }

    insert failures;
}
```

A queryable, reportable object beats an error email nobody reads. A dashboard showing open failures by system and age is what turns silent data loss into a work queue somebody clears.

The record must carry enough to **replay** the operation — the record Id, the operation, and any parameters — so resolution is a button rather than a manual reconstruction.

## Reconciliation

Retries and logging catch failures you know about. **Reconciliation** catches divergence you do not.

```java
public with sharing class ClaimReconciliationBatch
    implements Database.Batchable<SObject>, Database.AllowsCallouts, Database.Stateful {

    private Integer missingInErp = 0;
    private Integer amountMismatches = 0;

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Number__c, Claim_Amount__c, ERP_Confirmation__c
            FROM Warranty_Claim__c
            WHERE Status__c = 'Approved' AND Approved_Date__c = LAST_N_DAYS:7
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        // one lookup for the chunk, comparing what each system believes
        Map<String, ErpClaimDto> erpClaims = ErpClient.lookupBatch(claimNumbers(scope));

        List<Integration_Failure__c> discrepancies = new List<Integration_Failure__c>();

        for (Warranty_Claim__c claim : scope) {
            ErpClaimDto erp = erpClaims.get(claim.Claim_Number__c);

            if (erp == null) {
                missingInErp++;
                discrepancies.add(buildDiscrepancy(claim, 'Missing in ERP'));
            } else if (erp.amount != claim.Claim_Amount__c) {
                amountMismatches++;
                discrepancies.add(buildDiscrepancy(claim, 'Amount mismatch'));
            }
        }

        if (!discrepancies.isEmpty()) {
            insert discrepancies;
        }
    }

    public void finish(Database.BatchableContext ctx) {
        insert new Reconciliation_Run__c(
            System__c = 'ERP',
            Missing_Records__c = missingInErp,
            Mismatches__c = amountMismatches,
            Run_Date__c = Date.today()
        );
    }
}
```

Running weekly, this catches the records that were lost without anyone noticing — the ones where a retry chain gave up, or a subscriber was down past the event retention window, or someone edited a record in a way that never synced.

**Every integration that matters should have a reconciliation job.** Silent divergence is the failure mode nobody has a symptom for.

## Alerting on absence

The failure mode monitoring usually misses.

An integration that **stopped running** produces no errors. The job is not failing; it is not executing. Nothing in `AsyncApexJob` shows a problem, and the first symptom is a user asking why data is stale.

```sql
SELECT System__c, MAX(Started_At__c) lastRun
FROM Integration_Run__c
GROUP BY System__c
```

Any system whose last run is older than its expected interval is broken. A daily check on that query, alerting on staleness, is the only thing that catches it.

The same applies to event subscribers — a crashed Pub/Sub consumer looks healthy from inside Salesforce while events age out of retention. See [[13.9 - Pub-Sub API and Event Relay]].

## Circuit breaking

When an external system is down, continuing to call it wastes callout budget and delays recovery.

```java
public with sharing class CircuitBreaker {

    public static Boolean isOpen(String systemName) {
        Integration_Circuit__c circuit = Integration_Circuit__c.getInstance(systemName);
        if (circuit == null || circuit.Open_Until__c == null) {
            return false;
        }
        return circuit.Open_Until__c > Datetime.now();
    }

    public static void recordFailure(String systemName, Integer consecutiveFailures) {
        if (consecutiveFailures < 5) {
            return;
        }
        // stop calling for five minutes, then allow a probe attempt
        upsert new Integration_Circuit__c(
            Name = systemName,
            Open_Until__c = Datetime.now().addMinutes(5),
            Consecutive_Failures__c = consecutiveFailures
        );
    }
}
```

Callers check the breaker before attempting, and queue the work instead:

```java
if (CircuitBreaker.isOpen('ERP')) {
    deferToRetryQueue(claimIds);
    return;
}
```

Worth building when an external system's outages are frequent enough to matter. Over-engineering for a stable system is not.

## Practical guidance

**Classify every failure as transient or permanent** before deciding to retry.

**Cap retries and back off exponentially.**

**Use a Finalizer**, the only guaranteed post-failure hook.

**Send an idempotency key** on every write to an external system.

**Decide the timeout policy explicitly** with the external system's owner.

**Log every callout** through a platform event, with correlation Id and duration, and without sensitive payloads.

**Write permanent failures to a queryable object**, with enough context to replay.

**Run a reconciliation job.** It catches what monitoring does not.

**Alert on absence, not just failure.**
