# Batching and the Update Queue

**Batching** is grouping several state updates into a single re-render. Without it, every `setState` would trigger a full render pass.

```jsx
function handleClick() {
  setCount(c => c + 1);
  setFlag(true);
  setName("x");
}
// one render, not three
```

## Automatic batching

Before React 18, batching applied only inside React event handlers. Updates in timeouts, promises and native event listeners each triggered their own render:

```jsx
// React 17
setTimeout(() => {
  setA(1);   // render
  setB(2);   // render
}, 0);

// React 18+
setTimeout(() => {
  setA(1);
  setB(2);
}, 0);       // one render
```

React 18's `createRoot` batches **everywhere** — timers, promises, native handlers, any context. This is called automatic batching, and it was one of the main behavioral changes in the upgrade.

The rare code that relied on a render between two updates broke. The escape hatch is `flushSync`.

## The update queue

Each stateful hook holds a **circular linked list of pending updates** on its fiber ([[18.3 - Fiber Architecture]]).

```js
{
  memoizedState: 0,            // current value
  queue: {
    pending: update3 → update1 → update2 → update3   // circular
  }
}
```

Calling `setState` appends an update object to the queue and schedules a render. During the render, React walks the queue from the base state and applies each update in order:

```jsx
setCount(c => c + 1);   // update: (c) => c + 1
setCount(10);           // update: 10  — replaces
setCount(c => c * 2);   // update: (c) => c * 2

// base 0 → 1 → 10 → 20
```

Values replace; functions transform. Mixing them is legal and the order is exactly the call order.

This is why the updater form is required when the new value depends on the old one — a plain value captures the *render's* snapshot, while an updater receives the running result ([[16.4 - State and useState Mental Model]]).

Note that updater functions must be pure: React may run the queue twice in Strict Mode to check.

## The eager state bailout

An optimization worth knowing because it produces confusing behavior.

When the queue is empty, React computes the new state **eagerly** at the call site. If it equals the current state by `Object.is`, no render is scheduled at all:

```jsx
const [count, setCount] = useState(0);
setCount(0);   // no render scheduled
```

But if the queue is non-empty, React cannot compute the result without processing everything, so it schedules a render and bails out later — meaning the component function may still run once even though nothing changed.

Practical consequence: you cannot rely on "setting the same value never re-renders". It usually does not, sometimes it does.

## Bailing out mid-tree

If a component re-renders but produces the same element references, React can skip its children:

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return <div onClick={() => setCount(c => c + 1)}>{children}</div>;
}
```

`children` came from the parent as a prop, so it is the same element reference every render — React skips reconciling that subtree entirely ([[18.1 - Virtual DOM and React Elements]]). This is why composition avoids re-renders that memoization would otherwise be needed for.

## flushSync

Opts out of batching, forcing a synchronous render and commit:

```jsx
import { flushSync } from "react-dom";

function handleAdd() {
  flushSync(() => {
    setItems([...items, newItem]);
  });
  // the DOM now contains the new item
  listRef.current.lastElementChild.scrollIntoView();
}
```

Without it, the new item is not in the DOM when `scrollIntoView` runs.

The cost is real: it forces a full synchronous render and commit, disabling concurrent scheduling for that update. Two `flushSync` calls in one handler produce two renders and two layout passes.

Use it only when you must read or manipulate the DOM immediately after a state change within the same handler. A `useLayoutEffect` is usually the better answer ([[17.5 - useLayoutEffect vs useEffect]]).

## Batching across priorities

Updates are batched **per lane**, not globally ([[18.5 - Concurrent Rendering and the Scheduler]]):

```jsx
setUrgent(1);                              // SyncLane
startTransition(() => setDeferred(2));     // TransitionLane
```

These do not batch together. The urgent update commits first; the transition renders afterwards and can be interrupted. That separation is the entire point of transitions.

## Batching in async functions

```jsx
async function handleSubmit() {
  setLoading(true);                  // batch 1
  const data = await save(form);     // await splits the batches
  setLoading(false);                 // batch 2
  setData(data);                     // batch 2
}
```

Everything before the first `await` batches together; everything after it batches separately. Each `await` is a task boundary, so React starts a new batch — which is correct and desirable, since the loading state needs to be visible during the request.

## Interaction with external stores

A store that notifies subscribers synchronously outside React's batching used to cause a render per subscriber. `useSyncExternalStore` integrates with React's scheduling so store updates batch normally ([[17.12 - Lesser Known Hooks]]).

The legacy `unstable_batchedUpdates` export existed for libraries to force batching before React 18. It is no longer needed.

## What batching does not do

**It does not deduplicate.** Three different setState calls to three different hooks still produce three queue entries; they just share one render.

**It does not delay effects.** Effects run after the single resulting commit, once.

**It does not make renders cheaper.** It reduces the *number* of renders, not the cost of each.

## How senior engineers actually use this

**They rely on automatic batching** and no longer write code that assumes a render between two updates.

**They use the updater form** whenever an update depends on the previous value, since the queue applies updates in order against the running result.

**They avoid `flushSync`** and treat needing it as a signal to reconsider — usually a layout effect or a ref-based measurement is cleaner.

**They know that `await` splits batches**, which is why loading states work correctly in async handlers without extra effort.

## Common pitfalls

- Expecting state to be readable immediately after `setState`.
- `setCount(count + 1)` several times in one handler producing one increment.
- Code written for React 17 that relied on unbatched updates in timeouts or promises.
- `flushSync` used casually, producing extra synchronous renders.
- Assuming setting the same value never re-renders — the eager bailout only applies when the queue is empty.
- Expecting urgent and transition updates to batch together.

## Interview angle

"What is batching in React" plus "what changed in React 18" is a common pairing. Explain batching as grouping updates into one render, and that React 18 extended it from React event handlers to everywhere, including promises and timers. The depth comes from the update queue — a linked list applied in order, with values replacing and functions transforming — which directly explains why the updater form is necessary. Mentioning `flushSync` as the deliberate escape hatch, and that `await` splits batches, rounds it out.
