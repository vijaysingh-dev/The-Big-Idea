# Profiling Memory in DevTools

Finding a leak is a mechanical process, not an act of insight. The workflow below finds the retaining reference in most cases within ten minutes.

## Is it actually a leak?

Memory always grows between collections — that is normal ([[07.1 - How Garbage Collection Works]]). A leak is memory that survives repeated GCs.

Start in the **Performance panel** with "Memory" checked. Record while exercising the app, and read the JS Heap line:

```
Sawtooth pattern (up, drop, up, drop)     -> healthy
Staircase (each drop higher than the last) -> leak
```

The Performance Monitor (Command Menu → "Show Performance Monitor") gives the same signal live, plus DOM node count and listener count — which are often more diagnostic than heap size, because a rising DOM node count with a stable UI is unambiguous.

## The three-snapshot technique

The standard method for finding what leaks across a repeated action.

1. Open **Memory** → Heap snapshot. Click the collect-garbage icon first.
2. Take **Snapshot 1** (baseline).
3. Perform the suspect action several times — navigate to a route and back, open and close a modal, mount and unmount a chart. Ten iterations is usually enough.
4. Return to the starting state. Force GC.
5. Take **Snapshot 2**.
6. Repeat the action the same number of times, return, force GC, take **Snapshot 3**.

Now select Snapshot 3 and switch the dropdown to **Comparison**, comparing against Snapshot 2.

Objects with a positive **Delta** that appear in both comparisons are leaking. One growth could be lazy initialization; growth that repeats identically is a leak.

The reason for three snapshots rather than two: the first round of an action often allocates caches and module-level state that legitimately persist. Comparing the second round against the third removes that noise.

## Reading the retainer tree

Select a leaked object. The **Retainers** panel at the bottom shows the chain of references keeping it alive, read bottom-up from the GC root.

A typical chain:

```
Detached HTMLDivElement
  in nodes  (Map)
    in current  (Object)
      in useRef closure
        in ChartComponent
```

That reads: a `useRef` holds a `Map` called `nodes` which holds the detached element. The fix is to clear the map on unmount.

Two columns to understand:

- **Shallow size** — memory the object itself occupies.
- **Retained size** — memory freed if this object were collected, including everything only it references.

Sort by retained size to find the objects that matter. A 40-byte closure with a 50 MB retained size is your leak; a 5 MB array retaining only itself usually is not.

Yellow entries have direct JS references; red entries are detached DOM nodes reachable only through other detached nodes.

## Finding detached DOM

The highest-value single filter. In a heap snapshot, type `Detached` into the class filter box.

```
Detached HTMLDivElement × 1
Detached HTMLTableElement × 12    <- twelve mount/unmount cycles, twelve leaks
```

A count that matches your iteration count is conclusive. Click one and read its retainer chain.

Chrome also has a **Detached Elements** panel (available as a separate DevTools tab in recent versions) that lists detached nodes directly without taking a snapshot.

## Allocation instrumentation on timeline

The Memory panel's second option records allocations over time as blue bars. Bars that stay blue after the recording ends were never collected.

Useful when you know memory is growing but not which action causes it — record for thirty seconds of normal use, then look for the tall surviving bars and click into their allocation stack, which shows the exact line that allocated them.

The **Allocation sampling** option is the lighter-weight variant: it samples rather than records everything, so it can run for minutes without slowing the page to a crawl. Use it for long sessions.

## Practical checklist when memory grows

Work through these in order; they cover the large majority of real leaks.

1. **Timers** — is every `setInterval` cleared? ([[07.2 - Memory Leaks from Closures and Timers]])
2. **Listeners** — is the Performance Monitor's listener count rising? Check `window` and `document` handlers.
3. **Detached nodes** — filter a snapshot for `Detached`.
4. **Caches** — any `Map` or array that only grows? ([[07.4 - WeakMap WeakSet and WeakRef]])
5. **Third-party widgets** — is `destroy()` called on unmount?
6. **Observers** — is `disconnect()` called?
7. **Store subscriptions** — does every subscribe have a matching unsubscribe?

## Measuring in production

`performance.memory.usedJSHeapSize` (Chrome only) can be sampled and reported, but it is quantized and excludes DOM memory. The standardized replacement is `performance.measureUserAgentSpecificMemory()`, which includes DOM and worker memory but requires cross-origin isolation.

More practically, most teams monitor proxies for leaks rather than memory itself: session length before a crash, out-of-memory error rates, and rising DOM node counts reported from RUM ([[28.13 - Frontend Observability]]).

## How senior engineers actually use this

**They test the navigation loop before shipping any route-level feature.** Mount, unmount, repeat, snapshot. It takes five minutes and catches the class of bug that only appears after an hour of user activity.

**They read retained size, not shallow size.** The object consuming memory is rarely the object holding it.

**They check listener and node counts first.** These are cheaper to read than a heap snapshot and identify the category immediately.

**They profile in an incognito window with extensions disabled.** Extensions inject scripts and listeners that pollute snapshots badly.

**They do not chase small deltas.** A few hundred KB of growth over a session is normal. Look for growth proportional to user actions.

## Common pitfalls

- Comparing two snapshots without forcing GC first, and chasing garbage that would have been collected.
- Profiling in development mode, where React retains extra debugging structures and hot reloading leaks by design.
- Concluding "leak" from a single growth measurement rather than a repeated pattern.
- Ignoring the DOM node count because the JS heap looks stable — detached DOM is largely outside the JS heap.
- Profiling with extensions enabled.

## Interview angle

"How would you debug a memory leak" is a common senior question, and the expected answer is a process rather than a fact: confirm with the Performance panel that memory survives GC, use the three-snapshot comparison to find what accumulates, read the retainer chain to find what holds it, and check the usual suspects — timers, listeners, detached nodes, unbounded caches. Mentioning the `Detached` filter specifically signals you have actually done this.
