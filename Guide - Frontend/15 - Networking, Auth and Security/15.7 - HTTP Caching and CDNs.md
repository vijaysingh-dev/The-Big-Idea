# HTTP Caching and CDNs

The fastest request is the one that never leaves the browser. HTTP caching is the layer that makes that happen, and it is controlled almost entirely by response headers you may need to ask your backend team for.

## Cache-Control

```
Cache-Control: public, max-age=31536000, immutable
Cache-Control: private, max-age=0, must-revalidate
Cache-Control: no-store
```

The directives that matter:

- **`max-age=N`** — fresh for N seconds. Served from cache with no network request at all.
- **`s-maxage=N`** — overrides `max-age` for shared caches (CDNs) only. Lets you cache aggressively at the edge while keeping browsers conservative.
- **`public`** — any cache may store it, including CDNs.
- **`private`** — only the browser may store it. Required for anything user-specific.
- **`no-cache`** — store it, but revalidate before every use. Confusingly named; it does *not* mean "do not cache".
- **`no-store`** — never write it to disk or memory. The correct directive for sensitive data.
- **`immutable`** — the content will never change at this URL, so do not revalidate even on reload.
- **`stale-while-revalidate=N`** — serve stale content immediately while refreshing in the background.

`no-cache` versus `no-store` is a standard interview question and a standard production mistake: using `no-cache` for a page containing personal data still writes it to disk.

## Validation

When content is stale, the browser revalidates rather than re-downloading:

```
Response:  ETag: "abc123"
Request:   If-None-Match: "abc123"
Response:  304 Not Modified    (no body)
```

```
Response:  Last-Modified: Wed, 05 Aug 2026 10:00:00 GMT
Request:   If-Modified-Since: Wed, 05 Aug 2026 10:00:00 GMT
```

`ETag` is preferred — it is content-based and has second-level precision, while `Last-Modified` cannot distinguish changes within the same second. A 304 still costs a round trip, so it is much better than a full download but much worse than a cache hit with no request at all.

## The two-tier strategy

This is the standard pattern for any modern frontend build, and it is worth internalizing because it is what bundler hashing exists to enable.

**Hashed assets — cache forever:**

```
/assets/main.a3f9c2.js
Cache-Control: public, max-age=31536000, immutable
```

The filename changes when the content changes, so there is no invalidation problem. A returning user downloads nothing.

**HTML — never cache, or revalidate always:**

```
/index.html
Cache-Control: no-cache
```

The HTML references the hashed filenames, so it must always be fresh. One revalidation request gets the user the current asset manifest, and everything else comes from cache.

This is why deploying a build with unhashed filenames is a mistake: you must then choose between stale assets and no caching at all.

A related failure mode: after a deploy, a user with an open tab holds HTML referencing chunks that no longer exist, and a lazy import 404s. Handle it with a reload-on-chunk-error strategy ([[08.2 - Dynamic Imports]]), and keep old asset versions on the CDN for a grace period.

## Caching API responses

```
Cache-Control: private, max-age=0, must-revalidate
ETag: "user-42-v7"
```

For data that changes, `max-age=0` with an `ETag` gives you cheap 304s. For data that tolerates brief staleness:

```
Cache-Control: public, max-age=60, stale-while-revalidate=600
```

Fresh for a minute, then served stale instantly while the background refresh happens. This maps closely onto how TanStack Query's `staleTime` behaves in the client cache ([[24.7 - Caching Stale Time and Invalidation]]) — the difference being one is enforced by the browser and the other by your data library.

Note the browser HTTP cache and your client-side query cache are separate layers. A `fetch` that hits the HTTP cache still runs your query function; it just returns faster.

## Vary

```
Vary: Accept-Encoding, Accept-Language
```

Tells caches which request headers change the response, so a cached English response is not served to a Hindi request. Getting this wrong causes cross-user content bleed at the CDN — one of the more serious caching bugs possible.

Avoid `Vary: User-Agent`, which fragments the cache almost per-device and destroys hit rates.

## Cookies and caching

Any response with `Set-Cookie` should be `private` at minimum. A shared cache storing a response containing another user's session cookie is a critical vulnerability, and CDN misconfiguration here has caused real incidents at large companies.

## CDNs

A CDN caches responses at edge locations near users. For an Indian audience, an origin in Mumbai versus an edge in Delhi is roughly 30 ms versus 5 ms — and much more if the origin is in the US.

Concepts worth knowing:

- **Origin shield** — an intermediate cache layer so many edges do not all hit the origin on a miss.
- **Cache key** — what the CDN uses to identify a response, typically URL plus `Vary` headers. Configuring it to ignore irrelevant query parameters (like `utm_source`) dramatically improves hit rates.
- **Purge / invalidation** — explicitly evicting content. Fine for HTML, unnecessary for hashed assets.
- **Tiered TTLs** — `s-maxage` high at the edge, `max-age` low in the browser, so you can purge centrally without waiting for browser caches to expire.

Edge compute (Cloudflare Workers, Vercel Edge) lets you run logic at the edge — auth checks, A/B assignment, personalization headers — while still caching the expensive parts.

## Service Worker cache

A separate, script-controlled layer that sits in front of the network ([[14.4 - Cache API and Service Workers]]). It is the only cache you can program:

```js
// Cache-first for static assets, network-first for API calls
```

Because it is programmable, it can serve content offline, which no HTTP cache directive can achieve. It is also the layer most capable of breaking your site permanently if the caching logic is wrong, since a bad service worker can serve stale HTML indefinitely.

## Debugging

In DevTools' Network panel, the Size column tells you the layer:

- **`(memory cache)`** — in-process, no disk read, cleared on tab close
- **`(disk cache)`** — HTTP cache hit
- **`(ServiceWorker)`** — served by the service worker
- **`304`** — revalidated, body not re-sent
- **a byte count** — full download

Add the "Cache-Control" column to the Network panel to see the directive on each response without opening headers individually.

Note that a hard reload bypasses the cache entirely, so testing cache behavior requires normal navigation.

## How senior engineers actually use this

**They hash asset filenames and cache them immutably.** This one decision removes almost all cache-invalidation complexity.

**They keep HTML uncached.** It is small, and it is the pointer to everything else.

**They set `Vary` deliberately** and audit CDN cache keys, because a wrong cache key is either a performance problem or a security incident.

**They use `stale-while-revalidate` for data** that tolerates brief staleness, which gives instant responses without serving indefinitely old content.

**They treat the service worker cache as high-risk** and always ship a kill switch — a way to unregister and clear caches remotely.

## Common pitfalls

- `no-cache` used where `no-store` was meant, storing sensitive data on disk.
- Unhashed asset filenames with long `max-age`, so users get stale JavaScript.
- Cached HTML pointing at deleted chunk files after a deploy.
- Missing `private` on responses containing user data, allowing CDN storage.
- `Vary: User-Agent` destroying cache hit rates.
- Query parameters in the cache key that do not affect the response.
- A service worker caching HTML aggressively and pinning users to an old build.

## Interview angle

"Explain HTTP caching" wants `Cache-Control` directives, the difference between `no-cache` and `no-store`, and validation with `ETag` producing 304s. The strong follow-up is the two-tier strategy — immutable hashed assets plus uncached HTML — because it shows you understand why bundlers hash filenames at all. Mentioning `stale-while-revalidate` and CDN cache keys extends it into system design territory.
