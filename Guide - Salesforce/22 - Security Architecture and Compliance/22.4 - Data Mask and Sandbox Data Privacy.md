# Data Mask and Sandbox Data Privacy

## The exposure

A Full sandbox is a complete copy of production, including every customer's name, email, phone number, address, and claim history.

**It has weaker controls than production.** More developers have administrator access. Login IP restrictions are frequently relaxed. Sandboxes are refreshed and forgotten. Contractors and offshore teams get access to them precisely because they are "not production".

**A sandbox with real customer data is production data with weaker access controls**, and that is the whole problem.

The regulatory position is unambiguous: personal data in a non-production environment is still personal data, subject to the same obligations.

## Data Mask

Salesforce's product for this, and it is **free** — a managed package installed in the production org and configured per sandbox.

```
AppExchange → Salesforce Data Mask → install in production
Setup → Data Mask → configure per sandbox
```

Four masking types:

```
Anonymization      random values, no format preservation
Pseudonymization   realistic fake values, format preserved
Deletion           the field is emptied
Pattern-based      a defined pattern, format preserved
```

**Pseudonymization is usually right.** A phone number that still looks like a phone number keeps validation rules, formatting, and integrations working. Anonymized garbage breaks all three.

## Configuring it

```
Configuration: Northwind Sandbox Mask

Object: Contact
    FirstName        Pseudonymization — first names
    LastName         Pseudonymization — last names
    Email            Pseudonymization — email format
    Phone            Pattern-based — +91 90000 #####
    MailingStreet    Pseudonymization — street addresses
    Birthdate        Deletion

Object: Account
    Name             Pseudonymization — company names
    BillingStreet    Pseudonymization

Object: Warranty_Claim__c
    Fault_Description__c   Deletion — free text may contain anything
```

**Free text fields deserve deletion rather than masking.** A description field can contain a customer's name, a phone number, or a complaint about a named individual — and no pattern catches that.

**Serial numbers, external IDs, and matching keys are usually left alone**, since masking them breaks the integration testing the sandbox exists for. That is a judgement: the key identifies a customer indirectly, and preserving it is a deliberate acceptance.

## Running it automatically

Masking that depends on someone remembering is masking that does not happen.

```java
global with sharing class SandboxPostRefresh implements SandboxPostCopy {

    global void runApexClass(SandboxContext context) {
        // masking first, before anyone can log in and query
        maskSensitiveData();
        deactivateIntegrationUsers();
        repointEndpoints();
        createCustomSettings();
        scheduleJobs();
    }
}
```

Selected when creating or refreshing the sandbox, and it runs automatically.

**Data Mask itself can be scheduled** to run after a refresh, which is the cleaner path — the `SandboxPostCopy` then handles everything else.

**The window between refresh completion and masking completion is an exposure**, and on a large org masking takes hours. Restricting sandbox login until masking completes is the conservative approach, and few organizations do it.

## Masking without Data Mask

For orgs not using it, a batch job.

```java
public with sharing class ContactMaskBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, FirstName, LastName, Email, Phone, MailingStreet FROM Contact
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Contact> scope) {
        for (Contact contact : scope) {
            String suffix = String.valueOf(contact.Id).right(6);

            // deterministic from the Id, so re-running produces the same values
            contact.FirstName = 'Test';
            contact.LastName = 'Contact' + suffix;
            contact.Email = 'masked.' + suffix + '@example.invalid';
            contact.Phone = '+91 90000 ' + suffix.right(5);
            contact.MailingStreet = suffix + ' Test Street';
        }

        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) {
        Database.executeBatch(new AccountMaskBatch(), 200);
    }
}
```

**Deterministic masking from the record Id** means re-running produces the same values, which keeps test scripts stable across refreshes.

**Chaining from `finish`** processes objects in sequence rather than firing five batch jobs that queue behind the five-concurrent limit. See [[12.4 - Batch Apex]].

**Bypass the automation during masking**, or every trigger fires on every record:

```java
public void execute(Database.BatchableContext ctx, List<Contact> scope) {
    AutomationBypass.bypass('Contact');
    // ... masking
    Database.update(scope, false);
}
```

Without that, masking a million contacts runs a million trigger executions and takes days rather than hours.

## The other sandbox exposures

Masking data is necessary and not sufficient.

**Integration users still point at production endpoints.**

```java
private void repointEndpoints() {
    // without this, a refreshed sandbox writes test data into the live ERP
    for (User integrationUser : [
        SELECT Id FROM User WHERE Profile.Name = 'Integration User' AND IsActive = true
    ]) {
        integrationUser.IsActive = false;
    }
    update integrationUsers;
}
```

**This is the exposure that causes actual incidents.** A refreshed sandbox whose integration user still holds production credentials will call the live ERP with test data — and it will succeed, because the credentials are valid.

**Named Credential secrets do not survive a refresh**, which mitigates it partially. Connected app configurations in the external system frequently do.

**Email addresses are appended with `.invalid`** by the platform, and deliverability resets to "System email only" — both deliberate safeguards. Reversing them for the team to test email means being careful not to reverse them for the customer records. See [[21.11 - Sandbox Strategy and Data Seeding]].

**Scheduled jobs are not copied**, which means a scheduled integration will not run — helpful here, and it must be remembered when the sandbox is used for testing.

**Attachments and files are copied**, and a PDF invoice contains everything a masked field would have hidden. Data Mask can delete file content; a custom approach usually cannot.

## Partial Copy templates

An alternative to masking: **do not copy the sensitive data in the first place.**

```
Setup → Sandbox Templates → New

Objects: Account, Contact, Asset, Warranty_Claim__c
Records: up to 10,000 per object
```

**A template selects objects, not filters.** You cannot exclude a field or select "customers in India" — you get a sample of whole records.

**The sample creates orphans.** A claim whose asset was not sampled has a broken lookup, which makes some testing unrealistic.

**Combining approaches** is what most organizations settle on: Partial Copy to reduce volume, plus masking on what does come across.

## Synthetic data as the alternative

For a developer sandbox, generated data avoids the problem entirely.

```java
// scripts/apex/seed-sandbox.apex
List<Account> accounts = new List<Account>();
for (Integer i = 0; i < 50; i++) {
    accounts.add(new Account(
        Name = 'Northwind Customer ' + i,
        BillingCountry = 'India',
        Industry = 'Manufacturing'
    ));
}
insert accounts;

List<Asset> assets = new List<Asset>();
for (Account account : accounts) {
    for (Integer i = 0; i < 10; i++) {
        assets.add(new Asset(
            AccountId = account.Id,
            Name = 'Press P400',
            SerialNumber = 'SN-' + account.Id + '-' + i,
            Status = 'Installed'
        ));
    }
}
insert assets;
```

**No personal data exists**, so there is nothing to mask and nothing to leak.

**Where it does not serve:** performance testing, migration rehearsal, and UAT with realistic scenarios. Those need production-shaped data, which is why Full sandboxes and masking remain necessary. See [[21.4 - Dev Hub and Scratch Orgs]].

**The practical division:**

```
Scratch orgs, Developer sandboxes   synthetic data — no masking needed
Partial Copy                        sampled and masked
Full sandbox                        complete and masked
```

## Access control in sandboxes

The control that matters as much as masking, and gets less attention.

**Restrict who has a sandbox.** A Full sandbox with unmasked data accessible to twenty contractors is a larger exposure than an unencrypted field.

**Apply login IP restrictions**, which are frequently relaxed in sandboxes for convenience.

**Deactivate users who do not need access**, particularly in a Full sandbox where every production user is copied.

**Audit sandbox logins**:

```sql
SELECT UserId, LoginTime, SourceIp, CountryIso, Status
FROM LoginHistory
WHERE LoginTime = LAST_N_DAYS:30
ORDER BY LoginTime DESC
```

**A sandbox is in scope for a security audit**, and organizations are frequently surprised by that.

## Deciding what to mask

The analysis, per field.

```
[ ] Does this identify a person, directly or with other fields?
[ ] Is it special category data — health, financial, biometric?
[ ] Would a breach of the sandbox be reportable?
[ ] Is it needed unmasked for the sandbox's purpose?
```

**Direct identifiers always:** name, email, phone, address, national identifiers, payment details.

**Indirect identifiers usually:** a serial number tied to one customer, an account name, a case description.

**Free text always**, by deletion — no pattern catches what a person typed.

**What is genuinely needed unmasked:** external IDs for integration testing, record structure and relationships, and volume. Those can be preserved while masking everything that identifies a person.

## A sandbox privacy checklist

```
Before a refresh
  [ ] SandboxPostCopy class selected
  [ ] Masking configuration current for any new sensitive fields

After a refresh
  [ ] Masking completed — verify, do not assume
  [ ] Integration users deactivated or repointed
  [ ] Named Credential secrets not populated with production values
  [ ] Deliverability set appropriately
  [ ] Login IP restrictions applied
  [ ] Users who do not need access deactivated
  [ ] Files and attachments handled
  [ ] Access list reviewed

Ongoing
  [ ] New sensitive fields added to the masking configuration
  [ ] Sandbox logins audited
  [ ] Sandboxes nobody uses deleted
```

**"Verify, do not assume"** on masking completion is the line that matters. Masking a large org takes hours, and a job that failed partway leaves real data in place with everyone believing it is masked.

## Practical guidance

**Use Data Mask** — it is free and it is better than a custom script.

**Run it from `SandboxPostCopy`**, so it happens without anyone remembering.

**Prefer pseudonymization** to anonymization; format preservation keeps things working.

**Delete free text fields** rather than masking them.

**Deactivate integration users** — a sandbox calling the production ERP is a real incident.

**Bypass automation during masking**, or it takes days.

**Use synthetic data** for developer environments, so there is nothing to mask.

**Restrict sandbox access**, and audit logins.

**Verify masking completed** rather than assuming it did.
