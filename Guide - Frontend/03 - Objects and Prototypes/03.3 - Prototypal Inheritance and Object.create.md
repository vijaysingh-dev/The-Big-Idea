# Prototypal Inheritance and Object.create

Classical inheritance (Java, C++) *copies* structure from a class into an instance. Prototypal inheritance **delegates** — the object holds no copy, it holds a link, and lookups that miss are forwarded up the chain ([[03.2 - The Prototype Chain]]).

The practical difference: changing a prototype affects every existing object linked to it, immediately. There is no compile step and no snapshot.

## Object.create

```js
const animal = {
  init(name) {
    this.name = name;
    return this;
  },
  speak() {
    return `${this.name} makes a sound`;
  },
};

const dog = Object.create(animal);
dog.speak = function () {
  return `${this.name} barks`;
};

const rex = Object.create(dog).init("Rex");
rex.speak(); // "Rex barks"
```

No constructors, no `new`, no `class`. Just objects linked to objects — what Douglas Crockford called **OLOO** (Objects Linked to Other Objects). The chain here is `rex -> dog -> animal -> Object.prototype -> null`.

`Object.create` takes an optional second argument of property descriptors ([[03.1 - Objects and Property Descriptors]]):

```js
const obj = Object.create(animal, {
  id: { value: 1, enumerable: true },
});
```

## The constructor-function pattern

The pre-ES2015 idiom, still everywhere in older code and transpiler output:

```js
function Animal(name) {
  this.name = name;
}
Animal.prototype.speak = function () {
  return `${this.name} makes a sound`;
};

function Dog(name, breed) {
  Animal.call(this, name);       // borrow the parent constructor
  this.breed = breed;
}

Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;

Dog.prototype.speak = function () {
  return `${Animal.prototype.speak.call(this)} — specifically, barks`;
};
```

Three details that are always the interview follow-ups:

1. `Animal.call(this, name)` runs the parent's initialization against the child instance. Without it, `name` is never set.
2. `Object.create(Animal.prototype)` — **not** `new Animal()` and **not** `Animal.prototype`. Using `new Animal()` runs the parent constructor prematurely; assigning the prototype directly makes child and parent share one object, so adding a method to `Dog.prototype` adds it to `Animal.prototype` too.
3. Reassigning `Dog.prototype` wipes the default `constructor` property, so it must be restored — otherwise `rex.constructor` reports `Animal`.

Every one of these is handled automatically by `class ... extends`, which is the argument for using it.

## Delegation over copying

The distinctive capability of prototypes is that behavior can be shared and changed after the fact:

```js
const base = { greet() { return "hi"; } };
const obj = Object.create(base);

obj.greet();               // "hi"
base.greet = () => "hello";
obj.greet();               // "hello" — obj sees the change immediately
```

Useful for plugin systems and polyfills; dangerous as a general technique, because any object anywhere on that chain can change behavior for everything below it.

## Mixins

Prototypes give single inheritance only. When you need behavior from several sources, copy properties instead of linking:

```js
const serializable = {
  toJSON() { return JSON.stringify(this); },
};

const comparable = {
  equals(other) { return this.id === other.id; },
};

Object.assign(Dog.prototype, serializable, comparable);
```

`Object.assign` copies own enumerable properties, so getters are *invoked* and their return value copied, not the accessor itself. To preserve accessors:

```js
Object.defineProperties(
  Dog.prototype,
  Object.getOwnPropertyDescriptors(mixin)
);
```

The class-based equivalent is a mixin factory — a function taking a base class and returning a subclass — which is how TypeScript and libraries like Lit express the same idea.

## Composition, which is usually the right answer

```js
function createDog(name) {
  const state = { name };
  return {
    ...canSpeak(state),
    ...canFetch(state),
  };
}

const canSpeak = state => ({ speak: () => `${state.name} barks` });
const canFetch = state => ({ fetch: () => `${state.name} fetches` });
```

No inheritance, no `this`, no chain to reason about. Capabilities are explicit and independently testable. This is the closure-factory pattern from [[02.4 - Closure Patterns in Production]], and it is what most modern JavaScript codebases actually use.

The tradeoff is memory: every instance gets its own copy of each method, where prototypes share one. That matters at thousands of instances and not otherwise.

## How senior engineers actually use this

**They use `class` for anything hierarchical and factories for everything else.** Writing the manual constructor-function pattern by hand in new code is not defensible — `class` does it correctly and communicates intent.

**They prefer composition to deep hierarchies.** Inheritance chains past two levels become hard to change, because a modification in the base ripples everywhere. "Favor composition over inheritance" is not dogma here; it is a response to the fact that JavaScript's dynamic dispatch makes deep chains genuinely hard to trace.

**They use `Object.create(proto)` deliberately for two things:** null-prototype dictionaries, and setting up prototype relationships in library code where `class` is unavailable or too heavy.

**They read `Object.create` in transpiled output constantly.** Babel's ES5 class output is exactly the constructor-function pattern above, so recognizing it makes debugging compiled bundles far easier ([[27.5 - Babel and Transpilation]]).

## Common pitfalls

- Setting `Child.prototype = Parent.prototype`, linking them to the same object.
- Setting `Child.prototype = new Parent()`, which runs the parent constructor at definition time with no arguments.
- Forgetting to restore `constructor` after reassigning a prototype.
- Forgetting `Parent.call(this, ...)`, so parent instance fields are never initialized.
- Using `Object.assign` to mix in an object containing getters and silently freezing their current values.
- Building three- or four-level hierarchies where composition would do.

## Interview angle

Expect "how do you implement inheritance without `class`" and "difference between classical and prototypal inheritance". Frame it as delegation versus copying, then write the constructor-function pattern and explain each of the three fix-up lines. Mentioning that `class` compiles to roughly this shape, and that composition is usually preferable in application code, shows you understand the tradeoff rather than just the mechanics.
