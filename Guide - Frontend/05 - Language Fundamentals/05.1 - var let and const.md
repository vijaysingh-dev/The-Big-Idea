# var, let and const

Three ways to declare a binding, differing along four axes: scope, hoisting behavior, redeclaration and reassignment.

| | `var` | `let` | `const` |
| --- | --- | --- | --- |
| Scope | function | block | block |
| Initialized on hoist | `undefined` | TDZ | TDZ |
| Redeclarable | yes | no | no |
| Reassignable | yes | yes | no |
| Creates a global object property | yes | no | no |

## Scope

```js
function f() {
  if (true) {
    var a = 1;
    let b = 2;
    const c = 3;
  }
  console.log(a); // 1
  console.log(b); // ReferenceError
}
```

`var` ignores blocks entirely — only functions contain it. `let` and `const` respect every `{ }`, including `if`, `for`, `while`, bare blocks and `catch` ([[02.2 - Lexical Scope]]).

## The global object

At top level in a classic script:

```js
var x = 1;
let y = 2;

window.x; // 1
window.y; // undefined
```

`var` at top level creates a property on the global object; `let` and `const` create bindings in a separate global lexical environment. This is why `var` declarations across separate `<script>` tags collide and `let` declarations throw a redeclaration error instead — arguably a better failure mode.

In ES modules none of this applies: nothing at module top level touches the global object ([[08.1 - ES Modules vs CommonJS]]).

## Redeclaration

```js
var a = 1;
var a = 2;      // fine

let b = 1;
let b = 2;      // SyntaxError

function f(x) {
  let x = 1;    // SyntaxError — collides with the parameter
}
```

Silent `var` redeclaration is how a variable gets accidentally clobbered halfway down a 400-line function. The `let` error is a parse-time error, caught before anything runs.

## const does not mean immutable

```js
const arr = [1, 2];
arr.push(3);         // fine — the binding is unchanged
arr = [];            // TypeError — reassignment

const obj = { a: 1 };
obj.a = 2;           // fine
```

`const` freezes the *binding*, not the value. For value immutability use `Object.freeze` ([[03.1 - Objects and Property Descriptors]]), and remember it is shallow.

`const` also requires an initializer — `const x;` is a `SyntaxError`.

## The loop binding

The most-cited practical difference:

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2
```

With `var` there is one function-scoped binding shared by all three closures. With `let`, the spec creates a **fresh binding per iteration** and copies the current value into it before running the body — so each closure captures its own ([[02.3 - Closures]]).

`const` works in `for...of` and `for...in` but not in a C-style `for`, because the increment reassigns:

```js
for (const item of items) {}     // fine — new binding each iteration
for (const i = 0; i < 3; i++) {} // TypeError on i++
```

## var and function-scope surprises

```js
function f() {
  console.log(x); // undefined, not ReferenceError
  if (false) {
    var x = 1;    // still hoisted, even though unreachable
  }
}
```

The declaration is registered during the creation phase regardless of whether the code path executes ([[01.2 - Execution Context and Scope Chain]]). This is one of the clearer arguments against `var`.

## How senior engineers actually use this

**They use `const` by default and `let` only when reassignment is genuinely needed.** Not for immutability guarantees — for signalling intent. A reader seeing `let` knows to look for where the value changes; seeing `const` means they can stop tracking it.

**They treat `var` as a code smell in new code.** It survives only in transpiler output and legacy files. ESLint's `no-var` and `prefer-const` are near-universal in modern configs.

**They use `let` for accumulators and conditional assignment**, and prefer restructuring where it is easy:

```js
// Common
let label;
if (status === "active") label = "Active";
else label = "Inactive";

// Often better
const label = status === "active" ? "Active" : "Inactive";
```

**They know `const` is not a performance feature.** Engines infer immutability regardless; the benefit is readability and error prevention.

## Common pitfalls

- Assuming `const` makes objects immutable.
- `var` in loops with async callbacks.
- Redeclaring a `var` far from its first declaration and silently overwriting it.
- Relying on `var` hoisting to use a variable before its declaration line.
- Expecting `let` at top level to appear on `window`.

## Interview angle

"Difference between `var`, `let` and `const`" is close to guaranteed, usually followed by the loop-and-`setTimeout` snippet. Cover all four axes — scope, hoisting/TDZ, redeclaration, reassignment — then explain the per-iteration binding for `let` precisely, since "because `let` is block scoped" is an incomplete answer; the spec explicitly copies the value into a new binding each iteration. Add that `const` freezes the binding, not the value.
