# Sockets From First Principles

#backend #networking #sockets

> **In one line:** A socket is a file descriptor you can read and write, TCP gives you a stream of bytes with no message boundaries, and every protocol you have ever used exists to put those boundaries back.

---

## The Idea

A **socket** is the operating system's handle for one end of a network connection. You get an integer — a file descriptor — and you read and write it like a file.

That is genuinely the whole abstraction. Six system calls cover almost everything:

| Call | Who | Does |
|---|---|---|
| `socket()` | Both | Create the file descriptor |
| `bind()` | Server | Claim an address and port |
| `listen()` | Server | Start accepting connections |
| `accept()` | Server | Take one connection off the queue |
| `connect()` | Client | Open a connection |
| `send()` / `recv()` | Both | Move bytes |
| `close()` | Both | Done |

Every web server, database driver and message broker you have used is built on these.

## The Smallest Server and Client

### Server

```python
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("0.0.0.0", 8080))
server.listen(128)

while True:
    conn, addr = server.accept()
    data = conn.recv(4096)
    conn.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nhi")
    conn.close()
```

`AF_INET` is IPv4, `SOCK_STREAM` is TCP. (`AF_INET6` for IPv6, `SOCK_DGRAM` for UDP.)

### Client

```python
client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(("localhost", 8080))
client.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\n\r\n")
print(client.recv(4096))
client.close()
```

That is a working HTTP client and server. Everything else — routing, headers, keep-alive, TLS — is layered on top of these ten lines.

## The Four Things That Trip Everyone Up

### 1. TCP is a byte stream, not messages

This is the single most important fact in this note.

```python
# Sender
sock.sendall(b"HELLO")
sock.sendall(b"WORLD")

# Receiver — any of these can happen
recv(1024) → b"HELLOWORLD"      # merged
recv(1024) → b"HELLO"           # separate
recv(1024) → b"HEL"             # split mid-message
```

TCP guarantees the **bytes** arrive in order. It guarantees nothing about how they are grouped. Your two `sendall` calls are not two messages — they are ten bytes.

⚠️ **This is why every protocol needs framing.** Three standard approaches:

```python
# 1. Length prefix — most common, used by gRPC, Postgres, Redis (partly)
sock.sendall(len(payload).to_bytes(4, "big") + payload)

# 2. Delimiter — used by HTTP headers (\r\n\r\n) and Redis (\r\n)
sock.sendall(payload + b"\n")

# 3. Fixed size — used by some binary protocols
sock.sendall(payload.ljust(256, b"\x00"))
```

Length prefix is almost always the right choice: no escaping needed, you know how much to buffer, and you can reject oversized messages before reading them.

Reading a length-prefixed message correctly:

```python
def recv_exactly(sock, n: int) -> bytes:
    buf = bytearray()
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            raise ConnectionError("peer closed mid-message")
        buf.extend(chunk)
    return bytes(buf)

def recv_message(sock) -> bytes:
    length = int.from_bytes(recv_exactly(sock, 4), "big")
    if length > MAX_MESSAGE:
        raise ValueError("message too large")
    return recv_exactly(sock, length)
```

That `MAX_MESSAGE` check is not optional. Without it, a hostile client sends a length of 4 billion and you try to allocate 4GB.

### 2. `recv()` returning empty means the peer closed

```python
data = sock.recv(4096)
if not data:
    # clean close from the other side. Not an error
    ...
```

An empty result is **end of stream**, not "no data right now". On a blocking socket, "no data right now" means `recv` waits. On a non-blocking socket it raises `BlockingIOError`.

Getting these confused produces a busy loop that pegs a CPU core.

### 3. `send()` may not send everything

```python
sent = sock.send(b"x" * 1_000_000)      # might return 65536
```

`send` returns how many bytes it accepted into the kernel buffer. If the buffer is full — because the receiver is slow — it takes what fits.

```python
# Python handles the loop for you
sock.sendall(data)          # blocks until all of it is accepted

# What sendall does underneath
total = 0
while total < len(data):
    total += sock.send(data[total:])
```

⚠️ **On a non-blocking socket, `sendall` does not work.** You must track the offset yourself and wait for the socket to become writable. This is exactly what the write buffer and `drain()` in [[01.11 - Backpressure Inside One Process]] are doing.

### 4. Blocking vs non-blocking

```python
sock.setblocking(False)

try:
    data = sock.recv(4096)
except BlockingIOError:
    pass          # nothing available yet. Come back when the selector says so
```

Non-blocking sockets are what make event loops possible. A blocking `recv` stops your entire thread; a non-blocking one returns immediately and you ask the selector to tell you when to retry. See [[01.4 - Building an Event Loop From Scratch]].

## Socket Options You Will Actually Use

### SO_REUSEADDR — always set it on servers

```python
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
```

Without it, restarting your server gives `Address already in use` for 60 seconds, because old connections sit in `TIME_WAIT` holding the port. See [[02.3 - TCP Connection Lifecycle]].

### SO_REUSEPORT — multiple processes on one port

```python
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
```

Lets several processes each bind the same port, with the kernel distributing incoming connections between them. This is how some multi-process servers avoid a shared accept queue.

⚠️ Kernel distribution is by a hash of the connection tuple, not by which worker is least busy. One worker can get a run of slow connections while another idles. This is a real source of uneven load in `SO_REUSEPORT` deployments.

### TCP_NODELAY — disable Nagle's algorithm

```python
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

Nagle's algorithm buffers small writes to avoid sending tiny packets. Good for bulk transfer, bad for anything interactive — combined with delayed ACKs it can add 40ms to a small request/response.

💡 **Set `TCP_NODELAY` for any request/response protocol.** Redis, gRPC and most HTTP servers do it by default. If you write your own protocol and see mysterious 40ms delays on small messages, this is why.

### SO_KEEPALIVE — detect dead peers

```python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 60)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)
```

Without keepalive, a connection whose peer vanished (power loss, network partition, a NAT device forgetting the mapping) stays `ESTABLISHED` on your side **forever**. You are holding a file descriptor, a pool slot and possibly a database transaction for a peer that no longer exists.

⚠️ **The OS default for `TCP_KEEPIDLE` is 2 hours.** That is useless for a service. Set it to 60 seconds. This is a common cause of "leaked" connections that nobody can explain.

### The backlog

```python
server.listen(128)
```

Two queues actually exist in the kernel:

```
SYN arrives ──► [SYN queue: half-open]
handshake completes ──► [accept queue: ready] ──► your accept() call
```

`listen(backlog)` sizes the accept queue. If your app is slow to `accept()`, this queue fills, and new connections are refused or dropped.

```bash
ss -tln                          # Recv-Q on a listening socket = current accept queue
                                 # Send-Q = the backlog limit
cat /proc/sys/net/core/somaxconn # kernel cap — your listen() is clamped to this
```

⚠️ **The kernel silently caps your backlog at `somaxconn`.** Asking for 4096 when `somaxconn` is 128 gives you 128 with no warning. Under a connection surge, the excess is dropped and clients see timeouts rather than refusals — which looks like a network problem and is not.

## In Production

### Diagnosing with `ss`

```bash
ss -tan                          # all TCP sockets and states
ss -tan state established        # just established
ss -tan state time-wait | wc -l  # TIME_WAIT count
ss -tlnp                         # what is listening, and which process
ss -ti                           # detailed: rtt, cwnd, retransmits
ss -tm                           # memory used per socket
```

`ss -ti` output includes `rtt`, `cwnd` and `retrans`. High retransmits means packet loss. Small `cwnd` with high `rtt` means congestion control has throttled you. This is how you tell "the network is bad" from "the server is slow" — see [[02.4 - Flow Control and Congestion Control]].

### File descriptor limits

Every socket is a file descriptor.

```bash
ulimit -n                        # your soft limit
cat /proc/<pid>/limits           # what the process actually got
ls /proc/<pid>/fd | wc -l        # current usage
```

⚠️ **Running out produces incoherent errors.** `Too many open files` from an unrelated code path, a log file failing to open, or an accept loop that silently stops accepting new connections while existing ones work fine. If a service stops accepting connections but keeps serving old ones, check fd count first.

Set the limit high (65536+) in your container spec and export fd usage as a metric.

### Ephemeral port exhaustion

An outbound connection needs a source port from the ephemeral range (typically 32768–60999, about 28,000 ports).

```
Each connection is identified by: (src IP, src port, dst IP, dst port)
```

If your service opens many short-lived connections to **one** destination, you can exhaust the range. Worse, each closed connection sits in `TIME_WAIT` for 60 seconds still holding its port.

```bash
ss -tan state time-wait | wc -l          # if this approaches 28,000, you have a problem
sysctl net.ipv4.ip_local_port_range
```

The fix is almost never kernel tuning. **It is connection reuse.** One `httpx.AsyncClient` for the app lifetime instead of one per request eliminates the problem entirely — see [[01.10 - Connection Pools and Limits]].

💡 A service that opens a new connection per request will hit this wall at a few hundred requests per second to a single destination. It looks like the destination is refusing you, and it is actually your own kernel running out of source ports.

## Codebase

**Repo:** `redis/redis`

**Why this one:** The most readable production socket code in existence. Its networking layer is a few thousand lines of C written to be read.

**Question to answer:** Trace `GET key` from the moment the socket becomes readable to the bytes going back out. Specifically: where is the read buffer, how does Redis know it has a complete command, and what happens if a client stops reading while Redis keeps producing output?

**Read, in order:**

1. `src/anet.c` — the socket setup helpers. `anetTcpServer`, `anetNonBlock`, `anetEnableTcpNoDelay`, `anetKeepAlive`. Every option in this note appears here, in production use
2. `src/ae.c` — the event loop. Under 500 lines and it is complete
3. `src/networking.c` — `createClient`, `readQueryFromClient`, `processInputBuffer`, `addReply`, `writeToClient`
4. In the same file, find `closeClientOnOutputBufferLimitReached` — this is Redis's slow-client policy, and it is the answer to the third part of the question

**The third part is the important one.** Redis's answer to a slow client is to kill it above a configured buffer limit. That is a deliberate design decision with a real tradeoff, and it is exactly the decision you will make in Conduit phase 3 and in [[04.7 - Presence Fanout and Backpressure]].

**Also read:** `redis.conf` around `client-output-buffer-limit`. Three different limits for three client classes — normal, replica, pubsub. Think about why they differ.

**Size:** 2 sessions. This is one of the highest-value reading sessions in the whole vault.


**Part 1 — A real protocol.** Design a small length-prefixed request/response protocol and write it down in `SPEC.md`: message format, max size, error responses, how a connection closes.

Then write encode/decode with tests for: a message split across three `recv` calls, two messages merged into one, a partial message followed by a close, a declared length larger than your maximum, and a declared length of zero.

**These tests are the point of the drill.** Every one of them is a real bug in real network code.

**Part 2 — Three servers.** Same protocol, three concurrency models. Then benchmark with 10, 100, 1000, 5000 concurrent connections. Measure throughput, memory and p99.

Build the table. You now have your own numbers for the C10k problem instead of somebody's blog post.

**Part 3 — Measure the options.**

- `nodelay.py` — request/response with and without `TCP_NODELAY`. Find the 40ms delay. **You must see this yourself to believe it**
- `keepalive.py` — establish a connection, drop the peer's network with a firewall rule, and measure how long the connection stays `ESTABLISHED` with default settings versus tuned ones
- `backlog.py` — `listen(5)`, then connect 100 clients at once without accepting. Watch `ss -tln` Recv-Q fill, then watch connections get dropped

**Part 4 — Pathology.** For each: reproduce, observe with `ss` and `tcpdump`, then implement the mitigation.

- Slow reader: watch your send buffer fill via `ss -tm`. Implement an output buffer limit like Redis does
- Half-open: kill a client's network without closing. Watch the server hold the connection. Fix with keepalive
- FD exhaustion: `ulimit -n 64`, then open 100 connections. Observe what breaks and how confusing the error is

**Part 5 — Ephemeral ports.** Write a client that opens a new connection per request to one destination, at 500 requests/sec. Watch `ss -tan state time-wait | wc -l` climb. Find the point of failure. Then switch to connection reuse and show the problem disappearing.

**Done when:**
- All framing tests pass, including the hostile ones
- Your three-server benchmark table covers all four concurrency levels
- You have personally seen the 40ms Nagle delay and made it disappear
- All three pathologies are reproduced, observed, and mitigated
- Part 5 shows the failure and the fix, with the TIME_WAIT count as evidence
