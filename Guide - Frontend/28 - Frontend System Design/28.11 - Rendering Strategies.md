# Rendering Strategies

Where and when HTML is produced. This is usually the first architectural decision in a frontend design, because it constrains SEO, initial load, infrastructure and data fetching.

## The options

| | HTML generated | Data freshness | Needs a server | TTFB |
| --- | --- | --- | --- | --- |
| **CSR** | in the browser | request time | no | fast, empty |
| **SSR** | per request | request time | yes | slower |
| **SSG** | at build time | build time | no | fastest |
| **ISR** | build + revalidate | configurable | yes | fast |
| **RSC + streaming** | per request, streamed | request time | yes | fast shell |

## CSR

```html
<div id="root"></div>
<script src="/assets/main.js"></script>
```

The server sends an empty shell; JavaScript downloads, executes, fetches data, and renders.

```
HTML (fast) → JS download → JS execute → fetch → render
                                                    ↑ first meaningful paint
```

The user sees nothing until the whole chain completes. On a mid-range phone over 4G that is commonly 3–6 seconds, and the JavaScript execution is on the main thread ([[13.1 - The Critical Rendering Path]]).

**Right for:** authenticated dashboards, internal tools, editors, anything behind a login where SEO is irrelevant and users have long sessions.

**Wrong for:** content that must rank, anything where first-visit performance matters, and pages shared on social platforms — most crawlers do not execute JavaScript, so Open Graph tags set client-side produce blank previews ([[09.4 - Head Metadata and SEO Basics]]).

## SSR

The server renders React to HTML per request:

```
Request → server fetches data → renders HTML → sends → hydrate
```

The user sees content on first paint. The cost is server compute per request and a slower TTFB, since the server must fetch before it can respond.

**Hydration** is the second cost: React downloads the same component code, rebuilds the tree client-side, and attaches event handlers. Until it finishes, the page looks interactive and is not — a real UX problem on slow devices.

Hydration mismatches are the recurring bug:

```jsx
<span>{new Date().toLocaleTimeString()}</span>       // server and client differ
<span>{Math.random()}</span>
{typeof window !== "undefined" && <ClientOnly />}     // differs by definition
```

React logs a mismatch and discards the server HTML for that subtree. The fix is rendering the same thing on both, and deferring genuinely client-only content:

```jsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
if (!mounted) return <Placeholder />;
```

`useId` exists specifically to generate ids that match across the boundary ([[17.12 - Lesser Known Hooks]]).

## SSG

HTML generated at build time and served as static files. Fastest possible delivery — a CDN edge hit with no compute ([[15.7 - HTTP Caching and CDNs]]).

**Right for:** marketing pages, documentation, blogs, changelogs — anything where content changes on a publishing cadence rather than per request.

**Wrong for:** personalized content, frequently-changing data, and very large page counts where build time becomes prohibitive. Ten thousand product pages that each take 200ms to render is a 30-minute build.

## ISR

Static generation with background revalidation:

```ts
export const revalidate = 60;      // regenerate at most once a minute
```

Serve the cached page instantly; regenerate in the background when stale. The same stale-while-revalidate idea that appears at every caching layer ([[28.6 - Caching Strategy Across Layers]]).

On-demand revalidation triggered by a CMS webhook is usually better than time-based — the page updates when content actually changes rather than on a timer.

This is the right default for content-driven sites at scale: static performance with near-real-time freshness.

## Streaming SSR and Server Components

```jsx
export default function Page() {
  return (
    <>
      <Header />                              {/* sent immediately */}
      <Suspense fallback={<Skeleton />}>
        <SlowSection />                       {/* streamed when ready */}
      </Suspense>
    </>
  );
}
```

Without streaming, SSR is all-or-nothing — the server waits for every data dependency before sending a byte, so TTFB is bounded by the slowest query.

With Suspense, the shell is sent immediately and slow sections stream in. React also hydrates **selectively**, prioritizing whatever the user interacts with first, so interactivity is no longer gated on the whole page hydrating ([[19.4 - Suspense]]).

Server Components go further: their code never ships to the client at all, so data-fetching code, ORM clients and markdown parsers contribute zero bundle bytes ([[22.8 - Server Components]]).

The distinction worth stating precisely: **SSR renders on the server and ships the component code for hydration; RSC ships only the rendered output and never re-renders.**

## Mixing strategies

Real applications are not one strategy:

```
/                    SSG      marketing
/blog/*              ISR      CMS-driven
/products/*          ISR      catalogue, revalidate on change
/search              SSR      query-dependent
/dashboard/*         CSR      authenticated, no SEO value
/api/*               server
```

Choosing per route is normal and correct. Frameworks make this a per-route configuration rather than an application-wide decision.

## Islands and partial hydration

```astro
<StaticHeader />
<InteractiveSearch client:visible />
<StaticFooter />
```

Ship HTML for everything, hydrate only the interactive pieces — and only when needed (`client:load`, `client:idle`, `client:visible`).

For content-heavy sites this is dramatically cheaper than full-page hydration, because most of a blog or documentation page has no interactivity at all. Astro popularized it; Qwik takes it further with resumability, avoiding hydration entirely.

Worth knowing as the answer when someone asks "why hydrate a page that is 95% static".

## Choosing

```
Does content need to rank or be shared?     → not CSR
Is it personalized per user?                → SSR or CSR (not SSG)
Does content change rarely?                 → SSG or ISR
Is there a server budget?                   → no server → CSR or SSG
Is first-visit performance critical?        → SSG/ISR, then SSR
Long sessions, authenticated, no SEO?       → CSR is fine
```

The most common mistake is defaulting to CSR because it is what a Vite template gives you, then discovering the SEO and first-load requirements later. The second most common is adopting SSR for an internal dashboard that gains nothing from it and now needs a Node deployment.

## Infrastructure implications

Each strategy carries operational weight:

**CSR/SSG** — static files on a CDN. No servers, trivial rollback, essentially unlimited scale.

**SSR/ISR/RSC** — a Node or edge runtime, scaling with traffic, cold starts on serverless, and server-side observability. Render failures become a production incident category that static hosting does not have.

Edge runtimes reduce latency by running close to users but restrict the available APIs — no filesystem, limited Node built-ins, execution time limits.

This is a genuine cost, and it is why "just add SSR" is not free ([[27.9 - CI CD and Frontend Deployment]]).

## Measuring the difference

```
TTFB    server response time
FCP     first content painted
LCP     largest element painted
INP     interaction responsiveness
TTI     fully interactive
```

SSR improves FCP and LCP but can worsen TTFB. CSR has excellent TTFB and poor LCP. SSG wins on all of them for content that fits it ([[13.5 - Core Web Vitals]]).

Measure on a throttled mid-range device, not a development laptop — the JavaScript execution cost that CSR pays is where the difference is largest, and it is invisible on fast hardware.

## How senior engineers actually use this

**They choose per route**, not per application.

**They start from the content requirements** — ranking, sharing, personalization, freshness — rather than from a framework preference.

**They treat SSR as a server commitment**, with the deployment and observability cost that implies.

**They use ISR with on-demand revalidation** for content-driven pages, rather than time-based guessing.

**They test on throttled mobile**, where the strategies actually diverge.

## Common pitfalls

- CSR by default, discovering the SEO requirement after launch.
- OG tags set client-side, producing blank social previews.
- Hydration mismatches from dates, random values or `window` checks.
- SSR adopted for an authenticated dashboard that gains nothing.
- SSG with tens of thousands of pages and an unworkable build time.
- Assuming SSR fixes performance — it moves work, and hydration remains.
- Ignoring the operational cost of running a server.
- Confusing SSR with RSC in discussion.

## Interview angle

"Which rendering strategy would you choose" wants the decision driven by requirements: SEO and social sharing rule out CSR, personalization rules out SSG, freshness needs push toward ISR or SSR, and a no-server constraint rules out half the options. State clearly that SSR ships component code for hydration while RSC ships only output, and that hydration is a real cost SSR does not remove. Mentioning that real applications mix strategies per route, and that islands exist for mostly-static pages, shows current understanding.
