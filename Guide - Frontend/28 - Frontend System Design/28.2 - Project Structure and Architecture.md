# Project Structure and Architecture

## Group by feature, not by type

The default structure most projects start with:

```
src/
  components/     Button.tsx, ProductCard.tsx, CheckoutForm.tsx, ...
  hooks/          useAuth.ts, useCart.ts, useProducts.ts, ...
  utils/
  types/
  api/
```

This works to about twenty files and then stops working. Changing one feature means editing five directories, related code is scattered, and nothing indicates which pieces belong together. Deleting a feature requires archaeology.

```
src/
  features/
    checkout/
      components/
      hooks/
      api/
      types.ts
      index.ts          ← the public surface
    products/
    auth/
  shared/
    ui/                 ← design system primitives
    lib/                ← genuinely generic utilities
    api/                ← the HTTP client
  app/
    routes/
    providers.tsx
```

Everything for a feature sits together. Deleting `features/checkout/` deletes the feature. A new team member reading `features/checkout/` sees the whole thing.

The organizing principle: **things that change together should live together**.

## Enforce the boundaries

A feature directory means nothing if any file can import any other. Two rules make it real:

**Features do not import each other's internals.**

```ts
import { CheckoutButton } from "@/features/checkout";              // public API
import { calcTax } from "@/features/checkout/lib/tax";             // reaching inside
```

**Dependencies point in one direction:**

```
app  →  features  →  shared
```

`shared` never imports from `features`. A shared component that knows about checkout is not shared.

Enforce with lint rather than convention:

```js
// eslint.config.js
"import/no-restricted-paths": ["error", {
  zones: [
    { target: "./src/features/*/!(index.ts)", from: "./src/features", except: ["./index.ts"] },
    { target: "./src/shared", from: "./src/features" },
  ],
}]
```

Unenforced conventions decay. The first violation is a shortcut under deadline; a year later the boundaries are fiction.

## The public surface

```ts
// features/checkout/index.ts
export { CheckoutPage } from "./components/CheckoutPage";
export { useCart } from "./hooks/useCart";
export type { CartItem } from "./types";
```

Exporting deliberately means internals can be refactored freely — nothing outside depends on them. This is the same reasoning as `exports` in a published package ([[27.1 - npm and package.json]]).

Keep it small. A barrel re-exporting thirty things is not a boundary, and it also hurts build and IDE performance ([[27.6 - Tree Shaking]]).

## What goes in shared

The bar is high. Something belongs in `shared` when it is used by **three or more** features and contains no domain knowledge.

```
shared/ui/          Button, Input, Modal — no business logic
shared/lib/         formatDate, cn, debounce
shared/api/         the HTTP client, error types
shared/hooks/       useMediaQuery, useLocalStorage
```

The premature-abstraction trap is real: two features need something similar, it moves to `shared`, then their requirements diverge and it accumulates flags to serve both. Duplicating until the third use makes the right abstraction visible.

The reverse is also a failure — a `shared/utils.ts` that grows to 800 lines of unrelated functions is a dumping ground, not a module.

## Cross-feature communication

Features will need each other. Three acceptable mechanisms:

**Composition at the route level.** The route imports both and wires them:

```tsx
<ProductPage>
  <AddToCartButton productId={id} />
</ProductPage>
```

**Shared state through a store**, owned by neither:

```ts
// shared/stores/cart.ts
export const useCartStore = create(...);
```

**Events**, for genuinely decoupled reactions — analytics, notifications.

What to avoid: feature A importing feature B's internals, and circular imports between features. A cycle between two features usually means they are one feature ([[08.1 - ES Modules vs CommonJS]]).

## Layering within a feature

```
components/    presentation
hooks/         feature logic, state wiring
api/           queries, mutations, endpoint functions
lib/           pure domain logic — pricing, validation
types.ts
```

The valuable separation is **pure domain logic from React**. A `calculateOrderTotal` function with no hooks and no components is testable without a renderer, reusable on the server, and independently verifiable ([[26.2 - Unit Testing with Vitest and Jest]]).

Extracting logic specifically to make it a pure function is a legitimate design pressure, not over-engineering.

## Naming and colocation

```
ProductCard.tsx
ProductCard.test.tsx
ProductCard.module.css
```

Colocating tests and styles means deleting the component deletes everything belonging to it. A separate `styles/` or `__tests__/` tree reliably accumulates orphans nobody dares remove ([[11.5 - CSS Architecture]]).

Pick one file naming convention and lint it. `PascalCase` for components and `camelCase` for everything else is the most common. What matters is consistency — mixed conventions make files hard to find.

## Path aliases

```json
{ "compilerOptions": { "paths": { "@/*": ["./src/*"] } } }
```

```ts
import { Button } from "@/shared/ui/Button";       // not ../../../shared/ui/Button
```

Relative paths past two levels are unreadable and break on every file move. Configure the alias in both `tsconfig.json` and the bundler, or use `vite-tsconfig-paths` to derive one from the other ([[27.3 - Vite]]).

## Monorepos

Worth it when there are multiple deployable applications sharing code:

```
apps/
  web/
  admin/
packages/
  ui/
  schemas/          ← shared between client and server
  config/
```

The strongest case is **shared schemas** validated on both client and server, so validation rules cannot drift ([[25.7 - Typing API Responses and Zod]]).

The cost is real: tooling complexity, longer CI without task caching, and versioning decisions. For a single application, a monorepo is overhead. pnpm workspaces plus Turborepo is the standard setup when it is justified.

## Signals the structure is wrong

- A change to one feature touches five directories
- Nobody can say where a new file belongs
- `shared/utils.ts` is 800 lines
- Circular import warnings
- Two features import each other's internals
- Deleting a feature leaves orphaned files
- Import paths with four or more `../`

## Restructure incrementally

A full reorganization is a large, risky, unreviewable PR. Better:

1. Add the alias and lint rules first
2. Create `features/` and move **one** feature into it
3. Move the next feature when someone next touches it
4. Extract to `shared` only on the third use

The old and new structures coexist during the transition. Perfect consistency is not worth a week of merge conflicts.

## How senior engineers actually use this

**They group by feature and enforce boundaries with lint**, since conventions alone decay.

**They keep `shared` small** and require three uses before extracting.

**They separate pure domain logic from React**, which makes it testable and portable.

**They colocate tests and styles** so deletion is complete.

**They restructure incrementally**, feature by feature, rather than in one large PR.

## Common pitfalls

- Type-based folders (`components/`, `hooks/`) at scale.
- Unenforced boundaries that erode within months.
- Premature extraction to `shared`, then divergent requirements.
- Barrel files re-exporting everything, hurting builds and hiding coupling.
- Circular imports between features.
- Deep relative paths instead of aliases.
- A monorepo for a single application.
- Big-bang restructures.

## Interview angle

"How would you structure a large React application" wants feature-based organization with the reasoning — things that change together live together, and a feature directory is deletable as a unit. The details that mark experience: boundaries must be lint-enforced rather than conventional, `shared` needs a high bar (three uses, no domain knowledge), dependencies point one way from app to features to shared, and restructuring should be incremental. Mentioning that pure domain logic belongs outside React shows testing awareness too.
