# LWC Questions

## Fundamentals

**What is LWC, and how does it differ from Aura?**

LWC is built on web standards — custom elements, shadow DOM, ES modules, modern JavaScript — with a thin Salesforce layer for data access and navigation.

The practical difference is that what you know about web development transfers. Aura had its own component model, expression syntax, and event system, all learned separately.

Three specific changes: no logic in templates, so `{!v.a > v.b}` becomes a getter in the class; events are standard DOM events rather than a framework construct; and there is no two-way binding, so data flows down through properties and back up through events with the path always visible.

The nesting rule matters for migration: an LWC can be placed inside an Aura component, never the reverse. So migration works inward from the leaves.

**What is in a component bundle?**

The template, the JavaScript class, and the metadata file, plus optional CSS, an SVG icon for App Builder, and Jest tests.

The metadata file is the one people get wrong. `isExposed` must be true, and the right targets declared, or the component is invisible in App Builder regardless of what else is correct. That is the most common cause of "my component doesn't appear".

**How does shadow DOM affect what you can do?**

Styles are scoped — a class in one component cannot affect another, and that is enforced rather than conventional.

A parent cannot query into a child's shadow root. `this.template.querySelector` searches this component only.

And third-party libraries that expect global DOM access break, because `document.querySelector` cannot see inside a component. That is the check to run before committing to a library: does its initialization take an element, or a selector string?

## Reactivity

**How does reactivity work?**

Every field is reactive by default. Assigning to one that the template uses triggers a rerender.

The rule that matters: **reactivity is triggered by assignment to the field, not by mutation of what it holds.**

```javascript
this.claims = [...this.claims, newClaim];   // rerenders
this.claims.push(newClaim);                 // does not
```

That is the single most common source of "my UI isn't updating". The data changed; the field did not.

Treating component state as immutable — always producing new values — removes the whole class of bug.

**When would you use `@track`?**

Rarely. It makes deep mutations reactive, observing changes inside an object.

It earns its place in a form with many fields where spreading the whole object on every keystroke is noisy. Everywhere else, reassignment is clearer about what changed and cheaper.

A lot of documentation still shows `@track` on every field, which has not been necessary for several releases.

**Explain `@api` and its constraints.**

It exposes a property or method to the parent. Property names translate to kebab-case in markup — `showActions` becomes `show-actions`.

The constraint people miss: **public properties are read-only inside the component.** Assigning to `this.claim` throws, and mutating the object it holds is equally wrong — the child is modifying data the parent owns, and the parent's reactivity does not fire.

If the child needs a working copy, it takes one in a setter.

For a getter-setter pair, `@api` goes on the getter only. And the setter can fire before the component is connected, so anything needing the DOM has to be deferred.

**How does `@wire` work, and what is the `$` for?**

It connects the component to a data source that pushes updates.

The `$` prefix makes a parameter reactive — when `recordId` changes, the wire re-executes. Without it the value is captured once and never refreshes, which is a silent bug where the component works on first load and never updates.

Wires run automatically before `connectedCallback` completes and cannot be triggered on demand. Both `data` and `error` start undefined, so the loading state needs handling explicitly.

The way to defer a wire is leaving a reactive parameter undefined — a wire with an undefined parameter does not execute, which is how "don't search until three characters" works.

## Data

**Wire or imperative — how do you choose?**

Wire for read-only data tied to reactive inputs, where caching helps and automatic refresh is wanted. It requires `cacheable=true`, which forbids DML.

Imperative for anything a user triggers, anything that writes, anything needing sequencing, and anything conditional.

Most components use both — a wire for the list, imperative calls for the actions.

**After an imperative update, the wired list doesn't refresh. Why, and what do you do?**

The Apex client cache. `cacheable=true` means the result is cached by method and parameters, and the wire has no idea anything changed.

`refreshApex` on the stored wire result — which requires keeping the whole result object, not just its data, because `refreshApex` needs the handle attached to it.

The thing to know is that there are two caches. `refreshApex` invalidates the Apex cache; `notifyRecordUpdateAvailable` invalidates the Lightning Data Service record cache. They are different, and using the wrong one does nothing — which produces the confusing situation where `refreshApex` is called and the record panel still shows old values.

If the update went through LDS itself, neither is needed — the cache updates automatically.

**When would you use Lightning Data Service over Apex?**

For single-record read and write, LDS should be the default.

It enforces field-level security and sharing automatically, shares a cache across every component on the page, and keeps them in sync when a record changes. That removes an Apex class, its test class, the `WITH USER_MODE` you might forget, and the `stripInaccessible` you might not know about.

**The best Apex controller is frequently no Apex controller.**

Apex for filtered lists, aggregations, bulk operations, and cross-object logic — the things LDS cannot do.

The GraphQL wire adapter covers a useful middle ground: filtered, related queries with field-level security enforced and no Apex.

## Communication

**How do components communicate?**

Parent to child through `@api` properties, and public methods for imperative operations like refresh or validate.

Child to parent through a `CustomEvent`. The naming rule catches everyone once: **event names must be lowercase with no hyphens or camelCase**, because HTML attributes are case-insensitive — `onclaimApproved` in markup is read as `onclaimapproved`, so a camelCase event name never matches its handler. It fails silently.

Across the DOM — siblings, or a utility bar component talking to a record page — Lightning Message Service.

**What about `bubbles` and `composed`?**

Default to both false, so the event reaches the immediate parent only.

`composed: true` crosses shadow boundaries and can be caught by anything on the page, which couples the component to consumers it does not know about and makes refactoring risky.

Where an event needs to travel several levels, re-dispatching through each intermediate is more verbose and keeps each component's contract explicit. Where it needs to cross unrelated parts of the page, LMS is better than a composed event, because the channel is declared rather than depending on DOM position.

**When would you use Lightning Message Service?**

Siblings with no shared parent, utility bar to page, or crossing a technology boundary — LWC to Aura to Visualforce, which is genuinely useful in an org carrying old pages.

Two things it needs: `MessageContext` wired, without which publish and subscribe throw. And unsubscribe in `disconnectedCallback`, because in a console where components mount and unmount on every tab switch, leaked subscriptions accumulate.

`APPLICATION_SCOPE` is required for a utility bar component to hear page messages, and it is not the default — a subscriber without it receives nothing, with no error.

## Lifecycle

**Walk through the lifecycle hooks.**

Constructor, then `@api` properties are set, then `connectedCallback`, then render, then children go through the same sequence, then `renderedCallback`. Then `renderedCallback` again on every rerender, and `disconnectedCallback` on removal.

`connectedCallback` is where subscriptions, listeners, and imperative loads go. `@api` properties are available; the DOM is not.

`renderedCallback` is where the DOM exists, and it is the one most often misused. It fires on **every** rerender, so one-time work needs a guard. And setting reactive state there unguarded is an infinite loop — the assignment triggers a rerender, which calls it again.

`disconnectedCallback` is cleanup, and skipping it is how streaming subscriptions leak in a console.

`errorCallback` is the error boundary. It catches errors from descendants, not from the component itself, and it is underused — a dashboard where one failing child blanks the whole page is a worse experience than one showing five components and an error panel.

## Performance

**A record page takes eight seconds to load. How do you diagnose it?**

First, client or server. Chrome DevTools network tab, or the Page Optimizer extension which does it specifically for Lightning pages.

If it is the server, a debug log and the limit block — usually a non-selective query or accumulated automation.

If it is the client, the usual causes in order: too many components each making their own Apex call, read-only methods without `cacheable=true`, several wires where one composed method would do, expensive getters recomputing on every rerender, and large lists rendered without pagination.

**Why do getters matter?**

A getter used in the template is called on every rerender, including ones with nothing to do with its data. A getter sorting and mapping three hundred rows re-runs when an unrelated `isLoading` toggles.

There is a subtler cost too: a getter returning a new array each call defeats the diff, because LWC compares by reference — so the whole list rerenders even when nothing changed.

Transform data in the wire handler instead, so it runs once per data change.

**What else affects rendering?**

Iteration keys. Using the index means removing an item makes every subsequent row reuse the wrong DOM node and the wrong component state — the visible symptom is a checkbox appearing ticked on the wrong row. A stable unique identifier is what lets LWC reuse DOM for unchanged rows.

And `lwc:if` versus CSS hiding. A component behind a false `lwc:if` is not constructed, its wires do not run, and its `connectedCallback` does not fire. A tabset rendering all six panels on load pays for six components the user may never open.

All of this matters more in a console, where components rerender on every tab switch and an agent may hold six tabs open.

## Security

**What do you have to be careful about in the Apex behind a component?**

That every `@AuraEnabled` method is effectively a public endpoint. Any authenticated user can call it directly with any parameter, regardless of what the component renders.

So: a sharing keyword on the class, `WITH USER_MODE` on queries, `as user` on DML, and `stripInaccessible` on any sObject arriving from the client — because otherwise a component rendering three fields can be used to write to any field on the object.

And verifying entitlement for client-supplied record Ids, returning not-found rather than not-permitted so the response does not confirm the record exists.

The test that matters is calling the method as a non-administrator with an Id that user should not see. Testing as an administrator proves nothing, because they see everything.

**A component works for you and shows nothing for other users.**

Most likely Apex class access. A user without access to the class the component calls gets a blank component, and the developer's admin profile hides it.

Then field-level security, since LDS silently omits fields the user cannot read. Then component visibility filters in App Builder.

## Testing

**How do you test an LWC?**

Jest, through `sfdx-lwc-jest`. Create the element, set properties, append it to the document, and assert on the rendered output and the dispatched events.

Two mechanics that catch people: rendering is asynchronous, so a property set after the element is in the DOM needs an awaited promise before asserting. And the DOM persists between tests unless cleared in `afterEach`, which produces confusing failures where a selector matches the previous test's element.

Wires are mocked with the test wire adapter — `emit` pushes data in, `error` pushes a failure. Testing the error path matters as much as the success path; a component that renders correctly with data and blanks on error is a defect users will find.

**What is worth testing?**

Presentational components heavily, because they are cheap — set a property, assert on the output, no mocking needed. That is the payoff for separating them from containers.

Containers need mocking and there are fewer of them: that the right Apex is called with the right parameters, that data renders, that errors are handled.

And I would test that subscriptions unsubscribe on disconnect. Leaked subscriptions are invisible in manual testing and appear only under sustained use.

What I would not test: base component internals, the framework, or trivial getters. A test asserting that `lightning-button` renders a button tests Salesforce.

**How does LWC testing compare to Apex testing?**

Jest runs in seconds with no org, which makes it the fastest feedback available in a Salesforce project — worth running on every commit.

And there is no platform-imposed coverage requirement, so whatever the team sets is the standard. Enforcing it in CI is what makes it real.

## What is being assessed

**Junior:** knows the bundle, decorators, and basic templating.

**Mid:** knows the reassignment rule, wire versus imperative, the two caches, and lifecycle timing.

**Senior:** raises performance implications unprompted — getters on rerender, iteration keys, `lwc:if` versus hiding — and treats `@AuraEnabled` methods as public endpoints without being asked.

**The answer that marks experience** is preferring Lightning Data Service to a custom Apex controller, because it demonstrates knowing that the platform's data layer removes the security code most likely to be got wrong.
