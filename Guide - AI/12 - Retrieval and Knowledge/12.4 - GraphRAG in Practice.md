# GraphRAG in Practice

## What It Is

GraphRAG augments standard RAG with an explicit knowledge graph of entities and relationships, enabling multi-hop reasoning ("How is A connected to B?"), thematic summarization ("What are the main themes in this corpus?"), and structured relationship queries that vector similarity alone cannot handle.

This file covers two production implementations: **Microsoft GraphRAG** (community-based, global search focus) and **LightRAG** (simpler, incremental, better for dynamic corpora). The focus is on what actually works, what costs what, and when to choose graph-based retrieval over standard hybrid RAG.

---

## Why It Matters

- Standard RAG fails on multi-hop reasoning. GraphRAG's entity traversal is the fix.
- However, GraphRAG indexing costs 10-50× more than standard RAG. Recommending it without understanding the cost is a red flag in interviews.
- Microsoft GraphRAG is a frequently cited production system — being able to discuss its architecture, limitations, and when to use LightRAG instead shows genuine depth.
- DevRev and similar companies build knowledge systems over code, issues, and documentation — graph-based approaches are relevant.

## Microsoft GraphRAG — Architecture

### Pipeline Overview

```
Documents
    │
    ▼
[Text Chunking]
    │
    ▼
[Entity & Relationship Extraction]  ← LLM call per chunk (expensive)
    │
    ▼
[Knowledge Graph]                   ← entities as nodes, relationships as edges
    │
    ├── [Community Detection]        ← Leiden algorithm clusters related entities
    │
    └── [Hierarchical Summary Gen]  ← LLM generates summary per community level
                                       Level 0: individual entities
                                       Level 1: small clusters
                                       Level 2: medium clusters
                                       Level 3: large themes
At Query Time:
    ├── Global queries  → search community summaries (pre-computed)
    └── Local queries   → graph traversal from query entities
```

### Entity and Relationship Extraction

```python
EXTRACTION_PROMPT = """
Extract all entities and relationships from the following text.

Entity types to extract: PERSON, ORGANIZATION, PRODUCT, CONCEPT, LOCATION, EVENT, DATE

For each entity:
- name: canonical name
- type: entity type
- description: brief description

For each relationship:
- source: source entity name
- target: target entity name
- type: relationship type (e.g., WORKS_FOR, FOUNDED, ACQUIRED, PART_OF)
- description: brief description of the relationship

Text:
{text}

Output JSON:
{
  "entities": [...],
  "relationships": [...]
}
"""

def extract_graph_elements(chunk_text: str, llm) -> dict:
    result = llm.call(
        EXTRACTION_PROMPT.format(text=chunk_text),
        response_format={"type": "json_object"},
        temperature=0,
    )
    return json.loads(result)
```

### Community Detection with Leiden Algorithm

The Leiden algorithm partitions the entity graph into communities (clusters of highly connected entities) at multiple resolutions:

```python
import graspologic  # Microsoft's graph library used in GraphRAG

def detect_communities(graph: nx.Graph) -> dict[int, list[str]]:
    """
    Returns: {community_id: [entity_names]}
    """
    from graspologic.partition import hierarchical_leiden

    # Hierarchical Leiden gives communities at multiple levels
    community_mapping = hierarchical_leiden(
        graph,
        max_cluster_size=10,   # max entities per community at finest level
        random_seed=42,
    )

    # community_mapping: {node: community_id}
    communities = {}
    for node, community_id in community_mapping.items():
        communities.setdefault(community_id, []).append(node)

    return communities
```

### Community Summary Generation

For each community, generate a summary using an LLM:

```python
COMMUNITY_SUMMARY_PROMPT = """
You are analyzing a knowledge graph community. The following entities and their
relationships form a cluster of related concepts.

Entities: {entities}
Relationships: {relationships}

Write a comprehensive summary of what this community represents, the key themes,
important entities, and how they relate to each other.
Keep the summary concise (3-5 sentences) but information-dense.
"""

def generate_community_summary(community_entities: list, community_relationships: list, llm) -> str:
    return llm.call(COMMUNITY_SUMMARY_PROMPT.format(
        entities=json.dumps(community_entities, indent=2),
        relationships=json.dumps(community_relationships, indent=2),
    ))
```

### Query Modes

**Global search** (thematic / high-level questions):

```python
def global_search(query: str, community_summaries: list[str], llm) -> str:
    """
    Searches across pre-computed community summaries.
    Best for: "What are the main themes?", "Give me an overview of X"
    """
    # Score each community summary by relevance
    relevant_summaries = []
    for summary in community_summaries:
        relevance = llm.call(
            f"Rate relevance (0-10) of this summary to the query: {query}\n\nSummary: {summary}\n\nScore:",
            temperature=0,
        )
        if int(relevance.strip()) >= 6:
            relevant_summaries.append(summary)

    # Generate answer from relevant summaries
    context = "\n\n".join(relevant_summaries[:10])
    return llm.call(f"Answer this question using the provided summaries:\n{query}\n\nSummaries:\n{context}")
```

**Local search** (entity-specific questions):

```python
def local_search(query: str, graph: nx.Graph, entity_store: dict,
                 text_chunks: list, llm) -> str:
    """
    Traverses graph from entities mentioned in the query.
    Best for: "What did X say about Y?", "How is A related to B?"
    """
    # Find entities mentioned in query
    query_entities = extract_entities_from_query(query, llm)

    # Get k-hop neighborhood for each entity
    context_entities = set()
    for entity in query_entities:
        if entity in graph:
            neighbors = nx.ego_graph(graph, entity, radius=2).nodes()
            context_entities.update(neighbors)

    # Retrieve text chunks that mention these entities
    relevant_chunks = [
        chunk for chunk in text_chunks
        if any(entity.lower() in chunk.text.lower() for entity in context_entities)
    ]

    context = "\n\n".join(c.text for c in relevant_chunks[:10])
    return llm.call(f"Answer: {query}\n\nContext:\n{context}")
```

### Real Cost of Microsoft GraphRAG

```
For a 1,000-document corpus (avg 2,000 tokens each):
= 2,000,000 input tokens for extraction

At GPT-4o pricing ($2.50/1M):
= $5 in extraction LLM calls (input only)

But each chunk also generates ~200 output tokens:
= 200,000 output tokens @ $10/1M = $2

Community summaries (roughly 100 communities × 500 tokens):
= 50,000 output tokens @ $10/1M = $0.50

Total: ~$7.50 for 1,000 documents

For comparison: standard RAG embedding for same corpus:
= 2,000,000 tokens @ $0.02/1M (text-embedding-3-small) = $0.04

GraphRAG is ~190× more expensive to index than standard RAG.
```

**When this is worth it**: Corpus is relatively stable (you pay the indexing cost once), queries require multi-hop reasoning or thematic synthesis, and the quality improvement is demonstrable on your eval set.

## LightRAG — Simpler and Incremental

Microsoft GraphRAG is powerful but has significant limitations:
- Full re-index required when corpus changes (expensive)
- Complex operational dependencies (graspologic, networkx, specific LLM calls)
- Overkill for many use cases

**LightRAG** (HKPU, 2024) is a simpler alternative with incremental update support.

### Key Differences from Microsoft GraphRAG

| Dimension | Microsoft GraphRAG | LightRAG |
|-----------|-------------------|----------|
| Indexing | Full corpus, batch | Incremental, per-document |
| Community detection | Leiden (hierarchical) | No formal community detection |
| Query modes | Global + Local | Naive + Local + Global + Hybrid |
| Setup complexity | High | Low |
| Incremental updates | No | Yes |
| Code quality | Production-grade | Research-quality |
| Storage | Custom | Neo4j / NetworkX / JSON |

### LightRAG Implementation

```python
# Install: pip install lightrag-hku
from lightrag import LightRAG, QueryParam
from lightrag.llm import openai_complete_if_cache, openai_embedding
import asyncio

# Initialize
rag = LightRAG(
    working_dir="./lightrag_storage",
    llm_model_func=openai_complete_if_cache,        # LLM for extraction + generation
    embedding_func=openai_embedding,                # Embeddings for vector search
    llm_model_max_token_size=8192,
    llm_model_max_async=4,                          # parallel LLM calls during indexing
)

# Index documents (incremental — can call multiple times)
with open("document1.txt") as f:
    asyncio.run(rag.ainsert(f.read()))

with open("document2.txt") as f:
    asyncio.run(rag.ainsert(f.read()))  # adds to existing graph incrementally

# Query modes
print(asyncio.run(rag.aquery(
    "What are the main themes in these documents?",
    param=QueryParam(mode="global")    # global: community-level summaries
)))

print(asyncio.run(rag.aquery(
    "How is entity A related to entity B?",
    param=QueryParam(mode="local")     # local: entity neighborhood traversal
)))

print(asyncio.run(rag.aquery(
    "What did the CEO say about revenue?",
    param=QueryParam(mode="hybrid")    # hybrid: combines vector + graph
)))
```

### LightRAG Internal Storage

LightRAG stores its graph as a simple JSON/NetworkX graph alongside a vector store:

```
./lightrag_storage/
├── graph_chunk_entity_relation.graphml   ← entity-relationship graph (NetworkX)
├── kv_store_full_docs.json              ← full document text
├── kv_store_text_chunks.json            ← text chunks
├── vdb_entities.json                    ← entity embeddings (vector index)
└── vdb_chunks.json                      ← chunk embeddings (vector index)
```

For production: replace the default JSON storage with Neo4j + Qdrant:

```python
from lightrag.storage import Neo4JStorage, QdrantVectorDBStorge

rag = LightRAG(
    working_dir="./lightrag_storage",
    graph_storage="Neo4JStorage",        # production graph DB
    vector_storage="QdrantVectorDBStorge", # production vector DB
    # ... other config
)
```

## When to Use GraphRAG vs Standard RAG

```
Query type analysis:

"What was Apple's Q3 2024 revenue?"
→ Standard RAG (factual lookup, single-hop)

"Summarize the main themes across all earnings calls this year"
→ GraphRAG global search (thematic synthesis)

"How is Tim Cook's comments about China related to iPhone supply chain issues?"
→ GraphRAG local search (multi-hop entity relationship)

"What are all the products Apple mentioned in Q3?"
→ Standard RAG with metadata filter OR GraphRAG local

"Compare Apple's strategy to its competitors mentioned in this document set"
→ GraphRAG local (entity comparison via graph)
```

**Decision rule**:

```
Are your users frequently asking multi-hop or thematic questions?
├── No → Standard hybrid RAG (BM25 + dense + reranker)
│         Save 190× on indexing costs
└── Yes

Is your corpus relatively stable?
├── No → LightRAG (supports incremental updates)
└── Yes

Is your corpus large enough to benefit from community summaries?
├── < 500 docs → LightRAG or just skip GraphRAG
└── > 500 docs → Microsoft GraphRAG or LightRAG

Budget for indexing?
├── Low → LightRAG (cheaper per-document extraction)
└── High → Microsoft GraphRAG (higher quality community structure)
```

## Hybrid: GraphRAG + Standard RAG

The best production approach combines both:

```python
async def hybrid_graph_vector_retrieve(query: str, rag_system, graph_rag) -> list:
    """
    Use standard retrieval for most queries, graph only when needed.
    """
    # First: classify query type
    query_type = await classify_query(query)

    if query_type == "factual":
        # Standard hybrid RAG — fast, cheap
        return await rag_system.retrieve(query, top_k=10)

    elif query_type == "relational":
        # GraphRAG local search — entity traversal
        graph_context = await graph_rag.local_search(query)
        vector_chunks = await rag_system.retrieve(query, top_k=5)
        return merge_and_deduplicate(graph_context, vector_chunks)

    elif query_type == "thematic":
        # GraphRAG global search — community summaries
        return await graph_rag.global_search(query)

    else:
        # Default: standard RAG
        return await rag_system.retrieve(query, top_k=10)

async def classify_query(query: str) -> str:
    """Quick classification — use cheap/fast model."""
    result = await fast_llm.call(
        f"Classify this query as: factual, relational, thematic, or other.\n"
        f"factual: asks for a specific fact\n"
        f"relational: asks how things are connected\n"
        f"thematic: asks for themes or synthesis across many documents\n"
        f"Query: {query}\n"
        f"Output only: factual | relational | thematic | other"
    )
    return result.strip().lower()
```

## Revision Anchors

- **GraphRAG pipeline**: Chunk → extract entities/relationships (LLM) → build graph → community detection (Leiden) → generate summaries per community → at query time: global = search summaries, local = graph traversal.
- **Real cost**: GraphRAG indexing ≈ 190× more expensive than standard RAG embedding. Justify this only for stable corpora with clear multi-hop query patterns.
- **LightRAG advantages**: Incremental updates (no full re-index), simpler setup, research-friendly. Disadvantage: less mature, no formal community hierarchy.
- **Global vs local search**: Global = pre-computed community summaries → thematic/overview questions. Local = entity neighborhood traversal → relationship/specific questions.
- **Don't default to GraphRAG**: Standard hybrid RAG handles 80-90% of enterprise search use cases. Graph adds complexity and cost that must be justified by eval improvement on specific query types.
- **Hybrid pattern**: Classify query type first (cheap LLM call), then route: factual → standard RAG, relational → GraphRAG local, thematic → GraphRAG global.
