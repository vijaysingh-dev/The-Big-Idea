# GraphQL Caching

#backend #api-design #graphql #caching

> **In one line:** GraphQL sends every query to one URL as a POST, which makes HTTP caching useless — so caching moves into the client, into the resolvers, and into a persisted-query layer that gives you GETs back.

---

## The Idea

REST caching works because a URL identifies a response. GraphQL breaks all three assumptions ([[03.5 - HTTP Caching]]):

| Assumption | GraphQL |
|---|---|
| The URL identifies the response | Every query hits `/graphql` |
| GET is cacheable | Queries are POSTs |
| Responses are homogeneous | Every query returns a different shape |

💡 **The consequence is that you lose the entire caching chain — browser, CDN, reverse proxy — by default.** That is a real cost, and it is the one most GraphQL adoption discussions skip.

---

## Layer 1: Normalised Client Cache

```json
{"document": {"id": "doc_42", "title": "Q3", "author": {"id": "usr_7", "name": "Alice"}}}
```

```
"Document:doc_42": {"id": "doc_42", "title": "Q3", "author": {"__ref": "User:usr_7"}}
"User:usr_7":      {"id": "usr_7", "name": "Alice"}
```

Objects are stored once by type and ID. When a mutation returns an updated `User:usr_7`, **every view showing that user updates automatically.**

⚠️ **This only works if every object exposes a globally unique ID.** If two types can share an ID value, the cache merges unrelated objects. **Prefix your IDs or use globally unique opaque IDs.**

💡 **The implication for backend design: always return the mutated object with its ID from a mutation.** A mutation returning `{"ok": true}` forces a refetch; returning the object updates every cached view for free. **That is a schema decision with a large client-side payoff.**

**Where it breaks down: list membership.** A mutation creating a document updates `Document:doc_99`, but no existing list query knows to include it. Clients handle this with explicit cache updates or refetching, and **it is the main source of GraphQL client complexity.**

---

## Layer 2: Persisted Queries

The technique that gets HTTP caching back.

```
1. Client hashes the query:  sha256(query) = "a1b2c3..."
2. Client sends:  GET /graphql?id=a1b2c3&variables={"id":"doc_42"}
3. Server looks up the query text by hash and executes it
```

| Gain | |
|---|---|
| **CDN caching works** | Standard `Cache-Control` applies |
| **Smaller requests** | A hash instead of a 3KB query |
| **An allow-list** | Unknown hashes rejected — arbitrary queries become impossible |
| **Cost known in advance** | Every registered query can be analysed offline |

### Two flavours

**Build-time registration.** A build step extracts every query from client code and uploads them; the server rejects anything not in the manifest.

**Automatic Persisted Queries (APQ).** The client sends only the hash; if unknown, it retries with the full text and the server caches it.

💡 **Build-time registration is strictly better for a first-party API.** It gives you an allow-list, which eliminates the entire class of malicious-query attacks — depth limits, complexity analysis and introspection blocking all become moot when only known queries can run ([[05.8 - GraphQL Security and Limits]]).

⚠️ **APQ is not a security feature.** Any client can register any query. It gives smaller requests and GET-ability, not an allow-list.

### Getting GET right

⚠️ **The `Vary` and `private` rules from [[03.5 - HTTP Caching]] apply with force.** A GraphQL response almost always depends on the authenticated user; caching it `public` at a CDN serves one user's data to another.

**For genuinely public data, `public` caching is enormously effective. For anything authenticated, `private` plus ETags is the ceiling** — which still saves bandwidth via 304s.

## Layer 3: Server-Side Caching

### Cache inside the batch function

```python
async def batch_load_sources(ids: list[str]) -> list[Source | None]:
    cached = await redis.mget([f"source:{i}" for i in ids])
    result, missing = {}, []

    for i, raw in zip(ids, cached):
        if raw:
            result[i] = Source.model_validate_json(raw)
        else:
            missing.append(i)

    if missing:
        rows = await db.fetch("SELECT * FROM sources WHERE id = ANY($1)", missing)
        pipe = redis.pipeline()
        for r in rows:
            s = Source(**r)
            result[r["id"]] = s
            pipe.setex(f"source:{r['id']}", 300, s.model_dump_json())
        await pipe.execute()

    return [result.get(i) for i in ids]
```

💡 **Putting the cache inside the batch function is the right layering.** Every resolver needing a source benefits, batching still works for misses, and invalidation has one place to happen.

### Field-level cache hints

```python
@strawberry.field(extensions=[CacheControl(max_age=3600, scope="PUBLIC")])
def organisation_name(self) -> str: ...

@strawberry.field(extensions=[CacheControl(max_age=0, scope="PRIVATE")])
def unread_count(self) -> int: ...
```

The server computes the **minimum** `max-age` across all fields and emits one header.

⚠️ **One `max_age=0` field poisons an otherwise cacheable query.** In practice this means clients should split queries by cacheability — a cacheable query for reference data, a separate one for user-specific data. **That is a real design constraint worth telling your frontend team about early.**

### Response caching by query hash

```python
key = f"gql:{query_hash}:{hash(variables)}:{user.org_id}"
```

⚠️ **The key must include everything affecting the result** — query, variables, and the authorisation scope. **Omitting the org or user scope is a cross-tenant data leak.**

**Do not cache by default.** Only cache responses for queries explicitly marked cacheable, with the scope explicitly in the key.

## Invalidation

One mutation can affect many cached queries, and you cannot enumerate them.

| Approach | Trade |
|---|---|
| **Short TTLs** | Simple. Stale for the TTL |
| **Entity-based invalidation** | Track which entities each response touched, purge by entity |
| **Client normalised cache** | The client resolves it — **which is why layer 1 matters most** |

```python
# Entity tagging
touched: set[str] = info.context.touched_entities   # {"Document:42", "User:7"}
await redis.setex(f"gql:{key}", ttl, response)
for entity in touched:
    await redis.sadd(f"gql:dep:{entity}", key)

async def invalidate(entity: str):
    keys = await redis.smembers(f"gql:dep:{entity}")
    if keys:
        await redis.delete(*keys, f"gql:dep:{entity}")
```

This is surrogate keys ([[03.5 - HTTP Caching]]) applied inside your application. It works and it is real bookkeeping.

💡 **The honest position: most teams do not build entity-based invalidation.** They use short TTLs for public data, rely on the client cache for user data, and accept staleness. **That is reasonable and worth stating explicitly rather than discovering by omission.**

## In Production

### What to actually do

```
1. Normalised client cache               ← the biggest win, and free
2. DataLoader per-request cache          ← mandatory anyway
3. Redis behind batch functions          ← for hot reference data
4. Persisted queries + GET               ← for public, cacheable queries
5. CDN caching                           ← only for genuinely public data
```

⚠️ **Skip layers 4 and 5 unless you have genuinely public, high-volume queries.** The complexity is only justified by traffic you can actually offload.

### Measuring

```python
graphql_cache_hits_total.labels(layer=...).inc()
graphql_db_queries_per_request.observe(count)
graphql_persisted_query_hit_ratio.set(ratio)
```

**Queries-per-request is the metric that tells you whether any of this works.** If it is flat at 3 for your main query regardless of cache configuration, your caching is doing nothing.

### The comparison nobody makes

For a read-heavy public endpoint:

| | REST | GraphQL |
|---|---|---|
| CDN cacheable | Yes, trivially | Only with persisted queries + GET |
| Achievable hit ratio | 90%+ | **0% by default** |
| Origin requests at 10k rps | ~1,000 | 10,000 |

💡 **This is a genuine architectural cost of GraphQL and it should be part of the adoption decision.** If your API is dominated by a small number of cacheable public queries, REST plus a CDN serves them for a fraction of the infrastructure. **GraphQL earns its place when queries are diverse and user-specific — which is exactly when caching would not have helped anyway.**

**Being able to state that tradeoff clearly is worth more in a design discussion than any amount of GraphQL enthusiasm.**

### The hybrid that often wins

```
/api/public/*        REST, aggressively CDN-cached
/graphql             GraphQL, for authenticated app queries
```

**Nobody says you must choose one**, and the split usually maps cleanly onto cacheable-versus-personalised.

**Part 1 — Measure what you lost.** The same document-list data via REST and GraphQL, with nginx `proxy_cache` in front of both.

Measure origin requests per second and cache hit ratio for each.

**REST should be near 90%; GraphQL should be 0%.** Chart it. **That number is the cost of GraphQL's caching model, stated plainly.**

**Part 2 — Persisted queries.** Build-time registration with a manifest, plus a GET transport carrying hash and variables.

**Re-run part 1 for GraphQL. Measure the hit ratio now.**

Then add APQ and compare request size, first-request latency and hit ratio. Write down which you would use for a first-party app and why.

**Part 3 — Public versus private.** Cache the persisted-query GET endpoint at nginx with `public`.

Log in as two users, request the same query, and **show user B receiving user A's data.**

Fix it with `private` plus proper `Vary`, then write the test that fails if any authenticated query is ever marked `public`.

**Part 4 — Redis behind the loader.** Measure queries-per-request and p99 latency for a realistic query mix, cold and warm.

**Then the leak test:** build the cache key without the org ID. Confirm cross-tenant leakage. Fix it, and write the test.

**Part 5 — Field hints and the minimum rule.** A query mixing a 1-hour-cacheable field with a `max_age=0` field.

Confirm the computed header is `max-age=0`. Then split into two queries and confirm one becomes cacheable.

**Write the guidance you would give a frontend team** about structuring queries by cacheability.

**Part 6 — Invalidation, two ways.** TTL-based and entity-tag-based.

Measure for each: staleness window, invalidation latency, Redis operations per mutation, and implementation complexity.

Then the correctness test: mutate a document and assert every dependent cached query is invalidated. **Find the case entity tagging misses** — usually an aggregate like `organisationStats` that touched the entity without naming it.

**Part 7 — A normalised client cache.** Store by `__typename:id`, replace references, update views on mutation.

Then the list-membership problem: create a document via mutation and **show that existing list queries do not include it.** Implement both fixes and compare.

**Done when:**
- Your REST-versus-GraphQL hit-ratio chart shows the real gap
- Persisted queries with GET measurably restore CDN caching
- You caused and fixed a cross-user cache leak at both the CDN and Redis layers
- You have written the query-splitting guidance for cacheability
- Your invalidation comparison includes a case entity tagging misses
- Your normalised cache updates views on mutation, and you know its list limitation
