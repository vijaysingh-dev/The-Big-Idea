# Presence, Fanout and Backpressure

#backend #realtime #backpressure

> **In one line:** In a fanout system the slowest client sets the pace unless you deliberately stop it, and the fix is a bounded queue per client plus an explicit policy for what to discard.

---

## The Idea

You have 1,000 clients subscribed to a topic. An event arrives. You send it to all of them.

```python
async def broadcast(topic: str, event: Event):
    for client in subscribers[topic]:
        await client.send(event)          # ← the bug
```

One client is on a train with a bad connection. Its TCP send buffer is full. `await client.send()` blocks until it drains.

**Every other client waits.** Your 999 healthy clients now receive events at the pace of the worst one.

⚠️ **This is the single most common realtime scaling bug**, and it does not appear in testing because test clients read instantly.

---

## The Fix: A Queue Per Client

```python
class ClientConnection:
    def __init__(self, maxsize: int = 100, policy: str = "drop_oldest"):
        self.queue: asyncio.Queue[Event] = asyncio.Queue(maxsize=maxsize)
        self.policy = policy
        self.dropped = 0

    def publish(self, event: Event) -> None:
        """Never blocks. Never awaits. Called from the fanout loop."""
        try:
            self.queue.put_nowait(event)
        except asyncio.QueueFull:
            self.dropped += 1
            client_drops_total.labels(policy=self.policy).inc()

            if self.policy == "drop_oldest":
                try:
                    self.queue.get_nowait()
                    self.queue.put_nowait(event)
                except (asyncio.QueueEmpty, asyncio.QueueFull):
                    pass
            elif self.policy == "disconnect":
                self.close(reason="slow_consumer")

    async def writer(self):
        """One task per client. This is the only thing that awaits the socket."""
        while True:
            event = await self.queue.get()
            await self.transport.send(event)
```

The structure is the point:

```
fanout loop  ──put_nowait──►  [ bounded queue ]  ──►  writer task  ──await──►  socket
   never blocks                                        blocks here, alone
```

💡 **The fanout loop must never await on a client.** It hands off to a queue and moves on. Each client's writer task absorbs its own slowness. This separation is what makes one slow client harmless — and it is a pattern worth recognising generally: **put the blocking operation behind a bounded buffer owned by the slow party.**

---

## Choosing the Policy

There is no universally right answer. It depends entirely on what the data means.

| Policy | Behaviour | Right for |
|---|---|---|
| **Drop oldest** | Discard the stalest, keep the newest | Progress bars, cursor positions, live prices, presence |
| **Drop newest** | Reject the incoming event | Rarely correct. Only when order matters more than recency |
| **Disconnect** | Close the connection, force resync | Chat, LLM tokens, anything where a gap corrupts meaning |
| **Coalesce** | Replace the previous event of the same type | Typing indicators, cursor positions, status updates |
| **Block** | Slow the producer | **Never in a fanout.** Only in a 1:1 pipeline |

### Coalescing is the underrated one

```python
class CoalescingQueue:
    """Only the latest event of each key survives."""
    def __init__(self):
        self._latest: dict[str, Event] = {}
        self._wakeup = asyncio.Event()

    def publish(self, event: Event) -> None:
        self._latest[event.coalesce_key] = event      # overwrite
        self._wakeup.set()

    async def drain(self) -> list[Event]:
        await self._wakeup.wait()
        self._wakeup.clear()
        events = list(self._latest.values())
        self._latest.clear()
        return events
```

For cursor positions, a client that is 200 events behind does not need 200 cursor updates — it needs the latest one. Coalescing turns unbounded backlog into bounded state.

💡 **Coalescing by key is how you make a many-to-many realtime feature viable.** Ten users moving cursors 30 times a second produces 300 events per second; coalescing on a 50ms tick reduces it to 20 per second per recipient with no perceptible difference. **Reducing the event rate is almost always better than scaling the delivery.**

### Applied to Conduit

| Event | Policy | Why |
|---|---|---|
| Ingestion progress | Coalesce on `run_id` | Only the latest percentage matters |
| Document indexed | Drop oldest, warn at threshold | A gap is recoverable via replay |
| Annotation created | **Disconnect and resync** | Missing an annotation is a correctness bug |
| Cursor position | Coalesce on `user_id` | Only the current position matters |
| Presence change | Coalesce on `user_id` | Latest state wins |
| LLM answer tokens | Disconnect | A gap makes the text nonsense |

⚠️ **Notice that three of six coalesce.** Most realtime data is *state* rather than *events*, and state can be replaced rather than queued. Recognising which of your data is state is the highest-leverage design decision here.

## Detecting a Slow Client

Queue depth alone is not enough — a burst fills a queue temporarily and that is fine.

```python
class SlowClientDetector:
    def __init__(self, window: float = 30.0, drop_threshold: int = 50):
        self.drops = deque()          # timestamps
        self.window = window
        self.threshold = drop_threshold

    def record_drop(self) -> bool:
        now = time.monotonic()
        self.drops.append(now)
        while self.drops and self.drops[0] < now - self.window:
            self.drops.popleft()
        return len(self.drops) > self.threshold
```

**Sustained drops over a window** is the signal, not instantaneous depth. A client that drops 200 events in one burst and then keeps up is fine. A client dropping 2 events per second for a minute is not going to recover.

Other useful signals:

| Signal | Meaning |
|---|---|
| Queue depth consistently above 50% | Not keeping up |
| Time since last successful write | Socket buffer full |
| Write duration p99 | The transport is slow |
| `ss -tm` send queue for that socket | Kernel-level confirmation |

## Telling the Client It Lost Data

Dropping events silently is worse than disconnecting.

```python
if dropped_since_last_send:
    await client.send(Event(
        type="events_dropped",
        payload={"count": dropped_since_last_send, "resync_recommended": True},
    ))
```

💡 **A client that knows it missed data can recover. A client that does not know shows the user stale information indefinitely** — and nothing looks broken, which makes it the worst class of bug.

For anything where gaps matter, do not drop at all. Disconnect with a reason:

```python
await client.close(code=1013, reason="slow_consumer_resync_required")
```

The client reconnects, resyncs from its cursor, and is correct again. **A brief disconnect is a much better user experience than silently wrong data.**

## Presence at Scale

Presence looks like a small feature and generates a surprising amount of traffic.

```
100 users in a document
Each join/leave → 99 notifications
Users churning at 1/second → 99 events/second
```

Worse with typing indicators or cursors, where each user generates continuous events.

### Three techniques

**1. Coalesce on a tick.**

```python
async def presence_broadcaster(topic: str, interval: float = 1.0):
    while True:
        await asyncio.sleep(interval)
        if not dirty[topic]:
            continue
        snapshot = await get_presence(topic)
        broadcast(topic, Event(type="presence", payload=snapshot))
        dirty[topic] = False
```

Instead of N events for N changes, send one snapshot per second. **Latency goes from instant to 1 second, which nobody notices for presence.**

**2. Send deltas, not snapshots.**

```python
{"joined": ["user-7"], "left": ["user-3"]}
```

For a 500-person document, a full snapshot is 20KB and a delta is 40 bytes.

⚠️ Deltas require the client to have the correct base state. Send a full snapshot on connect and after any gap, deltas thereafter — the same replay-versus-resync problem as everywhere else in section 04.

**3. Cap what you send.**

```python
if len(online) > 50:
    payload = {"count": len(online), "sample": online[:50]}
```

A UI showing "247 online" does not need 247 user objects. Send the count and a sample.

## In Production

### The metrics

```python
fanout_recipients.observe(len(subscribers))
fanout_duration_seconds.observe(elapsed)
client_queue_depth.observe(depth)
client_drops_total.labels(policy=..., reason=...).inc()
slow_client_disconnects_total.inc()
coalesced_events_total.inc()
```

💡 **`coalesced_events_total` divided by `events_published_total` is your compression ratio.** If coalescing is discarding 90% of events, that is 90% of delivery work you are not doing. It is also a signal that your producers are emitting more than necessary — often the better fix.

**`fanout_duration_seconds` p99 tells you about hot topics.** If one topic takes 200ms to fan out while p50 is 2ms, you have a topic with far more subscribers than the rest, and it will show up as periodic latency spikes for everyone sharing that event loop.

### The event loop consideration

```python
def broadcast(topic: str, event: Event):
    for client in subscribers[topic]:      # 50,000 iterations
        client.publish(event)               # sync, but 50,000 of them
```

Even without awaiting, iterating 50,000 clients takes real time — and it is a single synchronous block in your event loop ([[01.6 - The Blocking Call Problem]]).

```python
async def broadcast(topic: str, event: Event):
    clients = subscribers[topic]
    for i, client in enumerate(clients):
        client.publish(event)
        if i % 1000 == 0:
            await asyncio.sleep(0)          # yield to the loop
```

⚠️ **A large fanout is a CPU-bound loop.** At 100,000 subscribers it will stall your event loop for tens of milliseconds every time, and that shows up as latency on every other request the process is handling.

The better structural fix is to shard large topics across pods so no single pod fans out to more than a few thousand.

### Memory

```
Per client: queue of 100 events × ~500 bytes = 50 KB worst case
10,000 clients × 50 KB = 500 MB
```

⚠️ **Queue size × event size × client count is a real memory budget** and it is worst-case-reachable during an incident, when everything is slow at once. Size your queues deliberately: 100 events at 500 bytes is generous for most realtime data, and 1,000 is almost never justified.

**Prefer coalescing over large queues.** A coalescing queue holds one event per key regardless of rate — bounded by key cardinality rather than by event volume.

### The checklist

1. Does the fanout loop ever `await` on a single client?
2. Is every client queue bounded?
3. Is the policy explicit and chosen per data type?
4. Does the client learn when it lost data?
5. Is there a slow-client detector with sustained-drop logic?
6. Does a large fanout yield to the event loop?
7. Is worst-case memory calculated?
8. Is presence coalesced rather than per-change?

⚠️ **Question 1 is the one that matters most**, and a single `await client.send()` in a loop anywhere in the codebase reintroduces the entire problem.

## Codebase

**Repo:** `centrifugal/centrifugo`, `redis/redis`, `django/channels_redis`

**Question to answer:** What does Centrifugo do when a client's write queue fills, and what is it configurable to? Then, in Redis: `client-output-buffer-limit` has different defaults for normal clients, replicas and pub/sub clients. **Why are they different?**

**Read, in order:**

1. `centrifugo/internal/client/client.go` — the per-client write queue and `client_queue_max_size`. **This is exactly the pattern in this note, as a production feature with an operator-facing knob**
2. `redis/src/networking.c` — `closeClientOnOutputBufferLimitReached` and `checkClientOutputBufferLimits`. Redis kills slow clients, and the code says why
3. `redis/redis.conf` — the `client-output-buffer-limit` documentation. **The answer to the second question is instructive:** pub/sub clients get a much tighter limit because a slow pub/sub subscriber can accumulate unbounded data with no flow control, whereas a normal client only receives responses to requests it made
4. `channels_redis/core.py` — `group_send` and the capacity handling. Note what happens when a channel is full, and consider whether that policy is right
5. `zulip/zerver/tornado/event_queue.py` — per-user queues with a maximum length and the resync signal

💡 The Redis insight in step three generalises: **a client that pulls (request/response) is naturally rate-limited by its own requests; a client that is pushed to has no such limit.** Any push-based system needs an explicit policy, and any request/response system mostly does not. That distinction explains why fanout is harder than serving HTTP.

**Part 1 — Prove the contamination.** Naive fanout, 100 clients, 5 of them reading at 1KB/sec, 100 events/second.

Measure event latency for the 95 fast clients. **It should track the slow ones almost exactly.**

Then chart fast-client p99 latency against the number of slow clients: 0, 1, 5, 20. The curve should be alarming.

**This chart is the reason for everything else in the drill.**

**Part 2 — Fix it with queues.** Bounded queue plus a writer task per client. Same test.

Fast-client latency should be completely flat regardless of how many slow clients exist. Chart both versions together.

**Part 3 — The policy matrix.** Five policies × three data types (progress percentage, chat messages, cursor positions).

For each combination measure: fast-client latency, slow-client data loss, memory, and **correctness** — does the slow client end up with a usable view of the world?

Fill in the 15-cell table. Then write your recommendation per data type with reasoning.

**The correctness column is what makes this exercise worth doing.** Latency numbers are easy; deciding that a chat client with a gap is *wrong* rather than merely degraded is the judgement being trained.

**Part 4 — Coalescing gains.** Cursor position updates at 30 per second per user, 10 users in a document.

Measure events delivered with no coalescing and with a 50ms coalescing tick. Report the compression ratio.

Then sweep the tick interval: 10ms, 50ms, 100ms, 500ms. Chart compression ratio against perceived smoothness — you will need to actually watch it to judge the second axis, which is the point.

**Part 5 — Stall the loop.** Fanout to 1,000, 10,000, 50,000 and 100,000 subscribers with no yielding.

Measure event loop lag during each fanout using the monitor from [[01.12 - Profiling and Debugging Async Services]].

Find the subscriber count at which fanout starts affecting unrelated requests. Then add periodic yielding and measure again — lag should flatten while total fanout time increases slightly.

**Record the tradeoff explicitly.**

**Part 6 — Presence three ways.** 500 users in one topic, churning at 5 joins/leaves per second.

Measure events per second, bytes per second, and client-side CPU for: per-change broadcast, 1-second ticked snapshots, and 1-second ticked deltas.

Then test correctness: disconnect a client, generate presence changes, reconnect. **Does the delta version end up with correct state?** Implement the full-snapshot-on-reconnect path and verify.

**Part 7 — Wire it into Conduit.** Annotation fanout with per-client queues, per-event-type policies, coalescing for cursors and presence, sustained-drop detection, and an explicit `events_dropped` signal.

Load test: 50 documents, 20 collaborators each, 10% of clients artificially slow, cursor movement at 30Hz.

**Requirement: no fast client is affected by any slow client, and every client either has complete annotation history or has been told to resync.** Prove it with the verifier checking event ID continuity.

**Done when:**
- Your contamination chart shows the damage and the fix side by side
- The 15-cell policy matrix includes a correctness verdict per cell
- You have a coalescing compression ratio and a chosen tick interval
- You know the subscriber count at which fanout stalls your loop
- The delta-based presence recovers correctly after a disconnect
- Conduit's annotation fanout isolates slow clients completely
