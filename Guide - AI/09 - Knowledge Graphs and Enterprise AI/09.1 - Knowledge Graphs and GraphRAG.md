# Knowledge Graphs and GraphRAG

## What Knowledge Graphs Are

A **knowledge graph** is a structured representation of entities and their relationships:

```
Entities:     Apple, Tim Cook, iPhone, Cupertino
Relationships: Tim_Cook → CEO_OF → Apple
               Apple → HEADQUARTERED_IN → Cupertino
               Apple → MANUFACTURES → iPhone
               iPhone → RELEASED_IN → 2007
```

Unlike a vector database (which stores text chunks as dense vectors), a knowledge graph explicitly models **named entities** and **typed relationships** between them.

---

## Why Knowledge Graphs for RAG?

Standard RAG fails on certain query types:

### Multi-Hop Reasoning

"Who is the CEO of the company that makes the iPhone?" → Requires knowing: iPhone → made by → Apple → CEO → Tim Cook → Standard chunk retrieval returns documents about iPhone separately from documents about Apple's leadership — the chain must be traversed

Knowledge graph: traverse `iPhone → MADE_BY → Apple → HAS_CEO → Tim Cook` directly.

### Relationship Queries

"Which products are made by companies headquartered in California?" → Standard RAG: retrieve chunks mentioning California + chunks mentioning products, then hope the LLM connects them → Knowledge graph: structured query returns exact answer

### Entity Disambiguation

"What did Cook say about the new product?" — is Cook the person (Tim Cook) or a role? The graph knows Tim Cook is an entity with type PERSON who is CEO_OF Apple.

---

## GraphRAG

**GraphRAG** (Microsoft, 2024) is the most prominent production approach combining knowledge graphs with RAG.

### Architecture

```
Documents (raw text)
    │
    ▼
[Entity & Relationship Extraction]  ← LLM extracts: (entity, relation, entity) triples
    │
    ▼
[Knowledge Graph Construction]      ← build graph in Neo4j or similar
    │
    ├── [Community Detection]        ← cluster related entities (Leiden algorithm)
    │
    └── [Hierarchical Summary Generation]  ← LLM writes summaries at community level

At Query Time:
    │
    ├── Global queries ("What are the main themes?")
    │   → Search community summaries (high-level)
    │
    └── Local queries ("What did X say about Y?")
        → Graph traversal from entities mentioned in query
```

### Two Retrieval Modes

**Global search** — for broad thematic questions:

```
Query: "What are the major security vulnerabilities discussed in these documents?"
Approach: Use community summaries (pre-computed, cover entire corpus at high level)
Result: Synthesized answer from multiple community summaries
```

**Local search** — for specific entity queries:

```
Query: "What has Alice said about the authentication system?"
Approach: Find entity "Alice" in graph → traverse edges to "authentication system" → retrieve relevant text chunks
Result: Targeted answer from entity-specific context
```

## Building a Simple Knowledge Graph Pipeline

### Step 1: Entity and Relationship Extraction

```python
EXTRACTION_PROMPT = """
Extract all entities and relationships from this text.

For each entity, identify: name, type (PERSON, ORGANIZATION, PRODUCT, CONCEPT, LOCATION, EVENT)
For each relationship, identify: (subject_entity, relationship_type, object_entity)

Text: {text}

Output JSON:
{
  "entities": [{"name": "...", "type": "..."}],
  "relationships": [{"subject": "...", "relation": "...", "object": "..."}]
}
"""

def extract_graph_elements(text, llm):
    result = llm.call(EXTRACTION_PROMPT.format(text=text))
    return json.loads(result)
```

### Step 2: Graph Construction

```python
from neo4j import GraphDatabase

class KnowledgeGraphStore:
    def add_document_extractions(self, entities, relationships, doc_id):
        with self.driver.session() as session:
            # Upsert entities
            for entity in entities:
                session.run("""
                    MERGE (e:Entity {name: $name})
                    SET e.type = $type
                """, name=entity["name"], type=entity["type"])
            
            # Upsert relationships
            for rel in relationships:
                session.run("""
                    MATCH (a:Entity {name: $subject})
                    MATCH (b:Entity {name: $object})
                    MERGE (a)-[r:RELATION {type: $relation}]->(b)
                    SET r.doc_id = $doc_id
                """, subject=rel["subject"], object=rel["object"],
                     relation=rel["relation"], doc_id=doc_id)
```

### Step 3: Graph-Enhanced Retrieval

```python
def graph_enhanced_retrieve(query, graph_store, vector_store, llm):
    # Extract entities from query
    query_entities = extract_entities(query, llm)
    
    # Graph traversal: get neighborhood of query entities
    graph_context = []
    for entity in query_entities:
        neighbors = graph_store.get_neighborhood(entity, max_hops=2)
        graph_context.extend(neighbors)
    
    # Standard vector retrieval
    vector_chunks = vector_store.search(query, top_k=5)
    
    # Combine
    return format_context(graph_context, vector_chunks)
```

## When Knowledge Graphs Help

|Query Type|Standard RAG|GraphRAG|
|---|---|---|
|"Summarize this document"|✅|Overkill|
|"What does X say about Y?"|✅|✅|
|"How is A related to B?"|❌|✅|
|"Multi-hop: A → B → C"|❌|✅|
|"List all entities of type X"|❌|✅|
|"Thematic overview of corpus"|Weak|✅ (community summaries)|

---

## When Knowledge Graphs Become Unnecessary Complexity

**Don't build a knowledge graph when**:

❌ Your queries are about document content, not entity relationships. Most enterprise search is "find me documents about X" — standard RAG handles this.

❌ Your corpus is small or changes frequently. Building and maintaining a graph is expensive. Standard RAG is fresher and simpler.

❌ Your entities don't have complex relationships. If documents are all self-contained (reports, tickets), graph traversal adds nothing.

❌ Your team doesn't have graph DB expertise. Neo4j, knowledge graph modeling, and graph query languages are non-trivial.

**Use knowledge graphs when**:

- Multi-hop reasoning is common (research, competitive intelligence)
- Entity relationships are the primary value (people networks, product relationships)
- Thematic synthesis across large corpora is needed
- Users ask "how is X related to Y" type questions

---

## GraphRAG Implementation Reality

Microsoft's GraphRAG implementation requires:

- LLM calls for every chunk (entity extraction) → 10–50× more LLM calls than standard RAG indexing
- Graph DB (Neo4j or similar)
- Community detection algorithm
- Summary generation at each community level

**Cost**: Indexing a 1,000-document corpus with GraphRAG costs ~$50–200 in LLM API calls. Standard RAG indexing costs ~$1–5 (just embedding calls).

**Recommendation**: Try standard RAG first. Add knowledge graph only when you've identified specific multi-hop query failures that the graph solves.
