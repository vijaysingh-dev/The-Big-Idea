# useReducer

`useReducer` moves state transition logic out of event handlers and into a single pure function.

```jsx
const [state, dispatch] = useReducer(reducer, initialState);

function reducer(state, action) {
  switch (action.type) {
    case "increment": return { ...state, count: state.count + 1 };
    case "reset":     return initialState;
    default:          throw new Error(`Unknown action: ${action.type}`);
  }
}

dispatch({ type: "increment" });
```

A reducer is `(state, action) => newState`. It must be **pure** — no fetching, no mutation, no side effects — because React may call it twice in Strict Mode and needs the result to be deterministic ([[16.5 - Rendering and Purity]]).

## When it beats useState

**Several state values change together.**

```jsx
// useState — four calls, easy to miss one
const handleSubmit = () => {
  setStatus("loading");
  setError(null);
  setRetries(r => r + 1);
  setLastAttempt(Date.now());
};

// useReducer — one dispatch, transition defined in one place
dispatch({ type: "submit_started" });
```

**Transitions depend on the current state in complex ways.** The reducer receives the current state, so no closure staleness and no chain of updater functions.

**The same transition is triggered from several places.** With `useState`, each handler duplicates the update; with a reducer, they all dispatch the same action.

**You need a state machine.** Modeling valid transitions explicitly prevents impossible states:

```jsx
function reducer(state, action) {
  switch (state.status) {
    case "idle":
      if (action.type === "fetch") return { status: "loading" };
      return state;
    case "loading":
      if (action.type === "success") return { status: "success", data: action.data };
      if (action.type === "error")   return { status: "error", error: action.error };
      return state;
    case "success":
      if (action.type === "refetch") return { status: "loading", data: state.data };
      return state;
  }
}
```

Returning `state` unchanged for invalid transitions makes them no-ops rather than corrupting state. This is the whole value of the pattern — a late `success` action after the user cancelled cannot revive a dead request.

**Testing matters.** A reducer is a pure function testable without React:

```js
expect(reducer({ status: "loading" }, { type: "success", data: [1] }))
  .toEqual({ status: "success", data: [1] });
```

## When useState is better

- One or two independent values
- Simple set-and-forget updates
- A boolean toggle, an input value, an open/closed flag

`useReducer` adds indirection: reading a handler now requires finding the matching case. For simple state that cost is not repaid.

## dispatch is stable

```jsx
const [state, dispatch] = useReducer(reducer, initial);

useEffect(() => {
  socket.on("message", msg => dispatch({ type: "received", msg }));
}, []);   // dispatch is guaranteed stable — no dependency needed
```

React guarantees `dispatch` has a stable identity for the component's lifetime. This makes it safe in dependency arrays, safe to pass to memoized children without `useCallback`, and ideal for the context split described in [[17.9 - useContext]]:

```jsx
<StateContext value={state}>
  <DispatchContext value={dispatch}>{children}</DispatchContext>
</StateContext>
```

Components that only dispatch never re-render when state changes — a substantial win in forms and toolbars.

## Lazy initialization

```jsx
function init(initialCount) {
  return { count: initialCount, history: [] };
}

const [state, dispatch] = useReducer(reducer, initialCount, init);
```

The third argument is an initializer called with the second. It runs once, avoiding expensive setup on every render, and it lets a `reset` action reuse the same function:

```jsx
case "reset": return init(action.payload);
```

## Action design

Model actions as **events that happened**, not as **setters**:

```jsx
// Setter-style — the reducer is just useState with extra steps
dispatch({ type: "set_status", value: "loading" });
dispatch({ type: "set_error", value: null });

// Event-style — one action describes what occurred
dispatch({ type: "submit_started" });
```

Event-style actions keep the transition logic in the reducer where it can be tested, make the action log readable in a debugger, and mean adding a field to the state does not change any call site.

Include the payload the reducer needs and nothing more:

```jsx
dispatch({ type: "item_added", item });
dispatch({ type: "quantity_changed", id, quantity });
```

## Reducers must not have side effects

```jsx
// Wrong
case "submit":
  fetch("/api/save", { method: "POST" });   // side effect in a reducer
  return { ...state, status: "loading" };
```

Side effects belong in the handler that dispatches, or in an effect that reacts to the resulting state. Reducers only compute the next state.

The reducer must also not mutate:

```jsx
case "add": state.items.push(item); return state;              // wrong — same reference
case "add": return { ...state, items: [...state.items, item] }; // correct
```

Immer removes the ceremony for deep updates ([[20.6 - Immer and Immutable Updates]]), and Redux Toolkit builds it in.

## Relationship to Redux

The API is deliberately identical — Redux's `(state, action) => state` is the same shape. The differences:

| | `useReducer` | Redux |
| --- | --- | --- |
| Scope | one component subtree | application-wide |
| Middleware | none | thunks, sagas, listeners |
| DevTools | none by default | time-travel debugging |
| Selectors | none | memoized, subscription-granular |
| Async | manual | built-in patterns |

`useReducer` plus context covers a surprising amount of what people reach for Redux to do, without the setup ([[20.3 - Redux Core Concepts]]). Redux earns its place when you need middleware, DevTools, or cross-cutting subscriptions.

## useActionState

React 19 adds a related hook for form submissions:

```jsx
const [state, formAction, isPending] = useActionState(
  async (prevState, formData) => {
    const result = await submit(formData);
    return result.error ? { error: result.error } : { success: true };
  },
  { }
);

<form action={formAction}>
```

Same reducer shape, but the function may be async and React manages the pending state. It is the idiomatic form-handling primitive in React 19 ([[21.2 - Validation Strategies]]).

## How senior engineers actually use this

**They switch to a reducer when a component has three or more interdependent state values**, or when the same transition fires from several handlers.

**They design actions as events**, which keeps the reducer as the single description of how state can change.

**They exploit the stable `dispatch`** to avoid `useCallback` and to split context.

**They model status as a machine** and return `state` unchanged for invalid transitions, which eliminates race-condition bugs structurally.

**They test reducers directly**, since that is where the logic lives.

## Common pitfalls

- Side effects inside the reducer.
- Mutating state instead of returning a new object.
- Setter-style actions that reduce the reducer to a verbose `useState`.
- No `default` case, so unknown actions silently return `undefined`.
- Reaching for a reducer for a single boolean.
- Forgetting that the initializer is the third argument, not the second.

## Interview angle

"When would you use useReducer over useState" expects: multiple interdependent values, complex transitions, the same transition from several places, and testability. The stronger material is the state-machine framing — invalid transitions become no-ops, which prevents a class of race conditions — and the stable `dispatch` enabling the state/dispatch context split. Noting that `useReducer` plus context covers many Redux use cases positions it correctly in the ecosystem.
