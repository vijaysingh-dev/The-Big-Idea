# How Systems Fail

#backend #reliability #operations

> **In one line:** Systems rarely fail because one thing broke — they fail because one thing degraded, a mechanism intended to help amplified it, and the amplification found a resource everything shared.

---

## The Idea

```
❌ The naive model:  component fails → system fails
✅ The real model:   component degrades → a coping mechanism amplifies it
                     → a shared resource saturates → everything fails
```

💡 **The interesting failures are not crashes.** A process that dies is replaced in seconds. A process that gets slow holds resources, accumulates work, and drags down everything connected to it.

⚠️ **Slow is worse than dead**, and almost every design in section 11 exists because of that sentence.

---

## Partial Failure

```
Monolith:      the process is up, or it is not
Distributed:   any component can be up, down, slow, or lying
```

| State | |
|---|---|
| **Up** | Responding correctly |
| **Down** | Not responding. **The easy case** |
| **Slow** | Responding, eventually. **The hard case** |
| **Lying** | Responding with wrong data |
| **Partitioned** | Up, and unreachable from here |

⚠️ **You often cannot tell which.** A request that has not returned might be slow, might be lost, might have succeeded with the response lost — and the caller has no way to know ([[03.4 - Idempotency and Safe Retries]]).

💡 **This ambiguity is the fundamental problem of distributed systems**, and it is why idempotency is not a nicety.

### The gray failure

```
Health check:  200 OK, 2ms
Real traffic:  p99 of 8 seconds
```

⚠️ **A component can be healthy by every metric you check and unable to do useful work.** The health check hits a cached path; real requests hit the degraded one.

💡 **Health checks should exercise a real path**, not just prove the process is running ([[10.10 - Deployment Strategies]]) — and they must not be so heavy that checking becomes the load problem.

## Cascading Failure

The shape of most large outages.

```
1. Service C slows down            (a bad query, a GC pause, a noisy neighbour)
2. Service B's calls to C queue    (no timeout, or a generous one)
3. B's connection pool exhausts    (every worker waiting on C)
4. B stops responding to A         (it has no capacity left)
5. A's pool exhausts
6. The gateway stops responding
7. Everything is down
```

⚠️ **The originating failure was one slow service.** Every step after that was a system designed to cope, coping badly.

### The amplifiers

| Amplifier | Effect |
|---|---|
| **No timeouts** | A caller waits indefinitely, holding a worker ([[03.11 - Timeouts and Deadlines Across Hops]]) |
| **Retries** | 3× the load on an already-struggling service ([[03.4 - Idempotency and Safe Retries]]) |
| **Nested retries** | 3 × 3 × 3 = 27× ([[08.6 - Retries Backoff and Dead Letters]]) |
| **Unbounded queues** | Latency grows without bound instead of failing |
| **Shared connection pools** | One slow dependency starves all others |
| **Health checks that check dependencies** | Cascading restarts ([[10.10 - Deployment Strategies]]) |
| **Autoscaling on latency** | Scales up, adds cold instances, makes it worse |

💡 **Every one of those is a mechanism intended to improve reliability.** Retries help with transient failures and amplify sustained ones. Autoscaling helps with load and makes a dependency problem worse.

⚠️ **Reliability mechanisms have a regime where they help and a regime where they hurt, and the boundary is usually the point at which you need them most.**

### Retry storms

```
Normal:      1,000 rps
C degrades:  clients retry 3× → 3,000 rps at a service that cannot handle 1,000
```

💡 **A retry budget bounds this** ([[08.6 - Retries Backoff and Dead Letters]]):

```python
if retry_rate_for(service) > 0.2 * request_rate_for(service):
    raise NoRetryBudget()
```

**Retries capped at 20% of traffic means a total dependency failure produces 1.2× load, not 3×.**

## Metastable Failure

The failure mode that does not fix itself.

```
1. A load spike causes queues to grow
2. Growing queues cause timeouts
3. Timeouts cause retries
4. Retries add load
5. The original spike ends
6. The system stays down          ← the retries are now the load
```

⚠️ **The trigger is gone and the system does not recover**, because the sustaining feedback loop is self-generated.

💡 **This is why "it recovered when we restarted everything" is a common incident resolution** — restarting breaks the loop by dropping all the in-flight retries and queued work.

**Prevention:**

| Mechanism | |
|---|---|
| **Load shedding** | Reject early, before the queue builds ([[11.4 - Backpressure and Load Shedding]]) |
| **Bounded queues** | Fail fast instead of accumulating |
| **Circuit breakers** | Stop retrying a service that is down ([[11.3 - Circuit Breakers and Bulkheads]]) |
| **Retry budgets** | Cap total amplification |

⚠️ **Recovery from a metastable state usually requires reducing load below the normal level**, not just below the spike. **Know how to shed load deliberately**, because you will need to.

## Correlated Failure

```
"We have three replicas, so we can survive one failure."
```

⚠️ **Only if the failures are independent, and they usually are not.**

| Correlation | |
|---|---|
| Same node | One node failure takes all three |
| Same availability zone | One zone outage |
| **Same bad deploy** | Rolled out to all three |
| **Same input** | A poison message kills every replica ([[08.9 - Celery in Production]]) |
| Same certificate expiry | Every service, at the same second |
| Same dependency | All three call the same database |
| **Same clock** | A leap second, or an NTP step |

💡 **Independence is an assumption that must be engineered**, not one you get by adding replicas.

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
```

⚠️ **The bad-deploy correlation is the one your architecture cannot fix** — only canaries and progressive rollout can ([[10.10 - Deployment Strategies]]).

**And certificate expiry is worth a specific alert**, because it takes down everything simultaneously with no warning and no gradual degradation.

## Common Failure Sources

### Resource exhaustion

| Resource | Symptom |
|---|---|
| **Connection pool** | Requests queue for a connection ([[01.10 - Connection Pools and Limits]]) |
| Memory | OOM kill, or GC thrashing |
| File descriptors | `Too many open files`. Often a leaked connection |
| Disk | **Writes fail. Postgres stops** ([[09.4 - Change Data Capture]]) |
| Thread or worker pool | New requests wait |
| **Database connections** | `too many clients` ([[06.9 - Connection Pooling and PgBouncer]]) |
| Ephemeral ports | Under very high connection churn |

💡 **Every resource has a limit, and the limits you have not set are set by the operating system at values you did not choose.**

### The queue that grew

```
Producers: 1,000/s
Consumers:   800/s
→ 200/s accumulating, indefinitely
```

⚠️ **The system appears healthy — no errors, no crashes — while latency grows without bound** ([[08.2 - Queue Semantics]]).

💡 **Queue *age* is the metric, not depth** ([[08.1 - Why Background Work Exists]]). Depth tells you volume; age tells you what a user experiences.

### The dependency you forgot

```
DNS
NTP
Certificate authority
Container registry
Secret manager
Identity provider
```

⚠️ **These are dependencies with no dashboard and no runbook**, and each has taken down large systems.

💡 **A container registry outage means no pod can start** — existing pods run, and any restart, scale-up or deploy fails. **The system appears fine until something needs to restart.**

**Cache images locally, and know which of these you cannot survive.**

## In Production

### Designing for failure

For every dependency:

```
□  What happens if it is slow?          ← the important one
□  What happens if it is down?
□  What happens if it returns wrong data?
□  Is it required or optional?
□  What is the degradation path?
□  What is the timeout, and where does it come from?
□  Is there a circuit breaker?
□  Is the failure isolated, or does it spread?
```

⚠️ **"What happens if it is slow" is the question that catches cascading failure**, and it is the one people skip because "down" seems like the worse case.

### The blast radius question

```
"If this component fails completely, what stops working?"
```

| Blast radius | |
|---|---|
| One feature | Good |
| One tenant | Acceptable ([[06.16 - Multi Tenant Data Models]]) |
| One region | Acceptable |
| **Everything** | ⚠️ A single point of failure |

💡 **Draw the blast radius for every component.** The ones where the answer is "everything" — the gateway, the database, the identity provider — are where reliability investment belongs.

### Failure injection

⚠️ **A degradation path that has never been exercised does not work.**

```python
async def test_degrades_when_search_slow(toxiproxy):
    await toxiproxy.add_latency("search", 5000)
    r = await api.get_document("doc_42")
    assert r.status_code == 200
    assert r.json()["related"] == []
```

💡 **Test slow, not just down** ([[10.9 - Testing Microservices]]). Most code handles a connection refused and hangs on a slow response.

**Toxiproxy in the test suite makes this routine** ([[00.4 - Setting Up Your Lab]]).

### The metrics that predict failure

| Leading indicator | Precedes |
|---|---|
| **Retry rate** | Error rate ([[08.6 - Retries Backoff and Dead Letters]]) |
| **Queue age** | User-visible latency |
| **Connection pool wait time** | Request timeouts |
| **p99 latency** | p50 latency |
| Saturation of any resource | Everything |

💡 **Alert on saturation and on leading indicators, not only on errors.** By the time the error rate rises, users are already affected.

⚠️ **The USE method — Utilisation, Saturation, Errors — applied to every resource is the systematic version of this.** For each resource: how busy is it, how much work is queued, and how many operations failed.

### The failure taxonomy for Conduit

| Component | Slow | Down | Blast radius |
|---|---|---|---|
| Postgres | Everything queues | **Everything fails** | **Total** |
| Redis (cache) | Slight latency | **20× database load** ([[07.1 - Cache Layers Across One Request]]) | Total, via the database |
| Redis (broker) | Tasks delayed | No background work | Ingestion |
| Kafka | Events delayed | Search index stale | Search freshness |
| Search index | Search slow | **Search degrades to Postgres FTS** | Search quality |
| Embedding API | Ingestion slow | Ingestion stalls, queue grows | New documents |
| Object storage | Uploads slow | No uploads or downloads | Documents |
| Identity provider | Auth slow | **No logins.** Existing sessions work | New sessions |

💡 **Two total-blast-radius components**, and the Redis-cache row is the non-obvious one: **losing the cache does not fail directly, it fails by overloading the database.**

⚠️ **That is a cascading failure waiting to happen, and the mitigation is load shedding on database pressure** ([[11.4 - Backpressure and Load Shedding]]), not a bigger Redis.

**Test it: flush Redis under production load and see whether you survive.**

## Codebase

**Repo:** Public postmortems, `Netflix/chaosmonkey`, `Shopify/toxiproxy`

**Question to answer:** Read three public postmortems and identify, for each: the trigger, the amplifier, and the shared resource that saturated. Then: how does Toxiproxy simulate the "slow" failure mode specifically?

**Read, in order:**

1. **The GitHub 2018 October incident report** — a 43-second network partition caused 24 hours of degradation. **The trigger was tiny; the recovery was the hard part**
2. **The Cloudflare 2019 July outage** — one regex caused global CPU exhaustion. **A single input, correlated across every machine**
3. **The AWS Kinesis 2020 November outage** — a thread limit on the front-end fleet. **A resource limit nobody knew was near**
4. `Shopify/toxiproxy` — `toxics/latency.go` and `bandwidth.go`. **How "slow" is simulated**, which is the failure mode you most need to test
5. `Netflix/chaosmonkey` — the termination logic, and the constraints that make it safe to run in production

💡 The three postmortems share a structure: **a small trigger, an amplifying mechanism, and a shared resource.** Reading them with that lens rather than as narratives is what makes them useful — and after three, you start seeing the same shape in your own systems.

**Size:** 1–2 sessions.

**Part 1 — Cause the cascade.** Four layers with Toxiproxy between each. Add 5 seconds of latency to C.

**Chart, for each layer:** connection pool utilisation, in-flight requests, p99 latency, and error rate, over time.

**Watch it propagate upward.** Measure time from C degrading to the gateway failing.

**This chart is the whole note in one image.** Keep it.

**Part 2 — Remove one amplifier at a time.** Re-run the cascade with each fix applied individually:

| Fix | Expected |
|---|---|
| Timeouts on every call | The cascade slows |
| No retries | Load on C stays at 1× |
| Bounded queues | Fail fast instead of accumulating |
| Per-dependency pools | Only C-dependent requests fail |
| Circuit breaker on C | C-dependent requests fail immediately |

**Measure how far the failure propagates in each case**, and rank the fixes by effectiveness.

**Then apply all five and confirm the failure is contained to C's callers.**

**Part 3 — Retry amplification.** Three layers each retrying three times.

Instrument C to count requests. **Confirm 27 per logical call.**

Chart load at C against failure rate for: no retries, one layer retrying, all three retrying, and a retry budget.

**The all-three curve should grow explosively; the budget curve should stay bounded.**

**Part 4 — Metastable failure.** Induce a 3× load spike for 60 seconds, with retries and unbounded queues, then remove it.

**Confirm the system stays down after the spike ends.**

Then measure the recovery threshold: reduce load progressively and find the level at which it recovers. **It should be well below normal.**

Then add load shedding and repeat. **Confirm it recovers immediately when the spike ends.**

**Part 5 — Correlated failures.** Three replicas.

- **Same node:** kill the node. Confirm all three die
- **Poison input:** a request that OOMs the process, sent to all three. **Confirm the whole fleet crash-loops**
- **Certificate expiry:** set a certificate to expire during the test. **Confirm every service fails simultaneously**

Then apply topology spread constraints, an input guard and a certificate expiry alert.

**Part 6 — Gray failure.** A service whose health check hits a cached path while real requests are slow.

**Confirm it stays in the load balancer while failing every real request.**

Then make the health check exercise a real path and confirm it is removed. **Measure the health check's own cost**, and find the balance between accurate and cheap.

**Part 7 — Conduit's taxonomy.** Fill in the eight-row table with your own measurements.

**For each: induce slow, induce down, and record what actually happens** rather than what you expect.

**The Redis-cache row is the one to test carefully** — flush it under load and measure whether the database survives.

**Then write the mitigation for every row where the blast radius is larger than it should be.**

**Done when:**
- Your cascade chart shows failure propagating through four layers
- You ranked five fixes by how far they contain the failure
- Retry amplification is measured at 27, and bounded by a budget
- You produced a metastable failure and found its recovery threshold
- Three correlated failure modes are reproduced and mitigated
- A gray failure kept a broken pod in the load balancer
- Every row of Conduit's taxonomy is measured, not assumed
