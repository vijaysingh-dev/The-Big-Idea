## Requirements Clarification

**Functional:**
- Accept payment from multiple sources: cards, UPI, wallets, net banking
- Support charge, refund, partial refund
- Idempotent retry-safe API
- Webhook callbacks to merchants on payment status change
- Dashboard: payment history, reconciliation reports

**Non-functional:**
- Strong consistency: no double charges, no lost payments
- 99.99% availability for charge endpoint (revenue-critical)
- Charge latency: < 2s p99
- Audit log: every event permanently recorded, immutable
- Compliance: PCI-DSS Level 1 (card data handling)

**Out of scope:** Fraud detection ML model, card tokenization details, currency conversion

```
Transactions/day: 10M
Peak TPS: 10M / 86,400 × 3 (peak factor) = ~350 TPS
Refunds: 2% of transactions = 200K/day

Storage per transaction: ~500 bytes
  10M × 500 bytes = 5 GB/day
  7-year retention (compliance): ~12.8 TB total

Webhook delivery: 10M callbacks/day = ~115/s
```

**Key challenges:** Not throughput — correctness. Ensuring every rupee is charged exactly once and never lost.

## Core Design Principles for Payments

### 1. Idempotency Is Non-Negotiable

Network failures cause retries. Without idempotency, retries mean double charges.

```
Every charge request must include an idempotency_key:
  POST /v1/charges
  Idempotency-Key: order-8821-attempt-1

Server: if this key was seen before → return stored result (don't re-execute)
```

### 2. The Ledger Never Lies

Use a double-entry ledger. Every money movement is two entries that sum to zero.

```
Charge of ₹500 from customer:
  DEBIT  customer_balance  ₹500   (customer owes)
  CREDIT merchant_balance  ₹480   (merchant receives)
  CREDIT platform_fees     ₹20    (platform takes fee)

Sum = 0. Money is conserved.
```

### 3. Events Are Immutable

Payment events are never updated or deleted. State is derived from the event log.

```
Events:
  CHARGE_INITIATED  {amount: 500, currency: INR, card: ****1234}
  CHARGE_AUTHORIZED {auth_code: XYZ, processor: Visa}
  CHARGE_CAPTURED   {captured_at: ...}

Never: UPDATE payments SET status = 'failed' WHERE id = X
Instead: INSERT INTO payment_events (payment_id, type, ...) VALUES (...)
```

## Payment Flow: Charge

```
1. Merchant: POST /v1/charges
   {
     amount: 50000,          # ₹500.00 in paise
     currency: "INR",
     payment_method: "card",
     card_token: "tok_xyz",  # tokenized card (never raw PAN)
     idempotency_key: "order-8821-attempt-1",
     metadata: { order_id: "8821" }
   }

2. Payment Service:
   a. Check idempotency key in Redis
      → If found: return cached response (do nothing)
      → If not found: continue

   b. Validate input (amount > 0, valid currency, etc.)

   c. Pre-fraud check (velocity limits, card BIN checks)

   d. Acquire payment_id (Snowflake ID)

   e. Write to DB in a single transaction:
      INSERT INTO payments (id, status='INITIATING', ...)
      INSERT INTO payment_events (payment_id, type='CHARGE_INITIATED', ...)
      INSERT INTO idempotency_store (key, payment_id, expires_at)

   f. Call payment processor (Visa/Mastercard network, UPI):
      result = processor.authorize(card_token, amount)

   g. Write result to DB:
      UPDATE payments SET status = result.status
      INSERT INTO payment_events (type='CHARGE_AUTHORIZED' or 'CHARGE_FAILED')

   h. If authorized: call processor.capture() → insert CHARGE_CAPTURED event

   i. Cache result in Redis against idempotency key (TTL: 24h)

   j. Return response to merchant

3. Async: emit PaymentCompleted event to Kafka → webhooks, analytics
```

## Idempotency Implementation

```python
IDEMPOTENCY_TTL = 86400  # 24 hours

def handle_charge(request):
    idempotency_key = request.headers.get("Idempotency-Key")

    if idempotency_key:
        # Check cache
        cached = redis.get(f"idempotency:{idempotency_key}")
        if cached:
            return json.loads(cached)   # replay stored response

    # Process payment
    response = process_charge(request.body)

    # Cache result
    if idempotency_key:
        redis.setex(
            f"idempotency:{idempotency_key}",
            IDEMPOTENCY_TTL,
            json.dumps(response)
        )

    return response
```

**What happens if we crash between processing and caching the idempotency key?**  
Merchant retries → we process again. That's why we also write to `idempotency_store` in the DB within the payment transaction. On retry, DB check catches it even if Redis is cold.

## Ledger Design

```sql
-- Accounts: every entity that can hold a balance
CREATE TABLE accounts (
    id          UUID PRIMARY KEY,
    owner_id    BIGINT NOT NULL,  -- merchant_id, customer_id, platform_id
    owner_type  VARCHAR(20),      -- merchant, customer, platform
    currency    CHAR(3),
    balance     BIGINT NOT NULL DEFAULT 0  -- in smallest unit (paise)
);

-- Ledger entries: immutable double-entry bookkeeping
CREATE TABLE ledger_entries (
    id             UUID PRIMARY KEY,
    account_id     UUID NOT NULL REFERENCES accounts(id),
    amount         BIGINT NOT NULL,  -- positive = credit, negative = debit
    entry_type     VARCHAR(30),      -- CHARGE, REFUND, FEE, PAYOUT
    payment_id     UUID,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    description    TEXT
);
-- Sum of ledger_entries.amount per account = current balance
-- Never update or delete entries
```

**Balance query:**
```sql
SELECT SUM(amount) FROM ledger_entries WHERE account_id = 'merchant-123';
```

For performance: maintain a running balance in `accounts.balance`, updated in the same transaction as new ledger entries. Use the ledger for audit; use `accounts.balance` for fast reads.

## Reconciliation

Daily reconciliation verifies our records match what the payment processors say.

```
1. Download settlement file from Visa/Mastercard (end of day)
2. For each transaction in file:
   a. Find matching record in our DB by processor reference ID
   b. Compare amounts, statuses
   c. Flag discrepancies

Discrepancy types:
  - Transaction in processor file, not in our DB → missed capture
  - Transaction in our DB as succeeded, but processor marked failed → refund needed
  - Amount mismatch → data corruption, requires investigation
```

This runs as a nightly batch job. Any discrepancies trigger an alert to the payments operations team.

## Compliance: PCI-DSS

PCI-DSS (Payment Card Industry Data Security Standard) governs how card data is handled.

**Key requirements affecting architecture:**
- **Never store raw PAN (card number)** — only tokenized form. Use a PCI-compliant tokenization vault (Stripe, Braintree handle this)
- **Encrypt cardholder data at rest** — AES-256 for anything that touches card data
- **Network segmentation** — payment systems in a separate VPC, no internet access, whitelist-only egress
- **Audit logs** — every access to card data logged, retained 1 year
- **Penetration testing** — annually required

**Design implication:** The card number never touches your servers in plaintext. The browser tokenizes it directly with the card vault (client-side tokenization). Your server only ever sees a token (`tok_xyz`).

## Failure Handling

| Failure | Effect | Mitigation |
|---|---|---|
| Processor timeout during capture | Money authorized but not captured | Async job retries capture; idempotent via auth_code |
| DB down during charge | Payment not recorded | Fail to client; merchant retries with same idempotency key |
| Redis down (idempotency cache) | Idempotency check falls through to DB | DB-backed idempotency_store as fallback |
| Duplicate payment (race condition) | Two charges for same order | Unique constraint on idempotency_key in DB |
| Webhook delivery fails | Merchant doesn't know about payment | Retry queue: exponential backoff, 72-hour window, DLQ |
| Ledger balance mismatch | Inconsistency detected | Reconciliation job flags; operations team investigates |

---

## What This Design Demonstrates

- Idempotency at both cache (Redis) and DB layers (belt and suspenders)
- Double-entry ledger for zero-drift money accounting
- Immutable event log for audit trail and state reconstruction
- Client-side tokenization to keep card data out of your systems (PCI compliance)
- Reconciliation as a correctness mechanism (don't trust your own records alone)
- Pre-authorization → capture two-phase payment (Uber/Zomato model)
