# Scaling Long-Lived Connections

#backend #realtime #architecture #scaling

> **In one line:** Once connections live on specific pods and events are generated anywhere, you need a backplane — and every design decision after that follows from how many connections each event must reach.

---

## The Idea

One server holding connections is easy. Two servers is a distributed systems problem.

```
User A ──── pod-1
User B ──── pod-2

Ingestion worker on pod-7 produces an event for User A.
pod-7 has no connection to User A.
```

You need a way for any producer to reach any connection. That is a **backplane**.

```
Producer ──► backplane ──► pod-1 ──► User A
                       ──► pod-2 ──► User B
```

💡 **The design question that determines everything else is the fanout ratio.** One event to one user is a routing problem. One event to 100,000 users is a broadcast problem. They need different architectures, and confusing them is the most common mistake in this area.

---

## The Fanout Spectrum

| Pattern | Example | Approach |
|---|---|---|
| **1 → 1** | "Your export is ready" | Route to the pod holding that connection |
| **1 → few** | Document annotation, 5 collaborators | Topic per document |
| **1 → many** | Org-wide announcement, 5,000 users | Topic per org, fan out locally |
| **1 → everyone** | System status change | Broadcast to all pods |
| **many → many** | Live cursors in a shared document | High rate, small payload, needs care |

⚠️ **The many-to-many case is qualitatively harder.** Ten users each moving a cursor 30 times per second is 300 events per second, each needing to reach 9 others — 2,700 deliveries per second for one document. This is where naive designs collapse, and the fix is usually to reduce the event rate (coalescing, throttling) rather than to scale the delivery.

## Backplane Options

### Redis Pub/Sub

```python
# Publisher, from anywhere
await redis.publish(f"org:{org_id}", orjson.dumps(event))

# Each pod, once
async def listen():
    pubsub = redis.pubsub()
    await pubsub.psubscribe("org:*")
    async for msg in pubsub.listen():
        org_id = msg["channel"].decode().split(":", 1)[1]
        fanout_locally(org_id, orjson.loads(msg["data"]))
```

| | |
|---|---|
| **Good** | Trivial, very fast, low latency |
| **Bad** | **Fire and forget.** A pod disconnected for 200ms loses those messages permanently |

⚠️ Redis pub/sub has no persistence, no acknowledgement and no replay. A message published while a subscriber is momentarily disconnected is simply gone.

💡 **This is acceptable only if you have a replay log.** The client reconnects with a cursor and catches up ([[04.2 - Server Sent Events]]). Without one, you have silent data loss that appears as "sometimes the UI is stale".

### Redis Streams

```python
await redis.xadd(f"events:{org_id}", {"data": payload}, maxlen=1000, approximate=True)

# Consumer reads from a known ID, so nothing is lost
entries = await redis.xread({f"events:{org_id}": last_id}, block=5000)
```

| | |
|---|---|
| **Good** | Persistent, bounded, replayable. Backplane and replay log in one primitive |
| **Bad** | Slightly more complex. One stream per topic can mean many streams |

💡 **Streams are the right default for a realtime backplane** and pub/sub is a premature optimisation. You need a replay log anyway; Streams give you both with one mechanism and one source of truth for event IDs.

### Kafka

| | |
|---|---|
| **Good** | Long retention, partitioned, high throughput, replay from any point |
| **Bad** | Higher latency (tens of ms), operational weight, consumer group rebalancing |

Right when you already run Kafka for other reasons, or when events must be retained for hours. Overkill as a realtime backplane on its own.

### Postgres LISTEN/NOTIFY

```sql
NOTIFY events, '{"org_id": 7, "type": "document_indexed"}';
```

| | |
|---|---|
| **Good** | No extra infrastructure. Transactional — notify only fires on commit |
| **Bad** | 8KB payload limit. Not persistent. Every listener needs a dedicated connection |

⚠️ **The dedicated-connection requirement is the killer.** `LISTEN` occupies a connection permanently, and it does not work through PgBouncer in transaction mode. For a handful of pods it is fine; beyond that it consumes your connection budget ([[01.10 - Connection Pools and Limits]]).

The transactional property is genuinely useful though: `NOTIFY` inside a transaction fires only if the transaction commits, which eliminates a class of "event published for a write that rolled back" bugs.

### Direct pod-to-pod

The client is registered in a shared table; producers look up the pod and call it directly.

```python
pod = await redis.get(f"conn:{user_id}")
await http.post(f"http://{pod}/internal/push", json=event)
```

| | |
|---|---|
| **Good** | Efficient for 1→1. No broadcast overhead |
| **Bad** | Registry must be accurate. Stale entries on crash. More moving parts |

Good for targeted delivery at scale, where broadcasting one event to every pod is wasteful. This is what Centrifugo does for direct messages.

## Topic Design

The decision that determines your backplane cost.

```
Too coarse:  one topic for everything
             → every pod receives every event, filters locally
             → wasted network and CPU

Too fine:    one topic per user
             → 100,000 subscriptions on the backplane
             → subscription management becomes the bottleneck
```

**The usual answer is topic-per-tenant with local fanout:**

```python
# Subscribe once per org that this pod has connections for
subscribed_orgs: set[int] = set()

async def on_connect(user):
    if user.org_id not in subscribed_orgs:
        await pubsub.subscribe(f"org:{user.org_id}")
        subscribed_orgs.add(user.org_id)
    local_connections[user.org_id].add(user.stream)

async def on_disconnect(user):
    local_connections[user.org_id].discard(user.stream)
    if not local_connections[user.org_id]:
        await pubsub.unsubscribe(f"org:{user.org_id}")
        subscribed_orgs.discard(user.org_id)
```

Each pod subscribes only to topics it actually has connections for. Events reach only relevant pods, which then fan out in memory.

⚠️ **The unsubscribe path is easy to get wrong and leaks quietly.** A pod that never unsubscribes accumulates subscriptions for orgs it no longer serves, receiving and discarding events forever. Test this explicitly.

### Filtering: where?

```
At the publisher:   most efficient, but the publisher must know who is listening
At the backplane:   topic granularity does the work
At the pod:         simple, but wastes network
At the client:      never. Sending data the user should not see is a security bug
```

⚠️ **Never filter at the client for authorisation.** If a user should not see an event, it must not leave the server. Filtering in the browser means the data was delivered and is visible in devtools. This sounds obvious and it happens regularly in realtime systems, because the fanout code is separate from the authorisation code.

## Presence

"Who is online" looks simple and is not.

```python
# Naive: a set of user IDs
await redis.sadd(f"presence:{org_id}", user_id)
await redis.srem(f"presence:{org_id}", user_id)      # on disconnect
```

⚠️ **A pod that crashes never runs the `srem`.** Users appear online forever. Over weeks, your presence set is mostly ghosts.

The correct approach is heartbeat-based with expiry:

```python
# Refresh every 15s while connected
await redis.zadd(f"presence:{org_id}", {user_id: time.time()})

# Read: only recent entries count
cutoff = time.time() - 45
online = await redis.zrangebyscore(f"presence:{org_id}", cutoff, "+inf")

# Periodic cleanup
await redis.zremrangebyscore(f"presence:{org_id}", "-inf", cutoff)
```

A sorted set scored by last-heartbeat time. Stale entries expire naturally whether or not the pod shut down cleanly.

💡 **Presence must be self-healing, because clean shutdown is not guaranteed.** Any design that depends on a disconnect handler running is wrong. This generalises: **in distributed systems, prefer leases that expire over registrations that must be revoked.**

## Load Distribution

Long-lived connections break normal load balancing.

```
3 pods, 3,000 connections, evenly spread
Scale to 6 pods
→ 3 new pods have zero connections
→ existing pods still have 1,000 each
```

⚠️ **Connections do not migrate.** Scaling up does not help until clients reconnect. Your autoscaler adds capacity that receives no traffic, then scales back down because CPU is low.

Mitigations:

| Approach | Notes |
|---|---|
| **Max connection lifetime** | Disconnect after 30–60 minutes. Clients reconnect and redistribute |
| **Connection draining on scale-down** | Gracefully close before terminating |
| **Client-side reconnect on rebalance signal** | Server tells a subset of clients to reconnect |
| **Consistent hashing at the LB** | Deterministic placement; still does not move existing connections |

💡 **Max connection lifetime is the practical answer** and it costs almost nothing if reconnection is seamless. A 45-minute lifetime with jitter means your fleet rebalances continuously, and it also bounds the "user whose access was revoked is still connected" problem.

Combine with jitter, or you get a synchronised reconnect storm every 45 minutes ([[04.3 - SSE in Production]]).

## In Production

### Sizing

```
Per connection in Python:
  asyncio task + buffers     ~10 KB
  application state          ~5–40 KB depending on what you keep
  file descriptor            1

10,000 connections ≈ 150–500 MB
```

⚠️ **Application state is what actually varies.** Keeping a user object, a permission set and a subscription list per connection can easily be 40KB. At 50,000 connections that is 2GB of avoidable memory. **Keep per-connection state minimal — an ID and a queue — and look up the rest.**

### The metrics

```python
connections_active.labels(pod=pod_id).set(count)
backplane_subscriptions.set(len(subscribed_topics))
backplane_lag_seconds.observe(now - event.created_at)
fanout_size.observe(len(recipients))
fanout_duration_seconds.observe(elapsed)
presence_ghost_entries.set(ghosts_cleaned)
```

**`backplane_lag_seconds` is the health metric** — the time from event creation to local delivery. If it climbs, your backplane is the bottleneck, not your pods.

**`fanout_size` distribution tells you whether you have a hot topic.** A p99 of 50,000 recipients for one event means one org is dominating your delivery cost, and it will show up as unexplained CPU spikes.

### The failure modes

| Symptom | Cause |
|---|---|
| Some users miss events | Backplane message lost (pub/sub), no replay log |
| Events arrive late for everyone | Backplane lag — Redis saturated or slow |
| One pod at 100% CPU | Hot topic, or uneven connection distribution |
| Presence shows offline users | Ghost entries from crashed pods |
| New pods get no traffic | Connections do not migrate |
| Memory grows steadily | Leaked subscriptions or leaked per-connection state |
| Reconnect storm every N minutes | Unjittered max connection lifetime |

### The design checklist

Before shipping any multi-pod realtime feature:

1. What is the fanout ratio, at p50 and p99?
2. What happens to an event published while a pod is briefly disconnected from the backplane?
3. Can a client detect and recover from a gap?
4. Where is authorisation enforced — publisher, backplane, or pod?
5. What happens to presence when a pod is `kill -9`'d?
6. How do connections redistribute after scaling?
7. What is the per-connection memory cost, measured?
8. What is the reconnect rate during a deploy?

⚠️ **Question 2 is the one that gets skipped**, and it is the one that produces "sometimes the UI is stale" bug reports that nobody can reproduce.

## Codebase

**Repo:** `centrifugal/centrifugo`, `django/channels_redis`, `zulip/zulip`

**Question to answer:** In Centrifugo, trace a message published via the API to a client connected on a different node. Where does the fanout happen, how are subscriptions managed, and what is the delivery guarantee? Then: how does Centrifugo's history feature let a reconnecting client recover missed messages, and what are its limits?

**Read, in order:**

1. `centrifugo/internal/client/hub.go` — the local connection registry and fanout. **Note how little of this is transport-specific**
2. `centrifugo/internal/` — the Redis engine. Subscription management, and how it batches subscribe/unsubscribe operations rather than issuing one per connection
3. Centrifugo docs on **history and recovery** — the replay mechanism, its retention limits, and the explicit "recovery failed" signal to clients. **This is the resync path as a product feature**
4. `channels_redis/core.py` — `RedisChannelLayer.group_send`. A simpler design, and its limitations are instructive: what happens when a group has 10,000 members?
5. `zulip/zerver/tornado/event_queue.py` — per-user queues rather than topic pub/sub. **A different architecture entirely**, and worth comparing

💡 The comparison between Centrifugo's topic model and Zulip's per-user-queue model is the valuable part. Centrifugo optimises for broadcast; Zulip optimises for per-user correctness and long offline periods. **Neither is universally right, and knowing which shape your product has is the actual design skill.** Conduit needs Zulip's model for ingestion progress and Centrifugo's for collaborative annotation.

**Drill 4.5 — A backplane that does not lose events**

```
drills/04-backplane/
├── stack/
│   ├── compose.yml       # 3 app pods + redis + nginx
│   └── nginx.conf
├── backplane/
│   ├── pubsub.py         # Redis pub/sub version
│   ├── streams.py        # Redis Streams version
│   ├── notify.py         # Postgres LISTEN/NOTIFY version
│   └── interface.py      # common abstraction
├── topics/
│   ├── per_tenant.py     # subscribe only to needed topics
│   ├── leak_test.py      # unsubscribe correctness
│   └── FINDINGS.md
├── presence/
│   ├── naive.py          # set-based, leaks ghosts
│   ├── heartbeat.py      # sorted set with expiry
│   └── crash_test.sh     # kill -9 a pod, count ghosts
├── distribution/
│   ├── scale_test.sh     # scale up, measure distribution
│   ├── lifetime.py       # max connection lifetime with jitter
│   └── PLOT.md
├── correctness/
│   ├── lossy_backplane.sh    # kill redis briefly during publishing
│   └── RESULTS.md
└── README.md
```

**Part 1 — Three backplanes, one interface.** Implement pub/sub, Streams and LISTEN/NOTIFY behind a common interface. Three pods behind a load balancer.

Verify basic function: a client on pod-1 receives an event published from pod-3.

**Part 2 — Prove pub/sub loses messages.** Steady event publishing. Kill Redis for two seconds, restart it.

Count events published versus events received per client.

**Pub/sub should lose exactly the events published during the outage. Streams should lose none** once clients reconnect with their cursor.

Then add a replay log alongside pub/sub and show the loss disappearing. **This experiment is the argument for why the replay log is not optional**, whichever backplane you pick.

**Part 3 — Topic subscription lifecycle.** Implement per-tenant topics with subscribe-on-first-connection and unsubscribe-on-last-disconnect.

Then the leak test: connect and disconnect 1,000 clients across 100 orgs in random order. Assert the pod's subscription count returns to zero.

Then break it deliberately — remove the unsubscribe — and show subscriptions accumulating and the pod receiving traffic for orgs it no longer serves.

**Part 4 — Presence that survives a crash.** Naive set-based presence. 100 users across 3 pods. `kill -9` one pod.

Count ghost entries. They should persist indefinitely.

Then heartbeat-based presence with expiry. Repeat. Ghosts should clear within one expiry window.

Then measure the cost: heartbeat traffic and Redis operations per second at 10,000 connections. Tune the interval against the ghost-clearing delay and record the tradeoff.

**Part 5 — Connection distribution.** 3,000 connections across 3 pods. Scale to 6.

Chart connections per pod over the next 10 minutes. The new pods should receive nothing.

Then add a 5-minute max connection lifetime with jitter and chart again. Distribution should even out.

Then remove the jitter and show the synchronised reconnect spike every 5 minutes. **Three charts, one clear story.**

**Part 6 — Fanout at scale.** One org with 5,000 connected users across 3 pods. Publish 100 events per second to that org.

Measure: backplane messages per second, per-pod CPU, fanout duration p99, and end-to-end latency.

Then add a second org with 5 users and confirm its latency is unaffected by the large org — or find that it is not, and fix it with per-topic isolation.

**Part 7 — Wire it into Conduit.** Ingestion progress (1→few, per run) and collaborative annotation (many→many, per document) over one backplane.

Requirements: three pods, zero silent event loss under a Redis restart, presence accurate within 45 seconds of a `kill -9`, and connections redistributing after a scale-up.

Load test with 2,000 connections and prove event-ID continuity for every client.

**Done when:**
- Your pub/sub-versus-Streams loss comparison has real counts
- The subscription leak test passes and fails appropriately
- Ghost presence entries clear after a `kill -9`
- Your three distribution charts show the scale-up problem, the fix, and the jitter requirement
- A large org's fanout does not degrade a small org's latency
- Conduit survives a Redis restart with zero silent gaps
