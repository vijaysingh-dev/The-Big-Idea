# Case Study - News Feed

The most common frontend system design question. Design the client for an infinite social feed.

## Scope it first

Questions worth asking before designing anything ([[28.1 - How to Approach a Frontend System Design Interview]]):

- Read-only, or can users post, comment and react?
- Real-time — do new posts appear live, or on refresh?
- Media — images, video, both? Autoplay?
- Scale — how many posts per session? Thousands, or dozens?
- Mobile web, native app webview, or desktop?
- Does the feed need to be shareable or indexable?

A reasonable scoped answer: **read-only feed with reactions, infinite scroll, images and video, real-time indicator for new posts, mobile-first, authenticated so no SEO requirement.**

That last point resolves the rendering strategy immediately: CSR or a client-heavy SSR shell is fine ([[28.11 - Rendering Strategies]]).

## API contract

**Cursor pagination, not offset.** A feed changes constantly; with offsets, a post inserted at the top shifts everything down, so page 2 repeats an item from page 1 and skips another ([[24.4 - Pagination and Infinite Scroll]]).

```
GET /api/feed?cursor=eyJ0cyI6MTcwMH0&limit=20
```

```json
{
  "items": [{
    "id": "p_123",
    "author": { "id": "u_9", "name": "...", "avatarUrl": "..." },
    "text": "...",
    "media": [{ "type": "image", "url": "...", "width": 1200, "height": 800, "blurhash": "..." }],
    "reactions": { "like": 42, "viewerReacted": true },
    "createdAt": "2026-08-05T10:00:00Z"
  }],
  "pageInfo": { "endCursor": "eyJ0cyI6MTY5MH0", "hasNextPage": true }
}
```

Three things to insist on in the response shape:

**Media dimensions.** Without width and height the client cannot reserve space, and every image load shifts the layout — the single largest CLS contributor in a feed ([[13.5 - Core Web Vitals]]).

**Denormalized author.** A separate request per author is a waterfall. Embedding the small author object is worth the duplication.

**`viewerReacted`** included, so the client does not need a second request to know reaction state.

## Component structure

```
FeedPage
├── NewPostsBanner        real-time indicator
├── VirtualizedFeed
│   └── PostCard          memoized
│       ├── PostHeader
│       ├── PostMedia     lazy, aspect-ratio reserved
│       ├── PostText      clamped with expand
│       └── ReactionBar   optimistic
└── LoadMoreSentinel
```

`PostCard` must be memoized, or every scroll tick re-renders every visible card ([[19.2 - React.memo and Memoization Strategy]]).

For that to work, the feed data must preserve references for unchanged posts — reacting to one post creates one new post object and leaves the rest identical, so only that card re-renders ([[06.7 - Immutable Data Patterns]]).

## Data layer

```ts
const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
  queryKey: feedKeys.list(),
  queryFn: ({ pageParam, signal }) => api.getFeed({ cursor: pageParam, signal }),
  initialPageParam: null,
  getNextPageParam: (last) => last.pageInfo.endCursor ?? undefined,
  staleTime: 60_000,
  maxPages: 10,
});

const posts = useMemo(() => {
  const seen = new Set();
  return data.pages.flatMap(p => p.items).filter(p => {
    if (seen.has(p.id)) return false;
    seen.add(p.id);
    return true;
  });
}, [data]);
```

`getNextPageParam` must return `undefined` — not `null` — to signal the end.

**Deduplicate on render.** Even with cursors, overlapping pages can produce duplicates, and duplicate React keys cause unpredictable reconciliation ([[16.6 - Lists and Keys]]).

`maxPages: 10` trims old pages from memory during a long scroll session.

## Loading more

```jsx
const sentinelRef = useRef(null);

useEffect(() => {
  const el = sentinelRef.current;
  if (!el || !hasNextPage) return;

  const observer = new IntersectionObserver(
    ([entry]) => { if (entry.isIntersecting) fetchNextPage(); },
    { rootMargin: "800px" }
  );

  observer.observe(el);
  return () => observer.disconnect();
}, [hasNextPage, fetchNextPage]);
```

`rootMargin: "800px"` triggers roughly two screens early, so the next page usually arrives before the user reaches the bottom ([[12.5 - Custom Events and Observer APIs]]).

Always ship a manual "Load more" button alongside — a scroll sentinel is not keyboard-operable and is unpredictable for screen reader users ([[09.5 - Accessibility Fundamentals]]).

## Virtualization

Above roughly 200 rendered posts, DOM node count becomes the bottleneck. Feed cards are variable height, which is the hard case ([[19.5 - Virtualization and Windowing]]):

```jsx
const virtualizer = useVirtualizer({
  count: posts.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 400,
  overscan: 5,
  measureElement: (el) => el.getBoundingClientRect().height,
});
```

Dynamic measurement via `ResizeObserver` handles unknown heights, at the cost of small scrollbar adjustments while scrolling through unmeasured regions.

Accessibility requires reporting the real totals:

```jsx
<div role="feed" aria-busy={isFetchingNextPage}>
  <article aria-posinset={index + 1} aria-setsize={-1}>
```

`role="feed"` is the correct ARIA pattern for exactly this, and `aria-setsize={-1}` communicates an unknown total.

## Media

```jsx
<div style={{ aspectRatio: `${media.width} / ${media.height}` }}>
  <img
    src={media.url}
    srcSet={`${media.url}?w=400 400w, ${media.url}?w=800 800w`}
    sizes="(max-width: 640px) 100vw, 600px"
    loading={index < 2 ? "eager" : "lazy"}
    fetchPriority={index === 0 ? "high" : "auto"}
    decoding="async"
    alt={media.alt ?? ""}
  />
</div>
```

The `aspectRatio` wrapper reserves space before the image loads — non-negotiable for CLS ([[09.3 - Images Media and Loading Attributes]]).

The first one or two posts load eagerly with high priority since one of them is the LCP element; everything below is lazy.

A blurhash or a tiny base64 placeholder behind the image gives an immediate impression of content.

Video should be muted, `playsinline`, `preload="metadata"`, and play only when substantially in view — an `IntersectionObserver` with a 0.5 threshold. Autoplaying every video in a feed is the fastest way to exhaust a mobile data plan.

## Reactions: optimistic

```ts
const { mutate: react } = useMutation({
  mutationFn: api.react,

  onMutate: async ({ postId, type }) => {
    await queryClient.cancelQueries({ queryKey: feedKeys.list() });
    const previous = queryClient.getQueryData(feedKeys.list());

    queryClient.setQueryData(feedKeys.list(), (old) => updatePostReaction(old, postId, type));

    return { previous };
  },

  onError: (_e, _v, ctx) => queryClient.setQueryData(feedKeys.list(), ctx.previous),
  onSettled: () => queryClient.invalidateQueries({ queryKey: feedKeys.list() }),
});
```

`cancelQueries` first is what prevents an in-flight background refetch landing after the optimistic write and silently reverting it — the most common bug in this pattern ([[24.8 - Optimistic Updates with TanStack Query]]).

## Real-time, without disrupting reading

Never insert new posts into the middle of a feed someone is reading. Buffer and announce:

```jsx
socket.on("post:new", (post) => setPendingPosts(p => [post, ...p]));

{pendingPosts.length > 0 && (
  <button className="new-posts-banner" onClick={showNewPosts}>
    {pendingPosts.length} new posts
  </button>
)}
```

The user decides when to jump. This is what every major feed does, and for good reason — content shifting under the reader is deeply disorienting.

For a feed, SSE is often a better fit than a WebSocket: the flow is one-directional, and it gives free reconnection and event replay via `Last-Event-ID` ([[15.8 - WebSockets and Server Sent Events]]).

## Scroll restoration

Tapping a post and pressing back should return to the same position with the same posts loaded. This is the single most-complained-about behavior in mobile web feeds.

```ts
useQuery({ gcTime: 10 * 60_000 });     // keep pages cached across navigation
```

The cache preserves the data; the router restores the scroll position. With virtualization, restoration also needs the scroll offset saved and reapplied after measurement ([[23.2 - React Router Setup and Nested Routes]]).

## Performance summary

| Concern | Approach |
| --- | --- |
| Initial load | SSR shell or a skeleton; route-level code splitting |
| LCP | eager + high priority on the first media item |
| CLS | aspect-ratio reservation on every media element |
| INP | memoized cards, virtualization, batched real-time updates |
| Memory | `maxPages`, virtualization, `gcTime` |
| Data usage | lazy media, responsive `srcSet`, no video autoplay off-screen |

## Failure modes

- **Empty feed** — first-use empty state with an action, not "no results" ([[24.2 - Loading Error and Empty States]])
- **Load failure mid-scroll** — inline retry, keeping loaded posts visible
- **A single broken post** — error boundary per card so one bad payload does not blank the feed
- **Offline** — serve the cached feed with an offline indicator
- **Slow network** — skeletons sized to the real cards

## How senior engineers approach this

**They insist on cursor pagination and media dimensions** in the API contract, because both are unfixable client-side.

**They buffer real-time posts** rather than inserting them.

**They memoize cards and preserve references** on update, so one reaction re-renders one card.

**They treat scroll restoration as a requirement**, not a nice-to-have.

**They add virtualization only above the measured threshold**, since it complicates scroll restoration and accessibility.

## Common pitfalls

- Offset pagination producing duplicates and skips.
- No media dimensions, so every image shifts the layout.
- Unmemoized cards re-rendering on every scroll tick.
- New posts inserted mid-scroll.
- Scroll position lost on back navigation.
- Unbounded page accumulation.
- Duplicate keys from overlapping pages.
- No keyboard-accessible way to load more.

## Interview angle

Lead with the API contract, because cursor pagination and media dimensions are decisions the client cannot fix later. Then the rendering path: infinite query, deduplication, virtualization above a threshold, memoized cards backed by reference-preserving updates. Cover optimistic reactions with the `cancelQueries` detail, real-time buffered into a banner rather than inserted, and scroll restoration on back navigation — that last one is the detail most candidates omit and most users notice.
