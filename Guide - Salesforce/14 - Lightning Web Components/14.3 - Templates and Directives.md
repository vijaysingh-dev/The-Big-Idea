# Templates and Directives

## The template

HTML wrapped in a `<template>` root, with expressions in braces.

```html
<template>
    <lightning-card title={cardTitle} icon-name="standard:case">
        <div class="slds-p-horizontal_small">
            <p>Claim {claimNumber} — {statusLabel}</p>
        </div>
    </lightning-card>
</template>
```

**Expressions are property references only.** No method calls, no operators, no logic.

```html
<!-- All invalid -->
{amount > 500000}
{formatAmount(amount)}
{claim.Amount__c * 1.18}
{isOpen ? 'Open' : 'Closed'}
```

Logic goes in a **getter**:

```javascript
get isHighValue() {
    return this.amount > 500000;
}

get statusLabel() {
    return this.isClosed ? 'Closed' : 'In progress';
}
```

```html
<template lwc:if={isHighValue}>
    <lightning-badge label="High Value"></lightning-badge>
</template>
```

This constraint is deliberate — it keeps logic testable in JavaScript rather than buried in markup. Coming from Aura's `{!v.x + v.y}` expressions, it feels restrictive at first and produces more maintainable components.

## Conditional rendering

```html
<template lwc:if={hasClaims}>
    <c-claim-list claims={claims}></c-claim-list>
</template>
<template lwc:elseif={isLoading}>
    <lightning-spinner alternative-text="Loading"></lightning-spinner>
</template>
<template lwc:else>
    <p>No claims found.</p>
</template>
```

`lwc:if`, `lwc:elseif`, and `lwc:else` replace the older `if:true` and `if:false`, which are deprecated. The newer directives support the else chain and are more efficient.

**Conditional rendering removes the element from the DOM entirely**, which is different from hiding it with CSS. A component inside a false branch is not constructed, its wires do not run, and its `connectedCallback` does not fire.

That matters for performance: a tab whose content is behind `lwc:if` costs nothing until shown.

## Iteration

```html
<template for:each={claims} for:item="claim" for:index="index">
    <div key={claim.Id} class="claim-row">
        <span>{index}. {claim.Claim_Number__c}</span>
        <lightning-formatted-number value={claim.Claim_Amount__c}
                                    format-style="currency"
                                    currency-code="INR">
        </lightning-formatted-number>
    </div>
</template>
```

**`key` is required** on the element directly inside `for:each`, and it must be a **unique primitive** — an Id or a unique string. Not the index, and not an object.

```html
<!-- Wrong: index as key breaks reordering and causes rerender bugs -->
<div key={index}>

<!-- Correct -->
<div key={claim.Id}>
```

Using the index means that when the list reorders or an item is removed, LWC reuses the wrong DOM nodes and component state attaches to the wrong item. The symptom is baffling — a checkbox appearing ticked on the wrong row.

The alternative iteration syntax gives first and last flags:

```html
<template iterator:it={claims}>
    <div key={it.value.Id} class={it.first ? 'first-row' : ''}>
        <span>{it.value.Claim_Number__c}</span>
        <hr lwc:if={it.last}/>
    </div>
</template>
```

`it.value`, `it.index`, `it.first`, `it.last`. Useful for separators and for styling the ends of a list, and more verbose otherwise.

## Iterating a map

Templates cannot iterate an object's keys. The data must be reshaped into an array in JavaScript:

```javascript
get groupedClaims() {
    // templates cannot iterate objects, so a map becomes an array of entries
    return Object.entries(this.claimsByStatus).map(([status, claims]) => ({
        key: status,
        status,
        claims
    }));
}
```

```html
<template for:each={groupedClaims} for:item="group">
    <div key={group.key}>
        <h3>{group.status}</h3>
        <template for:each={group.claims} for:item="claim">
            <p key={claim.Id}>{claim.Claim_Number__c}</p>
        </template>
    </div>
</template>
```

Nested iteration works, each level needing its own `key`.

## Attribute binding

```html
<lightning-input value={claimAmount}
                 disabled={isReadOnly}
                 label={amountLabel}>
</lightning-input>

<div class={rowClass} data-id={claim.Id}>
<a href={detailUrl}>View</a>
```

**Boolean attributes take the property's truthiness.** A `disabled` bound to `undefined` is not disabled; bound to `false` it is not disabled; bound to any truthy value it is.

**Dynamic classes** need a getter, since expressions are not allowed:

```javascript
get rowClass() {
    return this.claim.isOverdue
        ? 'claim-row slds-theme_error'
        : 'claim-row';
}
```

For anything with several conditions, building the string in JavaScript is clearer than a chain of ternaries.

## Event handlers

```html
<lightning-button label="Approve" onclick={handleApprove}></lightning-button>
<lightning-input onchange={handleAmountChange}></lightning-input>
<c-claim-row onclaimselected={handleClaimSelected}></c-claim-row>
```

**`on` plus the lowercase event name.** Custom event names must be all lowercase with no hyphens, which is why `claimselected` rather than `claimSelected`. See [[14.7 - Child to Parent Communication and Events]].

**Handlers are bound automatically**, so `this` inside a handler is the component. No `.bind(this)` needed, unlike raw DOM handlers.

Passing data to a handler uses `data-` attributes rather than arguments:

```html
<template for:each={claims} for:item="claim">
    <lightning-button key={claim.Id}
                      label="Approve"
                      data-claim-id={claim.Id}
                      onclick={handleApprove}>
    </lightning-button>
</template>
```

```javascript
handleApprove(event) {
    // dataset keys are camelCase versions of the data- attribute names
    const claimId = event.target.dataset.claimId;
    this.approve(claimId);
}
```

`data-claim-id` becomes `dataset.claimId`. This is the standard way to identify which item in a list was acted on.

## Querying the DOM

```javascript
// Within this component's shadow root only
const input = this.template.querySelector('lightning-input');
const rows = this.template.querySelectorAll('.claim-row');

// For light DOM slotted content
const slotted = this.querySelector('.passed-in');
```

Two constraints that matter:

**The DOM does not exist until after render.** Querying in `connectedCallback` returns null; `renderedCallback` is where the DOM is available. See [[14.5 - Component Lifecycle Hooks]].

**You cannot query into a child component's shadow root.** `this.template.querySelector('c-claim-row')` returns the child element, and reaching further inside it is not possible. Communication is through public properties and events.

## Working with inputs

```html
<lightning-input type="number"
                 label="Approved amount"
                 value={approvedAmount}
                 onchange={handleAmountChange}
                 min="0"
                 required>
</lightning-input>
```

```javascript
handleAmountChange(event) {
    this.approvedAmount = event.target.value;
}
```

**LWC does not have two-way binding.** The value flows down through the attribute and back up through the event handler. This is explicit and slightly more verbose than Aura's two-way binding, and it makes data flow traceable.

Validating a form means reaching every input and calling its validity methods:

```javascript
validateForm() {
    // reportValidity displays the message; checkValidity only returns the result
    const allValid = [...this.template.querySelectorAll('lightning-input')]
        .reduce((validSoFar, input) => {
            input.reportValidity();
            return validSoFar && input.checkValidity();
        }, true);

    return allValid;
}
```

The spread on `querySelectorAll` is necessary because it returns a NodeList rather than an array.

## Slots

```html
<!-- claimCard.html -->
<template>
    <div class="card">
        <header>
            <slot name="title">Default title</slot>
        </header>
        <div class="body">
            <slot></slot>
        </div>
    </div>
</template>
```

```html
<!-- parent -->
<c-claim-card>
    <h2 slot="title">Claim WC-00042</h2>
    <p>Bearing failure on the drive assembly.</p>
</c-claim-card>
```

Slotted content is rendered by the child and **owned by the parent** — the parent's styles apply to it, and the parent's event handlers work on it.

Covered fully in [[14.9 - Slots and Composition]].

## Comments and whitespace

```html
<!-- This comment is stripped from the rendered output -->
```

Comments are removed unless the template opts into preserving them. Whitespace between elements is collapsed, which occasionally matters for inline layout and is usually invisible.

## Dynamic components

Rendering a component whose type is decided at runtime:

```html
<template lwc:if={componentConstructor}>
    <lwc:component lwc:is={componentConstructor}></lwc:component>
</template>
```

```javascript
async loadComponent(componentName) {
    // dynamic import, so the component is only fetched when needed
    const { default: ctor } = await import(componentName);
    this.componentConstructor = ctor;
}
```

Useful for a configurable page rendering different components by metadata. It costs the compile-time safety of a static reference, so use it where the configurability is genuinely needed.

## Practical guidance

**Put logic in getters**, never in the template.

**Use `lwc:if` / `lwc:elseif` / `lwc:else`**, not the deprecated `if:true`.

**Never use the index as a `key`.** Use a stable unique identifier.

**Reshape maps into arrays** before iterating.

**Use `data-` attributes** to identify which list item an event came from.

**Query the DOM in `renderedCallback`**, not `connectedCallback`.

**Remember there is no two-way binding** — value down, event up.

**Build class strings in JavaScript** rather than chaining ternaries in markup.
