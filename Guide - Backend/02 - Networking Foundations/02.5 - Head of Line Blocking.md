# Head of Line Blocking

#backend #networking #performance

> **In one line:** When items must be processed in order, one stuck item stops everything behind it — and this single idea explains HTTP/1.1 pipelining, HTTP/2's flaw, HTTP/3's existence, and Kafka partition design.

---

## The Idea

**Head-of-line blocking** (HOL blocking) is what happens in a queue where only the front item can move.

A single supermarket checkout. The person at the front cannot find their card. Everyone behind them waits, including the person with one item. Nobody is served, even though the till is idle.

The pattern appears at every layer of a distributed system:

| Layer | The queue | The stuck item |
|---|---|---|
| TCP | Bytes must be delivered in order | One lost packet |
| HTTP/1.1 | One request per connection at a time | One slow response |
| HTTP/2 | Streams share one TCP connection | One lost TCP packet stalls all streams |
| Kafka | Messages in a partition are ordered | One message that keeps failing |
| Task queues | FIFO consumption | One long task |
| Databases | Transactions waiting on a lock | One long-held lock |

Once you can see this pattern, a lot of otherwise unrelated design decisions turn out to be the same decision.

---

## HOL Blocking in TCP

TCP promises **ordered delivery**. The application never sees byte 5000 before byte 4000.

The kernel enforces this by buffering:

```
Sent:      [1][2][3][4][5][6][7][8]
Received:  [1][2][ ][4][5][6][7][8]        packet 3 was lost
                    ▲
App receives: 1, 2, ... then nothing.
Packets 4–8 sit in the kernel buffer, complete and useless,
until packet 3 is retransmitted and arrives.
```

The data is *there*. The application cannot have it, because that would break ordering.

**Cost: one full round trip** — the time to notice the loss and get the retransmission. On a 100ms link, everything stops for 100ms+ even though 5 packets arrived fine.

⚠️ **This is a property of TCP itself.** You cannot configure it away. Any protocol built on TCP inherits it. That is the central fact of this note.

## The HTTP Story, Told Through HOL Blocking

The whole evolution of HTTP is an attempt to escape this, and each step trades one form for another.

### HTTP/1.0 — one connection per request

```
Request 1: connect → send → receive → close
Request 2: connect → send → receive → close
```

No HOL blocking, because there is no queue. But you pay a full handshake (and slow start) per request. Terrible.

### HTTP/1.1 — keep-alive, one at a time

```
Connection: [ req1 ──► resp1 ] [ req2 ──► resp2 ] [ req3 ──► resp3 ]
```

Reuses the connection, but requests are strictly serialized. Request 2 cannot start until response 1 finishes.

**Application-level HOL blocking.** One slow endpoint blocks everything queued behind it on that connection.

Browsers worked around this by opening **6 parallel connections per host**. Six independent queues instead of one. It works, and it costs 6 handshakes, 6 congestion windows starting from scratch, and 6× the server-side connection state.

### HTTP/1.1 pipelining — a good idea that failed

```
Send:     req1, req2, req3      (all at once, without waiting)
Receive:  resp1, resp2, resp3   (must come back in order)
```

Requests can be sent together, but responses **must return in request order**. If response 1 takes 5 seconds, responses 2 and 3 wait even if they were ready instantly.

⚠️ Pipelining is effectively dead. Browsers disabled it because of this exact problem, plus proxies that handled it incorrectly. It is a useful cautionary tale: partial concurrency without out-of-order completion buys you very little.

### HTTP/2 — multiplexing

```
One TCP connection:
  Stream 1: ══════╗
  Stream 3: ═══╗  ║      interleaved frames, any order
  Stream 5: ╗  ║  ║
```

Requests become **streams**, each split into frames, interleaved on one connection. Responses can complete in any order. Application-level HOL blocking is solved.

⚠️ **But TCP-level HOL blocking is now worse.** With HTTP/1.1's six connections, a lost packet stalled one connection and the other five kept going. With HTTP/2's single connection, one lost packet stalls **every stream**.

```
HTTP/1.1, 6 connections, 1 packet lost  → 1/6 of your requests stall
HTTP/2,   1 connection,  1 packet lost  → all requests stall
```

💡 **This is why HTTP/2 sometimes performs worse than HTTP/1.1 on lossy networks.** On a good connection HTTP/2 wins clearly. On mobile or WiFi with 1–2% loss, the single shared connection becomes a shared point of failure. Measured results on poor networks genuinely favour HTTP/1.1 sometimes, and this surprises people who assume newer is always better.

### HTTP/3 — escape TCP entirely

QUIC over UDP. UDP has no ordering guarantee, so QUIC implements ordering **per stream** rather than per connection.

```
Stream 1: [1][2][3]
Stream 3: [1][ ][3]      ← packet lost here
Stream 5: [1][2][3]

Streams 1 and 5 are delivered normally. Only stream 3 waits.
```

Loss is contained to the stream it affected. This is the entire reason HTTP/3 exists.

QUIC also brings a 1-RTT (or 0-RTT) handshake with TLS built in, and connection migration — the connection survives your phone switching from WiFi to cellular, because a QUIC connection is identified by a connection ID rather than an IP and port. See [[03.9 - HTTP3 and QUIC]].

### The summary table

| | Concurrency | App HOL | TCP HOL |
|---|---|---|---|
| HTTP/1.0 | 1 per connection | None | Per connection |
| HTTP/1.1 keep-alive | 1 at a time | **Yes** | Per connection |
| HTTP/1.1 × 6 connections | 6 | Per connection | Per connection (1/6 blast radius) |
| HTTP/1.1 pipelining | Send-only | **Yes**, on responses | Per connection |
| HTTP/2 | Many streams, 1 conn | None | **All streams** |
| HTTP/3 | Many streams, 1 conn | None | **Per stream** |

## HOL Blocking Beyond HTTP

### Kafka partitions

Messages within a partition are strictly ordered. A consumer processes them in order.

```
Partition 0: [msg1][msg2][msg3][msg4]
                     ▲
              this one keeps failing
```

If your consumer retries `msg2` forever, `msg3` and `msg4` never get processed. The partition is stuck.

**This is why dead letter queues exist.** After N attempts, move the message aside and continue. You trade strict ordering for liveness — and that trade must be a deliberate decision, because for some data (financial ledger entries) it is wrong.

💡 **Partition count is a HOL blocking decision.** More partitions means smaller blast radius per stuck message and more parallelism, at the cost of ordering only being guaranteed within each partition. Choosing a partition key is choosing which things must stay ordered relative to each other. See [[09.1 - Queue vs Log]].

### Task queues

A single FIFO queue with one worker: a 10-minute task blocks every 10-millisecond task behind it.

Fixes are all the same shape — **stop sharing one queue**:

- Separate queues by expected duration (`fast`, `slow`)
- More workers (more parallel queues)
- Priority queues
- Timeouts that move slow work aside

See [[08.7 - Routing Queues Priorities and Prefetch]].

### Database locks

```
Transaction A: holds a lock on row X for 30 seconds
Transaction B: waits for row X
Transaction C: waits behind B
```

A lock queue is a queue, so it blocks the same way. This is why "no network calls inside a transaction" ([[01.10 - Connection Pools and Limits]]) matters so much: you are putting a variable-latency operation at the head of a queue that other work depends on.

### Your own code

```python
for item in items:
    await process(item)          # one slow item blocks the rest
```

```python
async with asyncio.TaskGroup() as tg:
    for item in items:
        tg.create_task(process(item))    # independent, no HOL blocking
```

The fix is always the same: **if the items are genuinely independent, do not put them in a shared ordered queue.**

## In Production

### The diagnostic signature

HOL blocking has a recognisable shape: **latency for fast operations correlates with the presence of slow ones, even though they share no resource other than a queue.**

```
p50 of /fast endpoint:  5ms   (normally)
p50 of /fast endpoint:  5ms   (while /slow is idle)
p99 of /fast endpoint:  800ms (while /slow is busy)
```

Nothing is overloaded. CPU is fine, the database is fine. Fast requests are simply stuck behind slow ones somewhere.

Places to look, in order:

1. Event loop — a blocking call ([[01.6 - The Blocking Call Problem]])
2. Thread pool — a shared 40-thread limit ([[01.3 - Threads Processes and Coroutines]])
3. Connection pool — a shared pool ([[01.10 - Connection Pools and Limits]])
4. HTTP client — HTTP/2 with a slow response on the shared connection
5. Task queue — one queue, mixed durations
6. Kafka — a poison message in a partition
7. Database — a long-held lock

**All seven are the same problem.** Recognising that is the value of this note.

### The universal fix: separate the queues

| Problem | Separation |
|---|---|
| Slow endpoint blocking the loop | Move it to a thread or a queue |
| Slow dependency exhausting threads | Per-dependency `CapacityLimiter` |
| Slow query holding connections | Separate pool for analytics queries |
| Slow task blocking the queue | Separate queue by duration |
| Poison message stuck in a partition | Dead letter queue |
| One HTTP/2 connection stalling | Multiple connections, or HTTP/3 |

This is the **bulkhead** pattern in every case — [[11.3 - Circuit Breakers and Bulkheads]].

### The HTTP/2 decision

When your client talks to a service over HTTP/2:

| Situation | Choice |
|---|---|
| Internal network, low loss | HTTP/2, one connection. Best case |
| Internet clients, mobile | HTTP/3 if available, or HTTP/2 with multiple connections |
| Very high throughput, one destination | Multiple HTTP/2 connections to spread the risk |
| gRPC through an L4 load balancer | ⚠️ All streams pin to one backend. You need L7 |

That last row is a real production trap. gRPC multiplexes over one TCP connection, so an L4 load balancer — which only sees TCP — sends every request to whichever backend got the connection. Your load balancing silently stops working, and one backend gets all the traffic. You need an L7 proxy that understands HTTP/2 streams. See [[03.10 - Proxies and Load Balancers]].

## Codebase

**Repo:** `python-hyper/h2` and `quic-go/quic-go`

**Question to answer:** In HTTP/2, how are frames from different streams interleaved on one connection, and what stops one stream from starving the others? Then: in QUIC, what data structure lets stream 5 be delivered while stream 3 is waiting for a retransmission?

**Read, in order:**

1. `h2/connection.py` — `H2Connection`, especially how it multiplexes and how it applies per-stream flow control
2. `h2/stream.py` — the per-stream state machine
3. `h2/windows.py` — connection-level *and* stream-level windows. Understand why there are two
4. `quic-go/internal/flowcontrol/` — the same two-level idea in QUIC
5. `quic-go/receive_stream.go` and `internal/protocol/` — how per-stream reassembly works. **This is the answer to the second question**

💡 The key thing to notice: HTTP/2 already has per-stream flow control at the application layer, but it sits on top of a transport that does not. All the per-stream machinery is undone by TCP's single ordered byte stream underneath. That realisation is the whole argument for QUIC, and seeing it in code makes it permanent.

**Size:** 1–2 sessions.

**Part 1 — See it in TCP.** Two hosts (or netns), a bulk transfer, and `tc netem` dropping a single packet at a known point. Instrument the receiver to log both bytes-arrived-at-kernel and bytes-delivered-to-app.

Show the gap: data physically present, application starved. Capture the retransmit in `tcpdump` and measure the stall duration against the RTT.

**Part 2 — The HTTP ladder.** One server with `/fast` (5ms) and `/slow` (2s). Measure `/fast` p99 while `/slow` is under load, for each of:

| Client | Expect |
|---|---|
| HTTP/1.1, 1 connection | `/fast` badly blocked |
| HTTP/1.1, 6 connections | Roughly 1/6 the damage |
| HTTP/2, 1 connection, clean network | No blocking |
| HTTP/2, 1 connection, 1% loss | Blocking returns, at the TCP layer |
| HTTP/3, 1% loss | No blocking |

**This table is the whole note, proven with your own numbers.** It is also an excellent thing to have in your head for an interview.

**Part 3 — The gRPC load balancing trap.** Three backend instances behind an L4 load balancer. Send 1000 gRPC requests over one channel. Count requests per backend.

You should find one backend got nearly all of them. Then put an L7 proxy (Envoy or nginx with `grpc_pass`) in front and repeat. **This is a real production failure that people ship and do not notice until one pod is at 100% CPU.**

**Part 4 — Queue blocking.** Mixed workload: 100 tasks of 10ms and 5 tasks of 30s, one queue, 4 workers. Measure completion time distribution for the fast tasks.

Then split into `fast` and `slow` queues with dedicated workers. Same total capacity, completely different latency profile. Chart both.

**Part 5 — The poison message.** Kafka topic, 1 partition, a consumer that retries a bad message forever. Show the lag growing while healthy messages sit behind it.

Fix with a dead letter queue after 3 attempts. Then write down, in `README.md`, one type of data for which this fix would be **wrong**, and why.

**Part 6 — Pool separation.** A service calling two dependencies from one connection pool. Make one slow with toxiproxy. Measure the effect on the other. Then split the pools and repeat.

**Done when:**
- Part 1 shows arrived-but-undeliverable data with a measured stall
- The part 2 table has all five rows with your numbers
- Part 3's request distribution is lopsided before the fix and even after
- You can articulate all six experiments as instances of one idea
