# Aggregate Queries, GROUP BY and HAVING

## Why this matters more than it looks

An aggregate query makes the **database** do the counting and summing, rather than retrieving every row into Apex and looping.

The difference at scale is not marginal. Summing 200,000 claim amounts in Apex means retrieving 200,000 rows — exceeding both the row limit and the heap limit. The same sum as an aggregate query returns a handful of rows.

Any time you find yourself looping to accumulate a total or a count, an aggregate query is probably the right answer.

## The functions

```
COUNT()          number of rows, no field argument
COUNT(field)     number of rows where the field is not null
COUNT_DISTINCT(field)
SUM(field)
AVG(field)
MIN(field)
MAX(field)
```

`COUNT()` with no argument returns an Integer directly and does not produce `AggregateResult`:

```java
Integer openClaims = [
    SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c != 'Closed'
];
```

This is the cheapest way to count and it does not consume the row limit for the counted rows.

## AggregateResult

Any query with `GROUP BY` or a named aggregate returns `AggregateResult` objects, which are read by key.

```java
List<AggregateResult> results = [
    SELECT Status__c status, COUNT(Id) claimCount, SUM(Claim_Amount__c) totalValue
    FROM Warranty_Claim__c
    WHERE Claim_Date__c = LAST_N_DAYS:90
    GROUP BY Status__c
];

for (AggregateResult ar : results) {
    String status = (String) ar.get('status');
    Integer count = (Integer) ar.get('claimCount');
    Decimal total = (Decimal) ar.get('totalValue');
}
```

Three things about this:

**Aliases are essential.** Without one, the field is accessed as `expr0`, `expr1`, and so on, in an order that is not obvious. Always alias.

**Every value must be cast.** `AggregateResult.get()` returns `Object`.

**`COUNT()` returns Integer; `SUM()` and `AVG()` return Decimal.** Casting `SUM()` to Integer throws.

`AggregateResult` cannot be inserted, updated, or used where an sObject is expected. It is a read-only result container.

## GROUP BY

```sql
SELECT Asset__r.Product2.Family family,
       Status__c status,
       COUNT(Id) claims,
       SUM(Claim_Amount__c) total,
       AVG(Claim_Amount__c) average
FROM Warranty_Claim__c
WHERE Claim_Date__c = THIS_FISCAL_YEAR
GROUP BY Asset__r.Product2.Family, Status__c
ORDER BY SUM(Claim_Amount__c) DESC
```

Grouping by a parent field is allowed and is frequently what you want.

**Every non-aggregate field in the `SELECT` must appear in `GROUP BY`.** This is the same rule as SQL and the same error people hit.

Not every field can be grouped. Long text areas, rich text, multi-select picklists, and encrypted fields cannot. Formula fields generally can, at the cost of computing them per row.

## HAVING

`WHERE` filters rows before grouping. `HAVING` filters groups after.

```sql
SELECT Account__c account, COUNT(Id) claims, SUM(Claim_Amount__c) total
FROM Warranty_Claim__c
WHERE Claim_Date__c = THIS_FISCAL_YEAR
GROUP BY Account__c
HAVING COUNT(Id) > 5 AND SUM(Claim_Amount__c) > 1000000
ORDER BY SUM(Claim_Amount__c) DESC
```

"Customers with more than five claims totalling over ten lakh this year" is a single query. Doing it in Apex means retrieving every claim and aggregating in memory.

`HAVING` can only reference aggregate functions and grouped fields.

## GROUP BY ROLLUP and CUBE

Subtotals and grand totals in one query.

```sql
SELECT Asset__r.Product2.Family family, Status__c status, COUNT(Id) claims
FROM Warranty_Claim__c
WHERE Claim_Date__c = THIS_FISCAL_YEAR
GROUP BY ROLLUP(Asset__r.Product2.Family, Status__c)
```

`ROLLUP` adds subtotal rows for each family and a grand total row. In the subtotal rows the more granular grouped fields are null, which is how you identify them:

```java
for (AggregateResult ar : results) {
    String family = (String) ar.get('family');
    String status = (String) ar.get('status');

    if (family == null) {
        // grand total row
    } else if (status == null) {
        // subtotal for this family
    } else {
        // detail row
    }
}
```

`CUBE` produces every combination of subtotals rather than a hierarchy. Both are limited to three grouped fields.

Useful for building a summary table in one query instead of several.

## Roll-up recalculation

The most common production use of aggregate queries: maintaining a stored roll-up where a native roll-up summary is not available.

```java
public with sharing class ClaimRollupService {

    public static void recalculate(Set<Id> assetIds) {
        if (assetIds.isEmpty()) {
            return;
        }

        Map<Id, Asset> assets = new Map<Id, Asset>([
            SELECT Id, Open_Claim_Count__c, Total_Claim_Value__c, Last_Claim_Date__c
            FROM Asset WHERE Id IN :assetIds
        ]);

        // reset first, so assets whose last claim was deleted go to zero rather than keeping a stale value
        for (Asset a : assets.values()) {
            a.Open_Claim_Count__c = 0;
            a.Total_Claim_Value__c = 0;
            a.Last_Claim_Date__c = null;
        }

        for (AggregateResult ar : [
            SELECT Asset__c assetId,
                   COUNT(Id) claimCount,
                   SUM(Claim_Amount__c) claimTotal,
                   MAX(Claim_Date__c) lastClaim
            FROM Warranty_Claim__c
            WHERE Asset__c IN :assetIds AND Status__c != 'Closed'
            GROUP BY Asset__c
        ]) {
            Asset a = assets.get((Id) ar.get('assetId'));
            a.Open_Claim_Count__c = (Integer) ar.get('claimCount');
            a.Total_Claim_Value__c = (Decimal) ar.get('claimTotal');
            a.Last_Claim_Date__c = (Date) ar.get('lastClaim');
        }

        update assets.values();
    }
}
```

The reset before the aggregate is the detail most hand-rolled roll-ups get wrong. Without it, an asset whose last open claim was closed keeps its old count forever. See [[02.6 - Roll-Up Summary Fields]].

## The limits

**Aggregate queries have a 2,000-row limit on the number of groups returned.** A query grouping by a field with 50,000 distinct values fails. This is not the same as the 50,000-row retrieval limit — it is the number of result rows after grouping.

When grouping produces too many groups, the options are to filter the input more narrowly, group by something coarser, or process in chunks by another dimension.

**The rows scanned still count toward query selectivity.** An aggregate over an unfiltered multi-million-row object is still a non-selective query and can time out, even though it returns three rows. Aggregation reduces what comes back, not what is scanned. See [[08.9 - Indexes and Selective Queries]].

**Aggregate queries cannot be used in a `for` loop over chunks**, because the result is not an sObject list.

## Date grouping

Grouping by a date field groups by the exact date, which is rarely what you want for a trend. The date functions handle this:

```sql
SELECT CALENDAR_YEAR(Claim_Date__c) yr,
       CALENDAR_MONTH(Claim_Date__c) mth,
       COUNT(Id) claims,
       SUM(Claim_Amount__c) total
FROM Warranty_Claim__c
WHERE Claim_Date__c = LAST_N_MONTHS:24
GROUP BY CALENDAR_YEAR(Claim_Date__c), CALENDAR_MONTH(Claim_Date__c)
ORDER BY CALENDAR_YEAR(Claim_Date__c), CALENDAR_MONTH(Claim_Date__c)
```

The available functions: `CALENDAR_YEAR`, `CALENDAR_MONTH`, `CALENDAR_QUARTER`, `DAY_IN_MONTH`, `DAY_IN_WEEK`, `DAY_IN_YEAR`, `WEEK_IN_MONTH`, `WEEK_IN_YEAR`, `FISCAL_YEAR`, `FISCAL_QUARTER`, `FISCAL_MONTH`, `HOUR_IN_DAY`.

`DAY_ONLY(datetimeField)` extracts the date portion of a Datetime for grouping, which is how you get daily counts from a timestamp field.

The fiscal functions use the org's fiscal year settings, which is why they are preferable to computing fiscal periods with a formula.

## Aggregates versus reports

Reports do grouping and summing natively and require no code. Prefer them when the output is for a human to look at.

Aggregate queries are the right tool when:

- The result drives logic rather than display
- It feeds a Lightning component
- It runs in a batch job or a scheduled process
- The output goes to an external system
- The grouping is more complex than a report can express

Building an aggregate query to replicate a report a user could have built is work with no return.

## Practical guidance

**Always alias aggregate columns.** `expr0` is not a maintainable interface.

**Cast every value**, and use Decimal for `SUM` and `AVG`.

**Use `COUNT()` with no argument** when you only need a count. It is the cheapest form.

**Reset before applying aggregates** in roll-up recalculation.

**Watch the 2,000-group limit.**

**Remember aggregation does not fix selectivity.** An aggregate over an unfiltered large object still scans everything.

**Use the date grouping functions**, particularly the fiscal ones.
