# Memory Leaks from Listeners and Detached DOM

The most expensive leak category in frontend applications, because a single retained node can hold an entire subtree — and DOM memory is much larger per object than JS memory.

## Detached DOM

A node is **detached** when it has been removed from the document but is still referenced from JavaScript. It is invisible, consumes memory, and drags its whole subtree with it.

```js
const cache = {};

function show() {
  const table = document.createElement("table");
  buildRows(table, 5000);
  cache.table = table;          // JS reference
  document.body.append(table);
}

function hide() {
  document.body.removeChild(cache.table);   // removed from the document
  // cache.table still points at it — 5000 rows retained
}
```

Removing from the DOM is not enough. The JS reference must go too:

```js
function hide() {
  cache.table.remove();
  cache.table = null;
}
```

Note that holding a reference to a *child* retains its ancestors as well, because every node has a `parentNode` pointer:

```js
const cell = table.querySelector("td");
table.remove();
// keeping `cell` retains the entire table through parentNode
```

This is the surprising part and the reason detached-DOM leaks are hard to reason about without a profiler.

## Event listeners

`addEventListener` creates a reference from the target to the handler, and the handler closes over its scope.

```js
function attachTooltip(element, largeConfig) {
  element.addEventListener("mouseenter", () => show(largeConfig));
}
```

If `element` is later removed but the listener is never removed, and something still references `element` (or it was attached to a long-lived target like `window`), `largeConfig` stays alive.

The critical asymmetry: **listeners on nodes that are garbage collected go away with them**. If nothing references a removed node, its listeners do not prevent collection. The leak happens when the target is long-lived:

```js
function mount(component) {
  window.addEventListener("resize", () => component.relayout());
  document.addEventListener("keydown", component.onKey);
}
```

`window` and `document` live for the page's lifetime, so these handlers — and the entire component they close over — are permanently retained. Every navigation that mounts this component adds another.

## removeEventListener needs identity

```js
element.addEventListener("click", () => handle());
element.removeEventListener("click", () => handle());   // does nothing
```

Two different function objects. Removal matches by reference, so the handler must be stored:

```js
const handler = () => handle();
element.addEventListener("click", handler);
element.removeEventListener("click", handler);
```

The same applies to bound methods — `obj.method.bind(obj)` produces a new function each call ([[02.8 - call apply and bind]]).

## The AbortSignal shortcut

The cleanest modern approach removes the need to keep handler references at all:

```js
const controller = new AbortController();
const { signal } = controller;

window.addEventListener("resize", onResize, { signal });
document.addEventListener("keydown", onKey, { signal });
element.addEventListener("click", onClick, { signal });

controller.abort();   // removes all three
```

One teardown call for any number of listeners, across any number of targets ([[04.6 - AbortController and Cancellation]]).

## In React

```jsx
useEffect(() => {
  const controller = new AbortController();

  window.addEventListener("resize", onResize, { signal: controller.signal });

  return () => controller.abort();
}, [onResize]);
```

Refs also need clearing when they hold DOM nodes in long-lived structures:

```jsx
const nodesRef = useRef(new Map());

const registerNode = useCallback((id, node) => {
  if (node) nodesRef.current.set(id, node);
  else nodesRef.current.delete(id);   // callback ref receives null on unmount
}, []);
```

A callback ref is invoked with `null` when the element unmounts. Ignoring that and only handling the non-null case leaves a `Map` full of detached nodes — a common leak in virtualized lists.

## Third-party libraries

Chart libraries, maps, editors and video players frequently allocate large internal structures and register global listeners. Almost all provide a `destroy()` or `dispose()` method, and almost all leak badly if it is not called.

```jsx
useEffect(() => {
  const chart = new Chart(canvasRef.current, config);
  return () => chart.destroy();
}, [config]);
```

Checking whether a library exposes a teardown method — and calling it — should be part of adopting any DOM-heavy dependency.

## Observers

`IntersectionObserver`, `MutationObserver` and `ResizeObserver` hold strong references to observed elements:

```js
const observer = new IntersectionObserver(callback);
observer.observe(element);

observer.unobserve(element);
observer.disconnect();          // required on teardown
```

An observer left connected to a removed element retains it permanently.

## How senior engineers actually use this

**They use `{ signal }` for every listener in effects.** It collapses cleanup to one line and makes forgetting a removal structurally harder.

**They treat `window`, `document` and `body` listeners as high-risk.** Anything attached to a long-lived target gets extra scrutiny in review, because that is where the permanent retention lives.

**They test navigation loops.** Navigate between two routes twenty times, force GC in DevTools, take a heap snapshot, and filter for "Detached". A growing detached count is a definitive leak signal ([[07.5 - Profiling Memory in DevTools]]).

**They null out refs in teardown** when a ref holds a DOM node or a heavy library instance.

## Common pitfalls

- Removing a node from the DOM but keeping a JS reference.
- Holding a reference to a child node, retaining the whole ancestor chain.
- `removeEventListener` with a new inline function.
- Global listeners in components that mount repeatedly.
- Observers never disconnected.
- Third-party widgets never destroyed.
- Callback refs that ignore the `null` call on unmount.

## Interview angle

This is the most practically important part of "what causes memory leaks". Give the detached-DOM example, explain that removal from the document is not enough, and mention that holding a child retains the ancestors. Then cover listeners on long-lived targets and the `removeEventListener` identity requirement. Ending with the `AbortSignal` option shows current practice rather than 2015-era answers.
