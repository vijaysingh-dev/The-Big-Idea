# Flow Testing

## The coverage gap

**Flows have no test coverage requirement.** A flow deploys to production regardless of whether anything verifies it.

That is a substantial gap, because flows carry as much business logic as Apex in most orgs — and a change that breaks one is discovered by users rather than by a pipeline.

## Native flow tests

Record-triggered flows support tests built in Flow Builder.

```
Flow Builder → View Tests → Create Test

Test Name:        High value claim escalates
Trigger:          Record is updated
Initial Record:   set the field values before the change
Updated Record:   set the field values after the change
Assertions:       assert on outcomes after the flow runs
```

The test defines an input record, runs the flow against it, and asserts on the result.

**What they cover:** record-triggered flows only.

**What they do not:**

```
Screen flows
Autolaunched flows
Scheduled flows
Platform event-triggered flows
Bulk behaviour — the test runs one record
Subflows in isolation
```

**Screen flows are the largest gap**, since they carry the most user-facing logic and cannot be tested natively at all.

## Building one

```
Test: Claims over the coverage limit route to executive approval

Initial Record (Warranty Claim)
    Status__c:        Submitted
    Claim_Amount__c:  400000
    Asset__c:         [a test asset]

Updated Record
    Claim_Amount__c:  900000

Assertions
    $Record.Approval_Tier__c  Equals  Executive
    $Record.Approver__c       Is Null  False
```

**Tests are metadata** and deploy with the flow, which means they run in CI if the pipeline invokes them.

```bash
sf flow run test --flow-api-name Claim_Approval_Routing --target-org my-sandbox
```

Coverage results appear in Flow Builder, and unlike Apex there is no gate — the number is informational.

## Their limits

Being direct about what they do not do.

**One record per test.** The single most important property of automation — bulk safety — is untestable natively. A flow with a Get Records element inside a loop passes every native test and fails at 200 records. See [[07.10 - Flow Limits and Performance]].

**No fault path testing.** A flow's fault connectors, which are where error handling lives, cannot be exercised.

**Limited assertion expressiveness.** Field equality on the triggering record, primarily. Asserting that three related records were created is awkward.

**No mocking.** A flow calling an Apex action or an External Services action calls it for real.

**Subflows run as part of the parent**, not independently.

## Apex tests against flows

The workaround for everything native tests cannot do, and for most orgs the more valuable approach.

```java
@IsTest
static void theRoutingFlowEscalatesHighValueClaimsInBulk() {
    List<Asset> assets = TestDataFactory.createAssets(50);

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
    for (Integer i = 0; i < 200; i++) {
        claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 900000));
    }

    Test.startTest();
    // the flow fires as part of the save, so an Apex test exercises it in bulk
    insert claims;
    Test.stopTest();

    List<Warranty_Claim__c> saved = [
        SELECT Approval_Tier__c, Approver__c FROM Warranty_Claim__c WHERE Id IN :claims
    ];

    Assert.areEqual(200, saved.size(), 'All 200 should save');
    for (Warranty_Claim__c claim : saved) {
        Assert.areEqual('Executive', claim.Approval_Tier__c);
        Assert.isNotNull(claim.Approver__c, 'An executive-tier claim needs an approver');
    }
}
```

**An Apex test that inserts records exercises every flow on the object**, in bulk, with real limits. It is the only way to prove flow bulk safety.

**Assert on limit consumption**, because a flow with a query per record is the most common flow performance defect:

```java
Test.startTest();
insert claims;

Assert.isTrue(Limits.getQueries() < 40,
    'Automation on this object used ' + Limits.getQueries() + ' queries for 200 records');
Test.stopTest();
```

That assertion catches a flow element added inside a loop — which no native flow test can.

## Testing autolaunched flows from Apex

```java
@IsTest
static void theCoverageCheckFlowReturnsTheCorrectLimit() {
    TestScenarioFactory.CoveredAssetScenario scenario =
        TestScenarioFactory.coveredAsset(500000);

    Map<String, Object> inputs = new Map<String, Object>{
        'assetId' => scenario.asset.Id
    };

    Test.startTest();
    // an autolaunched flow can be invoked directly and its outputs read
    Flow.Interview.Coverage_Check flowInstance = new Flow.Interview.Coverage_Check(inputs);
    flowInstance.start();
    Test.stopTest();

    Decimal limitReturned = (Decimal) flowInstance.getVariableValue('coverageLimit');
    Assert.areEqual(500000, limitReturned);
}
```

`Flow.Interview` gives direct invocation with input variables and readable outputs, which makes an autolaunched flow genuinely unit-testable.

**Screen flows cannot be invoked this way**, since they require user interaction. The testable part is any invocable Apex they call.

## Testing invocable actions

The seam worth exploiting: **push the logic into invocable Apex and test that.**

```java
public with sharing class ClaimApprovalActions {

    public class Request {
        @InvocableVariable(required=true) public Id claimId;
        @InvocableVariable public Decimal approvedAmount;
    }

    public class Result {
        @InvocableVariable public Boolean success;
        @InvocableVariable public String errorCode;
    }

    @InvocableMethod(label='Approve Claims')
    public static List<Result> approve(List<Request> requests) {
        // receiving every row at once is what makes this bulk-safe from a flow
        Set<Id> claimIds = new Set<Id>();
        for (Request request : requests) {
            claimIds.add(request.claimId);
        }

        ClaimApprovalService.approve(claimIds, requests[0].approvedAmount);
        return buildResults(requests);
    }
}
```

```java
@IsTest
static void theInvocableActionHandlesTwoHundredRequests() {
    List<Warranty_Claim__c> claims = TestDataFactory.createClaims(200);

    List<ClaimApprovalActions.Request> requests = new List<ClaimApprovalActions.Request>();
    for (Warranty_Claim__c claim : claims) {
        ClaimApprovalActions.Request request = new ClaimApprovalActions.Request();
        request.claimId = claim.Id;
        request.approvedAmount = 100000;
        requests.add(request);
    }

    Test.startTest();
    List<ClaimApprovalActions.Result> results = ClaimApprovalActions.approve(requests);
    Test.stopTest();

    Assert.areEqual(200, results.size());
    Assert.areEqual(200, [
        SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c = 'Approved'
    ]);
}
```

**A flow calling a tested invocable action is more trustworthy than a flow doing the work itself**, because the logic has real test coverage and real bulk verification.

That is a genuine architectural argument, not just a testing convenience: complex logic in invocable Apex, orchestration in the flow. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Debug and testing in Flow Builder

```
Flow Builder → Debug
    Run with a specific record
    Run as another user
    Show details of what each element evaluated
    Roll back changes on completion
```

**Debug is not a test.** It runs once, manually, with one record, and proves nothing on the next deployment.

Two things it is genuinely good for:

**Understanding an unfamiliar flow.** The element-by-element evaluation shows what the flow actually did with real data.

**Diagnosing a specific failure.** Running with the record that failed shows where it diverged.

**Rollback mode** lets you debug against production-shaped data in a sandbox without persisting changes, which is useful and often forgotten.

## Testing fault paths

Fault connectors have no native test, and they are where error handling lives.

The workaround is forcing the failure from Apex:

```java
@IsTest
static void theFlowFaultPathLogsAndDoesNotBlockTheSave() {
    Warranty_Claim__c claim = TestDataFactory.buildClaim(150000);
    // a value the flow's Apex action will reject, forcing the fault path
    claim.Asset__c = null;

    Test.startTest();
    Database.SaveResult result = Database.insert(claim, false);
    Test.stopTest();

    Assert.isTrue(result.isSuccess(),
        'The fault path should log and continue rather than blocking the save');
    Assert.areEqual(1, [SELECT COUNT() FROM Automation_Log__c],
        'The fault path should have logged');
}
```

Contriving the failure is awkward and it is the only mechanism available. Whether the fault path is worth this effort depends on what it does — one that only logs is lower risk than one that compensates.

## What a flow testing strategy looks like

Given the gaps, a workable position:

**Native flow tests** for record-triggered flows, covering the main decision branches. Cheap, and they catch a criteria change.

**Apex tests inserting records in bulk** for every object with flows, asserting on the outcome and on limit consumption. This is where flow bulk safety is actually verified.

**Invocable Apex, fully tested**, for anything complex — which also makes the flow simpler.

**`Flow.Interview`** for autolaunched flows that produce outputs.

**Manual test scripts** for screen flows, since nothing else covers them. Documented, and executed before a release.

**A flow inventory** so nobody adds a fifth flow to an object without knowing about the other four:

```sql
SELECT ApiName, Label, TriggerType, TriggerObjectOrEventLabel, Status, VersionNumber
FROM FlowDefinitionView
WHERE Status = 'Active'
ORDER BY TriggerObjectOrEventLabel, ApiName
```

## The honest summary

**Flow testing is weaker than Apex testing**, and that asymmetry is a real argument in the flow-versus-Apex decision.

A screen flow with complex branching has no automated coverage available. An equivalent LWC has Jest tests running in seconds.

That does not mean avoid flows — they are the right tool for a great deal, and administrator maintainability has real value. It means **being clear-eyed that flow logic carries less safety net**, and compensating: keep flows simple, push complexity into tested Apex, and cover the object with bulk Apex tests. See [[07.1 - Automation Landscape and Tool Selection]].

## Practical guidance

**Write native tests for record-triggered flows**, accepting that they cover one record.

**Write Apex bulk tests for every object with flows** — that is where bulk safety is proven.

**Assert on limit consumption** to catch a query inside a flow loop.

**Push complex logic into invocable Apex** and test it properly.

**Use `Flow.Interview`** for autolaunched flows.

**Use Debug to understand and diagnose**, not as a test.

**Document manual test scripts for screen flows.**

**Keep a flow inventory per object.**
