# System Patterns: Sync/Async, Push/Pull, Stateless/Stateful

> **Revision tags:** #fundamentals #patterns  
> **Related:** [[01.10 - Advanced Patterns]] | [[03.8 - Message Queues and Kafka]]

---

## Synchronous vs Asynchronous Communication

### Synchronous

The caller sends a request and **waits** for a response before proceeding.

```
Client ──request──→ Service A ──request──→ Service B
Client ←─response── Service A ←─response── Service B
       (blocked)                (blocked)
```

**Properties:**
- Simple to reason about — request/response contract
- Tight coupling — caller and callee must both be up
- Back-pressure is natural — slow callee slows caller
- Error handling is immediate

**Examples:** HTTP REST, gRPC, GraphQL, SQL queries.

**When to use:** User-facing requests where the user needs a result immediately. Operations that need an answer to continue (authentication, pricing lookup).

**Problems:**
- If Service B is slow, Service A's threads block — cascading slowdown
- If Service B is down, Service A fails immediately
- Hard to fan out to many services (each adds to total latency)

---

### Asynchronous

The caller sends a message and **does not wait** for processing to complete.

```
Client ──message──→ Queue ←──poll── Worker
Client (continues)         (processes independently)
```

**Properties:**
- Decoupled — producer and consumer don't need to be up simultaneously
- Better fault isolation — consumer failures don't affect producer
- Natural buffering — queue absorbs traffic spikes
- Harder to reason about — error handling is complex, ordering may not be guaranteed

**Examples:** Message queues (Kafka, RabbitMQ, SQS), event streaming, webhooks (async from caller's perspective).

**When to use:** Operations that don't need immediate results (email sending, report generation, audit logging, payment processing after showing "pending").

---

### Choosing Between Them

| Situation | Sync | Async |
|---|---|---|
| User needs immediate feedback | ✅ | ❌ |
| Operation is long-running | ❌ | ✅ |
| Fan-out to many consumers | ❌ | ✅ |
| Strict ordering required | Depends | Careful with partitioning |
| Consumer may be down | ❌ | ✅ |
| Simple error handling needed | ✅ | ❌ |

**Hybrid (common in production):**  
Sync for the initial response ("Your order was received"), async for the actual processing ("We'll email you when shipped").

## Push vs Pull

### Push (Server-initiated)

The server sends data to clients when it's available, without the client asking.

```
Server ──push──→ Client (whenever data is ready)
```

**Mechanisms:** WebSockets, Server-Sent Events (SSE), long polling, webhooks, push notifications.

**Pros:**
- Real-time feel — minimal latency from event to client notification
- Efficient for high-frequency updates (no wasted poll cycles)

**Cons:**
- Server must maintain connections (stateful — scales poorly without special infrastructure)
- Client must handle unexpected messages at any time
- Hard to control rate — server pushes at its own pace

**Examples:** Live chat, real-time stock prices, collaborative editing, live sports scores.

---

### Pull (Client-initiated)

The client requests data on its own schedule.

```
Client ──request──→ Server (whenever the client wants)
Server ──response──→ Client
```

**Mechanisms:** HTTP polling, REST API calls, database queries.

**Pros:**
- Client controls rate — no overwhelming the client
- Simpler server — stateless, no connection management
- Easy to implement

**Cons:**
- Latency: Updates aren't known until next poll
- Wasteful: Most polls may return "nothing new"

**Examples:** Email checking ("check every 30 seconds"), batch data pipelines, most REST API integrations.

---

### Choosing Between Them

| Situation | Push | Pull |
|---|---|---|
| Real-time notification required | ✅ | ❌ |
| Client count is massive (millions) | ❌ | ✅ |
| Updates are infrequent | ❌ | ✅ |
| Updates are frequent | ✅ | ❌ (too many polls) |
| Consumer sets its own pace | ❌ | ✅ |

**Hybrid approach:** Long polling or WebSocket "subscribe" model — client initiates but server holds the connection open and responds when data is ready.

## Stateless vs Stateful Systems

### Stateless

Each request contains all information needed to process it. The server holds no memory between requests.

```
Request 1: GET /profile (with auth token)   → Server processes, forgets
Request 2: GET /orders  (with auth token)   → Server processes, no memory of Request 1
```

**Advantages:**
- Any server instance can handle any request → trivial horizontal scaling
- No server-side session management
- Easy to add/remove instances (no sticky routing)
- Simpler failure recovery (just restart the instance)

**Examples:** REST APIs (properly designed), stateless functions/lambdas.

---

### Stateful

The server maintains state between requests from the same client.

```
Connection 1 established → session stored on Server A
Next request from same client MUST go to Server A
```

**Advantages:**
- Natural for certain protocols (WebSockets, database connections)
- Some computations are more efficient with in-memory state

**Disadvantages:**
- Sticky routing required (breaks simple load balancing)
- Failover is hard (state on Server A is lost if A dies)
- Scaling is constrained by state distribution

**Examples:** WebSocket servers, game servers, database connections, Kafka consumers (partition assignment is stateful).

---

### Making Stateful Systems Scale

The standard pattern: **move state out of the application tier** into a shared store.

```
Before (stateful):
Client → Server A (holds session in memory)

After (stateless app, stateful store):
Client → Any Server → Redis (session store)
```

This is why Redis, JWTs (token contains the state), and cookie-based sessions exist — they let web servers become stateless while preserving session semantics.

---

### JWT as a Stateless Session

A JWT (JSON Web Token) encodes the user's identity and claims *inside the token* (signed by the server). The server doesn't store anything — it just validates the signature.

```
Stateful session:
  Server stores: { session_id: "abc" → user_id: 42, roles: ["admin"] }
  Client sends:  Cookie: session_id=abc

Stateless JWT:
  Client sends:  Authorization: Bearer eyJ... (token contains user_id, roles, expiry)
  Server:        Verify signature → extract claims → no DB lookup needed
```

Tradeoff: JWTs can't be invalidated before expiry without adding a blocklist (which reintroduces state).

---

## How These Three Patterns Interact

A real system combines all three:

```
User request (sync, stateless) 
→ API Gateway 
→ Order Service (stateless, pulls config from DB)
→ Payment Service (sync call for result)
→ Notification Service (async push via queue → push to mobile)
```

- The API call is **sync**
- The notification is **async**
- The API servers are **stateless** (scale freely)
- The WebSocket connection for live order tracking is **stateful, push**
