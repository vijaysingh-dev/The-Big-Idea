# Testing Microservices

#backend #microservices #testing

> **In one line:** End-to-end tests across services are slow, flaky and expensive, so the pyramid inverts into a diamond — most confidence comes from contract tests and integration tests against real dependencies, not from running the whole system.

---

## The Idea

```
Monolith:              Microservices:
      ╱E2E╲                  ╱E2E╲        ← a handful, and they hurt
   ╱ integ. ╲             ╱ contract ╲    ← the load-bearing layer
 ╱   unit    ╲          ╱ integration ╲
                      ╱     unit       ╲
```

💡 **In a monolith, integration tests are cheap — one process, one database.** In a microservice system, an integration test means several services, several databases, and a network between them.

⚠️ **The naive response is to write more end-to-end tests, and it is the wrong one.** They are slow, they fail for unrelated reasons, and a failure tells you something is broken without telling you what.

**The shape that works: heavy unit and integration testing per service, contract tests at every boundary, and a small number of end-to-end smoke tests.**

---

## The Layers

### Unit tests — no I/O

```python
def test_document_processor_rejects_oversized(fake_repo):
    processor = DocumentProcessor(fake_repo, max_bytes=1000)
    result = processor.validate(Document(size_bytes=2000))
    assert result.error == "too_large"
```

💡 **This works because the domain logic is separate from the transport** ([[08.5 - Task Design Rules]]). If your business logic imports `httpx` or `grpc`, it cannot be unit tested and the whole pyramid collapses.

**Most of your tests should be here**, and they should run in milliseconds.

### Integration tests — real dependencies, one service

```python
@pytest.fixture(scope="session")
def postgres():
    with PostgresContainer("postgres:17") as pg:
        yield pg.get_connection_url()


async def test_document_repository_enforces_tenant(db):
    await repo.create(org_a_doc)
    results = await repo.list(org_id=org_b)
    assert results == []
```

⚠️ **Test against a real database, not a mock.** A mocked repository verifies your mock, not your SQL — and the bugs are in the SQL: a missing index, a wrong join, an RLS policy that does not apply ([[06.16 - Multi Tenant Data Models]]).

💡 **Testcontainers makes this cheap enough to be the default.** A real Postgres, Redis and Kafka per test session, torn down afterwards.

**External services are stubbed here, not real.** You are testing your service against real infrastructure and fake collaborators.

### Contract tests — the boundary

```python
# In the CONSUMER's test suite
(pact.given("a document exists")
     .upon_receiving("a request for a document")
     .with_request("GET", "/documents/doc_42")
     .will_respond_with(200, body={"id": Like("doc_42"), "org_id": Like("org_7")}))
```

```python
# In the PROVIDER's test suite — replays the consumer's expectations
verifier.verify_with_broker(provider="documents-service", broker_url=PACT_BROKER)
```

💡 **The provider's own CI fails when it breaks a consumer, naming which consumer.** That is the property no other test layer gives you ([[05.13 - Contract Testing and Schema Evolution]]).

**Contract tests replace most integration tests between services**, and they run in each service's pipeline without the other service existing.

### End-to-end — a handful, and only the critical paths

```python
async def test_upload_becomes_searchable(deployed_env):
    doc = await api.upload("test.pdf")
    await wait_until(lambda: api.search("test content").contains(doc.id), timeout=60)
```

⚠️ **Keep these to a number you can count on one hand.** Login, the primary workflow, and payment. Everything else is covered by the layers below.

💡 **The reason to have any at all: they catch integration problems no unit or contract test can** — a misconfigured gateway route, a missing environment variable, an authorisation policy that blocks a real path.

**They are smoke tests, not a test suite.**

## Why E2E Tests Fail

Worth stating explicitly, because teams keep trying.

| Problem | |
|---|---|
| **Slow** | Minutes per test. A suite takes an hour |
| **Flaky** | Timing, async propagation, shared state. Retries hide real failures |
| **Expensive** | An environment with every service running |
| **Ambiguous** | A failure could be any of six services |
| **Shared state** | Tests interfere unless you isolate every entity |
| **Async timing** | "Wait until searchable" — how long? |

⚠️ **A flaky test suite is worse than no suite**, because it trains the team to re-run rather than investigate. **The first genuine failure gets re-run too.**

💡 **The measure: if your team's reflex on a red build is "re-run it", your E2E suite is a liability.** Delete the flaky tests rather than retrying them.

### Async makes assertion hard

```python
# ❌ Flaky
await api.upload("test.pdf")
assert await api.search("test").count() == 1        # indexing has not finished

# ⚠️ Better, still fragile
await asyncio.sleep(5)

# ✅ Poll with a bounded timeout
await wait_until(lambda: api.search("test").count() == 1, timeout=30, interval=0.5)
```

💡 **Never `sleep` in a test.** Poll for the condition with a generous timeout — it is faster in the common case and it does not break when a machine is slow ([[10.3 - Communication Patterns]]).

## Test Doubles

| Double | Use |
|---|---|
| **Stub** | Returns canned responses |
| **Fake** | A working lightweight implementation — an in-memory repository |
| **Mock** | Asserts on interactions |
| **Spy** | Records calls for later assertion |

⚠️ **Mocks that assert on interactions couple your tests to your implementation.** A refactor that changes call order breaks tests without breaking behaviour.

💡 **Prefer fakes over mocks.** An in-memory repository implementing the same interface tests behaviour, not calls.

```python
class InMemoryDocumentRepo(DocumentRepository):
    def __init__(self):
        self._docs: dict[str, Document] = {}

    async def create(self, doc: Document) -> Document:
        self._docs[doc.id] = doc
        return doc
```

⚠️ **A fake drifts from the real implementation.** Run the same test suite against both:

```python
@pytest.fixture(params=["fake", "postgres"])
def repo(request, db):
    return InMemoryDocumentRepo() if request.param == "fake" else PostgresDocumentRepo(db)
```

💡 **The same contract test suite against both implementations is what keeps a fake honest**, and it is a small amount of work for a large amount of confidence.

### Stubbing external services

```python
# Prism serves a mock from an OpenAPI spec
# WireMock for HTTP, or a hand-written stub
@pytest.fixture
def stripe_stub():
    with WireMockContainer() as wm:
        wm.stub_for("POST", "/v1/charges", returns={"id": "ch_test", "status": "succeeded"})
        yield wm.url
```

⚠️ **A stub encodes your belief about the external service, and beliefs go stale** ([[05.13 - Contract Testing and Schema Evolution]]).

💡 **For third-party APIs you cannot contract-test, record real responses and replay them** — VCR-style. **Re-record periodically**, and a diff in the recording is a signal the API changed.

## Testing the Hard Parts

### Idempotency

```python
async def test_concurrent_duplicates_produce_one_effect():
    key = str(uuid4())
    results = await asyncio.gather(
        *[create_payment(key, {"amount": 100}) for _ in range(20)],
        return_exceptions=True,
    )
    assert await count_payments() == 1
```

⚠️ **A sequential retry test passes against a broken implementation** ([[07.5 - Idempotency Keys and Deduplication]]). **Concurrency is where the bug lives.**

💡 **Add a deliberate delay between check and act in a test build** so the race is deterministic rather than occasional.

### Sagas and crash recovery

```python
@pytest.mark.parametrize("crash_at", ALL_CRASH_POINTS)
async def test_saga_recovers_consistently(crash_at):
    with crash_after(crash_at):
        await run_saga(order_id)
    await recover_sagas()
    assert await is_consistent(order_id)
```

💡 **Parameterising over every crash point is how you test a saga properly** ([[10.5 - Distributed Transactions and Sagas]]). A four-step saga has nine crash points and each must leave a recoverable state.

### Failure injection

```python
async def test_degrades_when_search_unavailable(toxiproxy):
    await toxiproxy.disable("search")
    response = await api.get_document("doc_42")
    assert response.status_code == 200                # ← degrades, does not fail
    assert response.json()["related"] == []
```

⚠️ **Degradation paths are almost never tested**, so they almost never work ([[11.6 - Graceful Degradation]]).

💡 **Toxiproxy in tests lets you assert on behaviour under failure** rather than hoping ([[00.4 - Setting Up Your Lab]]) — down, slow, and intermittently failing are all one API call away.

### Consumer replayability

```python
async def test_consumer_is_replayable():
    await consume_all(events)
    baseline = await snapshot_state()

    await reset_state_and_offsets()
    await consume_all(events)
    assert await snapshot_state() == baseline

    await consume_all(events)                          # replay on top
    assert await snapshot_state() == baseline
```

💡 **This test is what makes replay safe** ([[09.7 - Replay Backfill and Reprocessing]]), and it is cheap to write. **Without it, you discover the consumer is not idempotent during an incident.**

## In Production

### Test data

```python
@pytest.fixture
async def org(db):
    org = await create_org(name=f"test-{uuid4()}")
    yield org
    await delete_org(org.id)                      # ← cleanup
```

⚠️ **Shared test data across tests is the primary cause of flakiness.** Test A creates a document, test B counts documents, and the count depends on execution order.

💡 **Every test creates its own tenant.** With `org_id` on every table ([[06.10 - Schema Design]]), tests are naturally isolated and can run in parallel.

**This is a real benefit of the multi-tenant schema design that people do not anticipate.**

### Ephemeral environments

```yaml
# One environment per pull request
name: preview-${{ github.event.number }}
```

| | |
|---|---|
| **Good** | Real environment, no contention, testable by hand |
| **Bad** | Cost, provisioning time, data seeding |

💡 **Ephemeral environments are the practical alternative to a shared staging environment**, which is always broken by someone else's deploy.

⚠️ **Seeding realistic data is the hard part.** An empty environment does not catch the bugs that appear at scale ([[06.4 - Reading EXPLAIN ANALYZE]]).

### Testing in production

```python
# Synthetic monitoring — the E2E suite, running continuously
async def synthetic_check():
    doc = await api.upload(SYNTHETIC_FIXTURE, org_id=SYNTHETIC_ORG)
    found = await wait_until(lambda: api.search(...).contains(doc.id), timeout=60)
    synthetic_success.labels(check="upload_to_search").set(1 if found else 0)
```

💡 **A synthetic check running every minute catches integration failures your test suite cannot**, because it tests the real system with real configuration.

**It is the E2E test that earns its keep**, because a failure means production is broken now.

⚠️ **Use a dedicated synthetic tenant** so the data is isolated and can be cleaned up.

### The pipeline

```
Per commit:     unit + integration (testcontainers)     ~3 min
                contract tests (consumer + provider)     ~1 min
                schema compatibility check               ~10s
Per merge:      deploy to ephemeral env, smoke tests    ~10 min
Continuous:     synthetic checks in production           every 1 min
```

⚠️ **Nothing in the per-commit path should require another service to be running.** That is the property that keeps the pipeline fast and non-flaky.

💡 **Contract tests are what make that possible.** Without them, verifying a boundary requires the other service.

### The coverage that matters

| Property | Tested by |
|---|---|
| Business logic correct | Unit tests |
| SQL correct, indexes used | Integration with a real database |
| Tenant isolation | Integration, with a cross-tenant probe |
| **API contract honoured** | **Contract tests** |
| Idempotency under concurrency | Concurrent integration test |
| Saga recovers from any crash | Parameterised crash tests |
| Degrades when a dependency fails | Failure injection |
| Consumer is replayable | Replay test |
| **The deployed system works** | **Synthetic checks** |

💡 **Line coverage is a poor proxy for any of these.** A service at 95% line coverage with no contract tests, no crash tests and no failure injection is untested where it matters.

### Conduit's testing strategy

| Layer | Count | Runtime |
|---|---|---|
| Unit | ~600 | 8s |
| Integration (testcontainers) | ~120 | 3 min |
| Contract | ~20 | 40s |
| Crash / saga | ~15 | 90s |
| Failure injection | ~10 | 60s |
| E2E smoke | **4** | 5 min |
| Synthetic (production) | 3 checks | continuous |

💡 **Four E2E tests.** Upload-to-searchable, login, an annotation round trip, and organisation offboarding. **Everything else is covered lower down.**

⚠️ **The failure injection and crash tests are the ones a typical codebase lacks**, and they are the ones that verify the resilience work in sections 07, 08 and 11 actually functions.

## Codebase

**Repo:** `testcontainers/testcontainers-python`, `pact-foundation/pact-python`, `saleor/saleor`

**Question to answer:** How does testcontainers manage container lifecycle across a test session, and what makes it fast enough to use per-commit? Then: how does a large real project structure its test suite, and what is the ratio between layers?

**Read, in order:**

1. `testcontainers-python/core/testcontainers/core/container.py` — **container lifecycle and reuse.** Look for the session-scoped reuse mechanism, which is what makes it fast
2. `testcontainers-python/core/testcontainers/core/waiting_utils.py` — **readiness waiting.** How it knows a database is actually accepting connections, which is the difference between fast and flaky
3. `pact-python/src/pact/` — the consumer and provider sides. **How a pact file becomes both a mock and a verification**
4. `saleor/saleor/` — **count the tests by type.** `conftest.py` fixtures, and note how much real infrastructure they use versus mocking
5. `saleor/saleor/graphql/tests/` — API-level tests against a real database. **Note the fixture isolation strategy**

💡 The testcontainers wait strategies are worth attention, because **most test flakiness in integration suites is "the container started but the service inside is not ready yet".** Getting the readiness check right is what turns a flaky suite into a reliable one.

**Size:** 1 session.


**Part 1 — Build all four layers.** For one service: unit tests with no I/O, integration tests with testcontainers, contract tests with Pact, and two E2E tests.

**Measure the runtime and the failure isolation of each** — when a test fails, how quickly do you know what is broken?

**Part 2 — Prove a fake can lie.** An in-memory repository and a real Postgres one.

Write a test that passes against the fake and fails against the real one. **Candidates: a unique constraint, a cascade delete, an RLS policy, or a transaction rollback.**

Then run the same contract suite against both and confirm the drift is caught.

**Part 3 — The four hard parts.** For each, write the test that catches the bug:

- **Idempotency:** 20 concurrent duplicates, assert one effect. Then break the implementation and confirm the test fails
- **Saga:** parameterise over nine crash points, assert consistency after recovery
- **Failure injection:** with toxiproxy, take a dependency down and assert graceful degradation. Then remove the degradation handling and confirm the test fails
- **Replayability:** consume, snapshot, reset, re-consume, assert identical. Then make the consumer accumulate and confirm it fails

**All four should catch a deliberately introduced bug.** A test that cannot fail is not a test.

**Part 4 — Measure flakiness.** Write three deliberately flaky tests: shared state with order dependence, a `sleep`-based assertion, and one depending on wall-clock timing.

**Run the suite 100 times and count failures for each.**

Then fix all three — per-test tenants, polling, and injected time. **Run 100 times again.**

**Report the flakiness rate before and after.** Anything above zero is a liability.

**Part 5 — Contract tests replace integration.** Take three cross-service integration tests requiring both services running.

**Replace them with contract tests.** Measure: runtime, infrastructure required, and whether they still catch a breaking change.

Then break the provider and confirm the provider's own CI fails, naming the consumer.

**Part 6 — The pipeline.** Assemble the full pipeline with the timing targets from this note.

**Measure total per-commit time.** If it exceeds five minutes, find what to move to a later stage.

Then deliberately introduce five bugs — a logic error, a SQL error, a contract break, a missing config value, and a broken deployment manifest — and **measure which layer catches each and how quickly.**

**Part 7 — Synthetic checks.** Three production checks: upload-to-searchable, login, and a health probe touching every dependency.

**Then break something in a staging environment that no test caught** — a misconfigured route, a missing secret — and confirm the synthetic check detects it.

**Measure time to detection.**

**Part 8 — The ADR.** Conduit's testing strategy: the count and runtime per layer, what each layer is responsible for, and what you deliberately do not test.

**Justify your E2E count.** If it is more than five, explain why.

**Done when:**
- Your fake demonstrably lies, and a shared suite catches it
- All four hard-part tests fail when you introduce the corresponding bug
- Your flakiness rate is zero across 100 runs
- Contract tests replaced integration tests with no loss of coverage
- Your per-commit pipeline runs in under five minutes
- Five injected bugs are each caught by the appropriate layer
- A synthetic check caught something no test did
