# Subflows and Reusability

## The problem

Without reuse, the same logic gets rebuilt in every flow that needs it. Coverage checking appears in the claim intake flow, the case escalation flow, and the renewal flow — three copies that drift apart, and a rule change means finding and editing all three.

A **subflow** is an autolaunched flow called from another flow. It is flow's equivalent of a method.

## How it works

The called flow declares variables as **Available for Input** and **Available for Output**. The calling flow uses a Subflow element, maps values in, and reads values out.

```
Subflow: Check_Asset_Coverage

Inputs:
    assetId          ← {!$Record.Asset__c}
    checkDate        ← {!$Record.Claim_Date__c}

Outputs:
    isCovered        → {!hasCoverage}
    coverageLevel    → {!coverageTier}
    contractId       → {!activeContractId}
```

Only autolaunched flows can be subflows. A screen flow cannot be called as a subflow from a record-triggered flow, because the triggered context has no user interface. A screen flow *can* call another screen flow as a subflow, which is how multi-step wizards are composed.

## What to extract

The judgement is the same as for extracting a method.

**Extract when:**
- The same logic appears in two or more flows
- The logic represents a business rule likely to change independently
- A flow has grown past the point where the canvas is readable
- Different teams own different parts of a process

**Do not extract when:**
- It is used once and is unlikely to be reused
- The input and output mapping is more complex than the logic itself
- It is three elements

That last point matters. A subflow has real overhead — a separate flow to maintain, version, and deploy, plus the mapping at every call site. Extracting a two-element sequence makes the system harder to follow, not easier.

## A library worth building

For the Northwind model, the reusable pieces that earn their place:

**`Check_Asset_Coverage`** — given an asset and a date, return whether it is covered, at what level, and by which contract. Used by claim intake, case creation, and field service dispatch.

**`Resolve_Case_Owner`** — given a case's attributes, return the correct queue or user. Used by several intake paths.

**`Log_Automation_Error`** — given a context string and a message, write to the log object. Called from every fault path in the org.

**`Send_Templated_Notification`** — given a recipient, a template, and a record, send a custom notification. Centralizes notification behaviour so a change to how notifications work is one edit.

Each of these is a business rule that appears in several places and changes independently of the processes using it. That is the test.

## Composing one flow per object

Section 07.3 recommends one record-triggered flow per object per timing, to make execution order explicit. The obvious objection is that a single flow handling every concern on Case becomes an enormous canvas that several administrators cannot work on at once.

Subflows resolve this:

```
Case_AfterSave (the single entry point)
    Decision: what changed?
        Status changed to Escalated  → Subflow: Case_Handle_Escalation
        Status changed to Closed     → Subflow: Case_Handle_Closure
        Owner changed                → Subflow: Case_Handle_Reassignment
        Entitlement is null          → Subflow: Case_Assign_Entitlement
```

One entry point, so ordering is explicit and visible. Modular internals, so each concern is a separate flow that can be changed and versioned independently. The entry flow itself rarely changes.

This is the structural equivalent of the trigger handler pattern in [[11.5 - Trigger Handler Pattern]] — a thin dispatcher routing to focused units — and it works for the same reasons.

## Limits carry across

A subflow does **not** get fresh governor limits. It runs in the same transaction and draws from the same budget.

Two consequences:

**A subflow with a Get Records inside a loop is exactly as damaging as one in the parent.** Extraction hides the cost without removing it, which makes it easier to accumulate accidentally.

**Nesting depth compounds.** A flow calling a subflow calling a subflow, each with a query, is three queries per record. On a bulk save of 200 records, that is 600 against a limit of 100.

Reviewing a flow's total limit consumption means reviewing the whole call tree, not the entry flow. This is genuinely harder than the equivalent in Apex, where the call stack is visible in one place.

## Invocable Apex as a shared building block

Where the reusable logic is complex, bulk-sensitive, or needs a callout, the right unit of reuse is **invocable Apex** rather than a subflow.

```java
public with sharing class CoverageCheckAction {

    public class Request {
        @InvocableVariable(required=true label='Asset Id') public Id assetId;
        @InvocableVariable(required=true label='Check Date') public Date checkDate;
    }

    public class Result {
        @InvocableVariable public Boolean isCovered;
        @InvocableVariable public String coverageLevel;
        @InvocableVariable public Id contractId;
    }

    @InvocableMethod(label='Check Asset Coverage'
                     description='Returns active service contract coverage for an asset on a date')
    public static List<Result> check(List<Request> requests) {
        Set<Id> assetIds = new Set<Id>();
        for (Request req : requests) {
            assetIds.add(req.assetId);
        }

        // one query for every request, which a subflow cannot do
        Map<Id, Machine_Coverage__c> coverageByAsset = new Map<Id, Machine_Coverage__c>();
        for (Machine_Coverage__c coverage : [
            SELECT Asset__c, Coverage_Level__c, Service_Contract__c,
                   Coverage_Start_Date__c, Coverage_End_Date__c
            FROM Machine_Coverage__c
            WHERE Asset__c IN :assetIds
              AND Service_Contract__r.Status__c = 'Active'
            ORDER BY Coverage_End_Date__c DESC
        ]) {
            if (!coverageByAsset.containsKey(coverage.Asset__c)) {
                coverageByAsset.put(coverage.Asset__c, coverage);
            }
        }

        List<Result> results = new List<Result>();
        for (Request req : requests) {
            Result result = new Result();
            Machine_Coverage__c coverage = coverageByAsset.get(req.assetId);
            result.isCovered = coverage != null
                && coverage.Coverage_Start_Date__c <= req.checkDate
                && coverage.Coverage_End_Date__c >= req.checkDate;
            if (result.isCovered) {
                result.coverageLevel = coverage.Coverage_Level__c;
                result.contractId = coverage.Service_Contract__c;
            }
            results.add(result);
        }
        return results;
    }
}
```

The advantage over a subflow is stated in that first query: **invocable Apex receives all the records at once and can query once for all of them.** A subflow called from a record-triggered flow on 200 records runs 200 times and queries 200 times.

For anything called in a bulk context, this is not a marginal difference. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Versioning and change control

A subflow is a shared dependency, which brings the usual consequences.

**Changing a subflow affects every caller.** There is no way to version a subflow interface — activating a new version changes behaviour for all callers immediately.

**Removing an output variable breaks callers**, and the break is discovered at runtime rather than at save time.

**There is no dependency view that shows callers reliably.** Finding what calls a subflow means searching the flow metadata:

```bash
grep -rl "Check_Asset_Coverage" force-app/main/default/flows/
```

That grep, run before changing a shared subflow, is the practical substitute for a dependency graph.

The discipline that follows: **treat a subflow's inputs and outputs as an interface.** Add to it freely; change or remove from it only with a search for callers first.

## Practical guidance

**Extract logic used in two or more places**, not logic that is merely long.

**Build a small library of genuinely shared rules** rather than extracting everything.

**Use subflows to keep one-flow-per-object readable.**

**Remember limits do not reset.** Review the whole call tree.

**Prefer invocable Apex for anything bulk-sensitive.** A subflow cannot batch across records.

**Search for callers before changing a subflow's interface.**

**Name subflows by what they do, not where they are called from.** `Check_Asset_Coverage`, not `Claim_Flow_Step_2`.
