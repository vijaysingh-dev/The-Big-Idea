# Case Assignment and Auto-Response Rules

## The routing problem

A case arrives. Something must decide who works it, and the decision depends on product, language, region, severity, entitlement tier, and who is actually available right now.

Salesforce offers three mechanisms at increasing levels of capability, and choosing the right one is the design decision:

**Assignment rules** — criteria to a user or queue. Simple, declarative, no awareness of availability.
**Omni-Channel** — capacity and skill-based distribution to agents who are online. See [[05.7 - Omni-Channel Routing]].
**Apex or flow** — anything the first two cannot express.

Most real implementations use assignment rules to place cases into the right queue, then Omni-Channel to distribute from that queue to an available agent. The two are complementary rather than alternatives.

## Assignment rules

An ordered list of rule entries. The first entry whose criteria match wins, and evaluation stops.

```
Rule: Standard Case Assignment

1. Type = "Warranty Claim" AND Product_Line__c = "Press"     → Queue: Press Warranty
2. Type = "Warranty Claim"                                    → Queue: General Warranty
3. Priority = "Critical"                                      → Queue: Tier 2 Support
4. Origin = "Chat"                                            → Queue: Chat Support
5. (no criteria)                                              → Queue: Unassigned Cases
```

**Only one assignment rule can be active per object at a time.** Everything lives in that rule's entries, which is why ordering is the whole design.

Entry five is the pattern to always include. Without a catch-all, cases matching nothing keep whatever owner they were created with — for Email-to-Case that is the automated case user, for an integration it is the integration user. Cases silently owned by a system user are invisible to everyone, and they are the classic source of "we never received your email".

## When rules run, and when they do not

Assignment rules run at step 9 of the order of execution, **after** before and after triggers ([[07.13 - Order of Execution]]). A trigger cannot see the assigned owner.

They **do not run for records created through the API or Apex** unless explicitly requested. Through the UI there is a checkbox; through code there is a DML option.

```java
public with sharing class CaseIntakeService {

    public static void createWithRouting(List<Case> cases) {
        Database.DMLOptions options = new Database.DMLOptions();
        options.assignmentRuleHeader.useDefaultRule = true;
        options.emailHeader.triggerAutoResponseEmail = true;
        options.emailHeader.triggerUserEmail = true;

        for (Case c : cases) {
            c.setOptions(options);
        }

        Database.insert(cases, false);
    }
}
```

This is the same trap described for leads in [[04.3 - Lead Assignment Rules and Queues]], and it is worth restating because the failure is silent in both cases.

Assignment rules can also run **on update**, which assignment rules for Lead cannot. A rule entry can be configured to re-evaluate when the case is edited, which is how a case that changes product line gets rerouted. This is powerful and needs care — a rule that reassigns on every edit will take cases away from agents mid-work.

## Queues for support

Queues hold unassigned cases ([[03.12 - Public Groups, Queues and Territory Management]]). For support the typical structure mirrors the escalation path:

```
Tier 1 Support          → general triage, all channels
Tier 2 Technical        → product specialists
Press Warranty          → warranty claims on a specific product line
Field Dispatch          → cases requiring an on-site visit
Billing Enquiries       → finance team
```

Queue members see the queue's list view and claim cases by taking ownership.

The weakness of queues alone: **they do not distribute.** Everyone sees everything, and cases are claimed unevenly — easy cases get taken quickly and hard ones sit. This is precisely the gap Omni-Channel fills, and it is the main argument for adopting it.

## Skills-based and capacity-based routing

When routing needs to consider language, product certification, or current workload, assignment rules cannot express it because criteria only see the case record.

Omni-Channel with **skills-based routing** handles this natively: skills are defined, agents are assigned skills with proficiency levels, and work items carry skill requirements. See [[05.7 - Omni-Channel Routing]].

Where Omni-Channel is not in use, or where routing depends on something outside Salesforce, Apex sets the owner in a before-insert handler with a catch-all assignment rule behind it:

```java
public with sharing class CaseRoutingService {

    public static void route(List<Case> cases) {
        Map<String, Id> queueByKey = getQueueMap();

        for (Case c : cases) {
            String key = buildRoutingKey(c);
            Id queueId = queueByKey.get(key);
            if (queueId != null) {
                c.OwnerId = queueId;
            }
        }
    }

    private static String buildRoutingKey(Case c) {
        String product = String.isBlank(c.Product_Line__c) ? 'ANY' : c.Product_Line__c;
        String language = String.isBlank(c.Language__c) ? 'EN' : c.Language__c;
        return c.Type + '|' + product + '|' + language;
    }

    private static Map<String, Id> getQueueMap() {
        Map<String, String> queueNameByKey = new Map<String, String>();
        for (Case_Routing__mdt routing : Case_Routing__mdt.getAll().values()) {
            queueNameByKey.put(
                routing.Case_Type__c + '|' + routing.Product_Line__c + '|' + routing.Language__c,
                routing.Queue_Developer_Name__c
            );
        }

        Map<String, Id> result = new Map<String, Id>();
        Map<String, Id> queueIdByName = new Map<String, Id>();
        for (Group q : [
            SELECT Id, DeveloperName FROM Group
            WHERE Type = 'Queue' AND DeveloperName IN :queueNameByKey.values()
        ]) {
            queueIdByName.put(q.DeveloperName, q.Id);
        }

        for (String key : queueNameByKey.keySet()) {
            result.put(key, queueIdByName.get(queueNameByKey.get(key)));
        }
        return result;
    }
}
```

Custom Metadata driving the routing map means adding a product line or a language is a deployment of records, not a code change. `getAll()` consumes no SOQL query. Queues are resolved by developer name because IDs differ per org. See [[17.1 - Custom Metadata Types]].

## Auto-response rules

Separate from assignment, and often confused with it. An auto-response rule sends an acknowledgement email when a case is created, selecting the template by criteria.

```
1. Type = "Warranty Claim"    → Template: Warranty Claim Received
2. Priority = "Critical"       → Template: Critical Issue Acknowledgement
3. (no criteria)               → Template: Standard Case Acknowledgement
```

Same structure, same first-match-wins evaluation, same one-active-rule limit.

The value is disproportionate to the effort: an immediate acknowledgement with a case number substantially changes perceived responsiveness, and it prevents the customer sending three more emails because they heard nothing.

The limitations: it fires only on creation, not on update, and the sender address must be a verified organization-wide email address or it will fail silently in some configurations.

## Assignment notification

The assignment rule can email the new owner. For a queue, that means every member.

In practice email notification of queue assignment is noise, and most implementations disable it in favour of the queue list view, Omni-Channel push, or a custom notification for high-priority cases only.

```java
Messaging.CustomNotification notification = new Messaging.CustomNotification();
notification.setTitle('Critical case assigned');
notification.setBody(c.CaseNumber + ' — ' + c.Subject);
notification.setNotificationTypeId(criticalCaseNotificationTypeId);
notification.setTargetId(c.Id);
notification.send(recipientIds);
```

Custom notifications reach the mobile app and the desktop bell, which is meaningfully faster than email.

## Practical guidance

**Always include a catch-all entry.** Unassigned cases are the most common invisible failure in Service Cloud.

**Set the DML flags on every integration and Email-to-Case handler.**

**Route to queues, not individuals.** People go offline, take leave, and change teams.

**Use assignment rules for queue placement and Omni-Channel for agent distribution.** Rules answer "which team", Omni-Channel answers "which person, right now".

**Drive routing configuration from Custom Metadata** when it is more complex than a handful of entries. Forty rule entries is unmaintainable.

**Be careful with reassignment on update.** Taking a case from an agent mid-work is disruptive, and the rule should exclude cases already in progress.
