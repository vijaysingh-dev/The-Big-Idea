# Chaos and Failure Injection

#backend #reliability #testing

> **In one line:** Every resilience mechanism you built in section 11 is a hypothesis until you have broken something on purpose and watched it hold.

---

## The Idea

```
You added:  timeouts, retries, circuit breakers, bulkheads,
            load shedding, degradation paths, graceful shutdown

You verified: none of it
```

⚠️ **A defence that has never been exercised does not work.** Circuit breakers with thresholds nobody tuned, degradation paths that throw on the fallback line, retry budgets that were never wired in — **all common, all invisible until an incident.**

💡 **Chaos engineering is not "randomly break production".** It is: form a hypothesis about how the system behaves under a specific failure, inject that failure in a controlled way, and check whether reality matches.

**The value is in the hypotheses that turn out to be wrong.**

---

## The Method

```
1. Define steady state          — a metric that says "healthy"
2. Form a hypothesis            — "if X fails, steady state holds"
3. Inject the failure           — smallest blast radius that tests it
4. Observe                      — did steady state hold?
5. Stop                         — automatically, if it did not
6. Write down what surprised you
```

💡 **Step 1 is where most attempts fail.** "The system is healthy" is not measurable; **"checkout success rate stays above 99% and p99 stays below 800ms" is.**

```python
STEADY_STATE = {
    "checkout_success_rate": lambda: rate > 0.99,
    "p99_latency_ms": lambda: p99 < 800,
    "error_rate": lambda: rate < 0.01,
}
```

⚠️ **Step 5 is what makes this safe.** An experiment that cannot be aborted automatically should not run against anything that matters.

---

## What to Inject

| Failure | Tests |
|---|---|
| **Dependency down** | Circuit breakers, degradation ([[11.6 - Graceful Degradation]]) |
| **Dependency slow** | Timeouts, bulkheads. **The more important one** ([[11.1 - How Systems Fail]]) |
| Dependency intermittent | Retry logic, retry budgets |
| Process killed | Restart, in-flight work handling |
| **Node lost** | Replica spread, PDBs ([[10.10 - Deployment Strategies]]) |
| Zone lost | Cross-zone capacity |
| Network partition | Split brain, quorum ([[06.12 - Replication and Failover]]) |
| Clock skew | Token expiry, lease logic |
| **Disk full** | The one nobody tests |
| Cache flush | Cold-start survival ([[07.3 - Stampede Hot Keys and Negative Caching]]) |
| Certificate expiry | Correlated failure |

💡 **Slow is the highest-value injection**, because "down" fails fast and cleanly while "slow" is what actually exhausts your resources.

⚠️ **Disk full is the most under-tested.** Logs fill a volume, WAL accumulates behind a replication slot ([[06.7 - MVCC Vacuum and Bloat]]), and the failure mode is usually total and confusing.

## The Tools

### Application-level: toxiproxy

```python
proxy = toxiproxy.create(name="postgres", listen="0.0.0.0:5433", upstream="postgres:5432")

proxy.add_toxic(type="latency", attributes={"latency": 3000, "jitter": 500})
proxy.add_toxic(type="timeout", attributes={"timeout": 0})          # black hole
proxy.add_toxic(type="bandwidth", attributes={"rate": 10})          # 10 KB/s
proxy.add_toxic(type="slicer", attributes={"average_size": 64})     # fragment packets
```

💡 **Toxiproxy is the right tool for test-suite failure injection** ([[10.9 - Testing Microservices]]). It sits between your application and a dependency, it is controllable from code, and it needs no cluster-level permissions.

**Put it in your integration test stack from the start.**

### Kubernetes-level: Chaos Mesh, LitmusChaos

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
spec:
  action: delay
  mode: one
  selector:
    labelSelectors: {app: search}
  delay: {latency: "2s", jitter: "500ms"}
  duration: "5m"
```

**Pod kills, network delay and loss, partitions, DNS failures, IO faults, time skew.**

⚠️ **These operate at the infrastructure layer, so the blast radius is larger and the safety controls matter more.** Always set a `duration`, always scope with a selector, and always have an abort path.

### Infrastructure-level: AWS FIS, Gremlin

Instance termination, AZ failure, API throttling. **Closest to real failures, hardest to control.**

## Blast Radius

```
1. A single test, against a stub          — free, run in CI
2. Staging, full environment              — cheap, run nightly
3. Production, one pod                    — small, run weekly
4. Production, one zone                   — significant, run quarterly
5. Production, a whole region             — rare, planned, announced
```

💡 **Start at level 1 and stay there until it is boring.** Most of the value is at levels 1 and 2 — **a failure-injection test suite catches more than a production game day, and it catches it before it ships.**

⚠️ **Level 3 and above requires: an abort mechanism, a defined steady state, an announced window, and someone watching.** Anything less is not an experiment, it is an incident you caused.

### Automatic abort

```python
async def run_experiment(experiment, steady_state, max_duration=300):
    await experiment.start()
    try:
        deadline = time.monotonic() + max_duration
        while time.monotonic() < deadline:
            if not await steady_state.holds():
                log.error("steady state violated, aborting")
                return ExperimentResult.HYPOTHESIS_DISPROVED
            await asyncio.sleep(5)
        return ExperimentResult.HYPOTHESIS_HELD
    finally:
        await experiment.stop()                 # ← always
```

⚠️ **The `finally` is the whole safety story.** An experiment that leaves an injected fault running because the harness crashed is a self-inflicted outage.

**Add a dead man's switch too** — the injection expires on its own if the controller stops, which is what Chaos Mesh's `duration` field does.

## Game Days

The human version, and it tests things automation cannot.

```
1. Announce the window and the scenario
2. Assemble the on-call team
3. Inject the failure
4. The team responds using only runbooks and dashboards
5. Debrief: what was missing, what was wrong, what took too long
```

💡 **A game day tests your runbooks, dashboards and people, not just your code.** The most common findings are that a dashboard does not exist, an alert does not fire, or a runbook step references a tool nobody has access to.

⚠️ **Do not have the person who built the system run the game day.** They know where to look, which is exactly what you are trying to test.

**Rotate who leads the response**, and let the newest team member drive at least once.

## In Production

### The experiment catalogue

```markdown
### EXP-004: Redis unavailable

**Steady state:** document read p99 < 500ms, error rate < 1%
**Hypothesis:** the cache is optional; requests fall through to Postgres.
Database load rises ~20× and remains within capacity.
**Injection:** toxiproxy black-holes Redis for 5 minutes
**Blast radius:** staging, then production single pod
**Abort if:** database pool wait > 500ms, or error rate > 1%
**Last run:** 2026-08-12  **Result:** HYPOTHESIS DISPROVED —
database pool exhausted at 90 seconds. Fixed by adding load shedding at
pool pressure > 0.8. Re-ran 2026-08-19: held.
```

💡 **The "last run" and "result" fields are what make the catalogue valuable.** An experiment run once and never repeated tells you about a system that no longer exists.

**Re-run the whole catalogue quarterly**, and after any significant architectural change.

### Start with the failures you have already had

⚠️ **Do not start with random injection.** Start with your own postmortems.

```
Every incident → an experiment that reproduces it
Every experiment → runs forever, so the regression cannot return
```

💡 **This turns your incident history into a regression suite**, and it is the highest-value chaos work available. **An incident that can recur is a test you have not written.**

### The findings that recur

Across teams, the same discoveries come up:

| Finding | |
|---|---|
| Timeouts missing on one client | Usually a library added later |
| A degradation path that throws | Never exercised |
| An alert that does not fire | Threshold wrong, or the metric was renamed |
| A runbook referencing a deleted dashboard | |
| **Retry amplification** | Nested retries nobody counted ([[11.2 - Timeouts Retries and Jitter]]) |
| **Cache outage exceeding database capacity** | The 20× spike |
| A liveness probe checking a dependency | Cascading restarts |
| Grace period shorter than the longest task | Work redone every deploy |

⚠️ **If your first game day finds none of these, you probably did not inject hard enough.**

### Measuring the programme

```python
chaos_experiments_run_total.labels(experiment=..., result=...).inc()
chaos_hypotheses_disproved_total.inc()
chaos_mean_time_to_detect_seconds.observe(elapsed)
chaos_experiment_coverage.set(experiments / dependencies)
```

💡 **`chaos_hypotheses_disproved_total` going to zero is not success — it means your experiments have stopped being interesting.** Add harder ones.

**Track mean time to detect across game days.** It should fall as dashboards and alerts improve, and that trend is the clearest evidence the programme is working.

### What not to do

⚠️ **Do not run chaos in production without:**

```
□  A defined, measurable steady state
□  An automatic abort
□  A time-bounded injection that expires on its own
□  An announced window
□  Someone watching who can stop it
□  A rollback that does not depend on the thing you broke
```

**The last one catches people.** If your abort mechanism calls an API that goes through the dependency you just black-holed, you cannot abort.

### Conduit's experiment set

| ID | Injection | Hypothesis |
|---|---|---|
| EXP-001 | Search service down | Document pages load; search shows "unavailable" |
| EXP-002 | **Search service slow (5s)** | Circuit opens within 10s; no worker exhaustion |
| EXP-003 | Postgres replica lag 30s | Read-your-writes still correct via LSN tracking |
| EXP-004 | **Redis unavailable** | Falls through to Postgres within capacity |
| EXP-005 | Kafka unavailable | Outbox accumulates; no events lost ([[09.3 - The Outbox Pattern]]) |
| EXP-006 | Embedding API 429s | Tasks retry with backoff; queue drains after |
| EXP-007 | Kill a worker mid-task | Task requeued and completed exactly once |
| EXP-008 | **Primary Postgres down** | Read-only mode within 60s ([[11.6 - Graceful Degradation]]) |
| EXP-009 | Node lost | No user-visible impact; PDB respected |
| EXP-010 | Certificate 24h from expiry | Alert fires |

💡 **EXP-002 and EXP-004 are the two most likely to fail**, and they are the ones worth running first. **Slow-not-down and cache-outage-load-spike are where most systems are quietly broken.**

## Codebase

**Repo:** `Shopify/toxiproxy`, `chaos-mesh/chaos-mesh`, `Netflix/chaosmonkey`

**Question to answer:** How does toxiproxy inject latency without the application knowing, and what toxic types exist beyond latency? Then: how does Chaos Mesh ensure an injected fault is removed if the controller dies?

**Read, in order:**

1. `Shopify/toxiproxy/toxics/` — **read three or four toxics.** `latency.go`, `timeout.go`, `bandwidth.go`, `slicer.go`. **Each is small, and the set tells you what failures are worth simulating**
2. `Shopify/toxiproxy/link.go` — how a toxic is inserted into the proxied stream. **The interception mechanism**
3. `chaos-mesh/pkg/chaosdaemon/` — how faults are applied to a pod: `tc` for network, `iptables` for partitions, `cgroups` for CPU
4. `chaos-mesh/controllers/` — **the reconcile loop and `duration` handling.** **The answer to the second question**: the fault has an expiry recorded in the object, so it is removed even if the controller restarts
5. `Netflix/chaosmonkey` — the original. **Read the README for the philosophy**, which is more valuable than the code

💡 The toxiproxy toxic list is the most useful single artefact here. **`slicer` — fragmenting packets to simulate a lossy path — and `bandwidth` are failures most people never think to test**, and both surface bugs that latency injection does not.

**Size:** 1 session.

## Exercise

**Drill 11.9 — Disprove your own hypotheses**

```
drills/11-chaos/
├── harness/{experiment.py, steady_state.py, abort.py}
├── injection/{toxiproxy.py, chaos_mesh/, tests/}
├── catalogue/{experiments.md, results/}
├── from_incidents/{postmortem_to_experiment.py}
├── gameday/{runbook.md, debrief_template.md}
└── README.md
```

**Part 1 — Build the harness.** Steady-state definitions as code, an experiment runner with automatic abort, and a `finally` that always removes the injection.

**Test the harness itself:** kill it mid-experiment and **confirm the injection is removed anyway.** If it is not, fix that before injecting anything else.

**Part 2 — Write ten hypotheses.** Conduit's ten experiments, each with a measurable steady state, an explicit hypothesis, an injection, an abort condition, and a blast radius.

⚠️ **Write the hypothesis before running it.** Writing it afterwards is describing what happened, not testing a belief.

**Part 3 — Run them all, at level 2.** Staging, full environment, realistic load.

**Record which hypotheses were disproved.** For each: what actually happened, why your model was wrong, and what you changed.

**Target: at least three disproved.** If none are, your injections are too gentle or your hypotheses too vague.

**Part 4 — The two most likely failures.**

**EXP-002 (dependency slow):** confirm the circuit opens within your stated time and that unrelated endpoints stay healthy. **Then remove the bulkhead and confirm the failure spreads** ([[11.3 - Circuit Breakers and Bulkheads]]).

**EXP-004 (Redis down):** confirm the database absorbs the ~20× spike. **Measure pool wait time and p99 throughout.** If it does not hold, implement load shedding and re-run until it does.

**Part 5 — Incidents into experiments.** Take three past incidents — real, or from published postmortems if you have none.

**For each, write an experiment that reproduces the failure condition**, and confirm your current system survives it.

💡 **These experiments run forever. An incident that can recur is a test you have not written.**

**Part 6 — A game day.** Announce a window, assemble whoever you can, and inject a failure **without telling the responder which one.**

Measure: time to detection, time to correct diagnosis, time to mitigation. **Record every moment the responder needed information that did not exist.**

**Then fix those gaps and repeat with a different failure.** The second run should be measurably faster.

**Part 7 — Automate the catalogue.** Wire the experiment set into CI at level 1 (against stubs) and into a nightly staging run at level 2.

**Then deliberately regress something** — remove a timeout, break a degradation path — and **confirm the automated run catches it.**

**Done when:**
- Killing the harness still removes the injection
- Ten hypotheses are written before running, with measurable steady states
- At least three hypotheses were disproved and fixed
- Slow-dependency and cache-outage experiments both hold after fixes
- Three past incidents have permanent regression experiments
- A second game day is measurably faster than the first
- An automated run catches a deliberately introduced regression
