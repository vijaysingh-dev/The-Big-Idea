# Notification Systems

> **Revision tags:** #building-blocks #notifications

## What It Is

A notification system delivers messages to users across one or more channels (push, email, SMS, in-app) triggered by system events or user actions.

```
Event: OrderShipped
  → Notification Service
      ├── Push notification (mobile)
      ├── Email (confirmation with tracking link)
      └── SMS (if user opted in)
```

---

## Why It Exists

Notification delivery is harder than it looks:
- Multiple channels with different delivery protocols
- Fan-out at scale (millions of users, one event)
- User preferences (opt-ins, quiet hours, channel choice)
- Delivery guarantees (did the user get it?)
- Deduplication (don't send the same alert twice)
- Rate limiting (don't spam users)

Centralizing this in a dedicated service prevents every product team from re-implementing it.

## Notification Channels

### Push Notifications (Mobile)

Delivered via platform-specific services:
- **APNs** (Apple Push Notification service) — iOS/macOS
- **FCM** (Firebase Cloud Messaging) — Android + cross-platform

```
Your Server → APNs/FCM → Device
```

Your server never connects directly to the device. APNs/FCM maintain persistent connections to all registered devices.

**Device token:** When a user installs the app, the OS registers with APNs/FCM and returns a device token. Your app sends this token to your backend and stores it against the user.

```
Notification flow:
1. User installs app → OS registers → device_token = "abc123"
2. App sends token to your backend: POST /devices { user_id: 42, token: "abc123" }
3. Backend stores (user_id → token) mapping
4. Event triggers notification: lookup token for user 42 → send to APNs/FCM
```

**Challenges:**
- Tokens expire or change (app reinstall, OS upgrade)
- Silent push (background data sync) vs visible notification
- iOS requires explicit user permission; Android grants by default (changes in Android 13+)

### Email

Delivered via SMTP or a managed email API.

**Don't run your own SMTP server.** Managing email deliverability (SPF, DKIM, DMARC records, IP reputation, bounce handling, ISP relationships) is a full-time job.

**Managed providers:** SendGrid, Amazon SES, Mailgun, Postmark.

```
Your service → SendGrid API → SendGrid SMTP infrastructure → Recipient inbox
```

**Email-specific concerns:**
- **Bounce handling:** Hard bounce (invalid address) → remove from list. Soft bounce (mailbox full) → retry.
- **Unsubscribe handling:** CAN-SPAM / GDPR require one-click unsubscribe. The provider usually handles this.
- **Deliverability:** Warm up new IP/domain gradually. Monitor spam complaint rate.
- **Templating:** HTML email rendering is inconsistent across clients. Use tested templates (MJML, Cerberus).

### SMS

Delivered via telephony providers: Twilio, AWS SNS, Vonage.

**Concerns:**
- Cost per message (higher than email)
- Character limits (160 chars for standard SMS, concatenation for longer)
- International delivery reliability varies by country/carrier
- Regulations (TCPA in US — must have consent, provide opt-out)
- OTP use case: short TTL codes, verify delivery receipt

### In-App / Web Push

Delivered while the user has the app/website open (or via browser Web Push API when not on site).

- **In-app:** WebSocket or SSE connection; server pushes to connected client
- **Web push:** Browser Push API (uses FCM/Mozilla Push Service); works when browser is running even without the site open

## System Architecture

### Components

```
[Event Sources]       → order-service, payment-service, etc.
      │ events
      ▼
[Notification Service]
  ├── [Preference Store]   → user channel prefs, opt-outs, quiet hours
  ├── [Template Engine]    → render message content per channel
  ├── [Fan-out Workers]    → one per channel type
  │     ├── [Push Worker]  → calls APNs / FCM
  │     ├── [Email Worker] → calls SendGrid
  │     └── [SMS Worker]   → calls Twilio
  ├── [Rate Limiter]       → per-user notification frequency limits
  └── [Delivery Log]       → record sent/failed/opened per notification
```

### Fan-Out at Scale

Sending a notification to 10 million users on a single event (e.g., a product launch, a breaking news alert) requires massive fan-out.

**Naive approach:** Loop over all 10M users and call APNs/FCM per user → serial, takes hours.

**Production approach:**

```
Event → Notification Service → Kafka topic "notifications"
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
        Push Worker 1          Push Worker 2          Push Worker N
      (partition 0)           (partition 1)           (partition N)
   sends to 100K users       sends to 100K users     sends to 100K users
        in parallel               in parallel             in parallel
```

Partition users across Kafka partitions → N workers run in parallel → 10M notifications in minutes.

**APNs/FCM batch APIs:** Both support bulk sending — send up to 500 device tokens per API call. Workers batch tokens before calling.

## User Preference Management

Users must be able to control what they receive and how.

```
User preferences schema:
{
  user_id: 42,
  channels: {
    push: true,
    email: true,
    sms: false
  },
  categories: {
    order_updates: { push: true, email: true },
    marketing: { push: false, email: false },
    security_alerts: { push: true, email: true, sms: true }
  },
  quiet_hours: { start: "22:00", end: "08:00", timezone: "Asia/Kolkata" }
}
```

Notification service checks preferences before dispatching. Security alerts may bypass quiet hours (critical). Marketing never does.

## Deduplication

Retries can cause the same notification to be sent twice. Prevent duplicates:

```python
def send_notification(notification_id, user_id, channel, content):
    dedup_key = f"notif_sent:{notification_id}:{channel}"
    if redis.set(dedup_key, 1, nx=True, ex=86400):
        # First time seeing this — proceed
        dispatch(user_id, channel, content)
    else:
        # Already sent — skip
        log.info("Duplicate notification suppressed", notification_id=notification_id)
```

## Delivery Tracking

Track the lifecycle of each notification for debugging and analytics:

```
QUEUED → DISPATCHED → DELIVERED → OPENED
                   ↘ FAILED (APNs rejected token)
                   ↘ BOUNCED (email hard bounce)
```

- Push: APNs/FCM returns delivery receipts per token
- Email: Webhook callbacks from SendGrid (delivered, opened, bounced, spam)
- SMS: Delivery status webhooks from Twilio

Store in an append-only delivery log (Cassandra, ClickHouse) — high write volume, query by user_id + timestamp.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| APNs/FCM unreachable | Push notifications not delivered | Queue with retry, exponential backoff |
| Stale device token | APNs returns 410 Gone | Remove token from DB on 410 response |
| Email provider down | Emails not sent | Queue + retry, fallback to secondary provider |
| Fan-out worker crashes | Some users not notified | Kafka at-least-once + idempotent dedup |
| Preference store down | Fallback to default prefs or fail-safe | Cache preferences in Redis |
| Notification storm | Users flooded (bug sends 1000 notifications) | Per-user rate limit in notification service |

## Interview Expectations

- Know the three-tier architecture: event → notification service → channel providers
- Know that APNs/FCM are intermediaries — you never push directly to devices
- Know the fan-out problem and Kafka-based solution
- Know deduplication is required for at-least-once delivery
- Know user preferences must be checked before dispatch
