# Upsert, Merge and External IDs

## External IDs

A field marked as an **External ID** holds a record's identifier from another system. Marking it does three things:

- Creates an **index**, so filtering on it is selective
- Makes it available for **upsert matching**
- Makes it available to the API and Data Loader for relationship resolution

Only Text, Number, Email, and Auto Number fields can be external IDs, up to 25 per object. Marking it **Unique** as well is nearly always correct — a duplicate external ID makes upsert ambiguous and it will fail.

```
Object: Warranty_Claim__c
Field:  ERP_Claim_Id__c
Type:   Text(64)
        External ID: true
        Unique: true (case-sensitive)
```

Adding an external ID to an object that already holds a million records means backfilling every row, which is why this belongs in the data model design rather than in the integration build. See [[02.4 - Fields - Types and Behaviour]].

## Upsert

Upsert matches on a key: if a record exists, update it; if not, create it.

```java
// Match on the record Id
upsert claims;

// Match on an external Id field
upsert claims ERP_Claim_Id__c;

// Database form, with partial success
Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);
```

Without a specified field, upsert matches on `Id` — records with an Id are updated, records without are inserted. Useful when a mixed list comes from a UI.

**The value of upsert is idempotency.** An integration that runs twice, or replays a failed batch, produces the same result rather than duplicates:

```java
public with sharing class ClaimIngestService {

    public static void ingest(List<ErpClaimDto> payload) {
        List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();

        for (ErpClaimDto dto : payload) {
            claims.add(new Warranty_Claim__c(
                ERP_Claim_Id__c = dto.claimId,
                Claim_Amount__c = dto.amount,
                Status__c = dto.status,
                Claim_Date__c = dto.claimDate
            ));
        }

        // safe to rerun: the external id decides insert versus update
        Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);
    }
}
```

This is why external IDs appear throughout this course as integration advice. Without one, a retry after a timeout creates a second copy of everything. See [[13.17 - Error Handling, Retries and Idempotency]].

## Upsert and relationships

The most useful and least obvious capability: **a lookup can be set by the parent's external ID rather than its Salesforce Id.**

```java
Warranty_Claim__c claim = new Warranty_Claim__c(
    ERP_Claim_Id__c = 'CLM-99201'
);

// reference the parent by ITS external id, with no query and no Id mapping
Asset assetRef = new Asset(ERP_Asset_Id__c = 'MCH-88213');
claim.Asset__r = assetRef;

upsert claim ERP_Claim_Id__c;
```

Assigning to the **relationship field** `Asset__r` rather than the lookup `Asset__c`, with an object carrying only the external ID, tells the platform to resolve the parent by that key.

This removes the entire ID-mapping step from a migration. Without it, you insert parents, query back their Ids, join them into the child file, and then insert children. With it, both files carry only the source system's keys.

The same works in Data Loader and the Bulk API through the `Parent__r.External_Id__c` column syntax. See [[02.13 - Data Import and Export Tools]].

## Upsert behaviour and limits

**Three outcomes per record:** no match creates, one match updates, more than one match fails with `DUPLICATE_EXTERNAL_ID`.

**Upsert counts as one DML statement** regardless of how many records insert versus update.

**Triggers fire appropriately** — insert triggers for created records, update triggers for matched ones, both in the same transaction. `Trigger.isInsert` and `Trigger.isUpdate` are both potentially true across a single upsert operation, though not for the same record.

**The external ID must be populated** on every record. A null key throws.

**Case sensitivity matters.** A case-insensitive unique external ID treats `CLM-001` and `clm-001` as the same record; a case-sensitive one does not. Choosing wrongly produces either false matches or duplicates, and it cannot be changed without recreating the field.

## Merge

Merge combines up to three records of the same object into one, moving related records to the survivor and deleting the losers.

```java
Account master = [SELECT Id FROM Account WHERE Id = :masterId];
List<Account> duplicates = [SELECT Id FROM Account WHERE Id IN :duplicateIds LIMIT 2];

Database.MergeResult[] results = Database.merge(master, duplicates, false);

for (Database.MergeResult result : results) {
    if (result.isSuccess()) {
        System.debug('Merged into: ' + result.getId());
        System.debug('Deleted: ' + result.getMergedRecordIds());
        System.debug('Reparented children: ' + result.getUpdatedRelatedIds());
    }
}
```

Supported on **Account, Contact, Case, and Lead only**. Custom objects cannot be merged.

What happens:

- The master's Id survives; the duplicates are deleted to the recycle bin
- Related records — contacts, opportunities, cases, activities, custom lookup children — are reparented to the master
- The master's field values are kept; duplicate values are discarded unless explicitly copied first
- Delete triggers fire on the losers, update triggers on the master
- Merged record Ids are recorded, so external references can be reconciled

`getUpdatedRelatedIds()` returning the reparented children is what lets you drive downstream reconciliation.

## The merge problems

**External systems hold the dead Ids.** An ERP referencing a merged-away account now points at a deleted record. This is exactly what an external ID field solves — reconcile by the source key, not the Salesforce Id.

**Field values are lost.** The master's values win. Preserving the better value from a duplicate means reading both and updating the master **before** merging:

```java
public with sharing class AccountMergeService {

    public static void mergeWithFieldPreservation(Id masterId, Id duplicateId) {
        Map<Id, Account> accounts = new Map<Id, Account>([
            SELECT Id, Phone, Website, Industry, AnnualRevenue, ERP_Account_Id__c
            FROM Account WHERE Id IN (:masterId, :duplicateId)
        ]);

        Account master = accounts.get(masterId);
        Account duplicate = accounts.get(duplicateId);

        // fill blanks on the master from the duplicate before the duplicate is deleted
        master.Phone = master.Phone ?? duplicate.Phone;
        master.Website = master.Website ?? duplicate.Website;
        master.Industry = master.Industry ?? duplicate.Industry;
        master.AnnualRevenue = master.AnnualRevenue ?? duplicate.AnnualRevenue;

        update master;
        Database.merge(master, duplicate, false);
    }
}
```

**Custom object children may or may not follow.** Lookup children generally reparent; the behaviour is worth verifying in a sandbox rather than assuming.

**Merge is one DML statement per call and cannot be bulkified** in the usual sense. Merging 500 duplicate pairs means 500 calls, which exceeds the DML limit. Deduplication at scale belongs in Batch Apex with a small scope size.

## Duplicate rules

Merge cleans up duplicates after the fact. **Duplicate Rules and Matching Rules** prevent them.

Matching rules define what counts as a duplicate — fuzzy name matching, exact email, standardized company name. Duplicate rules define the action: block, or allow with a warning, and whether the API is subject to the rule.

Apex can inspect the result:

```java
Database.SaveResult result = Database.insert(newAccount, false);

if (!result.isSuccess()) {
    for (Database.Error err : result.getErrors()) {
        if (err instanceof Database.DuplicateError) {
            Datacloud.DuplicateResult dup = ((Database.DuplicateError) err).getDuplicateResult();
            for (Datacloud.MatchResult match : dup.getMatchResults()) {
                for (Datacloud.MatchRecord record : match.getMatchRecords()) {
                    System.debug('Possible duplicate: ' + record.getRecord().Id);
                }
            }
        }
    }
}
```

Surfacing the matched records to the user, rather than a generic "duplicate detected", is what makes a duplicate rule usable rather than obstructive.

Bypassing a duplicate rule deliberately — during a migration, or where the user has confirmed the record is distinct:

```java
Database.DMLOptions options = new Database.DMLOptions();
options.duplicateRuleHeader.allowSave = true;
newAccount.setOptions(options);
Database.insert(newAccount, false);
```

## Practical guidance

**Add an external ID to every object that will be integrated**, before data arrives.

**Mark it unique**, and choose case sensitivity deliberately.

**Upsert on the external ID** in every integration, so retries are safe.

**Use `Parent__r.External_Id__c` assignment** to avoid ID mapping in migrations.

**Preserve field values before merging**, not after.

**Reconcile external systems on the external ID**, not the Salesforce Id, so merges do not break references.

**Batch large deduplication jobs** with a small scope — merge does not bulkify.

**Enable duplicate rules**, and surface the matched records rather than a bare error.
