# Cancellation and Structured Concurrency

#backend #python #asyncio

> **In one line:** Cancelling a task means throwing an exception into it at its next `await` and hoping it cleans up properly. Structured concurrency is the rule that a task cannot outlive the block that started it — which turns "hoping" into "guaranteed".

---

## The Idea

Work needs to stop early all the time:

- The client disconnected. Nobody is waiting for this answer any more
- A timeout expired
- One of five parallel calls failed, so the other four are pointless
- The process is shutting down

Python has no way to stop a running coroutine from outside. It cannot preempt. So cancellation works the only way it can: **it throws an exception into the coroutine at its next suspension point.**

```python
task.cancel()
# → CancelledError is raised at whatever `await` the task is sitting on
```

Two consequences follow immediately, and they explain almost every cancellation bug:

1. **A task that never awaits can never be cancelled.** A tight CPU loop ignores `cancel()` completely.
2. **Cancellation is not instant.** It happens whenever the task next yields, which may be never.

---

## How It Really Works

### CancelledError is not an Exception

```python
class CancelledError(BaseException): ...
```

It inherits from `BaseException`, not `Exception`. This is deliberate, and it saves you constantly:

```python
try:
    await something()
except Exception:          # does NOT catch CancelledError. Good
    log.error("failed")
```

A blanket `except Exception` would otherwise swallow every cancellation and your service would refuse to shut down.

⚠️ **`except BaseException` and bare `except:` do catch it.** Both are almost always bugs in async code. If you must use them, re-raise:

```python
try:
    await something()
except asyncio.CancelledError:
    await cleanup()
    raise                  # ALWAYS re-raise. Swallowing it breaks the caller
```

💡 **The rule: you may catch `CancelledError` to clean up, but you must re-raise it.** A task that catches cancellation and continues is lying to whoever cancelled it, and `TaskGroup`s and shutdown logic will hang waiting for it.

### Where cancellation lands

```python
async def handler():
    conn = await db.acquire()          # ← could land here
    try:
        rows = await conn.fetch(query) # ← or here
        return process(rows)           # ← never here. No await, no landing
    finally:
        await conn.release()           # runs on cancellation too
```

`finally` blocks run. That is what makes cleanup possible at all.

⚠️ **But an `await` inside `finally` can itself be cancelled.** During shutdown, when a second cancellation arrives, your cleanup can be interrupted halfway.

```python
finally:
    await asyncio.shield(conn.release())   # protect the cleanup
```

Use `shield` sparingly and almost only here. Shielding normal work means your service will not shut down.

### Timeouts

Two APIs. Prefer the newer one.

```python
# Older: wraps one awaitable
result = await asyncio.wait_for(fetch(url), timeout=5)

# Newer (3.11+): wraps a block
async with asyncio.timeout(5):
    a = await fetch(url1)
    b = await fetch(url2)          # 5 seconds total for both
```

`asyncio.timeout` is better because it covers a region, not a single call, and because it can be rescheduled:

```python
async with asyncio.timeout(5) as cm:
    await first_part()
    cm.reschedule(loop.time() + 10)    # extend the deadline
    await second_part()
```

Both work the same way underneath: start a timer, and when it fires, cancel the task. There is no other mechanism.

⚠️ **A timeout on non-yielding code does nothing.**

```python
async with asyncio.timeout(1):
    huge_regex.match(giant_string)     # runs for 30s. Timeout never fires
```

The timer callback cannot run, because the loop is blocked. This surprises people constantly. See [[01.6 - The Blocking Call Problem]].

### Distinguishing your timeout from someone else's cancellation

Python 3.11 added `uncancel()` and `cancelling()` to solve a real problem: when `asyncio.timeout` cancels your task, how does the task know it was the timeout rather than a shutdown?

```python
try:
    async with asyncio.timeout(5):
        await work()
except TimeoutError:
    # timeout converted CancelledError → TimeoutError for you
    log.warning("work timed out")
```

The context manager calls `uncancel()` and re-raises as `TimeoutError` only if the cancellation was its own. If the cancellation came from outside, it propagates as `CancelledError` untouched. You rarely call these methods yourself, but knowing they exist explains why nested timeouts behave correctly.

## Structured Concurrency

### The problem with bare tasks

```python
async def handler():
    asyncio.create_task(background_work())
    return "ok"
```

Where does that task live? How long does it run? Who sees its exception? What cancels it when the request is cancelled?

Answers: nowhere, unknown, nobody, nothing.

This is the async equivalent of `goto` — a jump with no scope, no return, and no cleanup. The essay that made this argument (linked below) is why `TaskGroup` exists.

### The rule

**A task cannot outlive the block that created it.**

```python
async with asyncio.TaskGroup() as tg:
    tg.create_task(fetch(url1))
    tg.create_task(fetch(url2))
# guaranteed: both are finished here, one way or another
```

At the closing of the block:

- If all succeed, execution continues
- If one raises, the others are cancelled, and you get an `ExceptionGroup`
- If the enclosing task is cancelled, all children are cancelled
- The block does not exit until every child is done

You get scope back. Concurrency becomes an expression with a beginning and an end, like a function call.

### `ExceptionGroup` and `except*`

When several children fail, you get all the failures, not just the first.

```python
try:
    async with asyncio.TaskGroup() as tg:
        tg.create_task(a())
        tg.create_task(b())
except* ValueError as eg:
    for exc in eg.exceptions:
        log.warning("value error", exc_info=exc)
except* TimeoutError as eg:
    log.warning("%d timed out", len(eg.exceptions))
```

`except*` matches *any* exception of that type in the group, and can run more than one branch. It takes an hour to get used to and then it is obviously right.

### TaskGroup vs gather

| | `gather` | `TaskGroup` |
|---|---|---|
| Siblings on failure | Keep running, unobserved | Cancelled |
| Tasks can leak | Yes | No |
| Multiple errors | Only the first, unless `return_exceptions` | All, as an `ExceptionGroup` |
| Cancellation propagates down | Partially | Fully |
| Use when | Independent work where partial results are fine | Everything else |

💡 **Default to `TaskGroup`.** Reach for `gather(return_exceptions=True)` only when you genuinely want partial results from independent operations — fanning out to five recommendation providers where three answers is fine.

## In Production

### Client disconnect

When a browser closes the tab, uvicorn cancels the task running your endpoint. That is good — you stop wasting work.

It is also dangerous:

```python
@app.post("/orders")
async def create_order(data: OrderIn):
    order = await db.insert_order(data)
    await charge_payment(order)         # ← cancelled here
    await send_confirmation(order)      # never runs
```

You now have an order in the database, a charge that may or may not have gone through, and no confirmation. The user sees nothing and retries.

⚠️ **Never let a multi-step state change depend on the client staying connected.** The fix is not `shield` — it is to make the endpoint write one durable record and hand the rest to a queue:

```python
@app.post("/orders")
async def create_order(data: OrderIn):
    order_id = await db.insert_order_pending(data)
    await enqueue(process_order, order_id)      # survives disconnect
    return {"id": order_id, "status": "pending"}
```

This is the same reasoning as the outbox pattern in [[09.3 - The Outbox Pattern]].

### Graceful shutdown

On SIGTERM, a well-behaved service:

1. Stops accepting new connections
2. Lets in-flight requests finish, up to a deadline
3. Cancels whatever is left
4. Closes pools and flushes buffers

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.db = await create_pool()
    app.state.tasks = set()
    yield
    for t in app.state.tasks:
        t.cancel()
    await asyncio.gather(*app.state.tasks, return_exceptions=True)
    await app.state.db.close()
```

⚠️ **Kubernetes gives you `terminationGracePeriodSeconds` (default 30) and then SIGKILL.** Your drain deadline must be shorter than that, and your readiness probe must start failing *before* you stop accepting, so the load balancer removes you first. Full treatment in [[11.7 - Graceful Shutdown and Draining]].

### The uncancellable task

```python
async def sync_documents():
    while True:
        try:
            await do_batch()
        except Exception:
            log.exception("batch failed")
        await asyncio.sleep(60)
```

Looks fine. It is fine — `except Exception` does not catch `CancelledError`. But change it to `except BaseException` or add a bare `except:` and this task can never be stopped. Your pod hangs for 30 seconds every deploy and then gets killed, and nobody knows why.

Grep your codebase for bare `except:` and `except BaseException`. That is a five-minute audit worth doing today.

### Timeouts belong at every layer

```python
async with asyncio.timeout(10):                    # total request budget
    async with asyncio.timeout(3):
        user = await user_service.get(uid)         # per-dependency budget
    async with asyncio.timeout(5):
        docs = await search_service.query(q)
```

The inner budgets must sum to less than the outer one, or the outer timeout never gets a chance to be meaningful. Deadline propagation across services is [[03.11 - Timeouts and Deadlines Across Hops]].
