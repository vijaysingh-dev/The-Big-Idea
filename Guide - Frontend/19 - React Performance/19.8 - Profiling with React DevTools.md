# Profiling with React DevTools

Optimization without measurement is guessing, and the guess is usually wrong. This note is the workflow.

## Setup

Install the React Developer Tools extension. Two tabs appear: **Components** and **Profiler**.

Before profiling, enable in the Components tab settings:

- **Highlight updates when components render** — draws a flashing outline around re-rendering components. The fastest possible diagnostic: type in an input and see how much of the page lights up.
- **Record why each component rendered while profiling** — adds the attribution that makes the Profiler useful.

Profile in a **production build with profiling enabled**, not in development. Development React is several times slower and includes Strict Mode double-rendering, so relative costs are distorted.

```js
// vite.config.js — alias to the profiling build
resolve: {
  alias: process.env.PROFILE ? {
    "react-dom/client": "react-dom/profiling",
  } : {},
}
```

Next.js does this with `next build --profile`.

Also apply **CPU throttling at 4–6×** in the Performance panel. A mid-range Android phone is roughly that much slower than a development machine, and almost every React performance problem is invisible without it.

## The Profiler workflow

1. Open the Profiler tab, press record.
2. Perform the interaction — type, click, navigate.
3. Stop recording.
4. Read the commits.

The bar chart at the top shows each **commit** during the recording, with height proportional to duration. Tall bars are where the time went.

Select a commit to see the flamegraph:

- **Width** = time spent rendering that component and its children
- **Grey** = did not re-render in this commit
- **Yellow/orange** = took longer

Click any component to see, in the right panel:

- **Why did this render?** — "Props changed: onSelect", "Hook 1 changed", "Parent rendered", "Context changed"
- Its own render duration versus its subtree's

That "why" attribution is the single most valuable feature. It converts "something is re-rendering too much" into a specific fix.

## Reading the answers

**"Parent rendered"** on an expensive component means the fix is composition — move state down, or pass the component as `children` so its element identity is stable ([[19.1 - What Causes Re-renders]]).

**"Props changed: onClick"** on a memoized component means a callback identity is unstable — `useCallback`, or check that its dependencies are stable ([[19.2 - React.memo and Memoization Strategy]]).

**"Context changed"** means the provider's value is being recreated, or the context mixes fast- and slow-changing data ([[17.9 - useContext]]).

**"Hook 1 changed"** identifies the specific hook by index; hover the hooks list in the Components tab to map the index to a name.

## Ranked view

Toggle from flamegraph to **Ranked** to see components sorted by self-render time, ignoring tree structure. This answers "what is expensive" as opposed to "what re-rendered", and the two are often different components.

## The Profiler component

For measuring in code — CI checks, production sampling, or automated regression tests:

```jsx
import { Profiler } from "react";

<Profiler
  id="ProductList"
  onRender={(id, phase, actualDuration, baseDuration, startTime, commitTime) => {
    if (actualDuration > 16) {
      report({ id, phase, actualDuration });
    }
  }}
>
  <ProductList items={items} />
</Profiler>
```

- **`phase`** — `"mount"`, `"update"` or `"nested-update"`
- **`actualDuration`** — time for this commit, benefiting from memoization
- **`baseDuration`** — estimated time without any memoization

The `baseDuration` versus `actualDuration` gap tells you how much your memoization is actually saving. A gap near zero means the memos are not working.

Note the callback is disabled in production builds unless you use the profiling build, so this is a development and staging tool by default.

## Combining with the browser Performance panel

React DevTools shows React's work. The browser Performance panel shows everything ([[13.2 - Reflow Repaint and Composite]]).

React 18+ writes entries into the browser's timeline, so a Performance recording shows React render and commit phases inline with layout, paint, GC and long tasks. That combined view is what you need when the question is "is this React's fault at all" — often it is a forced synchronous layout, a large paint, or garbage collection ([[13.3 - Layout Thrashing]]).

Rule of thumb for reading the two together:

- **High render time in React DevTools** → too many components rendering, or expensive component logic. Fix with composition, memoization, or moving computation out of render.
- **High commit time** → large DOM changes. Fix with virtualization or by reducing how much of the tree actually changes ([[19.5 - Virtualization and Windowing]]).
- **Long tasks with little React time** → the problem is elsewhere: a heavy synchronous computation, a third-party script, or layout thrashing.

## Interaction tracking

React DevTools 5+ shows interactions in the timeline, linking a click or keystroke to the renders it caused. This maps directly onto **INP** ([[13.5 - Core Web Vitals]]), which measures input-to-paint latency — the metric most affected by React performance.

The budget: an interaction should produce a visible response within about 200ms, covering handler execution, render, commit and paint.

## What to actually look for

**A single interaction causing many commits.** Usually chained effects, each triggering a render ([[17.4 - useEffect Pitfalls]]).

**A component rendering that has no visible reason.** Read the "why".

**A commit far longer than the others.** Something is doing real work — sorting, filtering, or rendering a large list.

**Render time that is fine but interaction latency that is not.** The cost is outside React.

## Measuring the fix

Record before, apply the change, record after, compare durations on the same interaction with the same throttling.

If the numbers do not move, **revert the change**. An unnecessary `useMemo` or `React.memo` is cost plus a dependency array that can go stale — worse than nothing.

## How senior engineers actually use this

**They profile production builds with CPU throttling**, because development numbers are meaningless.

**They start with the highlight-updates overlay**, which takes five seconds and often identifies the problem immediately.

**They read the "why did this render" attribution** rather than reasoning about it.

**They check whether the problem is React at all** using the browser Performance panel before optimizing components.

**They revert optimizations that do not measure.**

## Common pitfalls

- Profiling a development build.
- Profiling without CPU throttling.
- Optimizing based on the flamegraph's largest box without checking self-time in Ranked view.
- Assuming a re-render is expensive — most produce no DOM work at all.
- Adding memoization without measuring, and leaving it in.
- Ignoring the browser Performance panel and optimizing React when the cost is layout or a third-party script.

## Interview angle

"How would you debug a React performance problem" is a process question. Give the sequence: reproduce with CPU throttling on a production build, use highlight-updates for a first read, record in the Profiler, read the "why did this render" attribution, and distinguish render cost from commit cost because they have opposite fixes. Adding that you verify the improvement and revert changes that do not measure demonstrates discipline rather than reflex.
