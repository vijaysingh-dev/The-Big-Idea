# JSON Serialization and Deserialization

## Where this matters

Every integration, every Lightning component call, every platform event payload, and every stored configuration blob passes through JSON. It is the most-used serialization format on the platform and the one with the most sharp edges.

## Serializing

```java
String json = JSON.serialize(someObject);
String pretty = JSON.serializePretty(someObject);

// Omit null fields — usually what an external API wants
String compact = JSON.serialize(someObject, true);
```

The three-argument form suppresses nulls, which matters for APIs that treat an explicit null differently from an absent field. Sending `"approvedAmount": null` to a system that interprets it as "clear this value" is a real class of integration bug.

Serializing an sObject directly works and is rarely what you want:

```java
Warranty_Claim__c claim = [SELECT Id, Claim_Number__c, Status__c FROM Warranty_Claim__c LIMIT 1];
String json = JSON.serialize(claim);
```

```json
{"attributes":{"type":"Warranty_Claim__c","url":"/services/data/v62.0/sobjects/..."},
 "Id":"a0X5g000001AbCdEAK","Claim_Number__c":"WC-00042","Status__c":"Submitted"}
```

The `attributes` block leaks internal detail, the field names carry `__c` suffixes, and only queried fields appear. External systems should receive a **wrapper class** you control, not raw sObjects.

## Wrapper classes

```java
public class ClaimPayload {

    public String claimNumber;
    public String serialNumber;
    public Decimal amount;
    public String status;
    public Datetime submittedAt;
    public List<PartLine> parts;

    public class PartLine {
        public String partCode;
        public Integer quantity;
        public Decimal unitCost;
    }

    public static List<ClaimPayload> from(List<Warranty_Claim__c> claims) {
        List<ClaimPayload> payloads = new List<ClaimPayload>();

        for (Warranty_Claim__c claim : claims) {
            ClaimPayload payload = new ClaimPayload();
            payload.claimNumber = claim.Claim_Number__c;
            payload.serialNumber = claim.Asset__r?.SerialNumber;
            payload.amount = claim.Claim_Amount__c;
            payload.status = claim.Status__c;
            payload.submittedAt = claim.CreatedDate;
            payload.parts = buildParts(claim.Claim_Parts__r);
            payloads.add(payload);
        }
        return payloads;
    }
}
```

The wrapper is a **contract**. It insulates the external system from field renames, controls exactly what is exposed, and gives clean names without platform suffixes.

Making the mapping a static factory method rather than a constructor keeps the wrapper a plain data holder, which matters because deserialization needs a no-argument constructor.

## Deserializing

**Typed deserialization** into a known class:

```java
ClaimResponse response = (ClaimResponse) JSON.deserialize(responseBody, ClaimResponse.class);
```

**Strict deserialization**, which throws on unexpected fields:

```java
ClaimResponse response = (ClaimResponse) JSON.deserializeStrict(responseBody, ClaimResponse.class);
```

`deserializeStrict` is the safer choice when you control both ends, because it catches a schema change rather than silently ignoring it. `deserialize` is more tolerant and is right when the external system may add fields you do not care about.

**Untyped deserialization** into a generic map, for unpredictable structures:

```java
Map<String, Object> parsed = (Map<String, Object>) JSON.deserializeUntyped(responseBody);

String status = (String) parsed.get('status');
List<Object> items = (List<Object>) parsed.get('items');

for (Object item : items) {
    Map<String, Object> itemMap = (Map<String, Object>) item;
    String code = (String) itemMap.get('code');
}
```

Every level requires a cast, which is verbose and error-prone. Use it only when the structure genuinely varies; otherwise a typed class is far more maintainable.

## The reserved word problem

JSON keys that are Apex reserved words cannot be property names.

```json
{ "class": "Premium", "currency": "INR", "date": "2026-08-07", "limit": 500000 }
```

`class`, `currency`, `date`, and `limit` are all problematic. The standard workaround is renaming during the string, before deserializing:

```java
String cleaned = responseBody
    .replace('"class"', '"coverageClass"')
    .replace('"currency"', '"currencyCode"')
    .replace('"date"', '"issueDate"')
    .replace('"limit"', '"coverageLimit"');

CoverageResponse response = (CoverageResponse) JSON.deserialize(cleaned, CoverageResponse.class);
```

Crude, and it is the accepted technique. The risk is replacing an occurrence inside a data value rather than a key — including the quotes in the search string reduces that, and it does not eliminate it. Where the payload could legitimately contain those strings as values, untyped deserialization is safer.

## Field name mismatches

Apex property names must match JSON keys exactly, and Apex is case-insensitive while JSON is not. There is no annotation for mapping a property to a differently named key, which is a real gap compared to other languages.

Options when the external system uses names you cannot use:

**Rename in the string**, as above.

**Deserialize untyped and map manually**, which is verbose but explicit.

**JSONParser** for full control, covered below.

## JSONParser

For large payloads or awkward structures, streaming with `JSONParser` avoids materializing everything.

```java
public with sharing class ClaimResponseParser {

    public static List<ClaimResult> parse(String jsonBody) {
        List<ClaimResult> results = new List<ClaimResult>();
        JSONParser parser = JSON.createParser(jsonBody);

        while (parser.nextToken() != null) {
            if (parser.getCurrentToken() == JSONToken.FIELD_NAME
                && parser.getText() == 'results') {

                parser.nextToken();  // move to START_ARRAY
                while (parser.nextToken() != JSONToken.END_ARRAY) {
                    results.add((ClaimResult) parser.readValueAs(ClaimResult.class));
                }
            }
        }
        return results;
    }
}
```

`readValueAs` deserializes a subtree into a typed class, so you can navigate to the part you want and deserialize only that. This is the technique for a large response where you need one nested array.

More code than `JSON.deserialize`, and worth it when heap or CPU is a constraint.

## Heap and CPU

Both serialization and deserialization are expensive.

**CPU.** Serializing a large structure consumes real CPU time against the 10-second synchronous limit. Serializing 10,000 records in a loop will exceed it.

**Heap.** The JSON string and the object graph both exist in memory simultaneously. A 3 MB payload deserialized into objects can approach the 6 MB synchronous heap limit on its own.

The mitigations:

**Chunk large payloads.** Send 200 records per request rather than 10,000 in one.

**Use `JSONParser`** to avoid materializing the whole structure.

**Move to async**, where heap is 12 MB and CPU is 60 seconds.

**Do not serialize what you do not need.** A wrapper containing five fields rather than a full sObject is a large saving at volume.

See [[16.3 - CPU Time and Heap Size]].

## Dates and numbers

**Datetime serializes as ISO 8601 in UTC**, which is correct for integrations:

```json
{ "submittedAt": "2026-08-07T09:30:00.000Z" }
```

**Date serializes as `yyyy-MM-dd`.**

Deserializing a datetime in a different format fails. Where an external system sends a non-standard format, the field must be a String in the wrapper and parsed manually:

```java
public class ExternalClaim {
    public String submittedAt;   // '07/08/2026 09:30'

    public Datetime parsedSubmittedAt() {
        return Datetime.parse(submittedAt);
    }
}
```

`Datetime.parse()` uses the running user's locale, which makes it unreliable for integration data. `Datetime.valueOf()` expects `yyyy-MM-dd HH:mm:ss` and is deterministic. For anything unusual, splitting the string and constructing explicitly is the only safe approach.

**Decimal serializes without quotes.** A system expecting a string-encoded amount needs the wrapper property typed as String.

## sObjects from JSON

Deserializing directly into an sObject works and is useful in tests:

```java
Warranty_Claim__c claim = (Warranty_Claim__c) JSON.deserialize(
    '{"Claim_Number__c":"WC-00042","Claim_Amount__c":150000}',
    Warranty_Claim__c.class
);
```

This is also the standard technique for **setting read-only fields in tests** — formula fields, roll-up summaries, and system fields that cannot be assigned normally:

```java
// Constructing a record with a formula field populated, for a unit test with no DML
Warranty_Claim__c claim = (Warranty_Claim__c) JSON.deserialize(
    '{"Id":"' + fakeId + '","Days_Open__c":45,"Asset__r":{"SerialNumber":"SN-88213"}}',
    Warranty_Claim__c.class
);
```

That trick — building a record with populated relationships and formula fields without touching the database — is what makes fast, DML-free unit tests possible. See [[19.3 - TestSetup and Test Data Factories]].

## Lightning component payloads

Data returned to a Lightning Web Component is serialized automatically, and `@AuraEnabled` controls what crosses the boundary.

```java
public class ClaimSummary {
    @AuraEnabled public Id claimId;
    @AuraEnabled public String claimNumber;
    @AuraEnabled public Decimal amount;
    public String internalNotes;   // NOT sent to the client
}
```

A property without `@AuraEnabled` is invisible on the client side. This is both a common source of "the field is undefined in JavaScript" and a useful mechanism for keeping internal fields server-side.

Inner classes returned to a component need `@AuraEnabled` on every property that should cross. See [[14.10 - Calling Apex - Wire vs Imperative]].

## Practical guidance

**Send wrapper classes, not raw sObjects**, to anything external.

**Use `serialize(obj, true)`** to suppress nulls where the receiving system distinguishes null from absent.

**Prefer `deserializeStrict`** when you control both ends.

**Rename reserved words in the string** before typed deserialization, and prefer untyped parsing where the payload could contain those strings as values.

**Use `JSONParser`** for large payloads.

**Chunk anything large**, and move to async when heap or CPU is tight.

**Use JSON deserialization to build test records** with read-only fields populated.

**Mark every property `@AuraEnabled`** that a component needs.
