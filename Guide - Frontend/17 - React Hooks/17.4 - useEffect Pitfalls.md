# useEffect Pitfalls

Most effects in most codebases should not exist. This note is the list of effects to delete and what to replace them with.

The test: **is this effect talking to something outside React?** If not, it is probably the wrong tool.

## Deriving state

```jsx
// Anti-pattern
const [fullName, setFullName] = useState("");
useEffect(() => {
  setFullName(`${first} ${last}`);
}, [first, last]);

// Correct
const fullName = `${first} ${last}`;
```

The effect version renders twice per change and shows a stale value for one frame. There is no upside.

Same for filtering, sorting, totals and formatting — all computed during render, wrapped in `useMemo` only if measurement justifies it ([[17.6 - useMemo]]).

## Resetting state when a prop changes

```jsx
// Anti-pattern
useEffect(() => {
  setSelection(null);
  setDraft("");
}, [userId]);

// Correct — key remounts with fresh state
<UserPanel key={userId} userId={userId} />
```

The effect version renders once with the old state before clearing it, which is visible as a flash of the previous user's data.

When only *part* of the state should reset, adjust during render instead ([[17.2 - useState in Depth]]):

```jsx
const [prevId, setPrevId] = useState(userId);
if (userId !== prevId) {
  setPrevId(userId);
  setSelection(null);
}
```

## Responding to user actions

```jsx
// Anti-pattern — runs on mount too, and on every unrelated change
useEffect(() => {
  if (submitted) {
    showToast("Saved");
    logAnalytics("form_submit");
  }
}, [submitted]);

// Correct
const handleSubmit = async () => {
  await save(form);
  showToast("Saved");
  logAnalytics("form_submit");
};
```

If the code should run *because the user did something*, it belongs in the handler. Effects run because a value changed, which is a different — and weaker — condition.

The same applies to notifying a parent:

```jsx
// Anti-pattern — extra render, fires on mount
useEffect(() => { onChange(value); }, [value]);

// Correct
const handleChange = (v) => { setValue(v); onChange(v); };
```

## Chained effects

```jsx
// Anti-pattern — a render per link in the chain
useEffect(() => { if (card) setGoldCount(c => c + 1); }, [card]);
useEffect(() => { if (goldCount > 3) setRound(r => r + 1); }, [goldCount]);
useEffect(() => { if (round > 5) setIsGameOver(true); }, [round]);

// Correct — compute the whole transition in the handler
function handlePlayCard(card) {
  const nextGold = goldCount + 1;
  const nextRound = nextGold > 3 ? round + 1 : round;
  setGoldCount(nextGold);
  setRound(nextRound);
  setIsGameOver(nextRound > 5);
}
```

Each effect in a chain triggers a full render before the next one runs, so a four-link chain costs four renders and is nearly impossible to debug. For genuinely complex transitions, `useReducer` handles the whole sequence in one dispatch ([[17.10 - useReducer]]).

## Fetching data

```jsx
// The naive version, with four bugs
useEffect(() => {
  fetch(`/api/search?q=${query}`)
    .then(r => r.json())
    .then(setResults);
}, [query]);
```

Missing: cancellation (a slow earlier request overwrites a fast later one), error handling, loading state, and deduplication when two components request the same data.

The minimum correct version:

```jsx
useEffect(() => {
  const controller = new AbortController();
  setStatus("loading");

  (async () => {
    try {
      const res = await fetch(url, { signal: controller.signal });
      if (!res.ok) throw new HttpError(res.status);
      setData(await res.json());
      setStatus("success");
    } catch (e) {
      if (e.name === "AbortError") return;
      setError(e);
      setStatus("error");
    }
  })();

  return () => controller.abort();
}, [url]);
```

And that still lacks caching, retries, refetch-on-focus and background updates. Use a data library ([[24.6 - TanStack Query Fundamentals]]) — this is the strongest single argument for one.

## Stale closures

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);      // captured count from the first render — always 0
  }, 1000);
  return () => clearInterval(id);
}, []);
```

The empty array means the effect never re-runs, so the closure never updates ([[02.3 - Closures]]). Two fixes: the updater form `setCount(c => c + 1)`, which reads no outer value, or adding `count` to the dependencies and accepting the interval being recreated.

The updater form is almost always correct here.

## Infinite loops

```jsx
// Object dependency, new every render
useEffect(() => { load(options); }, [options]);

// Effect sets state it depends on
useEffect(() => { setItems([...items, x]); }, [items]);
```

The first fires every render because `{}` !== `{}`. The second is a literal infinite loop.

For the first, construct the object inside the effect or depend on its primitive parts. For the second, the state update almost certainly belongs elsewhere.

## Initializing once per app

```jsx
// Anti-pattern — component-scoped, runs twice in Strict Mode
useEffect(() => { initializeSDK(); }, []);

// Correct — module scope, genuinely once
if (typeof window !== "undefined") initializeSDK();
```

Application-level initialization is not component behavior. Module scope runs once per import, which is what "once" actually means here.

## Suppressing Strict Mode

```jsx
// Anti-pattern
const hasRun = useRef(false);
useEffect(() => {
  if (hasRun.current) return;
  hasRun.current = true;
  doSomething();
}, []);
```

Double invocation reveals that the effect is not safely re-runnable. That is a real defect — it will surface in production when React discards and restores a tree, or when the component remounts. The guard hides it ([[18.7 - Strict Mode and Double Invocation]]).

The fix is proper cleanup, or moving the work out of the effect.

## When effects are correct

To be clear, effects are the right tool for:

- Subscribing to a store, WebSocket, or event emitter
- Setting up timers and animation frames
- Integrating a non-React library (charts, maps, editors)
- Syncing to `localStorage` or the URL
- Observing the DOM with `IntersectionObserver` / `ResizeObserver`
- Imperative focus and scroll management (often `useLayoutEffect`)
- Analytics on view, as opposed to on interaction

Each of these talks to something outside React and has a matching teardown.

## How senior engineers actually use this

**They count effects as a code-quality signal.** A component with four effects almost always has three that should be something else.

**They apply the external-system test** before writing one.

**They use `key` for resets** and derived values for computation.

**They never fetch in an effect** in application code — the data layer handles it.

**They treat a Strict Mode failure as a bug report**, not as noise.

## Common pitfalls

- Effects that derive state.
- Effects that reset state on prop change instead of `key`.
- Effects doing what an event handler should do.
- Chained effects producing cascading renders.
- Fetching without cancellation, causing race conditions.
- Stale closures from an empty dependency array.
- Object or function dependencies causing infinite loops.
- Ref guards to defeat Strict Mode.

## Interview angle

"When should you not use useEffect" is an excellent senior question and the list above is the answer: derived state, resets, event responses, and chained state transitions. Give the external-system test as the rule, then a concrete example — the derived-state effect that renders twice and flashes stale data. Adding that effect-based fetching is missing cancellation, deduplication and caching connects it to why the ecosystem standardized on data libraries.
