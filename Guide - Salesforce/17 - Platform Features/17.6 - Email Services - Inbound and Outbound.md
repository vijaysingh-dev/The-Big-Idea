# Email Services - Inbound and Outbound

## Sending from Apex

```java
public with sharing class ClaimNotificationService {

    public static void notifyApproval(List<Warranty_Claim__c> claims) {
        List<Messaging.SingleEmailMessage> messages = new List<Messaging.SingleEmailMessage>();

        for (Warranty_Claim__c claim : claims) {
            Messaging.SingleEmailMessage message = new Messaging.SingleEmailMessage();
            message.setTargetObjectId(claim.Contact__c);
            message.setWhatId(claim.Id);
            message.setTemplateId(approvalTemplateId());
            message.setOrgWideEmailAddressId(supportAddressId());
            // saveAsActivity logs the email against the record, which is usually wanted
            message.setSaveAsActivity(true);
            messages.add(message);
        }

        // one invocation for the whole list; the limit is 10 invocations per transaction
        Messaging.sendEmail(messages);
    }
}
```

**The 10-invocation-per-transaction limit is on `sendEmail` calls, not on messages.** One call with 200 messages is one invocation; a loop calling it per record dies at ten. See [[16.4 - Callout and Async Limits]].

## setTargetObjectId versus setToAddresses

The distinction that governs everything about templates and tracking.

```java
// A Contact, Lead, or User — enables templates, merge fields, and activity logging
message.setTargetObjectId(contactId);

// Raw addresses — no merge fields, and counts against the daily external limit
message.setToAddresses(new List<String>{ 'ops@northwind.com' });
```

**`setTargetObjectId` with a Contact or Lead does not count toward the daily external email limit.** Raw addresses do. On a high-volume notification process that difference decides whether the org runs out of email at 3pm.

**Merge fields only resolve with a target object**, so a template sent to a raw address renders the merge fields as blanks.

**`setWhatId`** supplies the related record for merge fields on that object — the claim, in the example above. Without it, `{!Warranty_Claim__c.Claim_Number__c}` resolves to nothing.

## Sending without saving a Contact

For an address with no Contact record, `setTreatTargetObjectAsRecipient(false)` lets you use a Contact for merge context while sending elsewhere:

```java
message.setTargetObjectId(contactId);
message.setTreatTargetObjectAsRecipient(false);
message.setToAddresses(new List<String>{ escalationAddress });
```

The merge fields resolve against the Contact; the email goes to the escalation address.

## Org-wide email addresses

```
Setup → Organization-Wide Addresses → Add

Display Name:  Northwind Support
Email Address: support@northwind.com
Allowed profiles: Support Agent, System Administrator
```

**Without this, email sends from the running user's address**, which for an integration user means customers receiving mail from `integration.erp@northwind.com`.

```java
OrgWideEmailAddress address = [
    SELECT Id FROM OrgWideEmailAddress WHERE Address = 'support@northwind.com' LIMIT 1
];
message.setOrgWideEmailAddressId(address.Id);
```

The address must be verified before use, which is a one-time click on a confirmation email.

## Deliverability

The part that decides whether the email arrives at all, and it is configuration rather than code.

```
Setup → Deliverability → Access level
  No access        nothing sends — the default in new sandboxes
  System email only  only password resets and system notifications
  All email        everything sends
```

**A refreshed sandbox defaults to "System email only"**, which is why tested email does not arrive and everyone assumes the code is broken. It is a deliberate safeguard against a sandbox emailing real customers.

**Bounce management** and **compliance BCC** are also here.

**SPF, DKIM, and DMARC** determine whether receiving servers trust mail claiming to come from your domain:

```
Setup → Email → DKIM Keys → Create a key for northwind.com
                          → publish the CNAME records in DNS
```

Without DKIM, mail sent by Salesforce on behalf of `@northwind.com` fails alignment checks and lands in spam. This is a DNS task rather than a Salesforce one, and it is the most common cause of "our emails go to junk".

**Enhanced Email Deliverability** and a verified sending domain improve reputation further, and for high volume a dedicated IP or Marketing Cloud is the right answer rather than the transactional email service.

## Email templates

```
Classic templates       Text, HTML, Custom, Visualforce
Lightning templates     built in the Email Template Builder, stored as EmailTemplate
```

**Visualforce email templates** remain the most capable for complex output — a claim summary with a line-item table, for instance:

```html
<messaging:emailTemplate subject="Claim {!relatedTo.Claim_Number__c} approved"
                         recipientType="Contact"
                         relatedToType="Warranty_Claim__c">
    <messaging:htmlEmailBody>
        <p>Dear {!recipient.FirstName},</p>
        <p>Claim {!relatedTo.Claim_Number__c} has been approved for
           <apex:outputText value="{0,number,###,###,##0.00}">
               <apex:param value="{!relatedTo.Approved_Amount__c}"/>
           </apex:outputText>.</p>

        <apex:repeat value="{!relatedTo.Claim_Parts__r}" var="part">
            <p>{!part.Product__r.Name} × {!part.Quantity__c}</p>
        </apex:repeat>
    </messaging:htmlEmailBody>
</messaging:emailTemplate>
```

`recipientType` and `relatedToType` are what make `{!recipient}` and `{!relatedTo}` resolve.

**Lightning templates are easier for administrators to maintain** and less capable for structured content. Choosing between them is usually a question of who owns the template.

## Attachments

```java
Messaging.EmailFileAttachment attachment = new Messaging.EmailFileAttachment();
attachment.setFileName('claim-summary.pdf');
attachment.setBody(pdfBlob);
attachment.setContentType('application/pdf');

message.setFileAttachments(new List<Messaging.EmailFileAttachment>{ attachment });
```

**Attachments count toward heap**, and the total message size is capped — around 10 MB for the message including attachments, 25 MB in some contexts.

For anything large, a **Content Distribution link** is better than an attachment: the email carries a URL, the file stays in Salesforce, and the link can expire. See [[17.5 - Files, ContentDocument and ContentVersion]].

`setEntityAttachments` sends existing ContentVersions by Id without loading them into heap, which is the better mechanism when the file is already in Salesforce.

## Inbound: Email Services

An email service gives Salesforce an address that routes incoming mail to an Apex class.

```
Setup → Email Services → New Email Service

Email Service Name:  Claim Evidence Intake
Apex Class:          ClaimEvidenceInboundHandler
Accept Attachments:  All
Advanced Email Security Settings: enabled
Accept Email From:   northwind.com, partner-domain.com
```

Each service gets one or more **email addresses**, each with a generated local part.

```java
global with sharing class ClaimEvidenceInboundHandler implements Messaging.InboundEmailHandler {

    global Messaging.InboundEmailResult handleInboundEmail(
        Messaging.InboundEmail email,
        Messaging.InboundEnvelope envelope
    ) {
        Messaging.InboundEmailResult result = new Messaging.InboundEmailResult();

        try {
            String claimNumber = extractClaimNumber(email.subject);

            List<Warranty_Claim__c> claims = [
                SELECT Id FROM Warranty_Claim__c
                WHERE Claim_Number__c = :claimNumber LIMIT 1
            ];

            if (claims.isEmpty()) {
                // returning success with no work avoids a bounce to the sender
                logUnmatched(email, envelope);
                result.success = true;
                return result;
            }

            attachEvidence(claims[0].Id, email);
            result.success = true;

        } catch (Exception e) {
            // an unhandled exception bounces the email back to the sender
            AutomationLogger.logError('ClaimEvidenceInbound', null, e.getMessage());
            result.success = false;
            result.message = 'The message could not be processed.';
        }

        return result;
    }
}
```

**`result.success = false` bounces the email back to the sender** with the message text. That is occasionally what you want and usually not — an unmatched claim number should be logged for review rather than bounced.

**An unhandled exception also bounces**, which makes the try/catch mandatory.

## What the inbound handler receives

```java
email.subject
email.fromAddress
email.fromName
email.toAddresses
email.ccAddresses
email.plainTextBody
email.htmlBody
email.messageId
email.inReplyTo
email.references
email.binaryAttachments      // List<Messaging.InboundEmail.BinaryAttachment>
email.textAttachments

envelope.fromAddress
envelope.toAddress
```

**`envelope.fromAddress` is the actual sender**; `email.fromAddress` is the From header, which can be forged. For anything security-relevant, use the envelope.

Saving attachments:

```java
List<ContentVersion> versions = new List<ContentVersion>();

if (email.binaryAttachments != null) {
    for (Messaging.InboundEmail.BinaryAttachment attachment : email.binaryAttachments) {
        versions.add(new ContentVersion(
            Title = attachment.fileName,
            PathOnClient = attachment.fileName,
            VersionData = attachment.body,
            FirstPublishLocationId = claimId
        ));
    }
}

if (!versions.isEmpty()) {
    insert versions;
}
```

`FirstPublishLocationId` creates the link automatically, saving the three-step dance.

## Inbound limits and security

```
Daily inbound messages   1,000 × user licences, capped by edition
Message size             around 25 MB including attachments
Handler runs             synchronously, with normal governor limits
```

**The handler runs as the Automated Process user**, so sharing and field-level security behave differently from an interactive session.

**Restrict `Accept Email From`** to known domains. An email service address left open is an unauthenticated entry point that anyone can write to, and it processes whatever arrives.

**Do not trust the From header.** Use `envelope.fromAddress`, and treat the body as untrusted input — particularly if it is parsed for identifiers or commands.

**Email-to-Case** is the packaged version of this for support, and is nearly always the right choice for case creation rather than a hand-built service. See [[05.6 - Email-to-Case and Web-to-Case]].

## Outbound limits

```
sendEmail invocations               10 per transaction
Single emails to external addresses  5,000 per day in most editions
Mass email recipients                by edition
Recipients per SingleEmailMessage    100 to, 25 cc, 25 bcc
Total emails per SingleEmailMessage  by edition
```

**The daily external limit is org-wide.** Exhausting it stops every email in the org — including password resets and case notifications — until the window resets.

```java
// Worth checking before a large send
Messaging.reserveSingleEmailCapacity(recipientCount);
```

`reserveSingleEmailCapacity` throws if the capacity is unavailable, which turns a silent partial send into an explicit failure.

**Emails to Contacts and Leads via `setTargetObjectId` do not count** toward the daily external limit, which is the primary mitigation for high-volume notification.

## Testing

```java
@IsTest
static void inboundHandlerAttachesEvidenceToTheClaim() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Messaging.InboundEmail email = new Messaging.InboundEmail();
    email.subject = 'Evidence for ' + claim.Claim_Number__c;
    email.fromAddress = 'engineer@partner-domain.com';
    email.plainTextBody = 'Report attached.';

    Messaging.InboundEmail.BinaryAttachment attachment =
        new Messaging.InboundEmail.BinaryAttachment();
    attachment.fileName = 'inspection.pdf';
    attachment.body = Blob.valueOf('report contents');
    email.binaryAttachments =
        new List<Messaging.InboundEmail.BinaryAttachment>{ attachment };

    Messaging.InboundEnvelope envelope = new Messaging.InboundEnvelope();
    envelope.fromAddress = 'engineer@partner-domain.com';

    Test.startTest();
    Messaging.InboundEmailResult result =
        new ClaimEvidenceInboundHandler().handleInboundEmail(email, envelope);
    Test.stopTest();

    Assert.isTrue(result.success);
    Integer files = [
        SELECT COUNT() FROM ContentDocumentLink WHERE LinkedEntityId = :claim.Id
    ];
    Assert.areEqual(1, files, 'The attachment should be linked to the claim');
}
```

Inbound handlers are straightforward to test because the input objects are constructible.

**Outbound email does not send in tests**, so assertions are on `Messaging.sendEmail` results or on a mocked service. Testing that the right template and target were chosen is more valuable than testing that send was called.

## Practical guidance

**One `sendEmail` invocation per batch**, never per record.

**Use `setTargetObjectId` with a Contact or Lead** to get merge fields, activity logging, and exemption from the daily external limit.

**Set an org-wide email address**, or mail comes from the running user.

**Check Deliverability first** when email does not arrive — a sandbox defaults to system-only.

**Configure DKIM** or expect mail to land in spam.

**Link to files rather than attaching**, for anything large.

**Wrap inbound handlers in try/catch** — an exception bounces the email.

**Use `envelope.fromAddress`**, not the From header.

**Restrict `Accept Email From`** on every email service.

**Use Email-to-Case** rather than a custom service for support intake.
