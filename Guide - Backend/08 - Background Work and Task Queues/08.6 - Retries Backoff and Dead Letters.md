# Retries, Backoff and Dead Letters

#backend #queues #reliability

> **In one line:** Retry what can succeed, back off with jitter so you do not make the outage worse, give up after a bounded number of attempts, and put what you gave up on somewhere a human will look.

---

## The Idea

A task fails. Three questions:

```
1. Should it retry?          → is the failure transient?
2. When?                     → backoff, with jitter
3. What if it never works?   → dead letter queue
```

⚠️ **Getting the first question wrong wastes capacity. Getting the second wrong turns a blip into an outage. Getting the third wrong loses work silently.**

💡 **The framing that makes retries make sense: a retry is a bet that the world changed.** If nothing about the failure suggests the world might change — malformed input, a deleted entity, invalid credentials — the bet is guaranteed to lose.

---

## Should It Retry?

```python
RETRYABLE = (
    ConnectionError,
    TimeoutError,
    RateLimitError,
    TemporaryServiceError,        # 502, 503, 504
)

TERMINAL = (
    ValidationError,              # the input is wrong and will stay wrong
    NotFoundError,                # the entity is gone
    PermissionDenied,             # authorisation will not change by retrying
    InvalidCredentials,           # needs human intervention
)
```

```python
@app.task(bind=True, max_retries=5)
def sync_source(self, source_id: str):
    try:
        return do_sync(source_id)
    except RETRYABLE as e:
        raise self.retry(exc=e, countdown=backoff(self.request.retries))
    except TERMINAL as e:
        mark_failed(source_id, reason=str(e))
        return
    except Exception:
        raise                     # unknown: retry, then DLQ, then a human looks
```

💡 **The `except Exception` branch is deliberate.** An unrecognised exception might be transient, so retry — but it should end up in the DLQ where someone classifies it. **Over time your `RETRYABLE` and `TERMINAL` tuples grow from what actually appears there.**

⚠️ **Swallowing unknown exceptions is how bugs hide for months.** A task that catches everything and returns quietly produces a system that appears healthy and does nothing.

### The ambiguous case

```python
except HTTPError as e:
    if e.status in (429, 502, 503, 504):
        raise self.retry(exc=e, countdown=retry_after(e) or backoff(...))
    if e.status in (400, 404, 422):
        mark_failed(...)
        return
    if e.status in (401, 403):
        raise self.retry(exc=e, max_retries=1)    # refresh credentials, then once
    raise
```

⚠️ **A 500 is genuinely ambiguous** — it might be a transient bug or a permanent one. **Retry it a small number of times**, and let repeated arrivals in the DLQ tell you which.

💡 **Honour `Retry-After` when the server sends it.** A 429 with `Retry-After: 60` is the server telling you exactly when to come back; ignoring it and retrying in 2 seconds is both rude and useless.

## Backoff

```python
def backoff(attempt: int, base: float = 1.0, cap: float = 600.0) -> float:
    delay = min(cap, base * (2 ** attempt))
    return random.uniform(0, delay)          # full jitter
```

```
attempt 0:  0–1s
attempt 1:  0–2s
attempt 2:  0–4s
attempt 3:  0–8s
attempt 4:  0–16s
```

⚠️ **Jitter is not optional.** Without it, 10,000 tasks that failed at the same moment retry at the same moment — a synchronised wave hitting a service that is already struggling.

💡 **Full jitter — a uniform random delay between 0 and the computed backoff — is the AWS-recommended variant and it measurably outperforms fixed backoff and half-jitter.** It spreads the retries across the whole window rather than clustering them at the end.

```python
@app.task(
    bind=True,
    autoretry_for=(ConnectionError, TimeoutError),
    retry_backoff=True,          # exponential
    retry_backoff_max=600,
    retry_jitter=True,
    max_retries=5,
)
def sync_source(self, source_id: str): ...
```

Celery's built-in options cover the common case. **Use them rather than hand-rolling**, and reach for manual `self.retry` only when the delay depends on the exception.

### The cap matters

```
No cap:  2^10 = 1024s = 17 minutes
         2^15 = 9 hours
```

⚠️ **Uncapped exponential backoff produces retries hours apart**, by which time the work may be irrelevant. **Cap at something meaningful for the work** — 10 minutes for most tasks, longer only for genuinely long-lived work.

### Retry storms

```
Your service retries 3×
  → the client also retries 3×
    → the gateway also retries 3×
```

**One user request becomes 27.** During an incident, when everything is retrying, load multiplies exactly when you can least handle it ([[03.4 - Idempotency and Safe Retries]]).

💡 **Retry at exactly one layer.** For background work, that layer is the task. **The caller that enqueued it should not also retry**, and the service the task calls should not retry internally if the task already does.

**A retry budget is strictly better than per-task limits:**

```python
async def should_retry(task_name: str) -> bool:
    recent_retries = await redis.get(f"retries:{task_name}") or 0
    recent_total = await redis.get(f"total:{task_name}") or 1
    return recent_retries / recent_total < 0.20      # retries ≤ 20% of traffic
```

⚠️ **Without a budget, a downstream outage means every task retries five times, and your worker fleet spends its entire capacity on retries.** The budget bounds system-wide amplification rather than per-task attempts.

## Dead Letter Queues

```
Task fails 5 times → move to the DLQ → stop retrying → alert
```

**What a DLQ is for:**

| Purpose | |
|---|---|
| Stop wasting capacity on hopeless work | |
| **Unblock the queue** | A poison message stops blocking others ([[02.5 - Head of Line Blocking]]) |
| Preserve the work for investigation | Not silently dropped |
| Enable replay after a fix | |

### Implementing it

Celery has no native DLQ. Build one:

```python
@app.task(bind=True, max_retries=5)
def process_document(self, document_id: str):
    try:
        return do_work(document_id)
    except RETRYABLE as e:
        try:
            raise self.retry(exc=e, countdown=backoff(self.request.retries))
        except MaxRetriesExceededError:
            dead_letter(self, exc=e)
            raise


def dead_letter(task, exc: Exception):
    db.execute(
        """INSERT INTO dead_letters
           (task_name, task_id, args, kwargs, exception, traceback, attempts, failed_at)
           VALUES ($1, $2, $3, $4, $5, $6, $7, now())""",
        task.name, task.request.id,
        json.dumps(task.request.args), json.dumps(task.request.kwargs),
        f"{type(exc).__name__}: {exc}", traceback.format_exc(),
        task.request.retries + 1,
    )
    dead_letter_total.labels(task=task.name, exception=type(exc).__name__).inc()
```

💡 **A database table is a better DLQ than a queue**, because you can query it: "all failures for this organisation", "all failures with this exception in the last hour", "group by exception type". A queue gives you none of that.

On RabbitMQ you can also use a native dead letter exchange, which is broker-enforced and does not depend on your task code running correctly.

### Replay

```python
async def replay_dead_letters(task_name: str | None = None, limit: int = 100):
    rows = await db.fetch(
        "SELECT * FROM dead_letters WHERE replayed_at IS NULL "
        "AND ($1::text IS NULL OR task_name = $1) LIMIT $2",
        task_name, limit,
    )
    for row in rows:
        app.send_task(row["task_name"], args=json.loads(row["args"]),
                      kwargs=json.loads(row["kwargs"]))
        await db.execute("UPDATE dead_letters SET replayed_at = now() WHERE id = $1",
                         row["id"])
```

⚠️ **Replay must be rate-limited.** Replaying 50,000 dead letters at once recreates the outage that caused them.

💡 **Track `replayed_at` and `replay_count`.** A message that has been dead-lettered, replayed and dead-lettered again is telling you the fix did not work — and you want to see that rather than loop forever.

## In Production

### The full retry policy

```python
class BaseTask(Task):
    autoretry_for = (ConnectionError, TimeoutError)
    retry_backoff = True
    retry_backoff_max = 600
    retry_jitter = True
    max_retries = 5
    acks_late = True
    reject_on_worker_lost = True

    def on_failure(self, exc, task_id, args, kwargs, einfo):
        if self.request.retries >= self.max_retries:
            dead_letter(self, exc)
```

💡 **`on_failure` firing after the final retry is the cleanest hook for dead-lettering**, because it catches both explicit `self.retry` exhaustion and `autoretry_for` exhaustion.

### The metrics that matter

```python
task_retries_total.labels(task=name, attempt=n, exception=type).inc()
task_retry_delay_seconds.observe(delay)
dead_letter_total.labels(task=name, exception=type).inc()
dead_letter_queue_depth.set(count)
dead_letter_oldest_age_seconds.set(age)
retry_budget_consumed_ratio.labels(task=name).set(ratio)
```

⚠️ **Alert on `dead_letter_total` rate, not on depth.** A DLQ with 500 old entries someone is working through is fine; one receiving 50 new entries per minute is an active incident.

💡 **`task_retries_total` labelled by exception type is the most useful diagnostic here.** A sudden rise in `ConnectionError` retries for one task points immediately at which dependency is failing, before any user-visible symptom.

### Retry rate as an early warning

```
Normal:     2% of tasks retry at least once
Degraded:  15%
Incident:  60%
```

💡 **The retry rate rises before the failure rate**, because retries succeed until they do not. It is one of the best leading indicators you can have, and it costs one counter.

### Draining the DLQ

**A DLQ nobody empties is a log file with extra steps.**

```
Weekly:
1. Group dead letters by exception type
2. For each group: is it a bug, a data problem, or a dependency?
3. Fix the cause
4. Replay, rate-limited
5. Anything that dead-letters twice gets investigated individually
```

⚠️ **Set a retention policy.** A `dead_letters` table that grows forever becomes unqueryable, and old entries are rarely replayable anyway because the world has moved on.

```sql
DELETE FROM dead_letters WHERE failed_at < now() - interval '30 days';
```

**Partition it by week** so cleanup is a `DROP` ([[06.13 - Partitioning and Sharding]]).

### Retries and idempotency

⚠️ **Every retry is a duplicate execution.** A task that is not idempotent and retries five times can produce five effects ([[07.5 - Idempotency Keys and Deduplication]]).

```
Task charges a card → the response times out → retry → charged again
```

💡 **`max_retries=5` on a non-idempotent task is a bug multiplier.** Either make it idempotent, or set `max_retries=0` and handle the failure explicitly — but do not retry a non-idempotent side effect and hope.

**The audit question: for every task with retries enabled, what happens if it runs five times?**

### The countdown trap

```python
raise self.retry(exc=e, countdown=300)
```

⚠️ **On Redis, `countdown` is implemented by the worker holding the message with an ETA, not by the broker.** With a long countdown and `acks_late`, the message stays unacked for the whole delay — and if the visibility timeout is shorter, it is redelivered while waiting ([[08.4 - Brokers and Result Backends]]).

**Keep `retry_backoff_max` well below your visibility timeout**, or use a broker with native delayed delivery.

💡 **The alternative is a separate retry queue with a scheduled sweep**, which decouples the delay from message-holding entirely. More machinery, and it scales better for long delays.

### Conduit's retry policy

| Task | Retryable | Max | Cap | Terminal → |
|---|---|---|---|---|
| `sync_source` | Network, 429, 5xx | 5 | 10 min | Invalid credentials → mark source failed, alert the owner |
| `fetch_document` | Network, 5xx | 3 | 2 min | 404 → mark document gone, no alert |
| `extract_text` | OOM (once, bounded) | 2 | 30s | Unsupported format → mark failed, no alert |
| `embed_chunks` | 429, network | 8 | 10 min | Content too long → chunk smaller, then terminal |
| `index_chunks` | Search backend errors | 5 | 5 min | Schema mismatch → DLQ, alert |
| `notify_collaborators` | Provider 5xx | 3 | 5 min | Invalid address → mark, no alert |

💡 **Note that most terminal failures do not alert.** A 404 on a document that was deleted at the source is normal. **Alerting on normal outcomes is how alerts get ignored**, and the discipline of deciding per-failure-type is what keeps the DLQ signal meaningful.

## Codebase

**Repo:** `celery/celery`, `Bogdanp/dramatiq`, `aws` (SQS docs)

**Question to answer:** In Celery, what exactly happens when `max_retries` is exhausted — which hooks fire, and in what order? Then: how does Dramatiq implement dead-lettering natively, and why did they make it a first-class feature when Celery did not?

**Read, in order:**

1. `celery/celery/app/task.py` — **`Task.retry`.** Note that it raises `Retry`, which the worker treats specially, and that `MaxRetriesExceededError` is raised when exhausted
2. `celery/celery/worker/request.py` — **how `Retry` is handled versus a normal failure**, and where `on_failure` and `on_retry` are invoked
3. `celery/celery/utils/time.py` — `get_exponential_backoff_interval`. **Celery's jitter implementation** — check whether it is full jitter
4. `dramatiq/dramatiq/middleware/retries.py` — **retry as middleware**, which is a cleaner design than a task method
5. `dramatiq/dramatiq/brokers/rabbitmq.py` — search for the dead letter queue setup. **Dramatiq creates a DLQ per queue by default**, and understanding why is the answer to the second question
6. **SQS redrive policy documentation** — broker-enforced dead-lettering, with `maxReceiveCount`

💡 Dramatiq's decision to make dead-lettering a default is instructive: **Celery leaves it to you, so most Celery deployments do not have one**, and failed tasks vanish into logs. A library default determines what most systems actually do, which is an argument for setting your own defaults deliberately ([[08.5 - Task Design Rules]]).

**Part 1 — Classify, then measure the cost of getting it wrong.** Build the exception taxonomy for a task calling an external API.

Then run a workload where 30% of failures are terminal, with three configurations: retry everything, retry nothing, and correct classification.

Measure: total worker time consumed, time until a real failure is visible in the DLQ, and successful completions.

**Retrying everything should waste a large fraction of capacity and delay the alert.** Quantify both.

**Part 2 — Backoff and the thundering herd.** 10,000 tasks all failing at the same instant against a dependency that recovers after 60 seconds.

Chart requests per second at the dependency over five minutes for: immediate retry, fixed 5s backoff, exponential without jitter, and exponential with full jitter.

**The first three should show sharp synchronised spikes; the fourth should be smooth.**

**Keep this chart.** It is the clearest possible argument for jitter and it takes fifteen minutes to produce.

Then measure time-to-full-recovery for each. **Jittered backoff should recover fastest**, which is the counterintuitive and important result.

**Part 3 — Retry amplification.** Three layers each retrying three times: an enqueueing service, the task, and the HTTP client inside the task.

Instrument the dependency to count calls. **One logical operation should produce 27.**

Chart total dependency load against failure rate for the naive version and with a retry budget at each layer.

**The naive version should grow quadratically; the budgeted one should stay bounded.**

**Part 4 — Build the DLQ.** A database-backed dead letter table with full context, plus a replay tool.

Then: generate 1,000 failures across five exception types. **Query the DLQ to answer three questions** — which task fails most, which exception dominates, and which organisation is affected.

Then replay, unrate-limited, against a still-broken dependency. **Watch it recreate the incident.** Then rate-limited, and confirm it does not.

Then track `replay_count` and demonstrate detecting a message that dead-letters twice.

**Part 5 — Retries multiply non-idempotent effects.** A task that sends an email, with `max_retries=5` and a flaky provider that succeeds but times out the response.

**Count the emails actually sent.** It should be up to five.

Then add a dedup record and confirm exactly one, regardless of retries.

**Part 6 — The countdown conflict.** Celery on Redis, `visibility_timeout=60`, a retry with `countdown=300`, `acks_late=True`.

**Confirm the message is redelivered while waiting for its retry**, producing concurrent execution.

Then fix it two ways — cap the backoff below the visibility timeout, and use a separate scheduled retry queue — and compare.

**Part 7 — Retry rate as a leading indicator.** Instrument retry rate, failure rate and success rate.

Then degrade a dependency gradually: 1% failures, then 5%, 20%, 50%.

**Chart all three metrics.** Confirm retry rate rises before failure rate becomes user-visible, and measure the lead time.

**That lead time is what you would gain by alerting on retries instead of errors.**

**Part 8 — The runbook.** Write it: what a retry rate spike means, what a DLQ rate spike means, how to triage the DLQ, how to replay safely, and when not to replay.

Then have someone introduce a failure and follow only the runbook.
