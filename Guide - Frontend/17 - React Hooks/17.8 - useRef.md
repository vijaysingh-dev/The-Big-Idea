# useRef

`useRef` returns a **mutable box** that persists across renders and does **not** trigger a re-render when its contents change.

```jsx
const ref = useRef(initialValue);
ref.current;    // read or write freely
```

That is the whole API. The two use cases — DOM access and instance-like storage — look unrelated but rest on the same property.

## useRef vs useState

| | `useState` | `useRef` |
| --- | --- | --- |
| Triggers re-render | yes | no |
| Value in render output | yes | should not be |
| Mutable | no — replace it | yes — assign to `.current` |
| Survives re-renders | yes | yes |
| Reset on remount | yes | yes |

The decision rule: **does the UI need to change when this value changes?** If yes, state. If no, ref.

```jsx
const [count, setCount] = useState(0);   // displayed → state
const timerId = useRef(null);            // internal bookkeeping → ref
const renderCount = useRef(0);           // diagnostic → ref
```

## DOM refs

```jsx
function Search() {
  const inputRef = useRef(null);

  useEffect(() => { inputRef.current?.focus(); }, []);

  return <input ref={inputRef} />;
}
```

The ref is `null` during render and is populated by React during the commit phase — **before** layout effects, and before passive effects. So it is safe to read in `useLayoutEffect` and `useEffect`, and never safe to read during render.

Legitimate DOM ref uses: focus, scroll, text selection, measurement, media playback control, canvas contexts, and integrating a non-React library.

Not legitimate: reading or writing values React controls, or manipulating DOM structure React owns — React will overwrite it on the next render ([[16.1 - Why React]]).

## Callback refs

```jsx
<div ref={node => {
  if (node) observer.observe(node);
  return () => observer.unobserve(node);   // React 19 cleanup form
}} />
```

A function ref is called with the node on mount and with `null` on unmount (or, in React 19, the returned cleanup runs instead). This handles cases an object ref plus effect cannot:

```jsx
// Measures whenever the node mounts, including conditional mounts
const measureRef = useCallback(node => {
  if (node) setHeight(node.getBoundingClientRect().height);
}, []);
```

An inline callback ref is recreated every render, so React calls it with `null` then the node on **every render**. Wrap it in `useCallback` if that matters.

Callback refs are also the answer for lists of refs:

```jsx
const nodesRef = useRef(new Map());

const register = useCallback((id) => (node) => {
  if (node) nodesRef.current.set(id, node);
  else nodesRef.current.delete(id);
}, []);
```

Handling the `null` call is essential — ignoring it leaves a map full of detached nodes ([[07.3 - Memory Leaks from Listeners and Detached DOM]]).

## Instance variables

The second use: values that must persist without causing renders.

```jsx
// Timer handles
const timerRef = useRef(null);
const start = () => {
  timerRef.current = setInterval(tick, 1000);
};
useEffect(() => () => clearInterval(timerRef.current), []);

// Previous value
function usePrevious(value) {
  const ref = useRef(undefined);
  useEffect(() => { ref.current = value; });
  return ref.current;
}

// Detecting the first render
const isFirst = useRef(true);
useEffect(() => { isFirst.current = false; }, []);

// Latest value without reacting to it
const latestProps = useRef(props);
useEffect(() => { latestProps.current = props; });
```

The last pattern deserves attention. It gives a callback access to current values without adding them as dependencies — used constantly inside libraries, and the problem `useEffectEvent` is designed to solve ([[17.3 - useEffect and the Dependency Array]]).

```jsx
const onChangeRef = useRef(onChange);
useEffect(() => { onChangeRef.current = onChange; });

const stableHandler = useCallback((v) => onChangeRef.current(v), []);
```

## The rules

**Do not read or write refs during render.**

```jsx
function Bad() {
  ref.current = ref.current + 1;   // impure
  return <p>{ref.current}</p>;     // will not update, and breaks concurrent rendering
}
```

Rendering must be pure ([[16.5 - Rendering and Purity]]). Reading a ref during render can produce different output for the same props if the render is retried, and writing during render is an observable side effect.

Refs belong in event handlers, effects, and callbacks.

The one documented exception is lazy initialization:

```jsx
function Video() {
  const playerRef = useRef(null);
  if (playerRef.current === null) {
    playerRef.current = new VideoPlayer();   // acceptable — creates once, idempotent
  }
}
```

This avoids `new VideoPlayer()` running on every render, which `useRef(new VideoPlayer())` would do.

**Refs do not trigger renders.** A value shown in the UI must be state:

```jsx
const count = useRef(0);
<button onClick={() => count.current++}>{count.current}</button>   // never updates
```

## Forwarding refs

In React 19, `ref` is a normal prop on function components:

```jsx
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}
```

Before 19, this required `forwardRef` ([[22.3 - forwardRef and useImperativeHandle]]):

```jsx
const Input = forwardRef((props, ref) => <input ref={ref} {...props} />);
```

Both are still supported; new code should use the prop form.

## Typing

```tsx
const inputRef = useRef<HTMLInputElement>(null);        // for DOM refs — read-only .current
const timerRef = useRef<number | null>(null);           // for mutable values
const countRef = useRef<number>(0);                      // initialized, never null
```

The distinction TypeScript enforces: `useRef<T>(null)` produces `RefObject<T>` with a readonly `current`, intended for React to populate. `useRef<T | null>(null)` produces a mutable ref you assign yourself.

## When a ref is the wrong tool

**Storing derived data** — compute it during render.
**Avoiding re-renders by hiding state in a ref** — the UI then does not update, which is a bug rather than an optimization.
**Caching across components** — refs are per-instance; use a module-level cache or a store.
**Replacing state for form values** — that is the uncontrolled pattern, which is legitimate, but reach for `defaultValue` and `FormData` rather than manual refs ([[16.8 - Controlled vs Uncontrolled Components]]).

## How senior engineers actually use this

**They use refs for things React does not model** — DOM handles, timer ids, third-party instances, and "the latest value" for stable callbacks.

**They never read refs during render**, which keeps components compatible with concurrent rendering.

**They use callback refs for measurement and registration**, since object refs plus `useEffect` miss conditional mounts.

**They handle the `null` call** in every callback ref to avoid retaining detached nodes.

**They treat "I'll put it in a ref to avoid a re-render" as a red flag** — if the UI depends on it, that is state.

## Common pitfalls

- Expecting a ref change to re-render.
- Reading or mutating `ref.current` during render.
- `useRef(expensiveInit())` running on every render.
- Reading a DOM ref during render, when it is still `null`.
- Inline callback refs firing with `null` on every render.
- Forgetting the `null` call in a callback ref, leaking detached nodes.
- Using refs to sidestep state management, producing a UI that silently does not update.

## Interview angle

"Difference between useRef and useState" is standard: both persist across renders, only state triggers re-renders, and refs are mutable in place. The follow-up worth volunteering is the two distinct uses — DOM access and instance variables — and the rule that refs must not be read or written during render because rendering has to be pure. The "latest value in a ref" pattern for stable callbacks is a good senior-level detail.
