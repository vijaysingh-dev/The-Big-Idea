# Function Declarations, Expressions and IIFE

Functions in JavaScript are **first-class values**: they can be assigned to variables, passed as arguments, returned from other functions and stored in data structures. Everything in this section follows from that.

## The forms

```js
// Declaration — hoisted and fully initialized
function add(a, b) {
  return a + b;
}

// Expression — the binding follows normal var/let/const rules
const subtract = function (a, b) {
  return a - b;
};

// Named function expression — the name is only visible inside
const factorial = function fact(n) {
  return n <= 1 ? 1 : n * fact(n - 1);
};

// Arrow function expression
const multiply = (a, b) => a * b;

// Method shorthand
const calc = {
  divide(a, b) {
    return a / b;
  },
};

// Constructor form — avoid, it evaluates strings at runtime
const bad = new Function("a", "b", "return a + b");
```

## Declaration vs expression: the hoisting difference

```js
sayHi();      // "hi" — the whole function is available during the creation phase
sayBye();     // TypeError: sayBye is not a function

function sayHi() { console.log("hi"); }
var sayBye = function () { console.log("bye"); };
```

Function declarations are registered *and assigned* during the creation phase of the execution context ([[01.2 - Execution Context and Scope Chain]]). `var sayBye` is registered but holds `undefined` until the assignment line runs, so calling it fails with a `TypeError` rather than a `ReferenceError`. With `const`, it would be a `ReferenceError` from the temporal dead zone instead.

A subtler point: function declarations inside blocks are inconsistently scoped across engines in sloppy mode. In strict mode and modules they are block-scoped, which is what you want. Never rely on a declaration inside an `if` leaking out.

## Named function expressions

The internal name is bound only inside the function body, which makes it safe for recursion even if the outer variable is reassigned:

```js
const f = function inner() {
  return typeof inner; // "function"
};
console.log(typeof inner); // "undefined" outside
```

The practical benefit is stack traces. An anonymous callback appears as `<anonymous>` in an error trace; a named one shows its name. Modern engines infer names from variable assignment (`const foo = () => {}` shows as `foo`), but callbacks passed inline still benefit from an explicit name.

## Parameters worth knowing

```js
function request(url, { method = "GET", retries = 3 } = {}) {
  // destructured options with defaults, and a default for the whole object
}

function sum(...nums) {
  return nums.reduce((a, b) => a + b, 0);
}

function greet(name, greeting = `Hello ${name}`) {
  return greeting; // later defaults can reference earlier parameters
}
```

`arguments` is an array-*like* object available in non-arrow functions. Rest parameters replaced it entirely — they are a real array, they work in arrow functions, and they do not deoptimize the function the way `arguments` historically did.

`fn.length` reports the count of parameters before the first default or rest parameter. Some libraries use this for arity detection, which is why adding a default to a parameter can silently change library behavior.

## IIFE

An **IIFE** (Immediately Invoked Function Expression) is a function defined and called in one expression. The wrapping parentheses turn the declaration into an expression so it can be invoked immediately.

```js
(function () {
  const secret = "not global";
  window.myLib = { get: () => secret };
})();

(async () => {
  const data = await fetch("/api").then(r => r.json());
  console.log(data);
})();
```

Historically IIFEs existed to create a private scope, because pre-2015 JavaScript had no block scope and no modules. Everything shipped as a `<script>` shared one global namespace, so libraries wrapped themselves in an IIFE to avoid collisions. jQuery, Underscore and every UMD bundle you have ever seen do exactly this.

Today `let`/`const` give block scope and ES modules give file scope, so the original motivation is gone. The remaining legitimate uses:

- **Top-level await in non-module scripts** — the async IIFE above.
- **Bundler output** — Rollup and Vite still emit IIFE-format bundles for `<script>` tags.
- **Immediate one-off computation** in a limited scope, though a plain block with `const` usually reads better.

## How senior engineers actually use this

**They default to `const` + arrow for callbacks and inline functions, and named declarations for top-level module functions.** The reasoning is practical rather than stylistic: declarations read well at module top level and produce clean stack traces, while arrows avoid `this` surprises inside callbacks ([[02.6 - Arrow Functions]]).

**They keep functions small and single-purpose because of testability, not aesthetics.** A function that takes its dependencies as parameters can be tested without mocks. This is the same dependency-injection idea that shows up in [[02.4 - Closure Patterns in Production]].

**They never use `new Function` or `eval` on anything user-influenced.** Both compile strings at runtime, defeat bundler analysis, break Content Security Policy ([[15.6 - Frontend Security]]), and open injection holes.

**They watch for accidental function creation in hot paths.** Defining a function inside a render or a loop allocates a new object every call. Usually irrelevant; occasionally the reason a React child re-renders on every parent render ([[17.7 - useCallback]]).

## Common pitfalls

- Relying on hoisting to call a function expression before its definition line.
- Assuming a function declaration inside an `if` block is visible outside it.
- Using `arguments` in an arrow function — it refers to the enclosing function's `arguments`, not the arrow's.
- Adding a default to an existing parameter and breaking code that reads `fn.length`.
- Reaching for an IIFE in modern module code where a plain block or a named function is clearer.

## Interview angle

The common questions are "difference between function declaration and expression" and "what is an IIFE and why was it used". Cover hoisting behavior precisely (declaration fully available, expression follows its binding's rules), and frame IIFEs historically: they solved the absence of block scope and modules, and are largely obsolete now except for async top-level code and bundler output. Mentioning that named function expressions improve stack traces is a small detail that reads as real experience.
