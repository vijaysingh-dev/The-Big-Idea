# Schema Design

#backend #databases #postgres #design

> **In one line:** The schema is the hardest thing to change and it constrains everything else, so the decisions worth agonising over are the ones about keys, types and constraints — not about normal forms.

---

## The Idea

💡 **Your schema is a set of promises about what data can exist.** Every constraint you add is a class of bug that becomes impossible; every constraint you leave out is a class of bug you will eventually find in production data, long after the code that created it was deleted.

**Push correctness into the schema wherever it will fit**, because the database enforces it against every code path, every service, every migration script and every person with a `psql` prompt.

---

## Keys

| Type | Size | Sortable | Guessable | Notes |
|---|---|---|---|---|
| `bigserial` | 8 bytes | Yes | **Yes** | Smallest, fastest. Leaks volume |
| `uuid` v4 | 16 bytes | **No** | No | **Random — terrible for index locality** |
| **`uuid` v7** | 16 bytes | **Yes** | No | Time-ordered. **The modern default** |
| ULID (as `uuid`) | 16 bytes | Yes | No | Same as v7, different encoding |

⚠️ **UUIDv4 as a primary key is one of the most costly schema mistakes available.** Random values scatter inserts across the entire index, causing page splits everywhere, rapid bloat, and a working set that will not stay in memory ([[06.1 - Storage Engines]]).

💡 **UUIDv7 gives you everything UUIDv4 does — non-guessable, generatable client-side, no coordination — with sequential index behaviour.** There is essentially no reason to use v4 for a primary key in 2026.

### Prefixed IDs at the API boundary

```
Internal:  550e8400-e29b-71d4-a716-446655440000  (uuid column)
External:  doc_01HQZX7C4M8NQR3TVWXYZ             (prefix + base32)
```

💡 **Store the raw UUID, render a prefixed form at the API boundary** ([[05.1 - REST Done Properly]]). Compact storage and good index behaviour internally, type-safe self-describing IDs externally.

### Natural vs surrogate keys

⚠️ **Natural keys are correct exactly when the value can never change.** An email can change. A country code can change. **A surrogate key means a change is one `UPDATE` instead of a cascade across every referencing table.**

**Use natural keys for genuinely immutable reference data, surrogate keys for everything else**, and always put a `UNIQUE` constraint on the natural key so the database still enforces it.

## Types

| Instead of | Use | Why |
|---|---|---|
| `varchar(255)` | `text` | No performance difference. `255` is a MySQL artifact |
| **`timestamp`** | **`timestamptz`** | **Always.** See below |
| `float` for money | `numeric(12,2)` or `bigint` minor units | Floats cannot represent 0.10 exactly |
| `text` for enums | `text` + `CHECK` | Constrained values |
| `text` for IPs | `inet` / `cidr` | Validation and operators |
| `text` for JSON | `jsonb` | Indexable, validated, binary |
| Two columns for a range | `tstzrange`, `int4range` | Overlap operators and exclusion constraints |

### timestamptz, always

⚠️ **`timestamp` stores a wall-clock reading with no reference point.** `timestamptz` stores an absolute instant (internally UTC) and converts on input and output. **It is the same 8 bytes.**

```sql
SET timezone = 'UTC';   -- in your application's connection setup
```

💡 **The one legitimate use of `timestamp` is a wall-clock time that is genuinely zone-independent** — "the shop opens at 09:00 local time everywhere". For anything that happened at a moment in time, use `timestamptz`.

### Enums: native or check constraint?

| | Native enum | Check constraint | Lookup table |
|---|---|---|---|
| Storage | 4 bytes | Full text | 4 bytes |
| Add a value | `ALTER TYPE ... ADD VALUE` — fast | Rewrite the constraint | `INSERT` |
| **Remove a value** | **Very difficult** | Easy | Easy |
| Extra metadata | No | No | **Yes** |

💡 **Default to a `CHECK` constraint on `text`.** Slightly more storage, and trivially alterable. Use a lookup table when the values need associated data; a native enum only when the set is stable and storage matters.

### JSONB: powerful and easy to misuse

**Good uses:** genuinely schemaless external data, sparse attributes, denormalised read models, audit payloads.

⚠️ **The entity-attribute-value trap:**

```sql
CREATE TABLE things (id uuid PRIMARY KEY, data jsonb);   -- do not
```

You have given up type checking, `NOT NULL`, foreign keys, planner statistics, and column-level permissions. **The planner's estimates for JSONB predicates are much worse than for real columns**, producing bad plans you cannot fix with statistics.

💡 **The rule: if you know the field exists on every row and you query it, make it a column.** JSONB is for the fields you do not know about.

```sql
CREATE INDEX ON documents USING gin (metadata jsonb_path_ops);   -- containment, smaller
CREATE INDEX ON documents ((metadata->>'source_type'));          -- one specific path
```

### Arrays

⚠️ **You cannot foreign-key an array element**, and you cannot attach metadata to the relationship. **Use an array when the values are simple labels; a join table when the relationship is an entity.**

## Constraints

```sql
CREATE TABLE documents (
    id           uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id       uuid NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
    source_id    uuid REFERENCES sources(id) ON DELETE SET NULL,
    title        text NOT NULL CHECK (length(title) BETWEEN 1 AND 500),
    status       text NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','indexing','indexed','failed')),
    size_bytes   bigint NOT NULL CHECK (size_bytes >= 0),
    content_hash bytea,
    metadata     jsonb NOT NULL DEFAULT '{}',
    created_at   timestamptz NOT NULL DEFAULT now(),
    deleted_at   timestamptz,

    CONSTRAINT indexed_has_hash
        CHECK (status <> 'indexed' OR content_hash IS NOT NULL),
    CONSTRAINT unique_hash_per_org
        UNIQUE NULLS NOT DISTINCT (org_id, content_hash)
);
```

**A cross-column `CHECK`** encodes a business rule the application cannot forget.

**`UNIQUE NULLS NOT DISTINCT`** (Postgres 15+) treats NULLs as equal for uniqueness — historically a "unique" column could hold unlimited NULL rows.

### Exclusion constraints

```sql
CREATE EXTENSION btree_gist;

CREATE TABLE bookings (
    id      uuid PRIMARY KEY DEFAULT uuidv7(),
    room_id uuid NOT NULL,
    during  tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

💡 **This makes double-booking structurally impossible**, atomically, at any isolation level, against any code path — solving the write skew problem from [[06.6 - Transactions and Isolation Levels]] **without any transaction reasoning at all.**

**Any "these two things must not overlap" rule should be an exclusion constraint, not application logic.**

### Soft deletes

⚠️ **Soft deletes contaminate every query in your application.** Forget `WHERE deleted_at IS NULL` once and you show deleted data.

```sql
CREATE INDEX ON documents (org_id, created_at) WHERE deleted_at IS NULL;
CREATE VIEW active_documents AS SELECT * FROM documents WHERE deleted_at IS NULL;
```

**Consider whether you need them at all.** An `archived_documents` table, or an audit log plus a hard delete, are often better. **Soft deletes are the default choice and often the wrong one.**

## Normalisation, Briefly

**Store each fact once.** Rename an organisation and you must update every document that copied the name; miss one and your data disagrees with itself.

**When denormalisation is correct:**

| Case | Why |
|---|---|
| **The value is a historical snapshot** | An invoice's address must not change when the customer moves |
| A counter you cannot afford to compute | `comment_count`, maintained by trigger or job |
| Cross-service data | Another service owns it; you keep a copy ([[10.4 - Data Ownership]]) |
| A materialised read model | Deliberately derived, with a defined refresh |

💡 **The snapshot case is the one people get backwards.** An order's shipping address should be *copied*, not referenced, because it records where the order actually went. **That is not denormalisation; it is a different fact.**

## In Production

### The audit columns

```sql
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now(),
created_by uuid REFERENCES users(id),
version    integer NOT NULL DEFAULT 1
```

💡 **The `version` column gives you optimistic concurrency and ETags for free** ([[03.3 - Methods Status Codes and Semantics]]). One integer, three uses.

⚠️ **`now()` returns the transaction start time**, not the statement time. Use `clock_timestamp()` if you genuinely need wall-clock time within a transaction.

### Multi-tenancy: put the tenant key everywhere

```sql
CREATE TABLE annotations (
    id       uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id   uuid NOT NULL,                       -- ← even though doc_id implies it
    doc_id   uuid NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    ...
);
CREATE INDEX ON annotations (org_id, doc_id);
```

| Benefit | |
|---|---|
| Every index starts with `org_id` | Naturally partitions your data |
| Row-level security is a one-column policy | No joins in the policy |
| A missing tenant filter is a missing column, not a missing join | Easier to audit |
| Future partitioning by tenant is possible | Cannot partition on a joined column |

💡 **This is one of the highest-value pieces of multi-tenant schema advice**, and it is the foundation for [[06.16 - Multi Tenant Data Models]].

### Naming conventions

```
Tables:       plural, snake_case          documents, source_credentials
Booleans:     is_ / has_ prefix            is_active, has_attachments
Timestamps:   _at suffix                   created_at, deleted_at
Foreign keys: <table_singular>_id          source_id, org_id
Constraints:  ck_ / fk_ / uq_ prefix       ck_documents_positive_size
```

⚠️ **Name your constraints explicitly.** Postgres generates names like `documents_status_check`, which are unstable across environments and useless in error messages.

```python
except UniqueViolationError as e:
    if e.constraint_name == "uq_documents_hash_per_org":
        raise DuplicateDocument()
```

### Column order affects storage

```sql
CREATE TABLE bad  (a boolean, b bigint, c boolean, d bigint);   -- 32 bytes
CREATE TABLE good (b bigint, d bigint, a boolean, c boolean);   -- 24 bytes
```

**Order columns from largest to smallest fixed-width type, then variable-width.**

💡 **On a billion-row table, 8 bytes per row is 8GB.** Not usually worth optimising for, and worth knowing when designing something very large — **it costs nothing to get right at design time.**

**Repo:** `saleor/saleor`, `getsentry/sentry`, `gitlabhq/gitlabhq`

**Question to answer:** Find three deliberate denormalisations in a large real schema and work out why each exists. Then: how does each project handle soft deletes, tenancy, and audit columns?

**Read, in order:**

1. `saleor/saleor/product/models.py` and `order/models.py` — **a large commercial schema.** Look for snapshot fields on orders: the price and address are copied, not referenced
2. `sentry/src/sentry/models/` — a very large Postgres schema under real pressure. Look for denormalised counters and their maintenance
3. `gitlab/db/structure.sql` — **the raw schema of a huge Rails+Postgres application.** Search for `CHECK` constraints, partial indexes and partitioned tables

5. Any of the three: search for `deleted_at` and see how consistently it is filtered

💡 The GitLab database documentation is the standout. **They run one of the largest open Postgres deployments and publish their rules** — column type guidance, when to add an index, constraint naming. **Reading it is closer to a code review from a very experienced DBA than to a tutorial.**

## Exercise

**Drill 6.10 — Design Conduit's schema twice**

```
drills/06-schema/
├── v1/{schema.sql, CRITIQUE.md}
├── v2/{schema.sql, constraints.sql, indexes.sql, DESIGN.md}
├── keys/{uuid_bench.py, RESULTS.md}
├── types/{jsonb_vs_columns.py, enum_migration.sql, RESULTS.md}
├── constraints/{exclusion.py, check_power.py, FINDINGS.md}
├── tenancy/{with_org_id.sql, via_join.sql, COMPARISON.md}
└── README.md
```

**Part 1 — The plausible first attempt.** Model Conduit's six entities the way a competent engineer would under time pressure: `varchar(255)`, `timestamp`, integer IDs, statuses as unconstrained text, JSONB for anything uncertain, soft deletes everywhere.

**Do not caricature it. It should look like most real schemas.**

**Part 2 — Critique it.** State what breaks concretely and when, then **verify three empirically** — load 5 million rows and measure.

**Part 3 — Key type benchmark.** Three identical tables keyed by `bigserial`, UUIDv4 and UUIDv7. Insert 5 million rows into each.

Measure **insert throughput over time** (not just total), final index size, index bloat, cache hit ratio, and point lookup latency.

**Chart insert throughput over time — UUIDv4's should degrade as the index grows past memory, while the others stay flat. That degradation curve is the argument.**

**Part 4 — JSONB versus columns.** The same five fields as real columns and inside a JSONB blob.

Compare storage, query latency with an index on each, **planner estimate accuracy**, and insert throughput.

**The estimate accuracy is the interesting one.** Run `EXPLAIN ANALYZE` on both and compare estimated versus actual rows — **the JSONB version should be much worse, and no amount of `ANALYZE` fixes it.**

**Part 5 — Try to remove an enum value.** Create a native enum, populate a table, then attempt to remove one value. **Document every step required.** Then do the same with a `CHECK` constraint and compare the effort.

**Part 6 — Constraints catching bugs.** Five application-level bugs: a negative size, an invalid status, an indexed document with no hash, two overlapping bookings, and a duplicate hash within an organisation.

**Confirm v1 accepts all five and v2 rejects all five.**

Then, for the overlap case, additionally implement it with Serializable isolation and compare — **including what happens when a second service inserts without knowing the rule.**

**Part 7 — Tenancy, both ways.** Annotations with `org_id` denormalised, and without it.

Compare query plans for a tenant-scoped list, index size, the complexity of an RLS policy, and what a missing tenant filter looks like in each.

**Write the RLS policy for both and note which you would trust more in a security review.**

**Done when:**
- `CRITIQUE.md` has a concrete consequence for every v1 decision, with three verified
- Your insert-throughput-over-time chart shows UUIDv4 degrading
- You have measured JSONB's planner estimate accuracy against real columns
- You have documented the full enum-value-removal procedure
- v2's constraints reject all five bugs that v1 accepts
- The exclusion constraint holds even against a service that does not know the rule
- You have written and compared RLS policies for both tenancy models
