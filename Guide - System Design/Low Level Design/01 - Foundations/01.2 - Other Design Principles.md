# Other Design Principles

These principles work alongside SOLID. They're mental filters — run your design through them before finalizing.

---

## Quick Reference

|Principle|Rule|Violation Smell|
|---|---|---|
|DRY|Don't Repeat Yourself|Copy-paste logic in 2+ places|
|KISS|Keep It Simple, Stupid|3-layer abstraction for a 2-field form|
|YAGNI|You Aren't Gonna Need It|Abstract factory for one known implementation|
|SoC|Separation of Concerns|Business logic inside a controller/route handler|
|LoD|Law of Demeter|`order.user.address.city`|
|CoI|Composition over Inheritance|Deep 5-level class hierarchy|
|High Cohesion|Related things stay together|"Util" class with 40 unrelated functions|
|Low Coupling|Independent change|Changing DB requires changing 8 files|

## DRY — Don't Repeat Yourself

### What It Says

Every piece of **knowledge** should have a single, authoritative representation in the system.

### The Subtlety

DRY is about _knowledge_, not _code_. Two similar-looking pieces of code are fine if they represent different concepts that happen to look the same today but will diverge tomorrow.

```python
# ❌ Duplication of knowledge — price calculation logic copied
class CheckoutService:
    def get_total(self, cart):
        return sum(item.price * item.qty for item in cart.items) * (1 - cart.discount)

class InvoiceService:
    def get_invoice_total(self, order):
        return sum(item.price * item.qty for item in order.items) * (1 - order.discount)
        # Identical logic — if pricing rule changes, must update in 2 places


# ✅ Single source of truth
class PricingEngine:
    def calculate_total(self, items, discount_rate: float) -> float:
        subtotal = sum(item.price * item.qty for item in items)
        return subtotal * (1 - discount_rate)

class CheckoutService:
    def get_total(self, cart):
        return self.pricing.calculate_total(cart.items, cart.discount)

class InvoiceService:
    def get_invoice_total(self, order):
        return self.pricing.calculate_total(order.items, order.discount)
```

### When NOT to Apply DRY

Premature DRY is dangerous. Two pieces of code that _look_ identical but represent _different business concepts_ should stay separate. Forcing them together creates **wrong abstractions** — the worst kind of coupling.

> "Duplication is far cheaper than the wrong abstraction." — Sandi Metz

## KISS — Keep It Simple, Stupid

### What It Says

Favor the simplest solution that solves the actual problem. Complexity should be justified by requirements, not by wanting to seem clever.

```python
# ❌ Over-engineered — StrategyFactoryRegistry for something used once
class SortStrategyRegistry:
    _registry = {}
    
    @classmethod
    def register(cls, name, strategy_class):
        cls._registry[name] = strategy_class
    
    @classmethod
    def get(cls, name) -> SortStrategy:
        return cls._registry[name]()

# ... used by one caller, one strategy

# ✅ KISS — just sort the list
items.sort(key=lambda x: x.created_at, reverse=True)
```

### Senior Engineer Lens

Complexity has a cost: debugging time, onboarding time, test maintenance. Each layer of abstraction should earn its keep. Ask: "what does this abstraction buy us?" If the answer is "future flexibility" for something with no concrete near-term requirement, lean toward KISS.

## YAGNI — You Aren't Gonna Need It

### What It Says

Don't implement functionality until it is actually needed. Don't design for requirements you _imagine_ you'll have.

```python
# ❌ YAGNI violation — multi-tenant aware from day one, single tenant product
class UserRepository:
    def find_by_email(self, email: str, tenant_id: str = None, 
                      region: str = None, shard_key: str = None):
        # massive query builder for features that don't exist yet
        ...

# ✅ Build what you need today
class UserRepository:
    def find_by_email(self, email: str) -> Optional[User]:
        return db.query(User).filter(User.email == email).first()
```

### YAGNI vs OCP — The Tension

YAGNI says don't over-build. OCP says design for extension. Resolution: **design for the extension points you can _see_, not ones you imagine**. If you have two payment methods today, abstract them. Don't abstract the payment currency system because "we might go global."

## SoC — Separation of Concerns

### What It Says

Different concerns (business logic, persistence, presentation, networking) should live in separate places and be independently changeable.

### Layers of SoC in a Backend System

```
┌────────────────────────────────────────┐
│  API Layer (routes, request parsing)   │  ← HTTP concern
├────────────────────────────────────────┤
│  Service Layer (business logic)        │  ← Domain concern
├────────────────────────────────────────┤
│  Repository Layer (data access)        │  ← Persistence concern
├────────────────────────────────────────┤
│  Infrastructure (DB, cache, queue)     │  ← I/O concern
└────────────────────────────────────────┘
```

```python
# ❌ SoC violation — business logic in route handler
@app.post("/orders")
def create_order(request: OrderRequest, db: Session):
    # Validation mixed with persistence mixed with notification
    if not request.items:
        return {"error": "empty order"}, 400
    total = sum(item.price * item.qty for item in request.items)
    order = Order(user_id=request.user_id, total=total)
    db.add(order)
    db.commit()
    smtp.send(request.email, f"Order placed: {order.id}")
    return {"order_id": order.id}


# ✅ Each layer owns its concern
@app.post("/orders")
def create_order(request: OrderRequest, service: OrderService = Depends()):
    result = service.place_order(request.to_domain())
    return OrderResponse.from_domain(result)  # controller only marshals


class OrderService:
    def place_order(self, order: Order) -> Order:  # pure business logic
        self.validator.validate(order)
        order.total = self.pricing.calculate(order)
        saved = self.repo.save(order)
        self.notifier.notify_placed(saved)
        return saved
```

## Law of Demeter (LoD) — Principle of Least Knowledge

### What It Says

A method should only call methods on:

1. The object itself (`self`)
2. Its direct field/attribute objects
3. Objects passed as parameters
4. Objects it creates locally

**Never reach through an object to talk to its internals.**

```python
# ❌ Violation — reaching through object chain
class OrderService:
    def get_customer_city(self, order):
        return order.user.address.city   # knows too much about internals
    
    def apply_regional_tax(self, order):
        country = order.user.address.location.country.code  # train wreck


# ✅ Tell, don't ask — delegate to the object that knows
class Order:
    def get_customer_city(self) -> str:
        return self.user.get_city()       # Order delegates to User

class User:
    def get_city(self) -> str:
        return self.address.city          # User delegates to Address


class OrderService:
    def get_customer_city(self, order):
        return order.get_customer_city()  # clean — one hop only
```

### Why It Matters at Scale

Violating LoD creates hidden coupling. If `Address` restructures, `OrderService` breaks — even though `OrderService` doesn't use `Address` directly. LoD violations make large systems fragile.

## Composition over Inheritance

### What It Says

Prefer building behavior by combining objects (composition) rather than extending class hierarchies (inheritance).

### Why Inheritance Breaks Down

```python
# ❌ Inheritance hierarchy becomes rigid
class Animal:
    def breathe(self): ...

class FlyingAnimal(Animal):
    def fly(self): ...

class SwimmingAnimal(Animal):
    def swim(self): ...

# Duck can fly AND swim — which class does it extend?
class Duck(FlyingAnimal, SwimmingAnimal):  # multiple inheritance pain
    pass

# Now add: can run. Can bark. Can be domesticated.
# The hierarchy explodes combinatorially.


# ✅ Compose behaviors as needed
class Animal:
    def __init__(self, name: str, behaviors: list[Behavior]):
        self.name = name
        self.behaviors = behaviors
    
    def perform(self, action: str):
        for behavior in self.behaviors:
            if behavior.can_perform(action):
                return behavior.execute(action)


class FlyBehavior:
    def can_perform(self, action): return action == "fly"
    def execute(self, action): print("Flying...")

class SwimBehavior:
    def can_perform(self, action): return action == "swim"
    def execute(self, action): print("Swimming...")

duck = Animal("Duck", [FlyBehavior(), SwimBehavior()])
duck.perform("fly")    # works
duck.perform("swim")   # works
```

### When Inheritance IS Appropriate

- "Is-a" relationship that's stable and won't need mixing
- Shallow hierarchies (1-2 levels)
- Sharing _interface contracts_ (ABCs), not implementations

## High Cohesion

### What It Says

Elements within a module/class should be strongly related to each other. A class that does one thing well has high cohesion.

**Measure:** If you removed one method from a class, would the other methods miss it? If yes → high cohesion. If no → low cohesion.

```python
# ❌ Low cohesion — unrelated responsibilities in one class
class AppUtils:
    def format_date(self, dt): ...
    def send_email(self, to, body): ...
    def compress_image(self, img): ...
    def calculate_tax(self, amount): ...
    def validate_phone_number(self, phone): ...

# ✅ High cohesion — DateFormatter, EmailSender, ImageProcessor are separate
```

## Low Coupling

### What It Says

Modules should know as little about each other as possible. A change in one module should not cascade into other modules.

**Coupling types (worst to best):**

1. **Content coupling** — one module modifies another's internals
2. **Common coupling** — shared global state
3. **Control coupling** — pass flags that control other module's behavior
4. **Data coupling** — pass only necessary data (ideal)

```python
# ❌ Control coupling — passing a flag to control behavior
class NotificationService:
    def send(self, message: str, is_urgent: bool):
        if is_urgent:
            self._send_sms(message)
        else:
            self._send_email(message)
        # caller is controlling internal behavior via flag


# ✅ Data coupling — caller picks the right method
class NotificationService:
    def send_email(self, message: str): ...
    def send_sms(self, message: str): ...

# Or better — Strategy pattern: caller provides the strategy
```

## How These Principles Interact

```
When you apply SRP      → Classes become small → need DIP to wire them
When you apply DRY      → Watch YAGNI — don't prematurely abstract
When you apply KISS     → Watch DRY — don't let laziness justify duplication
When you apply LoD      → Natural path to high cohesion and low coupling
Composition over Inherit → Enables OCP without rigid hierarchies
```

> "Name a principle you've violated and why."
