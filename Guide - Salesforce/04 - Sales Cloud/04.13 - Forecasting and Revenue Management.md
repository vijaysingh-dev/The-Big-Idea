# Forecasting and Revenue Management

## What forecasting is

A forecast is a prediction of how much will close in a period, rolled up through the sales organization. Reps forecast their deals, managers adjust, and the number reaching the executive team drives hiring, spending, and public guidance.

That last point is why forecasting deserves care. In a public company the forecast feeds guidance to investors, and a forecast process nobody trusts is a real business problem rather than a reporting inconvenience.

## Forecast categories

Every opportunity stage maps to a **forecast category**, and this is the mechanism the whole feature is built on.

| Category | Meaning |
| --- | --- |
| **Pipeline** | Early stage; possible but not predicted |
| **Best Case** | Might close, above the committed number |
| **Commit** | The rep is committing to this closing |
| **Closed** | Already won |
| **Omitted** | Excluded from the forecast entirely |

The forecast presents cumulative totals:

- **Closed** — won so far
- **Commit** — Closed plus Commit
- **Best Case** — Closed plus Commit plus Best Case
- **Pipeline** — everything open

So "Best Case" in the forecast view includes the committed deals. Reading it as only the best-case-category deals is a common misreading.

`ForecastCategoryName` defaults from the stage and can be overridden per opportunity. That override is the point — a rep can move a late-stage deal to Best Case because they know something the stage does not capture, or push an early deal to Commit because it is a formality.

**Omitted** deserves specific mention. It is how you exclude a deal from the forecast without deleting it or closing it — a deal that is real but whose timing is unknown, or one being handled outside the normal process.

## Collaborative Forecasts

The standard forecasting feature. Its structure:

**Forecast hierarchy.** Built from the role hierarchy, with a forecast manager designated at each level. Only users in the forecast hierarchy appear in forecasts, which means a rep whose role is not in it is invisible to their manager's forecast — a common configuration oversight.

**Forecast types.** What is being forecast. The main choices:

- Opportunity revenue, based on `Amount`
- Opportunity quantity
- Opportunity splits, so credit follows the split rather than ownership
- Product family revenue, forecasting each product line separately
- Custom currency or number fields on Opportunity

Several forecast types can run at once, which is how an organization forecasts both total revenue and recurring revenue separately.

**Adjustments.** Managers can adjust their team's numbers up or down without touching the underlying opportunities. The adjustment is recorded separately, so the difference between the rep's number and the manager's judgement is visible — which is often the most interesting number in the whole forecast.

**Quotas.** Per user, per period, per forecast type. Enables attainment reporting, and can be loaded through the API.

## Forecasting on splits

If opportunity splits are enabled, forecasting can run on splits rather than ownership. This is usually the correct configuration for any organization where more than one person is compensated on a deal.

The requirement is that the forecast type, the split type, and the compensation plan agree. When they do not — the forecast rolls up on ownership while commission pays on splits — reps see a forecast number that does not match their commission statement, and confidence in the system evaporates. See [[04.9 - Opportunity Teams and Opportunity Splits]].

## Custom forecasting

Collaborative Forecasts is configuration-driven and does not extend far. Organizations frequently need something it cannot do:

- Forecasting on a custom object rather than Opportunity
- Weighted pipeline using a custom probability model
- Multi-year or subscription revenue recognition
- Bookings versus billings versus recognized revenue as separate numbers
- Forecast snapshots for week-over-week comparison

The last one is the most commonly built. Salesforce shows the current forecast; it does not natively keep a history of what the forecast looked like each week, which is exactly what sales leadership wants for trend analysis.

```java
public with sharing class ForecastSnapshotBatch implements Database.Batchable<SObject>, Schedulable {

    private final Date snapshotDate = Date.today();

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT OwnerId, Owner.Name, ForecastCategoryName, Amount, CloseDate, StageName
            FROM Opportunity
            WHERE IsClosed = false AND CloseDate = THIS_FISCAL_QUARTER
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Opportunity> scope) {
        Map<String, Forecast_Snapshot__c> snapshots = new Map<String, Forecast_Snapshot__c>();

        for (Opportunity opp : scope) {
            String key = opp.OwnerId + '|' + opp.ForecastCategoryName;
            Forecast_Snapshot__c snapshot = snapshots.get(key);
            if (snapshot == null) {
                snapshot = new Forecast_Snapshot__c(
                    Snapshot_Date__c = snapshotDate,
                    Owner_User__c = opp.OwnerId,
                    Forecast_Category__c = opp.ForecastCategoryName,
                    Total_Amount__c = 0,
                    Opportunity_Count__c = 0
                );
                snapshots.put(key, snapshot);
            }
            snapshot.Total_Amount__c += (opp.Amount == null ? 0 : opp.Amount);
            snapshot.Opportunity_Count__c += 1;
        }

        insert snapshots.values();
    }

    public void finish(Database.BatchableContext ctx) { }

    public void execute(SchedulableContext ctx) {
        Database.executeBatch(this, 2000);
    }
}
```

Two things to note. The aggregation happens per batch chunk, so a rep whose opportunities span two chunks produces two snapshot rows — acceptable if the reporting sums them, and something to handle explicitly if not. And running weekly for a year across a large sales team produces a meaningful volume of snapshot records, which is a candidate for archiving. See [[23.4 - Archiving with Big Objects and External Storage]].

## Weighted pipeline

`ExpectedRevenue` is `Amount` multiplied by `Probability`, maintained by the platform. It is the simplest weighted pipeline number.

Its weakness: stage probability is a single org-wide default, and real close rates vary by segment, product, deal size, and rep. A more useful weighted number uses historical close rates:

```java
// Weighting by observed historical conversion rather than configured stage probability
Decimal weighted = opp.Amount * historicalCloseRate.get(opp.StageName + '|' + opp.Segment__c);
```

Calculating those rates from `OpportunityHistory` or a custom stage history object, and refreshing them quarterly, produces a forecast that reflects reality rather than an assumption someone made at implementation time.

## Fiscal years

Forecasting operates on fiscal periods. Salesforce supports **standard fiscal years** — twelve months starting in any month — and **custom fiscal years**, for 4-4-5 week patterns or other non-standard calendars.

Enabling custom fiscal years is one-way and affects reporting, forecasting, and the `FiscalQuarter` and `FiscalYear` fields on Opportunity. Establish it before go-live.

## The organizational problem

Worth stating, because it is the actual reason most forecast implementations struggle.

Forecasting depends on reps entering honest amounts, honest close dates, and honest categories. Reps are compensated on results, not on data quality, and there is a rational incentive to sandbag — to under-forecast so the number is beaten.

Configuration cannot fix this. What helps:

**Make the forecast the only number.** If leadership also runs a shadow spreadsheet, nobody maintains the forecast.

**Show adjustment history.** When a manager's adjustment is visible next to the rep's number, both parties become more careful.

**Report on forecast accuracy per person over time.** Consistently sandbagging or consistently over-forecasting both become visible, and visibility is what changes behaviour.

**Keep the required data minimal.** Every extra required field reduces the chance the forecast is maintained at all.

## Practical guidance

**Set fiscal year settings before go-live.**

**Put every relevant role in the forecast hierarchy.** Missing roles produce silently incomplete forecasts.

**Align the forecast type with the compensation plan.** Divergence destroys trust faster than any technical fault.

**Build forecast snapshots.** The trend is more useful than the current number, and the platform does not keep it.

**Use Omitted rather than deleting or closing deals** that should not count.

**Consider historical close rates** instead of configured stage probability for weighted pipeline.
