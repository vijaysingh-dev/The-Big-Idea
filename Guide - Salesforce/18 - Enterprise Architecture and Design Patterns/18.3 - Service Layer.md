# Service Layer

## What a service is

The place where a **business process** is implemented, once, callable from every entry point.

```
"Approve a warranty claim" means:
    verify coverage is active and the amount is within limit
    set the status and the approved amount
    create a payment record
    recalculate the asset's open claim total
    notify the ERP
    log the decision
```

That process should exist in exactly one place, whether it is triggered by a button, a trigger, a flow, a batch job, or an API call.

## The signature rules

**Static methods, taking collections.**

```java
public with sharing class ClaimApprovalService {

    public static void approve(Set<Id> claimIds, Decimal approvedAmount) { }

    public static void handleStatusTransitions(
        List<Warranty_Claim__c> claims,
        Map<Id, Warranty_Claim__c> priorClaims
    ) { }
}
```

**No `Trigger` reference anywhere.** The single constraint that makes the layer worth having.

**Tolerate a null prior map**, since the same method serves insert and update:

```java
Warranty_Claim__c prior = priorClaims == null ? null : priorClaims.get(claim.Id);
```

**Collections in, void or a result object out.** A service returning a single record for a single input invites a loop at the call site.

## The transaction boundary

The service is where a transaction's scope is decided — savepoints, partial success, and what rolls back with what.

```java
public with sharing class ClaimSettlementService {

    public static SettlementResult settle(Id claimId, Decimal amount) {
        Savepoint sp = Database.setSavepoint();

        try {
            Warranty_Claim__c claim = ClaimSelector.byIdForUpdate(claimId);

            validateSettlement(claim, amount);

            claim.Status__c = 'Approved';
            claim.Approved_Amount__c = amount;
            update claim;

            insert new Claim_Payment__c(
                Warranty_Claim__c = claim.Id,
                Amount__c = amount,
                Payment_Date__c = Date.today()
            );

            ClaimRollupService.recalculate(new Set<Id>{ claim.Asset__c });

            // enqueued, because a callout cannot follow DML in this transaction
            System.enqueueJob(new ErpSettlementQueueable(new Set<Id>{ claim.Id }));

            return SettlementResult.success(claim.Id);

        } catch (ClaimValidationException e) {
            Database.rollback(sp);
            // the log insert happens after the rollback, so it survives
            insert buildLog('ClaimSettlement', claimId, e);
            return SettlementResult.failure(e.getMessage());
        }
    }
}
```

**Entry points do not manage transactions.** A trigger, a controller, and a REST resource all call the service and let it decide. See [[10.5 - Savepoints, Rollback and Transaction Control]].

## Result objects, not exceptions, at the boundary

A service called from a Lightning controller or a REST endpoint should usually return a result rather than throwing, because the caller needs to render something either way.

```java
public class SettlementResult {
    public Boolean success;
    public String errorCode;
    public String message;
    public Id claimId;

    public static SettlementResult success(Id claimId) {
        SettlementResult result = new SettlementResult();
        result.success = true;
        result.claimId = claimId;
        return result;
    }

    public static SettlementResult failure(String message) {
        SettlementResult result = new SettlementResult();
        result.success = false;
        result.message = message;
        return result;
    }
}
```

**Exceptions for programmer error and genuinely exceptional conditions; results for expected business outcomes.** A claim exceeding its coverage limit is an expected outcome, not an exception — and modelling it as a result makes the caller handle it explicitly rather than by catching.

Where the service is called from a trigger, `addError` on the record is the right mechanism instead, because it blocks one record rather than the transaction. See [[11.1 - Trigger Anatomy and Events]].

## Sharing

```java
public with sharing class ClaimApprovalService { }
```

**Declare it explicitly.** A class with no keyword inherits the caller's context, and runs **without sharing** when it is the entry point — which for an `@AuraEnabled` method or a REST resource means no record-level security at all.

Where a service must genuinely bypass sharing — an aggregate across records the user cannot individually see — the pattern is a narrow `without sharing` inner class rather than opening the whole service:

```java
public with sharing class ClaimReportingService {

    public static Decimal totalExposureForAccount(Id accountId) {
        // deliberately elevated: the total is authorized, the individual records are not
        return new ElevatedQueries().sumClaimAmounts(accountId);
    }

    private without sharing class ElevatedQueries {
        private Decimal sumClaimAmounts(Id accountId) {
            AggregateResult result = [
                SELECT SUM(Claim_Amount__c) total
                FROM Warranty_Claim__c WHERE Account__c = :accountId
            ];
            return (Decimal) result.get('total');
        }
    }
}
```

Scoping the elevation to one method, with a comment saying why, is the difference between a deliberate decision and a security hole. See [[03.13 - Enforcing Security in Apex and SOQL]].

## What belongs in a service

**Business rules** — thresholds, eligibility, state transitions.

**Orchestration** across several objects.

**Transaction management** — savepoints, partial success.

**Change detection** against the prior state.

**Enqueuing async work.**

## What does not

**Queries.** They belong in a selector, so they are visible and countable.

**`Trigger` references.** Ever.

**Presentation logic.** Formatting, labels, and layout belong in the component.

**Per-object validation** that applies regardless of the process — that is domain. See [[18.4 - Domain Layer]].

**Raw DML scattered through the method** — batched at the end, or through a unit of work. See [[18.6 - Unit of Work]].

## One service per what?

The question people get stuck on.

**Per process, not per object.** `ClaimApprovalService` rather than a single `ClaimService` accumulating everything.

```
ClaimApprovalService      approve, reject, escalate
ClaimSettlementService    settle, reverse a settlement
ClaimIngestService        create from an ERP payload
ClaimRollupService        recalculate asset aggregates
```

Four focused services beat one class of two thousand lines. The signal to split: the class has more than a handful of public methods, or two developers keep conflicting in it.

**A shared `ClaimService`** holding genuinely common helpers — derived fields, Id collection — is reasonable alongside the process services.

## Calling from every entry point

The payoff, shown four ways.

```java
// Trigger handler
ClaimApprovalService.handleStatusTransitions(Trigger.new, Trigger.oldMap);
```

```java
// Lightning controller — thin, and translates exceptions for the UI
public with sharing class ClaimController {

    @AuraEnabled
    public static SettlementResult settle(Id claimId, Decimal amount) {
        return ClaimSettlementService.settle(claimId, amount);
    }
}
```

```java
// Invocable action for flow
public with sharing class ClaimApprovalActions {

    @InvocableMethod(label='Approve Claims')
    public static List<Result> approve(List<Request> requests) {
        // the invocable receives all rows at once, which is what keeps it bulk-safe
        Set<Id> claimIds = new Set<Id>();
        for (Request request : requests) {
            claimIds.add(request.claimId);
        }
        ClaimApprovalService.approve(claimIds, null);
        return buildResults(requests);
    }
}
```

```java
// Batch job
public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
    ClaimApprovalService.handleStatusTransitions(scope, null);
}
```

One implementation, four callers, no duplication. That is what the layer buys.

## Testing services

The reason the collection signature matters.

```java
@IsTest
static void claimsOverCoverageLimitAreNotApproved() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

    // constructed in memory — no DML, no queries, milliseconds
    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Claim_Amount__c = 900000, Status__c = 'Submitted')
    };
    Map<Id, Decimal> limits = new Map<Id, Decimal>{ claimId => 500000 };

    Test.startTest();
    List<Warranty_Claim__c> approvable = ClaimApprovalService.filterApprovable(claims, limits);
    Test.stopTest();

    Assert.isTrue(approvable.isEmpty(), 'A claim over its coverage limit is not approvable');
}
```

Where the service performs DML and queries, injection at the seams keeps tests fast — covered in [[18.8 - Dependency Injection and Testability]].

## Global services in packages

For a managed package, a service method marked `global` is a **permanent commitment** — it can never be removed or have its signature changed without breaking subscriber orgs.

The usual approach is a small, deliberately designed `global` surface delegating to `public` implementation, so the implementation can evolve while the contract holds. See [[18.12 - Package Design - Unlocked, Managed, 1GP vs 2GP]].

## Practical guidance

**Services are static, take collections, and never reference `Trigger`.**

**Declare the sharing keyword**, and scope any elevation to an inner class with a stated reason.

**Manage transactions in the service**, not in entry points.

**Return result objects** for expected business outcomes; throw for exceptional ones.

**One service per process**, not one per object.

**Keep entry points thin** — trigger, controller, and REST resource all route and nothing more.

**Query through selectors**, so consumption is visible.

**Test services with constructed records** and no DML.
