# Agent Architectures: Single vs Multi-Agent

## Single-Agent Architecture

One LLM with a set of tools. The model decides which tools to call and when to stop.

```
User Input
    │
    ▼
[Agent (LLM + Tools)]
    ├── tool: search
    ├── tool: calculator
    ├── tool: code_executor
    └── tool: write_file
    │
    ▼
Final Output
```

**When single-agent is sufficient**:

- Tasks involve 1–10 tool calls
- All tasks require the same knowledge/capabilities
- Simpler to debug and monitor
- Lower latency (no inter-agent communication overhead)

**When single-agent breaks down**:

- Task complexity requires deep specialization
- Too many tools causes the model to choose poorly (>15–20 tools degrades performance)
- Different subtasks require different context/system prompts
- Need to parallelize independent subtasks

## Multi-Agent Architecture

Multiple specialized agents collaborating, orchestrated by a coordinator.

### Supervisor Pattern

One orchestrator agent routes tasks to specialized workers:

```
[Supervisor Agent]
    │
    ├── "research needed" → [Research Agent]
    │                           ├── web_search
    │                           └── arxiv_search
    │
    ├── "code needed" → [Code Agent]
    │                       ├── python_executor
    │                       └── github_search
    │
    └── "writing needed" → [Writer Agent]
                               └── (pure generation, no tools)
```

```python
SUPERVISOR_PROMPT = """You are coordinating a team of specialized agents.
Agents available:
- research_agent: searches the web and academic papers
- code_agent: writes and executes Python code
- writer_agent: writes polished prose and reports

Given the user's request, route to the appropriate agent(s).
When all subtasks are done, output FINISH.
"""

def supervisor_node(state):
    response = supervisor_llm.invoke(
        [{"role": "system", "content": SUPERVISOR_PROMPT}] + state["messages"]
    )
    return {"next": response.content}  # "research_agent", "code_agent", "FINISH", etc.
```

### Peer / Network Pattern

Agents communicate laterally with no central coordinator:

```
[Agent A] ←→ [Agent B] ←→ [Agent C]
```

Less common in production — harder to reason about, harder to debug. Used in academic settings (debate, multi-perspective reasoning). Most production systems use supervisor pattern.

### Pipeline Pattern

Sequential specialist agents, each doing one stage:

```
[Researcher] → [Analyst] → [Writer] → [Reviewer]
```

Deterministic routing (not LLM-controlled). More reliable than dynamic multi-agent routing. Appropriate when the task structure is fixed.

## Tool Design for Agents

Tool quality is the biggest lever for agent performance. A well-described tool gets called correctly; a vague tool gets misused.

### Tool Description Anatomy

```python
tools = [{
    "name": "search_internal_docs",
    
    # CRITICAL: Model uses description to decide when to call the tool
    "description": """Search the company's internal knowledge base.
    USE THIS when: 
    - The question is about company policies, procedures, or internal products
    - You need information that would be in internal documentation
    - The question references internal teams, processes, or systems
    
    DO NOT USE for: general web knowledge, public information, coding help""",
    
    "parameters": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Natural language search query. Be specific about what you need."
            },
            "date_filter": {
                "type": "string",
                "description": "Optional: only return documents after this date (YYYY-MM-DD format)"
            }
        },
        "required": ["query"]
    }
}]
```

**Rules for tool design**:

1. Description should tell the model **when** to use the tool, not just what it does
2. Parameter names should be self-documenting
3. Fewer, broader tools > many narrow tools
4. Document edge cases and failure modes in the description

## Tool Execution Safety

Tools interact with real systems — databases, APIs, filesystems. Safety patterns:

### Idempotency

Read tools are safe to retry. Write/delete tools must be idempotent or require confirmation:

```python
class FilesystemTool:
    def delete_file(self, path: str) -> str:
        # Never actually delete — move to trash
        trash_path = f"~/.ai_trash/{Path(path).name}"
        shutil.move(path, trash_path)
        return f"Moved {path} to trash. Can be recovered."
    
    def write_file(self, path: str, content: str) -> str:
        # Check if file exists before overwriting
        if Path(path).exists():
            return f"File exists. Use overwrite_file to replace, or choose a different path."
        Path(path).write_text(content)
        return f"Created {path}"
```

### Sandboxing Code Execution

Code tools must run in isolated environments:

```python
import subprocess, tempfile, os

def execute_python(code: str, timeout: int = 10) -> str:
    with tempfile.NamedTemporaryFile(mode="w", suffix=".py", delete=False) as f:
        f.write(code)
        tmp_path = f.name
    
    try:
        result = subprocess.run(
            ["python", tmp_path],
            capture_output=True, text=True, timeout=timeout,
            # Security: no network access, limited filesystem
            env={"PATH": "/usr/bin", "HOME": "/tmp"},
        )
        return result.stdout or result.stderr
    except subprocess.TimeoutExpired:
        return "Execution timed out after 10 seconds"
    finally:
        os.unlink(tmp_path)
```

For production: use Docker containers, AWS Lambda, or E2B (sandbox-as-a-service) rather than subprocess.

## Failure Handling in Agents

### Retry with Backoff

```python
def execute_tool_with_retry(tool_name, args, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return execute_tool(tool_name, args)
        except ToolError as e:
            if attempt == max_retries:
                return f"Tool {tool_name} failed after {max_retries} retries: {e}"
            time.sleep(2 ** attempt)  # exponential backoff
```

### Tool Failure as Observation

Don't raise exceptions from tools — return informative error messages so the agent can reason about the failure:

```python
def web_search(query: str) -> str:
    try:
        results = search_api.search(query)
        return format_results(results)
    except RateLimitError:
        return "Search rate limit reached. Try again in 60 seconds or rephrase query."
    except NoResultsError:
        return f"No results found for '{query}'. Try a different search query."
```

The agent receives the error as an observation and can adapt — try a different query, use a different tool, or inform the user.

### Maximum Step Limits

Always bound the agent loop:

```python
MAX_STEPS = 15  # hard limit
SOFT_LIMIT = 10  # warn at this point

if step > SOFT_LIMIT:
    # Add to context: you're taking too long
    messages.append({"role": "system", "content": 
        "You have used many steps. Consider summarizing your findings and providing an answer now."})

if step >= MAX_STEPS:
    # Force stop
    return "Agent reached step limit. Partial result: " + get_best_answer(messages)
```

## Observability for Multi-Agent Systems

Multi-agent systems are hard to debug without traces. Every agent call, tool call, and state transition should be logged:

```python
import uuid

def run_agent_with_tracing(task, agents):
    trace_id = str(uuid.uuid4())
    
    with tracer.trace(name="multi_agent_run", trace_id=trace_id) as span:
        span.set_attribute("task", task)
        
        for step in run_agent(task, agents):
            span.add_event("agent_step", {
                "agent": step.agent_name,
                "action": step.action,
                "tool": step.tool_name,
                "result_length": len(str(step.result)),
                "step_latency_ms": step.latency_ms,
            })
```

Use LangSmith, Langfuse, or Arize Phoenix for multi-step traces.
