# Zero Downtime Migrations

#backend #databases #postgres #operations

> **In one line:** Old code and new code run simultaneously during every deploy, so every schema change must be compatible with both — which turns one migration into a sequence of four safe ones.

---

## The Idea

```
t=0    All pods running v1. Schema is v1.
t=1    Migration runs. Schema is now v2.
t=2    Rolling deploy: SOME pods v1, SOME pods v2.  ← the dangerous window
t=5    All pods v2.
```

⚠️ **At `t=2` both versions of your code are talking to the same database.** A migration that breaks v1 takes down half your fleet; one that requires v2 code fails before the deploy completes.

💡 **The rule that solves everything: every intermediate state must work with both the old and the new application code.** That single constraint generates the entire expand/contract pattern.

---

## Expand and Contract

```
1. EXPAND    Add the new thing. Old code ignores it. Both work
2. MIGRATE   Backfill data. Write to both. Both work
3. SWITCH    Read from the new thing. Old code still works
4. CONTRACT  Remove the old thing. Only after nothing uses it
```

### Renaming a column, properly

```sql
-- 1. EXPAND
ALTER TABLE documents ADD COLUMN author_id uuid;
CREATE INDEX CONCURRENTLY ix_documents_author_id ON documents (author_id);
```

```python
# 2. MIGRATE — deploy code that writes both
await conn.execute(
    "INSERT INTO documents (owner_id, author_id, ...) VALUES ($1, $1, ...)", data.author_id
)
```

```sql
-- 2b. Backfill in batches (see below)
-- 3. SWITCH — deploy code that reads author_id, still writes both
-- 4. CONTRACT — only after confirming nothing reads owner_id
ALTER TABLE documents DROP COLUMN owner_id;
```

⚠️ **A plain `ALTER TABLE ... RENAME COLUMN` is instant and it breaks every running v1 pod immediately.** The four-step version takes days and never causes an outage. **At any meaningful scale that trade is not close.**

## The Backfill

```sql
UPDATE documents SET author_id = owner_id;      -- never, on a large table
```

| Problem | |
|---|---|
| One enormous transaction | Holds back vacuum for its entire duration ([[06.7 - MVCC Vacuum and Bloat]]) |
| Locks every row it touches | Blocks concurrent writers |
| Massive WAL generation | Can fill disks and stall replicas |
| Cannot be paused or resumed | Kill it and everything rolls back |
| Bloat spike | Every row gets a new version at once |

### Batched, resumable, throttled

```python
async def backfill(batch_size: int = 5000, sleep: float = 0.1):
    last_id = await state.get("backfill_cursor", UUID(int=0))

    while True:
        rows = await conn.fetch(
            """
            WITH batch AS (
                SELECT id FROM documents
                WHERE id > $1 AND author_id IS NULL
                ORDER BY id LIMIT $2
            )
            UPDATE documents d SET author_id = d.owner_id
            FROM batch WHERE d.id = batch.id
            RETURNING d.id
            """,
            last_id, batch_size,
        )
        if not rows:
            break

        last_id = max(r["id"] for r in rows)
        await state.set("backfill_cursor", last_id)
        backfill_progress.set(await remaining_count())
        await asyncio.sleep(sleep)
```

| Property | Why |
|---|---|
| **Batched** | Each transaction is short; vacuum can keep up |
| **Keyset ordered** | No `OFFSET` scan cost ([[05.2 - Versioning Pagination and Filtering]]) |
| **Resumable** | Cursor persisted; a crash resumes rather than restarts |
| **Throttled** | The sleep is adjustable at runtime |
| **Observable** | Progress and remaining count as metrics |

💡 **Make the sleep and batch size runtime-configurable.** During a backfill you will want to slow down when replica lag climbs and speed up overnight — **hard-coding them means redeploying to adjust.**

⚠️ **Watch replication lag during any backfill.** WAL generated faster than replicas can apply pushes lag into minutes, and if you route reads to replicas your application starts serving stale data ([[06.12 - Replication and Failover]]).

```python
if await replication_lag_bytes() > 100 * 1024 * 1024:
    await asyncio.sleep(5)          # back off until replicas catch up
```

## Safe and Unsafe Operations

### Safe with a short `ACCESS EXCLUSIVE` lock

```sql
ALTER TABLE t ADD COLUMN c text;                     -- nullable, no default
ALTER TABLE t ADD COLUMN c text DEFAULT 'x';         -- PG 11+: metadata only
ALTER TABLE t DROP COLUMN c;
ALTER TABLE t ADD CONSTRAINT ... NOT VALID;
ALTER TABLE t VALIDATE CONSTRAINT ...;               -- SHARE UPDATE EXCLUSIVE only
CREATE INDEX CONCURRENTLY ...;
```

⚠️ **"Short lock" still means queued behind long transactions** ([[06.8 - Locking and Deadlocks]]). **Every migration needs `lock_timeout`.**

### Unsafe — full table rewrite

```sql
ALTER TABLE t ALTER COLUMN c TYPE bigint;
ALTER TABLE t ADD COLUMN c uuid DEFAULT gen_random_uuid();  -- volatile default
ALTER TABLE t ADD PRIMARY KEY (c);
CREATE INDEX ...;                                    -- without CONCURRENTLY
```

### The safe alternatives

Some type changes are free because the binary representation is unchanged:

```
varchar(50) → varchar(100)     free
varchar(n)  → text             free
int → bigint                   NOT free, rewrites
```

**Adding `NOT NULL` without a scan (PG 12+):**

```sql
ALTER TABLE documents ADD CONSTRAINT ck_title_nn CHECK (title IS NOT NULL) NOT VALID;
ALTER TABLE documents VALIDATE CONSTRAINT ck_title_nn;   -- weak lock, scans concurrently
ALTER TABLE documents ALTER COLUMN title SET NOT NULL;   -- instant: uses the constraint
ALTER TABLE documents DROP CONSTRAINT ck_title_nn;
```

💡 **Postgres 12 taught `SET NOT NULL` to trust an existing validated `CHECK` constraint.** This turns an hours-long exclusive lock into three fast statements, **and it is the single most useful migration technique in this note.**

**Adding a primary key without a rewrite:**

```sql
CREATE UNIQUE INDEX CONCURRENTLY ix_documents_pk ON documents (id);
ALTER TABLE documents ADD CONSTRAINT documents_pkey PRIMARY KEY USING INDEX ix_documents_pk;
```

## Migrations That Must Not Run in a Transaction

```python
# Alembic
def upgrade():
    with op.get_context().autocommit_block():
        op.create_index("ix_documents_author", "documents", ["author_id"],
                        postgresql_concurrently=True)
```

⚠️ **A `CREATE INDEX CONCURRENTLY` that fails leaves an invalid index** — not used by queries, but still maintained on every write.

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY ix_broken;
```

**Automate this check as a post-migration assertion.**

## In Production

### The migration wrapper

```python
async def run_ddl(sql: str, attempts: int = 10):
    for i in range(attempts):
        try:
            async with conn.transaction():
                await conn.execute("SET LOCAL lock_timeout = '3s'")
                await conn.execute(sql)
            return
        except asyncpg.LockNotAvailableError:
            await asyncio.sleep(random.uniform(1, 5))
    raise MigrationFailed(sql)
```

💡 **Fail fast and retry, rather than waiting and blocking.** A migration that waits 60 seconds for a lock has queued 60 seconds of application traffic behind it; **one that fails after 3 seconds and retries costs nothing.**

### Migrations run separately from deploys

```
❌  Deploy pod → run migration on startup → serve traffic
✅  Run migration as a job → verify → deploy pods
```

⚠️ **Running migrations on application startup means N pods racing to run the same migration.** Most tools take an advisory lock, so N−1 pods block on startup — delaying your deploy and possibly tripping readiness probes.

**Separate them so a migration failure does not become a deploy failure**, and so you can run a migration without deploying — which you will need for long backfills.

### Backward-compatible for at least one version

⚠️ **A rollback must work.** If deploy N+1 goes wrong and you roll back to N, **N must still function against the migrated schema.** That is the real reason for expand/contract — not just the rolling window, but reversing a bad deploy without a database restore.

💡 **The test worth writing: run your v1 test suite against the v2 schema.** If it passes, your migration is safe to deploy.

### Dangerous defaults in ORMs

```python
op.alter_column("documents", "owner_id", new_column_name="author_id")   # autogenerated
```

⚠️ **Autogenerated migrations produce the dangerous form by default**, because they describe the desired end state, not a safe path to it.

```python
FORBIDDEN = [
    "RENAME COLUMN", "RENAME TO", "ALTER COLUMN.*TYPE", "SET NOT NULL",
    r"CREATE INDEX(?! CONCURRENTLY)", r"DROP INDEX(?! CONCURRENTLY)",
]
```

**A linter rejecting these in a migration file, requiring an explicit override comment, is a small amount of work that prevents a real outage.**

### Long backfills need a home

⚠️ **A 500-million-row backfill takes days. It does not belong in a migration file.**

💡 **GitLab built a batched background migration framework precisely because backfills outlive deploys.** Migrations enqueue a background job; the job processes batches over hours or days, with progress tracking and automatic throttling based on database load. **For anything above a few million rows, this is the right shape.**

### The checklist

```
1. Is every intermediate state compatible with both old and new code?
2. Does it take ACCESS EXCLUSIVE, and for how long?
3. Is lock_timeout set, with retry?
4. Does it rewrite the table?
5. Is CREATE INDEX concurrent, and outside a transaction?
6. Is the backfill batched, resumable and throttled?
7. Is there a rollback path that works with data already migrated?
8. Has it been tested against a production-sized copy?
9. What is the plan if it must be aborted halfway?
```

⚠️ **Item 8 is the one that matters most and is skipped most.** A migration taking 200ms on a 10,000-row development table takes 40 minutes on 100 million rows, **and you will not discover that in staging with a small dataset.**

## Exercise

**Drill 6.11 — Rename a column on 50 million rows, with zero failed writes**

The flagship drill of section 06.

```
drills/06-migrations/
├── setup/{seed.py, load.py}
├── naive/{rename.sql, FINDINGS.md}
├── safe/{01_expand.sql, 02_dual_write.py, 02b_trigger.sql, 03_backfill.py, 04_switch.py, 05_contract.sql, RESULTS.md}
├── operations/{lock_timeout.py, invalid_index.sh, not_null.sql, type_change.py, RESULTS.md}
├── rollback/{v1_tests_on_v2.py, FINDINGS.md}
├── linting/{check.py, ci.yaml}
└── README.md
```

**Part 1 — Measure the naive version.** 50 million rows, continuous traffic at 500 writes/second and 2,000 reads/second.

Run `ALTER TABLE ... RENAME COLUMN`. Measure lock duration, failed queries, and application error rate.

**Then simulate the rolling deploy**: half your load generator uses the old column name. **Count the failures.**

**Part 2 — The full safe migration.** All five phases while traffic runs continuously.

**Requirement: zero failed writes and zero failed reads throughout.** Instrument your load generator to count every error.

Implement dual-write both ways — application code and trigger — and compare. **The trigger version should survive a code path you forgot to update; prove it by deliberately leaving one out.**

**Part 3 — The backfill under pressure.** Backfill 50 million rows while traffic runs.

Chart over the whole run: rows remaining, replication lag, table bloat, and application p99.

Then deliberately run it too fast — batch size 100,000, no sleep — and **watch replica lag climb and p99 degrade.** **Find the batch size and sleep that complete in reasonable time without measurable impact.**

Then kill the backfill halfway and restart it, **confirming it resumes rather than restarting.**

**Part 4 — Lock timeout under contention.** Start a 60-second query. Run a "safe" `ADD COLUMN` with no `lock_timeout`.

**Measure how many application queries queue behind it.** Chart availability.

Then with `lock_timeout = 3s` and retry: confirm the DDL eventually succeeds and no queue ever forms.

**Part 5 — Every unsafe operation, made safe.** For `SET NOT NULL`, `ALTER COLUMN TYPE int → bigint`, `ADD PRIMARY KEY`, and `ADD FOREIGN KEY`:

Measure the naive version's lock duration on 50M rows, then implement the safe alternative and measure again.

**Include the number of steps and total elapsed time for each safe version, so the trade is visible.**

**Part 6 — The rollback trap.** After phase 3, attempt to roll back to v1 code. Confirm it works.

Then construct a migration where it does **not** work — contracting too early — and demonstrate the failure.

Then write the automated test: **run the v1 test suite against the v2 schema in CI.**

**Part 7 — The linter.** A CI check rejecting dangerous patterns with an explicit override mechanism.

Test against ten migrations, five safe and five dangerous. **Then run it against your own naive migration from part 1 and confirm it would have been caught.**

**Done when:**
- Your naive rename caused measurable application errors, quantified
- The full safe migration completed with zero failed queries under load
- The trigger-based dual-write caught a code path you deliberately omitted
- You know the batch size and sleep that avoid replica lag on your setup
- Your backfill resumed correctly after being killed
- The unsafe-operations table shows lock duration before and after for four operations
- You have a rollback trap and a CI test that catches it
- Your linter rejects the part-1 migration
