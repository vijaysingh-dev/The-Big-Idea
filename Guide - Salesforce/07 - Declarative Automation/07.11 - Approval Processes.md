# Approval Processes

## The mechanism

An approval process is a declarative feature that submits a record for approval, routes it through steps, **locks the record** while pending, and takes actions on approval, rejection, or recall.

[[04.16 - Approval Processes in the Sales Cycle]] covers the sales application. This note covers the mechanism itself, which applies equally to warranty claims, expense records, contract terms, and anything else needing sign-off.

## Anatomy

**Entry criteria.** Which records can enter. A record not meeting them cannot be submitted.

**Initial submission actions.** Run on submission. Typically a field update setting a status, plus the automatic record lock.

**Steps.** Each with criteria, an approver, and behaviour on approve or reject. A step whose criteria are not met is skipped.

**Final approval, final rejection, and recall actions.**

Each action set can update fields, send email, create tasks, send outbound messages, or launch a flow. The flow option is the extension point — anything the built-in actions cannot do goes there.

## Approver selection

**Manager of the submitter** — uses `User.ManagerId`, not the role hierarchy. These are separate fields and are frequently out of sync, which is the most common cause of approvals reaching the wrong person. See [[03.8 - Role Hierarchy]].

**A specific user or queue.** A queue means any member can approve.

**A user from a lookup field on the record.** The flexible option, and the one worth defaulting to.

**Multiple approvers**, requiring either unanimous approval or first response.

The lookup-field approach is preferable for anything beyond "my manager", because it moves routing into automation you control. Editing an active approval process requires deactivating it, and deactivating with approvals pending is disruptive — so keeping the routing logic outside the process is what makes it changeable.

```java
public with sharing class ApproverAssignmentService {

    public static void assignClaimApprover(List<Warranty_Claim__c> claims) {
        Map<String, Id> approverByTier = new Map<String, Id>();
        for (Approval_Routing__mdt routing : Approval_Routing__mdt.getAll().values()) {
            approverByTier.put(routing.Region__c + '|' + routing.Tier__c, routing.Approver_User_Id__c);
        }

        for (Warranty_Claim__c claim : claims) {
            String tier = claim.Claim_Amount__c > 1000000 ? 'Executive'
                        : claim.Claim_Amount__c > 250000 ? 'Director'
                        : 'Manager';
            claim.Approver__c = approverByTier.get(claim.Region__c + '|' + tier);
        }
    }
}
```

Custom Metadata means changing an approver is a deployment of a record rather than a change to the process. See [[17.1 - Custom Metadata Types]].

## Record locking

While pending, only approvers and administrators can edit the record, and only fields the process permits.

**Apex cannot update a locked record either.** A trigger or batch job touching a record in approval fails. This is the behaviour that surprises developers, and it needs handling in any job that sweeps a table.

```java
if (Approval.isLocked(recordId)) {
    // the record is in an approval process
}

// Requires the org setting enabling record lock and unlock in Apex
Approval.unlock(recordId);
Approval.lock(recordId);
```

Unlocking behind the approver's back is usually a signal that the process design is wrong rather than that the lock is inconvenient. Where a batch job legitimately needs to update locked records — a nightly currency conversion, say — the pattern is to filter them out and report them, not to unlock:

```java
List<Warranty_Claim__c> updatable = new List<Warranty_Claim__c>();
List<Id> skipped = new List<Id>();

for (Warranty_Claim__c claim : scope) {
    if (Approval.isLocked(claim.Id)) {
        skipped.add(claim.Id);
    } else {
        updatable.add(claim);
    }
}
Database.update(updatable, false);
```

## Submitting from code

```java
public with sharing class ClaimApprovalService {

    public static List<Approval.ProcessResult> submit(List<Warranty_Claim__c> claims, String comment) {
        List<Approval.ProcessSubmitRequest> requests = new List<Approval.ProcessSubmitRequest>();

        for (Warranty_Claim__c claim : claims) {
            Approval.ProcessSubmitRequest req = new Approval.ProcessSubmitRequest();
            req.setObjectId(claim.Id);
            req.setComments(comment);
            req.setProcessDefinitionNameOrId('Warranty_Claim_Approval');
            req.setSkipEntryCriteria(false);
            requests.add(req);
        }

        return Approval.process(requests, false);
    }
}
```

Approving or rejecting works through the pending work item:

```java
List<ProcessInstanceWorkitem> items = [
    SELECT Id, ProcessInstance.TargetObjectId
    FROM ProcessInstanceWorkitem
    WHERE ProcessInstance.TargetObjectId IN :claimIds
];

List<Approval.ProcessWorkitemRequest> requests = new List<Approval.ProcessWorkitemRequest>();
for (ProcessInstanceWorkitem item : items) {
    Approval.ProcessWorkitemRequest req = new Approval.ProcessWorkitemRequest();
    req.setWorkitemId(item.Id);
    req.setAction('Approve');
    req.setComments('Within delegated authority');
    requests.add(req);
}
Approval.process(requests, false);
```

Each submission is DML plus the process actions, so bulk submission should be in batches of a few dozen rather than hundreds.

## Submitting from flow

A record-triggered flow can submit for approval through the **Submit for Approval** action, which is the usual way an automated submission is built.

The important detail: **approval processes do not submit records automatically.** Entry criteria decide who *may* enter, not who *does*. A claim created by an integration with an amount above the threshold sits unsubmitted unless something submits it.

Either the integration submits explicitly, or a record-triggered flow does. Forgetting this is a silent failure — records that should be in approval simply are not.

## Approval history

`ProcessInstance` is the approval, `ProcessInstanceStep` records completed steps, `ProcessInstanceWorkitem` records pending ones.

```sql
SELECT TargetObjectId, Status, CreatedDate, CompletedDate,
       (SELECT StepStatus, Actor.Name, Comments, CreatedDate FROM Steps ORDER BY CreatedDate)
FROM ProcessInstance
WHERE TargetObjectId IN :claimIds
ORDER BY CreatedDate DESC
```

The metric worth reporting is **time pending**, because a slow approval is a slow business process:

```sql
SELECT Actor.Name approver, COUNT(Id) pending
FROM ProcessInstanceWorkitem
GROUP BY Actor.Name
ORDER BY COUNT(Id) DESC
```

Run weekly, that finds the inbox that is the bottleneck.

## Approvals versus flow versus orchestration

Flow can now do much of what approvals do, so the choice is real.

**Approval processes give you** record locking, a standard approver interface in Lightning and mobile, native approval history, delegated approvers, and email approval responses. Rebuilding any of that is substantial work.

**Flow gives you** unlimited routing logic, dynamic step counts, mid-process integration, and changes without deactivation.

**Flow Orchestration** sits between: multi-step, multi-user processes with assignment and waiting, more flexible than approvals and more structured than a plain flow.

The guidance that holds: **approval processes for genuine approvals**, where locking and an audit trail matter. **Orchestration for multi-step processes that are not approvals** — onboarding, review workflows, checklists. Rebuilding an approval in flow to escape its limitations usually means rebuilding record locking badly.

## Limits and operational constraints

- 30 active approval processes per object, 15 steps each
- 25 approvals can be pending on one record
- Editing an active process requires deactivation
- Records created by integrations are not submitted automatically

## Practical guidance

**Keep steps few.** Three levels on a routine approval means the process takes a week, and the commercial cost usually exceeds the risk controlled.

**Set thresholds on value as well as percentage.**

**Configure delegated approvers.** `User.DelegatedApproverId` routes when someone is unavailable, and without it a holiday stops the process.

**Notify beyond email.** A custom notification or Slack message is faster than an inbox nobody reads.

**Handle locked records in every batch job** that touches an object with approvals.

**Report on approval duration.** It shows whether the process helps or obstructs.

**Route approvers through a lookup field**, so routing changes need no process deactivation.
