# Kubernetes for Backend Engineers

#backend #kubernetes #operations

> **In one line:** Kubernetes is a control loop that continuously moves the cluster toward a desired state you declared — and the objects a backend engineer actually needs are Deployment, Service, ConfigMap, Secret and a handful of others.

---

## The Idea

```
You declare:    "3 replicas of this image"
Controller:     observes 2 running → creates 1
                observes a node died → creates a replacement
                observes 4 running → deletes 1
```

💡 **Everything in Kubernetes is a reconciliation loop.** Nothing is imperative — you do not "start a pod", you declare that a pod should exist and a controller makes it so.

⚠️ **This explains most surprising behaviour.** Deleting a pod recreates it, because the ReplicaSet still wants three. **Editing a pod's image is reverted, because the Deployment owns it.** Change the desired state, not the observed state.

---

## The Objects That Matter

```
Deployment  → ReplicaSet → Pod → Container(s)
Service     → routes to Pods by label
Ingress     → routes external HTTP to Services
ConfigMap / Secret → configuration
PVC         → storage
```

### Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: documents
spec:
  replicas: 3
  selector:
    matchLabels: {app: documents}
  template:
    metadata:
      labels: {app: documents}
    spec:
      containers:
        - name: app
          image: ghcr.io/org/conduit@sha256:abc123
          ports: [{containerPort: 8000}]
          envFrom:
            - configMapRef: {name: documents-config}
            - secretRef: {name: documents-secrets}
```

⚠️ **`spec.selector` is immutable after creation.** Choosing labels badly means deleting and recreating the Deployment, which means downtime.

💡 **A Deployment creates a *new* ReplicaSet on every template change** and scales the old one down — **that is the rolling update mechanism** ([[10.10 - Deployment Strategies]]).

```bash
kubectl rollout history deployment/documents
kubectl rollout undo deployment/documents
```

**Old ReplicaSets are retained (10 by default), which is what makes rollback instant.**

### Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: documents
spec:
  selector: {app: documents}
  ports: [{port: 8080, targetPort: 8000}]
```

**A stable virtual IP and DNS name routing to whichever pods are currently *ready*.**

| Type | |
|---|---|
| `ClusterIP` | Internal only. **The default and usually correct** |
| `NodePort` | A port on every node. Rarely what you want |
| `LoadBalancer` | Provisions a cloud load balancer |
| `ExternalName` | A DNS alias |

⚠️ **Service load balancing is L4** — it balances *connections*, not requests. **For gRPC and HTTP/2, one connection carries everything, so all requests go to one pod** ([[10.7 - Service Discovery and Service Mesh]]).

```yaml
spec:
  clusterIP: None          # headless: DNS returns all pod IPs
```

💡 **A headless Service plus gRPC client-side load balancing solves this without a mesh**, and it is the fix most people do not know about.

### ConfigMap and Secret

```yaml
envFrom:
  - configMapRef: {name: documents-config}
```

⚠️ **Environment variables from a ConfigMap do not update in a running pod.** A ConfigMap change requires a rollout.

```yaml
metadata:
  annotations:
    checksum/config: "{{ sha256sum (toJson .Values.config) }}"
```

💡 **A checksum annotation forces a rollout on every config change**, which means every pod has the same values and a bad config is caught by your rollout health checks ([[10.8 - Configuration and Secrets]]).

⚠️ **Secrets are base64, not encrypted, unless etcd encryption at rest is enabled. Verify it.**

### StatefulSet — and when not to use it

| | Deployment | StatefulSet |
|---|---|---|
| Pod names | Random | **Ordinal: `db-0`, `db-1`** |
| Storage | Shared or none | **Per-pod PVC** |
| Startup | Parallel | **Ordered** |
| DNS | Service only | **Per-pod DNS** |

⚠️ **Do not run your production database in a StatefulSet unless you have a specific reason and an operator.** Backups, failover, upgrades and disk expansion are all your problem. **A managed database is almost always the right choice** ([[06.12 - Replication and Failover]]).

### Job and CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
```

⚠️ **`concurrencyPolicy: Allow` is the default**, so a job running longer than its interval overlaps with itself. **`Forbid` is usually what you want** ([[08.8 - Periodic Tasks and Distributed Cron]]).

⚠️ **A CronJob that fails to schedule does not alert.** It silently does not run ([[12.3 - Instrumenting Conduit End to End]]).

## Networking

```
Pod → Service DNS → kube-proxy (iptables/IPVS) → a pod IP
```

```
documents                                  same namespace
documents.default                          another namespace
documents.default.svc.cluster.local        fully qualified
```

⚠️ **DNS in Kubernetes is a common source of latency.** The `ndots:5` default in `/etc/resolv.conf` means `api.stripe.com` is tried as `api.stripe.com.default.svc.cluster.local` first — **four failed lookups before the right one.**

```yaml
dnsConfig:
  options: [{name: ndots, value: "2"}]
```

💡 **This single change measurably reduces external call latency**, and almost nobody knows about it ([[02.8 - DNS]]).

### NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  podSelector: {matchLabels: {app: documents}}
  policyTypes: [Ingress]
  ingress:
    - from: [{podSelector: {matchLabels: {app: gateway}}}]
```

⚠️ **By default every pod can reach every other pod.** A NetworkPolicy is what makes the gateway-only assumption from [[10.6 - API Gateway and BFF]] actually true.

**Requires a CNI that implements them** — Calico, Cilium. **Some clusters silently ignore them.** Verify by testing.

## Scheduling

```yaml
resources:
  requests: {cpu: "200m", memory: "256Mi"}     # for scheduling
  limits:   {memory: "512Mi"}                  # enforced
```

💡 **Requests determine placement; limits determine enforcement** ([[13.4 - Probes Resources and Autoscaling]]).

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector: {matchLabels: {app: documents}}
```

⚠️ **Without spread constraints, all three replicas can land on one node.** Redundancy that shares a failure domain is not redundancy ([[11.1 - How Systems Fail]]).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
  selector: {matchLabels: {app: documents}}
```

💡 **A PDB protects against *voluntary* disruptions** — node drains, cluster upgrades, autoscaler scale-down — not just your deploys.

⚠️ **`minAvailable` equal to `replicas` blocks node drains forever**, turning a routine cluster upgrade into a stuck operation.

## In Production

### The debugging sequence

```bash
kubectl get pods -l app=documents
kubectl describe pod <pod>              # ← Events at the bottom. Read these first
kubectl logs <pod> --previous           # the crashed instance
kubectl top pods
kubectl get events --sort-by=.lastTimestamp
```

💡 **`kubectl describe` Events answer most questions**: why a pod is Pending, why an image pull failed, why a probe is failing, why it was evicted. **It is the first command, not the fourth.**

| Status | Meaning |
|---|---|
| `Pending` | Cannot be scheduled — resources, taints, PVC unbound |
| `ImagePullBackOff` | Wrong tag, or missing credentials |
| **`CrashLoopBackOff`** | **Starts and exits. `logs --previous` is essential** |
| `OOMKilled` (exit 137) | Memory limit exceeded ([[13.1 - Containers From First Principles]]) |
| `Error` | Non-zero exit |
| **`Running` but not `Ready`** | **Readiness probe failing — no traffic** |

⚠️ **The last row is the one that confuses people.** The pod looks fine in `get pods` and receives no traffic, **because `READY 0/1` is easy to overlook.**

### Namespaces and quotas

```yaml
apiVersion: v1
kind: ResourceQuota
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    persistentvolumeclaims: "10"
```

💡 **A quota stops one team's runaway deployment from consuming the cluster.** With a quota in place, **every pod must specify requests** — which is a useful forcing function.

### RBAC for your application

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
rules:
  - apiGroups: ["coordination.k8s.io"]
    resources: ["leases"]
    verbs: ["get", "create", "update"]
```

⚠️ **The default ServiceAccount token is mounted into every pod.** If your application does not use the API:

```yaml
automountServiceAccountToken: false
```

**One line, and it removes a credential an attacker would otherwise find.**

### What to use, what to skip

| Object | Verdict |
|---|---|
| Deployment, Service, ConfigMap, Secret | **Essential** |
| Ingress or Gateway API | Essential for external traffic |
| PDB, topology spread | **Essential for availability** |
| HPA | Yes ([[13.4 - Probes Resources and Autoscaling]]) |
| NetworkPolicy | Yes, if your CNI supports them |
| CronJob | Yes, with `Forbid` |
| StatefulSet | **Only with an operator** |
| Service mesh | **Usually no** ([[10.7 - Service Discovery and Service Mesh]]) |
| Custom operators | Only if you are packaging software for others |

💡 **The genuinely useful surface is about eight objects.** Most Kubernetes complexity people encounter comes from adopting things they did not need.

### Managing manifests

| Tool | |
|---|---|
| Raw YAML | Fine for a small number of services |
| **Kustomize** | Overlays per environment. Built into `kubectl` |
| Helm | Templating and packaging. **Necessary for third-party charts** |

⚠️ **Helm templating produces YAML that is hard to read and hard to debug.** For your own applications, **Kustomize overlays are usually clearer**; use Helm for installing other people's software.

### Conduit's manifests

| Component | Objects |
|---|---|
| Gateway | Deployment (3), Service, Ingress, HPA, PDB, spread |
| Document service | Deployment (3), Service, HPA, PDB, spread |
| Workers | Deployment (2), **long `terminationGracePeriodSeconds`**, HPA on queue depth |
| Scheduler | Deployment (1), **Lease-based election** ([[07.6 - Leader Election and Coordination]]) |
| Migrations | Job, run before the deploy |
| Postgres, Redis, Kafka | **Managed services, not in-cluster** |

💡 **Running Postgres, Redis and Kafka outside the cluster is the right default for a small team.** The operational burden of running them well in Kubernetes is substantial and it is not where your product value is.

## Codebase

**Repo:** `kubernetes/kubernetes`

**Question to answer:** Trace what happens between `kubectl apply -f deployment.yaml` and a container running. Which controllers act, in what order? Then: how does a Service actually route traffic to a pod?

**Read, in order:**

1. `pkg/controller/deployment/deployment_controller.go` — **`syncDeployment`.** The reconciliation loop, and how it creates and scales ReplicaSets
2. `pkg/controller/replicaset/replica_set.go` — `manageReplicas`. **The simplest complete controller in Kubernetes**, and the clearest illustration of the reconcile pattern
3. `pkg/scheduler/schedule_one.go` — **filter then score.** Which nodes can run this pod, and which is best. **Where requests and topology constraints are evaluated**
4. `pkg/kubelet/kubelet.go` — `syncPod`. The node-level loop that actually starts containers
5. `pkg/proxy/iptables/proxier.go` — **the answer to the second question.** kube-proxy writes iptables rules mapping the Service IP to pod IPs. **Reading this makes Service networking concrete rather than magical**

💡 The ReplicaSet controller is the best single file for understanding Kubernetes. **It is short, and `manageReplicas` is literally "count what exists, compare to what is wanted, create or delete the difference".** Every other controller is that pattern with more conditions.

**Size:** 2 sessions.

## Exercise

**Drill 13.3 — Deploy Conduit properly**

```
drills/13-kubernetes/
├── cluster/{kind.yaml, setup.sh}
├── manifests/{base/, overlays/{dev,prod}}
├── networking/{service_l4.py, headless_grpc.py, dns_ndots.py, netpol.yaml, RESULTS.md}
├── scheduling/{spread.yaml, pdb.yaml, drain_test.sh, RESULTS.md}
├── debugging/{scenarios/, runbook.md}
├── config/{checksum.yaml, drift.sh}
└── README.md
```

**Part 1 — A real cluster, locally.** kind or k3d with three nodes across simulated zones. Deploy Conduit: gateway, document service, workers, scheduler, plus managed-service stand-ins.

**Kustomize base plus dev and prod overlays.**

**Part 2 — The L4 problem, reproduced.** Three gRPC server replicas behind a standard Service.

**Send 10,000 requests from one client and count requests per pod.** It should be roughly 10,000/0/0.

Then a headless Service with gRPC client-side round-robin. **Count again.**

Then scale to five mid-test and **measure how long until the client uses the new pods.**

**Part 3 — DNS latency.** Measure external DNS resolution time with the default `ndots:5` and with `ndots:2`.

**Count the failed lookups per external call in each.** Then measure end-to-end latency of a call to an external API in both configurations.

**Report the improvement.**

**Part 4 — Scheduling and disruption.** Deploy three replicas with no spread constraints.

**Check node placement. Then drain the node holding the most replicas and measure availability.**

Then add topology spread and a PDB, and repeat. **Confirm the drain respects the PDB and availability holds.**

Then set `minAvailable` equal to `replicas` and **confirm the drain blocks forever.**

**Part 5 — NetworkPolicy.** Confirm every pod can reach every other pod by default.

Apply a policy allowing only the gateway to reach the document service. **Confirm other pods are blocked.**

⚠️ **Verify your CNI actually enforces it.** Some clusters accept the object and ignore it — **test rather than assume.**

**Part 6 — Config drift.** Update a ConfigMap consumed as environment variables. **Confirm running pods keep the old values indefinitely.**

Then as a mounted file — **measure the propagation delay**, and confirm your application does not re-read it anyway.

Then add the checksum annotation and confirm every change triggers a rollout.

**Part 7 — Eight debugging scenarios.** Create each, then diagnose from `kubectl` alone, timed:

| Scenario | |
|---|---|
| Pending — insufficient resources | |
| Pending — unbound PVC | |
| ImagePullBackOff — wrong credentials | |
| CrashLoopBackOff — missing config | |
| **OOMKilled** | |
| **Running but not Ready** | |
| Evicted — node pressure | |
| Terminating stuck — finalizer or long grace period | |

**Write `runbook.md`: symptom, first command, likely causes, fix.**

**Then have someone else diagnose three scenarios using only your runbook, timed.**

**Part 8 — Migration Job before deploy.** A Job that runs migrations, and a deploy that waits for it.

**Confirm a failing migration blocks the deploy** rather than rolling out code against an unmigrated schema ([[06.11 - Zero Downtime Migrations]]).

**Done when:**
- Conduit runs on a three-node cluster with dev and prod overlays
- You reproduced 10,000/0/0 gRPC distribution and fixed it headlessly
- The `ndots` change measurably reduced external call latency
- A node drain respects your PDB, and an over-strict PDB blocks it entirely
- NetworkPolicy enforcement is verified, not assumed
- A ConfigMap change without a checksum left pods stale
- Someone else diagnosed three scenarios from your runbook within target time
- A failing migration Job blocks the deploy
