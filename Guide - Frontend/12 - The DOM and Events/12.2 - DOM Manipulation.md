# DOM Manipulation

Every DOM write invalidates layout. The browser is smart enough to batch those invalidations and recompute once per frame — unless you force it not to. Most DOM performance work is about not defeating that batching.

## The write queue

Style and DOM changes are queued and flushed at the next frame ([[01.7 - The Rendering Cycle]]):

```js
el.style.width = "100px";
el.style.height = "200px";
el.classList.add("active");
// one layout recalculation at the next frame, not three
```

But reading a layout-dependent property forces an immediate synchronous recalculation, because the browser must give you an accurate answer:

```js
el.style.width = "100px";
const h = el.offsetHeight;      // forces layout NOW
el.style.height = h + "px";
const w = el.offsetWidth;       // forces layout AGAIN
```

Properties that force layout include `offsetWidth/Height/Top/Left`, `clientWidth/Height`, `scrollWidth/Height/Top/Left`, `getBoundingClientRect()`, `getComputedStyle()` for layout-dependent values, and `innerText`.

The rule is **batch reads, then batch writes** ([[13.3 - Layout Thrashing]]):

```js
// Bad — read/write interleaved, layout per iteration
elements.forEach(el => {
  el.style.height = el.offsetHeight * 2 + "px";
});

// Good — one layout, then all writes
const heights = elements.map(el => el.offsetHeight);
elements.forEach((el, i) => {
  el.style.height = heights[i] * 2 + "px";
});
```

## Batching insertions

```js
// Bad — a DOM mutation per item
for (const item of items) {
  list.append(createRow(item));
}

// Better — one insertion
const fragment = document.createDocumentFragment();
for (const item of items) fragment.append(createRow(item));
list.append(fragment);

// Also fine — one parse, one insertion
list.innerHTML = items.map(rowHTML).join("");
```

The `innerHTML` version is often the fastest for large initial renders because the HTML parser is highly optimized, but it destroys existing children and their listeners, and it requires escaping every interpolated value ([[15.6 - Frontend Security]]).

A third option is building detached and attaching once:

```js
const container = document.createElement("ul");
// ...build inside container, which is not in the document...
list.replaceChildren(container);
```

Work on a detached element costs no layout at all, since it is not in the render tree.

`replaceChildren()` is worth knowing — it replaces all children in one operation, and with no arguments it empties an element (better than `innerHTML = ""`, which invokes the HTML parser).

## Style writes

```js
// Three separate style mutations
el.style.color = "red";
el.style.background = "blue";
el.style.padding = "1rem";

// One class change — preferred
el.classList.add("highlighted");

// One cssText assignment
el.style.cssText = "color: red; background: blue; padding: 1rem";

// Custom properties — one change drives many rules
el.style.setProperty("--progress", "60%");
```

Toggling a class is almost always better than setting individual styles: the CSS lives in the stylesheet where it belongs, it is one mutation, and it is overridable through the cascade.

Custom properties are the right tool when a value is genuinely dynamic ([[10.4 - Units Custom Properties and Theming]]) — set one property in JS and let CSS use it in as many rules as needed.

## Measuring correctly

```js
const rect = el.getBoundingClientRect();
// rect.top/left are relative to the VIEWPORT, not the document
// rect.width/height include transforms
```

Common confusions:

- `getBoundingClientRect()` returns viewport-relative coordinates and reflects any `transform`. `offsetTop`/`offsetLeft` are relative to `offsetParent` and ignore transforms.
- For document-relative position, add `window.scrollY` / `window.scrollX`.
- `offsetWidth` is rounded to an integer; `getBoundingClientRect().width` is fractional. Sub-pixel differences matter for precise positioning.
- `clientWidth` excludes the scrollbar; `offsetWidth` includes it.

Prefer observers over polling for size and position:

```js
const ro = new ResizeObserver(entries => {
  for (const entry of entries) {
    const { inlineSize, blockSize } = entry.contentBoxSize[0];
  }
});
ro.observe(el);
```

`ResizeObserver` fires only when the size actually changes, delivers the measurement without forcing a synchronous layout, and works for element resizes that `window.resize` never sees ([[12.5 - Custom Events and Observer APIs]]).

## Scrolling

```js
el.scrollIntoView({ behavior: "smooth", block: "center" });
window.scrollTo({ top: 0, behavior: "smooth" });
el.scrollTop = 0;

// Reading scroll position
window.scrollY;
el.scrollHeight - el.scrollTop - el.clientHeight;   // distance from bottom
```

Scroll handlers fire extremely often. Never do layout reads directly in one:

```js
window.addEventListener("scroll", () => {
  requestAnimationFrame(() => {
    const y = window.scrollY;
    header.classList.toggle("scrolled", y > 100);
  });
}, { passive: true });
```

`{ passive: true }` promises you will not call `preventDefault()`, which lets the browser scroll without waiting for your handler — a measurable smoothness improvement on touch devices.

For "is this element visible" logic, `IntersectionObserver` is strictly better than scroll math: it does not run on the main thread per scroll event and requires no measurement.

CSS often removes the need for JS entirely:

```css
html { scroll-behavior: smooth; }
.section { scroll-margin-top: 4rem; }   /* offset for a sticky header */
.carousel { scroll-snap-type: x mandatory; }
```

## Detached work and content-visibility

```css
.offscreen-section { content-visibility: auto; contain-intrinsic-size: 0 500px; }
```

`content-visibility: auto` tells the browser to skip layout and paint for offscreen content entirely. `contain-intrinsic-size` supplies a placeholder size so the scrollbar does not jump. For long documents this can be one of the largest single rendering wins available, and it requires no JavaScript.

## In React

Direct DOM manipulation and React's model conflict — React may overwrite your changes on the next render. Legitimate cases:

```jsx
const ref = useRef(null);

useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setPosition(computePosition(rect));
}, [deps]);
```

`useLayoutEffect` runs after DOM mutation but **before paint**, so measuring and adjusting there avoids a visible flash. `useEffect` runs after paint, which causes a one-frame flicker for positioning work ([[17.5 - useLayoutEffect vs useEffect]]).

Other valid direct-DOM cases: focus management, integrating a canvas or map library, scroll restoration, and reading measurements for a tooltip or virtualized list.

## How senior engineers actually use this

**They batch reads and writes**, and reach for the Performance panel when a scroll or resize feels sluggish — forced synchronous layout shows up explicitly as "Recalculate Style" and "Layout" markers with a warning triangle.

**They prefer observers to event handlers.** `IntersectionObserver`, `ResizeObserver` and `MutationObserver` are cheaper, more accurate and require no throttling.

**They toggle classes, not inline styles**, except for genuinely dynamic values which go through custom properties.

**They mark scroll and touch listeners passive** by default.

**They reach for CSS first.** `scroll-behavior`, `scroll-snap`, `content-visibility` and `position: sticky` each replace a chunk of JavaScript that used to be necessary.

## Common pitfalls

- Interleaved reads and writes causing layout thrashing.
- Measuring in `useEffect` and getting a visible flash of the unadjusted position.
- Non-passive scroll and touch listeners blocking scrolling.
- `innerHTML +=` in a loop, re-parsing everything each time.
- Polling with scroll handlers where `IntersectionObserver` applies.
- Confusing viewport-relative and document-relative coordinates.
- Mutating DOM that React owns and seeing it reverted on the next render.

## Interview angle

The core question is "how would you efficiently update a large list in the DOM" — answer with batching via `DocumentFragment` or a single `innerHTML`, avoiding interleaved reads, and using `requestAnimationFrame` for visual updates. Follow with the layout-thrashing explanation, since that is the underlying mechanism. Mentioning `content-visibility` and observers as modern alternatives shows you are current rather than reciting 2015 advice.
