# The Codebase First Method

#backend #meta #reading

> **In one line:** Never open a repo to look around. Open it with one question, trace one path, and stop.

---

## The Problem

You clone a repo with 400,000 lines of code. You open the folder tree. You see 200 directories. You read a few files at random, understand nothing, feel stupid, and close the tab.

This happens to everyone. It is not a knowledge problem, it is a **method** problem.

The mistake is trying to understand the repo. You cannot. Nobody understands a whole large repo, including the people who work on it full-time. They understand the paths they have walked.

---

## The Core Technique: Trace One Path

Pick one concrete thing that happens in the system. Follow it from start to finish. Ignore everything else, no matter how interesting it looks.

Examples of "one path":

| Repo | One path |
|---|---|
| uvicorn | A single GET request, from socket read to response written |
| Celery | One `.delay()` call, from your code to the worker running the function |
| Redis | One `GET key` command, from epoll wakeup to bytes sent back |
| Saleor | One GraphQL query for a product with its variants |
| Kafka | One `producer.send()`, from your call to bytes on disk |

Notice these are all **verbs**, not nouns. "Understand the consumer group logic" is a noun and it will fail. "Follow what happens when a consumer dies" is a verb and it will work.

## The Six Steps

### Step 1 — Write the question down first

Literally write it in your reading log before you open the editor.

> Bad: "Learn how Celery works."
> Good: "When exactly does Celery acknowledge a message — before or after my task function runs?"

A good question has a **factual answer** you either have or do not have. "Learn how X works" has no such property, which is why you can spend four hours and feel like you learned nothing.

### Step 2 — Find the entry point

Every repo has a door. Look in this order:

1. `README.md` — the "quick start" snippet is usually the entry point
2. `pyproject.toml` / `setup.py` — the `[project.scripts]` or `entry_points` section names the CLI function
3. `main.py`, `__main__.py`, `cmd/`, `server.go`
4. `docker-compose.yml` — the `command:` field of each service
5. The tests — `tests/` shows the public API being used correctly

Time-box this to five minutes. If you cannot find the door in five minutes, search for a string you know appears in the output, like an error message or a log line.

### Step 3 — Follow the call chain with tools, not eyes

Do not scroll. Use tools.

```bash
# Find where something is defined, not just mentioned
rg "def send_task" --type py

# Find every caller of a function
rg "\.send_task\(" --type py

# Find the string from a log line or error you saw
rg "Received task" --type py

# See file structure without opening files
rg "^class |^def " celery/worker/consumer/consumer.py
```

⚠️ **Grep for definitions, not usages, first.** Searching `send_task` gives you 200 hits. Searching `def send_task` gives you one.

### Step 4 — Use a debugger for the hard parts

Reading gets you 80% of the way. The last 20% — the part where five layers of abstraction meet — is much faster with a breakpoint.

```python
# Put this in the actual site-packages copy of the library
import pdb; pdb.set_trace()

# Then walk up the stack to see how you got here
(Pdb) w        # where — the full call stack
(Pdb) u        # up one frame
(Pdb) args     # what was passed in
(Pdb) l        # list source around here
```

For async code, `w` is less useful because the stack is shallow. Use it anyway, then look at the Task's coroutine.

💡 **The single best trick in this note:** install the library in editable mode or just edit the copy in your virtualenv. Add `print()` statements everywhere. Run it. Read the output. This is not beneath you — it is how professionals do it, and it is far faster than reading.

### Step 5 — Read the tests as documentation

Tests show you the intended usage and, more importantly, the **edge cases the authors were worried about**. A test named `test_consumer_reconnects_after_broker_restart` tells you the failure mode is real and handled.

```bash
# What did the authors think could go wrong?
ls tests/ && rg "^def test_" tests/ | grep -i "fail\|error\|retry\|timeout\|disconnect"
```

### Step 6 — Use git as a time machine

When you find code that looks strange, it usually is strange for a reason.

```bash
# Why does this line exist?
git log -L 45,60:celery/worker/request.py

# Who wrote it and what did the commit say?
git blame celery/worker/request.py | sed -n '45,60p'

# Find the commit and read the full message
git show <hash>
```

Commit messages and linked issues are where the real reasoning lives. This is how you learn *why*, not just *what* — and *why* is the part that makes you senior.

## What to Do When You Get Lost

You will get lost. Here is the recovery procedure.

| Symptom | Fix |
|---|---|
| Ten files deep, forgot the question | Go back to your reading log. Reread the question. Restart from step 2 |
| Hit a wall of abstraction (factories, registries, plugins) | Stop reading. Set a breakpoint at the far side and see what actually got called |
| Code is in a language you do not know | Read it anyway. Control flow is universal. Skip the syntax you cannot parse |
| The path branches into 5 options | Pick the one your config would use. Ignore the other four |
| Genuinely stuck for 30+ minutes | Note the question, move on. Come back after the drill — building often answers it |

## Reading Compiled or C Code

Do not be scared of C. For our purposes you need to read exactly four things:

```c
// 1. Struct definitions — these are the nouns of the system
typedef struct client {
    int fd;
    sds querybuf;
    list *reply;
} client;

// 2. Function signatures — the verbs
void readQueryFromClient(connection *conn);

// 3. Control flow — if, while, for. Same as everywhere
// 4. Comments — in Redis and Postgres these are essays and they are excellent
```

You can ignore pointer arithmetic, memory management and macros. They are implementation detail, not design.

## The Anti-Patterns

| Anti-pattern | Why it fails |
|---|---|
| Reading the folder tree top to bottom | No path, no question, no retention |
| Trying to understand everything before moving on | You will never move on |
| Reading the newest, cleverest file | The interesting logic is usually in the oldest, ugliest one |
| Skipping the tests | You miss every edge case the authors cared about |
| Reading without running | You will believe wrong things and not find out |
| Reading for four hours straight | Comprehension collapses after about 90 minutes |

## Session Structure

A reading session is 2 hours, structured:

| Time | Activity |
|---|---|
| 0:00–0:05 | Write the question in the reading log |
| 0:05–0:15 | Find the entry point. Run the thing if you can |
| 0:15–1:15 | Trace the path. Take notes only on surprises |
| 1:15–1:35 | Break |
| 1:35–1:50 | Answer your own question in writing, in plain words |
| 1:50–2:00 | Write down the new question this created |

That last step matters. Every session should produce the next session's question. That is how you build a chain instead of a pile.

**Drill 0.1 — Ten entry points**

For each of the ten repos below, find the entry point and write down the exact file and function. Five minutes maximum per repo. Set a timer.

```
drills/00-entry-points/

```

| Repo | What to find |
|---|---|

| saleor/saleor | Where the GraphQL schema is assembled |
| python/cpython | The eval loop function that executes bytecode |

**Done when:** `FINDINGS.md` has ten `path:function` entries and, for each, one sentence on how you found it. The "how" column is the actual learning — you are training a search strategy, not collecting trivia.
