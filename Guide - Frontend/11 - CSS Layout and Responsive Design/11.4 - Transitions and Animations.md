# Transitions and Animations

## Transitions

A transition interpolates a property between two states when the value changes.

```css
.button {
  background: var(--brand);
  transition: background 200ms ease-out, transform 150ms ease-out;
}

.button:hover {
  background: var(--brand-dark);
  transform: translateY(-1px);
}
```

The shorthand order is `property duration timing-function delay`. Listing properties explicitly is better than `transition: all` — `all` transitions properties you did not intend, including ones set by other rules, and it forces the browser to check every property on every change.

Transitions only fire between two *computed* values. Transitioning to or from `auto` does not work, which is why "animate height to auto" is a perennial problem. Modern solutions:

```css
.accordion {
  display: grid;
  grid-template-rows: 0fr;
  transition: grid-template-rows 300ms;
}
.accordion.open { grid-template-rows: 1fr; }
.accordion > div { overflow: hidden; }
```

The `0fr` to `1fr` grid transition animates to content height with no JavaScript measurement. `interpolate-size: allow-keywords` and `calc-size()` are arriving to make `height: auto` transitions work directly.

Similarly, transitioning `display: none` needs `@starting-style` and `transition-behavior: allow-discrete`:

```css
.popover {
  opacity: 0;
  transition: opacity 200ms, display 200ms allow-discrete;
}
.popover:popover-open { opacity: 1; }

@starting-style {
  .popover:popover-open { opacity: 0; }
}
```

`@starting-style` defines the value an element animates *from* when it first appears, which was previously impossible without a JavaScript double-`requestAnimationFrame` hack.

## Animations

```css
@keyframes slide-in {
  from { opacity: 0; transform: translateY(1rem); }
  to   { opacity: 1; transform: none; }
}

.toast {
  animation: slide-in 300ms ease-out both;
}
```

Full property list:

```css
animation-name: slide-in;
animation-duration: 300ms;
animation-timing-function: ease-out;
animation-delay: 0ms;
animation-iteration-count: 1 | infinite | 3;
animation-direction: normal | reverse | alternate | alternate-reverse;
animation-fill-mode: none | forwards | backwards | both;
animation-play-state: running | paused;
```

`animation-fill-mode` is the one people get wrong. Without `forwards`, an element snaps back to its pre-animation state when the animation ends. `both` applies the `from` state during the delay as well, which prevents a flash before a delayed animation starts.

Percentage keyframes give finer control:

```css
@keyframes pulse {
  0%, 100% { opacity: 1; }
  50% { opacity: 0.4; }
}
```

## Timing functions

```css
ease | ease-in | ease-out | ease-in-out | linear
cubic-bezier(0.4, 0, 0.2, 1)
steps(5, end)
linear(0, 0.25 25%, 1)     /* multi-point linear, for spring approximations */
```

Practical guidance: **`ease-out` for things entering**, since they should decelerate into place; **`ease-in` for things leaving**; **`ease-in-out` for movement between two on-screen positions**. `linear` looks mechanical for movement but is correct for continuous rotation and progress indicators.

`cubic-bezier(0.4, 0, 0.2, 1)` is the Material standard easing and a reasonable default.

Durations: 100–200ms for small state changes (hover, focus), 200–400ms for entrances and exits, and above 500ms starts to feel slow. Larger elements can afford slightly longer than small ones.

## The performance rule

Only two categories of property animate cheaply:

**`transform` and `opacity`** are handled by the **compositor thread**. They skip layout and paint entirely, and continue running smoothly even when the main thread is busy ([[13.2 - Reflow Repaint and Composite]]).

Everything else costs more. Animating `width`, `height`, `top`, `left`, `margin` or `padding` triggers **layout** on every frame — the most expensive stage. Animating `background-color`, `box-shadow`, `border-radius` or `color` triggers **paint**.

```css
/* Expensive — layout every frame */
.bad { transition: left 300ms, width 300ms; }

/* Cheap — compositor only */
.good { transition: transform 300ms, opacity 300ms; }
```

To move something, use `transform: translate()` rather than `left`/`top`. To resize, use `transform: scale()` where the visual result is acceptable — noting that `scale` distorts text and borders, which is why some cases genuinely need layout animation.

`will-change` promotes an element to its own compositor layer in advance:

```css
.card:hover { will-change: transform; }
```

Use it sparingly and remove it after. Each layer costs GPU memory, and applying `will-change` to many elements causes layer explosion, which is slower than not using it at all. It also creates a stacking context ([[10.5 - Positioning and Stacking Contexts]]).

## The FLIP technique

For animations that genuinely involve layout change — a card expanding, an item reordering — FLIP converts a layout animation into a transform animation:

**F**irst: record the element's position. **L**ast: apply the final state and record the new position. **I**nvert: apply a transform that visually returns it to the start. **P**lay: transition the transform away.

```js
const first = el.getBoundingClientRect();
el.classList.add("expanded");
const last = el.getBoundingClientRect();

const dx = first.left - last.left;
const dy = first.top - last.top;

el.animate(
  [{ transform: `translate(${dx}px, ${dy}px)` }, { transform: "none" }],
  { duration: 300, easing: "ease-out" }
);
```

The layout change happens once; the animation is pure transform.

## View Transitions

The modern replacement for most FLIP work:

```js
document.startViewTransition(() => {
  updateTheDOM();
});
```

```css
::view-transition-old(root) { animation: fade-out 200ms; }
::view-transition-new(root) { animation: fade-in 200ms; }

.card { view-transition-name: card-1; }
```

The browser snapshots before and after, and animates between them — including elements that moved, resized or changed position in the DOM. Naming an element with `view-transition-name` makes it animate as a continuous object across the change, which is how "shared element" transitions between routes work.

Cross-document view transitions extend this to full page navigations with a CSS opt-in.

## Web Animations API

```js
const animation = el.animate(
  [{ opacity: 0, transform: "scale(0.9)" }, { opacity: 1, transform: "none" }],
  { duration: 300, easing: "ease-out", fill: "forwards" }
);

animation.pause();
animation.reverse();
animation.finished.then(cleanup);
```

Keyframes in JavaScript, but running on the same engine as CSS animations — so still compositor-accelerated, unlike a `requestAnimationFrame` loop. The promise-based `finished` makes sequencing straightforward. Use it when the keyframe values are dynamic; use CSS when they are static.

## Respecting motion preferences

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

Not optional. Large-scale motion causes genuine physical discomfort for people with vestibular disorders. Note the goal is usually to remove *motion*, not all feedback — a fade is generally acceptable where a slide is not, so a more careful implementation replaces transforms with opacity changes rather than removing everything.

## How senior engineers actually use this

**They animate `transform` and `opacity` and treat anything else as needing justification.**

**They keep durations short.** Interface animation exists to explain a change, not to be admired. Anything over 400ms makes an application feel slow, and users encounter it hundreds of times per session.

**They use View Transitions for route and layout changes** rather than hand-rolling FLIP.

**They verify with the Performance panel.** The Rendering tab's "Paint flashing" and "Layer borders" overlays show immediately whether an animation is compositor-only.

**They ship the reduced-motion query with the first animation**, not as a later accessibility pass.

## Common pitfalls

- `transition: all`.
- Animating `left`/`top`/`width`/`height` and dropping frames.
- Missing `animation-fill-mode`, so the element snaps back.
- Transitioning to `height: auto` and getting nothing.
- `will-change` left on permanently, or applied to dozens of elements.
- No `prefers-reduced-motion` handling.
- Animations longer than 400ms on frequently-repeated interactions.
- Animating an element that is inside a container with `overflow: hidden` and wondering why it is clipped.

## Interview angle

"How do you make animations performant" is the question. Answer with the pipeline: `transform` and `opacity` are compositor-only, everything else triggers layout or paint; use `will-change` sparingly because layers cost memory; use FLIP or View Transitions when layout genuinely changes. Adding that you always ship `prefers-reduced-motion` handling turns a performance answer into a complete one.
