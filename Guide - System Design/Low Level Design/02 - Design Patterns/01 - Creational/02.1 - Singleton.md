# Singleton Pattern

## At a Glance

|||
|---|---|
|**Type**|Creational|
|**Intent**|Ensure a class has exactly one instance and provide a global access point|
|**Frequency in Backend**|★★★☆☆ — often misused; use judiciously|

---

## The Problem It Solves

Some resources must be shared globally and initialized once: DB connection pools, config loaders, logger instances, thread pools. Singleton controls instantiation and provides one shared reference.

---

## Implementations (Python)

### Thread-Safe with `__new__`

```python
import threading
from typing import Optional

class DatabaseConnectionPool:
    """
    Singleton DB pool — one pool per process.
    Thread-safe via double-checked locking.
    """
    _instance: Optional["DatabaseConnectionPool"] = None
    _lock = threading.Lock()
    
    def __new__(cls):
        # Double-checked locking — avoid lock on every access
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:  # re-check inside lock
                    cls._instance = super().__new__(cls)
                    cls._instance._initialized = False
        return cls._instance
    
    def __init__(self):
        # Guard against re-init on every __new__ call
        if self._initialized:
            return
        self._pool = self._create_pool()
        self._initialized = True
    
    def _create_pool(self):
        from sqlalchemy import create_engine
        return create_engine(
            "postgresql://...",
            pool_size=10,
            max_overflow=20,
            pool_pre_ping=True
        )
    
    def get_connection(self):
        return self._pool.connect()


# Usage — always same instance
pool1 = DatabaseConnectionPool()
pool2 = DatabaseConnectionPool()
assert pool1 is pool2   # True
```

### Pythonic: Module-Level Singleton (Preferred in Python)

```python
# config.py — module is imported once; module-level object is singleton by nature
import os
from dataclasses import dataclass

@dataclass(frozen=True)
class AppConfig:
    db_url: str
    redis_url: str
    secret_key: str
    debug: bool
    max_retries: int
    
    @classmethod
    def from_env(cls) -> "AppConfig":
        return cls(
            db_url=os.environ["DATABASE_URL"],
            redis_url=os.environ["REDIS_URL"],
            secret_key=os.environ["SECRET_KEY"],
            debug=os.environ.get("DEBUG", "false").lower() == "true",
            max_retries=int(os.environ.get("MAX_RETRIES", "3"))
        )

# Module-level instantiation — happens once
config = AppConfig.from_env()

# Usage anywhere
from config import config
print(config.db_url)
```

### Using `@lru_cache` (Clean and Lazy)

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def get_logger(name: str):
    """Returns the same logger for the same name — no class needed."""
    import logging
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    return logger

# Calling get_logger("orders") always returns the same instance
logger = get_logger("orders")
```

## Real-World Backend Use Cases

|Use Case|Why Singleton|
|---|---|
|DB connection pool|Pool creation is expensive; must be shared|
|App configuration|Load from env once; read-only after that|
|Logger|Same logger hierarchy across module|
|Feature flag client|Single connection to LaunchDarkly/Flagsmith|
|Circuit breaker registry|Shared state across service calls|
|In-memory cache|Shared cache between request handlers|

---

## When NOT to Use Singleton

- **Domain objects** — `Order`, `User` must have many instances
- **Stateful services with varying configuration** — testing becomes hard
- **Anything that varies by tenant/user** — Singleton is global, tenants need isolation
- **When DI container is available** — register as singleton scope in DI instead

---

## Singleton vs Dependency Injection

```python
# ❌ Singleton accessed globally — hard to test, hidden dependency
class OrderService:
    def place_order(self, order):
        pool = DatabaseConnectionPool()  # hidden dependency, hard to mock
        conn = pool.get_connection()
        ...

# ✅ Singleton managed by DI container — explicit dependency, testable
class OrderService:
    def __init__(self, db_pool: DatabaseConnectionPool):
        self._pool = db_pool     # visible dependency, injectable mock

# DI container registers pool as singleton scope
container.register(DatabaseConnectionPool, scope="singleton")
```

**Rule:** Use Singleton for instantiation control. Use DI for dependency delivery.

---

## Tradeoffs

|Pro|Con|
|---|---|
|Guarantees single instance|Global state — makes testing harder|
|Lazy initialization possible|Tight coupling when accessed globally|
|Controlled resource management|Violates SRP (manages own lifecycle)|
|Easy to access anywhere|Concurrency issues if not careful|

---

## Thread Safety Checklist

- [ ] Is initialization protected by a lock?
- [ ] Does the instance itself have mutable shared state? (lock its methods too)
- [ ] Does Python's GIL fully protect this use case?
- [ ] Is the instance truly stateless after init? (safest)
