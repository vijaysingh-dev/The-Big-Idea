# LocalStorage and SessionStorage

Two key-value stores with an identical API, differing only in lifetime and scope.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");        // "dark", or null if absent
localStorage.removeItem("theme");
localStorage.clear();
localStorage.length;
localStorage.key(0);
```

**`localStorage`** persists until explicitly cleared — across tabs, windows and browser restarts. Scoped per origin.

**`sessionStorage`** persists for the lifetime of a **tab**. Scoped per origin *per tab*. Two tabs on the same site have completely separate `sessionStorage`. Duplicating a tab copies it; opening a new tab does not.

Both are limited to roughly 5–10 MB per origin, both store **strings only**, and both are **synchronous**.

## The synchronous problem

Every read and write blocks the main thread. For small values this is microseconds and irrelevant. For large values it is not:

```js
localStorage.setItem("state", JSON.stringify(largeObject));
```

This serializes and writes to disk synchronously ([[08.5 - Serialization and Structured Clone]]). A 2 MB object can block for tens of milliseconds, and doing it on every state change — a common Redux persistence pattern — turns into visible jank.

Mitigations: debounce writes, store only what needs persisting rather than the whole state tree, or use IndexedDB for anything substantial ([[14.3 - IndexedDB]]).

Reading at startup is worse in one specific way: a synchronous read in the critical path delays first paint ([[13.1 - The Critical Rendering Path]]).

## Always guard both directions

```js
function getItem(key, fallback = null) {
  try {
    const raw = localStorage.getItem(key);
    return raw === null ? fallback : JSON.parse(raw);
  } catch {
    return fallback;
  }
}

function setItem(key, value) {
  try {
    localStorage.setItem(key, JSON.stringify(value));
    return true;
  } catch (err) {
    if (err.name === "QuotaExceededError") evictOld();
    return false;
  }
}
```

Reads fail when data was written by an older version of your app, or is corrupted. Writes fail on quota — and, importantly, **accessing `localStorage` at all throws in Safari private browsing in some versions and when cookies are blocked entirely**. A bare `localStorage.getItem()` at module top level can crash your entire application for those users.

Feature-detect properly:

```js
const storageAvailable = (() => {
  try {
    const k = "__test__";
    localStorage.setItem(k, k);
    localStorage.removeItem(k);
    return true;
  } catch {
    return false;
  }
})();
```

Checking `typeof localStorage !== "undefined"` is insufficient — the object exists but throws on use.

## Versioning

Stored data outlives your code. A schema change without versioning means every user with old data hits your fallback path or, worse, a subtle bug.

```js
const VERSION = 3;
const key = `app:v${VERSION}:settings`;
```

Changing the key on a breaking change is simpler than writing migrations, at the cost of losing the old data. For data worth migrating, store the version inside the value and migrate on read:

```js
function loadSettings() {
  const stored = getItem("app:settings");
  if (!stored) return DEFAULTS;
  return migrate(stored, stored.version ?? 1);
}
```

## Cross-tab synchronization

The `storage` event fires in **other** tabs of the same origin when a value changes — never in the tab that made the change:

```js
window.addEventListener("storage", (e) => {
  if (e.key === "auth-token") {
    if (e.newValue === null) logout();
    else refreshSession(e.newValue);
  }
  e.oldValue;
  e.url;
});
```

This is the standard mechanism for synchronizing logout across tabs — a real requirement, since a user who logs out in one tab expects the others to follow.

`BroadcastChannel` is cleaner for general cross-tab messaging, since it does not require writing to storage:

```js
const channel = new BroadcastChannel("auth");
channel.postMessage({ type: "logout" });
channel.onmessage = (e) => { if (e.data.type === "logout") logout(); };
```

Use `storage` events when the state genuinely lives in storage; use `BroadcastChannel` for ephemeral coordination.

## Security

**Everything in Web Storage is readable by any JavaScript on the page**, including injected scripts and third-party libraries. There is no `HttpOnly` equivalent.

Consequences:

- **Do not store auth tokens here** if you can avoid it. An XSS vulnerability means immediate, complete token theft, and the attacker can exfiltrate the token for use elsewhere. An `HttpOnly` cookie at least confines the attacker to the victim's browser ([[15.5 - JWT Sessions and Token Storage]]).
- **Do not store PII.** It persists indefinitely on shared and public machines.
- Storage is per **origin**, so `http://` and `https://` versions of the same host have separate stores, and a subdomain cannot read the parent's.

The counterargument sometimes offered — "if you have XSS you have lost anyway" — is not quite right. With an `HttpOnly` cookie the attacker can make requests as the user during the session; with a token in `localStorage` they can take it away and use it from their own infrastructure, potentially for a long time.

## What belongs here

**Yes:** UI preferences (sidebar collapsed, table column widths, sort order), draft form content, recently viewed items, a client-side cache with a TTL, feature-tour completion flags, non-sensitive analytics identifiers.

**No:** auth tokens, PII, anything large, anything the server needs (use cookies), anything that must survive across devices (use the server).

**`sessionStorage` specifically:** multi-step form progress, scroll position restoration, "return to this page after login" redirect targets — anything that should not leak between tabs.

## In React

```jsx
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => getItem(key, initialValue));

  useEffect(() => {
    setItem(key, value);
  }, [key, value]);

  useEffect(() => {
    const onStorage = (e) => {
      if (e.key === key && e.newValue !== null) setValue(JSON.parse(e.newValue));
    };
    window.addEventListener("storage", onStorage);
    return () => window.removeEventListener("storage", onStorage);
  }, [key]);

  return [value, setValue];
}
```

Two things this gets right: lazy initialization (the function form of `useState` avoids reading storage on every render), and cross-tab sync.

In SSR frameworks, reading storage during render breaks — there is no `window` on the server, and reading it in an effect causes a hydration flash. For values affecting the initial render, use a cookie instead ([[14.1 - Cookies]]).

## How senior engineers actually use this

**They wrap it once** in a module with try/catch, JSON handling, versioning and a namespace prefix, and never call the raw API elsewhere.

**They namespace keys** — `myapp:user:prefs` — because the origin is shared with anything else served from it, including third-party embeds.

**They keep it small and debounce writes.** Persisting an entire Redux store synchronously on every action is a well-known jank source.

**They never put tokens in it** without a specific, documented reason.

**They handle the storage-unavailable case**, because private browsing and blocked-cookie configurations are a real fraction of users.

## Common pitfalls

- Unguarded access throwing in private browsing or with cookies disabled.
- `JSON.parse` on corrupted or old-format data crashing at startup.
- Quota errors ignored, so writes silently fail.
- Storing tokens and treating XSS as theoretical.
- Expecting the `storage` event in the tab that wrote the value.
- Large synchronous writes blocking the main thread.
- Reading storage during SSR render.
- No versioning, so a schema change breaks returning users.

## Interview angle

"Difference between localStorage, sessionStorage and cookies" is a guaranteed question — cover lifetime, scope, size, server transmission and JS accessibility. The follow-up worth preparing is "where would you store a JWT", and the strong answer weighs `HttpOnly` cookies against `localStorage` on XSS exfiltration versus CSRF exposure, rather than asserting one is simply correct. Mentioning the synchronous-API cost and the cross-tab `storage` event shows practical depth.
