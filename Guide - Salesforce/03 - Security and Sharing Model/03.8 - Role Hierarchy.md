# Role Hierarchy

## What it does

The role hierarchy grants access **upward**. A user can see and edit the records owned by users below them in the hierarchy.

That is the whole mechanism. A sales manager sees their reps' opportunities because the manager's role sits above the reps' roles.

Access flows up, never down and never sideways. A manager sees their team's records; the team does not see the manager's, and two peers see nothing of each other's.

## What it is not

**It is not the org chart.** It is a record visibility structure that often resembles the org chart. When they diverge — a matrix organization, dotted-line reporting, a shared services team — the role hierarchy should follow the *visibility* requirement, not the reporting line.

**It is not the approval chain.** Approvals route through the `ManagerId` field on the User record, which is a separate field with a separate value. These two are frequently out of sync, and an approval routed to the wrong person is usually this.

**It is not permissions.** A role grants no object or field permissions whatsoever. Those come from profiles and permission sets. A user can have a very senior role and no access to an object at all.

**It is not required.** Users can have no role. They then get access only through ownership and sharing rules, and — importantly — records they own are not visible to anyone through the hierarchy.

## The structure

A tree, up to roughly 500 roles, with a practical depth limit of around 10 levels.

```
CEO
├── VP Sales
│   ├── Sales Director EMEA
│   │   ├── Sales Manager UK
│   │   │   ├── Sales Rep UK 1
│   │   │   └── Sales Rep UK 2
│   │   └── Sales Manager DACH
│   └── Sales Director APAC
└── VP Service
    ├── Service Manager
    │   ├── Service Coordinator
    │   └── Field Technician
    └── Knowledge Manager
```

VP Sales sees everything owned by anyone under them. Sales Manager UK sees the two UK reps' records. Service Manager sees nothing owned by sales, because there is no upward path.

## Grant Access Using Hierarchies

The hierarchy only grants access if the object's **Grant Access Using Hierarchies** checkbox is enabled.

For standard objects this is always on and cannot be changed. For custom objects it can be turned off, and turning it off is the *only* way to prevent managers from seeing their reports' records on that object.

The legitimate use case is narrow but real: performance reviews, compensation records, whistleblowing reports, or peer feedback, where a manager seeing the record would defeat the purpose. Outside those, leave it on.

## Roles and portal users

External users on Experience Cloud licenses interact with roles in a particular way that causes confusion.

**Customer Community** licenses have no roles at all. Access is granted through **Sharing Sets**, which give portal users access to records related to their own Account or Contact. This is deliberate: a portal with a million users cannot have a million roles.

**Customer Community Plus** and **Partner Community** licenses do get roles, and each portal-enabled Account generates its own small role hierarchy — typically three levels — beneath the account owner's role. This is why enabling a partner portal on many accounts can silently create thousands of roles and push an org toward the role limit.

Watching the role count in an org with a partner community is a genuine operational concern, because role hierarchy changes trigger sharing recalculation, and the cost scales with role count.

## Role hierarchy and performance

This is where architecture matters more than configuration.

Record access is materialized into share tables rather than computed at query time. The role hierarchy contributes to those tables through **group membership** — each role has an associated group, and a role's group includes everyone in it and below it.

Consequences:

**Changing a role's position triggers recalculation.** Moving a role in the tree means recomputing access for every record owned by anyone in that subtree. On a large org this is a long-running job.

**Deep hierarchies cost more.** Ten levels means more group membership rows and more recalculation work than four levels.

**Wide hierarchies at the top cost more.** A role directly under the CEO with 200 roles beneath it means a very large group.

**Ownership skew makes it worse.** If one user owns 500,000 records, every hierarchy change affecting their role recalculates all of them. See [[10.9 - Data Skew]].

The practical guidance: keep the hierarchy as shallow as the business allows. Most organizations need four to six levels for visibility purposes even if the org chart has twelve. Roles exist to answer "who should see whose records", and that question usually has fewer distinct answers than the reporting structure has levels.

## Roles in the data model

`UserRole` is a standard object with `ParentRoleId` forming the tree.

```sql
SELECT Id, Name, DeveloperName, ParentRoleId, ParentRole.Name
FROM UserRole
ORDER BY Name
```

Users in a role, and the roles beneath a given role, are frequently needed in code. Because there is no recursive query, walking the tree is level by level:

```java
public with sharing class RoleHierarchyService {

    public static Set<Id> getRoleAndSubordinateRoleIds(Id rootRoleId) {
        Map<Id, List<UserRole>> childrenByParent = new Map<Id, List<UserRole>>();
        for (UserRole role : [SELECT Id, ParentRoleId FROM UserRole WHERE ParentRoleId != null]) {
            if (!childrenByParent.containsKey(role.ParentRoleId)) {
                childrenByParent.put(role.ParentRoleId, new List<UserRole>());
            }
            childrenByParent.get(role.ParentRoleId).add(role);
        }

        Set<Id> result = new Set<Id>{ rootRoleId };
        List<Id> toProcess = new List<Id>{ rootRoleId };

        // single query above, then an in-memory walk, so hierarchy depth costs no extra SOQL
        while (!toProcess.isEmpty()) {
            Id current = toProcess.remove(0);
            if (childrenByParent.containsKey(current)) {
                for (UserRole child : childrenByParent.get(current)) {
                    if (result.add(child.Id)) {
                        toProcess.add(child.Id);
                    }
                }
            }
        }
        return result;
    }
}
```

The single query followed by an in-memory walk is the pattern to use. Querying per level costs one SOQL call per level and will eventually hit the limit on a deep hierarchy.

Getting the users beneath a role then becomes straightforward:

```java
Set<Id> roleIds = RoleHierarchyService.getRoleAndSubordinateRoleIds(managerRoleId);
List<User> team = [SELECT Id, Name FROM User WHERE UserRoleId IN :roleIds AND IsActive = true];
```

Salesforce also maintains role-derived groups, which is often the faster route when you need them for sharing:

```sql
SELECT Id, Name, Type, RelatedId
FROM Group
WHERE Type IN ('Role', 'RoleAndSubordinates') AND RelatedId = :roleId
```

`Role` contains only users directly in that role. `RoleAndSubordinates` contains that role and everything beneath it. These groups are what sharing rules actually target when you share "to a role and subordinates".

## Common problems

**Role and Manager field out of sync.** Visibility works, approvals go to the wrong person, or vice versa. Both need maintaining.

**Users with no role.** Their records are invisible to everyone except themselves and administrators, which usually surfaces as a manager complaining they cannot see a new hire's pipeline.

**Reorganizations causing recalculation storms.** Moving several roles at once during a reorg can queue hours of sharing recalculation. Plan these for a quiet window.

**Assuming the hierarchy grants sideways access.** Two peers under the same manager see nothing of each other's records. If they need to collaborate, that is a sharing rule, not a role change. See [[03.9 - Sharing Rules]].

**Using roles to model territories.** Roles are hierarchical and singular — a user has exactly one. Territories can overlap and a user can be in several. If the requirement involves overlapping coverage, roles are the wrong tool. See [[04.17 - Territory Management Deep Dive]].
