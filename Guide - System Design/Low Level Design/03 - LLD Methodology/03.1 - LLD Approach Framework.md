# LLD Approach Framework

A repeatable process for approaching any LLD problem — in interviews or real design sessions.

---

## The 6-Step Framework

```
1. Clarify Requirements
       ↓
2. Identify Core Entities
       ↓
3. Define Interfaces & Abstractions
       ↓
4. Design Classes & Relationships
       ↓
5. Handle Cross-Cutting Concerns
       ↓
6. Validate with Use Cases
```

---

## Step 1: Clarify Requirements (5 min in interview)

Before touching a class diagram, ask questions. Interviewers reward structured thinking.

### Functional Requirements (FRs) — What the system does

- What are the core user actions? (verbs)
- What data is stored/returned?
- What are the business rules?

### Non-Functional Requirements (NFRs) — How well it does it

- Scale: how many users? requests/sec?
- Availability: what's acceptable downtime?
- Consistency: eventual or strong?
- Latency: response time SLAs?
- Durability: data loss tolerance?

### Scope Bounding

Always ask: "For this LLD, should I focus on [core feature] or also include [auth/billing/admin]?" Get explicit scope confirmation.

**Template questions for any LLD:**

```
- Is this a new system or adding to existing?
- Single user or multi-tenant?
- What's the expected volume? (helps choose patterns)
- Any specific constraints? (must use SQL, must be CQRS, etc.)
- What are the failure scenarios we care most about?
- Do I need to design the API layer or just the core domain?
```

## Step 2: Identify Core Entities

Extract nouns from requirements. These become candidates for classes.

### Entity Identification Heuristic

```
From: "Users can place orders for products. 
       Orders can contain multiple items.
       Each item has a price and quantity.
       Users must pay before order ships."

Nouns:  User, Order, Product, Item, Price, Quantity, Payment, Shipment
                                                         
Filter out:
- Attributes (Price, Quantity → belong to Item)
- Duplicates (Item vs OrderItem → same thing)
- Value Objects (Money, Address → not entities)
- Trivial ones (System, Data → too generic)

Candidates: User, Order, OrderItem, Product, Payment
```

### Entity vs Value Object Quick Test

|Question|Entity|Value Object|
|---|---|---|
|Does identity matter?|Yes|No|
|Does it change over time?|Yes|No|
|Are two identical ones the same?|No|Yes|
|Can it exist alone?|Yes|Often no|

## Step 3: Define Interfaces & Abstractions

Identify the _variation points_ — places where behavior could differ. These become interfaces.

### Variation Point Detection

Ask: "Could this be done in multiple ways? Could this change without affecting everything else?"

```
Payment processing → multiple providers → PaymentStrategy interface
Notification sending → email/SMS/push → NotificationChannel interface  
Data persistence → SQL/NoSQL/cache → Repository interface
File storage → local/S3/GCS → StorageProvider interface
```

### Interface Design Rules

1. Name by _role_, not _implementation_ (`Notifier`, not `EmailNotifier`)
2. Small, focused interfaces (ISP)
3. Design from the caller's perspective
4. Methods should speak the domain language (`place_order`, not `insert_record`)

## Step 4: Design Classes & Relationships

### Relationship Types

```
Association:   A has reference to B           Order → User (has a user_id)
Aggregation:   A contains B (B can exist alone) Department ◇──→ Employee
Composition:   A contains B (B dies with A)    Order ◆──→ OrderItem
Inheritance:   A is a B                        CreditCard ──▷ PaymentMethod
Realization:   A implements B                  StripeGateway ──▷ PaymentGateway
Dependency:    A uses B temporarily            OrderService ···→ PricingEngine
```

### Class Design Checklist

For each class, define:

- [ ] Fields (attributes — use Value Objects where applicable)
- [ ] Methods (behavior — business rules live here)
- [ ] Invariants (rules that must always hold)
- [ ] State machine (if the object has a lifecycle)
- [ ] Events it emits (if event-driven)
- [ ] Collaborators (what it depends on)

### State Machine Design

```python
# Whenever an entity has a lifecycle, draw the state machine first
# Example: Order lifecycle

# States and valid transitions
ORDER_TRANSITIONS = {
    OrderStatus.DRAFT:     {OrderStatus.CONFIRMED, OrderStatus.CANCELLED},
    OrderStatus.CONFIRMED: {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID:      {OrderStatus.SHIPPED},
    OrderStatus.SHIPPED:   {OrderStatus.DELIVERED},
    OrderStatus.DELIVERED: set(),      # terminal
    OrderStatus.CANCELLED: set(),      # terminal
}

# Enforce in the entity
def transition_to(self, new_status: OrderStatus):
    allowed = ORDER_TRANSITIONS.get(self.status, set())
    if new_status not in allowed:
        raise InvalidStateTransition(
            f"Cannot transition from {self.status} to {new_status}"
        )
    self.status = new_status
```

## Step 5: Handle Cross-Cutting Concerns

These apply to almost every system. Address them explicitly.

### Validation

```python
# Input validation (at API layer) — prevent garbage entering
# Domain validation (in entity) — enforce business rules
# Cross-field validation (in domain service) — when one entity validates against another

class OrderValidator:
    def validate(self, order: Order):
        errors = []
        if not order.items:
            errors.append("Order must have at least one item")
        if order.total <= Decimal("0"):
            errors.append("Order total must be positive")
        if len(order.items) > Order.MAX_ITEMS:
            errors.append(f"Order cannot exceed {Order.MAX_ITEMS} items")
        if errors:
            raise ValidationError(errors)
```

### Error Handling Strategy

```
Domain errors    → DomainException subclasses (OrderNotFoundError, InsufficientStockError)
Validation       → ValidationError with field-level messages
Infrastructure   → Wrap in domain exceptions (don't leak DB errors to domain)
Unknown errors   → Let them propagate, catch at API boundary, return 500

Never:
- Swallow exceptions silently
- Return None instead of raising
- Expose DB errors to API clients
```

### Idempotency

```python
# For operations that must not double-execute (payments, order creation)
class OrderService:
    def place_order(self, command: PlaceOrderCommand) -> Order:
        # Use idempotency key to prevent duplicate processing
        existing = self._repo.find_by_idempotency_key(command.idempotency_key)
        if existing:
            return existing  # return same result, don't reprocess
        
        order = Order.create(command)
        order.idempotency_key = command.idempotency_key
        return self._repo.save(order)
```

### Retry Strategy

```
Transient errors (network timeout, rate limit, DB deadlock):
  → Retry with exponential backoff + jitter
  → Max 3-5 retries
  → Idempotent operations only

Non-transient errors (validation failure, not found):
  → Never retry — retrying won't fix them
  → Fail fast, return error

Example backoff: 1s, 2s, 4s with ±20% jitter
```

### Transaction Boundaries

```python
# Rule: one business operation = one transaction
# Cross-aggregate operations = use eventual consistency or Saga

# Application service defines transaction boundary
class OrderApplicationService:
    def place_order(self, command: PlaceOrderCommand):
        with self._uow.begin():        # transaction start
            order = Order.create(command)
            self._uow.orders.save(order)
            inventory = self._uow.inventory.find(command.product_id)
            inventory.reserve(command.quantity)
            self._uow.inventory.save(inventory)
        # transaction commits here — both saves atomic
        
        # After commit: dispatch events (outside transaction)
        self._event_bus.publish(order.get_events())
```

## Step 6: Validate with Use Cases

Walk through your design with the core use cases. Verify:

1. Can I trace a complete user flow through the classes?
2. Are there any orphaned classes (no one uses them)?
3. Are there any classes doing too much?
4. Can I easily add a new payment method / notification channel / etc.?
5. Can I write a unit test for the core business logic without a DB?

### Use Case Walkthrough Template

```
Use Case: Place Order
Actor: Customer

1. Customer submits PlaceOrderCommand (items, payment, address)
2. OrderApplicationService.place_order(command)
3. OrderValidator.validate(command) → raises ValidationError if invalid
4. Inventory.reserve(items) via InventoryRepository
5. Order.create(command) → Order entity with DRAFT status
6. Order.confirm() → transitions to CONFIRMED, emits OrderConfirmed event
7. OrderRepository.save(order)
8. Event dispatched → NotificationHandler, LoyaltyHandler, AnalyticsHandler
9. Return OrderId to customer

Failure paths:
- Item out of stock → InsufficientStockError → 409 Conflict
- Invalid payment method → ValidationError → 400 Bad Request
- DB failure → 500, order not created (transaction rolled back)
```

## LLD Interview Time Budget (45 min)

|Phase|Time|Activity|
|---|---|---|
|Requirements|5 min|Ask clarifying questions, define scope|
|Entities|5 min|Identify and categorize|
|High-level design|5 min|Draw class structure sketch|
|Core classes|15 min|Code 2-3 core classes with methods|
|Patterns|5 min|Identify and explain pattern choices|
|Extensions|5 min|How would you add X?|
|Cross-cutting|5 min|Error handling, concurrency, scale|

---

## Common LLD Mistakes to Avoid

|Mistake|Better Approach|
|---|---|
|Start coding immediately|Clarify requirements first|
|Too many classes upfront|Start with core entities, add as needed|
|No interfaces, only concrete classes|Every variation point = interface|
|Business logic in controllers|Domain logic in entities/services|
|God class (OrderManager does everything)|Split by responsibility|
|Ignoring failure cases|Explicitly design error paths|
|Over-engineering for "future scale"|Design for stated requirements|
