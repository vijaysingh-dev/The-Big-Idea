# Slots

#python #oop #memory #slots

> **In one line:** `__slots__` replaces each instance's `__dict__` with fixed storage for a declared set of attributes. You save memory and get slightly faster access, and you lose the ability to add arbitrary attributes. Worth it for classes with many instances, rarely otherwise.

---

## The Idea

A normal instance stores attributes in a per-instance dict ([[05.1 - How Dicts Work]]). With `__slots__`, the class declares its attributes up front, and each instance gets a small fixed array instead:

```python
class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

p = Point(1, 2)
p.z = 3            # AttributeError: 'Point' object has no attribute 'z'
p.__dict__         # AttributeError: no __dict__
```

```
regular instance                    slotted instance
┌──────────────┐                    ┌──────────────┐
│ header       │                    │ header       │
│ __dict__ ────┼──► { "x": 1,       │ x  ──► 1     │   attributes stored
│ __weakref__  │       "y": 2 }     │ y  ──► 2     │   directly in the object
└──────────────┘                    └──────────────┘
```

Each slot is a **descriptor** on the class (`Point.x` is a `member_descriptor`) that reads and writes a fixed offset inside the instance ([[06.5 - Descriptors]]).

---

## What You Gain

```python
import sys, tracemalloc

class Plain:
    def __init__(self, x, y): self.x, self.y = x, y
class Slotted:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y
```

Typical measurements for 1 million instances (exact numbers vary by Python version, because 3.11+ already shrank regular instances a lot):

| | Memory per instance | Attribute access |
|---|---|---|
| Regular class (3.12) | ~ 100–150 bytes incl. values storage | Baseline |
| `__slots__` | ~ 48–56 bytes | ~ 10–20% faster |
| `tuple` / `NamedTuple` | ~ 56 bytes | Index access |

The savings matter when you hold **hundreds of thousands to millions** of objects in memory: parsed records, graph nodes, cache entries, tokens. For a few hundred service objects they do not.

---

## What You Give Up

| Lost | Workaround |
|---|---|
| Adding attributes not in `__slots__` | Add `"__dict__"` to `__slots__` (but then you lose most of the savings) |
| Weak references | Add `"__weakref__"` to `__slots__` |
| `functools.cached_property` | It needs `__dict__`. Use a slot plus a manual cache, or a plain `property`. |
| Class-level defaults for slotted names | `x = 0` in the class body conflicts with slot `x` (ValueError). Set defaults in `__init__`. |
| Some pickling and copying edge cases | Handled for you in modern Python; custom `__getstate__` if needed |
| Monkeypatching instances in tests | Patch the class instead |

## Inheritance Rules

```python
class Base:
    __slots__ = ("id",)

class Child(Base):
    __slots__ = ("name",)        # declare ONLY the new attributes

class Sloppy(Base):
    pass                         # no __slots__ → instances get a __dict__ again; savings lost
```

- Every class in the hierarchy must declare `__slots__` (even an empty tuple) to keep instances dict-free.
- Do not repeat a parent's slot names in a child. It wastes space and hides the parent's descriptor.
- Multiple inheritance from two classes that **both** have non-empty slots raises a layout conflict `TypeError`. Mixins meant to combine with slotted classes should use `__slots__ = ()`.

---

## The Easy Way: Dataclasses

```python
from dataclasses import dataclass

@dataclass(slots=True, frozen=True)
class Point:
    x: float
    y: float
```

`slots=True` (3.10+) generates `__slots__` from the fields, which removes most of the boilerplate and the class-default conflict. This is the form to use in new code ([[07.2 - Dataclasses]]). Pydantic models do not use slots for fields, because Pydantic stores values in its own `__dict__`. They are the wrong tool for millions of tiny objects.

---

## When to Reach for Slots

| Use slots | Do not bother |
|---|---|
| Millions of small records held in memory at once | Service classes, repositories, clients (a handful of instances) |
| Nodes in a big graph or tree, a trie, an LRU's linked list | Classes that tests or frameworks need to monkeypatch |
| Hot inner-loop objects where attribute access is measurable | When columnar data (numpy, Polars, Arrow) would be better anyway |
| Preventing typos like `self.colour = ...` vs `self.color` on a value type | |

The last row is an underrated benefit: a slotted class raises `AttributeError` on a misspelled assignment instead of silently creating a new attribute.

## Codebase

**Repo:** `python/cpython`

**Question to answer:** How does `type.__new__` turn `__slots__ = ("x", "y")` into descriptors and offsets inside each instance?

**Read, in order:**

1. `Objects/typeobject.c` — in `type_new` (split into helpers such as `type_new_slots` / `type_new_descriptors` in newer versions), find where each slot name becomes a `PyMemberDef` with an offset, and where `__dict__` and `__weakref__` are added or not
2. `Objects/descrobject.c` — `member_get` / `member_set`: reading a slot is a fixed-offset memory read
3. `Lib/dataclasses.py` — `_add_slots()`: dataclasses must **create a new class** to add slots, because slots cannot be added to an existing class

**Size:** 1 session.
