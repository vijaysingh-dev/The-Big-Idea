# Image and Asset Optimization

Images are usually the largest bytes on a page and the most common LCP element. The HTML mechanics are in [[09.3 - Images Media and Loading Attributes]]; this note covers the pipeline and the React-specific parts.

## The checklist

1. **Right format** — AVIF or WebP with a JPEG fallback
2. **Right size** — never serve a 4000px image into a 400px slot
3. **Dimensions set** — prevent layout shift
4. **Lazy below the fold**, eager and high-priority above it
5. **Served through a CDN** that negotiates format and size

Most of the win is in points 1 and 2. A correctly sized AVIF is often 10–20% the bytes of an unoptimized JPEG.

## Format

| Format | Relative size | Use |
| --- | --- | --- |
| AVIF | ~50% of WebP | photos — best compression, slower to encode |
| WebP | ~70% of JPEG | photos, transparency — safe everywhere |
| JPEG | baseline | fallback |
| PNG | large for photos | screenshots, sharp edges |
| SVG | tiny | icons, logos, illustrations |

```html
<picture>
  <source type="image/avif" srcset="photo.avif">
  <source type="image/webp" srcset="photo.webp">
  <img src="photo.jpg" alt="..." width="800" height="450">
</picture>
```

For anything vector, SVG is the answer — it scales infinitely, compresses to a few hundred bytes, and can be styled with CSS when inlined.

## The LCP image

Identifying and prioritizing the largest above-the-fold image is the single highest-impact image change:

```jsx
<img
  src={hero}
  alt="..."
  width={1200}
  height={600}
  fetchPriority="high"
  loading="eager"
  decoding="async"
/>
```

Three rules:

**Never lazy-load it.** `loading="lazy"` on the LCP element directly delays the metric it defines.

**Make it a real `<img>` in the initial HTML.** A CSS `background-image` or a JavaScript-injected image is invisible to the preload scanner and is discovered late ([[13.1 - The Critical Rendering Path]]).

**Add `fetchPriority="high"`** so it outranks other resources competing for bandwidth.

Note the JSX casing: `fetchPriority` in React, `fetchpriority` in HTML.

## Responsive sizing

```jsx
<img
  src="photo-800.jpg"
  srcSet="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  alt="..."
  width={800}
  height={450}
/>
```

`sizes` describes how wide the image will *render*, and the browser combines that with device pixel ratio to pick from `srcSet`. A wrong `sizes` is why `srcSet` often appears not to work — telling the browser the image is full-width makes it download the largest variant for a 300px slot.

## Preventing layout shift

```css
img {
  max-width: 100%;
  height: auto;
}

.thumbnail {
  aspect-ratio: 16 / 9;
  object-fit: cover;
}
```

Explicit `width`/`height` attributes let the browser reserve space from the ratio before the image loads. This is the largest single contributor to a good CLS score ([[13.5 - Core Web Vitals]]).

## Framework image components

Next.js `<Image>`, and equivalents in other frameworks, automate most of this:

```jsx
import Image from "next/image";

<Image src={hero} alt="..." width={1200} height={600} priority />
```

It generates `srcSet`, negotiates format, enforces dimensions, lazy-loads by default, and can produce a blur placeholder. `priority` sets eager loading plus high fetch priority and emits a preload.

For a Vite-based SPA, `vite-imagetools` or `unplugin-imagemin` cover the build-time half; an image CDN covers the rest.

## Image CDNs

Hand-maintaining five variants of every image does not scale. An image CDN (Cloudinary, imgix, Cloudflare Images, or a self-hosted imgproxy) generates them on demand:

```
https://cdn.example.com/photo.jpg?w=800&format=auto&q=75
```

`format=auto` inspects `Accept` headers and serves AVIF, WebP or JPEG per browser. `q=75` is usually indistinguishable from 100 at a fraction of the size.

Combined with `Cache-Control: immutable` on the derived URLs, this removes the entire variant-management problem ([[15.7 - HTTP Caching and CDNs]]).

## Loading placeholders

```jsx
function Img({ src, blurDataURL, ...rest }) {
  const [loaded, setLoaded] = useState(false);

  return (
    <div style={{ background: `url(${blurDataURL})`, backgroundSize: "cover" }}>
      <img
        {...rest}
        src={src}
        onLoad={() => setLoaded(true)}
        style={{ opacity: loaded ? 1 : 0, transition: "opacity 200ms" }}
      />
    </div>
  );
}
```

A tiny base64 blur (typically 10–20px, under 1KB inline) shown behind the real image. It occupies the correct space and gives a sense of the content immediately.

Avoid `useState` per image in very long lists — a plain CSS background placeholder with no state is cheaper.

## Fonts

The other large asset category, and the one most often neglected ([[13.1 - The Critical Rendering Path]]):

```html
<link rel="preload" as="font" type="font/woff2" href="/fonts/inter.woff2" crossorigin>
```

```css
@font-face {
  font-family: Inter;
  src: url(/fonts/inter.woff2) format("woff2");
  font-display: swap;
  unicode-range: U+0000-00FF;   /* subset to the characters you use */
}
```

- **WOFF2 only** — every browser in use supports it, and it is 30% smaller than WOFF
- **`font-display: swap`** so text is never invisible; `optional` if CLS matters more than seeing the exact font
- **`crossorigin` on the preload**, required even same-origin, or the font downloads twice
- **Subset** — a full Devanagari or CJK font is enormous; `unicode-range` splits it so only needed ranges download
- **Two weights maximum** unless the design genuinely requires more; variable fonts cover a range in one file

## Icons

```jsx
import { Search } from "lucide-react";   // tree-shaken, one icon
import * as Icons from "some-icon-lib";  // pulls in everything
```

Named imports from a tree-shakeable library ship only what you use. A namespace import defeats it entirely ([[27.6 - Tree Shaking]]).

For a fixed icon set, an SVG sprite is smaller still:

```jsx
<svg><use href="/sprite.svg#search" /></svg>
```

One cacheable file, no JavaScript.

## How senior engineers actually use this

**They identify the LCP element first** — Lighthouse names it — and optimize that one image before anything else.

**They serve images through a CDN with `format=auto`**, which removes the format-negotiation and variant work.

**They always set dimensions or `aspect-ratio`.**

**They subset fonts and limit weights**, because font bytes are pure overhead on first paint.

**They audit icon imports**, since a namespace import of an icon library is a common quiet 200KB.

## Common pitfalls

- Lazy-loading the LCP image.
- Hero image as a CSS background, discovered late by the preload scanner.
- `srcSet` without a correct `sizes`.
- Missing dimensions, causing layout shift.
- Preloading a font without `crossorigin`, doubling the download.
- Serving a 4000px source scaled down by CSS.
- Namespace imports from icon libraries.
- Five font weights when two would do.

## Interview angle

Image optimization comes up inside "how would you improve LCP". Answer with: identify the LCP element, make it a real `<img>` in the HTML so the preload scanner finds it, set `fetchPriority="high"` and never lazy-load it, serve a correctly-sized modern format, and set dimensions to protect CLS. Adding the font side — WOFF2, `font-display`, subsetting, `crossorigin` on preload — shows you think about the full asset budget rather than just images.
