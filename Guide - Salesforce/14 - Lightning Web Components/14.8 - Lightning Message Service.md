# Lightning Message Service

## The gap it fills

Custom events travel up the DOM. Two components side by side on a record page, or one in the utility bar and one on the page, have no parent-child relationship — an event from one cannot reach the other.

**Lightning Message Service** is a publish-subscribe bus scoped to the page. Components subscribe to a channel; publishers send to it; neither knows the other exists.

It also crosses technology boundaries: **LWC, Aura, and Visualforce** can all publish and subscribe to the same channel, which is what makes it useful in mixed-technology orgs.

## The message channel

A metadata file defining the contract:

```xml
<!-- force-app/main/default/messageChannels/ClaimSelection.messageChannel-meta.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<LightningMessageChannel xmlns="http://soap.sforce.com/2006/04/metadata">
    <masterLabel>Claim Selection</masterLabel>
    <isExposed>true</isExposed>
    <description>Announces which warranty claim the user has selected.</description>

    <lightningMessageFields>
        <fieldName>claimId</fieldName>
        <description>The selected claim record Id</description>
    </lightningMessageFields>
    <lightningMessageFields>
        <fieldName>claimNumber</fieldName>
        <description>Human-readable claim number</description>
    </lightningMessageFields>
    <lightningMessageFields>
        <fieldName>source</fieldName>
        <description>Which component published this</description>
    </lightningMessageFields>
</LightningMessageChannel>
```

**`isExposed` must be true** for the channel to be usable outside its own namespace, and it is required for Aura and Visualforce subscribers.

The `lightningMessageFields` are documentation rather than enforcement — the runtime does not validate the payload shape. Declaring them anyway is what makes the channel's contract discoverable.

## Publishing

```javascript
import { LightningElement, wire } from 'lwc';
import { publish, MessageContext } from 'lightning/messageService';
import CLAIM_SELECTION_CHANNEL from '@salesforce/messageChannel/ClaimSelection__c';

export default class ClaimList extends LightningElement {

    @wire(MessageContext)
    messageContext;

    handleClaimSelected(event) {
        publish(this.messageContext, CLAIM_SELECTION_CHANNEL, {
            claimId: event.detail.claimId,
            claimNumber: event.detail.claimNumber,
            source: 'claimList'
        });
    }
}
```

**`MessageContext` is wired**, not imported as a value. Without it, `publish` and `subscribe` throw.

The channel import uses the `__c` suffix, matching the metadata file name.

## Subscribing

```javascript
import { LightningElement, wire } from 'lwc';
import { subscribe, unsubscribe, MessageContext, APPLICATION_SCOPE } from 'lightning/messageService';
import CLAIM_SELECTION_CHANNEL from '@salesforce/messageChannel/ClaimSelection__c';

export default class ClaimDetail extends LightningElement {

    subscription = null;
    claimId;

    @wire(MessageContext)
    messageContext;

    connectedCallback() {
        if (this.subscription) {
            return;
        }
        this.subscription = subscribe(
            this.messageContext,
            CLAIM_SELECTION_CHANNEL,
            (message) => this.handleMessage(message),
            { scope: APPLICATION_SCOPE }
        );
    }

    disconnectedCallback() {
        // without this, the subscription leaks every time the component unmounts
        unsubscribe(this.subscription);
        this.subscription = null;
    }

    handleMessage(message) {
        if (message.source === 'claimDetail') {
            return;   // ignore our own publications
        }
        this.claimId = message.claimId;
    }
}
```

Three things in that are not optional.

**Unsubscribe in `disconnectedCallback`.** In a console where components mount and unmount on every tab switch, leaked subscriptions accumulate and the same message gets handled several times by components that no longer exist.

**Guard against double subscription**, since `connectedCallback` can fire more than once.

**Ignore your own messages** by including a `source` field. A component that both publishes and subscribes will otherwise react to itself, which produces loops.

## Scope

```javascript
// Default: only components in the same Lightning page or app context
subscribe(this.messageContext, CHANNEL, handler);

// Application-wide: reaches the utility bar and other page regions
subscribe(this.messageContext, CHANNEL, handler, { scope: APPLICATION_SCOPE });
```

`APPLICATION_SCOPE` is what lets a utility bar component hear messages from a record page, and vice versa. In a console app this is usually what you want, and it is not the default.

Without it, a utility bar component subscribes and never receives anything, with no error — a confusing failure that is entirely down to this one option.

## Aura and Visualforce

The cross-technology capability, which is the other main reason to use LMS.

**Aura:**

```xml
<aura:component implements="flexipage:availableForRecordHome">
    <lightning:messageChannel type="ClaimSelection__c"
                              onMessage="{!c.handleMessage}"
                              scope="APPLICATION"/>
</aura:component>
```

**Visualforce:**

```html
<apex:page>
    <script>
        const channel = "{!$MessageChannel.ClaimSelection__c}";
        const subscription = sforce.one.subscribe(channel, handleMessage, {scope: "APPLICATION"});

        function handleMessage(message) {
            document.getElementById('claimNumber').textContent = message.claimNumber;
        }
    </script>
</apex:page>
```

This is genuinely useful in an org carrying a decade of Visualforce pages. A new LWC can coordinate with an old Visualforce page without either being rewritten. See [[01.9 - Classic vs Lightning Experience]].

## When to use LMS

**Sibling components on a page.** A list and a detail panel, side by side in App Builder, with no shared parent.

**Utility bar to page.** A console utility component telling a record page component that something changed.

**Across a technology boundary.** LWC to Aura, or LWC to Visualforce.

**Across an Aura wrapper.** An LWC inside an Aura component that needs to reach another LWC elsewhere on the page.

**Loosely coupled coordination**, where the publisher genuinely should not know its consumers.

## When not to use it

**Parent and child.** Properties down, events up. LMS between a parent and its own child is indirection with no benefit, and it makes the data flow invisible.

**Anything within one component tree.** Custom events are traceable — you can read the markup and see the handler. An LMS message is caught by whoever happens to be subscribed, which is harder to reason about.

**Passing large payloads.** The message is a plain object and should stay small. Send an Id; let the subscriber fetch what it needs.

**Anything requiring a response.** LMS is fire-and-forget. There is no acknowledgement and no return value.

The general rule: **use the most local mechanism that works.** Events within a tree, LMS across trees.

## A worked example

A console layout: a claim list in the main region, a detail panel beside it, and a notes component in the utility bar.

```javascript
// claimList.js — publisher
handleRowSelected(event) {
    publish(this.messageContext, CLAIM_SELECTION_CHANNEL, {
        claimId: event.detail.claimId,
        claimNumber: event.detail.claimNumber,
        source: 'claimList'
    });
}
```

```javascript
// claimDetail.js — subscriber on the page
handleMessage(message) {
    if (message.source === 'claimDetail') {
        return;
    }
    this.claimId = message.claimId;   // a reactive wire parameter, so the record reloads
}
```

```javascript
// claimNotes.js — subscriber in the utility bar
connectedCallback() {
    this.subscription = subscribe(
        this.messageContext,
        CLAIM_SELECTION_CHANNEL,
        (message) => this.loadNotesFor(message.claimId),
        // APPLICATION_SCOPE is required for a utility bar component to hear page messages
        { scope: APPLICATION_SCOPE }
    );
}
```

Three components, no shared parent, no direct references. Adding a fourth subscriber requires no change to the publisher.

## Debugging

LMS failures are usually silence rather than errors.

**Check `MessageContext` is wired.** Missing it is the most common cause of a publish that does nothing.

**Check the scope.** A utility bar subscriber without `APPLICATION_SCOPE` receives nothing.

**Check the channel import name** matches the metadata file, including the `__c`.

**Check `isExposed`** on the channel.

**Log in the subscriber** before assuming the publisher is at fault — it is more often the subscription than the publication.

```javascript
handleMessage(message) {
    console.log('claimDetail received', JSON.stringify(message));
}
```

## Testing

```javascript
import { publish, MessageContext } from 'lightning/messageService';
import CLAIM_CHANNEL from '@salesforce/messageChannel/ClaimSelection__c';

jest.mock('lightning/messageService', () => ({
    publish: jest.fn(),
    subscribe: jest.fn(),
    unsubscribe: jest.fn(),
    MessageContext: jest.fn(),
    APPLICATION_SCOPE: 'APPLICATION'
}), { virtual: true });

it('publishes the selected claim', () => {
    const element = createElement('c-claim-list', { is: ClaimList });
    document.body.appendChild(element);

    element.shadowRoot.querySelector('c-claim-row')
        .dispatchEvent(new CustomEvent('claimselected', {
            detail: { claimId: 'a0X123', claimNumber: 'WC-00042' }
        }));

    return Promise.resolve().then(() => {
        expect(publish).toHaveBeenCalledWith(
            undefined,
            CLAIM_CHANNEL,
            expect.objectContaining({ claimId: 'a0X123' })
        );
    });
});
```

Mocking the module and asserting on `publish` is the standard approach. Testing the subscriber side means capturing the handler passed to the mocked `subscribe` and invoking it directly. See [[14.18 - Jest Testing for LWC]].

## Practical guidance

**Wire `MessageContext`.** Nothing works without it.

**Unsubscribe in `disconnectedCallback`.**

**Use `APPLICATION_SCOPE`** for utility bar and cross-region communication.

**Include a `source` field** so components can ignore their own messages.

**Send Ids, not payloads.** Let subscribers fetch what they need.

**Declare the fields in the channel metadata**, even though they are not enforced.

**Use events within a component tree** and LMS only across trees.

**Log in the subscriber first** when debugging silence.
