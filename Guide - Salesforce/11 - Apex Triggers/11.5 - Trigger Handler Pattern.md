# Trigger Handler Pattern

## The three layers

```
Trigger      →  declares events, calls the handler, nothing else
Handler      →  reads Trigger context, dispatches by event
Service      →  business logic, takes collections, never references Trigger
```

Each layer has one job, and the separation is what makes the code testable and reusable.

## The trigger

```java
trigger WarrantyClaimTrigger on Warranty_Claim__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    WarrantyClaimTriggerHandler.run();
}
```

## The handler

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (AutomationBypass.isBypassed('WarrantyClaim')) {
            return;
        }

        switch on Trigger.operationType {
            when BEFORE_INSERT {
                ClaimService.applyDerivedFields(Trigger.new, null);
                ClaimValidationService.validate(Trigger.new, null);
            }
            when BEFORE_UPDATE {
                ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
                ClaimRoutingService.assignApprover(Trigger.new, Trigger.oldMap);
                ClaimValidationService.validate(Trigger.new, Trigger.oldMap);
            }
            when BEFORE_DELETE {
                ClaimValidationService.preventDeletionOfSettled(Trigger.old);
            }
            when AFTER_INSERT {
                ClaimService.createInitialParts(Trigger.new);
                ClaimRollupService.recalculate(ClaimService.assetIds(Trigger.new));
            }
            when AFTER_UPDATE {
                ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
                ClaimRollupService.recalculate(
                    ClaimService.affectedAssetIds(Trigger.new, Trigger.oldMap)
                );
            }
            when AFTER_DELETE {
                ClaimRollupService.recalculate(ClaimService.assetIds(Trigger.old));
            }
            when AFTER_UNDELETE {
                ClaimRollupService.recalculate(ClaimService.assetIds(Trigger.new));
            }
        }
    }
}
```

The handler is the **only place `Trigger` is referenced**. That constraint is what the whole pattern is for.

## The service

```java
public with sharing class ClaimService {

    public static void handleStatusChanges(
        List<Warranty_Claim__c> newClaims,
        Map<Id, Warranty_Claim__c> oldClaims
    ) {
        List<Warranty_Claim__c> newlyApproved = new List<Warranty_Claim__c>();

        for (Warranty_Claim__c claim : newClaims) {
            Warranty_Claim__c prior = oldClaims == null ? null : oldClaims.get(claim.Id);
            if (claim.Status__c == 'Approved'
                && (prior == null || prior.Status__c != 'Approved')) {
                newlyApproved.add(claim);
            }
        }

        if (newlyApproved.isEmpty()) {
            return;
        }

        ClaimPaymentService.createPayments(newlyApproved);
    }
}
```

Because it takes plain collections, this method can be called from:

- The trigger handler
- A batch job reprocessing historical claims
- An invocable action from a flow
- A REST endpoint
- A test, with records constructed in memory and no DML at all

A service reading `Trigger.new` directly can only ever run inside a trigger. That single restriction is what makes the separation worth the extra file.

## The bypass mechanism

Every org needs a way to disable trigger automation, for data migrations, bulk corrections, and incidents.

```java
public with sharing class AutomationBypass {

    private static Set<String> bypassed = new Set<String>();

    public static Boolean isBypassed(String handlerName) {
        if (bypassed.contains(handlerName)) {
            return true;
        }
        // the custom setting path allows a runtime bypass without a deployment
        Automation_Settings__c settings = Automation_Settings__c.getInstance();
        return settings != null
            && (settings.Disable_All_Triggers__c == true
                || isNamedInSetting(settings, handlerName));
    }

    public static void bypass(String handlerName) {
        bypassed.add(handlerName);
    }

    public static void clearBypass(String handlerName) {
        bypassed.remove(handlerName);
    }

    @TestVisible
    private static void reset() {
        bypassed.clear();
    }
}
```

Two paths, for two different situations:

**The static path** is for code — a migration script disabling a handler for its own run.

```java
AutomationBypass.bypass('WarrantyClaim');
update historicalClaims;
AutomationBypass.clearBypass('WarrantyClaim');
```

**The hierarchy custom setting path** is for runtime — an administrator disabling automation during an incident, per user or per profile, without a deployment. The setting form is what makes this genuinely useful, since deactivating a trigger requires a deployment and the custom setting does not. See [[17.2 - Custom Settings]].

Testing the bypass explicitly is not optional. An untested bypass that does not work is worse than none, because you will discover it during the incident.

## Recursion control

The handler is the right place for it, because it is the single entry point.

```java
public with sharing class WarrantyClaimTriggerHandler {

    public static void run() {
        if (AutomationBypass.isBypassed('WarrantyClaim')) {
            return;
        }

        if (Trigger.isAfter && Trigger.isUpdate) {
            // tracking ids rather than a boolean keeps later records in the same
            // transaction from being skipped
            List<Warranty_Claim__c> unprocessed = TriggerControl.filterUnprocessed(
                'WarrantyClaim_AfterUpdate', Trigger.new
            );
            if (unprocessed.isEmpty()) {
                return;
            }
            TriggerControl.markProcessed('WarrantyClaim_AfterUpdate', unprocessed);
            ClaimService.handleStatusChanges(unprocessed, Trigger.oldMap);
        }
    }
}
```

Covered fully in [[11.6 - Recursion Control and Static Guards]].

## Static or instance handler

Two styles in circulation.

**Static**, as above. Simplest, no instantiation, and the one this course uses.

**Instance**, usually with a virtual base class:

```java
public abstract class TriggerHandler {

    public void run() {
        if (!isEnabled()) {
            return;
        }
        switch on Trigger.operationType {
            when BEFORE_INSERT { beforeInsert(); }
            when BEFORE_UPDATE { beforeUpdate(); }
            when AFTER_INSERT  { afterInsert(); }
            when AFTER_UPDATE  { afterUpdate(); }
            when BEFORE_DELETE { beforeDelete(); }
            when AFTER_DELETE  { afterDelete(); }
            when AFTER_UNDELETE { afterUndelete(); }
        }
    }

    protected virtual void beforeInsert() { }
    protected virtual void beforeUpdate() { }
    protected virtual void afterInsert() { }
    protected virtual void afterUpdate() { }
    protected virtual void beforeDelete() { }
    protected virtual void afterDelete() { }
    protected virtual void afterUndelete() { }

    protected virtual Boolean isEnabled() {
        return !AutomationBypass.isBypassed(getHandlerName());
    }

    protected abstract String getHandlerName();
}
```

```java
public with sharing class WarrantyClaimTriggerHandler extends TriggerHandler {

    protected override String getHandlerName() {
        return 'WarrantyClaim';
    }

    protected override void beforeUpdate() {
        ClaimService.applyDerivedFields(Trigger.new, Trigger.oldMap);
    }

    protected override void afterUpdate() {
        ClaimService.handleStatusChanges(Trigger.new, Trigger.oldMap);
    }
}
```

The trigger becomes `new WarrantyClaimTriggerHandler().run();`.

**What the base class buys:** bypass and recursion control implemented once, a consistent shape across every object, and a subclass that only overrides the events it uses.

**What it costs:** an inheritance hierarchy, and the base class becomes a shared dependency where a change affects every object in the org.

Both work. The base class earns its place in an org with fifteen or more triggered objects; below that, the static form is less machinery for the same result. What matters most is that every handler in the org uses the same one.

## Where each concern belongs

A recurring question, and a workable answer:

| Concern | Layer |
| --- | --- |
| Which events exist | Trigger |
| Which service runs for which event | Handler |
| Bypass check | Handler, or base class |
| Recursion guard | Handler, or base class |
| Change detection against `oldMap` | Service |
| Querying related records | Selector, called by the service |
| Business rules | Service |
| Validation with `addError` | Service |
| Aggregate recalculation | A dedicated service |

**Change detection belongs in the service, not the handler.** The handler passes both collections; the service decides what changed. This keeps the handler a readable list of what runs when, and it means the service's logic is self-contained and testable.

## Testing the layers

**Service tests** are the bulk of the suite, and they can run without DML by constructing records in memory:

```java
@IsTest
static void onlyNewlyApprovedClaimsProducePayments() {
    Id claimId = TestIdFactory.generate(Warranty_Claim__c.SObjectType);

    List<Warranty_Claim__c> newClaims = new List<Warranty_Claim__c>{
        new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };
    Map<Id, Warranty_Claim__c> oldClaims = new Map<Id, Warranty_Claim__c>{
        claimId => new Warranty_Claim__c(Id = claimId, Status__c = 'Approved')
    };

    Test.startTest();
    List<Warranty_Claim__c> result = ClaimService.findNewlyApproved(newClaims, oldClaims);
    Test.stopTest();

    Assert.isTrue(result.isEmpty(), 'A claim already approved should not be treated as newly approved');
}
```

No records inserted, no queries consumed, milliseconds to run. On a suite of a thousand tests this is the difference between three minutes and forty.

**Handler tests** perform real DML and verify the wiring — that the right service runs for the right event, that the bypass works, that bulk behaviour holds. Fewer of these, and they are the slow ones.

That split — many fast service tests, few slow integration tests — is the shape a healthy Apex test suite has. See [[19.1 - Apex Testing Fundamentals]].

## Practical guidance

**Trigger routes, handler dispatches, service does the work.**

**Nothing outside the handler references `Trigger`.**

**Services take collections and tolerate a null `oldMap`.**

**Build a bypass mechanism with both a static and a custom setting path**, and test it.

**Put recursion control in the handler**, tracking record Ids.

**Put change detection in the service.**

**Pick one handler style for the org** and use it everywhere.
