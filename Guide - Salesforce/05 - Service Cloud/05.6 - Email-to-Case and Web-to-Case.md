# Email-to-Case and Web-to-Case

## Email-to-Case

Customers email `support@company.com`, and a case appears. Replies to that case go back as email, threaded into the same conversation.

This is the highest-volume channel in most support operations, and its plumbing has more sharp edges than any other part of Service Cloud.

## The two variants

**On-Demand Email-to-Case.** Salesforce provides a routing address; you forward your support mailbox to it. No infrastructure to run.

Limitations: attachment size caps, a daily volume limit tied to user licenses, and email arriving from outside your control means less filtering.

**Email-to-Case (with the agent).** A small Java agent runs inside your network, reading the mailbox and pushing to Salesforce over the API.

Advantages: larger attachments, higher volume, and email never leaves your infrastructure before processing — which is sometimes a compliance requirement.

Cost: you run and monitor a service. Most implementations use On-Demand unless a specific constraint forces the agent.

## What happens on arrival

1. The email is received at the routing address
2. Salesforce checks the subject and headers for an existing case reference
3. If found, an `EmailMessage` is attached to that case; if not, a new Case is created
4. `SuppliedEmail`, `SuppliedName`, `Subject`, and `Description` are populated
5. Contact matching runs — the sender's email is matched to a Contact, and the Contact's Account is set
6. Attachments become files on the case
7. Assignment rules, auto-response rules, and entitlement assignment run, if configured

Step 2 is the threading mechanism, and step 5 is where most data quality issues originate.

## Threading

Salesforce identifies the case a reply belongs to using a **thread token**, historically a string like `ref:_00D5g0000...:ref` embedded in the email body or subject.

More recent orgs use header-based threading, which relies on standard email headers rather than a visible token. It is cleaner and more reliable, and it is the setting to prefer in a new implementation.

Threading fails predictably in a few situations, and each produces a duplicate case:

- The customer removes the token when replying
- An intermediate mail system strips or rewrites headers
- The customer starts a fresh email rather than replying
- The case has been closed beyond the reopen window

Duplicate cases from broken threading are a normal operational reality, and worth building a merge or link process for rather than treating as a defect to eliminate.

## Contact matching, and its failure mode

The sender's email address is matched to a Contact. If matched, `ContactId` and `AccountId` are set. If not, the case has `SuppliedEmail` populated and no contact.

Cases with no contact are a real problem: entitlement assignment fails, account-based routing fails, and the case is invisible in any account-based view.

Handling it properly usually means custom logic:

```java
public with sharing class InboundEmailContactService {

    public static void matchOrCreateContacts(List<Case> cases) {
        Set<String> emails = new Set<String>();
        for (Case c : cases) {
            if (c.ContactId == null && String.isNotBlank(c.SuppliedEmail)) {
                emails.add(c.SuppliedEmail.toLowerCase());
            }
        }
        if (emails.isEmpty()) {
            return;
        }

        Map<String, Contact> contactByEmail = new Map<String, Contact>();
        for (Contact con : [
            SELECT Id, Email, AccountId FROM Contact WHERE Email IN :emails
        ]) {
            contactByEmail.put(con.Email.toLowerCase(), con);
        }

        // fall back to domain matching so an unknown sender still lands on the right account
        Set<String> domains = new Set<String>();
        for (String email : emails) {
            if (!contactByEmail.containsKey(email) && email.contains('@')) {
                domains.add(email.substringAfter('@'));
            }
        }

        Map<String, Id> accountByDomain = new Map<String, Id>();
        if (!domains.isEmpty()) {
            for (Account acc : [
                SELECT Id, Email_Domain__c FROM Account WHERE Email_Domain__c IN :domains
            ]) {
                accountByDomain.put(acc.Email_Domain__c.toLowerCase(), acc.Id);
            }
        }

        for (Case c : cases) {
            if (c.ContactId != null || String.isBlank(c.SuppliedEmail)) {
                continue;
            }
            String email = c.SuppliedEmail.toLowerCase();
            Contact match = contactByEmail.get(email);
            if (match != null) {
                c.ContactId = match.Id;
                c.AccountId = match.AccountId;
            } else if (email.contains('@')) {
                c.AccountId = accountByDomain.get(email.substringAfter('@'));
            }
        }
    }
}
```

Domain fallback is what catches a colleague of a known contact emailing for the first time. Whether to auto-create the Contact is a business decision — it improves data completeness and it also fills the database with people who emailed once.

## Custom inbound email handling

When the standard behaviour is insufficient — parsing structured content, routing on body text, handling machine-generated alerts — an **Inbound Email Service** gives full control.

```java
global with sharing class MachineAlertEmailHandler implements Messaging.InboundEmailHandler {

    global Messaging.InboundEmailResult handleInboundEmail(
        Messaging.InboundEmail email,
        Messaging.InboundEnvelope envelope
    ) {
        Messaging.InboundEmailResult result = new Messaging.InboundEmailResult();

        try {
            String serial = extractSerialNumber(email.subject, email.plainTextBody);

            List<Machine__c> machines = [
                SELECT Id, Account__c FROM Machine__c
                WHERE Serial_Number__c = :serial LIMIT 1
            ];

            Case c = new Case(
                Subject = email.subject,
                Description = email.plainTextBody,
                Origin = 'Machine Alert',
                Type = 'Technical Support',
                Priority = extractSeverity(email.plainTextBody),
                SuppliedEmail = envelope.fromAddress
            );

            if (!machines.isEmpty()) {
                c.Machine__c = machines[0].Id;
                c.AccountId = machines[0].Account__c;
            }

            Database.DMLOptions options = new Database.DMLOptions();
            options.assignmentRuleHeader.useDefaultRule = true;
            options.emailHeader.triggerAutoResponseEmail = true;
            c.setOptions(options);

            insert c;
            attachFiles(c.Id, email);

            result.success = true;
        } catch (Exception e) {
            // returning success = false tells the sender's mail system the message was rejected
            result.success = false;
            result.message = 'Unable to process: ' + e.getMessage();
        }

        return result;
    }
}
```

Two things worth knowing. `result.success = false` causes a bounce back to the sender, which is right for a malformed message and wrong for an internal error you would rather log and retry. And an inbound email handler runs **without sharing by default** and as a special automated user, so security enforcement is entirely the developer's responsibility.

Attachments arrive as `email.binaryAttachments` and `email.textAttachments`, and are saved as `ContentVersion` records linked to the case. See [[17.5 - Files, ContentDocument and ContentVersion]].

## Outbound email from cases

Replies are sent from the case feed, from a flow, or from Apex.

The sender address should be an **Organization-Wide Email Address** — a verified address like `support@company.com` — so replies thread correctly and do not come from the individual agent. Sending from an agent's personal address breaks threading and creates a problem when that agent leaves.

```java
Messaging.SingleEmailMessage message = new Messaging.SingleEmailMessage();
message.setTargetObjectId(contactId);
message.setWhatId(caseId);
message.setTemplateId(templateId);
message.setOrgWideEmailAddressId(supportAddressId);
message.setSaveAsActivity(true);

Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{ message });
```

`setWhatId(caseId)` is what merges case fields into the template and threads the reply. Omitting it produces an email with empty merge fields, which is a familiar embarrassment.

Email deliverability is a genuine operational concern: SPF, DKIM, and DMARC alignment determine whether your support replies reach the customer or their spam folder. This is usually an infrastructure conversation rather than a Salesforce one, and it is worth having before go-live rather than after complaints. See [[17.6 - Email Services - Inbound and Outbound]].

## Web-to-Case

A generated HTML form posting to Salesforce, creating a case. Same concept as Web-to-Lead, and the same limitations:

- No authentication, so it is spammable
- A daily submission limit
- No validation beyond field types
- Dated generated markup

For an anonymous "contact us" form it is adequate with a captcha in front. For anything serious — a logged-in customer portal, structured intake, file upload — the better options are an Experience Cloud site with a proper form, or a custom Apex REST endpoint that the company's own site posts to.

```java
@RestResource(urlMapping='/support/case/*')
global with sharing class InboundCaseService {

    @HttpPost
    global static CaseResponse create(String email, String subject, String description,
                                      String productSerial) {
        if (String.isBlank(email) || String.isBlank(subject)) {
            return CaseResponse.failure('Email and subject are required.');
        }

        Case c = new Case(
            SuppliedEmail = email,
            Subject = subject,
            Description = description,
            Origin = 'Web'
        );

        Database.DMLOptions options = new Database.DMLOptions();
        options.assignmentRuleHeader.useDefaultRule = true;
        options.emailHeader.triggerAutoResponseEmail = true;
        c.setOptions(options);

        insert as user c;
        return CaseResponse.success(c.Id, [SELECT CaseNumber FROM Case WHERE Id = :c.Id].CaseNumber);
    }
}
```

Returning the case number matters — the customer needs a reference, and giving it immediately reduces follow-up contacts.

## Practical guidance

**Prefer header-based threading** in new implementations.

**Build domain fallback for contact matching.** Unmatched cases break entitlements and routing.

**Set the DML flags** for assignment, auto-response, and owner notification on every code path that creates cases.

**Use an organization-wide email address** for outbound support email.

**Sort out email authentication before go-live.** Deliverability failures look like the support team ignoring customers.

**Expect duplicate cases from broken threading** and build a linking or merging process rather than trying to eliminate them.

**Do not use Web-to-Case for authenticated customers.** An Experience Cloud site gives them their case history, which prevents a large share of "what is happening with my issue" contacts.
