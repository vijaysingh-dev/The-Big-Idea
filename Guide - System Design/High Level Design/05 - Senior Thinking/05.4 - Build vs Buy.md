# Build vs Buy

> **Revision tags:** #senior-thinking #architecture #decision-making  
> **Related:** [[05.1 - Tradeoff Evaluation]] | [[02.6 - Observability Security Cost]]

---

## The Decision

For any infrastructure component or capability, you have three choices:

1. **Buy (SaaS/managed service):** Pay a vendor to run it for you
2. **Build on open-source:** Run it yourself on your own infrastructure
3. **Build from scratch:** Write it yourself

In practice, "build" almost always means "build on open-source." Very few teams should write their own database, message queue, or search engine. The real choice is: managed service vs self-hosted open-source.

---

## The Buy vs Build Framework

### Questions That Push Toward Buy

**"Is this a core differentiator?"**  
If yes → build (own the competitive advantage).  
If no → buy (redirect engineering to things that matter).

Your payment processing infrastructure is not a core differentiator. Stripe is. Your recommendation algorithm might be. Build that.

**"How long would it take to build a production-grade version?"**  
A Redis cache is "simple." A production Redis cluster with monitoring, backups, failover, and security hardening is 2–4 weeks of work. Buy managed Redis (ElastiCache) and spend those weeks on product.

**"What's the operational burden?"**  
Running Kafka requires: capacity planning, version upgrades, security patches, disk monitoring, consumer lag alerting, replication configuration, and on-call expertise. Amazon MSK does this for you.

**"What happens if it breaks at 3 AM?"**  
With a managed service, the vendor's on-call team wakes up. With self-hosted, your on-call team does.

**"Do you have the expertise?"**  
Operating Cassandra correctly requires deep knowledge of compaction strategies, consistency levels, and tombstone management. Don't self-host it unless you have that expertise.

---

### Questions That Push Toward Build

**"Is the managed service cost prohibitive at your scale?"**  
At 10M events/day, AWS Kinesis is fine. At 100B events/day, the cost is enormous — building on open-source Kafka becomes economical.

**"Do you need customization the managed service doesn't support?"**  
If your use case requires features the vendor doesn't offer, you'll fight the tool constantly. Self-host and customize.

**"Is this core to your product's performance or reliability?"**  
Airbnb runs their own Kafka. Netflix runs their own CDN. At their scale, the competitive and cost advantages justify it.

**"Are there compliance or data residency requirements?"**  
Some regulated industries require data to never leave your own infrastructure. Managed cloud services may not qualify.

## The Decision Matrix

| Component | Default Choice | Reason |
|---|---|---|
| Relational DB | Managed (RDS, Cloud SQL) | Backups, failover, patching handled |
| Cache (Redis) | Managed (ElastiCache, Upstash) | Replication, failover automated |
| Message queue | Managed (SQS, Pub/Sub) for simple; MSK/Confluent for Kafka features | Depends on replay needs |
| Search | Managed (Elastic Cloud, OpenSearch) | Cluster management is non-trivial |
| Object storage | Always managed (S3, GCS) | No reason to self-host |
| CDN | Always managed (CloudFront, Cloudflare) | No reason to self-host |
| Monitoring/APM | Managed (Datadog, New Relic) until cost is prohibitive | Setup cost too high for self-hosted at early stage |
| Auth/Identity | Managed (Auth0, Cognito) unless auth is core product | Getting auth wrong is a security disaster |
| Email delivery | Always managed (SES, SendGrid) | Deliverability requires vendor relationships |
| Feature flags | Managed (LaunchDarkly) or simple homegrown | Depends on targeting complexity needed |

## Total Cost of Ownership (TCO)

The sticker price of a managed service is not the full comparison. Calculate TCO:

```
Managed service cost:
  Monthly fee: $500/month
  Engineering setup time: 2 days
  Ongoing ops burden: ~0 hours/month
  On-call incidents: vendor's problem
  12-month TCO: $6,000 + 2 days engineer time

Self-hosted open source:
  Infrastructure cost: $200/month
  Engineering setup: 2 weeks
  Ongoing ops: 4 hours/month × 12 = ~6 engineer-days/year
  On-call incidents: your team's problem
  12-month TCO: $2,400 + 2 weeks + 6 days engineer time

At $150/engineer-hour:
  Engineer cost: (10 days + 6 days) × 8 hours × $150 = $19,200
  Self-hosted total: $2,400 + $19,200 = $21,600
  Managed total: $6,000 + ~$2,400 (2 days setup) = $8,400
```

The managed service is cheaper even at $300/month premium. The math usually favors managed services until very high scale.

## The "We'll Build It Later" Trap

Teams often start with a managed service, plan to migrate to self-hosted "when we're bigger," and never do — because migration is painful and the managed service becomes load-bearing infrastructure.

This is fine for most components. Accept the long-term managed service cost and move on.

The trap is the reverse: building from scratch "because we'll need it at scale" before reaching that scale. Most startups never reach the scale where this is justified. Start managed; migrate if and when the economics demand it.

## When Build Wins: The Right Reasons

**Stripe built its own distributed database (Vitess):** Their transaction volumes and consistency requirements made managed MySQL insufficient. The economics and competitive advantage justified the investment.

**Cloudflare built its own edge runtime:** Their latency requirements (sub-millisecond at the edge) and custom protocol handling couldn't be done with a managed product.

**Uber built its own geospatial data store:** The specific access patterns for real-time driver location updates at their scale weren't served by any existing managed solution.

The pattern: extreme scale + specific technical requirements + substantial engineering resources = build.

## Practical Interview Answer

When asked "what database / queue / search engine would you use?":

1. Name the technology
2. State whether managed or self-hosted
3. Give the reason: "We'd use Amazon MSK (managed Kafka) because at our expected scale, Kafka's replay capability is necessary, and MSK removes the operational burden of cluster management. If we reach a scale where MSK costs become prohibitive, we'd evaluate self-hosted Kafka on spot instances."

This shows you think about operational concerns, not just technology selection.
