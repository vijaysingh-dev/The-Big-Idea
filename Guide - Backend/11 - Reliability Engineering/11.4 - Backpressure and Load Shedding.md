# Backpressure and Load Shedding

#backend #reliability #capacity

> **In one line:** When demand exceeds capacity you can queue, slow down, or reject — and queueing is the only one that fails catastrophically, which is why it is the default.

---

## The Idea

```
Arrival rate:  1,200 rps
Capacity:      1,000 rps
```

Three responses:

| Response | Result |
|---|---|
| **Queue** | Latency grows without bound. Eventually everything times out |
| **Backpressure** | The producer slows down. Requires the producer to cooperate |
| **Shed** | Reject 200 rps immediately. **Serve 1,000 well** |

⚠️ **Queueing looks like the kind option and it is the cruel one.** Every request waits longer, every request eventually times out, and nobody is served — while you burn capacity on work that will be discarded.

💡 **The goal under overload is to serve as many requests as you can, well** — not to serve all of them badly. Rejecting 20% quickly is strictly better than failing 100% slowly.

---

## Why Queueing Fails

Little's Law: `L = λ × W`, where `L` is queue length, `λ` arrival rate, and `W` wait time.

```
λ = 1,200 rps, capacity 1,000 rps
→ 200 requests/second accumulate, forever
→ after 60 seconds: 12,000 queued
→ wait time: 12 seconds
→ every client has timed out
→ you are computing responses nobody will read
```

⚠️ **The system is now doing 100% useless work.** Every response completed is for a client that gave up.

💡 **This is the metastable state** ([[11.1 - How Systems Fail]]) — it does not recover when the load spike ends, because the queue is still full and the retries are still coming.

### The queue that hides the problem

```
No queue:     latency 50ms, error rate 20%     ← visible, actionable
With queue:   latency 8s, error rate 0%        ← looks fine on a dashboard
```

⚠️ **A dashboard showing zero errors and rising latency is the signature of an unbounded queue**, and it is the more dangerous of the two states because it does not trigger alerts.

**Bound every queue.** An unbounded queue converts a fast, visible failure into a slow, invisible one.

## Load Shedding

```python
if in_flight >= MAX_CONCURRENT:
    shed_total.inc()
    return Response(503, headers={"Retry-After": "1"})
```

💡 **Shed at the edge, before any work is done** ([[10.6 - API Gateway and BFF]]). A request rejected after a database query has already consumed the resource you were protecting.

### What to shed

⚠️ **Shedding randomly is much worse than shedding selectively.**

```python
PRIORITY = {
    "health":       0,     # never shed
    "auth":         1,
    "write":        2,
    "read":         3,
    "search":       4,
    "analytics":    5,     # shed first
}

if load_level() >= priority_for(request):
    return Response(503)
```

| Shed first | Never shed |
|---|---|
| Analytics and reporting | **Health checks** |
| Background refreshes | Authentication |
| Anonymous traffic | Requests already in flight |
| Retries | Payments |
| Prefetches and speculative requests | |

💡 **Shedding retries first is counterintuitive and correct.** A retry means the client already has one attempt outstanding or has already waited; a first attempt has not been served at all.

```python
if request.headers.get("x-retry-attempt") and load_high():
    return Response(503)
```

⚠️ **This requires clients to mark retries**, which is a small protocol addition with a large benefit under overload.

### Deciding when to shed

| Signal | |
|---|---|
| **Concurrent in-flight requests** | The best single signal. Directly reflects capacity |
| **Queue wait time** | Shed when a request has already waited too long |
| CPU utilisation | Lagging, and noisy |
| Latency | Lagging — by the time it rises, you are overloaded |
| **Downstream pool pressure** | Shed before exhausting the database |

```python
if pool.wait_time_p99 > 100:                     # ms
    shed(priority_threshold=3)
```

💡 **In-flight count is better than CPU or latency because it is immediate.** CPU rises after you are overloaded; in-flight count rises as it happens.

### Shed based on the deadline

```python
queued_for = time.monotonic() - request.received_at
if queued_for > request.deadline * 0.8:
    shed_expired.inc()
    return Response(503)                          # ← it will time out anyway
```

💡 **A request that has already consumed 80% of its budget waiting will fail even if you serve it.** Dropping it frees capacity for a request that can still succeed ([[11.2 - Timeouts Retries and Jitter]]).

**This is the single most effective shedding rule**, because it discards exactly the work that is guaranteed to be wasted.

## Backpressure

Making the producer slow down, rather than rejecting.

```
TCP:        the receive window shrinks, the sender slows ([[02.4 - Flow Control and Congestion Control]])
HTTP/2:     per-stream flow control windows
Queues:     a bounded queue blocks the producer
Async:      an unbounded queue is a memory leak ([[01.11 - Backpressure Inside One Process]])
```

```python
queue = asyncio.Queue(maxsize=1000)
await queue.put(item)          # ← blocks when full. This is backpressure
```

💡 **Backpressure propagates naturally through a chain of bounded queues**: the consumer slows, its queue fills, its producer blocks, and so on back to the source.

⚠️ **One unbounded queue anywhere in the chain breaks it.** The backpressure stops there and memory grows instead.

### Backpressure versus shedding

| | Backpressure | Shedding |
|---|---|---|
| Producer | **Must cooperate** | Does not need to |
| Works with | Internal pipelines, streaming | Public APIs |
| Result | The producer slows | The request is rejected |
| Latency | Grows, bounded | **Stays flat** |

💡 **Backpressure works when you control the producer.** For a public API you cannot slow clients down — they will retry — so shedding is the only option.

⚠️ **Applying backpressure to an untrusted client just moves the queue into their retry logic**, which is worse because you cannot see it.

## Rate Limiting Is Not Load Shedding

They are often confused and they solve different problems.

| | Rate limiting | Load shedding |
|---|---|---|
| Purpose | **Fairness and quotas** | **Survival** |
| Based on | Per-client configured limits | **Current system load** |
| Active | Always | **Only under overload** |
| Rejects | The client over their quota | Whatever is least valuable now |

💡 **You need both.** Rate limiting stops one client consuming everything; load shedding stops the aggregate of well-behaved clients from taking you down ([[11.5 - Rate Limiting and Quotas]]).

⚠️ **Rate limits set generously enough to be fair are usually too generous to protect you**, which is why load shedding is a separate mechanism.

## In Production

### The shedding implementation

```python
class LoadShedder:
    def __init__(self, max_concurrent: int):
        self.max = max_concurrent
        self.in_flight = 0

    def level(self) -> int:
        ratio = self.in_flight / self.max
        if ratio < 0.7:  return 0        # normal
        if ratio < 0.85: return 3        # shed analytics
        if ratio < 0.95: return 2        # shed reads
        return 1                          # shed everything but auth and health


@app.middleware("http")
async def shed(request: Request, call_next):
    priority = PRIORITY.get(route_class(request), 3)
    if priority >= shedder.level() and shedder.level() > 0:
        shed_total.labels(route=request.url.path, level=shedder.level()).inc()
        return JSONResponse({"error": "overloaded"}, 503,
                            headers={"Retry-After": "1"})

    if elapsed_since_receipt(request) > deadline(request) * 0.8:
        shed_expired_total.inc()
        return JSONResponse({"error": "deadline exceeded"}, 503)

    shedder.in_flight += 1
    try:
        return await call_next(request)
    finally:
        shedder.in_flight -= 1
```

💡 **Graduated levels are better than a single threshold**, because they degrade progressively rather than falling off a cliff.

### Finding `max_concurrent`

⚠️ **Do not guess it.** Load test until throughput plateaus and latency rises — that inflection point is your capacity.

```
concurrency  throughput  p99
    10          950      12ms
    25          1010     26ms
    50          1020     52ms      ← throughput plateau
   100          1015     104ms     ← latency doubling, no throughput gain
   200           980     280ms     ← throughput DECLINING
```

💡 **Set `max_concurrent` at the plateau, not beyond it.** Past that point, more concurrency produces worse latency and eventually less throughput — because of context switching, lock contention and cache pressure ([[06.9 - Connection Pooling and PgBouncer]]).

⚠️ **The declining-throughput region is real and it is where unbounded systems end up.**

### Adaptive limits

```python
# Gradient: compare current latency to the observed minimum
gradient = min_latency / max(current_latency, min_latency)
new_limit = current_limit * gradient + queue_size_allowance
limit = clamp(new_limit, MIN_LIMIT, MAX_LIMIT)
```

💡 **An adaptive limit removes the need to tune a fixed value** and adapts as your capacity changes — after a deploy, on a different instance size, or when a dependency slows ([[11.3 - Circuit Breakers and Bulkheads]]).

**Netflix's `concurrency-limits` implements several algorithms**, all derived from TCP congestion control.

### Shedding must be cheap

⚠️ **A 503 that costs as much as a real response provides no protection.**

```python
# ❌ Expensive rejection
user = await auth.verify(token)              # a network call
if overloaded(): return Response(503)

# ✅ Cheap rejection
if overloaded(): return Response(503)        # first thing, no I/O
user = await auth.verify(token)
```

💡 **Shed before authentication, before parsing the body, before any I/O.** The rejection path should be microseconds.

### Telling clients what to do

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 2
```

⚠️ **Without `Retry-After`, clients retry immediately and make it worse.** With it, well-behaved clients back off ([[11.2 - Timeouts Retries and Jitter]]).

💡 **Vary `Retry-After` with the load level and add jitter**, so shed clients do not all return at the same instant.

```python
retry_after = str(random.randint(1, 2 ** load_level))
```

### Monitoring

```python
in_flight_requests.set(n)
shed_total.labels(route=r, reason="overload"|"deadline"|"priority").inc()
shed_level.set(level)
capacity_utilisation.set(in_flight / max_concurrent)
queue_wait_seconds.observe(elapsed)
```

💡 **`shed_total` rising is not necessarily an incident — it is the system working.** The alert should be on *sustained* shedding, which means capacity is genuinely insufficient rather than a spike being absorbed.

⚠️ **Shedding with low CPU means the bottleneck is elsewhere** — a downstream dependency, a connection pool, or a lock. **Shedding at high CPU means you need more capacity.** The two need different responses.

### Where to shed

| Layer | |
|---|---|
| **Load balancer** | Cheapest, least context. Connection limits |
| **Gateway** | **The right default.** Global view, cheap rejection |
| Service | Per-service protection, more context |
| **Database pool** | The last line — shed before exhausting connections |

💡 **Shed at multiple layers with different thresholds**, so each protects the next. The gateway sheds at 80% of its capacity; a service sheds at 90% of its own.

### Conduit's shedding

| Layer | Signal | Threshold | Sheds |
|---|---|---|---|
| Gateway | In-flight requests | 70 / 85 / 95% | Analytics → reads → all but auth |
| Gateway | Deadline consumed | > 80% | The request, immediately |
| Documents service | Postgres pool wait | > 100ms p99 | Non-critical reads |
| Ingestion workers | **Queue age** | > 5 min | New enqueues rejected ([[08.1 - Why Background Work Exists]]) |
| Embedding | Concurrency limit | 4 concurrent | Queues rather than sheds — durable work |

💡 **Ingestion sheds on queue *age*, not depth.** A deep queue of fresh work is healthy; a shallow queue of old work is not.

⚠️ **Embedding queues rather than shedding**, because the work is durable and the user has already been told "processing". **Shedding is for synchronous requests with a waiting client; queueing is for durable background work** — and knowing which is which per path is the design decision.

💡 The Google SRE chapter's **client-side adaptive throttling** is the idea worth stealing: **a client that has been rejected repeatedly starts rejecting its own requests locally**, before sending them. It reduces load on an overloaded server without requiring the server to spend anything on rejection.

**Part 1 — Watch queueing fail.** A service with 1,000 rps capacity, offered 1,500 rps for five minutes.

**Unbounded queue:** chart queue depth, p99 latency, and **goodput** — responses delivered to clients that had not already timed out.

**Goodput should approach zero** while the success rate looks fine internally. That divergence is the point.

Then measure the same with the queue bounded at 100.

**Part 2 — Find your capacity.** Sweep concurrency: 5, 10, 25, 50, 100, 200, 400.

Chart throughput and p99 latency. **Find the plateau, and find the point where throughput declines.**

**Set `max_concurrent` at the plateau.** Then verify: at that limit, is p99 acceptable?

**Part 3 — Four shedding strategies.** Under 1.5× overload:

| Strategy | Measure |
|---|---|
| Random | Goodput, and which request types survived |
| Priority-based | Same, plus whether critical paths were preserved |
| Deadline-based | Same, plus wasted work eliminated |
| Graduated levels | Same, plus behaviour as load rises gradually |

**Chart goodput for each.** Priority and deadline shedding should preserve substantially more useful work than random.

**Then measure specifically: with random shedding, what fraction of authentication requests were dropped?** That number is the argument for priority.

**Part 4 — Backpressure through a pipeline.** Four stages with bounded queues, the last stage slow.

**Confirm the backpressure propagates to the producer** and that memory stays flat.

Then make one queue unbounded. **Confirm memory grows without bound** and the backpressure never reaches the producer.

**Chart memory for both.**

**Part 5 — Adaptive versus fixed.** A service whose capacity halves partway through the test — simulate with an injected dependency slowdown.

**Fixed limit:** measure goodput and latency after the capacity drop.
**Gradient adaptive:** measure the same, and chart the limit value over time.

**The adaptive version should track the new capacity within seconds.**

**Part 6 — The cost of rejection.** Two shedding implementations: one that rejects after authentication and body parsing, one that rejects first.

**Under 3× overload, measure the throughput of the rejection path itself.**

**The expensive version should be unable to reject fast enough**, which means it provides no protection at extreme load.

**Part 7 — Metastable recovery.** Induce a metastable failure ([[11.1 - How Systems Fail]]): a 3× spike with retries and an unbounded queue, then remove the spike.

**Confirm the system stays down.**

Then with shedding enabled, same test. **Confirm it recovers immediately** when the spike ends.

**Measure the recovery time for both.**

**Part 8 — The ADR.** Conduit's shedding configuration per layer.

**Every threshold derived from your capacity measurement.** For each path, state the priority, the shed trigger, and what the client is told.

**Justify the ingestion path queueing rather than shedding.**

**Done when:**
- Your goodput chart shows unbounded queueing delivering nothing
- You know your capacity from a measured throughput plateau
- Priority shedding demonstrably preserves more useful work than random
- Deadline shedding eliminates measurable wasted work
- Backpressure propagates through bounded queues and breaks at an unbounded one
- Your adaptive limit tracks a halved capacity within seconds
- The expensive rejection path fails to protect under extreme load
- Shedding turns a metastable failure into an immediate recovery
