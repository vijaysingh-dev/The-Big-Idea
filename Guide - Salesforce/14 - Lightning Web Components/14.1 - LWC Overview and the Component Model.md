# LWC Overview and the Component Model

## What LWC is

**Lightning Web Components** are built on native web standards — custom elements, shadow DOM, ES modules, and modern JavaScript. Salesforce adds a thin layer for data access, navigation, and platform integration.

The practical consequence: **what you know about web development transfers.** Aura had its own component model, its own expression syntax, and its own event system, all of which had to be learned separately. LWC is JavaScript classes and HTML templates.

```javascript
import { LightningElement, api } from 'lwc';

export default class ClaimSummary extends LightningElement {
    @api recordId;
    claimNumber;

    get isHighValue() {
        return this.amount > 500000;
    }
}
```

```html
<template>
    <lightning-card title="Claim Summary">
        <p class="slds-p-horizontal_small">{claimNumber}</p>
        <template lwc:if={isHighValue}>
            <lightning-badge label="High Value"></lightning-badge>
        </template>
    </lightning-card>
</template>
```

## The three files

A component is a folder containing files sharing the folder's name:

```
force-app/main/default/lwc/claimSummary/
    claimSummary.html          the template
    claimSummary.js            the class
    claimSummary.js-meta.xml   where it can be used
    claimSummary.css           optional styles
    __tests__/claimSummary.test.js   optional Jest tests
```

**The folder name is the component name**, in camelCase. Referenced from another template it becomes kebab-case with the `c-` namespace:

```html
<c-claim-summary record-id={recordId}></c-claim-summary>
```

That naming translation — `claimSummary` in the folder, `c-claim-summary` in markup, and `recordId` becoming `record-id` — catches everyone once.

## Shadow DOM

Each component's DOM is encapsulated. Styles do not leak in or out, and a parent cannot reach into a child's internals with a query selector.

```javascript
// Finds elements inside THIS component only
this.template.querySelector('.claim-row');

// Does not exist in LWC — you cannot reach into a child's shadow root
document.querySelector('.claim-row');
```

This is enforced, not conventional. It means:

**Styles are scoped.** A `.header` class in one component does not affect another. See [[14.15 - Styling, SLDS and Design Tokens]].

**Parents cannot manipulate children directly.** Communication happens through public properties downward and events upward. See [[14.6 - Parent to Child Communication]] and [[14.7 - Child to Parent Communication and Events]].

**Third-party libraries expecting global DOM access often break**, because they cannot see inside shadow roots.

Salesforce has been moving toward **native shadow DOM** from its earlier synthetic implementation, which changes some edge-case behaviour around events and styling. Components written to the standard rather than to synthetic quirks migrate cleanly.

## Where a component can run

```
Lightning record page, app page, home page
Lightning App Builder, as a draggable component
A quick action on a record
Experience Cloud pages
The Salesforce mobile app
A utility bar item in a console
A flow screen
Embedded in an Aura component
Standalone, via lightning-out, in an external page
Salesforce Field Service mobile
```

Where it runs is declared in the metadata file, and getting that wrong is why a component does not appear in App Builder. See [[14.2 - Component Structure and Metadata]].

## The platform modules

The Salesforce-specific surface, imported like any module:

```javascript
import { LightningElement, api, track, wire } from 'lwc';
import { getRecord, updateRecord } from 'lightning/uiRecordApi';
import { NavigationMixin } from 'lightning/navigation';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';
import { refreshApex } from '@salesforce/apex';
import { subscribe, unsubscribe } from 'lightning/empApi';
import { publish, MessageContext } from 'lightning/messageService';
import getClaims from '@salesforce/apex/ClaimController.getClaims';
import CLAIM_AMOUNT_FIELD from '@salesforce/schema/Warranty_Claim__c.Claim_Amount__c';
import USER_ID from '@salesforce/user/Id';
import HAS_APPROVAL_PERMISSION from '@salesforce/customPermission/Can_Approve_Claims';
```

Two of those deserve early attention.

**`@salesforce/schema` imports** give compile-time-checked field references. Importing a field that does not exist fails at deployment, and — importantly — **a field imported this way cannot be deleted** without first removing the reference. That dependency tracking is a genuine benefit over string field names.

**`@salesforce/customPermission`** imports a boolean for whether the running user holds a custom permission, which is how UI is gated without an Apex call. See [[03.4 - Permission Sets and Permission Set Groups]].

## What LWC gives you free

**Field-level security enforcement** through Lightning Data Service and the UI API. A field the user cannot see does not appear, with no Apex and no `stripInaccessible`. See [[14.12 - Lightning Data Service and Record Forms]].

**A record cache** shared across components. Two components displaying the same record fetch it once.

**Accessibility and responsive layout** from base components.

**Locale and currency formatting** from `lightning-formatted-*` components.

**Translation** through custom labels.

The recurring theme: **using the platform's data layer means less code and fewer security mistakes** than a custom Apex controller.

## Choosing LWC over the alternatives

Before building a component, the honest check:

**Can a page layout or Dynamic Forms do it?** Conditional field visibility, section arrangement, and related lists need no code. See [[04.14 - Path, Kanban and Sales Productivity]].

**Can a list view do it?** Filtering, inline editing, and mass actions are built in.

**Can a screen flow do it?** Guided data entry with branching, admin-maintainable, no test coverage burden. See [[07.5 - Screen Flows]].

**Does it need a component?** Custom interaction, custom visualization, a data shape no standard component expresses, or a screen flow that needs one interactive piece.

The pattern worth reaching for: **a screen flow as the container, with a custom LWC for the part that needs real interactivity.** The administrator owns the process; the developer owns the interaction.

Building a component to display three fields that Dynamic Forms would show is work with no return and permanent maintenance cost.

## Aura, and why it still exists

Aura components predate LWC and are still supported. You will meet them in any org more than a few years old.

**An LWC can be placed inside an Aura component. An Aura component cannot be placed inside an LWC.** That asymmetry shapes migration: the Aura shell stays, and its internals are replaced piece by piece.

A small number of things still require Aura — some quick action types and a few console APIs — though the list shrinks each release. See section 15.

## The mental adjustments

For a developer arriving from Aura, three things change.

**No expression syntax in templates.** Aura's `{!v.something}` becomes a getter in JavaScript. Logic lives in the class, not the markup.

**Events are DOM events**, not a separate framework construct. `CustomEvent` and `dispatchEvent`, standard browser APIs.

**Reactivity is automatic for fields**, and requires care for objects and arrays. Mutating a nested property does not trigger a rerender. See [[14.4 - Reactivity and Decorators]].

For a developer arriving from React or Vue, the adjustments are smaller: no virtual DOM diffing that you control, no JSX, and a template language closer to Angular's than to React's.
