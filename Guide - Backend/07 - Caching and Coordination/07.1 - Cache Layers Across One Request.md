# Cache Layers Across One Request

#backend #caching #architecture

> **In one line:** There are seven places a value can be cached between a user's browser and your disk, each with different invalidation properties — and choosing the wrong layer is why caches produce stale data and mysterious bugs.

---

## The Idea

```
Browser cache          ← 0 network, but you cannot invalidate it
  CDN edge             ← 0 origin load, purgeable
    Reverse proxy      ← in your control
      Application memory   ← nanoseconds, per-process, not shared
        Redis          ← microseconds, shared, invalidatable
          DB buffer pool   ← managed for you
            Disk
```

**Each layer is faster and less invalidatable than the one below it.**

💡 **The organising principle: cache as close to the user as the data's staleness tolerance allows.** Data that can be a day stale belongs at the CDN; data that must be current within a second belongs in Redis or nowhere.

⚠️ **The mistake is caching at the wrong layer for the invalidation you need.** A value cached in browser storage cannot be invalidated at all — you can only wait it out.

---

## The Layers

### 1. Browser

```http
Cache-Control: public, max-age=31536000, immutable
```

**Fastest possible: zero network.**

⚠️ **You cannot invalidate it.** The only escape is changing the URL.

💡 **This is why content-hashed asset URLs exist** — `/assets/app.a1b2c3.js` can be cached forever because its content can never change ([[03.5 - HTTP Caching]]).

**Only cache here what is genuinely immutable, or what you are content to have stale for the full TTL.**

### 2. CDN edge

```http
Cache-Control: public, s-maxage=300, stale-while-revalidate=600
Surrogate-Key: doc-42 org-7
```

**Removes load from your infrastructure entirely.** Purgeable by URL or by surrogate key.

⚠️ **`public` on anything user-specific is a data breach.** If the response depends on `Authorization` or a session cookie, it is `private`.

### 3. Reverse proxy

```nginx
proxy_cache api;
proxy_cache_valid 200 5m;
proxy_cache_lock on;              # stampede protection
proxy_cache_use_stale error timeout updating;
```

Same semantics as a CDN, inside your perimeter.

### 4. Application memory

```python
_config_cache = TTLCache(maxsize=1000, ttl=60)
```

**Nanoseconds. No serialisation, no network.**

| Good for | |
|---|---|
| Configuration and feature flags | Small, read constantly |
| Compiled regexes, parsed templates | Expensive to build, never change |
| Reference data | Country codes, currency lists |
| Per-request memoisation | DataLoader ([[05.6 - The N+1 Problem and DataLoader]]) |

⚠️ **Three properties make it dangerous for anything else:**

- **Not shared** — ten pods means ten copies with ten different values
- **Not invalidatable** — you cannot reach into every process to evict a key
- **Multiplied memory** — a 500MB cache × 40 workers is 20GB

💡 **The rule: application memory is for data that is small, read-heavy, and tolerant of being up to one TTL stale on each pod independently.** Anything user-specific or invalidatable belongs in Redis.

⚠️ **A per-process cache with unbounded size is a memory leak.** Always use a bounded structure with eviction.

### 5. Redis

**The workhorse layer.** Shared, invalidatable, sub-millisecond within a datacentre. A Redis lookup plus deserialisation is typically 0.2–1ms against a database query at 5–50ms.

⚠️ **Serialisation cost is real and often dominates.** A 100KB object with `json` costs several milliseconds; with `orjson` or msgpack, a fraction. **For large cached objects, serialisation is frequently more expensive than the network round trip.**

### 6. Database buffer pool

`shared_buffers` plus the OS page cache ([[06.2 - Postgres Architecture]]).

💡 **You do not manage this layer, but you influence it heavily.** Every unused index, bloated table and `SELECT *` displaces useful pages. **Reducing bloat is a caching optimisation, and often a larger one than adding a cache.**

### 7. Materialised results

```sql
CREATE MATERIALIZED VIEW org_stats AS
SELECT org_id, count(*) AS doc_count FROM documents GROUP BY org_id;

REFRESH MATERIALIZED VIEW CONCURRENTLY org_stats;
```

💡 **Underused for expensive aggregates.** It stays consistent with your data, it is queryable and joinable, and **it survives a Redis outage.**

⚠️ **`CONCURRENTLY` requires a unique index on the view** and takes longer, but does not block readers.

## Tracing One Request

```
GET /documents/42

Browser cache?           HIT  → 0 ms       (cannot invalidate)
  CDN?                   HIT  → 15 ms      (purgeable)
    nginx?               HIT  → 20 ms
      app memory?        HIT  → 21 ms      (per-pod, stale up to TTL)
        Redis?           HIT  → 22 ms      (shared, invalidatable)
          Postgres buffer pool?  HIT → 25 ms
            Disk               →  45 ms
```

| Value | Deepest tolerable layer |
|---|---|
| Content-hashed assets | Browser, forever |
| Public marketing content | CDN, minutes |
| Feature flags | App memory, 30s |
| A user's document list | Redis, 60s, invalidated on write |
| **A user's permissions** | **No cache**, or Redis with immediate invalidation |
| Live ingestion progress | No cache |

⚠️ **Permissions are the one to be careful with.** A cached permission 60 seconds stale means a revoked user retains access for 60 seconds. **Sometimes acceptable, and it must be a deliberate decision rather than an accident of using the same cache helper as everything else.**

## In Production

### Measure the hit ratio at every layer

```python
cache_requests_total.labels(layer="redis", result="hit").inc()
cache_get_duration_seconds.labels(layer="redis").observe(elapsed)
```

⚠️ **A layer with a low hit ratio is pure cost** — you pay the lookup and still go to the next layer. **Below roughly 30–50%, most caches are not worth their complexity.**

**Track it per key prefix, not globally.** A global 80% hit ratio can hide one prefix at 5% doing all the damage.

### Origin load is the number that matters

```
Requests at the edge:    10,000/s
Requests at nginx:        1,200/s
Requests at the app:        400/s
Queries at the database:    120/s
```

💡 **This ladder is the clearest possible picture of what your caching is doing.** Chart all four on one graph — when someone asks whether the CDN is worth it, the gap between the first two lines is the answer.

### The cost of getting it wrong

| Mistake | Consequence |
|---|---|
| Caching user data at a `public` layer | **Data breach** |
| Caching in app memory what needs invalidation | **Inconsistent behaviour across pods, very hard to debug** |
| Caching permissions with a long TTL | Revoked access persists |
| No stampede protection | Every expiry is a load spike ([[07.3 - Stampede Hot Keys and Negative Caching]]) |
| Unbounded in-process cache | Memory leak |

⚠️ **The "inconsistent across pods" case is the worst to debug.** A user refreshes and sees different data each time, depending on which pod served them. **It looks like a race condition and it is a caching layer choice.**

### When not to cache

💡 **Caching is a workaround for a slow operation, and sometimes fixing the operation is better.**

| Situation | Fix instead |
|---|---|
| A slow query | Add the index ([[06.3 - Indexes Deep Dive]]) |
| An N+1 | Batch it |
| An expensive aggregate | Materialised view, or a maintained counter |
| **A slow external API** | **Cache — this one is genuinely right** |
| Data that changes on every read | Do not cache |

⚠️ **A cache in front of a query that should have an index hides the problem and doubles your infrastructure.**

### The decision procedure

1. **How stale can it be?** → determines the deepest layer
2. **Is it user-specific?** → if yes, `private`, never a shared public layer
3. **How is it invalidated?** → TTL, event-driven, or never
4. **What is the read/write ratio?** → below about 10:1, caching rarely pays
5. **What happens on a cache miss storm?** → stampede protection needed
6. **What happens if the cache is down?** → degrade or fail
7. **What is the cost of stale data?** → a wrong number, or a security issue

⚠️ **Question 7 separates a caching decision from a caching accident.** "The document list is 30 seconds stale" is a minor annoyance; "the permission check is 30 seconds stale" is a vulnerability. **Same cache, same TTL, entirely different risk.**

### Cache-down behaviour

```python
try:
    if cached := await redis.get(f"doc:{doc_id}"):
        return Document.model_validate_json(cached)
except RedisError:
    cache_errors_total.inc()          # degrade, do not fail
return await repo.get(doc_id)
```

💡 **A cache should never be the reason a request fails.** Treat every cache read as best-effort with a short timeout.

⚠️ **But be aware of what happens when it is entirely down**: every request goes to the database at once. **If your database is sized assuming a 95% hit ratio, a Redis outage is a 20× load spike that takes the database down too.**

**Test this.** Turn Redis off under load and see whether you survive. If not, you need database headroom, load shedding ([[11.4 - Backpressure and Load Shedding]]), or a local fallback.

## Codebase

**Repo:** `nginx/nginx`, `redis/redis`, `caddyserver/caddy`

**Question to answer:** Trace one request through a caching proxy: how is the cache key computed, when is a response storable, and what happens on a stale hit? Then: how does Redis decide what to evict when memory is full?

**Read, in order:**

1. `nginx/src/http/ngx_http_file_cache.c` — **key computation and the storability decision.** Find `ngx_http_file_cache_open` and the stale-response handling
2. `nginx/src/http/modules/ngx_http_proxy_module.c` — how `Vary`, `Cache-Control` and `Set-Cookie` affect whether a response is cached
3. `redis/src/evict.c` — **`performEvictions` and the approximate LRU.** Redis samples keys rather than maintaining a true LRU, and the code explains why
4. `redis/src/expire.c` — **lazy plus sampled expiry.** A key with a TTL is deleted when accessed, or when the sampling cycle finds it
5. `caddy/modules/caddyhttp/reverseproxy/` — a modern readable implementation of the same decisions

💡 The Redis expiry mechanism has a practical consequence people are surprised by: **setting a TTL on a million keys does not free memory at the TTL.** Memory is reclaimed lazily and by sampling, **so your memory graph does not drop when you expect it to.**

**Size:** 1 session.

## Exercise

**Drill 7.1 — Build the full stack and measure each layer**

```
drills/07-cache-layers/
├── stack/{compose.yml, nginx.conf}
├── app/{layers.py, endpoints.py, instrumentation.py}
├── measure/{ladder.py, hit_ratios.py, latency.py, PLOT.md}
├── mistakes/{public_private.py, memory_divergence.py, stale_permissions.py, FINDINGS.md}
├── failure/{redis_down.py, degradation.py, RESULTS.md}
├── decision/conduit_matrix.md
└── README.md
```

**Part 1 — Build all the layers.** nginx with `proxy_cache`, an in-process TTL cache, Redis, and Postgres, all instrumented.

Five endpoints with genuinely different cacheability: an immutable asset, public configuration, a user's document list, a single document, and a live progress value.

**Part 2 — The ladder chart.** Chart requests per second arriving at each layer simultaneously.

**This one graph is the deliverable.** Then remove one layer at a time and re-chart, quantifying each layer's contribution.

**Part 3 — Latency contribution.** For a full-miss request, break down where the time goes: network, nginx, application, Redis lookup, deserialisation, database query, serialisation.

**Then do the same for a hit at each layer.**

⚠️ **Pay attention to the deserialisation column.** For a large cached object it is often larger than the Redis round trip, **and that changes what you should cache.**

**Part 4 — Three mistakes, demonstrated.**

- **`public` on user data:** two users behind the same cache, one receiving the other's data. Fix it and write the test
- **Per-pod divergence:** three pods with in-memory caches, a value updated on one. **Show a user refreshing and seeing alternating values.** Measure how long the inconsistency lasts
- **Stale permissions:** cache a permission for 60 seconds, revoke access, measure the exposure window. **Write down what TTL you would accept and why**

**Part 5 — Redis goes down.** Steady load with a 95% hit ratio. Kill Redis.

**Measure the database load spike — it should be roughly 20×.** Chart database CPU, connection pool wait time, and application p99. **Determine whether you survive.**

Then implement three mitigations and re-test: a small local fallback cache, load shedding based on database pool pressure, and request coalescing.

**Part 6 — Fix versus cache.** A slow endpoint (400ms) caused by a missing index.

Version A: Redis in front. Version B: add the index.

Measure p50, p99, infrastructure required, staleness introduced, and cold-cache behaviour. **Then combine them and measure again. Write down the general rule you would apply.**

**Part 7 — The Conduit matrix.** For every cached value: staleness tolerance, layer, TTL, invalidation mechanism, cost of staleness, and behaviour when unavailable.

**Answer all seven decision questions for each.** This matrix stops caching decisions from being made ad hoc.

**Done when:**
- Your ladder chart shows load removed at each layer
- Your latency table covers a full miss and a hit at every layer
- You have caused and fixed a cross-user cache leak, with a test
- You have measured per-pod cache divergence duration
- You know whether your system survives Redis going down, with numbers
- The fix-versus-cache comparison has a stated general rule
- The Conduit matrix answers seven questions for every cached value
