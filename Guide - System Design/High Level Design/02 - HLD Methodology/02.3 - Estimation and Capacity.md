## Why Estimation Matters

Estimation converts vague requirements into concrete numbers that drive architecture decisions.

"Design a URL shortener" could mean:
- 100 RPS → single Postgres instance, one server, done
- 100,000 RPS → load balancer, read replicas, Redis cache, horizontal scaling
- 10M RPS → global distribution, custom storage, sharding

You can't pick the right architecture without knowing which world you're in.

**In interviews:** Estimation demonstrates engineering judgment. Arriving at reasonable numbers quickly signals experience. Getting them exactly right is not the point.

## The Powers of 10 — Memorize These

```
1 thousand     = 10³  = 1K
1 million      = 10⁶  = 1M
1 billion      = 10⁹  = 1B
1 trillion     = 10¹² = 1T

1 KB  = 10³  bytes
1 MB  = 10⁶  bytes
1 GB  = 10⁹  bytes
1 TB  = 10¹² bytes
1 PB  = 10¹⁵ bytes

Seconds in a minute:    60
Seconds in an hour:     3,600
Seconds in a day:       86,400  ≈ 10⁵
Seconds in a year:      31,536,000 ≈ 3 × 10⁷
```

## Traffic Estimation

### DAU to QPS

```
QPS (avg) = DAU × actions_per_user_per_day / 86,400

Peak QPS  = avg QPS × peak_factor (typically 2–3×)
```

**Example (URL Shortener):**
```
DAU = 100M
Writes per user per day = 0.1 (most users just redirect)
Reads per user per day  = 1

Write QPS = 100M × 0.1 / 86,400 ≈ 120 writes/s
Read  QPS = 100M × 1   / 86,400 ≈ 1,160 reads/s
Peak read = 1,160 × 3 ≈ 3,500 reads/s
Read:write ratio ≈ 10:1
```

### QPS Benchmarks (rough rules of thumb)

| Load | Typical Solution |
|---|---|
| < 1,000 RPS | Single server + DB |
| 1K–10K RPS | Load balancer + 2–5 servers + read replica |
| 10K–100K RPS | Horizontal scaling + cache layer + DB replication |
| 100K–1M RPS | Sharding, distributed cache, CDN for statics |
| > 1M RPS | Global distribution, custom infrastructure |

## Storage Estimation

```
Storage = records_per_day × record_size_bytes × retention_days
```

**Example (URL Shortener):**
```
New URLs per day = Write QPS × 86,400 = 120 × 86,400 ≈ 10M/day

Record size:
  short_code:   7 bytes
  long_url:     100 bytes (avg)
  created_at:   8 bytes
  expires_at:   8 bytes
  user_id:      8 bytes
  Total:       ~131 bytes ≈ 130 bytes

Storage per day = 10M × 130 bytes = 1.3 GB/day
Storage per year = 1.3 × 365 ≈ 475 GB/year
Storage for 5 years ≈ 2.4 TB
```

A 2.4 TB relational database is manageable on a single well-provisioned machine with read replicas. No sharding needed.

---

## Bandwidth Estimation

```
Inbound  bandwidth = write QPS × avg_request_size
Outbound bandwidth = read  QPS × avg_response_size
```

**Example (URL Shortener):**
```
Write: 120 writes/s × 500 bytes/request = 60 KB/s   (negligible)
Read:  3,500 reads/s × 300 bytes/response = 1.05 MB/s (trivial)
```

For a video streaming platform:
```
Concurrent viewers = 1M
Bitrate per stream  = 5 Mbps (1080p)
Bandwidth = 1M × 5 Mbps = 5 Tbps  ← needs CDN, massive edge distribution
```

Bandwidth estimation reveals whether you need a CDN.

---

## Memory / Cache Estimation

```
Cache size = hot_data_fraction × total_data_size

Rule of thumb: 20% of data handles 80% of traffic (Pareto principle)
```

**Example (URL Shortener):**
```
Total data = 2.4 TB over 5 years
Hot data (20%) = 480 GB

That's too large for a single Redis instance.
→ Cache only the most recent/popular: 1% of data = 24 GB
→ Fits comfortably in Redis (64GB instance or Redis Cluster)
```

## Latency Budget

When you have a p99 requirement (e.g., < 200ms), allocate it across components:

```
200ms budget:
  Network (client → server):    10ms
  API Gateway / Load Balancer:   5ms
  Service processing:           20ms
  Cache lookup (hit):            1ms
  DB query (cache miss):        30ms
  Network back to client:       10ms
  ─────────────────────────────
  Total (happy path):           76ms  ✅ well within budget

Cache miss rate matters:
  If 90% cache hit: p99 mostly 76ms
  If 50% cache hit: p99 includes more DB queries → may exceed budget
```

This kind of thinking is what senior engineers do — they budget latency, not just estimate total.

## The Estimation Process in Interviews

**Step 1: State your inputs**
"Let me assume 100M DAU, users create 1 short URL per week on average, and do about 5 redirects per day."

**Step 2: Derive QPS**
"That gives us roughly 170 writes/s and 5,800 reads/s, with peak around 15K reads/s."

**Step 3: Derive storage**
"At 130 bytes per record and 15M new URLs per day, we're looking at about 700 GB per year."

**Step 4: Call out the implications**
"This scale is manageable with a single sharded Postgres + Redis cache. We don't need anything exotic."

The insight in step 4 is what interviewers are looking for — estimation feeding architecture decisions.

## Common Estimation Mistakes

| Mistake | Fix |
|---|---|
| Getting bogged down in precision | Round aggressively. 86,400 ≈ 10⁵ is fine. |
| Forgetting peak vs average | Always multiply avg by 2–3× for peak |
| Estimating storage but not bandwidth | Both matter — bandwidth decides CDN |
| Not connecting estimates to design | "So at 15K RPS, we'll need at least 5 app servers and Redis in front of the DB" |
| Assuming the same scale for all operations | Reads and writes have different rates — estimate separately |
