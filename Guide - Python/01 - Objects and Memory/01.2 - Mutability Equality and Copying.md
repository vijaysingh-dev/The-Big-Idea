# Mutability Equality and Copying

#python #memory #fundamentals

> **In one line:** Mutable objects can change in place, so every name bound to them sees the change. `is` compares identity and `==` compares value. A shallow copy duplicates the outer container only, and that is enough to cause most "why did my data change?" bugs.

---

## Mutable vs Immutable

| Immutable | Mutable |
|---|---|
| `int`, `float`, `bool`, `str`, `bytes`, `tuple`, `frozenset`, `None` | `list`, `dict`, `set`, `bytearray`, most user-defined class instances |

"Immutable" means **the object's value cannot change**. Operations that look like changes create new objects:

```python
s = "abc"
t = s
s += "d"          # new str object; t still "abc"

nums = [1, 2]
alias = nums
nums += [3]       # same list mutated; alias sees [1, 2, 3]
```

⚠️ **A tuple is immutable, but what it contains may not be.**

```python
t = ([1, 2], "x")
t[0].append(3)      # fine: the list inside changed, the tuple's references did not
print(t)            # ([1, 2, 3], 'x')
hash(t)             # TypeError: unhashable type: 'list'
```

The famous puzzle: `t[0] += [4]` **both raises `TypeError` and mutates the list**. The `+=` first calls `list.__iadd__` (which succeeds), then tries to assign back into the tuple (which fails).

## `is` vs `==`

| | Asks | Calls |
|---|---|---|
| `a is b` | Are these the **same object**? | Nothing. Compares identities. Cannot be overridden. |
| `a == b` | Do these have **equal values**? | `a.__eq__(b)`, which you can define |

Rules:

- Use `is` for singletons: `None`, `True`, `False`, sentinel objects. `if x is None:`.
- Use `==` for everything else.
- **Never** use `is` to compare numbers or strings. It sometimes works because of interning, which makes the bug worse.

### Interning: why `is` sometimes "works"

CPython caches some immutable objects so they are shared:

```python
a = 256; b = 256
a is b          # True — small ints from -5 to 256 are preallocated singletons

a = 257; b = 257
a is b          # may be True or False, depending on whether they were compiled together

x = "hello"; y = "hello"
x is y          # True — identifier-like string literals are interned
x = "hello world!"; y = "hello world!"
x is y          # implementation detail; do not rely on it
```

`sys.intern(s)` interns a string manually. It is useful when you have millions of repeated keys (column names from a parser, for example) and want dictionary lookups to hit the fast identity check first.

## Shared References: The Bugs

### Lists of lists

```python
grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)       # [[1, 0, 0], [1, 0, 0], [1, 0, 0]] — three references to ONE row

grid = [[0] * 3 for _ in range(3)]   # three separate rows
```

### Defaults shared between calls

```python
def add(item, bucket=[]):     # the [] is created ONCE, when def runs
    bucket.append(item)
    return bucket

add(1)   # [1]
add(2)   # [1, 2] — the same list
```

Covered with its fix in [[02.1 - Parameters and Arguments]].

### Class-level mutable attributes

```python
class Cart:
    items = []          # shared by EVERY instance
    def add(self, x):
        self.items.append(x)
```

Fix: create it in `__init__`, or use `field(default_factory=list)` in a dataclass ([[07.2 - Dataclasses]]).

## Copying

```python
import copy

orig = {"user": "a", "tags": ["x", "y"]}

alias = orig                    # no copy at all
shallow = orig.copy()           # or dict(orig), copy.copy(orig), {**orig}
deep = copy.deepcopy(orig)

orig["tags"].append("z")
shallow["tags"]                 # ['x', 'y', 'z'] — shares the inner list
deep["tags"]                    # ['x', 'y']
```

```
orig    ──►  {user: ─► "a",  tags: ─► [x, y, z]}
                                     ▲
shallow ──►  {user: ─► "a",  tags: ──┘}           new outer dict, same inner list
deep    ──►  {user: ─► "a",  tags: ─► [x, y]}     everything recreated
```

| Copy | How | Cost | Use when |
|---|---|---|---|
| Shallow | `list(x)`, `x[:]`, `x.copy()`, `copy.copy` | Cheap: O(n) references | Elements are immutable, or you want to share them |
| Deep | `copy.deepcopy` | Expensive: walks everything, handles cycles with a memo dict | You need full independence; nested mutable data |
| Custom | Define `__copy__` / `__deepcopy__` | You decide | Objects holding connections, locks, or caches that must not be copied |

⚠️ **`deepcopy` is slow.** In hot paths (per-request), it is a common hidden cost. Prefer immutable data (tuples, frozen dataclasses, Pydantic models with `frozen=True`) so copying is unnecessary, or build a new object explicitly. Pydantic's `model.model_copy(update={...})` is shallow by default, and `deep=True` is opt-in.

## Immutability as a Design Tool

Immutable values are safe to share between functions, threads and caches without defensive copying. In backend code:

- Configuration objects: frozen dataclasses or Pydantic settings ([[07.4 - Pydantic in Production]]).
- Cache keys: must be hashable, so immutable ([[05.2 - Sets and Hashing Your Own Classes]]).
- Domain events: should never change after creation.
