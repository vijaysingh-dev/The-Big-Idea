# Performance and Rendering

## Why this matters more in Salesforce

A support agent handles forty interactions a day. A page that takes two extra seconds costs them eighty seconds daily, and every one of those seconds is visible to a customer on the phone.

In a console app the multiplier is worse: components render on every tab switch, and an agent may hold six tabs open.

Performance in LWC is not a nice-to-have; it is the difference between a console people use and one they complain about. See [[05.8 - Service Console and Agent Productivity]].

## What triggers a rerender

Assigning to a field the template reads.

```javascript
this.claims = newClaims;              // rerenders
this.isLoading = false;               // rerenders
this.internalCounter = 5;             // no rerender if the template never reads it
this.claims.push(newClaim);           // no rerender — see 14.4
```

LWC then diffs and updates only the changed DOM. The diff is cheap; what happens **around** it usually is not.

## Getters run on every rerender

The most common invisible cost.

```javascript
// Recomputed on every rerender, including ones with nothing to do with claims
get sortedClaims() {
    return [...this.claims]
        .sort((a, b) => b.Claim_Amount__c - a.Claim_Amount__c)
        .map((claim) => ({
            ...claim,
            statusClass: claim.Status__c === 'Rejected' ? 'slds-theme_error' : '',
            formattedDate: new Date(claim.Claim_Date__c).toLocaleDateString()
        }));
}
```

With 300 rows, an unrelated `isLoading` toggle re-sorts and re-maps all 300.

Compute when the data changes instead:

```javascript
@wire(getClaims, { accountId: '$recordId' })
wiredClaims(result) {
    this.claimResult = result;

    if (result.data) {
        // done once per data change rather than once per rerender
        this.sortedClaims = [...result.data]
            .sort((a, b) => b.Claim_Amount__c - a.Claim_Amount__c)
            .map((claim) => ({ ...claim, statusClass: this.classFor(claim) }));
    }
}
```

**Keep getters trivial.** A getter returning a boolean or a property is fine. A getter sorting, mapping, or filtering a collection belongs in the data handler.

There is also a subtler cost: **a getter returning a new array or object on every call defeats the diff.** LWC compares by reference, so a fresh array each render means the whole list rerenders even when nothing changed.

## Keys in iteration

```html
<!-- Wrong: index keys break reuse on reorder and removal -->
<template for:each={claims} for:item="claim" for:index="index">
    <c-claim-row key={index} claim={claim}></c-claim-row>
</template>

<!-- Correct -->
<template for:each={claims} for:item="claim">
    <c-claim-row key={claim.Id} claim={claim}></c-claim-row>
</template>
```

With index keys, removing the first item makes every subsequent row reuse the wrong DOM node — and the wrong component state. The visible symptom is a checkbox appearing ticked on the wrong row, and the performance symptom is the whole list re-rendering when one item changes.

A stable unique key is what lets LWC reuse DOM for unchanged rows.

## Conditional rendering versus hiding

```html
<!-- Not constructed at all until shown -->
<template lwc:if={isDetailVisible}>
    <c-claim-detail claim-id={selectedId}></c-claim-detail>
</template>

<!-- Constructed, wired, and rendered — just invisible -->
<c-claim-detail claim-id={selectedId} class={detailClass}></c-claim-detail>
```

A component behind a false `lwc:if` is not constructed, its wires do not run, and its `connectedCallback` does not fire. A component hidden with CSS does all of it.

**Tabs, accordions, and modals should use `lwc:if`.** A tabset rendering all six panels on load pays for six components the user may never open.

The tradeoff: toggling `lwc:if` destroys and recreates the component, losing its state and re-running its wires. For something toggled frequently, CSS hiding may be the better trade — but for content the user opens once, `lwc:if` wins clearly.

## Reduce the number of Apex calls

Each round trip has latency independent of the query cost.

```javascript
// Three round trips
@wire(getClaims, { accountId: '$recordId' }) claims;
@wire(getCoverage, { accountId: '$recordId' }) coverage;
@wire(getAssets, { accountId: '$recordId' }) assets;
```

```java
// One
@AuraEnabled(cacheable=true)
public static AccountContext getContext(Id accountId) {
    AccountContext context = new AccountContext();
    context.claims = ClaimSelector.openByAccount(accountId);
    context.coverage = CoverageSelector.activeByAccount(accountId);
    context.assets = AssetSelector.byAccount(accountId);
    return context;
}
```

One method returning a composed object is one network round trip instead of three, and one Apex transaction instead of three. See [[14.10 - Calling Apex - Wire vs Imperative]].

**Use `cacheable=true` wherever the method is read-only.** The client cache is free performance, and two components asking for the same thing fetch once.

## Select fewer fields

```java
// Expensive per row: formula fields are computed on read
SELECT FIELDS(ALL) FROM Warranty_Claim__c WHERE Account__c = :accountId LIMIT 200

// What the component actually displays
SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c, Claim_Date__c,
       Asset__r.SerialNumber
FROM Warranty_Claim__c WHERE Account__c = :accountId LIMIT 200
```

Every field is data serialized, transferred, and held in memory. Cross-object formula fields are computed per row on the server. See [[06.4 - Cross-Object Formulas and Limits]].

## Cap the row count

```java
LIMIT 200
```

A component rendering 5,000 rows is slow regardless of how well it is written — `lightning-datatable` has no virtualization and renders every row.

Beyond a few hundred, paginate. See [[14.13 - Base Components and lightning-datatable]].

## Debounce user input

```javascript
handleSearchChange(event) {
    const value = event.target.value;

    // collapses a burst of keystrokes into one search
    clearTimeout(this.searchTimer);
    this.searchTimer = setTimeout(() => {
        this.searchTerm = value.length >= 3 ? value : undefined;
    }, 300);
}

disconnectedCallback() {
    clearTimeout(this.searchTimer);
}
```

Without debouncing, a ten-character search term fires ten Apex calls. With it, one.

Clearing the timer on disconnect prevents a search firing against an unmounted component.

## Component count

Every component has construction, connection, and render cost. A record page with fourteen components, several making Apex calls, is slow before any of them does anything expensive.

The audit worth running on a slow page:

1. Count the components
2. Identify which make Apex calls, and whether they are `cacheable`
3. Look for one fetching a large related list to display a count
4. Check for describe calls or heavy computation in getters
5. Consider whether some belong behind a tab rather than in the main view

A common finding: a component querying 500 related records to display a number that a roll-up summary field already holds.

## renderedCallback discipline

```javascript
renderedCallback() {
    // fires on EVERY rerender — unguarded work here runs repeatedly
    this.template.querySelectorAll('.claim-row').forEach((row) => {
        row.classList.toggle('highlight', row.dataset.status === 'Overdue');
    });
}
```

Guard one-time work, and avoid DOM manipulation that the template could express declaratively:

```html
<div key={claim.Id} class={claim.rowClass}>
```

Computing the class in the data handler and binding it is cheaper than a DOM pass on every render, and it survives rerenders correctly.

**Never set reactive state unguarded in `renderedCallback`** — it loops. See [[14.5 - Component Lifecycle Hooks]].

## Lazy loading

```javascript
async loadChartLibrary() {
    if (this.chartLoaded) {
        return;
    }
    this.chartLoaded = true;

    // loading only when the tab is opened keeps it off the initial page load
    await loadScript(this, CHART_JS + '/chart.min.js');
    this.initializeChart();
}

handleTabActive(event) {
    if (event.target.value === 'analytics') {
        this.loadChartLibrary();
    }
}
```

A charting library loaded on page render costs every user; loaded on tab activation it costs only those who open the tab.

The same applies to dynamic component imports:

```javascript
const { default: ctor } = await import('c/heavyVisualization');
this.componentConstructor = ctor;
```

## Measuring

**Chrome DevTools Performance panel** — record a page load, look at scripting time and layout.

**The Lightning Component Usage app** in Setup shows component load times across the org, aggregated. It is the only view that shows which components are slow **for real users**, and it is underused.

**`Instrumentation` markers** for custom timing:

```javascript
connectedCallback() {
    performance.mark('claimList-start');
}

renderedCallback() {
    if (this.measured) {
        return;
    }
    this.measured = true;
    performance.mark('claimList-end');
    performance.measure('claimList', 'claimList-start', 'claimList-end');
}
```

**The Salesforce Page Optimizer** browser extension analyses a Lightning page and reports the slow components, the number of server calls, and the metadata contributing to load time. It is the fastest way to find the problem on a specific page.

## Server-side contributions

A slow component is often a slow query rather than slow JavaScript.

**Check the Apex.** A non-selective query against a large object is the usual culprit, and it will not appear in browser profiling. See [[08.10 - Query Plan Tool and Query Optimization]].

**Check the automation.** A component doing an update triggers the whole save pipeline — validation rules, triggers, flows, roll-ups. A save that feels slow in a component may be twelve automations deep. See [[07.13 - Order of Execution]].

The diagnostic order that works: browser profiling to see whether time is client or server, then a debug log if it is server, then the query plan if it is a query.

## The console multiplier

Everything above matters more in a console app.

**Components rerender on tab switch.** Expensive getters run again each time.

**Several tabs mean several component instances**, each with its own wires and subscriptions.

**Leaked subscriptions accumulate.** A component not unsubscribing in `disconnectedCallback` leaves a subscription per tab opened, eventually hitting the concurrent client limit. See [[13.8 - Streaming API and PushTopics]].

**Utility bar components persist** across every tab, so anything expensive there costs continuously.

Testing a console component means opening ten tabs and switching between them, not opening one and looking at it.

## A checklist for a slow page

```
[ ] Count components on the page
[ ] Are read-only Apex methods cacheable?
[ ] Can several wires become one composed method?
[ ] Are getters doing sorting, mapping, or filtering?
[ ] Are iteration keys stable and unique?
[ ] Is hidden content behind lwc:if rather than CSS?
[ ] Is user input debounced?
[ ] Are queries selecting only needed fields, with a LIMIT?
[ ] Are queries selective? Check the query plan.
[ ] Is renderedCallback guarded?
[ ] Are third-party libraries loaded lazily?
[ ] Do subscriptions unsubscribe on disconnect?
[ ] How much automation runs on the objects being saved?
```

## Practical guidance

**Keep getters trivial.** Transform data when it arrives.

**Use stable unique keys** in iteration.

**Use `lwc:if` for content the user may never see.**

**Compose Apex responses** to reduce round trips.

**Mark read-only methods `cacheable=true`.**

**Select fewer fields, and cap rows.**

**Debounce search input.**

**Guard `renderedCallback`**, and prefer declarative class binding to DOM manipulation.

**Lazy-load heavy libraries.**

**Measure with the Page Optimizer and the Component Usage app** rather than guessing.

**Test console components with several tabs open.**
