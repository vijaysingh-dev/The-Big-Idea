# SOQL Fundamentals

## What SOQL is and is not

**SOQL** — Salesforce Object Query Language — reads records. It looks like SQL and is deliberately narrower.

What it does not have:

- **No `SELECT *`.** Every field must be named.
- **No joins in the SQL sense.** Relationships are traversed through defined relationship fields only.
- **No `UNION`, `INTERSECT`, or `EXCEPT`.**
- **No subqueries in the `SELECT` list**, except parent-to-child relationship subqueries.
- **No arbitrary expressions in `WHERE`.** Functions are limited.
- **No `INSERT`, `UPDATE`, or `DELETE`.** Writing is DML, a separate mechanism.

Those constraints exist because of multi-tenancy ([[01.5 - Multi-Tenant Architecture]]). The query engine rewrites every query against shared tables with your org's filter applied, and an arbitrary join surface would make that impossible to do safely.

## Basic shape

```sql
SELECT Id, Name, Status__c, Claim_Amount__c
FROM Warranty_Claim__c
WHERE Status__c = 'Submitted'
  AND Claim_Amount__c > 100000
ORDER BY Claim_Date__c DESC
LIMIT 100
```

In Apex, a query in square brackets is **inline SOQL**, compiled and validated at save time:

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c, Status__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
];
```

Compile-time validation is a real advantage — a typo in a field name fails at deployment, not at runtime. This is why inline SOQL is preferable to dynamic SOQL wherever the query is known in advance. See [[08.7 - Dynamic SOQL]].

## Bind variables

Apex variables are referenced with a colon. This is safe against injection and is the only correct way to pass values.

```java
String status = 'Submitted';
Decimal threshold = 100000;
Set<Id> assetIds = new Set<Id>{ assetId1, assetId2 };
Date cutoff = Date.today().addDays(-30);

List<Warranty_Claim__c> claims = [
    SELECT Id, Claim_Number__c
    FROM Warranty_Claim__c
    WHERE Status__c = :status
      AND Claim_Amount__c > :threshold
      AND Asset__c IN :assetIds
      AND Claim_Date__c >= :cutoff
];
```

Binding a `Set` or `List` to an `IN` clause is the single most useful form, and it is the foundation of every bulkified pattern — collect IDs into a set, query once for all of them.

Bind variables work in `WHERE`, `LIMIT`, `OFFSET`, and `IN`. They do **not** work for field names, object names, or the `ORDER BY` field. Those require dynamic SOQL with an allowlist.

## Returning a single record

```java
// Throws QueryException if zero or more than one row is returned
Account acc = [SELECT Id, Name FROM Account WHERE Id = :accountId];

// Safe: returns an empty list rather than throwing
List<Account> accounts = [SELECT Id, Name FROM Account WHERE Id = :accountId];
if (!accounts.isEmpty()) {
    Account acc = accounts[0];
}
```

Assigning directly to an sObject throws `List has no rows for assignment to SObject` when nothing matches. This is one of the most common runtime errors in Apex, and it is entirely avoidable by assigning to a list.

Use the direct form only where a missing record is genuinely exceptional and should fail loudly.

## Querying into a Map

Constructing a `Map` directly from a query result gives ID-keyed lookup with no loop. This removes most nested loops from Apex and is worth internalizing early.

```java
Map<Id, Account> accountsById = new Map<Id, Account>([
    SELECT Id, Name, Total_Revenue__c
    FROM Account
    WHERE Id IN :accountIds
]);

Account acc = accountsById.get(someAccountId);
Set<Id> foundIds = accountsById.keySet();
```

The map is keyed on `Id` automatically. Keying on any other field requires building the map manually in a loop.

## The FIELDS() shorthand

```sql
SELECT FIELDS(STANDARD) FROM Account WHERE Id = :accountId
SELECT FIELDS(CUSTOM) FROM Warranty_Claim__c WHERE Id = :claimId LIMIT 200
SELECT FIELDS(ALL) FROM Case WHERE Id = :caseId LIMIT 200
```

`FIELDS(ALL)` and `FIELDS(CUSTOM)` require a `LIMIT` of 200 or fewer, because they are unbounded in width. `FIELDS(STANDARD)` has no such requirement.

Convenient in anonymous Apex and in exploratory work. **Avoid it in production code**: it selects fields you do not need, inflates heap, computes every formula field on the object, and breaks the compile-time safety that makes inline SOQL valuable. It also silently changes behaviour when someone adds a field.

## Filtering

```sql
WHERE Status__c = 'Submitted'
WHERE Status__c != 'Closed'
WHERE Status__c IN ('Submitted', 'Under Review')
WHERE Status__c NOT IN ('Closed', 'Rejected')
WHERE Claim_Amount__c > 100000
WHERE Name LIKE 'North%'
WHERE Description__c LIKE '%press%'
WHERE Approved_Amount__c = NULL
WHERE Approved_Amount__c != NULL
WHERE (Status__c = 'Submitted' AND Priority__c = 'High')
   OR Escalated__c = true
```

Two things worth knowing:

**`LIKE` with a leading wildcard cannot use an index.** `Name LIKE 'North%'` can be selective; `Name LIKE '%press%'` cannot, and on a large object it will be slow or fail. Use SOSL for full-text search instead. See [[08.8 - SOSL and Full Text Search]] and [[08.9 - Indexes and Selective Queries]].

**`!= NULL` on a nullable field is not selective**, because most rows typically match. This is a common cause of a query that works in a dev org and times out in production.

## Date literals

The platform provides literals evaluated in the correct time zone, which is safer than constructing ranges in Apex:

```sql
WHERE CreatedDate = TODAY
WHERE CreatedDate = YESTERDAY
WHERE Claim_Date__c = THIS_WEEK
WHERE CloseDate = THIS_MONTH
WHERE CloseDate = THIS_FISCAL_QUARTER
WHERE ClosedDate = LAST_N_DAYS:30
WHERE End_Date__c = NEXT_N_DAYS:90
WHERE CreatedDate = LAST_N_MONTHS:12
WHERE CloseDate = LAST_N_FISCAL_QUARTERS:4
```

Prefer these to computing dates in Apex. They handle the user's time zone and the org's fiscal calendar, which manual construction gets wrong. See [[06.3 - Date and Datetime Functions]].

## The limits

Per synchronous transaction:

- **100 SOQL queries** (200 asynchronous)
- **50,000 rows retrieved** across all queries
- **6 MB heap** (12 MB asynchronous)

The row limit is cumulative across every query in the transaction, including queries in managed packages and flows. The heap limit is why selecting fewer fields matters — a query returning 50,000 rows with forty fields including long text areas will exhaust heap before it exhausts the row count.

For anything larger, use a `for` loop over the query, which processes in chunks of 200 rather than materializing everything:

```java
// Chunked: the platform retrieves 200 records at a time, keeping heap bounded
for (List<Warranty_Claim__c> chunk : [
    SELECT Id, Status__c FROM Warranty_Claim__c WHERE Status__c = 'Submitted'
]) {
    for (Warranty_Claim__c claim : chunk) {
        claim.Status__c = 'Under Review';
    }
    update chunk;
}
```

Beyond that, Batch Apex. See [[12.4 - Batch Apex]].

## Security

SOQL in Apex ignores sharing, object permissions, and field-level security by default.

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Approved_Amount__c
    FROM Warranty_Claim__c
    WHERE Status__c = 'Submitted'
    WITH USER_MODE
];
```

`WITH USER_MODE` enforces all three. Use it by default in anything a user can reach, and use `WITH SYSTEM_MODE` explicitly where elevated access is intended, so the intent is visible to a reviewer. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Where to run queries while developing

**Developer Console Query Editor** — quick, shows results in a grid, and includes the query plan.

**Salesforce CLI:**

```bash
sf data query --query "SELECT Id, Name FROM Account LIMIT 10" --target-org my-sandbox
sf data query --query "SELECT COUNT() FROM Case" --target-org production
```

**Workbench** and the REST API for exploratory work against an org you have credentials for.

Running a query against production data before writing code around it is worth the two minutes. Assumptions about data shape are wrong more often than assumptions about syntax.
