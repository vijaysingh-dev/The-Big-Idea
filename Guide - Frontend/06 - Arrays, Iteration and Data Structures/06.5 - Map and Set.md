# Map and Set

Two collection types that solve specific limitations of plain objects and arrays. Both are widely under-used in frontend code, usually because objects and arrays are the default habit.

## Map vs object

| | `Map` | Object |
| --- | --- | --- |
| Key types | any value | string or symbol only |
| Ordering | insertion order, always | integer-like keys first, then insertion |
| Size | `.size` | `Object.keys(o).length` — O(n) |
| Iteration | directly iterable | needs `Object.entries` |
| Prototype collisions | none | `toString`, `constructor`, `__proto__` |
| Frequent add/delete | optimized for it | deoptimizes the hidden class |
| JSON | not serializable directly | native |

```js
const map = new Map();

map.set("a", 1);
map.set(42, "number key");
map.set(someObject, "object key");
map.set(NaN, "works — SameValueZero");

map.get("a");        // 1
map.has(42);         // true
map.delete("a");
map.size;            // 3
map.clear();
```

**Object keys are always strings**, which silently loses type information:

```js
const obj = {};
obj[1] = "a";
obj["1"] = "b";     // same key
Object.keys(obj);   // ["1"]

const map = new Map();
map.set(1, "a");
map.set("1", "b");  // different keys
map.size;           // 2
```

This matters constantly when indexing by id — a numeric id in an object lookup comes back as a string key.

**Object keys collide with prototype properties:**

```js
const counts = {};
counts["toString"];      // a function, not undefined
counts["__proto__"] = 1; // may not do what you expect

const safe = new Map();
safe.get("toString");    // undefined
```

For user-supplied keys this is not just inconvenient — it is the prototype-pollution attack surface ([[15.6 - Frontend Security]]). `Map` or `Object.create(null)` are the correct choices.

## Iteration

```js
for (const [key, value] of map) {}
for (const key of map.keys()) {}
for (const value of map.values()) {}
map.forEach((value, key) => {});   // note the argument order

[...map];           // [[k, v], ...]
[...map.keys()];
Object.fromEntries(map);           // to a plain object
new Map(Object.entries(obj));      // from a plain object
```

Insertion order is guaranteed for `Map` in all cases, unlike objects where integer-like keys jump to the front ([[03.1 - Objects and Property Descriptors]]).

## Set

```js
const set = new Set([1, 2, 2, 3]);

set.add(4);
set.has(2);        // O(1)
set.delete(2);
set.size;          // 3

[...new Set(arr)]; // dedupe an array
```

Uniqueness uses **SameValueZero**, so `NaN` deduplicates correctly and `0`/`-0` are the same value:

```js
new Set([NaN, NaN]).size;  // 1
new Set([0, -0]).size;     // 1
```

Objects are compared by reference, so structurally identical objects are distinct members:

```js
new Set([{ a: 1 }, { a: 1 }]).size;  // 2
```

To dedupe objects by a field, index by that field instead:

```js
const unique = [...new Map(items.map(i => [i.id, i])).values()];
```

## Set operations

Recent additions give native set algebra:

```js
a.union(b);
a.intersection(b);
a.difference(b);
a.symmetricDifference(b);
a.isSubsetOf(b);
a.isSupersetOf(b);
a.isDisjointFrom(b);
```

Before these, the manual versions:

```js
const intersection = new Set([...a].filter(x => b.has(x)));
const difference = new Set([...a].filter(x => !b.has(x)));
const union = new Set([...a, ...b]);
```

Check browser support before relying on the native methods; the filter versions are still safe everywhere.

## Where a Set changes complexity

The highest-value use is turning repeated membership checks from O(n) to O(1):

```js
// O(n * m)
const selected = items.filter(i => selectedIds.includes(i.id));

// O(n + m)
const idSet = new Set(selectedIds);
const selected = items.filter(i => idSet.has(i.id));
```

With 5,000 items and 500 selected ids, that is 2.5 million comparisons versus 5,500 operations. Any `includes` or `indexOf` inside a loop should trigger this reflex ([[06.2 - find some every and includes]]).

## Serialization

Neither type survives `JSON.stringify`:

```js
JSON.stringify(new Map([["a", 1]]));  // "{}"
JSON.stringify(new Set([1, 2]));      // "{}"
```

Convert explicitly:

```js
JSON.stringify([...map]);
JSON.stringify([...set]);

new Map(JSON.parse(str));
new Set(JSON.parse(str));
```

`structuredClone` handles both correctly, which is one of its advantages over the JSON round-trip ([[03.5 - Shallow vs Deep Copy]]).

## Map and Set in React state

Both are mutable, and mutation does not change the reference — so React will not re-render:

```js
// Broken
setSelected(s => { s.add(id); return s; });

// Correct — new Set
setSelected(s => new Set(s).add(id));

// Removing
setSelected(s => {
  const next = new Set(s);
  next.delete(id);
  return next;
});
```

Copying a `Set` of a few thousand entries per update is cheap enough for UI purposes. For very large collections, an immutable library or a reducer holding a mutable ref is the alternative.

## Choosing

```
Keys are non-strings, or user-supplied?     -> Map
Frequent additions and deletions?           -> Map
Need size, ordering, or direct iteration?   -> Map
Fixed, known, string keys? Needs JSON?      -> object

Membership checks?                          -> Set
Deduplication?                              -> Set
Need indexing or order manipulation?        -> array
```

## How senior engineers actually use this

**They build a `Map` index before any join or repeated lookup.** This is the reflex described in [[06.3 - flat flatMap and Reshaping Data]], and `Map` is preferred over an object because ids keep their type.

**They use `Set` for selection state.** Selected row ids, expanded node ids, visited nodes in a traversal — all `Set`s, all O(1) checks during render.

**They use `Map` for caches with object keys**, and `WeakMap` when the keys are objects whose lifetime should not be extended by the cache ([[07.4 - WeakMap WeakSet and WeakRef]]).

**They keep plain objects for API payloads and config**, since those need JSON serialization and have fixed known keys.

## Common pitfalls

- Mutating a `Map` or `Set` in React state and getting no re-render.
- Expecting `JSON.stringify` to serialize them.
- Deduplicating objects with `Set` and getting no deduplication, because comparison is by reference.
- `map.forEach((value, key))` argument order — value first, unlike `Object.entries`.
- Using an object as a dictionary for user-supplied keys and hitting prototype collisions.
- Forgetting `.size` is a property, not a method.

## Interview angle

"When would you use a `Map` over an object" expects: non-string keys, guaranteed insertion order, O(1) size, direct iterability, no prototype collisions, and better performance under frequent insertion and deletion. The `Set` question is usually about deduplication and O(1) lookup. In coding rounds, reaching for a `Set` to avoid a nested loop is often the intended optimization.
