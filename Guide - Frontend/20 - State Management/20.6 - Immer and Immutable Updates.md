# Immer and Immutable Updates

Immer lets you write mutating code that produces an immutable result with correct structural sharing.

```js
import { produce } from "immer";

const next = produce(state, draft => {
  draft.user.address.city = "Delhi";
  draft.items.push(newItem);
  draft.items[0].done = true;
});
```

Compare with the manual equivalent:

```js
const next = {
  ...state,
  user: { ...state.user, address: { ...state.user.address, city: "Delhi" } },
  items: [{ ...state.items[0], done: true }, ...state.items.slice(1), newItem],
};
```

The Immer version is shorter, harder to get wrong, and produces the same result.

## How it works

`produce` wraps the base state in a `Proxy` ([[08.3 - Proxy and Reflect]]). Every read returns a proxy of the nested value; every write is recorded on a shallow copy of just that node.

When the recipe returns, Immer walks the recorded changes and builds the new state — copying only the nodes on the modified paths and **reusing every unchanged reference**.

```
state.user.address.city changed:

new: root'  →  user'  →  address'   (three new objects)
       ↓         ↓
    settings   profile               (same references — untouched)
```

That reference preservation is **structural sharing**, and it is what makes memoization work downstream: `settings` did not change, so a memoized component reading it does not re-render ([[19.2 - React.memo and Memoization Strategy]]).

Immer also copies lazily — a subtree that is only read, never written, is never copied at all.

## Where you already use it

**Redux Toolkit** wraps every `createSlice` reducer in `produce`:

```js
const slice = createSlice({
  name: "todos",
  initialState: { items: [] },
  reducers: {
    todoToggled(state, action) {
      const todo = state.items.find(t => t.id === action.payload);
      if (todo) todo.done = !todo.done;      // this is a draft
    },
  },
});
```

This is why RTK reducers look like they violate the immutability rule and do not ([[20.4 - Redux Toolkit]]).

**Zustand** offers it as middleware:

```js
import { immer } from "zustand/middleware/immer";

const useStore = create(immer((set) => ({
  items: [],
  toggle: (id) => set(state => {
    const item = state.items.find(i => i.id === id);
    if (item) item.done = !item.done;
  }),
})));
```

**useImmer** for component state:

```jsx
import { useImmer } from "use-immer";

const [form, updateForm] = useImmer({ user: { name: "", address: {} } });

updateForm(draft => { draft.user.address.city = "Delhi"; });
```

## The rules

**Either mutate the draft or return a new value — never both:**

```js
// Throws
produce(state, draft => {
  draft.count++;
  return { ...draft, count: 0 };
});

// Fine
produce(state, draft => { draft.count++; });
produce(state, () => ({ count: 0 }));
```

**Do not use the draft asynchronously or store it.** Immer revokes the proxy when `produce` returns, so any later access throws.

```js
produce(state, draft => {
  setTimeout(() => draft.x = 1, 0);   // throws — revoked proxy
});
```

**Returning `undefined` means "no change"** — which is why an arrow with a block body and no explicit return works correctly, but `draft => draft.items.push(x)` does not. The concise arrow returns `push`'s return value (a number), which Immer interprets as the new state.

```js
// Wrong — returns the new array length
produce(state, draft => draft.items.push(x));

// Right
produce(state, draft => { draft.items.push(x); });
```

This is a genuinely common bug, and RTK's ESLint setup does not always catch it.

## Curried produce

```js
const toggle = produce((draft, id) => {
  const item = draft.items.find(i => i.id === id);
  if (item) item.done = !item.done;
});

const next = toggle(state, 5);
```

Omitting the base state returns a function taking `(state, ...args)`. This is exactly what RTK uses internally to wrap reducers.

## Patches

```js
import { produceWithPatches, applyPatches } from "immer";

const [next, patches, inversePatches] = produceWithPatches(state, draft => {
  draft.items.push(newItem);
});

const undone = applyPatches(next, inversePatches);
```

Immer can record what changed as JSON Patch operations, which gives you undo/redo, optimistic updates with precise rollback, and a diff to send over the wire for collaborative editing.

Enable with `enablePatches()`. This is a genuinely useful capability that most people using Immer never discover.

## Maps, Sets and classes

```js
import { enableMapSet } from "immer";
enableMapSet();
```

Required for drafting `Map` and `Set` ([[06.5 - Map and Set]]).

Class instances need an explicit marker:

```js
import { immerable } from "immer";

class Todo {
  [immerable] = true;
  done = false;
}
```

Without it, Immer treats the instance as an atomic value and does not draft it.

## Costs

**Bundle size** — roughly 5KB gzipped. Already included if you use RTK.

**Runtime** — proxy interception is slower than direct property access ([[08.3 - Proxy and Reflect]]). For typical UI state (hundreds to low thousands of nodes) it is immaterial. For very large state trees updated at high frequency, measure.

Immer includes an optimization worth knowing: if nothing in the recipe actually changes, it returns the **original state object**, so a no-op update does not trigger a re-render.

**Debugging** — drafts appear as proxies in the debugger, which obscures values. `current(draft)` produces a plain snapshot:

```js
console.log(current(draft));
```

Use `original(draft)` for the pre-modification state.

## When not to use it

**Shallow updates.** `{ ...state, count: state.count + 1 }` is clearer and faster than a `produce` call.

**Very large state with frequent writes.** Proxy overhead becomes measurable.

**When flattening the state would solve it.** Deep nesting is often the real problem. Normalizing entity data removes most deep-update cases entirely ([[20.7 - State Normalization]]):

```js
// Deeply nested — needs Immer
{ users: [{ id, posts: [{ id, comments: [...] }] }] }

// Normalized — every update is one level deep
{ users: { byId }, posts: { byId }, comments: { byId } }
```

Immer is a good answer to "updates are verbose". It is not a good answer to "our state shape is wrong".

## How senior engineers actually use this

**They use it wherever RTK already includes it**, without a second thought.

**They add `useImmer` for deeply nested form or editor state**, where manual spreading becomes error-prone.

**They still prefer plain spreads for shallow updates**, because a `produce` call for a one-level change is noise.

**They reach for normalization first** when Immer is being used to paper over deep nesting.

**They know about patches** for undo/redo, which is otherwise a substantial thing to build.

## Common pitfalls

- Mutating the draft *and* returning a value.
- A concise arrow returning `push`'s result as the new state.
- Using a draft asynchronously after `produce` has returned.
- Forgetting `enableMapSet()` for `Map`/`Set`.
- Class instances without `[immerable]`.
- Confusing draft proxies in the debugger — use `current()`.
- Using Immer to avoid fixing a badly shaped state tree.

## Interview angle

"What is Immer and how does it work" expects: a library using Proxies to record writes to a draft and produce an immutable result with structural sharing. The important connection is *why* structural sharing matters — unchanged subtrees keep their references, so memoized components do not re-render, which a deep clone would destroy. Adding that RTK includes it by default, which is why RTK reducers look mutating, ties it to everyday practice.
