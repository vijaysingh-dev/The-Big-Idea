# Event Driven Architecture on Salesforce

## The shift

**Direct invocation:** the caller knows every consequence.

```java
public static void approve(Set<Id> claimIds) {
    updateClaims(claimIds);
    PaymentService.createPayments(claimIds);
    ErpNotificationService.enqueue(claimIds);
    SlackNotificationService.post(claimIds);
    AuditService.record(claimIds);
}
```

Adding a sixth consequence means editing this method, retesting it, and redeploying it.

**Event driven:** the caller announces what happened.

```java
public static void approve(Set<Id> claimIds) {
    updateClaims(claimIds);

    // the publisher does not know or care who is listening
    EventBus.publish(buildApprovalEvents(claimIds));
}
```

Adding a sixth consumer means a new subscriber. The publisher does not change, is not retested, and is not redeployed.

## When the decoupling is worth it

**Several independent consumers**, particularly ones added over time.

**Consumers owned by different teams**, so a change to one does not require coordinating with the publisher's team.

**Callouts after DML** — the subscriber runs in its own transaction where a callout is permitted.

**External systems reacting**, through Pub/Sub API or Event Relay, without polling.

**Logging that survives rollback**, using immediate publish behaviour.

**Serializing contended work** — publishing from many transactions and processing in one subscriber removes lock contention.

## When it is not

**One consumer, in the same org, with no callout.** A direct method call is simpler, synchronous, traceable in the code, and testable without event delivery.

**When the caller needs the result.** Publishing gives no response.

**When order matters strictly.** Delivery order is not guaranteed across publish calls.

**When it must happen exactly once.** Delivery is at-least-once, so subscribers must be idempotent regardless.

The honest position: **events are indirection, and indirection has a cost.** A codebase where every service call became an event is harder to reason about, not easier.

## Business events, not data changes

The design decision that determines whether the architecture is useful.

```java
// A data change — the subscriber has to infer what happened
new Claim_Changed__e(
    Claim_Id__c = claim.Id,
    Changed_Fields__c = 'Status__c,Approved_Amount__c'
);

// A business event — the meaning is in the payload
new Claim_Approved__e(
    Claim_Id__c = claim.Id,
    Claim_Number__c = claim.Claim_Number__c,
    Approved_Amount__c = claim.Approved_Amount__c,
    Approved_By__c = UserInfo.getUserId(),
    Approved_At__c = Datetime.now()
);
```

A subscriber to `Claim_Changed__e` has to re-derive the business meaning from a field list. A subscriber to `Claim_Approved__e` knows immediately.

**This is the difference between platform events and Change Data Capture.** CDC publishes data changes automatically; platform events express intent. Both have their place, and using CDC where a business event was needed pushes interpretation onto every subscriber. See [[12.9 - Change Data Capture]].

## Payload design

**Send an Id and the minimum context; let the subscriber fetch what it needs.**

```java
// Bloated, and stale by the time it is processed
new Claim_Approved__e(
    Claim_Id__c = claim.Id,
    Full_Payload__c = JSON.serialize(claim)
);

// Enough to decide whether to act, and to fetch the rest
new Claim_Approved__e(
    Claim_Id__c = claim.Id,
    Claim_Number__c = claim.Claim_Number__c,
    Approved_Amount__c = claim.Approved_Amount__c,
    Correlation_Id__c = correlationId
);
```

Two reasons: the payload is a snapshot from publish time and may be stale, and the delivery allocation counts every event to every subscriber.

**Include a correlation Id.** It is what lets a business operation be traced across the publishing transaction, the subscriber's transaction, and the external system's logs. See [[13.17 - Error Handling, Retries and Idempotency]].

**Include enough for a subscriber to filter** without querying. A subscriber that only cares about claims over 500,000 should be able to decide from the payload.

## Idempotent subscribers

Non-negotiable, because delivery is at-least-once.

```java
public with sharing class ClaimApprovedHandler {

    public static void handle(List<Claim_Approved__e> events) {
        Map<String, Claim_Approved__e> byKey = new Map<String, Claim_Approved__e>();

        for (Claim_Approved__e event : events) {
            // a composite key means a redelivery updates the same row rather than adding one
            byKey.put(event.Claim_Id__c + '|' + event.Approved_At__c.getTime(), event);
        }

        List<Payment_Instruction__c> instructions = new List<Payment_Instruction__c>();
        for (String key : byKey.keySet()) {
            instructions.add(new Payment_Instruction__c(
                Event_Key__c = key,
                Claim__c = byKey.get(key).Claim_Id__c,
                Amount__c = byKey.get(key).Approved_Amount__c
            ));
        }

        Database.upsert(instructions, Payment_Instruction__c.Event_Key__c, false);
    }
}
```

An upsert on a unique external key is the standard mechanism. Without it, a redelivered event produces a duplicate payment — the failure mode that is discovered by finance rather than by testing. See [[12.8 - Platform Events]].

## The publish behaviour choice

```
Publish After Commit    delivered only if the transaction commits — business events
Publish Immediately     delivered even if the transaction rolls back — logging
```

**After Commit for business events.** A claim-approved event should not fire if the approval was rolled back.

**Immediately for failure logging**, which is the one place this behaviour is essential:

```java
try {
    processClaims(claims);
} catch (Exception e) {
    // published immediately, so it survives the rollback that follows
    EventBus.publish(new Automation_Error__e(
        Context__c = 'ClaimProcessing',
        Message__c = e.getMessage(),
        Stack_Trace__c = e.getStackTraceString()
    ));
    throw e;
}
```

That is why platform events are the recommended logging mechanism throughout this course for synchronous code, and Transaction Finalizers for async. See [[20.5 - Custom Logging Frameworks]].

## Orchestration versus choreography

The architectural fork worth understanding.

**Orchestration** — one component directs the process.

```java
public with sharing class ClaimApprovalOrchestrator {

    public static void approve(Set<Id> claimIds) {
        ClaimService.markApproved(claimIds);
        PaymentService.createInstructions(claimIds);
        ErpNotificationService.enqueue(claimIds);
        AuditService.record(claimIds);
    }
}
```

*Strengths:* the whole process is readable in one place, ordering is explicit, and failure handling is centralized.
*Weaknesses:* the orchestrator knows every participant, and adding one means changing it.

**Choreography** — each component reacts independently.

```
ClaimService publishes Claim_Approved__e
    ↓
PaymentSubscriber creates the instruction
ErpSubscriber notifies the ERP
AuditSubscriber records the decision
```

*Strengths:* participants are independent, adding one changes nothing existing.
*Weaknesses:* **no single place shows the process.** Understanding what happens on approval means finding every subscriber.

**Most real systems need both.** Orchestrate the core transaction — the part that must be atomic and ordered — and choreograph the peripheral reactions.

```java
public static void approve(Set<Id> claimIds) {
    // orchestrated: must happen, must be atomic, must be ordered
    ClaimService.markApproved(claimIds);
    PaymentService.createInstructions(claimIds);

    // choreographed: independent reactions, added and removed freely
    EventBus.publish(buildApprovalEvents(claimIds));
}
```

That split is the practical answer, and it avoids both the rigid orchestrator and the untraceable event soup.

## The traceability problem

The genuine cost of choreography, and it deserves naming.

**"What happens when a claim is approved?"** has no answer from the publisher's code. Answering it means finding every subscriber:

```bash
grep -rl "Claim_Approved__e" force-app/main/default/
```

```sql
SELECT ApiName, Label, TriggerType
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerType = 'PlatformEvent'
```

**Mitigations worth adopting:**

**Document the event's consumers** in the event definition's description field, and keep it current.

**Use a correlation Id** so a single operation can be traced across logs.

**Keep an event catalogue** — a document or a Custom Metadata registry listing each event, its publisher, and its known subscribers.

Without one of these, an event-driven org becomes one nobody can reason about after eighteen months.

## Failure handling

A subscriber that throws is retried a limited number of times, then the event is **discarded**.

```java
public static void handle(List<Claim_Approved__e> events) {
    EventBus.TriggerContext context = EventBus.TriggerContext.currentContext();

    for (Claim_Approved__e event : events) {
        try {
            process(event);
        } catch (Exception e) {
            if (context.retries < 3) {
                // resume from here rather than reprocessing the whole batch
                context.setResumeCheckpoint(event.ReplayId);
                throw e;
            }
            // record it durably, because the event is about to be lost
            logPermanentFailure(event, e);
        }
    }
}
```

**Without `setResumeCheckpoint`, a retry reprocesses the entire batch** — including the events that succeeded, which for a non-idempotent handler produces duplicates.

**After the retry limit the event is gone.** Anything that must not be lost has to be recorded before giving up. See [[16.5 - Platform Event and Streaming Limits]].

## Events across the boundary

Where the architecture pays off most.

**Outbound:** an external system subscribes through Pub/Sub API or Event Relay, reacting without polling and without an API call per check.

**Inbound:** an external system publishes a platform event into Salesforce, which a trigger or flow subscribes to — asynchronous, decoupled, and it does not consume the daily API allocation the way per-record REST calls do.

```java
trigger ErpUpdateTrigger on Erp_Update__e (after insert) {
    ErpUpdateHandler.handle(Trigger.new);
}
```

That inbound pattern is genuinely good architecture: no synchronous coupling, no endpoint to build, and Salesforce processes at its own pace. See [[13.9 - Pub-Sub API and Event Relay]].

## Testing

```java
@IsTest
static void approvalPublishesAnEventAndTheSubscriberActs() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 150000);

    // events do not deliver until this is called
    Test.getEventBus().deliver();
    Test.stopTest();

    Integer instructions = [SELECT COUNT() FROM Payment_Instruction__c];
    Assert.areEqual(1, instructions, 'The subscriber should have created an instruction');
}
```

**`Test.getEventBus().deliver()` is required**, and omitting it produces a passing test that proves nothing about the subscriber.

**Test idempotency explicitly**, since it is the property most likely to be wrong:

```java
@IsTest
static void redeliveryDoesNotDuplicate() {
    Test.startTest();
    EventBus.publish(buildApprovalEvent('a0X123'));
    Test.getEventBus().deliver();

    // the same event again, simulating at-least-once redelivery
    EventBus.publish(buildApprovalEvent('a0X123'));
    Test.getEventBus().deliver();
    Test.stopTest();

    Assert.areEqual(1, [SELECT COUNT() FROM Payment_Instruction__c],
        'A redelivered event must not create a second instruction');
}
```

## A design checklist

```
[ ] Is the event a business fact, not a field diff?
[ ] Does the payload carry an Id and just enough context to filter?
[ ] Is there a correlation Id?
[ ] Is every subscriber idempotent?
[ ] Is the publish behaviour chosen deliberately?
[ ] Does the subscriber use setResumeCheckpoint?
[ ] Is there a path for permanently failed events?
[ ] Are the consumers documented somewhere findable?
[ ] Would a direct call have been simpler?
```

The last line is the one worth asking first.

## Practical guidance

**Publish business events, not data changes.**

**Send an Id and minimal context**, with a correlation Id.

**Make every subscriber idempotent** — at-least-once is a certainty.

**Choose the publish behaviour deliberately** — After Commit for business, Immediately for logging.

**Orchestrate the atomic core, choreograph the periphery.**

**Document the consumers**, or the process becomes untraceable.

**Use `setResumeCheckpoint`** and record permanently failed events.

**Call `Test.getEventBus().deliver()`**, and test redelivery.

**Use a direct call when there is one consumer.**
