# Partitioning and Sharding

#backend #databases #postgres #scaling

> **In one line:** Partitioning splits one table across many within a single database and is mostly an operational win; sharding splits data across many databases and costs you joins, transactions and most of your simplicity.

---

## The Idea

| | Partitioning | Sharding |
|---|---|---|
| Splits across | Tables in one database | **Separate databases** |
| Transparent to queries | Yes | No — needs routing |
| Cross-partition joins | Yes | **No** |
| Cross-partition transactions | Yes | **No** |
| Solves | Maintenance, retention, some query speed | Write throughput, total size |
| Complexity added | Low | **Very high** |

💡 **Partitioning is a maintenance tool that sometimes helps performance. Sharding is a scaling tool that costs you the relational model.** They are not points on the same spectrum, and reaching for sharding when partitioning would do is one of the more expensive architectural mistakes available.

---

## Partitioning

```sql
CREATE TABLE events (
    id          uuid NOT NULL DEFAULT uuidv7(),
    org_id      uuid NOT NULL,
    created_at  timestamptz NOT NULL,
    payload     jsonb NOT NULL,
    PRIMARY KEY (id, created_at)          -- ⚠️ must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
```

⚠️ **Every unique constraint must include the partition key.** Postgres cannot enforce global uniqueness across partitions, so a plain `PRIMARY KEY (id)` is impossible. **This is the constraint that most often forces a schema redesign.**

| Strategy | Use for |
|---|---|
| `RANGE` | Time-series, sequential IDs. **The common case** |
| `LIST` | Explicit value sets — region, tenant tier |
| `HASH` | Even distribution when there is no natural range |

### What partitioning actually buys you

**1. Dropping data is instant.**

```sql
DROP TABLE events_2025_08;              -- instant, zero bloat
DELETE FROM events WHERE created_at < '2025-09-01';   -- hours, massive bloat
```

💡 **This is the strongest argument for partitioning and it is operational, not performance.** A `DELETE` of 100 million rows creates 100 million dead tuples vacuum must clean ([[06.7 - MVCC Vacuum and Bloat]]); dropping a partition is a file unlink.

**Any table with a retention policy should be partitioned by time.**

**2. Maintenance operates per partition.** Vacuum, analyse, reindex and backup work on one partition at a time.

**3. Partition pruning skips irrelevant data.**

```sql
EXPLAIN SELECT * FROM events WHERE created_at >= '2026-08-01';
-- Append → Seq Scan on events_2026_08     ← only one partition touched
```

⚠️ **Pruning only works if the query filters on the partition key**, and the planner must prove it at plan time or execution time.

```sql
WHERE created_at > now() - interval '7 days'    -- runtime pruning, works
WHERE date(created_at) = '2026-08-17'           -- ❌ function defeats pruning
WHERE org_id = 7                                 -- ❌ not the partition key
```

**4. Smaller indexes per partition** — the *active* partition's index is small enough to stay in memory.

### What it costs

| Cost | |
|---|---|
| Planning time grows with partition count | Noticeable above ~100 |
| Queries not filtering the key scan everything | **Worse than an unpartitioned table** |
| Unique constraints must include the key | Often forces schema changes |
| Partition management | Must create future partitions before they are needed |

⚠️ **Forgetting to create next month's partition means inserts fail.**

```sql
CREATE TABLE events_default PARTITION OF events DEFAULT;   -- safety net
```

**A default partition catches rows that fit nowhere. It is a safety net, not a solution** — rows landing there defeat pruning.

💡 **Use `pg_partman` rather than writing partition management yourself.** It handles pre-creation, retention, and detaching on a schedule. **This is solved infrastructure.**

### Attaching and detaching

```sql
ALTER TABLE events DETACH PARTITION events_2025_08 CONCURRENTLY;   -- PG 14+

ALTER TABLE events_2026_09 ADD CONSTRAINT ck_range
    CHECK (created_at >= '2026-09-01' AND created_at < '2026-10-01');
ALTER TABLE events ATTACH PARTITION events_2026_09
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

⚠️ **Without the pre-existing `CHECK`, `ATTACH` scans the whole table** to verify every row belongs, holding a lock throughout.

## Sharding

**Everything gets harder.**

### Choosing a shard key

| Property | Why it matters |
|---|---|
| **High cardinality** | Few values means few shards can be used |
| **Even distribution** | One giant tenant on one shard defeats the point |
| **Present in most queries** | A query without it must hit every shard |
| **Stable** | Changing it means moving the row between databases |

💡 **For a multi-tenant SaaS, `org_id` is almost always the right shard key**, because virtually every query is already scoped to one tenant. **That is also why the "denormalise `org_id` onto every table" advice from [[06.10 - Schema Design]] matters so much — it makes sharding possible later.**

⚠️ **A hot tenant breaks even a good shard key.** One customer with 40% of your data means one shard with 40% of the load. **Real systems need per-tenant placement overrides, not just a hash.**

### What you lose

| Lost | Replacement |
|---|---|
| Cross-shard joins | Denormalise, or join in the application |
| Cross-shard transactions | Sagas ([[10.5 - Distributed Transactions and Sagas]]) |
| Global uniqueness | UUIDs, or a central sequence service |
| Global aggregates | Scatter-gather, or a separate analytics store |
| **Global sorted pagination** | Fetch N from each shard and merge |

⚠️ **Scatter-gather pagination is `O(shards × limit)`.** Deep pagination across shards becomes untenable quickly — page 100 requires fetching 2,000 rows from each shard.

### Resharding

```
4 shards → 8 shards. With hash(key) % 4, EVERY key's shard changes.
```

**Consistent hashing** limits the movement to roughly `1/n` of keys.

💡 **The better trick is to over-shard from the start:** create 1,024 *logical* shards, map them to 4 *physical* databases. **Growing to 8 databases means moving 512 logical shards, with no rehashing at all.**

```python
logical = hash(org_id) % 1024
physical = SHARD_MAP[logical]      # a lookup table you can change
```

**This is what Vitess, Citus and most large sharded systems do**, and deciding it at design time costs nothing while retrofitting it costs a migration.

### The tools

| Tool | Approach |
|---|---|
| **Citus** | Postgres extension. Distributed tables, cross-shard queries, mostly transparent |
| Vitess | MySQL sharding, used by YouTube and Slack |
| Application-level | You route. Maximum control, maximum work |
| CockroachDB / Yugabyte | Distributed SQL — sharding built into the database |

💡 **Citus is the right first answer for Postgres**, because it keeps you in the relational model. The cost is a constrained subset of SQL and an operational dependency.

## In Production

### Do not shard yet

⚠️ **Sharding is usually premature.** In order, exhaust these first:

```
1. Fix the queries         (indexes, N+1, plans — sections 06.3–06.5)
2. Add read replicas        (if read-bound)
3. Vertical scaling         (a 64-core, 512GB machine is not exotic)
4. Partition                (retention, maintenance, pruning)
5. Move cold data out       (archive to object storage)
6. Split by domain          (separate databases per service, not per shard)
7. Only then: shard
```

💡 **A single well-tuned Postgres instance on modern hardware handles tens of thousands of writes per second and tens of terabytes.** Most systems that believe they need sharding have an unindexed query, a hot row, or a missing partition strategy.

**Step 6 is the underrated one.** Splitting `documents` and `billing` into separate databases is far simpler than sharding either, and it often provides all the relief needed.

### When sharding is genuinely right

| Signal | |
|---|---|
| Write throughput exceeds one machine | Even after tuning |
| Dataset beyond ~30–50TB | |
| **Regulatory data residency** | **EU data must live in the EU** |
| Tenant isolation is a product requirement | Blast radius per tenant |
| Vertical scaling has genuinely run out | |

**Regulatory residency is not negotiable, and it is a legitimate reason to shard before you need to for scale.**

### Partition maintenance automation

```sql
CREATE EXTENSION pg_partman;
SELECT partman.create_parent('public.events', 'created_at', '1 month', p_premake => 3);
UPDATE partman.part_config SET retention = '12 months', retention_keep_table = false
WHERE parent_table = 'public.events';
```

⚠️ **Monitor that future partitions exist.** A silent failure of the maintenance job means inserts start failing on the first of the month, at midnight, when nobody is watching.

### Watching for pruning

```
"Subplans Removed: 22"       ← runtime pruning worked
Append with 24 children       ← no pruning: every partition scanned
```

💡 **Add a test that asserts partition pruning happens for your main query patterns.** A query that silently stops pruning — because someone wrapped the partition key in a function — degrades from scanning one partition to scanning all of them, **and the only symptom is gradual slowness.**

### Monitoring a sharded system

```python
shard_query_duration.labels(shard=...).observe(elapsed)
shard_size_bytes.labels(shard=...).set(size)
cross_shard_queries_total.inc()
scatter_gather_fanout.observe(shards_touched)
```

⚠️ **`cross_shard_queries_total` rising means your shard key is wrong for your access patterns.** If most queries touch multiple shards, **you have all the costs of sharding and none of the benefits** — and the fix is a different shard key, which means a full data migration.

**Track shard size skew.** A shard 3× larger than the median will become your bottleneck.

## Codebase

**Repo:** `citusdata/citus`, `pgpartman/pg_partman`, `postgres/postgres`

**Question to answer:** How does Citus decide whether a query can be pushed down to a single shard versus requiring a distributed plan? Then: in Postgres, where does partition pruning happen, and what is the difference between plan-time and runtime pruning?

**Read, in order:**

1. `postgres/src/backend/partitioning/partprune.c` — **partition pruning.** `prune_append_rel_partitions` for plan-time, and the execution-time path. **Plan-time uses constants; runtime uses parameter values available only at execution**
2. `postgres/src/backend/executor/nodeAppend.c` — where `Subplans Removed` comes from
3. `citus/src/backend/distributed/planner/distributed_planner.c` — **the routing decision.** Citus first tries a "router" plan (single shard); if that fails, it builds a distributed plan
4. `citus/src/backend/distributed/planner/multi_router_planner.c` — **how it proves a query touches exactly one shard**
5. `pg_partman/sql/functions/` — the partition creation and retention logic. Straightforward SQL, and it tells you exactly what maintenance a partitioned table needs

💡 The Citus router planner is the interesting read: **it tries hard to prove a query is single-shard, because a router query is dramatically cheaper than a distributed one.** Seeing what it can and cannot prove **tells you precisely how to write queries that shard well** — and that transfers to any sharded system.

**Size:** 2 sessions.

## Exercise

**Drill 6.13 — Partition a billion rows, then decide not to shard**

```
drills/06-partitioning/
├── partitioning/{setup.sql, pruning.sql, retention.py, maintenance.py, RESULTS.md}
├── limits/{partition_count.py, no_prune.py}
├── sharding/{router.py, scatter_gather.py, logical_shards.py, rebalance.py, RESULTS.md}
├── citus/{setup.sql, pushdown.sql, FINDINGS.md}
└── decision/ADR.md
```

**Part 1 — Partitioned versus monolithic.** 500 million rows of time-series events, both ways.

Compare: a time-range query, a query without the partition key, insert throughput, index size, `VACUUM` duration, and `ANALYZE` duration.

**The query without the partition key should be *slower* on the partitioned version.** That is the tradeoff, and measuring it prevents you from believing partitioning is free.

**Part 2 — Retention, the real argument.** Delete one month (~40 million rows) both ways.

Measure duration, WAL generated, dead tuples created, bloat afterwards, and vacuum time to recover.

**`DROP TABLE` should be effectively instant with zero bloat. Put the two numbers side by side — this single comparison justifies partitioning for any table with retention.**

**Part 3 — What prunes.** Ten query shapes:

| Query | Prunes? |
|---|---|
| `WHERE created_at > '2026-08-01'` | |
| `WHERE created_at > now() - interval '7 days'` | |
| `WHERE date(created_at) = '2026-08-17'` | |
| `WHERE created_at = $1` (parameter) | |
| `WHERE org_id = 7` | |
| Join on `created_at` | |
| `ORDER BY created_at LIMIT 20` | |
| `WHERE created_at IN (...)` | |
| A prepared statement with a generic plan | |
| `WHERE created_at > (SELECT max(...) ...)` | |

Record `Subplans Removed` or the number of Append children scanned for each.

**Then write the test that asserts pruning for your critical queries**, so a regression is caught in CI rather than in production.

**Part 4 — The partition count wall.** Sweep partition count: 12, 50, 100, 500, 1000, 5000.

Chart planning time and execution time for a pruning query and a non-pruning one. **Find the point where planning time becomes significant** — the practical upper bound on partition granularity.

**Part 5 — Application-level sharding.** Four Postgres instances, a router keyed on `org_id`, and a logical-shard mapping layer.

Implement single-shard queries, scatter-gather aggregates, cross-shard pagination, and a cross-shard "transaction" via a saga.

Measure single-shard versus scatter-gather latency, and pagination cost at page 1 versus page 50.

**Then measure how much application code this required compared to the monolithic version. That line count is a real part of the cost.**

**Part 6 — Rebalancing.** Grow from 4 to 8 physical shards.

Version A: `hash % N`. Version B: 1,024 logical shards remapped.

**A should move roughly 50% of your data; B should move roughly 50% of *logical shards* with no rehashing.** Implement the actual move for one shard and time it.

**Part 7 — Citus.** The same workload with `org_id` as the distribution column.

Test which queries push down to a single node and which require a distributed plan. **Then deliberately write a query that does not push down and measure the difference.**

**Part 8 — The ADR.** For Conduit, decide: partition, shard, or neither.

**Work through the seven-step ladder, and for each step state what you measured and whether it was sufficient.**

**The correct answer for Conduit is almost certainly "partition `events` and `documents` by time, do not shard".** Argue it with numbers, and state the specific signal that would change your mind.

**Done when:**
- Your partitioned-versus-monolithic table shows both the wins and the losses
- The DROP-versus-DELETE comparison is measured, including bloat
- Your ten-query pruning table is complete, with a CI test for the critical ones
- You know the partition count at which planning time becomes a problem
- Your sharded implementation handles scatter-gather and cross-shard pagination
- Logical shards demonstrably reduce rebalancing work
- The ADR reaches a conclusion via the ladder, with measurements at each step
