# Streaming API and PushTopics

## What it is

The Streaming API pushes notifications to subscribers over a long-lived connection, using the **CometD** protocol — HTTP long-polling with a Bayeux message layer.

It is the older of the two streaming mechanisms. **Pub/Sub API is the current one** for external subscribers, and this note exists because Streaming API is still in wide use and still the right tool inside a Lightning component. See [[13.9 - Pub-Sub API and Event Relay]].

## The channels

Everything streams over a channel, and the prefix tells you what it is:

```
/topic/ClaimUpdates              PushTopic — record changes matching a SOQL query
/event/Claim_Approved__e         Platform event
/data/Warranty_Claim__ChangeEvent   Change Data Capture
/data/ChangeEvents               all CDC events for the org
/systemTopic/Logging             system events
```

## PushTopics

A PushTopic defines a SOQL query; changes to records matching it produce notifications.

```java
PushTopic topic = new PushTopic();
topic.Name = 'ClaimUpdates';
topic.Query = 'SELECT Id, Claim_Number__c, Status__c, Claim_Amount__c '
            + 'FROM Warranty_Claim__c WHERE Status__c != \'Closed\'';
topic.ApiVersion = 62.0;
topic.NotifyForOperationCreate = true;
topic.NotifyForOperationUpdate = true;
topic.NotifyForOperationDelete = false;
topic.NotifyForOperationUndelete = false;
topic.NotifyForFields = 'Referenced';
insert topic;
```

`NotifyForFields` controls when a change fires a notification:

- **`All`** — any field change on the record
- **`Referenced`** — a change to any field in the SELECT or WHERE clause (the default, and usually right)
- **`Select`** — only fields in the SELECT
- **`Where`** — only fields in the WHERE

`Referenced` is the sensible default: a notification fires when something the subscriber cares about changes, and not when an unrelated field is edited.

## The constraints that make PushTopics legacy

**Only one object per topic**, with no relationship traversal beyond one level.

**Query complexity is heavily restricted.** No aggregate functions, no semi-joins, limited WHERE clauses.

**The record Id must be in the SELECT.**

**Notifications carry only the queried fields**, not the whole record.

**Retention is 24 hours**, shorter than platform events and CDC.

**No replay guarantees comparable to CDC**, though replay is supported.

For anything beyond a simple "tell me when a record in this filter changes", **Change Data Capture or a platform event is the better mechanism** — CDC because it is automatic and complete, platform events because they carry business meaning rather than a field diff. See [[12.8 - Platform Events]] and [[12.9 - Change Data Capture]].

## Generic streaming

A channel for arbitrary messages, unconnected to records:

```java
StreamingChannel channel = new StreamingChannel();
channel.Name = '/u/SystemAlerts';
channel.Description = 'Operational alerts to console users';
insert channel;
```

Publishing to it is a REST call:

```
POST /services/data/v62.0/sobjects/StreamingChannel/{channelId}/push
```

```json
{
  "pushEvents": [
    { "payload": "ERP sync degraded — claims may be delayed", "userIds": [] }
  ]
}
```

An empty `userIds` broadcasts to every subscriber; populating it targets specific users.

Generic streaming has largely been superseded by platform events, which are typed, monitorable, and have proper retention. It survives for simple broadcast notifications where defining an event object is more ceremony than the requirement deserves.

## Subscribing from a Lightning component

**This is where Streaming API remains the right tool.** The `empApi` module is the supported way for a component to react to server-side events in real time, and it uses CometD underneath.

```javascript
import { LightningElement } from 'lwc';
import { subscribe, unsubscribe, onError, setDebugFlag } from 'lightning/empApi';

export default class ClaimMonitor extends LightningElement {
    subscription = {};
    channelName = '/event/Claim_Approved__e';
    approvals = [];

    connectedCallback() {
        this.registerErrorListener();

        // -1 means new events only; -2 replays everything retained
        subscribe(this.channelName, -1, (message) => {
            this.handleApproval(message.data.payload);
        }).then((response) => {
            this.subscription = response;
        });
    }

    disconnectedCallback() {
        // unsubscribing on teardown prevents orphaned connections accumulating
        unsubscribe(this.subscription, () => {});
    }

    handleApproval(payload) {
        this.approvals = [
            {
                id: payload.Claim_Id__c,
                number: payload.Claim_Number__c,
                amount: payload.Approved_Amount__c
            },
            ...this.approvals
        ].slice(0, 20);
    }

    registerErrorListener() {
        onError((error) => {
            console.error('Streaming error', JSON.stringify(error));
        });
    }
}
```

The `disconnectedCallback` unsubscribe matters. A component navigated away from without unsubscribing leaves a subscription open, and a console user opening many tabs accumulates them until the concurrent-client limit is hit.

## Replay

Every event carries a `replayId`, and a subscriber can resume from a specific one.

```javascript
subscribe(this.channelName, replayId, callback);
```

```
-1    new events only, from the moment of subscription
-2    everything currently retained
 n    resume from just after replay Id n
```

Storing the last processed `replayId` durably is what makes a subscriber recoverable after an outage. Without it, a disconnection means a gap.

**Retention is 24 hours for PushTopics and generic streaming, 72 hours for platform events and CDC.** A subscriber down longer than the retention window has lost events permanently and needs a reconciliation pass.

## Subscribing from an external system

The CometD client pattern, in outline:

```javascript
const cometd = new CometD();

cometd.configure({
    url: `${instanceUrl}/cometd/62.0/`,
    requestHeaders: { Authorization: `Bearer ${accessToken}` },
    appendMessageTypeToURL: false
});

cometd.handshake((handshakeReply) => {
    if (handshakeReply.successful) {
        cometd.subscribe('/event/Claim_Approved__e', (message) => {
            processEvent(message.data.payload, message.data.event.replayId);
        });
    }
});
```

The extension for replay support is registered before handshake and supplies the replay Id per channel.

**For a new external subscriber, use Pub/Sub API instead.** It is gRPC-based, more efficient, has proper flow control, and is the mechanism Salesforce is investing in. CometD remains supported and is what you will find in existing integrations. See [[13.9 - Pub-Sub API and Event Relay]].

## Limits

- **Concurrent clients** per org, based on edition — typically 1,000 to 2,000
- **Daily delivery allocation**, counted per subscriber
- **Events per channel** capped per rolling period
- **Retention** as above
- **Maximum subscribers per channel**

The concurrent client limit is the one that bites in a console-heavy Service Cloud org. Every open browser tab with a subscribing component is a client, and agents with several tabs each consume the allocation quickly.

That is a real design constraint: a streaming component on a record page, in a console where agents open dozens of tabs, multiplies faster than expected.

## Debugging

Streaming problems are awkward because the failure is usually a missing message rather than an error.

**`setDebugFlag(true)`** in `empApi` logs the CometD handshake and message traffic to the browser console.

**Check the subscription succeeded**, not just that `subscribe` was called:

```javascript
subscribe(channel, -1, callback).then((response) => {
    console.log('Subscribed to', response.channel, 'with id', response.id);
});
```

**`EventBusSubscriber`** shows subscriber position and lag for platform events and CDC:

```sql
SELECT Topic, Type, Position, Tip, Status
FROM EventBusSubscriber
WHERE Topic = 'Claim_Approved__e'
```

A `Position` well behind `Tip` means the subscriber is not keeping up.

**Verify the event is actually published.** A missing notification is more often a publisher problem than a subscriber one, and checking that first saves time.

## Choosing among the streaming options

| Need | Mechanism |
| --- | --- |
| Lightning component reacting to server events | `empApi` over Streaming API |
| External system consuming events | Pub/Sub API |
| External system on AWS | Event Relay to EventBridge |
| Notify on record changes matching a filter | CDC, or a platform event |
| Simple broadcast to console users | Generic streaming, or a platform event |
| Business events with defined structure | Platform events |
| Complete record change replication | CDC |

**Do not build new integrations on PushTopics.** CDC covers the record-change case properly, with better retention, gap handling, and replay.

## Practical guidance

**Use `empApi` for components**, and always unsubscribe in `disconnectedCallback`.

**Store the last `replayId`** so a subscriber can recover from an outage.

**Prefer platform events or CDC to PushTopics** for anything new.

**Watch the concurrent client limit** in console-heavy orgs.

**Use `setDebugFlag`** when a subscription silently does nothing.

**Confirm the publisher first** when a message does not arrive.

**Move external subscribers to Pub/Sub API** when you touch them.
