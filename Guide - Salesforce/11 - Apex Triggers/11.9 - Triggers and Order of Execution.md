# Triggers and Order of Execution

## Where triggers sit

[[07.13 - Order of Execution]] covers the whole pipeline. This note is the trigger's-eye view of it — what has already happened when your code runs, and what has not.

```
 3.  System validation
 4.  Before-save flows                    ← may have already set fields
 5.  BEFORE TRIGGERS                      ← you are here
 6.  Custom validation rules              ← has NOT run yet
 7.  Record saved, not committed
 8.  AFTER TRIGGERS                       ← you are here
 9.  Assignment rules
10.  Auto-response rules
11.  Workflow field updates               ← re-runs steps 5-8 for that record
12.  Escalation rules
13.  After-save flows                     ← runs AFTER your after trigger
14.  Entitlement processes
15.  Roll-up recalculation                ← may cascade the parent through its own pipeline
16.  Criteria-based sharing evaluation
17.  COMMIT
18.  Post-commit: email, platform events, async jobs start
```

## What this tells you in a before trigger

**A before-save flow may already have set fields.** If both write the same field, your trigger wins because it runs later — silently, with the flow author believing their flow is broken. This is the concrete reason for one-mechanism-per-concern in [[07.1 - Automation Landscape and Tool Selection]].

**Validation rules have not run.** You can populate a field a validation rule requires, and it will pass. Useful for defaults.

**The record has no Id on insert.** Anything referencing it must wait for after insert.

**Relationship traversal does not work on insert.** `claim.Asset__r.SerialNumber` is null in before insert even when `Asset__c` is populated, because the record was never saved. Query the parents explicitly. See [[11.3 - Before vs After - Choosing the Right Event]].

**Formula fields and roll-ups are stale.** They reflect the pre-save state.

## What this tells you in an after trigger

**The record is saved but not committed.** An exception anywhere before step 17 rolls it back.

**Formula fields, auto-numbers, and roll-ups are populated** — on the database record. `Trigger.new` holds them as of the save, which is why re-querying is sometimes necessary for values computed at step 15.

**Assignment rules have not run yet.** A trigger cannot see the assigned owner, because assignment happens at step 9. Code needing the routed owner has to be async or a post-commit subscriber.

**After-save flows run after you.** A field an after-save flow sets is invisible to your after trigger. The reverse works — the flow sees what your trigger set.

**Roll-up recalculation has not happened.** A parent's roll-up reflects the pre-save state until step 15.

**Callouts are prohibited.** DML has occurred, so an HTTP call throws `You have uncommitted work pending`. Enqueue instead.

## The cascade

Step 15 is where an ordinary-looking operation becomes expensive.

```
Insert 200 Claim_Part__c records
  → each locks its parent Warranty_Claim__c for roll-up
  → Warranty_Claim__c roll-up updates
    → Warranty_Claim__c trigger fires (before + after)
      → which updates Asset
        → Asset roll-up updates
          → Asset trigger fires
            → which updates Account
```

One insert, four objects' automation, all consuming the same limit budget. This is the usual explanation for `Apex CPU time limit exceeded` on an operation nobody thought was heavy.

Reading a debug log makes it visible — nested `DML_BEGIN` blocks are cascade levels:

```
DML_BEGIN [1] Op:Insert Type:Claim_Part__c Rows:200
  CODE_UNIT_STARTED Trigger:ClaimPartTrigger after insert
    DML_BEGIN [2] Op:Update Type:Warranty_Claim__c Rows:48
      CODE_UNIT_STARTED Trigger:WarrantyClaimTrigger before update
      CODE_UNIT_STARTED Trigger:WarrantyClaimTrigger after update
        DML_BEGIN [3] Op:Update Type:Asset Rows:12
          CODE_UNIT_STARTED Trigger:AssetTrigger after update
LIMIT_USAGE_FOR_NS ... queries: 87 of 100, CPU: 8214 of 10000
```

Reducing the cascade is usually more effective than optimizing any single trigger: fewer roll-ups on hot parents, updating only changed records, and moving non-urgent aggregation to a scheduled job.

## Recursion through the pipeline

Steps 11, 13, and 15 can all send a record back through steps 5 to 8.

The platform caps this and throws `maximum trigger depth exceeded`, which is a crash rather than a design. Guards and change detection are covered in [[11.6 - Recursion Control and Static Guards]].

The important framing: **recursion is a property of the pipeline, not of your code.** A perfectly written trigger recurses if a roll-up sends its record back through.

## Order between triggers and flows

The question that comes up constantly.

**Before-save flow, then before trigger.** The trigger wins on conflicting writes.

**After trigger, then after-save flow.** The flow wins on conflicting writes, and the flow can see what the trigger set.

Neither order is configurable. The practical consequence: **do not have a flow and a trigger writing the same field on the same object.** Debugging it means reading both and reasoning about pipeline position, which nobody does correctly under pressure.

Where both must exist on an object, split by concern — flows own notifications and simple defaults, triggers own cross-object business logic — and document the split.

## Order among triggers

Undefined, and the reason for one trigger per object ([[11.4 - One Trigger Per Object]]).

The exception you cannot control: a managed package's trigger on the same object. Its position relative to yours is not guaranteed and can change between package versions. Do not depend on its output within the same save.

## What runs post-commit

Step 18 explains several behaviours that otherwise look inconsistent.

**Email sends.** Which is why a rolled-back transaction sends no email, and why an email sent from a trigger cannot be recalled if a later step fails.

**Platform events with immediate publish behaviour** are delivered even if the transaction rolls back — deliberately, so failure logging works. Events with the default publish-after-commit behaviour are not.

**Async jobs enqueued during the transaction actually start.** A Queueable enqueued in a trigger does not run if the transaction fails.

That last point is the correct behaviour and worth stating: enqueuing a job to notify an external system, in a transaction that then rolls back, results in no notification — which is right, because nothing happened.

## Debugging with the sequence

The diagnostic questions and what they point at:

**"My field is being overwritten."** Something later writes it. Check, in order: before trigger, after trigger, workflow field update, after-save flow.

**"My validation rule fires unexpectedly."** Something before step 6 changed the field — a before-save flow or a before trigger.

**"My trigger cannot see a field."** That field is set later in the pipeline. Assignment rules (9), workflow (11), after-save flows (13), and roll-ups (15) all run after after-triggers.

**"CPU limit on a simple update."** Cascade at step 15, or accumulated automation. Enumerate what fires on the object and its parents.

**"Uncommitted work pending."** A callout after DML. Move it async.

**"The parent record did not update."** Either the roll-up has not run yet from your vantage point, or the update was rolled back with the transaction.

## The org audit

Enumerating what fires on a save, which is the first thing to do in an unfamiliar org:

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status FROM ApexTrigger WHERE TableEnumOrId = 'Warranty_Claim__c'" \
  --target-org production
```

```sql
SELECT ApiName, Label, TriggerType, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerObjectOrEventLabel = 'Warranty Claim'
```

Add the validation rules, the roll-up summaries on the object and its parents, and any assignment or escalation rules, and that is the complete picture of one save.

## Practical guidance

**Know which pipeline step your code occupies.** It answers most "why is this happening" questions.

**Do not depend on anything after step 8** from within an after trigger.

**Never make a callout after DML.**

**Watch the cascade at step 15.** It is where cheap operations become expensive.

**Do not have a flow and a trigger writing the same field.**

**Read nested `DML_BEGIN` blocks in debug logs** — each level is a cascade.

**Audit the object's full automation** before adding to it.
