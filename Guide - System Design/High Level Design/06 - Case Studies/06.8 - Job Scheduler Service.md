# Case Study: Distributed Job Scheduler Service

> **Revision tags:** #case-study #scheduling #distributed  
> **Related:** [[03.15 - Schedulers and Cron]] | [[04.6 - Job Scheduler]]

---

## Requirements Clarification

**Functional:**
- Register jobs with cron expressions or one-time schedules
- Execute jobs at specified times with at-least-once guarantee
- Support job dependencies (Job B runs after Job A completes)
- Retry failed jobs with configurable policy
- Job history, logs, and status dashboard
- Pause/resume/trigger jobs manually

**Non-functional:**
- Scale: 1M registered jobs, 100K executions/day
- Trigger precision: within 1 second of scheduled time
- No missed executions (even after system restarts)
- No duplicate executions for the same scheduled time (idempotent)
- 99.9% scheduler availability

**Out of scope:** Job code execution environment (assume jobs call external HTTP endpoints or enqueue tasks); ML pipeline orchestration

---

## Estimation

```
Registered jobs: 1M
Executions/day: 100K = ~1.2 executions/s average
Peak: 10× = 12 executions/s (midnight batch jobs)

Job metadata: ~1KB/job = 1 GB total (tiny)
Execution history: 100K × 500 bytes = 50 MB/day, 18 GB/year

Trigger loop: check 1M jobs every second → too expensive
Better: use a priority queue (heap) — only check jobs due in the next window
```

**Key challenge:** At 1M jobs, naively scanning all jobs every second is O(1M) per tick. Need a data structure that efficiently surfaces the next job due.

---

## Architecture

```
[Admin API]          [Job Executor API]
  (register, pause)    (report status)
       │                     │
       ▼                     ▼
[Job Registry DB]    [Execution Log DB]
  (PostgreSQL)         (PostgreSQL / Cassandra)
       │
[Scheduler Service]  (leader-elected, single active instance)
  ├── In-memory priority queue (next-run-at heap)
  ├── Dispatch: emit to [Kafka: job-triggers]
  └── Watch for job updates (invalidate queue)
       │
       ▼
[Worker Pool]         (horizontally scalable)
  Consumes job-triggers → executes → reports back
       │
  ├── HTTP executor (calls webhook URL)
  ├── Queue executor (pushes message to SQS/RabbitMQ)
  └── Container executor (launches ephemeral container)
```

## Core Data Model

```sql
-- Job definitions
CREATE TABLE jobs (
    id              UUID PRIMARY KEY,
    name            VARCHAR(255) NOT NULL UNIQUE,
    description     TEXT,
    schedule        VARCHAR(100),      -- cron expression or NULL for one-time
    next_run_at     TIMESTAMPTZ,       -- pre-computed, indexed
    last_run_at     TIMESTAMPTZ,
    status          VARCHAR(20) NOT NULL DEFAULT 'active',  -- active, paused, deleted
    executor_type   VARCHAR(20) NOT NULL,   -- http, queue, container
    executor_config JSONB NOT NULL,          -- {url: ..., method: ..., headers: ...}
    retry_policy    JSONB NOT NULL,          -- {max_attempts: 3, backoff: exponential}
    timeout_seconds INT NOT NULL DEFAULT 300,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Critical index: scheduler polls this
CREATE INDEX idx_jobs_next_run_active
    ON jobs(next_run_at)
    WHERE status = 'active';

-- Execution records
CREATE TABLE job_executions (
    id              UUID PRIMARY KEY,
    job_id          UUID NOT NULL REFERENCES jobs(id),
    scheduled_at    TIMESTAMPTZ NOT NULL,  -- when it was supposed to run
    started_at      TIMESTAMPTZ,
    finished_at     TIMESTAMPTZ,
    status          VARCHAR(20) NOT NULL,  -- pending, running, success, failed, timeout
    attempt_number  INT NOT NULL DEFAULT 1,
    executor_output TEXT,
    error_message   TEXT
);

CREATE INDEX idx_executions_job_id ON job_executions(job_id, scheduled_at DESC);
```

## Scheduler: Priority Queue Approach

The scheduler maintains an in-memory min-heap of (next_run_at, job_id) pairs. This makes finding the next due job O(log N) instead of O(N).

```python
import heapq
from datetime import datetime, timezone

class SchedulerCore:
    def __init__(self, db, kafka_producer):
        self.db = db
        self.kafka = kafka_producer
        self._heap = []         # min-heap: (next_run_at, job_id)
        self._job_cache = {}    # job_id → job definition

    def load_jobs(self):
        """Load all active jobs from DB into heap on startup."""
        jobs = self.db.query(
            "SELECT id, name, schedule, next_run_at, executor_type, executor_config, "
            "       retry_policy, timeout_seconds "
            "FROM jobs WHERE status = 'active'"
        )
        for job in jobs:
            self._push_job(job)

    def _push_job(self, job):
        if job.next_run_at:
            heapq.heappush(self._heap, (job.next_run_at, job.id))
            self._job_cache[job.id] = job

    def tick(self):
        """Called every second. Dispatch all jobs due now."""
        now = datetime.now(timezone.utc)

        while self._heap and self._heap[0][0] <= now:
            run_at, job_id = heapq.heappop(self._heap)

            job = self._job_cache.get(job_id)
            if not job or job.status != 'active':
                continue   # job was paused or deleted since we enqueued it

            # Dispatch to workers
            self._dispatch(job, scheduled_at=run_at)

            # Compute and enqueue next run
            if job.schedule:
                next_run = compute_next_run(job.schedule, run_at)
                self.db.execute(
                    "UPDATE jobs SET next_run_at = %s WHERE id = %s",
                    [next_run, job_id]
                )
                job.next_run_at = next_run
                heapq.heappush(self._heap, (next_run, job_id))

    def _dispatch(self, job, scheduled_at):
        """Write execution record + emit to Kafka (atomic via outbox)."""
        execution_id = generate_uuid()

        # Outbox pattern: write to DB first, then Kafka
        self.db.execute_in_transaction([
            ("INSERT INTO job_executions (id, job_id, scheduled_at, status) "
             "VALUES (%s, %s, %s, 'pending')",
             [execution_id, job.id, scheduled_at]),
            ("INSERT INTO outbox (topic, key, value) VALUES (%s, %s, %s)",
             ["job-triggers", job.id,
              json.dumps({
                  "execution_id": execution_id,
                  "job_id": job.id,
                  "executor_type": job.executor_type,
                  "executor_config": job.executor_config,
                  "retry_policy": job.retry_policy,
                  "timeout_seconds": job.timeout_seconds,
                  "scheduled_at": scheduled_at.isoformat()
              })])
        ])
```

## Leader Election (Preventing Duplicate Triggers)

Only one scheduler instance should fire triggers. Use distributed lock for leader election:

```python
class SchedulerLeader:
    LOCK_KEY = "scheduler:leader"
    LOCK_TTL = 15  # seconds

    def __init__(self, redis_client, scheduler_core):
        self.redis = redis_client
        self.scheduler = scheduler_core
        self.instance_id = str(uuid.uuid4())

    def run(self):
        while True:
            if self._try_acquire_leadership():
                self._run_as_leader()
            else:
                time.sleep(5)   # stand by, check again

    def _try_acquire_leadership(self) -> bool:
        return bool(self.redis.set(
            self.LOCK_KEY, self.instance_id,
            nx=True, ex=self.LOCK_TTL
        ))

    def _run_as_leader(self):
        """Run scheduler loop while renewing leadership lock."""
        self.scheduler.load_jobs()

        while True:
            # Renew leadership lock
            renewed = self.redis.eval(
                "if redis.call('get',KEYS[1])==ARGV[1] then "
                "return redis.call('expire',KEYS[1],ARGV[2]) else return 0 end",
                1, self.LOCK_KEY, self.instance_id, self.LOCK_TTL
            )
            if not renewed:
                print("Lost leadership — stopping scheduler loop")
                return

            self.scheduler.tick()
            time.sleep(1)
```

If the leader crashes, its lock expires in 15 seconds. A standby picks up leadership and resumes.

## Idempotent Job Execution

Workers must be safe to retry:

```python
def execute_job(execution_id, job):
    # Claim execution: only one worker runs this execution_id
    claimed = db.execute("""
        UPDATE job_executions
        SET status = 'running', started_at = NOW()
        WHERE id = %s AND status = 'pending'
        RETURNING id
    """, [execution_id])

    if not claimed:
        logger.info(f"Execution {execution_id} already claimed by another worker")
        return   # another worker got it

    try:
        result = run_executor(job)
        db.execute("""
            UPDATE job_executions
            SET status = 'success', finished_at = NOW(), executor_output = %s
            WHERE id = %s
        """, [result, execution_id])

    except Exception as e:
        handle_failure(execution_id, job, e)
```

The `UPDATE WHERE status = 'pending'` acts as an optimistic lock — only one worker transitions from pending to running.

## Retry Policy

```json
{
  "max_attempts": 3,
  "backoff": "exponential",
  "base_delay_seconds": 60,
  "max_delay_seconds": 3600
}
```

```python
def handle_failure(execution_id, job, error):
    execution = db.get_execution(execution_id)

    if execution.attempt_number >= job.retry_policy["max_attempts"]:
        # Permanent failure
        db.execute("UPDATE job_executions SET status='failed', error=%s WHERE id=%s",
                   [str(error), execution_id])
        alert_on_call(job, error)
        return

    # Schedule retry
    delay = min(
        job.retry_policy["base_delay_seconds"] * (2 ** (execution.attempt_number - 1)),
        job.retry_policy["max_delay_seconds"]
    )
    retry_at = datetime.now(timezone.utc) + timedelta(seconds=delay)

    db.execute("""
        INSERT INTO job_executions
        (id, job_id, scheduled_at, status, attempt_number)
        VALUES (%s, %s, %s, 'pending', %s)
    """, [uuid4(), job.id, retry_at, execution.attempt_number + 1])
```

## Missed Execution Recovery

On scheduler restart, detect and backfill missed jobs:

```sql
-- Find jobs that should have run while scheduler was down
SELECT id, name, next_run_at
FROM jobs
WHERE status = 'active'
  AND next_run_at < NOW() - INTERVAL '10 seconds';
```

For each missed job: either run immediately (catch-up) or skip to the next scheduled time depending on job's `missed_execution_policy` (run_once, skip, backfill_all).

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Leader crashes | No triggers for up to 15s | Standby picks up; missed runs detected on startup |
| Worker crashes mid-execution | Execution stuck in 'running' | Timeout sweeper: mark as failed after timeout_seconds |
| DB unavailable | Can't dispatch jobs | Scheduler keeps heap; retries DB write; jobs delayed not lost |
| Clock skew across nodes | Jobs trigger at wrong time | All times stored/compared in UTC; NTP sync enforced |
| Heap too large for memory | OOM on scheduler | Partition scheduler by job_id range across multiple scheduler instances |

## What This Design Demonstrates

- Priority queue (heap) for efficient next-job lookup at scale
- Leader election via Redis lock for single-active-scheduler guarantee
- Outbox pattern for atomic DB write + Kafka emit
- Optimistic locking for idempotent worker claim
- Missed execution recovery on restart
