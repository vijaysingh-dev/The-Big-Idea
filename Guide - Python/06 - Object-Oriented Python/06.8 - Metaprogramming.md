# Metaprogramming

#python #metaprogramming #metaclasses #advanced

> **In one line:** Classes are created at runtime by calling `type`, so code can inspect and change classes as they are made. Reach for `__init_subclass__` and class decorators first; metaclasses are for the rare case where you must control class creation itself, as Enum, ABCs, Django models and Pydantic do.

---

## Classes Are Made by type

```python
class User:
    role = "member"
    def greet(self): return f"hi {self.role}"

# is equivalent to
def greet(self): return f"hi {self.role}"
User = type("User", (object,), {"role": "member", "greet": greet})
```

The `class` statement:

1. Determines the **metaclass** (`type` unless a base or `metaclass=` says otherwise).
2. Calls `metaclass.__prepare__(name, bases)` to get the namespace (normally a dict).
3. Executes the class body in that namespace.
4. Calls `metaclass(name, bases, namespace)`, i.e. `__new__` then `__init__`, to build the class.
5. Calls `__set_name__` on descriptors, then `__init_subclass__` on the parent.
6. Applies class decorators.

Each step is a hook. From least to most powerful:

| Tool | Hook point | Use for |
|---|---|---|
| **Class decorator** | After the class exists | Add methods, register, validate. `@dataclass`. |
| **`__init_subclass__`** | When any subclass is defined | Registries, validating subclass definitions, configuring subclasses with keyword arguments |
| **`__set_name__`** | When a descriptor is attached to a class | Fields that know their own names ([[06.5 - Descriptors]]) |
| **Metaclass** | Before and during class creation; also class-level behaviour (`Cls[...]`, iteration over a class, `isinstance` checks) | Enum, ABCMeta, ORMs, Pydantic |

## Class Decorators

```python
def register(cls):
    REGISTRY[cls.__name__.lower()] = cls
    return cls

def auto_repr(cls):
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}" for k, v in vars(self).items())
        return f"{cls.__name__}({fields})"
    cls.__repr__ = __repr__
    return cls

@register
@auto_repr
class Invoice:
    def __init__(self, number): self.number = number
```

`@dataclass` is a class decorator that reads `__annotations__` and generates `__init__`, `__repr__` and `__eq__` as source code, then `exec`s it ([[07.2 - Dataclasses]]).

## `__init_subclass__`: The Modern Default

```python
class Handler:
    registry: dict[str, type["Handler"]] = {}

    def __init_subclass__(cls, *, event: str, **kwargs):
        super().__init_subclass__(**kwargs)
        if not hasattr(cls, "handle"):
            raise TypeError(f"{cls.__name__} must define handle()")
        Handler.registry[event] = cls

class OrderCreated(Handler, event="order.created"):
    def handle(self, payload): ...

class OrderPaid(Handler, event="order.paid"):
    def handle(self, payload): ...

Handler.registry["order.paid"]       # <class OrderPaid>
```

Plugin registration, validating that subclasses define required attributes, and configuring subclasses through class keywords used to need metaclasses. Since 3.6, `__init_subclass__` covers almost all of it with ordinary code.

## Metaclasses

A metaclass is the class of a class. Subclass `type` and override its methods:

```python
class Singleton(type):
    _instances = {}
    def __call__(cls, *args, **kwargs):           # runs when you call the CLASS: Config()
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]

class Config(metaclass=Singleton):
    def __init__(self): self.loaded = load()

Config() is Config()    # True
```

(A module-level instance is the more Pythonic singleton; see [[02.1 - Singleton]] in the LLD guide.)

```python
class Model(type):
    def __new__(mcls, name, bases, ns):
        fields = {k: v for k, v in ns.get("__annotations__", {}).items()}
        ns["_fields"] = fields
        cls = super().__new__(mcls, name, bases, ns)
        return cls

    def __prepare__(name, bases):                 # control the namespace the body runs in
        return {}                                 # e.g. Enum returns a dict that rejects duplicate names
```

Where metaclasses really exist in your stack:

| Library | Metaclass | What it does at class creation |
|---|---|---|
| `abc` | `ABCMeta` | Collects abstract methods, blocks instantiation if any remain |
| `enum` | `EnumType` | Turns class attributes into singleton members; makes the class iterable and callable by value ([[06.6 - Enums]]) |
| Django | `ModelBase` | Builds `_meta`, fields, managers and the table mapping |
| SQLAlchemy | `DeclarativeMeta` / `DeclarativeBase` | Maps annotated attributes to columns, creates the mapper |
| Pydantic v2 | `ModelMetaclass` | Reads annotations, builds the core schema and the Rust validator **once per class** |

⚠️ **Metaclass conflicts.** A class cannot have two unrelated metaclasses: inheriting from a Django model and an ABC fails with "metaclass conflict". This is one reason libraries moved to `__init_subclass__` where they could.

The rule of thumb, often quoted: "Metaclasses are deeper magic than 99% of users should ever worry about. If you wonder whether you need them, you don't." Read them; write `__init_subclass__`.

## Dynamic Code: When It Is Justified

```python
cls = type(name, (Base,), namespace)        # build classes from config or a schema
setattr(cls, "method", func)                # attach functions
exec(source, namespace)                     # what dataclasses and namedtuple do internally
```

Legitimate uses: generating classes from an external schema (OpenAPI clients, protobuf), ORMs, test factories. Costs: harder to read, invisible to IDEs and type checkers unless you also generate stubs or use `dataclass_transform` (PEP 681, which is how type checkers understand Pydantic and SQLAlchemy models).

⚠️ Never `exec` or `eval` strings that contain user input.

**Repos:** `python/cpython`, `pydantic/pydantic`

**Question to answer:** What does Pydantic do between the end of your class body and the moment `User(...)` can validate input?

**Read, in order:**

1. CPython `Lib/types.py` — `new_class`, `prepare_class`, `resolve_bases`: the class-creation steps in pure Python
2. CPython `Lib/dataclasses.py` — `_process_class` and `_create_fn`: generating methods as source code and `exec`ing them

**Size:** 2 sessions.
