# Composite and Composite Graph API

## The problem

An external system creates an account, then a contact on it, then an opportunity, then adds a contact role. Four REST calls, four round trips, four of the daily API allocation — and if the third fails, the first two are already committed and something has to clean up.

The composite family solves both problems: fewer requests, and transactional behaviour across them.

## The four resources

**Composite** — several subrequests in one call, with the ability to reference earlier results.
**Composite Batch** — several independent subrequests, no referencing, no shared transaction.
**Composite Graph** — related record graphs, up to 500 records, transactional per graph.
**sObject Collections** — up to 200 records of one operation.

## Composite

```
POST /services/data/v62.0/composite
```

```json
{
  "allOrNone": true,
  "compositeRequest": [
    {
      "method": "POST",
      "url": "/services/data/v62.0/sobjects/Account",
      "referenceId": "newAccount",
      "body": { "Name": "Northwind Manufacturing", "Industry": "Manufacturing" }
    },
    {
      "method": "POST",
      "url": "/services/data/v62.0/sobjects/Contact",
      "referenceId": "newContact",
      "body": {
        "LastName": "Sharma",
        "FirstName": "Priya",
        "AccountId": "@{newAccount.id}"
      }
    },
    {
      "method": "POST",
      "url": "/services/data/v62.0/sobjects/Warranty_Claim__c",
      "referenceId": "newClaim",
      "body": {
        "Account__c": "@{newAccount.id}",
        "Contact__c": "@{newContact.id}",
        "Claim_Amount__c": 150000
      }
    }
  ]
}
```

**`@{referenceId.field}` is the mechanism.** A subrequest references a value from an earlier one — usually the Id of a record just created — which is what removes the need for round trips to learn Ids.

`allOrNone: true` makes the whole thing one transaction: any failure rolls everything back. `false` allows partial success.

The response mirrors the structure:

```json
{
  "compositeResponse": [
    { "referenceId": "newAccount", "httpStatusCode": 201, "body": { "id": "0015g...", "success": true } },
    { "referenceId": "newContact", "httpStatusCode": 201, "body": { "id": "0035g...", "success": true } }
  ]
}
```

**Limits:** 25 subrequests per composite call, of which at most 5 can be query or query-more.

## Composite Batch

Simpler, and less capable:

```
POST /services/data/v62.0/composite/batch
```

```json
{
  "batchRequests": [
    { "method": "GET", "url": "v62.0/sobjects/Account/0015g000..." },
    { "method": "GET", "url": "v62.0/query?q=SELECT+Id+FROM+Contact+LIMIT+10" },
    { "method": "POST", "url": "v62.0/sobjects/Task", "richInput": { "Subject": "Follow up" } }
  ]
}
```

**No `referenceId`, no cross-referencing, no shared transaction.** Each subrequest succeeds or fails independently.

Use it when the operations are genuinely unrelated and you only want to reduce round trips — fetching several unrelated records for a screen, for example.

**Limit:** 25 subrequests.

## Composite Graph

The most capable of the family, and the one worth knowing well.

```
POST /services/data/v62.0/composite/graph
```

```json
{
  "graphs": [
    {
      "graphId": "claim-CLM-99201",
      "compositeRequest": [
        {
          "method": "PATCH",
          "url": "/services/data/v62.0/sobjects/Account/ERP_Account_Id__c/ACC-4471",
          "referenceId": "account",
          "body": { "Name": "Northwind Manufacturing", "Industry": "Manufacturing" }
        },
        {
          "method": "PATCH",
          "url": "/services/data/v62.0/sobjects/Asset/ERP_Asset_Id__c/MCH-88213",
          "referenceId": "asset",
          "body": { "Name": "Press P400", "AccountId": "@{account.id}" }
        },
        {
          "method": "PATCH",
          "url": "/services/data/v62.0/sobjects/Warranty_Claim__c/ERP_Claim_Id__c/CLM-99201",
          "referenceId": "claim",
          "body": {
            "Asset__c": "@{asset.id}",
            "Account__c": "@{account.id}",
            "Claim_Amount__c": 150000
          }
        }
      ]
    },
    {
      "graphId": "claim-CLM-99202",
      "compositeRequest": [ "..." ]
    }
  ]
}
```

Three properties make this the right tool for record-graph integration:

**500 records per call**, across all graphs — far beyond composite's 25.

**Each graph is its own transaction.** Graph one failing does not affect graph two. This is the important difference from `allOrNone` on a plain composite, where one failure loses everything.

**Upsert by external ID throughout**, so the whole call is idempotent. A retry updates rather than duplicates.

The response reports per graph:

```json
{
  "graphs": [
    { "graphId": "claim-CLM-99201", "isSuccessful": true, "graphResponse": { "compositeResponse": [] } },
    { "graphId": "claim-CLM-99202", "isSuccessful": false, "graphResponse": { "compositeResponse": [] } }
  ]
}
```

**Limits:** 500 records total, 15 graphs per call, and a graph cannot span more than 500 records.

## Choosing among them

| Situation | Resource |
| --- | --- |
| Several records of one object, one operation | sObject Collections |
| A dependent chain — create parent, then child | Composite |
| Unrelated operations, just fewer round trips | Composite Batch |
| Record graphs, several at once, each atomic | Composite Graph |
| Thousands or millions of records | Bulk API |

The decision most integrations get wrong: using individual REST calls where **sObject Collections** or **Composite Graph** would do. It is the largest available reduction in API consumption and it requires no architectural change.

## A worked comparison

Loading 100 claims, each with its account and asset, from an ERP.

**Naive:** 300 individual REST calls, plus 200 lookups to resolve parent Ids. 500 API requests.

**With external IDs and sObject Collections:** three calls of 100 records each, upserting accounts, then assets, then claims. 3 API requests — but three sequential passes, and a failure partway leaves the data half-loaded.

**With Composite Graph:** 100 graphs in a few calls, each graph atomic, each upserting on external IDs. Roughly 2 API requests, each graph independently recoverable, and a retry is safe.

The third is both cheaper and more correct, which is unusual enough to be worth noting.

## Calling composite from Apex

Salesforce calling another org, or calling itself:

```java
public with sharing class CompositeGraphClient {

    public class GraphNode {
        public String method;
        public String url;
        public String referenceId;
        public Map<String, Object> body;
    }

    public static void pushClaims(List<Warranty_Claim__c> claims) {
        List<Object> graphs = new List<Object>();

        for (Warranty_Claim__c claim : claims) {
            graphs.add(new Map<String, Object>{
                'graphId' => 'claim-' + claim.ERP_Claim_Id__c,
                'compositeRequest' => buildNodes(claim)
            });
        }

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:Partner_Org/services/data/v62.0/composite/graph');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(new Map<String, Object>{ 'graphs' => graphs }));
        req.setTimeout(120000);

        HttpResponse res = new Http().send(req);
        handleGraphResponse(res);
    }

    private static void handleGraphResponse(HttpResponse res) {
        Map<String, Object> parsed = (Map<String, Object>) JSON.deserializeUntyped(res.getBody());

        // each graph reports independently, so partial success must be handled per graph
        for (Object graphObj : (List<Object>) parsed.get('graphs')) {
            Map<String, Object> graph = (Map<String, Object>) graphObj;
            if (graph.get('isSuccessful') != true) {
                logGraphFailure((String) graph.get('graphId'), graph);
            }
        }
    }
}
```

The per-graph result handling is the part that matters. Treating the HTTP 200 as success and moving on loses every individual graph failure.

## Composite and limits

**One composite call counts as one API request** against the daily allocation, regardless of how many subrequests it contains. This is the primary commercial benefit.

Governor limits still apply **per subrequest** — each one is a separate transaction internally, so a subrequest hitting a query limit fails on its own.

For Composite Graph, each graph is a transaction with its own limits.

## Practical guidance

**Use Composite Graph for record-graph integration**, with upsert on external IDs throughout.

**Use `@{referenceId.id}`** rather than round-tripping to learn Ids.

**Prefer per-graph atomicity to `allOrNone`** across a large composite, so one bad record does not lose the batch.

**Handle the per-subrequest and per-graph responses.** An HTTP 200 does not mean everything succeeded.

**Use sObject Collections** where the operation is uniform and no relationships need resolving.

**Move to Bulk API** above a few thousand records.
