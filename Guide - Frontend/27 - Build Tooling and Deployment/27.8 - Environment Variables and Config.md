# Environment Variables and Config

## The rule that governs everything

**Anything in a frontend bundle is public.**

```js
const apiKey = import.meta.env.VITE_API_KEY;
```

At build time this becomes:

```js
const apiKey = "sk_live_abc123";
```

The value is a string literal in a file anyone can download. There is no obfuscation, no environment, no server-side lookup. Minification does not hide it, and neither does the absence of source maps ([[27.7 - Source Maps]]).

The prefix requirements — `VITE_`, `NEXT_PUBLIC_`, `REACT_APP_` — exist precisely to make exposure explicit. They are a speed bump requiring you to opt in, not a security mechanism.

**Never in a frontend bundle:** database credentials, private API keys, signing secrets, admin tokens, third-party service secrets.

**Fine in a frontend bundle:** public API base URLs, publishable keys (Stripe `pk_`, Firebase config), feature flag defaults, analytics site ids, the app version.

Firebase config and Stripe publishable keys look like secrets and are not — they are designed for client exposure, with security enforced server-side by rules and by the secret key. Confusing the two directions costs people a lot of unnecessary anxiety, and occasionally a real breach.

## Build-time replacement

```ts
// Vite
import.meta.env.VITE_API_URL
import.meta.env.MODE          // "development" | "production" | custom
import.meta.env.DEV
import.meta.env.PROD
```

```js
// Next.js and webpack
process.env.NEXT_PUBLIC_API_URL
```

Both are **textual replacement during the build**, not a runtime lookup. Two consequences that surprise people:

**Dynamic access does not work:**

```js
const key = `VITE_${name}_URL`;
import.meta.env[key];              // undefined — no static string to replace
```

**Changing the value requires a rebuild.** The same artifact cannot be promoted from staging to production if the API URL is baked in — you must build once per environment.

## Runtime configuration

To build once and deploy everywhere, the config must arrive at runtime rather than at build time.

**Injected into HTML at serve time:**

```html
<script>
  window.__CONFIG__ = { apiUrl: "https://api.production.example.com" };
</script>
```

A small server-side template or an edge function substitutes the values per environment. The bundle stays identical.

**Fetched on startup:**

```ts
const config = await fetch("/config.json").then(r => r.json());
```

Simple and cache-friendly, but it adds a request before the app can initialize — acceptable if the file is tiny and served from the same origin.

**Derived from the hostname:**

```ts
const API_URL = location.hostname.endsWith("staging.example.com")
  ? "https://api.staging.example.com"
  : "https://api.example.com";
```

Crude but zero-cost, and adequate for a small number of environments.

The build-once-deploy-many property is what makes runtime config worth the complexity in a real deployment pipeline: the artifact tested in staging is byte-identical to the one released to production ([[27.9 - CI CD and Frontend Deployment]]).

## Validating config

Missing or malformed configuration should fail at startup with a clear message, not at the first API call:

```ts
import { z } from "zod";

const envSchema = z.object({
  VITE_API_URL: z.string().url(),
  VITE_SENTRY_DSN: z.string().url().optional(),
  VITE_ENABLE_BETA: z.coerce.boolean().default(false),
});

export const env = envSchema.parse(import.meta.env);
```

Three benefits: a typo in a variable name is caught immediately, types are derived rather than asserted, and `z.coerce.boolean()` handles the fact that **every environment variable is a string** ([[25.7 - Typing API Responses and Zod]]).

That last point causes a specific recurring bug:

```ts
if (import.meta.env.VITE_DEBUG) {}          // "false" is truthy
if (env.VITE_DEBUG) {}                       // properly coerced
```

Note the schema must reference `import.meta.env` statically — spreading it works, but constructing keys dynamically does not.

## File conventions

```
.env                    committed — safe defaults
.env.example            committed — documents every required variable
.env.local              gitignored — local overrides
.env.production         committed if it contains no secrets
.env.production.local   gitignored
```

`.env.example` is the one people skip and then regret. It is the only place a new team member can discover what the application needs:

```
VITE_API_URL=http://localhost:3000
VITE_SENTRY_DSN=
```

Verify the gitignore covers `*.local` and any `.env` file containing real values. A committed `.env` with production credentials is among the more common credential leaks, and rotation is the only fix once it is in history.

## Feature flags

Build-time flags are dead-code eliminated:

```ts
if (import.meta.env.VITE_ENABLE_NEW_CHECKOUT === "true") {
  return <NewCheckout />;
}
```

The disabled branch is removed entirely from the production bundle, which is good for size and means the code cannot be reached by inspection.

The cost is that changing a flag requires a rebuild and redeploy, and different builds exist per environment.

Runtime flags come from a service:

```ts
const { newCheckout } = useFlags();
```

Instant toggles, per-user targeting, gradual rollout and a kill switch — at the cost of shipping both code paths and a request to the flag service ([[28.8 - Feature Flags and Progressive Rollout]]).

Use build-time flags for permanent environment differences, and a flag service for anything that needs to change without a deploy.

## Server-side environments

In Next.js the boundary is enforced by the framework:

```ts
// Server Component or route handler — never sent to the client
const dbUrl = process.env.DATABASE_URL;

// Client Component — must be prefixed, and is public
const apiUrl = process.env.NEXT_PUBLIC_API_URL;
```

Referencing an unprefixed variable in a Client Component yields `undefined` rather than leaking it — the build enforces the split.

This is a genuine advantage of a server-rendering framework: secrets can be used directly without an intermediate API layer, because the code never reaches the browser ([[22.8 - Server Components]]).

## The proxy pattern

When a frontend genuinely needs a service that requires a secret, the answer is a thin server-side proxy:

```
browser → your backend (holds the secret) → third-party API
```

This is the only correct solution for a secret-requiring integration. There is no client-side alternative — obfuscation, encoding and runtime assembly all fail, because the key must exist in memory for the request to be signed.

If a vendor's SDK requires a secret key in the browser, that is a vendor design flaw and the integration belongs on your server.

## How senior engineers actually use this

**They treat every bundled value as public**, and audit for anything that should not be.

**They validate environment config with a schema at startup**, so misconfiguration fails loudly and immediately.

**They maintain `.env.example`** as the documentation of what the app requires.

**They use runtime config** where build-once-deploy-many matters, and accept build-time replacement where it does not.

**They put anything needing a secret behind a server proxy**, without exception.

## Common pitfalls

- Secrets in prefixed variables, believing the prefix protects them.
- Expecting a runtime change to take effect without a rebuild.
- Dynamic key access into `import.meta.env`, which returns `undefined`.
- String `"false"` treated as truthy.
- `.env` with real values committed to git.
- No `.env.example`, so setup requires asking someone.
- Confusing publishable keys with secret keys in both directions.
- Building separate artifacts per environment when runtime config would allow one.

## Interview angle

"How do you handle environment variables in a frontend app" has a security answer and a deployment answer. Security: anything in the bundle is public, prefixes make exposure explicit rather than preventing it, and anything requiring a secret must go through a server proxy. Deployment: build-time replacement means a separate artifact per environment, so runtime config — injected HTML or a fetched config file — is what enables build-once-deploy-many. Adding schema validation at startup shows you have debugged a misconfigured deploy.
