# Sorting and Comparators

`Array.prototype.sort` has two behaviors that surprise people every time: it **mutates** the array, and without a comparator it sorts by **string** comparison.

```js
[10, 9, 1].sort();          // [1, 10, 9]  — "10" < "9" as strings
[10, 9, 1].sort((a, b) => a - b);  // [1, 9, 10]
```

The default converts every element with `String()` and compares UTF-16 code units. This means numeric arrays are sorted wrongly, and it is the single most common sort bug.

## Mutation

```js
const original = [3, 1, 2];
const sorted = original.sort();
original === sorted;   // true — same array, mutated in place
```

Sorting props or state directly is a real bug in React: it mutates data the parent owns, and because the reference is unchanged, no re-render is triggered.

```js
// Safe copies
const sorted = [...items].sort(cmp);
const sorted = items.slice().sort(cmp);
const sorted = items.toSorted(cmp);   // non-mutating, ES2023
```

`toSorted`, `toReversed`, `toSpliced` and `with` are the non-mutating counterparts to `sort`, `reverse`, `splice` and index assignment. They are the right default in React code.

## The comparator contract

```js
(a, b) => negative  // a before b
(a, b) => 0         // treat as equal
(a, b) => positive  // b before a
```

The comparator must be **consistent**: if it says `a < b` and `b < c`, it must say `a < c`, and `cmp(a, b)` must be the negation of `cmp(b, a)`. An inconsistent comparator — one returning random values, or `true`/`false` instead of numbers — produces an implementation-defined result rather than an error.

```js
arr.sort((a, b) => a > b);   // wrong — returns boolean, coerced to 0/1, never negative
```

Since ES2019, `sort` is required to be **stable**: elements comparing equal keep their original relative order. This is what makes multi-pass sorting work.

## Common comparators

```js
// Numbers
(a, b) => a - b;              // ascending
(a, b) => b - a;              // descending

// Strings — locale-aware, handles accents and case correctly
(a, b) => a.name.localeCompare(b.name);
(a, b) => a.name.localeCompare(b.name, "en", { sensitivity: "base" });

// Dates
(a, b) => new Date(a.date) - new Date(b.date);
(a, b) => a.date.getTime() - b.date.getTime();

// Booleans — true first
(a, b) => Number(b.pinned) - Number(a.pinned);
```

Never sort strings with `<` and `>` if users will see the result — `"Z" < "a"` is `true` in code-unit order, so uppercase sorts before all lowercase, and accented characters land after `z`. `localeCompare` handles this. For repeated comparisons, `Intl.Collator` is substantially faster because it builds the collation table once:

```js
const collator = new Intl.Collator("en", { numeric: true, sensitivity: "base" });
items.sort((a, b) => collator.compare(a.name, b.name));
```

The `numeric: true` option gives natural sorting: `"file2"` before `"file10"`.

## Multi-key sorting

```js
const byDeptThenName = (a, b) =>
  a.dept.localeCompare(b.dept) || a.name.localeCompare(b.name);
```

`||` works because a comparator returns `0` for ties, which is falsy, so the next comparison runs. Chaining more keys extends the same pattern.

A composable version:

```js
const by = (...comparators) => (a, b) => {
  for (const cmp of comparators) {
    const result = cmp(a, b);
    if (result !== 0) return result;
  }
  return 0;
};

const byName = (a, b) => a.name.localeCompare(b.name);
const byAge = (a, b) => a.age - b.age;

items.sort(by(byAge, byName));
```

Because sort is stable, an alternative is sorting by the least significant key first and then by the most significant — but a compound comparator is clearer and does one pass.

## Handling missing values

```js
const byDate = (a, b) => {
  if (!a.date && !b.date) return 0;
  if (!a.date) return 1;     // undefined goes last
  if (!b.date) return -1;
  return new Date(a.date) - new Date(b.date);
};
```

`undefined` elements are always moved to the end by `sort` itself, without ever being passed to the comparator — but a `undefined` *property* is not, and `undefined - 5` is `NaN`, which makes the comparator inconsistent and the result arbitrary. Explicit handling is required.

## Expensive keys

If the sort key is costly to compute, precompute it once per element rather than on every comparison — sorting performs O(n log n) comparisons, so a key computed inside the comparator runs many times per element:

```js
const decorated = items
  .map(item => ({ item, key: expensiveKey(item) }))
  .sort((a, b) => a.key - b.key)
  .map(d => d.item);
```

This is the Schwartzian transform. Worth reaching for when the key involves parsing dates, normalizing strings or traversing objects.

## Complexity

Engines use variants of Timsort (V8 since 2018), which is O(n log n) worst case, stable, and near O(n) on partially sorted data. There is no need to implement your own sort for application data.

For very large lists rendered in a UI, the sort is rarely the bottleneck — rendering is. Virtualization ([[19.5 - Virtualization and Windowing]]) matters far more than sort performance.

## Sorting in React

```jsx
function Table({ rows, sortKey, direction }) {
  const sorted = useMemo(
    () => [...rows].sort(makeComparator(sortKey, direction)),
    [rows, sortKey, direction]
  );
  return <Rows items={sorted} />;
}
```

Two things here: the copy prevents mutating props, and `useMemo` prevents re-sorting on unrelated renders. Without the memo, a large table re-sorts on every keystroke elsewhere in the page.

## How senior engineers actually use this

**They never sort in place on shared data.** `toSorted` or a spread copy is the default in any code touching props, state or a store.

**They use `Intl.Collator` for user-facing string sorting**, especially in multilingual products. For an Indian product with mixed English and Devanagari content, code-unit sorting produces visibly wrong order.

**They sort on the server when the dataset is large or paginated.** Client-side sorting of a paginated list sorts only the current page, which is almost always a bug in the UX rather than the code.

**They keep comparators as named, testable functions.** Inline multi-key comparators inside JSX are hard to test and easy to get subtly wrong.

## Common pitfalls

- Default sort on numbers.
- Mutating props or state with `.sort()`.
- `(a, b) => a > b` returning a boolean.
- `NaN` from comparing undefined properties, producing arbitrary order.
- Sorting inside render without memoization.
- Assuming sort is stable in very old environments — it is guaranteed only since ES2019.
- Client-side sorting a paginated dataset.

## Interview angle

The default-string-sort behavior and the mutation are the two things asked directly. Beyond that, multi-key sorting with the `||` chain, stability and what it enables, and `localeCompare` for user-facing text are the details that show practical experience. If asked to implement a sort algorithm, that is a data-structures question rather than a JavaScript one — but knowing engines use Timsort and why stability matters is a good closing remark.
