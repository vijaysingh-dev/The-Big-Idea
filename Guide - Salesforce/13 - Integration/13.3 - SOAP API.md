# SOAP API

## Why this note exists

SOAP is not the choice for new integrations. It is here because you will meet it: in older enterprise systems whose tooling expects a WSDL, in middleware configured a decade ago, and in a small number of operations the REST API does not expose.

Knowing when SOAP is genuinely required, and when it is merely inherited, is the useful part.

## The two WSDLs

**Enterprise WSDL.** Strongly typed and generated for **your specific org**. Every object and field appears as a typed element, so client tooling produces classes matching your schema exactly.

*Strength:* compile-time type safety in the client.
*Weakness:* it is org-specific. Adding a field means regenerating the WSDL and rebuilding the client. A WSDL generated from a sandbox does not match production if the schemas have diverged.

**Partner WSDL.** Loosely typed and generic across all orgs. Records are name-value pairs rather than typed objects.

*Strength:* one WSDL works against any org and survives schema changes.
*Weakness:* no type safety; the client handles strings.

The guidance: **Partner WSDL for anything that must work across orgs or survive schema evolution** — which is most integrations, and certainly any managed package or multi-tenant middleware. Enterprise WSDL only when the client team genuinely wants generated typed classes and the schema is stable.

Download either from Setup, under API.

## The core calls

```
login()          authenticate, returns a session Id and server URL
create()         insert up to 200 records
update()         update up to 200
upsert()         upsert on an external Id, up to 200
delete()         delete up to 200
undelete()
merge()
query()          SOQL
queryMore()      pagination cursor
queryAll()       including deleted
retrieve()       by Id
search()         SOSL
describeSObject()
describeGlobal()
getUserInfo()
convertLead()
```

**200 records per call**, the same as REST's sObject Collections.

`queryMore()` uses a query locator returned by `query()`, which is the SOAP equivalent of `nextRecordsUrl`.

## Session-based authentication

The historical model, and the reason SOAP feels dated:

```xml
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:urn="urn:partner.soap.sforce.com">
  <soapenv:Body>
    <urn:login>
      <urn:username>integration@company.com</urn:username>
      <urn:password>passwordSECURITYTOKEN</urn:password>
    </urn:login>
  </soapenv:Body>
</soapenv:Envelope>
```

The password is concatenated with a **security token**, and the response returns a session Id used in subsequent calls.

Two problems with this in a modern org:

**The password is stored somewhere.** OAuth exists so that it does not have to be.

**The security token changes** whenever the password is reset, which silently breaks the integration.

**Session-based login is not the recommendation.** SOAP accepts an OAuth access token as the session Id, so a SOAP client can authenticate through the JWT bearer flow like any other integration. Doing so removes the stored password entirely. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

Where an org has enabled the setting to disable username-password OAuth flows, session login may not be available at all.

## What SOAP still does that REST does not

A short list, and the honest reason to keep a SOAP client:

**`convertLead()`.** Lead conversion is exposed through SOAP and not through the standard REST resources. An external system converting leads either uses SOAP or calls a custom Apex REST endpoint wrapping `Database.convertLead`.

**`merge()`.** Same situation.

**Certain describe details** are richer in the SOAP describe result.

**Some Metadata API operations** are SOAP-only, though the Metadata API is a separate service. See [[13.6 - Metadata API and Tooling API]].

In practice, wrapping the operation in a custom Apex REST service is usually cleaner than maintaining a SOAP client for one call:

```java
@RestResource(urlMapping='/lead-conversion/*')
global with sharing class LeadConversionResource {

    @HttpPost
    global static ConversionResult convert(String leadId, Boolean createOpportunity) {
        LeadStatus convertedStatus = [
            SELECT MasterLabel FROM LeadStatus WHERE IsConverted = true LIMIT 1
        ];

        Database.LeadConvert lc = new Database.LeadConvert();
        lc.setLeadId(leadId);
        lc.setConvertedStatus(convertedStatus.MasterLabel);
        lc.setDoNotCreateOpportunity(!createOpportunity);

        Database.LeadConvertResult result = Database.convertLead(lc, false);
        return ConversionResult.from(result);
    }
}
```

One endpoint, REST, OAuth, and no WSDL. See [[13.15 - Building Apex REST and SOAP Services]].

## Headers

SOAP headers control behaviour the body cannot:

```xml
<urn:AssignmentRuleHeader>
    <urn:useDefaultRule>true</urn:useDefaultRule>
</urn:AssignmentRuleHeader>

<urn:EmailHeader>
    <urn:triggerAutoResponseEmail>true</urn:triggerAutoResponseEmail>
    <urn:triggerUserEmail>true</urn:triggerUserEmail>
</urn:EmailHeader>

<urn:AllOrNoneHeader>
    <urn:allOrNone>false</urn:allOrNone>
</urn:AllOrNoneHeader>

<urn:DuplicateRuleHeader>
    <urn:allowSave>true</urn:allowSave>
</urn:DuplicateRuleHeader>
```

`AssignmentRuleHeader` and `EmailHeader` are the ones that matter, for the same reason as everywhere else: **assignment rules and auto-response rules do not run by default** through the API. A SOAP integration creating leads or cases without these headers produces records owned by the integration user, invisible to everyone.

## Calling SOAP from Apex

Occasionally Salesforce is the SOAP client, calling an external service.

```bash
# Generate an Apex stub from a WSDL
Setup → Apex Classes → Generate from WSDL
```

The generated class is usually ugly and often needs hand-editing — the WSDL-to-Apex generator handles a limited subset of WSDL and fails on complex schemas.

Where it fails, constructing the envelope by hand is the fallback:

```java
public with sharing class LegacyErpSoapClient {

    public static String submitClaim(Warranty_Claim__c claim) {
        String envelope =
            '<?xml version="1.0" encoding="UTF-8"?>'
            + '<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"'
            + ' xmlns:erp="http://erp.northwind.com/claims">'
            + '<soapenv:Body>'
            + '<erp:SubmitClaim>'
            + '<erp:ClaimNumber>' + escapeXml(claim.Claim_Number__c) + '</erp:ClaimNumber>'
            + '<erp:Amount>' + claim.Claim_Amount__c + '</erp:Amount>'
            + '</erp:SubmitClaim>'
            + '</soapenv:Body></soapenv:Envelope>';

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:Legacy_ERP/ClaimService');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'text/xml; charset=UTF-8');
        req.setHeader('SOAPAction', 'SubmitClaim');
        req.setBody(envelope);
        req.setTimeout(60000);

        HttpResponse res = new Http().send(req);

        if (res.getStatusCode() != 200) {
            throw new IntegrationException('SOAP call failed: ' + res.getStatusCode());
        }
        return parseResponse(res.getBody());
    }

    private static String escapeXml(String value) {
        // unescaped values break the envelope, and a claim number is user-supplied data
        return value == null ? '' : value
            .replace('&', '&amp;').replace('<', '&lt;').replace('>', '&gt;')
            .replace('"', '&quot;').replace('\'', '&apos;');
    }
}
```

XML escaping is not optional. An unescaped ampersand in a field value produces a malformed envelope, and the failure message from the receiving system is rarely helpful.

Parsing the response uses `Dom.Document` or `XmlStreamReader`:

```java
private static String parseResponse(String body) {
    Dom.Document doc = new Dom.Document();
    doc.load(body);

    Dom.XmlNode envelope = doc.getRootElement();
    Dom.XmlNode soapBody = envelope.getChildElement('Body', SOAP_NS);
    Dom.XmlNode response = soapBody.getChildElements()[0];

    return response.getChildElement('ConfirmationNumber', ERP_NS)?.getText();
}
```

Namespace handling is where hand-rolled SOAP parsing usually goes wrong — every element lookup needs the right namespace, and the namespace differs between the envelope and the payload.

## SOAP faults

Errors arrive as a fault element with a 500 status:

```xml
<soapenv:Fault>
    <faultcode>sf:INVALID_FIELD</faultcode>
    <faultstring>INVALID_FIELD: No such column 'Statuss__c'</faultstring>
</soapenv:Fault>
```

A client must parse the fault rather than treating the 500 as a transport failure, because a SOAP fault is an application error and is frequently permanent — retrying it achieves nothing.

## Migrating away

When you inherit a SOAP integration, the question is whether to migrate.

**Migrate when:** the WSDL is Enterprise and schema changes keep breaking it, the integration stores a password and security token, or the client is being rewritten anyway.

**Leave it when:** it works, it uses the Partner WSDL, and nothing about it is changing. A working SOAP integration is not a defect, and rewriting it consumes budget for no business outcome.

The middle path most teams take: **move authentication to OAuth first**, which removes the stored password and the security token fragility, and leave the SOAP calls in place. That is a small change with most of the benefit.

## Practical guidance

**Use Partner WSDL** over Enterprise unless typed client classes are genuinely wanted.

**Authenticate with OAuth**, not username-password login.

**Set the assignment and email headers** where those rules should run.

**Escape XML** in any hand-built envelope.

**Parse SOAP faults** rather than treating a 500 as transport failure.

**Wrap SOAP-only operations in Apex REST** rather than maintaining a SOAP client for one call.

**Do not choose SOAP for new work.** REST, Bulk, or Composite covers everything except lead conversion and merge.
