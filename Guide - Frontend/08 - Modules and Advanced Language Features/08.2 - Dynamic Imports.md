# Dynamic Imports

`import()` loads a module at runtime and returns a promise. It is the mechanism behind every code-splitting strategy in modern frontend applications.

```js
const module = await import("./heavy-module.js");
module.default;
module.namedExport;
```

Unlike static `import`, it is an expression: it can appear anywhere, take a computed specifier, and be conditional.

## What it returns

The resolved value is the **module namespace object**, not the default export. This trips people up constantly:

```js
// Wrong
const Chart = await import("./Chart.js");
new Chart();   // TypeError — Chart is a namespace object

// Right
const { default: Chart } = await import("./Chart.js");
const Chart = (await import("./Chart.js")).default;
```

## What the bundler does with it

Every `import()` becomes a **split point**. The bundler emits the target and its unique dependencies as a separate chunk, fetched only when that line executes.

```js
// Creates a separate chunk
button.addEventListener("click", async () => {
  const { openEditor } = await import("./editor.js");
  openEditor();
});
```

The editor code — and its dependencies, minus anything already in the main bundle — is not downloaded until the user clicks.

Bundlers need to see enough statically to know what to emit. A fully dynamic specifier defeats this:

```js
// Bundler cannot determine the target — often fails or bundles everything
await import(userSuppliedPath);

// Bundler emits a chunk per matching file
await import(`./locales/${lang}.js`);
```

The template-literal form works in Vite and webpack because the static prefix and suffix bound the possibilities, but it emits a chunk for every match — so `./locales/*` with forty languages produces forty chunks. That is usually what you want for locales and usually not what you want elsewhere.

## Magic comments

Webpack (and Vite, partially) reads inline comments to control chunk behavior:

```js
const mod = await import(
  /* webpackChunkName: "editor" */
  /* webpackPrefetch: true */
  "./editor.js"
);
```

- **`webpackChunkName`** gives the chunk a readable filename, which matters for debugging and cache analysis.
- **`webpackPrefetch: true`** emits `<link rel="prefetch">`, fetching the chunk at low priority during idle time — good for things the user will *probably* need next.
- **`webpackPreload: true`** fetches in parallel with the parent chunk at normal priority — for things needed almost immediately.

Prefetch is the more useful of the two in practice ([[29.2 - Prefetching and Preloading]]).

## React.lazy

```jsx
const Dashboard = lazy(() => import("./Dashboard"));

<Suspense fallback={<Spinner />}>
  <Dashboard />
</Suspense>
```

`React.lazy` takes a function returning a promise for a module with a **default export**. Named exports need re-mapping:

```jsx
const Chart = lazy(() =>
  import("./charts").then(m => ({ default: m.BarChart }))
);
```

Route-level splitting is the highest-value application ([[23.5 - Lazy Routes]]), because routes are natural boundaries the user navigates between and the payoff is a smaller initial bundle.

## Error handling

Network failures on chunk loads are real and common — particularly after a deploy, when the hashed chunk filenames the user's page references no longer exist on the CDN.

```js
async function loadWithRetry(loader, attempts = 3) {
  for (let i = 0; i < attempts; i++) {
    try {
      return await loader();
    } catch (err) {
      if (i === attempts - 1) throw err;
      await new Promise(r => setTimeout(r, 500 * 2 ** i));
    }
  }
}

const Dashboard = lazy(() => loadWithRetry(() => import("./Dashboard")));
```

The post-deploy case deserves special handling: if a chunk 404s and the app has been open across a deployment, the correct recovery is usually a full page reload to pick up the new asset manifest.

```js
window.addEventListener("vite:preloadError", () => window.location.reload());
```

Without this, users who leave a tab open overnight see a blank screen on their next navigation. It is one of the most common production issues in code-split SPAs.

## Preloading on intent

Splitting trades bundle size for latency at navigation time. Prefetching on hover recovers most of that latency:

```jsx
const Settings = lazy(() => import("./Settings"));
const preload = () => import("./Settings");   // same specifier, cached

<Link to="/settings" onMouseEnter={preload} onFocus={preload}>
  Settings
</Link>
```

Calling `import()` twice on the same specifier does not fetch twice — the module registry caches by resolved URL. So the hover call warms the cache and the render call resolves instantly.

Hover-to-click is typically 100–300 ms, which covers most chunk downloads on a decent connection.

## Conditional and lazy loading

```js
// Polyfill only where needed
if (!("IntersectionObserver" in window)) {
  await import("intersection-observer");
}

// Heavy dependency only on the path that needs it
async function exportToPdf(data) {
  const { jsPDF } = await import("jspdf");
  return new jsPDF().text(data).save();
}
```

The second pattern is the highest-leverage use after route splitting: a PDF library, a rich text editor, a charting library or a date picker used on one screen should not be in the initial bundle.

## What not to split

Splitting has costs — an extra network round trip, a loading state, more complexity, and a larger total payload due to duplicated module boilerplate.

Do not split:

- Small modules. A 3 KB chunk is not worth a round trip.
- Anything needed immediately on first paint.
- Components inside a tight interaction loop, where the loading flash is worse than the bytes.

A rough threshold: split when the chunk is over ~30 KB and is not needed on the initial render.

## How senior engineers actually use this

**They split by route first, then by heavy dependency.** These two cover the majority of the achievable win. Splitting individual small components rarely moves the metric.

**They pair every split with a prefetch on intent.** Splitting without prefetching moves the delay from load time to interaction time, which is often a worse trade for perceived performance.

**They handle chunk-load failure globally**, with a reload-on-stale-manifest strategy.

**They verify with the bundle analyzer.** Assumptions about what ended up in which chunk are frequently wrong — a shared utility import can pull a "lazy" dependency into the main bundle ([[27.7 - Source Maps]] and [[19.7 - Bundle Analysis and Optimization]]).

## Common pitfalls

- Forgetting `.default` on the resolved namespace.
- Fully dynamic specifiers that bundlers cannot analyze.
- No error handling, so a failed chunk shows a blank screen.
- Stale chunk references after deploy.
- Over-splitting into dozens of tiny chunks, adding round trips without reducing bytes.
- Lazy-loading a component that renders immediately on the same screen, which just adds a spinner.

## Interview angle

"What is code splitting and how do you implement it" leads here. Cover `import()` returning a promise for the namespace object, bundlers creating chunks at each call site, `React.lazy` plus `Suspense` for components, and route-level splitting as the default strategy. The details that stand out are prefetch-on-hover and handling chunk-load failures after a deploy — both are things you only learn from shipping.
