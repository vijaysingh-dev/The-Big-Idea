# Portals

A portal renders children into a **different DOM node** while keeping them in the same React tree.

```jsx
import { createPortal } from "react-dom";

function Modal({ children, isOpen }) {
  if (!isOpen) return null;

  return createPortal(
    <div className="overlay">{children}</div>,
    document.body
  );
}
```

The DOM output lands in `document.body`; the React position is unchanged.

## Why they exist

Two CSS problems that no amount of positioning solves.

**`overflow: hidden` clips descendants.** A dropdown inside a scrollable table is cut off at the container edge, regardless of `position: absolute` or `z-index`.

**Stacking contexts trap `z-index`.** A parent with `transform`, `opacity < 1`, or `filter` creates a stacking context, and a descendant cannot paint above anything outside it — no matter how large its `z-index` ([[10.5 - Positioning and Stacking Contexts]]).

The same rule breaks `position: fixed`: an ancestor with a `transform` becomes the containing block, so a "fixed" modal positions relative to it rather than the viewport.

Portals escape both by moving the node out of the problematic subtree entirely.

## Events bubble through the React tree

The behavior that surprises people:

```jsx
<div onClick={() => console.log("parent clicked")}>
  <Modal>                        {/* rendered into document.body */}
    <button>Click me</button>    {/* clicking logs "parent clicked" */}
  </Modal>
</div>
```

The DOM node is in `body`, but React's synthetic event system propagates along the **React tree**, not the DOM tree ([[12.3 - The Event Model]]).

This is usually what you want — context, event handlers and error boundaries all work as if the portal were in place. It becomes a problem for outside-click detection:

```jsx
// Broken — the modal's own clicks count as "outside" in DOM terms
useEffect(() => {
  const handler = (e) => {
    if (!containerRef.current?.contains(e.target)) close();
  };
  document.addEventListener("click", handler);
  return () => document.removeEventListener("click", handler);
}, []);
```

Fix by checking the portal's node, or by using `composedPath()` which reports the actual DOM path.

Note the ordering issue too: a native `document` listener added on open fires for the very click that opened the modal, closing it immediately. Attach the listener in a `setTimeout(…, 0)`, use the capture phase, or check `event.timeStamp`.

## Prefer the native dialog

For modals specifically, `<dialog>` with `showModal()` is now the better answer:

```jsx
function Modal({ isOpen, onClose, children }) {
  const ref = useRef(null);

  useEffect(() => {
    const dialog = ref.current;
    if (isOpen) dialog?.showModal();
    else dialog?.close();
  }, [isOpen]);

  return (
    <dialog ref={ref} onClose={onClose} onClick={e => {
      if (e.target === ref.current) onClose();     // backdrop click
    }}>
      {children}
    </dialog>
  );
}
```

`showModal()` renders the element in the browser's **top layer**, which sits above everything on the page regardless of stacking contexts — so no portal is needed at all. It also provides focus trapping, `Escape` to close, background inertness, and a `::backdrop` pseudo-element, all of which custom modals routinely get wrong ([[09.5 - Accessibility Fundamentals]]).

The Popover API (`popover` attribute) does the same for tooltips and menus.

Portals remain the right tool when you need arbitrary DOM placement rather than "above everything" — rendering into a specific container, an iframe, or a third-party mount point.

## Accessibility is not free

A portal moves the DOM node, which changes the reading order for assistive technology and breaks the visual/DOM relationship keyboard users rely on. A portalled modal needs, at minimum:

```jsx
<div role="dialog" aria-modal="true" aria-labelledby="title">
```

Plus focus moved into the dialog on open, focus trapped inside, focus returned to the trigger on close, and background content marked `inert`:

```jsx
useEffect(() => {
  if (!isOpen) return;
  const previous = document.activeElement;
  dialogRef.current?.focus();
  document.getElementById("root")?.setAttribute("inert", "");
  return () => {
    document.getElementById("root")?.removeAttribute("inert");
    previous?.focus();
  };
}, [isOpen]);
```

This is exactly what `<dialog>.showModal()` does for you, which is the strongest argument for using it.

## Portal targets

```jsx
// A dedicated node, not document.body
createPortal(children, document.getElementById("portal-root"));
```

A dedicated container is preferable to `body` — it keeps portal content in a predictable place, avoids conflicts with third-party scripts appending to `body`, and lets you scope CSS to it.

For SSR, `document` does not exist during the server render:

```jsx
function Portal({ children }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);

  if (!mounted) return null;
  return createPortal(children, document.getElementById("portal-root"));
}
```

The alternative is a ref-based container rendered by React itself, which avoids the client-only render.

## Body scroll locking

```jsx
useEffect(() => {
  if (!isOpen) return;
  const original = document.body.style.overflow;
  document.body.style.overflow = "hidden";
  return () => { document.body.style.overflow = original; };
}, [isOpen]);
```

`overflow: hidden` on body causes a layout shift when the scrollbar disappears. `scrollbar-gutter: stable` on `html` reserves the space permanently and avoids it.

iOS Safari ignores body overflow locking in several cases, which is why libraries like `body-scroll-lock` exist. `<dialog>` handles this natively.

## Other uses

**Tooltips and popovers** that must escape `overflow: hidden`.

**Toast notifications** rendered into a fixed container while triggered from anywhere in the tree.

**Rendering into an iframe or a canvas overlay** in an editor.

**Third-party widget mount points** — rendering React into a container owned by another library.

## How senior engineers actually use this

**They reach for `<dialog>` and the Popover API first**, and use portals only when the requirement is specific DOM placement rather than top-layer rendering.

**They use a dedicated portal root**, not `document.body`.

**They implement focus management deliberately** — or use a headless library (Radix, React Aria) that has done it correctly.

**They remember events bubble through the React tree** when debugging outside-click handlers.

**They test with a keyboard**, since portalled overlays are where focus bugs concentrate.

## Common pitfalls

- Outside-click handlers treating portal content as outside.
- The opening click immediately closing the modal via a `document` listener.
- No focus trap, letting Tab escape behind the overlay.
- Focus not returned to the trigger on close.
- Missing `role="dialog"` and `aria-modal`.
- `document` accessed during SSR.
- Body scroll lock causing layout shift, or failing on iOS.
- Reaching for a portal when `<dialog>` would do everything.

## Interview angle

"What are portals and when would you use them" wants: rendering into a different DOM node while staying in the React tree, to escape `overflow: hidden` and stacking contexts. The detail that distinguishes a strong answer is that events still bubble through the React tree rather than the DOM tree — with the outside-click consequence — and that `<dialog>` with `showModal()` renders in the top layer and now covers most modal use cases natively, including focus trapping.
