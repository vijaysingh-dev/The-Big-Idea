# Salesforce Platform Architecture End to End

## The purpose of this note

Everything in section 01 has been a separate piece. This note assembles them by following one request from a user's click to the database and back, naming what happens at each step and where in this course it is covered properly.

Treat this as a map. You are not expected to understand every step yet.

## The scenario

A support agent in the Mumbai office opens a Case, changes its Status to "Escalated", and clicks Save. Behind the scenes this must notify an engineering team, update a related Account field, and respect a rule that only senior agents may escalate certain case types.

## Step 1: The request arrives

The browser sends the save request to the org's My Domain URL. Salesforce resolves which **instance** hosts this org and routes it to an application server there.

The **session** is validated. Salesforce checks the session is live, has not expired, and satisfies the org's login policies — IP ranges, login hours, multi-factor authentication, session timeout. See [[03.14 - Login Policies, MFA and Session Security]].

At this point the platform knows the **running user**, which determines everything that follows.

## Step 2: Object and field permissions

Before anything touches data, the platform checks whether this user may edit the Case object at all, and whether they may edit each field being changed.

These come from the user's **profile** and their **permission sets**, combined additively — a permission granted anywhere is granted. Object permissions ([[03.5 - Object Level Security - CRUD]]) and field permissions ([[03.6 - Field Level Security]]) are separate checks, and failing either stops the save with a permission error.

## Step 3: Record access

Permission to edit Cases in general is not permission to edit *this* Case. Record-level access is evaluated from a stack of rules:

organization-wide defaults, then role hierarchy, then sharing rules, then manual and team shares, then implicit sharing. Access is additive and cannot be reduced by a later rule. See [[03.7 - Organization-Wide Defaults]] through [[03.10 - Manual, Team and Implicit Sharing]].

The platform does not compute this on the fly. Access has been materialized into share tables in advance, which is why sharing changes trigger expensive background recalculation ([[23.3 - Sharing at Scale and Sharing Recalculation]]).

## Step 4: The save pipeline begins

Now the record enters the **order of execution** — a fixed sequence of roughly twenty steps that runs on every save. The sequence never changes and is the most important thing to know on this platform. Full treatment in [[07.13 - Order of Execution]]. The shape of it:

1. The record is loaded from the database
2. New values from the request overwrite the old ones
3. System validation runs — required fields, field types, field length
4. **Before-save record-triggered flows** run
5. **Before triggers** run
6. System validation runs again, and custom **validation rules** run
7. The record is saved to the database, but **not committed**
8. **After triggers** run
9. **Assignment rules**, auto-response rules, and workflow field updates run
10. **After-save record-triggered flows** and processes run
11. **Escalation rules** run
12. **Roll-up summary fields** on parent records recalculate, which can cascade the parent through its own save pipeline
13. Criteria-based sharing is recalculated
14. Everything is **committed**, and post-commit logic such as sending email and publishing platform events runs

Two details in that list explain an enormous amount of confusing platform behaviour. Nothing is committed until step 14, so an exception anywhere rolls the whole thing back. And step 12 can recursively re-enter the pipeline for a parent record, which is how a single update quietly becomes a cascade.

## Step 5: Your code runs

In our scenario, a trigger on Case fires. The trigger itself does nothing but route:

```java
trigger CaseTrigger on Case (before update, after update) {
    CaseTriggerHandler.run();
}
```

The handler dispatches by event:

```java
public with sharing class CaseTriggerHandler {

    public static void run() {
        if (Trigger.isBefore && Trigger.isUpdate) {
            CaseEscalationService.validateEscalationAuthority(Trigger.new, Trigger.oldMap);
        }
        if (Trigger.isAfter && Trigger.isUpdate) {
            CaseEscalationService.handleNewlyEscalated(Trigger.new, Trigger.oldMap);
        }
    }
}
```

The service holds the logic, takes collections, and never reads `Trigger` context itself:

```java
public with sharing class CaseEscalationService {

    public static void handleNewlyEscalated(List<Case> newCases, Map<Id, Case> oldCases) {
        Set<Id> accountIds = new Set<Id>();
        List<Case> escalated = new List<Case>();

        for (Case c : newCases) {
            if (c.Status == 'Escalated' && oldCases.get(c.Id).Status != 'Escalated') {
                escalated.add(c);
                if (c.AccountId != null) {
                    accountIds.add(c.AccountId);
                }
            }
        }

        if (escalated.isEmpty()) {
            return;
        }

        Map<Id, Account> accounts = new Map<Id, Account>([
            SELECT Id, Open_Escalations__c FROM Account WHERE Id IN :accountIds
        ]);

        for (Case c : escalated) {
            Account acc = accounts.get(c.AccountId);
            if (acc != null) {
                acc.Open_Escalations__c = (acc.Open_Escalations__c == null ? 0 : acc.Open_Escalations__c) + 1;
            }
        }
        update accounts.values();

        // notification is published rather than called directly, keeping the callout outside this transaction
        EventBus.publish(buildEscalationEvents(escalated));
    }
}
```

Three things in there reflect everything section 01 has established. The code is bulkified because governor limits are per transaction ([[01.5 - Multi-Tenant Architecture]]). The class is `with sharing` so it respects the record access from step 3. The external notification goes through a platform event rather than an HTTP callout, because callouts are not permitted after DML in the same transaction — a rule that exists to stop long-running requests holding open database transactions on shared servers.

## Step 6: Governor limits are counted throughout

Every query, DML statement, CPU millisecond, and byte of heap used by *all* of it — your trigger, other triggers, flows, validation rules, managed packages — draws from one shared budget for this transaction. Cross a limit and the whole transaction fails and rolls back. See section 16.

## Step 7: Commit and post-commit work

The transaction commits. The platform event published earlier is delivered to its subscribers, which run in their own separate transactions with their own fresh limits. A subscriber makes the HTTP callout to the engineering system, safely outside the user's save. See [[12.8 - Platform Events]].

## Step 8: The response

The record page re-renders. Lightning Data Service refreshes the cached record, related components update, and the agent sees the saved state. See [[14.12 - Lightning Data Service and Record Forms]].

Elapsed time: a few hundred milliseconds, assuming nothing in the org's accumulated automation is slow.

## What this trace is meant to teach

**Security is not a layer you add.** It runs before your code and is not optional. Code that ignores sharing and permissions is not simpler, it is wrong.

**Your code is a guest in a pipeline you do not control.** The order of execution runs regardless. Your trigger occupies one slot in it, alongside automation written by other people and by installed packages.

**Limits are shared and cumulative.** Perfectly written code can still fail because of what ran before it. This is why orgs consolidate automation and audit what fires on hot objects.

**Transactions are all-or-nothing until commit.** This is a strength — no half-saved records — and a constraint, because one failure anywhere destroys all the work.

**Async is the escape hatch, and it exists for a reason.** Callouts, heavy processing, and anything that would hold the transaction open get pushed out of it. Learning which tool to use, and when, is most of section 12.

## Section 01 in one paragraph

Salesforce is a multi-tenant platform that is both a finished CRM application and a place to build your own applications. Because it is multi-tenant, your code runs under hard per-transaction limits, on shared infrastructure that upgrades three times a year, with no servers, filesystem, or threads of your own. Configuration is metadata that deploys between orgs, and records are data that does not. Every save runs through a fixed pipeline of security checks and automation that you extend rather than replace. Everything in the rest of this course is a detail of one of those facts.
