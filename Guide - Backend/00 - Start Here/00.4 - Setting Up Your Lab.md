# Setting Up Your Lab

#backend #tooling #setup

> **In one line:** You cannot learn backend engineering by reading about it. You need a machine where you can start things, break things, and watch what happens.

---

## What a Lab Is For

Almost every important lesson in this vault comes from **watching something misbehave**. Not from a diagram — from your own terminal.

You need to be able to, on demand:

- Start Postgres, Redis, Kafka and a load balancer in 30 seconds
- Send 10,000 requests per second at your own service
- Watch raw packets go past
- Add 300ms of latency to a dependency
- Kill a process mid-operation and see what survived

If any of those takes more than a minute of setup, you will skip it, and skipping it is where learning stops.

---

## The Stack

One `docker-compose.yml` that has everything. You will use it all year.

```yaml
name: lab

services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: lab
      POSTGRES_DB: lab
    ports: ["5432:5432"]
    command: >
      postgres
      -c shared_preload_libraries=pg_stat_statements
      -c pg_stat_statements.track=all
      -c log_min_duration_statement=100
      -c log_lock_waits=on
      -c wal_level=logical
    volumes:
      - pgdata:/var/lib/postgresql/data

  pgbouncer:
    image: edoburu/pgbouncer:latest
    environment:
      DB_HOST: postgres
      DB_USER: postgres
      DB_PASSWORD: lab
      POOL_MODE: transaction
      MAX_CLIENT_CONN: 1000
      DEFAULT_POOL_SIZE: 20
    ports: ["6432:5432"]
    depends_on: [postgres]

  redis:
    image: redis:7
    ports: ["6379:6379"]
    command: >
      redis-server
      --maxmemory 256mb
      --maxmemory-policy allkeys-lru
      --appendonly yes

  kafka:
    image: apache/kafka:latest
    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1

  jaeger:
    image: jaegertracing/all-in-one:latest
    ports: ["16686:16686", "4317:4317", "4318:4318"]
    environment:
      COLLECTOR_OTLP_ENABLED: "true"

  prometheus:
    image: prom/prometheus:latest
    ports: ["9090:9090"]
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro

  grafana:
    image: grafana/grafana:latest
    ports: ["3000:3000"]
    environment:
      GF_AUTH_ANONYMOUS_ENABLED: "true"
      GF_AUTH_ANONYMOUS_ORG_ROLE: Admin

  toxiproxy:
    image: ghcr.io/shopify/toxiproxy:latest
    ports: ["8474:8474", "15432:15432", "16379:16379"]

volumes:
  pgdata:
```

💡 **The two non-obvious services here are `pgbouncer` and `toxiproxy`.** Most people never install them and it costs them years. Toxiproxy sits between your app and a dependency and lets you inject latency, packet loss and disconnects on demand. It is how you test failure without waiting for a real outage.

Postgres is started with logging settings that matter: slow queries over 100ms are logged, lock waits are logged, and `wal_level=logical` means CDC will work in phase 5 without reconfiguring.

## Command Line Tools

Install these once. Grouped by what they answer.

### "What is my service doing?"

| Tool | Use |
|---|---|
| **py-spy** | Sample a running Python process without stopping it. `py-spy top --pid X` |
| **htop** | CPU and memory per process |
| **hyperfine** | Benchmark a command properly, with warmup and statistics |

```bash
pip install py-spy
brew install htop hyperfine        # or apt install
```

⚠️ **py-spy is the single most valuable tool on this list.** It attaches to a *running production process* and shows you where time is going, with no code change and no restart. Learn it now, not during an incident.

### "What is on the network?"

| Tool | Use |
|---|---|
| **tcpdump** | Capture packets on the command line |
| **Wireshark** | Read those captures with a UI |
| **ss** | Socket states. Replaces `netstat` |
| **mitmproxy** | Intercept and read HTTP/HTTPS traffic from your own app |
| **curl** | With `-v`, `--http2`, `--trace-time` it becomes a protocol debugger |

```bash
brew install wireshark mitmproxy
```

### "What is the database doing?"

| Tool | Use |
|---|---|
| **pgcli** | Postgres shell with autocomplete and syntax highlighting |
| **pgbadger** | Turns Postgres logs into an HTML report of your worst queries |
| **pg_stat_statements** | Already enabled in the compose file above. Query it directly |

```bash
pip install pgcli
```

### "How much can it take?"

| Tool | Use |
|---|---|
| **k6** | Load testing. Scripts are JavaScript, output is good, scales well |
| **vegeta** | Simpler constant-rate HTTP load. Great for quick checks |
| **wrk** | Fastest for raw HTTP throughput numbers |

```bash
brew install k6 vegeta wrk
```

k6 is the one used throughout Conduit. Learn it properly.

### "What is Redis / Kafka doing?"

```bash
# Redis: watch every command as it arrives — do not run in prod
redis-cli monitor

# Redis: what is slow?
redis-cli slowlog get 10

# Redis: memory breakdown by key pattern
redis-cli --bigkeys

# Kafka: consumer group lag
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --all-groups
```

## Verify Everything Works

Run this before you start section 01. It should print all green.

```bash
#!/usr/bin/env bash
# lab/verify.sh
set -u

check() {
  printf "%-16s" "$1"
  if eval "$2" >/dev/null 2>&1; then echo "OK"; else echo "MISSING"; fi
}

docker compose up -d
sleep 10

check "postgres"   "docker compose exec -T postgres pg_isready"
check "pgbouncer"  "psql postgresql://postgres:lab@localhost:6432/lab -c 'select 1'"
check "redis"      "redis-cli ping"
check "kafka"      "docker compose exec -T kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list"
check "jaeger"     "curl -sf localhost:16686"
check "prometheus" "curl -sf localhost:9090/-/healthy"
check "toxiproxy"  "curl -sf localhost:8474/version"
check "py-spy"     "py-spy --version"
check "k6"         "k6 version"
check "tcpdump"    "which tcpdump"
check "pgcli"      "pgcli --version"
```

## Your First Failure Injection

Do this now. It takes three minutes and it changes how you think.

```bash
# Point toxiproxy at postgres
curl -X POST localhost:8474/proxies -d '{
  "name": "pg",
  "listen": "0.0.0.0:15432",
  "upstream": "postgres:5432"
}'

# Connect through it — normal speed
time psql postgresql://postgres:lab@localhost:15432/lab -c "select 1"

# Now add 500ms of latency in each direction
curl -X POST localhost:8474/proxies/pg/toxics -d '{
  "type": "latency",
  "attributes": {"latency": 500}
}'

time psql postgresql://postgres:lab@localhost:15432/lab -c "select 1"

# Now cut the connection entirely
curl -X POST localhost:8474/proxies/pg -d '{"enabled": false}'
```

💡 The point is not the latency number. The point is that **you now have a switch that makes any dependency slow or dead, on demand.** Every reliability lesson in section 11 depends on having this switch.

## Exercise

**Drill 0.2 — The lab, committed**

```
study/lab/
├── docker-compose.yml
├── prometheus.yml
├── verify.sh
├── toxics.sh            # helper: add/remove latency, drops, disconnects
├── Makefile             # up, down, reset, toxic-slow, toxic-dead
└── README.md            # every command you will forget in a month
```

The `Makefile` matters more than it looks. If breaking a dependency is `make toxic-slow` instead of a curl you have to look up, you will actually do it during experiments. If it is not, you will not.

**Done when:** `make up && ./verify.sh` prints all OK from a clean machine, `make toxic-slow` makes Postgres take 500ms, and `make toxic-dead` makes it refuse connections.
