# AppExchange Security Review

## What it is

Salesforce reviews every application listed on AppExchange before it can be distributed, and again periodically afterwards.

**It is not a formality.** Reviews take weeks, rejections are common, and a rejection costs a release cycle.

**Why a non-ISV should care:** the review's criteria are the platform's security standards, written down. An org that codes to them is more secure than one that does not, whether or not anything is being listed.

## The process

```
1. Register the package and namespace
2. Build and promote a version
3. Run the self-assessment
4. Submit for review
5. Salesforce reviews — typically several weeks
6. Findings returned, if any
7. Remediate and resubmit
8. Pass, and list
9. Re-review periodically, and on major changes
```

**The self-assessment questionnaire** covers architecture, data flows, external services, and authentication. Answering it honestly and completely shortens the review; answering it vaguely lengthens it.

**Every external service the package calls must be declared**, along with what data is sent. An undeclared endpoint discovered during review is a serious finding.

## What is reviewed

Not only Apex.

```
Apex and Visualforce         injection, access control, escaping
Lightning components         XSS, CSRF, data exposure
JavaScript libraries         known vulnerabilities
External services            TLS, authentication, data handling
The application itself       if there is a hosted component
Authentication flows         OAuth implementation, token handling
Data storage                 what is stored, where, and how
```

**A hosted component is reviewed too.** A package calling your own web service means that service is in scope — its TLS configuration, its authentication, and its own vulnerabilities.

## The findings that recur

Ordered roughly by frequency.

**Missing sharing declarations.**

```java
public class ClaimController { }                  // finding
public with sharing class ClaimController { }     // correct
```

**A class with no keyword runs without sharing when it is the entry point.** Every class needs an explicit declaration.

**Missing CRUD and field-level security enforcement.**

```java
// Finding
return [SELECT Id, Claim_Amount__c FROM Warranty_Claim__c WHERE Account__c = :accountId];

// Correct
return [
    SELECT Id, Claim_Amount__c FROM Warranty_Claim__c
    WHERE Account__c = :accountId
    WITH USER_MODE
];
```

**And on the write path:**

```java
SObjectAccessDecision decision = Security.stripInaccessible(
    AccessType.UPSERTABLE, incomingRecords
);
upsert as user decision.getRecords();
```

**SOQL injection.**

```java
// Finding
String query = 'SELECT Id FROM Warranty_Claim__c WHERE Status__c = \'' + status + '\'';

// Correct
List<SObject> results = Database.queryWithBinds(
    'SELECT Id FROM Warranty_Claim__c WHERE Status__c = :status',
    new Map<String, Object>{ 'status' => status },
    AccessLevel.USER_MODE
);
```

**Field and object names cannot be bound** — an allowlist is the only defence there. See [[22.5 - Secure Apex Coding and OWASP on Platform]].

**Cross-site scripting.**

```html
<!-- Finding -->
<apex:outputText value="{!userInput}" escape="false"/>
```

```javascript
// Finding
this.template.querySelector('.output').innerHTML = userInput;
```

**Hardcoded credentials, endpoints, or Ids.**

```java
// Finding
req.setEndpoint('https://api.northwind.com/v2/claims');
req.setHeader('Authorization', 'Bearer sk_live_4f3a2b91c8d7');

// Correct
req.setEndpoint('callout:ERP_System/api/v2/claims');
```

**Insecure endpoints.** `http://` rather than `https://` is an automatic finding.

**Storing secrets in custom settings or metadata.** Both are queryable; Named Credentials are the answer. See [[13.13 - Named Credentials and External Credentials]].

**CSRF on state-changing operations.** A Visualforce page performing DML in a page action.

**Vulnerable JavaScript libraries.** RetireJS flags known-vulnerable versions, and a three-year-old bundled library is a finding.

## Running the checks yourself

```bash
sf scanner run --target force-app --severity-threshold 3 --format table
sf scanner run dfa --target force-app --projectdir force-app --format table
```

**The Graph Engine is the one that matters most here.** It traces user-supplied data across method calls into a dynamic query, which is the injection finding that PMD misses and the review does not.

```java
@AuraEnabled
public static List<Warranty_Claim__c> search(String field, String value) {
    return ClaimSelector.dynamicSearch(field, value);
}
```

```java
public static List<Warranty_Claim__c> dynamicSearch(String field, String value) {
    // three method calls from an @AuraEnabled parameter — PMD sees a concatenation,
    // the Graph Engine sees an injection path from an entry point
    return Database.query('SELECT Id FROM Warranty_Claim__c WHERE ' + field + ' = \'' + value + '\'');
}
```

**Run it before submitting.** A finding caught locally costs an hour; the same finding in a review costs a cycle.

**Also run:**

```bash
npm audit
sf scanner run --target force-app --engine retire-js
```

for the JavaScript dependency findings.

See [[21.9 - Static Analysis, PMD and Code Review]].

## Justifying an exception

Some findings are false positives or deliberate design decisions. The review accepts justifications; it does not accept silence.

```java
public with sharing class ClaimReportingService {

    public static Decimal totalExposureForAccount(Id accountId) {
        // Deliberately elevated: the aggregate is authorized for account managers,
        // while the individual claims are not visible to them. The account Id is
        // verified against the running user's entitlement above.
        return new ElevatedAggregates().sumClaimAmounts(accountId);
    }

    private without sharing class ElevatedAggregates {
        private Decimal sumClaimAmounts(Id accountId) { }
    }
}
```

**The pattern that passes review:**

**Scope the elevation narrowly** — an inner class, not the whole service.

**Comment the reason** in the code, not only in the submission.

**Verify entitlement before elevating**, so the elevation is bounded.

**Document it in the self-assessment.**

A `without sharing` class with no explanation is a finding. The same class with a stated reason and a bounded scope is usually accepted.

## The design decisions that shape a review

Made early, and expensive to change late.

**Named Credentials from the start.** Retrofitting them across a codebase where endpoints are in custom settings is a project, and every one of those credentials must be rotated because they have been readable.

**`with sharing` as the default**, with `inherited sharing` on utilities.

**`WITH USER_MODE` in the selector layer**, so callers cannot forget it. That single architectural decision removes an entire finding category. See [[18.5 - Selector Layer]].

**Protected custom metadata** for internal configuration, so subscribers cannot alter the package's behaviour in ways it does not expect. See [[17.1 - Custom Metadata Types]].

**A minimal `global` surface.** Everything global is permanent and is reviewed; a small facade is both better design and less to defend. See [[21.6 - Managed Packages and ISV Basics]].

**No personal data in logs**, which is checked.

## The re-review

Passing once is not permanent.

```
Periodic re-review          on a cycle Salesforce sets
On major version changes
On new external services
On changes to the authentication model
```

**A package that has drifted since its first review fails the second.** Keeping the standards as development practice rather than as a submission exercise is what makes re-review uneventful.

**Running the scanner in CI** is the mechanism. A gate at severity 3 means the codebase cannot drift below the standard between reviews. See [[21.8 - CI-CD Pipelines]].

## Timelines

```
First submission        several weeks, longer for a complex package
Remediation             your time
Resubmission            a further review cycle
```

**Plan for at least one rejection** on a first submission. Budgeting a single review cycle is optimistic, and the schedule pressure that follows produces rushed remediation.

**Submitting early**, before the application is complete, is not possible — the review is of the actual package.

## What the review does not check

Worth knowing, because passing does not mean secure.

**Business logic authorization.** The review checks that sharing is enforced; it cannot know whether your approval logic lets the wrong person approve.

**Data model design.** An object with no sharing model at all passes if the code enforces what exists.

**Operational security.** How your own team accesses subscriber orgs, how support access is managed.

**Whether the application does what it claims.**

**Passing the review is a floor**, not a certification of security.

## A pre-submission checklist

```
Code
  [ ] Sharing keyword on every class
  [ ] WITH USER_MODE on every query
  [ ] as user on every DML
  [ ] stripInaccessible on inbound sObjects
  [ ] Bind variables everywhere; allowlists for identifiers
  [ ] No escape="false" or innerHTML with user content
  [ ] No hardcoded credentials, endpoints, or Ids
  [ ] Named Credentials for every callout
  [ ] https:// only
  [ ] No personal data in logs

Analysis
  [ ] sf scanner run at severity 3, clean
  [ ] sf scanner run dfa, clean
  [ ] npm audit clean, dependencies current

Package
  [ ] Global surface minimal and deliberate
  [ ] Protected metadata for internal configuration
  [ ] Tests fast — they run on every install
  [ ] Tested on Professional Edition

Submission
  [ ] Self-assessment complete and accurate
  [ ] Every external service declared
  [ ] Every exception justified in code and in the submission
```

## Practical guidance

**Code to the review's standards from the start**, not before submission.

**Run the Graph Engine**, not just PMD — the injection findings it catches are the ones that fail reviews.

**Named Credentials from day one.** Retrofitting means rotating every credential.

**Put `WITH USER_MODE` in the selector layer**, so it cannot be forgotten.

**Justify exceptions in code and in the submission**, with narrow scope.

**Budget for at least one rejection.**

**Gate the scanner in CI**, so the codebase cannot drift between reviews.

**Remember passing is a floor**, not a security certification.
