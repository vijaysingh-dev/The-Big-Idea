# Function Calling and Structured Outputs Deep Dive

## What It Is

Function calling (also called tool use) is the mechanism by which an LLM outputs a structured description of a function it wants invoked, including the function name and arguments. Structured outputs is the broader capability of constraining LLM output to conform to a schema — whether for tool calls, data extraction, classification, or any other case where downstream code needs parseable output.

These two capabilities are the foundation of every agent system and most production AI integrations. Getting them wrong means brittle parsing, silent data corruption, and agents that fail non-deterministically.

---

## Why It Matters

- Every agent system in your target companies runs on tool use. Understanding the full call-execute-observe loop, parallel tool calls, retry semantics, and schema design is table stakes.
- Structured output failures are among the most common production bugs — the model returns valid JSON but with the wrong field names, or returns a string where a number is expected, or truncates a required field.
- Parallel tool calls can reduce agent latency by 3-5× when multiple independent tools are needed — but require careful result fan-in.
- Schema design directly affects model performance: overly complex schemas degrade tool selection accuracy significantly.

---

## The Tool Call Protocol

### Full Request-Response Cycle

```
1. Client sends: messages + tools definition
   ↓
2. Model decides: answer directly OR call tool(s)
   ↓
3. If tool call: model returns ToolUse blocks (NOT a text response)
   ↓
4. Client executes tools, collects results
   ↓
5. Client sends: original messages + assistant ToolUse + ToolResult blocks
   ↓
6. Model generates: final response using tool results
```

### OpenAI Protocol

```python
import json, openai

client = openai.OpenAI()

# Step 1: Define tools
tools = [
    {
        "type": "function",
        "function": {
            "name": "search_documents",
            "description": "Search the internal knowledge base for relevant documents. "
                           "Use when the question requires company-specific information, "
                           "policies, or data not available in your training.",
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "Natural language search query. Be specific."
                    },
                    "date_filter": {
                        "type": "string",
                        "description": "Optional ISO date (YYYY-MM-DD). Only return docs after this date.",
                    },
                    "source_filter": {
                        "type": "string",
                        "enum": ["confluence", "github", "slack", "all"],
                        "description": "Filter by source system. Default: all",
                    }
                },
                "required": ["query"],
                "additionalProperties": False,
            }
        }
    }
]

# Step 2: First call
messages = [{"role": "user", "content": "What's our parental leave policy?"}]
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    tools=tools,
    tool_choice="auto",  # "auto" | "required" | "none" | {"type":"function","function":{"name":"..."}}
)

# Step 3: Check if model wants to call tools
message = response.choices[0].message
messages.append(message)  # append assistant message to history

if message.tool_calls:
    for tool_call in message.tool_calls:
        # Step 4: Execute the tool
        args = json.loads(tool_call.function.arguments)
        result = execute_tool(tool_call.function.name, args)

        # Step 5: Append tool result
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(result),
        })

    # Step 6: Final response
    final = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools,
    )
    print(final.choices[0].message.content)
```

### Anthropic Protocol

```python
import anthropic

client = anthropic.Anthropic()

tools = [
    {
        "name": "search_documents",
        "description": "Search the internal knowledge base...",
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {"type": "string"},
                "date_filter": {"type": "string"},
            },
            "required": ["query"],
        }
    }
]

# First call
response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    tools=tools,
    messages=[{"role": "user", "content": "What's our parental leave policy?"}],
)

if response.stop_reason == "tool_use":
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            result = execute_tool(block.name, block.input)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": json.dumps(result),
            })

    # Second call with results
    final = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=1024,
        tools=tools,
        messages=[
            {"role": "user", "content": "What's our parental leave policy?"},
            {"role": "assistant", "content": response.content},
            {"role": "user", "content": tool_results},
        ],
    )
```

## Parallel Tool Calls

Modern models (GPT-4o, Claude 3.5+) can request multiple tool calls in a single response. This is essential for agent performance.

```python
# Model may return multiple tool calls in one response
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{
        "role": "user",
        "content": "Compare Apple and Microsoft's Q3 2024 revenue"
    }],
    tools=tools,
    parallel_tool_calls=True,  # OpenAI: explicitly enable (default True)
)

# Response might contain:
# tool_calls = [
#   ToolCall(id="call_abc", function=Function(name="search_documents",
#            arguments='{"query": "Apple Q3 2024 revenue"}')),
#   ToolCall(id="call_xyz", function=Function(name="search_documents",
#            arguments='{"query": "Microsoft Q3 2024 revenue"}')),
# ]

# Execute in parallel (CRITICAL for latency)
import asyncio

async def execute_all_tool_calls(tool_calls):
    tasks = []
    for tc in tool_calls:
        args = json.loads(tc.function.arguments)
        tasks.append(asyncio.create_task(
            async_execute_tool(tc.function.name, args)
        ))
    results = await asyncio.gather(*tasks)
    return list(zip(tool_calls, results))

tool_results = asyncio.run(execute_all_tool_calls(message.tool_calls))

# Append ALL results before the next model call
for tool_call, result in tool_results:
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": json.dumps(result),
    })
```

**Common mistake**: Executing parallel tool calls sequentially. If each call takes 500ms and you have 3 calls, sequential = 1500ms, parallel = 500ms.

**Critical protocol requirement**: You must return results for ALL tool calls from a response before calling the model again. Returning partial results (e.g., only the first of three) causes model confusion or API errors.

## Tool Schema Design

Schema quality directly affects how reliably models select and invoke tools. This is empirically measurable — poor schemas cause wrong tool selection and malformed arguments.

### Principles

**1. Description is the most important field**

The model reads the description to decide *when* to use the tool. Function names alone are not enough.

```python
# BAD: ambiguous description
{
    "name": "get_data",
    "description": "Gets data",  # useless
}

# GOOD: explains when and why to use it
{
    "name": "search_financial_reports",
    "description": "Search SEC filings, earnings reports, and investor presentations. "
                   "Use when the question requires specific financial figures, earnings results, "
                   "guidance, or regulatory disclosures. Do NOT use for general market knowledge.",
}
```

**2. Enumerate valid values with `enum`**

```python
# BAD: free text for constrained input
{"name": "source", "type": "string", "description": "The data source"}

# GOOD: enum prevents hallucinated values
{"name": "source", "type": "string",
 "enum": ["bloomberg", "reuters", "sec_edgar", "internal"],
 "description": "Data source to query"}
```

**3. `additionalProperties: false` prevents schema drift**

```python
"parameters": {
    "type": "object",
    "properties": {...},
    "required": ["query"],
    "additionalProperties": False,  # model can't invent extra fields
}
```

**4. Fewer tools, better selection**

Tool selection accuracy degrades with more tools. Benchmark data from various studies:

```
5 tools:  ~97% correct selection
10 tools: ~92% correct selection
20 tools: ~83% correct selection
50 tools: ~65% correct selection
```

If you have many tools, use two-stage selection: first retrieve relevant tools from a tool registry (semantic search over tool descriptions), then pass only the relevant subset to the model.

```python
def get_relevant_tools(query: str, all_tools: list[dict], top_k: int = 5) -> list[dict]:
    """Select the k most relevant tools for this query using embedding similarity."""
    query_emb = embedding_model.encode(query)
    tool_embs = [embedding_model.encode(t["function"]["description"]) for t in all_tools]

    scores = [cosine_similarity(query_emb, e) for e in tool_embs]
    top_indices = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)[:top_k]
    return [all_tools[i] for i in top_indices]
```

**5. Separate read vs write tools clearly**

Write tools (create, update, delete) should have explicit confirmation mechanisms. Make this visible in the description:

```python
{
    "name": "create_jira_ticket",
    "description": "Creates a new Jira ticket. IMPORTANT: This action is irreversible "
                   "and immediately creates a visible ticket. Only call when explicitly "
                   "asked to create a ticket, not just to note or remember something.",
}
```

## Structured Outputs (Non-Tool Use)

For data extraction, classification, and any case where you need parseable output without the tool call protocol.

### OpenAI Structured Outputs (Constrained Decoding)

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional
from openai import OpenAI

client = OpenAI()

class EarningsExtraction(BaseModel):
    company_name: str
    fiscal_period: str = Field(description="e.g., 'Q3 2024'")
    revenue_usd_millions: Optional[float] = Field(
        description="Total revenue in USD millions. None if not mentioned."
    )
    revenue_growth_yoy_pct: Optional[float] = Field(
        description="YoY revenue growth as percentage. None if not mentioned."
    )
    sentiment: Literal["positive", "negative", "mixed", "neutral"]
    key_risks: list[str] = Field(description="Up to 3 key risks mentioned")

response = client.beta.chat.completions.parse(
    model="gpt-4o-2024-08-06",  # structured outputs requires this version or later
    messages=[
        {"role": "system", "content": "Extract financial data from earnings reports."},
        {"role": "user", "content": earnings_text},
    ],
    response_format=EarningsExtraction,
)

result: EarningsExtraction = response.choices[0].message.parsed
# Type-safe — result.revenue_usd_millions is float | None, never a string
print(f"Revenue: ${result.revenue_usd_millions}M ({result.revenue_growth_yoy_pct:+.1f}% YoY)")
```

**How constrained decoding works**: The model's token sampling is masked at each step to only allow tokens that would produce valid output for the current schema state. Guarantees syntactic validity but NOT semantic correctness (model can still put wrong values in correct-type fields).

### Anthropic Tool-for-Structured-Output Pattern

Anthropic doesn't have a `response_format` parameter. The idiomatic pattern is to define a single tool and force its use:

```python
response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    tools=[{
        "name": "submit_extraction",
        "description": "Submit the extracted financial data",
        "input_schema": EarningsExtraction.model_json_schema(),
    }],
    tool_choice={"type": "tool", "name": "submit_extraction"},  # force this tool
    messages=[{"role": "user", "content": earnings_text}],
)

tool_use = next(b for b in response.content if b.type == "tool_use")
result = EarningsExtraction(**tool_use.input)
```

### Instructor Library (Cross-Provider)

The `instructor` library provides a unified structured output API across OpenAI, Anthropic, Gemini, and local models:

```python
import instructor
from anthropic import Anthropic

# Patch any client
client = instructor.from_anthropic(Anthropic())

# Same Pydantic model, works across providers
result = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    response_model=EarningsExtraction,
    messages=[{"role": "user", "content": earnings_text}],
)
# result is already typed as EarningsExtraction
```

## Retry and Failure Handling

### Schema Validation Failure Recovery

```python
import instructor
from pydantic import ValidationError

client = instructor.from_openai(openai.OpenAI())

def extract_with_retry(text: str, model_class, max_retries: int = 3):
    """instructor handles retries automatically on ValidationError."""
    return client.chat.completions.create(
        model="gpt-4o",
        response_model=model_class,
        max_retries=max_retries,  # instructor retries with validation error context
        messages=[{"role": "user", "content": text}],
    )
    # On ValidationError, instructor sends the error back to the model:
    # "Your response failed validation: field 'revenue' must be a number, got 'N/A'
    #  Please fix and respond again."
```

### Tool Execution Failure Recovery

When a tool fails, pass the error back as the tool result so the model can adapt:

```python
def execute_tool_safe(tool_name: str, args: dict) -> str:
    try:
        result = tool_registry[tool_name](**args)
        return json.dumps({"success": True, "result": result})
    except ToolNotFoundError:
        return json.dumps({"success": False, "error": f"Tool '{tool_name}' not available"})
    except InvalidArgumentError as e:
        return json.dumps({"success": False, "error": f"Invalid argument: {e}",
                          "hint": "Check the tool's parameter requirements"})
    except RateLimitError:
        return json.dumps({"success": False, "error": "Rate limit reached. Try again in 30 seconds."})
    except Exception as e:
        return json.dumps({"success": False, "error": f"Execution failed: {str(e)}"})
```

The model receives the error string as its observation and will typically adapt — try different arguments, use a different tool, or acknowledge the limitation.

### Infinite Loop Prevention

```python
MAX_TOOL_CALL_ROUNDS = 10

async def run_agent(messages, tools, llm):
    for round_num in range(MAX_TOOL_CALL_ROUNDS):
        response = await llm.call(messages=messages, tools=tools)
        messages.append(response.message)

        if not response.message.tool_calls:
            return response.message.content  # Done

        # Execute tools and append results
        tool_results = await execute_all_tools(response.message.tool_calls)
        messages.extend(tool_results)

    # Hit round limit — force conclusion
    messages.append({
        "role": "system",
        "content": "You have used the maximum number of tool calls. "
                   "Please provide your best answer with the information gathered so far."
    })
    final = await llm.call(messages=messages, tools=[])  # no tools → forces text response
    return final.message.content
```

## Failure Modes

### 1. Hallucinated Tool Names

Model invents a tool name not in the provided list.

**Cause**: Tool descriptions are too similar; model confuses them. Or model was fine-tuned on different tool names.

**Fix**: Validate tool_name against your registry before execution. Return error if not found.

```python
if tool_call.function.name not in tool_registry:
    # Return error rather than executing
    return json.dumps({"error": f"Unknown tool: {tool_call.function.name}. Available: {list(tool_registry.keys())}"})
```

### 2. Argument Type Mismatch

Model passes `"$85.8B"` for a field typed as `float`.

**Cause**: Ambiguous field descriptions, or model predicts likely human-readable format rather than machine-readable.

**Fix**: Be explicit in descriptions. Use `enum` for constrained values. Use instructor's auto-retry.

```python
# BAD
"revenue": {"type": "number", "description": "Revenue"}

# GOOD
"revenue_usd_millions": {
    "type": "number",
    "description": "Revenue as a plain decimal number in millions USD. "
                   "Example: 85800 for $85.8B. No currency symbols or text."
}
```

### 3. Missing Required Fields

Model omits a required field, returning `null` or omitting it entirely.

**Cause**: Information not present in context; model uncertain.

**Fix**: Use `Optional` with explicit null semantics. Tell the model explicitly what to do when information is absent.

```python
class Extraction(BaseModel):
    revenue: Optional[float] = Field(
        description="Revenue in USD millions. Set to null if not mentioned in the text."
    )
```

### 4. Nested Schema Complexity

Models make more errors with deeply nested schemas.

**Fix**: Flatten schemas where possible. For complex extractions, use a two-step process: rough extraction first, structured formatting second.

```python
# Step 1: Extract as free text
raw = llm.call("Extract all financial metrics from this text: " + doc)

# Step 2: Parse free text into schema (simpler task for the model)
structured = client.beta.chat.completions.parse(
    response_format=EarningsExtraction,
    messages=[
        {"role": "user", "content": f"Parse this into the required format:\n{raw}"}
    ]
)
```

## Revision Anchors

- **Tool call protocol**: (1) Send messages + tools. (2) Model returns ToolUse blocks. (3) Execute ALL tools. (4) Append ALL results. (5) Call model again. Never skip step 3 or return partial results.
- **Parallel tool calls**: Execute all tool calls from one model response concurrently with `asyncio.gather`. Sequential execution is a latency bug.
- **Schema design rules**: Description explains WHEN to use the tool (not just what). Use `enum` for constrained values. Use `additionalProperties: False`. Fewer tools = better selection accuracy.
- **Constrained decoding**: Guarantees syntactic validity (correct types, no missing required fields). Does NOT guarantee semantic correctness (wrong value in right-type field).
- **Error as observation**: Always return tool failures as strings — don't raise exceptions. The model can adapt to an error message but cannot recover from an unhandled exception.
- **Max rounds**: Always bound the tool call loop. At limit, inject a system message forcing text conclusion without tools.
