# Event Modeling

#backend #streaming #design

> **In one line:** An event is a fact about something that already happened, named in the past tense, owned by exactly one service — and getting the payload shape right is what determines whether consumers can be added later without touching the producer.

---

## The Idea

```json
{"type": "document.indexed", "document_id": "doc_42"}
```

That is an event. Everything interesting is in the decisions around it:

| Decision | |
|---|---|
| **What is an event?** | Granularity — one per field change, or one per meaningful transition |
| **What goes in the payload?** | An ID, or the whole entity, or the delta |
| **Who owns it?** | Exactly one service defines its schema |
| **How does it evolve?** | Adding fields, removing fields, changing meaning |

💡 **The organising principle: an event is a fact, not a request.** `DocumentIndexed` states that something happened. `IndexDocument` asks for something to happen — that is a command, and it belongs in a queue ([[09.1 - Queue vs Log]]).

---

## Naming

```
✅  document.indexed
✅  source.sync_failed
✅  organisation.plan_upgraded

❌  index_document          ← imperative. A command
❌  document.indexing       ← present tense. Not yet a fact
❌  document.changed        ← too vague. Changed how?
```

**The convention:**

```
<entity>.<past_tense_verb>
```

⚠️ **Vague events are the most common modelling mistake.** `document.updated` forces every consumer to diff the payload to work out what actually happened, and it means every consumer wakes for every change even if it only cares about one field.

```
document.title_changed
document.indexed
document.archived
document.permissions_changed
```

💡 **Specific events let consumers subscribe to what they care about**, and they make the event log readable as a history of what the system did. **A log full of `entity.updated` is not a history, it is a diff feed.**

⚠️ **The counter-pressure is event proliferation.** One event per field change gives you fifty event types nobody can keep track of.

**The rule: an event per meaningful business transition, not per field.** If a product person would describe it as a thing that happened, it is an event. `document.title_changed` is borderline; `document.published` is clearly one.

## Payload Shape

Three options, and the choice has real consequences.

### Thin: an identifier only

```json
{
  "type": "document.indexed",
  "id": "evt_01HQZX",
  "occurred_at": "2026-08-17T14:32:07.500Z",
  "document_id": "doc_42",
  "org_id": "org_7"
}
```

| | |
|---|---|
| **Good** | Small, never stale, no schema coupling on the entity |
| **Bad** | **Every consumer must call back** to fetch details |

⚠️ **The callback is the cost, and it can be severe.** Ten consumers each fetching the document means ten API calls per event, and if the producer is down the consumers cannot proceed.

### Fat: the full entity

```json
{
  "type": "document.indexed",
  "id": "evt_01HQZX",
  "occurred_at": "...",
  "document": {
    "id": "doc_42",
    "org_id": "org_7",
    "title": "Q3 Report",
    "status": "indexed",
    "size_bytes": 104857,
    "chunk_count": 42
  }
}
```

| | |
|---|---|
| **Good** | Self-sufficient. No callback. Consumers work when the producer is down |
| **Bad** | Larger. **Couples consumers to the entity schema.** Can be stale by the time it is read |

💡 **"Event-carried state transfer" is the name for this pattern**, and it is what makes consumers genuinely independent — a consumer can rebuild its entire view from the event log alone, with no calls to anyone.

⚠️ **The staleness point matters for compacted topics and replays.** An event from three months ago carries the entity as it was then, which is correct for an audit log and wrong if you are trying to rebuild current state without processing everything after it.

### Delta: what changed

```json
{
  "type": "document.updated",
  "document_id": "doc_42",
  "changes": {"title": {"from": "Q3", "to": "Q3 Report"}}
}
```

| | |
|---|---|
| **Good** | Precise, small |
| **Bad** | **Requires ordered processing and a base state.** Fragile |

⚠️ **Deltas require the consumer to have the correct prior state**, which means ordering matters absolutely and a single missed event corrupts everything afterwards.

**Avoid deltas unless you have a specific reason.** They look efficient and they make replay, out-of-order delivery and new consumers all much harder.

### Choosing

💡 **Default to fat events with the fields consumers actually need — not the whole entity, and not just an ID.**

```json
{
  "type": "document.indexed",
  "document_id": "doc_42",
  "org_id": "org_7",
  "title": "Q3 Report",
  "chunk_count": 42,
  "indexed_at": "..."
}
```

**The test: can a consumer do its job without calling back?** If most consumers need three fields, include those three. If one consumer needs the full content, it can fetch — and it is the only one paying that cost.

## The Envelope

Every event should share a common wrapper.

```json
{
  "id": "evt_01HQZX7C4M8N",
  "type": "document.indexed",
  "version": 2,
  "occurred_at": "2026-08-17T14:32:07.500Z",
  "producer": "ingestion-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "org_id": "org_7",
  "subject": "document/doc_42",
  "data": { ... }
}
```

| Field | Why |
|---|---|
| `id` | **Deduplication** ([[07.5 - Idempotency Keys and Deduplication]]) |
| `type` | Routing and filtering |
| `version` | Schema evolution |
| `occurred_at` | **When it happened**, not when it was published |
| `producer` | Provenance and debugging |
| `trace_id` | **Links the event to the request that caused it** ([[12.3 - Instrumenting Conduit End to End]]) |
| `org_id` | Tenant scoping, filtering, partition key |
| `subject` | What it is about |

💡 **`trace_id` in the envelope is the difference between an event log you can debug and one you cannot.** Without it, you can see that an event happened and not what caused it.

⚠️ **`occurred_at` is not `published_at`.** An event produced by a batch job may describe something that happened hours earlier. Consumers computing time windows need the former; consumers measuring pipeline lag need the latter. **Include both if they can differ.**

**CloudEvents** is a CNCF specification for exactly this envelope. **Adopting it costs nothing and gives you tooling compatibility** — worth doing rather than inventing your own field names.

## Ownership

⚠️ **Exactly one service owns each event type and its schema.**

```
ingestion-service  owns  document.*
billing-service    owns  subscription.*, invoice.*
auth-service       owns  user.*, organisation.*
```

| Rule | |
|---|---|
| One producer per event type | Two producers means two schemas drifting |
| The owner defines the schema | And it lives in a registry, not in a wiki |
| **Consumers never produce events they do not own** | A consumer that emits `document.indexed` breaks the model |
| Breaking changes are the owner's responsibility | Including migration |

💡 **The ownership rule is what makes an event log a contract rather than a shared mutable space.** Without it, three teams emit slightly different `user.created` events and every consumer accumulates special cases.

## Granularity

```
❌  Too fine
    document.title_changed
    document.size_changed
    document.status_changed
    document.chunk_count_changed
    → consumers subscribe to twelve types to track one entity

❌  Too coarse
    document.changed
    → every consumer wakes for everything and must diff

✅  About right
    document.created
    document.content_updated
    document.indexed
    document.index_failed
    document.archived
    document.deleted
```

💡 **Model the lifecycle, not the fields.** The events should read as the story of the entity's life, and a new engineer should be able to understand what the system does by reading the event catalogue.

⚠️ **Include failure events.** `document.index_failed` is as important as `document.indexed` — consumers need to know about failures, and without an event they have to poll or infer.

## In Production

### The event catalogue

```markdown
### `document.indexed`

**Owner:** ingestion-service
**Version:** 2
**Partition key:** `document_id`
**Retention:** 30 days
**Emitted when:** all chunks of a document are successfully written to the index

**Payload:**
| Field | Type | Since | Notes |
|---|---|---|---|
| document_id | string | v1 | |
| org_id | string | v1 | |
| chunk_count | int | v1 | |
| index_version | string | **v2** | added 2026-06-01 |

**Consumers:** search-service, analytics-service, notification-service
```

💡 **Generate this from your schema definitions** so it cannot drift, and publish it where consumers can find it ([[05.13 - Contract Testing and Schema Evolution]]).

⚠️ **The consumers list is the field that matters most operationally.** Before changing an event, you need to know who reads it — and without that list, every change is a guess.

**Track it automatically** by having consumers register, or by parsing consumer group metadata.

### Schema evolution

| Change | Safe? |
|---|---|
| Adding an optional field | **Yes** |
| Adding a required field | No |
| Removing a field | **No** — a consumer may read it |
| Renaming a field | No |
| Changing a type | No |
| Adding an event type | Yes |
| **Removing an event type** | No — check consumers first |
| Changing what an event *means* | **No, and it is the worst kind** |

⚠️ **Semantic changes are the most dangerous because no schema check catches them.** If `document.indexed` starts being emitted when indexing *begins* rather than completes, every consumer is silently wrong and every contract test passes.

💡 **When the meaning changes, emit a new event type.** `document.indexed` and `document.indexing_started` are two facts; overloading one name for both is a bug that will take weeks to find.

Full mechanics in [[09.6 - Schema Registry and Compatibility]].

### Events are forever

⚠️ **An event in a log with 90-day retention will be read by a consumer replaying from 90 days ago.** Your v1 schema is live as long as any retained event uses it.

```python
def handle(event: dict):
    version = event.get("version", 1)
    if version == 1:
        event = migrate_v1_to_v2(event)
    ...
```

💡 **Consumers should upcast old versions to the current one at the boundary**, so the rest of the handler only knows one shape. **The upcast functions are permanent** and that is fine — they are small and they are what makes replay possible.

**With infinite retention or event sourcing, this becomes a serious discipline** — you are maintaining every schema version that ever existed.

### Personal data

⚠️ **An event log is append-only, which conflicts directly with the right to erasure.**

| Approach | |
|---|---|
| **Do not put personal data in events** | Reference an ID; the data lives in a deletable store |
| Crypto-shredding | Encrypt per-subject; delete the key to render events unreadable |
| Compacted topic with tombstones | Works for keyed data, not for a history |
| Short retention | Limits the problem window |

💡 **"Reference, do not embed" is the cleanest answer for personal data**, and it is the one case where a thin event is clearly correct. The event says `user_id`; the name and email live in a database row you can delete.

⚠️ **Crypto-shredding is elegant and needs real key management** — one key per subject, stored somewhere deletable, and every consumer able to decrypt. It is a genuine solution and it is not free.

### Conduit's event catalogue

| Event | Payload shape | Partition key | Consumers |
|---|---|---|---|
| `document.created` | Fat — id, org, title, source | `document_id` | search, analytics |
| `document.indexed` | Fat — id, org, chunk_count | `document_id` | search, notification, analytics |
| `document.index_failed` | Fat — id, org, reason | `document_id` | notification, analytics |
| `document.archived` | Thin — id, org | `document_id` | search, analytics |
| `source.sync_started` | Fat — id, org, run_id | `source_id` | notification |
| `source.sync_completed` | Fat — counts, duration | `source_id` | notification, analytics |
| `annotation.created` | Fat — id, doc, author, text | `document_id` | notification, search |
| `organisation.deleted` | Thin — id | `org_id` | **all** — triggers cleanup |

💡 **Note the partition keys.** Document events key by `document_id` so all events for one document are ordered; source events key by `source_id`. **`organisation.deleted` keys by `org_id` and every consumer reads it**, because offboarding requires cleanup everywhere ([[06.16 - Multi Tenant Data Models]]).

⚠️ **`annotation.created` carries the text**, which may be personal data. **Decide explicitly**: reference-only, or short retention, or accept it. **This is exactly the decision people skip and regret.**

## Codebase

**Repo:** `cloudevents/spec`, `getsentry/sentry`, `saleor/saleor`

**Question to answer:** What does the CloudEvents specification require in an envelope, and why is each field there? Then: how does a large product model its domain events, and how granular are they?

**Read, in order:**

1. **CloudEvents specification** (`cloudevents/spec/cloudevents/spec.md`) — **short, and it is the envelope design already solved.** Read the required and optional attributes and the reasoning
2. `cloudevents/spec/cloudevents/bindings/kafka-protocol-binding.md` — how the envelope maps onto Kafka headers versus the payload
3. `saleor/saleor/webhook/event_types.py` — **a large real event catalogue.** Note the granularity and the naming, and count how many event types they have
4. `saleor/saleor/webhook/payloads.py` — **the payload shapes.** Note how much entity data they include and where they reference instead
5. `sentry/src/sentry/signals.py` and their analytics events — a different style, and worth contrasting

💡 The Saleor event catalogue is the most useful read here because **it is a mature product's answer to the granularity question**, made over years under real pressure from integrators. Counting their event types and looking at where they chose specific versus general names calibrates your own instinct better than any guideline.

**Size:** 1 session.

**Part 1 — The plausible first attempt.** Model Conduit's events the way a team would under time pressure: `document.updated` for everything, mixed naming, no envelope, payloads that are whatever was convenient.

**Do not caricature it.**

**Part 2 — Critique it.** For each decision, state what breaks concretely and when.

Then **verify three empirically**: add a consumer that only cares about title changes and measure how much irrelevant traffic it processes; replay a month of events and find where the schema broke; try to answer "who consumes this event" and record how long it took.

**Part 3 — Payload shapes, measured.** The same `document.indexed` event, three ways.

Build three consumers — search, notification, analytics — and for each payload shape measure:

| Metric | |
|---|---|
| Event size | |
| Callbacks per event | Across all three consumers |
| **Consumer independence** | Do they work with the producer down? |
| Replay correctness | Rebuild from 30 days ago |
| Coupling | Which schema changes break consumers |

**Then kill the producer and confirm which consumers still function.** That column is the argument for fat events.

**Part 4 — Granularity.** Model document lifecycle three ways: twelve field-level events, one `document.changed`, and six lifecycle events.

For each, implement a consumer that only cares about indexing completion. Measure: events processed, events discarded, and lines of filtering logic.

**Then add a new requirement** — "notify when a document is archived" — and measure what had to change in each model.

**Part 5 — Evolution, including the dangerous case.** With consumers running:

- Add an optional field. **Confirm nothing breaks.**
- Remove a field a consumer reads. **Count the failures.**
- **Change what an event means** — emit `document.indexed` at the start instead of the end.

⚠️ **The third should break consumers silently, with no schema error and no failed test.** Measure how long until you would notice.

Then implement versioned events with upcasting, and confirm a consumer handles v1 and v2 simultaneously.

**Part 6 — Privacy.** An `annotation.created` event carrying user-written text and an author email.

Implement three approaches: embedded, reference-only, and crypto-shredded.

**Then execute an erasure request** for a user with 500 annotations across a 90-day log.

Measure for each: time to comply, whether the data is genuinely unreadable, consumer complexity, and whether replay still works afterwards.

**Write in `COMPARISON.md` which you would use for Conduit and what it costs.**

**Part 7 — The generated catalogue.** Typed event definitions that produce the markdown catalogue automatically, including a consumers list built from consumer group metadata.

Then add a CI check: **removing a field from an event with registered consumers fails the build.**

**Done when:**
- `CRITIQUE.md` has a concrete consequence per v0 decision, with three verified
- Your payload comparison shows which consumers survive a producer outage
- The granularity comparison shows what changes when a requirement is added
- A semantic change broke consumers silently, and you measured detection time
- You executed an erasure request three ways with measured compliance time
- Your catalogue is generated and CI blocks breaking changes
