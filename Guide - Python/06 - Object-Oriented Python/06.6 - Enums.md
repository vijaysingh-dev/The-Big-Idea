# Enums

#python #enum #oop

> **In one line:** An `Enum` is a closed set of named constants that are singletons, compare by identity, and are iterable. `StrEnum` and `IntEnum` also behave as strings or ints, which is what you want at API and database boundaries, and the trade-off is that mixed comparisons get looser.

---

## Basics

```python
from enum import Enum, auto

class OrderStatus(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"

s = OrderStatus.PAID
s.name, s.value                 # ('PAID', 'paid')
OrderStatus("paid")             # lookup by value → OrderStatus.PAID
OrderStatus["PAID"]             # lookup by name
list(OrderStatus)               # all members, in definition order
s is OrderStatus.PAID           # True — members are singletons
OrderStatus.PAID == "paid"      # False — a plain Enum is not its value
```

Why enums instead of string constants:

- **A closed set.** `OrderStatus("refunded")` raises `ValueError`. A typo becomes an error instead of a silent new state.
- **Type checking.** A function typed `status: OrderStatus` cannot receive an arbitrary string.
- **Exhaustiveness.** With `match` plus `typing.assert_never`, the type checker tells you when a new member is not handled.

```python
from typing import assert_never

def label(s: OrderStatus) -> str:
    match s:
        case OrderStatus.PENDING: return "Awaiting payment"
        case OrderStatus.PAID: return "Paid"
        case OrderStatus.SHIPPED: return "On its way"
        case OrderStatus.CANCELLED: return "Cancelled"
        case _: assert_never(s)       # mypy/pyright error if a member is missing
```

## StrEnum and IntEnum

```python
from enum import StrEnum, IntEnum

class Role(StrEnum):                # 3.11+
    ADMIN = auto()                  # auto() in a StrEnum gives the lowercased name: "admin"
    MEMBER = auto()

Role.ADMIN == "admin"               # True — it IS a str
f"role={Role.ADMIN}"                # 'role=admin'
json.dumps({"role": Role.ADMIN})    # '{"role": "admin"}' — serialises with no custom encoder

class Priority(IntEnum):
    LOW = 1
    HIGH = 3
Priority.HIGH > Priority.LOW        # True
Priority.HIGH == 3                  # True
```

| | `Enum` | `StrEnum` / `IntEnum` |
|---|---|---|
| Equal to its raw value | No | Yes |
| JSON serialisable as-is | No | Yes |
| Accidental comparisons with unrelated strings or ints | Prevented | Allowed |
| Best for | Pure domain logic | **API payloads, database columns, config, anything crossing a boundary** |

In practice, most backend enums are `StrEnum`: readable in JSON, readable in the database, and stable if you reorder members (unlike ints).

## Flags

```python
from enum import Flag, auto

class Perm(Flag):
    READ = auto()       # 1
    WRITE = auto()      # 2
    DELETE = auto()     # 4
    ADMIN = READ | WRITE | DELETE

p = Perm.READ | Perm.WRITE
Perm.WRITE in p         # True
Perm.DELETE in p        # False
list(p)                 # [Perm.READ, Perm.WRITE] (3.11+)
```

Useful for compact permission sets and feature bitmasks. For permissions visible to humans and auditors, a set of `StrEnum` values is often clearer than a bitmask.

## Enums With Behaviour

Members are instances of the enum class, so they can have methods and properties:

```python
class OrderStatus(StrEnum):
    PENDING = auto()
    PAID = auto()
    SHIPPED = auto()
    CANCELLED = auto()

    @property
    def is_terminal(self) -> bool:
        return self in {OrderStatus.SHIPPED, OrderStatus.CANCELLED}

    def can_transition_to(self, new: "OrderStatus") -> bool:
        return new in _TRANSITIONS[self]

_TRANSITIONS = {
    OrderStatus.PENDING: {OrderStatus.PAID, OrderStatus.CANCELLED},
    OrderStatus.PAID: {OrderStatus.SHIPPED, OrderStatus.CANCELLED},
    OrderStatus.SHIPPED: set(),
    OrderStatus.CANCELLED: set(),
}
```

That is a small state machine with the allowed transitions in one place. See [[02.16 - State]] in the LLD guide for the full pattern.

## Enums at the Boundaries

| Boundary | How |
|---|---|
| **Pydantic / FastAPI** | Annotate fields with the enum. Input is validated against the values, and the OpenAPI schema lists them. `use_enum_values=True` stores the raw value instead of the member ([[07.3 - Pydantic Fundamentals]]). |
| **Postgres** | Either a native `ENUM` type (adding values needs `ALTER TYPE`, and removing them is painful) or a `TEXT` column with a `CHECK` constraint, which is easier to evolve. See [[07.10 - Schema Design]]. |
| **SQLAlchemy** | `Enum(OrderStatus, native_enum=False)` for the CHECK approach. Watch whether it stores names or values. |
| **Events and messages** | Treat enum values as part of the schema. Adding a value can break consumers that validate strictly. Consumers should tolerate unknown values ([[10.2 - Event Modeling]]). |

⚠️ **Never persist `.name` if you might rename a member, and never persist auto-generated ints if you might reorder members.** Persist explicit, stable string values.

## Codebase

**Repo:** `python/cpython`

**Question to answer:** How does `EnumType` (the metaclass) turn the class body's assignments into singleton members, and how does `Color("red")` find a member by value?

**Read, in order:**

1. `Lib/enum.py` — `_EnumDict` (the special namespace returned by `__prepare__`, which records member assignments and rejects duplicates), `EnumType.__new__` (creates members), `EnumType.__call__` (value lookup), `_missing_`
2. `Lib/enum.py` — `StrEnum` and `auto` / `_generate_next_value_`
3. `Lib/enum.py` — `Flag.__or__` and `__contains__`

`enum.py` is a superb example of metaclass programming in production. It previews [[06.8 - Metaprogramming]].
