# Custom Metadata Driven Architecture

## The idea

Move the parts of a system that change often out of code and into Custom Metadata, so that changing them is a configuration deployment rather than a code change.

```java
// Every threshold change is a code change, a review, and a release
if (claim.Claim_Amount__c > 500000) { }
```

```java
// The threshold lives in metadata, deployed independently
for (Approval_Tier__mdt tier : ApprovalTierService.tiers()) { }
```

The distinction that makes this work on Salesforce specifically: **Custom Metadata records deploy with the code, cost no SOQL queries, and are readable from Apex, flows, formulas, and validation rules alike.** See [[17.1 - Custom Metadata Types]].

## Handler registration

The most valuable application: which classes run for which object and event, driven by configuration.

```
Trigger_Handler__mdt
  Object_API_Name__c:  Warranty_Claim__c
  Handler_Class__c:    ClaimValidationHandler
  Event__c:            BEFORE_UPDATE
  Execution_Order__c:  10
  Active__c:           true

  Object_API_Name__c:  Warranty_Claim__c
  Handler_Class__c:    ClaimRoutingHandler
  Event__c:            BEFORE_UPDATE
  Execution_Order__c:  20
  Active__c:           true
```

```java
public interface ITriggerHandler {
    void handle(List<SObject> records, Map<Id, SObject> priorRecords);
}
```

```java
public with sharing class MetadataTriggerDispatcher {

    public static void run() {
        String objectName = objectNameFromContext();
        String event = String.valueOf(Trigger.operationType);

        for (ITriggerHandler handler : handlersFor(objectName, event)) {
            handler.handle(Trigger.new, Trigger.oldMap);
        }
    }

    private static List<ITriggerHandler> handlersFor(String objectName, String event) {
        List<ITriggerHandler> handlers = new List<ITriggerHandler>();

        for (Trigger_Handler__mdt config : [
            SELECT Handler_Class__c
            FROM Trigger_Handler__mdt
            WHERE Object_API_Name__c = :objectName
              AND Event__c = :event
              AND Active__c = true
            ORDER BY Execution_Order__c
        ]) {
            Type handlerType = Type.forName(config.Handler_Class__c);

            // a bad configuration row is logged rather than breaking every save
            if (handlerType == null) {
                AutomationLogger.logError('TriggerDispatcher', null,
                    'Unknown handler: ' + config.Handler_Class__c);
                continue;
            }
            handlers.add((ITriggerHandler) handlerType.newInstance());
        }
        return handlers;
    }
}
```

**What this buys:** explicit, configurable execution order; a handler can be deactivated without a deployment; and the org's automation is queryable.

**What it costs:** the compiler no longer knows the dependency, so deleting a handler class fails at runtime rather than at deploy time.

That tradeoff is the recurring theme of this note, and it is why the null check and the logging matter. See [[11.8 - Trigger Frameworks in the Wild]].

## Field mappings

Integration mappings are the other natural fit, and metadata relationships make them safe.

```
Field_Mapping__mdt
  Integration__c:      ERP_Claim_Sync
  Source_Field__c:     erpClaimAmount
  Target_Object__c:    Metadata Relationship → Warranty_Claim__c
  Target_Field__c:     Metadata Relationship → Claim_Amount__c
  Transform__c:        None / Uppercase / Currency
```

```java
public with sharing class MappingService {

    public static SObject applyMapping(String integrationName, Map<String, Object> payload) {
        List<Field_Mapping__mdt> mappings = [
            SELECT Source_Field__c,
                   Target_Object__r.QualifiedApiName,
                   Target_Field__r.QualifiedApiName,
                   Transform__c
            FROM Field_Mapping__mdt
            WHERE Integration__c = :integrationName AND Active__c = true
        ];

        if (mappings.isEmpty()) {
            throw new ConfigurationException('No mapping configured for ' + integrationName);
        }

        SObject record = Schema.getGlobalDescribe()
            .get(mappings[0].Target_Object__r.QualifiedApiName)
            .newSObject();

        for (Field_Mapping__mdt mapping : mappings) {
            Object value = payload.get(mapping.Source_Field__c);
            if (value != null) {
                record.put(mapping.Target_Field__r.QualifiedApiName,
                    transform(value, mapping.Transform__c));
            }
        }
        return record;
    }
}
```

**Metadata relationships give deploy-time validation.** A mapping referencing a deleted field fails deployment rather than failing silently at runtime — which is the single strongest argument for using them over storing field API names as text.

## Validation rules in metadata

Where business validation changes frequently and an administrator should own it:

```
Claim_Validation_Rule__mdt
  Rule_Name__c:        Amount within coverage limit
  Field__c:            Claim_Amount__c
  Operator__c:         LessThanOrEqual
  Compare_To_Field__c: Coverage_Limit__c
  Error_Message__c:    $Label.Claim_Error_Exceeds_Coverage
  Severity__c:         Error
  Active__c:           true
```

```java
public with sharing class ConfigurableValidationService {

    public static void validate(
        List<Warranty_Claim__c> claims,
        Map<Id, Machine_Coverage__c> coverageByAsset
    ) {
        List<Claim_Validation_Rule__mdt> rules = ValidationRuleCache.active();

        for (Warranty_Claim__c claim : claims) {
            Machine_Coverage__c coverage = coverageByAsset.get(claim.Asset__c);

            for (Claim_Validation_Rule__mdt rule : rules) {
                if (!RuleEvaluator.passes(claim, coverage, rule)) {
                    claim.addError(rule.Field__c, resolveMessage(rule));
                }
            }
        }
    }
}
```

**Be honest about when this is worth it.** A rule engine is real code with real complexity, and it is justified when rules genuinely change monthly and an administrator maintains them. For three stable rules, a validation rule or a hardcoded check is better. See [[06.5 - Validation Rules]].

## Feature toggles

```
Feature_Toggle__mdt
  Feature__c:      New_Approval_Flow
  Enabled__c:      true
  Description__c:  Routes approvals through the tiered service
```

```java
public with sharing class FeatureToggles {

    private static Map<String, Boolean> cached;

    public static Boolean isEnabled(String feature) {
        if (cached == null) {
            cached = new Map<String, Boolean>();
            for (Feature_Toggle__mdt toggle : Feature_Toggle__mdt.getAll().values()) {
                cached.put(toggle.Feature__c, toggle.Enabled__c);
            }
        }
        return cached.get(feature) == true;
    }
}
```

**Custom Metadata toggles deploy** — which means the toggle state travels with the code, and a feature enabled in a sandbox is enabled in production when deployed.

**Custom Settings toggles do not deploy** — which is what makes them right for per-user pilots and for the automation bypass, where the value should differ by environment and by user. See [[17.2 - Custom Settings]].

Choosing between them is a question of whether the value should be the same everywhere.

## Integration configuration

```
Integration_Config__mdt
  System__c:           ERP
  Named_Credential__c: ERP_System
  Base_Path__c:        /api/v2
  Timeout_Ms__c:       30000
  Max_Retries__c:      3
  Batch_Size__c:       200
  Active__c:           true
```

```java
public with sharing class ErpClient {

    private static Integration_Config__mdt config() {
        return Integration_Config__mdt.getInstance('ERP');
    }

    public static Response post(String path, Object payload) {
        Integration_Config__mdt cfg = config();

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:' + cfg.Named_Credential__c + cfg.Base_Path__c + path);
        req.setTimeout((Integer) cfg.Timeout_Ms__c);
        req.setBody(JSON.serialize(payload));

        return send(req);
    }
}
```

**Never the credential itself** — that belongs in a Named Credential. The metadata holds the credential's *name*, the timeout, and the retry policy. See [[13.13 - Named Credentials and External Credentials]].

Tuning a timeout or a retry count then becomes a metadata deployment rather than a code release, which matters when an external system's behaviour changes.

## Caching and invalidation

```java
public with sharing class ApprovalTierService {

    private static List<Approval_Tier__mdt> cached;

    public static List<Approval_Tier__mdt> tiers() {
        if (cached == null) {
            cached = [
                SELECT Tier_Name__c, Minimum_Amount__c, Approver_Role__c
                FROM Approval_Tier__mdt
                WHERE Active__c = true
                ORDER BY Minimum_Amount__c DESC
            ];
        }
        return cached;
    }

    @TestVisible
    private static void override(List<Approval_Tier__mdt> tiers) {
        cached = tiers;
    }
}
```

**The static cache is for the transaction, not for the query limit** — metadata queries are free. It avoids repeated retrieval and gives a clean injection point for tests.

**Platform Cache is almost never needed** for custom metadata, because the platform already caches it. See [[16.8 - Platform Cache]].

## Testing

Deployed metadata records **are** visible in tests, unlike Custom Setting data. That is convenient and couples the test to org configuration.

```java
@IsTest
static void executiveTierAppliesAtTheBoundary() {
    // constructed in memory: the test does not depend on what is deployed
    ApprovalTierService.override(new List<Approval_Tier__mdt>{
        new Approval_Tier__mdt(Tier_Name__c = 'Executive', Minimum_Amount__c = 500000),
        new Approval_Tier__mdt(Tier_Name__c = 'Manager', Minimum_Amount__c = 100000)
    });

    Test.startTest();
    String tier = ApprovalTierService.tierFor(500000);
    Test.stopTest();

    Assert.areEqual('Executive', tier, 'The boundary value falls in the higher tier');
}
```

Custom metadata records can be constructed with `new`, which is what makes this possible. A test depending on deployed records breaks when someone changes a threshold — and a test with an override does not.

**Also test the configuration itself**, since a bad metadata record is now a production defect:

```java
@IsTest
static void everyRegisteredHandlerClassExists() {
    for (Trigger_Handler__mdt config : [
        SELECT Handler_Class__c FROM Trigger_Handler__mdt WHERE Active__c = true
    ]) {
        Assert.isNotNull(Type.forName(config.Handler_Class__c),
            'Registered handler does not exist: ' + config.Handler_Class__c);
    }
}
```

That single test catches the failure mode this whole approach introduces.

## The tradeoffs, stated plainly

**What you gain:**

Configuration changes without code changes. Administrator ownership of business rules. A queryable inventory of behaviour. Deploy-time validation through metadata relationships. Testable configuration.

**What you lose:**

**Compile-time safety.** `Type.forName` failures are runtime failures. A deleted class compiles fine and breaks at save time.

**Traceability.** "Where is this discount calculated" has no answer from the code alone — you have to read the metadata too.

**Debuggability.** A stack trace through a dynamically instantiated class is harder to follow, and a misconfigured record produces a failure with no obvious cause.

**Simplicity.** A hardcoded threshold is one line; a metadata-driven one is a type, records, a service, a cache, and a test.

## When to reach for it

**Worth it when:**

- The values genuinely change — quarterly or more often
- An administrator should own them
- The same rule is needed by Apex, flows, and formulas
- The org is a managed package needing per-subscriber configuration
- New variants are added regularly

**Not worth it when:**

- The value has not changed in two years
- Only developers will ever change it
- There is one variant
- The indirection costs more clarity than the flexibility is worth

**The honest test:** has this actually changed, or does it feel like it might? Configurability built for change that never comes is pure cost, and it is one of the most common forms of over-engineering in mature Salesforce orgs.

## Practical guidance

**Use metadata relationships** for object and field references, so a rename fails the deployment.

**Null-check `Type.forName`**, and log rather than throw on an unknown class.

**Cache in a static**, with a `@TestVisible` override.

**Test the configuration**, not just the code that reads it.

**Never store secrets** in custom metadata.

**Use Custom Metadata when the value should be the same everywhere**, Custom Settings when it should differ by environment or user.

**Ask whether it has actually changed** before making it configurable.
