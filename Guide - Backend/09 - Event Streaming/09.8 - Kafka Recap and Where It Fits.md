## The Decision

```
Do you need any of: replay, multiple independent consumers, an audit trail?
├── NO → a task queue. Do not add a log ([[08.1 - Why Background Work Exists]])
│
└── YES → how much, and for how long?
    ├── Moderate volume, days of retention, one datacentre
    │   └── Redis Streams
    └── High volume, weeks of retention, many consumers, cross-region
        └── Kafka
```

### Redis Streams is the underrated middle

```python
await redis.xadd("documents", {"data": payload}, maxlen=1_000_000, approximate=True)

entries = await redis.xreadgroup("indexer", consumer_id, {"documents": ">"}, count=100)
await redis.xack("documents", "indexer", entry_id)
```

💡 **Redis Streams gives you the log model — append-only, offsets, consumer groups, replay — without a Kafka cluster.**

| Has | Lacks |
|---|---|
| Consumer groups | Partitions (one stream, one order) |
| Per-consumer offsets | Replication across datacentres |
| Replay from any ID | Compaction |
| Pending-entry tracking (acks) | Tiered storage |
| Bounded retention (`MAXLEN`) | Very high throughput |

⚠️ **The absence of partitions is the real limit.** A Redis Stream is one ordered sequence, so parallelism comes from consumer groups distributing entries — which means **no per-key ordering guarantee** ([[09.1 - Queue vs Log]]). If ordering per document matters, you must shard across multiple streams yourself.

💡 **For a system of Conduit's size — thousands of events per second, days of retention, one region — Redis Streams is genuinely sufficient**, and it is already deployed for caching and the SSE backplane ([[04.6 - Scaling Long Lived Connections]]).

**The honest position: most teams that adopt Kafka did not need it, and the ones that did could name the specific requirement.**

### When Kafka is genuinely right

| Signal | |
|---|---|
| **Throughput above ~50k events/second sustained** | Redis becomes the bottleneck |
| **Retention measured in weeks or months** | Redis is memory-resident |
| **Per-key ordering with parallelism** | Partitions are the mechanism |
| **Many independent consumer groups** | Each with its own offsets and lag |
| **Cross-datacentre replication** | MirrorMaker, or a managed equivalent |
| **You need tiered storage** | Offload old segments to object storage |
| **Compaction as a state distribution mechanism** | Config, permissions, reference data |
| **An ecosystem requirement** | Debezium, Kafka Connect, ksqlDB |

💡 **The ecosystem argument is stronger than it sounds.** Debezium requires Kafka (or at least Kafka Connect), and CDC is often the reason Kafka arrives ([[09.4 - Change Data Capture]]). "We need Debezium" is a legitimate answer to "why Kafka".

## What Kafka Costs

⚠️ **Be honest about this in a design discussion, because it is consistently understated.**

| Cost | |
|---|---|
| **Operational** | A cluster (or KRaft quorum), broker sizing, disk management, upgrades |
| **Cognitive** | Partitions, ISR, consumer groups, rebalancing — a vocabulary the team must learn |
| **Configuration surface** | Hundreds of settings, several of which have dangerous defaults |
| **Debugging** | Consumer lag, rebalance storms, and partition skew are their own discipline |
| **Schema management** | A registry, or the discipline without one ([[09.6 - Schema Registry and Compatibility]]) |
| **Connect cluster** | If you use Debezium or sinks, that is more infrastructure |

💡 **Managed Kafka — Confluent Cloud, MSK, Redpanda Cloud — removes most of the operational cost and none of the cognitive cost.** Your team still needs to understand partitions, consumer groups and lag. **Budget for that.**

⚠️ **Redpanda is worth evaluating** — Kafka-API-compatible, single binary, no ZooKeeper or JVM. For a team that wants Kafka's model without Kafka's operational profile, it is a genuine option.

## How Section 09 Composes

The pieces are not independent. Here is the whole system.

```
Application writes
    │
    ▼  transaction: domain row + outbox row      ← [[09.3 - The Outbox Pattern]]
Postgres
    │
    ├── WAL ──► Debezium ──► Kafka               ← [[09.4 - Change Data Capture]]
    │           (outbox router)
    ▼
Kafka topics                                     ← [[09.1 - Queue vs Log]]
    │  schemas registered and checked            ← [[09.6 - Schema Registry and Compatibility]]
    │
    ├──► search-indexer      (idempotent upsert)
    ├──► analytics           (event-time windows) ← [[09.5 - Stream Processing Basics]]
    ├──► notifier            (side effects — never replayed)
    └──► audit               (infinite retention)
              │
              └── any consumer replayable         ← [[09.7 - Replay Backfill and Reprocessing]]
```

💡 **Each note in section 09 solves one link in that chain, and the chain only works if every link holds:**

| Link | Without it |
|---|---|
| Outbox | Events lost when the publish fails after commit |
| CDC or a relay | Nothing reaches Kafka |
| Correct partition key | No ordering where you need it |
| Schema discipline | Consumers break silently on evolution |
| Idempotent consumers | Replay is impossible, duplicates corrupt state |
| Event-time semantics | Replay produces different results |
| Retention policy | You cannot rebuild from far enough back |

⚠️ **The weakest link determines the system.** A perfectly configured Kafka cluster with a non-idempotent consumer gives you a pipeline you cannot replay, which removes the main reason you built it.

## The Three Guarantees, Assembled

**"No event is lost"** — the outbox writes the event in the same transaction as the data, so if the data exists the event exists.

**"No event is processed twice, observably"** — delivery is at-least-once; the consumer deduplicates or writes idempotently ([[07.5 - Idempotency Keys and Deduplication]]).

**"Any derived store can be rebuilt"** — retention covers the rebuild window, consumers are replayable, and the parallel-pipeline pattern makes the switch safe ([[09.7 - Replay Backfill and Reprocessing]]).

💡 **Those three sentences are the value proposition of an event-driven architecture**, and each requires specific work. **A system that has Kafka but not those three guarantees has the cost and not the benefit.**

## In Production

### The configuration that matters

Your Kafka guide covers the full surface. These are the ones that are wrong by default and cause real incidents.

```python
# Producer
acks="all"                                  # ⚠️ default is 1: can lose data
enable_idempotence=True                     # dedup + safe retries with in-flight > 1
compression_type="lz4"
linger_ms=10
```

```python
# Consumer
enable_auto_commit=False                    # ⚠️ default True: loses and duplicates
partition_assignment_strategy="cooperative-sticky"   # ⚠️ default is eager
max_poll_records=100                        # so processing fits max.poll.interval.ms
```

```
# Broker / topic
min.insync.replicas=2                       # with acks=all, this is what makes it durable
unclean.leader.election.enable=false        # ⚠️ true trades data for availability
```

⚠️ **`acks=all` without `min.insync.replicas=2` is not durable** — with one in-sync replica, "all" means one. The two settings only work together.

⚠️ **`unclean.leader.election.enable=true` allows an out-of-sync replica to become leader, which silently discards committed records.** It is off by default in modern Kafka; verify it.

💡 **`cooperative-sticky` is the single highest-value non-default setting**, because it turns a rolling deploy from minutes of stalled consumption into seconds ([[09.1 - Queue vs Log]]).

### Monitoring

```python
kafka_consumer_lag_records.labels(topic=t, partition=p, group=g).set(lag)
kafka_consumer_lag_seconds.labels(...).set(time_lag)          # ← better
kafka_rebalance_total.labels(group=g).inc()
kafka_producer_error_total.labels(reason=...).inc()
kafka_under_replicated_partitions.set(n)
kafka_offline_partitions.set(n)
```

| Alert | Condition |
|---|---|
| **Consumer lag (time)** | > your staleness budget for that consumer |
| **Under-replicated partitions** | > 0 sustained |
| **Offline partitions** | > 0. **Immediate** |
| Rebalance rate | Rising — usually a consumer exceeding `max.poll.interval.ms` |
| Producer errors | Any sustained rate |

💡 **Lag in *time* rather than records is the metric that matters.** 10,000 records might be a second or an hour, and only the time version maps onto "how stale is the search index".

⚠️ **Track lag per partition, not just per group.** Even lag across partitions is a capacity problem; lag concentrated on one is a stuck consumer or a hot key ([[09.1 - Queue vs Log]]).

### The failure modes worth rehearsing

| Failure | Rehearse |
|---|---|
| A broker dies | Confirm leadership moves and producers continue |
| A consumer group stalls | Confirm lag alerts fire and the runbook works |
| A poison record blocks a partition | Confirm the retry-topic path works |
| Debezium stops | **Confirm `max_slot_wal_keep_size` bounds the damage** ([[09.4 - Change Data Capture]]) |
| A schema change breaks a consumer | Confirm CI catches it, or the consumer degrades |
| A full replay is needed | Confirm it completes without affecting production |

💡 **The Debezium one is the highest-severity failure in this whole section**, because an unattended replication slot fills the database disk and stops your primary. **It is the one to alert on hardest.**

### Conduit's phase 5

| Component | Decision |
|---|---|
| Log | **Kafka**, because CDC via Debezium and multiple consumer groups |
| Topics | `documents`, `document-events`, `annotations`, `org-config` (compacted) |
| Partition key | `document_id` for document events, `org_id` for config |
| Retention | 90 days for events, infinite for the compacted config topic |
| Schema | **Version envelope plus CI diff.** No registry yet |
| Outbox | For domain events; CDC for the search index sync |
| Consumers | search-indexer, analytics, notifier, audit |

💡 **The reason Kafka rather than Redis Streams: the search index must be rebuildable from 90 days of history, and the embedding model upgrade in phase 9 requires reprocessing everything** ([[09.7 - Replay Backfill and Reprocessing]]). **Redis Streams cannot hold 90 days of document events in memory.**

**Write that justification down.** "We chose Kafka because we need 90-day retention for index rebuilds and Debezium for CDC" is a defensible answer; "Kafka is the standard" is not.

⚠️ **The schema decision is deliberately minimal.** One team, four event types, JSON payloads — a registry is disproportionate. **The trigger for adding one: a second team consuming these events** ([[09.6 - Schema Registry and Compatibility]]).

## Codebase

**Repo:** `apache/kafka`, `redpanda-data/redpanda`, `redis/redis`

**Question to answer:** How does Kafka's ISR mechanism decide a replica is in sync, and what does `acks=all` actually wait for? Then: how do Redis Streams implement consumer groups, and what do they lack compared to Kafka partitions?

**Read, in order:**

1. `kafka/core/src/main/scala/kafka/cluster/Partition.scala` — **`maybeIncrementLeaderHW` and the ISR management.** What "in sync" means, and how the high watermark advances. **The answer to the first question**
2. `kafka/core/src/main/scala/kafka/server/DelayedProduce.scala` — **what `acks=all` waits for.** A produce request is held until the high watermark advances past it
3. `redis/src/t_stream.c` — **`streamCreateConsumerGroup` and the PEL (pending entries list).** Consumer groups in Redis: each group tracks a last-delivered ID and a per-consumer pending list. **The answer to the second question — note there is no partition concept**
4. `redis/src/t_stream.c` — `xautoclaimCommand`, which handles reclaiming entries from a dead consumer. Compare to Kafka's rebalance
5. `redpanda-data/redpanda` — the architecture documentation. **A Kafka-compatible implementation with no JVM and no ZooKeeper**, worth understanding as an option

💡 The `DelayedProduce` reading clarifies something people get wrong: **`acks=all` does not wait for all replicas, it waits for the high watermark to advance — which requires `min.insync.replicas` acknowledgements.** With `min.insync.replicas=1`, `acks=all` is `acks=1` with extra steps. **Seeing that in code makes the two-setting relationship obvious.**

**Size:** 1–2 sessions.

**Part 1 — Three substrates, one requirement.** "Document events consumed by a search indexer, an analytics aggregator and a notifier, with 30-day replay."

Implement on Redis Streams, Kafka, and a task queue (with three separate queues).

Measure: max sustained throughput, memory or disk for 30 days of retention, per-key ordering achieved, work to add a fourth consumer, and operational components.

**The task queue version should fail the replay requirement entirely.** Quantify what Redis Streams costs in memory for 30 days at your event rate — that number is usually the deciding one.

**Part 2 — Durability, verified.** Three brokers, `replication.factor=3`.

Test the matrix: `acks` in (0, 1, all) × `min.insync.replicas` in (1, 2).

For each: produce 10,000 records, kill the leader mid-produce, and **count records lost.**

**Confirm `acks=all` with `min.insync.replicas=1` loses data**, which is the combination people assume is safe.

Then enable `unclean.leader.election` and **demonstrate committed records disappearing.**

**Part 3 — Rebalance cost.** A group of 6 on 24 partitions, processing continuously.

Measure total consumption stall during a rolling restart with `range` and with `cooperative-sticky`.

Then cause an eviction: make processing exceed `max.poll.interval.ms`. **Confirm the consumer is evicted mid-work and the batch is redone.** Then fix with a lower `max_poll_records`.

**Chart stall time for all four configurations.**

**Part 4 — The whole pipeline.** Assemble everything from section 09:

```
Postgres (outbox) → Debezium (outbox router) → Kafka → 4 consumers
```

Requirements:

| Requirement | |
|---|---|
| Zero events lost across 1,000 crash injections | |
| Every consumer idempotent | Verified by replay |
| Schema versioned with upcasting | |
| Search index rebuildable from offset 0 | **Verified byte-identical** |
| Notifier never replayed | Separate consumer, no replay flag needed |

**Then execute the full rebuild** — drop the search index, replay from zero, verify against the source database.

**Part 5 — Five failure scenarios.** Rehearse each, following only your runbook:

- Kill a broker mid-produce
- Stall a consumer group
- Inject a poison record into a partition
- **Stop Debezium and watch WAL accumulate**
- Ship an incompatible schema

For each: time to detection, time to mitigation, and data lost.

**The Debezium one should be the most severe.** Confirm `max_slot_wal_keep_size` bounds it, and measure how long you have before the disk fills.

**Part 6 — The ADR.** Decide Conduit's phase 5 substrate.

**Cite your own numbers**: the Redis Streams memory requirement for your retention, your measured throughput, and the specific requirement that decides it.

State what you are giving up, and name the trigger that would change the decision in either direction.

**Done when:**
- Your three-substrate comparison has the memory number that decides Redis Streams in or out
- The durability matrix shows `acks=all` with `min.insync.replicas=1` losing data
- Unclean leader election demonstrably discards committed records
- Your rebalance chart covers four configurations
- The full pipeline survives 1,000 crash injections with zero loss
- The search index rebuilds byte-identically from offset 0
- All five failure scenarios are rehearsed with measured detection times
- The ADR cites your numbers and names its reconsideration triggers
