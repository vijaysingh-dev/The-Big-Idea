# Field Service Basics

## When support has to physically go somewhere

Everything so far assumed support happens remotely. For a manufacturer selling industrial machinery, a large fraction of cases end with an engineer driving to a site with a part in the van.

**Field Service** is the licensed add-on that models that: work orders, scheduling against real technician availability, parts inventory, and a mobile app that works offline.

This note is an orientation rather than deep coverage — Field Service is a large product with its own certification track — but the object model and the decision points are worth knowing, because a manufacturing Service Cloud implementation will meet it.

## The object model

**Work Order.** The job to be done. Usually created from a Case, linked to an Account, Contact, and Asset. Has a status, priority, subject, and a duration estimate.

**Work Order Line Item.** Individual tasks within a work order. Replace the drive belt, calibrate the sensor, run the test cycle. Each can have its own duration and its own required skills.

**Service Appointment.** The scheduled visit. This is the object the scheduler actually works with — it carries the time window, the assigned resource, and the status. A work order can have several appointments if the job takes multiple visits.

**Service Resource.** A technician, or a piece of equipment, or a crew. Linked to a User for people.

**Service Territory.** A geographic area with operating hours. Resources are assigned to territories, and appointments are scheduled within them.

**Resource Absence.** Leave, training, or any period a resource is unavailable.

**Work Type.** A template for a kind of job — estimated duration, required skills, required parts. Applying a work type to a work order populates the rest.

**Skill and Service Resource Skill.** What a technician is qualified to do, with proficiency and an expiry date, which matters for certifications that lapse.

**Product Item, Product Request, Product Consumed.** Parts inventory: what is in the van, what needs ordering, what was used on the job.

```sql
SELECT Id, WorkOrderNumber, Status, Priority, Subject,
       Account.Name, Asset.Name, CaseId,
       (SELECT Id, Status, SchedStartTime, SchedEndTime,
               ServiceTerritory.Name, Duration
        FROM ServiceAppointments)
FROM WorkOrder
WHERE Status NOT IN ('Completed', 'Cannot Complete')
ORDER BY CreatedDate DESC
```

## How it connects to the case

The typical flow in a manufacturing support desk:

```
Case created                 → customer reports a machine fault
  ↓
Remote diagnosis             → agent works it, cannot resolve remotely
  ↓
Work Order created           → from the case, with a Work Type
  ↓
Work Order Line Items        → the specific tasks
  ↓
Service Appointment          → scheduled
  ↓
Dispatcher assigns resource  → manually or through optimization
  ↓
Technician completes on site → mobile app, offline capable
  ↓
Parts consumed recorded      → inventory decremented
  ↓
Work Order completed         → case updated and closed
```

Creating the work order from the case is the integration point most implementations build:

```java
public with sharing class WorkOrderCreationService {

    public static List<WorkOrder> createFromCases(Set<Id> caseIds, String workTypeName) {
        WorkType workType = [
            SELECT Id, EstimatedDuration, DurationType, DurationUnit
            FROM WorkType WHERE Name = :workTypeName LIMIT 1
        ];

        List<WorkOrder> workOrders = new List<WorkOrder>();
        for (Case c : [
            SELECT Id, AccountId, ContactId, AssetId, Subject, Description, Priority,
                   Machine__r.Site_Address__c
            FROM Case WHERE Id IN :caseIds
        ]) {
            workOrders.add(new WorkOrder(
                CaseId = c.Id,
                AccountId = c.AccountId,
                ContactId = c.ContactId,
                AssetId = c.AssetId,
                WorkTypeId = workType.Id,
                Subject = c.Subject,
                Description = c.Description,
                Priority = c.Priority,
                Status = 'New'
            ));
        }

        insert workOrders;
        return workOrders;
    }
}
```

Applying a **Work Type** is what makes this efficient — it carries the estimated duration, the required skills, and the standard line items, so a "Press Belt Replacement" work order arrives fully specified rather than needing manual completion.

## Scheduling

Three levels, and organizations move up this ladder as volume grows:

**Manual dispatch.** A dispatcher looks at the Gantt chart and assigns appointments. Fine at low volume.

**The Dispatcher Console.** A Gantt view showing resources, appointments, travel time, and territory boundaries, with drag-and-drop assignment and rule-based candidate suggestions.

**Enhanced Scheduling and Optimization.** An engine that assigns appointments automatically, optimizing across travel time, skills, priority, service level targets, and resource utilization. Runs on a schedule or in response to changes.

Optimization is where the return is largest, and also where the configuration effort is largest. It needs accurate durations, accurate skills, accurate territories, and accurate travel time estimates. Feeding it bad data produces schedules technicians ignore, which is worse than manual dispatch.

**Scheduling policies** define what the optimizer weights: is it minimizing travel, maximizing appointments per day, or prioritizing service level compliance? Different policies for different situations — an emergency policy that ignores travel efficiency to get someone there fast, a routine policy that clusters jobs geographically.

## The mobile app

The Field Service mobile app is the piece technicians actually use, and its defining feature is **offline capability**. A technician in a basement plant room with no signal must still be able to complete the job, record parts used, capture a signature, and take photos. Everything syncs when connectivity returns.

That constraint shapes what you can build. Offline means:

- Data must be pre-cached before the technician leaves connectivity
- Custom logic runs client-side, not as Apex
- Conflicts must be resolved on sync
- Anything requiring a callout does not work offline

Customization is through **mobile flows**, **quick actions**, and the app's own extension points rather than standard Lightning components. This is a genuinely different development model from the console, and assuming console patterns transfer is a common early mistake.

## Parts and inventory

**Product Item** records what stock exists at a location — a warehouse, a van, a customer site.

**Product Request** and **Product Transfer** handle ordering and moving parts.

**Product Consumed** records what was used on a work order, which decrements inventory and feeds billing.

For a manufacturer this connects to the ERP, which usually owns inventory as the system of record. The integration question is which system is authoritative for van stock — Salesforce for real-time visibility, the ERP for financial accuracy — and whether they reconcile nightly or continuously.

## Deciding whether to adopt it

Field Service is a substantial product with a substantial licence cost and a substantial implementation. The honest decision points:

**Adopt it when** you dispatch technicians regularly, scheduling is genuinely complex, parts inventory matters, and technicians need offline mobile access.

**Do not adopt it when** site visits are rare and ad hoc. A custom object with a date field and an owner handles a handful of visits a month perfectly well, and building that is a fraction of the cost.

The signal that it is needed: someone maintains a scheduling spreadsheet, and technicians are driving inefficient routes because nobody can see the whole picture.

The signal that it is not: the requirement is "we want to track site visits", and the volume is low.

## Where it touches the rest of the model

For the Northwind architecture from [[04.18 - End to End Enterprise Sales Cloud Design]]:

- `Machine__c` maps naturally onto the standard **Asset** object, which Field Service uses throughout. This is another argument for that choice, alongside the entitlement integration noted in [[05.5 - Entitlements, Milestones and SLAs]].
- Service contracts and entitlements determine whether a visit is billable, which the work order needs to know.
- Warranty claims and field visits are related but distinct — a claim is a commercial process, a work order is an operational one.
- The ERP owns parts pricing and billing, so completed work orders push consumption downstream.

## Practical guidance

**Use the standard Asset object for installed equipment** if field service is anywhere on the roadmap.

**Get durations and skills right before enabling optimization.** The engine is only as good as its inputs.

**Design for offline from the start.** Retrofitting offline capability onto an online-assumption design is a rewrite.

**Decide inventory ownership explicitly.** Salesforce and the ERP both tracking stock without a clear source of truth produces permanent reconciliation work.

**Do not adopt Field Service for low volume.** A custom object is the right answer more often than the product page suggests.
