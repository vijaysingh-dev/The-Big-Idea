# How to Approach a Frontend System Design Interview

The failure mode is not lack of knowledge — it is starting to design before knowing what is being designed. A candidate who spends five minutes on requirements and forty on a focused design outperforms one who spends forty-five minutes covering everything shallowly.

## The framework

A 45-minute round, roughly:

```
 5 min   Requirements and scope
 5 min   High-level architecture
10 min   Data model and API contract
15 min   Component and state design
 5 min   Performance and optimization
 5 min   Accessibility, error handling, edge cases
```

The interviewer will steer. The framework exists so you always have a next step rather than stalling.

## Requirements first

Never start drawing. Ask until the problem is bounded:

**Functional.** What must it do? What is explicitly out of scope? "Design a news feed" — does it support posting, or only reading? Comments? Reactions? Real-time updates?

**Scale.** How many items? A list of 50 and a list of 500,000 are different designs. How many concurrent users? How often does data change?

**Users and constraints.** Desktop, mobile web, or both? Which browsers? Is offline support needed? Is this an internal tool or a public product with SEO requirements?

**Non-functional.** How fresh must data be? What is the acceptable initial load time? Accessibility level? Internationalization and RTL?

Then state the scope back:

> "So: an infinite-scrolling feed, read-only, real-time updates for new posts, mobile-first, roughly 10,000 daily active users, no offline requirement. I will focus on the feed rendering and data layer, and treat authentication as a given."

That sentence is worth several minutes of design. It shows you scope before building, and it prevents the interviewer watching you solve the wrong problem.

## Frontend system design is not backend system design

The interviewer is not looking for database sharding or a message queue. The frontend-specific concerns:

| Backend focus | Frontend focus |
| --- | --- |
| Throughput, replication | Rendering strategy, bundle size |
| Database schema | Client state shape and cache |
| Service boundaries | Component boundaries |
| Horizontal scaling | Perceived performance |
| Consistency models | Optimistic updates and reconciliation |
| Rate limiting | Debouncing, pagination, cancellation |

You should know enough backend to discuss the API contract intelligently. The design work is on the client.

## What to cover

**Architecture.** Rendering strategy first, because it determines much else — CSR, SSR, SSG or a hybrid, and why ([[28.11 - Rendering Strategies]]). Then the layer diagram: components, state, data layer, API.

**Data model and API.** Sketch the response shapes. Cursor or offset pagination, and why ([[24.4 - Pagination and Infinite Scroll]]). REST, GraphQL, or a hybrid. What the client normalizes ([[20.7 - State Normalization]]).

**Component design.** The main components and their boundaries. Which are reusable. Where the state lives — and be specific: server state in a query cache, URL state for filters, local state for ephemeral UI ([[20.1 - Where State Should Live]]).

**Performance.** Virtualization for long lists, code splitting by route, image strategy, and the specific metric each addresses ([[19.5 - Virtualization and Windowing]]).

**Reliability.** Loading, error and empty states. Retry and cancellation. Error boundaries ([[24.2 - Loading Error and Empty States]]).

**Accessibility.** Keyboard navigation, focus management, announcements. Mentioning this unprompted is unusual and lands well ([[09.5 - Accessibility Fundamentals]]).

## Talk about tradeoffs, not choices

The strongest signal is comparing options and choosing for stated reasons:

> "Infinite scroll or pagination? Infinite scroll suits a feed, but it makes the footer unreachable and breaks back-navigation unless we restore scroll position and cached pages. Given this is a feed and there is no footer content, I would take infinite scroll with virtualization above about 200 items, and cursor pagination on the API so inserts do not cause duplicates."

That is one decision, one alternative, and the reason. Repeat that shape for each major choice.

Avoid absolutes. "Always use X" invites a counterexample; "X here because Y, though Z would be better if W" does not.

## Drawing

Keep diagrams simple and legible:

```
┌─────────────────────────────────────────┐
│  Components                             │
│  Feed → PostList → PostCard             │
├─────────────────────────────────────────┤
│  State                                  │
│  Query cache | URL params | local UI    │
├─────────────────────────────────────────┤
│  Data layer                             │
│  API client · schema validation · retry │
├─────────────────────────────────────────┤
│  Network — REST + WebSocket             │
└─────────────────────────────────────────┘
```

Component trees, data flow arrows and layer boxes. Not detailed code — write a signature or a state shape when it clarifies, and keep going.

## Common questions

**Infinite feed** — pagination strategy, virtualization, real-time updates, scroll restoration, media loading ([[28.14 - Case Study - News Feed]]).

**Autocomplete or typeahead** — debouncing, cancellation, caching, keyboard navigation, ARIA combobox semantics ([[28.15 - Case Study - Autocomplete]]).

**Chat** — transport choice, message ordering, optimistic sends, presence, reconnection ([[28.16 - Case Study - Chat Application]]).

**Collaborative editor** — conflict resolution, operational transform or CRDT, cursor presence, offline.

**Dashboard** — parallel data loading, widget-level error isolation, polling versus streaming, layout persistence.

**Design system** — token architecture, component API design, versioning, adoption ([[28.10 - Design Systems and Component Libraries]]).

**File upload** — chunking, resumption, progress, validation, concurrency limits.

The first three are the most common by a wide margin.

## Signals interviewers look for

**Requirements gathering.** Designing before scoping is the most common failure.

**Prioritization.** Recognizing what matters most for *this* problem rather than reciting a checklist.

**Depth on request.** Being able to go two levels deeper on any component you named.

**Awareness of failure modes.** What happens when the network is slow, the request fails, the list is empty, the user is offline.

**Communication.** Thinking aloud, checking in, adjusting when redirected.

**Honesty.** "I have not built that; here is how I would approach it" is far better than confident invention. Interviewers detect the latter reliably.

## Signals that hurt

- Jumping to a solution without questions
- Naming libraries instead of describing behavior — "I'd use Redux" is not a design
- Ignoring the interviewer's hints, which are usually the topic they want to explore
- Over-engineering — proposing micro frontends for a five-person team
- Silence while thinking; narrate instead
- Refusing to commit to a decision after weighing options

## Practising

Take a product you use and design it aloud in 45 minutes. Then look at how it actually behaves — open DevTools, watch the network panel, check whether the list is virtualized, see how it handles a throttled connection.

That exercise builds the vocabulary of real tradeoffs faster than reading about them, because you see what a team shipping at scale actually chose.

## How senior engineers actually approach this

**They scope before designing**, and state the scope back explicitly.

**They lead with the rendering strategy**, since it constrains everything downstream.

**They name a tradeoff for every decision**, rather than presenting choices as obvious.

**They raise accessibility and error states unprompted**, which most candidates omit entirely.

**They say what they do not know** and describe how they would find out.

## Common pitfalls

- Designing before requirements are clear.
- Treating it as a backend design question.
- Breadth with no depth — mentioning twenty things, explaining none.
- Library names substituting for design reasoning.
- Ignoring the interviewer's steering.
- Over-engineering for imagined scale.
- Skipping error, empty and loading states.

## Interview angle

This note *is* the interview angle. The compressed version: spend the first five minutes on requirements and state the scope back; lead with rendering strategy; give one alternative and one reason for every major decision; cover state placement, performance and failure modes explicitly; and raise accessibility before being asked. Depth on two or three things beats coverage of ten.
