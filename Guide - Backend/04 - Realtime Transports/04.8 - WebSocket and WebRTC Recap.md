## Where WebSocket Actually Fits

From [[04.1 - Choosing a Realtime Transport]], the rule is: **WebSocket when the client sends frequently.**

That is a narrower set of use cases than people assume:

| Use case | Client sends often? | Right answer |
|---|---|---|
| Progress updates | No | SSE |
| Notifications | No | SSE |
| Live dashboard | No | SSE |
| LLM token streaming | No | SSE |
| Log tailing | No | SSE |
| Chat with typing indicators | **Yes** | WebSocket |
| Collaborative editing | **Yes** | WebSocket |
| Live cursors | **Yes** | WebSocket |
| Multiplayer game state | **Yes** | WebSocket |
| Trading terminal with order entry | **Yes** | WebSocket |

💡 **The honest test: if you removed the client-to-server direction, would the feature still work?** If yes, use SSE. WebSocket costs you a separate protocol, a separate auth story, separate proxy configuration, separate observability, and a separate reconnection implementation — pay that only when you need the upstream channel.

### What WebSocket genuinely gives you

| Advantage | Matters when |
|---|---|
| Client→server without a new request | Frequent small messages upstream |
| Binary frames | Protobuf, MessagePack, media chunks |
| Lower per-message overhead | Thousands of messages per second |
| Subprotocol negotiation | Versioning your message contract |

⚠️ **The per-message overhead point is real at high rates.** An SSE event costs ~20 bytes of framing; a WebSocket frame costs 2–14 bytes. At 10,000 messages per second per client that difference matters. Below a few hundred per second it does not.

## What Section 04 Adds

Everything in sections 04.3 through 04.7 applies to WebSocket unchanged. The existing guide covers the protocol; these are the operational requirements.

### Heartbeats — you must implement them

SSE lets you send a comment line. WebSocket has protocol-level ping/pong frames:

```python
async def heartbeat(ws, interval: float = 20.0, timeout: float = 10.0):
    while True:
        await asyncio.sleep(interval)
        try:
            pong = await asyncio.wait_for(ws.ping(), timeout=timeout)
            await pong
        except (TimeoutError, ConnectionClosed):
            await ws.close(code=1001, reason="heartbeat_timeout")
            break
```

⚠️ **Browsers respond to protocol pings automatically but do not expose them to JavaScript.** So a protocol ping proves the *browser* is alive, not that your application code is running. For detecting a wedged tab you need an application-level ping in your own message format.

Most production systems use both: protocol ping for the network path, application ping for the application.

### Replay — you must build it

SSE gives you `Last-Event-ID` for free. WebSocket gives you nothing.

```python
# On connect, the client sends its cursor
{"type": "subscribe", "topic": "doc-42", "since": 1043}

# Server replays, then goes live
for event in log.since(1043):
    await ws.send_json(event)
await ws.send_json({"type": "live"})       # marker: you are now current
```

⚠️ **The `live` marker matters.** Without it the client cannot distinguish replayed history from live events, which breaks any UI that animates new arrivals differently.

The same buffer-overflow case applies: if the cursor is too old, send `resync_required` rather than silently continuing ([[04.2 - Server Sent Events]]).

### Backpressure — same pattern, both directions

The fanout pattern from [[04.7 - Presence Fanout and Backpressure]] applies unchanged: bounded queue per client, writer task, explicit drop policy.

WebSocket adds a second direction. **A client can flood you.**

```python
class RateLimitedConnection:
    def __init__(self, ws, max_per_second: int = 50, max_message_bytes: int = 64 * 1024):
        self.bucket = TokenBucket(rate=max_per_second, capacity=max_per_second * 2)
        self.max_message_bytes = max_message_bytes

    async def receive(self):
        msg = await self.ws.receive()
        if len(msg) > self.max_message_bytes:
            await self.ws.close(code=1009, reason="message_too_big")
            raise ConnectionClosed()
        if not self.bucket.consume():
            await self.ws.close(code=1008, reason="rate_limit")
            raise ConnectionClosed()
        return msg
```

⚠️ **An unrated WebSocket endpoint is a denial-of-service vector.** A client can send messages as fast as it can generate them, and each one costs you parsing, authorisation and fanout. Rate limit inbound messages and cap message size. Close code 1009 exists specifically for oversized messages.

### Auth — the ticket pattern

The browser `WebSocket` constructor cannot set headers ([[04.1 - Choosing a Realtime Transport]]). Use a short-lived single-use ticket obtained over authenticated HTTP:

```python
@app.post("/ws/ticket")
async def create_ticket(user: User = Depends(current_user)):
    ticket = secrets.token_urlsafe(32)
    await redis.setex(f"ws_ticket:{ticket}", 30, str(user.id))
    return {"ticket": ticket}

@app.websocket("/ws")
async def ws_endpoint(ws: WebSocket, ticket: str):
    user_id = await redis.getdel(f"ws_ticket:{ticket}")     # atomic single-use
    if user_id is None:
        await ws.close(code=1008)
        return
    await ws.accept()
```

`GETDEL` makes it single-use atomically. 30 seconds is long enough for a connection attempt and short enough that a leaked ticket in a log is harmless.

⚠️ **Re-authorise periodically on long-lived connections.** A user whose access is revoked should stop receiving data within minutes, not when they happen to reconnect. Either re-check on a timer, or enforce a maximum connection lifetime ([[04.6 - Scaling Long Lived Connections]]).

### Proxy configuration

```nginx
location /ws {
    proxy_pass http://app;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

The `Upgrade` and `Connection` headers are mandatory — without them the handshake fails with a confusing 400. `proxy_read_timeout` must exceed your heartbeat interval by a comfortable margin.

## Where WebRTC Fits

WebRTC is for **media between peers**, and essentially nothing else in backend work.

| Use case | WebRTC? |
|---|---|
| Video or audio call | **Yes** |
| Screen sharing | **Yes** |
| Live video broadcast to many viewers | Yes, with an SFU |
| Large file transfer between users | Possibly, via data channel |
| Chat messages | **No.** WebSocket |
| Game state | **No** in almost all cases. WebSocket |
| Anything server-to-client | **No** |

💡 **The reason WebRTC is not a general realtime transport is that it is peer-to-peer by design.** Your server is not a peer — it is a signalling coordinator and, when direct connection fails, a relay. Using it for server-to-client data means running a TURN server and an SFU to reimplement what WebSocket does natively.

### What your backend actually does for WebRTC

Even in a WebRTC product, most of your backend work is not WebRTC:

| Component | Your responsibility |
|---|---|
| **Signalling** | Exchange SDP offers and ICE candidates — **usually over WebSocket** |
| **STUN** | Usually a public server; low cost |
| **TURN** | You run it, you pay the bandwidth. 10–20% of connections need it |
| **SFU** | For multi-party. Significant infrastructure |
| **Recording** | Server-side media pipeline |

⚠️ **Signalling is a WebSocket application**, which is why WebRTC appears in this section at all. Everything in 04.6 and 04.7 applies to your signalling layer — backplane, presence, fanout, backpressure.

The media path does not touch your servers at all in the peer-to-peer case, which is the entire point.

## In Production

### Running WebSocket alongside HTTP

Same warnings as SSE ([[04.3 - SSE in Production]]), plus:

| Issue | Note |
|---|---|
| `--limit-concurrency` counts WS connections | Same starvation trap |
| Deploys drop every connection | Reconnect storm, needs jitter |
| L4 load balancers pin connections | New pods get no traffic |
| Long connections outlive credentials | Needs re-auth or max lifetime |
| Metrics look wrong | One "request" lasting hours |

💡 **Separate your WebSocket service from your API service**, for the same reasons as SSE: different scaling shape, different deploy tolerance, different limits.

### Close codes carry meaning

```python
1000  # normal closure
1001  # going away — server shutting down. Client should reconnect
1008  # policy violation — auth failure, rate limit. Client should NOT retry blindly
1009  # message too big
1011  # internal error
1013  # try again later — overloaded. Client should back off
```

⚠️ **Clients should branch on the close code.** Reconnecting immediately after a 1008 auth failure produces an infinite loop hammering your service. Reconnecting after 1001 is correct and expected.

Send a reason string too — it costs nothing and it is the only diagnostic your client-side logs will have.

### Compression

`permessage-deflate` is negotiated per connection. It helps for repetitive JSON and costs CPU and memory per connection.

⚠️ **The memory cost is per-connection and not small** — a deflate context is tens of KB. At 50,000 connections that is gigabytes. Enable it only when your messages are large and repetitive, and measure.

For small frequent messages, compression is usually a loss.

## Codebase

**Repo:** `python-websockets/websockets`, `centrifugal/centrifugo`, `pion/webrtc`

**Question to answer:** In the `websockets` library, how are ping/pong and connection liveness handled, and what happens to a client whose write buffer fills? Then: in pion, what is the minimum a signalling server must do, and why is it always a separate protocol from WebRTC itself?

**Read, in order:**

1. `websockets/src/websockets/asyncio/connection.py` — the connection lifecycle, keepalive task, and close handshake. **Look at how it bounds the write buffer** — the same pattern as [[04.7 - Presence Fanout and Backpressure]]
2. `websockets/src/websockets/frames.py` — frame encoding and masking, for comparison with your existing guide
3. `centrifugo/internal/client/client.go` — a production WebSocket server with queueing, rate limiting and presence. **Note how much is transport-independent**
4. `pion/webrtc/examples/` — the signalling examples. **The answer to the second question:** WebRTC has no signalling protocol by design, because the peers cannot talk to each other until signalling completes. Something out-of-band must bootstrap it, and that something is your WebSocket server
5. `pion/turn` — a TURN server implementation, if you want to understand the relay cost

💡 The signalling point is worth internalising: **WebRTC deliberately does not specify signalling**, leaving it to the application. That is why every WebRTC tutorial starts by building a WebSocket server. Your backend skills are the load-bearing part of a WebRTC product, not the media handling.

**Size:** 1 session.

**Part 1 — WebSocket with everything.** Ticket auth, dual heartbeats, inbound rate limiting and size caps, cursor replay with a `live` marker, bounded outbound queues with per-event-type policies, and close codes with reasons.

Reuse the fanout machinery from drill 4.6 unchanged — **that reuse is the point**, and if it does not slot in cleanly your abstraction was transport-coupled.

**Part 2 — SSE versus WebSocket, measured.** The same feature — document annotation with presence — implemented over both. For SSE, upstream messages go via normal POST requests.

Measure at 500 clients, at three upstream message rates (1/min, 1/sec, 10/sec per client):

| Metric | |
|---|---|
| Server CPU | |
| Bytes transferred | |
| Upstream message latency | |
| Downstream event latency | |
| Lines of code | |
| Configuration complexity | Subjective, but write it down |

**Find the upstream rate at which WebSocket clearly wins.** Below it, SSE plus POST is simpler and comparable. Having this crossover as a measured number rather than an opinion is the deliverable.

**Part 3 — Client flood.** No inbound rate limiting. A client sends 10,000 messages per second.

Measure server CPU, event loop lag, and the effect on other clients.

Then add rate limiting and size caps. Confirm the flooding client is closed with 1008 and everyone else is unaffected.

Then test the message-size attack separately: a single 100MB message. Confirm it is rejected before allocation.

**Part 4 — Close code handling.** A client that reconnects on any disconnect, with no code branching. Trigger a 1008 auth failure.

Watch the infinite reconnect loop. Measure the request rate it generates.

Then implement proper branching: retry on 1001 and 1013 with backoff, stop on 1008, resync on 1013. Confirm the loop is gone.

**Part 5 — Deploy storm.** 1,000 WebSocket clients. Rolling restart.

Compare to the SSE deploy storm from drill 4.2. Chart both. Apply jittered reconnect and staggered shutdown, and chart again.

**Part 6 — Signalling.** A minimal WebRTC signalling server over WebSocket: room join, SDP offer/answer exchange, ICE candidate relay.

Get two browsers connected peer-to-peer with a data channel. Then block direct connectivity with a firewall rule and observe the connection failing without TURN.

Write in `FINDINGS.md`: exactly which parts of this were WebRTC and which were ordinary WebSocket backend work. **The ratio will surprise you** and it is the practical argument of this note.

**Done when:**
- Your fanout machinery slotted into WebSocket without modification
- You have a measured upstream-rate crossover between SSE and WebSocket
- A flooding client is isolated and closed without affecting others
- The reconnect loop is reproduced and fixed with close-code branching
- Deploy storm charts exist for both transports, with mitigations
- Two browsers are connected peer-to-peer, and you have written down how little of that was WebRTC-specific
