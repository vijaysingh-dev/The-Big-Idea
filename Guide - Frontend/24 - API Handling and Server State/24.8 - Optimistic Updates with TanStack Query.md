# Optimistic Updates with TanStack Query

The mutation lifecycle gives four callbacks, and the optimistic pattern uses all of them.

```jsx
const { mutate } = useMutation({
  mutationFn: toggleLike,

  onMutate: async (postId) => {
    // 1. Cancel in-flight refetches so they cannot overwrite the optimistic write
    await queryClient.cancelQueries({ queryKey: postKeys.detail(postId) });

    // 2. Snapshot for rollback
    const previous = queryClient.getQueryData(postKeys.detail(postId));

    // 3. Apply optimistically
    queryClient.setQueryData(postKeys.detail(postId), (old) =>
      old && { ...old, liked: !old.liked, likeCount: old.likeCount + (old.liked ? -1 : 1) }
    );

    // 4. Return context for the error handler
    return { previous };
  },

  onError: (err, postId, context) => {
    queryClient.setQueryData(postKeys.detail(postId), context.previous);
  },

  onSettled: (data, err, postId) => {
    queryClient.invalidateQueries({ queryKey: postKeys.detail(postId) });
  },
});
```

## Why each step matters

**`cancelQueries` is not optional.** Without it, a background refetch started before the mutation can resolve *after* the optimistic write and overwrite it with pre-mutation data. The user sees their change apply and then silently revert a moment later — a bug that is intermittent and very hard to reproduce ([[04.6 - AbortController and Cancellation]]).

**The snapshot must be restored, not inverted.** With two toggles in flight, applying the inverse produces the wrong result. Restoring the captured value is correct regardless of concurrency ([[24.5 - Optimistic UI]]).

**The context object** is whatever `onMutate` returns, passed to `onError` and `onSettled`. This is how the snapshot travels between callbacks.

**`onSettled` runs on both success and failure**, so invalidation happens either way — reconciling the cache with the server after a success, and correcting any drift after a rollback.

## Updating several caches

A mutation usually affects both a detail entry and the lists containing it:

```jsx
onMutate: async (updated) => {
  await queryClient.cancelQueries({ queryKey: productKeys.all });

  const previousDetail = queryClient.getQueryData(productKeys.detail(updated.id));
  const previousLists = queryClient.getQueriesData({ queryKey: productKeys.lists() });

  queryClient.setQueryData(productKeys.detail(updated.id), updated);

  queryClient.setQueriesData({ queryKey: productKeys.lists() }, (old) =>
    old && { ...old, items: old.items.map(p => p.id === updated.id ? updated : p) }
  );

  return { previousDetail, previousLists };
},

onError: (err, updated, context) => {
  queryClient.setQueryData(productKeys.detail(updated.id), context.previousDetail);
  context.previousLists.forEach(([key, data]) => queryClient.setQueryData(key, data));
},
```

`getQueriesData` returns every matching entry as `[key, data]` pairs, which is what makes rolling back multiple list variants possible.

Note the updater guards on `old &&` — an entry may not exist, and writing `undefined` into the cache creates a phantom entry.

## Adding items optimistically

```jsx
onMutate: async (newTodo) => {
  await queryClient.cancelQueries({ queryKey: todoKeys.lists() });
  const previous = queryClient.getQueryData(todoKeys.list());

  const optimistic = {
    ...newTodo,
    id: `temp-${crypto.randomUUID()}`,
    pending: true,
  };

  queryClient.setQueryData(todoKeys.list(), (old) => [...(old ?? []), optimistic]);

  return { previous, tempId: optimistic.id };
},

onSuccess: (created, _vars, context) => {
  queryClient.setQueryData(todoKeys.list(), (old) =>
    old?.map(t => t.id === context.tempId ? created : t)
  );
},
```

The temporary id must be **unique and stable** for the item's lifetime, or React reconciliation attaches state to the wrong row ([[16.6 - Lists and Keys]]). The `temp-` prefix makes it trivially checkable so navigation code never uses it.

Replacing the temp item in `onSuccess` avoids a visible flicker between the optimistic row disappearing and the refetched row appearing.

## Deriving pending state from the mutation cache

Rather than writing optimistic entries, the pending mutation itself can drive the UI:

```jsx
function TodoList() {
  const { data: todos } = useQuery(todoQuery());

  const pendingTodos = useMutationState({
    filters: { mutationKey: ["addTodo"], status: "pending" },
    select: (m) => m.state.variables,
  });

  return (
    <ul>
      {todos.map(t => <Todo key={t.id} todo={t} />)}
      {pendingTodos.map((t, i) => <Todo key={`pending-${i}`} todo={t} pending />)}
    </ul>
  );
}
```

This is simpler for the append case: no cache writes, no snapshots, no rollback. If the mutation fails, the entry vanishes on its own because the mutation leaves the pending state.

The tradeoff is that it only shows in components that query the mutation state, whereas a cache write is visible everywhere the data is read.

## Showing pending state

```jsx
const isPending = Boolean(
  queryClient.isMutating({ mutationKey: ["updateProduct", id] })
);

<div style={{ opacity: isPending ? 0.6 : 1 }}>
```

Or, more directly, mark the optimistic entry:

```jsx
{ ...updated, _optimistic: true }
```

The user should be able to tell a change has not yet been confirmed without being blocked from continuing.

## Retry and offline

```jsx
useMutation({
  mutationFn: updateProduct,
  retry: 3,           // ONLY if the endpoint is idempotent
  networkMode: "offlineFirst",
});
```

Mutations do not retry by default, which is correct — a POST is not idempotent, and a retry can create a duplicate. Enabling retry requires either an idempotent endpoint or an idempotency key ([[24.3 - Retries Timeouts and Cancellation]]).

`networkMode: "offlineFirst"` queues the mutation while offline and fires it on reconnect. Combined with mutation persistence, this gives basic offline support — though conflict resolution remains your problem ([[28.12 - Real Time and Offline First]]).

## Common failure modes

**Skipping `cancelQueries`.** The single most common bug in this pattern, and the resulting revert is intermittent.

**Mutating the cached object.** The cache compares by reference, so an in-place mutation produces no re-render and corrupts the snapshot, which now points at the mutated object ([[06.7 - Immutable Data Patterns]]):

```jsx
// Broken — the snapshot now reflects the change too
setQueryData(key, (old) => { old.liked = true; return old; });
```

**Rollback that undoes a concurrent mutation.** Two mutations, the first fails, and restoring its snapshot also reverts the second. Cancelling in-flight mutations for the same entity, or invalidating in `onSettled`, limits the damage.

**Optimistically predicting server-computed values.** A derived total, a re-sorted position, or a server-generated timestamp will not match, producing a visible correction when the real data arrives.

## When invalidation alone is enough

```jsx
useMutation({
  mutationFn: updateProduct,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: productKeys.all }),
});
```

If the mutation is fast and the operation is not on a hot interaction path, plain invalidation is correct, simpler, and always consistent with the server.

Reserve the optimistic pattern for interactions where latency is genuinely felt — toggles, reordering, inline edits, anything the user repeats rapidly ([[24.5 - Optimistic UI]]).

## How senior engineers actually use this

**They always start `onMutate` with `cancelQueries`.**

**They snapshot and restore**, never invert.

**They invalidate in `onSettled`**, so the cache reconciles with the server on both paths.

**They use `useMutationState` for append-only cases**, which avoids the whole snapshot dance.

**They reserve the pattern for interactions where it is felt**, and use plain invalidation everywhere else.

## Common pitfalls

- No `cancelQueries`, so a background refetch reverts the optimistic write.
- Mutating cached objects in the updater.
- Inverting instead of restoring on rollback.
- Temporary ids leaking into navigation or requests.
- Enabling mutation retry on a non-idempotent endpoint.
- Optimistically showing values the server computes.
- Silent rollback with no user-visible explanation.

## Interview angle

"How would you implement optimistic updates" invites the four-step lifecycle: cancel in-flight queries, snapshot, apply, and roll back from the snapshot on error with invalidation on settle. The step that distinguishes a real answer is `cancelQueries` — explaining that without it, a refetch already in flight can land after the optimistic write and silently revert it. Adding that rollback must restore rather than invert, because of concurrent mutations, shows you have debugged this rather than copied it.
