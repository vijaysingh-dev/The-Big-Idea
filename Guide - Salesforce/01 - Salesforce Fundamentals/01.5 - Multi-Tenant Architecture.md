# Multi-Tenant Architecture

## The question this answers

Thousands of companies run on Salesforce. They all have different objects, different fields, different validation rules. Yet there is one codebase, one set of servers, and one upgrade that happens to everyone on the same weekend.

How can one physical database hold your custom object and someone else's custom object, with different columns, and still be fast?

The answer explains almost every constraint you will meet on this platform.

## Single-tenant versus multi-tenant

**Single-tenant** is the normal enterprise model. Each customer gets their own application instance and their own database. Customization means changing that customer's schema and code. Upgrades happen per customer, on their schedule. Costly to run, and every customer drifts into a slightly different version.

**Multi-tenant** means one running application and one database serving all customers, with data separated logically rather than physically. Every customer runs the same version of the same code at the same time.

The tenant boundary is the **org** (organization), identified by a 15 or 18 character Org ID. Every record in the shared database carries that Org ID, and the platform adds a filter on it to every single query before it runs. You have never written that filter and you cannot remove it.

## How different customers share one table

Here is the part that surprises people. When you create a custom object `Property__c` with ten custom fields, Salesforce does **not** create a table called `Property__c` with ten columns.

Instead there is a small number of very large internal tables shared by everyone. The essential idea:

- A **metadata layer** stores the *definition* of your object and fields — names, data types, relationships, picklist values. This is one row per field definition, not a table structure.
- A **data layer** stores actual record values in a wide, generic table with a large number of untyped columns, plus the Org ID, the object type, and the record ID.
- **Pivot tables** hold denormalized copies of specific things that need to be searchable or unique, such as indexed fields, foreign keys, and unique constraints.

So your `Purchase_Price__c` field is not a `DECIMAL` column. It is a value in a generic slot, described by a metadata row that says "for org 00D..., on object Property__c, slot 7 is a currency field called Purchase_Price__c".

Salesforce calls this the **universal data dictionary**. When you run SOQL, the query engine reads the metadata, works out which slots your fields map to, and rewrites your query into one against the shared tables with your Org ID applied.

Two consequences follow immediately:

**Creating a field is instant and non-blocking.** You are inserting a metadata row, not running `ALTER TABLE` on a table with billions of rows. This is genuinely remarkable and is why platform customization feels so fast.

**You cannot use normal database tuning.** There is no query planner you control, no index you create directly, no execution plan you rewrite. Indexes on the platform are managed for you, and getting a non-standard one requires asking Salesforce Support. See [[08.9 - Indexes and Selective Queries]].

## Why governor limits exist in exactly this form

Since your code and another customer's code run on the same application servers, one badly written loop could degrade service for everyone else. There are two ways to prevent that: give each tenant dedicated resources, which defeats the economics, or cap what any single transaction may consume.

Salesforce chose the cap, enforced by throwing an exception the moment you cross it.

This is why the limits are shaped the way they are. They are not performance guidance. They are a fairness mechanism, and that is why they fail hard rather than degrading gracefully:

- 100 SOQL queries per synchronous transaction
- 50,000 records retrieved per transaction
- 150 DML statements per transaction
- 10 seconds of CPU time in a synchronous transaction
- 6 MB heap
- 100 callouts, 120 seconds total callout time

Notice they are all *per transaction*, not per day. Salesforce does not care how much work you do in total. It cares that no single request monopolizes a server. That distinction is the key to designing around them: split work into more, smaller transactions. Section 12 and section 16 are largely about doing exactly that.

## Things that make sense once you know this

**Why queries get slow without an index.** Your filter runs against a shared table containing every customer's data for that object type. Without a selective index, the engine cannot narrow the search efficiently. A query is considered *selective* when its filter uses an indexed field and matches a small enough fraction of rows. Non-selective queries against large objects fail outright with a timeout error. See [[08.10 - Query Plan Tool and Query Optimization]].

**Why data skew matters.** If one Account owns 300,000 Contacts, operations touching that Account cause lock contention on shared structures and sharing recalculation storms. In a single-tenant database this would be merely slow. Here it can affect performance across the org. See [[10.9 - Data Skew]].

**Why sharing recalculation is expensive.** Record access is not computed at read time. It is materialized into share tables, so changing a role hierarchy or an ownership pattern triggers a background recalculation across potentially millions of share rows. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

**Why skinny tables exist.** For very large objects, Salesforce Support can create a *skinny table* — a flattened copy containing only the frequently used fields, kept in sync automatically, which avoids joining across the standard and custom field structures. You cannot create one yourself. See [[16.9 - Skinny Tables and Custom Indexes]].

**Why upgrades are not optional.** Everyone runs the same code, so everyone upgrades together, three times a year. See [[01.11 - Release Cycle, Trust and Status]].

**Why your org ID appears everywhere.** Record IDs, session IDs, deployments, and support cases are all scoped to the org because it is the tenant boundary.

```java
System.debug('Org Id: ' + UserInfo.getOrganizationId());
System.debug('Instance: ' + URL.getOrgDomainUrl().toExternalForm());
```

## Instances, pods, and Hyperforce

Salesforce runs many isolated infrastructure units. Historically these were **pods** or **instances** with names like NA45 or EU16; each hosts many orgs, and your org lives on exactly one. More recently, **Hyperforce** re-platformed this onto public cloud infrastructure, which enables data residency in specific countries — increasingly a legal requirement.

What this means practically: performance issues can be instance-wide and nothing to do with your code, which is why checking Salesforce Trust before debugging a sudden slowdown is a real troubleshooting step, not a joke. Maintenance windows and release dates are also scheduled per instance.

## How this changes the way you write code

**Design for the limits from the first line.** Not "make it work, then optimize". On this platform the first version either respects the limits or it does not run at all at scale.

**Assume every query needs a selective filter.** In a dev org with fifty records everything is fast. Nothing you learn about performance in a small org transfers.

**Never assume you have the machine to yourself.** Your trigger shares its transaction with flows, validation rules, managed packages, and other triggers, all drawing from the same limit budget. See [[07.13 - Order of Execution]].

**Read the errors as tenancy messages.** `Too many SOQL queries`, `Apex CPU time limit exceeded`, `UNABLE_TO_LOCK_ROW`, `Query non-selective` — every one of these is the multi-tenant architecture telling you that your design is asking for more than its share.
