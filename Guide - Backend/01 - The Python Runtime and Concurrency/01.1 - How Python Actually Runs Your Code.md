# How Python Actually Runs Your Code

#backend #python #runtime

> **In one line:** Python compiles your source to bytecode, then a C loop reads that bytecode one instruction at a time and does what it says. Everything slow about Python comes from that loop, and everything fast about Python comes from escaping it.

---

## The Idea

People say "Python is interpreted" and stop there. That is not enough to be useful.

What actually happens is two steps:

1. **Compile.** Your `.py` file is turned into **bytecode** — a simple list of instructions for a made-up machine. This happens once and gets cached in `__pycache__`.
2. **Execute.** A big C function reads those instructions one at a time and does them. This is the **eval loop**, and it is where your program spends its life.

So Python is compiled *and* interpreted. It is compiled to bytecode, and the bytecode is interpreted.

Why you should care: when your API endpoint is slow, the cause is one of three things — you are running too many bytecode instructions, you are waiting on I/O, or you are waiting on a lock. Knowing which one it is comes from understanding this pipeline.

## How It Really Works

### Step 1 — Source to bytecode

```
your_code.py
   │
   ▼  tokenizer          "def", "add", "(", ...
   ▼  parser             builds an Abstract Syntax Tree (AST)
   ▼  compiler           walks the tree, emits instructions
   ▼
code object              bytecode + constants + names + flags
   │
   ▼  cached as __pycache__/your_code.cpython-313.pyc
```

An **AST** (Abstract Syntax Tree) is your code represented as a tree structure — a function call is a node with children for its arguments. You can see it:

```python
import ast
print(ast.dump(ast.parse("x = a + 1"), indent=2))
```

### Step 2 — Look at the bytecode

This is the part almost nobody does, and it takes ten seconds.

```python
import dis

def add_tax(price):
    return price * 1.18

dis.dis(add_tax)
```

```
  2           RESUME                   0
  3           LOAD_FAST                price
              LOAD_CONST               1.18
              BINARY_OP                5 (*)
              RETURN_VALUE
```

Five instructions. Each one is a case in a giant C switch statement. `LOAD_FAST` pushes a local variable onto a stack, `BINARY_OP` pops two things and multiplies them, `RETURN_VALUE` pops the result and returns.

Python's virtual machine is a **stack machine** — instructions do not name registers, they push and pop from a stack.

### Step 3 — The code object

The bytecode is not alone. It lives inside a **code object** with everything needed to run it.

```python
def add_tax(price):
    return price * 1.18

c = add_tax.__code__
c.co_code        # the raw bytecode bytes
c.co_consts      # (None, 1.18)
c.co_varnames    # ('price',)
c.co_names       # global names it references
c.co_argcount    # 1
c.co_flags       # bit flags — is it a generator? a coroutine?
```

`co_flags` matters later. When you write `async def`, the compiler sets a flag on the code object marking it a coroutine. That is literally how Python knows the difference.

### Step 4 — Frames

Every function call creates a **frame** — a small object holding the local variables, the value stack, and a pointer to the current instruction.

```
Frame: handle_request        ← currently executing
  ├── locals: {request: ..., db: ...}
  ├── value stack: [...]
  └── instruction pointer: 42
        │
        │ calls
        ▼
Frame: fetch_user
  ├── locals: {user_id: 7}
  └── ...
```

Frames are chained to their caller. That chain is exactly what you see in a traceback — a traceback is a walk up the frame chain.

```python
import sys
def inner():
    f = sys._getframe()
    while f:
        print(f.f_code.co_name)
        f = f.f_back
```

💡 This is how py-spy works. It reads another process's memory, finds the frame chain, and prints it — without stopping the process.

### Step 5 — The eval loop

In CPython the loop lives in `Python/ceval.c`, in a function called `_PyEval_EvalFrameDefault`. Simplified to death:

```c
for (;;) {
    opcode = *next_instr++;
    switch (opcode) {
        case LOAD_FAST:  PUSH(frame->localsplus[oparg]); break;
        case BINARY_OP:  right = POP(); left = POP();
                         PUSH(PyNumber_Multiply(left, right)); break;
        case RETURN_VALUE: return POP();
        ...
    }
}
```

That is the whole thing. Fetch an instruction, switch on it, do the work, repeat.

## Why Python Is Slow

Not because it is "interpreted." Because of four specific costs.

### 1. Dispatch overhead

For `price * 1.18`, C does one CPU instruction. Python does: fetch opcode, jump in switch, read the stack, call a generic multiply function, allocate a result object, push it back. Maybe 100x the work for the same arithmetic.

### 2. Everything is an object

```python
x = 5
```

`x` is not 8 bytes on the stack. It is a pointer to a `PyLongObject` on the heap, with a reference count, a type pointer, and the digits. A Python integer costs ~28 bytes. A list of a million ints is a million pointers to a million separate objects, scattered across memory. Your CPU cache hates this.

### 3. Dynamic lookup

```python
user.name
```

The type of `user` is unknown until runtime. Every attribute access is a dictionary lookup, possibly walking the class hierarchy. Compiled languages resolve this at compile time to a fixed memory offset.

### 4. Reference counting

Every object has a counter. Every time you pass it around, the counter goes up and down.

```python
import sys
a = [1, 2, 3]
b = a
sys.getrefcount(a)     # 3 — a, b, and the argument to getrefcount
```

When it hits zero the object is freed immediately. That is nice — deterministic cleanup, no GC pause. But it means constant small writes to memory, which is why the GIL exists (see [[01.2 - The GIL]]).

Reference counting cannot free **cycles** — `a` points to `b`, `b` points to `a`, nothing else points to either. So CPython also has a separate **generational garbage collector** that periodically hunts for cycles.

```python
import gc
gc.get_threshold()      # (2000, 10, 10) — how often each generation is scanned
gc.freeze()             # move current objects out of GC scanning entirely
```

## How Modern Python Fights Back

Python 3.11 onwards is meaningfully faster, and the reasons are worth knowing.

### Specializing adaptive interpreter (3.11+)

The interpreter watches which types actually flow through each instruction, then rewrites that instruction in place with a specialized version.

```
First few runs:   BINARY_OP  (generic — handles any types)
After warmup:     BINARY_OP_ADD_INT  (assumes ints, checks, fast path)
```

If the assumption breaks — you suddenly pass a string — it falls back to the generic version. This is a cheap form of what JIT compilers do.

⚠️ **Practical consequence:** code that keeps types stable is now measurably faster than code that does not. A function that receives `int` sometimes and `float` other times will de-specialize and stay slow.

### Cheaper function calls (3.11+)

Python function calls used to allocate a C stack frame per Python frame. Now Python frames live in a contiguous chunk and calling a Python function from Python does not recurse into C. Recursion and deep call stacks got much faster.

### Free-threaded builds (3.13 experimental, 3.14 supported)

A build of CPython with no GIL at all. Threads can run Python bytecode in genuine parallel. It comes with a single-thread performance cost and needs C extensions to be rebuilt for it, so it is not yet the default. Covered properly in [[01.2 - The GIL]].

### JIT (3.13 experimental)

A copy-and-patch JIT that compiles hot bytecode to machine code. Small gains so far, but the groundwork for larger ones.

## In Production

### Where the time actually goes in a web request

For a typical FastAPI endpoint doing one database query, the breakdown looks roughly like:

```
Total 45ms
├── Network in / ASGI parsing         2ms
├── Routing, validation (Pydantic)    3ms
├── Your Python business logic        1ms    ← almost nothing
├── Database query wait              35ms    ← almost everything
├── Serialization to JSON             3ms
└── Network out                       1ms
```

💡 **This is the most important number in this note.** For most backend services, Python's slowness is not your bottleneck. Waiting is. That is exactly why async matters more than raw speed, and why "rewrite it in Go" is usually the wrong first answer.

The exception is CPU-heavy endpoints — parsing large payloads, image work, big loops over data. There, the eval loop is the bottleneck and you should push the work into C (numpy, polars, orjson, Rust extensions) or out of the request path entirely.

### Practical speedups, in order of payoff

| Move | Typical gain | Cost |
|---|---|---|
| Fix the N+1 query | 10–100x | Low. Do this first, always |
| Use `orjson` instead of `json` | 2–5x on serialization | Trivial |
| Stop doing CPU work in the request path | Depends | Medium — needs a queue |
| Upgrade Python version | 10–40% since 3.10 | Low. Free performance |
| Replace a hot loop with numpy/polars | 10–100x | Medium |
| Rewrite the hot function in Rust (PyO3) | 10–100x | High |
| Rewrite the service in Go | 2–5x | Very high. Rarely correct |

⚠️ **Never optimize before profiling.** The function you think is slow is almost never the function that is slow. Use py-spy, see [[01.12 - Profiling and Debugging Async Services]].

### The `__pycache__` gotcha

Bytecode is cached by source path plus modification time. In containers, if you build an image and the timestamps are all identical, or the cache directory is not writable, Python recompiles every module on every start. On a large codebase this adds seconds to cold start.

```dockerfile
# Precompile at build time so runtime never pays for it
RUN python -m compileall -q /app
```

## Common Misunderstandings

| Belief | Reality |
|---|---|
| "Python is interpreted line by line" | It is compiled to bytecode first. Syntax errors in a function you never call still stop your program at import |
| "`.pyc` files are compiled like C" | They are bytecode for Python's VM, not machine code. They are not faster to run, only faster to load |
| "Python has no compiler" | It does. `compile()` is a builtin |
| "The GC handles all memory" | Reference counting handles almost all of it. The GC only handles cycles |
| "Python is slow so my API is slow" | Your API is usually waiting on I/O, not on Python |

## Codebase

**Repo:** `python/cpython`

**Question to answer:** Take the function `def f(x): return x + 1`. Find the exact C code that runs for each of its bytecode instructions, and find where the specialized `BINARY_OP_ADD_INT` version is chosen instead of the generic one.

**Read, in order:**

1. `Python/ceval.c` — find `_PyEval_EvalFrameDefault`. Do not read it all. Find the dispatch loop and one or two instruction cases
2. `Python/bytecodes.c` — this is where instructions are *defined*; `ceval.c` cases are generated from it. Much more readable. Look at `LOAD_FAST`, `BINARY_OP`, `RETURN_VALUE`
3. `Python/specialize.c` — find `_Py_Specialize_BinaryOp` and see what conditions trigger specialization
4. `Include/cpython/code.h` — the code object structure
5. `Objects/longobject.c` — skim `long_add` to see what "adding two ints" really costs

**Size:** 2 sessions.

💡 Read `bytecodes.c`, not `ceval.c`. Almost everyone who tries this reads the generated file, finds it unreadable, and gives up. The source file is written to be read.

### Part 1 — Compare constructs

For each pair, print `dis` output and write down which is fewer instructions and why:

| A | B |
|---|---|
| `[x*2 for x in items]` | `list(map(lambda x: x*2, items))` |
| `a + b + c` | `"".join([a, b, c])` (for strings) |
| `d["k"]` | `d.get("k")` |
| `if x in (1,2,3)` | `if x in [1,2,3]` |
| `for i in range(n)` | `while i < n` |
| a normal `def` | an `async def` (compare `co_flags`) |
| a plain function | a generator with `yield` |

### Part 2 — Build a stack machine

Write an interpreter for a tiny instruction set: `LOAD_CONST`, `LOAD_VAR`, `STORE_VAR`, `ADD`, `MUL`, `JUMP_IF_FALSE`, `JUMP`, `PRINT`, `RETURN`.

```python
program = [
    ("LOAD_CONST", 0),
    ("STORE_VAR", "i"),
    ("LOAD_VAR", "i"),
    ...
]
```

Then write a program in it that computes factorial. You now understand what the eval loop does, because you wrote one.

### Part 3 — Measure the four costs

Write benchmarks that demonstrate each claim in the "Why Python Is Slow" section:

1. Dispatch overhead — same loop in pure Python vs numpy, report the ratio
2. Object overhead — `sys.getsizeof` for a list of 1M ints vs a numpy array of 1M ints
3. Dynamic lookup — attribute access vs local variable in a hot loop
4. Specialization — run a loop with stable types vs alternating `int`/`float`, compare timings on Python 3.13

**Done when:** `FINDINGS.md` has your own measured numbers for all four, and your stack machine runs factorial correctly. Part 3 point 4 is the interesting one — most people do not believe it until they measure it.
