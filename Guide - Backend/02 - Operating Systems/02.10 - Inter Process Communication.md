# Inter Process Communication

#backend #os #ipc #linux

> **In one line:** Processes cannot see each other's memory, so the kernel offers ways to pass data between them: pipes, Unix sockets, shared memory, and plain files. Unix domain sockets are the one backend engineers use most without noticing.

---

## The Idea

Isolation between processes is the whole point of [[02.5 - Virtual Memory]]. But workers need to talk to a master, a sidecar needs to talk to your app, and Postgres backends need a shared buffer pool. IPC is the set of sanctioned holes in the wall.

| Mechanism | Shape | Speed | Crosses machines? | Seen in |
|---|---|---|---|---|
| **Pipe** | One-way byte stream, parent to child | Fast | No | Shell pipelines, `subprocess` |
| **Named pipe (FIFO)** | A pipe with a filesystem name | Fast | No | Old-school tooling |
| **Unix domain socket** | Two-way stream or datagrams, with a filesystem path | Fast, no TCP stack | No | Docker daemon, Postgres local connections, gunicorn ↔ nginx, sidecars |
| **TCP on localhost** | Two-way stream | Slower: full TCP/IP stack | Yes, with the same code | Most microservice traffic |
| **Shared memory** | Both processes map the same physical pages | Fastest: no copying | No | Postgres `shared_buffers`, `multiprocessing.shared_memory`, Chrome |
| **Signals** | A number, no data | — | No | Control only ([[02.9 - Signals and Process Lifecycle]]) |
| **Files** | Write, then the other process reads | Slow-ish, durable | Via a shared filesystem | Lock files, PID files, spool directories |
| **Message queues (POSIX / SysV)** | Discrete messages | Fast | No | Rare in modern backends; Redis or a broker replaced them |

## Unix Domain Sockets

Same socket API as TCP: `socket`, `bind`, `listen`, `accept`, `connect`. Address family `AF_UNIX`, and the address is a file path.

```python
# server
import socket, os
path = "/tmp/app.sock"
if os.path.exists(path):
    os.unlink(path)
srv = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
srv.bind(path)
srv.listen()
conn, _ = srv.accept()
print(conn.recv(1024))

# client
cli = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
cli.connect("/tmp/app.sock")
cli.sendall(b"hello")
```

Why use them instead of `127.0.0.1`:

| Advantage | Detail |
|---|---|
| **Faster** | No TCP handshake, checksums, congestion control or loopback routing. Often 30–50% lower latency for small messages. |
| **Permissions** | Access is controlled by **file permissions** on the socket path. No port to expose by accident. |
| **Peer credentials** | The server can ask the kernel who connected (`SO_PEERCRED`: PID, UID, GID). Postgres `peer` auth uses this. |
| **Pass file descriptors** | You can send an open fd to another process (`SCM_RIGHTS`). This is how zero-downtime socket handoff works. |
| **No port exhaustion** | No ephemeral ports, no `TIME_WAIT` pile-up ([[03.3 - TCP Connection Lifecycle]]) |

Where you already use them:

```bash
psql -h /var/run/postgresql            # local Postgres
ls -l /var/run/docker.sock             # the Docker API: root-equivalent access!
uvicorn app:app --uds /tmp/uvicorn.sock    # nginx → uvicorn on the same host
redis-server --unixsocket /tmp/redis.sock
```

⚠️ **Mounting `/var/run/docker.sock` into a container gives that container root on the host.** Anyone who can talk to the Docker API can start a privileged container that mounts `/`. Treat that socket like a root password.

## Shared Memory

Two processes map the **same physical pages**. A write by one is immediately visible to the other. No syscalls, no copies.

```python
from multiprocessing import shared_memory
import numpy as np

# process A
shm = shared_memory.SharedMemory(create=True, size=8 * 1_000_000, name="prices")
arr = np.ndarray((1_000_000,), dtype=np.float64, buffer=shm.buf)
arr[:] = load_prices()

# process B
shm = shared_memory.SharedMemory(name="prices")
arr = np.ndarray((1_000_000,), dtype=np.float64, buffer=shm.buf)
print(arr.mean())       # no pickling, no copy
```

The catch: **you are now back in shared-state concurrency.** Two processes writing the same region need synchronization ([[02.4 - Locks and Synchronization]]), and a crash mid-write can leave the data half-updated. Postgres guards its shared buffers with lightweight locks and spinlocks, and it restarts **every** backend if one crashes, because a dying backend may have corrupted shared memory.

💡 **This is why Postgres restarts all connections when one backend segfaults.** When one backend dies abnormally, the postmaster cannot trust shared memory any more. It kills every backend, runs crash recovery from the WAL, and starts again. One bad extension can disconnect your whole application.

## Passing Sockets Between Processes

The prefork pattern (gunicorn, nginx, Postgres, uvicorn with `--workers`) relies on a simple fact: **fds survive `fork`.**

```
master: socket() → bind(:8000) → listen()
   │ fork × 4
   ├── worker 1: accept() on the same listening fd
   ├── worker 2: accept()
   ├── worker 3: accept()
   └── worker 4: accept()
```

All workers call `accept()` on one shared listening socket, and the kernel hands each new connection to one of them. Two refinements:

- **`SO_REUSEPORT`**: each worker opens its **own** socket bound to the same port, and the kernel load-balances between them by hashing. This avoids the "thundering herd" of every worker waking for one connection, and spreads load more evenly.
- **Zero-downtime upgrades**: a new binary receives the listening fd from the old one (inherited across `exec`, or sent over a Unix socket with `SCM_RIGHTS`). The socket never closes, so no connection is refused during the upgrade. That is what gunicorn's `USR2` and nginx's binary upgrade do.

## Choosing IPC in a Backend

| Situation | Use |
|---|---|
| App and sidecar in the same pod (Envoy, an OTel collector, a Cloud SQL proxy) | localhost TCP (simplest) or a Unix socket via a shared `emptyDir` volume |
| nginx in front of uvicorn on the same VM | A Unix socket |
| Big read-only data shared by worker processes | Load it before `fork` (copy-on-write; see the refcount caveat in [[02.2 - Processes]]), or `mmap` a file, or `shared_memory` |
| Results from a process pool | Return values (pickled through a pipe). Keep them small. |
| Anything across machines, or needing durability or retries | Not OS IPC. Use HTTP/gRPC, or a queue ([[09.2 - Queue Semantics]]) |

## Codebase

**Repos:** `python/cpython`, `benoitc/gunicorn`

**Question to answer:** How do gunicorn's workers share one listening socket, and how does the master know a worker is still alive?

**Read, in order:**

1. gunicorn `gunicorn/arbiter.py` — `start()` creates listeners, `spawn_worker()` forks, `murder_workers()` checks timeouts. Note the self-pipe (`PIPE`) the arbiter uses to wake its own main loop on signals.
2. gunicorn `gunicorn/workers/workertmp.py` — the heartbeat: each worker periodically changes the timestamp of a temporary file, and the arbiter checks it. IPC through file metadata.
3. gunicorn `gunicorn/sock.py` — `create_sockets()`, including inheriting fds from the environment on upgrade (`GUNICORN_FD`)
4. CPython `Lib/multiprocessing/shared_memory.py` — how a named shared segment is created (`shm_open` + `mmap`)
5. CPython `Lib/multiprocessing/connection.py` — `Pipe()`, and how pickled objects are framed over it

**Size:** 2 sessions. The arbiter is one of the most readable process supervisors in any language.
