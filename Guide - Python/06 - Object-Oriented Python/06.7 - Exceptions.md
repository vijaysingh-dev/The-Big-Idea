# Exceptions

#python #exceptions #errors

> **In one line:** Exceptions are classes in a hierarchy. Catch narrowly, chain with `raise ... from` so the cause survives, give your application its own hierarchy that maps cleanly to HTTP errors, and use `ExceptionGroup` with `except*` when several things fail at once.

---

## The Hierarchy That Matters

```
BaseException
├── SystemExit              ← sys.exit()
├── KeyboardInterrupt       ← Ctrl-C
├── GeneratorExit           ← generator.close()
├── BaseExceptionGroup
└── Exception               ← everything you should ever catch
    ├── ArithmeticError → ZeroDivisionError, OverflowError
    ├── LookupError → KeyError, IndexError
    ├── ValueError → UnicodeDecodeError, ...
    ├── TypeError
    ├── AttributeError, NameError, ImportError → ModuleNotFoundError
    ├── OSError → FileNotFoundError, PermissionError, ConnectionError, TimeoutError, ...
    ├── RuntimeError → RecursionError, NotImplementedError
    ├── StopIteration, StopAsyncIteration
    └── ExceptionGroup
```

And one that is **not** under `Exception` since 3.8: `asyncio.CancelledError` inherits from `BaseException`, so a bare `except Exception:` does not swallow task cancellation. That change was deliberate ([[01.7 - Cancellation and Structured Concurrency]]).

## Catch Narrowly

```python
# ❌ Hides bugs: a typo (NameError) or a wrong argument (TypeError) is "handled"
try:
    user = repo.get(user_id)
    send(user.emial)
except Exception:
    pass

# ✅ Catch what you expect, where you can do something about it
try:
    user = repo.get(user_id)
except UserNotFound:
    return None
```

| Rule | Why |
|---|---|
| Keep `try` blocks small | So you know which line raised |
| Catch the most specific class | `KeyError`, not `LookupError`, not `Exception` |
| Never bare `except:` | It catches `SystemExit` and `KeyboardInterrupt` too |
| `except Exception` only at boundaries | The top of a request handler, a worker loop, a CLI main: log with traceback, return a 500 or retry |
| Never silently `pass` | At least log. A swallowed error becomes a mystery later. |

## try / except / else / finally

```python
try:
    conn = pool.acquire()
except PoolTimeout:
    raise ServiceUnavailable() from None
else:
    # runs only if no exception: keeps the try block minimal
    result = conn.execute(q)
finally:
    # always runs: cleanup
    metrics.inc("db_attempts")
```

⚠️ A `return` inside `finally` **swallows** any in-flight exception. Python 3.14 warns about it (PEP 765). Never return from `finally`.

## Chaining: `raise ... from`

```python
try:
    row = await conn.fetchrow(q, user_id)
except asyncpg.PostgresConnectionError as e:
    raise RepositoryUnavailable("users DB down") from e
```

The traceback then shows both: **"The above exception was the direct cause of the following exception"**. The original cause is in `__cause__`.

| Form | Traceback shows | Use |
|---|---|---|
| `raise New() from e` | Explicit cause | Translating a low-level error into a domain error. **The usual choice.** |
| `raise New()` inside `except` | "During handling of the above exception, another exception occurred" (implicit `__context__`) | Usually an accident: it looks like your handler had a bug |
| `raise New() from None` | Hides the original | When the original is noise (KeyError → a clearer NotFound) |
| bare `raise` | Re-raises the current exception unchanged | Log-and-rethrow, cleanup-then-rethrow |

```python
e.add_note("while processing order 42")    # 3.11+: attach context without wrapping
```

## Your Own Exception Hierarchy

```python
class AppError(Exception):
    """Base for all errors this service raises on purpose."""
    status_code = 500
    code = "internal_error"

    def __init__(self, message: str = "", **details):
        super().__init__(message or self.__doc__)
        self.details = details

class NotFound(AppError):
    """Resource not found."""
    status_code = 404
    code = "not_found"

class Conflict(AppError):
    status_code = 409
    code = "conflict"

class ValidationFailed(AppError):
    status_code = 422
    code = "validation_failed"

class UpstreamUnavailable(AppError):
    status_code = 503
    code = "upstream_unavailable"
    retryable = True
```

Then **one** handler maps them to responses:

```python
@app.exception_handler(AppError)
async def app_error_handler(request, exc: AppError):
    return JSONResponse(
        status_code=exc.status_code,
        content={"type": exc.code, "detail": str(exc), **exc.details},
    )
```

The benefits: business code raises meaningful errors without knowing about HTTP, callers can catch `AppError` to handle anything from your library, and the API's error format stays consistent. The response shape (Problem Details, retryable vs terminal) is designed in [[06.3 - Error Design]].

⚠️ Do not define an exception per function. A dozen classes covering the distinct ways callers **react** (not found, conflict, invalid, unavailable, forbidden) is plenty.

## EAFP vs LBYL

```python
# LBYL — Look Before You Leap
if key in cache:
    return cache[key]

# EAFP — Easier to Ask Forgiveness than Permission (idiomatic Python)
try:
    return cache[key]
except KeyError:
    ...
```

EAFP avoids race conditions in concurrent code. `if os.path.exists(p): open(p)` can fail if the file is deleted in between, while `try: open(p) except FileNotFoundError:` cannot. Exceptions in Python are cheap when not raised and fairly cheap when raised, so EAFP is fine for genuinely exceptional paths. For a hot path where the "miss" is common, `dict.get` is clearer and faster.

## ExceptionGroup and except* (3.11+)

When several operations run concurrently, several can fail. `asyncio.TaskGroup` raises them together as an `ExceptionGroup`:

```python
try:
    async with asyncio.TaskGroup() as tg:
        tg.create_task(fetch_user(uid))
        tg.create_task(fetch_orders(uid))
        tg.create_task(fetch_recs(uid))
except* TimeoutError as eg:          # handles ONLY the TimeoutErrors in the group
    log.warning("timeouts: %d", len(eg.exceptions))
except* ConnectionError as eg:
    raise UpstreamUnavailable() from eg
```

Each `except*` clause takes the matching part of the group. Unmatched exceptions propagate in a new group. This is how structured concurrency reports multiple failures without losing any ([[01.7 - Cancellation and Structured Concurrency]]).

## Exceptions and Logging

```python
try:
    process(order)
except Exception:
    log.exception("order processing failed", extra={"order_id": order.id})   # includes the traceback
    raise
```

Use `log.exception` (or `exc_info=True`) inside `except`. Log **or** re-raise at each level, not both at every level, or one failure produces five tracebacks ([[07.6 - Logging Done Right]]).
