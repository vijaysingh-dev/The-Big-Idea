# Controlled vs Uncontrolled Components

The question is simply: **who owns the value?**

**Controlled** — React state owns it. The DOM displays what state says.

```jsx
const [value, setValue] = useState("");
<input value={value} onChange={e => setValue(e.target.value)} />
```

**Uncontrolled** — the DOM owns it. React reads it when needed.

```jsx
const ref = useRef(null);
<input defaultValue="" ref={ref} />
// later: ref.current.value
```

## The distinguishing props

```jsx
<input value={x} />          // controlled
<input defaultValue={x} />   // uncontrolled, initial value only
<input checked={x} />        // controlled
<input defaultChecked={x} /> // uncontrolled
```

A controlled input **must** have an `onChange`, or it becomes read-only — the DOM tries to update, React re-renders with the unchanged state, and the typed character disappears. React warns about this.

## Switching between them

```jsx
<input value={value ?? ""} />
```

Passing `undefined` or `null` as `value` makes React treat the input as uncontrolled, and switching mid-life produces a warning and unpredictable behavior. The usual cause is data arriving asynchronously:

```jsx
const [form, setForm] = useState({});          // form.name is undefined initially
<input value={form.name} />                    // uncontrolled, then controlled
<input value={form.name ?? ""} />              // always controlled
```

Initialize every controlled field to `""` or `false`, never `undefined`.

## When controlled is right

- The value must be **read during typing** — live validation, character count, search-as-you-type
- Another part of the UI **derives** from it — a preview, a filtered list, an enabled/disabled button
- The value must be **transformed** — formatting a phone number, uppercasing, masking
- Two inputs must stay **in sync**
- The value comes from **outside** — restoring a draft, a URL parameter

## When uncontrolled is right

- A simple form read once on submit
- File inputs — always uncontrolled; their value cannot be set programmatically for security reasons
- Large forms where per-keystroke re-rendering is measurable
- Integrating a non-React widget

```jsx
function LoginForm({ onSubmit }) {
  const handleSubmit = (e) => {
    e.preventDefault();
    onSubmit(Object.fromEntries(new FormData(e.currentTarget)));
  };

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" type="email" required />
      <input name="password" type="password" required />
      <button>Sign in</button>
    </form>
  );
}
```

No state, no re-renders, and native validation still works ([[09.2 - Forms and Native Input Behavior]]). For a login form this is strictly better than a controlled version.

## The cost of controlled inputs

**A re-render per keystroke.** For one input this is irrelevant. For a form of forty fields where every keystroke re-renders the whole form, it becomes visible on a mid-range phone — this is precisely the problem React Hook Form was built to solve ([[21.3 - React Hook Form]]).

**Cursor position resets on reformatting.** Transforming the value in `onChange` moves the caret to the end:

```jsx
onChange={e => setValue(e.target.value.toUpperCase())}
```

Type into the middle of the text and the caret jumps. Preserving it requires capturing `selectionStart` and restoring it in a layout effect — which is why input masking libraries exist.

**IME composition breaks.** For Chinese, Japanese, Korean and phonetic Indic input, intermediate composition states fire `onChange`. Transforming or validating mid-composition corrupts the input:

```jsx
const [composing, setComposing] = useState(false);

<input
  value={value}
  onChange={e => setValue(e.target.value)}
  onCompositionStart={() => setComposing(true)}
  onCompositionEnd={e => { setComposing(false); commit(e.target.value); }}
/>
```

Any product with a non-Latin-script audience needs to handle this.

## The hybrid pattern

Most production forms are uncontrolled underneath with controlled behavior where needed — subscribing to specific fields rather than re-rendering everything:

```jsx
const { register, watch, handleSubmit } = useForm();

<input {...register("email")} />          {/* uncontrolled */}
{watch("plan") === "custom" && <CustomFields />}   {/* subscribed */}
```

`register` attaches a ref and native listeners; only components that `watch` a field re-render when it changes.

## Beyond form inputs

The same distinction applies to any component with internal state:

```jsx
<Accordion defaultExpanded />                       // uncontrolled
<Accordion expanded={open} onToggle={setOpen} />    // controlled
```

Well-designed components support both. The standard implementation:

```jsx
function Accordion({ expanded: controlledExpanded, defaultExpanded = false, onToggle }) {
  const [internal, setInternal] = useState(defaultExpanded);
  const isControlled = controlledExpanded !== undefined;
  const expanded = isControlled ? controlledExpanded : internal;

  const toggle = () => {
    if (!isControlled) setInternal(v => !v);
    onToggle?.(!expanded);
  };
}
```

This is how Radix, Headless UI and MUI components work. Two rules: decide controlled-ness by whether the prop is `undefined`, and always call the callback so controlled consumers stay informed.

## defaultValue is only the initial value

```jsx
<input defaultValue={user.name} />
```

Changing `user.name` later does **not** update the input — `defaultValue` is read once at mount. To reset an uncontrolled form when the entity changes, use `key` ([[16.6 - Lists and Keys]]):

```jsx
<UserForm key={user.id} defaultValues={user} />
```

## How senior engineers actually use this

**They default to uncontrolled** for forms and reach for controlled only where a specific field's value is genuinely needed during typing.

**They use a form library** for anything past a handful of fields, rather than hand-rolling forty pieces of state.

**They initialize controlled values to `""` or `false`**, never `undefined`.

**They support both modes** in reusable components, using the `prop !== undefined` check.

**They avoid transforming values in `onChange`** unless they also handle caret position and IME composition.

## Common pitfalls

- Switching from uncontrolled to controlled when async data arrives.
- A controlled input without `onChange`, making it read-only.
- Expecting `defaultValue` to update after mount.
- Reformatting in `onChange` and losing cursor position.
- Breaking IME input by transforming during composition.
- Trying to set a file input's value programmatically.
- A large controlled form re-rendering entirely per keystroke.

## Interview angle

"Controlled versus uncontrolled" is a standard question — answer with who owns the value, the `value`/`defaultValue` distinction, and when each is appropriate rather than declaring one universally better. The strong additions are the cost of controlled inputs (per-keystroke re-render, cursor position, IME) and the dual-mode component pattern with the `undefined` check, which is what every real component library does.
