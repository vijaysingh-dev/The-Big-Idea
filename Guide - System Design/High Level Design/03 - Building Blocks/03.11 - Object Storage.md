# Object Storage

> **Revision tags:** #building-blocks #storage  
> **Related:** [[03.3 - CDN]] | [[06.10 - Video Streaming]]

---

## What It Is

Object storage is a flat storage system where data is stored as discrete objects — each identified by a unique key — alongside metadata. There is no directory hierarchy (though key prefixes simulate one).

```
Bucket: "user-uploads"
  Key: "avatars/user-42/profile.jpg"     → binary blob + metadata
  Key: "avatars/user-99/profile.jpg"     → binary blob + metadata
  Key: "documents/report-2024-q1.pdf"    → binary blob + metadata
```

The canonical implementation: **Amazon S3**. The API has become an industry standard — GCS, Azure Blob, MinIO all implement S3-compatible APIs.

---

## Why It Exists

Traditional filesystems and block storage are not designed for:
- Billions of files
- Petabytes of data
- High concurrent reads globally
- Cost-effective long-term retention
- HTTP-accessible storage without a server in the middle

Object storage solves all of these. It's the default choice for any unstructured or semi-structured data at scale.

## When to Use Object Storage

| Data Type | Object Storage? |
|---|---|
| User-uploaded images, videos, documents | ✅ |
| Application log archives | ✅ |
| ML training datasets | ✅ |
| Database backups | ✅ |
| Static website assets | ✅ |
| Software distribution (APKs, binaries) | ✅ |
| Frequently updated small records | ❌ (use DB) |
| Data requiring transactional updates | ❌ (use DB) |
| Files requiring low-latency random access | ❌ (use block storage) |

## S3 Data Model

**Bucket:** A namespace for objects. Globally unique name (across all AWS accounts). One bucket = one region.

**Object:** The actual data blob + metadata. Max size: 5 TB per object. No size minimum.

**Key:** The object's unique identifier within the bucket. Looks like a path but is a flat string.

**Metadata:** System metadata (content-type, size, etag, last-modified) + custom user metadata (key-value pairs).

**ETag:** MD5 hash of the object content. Used for cache validation and integrity checks.

---

## Core Operations

```
PUT    s3://bucket/key    → upload object
GET    s3://bucket/key    → download object
DELETE s3://bucket/key    → delete object
HEAD   s3://bucket/key    → get metadata only (no body)
LIST   s3://bucket?prefix=avatars/  → list keys with prefix
```

**Multipart upload:** For objects > 100 MB, upload in parallel parts (5 MB min per part). Faster, resumable on failure.

```
Initiate multipart upload → upload_id
Upload Part 1 (5 MB) → etag1
Upload Part 2 (5 MB) → etag2
Upload Part 3 (3 MB) → etag3
Complete multipart upload (list [etag1, etag2, etag3])
```

## Presigned URLs

Allow temporary, scoped access to an object without exposing credentials.

**Upload flow (presigned PUT):**
```
Client → Backend: "I want to upload a profile photo"
Backend: generate presigned PUT URL (expires in 15 min) → return to client
Client → S3: PUT /bucket/avatars/user-42/profile.jpg (presigned URL, no auth needed)
S3: stores the object
Client → Backend: "Upload complete, my photo key is avatars/user-42/profile.jpg"
Backend: update user record with photo key
```

**Download flow (presigned GET):**
```
Client → Backend: "Get my invoice PDF"
Backend: generate presigned GET URL → return to client
Client → S3: GET (presigned URL) → downloads PDF directly
```

Benefits:
- Backend doesn't proxy file bytes (saves bandwidth + compute)
- Access is time-limited and scoped to one object
- Credentials never exposed to client

## Storage Classes (Tiering)

S3 offers multiple storage classes at different price/access tradeoff points:

| Class | Access Pattern | Latency | Cost |
|---|---|---|---|
| **S3 Standard** | Frequent access | Milliseconds | High |
| **S3 Standard-IA** | Infrequent access | Milliseconds | Lower storage, retrieval fee |
| **S3 One Zone-IA** | Infrequent, non-critical | Milliseconds | Cheaper, single AZ |
| **S3 Glacier Instant** | Archive, occasional access | Milliseconds | Low |
| **S3 Glacier Flexible** | Archive, rare access | Minutes | Very low |
| **S3 Glacier Deep Archive** | Long-term archive | Hours | Cheapest |

**Lifecycle policies:** Automatically transition objects between classes:

```
Day 0:    Upload → Standard
Day 30:   Transition → Standard-IA (not accessed recently)
Day 90:   Transition → Glacier Instant
Day 365:  Transition → Glacier Deep Archive
Day 2555: Delete (7-year retention policy met)
```

## Consistency Model

S3 offers **strong read-after-write consistency** (as of December 2020). After a successful PUT, any subsequent GET returns the new object. After a DELETE, the object is gone.

Previously S3 was eventually consistent — a common source of bugs. This is no longer a concern.

## Access Control

**Bucket policies:** JSON policies attached to the bucket. Control who can do what.

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123456789:role/app-role" },
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::my-bucket/avatars/*"
}
```

**IAM policies:** Attached to users/roles. Control what AWS identities can access.

**Block Public Access:** Account-level setting to prevent accidental public exposure. Enable this by default; only override intentionally.

**Object ACLs:** Per-object permissions. Largely superseded by bucket policies — avoid using unless specifically needed.

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| S3 AZ outage | Objects in that AZ temporarily unavailable | S3 Standard automatically replicates across ≥ 3 AZs |
| Accidental deletion | Object permanently gone | Enable versioning + MFA delete |
| Region outage | All bucket access fails | Cross-region replication (CRR) for critical data |
| Presigned URL exposed | Unauthorized access for TTL duration | Short TTL, monitor access logs |
| Large object upload fails | Partial upload, storage costs without usable object | Lifecycle rule to abort incomplete multipart uploads |

---

## Interview Expectations

- Know object storage is the default for unstructured data at scale (images, videos, backups)
- Know the presigned URL pattern — don't proxy file bytes through your app servers
- Know storage tiering for cost optimization
- Know that S3 is not a filesystem — no atomic rename, no locking, no in-place update
