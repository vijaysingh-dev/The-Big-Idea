# Jest Testing for LWC

## The setup

```bash
npm install --save-dev @salesforce/sfdx-lwc-jest
```

```json
{
  "scripts": {
    "test:unit": "sfdx-lwc-jest",
    "test:unit:watch": "sfdx-lwc-jest --watch",
    "test:unit:coverage": "sfdx-lwc-jest --coverage"
  }
}
```

Tests live in a `__tests__` folder inside the component bundle:

```
force-app/main/default/lwc/claimList/
    claimList.html
    claimList.js
    claimList.js-meta.xml
    __tests__/
        claimList.test.js
```

**Jest tests are not deployed** and do not count toward Apex coverage. They run locally and in CI, which is what makes them fast enough to run on every commit.

## The basic shape

```javascript
import { createElement } from 'lwc';
import ClaimRow from 'c/claimRow';

describe('c-claim-row', () => {
    afterEach(() => {
        // the DOM persists between tests unless cleared, which causes confusing failures
        while (document.body.firstChild) {
            document.body.removeChild(document.body.firstChild);
        }
    });

    it('renders the claim number', () => {
        const element = createElement('c-claim-row', { is: ClaimRow });
        element.claim = { Id: 'a0X123', Claim_Number__c: 'WC-00042', Claim_Amount__c: 150000 };

        document.body.appendChild(element);   // connectedCallback and render happen here

        const heading = element.shadowRoot.querySelector('.claim-number');
        expect(heading.textContent).toBe('WC-00042');
    });
});
```

Three mechanics:

**`createElement`** constructs the component. Setting properties happens **before** appending, so they are available in `connectedCallback`.

**`document.body.appendChild`** triggers the lifecycle.

**`element.shadowRoot.querySelector`** reaches inside — tests can cross the shadow boundary where production code cannot.

**The `afterEach` cleanup is not optional.** Without it, elements from previous tests remain in the DOM and selectors match the wrong one.

## Asynchronous rendering

Rendering is asynchronous. A property set after the element is in the DOM does not appear immediately.

```javascript
it('updates when the claim changes', async () => {
    const element = createElement('c-claim-row', { is: ClaimRow });
    element.claim = { Claim_Number__c: 'WC-00042' };
    document.body.appendChild(element);

    element.claim = { Claim_Number__c: 'WC-00043' };

    // a resolved promise lets the rerender complete before the assertion
    await Promise.resolve();

    expect(element.shadowRoot.querySelector('.claim-number').textContent).toBe('WC-00043');
});
```

A shared helper is worth having:

```javascript
// jest-mocks/flushPromises.js
export default function flushPromises() {
    return new Promise((resolve) => setTimeout(resolve, 0));
}
```

Forgetting the await is the most common cause of a test that fails with the old value and looks inexplicable.

## Testing events

```javascript
it('dispatches claimapproved when the button is clicked', () => {
    const element = createElement('c-claim-row', { is: ClaimRow });
    element.claim = { Id: 'a0X123', Claim_Number__c: 'WC-00042' };
    document.body.appendChild(element);

    const handler = jest.fn();
    element.addEventListener('claimapproved', handler);

    element.shadowRoot.querySelector('[data-action="approve"]').click();

    expect(handler).toHaveBeenCalled();
    expect(handler.mock.calls[0][0].detail).toEqual({
        claimId: 'a0X123',
        claimNumber: 'WC-00042'
    });
});
```

Asserting on `detail` rather than only on the call verifies the payload contract, which is what a parent actually depends on.

## Mocking Apex

The Jest setup auto-mocks `@salesforce/apex/*` imports, and the mock exposes test helpers.

**Imperative:**

```javascript
import approveClaim from '@salesforce/apex/ClaimController.approveClaim';

jest.mock(
    '@salesforce/apex/ClaimController.approveClaim',
    () => ({ default: jest.fn() }),
    { virtual: true }
);

it('calls Apex with the claim id', async () => {
    approveClaim.mockResolvedValue('a0X123');

    const element = createElement('c-claim-panel', { is: ClaimPanel });
    element.recordId = 'a0X123';
    document.body.appendChild(element);

    element.shadowRoot.querySelector('lightning-button').click();
    await flushPromises();

    expect(approveClaim).toHaveBeenCalledWith({ claimId: 'a0X123', approvedAmount: undefined });
});
```

**Wire**, using the wire adapter emitter:

```javascript
import getClaims from '@salesforce/apex/ClaimController.getClaims';

const mockClaims = require('./data/claims.json');

jest.mock(
    '@salesforce/apex/ClaimController.getClaims',
    () => {
        const { createApexTestWireAdapter } = require('@salesforce/sfdx-lwc-jest');
        return { default: createApexTestWireAdapter(jest.fn()) };
    },
    { virtual: true }
);

it('renders a row per claim', async () => {
    const element = createElement('c-claim-list', { is: ClaimList });
    document.body.appendChild(element);

    // emit pushes data into the wire as though the server responded
    getClaims.emit(mockClaims);
    await flushPromises();

    const rows = element.shadowRoot.querySelectorAll('c-claim-row');
    expect(rows.length).toBe(mockClaims.length);
});

it('shows an error panel when the wire fails', async () => {
    const element = createElement('c-claim-list', { is: ClaimList });
    document.body.appendChild(element);

    getClaims.error({ body: { message: 'Insufficient access' } });
    await flushPromises();

    expect(element.shadowRoot.querySelector('c-error-panel')).not.toBeNull();
});
```

**Testing the error path matters as much as the success path.** A component that renders correctly with data and blanks on error is a defect users will find.

Keeping mock data in `__tests__/data/*.json` rather than inline keeps tests readable and makes the fixtures reusable.

## Mocking Lightning Data Service

```javascript
import { getRecord } from 'lightning/uiRecordApi';

const mockRecord = require('./data/claimRecord.json');

it('renders fields from the record', async () => {
    const element = createElement('c-claim-summary', { is: ClaimSummary });
    element.recordId = 'a0X123';
    document.body.appendChild(element);

    getRecord.emit(mockRecord);
    await flushPromises();

    expect(element.shadowRoot.querySelector('.amount').textContent).toContain('150,000');
});
```

`lightning/uiRecordApi` is stubbed by the framework with the same emitter interface.

The mock record JSON must match the UI API shape — `fields` with `value` and `displayValue` per field — which is easiest to obtain by capturing a real response from the browser.

## Mocking navigation and messaging

```javascript
import { getNavigateCalledWith } from 'lightning/navigation';

it('navigates to the record', () => {
    const element = createElement('c-claim-row', { is: ClaimRow });
    element.claim = { Id: 'a0X123' };
    document.body.appendChild(element);

    element.shadowRoot.querySelector('a').click();

    const { pageReference } = getNavigateCalledWith();
    expect(pageReference.attributes.recordId).toBe('a0X123');
});
```

```javascript
import { publish } from 'lightning/messageService';
import CLAIM_CHANNEL from '@salesforce/messageChannel/ClaimSelection__c';

jest.mock('lightning/messageService', () => ({
    publish: jest.fn(),
    subscribe: jest.fn(),
    unsubscribe: jest.fn(),
    MessageContext: jest.fn(),
    APPLICATION_SCOPE: 'APPLICATION'
}), { virtual: true });

it('publishes the selection', async () => {
    const element = createElement('c-claim-list', { is: ClaimList });
    document.body.appendChild(element);

    element.shadowRoot.querySelector('c-claim-row')
        .dispatchEvent(new CustomEvent('claimselected', { detail: { claimId: 'a0X123' } }));
    await flushPromises();

    expect(publish).toHaveBeenCalledWith(
        undefined,
        CLAIM_CHANNEL,
        expect.objectContaining({ claimId: 'a0X123' })
    );
});
```

Testing the **subscriber** side means capturing the handler passed to the mocked `subscribe` and invoking it:

```javascript
it('reacts to a published message', async () => {
    const element = createElement('c-claim-detail', { is: ClaimDetail });
    document.body.appendChild(element);

    const handler = subscribe.mock.calls[0][2];
    handler({ claimId: 'a0X999', source: 'claimList' });
    await flushPromises();

    expect(element.shadowRoot.querySelector('.claim-id').textContent).toBe('a0X999');
});
```

## Testing cleanup

The test worth writing that nobody writes.

```javascript
it('unsubscribes when removed from the DOM', () => {
    const element = createElement('c-claim-monitor', { is: ClaimMonitor });
    document.body.appendChild(element);

    document.body.removeChild(element);

    expect(unsubscribe).toHaveBeenCalled();
});
```

Leaked subscriptions are invisible in manual testing and appear only under sustained use in a console. This test costs four lines and catches a defect that is otherwise found in production. See [[14.5 - Component Lifecycle Hooks]].

## What to test

**Presentational components** are the cheapest and most valuable to test — set a property, assert on the rendered output, assert on dispatched events. No mocking needed.

```javascript
it('applies the overdue class when the claim is late', () => {
    const element = createElement('c-claim-row', { is: ClaimRow });
    element.claim = { Id: 'a0X1', Days_Open__c: 45, SLA_Days__c: 30 };
    document.body.appendChild(element);

    expect(element.shadowRoot.querySelector('.claim-row').className)
        .toContain('slds-theme_error');
});
```

**Container components** need mocking and are fewer. Test that the right Apex is called with the right parameters, that data renders, and that errors are handled.

**What not to test:** base component internals, the framework, and trivial getters. A test asserting that `lightning-button` renders a button tests Salesforce, not your code.

The split from [[14.9 - Slots and Composition]] pays off here: separating presentational from container components means most tests are fast and mock-free.

## Accessibility assertions

```javascript
it('provides assistive text on the icon-only button', () => {
    const element = createElement('c-claim-row', { is: ClaimRow });
    element.claim = { Id: 'a0X1' };
    document.body.appendChild(element);

    const assistiveText = element.shadowRoot.querySelector('.slds-assistive-text');
    expect(assistiveText.textContent).toBe('Approve claim');
});
```

Cheap to assert, and it catches the regression where someone removes the span while tidying markup.

## Coverage

```bash
npm run test:unit:coverage
```

```json
{
  "coverageThreshold": {
    "global": { "branches": 70, "functions": 80, "lines": 80, "statements": 80 }
  }
}
```

Unlike Apex, **there is no platform-imposed coverage requirement for LWC.** Whatever threshold the team sets is the standard, and enforcing it in CI is what makes it real.

The same caution applies as for Apex: coverage measures what executed, not what was verified. A test with no assertions produces coverage and proves nothing. See [[19.10 - Code Coverage, Quality and CI Gates]].

## Running in CI

```yaml
- name: Run LWC tests
  run: npm run test:unit:coverage
```

Jest tests run in **seconds** with no org, which makes them the fastest feedback available in a Salesforce project. Running them on every pull request costs almost nothing and catches most component regressions before a deployment is attempted.

This is a genuine advantage over Apex tests, which need an org and take minutes. See [[21.8 - CI-CD Pipelines]].

## Debugging tests

```bash
npm run test:unit -- claimList --verbose
npm run test:unit -- --watch
```

```javascript
// Print the rendered markup when a selector does not match
console.log(element.shadowRoot.innerHTML);
```

The most common causes of a puzzling failure: a missing `await` before the assertion, a missing `afterEach` cleanup, and a mock that was never configured to return anything.

## Practical guidance

**Clean up the DOM in `afterEach`.**

**Await a flushed promise** before asserting on anything rendered after a change.

**Assert on event `detail`**, not just that the event fired.

**Test the error path** for every wire and every imperative call.

**Test that subscriptions unsubscribe on disconnect.**

**Keep mock data in JSON files**, not inline.

**Test presentational components heavily** — they are cheap and mock-free.

**Do not test base components or the framework.**

**Run tests in CI on every pull request.** They take seconds.
