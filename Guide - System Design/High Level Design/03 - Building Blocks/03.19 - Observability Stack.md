# Observability Stack: Logging, Metrics, and Tracing

> **Revision tags:** #building-blocks #observability #monitoring  
> **Related:** [[02.6 - Observability Security Cost]] | [[02.5 - Failure and Resilience]]

## What Observability Is

Observability is the ability to understand the internal state of a system by examining its outputs — without needing to add new instrumentation or redeploy code to answer a new question.

The three pillars:

```
Logs    → What happened, event by event
Metrics → How the system is behaving over time (numbers)
Traces  → How a single request moved through the entire system
```

Each answers different questions:
- "What errors occurred in the last hour?" → Logs
- "Is p99 latency degrading over time?" → Metrics
- "Why did this specific user's request take 3 seconds?" → Traces

## Logging Pipeline

### Log Production

Services emit structured JSON logs:

```json
{
  "timestamp": "2024-01-15T10:23:45.123Z",
  "level": "ERROR",
  "service": "order-service",
  "host": "web-01",
  "trace_id": "abc123def456",
  "span_id": "7890abcd",
  "user_id": "u_9281",
  "order_id": "ord_4421",
  "event": "payment_charge_failed",
  "error_code": "insufficient_funds",
  "duration_ms": 234,
  "message": "Payment charge failed for order ord_4421"
}
```

**Key fields:**
- `trace_id` / `span_id`: Links logs to distributed traces
- `user_id` / `order_id`: Business context for filtering
- `duration_ms`: Performance signal
- Structured fields (not free-text): enables querying by field

### Log Pipeline Architecture

```
Service instances
    │ (stdout / log file)
    ▼
[Log Shipper]          → Fluentd, Filebeat, Fluent Bit
    │ (batched, buffered)
    ▼
[Log Aggregator/Buffer] → Kafka (for high volume), or direct to storage
    │
    ▼
[Log Storage & Index]  → Elasticsearch (ELK stack), Loki (Grafana stack), Datadog, CloudWatch
    │
    ▼
[Query & Visualization] → Kibana, Grafana, Datadog UI
```

**Why a shipper?** Services shouldn't know about the logging infrastructure. The shipper runs as a sidecar or DaemonSet, reads log output, and forwards it. If the logging backend is slow, the shipper buffers — service is unaffected.

**Why Kafka in the middle?** For high-volume systems, Kafka absorbs spikes and decouples the shipper from the storage backend. At moderate scale (< 100K logs/sec), you can skip Kafka and ship directly.

### Log Retention and Cost

Logs are expensive at scale. Tier retention:

```
Hot (Elasticsearch, 7 days):  full-text search, alerting
Warm (Elasticsearch, 30 days): slower queries, incident investigation
Cold (S3, 1 year):            compliance, rare access, compressed
Archive (S3 Glacier, 7 years): regulatory requirements
```

Use sampling for high-volume, low-value logs (e.g., health check pings). Log 1% of successful health checks, 100% of errors.

## Metrics Pipeline

### What Metrics Are

Numeric measurements sampled over time. Unlike logs (events), metrics aggregate behavior.

```
http_requests_total{service="order", endpoint="/checkout", status="200"} = 48291
http_request_duration_p99{service="order", endpoint="/checkout"} = 187ms
db_connections_active{db="orders-primary"} = 42
```

### Metric Types

**Counter:** Monotonically increasing value. Resets to 0 on restart.
```
http_requests_total = 48291  (total since start)
Rate: increase per second = requests per second
```

**Gauge:** Current value, can go up or down.
```
db_connections_active = 42
memory_used_bytes = 2147483648
queue_depth = 1203
```

**Histogram:** Distribution of values. Records counts in predefined buckets.
```
http_request_duration_seconds_bucket{le="0.1"} = 45000  (45K requests under 100ms)
http_request_duration_seconds_bucket{le="0.5"} = 49500
http_request_duration_seconds_bucket{le="1.0"} = 49900
http_request_duration_seconds_count = 50000
→ p90 ≈ 100ms, p99 ≈ 500ms
```

### The RED Method (Services)

For every service, track:
```
Rate:     requests per second
Errors:   error rate (%)
Duration: latency distribution (p50, p95, p99)
```

These three signals detect almost all service degradation.

### The USE Method (Resources)

For every resource (CPU, memory, disk, network):
```
Utilization:  % of time the resource is busy
Saturation:   queue depth / wait time
Errors:       error count
```

### Metrics Pipeline Architecture

```
Services expose /metrics endpoint (Prometheus format)
    │
    ▼
[Prometheus] scrapes every 15s → stores time-series data (15-day retention)
    │
    ├──→ [Grafana] → dashboards, visualization
    └──→ [Alertmanager] → fires alerts to PagerDuty/Slack
    │
    ▼
[Long-term storage] → Thanos / Cortex / VictoriaMetrics (months/years of retention)
```

**Push vs pull:** Prometheus pulls (scrapes) from services. Some systems push to a gateway (short-lived jobs that don't persist long enough to be scraped). Both approaches work.

**Managed alternatives:** Datadog, New Relic, AWS CloudWatch, Google Cloud Monitoring — handle the entire pipeline for you, at cost.

## Distributed Tracing

### The Problem

In a microservices system, a single user request touches multiple services. A log from Order Service shows an error, but the root cause is in Payment Service. How do you connect them?

```
User request: POST /checkout → total time: 1.8s  ← slow!

Without tracing:
  Order Service log:    "checkout processed in 1800ms"  → which service was slow?

With tracing:
  Order Service:        50ms
  Payment Service:      1600ms  ← THE SLOW ONE
    Fraud Service:      1500ms  ← ACTUAL ROOT CAUSE
  Notification Service: 100ms
```

### Trace Anatomy

**Trace:** The full journey of one request through the system. Has a unique `trace_id`.

**Span:** One unit of work within a trace (one service call, one DB query, one cache lookup). Has a `span_id` and a `parent_span_id`.

```
Trace abc123:
  Span 1: API Gateway       (0ms–50ms)     parent: none (root span)
  Span 2: Order Service     (50ms–200ms)   parent: Span 1
  Span 3: DB query          (55ms–80ms)    parent: Span 2
  Span 4: Payment Service   (200ms–1800ms) parent: Span 2  ← 1600ms!
  Span 5: Fraud API call    (205ms–1700ms) parent: Span 4  ← 1495ms!
```

### Trace Propagation

Trace context is propagated via HTTP headers across service boundaries:

```
Service A calls Service B:
  Headers added to outbound request:
    traceparent: 00-abc123def456...-7890abcd-01
    (trace_id=abc123def456, parent_span_id=7890abcd, flags=01)

Service B reads these headers → creates child span → continues the trace
```

**W3C Trace Context** is the standard format. OpenTelemetry implements it across all languages.

### OpenTelemetry

The industry standard instrumentation layer. Vendor-neutral SDK for producing traces, metrics, and logs.

```
Application code → OpenTelemetry SDK → [OTLP exporter]
                                              │
                                    ┌─────────┴──────────┐
                                    ▼                     ▼
                               [Jaeger]              [Datadog]
                             (open source)           (managed)
```

You instrument once with OpenTelemetry; the backend is swappable.

### Sampling

Tracing every request at high volume is expensive. Use sampling:

**Head-based sampling:** Decision made at the start of the trace (at the entry point). Simple, consistent.
```
Sample 1% of all requests → 99% dropped, 1% fully traced
```

**Tail-based sampling:** Decision made after the trace completes. Can sample 100% of slow or error traces.
```
Sample:
  - 100% of traces with errors
  - 100% of traces > 1s latency
  - 1% of healthy, fast traces
```

Tail-based sampling is more useful (you always capture the interesting requests) but requires buffering full traces before the sampling decision.

## Alerting

### Alert on Symptoms, Not Causes

```
Bad:  Alert when CPU > 80%           (cause — users may not be affected)
Good: Alert when p99 latency > 500ms (symptom — users are affected)

Bad:  Alert when DB connection count > 80
Good: Alert when error rate > 1% for 5 minutes
```

### SLO-Based Alerting

Define an SLO (Service Level Objective):
```
99.9% of requests succeed within 200ms over a 30-day rolling window
```

Error budget = 0.1% of requests can fail = 43.2 minutes of downtime per month.

Alert when the error budget is being burned too fast:
```
Alert: "Burning 10% of monthly error budget in 1 hour"
→ Requires immediate attention (will exhaust budget in 10 hours)
```

**Tools:** Google SRE Workbook has the canonical burn rate alert formulas. Implemented in Prometheus + Alertmanager natively.

## Putting It Together: The Observability Toolkit

| Tool | Role | Open Source | Managed |
|---|---|---|---|
| Prometheus | Metrics collection & storage | ✅ | AWS Managed Prometheus |
| Grafana | Dashboards & visualization | ✅ | Grafana Cloud |
