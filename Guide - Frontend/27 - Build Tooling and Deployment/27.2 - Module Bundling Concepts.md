# Module Bundling Concepts

## Why bundlers exist

Three problems, in historical order.

**No module system in browsers.** Before ES modules, scripts shared one global scope. Bundlers gave JavaScript a module system by resolving `require`/`import` at build time and emitting code with private scopes ([[08.1 - ES Modules vs CommonJS]]).

**Request cost.** Over HTTP/1.1, an application with 500 modules meant 500 requests with a six-connection limit — catastrophic latency. Bundling into a few files was essential. HTTP/2 multiplexing reduced this, but per-request overhead and browser priority handling still make hundreds of tiny modules slower than a few well-sized chunks.

**Non-JavaScript assets.** TypeScript, JSX, CSS modules, SVG imports and image URLs all need transformation. The bundler is where that pipeline lives.

The first reason is largely obsolete — browsers support ES modules natively. The second and third are why bundlers remain standard for production builds.

## The pipeline

```
entry point
  ↓ resolve
module graph      — follow every import, recursively
  ↓ transform
transformed modules — TS → JS, JSX → JS, CSS → JS or a file
  ↓ optimize
tree shaking, minification, chunk splitting
  ↓ emit
output files + manifest + source maps
```

**Resolution** turns a specifier into a file path:

```js
import x from "./utils";        // relative — try .ts, .tsx, .js, /index.ts
import y from "lodash";          // bare — walk node_modules, read exports/main
import z from "@/components";    // alias — configured mapping
```

The `exports` field in a dependency's `package.json` controls which file a bare specifier resolves to, and can differ per condition — `import` versus `require`, `browser` versus `node` ([[27.1 - npm and package.json]]).

**The module graph** is the dependency tree from the entry point. A module reachable from the entry is included; one that is not is dead code, even if it exists in the project.

## Chunks

```js
// Static import — same chunk
import { formatDate } from "./utils";

// Dynamic import — a split point, emitted as a separate chunk
const { Editor } = await import("./Editor");
```

Every `import()` creates a chunk boundary. The bundler emits that module and its unique dependencies separately, loaded on demand ([[08.2 - Dynamic Imports]]).

Shared dependencies are hoisted into a common chunk rather than duplicated. If routes A and B both import a chart library, it lands in a shared chunk that both reference.

Manual chunking controls grouping for caching:

```js
// vite.config.js
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        react: ["react", "react-dom"],
        vendor: ["date-fns", "@tanstack/react-query"],
      },
    },
  },
}
```

The reasoning is cache lifetime, not size. Framework code changes rarely; application code changes on every deploy. Separating them means a deploy invalidates a small chunk rather than everything ([[15.7 - HTTP Caching and CDNs]]).

Over-splitting is counterproductive — each chunk is a request, and dozens of tiny chunks add round trips and duplicated module boilerplate.

## Content hashing

```
main.a3f9c2e1.js
vendor.7b2d4f88.js
```

The hash is derived from the file's content, so it changes only when the content does. This enables the two-tier caching strategy: hash-named assets cached forever with `immutable`, and an uncached HTML file that points at the current filenames.

```
/assets/main.a3f9c2.js   Cache-Control: public, max-age=31536000, immutable
/index.html              Cache-Control: no-cache
```

Without hashing you must choose between stale assets and no caching at all.

A related failure worth knowing: after a deploy, an open tab holds HTML referencing chunk filenames that no longer exist, so a lazy import 404s. Handle it with reload-on-chunk-error ([[19.3 - Code Splitting and React.lazy]]).

## Optimizations

**Tree shaking** removes unused exports, requiring static ES module syntax and accurate `sideEffects` metadata ([[27.6 - Tree Shaking]]).

**Minification** removes whitespace, shortens identifiers, and applies safe transformations. esbuild and SWC do this an order of magnitude faster than Terser with comparable output.

**Scope hoisting** concatenates modules into a single scope rather than wrapping each in a function, reducing both size and startup cost. Rollup pioneered this and it is why its output is typically smaller than webpack's.

**Dead code elimination** removes unreachable branches after constant folding:

```js
if (process.env.NODE_ENV !== "production") {
  expensiveDevChecks();      // removed entirely in a production build
}
```

This is how React ships development warnings that cost nothing in production, and it is why `NODE_ENV` must be set correctly at build time.

**Asset handling** — small images inlined as data URIs, larger ones emitted with hashed names, CSS extracted or injected.

## The bundlers

| | Model | Notes |
| --- | --- | --- |
| **Vite** | esbuild in dev, Rollup for build | the default for new projects |
| **webpack** | single JS-based bundler | most configurable, slowest, huge ecosystem |
| **Rollup** | library-focused | cleanest ESM output, powers Vite's build |
| **esbuild** | Go | extremely fast, less flexible |
| **Rspack** | Rust, webpack-compatible config | drop-in speed upgrade for webpack projects |
| **Turbopack** | Rust, Next.js | incremental, bundled with Next |
| **Rolldown** | Rust, Rollup-compatible | replacing Rollup inside Vite |

The direction is clear: the JavaScript-implemented bundlers are being replaced by Rust and Go implementations, typically 10–50× faster on large projects. Configuration formats are being kept compatible so migration is cheap.

## Dev server versus production build

These are different problems, and the split is what made Vite fast.

**Development** prioritizes startup and update speed. Vite serves source files as native ES modules with no bundling, transforming each on request. Startup is near-instant regardless of project size, and an edit re-transforms one file ([[27.3 - Vite]]).

**Production** prioritizes the shipped artifact. Full bundling, tree shaking, minification, chunk splitting and hashing — a slower process producing an optimized result.

The tradeoff is that dev and production use different code paths, so behavior can occasionally differ. Running `vite build && vite preview` before shipping catches this.

## When you do not need a bundler

Native ES modules plus an import map work without a build step:

```html
<script type="importmap">
  { "imports": { "react": "https://esm.sh/react@19" } }
</script>
<script type="module" src="/app.js"></script>
```

Viable for small projects, prototypes and internal tools. You lose TypeScript, JSX, tree shaking, minification and hashing — which is most of the value for anything production-facing.

Worth knowing mostly because it clarifies what a bundler is actually providing.

## How senior engineers actually use this

**They use Vite for new projects** and migrate webpack projects to Rspack when build times become a bottleneck.

**They separate vendor chunks by change frequency**, not by size, so deploys invalidate as little as possible.

**They verify chunk composition with an analyzer** rather than assuming, since a single shared import can pull a "lazy" dependency into the main bundle ([[19.7 - Bundle Analysis and Optimization]]).

**They test a production build before shipping**, because dev and build pipelines differ.

**They keep chunk counts moderate** — a handful of meaningful chunks beats dozens of tiny ones.

## Common pitfalls

- Over-splitting into many small chunks, adding requests without reducing bytes.
- Assuming HTTP/2 makes bundling unnecessary.
- Unhashed filenames with long cache lifetimes, serving stale JavaScript.
- Stale chunk references after a deploy causing blank screens.
- `NODE_ENV` not set to `production`, shipping development builds of React.
- Dynamic import specifiers the bundler cannot statically analyze.
- Trusting dev-server behavior without checking the production build.

## Interview angle

"Why do we need bundlers" has a three-part answer: originally a module system for browsers, then request-count reduction, and now primarily the transformation pipeline for TypeScript, JSX and assets plus optimizations like tree shaking and code splitting. The follow-up worth volunteering is why Vite is fast — it skips bundling in development by serving native ES modules and only bundles for production — and that content hashing is what makes aggressive caching safe.
