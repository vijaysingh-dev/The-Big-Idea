# Roll-Up Summary Fields

## What they do

A roll-up summary aggregates child records onto a parent. Count of claims on a machine. Sum of line item amounts on an opportunity. Maximum close date across a set of children.

Unlike a formula field, the value **is stored** on the parent record. The platform recalculates it whenever a child changes.

That difference is the whole point: because it is stored, it can be indexed, filtered efficiently, used in list view filters at scale, and it triggers automation on the parent when it changes.

## The hard constraint

**Roll-up summaries only work over master-detail relationships.**

Not lookups. This single restriction shapes a large part of Salesforce data modelling, and it is the reason people choose master-detail relationships they otherwise would not want. See [[02.7 - Relationships - Lookup vs Master-Detail]].

There are a few standard exceptions where Salesforce provides roll-ups over what is technically a lookup — Opportunity to Account, and Campaign to Opportunity via Campaign Influence — but you cannot create your own.

## The four operations

- **COUNT** — number of child records
- **SUM** — total of a numeric child field
- **MIN** — smallest value, works on number, date, and datetime
- **MAX** — largest value

Each can be filtered, so you can count only children matching criteria.

```
Roll-Up Summary on Machine__c
  Summarized object: Warranty_Claim__c
  Operation: COUNT
  Filter: Status__c equals "Submitted" OR Status__c equals "In Review"
  Field label: Open Claims
```

```
Roll-Up Summary on Opportunity
  Summarized object: OpportunityLineItem
  Operation: SUM
  Field: TotalPrice
  Field label: Total Line Item Value
```

## How recalculation actually works

When a child record is inserted, updated, deleted, or undeleted, the platform recalculates the parent's roll-up fields. This happens inside the same transaction, at step 12 of the order of execution ([[07.13 - Order of Execution]]).

Two consequences follow, and both cause real production issues.

**The parent record is locked.** While a child is being saved, the parent is locked so its roll-up can be updated safely. If two users, or two batch threads, modify children of the *same* parent simultaneously, one of them fails with `UNABLE_TO_LOCK_ROW`. This is the single most common cause of that error in data loading. See [[10.8 - Record Locking and Deadlocks]].

**The parent re-enters the save pipeline.** Updating the parent's roll-up field can fire the parent's triggers, flows, and validation rules, and can cascade further to *its* parent. A single child insert can therefore set off a chain of saves that consumes limits you did not budget for.

The practical mitigation when loading data in bulk: sort records by parent so that children of the same parent land in the same batch rather than being spread across parallel threads, and consider serial mode in Bulk API for objects with heavy roll-ups. See [[23.5 - Bulk Data Loading at Scale]].

## Limits

- **40 roll-up summary fields per object**, and this is a hard ceiling
- Roll-ups count toward the 15 spanning relationships per object shared with formulas and validation rules
- A roll-up cannot summarize a formula field that itself references another object's fields, or a field that depends on a roll-up
- Long text areas, multi-select picklists, and encrypted fields cannot be summarized

The 40-field limit is reached in mature orgs more often than people expect, particularly on Account and Opportunity.

## When you cannot use one

Three situations force an alternative: the relationship is a lookup, you have exhausted the 40-field limit, or you need an aggregation the four operations do not cover — an average, a concatenation, a "most recent child's status".

The alternatives, in order of preference:

**1. Change the relationship to master-detail, if the semantics genuinely fit.** Do not do this purely to get a roll-up; master-detail brings ownership, sharing inheritance, and cascade delete with it, and those are bigger commitments than a rolled-up number.

**2. A record-triggered flow.** Suitable for low-volume, simple aggregations. Runs on child save, queries siblings, updates the parent. Straightforward to build and easy for an admin to maintain, but it fires per transaction and does not scale gracefully.

**3. Apex.** The right answer for anything with real volume or real complexity. The pattern is worth having in your head, because it is one of the most-written pieces of Apex in the ecosystem:

```java
public with sharing class ClaimRollupService {

    public static void recalculateForMachines(Set<Id> machineIds) {
        if (machineIds.isEmpty()) {
            return;
        }

        Map<Id, Machine__c> machines = new Map<Id, Machine__c>([
            SELECT Id, Open_Claim_Count__c, Total_Claim_Value__c
            FROM Machine__c WHERE Id IN :machineIds
        ]);

        for (Machine__c m : machines.values()) {
            m.Open_Claim_Count__c = 0;
            m.Total_Claim_Value__c = 0;
        }

        // aggregate query does the counting in the database rather than in Apex
        for (AggregateResult ar : [
            SELECT Machine__c machineId, COUNT(Id) claimCount, SUM(Claim_Amount__c) claimTotal
            FROM Warranty_Claim__c
            WHERE Machine__c IN :machineIds AND Status__c IN ('Submitted', 'In Review')
            GROUP BY Machine__c
        ]) {
            Machine__c m = machines.get((Id) ar.get('machineId'));
            m.Open_Claim_Count__c = (Integer) ar.get('claimCount');
            m.Total_Claim_Value__c = (Decimal) ar.get('claimTotal');
        }

        update machines.values();
    }
}
```

Three details in that make it correct rather than merely working. It resets every parent first, so parents whose last child was deleted go to zero instead of keeping a stale value. It uses an aggregate query so the database does the summing instead of Apex looping over potentially tens of thousands of children. And it takes a `Set<Id>` so it works identically for one parent or two hundred. See [[08.4 - Aggregate Queries, GROUP BY and HAVING]].

The service must be called from the child object's trigger on insert, update, delete, and undelete — and on update it must handle a child moving from one parent to another, recalculating both. Forgetting the delete and undelete events is the most common bug in hand-rolled roll-ups.

**4. A managed package.** Declarative Lookup Rollup Summaries (DLRS) is a widely used open-source package that provides configurable roll-ups over lookups, with both realtime and scheduled modes. Many orgs use it rather than writing the Apex above. It is genuinely good, and it is also one more thing running in your save pipeline that consumes limits.

## Design guidance

**Prefer a roll-up to a hand-written aggregation whenever the relationship allows it.** Less code, correct by construction, and it survives every path that modifies children.

**Watch the parent's automation.** A roll-up that fires the parent's trigger, which updates a grandparent, which fires another trigger, is a chain that shows up as mysterious CPU limit failures under load. Section 16 covers diagnosing this.

**Be careful with roll-ups on objects that receive bulk loads.** Locking contention during a large import is usually a roll-up problem, and the fix is data ordering rather than code.

**Do not roll up what you can query.** A number that is only ever read in a report can often come from a report's own grouping rather than a stored field, saving a roll-up slot and a recalculation cost.
