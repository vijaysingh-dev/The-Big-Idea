# Same Origin Policy and CORS

## The Same Origin Policy

An **origin** is the triple `(scheme, host, port)`. All three must match.

```
https://example.com/a       and  https://example.com/b       same origin
https://example.com         and  http://example.com          different — scheme
https://example.com         and  https://api.example.com     different — host
https://example.com         and  https://example.com:8080    different — port
```

The Same Origin Policy prevents a document from one origin reading data from another. Without it, any page you visited could read your email by fetching `mail.google.com` with your cookies attached.

**Note what is not blocked.** SOP restricts *reading responses*, not *sending requests*. A cross-origin form POST still happens; you just cannot read the reply. That gap is exactly what CSRF exploits ([[15.6 - Frontend Security]]).

Things that were always allowed cross-origin: `<img>`, `<script>`, `<link rel=stylesheet>`, `<iframe>`, `<video>`, and form submissions. This is why JSONP worked — a `<script>` tag bypasses SOP entirely.

**Same-site is a different concept.** `app.example.com` and `api.example.com` are the same *site* (same registrable domain) but different *origins*. Cookies use same-site rules ([[14.1 - Cookies]]); CORS uses same-origin rules. Confusing them is behind a lot of "the cookie is sent but the request is still blocked" debugging.

## CORS

Cross-Origin Resource Sharing is the server's mechanism for opting in to cross-origin access. The critical point: **CORS is enforced by the browser and configured by the server.** There is nothing you can do in frontend code to fix a CORS error.

The response header:

```
Access-Control-Allow-Origin: https://app.example.com
```

or `*` for public resources — but `*` is incompatible with credentials.

## Simple vs preflighted requests

A **simple request** is sent directly, with the browser checking the response headers afterwards. It qualifies only if:

- Method is `GET`, `HEAD` or `POST`
- Headers are limited to CORS-safelisted ones: `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`, `Range`
- `Content-Type` is `text/plain`, `multipart/form-data` or `application/x-www-form-urlencoded`
- No `ReadableStream` body, no event listeners on `XMLHttpRequestUpload`

Anything else triggers a **preflight** — an `OPTIONS` request sent first to ask permission:

```
OPTIONS /api/users
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

```
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

Two things almost always trigger preflight in a typical SPA: `Content-Type: application/json` (not on the safelist) and an `Authorization` header. So essentially every authenticated JSON API call is preflighted.

**`Access-Control-Max-Age`** caches the preflight result, avoiding a round trip on every subsequent request. Without it, each API call costs two requests. Browsers cap this — Chrome at 2 hours, Firefox at 24 — but setting it is one of the cheapest latency improvements available for a cross-origin API.

## Credentials

```js
fetch(url, { credentials: "include" });
```

For cookies to be sent and accepted cross-origin, **all** of these must hold:

- `credentials: "include"` on the request
- `Access-Control-Allow-Credentials: true` on the response
- `Access-Control-Allow-Origin` set to the **specific origin**, never `*`
- The cookie itself has `SameSite=None; Secure`

Missing any one produces a silent failure or a CORS error. The wildcard restriction is the most common: a server configured with `*` works fine for public endpoints and breaks the moment credentials are added.

Because the origin must be echoed specifically, servers typically read the `Origin` header and reflect it if it is in an allowlist — and must send `Vary: Origin` so caches do not serve one origin's response to another.

## Reading response headers

By default JavaScript can read only CORS-safelisted response headers: `Cache-Control`, `Content-Language`, `Content-Length`, `Content-Type`, `Expires`, `Last-Modified`, `Pragma`.

Anything custom must be exposed explicitly:

```
Access-Control-Expose-Headers: X-Total-Count, X-Rate-Limit-Remaining
```

This is why pagination metadata in a header often appears as `null` in the client despite being visible in DevTools — DevTools shows the raw response, JavaScript sees the filtered one.

## Debugging

The error message names the missing piece. Read it carefully:

- *"No 'Access-Control-Allow-Origin' header is present"* — the server did not send it, or did not handle the `OPTIONS` request.
- *"The value of the 'Access-Control-Allow-Origin' header ... must not be the wildcard '*' when the request's credentials mode is 'include'"* — echo the specific origin.
- *"Request header field authorization is not allowed"* — add it to `Access-Control-Allow-Headers`.
- *"Response to preflight request doesn't pass access control check"* — the `OPTIONS` handler is missing or returning a non-2xx.
- *"Redirect is not allowed for a preflight request"* — the `OPTIONS` request hit a redirect, often a trailing-slash or HTTP-to-HTTPS rule.

In the Network panel, enable the `OPTIONS` request filter — preflights are hidden by default in some configurations, and a failing preflight is often invisible otherwise.

## Development workarounds

**A dev-server proxy** is the correct approach — requests appear same-origin to the browser:

```js
// vite.config.js
export default {
  server: {
    proxy: {
      "/api": { target: "http://localhost:8080", changeOrigin: true },
    },
  },
};
```

This also means development matches production if production sits behind a reverse proxy on the same origin, which is the simplest architecture — no CORS at all.

**Browser extensions that disable CORS** and `--disable-web-security` should never be used. They hide a real configuration problem until production, and they disable a genuine security boundary in the developer's own browser.

## Related isolation policies

**COOP / COEP** — `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` enable **cross-origin isolation**, which is required for `SharedArrayBuffer` and high-resolution timers ([[08.4 - Web Workers]]). Enabling them breaks most third-party embeds, so it is a deliberate architectural decision.

**CORP** — `Cross-Origin-Resource-Policy` lets a resource declare who may embed it.

**`crossorigin` attribute** — on `<script>`, `<img>` and `<link>`, opts into CORS mode. Required for readable error details from cross-origin scripts (otherwise you get "Script error." with no stack), for fonts, and for canvas operations on cross-origin images.

## How senior engineers actually use this

**They put the API behind the same origin in production** — a reverse proxy path like `/api` — which removes CORS entirely along with its preflight latency and cookie complications.

**They set `Access-Control-Max-Age`** when a cross-origin API is unavoidable.

**They configure an origin allowlist with `Vary: Origin`**, never a blanket reflection of any origin.

**They add `crossorigin` to script tags** so production error reporting gets real stack traces instead of "Script error." ([[28.13 - Frontend Observability]]).

**They never work around CORS in the browser.** It is a server configuration task.

## Common pitfalls

- Trying to fix CORS in frontend code.
- `Access-Control-Allow-Origin: *` with credentials.
- Missing `OPTIONS` handling on the server.
- Custom response headers unreadable because they are not in `Access-Control-Expose-Headers`.
- Preflight on every request because `Max-Age` is unset.
- Confusing same-site with same-origin when debugging cookies.
- Reflecting any `Origin` without an allowlist, which defeats the policy.
- Missing `crossorigin` on scripts, losing production stack traces.

## Interview angle

"What is CORS and why does it exist" is extremely common. Lead with the Same Origin Policy and what it protects, then CORS as the server's opt-in mechanism, then the simple-versus-preflight distinction with the concrete triggers — `application/json` and `Authorization` — since that explains why almost every real API call is preflighted. Stating clearly that CORS is browser-enforced and server-configured, so it cannot be fixed client-side, is the point interviewers listen for.
