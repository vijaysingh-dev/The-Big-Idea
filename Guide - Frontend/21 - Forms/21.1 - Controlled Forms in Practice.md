# Controlled Forms in Practice

The controlled/uncontrolled distinction is covered in [[16.8 - Controlled vs Uncontrolled Components]]. This note is about what happens when a controlled form grows past three fields.

## The naive version and where it breaks

```jsx
function ProfileForm() {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");
  const [bio, setBio] = useState("");
  // ... twelve more
}
```

Fifteen `useState` calls, fifteen handlers, and every keystroke re-renders the entire form. On a mid-range phone with a moderately complex form, that becomes visible input lag.

## One state object

```jsx
const [form, setForm] = useState({ name: "", email: "", bio: "" });

const handleChange = (e) => {
  const { name, value, type, checked } = e.target;
  setForm(f => ({ ...f, [name]: type === "checkbox" ? checked : value }));
};

<input name="name" value={form.name} onChange={handleChange} />
<input name="email" value={form.email} onChange={handleChange} />
```

One handler for every field, driven by the `name` attribute. This is the standard shape for small-to-medium controlled forms.

Two details: the handler must be stable (defined once, or wrapped in `useCallback`) if any field component is memoized, and `type === "checkbox"` needs `checked` rather than `value`.

## Never initialize to undefined

```jsx
// If the API is slow, fields start uncontrolled and become controlled — React warns
const [form, setForm] = useState({});
<input value={form.name} />

// Always defined
const [form, setForm] = useState({ name: "", email: "" });
<input value={form.name ?? ""} />
```

Switching a field from uncontrolled to controlled mid-life produces a warning and unpredictable behavior. Initialize every field to `""` or `false`.

For a form populated from an async fetch, use `key` to remount once the data arrives rather than syncing with an effect ([[17.4 - useEffect Pitfalls]]):

```jsx
{user && <ProfileForm key={user.id} defaultValues={user} />}
```

## The re-render cost

Every keystroke re-renders the component holding the state and everything below it ([[19.1 - What Causes Re-renders]]).

For a form with a live preview, a large field list, or expensive sibling components, that is measurable. Three ways to contain it:

**Isolate the state.** If only one section needs the value, push the state into that section.

**Split the form into subcomponents with their own state**, lifting only on submit. This trades cross-field validation ease for render isolation.

**Use an uncontrolled library.** React Hook Form keeps values in refs and re-renders only components that subscribe to a specific field ([[21.3 - React Hook Form]]).

The threshold in practice: below about eight simple fields, controlled state is fine. Above that, or when fields are expensive to render, reach for a library.

## Debouncing derived work

```jsx
const [query, setQuery] = useState("");
const debouncedQuery = useDebounce(query, 300);

const { data } = useQuery({
  queryKey: ["search", debouncedQuery],
  queryFn: () => search(debouncedQuery),
  enabled: debouncedQuery.length > 2,
});
```

Debounce the **derived work**, not the input itself. Debouncing the input value makes typing feel laggy; debouncing what the value triggers keeps the field instant ([[29.1 - Debounce and Throttle]]).

`useDeferredValue` is the React-native alternative when the expensive work is rendering rather than fetching ([[22.5 - useDeferredValue]]):

```jsx
const deferredQuery = useDeferredValue(query);
const results = useMemo(() => filterLargeList(deferredQuery), [deferredQuery]);
```

## Transforming values breaks the caret

```jsx
onChange={e => setValue(e.target.value.toUpperCase())}
```

Type into the middle of the text and the caret jumps to the end. React sets `value`, and setting `value` on an input resets the selection.

Preserving it requires capturing and restoring the selection:

```jsx
const ref = useRef(null);
const selectionRef = useRef(null);

const handleChange = (e) => {
  selectionRef.current = e.target.selectionStart;
  setValue(format(e.target.value));
};

useLayoutEffect(() => {
  if (selectionRef.current != null) {
    ref.current.setSelectionRange(selectionRef.current, selectionRef.current);
  }
});
```

`useLayoutEffect` is required — doing this in `useEffect` produces a visible caret jump ([[17.5 - useLayoutEffect vs useEffect]]).

This gets substantially harder when the transform changes length (inserting thousand separators, formatting a card number), which is why masking libraries exist. Do not hand-roll input masking.

## IME composition

For Chinese, Japanese, Korean and phonetic Indic input, intermediate composition states fire `onChange`. Transforming or validating mid-composition corrupts the input:

```jsx
const [composing, setComposing] = useState(false);

<input
  value={value}
  onChange={e => setValue(e.target.value)}
  onCompositionStart={() => setComposing(true)}
  onCompositionEnd={(e) => {
    setComposing(false);
    validate(e.target.value);
  }}
/>
```

Skip validation and transformation while `composing` is true. Any product with a non-Latin-script audience needs this.

## Accessibility essentials

```jsx
<label htmlFor="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  autoComplete="email"
  value={form.email}
  onChange={handleChange}
  aria-invalid={Boolean(errors.email)}
  aria-describedby={errors.email ? "email-error" : undefined}
/>
{errors.email && <p id="email-error" role="alert">{errors.email}</p>}
```

`aria-describedby` links the error to the field so it is announced on focus; `role="alert"` announces it when it appears. Errors shown only as a red border are invisible to screen reader users ([[09.5 - Accessibility Fundamentals]]).

`autoComplete` with the correct token is one of the cheapest UX improvements available — it lets browsers and password managers fill a form in one tap ([[09.2 - Forms and Native Input Behavior]]).

## Submission

```jsx
const [status, setStatus] = useState("idle");

async function handleSubmit(e) {
  e.preventDefault();
  if (status === "submitting") return;      // prevent double submit

  setStatus("submitting");
  try {
    await save(form);
    setStatus("success");
  } catch (err) {
    setServerErrors(err.fieldErrors ?? {});
    setStatus("error");
  }
}

<form onSubmit={handleSubmit} noValidate>
  <button type="submit" disabled={status === "submitting"}>
    {status === "submitting" ? "Saving..." : "Save"}
  </button>
</form>
```

Use a real `<form>` with `onSubmit`, not a button `onClick`. It gives Enter-to-submit for free and works with native validation and autofill.

`noValidate` disables the browser's own validation UI while keeping the Constraint Validation API available for your own messages.

Disable the submit button during submission, and guard in the handler as well — a fast double-click can fire twice before the state updates.

## How senior engineers actually use this

**They use one state object with a name-driven handler** for small forms, and a library above roughly eight fields.

**They debounce the consequence, never the input.**

**They avoid transforming values in `onChange`** unless caret and IME handling are also implemented — which usually means using a library.

**They wire `autoComplete`, `aria-invalid` and `aria-describedby` on every field**, because retrofitting accessibility to forms is far more work than building it in.

**They always use a real form element** with `onSubmit`.

## Common pitfalls

- Fields initialized to `undefined`, switching from uncontrolled to controlled.
- A controlled input without `onChange`, making it read-only.
- Debouncing the input value, making typing feel laggy.
- Reformatting in `onChange` and losing the caret.
- Breaking IME composition for non-Latin scripts.
- Submit via button `onClick`, losing Enter-to-submit.
- No double-submit guard.
- Errors conveyed only by colour.

## Interview angle

"How would you build a form in React" invites the controlled-versus-uncontrolled discussion, and the strong answer covers the scaling problem: controlled state re-renders per keystroke, which is fine for small forms and not for large ones, which is why libraries keep values in refs. The details that mark experience are the caret-position and IME issues with transformed values, and debouncing the derived work rather than the input.
