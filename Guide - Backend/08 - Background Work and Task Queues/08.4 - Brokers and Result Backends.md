# Brokers and Result Backends

#backend #queues #celery #infrastructure

> **In one line:** Redis is fast and loses messages, RabbitMQ is a real broker with real operational weight, SQS is managed and limited — and the choice changes what guarantees your tasks actually have.

---

## The Idea

Celery does not implement queueing. **Kombu abstracts over a broker**, and the broker determines your semantics.

⚠️ **The abstraction leaks heavily.** The same Celery code behaves differently on Redis and RabbitMQ under worker crashes, broker restarts and network partitions. Treating the broker as an interchangeable detail is how you discover this in production.

| | Redis | RabbitMQ | SQS |
|---|---|---|---|
| Native queueing | **No** — emulated | **Yes** | Yes |
| Durability | Optional (AOF/RDB) | Configurable, real | **Always** |
| Visibility timeout | Emulated by Kombu | Native (unacked) | Native |
| Priority queues | Emulated, poorly | **Native** | No |
| Publisher confirms | No | **Yes** | Yes |
| Operational weight | Low | **High** | None |
| Latency | **Sub-ms** | ~1–5 ms | ~10–50 ms |
| Max message | 512 MB | ~128 MB | **256 KB** |
| Cost | Cheap | Cheap | Per-request |

---

## Redis as a Broker

The default choice, and the one with the most surprises.

### How Kombu emulates a broker

Redis has lists and sorted sets. **It has no concept of acknowledgement, delivery or visibility.** Kombu builds them:

```
queue:celery              a LIST. RPUSH to enqueue, BRPOP to consume
unacked                   a HASH of in-flight messages
unacked_index             a ZSET scored by delivery deadline
```

```
1. Worker BRPOPs a message
2. Kombu writes it to `unacked` and `unacked_index` with a deadline
3. Worker processes, then acks → Kombu deletes from both
4. A background thread scans `unacked_index` for expired entries
   and pushes them back onto the queue
```

💡 **The `visibility_timeout` is entirely a Kombu construct.** Redis knows nothing about it.

⚠️ **The consequences are significant:**

| Consequence | |
|---|---|
| The restore thread lives **in the worker** | If every worker dies, nothing restores unacked messages |
| Default `visibility_timeout` is **1 hour** | A task longer than that is redelivered while running |
| The unacked set grows if restores fail | And it is not obvious that it has |
| **Not atomic** | The move from `unacked` back to the queue has a small window |

```python
app.conf.broker_transport_options = {
    "visibility_timeout": 3600,          # ⚠️ must exceed your longest task
    "fanout_prefix": True,
    "fanout_patterns": True,
}
```

⚠️ **If a task can take longer than `visibility_timeout`, it will be delivered to a second worker while the first is still running.** With `acks_late=True` and long tasks, this is the most common cause of mysterious duplicate execution in Celery-on-Redis.

**Set it well above your hard time limit** ([[08.3 - Celery Architecture]]).

### Durability

```
appendonly no         ← default. Everything queued is lost on restart
appendonly yes
appendfsync everysec  ← up to 1 second of messages lost
appendfsync always    ← durable, and much slower
```

⚠️ **The default Redis configuration loses every queued task on restart.** Not "some" — all of them.

💡 **This is the single most important thing to check about a Celery-on-Redis deployment**, and it is frequently wrong because the default is convenient for development and nobody revisits it.

### The eviction trap

```
maxmemory-policy allkeys-lru
```

⚠️ **Your queue keys are evictable.** Under memory pressure, Redis evicts them — silently — and the tasks are gone.

```
maxmemory-policy noeviction      # for a broker
```

**Or use a separate Redis instance for the broker and the cache**, which is the better answer ([[07.2 - Cache Strategies and Invalidation]]).

### Where Redis is genuinely right

| Situation | |
|---|---|
| You already run Redis | No new infrastructure |
| Task loss on a rare broker restart is acceptable | With persistence, this is a narrow window |
| Low latency matters | Sub-millisecond enqueue |
| Moderate volume | Below roughly 10,000 messages/second |
| Simple routing | One or a few queues |

⚠️ **Redis is not right when task loss is unacceptable**, when you need priorities, or when you need publisher confirms.

## RabbitMQ

A purpose-built message broker implementing AMQP.

```
Producer → Exchange → (routing) → Queue → Consumer
```

| Exchange type | Routes by |
|---|---|
| `direct` | Exact routing key match |
| `topic` | Pattern match (`document.*.indexed`) |
| `fanout` | To every bound queue |
| `headers` | Header values |

💡 **The exchange/binding model is genuinely more expressive than a flat queue namespace.** One publish can reach several queues with different consumers, without the producer knowing who they are — which is a real decoupling benefit.

### What you get that Redis cannot give you

**Publisher confirms:**

```python
app.conf.broker_transport_options = {"confirm_publish": True}
```

The broker confirms the message is durably stored. **This closes the enqueue gap** from [[08.2 - Queue Semantics]] — without it, `.delay()` returning tells you nothing.

**Real acknowledgement:**

Unacked messages are tracked by the broker and tied to the consumer's channel. **When a connection drops, the broker requeues them immediately** — no restore thread, no visibility timeout, no window.

**Native priorities:**

```python
app.conf.task_queue_max_priority = 10
task.apply_async(priority=9)
```

⚠️ Priorities have a real cost — the queue becomes a priority queue internally — and they do not preempt running tasks. Still, they work, and on Redis they are emulated with separate keys and work poorly.

**Dead letter exchanges:**

```python
queue_arguments = {
    "x-dead-letter-exchange": "dlx",
    "x-message-ttl": 3600000,
    "x-max-length": 100000,
}
```

Broker-level DLQ, TTL and queue length limits — **backpressure enforced by the broker** rather than hoped for.

### The operational cost

⚠️ **RabbitMQ is a stateful clustered Erlang system, and running it well is a specialisation.**

| Concern | |
|---|---|
| **Clustering and partitions** | Requires a partition handling strategy |
| **Quorum queues** | Raft-based, the modern choice, and heavier than classic |
| Memory and disk alarms | The broker blocks publishers when thresholds are hit |
| Upgrades | Rolling upgrades across a cluster need care |
| The management UI | Useful, and another thing to secure |

💡 **A blocked publisher due to a memory alarm is a distinctive RabbitMQ failure**: `.delay()` hangs rather than failing, and your request path stalls. **Always set a publish timeout.**

## SQS

Managed, and the constraints are the interesting part.

```python
app.conf.broker_url = "sqs://"
app.conf.broker_transport_options = {
    "region": "ap-south-1",
    "visibility_timeout": 3600,
    "polling_interval": 1,
    "wait_time_seconds": 20,          # long polling
}
```

| Constraint | |
|---|---|
| **256 KB message limit** | Send references, not payloads |
| **No priorities** | Use separate queues |
| No `fanout` | So no Celery remote control, no events, no Flower |
| At-least-once (standard queues) | FIFO queues exist, with throughput limits |
| **Per-request pricing** | Polling costs money |

⚠️ **`wait_time_seconds` is not optional.** Without long polling, workers poll continuously and you pay for every empty poll. With it set to 20, an idle worker makes 3 requests per minute instead of thousands.

💡 **SQS's operational story is unbeatable** — no cluster, no upgrades, no disk alarms, effectively infinite scale. **The cost is the feature set**, and the loss of Celery's remote control and monitoring is more disruptive than people expect.

**FIFO queues** give per-group ordering and deduplication, at 300 messages/second per group. **Useful when you need ordering and the throughput fits.**

## The Result Backend

A separate choice from the broker, and often the wrong thing to enable.

```python
app.conf.result_backend = "redis://localhost/1"
app.conf.result_expires = 3600
```

| Backend | Notes |
|---|---|
| Redis | Fast. Evictable ⚠️. TTL-based expiry |
| RabbitMQ (RPC) | One queue per result. **Does not scale** |
| Database | Durable, queryable, slower |
| S3 / filesystem | For large results |
| **None** | **Usually correct** |

💡 **The strongest advice in this note: turn results off and write to your own database instead.**

```python
app.conf.task_ignore_result = True
```

**Why:**

| Reason | |
|---|---|
| You control the schema and the states | `PENDING` is not a real state ([[08.3 - Celery Architecture]]) |
| It is queryable and joinable | "All failed documents for this org" is a `SELECT` |
| It is durable and backed up | Not a Redis key with a TTL |
| It survives eviction | Redis results can be evicted before being read |
| Your API needs a status resource anyway | ([[08.1 - Why Background Work Exists]]) |

⚠️ **Every enabled result backend is a write per task plus a key that must expire.** At 10,000 tasks/minute that is meaningful Redis load for data nobody reads.

**Enable results only for the specific tasks whose return value you genuinely consume**, typically chords and chains.

## In Production

### Choosing

```
Do you need publisher confirms or guaranteed durability?
├── YES → RabbitMQ, or SQS
│
└── NO
    ├── Already running Redis, moderate volume, simple routing?
    │   └── Redis, with appendonly yes and noeviction
    ├── On AWS, want zero operations?
    │   └── SQS, accepting the 256 KB and no-fanout constraints
    └── Complex routing, priorities, or high reliability?
        └── RabbitMQ, and budget for operating it
```

💡 **For Conduit: Redis with persistence.** The volume is moderate, routing is simple, Redis is already there for caching (on a separate instance), and the outbox pattern closes the durability gap that publisher confirms would otherwise address ([[09.3 - The Outbox Pattern]]).

**Being able to say "we do not need publisher confirms because the outbox guarantees the message exists" is the sophisticated version of this decision.**

### Separate instances

```
redis-cache      maxmemory 4gb, allkeys-lru
redis-broker     maxmemory 2gb, noeviction, appendonly yes
redis-results    (if used) allkeys-lru, short TTLs
```

⚠️ **One Redis for cache and broker with `allkeys-lru` means your queue can be evicted.** This is a real and quiet failure.

### Connection handling

```python
app.conf.update(
    broker_pool_limit=10,
    broker_connection_timeout=10,
    broker_connection_retry_on_startup=True,
    broker_connection_max_retries=None,          # retry forever
    broker_heartbeat=30,                          # RabbitMQ
)
```

⚠️ **`broker_connection_max_retries=None` means a worker retries forever rather than exiting.** Usually correct — you want the worker to reconnect after a broker restart rather than crash-looping through your orchestrator.

**In the web process, use a bounded publish timeout** so a broker problem does not hang request handling:

```python
task.apply_async(args, retry=False)      # fail fast in the request path
```

💡 **A hanging `.delay()` in a request handler is a worse failure than a failed enqueue**, because it consumes a worker and the user waits. Fail fast, and let the outbox retry.

### Monitoring the broker

```bash
# Redis
redis-cli llen celery
redis-cli hlen unacked
redis-cli zcard unacked_index
redis-cli info persistence | grep aof_last_write_status

# RabbitMQ
rabbitmqctl list_queues name messages messages_unacknowledged consumers
rabbitmqctl status | grep -A5 alarms
```

```python
broker_queue_depth.labels(queue=name).set(depth)
broker_unacked_count.set(count)
broker_oldest_message_age_seconds.set(age)
broker_connection_errors_total.inc()
```

⚠️ **On Redis, a growing `unacked` hash with a stable queue depth means the restore thread is not running or messages are stuck.** It is a specific and diagnosable symptom that most people do not monitor.

💡 **On RabbitMQ, `messages_unacknowledged` climbing means consumers are holding messages without acking** — either prefetch is too high, or tasks are slow, or workers are stuck.

### Broker failure behaviour

| Failure | Redis | RabbitMQ | SQS |
|---|---|---|---|
| Broker restart, no persistence | **All tasks lost** | Durable queues survive | N/A |
| Broker unreachable during enqueue | `.delay()` raises | Blocks or raises | Raises |
| Worker loses connection mid-task | Unacked restored after visibility timeout | **Requeued immediately** | After visibility timeout |
| Memory pressure | Evicted (if `allkeys-lru`) | **Publishers blocked** | N/A |

**Test each of these against your configuration.** The differences are large and they only appear under failure.

## Codebase

**Repo:** `celery/kombu`, `rabbitmq/rabbitmq-server`

**Question to answer:** In Kombu's Redis transport, what exactly happens to an in-flight message when the only worker holding it is `SIGKILL`ed? Trace the restore path. Then: in RabbitMQ, what triggers a memory alarm and what does it do to publishers?

**Read, in order:**

1. `kombu/kombu/transport/redis.py` — **`QoS.append`, `QoS.ack`, and `QoS.restore_visible`.** The unacked hash, the sorted set, and the restore loop. **The answer to the first question is here — and note that the restore thread runs in the worker, so if all workers die, nothing restores**
2. `kombu/kombu/transport/virtual/base.py` — the generic emulation layer that Redis, SQS and others build on. **Seeing what is generic versus broker-specific clarifies the whole abstraction**
3. `kombu/kombu/transport/SQS.py` — how SQS's native visibility timeout maps onto the same interface. Note what is unsupported
4. `rabbitmq-server/deps/rabbit/src/rabbit_alarm.erl` and `vm_memory_monitor.erl` — **memory and disk alarms.** The answer to the second question: publishers are blocked, not rejected, which is why `.delay()` hangs
5. `rabbitmq-server/deps/rabbit/src/rabbit_channel.erl` — acknowledgement and requeue on channel close

💡 The restore-thread detail in step one is the most operationally valuable thing in this note. **Celery on Redis has no broker-side recovery** — if your entire worker fleet dies, in-flight messages sit in the unacked hash until a worker starts and its restore thread finds them. On RabbitMQ, the broker requeues them the instant the connection drops. **That difference matters during an incident.**

**Size:** 1–2 sessions.

```
│   └── RESULTS.md

│   └── queue_evicted.py  # allkeys-lru eats the queue

│   ├── no_confirm.py     # enqueue "succeeds", message lost
│   ├── with_confirm.py
│   └── outbox.py         # the alternative
├── features/
│   ├── priorities.py     # rabbitmq vs redis emulation
│   ├── routing.py        # exchanges vs flat queues
│   └── COMPARISON.md
├── results/
│   ├── backend_cost.py   # load with results on vs off
│   ├── db_status.py      # the alternative
│   └── RESULTS.md
└── README.md
```

**Part 1 — One app, three brokers.** The same Celery application configured for Redis, RabbitMQ and SQS (via LocalStack).

Run an identical workload against each. Measure enqueue latency, end-to-end latency, and throughput.

**Part 2 — Broker restart with queued work.** Enqueue 10,000 tasks, stop all workers, restart the broker.

Test: Redis with `appendonly no`, Redis with `appendonly yes appendfsync everysec`, Redis with `appendfsync always`, RabbitMQ with transient queues, RabbitMQ with durable queues and persistent messages.

**Count survivors in each.** The first should be zero, and seeing that number yourself is the point.

Also measure the enqueue throughput cost of each durability setting.

**Part 3 — Worker death and recovery.** A task taking 60 seconds. `SIGKILL` the worker at 30 seconds.

Measure **time until another worker picks it up** on Redis and on RabbitMQ.

**RabbitMQ should be immediate; Redis should wait for the visibility timeout.**

Then the crucial variant: kill **all** workers while a task is in flight, wait five minutes, then start a worker. **Confirm on Redis that nothing was restored until a worker started**, and inspect the `unacked` hash directly to see the message sitting there.

**Part 4 — Exceed the visibility timeout.** `visibility_timeout=60`, a task taking 180 seconds, `acks_late=True`.

**Confirm the task is delivered three times and runs concurrently.** Instrument to prove all three executions overlapped.

Then set the timeout correctly, and separately show that splitting the task into shorter stages removes the risk entirely.

**Part 5 — Evict the queue.** Redis with `maxmemory` low and `allkeys-lru`, shared with a cache workload.

Enqueue tasks, then drive cache writes until eviction. **Confirm queued tasks disappear with no error anywhere.**

Then `noeviction`, and confirm enqueues fail loudly instead — which is far better.

**Part 6 — The enqueue gap.** Commit a database row, then kill the process before `.delay()` completes.

**Confirm the row exists and no task was ever queued.** Measure how often this happens with realistic timing.

Then three fixes: RabbitMQ publisher confirms, a retry loop around the publish, and the outbox pattern. **Compare correctness and complexity.**

**The outbox should be the only one that is fully correct**, because confirms still leave a gap between the database commit and the publish.

**Part 7 — Features that differ.** Priorities on RabbitMQ versus Redis emulation: enqueue 1,000 mixed-priority tasks and measure whether high-priority tasks actually run first.

Then topic routing on RabbitMQ versus separate queues on Redis for the same fan-out requirement, and compare the producer-side coupling.

**Part 8 — The result backend cost.** 100,000 tasks with results enabled and disabled.

Measure: Redis memory used, Redis operations per second, task latency, and worker throughput.

Then implement the database-status alternative and measure the same, plus what you gain — queryability, durability, and real states.

**Done when:**
- Your durability table has survivor counts for five configurations
- You know the recovery time difference between Redis and RabbitMQ after a worker kill
- You have seen a message sitting in the Redis `unacked` hash with no worker to restore it
- You produced three concurrent executions of one task via visibility timeout
- Your queue was silently evicted, and `noeviction` made it fail loudly
- The enqueue gap is reproduced and only the outbox fully closes it
- You have measured the result backend's cost and the database alternative's benefit
