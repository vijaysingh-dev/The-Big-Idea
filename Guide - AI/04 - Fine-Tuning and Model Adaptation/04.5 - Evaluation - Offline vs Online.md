# Evaluation: Offline vs Online

## Why Evaluation is the Hardest Part

Training a model is mechanical. Evaluating whether it's actually better is hard:

- LLM outputs are non-deterministic
- "Better" is often subjective
- Automatic metrics are proxies that can be gamed
- Distribution shift: eval set ≠ production traffic

Invest heavily in evaluation infrastructure before training. If you can't measure improvement, you can't improve.

---

## Offline Evaluation

Evaluation against a fixed held-out dataset, before deployment.

### Types of Offline Metrics

**Exact match / Accuracy** For tasks with clear correct answers:

```python
accuracy = sum(1 for pred, gold in zip(predictions, labels) if pred == gold) / len(labels)
```

Appropriate for: classification, extraction tasks, multiple-choice QA.

**ROUGE (Recall-Oriented Understudy for Gisting Evaluation)** Measures n-gram overlap between generated and reference text.

```
ROUGE-1: unigram overlap
ROUGE-2: bigram overlap
ROUGE-L: longest common subsequence
```

Used for: summarization. Correlation with human judgment is moderate — a model can get high ROUGE by outputting text similar to the reference in surface form without being actually correct.

**BLEU** Precision-based n-gram overlap. Standard for translation.

**BERTScore** Semantic similarity between generated and reference text using BERT embeddings. Correlates better with human judgment than ROUGE for open-ended generation.

**Perplexity** Measures how well the model predicts a test corpus (lower = better). Useful for comparing models but doesn't directly reflect task performance.

### LLM-as-Judge (Most Important)

Use a strong LLM (GPT-4, Claude) to score your model's outputs:

```python
JUDGE_PROMPT = """
You are evaluating the quality of an AI response.

Question: {question}
Reference answer: {reference}
Model response: {response}

Score the model response on:
1. Factual accuracy (0-10): Does it contain only true statements?
2. Completeness (0-10): Does it fully answer the question?
3. Clarity (0-10): Is it well-written and easy to understand?
4. Conciseness (0-10): Does it avoid unnecessary verbosity?

Output JSON: {"accuracy": N, "completeness": N, "clarity": N, "conciseness": N, "reasoning": "..."}
"""

def evaluate_response(question, reference, response):
    result = judge_llm.call(JUDGE_PROMPT.format(...))
    return json.loads(result)
```

**LLM-as-judge biases to know**:

- **Position bias**: Prefers the response listed first in comparisons
- **Verbosity bias**: Prefers longer responses
- **Self-enhancement bias**: Models prefer outputs similar to their own style
- **Mitigation**: Randomize order, calibrate with human labels

### MT-Bench and Standard Benchmarks

|Benchmark|What it tests|Use for|
|---|---|---|
|MT-Bench|Multi-turn instruction following, reasoning|General chat quality|
|HumanEval|Python code generation|Coding tasks|
|MMLU|Broad knowledge across 57 subjects|Knowledge retention|
|TruthfulQA|Resistance to hallucination|Factual reliability|
|RAGAS|RAG pipeline quality|RAG-specific|

Run applicable standard benchmarks before and after fine-tuning to catch regression.

## Regression Prevention

The most important and most neglected aspect of fine-tuning evaluation.

**The risk**: Fine-tuning on task A improves task A but degrades task B (catastrophic forgetting of general abilities).

**Strategy**:

```
Pre-training eval set
├── Core capabilities (MMLU, MT-Bench subset)
├── Format/style behaviors from previous fine-tuning
├── Safety behaviors (shouldn't say harmful things)
└── Task-specific golden examples

Run this eval:
- Before fine-tuning (baseline)
- After fine-tuning
- Compare: any degradations > threshold → reject the model
```

Define acceptance criteria:

```python
REGRESSION_THRESHOLDS = {
    "mmlu_accuracy": -2.0,        # Max allowed drop: 2 percentage points
    "safety_score": -0.5,         # Max allowed drop: 0.5 points
    "format_compliance": -5.0,    # Max allowed drop: 5 percentage points
}

def passes_regression_check(before_scores, after_scores):
    for metric, threshold in REGRESSION_THRESHOLDS.items():
        delta = after_scores[metric] - before_scores[metric]
        if delta < threshold:
            print(f"REGRESSION FAIL: {metric} dropped by {delta}")
            return False
    return True
```

## Online Evaluation

Measuring model quality in production using real user traffic.

### Implicit Signals

Users express preference through behavior:

- **Click-through rate**: Did the user click on a cited source?
- **Session length**: Did the user continue the conversation? (engagement signal)
- **Task completion rate**: Did the user achieve their goal?
- **Return rate**: Does the user come back?

These are weak signals but available at scale without extra instrumentation.

### Explicit Feedback

Direct quality signals from users:

```
[Thumbs up / Thumbs down]  ← simplest, lowest friction
[1–5 star rating]
[Edited response]           ← strongest signal: user changed the answer
["Report an issue" button]
```

Log these with: the prompt, the retrieved context (for RAG), the model response, and any model/prompt version identifiers.

### A/B Testing

Compare two model versions (or prompt versions) on real traffic:

```python
def route_request(user_id, request):
    # 90% to current production model, 10% to challenger
    if hash(user_id) % 100 < 10:
        return call_model_v2(request), "v2"
    else:
        return call_model_v1(request), "v1"
```

Track: task completion, feedback rates, latency, cost per response.

**Statistical significance**: Run A/B tests long enough to reach significance. LLM quality differences are often small; you need thousands of samples to detect a 2% improvement.

### Shadow Evaluation

Run a new model version silently alongside production without serving its outputs. Log and evaluate responses without risk. Useful before promoting a model to production.

## RAG-Specific Evaluation

For RAG systems, evaluate each component separately:

```
Retrieval quality:
├── Recall@K: Is the relevant document in the top-K results?
├── MRR (Mean Reciprocal Rank): How highly is the relevant doc ranked?
└── NDCG: How well are results ordered?

Generation quality:
├── Faithfulness: Is the answer grounded in retrieved context?
├── Answer relevance: Does the answer address the question?
└── Context precision: Did the model use the retrieved context efficiently?
```

RAGAS framework automates these metrics using LLM-as-judge. See [[../10 - Production AI Engineering/10.5 - Evaluation Pipelines and Monitoring]].

## Evaluation Infrastructure

```
eval/
├── datasets/
│   ├── regression_suite.jsonl      ← golden examples, never changes
│   ├── domain_qa.jsonl             ← domain-specific test set
│   └── safety_probes.jsonl         ← adversarial inputs
├── metrics/
│   ├── llm_judge.py                ← LLM-as-judge scorer
│   ├── exact_match.py
│   └── rouge.py
├── run_eval.py                     ← CI integration point
└── reports/                        ← stored eval results per run
    ├── 2024-01-15_v1.2_results.json
    └── ...
```

**Run evals in CI**: Before any model deployment, evals should run automatically and block deployment on regression.
