# Requirements Clarification

> **Revision tags:** #methodology #requirements  
> **Related:** [[02.2 - Requirements Clarification]] | [[02.3 - Estimation and Capacity]]

---

## Why Clarification Is the Most Valuable 5 Minutes

Every HLD decision is downstream of requirements. A URL shortener designed for Twitter scale (billions of redirects/day) looks completely different from one designed for an internal tool (1,000 redirects/day).

Designing without clarification is solving the wrong problem very precisely.

In interviews: interviewers intentionally give vague prompts ("design Twitter"). They're testing whether you know to ask before you draw.

---

## The Clarification Question Bank

Use these as a checklist. Not all apply to every problem — pick what's relevant.

### Functional Scope

```
- What are the 2–3 core use cases we must support?
- What is explicitly out of scope?
- Are there multiple user types? (consumers vs merchants, users vs admins)
- Is this a new system or integrating with an existing one?
- What does success look like for a user completing the core flow?
```

### Scale and Traffic

```
- How many daily active users (DAU)?
- How many requests per second at peak?
- What's the read:write ratio?
- Is traffic bursty (flash sales, live events) or steady?
- What's the growth expectation? (2x/year? 10x?)
```

### Data

```
- What's the total data volume today and in 3 years?
- Is data ever deleted, or does it accumulate indefinitely?
- Are there data residency requirements? (data must stay in EU)
- How long does data need to be retained?
```

### Consistency and Availability

```
- What's the availability SLA? (99.9%? 99.99%?)
- Can users tolerate stale reads? If so, how stale?
- Are there operations that require strong consistency?
- What's the impact of data loss? (financial? reputational? recoverable?)
```

### Latency

```
- What's the acceptable response time for user-facing operations? (p99)
- Are there SLA requirements with external parties?
- Are there real-time requirements? (chat, live feeds, collaborative editing)
```

### Geography

```
- Is this a global system (users in multiple continents)?
- Are there geo-compliance requirements (GDPR, data sovereignty)?
- Do we need multi-region for latency or for DR?
```

### Security and Compliance

```
- Are there regulatory requirements? (PCI DSS for payments, HIPAA for health)
- Who are the authorized callers? (public, authenticated users, service-to-service)
- Is PII involved? If so, what are the handling requirements?
```

## Writing Down Assumptions

After clarification, state your assumptions explicitly. This matters in interviews (shows clarity) and in real projects (prevents misalignment).

**Template:**
```
Functional:
- Core flows: [list them]
- Out of scope: [list them]

Scale:
- 10M DAU
- Peak 50,000 RPS
- Read:write = 100:1

Non-functional:
- 99.9% availability
- p99 latency < 200ms for reads
- Eventual consistency acceptable for feed
- Strong consistency required for payment operations
- Data must not be lost (RPO = 0 for transactions)
```

Write this at the top of your design. It anchors every decision you make next.

## Scope Creep — How to Prevent It

In a 45-minute interview, you cannot design all of Facebook. Scope ruthlessly.

**How to scope:**
1. Identify the 2–3 flows that are architecturally interesting (not all flows are).
2. Explicitly call out what you're not designing.
3. Say: "I'll focus on the write path and the feed read path — auth, admin, and analytics are out of scope for today."

Interviewers respect this. It shows you understand that real systems are scoped.

**What makes a flow architecturally interesting:**
- High scale / potential bottleneck
- Complex consistency requirements
- Non-trivial failure modes
- Novel tradeoffs

For Instagram: the interesting flows are *photo upload* (storage, transcoding) and *feed generation* (fan-out problem). Direct messages are a separate system. Ads are a separate system. Focus.

## Turning Vague Requirements into Design Drivers

Raw requirement → Design implication:

| Requirement | Design Implication |
|---|---|
| 10M DAU, 50K RPS | Need load balancer, horizontal scaling, DB read replicas |
| Read:write = 100:1 | Optimize heavily for reads — caching, CDN, read replicas |
| Global users | CDN, multi-region, geo-aware routing |
| Real-time updates | WebSockets or SSE, push architecture |
| Strong consistency for payments | Single-leader DB, synchronous replication, no caching for balances |
| 99.99% availability | Multi-AZ, auto-failover, no SPOF |
| Data retention 7 years | Cold storage tier, archival pipeline |
| GDPR | Data residency controls, right-to-deletion implementation |

## Common Clarification Mistakes

**Asking too many questions:** Pick the 5 most impactful. Don't interrogate.

**Not writing down answers:** You'll forget. Write assumptions explicitly.

**Assuming scale:** Don't assume it's Twitter scale. Don't assume it's toy scale. Ask.

**Skipping NFRs entirely:** Most junior engineers only ask about features. The architecture lives in the NFRs.

**Treating scope as fixed after clarification:** New requirements emerge during design. It's fine to say "this assumption changes X, let me adjust."
