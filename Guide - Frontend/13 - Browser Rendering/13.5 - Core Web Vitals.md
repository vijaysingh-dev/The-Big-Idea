# Core Web Vitals

Three metrics Google uses to quantify user experience, measured on real users rather than in a lab. They matter because they are a search ranking input and because they correlate with actual perceived quality.

| Metric | Measures | Good | Poor |
| --- | --- | --- | --- |
| **LCP** — Largest Contentful Paint | loading | ≤ 2.5s | > 4.0s |
| **INP** — Interaction to Next Paint | responsiveness | ≤ 200ms | > 500ms |
| **CLS** — Cumulative Layout Shift | visual stability | ≤ 0.1 | > 0.25 |

The threshold is the **75th percentile** across real sessions. A good median with a bad p75 fails, which is deliberate — the metric is about the experience of your slower quarter of users, typically those on mid-range Android devices and congested networks.

## LCP

The render time of the largest text block or image in the viewport. Candidates are `<img>`, `<image>` inside `<svg>`, `<video>` poster frames, elements with a CSS `background-image`, and block-level text nodes.

Breakdown into four phases, which is how you diagnose it:

1. **TTFB** — server response time
2. **Resource load delay** — time between TTFB and the browser starting to fetch the LCP resource
3. **Resource load duration** — the fetch itself
4. **Element render delay** — time between the resource arriving and it being painted

Most LCP problems are phase 2 — the browser did not know it needed the resource early enough. Fixes:

```html
<img src="hero.avif" fetchpriority="high" loading="eager" width="1200" height="600" alt="...">
<link rel="preload" as="image" href="hero.avif" fetchpriority="high">
```

The LCP element should be a real `<img>` in the server-rendered HTML so the preload scanner finds it ([[13.1 - The Critical Rendering Path]]). A CSS background image or a JS-injected element is discovered late, and that delay is usually the whole problem.

Phase 4 is common in client-rendered SPAs: the image has downloaded but React has not rendered yet. That is a rendering-strategy problem, not an image problem ([[28.11 - Rendering Strategies]]).

**Never lazy-load the LCP element.** `loading="lazy"` on a hero image is a self-inflicted wound.

## INP

Replaced FID in March 2024. FID measured only the *delay* before the first interaction's handler started; INP measures the **full latency of the worst interaction** on the page — from input to the next frame being painted.

Three phases again:

1. **Input delay** — the main thread was busy when the input arrived
2. **Processing time** — your event handlers running
3. **Presentation delay** — rendering and painting the result

INP is much harder to satisfy than FID because it includes the work your handler causes, not just the wait before it.

Practical fixes:

**Yield to let the browser paint** before doing heavy work:

```js
button.addEventListener("click", async () => {
  showSpinner();                       // cheap, visible immediately
  await scheduler.yield?.() ?? new Promise(r => setTimeout(r, 0));
  doExpensiveWork();                   // now the spinner is on screen
});
```

`await` alone does not help — it yields to the microtask queue, which drains before paint ([[01.6 - Microtasks vs Macrotasks]]). A real task boundary is required.

**Break up long tasks.** Anything over 50 ms blocks input. Chunk it, or move it to a worker ([[08.4 - Web Workers]]).

**Mark non-urgent React updates as transitions:**

```jsx
const [isPending, startTransition] = useTransition();

const onChange = (e) => {
  setQuery(e.target.value);                    // urgent — input stays responsive
  startTransition(() => setResults(filter(e.target.value)));  // interruptible
};
```

This is exactly what concurrent rendering was built for ([[22.4 - useTransition and startTransition]]).

**Reduce DOM size.** Presentation delay scales with how much the browser must lay out and paint. A 10,000-node list is slow to update regardless of how fast your handler is — hence virtualization ([[19.5 - Virtualization and Windowing]]).

Third-party scripts are a frequent INP culprit, since they occupy the main thread at unpredictable moments.

## CLS

A score combining how much of the viewport shifted (impact fraction) and how far things moved (distance fraction), summed over the worst 5-second window of shifts.

Shifts within 500 ms of a user interaction are excluded — expanding an accordion is expected movement, not instability.

The causes are a short list, and each has a direct fix:

**Images without dimensions.** Always set `width` and `height`, or `aspect-ratio` ([[09.3 - Images Media and Loading Attributes]]).

**Ads, embeds and iframes.** Reserve space with a `min-height` container sized to the most common creative.

**Web fonts.** A fallback swapping to a differently-proportioned webfont reflows all the text. Use `font-display: optional`, or match fallback metrics with `size-adjust` and `ascent-override`.

**Content injected above existing content.** A cookie banner, a promotional bar, or an error message pushing the page down. Reserve space, or overlay rather than insert.

**Dynamically loaded content without a placeholder.** Skeletons should match the final content's dimensions, not just be present.

**`position: sticky` elements** that change height when they stick.

## Measuring

**Field data (real users)** is what counts for ranking. Sources: Chrome UX Report (CrUX), the `web-vitals` library, or a RUM provider.

```js
import { onLCP, onINP, onCLS } from "web-vitals";

onLCP(m => report(m));
onINP(m => report(m));
onCLS(m => report(m));
```

Each metric object includes `attribution` data when using `web-vitals/attribution` — the actual LCP element selector, the INP event target and phase breakdown, the largest shift source. That attribution is what turns "INP is 400ms" into "the search input's change handler is the problem".

**Lab data** — Lighthouse, DevTools Performance panel — is for debugging, not for judging. Lighthouse cannot measure INP at all (there are no real interactions) and substitutes Total Blocking Time as a proxy.

The gap between lab and field scores is normal and expected. Lab runs on one device with a synthetic network profile; the field is every device your users own.

## Other metrics worth tracking

- **TTFB** — server and network. A slow TTFB caps every other metric.
- **FCP** — first pixel of any content. Useful for diagnosing render-blocking resources.
- **TBT** — Total Blocking Time, the lab proxy for INP.

## How senior engineers actually use this

**They measure the field, debug in the lab.** Optimizing against a Lighthouse score without RUM data routinely improves the wrong thing.

**They use attribution data** to identify the specific element or handler rather than guessing.

**They set performance budgets in CI.** Bundle size limits and Lighthouse CI thresholds catch regressions before they ship ([[27.9 - CI CD and Frontend Deployment]]).

**They watch p75, not the average.** An average hides exactly the users the metric exists to protect.

**They treat CLS as mostly preventable.** Unlike LCP and INP, which involve real tradeoffs, layout shift is nearly always an omission — a missing dimension or an unreserved space.

## Common pitfalls

- Optimizing Lighthouse scores without field data.
- Lazy-loading the LCP element.
- Missing image dimensions.
- Assuming `await` yields to rendering.
- Ignoring third-party scripts, which frequently dominate INP.
- Reporting averages instead of p75.
- Treating a good desktop score as representative — the field is mostly mobile.
- Skeleton screens whose dimensions differ from the loaded content, causing shift anyway.

## Interview angle

Core Web Vitals come up in any performance conversation. Name the three, what each measures, and the thresholds. The stronger material is the diagnostic breakdown: LCP's four phases with resource load delay as the usual culprit, INP's three phases and why yielding to a task boundary (not just `await`) is the fix, and CLS's causes being almost entirely preventable omissions. Mentioning that INP replaced FID, and why the change made the bar harder, signals current knowledge.
