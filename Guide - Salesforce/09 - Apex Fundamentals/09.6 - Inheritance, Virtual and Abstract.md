# Inheritance, Virtual and Abstract

## Opt-in extensibility

Apex classes are **final by default**. A class cannot be extended and a method cannot be overridden unless explicitly declared otherwise.

```java
public class ClaimService { }            // cannot be extended
public virtual class ClaimService { }    // can be extended
public abstract class ClaimService { }   // must be extended, cannot be instantiated
```

This differs from Java, where classes are extensible unless marked `final`. The Apex default is the safer one: extensibility is a design decision, not an accident.

## Virtual classes and methods

```java
public virtual with sharing class ClaimProcessor {

    public virtual void process(List<Warranty_Claim__c> claims) {
        validate(claims);
        applyBusinessRules(claims);
        update claims;
    }

    protected virtual void validate(List<Warranty_Claim__c> claims) {
        for (Warranty_Claim__c claim : claims) {
            if (claim.Asset__c == null) {
                claim.addError('A machine must be specified.');
            }
        }
    }

    protected virtual void applyBusinessRules(List<Warranty_Claim__c> claims) {
        for (Warranty_Claim__c claim : claims) {
            claim.Approval_Tier__c = tierFor(claim.Claim_Amount__c);
        }
    }

    protected String tierFor(Decimal amount) {
        return amount > 500000 ? 'Executive' : amount > 100000 ? 'Director' : 'Manager';
    }
}
```

```java
public with sharing class PremiumClaimProcessor extends ClaimProcessor {

    protected override void validate(List<Warranty_Claim__c> claims) {
        super.validate(claims);   // reuse the base checks, then add

        for (Warranty_Claim__c claim : claims) {
            if (claim.Claim_Amount__c > 1000000 && !claim.Engineer_Report_Attached__c) {
                claim.addError('An engineer report is required above 10 lakh.');
            }
        }
    }
}
```

**A method must be `virtual` or `abstract` in the parent to be overridden**, and the child must use the `override` keyword. Both are compile-time enforced, which prevents the accidental-override problem that Java has.

`super.method()` calls the parent implementation. `super(...)` in a constructor calls the parent constructor and must be the first statement.

## Abstract classes

An abstract class cannot be instantiated and may contain abstract methods that subclasses must implement.

```java
public abstract with sharing class IntegrationJob implements Queueable, Database.AllowsCallouts {

    protected final Set<Id> recordIds;

    public IntegrationJob(Set<Id> recordIds) {
        this.recordIds = recordIds;
    }

    // the template method: fixed sequence, variable steps
    public void execute(QueueableContext context) {
        try {
            List<SObject> records = loadRecords();
            if (records.isEmpty()) {
                return;
            }
            HttpResponse response = send(buildPayload(records));
            handleResponse(records, response);
        } catch (Exception e) {
            AutomationLogger.logError(jobName(), null, e.getMessage() + '\n' + e.getStackTraceString());
        }
    }

    protected abstract String jobName();
    protected abstract List<SObject> loadRecords();
    protected abstract String buildPayload(List<SObject> records);
    protected abstract void handleResponse(List<SObject> records, HttpResponse response);

    protected virtual String namedCredential() {
        return 'callout:ERP_System';
    }

    private HttpResponse send(String body) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint(namedCredential() + '/api/sync');
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(body);
        return new Http().send(req);
    }
}
```

```java
public with sharing class ClaimSyncJob extends IntegrationJob {

    public ClaimSyncJob(Set<Id> claimIds) {
        super(claimIds);
    }

    protected override String jobName() {
        return 'ClaimSyncJob';
    }

    protected override List<SObject> loadRecords() {
        return [
            SELECT Id, Claim_Number__c, Claim_Amount__c, Status__c, Asset__r.SerialNumber
            FROM Warranty_Claim__c WHERE Id IN :recordIds
        ];
    }

    protected override String buildPayload(List<SObject> records) {
        return JSON.serialize(ClaimPayload.from((List<Warranty_Claim__c>) records));
    }

    protected override void handleResponse(List<SObject> records, HttpResponse response) {
        if (response.getStatusCode() >= 300) {
            throw new CalloutException('Claim sync failed: ' + response.getStatusCode());
        }
        markSynced(records);
    }
}
```

This is the **template method pattern** — the base class fixes the sequence and error handling; subclasses supply the varying steps. It is the most useful application of abstract classes in Apex, because the error handling, logging, and callout plumbing are identical across integrations and only the payload and record loading differ.

## What Apex does not have

**No multiple inheritance.** One superclass. Multiple interfaces are allowed.

**No `final` on methods** to prevent further overriding. A method is either non-virtual (unoverridable) or virtual (overridable indefinitely).

**No static method overriding.** Statics are resolved by the declared type, not the runtime type.

**No abstract properties.**

**Constructors are not inherited.** A subclass must define its own and call `super(...)` explicitly.

## Inheritance and sharing

A subclass **does not inherit** the parent's sharing keyword. It must declare its own.

```java
public virtual with sharing class BaseService { }
public class ChildService extends BaseService { }        // runs WITHOUT sharing
public with sharing class ChildService extends BaseService { }  // correct
```

This is a genuine security trap. A subclass omitting the keyword silently loses the parent's `with sharing` protection, and nothing warns you. Declaring the keyword on every class, as recommended in [[09.5 - Classes, Constructors and Access Modifiers]], prevents it.

## When to use inheritance, and when not

Inheritance is often the wrong tool, and Apex codebases suffer from it more than most because the trigger handler frameworks in circulation encourage deep hierarchies.

**Use inheritance when:**
- There is a genuine "is-a" relationship
- A fixed algorithm has variable steps — the template method case above
- Shared state and shared behaviour both need inheriting

**Prefer composition when:**
- You want to share behaviour without a type relationship
- The variation is in one behaviour rather than a whole algorithm
- Testability matters — an injected dependency is easier to mock than an overridden method

```java
// Inheritance: the discount logic is baked into the type hierarchy
public virtual class ClaimCalculator {
    protected virtual Decimal discountFor(Warranty_Claim__c claim) { return 0; }
}
public class PremiumClaimCalculator extends ClaimCalculator {
    protected override Decimal discountFor(Warranty_Claim__c claim) { return 0.1; }
}

// Composition: the strategy is injected and can be swapped or mocked
public class ClaimCalculator {
    private final DiscountStrategy strategy;

    public ClaimCalculator(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    public Decimal calculate(Warranty_Claim__c claim) {
        return claim.Claim_Amount__c * (1 - strategy.discountFor(claim));
    }
}
```

The composed version can be tested with a stub strategy, extended without touching the calculator, and combined with other strategies. The inherited version requires a new subclass for every combination.

The general guidance: **reach for interfaces and composition first, inheritance when there is a real algorithm skeleton to share.** See [[09.7 - Interfaces and Polymorphism]] and [[18.9 - Factory, Strategy and Singleton in Apex]].

## Testing subclasses

An abstract class cannot be instantiated, so testing its shared behaviour needs a test-only concrete subclass:

```java
@IsTest
private class IntegrationJobTest {

    private class StubJob extends IntegrationJob {
        public String payloadBuilt;

        public StubJob(Set<Id> ids) { super(ids); }

        protected override String jobName() { return 'StubJob'; }
        protected override List<SObject> loadRecords() {
            return new List<SObject>{ new Warranty_Claim__c(Id = fakeId) };
        }
        protected override String buildPayload(List<SObject> records) {
            payloadBuilt = '{"test":true}';
            return payloadBuilt;
        }
        protected override void handleResponse(List<SObject> records, HttpResponse response) { }
    }

    @IsTest
    static void executeCallsTemplateStepsInOrder() {
        Test.setMock(HttpCalloutMock.class, new SuccessMock());
        StubJob job = new StubJob(new Set<Id>{ someId });

        Test.startTest();
        System.enqueueJob(job);
        Test.stopTest();

        Assert.isNotNull(job.payloadBuilt, 'buildPayload should have been called');
    }
}
```

A private inner class in the test file is the right home for the stub — it keeps test-only code out of the production namespace.

## Practical guidance

**Classes are final by default.** Mark `virtual` or `abstract` only where extension is intended.

**Declare a sharing keyword on every subclass.** It is not inherited.

**Use the template method pattern** for families of jobs sharing a skeleton — integrations, batch jobs, import routines.

**Prefer composition to inheritance** for varying a single behaviour.

**Do not build deep hierarchies.** Two levels is usually the ceiling before a codebase becomes hard to follow.

**Use a private inner subclass in tests** to exercise abstract base behaviour.
