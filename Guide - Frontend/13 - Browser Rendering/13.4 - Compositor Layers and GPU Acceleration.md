# Compositor Layers and GPU Acceleration

The final stage of the rendering pipeline assembles painted layers into the image on screen. Because this happens on a separate thread and often on the GPU, work that can be expressed as layer composition is dramatically cheaper than work requiring layout or paint.

## Threads involved

**Main thread** — JavaScript, style recalculation, layout, and painting into layer bitmaps.

**Compositor thread** — takes painted layers, applies transforms and opacity, and hands the result to the GPU. It can produce frames **without the main thread**, which is why a CSS transform animation keeps running smoothly even while JavaScript is blocking.

**Raster threads** — convert paint instructions into bitmaps.

This separation is why `transform` and `opacity` animations survive a busy main thread and `left`/`width` animations do not ([[13.2 - Reflow Repaint and Composite]]).

It also explains a specific behavior: a page frozen by a long JavaScript task can still be scrolled, because scrolling is compositor-driven — until a non-passive scroll handler forces the compositor to wait for the main thread ([[12.3 - The Event Model]]).

## What creates a layer

- 3D transforms: `translate3d`, `translateZ`, `rotate3d`, `perspective`
- `will-change: transform`, `will-change: opacity`
- `position: fixed` (in most browsers)
- `<video>`, `<canvas>`, WebGL, plugins
- `backdrop-filter`
- Elements with a running CSS animation on `transform` or `opacity`
- **Overlap**: an element painted above an already-composited layer gets its own layer, so it can be composited in the correct order

That last rule is the source of surprising layer counts. Promoting one element can implicitly promote everything visually above it — the "layer explosion" cascade.

## The cost

Each layer stores a bitmap at device resolution:

```
memory ≈ width × height × devicePixelRatio² × 4 bytes
```

A full-screen layer on a 2× display at 1440×900 is roughly 20 MB. Twenty such layers exhausts GPU memory on a mid-range phone, at which point the browser falls back to slower paths or the tab crashes.

Layers also cost management overhead: the compositor must track, sort and composite each one every frame.

The practical rule: **promote a small number of elements that are actually animating, and unpromote them afterwards.**

```css
/* Reasonable */
.drawer.is-animating { will-change: transform; }

/* Bad */
* { will-change: transform; }
.card { will-change: transform; }   /* 50 cards = 50 layers */
```

`will-change` should be applied shortly before the animation and removed after — in practice, adding it on hover for a click-triggered animation, or toggling a class in JavaScript.

The old `translateZ(0)` / `translate3d(0,0,0)` "hack" does the same thing less explicitly, and should be considered legacy.

## Side effects of promotion

Promotion is not free of semantic consequences:

- It creates a **stacking context**, so z-index ordering changes ([[10.5 - Positioning and Stacking Contexts]]).
- `will-change: transform` creates a **containing block for fixed and absolutely positioned descendants**, which breaks `position: fixed` children — a genuinely hard bug to trace.
- Text rendering can change subtly, since composited layers may use different antialiasing (this is why some elements look slightly different mid-animation).

## Inspecting layers

Chrome DevTools:

- **Layers panel** — a 3D view of every layer with its memory size and, crucially, the **compositing reason** for each. When you cannot explain why something was promoted, this answers it directly.
- **Rendering tab → Layer borders** — orange borders around layers, cyan around tiles.
- **Rendering tab → Paint flashing** — highlights repainted regions in green. During a well-built transform animation, nothing should flash.
- **Rendering tab → Frame rendering stats** — live FPS and GPU memory.

Paint flashing is the fastest diagnostic: if a large region flashes green during what should be a compositor-only animation, something in the subtree is forcing repaint.

## Scrolling and the compositor

Scrolling is compositor-driven by default. Things that force it back onto the main thread:

- **Non-passive `touchstart`/`touchmove`/`wheel` listeners.** The compositor must wait to see whether you call `preventDefault()`. Mark them `{ passive: true }`.
- **`background-attachment: fixed`**, which requires repainting the background on every scroll frame.
- **Complex `box-shadow` or `filter`** on scrolled content, requiring repaint.
- **`position: sticky` in some configurations**, though modern browsers handle most sticky cases on the compositor.

DevTools' Performance panel labels main-thread scrolling explicitly, and the Rendering tab has a "Scrolling performance issues" overlay that highlights the responsible elements.

## Canvas and GPU work

`<canvas>` is its own layer. Two considerations:

**Resolution.** A canvas has a CSS size and a bitmap size, and they must be reconciled for the device pixel ratio or output looks blurry:

```js
const dpr = window.devicePixelRatio;
canvas.width = cssWidth * dpr;
canvas.height = cssHeight * dpr;
canvas.style.width = cssWidth + "px";
ctx.scale(dpr, dpr);
```

**OffscreenCanvas** moves rendering to a worker entirely, so canvas drawing does not compete with the main thread:

```js
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);
```

This is a transfer, not a copy ([[08.4 - Web Workers]]), and is the right architecture for data-heavy visualizations.

## Practical guidance

**Animate `transform` and `opacity`.** Everything else needs a reason.

**Promote only what animates, temporarily.**

**Keep layer count in the single digits** for typical pages. Check the Layers panel if unsure.

**Mark scroll and touch listeners passive.**

**Avoid `backdrop-filter` on large or frequently-updating regions.** It is expensive — the browser must sample and blur everything behind the element on each frame.

**Test on a real mid-range device.** GPU memory pressure and thermal throttling are invisible on a development laptop, and layer explosion manifests very differently on a phone.

## How senior engineers actually use this

**They check the Layers panel's compositing reason** rather than guessing why something was promoted.

**They use paint flashing as the first diagnostic** for a heavy animation — it takes five seconds and immediately distinguishes compositor-only from repainting.

**They treat `will-change` as a temporary hint**, applied and removed around specific interactions.

**They keep animations off the main thread by construction** — CSS animations and the Web Animations API stay composited; `requestAnimationFrame` loops setting styles do not.

**They know the fixed-position interaction**, because "the modal is positioned wrong inside an animated container" is otherwise unexplainable.

## Common pitfalls

- `will-change` applied globally or permanently.
- Layer explosion from the overlap rule, promoting far more than intended.
- `position: fixed` breaking because an ancestor was promoted.
- Non-passive scroll listeners defeating compositor scrolling.
- `background-attachment: fixed` on a long page.
- Blurry canvas from ignoring `devicePixelRatio`.
- Assuming GPU acceleration is universally faster — layer memory is a real and finite budget.

## Interview angle

This comes up as "why are `transform` and `opacity` the properties you should animate" and "what does `will-change` do". The complete answer covers the compositor thread running independently of the main thread, layers costing GPU memory proportional to their pixel area, and `will-change` being a temporary hint with stacking-context and containing-block side effects. Mentioning that promotion cascades through the overlap rule, and that non-passive listeners move scrolling back to the main thread, demonstrates you have debugged this rather than read about it.
