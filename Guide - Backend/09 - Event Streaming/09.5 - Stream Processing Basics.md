# Stream Processing Basics

#backend #streaming #architecture

> **In one line:** Processing an unbounded stream means deciding what "now" is, what to do about records that arrive late, and where to keep the state you accumulate — and most systems do not need a framework to do it.

---

## The Idea

```
Batch:   a bounded dataset. Run, produce a result, finish
Stream:  an unbounded sequence. Never finishes. Results are always provisional
```

💡 **The fundamental difference is that a stream has no end, so you can never know you have seen everything.** Every aggregate is a statement about what you have seen so far, and a late record can change an answer you already emitted.

That single fact generates every concept in this note.

---

## Stateless Operations

The easy half. No memory between records.

```python
async for msg in consumer:
    event = decode(msg)
    if event["type"] != "document.indexed":       # filter
        continue
    enriched = {**event, "org_name": lookup(event["org_id"])}   # map
    await producer.send("enriched", enriched)
    await consumer.commit()
```

| Operation | |
|---|---|
| Filter | Drop records not matching a predicate |
| Map | Transform each record |
| Flat-map | One record in, zero or many out |
| Route | Send to different topics by content |

⚠️ **Enrichment via a lookup is stateless in the streaming sense and stateful operationally** — it is a network call per record, which is an N+1 problem at stream scale ([[05.6 - The N+1 Problem and DataLoader]]).

💡 **Cache the lookup, or better, make the reference data a compacted topic you consume into local state** ([[09.1 - Queue vs Log]]). That turns a per-record network call into a local dictionary read.

**Stateless processing needs no framework.** A consumer loop with idempotent output is sufficient and it is what you should start with.

## Windows

The moment you aggregate, you must define a boundary.

```
Tumbling:   [0-5m][5-10m][10-15m]          non-overlapping, fixed
Hopping:    [0-5m]                          overlapping
              [1-6m]
                [2-7m]
Session:    [.. gap ..][.. gap ..]          bounded by inactivity
```

| Window | Use for |
|---|---|
| **Tumbling** | "Documents indexed per hour". The common case |
| **Hopping** | "Rate over the last 5 minutes, updated every minute" |
| **Session** | "One user's activity burst", with a gap timeout |

```python
def window_start(ts: datetime, size: timedelta) -> datetime:
    epoch_seconds = int(ts.timestamp())
    size_seconds = int(size.total_seconds())
    return datetime.fromtimestamp((epoch_seconds // size_seconds) * size_seconds, tz=UTC)
```

💡 **Tumbling windows are just integer division on a timestamp**, and implementing them by hand is a few lines. **Do not reach for a framework to compute hourly counts.**

## Event Time versus Processing Time

The distinction that causes the most confusion, and the most bugs.

```
Event time:       when the thing actually happened      (in the payload)
Ingestion time:   when it reached the broker
Processing time:  when your code saw it
```

```
Event occurred at 14:59:58
Network delay, retry, consumer lag
Processed at 15:00:07
```

⚠️ **Windowing by processing time puts that record in the 15:00 window, which is wrong.** Every aggregate computed by processing time is a lie about when things happened, and it changes if you replay.

💡 **Always window by event time.** It is the only definition that produces the same answer on a replay, which is what makes results reproducible ([[09.7 - Replay Backfill and Reprocessing]]).

```python
window = window_start(event["occurred_at"], timedelta(hours=1))
```

⚠️ **This requires `occurred_at` in your event envelope** ([[09.2 - Event Modeling]]), and it requires it to be the time the thing happened rather than the time it was published.

### When do you close a window?

If you window by event time, you cannot know when the 14:00–15:00 window is complete — a record from 14:59 might arrive at 15:30.

**Three answers:**

| Approach | |
|---|---|
| **Wait a fixed grace period** | Close at 15:05, accept losing anything later |
| **Watermarks** | Track "we believe we have seen everything up to time T" |
| **Never close** | Keep updating and re-emitting. Correct, expensive |

```python
# Watermark: the minimum event time across partitions, minus a slack
watermark = min(partition_max_event_time.values()) - timedelta(minutes=2)

for window_end, state in list(windows.items()):
    if window_end <= watermark:
        await emit(window_end, state)
        del windows[window_end]
```

💡 **A watermark is a heuristic, not a guarantee.** It says "we are reasonably confident nothing older than T is still coming", and it is wrong sometimes — which is why late records need an explicit policy.

## Late Records

```
Window 14:00–15:00 emitted at 15:05
A record with occurred_at = 14:47 arrives at 15:20
```

| Policy | |
|---|---|
| **Drop** | Simplest. Count them and alert if the rate rises |
| **Update and re-emit** | Correct, and downstream must handle a corrected value |
| **Side output** | Route to a separate topic for reconciliation |
| **Allowed lateness** | Keep the window open for an extra period, then drop |

```python
if event_time < watermark - allowed_lateness:
    late_records_total.labels(topic=t).inc()
    return                                       # drop
```

⚠️ **Dropping silently is the default in most hand-rolled implementations**, and it means your aggregates are quietly wrong during any consumer lag incident.

💡 **Always count dropped late records.** A rising `late_records_total` means your watermark is too aggressive, or a producer is lagging — and it is a signal you would otherwise never see.

**For anything financial or user-visible, "update and re-emit" is the only defensible choice**, and downstream consumers must be able to handle a corrected aggregate.

## State

Aggregation means remembering things between records.

```python
counts: dict[tuple[str, datetime], int] = defaultdict(int)

async for msg in consumer:
    event = decode(msg)
    key = (event["org_id"], window_start(event["occurred_at"], HOUR))
    counts[key] += 1
```

⚠️ **In-memory state has three problems and all of them are fatal at scale:**

| Problem | |
|---|---|
| **Lost on restart** | Every deploy resets your aggregates |
| **Unbounded growth** | Windows accumulate forever without eviction |
| **Not partition-aware** | A rebalance moves partitions and the state is wrong |

### Where state lives

| Option | |
|---|---|
| **Memory** | Fast, lost on restart. Only with replay from a known offset |
| **Local disk (RocksDB)** | What Kafka Streams and Flink use. Fast, survives restart |
| **External store (Redis, Postgres)** | Shared, survives everything, adds a network hop per record |
| **The output topic itself** | Aggregate is the state; recompute by replay |

💡 **The simplest correct approach for moderate volume: keep state in Postgres with an upsert, and let the database be the state store.**

```python
await conn.execute(
    """INSERT INTO hourly_counts (org_id, window_start, count)
       VALUES ($1, $2, 1)
       ON CONFLICT (org_id, window_start) DO UPDATE SET count = hourly_counts.count + 1""",
    org_id, window,
)
```

⚠️ **This is not idempotent — a replayed record double-counts.** Combine it with offset-storage-in-the-same-transaction ([[09.1 - Queue vs Log]]):

```python
async with conn.transaction():
    await upsert_count(org_id, window)
    await store_offset(msg.topic, msg.partition, msg.offset)
```

**Now the aggregate and the position advance atomically**, and a replay from the stored offset produces the correct result. **That is exactly-once aggregation, in about ten lines, with no framework.**

### The rebalance problem

⚠️ **When partitions move between consumers, any local state for those partitions is now on the wrong node** ([[09.1 - Queue vs Log]]).

| Response | |
|---|---|
| **External state keyed by partition** | Any consumer can read it |
| **Rebuild on assignment** | Replay the partition from a checkpoint |
| **Sticky assignment** | Minimise movement, but does not eliminate it |
| **Framework changelog topics** | Kafka Streams replicates state to a topic and restores it |

💡 **This is the single strongest argument for a stream processing framework.** State migration on rebalance is genuinely hard, and Kafka Streams and Flink solve it properly with changelog topics and checkpointed state.

**If your state is in Postgres keyed by partition, you sidestep it entirely** — which is why the simple approach works better than people expect.

## Joins

### Stream-table join (enrichment)

```
document.indexed  ⋈  organisations (compacted topic → local state)
```

💡 **The clean pattern: consume a compacted topic into a local dictionary, join against it in memory.** No network call per record, and the table stays current because the compacted topic delivers updates.

```python
orgs: dict[str, dict] = {}

async def maintain_org_table():
    async for msg in org_consumer:                # compacted topic, from offset 0
        if msg.value is None:
            orgs.pop(msg.key.decode(), None)      # tombstone
        else:
            orgs[msg.key.decode()] = decode(msg.value)
```

⚠️ **Bootstrapping requires reading the whole compacted topic before processing begins**, which is why startup takes longer. **Do not serve traffic until the table is loaded**, or you enrich with missing data.

### Stream-stream join

```
document.indexed  ⋈  annotation.created   within a 1-hour window
```

⚠️ **Requires buffering both streams for the join window**, which means state proportional to the window size times the throughput.

💡 **Stream-stream joins are where hand-rolling stops being reasonable.** Windowed buffering, out-of-order arrival on both sides, and state cleanup are exactly what frameworks are for.

**If you need a stream-stream join, that is a strong signal to use Flink or Kafka Streams** rather than continuing to build.

## When You Need a Framework

```
Stateless map, filter, route              → a consumer loop
Simple windowed aggregation                → a consumer loop + Postgres
Enrichment from reference data             → a consumer loop + a compacted topic
Complex event-time semantics               → framework
Stream-stream joins                        → framework
Large state with rebalance migration       → framework
Exactly-once across multiple topics        → framework
Very high throughput with low latency      → framework
```

💡 **The honest position: most "stream processing" requirements are a consumer loop, an upsert, and offsets stored transactionally.** Reaching for Flink to compute hourly counts is paying a large operational bill for something Postgres does correctly.

| Framework | |
|---|---|
| **Kafka Streams** | A library, not a cluster. JVM only. Excellent if you are on the JVM |
| **Flink** | A cluster. The most capable, and the heaviest. PyFlink exists and is second-class |
| **Faust / quix-streams** | Python-native. Smaller ecosystems, worth evaluating for Python shops |
| **ksqlDB** | SQL over streams. Good for simple transformations, limited beyond that |

⚠️ **For a Python backend, the framework options are genuinely weaker than on the JVM.** PyFlink works and is not where the investment goes. **That asymmetry is a real input to the decision** — a consumer loop in Python you fully understand beats a PyFlink job you do not.

## In Production

### The consumer-loop pattern that covers most cases

```python
async def process_stream():
    async for msg in consumer:
        event = decode(msg)
        event_time = parse(event["occurred_at"])

        if event_time < watermark() - ALLOWED_LATENESS:
            late_records_total.inc()
            await consumer.commit()
            continue

        window = window_start(event_time, WINDOW_SIZE)

        async with conn.transaction():
            await upsert_aggregate(event["org_id"], window, event)
            await store_offset(msg.topic, msg.partition, msg.offset)

        update_watermark(msg.partition, event_time)
```

💡 **That is event-time windowing with late-record handling and exactly-once aggregation, in about fifteen lines.** It is the right starting point, and the point at which it stops being sufficient is a clear signal.

### Monitoring

```python
stream_records_processed_total.labels(topic=t).inc()
stream_event_time_lag_seconds.set(now - event_time)      # ← how far behind reality
stream_processing_lag_seconds.set(now - ingestion_time)  # ← how far behind the broker
late_records_total.labels(topic=t).inc()
window_state_size.set(len(windows))
watermark_timestamp.set(watermark().timestamp())
```

⚠️ **Two different lags, and confusing them causes misdiagnosis:**

| Lag | Means |
|---|---|
| **Processing lag** | Your consumer is behind the broker. Scale consumers |
| **Event time lag** | The events themselves are old. **The producer is behind, or you are replaying** |

💡 **A high event-time lag with zero processing lag means the producer is the problem, not you.** Without both metrics that is a confusing investigation.

### Reprocessing

```python
await consumer.seek(partition, offset=0)
```

⚠️ **Reprocessing only produces the correct answer if your aggregation is idempotent or the state is reset first.** An upsert that increments double-counts on replay.

💡 **Design aggregates to be recomputable from scratch:**

```
1. Truncate the aggregate table for the affected window range
2. Reset offsets to the start of that range
3. Replay
```

**Test this.** A pipeline you cannot reprocess is a pipeline whose bugs are permanent ([[09.7 - Replay Backfill and Reprocessing]]).

### Conduit's stream processing

| Requirement | Approach |
|---|---|
| Documents indexed per org per hour | **Consumer loop + Postgres upsert + transactional offsets** |
| Enrich events with org name | **Compacted topic → local dictionary** |
| Search index maintenance | CDC → idempotent upsert. **Not aggregation** |
| Ingestion throughput dashboard | Consumer loop + time-bucketed counts |
| Per-user activity sessions | **Deferred** — this is a session window and needs real machinery |

💡 **Four out of five need no framework**, and the fifth is deferred until there is a reason to build it. **That distribution is what a proportionate architecture looks like**, and being able to defend "we did not add Flink" with the specific requirements is the senior version of this decision.

## Codebase

**Repo:** `apache/kafka` (Streams), `apache/flink`, `quixio/quix-streams`

**Question to answer:** In Kafka Streams, how is state stored locally and restored after a rebalance? Then: how does Flink's watermark propagation work across parallel operators?

**Read, in order:**

1. `kafka/streams/src/main/java/org/apache/kafka/streams/state/internals/RocksDBStore.java` — **local state on disk**
2. `kafka/streams/src/main/java/org/apache/kafka/streams/processor/internals/StoreChangelogReader.java` — **state restoration from a changelog topic.** This is the answer to the first question, and it is the mechanism that makes rebalancing survivable
3. `kafka/streams/src/main/java/org/apache/kafka/streams/kstream/internals/KStreamWindowAggregate.java` — windowed aggregation, including the late-record handling
4. `flink/flink-streaming-java/src/main/java/org/apache/flink/streaming/runtime/watermarkstatus/` — **watermark propagation.** How the minimum watermark across inputs flows through a parallel graph. **The answer to the second question**
5. `quixio/quix-streams` — a Python-native library. **Read the windowing and state modules** to see what the Python ecosystem offers

💡 The changelog restoration mechanism in Kafka Streams is the idea worth understanding: **every local state store is backed by a compacted Kafka topic, so state is durable and can be rebuilt on any node.** It is the same "the log is the source of truth" insight as CDC ([[09.4 - Change Data Capture]]), applied to processor state.

**Part 1 — Enrichment, two ways.** Events needing an organisation name.

Version A: a lookup per record. Version B: a compacted topic consumed into a local dictionary.

Measure at 10,000 events/second: throughput, latency per record, and load on the source of the reference data.

**Then update an organisation name and measure how long until each version reflects it.**

**Part 2 — Event time versus processing time.** Produce events with `occurred_at` deliberately skewed — some 5 minutes old, some 30 seconds old.

Compute hourly counts by both definitions. **Compare the results.**

Then **replay the same input** and confirm the event-time version produces identical output while the processing-time version does not.

**That reproducibility is the argument**, and having produced the difference yourself makes it stick.

**Part 3 — Watermarks and late records.** Implement a watermark as the minimum event time across partitions minus a slack.

Then inject records that arrive after their window closed: 1% at 2 minutes late, 0.1% at 30 minutes late.

Implement all four policies. For each measure: aggregate accuracy, records dropped, and downstream complexity of handling corrections.

**Then simulate consumer lag** — stop the consumer for 20 minutes — and measure how many records become "late" purely because of the lag. **This is the scenario where a silent drop policy quietly corrupts your data.**

**Part 4 — State, three ways.** Hourly aggregation with state in memory, in Postgres non-transactionally, and in Postgres with offsets in the same transaction.

For each: restart the consumer mid-stream and **verify the final aggregate against a batch computation over the same input.**

**Only the third should be correct.**

Then force a rebalance by adding a consumer, and confirm which versions produce wrong results.

**Part 5 — Reprocessing.** Reset offsets to zero and replay the entire stream.

For each state approach, **verify the result matches a fresh batch computation.**

Then implement the truncate-and-replay procedure and confirm it produces a correct result even for the non-idempotent version.

**Part 6 — Two lags, distinguished.** Instrument both processing lag and event-time lag.

Then create two situations: a slow consumer, and a producer publishing events with old timestamps.

**Confirm your metrics distinguish them**, and write the runbook entry for each.

**Part 7 — Framework comparison.** Implement the same hourly aggregation with quix-streams or PyFlink.

Compare: lines of code, correctness guarantees out of the box, rebalance behaviour, operational components, and startup time.

**Then write the ADR for Conduit**, naming the specific requirement that would justify a framework.

**Done when:**
- Compacted-topic enrichment measurably outperforms per-record lookup
- Event-time windowing reproduces on replay and processing-time does not
- You measured how consumer lag turns normal records into late ones
- Only transactional offset storage produced correct aggregates across restarts and rebalances
- Truncate-and-replay produces a batch-verified correct result
- Your two lag metrics distinguish a slow consumer from a lagging producer
- The ADR names the requirement that would justify a framework
