# External Services and Declarative Integration

## The idea

Point Salesforce at an **OpenAPI specification**, and it generates invocable actions for each operation. Those actions appear in Flow Builder, in Agentforce, and callable from Apex — with no callout code written.

The external system's API becomes a set of drag-and-drop actions.

## Setting it up

```
Setup → External Services → Add an External Service

Service Name:         ErpInventory
Named Credential:     ERP_System
Service Schema:       Upload from local, or provide a URL
```

The schema is an OpenAPI 2.0 or 3.0 document:

```yaml
openapi: 3.0.0
info:
  title: ERP Inventory Service
  version: 2.0.0
paths:
  /api/v2/inventory/{serialNumber}:
    get:
      operationId: getInventory
      parameters:
        - name: serialNumber
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: Inventory levels
          content:
            application/json:
              schema:
                type: object
                properties:
                  available: { type: integer }
                  warehouse: { type: string }
                  leadTimeDays: { type: integer }
  /api/v2/parts/reserve:
    post:
      operationId: reserveParts
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              properties:
                partCode: { type: string }
                quantity: { type: integer }
                claimNumber: { type: string }
      responses:
        '201':
          description: Reservation created
          content:
            application/json:
              schema:
                type: object
                properties:
                  reservationId: { type: string }
                  expiresAt: { type: string, format: date-time }
```

Salesforce registers `getInventory` and `reserveParts` as invocable actions.

**`operationId` becomes the action name**, so a specification with unhelpful operation Ids produces unhelpful actions. This is worth raising with the API owner before importing.

## Using it in a flow

```
Screen Flow: Log Warranty Claim

  Screen: capture the serial number
  Action: getInventory
      serialNumber = {!enteredSerial}
      → {!inventoryResult}

  Decision: parts available?
      {!inventoryResult.available} > 0  → continue
      otherwise                          → screen explaining the lead time

  Action: reserveParts
      partCode    = {!selectedPart}
      quantity    = {!requiredQuantity}
      claimNumber = {!claimRecord.Claim_Number__c}
      → {!reservation}

  Update Records: store the reservation Id on the claim
```

No Apex. An administrator builds this, and adding a new operation to the flow is a matter of the API owner publishing an updated specification.

Authentication comes entirely from the Named Credential, so no secret appears anywhere in the flow. See [[13.13 - Named Credentials and External Credentials]].

## Calling from Apex

The generated actions are callable from Apex, which is occasionally useful when the schema handling is the valuable part:

```java
public with sharing class InventoryService {

    public static Integer available(String serialNumber) {
        ExternalService.ErpInventory service = new ExternalService.ErpInventory();

        ExternalService.ErpInventory.getInventory_Request request =
            new ExternalService.ErpInventory.getInventory_Request();
        request.serialNumber = serialNumber;

        ExternalService.ErpInventory.getInventory_Response response =
            service.getInventory(request);

        return response.Code200?.available;
    }
}
```

The generated classes are verbose and their names are derived mechanically from the specification. For Apex, a hand-written client is usually cleaner — the value of External Services is the **declarative** surface, not the Apex one. See [[13.14 - Apex Callouts]].

## Where it genuinely helps

**Admin-owned integration.** An administrator adds an external lookup to a flow without a developer and without a release.

**Agentforce actions.** An agent can call an external API directly, with the schema describing what each operation does. This is increasingly the main use — the OpenAPI descriptions become the tool descriptions the model reads. See [[05.15 - Einstein for Service and Agentforce]].

**Rapid prototyping.** Wiring up an external API to a screen flow in twenty minutes to prove a concept.

**Well-specified partner APIs.** Where the external team maintains a good OpenAPI document, importing it is faster than writing a client.

## Where it does not

Being honest about the limitations, because they are substantial.

**Schema support is incomplete.** Deeply nested objects, `oneOf`/`anyOf`, polymorphic responses, and some array structures either fail to import or import in a shape that is awkward to use. A specification that works elsewhere may not import cleanly.

**Error handling is coarse.** A non-200 response surfaces as a flow fault. Distinguishing a 404 from a 500 from a timeout, and reacting differently, is difficult. Anything needing retry logic or nuanced failure handling belongs in Apex.

**No control over the request.** Custom headers, request signing, conditional logic before the call — none of it is available beyond what the Named Credential provides.

**Regeneration on schema change.** When the external team publishes a new version, the service must be re-imported, and existing flows may break if operation names or response shapes changed.

**Bulk is awkward.** One action call per flow execution, so a record-triggered flow calling an external service on 200 records makes 200 calls — against the 100-callout limit. This is the flow bulkification problem from [[07.10 - Flow Limits and Performance]] applied to integration, and it is a hard ceiling.

That last point is the one that most often forces a rewrite: an External Services action works in a screen flow and fails in a record-triggered flow at volume.

## The decision

| Situation | Approach |
| --- | --- |
| Screen flow, one call, admin-owned | External Services |
| Agentforce action against an external API | External Services |
| Prototype or proof of concept | External Services |
| Record-triggered flow, bulk context | Invocable Apex |
| Retry, backoff, error classification needed | Apex |
| Custom headers or request signing | Apex |
| Complex or nested response schema | Apex |
| High volume | Apex, async |

The pattern that gets both: **an invocable Apex action wrapping a hand-written client**, exposed to flow. The administrator gets a drag-and-drop action; the developer keeps control of bulk behaviour, error handling, and retries.

```java
public with sharing class InventoryActions {

    public class Request {
        @InvocableVariable(required=true label='Serial Number') public String serialNumber;
    }

    public class Result {
        @InvocableVariable public Integer available;
        @InvocableVariable public String warehouse;
        @InvocableVariable public Boolean lookupSucceeded;
    }

    @InvocableMethod(label='Check Part Availability'
                     description='Returns current inventory for a machine serial number')
    public static List<Result> check(List<Request> requests) {
        List<Result> results = new List<Result>();

        // one callout for the whole batch, which an External Services action cannot do
        Map<String, InventoryDto> byserial = ErpClient.lookupInventoryBatch(
            collectSerials(requests)
        );

        for (Request req : requests) {
            Result result = new Result();
            InventoryDto dto = bySerial.get(req.serialNumber);
            result.lookupSucceeded = dto != null;
            if (dto != null) {
                result.available = dto.available;
                result.warehouse = dto.warehouse;
            }
            results.add(result);
        }
        return results;
    }
}
```

The invocable method receives all requests in one list and makes **one** callout. That is the capability External Services cannot provide, and it is why this wrapper is the standard answer for anything bulk. See [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Testing

External Services actions can be tested with a standard callout mock, since they use the Named Credential and the HTTP stack underneath:

```java
@IsTest
static void inventoryLookupReturnsAvailability() {
    Test.setMock(HttpCalloutMock.class,
        new ErpSuccessMock(200, '{"available":12,"warehouse":"Pune","leadTimeDays":3}'));

    Test.startTest();
    Integer available = InventoryService.available('SN-88213');
    Test.stopTest();

    Assert.areEqual(12, available);
}
```

Testing a **flow** that uses the action is harder — flow tests are limited and cannot easily mock the callout. This is another reason to prefer an invocable Apex wrapper for anything whose correctness matters. See [[19.9 - Flow Testing]].

## Practical guidance

**Use External Services for screen flows, Agentforce actions, and prototypes.**

**Do not use it in record-triggered flows.** One callout per record is a hard ceiling.

**Wrap in invocable Apex** when bulk behaviour, retries, or error classification matter.

**Check the specification imports cleanly** before designing around it — schema support is incomplete.

**Ask the API owner for meaningful `operationId` values**, since they become the action names.

**Expect to re-import** when the external specification changes, and check existing flows afterwards.

**Publish an OpenAPI spec for your own Apex REST endpoints**, so consumers can use External Services against them. See [[13.15 - Building Apex REST and SOAP Services]].
