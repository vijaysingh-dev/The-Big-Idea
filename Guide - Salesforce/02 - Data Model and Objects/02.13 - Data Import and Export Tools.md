# Data Import and Export Tools

## The tools, and when each is right

| Tool | Volume | Interface | Best for |
| --- | --- | --- | --- |
| Data Import Wizard | Up to 50,000 | Browser | Admins, simple imports, duplicate matching |
| Data Loader | Up to 5 million | Desktop app or CLI | Developers, all objects, scripting |
| Salesforce CLI (`sf data`) | Moderate | Command line | Scripted seeding, CI pipelines |
| Bulk API 2.0 | Millions | API | Integrations, large migrations |
| SOQL export | Any | Various | Extracting data |

The distinction that matters most is between the **REST/SOAP path** (Data Import Wizard, Data Loader in its default mode) and the **Bulk API path**. The first processes records in small synchronous batches; the second queues an asynchronous job that Salesforce processes in parallel. The second is dramatically faster at volume and behaves differently around limits and locking.

## Data Import Wizard

In Setup, browser-based, no installation. Handles Accounts, Contacts, Leads, Campaign Members, Person Accounts, and custom objects.

Its distinguishing feature is **duplicate matching**: it can match on name and email, or on an external ID, and update rather than create. For an admin importing a list of leads from an event, this is the right tool.

Its limits are real: 50,000 records, no delete, no support for all objects, and no scripting. It is not a migration tool.

## Data Loader

The workhorse. A desktop application, also runnable from the command line, supporting every object and all operations: insert, update, upsert, delete, hard delete, and export.

The operations, precisely:

- **Insert** — creates new records, ignores any Id column
- **Update** — requires Id, fails on records that do not exist
- **Upsert** — matches on an external ID, updating matches and creating the rest
- **Delete** — moves to the recycle bin
- **Hard delete** — bypasses the recycle bin, requires a specific permission
- **Export** — SOQL results to CSV, excluding deleted records
- **Export All** — includes deleted and archived records

**Upsert is the operation that matters for integrations.** Matching on an external ID means the same file can be loaded twice without creating duplicates, which makes a failed load safe to rerun. This is idempotency, and it is the foundation of reliable data loading.

Command-line mode is what makes Data Loader useful in a pipeline. Configuration lives in `process-conf.xml`, and the job runs unattended:

```bash
./process.sh ./config upsertMachines
```

## Salesforce CLI

For developers, the CLI is usually the fastest path for small and moderate loads, and it is what belongs in scratch org setup scripts.

```bash
# Bulk upsert from CSV, matching on an external id
sf data upsert bulk \
  --sobject Machine__c \
  --file data/machines.csv \
  --external-id ERP_Machine_Id__c \
  --wait 10 \
  --target-org my-sandbox

# Export a query to CSV
sf data query \
  --query "SELECT Id, Name, Serial_Number__c FROM Machine__c WHERE Status__c = 'Active'" \
  --result-format csv \
  --target-org my-sandbox > machines.csv

# Import a related record tree, preserving relationships between objects
sf data import tree --plan data/sample-data-plan.json --target-org scratch-org
```

`data import tree` is worth knowing: it loads a set of related records from JSON, resolving relationships by reference rather than by ID, which is exactly what you need to seed a scratch org with a coherent sample dataset. See [[21.11 - Sandbox Strategy and Data Seeding]].

## Bulk API

For anything above a few hundred thousand records. Records are submitted as a job, split into batches, and processed asynchronously in parallel. Covered fully in [[13.4 - Bulk API 2.0]].

Two modes matter here:

**Parallel** is the default and is fast. It is also where lock contention appears, because multiple batches touching children of the same parent will collide.

**Serial** processes batches one at a time. Slower, and the fix when parallel mode produces `UNABLE_TO_LOCK_ROW` errors.

## Load ordering, which is where migrations fail

Records must be loaded in dependency order, and the ordering is not always obvious.

For our manufacturing model:

1. Accounts
2. Contacts, referencing accounts
3. Product2, then PricebookEntry (standard price book first, then any custom ones)
4. Machines, referencing accounts and products
5. Service Contracts, referencing accounts
6. Machine Coverage junction records, referencing both
7. Cases, referencing accounts, contacts, machines
8. Claim Parts, referencing cases and products

The general rules: parents before children, lookups before the records that reference them, and users before anything that references an owner.

The problem this creates: your CSV has the legacy system's identifiers, not Salesforce IDs. Two solutions.

**External IDs.** Load parents with their external ID populated, then reference the parent by external ID in the child file using the `Parent__r.External_Id__c` column syntax. Data Loader and the Bulk API both resolve this.

```
Name,Serial_Number__c,Account__r.ERP_Account_Id__c,ERP_Machine_Id__c
Press Line 3,SN-88213,ACC-4471,MCH-99201
```

No lookup pass, no ID mapping file. This is by far the cleanest approach and is the main practical reason to define external IDs before migration rather than after.

**ID mapping.** Load parents, export the resulting Id alongside the legacy key, then join that mapping into the child file before loading. Necessary when external IDs were not planned, and it is exactly as tedious as it sounds.

## Preparing for a large load

Things that experienced people do before a big migration, roughly in order of impact:

**Disable what does not need to run.** Validation rules, workflow, flows, and triggers all execute on every loaded record. Deactivating non-essential automation for the load window can cut hours off the runtime. This must be deliberate and reversible, and anything skipped must be reconciled afterwards.

**Defer sharing calculation.** Setup has an option to suspend sharing rule recalculation during a load, then run it once at the end rather than continuously. On a large load into a private object this is often the single biggest speedup.

**Sort by parent.** Grouping child records by their parent ID means each batch touches a small set of parents, which dramatically reduces lock contention.

**Turn off field history tracking temporarily** where it is not needed for the migrated data. History rows are written for every tracked field on every record.

**Load into a Full sandbox first and time it.** A migration that takes three hours in a sandbox will not take twenty minutes in production.

See [[23.5 - Bulk Data Loading at Scale]] for the full treatment.

## Errors, and reading them

Both Data Loader and the Bulk API produce a success file and an error file. The error file contains the original row plus the error message, which means the standard recovery loop is: fix the error file, reload just that file, repeat.

Errors you will meet constantly:

- `REQUIRED_FIELD_MISSING` — a field required at field level, not just on the layout
- `INVALID_CROSS_REFERENCE_KEY` — a lookup pointing at an ID that does not exist, usually a load ordering problem
- `DUPLICATE_VALUE` — a unique field or external ID collision
- `FIELD_CUSTOM_VALIDATION_EXCEPTION` — a validation rule rejected the row
- `UNABLE_TO_LOCK_ROW` — concurrent access to the same parent; sort by parent or switch to serial mode
- `CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY` — a trigger threw an exception, and the message usually names the class

Keeping every error file from a migration is worth doing. Reconciliation at the end is counting what went in against what was in the source, and the error files are half of that arithmetic.

## Exporting

For extraction, options in increasing capability: a report exported to CSV for small ad hoc needs, Data Loader export for anything structured, `sf data query` for scripted extracts, and the Bulk API query for millions of rows.

Salesforce also offers a **weekly data export** in Setup, producing a full CSV backup delivered as a zip. Worth knowing it exists, and worth knowing it is not a backup strategy — it has no incremental option, no point-in-time restore, and restoring from it means a full reload with all the ordering problems above. Orgs with real recovery requirements use a dedicated backup product.
