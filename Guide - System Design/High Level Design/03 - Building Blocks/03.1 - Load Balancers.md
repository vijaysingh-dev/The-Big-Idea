# Load Balancers

> **Revision tags:** #building-blocks #networking  
> **Related:** [[03.2 - Reverse Proxies and API Gateways]] | [[02.4 - Architecture Decisions]]

---

## What It Is

A load balancer distributes incoming requests across multiple backend servers so that no single server becomes a bottleneck or single point of failure.

```
Clients
  │  │  │
  ▼  ▼  ▼
[Load Balancer]
  ├──→ [Server A]
  ├──→ [Server B]
  └──→ [Server C]
```

---

## Why It Exists

- **Scalability:** One server can only handle so much traffic. A load balancer lets you add more servers to increase capacity.
- **High availability:** If one server dies, the load balancer stops sending it traffic. The system stays up.
- **No single point of failure:** Without a LB, every client must know server addresses directly — one server failure breaks some clients.

---

## L4 vs L7 Load Balancing

### Layer 4 (Transport Layer)

Operates on TCP/UDP packets. Doesn't look at the content of the request.

```
Decision based on: source IP, destination IP, port
Routing: forward TCP stream to a backend
```

**Pros:** Very fast (no parsing), handles any protocol  
**Cons:** Can't route based on request content (path, headers, cookies)  
**Examples:** AWS NLB, HAProxy (TCP mode), hardware LBs

### Layer 7 (Application Layer)

Operates on HTTP/HTTPS. Reads request content to make routing decisions.

```
Decision based on: URL path, headers, cookies, request body
Routing: terminate TLS, parse HTTP, route based on content
```

**Pros:** Smart routing (route /api → API servers, /static → CDN), SSL termination, session stickiness  
**Cons:** Slightly more overhead (must parse HTTP)  
**Examples:** AWS ALB, Nginx, HAProxy (HTTP mode), Envoy

**In practice:** L7 load balancers are the default for web applications. L4 is used for non-HTTP protocols or when you need extreme throughput with minimal overhead.

## Load Balancing Algorithms

### Round Robin

Requests are distributed sequentially across servers.

```
Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
Request 4 → Server A (wraps around)
```

**Pros:** Simple, even distribution  
**Cons:** Doesn't account for server load or request weight. A heavy request to Server A and a light request to Server B get equal "slots."

**Weighted Round Robin:** Assign weights — Server A (weight 3) gets 3× the requests of Server B (weight 1). Used when servers have different capacities.

### Least Connections

Route new requests to the server with the fewest active connections.

```
Server A: 10 active connections
Server B: 4 active connections  ← next request goes here
Server C: 7 active connections
```

**Pros:** Better for long-lived connections (WebSockets, file uploads) where servers may become unevenly loaded  
**Cons:** Slightly more overhead — must track connection counts

### IP Hash

Hash the client's IP address to determine which server handles it.

```
hash(client_ip) % num_servers = server_index
```

**Pros:** Same client always hits the same server (sticky sessions without cookies)  
**Cons:** Uneven if certain IPs generate more traffic; breaks if server count changes

### Least Response Time

Route to the server with the lowest combination of active connections and response time.

Most sophisticated. Used when servers have varying performance characteristics.

### Random

Pick a server randomly. Works surprisingly well with many servers due to the law of large numbers.

## Health Checks

The load balancer must know which backends are healthy.

**Passive health checks:** Observe responses. If a backend returns 5xx or times out too often, mark it unhealthy. Low overhead but slow to detect failures.

**Active health checks:** LB periodically sends probe requests to each backend.

```
Every 10 seconds:
  GET http://server-a:8080/health → 200 OK → healthy
  GET http://server-b:8080/health → timeout → unhealthy → stop sending traffic
```

**What `/health` should check:**
- Is the process running? (trivial)
- Can it reach the database? (meaningful)
- Is the job queue backed up beyond threshold? (advanced)

A `/health` that always returns 200 is useless. A `/health` that checks real dependencies is valuable.

---

## Sticky Sessions (Session Affinity)

Routes requests from the same client to the same backend — needed when the application stores state in memory on the server.

**Cookie-based stickiness:** LB inserts a cookie identifying which server handled the first request. Subsequent requests with that cookie go to the same server.

**Problem with stickiness:**
- If Server A goes down, all sticky sessions to A are disrupted
- Defeats the purpose of horizontal scaling for stateful apps
- Causes uneven load distribution

**Better solution:** Make your app stateless. Store session state in Redis, not in-process memory. Then any server can handle any request.

---

## SSL Termination

The load balancer handles TLS encryption/decryption. Backends communicate over plain HTTP internally.

```
Client ──HTTPS──→ Load Balancer ──HTTP──→ Backend Servers
         (TLS)    (terminates TLS)         (unencrypted, internal network)
```

**Pros:** Backends are simpler (no TLS handling), LB can inspect HTTP headers  
**Cons:** Traffic between LB and backends is unencrypted (acceptable within trusted VPC; use mTLS if not)

---

## The Load Balancer as a SPOF

If you have one load balancer, it becomes the single point of failure.

**Solutions:**
- **Active-passive pair:** Primary LB serves all traffic; standby takes over if primary fails (via VIP/floating IP and health checks)
- **Active-active pair:** Both LBs serve traffic; DNS load balancing between them
- **Managed LBs (cloud):** AWS ALB/NLB are managed services — Amazon handles redundancy. This is why cloud-managed LBs are preferred.

---

## Failure Modes

| Failure | Effect | Mitigation |
|---|---|---|
| Backend crashes | Traffic still sent to crashed server | Active health checks, auto-remove |
| LB crashes | All traffic lost | Active-passive pair, managed LB |
| Health check too slow | Slow detection of backend failure | Short check intervals, low threshold |
| Sticky session server down | Session lost | Stateless apps + shared session store |
| Overloaded LB itself | Becomes bottleneck | DNS round-robin across multiple LBs |

## Interview Expectations

- Know L4 vs L7 and when to use each
- Know at least 3 algorithms and their tradeoffs
- Know why sticky sessions are a code smell
- Know how health checks work
- Mention that cloud LBs (ALB/NLB) handle redundancy — don't need to design HA for the LB itself in most cases

---

## Real Production Examples

- **AWS ALB:** L7, path-based routing, WebSocket support, integrated with WAF
- **AWS NLB:** L4, ultra-low latency, static IP, TCP/UDP pass-through
- **Nginx:** Open-source, used both as reverse proxy and L7 LB
- **HAProxy:** Battle-tested, fine-grained control, used in many high-traffic sites
- **Envoy:** Modern, L7, service mesh sidecar proxy (used in Istio)
