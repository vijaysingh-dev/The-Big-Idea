# Authentication and OAuth Flows

## The question every flow answers

**Who is asking, and how do we know?**

OAuth 2.0 issues an **access token** that carries identity and scope. Every API call in this section presents one. The flows differ in how the token is obtained, and the right flow depends on one thing: **is a human present, and can the client keep a secret?**

## The decision

| Situation | Flow |
| --- | --- |
| Server-to-server, no human | **JWT Bearer** |
| A user authorizes a web app | **Web Server** (authorization code with PKCE) |
| A mobile or single-page app | **Web Server with PKCE** |
| Machine-to-machine with client credentials | **Client Credentials** |
| A device with no browser | **Device Flow** |
| Salesforce calling out on a user's behalf | **Named Credential** with a per-user auth provider |
| A user is already logged into Salesforce | **Session Id**, only in-org |

**JWT Bearer is the default for integrations.** No stored password, no interactive login, no refresh token to expire. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

## What is retired

Two flows appear constantly in older documentation and should not be used.

**Username-Password flow.** Sends a username, password, and security token to get a token directly. It stores a password, the security token silently changes on every password reset, and Salesforce now blocks it by default in new orgs.

```
POST /services/oauth2/token
grant_type=password&client_id=...&client_secret=...&username=...&password=passwordTOKEN
```

If you find this in an inherited integration, migrating it to JWT is the single highest-value security change available — it removes a stored credential entirely.

**Implicit flow.** Returned a token directly in a browser redirect fragment. Superseded by the authorization code flow with PKCE.

## Web Server flow

The standard flow when a user authorizes an application.

**Step 1: redirect the user to authorize**

```
GET https://login.salesforce.com/services/oauth2/authorize
  ?response_type=code
  &client_id={consumer_key}
  &redirect_uri=https://app.example.com/callback
  &scope=api refresh_token
  &state={csrf_token}
  &code_challenge={base64url(sha256(verifier))}
  &code_challenge_method=S256
```

**Step 2: exchange the code for tokens**

```
POST https://login.salesforce.com/services/oauth2/token

grant_type=authorization_code
&code={authorization_code}
&client_id={consumer_key}
&client_secret={consumer_secret}
&redirect_uri=https://app.example.com/callback
&code_verifier={original_verifier}
```

```json
{
  "access_token": "00D5g...!AQ...",
  "refresh_token": "5Aep8...",
  "instance_url": "https://myorg.my.salesforce.com",
  "id": "https://login.salesforce.com/id/00D5g.../0055g...",
  "token_type": "Bearer",
  "issued_at": "1754553600000",
  "signature": "..."
}
```

**PKCE** — the `code_challenge` and `code_verifier` pair — prevents an intercepted authorization code being exchanged by an attacker. It was originally for mobile apps and is now recommended for every client, including confidential ones.

**`state`** is a CSRF token you generate and verify on return. Omitting it leaves the callback open to forgery.

**`instance_url`** from the response is the base for all subsequent API calls. Hardcoding a pod-specific URL breaks when the org migrates instances; always use the returned value.

## Refresh tokens

An access token expires; a refresh token obtains a new one without user interaction.

```
POST /services/oauth2/token

grant_type=refresh_token
&refresh_token={refresh_token}
&client_id={consumer_key}
&client_secret={consumer_secret}
```

The refresh token's lifetime is set by the connected app's **refresh token policy**:

```
Refresh token is valid until revoked            the usual choice for integrations
Immediately expire refresh token
Expire refresh token if not used for [n] days
Expire refresh token after [n] hours
```

**Getting this wrong is a classic failure mode**: an integration works for ninety days and then stops, because the policy expires unused refresh tokens and a quiet period exceeded the window.

For server-to-server integration, JWT avoids the whole issue — there is no refresh token to expire.

## Client Credentials flow

Machine-to-machine, without JWT's certificate handling:

```
POST /services/oauth2/token

grant_type=client_credentials
&client_id={consumer_key}
&client_secret={consumer_secret}
```

The connected app is configured with a **run-as user**, and the token carries that user's permissions.

Simpler than JWT — no certificate, no signed assertion — and it stores a client secret where JWT stores a private key. Both need protecting; the practical difference is that a JWT private key never travels over the wire, while a client secret does on every token request.

Reasonable when the client platform makes JWT signing awkward. JWT is still the stronger choice where it is available.

## Scopes

What the token is allowed to do:

```
api                  REST, SOAP, Bulk — the core data APIs
refresh_token        issue a refresh token
offline_access       same as refresh_token
web                  access the web UI with the token
full                 everything the user can do — avoid
openid               OpenID Connect identity
profile / email      identity claims
chatter_api          Connect API
custom_permissions   include custom permissions in the identity response
lightning            Lightning app access
content              Files and content
```

**Do not grant `full`.** An integration reading accounts and writing cases needs `api` and `refresh_token`. Granting `full` gives it everything the run-as user can do, including Setup access if that user has it.

Scoping the connected app is the first half of least privilege; scoping the run-as user's permission set is the second, and the more important one. See [[03.5 - Object Level Security - CRUD]].

## Token introspection and revocation

```
GET /services/oauth2/userinfo
Authorization: Bearer {token}
```

Returns the authenticated user's identity — useful for a client confirming which user and org a token belongs to.

```
POST /services/oauth2/revoke
token={access_or_refresh_token}
```

Revocation is what an offboarding process should call. Deactivating a user does not immediately invalidate every issued token.

## Login endpoints

```
https://login.salesforce.com          production and developer orgs
https://test.salesforce.com           sandboxes
https://myorg.my.salesforce.com       My Domain — preferred
```

**Use the org's My Domain URL** where possible. It is required for some features, it survives instance migration, and it is what the `instance_url` in the token response gives you.

A common configuration error is pointing a sandbox integration at `login.salesforce.com`, which fails with an unhelpful `invalid_grant`.

## Errors

```
invalid_client_id          the consumer key is wrong
invalid_client             the consumer secret is wrong
invalid_grant              bad code, expired token, wrong endpoint, or an IP restriction
inactive_user              the run-as user is deactivated
inactive_org               the org is locked or suspended
rate_limit_exceeded        too many token requests
```

**`invalid_grant` is the least informative and most common.** It covers a wrong login endpoint, an expired authorization code, a user without access to the connected app, an IP restriction, and several other causes. Working through them in order — endpoint, then app policy, then user permissions, then IP — is faster than guessing.

## Salesforce as the client

For outbound calls, **never implement OAuth by hand in Apex.** Named Credentials handle the token lifecycle, storage, and refresh.

```java
// The platform resolves and refreshes the credential; no token appears in code
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:ERP_System/api/claims');
req.setMethod('POST');
```

Storing a client secret in a custom setting and writing a token-refresh method is a pattern that appears in older orgs and should be migrated. It leaks secrets into data, it does not handle refresh reliably, and it is a security review finding. See [[13.13 - Named Credentials and External Credentials]].

## Session Id, and its limits

Inside Salesforce, `UserInfo.getSessionId()` returns the running user's session, usable against the org's own APIs.

Two constraints:

**It is not available in asynchronous contexts.** In a Queueable, a Batch job, or a future method, it returns null or a restricted token. Code calling the org's own API from async needs a Named Credential pointing at the org itself.

**Never send it externally.** A session Id in an outbound request is a credential leak, and it is one of the specific things a security review checks for.

```java
// Wrong
req.setHeader('Authorization', 'Bearer ' + UserInfo.getSessionId());
req.setEndpoint('https://external-system.com/api');

// Correct
req.setEndpoint('callout:External_System/api');
```

## Connected app policies

Beyond the flow, the connected app carries policies that determine whether a token works at all:

**Permitted Users** — admin-approved users only, or all users who self-authorize. Admin-approved is the right default for internal integrations.

**IP Relaxation** — whether the app is subject to the org's IP restrictions. Integration users generally need relaxation, because source IPs change.

**Refresh Token Policy** — as above.

**Session Policies** — separate timeout and high-assurance requirements for that app.

See [[13.12 - Connected Apps and Auth Providers]].

## Practical guidance

**JWT Bearer for server-to-server.** No stored password, no refresh token expiry.

**Web Server with PKCE for user-facing apps**, always with a `state` parameter.

**Never use username-password flow.** Migrate it where you find it.

**Grant minimal scopes.** Never `full`.

**Use the `instance_url` from the token response**, not a hardcoded URL.

**Set the refresh token policy deliberately.** The 90-day surprise is avoidable.

**Use Named Credentials for outbound**, never hand-rolled token handling.

**Never send a session Id externally.**

**Revoke tokens during offboarding**, not just deactivate the user.
