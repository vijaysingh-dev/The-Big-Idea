# Protected Routes and Auth Flows

## The starting point

**Client-side route protection is UX, not security.** Anyone can open DevTools, modify the JavaScript, or call your API directly with `curl`. Hiding a route hides the *UI*, not the data.

**Every API endpoint must authorize independently.** If the server returns a user's data to any request with a valid token regardless of role, no amount of client routing fixes it ([[15.4 - Authentication vs Authorization]]).

With that established, route guards exist to avoid showing users screens that will fail.

## A layout route guard

```jsx
function RequireAuth() {
  const { user, isLoading } = useAuth();
  const location = useLocation();

  if (isLoading) return <FullPageSpinner />;

  if (!user) {
    return <Navigate to="/login" state={{ from: location }} replace />;
  }

  return <Outlet />;
}
```

```jsx
const router = createBrowserRouter([
  {
    element: <RequireAuth />,
    children: [
      { path: "dashboard", element: <Dashboard /> },
      { path: "settings", element: <Settings /> },
    ],
  },
  { path: "login", element: <Login /> },
]);
```

A pathless layout route guards a whole branch with one component rather than wrapping each route ([[23.2 - React Router Setup and Nested Routes]]).

Three details:

**The `isLoading` check is essential.** Without it, the first render before auth resolves redirects an authenticated user to login — a very common bug that appears as a flash of the login page on every refresh.

**`replace` prevents a back-button loop.** Without it, back returns to the protected route, which redirects again.

**`state={{ from: location }}`** captures where the user was headed.

## Returning after login

```jsx
function Login() {
  const navigate = useNavigate();
  const location = useLocation();
  const from = location.state?.from?.pathname ?? "/dashboard";

  const onSubmit = async (credentials) => {
    await signIn(credentials);
    navigate(from, { replace: true });
  };
}
```

Note the fallback — a user who navigates directly to `/login` has no state ([[23.3 - Dynamic Routes and Params]]).

Validate the destination if it can come from a query parameter rather than location state:

```jsx
const redirect = searchParams.get("redirect");
const safe = redirect?.startsWith("/") && !redirect.startsWith("//") ? redirect : "/";
```

An unvalidated redirect parameter is an **open redirect** vulnerability — an attacker sends `/login?redirect=https://evil.com`, and the user is bounced to a phishing page from a legitimate-looking link. The `//` check matters because `//evil.com` is a protocol-relative URL ([[15.6 - Frontend Security]]).

## Role-based access

```jsx
function RequireRole({ allowed }) {
  const { user } = useAuth();

  if (!user) return <Navigate to="/login" replace />;
  if (!allowed.includes(user.role)) return <Navigate to="/forbidden" replace />;

  return <Outlet />;
}

{
  element: <RequireRole allowed={["admin"]} />,
  children: [{ path: "admin", element: <AdminPanel /> }],
}
```

Redirect to a **403 page**, not to login. Sending an authenticated user to a login screen they are already past is confusing, and it hides the real problem.

For finer-grained permissions, a capability check reads better than role strings:

```jsx
const { can } = usePermissions();
if (!can("invoice:refund")) return <Forbidden />;
```

Roles map to capabilities in one place, so adding a role does not require editing every guard.

## Where the auth state comes from

```jsx
function AuthProvider({ children }) {
  const { data: user, isLoading } = useQuery({
    queryKey: ["session"],
    queryFn: fetchSession,
    retry: false,
    staleTime: 5 * 60 * 1000,
  });

  const value = useMemo(() => ({ user, isLoading }), [user, isLoading]);
  return <AuthContext value={value}>{children}</AuthContext>;
}
```

Treating the session as **server state** rather than client state is the cleaner model — it has a source of truth on the server, it goes stale, and it needs revalidation ([[24.6 - TanStack Query Fundamentals]]).

The alternative — reading a token from storage and decoding it client-side — is faster but trusts a client-held value. Decoding a JWT tells you what the token *claims*, not whether the server still accepts it ([[15.5 - JWT Sessions and Token Storage]]).

A reasonable hybrid: optimistically render from a cached session for instant paint, and revalidate in the background.

## Handling 401 globally

```js
api.interceptors.response.use(null, async (error) => {
  if (error.response?.status !== 401) throw error;

  try {
    await refreshToken();
    return api.request(error.config);      // retry once
  } catch {
    queryClient.clear();
    window.location.href = "/login";       // full reload clears all state
    throw error;
  }
});
```

Centralizing this in the API layer means no component needs to handle expired sessions ([[24.1 - Building an API Layer]]).

Two things worth getting right: **deduplicate concurrent refreshes**, or five parallel requests trigger five refresh calls and four of them fail ([[04.7 - Async Concurrency Patterns]]); and **only retry once**, or a persistently failing refresh produces an infinite loop.

Using `window.location.href` rather than client navigation for the final logout is deliberate — it guarantees every cache, store and in-memory secret is cleared.

## Logout

```jsx
async function signOut() {
  await api.post("/auth/logout");     // invalidate server-side
  queryClient.clear();                // clear cached data
  window.location.href = "/login";
}
```

Clearing the client cache matters: without it, the next user on a shared device sees the previous user's data flash before refetching.

For logout across tabs, `BroadcastChannel` or a `storage` event listener propagates the signal ([[14.2 - LocalStorage and SessionStorage]]).

## Server-side protection

With loaders, the check moves out of render entirely ([[23.6 - Data Loading with Loaders and Actions]]):

```jsx
{
  path: "dashboard",
  loader: async ({ request }) => {
    const session = await getSession(request);
    if (!session) {
      const from = new URL(request.url).pathname;
      throw redirect(`/login?redirect=${encodeURIComponent(from)}`);
    }
    return getDashboardData(session.userId);
  },
  element: <Dashboard />,
}
```

The redirect happens before the component renders, so there is no flash of protected content. In a framework with server rendering, this runs on the server and the protected UI is never sent at all — which is the genuinely correct place for the check ([[28.7 - Authentication Flow Design]]).

Middleware in Next.js does the equivalent at the edge.

## Hiding UI versus guarding routes

```jsx
{can("invoice:refund") && <RefundButton />}
```

Hiding a button the user cannot use is good UX. It is not access control — the endpoint still needs to reject the request.

A useful discipline: write the server check first, then hide the UI. Doing it in the other order tends to leave the server check for later.

## How senior engineers actually use this

**They treat client guards as UX and enforce authorization server-side**, always.

**They handle the loading state in guards**, since the flash-of-login bug is otherwise guaranteed.

**They centralize 401 handling** in the API layer with deduplicated refresh and single retry.

**They validate redirect destinations** to close the open-redirect hole.

**They move the check into loaders or middleware** where the framework supports it, so protected content never renders at all.

## Common pitfalls

- No loading state, redirecting authenticated users on every refresh.
- Missing `replace`, creating back-button loops.
- Unvalidated redirect parameters — open redirect.
- Sending unauthorized-but-authenticated users to login instead of a 403 page.
- Concurrent 401s triggering parallel refresh calls.
- Retry loops when refresh itself fails.
- Cache not cleared on logout, leaking data to the next user.
- Assuming a hidden route is a secured route.

## Interview angle

"How do you implement protected routes" should open with the framing that client-side guards are UX and the server enforces access — that alone separates a strong answer. Then the mechanics: a pathless layout route wrapping the protected branch, handling the loading state to avoid the redirect flash, capturing the intended destination in location state, and `replace` to avoid loops. Mentioning open-redirect validation and deduplicated token refresh signals real production experience.
