# Databases

## SQL vs NoSQL Decision Tree

```
Does data have complex relationships requiring joins?
    Yes → SQL

Is the schema evolving rapidly or document-shaped?
    Yes → consider NoSQL (MongoDB)

Need ACID transactions across multiple records?
    Yes → SQL

Massive write throughput (>100K writes/sec)?
    Yes → consider Cassandra/DynamoDB

Time-series data (metrics, logs, events)?
    Yes → TimescaleDB, InfluxDB, Cassandra

Key-value lookups only?
    Yes → Redis, DynamoDB

Full-text search primary use case?
    Yes → Elasticsearch (+ SQL for source of truth)

When in doubt: Start with PostgreSQL.
```

## Schema Design Principles

### Normalization vs Denormalization

```
Normalized (3NF):
  - Data stored once, referenced by ID
  - ✅ No update anomalies
  - ✅ Storage efficient
  - ❌ Joins required for reads
  Use: Write-heavy, OLTP, financial systems

Denormalized:
  - Data duplicated for fast reads
  - ✅ No joins — fast queries
  - ❌ Update anomalies (update in multiple places)
  - ❌ More storage
  Use: Read-heavy, OLAP, reporting, CQRS read models

Rule: Normalize the write model, denormalize the read model.
```

### Column Design Rules

```python
# Data type discipline
user_id: UUID         # not INT — UUIDs are portable, distributed-safe
price: DECIMAL(10,2)  # not FLOAT — floats have precision errors for money
status: VARCHAR(20)   # or ENUM — not INT (1=pending, 2=active is opaque)
created_at: TIMESTAMPTZ  # always timezone-aware
email: VARCHAR(255) UNIQUE NOT NULL

# Avoid:
# - Storing JSON blobs for structured data that needs querying
# - Using NULL for "not applicable" and "unknown" interchangeably
# - Storing currency as float
# - Auto-increment INT as primary key for distributed systems
```

## Indexing

### When to Index

```sql
-- Index on:
-- 1. Foreign keys (almost always)
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 2. Columns in WHERE clauses with high selectivity
CREATE INDEX idx_orders_status ON orders(status);

-- 3. Columns in ORDER BY (for pagination)
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);

-- 4. Composite for multi-column WHERE + ORDER BY
CREATE INDEX idx_orders_user_status_date 
  ON orders(user_id, status, created_at DESC);
-- Useful for: WHERE user_id = ? AND status = 'PENDING' ORDER BY created_at

-- 5. Partial index for filtered queries
CREATE INDEX idx_orders_pending 
  ON orders(created_at) 
  WHERE status = 'PENDING';
-- Much smaller index — only pending orders
```

### Index Types

|Type|Use Case|
|---|---|
|B-tree (default)|=, <, >, BETWEEN, ORDER BY|
|Hash|= only, faster than B-tree for equality|
|GIN|Full-text search, array contains, JSONB|
|BRIN|Time-series, append-only large tables (tiny index)|

### Index Anti-patterns

```sql
-- ❌ Index on low-cardinality column alone (e.g., gender: M/F)
--    Index on status with 3 values is rarely useful by itself
--    But fine as part of composite index

-- ❌ Too many indexes — every index slows writes
--    General rule: <5 indexes per table for OLTP

-- ❌ Index not used due to function on column
WHERE LOWER(email) = 'user@example.com'  -- won't use index on email
-- Fix: expression index
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

-- ❌ Index not used due to leading wildcard
WHERE name LIKE '%john%'   -- can't use B-tree index
-- Fix: full-text search index
```

## Transactions & Locking

### Isolation Levels

```
READ UNCOMMITTED:  Reads dirty (uncommitted) data. Never use.
READ COMMITTED:    Default in PostgreSQL. Reads only committed data.
                   Phantom reads possible.
REPEATABLE READ:   Same row read twice returns same value within tx.
                   Phantom reads possible.
SERIALIZABLE:      Strictest. Transactions appear to execute serially.
                   Performance cost. Use for financial accuracy.
```

### Optimistic vs Pessimistic Locking

```python
# Optimistic locking — no lock held, conflict detected at commit
class Order(Base):
    version: int = Column(Integer, default=0)
    
    # SQLAlchemy uses version_id_col for optimistic locking
    __mapper_args__ = {"version_id_col": version}

# If two processes load same order (version=5), 
# first to commit wins; second gets StaleDataError

# Pessimistic locking — lock row for duration of transaction
order = session.query(Order).filter_by(id=order_id).with_for_update().first()
# Now locked — other transactions that try to lock same row block
# Use when: high contention, short-lived operations
# Avoid when: long operations (holds lock too long)
```

### Deadlock Prevention

```python
# Always acquire locks in consistent order
# Bad: tx1 locks orders then payments; tx2 locks payments then orders → deadlock
# Good: always lock in alphabetical order: orders, payments

# Use retry logic for deadlock victims
from sqlalchemy.exc import OperationalError

def execute_with_retry(session, operation, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = operation(session)
            session.commit()
            return result
        except OperationalError as e:
            if "deadlock" in str(e).lower() and attempt < max_retries - 1:
                session.rollback()
                time.sleep(0.1 * (2 ** attempt))
            else:
                raise
```

## Database Migrations

### Migration Principles

```
1. Migrations are code — commit them, review them
2. Never edit old migrations — create new ones
3. Make migrations backward-compatible (expand-contract pattern)
4. Test rollback before deploying to production
```

### Expand-Contract Pattern (Zero-Downtime Migrations)

```sql
-- Phase 1: Expand (add new — old code still works)
ALTER TABLE users ADD COLUMN display_name VARCHAR(100);
-- Both old (uses `name`) and new code can run simultaneously

-- Phase 2: Migrate data
UPDATE users SET display_name = name WHERE display_name IS NULL;

-- Phase 3: Switch code to use display_name (deploy new code)

-- Phase 4: Contract (remove old — after verifying new code works)
ALTER TABLE users DROP COLUMN name;
```

## Connection Pooling

```python
# SQLAlchemy pool configuration
from sqlalchemy import create_engine

engine = create_engine(
    DATABASE_URL,
    pool_size=10,           # connections kept open
    max_overflow=20,        # max extra connections at peak
    pool_pre_ping=True,     # test connection before use (handles dropped connections)
    pool_recycle=3600,      # recycle connections after 1 hour
    pool_timeout=30,        # wait max 30s for a connection
)

# Pool sizing rule of thumb:
# pool_size = (num_cpu_cores * 2) + effective_spindle_count
# For most web apps: 5-20 connections per service instance
```

## Read Replicas

```
Primary (writes):   ──────► Replica 1 (reads)
                    ──────► Replica 2 (reads)
                    ──────► Replica 3 (reads)

Route reads to replicas for:
  - Analytics queries
  - Reporting
  - Search queries
  - Non-critical reads (product listings)

Keep on primary:
  - Financial operations (need latest data)
  - Auth decisions (need latest data)
  - Any read-then-write patterns
```
