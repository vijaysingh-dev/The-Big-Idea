# Pydantic Fundamentals

#python #pydantic #validation #serialization

> **In one line:** Pydantic turns type hints into a validator. You declare a model once, and untrusted input (JSON, dicts, env vars) is parsed, coerced and checked into typed objects, with precise errors when it does not fit, then serialised back out. It is the boundary layer of almost every modern Python service.

---

## The Idea

```python
from datetime import datetime
from pydantic import BaseModel, EmailStr, Field

class SignUp(BaseModel):
    email: EmailStr
    password: str = Field(min_length=12)
    age: int = Field(ge=13)
    referral: str | None = None
    signed_up_at: datetime

data = {"email": "a@x.com", "password": "correct horse battery", "age": "30",
        "signed_up_at": "2026-11-15T10:00:00Z"}
s = SignUp.model_validate(data)
s.age                 # 30 — an int; the string "30" was coerced
s.signed_up_at        # datetime(2026, 11, 15, 10, 0, tzinfo=UTC)
```

```python
SignUp.model_validate({"email": "nope", "password": "short", "age": 5})
```
```
pydantic_core.ValidationError: 4 validation errors for SignUp
email           value is not a valid email address
password        String should have at least 12 characters
age             Input should be greater than or equal to 13
signed_up_at    Field required
```

All errors at once, each with a location, a message and a machine-readable type. FastAPI turns exactly this into its 422 response.

💡 **Pydantic parses, it does not just check.** The guarantee is about the **output**: after validation, `s.age` is an `int` no matter what came in. Think "parse, don't validate": once data is through the boundary, the rest of your code can trust its types.

## Under the Hood (v2)

```
class definition ──► ModelMetaclass reads annotations ──► core schema (a dict tree)
                                                              │
                                                              ▼
                                       pydantic-core (Rust) builds SchemaValidator + SchemaSerializer
                                                              │
model_validate(data) ─────────────────────────────────────────┘  runs in Rust, returns the model
```

The schema is built **once per class**, at import time ([[06.8 - Metaprogramming]]). Validation runs in compiled Rust, which is why v2 is typically 5–20x faster than v1. The cost moved to class definition: hundreds of complex models make imports slower. Use `defer_build=True` in `model_config` if startup time matters.

## Fields

```python
from typing import Annotated, Literal
from uuid import UUID, uuid4
from decimal import Decimal
from pydantic import BaseModel, Field, HttpUrl, PositiveInt

Sku = Annotated[str, Field(pattern=r"^[A-Z]{3}-\d{4}$")]   # a reusable constrained type

class Item(BaseModel):
    id: UUID = Field(default_factory=uuid4)
    sku: Sku
    name: str = Field(min_length=1, max_length=200)
    price: Decimal = Field(gt=0, max_digits=10, decimal_places=2)
    qty: PositiveInt = 1
    tags: list[str] = []                 # safe: Pydantic copies mutable defaults per instance
    kind: Literal["physical", "digital"] = "physical"
    homepage: HttpUrl | None = None
    internal_code: str = Field(default="", exclude=True)          # never serialised
    display_name: str = Field(alias="displayName", default="")    # JSON uses camelCase
```

| Want | Use |
|---|---|
| Required | No default |
| Optional (may be missing) | A default, e.g. `= None` or `= ""` |
| Nullable (may be `null`) | `X \| None` |
| Required **and** nullable | `x: int \| None` with no default |
| Constraints | `Field(gt=, ge=, lt=, le=, min_length=, max_length=, pattern=, multiple_of=)` |
| Reusable constrained types | `Annotated[T, Field(...)]` aliases |
| Rich types | `EmailStr` (needs `email-validator`), `HttpUrl`, `IPvAnyAddress`, `SecretStr`, `PastDatetime`, `AwareDatetime`, `conlist`, `UUID`, `Decimal`, enums |

⚠️ **"Optional" and "nullable" are different.** `x: int | None` without a default is **required** but may be `null`. That surprises v1 users, where `Optional[int]` implied a default of `None`.

## Lax vs Strict

By default Pydantic is **lax**: it coerces sensible inputs.

| Input → field type | Lax (default) | Strict |
|---|---|---|
| `"42"` → `int` | `42` | Error |
| `42.0` → `int` | `42` | Error |
| `42.5` → `int` | Error (fractional) | Error |
| `"true"`, `1` → `bool` | `True` | Error |
| `"2026-11-15"` → `date` | `date(...)` | Error (in Python mode; JSON strings are allowed) |
| `1` → `str` | **Error** (v2 does not coerce numbers to strings) | Error |

```python
class Payment(BaseModel):
    model_config = {"strict": True}           # whole model
    amount_cents: int
    flag: Annotated[bool, Field(strict=True)] # or per field
```

Lax mode suits query strings and form data, where everything arrives as strings. Strict mode suits internal messages, where a type mismatch means a bug upstream.

## Validators

```python
from pydantic import BaseModel, field_validator, model_validator

class DateRange(BaseModel):
    start: date
    end: date
    timezone: str = "UTC"

    @field_validator("timezone")
    @classmethod
    def known_tz(cls, v: str) -> str:
        if v not in zoneinfo.available_timezones():
            raise ValueError(f"unknown timezone {v!r}")
        return v

    @model_validator(mode="after")
    def check_order(self) -> "DateRange":
        if self.end < self.start:
            raise ValueError("end must be on or after start")
        return self
```

| Validator | Runs | Receives | Use for |
|---|---|---|---|
| `field_validator(mode="after")` (default) | After type validation | The typed value | Business rules on one field |
| `field_validator(mode="before")` | Before type validation | The raw input | Normalising input: strip strings, split `"a,b"` into a list |
| `model_validator(mode="after")` | After all fields | The model | Rules across fields |
| `model_validator(mode="before")` | First | The raw dict | Reshaping legacy payloads |
| `Annotated[T, AfterValidator(fn)]` | Like `field_validator`, but attached to a reusable type | | Shared rules: `Slug`, `Username` |

Raise `ValueError` (or `PydanticCustomError` for a custom error type) inside validators. Pydantic collects them into the `ValidationError` with locations.

## Nested Models

```python
class Address(BaseModel):
    city: str
    country: Annotated[str, Field(min_length=2, max_length=2)]

class Customer(BaseModel):
    name: str
    addresses: list[Address]
    default_address: Address | None = None

Customer.model_validate({"name": "A", "addresses": [{"city": "Lima", "country": "PEE"}]})
# error location: ('addresses', 0, 'country')
```

Errors point to the exact nested location, which maps straight onto a form field or a JSON path for API clients.

## Serialisation

```python
c.model_dump()                          # dict of Python objects (datetime stays datetime)
c.model_dump(mode="json")               # dict of JSON-safe values (datetime → str, Decimal → str)
c.model_dump_json()                     # JSON string, built in Rust: fast
c.model_dump(by_alias=True)             # use aliases (camelCase) as keys
c.model_dump(exclude_none=True, exclude={"internal_code"})
c.model_dump(include={"name", "addresses": {0: {"city"}}})   # nested include
```

Customise output with `@field_serializer` / `@model_serializer`, and expose computed values with `@computed_field`:

```python
from pydantic import computed_field

class Cart(BaseModel):
    items: list[Item]

    @computed_field
    @property
    def total(self) -> Decimal:
        return sum((i.price * i.qty for i in self.items), Decimal(0))
```

## model_config

```python
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel

class ApiModel(BaseModel):
    model_config = ConfigDict(
        extra="forbid",              # unknown fields → error ("ignore" is the default, "allow" keeps them)
        frozen=True,                 # immutable and hashable
        str_strip_whitespace=True,
        alias_generator=to_camel,    # snake_case in Python, camelCase on the wire
        populate_by_name=True,       # accept both names on input
        from_attributes=True,        # validate from ORM objects: Model.model_validate(orm_row)
        use_enum_values=False,
    )
```

A shared base model for each boundary (an `ApiModel` for the public API, an `EventModel` for messages) keeps these rules consistent across a codebase.

| Setting | For request bodies | For responses / events you consume |
|---|---|---|
| `extra="forbid"` | Good: catches client typos (`emial`) | Bad: breaks when the producer adds a field |
| `extra="ignore"` | Silent typos | **Good: tolerant reader** ([[06.13 - Contract Testing and Schema Evolution]]) |

## Copying and Updating

```python
updated = order.model_copy(update={"status": "paid"})   # shallow; does NOT re-validate
validated = Order.model_validate(order.model_dump() | {"status": "paid"})  # re-validates
```

⚠️ `model_copy(update=...)` and plain attribute assignment skip validation by default. Turn on `validate_assignment=True` if you mutate models and need the rules enforced, or keep models frozen and rebuild them.

## Codebase

**Repos:** `pydantic/pydantic`, `pydantic/pydantic-core`

**Question to answer:** What does the core schema look like for a small model, and where does an `int` field's lax coercion of `"42"` happen?

**Read, in order:**

1. Print `SignUp.__pydantic_core_schema__` for a three-field model. It is a plain nested dict. Read it.
2. pydantic `pydantic/_internal/_generate_schema.py` — `GenerateSchema` and `_model_schema` / `match_type`: how annotations become schema nodes
3. pydantic `pydantic/main.py` — `BaseModel.model_validate` and `__init__`: both call `__pydantic_validator__`
4. pydantic-core `src/validators/int.rs` (and `src/input/input_python.rs`, `validate_int` / `strict_int`): where `"42"` becomes `42` in lax mode and fails in strict mode

**Size:** 2 sessions. Even skimming the Rust gives a real sense of where the speed comes from.
