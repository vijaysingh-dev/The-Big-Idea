# Apex Language Overview

## What Apex is

A strongly typed, object-oriented language that runs on Salesforce servers, syntactically close to Java, with the database built into the language rather than accessed through a driver.

```java
public with sharing class WarrantyClaimService {

    public static void approve(Set<Id> claimIds, Decimal approvedAmount) {
        List<Warranty_Claim__c> claims = [
            SELECT Id, Status__c, Claim_Amount__c
            FROM Warranty_Claim__c
            WHERE Id IN :claimIds AND Status__c = 'Under Review'
        ];

        for (Warranty_Claim__c claim : claims) {
            claim.Status__c = 'Approved';
            claim.Approved_Amount__c = Math.min(approvedAmount, claim.Claim_Amount__c);
        }

        update claims;
    }
}
```

SOQL is a language construct, not a string passed to a driver. There is no connection, no cursor, no ORM. That is the most visible difference from anything else you have written.

## What it is not

The constraints follow directly from running on shared infrastructure ([[01.2 - SaaS vs PaaS vs IaaS]]):

**No `main()`.** Apex only runs when something invokes it: a trigger, a controller, a REST endpoint, a scheduled job, an anonymous block.

**No threads.** No `Thread`, no `synchronized`, no concurrency primitives. Background work goes to Queueable, Batch, or Scheduled Apex.

**No filesystem.** No `File`, no streams to disk.

**No package manager.** No Maven, no npm. The standard library is what you get.

**No arbitrary networking.** HTTP callouts only, through `Http` and `HttpRequest`, subject to limits and to Named Credentials.

**Hard runtime limits.** Queries, DML, CPU time, heap — all capped per transaction, enforced by exception. See section 16.

**Case-insensitive.** `myVariable` and `MYVARIABLE` are the same identifier. This surprises people from Java, and it means a variable and a field differing only in case are a collision.

## Differences from Java worth knowing early

**Everything is `private` by default**, including at the class level.

**No package system.** Classes live in a flat namespace within the org, so class names must be unique. This is why naming conventions matter more than they would elsewhere.

**No checked exceptions.** Every exception is unchecked.

**`String` comparison uses `==`** and is case-insensitive by default. `equals()` exists and is case-sensitive.

```java
String a = 'Press';
String b = 'PRESS';

a == b            // true — case-insensitive
a.equals(b)       // false — case-sensitive
a.equalsIgnoreCase(b)  // true
```

This is a genuine source of subtle bugs for anyone expecting Java semantics.

**Decimal, not double, for money.** `Decimal` is arbitrary precision. `Double` is floating point and should never hold currency.

**No `char` type.** Single characters are one-character Strings.

**Static variables persist for the transaction**, not the session or the request in the usual sense. See [[09.8 - Static Members and Class Level State]].

## Where Apex runs

The entry points, each with its own context and its own limits:

| Entry point | Invoked by | Notes |
| --- | --- | --- |
| Trigger | A record save | Section 11 |
| `@AuraEnabled` method | A Lightning component | Effectively a public endpoint |
| `@RestResource` | An external system | Section 13 |
| `@InvocableMethod` | Flow or Agentforce | [[07.9 - Invocable Apex and Flow-Apex Interop]] |
| `Queueable` | `System.enqueueJob` | Async, own limits |
| `Batchable` | `Database.executeBatch` | Async, chunked |
| `Schedulable` | The scheduler | Async |
| Platform event subscriber | An event publish | Async |
| Anonymous Apex | Developer Console or CLI | Not saved, runs once |
| Test method | The test runner | Isolated data context |

Each of these is a separate transaction with a fresh limit budget, which is the basis of most scaling strategies on the platform.

## Anonymous Apex

Code executed once without being saved as a class. The developer's scratchpad, and genuinely useful for one-off data fixes and exploration.

```bash
sf apex run --file scripts/fix-claim-regions.apex --target-org my-sandbox
```

```java
List<Warranty_Claim__c> claims = [
    SELECT Id, Asset__r.Account.BillingCountry
    FROM Warranty_Claim__c
    WHERE Region__c = null AND Asset__c != null
    LIMIT 10000
];

for (Warranty_Claim__c claim : claims) {
    claim.Region__c = claim.Asset__r?.Account?.BillingCountry;
}

Database.SaveResult[] results = Database.update(claims, false);
Integer failed = 0;
for (Database.SaveResult r : results) {
    if (!r.isSuccess()) {
        failed++;
    }
}
System.debug('Updated ' + (results.size() - failed) + ', failed ' + failed);
```

Two cautions worth holding. Anonymous Apex runs with your permissions, including Modify All Data if you are an administrator, so a mistake affects everything. And it is subject to normal governor limits, so a data fix touching more than 10,000 records needs Batch Apex instead.

Running a `SELECT COUNT()` before the update, to confirm the scope is what you expect, is a two-second habit that prevents real incidents.

## API version

Every Apex class carries an API version in its metadata, which pins platform behaviour for that class.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ApexClass xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>62.0</apiVersion>
    <status>Active</status>
</ApexClass>
```

Salesforce changes semantics between versions, and old code keeps its old behaviour until the version is raised deliberately. Bumping a class from 45 to 62 is a real change requiring tests, not housekeeping. See [[01.11 - Release Cycle, Trust and Status]].

## Compilation and deployment

Apex compiles at save. A syntax error or an unknown field name fails immediately, which is a genuine advantage of inline SOQL over dynamic.

Deployment to production requires **75% test coverage across the org**, every trigger to have some coverage, and all tests to pass. Coverage is a deployment gate, not a quality measure — the distinction matters and is covered in [[19.10 - Code Coverage, Quality and CI Gates]].

Code cannot be edited directly in production. Changes are deployed from a sandbox or from source. See [[21.1 - Metadata, Source of Truth and Deployment Concepts]].

## The mental shift

For someone arriving from another backend stack, three adjustments matter more than syntax.

**Think in collections, always.** Every entry point can hand you 200 records. A method taking a single record invites someone to call it in a loop, and that is how limit failures happen. Method signatures take `List` by default. See [[10.6 - Bulkification Patterns]].

**Queries are scarce, not cheap.** 100 per transaction, shared with everything else running. The instinct to query inside a loop must be trained out early, and it is the single most important habit.

**Your code is a guest in a pipeline.** It runs alongside flows, validation rules, other triggers, and managed packages, in a fixed sequence, sharing one limit budget. See [[07.13 - Order of Execution]].

## Tooling

**Salesforce Extensions for VS Code** is the standard environment — syntax highlighting, deployment, test running, debug log retrieval, and an interactive debugger.

**Salesforce CLI** for everything scriptable:

```bash
sf project deploy start --source-dir force-app --target-org my-sandbox
sf apex run test --tests WarrantyClaimServiceTest --result-format human
sf apex tail log --target-org my-sandbox
```

**Developer Console** in the browser for quick queries, the query plan, and log inspection.

**PMD with the Apex ruleset** for static analysis, catching SOQL in loops, missing sharing declarations, and unbounded queries before review does. See [[21.9 - Static Analysis, PMD and Code Review]].
