# DML Statements

## The two forms

**DML** — Data Manipulation Language — writes records. Apex offers two syntaxes for the same operations.

```java
// Statement form: all-or-none
insert claims;
update claims;
delete claims;
upsert claims ERP_Claim_Id__c;
undelete claims;
merge masterAccount duplicateAccounts;

// Database method form: optional partial success
Database.insert(claims, false);
Database.update(claims, false);
Database.delete(claims, false);
Database.upsert(claims, Warranty_Claim__c.ERP_Claim_Id__c, false);
Database.undelete(claims, false);
Database.merge(masterAccount, duplicateAccount, false);
```

The difference is failure behaviour and is the subject of [[10.2 - Database Class Methods and Partial Success]]. The statement form throws `DmlException` and rolls back everything; the method form can report per record and continue.

## Insert

```java
List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
for (Asset asset : affectedAssets) {
    claims.add(new Warranty_Claim__c(
        Asset__c = asset.Id,
        Account__c = asset.AccountId,
        Claim_Date__c = Date.today(),
        Status__c = 'Submitted'
    ));
}

insert claims;

// Ids are populated on the in-memory records after a successful insert
for (Warranty_Claim__c claim : claims) {
    System.debug(claim.Id);
}
```

**Ids are assigned back to the objects in the list**, which is what makes creating parent-then-child work without re-querying:

```java
insert claims;

List<Claim_Part__c> parts = new List<Claim_Part__c>();
for (Warranty_Claim__c claim : claims) {
    parts.add(new Claim_Part__c(
        Warranty_Claim__c = claim.Id,      // available immediately
        Product__c = defaultPartId,
        Quantity__c = 1
    ));
}
insert parts;
```

**Auto-number, formula, and roll-up fields are not populated** on the in-memory record after insert. Reading `claim.Claim_Number__c` immediately after inserting returns null. Re-query if you need them:

```java
insert claim;
claim = [SELECT Id, Claim_Number__c, Days_Open__c FROM Warranty_Claim__c WHERE Id = :claim.Id];
```

## Update

```java
List<Warranty_Claim__c> toUpdate = new List<Warranty_Claim__c>();

for (Warranty_Claim__c claim : claims) {
    if (claim.Status__c == 'Under Review' && claim.Approved_Amount__c != null) {
        claim.Status__c = 'Approved';
        toUpdate.add(claim);
    }
}

if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

**Every record must have an Id.** A record without one throws `MISSING_ARGUMENT`.

**Only fields you set are written** — Salesforce sends the populated fields, not the whole record. A record queried with three fields and updated writes only what changed among those three.

That behaviour enables a useful pattern: constructing a record with only an Id and the fields to change, avoiding a query entirely.

```java
// No query needed to update a known record
update new Warranty_Claim__c(Id = claimId, Status__c = 'Approved');
```

For bulk updates where you already have the Ids, this saves a query and reduces heap significantly.

## The empty list guard

```java
if (!toUpdate.isEmpty()) {
    update toUpdate;
}
```

DML on an empty list succeeds and **still consumes one of the 150 DML statements**. In a handler with several conditional update paths, guarding each one conserves the budget in the common case where most paths find nothing.

## Mixing operations

Each DML statement counts separately, so combining where possible matters:

```java
// Three DML statements
insert newClaims;
insert newParts;
insert newLogs;

// One, using a generic list
List<SObject> toInsert = new List<SObject>();
toInsert.addAll((List<SObject>) newClaims);
toInsert.addAll((List<SObject>) newParts);
insert toInsert;
```

**This only works when the records have no dependency on each other.** Parts referencing claims that do not yet exist will fail — the claims must be inserted first so their Ids exist.

The platform does not guarantee ordering within a mixed list, so use it only for genuinely independent records. In practice the saving is rarely worth the risk, and the technique matters mainly when approaching the DML limit in a large handler.

## The limits

Per synchronous transaction:

- **150 DML statements**
- **10,000 records processed by DML** across all statements
- Records processed by a trigger cascade count toward the same total

The record limit is the one that catches people. Updating 200 opportunities, each cascading a roll-up to its account, processes 200 plus up to 200 more — and if account triggers update contacts, more still.

Approaching either limit means moving to async. See [[12.4 - Batch Apex]].

## DML re-enters the save pipeline

Every DML statement runs the full order of execution for the affected records: validation rules, before triggers, after triggers, flows, roll-ups, sharing recalculation. See [[07.13 - Order of Execution]].

Two consequences that shape design:

**DML is expensive.** Not just one operation — a whole pipeline per record.

**DML can recurse.** A trigger updating records of the same object re-enters its own trigger. Recursion control is not optional. See [[11.6 - Recursion Control and Static Guards]].

## Security

```java
insert as user claims;
update as user claims;
delete as user claims;
```

`as user` enforces object permissions, field-level security, and sharing, throwing if the running user lacks access. `as system` is the explicit opposite.

Without either, DML runs in system mode — the running user's field-level security is not applied, and a user can write to fields they cannot see. For anything reachable by a user, `as user` should be the default. See [[03.13 - Enforcing Security in Apex and SOQL]].

For sObjects arriving from a client, `stripInaccessible` before the DML is the complementary defence:

```java
SObjectAccessDecision decision = Security.stripInaccessible(
    AccessType.UPDATABLE, new List<Warranty_Claim__c>{ incoming }
);
update as user decision.getRecords();
```

## DML in triggers

A trigger updating its own triggering records is different depending on timing.

**In a before trigger**, modify `Trigger.new` directly. No DML needed, and DML on those records would be wrong.

```java
// before insert or before update
for (Warranty_Claim__c claim : Trigger.new) {
    claim.Region__c = deriveRegion(claim);
}
// no DML — the values are saved as part of this operation
```

**In an after trigger**, `Trigger.new` is read-only. Updating the same records requires a DML statement, which re-enters the pipeline.

The rule: **anything that only sets fields on the triggering record belongs in a before trigger.** An after trigger updating its own records is nearly always a mistake, for the same reason an after-save flow updating `$Record` is. See [[07.4 - Before-Save vs After-Save Flows]].

## DML options

`Database.DMLOptions` controls behaviour the statement form cannot reach:

```java
Database.DMLOptions options = new Database.DMLOptions();
options.assignmentRuleHeader.useDefaultRule = true;
options.emailHeader.triggerAutoResponseEmail = true;
options.emailHeader.triggerUserEmail = true;
options.optAllOrNone = false;
options.duplicateRuleHeader.allowSave = true;

for (Case c : cases) {
    c.setOptions(options);
}
Database.insert(cases, false);
```

The assignment and email headers are the important ones: **assignment rules and auto-response rules do not run for records created by Apex or the API unless explicitly requested.** Forgetting this is a silent failure that leaves cases and leads owned by the integration user, invisible to everyone. See [[05.3 - Case Assignment and Auto-Response Rules]].

`duplicateRuleHeader.allowSave` bypasses duplicate rules, which is occasionally necessary during a migration and should be deliberate.

## Ordering and dependencies

Records must be inserted in dependency order — parents before children, since a child needs its parent's Id.

```java
insert accounts;

List<Asset> assets = new List<Asset>();
for (Account acc : accounts) {
    assets.add(new Asset(AccountId = acc.Id, Name = acc.Name + ' Press'));
}
insert assets;

List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
for (Asset asset : assets) {
    claims.add(new Warranty_Claim__c(Asset__c = asset.Id, Account__c = asset.AccountId));
}
insert claims;
```

Three DML statements, unavoidable because of the dependency chain. This ordering requirement is the same one that governs data loading ([[02.13 - Data Import and Export Tools]]) and it is the usual reason a migration script has more DML statements than it looks like it should.

## Practical guidance

**Collect and perform one DML per operation.** Never one per record.

**Guard against empty lists.**

**Use partial success for bulk operations.**

**Modify `Trigger.new` in before triggers**, never DML the triggering records in an after trigger.

**Set assignment and email DML options** in any code creating Leads or Cases.

**Use `as user`** on anything a user can reach.

**Re-query for auto-number, formula, and roll-up values** after insert.

**Construct an Id-only record** to update without querying.
