# GDPR, HIPAA and Compliance Patterns

## The framing that matters

**Compliance is not a feature you enable.** It is a set of obligations about what data you hold, why, for how long, who can see it, and what happens when someone asks you to delete it.

Salesforce provides tools that make some of those obligations satisfiable. It does not make an org compliant, and no configuration does.

**A developer's part** is narrower than the whole and specific: building systems where the obligations can actually be met. A right-to-erasure request that takes three weeks of manual work is a system design failure, not a legal one.

**This note is not legal advice.** It covers the technical patterns; the obligations themselves are for the organization's legal and privacy function to determine.

## The obligations that shape design

Across GDPR, HIPAA, CCPA, India's DPDP Act, and most similar regimes, a common set:

```
Lawful basis         a documented reason for holding the data
Data minimization    hold only what is needed
Purpose limitation   use it only for the stated purpose
Retention limits     delete when no longer needed
Right of access      produce everything held about a person
Right of erasure     delete it on request
Right to rectification  correct it
Right to portability    export it in a usable format
Consent management   record and honour preferences
Breach notification  detect and report within a deadline
Audit trail          prove who accessed what
```

**Four of these have direct technical consequences**: access, erasure, retention, and audit. The rest are largely process.

## Knowing where the data is

The prerequisite, and the step most often skipped.

**A data inventory** — which objects and fields hold personal data, of what kind, for what purpose.

```
Object                Field                  Category        Purpose         Retention
Contact               Email                  Identifier      Service         Duration + 2y
Contact               Phone                  Identifier      Service         Duration + 2y
Contact               Birthdate              Identifier      Verification    Duration
Warranty_Claim__c     Fault_Description__c   Free text       Service         7y (regulatory)
Case                  Description            Free text       Service         3y
Attachment            (file content)         Unknown         Various         Varies
```

**Free text and files are the hard part.** A case description can contain anything, and a PDF attachment can contain everything.

**Data Classification metadata** records this on the field itself:

```
Setup → Object Manager → field → Data Classification
    Compliance Categorization:  GDPR, PII, HIPAA
    Data Sensitivity Level:     Public / Internal / Confidential / Restricted
    Data Owner:                 the accountable role
```

```sql
SELECT QualifiedApiName, EntityDefinition.QualifiedApiName,
       ComplianceGroup, SecurityClassification
FROM FieldDefinition
WHERE ComplianceGroup != null
```

**Queryable classification is what makes the inventory maintainable** rather than a spreadsheet that goes stale. It is free, and it is underused.

## Right of access

Producing everything held about a person.

```java
public with sharing class DataSubjectAccessService {

    public class SubjectData {
        public Contact contact;
        public List<Case> cases;
        public List<Warranty_Claim__c> claims;
        public List<Task> activities;
        public List<EmailMessage> emails;
        public List<ContentDocumentLink> files;
        public List<Contact_History> fieldHistory;
    }

    public static SubjectData gather(Id contactId) {
        SubjectData data = new SubjectData();

        data.contact = ContactSelector.byId(contactId);
        data.cases = CaseSelector.byContact(contactId);
        data.claims = ClaimSelector.byContact(contactId);
        data.activities = ActivitySelector.byWho(contactId);
        data.emails = EmailSelector.byContact(contactId);

        // the awkward part: free text and files may reference the person
        // without a lookup, and cannot be found by relationship
        data.files = FileSelector.linkedTo(contactId);

        return data;
    }
}
```

**Traversing relationships finds the structured data.** What it misses:

**Free text mentioning the person** on records not linked to them — a case description naming a customer's spouse.

**Files** whose content is not indexed by person.

**Archived data** in big objects.

**Data in integrated systems** that received it from Salesforce.

**Backups.**

**The realistic position:** an automated gather covers the structured data, and a documented manual process covers the rest. Claiming full automation is usually inaccurate.

## Right of erasure

Harder than deletion, and the requirement most likely to be underestimated.

```java
// Not sufficient
delete contact;
```

**What that leaves behind:**

```
Field history                    OldValue and NewValue retain the data
Feed items and Chatter posts
Email messages                   sender and recipient addresses
Files and attachments
Related records                  cases, claims, activities
Free text on other records
Archived data in big objects
The recycle bin                  15 days
Debug logs                       7 days
Event Monitoring logs
Backups
Downstream systems
```

**Field history is the one people miss.** Deleting a contact removes the record; the history rows recording their email address remain, and they are queryable.

**A more complete approach:**

```java
public with sharing class ErasureService {

    public static ErasureResult erase(Id contactId) {
        ErasureResult result = new ErasureResult();

        // anonymize rather than delete where records must be retained for other reasons
        Contact contact = ContactSelector.byId(contactId);
        contact.FirstName = 'Erased';
        contact.LastName = 'Subject ' + contactId;
        contact.Email = null;
        contact.Phone = null;
        contact.MailingStreet = null;
        contact.Birthdate = null;
        contact.Erased__c = true;
        contact.Erased_Date__c = Date.today();
        update contact;

        clearFreeTextOnRelatedRecords(contactId);
        deleteFilesAndAttachments(contactId);
        deleteEmailMessages(contactId);

        // hard delete, so the recycle bin does not retain it
        Database.emptyRecycleBin(new List<Id>{ });

        publishErasureEvent(contactId);   // downstream systems act on this

        return result;
    }
}
```

**Anonymization rather than deletion** is frequently the right answer where records must be retained for other reasons — a warranty claim has a regulatory retention period, and the claim can survive while the person is anonymized.

**Field history cannot be selectively deleted.** The options are deleting the parent record entirely, or accepting it — and the second requires a documented position.

**Publishing an erasure event** is what makes downstream systems act:

```java
EventBus.publish(new Data_Subject_Erased__e(
    Contact_Id__c = contactId,
    External_Id__c = contact.ERP_Contact_Id__c,
    Erased_At__c = Datetime.now()
));
```

An external subscriber then erases its own copy. Without that, the data lives on in the ERP and the warehouse. See [[13.19 - Real World Integration Architectures]].

## Retention and deletion

```java
public with sharing class RetentionEnforcementBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id FROM Case
            WHERE Status = 'Closed'
              AND ClosedDate < LAST_N_YEARS:3
              AND Legal_Hold__c = false
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Case> scope) {
        Database.delete(scope, false);
        // permanent, since the recycle bin is still retention
        Database.emptyRecycleBin(scope);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**`Legal_Hold__c` is the field that prevents a compliance problem becoming a legal one.** A record under litigation hold must not be deleted by a retention job, and the flag is what stops it.

**Retention and erasure pull in opposite directions**, and the resolution is a documented policy stating which wins in each case. See [[22.3 - Field Audit Trail and Data Retention]].

## Consent

```
Individual object                 the platform's consent model
Contact Point Type Consent        per channel — email, phone, post
Contact Point Consent
Data Use Purpose                  what the consent covers
Party Consent
```

The model is more granular than most organizations need, and using the parts that map to the actual requirement is better than adopting all of it.

**A simpler pattern that covers many cases:**

```
Contact.HasOptedOutOfEmail        standard
Contact.DoNotCall                 standard
Contact.Marketing_Consent__c      custom, with a date and source
Contact.Consent_Source__c         where and how it was given
Contact.Consent_Date__c
```

**Recording the source and date** is what makes consent defensible — "they consented" is not an answer without evidence of when and how.

**Honouring consent is the enforcement problem.** A marketing integration that queries contacts without filtering on consent is a compliance failure regardless of how carefully the consent was recorded:

```java
// The filter that makes the consent record meaningful
List<Contact> recipients = [
    SELECT Id, Email FROM Contact
    WHERE Marketing_Consent__c = true
      AND HasOptedOutOfEmail = false
      AND Email != null
    WITH USER_MODE
];
```

## Data residency

Where the data physically sits.

**Hyperforce** allows an org to be provisioned in a specific region, which is what satisfies a data residency requirement.

**What still leaves the region:** integrations calling external systems, Event Relay to a cloud provider in another region, backups depending on the arrangement, and support access.

**A data residency requirement is an architecture constraint**, and it needs checking against every integration rather than only against the org's location.

## Breach detection and notification

Most regimes require notification within a deadline — 72 hours under GDPR.

**Detection is the hard part**, and it needs to be built before it is needed:

```
Event Monitoring         ReportExport, ContentTransfer, API row counts
Transaction Security     block or alert on large exports in flight
Login anomalies          unexpected country, unexpected IP
Custom logging           application-level access to sensitive records
```

**Without Event Monitoring**, `LoginHistory` and `SetupAuditTrail` cover a fraction. See [[20.6 - Event Monitoring and Operational Visibility]].

**A 72-hour deadline is not survivable without detection.** An organization that discovers a breach when a customer reports it has already missed it.

## Special categories

Health data, financial data, biometric data, and similar carry stricter requirements.

**HIPAA specifically** requires a Business Associate Agreement with Salesforce, and the org must be configured accordingly. Health Cloud is designed for it; a standard org holding health data without the agreement is a problem regardless of technical controls.

**Payment card data** should not be in Salesforce at all in most designs. Tokenization — storing a reference rather than the card number — is the standard pattern, and it removes the org from PCI scope.

**The general principle:** for special category data, the first question is whether it needs to be in Salesforce. Frequently the answer is a token or a reference, held in a system built for it.

## What a developer should build in

The patterns that make compliance achievable rather than a manual project.

**Data classification on every sensitive field**, so the inventory is queryable.

**An `Erased__c` flag and date**, so anonymized records are identifiable.

**A `Legal_Hold__c` flag** honoured by every retention job.

**An erasure event** published for downstream systems.

**Consent fields with source and date**, and every query that sends anything filtering on them.

**Retention jobs per object**, with the policy stated in the code or its configuration.

**Access logging** for sensitive records, so an access request can be answered.

**No personal data in logs**, application or debug.

**A documented list of what erasure does not reach** — field history, backups, downstream systems — so the gap is known rather than discovered.

## A compliance readiness checklist

```
Inventory
  [ ] Data classification applied to sensitive fields
  [ ] Free text fields identified as unbounded risk
  [ ] Integrated systems receiving personal data listed

Rights
  [ ] Access request produces structured data automatically
  [ ] Erasure anonymizes and cascades to downstream systems
  [ ] What erasure cannot reach is documented
  [ ] Rectification and portability paths exist

Retention
  [ ] A stated period per object, with a reason
  [ ] Retention jobs running and monitored
  [ ] Legal hold honoured

Security
  [ ] Sandbox data masked
  [ ] No personal data in logs
  [ ] Access to sensitive records logged
  [ ] Breach detection in place

Consent
  [ ] Recorded with source and date
  [ ] Every outbound process filters on it
```

## Practical guidance

**Apply data classification** — it is free and it makes the inventory queryable.

**Anonymize rather than delete** where records must be retained.

**Publish an erasure event** so downstream systems act.

**Honour a legal hold flag** in every retention job.

**Filter on consent in every outbound query**, not just when recording it.

**Never log personal data.**

**Build detection before the deadline exists.**

**Question whether special category data belongs in Salesforce at all.**

**Document what erasure cannot reach**, so the gap is known.
