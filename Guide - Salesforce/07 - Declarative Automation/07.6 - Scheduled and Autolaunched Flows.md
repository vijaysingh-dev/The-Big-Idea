# Scheduled and Autolaunched Flows

## Scheduled flows

A scheduled flow runs on a schedule, optionally against a set of records matching a filter. It is flow's answer to Batch Apex for straightforward work.

Configuration: a start date, a time, a frequency (once, daily, or weekly), and optionally an object with entry criteria.

When an object and criteria are specified, **the flow runs once per matching record**, with `$Record` holding that record. This is the important behavioural detail and the source of its main limitation.

## The batch size problem

A scheduled flow processes matching records in batches, and the flow body executes per record. Governor limits apply per batch, not per record, so a Get Records element inside the flow consumes one query per record within a batch.

That works for a few hundred records and does not work for a hundred thousand. Batch Apex, by contrast, hands you 200 records as a collection and lets you query once for all of them.

The practical guidance:

**Scheduled flow is right when:** the record volume is modest (thousands, not hundreds of thousands), the per-record work is simple, and no query per record is needed.

**Batch Apex is right when:** volume is large, work per record needs a query, or the job must handle failures per record with retry. See [[12.4 - Batch Apex]].

The signal to switch: the scheduled flow starts failing intermittently as data grows, which is exactly the point at which rewriting it is most disruptive. Estimating volume growth at design time avoids it.

## A worked example

Contract renewal generation — the same requirement built with Apex in [[04.11 - Quotes, Orders and Contracts]], here in flow because the volume is small.

```
Start: Scheduled Flow
       Daily at 02:00
       Object: Contract
       Filter: Status = "Activated"
               AND EndDate = NEXT_N_DAYS:120
               AND Renewal_Opportunity__c = null

Get Records: Account where Id = {!$Record.AccountId}

Create Records: Opportunity
       AccountId       = {!$Record.AccountId}
       Name            = {!accountRecord.Name} & " - Renewal " & TEXT(YEAR({!$Record.EndDate}))
       StageName       = "Qualification"
       CloseDate       = {!$Record.EndDate}
       Amount          = {!$Record.Annual_Value__c}
       Type            = "Renewal"
       OwnerId         = {!$Record.OwnerId}
       Source_Contract__c = {!$Record.Id}
       → store the new Id in {!newOpportunityId}

Update Records: Contract
       Id = {!$Record.Id}
       Renewal_Opportunity__c = {!newOpportunityId}
```

The `Renewal_Opportunity__c = null` filter in the entry criteria is what makes the job **idempotent** — running twice does not create duplicate renewal opportunities. Building that in from the start is the difference between a scheduled job you can rerun safely and one that requires cleanup after every failure.

The Get Records on Account is the weakness. It runs once per contract, so at 3,000 contracts due for renewal it consumes 3,000 queries across the batches. Fine at this volume, and the thing that would push it to Apex at ten times the scale.

## Scheduled paths on record-triggered flows

Worth distinguishing, because they are often confused.

A **scheduled flow** runs on a clock against a query. It asks "which records match right now".

A **scheduled path** on a record-triggered flow is scheduled per record when the trigger fires, relative to the record's own dates. It asks "do something to *this* record later". See [[07.3 - Record-Triggered Flows]].

The choice: if the timing is relative to something on the record, use a scheduled path. If it is a periodic sweep, use a scheduled flow.

A scheduled path is generally more efficient, because it schedules only the records that need it rather than querying everything daily.

## Autolaunched flows

An autolaunched flow has no screens and no trigger. It runs when something calls it.

Callers:

- Another flow, as a **subflow**
- Apex, through the `Flow.Interview` class
- A record-triggered flow's action
- A platform event subscription
- The REST API
- A custom button or action configured to launch it
- Agentforce, as an agent action

This is the reusable building block, and it is what makes a flow library possible rather than a collection of duplicated logic.

## Calling a flow from Apex

```java
public with sharing class ClaimAssessmentService {

    public static Map<String, Object> assess(Id claimId, Decimal requestedAmount) {
        Map<String, Object> inputs = new Map<String, Object>{
            'claimId' => claimId,
            'requestedAmount' => requestedAmount
        };

        Flow.Interview.Assess_Warranty_Claim assessment =
            new Flow.Interview.Assess_Warranty_Claim(inputs);
        assessment.start();

        return new Map<String, Object>{
            'approved' => assessment.getVariableValue('isApproved'),
            'approvedAmount' => assessment.getVariableValue('approvedAmount'),
            'reason' => assessment.getVariableValue('assessmentReason')
        };
    }
}
```

The class name is `Flow.Interview.<Flow_API_Name>`. Input variables must be marked **Available for Input**, and outputs **Available for Output**, or they are invisible to the caller.

A caution worth stating: **this couples Apex to a flow that an administrator can change.** A flow renamed or a variable removed breaks the Apex at compile time, which is at least a loud failure. A flow whose *logic* changes breaks the Apex silently. Where Apex depends on a flow, both should be treated as one unit under change control.

The more common direction — flow calling Apex — is generally safer and is covered in [[07.9 - Invocable Apex and Flow-Apex Interop]].

## Platform event-triggered flows

A flow that runs when a platform event is published. The declarative subscriber.

```
Start: Platform Event-Triggered
       Event: Escalation_Notification__e

Get Records: Case where Id = {!$Record.Case_Id__c}

Decision: Escalation level
    Level 1 → Create custom notification to the support manager
    Level 2 → Create notification to the service director
              Create Task for follow-up
    Level 3 → Action: post to Slack via an invocable Apex method
```

This pairs with the escalation batch in [[05.4 - Escalation Rules]], which publishes the event. The benefit of that split: the batch job stays fast and limit-bounded, and the notification work happens in a separate transaction with its own limits and its own retry behaviour.

The behaviours to know: event-triggered flows run **asynchronously**, as the Automated Process user by default, and event delivery is at-least-once, so the flow must tolerate being run twice for the same event. See [[12.8 - Platform Events]].

## Testing and monitoring

Neither scheduled nor autolaunched flows have a user watching when they fail, which makes monitoring the difference between working automation and silently broken automation.

**Scheduled jobs** appear in Setup and are queryable:

```sql
SELECT Id, CronJobDetail.Name, State, NextFireTime, PreviousFireTime, TimesTriggered
FROM CronTrigger
ORDER BY NextFireTime
```

**Failed interviews** are visible in Setup and queryable through `FlowInterview`.

**Error emails** go to the flow's last modifier by default, which is almost never the right recipient. Setting a monitored address in Process Automation Settings is the single most important configuration step for unattended flows.

Beyond that, the pattern used by mature orgs is a **custom log object** written by a fault path, so failures are queryable, reportable, and visible on a dashboard rather than sitting in someone's inbox. See [[20.5 - Custom Logging Frameworks]].

## Practical guidance

**Make scheduled flows idempotent.** Filter out records already processed, so a rerun is safe.

**Estimate volume growth.** A scheduled flow that works at 3,000 records fails at 300,000, and the rewrite happens under pressure.

**Prefer scheduled paths to scheduled flows** when the timing is relative to a record's own dates.

**Mark input and output variables explicitly** on autolaunched flows, or callers cannot see them.

**Route error notifications to a monitored address**, and log failures to a custom object.

**Treat Apex calling a flow as coupled.** Both change together.
