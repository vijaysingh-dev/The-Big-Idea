# Enums and Constants

## Enums

A fixed set of named values, checked at compile time.

```java
public enum ClaimStatus {
    SUBMITTED,
    UNDER_REVIEW,
    AWAITING_EVIDENCE,
    APPROVED,
    REJECTED,
    CLOSED
}
```

```java
public enum ApprovalTier { MANAGER, DIRECTOR, EXECUTIVE }
```

Enums can be declared at the top level in their own file, or nested inside a class. Top level is preferable when several classes use them.

## Why they matter

The alternative is string literals, and the difference is compile-time safety.

```java
// Typo compiles, fails at runtime or silently does nothing
if (claim.Status__c == 'Aproved') { }

// Typo does not compile
if (status == ClaimStatus.APROVED) { }
```

With `switch on`, the compiler also tells you when a new enum value is unhandled, which is the strongest argument for using them in branching logic.

```java
public static ApprovalTier tierFor(Decimal amount) {
    if (amount == null) {
        return ApprovalTier.MANAGER;
    }
    return amount > 500000 ? ApprovalTier.EXECUTIVE
         : amount > 100000 ? ApprovalTier.DIRECTOR
         : ApprovalTier.MANAGER;
}

public static Id approverFor(ApprovalTier tier, String region) {
    switch on tier {
        when EXECUTIVE { return executiveApprover(region); }
        when DIRECTOR  { return directorApprover(region); }
        when MANAGER   { return managerApprover(region); }
        when else      { return null; }
    }
}
```

## Enum methods

```java
ClaimStatus status = ClaimStatus.UNDER_REVIEW;

status.name();                     // 'UNDER_REVIEW'
status.ordinal();                  // position, zero-based
ClaimStatus.values();              // List<ClaimStatus> of all values
```

Converting from a string is the operation you need constantly, since picklist values arrive as strings:

```java
public static ClaimStatus fromPicklist(String value) {
    if (String.isBlank(value)) {
        return null;
    }
    String normalized = value.toUpperCase().replace(' ', '_');
    for (ClaimStatus status : ClaimStatus.values()) {
        if (status.name() == normalized) {
            return status;
        }
    }
    return null;
}
```

There is no built-in `valueOf` for enums in Apex, which is a real gap. The loop above is the standard workaround, and caching the mapping in a static Map is worth it if it runs per record:

```java
private static Map<String, ClaimStatus> statusByName;

private static Map<String, ClaimStatus> statusMap() {
    if (statusByName == null) {
        statusByName = new Map<String, ClaimStatus>();
        for (ClaimStatus s : ClaimStatus.values()) {
            statusByName.put(s.name(), s);
        }
    }
    return statusByName;
}
```

## The picklist mismatch problem

This is the practical difficulty with enums in Apex, and it is worth being clear about.

Enum values cannot contain spaces or hyphens. Picklist API names frequently do — `Under Review`, `Closed - Won`, `Awaiting Customer`.

Three approaches:

**Normalize on conversion**, as above — uppercase and replace spaces with underscores. Works when the mapping is mechanical, and breaks the moment a picklist value contains a character that does not map cleanly.

**An explicit mapping**, which is more verbose and more robust:

```java
public with sharing class ClaimStatusMapper {

    private static final Map<String, ClaimStatus> BY_API_NAME = new Map<String, ClaimStatus>{
        'Submitted'         => ClaimStatus.SUBMITTED,
        'Under Review'      => ClaimStatus.UNDER_REVIEW,
        'Awaiting Evidence' => ClaimStatus.AWAITING_EVIDENCE,
        'Approved'          => ClaimStatus.APPROVED,
        'Rejected'          => ClaimStatus.REJECTED,
        'Closed'            => ClaimStatus.CLOSED
    };

    private static final Map<ClaimStatus, String> TO_API_NAME = buildReverse();

    public static ClaimStatus fromApiName(String value) {
        return BY_API_NAME.get(value);
    }

    public static String toApiName(ClaimStatus status) {
        return TO_API_NAME.get(status);
    }

    private static Map<ClaimStatus, String> buildReverse() {
        Map<ClaimStatus, String> reverse = new Map<ClaimStatus, String>();
        for (String apiName : BY_API_NAME.keySet()) {
            reverse.put(BY_API_NAME.get(apiName), apiName);
        }
        return reverse;
    }
}
```

Centralizing the mapping in one class means a picklist value change is one edit. Scattering `'Under Review'` through fifteen classes means fifteen.

**Skip enums for picklist values entirely** and use string constants instead. This is what many Apex codebases do, and it is a defensible choice given the friction above.

## String constants

```java
public with sharing class ClaimConstants {

    public static final String STATUS_SUBMITTED = 'Submitted';
    public static final String STATUS_UNDER_REVIEW = 'Under Review';
    public static final String STATUS_APPROVED = 'Approved';
    public static final String STATUS_REJECTED = 'Rejected';
    public static final String STATUS_CLOSED = 'Closed';

    public static final Set<String> OPEN_STATUSES = new Set<String>{
        STATUS_SUBMITTED, STATUS_UNDER_REVIEW
    };

    public static final Set<String> TERMINAL_STATUSES = new Set<String>{
        STATUS_APPROVED, STATUS_REJECTED, STATUS_CLOSED
    };

    public static final String RT_TECHNICAL = 'Technical_Support';
    public static final String RT_WARRANTY = 'Warranty_Claim';
}
```

The value is that a renamed picklist value is one edit rather than a search across the codebase — and a search that will miss the occurrences inside string concatenation.

Grouping related values into sets is what makes the constants genuinely useful rather than merely tidy:

```java
if (ClaimConstants.OPEN_STATUSES.contains(claim.Status__c)) { }
```

`final` on a collection prevents reassignment, not mutation. `OPEN_STATUSES` above can still have values added at runtime, which is a small hazard worth knowing about and rarely a practical problem.

## Reading picklist values from the schema

Where the set of values must reflect what the org actually has, read the describe rather than hardcoding:

```java
public with sharing class PicklistService {

    public static List<Map<String, String>> activeValues(String objectName, String fieldName) {
        List<Map<String, String>> options = new List<Map<String, String>>();

        Schema.DescribeFieldResult describe = SchemaCache.fields(objectName)
            .get(fieldName.toLowerCase())
            .getDescribe();

        for (Schema.PicklistEntry entry : describe.getPicklistValues()) {
            if (entry.isActive()) {
                options.add(new Map<String, String>{
                    'value' => entry.getValue(),
                    'label' => entry.getLabel()
                });
            }
        }
        return options;
    }
}
```

`getValue()` returns the API name; `getLabel()` returns the translated label. A component populating a picklist should send both and display the label.

Describe calls are expensive, so cache them ([[09.8 - Static Members and Class Level State]]). Better still, the `getPicklistValues` wire adapter in a Lightning Web Component reads them without Apex at all. See [[14.10 - Calling Apex - Wire vs Imperative]].

## Constants versus Custom Metadata

The decision worth making deliberately.

**Apex constants** are right for values that are genuinely part of the code — picklist API names, record type developer names, internal keys. Changing them means changing code, and that is appropriate because the code depends on them.

**Custom Metadata** is right for values the business owns — thresholds, routing rules, rates, feature toggles. Changing them should not require a deployment.

```java
// Code-owned: a picklist API name the logic branches on
public static final String STATUS_APPROVED = 'Approved';

// Business-owned: a threshold that may change quarterly
Decimal threshold = Approval_Threshold__mdt.getInstance('India').Auto_Approve_Limit__c;
```

Putting a business threshold in an Apex constant means a release cycle every time finance changes it. Putting a picklist API name in Custom Metadata is indirection with no benefit. See [[17.1 - Custom Metadata Types]] and [[18.10 - Custom Metadata Driven Architecture]].

## Enums in practice

Where enums earn their place in Apex, given the picklist friction:

**Internal state machines** with no picklist counterpart — job phases, retry outcomes, validation severity levels.

**Method parameters** where a boolean would be ambiguous:

```java
// Unreadable at the call site
processClaims(claims, true, false);

// Self-documenting
processClaims(claims, ValidationMode.STRICT, NotificationMode.SUPPRESS);
```

**Return values** classifying an outcome:

```java
public enum SyncOutcome { SUCCESS, RETRYABLE_FAILURE, PERMANENT_FAILURE }
```

That last one is genuinely useful — an integration returning an enum rather than a boolean lets the caller distinguish a transient failure worth retrying from a permanent one worth logging. See [[13.17 - Error Handling, Retries and Idempotency]].

## Practical guidance

**Never scatter picklist string literals through the codebase.** Constants or a mapper class.

**Group related constants into sets** so membership tests read cleanly.

**Use enums for internal state and for method parameters** where a boolean would be opaque.

**Centralize picklist-to-enum mapping** in one class if you use enums for picklist values.

**Use `switch on` with enums** so the compiler flags unhandled cases.

**Put business-owned values in Custom Metadata**, code-owned values in constants.

**Read picklist values from the describe** where the UI must reflect the org, and cache the result.
