# ASGI and How Uvicorn Serves a Request

#backend #python #asgi #fastapi

> **In one line:** ASGI is a three-argument contract — a dict describing the connection, a function to receive messages, and a function to send them. Everything from uvicorn to FastAPI to your middleware is built on those three things.

---

## The Idea

A web server speaks HTTP. Your framework speaks Python. Something has to define the boundary.

**WSGI** did this for synchronous Python: one function, called with the request, returning the response. Simple, and permanently unable to do WebSockets, streaming, or concurrency.

**ASGI** is the async replacement. The contract is one function:

```python
async def app(scope, receive, send):
    ...
```

| Argument | What it is |
|---|---|
| `scope` | A dict describing this connection — type, path, headers, client |
| `receive` | An async function you call to get the next incoming message |
| `send` | An async function you call to push a message out |

That is the entire specification. Everything else is convention.

---

## The Smallest ASGI App

```python
async def app(scope, receive, send):
    assert scope["type"] == "http"

    await send({
        "type": "http.response.start",
        "status": 200,
        "headers": [(b"content-type", b"text/plain")],
    })
    await send({
        "type": "http.response.body",
        "body": b"hello",
    })
```

```bash
uvicorn app:app
```

That is a working web application. No framework. FastAPI, Starlette, Django and Litestar are all elaborate ways of producing these same `send` calls.

### The scope dict

```python
{
    "type": "http",
    "asgi": {"version": "3.0", "spec_version": "2.3"},
    "http_version": "1.1",
    "method": "POST",
    "scheme": "https",
    "path": "/documents/42",
    "raw_path": b"/documents/42",
    "query_string": b"limit=10",
    "root_path": "",
    "headers": [(b"host", b"api.local"), (b"content-type", b"application/json")],
    "client": ("10.0.0.5", 51234),
    "server": ("10.0.0.9", 8000),
    "state": {},
}
```

⚠️ **Headers are a list of byte tuples, not a dict.** Deliberately — HTTP allows repeated headers, and a dict would silently lose them. This matters for `Set-Cookie` and `Forwarded`, and it is where naive middleware goes wrong.

`scope["state"]` is a per-connection dict you can use to pass data between middleware without global state.

### Message types

**HTTP:**

| Direction | Message | Meaning |
|---|---|---|
| receive | `http.request` | A chunk of the request body. `more_body` says if more is coming |
| receive | `http.disconnect` | The client went away |
| send | `http.response.start` | Status and headers. Once only |
| send | `http.response.body` | A chunk of the response. `more_body` for streaming |

**WebSocket:**

| Direction | Message |
|---|---|
| receive | `websocket.connect`, `websocket.receive`, `websocket.disconnect` |
| send | `websocket.accept`, `websocket.send`, `websocket.close` |

**Lifespan** — startup and shutdown of the app itself:

| Direction | Message |
|---|---|
| receive | `lifespan.startup`, `lifespan.shutdown` |
| send | `lifespan.startup.complete`, `lifespan.shutdown.complete` |

This is what FastAPI's `lifespan` context manager is built on. Pools are created on startup and closed on shutdown through these messages.

## The Full Path of One Request

This is the trace worth knowing by heart.

```
1.  Kernel      TCP packet arrives, socket becomes readable
2.  Loop        epoll wakes, calls uvicorn's data_received
3.  uvicorn     h11/httptools parses bytes into a request
4.  uvicorn     builds the scope dict
5.  uvicorn     creates a Task running app(scope, receive, send)
6.  Starlette   middleware stack, outermost first
7.  Starlette   router matches the path, extracts params
8.  FastAPI     resolves dependencies, validates with Pydantic
9.  YOUR CODE   the endpoint function finally runs
10. FastAPI     serializes the return value to JSON
11. Starlette   Response.__call__ → send(response.start), send(response.body)
12. uvicorn     turns messages into HTTP bytes
13. Kernel      bytes written to the socket
14. uvicorn     keep-alive: reset and wait for the next request
```

Steps 6–10 are usually 60–80% of the framework overhead. Steps 1–5 and 11–14 are the server.

### Where the body is read

```python
@app.post("/upload")
async def upload(request: Request):
    body = await request.body()      # THIS is where receive() is called
```

The body is not in `scope`. It arrives as `http.request` messages, and only when you ask.

⚠️ **If you never read the body, the bytes sit in the socket buffer.** With keep-alive, the next request on that connection then starts parsing at the wrong offset. Servers handle this by draining or closing, but the cost is real — an endpoint that rejects a request early without reading the body can force a connection close on every call. Symptom: connection churn and TLS handshake cost you cannot explain.

### Streaming responses

```python
from starlette.responses import StreamingResponse

async def generate():
    for chunk in produce():
        yield chunk

@app.get("/stream")
async def stream():
    return StreamingResponse(generate(), media_type="text/plain")
```

This sends one `http.response.start`, then many `http.response.body` messages with `more_body: True`, then a final one with `more_body: False`. That is exactly the mechanism SSE uses — [[04.2 - Server Sent Events]].

## Middleware

Two kinds, and the difference matters.

### Pure ASGI middleware

```python
class TimingMiddleware:
    def __init__(self, app):
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)

        start = time.perf_counter()

        async def send_wrapper(message):
            if message["type"] == "http.response.start":
                elapsed = time.perf_counter() - start
                message["headers"].append(
                    (b"x-process-time", f"{elapsed:.4f}".encode())
                )
            await send(message)

        await self.app(scope, receive, send_wrapper)
```

Wrapping `send` is the standard technique. It costs almost nothing.

### BaseHTTPMiddleware

```python
class TimingMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        response.headers["x-process-time"] = str(time.perf_counter() - start)
        return response
```

Nicer to write. Meaningfully more expensive.

⚠️ **`BaseHTTPMiddleware` runs your endpoint in a separate task connected by an `anyio` memory stream**, so that `call_next` can hand you a Response object. Consequences:

| Effect | Why it matters |
|---|---|
| Extra task + stream per request | Measurable overhead at high request rates |
| Streaming responses get buffered through the stream | Breaks SSE flushing in some configurations |
| `contextvars` set inside it do not propagate outward | Tracing and request-ID context can be lost |
| Background tasks and exception handling behave subtly differently | Hard-to-diagnose edge cases |

💡 **Use `BaseHTTPMiddleware` for convenience in small apps. Write pure ASGI middleware for anything on the hot path, anything touching streaming, and anything involving context propagation.** This is a real, commonly-hit performance and correctness difference, and knowing it marks you as someone who has read the framework rather than only used it.

## uvicorn Internals

### Startup

```
uvicorn.run()
  → Config: import your app, resolve settings
  → Server.serve()
      → install signal handlers (SIGTERM, SIGINT)
      → run lifespan startup
      → loop.create_server(protocol_factory, host, port)
      → main_loop(): tick every 100ms, check for shutdown
```

With `--workers N`, a supervisor process binds the socket once and forks N children that all `accept()` on it. The kernel distributes connections.

### Per connection

`create_server` makes a new protocol object per connection. That object holds the parser state, the buffer, and the current request's task.

Two HTTP implementations:

| | `h11_impl` | `httptools_impl` |
|---|---|---|
| Parser | h11, pure Python | httptools, C wrapper around Node's parser |
| Speed | Slower | Faster |
| Used when | `uvicorn` plain | `uvicorn[standard]` |

Same behaviour, different speed. `uvicorn[standard]` also brings `uvloop` and `websockets`.

### Backpressure at the connection

```python
# in the protocol, roughly
if len(self.buffer) > HIGH_WATER:
    self.transport.pause_reading()
```

When your app is not consuming the request body fast enough, uvicorn stops reading from the socket. The kernel receive buffer fills, the TCP window shrinks, and the sender slows down.

💡 **This is TCP flow control being used as application backpressure, and it is completely automatic.** It is also why an async server degrades more gracefully than a thread-per-request one: the pushback reaches the client rather than piling up as memory in your process. The mechanism is covered in [[02.4 - Flow Control and Congestion Control]].

## In Production

### Server settings that matter

```bash
uvicorn app:app \
  --workers 4 \
  --limit-concurrency 1000 \
  --limit-max-requests 10000 \
  --timeout-keep-alive 5 \
  --timeout-graceful-shutdown 30 \
  --backlog 2048 \
  --proxy-headers --forwarded-allow-ips='*'
```

| Setting | Why |
|---|---|
| `--limit-concurrency` | Returns 503 above this instead of queueing forever. Load shedding, for free |
| `--limit-max-requests` | Restart a worker after N requests. A blunt but effective fix for slow memory leaks |
| `--timeout-keep-alive` | How long an idle connection is held. Too high wastes file descriptors |
| `--backlog` | Kernel accept queue depth. See [[02.3 - TCP Connection Lifecycle]] |
| `--proxy-headers` | Trust `X-Forwarded-For`. **Only** with `--forwarded-allow-ips` set to your actual proxy, or clients can spoof their IP |

⚠️ **`--limit-concurrency` is underused and it is your cheapest load-shedding mechanism.** Without it, an overloaded worker accepts unlimited work, memory grows, latency grows unbounded, and the health check eventually fails. With it, excess requests get an immediate 503 that a load balancer can retry elsewhere. Fast failure beats slow failure. More in [[11.4 - Backpressure and Load Shedding]].

### uvicorn vs gunicorn+uvicorn workers

| | uvicorn `--workers` | gunicorn with `UvicornWorker` |
|---|---|---|
| Supervision | Basic | Mature: restarts, timeouts, worker recycling |
| Signals | Fine | Better tested |
| In Kubernetes | Recommended | Redundant — K8s already supervises |

In containers, prefer plain uvicorn with one worker per container and let the orchestrator scale. Two layers of process supervision means two places to configure graceful shutdown and two places to get it wrong.

### Where framework overhead goes

Measured on a trivial endpoint, roughly:

```
Raw ASGI app             ~0.05 ms
+ Starlette routing      ~0.15 ms
+ FastAPI DI + Pydantic  ~0.50 ms
+ BaseHTTPMiddleware ×3  ~0.80 ms
```

Under a millisecond total. If your endpoint takes 40ms because of a database query, none of this is worth optimizing.

💡 **It becomes worth optimizing in exactly two cases:** very high request rates on trivial endpoints (a health check hammered by a mesh, a token validation endpoint), and Pydantic validation of large payloads, which is genuinely expensive and grows with payload size. Everywhere else, look at your queries first.

## Codebase

**Repo:** `encode/uvicorn` and `encode/starlette`

**Question to answer:** Follow a single `POST /documents` with a 2MB body from the socket read to the response bytes. Name every object created. Then answer: at what point is the request body actually read from the kernel, and what happens if the endpoint returns without reading it?

**Read, in order:**

1. `uvicorn/main.py` and `uvicorn/config.py` — how the app is imported and settings resolved
2. `uvicorn/server.py` — `serve`, `startup`, `main_loop`, `shutdown`. Note the graceful shutdown sequence
3. `uvicorn/protocols/http/httptools_impl.py` — `data_received`, `on_message_begin`, `on_headers_complete`. **This is where the scope is built.** Also find `pause_reading` and note when it is called
4. `uvicorn/protocols/http/h11_impl.py` — the same job with a different parser. Compare the two
5. `uvicorn/lifespan/on.py` — how startup and shutdown messages flow
6. `starlette/applications.py` → `starlette/middleware/errors.py` → `starlette/routing.py` → `starlette/responses.py`

**The most valuable file here is `httptools_impl.py`.** Read the whole thing. It is under 600 lines and it is the complete bridge from TCP bytes to your function.

**Then:** `starlette/middleware/base.py`. Understand *why* `BaseHTTPMiddleware` needs a memory stream and a second task. Once you see it, the whole list of its side effects becomes obvious rather than memorised.

**Size:** 2 sessions.

**Part 1 — See the protocol.** Write an ASGI app that logs the scope and every `receive`/`send` message. Hit it with: a GET, a POST with a body, a chunked upload, a client that disconnects mid-request, and a WebSocket. Save the message transcripts.

Nothing about ASGI stays mysterious after you have read those transcripts.

**Part 2 — A mini framework.** Routing with path params, request parsing, JSON responses, a middleware chain, and exception handling. Under 300 lines. No Starlette.

**Part 3 — Your own server.** Serve your mini framework on the event loop from [[01.4 - Building an Event Loop From Scratch]]. Keep-alive, correct framing, and a graceful shutdown that drains in-flight requests.

This is the moment the whole stack becomes yours: your loop, your server, your framework, your app.

**Part 4 — Measure the layers.** Benchmark: raw ASGI, your framework, Starlette, FastAPI, FastAPI with 3 `BaseHTTPMiddleware`, FastAPI with 3 pure ASGI middleware. Same trivial endpoint. Report requests per second and per-request overhead.

**Part 5 — The middleware trap.** Build an SSE endpoint. Put a `BaseHTTPMiddleware` in front of it. Observe what happens to chunk timing. Then swap to pure ASGI middleware and observe again.

Then set a `contextvar` inside a `BaseHTTPMiddleware` and try to read it in the endpoint, and vice versa. Document exactly what propagates and what does not.

**Part 6 — Load shedding.** Run with and without `--limit-concurrency`. Overload both with k6. Chart p99 and error rate over time.

Without the limit: latency climbs without bound, memory grows, health checks fail. With it: latency stays flat and excess requests get an immediate 503. Two very different failure shapes, and one of them is survivable.

**Done when:**
- Your message transcripts cover all five scenarios in part 1
- Your framework serves on your own server with working keep-alive
- The part 4 table has all six rows with your own numbers
- Part 5 documents the streaming and contextvar differences concretely
- The part 6 chart shows bounded versus unbounded failure
