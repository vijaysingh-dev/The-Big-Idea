# Virtual Memory

#backend #os #memory #linux

> **In one line:** Every process gets its own private, enormous, made-up address space. The kernel and the CPU translate it to real RAM one 4 KB page at a time, lazily, and that laziness explains copy-on-write, `mmap`, page faults and most memory numbers you will ever misread.

---

## The Idea

When your Python process reads address `0x7f3a2c001000`, that is not a location in RAM. It is a **virtual address**. The CPU's memory management unit (MMU) translates it to a **physical address** using a table the kernel maintains for that process.

This one trick buys four things:

| Benefit | How |
|---|---|
| **Isolation** | Process A's address `0x1000` and process B's `0x1000` map to different RAM. Neither can see the other. |
| **Simplicity** | Every process thinks it has a huge, empty, contiguous space starting near zero |
| **Laziness** | Memory is not backed by RAM until it is touched. Asking for 1 GB costs nothing until you write to it. |
| **Sharing** | Two processes can map the same physical page: shared libraries, `fork` copy-on-write, shared memory |

---

## Pages and Page Tables

Memory is managed in fixed-size **pages**, usually 4 KB. The kernel keeps a **page table** per process mapping virtual pages to physical frames.

```
Virtual address (x86-64, 48 bits used)
┌────────┬────────┬────────┬────────┬──────────────┐
│ L4 idx │ L3 idx │ L2 idx │ L1 idx │ offset (12b) │
└───┬────┴───┬────┴───┬────┴───┬────┴──────┬───────┘
    ▼        ▼        ▼        ▼           │
  [PML4] → [PDPT] → [PD]  →  [PT] → physical frame + offset
   four memory lookups to translate one address
```

Four memory lookups for every memory access would be unbearably slow. So the CPU caches recent translations in the **TLB** (translation lookaside buffer). A TLB hit is nearly free. A miss costs a page-table walk, around 10–100 ns.

💡 **Huge pages** (2 MB or 1 GB instead of 4 KB) mean far fewer TLB entries for big memory regions. Databases and JVMs with large heaps use them. Linux can do this automatically with **Transparent Huge Pages (THP)**, but THP's background compaction causes latency spikes. Redis, MongoDB and many Postgres guides tell you to set THP to `madvise` or `never`.

## What a Process's Address Space Looks Like

```bash
cat /proc/$PID/maps        # every mapped region
pmap -x $PID               # same, with sizes
```

```
High addresses
┌──────────────────────────────┐
│ kernel (not accessible)      │
├──────────────────────────────┤
│ stack (main thread)          │  grows down
│   ↓                          │
│                              │
│ mmap region                  │  shared libs (libc, libpython),
│   thread stacks (8 MB each)  │  mmap'd files, big malloc()s,
│   anonymous mappings         │  Python arenas
│   ↑                          │
│ heap (brk)                   │  grows up — small malloc()s
├──────────────────────────────┤
│ .bss / .data                 │  globals
│ .text                        │  program code (read-only, shared)
└──────────────────────────────┘
Low addresses
```

## Page Faults: Laziness in Action

A **page fault** happens when a process touches a virtual page that has no valid mapping right now. The CPU traps into the kernel, which decides what to do:

| Fault type | Cause | Cost | Example |
|---|---|---|---|
| **Minor fault** | The page is in RAM or can be made instantly: first touch of fresh memory, copy-on-write | ~0.1–1 µs | `malloc` then the first write; a child process writing after `fork` |
| **Major fault** | The page must be read from disk | ~100 µs (SSD) to 10 ms (HDD) | First read of an `mmap`ed file, or a page that was swapped out |
| **Invalid** | The address is not mapped at all | The process dies | `SIGSEGV`: segmentation fault |

```bash
ps -o pid,min_flt,maj_flt,cmd -p $PID
pidstat -r -p $PID 1       # minflt/s, majflt/s
```

⚠️ **A steady stream of major faults on a server is a red flag.** It means the working set does not fit in RAM and the process is reading pages back from disk on demand. Latency becomes disk latency.

## Overcommit: The Kernel Says Yes to Everything

By default Linux **overcommits**: `malloc(10 GB)` on a 4 GB machine usually succeeds. The kernel hands out address space, not RAM, betting that you will not touch it all.

```bash
cat /proc/sys/vm/overcommit_memory
# 0 = heuristic (default): refuse only obviously absurd requests
# 1 = always say yes
# 2 = strict: refuse if commitments exceed swap + RAM × overcommit_ratio
```

The consequence: **allocation almost never fails on Linux. Instead, when the bet loses, the OOM killer picks a process and kills it.** Your code does not get a `MemoryError`; it gets `SIGKILL`. See [[02.6 - Memory in Practice]].

💡 Redis tells you to set `vm.overcommit_memory = 1`. A `BGSAVE` fork doubles the virtual commitment instantly even though almost nothing is copied. Under heuristic mode the fork can fail with `Cannot allocate memory`.

## mmap: Files as Memory

`mmap` maps a file (or anonymous memory) directly into the address space. Reading the memory reads the file, via page faults and the page cache, with no `read()` calls.

```python
import mmap

with open("big.bin", "rb") as f:
    mm = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)
    header = mm[:16]            # page fault → kernel loads that page from the page cache or disk
    idx = mm.find(b"needle")    # scans as if it were bytes in memory
```

| Who uses mmap | Why |
|---|---|
| Every program | Shared libraries (`libc.so`, `libpython.so`) are mmapped and shared between all processes |
| SQLite, LMDB, older MongoDB | The database file *is* the memory. The OS page cache is the buffer pool. |
| Kafka (index files), Lucene | Fast random access to on-disk indexes |
| numpy `memmap`, Arrow, safetensors | Work with arrays larger than RAM; load model weights with no copy |
| glibc `malloc` | Large allocations (over 128 KB by default) become their own anonymous `mmap` |

⚠️ **mmap is not free speed.** Errors (disk full, file truncated) arrive as `SIGBUS` instead of an exception, and you give up control of eviction to the kernel. This is why Postgres and most serious databases manage their own buffer pool with plain `read`/`write`. The paper "Are You Sure You Want to Use MMAP in Your DBMS?" makes the case in full.

## Copy-on-Write, Revisited

Now the mechanism behind `fork` in [[02.2 - Processes]] is clear:

1. `fork` copies the parent's page tables, not its pages.
2. Every writable page is marked read-only in **both** processes and shared.
3. A write by either side causes a minor page fault. The kernel copies that one page, gives the writer a private copy, and marks it writable.

Same trick, other places: Redis `BGSAVE`, Python's `multiprocessing` with `fork`, container image layers (at the filesystem level), and ZFS/Btrfs snapshots.

---

## Swap

Swap is disk space the kernel can move rarely used anonymous pages into, to free RAM.

| Setting | Effect |
|---|---|
| Swap on, low `vm.swappiness` | The kernel prefers dropping page cache over swapping your process |
| Swap on, under memory pressure | Latency becomes terrible before anything gets killed. The service is "up" but useless. |
| Swap off (the Kubernetes default for years) | Pressure turns straight into OOM kills. Failures are fast and loud. |

For latency-sensitive services, a fast clean death is usually better than a slow swap-thrashing one. Kubernetes added swap support (beta in 1.28, then GA), but most clusters still run without it.

## In Production

| Question | Answer |
|---|---|
| "My process has a VSZ of 20 GB and the box has 8 GB. Is that bad?" | No. VSZ is address space, mostly untouched. Look at RSS or PSS. |
| "Why did Redis fail to fork for BGSAVE?" | `overcommit_memory=0` refused the doubled commitment. Set it to 1. |
| "Why is latency spiky on the database host?" | Check THP: `cat /sys/kernel/mm/transparent_hugepage/enabled` |
| "Why did my first query after deploy take 2 s?" | Major faults: the index or mmapped file was not in the page cache yet. Cold start. |
