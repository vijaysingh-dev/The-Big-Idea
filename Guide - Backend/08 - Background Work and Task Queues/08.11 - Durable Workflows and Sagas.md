# Durable Workflows and Sagas

#backend #distributed-systems #workflows

> **In one line:** When work spans several systems and a failure halfway must be undone, you need either a persisted state machine you drive yourself or an engine that makes crash recovery ordinary — and the hard part is that compensation can also fail.

---

## The Idea

```
Place an order:
  1. Reserve inventory      (inventory service)
  2. Charge the card        (payment provider)
  3. Arrange shipping       (logistics API)
  4. Send confirmation      (email provider)
```

⚠️ **There is no transaction spanning four systems.** If step 3 fails, steps 1 and 2 have already happened and must be undone.

A chain of tasks does not solve this:

```python
chain(reserve.s(order_id), charge.s(), ship.s(), notify.s())()
```

| Missing | |
|---|---|
| Compensation | No way to express "if 3 fails, undo 2 and 1" |
| Visibility | Where is order 4271 right now? |
| Crash recovery | A worker dying between steps loses the position |
| Timeouts across steps | No overall deadline |
| Human intervention | No way to pause and resume |

💡 **The distinguishing signal: the work has state that persists across steps, and a failure requires undoing earlier steps.** That is a workflow, not a chain of tasks.

---

## The Saga Pattern

A sequence of local transactions, each with a compensating action.

```
T1 → T2 → T3 → T4
 ↓    ↓    ↓
C1 ← C2 ← C3        compensate in reverse on failure
```

| Step | Compensation |
|---|---|
| Reserve inventory | Release the reservation |
| Charge the card | Refund |
| Arrange shipping | Cancel the shipment |
| Send confirmation | **Send a cancellation email** — you cannot unsend |

⚠️ **Compensation is not rollback.** A refund is a new transaction, visible in the customer's statement. A cancellation email is an additional message, not the removal of one. **The system is eventually consistent, not atomic**, and the user-visible effects of the failed attempt remain.

💡 **Design compensations to be semantically meaningful rather than pretending nothing happened.** "Your order was cancelled and refunded" is honest; silently reversing state and hoping nobody noticed is not.

### Two shapes

**Choreography** — each step emits an event, the next reacts:

```
OrderPlaced → [inventory] → InventoryReserved → [payment] → PaymentCharged → ...
                                                     ↓ failed
                                             PaymentFailed → [inventory compensates]
```

| | |
|---|---|
| **Good** | No central coordinator, services stay decoupled |
| **Bad** | **No single place shows the state.** Hard to answer "where is order 4271" |

**Orchestration** — a coordinator drives the steps:

```python
async def process_order(order_id: str):
    state = await load_or_create(order_id)
    for step in STEPS:
        if step.name in state.completed:
            continue
        try:
            result = await step.execute(state)
            await record_completed(order_id, step.name, result)
        except Exception:
            await compensate(order_id, state)
            raise
```

| | |
|---|---|
| **Good** | One place holds the state. Visible, debuggable, testable |
| **Bad** | The coordinator is a dependency and a potential bottleneck |

💡 **Orchestration is almost always the right choice for business processes.** The ability to answer "what is the state of this order" from one query is worth more than the decoupling choreography offers, and the coordinator is not a real bottleneck for order-rate work.

**Choreography suits event-driven fan-out** where nobody needs the aggregate state ([[10.3 - Communication Patterns]]).

## Rolling Your Own

The persisted state machine, and it is not that much code.

```sql
CREATE TABLE workflow_runs (
    id            uuid PRIMARY KEY,
    workflow      text NOT NULL,
    entity_id     text NOT NULL,
    state         text NOT NULL,       -- running | compensating | completed | failed
    current_step  text,
    context       jsonb NOT NULL DEFAULT '{}',
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workflow, entity_id)
);

CREATE TABLE workflow_steps (
    run_id     uuid REFERENCES workflow_runs(id) ON DELETE CASCADE,
    step       text NOT NULL,
    state      text NOT NULL,          -- completed | compensated | failed
    result     jsonb,
    attempts   int NOT NULL DEFAULT 0,
    completed_at timestamptz,
    PRIMARY KEY (run_id, step)
);
```

```python
@dataclass
class Step:
    name: str
    execute: Callable[[Context], Awaitable[dict]]
    compensate: Callable[[Context, dict], Awaitable[None]] | None = None
    retryable: tuple[type[Exception], ...] = (ConnectionError, TimeoutError)
    max_attempts: int = 3


async def run_workflow(run_id: UUID, steps: list[Step]):
    run = await load_run(run_id)

    for step in steps:
        if await step_completed(run_id, step.name):
            continue                                  # ← resume point

        try:
            result = await execute_with_retry(step, run.context)
            await mark_step_completed(run_id, step.name, result)
            run.context.update(result)
        except Exception as e:
            await mark_step_failed(run_id, step.name, e)
            await compensate(run_id, steps, run.context)
            return

    await mark_run_completed(run_id)


async def compensate(run_id: UUID, steps: list[Step], ctx: Context):
    await set_state(run_id, "compensating")
    completed = await completed_steps(run_id)

    for step in reversed(steps):
        if step.name not in completed or step.compensate is None:
            continue
        try:
            await step.compensate(ctx, completed[step.name])
            await mark_step_compensated(run_id, step.name)
        except Exception:
            await set_state(run_id, "compensation_failed")
            alert_human(run_id, step.name)            # ⚠️ needs intervention
            return

    await set_state(run_id, "failed")
```

💡 **The `if await step_completed(...): continue` line is what makes this crash-recoverable.** Restart the workflow from the beginning and it skips what is already done. **That is the same replay idea Temporal implements, done manually.**

⚠️ **Each step's completion must be recorded atomically with its effect where possible** ([[07.5 - Idempotency Keys and Deduplication]]). If the effect is external, use the two-phase pattern with an idempotency key passed downstream.

## When Compensation Fails

The case that separates a real implementation from a demonstration.

```
Step 2 (charge) succeeded
Step 3 (ship) failed
Compensating step 2 (refund) → the payment provider is down
```

⚠️ **You are now stuck in an inconsistent state that no automatic mechanism can resolve.**

| Response | |
|---|---|
| **Retry the compensation** | With backoff, for a long time. Usually works |
| **Escalate to a human** | With full context, after N attempts |
| **Record and reconcile later** | A job that periodically retries stuck compensations |
| **Design so it cannot fail** | Compensations that are local database writes always succeed |

💡 **The strongest design move is to order steps so that irreversible operations happen last.** If charging is the final step, there is nothing to compensate when it fails.

```
Reserve inventory  (compensable — local write)
Arrange shipping   (compensable — provider supports cancellation)
Charge the card    (LAST — nothing after it to fail)
```

⚠️ **This is not always possible**, and when it is not, you need the human escalation path and you need to have tested it.

**A `compensation_failed` state with an alert is not a failure of design — it is the design.** Some inconsistencies genuinely require a human decision.

## Temporal

The engine that makes all of the above ordinary control flow.

```python
@workflow.defn
class OrderWorkflow:
    @workflow.run
    async def run(self, order_id: str) -> str:
        reserved = await workflow.execute_activity(
            reserve_inventory, order_id,
            start_to_close_timeout=timedelta(minutes=2),
            retry_policy=RetryPolicy(maximum_attempts=5),
        )
        try:
            shipment = await workflow.execute_activity(arrange_shipping, order_id, ...)
            try:
                await workflow.execute_activity(charge_payment, order_id, ...)
            except ActivityError:
                await workflow.execute_activity(cancel_shipment, shipment, ...)
                raise
        except ActivityError:
            await workflow.execute_activity(release_inventory, reserved, ...)
            raise

        await workflow.execute_activity(send_confirmation, order_id, ...)
        return "completed"
```

💡 **That is a `try/except` and it is a durable saga.** The process can die at any point; on recovery Temporal replays the workflow function, feeding recorded results back for completed activities, and execution continues from exactly where it stopped ([[08.10 - Celery vs Dramatiq vs arq vs Temporal]]).

### What it removes

| You no longer write | |
|---|---|
| State persistence | Temporal records it |
| Resume logic | Replay handles it |
| Retry per step | `RetryPolicy` per activity |
| Timeout per step | `start_to_close_timeout` |
| Visibility | The UI shows every step, input, output and retry |
| Idempotency for the *workflow* | Workflow ID uniqueness |

### The determinism constraint

⚠️ **Workflow code is replayed, so it must produce the same decisions given the same history.**

```python
# Forbidden in workflow code
datetime.now()          → workflow.now()
random.random()         → workflow.random()
uuid.uuid4()            → workflow.uuid4()
requests.get(...)       → must be an activity
asyncio.sleep(...)      → workflow.sleep(...)
```

💡 **The rule: workflow code orchestrates and makes decisions; activities do things.** Anything touching the outside world is an activity, and activity results are recorded.

⚠️ **Changing workflow code while workflows are running causes replay divergence.** Temporal has `workflow.patched()` for versioning, and it is a real operational discipline:

```python
if workflow.patched("add-fraud-check"):
    await workflow.execute_activity(fraud_check, order_id, ...)
```

**Old workflows replay the old path; new ones take the new path.** This is [[05.13 - Contract Testing and Schema Evolution]] applied to running processes.

## In Production

### Choosing

```
Is it a single step, or independent steps with no shared state?
├── YES → task queue. Do not build a workflow
│
└── NO — multi-step with state
    ├── Does a failure require undoing earlier steps?
    │   ├── NO  → a chain of tasks with a status resource is enough
    │   └── YES → saga
    │        ├── Under ~5 steps, one team, tolerable state table?
    │        │   └── Roll your own orchestrator
    │        └── Many workflows, long durations, or complex compensation?
    │            └── Temporal
    └── Does it run for days, need signals, or need human approval steps?
        └── Temporal
```

⚠️ **Do not build a workflow engine for a three-step pipeline with no compensation.** Conduit's ingestion — fetch, extract, chunk, embed, index — has no compensation requirement, because a failure just means the document is not indexed. **A chain of tasks with a status row is correct** ([[08.1 - Why Background Work Exists]]).

💡 **The signal that changes it: if a partial ingestion leaves the system in a state a user can observe and object to**, you need compensation. If the document simply shows as "failed" and can be retried, you do not.

### Observability

```python
workflow_started_total.labels(workflow=name).inc()
workflow_completed_total.labels(workflow=name, outcome=...).inc()
workflow_duration_seconds.labels(workflow=name).observe(elapsed)
workflow_step_duration_seconds.labels(workflow=name, step=s).observe(elapsed)
workflow_compensations_total.labels(workflow=name, step=s).inc()
workflow_stuck_total.labels(state="compensation_failed").set(count)
```

⚠️ **`workflow_stuck_total` is the metric that must page someone.** A workflow in `compensation_failed` is an inconsistent state that will not resolve itself, and every hour it sits there is an hour a customer's money or inventory is in limbo.

💡 **The operational question a workflow system must answer instantly: "where is order 4271?"** With an orchestrator plus a state table it is one query. With choreography it is a log search across services. **That difference is why orchestration usually wins.**

### Timeouts across the whole workflow

```python
@workflow.run
async def run(self, order_id: str):
    async with asyncio.timeout(3600):        # the whole workflow
        ...
```

⚠️ **A workflow with per-step timeouts but no overall deadline can run forever** — five steps × three retries × a five-minute timeout is over an hour, and a retry loop can extend it indefinitely.

**Set a workflow-level deadline and decide what happens when it expires**: compensate, or escalate.

### Human-in-the-loop

```python
@workflow.run
async def run(self, order_id: str):
    if order.total > 10_000:
        await workflow.wait_condition(lambda: self.approved, timeout=timedelta(days=2))
        if not self.approved:
            await workflow.execute_activity(reject_order, order_id, ...)
            return "rejected"
    ...

@workflow.signal
def approve(self):
    self.approved = True
```

💡 **A workflow that waits two days for a human approval is trivial in Temporal and genuinely hard to build otherwise.** It is one of the clearest cases where the engine earns its operational cost.

### Conduit's position

| Process | Needs a workflow? |
|---|---|
| Document ingestion | **No** — a task chain plus a status row. Failure means "not indexed", which is a state, not an inconsistency |
| Source sync | **No** — periodic and idempotent |
| Export generation | **No** — a single long task with an operation resource |
| **Organisation offboarding** | **Yes** — delete from the database, search index, object storage and cache, with compensation if one fails partway |
| **Plan upgrade with payment** | **Yes** — charge, provision, notify, with compensation on failure |

💡 **Two out of five, and both involve external systems that can fail after money or data has moved.** That is the signal.

**Roll your own for these two** — the state table plus orchestrator above is around 200 lines and Conduit does not have enough workflows to justify a Temporal cluster. **Write down the trigger for reconsidering: a third workflow, or a requirement for long waits and human approval.**

## Codebase

**Repo:** `temporalio/samples-python`, `temporalio/sdk-python`, `eventuate-tram` (docs)

**Question to answer:** In Temporal, trace what happens when a worker crashes mid-workflow — what is recorded, what is replayed, and what is skipped? Then: how does a saga implementation decide compensation order, and what does it do when compensation fails?

**Read, in order:**

1. `temporalio/samples-python/message_passing/` and the saga samples — **the workflow code first**, so you see how ordinary it looks
2. `temporalio/sdk-python/temporalio/worker/_workflow_instance.py` — **the replay mechanism.** How recorded activity results are fed back instead of re-executing. **The answer to the first question**
3. `temporalio/sdk-python/temporalio/workflow.py` — the determinism helpers, and `patched` for versioning
4. `temporalio/sdk-python/temporalio/common.py` — `RetryPolicy`, and how it differs from a task queue's retry
5. **Eventuate Tram Sagas documentation** — a Java saga framework, and the **compensation ordering and failure handling** is well documented. **The answer to the second question**
6. **Microservices.io — Saga pattern** — Chris Richardson's write-up, which is the canonical description

💡 The Temporal replay code is worth real attention. **Once you understand that the workflow function is re-executed from line one on every recovery, with completed activities short-circuited from history**, the determinism rules become obviously necessary rather than arbitrary — and you also understand exactly what your hand-rolled orchestrator is approximating.

**Size:** 2 sessions.

**Part 1 — The naive version fails.** A four-step order process as a Celery chain, no compensation.

Kill the worker between steps 2 and 3. **Inspect the state: inventory reserved, card charged, nothing shipped, no record of where it stopped.**

Then try to write recovery logic for it. **Record how many distinct partial states you have to handle.**

**Part 2 — Build the orchestrator.** The state table plus the engine above. Four steps with compensations.

Test the happy path, then a failure at each step, confirming compensation runs in reverse and the final state is consistent.

**Part 3 — The crash matrix.** Kill the process at every point: before each step, during each step, after each step before recording, and at each point during compensation.

**Roughly 20 crash points.** For each: restart, let it recover, and assert the final state is consistent.

⚠️ **The "after the effect, before recording it" points are the hard ones**, and they are where the two-phase pattern with a downstream idempotency key matters ([[07.5 - Idempotency Keys and Deduplication]]).

**Part 4 — When compensation fails.** Make the refund step fail permanently.

**Confirm the workflow reaches `compensation_failed`** and stops rather than looping.

Then implement: retry with long backoff, escalation with full context after N attempts, and a reconciliation job that periodically retries stuck compensations.

Then measure: how long a stuck workflow sits before a human is alerted, and whether the alert contains enough to act on.

**Part 5 — Ordering to avoid the problem.** Reorder so the irreversible step is last.

**Re-run the crash matrix.** Count how many crash points now require compensation at all.

**Write in `README.md` the general rule** — and note where it could not be applied and why.

**Part 6 — The same saga in Temporal.** Implement it as a Temporal workflow.

**Re-run the crash matrix.** Measure: crash points requiring explicit handling in your code, lines of code, and time to recover.

Then add a two-day human approval step. **Implement it in both** and compare the effort.

**Part 7 — "Where is order 4271?"** Both implementations. Answer the question during: normal execution, mid-compensation, and stuck.

Measure time to answer and what tooling each required.

**Part 8 — The Conduit decision.** Identify every multi-step process in Conduit and apply the decision tree.

For the two that need workflows, implement them with your orchestrator.

**Write the trigger for reconsidering Temporal** and put it in the ADR.

**Done when:**
- The naive chain leaves an unrecoverable state you enumerated
- Your orchestrator survives ~20 crash points with consistent final state
- A permanently-failing compensation escalates with actionable context
- Reordering measurably reduced the crash points needing compensation
- The Temporal comparison quantifies code and crash points eliminated
- You can answer "where is this workflow" in seconds in both implementations
- Conduit's two workflows are implemented, with a written Temporal trigger
