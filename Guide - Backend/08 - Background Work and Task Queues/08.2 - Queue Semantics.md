# Queue Semantics

#backend #queues #distributed-systems

> **In one line:** Every queue makes the same three promises — when a message is acknowledged, how many times it may be delivered, and whether order is preserved — and almost every queue bug comes from assuming a stronger promise than the queue actually makes.

---

## The Idea

```
Producer → [ queue ] → Consumer
```

Four questions determine everything:

| Question | |
|---|---|
| **When is a message removed?** | On delivery, or on acknowledgement |
| **How many times can it be delivered?** | At-most-once, at-least-once |
| **Is order preserved?** | Globally, per key, or not at all |
| **What happens when the consumer dies?** | Lost, or redelivered |

💡 **A queue is a durability and delivery contract, not just a buffer.** Two queues with identical APIs can have completely different semantics, and code written against one will silently misbehave on the other.

---

## Delivery Guarantees

### At-most-once

```
Broker delivers → removes the message immediately
Consumer crashes mid-processing → the message is gone
```

Fast. **Work can be lost.**

Acceptable for: metrics samples, presence updates, cache warming — anything where losing one is invisible.

### At-least-once

```
Broker delivers → holds the message
Consumer processes → acknowledges → broker removes
Consumer crashes before acking → redelivered
```

**Nothing is lost. Some things happen twice.**

💡 **This is what essentially every production queue gives you, and it is the correct default.** The duplicate is your problem to handle, and the mechanism is deduplication ([[07.5 - Idempotency Keys and Deduplication]]).

### Exactly-once

⚠️ **Does not exist as a delivery guarantee.** What systems claiming it actually provide is at-least-once delivery plus deduplication, producing **exactly-once effects**.

**Say it precisely:** *"Exactly-once delivery is impossible over an unreliable network, so you build at-least-once delivery with idempotent handlers, which gives exactly-once effects."*

## Acknowledgement Timing

The single most consequential setting in any queue.

```python
# Ack early — at-most-once
message = await queue.get()
await message.ack()
await process(message)          # ← crash here, message lost

# Ack late — at-least-once
message = await queue.get()
await process(message)
await message.ack()             # ← crash before this, message redelivered
```

⚠️ **Late acking is what you want, and it is not always the default.** Celery's `acks_late` defaults to `False`, meaning a task is acknowledged when the worker receives it — so a worker killed mid-task loses the task entirely.

```python
@app.task(acks_late=True, reject_on_worker_lost=True)
def process_document(doc_id: str): ...
```

💡 **`reject_on_worker_lost` matters as much as `acks_late`.** Without it, a worker killed by the OOM killer or `SIGKILL` may have its message treated as rejected-and-discarded rather than requeued.

### Visibility timeout

The mechanism that makes at-least-once work without a persistent connection.

```
Consumer receives a message
  → the message becomes invisible to other consumers for N seconds
  → consumer acks → deleted
  → consumer does not ack within N seconds → visible again
```

⚠️ **If processing takes longer than the visibility timeout, the message is redelivered while you are still working on it.** Two workers now process the same message.

```python
# Extend the visibility while working
async def process_with_heartbeat(message, work):
    async def extend():
        while True:
            await asyncio.sleep(visibility_timeout / 3)
            await message.change_visibility(visibility_timeout)

    task = asyncio.create_task(extend())
    try:
        return await work()
    finally:
        task.cancel()
```

💡 **This is the same problem as lease renewal in distributed locks** ([[07.4 - Distributed Locks Done Right]]), including the fact that a paused process cannot extend and cannot know it failed to. **Long tasks need idempotent handlers regardless of how carefully you extend.**

**The better answer for long work: make the task short.** Split it into stages ([[08.1 - Why Background Work Exists]]) so no single message is held for minutes.

## Ordering

Three levels, and the difference matters enormously.

| Guarantee | Meaning |
|---|---|
| **None** | Messages may arrive in any order |
| **Per-key (partition)** | Messages with the same key arrive in order relative to each other |
| **Global** | All messages arrive in the order sent |

⚠️ **Global ordering means one consumer.** Any parallelism destroys it, because two consumers processing concurrently have no coordination.

💡 **Per-key ordering is what you almost always actually want**, and it is what Kafka provides via partitions ([[09.1 - Queue vs Log]]). "All events for document 42 in order, no ordering guarantee between documents" gives you correctness where it matters and parallelism everywhere else.

### What breaks ordering even when the queue provides it

```
Message 1 fails → retried with 5s backoff
Message 2 succeeds immediately
→ message 2's effect happens before message 1's
```

⚠️ **Retries reorder.** A queue that delivers in order does not deliver *successfully* in order once retries exist.

```
Consumer prefetches 10 messages, processes them concurrently
→ completion order is arbitrary
```

⚠️ **Concurrency within a consumer reorders.** `prefetch=10` with async processing means ten in flight and no ordering between them.

💡 **If you genuinely need ordering, you need: one partition per key, one consumer per partition, prefetch of 1, and no retries that skip ahead.** That is a serious throughput cost, and it is why the better answer is usually to **make the handler order-independent** — use absolute values rather than deltas, and include a version or timestamp so a stale message can be detected and dropped.

```python
# Order-independent: reject stale updates
await conn.execute(
    "UPDATE documents SET status = $1, version = $2 WHERE id = $3 AND version < $2",
    status, event.version, doc_id,
)
```

## Head-of-Line Blocking

```
Queue: [msg1] [msg2] [msg3] [msg4]
        ▲ fails, retries forever
```

⚠️ **A message that cannot succeed blocks everything behind it** in an ordered queue ([[02.5 - Head of Line Blocking]]).

This is why dead letter queues exist:

```
After N attempts → move to the dead letter queue → continue
```

💡 **A DLQ trades ordering for liveness**, and that trade must be deliberate. For a ledger where every entry must be applied in sequence, skipping a poison message is worse than stopping. For document indexing, it is obviously correct.

**Write down which of your queues can tolerate skipping.**

## Durability

```
In-memory     fast, lost on broker restart
Persisted     survives restart, slower
Replicated    survives node loss
```

| Broker | Default |
|---|---|
| Redis (as a queue) | In-memory, with optional AOF/RDB persistence |
| RabbitMQ | Configurable per queue and per message |
| SQS | Replicated, durable, always |
| Kafka | Replicated to disk, configurable `acks` |

⚠️ **Redis used as a Celery broker without persistence loses every queued task on restart.** With `appendonly yes` it loses up to `appendfsync` worth. **Know which you have configured**, because "we lost 40,000 queued jobs during the Redis upgrade" is a bad way to find out.

### Producer-side durability

```python
await queue.enqueue(task, args)     # returned — is it durable?
```

⚠️ **The enqueue returning does not mean the message is durable** unless the broker confirms it.

```python
# RabbitMQ: publisher confirms
channel.confirm_delivery()

# Kafka: acks
producer = KafkaProducer(acks="all")
```

💡 **The database-commits-then-enqueue-fails gap is the classic dual-write problem** ([[06.14 - Beyond Postgres]]):

```python
async with conn.transaction():
    await repo.create(doc)
await enqueue(process, doc.id)      # ← if this fails, the document is never processed
```

**The outbox pattern is the fix** ([[09.3 - The Outbox Pattern]]), and it is the correct default whenever a message must accompany a database write.

## Backpressure

```
Producers: 1,000/sec
Consumers:   500/sec
```

The queue grows without bound. **Same problem as [[01.11 - Backpressure Inside One Process]], at the infrastructure layer.**

| Response | |
|---|---|
| **Let it grow** | Fine for a burst, fatal for sustained overload |
| **Bound the queue, reject producers** | Backpressure reaches the source |
| **Bound the queue, drop oldest** | For data where fresh beats complete |
| **Scale consumers** | The real fix, if you can |

⚠️ **An unbounded queue does not solve overload, it hides it** — converting a fast visible failure into rising latency and eventual collapse.

💡 **The signal to watch is queue *age*, not depth** ([[08.1 - Why Background Work Exists]]). Depth tells you how much is waiting; age tells you how long the wait is, and age is what the user experiences.

```python
queue_oldest_message_age_seconds.set(age)
```

**Alert on age.** A queue with 100,000 messages all under a second old is a healthy burst; one with 50 messages 4 hours old is broken.

## In Production

### The semantics audit

For every queue in your system, write down:

```
Delivery:      at-least-once / at-most-once
Ack timing:    early / late
Visibility:    N seconds, extendable?
Ordering:      none / per-key / global
Durability:    memory / disk / replicated
Bounded:       yes, at N / no
On full:       block / reject / drop
Poison policy: DLQ after N attempts / retry forever
Max message:   N KB
Retention:     N days
```

⚠️ **Most teams cannot answer half of these for their own queues.** The exercise takes twenty minutes and it consistently finds at least one assumption that is wrong.

### Message size

| Broker | Limit |
|---|---|
| SQS | 256 KB |
| RabbitMQ | Configurable, practically ~128 MB, and you should not |
| Kafka | 1 MB default |
| Redis | 512 MB per value, and you should not |

💡 **Send references, not payloads.**

```python
# Bad
await enqueue(process_document, content=file_bytes)

# Good
await enqueue(process_document, document_id=doc.id)
```

⚠️ **A large payload in a queue is copied on every retry, held in broker memory, and serialised twice.** It also means the message can become stale — the document may have changed between enqueue and processing, and the worker acts on the old copy.

**Passing an ID means the worker reads current state.** That is almost always what you want, and it is one of those small decisions with a large downstream effect.

### Poison messages

```python
@app.task(bind=True, max_retries=3)
def process(self, doc_id: str):
    try:
        ...
    except PermanentError:
        raise                       # do not retry — it will fail identically
    except TransientError as e:
        raise self.retry(exc=e, countdown=backoff(self.request.retries))
```

💡 **Distinguish permanent from transient failures.** Retrying a validation error three times with exponential backoff wastes 30 seconds and ends in the same place. Retrying a network timeout is exactly right.

**A task that cannot distinguish them retries everything, which is both wasteful and slow to surface real bugs.**

### The at-least-once checklist

Every consumer needs:

```
□  Idempotent handler, or a dedup record ([[07.5 - Idempotency Keys and Deduplication]])
□  Ack after the work commits, never before
□  Visibility timeout longer than p99 processing time
□  Extension for long tasks, or shorter tasks
□  Permanent vs transient failure distinction
□  DLQ with an alert
□  Max attempts, not infinite retry
□  Order-independent, or explicitly ordered with the cost accepted
```

⚠️ **The first item is not optional and it is the one most often missing.** At-least-once delivery with a non-idempotent handler is a data corruption bug waiting for a network blip.

### What "the queue is backed up" actually means

```
1. Consumers are down or crash-looping        → check worker health
2. Consumers are slower than producers        → scale, or the work got slower
3. One poison message blocking an ordered queue → check the oldest message
4. A downstream dependency is slow             → check what the task calls
5. Prefetch too high, work unevenly distributed → some workers idle, some loaded
```

💡 **Check the oldest message first.** If the oldest is old and the newest is recent, you have a stuck message. If both are old, you have a throughput problem. Those need entirely different responses, and the two metrics distinguish them immediately.

## Codebase

**Repo:** `celery/kombu`, `rabbitmq/rabbitmq-server`, `apache/kafka`

**Question to answer:** How does Kombu implement a visibility timeout on Redis, which has no such concept natively? Then: in RabbitMQ, what exactly happens to an unacked message when a consumer's connection drops?

**Read, in order:**

1. `kombu/kombu/transport/redis.py` — **`QoS.restore_visible` and the unacked message tracking.** Redis has no visibility timeout, so Kombu builds one with a sorted set of in-flight messages scored by deadline. **This is the answer to the first question and it is worth understanding because it explains several Celery-on-Redis surprises**
2. `kombu/kombu/transport/virtual/base.py` — the generic virtual transport, including `QoS` and prefetch handling
3. `rabbitmq-server/deps/rabbit/src/rabbit_channel.erl` — search for consumer cancellation and `requeue`. **When a channel closes, unacked messages are requeued** — the answer to the second question
4. `kafka/clients/src/main/java/.../consumer/internals/ConsumerCoordinator.java` — offset commits, which are Kafka's equivalent of acking. **Note that committing an offset acks everything before it**, which is a meaningfully different model
5. `celery/celery/worker/request.py` — **where Celery decides to ack.** Find the `acks_late` handling and `reject_on_worker_lost`

💡 The Kombu Redis transport is the most practically valuable read here, because **Redis is not a message broker and Kombu is emulating one.** Understanding that the visibility timeout is a sorted set that a background thread restores from explains why Celery-on-Redis behaves differently from Celery-on-RabbitMQ under worker crashes ([[08.4 - Brokers and Result Backends]]).

**Size:** 1–2 sessions.

**Part 1 — A verifier that catches everything.** Producer sends numbered messages; consumer records effects; verifier detects duplicates, gaps and reordering.

**This harness is the reusable asset.** Every subsequent part uses it.

**Part 2 — The crash matrix.** Kill the consumer at six points: before receive, after receive before ack (early-ack config), after ack before work, mid-work, after work before ack (late-ack config), and after ack.

Run each against both ack configurations. **Twelve cells.**

For each, record: message lost, message duplicated, or exactly-once.

**Confirm early acking loses messages and late acking duplicates them.** These are the two options and there is no third.

**Part 3 — Visibility timeout exceeded.** A task taking 90 seconds with a 30-second visibility timeout.

**Confirm the message is redelivered twice while the first worker is still processing** — three concurrent executions of the same message.

Then implement extension and confirm it holds. Then `SIGSTOP` the worker past the extension interval and **confirm redelivery happens anyway** — the same pause problem as locks.

Then split the task into three 30-second stages and confirm the problem disappears.

**Part 4 — Is your order actually preserved?** Send 10,000 sequentially numbered messages.

Measure ordering with: one consumer prefetch 1, one consumer prefetch 10, four consumers, and one consumer with 10% transient failures and retries.

**Build the table of how many messages arrived out of order in each.**

**The retry case should reorder even with one consumer and prefetch 1.** That result is the one people do not expect.

Then implement an order-independent handler using version checks and confirm correctness regardless of arrival order.

**Part 5 — Durability.** Enqueue 10,000 messages, restart the broker before any are consumed.

Test with Redis without persistence, Redis with AOF, and RabbitMQ with durable queues and persistent messages.

**Count survivors in each.** The first should be zero.

Then the enqueue gap: commit a database transaction, then kill the process before the enqueue. **Confirm the row exists and the work never happens.** Then implement the outbox and confirm the gap closes.

**Part 6 — Backpressure.** Producers at 1,000/sec, consumers at 500/sec.

Unbounded: chart queue depth, oldest message age, broker memory, and end-to-end latency over 10 minutes. **Find where it breaks.**

Bounded with producer rejection: chart the same, plus the producer rejection rate.

**Put the two latency charts side by side.** The unbounded one climbs without limit; the bounded one stays flat with visible errors. **That is the fast-versus-slow failure argument again** ([[11.4 - Backpressure and Load Shedding]]).

**Part 7 — The audit.** Fill in the eleven-line semantics table for every queue in Conduit.

Then **verify three of your answers empirically** rather than reading the documentation. At least one will be wrong.

**Done when:**
- Your twelve-cell crash matrix is complete
- You have demonstrated three concurrent executions from a visibility timeout
- Your ordering table shows retries reordering even with prefetch 1
- You know exactly how many messages each durability configuration loses
- Your bounded and unbounded latency charts are side by side
