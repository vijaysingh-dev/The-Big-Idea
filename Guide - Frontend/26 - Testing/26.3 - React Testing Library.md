# React Testing Library

RTL renders components and queries the resulting DOM the way a user would find things — by role, label and text. It deliberately provides **no** access to state, props or instance methods, which is what pushes tests toward behavior ([[26.1 - Testing Philosophy]]).

## A representative test

```jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("submits the form with entered values", async () => {
  const onSubmit = vi.fn();
  const user = userEvent.setup();

  render(<SignupForm onSubmit={onSubmit} />);

  await user.type(screen.getByLabelText(/email/i), "a@b.com");
  await user.type(screen.getByLabelText(/password/i), "hunter2222");
  await user.click(screen.getByRole("button", { name: /sign up/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "a@b.com", password: "hunter2222" });
});
```

Nothing here references implementation. The component could be rewritten from `useState` to React Hook Form and the test would still pass.

## Query priority

The order is not stylistic — it encodes accessibility.

**1. Accessible to everyone:**

```jsx
screen.getByRole("button", { name: /submit/i });
screen.getByLabelText(/email address/i);
screen.getByPlaceholderText(/search/i);
screen.getByText(/welcome back/i);
screen.getByDisplayValue("current value");
```

**2. Semantic:**

```jsx
screen.getByAltText(/company logo/i);
screen.getByTitle(/close/i);
```

**3. Last resort:**

```jsx
screen.getByTestId("submit-button");
```

**`getByRole` should be the default.** If you cannot find an element by role and accessible name, that usually means the markup has an accessibility problem — an unlabelled input, a clickable `div`, a missing `aria-label` ([[09.5 - Accessibility Fundamentals]]).

The test failing for that reason is the library working as designed.

`getByTestId` is an escape hatch for elements with no accessible identity — a chart container, a layout wrapper. Reaching for it constantly is a signal about the markup, not about the query API.

`screen.logTestingPlaygroundURL()` opens a tool that suggests the best query for any element, which is the fastest way to learn the priority order.

## Query variants

```jsx
getBy...      // one match, throws if 0 or 2+
queryBy...    // one match, returns null if 0 — for asserting absence
findBy...     // async, retries until found or times out
getAllBy...   // multiple matches
```

The rule:

```jsx
expect(screen.getByRole("alert")).toBeInTheDocument();          // present
expect(screen.queryByRole("alert")).not.toBeInTheDocument();    // absent
expect(await screen.findByText(/loaded/i)).toBeInTheDocument(); // appears later
```

Using `getBy` to assert absence throws instead of failing cleanly. Using `queryBy` for presence gives a null-pointer error rather than a useful message.

`findBy` wraps `waitFor` and is the correct tool for anything asynchronous — data loading, transitions, animations ([[24.2 - Loading Error and Empty States]]).

## userEvent, not fireEvent

```jsx
// fireEvent — dispatches one synthetic event
fireEvent.click(button);

// userEvent — the full interaction sequence
await user.click(button);   // pointerdown, mousedown, focus, pointerup, mouseup, click
```

`userEvent` simulates what a real interaction produces: focus changes, hover states, keyboard events during typing, and respect for `disabled` and `pointer-events: none`.

That last point matters — `fireEvent.click` on a disabled button succeeds, while `user.click` correctly does not. The `fireEvent` version passes a test for a feature that is broken.

Always call `userEvent.setup()` before `render`, and `await` every interaction.

```jsx
await user.type(input, "hello");
await user.clear(input);
await user.selectOptions(select, "option-value");
await user.upload(fileInput, file);
await user.keyboard("{Enter}");
await user.tab();
await user.hover(element);
```

With fake timers, setup needs a bridge or interactions hang ([[26.2 - Unit Testing with Vitest and Jest]]):

```jsx
const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
```

## waitFor and findBy

```jsx
// Preferred — a single retried query
expect(await screen.findByText(/saved/i)).toBeInTheDocument();

// For assertions that are not a query
await waitFor(() => expect(mockSave).toHaveBeenCalled());

// Waiting for something to disappear
await waitForElementToBeRemoved(() => screen.queryByRole("progressbar"));
```

Two rules for `waitFor`: keep exactly one assertion inside it, and never put side effects inside it. The callback runs repeatedly, so a `user.click` inside `waitFor` fires many times.

Arbitrary sleeps are always wrong:

```jsx
await new Promise(r => setTimeout(r, 1000));   // flaky and slow
```

## Rendering with providers

```jsx
function renderWithProviders(ui, { route = "/", ...options } = {}) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false, gcTime: 0 } },
  });

  function Wrapper({ children }) {
    return (
      <QueryClientProvider client={queryClient}>
        <MemoryRouter initialEntries={[route]}>{children}</MemoryRouter>
      </QueryClientProvider>
    );
  }

  return { ...render(ui, { wrapper: Wrapper, ...options }), queryClient };
}
```

Export this from a test utility module and use it everywhere instead of raw `render`.

`retry: false` is essential — the default retry behavior makes error-path tests wait through three exponential backoffs before failing ([[24.6 - TanStack Query Fundamentals]]). A **fresh `QueryClient` per test** prevents cache leakage between tests.

## Testing hooks

```jsx
import { renderHook, act } from "@testing-library/react";

test("useCounter increments", () => {
  const { result } = renderHook(() => useCounter(0));

  act(() => result.current.increment());

  expect(result.current.count).toBe(1);
});
```

`result.current` is re-read after each render, so hold the reference fresh rather than destructuring once.

Providers go through the `wrapper` option, same as components ([[17.11 - Custom Hooks]]).

Test a hook directly only when it has meaningful standalone logic. A hook used by one component is usually better tested through that component.

## act warnings

```
Warning: An update to X inside a test was not wrapped in act(...)
```

This means state updated after the test finished asserting — almost always an un-awaited async operation.

The fix is generally not to add `act` manually. RTL wraps `render` and `userEvent` in `act` already. The warning usually means a missing `await`:

```jsx
await user.click(button);                          // not fireEvent.click
await screen.findByText(/done/i);                  // not getByText
await waitFor(() => expect(mock).toHaveBeenCalled());
```

Suppressing the warning hides a real race in the test.

## What not to do

```jsx
// Reaching into implementation
const { container } = render(<Component />);
container.querySelector(".submit-button");         // couples to CSS classes

// Testing that it rendered
expect(container).toBeTruthy();                    // asserts nothing useful

// Snapshotting whole components
expect(container).toMatchSnapshot();               // never reviewed on failure

// Asserting on props or state
expect(component.props.isOpen).toBe(true);         // RTL deliberately prevents this
```

Querying by CSS class couples the test to styling — a class rename breaks a working feature's test.

## Debugging

```jsx
screen.debug();                       // print the whole DOM
screen.debug(screen.getByRole("form"));
screen.logTestingPlaygroundURL();     // suggests the best query
```

When a query fails, RTL prints the accessible roles present in the DOM, which usually identifies the problem immediately — a missing label, or an element rendered as the wrong role.

## How senior engineers actually use this

**They default to `getByRole` with an accessible name**, treating a failure to find one as an accessibility bug to fix rather than a query to work around.

**They use `userEvent`, never `fireEvent`**, because `fireEvent` passes tests for broken features.

**They export a `renderWithProviders` helper** with `retry: false` and a fresh query client.

**They use `findBy` for async** and never a fixed sleep.

**They treat `act` warnings as missing awaits**, not as noise to suppress.

## Common pitfalls

- `getBy` used to assert absence, throwing instead of failing.
- `fireEvent` succeeding on disabled elements.
- Missing `await` on user interactions, producing `act` warnings.
- Query retry enabled, making error tests slow.
- Shared `QueryClient` leaking cache between tests.
- Querying by CSS class or test id where a role would work.
- Multiple assertions or side effects inside `waitFor`.
- Full-component snapshots that nobody reads.

## Interview angle

"How do you test React components" wants: render, query the way a user would find things, interact with `userEvent`, assert on visible outcomes — with no access to state or props by design. The point worth making explicitly is that query priority encodes accessibility, so a component that is hard to query is usually a component that is hard to use with a screen reader. Adding that `fireEvent` will happily click a disabled button while `userEvent` will not is a concrete illustration of why the distinction matters.
