# Change Data Capture

## What it is

**Change Data Capture** publishes an event automatically whenever a record is created, updated, deleted, or undeleted. No trigger, no code, no publish call.

Enable it per object in Setup, and every change to that object produces a `ChangeEvent` on the bus.

```
Setup → Change Data Capture → select Warranty_Claim__c
→ Warranty_Claim__ChangeEvent is now published on every change
```

The distinction from platform events ([[12.8 - Platform Events]]):

**Platform events** are business messages you design and publish deliberately. "A claim was approved."

**Change events** are data messages the platform publishes automatically. "This record's Status field changed from Under Review to Approved."

One expresses intent; the other expresses a database change.

## The event shape

A change event carries the fields that changed, plus a header describing the change.

```java
trigger ClaimChangeTrigger on Warranty_Claim__ChangeEvent (after insert) {
    ClaimChangeHandler.handle(Trigger.new);
}
```

```java
public with sharing class ClaimChangeHandler {

    public static void handle(List<Warranty_Claim__ChangeEvent> events) {
        List<Claim_Audit__c> auditEntries = new List<Claim_Audit__c>();

        for (Warranty_Claim__ChangeEvent event : events) {
            EventBus.ChangeEventHeader header = event.ChangeEventHeader;

            // one event can cover several records changed in the same transaction
            for (String recordId : header.getRecordIds()) {
                auditEntries.add(new Claim_Audit__c(
                    Claim_Id__c = recordId,
                    Change_Type__c = header.getChangeType(),
                    Changed_Fields__c = String.join(header.getChangedFields(), ','),
                    Changed_By__c = header.getCommitUser(),
                    Changed_At__c = Datetime.newInstance(header.getCommitTimestamp()),
                    Transaction_Key__c = header.getTransactionKey(),
                    New_Status__c = event.Status__c
                ));
            }
        }

        if (!auditEntries.isEmpty()) {
            insert auditEntries;
        }
    }
}
```

## The header

`ChangeEventHeader` is where the useful metadata lives:

```java
header.getEntityName()        // 'Warranty_Claim__c'
header.getChangeType()        // CREATE, UPDATE, DELETE, UNDELETE, GAP_CREATE, GAP_UPDATE...
header.getRecordIds()         // the records this event covers
header.getChangedFields()     // field API names that changed — UPDATE only
header.getCommitUser()        // who made the change
header.getCommitTimestamp()   // when, as epoch milliseconds
header.getCommitNumber()      // orders changes within a transaction
header.getTransactionKey()    // groups all events from one transaction
header.getSequenceNumber()    // position within the transaction
```

**`getRecordIds()` returns a list.** When 200 records are updated in one transaction with identical field changes, the platform may consolidate them into a single event covering all 200. A handler assuming one record per event is wrong.

**`getChangedFields()` is populated only for UPDATE.** For CREATE it is empty, because everything is new.

**`getTransactionKey()` groups events** from the same transaction, which is what lets a downstream consumer reassemble a multi-object change into one logical operation.

## Gap events

Occasionally the platform cannot deliver full detail — under extreme load, or when a change is too large. It publishes a **gap event** instead, with a change type of `GAP_CREATE`, `GAP_UPDATE`, `GAP_DELETE`, or `GAP_UNDELETE`.

A gap event says "this record changed" without the field values.

A consumer that ignores gap events silently misses changes. Handling them means re-querying:

```java
Set<String> gapRecordIds = new Set<String>();

for (Warranty_Claim__ChangeEvent event : events) {
    EventBus.ChangeEventHeader header = event.ChangeEventHeader;

    if (header.getChangeType().startsWith('GAP_')) {
        // the payload is incomplete, so the current state must be fetched
        gapRecordIds.addAll(header.getRecordIds());
    } else {
        processNormally(event);
    }
}

if (!gapRecordIds.isEmpty()) {
    reconcileFromDatabase(gapRecordIds);
}
```

Any production CDC consumer needs this branch. It is the detail most implementations discover after a load spike.

## Where CDC is the right tool

**Replication to an external system.** A data warehouse, a search index, a reporting database kept current without polling. This is the primary use.

**Audit trails** beyond what field history tracking provides — more than twenty fields, longer retention, or a custom structure.

**Cache invalidation** in an external application holding Salesforce data.

**Event-driven integration** where the external system reacts to changes rather than polling for them.

**Cross-org synchronization.**

The common thread: **a consumer that wants to know about every change without asking.**

## Where it is not

**Business logic.** CDC tells you a field changed, not why. "Status changed to Approved" is data; "a claim was approved and here is the approved amount and the approver" is a business event. Use a platform event for the second.

**In-org automation.** A trigger is simpler, synchronous, and can prevent the save. CDC runs after commit and cannot.

**Selective notification.** CDC fires on every change to the object, including ones you do not care about. Filtering happens in the subscriber, which means paying for delivery on everything.

**Anything needing the old values.** Change events carry new values and the list of changed field names, not the previous values. Reconstructing "changed from X to Y" needs the consumer to hold prior state.

That last limitation is significant and frequently discovered late. A downstream system wanting before-and-after values must maintain its own copy.

## Subscribing from outside

The main use, and the reason CDC exists.

**Pub/Sub API** over gRPC is the current mechanism — efficient binary protocol, replay support, and flow control. See [[13.9 - Pub-Sub API and Event Relay]].

**Event Relay** forwards events to AWS EventBridge with no code, which is the lowest-effort path into an AWS-based architecture.

**CometD Streaming API** is the older mechanism, still supported.

All three support **replay**, which is what makes CDC viable for replication:

```
Replay from a specific ReplayId    → resume after a consumer outage
Replay from -1                     → new events only
Replay from -2                     → everything retained (72 hours)
```

A consumer that goes down for an hour resumes from its last processed `ReplayId` and catches up. Without replay, an outage means a full reconciliation.

Storing the last processed `ReplayId` durably is therefore the single most important thing a CDC consumer does.

## Retention and volume

**72 hours** of retention in the event bus. A consumer down longer than that has a gap requiring a full reconciliation.

**CDC events count against the delivery allocation**, per subscriber. Enabling CDC on a high-volume object with several subscribers consumes it quickly.

**Enabling CDC on the wrong object is expensive.** A Case object receiving 80,000 records a year with several updates each produces several hundred thousand events annually — each counting toward delivery limits for every subscriber.

The practical guidance: **enable CDC only on objects an external system genuinely needs to track**, not on everything for completeness.

## CDC versus the alternatives

| Need | Tool |
| --- | --- |
| External system tracks all record changes | CDC |
| External system reacts to a business event | Platform Event |
| In-org reaction to a change | Trigger or flow |
| Periodic bulk extract | Bulk API with `SystemModstamp` |
| Field-level history in Salesforce | Field History Tracking |
| Long-term audit history | Field Audit Trail |

The `SystemModstamp` polling alternative is worth naming, because it is the pattern CDC replaces:

```sql
SELECT Id, Name, Status__c, SystemModstamp
FROM Warranty_Claim__c
WHERE SystemModstamp > :lastSyncTimestamp
ORDER BY SystemModstamp ASC
LIMIT 10000
```

Polling is simpler, needs no CDC enablement, and works with the standard API. Its costs are latency between polls, API consumption on every poll whether or not anything changed, and no visibility of deletions.

**Polling is often the right answer** for a nightly warehouse load. CDC earns its place when latency matters or deletions need tracking.

## Testing

```java
@IsTest
static void claimUpdatePublishesChangeEvent() {
    Warranty_Claim__c claim = TestDataFactory.createClaim();

    Test.startTest();
    Test.enableChangeDataCapture();

    claim.Status__c = 'Approved';
    update claim;

    Test.getEventBus().deliver();
    Test.stopTest();

    List<Claim_Audit__c> audit = [
        SELECT Change_Type__c, Changed_Fields__c FROM Claim_Audit__c
    ];
    Assert.areEqual(1, audit.size(), 'The change event handler should have written an audit entry');
    Assert.isTrue(audit[0].Changed_Fields__c.contains('Status__c'),
        'The changed field list should include Status');
}
```

Two required calls: **`Test.enableChangeDataCapture()`** before the DML, and **`Test.getEventBus().deliver()`** to run subscribers. Omitting either produces a passing test that proves nothing.

Gap events cannot be simulated in tests, which means the gap-handling branch is untestable and needs review rather than coverage.

## Practical guidance

**Enable CDC only where an external consumer needs it.** Every enabled object costs delivery allocation.

**Handle gap events.** Ignoring them means silently losing changes.

**Handle multiple record Ids per event.** Bulk changes are consolidated.

**Store the last processed `ReplayId` durably**, so a consumer outage is recoverable.

**Do not expect old values.** They are not in the payload.

**Use platform events for business meaning**, CDC for data replication.

**Consider `SystemModstamp` polling** before enabling CDC — it is simpler and often sufficient.
