# Salesforce Knowledge

## Why knowledge matters more now

A knowledge base has always reduced handle time and improved consistency. Two things have raised the stakes.

**Self-service deflection.** A customer who finds the answer themselves never creates a case. In high-volume support this is the largest single lever on cost.

**AI grounding.** Generative features — reply drafting, article recommendation, Agentforce agents answering customers directly — are grounded in knowledge articles. The quality of the AI output is bounded by the quality of the knowledge base. An org with a stale, thin knowledge base gets confidently wrong AI answers. See [[24.4 - Agentforce Fundamentals]].

That second point has changed knowledge from a nice-to-have into a prerequisite for anything AI-driven.

## The data model

**Knowledge__kav** is the article object. The `kav` suffix means "knowledge article version", and the versioning is the important structural detail.

Articles exist in versions with a `PublishStatus`:

- **Draft** — being written or edited
- **Online** — published and visible
- **Archived** — retired but retained

An article can have one Online version and one Draft version simultaneously, which is how an article is edited without taking the published one down. Publishing the draft replaces the online version and archives the previous one.

```sql
SELECT Id, KnowledgeArticleId, Title, UrlName, PublishStatus, VersionNumber,
       LastPublishedDate, ArticleTotalViewCount, IsLatestVersion
FROM Knowledge__kav
WHERE PublishStatus = 'Online' AND Language = 'en_US'
ORDER BY ArticleTotalViewCount DESC
```

`KnowledgeArticleId` is the stable identifier across versions. `Id` changes with each version. Code that stores an article reference should store `KnowledgeArticleId`, not `Id` — this is a common and confusing bug.

**Record types** on Knowledge define article types: a Troubleshooting article has different fields from a Product FAQ or a Policy document.

**Data Categories** classify articles along dimensions — product line, region, audience — and control visibility. A category group can be made visible to specific profiles or Experience Cloud audiences, which is how internal-only articles stay internal.

## Article lifecycle

```
Draft → Review (approval process) → Published (Online)
   ↑                                      ↓
   └──────── new draft version ←──────────┘
                                          ↓
                                      Archived
```

An approval process on the article record type is how quality is controlled. Whether to require approval is a real decision: it improves accuracy and slows publishing, and a support desk where articles take two weeks to approve will stop writing them.

The pattern that tends to work: no approval for internal-only articles, approval required for customer-facing ones.

## Creating articles from cases

The moment of case closure is when the agent knows the answer, and it is the only moment they will ever write it down.

Salesforce supports drafting an article from a case, prefilled from case content, and attaching articles to cases. Orgs that use this build a knowledge base as a by-product of working cases rather than as a separate project that never gets prioritized.

```java
public with sharing class KnowledgeDraftService {

    public static Id createDraftFromCase(Id caseId) {
        Case c = [
            SELECT Id, Subject, Description, Resolution__c, Product_Line__c
            FROM Case WHERE Id = :caseId WITH USER_MODE
        ];

        Knowledge__kav article = new Knowledge__kav(
            Title = c.Subject,
            UrlName = buildUrlName(c.Subject, caseId),
            Summary__c = c.Description,
            Resolution__c = c.Resolution__c,
            Language = 'en_US'
        );
        insert as user article;

        // link the draft to the originating case so the loop is visible in reporting
        insert new CaseArticle(
            CaseId = caseId,
            KnowledgeArticleId = [
                SELECT KnowledgeArticleId FROM Knowledge__kav WHERE Id = :article.Id
            ].KnowledgeArticleId
        );

        return article.Id;
    }

    private static String buildUrlName(String title, Id caseId) {
        // URL name must be unique and URL-safe; appending the case id guarantees uniqueness
        String base = title.toLowerCase().replaceAll('[^a-z0-9]+', '-').left(180);
        return base.removeEnd('-') + '-' + String.valueOf(caseId).right(6);
    }
}
```

`UrlName` must be unique across all articles and URL-safe. Generating it from the title alone produces collisions the moment two cases have the same subject, which is often.

Publishing programmatically uses `KbManagement.PublishingService`:

```java
KbManagement.PublishingService.publishArticle(knowledgeArticleId, true);
KbManagement.PublishingService.archiveOnlineArticle(knowledgeArticleId, null);
KbManagement.PublishingService.editOnlineArticle(knowledgeArticleId, true);
```

## Search and the Lightning Knowledge component

Agents find articles through the Knowledge component in the console, which searches as they type and can be seeded with the case subject.

Search quality depends on things nobody thinks about when writing articles:

**Titles matter most.** Search weights the title heavily. "Press P400 will not start after power cut" outperforms "Troubleshooting Guide 47".

**Use the customer's words.** Articles written in internal terminology do not match what customers or agents actually type.

**Keywords and summary fields** feed search. Populating them is worth the effort.

**Data category filtering** narrows results, and mis-categorized articles are effectively invisible.

Searching from Apex uses SOSL:

```java
public with sharing class ArticleSearchService {

    @AuraEnabled(cacheable=true)
    public static List<Knowledge__kav> search(String searchTerm, String productLine) {
        String query = 'FIND :searchTerm IN ALL FIELDS RETURNING Knowledge__kav('
            + 'Id, KnowledgeArticleId, Title, Summary__c, UrlName '
            + 'WHERE PublishStatus = \'Online\' AND Language = \'en_US\' '
            + 'ORDER BY ArticleTotalViewCount DESC LIMIT 10)';

        List<List<SObject>> results = Search.query(query);
        return (List<Knowledge__kav>) results[0];
    }
}
```

Bind variables work in SOSL and should always be used rather than concatenating the search term. See [[08.8 - SOSL and Full Text Search]].

## Self-service and deflection

Publishing articles to an Experience Cloud site lets customers find answers themselves. **Case deflection** goes further: as a customer types a case subject into the web form, matching articles appear, and the case is only created if none help.

Deflection rate is the metric, and it is the one that justifies the investment:

```sql
SELECT Knowledge__kav.Title article, COUNT(Id) deflections
FROM CaseArticle
WHERE CreatedDate = LAST_N_DAYS:90
GROUP BY Knowledge__kav.Title
ORDER BY COUNT(Id) DESC
```

More directly, comparing case volume for a topic before and after publishing a good article on it is the number that gets the programme funded.

## Article quality and maintenance

A knowledge base decays. Products change, processes change, and articles quietly become wrong.

Signals worth monitoring:

**Articles never viewed.** Either unnecessary or unfindable.
**Articles with poor ratings.** Knowledge supports voting, and low-rated articles are actively harmful.
**Articles not updated in over a year** on a product that has changed.
**High-volume case reasons with no article.** The gap analysis that shows where to write next.

```sql
SELECT Reason, COUNT(Id) caseVolume
FROM Case
WHERE CreatedDate = LAST_N_DAYS:90 AND Id NOT IN (SELECT CaseId FROM CaseArticle)
GROUP BY Reason
ORDER BY COUNT(Id) DESC
```

Cases closed with no article attached, grouped by reason, is the most useful gap report available and takes one query.

A scheduled review process — assigning articles to owners with a review date — is what keeps a knowledge base alive. Without one it degrades to the point where agents stop trusting it, and once trust is gone it is very hard to recover.

## Multilingual knowledge

Articles support translation, with each language as a separate version of the same article. Translation can be managed in Salesforce or exported to a translation vendor and imported back.

For a business operating across India, EMEA, and APAC this is a real requirement, and it multiplies the maintenance burden — an article updated in English is stale in four other languages until translated. The practical approach is to translate only the highest-volume articles rather than the whole base.

## Practical guidance

**Store `KnowledgeArticleId`, not `Id`.** Versions change the Id.

**Draft articles from cases at closure.** It is the only moment the knowledge exists in someone's head.

**Write titles the way customers describe problems.**

**Run the gap report.** High-volume case reasons with no article is where the next article should come from.

**Assign owners and review dates.** Unmaintained knowledge is worse than none.

**Invest here before investing in AI features.** Generative service features are grounded in these articles, and a thin knowledge base produces confidently wrong answers at scale.
