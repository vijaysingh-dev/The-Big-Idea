# Savepoints, Rollback and Transaction Control

## The default transaction model

Everything in one Apex execution is one transaction. Nothing commits until the very end of the order of execution, and an uncaught exception rolls all of it back. See [[07.13 - Order of Execution]].

That is usually what you want — no half-completed operations, no records referencing parents that were never created.

The problem it creates: when you **catch** an exception and continue, the work before the failure is still there, potentially in an inconsistent state.

## Savepoints

A savepoint marks a point in the transaction you can return to.

```java
public with sharing class ClaimSubmissionService {

    public static SubmissionResult submit(Warranty_Claim__c claim, List<Claim_Part__c> parts) {
        Savepoint sp = Database.setSavepoint();

        try {
            insert claim;

            for (Claim_Part__c part : parts) {
                part.Warranty_Claim__c = claim.Id;
            }
            insert parts;

            ClaimApprovalService.submitForApproval(new List<Warranty_Claim__c>{ claim });

            return SubmissionResult.success(claim.Id);

        } catch (Exception e) {
            // discard the claim and its parts, so no orphaned claim survives the failure
            Database.rollback(sp);
            AutomationLogger.logError('ClaimSubmission', null, e.getMessage());
            return SubmissionResult.failure(e.getMessage());
        }
    }
}
```

Without the rollback, a failure at the approval step leaves a claim and its parts inserted but never submitted — a record in a state the business process does not have.

## The rules

**A savepoint is not a nested transaction.** Rolling back to it undoes DML performed after it, in the same transaction.

**DML statement count is not restored.** If you performed 10 DML statements and roll back, you have still consumed 10 of the 150. Rollback undoes the data, not the limits. This is the detail people are most surprised by, and it means a retry loop with savepoints exhausts limits quickly.

**Ids assigned before rollback stay on the in-memory objects.** After rolling back an insert, `claim.Id` still holds a value, but no record exists with that Id. Reinserting the same object throws `DUPLICATE_VALUE` because the Id is set. Clear it explicitly:

```java
Database.rollback(sp);
claim.Id = null;   // required before attempting a reinsert
```

**Static variables are not rolled back.** A recursion guard marked as run stays marked. State set before the rollback persists.

**Only 5 savepoints per transaction.** Setting more throws.

**Savepoints must be released in order.** Rolling back to an earlier savepoint invalidates later ones.

**Anything published or enqueued may still happen.** Platform events published with immediate behaviour survive rollback deliberately. Queueable jobs enqueued before a rollback are not enqueued if the transaction ultimately fails — but if you catch and continue, they are.

## When savepoints are the right tool

**A multi-step operation that must be atomic beyond one DML statement.** The claim-and-parts example above.

**Attempting an operation that may fail, with a defined fallback.**

```java
Savepoint sp = Database.setSavepoint();
try {
    applyPremiumPricing(claim);
} catch (PricingException e) {
    Database.rollback(sp);
    applyStandardPricing(claim);
}
```

**Logging a failure that must survive.** Roll back the failed work, then write the log in the surviving transaction.

```java
Savepoint sp = Database.setSavepoint();
try {
    processClaims(claims);
} catch (Exception e) {
    Database.rollback(sp);
    // the log insert happens after the rollback, so it commits
    insert new Automation_Log__c(
        Context__c = 'ClaimProcessing',
        Message__c = e.getMessage(),
        Stack_Trace__c = e.getStackTraceString()
    );
}
```

This is one of two ways to log a failure that survives, the other being platform events. The savepoint approach is simpler when you are already catching; the event approach works even when the exception propagates. See [[09.10 - Exception Handling and Custom Exceptions]].

## When they are the wrong tool

**As a general safety wrapper.** Wrapping every method in a savepoint costs nothing at runtime and signals uncertainty about what the code does. If the whole transaction should roll back on failure, let the exception propagate — that is the default behaviour and it is free.

**In a loop.** Five savepoints is the ceiling, and a savepoint per iteration exhausts it immediately.

**As a substitute for validation.** Checking a condition before acting is cheaper and clearer than acting and rolling back.

**For retrying.** DML statement count is not restored, so a retry loop consumes limits on every attempt and fails faster than a single attempt would.

## Savepoints and triggers

A savepoint inside a trigger rolls back work done by that trigger, and it does **not** undo the DML that fired the trigger — that is outside the savepoint's scope.

This makes savepoints inside triggers rarely useful and occasionally confusing. The better mechanism for preventing a record from saving is `addError()`, which blocks that specific record and, with partial-success DML, lets the others through. See [[11.1 - Trigger Anatomy and Events]].

## Post-commit behaviour

Understanding what happens **after** the commit clarifies why some things survive rollback and others do not.

At step 18 of the order of execution, after commit:

- Email is sent
- Platform events published with immediate behaviour are delivered
- Async jobs enqueued during the transaction actually start
- Outbound messages fire

Anything before commit is subject to rollback. Anything at step 18 has already been decided by a successful commit.

The exception is `EventBus.publish` with the immediate publish behaviour, which is designed to survive rollback precisely so failure logging works. That design decision is why platform events are the recommended logging mechanism throughout this course. See [[12.8 - Platform Events]].

## Callouts and the transaction

**A callout cannot be made after DML in the same transaction.** The platform throws `You have uncommitted work pending`.

The reason is that the transaction holds open database work from step 7 to step 17, and an HTTP call during that window would hold it open for the duration of an external system's response.

```java
// Throws
insert claim;
HttpResponse response = new Http().send(request);

// Correct: the callout happens in a separate transaction
insert claim;
System.enqueueJob(new NotifyErpQueueable(new Set<Id>{ claim.Id }));
```

The Queueable runs after commit, in its own transaction, with its own limits and its own retry behaviour. See [[12.3 - Queueable Apex]] and [[13.14 - Apex Callouts]].

A callout **before** any DML is fine, which is why integrations that read external data then write records work, and integrations that write then notify need async.

## A worked pattern

The shape that combines all of it — an operation that must be atomic, logs failures durably, and defers external notification:

```java
public with sharing class ClaimSettlementService {

    public static SettlementResult settle(Id claimId, Decimal amount) {
        Savepoint sp = Database.setSavepoint();

        try {
            Warranty_Claim__c claim = [
                SELECT Id, Status__c, Claim_Amount__c, Asset__c
                FROM Warranty_Claim__c WHERE Id = :claimId FOR UPDATE
            ];

            claim.Status__c = 'Approved';
            claim.Approved_Amount__c = amount;
            update claim;

            insert new Claim_Payment__c(
                Warranty_Claim__c = claim.Id,
                Amount__c = amount,
                Payment_Date__c = Date.today()
            );

            ClaimRollupService.recalculate(new Set<Id>{ claim.Asset__c });

            // enqueued rather than called: the callout cannot run after DML
            System.enqueueJob(new ErpSettlementQueueable(new Set<Id>{ claim.Id }));

            return SettlementResult.success();

        } catch (Exception e) {
            Database.rollback(sp);
            insert new Automation_Log__c(
                Context__c = 'ClaimSettlement',
                Related_Record_Id__c = claimId,
                Message__c = e.getMessage(),
                Stack_Trace__c = e.getStackTraceString()
            );
            return SettlementResult.failure(e.getMessage());
        }
    }
}
```

`FOR UPDATE` on the query serializes concurrent settlement attempts on the same claim ([[08.6 - FOR UPDATE and Record Locking]]). The rollback discards the partial settlement. The log insert after the rollback survives. The Queueable never starts, because the enqueue was rolled back with everything else — which is correct, since there is nothing to notify the ERP about.

## Practical guidance

**Use savepoints for multi-step operations that must be atomic**, not as a general wrapper.

**Clear `Id` before reinserting** a rolled-back record.

**Remember limits are not restored** by a rollback.

**Log after the rollback**, or publish a platform event.

**Never use savepoints in a loop.** Five is the ceiling.

**Move callouts to async** whenever DML has occurred.

**Let exceptions propagate** when the whole transaction should fail — that is the default and it costs nothing.
