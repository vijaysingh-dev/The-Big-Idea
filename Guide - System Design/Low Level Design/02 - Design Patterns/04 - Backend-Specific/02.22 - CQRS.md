# CQRS Pattern

## At a Glance

|||
|---|---|
|**Type**|Backend / Enterprise|
|**Stands For**|Command Query Responsibility Segregation|
|**Intent**|Separate the models used for reading and writing data|
|**Frequency in Backend**|★★★☆☆ — high-scale read-heavy systems, complex domains|

---

## The Problem It Solves

A single model tries to serve both writes (business logic, validation, events) and reads (projections, summaries, joins). These have conflicting needs:

```
Write model needs:     Read model needs:
- Business validation  - Denormalized data
- Domain invariants    - Pre-joined views
- Aggregate isolation  - Flexible projections
- Event generation     - Fast query response
- Strong consistency   - Can tolerate staleness
```

---

## Architecture

```
                    ┌─────────────────────────────────────────┐
                    │              Application                │
                    └──────┬──────────────────┬──────────────┘
                           │ Commands          │ Queries
                    ┌──────▼──────┐     ┌─────▼──────────┐
                    │  Command    │     │  Query          │
                    │  Handlers   │     │  Handlers       │
                    └──────┬──────┘     └─────┬──────────┘
                           │                  │
                    ┌──────▼──────┐     ┌─────▼──────────┐
                    │  Domain     │     │  Read Model     │
                    │  (Aggregate)│     │  (Projection)   │
                    └──────┬──────┘     └────────────────-┘
                           │ domain events       ↑
                    ┌──────▼──────┐     projections update
                    │  Event      │─────────────────────────┘
                    │  Store /    │
                    │  Write DB   │
                    └─────────────┘
```

## Full Backend Example: Order System with CQRS

```python
# ── WRITE SIDE ────────────────────────────────────────────

# commands.py
@dataclass
class PlaceOrderCommand:
    user_id: UUID
    items: list[dict]
    payment_method_id: str
    shipping_address_id: str
    idempotency_key: str

@dataclass
class CancelOrderCommand:
    order_id: UUID
    user_id: UUID
    reason: str

@dataclass
class MarkOrderShippedCommand:
    order_id: UUID
    tracking_number: str
    carrier: str


# command_handlers.py
class PlaceOrderCommandHandler:
    def __init__(self, order_repo: OrderRepository, event_bus):
        self._repo = order_repo
        self._bus = event_bus
    
    def handle(self, cmd: PlaceOrderCommand) -> UUID:
        # Idempotency
        existing = self._repo.find_by_idempotency_key(cmd.idempotency_key)
        if existing:
            return existing.id
        
        # Domain logic lives in aggregate
        order = Order.place(
            user_id=cmd.user_id,
            items=cmd.items,
            idempotency_key=cmd.idempotency_key
        )
        self._repo.save(order)
        
        # Publish domain events for projection updates
        for event in order.get_events():
            self._bus.publish(event)
        
        return order.id

class CancelOrderCommandHandler:
    def __init__(self, order_repo: OrderRepository, event_bus):
        self._repo = order_repo
        self._bus = event_bus
    
    def handle(self, cmd: CancelOrderCommand):
        order = self._repo.get_or_raise(cmd.order_id)
        order.cancel(cmd.reason)
        self._repo.save(order)
        
        for event in order.get_events():
            self._bus.publish(event)


# ── READ SIDE ─────────────────────────────────────────────

# read_models.py — Optimized for query, not for domain logic
@dataclass
class OrderSummaryView:
    """Denormalized for listing — no joins needed at query time."""
    order_id: str
    user_id: str
    customer_name: str       # denormalized from User
    customer_email: str      # denormalized from User
    status: str
    total: str
    item_count: int
    created_at: str
    last_updated: str

@dataclass
class OrderDetailView:
    """Full order detail — pre-joined."""
    order_id: str
    customer: dict          # full customer snapshot
    items: list[dict]       # items with product names, prices
    payment: dict           # payment info
    shipping: dict          # shipping info
    timeline: list[dict]    # status change history
    total: str
    status: str


# queries.py
@dataclass
class GetOrdersByUserQuery:
    user_id: UUID
    status_filter: Optional[str] = None
    page: int = 1
    page_size: int = 20

@dataclass
class GetOrderDetailQuery:
    order_id: UUID


# query_handlers.py — hit read DB/cache directly, no domain logic
class GetOrdersByUserQueryHandler:
    def __init__(self, read_db):
        self._db = read_db
    
    def handle(self, query: GetOrdersByUserQuery) -> list[OrderSummaryView]:
        sql = """
            SELECT 
                o.id, o.user_id, u.name as customer_name, u.email as customer_email,
                o.status, o.total, o.item_count, o.created_at, o.updated_at
            FROM order_summaries o    -- denormalized view/table
            JOIN users u ON o.user_id = u.id
            WHERE o.user_id = %s
        """
        params = [str(query.user_id)]
        
        if query.status_filter:
            sql += " AND o.status = %s"
            params.append(query.status_filter)
        
        sql += " ORDER BY o.created_at DESC LIMIT %s OFFSET %s"
        params.extend([query.page_size, (query.page - 1) * query.page_size])
        
        rows = self._db.execute(sql, params)
        return [OrderSummaryView(**row) for row in rows]


# ── PROJECTIONS ───────────────────────────────────────────
# Projections update read models when domain events are received

class OrderSummaryProjection:
    """Updates read model when order events arrive."""
    
    def __init__(self, read_db):
        self._db = read_db
    
    def on_order_placed(self, event: OrderPlacedEvent):
        self._db.execute("""
            INSERT INTO order_summaries 
            (id, user_id, status, total, item_count, created_at, updated_at)
            VALUES (%s, %s, 'PENDING', %s, %s, NOW(), NOW())
            ON CONFLICT (id) DO NOTHING
        """, (str(event.order_id), str(event.user_id), 
              str(event.total), event.item_count))
    
    def on_order_paid(self, event: OrderPaidEvent):
        self._db.execute("""
            UPDATE order_summaries 
            SET status = 'PAID', updated_at = NOW()
            WHERE id = %s
        """, (str(event.order_id),))
    
    def on_order_cancelled(self, event: OrderCancelledEvent):
        self._db.execute("""
            UPDATE order_summaries 
            SET status = 'CANCELLED', updated_at = NOW()
            WHERE id = %s
        """, (str(event.order_id),))


# ── API LAYER ─────────────────────────────────────────────
class OrderController:
    def __init__(self, mediator: Mediator):
        self._mediator = mediator
    
    def place_order(self, request):
        # Sends command — returns only the ID
        order_id = self._mediator.send(PlaceOrderCommand(**request))
        return {"order_id": str(order_id)}, 201
    
    def get_orders(self, user_id, page=1):
        # Queries read model — fast, no domain logic
        orders = self._mediator.send(GetOrdersByUserQuery(
            user_id=UUID(user_id), page=page
        ))
        return [asdict(o) for o in orders]
```

## When to Use CQRS

|Use It When|Skip It When|
|---|---|
|Read/write have very different scaling needs|Simple CRUD|
|Complex domain + simple reports|Read/write models would be identical|
|Audit trail needed|Small team, not much complexity|
|High read volume, low write volume|No event-driven architecture|
|Different teams own reads vs writes||

---

## Tradeoffs

|Pro|Con|
|---|---|
|Read models optimized for queries|Eventual consistency between write and read|
|Write side stays clean (domain logic)|Higher complexity — more moving parts|
|Independent scaling|Projection rebuild time on failure|
|Teams can own different sides|Stale reads during propagation delay|
