# Org Types and Org Strategy

## The vocabulary

An **org** (organization) is a single Salesforce instance with its own data, configuration, and users. It is the tenant boundary in a multi-tenant system, and it has a unique 18-character Org ID.

Everything you build lives in an org. Everything you deploy moves from one org to another. Understanding the types, and which one you are standing in, prevents a specific category of expensive mistake.

## Production

The live org. Real customers, real revenue, real users who will notice a bad deployment within minutes.

Two things to internalize: you cannot develop directly in production (Apex cannot be edited there, by design), and everything else can be changed there directly, which is exactly the problem. Fields, flows, and validation rules can all be created in production by anyone with the permission, and orgs where that happens routinely become impossible to keep in sync with source control.

## Sandboxes

Copies of production used for development and testing. Every sandbox copies the **metadata** — objects, fields, code, flows, layouts. They differ in whether they copy **data**, how big they can be, and how often they can be refreshed.

| Type | Data copied | Storage | Refresh interval | Typical use |
| --- | --- | --- | --- | --- |
| Developer | None | 200 MB | Daily | Individual development |
| Developer Pro | None | 1 GB | Daily | Development with more test data |
| Partial Copy | Sample, defined by a template | 5 GB | Every 5 days | Integration testing, user acceptance testing |
| Full | Complete copy of production | Same as production | Every 29 days | Performance testing, final release validation, training |

The refresh intervals are the constraint that shapes strategy. A Full sandbox can be refreshed roughly once a month and the refresh itself can take many hours or days for a large org. That means your release schedule has to be planned around it, not the other way around.

A detail that trips people up: sandboxes get a modified domain, and email addresses in a sandbox are altered — for example `user@company.com` becomes `user@company.com.sandboxname`. Email deliverability is also switched off by default in a new sandbox, which is deliberate. Turning it on to test a notification and forgetting to turn it off has resulted in real customers receiving thousands of test emails.

## Scratch orgs

A newer model, and the one modern development is built around. A **scratch org** is a temporary, disposable org created from a definition file, lasting up to thirty days.

```json
{
  "orgName": "Feature - Case Escalation",
  "edition": "Developer",
  "features": ["EnableSetPasswordInApi", "ServiceCloud"],
  "settings": {
    "lightningExperienceSettings": { "enableS1DesktopEnabled": true },
    "securitySettings": { "passwordPolicies": { "enableSetPasswordInApi": true } }
  }
}
```

```bash
sf org create scratch --definition-file config/project-scratch-def.json --alias feature-escalation --duration-days 7
sf project deploy start --target-org feature-escalation
sf apex run --file scripts/seed-data.apex --target-org feature-escalation
```

The difference from a sandbox is philosophical, not just technical. A sandbox is a *copy of what exists*. A scratch org is *built from source*, which forces your repository to be the real definition of the org. If something is missing from source control, the scratch org does not have it, and you find out immediately rather than at release time.

Scratch orgs require a **Dev Hub** — a production org with the feature enabled, which allocates and tracks them. See [[21.4 - Dev Hub and Scratch Orgs]].

## Developer Edition orgs

Free, permanent, personal orgs with the full feature set and very small limits. Not connected to any company's production org. This is where you learn, experiment, and try a feature you have only read about. Sign up for one and use it constantly — this platform does not reward reading without doing.

## Trial and demo orgs

Time-limited orgs with sample data, used by sales and for demonstrations. Occasionally useful for exploring a product you do not have licensed.

## Choosing a strategy

A typical mid-to-large org runs something like this:

- **Developer sandboxes or scratch orgs**, one per developer or per feature. Isolated, cheap, disposable.
- **An integration or shared development sandbox** where features merge and are tested together for the first time.
- **A UAT sandbox**, usually Partial Copy, with realistic data, where the business validates work.
- **A staging sandbox**, usually Full, refreshed before a major release, used as the final rehearsal against production-like data and volume.
- **Production.**

Code flows in one direction: developer environment, to integration, to UAT, to staging, to production. Metadata never flows backwards; environments are brought back into line by refreshing them from production.

The reason for the ladder is that each level catches a different class of problem. A developer sandbox catches syntax and logic errors. Integration catches conflicts between two people's work. UAT catches "this is not what we asked for". Staging catches everything that only appears with real data volume — the slow query, the non-selective filter, the batch job that takes four hours.

## The mistakes that keep happening

**Hardcoded IDs.** A Record Type, Profile, Queue, or reference record has a different ID in every org. Code that hardcodes one works everywhere it was written and nowhere else. Resolve by name at runtime, or store the reference in Custom Metadata.

```java
// Fails on deployment to any other org
Id supportQueue = '00G5g000004XyZaEAK';

// Resolves correctly in every org
Id supportQueue = [
    SELECT Id FROM Group
    WHERE Type = 'Queue' AND DeveloperName = 'Tier_2_Support'
    LIMIT 1
].Id;
```

**Testing on empty sandboxes.** Code that runs in 200 milliseconds against fifty records may time out against two million. If your only pre-production environment has no data, you are shipping performance untested. This is the single strongest argument for a Full or Partial Copy sandbox in the release path. See section 23.

**Changes made directly in production.** An admin adds a field, a developer's next deployment overwrites or conflicts with it, and nobody can explain the difference between production and the repository. Production changes need the same discipline as code changes.

**Forgetting that sandbox refresh destroys work.** Refreshing a sandbox overwrites everything in it. Unmerged work in that sandbox is gone. This has cost real teams real weeks.

**Sensitive data in sandboxes.** A Full sandbox contains a complete copy of production data, including anything personal or regulated, in an environment with looser access. This is a genuine compliance exposure, and the reason Data Mask exists. See [[22.4 - Data Mask and Sandbox Data Privacy]].

## How to tell where you are

Worth building into any automation that behaves differently by environment:

```java
Organization org = [SELECT Id, Name, IsSandbox, InstanceName, OrganizationType FROM Organization LIMIT 1];

if (org.IsSandbox) {
    // route notifications to a test address rather than real customers
}
```

Better still, drive environment-specific behaviour from Custom Metadata rather than an `IsSandbox` check, so the behaviour is configurable rather than compiled in. See [[18.10 - Custom Metadata Driven Architecture]].
