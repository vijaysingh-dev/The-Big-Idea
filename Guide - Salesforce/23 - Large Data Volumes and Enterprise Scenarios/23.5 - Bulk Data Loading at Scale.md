# Bulk Data Loading at Scale

## The difference between a three-hour load and a three-day one

Rarely the tool. Almost always the preparation.

```
Sort order
Automation left running
Sharing recalculation
Parallelism and contention
Load sequence
Field history and roll-ups
```

Each of those can multiply the runtime, and together they are the difference between an overnight window and a weekend.

## Sort by parent

**The single most effective change.**

```
Unsorted file
    chunk 1: claims for assets 1, 47, 92, 3, 51...
    chunk 2: claims for assets 47, 3, 88, 1...
        → both chunks lock asset 47 and asset 3
            → UNABLE_TO_LOCK_ROW

Sorted by Asset__c
    chunk 1: claims for assets 1 through 12
    chunk 2: claims for assets 12 through 23
        → almost no overlap
```

**Parallel chunks touching children of the same parent contend on the parent's lock**, which the platform takes for roll-up recalculation and implicit sharing.

**Sorting the file by the parent Id groups those children into the same chunk**, and the contention disappears.

```bash
sort -t, -k3 claims.csv > claims-sorted.csv
```

This costs nothing and resolves most lock errors in a bulk load. See [[10.8 - Record Locking and Deadlocks]].

## Serial versus parallel

```json
{
  "object": "Warranty_Claim__c",
  "operation": "upsert",
  "externalIdFieldName": "ERP_Claim_Id__c",
  "concurrencyMode": "Serial"
}
```

**Parallel is the default** and is faster where contention is absent.

**Serial processes one chunk at a time**, eliminating contention entirely at the cost of throughput.

**Try sorting first.** Serial mode is the fallback when sorting is not possible — a file whose parent relationships are resolved by external ID rather than by a sortable Id column, for instance.

## Disabling automation

Every loaded record runs the object's full save pipeline: validation rules, triggers, flows, roll-ups, and workflow. On a million records that is a million executions of each.

```java
// Before the load
Automation_Settings__c settings = Automation_Settings__c.getOrgDefaults();
settings.Disable_All_Automation__c = true;
upsert settings;
```

**Or scoped to the loading user**, which is safer:

```java
// only the integration user's saves skip automation; everyone else is unaffected
insert new Automation_Settings__c(
    SetupOwnerId = loadingUserId,
    Disable_All_Automation__c = true
);
```

**Scoping to the user is the better pattern** — the business continues working normally while the load runs.

**What to disable, and what it costs:**

```
Triggers               via the bypass — the derived fields must be backfilled
Flows                  deactivate, or bypass via a decision on the setting
Validation rules       deactivate — the data must be known-good
Workflow rules         deactivate
Field history tracking turn off temporarily — history rows are a large write
Roll-up summaries      cannot be disabled; consider a lookup during the load
```

**Everything skipped must be reconciled afterwards.** A derived field not populated by the trigger needs a backfill job, and forgetting is how a load completes and the data is subtly wrong.

**Write down what was disabled.** Loads finish, people move on, and the validation rule stays off for three months.

## Deferred sharing calculation

```
Setup → Defer Sharing Calculation → Suspend
    [run the load]
Setup → Defer Sharing Calculation → Resume
```

**On a large load into a private object, this is frequently the largest single speedup.**

Without it, sharing rows are calculated per record as they load. With it, one full recalculation runs at the end.

**The costs:** sharing is stale while suspended, and the final recalculation can take hours. It must be enabled by Salesforce.

See [[23.3 - Sharing at Scale and Sharing Recalculation]].

## Load sequence

Dependency order, and it is not negotiable.

```
1. Account
2. Asset                  requires Account
3. Service_Contract__c    requires Account
4. Machine_Coverage__c    requires Asset and Service_Contract__c
5. Warranty_Claim__c      requires Asset
6. Claim_Part__c          requires Warranty_Claim__c
```

**`INVALID_CROSS_REFERENCE_KEY` in a bulk load almost always means load order** — children before parents, or a key that does not resolve.

**External IDs remove the ID-mapping step entirely:**

```csv
ERP_Claim_Id__c,Claim_Amount__c,Status__c,Asset__r.ERP_Asset_Id__c
CLM-99201,150000,Under Review,MCH-88213
CLM-99202,90000,Submitted,MCH-88214
```

**`Asset__r.ERP_Asset_Id__c` sets the lookup by the parent's external key.** No query for the Salesforce Id, no join in the source file, and the load is idempotent — a resubmission updates rather than duplicates.

**That single technique is what makes a migration manageable.** Without it, every file needs an ID-mapping pass after its parent loads. See [[10.3 - Upsert, Merge and External IDs]].

## Bulk API 2.0

```bash
sf data upsert bulk \
  --sobject Warranty_Claim__c \
  --file claims-sorted.csv \
  --external-id ERP_Claim_Id__c \
  --wait 60 \
  --target-org production
```

Or through the API directly, for control over concurrency mode:

```
POST /services/data/v62.0/jobs/ingest
{
  "object": "Warranty_Claim__c",
  "externalIdFieldName": "ERP_Claim_Id__c",
  "operation": "upsert",
  "lineEnding": "LF",
  "concurrencyMode": "Serial"
}
```

**Bulk API consumes a separate allocation** from the daily REST API limit, which is the commercial argument for it beyond speed.

**The failed-results file** drives the retry loop:

```
GET /services/data/v62.0/jobs/ingest/{jobId}/failedResults/
```

It contains the original row plus the error, so fixing and resubmitting is straightforward.

**Keep every failed-results file.** Reconciliation at the end of a migration is counting what went in against what was in the source, and these files are half the arithmetic. See [[13.4 - Bulk API 2.0]].

## Chunking and file size

```
100 MB per uploaded file
150 million records per rolling 24 hours
```

**Splitting a large file** into several jobs gives better monitoring and easier recovery — a failed job of 500,000 rows is easier to reason about than a failed job of five million.

**Batch size within a job is managed by the platform** in Bulk 2.0, unlike 1.0 where the client chunked.

## Timing the load

**Off-hours, always** — for contention, for user experience, and because a load competing with normal usage is slower.

**Away from scheduled jobs.** A nightly batch job running during a load competes for locks and for the five-concurrent-batch allocation. See [[12.5 - Scheduled Apex]].

**Away from sharing recalculation**, if one is running from a recent hierarchy change.

**Rehearse in a Full sandbox** with production-shaped data, and time it. A load taking three hours there will not take twenty minutes in production, and the rehearsal is what makes the window realistic. See [[21.11 - Sandbox Strategy and Data Seeding]].

## Skew during a load

**A load can create skew** that did not exist before.

```
500,000 claims, all with Region__c defaulting to the same lookup record
    → every insert locks that one record
        → contention throughout the load
```

**Check the distribution of the incoming data**, not just the existing data:

```bash
awk -F, '{print $5}' claims.csv | sort | uniq -c | sort -rn | head
```

**A value appearing in 80% of rows is a lookup skew problem waiting to happen.** The fixes: leave the field null, spread across several records, or make it a picklist. See [[10.9 - Data Skew]].

## Post-load reconciliation

The step that gets cut, and the one that catches silent failure.

```java
// Counts
Integer loaded = [SELECT COUNT() FROM Warranty_Claim__c WHERE ERP_Claim_Id__c != null];
System.debug('Loaded: ' + loaded + ', expected: ' + expectedCount);

// Orphans — children whose parent did not resolve
Integer orphans = [SELECT COUNT() FROM Warranty_Claim__c WHERE Asset__c = null];

// Records the automation should have derived, and did not because it was bypassed
Integer missingDerived = [
    SELECT COUNT() FROM Warranty_Claim__c WHERE Approval_Tier__c = null
];
```

**The third check is the one that matters most after a load with automation disabled.** Every field the triggers would have populated needs a backfill:

```java
public with sharing class ClaimBackfillBatch implements Database.Batchable<SObject> {

    public Database.QueryLocator start(Database.BatchableContext ctx) {
        return Database.getQueryLocator([
            SELECT Id, Claim_Amount__c, Asset__c
            FROM Warranty_Claim__c WHERE Approval_Tier__c = null
        ]);
    }

    public void execute(Database.BatchableContext ctx, List<Warranty_Claim__c> scope) {
        // calling the service directly, so the logic is identical to the trigger's
        ClaimService.applyDerivedFields(scope, null);
        Database.update(scope, false);
    }

    public void finish(Database.BatchableContext ctx) { }
}
```

**Calling the same service the trigger calls** is what makes the backfill correct — a separate implementation drifts. That is one of the practical payoffs of the service layer. See [[18.3 - Service Layer]].

## Re-enabling everything

```
[ ] Automation bypass removed
[ ] Validation rules reactivated
[ ] Flows reactivated
[ ] Field history tracking re-enabled
[ ] Sharing calculation resumed
[ ] Derived fields backfilled
[ ] Roll-ups recalculated
[ ] Counts reconciled
[ ] Failed-results files reviewed and resolved
```

**Roll-up summaries need recalculating** after a load with them disabled, and the platform offers a recalculation per roll-up in Setup.

**Sharing recalculation resumed** is the long one — expect hours.

## A migration runbook

```
Two weeks before
  [ ] External IDs created and indexed on every target object
  [ ] Full sandbox refreshed
  [ ] Load rehearsed and timed
  [ ] Failure modes documented from the rehearsal
  [ ] Deferred sharing calculation enabled in the org

One week before
  [ ] Files prepared, sorted by parent
  [ ] Distribution checked for skew
  [ ] Load sequence confirmed
  [ ] Backfill jobs written and tested
  [ ] Window agreed and communicated

On the day
  [ ] Automation disabled, scoped to the loading user
  [ ] Validation rules and flows deactivated, recorded
  [ ] Field history tracking disabled
  [ ] Sharing calculation suspended
  [ ] Load in sequence, monitoring each job
  [ ] Failed-results files retained

After
  [ ] Counts reconciled against the source
  [ ] Orphans checked
  [ ] Backfill jobs run
  [ ] Roll-ups recalculated
  [ ] Everything re-enabled, from the record
  [ ] Sharing calculation resumed
  [ ] Spot-check records in the UI
```

**"From the record" on the re-enable step** is the line that prevents a validation rule staying off for three months.

## Ongoing loads

A daily or hourly integration load has different constraints from a migration.

**It cannot disable automation**, because the business is working.

**It must be idempotent**, because it will be retried.

**It must be bounded**, so a bad day's file does not consume the API allocation.

**The patterns:**

```
Upsert on an external ID, always
Sort by parent in the extract, not after
Cap the batch size, and split large days into several jobs
Monitor duration, and alert when it grows
Alert on absence — a load that stopped running produces no error
```

**Alerting on absence is the one most often missing.** A nightly load that silently stopped three weeks ago looks exactly like a load with nothing to do. See [[13.17 - Error Handling, Retries and Idempotency]].

## Practical guidance

**Sort by parent Id.** It resolves most lock errors and costs nothing.

**Use external IDs and `Parent__r.External_Id__c`** to avoid ID mapping entirely.

**Disable automation scoped to the loading user**, not org-wide.

**Suspend sharing calculation** for large loads into private objects.

**Check the incoming distribution for skew**, not just the existing data.

**Rehearse in a Full sandbox and time it.**

**Keep every failed-results file.**

**Backfill by calling the same service the trigger calls.**

**Re-enable from a written record**, not from memory.

**Reconcile counts** — a load that silently dropped rows is the worst outcome.
