# Service Cloud Overview and the Support Model

## What Service Cloud is

Service Cloud is the set of objects, routing, and agent tooling that models customer support, built on the same platform and the same Account and Contact records as Sales Cloud.

That shared foundation is the commercial argument for buying both. The agent taking an angry call sees the deal a rep is trying to close with the same company, because it is literally the same Account record. No integration, no sync, no reconciliation.

## How service differs from sales, and why it matters technically

Sales and service look similar — records, stages, owners, automation — and their operational characteristics are very different.

**Volume is an order of magnitude higher.** A sales org might create 8,000 opportunities a year. The same company's support team might create 80,000 cases. Everything about design changes at that volume: query selectivity, archiving, automation cost per save.

**Speed matters per interaction.** A rep can spend a minute updating an opportunity. An agent handling 40 cases a day cannot afford a page that takes four seconds to load. Console performance is a functional requirement, not a nice-to-have.

**Work is routed, not owned.** Sales opportunities have an owner from creation. Cases arrive unassigned and are distributed by capacity, skill, and availability. This is why queues and Omni-Channel exist and why `OwnerId` on Case is polymorphic.

**Time is contractual.** Response and resolution times are often written into contracts, with financial consequences. That is what entitlements and milestones exist to track.

**Channels are many.** Email, web, phone, chat, messaging, social, and self-service portal all create cases. Each has its own plumbing.

## The core objects

**Case.** The unit of work. A customer problem, question, or request.

**Entitlement.** What level of service this customer is contractually owed.

**Milestone.** A time-based target within a case — first response within two hours, resolution within two days.

**Knowledge Article.** Documented answers, used by agents and published to customers.

**Queue.** Holds unassigned cases until claimed or routed.

**Omni-Channel objects.** `AgentWork`, `ServiceChannel`, `RoutingConfiguration`, `PresenceUserConfig` — the machinery for capacity-based distribution.

**ServiceContract, ContractLineItem, Asset.** The commercial and equipment context, connecting support to what the customer actually bought.

## The support model, end to end

```
Customer contacts support
   via email / web / phone / chat / portal / social
              ↓
        Case created
              ↓
   Entitlement matched → milestones started
              ↓
   Assignment rules or Omni-Channel routing
              ↓
      Agent works the case
        (console, knowledge, macros)
              ↓
   Escalation if milestones breach
              ↓
        Case resolved
              ↓
   Customer notified, satisfaction survey
              ↓
   Knowledge article created or updated
```

Each step is a place where configuration, automation, or integration lives, and the rest of section 05 works through them in order.

## Case as an object

`AccountId`, `ContactId`, `Subject`, `Description`, `Status`, `Priority`, `Origin`, `Type`, `Reason`, `OwnerId`, `ParentId`, `IsEscalated`, `IsClosed`, `ClosedDate`, `EntitlementId`, `AssetId`, `SuppliedEmail`, `SuppliedName`, `CaseNumber`.

Three behaviours worth knowing immediately:

**`OwnerId` is polymorphic.** It can be a User (`005` prefix) or a Queue (`00G` prefix). Apex that assumes `Owner.Name` refers to a person breaks the moment a case sits in a queue.

```sql
SELECT Id, CaseNumber, OwnerId, Owner.Name,
       TYPEOF Owner WHEN User THEN Email, IsActive WHEN Group THEN DeveloperName END
FROM Case
WHERE Status = 'New'
```

**`IsClosed` is derived** from whether the case's status is flagged as closed in the support process configuration, exactly as `IsWon` works on Opportunity. You cannot write it.

**`CaseNumber` is auto-generated** and read-only, which means a migration from a legacy ticketing system cannot preserve the old numbers in that field. An external ID field is needed to hold them.

## Support processes and record types

A **Support Process** defines which Case statuses are available, tied to a Record Type — the same pattern as Sales Process on Opportunity.

Typical use in our manufacturing example:

```
Technical Support
  New → In Progress → Awaiting Customer → Awaiting Parts → Resolved → Closed

Warranty Claim
  Submitted → Under Review → Approved → Rejected → Closed

Billing Enquiry
  New → In Progress → Resolved → Closed
```

The design principle mirrors sales stages: **status should describe the state of the case, not what the agent last did.** "Awaiting Customer" is a state, and it is also the single most valuable status in any support model, because it separates time the team is responsible for from time the customer is responsible for. Without it, every service level metric is wrong.

## The metrics that drive design

Understanding what support leaders measure explains most of the feature set:

**First Response Time.** How long until a human replied. Usually the most contractually significant number.

**Resolution Time.** Creation to closure, ideally excluding time in customer-waiting statuses.

**First Contact Resolution.** Percentage resolved without a second interaction.

**Backlog.** Open cases, trended over time.

**Case volume by type and product.** What is actually breaking.

**CSAT.** Customer satisfaction, usually from a post-closure survey.

Every one of these depends on data captured during the case, which is why case field design matters more than it looks. A `Reason` picklist that is never filled in means nobody can answer what is breaking.

## Case hierarchies

`ParentId` allows parent and child cases. Two genuine uses:

**Splitting.** One customer report turns out to be three separate problems, each needing a different specialist.

**Grouping.** A widespread outage produces 400 cases; a parent case tracks the underlying incident and the individual cases attach to it.

The grouping case is where it earns its place, and the automation to attach and close children in bulk is a common build:

```java
public with sharing class ParentCaseService {

    public static void closeChildCases(Set<Id> parentCaseIds, String resolution) {
        List<Case> children = [
            SELECT Id, ParentId FROM Case
            WHERE ParentId IN :parentCaseIds AND IsClosed = false
        ];

        for (Case child : children) {
            child.Status = 'Closed';
            child.Resolution__c = resolution;
        }

        // partial success so one child failing validation does not block the rest
        Database.update(children, false);
    }
}
```

Note the query has no `LIMIT` and could return a very large number of children during a mass outage. In production this belongs in a Queueable or Batch job, chunked, rather than running synchronously from a trigger.

## What Service Cloud gives you free

Rebuilding any of these is a familiar and expensive mistake:

- Multi-channel case creation, including email threading
- Assignment, escalation, and auto-response rules
- Entitlement and milestone tracking with business hours
- Omni-Channel capacity-based routing
- The Service Console with tabs, split view, and utility bar
- Knowledge with versioning, approval, and data categories
- Macros and quick text
- CTI framework and Service Cloud Voice
- Einstein case classification and reply recommendations
- A large library of service report types
