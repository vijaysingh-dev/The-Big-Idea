# Organization-Wide Defaults

## The baseline

Organization-wide defaults, almost always shortened to **OWD**, set the minimum level of record access every user has to records they do not own.

This is the floor. Everything else in the sharing model — role hierarchy, sharing rules, manual shares, teams, Apex sharing — can only raise access above this floor. Nothing lowers it.

That asymmetry drives the entire design approach: **set OWD as restrictive as the business genuinely allows, then open access deliberately.**

## The settings

Per object, in Setup under Sharing Settings:

**Private.** Only the owner, users above the owner in the role hierarchy, and administrators can see the record. Everyone else sees nothing.

**Public Read Only.** Everyone can see every record. Only the owner and those above them can edit.

**Public Read/Write.** Everyone can see and edit every record. Only the owner and those above them can delete.

**Public Read/Write/Transfer.** Available on Lead and Case only. Adds the ability to change ownership.

**Controlled by Parent.** The record inherits its access entirely from a parent record. This is automatic and mandatory for master-detail children, and it is an option on a few standard relationships such as Contact under Account.

**Public Full Access.** Available on Campaign only.

There is also a separate setting for **external users** — Experience Cloud users get their own OWD per object, which can be more restrictive than the internal one. This is how a partner portal shows partners only their own records while internal staff see everything.

## Choosing an OWD

The question to ask, precisely: *should a user be able to see records of this type that belong to someone else, by default?*

**Private** is right when records are personal, commercially sensitive, or territory-bound. Opportunities in a competitive sales organization. Warranty claims containing customer detail. Anything with personal or financial data.

**Public Read Only** is right when visibility helps and editing should stay with the owner. Accounts and Contacts in many organizations — everyone benefits from seeing the customer list, but only the account owner should change it.

**Public Read/Write** is right for genuinely shared operational data where collaboration matters more than control. Reference data, shared task lists, internal knowledge records.

**Controlled by Parent** is right when the child has no independent meaning. Claim lines under a claim.

The default instinct that serves best: **Private for anything with commercial or personal content, Public Read Only for reference and directory data.** You can always open access with a sharing rule. You cannot close it without a recalculation event.

## Standard object dependencies

Several standard objects have OWD relationships that constrain each other, and getting caught by these is common.

**Contact cannot be more permissive than Account.** If Account is Private, Contact must be Private or Controlled by Parent.

**Opportunity and Case relate to Account** through implicit sharing: access to an Opportunity grants read access to its Account. See [[03.10 - Manual, Team and Implicit Sharing]].

**Price Book has its own model** — Use, View Only, or No Access — which is unlike anything else.

**Contact is very often set to Controlled by Parent**, which is usually the right answer because a contact without its account has little meaning.

## Changing OWD after go-live

This is why the decision matters so much at design time.

**Making OWD more restrictive** — Public Read Only to Private — requires the platform to recalculate sharing for every record of that object. On an object with millions of rows this is a long-running background job, during which users may see inconsistent access. It is a scheduled maintenance activity, not a configuration tweak.

**Making OWD more permissive** also triggers recalculation, though it is generally less disruptive.

**Changing OWD on an object with many sharing rules** compounds the cost, because every rule must be re-evaluated against every record.

Practical guidance: decide OWD before the object holds significant data. If a change is genuinely needed later, schedule it, communicate it, and expect the recalculation to take hours on a large object. See [[23.3 - Sharing at Scale and Sharing Recalculation]].

## Grant Access Using Hierarchies

Alongside each object's OWD is a checkbox: **Grant Access Using Hierarchies**.

When enabled, users above a record's owner in the role hierarchy inherit the owner's access. This is on by default and cannot be disabled for standard objects.

For custom objects it can be turned off, and there is one situation where that is the right call: when managers genuinely should not see their reports' records. Human resources data, personal performance records, or a peer-review process are the usual examples. In every other case, leaving it on is correct, because managers seeing their team's work is the normal expectation.

Turning it off is worth knowing about precisely because it is the only way to prevent hierarchical access, and people frequently assume there is no such mechanism.

## Verifying OWD in code

The sharing model is exposed through describe:

```java
Schema.DescribeSObjectResult claimDescribe = Warranty_Claim__c.SObjectType.getDescribe();
System.debug('Sharing model: ' + claimDescribe.getSObjectType());
```

More usefully, the `UserRecordAccess` object answers "what access does this specific user have to this specific record", which is the single most useful query when debugging an access problem:

```sql
SELECT RecordId, HasReadAccess, HasEditAccess, HasDeleteAccess, HasTransferAccess,
       MaxAccessLevel
FROM UserRecordAccess
WHERE UserId = '0055g00000ABCDeAAN'
  AND RecordId IN ('a0X5g000001AbCdEAK', 'a0X5g000001AbCdFAK')
```

This is worth committing to memory. Instead of reasoning through OWD, hierarchy, and four sharing rules, ask the platform directly.

The share object for each object also records why access exists:

```sql
SELECT ParentId, UserOrGroupId, AccessLevel, RowCause
FROM Warranty_Claim__Share
WHERE ParentId = 'a0X5g000001AbCdEAK'
```

`RowCause` names the mechanism: `Owner`, `Manual`, `Rule`, `ImplicitChild`, `Team`, or a custom Apex sharing reason. Combined with `UserRecordAccess`, these two queries resolve almost every access question in an org.

Note that share objects only exist for objects whose OWD is more restrictive than Public Read/Write. If everyone can already see everything, there is nothing to record.

## Design guidance

**Start private and open up.** More work initially, dramatically less work than tightening later.

**Set OWD before loading data.** The recalculation cost scales with record count.

**Document the reasoning.** "Why is Machine private?" should have a recorded answer, because someone will propose changing it.

**Be careful with Public Read/Write on high-volume objects.** No share rows are maintained, which is efficient, but it also means there is no mechanism to restrict anything later without a full recalculation.

**Remember that OWD is per object, not per record type.** Two business processes on one object share one baseline. If they genuinely need different visibility, that is a signal they might need different objects — or that criteria-based sharing rules are the answer. See [[03.9 - Sharing Rules]].
