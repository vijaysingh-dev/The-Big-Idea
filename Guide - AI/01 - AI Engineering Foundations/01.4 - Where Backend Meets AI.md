# Where Backend Meets AI

## Your Existing Skills Already Apply

As a backend engineer, you already understand the problems AI systems face — you've just seen them in different contexts. Here's the translation:

|Backend Problem|AI System Equivalent|
|---|---|
|API rate limiting|LLM token rate limits, request quotas|
|Async job queues|Document ingestion pipelines (Celery/Redis)|
|Database indexing|Vector index construction (HNSW, IVF)|
|Cache invalidation|Embedding cache staleness, index freshness|
|Distributed tracing|LLM call tracing (LangSmith, Langfuse)|
|Schema validation|Structured output validation from LLMs|
|Retry logic|LLM API failure handling + fallback models|
|Multi-tenancy|Per-tenant document isolation in vector DBs|
|Batch processing|Bulk embedding, parallel chunk processing|
|Observability|Prompt/response logging, eval pipelines|

## Where AI Introduces NEW Problems

These are genuine new challenges that backend patterns don't fully address:

### 1. Non-Determinism

LLMs produce different outputs for the same input. This breaks standard testing assumptions.

**Implication**: You can't write `assertEqual(llm_output, expected)`. You need probabilistic evaluation — LLM-as-judge, human eval, or embedding similarity scoring. See [[../10 - Production AI Engineering/10.5 - Evaluation Pipelines and Monitoring]].

### 2. Latency Profile is Inverted

In backend systems, you optimize hot paths. In AI systems, the bottleneck _is_ the hot path — the LLM call itself takes 1–30 seconds and you can't make it faster by indexing differently.

**Implication**: Optimization focuses on reducing the number of LLM calls (caching, early termination), parallelizing retrieval, and streaming responses to hide latency. See [[../10 - Production AI Engineering/10.1 - Latency and Cost Optimization]].

### 3. Failure Modes are Invisible

A database returns an error code. An LLM returns a confident but wrong answer. Silent failures are the hardest to catch.

**Implication**: You need active monitoring of answer quality, not just uptime and error rates. Retrieval quality degradation (e.g., index drift) can silently destroy answer quality.

### 4. Cost Scales With Usage in Unexpected Ways

In traditional systems, cost scales with compute. In LLM systems, cost scales with _tokens_ — and verbose prompts, long contexts, and chain-of-thought can silently 10x your costs.

**Implication**: Token budgeting is a first-class engineering concern. See [[../10 - Production AI Engineering/10.1 - Latency and Cost Optimization]].

### 5. Context Window as a Resource

The LLM's context window is like RAM — finite, expensive, and you must carefully manage what you put in it. Everything you include competes for attention.

**Implication**: Context assembly is a core engineering problem. How you pack the context window determines answer quality more than the model you use.

## The Backend Engineer's Entry Path into AI Systems

```
Phase 1 — Understand the AI layer (Weeks 1–4)
├── LLM APIs: OpenAI, Anthropic — understand tokens, context, costs
├── Embeddings: what they are, cosine similarity, why they enable search
└── Vector DBs: Chroma/Qdrant locally, understand ANN search

Phase 2 — Build a RAG system (Weeks 5–8)
├── Ingest documents → chunk → embed → store in vector DB
├── Query: embed query → search → retrieve top-K → assemble prompt → call LLM
└── Add: BM25 hybrid search, reranker, streaming response

Phase 3 — Production concerns (Weeks 9–16)
├── Evaluation: RAGAS metrics, LLM-as-judge pipeline
├── Observability: trace every query, log retrieval results
├── Latency: profile each stage, add caching, parallelize retrieval
└── Cost: token tracking, budget alerts, prompt compression

Phase 4 — Advanced systems (Months 4–6)
├── Agents: tool use, multi-step reasoning, failure recovery
├── Fine-tuning: LoRA for domain adaptation (when RAG isn't enough)
├── Multi-tenant: per-tenant isolation, ACL-aware retrieval
└── Read Onyx codebase in depth
```

## Key Mental Shift

**Backend mindset**: "Make the system correct and fast."

**AI engineering mindset**: "Make the system _probably_ correct, measure that probability continuously, and degrade gracefully when it's wrong."

The shift is from **correctness by construction** to **correctness by measurement**.

This is uncomfortable at first, but it's the right mental model for systems built on probabilistic components.
