# Real World Integration Architectures

## Five worked designs

Each with the decision, the mechanism, and the reasoning. The running example remains Northwind Industrial from [[04.18 - End to End Enterprise Sales Cloud Design]] and [[05.16 - End to End Enterprise Service Cloud Design]].

---

## 1. ERP: the product and price catalogue

**Requirement.** SAP owns the product master. Around 4,000 products, prices in three currencies, changing daily.

**Direction.** SAP to Salesforce, one way.

**Latency.** Overnight is fine.

**Design:** scheduled Bulk API load.

```
02:00  SAP exports a delta CSV to SFTP
02:15  A middleware job picks it up
02:20  Bulk API 2.0 upsert on ERP_Product_Code__c → Product2
02:35  Bulk API upsert → PricebookEntry, standard price book first
02:50  Bulk API upsert → PricebookEntry, regional price books
03:10  Reconciliation: count comparison, discrepancies logged
```

**Why Bulk, not REST:** 4,000 products with three price book entries each is 16,000 records. Through REST that is 80 sObject Collections calls; through Bulk it is four jobs consuming almost none of the daily allocation.

**Why the ordering matters:** a product must have a standard price book entry before any custom one. Getting this wrong fails every row of the second load. See [[04.10 - Products, Price Books and Pricing]].

**Idempotency:** upsert on `ERP_Product_Code__c`, so a rerun updates rather than duplicating.

**Failure handling:** the failed-results file drives a retry of just those rows. Repeated failures on the same product raise an alert rather than being retried indefinitely.

## 2. ERP: closed-won opportunities

**Requirement.** When a deal closes won, create an order in SAP.

**Direction.** Salesforce to SAP.

**Latency.** Within minutes.

**Design:** platform event with a subscriber that calls out.

```
Opportunity trigger
    → detects the transition to Closed Won (oldMap comparison)
    → publishes Opportunity_Won__e

Platform event subscriber
    → queries the opportunity and its line items
    → POSTs to the middleware with an idempotency key
    → stores the SAP order number back on the opportunity
```

**Why an event, not a Queueable:** three consumers eventually needed this — SAP, the fulfilment system, and a revenue-reporting warehouse. Adding the second and third required no change to the publisher.

**Why not synchronous:** a callout cannot follow DML, and SAP being down should not prevent a rep closing a deal.

**Idempotency:** an `Idempotency-Key` header of `opportunityId + LastModifiedDate`, and the stored SAP order number as a guard — a claim with a confirmation is skipped.

**Retry:** a Finalizer on the subscriber's callout job, four attempts with exponential backoff, then a `Integration_Failure__c` record for manual review. See [[13.17 - Error Handling, Retries and Idempotency]].

## 3. ERP: invoice history

**Requirement.** Support agents need to see a customer's invoices — twelve years, several million rows.

**Direction.** Read only, on demand.

**Design:** external objects through Salesforce Connect.

```
ERP exposes an OData endpoint
    → Salesforce Connect external data source
        → ErpInvoice__x external object
            → indirect lookup on Account.ERP_Account_Id__c
                → related list on the Account page
```

**Why not sync:** several million invoice records would consume substantial storage, need a nightly sync, and be stale between runs. The data is read-only and rarely accessed.

**The tradeoffs accepted:** no reporting on invoices in Salesforce, no automation on them, and the related list shows an error when the ERP is down. All acceptable, because the requirement is "let the agent look it up".

**What would change the decision:** if invoices needed to appear in Salesforce reports or drive automation, they would have to be synced. See [[02.14 - External Objects and Salesforce Connect]].

## 4. Machine telemetry

**Requirement.** Machines emit fault codes. High volume, and a critical fault must create a case within minutes.

**Direction.** Machines to Salesforce.

**Design:** filtered at the edge, platform event inbound.

```
Machines → IoT gateway → Kafka
    → a consumer filters: only faults above a severity threshold
        → publishes Machine_Fault__e to Salesforce via Pub/Sub API
            → platform event-triggered flow
                → resolves the Asset by serial number
                → creates a Case with the right priority and queue
```

**Why filtering happens outside Salesforce:** raw telemetry is millions of readings a day. Sending all of it would exhaust the event allocation and provide no value — Salesforce only needs the faults.

**Why publish an event rather than call a REST endpoint:** the external system does not wait, Salesforce processes asynchronously with its own limits, and adding a second Salesforce-side consumer needs no change upstream.

**Historical readings** go to a big object through a separate nightly Bulk load, so a component on the Asset page can show trend data without any of it living in a normal object. See [[02.15 - Big Objects]].

## 5. Data warehouse replication

**Requirement.** A warehouse needs current Salesforce data for reporting across systems.

**Direction.** Salesforce to warehouse.

**Latency.** Near real time preferred; hourly acceptable.

**Design considered two ways, and the honest comparison matters.**

**Option A: Change Data Capture with a Pub/Sub subscriber.**

```
CDC enabled on Account, Opportunity, Case, Warranty_Claim__c
    → Pub/Sub API subscriber on the warehouse side
        → applies changes to the warehouse tables
        → persists the replay Id after each successful batch
```

*Gains:* near real-time, and deletions are visible.
*Costs:* a subscriber process to operate and monitor, gap-event handling, replay Id management, and a 72-hour retention window beyond which recovery means full reconciliation.

**Option B: hourly Bulk API extract on `SystemModstamp`.**

```
Hourly job queries each object where SystemModstamp > last run
    → Bulk API query job
        → CSV to the warehouse
```

*Gains:* far simpler, nothing long-running to operate, trivially recoverable.
*Costs:* up to an hour of latency, and **deletions are invisible** — a deleted record simply stops appearing.

**Chosen: Option B, with a weekly full reconciliation** to catch deletions and divergence.

The reasoning: hourly latency met the actual reporting requirement, and the operational cost of a continuously running subscriber was not justified. The deletion gap is handled by the weekly reconciliation rather than by a more complex mechanism.

**This is the decision most often made the other way for the wrong reason** — streaming looks more sophisticated. It is worth being explicit that polling is frequently correct. See [[12.9 - Change Data Capture]].

## The architecture as a whole

```
                          ┌──────────────────┐
    SAP ◄──── Bulk ───────┤                  │
        ◄──── Events ─────┤                  │
                          │                  │
    Machines ── Kafka ────► SALESFORCE       │
                          │                  │
    Warehouse ◄─ Bulk ────┤                  │
                          │                  │
    Invoices ◄─ OData ────┤ (external obj)   │
                          └──────────────────┘
```

Four mechanisms, each chosen for a specific reason: Bulk for volume, events for decoupled notification, external objects for data that should not move, and a filtered stream for high-frequency telemetry.

## The decisions that mattered most

Looking back across all five, the choices that shaped everything else.

**Source of truth per field, written down.** SAP owns product data, pricing, and billing address; Salesforce owns opportunity, case, activity, and segment. Ambiguity here produces update loops, and the document preventing them costs an afternoon.

**External IDs on every integrated object, from day one.** `ERP_Product_Code__c`, `ERP_Account_Id__c`, `ERP_Claim_Id__c`. Every one gives an index and makes every write idempotent. Retrofitting them onto populated objects is a backfill project. See [[10.3 - Upsert, Merge and External IDs]].

**One integration user per system**, each with a permission set granting exactly what it touches, no role, and no `View All Data`. The most commonly skipped security measure, and the highest value.

**Correlation Ids on every callout and event**, so a business operation can be traced across two systems' logs.

**A reconciliation job per integration**, because silent divergence has no symptom.

## What was deliberately not built

**No middleware initially.** Three systems and simple transformations did not justify it. The design leaves room — Salesforce calls one endpoint per system — so introducing a broker later is a configuration change rather than a rewrite. See [[13.18 - MuleSoft and Middleware Basics]].

**No custom Apex REST endpoints for record CRUD.** SAP uses the standard REST and Bulk APIs. Custom endpoints exist only for genuine business operations — claim submission, which involves coverage checking and approval routing.

**No CDC on high-volume objects.** Case and Warranty Claim were candidates and were rejected: the delivery allocation cost per subscriber, against a requirement that hourly polling satisfied.

**No real-time inventory lookup on the case page.** It was requested, and it would have meant a Continuation against a system whose 95th-percentile response time was eleven seconds. Instead, inventory is synced hourly into a custom object and displayed from there, with a manual refresh action for the rare case where currency matters.

That last one is worth dwelling on: **the requested design was a real-time integration, and the right answer was a cached one.** Asking what latency the business actually needs, rather than what it asks for, changed a fragile synchronous dependency into a simple scheduled job.

## Section 13 in one paragraph

Integration design starts with three questions — which system owns each field, which direction data flows, and whether the caller needs the answer now — and the answers determine everything after. The API is a consequence: REST for moderate CRUD, Bulk above a few thousand records, Composite Graph for record graphs, events for decoupling, external objects for data that should stay where it is. Authenticate with JWT and a dedicated, minimally scoped integration user; never store a password, and never hand-roll token handling when Named Credentials exist. Callouts cannot follow DML, which pushes most outbound work into Queueables and event subscribers. Everything fails eventually, so classify failures as transient or permanent, retry only the transient ones with backoff and a cap, make every write idempotent through external IDs, log with correlation Ids, and run a reconciliation job — because the failures that hurt are the silent ones, and the integration that stopped running looks exactly like the one that has nothing to do.
