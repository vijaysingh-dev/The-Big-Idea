# async await

`async/await` is syntax over promises. It changes nothing about how they work — it changes how the code reads, and it restores `try/catch` for asynchronous errors.

## The two keywords

**`async`** on a function means: this function always returns a promise. A returned value is wrapped, a thrown error becomes a rejection.

```js
async function f() { return 1; }
f(); // Promise { 1 }

async function g() { throw new Error("x"); }
g(); // Promise { <rejected> Error: x }
```

**`await`** pauses the function until a promise settles, then resumes with its value — or throws its rejection reason.

```js
async function load() {
  const user = await getUser(1);       // unwraps the promise
  const orders = await getOrders(user.id);
  return { user, orders };
}
```

`await` on a non-promise still works: the value is wrapped with `Promise.resolve` and the continuation is still deferred to a microtask.

## What it desugars to

```js
async function load() {
  const user = await getUser(1);
  const orders = await getOrders(user.id);
  return { user, orders };
}

// roughly equivalent to
function load() {
  return getUser(1).then(user =>
    getOrders(user.id).then(orders => ({ user, orders }))
  );
}
```

The compiled form is actually a state machine driven by a generator, which is why generators and `async` functions share machinery ([[06.6 - Iterators and Generators]]).

## The execution model

An `async` function runs **synchronously until the first `await`**. Then it returns a pending promise to its caller and schedules its continuation as a microtask.

```js
async function f() {
  console.log("1");
  await null;
  console.log("3");
}

f();
console.log("2");
// 1, 2, 3
```

Nothing about `async` moves work to another thread. A synchronous 500 ms computation inside an `async` function still blocks the main thread for 500 ms ([[01.4 - The Event Loop]]).

And because `await` yields to the **microtask** queue, not a task boundary, the browser does not repaint in between. This is why a loading spinner set just before an `await` of synchronous work never appears ([[01.6 - Microtasks vs Macrotasks]]).

## The sequential-await performance bug

```js
// 900ms — each waits for the previous
const user = await getUser();     // 300ms
const posts = await getPosts();   // 300ms
const tags = await getTags();     // 300ms

// 300ms — all three start immediately
const [user, posts, tags] = await Promise.all([getUser(), getPosts(), getTags()]);
```

The rule: `await` sequentially only when a later call genuinely needs an earlier result. This is the most common real performance problem in `async` code, and it is easy to miss in review because sequential awaits read so naturally.

A middle case — start everything, await later:

```js
const userPromise = getUser();
const configPromise = getConfig();

const user = await userPromise;
if (user.needsConfig) {
  const config = await configPromise; // already in flight
}
```

Careful: if `configPromise` rejects and you never await it, you get an unhandled rejection. Attach a `.catch(() => {})` or use `Promise.allSettled`.

## Error handling

```js
async function load() {
  try {
    const data = await fetchData();
    return process(data);
  } catch (err) {
    if (err instanceof HttpError && err.status === 404) return null;
    throw err;
  } finally {
    setLoading(false);
  }
}
```

`try/catch` now works across asynchronous boundaries, which it never could with callbacks ([[04.1 - Callbacks and Callback Hell]]). Note that `catch` here also catches synchronous errors from `process(data)` — usually desirable, occasionally too broad.

Two common patterns for narrower handling:

```js
// Handle one call's failure without wrapping everything
const data = await fetchData().catch(() => null);

// Go-style tuple, avoids nesting try blocks
const [err, data] = await fetchData().then(d => [null, d], e => [e, null]);
```

## Loops

```js
// Sequential — sometimes exactly what you want (rate limits, ordering)
for (const id of ids) {
  await process(id);
}

// Parallel
await Promise.all(ids.map(id => process(id)));

// Broken — forEach ignores the returned promise, so nothing is awaited
ids.forEach(async id => { await process(id); });
```

The `forEach` version completes immediately and the work continues unobserved, with any rejections becoming unhandled. `forEach` has no awareness of promises. Use `for...of` for sequential and `map` + `Promise.all` for parallel.

For bounded parallelism — the usual production requirement — use a concurrency limiter ([[04.7 - Async Concurrency Patterns]]).

## Top-level await

Available in ES modules only:

```js
// module.js
const config = await fetch("/config.json").then(r => r.json());
export { config };
```

Any module importing this one waits for it. Convenient for configuration, dangerous on a critical path: it delays module evaluation for every dependent, and a rejection becomes a module load failure. It does not work in CommonJS or in classic scripts ([[08.1 - ES Modules vs CommonJS]]).

## async in React

```js
// Invalid — an async function returns a promise, but useEffect expects a cleanup function
useEffect(async () => {
  const data = await fetchData();
  setData(data);
}, []);

// Correct
useEffect(() => {
  let cancelled = false;

  (async () => {
    const data = await fetchData();
    if (!cancelled) setData(data);
  })();

  return () => { cancelled = true; };
}, []);
```

The `cancelled` flag prevents setting state after unmount, and — more importantly — prevents a slow earlier request from overwriting a fast later one when dependencies change. A better solution is `AbortController` ([[04.6 - AbortController and Cancellation]]), and a better solution still is to not fetch in effects at all ([[24.6 - TanStack Query Fundamentals]]).

Also note components themselves cannot be `async` in client React. Server Components can ([[22.8 - Server Components]]).

## How senior engineers actually use this

**They audit every consecutive pair of awaits.** "Does the second actually need the first?" is a habitual question in code review, and the answer is often no.

**They keep `try` blocks narrow.** Wrapping an entire function body catches rendering and processing errors alongside network ones, making the handler either wrong or vague.

**They never mix `await` with `.then` in the same function.** Pick one style per function; mixing makes control flow hard to follow and is a frequent source of missed error paths.

**They mark fire-and-forget calls explicitly.** `void logAnalytics()` or `logAnalytics().catch(noop)` communicates intent and prevents unhandled rejections. A bare unawaited call looks like a bug.

## Common pitfalls

- Sequential awaits for independent work.
- `forEach` with an `async` callback.
- `async` directly as a `useEffect` callback.
- Assuming `await` yields to rendering. It yields to microtasks only.
- Forgetting that `async` adds a microtask even when nothing is actually asynchronous, so ordering relative to synchronous code changes.
- Starting a promise, awaiting it conditionally, and getting an unhandled rejection on the branch that skips it.

## Interview angle

"How does `async/await` work internally" wants: syntax over promises, compiled to a generator-driven state machine, the function runs synchronously to the first `await` then returns a pending promise, and each `await` resumes via a microtask. Follow with the sequential-vs-parallel bug and the `forEach` trap unprompted — both are things interviewers plant in code-reading questions.
