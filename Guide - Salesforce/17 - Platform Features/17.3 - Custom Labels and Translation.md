# Custom Labels and Translation

## The problem

```java
claim.addError('This claim exceeds the coverage limit on the service contract.');
```

That string is in English, in code, and changing it requires a deployment. In an org with users in Mumbai, Frankfurt, and Osaka, two-thirds of them read an error message in a language they may not use.

**Custom Labels** move user-facing text out of code and make it translatable.

```java
claim.addError(Label.Claim_Exceeds_Coverage_Limit);
```

## Defining one

```
Setup → Custom Labels → New

Short Description:  Claim Exceeds Coverage Limit
Name:               Claim_Exceeds_Coverage_Limit
Categories:         Claims, Validation
Value:              This claim exceeds the coverage limit on the service contract.
```

`Name` is what code references. `Categories` is a comma-separated tag list, and it is the only organizational mechanism available — labels are a flat namespace, so a naming convention matters.

```
Claim_Error_Exceeds_Coverage
Claim_Error_No_Active_Contract
Claim_Success_Approved
Claim_Button_Submit
Claim_Help_Approval_Process
```

Prefixing by domain and type is worth doing from the start. An org with 400 labels named arbitrarily is unnavigable.

## Using them

**Apex:**

```java
String message = Label.Claim_Exceeds_Coverage_Limit;
```

**LWC:**

```javascript
import CLAIM_EXCEEDS_LIMIT from '@salesforce/label/c.Claim_Exceeds_Coverage_Limit';
import SUBMIT_BUTTON from '@salesforce/label/c.Claim_Button_Submit';

export default class ClaimForm extends LightningElement {
    // exposing a single object keeps the template tidy
    labels = {
        exceedsLimit: CLAIM_EXCEEDS_LIMIT,
        submit: SUBMIT_BUTTON
    };
}
```

```html
<lightning-button label={labels.submit}></lightning-button>
```

**Flow:** available in the resource picker under Global Constants.

**Validation rules and formulas:**

```
$Label.Claim_Exceeds_Coverage_Limit
```

**Aura:**

```xml
{!$Label.c.Claim_Exceeds_Coverage_Limit}
```

The `c.` namespace prefix is required in Aura and LWC imports, and omitted in Apex and formulas — a small inconsistency worth remembering.

## Merge fields

Labels support positional placeholders:

```
Value: Claim {0} exceeds the coverage limit of {1} for machine {2}.
```

```java
String message = String.format(
    Label.Claim_Exceeds_Coverage_Limit,
    new List<String>{ claim.Claim_Number__c, formattedLimit, serialNumber }
);
```

```javascript
import { format } from 'c/labelUtils';

const message = format(CLAIM_EXCEEDS_LIMIT, [claimNumber, limit, serial]);
```

There is no built-in JavaScript formatter, so a small utility is standard:

```javascript
// c/labelUtils/labelUtils.js
export function format(template, params) {
    return template.replace(/\{(\d+)\}/g, (match, index) => params[index] ?? match);
}
```

**Positional placeholders matter for translation.** Word order differs between languages, and `{0}` and `{1}` can be reordered by the translator in a way that concatenation cannot.

```java
// Cannot be reordered by a translator
String message = 'Claim ' + claimNumber + ' exceeds ' + limit;

// Can
String.format(Label.Claim_Exceeds, new List<String>{ claimNumber, limit });
```

## Translation

```
Setup → Translation Workbench → Enable
Setup → Translation Workbench → Translation Language Settings → add languages and translators
Setup → Translate → select language, setup component "Custom Label"
```

Translators enter values per label per language. At runtime the platform serves the value for the **user's language**, falling back to the master value when no translation exists.

**Export and import** for bulk work:

```
Setup → Translation Workbench → Export
  Source        untranslated values only
  Untranslated  what still needs work
  Bilingual     both, for review
```

The file is tab-delimited and goes to a translation vendor, who returns it for import. That round trip is how translation actually happens at scale rather than through the UI.

## What else is translatable

Custom Labels are one component among many:

```
Custom field labels and help text
Picklist values
Record type names
Page layout section names
Validation rule error messages
Quick action labels
App and tab names
Report and dashboard names
Knowledge articles
Email templates
Flow screen text
Lightning page component labels
```

**A field's label and its picklist values are separate translation components**, which is a common gap — the field is translated and its picklist values are not.

**Validation rule messages are translatable**, which means a validation rule using `$Label` is translated twice over. Referencing a label from the rule is the cleaner approach:

```
AND(
    ISPICKVAL(Status__c, "Approved"),
    Claim_Amount__c > 500000,
    NOT($Permission.Can_Approve_Large_Claims)
)
Error message: $Label.Claim_Error_Requires_Executive_Approval
```

## User language versus locale

Two separate settings that people conflate.

**Language** determines the interface text and translated values.

**Locale** determines number, date, currency, and name formats.

A user in Frankfurt might read English but expect `31.12.2026` and `1.234,56 €`. Setting one and not the other produces a half-localized experience.

**Locale formatting is handled by the platform** when you let it:

```html
<lightning-formatted-number value={amount} format-style="currency" currency-code="EUR">
</lightning-formatted-number>

<lightning-formatted-date-time value={claimDate}></lightning-formatted-date-time>
```

```java
String formatted = claim.Claim_Amount__c.format();   // running user's locale
String dateText = claim.Claim_Date__c.format();
```

Hand-formatting a date as `MM/DD/YYYY` in JavaScript defeats this and is wrong for most of the world. See [[14.13 - Base Components and lightning-datatable]].

## Limits

```
5,000 custom labels per org
1,000 characters per label value
Labels are cached and read at no query cost
Categories are free-text and unenforced
```

The 5,000 cap is generous and reachable in a large managed package. Within a normal org it is not a practical concern.

**Label values cannot be changed by Apex.** They are metadata, deployed like anything else.

## Where labels help beyond translation

Even in a single-language org, they earn their place.

**Consistency.** One label used in six places means one edit rather than six.

**Editable without a deployment** — a label value change is a metadata change an administrator can make in Setup, subject to the org's change management.

**Findability.** Searching for user-facing text across a codebase is unreliable; searching the label list is not.

**Reviewability.** A pull request changing a message shows the label value, not a string buried in a method.

An org that puts every user-facing message in a label ends up with a readable inventory of everything the system says.

## What not to make a label

**Debug output and log messages.** Nobody translates a log.

**Field API names, developer names, and technical identifiers.**

**Anything dynamic** that would need a label per value. A label per country name is worse than a picklist with translated values.

**Very long content.** A 1,000-character cap and no rich text make labels wrong for help content — that belongs in Knowledge or a static resource.

## Testing

```java
@IsTest
static void errorMessageUsesTheLabel() {
    Warranty_Claim__c claim = TestDataFactory.buildClaim(900000);

    Test.startTest();
    Database.SaveResult result = Database.insert(claim, false);
    Test.stopTest();

    Assert.isFalse(result.isSuccess());
    // asserting on the label, not the literal, so a wording change does not break the test
    Assert.areEqual(Label.Claim_Exceeds_Coverage_Limit,
        result.getErrors()[0].getMessage());
}
```

Asserting against `Label.X` rather than the literal string means a copy change does not break the test — which is the point of extracting it in the first place.

**Tests run in the org's default language**, so a translation is not exercised. Verifying a translation means logging in as a user with that language set.

## A rollout approach

For an org going multilingual, the sequence that works:

**1. Extract to labels.** Every user-facing string in Apex, LWC, and flow screens.

**2. Translate the schema first** — field labels, picklist values, record types. Users notice untranslated field labels more than untranslated error messages.

**3. Export, translate, import** rather than using the UI for volume.

**4. Set language and locale** on users, not just language.

**5. Test as a translated user.** A partially translated interface is more confusing than an untranslated one, and only a real login reveals the gaps.

**6. Add translation to the definition of done.** A new field without a translation is a regression, and it accumulates quickly without a process.

## Practical guidance

**Put every user-facing string in a label**, even in a single-language org.

**Use a naming convention** — domain, then type, then meaning.

**Use `String.format` with positional placeholders**, never concatenation, so translators can reorder.

**Translate picklist values as well as field labels** — they are separate components.

**Reference labels from validation rules** rather than typing the message inline.

**Set locale as well as language** on users.

**Assert against `Label.X`** in tests, not the literal.

**Export and import in bulk** for real translation work.
