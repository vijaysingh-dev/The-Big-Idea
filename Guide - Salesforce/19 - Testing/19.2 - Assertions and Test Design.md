# Assertions and Test Design

## The test that proves nothing

```java
@IsTest
static void testApprove() {
    Warranty_Claim__c claim = new Warranty_Claim__c(Claim_Amount__c = 150000);
    insert claim;

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 120000);
    Test.stopTest();
}
```

It passes. It produces coverage. It will pass if `approve` is emptied to a no-op, if the status is set to the wrong value, or if it silently swallows an exception.

**Coverage measures what executed. Assertions measure what was verified.** A codebase at 78% with meaningful assertions is in better shape than one at 95% with none.

## The rewrite

```java
@IsTest
static void approvalSetsStatusAndAmountAndCreatesAPayment() {
    Warranty_Claim__c claim = TestDataFactory.createClaimWithCoverage(150000, 200000);

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 120000);
    Test.stopTest();

    Warranty_Claim__c refreshed = [
        SELECT Status__c, Approved_Amount__c, Approved_Date__c
        FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];

    Assert.areEqual('Approved', refreshed.Status__c,
        'A claim within its coverage limit should be approved');
    Assert.areEqual(120000, refreshed.Approved_Amount__c,
        'The approved amount should be what was passed, not the claimed amount');
    Assert.areEqual(Date.today(), refreshed.Approved_Date__c,
        'The approval date should be stamped');

    List<Claim_Payment__c> payments = [
        SELECT Amount__c FROM Claim_Payment__c WHERE Warranty_Claim__c = :claim.Id
    ];
    Assert.areEqual(1, payments.size(), 'Approval should create exactly one payment');
    Assert.areEqual(120000, payments[0].Amount__c, 'The payment matches the approved amount');
}
```

Same coverage. Entirely different value.

## The mutation check

The most useful discipline in test design, and it takes seconds.

**Break the code deliberately and confirm the test fails.**

```java
public static void approve(Set<Id> claimIds, Decimal amount) {
    for (Warranty_Claim__c claim : claims) {
        claim.Status__c = 'Approved';
        // claim.Approved_Amount__c = amount;     ← comment this out
    }
}
```

If the test still passes, it was not testing that line. Running this check on a handful of assertions in a new test class reveals more about its quality than reading it does.

## Assertion messages

```java
// A failure report that requires opening the file
Assert.areEqual('Approved', claim.Status__c);

// A failure report that explains itself
Assert.areEqual('Approved', claim.Status__c,
    'A claim within its coverage limit should be approved automatically');
```

The message is read by someone six months from now, in a CI log, with no context. Write it as an explanation of the expected behaviour, not a restatement of the code.

**Include the actual value when it helps:**

```java
Assert.isTrue(Limits.getQueries() < 30,
    'Expected fewer than 30 queries for 200 records, used ' + Limits.getQueries());
```

## Argument order

```java
Assert.areEqual(expected, actual, message);
```

**Expected first.** Reversing it produces a backwards failure message — `Expected: Submitted, Actual: Approved` when the truth is the opposite — which sends the reader in the wrong direction.

## Test one behaviour

```java
// Tests four things; a failure tells you little
@IsTest
static void testClaimProcessing() {
    testApproval();
    testRejection();
    testEscalation();
    testNotification();
}
```

```java
// Four tests; a failure names the broken behaviour
@IsTest
static void claimsWithinCoverageAreApproved() { }

@IsTest
static void claimsOverCoverageAreRejected() { }

@IsTest
static void highValueClaimsEscalateToExecutive() { }

@IsTest
static void approvalNotifiesTheErp() { }
```

**One behaviour per method.** When three fail, you learn three things instead of one.

The exception: several assertions verifying **one** behaviour — status, amount, and date after an approval — belong together, because they describe one outcome.

## The cases worth covering

For any piece of logic, in order of value.

**The happy path.** It works.

**The boundaries.** Where the behaviour changes.

```java
@IsTest
static void theCoverageLimitIsInclusive() {
    Warranty_Claim__c claim = TestDataFactory.createClaimWithCoverage(500000, 500000);

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, 500000);
    Test.stopTest();

    // exactly at the limit — the case an off-by-one gets wrong
    Assert.areEqual('Approved', refresh(claim).Status__c,
        'A claim exactly at the coverage limit should be approved');
}
```

**Boundaries are where defects live.** A claim at 499,999, at 500,000, and at 500,001 tests the rule; a claim at 150,000 tests nothing about the boundary.

**The negative cases.** What should be rejected, blocked, or skipped.

**Nulls and empties.** A null amount, an empty list, a missing parent.

```java
@IsTest
static void nullAmountsDoNotThrow() {
    Warranty_Claim__c claim = TestDataFactory.createClaim(null);

    Test.startTest();
    ClaimApprovalService.approve(new Set<Id>{ claim.Id }, null);
    Test.stopTest();

    Assert.areEqual('Pending Review', refresh(claim).Status__c,
        'A claim with no amount should route for manual review rather than failing');
}
```

**Bulk.** 200 records, with a realistic parent distribution.

**Permissions.** As a user without the relevant access, using `System.runAs`.

## Bulk tests are not optional

```java
@IsTest
static void rollupIsCorrectWhenClaimsShareAnAsset() {
    List<Asset> assets = TestDataFactory.createAssets(50);

    List<Warranty_Claim__c> claims = new List<Warranty_Claim__c>();
    for (Integer i = 0; i < 200; i++) {
        // four claims per asset — the distribution a broken aggregation gets wrong
        claims.add(TestDataFactory.buildClaim(assets[Math.mod(i, 50)].Id, 10000));
    }

    Test.startTest();
    insert claims;
    Test.stopTest();

    Map<Id, Asset> refreshed = new Map<Id, Asset>([
        SELECT Id, Open_Claim_Count__c, Total_Claim_Value__c FROM Asset WHERE Id IN :assets
    ]);

    for (Asset asset : assets) {
        Assert.areEqual(4, refreshed.get(asset.Id).Open_Claim_Count__c,
            'Each asset should have four claims');
        Assert.areEqual(40000, refreshed.get(asset.Id).Total_Claim_Value__c,
            'Each asset should total 40000');
    }
}
```

**The distribution matters as much as the count.** Two hundred claims across two hundred assets passes even with a broken aggregation; two hundred across fifty does not.

**A single-record test proves nothing about bulk safety**, and bulk safety is the property most likely to be wrong. See [[19.7 - Testing Triggers and Bulk Behaviour]].

## Asserting on limits

For anything on a hot object, worth adding.

```java
@IsTest
static void bulkInsertStaysWellWithinLimits() {
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(200);

    Test.startTest();
    insert claims;

    Assert.isTrue(Limits.getQueries() < 30,
        'Expected well under the query limit, used ' + Limits.getQueries());
    Assert.isTrue(Limits.getCpuTime() < 4000,
        'CPU headroom is thin: ' + Limits.getCpuTime() + 'ms');
    Test.stopTest();
}
```

A query added inside a loop passes every functional test and fails this one. It is the only mechanism that catches a limit regression before production. See [[16.7 - Designing Around Limits]].

## Arrange, act, assert

A structure that makes tests readable at a glance.

```java
@IsTest
static void escalatedClaimsAreAssignedToTheRegionalDirector() {
    // Arrange
    User director = TestUserFactory.createWithRole('Regional Director');
    Warranty_Claim__c claim = TestDataFactory.createClaim(900000);

    // Act
    Test.startTest();
    ClaimRoutingService.route(new List<Warranty_Claim__c>{ claim }, null);
    Test.stopTest();

    // Assert
    Warranty_Claim__c refreshed = [
        SELECT Approver__c, Approval_Tier__c FROM Warranty_Claim__c WHERE Id = :claim.Id
    ];
    Assert.areEqual('Executive', refreshed.Approval_Tier__c);
    Assert.areEqual(director.Id, refreshed.Approver__c,
        'An executive-tier claim should route to the regional director');
}
```

The comments are optional; the shape is not. A test where setup, action, and verification are interleaved is hard to read and usually testing more than one thing.

## Avoiding brittleness

Tests that break for the wrong reasons erode trust in the suite.

**Do not assert on message text you do not control:**

```java
// Breaks when someone improves the wording
Assert.areEqual('This claim exceeds the coverage limit on the service contract.', message);

// Stable
Assert.areEqual(Label.Claim_Error_Exceeds_Coverage, message);
```

**Do not depend on record order** unless the query has an `ORDER BY`.

**Do not depend on the current date:**

```java
// Fails at a month boundary
Assert.areEqual(Date.today().addDays(30), claim.Due_Date__c);

// Deterministic
ClockService.todayOverride = Date.newInstance(2026, 6, 15);
Assert.areEqual(Date.newInstance(2026, 7, 15), claim.Due_Date__c);
```

**Do not depend on org configuration** — inject the metadata rather than relying on deployed records. See [[18.10 - Custom Metadata Driven Architecture]].

**Do not assert on auto-numbers or generated Ids.**

## Testing what you did not write

A test can verify that a validation rule, a flow, or a roll-up behaves as intended — and doing so is worth it for the ones that carry business rules.

```java
@IsTest
static void theValidationRuleBlocksReopeningAClosedClaim() {
    Warranty_Claim__c claim = TestDataFactory.createClosedClaim();

    claim.Status__c = 'Under Review';

    Test.startTest();
    Database.SaveResult result = Database.update(claim, false);
    Test.stopTest();

    Assert.isFalse(result.isSuccess(), 'Reopening a closed claim should be blocked');
    Assert.areEqual(StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION,
        result.getErrors()[0].getStatusCode());
}
```

Declarative automation has no other test coverage, and it breaks as readily as code — someone deactivates the rule, or edits its criteria. A test is the only thing that notices.

## Characterization tests

Before refactoring code you did not write and do not fully understand, write tests asserting its **current** behaviour.

```java
@IsTest
static void currentBehaviour_statusIsSetToApprovedAndAmountIsHalved() {
    // documenting what it does today, correct or not, so the refactor can be verified
}
```

These are not tests of correct behaviour; they are a safety net. They should pass identically before and after the change, and they are the step that makes consolidating an org's triggers safe. See [[11.4 - One Trigger Per Object]].

## Practical guidance

**Every test asserts something meaningful.**

**Supply a message explaining the expected behaviour.**

**Expected first**, actual second.

**One behaviour per test method.**

**Test the boundaries**, not the middle.

**Test nulls, empties, and negative cases.**

**Test in bulk, with a realistic parent distribution.**

**Assert on limit consumption** for hot objects.

**Assert against labels and injected values**, not literals and today's date.

**Run the mutation check** — break the code and confirm the test fails.

**Write characterization tests before refactoring.**
