# Virtualization and Windowing

Rendering 10,000 rows creates 10,000 DOM subtrees. The browser must lay out, paint and maintain all of them, and memory grows linearly. **Virtualization** renders only the rows currently visible, plus a small buffer.

```
Viewport (shows 10 rows)
┌──────────────┐
│ row 42       │  ← rendered
│ row 43       │  ← rendered
│ ...          │
│ row 51       │  ← rendered
└──────────────┘
rows 0-41 and 52-9999: not in the DOM at all
```

## The mechanism

Three pieces:

1. A **scroll container** with fixed height and `overflow: auto`
2. A **spacer** with the full scrollable height, so the scrollbar is correct
3. Absolutely positioned visible items, offset by their index

```jsx
function VirtualList({ items, itemHeight = 40, height = 400 }) {
  const [scrollTop, setScrollTop] = useState(0);

  const startIndex = Math.max(0, Math.floor(scrollTop / itemHeight) - 3);
  const visibleCount = Math.ceil(height / itemHeight) + 6;
  const visible = items.slice(startIndex, startIndex + visibleCount);

  return (
    <div
      style={{ height, overflow: "auto" }}
      onScroll={e => setScrollTop(e.currentTarget.scrollTop)}
    >
      <div style={{ height: items.length * itemHeight, position: "relative" }}>
        {visible.map((item, i) => (
          <div
            key={item.id}
            style={{
              position: "absolute",
              top: (startIndex + i) * itemHeight,
              height: itemHeight,
              width: "100%",
            }}
          >
            {item.name}
          </div>
        ))}
      </div>
    </div>
  );
}
```

The `- 3` and `+ 6` are the **overscan** — extra rows rendered outside the viewport so fast scrolling does not reveal blank space before React catches up.

## Use a library

The version above works for fixed-height rows and nothing else. Real requirements include variable heights, horizontal scrolling, sticky headers, grids, scroll restoration, keyboard navigation, and accessibility. Building that is a project.

**TanStack Virtual** is the current standard — headless, framework-agnostic, handles dynamic measurement:

```jsx
import { useVirtualizer } from "@tanstack/react-virtual";

function List({ items }) {
  const parentRef = useRef(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40,
    overscan: 5,
  });

  return (
    <div ref={parentRef} style={{ height: 400, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map(v => (
          <div
            key={items[v.index].id}
            ref={virtualizer.measureElement}
            data-index={v.index}
            style={{
              position: "absolute",
              top: 0,
              transform: `translateY(${v.start}px)`,
              width: "100%",
            }}
          >
            <Row item={items[v.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

`measureElement` uses `ResizeObserver` to measure real heights as items render, which handles variable content without you supplying sizes ([[12.5 - Custom Events and Observer APIs]]).

`react-window` remains a lighter option for simple fixed-size lists; `react-virtuoso` handles complex cases like chat with reverse scrolling.

## Variable heights

The hard part. The total scroll height depends on item heights, which are unknown until rendered.

The standard approach is estimate-then-correct: start with an estimated size, measure items as they render, cache the measurements, and adjust offsets and total height. This causes small scrollbar adjustments while scrolling through unmeasured regions — visible but generally acceptable.

For content whose height can be computed from data (a known number of text lines), supplying an accurate `estimateSize` eliminates most of the jitter.

## Accessibility

Virtualization breaks assistive technology by default: only ten of ten thousand rows exist, so a screen reader reports ten items.

```jsx
<div role="grid" aria-rowcount={items.length}>
  <div role="row" aria-rowindex={virtualItem.index + 1}>
```

`aria-rowcount` and `aria-rowindex` tell assistive technology the real totals and positions. Also required: keyboard navigation must scroll the container so focused items are actually rendered, and Ctrl+F browser search will not find unrendered content — which is a genuine limitation worth flagging in product discussions ([[09.5 - Accessibility Fundamentals]]).

## When to virtualize

**Above roughly 100–200 complex rows**, or 1,000+ simple ones. Below that, the DOM handles it fine and virtualization adds complexity for nothing.

Measure first: the DevTools Performance panel shows commit time and node counts. If commit time is the cost, virtualization helps; if render time is the cost, memoization may be the better lever ([[19.8 - Profiling with React DevTools]]).

## Alternatives to consider first

**Pagination.** Often better UX for browsing, and trivially simpler. Users generally prefer pages over an infinite list for tabular data ([[24.4 - Pagination and Infinite Scroll]]).

**`content-visibility: auto`.** A one-line CSS alternative that skips layout and paint for offscreen content:

```css
.row {
  content-visibility: auto;
  contain-intrinsic-size: auto 40px;
}
```

The nodes remain in the DOM — so search, accessibility and anchors still work — but rendering work is skipped. It does not reduce memory or React render cost, so it is not a full substitute, but for a few thousand rows it is often enough and costs one CSS rule ([[13.2 - Reflow Repaint and Composite]]).

**Server-side filtering.** If the user cannot meaningfully use 10,000 rows, do not send them.

## Combining with other techniques

Virtualization pairs with memoized rows — a row that re-renders on every scroll tick defeats the purpose:

```jsx
const Row = React.memo(function Row({ item }) { ... });
```

And with infinite loading:

```jsx
const lastItem = virtualizer.getVirtualItems().at(-1);
useEffect(() => {
  if (lastItem?.index >= items.length - 1 && hasNextPage) fetchNextPage();
}, [lastItem?.index, hasNextPage]);
```

## How senior engineers actually use this

**They try pagination and `content-visibility` before virtualizing.** Both are far cheaper to implement and maintain.

**They use a library.** Hand-rolled virtualization is a maintenance liability the first time someone asks for variable heights.

**They memoize row components**, since rows re-render on every scroll otherwise.

**They handle the accessibility attributes**, because virtualized tables are otherwise unusable with a screen reader.

**They profile commit time** to confirm node count is actually the bottleneck.

## Common pitfalls

- Virtualizing a list of fifty items.
- No overscan, producing blank rows during fast scrolling.
- Unmemoized rows re-rendering on every scroll event.
- Missing `aria-rowcount`/`aria-rowindex`, breaking screen readers.
- Index-based keys causing state to attach to the wrong row as the window moves ([[16.6 - Lists and Keys]]).
- Nested scroll containers confusing scroll position tracking.
- Forgetting that Ctrl+F cannot find unrendered content.

## Interview angle

"How would you render 100,000 rows efficiently" is a standard question. Explain windowing — render only the visible slice plus overscan, with a spacer preserving scroll height — and note the variable-height problem and how estimate-and-measure handles it. The stronger answer also raises the alternatives: pagination is often better UX, and `content-visibility: auto` is a one-line CSS option, so virtualization is what you reach for when those do not fit. Mentioning the accessibility attributes signals production experience.
