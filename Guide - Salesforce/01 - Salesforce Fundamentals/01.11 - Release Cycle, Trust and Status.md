# Release Cycle, Trust and Status

## Three upgrades a year, whether you want them or not

Because every customer runs the same code on shared infrastructure ([[01.5 - Multi-Tenant Architecture]]), Salesforce upgrades everyone. You do not choose the version, you do not choose the date, and you cannot skip one.

The three releases are named after seasons, with the year of the *upcoming* season:

- **Spring** — around February
- **Summer** — around June
- **Winter** — around October

Winter '27 arrives in October 2026. The naming looks off by one until you get used to it.

Each release is a weekend maintenance window of a few minutes to a few hours per instance, and instances upgrade in waves rather than all at once. Your org's specific date is published in advance on the Trust site.

## The preview period

You cannot skip a release, but you can see it early. Roughly four to six weeks before general availability, some sandbox instances are upgraded to the new version while production stays behind. This is the **preview window**, and using it well is what separates teams that get surprised from teams that do not.

Which sandboxes preview depends on which instance they were created on, which you can check in Setup. Sandboxes on non-preview instances stay on the current release, which is what you want for hotfix testing against production.

The practical pattern most mature teams follow:

1. Read the release notes when the preview drops. They are long; skim the sections for the features and objects your org actually uses.
2. Have at least one preview sandbox available.
3. Run the full regression suite there — automated Apex tests plus manual testing of the critical business flows.
4. Review the **Release Updates** page in Setup, which lists behaviour changes that are being enforced on a schedule.
5. Log anything broken as a support case before the release reaches production, when it is still a preventable problem rather than an outage.

## Release Updates

This is the mechanism that deserves the most attention, because it is where breaking changes hide.

Salesforce rarely breaks behaviour instantly. Instead, a change is introduced as a **Release Update** with a published enforcement date, usually two or three releases in the future. During that window you can enable it early to test, and after the enforcement date it becomes mandatory.

Examples of the kind of thing that arrives this way: stricter enforcement of security in Apex, changes to how flows run in system context, removal of legacy API versions, changes to the way related lists resolve.

The Release Updates page in Setup is one of the highest-value pages in the whole product, and most teams ignore it until something breaks. Checking it once per release, and scheduling the work with real deadlines, is a small habit with a large payoff.

## API versions and why they insulate you

Every Apex class, trigger, and component is stamped with an API version in its metadata:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ApexClass xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>62.0</apiVersion>
    <status>Active</status>
</ApexClass>
```

That version pins the behaviour of the platform for that piece of code. When Salesforce changes semantics, the change usually applies only to code compiled at the new API version. Old code keeps its old behaviour until you deliberately raise the version.

Two consequences worth knowing:

**Upgrading API version is a real change, not housekeeping.** Bumping a class from version 45 to version 62 can alter its behaviour. Do it deliberately, with tests, not in a bulk find-and-replace across the repository.

**Very old API versions get retired.** Salesforce periodically deprecates and then removes support for old API versions, typically the ones from around a decade earlier. When that happens, integrations calling those endpoints stop working. Announcements come well in advance, but they are frequently missed because the integration was built by someone who left years ago. Auditing which API versions your inbound integrations actually use is a genuinely useful thing to do once a year:

```sql
SELECT Id, LoginTime, SourceIp, ApiType, ApiVersion, Application
FROM LoginHistory
WHERE ApiVersion != null
ORDER BY LoginTime DESC
```

## Trust and status

**Salesforce Trust** (status.salesforce.com) publishes live status, incident history, planned maintenance, and release dates per instance.

Two habits worth forming:

**Check Trust before debugging a sudden problem.** If queries got slow ten minutes ago and nothing was deployed, the cause may not be yours. This sounds obvious and is routinely skipped during incidents.

**Know your instance and its maintenance window.** Find it in Setup under Company Information. It determines when your org upgrades and when scheduled maintenance affects you, which matters if your business runs overnight batch jobs.

Trust also publishes historical availability and security advisories, which is often what a security or compliance team is actually asking for when they ask about uptime.

## What experienced teams do differently

**They treat release testing as scheduled work, not an interruption.** Three times a year, a known block of regression testing goes into the plan. Teams that do not schedule it end up doing it anyway, unplanned, in the form of an incident.

**They keep automated tests genuinely useful.** A test suite written only to reach the coverage threshold proves nothing about a release. A suite that asserts real business behaviour catches platform changes before customers do. This is the single strongest practical argument for section 19.

**They read release notes selectively but reliably.** Nobody reads all of them. The reliable pattern is to search the notes for the features the org depends on — the objects, the automation types, the APIs in use — and read those parts properly.

**They watch for retirements, not just new features.** The interesting content is usually in what is going away.

**They avoid depending on undocumented behaviour.** Anything that works but is not documented is not a contract, and a release can remove it without notice. This includes relying on the order of unordered query results, on internal field behaviour, or on the specific sequence in which two triggers on the same object happen to fire.

## A note on stability

Despite three forced upgrades a year, Salesforce releases break far less than people expect. The API versioning model is the reason: most changes are opt-in by version. The failures that do happen are usually caused by code depending on something undocumented, or by a Release Update whose enforcement date arrived while nobody was looking. Both are avoidable with the habits above.
