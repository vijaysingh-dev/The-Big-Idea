# Graceful Shutdown and Draining

#backend #reliability #operations

> **In one line:** A process receiving SIGTERM is still receiving traffic, so shutting down immediately drops requests — the fix is to fail readiness first, wait, then stop.

---

## The Idea

```
Kubernetes decides to terminate a pod:
  t=0     pod marked Terminating, endpoint removal STARTS
  t=0     SIGTERM sent to the container
  t=?     endpoint actually removed from every kube-proxy / load balancer
  t=grace SIGKILL
```

⚠️ **Endpoint removal and SIGTERM happen concurrently, and endpoint removal is eventually consistent.** For some seconds after SIGTERM, traffic is still arriving.

💡 **A process that exits on SIGTERM drops every request that arrives in that window.** On a busy service with frequent deploys, that is a continuous low-level error rate nobody attributes to deploys.

---

## The Correct Sequence

```python
shutting_down = asyncio.Event()

@app.get("/readyz")
async def readyz():
    if shutting_down.is_set():
        raise HTTPException(503)          # ← fail readiness immediately
    return {"ready": True}


async def shutdown():
    shutting_down.set()                    # 1. fail readiness
    await asyncio.sleep(DRAIN_SECONDS)     # 2. let endpoint removal propagate
    await server.shutdown()                # 3. finish in-flight requests
    await pool.close()                     # 4. release resources
```

```yaml
lifecycle:
  preStop:
    exec: {command: ["sleep", "10"]}
terminationGracePeriodSeconds: 60
```

| Step | Why |
|---|---|
| **Fail readiness first** | Tells the load balancer to stop sending, before you stop serving |
| **Sleep** | Endpoint removal is not instant. 5–15 seconds |
| **Finish in-flight** | Requests already accepted must complete |
| **Close resources** | Connections, pools, consumers |

💡 **The `preStop` sleep is not a hack, it is the fix for a genuine race.** Kubernetes explicitly documents that endpoint removal and SIGTERM are not ordered, and the sleep is the recommended workaround.

⚠️ **`preStop` runs *before* SIGTERM.** So `preStop: sleep 10` plus an in-process drain gives you both — the sleep covers endpoint propagation and the in-process handling covers in-flight requests.

**Either approach works; using both is belt and braces and costs ten seconds per pod.**

### The grace period arithmetic

```
terminationGracePeriodSeconds must exceed:
    preStop duration
  + drain sleep
  + longest in-flight request
  + resource cleanup
```

⚠️ **If the grace period expires, SIGKILL.** In-flight requests are dropped and cleanup does not run.

```
preStop sleep:        10s
longest request:      30s
cleanup:               5s
→ terminationGracePeriodSeconds: 60      (with headroom)
```

💡 **For workers with long tasks, this number gets large** ([[08.9 - Celery in Production]]). A worker with 60-second tasks needs a 90-second grace period, and every deploy takes that much longer per pod.

**The better answer is shorter tasks**, so the grace period can be short.

## Draining Different Things

### HTTP requests

```python
server = uvicorn.Server(config)

async def shutdown():
    shutting_down.set()
    await asyncio.sleep(10)
    server.should_exit = True              # stop accepting, finish in-flight
    await server.shutdown()
```

⚠️ **Keep-alive connections complicate this.** A client with an idle keep-alive connection may send a request just as you stop accepting.

```python
config = uvicorn.Config(app, timeout_keep_alive=5)
```

💡 **Send `Connection: close` on responses during shutdown**, so clients establish a new connection to a healthy pod rather than reusing one to a dying one.

### Long-lived connections

```python
async def shutdown_sse():
    for conn in active_sse_connections:
        await conn.send_event("reconnect", {"reason": "shutdown"})
        conn.close()
```

⚠️ **SSE and WebSocket connections do not drain — they must be told to reconnect** ([[04.3 - SSE in Production]]).

💡 **Stagger the disconnections.** Closing 5,000 connections simultaneously produces a reconnect storm against the remaining pods.

```python
for i, conn in enumerate(connections):
    await conn.close()
    if i % 50 == 0:
        await asyncio.sleep(0.5)
```

⚠️ **Clients must reconnect with jitter**, or they all return at the same moment ([[11.2 - Timeouts Retries and Jitter]]).

### Background workers

```python
async def shutdown_worker():
    await consumer.stop_consuming()        # 1. take no new work
    await asyncio.gather(*in_flight)       # 2. finish what you have
    await consumer.close()
```

💡 **Stop consuming before finishing in-flight work**, or the worker keeps pulling new tasks right up until the grace period expires and then abandons them.

```yaml
# Celery
lifecycle:
  preStop:
    exec:
      command: ["celery", "-A", "app", "control", "cancel_consumer",
                "--destination", "celery@$(HOSTNAME)", "default"]
```

⚠️ **With `acks_late`, abandoned tasks are requeued and redone** — nothing is lost, and you waste the work already done ([[08.2 - Queue Semantics]]).

**Measure work redone per deploy.** It is often surprisingly large.

### Kafka consumers

```python
async def shutdown_consumer():
    await consumer.stop()                  # triggers a rebalance
    await commit_offsets()                 # ⚠️ commit what you have processed
```

⚠️ **Leaving without committing means the next consumer reprocesses**, which is safe only if the consumer is idempotent ([[09.1 - Queue vs Log]]).

💡 **A clean shutdown that leaves the group explicitly triggers a fast rebalance**; being killed means the group waits for `session.timeout.ms` before noticing — seconds of stalled consumption per pod.

### Database connections

```python
await pool.close()                          # wait for in-use connections to return
```

⚠️ **Closing the pool while connections are in use can abort transactions mid-flight.** Close after in-flight requests finish, not before.

💡 **An abandoned transaction leaves locks held until the server notices the connection is gone**, which can be `tcp_keepalive` seconds — blocking other queries meanwhile ([[06.8 - Locking and Deadlocks]]).

**Set `idle_in_transaction_session_timeout`** as a backstop ([[06.7 - MVCC Vacuum and Bloat]]).

## Signals

```python
import signal

def install_handlers(loop):
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, lambda: asyncio.create_task(shutdown()))
```

| Signal | Meaning |
|---|---|
| **SIGTERM** | Please stop. **The one Kubernetes sends** |
| SIGINT | Ctrl-C. Treat as SIGTERM |
| **SIGKILL** | Cannot be caught. The grace period expired |
| SIGQUIT | Celery's cold shutdown |

⚠️ **PID 1 in a container does not get default signal handling.** If your process is PID 1 and does not install a SIGTERM handler, the signal is ignored entirely and you always get SIGKILL.

```dockerfile
ENTRYPOINT ["tini", "--"]         # or use exec form so your process IS PID 1 correctly
CMD ["python", "-m", "app"]
```

💡 **`docker run python app.py` with a shell-form CMD makes the shell PID 1**, which does not forward signals. **Always use exec form**, or an init like tini.

**Test it:** `docker stop` a container and see whether it exits in under a second or waits ten seconds for SIGKILL.

## In Production

### The shutdown checklist

```
□  SIGTERM handler installed
□  The process is PID 1, or an init forwards signals
□  Readiness fails immediately on SIGTERM
□  A drain delay covers endpoint propagation
□  In-flight requests complete
□  Long-lived connections told to reconnect, staggered
□  Workers stop consuming before finishing
□  Consumer offsets committed
□  Database pool closed after requests finish
□  terminationGracePeriodSeconds > preStop + drain + longest operation
□  Metrics flushed before exit
```

⚠️ **The last one is quietly important.** A process that exits before its metrics are scraped loses the final interval — including the metrics that would tell you the shutdown went badly.

```python
await metrics_pusher.push_final()
```

### Measuring it

```python
shutdown_duration_seconds.observe(elapsed)
shutdown_inflight_at_start.set(n)
requests_dropped_during_shutdown_total.inc()
tasks_abandoned_total.inc()
connections_closed_at_shutdown.set(n)
```

💡 **`requests_dropped_during_shutdown_total` should be zero.** If it is not, your drain is too short or readiness is not failing fast enough.

**Measure it across a deploy**, not in a test — the endpoint propagation delay is a property of your cluster.

### Finding the right drain delay

```python
# Measure how long endpoint removal actually takes
await mark_not_ready()
start = time.monotonic()
while await still_receiving_traffic():
    await asyncio.sleep(0.1)
print(f"endpoint propagation: {time.monotonic() - start:.1f}s")
```

⚠️ **It varies by cluster size and load balancer.** A small cluster might propagate in 2 seconds; a large one with an external load balancer might take 30.

💡 **Measure yours, then set the drain to twice it.** A guessed value is either dropping requests or slowing every deploy unnecessarily.

### Rolling deploys and the multiplier

```
20 pods × (10s preStop + 5s drain + 30s longest request) = 15 minutes
```

⚠️ **A long grace period makes every deploy slow**, and slow deploys make teams deploy less often, which makes each deploy riskier ([[10.10 - Deployment Strategies]]).

```yaml
strategy:
  rollingUpdate:
    maxSurge: 25%           # replace several at once
    maxUnavailable: 0
```

💡 **Surge more pods rather than accepting a slow serial rollout**, or reduce the longest operation so the grace period can shrink.

### Node drains and disruptions

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
```

⚠️ **Shutdown handling is not only about your deploys.** Node drains, cluster upgrades, spot instance reclamation and autoscaler scale-down all terminate pods, and they use the same path.

💡 **Spot instances give a 2-minute warning**, which is shorter than some grace periods. **If you run on spot, your grace period must fit inside it** or you get SIGKILLed.

### Testing shutdown

```python
async def test_no_requests_dropped_during_shutdown(load_generator):
    async with load_generator(rps=200):
        await asyncio.sleep(5)
        await trigger_shutdown()
        await asyncio.sleep(30)
    assert load_generator.errors == 0
```

💡 **A test that generates load, triggers shutdown, and asserts zero errors is the only way to know this works** ([[10.9 - Testing Microservices]]).

**Run it in CI against a real container**, so a change to the signal handling is caught.

### Conduit's configuration

| Component | preStop | Drain | Longest op | Grace |
|---|---|---|---|---|
| Gateway | 10s | 5s | 8s | **45s** |
| Document service | 10s | 5s | 5s | 40s |
| SSE service | 5s | staggered close | — | 60s |
| **Ingestion worker** | `cancel_consumer` | — | **60s task** | **120s** |
| Kafka consumer | — | commit offsets | 5s batch | 30s |

⚠️ **The worker's 120-second grace period is the outlier**, and it means a 10-pod worker rollout takes 20 minutes serially.

💡 **The fix is task granularity, not a longer grace period** ([[08.5 - Task Design Rules]]). Splitting the 60-second task into six 10-second stages would bring the grace period to 30 seconds and the rollout to 5 minutes.

**Write that down as a known trade** rather than accepting it silently.

## Codebase

**Repo:** `kubernetes/kubernetes`, `encode/uvicorn`, `celery/celery`

**Question to answer:** In Kubernetes, what is the exact ordering between endpoint removal and SIGTERM, and why can a pod still receive traffic after SIGTERM? Then: how does uvicorn handle in-flight requests during shutdown?

**Read, in order:**

1. `kubernetes/pkg/kubelet/kubelet_pods.go` — `killPod` and the termination sequence. **Note that `preStop` runs before SIGTERM**
2. `kubernetes/pkg/controller/endpointslice/` — **endpoint removal is a separate controller reacting to the pod's state.** **This is the answer to the first question**: two independent processes, not a sequence
3. **Kubernetes docs — "Pod termination"** — the official statement that these are concurrent, and the recommendation to use `preStop`
4. `uvicorn/uvicorn/server.py` — `shutdown`. **How it stops accepting, waits for in-flight tasks, and handles keep-alive connections.** The answer to the second question
5. `celery/celery/worker/consumer/consumer.py` — warm shutdown: stop consuming, wait for in-flight, and what happens to reserved-but-unstarted messages

💡 The endpoint removal reading is the one that makes this note make sense. **The kubelet kills your pod and a completely separate controller removes it from the endpoints, and nothing orders them.** Once you have seen that, the `preStop` sleep stops looking like superstition.

**Size:** 1 session.

**Part 1 — The naive version.** A service exiting immediately on SIGTERM, under 200 rps, with a rolling deploy.

**Count requests dropped per rollout.** Run ten rollouts and report the mean.

**Part 2 — Measure endpoint propagation.** Instrument a pod to log every request received, then mark it not-ready and record how long traffic continues.

**Report the number for your cluster.** This determines your drain delay, and guessing it is how you either drop requests or slow deploys.

**Part 3 — The correct sequence.** Implement readiness-fail, drain, in-flight completion, and cleanup.

**Re-run ten rollouts. Requests dropped must be zero.**

Then remove each step in turn and confirm which failure it prevents:

| Removed | Expected failure |
|---|---|
| Readiness fail | Traffic continues to a dying pod |
| Drain sleep | Requests dropped during propagation |
| In-flight wait | Requests aborted mid-processing |
| Pool close | Transactions left open, locks held |

**Part 4 — Signals and PID 1.** Three Dockerfiles: shell-form CMD, exec-form CMD, and tini.

**`docker stop` each and time the exit.** The shell-form one should take the full 10-second SIGKILL timeout.

Then confirm your signal handler runs in each case.

**Part 5 — Long-lived connections.** 2,000 SSE connections across three pods.

**Naive:** kill a pod. Measure the reconnect burst on the remaining pods and the time to reconnect all clients.

**Staggered close with client-side jitter:** measure again.

**Chart connections-per-second on the surviving pods for both.**

**Part 6 — Worker shutdown.** A Celery worker with 60-second tasks and a 30-second grace period.

**Measure tasks abandoned and redone per rollout.**

Then correct the grace period. Then add `cancel_consumer` in `preStop` and measure again — the worker should have less in flight when the grace period starts.

Then split the task into 10-second stages and measure the rollout time with a 30-second grace period.

**Report all four configurations.**

**Part 7 — Kafka consumer shutdown.** A consumer processing a batch.

**Kill it without committing.** Measure reprocessed messages and the rebalance delay.

Then clean shutdown with an explicit commit and group leave. **Measure the rebalance delay again** — it should be dramatically shorter.

**Part 8 — The grace period trade.** Sweep `terminationGracePeriodSeconds`: 10, 30, 60, 120.

For each measure: requests dropped, tasks abandoned, and **total rollout duration for 20 pods.**

**Chart the trade**, then pick the value and justify it.

**Done when:**
- Your naive version drops a measured number of requests per rollout, and the correct one drops zero
- You know your cluster's actual endpoint propagation delay
- Removing each shutdown step causes its predicted failure
- Shell-form CMD demonstrably ignores SIGTERM
- Staggered SSE close eliminates the reconnect burst
- Your four worker configurations are measured, including the task-splitting option
- A clean Kafka shutdown measurably shortens the rebalance
- Your grace period is chosen from the measured trade, not guessed
