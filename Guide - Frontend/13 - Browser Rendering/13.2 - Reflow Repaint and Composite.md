# Reflow, Repaint and Composite

Once the page is rendered, every change re-runs some portion of the pixel pipeline. Which portion depends entirely on what you changed — and the cost difference between the three outcomes is roughly an order of magnitude at each step.

## The pipeline, per change

```
Recalculate Style -> Layout -> Paint -> Composite
```

Three possible paths:

**Layout (reflow)** — geometry changed. Runs style, layout, paint and composite. Most expensive, because changing one element's size can affect its siblings, children and ancestors.

**Paint** — appearance changed but geometry did not. Skips layout. Runs style, paint, composite.

**Composite only** — the element just moves or fades. Skips layout *and* paint. Runs on the compositor thread, often on the GPU, and continues smoothly even when the main thread is busy.

## Which properties trigger what

**Layout:** `width`, `height`, `padding`, `margin`, `border`, `top`, `left`, `right`, `bottom`, `display`, `position`, `float`, `font-size`, `line-height`, `overflow`, `flex`, `grid-template-*`.

**Paint (no layout):** `background`, `color`, `border-radius`, `box-shadow`, `visibility`, `outline`, `background-image`.

**Composite only:** `transform`, `opacity`, and `filter` in most cases.

That last line is the entire practical takeaway. Animating `left` costs layout on every frame; animating `transform: translateX()` costs nothing but a compositor matrix update ([[11.4 - Transitions and Animations]]).

CSS Triggers-style tables exist for the full property list, but the three-bucket model above covers virtually every decision you will make.

## Forced synchronous layout

The browser batches style and layout work and flushes it once per frame ([[01.7 - The Rendering Cycle]]). Reading a layout-dependent property forces it to flush immediately, because it must give you a correct answer:

```js
el.style.width = "100px";        // queued
const h = el.offsetHeight;       // forces layout NOW — flush the queue
```

Properties that force layout: `offsetTop/Left/Width/Height`, `clientTop/Left/Width/Height`, `scrollTop/Left/Width/Height`, `getBoundingClientRect()`, `getComputedStyle()` (for layout-dependent values), `innerText`, `focus()`, `scrollIntoView()`, and several others.

One forced layout is fine. In a loop it is layout thrashing, covered in [[13.3 - Layout Thrashing]].

## Compositor layers

The browser promotes certain elements onto their own layers, which can then be transformed and composited independently without repainting.

Promotion triggers:

- `will-change: transform` or `will-change: opacity`
- 3D transforms (`translate3d`, `translateZ`)
- `position: fixed` (in most browsers)
- `<video>`, `<canvas>`, WebGL contexts
- CSS animations of `transform` or `opacity`
- an element overlapping an already-composited layer

Each layer costs GPU memory, roughly `width × height × 4 bytes`. A full-screen layer at 1920×1080 is about 8 MB. Promoting dozens of elements causes **layer explosion**, where the memory and layer-management cost exceeds the savings — a common outcome of applying `will-change` liberally.

```css
/* Reasonable — hint just before the animation */
.card:hover { will-change: transform; }

/* Bad — permanent promotion of every card */
.card { will-change: transform; }
```

`will-change` should be added shortly before an animation and removed after. It also creates a stacking context and a containing block for fixed descendants, which causes the positioning bugs described in [[10.5 - Positioning and Stacking Contexts]].

DevTools' Layers panel shows every layer, its memory cost, and the reason it was promoted. The Rendering tab's "Layer borders" overlay gives a quick visual.

## Reducing the scope of work

**`contain`** tells the browser that an element's internals cannot affect anything outside it, so layout and paint can be scoped to that subtree:

```css
.widget { contain: layout paint; }
.widget { contain: content; }    /* shorthand for layout paint style */
.widget { contain: strict; }     /* also size — requires explicit dimensions */
```

For a page with many independent components, `contain: content` measurably reduces recalculation cost when one of them changes.

**`content-visibility: auto`** goes further — the browser skips layout and paint for offscreen elements entirely:

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}
```

`contain-intrinsic-size` provides a placeholder size so the scroll height is stable and the scrollbar does not jump as content renders. On long documents this is one of the largest single-property wins available.

Caveat: content skipped this way is not searchable with Ctrl+F in some browsers until it renders, and it can affect anchor navigation.

## Style recalculation cost

Before layout comes style recalculation, and its cost is proportional to `number of elements affected × number of rules to check`.

The usual cause of expensive recalculation is a class toggled on a high ancestor:

```js
document.body.classList.toggle("dark");   // invalidates every element's style
```

That is unavoidable for a theme switch and fine as a one-off. It becomes a problem when done repeatedly — a scroll handler toggling a class on `<body>` forces a full-document style recalculation on every frame.

Scoping the change as low in the tree as possible is the fix. Custom properties help here too: changing a custom property on `:root` invalidates everything that uses it, so setting it on a subtree root instead limits the blast radius ([[10.4 - Units Custom Properties and Theming]]).

## Measuring

In the Performance panel, the coloured blocks are the pipeline stages:

- **Purple** — Recalculate Style, Layout
- **Green** — Paint, Composite Layers
- **Yellow** — Scripting

A red triangle on a Recalculate Style or Layout entry marks a forced synchronous layout, and clicking it shows the exact line of JavaScript that triggered it. This is the fastest path from "the page feels janky" to the responsible code.

The Rendering tab overlays are worth knowing: **Paint flashing** highlights repainted regions in green (if large areas flash during a small animation, something is repainting unnecessarily), and **Frame rendering stats** gives a live FPS meter.

## How senior engineers actually use this

**They animate only `transform` and `opacity`**, and treat anything else as requiring justification and measurement.

**They use `contain` and `content-visibility` on long pages** with many independent sections — often a larger win than any JavaScript optimization.

**They check paint flashing** when an animation feels heavy. Large green flashes during a small transition mean a layer is not doing what they assumed.

**They add `will-change` narrowly and temporarily.** Permanent promotion of many elements is slower than none.

**They scope class toggles low in the tree** rather than on `<body>`, except for genuine one-off theme changes.

## Common pitfalls

- Animating `width`, `height`, `top` or `left`.
- `will-change` applied permanently to many elements.
- Forced synchronous layout inside a loop.
- Toggling classes on `<body>` on every scroll frame.
- `content-visibility: auto` without `contain-intrinsic-size`, causing scrollbar jumps.
- Assuming a GPU layer is always faster — layer memory and management have real costs.
- Using `translate3d(0,0,0)` as a blanket promotion hack.

## Interview angle

"What is the difference between reflow and repaint" is the standard framing. Give the three-tier model — layout, paint, composite — with which property categories trigger each, and explain that `transform` and `opacity` skip to compositing which is why they are the animation properties. Following with forced synchronous layout, and `contain`/`content-visibility` as ways to reduce scope, takes the answer well past the memorized version.
