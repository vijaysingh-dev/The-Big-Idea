# Building an API Layer

Scattering `fetch` calls through components means every call site independently handles base URLs, auth headers, error checking, JSON parsing, retries and cancellation. An API layer does each of those once.

## fetch versus axios

```js
// fetch — built in, zero bytes
const res = await fetch("/api/users");
if (!res.ok) throw new HttpError(res.status);
const data = await res.json();

// axios — ~15KB, more conveniences
const { data } = await axios.get("/api/users");
```

`fetch` wins on bundle size and is now capable enough for most applications. Its two real gaps:

**It does not reject on HTTP errors.** A 404 or 500 is a successful exchange as far as `fetch` is concerned — you must check `res.ok` yourself ([[04.3 - Promise Chaining and Error Handling]]).

**No upload progress.** Only `XMLHttpRequest` reports it, which is why upload libraries persist.

Axios adds interceptors, automatic JSON, timeouts and error rejection. Once you have written a thin wrapper around `fetch`, most of that is covered — so the choice is usually "wrapper" versus "dependency", and the wrapper is about forty lines.

## A minimal client

```js
class HttpError extends Error {
  constructor(status, body, url) {
    super(`HTTP ${status} on ${url}`);
    this.name = "HttpError";
    this.status = status;
    this.body = body;
  }

  get isRetryable() {
    return this.status >= 500 || this.status === 429;
  }
}

export function createClient({ baseUrl, getToken, onUnauthorized }) {
  async function request(path, { body, headers, ...options } = {}) {
    const res = await fetch(`${baseUrl}${path}`, {
      ...options,
      headers: {
        "Content-Type": "application/json",
        ...(getToken() && { Authorization: `Bearer ${getToken()}` }),
        ...headers,
      },
      body: body ? JSON.stringify(body) : undefined,
    });

    if (res.status === 401) onUnauthorized();

    if (!res.ok) {
      const errorBody = await res.json().catch(() => null);
      throw new HttpError(res.status, errorBody, path);
    }

    if (res.status === 204) return null;
    return res.json();
  }

  return {
    get: (path, opts) => request(path, opts),
    post: (path, body, opts) => request(path, { method: "POST", body, ...opts }),
    put: (path, body, opts) => request(path, { method: "PUT", body, ...opts }),
    patch: (path, body, opts) => request(path, { method: "PATCH", body, ...opts }),
    delete: (path, opts) => request(path, { method: "DELETE", ...opts }),
  };
}
```

Details worth noting:

**`getToken` is a function, not a value.** Closing over a token string captures a stale token after refresh; closing over a getter always reads the current one ([[02.4 - Closure Patterns in Production]]).

**204 returns null.** Calling `.json()` on an empty body throws — a common bug on DELETE endpoints.

**Error body parsing is guarded.** A 500 returning an HTML error page would otherwise throw a `SyntaxError` that masks the real status.

**`isRetryable` lives on the error**, so retry logic does not need to know status codes ([[04.7 - Async Concurrency Patterns]]).

## Cancellation

```js
async function request(path, { signal, ...options } = {}) {
  const res = await fetch(url, { ...options, signal });
}

// Callers thread the signal through
const products = await api.get("/products", { signal: controller.signal });
```

Every function in the data layer should accept and forward a `signal`. Query libraries and router loaders both supply one automatically, and without forwarding it, cancellation silently does nothing ([[04.6 - AbortController and Cancellation]]).

Add a default timeout:

```js
signal: signal ?? AbortSignal.timeout(30_000)
```

Or combine both:

```js
signal: AbortSignal.any([signal, AbortSignal.timeout(30_000)].filter(Boolean))
```

## Resource modules

Wrap endpoints in typed functions grouped by resource, rather than calling the client directly from components:

```ts
export const productsApi = {
  list: (params: ListParams, opts?: RequestOptions) =>
    api.get(`/products?${new URLSearchParams(params)}`, opts) as Promise<Product[]>,

  byId: (id: string, opts?: RequestOptions) =>
    api.get(`/products/${id}`, opts) as Promise<Product>,

  create: (input: CreateProduct) =>
    api.post("/products", input) as Promise<Product>,
};
```

This gives one place where the URL shape lives, so an endpoint rename is a one-line change rather than a search across the codebase.

## Runtime validation

TypeScript types are erased at build time — they assert nothing about what the server actually sent ([[25.7 - Typing API Responses and Zod]]).

```ts
import { z } from "zod";

const productSchema = z.object({
  id: z.string(),
  name: z.string(),
  price: z.number(),
  createdAt: z.coerce.date(),        // ISO string → Date
});

export const productsApi = {
  byId: async (id: string, opts?: RequestOptions) => {
    const raw = await api.get(`/products/${id}`, opts);
    return productSchema.parse(raw);
  },
};
```

Two benefits beyond safety: **the type is derived from the schema** (`z.infer`), so they cannot drift; and **`z.coerce.date()` normalizes at the boundary**, so no component ever receives a date-shaped string ([[08.5 - Serialization and Structured Clone]]).

Validating everything has a cost on large payloads. A reasonable compromise is validating in development and on critical paths only.

## Normalizing the response shape

```js
// Defaults applied once, not at fifty call sites
const normalized = {
  ...product,
  tags: product.tags ?? [],
  metadata: product.metadata ?? {},
};
```

Returning `[]` instead of `null` for collections removes a null check from every consumer. Doing this in the API layer is much cheaper than optional chaining scattered through components ([[05.7 - Optional Chaining and Nullish Coalescing]]).

## Error normalization

```js
function toAppError(err) {
  if (err.name === "AbortError") return { kind: "cancelled" };
  if (err.name === "TimeoutError") return { kind: "timeout" };
  if (err instanceof TypeError) return { kind: "network" };   // fetch network failure
  if (err instanceof HttpError) {
    if (err.status === 422) return { kind: "validation", fields: err.body.fieldErrors };
    if (err.status === 403) return { kind: "forbidden" };
    if (err.status === 404) return { kind: "notFound" };
    return { kind: "server", status: err.status };
  }
  return { kind: "unknown", error: err };
}
```

Downstream code branches on one shape instead of inspecting raw responses. The `kind: "cancelled"` case matters — aborts must never reach error reporting or a toast ([[05.9 - Error Handling and Custom Errors]]).

## Auth refresh

```js
let refreshPromise = null;

async function withAuth(request) {
  try {
    return await request();
  } catch (err) {
    if (err.status !== 401) throw err;

    refreshPromise ??= refreshToken().finally(() => { refreshPromise = null; });
    await refreshPromise;

    return request();          // retry ONCE
  }
}
```

Two requirements: **deduplicate concurrent refreshes**, or five parallel 401s trigger five refresh calls and four fail; and **retry only once**, or a persistently failing refresh loops forever ([[23.4 - Protected Routes and Auth Flows]]).

## Where it sits

```
Components
   ↓ (hooks)
Query layer     — caching, deduplication, background refetch
   ↓
API layer       — URLs, auth, errors, validation, cancellation
   ↓
fetch
```

The API layer knows nothing about React. That makes it testable without a renderer, reusable in loaders and server code, and callable from event handlers ([[24.6 - TanStack Query Fundamentals]]).

Components should never call `fetch` directly, and rarely call the API layer directly — they go through query hooks.

## Testing

```js
// MSW intercepts at the network level
http.get("/api/products/:id", ({ params }) =>
  HttpResponse.json({ id: params.id, name: "Test", price: 100 })
);
```

Mocking at the network boundary rather than mocking the API module means the tests exercise the real client, including error handling and validation ([[26.4 - Mocking the Network with MSW]]).

## How senior engineers actually use this

**They build one client and never call `fetch` in a component.**

**They inject dependencies as functions** — `getToken`, `onUnauthorized` — so the client is testable and never holds stale values.

**They thread `signal` through every function**, since cancellation is otherwise silently absent.

**They normalize errors into a small union** so downstream branching is uniform.

**They validate and normalize at the boundary**, converting dates and defaulting collections once.

## Common pitfalls

- Assuming `fetch` rejects on 4xx/5xx.
- Calling `.json()` on a 204 response.
- Capturing a token value instead of a getter.
- Not forwarding `signal`, so cancellation does nothing.
- Concurrent 401s triggering parallel refreshes.
- Trusting TypeScript types as runtime guarantees.
- Aborts surfacing as user-visible errors.
- Endpoint URLs duplicated across components.

## Interview angle

"How would you structure API calls in a React app" is a design question. Describe the layering — components → query hooks → API layer → fetch — and what each layer owns. The specifics that stand out: `fetch` not rejecting on HTTP errors, injecting a token *getter* rather than a value, threading `AbortSignal` through everything, normalizing errors into a discriminated union, and validating responses at runtime because TypeScript types are erased.
