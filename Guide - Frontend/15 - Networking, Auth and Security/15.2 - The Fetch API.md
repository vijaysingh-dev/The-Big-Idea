# The Fetch API

The modern network primitive. Promise-based, stream-capable, and built on `Request`/`Response` objects that are also used by service workers and the Cache API.

## Basics

```js
const res = await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Vijay" }),
  credentials: "same-origin",
  signal: controller.signal,
  cache: "no-store",
  mode: "cors",
  redirect: "follow",
  keepalive: false,
});

const data = await res.json();
```

## The rejection rule

**`fetch` rejects only on network-level failure** — DNS failure, connection refused, CORS block, abort, or a malformed URL. A 404 or 500 is a successfully completed HTTP exchange, so the promise fulfills.

```js
const res = await fetch("/api/missing");
res.ok;      // false
res.status;  // 404
```

This is the single most common `fetch` mistake. Every wrapper must check `res.ok`:

```js
async function request(url, options = {}) {
  const res = await fetch(url, options);

  if (!res.ok) {
    const body = await res.json().catch(() => null);
    throw new HttpError(res.status, body);
  }

  return res.status === 204 ? null : res.json();
}
```

The `204` check matters — calling `.json()` on an empty body throws a `SyntaxError` that looks like a parsing bug rather than an empty response ([[05.9 - Error Handling and Custom Errors]]).

Note that a rejected `fetch` gives a bare `TypeError` with a message like "Failed to fetch", deliberately vague to avoid leaking cross-origin information. You cannot distinguish a CORS failure from an offline device from the error object — checking `navigator.onLine` is the usual heuristic.

## Reading the body

```js
await res.json();
await res.text();
await res.blob();
await res.arrayBuffer();
await res.formData();
await res.bytes();
```

**The body can be read only once.** `res.bodyUsed` tells you whether it has been consumed. To read it twice — logging and parsing, or caching and returning — clone first:

```js
const copy = res.clone();
```

Cloning buffers the body in memory, so avoid it for large responses.

## Request bodies

```js
body: JSON.stringify(obj);                       // set Content-Type manually

body: new FormData(formElement);                 // multipart, Content-Type set automatically
body: new URLSearchParams({ a: 1, b: 2 });       // form-urlencoded, set automatically
body: fileInput.files[0];                        // raw file
body: blob;
body: readableStream;                            // requires duplex: "half"
```

**Do not set `Content-Type` manually for `FormData`** — the browser must add the multipart boundary parameter, and setting the header yourself omits it, causing a server-side parse failure. This trips people up regularly.

## Credentials

```js
credentials: "same-origin"   // default — cookies on same-origin only
credentials: "include"       // cookies on cross-origin too
credentials: "omit"          // never
```

`include` requires the server to send `Access-Control-Allow-Credentials: true` and a specific origin — a wildcard `*` is rejected when credentials are involved ([[15.3 - Same Origin Policy and CORS]]).

## Streaming

```js
const res = await fetch("/large.json");
const reader = res.body.getReader();

let received = 0;
const total = +res.headers.get("Content-Length");

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  received += value.length;
  onProgress(received / total);
}
```

`res.body` is a `ReadableStream`, which is how you implement download progress — `fetch` has no progress event, unlike `XMLHttpRequest`.

Processing a streamed response line by line:

```js
for await (const chunk of res.body.pipeThrough(new TextDecoderStream())) {
  process(chunk);
}
```

This is how streaming LLM responses and NDJSON APIs are consumed.

**Upload progress is not available with `fetch`** in most browsers — request streams with `duplex: "half"` are supported only in Chromium and only over HTTP/2. For upload progress, `XMLHttpRequest` remains the correct tool, which is one of the few remaining reasons to use it.

## keepalive and sendBeacon

A `fetch` in progress is cancelled when the page unloads, which loses analytics events fired on exit.

```js
fetch("/analytics", { method: "POST", body, keepalive: true });
navigator.sendBeacon("/analytics", body);
```

`keepalive` allows the request to outlive the page, capped at 64 KB across all in-flight keepalive requests. `sendBeacon` is the purpose-built alternative — fire-and-forget, queued by the browser, no response available.

Use `visibilitychange` rather than `unload` to trigger these; `unload` is unreliable on mobile.

## Building a client

```js
function createClient({ baseUrl, getToken }) {
  async function request(path, { timeout = 10_000, signal, ...options } = {}) {
    const combined = signal
      ? AbortSignal.any([signal, AbortSignal.timeout(timeout)])
      : AbortSignal.timeout(timeout);

    const res = await fetch(`${baseUrl}${path}`, {
      ...options,
      signal: combined,
      headers: {
        "Content-Type": "application/json",
        Authorization: `Bearer ${getToken()}`,
        ...options.headers,
      },
    });

    if (!res.ok) throw new HttpError(res.status, await res.json().catch(() => null));
    return res.status === 204 ? null : res.json();
  }

  return {
    get: (path, opts) => request(path, opts),
    post: (path, body, opts) => request(path, { ...opts, method: "POST", body: JSON.stringify(body) }),
  };
}
```

Points worth noting: `getToken` is a function so it always reads the current token rather than closing over a stale one ([[02.4 - Closure Patterns in Production]]); `AbortSignal.any` combines caller cancellation with a timeout; and spreading `options.headers` last lets callers override defaults.

## fetch vs axios

Axios still offers: automatic JSON parsing and stringifying, throwing on non-2xx by default, interceptors, upload and download progress, request cancellation (now via `AbortSignal`), and identical behavior in Node.

`fetch` offers: no dependency, streaming, service worker integration, and a standard API. Modern Node has it built in.

For most projects a thin `fetch` wrapper of forty lines covers what axios provides, minus progress. The decision is usually about whether you want a dependency, not about capability ([[24.1 - Building an API Layer]]).

## How senior engineers actually use this

**They never call raw `fetch` from components.** One client module handles base URL, auth, timeouts, error normalization and retries; components call typed functions.

**They always check `res.ok`.** It is the most-repeated `fetch` bug and it fails silently — `res.json()` on a 500 HTML error page throws a confusing `SyntaxError`.

**They set a timeout on every request** via `AbortSignal.timeout`.

**They use `sendBeacon` or `keepalive` for exit-time telemetry**, triggered on `visibilitychange`.

**They stream large responses** rather than buffering, both for progress reporting and for memory.

## Common pitfalls

- Assuming `fetch` rejects on 4xx/5xx.
- Reading the body twice without cloning.
- Setting `Content-Type` manually with `FormData`.
- `credentials: "include"` against a server sending `Access-Control-Allow-Origin: *`.
- `.json()` on a 204 response.
- Expecting upload progress from `fetch`.
- Losing analytics on unload because the request was cancelled.
- Not distinguishing `AbortError` from real failures in catch blocks.

## Interview angle

"What is the difference between `fetch` and `XMLHttpRequest`" and "does `fetch` throw on a 404" are both common — the second is a filter question, and the correct answer is no, only on network failure. Follow with what a production wrapper must add: `res.ok` checks, timeouts, error normalization, auth headers and cancellation. Mentioning streaming and `sendBeacon` shows breadth beyond the basic call.
