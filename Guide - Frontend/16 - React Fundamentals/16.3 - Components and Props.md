# Components and Props

A component is a function that takes props and returns a description of UI. That is the entire contract.

```jsx
function Greeting({ name, tone = "friendly" }) {
  return <p className={tone}>Hello, {name}</p>;
}
```

## Props are read-only

```jsx
function Bad({ user }) {
  user.name = "changed";     // mutating the parent's object
  return <span>{user.name}</span>;
}
```

A component must never mutate its props. React assumes rendering is pure — same props, same output, no side effects ([[16.5 - Rendering and Purity]]). Mutating props breaks that assumption, and because the object reference is unchanged, the parent will not re-render to reflect it.

To change something a parent owns, call a callback the parent supplied:

```jsx
function Child({ user, onRename }) {
  return <button onClick={() => onRename(user.id, "new")}>Rename</button>;
}
```

This is unidirectional data flow: data down, events up.

## Designing the prop API

A component's props are its public API. The same considerations apply as to any function signature.

**Prefer specific props over configuration objects:**

```jsx
<Button variant="primary" size="lg" />          // discoverable, typeable
<Button config={{ variant: "primary" }} />      // opaque
```

**Prefer enums over booleans** once there are more than two states:

```jsx
<Alert isError isWarning isSuccess />    // invalid combinations possible
<Alert severity="error" />               // one valid value at a time
```

Boolean props also compound badly: three booleans mean eight states, most of which are meaningless. A `variant` prop makes invalid states unrepresentable.

**Accept `children` rather than a content prop** when the content is arbitrary:

```jsx
<Card title="Sales">{anything}</Card>
<Card title="Sales" content="only strings" />
```

**Forward the rest.** A component that swallows unknown props forces consumers to wrap it whenever they need `aria-label` or `data-testid`:

```jsx
function Input({ label, id, ...rest }) {
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} {...rest} />
    </>
  );
}
```

## Composition over configuration

The recurring design pressure is a component accumulating props to cover every variation. Composition is the escape:

```jsx
// Configuration — grows without bound
<Modal
  title="Confirm"
  showCloseButton
  footerButtons={[{ label: "OK", primary: true }]}
  headerIcon="warning"
/>

// Composition — arbitrary content, no new props
<Modal>
  <Modal.Header icon={<WarningIcon />}>Confirm</Modal.Header>
  <Modal.Body>Are you sure?</Modal.Body>
  <Modal.Footer>
    <Button variant="primary">OK</Button>
  </Modal.Footer>
</Modal>
```

The second form has a smaller API and covers more cases. Shared state between the parts flows through context ([[22.6 - Compound Components]]).

## Elements as props

Passing an element rather than data is a distinct and useful technique:

```jsx
function Page({ sidebar, children }) {
  return (
    <div className="layout">
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}

<Page sidebar={<Filters onChange={setFilters} />}>
  <Results filters={filters} />
</Page>
```

Two benefits. It avoids drilling props through `Page`, which knows nothing about filters. And because the element is created in the *parent's* render, `Page` re-rendering does not re-render `Filters` — the element object is the same reference ([[19.1 - What Causes Re-renders]]).

This is also the mechanism behind Server Components passing client components as children ([[22.8 - Server Components]]).

## Typing props

```tsx
type ButtonProps = {
  variant?: "primary" | "secondary";
  children: React.ReactNode;
} & React.ComponentPropsWithoutRef<"button">;

function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}
```

`ComponentPropsWithoutRef<"button">` inherits every native button prop, so consumers get `onClick`, `disabled`, `type` and all ARIA attributes typed correctly without enumeration.

`React.FC` is no longer recommended — it historically added an implicit `children` prop and complicates generic components ([[25.4 - Typing Props and Children]]).

## Default values

```jsx
function Card({ padding = "md", items = [] }) {}
```

Destructuring defaults replaced `defaultProps`, which is deprecated for function components.

One trap: a default object or array literal creates a **new reference every render**:

```jsx
function List({ items = [] }) {
  useEffect(() => { /* ... */ }, [items]);   // runs every render when items is omitted
}
```

Hoist the default to module scope:

```jsx
const EMPTY = [];
function List({ items = EMPTY }) {}
```

## Component granularity

Split a component when:

- A section has its own state that the rest does not need
- A part is reused elsewhere
- The file exceeds what fits comfortably on screen (roughly 150–200 lines)
- A part re-renders far more often than the rest, and isolating it helps

Do **not** split just because a function feels long. Two components that always change together, share five props and are used in one place are harder to follow than one component. Premature extraction produces prop drilling and indirection with no benefit.

A useful heuristic: if extracting requires passing more than three or four props back down, the boundary is probably wrong.

## Rendering a component vs calling it

```jsx
<Component />       // creates an element — a real component instance with its own state
{Component()}       // calls the function — its hooks belong to the PARENT
```

The second form breaks hooks, memoization and the component boundary entirely. It happens accidentally when someone defines a render helper inside a component and calls it:

```jsx
function Parent() {
  const renderRow = (item) => <li>{item.name}</li>;   // fine — returns JSX, no hooks
  const Row = (item) => { useState(); return <li /> }; // NOT fine if called directly
}
```

Related: **never define a component inside another component**. It is a new function identity on every render, so React unmounts and remounts the entire subtree, losing all state and DOM.

```jsx
function Parent() {
  function Child() { return <input /> }   // remounts every render — input loses focus
  return <Child />;
}
```

This is a frequent cause of "my input loses focus while typing".

## How senior engineers actually use this

**They design props like a public API** — few, specific, hard to misuse — and treat adding a boolean prop as a signal to reconsider composition.

**They pass elements as props for layout**, which both flattens the data flow and avoids unnecessary re-renders.

**They forward unknown props** on any component that wraps a DOM element, so consumers are never blocked.

**They hoist default objects and arrays** out of the component body.

**They never nest component definitions**, and lint for it.

## Common pitfalls

- Mutating props.
- Component defined inside another component, remounting the subtree.
- Calling a component as a function instead of rendering it.
- Default `[]` or `{}` in destructuring creating new references every render.
- Boolean prop explosion where a `variant` enum belongs.
- Components that swallow props, forcing wrappers for `data-testid` or ARIA.
- Splitting components so aggressively that prop drilling appears.

## Interview angle

"When would you split a component" and "how do you avoid prop drilling" both land here. Give concrete criteria for splitting (independent state, reuse, differing re-render frequency) and note that splitting has a cost. For prop drilling, the answers in order are: composition and elements-as-props first, context second, a store third — reaching for context immediately is the common weak answer. The nested-component-definition bug is a good one to mention unprompted.
