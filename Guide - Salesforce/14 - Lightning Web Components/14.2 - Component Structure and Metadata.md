# Component Structure and Metadata

## The bundle

```
force-app/main/default/lwc/claimSummary/
    claimSummary.html
    claimSummary.js
    claimSummary.js-meta.xml
    claimSummary.css
    claimSummary.svg
    __tests__/
        claimSummary.test.js
```

Every file shares the folder name. The folder name is the component name, in **camelCase**, and it becomes `c-claim-summary` in markup.

`.svg` is the icon shown in Lightning App Builder — worth adding for anything an administrator will place, since the default is generic.

## The JavaScript

```javascript
import { LightningElement, api } from 'lwc';

export default class ClaimSummary extends LightningElement {
    @api recordId;
}
```

**A default export**, extending `LightningElement`. The class name conventionally matches the folder in PascalCase, though the export being default is what actually matters.

## The metadata file

This is what determines where a component can be used, and it is the most common reason a component does not appear where expected.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>62.0</apiVersion>
    <isExposed>true</isExposed>
    <masterLabel>Claim Summary</masterLabel>
    <description>Shows claim status and coverage for the current record.</description>

    <targets>
        <target>lightning__RecordPage</target>
        <target>lightning__AppPage</target>
        <target>lightning__HomePage</target>
    </targets>

    <targetConfigs>
        <targetConfig targets="lightning__RecordPage">
            <objects>
                <object>Warranty_Claim__c</object>
                <object>Asset</object>
            </objects>
            <property name="showCoverageDetail" type="Boolean" label="Show coverage detail"
                      default="true"/>
            <property name="maxRows" type="Integer" label="Maximum rows" default="10"
                      min="1" max="50"/>
        </targetConfig>
    </targetConfigs>
</LightningComponentBundle>
```

**`isExposed` must be true**, or the component is invisible in App Builder regardless of its targets. This is the single most common cause of "my component does not appear".

**`masterLabel` and `description`** are what an administrator sees when choosing components. Leaving them out gives them the folder name and nothing else.

## Targets

```
lightning__RecordPage        a record page
lightning__AppPage           an app page
lightning__HomePage          the home page
lightning__RecordAction      a quick action
lightning__Tab               a custom tab
lightning__FlowScreen        a flow screen
lightning__UtilityBar        the console utility bar
lightningCommunity__Page     an Experience Cloud page
lightningCommunity__Default  an Experience Cloud component
lightning__AppHome
lightningSnapin__ChatMessage assorted embedded service targets
```

A component can declare several, and each can have its own `targetConfig` with different properties.

## The recordId contract

On a record page, the platform passes the record's Id automatically — **if** the property is named exactly `recordId` and marked `@api`.

```javascript
export default class ClaimSummary extends LightningElement {
    @api recordId;      // populated automatically on a record page
    @api objectApiName; // also populated automatically
}
```

Naming it anything else means it stays undefined, with no error. The same applies to `objectApiName`, which is what makes a component work generically across objects.

For a flow screen, the convention differs — an input variable must be declared in the target config and marked `role="inputOnly"`. See [[07.5 - Screen Flows]].

## Design properties

Properties exposed in `targetConfigs` become configurable in App Builder, which is how one component serves several placements without code changes.

```xml
<property name="cardTitle" type="String" label="Card title" default="Warranty Claims"/>
<property name="maxRows" type="Integer" label="Rows to show" default="10" min="1" max="50"/>
<property name="showClosed" type="Boolean" label="Include closed claims" default="false"/>
<property name="statusFilter" type="String" label="Status" datasource="Submitted,Approved,Rejected"/>
```

```javascript
export default class ClaimList extends LightningElement {
    @api cardTitle = 'Warranty Claims';
    @api maxRows = 10;
    @api showClosed = false;
    @api statusFilter;
}
```

`datasource` produces a picklist in App Builder. A dynamic datasource is possible through a design-time class, which is how a property offers the org's actual picklist values rather than a hardcoded list.

**Default values must be set in both places** — the metadata default is what App Builder shows; the JavaScript default is what applies when the component is used outside App Builder, such as inside another component.

## Property binding on a record page

An App Builder property can bind to a field on the current record:

```xml
<property name="accountId" type="String" label="Account"
          datasource="apex://AccountPickerDatasource"/>
```

More usefully, `{!Record.Field__c}` bindings in some contexts let a property take its value from the record, which avoids a query for something already on screen.

## The API version

```xml
<apiVersion>62.0</apiVersion>
```

Pins platform behaviour for this component. Raising it is a deliberate change requiring testing, not housekeeping — the same principle as Apex classes. See [[01.11 - Release Cycle, Trust and Status]].

## Experience Cloud specifics

Components for Experience Cloud need their own target and often their own configuration:

```xml
<targets>
    <target>lightningCommunity__Page</target>
    <target>lightningCommunity__Default</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightningCommunity__Default">
        <property name="recordId" type="String" label="Record Id"
                  default="{!recordId}"/>
    </targetConfig>
</targetConfigs>
```

`lightningCommunity__Page` makes it available on a page; `lightningCommunity__Default` makes it available inside other components.

The `{!recordId}` default binds to the page's record context, which is how a component on a detail page in Experience Cloud gets its Id — the automatic injection that works on internal record pages does not apply the same way.

Guest user access matters here too: a component on a public Experience Cloud page runs as the Guest User, which is the highest-risk surface on the platform. See [[03.14 - Login Policies, MFA and Session Security]].

## Quick actions

```xml
<targets>
    <target>lightning__RecordAction</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightning__RecordAction">
        <actionType>ScreenAction</actionType>
    </targetConfig>
</targetConfigs>
```

**`ScreenAction`** opens the component in a modal. **`Action`** runs it headlessly with no UI, which is right for a one-click operation.

A headless action must implement `invoke()`:

```javascript
import { LightningElement, api } from 'lwc';
import approveClaim from '@salesforce/apex/ClaimController.approve';

export default class ApproveClaimAction extends LightningElement {
    @api recordId;

    @api
    async invoke() {
        // invoke() is the entry point for a headless quick action
        await approveClaim({ claimId: this.recordId });
        this.dispatchEvent(new ShowToastEvent({
            title: 'Approved',
            variant: 'success'
        }));
    }
}
```

Headless actions are the correct replacement for the JavaScript buttons that Lightning does not support. See [[01.9 - Classic vs Lightning Experience]].

## Static resources and third-party libraries

```javascript
import { loadScript, loadStyle } from 'lightning/platformResourceLoader';
import CHART_JS from '@salesforce/resourceUrl/chartjs';

export default class ClaimChart extends LightningElement {
    chartInitialized = false;

    renderedCallback() {
        if (this.chartInitialized) {
            return;
        }
        this.chartInitialized = true;

        // loadScript resolves once, so the guard prevents repeated loading on rerender
        loadScript(this, CHART_JS + '/chart.min.js')
            .then(() => this.initializeChart())
            .catch((error) => this.handleError(error));
    }
}
```

The `chartInitialized` guard is essential. `renderedCallback` fires on every rerender, and without it the library loads repeatedly.

Shadow DOM constrains what third-party libraries can do — anything reaching for `document.getElementById` will not find elements inside a component. Libraries designed to attach to a passed element work; libraries assuming global DOM access often do not. See [[17.4 - Static Resources]].

## The CSS file

```css
:host {
    display: block;
}

.claim-row {
    padding: var(--lwc-spacingSmall, 0.75rem);
    border-bottom: 1px solid var(--lwc-colorBorder, #dddbda);
}

.high-value {
    font-weight: var(--lwc-fontWeightBold, 700);
}
```

`:host` styles the component's own element. Styles are scoped to the component and cannot leak out or in.

Design tokens as CSS custom properties keep the component consistent with the org's theme. See [[14.15 - Styling, SLDS and Design Tokens]].

## Naming conventions

Consistency matters more than the specific choice, and these hold up:

```
claimSummary              a display component
claimList                 a list
claimEditForm             a form
claimApprovalModal        a modal
claimApprovalAction       a quick action
claimUtils                a shared JavaScript module, not a component
```

**A shared JavaScript module** is a folder with just a `.js` file and no template, exporting functions:

```
force-app/main/default/lwc/claimUtils/
    claimUtils.js
```

```javascript
export function formatCurrency(amount, currencyCode) { }
export function tierFor(amount) { }
```

```javascript
import { formatCurrency, tierFor } from 'c/claimUtils';
```

This is how logic is shared between components without duplication, and it needs no metadata file beyond `isExposed` being false.

## Practical guidance

**Set `isExposed` to true** and declare the right targets, or the component will not appear.

**Name the property `recordId` exactly** for automatic injection.

**Fill in `masterLabel` and `description`** — an administrator sees them.

**Add an `.svg` icon** for anything placed in App Builder.

**Expose configuration as design properties** rather than hardcoding, so one component serves several placements.

**Set defaults in both the metadata and the JavaScript.**

**Guard library loading in `renderedCallback`.**

**Extract shared logic into a module component** rather than duplicating it.
