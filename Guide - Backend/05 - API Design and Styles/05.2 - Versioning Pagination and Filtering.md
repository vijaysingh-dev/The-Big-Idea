# Versioning, Pagination and Filtering

#backend #api-design #rest

> **In one line:** Offset pagination breaks silently on changing data and gets slower the deeper you go, cursor pagination fixes both, and versioning is a promise you cannot take back.

---

## Pagination

### Offset is the obvious choice and the wrong one

```sql
SELECT * FROM documents ORDER BY created_at DESC LIMIT 20 OFFSET 4000;
```

**1. It gets slower the deeper you go.** The database scans and discards 4,000 rows to return 20 — `O(offset)`, not `O(limit)`.

```
OFFSET 0       → 0.4 ms
OFFSET 10000   → 12 ms
OFFSET 100000  → 140 ms
OFFSET 1000000 → 1.4 s
```

⚠️ **This makes deep pagination a denial-of-service vector.** A crawler walking to page 50,000 costs you far more than the client pays.

**2. It skips and duplicates rows when data changes.**

```
Page 1: rows 1-20
        (a row is inserted at the top)
Page 2: OFFSET 20 → row 20 again. Row 21 is never seen.
```

💡 **For any list ordered by recency where new items arrive — which is almost every list in a real product — offset pagination is quietly incorrect.** It works in development because nothing is being inserted.

### Cursor pagination

```sql
SELECT * FROM documents
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Constant time regardless of depth, and stable under insertion.

```python
def encode_cursor(created_at: datetime, doc_id: str) -> str:
    payload = {"c": created_at.isoformat(), "i": doc_id}
    return base64.urlsafe_b64encode(orjson.dumps(payload)).decode().rstrip("=")
```

⚠️ **The tiebreaker column is not optional.** Ordering by `created_at` alone means two rows with identical timestamps can be returned twice or skipped. **Always include a unique column in both the ordering and the cursor.**

The index must match exactly:

```sql
CREATE INDEX ON documents (created_at DESC, id DESC);
```

Without a matching composite index, the query still scans ([[06.3 - Indexes Deep Dive]]).

### Cursor design

| Question | Answer |
|---|---|
| Opaque or readable? | **Opaque.** Base64 discourages parsing, so you can change the format |
| Signed? | Yes for public APIs — stops crafted cursors reading arbitrary data |
| Include the filter set? | **Yes.** A cursor from one filter set is meaningless with another |
| Expiry? | Optional. Useful if the ordering can change |

```python
payload = {
    "c": created_at.isoformat(),
    "i": doc_id,
    "f": hashlib.sha256(orjson.dumps(filters, sort_keys=True)).hexdigest()[:8],
}
```

**If the filter hash does not match, return 400** rather than silently returning wrong results.

### What cursors cost

| Lost | Workaround |
|---|---|
| Jump to page N | Usually not needed. If it is, offset for the first N pages only |
| Total count | Approximate, or none |
| Random access | Not possible by design |

⚠️ **`SELECT COUNT(*)` on a large filtered table scans everything matching.** For most product UIs `has_more` is sufficient.

```sql
SELECT reltuples::bigint FROM pg_class WHERE relname = 'documents';   -- fast estimate
```

💡 **"Showing 1–20 of about 4,300" is almost always acceptable**, and it is orders of magnitude cheaper. Products showing exact counts on large datasets are usually paying more than they realise.

### Multiple sort columns

```sql
-- ORDER BY status ASC, created_at DESC, id DESC
WHERE status > $1
   OR (status = $1 AND created_at < $2)
   OR (status = $1 AND created_at = $2 AND id < $3)
```

⚠️ **Row comparison `(a,b,c) > ($1,$2,$3)` requires all columns to sort in the same direction.** Mixed directions need the expanded form, and some ORMs get this wrong — verify with `EXPLAIN`.

## Filtering

### Every filter needs an index and a limit

```python
ALLOWED_FILTERS = {"status": str, "source_id": str, "created_after": datetime}
ALLOWED_SORTS = {"created_at", "title", "size_bytes"}
MAX_LIMIT = 100
```

⚠️ **An unindexed filter or sort a client can request is a sequential scan on demand.** Every allowed sort column needs an index covering the tiebreaker; every allowed filter needs to be selective, or be documented as slow.

💡 **This is the most common cause of "the API got slow and we do not know why".** Someone added a filter, it was fine on 10,000 rows, and it is a table scan on 10 million.

### Search is not a filter

```
?q=quarterly report
```

Full-text search has different performance characteristics, different indexes and different ranking semantics. **Be explicit about whether results are relevance-ordered or still sorted by `sort`** — they cannot be both ([[06.15 - Search - Postgres vs Elasticsearch]]).

## Versioning

| Strategy | Example | Best for |
|---|---|---|
| **URL path** | `/v1/documents` | Most APIs. Visible, testable, cacheable |
| Header | `Accept: application/vnd.conduit.v2+json` | Purists. Hard to curl |
| **Date-based** | `X-API-Version: 2026-08-17` | Large public APIs |

**URL path is the right default.** Visible in logs, easy to test, works with caching, every client library handles it.

### Date-based versioning

```
Client integrates on 2026-03-01 → pinned forever
Server ships a breaking change  → old client still sees the old shape
```

```python
VERSIONS = ["2026-03-01", "2026-06-15", "2026-08-17"]

def downgrade(response: dict, from_v: str, to_v: str) -> dict:
    for version in reversed(versions_between(to_v, from_v)):
        response = TRANSFORMS[version].down(response)
    return response
```

💡 **The genius is that your core code only knows the latest version.** Transformations are small, isolated, individually testable and composable. You never maintain three copies of a handler.

⚠️ The cost is real: every breaking change needs a transformation written and tested both directions, and the chain grows forever. **Adopt when you have many external clients you cannot force to upgrade** — not before.

### Deprecation

```http
Deprecation: Sun, 01 Nov 2026 00:00:00 GMT
Sunset: Sun, 01 Feb 2027 00:00:00 GMT
Link: <https://docs.conduit.local/migrate-v2>; rel="deprecation"
```

The realistic process:

```
1. Ship the new version, both running
2. Add deprecation headers
3. Instrument per-client usage of the old version   ← the step people skip
4. Contact the top consumers directly
5. Brownout: return errors for a scheduled hour, twice
6. Turn it off
```

⚠️ **Step 3 determines whether you can ever remove anything.** Without per-client version metrics you never know if it is safe, so you never do, and you maintain v1 forever.

💡 **The brownout in step 5 is the technique most teams have not heard of.** Returning 410 for one hour on an announced date surfaces every client that has not migrated — including the ones that never read your emails — while being recoverable.

## In Production

### Limits and defaults

```python
DEFAULT_LIMIT = 20
MAX_LIMIT = 100
```

⚠️ **`limit` must be capped server-side.** `?limit=1000000` should return 400, not a million rows.

💡 **Returning 400 beats silently clamping** — silently returning fewer results than requested causes client bugs where the caller assumes it got everything.

### Consistency across endpoints

⚠️ **The moment one endpoint uses `page_size` and another uses `limit`, every client has special cases forever.** Enforce with a shared dependency:

```python
async def page_params(limit: int = 20, cursor: str | None = None) -> Page:
    if limit > MAX_LIMIT:
        raise HTTPException(400, f"limit must be <= {MAX_LIMIT}")
    return Page(limit=limit, cursor=cursor)
```

### Migrating from offset

```python
if cursor:
    query = keyset_query(cursor, limit)
elif offset is not None:
    deprecated_offset_total.inc()
    query = offset_query(min(offset, MAX_OFFSET), limit)
```

**Cap the offset** so deep pagination fails loudly instead of being slow, then instrument, contact the clients, and remove.

### Stable ordering matters more than you think

⚠️ **Without a tiebreaker, Postgres may return tied rows in different orders on different executions**, depending on plan and parallelism. Users see rows appear twice with no obvious cause.

**Add the tiebreaker to every list query, not just paginated ones.**

## Codebase

**Repo:** `kubernetes/kubernetes`, `django/django-rest-framework`, `stripe` (docs)

**Question to answer:** How does Kubernetes paginate 100,000 pods, and what happens if the `continue` token is used after the data changed? Then: where do Stripe's version transformations live?

**Read, in order:**

1. `kubernetes/staging/src/k8s.io/apiserver/pkg/storage/` — search for `continue` token handling. **Kubernetes returns `410 Gone` when a token is too old** rather than silently returning inconsistent data. That explicit failure is the right design
2. `kubernetes/staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go` — `ListOptions` and `ListMeta`. `resourceVersion` plus `continue` gives consistent pagination over changing data
3. `django-rest-framework/rest_framework/pagination.py` — three pagination classes side by side. **`CursorPagination` is well-commented and explains the tiebreaker requirement**
4. Stripe's versioning documentation and upgrades changelog — the public face of the transformation chain
5. `saleor/saleor/graphql/core/connection.py` — Relay cursor pagination, for comparison

💡 The Kubernetes `410 Gone` behaviour is the detail worth stealing. **When you cannot serve a consistent page, say so explicitly** rather than returning something plausible and wrong.

**Size:** 1–2 sessions.

## Exercise

**Drill 5.2 — Pagination that survives a moving dataset**

```
drills/05-pagination/
├── data/seed.py              # 5M rows, continuous inserts
├── offset/{api.py, depth_bench.py, correctness.py, RESULTS.md}
├── cursor/{encode.py, api.py, multisort.py, tests/}
├── filtering/{allowlist.py, unindexed.py, FINDINGS.md}
├── versioning/{path.py, datebased.py, deprecation.py, RESULTS.md}
└── README.md
```

**Part 1 — Prove offset is broken.** 5 million rows. Sweep offset 0 → 1M, chart latency.

Then the correctness test, which matters more:

```
1. Fetch page 1, record IDs
2. Insert 5 rows at the top
3. Fetch page 2 with OFFSET 20
4. Assert no ID repeats     ← will fail
5. Assert no row was skipped ← will also fail
```

**Quantify it:** with inserts at 10/second and a client paginating at 1 page/second, what fraction of rows is missed across 50 pages? **That number is the argument.**

**Part 2 — Cursor pagination properly.** Opaque, signed, filter-bound, with a tiebreaker.

Repeat the correctness test — it should pass. Repeat the depth benchmark — latency should be flat.

Then the edge cases: identical timestamps, a cursor from a different filter set, a tampered cursor, and a cursor pointing at a deleted row.

**Part 3 — Multi-column sort.** `sort=status,-created_at` with the correct keyset predicate. Verify the index is used with `EXPLAIN ANALYZE`, then drop the index and measure what an unindexed sort costs a client who requests it.

**Part 4 — Attack your own endpoint.** A sort on an unindexed column, a filter on a high-cardinality unindexed column, `limit=1000000`, a filter on a field the user should not see, and SQL injection through a sort parameter.

**For each, confirm the allow-list blocks it, then measure what it would have cost.**

**Part 5 — Date-based versioning.** Three versions with transformations; core handlers know only the latest.

Test a client pinned to v1 receiving the v1 shape through two chained transformations. Then add a fourth version and **confirm you only wrote one transformation, not three handlers.**

**Part 6 — Deprecation with a brownout.** v1 and v2 running, per-client version metrics, deprecation headers.

Run a scheduled brownout against simulated clients, some migrated and some not. **Measure how many distinct clients it surfaced that the metrics alone had not made obvious.**

**Done when:**
- You can state the fraction of rows offset pagination loses at realistic insert rates
- Cursor pagination passes the correctness test with flat latency to 1M rows
- Multi-column keyset uses the index, confirmed by `EXPLAIN`
- All five attacks are blocked, with the cost of each quantified
- Adding a fourth version required exactly one transformation
- The brownout surfaced clients your metrics had not
