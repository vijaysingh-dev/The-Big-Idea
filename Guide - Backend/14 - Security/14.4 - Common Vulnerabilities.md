# Common Vulnerabilities

#backend #security #review

> **In one line:** The same dozen bugs account for almost every real breach, they all pass code review, and the fix is usually a structural change that makes the vulnerable pattern impossible rather than a check you have to remember.

---

## The Idea

💡 **The organising principle for every item below: prefer a mechanism that cannot be forgotten over a rule someone must remember.** A parameterised query cannot be vulnerable to SQL injection; a code review "remember to escape" can be.

This note covers the backend classes. Access control is [[14.1 - AuthN vs AuthZ]], secrets are [[10.8 - Configuration and Secrets]], and tenant isolation is [[14.6 - Multi Tenant Isolation]].

## Injection

### SQL

```python
# ❌
await conn.fetch(f"SELECT * FROM documents WHERE org_id = '{org_id}'")

# ✅ parameterised — the value can never become code
await conn.fetch("SELECT * FROM documents WHERE org_id = $1", org_id)
```

⚠️ **The dangerous cases are where parameters do not work** — identifiers and structural elements:

```python
# ❌ a sort column cannot be a parameter
query = f"SELECT * FROM documents ORDER BY {sort_column}"

# ✅ allow-list, always
ALLOWED_SORTS = {"created_at", "title", "size_bytes"}
if sort_column not in ALLOWED_SORTS:
    raise HTTPException(400)
```

💡 **This is the same allow-list requirement as [[05.2 - Versioning Pagination and Filtering]]**, and it is both a security and a performance control — an unindexed sort is a denial-of-service vector as well as an injection risk.

⚠️ **ORMs are not automatically safe.** `.raw()`, `text()`, `.extra()` and any string-built filter reintroduce the problem.

**Grep your codebase for f-strings near SQL keywords. You will find something.**

### Command injection

```python
subprocess.run(f"pdftotext {filename} -", shell=True)      # ❌
subprocess.run(["pdftotext", filename, "-"], shell=False)  # ✅
```

⚠️ **`shell=True` is the vulnerability.** Without a shell there is no metacharacter interpretation.

**Still validate the filename** — a leading `-` can be interpreted as a flag by the target program.

### Template injection

```python
Template(f"Hello {user_input}").render()      # ❌ SSTI → remote code execution
template.render(name=user_input)              # ✅ data, not template source
```

⚠️ **Server-side template injection in Jinja2 leads directly to code execution.** Never build template *source* from user input.

## SSRF

```python
r = await client.get(user_supplied_url)       # ❌
```

⚠️ **Your server fetches a URL the user controls, from inside your network.**

```
http://169.254.169.254/latest/meta-data/    ← cloud credentials
http://localhost:6379/                       ← your Redis
http://10.0.0.5:5432/                        ← your database
```

**The full defence is in [[05.12 - Webhooks and Callbacks]]**, and the essentials:

| Defence | |
|---|---|
| Allow-list the scheme and port | https, 443 |
| **Resolve, then check the IP against private ranges** | |
| **Connect to the resolved IP**, with the hostname in `Host`/SNI | Defeats DNS rebinding |
| **Never follow redirects** | A 302 to `localhost` defeats URL validation |
| **Egress-restricted network** | The strongest layer |

💡 **Network isolation is the defence that survives a bypass in your validation code**, and validation bypasses do eventually happen.

⚠️ **SSRF appears wherever you fetch user-supplied URLs**: webhooks, source connectors, avatar imports, link previews, PDF generation, and "import from URL". **Audit all of them, not just the obvious one.**

## Deserialisation

```python
pickle.loads(data)              # ⚠️ arbitrary code execution
yaml.load(data)                 # ⚠️ same, unless SafeLoader
yaml.safe_load(data)            # ✅
orjson.loads(data)              # ✅ data only
```

⚠️ **`pickle` on untrusted input is remote code execution, full stop.** It appears in caches, session stores, task queue payloads and cached ML artefacts.

💡 **Check what your task queue serialises with.** Celery's default is JSON now; older configurations used pickle, **and a queue an attacker can write to becomes code execution on every worker** ([[08.9 - Celery in Production]]).

## XXE and File Handling

```python
etree.parse(data)                                     # ⚠️ external entities
etree.parse(data, etree.XMLParser(resolve_entities=False))   # ✅
```

⚠️ **XML external entities read local files and make outbound requests** — SSRF and file disclosure in one. **Relevant anywhere you parse XML: SAML, SOAP, document formats, SVG.**

### Path traversal

```python
path = UPLOAD_DIR / filename                          # ❌ "../../etc/passwd"

safe = (UPLOAD_DIR / filename).resolve()
if not safe.is_relative_to(UPLOAD_DIR.resolve()):     # ✅
    raise HTTPException(400)
```

💡 **Better: never use the user's filename for storage.** Store by generated ID, keep the original name as metadata for display only.

### Uploads

| Control | |
|---|---|
| **Validate content, not the extension** | Magic bytes, or a library |
| **Never execute anything in the upload path** | |
| **Serve from a separate origin** | So stored HTML/SVG cannot script your domain |
| `Content-Disposition: attachment` | Force download for untrusted types |
| Bound size and decompressed size | Zip bombs |
| Scan for malware if you serve files back | |

⚠️ **SVG is an executable format.** An uploaded SVG served from your origin is stored XSS.

💡 **Serving user content from a separate domain is the structural fix**, and it neutralises an entire class of upload bugs at once.

## Race Conditions

```python
if await repo.get_balance(user) >= amount:      # ← two requests both pass
    await repo.deduct(user, amount)
```

⚠️ **Check-then-act is a race at every isolation level below Serializable** ([[06.6 - Transactions and Isolation Levels]]).

```sql
UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1;
```

💡 **The database constraint or the atomic update is the fix**, not a lock and not more careful code.

**The security-relevant cases:** redeeming a single-use coupon twice, exceeding a quota, double-spending credits, and using a password reset token twice.

⚠️ **Test these concurrently.** A sequential test passes against a broken implementation ([[07.5 - Idempotency Keys and Deduplication]]).

## Mass Assignment

```python
@app.patch("/users/me")
async def update(data: dict, user: User):
    await repo.update(user.id, **data)          # ❌ {"role": "admin", "org_id": ...}
```

```python
class UserUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    display_name: str | None = None
    timezone: str | None = None
```

💡 **`extra="forbid"` turns an unexpected field into a 422 instead of a privilege escalation**, and it should be your default model configuration.

⚠️ **Never let a request body set `id`, `org_id`, `role`, `created_at`, `is_admin` or any billing field.** Those come from the authenticated context.

## Rate Limiting Gaps

⚠️ **Endpoints that are expensive or security-sensitive need their own limits** ([[11.5 - Rate Limiting and Quotas]]):

```
Login              → per account AND per IP, different thresholds
Password reset     → per account, or you enable email bombing
Signup             → per IP
Search             → expensive
Export             → very expensive
Anything with an ID → enumeration
```

💡 **A global limit does not protect a specific expensive endpoint**, and a per-IP limit does not stop credential stuffing that spreads across a botnet. **Layer them.**

## Information Disclosure

| Leak | Fix |
|---|---|
| Stack traces in responses | Generic message + request ID ([[05.3 - Error Design]]) |
| **"No account with that email"** | **"Invalid email or password"** |
| 403 vs 404 | 404 for invisible objects, with equal timing |
| Sequential integer IDs | ULID/UUIDv7 ([[06.10 - Schema Design]]) |
| Version headers | Remove `Server`, `X-Powered-By` |
| Verbose GraphQL errors | Mask in production ([[05.8 - GraphQL Security and Limits]]) |
| Debug endpoints | Disable, or restrict to admins |

⚠️ **Timing is a disclosure channel too.** If a nonexistent user returns faster than a wrong password, you have built an enumeration oracle regardless of your message wording.

## In Production

### The dependency supply chain

⚠️ **Your dependencies are the largest part of your attack surface, and you did not write any of it.**

```yaml
- run: pip-audit --require-hashes -r requirements.txt
- run: trivy fs --severity HIGH,CRITICAL .
```

| Practice | |
|---|---|
| **Pin with hashes** | A compromised index cannot substitute a package ([[13.2 - Production Dockerfiles]]) |
| Automated dependency updates | Dependabot, Renovate |
| SBOM | Answer "are we affected" in seconds |
| **Review new dependencies** | Maintainer count, release cadence, transitive weight |
| Vendor critical small dependencies | Sometimes better than a supply-chain risk |

💡 **The most valuable habit: before adding a dependency, look at how many transitive dependencies it brings.** A convenience library pulling in forty packages is forty new maintainers you are trusting.

### Security headers

```python
response.headers.update({
    "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
    "X-Content-Type-Options": "nosniff",
    "X-Frame-Options": "DENY",
    "Referrer-Policy": "strict-origin-when-cross-origin",
    "Content-Security-Policy": "default-src 'self'; frame-ancestors 'none'",
})
```

💡 **CSP is the highest-value header and the hardest to deploy.** Start in `Content-Security-Policy-Report-Only`, collect violations for a fortnight, then enforce.

### The review checklist

```
□  All SQL parameterised; identifiers allow-listed
□  No shell=True; no template source from user input
□  URL fetching: scheme, resolved IP, no redirects, egress-restricted
□  No pickle or unsafe YAML on untrusted input
□  XML parsers with entities disabled
□  Uploads: content-validated, stored by ID, served from another origin
□  Request models: extra="forbid"
□  No user-settable id, org_id, role, or billing fields
□  Check-then-act replaced with atomic updates or constraints
□  Rate limits on login, reset, signup, and expensive endpoints
□  No stack traces, no user enumeration, no timing oracles
□  Security headers, including CSP
□  Dependencies pinned with hashes and scanned
```

### Automate what you can

| Check | Tool |
|---|---|
| Static analysis | `bandit`, `semgrep` |
| Dependencies | `pip-audit`, Dependabot |
| Secrets | `gitleaks` in pre-commit and CI |
| Containers | `trivy` |
| **Custom patterns** | **`semgrep` rules for your own anti-patterns** |

💡 **Custom `semgrep` rules are the highest-leverage security automation available.** Encode your own rules — "no f-string near `execute`", "no `shell=True`", "every Pydantic model has `extra='forbid'`" — **and every future violation is caught at authorship.**

⚠️ **Scanners produce noise. A policy that fails the build on every finding gets bypassed within a month.** Fail on high-confidence rules, report the rest.

### Conduit's specific exposure

| Feature | Risk | Control |
|---|---|---|
| **Source connectors** | **SSRF** | Resolved-IP checks, no redirects, egress-restricted workers |
| **Document upload** | Malicious files, zip bombs | Content validation, size limits, separate serving origin |
| **Text extraction** | Parser exploits, XXE | Sandboxed workers, entities disabled, resource limits |
| **Webhooks** | SSRF | ([[05.12 - Webhooks and Callbacks]]) |
| Search | Injection, DoS | Parameterised, allow-listed sorts, cost limits |
| **Exports** | Expensive, enumeration | Rate limited, authorised per document |
| Multi-tenancy | Cross-tenant access | ([[14.6 - Multi Tenant Isolation]]) |

💡 **The extraction workers process untrusted files with third-party parsers, which is Conduit's highest-risk surface.** A PDF library vulnerability becomes code execution on a worker.

**Run them with no credentials, no network egress beyond what they need, a read-only root filesystem, and strict resource limits** ([[13.1 - Containers From First Principles]]). **Assume the parser will eventually be exploited and bound what that gets an attacker.**

## Codebase

**Repo:** `returntocorp/semgrep`, `PyCQA/bandit`, published CVEs

**Question to answer:** How does a static analyser find an injection pattern, and why does it produce false positives? Then: pick three CVEs in libraries you use and work out whether your usage was vulnerable.

**Read, in order:**

1. `semgrep/semgrep-rules/python/` — **the injection and SSRF rules.** Pattern syntax is readable, and **these rules are a catalogue of what to look for**
2. `bandit/bandit/plugins/injection_shell.py` and `injection_sql.py` — AST-based detection. **Note why it cannot always tell a constant from user input** — that limitation is the source of false positives
3. **`semgrep` rule writing documentation** — **write two rules for your own codebase's patterns.** This is the transferable skill
4. **Three CVEs in your dependencies** — read the advisory, the patch, and the test added. **Then check whether your usage was actually vulnerable**
5. **OWASP Top 10 2021** — read it once, properly, as a checklist against your own system

💡 Reading a CVE patch is the most efficient security education available. **The diff shows exactly what was wrong and what fixed it**, and after three or four you start recognising the shape of the bug class rather than memorising instances.

**Size:** 1–2 sessions.

## Exercise

**Drill 14.4 — Exploit your own application**

⚠️ Everything runs against your own local stack, on a throwaway branch.

```
drills/14-vulns/
├── vulnerable/{app.py}
├── exploits/{sqli.py, cmdi.py, ssrf.py, deser.py, xxe.py, traversal.py,
│              mass_assign.py, race.py, enumeration.py}
├── fixes/{parameterised.py, allowlist.py, url_validation.py, models.py}
├── automation/{semgrep_rules/, bandit.yaml, ci.yaml}
├── upload/{validation.py, svg_xss.py, zipbomb.py}
└── FINDINGS.md
```

**Part 1 — Build a plausibly vulnerable application.** Every class in this note, written the way a competent engineer under time pressure would. **Not caricatured.**

**Part 2 — Exploit all nine.** For each: a working exploit, the impact achieved, and how it would look in your logs.

| Exploit | Target impact |
|---|---|
| SQL injection via a sort parameter | Read another table |
| Command injection via a filename | Execute a command |
| **SSRF** | **Read the cloud metadata endpoint** |
| Pickle deserialisation | Execute code on a worker |
| XXE | Read a local file |
| Path traversal | Read outside the upload directory |
| Mass assignment | Escalate to admin |
| **Race condition** | **Redeem a single-use coupon twice** |
| User enumeration | Distinguish valid emails, including by timing |

**Part 3 — Fix each structurally.** Not with a check to remember — with a mechanism that makes the pattern impossible.

**For each, write down which is which.** "I added validation" is weaker than "the value can no longer reach a code position".

**Part 4 — SSRF properly.** Attempt eight bypasses: `localhost`, `127.0.0.1`, `0.0.0.0`, `169.254.169.254`, decimal-encoded IPs, IPv6 loopback, a hostname resolving to a private IP, and a redirect to `localhost`.

**Then DNS rebinding** — a DNS server returning public then private. **Confirm your validation is bypassed.**

Then implement resolve-then-connect-to-IP and confirm it holds. **Then add egress restriction and confirm it holds even with validation removed.**

**Part 5 — Uploads.** Three attacks: an SVG containing script served from your origin, a zip bomb, and a file with a mismatched extension and content.

**Confirm each succeeds**, then implement content validation, decompression limits, and a separate serving origin.

**Part 6 — The concurrent race.** The single-use coupon, with 50 concurrent redemptions.

**Count successful redemptions.** Then fix with a unique constraint and re-run.

Then confirm the **sequential** test passes against the broken version — **demonstrating why concurrency is required to test this.**

**Part 7 — Custom semgrep rules.** Write five for your own patterns:

```
- f-string adjacent to execute/fetch
- subprocess with shell=True
- Pydantic model without extra="forbid"
- pickle.loads anywhere
- HTTP client call with a non-constant URL
```

**Run them against your vulnerable version and confirm all five fire.** Then wire into CI and confirm a newly-introduced violation fails the build.

**Part 8 — Audit Conduit.** Run the thirteen-item checklist and your semgrep rules against the real codebase.

**Fix every finding, or write a justification.** Then check the extraction worker specifically: **confirm it has no credentials, no unnecessary egress, a read-only root, and resource limits** — and test what an attacker who achieves code execution there can actually reach.

**Done when:**
- All nine exploits work against the vulnerable version
- Every fix is structural, and you can say why for each
- DNS rebinding bypasses naive validation and fails against resolve-then-connect
- Egress restriction holds even with URL validation removed
- Stored SVG XSS is prevented by a separate serving origin
- The concurrent coupon race succeeds and the sequential test does not catch it
- Five custom semgrep rules fire and run in CI
- A compromised extraction worker demonstrably reaches nothing useful
