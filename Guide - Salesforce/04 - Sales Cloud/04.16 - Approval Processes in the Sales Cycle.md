# Approval Processes in the Sales Cycle

## What an approval process is

A declarative feature that submits a record for approval, routes it through one or more steps, locks it while pending, and takes actions on approval, rejection, or recall.

The canonical sales use is discount approval: any deal discounted more than fifteen percent needs a manager, more than thirty needs a director, more than fifty needs the VP.

## The anatomy

**Entry criteria.** Which records can enter the process. A record not meeting them cannot be submitted.

**Initial submission actions.** Run when submitted. Typically a field update setting a status to "Pending Approval", and record locking.

**Steps.** Each with its own criteria, an approver, and what happens on approve or reject. Steps run in order, and a step whose criteria are not met is skipped.

**Final approval actions.** Run when every step approves.

**Final rejection actions.** Run on rejection at any step, unless the step is configured to go back rather than terminate.

**Recall actions.** Run when the submitter withdraws.

## Choosing the approver

The options, and when each is right:

**Manager of the submitter.** Uses the `ManagerId` field on User — not the role hierarchy. This is the most common source of "the approval went to the wrong person": role and manager are separate fields and are frequently out of sync. See [[03.8 - Role Hierarchy]].

**A specific user or queue.** Fixed routing. A queue means any member can approve, which is right when a team shares the responsibility.

**A user from a lookup field on the record.** The flexible option. A `Regional_Director__c` lookup populated by automation lets routing depend on anything you can compute.

**Multiple approvers.** Either all must approve, or the first response decides.

The lookup-field approach is worth reaching for whenever routing is anything more than "my manager", because it moves the routing logic into automation you control rather than into the approval configuration.

```java
public with sharing class ApproverAssignmentService {

    public static void assignDiscountApprover(List<Opportunity> opps) {
        Map<String, Id> approverByRegion = new Map<String, Id>();
        for (Approval_Routing__mdt routing : Approval_Routing__mdt.getAll().values()) {
            approverByRegion.put(routing.Region__c + '|' + routing.Tier__c, routing.Approver_User_Id__c);
        }

        for (Opportunity opp : opps) {
            String tier = opp.Discount_Percent__c > 50 ? 'Executive'
                        : opp.Discount_Percent__c > 30 ? 'Director'
                        : 'Manager';
            opp.Discount_Approver__c = approverByRegion.get(opp.Region__c + '|' + tier);
        }
    }
}
```

Custom Metadata means changing the approver for a region is a deployment of a record, not a change to the approval process itself — which matters because editing an active approval process requires deactivating it, and deactivating it while approvals are pending is disruptive.

## Record locking

While pending, the record is locked. Only approvers, and administrators, can edit it — and even they can only edit fields the process allows.

This is the behaviour that most surprises developers: **Apex cannot update a locked record either.** A trigger or batch job attempting to update an opportunity pending approval fails.

```java
// Detect and handle the locked state
if (Approval.isLocked(opportunityId)) {
    // the record is in an approval process
}

// Unlock programmatically, if the org permits it
Approval.unlock(opportunityId);
Approval.lock(opportunityId);
```

`Approval.unlock()` requires the "Enable record locking and unlocking in Apex" setting to be on. Unlocking behind the approver's back is a decision to make carefully — it usually means the process design is wrong, not that the lock is inconvenient.

## Submitting from code

```java
public with sharing class DiscountApprovalService {

    public static List<Approval.ProcessResult> submit(List<Opportunity> opps, String comment) {
        List<Approval.ProcessSubmitRequest> requests = new List<Approval.ProcessSubmitRequest>();

        for (Opportunity opp : opps) {
            Approval.ProcessSubmitRequest req = new Approval.ProcessSubmitRequest();
            req.setObjectId(opp.Id);
            req.setComments(comment);
            req.setProcessDefinitionNameOrId('Discount_Approval');
            req.setSkipEntryCriteria(false);
            requests.add(req);
        }

        return Approval.process(requests, false);
    }
}
```

Approving or rejecting programmatically works through the pending work item:

```java
List<ProcessInstanceWorkitem> workItems = [
    SELECT Id, ProcessInstance.TargetObjectId
    FROM ProcessInstanceWorkitem
    WHERE ProcessInstance.TargetObjectId IN :opportunityIds
];

List<Approval.ProcessWorkitemRequest> requests = new List<Approval.ProcessWorkitemRequest>();
for (ProcessInstanceWorkitem item : workItems) {
    Approval.ProcessWorkitemRequest req = new Approval.ProcessWorkitemRequest();
    req.setWorkitemId(item.Id);
    req.setAction('Approve');
    req.setComments('Auto-approved: within delegated authority');
    requests.add(req);
}
Approval.process(requests, false);
```

Submitting in bulk has a practical limit — each submission is DML plus the process actions — so batches of a few dozen rather than hundreds.

## Approval history and reporting

`ProcessInstance` records the approval, `ProcessInstanceStep` records each completed step, and `ProcessInstanceWorkitem` records pending ones.

```sql
SELECT TargetObjectId, Status, CreatedDate, CompletedDate,
       (SELECT StepStatus, Actor.Name, Comments, CreatedDate FROM Steps ORDER BY CreatedDate)
FROM ProcessInstance
WHERE TargetObjectId IN :opportunityIds
ORDER BY CreatedDate DESC
```

The metric worth reporting: **time spent pending approval**. Approvals sitting for four days are a bottleneck in the sales cycle, and this is the only place that data exists.

```sql
SELECT Actor.Name approver, COUNT(Id) pendingCount
FROM ProcessInstanceWorkitem
GROUP BY Actor.Name
ORDER BY COUNT(Id) DESC
```

That query, run weekly, finds the person whose inbox is the bottleneck.

## Approval processes versus flows

Flow can now do much of what approvals do, and can do things approvals cannot. The honest comparison:

**Approval processes give you** built-in record locking, a standard approval user interface in Lightning and mobile, native approval history, delegated approvers, and the standard email approval response mechanism. All of that is real work to rebuild.

**Flows give you** unlimited routing logic, dynamic step counts, integration with external systems mid-process, and no need to deactivate anything to make a change.

**Flow Orchestration** sits between them, providing multi-step, multi-user processes with more flexibility than approvals and more structure than a plain flow.

The guidance most teams land on: **use approval processes for genuine approvals** — where locking, an audit trail, and a standard approver experience matter. Use flow or orchestration for multi-step processes that are not really approvals, such as onboarding checklists or review workflows.

Rebuilding an approval in flow to avoid the limitations usually means rebuilding record locking and approval history badly.

## Limits and operational constraints

- 30 active approval processes per object, 15 steps each
- 25 approval steps can be pending on one record
- Editing an active process requires deactivating it, and deactivating with pending approvals leaves those records in an awkward state
- Approvals do not fire on records created by an integration unless explicitly submitted

That last one matters: an opportunity created by an integration with a fifty percent discount does not enter approval automatically. Entry criteria do not submit records; something must submit them. Either the integration submits, or a record-triggered flow does.

## Designing approvals that work

**Keep steps few.** Three levels of approval on a routine discount means deals wait a week. The commercial cost of slow approvals usually exceeds the risk being controlled.

**Set thresholds by value, not just percentage.** A fifty percent discount on a ten thousand rupee order is not the same decision as a ten percent discount on a two crore order.

**Provide delegated approvers.** The `DelegatedApproverId` field on User routes approvals to a delegate when someone is unavailable. Without it, a manager on holiday stops the pipeline.

**Send actionable notifications.** Email approval responses work, and a custom notification or Slack message is faster. The approval sitting unseen in an inbox is the normal failure mode.

**Report on approval duration.** It is the metric that shows whether the process is helping or obstructing.

**Handle the locked-record case in code.** Any batch job touching opportunities will eventually meet one.
