# Retries, Timeouts and Cancellation

Networks fail intermittently. A request that fails once often succeeds immediately after — mobile handoffs, transient server load, brief DNS issues. Handling that correctly requires three mechanisms working together.

## What to retry

```js
function isRetryable(error) {
  if (error.name === "AbortError") return false;      // deliberate cancellation
  if (error instanceof TypeError) return true;         // fetch network failure
  if (error.status === 429) return true;               // rate limited
  if (error.status >= 500) return true;                // server error
  return false;                                        // 4xx — will fail identically
}
```

Retrying a 400 or 404 wastes time and hides the bug. Retrying an abort actively fights the user's intent.

The categories worth retrying: network failures, 5xx, 429, and timeouts.

## Idempotency is the precondition

```
GET, PUT, DELETE, HEAD   → idempotent, safe to retry
POST, PATCH              → not idempotent
```

Retrying a POST that creates an order can create two orders. The request may have succeeded and only the *response* was lost — the client cannot distinguish that from a failure.

The correct fix is an idempotency key:

```js
await api.post("/orders", order, {
  headers: { "Idempotency-Key": crypto.randomUUID() },
});
```

The server stores the key with the result and returns the same response for a repeat. The key must be generated **once per logical operation**, not per attempt — regenerating it defeats the purpose.

Without server support, non-idempotent requests should not be retried automatically. Surface a retry button and let the user decide ([[15.1 - HTTP Fundamentals]]).

## Backoff with jitter

```js
async function retry(fn, { attempts = 3, baseDelay = 300, signal } = {}) {
  for (let attempt = 0; attempt < attempts; attempt++) {
    try {
      return await fn({ signal });
    } catch (err) {
      const isLast = attempt === attempts - 1;
      if (isLast || !isRetryable(err) || signal?.aborted) throw err;

      const backoff = baseDelay * 2 ** attempt;      // 300, 600, 1200
      const jitter = Math.random() * backoff * 0.5;
      await delay(backoff + jitter, { signal });
    }
  }
}
```

**Exponential backoff** — retrying immediately against a struggling server makes the outage worse.

**Jitter** — without random spread, every client that failed at the same moment retries at the same moment, producing a synchronized thundering herd. This is the part people omit, and it is why AWS documents it prominently ([[04.7 - Async Concurrency Patterns]]).

**Respect `Retry-After`** when the server sends it on a 429 or 503 — an explicit instruction beats your calculation:

```js
const retryAfter = err.headers?.get("Retry-After");
const wait = retryAfter ? Number(retryAfter) * 1000 : backoff + jitter;
```

**Cap the delay**, typically at 30 seconds, so a long outage does not leave a request scheduled for ten minutes out.

## Timeouts

```js
const res = await fetch(url, { signal: AbortSignal.timeout(10_000) });
```

`AbortSignal.timeout` aborts with a `TimeoutError` rather than an `AbortError`, so you can distinguish a timeout from a user cancellation.

Combining a timeout with user-driven cancellation:

```js
const signal = AbortSignal.any([
  userController.signal,
  AbortSignal.timeout(10_000),
]);
```

Choose timeouts by operation, not globally:

```
Interactive read (search, autocomplete)   3-5s
Standard read                             10s
Mutation                                  15-30s
File upload                               minutes, or none
```

A timeout that is too aggressive turns a slow connection into a broken app. A timeout that is too long leaves users staring at a spinner with no feedback. The important part is that there **is** one — a request with no timeout can hang indefinitely on a stalled connection, and the browser's own limits are minutes long.

Note the timeout must reset per retry attempt, not span all attempts — otherwise the second attempt starts with a nearly-expired budget.

## Cancellation

Three situations require it:

**Component unmount** — the response arrives for a view that no longer exists.

**Superseded requests** — the user typed again, so the previous search is irrelevant. This is the more important case, because a slow earlier response can resolve *after* a fast later one and overwrite it ([[04.6 - AbortController and Cancellation]]).

**Explicit user cancellation** — a cancel button on a long operation.

```jsx
useEffect(() => {
  const controller = new AbortController();

  (async () => {
    try {
      const data = await api.search(query, { signal: controller.signal });
      setResults(data);
    } catch (err) {
      if (err.name === "AbortError") return;      // expected — not an error
      setError(err);
    }
  })();

  return () => controller.abort();
}, [query]);
```

The `AbortError` guard is essential. An abort must never reach an error boundary, a toast, or error reporting — it is normal control flow.

Note that aborting does **not** stop the server. For a mutation, the operation may have completed; abort only stops the client waiting. This is another reason non-idempotent requests need care.

## Query library defaults

```jsx
useQuery({
  queryKey: ["products"],
  queryFn: ({ signal }) => api.getProducts({ signal }),
  retry: (failureCount, error) => {
    if (error.status >= 400 && error.status < 500) return false;
    return failureCount < 3;
  },
  retryDelay: (attempt) => Math.min(1000 * 2 ** attempt, 30_000),
});
```

TanStack Query retries three times with exponential backoff by default and passes a `signal` to every query function, aborting on unmount or key change ([[24.6 - TanStack Query Fundamentals]]).

Two adjustments worth making: **do not retry 4xx**, since the default retries everything; and **do not retry mutations** by default, which is already the library's behavior and should stay that way unless the endpoint is idempotent.

Getting cancellation for free is one of the strongest practical arguments for using a data library rather than effects.

## Circuit breaking

After repeated failures, stopping requests entirely is better than continuing to hammer a dead service:

```js
function createCircuit({ threshold = 5, resetAfter = 30_000 }) {
  let failures = 0;
  let openedAt = null;

  return async function call(fn) {
    if (openedAt && Date.now() - openedAt < resetAfter) {
      throw new Error("Service unavailable");
    }
    if (openedAt) { openedAt = null; failures = 0; }   // half-open: try once

    try {
      const result = await fn();
      failures = 0;
      return result;
    } catch (err) {
      if (++failures >= threshold) openedAt = Date.now();
      throw err;
    }
  };
}
```

More common on the server than the client, but valuable for a frontend polling a flaky service — it turns a stream of failed requests into one fast, clear failure.

## How senior engineers actually use this

**They classify errors before retrying**, and never retry 4xx or aborts.

**They add jitter**, because synchronized retries after an outage are how a recovering service gets knocked over again.

**They require an idempotency key** before retrying any mutation.

**They thread `AbortSignal` through the entire data layer**, so cancellation works end to end ([[24.1 - Building an API Layer]]).

**They treat `AbortError` as normal**, filtering it out of every error path.

**They set per-operation timeouts** rather than one global value.

## Common pitfalls

- Retrying non-idempotent requests without an idempotency key.
- Retrying 4xx errors.
- Backoff without jitter.
- Ignoring `Retry-After`.
- Aborts surfacing as user-visible errors or reaching error reporting.
- No timeout, so a stalled connection hangs indefinitely.
- Timeout spanning all retry attempts instead of resetting per attempt.
- Nested retry layers multiplying attempts — a retry inside a retry gives nine tries, not three.

## Interview angle

"How do you handle a failed API request" opens this. Cover classification (which errors are retryable), exponential backoff with jitter and why jitter matters, and idempotency as the precondition for retrying mutations. Then cancellation — not just for unmount, but for superseded requests, since a slow earlier response overwriting a newer one is a real bug that abort fixes. Noting that `AbortError` must be treated as normal control flow is the detail that shows you have shipped this.
