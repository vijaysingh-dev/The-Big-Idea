# Performance Profiling Workflow

## Start with a number

"The page is slow" is not actionable. "Saving a claim takes 9 seconds; it took 3 in March" is.

Before investigating, establish:

- **What operation**, exactly — a save, a page load, a report, a batch chunk
- **How slow**, measured
- **For whom** — all users, one region, one profile
- **Since when**, if known
- **How often** — always, or under load

The last two narrow the cause more than anything else. A change in March points at a deployment; slowness only under load points at concurrency or contention.

## Step 1: client or server

The first fork, and it saves hours.

**Chrome DevTools, Network tab.** Look at the Aura or Apex request duration.

- Long **server time**, short rendering → the problem is in Apex, queries, or automation
- Short server time, long **scripting or rendering** → the problem is in the components

The **Salesforce Page Optimizer** extension does this specifically for Lightning pages, reporting slow components, the number of server calls, and the metadata contributing to load time. It is the fastest first tool for a slow record page. See [[14.17 - Performance and Rendering]].

## Step 2: if it is the client

The usual causes, in order:

**Too many components.** Fourteen components on a record page, several making their own Apex calls.

**Uncacheable Apex.** Read-only methods without `cacheable=true` fetch on every render.

**Several wires where one composed method would do.** Three round trips instead of one. See [[14.10 - Calling Apex - Wire vs Imperative]].

**Expensive getters** recomputing on every rerender.

**Large lists** rendered without pagination.

The audit is the checklist in [[14.17 - Performance and Rendering]]. Most slow Lightning pages resolve to component count and uncached Apex.

## Step 3: if it is the server

Capture a debug log for the operation, with `APEX_PROFILING` at FINE and `DB` at INFO.

```
Setup → Debug Logs → New Trace Flag on the affected user
```

Then read it in this order.

**The limit block first.**

```
LIMIT_USAGE_FOR_NS|(default)|
  Number of SOQL queries: 94 out of 100
  Number of query rows: 41203 out of 50000
  Number of DML statements: 118 out of 150
  Maximum CPU time: 8214 out of 10000
```

This tells you which resource is the constraint before you read a single line of code.

**Note the namespace headers.** A managed package's consumption appears separately, and a package consuming 60 queries leaves you 40.

**Then the execution tree**, in the Developer Console, which attributes time per operation rather than showing a flat log. This is what identifies the expensive step. See [[20.3 - Developer Console and Log Inspector]].

## Step 4: attribute the cost

Three broad outcomes, each with a different fix.

**Queries dominate.** Either too many — a query in a loop — or too slow, meaning non-selective.

**CPU dominates.** Nested loops, describe calls, string concatenation, JSON, or accumulated automation.

**DML dominates.** The cost is downstream: triggers, flows, and roll-ups firing on the save.

Bracketing narrows it quickly:

```java
Long start = Limits.getCpuTime();
Map<Id, Asset> assets = loadAssets(claims);
System.debug('LOAD: ' + (Limits.getCpuTime() - start) + 'ms, '
    + Limits.getQueries() + ' queries');

Long afterLoad = Limits.getCpuTime();
enrichClaims(claims, assets);
System.debug('ENRICH: ' + (Limits.getCpuTime() - afterLoad) + 'ms');

Long afterEnrich = Limits.getCpuTime();
update claims;
System.debug('UPDATE: ' + (Limits.getCpuTime() - afterEnrich) + 'ms');
```

**If `UPDATE` dominates, the problem is not your code** — it is what runs on save. That distinction changes the entire investigation.

## Step 5a: slow queries

```sql
SELECT Id, Status__c FROM Warranty_Claim__c
WHERE Account__c = :accountId AND Status__c != 'Closed'
```

**Read the query plan.** Developer Console → Query Plan, or the REST explain endpoint. A **cost above 1 means a table scan**.

**Check whether the filter is selective at all:**

```sql
SELECT COUNT() FROM Warranty_Claim__c WHERE Status__c != 'Closed'
SELECT COUNT() FROM Warranty_Claim__c
```

If it returns most of the table, no index helps.

**Fix in this order:**

1. Remove `!=` and `NOT IN` — rewrite as a positive `IN` list
2. Remove leading wildcards
3. Add a date bound
4. Select fewer fields
5. Then consider a custom index

See [[08.10 - Query Plan Tool and Query Optimization]] and [[16.9 - Skinny Tables and Custom Indexes]].

## Step 5b: too many queries

Count occurrences of a query in the log — the same line number appearing 200 times is a query in a loop.

```bash
grep "SOQL_EXECUTE_BEGIN" debug.log | sort | uniq -c | sort -rn | head -20
```

That one command finds most query-limit problems in an unfamiliar codebase.

The fix is collect-query-act. See [[10.6 - Bulkification Patterns]].

## Step 5c: CPU

Bracket to find the section, then look for the usual causes: nested loops over collections, `getGlobalDescribe()` in a loop, `+=` string building, JSON on large structures.

If none of your code is expensive, the cost is **accumulated automation**. See [[16.3 - CPU Time and Heap Size]].

## Step 6: audit the automation

When the cost is in the DML rather than in your code.

```bash
sf data query --use-tooling-api \
  --query "SELECT Name, TableEnumOrId, Status, LengthWithoutComments FROM ApexTrigger WHERE TableEnumOrId = 'Warranty_Claim__c'"
```

```sql
SELECT ApiName, Label, TriggerType, Status
FROM FlowDefinitionView
WHERE Status = 'Active' AND TriggerObjectOrEventLabel = 'Warranty Claim'
```

Plus validation rules, roll-up summaries **on the object and its parents**, assignment and escalation rules, and any managed package.

**Look for the cascade.** Nested `DML_BEGIN` blocks in the log are cascade levels:

```
DML_BEGIN [1] Op:Insert Type:Claim_Part__c Rows:200
  CODE_UNIT_STARTED Trigger:ClaimPartTrigger after insert
    DML_BEGIN [2] Op:Update Type:Warranty_Claim__c Rows:48
      CODE_UNIT_STARTED Trigger:WarrantyClaimTrigger after update
        DML_BEGIN [3] Op:Update Type:Asset Rows:12
```

Four levels on one user action is an org where automation accumulated without an owner. See [[11.9 - Triggers and Order of Execution]].

## Step 7: intermittent failures

Failures that appear under load and not in testing point at contention or concurrency.

**`UNABLE_TO_LOCK_ROW`** → lock contention. Ask what the failing records have in common; it is almost always a shared parent or owner. See [[10.8 - Record Locking and Deadlocks]] and [[10.9 - Data Skew]].

**`CONCURRENT_REQUESTS_LIMIT_EXCEEDED`** → too many slow synchronous requests at once. The failing request is usually not the cause; correlate with what else was running. See [[16.6 - Concurrency and Long Running Requests]].

**A batch job failing on some chunks** → scope size. Halve it as the first move.

**Failures clustering at a time of day** → a scheduled job or an integration window.

## Step 8: verify

Measure the same operation the same way, and record both numbers.

```java
@IsTest
static void claimSaveStaysWithinBudget() {
    List<Warranty_Claim__c> claims = TestDataFactory.buildClaims(200);

    Test.startTest();
    insert claims;

    // asserting on consumption is what stops the regression coming back
    Assert.isTrue(Limits.getQueries() < 30,
        'Queries: ' + Limits.getQueries());
    Assert.isTrue(Limits.getCpuTime() < 4000,
        'CPU: ' + Limits.getCpuTime() + 'ms');
    Test.stopTest();
}
```

An optimization without a test is an optimization that will be undone. Someone adds a query inside a loop, every functional test passes, and the problem returns in three months.

## Ongoing monitoring

Profiling reactively is worse than noticing early.

**Event Monitoring**, with Shield, gives real-user request durations across the org — the only view of what is actually slow in production. See [[20.6 - Event Monitoring and Operational Visibility]].

**The Lightning Usage App** shows page load times by page and browser.

**A batch run log** with duration per job, so a job taking twice as long as last month is visible.

**Org limits, logged daily:**

```java
for (System.OrgLimit limit : OrgLimits.getAll()) {
    if (limit.getValue() > limit.getLimit() * 0.7) {
        AutomationLogger.logWarning('OrgLimits',
            limit.getName() + ': ' + limit.getValue() + ' of ' + limit.getLimit());
    }
}
```

Anything above 70 percent is a warning worth acting on before it becomes an incident.

## The workflow in short

```
1. Get a number, and know when it changed
2. Client or server?
3. Server → debug log → limit block first, then the execution tree
4. Attribute: queries, CPU, or DML?
5. Queries    → query plan, selectivity, then indexes
   CPU        → bracket, find the section
   DML        → audit the automation and the cascade
6. Intermittent → contention, concurrency, or scope size
7. Fix, measure, and assert on the result
8. Monitor so the next one is noticed early
```

## Section 16 in one paragraph

Governor limits are a fairness mechanism in a multi-tenant system, which is why they fail hard and cannot be caught — a soft limit could be ignored, and ignoring it would still consume the resource. They are per transaction and shared with every flow, validation rule, roll-up, and managed package running alongside your code, so perfectly bulkified Apex can fail because something else spent the budget first. The two that bind are 100 queries and 10 seconds of CPU, and the two that are hardest to debug are CPU and heap, because neither points at a line number and both are frequently consumed by automation you did not write. Async exists to give more transactions rather than bigger ones, which is why "move it to a Queueable" answers so many limit problems. And the design target is headroom rather than compliance: a transaction at 94 of 100 queries is not working, it is one deployment away from failing, and the person who adds that flow will have no way to know.
