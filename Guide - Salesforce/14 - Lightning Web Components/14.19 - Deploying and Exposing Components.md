# Deploying and Exposing Components

## Deployment

An LWC bundle is metadata like anything else.

```bash
sf project deploy start --source-dir force-app/main/default/lwc/claimList --target-org my-sandbox
sf project deploy start --manifest manifest/package.xml --target-org staging
```

**No test coverage requirement.** Unlike Apex, LWC has no platform-imposed coverage gate — Jest tests run in CI and never reach the org. See [[14.18 - Jest Testing for LWC]].

**A deployment fails on a compile error**, including an unknown field in a `@salesforce/schema` import. That is a feature: schema imports give deploy-time validation that string field names do not.

## The exposure checklist

A deployed component that does not appear is nearly always one of five things:

```
[ ] isExposed is true
[ ] The right target is declared
[ ] The object is listed in targetConfig for a record page
[ ] The user's profile has access to the Apex class the component calls
[ ] The component was added to the page in App Builder
```

The fourth is the one that surprises people: a component calling an Apex method silently renders nothing for a user without access to that class. Apex class access is granted through a permission set, and it is easy to forget when the developer's own admin profile has everything. See [[03.4 - Permission Sets and Permission Set Groups]].

## Placing it in App Builder

```xml
<targets>
    <target>lightning__RecordPage</target>
    <target>lightning__AppPage</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightning__RecordPage">
        <objects>
            <object>Warranty_Claim__c</object>
        </objects>
        <property name="showCoverage" type="Boolean" label="Show coverage detail" default="true"/>
    </targetConfig>
</targetConfigs>
```

**Lightning record pages are metadata too.** A component added to a page in App Builder is a change to the `FlexiPage`, which must be deployed alongside the component or the target org shows nothing.

```
force-app/main/default/flexipages/Warranty_Claim_Record_Page.flexipage-meta.xml
```

Forgetting the FlexiPage is the most common "it worked in the sandbox" deployment gap — the component deployed, and nothing placed it.

**Component visibility filters** in App Builder let a component show conditionally, by record field, device, or user permission, with no code:

```
Filter: Status__c equals "Submitted"
Filter: $Permission.Can_Approve_Claims equals true
```

Using a visibility filter rather than an `lwc:if` inside the component means the component is not constructed at all when hidden, which is cheaper. See [[14.17 - Performance and Rendering]].

## Quick actions

```xml
<targets>
    <target>lightning__RecordAction</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightning__RecordAction">
        <actionType>ScreenAction</actionType>
    </targetConfig>
</targetConfigs>
```

Then a quick action in Setup, with type **Lightning Web Component**, pointing at it — and the action added to the page layout or the Highlights Panel.

Three metadata pieces: the component, the `QuickAction`, and the layout. Missing the third means the action exists and appears nowhere.

`ScreenAction` opens in a modal; `Action` runs headlessly through `invoke()`. See [[14.2 - Component Structure and Metadata]].

## Flow screens

```xml
<targets>
    <target>lightning__FlowScreen</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightning__FlowScreen">
        <property name="assetId" type="String" label="Asset Id" role="inputOnly"/>
        <property name="selectedFaultCode" type="String" label="Selected Fault Code"
                  role="outputOnly"/>
    </targetConfig>
</targetConfigs>
```

`role` of `inputOnly`, `outputOnly`, or omitted for both directions.

The component must dispatch `FlowAttributeChangeEvent` for the flow to see an output value:

```javascript
import { FlowAttributeChangeEvent } from 'lightning/flowSupport';

handleSelection(event) {
    this.selectedFaultCode = event.detail.value;
    // without this the flow never sees the value, even though the property is set
    this.dispatchEvent(new FlowAttributeChangeEvent('selectedFaultCode', this.selectedFaultCode));
}
```

Navigation within a flow uses `FlowNavigationNextEvent`:

```javascript
import { FlowNavigationNextEvent } from 'lightning/flowSupport';

handleContinue() {
    this.dispatchEvent(new FlowNavigationNextEvent());
}
```

See [[07.5 - Screen Flows]].

## Experience Cloud

```xml
<targets>
    <target>lightningCommunity__Page</target>
    <target>lightningCommunity__Default</target>
</targets>

<targetConfigs>
    <targetConfig targets="lightningCommunity__Default">
        <property name="recordId" type="String" label="Record Id" default="{!recordId}"/>
    </targetConfig>
</targetConfigs>
```

`{!recordId}` binds to the page's record context — the automatic injection that works on internal record pages does not apply the same way.

Two things to verify separately:

**Guest user access.** A component on a public page runs as the Guest User, which needs explicit access to the Apex class and the objects. This is the highest-risk surface on the platform, and a component that works for an authenticated user may silently render nothing for a guest. See [[03.14 - Login Policies, MFA and Session Security]].

**Styling.** Site branding differs from the internal theme, and toasts may not work. Test in the published site, not the builder preview. See [[14.15 - Styling, SLDS and Design Tokens]].

## The utility bar

```xml
<targets>
    <target>lightning__UtilityBar</target>
</targets>
```

Added to a Lightning App's utility bar in Setup.

Utility bar components **persist across every tab**, which has two consequences: anything expensive runs continuously, and messaging needs `APPLICATION_SCOPE` to hear page components. See [[14.8 - Lightning Message Service]].

## Mobile

A component on a record page appears in the Salesforce mobile app automatically, and appearing is not the same as working.

```javascript
import { LightningElement } from 'lwc';
import FORM_FACTOR from '@salesforce/client/formFactor';

export default class ClaimList extends LightningElement {
    get isPhone() {
        // Small, Medium, or Large — the basis for a genuinely different mobile layout
        return FORM_FACTOR === 'Small';
    }
}
```

Testing on an actual device rather than a narrowed browser is worth doing. Touch targets, keyboard behaviour, and network latency all differ.

Component visibility filters in App Builder can also target form factor, which hides a desktop-oriented component on phones without code.

## Lightning Out

Embedding an LWC in an external page or a Visualforce page.

```html
<apex:page>
    <apex:includeLightning />
    <div id="claimContainer"></div>

    <script>
        $Lightning.use("c:ClaimApp", function() {
            $Lightning.createComponent(
                "c:claimList",
                { recordId: "{!$CurrentPage.parameters.id}" },
                "claimContainer",
                function(component) { }
            );
        });
    </script>
</apex:page>
```

**An Aura dependency app is required** — Lightning Out cannot bootstrap an LWC directly:

```xml
<aura:application access="GLOBAL" extends="ltng:outApp">
    <aura:dependency resource="c:claimList"/>
</aura:application>
```

The constraints are real: no navigation service, toasts may not work, and the styling context differs. Lightning Out is for genuinely external embedding, and for a Visualforce page an inline LWC through `lightning:container` or a rewrite is usually better.

## Component visibility and permissions

Three separate layers, and all three must permit the user:

**Apex class access** through a permission set, for any class the component calls.

**Object and field permissions**, since LDS enforces them and a component reading a restricted field renders nothing.

**Component visibility filters** in App Builder, including `$Permission` checks.

A component hidden by a visibility filter is a UI decision, not security. **The Apex behind it must still check the permission** — a user can call an `@AuraEnabled` method directly regardless of what is rendered. See [[03.13 - Enforcing Security in Apex and SOQL]].

## Packaging

For a managed or unlocked package, components need `isExposed` true to be usable outside the namespace, and they gain the namespace prefix:

```html
<c-claim-list></c-claim-list>              <!-- within the package -->
<northwind-claim-list></northwind-claim-list>   <!-- in a subscriber org -->
```

**A `global` Apex method backing a packaged component can never be removed**, so the component's Apex surface is a permanent contract. See [[18.12 - Package Design - Unlocked, Managed, 1GP vs 2GP]].

## The deployment checklist

```
[ ] Component bundle
[ ] Apex classes it calls
[ ] Custom fields referenced in schema imports
[ ] Message channels
[ ] Static resources
[ ] Custom labels
[ ] Custom permissions
[ ] The FlexiPage placing the component
[ ] The QuickAction, if any
[ ] The page layout referencing the quick action
[ ] Permission sets granting Apex class access
[ ] Permission sets granting object and field access
```

The last three are the ones most often missing, and they produce the same symptom: the component deploys cleanly and nobody can see it.

## Section 14 in one paragraph

LWC is web standards with a thin Salesforce layer, and the platform data layer is the part worth leaning on: Lightning Data Service enforces field-level security and sharing with no Apex, caches across components, and keeps the page in sync — so the best Apex controller is often none. Data flows down through `@api` properties and up through lowercase `CustomEvent`s, with Lightning Message Service only for crossing component trees. Fields are reactive on assignment, not mutation, which is the single most common source of a UI that will not update, and wire parameters need the `$` prefix to be reactive at all. Performance is dominated by getters recomputing on every rerender, unstable iteration keys, and one component making three round trips where a composed Apex method would make one — all of which multiply in a console where components rerender on every tab switch. And a component that deploys but does not appear is nearly always `isExposed`, a missing FlexiPage, or a permission set that grants no access to the Apex class behind it.
