# CI-CD Pipelines

## What a pipeline is for

Not automation for its own sake. Three specific outcomes:

**Nothing reaches production without validation.** A pull request that would fail deployment fails the build instead.

**Feedback is fast enough to act on.** A developer learns within minutes, not after a release window.

**Releases are repeatable.** The same steps, in the same order, every time — rather than someone's memory at 11pm.

## The two stages

**On a pull request: validate.**

```
Static analysis
LWC unit tests
Delta manifest from the diff
Deploy validate against the target org
Coverage gate
```

Nothing is deployed. The check is whether it *would* deploy.

**On merge: deploy.**

```
Delta manifest
Deploy to the target org
Post-deployment script
Smoke check
```

That split — validate on PR, deploy on merge — is the shape of every working Salesforce pipeline.

## Authentication

```bash
sf org login jwt \
  --client-id "$SF_CLIENT_ID" \
  --jwt-key-file server.key \
  --username "$SF_USERNAME" \
  --instance-url "$SF_INSTANCE_URL" \
  --alias target
```

**JWT is the only sensible CI authentication.** No browser, no password, no refresh token to expire quietly after ninety days. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**The private key is a secret**, stored in the pipeline's secret store and decoded at runtime:

```yaml
- name: Decode the JWT key
  run: echo "${{ secrets.SF_JWT_KEY }}" | base64 --decode > server.key
```

**Never commit `server.key`.** It belongs in `.gitignore`, and a committed one is a security incident requiring rotation.

**One connected app per environment**, with a dedicated integration user scoped to what deployment requires — not System Administrator, though deployment does need broad metadata permissions in practice.

## A GitHub Actions pipeline

```yaml
name: Salesforce CI

on:
  pull_request:
    branches: [integration, uat, main]
  push:
    branches: [integration, uat, main]

jobs:
  validate:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # full history, required for the diff

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: |
          npm ci
          npm install --global @salesforce/cli
          sf plugins install sfdx-git-delta
          sf plugins install @salesforce/sfdx-scanner

      - name: Static analysis
        run: sf scanner run --target force-app --severity-threshold 3 --format table

      - name: LWC unit tests
        run: npm run test:unit -- --coverage

      - name: Authenticate
        run: |
          echo "${{ secrets.SF_JWT_KEY }}" | base64 --decode > server.key
          sf org login jwt --client-id "${{ secrets.SF_CLIENT_ID }}" \
            --jwt-key-file server.key \
            --username "${{ secrets.SF_USERNAME }}" \
            --instance-url "${{ secrets.SF_INSTANCE_URL }}" \
            --alias target

      - name: Generate the delta manifest
        run: |
          sf sgd source delta \
            --to HEAD \
            --from origin/${{ github.base_ref }} \
            --output manifest/ \
            --generate-delta

      - name: Validate the deployment
        run: |
          sf project deploy validate \
            --manifest manifest/package/package.xml \
            --post-destructive-changes manifest/destructiveChanges/destructiveChanges.xml \
            --test-level RunSpecifiedTests \
            --tests $(node scripts/affected-tests.js) \
            --target-org target \
            --wait 60

      - name: Clean up
        if: always()
        run: rm -f server.key
```

**`fetch-depth: 0`** is required — a shallow clone has no history to diff against.

**`sfdx-git-delta`** produces a manifest containing only what changed, which turns a twenty-minute full deployment into a two-minute incremental one. It is close to essential. See [[21.3 - Salesforce CLI and SFDX]].

**`--generate-delta`** also copies the changed source files into a delta directory, which some deployment steps prefer over a manifest.

## Choosing which tests to run

The decision that determines pipeline speed.

```
RunSpecifiedTests   fast, and coverage must still clear for deployed classes
RunLocalTests       everything except managed packages — slow, and thorough
```

**Specified tests on a pull request, all tests before production.**

Determining which tests are affected, by convention:

```javascript
// scripts/affected-tests.js
const { execSync } = require('child_process');

const changed = execSync('git diff --name-only origin/main -- force-app')
    .toString().split('\n').filter(Boolean);

const testClasses = new Set();

for (const file of changed) {
    const match = file.match(/classes\/(\w+)\.cls$/);
    if (!match) continue;

    const className = match[1];
    // the convention: ClaimService is tested by ClaimServiceTest
    testClasses.add(className.endsWith('Test') ? className : `${className}Test`);
}

console.log([...testClasses].join(','));
```

Crude, and it works when the naming convention holds. A more thorough version uses the dependency graph:

```sql
SELECT MetadataComponentName FROM MetadataComponentDependency
WHERE RefMetadataComponentName = 'ClaimApprovalService'
  AND MetadataComponentType = 'ApexClass'
```

**Always run everything before production**, whatever the pull request check does.

## Deploying on merge

```yaml
  deploy:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - name: Authenticate
        run: |
          echo "${{ secrets.SF_JWT_KEY }}" | base64 --decode > server.key
          sf org login jwt --client-id "${{ secrets.SF_CLIENT_ID }}" \
            --jwt-key-file server.key --username "${{ secrets.SF_USERNAME }}" \
            --instance-url "${{ secrets.SF_INSTANCE_URL }}" --alias target

      - name: Generate the delta manifest
        run: sf sgd source delta --to HEAD --from HEAD~1 --output manifest/

      - name: Deploy
        run: |
          sf project deploy start \
            --manifest manifest/package/package.xml \
            --post-destructive-changes manifest/destructiveChanges/destructiveChanges.xml \
            --test-level RunLocalTests \
            --target-org target \
            --wait 90

      - name: Post-deployment steps
        run: sf apex run --file scripts/apex/post-deploy.apex --target-org target

      - name: Smoke check
        run: sf apex run --file scripts/apex/smoke-test.apex --target-org target
```

**The post-deployment script is what makes releases repeatable.** Creating Custom Setting records, rescheduling jobs, backfilling a field — all versioned, all automatic:

```java
// scripts/apex/post-deploy.apex
if ([SELECT COUNT() FROM Automation_Settings__c] == 0) {
    insert new Automation_Settings__c(
        SetupOwnerId = UserInfo.getOrganizationId(),
        Disable_All_Automation__c = false
    );
}

// scheduled classes cannot be modified while scheduled, so reschedule after deploying
for (CronTrigger ct : [
    SELECT Id FROM CronTrigger
    WHERE CronJobDetail.Name LIKE 'Claim Reconciliation%' AND State != 'DELETED'
]) {
    System.abortJob(ct.Id);
}
System.schedule('Claim Reconciliation Daily', '0 0 2 * * ?', new ClaimReconciliationBatch());
```

The abort-and-reschedule step is the one most often forgotten, and it produces a scheduled job that silently stops running. See [[12.5 - Scheduled Apex]].

## Validate then quick deploy

For a production release with a short window.

```yaml
      - name: Validate ahead of the window
        id: validate
        run: |
          RESULT=$(sf project deploy validate \
            --manifest manifest/package/package.xml \
            --test-level RunLocalTests \
            --target-org production --wait 90 --json)
          echo "job_id=$(echo $RESULT | jq -r '.result.id')" >> $GITHUB_OUTPUT

      - name: Deploy during the window
        run: sf project deploy quick --job-id ${{ steps.validate.outputs.job_id }} --target-org production
```

**Validation runs every test and takes as long as it takes. The quick deploy commits in seconds.**

The validation is good for 10 days, and the target org must not have changed materially in between. This is how a thirty-minute test run happens on Thursday afternoon and the release happens in a two-minute window on Saturday morning.

## Scratch org validation

For a stronger check than validating against a shared sandbox.

```yaml
      - name: Create a scratch org
        run: |
          sf org create scratch --definition-file config/project-scratch-def.json \
            --alias ci --duration-days 1 --wait 10

      - name: Deploy everything and run all tests
        run: |
          sf project deploy start --source-dir force-app --target-org ci
          sf apex run test --test-level RunLocalTests --code-coverage --wait 30 --target-org ci

      - name: Clean up
        if: always()
        run: sf org delete scratch --target-org ci --no-prompt
```

**A clean org proves the repository is complete** — no residue, no drift, no manual configuration someone applied months ago.

**`if: always()` on the cleanup is essential.** A failed build leaving the org behind exhausts the Dev Hub allocation within days, and then every subsequent build fails for an unrelated reason. See [[21.4 - Dev Hub and Scratch Orgs]].

Creation costs two to five minutes, which is the tradeoff against validating into a persistent sandbox.

## Coverage gates

```javascript
// scripts/check-coverage.js
const fs = require('fs');
const results = JSON.parse(fs.readFileSync('test-results/test-result.json'));

const orgWide = results.summary.testRunCoverage.replace('%', '');
const minimum = 85;

if (Number(orgWide) < minimum) {
    console.error(`Coverage ${orgWide}% is below the ${minimum}% gate`);
    process.exit(1);
}

const failures = results.coverage.coverage
    .filter(c => c.coveredPercent < 70)
    .map(c => `${c.name}: ${c.coveredPercent}%`);

if (failures.length) {
    console.error('Classes below the 70% per-class floor:\n' + failures.join('\n'));
    process.exit(1);
}
```

**A gate above the platform's 75%** so a release is never blocked by being at exactly the minimum.

**A per-class floor** is what actually prevents untested classes, since the org-wide figure hides them.

**Gate the diff, not the org**, when improving a low-coverage codebase — no *new* class below the floor. That stops the problem growing without requiring a remediation project. See [[19.10 - Code Coverage, Quality and CI Gates]].

## Other platforms

**Azure DevOps:**

```yaml
trigger:
  branches: { include: [integration, uat, main] }

pool: { vmImage: 'ubuntu-latest' }

steps:
  - task: NodeTool@0
    inputs: { versionSpec: '20.x' }

  - script: |
      npm install --global @salesforce/cli
      sf plugins install sfdx-git-delta
    displayName: 'Install the CLI'

  - script: |
      echo "$(SF_JWT_KEY)" | base64 --decode > server.key
      sf org login jwt --client-id "$(SF_CLIENT_ID)" --jwt-key-file server.key \
        --username "$(SF_USERNAME)" --alias target
    displayName: 'Authenticate'
```

**Jenkins** works with the same commands in a `Jenkinsfile`, and is common in organizations with existing Jenkins infrastructure.

**GitLab CI**, **Bitbucket Pipelines**, and **CircleCI** all follow the same shape. **The CLI commands are identical; only the YAML differs**, which makes the choice of platform largely a question of what the organization already runs.

## Managed DevOps platforms

Several products wrap this: **Gearset**, **Copado**, **Flosum**, **AutoRABIT**, and **Salesforce DevOps Center**.

**What they add:** a UI for administrators, metadata-aware diffing and merging, automated drift detection, back-promotion, and data deployment.

**What they cost:** licensing, and a layer between the team and the underlying tooling.

**Gearset's metadata comparison** is genuinely better than a Git diff for declarative work — it understands that reordering picklist values is not a change, which Git does not.

**DevOps Center** is Salesforce's own free offering, targeted at teams moving off change sets, and less capable than the commercial products.

**The honest position:** a team with developers who know Git and the CLI does not need a commercial platform. A team of administrators moving off change sets frequently does, because the UI is the point.

## Pipeline speed

The metric that determines whether the pipeline is used or worked around.

```
Static analysis        30 seconds
Jest tests             45 seconds
Delta manifest         10 seconds
Deploy validate        3 to 20 minutes  ← dominates
```

**The deployment validation dominates**, and the levers are:

**Delta manifests** rather than full deployments.

**`RunSpecifiedTests`** on pull requests.

**Parallel jobs** — static analysis and Jest run alongside authentication.

**A faster test suite**, which is the deepest fix and the hardest. See [[19.10 - Code Coverage, Quality and CI Gates]].

**Under ten minutes for a pull request check** is the target. Beyond twenty, people stop waiting and start merging optimistically.

## What breaks

**Authentication fails after a certificate expires.** Track the expiry date; a JWT certificate has a fixed lifetime and its expiry stops every pipeline at once. See [[13.11 - JWT Bearer Flow and Server to Server Auth]].

**A shallow clone breaks the delta.** `fetch-depth: 0`.

**Someone else's failing test blocks the release.** `RunLocalTests` runs everything.

**Scratch org allocation exhausted** by builds that did not clean up.

**A CLI update changes behaviour.** Pinning the version is defensible; letting it float catches new capabilities and occasionally breaks.

**The org drifted** and the validation fails on something nobody changed. See [[21.7 - Git Branching Strategies for Salesforce]].

## Practical guidance

**Validate on pull requests, deploy on merge.**

**Authenticate with JWT**, and never commit the key.

**Use `sfdx-git-delta`** — full deployments are too slow for a pull request check.

**Run all tests before production**, specified tests on a pull request.

**Validate then quick-deploy** for a short release window.

**Put post-deployment steps in a versioned Apex script**, including scheduled job rescheduling.

**Always clean up scratch orgs**, including on failure.

**Gate coverage above the platform minimum**, with a per-class floor.

**Keep the pull request check under ten minutes.**

**Track the JWT certificate expiry.**
