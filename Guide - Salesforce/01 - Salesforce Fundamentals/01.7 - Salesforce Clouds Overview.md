# Salesforce Clouds Overview

## What a "cloud" actually is

Salesforce sells products with cloud names, and the naming hides an important technical fact: some of them are the same system with different features switched on, and some are entirely separate platforms that happen to be owned by the same company.

Knowing which is which tells you whether two things share a database or need an integration. That is the single most useful thing in this note.

## The ones that share the core platform

These run on the Lightning Platform. Same database, same objects, same Apex runtime, same sharing model. Data flows between them with no integration at all.

**Sales Cloud.** Pipeline management. Lead, Account, Contact, Opportunity, Quote, Campaign, Forecast, Product, Price Book. The original product. Section 04.

**Service Cloud.** Customer support. Case, Entitlement, Knowledge, Omni-Channel routing, Service Console. Built on the same records — a Case links to the same Account a sales rep works. Section 05.

**Experience Cloud** (formerly Community Cloud). Externally facing sites — customer portals, partner portals, help centres — running on your org's data with restricted external user access. Not a separate system; a different front door onto the same records. See [[17.9 - Experience Cloud Basics]].

**Field Service.** Work orders, service appointments, scheduling optimization, a mobile app for technicians. An add-on on top of Service Cloud. See [[05.13 - Field Service Basics]].

**Revenue Cloud and CPQ** (Configure, Price, Quote). Complex product configuration, pricing rules, discount approval, subscriptions, and billing. Historically delivered as a managed package installed into your org, which is why its objects have a namespace prefix and its behaviour is partly opaque. Shares the platform but adds a substantial layer of its own. See [[04.10 - Products, Price Books and Pricing]].

**CRM Analytics** (formerly Tableau CRM, formerly Einstein Analytics). Advanced analytics with its own data layer built from replicated CRM data. Adjacent rather than fully shared: it reads from the core objects but stores its own datasets.

For everything in this list, a query like this simply works, with no synchronization involved:

```sql
SELECT Name,
       (SELECT StageName, Amount FROM Opportunities WHERE IsClosed = false),
       (SELECT Subject, Status FROM Cases WHERE IsEscalated = true)
FROM Account
WHERE Id = :accountId
```

## The ones that are separate platforms

These are Salesforce products in name and branding, but technically distinct systems. Moving data between them and your org requires integration.

**Marketing Cloud Engagement** (formerly ExactTarget). Email, SMS, mobile push, and multi-step customer journeys at very high volume. Completely different architecture: its own data model built on Data Extensions rather than objects, its own scripting languages (AMPscript and SSJS), its own APIs, its own user administration. Connecting it to your CRM org is a real integration project, usually via Marketing Cloud Connect or the APIs.

**Marketing Cloud Account Engagement** (formerly Pardot). Business-to-business marketing automation — lead nurturing, scoring, landing pages. Also a separate system, but with a much tighter native connector to Sales Cloud that syncs Leads and Contacts. Still a sync, with all the latency and conflict problems syncs have.

**Commerce Cloud** (formerly Demandware). Ecommerce storefronts. A separate platform with its own data model and its own development approach.

**MuleSoft.** Integration middleware, and a genuinely separate product. Not where your CRM data lives; where the pipes between systems are built and managed. See [[13.18 - MuleSoft and Middleware Basics]].

**Tableau.** Business intelligence and visualization. Separate product, connects to many data sources including Salesforce.

**Slack.** Owned by Salesforce, integrates with the platform, but obviously its own system.

**Heroku.** A general-purpose platform-as-a-service. Useful precisely because it has none of Salesforce's runtime limits. See [[01.2 - SaaS vs PaaS vs IaaS]].

## The newer layer

**Data Cloud** (formerly Customer Data Platform, formerly Genie). A large-scale data platform that ingests data from many systems, harmonizes it into a common model, and resolves identities so that one human being scattered across five systems becomes one unified profile. Increasingly the foundation for personalization and for grounding AI features in real customer data. Not a normal Salesforce object model — it has its own data model and its own scale characteristics. See [[24.2 - Data Cloud Fundamentals]].

**Agentforce.** The framework for building AI agents that can take actions on CRM data, using topics and actions rather than hand-written conversation flows. See [[24.4 - Agentforce Fundamentals]].

**Einstein.** The umbrella name for predictive and generative features embedded in the clouds — lead scoring, case classification, reply drafting, forecast prediction. See [[24.1 - Einstein Platform Overview]].

**Industry Clouds** (Financial Services, Health, Nonprofit, Automotive, Energy, and others). Pre-built data models and processes for a specific industry, delivered as managed packages on the core platform. They add objects like `FinancialAccount` or `CarePlan` and their own automation. Working in one means learning its conventions on top of the standard platform, and being careful not to duplicate what the package already provides.

## Why this matters to your design

**Cross-cloud reporting is easy inside the platform and hard outside it.** A report combining Opportunities and Cases is trivial. A report combining Opportunities and Marketing Cloud email engagement requires data to be brought into the org first, or assembled in a warehouse. When a stakeholder asks for a "single view", the first question is which of these two situations you are in.

**"Which cloud is this?" determines your skill needs.** A Marketing Cloud developer and a Sales Cloud developer share almost no technical skills beyond general programming. Nothing in this course transfers to AMPscript.

**Managed-package clouds behave differently from native ones.** CPQ and the industry clouds install as packages, which means namespaced objects, code you cannot read, upgrade cycles you do not control, and automation you must design around rather than modify. Discovering that a package trigger already fires on Opportunity, after you have built your own, is a familiar and painful moment.

**Do not build what a cloud already provides.** Reimplementing case routing, quoting, or field scheduling on custom objects is a well-trodden road to a system nobody can maintain. The licensing conversation ([[01.4 - Salesforce Editions and Licensing]]) is usually cheaper than the build.

## Scope of this course

This course covers the Lightning Platform, Sales Cloud, and Service Cloud in depth, plus the integration patterns you need to connect to everything else. Marketing Cloud, Commerce Cloud, and Tableau are named where they touch your work and otherwise left alone — they are separate disciplines, and pretending otherwise would produce shallow coverage of all three.
