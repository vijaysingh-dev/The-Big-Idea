# HTTP/3 and QUIC

#backend #http #protocols #quic

> **In one line:** QUIC is TCP rebuilt in userspace on top of UDP, with encryption built in and ordering applied per stream instead of per connection — which removes the one flaw HTTP/2 could not fix.

---

## The Idea

HTTP/2 solved application-level queueing and then hit a wall it could not climb: **TCP delivers bytes in order, so one lost packet stalls every stream** ([[02.5 - Head of Line Blocking]]).

You cannot fix that in HTTP. You have to replace the transport. But TCP is implemented in kernels and middleboxes worldwide — a genuinely new transport protocol would be blocked everywhere.

So QUIC is built on UDP, which passes through existing infrastructure, and reimplements everything TCP provides in userspace:

| TCP gives you | QUIC reimplements it |
|---|---|
| Reliable delivery | Yes, per stream |
| Ordering | Yes, **per stream, not per connection** |
| Congestion control | Yes, in userspace (CUBIC or BBR) |
| Flow control | Yes, two levels |
| Connection setup | Yes, merged with TLS |

Plus three things TCP cannot do: **encryption of almost everything including headers**, **connection migration across network changes**, and **rapid protocol evolution** because it lives in applications rather than kernels.

---

## Per-Stream Ordering

The central improvement.

```
TCP (HTTP/2):
  Stream 1: [1][2][3]
  Stream 3: [1][ ][3]    ← packet lost
  Stream 5: [1][2][3]
  → ALL streams stall until the retransmission arrives

QUIC (HTTP/3):
  Stream 1: [1][2][3]    → delivered
  Stream 3: [1][ ][3]    → this stream waits
  Stream 5: [1][2][3]    → delivered
  → only stream 3 is affected
```

QUIC packets carry frames tagged with stream IDs. The receiver reassembles each stream independently. A gap in one stream's byte range does not block another's.

💡 **This is the entire reason HTTP/3 exists.** Everything else is a bonus. If you remember one thing from this note, it is that HTTP/3's advantage appears specifically under packet loss — and it is negligible on a clean network.

---

## Handshake

```
TCP + TLS 1.3:   1 RTT (TCP) + 1 RTT (TLS) = 2 RTT
QUIC:            1 RTT total
QUIC 0-RTT:      0 RTT for a resumed connection
```

QUIC merges the transport and cryptographic handshakes. There is no unencrypted QUIC — TLS 1.3 is part of the protocol, not a layer above it.

⚠️ **0-RTT data is replayable**, exactly as in TLS 1.3 ([[02.9 - TLS]]). Only idempotent requests may use it. QUIC implementations restrict this, but if you build on it, the constraint is yours to respect.

---

## Connection Migration

A TCP connection is identified by `(src IP, src port, dst IP, dst port)`. Change any one and the connection is dead.

```
Phone on WiFi:      10.0.1.5:51234  →  connection established
Walks outside:      100.64.2.9:33221 →  TCP connection dies, everything restarts
```

QUIC identifies a connection by a **connection ID** carried in the packet header.

```
Same connection ID → same connection, regardless of address
```

Your video call, download or streaming response survives the network change with no interruption.

💡 **For mobile clients this is significant and it is not achievable any other way.** The alternative is application-level reconnection with resume logic, which every mobile app hand-rolls badly. QUIC gets it right at the transport layer.

⚠️ Migration has a privacy implication: a passive observer could link your old and new addresses via the connection ID. QUIC addresses this by having each side offer multiple connection IDs and rotating them on migration.

---

## What Is Encrypted

```
TCP:   IP header | TCP header (plaintext) | TLS record (encrypted)
QUIC:  IP header | UDP header | QUIC header (mostly encrypted) | payload
```

QUIC encrypts almost everything, including packet numbers and most header fields. Only what a router strictly needs is visible.

Consequences:

| Effect | Meaning |
|---|---|
| Middleboxes cannot inspect or modify | No more "helpful" TCP optimisers breaking things |
| Protocol can evolve freely | No ossification — nothing in the middle depends on the format |
| Network operators lose visibility | Some organisations block QUIC for this reason |
| Debugging is harder | You cannot `tcpdump` and read it |

⚠️ **The debugging point is practical.** You need `SSLKEYLOGFILE` and Wireshark's QUIC dissector, or `qlog` output from the implementation. There is no equivalent of reading plaintext HTTP/1.1 off the wire.

**qlog** is the standard structured logging format for QUIC, and it is the main reason QUIC debugging is tractable at all. Tools like `qvis` render qlog files into timelines showing every stream, loss event and congestion window change. If you work with QUIC seriously, learn qlog before anything else.

## HTTP/3 on Top

HTTP/3 is HTTP semantics mapped onto QUIC streams.

```
One QUIC stream per request/response pair
```

Differences from HTTP/2:

| | HTTP/2 | HTTP/3 |
|---|---|---|
| Header compression | HPACK | **QPACK** |
| Flow control | HTTP-level | QUIC-level (already there) |
| Stream multiplexing | HTTP-level | QUIC-level |
| Server push | Defined, dead | Removed |
| Priority | `PRIORITY` frames, deprecated | Extensible Priorities (RFC 9218) |

### QPACK — HPACK that tolerates reordering

HPACK's dynamic table assumes headers arrive in order. With QUIC's independent streams, they do not.

If stream 5 references a dynamic table entry created by stream 3, and stream 3's packet is lost, stream 5 cannot decode.

QPACK solves this with separate unidirectional streams for table updates and an explicit blocking mechanism: a request can indicate it depends on table state, and the decoder waits only if necessary.

💡 **QPACK is a good illustration of what happens when you remove a global ordering guarantee** — every stateful mechanism above it needs redesigning. Worth understanding as a general lesson, not just a QUIC detail.

## Discovery: Alt-Svc

There is no way to know a server speaks HTTP/3 before connecting, since UDP has no equivalent of ALPN over a handshake you have already begun.

So the first connection uses HTTP/1.1 or HTTP/2, and the server advertises:

```http
Alt-Svc: h3=":443"; ma=86400
```

The client remembers this and uses HTTP/3 next time. It also races both in parallel on subsequent connections, falling back if UDP is blocked.

⚠️ **This means the first request from a client never uses HTTP/3.** Benchmarks that measure a single cold request will show no HTTP/3 benefit at all. `HTTPS` DNS records (RFC 9460) can advertise HTTP/3 support before the first connection, which fixes this, but support is still rolling out.

## In Production

### When HTTP/3 actually helps

| Situation | Verdict |
|---|---|
| Mobile clients | **Clear win.** Loss tolerance plus migration |
| Lossy WiFi | **Clear win** |
| High-latency links | Win — fewer handshake round trips |
| Clean datacentre network | **Negligible.** Sometimes slower due to userspace overhead |
| Internal service-to-service | Usually not worth it |
| Networks blocking UDP | Fails, falls back |

💡 **The honest summary: HTTP/3 is for the public internet and mobile clients. For internal traffic, HTTP/2 is fine and simpler.** Adopting HTTP/3 between your own services in a datacentre is almost always premature — you get the operational complexity without the loss conditions that justify it.

### The CPU cost

TCP runs in the kernel with decades of optimisation, hardware offload for checksums and segmentation, and zero-copy paths. QUIC runs in userspace.

```
Rough figures: QUIC costs 2–3× the CPU per byte compared to TCP
```

This is improving — UDP GSO/GRO offload, and eventually kernel QUIC — but it is real today. At CDN scale it matters enormously; at typical service scale it does not.

⚠️ **Measure before adopting.** "Newer protocol" is not a reason. The reason is your loss profile.

### Deployment

You almost certainly do not implement HTTP/3 yourself. You enable it at the edge:

```nginx
# nginx 1.25+
listen 443 quic reuseport;
listen 443 ssl;
http2 on;
add_header Alt-Svc 'h3=":443"; ma=86400' always;
```

```caddy
# Caddy enables HTTP/3 automatically
```

Cloudflare, Fastly and the major cloud load balancers support it with a toggle. Your origin continues speaking HTTP/1.1 or HTTP/2 and never knows.

**Requirements people miss:**

- UDP port 443 must be open **inbound** in your firewall and security groups
- Your load balancer must support UDP, which not all do
- Anycast plus connection migration needs care — a migrated connection may land on a different edge node, which needs connection ID routing

### Debugging

```bash
curl --http3 https://cloudflare-quic.com/
curl -w '%{http_version}\n' --http3 -o /dev/null -s https://example.com/

# Did Alt-Svc get advertised?
curl -I https://example.com | grep -i alt-svc
```

For anything deeper, use qlog:

```python
# aioquic supports qlog output
QuicConfiguration(quic_logger=QuicFileLogger("./qlog"))
```

Then load the file into [qvis](https://qvis.quictools.info/) for a visual timeline. **This is genuinely the only practical way to debug QUIC performance**, and it is far better than what TCP offers — you get every congestion event and stream state change in one view.

### Python support

| Library | Status |
|---|---|
| `aioquic` | The reference Python implementation. Solid, used for testing |
| `httpx` | No HTTP/3 support |
| `aiohttp` | No HTTP/3 support |
| Hypercorn | Experimental HTTP/3 via aioquic |

⚠️ **Python's HTTP/3 story is weak.** For a Python backend, the realistic answer is HTTP/3 at the edge and HTTP/1.1 or HTTP/2 to your application. That is not a limitation in practice — it is the recommended architecture anyway.

## Codebase

**Repo:** `aiquic/aioquic`, `quic-go/quic-go`, `cloudflare/quiche`

**Question to answer:** Find the code that reassembles a stream's bytes independently of other streams — the mechanism that eliminates head-of-line blocking. Then: how does connection migration work? What happens when a packet arrives from a new address with a known connection ID, and how is that prevented from being an address-spoofing attack?

**Read, in order:**

1. `aioquic/src/aioquic/quic/connection.py` — **start here, it is Python.** Find `_handle_stream_frame` and see how frames are dispatched to per-stream buffers
2. `aioquic/src/aioquic/quic/stream.py` — the per-stream receive buffer and reassembly. **This is the answer to the first question**, and it is a small amount of readable code for such a significant idea
3. `aioquic/src/aioquic/quic/recovery.py` — loss detection and congestion control in userspace. Compare with the kernel version from [[02.4 - Flow Control and Congestion Control]]
4. `quic-go/connection.go` — search for path validation and connection ID handling. **The migration answer:** QUIC requires path validation — a `PATH_CHALLENGE`/`PATH_RESPONSE` exchange — before sending significant data to a new address, which prevents using migration to flood a third party
5. `cloudflare/quiche` — read the README and the qlog integration. Cloudflare runs this at enormous scale

💡 The path validation detail in part four is worth internalising. **Connection migration without it would be an amplification attack primitive** — spoof a victim's address, claim migration, and the server floods them. The designers had to add a challenge-response specifically to prevent it. That is a good example of how transport protocol design is largely defensive.

**Size:** 2 sessions.

## Exercise

**Drill 3.9 — Prove where HTTP/3 wins**

The point of this drill is to establish, with your own numbers, exactly when HTTP/3 is worth it — and when it is not.

```
drills/03-http3/
├── setup/
│   ├── caddy/            # HTTP/1.1, 2 and 3 from one server
│   ├── compose.yml
│   └── verify.sh
├── comparison/
│   ├── matrix.py         # h1 × h2 × h3, loss × RTT
│   ├── PLOT.md
│   └── RESULTS.md
├── migration/
│   ├── switch_network.sh # change the client's address mid-transfer
│   ├── tcp_behaviour.md
│   └── quic_behaviour.md
├── handshake/
│   └── rtt_count.py      # count round trips to first byte
├── qlog/
│   ├── capture.py        # aioquic with qlog enabled
│   └── ANALYSIS.md       # read it in qvis
├── cost/
│   └── cpu.py            # CPU per byte, h2 vs h3
└── README.md
```

**Part 1 — The matrix.** Caddy serving over HTTP/1.1, HTTP/2 and HTTP/3. A realistic workload: 50 requests of mixed sizes, as a page load would produce.

Sweep with `tc netem`:
- Loss: 0%, 0.5%, 1%, 2%, 5%
- RTT: 20ms, 100ms, 300ms

Fifteen cells × three protocols. Measure total completion time and p99 per-request latency.

**Chart it.** You are looking for the region where HTTP/3 pulls ahead. **Predict where that boundary is before you run it**, then compare.

The expected result: near-identical at 0% loss, HTTP/3 clearly ahead above ~1% loss, and the gap widening with RTT.

**Part 2 — Connection migration.** Start a large download. Mid-transfer, change the client's source address — a second network namespace, or a NAT rule change.

Over TCP: the connection dies. Record what the client sees and how long recovery takes with application-level resume.

Over QUIC: it should continue uninterrupted. Capture the `PATH_CHALLENGE`/`PATH_RESPONSE` exchange in the qlog.

**This is the demonstration that has no TCP equivalent**, and it is the most memorable part of the drill.

**Part 3 — Count the round trips.** Time-to-first-byte for a cold connection over HTTP/2-over-TLS and HTTP/3, at 20ms, 100ms and 300ms RTT.

Confirm the 2-RTT versus 1-RTT difference shows up as expected. Then test 0-RTT resumption and confirm it disappears entirely.

Then measure something people miss: **the very first request from a fresh client**, which must use HTTP/2 and discover `Alt-Svc`. Show that HTTP/3 provides no benefit at all on a genuinely cold first visit.

**Part 4 — Read a qlog.** Run a transfer with `aioquic` and qlog enabled, under 2% loss. Load the qlog into qvis.

Identify visually: the handshake, the congestion window growth, each loss event and recovery, and per-stream progress.

Write in `ANALYSIS.md` three things the qlog showed you that you could not have seen from `tcpdump` of an equivalent TCP connection. **This is the argument for qlog** and it is a genuinely better debugging story than TCP has.

**Part 5 — The CPU cost.** Transfer 1GB over HTTP/2 and HTTP/3 on a clean local network. Measure CPU time on both the server and client, per byte transferred.

Report the ratio. Then compute: at what request rate does the CPU cost outweigh the loss-tolerance benefit for a network with 0.1% loss? **This is the actual adoption calculation** and having done it once means you can answer the question properly rather than by reputation.

**Part 6 — Blocked UDP.** Firewall outbound UDP 443. Confirm the client falls back to HTTP/2 and measure how long the fallback takes.

Then confirm the `Alt-Svc` cache does not cause repeated failed attempts.

**Done when:**
- Your 15-cell matrix chart shows the crossover region clearly
- You can state the loss rate above which HTTP/3 wins on your setup
- You have demonstrated connection migration surviving a network change
- Your qlog analysis names three things TCP tooling cannot show you
- You have a CPU-cost ratio and an adoption threshold
- Fallback on blocked UDP is measured, not assumed
