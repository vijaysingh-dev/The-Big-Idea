# null vs undefined

Two ways to represent "no value", which is one more than most languages have. The distinction is about **intent**.

- **`undefined`** — the language's default absence. Nobody set this.
- **`null`** — a deliberate absence. Someone set this to nothing.

## Where undefined appears on its own

```js
let x;                     // declared, never assigned
obj.missingKey;            // property does not exist
function f(a) { }
f();                       // a is undefined
function g() {}
g();                       // returns undefined
[1, 2].find(n => n > 5);   // no match
arr[99];                   // out of range
```

The engine produces `undefined` in all of these. You never had to write it.

## Where null appears

`null` only exists because someone wrote it — you, a library, or an API. The DOM is the main built-in producer:

```js
document.querySelector(".missing");  // null
regex.exec("no match");              // null
JSON.parse("null");                  // null
```

Note the DOM's inconsistency: `querySelector` returns `null`, but `querySelectorAll` returns an empty `NodeList`, and `getElementById` returns `null`. There is no unifying rule; it has to be learned per API.

## Behavioral differences

```js
typeof undefined;   // "undefined"
typeof null;        // "object"  — the historical bug

null == undefined;  // true
null === undefined; // false

Number(null);       // 0
Number(undefined);  // NaN

null + 1;           // 1
undefined + 1;      // NaN

JSON.stringify({ a: null, b: undefined });  // '{"a":null}'
JSON.stringify([null, undefined]);          // '[null,null]'
```

Two of these matter constantly.

**JSON drops `undefined` object properties but converts `undefined` array elements to `null`.** So a round-trip through the network silently changes shape:

```js
const before = { a: undefined, b: [undefined] };
JSON.parse(JSON.stringify(before)); // { b: [null] }
```

**Default parameters trigger on `undefined` only:**

```js
function f(x = 10) { return x; }
f();          // 10
f(undefined); // 10
f(null);      // null — the default does NOT apply
```

The same rule governs destructuring defaults ([[05.5 - Destructuring]]). This is the single most practically important difference between the two values.

## Checking for either

```js
if (value == null) { }              // true for null and undefined only
if (value === null || value === undefined) { }  // explicit equivalent
if (value ?? fallback) { }          // nullish coalescing — see 05.7
value?.property;                    // optional chaining — see 05.7
```

The `== null` idiom is the one sanctioned use of loose equality, because `null` and `undefined` are loosely equal to each other and to nothing else ([[05.3 - Types Coercion and Equality]]).

Avoid truthiness checks when `0` or `""` are valid:

```js
if (!count) {}          // wrong — fires on 0
if (count == null) {}   // right
```

## API design: which to use

There is no universal answer, but there are defensible positions.

**Prefer `undefined` for "not provided", `null` for "explicitly empty".** This maps cleanly onto HTTP PATCH semantics: omitting a field means "leave it alone", sending `null` means "clear it".

```js
// PATCH /users/1
{ "nickname": null }   // remove the nickname
{ }                    // leave the nickname unchanged
```

If your API cannot distinguish these, partial updates become ambiguous.

**Some teams ban `null` entirely** (the TypeScript codebase does this) and use only `undefined`, on the grounds that two absence values create pointless branching. That is a coherent position provided you normalize at the boundary, since JSON APIs will send you `null` regardless.

**Databases produce `null`.** SQL `NULL` serializes to JSON `null`, so any data coming from a backend will contain it. Normalizing incoming `null` to `undefined` at the parse layer is a reasonable policy — just do it in one place.

## TypeScript

```ts
type A = string | null;
type B = string | undefined;
type C = string | null | undefined;

function f(x?: string) {}        // string | undefined
function g(x: string | null) {}  // must pass null explicitly
```

With `strictNullChecks` on, these are distinct types and the compiler forces you to handle each. An optional parameter (`x?`) means `string | undefined` and cannot accept `null` — a common source of confusion when consuming an API that returns `null` ([[25.6 - Discriminated Unions and Narrowing]]).

## React specifics

```jsx
{null}       // renders nothing
{undefined}  // renders nothing
{false}      // renders nothing
{0}          // renders "0"  — the classic bug

{items.length && <List />}   // renders "0" when empty
{items.length > 0 && <List />} // correct
```

`0` being renderable while `null`/`undefined`/`false` are not is behind one of the most common React display bugs ([[16.7 - Conditional Rendering and Composition]]).

## How senior engineers actually use this

**They normalize at the boundary.** One parse layer decides the codebase's convention, so internal code checks one thing rather than two.

**They use `null` as an explicit "loaded but empty" state.** `undefined` means "not fetched yet", `null` means "fetched, nothing there" — a useful two-bit state machine that avoids a separate `hasLoaded` flag.

**They avoid returning `null` from functions where an empty array or object would do.** Returning `[]` instead of `null` from a list-fetching function removes a null check at every call site.

**They watch defaults carefully.** Passing `null` where a default was expected is a frequent bug when data flows from a database through an API into a component with default props.

## Common pitfalls

- Expecting a default parameter to apply to `null`.
- `typeof null === "object"` breaking a naive type check.
- `undefined` properties vanishing through JSON while `undefined` array elements become `null`.
- Truthiness checks that reject `0` and `""`.
- Mixing both conventions in one codebase so every check needs `== null` anyway.
- In React, `{0 && ...}` rendering a stray zero.

## Interview angle

"Difference between `null` and `undefined`" wants intent first — engine-assigned absence versus developer-assigned absence — then the concrete behavioral differences: `typeof`, `Number()` coercion, JSON handling, and default-parameter triggering. The default-parameter point is the one that most clearly demonstrates you have hit this in real code.
